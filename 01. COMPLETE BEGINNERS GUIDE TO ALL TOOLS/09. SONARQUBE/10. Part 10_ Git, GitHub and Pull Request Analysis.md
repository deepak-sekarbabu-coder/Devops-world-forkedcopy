# Part 10: Git, GitHub and Pull Request Analysis

## Bring SonarQube Into the Developer Workflow

In the previous parts, you built several pieces of the SonarQube workflow.

You learned:

```text
Source Code
    ↓
Quality Profile
    ↓
Active Rules
    ↓
Analysis
    ↓
Issues
```

Then:

```text
Analysis Results
    ↓
Quality Gate
    ↓
PASS / FAIL
```

Then:

```text
Application
    ↓
Unit Tests
    ↓
Coverage Tool
    ↓
Coverage Report
    ↓
SonarScanner
    ↓
SonarQube
```

Now we need to connect those ideas to the way developers actually work.

Most production teams do not manually copy application folders to a SonarQube server and click a button after every code change.

They work through:

```text
Git
↓
Branches
↓
Remote Repository
↓
Pull Requests
↓
CI/CD
```

SonarQube must therefore become part of that workflow.

The architecture for this part is:

```text
Developer
    ↓
Feature Branch
    ↓
GitHub
    ↓
Pull Request
    ↓
SonarQube Analysis
    ↓
Quality Gate
   ↙          ↘
Merge         Fix
```

This is one of the most important stages in learning SonarQube because it changes SonarQube from:

```text
A dashboard engineers occasionally visit
```

into:

```text
A normal part of the code review and delivery process
```

---

# 1. The Problem We Are Solving

Imagine five developers are working on the same application.

Developer A changes authentication.

Developer B changes payment processing.

Developer C modifies database logic.

Developer D updates the frontend.

Developer E fixes a production bug.

If everyone edits the same copy of the application directly, chaos follows.

You need a system that tracks:

```text
Who changed what

When they changed it

Why they changed it

Which version is current

Which changes are ready

Which changes are not ready
```

Git solves this problem.

Then GitHub adds collaboration around Git.

Then pull requests provide a controlled review point.

Then SonarQube provides automated quality analysis before the change is merged.

The full idea becomes:

```text
Developer Change
       ↓
Git Tracks Change
       ↓
GitHub Hosts Repository
       ↓
Pull Request Proposes Change
       ↓
SonarQube Evaluates Change
       ↓
Quality Gate Decides
       ↓
Merge or Remediate
```

---

# 2. What Is Git?

Git is a distributed version-control system.

At beginner level, think:

```text
Git
=
A system for tracking changes to files over time
```

Instead of having:

```text
project-final

project-final2

project-final-final

project-final-real

project-final-real2
```

Git records versions systematically.

---

# 3. Git Tracks History

Suppose:

```text
Monday:
app.py version A

Tuesday:
app.py version B

Wednesday:
app.py version C
```

Git can preserve the history of those changes.

Conceptually:

```text
Commit A
   ↓
Commit B
   ↓
Commit C
```

Each commit represents a recorded state/change in the repository.

---

# 4. What Is a Git Repository?

A **repository**, often shortened to **repo**, is a project directory managed by Git.

Example:

```text
payment-service/
├── .git/
├── src/
├── tests/
├── README.md
└── sonar-project.properties
```

The hidden:

```text
.git/
```

directory contains Git metadata.

That metadata is extremely important.

It contains information about:

```text
Branches

Commits

References

History

Remote configuration
```

SonarQube pull-request analysis relies on valid repository information during CI analysis.

---

# 5. Local Repository vs Remote Repository

A developer might have:

```text
Laptop
  ↓
Local Git Repository
```

GitHub hosts:

```text
Remote Repository
```

Architecture:

```text
Developer Laptop
      ↓
Local Git Repository
      ↓
git push
      ↓
GitHub Repository
```

Git is the version-control technology.

GitHub is a hosted collaboration platform built around Git repositories.

They are related but not identical.

---

# 6. Git vs GitHub

Remember:

```text
Git
=

```

```text
GitHub

```

You can use Git without GitHub.

You can host Git repositories on other systems.

But GitHub is one of the most common platforms.

# 9. What Is a Branch?

A branch is an independent line of development in Git.

Suppose:

```text
main
```

contains production-ready code.

A developer wants to build a new login feature.

Instead of directly changing:

```text
main
```

they create:

```text
feature/login
```

Architecture:

```text
main
  │
  ├── Commit A
  ├── Commit B
  │
  └──────── feature/login
               │
               ├── Commit C
               └── Commit D
```

The feature work is isolated from main.

---

# 10. Why Branches Matter

Branches allow developers to work without immediately modifying the stable branch.

This provides:

```text
Isolation

Parallel development

Code review

Testing

CI validation

Safe experimentation
```

A developer can make several commits before asking for the branch to be merged.

---

# 11. Main Branch

The central branch is commonly called:

```text
main
```

Older repositories may use:

```text
master
```

Other organizations may use:

```text
develop
```

or another convention.

In SonarQube, one branch is treated as the project's main branch.

Conceptually:

```text
main
=
Primary project branch
```

---

# 12. Feature Branch

A feature branch is created for a specific piece of work.

Examples:

```text
feature/payment-validation

feature/user-profile

feature/search

fix/login-timeout

bugfix/cart-total

hotfix/payment-error
```

Naming conventions vary.

The important principle is isolation.

# 19. GitHub Repository State

Now:

```text
GitHub Repository
```

# 20. What Is a Pull Request?

A **pull request**, usually shortened to **PR**, is a request to merge changes from one branch into another.

Example:

```text
Source Branch:
feature/payment-validation

Target Branch:
main
```

Meaning:

> Please review the changes in feature/payment-validation and consider merging them into main.

---

# 21. Pull Request Architecture

```text
feature/payment-validation
        ↓
Pull Request
        ↓
main
```

The PR creates a review boundary before integration.

---

# 22. What Happens in a Pull Request?

A PR may include:

```text
Code changes

Commit history

Comments

Human reviews

CI checks

Unit-test results

Security checks

SonarQube Quality Gate results
```

That makes the PR an excellent enforcement point.

---

# 23. Why Analyze Pull Requests?

Suppose SonarQube only analyzes main after merge.

Workflow:

```text
Developer
    ↓
Bad Code
    ↓
Merge to main
    ↓
SonarQube
    ↓
Problem Discovered
```

The code is already merged.

Better:

```text
Developer
    ↓
Feature Branch
    ↓
Pull Request
    ↓
SonarQube
    ↓
Problem Discovered
    ↓
Fix Before Merge
```

Earlier feedback is safer.

---

# 24. Pull Request Analysis Goal

The main question becomes:

> Is the change introduced by this pull request clean enough to merge?

This matches Clean as You Code perfectly.

Instead of asking:

```text
Is this entire 10-year-old application perfect?
```

ask:

```text
Is this proposed change acceptable?
```

---

```text

```

It contains the proposed changes.

# 26. Pull Request Target Branch

Imagine:

```text

```

This is the target branch.

The developer wants the feature branch merged into main.

Architecture:

```text

          ↓
```

# 27. Changed Code

The feature branch may differ from main.

Example:

```text
main:

payment.py
version A
```

Feature branch:

```text
payment.py
version B
```

The difference between them represents the proposed change.

Conceptually:

```text
Feature Branch
    -
Target Branch
    =
Changed Code
```

---

# 28. Why Changed Code Matters

A PR may contain:

```text
10 changed lines
```

inside a repository containing:

```text
2,000,000 lines
```

The developer should receive feedback focused primarily on those changes.

That makes code review practical.

---

# 29. Changed Code vs New Code

These ideas are related but should not be confused.

**Changed code** usually means the code differences introduced by the current change.

**New code** is SonarQube's broader quality concept for recently added or modified code according to the configured definition.

For PR analysis, the relevant new-code scope is naturally tied closely to the change introduced by the pull request.

# 51. Example Remediation

Developer introduces:

```python
def discount(price, percentage):
    unused = 100
    return price - (price * percentage / 100)
```

SonarQube reports a maintainability issue.

Developer removes:

```python
unused = 100
```

Then:

```bash
git add src/pricing.py
git commit -m "Remove unused pricing variable"
git push
```

The same PR is updated.

CI runs again.

SonarQube analyzes again.

```text

↓

```

# 61. Git Metadata Requirement

PR analysis depends heavily on repository context.

The CI checkout should retain:

```text
.git/
```

If CI copies only source files:

```text
src/
tests/
```

and deletes:

```text
.git/
```

SonarQube loses important Git context.

This can break or degrade pull-request analysis.

---

# 62. Why `.git` Matters

The repository metadata helps establish:

```text
Commit history

Branches

References

Changed files

Repository relationships
```

PR analysis is not simply:

```text
Scan this random directory.
```

It is:

```text
Analyze this repository change
in relation to another branch.
```

---

# 63. Target Branch Must Be Available

Suppose PR is:

```text
feature/payment
    ↓
main
```

CI checks out only:

```text
feature/payment
```

with insufficient target-branch history.

SonarQube may not have enough information for correct comparison.

The target branch must be fetched and available appropriately.

---

# 64. Shallow Clone Problems

CI systems often optimize checkout using limited Git history.

Example:

```text
Only latest commit downloaded
```

This is called a shallow clone.

It saves time.

But analysis tools sometimes need additional history.

If PR analysis behaves strangely, investigate checkout depth.

---

# 65. Do Not Randomly Disable Shallow Clone Everywhere

First understand the requirement.

Ask:

```text
Does this CI checkout include required target history?

Can SonarQube identify merge base?

Do scanner logs complain about SCM information?
```

Then configure checkout depth appropriately.

Troubleshooting should be evidence-based.

---

# 66. CI Code Must Match Repository Code

During PR analysis, CI should analyze the actual code associated with the PR.

Avoid strange workflows such as:

```text
Checkout PR
↓
Modify source in CI
↓
Analyze different code
```

Then the analysis no longer accurately represents what is proposed for merge.

---

# 67. Avoid Pre-Merging Main Into the PR Workspace for Analysis

Some CI systems may create synthetic merge states.

Be careful.

PR analysis expects a valid repository state corresponding appropriately to the PR source and target relationship.

Do not manipulate the branch blindly before analysis.


# 72. Branch and PR Parameters Should Not Be Confused

Do not run:



Modern SonarQube-to-GitHub integrations may use a GitHub App.

Conceptually:

```text
SonarQube
    ↓
GitHub App Identity
    ↓
Authorized Repository Access
    ↓
PR Decoration / Repository Integration
```

This is preferable to sharing a developer's personal password.

# 75. Why Machine Identities Are Better

Bad:

```text
SonarQube uses Ann's personal GitHub password.
```

Problems:

```text
Password changes

Employee leaves

Account disabled

Excessive permissions

Poor auditability
```

Better:

```text
Dedicated application identity
```

with controlled permissions.

# 77. SonarQube Token


# 78. Keep Sonar Token Secret

Do not commit:

```text

```

into:

```text

```

Use:

```text

CI secret store

Environment injection
```

depending on your platform.

# 79. Example Secret Pattern

```text
No secret stored
```

GitHub Actions secret:

```text

```


The secret value remains in GitHub's secret-management system.

# 81. Least Privilege

The analysis identity should receive only permissions required for analysis.

Do not give CI:

```text

```

merely because it needs to scan a project.

Likewise, GitHub integration should receive only the permissions required for:

```text
Repository access

PR feedback

Status checks
```

according to your configuration.

# 82. Token Rotation

Production credentials should have lifecycle management.

Consider:

```text
Creation

Storage

Expiration

Rotation

Revocation

Audit
```

Do not create a token and forget it forever.

# 83. Token Revocation

If a token is exposed:

```text
Do not merely delete it from the latest commit.
```

Once a secret has entered Git history, assume compromise.

Steps:

```text
Revoke token
↓
Create replacement
↓
Update CI secret
↓
Remove secret from repository/history as appropriate
↓
Investigate exposure
```

# 84. GitHub Integration Permissions

For repository integration, SonarQube needs sufficient GitHub permissions to perform configured actions.

If permissions are too weak:

```text

```

If permissions are too broad:


Use the minimum documented permissions for the integration you actually need.
