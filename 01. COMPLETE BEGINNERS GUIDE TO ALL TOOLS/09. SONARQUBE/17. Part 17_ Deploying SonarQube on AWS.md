# Part 17: Deploying SonarQube on AWS

## Build a Realistic Cloud Environment Rather Than Leaving SonarQube on Localhost

In the earlier parts, we started SonarQube locally.

You may have accessed it using:

```text
http://localhost:9000
```

That was useful for learning.

But localhost is not a production architecture.

If SonarQube needs to support:

* developers
* CI/CD pipelines
* pull requests
* webhooks
* engineering teams
* centralized authentication
* production administration

then SonarQube must become a properly operated network service.

In this part, we will move from:

```text
Laptop
↓
localhost:9000
↓
SonarQube
```

to:

```text
Developer / CI
↓
DNS
↓
HTTPS / TLS
↓
Application Load Balancer
↓
Security Group
↓
SonarQube EC2
↓
Private Database / RDS
```

But we are going to build the architecture from the bottom up so that you understand why every AWS component exists.

---

# 1. What We Are Building

Our target architecture is:

```text
                         INTERNET / CORPORATE NETWORK
                                   │
                                   │
                         Developer / CI Runner
                                   │
                                   ↓
                          sonarqube.example.com
                                   │
                                   ↓
                               Route 53
                                   │
                                   ↓
                         Application Load Balancer
                              HTTPS :443
                                   │
                          ALB Security Group
                                   │
                                   ↓
                          SonarQube EC2 Instance
                              HTTP :9000
                                   │
                         EC2 Security Group
                                   │
                                   ↓
                          PostgreSQL on RDS
                             TCP :5432
                                   │
                          RDS Security Group
```

The major AWS services are:

```text
VPC
EC2
RDS
Application Load Balancer
Route 53
Certificate Manager
IAM
CloudWatch
Secrets Manager
EBS
Security Groups
```

You should not memorize this list.

You should understand what problem each component solves.

---

# 2. The Most Important Architectural Principle

Do not think:

```text
AWS SonarQube
=
Launch EC2
+
Install SonarQube
```

That only solves compute.

Production architecture also needs:

```text
Networking

Database

Storage

DNS

Encryption

Access Control

Secrets

Monitoring

Backups

Recovery

Operations
```

That is why the complete system matters.

---

# 3. What Is AWS?

AWS means:

```text
Amazon Web Services
```

AWS provides cloud infrastructure and managed services.

Instead of buying a physical server:

```text
Buy Hardware
↓
Rack Server
↓
Install Operating System
↓
Configure Network
```

you can provision infrastructure through AWS.

For our SonarQube environment, AWS will provide the infrastructure around SonarQube.

---

# 4. AWS Region

AWS infrastructure is divided geographically into Regions.

A Region is a geographical AWS deployment area.

Examples include regions in:

```text
United States

Europe

Asia

Africa

Latin America
```

A Region contains multiple Availability Zones.

Our SonarQube resources should normally be intentionally located within the same Region unless we are designing a specific cross-Region architecture.

---

# 5. Availability Zone

An Availability Zone, or AZ, is an isolated location within an AWS Region.

Conceptually:

```text
AWS Region
│
├── Availability Zone A
├── Availability Zone B
└── Availability Zone C
```

Multiple AZs help us design systems that are less dependent on one physical location.

---

# 6. Why Availability Zones Matter

Imagine everything exists in one location:

```text
AZ-A
│
├── SonarQube
└── Database
```

A serious AZ failure could affect everything.

A stronger database architecture may use:

```text
AZ-A
│
└── SonarQube

RDS Multi-AZ
│
├── Primary
└── Standby in another AZ
```

The exact RDS topology depends on the deployment option you select.

---

# 7. VPC

VPC means:

```text
Virtual Private Cloud
```

A VPC is your logically isolated network inside AWS.

Think:

```text
AWS
↓
Your Private Network
↓
Your Resources
```

Instead of putting resources randomly into AWS, you create network boundaries.

---

# 8. Example VPC

Suppose we create:

```text
VPC CIDR:
10.20.0.0/16
```

CIDR describes an IP address range.

For now, understand:

```text
10.20.0.0/16
```

provides an address space from which we can create smaller subnet networks.

---

# 9. Why SonarQube Needs a VPC

Our architecture contains resources that need controlled communication.

For example:

```text
ALB
↓
SonarQube EC2
↓
RDS
```

The VPC gives us the network in which these resources communicate.

---

# 10. Subnets

A subnet divides the VPC network into smaller networks.

Example:

```text
VPC
10.20.0.0/16

├── Public Subnet A
│   10.20.1.0/24
│
├── Public Subnet B
│   10.20.2.0/24
│
├── Private App Subnet A
│   10.20.11.0/24
│
├── Private App Subnet B
│   10.20.12.0/24
│
├── Private DB Subnet A
│   10.20.21.0/24
│
└── Private DB Subnet B
    10.20.22.0/24
```

These are example ranges.

Your organization may use a completely different addressing plan.

---

# 11. Public Subnet

A public subnet is generally a subnet whose route table provides a route toward an Internet Gateway.

A public subnet does not mean:

```text
Everything inside it is automatically exposed.
```

Exposure also depends on:

* public IP addressing
* route tables
* security groups
* network ACLs
* application listeners
* other network controls

---

# 12. Private Subnet

A private subnet does not have a direct route to an Internet Gateway.

Private subnets are useful for systems that should not receive direct Internet traffic.

Examples:

```text
Application servers

Internal services

Databases
```

---

# 13. Recommended SonarQube Layout

A stronger architecture is:

```text
PUBLIC SUBNETS

Application Load Balancer
```

then:

```text
PRIVATE APPLICATION SUBNET

SonarQube EC2
```

then:

```text
PRIVATE DATABASE SUBNETS

RDS PostgreSQL
```

Architecture:

```text
Internet
↓
Public ALB
↓
Private SonarQube
↓
Private RDS
```

This is preferable to exposing every component directly.

---

# 14. Why Use Multiple Public Subnets?

An internet-facing Application Load Balancer is normally configured across multiple Availability Zones.

Example:

```text
                 Application Load Balancer
                       /          \
                      /            \
                 Public A        Public B
                   AZ-A            AZ-B
```

This gives the load balancer presence across more than one Availability Zone.

---

# 15. Why Use Multiple Database Subnets?

RDS uses a DB subnet group.

The subnet group tells RDS which subnets it may use.

For a resilient architecture:

```text
DB Subnet Group
│
├── Private DB Subnet A
└── Private DB Subnet B
```

across multiple Availability Zones.

---

# 16. Internet Gateway

An Internet Gateway allows communication between a VPC and the Internet when routing and resource configuration permit it.

Conceptually:

```text
Internet
↓
Internet Gateway
↓
VPC
```

It is attached to the VPC.

---

# 17. Internet Gateway Does Not Automatically Expose Everything

Creating:

```text
Internet Gateway
```

does not mean:

```text
RDS is now public.
```

Network reachability depends on multiple layers.

Think:

```text
IP Address
+
Route
+
Security Rules
+
Listening Service
=
Possible Connectivity
```

---

# 18. Route Tables

A route table determines where network traffic should go.

Example public route:

```text
Destination      Target

10.20.0.0/16     local
0.0.0.0/0        Internet Gateway
```

Meaning:

```text
Traffic for VPC
→ remain inside VPC

Everything else
→ Internet Gateway
```

---

# 19. Private Route Table

A private database subnet might contain:

```text
Destination      Target

10.20.0.0/16     local
```

There is no direct:

```text
0.0.0.0/0 → Internet Gateway
```

route.

Therefore the database does not have a direct Internet path through that subnet.

---

# 20. NAT Concept

Private application servers may still need outbound Internet access.

For example:

```text
Operating system updates

Package downloads

External integrations
```

A common architecture uses a NAT mechanism for outbound Internet connectivity from private subnets.

Conceptually:

```text
Private EC2
↓
NAT
↓
Internet Gateway
↓
Internet
```

But Internet systems cannot use that path to initiate arbitrary inbound connections to the private EC2 instance.

---

# 21. NAT Is Not Required for Every Architecture

Do not automatically create NAT infrastructure because:

```text
Every architecture diagram has one.
```

Ask:

```text
Does this private workload need outbound Internet access?

Can VPC endpoints satisfy some dependencies?

What external systems must SonarQube reach?

What does the organization permit?
```

Architecture should follow requirements.

---

# 22. EC2

EC2 means:

```text
Elastic Compute Cloud
```

EC2 provides virtual machines.

Our SonarQube Server will run on an EC2 instance.

Architecture:

```text
EC2
↓
Linux
↓
JDK
↓
SonarQube Server
```

---

# 23. EC2 Is Not SonarQube

This distinction matters.

EC2 provides:

```text
CPU

Memory

Network

Virtual Machine

Storage attachment
```

SonarQube provides:

```text
Code analysis platform
```

Architecture:

```text
AWS EC2
└── Linux
    └── SonarQube
```

---

# 24. Choosing an EC2 Instance

Instance selection depends on:

```text
Project size

Lines of code

Analysis frequency

Number of users

Compute Engine workload

Search workload

Concurrent activity
```

Do not select an instance solely because:

```text
It is the cheapest.
```

SonarQube contains Java processes and Elasticsearch-based search components that require meaningful memory and operating-system resources.

---

# 25. SonarSource Reference Sizing

SonarSource provides reference architectures for different SonarQube sizes.

Treat them as:

```text
Starting architecture guidance
```

not:

```text
Universal sizing law.
```

Real environments must be monitored and resized according to workload.

---

# 26. SonarQube Linux Requirements

SonarQube includes Elasticsearch.

Therefore Linux host configuration matters.

Before installing SonarQube, verify required operating-system limits such as:

```bash
sysctl vm.max_map_count
sysctl fs.file-max
ulimit -n
ulimit -u
```

Do not simply install SonarQube and assume the operating system is ready.

---

# 27. Why These Limits Matter

Elasticsearch can use:

```text
Many memory mappings

Many file descriptors

Many threads
```

If Linux limits are too low:

```text
SonarQube
↓
Elasticsearch startup
↓
Failure
```

The symptom may look like:

```text
SonarQube won't start.
```

But the root cause is:

```text
Operating system configuration.
```

---

# 28. Java Requirements

Your SonarQube version determines the supported Java runtime requirements.

For SonarQube Server 2026.1 LTA, current requirements use a full JDK, with Java 21 as the minimum supported Java version.

Never install:

```text
whatever Java apt happens to give me
```

without checking your SonarQube version.

---

# 29. EC2 Operating System

A common deployment might use:

```text
Ubuntu Server
```

or another supported Linux distribution.

Architecture:

```text
EC2
↓
Ubuntu
↓
JDK
↓
SonarQube
```

---

# 30. Dedicated SonarQube User

Do not run SonarQube as:

```text
root
```

Create a dedicated operating-system identity.

Conceptually:

```text
sonarqube
```

The process should run with the permissions it actually needs.

This follows least privilege.

---

# 31. Persistent Storage

An EC2 instance has storage.

But production storage must be deliberately designed.

Important SonarQube data exists in places such as:

```text
Database

Configuration

Extensions/plugins

Logs

Search indexes
```

Not all of these have the same backup importance.

---

# 32. EBS

EBS means:

```text
Elastic Block Store
```

EBS provides block storage volumes that can be attached to EC2 instances.

Think:

```text
EC2
+
EBS Volume
=
Server + Persistent Block Storage
```

---

# 33. Root Volume

Your EC2 instance normally has a root EBS volume containing:

```text
Operating system

Installed software

Configuration
```

Do not size it so tightly that:

```text
Logs grow
↓
Disk reaches 100%
↓
SonarQube fails
```

---

# 34. Disk Space Matters

SonarQube needs free disk space for:

```text
Logs

Temporary files

Search indexes

Updates

Operational headroom
```

A disk at:

```text
99.9% full
```

is not healthy simply because it has not reached exactly 100%.

Monitor disk usage.

---

# 35. Database Is the Critical Persistent Data Store

A major beginner mistake is thinking:

```text
Everything important is stored in /opt/sonarqube.
```

The production database is critically important.

It stores SonarQube application data such as:

```text
Projects

Issues

Metrics

Configuration

Quality information
```

Therefore database backup is central to recovery.

---

# 36. PostgreSQL

PostgreSQL is a relational database management system.

SonarQube can use PostgreSQL as its external database.

Architecture:

```text
SonarQube
↓
JDBC
↓
PostgreSQL
```

---

# 37. Why Not H2?

SonarQube's embedded H2 database is appropriate for:

```text
Testing

Evaluation

Learning
```

not production.

Production should use a supported external database.

---

# 38. Amazon RDS

RDS means:

```text
Relational Database Service
```

RDS is AWS's managed relational database service.

Instead of manually operating PostgreSQL on another EC2 instance:

```text
EC2
↓
Install PostgreSQL
↓
Patch PostgreSQL
↓
Manage Backups
↓
Operate Database
```

we can use:

```text
Amazon RDS for PostgreSQL
```

AWS manages significant parts of the underlying database infrastructure.

You still remain responsible for correct configuration, security, capacity, monitoring and recovery planning.

---

# 39. RDS Is Not a Magic Database

Managed does not mean:

```text
No administration required.
```

You still need to manage:

```text
Engine version

Instance size

Storage

Security

Backups

Retention

Maintenance

Monitoring

Credentials

Connections

Recovery testing
```

---

# 40. Supported PostgreSQL Version

Always verify SonarQube's current database compatibility before creating RDS.

Do not choose:

```text
Newest PostgreSQL available in AWS
```

and assume SonarQube supports it.

Your SonarQube version and PostgreSQL version must be compatible.

---

# 41. Database Placement

The database should not be exposed to the public Internet.

Architecture:

```text
Private DB Subnets
↓
RDS PostgreSQL
```

Set:

```text
Publicly accessible:
No
```

for this architecture.

---

# 42. Database Connectivity

SonarQube connects to PostgreSQL using JDBC.

Conceptually:

```text
SonarQube EC2
↓
TCP 5432
↓
RDS PostgreSQL
```

The RDS endpoint may resemble:

```text
sonarqube-db.xxxxx.region.rds.amazonaws.com
```

Do not hard-code an RDS private IP address.

Use the provided database endpoint.

---

# 43. JDBC URL

Conceptually:

```text
jdbc:postgresql://DATABASE_ENDPOINT:5432/sonarqube
```

Example configuration concept:

```text
sonar.jdbc.url=jdbc:postgresql://DATABASE_ENDPOINT:5432/sonarqube
```

Then SonarQube also needs:

```text
Database username

Database password
```

---

# 44. Never Commit Database Credentials

Bad:

```text
sonar.jdbc.username=sonarqube
sonar.jdbc.password=MySuperSecretPassword123
```

committed to Git.

Do not store secrets in:

```text
Git repositories

README files

Terraform variables committed in plaintext

User-data scripts stored carelessly

CI logs
```

---

# 45. Security Groups

A security group acts as a stateful virtual firewall for AWS resources.

Security groups control:

```text
Inbound traffic

Outbound traffic
```

Our architecture should use separate groups for different trust boundaries.

---

# 46. Three Security Groups

Create conceptually:

```text
SG-ALB

SG-SONARQUBE

SG-RDS
```

Each has a specific purpose.

---

# 47. ALB Security Group

For an Internet-accessible SonarQube service, ALB rules might conceptually be:

```text
Inbound

HTTPS 443
Source: Approved networks
```

or, if intentionally public:

```text
HTTPS 443
Source: Internet
```

Whether SonarQube should be globally Internet-accessible is a security decision, not a default.

---

# 48. HTTP 80

If you allow HTTP port 80, use it deliberately.

One common pattern:

```text
HTTP :80
↓
Redirect
↓
HTTPS :443
```

Do not provide normal authenticated SonarQube sessions over plaintext HTTP across untrusted networks.

---

# 49. SonarQube EC2 Security Group

The EC2 instance should not accept port 9000 from:

```text
0.0.0.0/0
```

Instead:

```text
Inbound

TCP 9000
Source: SG-ALB
```

Meaning:

```text
Only traffic coming through resources associated with the ALB security group
```

can reach SonarQube's application port.

---

# 50. Security Group Referencing

This is powerful.

Instead of:

```text
Allow 10.20.1.50
```

you can conceptually say:

```text
Allow SG-ALB
```

Then the security relationship becomes:

```text
ALB Security Group
↓
SonarQube Security Group
```

---

# 51. RDS Security Group

The database should allow PostgreSQL only from SonarQube.

Conceptually:

```text
Inbound

TCP 5432
Source: SG-SONARQUBE
```

Not:

```text
TCP 5432
Source: 0.0.0.0/0
```

---

# 52. Complete Security Group Chain

```text
User / CI
     │
     │ HTTPS 443
     ↓
SG-ALB
     │
     │ HTTP 9000
     ↓
SG-SONARQUBE
     │
     │ PostgreSQL 5432
     ↓
SG-RDS
```

This is one of the most important diagrams in this part.

---

# 53. Why This Is Better

Suppose an attacker discovers the EC2 private IP.

The SonarQube security group still does not permit arbitrary Internet traffic directly to port 9000.

Suppose someone discovers the RDS endpoint.

The RDS security group does not permit arbitrary Internet traffic to 5432.

Security uses layers.

---

# 54. Application Load Balancer

ALB means:

```text
Application Load Balancer
```

An ALB operates at the application HTTP/HTTPS layer.

It receives client requests and forwards them to targets.

Our target is:

```text
SonarQube EC2
```

---

# 55. Why Put ALB in Front of SonarQube?

The ALB can provide:

```text
HTTPS listener

TLS termination

Stable AWS endpoint

Health checks

Security-group boundary

Future multi-target routing capabilities
```

It also prevents us from exposing SonarQube port 9000 directly as the normal public entry point.

---

# 56. ALB Architecture

```text
Developer
↓
HTTPS :443
↓
ALB
↓
HTTP :9000
↓
SonarQube
```

TLS terminates at the ALB in this design.

---

# 57. SonarQube and HTTPS

SonarQube itself receives HTTP traffic.

For production HTTPS, place a TLS-terminating proxy or equivalent infrastructure in front.

Our AWS ALB provides that function.

Therefore:

```text
Client
↓
HTTPS
↓
ALB
↓
HTTP
↓
SonarQube
```

can be a valid architecture inside the controlled VPC.

---

# 58. What Is TLS?

TLS means:

```text
Transport Layer Security
```

TLS protects data in transit.

HTTPS is HTTP carried over TLS.

Instead of:

```text
HTTP
```

we expose:

```text
HTTPS
```

to users and CI clients.

---

# 59. Why HTTPS Matters for SonarQube

SonarQube traffic may contain:

```text
Authentication sessions

API tokens

Analysis information

Project information

Administrative actions
```

Sending this over untrusted plaintext networks creates unnecessary risk.

---

# 60. AWS Certificate Manager

AWS Certificate Manager, or ACM, can manage TLS certificates used by supported AWS services such as an Application Load Balancer.

Architecture:

```text
ACM Certificate
↓

```

Conceptually:


# 63. Target Group

Our target group:

```text

```


# 64. Target Group Architecture

```text

↓
```

---

# 65. Health Checks

The ALB performs health checks against registered targets.

Conceptually:

```text
ALB
↓
Is SonarQube responding?
↓
YES
Target healthy

NO
Target unhealthy
```

Traffic is normally routed to healthy registered targets.

---

# 66. Health Check Is Not Full Monitoring

An ALB health check may tell you:

```text
HTTP endpoint responds.
```

It does not necessarily prove:

```text
Database healthy

Compute Engine healthy

Analysis queue healthy

Disk healthy

All plugins healthy

Every workflow healthy
```

Health checks are one layer of observability.

---

# 67. Single EC2 Limitation

If your architecture contains:

```text
1 SonarQube EC2
```

then the ALB does not magically make SonarQube highly available.

Architecture:

```text
ALB
↓
ONE EC2
```

If that EC2 instance fails:

```text
No healthy SonarQube target
```

The load balancer cannot invent another SonarQube server.

---

# 68. Load Balancer Is Not High Availability by Itself

This is a common beginner misunderstanding.

```text
ALB
≠
Automatically Highly Available Application
```

Application architecture determines application availability.

SonarQube Data Center Edition provides a different clustered architecture for environments requiring SonarQube application-layer high availability.

---


# 70. ALB as Our Front-End Proxy Layer

```text
ALB
```

# 71. When nginx Might Still Appear

```text

```

# 72. DNS

DNS means:

```text
Domain Name System
```

Humans prefer:

```text
sonarqube.example.com
```

instead of:

```text
internal-abc123.us-east-1.elb.amazonaws.com
```

DNS maps names to destinations.

---

# 73. Route 53

Amazon Route 53 is AWS's DNS service.

We can create a record such as:

```text
sonarqube.example.com
```

pointing to the ALB.

Architecture:

```text
sonarqube.example.com
↓
Route 53
↓
ALB
```

---

# 74. Route 53 Alias

Route 53 supports alias records pointing to Elastic Load Balancing resources.

Conceptually:

```text
sonarqube.example.com
↓
Alias
↓
Application Load Balancer
```

Do not point normal production DNS directly at the EC2 instance if the ALB is supposed to be the entry point.

---

# 75. Complete Request Flow

A developer opens:

```text
https://sonarqube.example.com
```

What happens?

```text
1. DNS lookup

2. Route 53 resolves the name toward ALB

3. Client connects to ALB on 443

4. TLS session established

5. ALB receives HTTP request inside TLS

6. ALB selects healthy target

7. ALB forwards request to EC2 port 9000

8. SonarQube processes request

9. SonarQube may query PostgreSQL

10. Response returns through ALB

11. Developer receives response
```

---

# 76. CI Request Flow

A CI runner may perform analysis:

```text
CI Runner
↓
https://sonarqube.example.com
↓
DNS
↓
ALB
↓
SonarQube
↓
Analysis accepted
```

The CI runner does not need direct access to:

```text
RDS
```

It only needs SonarQube.

---

# 77. Database Flow

When SonarQube needs database access:

```text
SonarQube EC2
↓
RDS endpoint
↓
TCP 5432
↓
PostgreSQL
```

The developer does not need direct database access.

The CI runner does not need direct database access.

The ALB does not need database access.

That is least privilege applied to networking.

---

# 78. Network Access Matrix

A useful design table is:

| Source                   | Destination  |       Port | Purpose               |
| ------------------------ | ------------ | ---------: | --------------------- |
| Approved user/CI network | ALB          |        443 | SonarQube HTTPS       |
| ALB SG                   | SonarQube SG |       9000 | Application traffic   |
| SonarQube SG             | RDS SG       |       5432 | PostgreSQL            |
| Admin channel            | EC2          | controlled | Server administration |

Everything else should require justification.

---

# 79. Administration Access

Do not automatically expose:

```text
SSH 22
```


# 80. AWS Systems Manager Concept

Systems Manager can provide managed administrative capabilities without requiring a broadly Internet-accessible SSH service.

Conceptually:

```text
Administrator
↓

↓
Systems Manager
↓
EC2
```

This can significantly reduce SSH exposure.

# 81. IAM

IAM means:

```text
Identity and Access Management
```

IAM controls who or what can perform actions against AWS resources.

Examples:

```text
Who can create EC2?

Who can modify security groups?

Who can read secrets?

Who can delete RDS?

What can the EC2 instance access?
```

---

# 82. Human IAM Identity vs EC2 Role

These are different concepts.

Human administrator:

```text
Human
↓
IAM/Federated Role
↓
AWS API
```

EC2 workload:

```text
EC2
↓
Instance Role
↓
AWS API
```

Do not put a human administrator's permanent AWS access keys on the SonarQube server.

---

# 83. EC2 IAM Role

Applications running on EC2 can use an IAM role attached through an instance profile.

Architecture:

```text
EC2
↓
IAM Role
↓
Temporary AWS Credentials
↓
Allowed AWS Services
```

This avoids storing long-lived AWS access keys on the server.

---

# 84. Example EC2 Role

Suppose SonarQube operational scripts need to retrieve one secret.

The EC2 role might be permitted:

```text
Read:
specific Secrets Manager secret
```

but not:

```text
Read every secret in AWS

Delete RDS

Create IAM users

Modify VPC
```

Least privilege matters.

---

# 85. Do Not Use AdministratorAccess

A common lab shortcut is:

```text
Attach AdministratorAccess to EC2.
```

That is a dangerous production pattern.

Ask:

```text
What exact AWS API actions does this workload need?
```

Then grant those.

# 88. Secret Still Needs Safe Handling

```text

Logging secret

Writing secret to world-readable file

Passing secret carelessly

Exposing secret through process debugging
```

# 113. RDS Automated Backups


# 115. Point-in-Time Recovery

Suppose an administrator accidentally causes a destructive database event at:

```text
14:32
```

A point-in-time recovery capability may allow you to restore the database to an earlier point within the supported retention window.

That is very different from:

```text
We take one backup every month.
```

---

# 116. Restore Creates a New Resource

An important AWS concept:

Restoring an RDS database generally creates a new database resource.

Think:

```text
Original RDS
↓
Restore
↓
New RDS Instance
```

Then you must reconnect SonarQube to the restored database as part of recovery.

---

# 117. Backups Need Restore Runbooks

A proper runbook should explain:

```text
1. Detect failure

2. Stop unsafe writes if necessary

3. Select recovery point

4. Restore database

5. Apply correct network/security configuration

6. Update SonarQube database endpoint if required

7. Start/validate SonarQube

8. Verify projects/issues/configuration

9. Verify CI integration

10. Verify webhooks

11. Reopen service
```

# 118. Test Restores

```text
DEPLOYING SONARQUBE ON AWS

```

A production SonarQube environment is a system:

```text
NETWORK
+
COMPUTE
+
DATABASE
+
STORAGE
+
DNS
+
TLS
+
ACCESS CONTROL
+
SECRETS
+
MONITORING
+
BACKUPS
+
RECOVERY
```

The architecture should deliberately enforce:

```text
Internet / Approved Network
        │
        ↓
     HTTPS 443
        │
        ↓
       ALB
        │
        │ Only ALB may reach 9000
        ↓
    SonarQube
        │
        │ Only SonarQube may reach 5432
        ↓
       RDS
```

That is the difference between:

```text
SonarQube running somewhere in AWS
```

and:

```text
SonarQube engineered as a production cloud service.
```
