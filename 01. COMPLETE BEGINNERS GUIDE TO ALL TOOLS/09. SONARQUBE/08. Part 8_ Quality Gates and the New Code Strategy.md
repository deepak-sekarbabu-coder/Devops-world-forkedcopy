# Part 8: Quality Gates and the New Code Strategy

## Turn Analysis Results Into Enforceable Engineering Standards

In Part 7, you learned how SonarQube decides what to check.

The architecture was:

```text
Programming Language
        ↓
Quality Profile
        ↓
Active Rules
        ↓
Source Code Analysis
        ↓
Issues
```

But there is still a major problem.

Imagine SonarQube analyzes an application and reports:

```text
3 reliability issues
1 security issue
8 maintainability issues
Coverage: 52%
Duplications: 9%
```

What happens next?

If SonarQube simply displays those numbers and everybody ignores them, then the analysis has little enforcement value.

We need another mechanism.

We need a way to say:

> These are the minimum engineering conditions required before this code is considered acceptable.

That is the job of a **Quality Gate**.

Our architecture now becomes:

```text
Code Change
     ↓
Analysis
     ↓
New Code Metrics
     ↓
Quality Gate
   ↙         ↘
PASS        FAIL
 ↓            ↓
Continue    Fix Code
```

This is where SonarQube moves from:

```text
Code Analysis Tool
```

toward:

```text
Engineering Policy Enforcement
```

---

# 1. The Problem Before Quality Gates

Suppose two developers analyze their code.

Developer A sees:

```text
Coverage: 84%
No security issues
No new reliability issues
```

Developer B sees:

```text
Coverage: 21%
1 serious security issue
7 reliability issues
```

Without a defined policy, both developers might say:

> Analysis completed successfully.

Technically, the scanner may indeed have completed successfully.

But:

```text
Successful Analysis
≠
Acceptable Code
```

We need a decision layer.

```text
Analysis
    ↓
Results
    ↓
Policy Evaluation
    ↓
Acceptable?
```

That policy evaluation is the Quality Gate.

---

# 2. What Is a Quality Gate?

A **Quality Gate** is a set of conditions that determines whether analyzed code satisfies your organization's required quality standard.

The fundamental question is:

> Is this project or code change acceptable according to the defined quality policy?

Conceptually:

```text
Analysis Results
      ↓
Quality Gate Conditions
      ↓
Evaluate
      ↓
PASS / FAIL
```

For example:

```text
Coverage on new code >= 80%

Duplicated lines on new code <= 3%

No new issues

All new Security Hotspots reviewed
```

If every required condition passes:

```text
QUALITY GATE
    ↓
PASS
```

If a required condition fails:

```text
QUALITY GATE
    ↓
FAIL
```

---

# 3. Quality Profile vs Quality Gate

You must now be able to explain this distinction immediately.

## Quality Profile

Answers:

> What problems should SonarQube look for?

## Quality Gate

Answers:

> Based on the resulting analysis, is this code acceptable?

Architecture:

```text
Source Code
    ↓
Quality Profile
    ↓
Active Rules
    ↓
Analysis
    ↓
Issues + Metrics
    ↓
Quality Gate
    ↓
PASS / FAIL
```

Therefore:

```text
QUALITY PROFILE
=
What to check
```

while:

```text
QUALITY GATE
=
What must pass
```

They work together.

They are not interchangeable.

---

# 4. Why Quality Gates Matter

Without a Quality Gate:

```text
Developer
    ↓
Push Code
    ↓
SonarQube Finds Problems
    ↓
Dashboard Shows Problems
    ↓
Developer Ignores Dashboard
    ↓
Deployment Continues
```

With enforcement:

```text
Developer
    ↓
Push Code
    ↓
SonarQube Analysis
    ↓
Quality Gate
    ↓
FAIL
    ↓
Pipeline Stops
    ↓
Developer Fixes Code
```

The difference is:

```text
Information
```

versus:

```text
Enforceable Standard
```

---

# 5. Quality Gates Create a Decision Point

A delivery pipeline needs decision points.

For example:

```text
Did the build succeed?

Did unit tests pass?

Did integration tests pass?

Did security scanning pass?

Did SonarQube Quality Gate pass?
```

The pipeline becomes:

```text
Code
 ↓
Build
 ↓
Tests
 ↓
Static Analysis
 ↓
Quality Gate
 ↓
Deploy?
```

That question mark is important.

The gate helps answer it.

---

# 6. What Is a Quality Gate Condition?

A **condition** is a requirement inside the Quality Gate.

Example:

```text
Coverage on New Code
must be at least
80%
```

We can break that into:

```text
Metric:
Coverage

Scope:
New Code

Operator:
>=

Threshold:
80%
```

Together:

```text
Coverage on New Code >= 80%
```

That is a gate condition.

---

# 7. Anatomy of a Condition

Think:

```text
Metric
   ↓
Operator
   ↓
Threshold
```

Example:

```text
Duplicated Lines (%)
        ↓
       <=
        ↓
        3%
```

Another:

```text
New Issues
    ↓
    >
    ↓
    0

If true:
FAIL
```

Conditions convert measurements into decisions.

---

# 8. What Is a Metric?

A **metric** is something SonarQube measures.

Examples include:

```text
Coverage

Duplicated Lines

Reliability Rating

Security Rating

Maintainability Rating

Security Hotspots Reviewed

Issues

Lines of Code

Complexity
```

But just because SonarQube measures something does not mean it should automatically become a gate condition.

That distinction matters.

---

# 9. Metric vs Condition

Example:

```text
Coverage = 76%
```

is a metric value.

But:

```text
Coverage must be >= 80%
```

is a policy condition.

Therefore:

```text
Measurement
      ↓
Threshold
      ↓
Decision
```

The Quality Gate turns measurements into decisions.

---

# 10. Quality Gate Pass

A Quality Gate passes when all required conditions are satisfied.

Example:

```text
No new issues
PASS

Security Hotspots reviewed
PASS

Coverage >= 80%
PASS

Duplication <= 3%
PASS
```

Result:

```text
QUALITY GATE
    ↓
PASSED
```

Now the pipeline may continue.

---

# 11. Quality Gate Fail

Suppose:

```text
No new issues
PASS

Security Hotspots reviewed
PASS

Coverage >= 80%
FAIL

Duplication <= 3%
PASS
```

The overall result becomes:

```text
QUALITY GATE
    ↓
FAILED
```

The gate is not:

> Average the results and decide that three out of four is good enough.

If a required blocking condition fails, the gate fails.

---

# 12. Scanner Success vs Quality Gate Pass

This distinction remains critical.

You can have:

```text
SonarScanner
    ↓
EXECUTION SUCCESS
```

and still:

```text
Quality Gate
    ↓
FAILED
```

Why?

Because the scanner successfully performed its job.

It successfully discovered that the code does not satisfy your policy.

Think:

```text
Analysis worked correctly
        ↓
Results produced
        ↓
Policy evaluated
        ↓
Code failed policy
```

That is not a scanner malfunction.

---

# 13. Build Success vs Gate Success

Similarly:

```text
Application compiles
```

does not imply:

```text
Quality Gate passes
```

You may have:

```text
Build
PASS

Unit tests
PASS

SonarScanner
PASS

Quality Gate
FAIL
```

because static analysis found an unacceptable new issue or another gate condition failed.

Different pipeline stages answer different questions.

---

# 14. SonarQube's Built-In Default Quality Gate

Current SonarQube Server provides a built-in Quality Gate called:

```text
Sonar way
```

It is Sonar's recommended default Quality Gate.

In current SonarQube 2026.1 LTA, it is:

```text
Built-in
Default
Read-only
Focused on new code
```

Its four conditions are currently:

```text
1. No new issues are introduced

2. All new Security Hotspots are reviewed

3. New code coverage >= 80%

4. Duplication on new code <= 3%
```

This is important because many older tutorials describe older default conditions.

When administering a real instance, verify behavior against the exact SonarQube version you operate.

---

# 15. Understanding the Sonar Way Gate

Let's examine those conditions.

```text
Sonar way
│
├── No new issues
│
├── New Security Hotspots reviewed
│
├── New Code Coverage >= 80%
│
└── New Code Duplication <= 3%
```

Notice something important:

Most of the attention is on:

```text
NEW CODE
```

not:

```text
ENTIRE HISTORICAL CODEBASE
```

That is deliberate.

---

# 16. Why the Default Gate Focuses on New Code

Imagine a legacy application:

```text
Age:
12 years

Lines:
3 million

Historical issues:
18,000

Coverage:
27%

Duplications:
17%
```

You introduce:

```text
20 new lines
```

If the gate demanded:

```text
Overall coverage >= 80%
```

before allowing your small change, you might need to write tests across years of unrelated legacy code.

That may make normal engineering work impossible.

Instead, ask:

```text
Is the code we are adding today clean?
```

That is the core idea behind the new-code strategy.

---

# 17. Clean as You Code

Sonar's methodology is called:

```text
Clean as You Code
```

The principle is straightforward:

> Focus first on keeping code that is being added or changed clean.

Current SonarQube documentation describes new code as recently added or modified code and emphasizes using it to progressively improve the overall codebase.

Architecture:

```text
Existing Codebase
      ↓
Contains Historical Debt

Developer Changes Code
      ↓
New Code

Apply Strong Standards
      ↓
New Code Remains Clean

Repeat
      ↓
Overall Code Improves Gradually
```

---

# 18. Clean as You Code Does Not Mean Ignore Old Code

This is important.

Wrong interpretation:

```text
Old code doesn't matter.
```

Correct interpretation:

```text
Stop creating new debt
while managing existing debt intelligently.
```

You can still:

```text
Fix historical vulnerabilities

Improve old modules

Increase overall coverage

Remove duplication

Refactor legacy code
```

Clean as You Code simply gives you a practical first control:

```text
Do not make the problem worse.
```

---

# 19. The Financial Analogy

Suppose you owe:

```text
$100,000
```

and every month you add:

```text
$5,000 new debt
```

Paying old debt while continuing to create large new debt is difficult.

Software behaves similarly.

```text
Historical Technical Debt
        +
New Technical Debt Every Sprint
        ↓
Growing Problem
```

Clean as You Code says:

```text
First:
Stop adding bad debt.

Then:
Reduce existing debt progressively.
```

---

# 20. What Is New Code?

New code is code considered recently added or modified according to the project's configured **new code definition**.

Think:

```text
Entire Repository
      ↓
Which parts count as "new"?
      ↓
New Code Definition
      ↓
New Code
```

This matters because the Quality Gate may evaluate conditions specifically against that scope.

---

# 21. New Code vs Overall Code

Imagine:

```text
Repository
100,000 lines
```

Developer changes:

```text
400 lines
```

SonarQube may present:

```text
OVERALL CODE

100,000 lines
```

and:

```text
NEW CODE

Relevant recent/changed code
```

These answer different questions.

---

# 22. Overall Code Question

Overall code answers:

> What is the broader condition of this codebase?

It can tell you about:

```text
Historical issues
Overall coverage
Overall duplication
Overall ratings
Overall technical debt
```

---

# 23. New Code Question

New code asks:

> What quality are we introducing now?

This is especially useful during:

```text
Feature development

Bug fixes

Pull requests

Release cycles

Continuous delivery
```

---

# 24. New Code Definitions

Current SonarQube documentation supports several approaches for defining new code, including:

```text
Previous Version

Number of Days

Specific Analysis

Reference Branch
```

Which one is appropriate depends on how the project is developed and released.

---

# 25. Previous Version

Conceptually:

```text
Version 2.3 released
       ↓
Version changes to 2.4
       ↓
Code changed during 2.4 development
       ↓
New Code
```

This approach can make sense for applications that follow explicit release versions.

The new-code period is associated with changes since the current version began.

---

# 26. Number of Days

Example:

```text
New Code Definition:
30 days
```

SonarQube considers code changed during the configured time window as new according to this strategy.

Think:

```text
Today
  ↓
Look Back 30 Days
  ↓
Relevant Changed Code
  ↓
New Code
```

This can fit continuous development models.

But choose the number deliberately.

---

# 27. The Danger of Arbitrary Day Windows

Suppose:

```text
New Code = last 5 days
```

A serious problem is introduced.

Nobody fixes it.

After enough time, it may leave that rolling new-code window.

You should not design policy around the idea:

> If we ignore the problem long enough, it becomes old code.

Your workflow should enforce the gate while the change is being introduced.

---

# 28. Specific Analysis

Another strategy can use a specific previous analysis as the baseline.

Conceptually:

```text
Baseline Analysis
      ↓
Changes After Baseline
      ↓
New Code
```

This can provide precise control in particular project workflows.

---

# 29. Reference Branch

For branch-based development, SonarQube can use another branch as the reference.

Conceptually:

```text
main
 ↓
Reference

feature/payment
 ↓
Compare Against main
 ↓
Changes
 ↓
New Code
```

This is especially intuitive in pull-request workflows.

For pull requests, SonarQube can define new code based on what changed relative to the target branch.

---

# 30. New Code Strategy Must Match Development Strategy

Do not choose new-code definitions randomly.

Ask:

```text
How do we release?

Do we use version numbers?

Do we use continuous deployment?

Do we use short-lived feature branches?

Do we use long-lived branches?

How frequently do we analyze?

How do pull requests work?
```

Your SonarQube configuration should support the engineering workflow rather than fight it.

---

# 31. Coverage Thresholds

Coverage is one of the most common Quality Gate conditions.

The current Sonar way gate requires:

```text
New Code Coverage >= 80%
```

This means the relevant new code must have sufficient test coverage data.

Example:

```text
New code executable lines:
100

Covered:
85
```

Result:

```text
Coverage:
85%

Threshold:
80%

PASS
```

---

# 32. Coverage Failure Example

Suppose:

```text
New code coverage:
62%

Required:
80%
```

Then:

```text
62% < 80%
```

Result:

```text
FAIL
```

The correct response is not automatically:

> Lower the threshold.

Investigate why coverage is low.

---

# 33. Why Coverage Thresholds Matter

Without a coverage requirement, developers could introduce:

```text
500 new lines of complex business logic
```

with:

```text
0 tests
```

The static analysis might look clean.

But critical behavior remains untested.

A coverage threshold creates pressure to accompany new code with tests.

---

# 34. Coverage Does Not Prove Test Quality

You learned this in Part 6.

```text
Coverage >= 80%
```

does not mean:

```text
Application is correct.
```

It only means that the configured coverage measurement satisfies the threshold.

Tests may still:

```text
Miss edge cases

Use weak assertions

Ignore failure scenarios

Miss business requirements
```

Coverage is one guardrail.

Not proof.

---

# 35. Should Every Project Use 80%?

Not necessarily.

80% is Sonar way's current recommended new-code condition.

But custom gates may be appropriate for different engineering contexts.

For example:

```text
Business-critical calculation library
```

might require stronger standards.

A generated-code-heavy or specialized project may require a different carefully justified approach.

The important point is:

```text
Threshold
=
Engineering Policy
```

not:

```text
Random Number
```

---

# 36. Unrealistic Coverage Thresholds

Suppose a team with almost no tests changes the gate overnight to:

```text
New Code Coverage >= 100%
```

without understanding the consequences.

Possible result:

```text
Developers write meaningless tests
        ↓
Coverage reaches 100%
        ↓
Tests provide little assurance
```

You have optimized the metric instead of the engineering outcome.

---

# 37. Realistic Coverage Standards

A good threshold should be:

```text
Meaningful

Achievable

Strict enough to improve behavior

Appropriate to the project

Supported by testing infrastructure

Reviewed over time
```

Do not interpret realistic as:

```text
easy enough that it never fails.
```

A gate that can never fail is barely a gate.

---

# 38. Duplication Thresholds

The current Sonar way Quality Gate allows:

```text
Duplicated Lines on New Code <= 3%
```

This aims to reduce the introduction of copy-paste maintenance debt.

Example:

```text
New code duplication:
1.4%

Threshold:
3%

PASS
```

Another:

```text
New code duplication:
8%

Threshold:
3%

FAIL
```

---

# 39. Why Focus Duplication on New Code

Suppose the existing project has:

```text
Overall duplication:
22%
```

You may not be able to refactor the entire system immediately.

But you can say:

```text
New code must not continue the same pattern.
```

Over time:

```text
Old duplication remains
      ↓
New code stays cleaner
      ↓
Old modules touched during work are improved
      ↓
Overall duplication can gradually decrease
```

---

# 40. Do Not Refactor Blindly to Reach 0%

Remember:

```text
0% duplication
```

is not automatically the perfect engineering objective.

Some similar code may exist for legitimate architectural reasons.

Do not create an inappropriate abstraction simply to satisfy a metric.

The goal is maintainable code.

---

# 41. Reliability Conditions

Quality Gates can use reliability-related conditions.

Conceptually:

```text
New Reliability Problems
        ↓
Rating / Issues
        ↓
Gate Condition
```

A Clean as You Code-oriented custom gate may enforce:

```text
Reliability Rating on New Code = A
```

as part of its policy.

Current Sonar documentation describes a compliant alternative using A ratings for new-code reliability, security and maintainability when not using the simpler "no new issues" condition.

---

# 42. What Does a Reliability Gate Protect Against?

The intent is:

```text
Do not introduce code likely to behave incorrectly.
```

Examples of relevant concerns can include:

```text
Runtime errors

Incorrect conditions

Improper resource handling

Dangerous null behavior

Incorrect API use
```

depending on the language and active rules.

---

# 43. Security Conditions

Quality Gates can also enforce security quality.

Conceptually:

```text
New Code
   ↓
Security Analysis
   ↓
Security Issues
   ↓
Security Condition
```

A strong policy may require:

```text
Security Rating on New Code = A
```

and also ensure that Security Hotspots receive the required review.

---

# 44. Security Hotspots Reviewed

The current Sonar way gate requires:

```text
All new Security Hotspots reviewed
```

That effectively means the review requirement must be satisfied for new hotspots before the condition passes.

Remember:

```text
Security Hotspot
≠
Confirmed Vulnerability
```

but:

```text
Security Hotspot
=
Security-sensitive code requiring review
```

The gate ensures they are not casually ignored.

---

# 45. Why Security Review Should Not Be Optional

Imagine a pull request introduces:

```text
New cryptographic logic
```

SonarQube identifies it as security-sensitive.

If the pipeline continues without review:

```text
Hotspot detected
    ↓
Nobody investigates
    ↓
Deployment
```

the hotspot mechanism provides little value.

A gate can enforce:

```text
Review first
    ↓
Then proceed
```

---

# 46. Maintainability Conditions

Maintainability conditions aim to prevent new technical debt from becoming normal.

Conceptually:

```text
New Code
    ↓
Maintainability Analysis
    ↓
Maintainability Issues
    ↓
Rating / Gate
```

A Clean as You Code policy may require:

```text
Maintainability Rating on New Code = A
```

depending on the custom gate design.

---

# 47. Maintainability Is Not Cosmetic

A maintainability gate is not about:

```text
making code pretty.
```

Poor maintainability can lead to:

```text
Slower feature delivery

More defects

Harder debugging

Higher onboarding cost

More incident risk

More technical debt
```

So maintaining good new code can have real operational consequences.

---

# 48. One Powerful Condition: No New Issues

Modern Sonar way uses a particularly simple condition:

```text
No New Issues
```

The idea is powerful:

```text
New Issue?
  ↓
Yes
  ↓
Gate Fails
```

This avoids lengthy debates over which new issue type is acceptable.

The target becomes:

```text
New code should introduce no unresolved issues.
```

---

# 49. No New Issues Does Not Mean No Historical Issues

Suppose:

```text
Overall issues:
9,000
```

Your pull request introduces:

```text
0 new issues
```

The new-code condition can pass.

This does not mean SonarQube believes the historical 9,000 issues are good.

It means:

```text
This change did not add another problem.
```

---

# 50. Custom Quality Gates

Organizations can create custom Quality Gates when they have the appropriate administration permission.

Current SonarQube documentation distinguishes built-in gates from administrator-created custom gates.

Example:

```text
VERIQTA Production Gate
```

Conditions:

```text
No new issues

Security Hotspots reviewed = 100%

Coverage on new code >= 85%

Duplication on new code <= 2%
```

Another project class might use a different justified standard.

---

# 51. Why Create a Custom Gate?

Possible reasons:

```text
Stricter testing requirement

Different application risk profile

Security-critical software

Internal framework

Regulatory requirement

Different supported technology

Organization-specific standards
```

But do not customize just because you can.

---

# 52. Avoid Gate Proliferation

Bad architecture:

```text
Project 1 → Gate 1

Project 2 → Gate 2

Project 3 → Gate 3

Project 4 → Gate 4

Project 5 → Gate 5
```

Soon:

```text
500 Projects
400 Gates
Nobody knows why
```

This destroys consistency.

Prefer:

```text
Small Number of Standard Gates
```

with documented exceptions.

---

# 53. Example Gate Strategy

An organization might reasonably use:

```text
Standard Production Gate

Critical Systems Gate

Legacy Transition Gate
```

rather than:

```text
One gate per repository
```

Even then, each gate should have:

```text
Purpose

Owner

Conditions

Reasoning

Applicable systems

Review process
```

---

# 54. Default Quality Gate

A SonarQube instance has a default Quality Gate.

Projects not explicitly assigned another gate use that default.

Current SonarQube 2026.1 documentation states that **Sonar way** is the built-in gate used as the default unless administrators change the instance's default or explicitly associate a project with another gate.

Conceptually:

```text
Project
   ↓
Specific Gate Assigned?
  ↙                ↘
Yes                 No
 ↓                   ↓
Use Assigned       Use Default
Gate               Gate
```

---

# 55. Why Defaults Matter

Imagine:

```text
300 repositories
```

If every repository requires manual gate configuration:

```text
Human errors

Forgotten projects

Inconsistent policies

Configuration drift
```

become likely.

A strong default gives:

```text
New Project
    ↓
Automatically receives baseline policy
```

---

# 56. Assigning a Gate to a Project

A project can be explicitly associated with a Quality Gate.

Example:

```text
General applications
       ↓
Sonar way
```

but:

```text
Authentication Service
       ↓
Critical Systems Gate
```

This gives flexibility.

But explicit exceptions should be controlled.

---

# 57. Project Association Architecture

```text
SonarQube Instance
│
├── Default Gate
│     └── Sonar way
│
├── Project A
│     └── Default
│
├── Project B
│     └── Default
│
└── Critical Project
      └── Custom Security Gate
```

# 58. Quality Gate Status

After analysis and server-side processing, SonarQube determines the gate status.

Typical conceptual outcomes:

```text
PASSED
```

or:

```text
FAILED
```

The status appears in the project's analysis results.

But the more important question is:

> What do we do with that status?

---

# 59. Dashboard-Only Gate

At the most basic level:

```text
Analysis
   ↓
Gate Status
   ↓
Dashboard
```

A developer opens SonarQube and sees:

```text
FAILED
```

This is useful.

But humans may still ignore it.

---

# 60. CI-Enforced Gate

A more mature architecture is:

```text
Analysis
    ↓
Quality Gate
    ↓
Status Returned to CI
    ↓
PASS / FAIL
```

If:

```text
PASS
```

then:

```text
Continue Pipeline
```

If:

```text
FAIL
```

then:

```text
Stop Pipeline
```

Current SonarQube supports reporting Quality Gate status to CI, where it can be used to fail the pipeline.

---

# 61. Pull Request Enforcement

Quality Gate status can also be surfaced in the repository platform during pull requests.

Conceptually:

```text
Developer
    ↓
Pull Request
    ↓
SonarQube Analysis
    ↓
Quality Gate
    ↓
PR Check
```

Then:

```text
PASS
 ↓
Merge Allowed
```

or:

```text
FAIL
 ↓
Merge Blocked
```

when repository branch protection is configured accordingly. SonarQube's current documentation explicitly describes using PR decoration and repository controls to block merges on gate failure.

---

# 62. The Ultimate Goal

We want:

```text
Problem discovered
```

before:

```text
production deployment
```

Better:

```text
Developer writes issue
      ↓
Pull request analysis
      ↓
Quality Gate fails
      ↓
Developer fixes
```

than:

```text
Developer writes issue
      ↓
Deploy
      ↓
Customer finds issue
      ↓
Production incident
```

Earlier feedback is usually cheaper.

# 64. Why Teams Focus on New Code

There are several reasons.

## Reason 1: Developers Own Their Changes

It is reasonable to say:

```text
You do not need to fix the entire 10-year-old system today.
```

But:

```text
Do not add new problems in your change.
```

---

# 65. Reason 2: New Problems Are Cheaper to Fix

The engineer who wrote the code:

```text
still understands the context.
```

Fixing today may take:

```text
10 minutes
```

Six months later:

```text
Nobody remembers why the code exists.
```

The same fix might require hours of investigation.

---

# 66. Reason 3: Prevent Technical Debt Growth

Without new-code control:

```text
Old Debt
    +
New Debt
    ↓
Growing Debt
```

With control:

```text
Old Debt
    +
Clean New Code
    ↓
Debt Stops Growing as Quickly
```

---

# 67. Reason 4: Legacy Projects Become Manageable

Legacy systems often cannot be cleaned all at once.

New-code policy provides a migration path:

```text
Do not worsen old code
      ↓
Clean touched areas
      ↓
Refactor strategically
      ↓
Improve gradually
```

---

# 68. Reason 5: Pull Requests Become Natural Enforcement Points

A pull request represents:

```text
A specific proposed change
```

That is an excellent place to ask:

> Does this change meet our standard?

The Quality Gate can therefore become part of normal code review.

---

# 69. Realistic vs Unrealistic Thresholds

A Quality Gate should challenge engineering teams appropriately.

But bad thresholds can produce bad behavior.

There are two dangerous extremes.

---

# 70. Extreme 1: Gate Too Weak

Example:

```text
Coverage >= 5%

Duplication <= 60%

Security issues allowed
```

This almost never fails.

Result:

```text
Green Gate
    ↓
Little Actual Protection
```

The gate becomes theatre.

---

# 71. Extreme 2: Gate Unrealistically Strict

Example:

```text
Coverage = 100%

Duplication = 0%

No complexity anywhere

Every possible rule active
```

Result:

```text
Constant Failure
    ↓
Developer Frustration
    ↓
Bypass Requests
    ↓
Metric Gaming
    ↓
Loss of Trust
```

Extremely strict numbers are not automatically mature engineering.

---

# 72. Strong Standards vs Impossible Standards

A useful gate should be:

```text
Strict enough to matter

Clear enough to understand

Stable enough to trust

Realistic enough to follow

Difficult enough to improve engineering
```

It should not be:

```text
Arbitrary

Unachievable

Frequently changed

Designed only to look impressive
```

---

# 73. A Gate Should Fail Sometimes

This is important.

If your Quality Gate has:

```text
never failed in two years
```

ask whether:

```text
The team is exceptionally disciplined
```

or:

```text
The gate is too weak to catch anything meaningful.
```

Controls should occasionally detect violations.

That is why they exist.

---

# 74. A Gate Should Also Be Fixable

When a gate fails, the developer should be able to understand:

```text
What failed?

Why?

Which code?

Which metric?

Which threshold?

What do I need to change?
```

A mysterious gate destroys trust.

---

# 75. Quality Gate Failure Should Be Actionable

Bad feedback:

```text
QUALITY FAILED
```

Better:

```text
QUALITY GATE FAILED

Reason:
Coverage on New Code = 62%

Required:
>= 80%
```

or:

```text
Reason:
2 new issues introduced
```

Developers need actionable feedback.

## What beginner sees

```text

Required:
```

## Possible causes

```text
Coverage report path wrong
```

## Investigation

Follow:

```text
Source Code
    ↓
Tests
    ↓
Coverage Tool
    ↓
Coverage Report
    ↓
SonarScanner
    ↓
SonarQube
```

Determine whether the problem is:

```text
Real lack of tests
```

or:

```text
Broken coverage integration
```

# 78. Troubleshooting: Coverage Suddenly Becomes 0%

Do not instantly write hundreds of new tests.

First check:

```text
Did tests run?

Was coverage report generated?

Did report location change?

Can scanner find it?

Did CI working directory change?

Did tooling version change?
```

A measurement pipeline can fail independently of source quality.

---

# 79. Troubleshooting: Duplication Gate Fails

## Problem

```text
New Code Duplication:
7%

Required:
<= 3%
```

## Investigate

Find:

```text
Which blocks are duplicated?

Were they copied from existing code?

Can shared logic be extracted?

Would abstraction actually improve maintainability?
```

Do not:

```text
rename variables
```

merely to fool duplication detection.

Fix the design where appropriate.

# 80. Troubleshooting: No New Issues Condition Fails

## Problem

```text

3
```

## Investigation

For every issue:

```text
Issue
  ↓
Rule
  ↓
Software Quality
  ↓
Code Location
  ↓
Is Finding Valid?
```

Then:

```text
Fix
or
Appropriately Review / Classify
```

according to organizational policy.

Do not immediately weaken the gate.

# 81. Troubleshooting: Security Hotspot Condition Fails

## Problem

```text

Not 100%
```

## Meaning

At least one relevant new hotspot still requires review.

## Action

Open the hotspot.

```text

What data reaches it?

What existing controls exist?

Is implementation safe?

Does code require remediation?
```

Then complete the security review appropriately.

Do not mark it reviewed without understanding it.

```text
       ↓
Permanent Control Failure
```

This happens in real organizations.

Exceptions must be governed.
