# Part 4: Running SonarQube with Docker and Docker Compose

## Build a Reproducible Containerized SonarQube Environment

In Part 3, we installed SonarQube directly on a laptop.

Our architecture was:

```text
Laptop
   ↓
Java
   ↓
SonarQube Server
   ↓
Embedded Database
   ↓
localhost:9000
```

That lab was valuable because you directly encountered:

```text
Java
Directories
Configuration files
Processes
Logs
Permissions
Port 9000
Startup and shutdown
```

Now we will rebuild SonarQube differently.

Instead of installing SonarQube directly on the operating system, we will run it inside a Docker container.

Then we will replace the temporary embedded database with PostgreSQL running in another container.

Our final architecture will be:

```text
                    DOCKER HOST
                         │
          ┌──────────────┴──────────────┐
          │                             │
          ↓                             ↓
┌──────────────────┐          ┌──────────────────┐
│ SonarQube        │          │ PostgreSQL       │
│ Container        │          │ Container        │
│                  │          │                  │
│ Web              │          │ SonarQube DB     │
│ Compute Engine   │◄────────►│ TCP 5432         │
│ Elasticsearch    │          │                  │
│ TCP 9000         │          │                  │
└────────┬─────────┘          └────────┬─────────┘
         │                             │
         ↓                             ↓
 SonarQube Volumes              PostgreSQL Volume
         │
         ↓
 localhost:9000
```

This chapter will teach not only how to run two containers, but why the architecture works.

---

# 1. What We Are Building

We will build the environment progressively.

First:

```text
Docker Host
    ↓
SonarQube Container
    ↓
localhost:9000
```

Then:

```text
Docker Host
│
├── SonarQube Container
│
└── PostgreSQL Container
```

Then:

```text
Docker Host
│
├── SonarQube Container
│       │
│       ├── data volume
│       ├── logs volume
│       └── extensions volume
│
└── PostgreSQL Container
        │
        └── database volume
```

Finally, Docker Compose will define the entire environment as code:

```text
compose.yaml
     ↓
Docker Compose
     ↓
Network
     ↓
SonarQube + PostgreSQL
     ↓
Persistent Volumes
     ↓
Health Checks
```

The goal is reproducibility.

# 2. What Does Reproducible Mean?

Suppose you manually configure a server.

You run:

```text
Command A
Command B
Command C
```

Then edit:

```text
File X
File Y
```

Then create:

```text
Directory Z
```

Six months later, another engineer asks:

> How exactly did you build this SonarQube server?

If your answer is:

> I don't remember. I ran some commands.

the environment is difficult to reproduce.

Docker Compose allows us to describe much of the environment declaratively.

Instead of remembering:

```text
Create PostgreSQL
Create network
Create SonarQube
Connect database
Create volumes
Map ports
Set environment variables
```

we can define those things in:

```text
compose.yaml
```

Then run:

```bash
docker compose up -d
```

That is a major reason containers are useful in DevOps.

# 3. Why Run SonarQube in Containers?

Containers provide several useful characteristics.

They make application environments:

```text
Repeatable
Isolated
Portable
Declarative
Replaceable
Easier to automate
```

Consider the ZIP installation from Part 3.

You needed:

```text
Host operating system
        ↓
Compatible Java
        ↓
Extract SonarQube
        ↓
Manage directories
        ↓
Run scripts
```

With the official Docker image:

```text
Docker
   ↓
SonarQube Image
   ↓
Container
```

much of the application runtime is already packaged.

---

# 4. Containerization Does Not Eliminate Infrastructure

This is important.

A beginner may think:

> If SonarQube runs in Docker, I don't need to care about Java, memory, disk, networking or Elasticsearch anymore.

Wrong.

Docker packages the application.

It does not repeal the operating system.

The real architecture is still:

```text
Physical / Virtual Host
        ↓
Operating System
        ↓
Docker Engine
        ↓
Container
        ↓
SonarQube
        ↓
Java Processes
        ↓
Elasticsearch
```

SonarQube still needs:

```text
CPU
Memory
Disk
Networking
Database
```

Elasticsearch still has operating-system considerations.

PostgreSQL still needs durable storage.

Containers change how we package and operate the application.

They do not remove the application's requirements.

# 5. What Is a Docker Image?

Before running SonarQube, understand the terminology.

A Docker **image** is a packaged, read-only template used to create containers.

Think:

```text
IMAGE
  ↓
Blueprint
  ↓
CONTAINER
```

For example:

```text
sonarqube:community
        ↓
docker run
        ↓
Running SonarQube Container
```

The image contains the application and runtime components required by the image.

---

# 6. Image vs Container

Do not confuse these.

## Image

A packaged template.

Example:

```text
sonarqube:community
```

## Container

A running or stopped instance created from an image.

Example:

```text
sonarqube-local
```

One image can create multiple containers.

```text
              sonarqube:community
                      │
          ┌───────────┼───────────┐
          ↓           ↓           ↓
     Container A  Container B  Container C
```

Think:

```text
Image = blueprint

Container = instance created from blueprint
```

# 8. Why Official Images Matter

A container image can contain executable software.

Running:

```bash
docker run some-random-user/sonarqube
```

means you are trusting whatever that image contains.

SonarQube will eventually have access to:

```text
Source analysis information
Database credentials
CI/CD connectivity
Authentication information
Plugins
```

Therefore:

```text
Official / trusted image
          ↓
Known source
          ↓
Lower supply-chain risk
```

is preferable to downloading random customized images.

# 11. Moving Tags vs Version-Pinned Tags

Suppose you use:

```text
sonarqube:community
```

That is a moving tag.

A later pull can retrieve a newer Community Build.

This is convenient for learning.

But production environments often benefit from pinning an explicit version.

For example:

```text
sonarqube:<specific-version>-community
```

Why?

Because:

```text
Monday
docker pull sonarqube:community
        ↓
Version A
```

could eventually become:

```text
Future Monday
docker pull sonarqube:community
        ↓
Version B
```

A production deployment should not unexpectedly upgrade merely because an image was pulled again.

---

# 12. Lab Tag vs Production Tag

For our learning lab, we can use:

```text
sonarqube:community
```

because the objective is learning.

For a controlled production deployment:

```text
Explicitly tested version
```

is safer.

Principle:

```text
LAB
Moving tag may be acceptable

PRODUCTION
Pin tested version
```

This is port publishing.

Syntax:

```text
HOST_PORT:CONTAINER_PORT
```

Therefore:


```text

        ↓
Container TCP 9000
```

```text

   ↓
localhost:9000
   ↓

   ↓
Docker Port Mapping
   ↓
SonarQube Container Port 9000
   ↓
SonarQube Web Server
```

# 26. Host Port and Container Port Are Different Concepts

Consider:

```bash
-p 9001:9000
```

This means:

```text
Host
9001
 ↓
Container
9000
```

You would open:

```text
http://localhost:9001
```

SonarQube would still be listening on:

```text
9000
```

inside the container.

This is important.

Port mapping does not necessarily change the application's internal port.

# 33. Removing a Container

Stop it:

```bash
docker stop sonarqube-local
```

Then remove it:

```bash
docker rm sonarqube-local
```

Now:

```bash
docker ps -a
```

should no longer show it.

This introduces a critical container concept.

**Containers should be considered replaceable.**

Your important data should not depend solely on the writable filesystem of one particular container.

---

# 34. The Container Persistence Problem

Imagine:

```text
SonarQube Container
      │
      ├── configuration/state
      ├── search data
      ├── extensions
      └── logs
```

Then:

```bash
docker rm sonarqube
```

If important state exists only inside that container's writable layer, deleting the container can delete that state with it.

That is not what we want.

We need persistent storage.

---

# 35. Docker Volumes

A Docker volume stores data separately from the lifecycle of a container.

Architecture:

```text
Container
    ↓
Mounted Path
    ↓
Docker Volume
    ↓
Persistent Data
```

Then:

```text
Container A
    ↓
Volume
```

can be replaced by:

```text
Container B
    ↓
Same Volume
```

and the persistent data remains.

---

# 36. Container Lifecycle vs Data Lifecycle

Without volume:

```text
Container
   ↓
Data inside container
   ↓
Delete container
   ↓
Data lost
```

With volume:

```text
Container
   ↓
Volume
   ↓
Delete container
   X
Volume remains
   ↓
New container
   ↓
Reuse volume
```

This is one of the most important Docker concepts.

# 41. Mounting Volumes

A more persistent SonarQube container could conceptually use:

```bash
docker run -d \
  --name sonarqube-local \
  -p 9000:9000 \
  -v sonarqube_data:/opt/sonarqube/data \
  -v sonarqube_extensions:/opt/sonarqube/extensions \
  -v sonarqube_logs:/opt/sonarqube/logs \
  sonarqube:community
```

Now the architecture becomes:

```text
SonarQube Container
        │
        ├── /opt/sonarqube/data
        │          ↓
        │   sonarqube_data
        │
        ├── /opt/sonarqube/extensions
        │          ↓
        │   sonarqube_extensions
        │
        └── /opt/sonarqube/logs
                   ↓
            sonarqube_logs
```

---

# 42. Understanding `-v`

Syntax:

```text
-v VOLUME_NAME:CONTAINER_PATH
```

Example:

```text
-v sonarqube_data:/opt/sonarqube/data
```

means:

> Mount the Docker volume named `sonarqube_data` at `/opt/sonarqube/data` inside the container.

---

# 43. Named Volumes vs Bind Mounts

Docker supports different storage approaches.

## Named volume

Example:

```text
sonarqube_data:/opt/sonarqube/data
```

Docker manages the host storage location.

## Bind mount

Example conceptually:

```text
./data:/opt/sonarqube/data
```

A specific host directory is mounted.

For application data, Docker-managed named volumes are often easier for beginner Compose deployments.

---

# 44. Do Not Mount Random Directories Over SonarQube

A mount hides whatever was originally visible at that container path.

Therefore, mounting an incorrectly prepared host directory can cause:

```text
Missing files
Permission problems
Plugin problems
Startup failures
```

Do not think:

> More mounts = better.

Mount what the application expects and what you actually need to persist.

---

# 45. Logs: Two Different Views

With Dockerized SonarQube, you may have:

```text

```

and:


They are related but not conceptually identical.

`docker logs` shows output captured by the container runtime.

For deeper troubleshooting you may need both.

# 55. Docker Networking

Now we have a new problem.

How does:

```text
SonarQube Container
```

find:

```text
PostgreSQL Container
```

Do not configure:

```text
localhost
```

inside the SonarQube container.

Why?

Because:

```text
localhost
```

inside the SonarQube container means:

```text
the SonarQube container itself
```

not PostgreSQL.

This is one of the most important container-networking concepts.

---

# 56. Localhost Inside Containers

Consider:

```text
Host
│
├── SonarQube Container
│      localhost = SonarQube container
│
└── PostgreSQL Container
       localhost = PostgreSQL container
```

Therefore:

```text
SonarQube → localhost:5432
```

means:

> SonarQube, connect to PostgreSQL on yourself.

But PostgreSQL is not running inside the SonarQube container.

The connection fails.

---

# 57. Docker Network

Create a user-defined network:

```bash
docker network create sonarnet
```

Inspect:


# 62. Why We Do Not Need to Publish PostgreSQL to the Host



```text
Browser
   ↓
Host 9000
   ↓
SonarQube

SonarQube
   ↓
Internal Docker Network
   ↓
PostgreSQL
```

not:

```text
Everyone
   ↓
Host 5432
   ↓
PostgreSQL
```

This is an example of reducing unnecessary network exposure.

# 85. `stop` vs `down`

This distinction matters.

## `docker compose stop`

Stops containers.

They remain defined.

## `docker compose down`

Stops and removes the Compose containers and default network.

Run:

```bash
docker compose down
```

The containers disappear.

But named volumes are normally retained unless you explicitly request volume removal.

This is critical for persistence.

---

# 86. Dangerous Command: `down -v`

Be careful with:

```bash
docker compose down -v
```

The:

```text
-v
```

requests removal of named volumes associated with the Compose application.

That can delete persistent database and SonarQube data.

Before running destructive commands, ask:

```text
What exactly will this delete?

Do I need the data?

Do I have a backup?
```

Do not casually use `-v` in an environment containing important information.

# 90. Restart Policies

Containers can stop because of:

```text
Host reboot
Application crash
Docker restart
Manual stop
Resource failure
```

Docker supports restart policies.

Common policies include concepts such as:

```text
no
on-failure
always
unless-stopped
```

Docker documents restart policies as controls for whether containers are automatically restarted after exit or Docker daemon restart.

---

# 91. `restart: no`

This means:

```text
Do not automatically restart.
```

This is the default behavior if no restart policy is configured.

---

# 92. `restart: on-failure`

Conceptually:

```text
Container exits successfully
        ↓
Do not restart

Container exits with failure
        ↓
Restart
```

This can be useful for certain workloads.

---

# 93. `restart: always`

Conceptually:

```text
Container stops
     ↓
Docker attempts restart
```

This is aggressive automatic restart behavior.

---

# 94. `restart: unless-stopped`

This is commonly useful for long-running local/server services.

Conceptually:

```text
Unexpected stop
      ↓
Restart

Docker/host restarts
      ↓
Restart

Administrator intentionally stopped container
      ↓
Respect intentional stop
```

For our lab:

```yaml
restart: unless-stopped
```

is reasonable.

---

# 95. Restart Policy Is Not High Availability

This distinction matters.

Suppose your host suffers:

```text
Disk failure
Hardware failure
Network failure
Entire VM loss
```

A restart policy cannot fix that.

```text
restart: always
```

does not mean:

```text
high availability
```

It only controls container restart behavior on the same Docker environment.

High availability requires a broader architecture.

# 96. Health Checks

A running container is not necessarily a healthy application.

Consider:

```text
Container process exists
        ↓
Docker says running
```

but:

```text
SonarQube still initializing
```

or:

```text
SonarQube cannot reach database
```

or:

```text
Web service unhealthy
```

Therefore:

```text
RUNNING
≠
READY
≠
HEALTHY
```

Health checks help distinguish these states.

---

# 97. PostgreSQL Health Check

A useful PostgreSQL health check can use:

```bash
pg_isready
```

For example in Compose:

```yaml
healthcheck:
  test: ["CMD-SHELL", "pg_isready -U sonar -d sonarqube"]
  interval: 10s
  timeout: 5s
  retries: 5
  start_period: 10s
```

---

# 98. Understanding PostgreSQL Health Check

`pg_isready` checks whether PostgreSQL is accepting connections.

So:

```text
Container started
        ↓
PostgreSQL initializing
        ↓
pg_isready fails
        ↓
Not healthy yet
        ↓
PostgreSQL ready
        ↓
pg_isready succeeds
        ↓
Healthy
```

This gives Compose better information than simply knowing the container process exists.

---

# 99. Health-Based `depends_on`

We can improve SonarQube:

```yaml
depends_on:
  db:
    condition: service_healthy
```

Now the intention becomes:

```text
Start PostgreSQL
      ↓
Wait for health check
      ↓
PostgreSQL healthy
      ↓
Start SonarQube
```

This is better than assuming that:

```text
PostgreSQL container started
```

means:

```text
PostgreSQL ready.
```

# 100. SonarQube Health Check

A health/readiness check should query an appropriate endpoint from the exact SonarQube version being deployed.

For teaching purposes, the pattern is:

```text

    ↓
HTTP request
    ↓
SonarQube endpoint
    ↓
Response
    ↓
healthy / unhealthy
```

Before relying on a specific API path in production, verify it against the exact current SonarQube version because supported APIs can evolve.

# 117. Important PostgreSQL Initialization Trap

The PostgreSQL image uses its initialization variables when creating a new database data directory.


```text

Environment configuration
```

```text
Empty new volume
```

# 138. Complete Teaching Compose File

A more explicit lab configuration becomes:

```yaml
services:
  db:
    image: postgres:17
    container_name: sonar-db
    environment:
      POSTGRES_DB: sonarqube
      POSTGRES_USER: sonar
      POSTGRES_PASSWORD: ${SONAR_DB_PASSWORD}
    volumes:
      - postgresql_data:/var/lib/postgresql/data
    networks:
      - sonar-network
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U sonar -d sonarqube"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 10s
    restart: unless-stopped

  sonarqube:
    image: sonarqube:community
    container_name: sonarqube
    depends_on:
      db:
        condition: service_healthy
    environment:
      SONAR_JDBC_URL: jdbc:postgresql://db:5432/sonarqube
      SONAR_JDBC_USERNAME: sonar
      SONAR_JDBC_PASSWORD: ${SONAR_DB_PASSWORD}
    ports:
      - "9000:9000"
    volumes:
      - sonarqube_data:/opt/sonarqube/data
      - sonarqube_extensions:/opt/sonarqube/extensions
      - sonarqube_logs:/opt/sonarqube/logs
    networks:
      - sonar-network
    restart: unless-stopped

volumes:
  sonarqube_data:
  sonarqube_extensions:
  sonarqube_logs:
  postgresql_data:

networks:
  sonar-network:
    driver: bridge
```

This gives us:

```text
Docker Host
│
├── sonar-network
│      │
│      ├── sonarqube
│      │      ↓
│      │   TCP 9000
│      │
│      └── db
│             ↓
│          TCP 5432
│
├── sonarqube_data
├── sonarqube_extensions
├── sonarqube_logs
└── postgresql_data
```

# 139. What Is a Bridge Network?

For a normal single-host Docker environment, a bridge network allows containers on the same Docker host to communicate through an isolated virtual network.

Conceptually:

```text
Physical Host
    ↓
Docker
    ↓
Virtual Bridge Network
    │
    ├── SonarQube
    └── PostgreSQL
```

It is not a physical Ethernet bridge sitting beside your laptop.

It is software-defined container networking.

# 150. Data Persistence vs Container Immutability

A useful DevOps mental model is:

```text
CONTAINERS
Disposable

DATA
Persistent
```

```text
Application container breaks
       ↓
Replace container
```

rather than:

```text
SSH into container
↓
manually repair it for six months
```

This is one of the philosophical differences between traditional server management and container-oriented operations.

# 151. Why Extensions Need Persistence

Suppose SonarQube has an extension installed under:

```text
/opt/sonarqube/extensions
```

If that extension exists only inside a container's writable layer:

```text
Container deleted
      ↓
Extension gone
```

A persistent extensions volume prevents this.

However, plugin management should still be deliberate.

An incompatible plugin can prevent a future SonarQube version from starting correctly.

Persistence does not eliminate compatibility concerns.

---

# 152. Why Logs May Need Persistence

Containers can be recreated.

If diagnostic information exists only inside a removed container:

```text
Failure
↓
Container deleted
↓
Evidence lost
```

Persistent logging or centralized log collection makes troubleshooting easier.

In production, a stronger design might send logs to:

```text
Central logging platform
```

rather than depending only on a local Docker volume.

# 153. Why SonarQube Data Needs Persistence

SonarQube's data directory includes search/index-related state.

A volume allows that state to survive container replacement.

But remember:

```text
SonarQube data volume
+
PostgreSQL volume
```

do not have equal roles.

The relational database remains fundamental persistent application state.

Later backup design must respect that architecture.

# 158. Common Beginner Mistakes

### Mistake 1: Thinking an image is a container

Remember:

```text
Image = template
Container = instance
```

### Mistake 2: Using `localhost` for the PostgreSQL hostname

Inside SonarQube:

```text
localhost = SonarQube container
```

Use the database service name.

### Mistake 3: Forgetting volumes

Container deletion can otherwise remove container-local state.

### Mistake 4: Publishing PostgreSQL unnecessarily

Containers can communicate over their internal Docker network.

### Mistake 5: Hard-coding production passwords into Compose

Use appropriate secret management.

### Mistake 6: Assuming `depends_on` alone means PostgreSQL is ready

Startup and readiness are different.

### Mistake 7: Assuming `running` means `healthy`

Check application readiness.

### Mistake 8: Using `docker compose down -v` casually

It can remove persistent volumes.

### Mistake 9: Treating restart policies as high availability

They only restart containers within the Docker environment.

### Mistake 10: Using moving tags blindly in production

Pin tested versions.

### Mistake 11: Assuming Docker eliminates memory requirements

SonarQube and Elasticsearch still consume real host resources.

### Mistake 12: Editing running containers manually

Prefer reproducible configuration.

### Mistake 13: Treating a Docker volume as a backup

Persistence and backup solve different problems.

### Mistake 14: Ignoring database initialization state

Changing an environment variable does not necessarily modify an existing persistent database.

### Mistake 15: Running random third-party SonarQube images

Prefer official, trusted images.

**20.** No. Persistence is not backup.
