# Part 12: Building a SonarQube CI/CD Pipeline

## Move from Manual Scanning to Automated Quality Control

In the previous parts, you learned how to analyze code manually.

You learned workflows such as:

```text
Application
↓
Build
↓
Unit Tests
↓
Coverage
↓
SonarScanner
↓
SonarQube
```

You also learned how build systems change the scanning process:

```text
Maven
↓
mvn clean verify sonar:sonar
```

and:

```text
Gradle
↓
./gradlew build sonar
```

But there is a serious limitation.

A developer must remember to run those commands.

That is not enough for a production engineering process.

What happens when someone forgets?

What happens when someone intentionally skips SonarQube?

What happens when the developer runs SonarQube locally but pushes different code?

What happens when tests were never executed?

What happens when coverage falls below the team's standard?

What happens when the Quality Gate fails but the application is still deployed?

This is where CI/CD changes everything.

Instead of saying:

```text
Developer SHOULD run SonarQube
```

we create:

```text
Pipeline MUST run SonarQube
```

That difference is extremely important.

The complete architecture becomes:

```text
Git Push
↓
Checkout
↓
Build
↓
Unit Tests
↓
Coverage
↓
SonarQube Analysis
↓
Quality Gate
↓
PASS?
↙        ↘
YES       NO
↓          ↓
Build      Stop
Artifact   Pipeline
↓
Deploy
```

By the end of this part, you should understand not only how SonarQube runs inside CI/CD, but how to design the pipeline so that bad code cannot simply bypass your engineering standards.

---

# 1. The Problem With Manual SonarQube Analysis

Imagine five developers:

```text
Developer A
Developer B
Developer C
Developer D
Developer E
```

The team tells everyone:

```text
Before pushing code,
please run SonarQube.
```

Developer A remembers.

Developer B forgets.

Developer C runs it but ignores the Quality Gate.

Developer D runs it against old code.

Developer E does not have SonarScanner configured correctly.

Now your quality process looks like:

```text
Developer A → Scan ✓

Developer B → No Scan

Developer C → Scan → Gate Failed → Push Anyway

Developer D → Wrong Analysis

Developer E → Scanner Broken → Push Anyway
```

This is not enforcement.

It is a recommendation.

---

# 2. Why Manual Scanning Is Insufficient

Manual analysis depends on human behavior.

Humans:

```text
Forget

Make mistakes

Use different environments

Use different tool versions

Skip inconvenient steps

Misconfigure scanners

Ignore warnings

Run commands in the wrong order
```

Production engineering should not depend entirely on remembering a checklist.

We automate the checklist.



# 5. What Is CI?

CI means:

```text
Continuous Integration
```

It is the practice of frequently integrating code changes into a shared repository while automatically validating those changes.

At beginner level:

```text
Developer changes code
↓
Pushes code
↓
Automated system checks code
↓
Problems are discovered early
```

---

# 6. What Does CI Usually Do?

CI may automatically perform:

```text
Checkout

Compilation

Linting

Unit testing

Coverage generation

Static analysis

Security checks

Packaging
```

SonarQube normally belongs primarily in this part of the software-delivery process.



```text
↓

↓

↓

↓
```

# 9. Continuous Deployment

Example:

```text

↓

↓

↓
Analyze
↓

↓

↓

↓

```

# 22. Why Checkout Must Come First

You cannot:

```text

↓
```

# 23. Checkout Must Use the Correct Commit

Imagine:

```text

```

---

# 42. What Is a Token?

A token is an authentication credential.

Instead of giving CI:

```text
Username
+
Password
```

you provide a generated token with appropriate permissions.

The token represents an identity allowed to perform analysis.

---

# 43. Why Tokens Are Better for Automation

Tokens can generally be:

```text
Generated

Scoped

Rotated

Revoked

Managed independently
```

This makes them more appropriate for automation than sharing a human password.

---

# 44. Tokens Are Secrets

Treat:

```text
SONAR_TOKEN
```

like a password.

Never:

```text
Commit it to Git
```

Never:

```text
Put it in README
```

Never:

```text
Post it in screenshots
```

Never:

```text
Print it in CI logs
```

---

# 45. Pipeline Credentials

A production pipeline may require multiple credentials.

Examples:

```text
SONAR_TOKEN

Artifact Repository Credential

Container Registry Credential

Cloud Deployment Credential

Kubernetes Credential
```

Do not combine everything into one powerful secret.

---

# 46. Least Privilege

A SonarQube scanner credential should have only the permissions it needs.

If the CI job only needs to analyze one project, do not automatically give it broad administrative privileges.

Think:

```text
Required Action
↓
Minimum Permission
↓
Dedicated Credential
```

---

# 47. Environment Variables

CI systems can expose configuration to commands through environment variables.

Example:

```text
SONAR_HOST_URL
```

and:

```text
SONAR_TOKEN
```

Then scanner processes can read those values.

---

# 48. Why Environment Variables Help

Without them:

```text
Source Repository
↓
Contains Secret
```

Dangerous.

With secret management:

```text
CI Secret Store
↓
Runtime Environment Variable
↓
Scanner
```

The repository never needs the real secret.

---

# 49. Example Local Environment Variables

For a local lab:

```bash
export SONAR_HOST_URL='http://localhost:9000'
export SONAR_TOKEN='YOUR_TOKEN'
```

Then:

```bash
sonar-scanner
```

can use those values.

In production CI, use the CI platform's secret-management mechanism instead of manually exporting permanent secrets.

---

# 50. Environment Variable vs Secret Store

These are related but not identical.

A secret store protects the value at rest.

Example:

```text
CI Secrets
↓
Encrypted/Protected Storage
```

At runtime:

```text
Secret
↓
Environment Variable
↓
Process
```

So:

```text
Secret Store
```

protects storage.

```text
Environment Variable
```

is one way of delivering the value to the process.

---

# 51. Never Commit a `.env` File Containing Real Secrets

Bad:

```text
.env
```

contains:

```text
SONAR_TOKEN=real-secret
```

and gets committed.

Now:

```text
Git History
↓
Contains Secret
```

Deleting the latest file may not remove it from history.

Prevent the exposure in the first place.

---

# 52. Secret Rotation

Suppose a SonarQube token is exposed.

Correct response:

```text
Revoke Token
↓
Create Replacement
↓
Update CI Secret
↓
Verify Pipeline
↓
Investigate Exposure
```

Do not merely delete the token from the latest commit and assume the problem is solved.

---

# 53. Stage Eight: Quality Gate

This is where analysis becomes policy enforcement.

Without the Quality Gate:

```text
SonarQube
↓
Interesting Dashboard
```

With the Quality Gate:

```text
SonarQube
↓
Engineering Decision
↓
Continue / Stop
```

---

# 54. Analysis Submission and Quality Gate Are Not the Same Event

This distinction is extremely important.

Scanner:

```text
Analyze
↓
Submit Report
```

SonarQube Server:

```text
Receive Report
↓
Compute Engine Processes Report
↓
Metrics Calculated
↓
Issues Evaluated
↓
Quality Gate Calculated
```

There is a time gap.

---

# 55. Why Scanner Success Does Not Mean Quality Gate Success

You may see:

```text
EXECUTION SUCCESS
```

This can mean:

```text
Analysis report was successfully submitted
```

It does not necessarily mean:

```text
Quality Gate passed.
```

Those are separate results.

---

# 56. Asynchronous Processing

The architecture is:

```text
Scanner
↓
Submit Analysis
↓
SonarQube Queue
↓
Compute Engine
↓
Process
↓
Quality Gate
```

The scanner may finish before server processing is complete.

---

# 57. The Deployment Race Condition

Consider this dangerous pipeline:

```text
SonarScanner
↓
Report Submitted
↓
Pipeline Immediately Deploys
```

Meanwhile:

```text
SonarQube
↓
Still Processing
```

Two seconds later:

```text
Quality Gate = FAILED
```

But the application has already deployed.

That defeats enforcement.

---

# 58. The Correct Architecture

You need:

```text
SonarQube Analysis
↓
Wait for Quality Gate
↓
PASS?
```

Only then:

```text
Package / Deploy
```

---

# 59. Waiting for the Quality Gate

One scanner-based approach is:

```text
sonar.qualitygate.wait=true
```

Conceptually:

```text
Scanner submits report
↓
Scanner waits
↓
SonarQube processes report
↓
Quality Gate calculated
↓
Result returned
```

---

# 60. Example Scanner Command

Conceptually:

```bash
sonar-scanner \
  -Dsonar.qualitygate.wait=true
```

If the gate fails, the analysis step can fail the pipeline.

---

# 61. Maven Example

Conceptually:

```bash
mvn clean verify sonar:sonar \
  -Dsonar.qualitygate.wait=true
```

Flow:

```text
Maven Build
↓
Tests
↓
Coverage
↓
Sonar Analysis
↓
Wait
↓
Quality Gate
```

---

# 62. Gradle Example

Conceptually:

```bash
./gradlew clean test jacocoTestReport sonar \
  -Dsonar.qualitygate.wait=true
```

Exact task sequence still depends on the project.

---

# 63. Quality Gate Timeout

Waiting forever would also be dangerous.

Suppose SonarQube is overloaded.

The analysis enters:

```text
Compute Engine Queue
```

and never completes within an acceptable pipeline window.

Therefore waiting has a timeout.

The pipeline needs to distinguish:

```text
Quality Gate FAILED
```

from:

```text
Quality Gate result could not be obtained in time.
```

Both should normally prevent automatic deployment until understood.

---

# 64. Why Timeout Should Not Mean PASS

Bad logic:

```text
Could not obtain Quality Gate
↓
Assume PASS
↓
Deploy
```

That is fail-open behavior.

For an enforcement control, you usually want:

```text
Could not verify required control
↓
Stop
↓
Investigate
```

This is fail-closed behavior.

---

# 65. Fail Open vs Fail Closed

Fail open:

```text
Control unavailable
↓
Continue anyway
```

Fail closed:

```text
Control unavailable
↓
Stop
```

For a required production quality control, fail closed is usually safer.

---

# 66. Failing Pipelines Safely

A failed pipeline should stop risky downstream actions.

It should not:

```text
Delete production

Corrupt infrastructure

Leak credentials

Leave half-deployed resources
```

Failure handling should be intentional.

---

# 67. Pipeline Exit Codes

Most CI systems use process exit codes.

Conceptually:

```text
0
=
Success
```

```text
Non-zero
=
Failure
```

If SonarScanner exits non-zero because the Quality Gate fails, the CI platform can mark the step/job as failed.

---

# 68. Do Not Hide Failure

Dangerous shell pattern:

```bash
sonar-scanner || true
```

This says:

```text
If scanner fails
↓
pretend command succeeded
```

That can defeat enforcement.

---

# 69. Another Dangerous Pattern

```bash
mvn sonar:sonar || echo "Sonar failed"
```

If the shell command ultimately exits successfully, the pipeline may continue.

Logging:

```text
Sonar failed
```

is not the same as:

```text
Pipeline stopped.
```

---

# 70. `continue-on-error` Style Configuration

Many CI systems provide a feature equivalent to:

```text
Continue even if this step fails
```

That can be useful for optional informational checks.

But do not use it for a mandatory Quality Gate unless you deliberately want the gate to be non-blocking.

---

# 71. Blocking vs Informational Analysis

Informational:

```text
SonarQube Fails
↓
Show Warning
↓
Continue
```

Blocking:

```text
SonarQube Fails
↓
Stop Pipeline
```

For production quality enforcement, the second is usually the intended model.

---

# 72. Quality Gate as a Release Control

Think of the gate as:

```text
Release Control
```

not:

```text
Pretty Dashboard Badge
```

Architecture:

```text
Analysis Results
↓

↓
Release Decision
```

# 74. Why Package After Quality Gate?

One strategy is:

```text
Validate first
↓
Only create/publish release artifact if acceptable
```

This avoids publishing artifacts that should never be released.

However, some pipelines build the artifact earlier and only publish/promote it after validation.

The important requirement is:

```text
Failed Quality Gate
must not reach
deployment.
```

---

# 75. Build Once Principle

In mature pipelines, you often want to build a release artifact once and promote the exact same artifact through environments.

Example:

```text
Build Artifact
↓
Test Artifact
↓
Approve Artifact
↓
Deploy Same Artifact
```

rather than rebuilding different binaries for:

```text
Development

Staging

Production
```

This improves traceability.

---

# 76. Artifact Identity

A release artifact should be traceable back to:

```text
Commit

Build

Pipeline

Version
```

For example:

```text
payment-service:1.4.2
```

should correspond to a known source commit.

---

# 77. Stage Ten: Deploy

Deployment means moving the validated application into a runtime environment.

Examples:

```text
EC2

Kubernetes

ECS

Azure

Google Cloud

Virtual Machines

On-premises Servers
```

SonarQube itself does not deploy the application.

It controls whether the pipeline should be allowed to reach this stage.

---

# 78. Correct Deployment Relationship

```text
SonarQube
↓
Quality Gate
↓
Decision
```

Then:

