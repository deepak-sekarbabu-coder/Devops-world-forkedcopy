# Part 9: Code Coverage, Unit Tests and Test Reports

## Connect Testing Information to SonarQube

In Part 8, you learned how a Quality Gate turns analysis results into an engineering decision.

The flow was:

```text
Code Change
    ↓
Analysis
    ↓
New Code Metrics
    ↓
Quality Gate
  ↙          ↘
PASS         FAIL
 ↓             ↓
Continue      Fix Code
```

One of the most important Quality Gate measurements is:

```text
Coverage
```

But where does SonarQube get coverage information?

This is where many beginners become confused.

They run SonarQube and expect it to automatically execute tests and calculate coverage.

That is not how the normal architecture works.

The correct architecture is:

```text
Application
    ↓
Unit Tests
    ↓
Coverage Tool
    ↓
Coverage Report
    ↓
SonarScanner
    ↓
SonarQube
```

The key principle of this entire part is:

```text
SONARQUBE DOES NOT NORMALLY
CREATE YOUR TEST COVERAGE.

YOUR TESTING / COVERAGE TOOL
CREATES THE COVERAGE REPORT.

SONARQUBE IMPORTS IT.
```

That distinction explains many real-world coverage problems.

---

# 1. What Problem Does Code Coverage Solve?

Imagine you have this function:

```python
def calculate_discount(price, percentage):
    return price - (price * percentage / 100)
```

You write the code.

It looks reasonable.

But one important question remains:

> Did your automated tests actually execute this code?

That is what code coverage helps answer.

Coverage provides information about which parts of your source code were exercised when tests ran.

Think:

```text
Application Code
      ↓
Tests Execute
      ↓
Coverage Tool Observes Execution
      ↓
Coverage Data
```

Without coverage, you may have hundreds of tests but still not know which parts of the application they actually exercise.

---

# 2. What Code Coverage Means

Code coverage measures how much of your code was exercised during testing.

At beginner level, think:

```text
Code
↓
Tests Run
↓
Which Code Was Actually Executed?
```

If:

```text
100 executable lines
```

exist and tests execute:

```text
80 of them
```

you may have roughly:

```text
80% line coverage
```

depending on the language, tool and coverage calculation.

Coverage is not merely:

```text
Do tests exist?
```

It is closer to:

```text
Which portions of the code did those tests execute?
```

---

# 3. Coverage Does Not Tell You Everything

This distinction is essential.

Suppose you have:

```text
Coverage:
90%
```

That does not automatically mean:

```text
Software quality:
90%
```

Coverage is only one measurement.

It does not prove that:

```text
Tests contain good assertions

Business requirements are correct

Security is correct

Edge cases are covered

Tests verify failure scenarios

Integration works

Production configuration is correct
```

Coverage tells you about execution during tests.

It does not prove correctness.

---

# 4. SonarQube Does Not Replace Testing

SonarQube performs static analysis and imports information from other tools.

It is not a replacement for:

```text
Unit tests

Integration tests

API tests

End-to-end tests

Performance tests

Security tests

Manual testing
```

Static analysis and testing solve different problems.

Think:

```text
STATIC ANALYSIS

Inspect code without running application behavior
```

versus:

```text
TESTING

Execute code and verify behavior
```

Both matter.

---

# 5. Static Analysis vs Testing

Consider:

```python
def divide(a, b):
    return a / b
```

Static analysis may identify certain suspicious patterns.

But a unit test can actually execute:

```python
divide(10, 2)
```

and verify:

```text
Expected:
5
```

Another test can execute:

```python
divide(10, 0)
```

and determine how the application handles division by zero.

Static analysis does not replace this behavioral verification.

---

# 6. SonarQube's Role in Testing

SonarQube can consume coverage information generated during testing.

Architecture:

```text
Tests
 ↓
Coverage Tool
 ↓
Coverage Report
 ↓
SonarScanner
 ↓
SonarQube
 ↓
Coverage Metric
```

SonarQube then combines coverage with:

```text
Issues
Duplications
Complexity
Security findings
Reliability findings
Maintainability findings
```

to provide a broader quality view.

---

# 7. What Is a Unit Test?

A **unit test** checks a small unit of code independently.

A unit may be:

```text
Function
Method
Class
Small component
```

Example:

```python
def add(a, b):
    return a + b
```

Test:

```python
def test_add():
    assert add(2, 3) == 5
```

The test verifies expected behavior.

---

# 8. Why Unit Tests Matter

Unit tests provide fast feedback.

Suppose someone changes:

```python
def add(a, b):
    return a - b
```

The existing test should fail:

```text
Expected:
5

Actual:
-1
```

That gives engineers immediate evidence that behavior changed incorrectly.

---

# 9. Unit Tests and DevOps

Unit tests are not only a developer concern.

In CI/CD:

```text
Developer
    ↓
Git Push
    ↓
CI Runner
    ↓
Unit Tests
    ↓
PASS / FAIL
```

If tests fail:

```text
Pipeline Stops
```

If they pass:

```text
Continue
```

Now add coverage:

```text
Unit Tests
    ↓
Coverage Tool
    ↓
Coverage Report
```

Then SonarQube can evaluate coverage as part of the Quality Gate.

---

# 10. Test Success vs Coverage

These are different.

Suppose:

```text
20 tests
```

all pass.

Result:

```text
Tests:
PASS
```

But coverage may be:

```text
34%
```

Why?

Because those 20 tests may only exercise a small portion of the application.

Therefore:

```text
All Tests Passing
≠
High Coverage
```

---

# 11. High Coverage vs Passing Tests

The reverse distinction also matters.

Suppose coverage is:

```text
95%
```

but one test fails.

You still have:

```text
Test Failure
```

Coverage does not override correctness.

Pipeline logic may be:

```text
Run Tests
   ↓
Tests Pass?
 ↙       ↘
No       Yes
↓         ↓
Stop    Generate Coverage
```

Depending on tooling, coverage may still be produced on failed tests, but the build should still treat test failures appropriately.

---

# 12. Line Coverage

Line coverage measures whether executable lines were run during tests.

Example:

```python
def calculate_total(price, quantity):
    subtotal = price * quantity
    tax = subtotal * 0.1
    return subtotal + tax
```

Suppose your test calls:

```python
calculate_total(100, 2)
```

The executable lines inside the function run.

They can therefore count as covered.

---

# 13. Uncovered Line Example

Consider:

```python
def calculate_total(price, quantity):
    if quantity <= 0:
        return 0

    subtotal = price * quantity
    return subtotal
```

Test:

```python
def test_total():
    assert calculate_total(50, 2) == 100
```

This executes:

```text
quantity <= 0
```

as false and then continues.

But the line:

```python
return 0
```

may never execute.

Coverage tooling can reveal that missing path.

---

# 14. Why Line Coverage Helps

Without coverage information, you may believe:

> I tested calculate_total.

Technically yes.

But coverage tells you:

```text
Normal path tested
Error/edge path not exercised
```

That can guide additional testing.

---

# 15. Branch Coverage

Branch coverage goes deeper.

It considers the possible outcomes of control-flow decisions.

Example:

```python
def access(age):
    if age >= 18:
        return "allowed"
    return "denied"
```

There are two meaningful paths:

```text
age >= 18
    ↓
TRUE
    ↓
allowed
```

and:

```text
age >= 18
    ↓
FALSE
    ↓
denied
```

---

# 16. Partial Branch Testing

Suppose you test only:

```python
assert access(30) == "allowed"
```

You have tested the true branch.

You have not tested:

```python
assert access(15) == "denied"
```

Branch coverage helps identify that gap.

---

# 17. Why Branch Coverage Matters

Imagine:

```python
def withdraw(balance, amount):
    if amount <= balance:
        return balance - amount
    return balance
```

Testing only:

```python
withdraw(100, 20)
```

does not test insufficient funds.

That missing branch may contain critical behavior.

For:

```text
Banking
Payments
Authentication
Permissions
Billing
```

branch coverage can be particularly useful.

---

# 18. Line Coverage vs Branch Coverage

Remember:

```text
LINE COVERAGE
↓
Were executable lines run?
```

```text
BRANCH COVERAGE
↓
Were different decision outcomes exercised?
```

A project may have strong line coverage but weaker branch coverage.

That is not contradictory.

---

# 19. Example of Misleading Line Coverage

Consider:

```python
def classify(value):
    if value > 100:
        return "large"
    return "small"
```

One test:

```python
assert classify(150) == "large"
```

executes the conditional line and return line for the true path.

But:

```text
value <= 100
```

has never been tested.

Branch coverage gives better information about that decision.

---

# 20. What Is a Coverage Tool?

A coverage tool observes code execution while tests run.

Examples include:

```text
Java
→ JaCoCo

JavaScript
→ Jest / Istanbul-based coverage tooling

Python
→ Coverage.py / pytest-cov
```

The specific ecosystem matters.

SonarQube generally consumes the report produced by these tools rather than replacing them.

---

# 21. Coverage Tool Architecture

```text
Application Code
       ↓
Coverage Instrumentation / Monitoring
       ↓
Tests Run
       ↓
Coverage Data Collected
       ↓
Report Generated
```

Different tools implement this differently.

At beginner level, remember:

```text
Test Framework
≠
Coverage Tool
```

although some test frameworks integrate coverage tooling conveniently.

---

# 22. Test Framework vs Coverage Tool

For Python:

```text
pytest
```

primarily runs tests.

Coverage may come from:

```text
coverage.py
```

or:

```text
pytest-cov
```

For Java:

```text
JUnit
```

runs tests.

JaCoCo collects coverage.

For JavaScript:

```text
Jest
```

can run tests and integrate coverage generation conveniently.

Different responsibilities can be bundled into one developer experience.

---

# 23. What Is a Coverage Report?

After testing, the coverage tool must produce coverage data in a format SonarQube understands.

Conceptually:

```text
Tests
 ↓
Coverage Tool
 ↓
coverage.xml
```

or:

```text
lcov.info
```

or:

```text
jacoco.xml
```

The exact format depends on the language/tool.

---

# 24. Human Report vs Machine Report

Coverage tools may generate reports intended for humans:

```text
HTML report
```

and reports intended for machines:

```text
XML
LCOV
JSON
```

SonarQube expects supported machine-readable formats.

Do not assume:

```text
coverage/index.html
```

is automatically what SonarQube needs.

---

# 25. The Critical Ordering Requirement

Coverage must be generated before SonarScanner attempts to import it.

Correct:

```text
Run Tests
   ↓
Generate Coverage Report
   ↓
Run SonarScanner
```

Wrong:

```text
Run SonarScanner
   ↓
Generate Coverage Later
```

Why?

Because at scan time SonarScanner needs the report available at the expected location.

---

# 26. Correct CI Ordering

```text
Checkout
 ↓
Install Dependencies
 ↓
Compile / Build
 ↓
Run Tests
 ↓
Generate Coverage
 ↓
Verify Coverage Report Exists
 ↓
Run SonarQube Analysis
```

That sequence solves many real-world problems.

---

# 27. What Does SonarScanner Do With Coverage?

Conceptually:

```text
Coverage Report
       ↓
SonarScanner finds report
       ↓
Parses coverage information
       ↓
Associates coverage with source files
       ↓
Sends analysis report
       ↓
SonarQube processes results
       ↓
Dashboard displays coverage
```

SonarQube does not need to rerun the tests.

---

# 28. Coverage Report Paths

SonarScanner needs to know:

> Where is the coverage report?

That is why report-path parameters exist.

Example:

```properties
sonar.python.coverage.reportPaths=coverage.xml
```

or:

```properties
sonar.javascript.lcov.reportPaths=coverage/lcov.info
```

or:

```properties
sonar.coverage.jacoco.xmlReportPaths=target/site/jacoco/jacoco.xml
```

Current SonarQube documentation uses these language-specific properties for Python, JS/TS and JVM JaCoCo reports.

---

# 29. Relative Paths

Suppose project structure is:

```text
my-project/
├── src/
├── tests/
├── coverage/
│   └── lcov.info
└── sonar-project.properties
```

Then:

```properties
sonar.javascript.lcov.reportPaths=coverage/lcov.info
```

means:

```text
Start from project root
      ↓
coverage/
      ↓
lcov.info
```

Understanding working directories is essential.

---

# 30. Absolute vs Relative Paths

Some coverage report properties allow:

```text
Relative paths
```

and/or:

```text
Absolute paths
```

depending on the language-specific property.

Relative paths are usually easier to keep portable across:

```text
Developer laptop

CI runner

Different environments
```

Avoid hard-coding a path like:

```text
/Users/ann/Desktop/project/coverage.xml
```

inside repository configuration.

That will fail on another machine.

---

# 31. The Most Common Coverage Failure

One of the most common SonarQube problems is:

```text
Tests passed.

Coverage report exists.

SonarQube shows 0% coverage.
```

Why?

Often:

```text
Scanner cannot find the report.
```

Architecture:

```text
Report Exists
       ↓
But Wrong Path Configured
       ↓
Scanner Does Not Import It
       ↓
SonarQube Coverage Missing
```

---

# 32. Always Verify the File

Before running SonarScanner, verify:

```bash
ls -l coverage.xml
```

or:

```bash
ls -l coverage/lcov.info
```

or:

```bash
ls -l target/site/jacoco/jacoco.xml
```

If the file does not exist, SonarScanner cannot import it.

This simple check saves enormous troubleshooting time.

---

# 33. Useful File Investigation Commands

Use:

```bash
pwd
```

Purpose:

```text
Show current working directory.
```

Use:

```bash
find . -name "coverage.xml"
```

Purpose:

```text
Search for coverage.xml below the current directory.
```

Use:

```bash
find . -name "lcov.info"
```

Use:

```bash

```

This tells you the report's actual location.

---

# 34. Do Not Guess the Report Path

Bad troubleshooting:

```text
I think Jest created coverage.xml somewhere.
```

Better:

```bash
find . -type f | grep -E 'coverage|jacoco|lcov'
```

Then inspect the actual output.

Troubleshooting should use evidence.

---

# 35. Report Path Mental Model

Always answer these questions:

```text
What command generated the report?

What file was generated?

What format is it?

Where was it written?

From which directory does SonarScanner run?

What path is configured?

Does that path resolve to the file?
```

If you can answer all seven, most report-path problems become straightforward.

JaCoCo stands for:


JaCoCo can instrument Java code during testing, collect execution data and generate coverage reports.

For SonarQube, the important output is:

# 39. Java Unit Test

Example:

```java
import static org.junit.jupiter.api.Assertions.assertEquals;
import org.junit.jupiter.api.Test;

public class CalculatorTest {

    @Test
    void addsTwoNumbers() {
        Calculator calculator = new Calculator();

```

This test verifies the `add()` method.

It does not necessarily exercise `divide()`.

Coverage should reveal that gap.

# 40. JaCoCo Maven Plugin

In a Maven project, JaCoCo is commonly configured through:

```xml
org.jacoco:jacoco-maven-plugin
```

Conceptually:

```text
Maven
 ↓
JaCoCo prepares agent
 ↓
Tests execute
 ↓
Coverage collected
 ↓
JaCoCo report generated
```

Sonar's Java coverage guidance specifically describes using `jacoco:prepare-agent` and `jacoco:report` to produce the report before Sonar analysis.

---

# 41. Teaching Example: Maven JaCoCo Configuration

A simplified configuration might look like:

```xml
<plugin>
    <groupId>org.jacoco</groupId>
    <artifactId>jacoco-maven-plugin</artifactId>

    <executions>
        <execution>
            <goals>
                <goal>prepare-agent</goal>
            </goals>
        </execution>

        <execution>
            <id>report</id>
            <phase>test</phase>
            <goals>
                <goal>report</goal>
            </goals>
        </execution>
    </executions>
</plugin>
```

The exact plugin version should be pinned according to the project's dependency-management policy.

Do not blindly copy old plugin versions from tutorials.

# 42. Generate Java Coverage

A typical workflow may include:

```bash
mvn clean test
```

or a project-specific profile such as:

```bash
mvn clean verify -Pcoverage
```

depending on the Maven configuration.

Then inspect:

```bash

```

# 43. Explicit Java Report Path

If the report is generated somewhere nonstandard, configure:

```properties
sonar.coverage.jacoco.xmlReportPaths=target/site/jacoco/jacoco.xml
```

For multiple reports, SonarQube supports comma-delimited paths, and wildcards are supported for this property.

# 46. Java Troubleshooting: Report Missing

## Problem

```text
SonarQube coverage:
0%
```

## Investigation

Run:

```bash
find . -name "jacoco.xml"
```

If no result:

```text
JaCoCo report was not generated.
```

Possible causes:

```text
Plugin not configured

Report goal not executed

Tests skipped

Build failed before report generation

Wrong Maven profile
```

Fix report generation first.

Do not troubleshoot SonarQube yet.

---

# 47. Java Troubleshooting: Report Exists but Is Not Imported

Suppose:

```text
./module-a/target/site/jacoco/jacoco.xml
```

exists.

But configuration says:

```properties
sonar.coverage.jacoco.xmlReportPaths=target/site/jacoco/jacoco.xml
```

Scanner is running from the parent project.

The configured path may be wrong.

Correct it to match the project structure.

Evidence first:

```bash
pwd
find . -name jacoco.xml
```

# 48. Java Multi-Module Projects

Real Maven repositories may look like:

```text

├── service-a/
├── service-b/
├── common/
└── pom.xml
```

Coverage may be generated per module or aggregated.

This complicates path configuration.

For multi-module projects, you may need:

```text

```


Sonar's documentation provides a `report-aggregate` approach for Maven multi-module builds.
