# Part 11: SonarQube with Maven, Gradle and Common Build Systems

## Understand How Scanning Changes Depending on How Applications Are Built

In Part 10, you connected SonarQube to Git, branches, GitHub and pull requests.

You built this workflow:

```text
Developer
↓
Feature Branch
↓
GitHub
↓
Pull Request
↓
CI
↓
SonarQube Analysis
↓
Quality Gate
↓
Merge / Fix
```

But there is an important piece hidden inside:

```text
CI
```

What actually happens inside CI?

For many applications, SonarQube cannot simply appear and analyze a random folder without understanding how the application is structured.

Applications are built differently.

A Java project might use:

```text
Maven
```

Another Java project might use:

```text
Gradle
```

A JavaScript project might use:

```text
npm
```

A Python project might use:

```text
pip
pytest
coverage.py
```

A .NET project might use:

```text
dotnet
MSBuild
```

Therefore the real architecture is closer to:

```text
Source Code
↓
Build System
↓
Dependencies
↓
Compilation
↓
Tests
↓
Coverage
↓
Build Output
↓
SonarScanner
↓
SonarQube
```

This part teaches you how SonarQube fits into those different build ecosystems.

---

# 1. What Is a Build System?

Before learning SonarQube integration, understand the problem build systems solve.

Imagine a Java application containing:

```text
payment-service/
├── src/
│   ├── main/
│   │   └── java/
│   └── test/
│       └── java/
├── libraries
├── configuration
└── resources
```

The developer eventually needs to transform this into something the application can run.

That may require:

```text
Download dependencies
↓
Compile source code
↓
Compile tests
↓
Run tests
↓
Generate reports
↓
Package application
```

Doing all of this manually would become painful.

A build system automates those operations.

---

# 2. Build System Definition

At beginner level:

```text
Build System
=
A tool that coordinates the steps required
to turn source code into a usable application artifact
```

It may handle:

```text
Dependencies

Compilation

Testing

Packaging

Plugins

Code generation

Coverage

Static analysis

Deployment-related tasks
```

---

# 3. Build Systems Are Not All Identical

Different ecosystems use different tools.

Examples:

| Ecosystem             | Common Tools            |
| --------------------- | ----------------------- |
| Java                  | Maven, Gradle           |
| Kotlin                | Gradle, Maven           |
| JavaScript/TypeScript | npm, yarn, pnpm         |
| Python                | pip, Poetry, uv, pytest |
| .NET                  | dotnet CLI, MSBuild     |
| C/C++                 | CMake, Make, Ninja      |

SonarQube must work with the structure created by these tools.

---

# 4. Why Build-System Integration Matters to SonarQube

Suppose SonarQube needs to analyze Java.

Useful information may include:

```text
Source directories

Test directories

Compiled bytecode

Dependencies

Java version

Test reports

Coverage reports

Module structure
```

Your build system already knows much of this information.

Instead of manually telling SonarQube everything, build-integrated scanners can obtain much of it from the build.

Architecture:

```text
Build System
     ↓
Knows Project Structure
     ↓
SonarScanner Integration
     ↓
Less Manual Configuration
```

# 5. Scanner CLI vs Build-Integrated Scanner

Earlier you learned about SonarScanner.

Conceptually:

```text

↓
SonarScanner
↓

```

That model still exists.

But Maven and Gradle offer tighter integrations.

Maven:

```text

↓

↓
SonarQube
```

Gradle:

```text
Gradle Project
↓
SonarScanner for Gradle
↓
```

These scanners understand their build environments.

# 6. Why Build Integration Is Useful

Without integration you might manually configure:

```text
Where are sources?

Where are tests?

Where are compiled classes?

Where are dependencies?

What is the project version?

What is the project name?
```

Maven or Gradle already knows many of those answers.

That reduces configuration duplication.

---

# 7. Build Integration Does Not Mean SonarQube Builds Your Application

This distinction is critical.

SonarQube is not your compiler.

It is not Maven.

It is not Gradle.

It is not your test framework.

It is not your coverage generator.

Think:

```text
Build Tool
↓
Produces information

SonarScanner
↓
Consumes relevant information

SonarQube
↓
Evaluates quality
```

# 17. SonarScanner for Maven

For Maven projects, use:


You do not normally need a separately installed SonarScanner CLI for a standard Maven project.


# 19. Full Maven Goal

The full plugin goal is conceptually:

```bash
mvn org.sonarsource.scanner.maven:sonar-maven-plugin:sonar
```

The short:

```bash
mvn sonar:sonar
```

is much easier to read and commonly encountered.

# 20. What Happens When `mvn sonar:sonar` Runs?

Conceptually:

```text
Maven Starts
↓
Loads pom.xml
↓
Understands Project
↓
Loads Sonar Maven Plugin
↓
Collects Analysis Configuration
↓
Runs Analysis
↓
Creates Analysis Report
↓
Submits Report to SonarQube
```

Then SonarQube processes the report.

---

# 21. `mvn sonar:sonar` Does Not Automatically Mean Tests Were Run

This is an important beginner mistake.

If you only run:

```bash
mvn sonar:sonar
```

do not automatically assume:

```text
Compilation happened
Tests ran
Coverage was generated
Everything needed exists
```

The safer workflow commonly includes the build lifecycle first.

Example:

```bash
mvn clean verify sonar:sonar
```

---

# 22. Understanding Maven Lifecycle

Maven has predefined build lifecycle phases.

A simplified sequence is:

```text
validate
↓
compile
↓
test
↓
package
↓
verify
↓
install
↓
deploy
```

There are additional phases internally, but this is enough for our beginner mental model.

---

# 23. `validate`

Maven checks whether the project is correctly structured enough to proceed.

---

# 24. `compile`

Maven compiles application source code.

Conceptually:

```text
.java
↓
Java Compiler
↓
.class
```

Compiled output usually goes under:

```text
target/classes/
```

---

# 25. `test`

Maven runs unit tests.

Typical test output may include:

```text
target/surefire-reports/
```

depending on the test plugin configuration.

---

# 26. `package`

Maven packages compiled code.

For example:

```text
target/payment-service-1.0.0.jar
```

or:

```text
WAR
```

depending on the project.

---

# 27. `verify`

The `verify` phase performs verification steps configured in the project after packaging.

This is often a useful point for SonarQube workflows because compilation and testing have already occurred.

---

# 28. `install`

Maven installs the built artifact into the local Maven repository.

This becomes especially important for some multi-module analysis workflows.

---

# 29. `deploy`

Maven can publish artifacts to a remote artifact repository.

Do not confuse:

```text
Maven deploy
```

with:

```text
Deploy application to production
```

They are not necessarily the same thing.

---

# 30. Why Maven Lifecycle Order Matters

Suppose SonarQube needs:

```text
Compiled classes
Coverage report
Test report
```

but you run analysis before generating them.

Then:

```text

↓

↓
Output does not exist
↓

```

Correct:

```text

↓

↓
Coverage
↓
Analyze
```

# 32. Why `clean` Helps

Suppose yesterday's build produced:

```text

```

Today the code changed.

Old artifacts might remain.

Running:

```bash
mvn clean
```

removes previous build output.

Then the new build starts from a cleaner state.


In production:


# 52. Gradle Plugin Concept

A build file can apply the SonarQube plugin.

Conceptual Kotlin DSL:

```kotlin

}
```

Groovy DSL:

```groovy
plugins {

```

In real projects, pin an appropriate supported plugin version rather than blindly copying an old tutorial version.

# 53. Gradle Analysis Task

The analysis task is:

```bash

```

---

# 54. Why Prefer the Gradle Wrapper?

Many Gradle projects contain:

```text
gradlew
gradlew.bat
gradle/wrapper/
```

The wrapper lets the project define the Gradle version it expects.

Instead of relying on whichever global Gradle version happens to be installed:

```bash
gradle sonar
```

you commonly use:

```bash
./gradlew sonar
```

This improves reproducibility.

---

# 55. The Important Modern Gradle Behavior

Do not assume:

```bash
./gradlew sonar
```

automatically runs:

```text
compile

test

coverage
```

first.

Modern SonarScanner for Gradle expects the tasks producing required outputs to be executed before the `sonar` task.

This is extremely important.

---

# 56. Why This Matters

Suppose:

```text
sonar
```

needs:

```text
Compiled Java bytecode

JaCoCo XML report
```

but you never ran:

```text

test

jacocoTestReport
```

Then those files may not exist.

SonarQube cannot import files that were never generated.

# 61. `mustRunAfter` Is Not the Same as `dependsOn`

This is a useful Gradle distinction.

Conceptually:

```text
mustRunAfter
=
If both tasks run, enforce order.
```

Whereas:

```text
dependsOn
=
Running this task causes the dependency task to run.
```

Therefore ordering alone does not necessarily create the required task execution.

# 72. Multi-Module Projects

Real enterprise applications are often not one directory.

Example:

```text

├── pom.xml

├── payment-service/
├── notification-service/
```

---

# 73. Maven Parent Project

The root `pom.xml` might contain:

```xml
<modules>
    <module>customer-service</module>
    <module>payment-service</module>
    <module>notification-service</module>
    <module>shared-library</module>
</modules>
```

Maven understands the module relationship.

---

# 74. Maven Reactor

When Maven builds a multi-module project, it creates a reactor containing participating modules.

Conceptually:

```text
Root
├── Module A
├── Module B
└── Module C
```

Maven determines build order based on project relationships.

---

# 75. Why Multi-Module Sonar Analysis Is Different

Module B may depend on:

```text
Module A
```

If you analyze B before A has been built appropriately, dependency information may be missing.

That is why build order matters.

---

# 76. Multi-Module Maven Recommended Pattern

When build and analysis are separate steps:

```bash
mvn clean install
```

then:

```bash
mvn sonar:sonar
```

The first step builds and installs the modules locally.

The second performs analysis with the built module relationships available.

---

# 77. Why `install` Helps Multi-Module Builds

Imagine:

```text
payment-service

shared-library
```

Running:

```bash
mvn clean install
```

builds:

```text

```

and makes its artifact available in the local Maven repository.

Then dependent modules can resolve it.

# 79. Do Not Run Random Module-Level Scans

A common mistake:

```text

mvn sonar:sonar
```

without understanding the parent build.

This can break:

```text
Dependency resolution

Module relationships

Project identity

Coverage aggregation
```

Start from the project's intended build root unless you have a deliberate reason not to.

# 175. Production Awareness: Caching

CI may cache:

```text
Maven dependencies

Gradle dependencies

npm dependencies
```

to improve build speed.

Do not cache random build outputs without understanding consequences.

# 176. Production Awareness: Private Dependency Repositories

```text
Nexus Repository

Private npm registry

Private NuGet feed
```

If CI cannot authenticate to them:

```text

↓
Build fails
↓
Sonar analysis never happens
```

This is why DevOps engineers need to understand the entire pipeline, not only SonarQube.

# 177. Security: Dependency Credentials

```text
Tokens

API keys
```

# 178. Security: Build Scripts Are Powerful

Build systems can execute code.

A malicious:

```text

build.gradle

package.json script
```

can execute commands in CI.

Therefore build execution itself is a security boundary.

This matters especially for untrusted pull requests.

```text
↓
```

If powerful secrets are available to untrusted code, they may be stolen.

Design CI permissions carefully.
