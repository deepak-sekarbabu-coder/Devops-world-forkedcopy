# 1. What We Are Building

Imagine you have joined a company called:

```text
Example Payments
```

This is only our lab company.

The development team maintains a small payment API.

Developers regularly change the application.

Management does not want developers to merge code directly into `main` without automated checks.

The engineering requirements are:

1. Developers work on feature branches.
2. Changes go through pull requests.
3. The application must compile.
4. Unit tests must pass.
5. Coverage must be generated.
6. SonarQube must analyze the code.
7. The Quality Gate must pass.
8. Failed Quality Gates must block merging.
9. Secrets must not be stored in Git.
10. Successful code is packaged.
11. A container image is created.
12. Deployment occurs only from approved code.
13. SonarQube itself must be monitored.
14. SonarQube data must be backed up.
15. Operational failures must be diagnosable through logs and metrics.

This is much closer to real DevOps work than:

```text
Run sonar-scanner manually from laptop.
```

# 9. Create PaymentService

Create:

```text
src/main/java/com/veriqta/payments/PaymentService.java
```

Contents:

```java
package com.veriqta.payments;

public class PaymentService {

    private final PaymentValidator validator;

    public PaymentService(PaymentValidator validator) {
        this.validator = validator;
    }

    public String processPayment(double amount) {
        if (!validator.isValidAmount(amount)) {
            return "REJECTED";
        }

        return "APPROVED";
    }

    public static void main(String[] args) {
        PaymentValidator validator = new PaymentValidator();
        PaymentService service = new PaymentService(validator);

        System.out.println(service.processPayment(100.00));
    }
}
```

This is intentionally small.

But it contains real concepts:

```text
Input
↓
Validation
↓
Business Decision
↓
Result
```

# 11. Create the First Unit Test

```java
package com.veriqta.payments;

import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.assertFalse;
import static org.junit.jupiter.api.Assertions.assertTrue;

class PaymentValidatorTest {

    @Test
    void positiveAmountShouldBeValid() {
        PaymentValidator validator = new PaymentValidator();

        assertTrue(validator.isValidAmount(100.00));
    }

    @Test
    void zeroAmountShouldBeInvalid() {
        PaymentValidator validator = new PaymentValidator();

        assertFalse(validator.isValidAmount(0));
    }

    @Test
    void negativeAmountShouldBeInvalid() {
        PaymentValidator validator = new PaymentValidator();

        assertFalse(validator.isValidAmount(-50));
    }
}
```

We test three cases:

```text
Positive
Zero
Negative
```

This is already better than testing only the happy path.

Tests answer:

```text
Does the application behave as expected
for the cases we tested?
```

They do not answer:

```text

Are there security concerns?

Is code duplicated?

Are all important branches tested?

Does the code satisfy our engineering policy?
```

That is why we combine testing and SonarQube.

# 40. Quality Gate Strategy

For our beginner production project, use the current built-in Sonar way gate as the starting standard unless you have a justified custom policy.

Conceptually, our release expectation is:

```text

New Security Hotspots must be reviewed.

New code coverage must satisfy the gate.

New code duplication must remain acceptable.
```

Do not design a gate merely to produce green dashboards.

Design it to protect engineering quality.

# 42. Build the Pull Request Workflow

Create:

```text
.github/workflows/pull-request.yml
```

A teaching implementation:

```yaml
name: Pull Request Quality

on:
  pull_request:
    types: [opened, synchronize, reopened]

jobs:
  quality:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout repository
        uses: actions/checkout@v6
        with:
          fetch-depth: 0

      - name: Set up Java
        uses: actions/setup-java@v5
        with:
          distribution: temurin
          java-version: "21"
          cache: maven

      - name: Build, test and generate coverage
        run: mvn -B clean verify

      - name: SonarQube analysis
        run: >
          mvn -B
          org.sonarsource.scanner.maven:sonar-maven-plugin:sonar
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
          SONAR_HOST_URL: ${{ vars.SONAR_HOST_URL }}
```

Before using any third-party or GitHub Action version in a real production environment, review and pin versions according to your organization's supply-chain policy.

---

# 43. Why fetch-depth: 0?

SonarQube benefits from proper repository history and SCM metadata.

A shallow checkout can reduce analysis relevance.

Therefore:

```yaml
fetch-depth: 0
```

gives the workflow full history.

# 72. Main Branch Workflow

```yaml

  push:

      - main

        uses: actions/checkout@v6
        with:

        with:
          distribution: temurin

        run: mvn -B clean verify

      - name: SonarQube analysis and gate

      - name: Save application artifact
        uses: actions/upload-artifact@v4
        with:
          name: payment-service
```

# 73. Why Wait for the Gate Here?

For pull requests, repository decoration and required checks are usually a better developer-feedback mechanism.

For a deployment pipeline, we need a decision:

```text

```

Therefore waiting for the gate can be appropriate.

The tradeoff is that the workflow spends additional time waiting for SonarQube to finish server-side processing.
