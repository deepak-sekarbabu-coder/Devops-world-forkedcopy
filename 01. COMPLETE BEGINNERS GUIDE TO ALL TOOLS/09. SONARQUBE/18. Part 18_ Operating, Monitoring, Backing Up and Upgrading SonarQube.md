# Part 18: Operating, Monitoring, Backing Up and Upgrading SonarQube

## Learn the Work That Begins After Installation

Installing SonarQube is not the end of the work.

It is the beginning of operations.

In Part 17, we built this architecture:

```text
Developer / CI
↓
DNS
↓
HTTPS / TLS
↓
Application Load Balancer
↓
SonarQube EC2
↓
Private PostgreSQL / RDS
```

Now imagine that architecture has been running for six months.

Developers depend on it.

CI/CD pipelines depend on it.

Pull requests depend on it.

Quality Gates depend on it.

Security teams depend on its findings.

Then one morning:

```text
GitHub Actions
↓
SonarQube Analysis
↓
Waiting for Quality Gate...
↓
Timeout
```

The SonarQube website still opens.

So what is wrong?

Maybe:

```text
Compute Engine queue is overloaded
```

or:

```text
Database latency increased
```

or:

```text
Disk is almost full
```

or:

```text
Search is unhealthy
```

or:

```text
A large analysis is blocking the queue
```

or:

```text
The server is running out of memory
```

This is why production engineering does not stop at:

```text
INSTALL
```

It continues through:

```text
OPERATE
↓
MONITOR
↓
DETECT
↓
INVESTIGATE
↓
FIX
↓
VERIFY
↓
BACK UP
↓
MAINTAIN
↓
UPGRADE SAFELY
```

That is the focus of Part 18.

# 2. What SonarQube Administration Means

Administration means managing the SonarQube platform itself.

This is different from simply using SonarQube to view code issues.

A developer might ask:

```text
Why did my Quality Gate fail?
```

A SonarQube administrator might ask:

```text
Is the Compute Engine healthy?

Is the database responding normally?

Are background tasks backing up?

Is Elasticsearch healthy?

Is disk space sufficient?

Are plugins compatible?

Are backups working?

Is an upgrade required?

Are users and permissions correct?
```

Administration operates the platform behind the developer experience.

# 5. Main Process

The main process coordinates SonarQube startup and shutdown.

Its main log is:

```text
sonar.log
```

If SonarQube refuses to start, this is one of the first places to inspect.

But it often provides the high-level failure rather than every detailed root cause.

# 12. Administration > System

The SonarQube administration interface provides system information.

Conceptually:

```text
Administration
↓
System
```

---

# 13. Service-Level Checks

If SonarQube runs under systemd, a Linux administrator may use:

```bash
systemctl status sonarqube
```

This asks:

```text
What does systemd think about the service?
```

It does not prove every SonarQube subsystem is healthy.

---

# 14. Process Checks

Useful commands may include:

```bash
ps aux | grep sonar
```

and:

```bash
ps aux | grep java
```

These help answer:

```text
Are relevant processes running?
```

Be careful not to interpret the `grep` process itself as SonarQube.

---

# 15. Port Check

SonarQube normally listens on port 9000 internally unless configured differently.

Check:

```bash
ss -lntp
```

You may filter:

```bash
ss -lntp | grep 9000
```

This answers:

```text
Is something listening on TCP port 9000?
```

It does not prove the application is completely healthy.

---

# 16. HTTP Check

From the SonarQube host:

```bash
curl -I http://localhost:9000
```

This tests the local HTTP path.

Then test through the production entry point:

```bash
curl -I https://sonarqube.example.com
```

These test different layers.

---

# 17. Local Works, External Fails

Suppose:

```text
curl localhost:9000
=
Works
```

but:

```text
https://sonarqube.example.com
=
Fails
```

This tells you SonarQube itself may be healthy.

Investigate:

```text
DNS

TLS

Load balancer

Reverse proxy

Security group

Firewall

Routing
```

instead of reinstalling SonarQube.

---

# 18. External Works, Analysis Fails

Suppose the dashboard loads.

But CI says:

```text
Quality Gate timeout
```

Now the problem may be:

```text
Compute Engine

Background task queue

Database performance

Analysis processing
```

The Web Server being healthy does not prove the Compute Engine is healthy.

# 29. Access Log vs Web Log

Do not confuse them.

Conceptually:

```text
access.log
=
Who requested what and what HTTP response occurred?
```

while:

```text
web.log
=
What happened inside the Web Server while handling activity?
```

Both can be useful during the same incident.

# 31. Reading Stack Traces

Java applications often produce stack traces.

A beginner may see:

```text
java.lang.IllegalStateException
    at ...
    at ...
    at ...
Caused by: ...
    at ...
```

and think:

```text
I need to understand every line.
```

You usually do not.

Start with:

```text
First exception message
```

and:

```text
Caused by:
```

especially the deepest relevant cause.

---

# 32. Example

Suppose:

```text
ERROR Unable to connect to database

Caused by:
java.net.ConnectException: Connection timed out
```

The important clue is:

```text
Connection timed out
```

That suggests investigating network/database reachability.

Not reinstalling Java.

---

# 33. Log Levels

Common SonarQube server log levels include:

```text
INFO

DEBUG

TRACE
```

`INFO` is the normal default.

---

# 34. DEBUG

DEBUG provides more detailed diagnostic information.

Use it when:

```text
Normal logs do not provide enough information
```

But additional logging may include more user-related information and produce much larger logs.

Do not leave increased logging enabled indefinitely without reason.

---

# 35. TRACE

TRACE is even more detailed.

It may include extensive database and search request information.

TRACE can negatively affect performance.

Therefore:

```text
TRACE
=
Temporary diagnostic tool
```

not:

```text
Permanent production setting
```

---

# 36. Temporary vs Persistent Log-Level Changes

An administrator may temporarily adjust log levels from the UI.

But temporary changes can reset after restart.

Persistent logging configuration belongs in the relevant SonarQube configuration.

Understand whether your change is:

```text
Temporary
```

or:

```text
Persistent
```

before depending on it.

---

# 37. Log Rotation

Logs grow.

Without rotation:

```text
Logs
↓
Grow
↓
Disk fills
↓
Application problems
```

SonarQube supports log rolling policies.

Operationally, you need a strategy for:

```text
Rotation

Retention

Central collection

Searchability

Disk protection
```

---

# 38. Why Log Retention Matters

Too little retention:

```text
Incident happened yesterday
↓
Logs already gone
```

Too much retention:

```text
Months of verbose logs
↓
Disk exhausted
```

Retention is a balance.

Problem:

```text

↓
```

---

# 44. Queue Length Alone Is Not Enough

Suppose:

```text
10 pending tasks
```

Is that bad?

Maybe.

Maybe not.

Ask:

```text
How long is the oldest task waiting?

How quickly does the queue drain?

What is normal at this time?

Are tasks failing?

Is one huge project blocking others?
```

Context matters.

---

# 45. Failed Background Task

A failed task should be inspected.

The failure message may point directly toward:

```text
Database problem

Search problem

Memory problem

Project problem

Plugin problem

Infrastructure problem
```

Do not only re-run it repeatedly.

Find why it failed.

---

# 46. Large Project Blocking Queue

Imagine:

```text
Project A
=
very large analysis

Projects B–Z
=
waiting
```

One expensive task may occupy Compute Engine capacity for a long time.

Investigate:

```text
Analysis scope

Generated files

Dependencies accidentally scanned

Test fixtures

Build artifacts

Project size
```

---

# 47. Compute Engine Capacity

Compute Engine workers consume memory.

More workers can increase parallel processing.

But:

```text
More workers
≠
Free performance
```

Each worker requires resources.

If you increase worker count without enough memory:

```text
More workers
↓
Memory pressure
↓
Garbage collection / OOM / instability
```

Capacity must be balanced.

---

# 48. CPU Monitoring

CPU tells you how much processing capacity is being used.

Useful questions:

```text
Is CPU constantly saturated?

Did CPU increase after a new project?

Does CPU spike during analysis periods?

Is Web responsive while CE is busy?

Did behavior change after upgrade?
```

---

# 49. High CPU Does Not Automatically Mean Problem

CPU at:

```text
90%
```

during a short analysis burst may be expected.

CPU at:

```text
95–100%
```

for hours while queue latency grows may indicate capacity or workload problems.

Monitor:

```text
Level

Duration

Context

Impact
```

---

# 50. Memory Monitoring

SonarQube is Java-based and contains multiple Java processes.

Memory is critical.

You must think about:

```text
Operating-system memory

Web JVM

Compute Engine JVM

Search JVM

Other processes
```

---

# 51. Linux Memory Commands

Examples:

```bash
free -h
```

This displays system memory.

You may also use:

```bash
top
```

or:

```bash
ps aux --sort=-%mem | head
```

depending on what you need to investigate.

---

# 52. Understanding free -h

Example conceptual output:

```text
              total    used    free   available
Mem:            16G      8G      2G        7G
```

Do not focus only on:

```text
free
```

Linux uses memory for caching.

`available` can be more useful when estimating how much memory is available for applications without heavy swapping.

---

# 53. Swap

Swap allows memory pages to be moved to disk.

Heavy swap activity can severely hurt performance.

If SonarQube is constantly swapping:

```text
Memory pressure
↓
Disk activity
↓
Slow JVM
↓
Slow SonarQube
```

Investigate the cause.

---

# 54. JVM

JVM means:

```text
Java Virtual Machine
```

SonarQube's Java processes run inside JVMs.

The JVM manages:

```text
Heap memory

Threads

Garbage collection

Class loading

Runtime execution
```

---

# 55. Heap

Heap is memory used by Java applications for runtime objects.

You may encounter settings involving:

```text
-Xms
```

and:

```text
-Xmx
```

Conceptually:

```text
-Xms
=
Initial heap size

-Xmx
=
Maximum heap size
```

Do not blindly copy JVM settings from a blog.

---

# 56. Bigger Heap Is Not Always Better

Suppose server has:

```text
8 GB RAM
```

and you allocate nearly all of it to Java processes.

Now the operating system and other SonarQube components have no headroom.

Result:

```text
Memory pressure

Swap

OOM

Instability
```

JVM tuning must consider the whole host.

---

# 57. Out of Memory

A JVM may report:

```text
OutOfMemoryError
```

Do not immediately conclude:

```text
Increase Xmx.
```

First investigate:

```text
Which process?

What workload?

Was configuration changed?

Did project size increase?

Did worker count increase?

Is host RAM sufficient?

Is there abnormal memory growth?
```

---

# 58. Garbage Collection

The JVM automatically reclaims memory through garbage collection.

If memory pressure is severe, the JVM may spend excessive time performing garbage collection.

Symptoms may include:

```text
Slow responses

High CPU

Long pauses

Reduced throughput
```

Memory problems can therefore appear as performance problems.

---

# 59. Disk Usage

Disk exhaustion is one of the most preventable production failures.

Check:

```bash
df -h
```

This shows filesystem usage.

Example:

```text
Filesystem      Size  Used Avail Use%
/dev/xvda1       80G   72G    8G  90%
```

90% usage deserves attention.

---

# 60. Why SonarQube Needs Disk

Disk may be consumed by:

```text
Logs

Search indexes

Temporary data

Installed files

Plugins

Operating system

Diagnostic files
```

Database storage is separate when using external PostgreSQL/RDS.

---

# 61. Find Large Directories

A careful investigation might use:

```bash
du -sh /opt/sonarqube/*
```

This shows approximate size per directory.

For logs:

```bash
du -sh /opt/sonarqube/logs
```

Do not delete directories merely because they are large.

First identify what they contain and whether deletion is supported.

---

# 62. Dangerous Disk Cleanup

Do not do:

```bash
rm -rf /opt/sonarqube/data/*
```

because:

```text
Disk is full
```

without understanding what you are deleting.

Production troubleshooting should not create a second incident.

---

# 63. Disk Alerting

Do not wait for:

```text
100%
```

Set thresholds that give operators time to respond.

Example conceptual levels:

```text
70%
↓
Observe trend

80%
↓
Warning

90%
↓
Critical
```

Exact thresholds depend on environment and growth rate.

---

# 64. Disk Trend Matters

Suppose disk grows:

```text
1 GB per month
```

versus:

```text
10 GB per hour
```

Both might currently show 70%.

They represent completely different risks.

Monitor rate of change.

# 66. Database Connection Pool

Applications generally maintain database connections.

If SonarQube cannot obtain usable database connections:

```text
Web requests may fail

Background tasks may fail

Startup may fail
```

Investigate both application and database sides.

---

# 67. Database Latency

Slow database writes can slow Compute Engine processing.

Architecture:

```text
Compute Engine
↓
Persist Results
↓
Slow Database
↓
Task takes longer
↓
Queue grows
↓
Quality Gate waits longer
```

This is a good example of an infrastructure problem becoming a developer pipeline problem.

---

# 68. Database Storage

Database storage must have headroom.

During some SonarQube upgrades, database migration may temporarily require substantially more disk space than normal.

Therefore:

```text
Database normally fits
```

does not automatically mean:

```text
Database has enough space for upgrade.
```

---

# 69. Database Maintenance

Large production databases may require routine database maintenance according to the database platform.

Examples for PostgreSQL concepts include:

```text
VACUUM

REINDEX

ANALYZE
```

These are database-administration operations.

Do not execute potentially locking maintenance commands casually in production.

Coordinate them with the DBA and maintenance window.

---

```text

Unhealthy search state
```

---

# 71. Search Storage

Search workloads benefit from:

```text
Low latency

Good IOPS

Reliable storage
```

Slow storage can affect SonarQube performance.

Storage architecture is therefore not just about capacity.

It is also about performance.

# 73. Reindexing


Search indexes can be reconstructed.

# 92. RPO

RPO means:

```text
Recovery Point Objective
```

It answers:

```text
How much data can we afford to lose?
```

Example:

```text
RPO = 15 minutes
```

means the business aims not to lose more than roughly 15 minutes of data.

---

# 93. RTO

RTO means:

```text
Recovery Time Objective
```

It answers:

```text
How long can the service remain unavailable?
```

Example:

```text
RTO = 2 hours
```

means the target is to restore service within approximately two hours.

---

# 94. Why RPO and RTO Matter

Without them, someone says:


But how often?

Daily?

Hourly?

Every 15 minutes?

And how quickly must it recover?

RPO and RTO turn vague requirements into operational targets.

