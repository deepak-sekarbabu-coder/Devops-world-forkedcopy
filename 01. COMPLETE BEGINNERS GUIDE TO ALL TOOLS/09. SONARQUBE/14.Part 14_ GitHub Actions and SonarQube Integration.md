# Part 14: GitHub Actions and SonarQube Integration

## Build a Modern Repository-Driven Quality Pipeline

In Part 13, you built this architecture with Jenkins:

```text
Developer
↓
Git
↓
Jenkins
↓
Build
↓
Test
↓
Coverage
↓
SonarQube
↓
Quality Gate
↓
Continue / Stop
```

Now we are going to build the same engineering control using GitHub Actions.

The architecture changes to:

```text
Developer
↓
GitHub Repository
↓
GitHub Actions
↓
GitHub Actions Runner
↓
Checkout
↓
Build
↓
Unit Tests
↓
Coverage
↓
SonarQube Analysis
↓
Quality Gate
↓
Merge Decision
```

The most important difference is architectural.

With Jenkins, you normally operate a separate automation server.

With GitHub Actions, the automation definition lives directly with the GitHub repository:

```text
Repository
│
├── src/
├── tests/
├── pom.xml
├── sonar-project.properties
└── .github/
    └── workflows/
        └── build.yml
```

Your repository contains not only your application code, but also instructions describing how GitHub should build, test and analyze that application.

That is what we will learn in Part 14.

---

# 1. What Problem Are We Solving?

Suppose a developer writes code and pushes it to GitHub.

Without CI:

```text
Developer
↓
Write Code
↓
Run Tests Maybe
↓
Run SonarQube Maybe
↓
Push
↓
Merge
```

Notice the word:

```text
Maybe
```

That is the problem.

Engineering controls should not depend entirely on someone remembering to run them manually.

We want:

```text
Developer
↓
Push Code
↓
Automation Starts
```

Then:

```text
Checkout
↓
Build
↓
Test
↓
Coverage
↓
SonarQube
↓
Quality Gate
↓
Merge Decision
```


For DevOps engineers, common uses include:

```text
Continuous Integration

```

# 4. Repository

The repository contains your project.

Example:

```text
payment-service/
├── src/
├── tests/
├── pom.xml
├── README.md
└── .github/
```

GitHub Actions automation belongs to this repository.

---

# 5. Event

An event is something that happens in GitHub.

Examples:

```text
Developer pushes code

Developer opens pull request

Developer updates pull request

Someone manually starts workflow

A scheduled time occurs
```

The event can trigger a workflow.

---

# 6. Workflow

A workflow is an automated process defined using YAML.

Example:

```text
.github/workflows/ci.yml
```

The workflow might say:

```text
When code is pushed
↓
Run build
↓
Run tests
↓
Run SonarQube
```

---

# 7. Job

A workflow contains one or more jobs.

Example:

```text
Workflow
│
├── Job: build
├── Job: test
└── Job: deploy
```

Jobs can sometimes run independently or depend on other jobs.

---

# 8. Runner

A runner is the machine that executes a GitHub Actions job.

Architecture:

```text
GitHub
↓
Assign Job
↓
Runner
↓
Execute Steps
```

The runner is where commands such as:

```bash
mvn verify
npm test
pytest
sonar-scanner
```

actually execute.

---

# 9. GitHub-Hosted Runners

GitHub can provide temporary runners.

Common operating-system labels include environments such as:

```text
ubuntu-latest

windows-latest

macos-latest
```

For example:

```yaml
runs-on: ubuntu-latest
```

means the job should execute on a GitHub-hosted Ubuntu runner matching that label.

# 10. Self-Hosted Runners

Organizations can also operate their own runners.

Architecture:

```text
GitHub
↓
Job
↓
Company-Managed Runner
```

Examples:

```text
AWS EC2

```

---

# 11. Why Self-Hosted Runners Matter for SonarQube

Suppose SonarQube is accessible only inside:

```text
10.20.0.0/16
```

and has no public route.

A GitHub-hosted runner may not be able to reach it.

A self-hosted runner inside the organization's network may have:

```text
Runner
↓
Private Network
↓
SonarQube
```

This is an architecture decision, not merely a YAML problem.

---

# 12. Step

A job contains steps.

Example:

```yaml
steps:
  - name: Checkout
    ...

  - name: Build
    ...

  - name: Test
    ...
```

Steps execute in sequence within a job unless workflow behavior changes through conditions or failures.

---

# 13. Action

An action is a reusable unit of automation.

For example:

```yaml
uses: actions/checkout@v6
```

uses GitHub's checkout action.

Another example:

```yaml
uses: SonarSource/sonarqube-scan-action@v7
```

uses SonarSource's SonarQube scanning action.

---

# 14. `uses` vs `run`

This distinction is important.

`uses`:

```yaml
uses: actions/checkout@v6
```

means:

```text
Run an existing reusable action.
```

`run`:

```yaml
run: mvn test
```

means:

```text
Execute this shell command.
```

# 23. Current SonarQube-Style PR Trigger

A common SonarQube workflow pattern is:

```yaml
pull_request:
  types: [opened, synchronize, reopened]
```

This covers important PR lifecycle events.

`opened`:

```text
PR created
```

`synchronize`:

```text
New commits pushed to PR branch
```

`reopened`:

```text
Closed PR reopened
```

---

# 24. Why `synchronize` Matters

Suppose:

```text
Developer opens PR
↓
SonarQube finds problem
↓
Developer fixes problem
↓
Pushes new commit
```

You need analysis to run again.

That is why changes pushed to the PR must retrigger analysis.

---

# 25. Combined Push and PR Workflow

Example:

```yaml
on:
  push:
    branches:
      - main

  pull_request:
    types: [opened, synchronize, reopened]
```

Now analysis can run:

```text
On PR changes
```

and:

```text
On pushes to main
```

---

# 26. Why Analyze Pull Requests?

Pull-request analysis moves quality feedback earlier.

Without PR analysis:

```text
Bad Change
↓
Merge to Main
↓
Analysis
↓
Discover Problem
```

With PR analysis:

```text
Bad Change
↓
Pull Request
↓
Analysis
↓
Discover Problem
↓
Fix
↓
Merge
```

That is much better.

---

# 27. Pull Request Quality Philosophy

The core idea is:

```text
Inspect the change before accepting it.
```

SonarQube PR analysis focuses on what the pull request introduces relative to its target.

Therefore:

```text
Existing Legacy Code
+
New PR Changes
```

does not mean the developer must necessarily repair the entire historical codebase before merging one small change.

The Quality Gate can focus on the new code introduced by the PR.

# 31. Checkout

A GitHub Actions runner does not automatically mean your repository files are ready for your commands.

Normally you use:

```yaml
- name: Checkout source
  uses: actions/checkout@v6
```

This places repository content into the runner workspace.

---

# 32. Why Checkout Matters

Before checkout:

```text
Runner
```

After checkout:

```text
Runner
└── Workspace
    ├── src/
    ├── pom.xml
    ├── tests/
    └── configuration
```

Now build tools can work with the source.

---

# 33. SonarQube Checkout Recommendation

For SonarQube analysis, use complete Git history where required for accurate analysis context.

Current SonarSource examples use:

```yaml
- uses: actions/checkout@v6
  with:
    fetch-depth: 0
```

---

# 34. What Is `fetch-depth`?

Git repositories contain history.

A shallow checkout retrieves limited history.

Example:

```text
Only Recent Commit
```

rather than:

```text
Commit 1
↓
Commit 2
↓
Commit 3
↓
...
↓
Current Commit
```

---

# 35. Why `fetch-depth: 0`?

For SonarQube, complete repository history improves the information available for analysis features that depend on SCM history and branch context.

Therefore:

```yaml
fetch-depth: 0
```

means:

```text
Do not intentionally limit checkout to shallow history.
```

Remember Part 10.


before analysis.

That destroys information SonarQube may need.

# 47. Repository Secrets

Now we reach security.

SonarQube analysis needs authentication.

You should not write:

```yaml
SONAR_TOKEN: abc123secret
```

inside the workflow.

Instead use GitHub secrets.

---

# 48. What Is a GitHub Actions Secret?

A secret is sensitive information stored separately from repository code and made available to authorized workflows.

Examples:

```text
API tokens

Passwords

Private credentials

Deployment credentials

SonarQube tokens
```

---

# 49. `SONAR_TOKEN`

For SonarQube analysis, create a secret commonly named:

```text
SONAR_TOKEN
```

Conceptually:

```text
GitHub Repository
↓
Settings
↓
Actions Secrets
↓
SONAR_TOKEN
↓
Actual SonarQube Token
```

The actual token does not belong in your YAML.

---

# 50. Referencing the Secret

Workflow syntax:

```yaml
env:
  SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
```

This means:

```text
Environment Variable
SONAR_TOKEN

gets value from

GitHub Secret
SONAR_TOKEN
```

---

# 51. Left Side vs Right Side

Understand this carefully.

```yaml
SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
```

Left:

```text
SONAR_TOKEN
```

is the environment variable exposed to the step.

Right:

```text
secrets.SONAR_TOKEN
```

is the GitHub Actions expression retrieving the stored secret.

---

# 52. `SONAR_HOST_URL`

The scanner also needs to know where SonarQube Server lives.

Example conceptual value:

```text
https://sonarqube.company.internal
```

Current SonarSource examples can provide this through a GitHub variable:

```yaml
SONAR_HOST_URL: ${{ vars.SONAR_HOST_URL }}
```

---

# 53. Secret vs Variable

A SonarQube token is sensitive.

Therefore:

```text
SONAR_TOKEN
→ Secret
```

A SonarQube server URL is often configuration rather than a secret.

Therefore it may be:

```text
SONAR_HOST_URL
→ Variable
```

depending on your organization's requirements.

Do not treat a value as non-sensitive merely because an example does.

Your security model may classify internal infrastructure information differently.

---

# 54. Environment Variable Architecture

```text
GitHub Secret
SONAR_TOKEN
↓
Workflow
↓
Environment Variable
SONAR_TOKEN
↓
SonarScanner
```

And:

```text
GitHub Variable
SONAR_HOST_URL
↓
Workflow
↓
Environment Variable
SONAR_HOST_URL
↓
SonarScanner
```

---

# 55. Why Environment Variables?

They let runtime processes receive configuration without hard-coding sensitive values into repository files.

But environment variables are not magically secure.

A malicious command can still attempt to print or exfiltrate them.

Therefore workflow security still matters.

---

# 56. Never Echo Secrets

Bad:

```yaml
- name: Debug
  run: echo "$SONAR_TOKEN"
```

Do not intentionally print credentials.

GitHub masks recognized secrets in many log situations, but masking should not be your security strategy.

---

# 57. Secret Security Principle

Treat:

```text
Repository Workflow Code
```

as code capable of accessing whatever credentials you expose to it.

Therefore changes to workflow files deserve careful review.

---

# 58. Dangerous Workflow Change

Imagine someone changes:

```yaml
run: mvn verify
```

to a malicious command designed to send secrets elsewhere.

If that workflow receives powerful secrets, the attacker may attempt credential theft.

This is why CI/CD configuration is security-sensitive code.

---

# 59. Least Privilege

Your SonarQube analysis token should have only the permissions required for its intended analysis function.

Do not automatically use:

```text
Global Administrator Token
```

for CI.

---

# 60. Separate Credentials

Do not use one giant credential for:

```text
SonarQube

AWS Production

Container Registry

Database

Terraform

GitHub Administration
```

Separate identities reduce blast radius.

# 74. Example Maven Workflow

```yaml
name: Build and SonarQube Analysis

on:
  push:
    branches:
      - main

  pull_request:
    types: [opened, synchronize, reopened]

jobs:
  build:
    name: Build and Analyze
    runs-on: ubuntu-latest

    steps:
      - name: Checkout source
        uses: actions/checkout@v6
        with:
          fetch-depth: 0

      - name: Set up Java
        uses: actions/setup-java@v5
        with:
          distribution: temurin
          java-version: '21'
          cache: maven

      - name: Build, test and analyze
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
          SONAR_HOST_URL: ${{ vars.SONAR_HOST_URL }}
        run: >
          mvn -B clean verify
          org.sonarsource.scanner.maven:sonar-maven-plugin:sonar
```

This is a teaching example. Match Java and Maven configuration to the actual project.

# Part 14 Summary

You began with:

```text
Developer
↓
GitHub
```

Then GitHub Actions turned repository events into automated execution:

```text
GitHub Event
↓
Workflow
↓
Job
↓
Runner
↓
Steps
```

The runner checked out the repository:

```text
GitHub
↓
actions/checkout
↓
Runner Workspace
```

Then prepared the application:

```text
Build
↓
Tests
↓
Coverage
```

SonarQube credentials were kept outside the repository:

```text
GitHub Secret
↓
SONAR_TOKEN
↓
Scanner
```

and the server location was provided through configuration:

```text
SONAR_HOST_URL
↓
Scanner
↓
SonarQube Server
```

The scanner submitted analysis:

```text
Runner
↓
SonarScanner
↓
SonarQube
```

SonarQube processed the code:

```text
Analysis
↓
Issues
↓
Metrics
↓
New Code
↓
Quality Gate
```

For pull requests, GitHub integration brought the decision back to the developer workflow:

```text
SonarQube
↓
GitHub
↓
SonarQube Code Analysis
```

But reporting alone was not enough.

You then added enforcement:

```text
GitHub Ruleset
↓
Require SonarQube Code Analysis
```

which produced:

```text
Quality Gate PASS
↓
Required Check PASS
↓
Merge Eligible
```

or:

```text
Quality Gate FAIL
↓
Required Check FAIL
↓
Merge Blocked
```

The final architecture is:

```text
Developer
↓
Feature Branch
↓
GitHub
↓
Pull Request
↓
GitHub Actions
↓
Runner
↓
Checkout
↓
Build
↓
Unit Tests
↓
Coverage
↓
SonarQube Analysis
↓
Quality Gate
↓
GitHub Check
↓
Repository Rules
↓
PASS?
↙                    ↘
YES                   NO
↓                      ↓
MERGE                  FIX CODE
↓                      ↓
MAIN                  PUSH AGAIN
                       ↓
                    REANALYZE
```

The central lesson is:

```text
SONARQUBE FINDS AND EVALUATES QUALITY.
```

```text
GITHUB ACTIONS AUTOMATES THE PROCESS.
```

```text
GITHUB REPOSITORY RULES ENFORCE THE MERGE DECISION.
```

A mature integration therefore does not stop at:

```text
We run SonarQube.
```

It answers four questions:

```text
1. Does analysis run automatically?

2. Does it run on the correct code?

3. Does the developer receive the Quality Gate result?

4. Can unacceptable code actually be prevented from merging?
```

When all four are true, SonarQube has moved from being a dashboard developers may occasionally inspect to an enforceable part of the repository's engineering workflow.
