# Part 19: SonarQube Troubleshooting and Production Failure Scenarios

## Learn to Diagnose SonarQube Instead of Reinstalling It Whenever Something Breaks

By this point, you know how to:

* understand SonarQube architecture
* install SonarQube
* run it with Docker
* analyze source code
* interpret results
* configure rules and Quality Profiles
* enforce Quality Gates
* import coverage
* integrate Git and GitHub
* use Maven and Gradle
* build CI/CD pipelines
* integrate Jenkins
* integrate GitHub Actions
* secure users, permissions and tokens
* automate SonarQube through APIs and webhooks
* deploy SonarQube on AWS
* monitor, back up and upgrade SonarQube

Now comes one of the most important engineering skills:

```text
TROUBLESHOOTING
```

A beginner often responds to failure like this:

```text
Something broke
↓
Restart
↓
Still broken
↓
Reinstall
↓
Still broken
↓
Search random commands online
↓
Change five configurations
↓
Problem becomes worse
```

A production engineer works differently:

```text
Observe Symptom
↓
Check Scope
↓
Check Logs
↓
Check Resources
↓
Check Network
↓
Check Configuration
↓
Form Hypothesis
↓
Test
↓
Fix Root Cause
↓
Verify
```

That is the central lesson of Part 19.

---

# 1. Troubleshooting Is a Method, Not a Collection of Commands

Troubleshooting does not mean:

```text
Know 500 Linux commands
```

It means being able to answer:

```text
What exactly is failing?

Where is it failing?

When did it begin?

What changed?

Which component owns that part of the workflow?

What evidence supports my theory?

How can I test the theory safely?

Did my fix actually solve the original problem?
```

Commands are tools for answering those questions.

---

---

# 3. Step 1: Observe the Symptom

Do not begin with:

```text
SonarQube is broken.
```

That statement is too broad.

Ask what actually happened.

Examples:

```text
Browser returns 502.

SonarQube service will not start.

Scanner returns authentication failed.

Quality Gate waits for 10 minutes.

Dashboard still shows old analysis.

Coverage suddenly shows 0%.

Jenkins waits forever.

GitHub PR has no SonarQube check.

Port 9000 refuses connections.

Search process crashes.

Background task failed.
```

Those are useful symptoms.

---

# 4. Describe the Symptom Precisely

Bad:

```text
SonarQube doesn't work.
```

Better:

```text
The SonarQube web interface works,
but GitHub Actions cannot connect to
https://sonarqube.example.com.
```

Much better:

```text
The SonarQube web interface is reachable
from my laptop.

GitHub Actions started failing at 10:12 UTC.

curl from the self-hosted runner to
https://sonarqube.example.com returns
"Could not resolve host."

The last successful pipeline was at 09:58 UTC.
```

Now you have evidence.

---

# 5. Step 2: Check Scope

Scope means:

```text
How much of the system is affected?
```

Ask:

```text
One user?

One project?

One branch?

One scanner?

One CI runner?

All CI pipelines?

Only Jenkins?

Only GitHub Actions?

Only the Web UI?

All SonarQube users?

The entire SonarQube server?
```

Scope dramatically reduces the search space.

---

# 6. Scope Example

Suppose:

```text
Project A fails analysis.

Projects B, C and D succeed.
```

This suggests:

```text
SonarQube server-wide outage
```

is less likely.

Investigate project-specific things:

```text
Project key

Token permissions

Source paths

Build configuration

Coverage path

Project-specific Quality Gate

Project-specific webhook
```

---

# 7. Another Scope Example

Suppose:

```text
Every project fails to connect.
```

Now investigate shared dependencies:

```text
SonarQube availability

DNS

TLS certificate

Load balancer

Firewall

Security group

Server outage

Database failure
```

Scope prevents wasted work.

# 11. Step 6: Check Configuration

Examples:

```text

sonar.projectKey

sonar.sources

coverage report path

database JDBC URL

tokens

```

---

# 12. Step 7: Form a Hypothesis

A hypothesis is a testable explanation.

Example:

```text
Symptom:
Scanner cannot connect.

Evidence:
DNS resolves.
Port 443 responds.
Browser works.
Scanner reports certificate error.

Hypothesis:
CI runner does not trust the certificate chain.
```

That is much better than:

```text
Maybe SonarQube is broken.
```

---

# 13. Step 8: Test the Hypothesis

Test one theory.

For example:

```bash
curl -v https://sonarqube.example.com
```

from the affected runner.

If certificate validation fails there too, your hypothesis becomes stronger.

---

# 14. Change One Important Variable at a Time

Avoid:

```text
Change DNS
+
Change security group
+
Replace certificate
+
Restart SonarQube
+
Upgrade Java
+
Regenerate token
```

all at once.

If the problem disappears, you will not know what fixed it.

---

# 15. Step 9: Fix the Root Cause

Suppose:

```text
Disk filled because TRACE logging
was accidentally left enabled.
```

Deleting old logs temporarily fixes the symptom.

The root fix also includes:

```text
Return logging to INFO

Configure rotation

Configure retention

Add disk alerts

Document incident
```

---

# 16. Step 10: Verify

Verification asks:

```text
Does the original workflow now succeed?
```

If the original problem was:

```text
Jenkins Quality Gate timeout
```

verification should include:

```text
New commit
↓
Jenkins
↓
Build
↓
Test
↓
SonarQube analysis
↓
CE processing
↓
Webhook
↓
waitForQualityGate
↓
Correct gate result
```

Not merely:

```text
SonarQube page opens.
```

---

# 17. Troubleshooting by Architecture

Keep the architecture in your head:

```text
Developer / CI
        │
        ↓
       DNS
        │
        ↓
    HTTPS/TLS
        │
        ↓
Load Balancer / Proxy
        │
        ↓
   SonarQube Web
        │
   ┌────┴─────┐
   ↓          ↓
Compute      Search
Engine
   │
   └────┬─────┘
        ↓
     Database
```

A failure belongs somewhere in this chain.

# 18. Failure Scenario 1: SonarQube Will Not Start

## What the Beginner Sees

```text
SonarQube is down.
```

or:

```text
systemctl start sonarqube
```

returns failure.

---

# 19. Do Not Reinstall

Start with:

```text
What component failed during startup?
```

Inspect:

```text
sonar.log
↓
web.log
↓
es.log
↓
ce.log
```

depending on the evidence.

---

# 20. Common Startup Causes

Possible causes include:

```text
Unsupported Java

Wrong Java path

Insufficient memory

Elasticsearch failure

Database unavailable

Database credentials wrong

Port conflict

File permissions

Running as root

Disk full

Linux host limits

Broken plugin

Failed upgrade

Configuration syntax/error
```

---

# 21. Check Service State

```bash
systemctl status sonarqube
```

If systemd is used.

Then inspect system logs:

```bash
journalctl -u sonarqube
```

Recent entries:

```bash
journalctl -u sonarqube -n 100
```

---

# 22. Check SonarQube Logs

```bash
tail -n 100 /opt/sonarqube/logs/sonar.log
```

Then:

```bash
tail -n 100 /opt/sonarqube/logs/web.log
```

```bash
tail -n 100 /opt/sonarqube/logs/es.log
```

```bash
tail -n 100 /opt/sonarqube/logs/ce.log
```

Follow the component that failed.

---

# 23. Look for Root-Cause Language

Search:

```bash
grep -i "error" /opt/sonarqube/logs/sonar.log
```

Also inspect:

```text
Exception

Caused by

OutOfMemory

Connection refused

Permission denied

Address already in use

No space left

Unsupported
```

Do not depend only on `grep ERROR`.

Sometimes the most useful cause is several lines below the first error.

---

# 24. Failure Scenario 2: Port 9000 Unavailable

Symptoms:

```text
Connection refused

Address already in use

Browser cannot connect to localhost:9000
```

Two very different problems can exist:

```text
Nothing listening on 9000
```

or:

```text
Something else already owns 9000
```

---

# 25. Check Port 9000

```bash
ss -lntp | grep 9000
```

Possible result:

```text
LISTEN ... :9000 ...
```

means a process is listening.

No output may mean:

```text
SonarQube never started

SonarQube uses another port

Binding failed
```

---

# 26. Find Port Owner

Depending on permissions:

```bash
sudo lsof -i :9000
```

or:

```bash
sudo ss -lntp | grep :9000
```

Identify the process before killing anything.

---

# 27. Beginner Mistake

Do not immediately:

```bash
kill -9 <PID>
```

just because a process owns port 9000.

Determine:

```text
What process?

Should it be running?

Is SonarQube already running?

Is another application intentionally using that port?
```

---

# 28. Port Binding vs Network Reachability

Suppose:

```text
SonarQube listens on 9000 locally.
```

But external users cannot connect.

Now the problem is probably not port binding.

Investigate:

```text
Firewall

Security group

Load balancer

Reverse proxy

Network ACL

Routing

Bind address
```

---

# 29. Failure Scenario 3: Java/JVM Failure

Symptoms may include:

```text
Unsupported Java version

Java command not found

Wrong Java executable

JVM cannot allocate memory

OutOfMemoryError

Process exits immediately
```

---

# 30. Verify Java

```bash
java -version
```

Then:

```bash
which java
```

or:

```bash
command -v java
```

Check the runtime actually used by SonarQube.

---

# 31. Do Not Confuse Shell Java With Service Java

Your shell may use:

```text
Java A
```

while systemd uses:

```text
Java B
```

because of:

```text
Environment variables

Service configuration

SONAR_JAVA_PATH

PATH differences
```

Always inspect the environment used by the service.

---

# 32. JVM Memory Failure

Symptom:

```text
java.lang.OutOfMemoryError
```

Ask:

```text
Which JVM?

Web?

Compute Engine?

Search?

Scanner?
```

Different processes require different fixes.

---

# 33. Check Memory

```bash
free -h
```

Then:

```bash
ps aux --sort=-%mem | head
```

Check:

```text
Available RAM

Swap

Largest processes

Recent worker changes

Recent workload changes
```

---

# 34. Do Not Blindly Increase Xmx

Bad:

```text
OutOfMemory
↓
Set every Xmx to 8 GB
```

Better:

```text
Identify process
↓
Identify workload
↓
Check current heap
↓
Check host RAM
↓
Check other processes
↓
Size deliberately
```

---

# 35. Compute Engine Memory Example

Suppose:

```text
sonar.ce.workerCount = 8
```

but the CE heap allocation is too small.

You may create:

```text
Parallel workers
↓
Memory pressure
↓
Slow processing
↓
Failures
```

More workers require more memory.

# 38. Test DNS

For:

```text
sonarqube-db.internal
```

use:

```bash
getent hosts sonarqube-db.internal
```

or:

```bash
nslookup sonarqube-db.internal
```

If DNS does not resolve, do not troubleshoot the database password yet.

---

# 39. Test TCP Connectivity

For PostgreSQL:

```bash
nc -vz sonarqube-db.internal 5432
```

This tests basic TCP reachability.

It does not prove authentication works.

---

# 40. PostgreSQL Client Test

If the client is installed:

```bash
psql -h sonarqube-db.internal -p 5432 -U sonarqube -d sonarqube
```

Do not expose passwords in command history.

Use secure authentication mechanisms.

# 41. Database Error Categories

Distinguish:

```text
Connection refused
```

from:

```text
Connection timed out
```

from:

```text
Password authentication failed
```

from:

```text
Permission denied
```

from:

```text
Too many connections
```

Each suggests a different layer.

# 42. Connection Refused

Usually suggests:


```text

```

# 43. Connection Timeout

# 44. Authentication Failure

Suggests:

```text

```

```text

```

---

# 45. Database Pool Exhaustion

SonarQube uses a connection pool.

Symptoms may include messages similar to:

```text
Connection is not available
```

or:

```text
Cannot acquire connection
```

Investigate:

```text
Database health

Connection limits

Long transactions

Database latency

Pool sizing

Firewall idle-connection behavior
```

Do not simply increase connection counts indefinitely.

---

# 46. AWS RDS Failure Scenario

Architecture:

```text
SonarQube EC2
↓
Security Group
↓
RDS PostgreSQL
```

Correct security model commonly resembles:

```text
RDS inbound TCP 5432
Source:
SonarQube EC2 Security Group
```

not:

```text
0.0.0.0/0
```

A database connectivity problem should not be solved by exposing PostgreSQL to the internet.

```text

Index errors

Read-only indices

```

```text

```

---

# 48. Search Failure Causes

Possible causes include:

```text
Disk exhaustion

Insufficient memory

Running SonarQube as root

Linux host requirements

Bad filesystem permissions

Slow storage

Temporary-directory restrictions

Upgrade problems

Index corruption/inconsistency
```

---

# 49. SonarQube Must Not Run as Root

Elasticsearch cannot run as root.

Therefore SonarQube Server should run under a dedicated non-root account.

Bad:

```text
root → SonarQube
```

Better:

```text
dedicated sonar user → SonarQube
```

---

# 50. Search and Disk

Elasticsearch protects itself when disk usage becomes dangerously high.

A production pattern can become:

```text
Disk fills
↓
Search indices protected/read-only
↓
Web/CE operations fail
↓
Developers see SonarQube errors
```

Freeing disk is necessary, but depending on the condition, additional recovery action may be required.

Never delete search data casually.

# 57. Never Solve Disk Problems Blindly

Do not:

```text

```


# 58. Failure Scenario 8: Slow Analysis


# 62. Failure Scenario 9: Scanner Cannot Reach Server

If Jenkins runs the scanner:

```text

```

```text

```


# 67. Failure Scenario 10: Authentication Failure

Symptoms:

```text
Not authorized

Unauthorized

Insufficient privileges

Authentication failed
```

Separate:

```text
Who are you?
```

from:

```text
What are you allowed to do?
```

Authentication answers the first.

Authorization answers the second.

# 68. Scanner Authentication

Modern scanner authentication uses:

```text
sonar.token
```

and many scanners support:

```text
SONAR_TOKEN
```

The associated identity also requires appropriate Execute Analysis permission.

---

# 69. Authentication Troubleshooting

Check:

```text
Token exists?

Token expired?

Token revoked?

Correct secret loaded?

Wrong environment?

Whitespace/newline accidentally included?

Correct user?

Correct project?

Correct permissions?
```

---

# 70. Never Print Tokens

Do not troubleshoot with:

```bash
echo "$SONAR_TOKEN"
```

in shared CI logs.

Instead check presence safely:

```bash
if [ -n "$SONAR_TOKEN" ]; then
  echo "SONAR_TOKEN is set"
else
  echo "SONAR_TOKEN is missing"
fi
```

This proves presence without revealing the value.

---

# 71. Failure Scenario 11: Invalid Token

Suppose yesterday analysis worked.

Today:

```text
Authentication failed.
```

Ask:

```text
Was token rotated?

Was it revoked?

Did it expire?

Was the CI secret updated?

Is pipeline using another environment?

Was token copied incorrectly?

Did permission change?
```

---

# 72. Secret Rotation Failure Pattern

```text
Old token revoked
↓
New token created
↓
Jenkins secret not updated
↓
Every analysis fails
```

The SonarQube server is healthy.

The problem is credential lifecycle.

---

# 73. Failure Scenario 12: Project Key Error

The project key identifies the SonarQube project.

Typical property:

```text
sonar.projectKey
```

Potential problems:

```text
Missing key

Wrong key

Typo

Wrong project

Different environment uses different key

Unauthorized project

Duplicate/incorrect configuration
```

---

# 74. Project Key vs Project Name

Do not confuse:

```text
sonar.projectKey
```

with:

```text
sonar.projectName
```

The key is the unique project identifier used by analysis.

The displayed name is not a substitute.

---

# 75. Troubleshoot Project Key

Find where it comes from:

```text

Maven build?

Gradle build?

Command line?

Environment?

CI template?
```

Then compare it with the intended SonarQube project.

# 78. Wrong Working Directory Example

Repository:

```text
repo/
├── backend/
│   └── src/
└── frontend/
    └── src/
```

Pipeline changes into:

```text
repo/frontend
```

but scanner expects:

```text
backend/src
```

The path may now be wrong relative to the analysis base directory.

# 79. Check Analysis Scope

If configured:

```text

```

confirm:

```bash
ls -la src
```

from the analysis base directory.

Do not assume the CI workspace matches your laptop.



# 81. Coverage Pipeline

```text
Application
↓
Tests
↓
Coverage Tool
↓
Coverage Report File
↓
Scanner
↓
SonarQube
```

Break any arrow and SonarQube may show missing coverage.

---

# 82. Coverage Troubleshooting

Ask:

```text
Did tests run?

Did coverage tool run?
```

# 159. The Restart Trap

Restarting can be appropriate.

But restart is not RCA.

If:

```text
Memory leak/resource pressure
↓
Restart
↓
Problem disappears
```

you still need to know:

```text
Why did memory grow?
```

Otherwise:

```text
Restart
↓
Temporary recovery
↓
Same incident tomorrow
```

---

# 160. The Reinstall Trap

Reinstalling is even more dangerous as a default response.

It can:

```text
Destroy evidence

Introduce configuration differences

Break plugins

Lose local configuration

Create downtime

Hide the root cause
```

Reinstallation belongs to specific recovery procedures, not ordinary troubleshooting.

---

# 161. The "Change Permissions to 777" Trap

Do not solve permission problems with:

```bash
chmod -R 777 ...
```

This grants excessive permissions.

Instead determine:

```text
Which user runs SonarQube?

Which directory?

What exact read/write/execute access is needed?

Who should own the files?
```

Then apply least privilege.

---

# 162. The "Disable Firewall" Trap

Do not solve connectivity by permanently disabling the firewall.

Instead:

```text
Identify source
↓
Identify destination
↓
Identify protocol
↓
Identify port
↓
Allow only required path
```

---

# 163. The "Disable TLS Verification" Trap

Do not solve certificate errors by disabling validation permanently.

Fix trust correctly.

---

# 164. The "Create Admin Token" Trap

Do not solve CI authorization by giving every pipeline an administrator token.

CI needs:

```text
Only the permissions necessary for its job.
```

Least privilege reduces blast radius.
