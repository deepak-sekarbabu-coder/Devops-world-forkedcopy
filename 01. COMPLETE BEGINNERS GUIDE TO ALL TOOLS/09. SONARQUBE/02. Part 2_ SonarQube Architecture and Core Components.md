# Part 2: SonarQube Architecture and Core Components

Before installing SonarQube, you should understand what is actually running behind the web interface.

When a beginner opens SonarQube in a browser, it can look like a normal dashboard:

```text
Projects
Issues
Security
Measures
Quality Gates
Administration
```

But SonarQube Server is not simply a website.

Behind that interface are several cooperating components responsible for:

* receiving analysis information
* processing reports
* storing project data
* indexing searchable information
* presenting results
* managing configuration
* evaluating quality information
* serving users and CI/CD systems

A useful starting architecture is:

```text
Developer / CI Pipeline
        ↓
   SonarScanner
        ↓
   SonarQube Server
┌───────────────────────┐
│ Web Server            │
│ Compute Engine        │
│ Search Engine         │
└───────────────────────┘
        ↓
     Database
```

This chapter will unpack every layer.

---

# 1. What We Are Trying to Understand

By the end of this part, you should understand the complete journey from:

```text
Developer changes code
        ↓
Scanner starts
        ↓
Code is analyzed
        ↓
Analysis report is generated
        ↓
Report reaches SonarQube
        ↓
Compute Engine processes it
        ↓
Results are stored
        ↓
Search indexes are updated
        ↓
Dashboard displays results
```

This matters because later, when something goes wrong, you need to know which part of the system failed.

For example:

```text
Scanner says success
but
dashboard does not update
```

A beginner might conclude:

```text
SonarQube is broken.
```

A more experienced engineer thinks:

```text
Did the scanner successfully create the report?

Was the report uploaded?

Is it waiting in the Compute Engine queue?

Did background processing fail?

Is the database available?

Is Elasticsearch healthy?

Is the web interface reading updated data?
```

Architecture gives you a troubleshooting map.

---

# 2. The Main SonarQube Components

A standard SonarQube Server instance contains three important server-side Java processes:

```text
Web
Compute Engine
Elasticsearch
```

Sonar's documentation describes these as the principal SonarQube Server processes. The Web process serves the user interface, the Compute Engine processes analysis reports, and Elasticsearch manages an indexed copy of database information for search and retrieval.

A separate database stores persistent SonarQube information.

Outside the server, one or more SonarScanners run against projects.

The architecture therefore looks more accurately like:

```text
                  CLIENT SIDE

Developer / CI Server
        ↓
    Source Code
        ↓
    SonarScanner
        │
        │ HTTP/HTTPS
        ▼

                  SERVER SIDE

┌──────────────────────────────────────┐
│          SonarQube Server            │
│                                      │
│   ┌──────────────┐                   │
│   │ Web Process  │                   │
│   └──────┬───────┘                   │
│          │                           │
│   ┌──────▼────────┐                  │
│   │ Compute Engine│                  │
│   └──────┬────────┘                  │
│          │                           │
│   ┌──────▼────────┐                  │
│   │ Elasticsearch │                  │
│   └───────────────┘                  │
└──────────────┬───────────────────────┘
               │
               ▼
          SQL Database
```

The components have different responsibilities.

That separation is extremely important.

---

# 3. SonarQube Server

The SonarQube Server is the central platform.

Think of it as the control center.

It provides services for:

```text
Projects
Users
Rules
Issues
Metrics
Quality profiles
Quality gates
Security findings
Administration
Analysis processing
APIs
Dashboards
```

The server does not normally sit inside the developer's application.

You do not install SonarQube inside your Python project or Java application.

Instead:

```text
Application
     ↓
Analyzed externally
     ↓
SonarQube
```

One SonarQube Server can manage many projects.

For example:

```text
SonarQube Server
     │
     ├── payment-service
     ├── user-service
     ├── inventory-api
     ├── web-frontend
     └── reporting-service
```

Each project has its own analysis results and configuration while sharing the same central platform.

---

# 4. SonarQube Is Not the Scanner

This distinction is fundamental.

Many beginners use the words SonarQube and SonarScanner as if they mean the same thing.

They do not.

## SonarQube Server

Runs centrally.

It:

```text
receives reports
processes reports
stores results
serves dashboards
manages configuration
evaluates project information
```

## SonarScanner

Runs where the source code is available.

Typically:

```text
Developer laptop
CI runner
Jenkins agent
GitHub Actions runner
Build server
```

It performs the project analysis and creates an analysis report.

Think:

```text
Scanner = worker near the code

SonarQube Server = central platform
```

---

# 5. The Web Server

The first important SonarQube Server process is the **Web process**.

It serves the SonarQube web interface and handles HTTP requests.

When you open:

```text
http://sonarqube.example.com
```

your browser communicates with the web layer.

Conceptually:

```text
Browser
   ↓
HTTP/HTTPS
   ↓
SonarQube Web Server
   ↓
SonarQube Interface
```

The web process is responsible for much more than drawing HTML pages.

It also handles requests involving:

```text
authentication
project browsing
administration
settings
Web API requests
project information
quality information
issue viewing
```

SonarQube currently runs the web component as one of its main Java processes.

---

# 6. Example: What Happens When You Open a Project

Suppose you visit:

```text
https://sonarqube.example.com/dashboard?id=payment-service
```

A simplified path is:

```text
Browser
   ↓
HTTPS Request
   ↓
Reverse Proxy / Load Balancer
   ↓
SonarQube Web Process
   ↓
Retrieve required information
   ↓
Database / Search Index
   ↓
Web Process
   ↓
HTTP Response
   ↓
Browser
```

The browser itself does not directly query the SonarQube database.

The web application handles that communication.

This is a common architecture pattern.

---

# 7. Why the Web Process Matters Operationally

If the web process fails, you may see symptoms such as:

```text
SonarQube page unavailable

HTTP connection refused

502 Bad Gateway

503 Service Unavailable

API requests failing
```

But notice something important.

A broken web interface does not automatically mean:

```text
Database destroyed
```

or:

```text
All analysis information lost
```

Different components can fail independently.

That is one reason architecture knowledge matters.

---

# 8. The Compute Engine

The Compute Engine, usually abbreviated **CE**, is one of the most important SonarQube components.

Its job is to process analysis reports.

This is easy to misunderstand.

The scanner performs project analysis and generates information.

But the scanner does not directly perform every final server-side update.

Instead:

```text
SonarScanner
     ↓
Analysis Report
     ↓
SonarQube Server
     ↓
Queue
     ↓
Compute Engine
     ↓
Process Results
     ↓
Store Results
```

Sonar documentation specifically describes the Compute Engine as the process responsible for processing code-analysis reports and saving resulting information to the SonarQube database.

---

# 9. Why SonarQube Uses a Compute Engine

Imagine 50 developers push changes at approximately the same time.

That could result in many analysis reports arriving at the server.

```text
Project A report ──┐
Project B report ──┤
Project C report ──┤
Project D report ──┤
Project E report ──┘
                   ↓
                Queue
                   ↓
            Compute Engine
```

The web interface should not have to perform every heavy report-processing task synchronously while users wait.

Instead, SonarQube can process analysis results as background work.

This creates an asynchronous model.

---

# 10. What Does Asynchronous Mean?

Suppose the scanner says:

```text
EXECUTION SUCCESS
```

A beginner may think:

```text
Everything is fully processed.
```

Not necessarily.

The scanner may have successfully completed its side of the work and submitted the report.

The server may still be processing it.

Conceptually:

```text
Scanner
   ↓
Analysis completed locally
   ↓
Report uploaded
   ↓
Scanner finishes
   ↓
Compute Engine still processing
   ↓
Dashboard updated later
```

Sonar's documentation explicitly notes that analysis is not considered fully complete until the corresponding background processing finishes. Scanner success can therefore occur before updated project values become visible.

This is one of the most important SonarQube architecture concepts to remember.

---

# 11. Background Tasks

The processing performed after an analysis report reaches SonarQube is handled as a **background task**.

Think of a background task as:

> Work SonarQube performs asynchronously after receiving information.

A common example is:

```text
Import analysis report
```

Other server operations can also use background tasks.

A simplified process:

```text
Scanner sends report
       ↓
Report enters queue
       ↓
Background task created
       ↓
Compute Engine selects task
       ↓
Task processed
       ↓
Database updated
       ↓
Indexes updated
       ↓
Results visible
```

---

# 12. Background Task States

Conceptually, tasks can be thought of as:

```text
PENDING
   ↓
IN PROGRESS
   ↓
SUCCESS
```

or:

```text
PENDING
   ↓
IN PROGRESS
   ↓
FAILED
```

If many analyses arrive faster than SonarQube can process them:

```text
Analysis 1 → waiting
Analysis 2 → waiting
Analysis 3 → waiting
Analysis 4 → waiting
Analysis 5 → waiting
```

the queue grows.

Operationally, engineers monitor values such as pending task count and pending time because a growing queue can indicate that Compute Engine processing is falling behind.

---

# 13. The Search Engine

SonarQube uses Elasticsearch as its search engine.

This is not an optional random component.

Sonar uses Elasticsearch internally to maintain indexed information that allows data to be searched and retrieved efficiently. Sonar describes Elasticsearch as managing an indexed copy of database information.

Think:

```text
Database
    ↓
Persistent authoritative data
    ↓
Elasticsearch indexes
    ↓
Fast searching and retrieval
```

---

# 14. What Is an Index?

An index helps a system locate information efficiently.

Think about the index at the back of a textbook.

Without an index, if you want information about:

```text
Kubernetes
```

you might have to read every page.

With an index:

```text
Kubernetes → pages 152, 173, 241
```

you reach the relevant information quickly.

Search indexes work on a much larger automated scale.

---

# 15. Why Elasticsearch Is Involved

SonarQube may contain information for:

```text
thousands of projects
millions of issues
millions of lines of code
many users
many rules
historical measures
```

Users expect searches and dashboards to respond quickly.

For example:

```text
Show all critical security issues.

Show unresolved maintainability problems.

Find this project.

Filter issues by rule.

Filter issues by severity.

Search projects.
```

Performing every search directly against large relational tables would not necessarily provide the desired search behavior or performance.

Elasticsearch creates indexes optimized for search.

---

# 16. Database vs Elasticsearch

Do not confuse them.

The relational database is the persistent system of record for SonarQube information.

Elasticsearch provides searchable indexes.

Conceptually:

```text
          SonarQube
             │
       ┌─────┴─────┐
       ↓           ↓
   Database    Elasticsearch
       ↓           ↓
Persistent      Searchable
information      indexes
```

Sonar documents that the Web and Compute Engine processes maintain consistency between database information and search indexes, and that indexes can be rebuilt from database information when necessary.

That tells you something important:

```text
DATABASE
is more fundamental than
ELASTICSEARCH INDEX
```

The search index is not intended to replace the database.

---

# 17. The Database

SonarQube requires persistent storage.

The database is where SonarQube stores important application data.

Sonar documents storage of information including:

* code quality and security metrics
* issues generated from analysis
* SonarQube configuration
* the analysis-report job queue

Think of the database as SonarQube's long-term memory.

---

# 18. Examples of Data Stored by SonarQube

Conceptually, the database may hold information associated with:

```text
Projects
Issues
Metrics
Configuration
Users
Permissions
Quality profiles
Quality gates
Analysis history
Background-task information
Security findings
Project settings
```

For example:

```text
Project:
payment-service

Last Analysis:
2026-09-11

Reliability:
A

Security:
A

Coverage:
82%

Quality Gate:
PASSED
```

This type of persistent project information must survive:

```text
SonarQube restart
Operating-system reboot
Application process restart
```

That persistence is why a proper database matters.

---

# 19. Supported Production Databases

Current SonarQube Server documentation supports external relational databases such as PostgreSQL, Microsoft SQL Server and Oracle, depending on the active SonarQube release. Sonar also includes an embedded H2 database for lightweight non-production scenarios, but explicitly advises against using H2 for production.

For our later labs, you will commonly see:

```text
SonarQube
    ↓
PostgreSQL
```

because PostgreSQL is a common production choice.

---

# 20. Why H2 Is Not a Production Database Choice

The embedded database is useful when a beginner wants to:

```text
install SonarQube
open it
experiment
learn the interface
```

But production systems require stronger characteristics around:

```text
durability
concurrency
backup
recovery
performance
scalability
high availability
```

Sonar specifically recommends external production databases and advises using the embedded H2 database for development, testing and trial scenarios rather than production workloads.

```text
        SonarScanner

        Analysis Report
```

The scanner is responsible for coordinating project analysis.

Examples include:

```text
Developer laptop

Jenkins agent
```

Usually, production teams perform authoritative analysis in CI rather than depending entirely on developers manually running scans.

```text
     ↓
Same pipeline
     ↓
Same quality checks
```

You will encounter different scanner integrations depending on the project.

Examples include concepts such as:

```text
SonarScanner CLI
```

# 24. What the Scanner Actually Does

At a simplified beginner level, the scanner:

1. loads analysis configuration
2. contacts SonarQube
3. determines relevant project configuration
4. identifies files within analysis scope
5. invokes appropriate language analyzers
6. processes source-code information
7. gathers metrics and findings
8. gathers supported external report information such as coverage
9. creates an analysis report
10. uploads the report to SonarQube

Sonar documentation describes analysis as a process where data is requested from the server, project files are processed, and resulting information is returned to the server as an analysis report.

---

# 25. Does SonarScanner Upload Your Entire Repository?

Avoid thinking of the workflow as:

```text
Scanner copies complete Git repository
        ↓
Server does everything
```

That is an oversimplification.

Much of the source-code analysis occurs on the scanner side.

The scanner generates analysis information and sends an analysis report to the server for further processing.

Think:

```text
SOURCE CODE
   ↓
SCANNER-SIDE ANALYSIS
   ↓
ANALYSIS REPORT
   ↓
SERVER-SIDE PROCESSING
```

That distinction will become critical later when troubleshooting.

---

# 26. Scanner-Side vs Server-Side Responsibilities

This is one of the most useful architecture distinctions.

## Scanner side

Think:

```text
Near the source code
```

Responsibilities include:

```text
Read project configuration

Determine source files

Load analyzers

Analyze source code

Read relevant build information

Read test/coverage reports

Generate analysis information

Upload analysis report
```

## Server side

Think:

```text
Central processing and storage
```

Responsibilities include:

```text
Receive report

Queue processing job

Process report

Persist results

Update issue information

Update metrics

Update search indexes

Evaluate and expose project state

Serve dashboards

Provide APIs
```

So:

```text
SCANNER
answers:
"What does this project analysis contain?"

SERVER
answers:
"How should the results be processed, stored and presented?"
```

# 27. Projects

A **project** in SonarQube represents a codebase being analyzed and tracked.

Example:

```text
payment-service
```

could have a SonarQube project.

So could:

```text
inventory-api
customer-portal
mobile-backend
authentication-service
```

Each project has an identifying key.

Conceptually:

```text
SonarQube
   │
   ├── payment-service
   │     ├── issues
   │     ├── measures
   │     ├── history
   │     └── settings
   │
   ├── inventory-api
   │     ├── issues
   │     └── measures
   │
   └── customer-portal
```

A project can be created beforehand or can be introduced through analysis depending on configuration and workflow. Sonar documentation notes that projects can be created/imported before analysis and, in supported workflows, can also appear through their first analysis.

---

# 28. Why Project Keys Matter

Consider two applications:

```text
payment-service
payment-service-v2
```

SonarQube needs a stable identifier so new analyses can be associated with the correct project.

Otherwise each scan could appear as an unrelated application.

Conceptually:

```text
Analysis Report
       ↓
Project Key
       ↓
payment-service
       ↓
Update Existing Project
```

Later you will use properties such as:

```text
sonar.projectKey
```

We will not configure them yet.

The important concept is identity.

# 29. Plugins

Plugins extend or integrate SonarQube capabilities.

Historically, SonarQube has used plugins for areas such as:

```text
language analysis
authentication
integration capabilities
additional functionality
```

However, you should not think:

```text
Need anything?
Just install random plugin.
```

Plugins run inside an important production platform.

That means a plugin can affect:

```text
compatibility
upgrades
stability
security
supportability
```

Production teams should use plugins deliberately and verify compatibility with the SonarQube version they operate.

---

# 30. Plugin Risk

Imagine:

```text
SonarQube 1
    +
Third-party plugin version X
```

works.

Then you upgrade SonarQube.

```text
SonarQube 2
    +
Old plugin X
```

The plugin may no longer be compatible.

Potential outcome:

```text
Startup failure

Feature failure

Unexpected behavior

Upgrade blocked
```

This is why plugin inventory becomes part of upgrade planning.

# 31. Analysis Reports

An **analysis report** is the package of analysis information produced by the scanner and submitted to SonarQube for server-side processing.

Conceptually:

```text
Source Files
    ↓
Scanner
    ↓
Analysis
    ↓
Issues + Metrics + Metadata
    ↓
Analysis Report
    ↓
SonarQube
```

The report is not simply:

```text
a PDF
```

or:

```text
a human-readable report document
```

It is machine-oriented analysis information intended for SonarQube processing.

---

# 32. What Can an Analysis Report Represent?

At a conceptual level, it can carry information derived from analysis including things such as:

```text
source information
issues
metrics
analysis metadata
coverage-related information
SCM-related information
```

Sonar documentation describes the scanner output submitted to the server as containing analysis information such as sources, issues and metrics.

# 33. How Source Code Reaches SonarQube

This needs a precise explanation.

The common beginner assumption is:

```text
GitHub
  ↓
SonarQube downloads repository
  ↓
SonarQube scans everything
```

That is not the normal scanner-based architecture.

A more accurate workflow is:

```text
Git Repository
      ↓
CI Runner checks out code
      ↓
Files exist on CI runner
      ↓
SonarScanner runs there
      ↓
Scanner analyzes code
      ↓
Analysis report produced
      ↓
Report sent to SonarQube
```

For example:

```text
GitHub
   ↓
GitHub Actions
   ↓
Checkout repository
   ↓
Build
   ↓
Test
   ↓
SonarScanner
   ↓
SonarQube Server
```

This distinction matters tremendously for debugging.

---

# 34. Example: GitHub Actions Architecture

Consider:

```text
Developer
    ↓
git push
    ↓
GitHub Repository
    ↓
GitHub Actions Runner
    ↓
Checkout Code
    ↓
Build
    ↓
Tests
    ↓
Coverage
    ↓
SonarScanner
    ↓
HTTPS
    ↓
SonarQube
```

Notice where the code exists during analysis:

```text
GitHub Actions Runner
```

That means failures involving:

```text
missing files
wrong working directory
missing compiled classes
coverage report path
Git history
permissions
```

may be scanner/runner-side problems rather than server problems.

# 35. What Happens During Analysis?

Now connect everything together.

Suppose a developer pushes Java code.

The sequence may look like:

```text
1. Developer pushes code

2. CI pipeline starts

3. CI runner checks out repository

4. Application compiles

5. Tests run

6. Coverage report is generated

7. SonarScanner starts

8. Scanner contacts SonarQube

9. Scanner retrieves relevant configuration

10. Scanner analyzes project files

11. Scanner gathers analysis data

12. Scanner creates analysis report

13. Report is uploaded

14. SonarQube queues background task

15. Compute Engine processes report

16. Database is updated

17. Elasticsearch indexes are updated

18. Project dashboard becomes current

19. Quality information is available to pipeline/users
```

This is the architecture you should visualize whenever you hear:

```text
Run SonarQube analysis
```

# 36. Step 1: Scanner Contacts the Server

The scanner first needs server information.

Conceptually:

```text
Scanner
   ↓
HTTPS
   ↓
SonarQube
```

It may require:

```text
Server URL

Authentication token

Project information

Analysis configuration
```

If this communication fails:

```text
Connection refused

DNS failure

Certificate error

401 Unauthorized

403 Forbidden
```

the scanner may never begin meaningful analysis.

---

# 37. Step 2: Scanner Determines Analysis Scope

Not every file is necessarily analyzed.

The scanner considers configuration and language support.

Examples:

```text
src/
tests/
generated/
vendor/
node_modules/
build/
```

Some directories may be excluded.

Only supported and relevant files participate according to configuration.

This means:

```text
File exists
```

does not automatically mean:

```text
File was analyzed.
```

---

# 38. Step 3: Language Analysis

Different programming languages require different analysis logic.

For example:

```text
Java
Python
JavaScript
C#
```

are different languages with different syntax and semantics.

Appropriate analyzers inspect them differently.

For some languages, analysis may also depend on compiled artifacts. Sonar's documentation notes, for example, that certain language analyses require compiled forms such as Java `.class` files or .NET assemblies.

This explains why:

```text
Source exists
```

may still not be enough for a correct analysis.

---

# 39. Step 4: Report Creation

After scanner-side analysis finishes:

```text
Analysis data
      ↓
Packaged
      ↓
Analysis Report
```

At this stage, the scanner has not directly rewritten the SonarQube project dashboard.

It submits the report to the server.

---

# 40. Step 5: Report Upload

The scanner sends the report to SonarQube through the network.

Usually:

```text
HTTP / HTTPS
```

Conceptually:

```text
CI Runner
   ↓
TCP connection
   ↓
HTTPS
   ↓
Reverse Proxy
   ↓
SonarQube Web Layer
```

The communication must cross whatever infrastructure exists between them:

```text
DNS
Firewall
Proxy
Load balancer
Security groups
TLS
Network routing
Authentication
```

Any of those can break analysis upload.

---

# 41. Step 6: Report Enters the Queue

After receipt:

```text
Analysis Report
       ↓
Background Task Queue
```

The report waits for server-side processing.

If the system has little load:

```text
Wait time ≈ short
```

If hundreds of reports are arriving:

```text
Queue
 ↓
Queue
 ↓
Queue
 ↓
processing delayed
```

This is why Compute Engine capacity matters in larger environments.

---

# 42. Step 7: Compute Engine Processes the Report

The Compute Engine takes the task.

```text
Queue
  ↓
Compute Engine
  ↓
Process Report
```

During processing, SonarQube can:

```text
update issues
calculate final measures
compare analysis state
persist project information
update project history
prepare searchable information
```

The resulting state becomes part of the SonarQube project.

---

# 43. Step 8: Database Is Updated

Persistent information is written to the database.

Conceptually:

```text
Compute Engine
     ↓
SQL Database
```

This may include updates related to:

```text
issues
metrics
analysis state
project data
configuration-dependent results
```

The database therefore has direct performance implications for analysis processing.

---

# 44. Step 9: Search Indexes Are Updated

Searchable information must remain aligned with persistent SonarQube state.

Conceptually:

```text
Database State
      +
Processed Analysis
      ↓
Search Index Updates
      ↓
Elasticsearch
```

Users can then efficiently query and filter SonarQube information.

---

# 45. Step 10: Dashboard Becomes Current

Eventually:

```text
Compute Engine
     ↓
Task completes
     ↓
Project state updated
     ↓
Dashboard reflects new analysis
```

This explains why there can be a short delay between:

```text
Scanner: SUCCESS
```

and:

```text
Dashboard: updated
```

That delay is architectural, not necessarily an error.

You generally administer SonarQube through:

```text
UI
Web API
supported configuration
```

rather than directly modifying database tables.

---

# 47. Why You Should Not Manually Edit the SonarQube Database

Suppose you see a project setting and decide:

```text
I'll just change this directly with SQL.
```

That can create problems because SonarQube has internal expectations around:

```text
schema
relationships
indexes
caches
search indexes
application logic
```

Direct manual database changes can create inconsistent state.

Production rule:

```text
Use supported SonarQube interfaces.

Do not treat the SonarQube database as an application database you casually modify.
```

# 52. Why Database Latency Matters

Every analysis can involve substantial database interaction.

If:

```text
SonarQube
```

is in:

```text
New York
```

while the database is unnecessarily located very far away with high latency, every interaction becomes slower.

Sonar recommends locating the production database on a separate host while keeping network latency between SonarQube and the database low.

Architecture:

```text

       ↕
    Database
```

not:

```text

   ↓

   ↓
```

# 55. What Single-Node Means

Single-node does not mean:

```text
Only one Java process.
```

It means the major SonarQube server processes are running on the same SonarQube host.

Conceptually:

```text
ONE HOST
│
├── Web JVM
├── Compute Engine JVM
└── Elasticsearch JVM
```

Sonar's monitoring documentation treats Web, Compute Engine and Elasticsearch as distinct Java processes, each with its own memory configuration.

This matters when sizing memory.

---

# 56. Why Memory Matters

Imagine a SonarQube machine with:

```text
4 GB RAM
```

You cannot think:

```text
SonarQube = one small web app.
```

Multiple Java processes need memory.

Elasticsearch also has significant memory requirements.

The operating system needs memory.

The host therefore needs enough resources for all components.

Sonar's current host guidance uses approximately 4 GB RAM as a starting point for small-scale installations and higher resources for larger ones. Actual production sizing depends on workload.

---

# 57. Why Disk Matters

Elasticsearch performs indexing.

Analysis creates persistent data.

Logs are written.

Database information grows.

Therefore:

```text
Disk capacity
+
Disk speed
+
Free disk space
```

matter.

Sonar specifically warns that Elasticsearch depends on sufficient free disk space and can protect itself by restricting index writes when disk usage becomes dangerously high.

This can cause surprising operational failures.

Example:

```text
Disk fills
   ↓
Elasticsearch protects indices
   ↓
SonarQube behavior degrades
```

# 59. Why Separate the Database?

One reason is resource isolation.

Imagine one server running:

```text
SonarQube Web
Compute Engine
Elasticsearch
PostgreSQL
Monitoring
Reverse Proxy
```

All these components compete for:

```text
CPU
RAM
Disk
I/O
```

If Elasticsearch creates heavy disk activity:

```text
Elasticsearch
     ↓
High disk I/O
     ↓
PostgreSQL slows
     ↓
Compute Engine slows
```

Resource contention can affect the whole platform.

Separating the database helps isolate workloads and improves production manageability.

# 61. Production Security Boundary

A good deployment does not expose every component to everyone.

Example:

```text
Users
  ↓
443
  ↓
Load Balancer
  ↓
9000
  ↓
SonarQube

SonarQube
  ↓
5432
  ↓
PostgreSQL
```

Users should not normally be allowed:

```text
User → PostgreSQL
```

CI runners need access to SonarQube.

They do not need unrestricted database access.

So network permissions might conceptually be:

```text
Developer → SonarQube 443      ALLOW

CI Runner → SonarQube 443      ALLOW

SonarQube → PostgreSQL 5432    ALLOW

Internet → PostgreSQL 5432     DENY
```

This is basic least-privilege networking.

# 62. High Availability and Data Center Architecture

For larger environments requiring horizontal scaling or higher availability, SonarQube Data Center Edition supports clustered architectures.

The architecture becomes more complex.

Conceptually:



is not the only possible architecture.

# 67. Common Beginner Mistakes

## Mistake 1: Thinking SonarQube performs all analysis on the server

Much of project analysis occurs where the scanner runs.

---

## Mistake 2: Thinking scanner success means server processing finished

The report can still be waiting for Compute Engine processing.

---

## Mistake 3: Treating Elasticsearch as the primary database

It is primarily used for indexed search data.

The relational database is critical persistent storage.

---

## Mistake 4: Using the embedded H2 database in production

H2 is intended for learning, trial and testing scenarios, not serious production use.

---

## Mistake 5: Exposing the database publicly

Only systems that require database communication should be able to reach it.

---

## Mistake 6: Running everything on one undersized server

Web, Compute Engine, Elasticsearch and possibly the database all consume resources.

---

## Mistake 7: Assuming port 9000 should be publicly exposed

Production deployments commonly place HTTPS infrastructure in front of SonarQube.

---

## Mistake 8: Treating plugins casually

Plugins can affect stability and upgrade compatibility.

---

## Mistake 9: Ignoring the background-task queue

A growing queue can indicate capacity or performance problems.

---

## Mistake 10: Troubleshooting without understanding component boundaries

Always ask:

```text
Where did the failure occur?
```
