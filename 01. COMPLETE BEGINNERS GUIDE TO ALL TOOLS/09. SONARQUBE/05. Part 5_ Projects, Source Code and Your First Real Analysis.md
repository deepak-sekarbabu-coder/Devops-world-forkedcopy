# Part 5: Projects, Source Code and Your First Real Analysis

## Stop Administering SonarQube Temporarily and Actually Use It

In Parts 1 through 4, most of our attention was on the **SonarQube platform itself**.

You learned what SonarQube is, how its architecture works, how to install it directly, and how to run it with Docker and PostgreSQL.

Our Part 4 architecture looked roughly like this:

```text
Developer
    ↓
Browser
    ↓
localhost:9000
    ↓
SonarQube Container
    ↓
PostgreSQL Container
```

But there is an obvious question:

**Where is the source code?**

SonarQube exists to analyze software.

So in this part, we will temporarily stop thinking like the administrator maintaining the SonarQube server and start thinking like the engineer who actually wants to analyze an application.

We will build this:

```text
Sample Application
        ↓
   SonarScanner
        ↓
     SonarQube
        ↓
   Find Problem
        ↓
     Fix Code
        ↓
    Scan Again
        ↓
    Verify Fix
```

By the end, you will understand the complete first-analysis workflow:

```text
Create Project
      ↓
Generate Token
      ↓
Prepare Source Code
      ↓
Install SonarScanner
      ↓
Configure Project
      ↓
Run Scanner
      ↓
Upload Analysis
      ↓
SonarQube Processes Report
      ↓
View Dashboard
      ↓
Investigate Issue
      ↓
Fix Source Code
      ↓
Scan Again
      ↓
Verify Issue Disappears
```

This is the point where SonarQube becomes useful rather than merely installed.

# 5. What Is a SonarQube Project?

A SonarQube project represents a codebase being analyzed and tracked by SonarQube.

For example, an organization might have:

```text
SonarQube
│
├── payment-service
├── customer-api
├── inventory-service
├── authentication-service
├── mobile-backend
└── reporting-service
```

Each can be represented as a separate SonarQube project.

A project provides a place where SonarQube can track things such as:

```text
Issues
Reliability
Security
Maintainability
Duplications
Coverage
Lines of code
Quality Gate status
Analysis history
```

Think:

```text
Git Repository
      ↓
Application / Service
      ↓
SonarQube Project
      ↓
Quality History
```

---

# 6. A SonarQube Project Is Not Your Source-Code Repository

This distinction matters.

Your Git repository contains your actual files and history.

For example:

```text
GitHub Repository
│
├── src/
├── tests/
├── README.md
└── configuration files
```

SonarQube does not replace that repository.

Instead:

```text
Git Repository
     ↓
Working Copy
     ↓
SonarScanner
     ↓
SonarQube Project
```

The SonarQube project represents the analysis of that codebase.

So:

```text
GitHub
=
source control

SonarQube
=
code quality/security analysis and quality management
```

They solve different problems.

# 9. Project Key

The project key is the identifier SonarQube uses to identify the project.

For example:

```text
sonarqube-beginner-demo
```

This becomes extremely important because the scanner must know:

> Which SonarQube project should receive this analysis?

The connection is:

```text
Source Code
      ↓
SonarScanner
      ↓
sonar.projectKey
      ↓
SonarQube Project
```

If the scanner sends:

```text
sonar.projectKey=sonarqube-beginner-demo
```

SonarQube associates that analysis with that project.

---

# 10. Project Name vs Project Key

Think:

| Concept      | Example                 | Purpose                     |
| ------------ | ----------------------- | --------------------------- |
| Project name | SonarQube Beginner Demo | Human-readable display name |
| Project key  | sonarqube-beginner-demo | Stable project identifier   |

A beginner mistake is treating them as interchangeable.

They are related, but they serve different purposes.

---

# 11. Choosing Good Project Keys

A project key should be:

```text
Predictable
Unique
Meaningful
Stable
```

For example:

```text
payment-service
```

could work.

In a larger organization, you might use a naming convention such as:

```text
team-a:payment-service
```

or another organization-approved scheme.

The exact convention is less important than consistency.

Avoid meaningless identifiers such as:

```text
project123
test-final-new2
abc
```

for real production projects.

A project key may eventually appear in:

```text
Scanner configuration
CI/CD pipelines
API calls
Automation
Dashboards
Scripts
```

Changing identifiers carelessly creates unnecessary operational work.

# 13. Why Authentication Is Required

Imagine SonarQube accepted arbitrary analysis from anyone who could reach it.

An unauthorized person could potentially attempt to:

```text
Submit analyses
Pollute project results
Interact with protected project information
Abuse server resources
```

Therefore, scanner operations need appropriate authorization.

We need:

```text
Scanner
   ↓
Credential
   ↓
SonarQube
   ↓
Authentication
   ↓
Authorized?
   ↓
Accept / Reject
```

This is where tokens enter the workflow.

---

# 14. What Is a SonarQube Token?

A token is a credential that can be used to authenticate to SonarQube without repeatedly embedding a user's normal account password in automation.

Conceptually:

```text
Username + Password
```

is not what we want to place throughout automated CI pipelines.

Instead:

```text
Authentication Token
```

can be used for automation.

Architecture:

```text
SonarScanner
      ↓
Token
      ↓
SonarQube
      ↓
Validate Token
      ↓
Authorized Analysis
```

---

# 15. Why Tokens Are Better for Automation

Imagine a Jenkins pipeline containing:

```text
Ann's normal SonarQube password
```

Now Ann changes her password.

The pipeline breaks.

Or someone obtains the pipeline configuration.

Now they may possess her interactive account password.

A better pattern is:

```text
Automation
   ↓
Dedicated credential/token
   ↓
Limited intended use
```

Tokens can also be managed separately from normal interactive credentials.

---

# 16. Generate a Token

During manual project setup, SonarQube may guide you through generating a token.

Alternatively, token management is available through your account/security area, depending on the version and permissions.

Create a token with a recognizable name such as:

```text
sonarqube-beginner-lab
```

SonarQube will generate a value resembling a long random credential.

Do not use examples from tutorials as your actual token.

Your real token should be generated by your SonarQube instance.

---

# 17. Critical Token Security Rule

When SonarQube displays the token:

**store it securely.**

Do not put it in:

```text
GitHub repository
README.md
sonar-project.properties
Application source code
Dockerfile
Screenshots
Public tutorials
Slack messages
Plaintext documentation
```

Treat it as a password.

If you accidentally expose it:

```text
Revoke token
     ↓
Generate replacement
     ↓
Update authorized systems
```

Do not simply delete it from the latest Git commit and assume the secret was never exposed.

---

# 18. Token vs Project Key

Do not confuse these.

```text
Project Key
=
Which project?
```

```text
Token
=
Who/what is authenticating?
```

Together:

```text
Scanner
│
├── Project Key
│       ↓
│   Target Project
│
└── Token
        ↓
    Authentication
```

This is critical.

# 40. Understanding `-D`

You will frequently see scanner commands containing:

```text
-D
```

For example:

```bash
sonar-scanner -Dsonar.host.url=http://localhost:9000
```

`-D` supplies an analysis/system property to the scanner invocation.

Conceptually:

```text
-D
 ↓
property=value
```

Example:

```text
sonar.host.url=http://localhost:9000
```

means:

> For this scanner execution, use this SonarQube server address.

---

# 41. Authentication Without Hard-Coding the Token

A better local-lab pattern is to place the token in an environment variable for the current shell rather than in the repository.

For example:

```bash
export SONAR_TOKEN='YOUR_REAL_TOKEN'
```

Replace:

```text
YOUR_REAL_TOKEN
```

with the token generated by your own SonarQube server.

Do not literally use the placeholder.

---

# 42. What `export` Does

On Bash/Zsh:

```bash
export SONAR_TOKEN='...'
```

creates an environment variable and makes it available to child processes started from that shell.

Conceptually:

```text
Terminal Shell
     ↓
SONAR_TOKEN exists
     ↓
sonar-scanner process
     ↓
Can read credential
```

Verify only that the variable exists without printing the secret:

```bash
if [ -n "$SONAR_TOKEN" ]; then
  echo "SONAR_TOKEN is set"
else
  echo "SONAR_TOKEN is not set"
fi
```

Avoid:

```bash
echo $SONAR_TOKEN
```

when screen sharing, recording tutorials, collecting terminal logs, or working around other people.

# 44. What Happens When You Press Enter?

A lot happens.

Do not think:

```text
sonar-scanner
=
upload file
```

A more useful mental model is:

```text
1. Scanner starts

2. Scanner reads configuration

3. Scanner identifies project

4. Scanner connects to SonarQube

5. Scanner obtains relevant server-side analysis configuration

6. Scanner discovers files

7. Language analysis is performed

8. Metrics/issues are calculated or collected

9. Analysis report is prepared

10. Report is submitted to SonarQube

11. SonarQube accepts the report

12. Server processes it asynchronously

13. Project results are updated
```

This explains why scanner completion and dashboard processing are related but not identical events.

# 46. How Source Code Reaches SonarQube

There is an important nuance.

Beginners often say:

> SonarScanner uploads my whole repository into SonarQube.

That mental model is too simplistic.

The scanner examines the source code in the analysis environment and produces analysis information/report data that is sent to the SonarQube server. SonarQube stores the information needed to present issues, metrics and source-related analysis views according to its analysis architecture.

The practical lesson is:

```text
Repository
   ↓
Scanner works where source exists
   ↓
Analysis information
   ↓
SonarQube
```

The SonarQube server does not need to `cd` into your MacBook project directory.

# 48. What Does `EXECUTION SUCCESS` Mean?

A successful scanner execution generally means the scanner completed its job and submitted the analysis successfully.

But be precise.

It does not mean:

```text
The code has zero issues.
```

It does not necessarily mean:

```text
The Quality Gate passed.
```

### Mistake 14: Copying an old scanner command blindly

Scanner authentication and runtime behavior can evolve. Verify against the scanner/server version being deployed.

### Mistake 15: Ignoring the scanner logs

The logs often tell you exactly which layer failed.
