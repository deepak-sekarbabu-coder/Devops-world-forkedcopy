# Part 15: Users, Groups, Permissions, Tokens and Security

## Secure SonarQube Properly

In Parts 12, 13 and 14, we automated SonarQube.

We built pipelines like:

```text
Developer
↓
GitHub / Jenkins
↓
CI/CD Pipeline
↓
Build
↓
Test
↓
Coverage
↓
SonarQube
↓
Quality Gate
↓
Continue / Stop
```

But automation creates a new question:

```text
WHO IS ALLOWED TO DO WHAT?
```

Who can log in?

Who can see source code?

Who can analyze a project?

Who can change a Quality Gate?

Who can change a Quality Profile?

Who can administer a project?

Who can administer the entire SonarQube instance?

What credentials should Jenkins use?

What credentials should GitHub Actions use?

What happens when an employee leaves?

What happens when a token leaks?

Those are security and access-control questions.

Part 15 answers them.

---

# 1. The Security Architecture

Start with this mental model:

```text
IDENTITY
↓
AUTHENTICATION
↓
AUTHORIZATION
↓
PERMISSIONS
↓
RESOURCE
↓
ACTION
```

Example:

```text
Ann
↓
Logs in
↓
SonarQube verifies identity
↓
Checks permissions
↓
Project A
↓
Browse allowed
```

Another identity:

```text
github-actions-payment-service
↓
Authenticates with token
↓
SonarQube verifies token
↓
Checks Execute Analysis permission
↓
Payment Service
↓
Analysis allowed
```

Security begins with identity.

---

# 2. Authentication

Authentication answers:

```text
WHO ARE YOU?
```

Examples:

```text
Username + Password

LDAP

SAML

GitHub Authentication

GitLab Authentication

Bitbucket Cloud Authentication

HTTP Header Authentication

Authentication Token
```

Authentication proves or establishes identity.

---

# 3. Authorization

Authorization answers:

```text
WHAT ARE YOU ALLOWED TO DO?
```

For example:

```text
User = Alice

Authenticated?
YES

Administer System?
NO

Browse Payment Service?
YES

Execute Analysis?
NO

Administer Issues?
YES
```

Authentication and authorization are not the same.

---

# 4. Authentication vs Authorization

Memorize this:

```text
Authentication
=
Who are you?
```

```text
Authorization
=
What can you do?
```

A person can authenticate successfully and still be unauthorized to perform an action.

Example:

```text
Alice logs in successfully
↓
Authentication PASS
↓
Alice tries to change global permissions
↓
Authorization FAIL
```

Nothing is wrong with Alice's password.

She simply does not have that permission.

---

# 5. Why Beginners Confuse Them

Suppose SonarScanner returns:

```text
Not authorized
```

A beginner may immediately regenerate the token.

But the token may be valid.

The real problem might be:

```text
Token Valid
↓
Identity Recognized
↓
Execute Analysis Permission Missing
```

That is an authorization problem.

Always distinguish:

```text
Authentication failure
```

from:

```text
Authorization failure
```

---

# 6. Identity

An identity represents an actor.

Actors can be human:

```text
Developer

Security Engineer

DevOps Engineer

SonarQube Administrator

Engineering Manager
```

or non-human:

```text
Jenkins

GitHub Actions

GitLab CI

Automation Script

API Integration
```

Do not design security only around human users.

CI/CD systems are identities too.

---

# 7. Human vs Machine Identities

Human:

```text
Alice
↓
Browser
↓
SonarQube
```

Machine:

```text
GitHub Actions
↓
Token
↓
SonarQube API / Scanner
```

The machine should not normally pretend to be a global administrator.

It should receive only the capabilities required for its job.

---

# 8. Users

A SonarQube user is an identity represented inside SonarQube.

A user may originate from:

```text
Local SonarQube Account

LDAP

SAML Identity Provider

GitHub

GitLab

Bitbucket Cloud

Other supported authentication integration
```

The exact lifecycle depends on the authentication and provisioning method.

---

# 9. Local Users

A local account is managed directly within SonarQube rather than relying entirely on an external identity provider.

A simple lab might have:

```text
admin

developer1

ci-payment-service
```

But large organizations often prefer centralized identity management.

---

# 10. Why Centralized Identity Helps

Imagine a company with:

```text
3,000 employees

150 internal systems
```

Without centralized identity management:

```text
Employee Leaves
↓
Disable 150 Accounts Manually
```

That is difficult and error-prone.

Centralized identity architecture aims for something closer to:

```text
Identity Provider
↓
User Disabled
↓
Connected Systems Reflect Access Change
```

The exact deprovisioning behavior depends on the integration and provisioning mode.

---

# 11. Groups

Managing every permission individually becomes difficult.

Imagine:

```text
200 Developers
```

You could configure:

```text
Developer 1 → Permission
Developer 2 → Permission
Developer 3 → Permission
...
Developer 200 → Permission
```

That is poor administration.

Instead:

```text
Developers Group
↓
Permissions
```

Then:

```text
Alice ─┐
Bob ───┼→ Developers
Maria ─┤
John ──┘
```

---

# 12. Why Groups Matter

Groups provide:

```text
Consistency

Scalability

Simpler onboarding

Simpler offboarding

Reduced configuration mistakes

Easier audits
```

Instead of asking:

```text
What permissions does every employee need?
```

you ask:

```text
What role does this person perform?
```

Then place them into the appropriate group.

---

# 13. User Permissions Are Additive

A user may receive permissions:

```text
Directly
+
From Group A
+
From Group B
```

Conceptually:

```text
User
├── Direct Permissions
├── Developer Group Permissions
└── Security Reviewers Group Permissions
        ↓
Effective Permissions
```

This matters during troubleshooting.

---

# 14. Permission Troubleshooting Example

Suppose Alice unexpectedly has:

```text
Administer Issues
```

You inspect Alice directly.

Nothing appears unusual.

But Alice belongs to:

```text
Developers

Payment Team

Security Reviewers
```

and:

```text
Security Reviewers
↓
Administer Issues
```

That group membership explains the access.

Never inspect only direct permissions.

---

# 15. Built-In Groups

SonarQube includes important built-in groups.

Two you should recognize are:

```text
sonar-users
```

and:

```text
sonar-administrators
```

---

# 16. `sonar-users`

Conceptually:

```text
Authenticated User
↓
sonar-users
```

This group represents authenticated users.

Do not assume its default permissions automatically match your organization's security policy.

Review them.

---

# 17. Why Reviewing `sonar-users` Matters

Suppose:

```text
sonar-users
↓
Global Execute Analysis
```

Then a large population of authenticated users may inherit powerful analysis capability.

Your organization's desired architecture might instead be:

```text
Developers
↓
Browse

CI Service Identities
↓
Execute Analysis
```

The correct model depends on organizational requirements.

The important lesson is:

```text
DEFAULT
≠
AUTOMATICALLY SECURE FOR YOUR ORGANIZATION
```

---

# 18. `sonar-administrators`

This is associated with administrative access.

Administrative access is extremely powerful.

Think:

```text
sonar-administrators
↓
System Administration
↓
Security Configuration
↓
Permissions
↓
Projects
↓
Quality Configuration
```

Membership should be tightly controlled.

---

# 19. Important Group-Synchronization Risk

If external group synchronization is configured, group names become security-sensitive.

An external group that maps unexpectedly to a highly privileged SonarQube group could create unauthorized privilege.

Therefore administrative group mapping must be designed carefully.

---

# 20. Role-Based Thinking

A useful enterprise model might include groups such as:

```text
sq-system-admins

sq-quality-admins

sq-security-reviewers

sq-developers

sq-project-admins-payment

sq-project-admins-orders
```

Then assign permissions to groups.

Do not treat these names as mandatory SonarQube defaults.

They are examples of a security design.

---

# 21. Permission Scope

SonarQube permissions broadly operate at different scopes.

Think:

```text
GLOBAL
```

and:

```text
PROJECT
```

This distinction is critical.

---

# 22. Global Permissions

Global permissions affect the SonarQube instance rather than one specific project.

Examples include capabilities such as:

```text
Administer System

Administer Quality Gates

Administer Quality Profiles

Execute Analysis

Create Projects

Create Applications

Create Portfolios
```

Some capabilities depend on edition/features.

---

# 23. Administer System

This is extremely powerful.

Conceptually:

```text
Administer System
↓
Control SonarQube Instance
```

Treat it as privileged administrative access.

Do not grant it merely because someone:

```text
Uses SonarQube frequently
```

or:

```text
Is a senior developer
```

Seniority does not automatically require system administration.

---

# 24. Administrator Is a Responsibility

An administrator may be responsible for:

```text
Security configuration

Authentication

Permissions

System configuration

Operational settings

Integration configuration
```

This is infrastructure administration.

It should not be confused with normal project use.

---

# 25. Administer Quality Gates

This permission controls the ability to create or modify Quality Gates.

Remember Part 8.

Quality Gates define engineering policy.

Therefore:

```text
Change Quality Gate
=
Change Engineering Control
```

This should be restricted.

---

# 26. Why Quality Gate Administration Is Sensitive

Suppose policy requires:

```text
New Coverage ≥ 80%
```

Someone changes it to:

```text
New Coverage ≥ 10%
```

The application code did not improve.

The control was weakened.

Therefore changing a Quality Gate is a governance action.

---

# 27. Administer Quality Profiles

Remember Part 7.

Quality Profiles control which rules participate in analysis.

Therefore:

```text
Deactivate Security Rule
```

can materially affect what SonarQube reports.

Quality Profile administration should not be handed to everyone.

---

# 28. Separation of Duties

You may intentionally separate:

```text
System Administrators

Quality Profile Administrators

Quality Gate Administrators

Project Administrators

Developers

Security Reviewers
```

One person does not automatically need every privilege.

---

# 29. Execute Analysis

This permission deserves special attention.

It permits an identity to submit analysis.

At global scope:

```text
Global Execute Analysis
↓
Ability to analyze projects across instance
```

That is broader than:

```text
Execute Analysis on Project A
```

---

# 30. Why Global Execute Analysis Is Powerful

Imagine a CI token leaks.

If it has:

```text
Global Execute Analysis
```

the exposure can potentially affect analysis capabilities across many projects.

If it has:

```text
Project A Execute Analysis
```

the blast radius is much smaller.

This is why project-scoped analysis credentials are generally preferable when possible.

---

# 31. Create Projects

This controls whether users can create projects.

Do you want:

```text
Every authenticated employee
```

to create arbitrary SonarQube projects?

Maybe.

Maybe not.

An enterprise might require:

```text
Repository Onboarding Process
↓
Approved Project Creation
```

The decision should be intentional.

---

# 32. Project Permissions

Project permissions apply to a specific project.

Important examples include:

```text
Browse Project

See Source Code

Administer Issues

Administer Security Hotspots

Administer Project

Execute Analysis on Project
```

---

# 33. Browse Project

For a private project, this controls whether a user can access the project.

Architecture:

```text
User
↓
Browse Project?
↓
YES
↓
Project Visible
```

---

# 34. See Source Code

This controls access to source code through SonarQube for private projects, together with the necessary project browsing access.

Do not assume:

```text
Everyone who can view metrics
```

must automatically be allowed to inspect source.

Source code can contain sensitive intellectual property.

---

# 35. Public vs Private Projects

This is a major security decision.

A public project can expose project information more broadly.

A private project allows explicit access control.

Do not assume the word:

```text
public
```

means:

```text
public Internet
```

in every deployment architecture.

It refers to SonarQube project visibility semantics.

But the security consequence remains important.

---

# 36. Default Project Visibility

Review the default visibility configured for new projects.

A security-conscious internal organization may decide:

```text
Private by default
```

is appropriate.

That decision depends on business requirements.

The key principle is:

```text
Do not discover months later that sensitive source was visible more broadly than intended.
```

---

# 37. Administer Issues

This permission allows privileged issue-management actions.

Examples can include actions such as:

```text
Accept Issue

Mark False Positive

Change Severity
```

These actions affect the meaning of SonarQube results.

Therefore this is not merely:

```text
Can read issue.
```

It is a governance capability.

---

# 38. False Positive Is Security-Sensitive

Suppose SonarQube reports a security-related issue.

Someone marks it:

```text
False Positive
```

without proper investigation.

The code did not change.

The issue's treatment changed.

Therefore issue administration deserves controls.

---

# 39. Administer Security Hotspots

Security Hotspots require human review.

The permission to change their review status should be assigned intentionally.

A mature organization may assign this to:

```text
Security Team

AppSec Team

Trained Security Champions
```

rather than every user.

---

# 40. Administer Project

This is powerful within one project.

A project administrator may be able to modify project settings and project-level permissions.

Think:

```text
Project Admin
↓
Project Configuration
↓
Project Permissions
↓
Webhooks / Settings
```

Do not confuse:

```text
Project Administrator
```

with:

```text
System Administrator
```

---

# 41. Project Admin vs System Admin

Project admin:

```text
Payment Service
↓
Administrative Control
```

System admin:

```text
Entire SonarQube Instance
↓
Administrative Control
```

Prefer the narrower permission when it solves the requirement.

---

# 42. Execute Analysis on Project

This allows analysis for a particular project.

Architecture:

```text
CI Identity
↓
Execute Analysis on Payment Service
↓
Payment Service Analysis
```

This is ideal for many CI/CD identities.

---

# 43. CI Identity Design

Bad:

```text
GitHub Actions
↓
Global Administrator Token
```

Better:

```text
GitHub Actions
↓
Project Analysis Token
↓
Payment Service
```

The second design follows least privilege much more closely.

---

# 44. Permission Templates

Imagine creating 500 projects.

Without templates:

```text
Project 1 → Configure permissions manually
Project 2 → Configure permissions manually
...
Project 500 → Configure permissions manually
```

That does not scale.

Permission templates solve this problem.

---

# 45. What Is a Permission Template?

A permission template defines default project-related permissions.

Conceptually:

```text
Permission Template
↓
New Project
↓
Standard Permissions
```

Example:

```text
Private Application Template

Developers
→ Browse

Security Reviewers
→ Browse
→ See Source Code
→ Administer Security Hotspots

CI Identity
→ Execute Analysis

Project Admins
→ Administer Project
```

---

# 46. Why Permission Templates Matter

They improve:

```text
Consistency

Security

Automation

Onboarding

Governance

Auditability
```

Instead of relying on humans to remember every permission, you define a standard.

---

# 47. Default Permission Template

SonarQube can use a default template for new projects.

Architecture:

```text
New Project
↓
No Special Matching Rule
↓
Default Permission Template
↓
Permissions Applied
```

---

# 48. Project-Key Pattern Templates

Templates can also be selected using project-key patterns.

Conceptually:

```text
payments-*
↓
Payments Template
```

```text
internal-*
↓
Internal Template
```

This can help automate permission models for different project families.

---

# 49. Be Careful With Patterns

A bad regular expression can match unintended projects.

Before deploying:

```text
Pattern
↓
Test
↓
Confirm Intended Projects
↓
Apply
```

Never casually introduce permission regex rules into production.

---

# 50. Important Template Behavior

Changing a permission template later does not necessarily mean every existing project automatically inherits the new permission configuration.

You may need to reapply the template to existing projects.

This is operationally important.

---

# 51. Security Drift

Suppose:

```text
January
Template updated
```

but:

```text
Existing Projects
↓
Old Permissions
```

while:

```text
New Projects
↓
New Permissions
```

Now your environment has permission drift.

Regular access reviews help identify this.

---

# 52. Administrators

A mature SonarQube deployment should have a small, clearly identified administrative population.

Example:

```text
SonarQube Platform Team
↓
2–5 Authorized Administrators
```

not:

```text
Entire Engineering Organization
↓
Admin
```

The exact number depends on organization size and availability requirements.

---

# 53. Avoid One Administrator Only

Least privilege does not mean:

```text
Only one person in the company can ever administer SonarQube.
```

That creates operational risk.

You need controlled redundancy.

For example:

```text
Primary Administrators
+
Emergency Recovery Process
```

---

# 54. Break-Glass Access

A mature environment may maintain emergency administrative recovery procedures.

Purpose:

```text
Primary Authentication Failure
↓
Emergency
↓
Controlled Recovery
```

Break-glass access should be:

```text
Rarely used

Strongly protected

Monitored

Documented

Reviewed after use
```

---

# 55. Developers

Developers generally need enough access to:

```text
View relevant projects

Inspect issues

Understand Quality Gate failures

Review source context where appropriate

Participate in remediation
```

They usually do not require:

```text
Administer System
```

---

# 56. Developer Principle

Give developers:

```text
Everything required to fix their code
```

without giving:

```text
Everything required to reconfigure the platform.
```

---

# 57. Security Reviewers

Security-focused identities may need:

```text
Browse Project

See Source Code

Review Security Findings

Administer Security Hotspots
```

depending on organizational responsibilities.

They do not automatically need:

```text
Administer System
```

---

# 58. CI/CD Service Identities

This is one of the most important sections.

CI/CD should be treated as its own identity.

Examples:

```text
Jenkins SonarQube Identity

GitHub Actions SonarQube Identity

GitLab CI SonarQube Identity
```

Do not simply reuse:

```text
Ann's Personal Token
```

for every production pipeline.

---

# 59. Why Personal CI Credentials Are Dangerous

Imagine:

```text
Pipeline
↓
Alice's Token
```

Then Alice leaves the company.

What happens?

```text
Alice Deactivated
↓
Token Invalid / Should Be Revoked
↓
Pipeline Breaks
```

or worse, poorly managed credentials continue existing without clear ownership.

Machine automation should have intentional lifecycle management.

---

# 60. Service Identity Ownership

Every CI identity should answer:

```text
What system owns this identity?

What project can it analyze?

Who manages it?

Where is its token stored?

When does it expire?

How is it rotated?

How is it revoked?

What happens if it leaks?
```

If nobody can answer these questions, credential governance is weak.

---

# 61. Analysis Permissions

A scanner does not need permission to administer SonarQube merely to submit analysis.

Its core requirement is analysis authorization.

Architecture:

```text
CI Runner
↓
Authentication Token
↓
Execute Analysis
↓
Submit Analysis
```

That is much narrower than:

```text
Administer System
```

---

# 62. Tokens

A token is a credential.

It allows software or users to authenticate without supplying the account password directly.

Think:

```text
Identity
↓
Token
↓
Authenticated Request
```

Tokens must be treated like secrets.

---

# 63. Why Tokens Are Better Than Passwords for Automation

Bad:

```text
Jenkins
↓
Human Username + Password
```

Better:

```text
Jenkins
↓
Purpose-Specific Token
```

Tokens can provide better lifecycle management:

```text
Generate

Scope

Store

Rotate

Expire

Revoke
```

---

# 64. Token Types

Current SonarQube Server distinguishes important token types including:

```text
User Token

Project Analysis Token

Global Analysis Token
```

Understand the difference.

---

# 65. User Token

A user token represents the permissions of the user who created it.

Conceptually:

```text
Alice
↓
User Token
↓
Alice's Permissions
```

If Alice is:

```text
System Administrator
```

then a user token can be extremely powerful.

---

# 66. Why Admin User Tokens Are Dangerous

Imagine:

```text
Global Admin
↓
User Token
↓
Stored in CI
↓
Token Leaks
```

The attacker may inherit a very broad set of capabilities.

Avoid using administrator user tokens for routine scanning.

---

# 67. Project Analysis Token

A project analysis token is associated with one project.

Architecture:

```text
Payment Service Token
↓
Payment Service
```

This is excellent for least privilege.

---

# 68. Blast Radius

Compare:

```text
Token A
↓
500 Projects
```

with:

```text
Token B
↓
1 Project
```

If each token leaks, which creates less potential exposure?

Usually:

```text
Token B
```

This is the blast-radius principle.

---

# 69. Recommended CI Pattern

For individual application pipelines:

```text
Application Repository
↓
Dedicated Project Analysis Token
↓
SonarQube Project
```

Example:

```text
payment-service repository
↓
payment-service Sonar token
↓
payment-service SonarQube project
```

---

# 70. Global Analysis Token

A global analysis token can analyze across projects.

Architecture:

```text
Central Analysis System
↓
Global Analysis Token
↓
Project A
Project B
Project C
...
```

This may be appropriate for some centralized automation.

But the credential is more powerful.

Therefore:

```text
More Scope
=
More Protection Required
```

---

# 71. Token Selection Decision

Ask:

```text
Does this pipeline analyze only one project?
```

If yes:

```text
Prefer narrow project-scoped analysis credential where possible.
```

If no:

```text
Determine whether broader analysis capability is genuinely required.
```

Never choose the broadest token because:

```text
It is easier.
```

---

# 72. Generating a Token

Conceptually:

```text
User
↓
My Account
↓
Security
↓
Generate Token
```

Choose:

```text
Name

Type

Expiration
```

according to current SonarQube capabilities and organizational policy.

---

# 73. Token Naming

Bad:

```text
token1
```

Better:

```text
github-actions-payment-service-prod
```

or:

```text
jenkins-orders-analysis
```

A good name tells operators:

```text
Who uses it?

What uses it?

Why does it exist?
```

---

# 74. Token Value Visibility

When a token is generated, treat the displayed token value carefully.

Copy it to the approved secret-management system immediately.

Do not:

```text
Paste into Slack

Email it

Put it in README

Save it in Notes

Commit it to Git
```

---

# 75. Token Expiration

A token can have an expiration date.

Architecture:

```text
Token Created
↓
Valid
↓
Expiration Date
↓
Invalid
```

Expiration reduces the lifetime of forgotten credentials.

---

# 76. Why Expiration Matters

Without expiration:

```text
Forgotten Token
↓
Exists for Years
↓
Nobody Remembers It
↓
Potential Long-Term Risk
```

With managed expiration:

```text
Token
↓
Rotation Process
↓
Replacement
↓
Old Token Invalid
```

---

# 77. Expiration Is Not Enough

Do not think:

```text
Token expires in 90 days
=
Secure
```

A stolen token can still be abused during those 90 days.

Security also requires:

```text
Least Privilege

Secure Storage

Monitoring

Rotation

Revocation
```

---

# 78. Token Rotation

Rotation means replacing a credential.

Safe pattern:

```text
Create New Token
↓
Store New Token
↓
Update CI
↓
Test Pipeline
↓
Confirm New Token Works
↓
Revoke Old Token
```

Avoid:

```text
Revoke Old Token
↓
Production Pipeline Breaks
↓
Everyone Panics
```

Plan rotations.

---

# 79. Token Revocation

Revocation immediately invalidates a token.

Use it when:

```text
Token leaked

Employee leaves

Service retired

Repository retired

Credential replaced

Suspicious activity detected

Token no longer required
```

---

# 80. Compromised Token Response

If a token appears in a public repository:

```text
DO NOT ONLY DELETE THE COMMIT.
```

Treat the credential as compromised.

Correct response:

```text
Detect Exposure
↓
Revoke Token
↓
Generate Replacement
↓
Update Secret Store
↓
Investigate Usage
↓
Remove Secret From Repository History Where Required
↓
Review Root Cause
↓
Prevent Recurrence
```

Revocation comes first.

---

# 81. Why Deleting the File Is Not Enough

Git preserves history.

A token removed from the current file may still exist in:

```text
Previous Commit

Fork

Clone

CI Log

Artifact

Cache

Screenshot
```

Once exposed, assume compromise.

Rotate/revoke it.

---

# 82. Least Privilege

Least privilege means:

```text
Give an identity only the access required
to perform its legitimate task.
```

Example:

```text
CI Pipeline
Needs:
Execute Analysis on Payment Service
```

Therefore give:

```text
Execute Analysis on Payment Service
```

not:

```text
Administer System
```

---

# 83. Least Privilege Is Not Zero Privilege

The goal is not:

```text
Nobody can do anything.
```

The goal is:

```text
Correct identity
+
Correct permission
+
Correct resource
+
Correct duration
```

---

# 84. Least Privilege Questions

For every permission ask:

```text
Why does this identity need this?

What breaks if we remove it?

Can we scope it to one project?

Can we use a group?

Can we make it temporary?

Can we audit it?
```

---

# 85. Secrets Management

A secret is sensitive information that must be protected.

Examples:

```text
SONAR_TOKEN

LDAP Bind Password

Database Password

API Credentials

Private Keys
```

Do not treat secrets as ordinary configuration.

---

# 86. Configuration vs Secret

Configuration:

```text
SONAR_HOST_URL
```

may often be non-secret.

Secret:

```text
SONAR_TOKEN
```

must be protected.

Another example:

```text
Database Host
=
Configuration
```

```text
Database Password
=
Secret
```

---

# 87. Secrets Should Not Live in Source Code

Bad:

```yaml
env:
  SONAR_TOKEN: "sqp_real_secret_here"
```

Bad:

```properties
sonar.token=sqp_real_secret_here
```

Bad:

```bash
TOKEN="sqp_real_secret_here"
```

committed into Git.

# 88. CI/CD Secret Storage

```text
↓

```

```text

↓

```

Other CI systems should use their supported secret-management mechanisms.

# 89. Environment Variables

A CI secret may be exposed to a process through an environment variable:

```text
Secret Store
↓
SONAR_TOKEN
↓
Scanner Process
```

Environment variables are a delivery mechanism.

They are not themselves a complete security strategy.

---

# 90. Do Not Print Environment Variables Blindly

Dangerous debugging:

```bash
env
```

or:

```bash
printenv
```

can expose sensitive environment values.

Do not dump the environment in production CI.

---

# 91. Safe Presence Check

Instead of:

```bash
echo "$SONAR_TOKEN"
```

you can test presence without revealing the value:

```bash
if [ -n "$SONAR_TOKEN" ]; then
  echo "SONAR_TOKEN is set"
else
  echo "SONAR_TOKEN is missing"
  exit 1
fi
```

This checks whether a value exists.

It does not print the token.

---

# 92. CI/CD Credential Separation

Do not use one credential for:

```text

Kubernetes

Container Registry

Terraform

GitHub

Database
```

Instead:

```text

→ SonarQube

Registry Credential
→ Registry

Deployment Identity
→ Deployment

Cloud Identity
→ Cloud
```

Compromise of one credential should not automatically compromise everything.

---

# 93. Separate Projects, Separate Tokens

A strong pattern:

```text
Repository A
↓
Token A
↓
Project A
```

```text
Repository B
↓
Token B
↓
Project B
```

Then:

```text
Token A leaked
```

does not automatically mean:

```text

```

```text
↓
```

Understand:

```text

```

vs:

```text

```

in your environment.

# 118. MFA



# 119. Protecting Administrative Access

```text
Admin Access
=
High Value
```

# 120. Administrative Security Controls

Consider:

```text
Very small administrator population

Central authentication

MFA where supported by IdP

Dedicated admin groups

Least privilege

Secure network exposure

Access reviews

Audit logging

Controlled emergency access

No shared administrator accounts
```

# 121. Never Share Admin Credentials

Bad:

```text

Password:
TeamPassword123
```

used by six engineers.

Why is this bad?

Because:

```text

```

becomes difficult to answer.

Individual identities improve accountability.

```text
↓

↓
Restrict Administrative Access
```

# 123. Administrative Tokens

```text

```

inside:


# 124. Network Protection

# 128. Why Access Reviews Matter

Permissions accumulate.

Example:

```text
Alice joins Payment Team
↓
Gets Payment Permissions

6 months later
↓
Moves to Data Team

Old Payment Permissions
↓
Never Removed
```

This is called access accumulation or privilege creep.

Periodic reviews help detect it.

---

# 129. Privilege Creep

Architecture:

```text
Role 1
↓
Permissions A

Move to Role 2
↓
Permissions B

Old A Not Removed
↓
A + B

Move to Role 3
↓
A + B + C
```

Eventually a normal employee may hold unnecessary access.

---

# 130. Group-Based Access Helps

Instead:

```text

↓

```

then when she moves:

```text

↓

```

This makes lifecycle management easier.

```text
↓
```

# 154. Security Mistake: Overexposed Projects


beyond intended boundaries.

# 155. Security Mistake: Broad Source Access


# 156. Security Mistake: Uncontrolled False Positives

```text
False Positive
```

Restrict issue administration appropriately.

# 157. Security Mistake: Uncontrolled Security Hotspot Review

Do not make:


a button everyone presses merely to turn the dashboard green.

# 159. Security Mistake: Quality Profile Changes Without Governance

# 162. Security Mistake: Forgetting Offboarding Tokens

```text
3. Update CI secret

4. Verify pipeline

8. Identify why secret scanning/prevention failed

9. Improve process
```



You should understand project-key-based template selection.

You should understand that changing a template does not mean you should assume every existing project has automatically changed.

You should understand human identities.

You should understand machine identities.

You should understand why CI/CD should have intentional service identities.

You should understand:



You should understand token generation.

You should understand token expiration.

You should understand token rotation.

You should understand token revocation.

You should understand identity providers.

```text
↓

↓

↓
```
