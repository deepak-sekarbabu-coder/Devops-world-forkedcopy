# 3. Docker Engine

Docker Engine is the core container platform.

On a typical Linux Docker host, it provides the components necessary to create and manage containers.

Conceptually:

```text
Docker CLI
    ↓
Docker API
    ↓
Docker daemon
    ↓
containerd
    ↓
Container runtime
    ↓
Linux Kernel
```

For a Linux server, especially a remote production-style server, you will commonly install Docker Engine directly.

For example:

```text
AWS EC2
   ↓
Ubuntu
   ↓
Docker Engine
   ↓
Application Containers
```

There is usually no need for a desktop graphical application on a headless EC2 server.

---

# 4. Docker Desktop

Docker Desktop is a packaged desktop development environment.

It is commonly used on:

```text
macOS
Windows
Linux desktop environments
```

It combines Docker functionality with desktop-oriented features and management tools.

Depending on platform and current release, it can provide or integrate components such as:

```text
Docker Engine environment
Docker CLI
Docker Compose
Build tooling
Graphical interface
Configuration management
Local container development features
```

For a beginner using a Mac or Windows laptop, Docker Desktop is often the easiest way to establish a local Docker environment.

---

# 5. Docker Desktop vs Docker Engine

Do not think:

> Docker Desktop is Docker for beginners, while Docker Engine is Docker for professionals.

That is inaccurate.

They serve different environments.

A simplified comparison:

| Docker Desktop                                    | Docker Engine                       |
| ------------------------------------------------- | ----------------------------------- |
| Desktop-focused product                           | Core container engine               |
| Common on macOS/Windows                           | Common directly on Linux servers    |
| Includes GUI                                      | Primarily CLI/API driven            |
| Manages local desktop integration                 | Suitable for headless Linux hosts   |
| Can manage Linux VM requirements on macOS/Windows | Uses Linux kernel directly on Linux |
| Convenient local development                      | Common server/container-host setup  |

A DevOps engineer may use both.

For example:

```text
Developer MacBook
      ↓
Docker Desktop
      ↓
Local Development
```

and later:

```text
AWS EC2 Ubuntu Server
        ↓
Docker Engine
        ↓
Production Application
```

Same engineer.

Different environments.

# 19. Why `sudo` Appears During Installation

Installing system packages changes the operating system.

Normal users should not automatically have unrestricted permission to modify system software.

Therefore:

```bash
sudo apt install ...
```

temporarily runs the requested command with elevated privileges, assuming the user is authorized through `sudo`.

This is separate from Docker's own permission model, which we will discuss later.

# 23. What Is a Linux Service?

A service is a program designed to run in the background and provide functionality.

Examples might include:

```text

Database
Docker daemon
```

Docker's daemon needs to remain available so that clients can send it requests.

On systemd-based Linux distributions, service management commonly uses:

```bash

```

# 24. Checking Docker Service Status

Run:

```bash
sudo systemctl status docker
```

Breakdown:

```text
sudo
→ elevated privilege

systemctl
→ control/query systemd services

status
→ show service state

→ target Docker service
```

You are looking for information indicating whether Docker is active.

A healthy system may show something similar to:

```text

```

```text

        ≠

```

If Docker is installed but stopped:

```bash

```

```text

   ↓

   ↓

   ↓

```

# 26. Stopping Docker

Run:

```bash
sudo systemctl stop docker
```

This stops the Docker service.

Be careful.

On a Docker host, stopping Docker can affect running container workloads depending on configuration and runtime behavior.

Do not practice stopping Docker on a production server containing important workloads.

Use your lab environment.

# 27. Restarting Docker

You can restart the service:

```bash
sudo systemctl restart docker
```

This is useful after certain daemon configuration changes.

But again:

> Restarting Docker on a production host is not a harmless troubleshooting button.

Understand the workloads and daemon configuration before restarting services in production.

On systemd-based systems, you may encounter:

```bash

```

This configures the service to start automatically during appropriate system boot targets.

You can check enablement with:

```bash

```

Possible output might be:

```text

```

The distinction matters:


```text

```

```text

```

# 30. The Docker Socket

From Part 1, remember:

```text
Docker CLI
    ↓
Docker API
    ↓
Docker daemon
```

On a local Linux installation, the client commonly communicates with the daemon through a Unix socket:

```text
/var/run/docker.sock
```

You can inspect it:

```bash
ls -l /var/run/docker.sock
```

You may see something conceptually similar to:

```text
srw-rw---- root docker ... /var/run/docker.sock
```

The exact output may vary.

This tells us something important about Docker permissions.

---

# 31. What Is a Unix Socket?

A Unix domain socket allows processes on the same Unix-like system to communicate.

Think:

```text
Docker CLI Process
       ↓
Unix Socket
       ↓
Docker Daemon Process
```

Instead of communicating over an external network connection, local software can communicate through this filesystem-referenced socket.

The socket path is:

```text
/var/run/docker.sock
```

for a common local Docker Engine configuration.

---

# 32. Why Docker Socket Permissions Matter

Suppose the socket is owned by:

```text
root:docker
```

with permissions allowing the owner and Docker group to access it.

Then:

```text
root
→ can communicate with Docker

members of docker group
→ may communicate with Docker
```

A normal user outside the permitted group may receive a permission error.

This is why you may find:

```bash
sudo docker ps
```

works while:

```bash
docker ps
```

fails.

---

# 33. Running Docker With `sudo`

Immediately after installing Docker Engine on Linux, you may need:

```bash
sudo docker ps
```

Why?

Because your normal user may not have permission to access the Docker daemon's Unix socket.

Architecture:

```text
Normal User
    ↓
docker CLI
    ↓
Permission denied
    ↓
Docker socket
```

Using `sudo`:

```text
Normal User
    ↓
sudo
    ↓
Root privilege
    ↓
docker CLI
    ↓
Docker socket
    ↓
Docker daemon
```

---

# 34. The Docker Group

Docker commonly creates or uses a Unix group named:

```text
docker
```

Authorized users can be added to this group so they can run Docker commands without typing `sudo` each time.

A common administrative command is:

```bash
sudo usermod -aG docker $USER
```

Do not blindly memorize it. Understand it.

---

# 35. Understanding `usermod -aG docker $USER`

Breakdown:

```text
sudo
→ run with elevated privileges

usermod
→ modify a user account

-a
→ append

-G
→ supplementary groups

docker
→ group being added

$USER
→ current user's username from the shell environment
```

The `-a` is important.

When modifying supplementary groups, using `-G` incorrectly without append behavior can replace existing supplementary group membership in some usages.

So:

```bash
sudo usermod -aG docker $USER
```

means approximately:

> Add the current user to the Docker supplementary group while preserving existing supplementary group memberships.

---

# 36. Group Membership Does Not Always Update Immediately

After adding a user to a group, the current login session may not automatically gain the new group membership.

Common approaches include:

```text
Log out and log back in
```

or, in suitable lab contexts:

```bash
newgrp docker
```

`newgrp` starts a shell with updated group context.

Then test:

```bash
docker ps
```

If it works without `sudo`, the client can access the daemon with your current permissions.

---

# 37. Important Security Warning About the Docker Group

Do not treat membership in the `docker` group as ordinary low-level access.

Docker daemon access is highly privileged.

A user who can fully control Docker can often perform actions that effectively provide root-level control over the host.

For example, Docker can potentially be instructed to:

```text
Mount host filesystems
Start privileged containers
Access sensitive host resources
Control containers
Manipulate networking
```

Therefore:

> Membership in the Docker group should be treated as privileged access.

Do not add every user to it merely for convenience.

# 44. Testing Docker Properly With `hello-world`

Now we want to test more than whether the CLI exists.

Run:

```bash
docker run hello-world
```

This is an important test because it exercises several Docker components together.

It does not merely print a message locally.

It tests a workflow.

---

# 45. Breaking Down `docker run hello-world`

```text
docker
→ invoke Docker CLI

run
→ create and start a new container

hello-world
→ image reference
```

Remember:

```text
docker run
≈
create new container
+
start container
```

So:

```bash
docker run hello-world
```

means:

> Create and start a container using the `hello-world` image.

If the image is not available locally, Docker will attempt to retrieve it from the configured registry.

---

# 46. What Happens Internally During `docker run hello-world`?

This is where Part 1 becomes practical.

You type:

```bash
docker run hello-world
```

Step 1:

```text
Shell
 ↓
Finds docker executable
```

Step 2:

```text
Docker CLI
 ↓
Parses:
run
hello-world
```

Step 3:

```text
Docker CLI
 ↓
Docker API request
 ↓
Docker daemon
```

Step 4:

The daemon checks whether the required image exists locally.

```text
Local Image Store
       ↓
hello-world exists?
```

If no:

```text
Docker daemon
      ↓
Registry
      ↓
Pull image
```

Step 5:

Image layers/content are downloaded and stored locally.

```text
Registry
   ↓
hello-world image
   ↓
Docker local image store
```

Step 6:

Docker creates a container from that image.

```text
Image
 ↓
Container metadata
 ↓
Writable layer
 ↓
Runtime configuration
```

Step 7:

The runtime prepares the container environment.

Conceptually:

```text
Namespaces
cgroups
Filesystem
Process environment
Networking
```

Step 8:

The container's configured process starts.

```text
Container
   ↓
hello-world process
```

Step 9:

The program prints its message.

Step 10:

The process finishes.

Step 11:

Because the main process exits, the container stops.

The container may still exist in Docker's container metadata until you remove it.

---

# 47. Why `hello-world` Stops

Beginners sometimes run:

```bash
docker run hello-world
```

then:

```bash
docker ps
```

and ask:

> Where did my container go?

Remember:

```text
Container running
       ↓
Main process running
```

For `hello-world`:

```text
Process starts
    ↓
Prints message
    ↓
Process exits
    ↓
Container stops
```

So:

```bash
docker ps
```

may show nothing.

But:

```bash
docker ps -a
```

can show the stopped container.

This reinforces a major rule:

> A container normally remains running while its main process remains running.

---

# 48. Verify the `hello-world` Image

Run:

```bash
docker image ls
```

You should find the `hello-world` image if it remains locally.

Now compare:

```bash
docker ps
```

with:

```bash
docker ps -a
```

You have three different concepts:

```text
Image exists locally
        ↓
Container was created
        ↓
Container process has exited
```

The image can still exist.

The stopped container can still exist.

The process does not have to still be running.

# 50. Docker's Data Directory

Docker needs somewhere to store its local data.

On a typical rootful Docker Engine installation on Linux, the traditional Docker data root is:

```text
/var/lib/docker
```

You may find data associated with:

```text
Images
Container metadata
Writable layers
Volumes
Network-related state
Build data
```

However, modern Docker installations can also use storage arrangements where some image/container snapshot content is managed through containerd storage outside the traditional `/var/lib/docker` layout.

The important professional rule is:

> Do not assume the path. Verify the active Docker configuration.

Run:

```bash
docker info
```

Look for information such as:

```text
Docker Root Dir
```

For many Linux installations, that will be:

```text
/var/lib/docker
```

# 51. Do Not Manually Edit `/var/lib/docker`

This deserves a warning.

Do not think:

> I need to delete an image, so I'll just enter `/var/lib/docker` and delete some files.

Do not manually manipulate Docker's internal data directory unless you deeply understand the consequences and are following a supported recovery procedure.

Docker maintains relationships between:

```text
Images
Layers
Containers
Volumes
Metadata
Snapshots
```

Random deletion can corrupt Docker state or destroy data.

Use Docker commands:

```bash
docker image rm
docker container rm
docker volume rm
```

and appropriate pruning commands when you understand them.

# 52. Docker Configuration Locations

Docker configuration can exist in several places depending on what is being configured.

Two categories matter:

```text
Docker daemon configuration
Docker client configuration
```

Do not confuse them.

---

# 53. Docker Daemon Configuration

On Linux, a common daemon configuration file is:

```text
/etc/docker/daemon.json
```

This file configures Docker daemon behavior.

Example structure:

```json
{
  "log-driver": "local"
}
```

That is only an example.

The exact settings you use depend on your requirements.

Possible daemon-level concerns include:

```text
Logging
Storage
Registry settings
Networking
Runtime configuration
Data-root
DNS
Security-related settings
```

---

# 54. Why JSON Syntax Matters

`daemon.json` uses JSON.

JSON is strict.

For example:

```json
{
  "log-driver": "local"
}
```

is valid.

A malformed configuration can prevent Docker from starting.

For example, careless syntax such as a trailing comma may be invalid JSON:

```json
{
  "log-driver": "local",
}
```

Before restarting a production Docker daemon after configuration changes, validate the configuration and understand the impact.

---

# 55. Applying Daemon Configuration

After changing daemon-level configuration, a Docker daemon restart may be required for the setting to take effect.

On a systemd-based Linux lab:

```bash
sudo systemctl restart docker
```

But remember:

```text
Edit daemon configuration
        ↓
Restart Docker
        ↓
Potential workload impact
```

Do not experiment with daemon restarts on production systems.

---

# 56. Docker Client Configuration

The Docker CLI also has user-specific configuration.

A common location is:

```text
~/.docker/
```

and a common client configuration file is:

```text
~/.docker/config.json
```

Here:

```text
~
```

means the current user's home directory.

For example:

```text
/home/anne/.docker/config.json
```

or on another system:

```text
/Users/anne/.docker/config.json
```

depending on the operating system.

The client configuration may contain CLI-related settings and credential-helper configuration.

Be careful with Docker credentials and configuration files.

---

# 57. Daemon Config vs Client Config

Remember:

```text
/etc/docker/daemon.json
        ↓
Docker daemon configuration
```

versus:

```text
~/.docker/config.json
        ↓
Docker client/user configuration
```

A troubleshooting question should therefore be:

> Is this setting controlling the server-side Docker daemon or my user-side Docker client?

That distinction saves time.

# 58. Changing Docker's Data Root

Docker can be configured to use another data directory.

Conceptually:

```json
{
  "data-root": "/docker-data"
}
```

This tells the daemon to use another location for Docker's data root.

This is **not** something a beginner should change casually on an existing Docker host.

Changing storage locations can involve:

```text

Existing containers
Volumes
Permissions
Disk mounts
Filesystem compatibility
Migration planning
Downtime
```

For now, know that the location is configurable.

Do not move production Docker data simply because another disk has more space without planning the migration properly.

# 60. macOS Considerations

macOS does not use the Linux kernel.

But Linux containers rely on Linux kernel features.

Therefore Linux containers cannot simply use the macOS kernel as though it were Linux.

Docker Desktop solves this by providing a Linux environment using virtualization.

Conceptually:

```text
Mac Hardware
     ↓
macOS
     ↓
Docker Desktop
     ↓
Linux Virtual Machine
     ↓
Linux Kernel
     ↓
Docker Environment
     ↓
Linux Containers
```

This is largely managed for you.

You type:

```bash
docker ps
```

from your Mac terminal.

But the Linux container environment exists underneath Docker Desktop.


# 62. macOS File Sharing and Performance

Because Linux containers may run inside a virtualized Linux environment, mounting macOS directories into containers crosses an environment boundary.

Conceptually:

```text

    ↓

    ↓

    ↓
```

# 64. What Is WSL 2?

WSL 2 provides a Linux environment integrated with Windows and uses a real Linux kernel in a lightweight virtualized architecture.

This matters because our Linux containers need Linux kernel functionality.

So:

```text

   ↓

   ↓
Linux Kernel
   ↓
Docker
   ↓
Linux Containers
```

Docker Desktop handles much of the integration.

and thinks:

```bash
sudo systemctl restart docker
```

A production engineer first asks:

```text
What is failing?
Which containers are running?
Will restart affect them?
What changed?
What do the logs show?
Can I fix without disruption?
```

The correct troubleshooting philosophy is:

```text
Evidence before disruption
```

Restarting something can hide the symptom without explaining the root cause.

# 105. What You Should Now Understand

Before moving to Part 3, you should understand:

* Docker Desktop and Docker Engine are related but different products/components.
* Docker Engine is commonly installed directly on Linux servers.
* Docker Desktop is commonly used for desktop development on macOS and Windows.
* Linux containers depend on Linux kernel functionality.
* Docker Desktop can provide the Linux environment needed on macOS and Windows.
* Windows Docker environments can involve WSL 2 for Linux containers.
* Linux containers and Windows containers use different kernel families.
* Ubuntu uses package repositories and APT for package management.
* Docker maintains official package repositories for supported Linux distributions.
* `docker-ce` provides Docker Engine components.
* `docker-ce-cli` provides the Docker CLI.
* `containerd.io` provides container runtime functionality used underneath Docker.
* Docker runs as a service on common Linux server installations.
* `systemctl status docker` checks service status.
* `systemctl start docker` starts Docker.
* `systemctl stop docker` stops Docker.
* `systemctl restart docker` restarts Docker.
* `systemctl enable docker` configures service startup behavior.
* `/var/run/docker.sock` is commonly used for local client-daemon communication.
* Docker socket access is highly privileged.
* Linux users may need `sudo` to access Docker.
* The Docker group can provide non-sudo Docker access.
* Docker group membership should be treated as privileged access.
* `docker --version` verifies the CLI/version at a basic level.
* `docker version` shows detailed client/server version information.
* `docker info` provides broader environment information.
* `docker run hello-world` tests a complete image-to-container workflow.
* `hello-world` stops because its main process completes.
* Docker maintains local images and container metadata.
* `/var/lib/docker` is a common traditional Docker data root on rootful Linux installations, but you should verify the actual environment.
* `/etc/docker/daemon.json` is a common Linux daemon configuration file.
* `~/.docker/config.json` is commonly associated with user/client configuration.
* Daemon configuration and client configuration are different.
* Docker's internal data directories should not be edited casually.
* Docker CLI help is available directly from the terminal.
* Official documentation should be used for current installation procedures.
* Docker troubleshooting should proceed layer by layer.
