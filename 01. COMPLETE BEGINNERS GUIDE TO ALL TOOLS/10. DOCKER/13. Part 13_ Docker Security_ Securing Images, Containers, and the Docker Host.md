# Part 13: Docker Security: Securing Images, Containers, and the Docker Host

## Treat Security as Part of Container Engineering

Up to this point, you have learned how to:

* build Docker images;
* run containers;
* connect multiple containers;
* manage complete stacks with Docker Compose;
* engineer smaller production images;
* use multi-stage builds;
* push images to registries;
* pull images onto servers;
* identify images with tags and digests.

Now we need to ask a different question:

```text
What happens if something goes wrong?
```

Not just:

```text
What happens if the application crashes?
```

but:

```text
What happens if the application is compromised?

What can the attacker access?

Can the container modify the host?

Can it read secrets?

Can it reach other services?

Can it consume all CPU or memory?

Can it control Docker itself?

Can it access sensitive host directories?

Can it exploit a vulnerable package?

Can it use unnecessary Linux privileges?

Can a malicious dependency enter during the build?
```

This is container security.

The security path for this part is:

```text
Source
  ↓
Dependencies
  ↓
Image
  ↓
Registry
  ↓
Container
  ↓
Host
```

Security must exist across the entire path.

A secure Dockerfile does not compensate for a compromised registry.

A secure registry does not compensate for a container running with excessive privileges.

A non-root container does not compensate for mounting the Docker socket into it.

A vulnerability scanner does not compensate for exposing unnecessary services directly to the internet.

Container security is therefore not one setting.

It is a collection of controls.

# 2. Security Is a System

Beginners sometimes think Docker security means:

```text
Use a small image.
```

That helps.

But it is only one part.

Consider:

```text
Source Code
     ↓
Dependencies
     ↓
Dockerfile
     ↓
Build System
     ↓
Container Image
     ↓
Registry
     ↓
Docker Host
     ↓
Container Runtime
     ↓
Application
     ↓
Network
     ↓
Data
```

Every layer creates possible risk.

For example:

| Layer         | Example Risk                   |
| ------------- | ------------------------------ |
| Source        | malicious or insecure code     |
| Dependency    | vulnerable package             |
| Build         | leaked build secret            |
| Image         | unnecessary tools/packages     |
| Registry      | unauthorized image replacement |
| Deployment    | wrong image/tag                |
| Container     | excessive privileges           |
| Mount         | sensitive host files exposed   |
| Network       | unnecessary public port        |
| Host          | outdated kernel/runtime        |
| Docker daemon | unauthorized control           |
| Secrets       | credential exposure            |

Container security must consider all of them.

# 3. Threat Modeling From the Beginning

Before securing a container, ask:

```text
What are we protecting?

From whom?

What can this workload access?

What would happen if the application were compromised?
```

Imagine:

```text
Internet
   ↓
Frontend
   ↓
Backend API
   ↓
Database
```

Suppose the backend is compromised.

Ask:

```text
Can it access the host filesystem?

Can it access Docker?

Can it reach unrelated containers?

Can it read database credentials?

Can it modify its own executable files?

Can it create unlimited processes?

Can it consume all host memory?

Can it perform privileged kernel operations?
```

Those questions lead directly to security controls.

---

# 4. The Container Security Model

Docker containers are isolated processes running on a host operating system.

A simplified model:

```text
+----------------------------------+
| Docker Host                      |
|                                  |
| Linux Kernel                     |
|                                  |
| +-----------+  +-----------+     |
| |Container A|  |Container B|     |
| |Processes  |  |Processes  |     |
| +-----------+  +-----------+     |
|                                  |
+----------------------------------+
```

Containers share the host kernel.

That is one of the most important facts in container security.

---

# 5. Containers Are Not Separate Physical Machines

A virtual machine commonly has:

```text
VM
├── Guest kernel
├── Operating system
└── Applications
```

A Linux container normally has:

```text
Container
├── isolated process environment
├── filesystem view
├── network namespace
└── application
```

while relying on the host's Linux kernel.

Conceptually:

```text
Container A ──┐
Container B ──┼──> Host Linux Kernel
Container C ──┘
```

Therefore the kernel is part of the security boundary.

---

# 6. Container Isolation

Docker uses Linux kernel mechanisms to provide isolation.

Important concepts include:

```text
Namespaces
Capabilities
Control groups
Seccomp
Linux security modules
Filesystem isolation
Network isolation
```

These mechanisms work together.

There is no single magical:

```text
Docker isolation switch
```

---

# 7. Linux Namespaces

Namespaces provide isolated views of system resources.

Conceptually:

```text
Container A
sees:
Processes A
Network A
Mounts A

Container B
sees:
Processes B
Network B
Mounts B
```

rather than every container automatically seeing everything on the host.

---

# 8. Important Namespace Concepts

Linux provides namespaces for areas including:

```text
PID
Network
Mount
IPC
UTS
User
Cgroup
```

You do not need to become a Linux kernel engineer before using Docker securely.

But you should understand why they matter.

---

# 9. PID Namespace

The PID namespace isolates process IDs.

Inside a container:

```bash
ps
```

normally shows the container's process view rather than every process on the host.

This helps isolate workloads.

---

# 10. Network Namespace

A container normally receives its own network namespace.

It can have:

```text
interfaces
routes
IP addresses
ports
```

separate from the host network namespace.

Docker networking then connects containers where required.

---

# 11. Mount Namespace

The mount namespace gives a container its own filesystem/mount view.

A container may see:

```text
/
├── app
├── usr
├── etc
└── tmp
```

without automatically seeing the host's entire:

```text
/
```

But mounts can deliberately expose host paths.

That becomes extremely important later.

---

# 12. User Namespace

User namespaces can map user identities inside one namespace to different identities outside it.

This can reduce the impact of container-root privileges.

Docker supports user-namespace mechanisms, and Docker Rootless mode makes extensive use of user namespaces.

---

# 13. Control Groups

Control groups, usually called:

```text
cgroups
```

help control and account for resource usage.

Examples include:

```text
CPU
memory
processes
```

Security is not only about unauthorized file access.

Availability matters too.

A container that consumes all host memory can affect other workloads.

---

# 14. Isolation Has Limits

Containers provide isolation.

But containers are not an absolute security boundary.

They:

```text
share the host kernel
```

and can be configured in dangerous ways.

Security can be weakened by:

```text
privileged mode
dangerous capabilities
sensitive host mounts
Docker socket access
host networking
unsafe device access
weak kernel security
runtime vulnerabilities
poor secret handling
```

Therefore:

```text
Containerized
```

does not mean:

```text
Automatically secure.
```

---

# 15. Defense in Depth

Container security should use multiple controls.

Example:

```text
Non-root user
     +
Dropped capabilities
     +
Seccomp
     +
AppArmor/SELinux
     +
Read-only filesystem
     +
Resource limits
     +
Minimal network exposure
     +
Safe mounts
     +
Secure secrets
     +
Patched image
     +
Hardened host
```

If one control fails, others still reduce risk.

This is defense in depth.

---

# 16. The Docker Daemon

Docker Engine commonly includes a daemon:

```text
dockerd
```

that manages:

```text
containers
images
networks
volumes
builds
runtime operations
```

The Docker CLI communicates with this daemon.

Conceptually:

```text
docker CLI
    ↓
Docker API
    ↓
Docker daemon
    ↓
container runtime
    ↓
containers
```

---

# 17. Why the Docker Daemon Is Security-Critical

Traditional Docker Engine deployments commonly run the daemon with root privileges.

The daemon can perform powerful operations such as:

```text
create containers
mount host directories
create networks
access devices
configure container privileges
```

Therefore access to the daemon must be tightly controlled.

---

# 18. Docker Daemon Access Is Highly Privileged

Suppose someone can instruct Docker to create:

```text
Host /
   ↓
mounted into container
```

That person may be able to interact with highly sensitive host files.

This is why Docker documentation warns that only trusted users should control the Docker daemon.

Treat daemon access as administrative-level access.

---

# 19. The Docker Socket

On many Linux Docker installations, the Docker daemon listens locally through:

```text
/var/run/docker.sock
```

You may see it with:

```bash
ls -l /var/run/docker.sock
```

Representative output might resemble:

```text
srw-rw---- 1 root docker ... /var/run/docker.sock
```

Exact ownership and permissions depend on the environment.

---

# 20. What Is a Unix Socket?

A Unix socket provides local inter-process communication.

Conceptually:

```text
Docker CLI
    ↓
/var/run/docker.sock
    ↓
Docker daemon
```

When you run:

```bash
docker ps
```

the CLI can communicate with the Docker daemon through the socket.

---

# 21. Why the Docker Socket Is Dangerous

If a container receives:

```text
/var/run/docker.sock
```

it may be able to control Docker according to the daemon/API permissions available through that socket.

For example, a process capable of controlling the daemon may potentially ask Docker to:

```text
start containers
mount host directories
create privileged containers
inspect other containers
access container configuration
```

That can effectively become host-level control.

---

# 22. Dangerous Docker Socket Mount

You may encounter:

```bash
docker run \
  -v /var/run/docker.sock:/var/run/docker.sock \
  some-image
```

Do not treat this as an ordinary mount.

You are potentially giving the container powerful control over the Docker daemon.

---

# 23. Common Docker Socket Scenario

Some tools request Docker socket access because they need to:

```text
discover containers
start containers
inspect workloads
build images
manage Docker
```

Before granting it, ask:

```text
Does this tool truly need daemon control?

Can it use a safer API/proxy?

Can access be restricted?

Is the image trusted?

What happens if the tool is compromised?
```

---

# 24. Docker Group Security

On Linux, Docker documentation warns that membership in the:

```text
docker
```

group grants root-level privileges in typical rootful Docker configurations.

Therefore:

```bash
sudo usermod -aG docker USER
```

should not be treated as a harmless convenience command.

Only trusted users should receive Docker daemon access.

---

# 25. Rootful Docker

Traditional Docker Engine deployments commonly use a rootful daemon.

Conceptually:

```text
User
  ↓
Docker CLI
  ↓
Rootful Docker Daemon
  ↓
Host Operations
```

This architecture works well but makes daemon security critical.

---

# 26. Docker Rootless Mode

Docker also provides:

```text
Rootless mode
```

In Rootless mode:

```text
Docker daemon
+
containers
```

run without root privileges for the Docker user.

Conceptually:

```text
Non-root user
      ↓
Rootless Docker daemon
      ↓
Containers
```

This reduces risks associated with daemon/runtime vulnerabilities.

---

# 27. Rootless Is Not Magic

Rootless Docker improves security but does not mean:

```text
Nothing can go wrong.
```

You still need:

```text
secure images
safe secrets
network controls
resource controls
patched software
secure application code
proper permissions
```

Rootless mode is one security layer.

---

# 28. Root Inside a Container

A process can run as:

```text
UID 0
```

inside a container.

This is commonly called:

```text
container root
```

Container root is constrained by namespaces, capabilities, seccomp, and other controls compared with unrestricted host root.

But it is still more privilege than most applications require.

---

# 29. Check the Container User

Run:

```bash
docker run \
  --rm \
  alpine \
  id
```

Depending on the image, you may see:

```text
uid=0(root) gid=0(root) groups=0(root)
```

That container process is running as root inside the container.

---

# 30. Why Container Root Matters

Suppose an application vulnerability allows command execution.

If the process runs as root inside the container, the attacker begins with more privilege inside that environment.

That can increase the impact of:

```text
misconfigured mounts
runtime vulnerabilities
excessive capabilities
writable files
device exposure
```

Therefore applications should generally avoid root when they do not need it.

---

# 31. Non-Root Containers

A stronger production Dockerfile often creates a dedicated user.

Example:

```dockerfile
FROM python:3.13-slim

WORKDIR /app

RUN groupadd --system appgroup \
    && useradd \
       --system \
       --gid appgroup \
       --create-home \
       appuser

COPY --chown=appuser:appgroup . /app

USER appuser

CMD ["python", "app.py"]
```

Now the application does not intentionally run as root.

---

# 32. Verify Non-Root Execution

Build:

```bash
docker build \
  -t veriqta-security-lab:1.0 \
  .
```

Run:

```bash
docker run \
  --rm \
  veriqta-security-lab:1.0 \
  id
```

Expected conceptually:

```text
uid=... (appuser)
gid=... (appgroup)
```

not:

```text
uid=0(root)
```

---

# 33. Runtime User Override

Docker can also select a runtime user.

Example:

```bash
docker run \
  --rm \
  --user 10001:10001 \
  IMAGE \
  id
```

This can add runtime control.

But arbitrary UID changes can break applications if files are not owned or permissioned correctly.

Test the image properly.

---

# 34. File Ownership Matters

Imagine:

```text
/app
owned by root
```

but your application runs as:

```text
appuser
```

If the application needs to write there, you may receive:

```text
Permission denied
```

Do not respond by running the entire application as root.

Fix ownership or design a dedicated writable location.

---

# 35. `COPY --chown`

You learned this in Part 11.

Example:

```dockerfile
COPY --chown=appuser:appgroup . /app
```

This gives copied files appropriate ownership during the image build.

Security and correct filesystem design often work together.

---

# 36. Least Privilege

Least privilege means:

```text
Give a process only what it needs.
```

Not:

```text
Give everything and hope it behaves.
```

For a web API, ask:

```text
Does it need root?

Does it need host filesystem access?

Does it need Docker access?

Does it need kernel administration?

Does it need every Linux capability?

Does it need outbound access everywhere?

Does it need a writable root filesystem?
```

Usually the answer to many of these is:

```text
No.
```

---

# 37. Linux Capabilities

Historically, Unix privilege often looked like:

```text
root
or
not root
```

Linux capabilities divide privileged operations into smaller units.

Conceptually:

```text
Root Privilege
      ↓
+----------------------+
| CAP_CHOWN            |
| CAP_NET_BIND_SERVICE |
| CAP_SETUID           |
| CAP_SETGID           |
| CAP_KILL             |
| ...                  |
+----------------------+
```

This allows more granular privilege control.

---

# 38. Docker and Capabilities

Docker containers receive a restricted capability set by default rather than every Linux capability.

You can inspect capabilities from inside a suitable Linux container with tools such as:

```bash
capsh --print
```

when the image includes `capsh`.

Do not install unnecessary tools into a production image only for diagnostics.

Use a disposable diagnostic environment where appropriate.

---

# 39. Dropping Capabilities

Docker supports:

```text
--cap-drop
```

Example:

```bash
docker run \
  --rm \
  --cap-drop ALL \
  IMAGE
```

This removes all capabilities initially granted to the container.

---

# 40. Add Back Only What Is Required

If the application genuinely requires one capability:

```bash
docker run \
  --rm \
  --cap-drop ALL \
  --cap-add NET_BIND_SERVICE \
  IMAGE
```

Conceptually:

```text
Start with nothing
      ↓
Add required privilege
```

rather than:

```text
Start with everything
      ↓
Hope nothing is abused
```

---

# 41. Capability Names

Docker commonly accepts capability names such as:

```text
NET_BIND_SERVICE
CHOWN
SETUID
SETGID
```

Do not add capabilities simply because an error disappeared when you added them.

Understand what the application requires.

---

# 42. Capability Troubleshooting

Suppose:

```bash
docker run \
  --cap-drop ALL \
  IMAGE
```

breaks the application.

Do not immediately use:

```text
--privileged
```

Instead:

```text
Observe failure
↓
Read logs
↓
Identify denied operation
↓
Determine required privilege
↓
Add minimum required capability
↓
Retest
```

That is security engineering.

---

# 43. Privileged Containers

Docker provides:

```text
--privileged
```

Example:

```bash
docker run \
  --privileged \
  IMAGE
```

This grants the container substantially elevated access and relaxes several normal isolation restrictions.

Treat this option as extremely powerful.

---

# 44. Why `--privileged` Is Dangerous

A privileged container can receive broad capabilities and access that ordinary containers do not have.

The security boundary between:

```text
container
```

and:

```text
host
```

becomes dramatically weaker.

If the application is compromised, the consequences can be much more serious.

---

# 45. Do Not Use `--privileged` as a Troubleshooting Shortcut

Bad pattern:

```text
Application failed
     ↓
docker run --privileged
     ↓
Application works
     ↓
Ship to production
```

You learned nothing about the actual requirement.

Instead:

```text
Application failed
     ↓
Inspect error
     ↓
Identify required permission
     ↓
Grant smallest permission
     ↓
Verify
```

---

# 46. Read-Only Root Filesystems

Many applications do not need to modify most of their container filesystem.

Docker supports:

```text
--read-only
```

Example:

```bash
docker run \
  --read-only \
  IMAGE
```

The container root filesystem becomes read-only.

---

# 47. Why Read-Only Helps

Suppose an attacker compromises the application.

A read-only filesystem can make certain actions more difficult, such as:

```text
modifying application binaries
replacing configuration
dropping files throughout the root filesystem
persisting changes in normal image paths
```

It is not complete protection.

But it reduces writable attack surface.

---

# 48. Applications Still Need Temporary Storage

Some applications legitimately need:

```text
/tmp
```

or another writable runtime location.

You can combine a read-only root filesystem with a temporary filesystem.

Example:

```bash
docker run \
  --read-only \
  --tmpfs /tmp \
  IMAGE
```

Now:

```text
root filesystem = read-only
/tmp = temporary writable memory-backed filesystem
```

subject to the platform's tmpfs behavior and configuration.

---

# 49. Test Read-Only Compatibility

Do not enable:

```text
--read-only
```

and assume success.

Run the application.

Check:

```bash
docker logs CONTAINER
```

Test:

```text
startup
requests
uploads if relevant
temporary files
caches
PID files
logs
shutdown
```

Then explicitly provide only the writable locations the application genuinely needs.

---

# 50. Resource Exhaustion Is a Security Problem

Imagine one container consumes:

```text
100% CPU
all available memory
thousands of processes
```

Other applications on the host may fail.

Therefore availability controls are security controls too.

---

# 51. Memory Limits

Docker supports memory constraints.

Example:

```bash
docker run \
  --memory 256m \
  IMAGE
```

This limits the container's memory according to Docker/kernel resource-control behavior.

---

# 52. CPU Limits

Example:

```bash
docker run \
  --cpus 1.0 \
  IMAGE
```

This constrains the container to approximately one CPU worth of execution capacity.

---

# 53. PID Limits

Docker can limit process creation.

Example:

```bash
docker run \
  --pids-limit 100 \
  IMAGE
```

This can help reduce the impact of runaway process creation or fork-bomb-like behavior.

---

# 54. Combined Resource Controls

Example:

```bash
docker run \
  --memory 256m \
  --cpus 1.0 \
  --pids-limit 100 \
  IMAGE
```

Do not copy arbitrary values into production.

Measure your application.

Set limits based on expected workload and operational testing.

---

# 55. Resource Limit Failure Lab

Run a memory-intensive test container with a deliberately low memory limit in a safe lab.

Observe:

```bash
docker ps -a
```

Then:

```bash
docker inspect CONTAINER
```

Look at its exit information.

The goal is to understand that:

```text
resource constraint
```

can create application failure that resembles other runtime problems.

---

# 56. Secrets

A secret is sensitive information such as:

```text
database password
API token
private key
registry credential
cloud credential
TLS private key
```

Secrets require special handling.

---

# 57. Secrets Do Not Belong in Images

Bad:

```dockerfile
ENV DATABASE_PASSWORD=supersecret
```

Bad:

```dockerfile
COPY production-key.pem /app/key.pem
```

Bad:

```dockerfile
RUN echo "secret" > /app/password.txt
```

Image layers can preserve sensitive information.

If a secret enters an image layer, deleting it in a later layer does not necessarily remove it from earlier image history/content.

---

# 58. Build Secrets

Recall Part 11.

BuildKit supports secret mounts for build-time secrets.

Conceptual Dockerfile:

```dockerfile
RUN --mount=type=secret,id=mysecret \
    some-build-command
```

Build command:

```bash
docker build \
  --secret id=mysecret,src=./secret.txt \
  .
```

This is designed to avoid baking the secret into ordinary image layers.

---

# 59. Build Arguments Are Not Secret Storage

Do not treat:

```dockerfile
ARG PASSWORD
```

as a secret-management system.

Build arguments are appropriate for non-sensitive build configuration.

Sensitive build credentials should use proper secret mechanisms.

---

# 60. Environment Variables

Environment variables are widely used for application configuration.

Example:

```bash
docker run \
  -e DB_HOST=database \
  -e DB_NAME=production \
  IMAGE
```

This is useful.

But sensitive environment variables require caution.

---

# 61. Environment-Variable Secret Risks

Secrets in environment variables can potentially appear through:

```text
container inspection
debugging output
application error messages
process environments
support bundles
misconfigured logs
CI/CD logs
shell history
```

depending on the system and how values are supplied.

Therefore:

```text
environment variable
```

does not automatically mean:

```text
secure secret storage.
```

---

# 62. Safer Secret Design

Production environments may use:

```text
secret managers
orchestrator secret mechanisms
mounted secret files
short-lived credentials
workload identity
cloud identity
```

depending on the platform.

The best option depends on architecture.

---

# 63. Never Log Secrets

Bad:

```python
print(os.environ)
```

Bad:

```text
Connecting with password supersecret123
```

Better:

```text
Connecting to database host=db.internal
```

Log operational context without credential values.

---

# 64. Sensitive Mounts

Docker can mount host paths into containers.

Example:

```bash
docker run \
  --mount type=bind,source=/host/path,target=/container/path \
  IMAGE
```

This is powerful.

It can also be dangerous.

---

# 65. Host Filesystem Exposure

Imagine:

```text
Host
/
├── etc
├── home
├── var
└── root
```

Then:

```bash
docker run \
  -v /:/host \
  IMAGE
```

You have exposed the host root filesystem to the container.

This destroys much of the filesystem isolation you expected.

Do not use this casually.

---

# 66. Dangerous Mount Examples

Sensitive host locations may include:

```text
/
 /etc
 /root
 /home
 /var/lib/docker
 /var/run/docker.sock
 SSH directories
 cloud credential directories
 application secret directories
```

Mount only what the workload actually needs.

---

# 67. Read-Only Bind Mounts

If a container only needs to read data, use a read-only mount where appropriate.

Example:

```bash
docker run \
  --mount \
  type=bind,source=/host/config,target=/app/config,readonly \
  IMAGE
```

Now the container should not need write access to that mount.

---

# 68. Verify Mounts

Inspect:

```bash
docker inspect CONTAINER
```

Look for:

```text
Mounts
```

Ask:

```text
Why is each mount here?

Does it need write access?

Does it expose sensitive host data?

Could a named volume work instead?

Could the application avoid this mount entirely?
```

---

# 69. Network Exposure

A secure container can still expose an insecure application.

Consider:

```bash
docker run \
  -p 5432:5432 \
  postgres
```

Depending on host firewall/routing and Docker configuration, this may expose the database much more broadly than intended.

Do not publish ports automatically.

---

# 70. Publish Only Required Ports

Recall the multi-container architecture:

```text
Internet
   ↓
Frontend
   ↓
Backend
   ↓
Database
```

Normally:

```text
Frontend
→ externally reachable

Backend
→ internal where architecture permits

Database
→ internal
```

Do not publish every container port to the host.

---

# 71. Bind Published Ports Deliberately

For local-only access:

```bash
docker run \
  -p 127.0.0.1:8080:8080 \
  IMAGE
```

This binds the published port to the host loopback address.

Compare with a broader host bind.

Understand the intended audience for every published port.

---

# 72. `EXPOSE` Is Not Publication

Recall:

```dockerfile
EXPOSE 8080
```

does not automatically publish the port to the host.

Runtime publication happens through options such as:

```text
-p
--publish
```

Do not confuse image documentation with network exposure.

---

# 73. Inspect Published Ports

Run:

```bash
docker ps
```

and:

```bash
docker port CONTAINER
```

Verify what is actually published.

Do not assume.

---

# 74. Network Segmentation

Instead of:

```text

    ↓
One giant network
```

consider:

```text

Frontend
   ↓
Backend


Backend Network

Backend
   ↓

```

Now the frontend does not need direct database access.

This reduces unnecessary reachability.

# 80. Pinning and Updates

Pinning can improve reproducibility.

For example:


```text

```

Reproducibility without patch management becomes stagnation.

# 81. Rebuild Images Regularly

Even if your application code did not change, the security environment did.

Production teams need a rebuild/update strategy.

# 115. Seccomp

Seccomp means:

```text
secure computing mode
```

It is a Linux kernel security mechanism that can restrict system calls available to processes.

System calls are how applications request operations from the kernel.

---

# 116. System Call Mental Model

Application:

```text
I need to open a file.
I need to create a process.
I need to create a socket.
```

Those operations eventually interact with the kernel through system calls.

Seccomp can restrict which calls are allowed.

Conceptually:

```text
Application
    ↓
System Call
    ↓
Seccomp Policy
   / \
Allow Deny
```

---

# 117. Docker Default Seccomp

On supported Linux environments, Docker normally applies its default seccomp profile unless you override it.

The default profile blocks a number of potentially dangerous or unnecessary system calls while maintaining broad application compatibility.

Do not disable it casually.

---

# 118. Custom Seccomp Profile

Docker supports custom seccomp profiles.

Example:

```bash
docker run \
  --security-opt \
  seccomp=/path/to/profile.json \
  IMAGE
```

Custom profiles are an advanced control.

Test them thoroughly.

---

# 119. Dangerous Seccomp Shortcut

You may encounter:

```bash
docker run \
  --security-opt seccomp=unconfined \
  IMAGE
```

This disables the normal seccomp confinement for that container.

Do not use this as a generic:

```text
make the error disappear
```

solution.

Determine why the application needs a blocked syscall.

---

# 120. AppArmor

AppArmor is a Linux Security Module.

It can restrict what programs may access and perform according to profiles.

On supported Docker environments, Docker can use AppArmor confinement.

Docker commonly applies a default profile named:

```text
docker-default
```

to containers when AppArmor is available and configured appropriately.

---

# 121. Check AppArmor

On an AppArmor-enabled Linux host, tools such as:

```bash
aa-status
```

can show AppArmor status if the relevant package/tools are installed.

Your Linux distribution determines availability and configuration.

---

# 122. AppArmor Mental Model

```text
Container Process
      ↓
AppArmor Profile
      ↓
Allowed Operations
      ↓
Kernel
```

AppArmor adds another security layer beyond basic container namespaces.

---

# 123. SELinux

SELinux is another Linux Security Module used by many Linux distributions.

It applies mandatory access-control policy and security labels.

Docker can integrate with SELinux on appropriately configured systems.

---

# 124. SELinux Context Matters

On SELinux-enabled hosts, bind mounts and container access can be affected by security labels.

A mount may have correct Unix file permissions and still be denied by SELinux policy.

Therefore:

```text
Permission denied
```

does not always mean:

```text
chmod problem.
```

---

# 125. Do Not Disable SELinux to Fix Everything

Bad:

```text
Container cannot access file
↓
disable SELinux
```

Better:

```text
Check Unix permissions
↓
Check ownership
↓
Check SELinux context/policy
↓
Correct configuration
↓
Retest
```

Security controls should not be globally removed merely to avoid troubleshooting.

---

# 126. AppArmor vs SELinux

Both provide additional mandatory access-control mechanisms.

They differ significantly in design and administration.

Which one you encounter depends largely on your Linux distribution and environment.

For this beginner foundation, remember:

```text
Namespaces
Capabilities
Seccomp
AppArmor/SELinux
```

can work together as layers of container confinement.

# 146. Security Failure Lab 5: Sensitive Mount

Create a harmless disposable host directory:

```bash
mkdir -p /tmp/veriqta-sensitive-lab
```

Create:

```bash
echo "lab-secret" \
  > /tmp/veriqta-sensitive-lab/example.txt
```

Mount it into a disposable container:

```bash
docker run \
  --rm \
  -v /tmp/veriqta-sensitive-lab:/data \
  alpine \
  cat /data/example.txt
```

Observe how easily host data becomes visible.

Lesson:

```text

```

Delete the lab directory afterward.

# 168. Incident Thinking

Suppose the web application is compromised.

A poorly hardened container may have:

```text
root
+
privileged
+
Docker socket
+
host root mount
+
no resource limits
+
broad network access
```

The attacker may have a very large blast radius.

Compare:

```text
non-root
+
no Docker socket
+
no sensitive host mounts
+
capabilities dropped
+
read-only root
+
resource limits
+
segmented network
+
seccomp
+
AppArmor/SELinux
```

The application is still compromised.

But the attacker's available actions may be dramatically reduced.

That is the purpose of runtime hardening.

# 169. Security Does Not Mean Prevent Every Compromise

A mature security mindset assumes:

```text
Some controls will eventually fail.
```

Therefore ask:

```text
How do we prevent?

How do we detect?

How do we contain?

How do we recover?
```

Container security contributes especially to:

```text
prevention
+
containment
```

while logs, monitoring, backups, and incident response contribute to detection and recovery.

4. Using `--privileged` to solve permission problems.
5. Adding every capability.
6. Disabling seccomp because something failed.
7. Disabling SELinux because a mount failed.
8. Mounting `/` into containers.
9. Mounting Docker socket unnecessarily.
10. Giving untrusted users Docker daemon access.
11. Giving every user Docker-group membership.
12. Publishing every service port.
13. Publishing databases unnecessarily.
14. Storing passwords in Dockerfiles.
15. Baking private keys into images.
16. Treating build arguments as secret storage.
17. Dumping environment variables into logs.
18. Ignoring resource limits.
19. Using ancient base images.
20. Assuming small images are automatically secure.
21. Ignoring vulnerability scans.
22. Treating scanner output as infallible.
23. Ignoring SBOMs.
24. Using mutable tags without understanding them.
25. Ignoring image provenance.
26. Assuming signatures prove code is vulnerability-free.


```text
"The container runs with deliberately limited privilege, access, resources, and trust."
```
