# Part 1: Docker Foundations: Containers, Images, and How Docker Actually Works

Docker becomes much easier once you stop thinking of it as a collection of commands and understand the system underneath those commands.

In this first part, we will start from zero. You do not need previous Docker knowledge. We will first understand the problem containers were designed to solve, then build a mental model of Docker itself, and finally run through the lifecycle of a real container.

By the end of this part, you should understand this entire flow:

```text
Developer
   ↓
Docker CLI
   ↓
Docker API
   ↓
Docker Daemon
   ↓
Docker Image
   ↓
Docker Container
   ↓
Running Application
```

You should also understand what happens behind the scenes when you type something as simple as:

```bash
docker run nginx
```

That one command involves the Docker client, Docker daemon, image storage, potentially a registry, Linux kernel isolation, filesystem layers, networking, and a running process.

We will unpack all of it.

---

# 1. The Problem Docker Was Created to Solve

Before learning Docker, we need to understand the problem.

Imagine a developer creates a web application on a laptop.

The application requires:

```text
Ubuntu
Python 3.12
Flask
Redis
PostgreSQL
Several Python libraries
Environment variables
Specific configuration files
```

Everything works perfectly on the developer's laptop.

The developer sends the application to another engineer.

The second engineer tries to run it.

It fails.

Why?

Their computer might have:

```text
Python 3.10 instead of 3.12

Different library versions

Different operating system

Different environment variables

Different configuration

Missing system packages

Different file permissions
```

The source code may be identical.

The environment is not.

This creates one of the oldest problems in software engineering:

> "It works on my machine."

The application itself is only one part of what makes software run.

A more accurate model is:

```text
Application
    +
Runtime
    +
Libraries
    +
Dependencies
    +
Configuration
    +
Operating-system components
    =
Working Application
```

If you move only the application code, you have not necessarily moved the environment required to run it.

Docker helps package those pieces into a standardized, portable unit.

---

# 2. What Is Docker?

Docker is a platform for building, packaging, distributing, and running applications inside containers.

A container packages an application together with the environment it needs to run.

For example:

```text
Application
├── Runtime
├── Libraries
├── Dependencies
├── Configuration
└── Application files
```

Docker packages this environment into an **image**.

The image can then be used to create one or more **containers**.

Think of the relationship as:

```text
Application Files
      ↓
Dockerfile
      ↓
Build
      ↓
Docker Image
      ↓
Run
      ↓
Docker Container
      ↓
Running Application
```

We will learn Dockerfiles and image building later. For now, the important idea is:

**Image = packaged blueprint**

**Container = running instance created from that blueprint**

---

# 3. Why Docker Was Created

Before container platforms became popular, deploying applications consistently was difficult.

Development might happen on:

```text
Developer Laptop
```

Testing might happen on:

```text
Testing Server
```

Production might run on:

```text
Production Linux Server
```

Each environment could have different software versions and configuration.

Consider this example.

Development:

```text
Ubuntu 24.04
Python 3.12
Library A 2.1
Library B 4.0
```

Production:

```text
Ubuntu 22.04
Python 3.10
Library A 1.9
Library B 3.6
```

The application behaves differently.

Teams therefore spent considerable effort maintaining environments.

Docker helped standardize application packaging.

Instead of saying:

> Install Python, install these packages, configure these files, create these directories, set these permissions, and then run my application.

You can distribute a container image that already describes the application environment.

The workflow becomes:

```text
Build once
    ↓
Create image
    ↓
Store image
    ↓
Run the same image
    ↓
Development
Testing
Staging
Production
```

There can still be environment-specific configuration, infrastructure differences, external services, secrets, CPU architecture differences, and other variables. Docker does not magically make every environment identical.

But it makes the application's packaged runtime much more consistent.

# 4. Applications Before Containers

To appreciate containers, look at how infrastructure evolved.

A simplified progression is:

```text
Physical Servers
      ↓
Virtual Machines
      ↓
Containers
```

Each solved important problems.

---

# 5. Physical Servers

A physical server is an actual computer.

Like a laptop, it has:

```text
CPU
Memory
Storage
Network interfaces
Operating system
```

But servers are normally designed for continuous workloads in data centers or cloud infrastructure.

Historically, an organization might buy a physical server for an application.

For example:

```text
Physical Server
│
├── Linux
│
└── Company Website
```

Another application might receive another server:

```text
Physical Server 1
└── Website

Physical Server 2
└── Database

Physical Server 3
└── Internal Application
```

This provided isolation but often wasted resources.

Imagine Server 1 has:

```text
16 CPU cores
64 GB RAM
```

but its application normally uses:

```text
2 CPU cores
8 GB RAM
```

Much of the machine remains unused.

This led to greater adoption of virtualization.

---

# 6. Virtual Machines

Virtual machines allow multiple isolated operating-system environments to run on one physical server.

Instead of:

```text
Physical Server
└── One Operating System
    └── One Application
```

you can have:

```text
Physical Server
        │
    Hypervisor
   ┌────┼────┐
   ↓    ↓    ↓
  VM1  VM2  VM3
```

Each VM behaves like a separate computer.

For example:

```text
Physical Server
│
└── Hypervisor
    │
    ├── VM 1
    │   ├── Ubuntu
    │   └── Web Application
    │
    ├── VM 2
    │   ├── Ubuntu
    │   └── API
    │
    └── VM 3
        ├── Linux
        └── Database
```

## What is a hypervisor?

A hypervisor is software that creates and manages virtual machines.

Examples include technologies such as:

```text
VMware ESXi
Microsoft Hyper-V
KVM
```

The important point is that every traditional VM normally includes its own guest operating system.

That provides strong isolation, but it also adds overhead.

---

# 7. The Cost of Virtual Machines

Suppose you want to run three applications.

With VMs:

```text
Physical Server
│
└── Hypervisor
    │
    ├── VM 1
    │   ├── Guest OS
    │   ├── Libraries
    │   └── App A
    │
    ├── VM 2
    │   ├── Guest OS
    │   ├── Libraries
    │   └── App B
    │
    └── VM 3
        ├── Guest OS
        ├── Libraries
        └── App C
```

Each VM needs resources for its operating system.

VM images can also be large, and operating systems take time to boot.

Containers approach the problem differently.

---

# 8. What Is a Container?

A container is an isolated environment for running one or more processes while sharing the host's underlying kernel.

A simplified Linux container architecture looks like:

```text
Physical/Virtual Machine
        ↓
Host Operating System
        ↓
Linux Kernel
        ↓
Container Runtime
   ┌────┼────┐
   ↓    ↓    ↓
Container A
Container B
Container C
```

Each container can contain its own:

```text
Application
Runtime
Libraries
Dependencies
Filesystem
Configuration
```

But unlike a traditional VM, it does not normally boot its own complete guest kernel.

This is one reason containers are generally lightweight.

---

# 9. Containers vs Virtual Machines

This distinction is fundamental.

## Virtual machines

```text
Physical Hardware
       ↓
Host / Hypervisor
       ↓
┌───────────────┐
│ VM 1          │
│ Guest OS      │
│ Libraries     │
│ Application   │
└───────────────┘

┌───────────────┐
│ VM 2          │
│ Guest OS      │
│ Libraries     │
│ Application   │
└───────────────┘
```

## Containers

```text
Physical/Virtual Hardware
          ↓
Host Operating System
          ↓
Host Kernel
          ↓
Container Runtime
      ↓       ↓
┌─────────┐ ┌─────────┐
│ App A   │ │ App B   │
│ Libs    │ │ Libs    │
└─────────┘ └─────────┘
```

The key difference is:

**VMs virtualize machines. Containers isolate processes.**

A traditional VM generally includes a complete guest operating system and its own kernel.

Linux containers share the host Linux kernel while receiving isolated views of resources such as processes, networking, filesystems, and hostnames.

That distinction has major consequences.

| Characteristic    | Container                          | Virtual Machine        |
| ----------------- | ---------------------------------- | ---------------------- |
| Guest OS          | Usually no full guest OS           | Yes                    |
| Kernel            | Shares host kernel                 | Own guest kernel       |
| Startup           | Usually fast                       | Usually slower         |
| Size              | Often MB to hundreds of MB         | Often GB               |
| Resource overhead | Lower                              | Higher                 |
| Isolation model   | Process/kernel isolation           | Machine virtualization |
| Portability       | Very high for compatible platforms | High                   |
| Density           | Often high                         | Usually lower          |

This does **not** mean containers are always better than virtual machines.

They solve different problems.

In fact, containers frequently run **inside virtual machines** in cloud environments.

For example:

```text
AWS Physical Infrastructure
        ↓
EC2 Virtual Machine
        ↓
Linux
        ↓
Docker
        ↓
Containers
```

Docker does not replace EC2.

Docker and EC2 operate at different layers.

# 10. What Does Containerization Mean?

Containerization means packaging an application and the required user-space dependencies into a standardized image that can be executed as an isolated container.

Imagine this application:

```text
payment-api/
├── application code
├── Python runtime requirements
├── libraries
├── configuration expectations
└── startup command
```

Containerization turns the application's runtime environment into something that can be represented by a container image.

Conceptually:

```text
Source Code
     +
Runtime
     +
Dependencies
     +
Filesystem Content
     +
Startup Instructions
     ↓
Container Image
```

That image can then be transported to another compatible environment.

```text
Developer Laptop
       ↓
Container Registry
       ↓
Test Environment
       ↓
Production Environment
```

# 11. Docker's Three Concepts You Must Never Confuse

At this stage, remember three words:

```text
IMAGE
CONTAINER
REGISTRY
```

They are related but different.

---

# 12. What Is a Docker Image?

A Docker image is a packaged, read-only template used to create containers.

It contains the filesystem content and metadata necessary for the containerized application.

For example, an Nginx image might include:

```text
Linux user-space files
Nginx binaries
Required libraries
Default configuration
Startup instructions
```

You can download an existing image:

```bash
docker pull nginx
```

Later, you will build your own:

```text
Your Code
   ↓
Dockerfile
   ↓
docker build
   ↓
Your Image
```

An image itself is not the running application.

It is the template used to create the runtime environment.

---

# 13. Image vs Container

A useful analogy is:

```text
Class → Object
```

or:

```text
Blueprint → House
```

For Docker:

```text
Image → Container
```

One image can create many containers.

```text
             nginx image
                 │
       ┌─────────┼─────────┐
       ↓         ↓         ↓
Container 1 Container 2 Container 3
```

Each container is a separate runtime instance.

For example:

```bash
docker run --name web1 nginx
docker run --name web2 nginx
docker run --name web3 nginx
```

All three containers can originate from the same Nginx image.

---

# 14. What Is a Container Registry?

Images need somewhere to be stored and distributed.

That is the purpose of a **container registry**.

A registry is a service that stores and distributes container images.

Conceptually:

```text
Developer
    ↓
Build Image
    ↓
Push
    ↓
Container Registry
    ↓
Pull
    ↓
Server
    ↓
Container
```

Registries become particularly important in CI/CD.

For example:

```text
GitHub
  ↓
CI Pipeline
  ↓
Build Docker Image
  ↓
Push Image
  ↓
Registry
  ↓
Production Server
  ↓
Pull Image
  ↓
Run Container
```

Examples of container registry services include Docker Hub, Amazon Elastic Container Registry, GitHub Container Registry, Google Artifact Registry, and Azure Container Registry.

---

# 15. What Is Docker Hub?

Docker Hub is a hosted container registry service associated with Docker.

It contains public and private repositories of container images.

Common images include:

```text
nginx
ubuntu
redis
postgres
mysql
node
python
```

When you run:

```bash
docker pull nginx
```

Docker can retrieve the requested Nginx image from its configured registry, commonly Docker Hub for this simple image reference.

You can think of Docker Hub as a distribution point for container images.

But do not think of it as exactly equivalent to GitHub.

GitHub primarily hosts source-code repositories.

Docker Hub primarily distributes container images.

```text
Git Repository
     ↓
Source Code

Container Registry
     ↓
Container Images
```

# 16. Repository, Image, and Tag

You will frequently see something like:

```text
nginx:1.27
```

This has two important parts:

```text
nginx : 1.27
  ↑       ↑
repository tag
```

The repository groups related image versions.

The tag identifies a particular reference/version within that repository.

Another common example is:

```text
python:3.12
```

You will later learn that tags are not the strongest form of immutable identity. Images can also be referenced using content digests.

For now, remember:

```text
Repository = collection/name
Tag        = named image reference
Image      = packaged content
Container  = runtime instance
Registry   = stores/distributes images
```

# 17. What Is Docker Engine?

Docker Engine is the core software responsible for building and running Docker containers.

On a Linux Docker host, its architecture can be simplified as:

```text
Docker CLI
    ↓
Docker API
    ↓
Docker Daemon
    ↓
Container Runtime
    ↓
Linux Kernel
```

Docker Engine handles operations such as:

```text
Building images
Pulling images
Creating containers
Starting containers
Stopping containers
Networking
Storage
Managing container resources
```

When people casually say "Docker," they may be referring to the broader ecosystem rather than one specific component.

Understanding the components removes that ambiguity.

---

# 18. What Is the Docker CLI?

CLI means:

**Command-Line Interface**

The Docker CLI is the command-line program through which you issue Docker commands.

For example:

```bash
docker ps
```

or:

```bash
docker pull nginx
```

or:

```bash
docker run nginx
```

The CLI is primarily the client.

It accepts your request and communicates with the Docker Engine's API.

Think:

```text
You
 ↓
Docker CLI
 ↓
Request
 ↓
Docker Daemon
```

The CLI itself is not normally doing all the work of creating and isolating the container.

The daemon and lower-level runtime components perform the backend operations.

---

# 19. What Is the Docker Daemon?

The Docker daemon is the long-running background service that manages Docker objects and container operations.

The daemon process is commonly:

```text
dockerd
```

It manages things such as:

```text
Images
Containers
Networks
Volumes
Build operations
Registry interactions
```

For example, you type:

```bash
docker run nginx
```

The CLI sends a request.

The daemon receives it.

The daemon determines what must happen.

If the required image is unavailable locally, it can retrieve it.

Then it coordinates creation and startup of the container.

Simplified:

```text
You
 ↓
docker run nginx
 ↓
Docker CLI
 ↓
Docker API
 ↓
dockerd
 ↓
Check image
 ↓
Create container
 ↓
Configure isolation/network/storage
 ↓
Start process
```

---

# 20. Docker Uses Lower-Level Container Components

Docker Engine is not the only software involved behind the scenes.

Modern Docker installations use lower-level container runtime components.

A useful simplified model is:

```text
Docker CLI
    ↓
dockerd
    ↓
containerd
    ↓
runc
    ↓
Linux Kernel
```

## containerd

`containerd` manages much of the container lifecycle and runtime functionality.

## runc

`runc` is a low-level OCI-compatible runtime responsible for creating and starting containers according to an OCI runtime specification.

You do not need to operate these manually as a beginner.

But knowing they exist helps prevent the mistaken idea that Docker itself invented every mechanism used to isolate a container.

Much of the actual isolation comes from Linux kernel functionality.

---

# 21. What Is Docker Desktop?

Docker Desktop provides a packaged Docker development environment for desktop operating systems such as macOS and Windows, and it is also available for Linux.

It provides features such as:

```text
Docker Engine environment
Docker CLI integration
Docker Compose
Graphical interface
Configuration tools
Development integrations
```

There is an important architectural detail on macOS and Windows.

Linux containers depend on Linux kernel features.

macOS does not use the Linux kernel.

Windows does not normally expose a Linux kernel as its native kernel in the same way as a Linux host.

Therefore, Docker Desktop can use a lightweight Linux virtual machine/environment to provide the Linux kernel required by Linux containers.

Conceptually on macOS:

```text
Mac
 ↓
Docker Desktop
 ↓
Linux VM
 ↓
Linux Kernel
 ↓
Docker Engine
 ↓
Linux Containers
```

This explains something important:

Docker containers may be lightweight, but Docker Desktop can still involve virtualization underneath them.

# 23. Docker Uses a Client-Server Architecture

Docker uses a client-server model.

This means one component requests work and another performs/manages the work.

The client is commonly:

```text
docker
```

The server-side daemon is:

```text
dockerd
```

Flow:

```text
Docker Client
     ↓
Request through Docker API
     ↓
Docker Daemon
     ↓
Operation performed
```

For example:

```bash
docker ps
```

means roughly:

> Ask the Docker daemon for information about containers.

The daemon returns information.

The CLI formats it for your terminal.

---

# 24. What Is an API?

API means:

**Application Programming Interface**

An API defines a structured way for software components to communicate.

The Docker CLI does not need to manually manipulate every kernel feature itself.

Instead, it communicates with the Docker daemon using Docker's API.

Conceptually:

```text
Human
 ↓
CLI
 ↓
API request
 ↓
Docker daemon
 ↓
Result
 ↓
API response
 ↓
CLI
 ↓
Human
```

This architecture also means software other than the Docker CLI can interact with Docker through APIs.

---

# 25. Docker Socket

On Linux, the Docker client commonly communicates with the local daemon through a Unix socket:

```text
/var/run/docker.sock
```

Conceptually:

```text
docker CLI
    ↓
/var/run/docker.sock
    ↓
dockerd
```

A Unix socket allows local processes to communicate.

You should also understand a security implication very early:

**Access to the Docker daemon/socket is highly privileged.**

Giving an untrusted application unrestricted access to the Docker socket can effectively give it extensive control over the Docker host.

Later, our Docker security part will examine this properly.

For now:

> Do not casually expose or mount the Docker socket into containers.

---

# 26. What Is the Host Operating System?

The host is the machine/environment running the container engine.

For example:

```text
EC2 Instance
   ↓
Ubuntu Linux
   ↓
Docker Engine
   ↓
Containers
```

Ubuntu is the host operating system.

On a Linux Docker host, the containers rely on the host Linux kernel.

This leads us to one of the most important Docker concepts.

---

# 27. Containers and the Linux Kernel

A common beginner misunderstanding is:

> "Every Docker container contains its own operating system."

That is not quite correct.

Suppose you run:

```bash
docker run ubuntu
```

The Ubuntu image contains Ubuntu user-space files and tools.

It does not boot a completely separate Ubuntu kernel like a traditional VM.

Conceptually:

```text
Ubuntu Container
├── Ubuntu user-space tools
├── Libraries
├── Files
└── Processes
        ↓
Host Linux Kernel
```

Another container might use Alpine:

```text
Alpine Container
├── Alpine user-space
├── Libraries
└── Processes
        ↓
Same Host Linux Kernel
```

So:

```text
Linux Host Kernel
      ↑       ↑
      │       │
 Ubuntu     Alpine
Container  Container
```

This shared-kernel model is central to Linux containers.

---

# 28. If Containers Share the Kernel, How Are They Isolated?

This is where Linux kernel features become important.

Three major concepts to understand are:

```text
Namespaces
cgroups
Layered filesystems
```

Very roughly:

```text
Namespaces → What the process can see

cgroups → How many resources it can use

Layered filesystem → How container/image files are organized
```

These are not the only mechanisms involved, but they form an excellent beginner mental model.

---

# 29. Linux Namespaces

Namespaces provide isolation.

They allow processes to have different views of system resources.

Without isolation, every process would see the same global system environment.

With namespaces, a container can behave as though it has its own environment.

Important namespace categories include:

```text
PID
Network
Mount
UTS
IPC
User
Cgroup
```

Let's understand several.

---

# 30. PID Namespace

PID means:

**Process ID**

Every Linux process has an ID.

A PID namespace isolates process numbering and visibility.

Inside a container, an application may appear to be process:

```text
PID 1
```

But on the host, that same process has another host PID.

Conceptually:

```text
Container View

PID 1 → nginx
PID 7 → worker
```

Host view:

```text
PID 19482 → nginx
PID 19501 → worker
```

This gives the container its own process view.

---

# 31. Network Namespace

A network namespace gives processes an isolated networking environment.

A container can have its own:

```text
Network interfaces
IP addresses
Routing table
Ports
```

For example:

```text
Host
│
├── Container A
│   └── eth0 → 172.x.x.x
│
└── Container B
    └── eth0 → 172.x.x.x
```

Docker networking then connects these isolated environments using virtual networking mechanisms.

We will spend an entire part on Docker networking.

---

# 32. Mount Namespace

A mount namespace controls what filesystem mounts a process sees.

This helps give a container its own filesystem view.

Container A might see:

```text
/
├── bin
├── etc
├── app
└── var
```

Container B may see something entirely different.

Both containers are still running on the same host.

---

# 33. UTS Namespace

UTS namespaces isolate hostname and domain-name information.

That is why a container can have a hostname different from the host.

For example:

```text
Host hostname:
docker-server

Container hostname:
a84b712c39ef
```

---

# 34. IPC Namespace

IPC means:

**Inter-Process Communication**

Linux processes can communicate using mechanisms such as shared memory and message queues.

IPC namespaces help isolate these resources between groups of processes.

---

# 35. User Namespace

User namespaces can map user and group identities between a container and the host.

This can improve isolation.

For example, a process may appear as a particular UID inside its namespace while mapping differently outside it.

User namespaces are an important advanced security topic.

---

# 36. Namespaces in One Diagram

Think:

```text
                 Linux Kernel
                      │
        ┌─────────────┴─────────────┐
        │                           │
 Container A Namespace Set   Container B Namespace Set
        │                           │
   Processes                   Processes
   Network                     Network
   Mounts                      Mounts
   Hostname                    Hostname
   IPC                         IPC
```

Each container gets an isolated view.

But isolation does not answer another question:

> What stops one container from consuming all CPU and memory?

That is where cgroups become important.

---

# 37. What Are cgroups?

cgroups means:

**control groups**

Linux cgroups allow the kernel to organize processes and control/account for resource consumption.

Resources include things such as:

```text
CPU
Memory
I/O
Process counts
```

Imagine:

```text
Server
CPU: 8 cores
RAM: 16 GB
```

You run three containers.

Without appropriate controls, a badly behaving application could consume excessive resources and affect other workloads.

cgroups provide the kernel mechanisms used to control and account for resource usage.

Conceptually:

```text
Host Resources
CPU + Memory + I/O
        ↓
      cgroups
   ┌────┼────┐
   ↓    ↓    ↓
 App A App B App C
```

Later you will use Docker options that expose resource controls.

For example:

```bash
docker run --memory=512m nginx
```

This requests a memory limit for the container.

Docker translates high-level configuration into lower-level runtime/kernel configuration.

---

# 38. Namespaces vs cgroups

This is worth memorizing conceptually.

```text
Namespaces = isolation / visibility
cgroups    = resource control / accounting
```

Example:

**Namespace question:**

> Which processes can this container see?

**cgroup question:**

> How much memory can these processes consume?

Together, they help create the container environment.

---

# 39. Containers Are Really Processes

This is one of the most useful mental shifts in Docker.

A container is not a tiny magical server living somewhere inside your server.

At runtime, containerized applications ultimately execute as processes on the host kernel, with isolation and resource controls applied.

Conceptually:

```text
Host Linux
│
├── Process 100
├── Process 200
├── Process 300
│
└── Containerized Process
      ├── Namespace isolation
      ├── cgroup controls
      ├── Container filesystem
      └── Container networking
```

This understanding becomes extremely useful during troubleshooting.

If you later see:

```text
Container exited
```

you should immediately think:

> The main process running inside the container stopped.

That is much more useful than thinking:

> Docker randomly killed my mini virtual machine.

---

# 40. How Docker Images Store Files

Now we need another important concept.

Docker images are composed of filesystem layers.

Imagine an image:

```text
Application Layer
      ↓
Dependency Layer
      ↓
Runtime Layer
      ↓
Base Image Layer
```

These layers are stacked to present one filesystem view.

For example:

```text
Layer 4 → Application code
Layer 3 → Python dependencies
Layer 2 → Python runtime
Layer 1 → Base filesystem
```

To the container, they appear together:

```text
/
├── app
├── bin
├── etc
├── lib
├── usr
└── var
```

# 41. Why Images Use Layers

Layers provide several benefits.

They can support:

```text
Reuse
Caching
Efficient distribution
Storage efficiency
Faster builds
```

Suppose five images share the same base layer.

Docker does not necessarily need five independent copies of identical underlying content.

Layers can be reused.

Conceptually:

```text
              Common Base
             /     |     \
            /      |      \
         Image A Image B Image C
```

This is one reason image construction strategy matters.

We will examine it deeply when learning Dockerfiles.

# 42. Union and Overlay Filesystems

Docker uses layered filesystem technologies to combine image layers into a unified filesystem view.

On many modern Linux Docker installations, you will encounter:

```text
OverlayFS
```

and Docker's storage driver:

```text
overlay2
```

Conceptually:

```text
Layer 4 ─ Application
Layer 3 ─ Dependencies
Layer 2 ─ Runtime
Layer 1 ─ Base filesystem
          ↓
    Unified View
          ↓
       Container
```

The lower image layers are treated as read-only.

When a container runs, Docker provides a writable container layer above them.

```text
Container Writable Layer
-------------------------
Application Layer
Dependency Layer
Runtime Layer
Base Layer
```

This helps explain a major Docker behavior.

# 43. Why Container Changes Can Disappear

Suppose you run a container and create:

```text
/test.txt
```

That change exists in the container's writable layer.

If that container is deleted, its writable layer is also removed.

So:

```text
Image
 ↓
Container
 ↓
Create /test.txt
 ↓
Delete Container
 ↓
Container writable layer disappears
```

If you create another container from the original image:

```text
Image
 ↓
New Container
```

the new container will not automatically contain the file you created in the previous container.

This is why persistent data should not simply be treated as ordinary container writable-layer data.

Later, we will learn:

```text
Docker volumes
Bind mounts
Persistent storage
```

# 44. Images Are Designed to Be Immutable

Docker images are intended to behave as immutable artifacts.

Immutable means you do not normally modify an existing built image in place as your deployment workflow.

Instead:

```text
Old Image
   ↓
Change Dockerfile/application
   ↓
Build
   ↓
New Image
```

For example:

```text
myapp:1.0
myapp:1.1
myapp:1.2
```

This supports predictable deployment.

Rather than manually modifying production containers:

```text
SSH
 ↓
Change random files
 ↓
Install package
 ↓
Restart
```

a stronger container workflow is:

```text
Change source/configuration
 ↓
Build new image
 ↓
Test
 ↓
Publish
 ↓
Deploy new container
```

That principle will become very important when we reach CI/CD.

# 64. What Docker Does Not Do

Understanding Docker also means knowing its boundaries.

Docker does not automatically:

* Fix badly written applications.
* Make applications stateless.
* Make databases safe to delete.
* Secure an insecure application.
* Replace backups.
* Replace monitoring.
* Replace CI/CD.
* Replace cloud infrastructure.
* Replace Kubernetes.
* Guarantee identical behavior across incompatible CPU architectures or kernels.
* Automatically configure production networking.
* Automatically manage application secrets safely.
* Make every container secure simply because it is isolated.

Docker is a tool.

Good engineering practices still matter.

# 71. Safe Docker Habits From Day One

Even as a beginner, develop good habits.

Do not blindly run commands such as:

# 76. What You Should Now Understand

Before moving to Part 2, you should be able to explain the following in your own words:

* Docker packages and runs applications using containers.
* Docker helps reduce environment inconsistency.
* Physical servers, VMs, and containers represent different infrastructure/isolation approaches.
* A VM normally contains a guest operating system and guest kernel.
* Linux containers share the host Linux kernel.
* Containers are not simply miniature VMs.
* Containerized workloads ultimately run as processes.
* Containerization packages application runtime requirements into standardized images.
* Docker images are templates used to create containers.
* One image can create multiple containers.
* Registries store and distribute container images.

* Docker Engine provides the core Docker container functionality.

* Local Docker communication on Linux commonly uses `/var/run/docker.sock`.
* Docker Desktop provides a desktop Docker environment and can use Linux virtualization for Linux containers on non-Linux hosts.
* Linux namespaces provide isolated views of resources.
* cgroups provide resource management/accounting mechanisms.
* Docker images use filesystem layers.
* A running container receives a writable layer.
* Deleting a container removes its container-specific writable layer.
* Persistent data therefore requires deliberate storage design.
* `docker pull` retrieves an image.
* `docker create` creates a container.
* `docker start` starts an existing container.
* `docker run` creates and starts a new container.
* `docker ps` shows running containers.

# 79. Knowledge Check Answers

**1.** Docker helps package applications and their runtime dependencies into standardized images, reducing environment inconsistencies between development, testing, and deployment.

**2.** An image is the packaged template. A container is an instance created from that image.

**3.** Yes. One image can create many independent containers.

**4.** A registry stores and distributes container images.

**5.** Docker Hub is a hosted container registry service commonly used to distribute Docker/OCI container images.

**6.** The Docker CLI is the command-line client through which users send Docker commands.

**7.** The Docker daemon is the background service responsible for managing Docker resources and coordinating operations such as images, containers, networks, and volumes.

**8.** The API provides the interface through which the Docker client and other software communicate with the Docker daemon.

**9.** No. Linux containers normally share the host's Linux kernel rather than booting a separate kernel for every container.

**10.** The host Linux kernel.

**11.** Namespaces provide isolated views of system resources such as processes, networking, mounts, hostnames, and IPC.

**12.** cgroups organize processes and provide resource accounting/control mechanisms for resources such as CPU and memory.

**13.** `docker create` creates a container without starting it. `docker run` creates a new container and starts it.

**14.** `docker ps` normally displays running containers. `docker ps -a` includes containers that are stopped, exited, or otherwise not currently running.

**15.** Container-specific filesystem changes are normally stored in the container's writable layer. Removing the container removes that writable layer unless the data has been stored externally using persistent storage.

**16.** No. The image can remain after its containers are removed.

**17.** Containers do not normally require a complete guest OS and separate guest kernel for every workload. Linux containers share the host kernel while isolating processes and resources.

**18.** Check the container state and logs, then determine why its main process exited.

**19.** It is commonly the Unix socket through which local Docker clients communicate with the Docker daemon. Access to it is highly privileged.

**20.**
