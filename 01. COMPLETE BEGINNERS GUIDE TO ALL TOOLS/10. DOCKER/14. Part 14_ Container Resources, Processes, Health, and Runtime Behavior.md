# Part 14: Container Resources, Processes, Health, and Runtime Behavior

## Understand What Happens While Containers Are Actually Running

A Docker image can be perfectly built.

A container can start successfully.

The application can even respond to its first request.

None of those things guarantee that the application will continue working correctly.

Production containers operate under changing conditions:

* traffic increases;
* memory usage grows;
* CPU becomes saturated;
* processes crash;
* child processes accumulate;
* file descriptors are exhausted;
* dependencies become unavailable;
* health checks begin failing;
* applications receive shutdown signals;
* containers restart;
* the Linux kernel kills processes because memory is exhausted.

This is runtime behavior.

In this part, we move from:

```text
The container started.
```

to:

```text
What is actually happening inside the running container?
```

The investigation path for this part is:

```text
Container
   ↓
Processes
   ↓
PID 1
   ↓
Signals
   ↓
CPU / Memory / PIDs
   ↓
cgroups
   ↓
Health
   ↓
Runtime Metrics
   ↓
Failure Evidence
   ↓
Recovery
```

And the main lab follows:

```text

  ↓

  ↓
Failure
  ↓
Evidence
  ↓
Limit
  ↓
Recover
  ↓
Verify
```

# 2. Start With the Correct Mental Model

When you run:

```bash
docker run nginx
```

Docker does not create a tiny virtual computer containing some mysterious object called a container.

At the operating-system level, Docker ultimately starts processes.

A simplified mental model is:

```text
Docker Host
│
├── Linux Kernel
│
├── Container A
│   └── Process
│
├── Container B
│   ├── Process
│   └── Child Process
│
└── Container C
    ├── Process
    ├── Child Process
    └── Child Process
```

Containers provide isolated environments around processes.

This matters because nearly everything we discuss in this part eventually comes back to processes.

CPU is consumed by processes.

Memory is consumed by processes.

Signals are delivered to processes.

File descriptors belong to processes.

Zombie processes are process-management problems.

The container stops when its main process exits.

---

# 3. What Is a Process?

A process is a running instance of a program.

Suppose you have:

```text
/usr/bin/python
```

That is an executable program on disk.

When the operating system runs it, you get a process.

Conceptually:

```text
Program on disk
      ↓
Operating system starts it
      ↓
Running process
```

A process receives a:

```text
PID
```

which means:

```text
Process ID
```

---

# 4. Process IDs

On Linux, processes are identified using numbers.

For example:

```text
PID 1
PID 25
PID 103
PID 984
```

You can normally inspect processes using commands such as:

```bash
ps
```

or:

```bash
ps aux
```

depending on the utilities installed in the environment.

Minimal container images may not contain the full `ps` utility.

That does not mean the container has no processes.

It means the diagnostic command is absent from the image.

---

# 5. Containers Run Processes

Consider:

```bash
docker run \
  --name veriqta-process-lab \
  alpine \
  sleep 3600
```

The important application process is:

```text
sleep 3600
```

The container exists while its main process remains alive.

If that process exits, the container stops.

---

# 6. Verify the Container

Run:

```bash
docker ps
```

You should see:

```text
veriqta-process-lab
```

with a running status.

Now inspect the processes from the host using Docker:

```bash
docker top \
  veriqta-process-lab
```

You should see the `sleep` process.

Exact columns and PID values depend on your host.

---

# 7. `docker top`

The command:

```bash
docker top CONTAINER
```

shows running processes associated with a container.

Example:

```bash
docker top \
  veriqta-process-lab
```

Use it when you need to answer:

```text
What processes are actually running inside this container?
```

This is useful when:

* the container uses unexpected CPU;
* you suspect additional child processes;
* the application appears hung;
* process counts are increasing;
* you are investigating runtime behavior.

---

# 8. Container Process vs Host Process

The same process can have different PID visibility depending on the namespace from which you observe it.

Inside a container, you might see:

```text
PID 1
```

while the host sees the corresponding process with another PID.

Conceptually:

```text
Inside container:
PID 1

Host:
PID 4821
```

It is still the same underlying process.

The difference comes from PID namespaces.

---

# 9. PID Namespaces

A PID namespace isolates process ID visibility.

Without process isolation, every container could easily see the host's complete process tree.

Instead:

```text
Host PID Namespace
│
├── host processes
├── Container A processes
└── Container B processes
```

while Container A sees a restricted process view:

```text
Container A PID Namespace
│
├── PID 1
├── PID 7
└── PID 15
```

Container B has its own view.

---

# 10. Why PID Namespaces Matter

PID namespaces contribute to container isolation.

Container A normally does not need to manage arbitrary processes belonging to:

```text
Container B
```

or:

```text
the host
```

This reduces unnecessary visibility and interaction.

But remember from Part 13:

```text
Isolation is not absolute security.
```

Namespaces are one layer.

```bash
docker inspect \
```

You may receive something such as:

```text

```

---

# 12. PID 1 Inside a Container

Inside a normal container PID namespace, the main process becomes:

```text
PID 1
```

This is extremely important.

For:

```bash
docker run \
  alpine \
  sleep 3600
```

the `sleep` process becomes the container's main process.

Conceptually:

```text
Container
│
└── PID 1
    └── sleep 3600
```

---

# 13. Why PID 1 Matters

PID 1 has special responsibilities and behavior on Linux.

Two particularly important container concerns are:

```text
signal handling
```

and:

```text
child-process reaping
```

Poor PID 1 behavior can create:

* slow shutdowns;
* forced SIGKILL termination;
* incomplete cleanup;
* zombie processes;
* confusing restart behavior.

---

# 14. The Main Container Process

The container's lifetime is tied to its main process.

If PID 1 exits:

```text
PID 1 exits
    ↓
Container stops
```

This is why a container does not normally need:

```text
systemd
```

just to keep itself alive.

The application should normally run directly as the container's foreground process.

---

# 15. Foreground Processes

Traditional servers sometimes daemonize themselves.

That means:

```text
start
↓
fork/background
↓
original process exits
```

That pattern can cause problems in containers.

Docker generally expects the main application process to remain in the foreground.

Conceptually:

```text
Container
└── PID 1
    └── Application running in foreground
```

---

# 16. Bad Container Pattern

Imagine:

```text
Container starts
↓
startup script launches application in background
↓
startup script exits
↓
PID 1 exits
↓
container stops
```

The application may have briefly started.

But Docker tracks the container through its main process.

This is why container startup commands matter.

---

Run:

```bash
docker inspect \

```

This helps identify what Docker launched as the container command.

You can also inspect:

```bash

```

Always gather evidence rather than guessing.

# 18. Parent and Child Processes

Processes can create other processes.

Example:

```text
PID 1
Application
│
├── Worker 1
├── Worker 2
└── Worker 3
```

This is normal.

Web servers, job workers, application servers, databases, and other systems may use multiple processes or threads.

---

# 19. One Container Does Not Mean One Process

A common beginner statement is:

```text
One container should have one process.
```

That is too simplistic.

A better principle is:

```text
One container should generally have one primary responsibility.
```

A container may legitimately contain:

```text
main application process
+
worker processes
+
helper processes
```

if they belong to that responsibility.

# 21. Signals

Processes need a way to receive notifications from the operating system or other processes.

Linux uses:

```text
signals
```

A signal communicates an event or requested action.

Examples include:

```text
SIGTERM
SIGKILL
SIGINT
SIGHUP
```

For this part, the most important are:

```text
SIGTERM
SIGKILL
SIGINT
```

---

# 22. SIGTERM

SIGTERM means:

```text
termination request
```

Think:

```text
Please shut down.
```

The process can normally handle SIGTERM.

That gives the application an opportunity to:

* stop accepting new work;
* finish active requests;
* close database connections;
* flush buffers;
* write final logs;
* release resources;
* exit cleanly.

This is graceful termination.

---

# 23. SIGKILL

SIGKILL is very different.

Think:

```text
Stop immediately.
```

SIGKILL cannot be caught, blocked, or handled by the target process.

The application does not receive an opportunity to perform graceful cleanup.

Conceptually:

```text
SIGTERM
→ request shutdown
→ application can clean up

SIGKILL
→ kernel terminates process
→ no application cleanup opportunity
```

---

# 24. SIGINT

SIGINT is commonly associated with an interrupt from an interactive terminal.

For example:

```text
Ctrl+C
```

often generates SIGINT.

Applications may handle SIGINT to perform a controlled shutdown.

SIGINT and SIGTERM are different signals, even though many applications respond similarly to both.

---

# 25. What `docker stop` Does

When you run:

```bash
docker stop CONTAINER
```

Docker sends the configured stop signal to the container's main process.

If no different stop signal is configured, the normal default is:

```text
SIGTERM
```

Docker then waits for a grace period.

Conceptually:

```text
docker stop
    ↓
SIGTERM
    ↓
Wait
    ↓
Did process exit?
   / \
 Yes  No
 ↓     ↓
Done  SIGKILL
```

For Linux containers, the daemon-determined default stop timeout is normally 10 seconds unless another timeout is configured.

---

# 26. Why the Grace Period Exists

Imagine a backend processing:

```text
POST /payment
```

while the container is shutting down.

Immediate termination could interrupt:

```text
database transaction
network request
file write
message processing
```

A graceful shutdown allows the application to coordinate its exit.

---

# 27. Custom Stop Timeout

You can specify a timeout:

```bash
docker stop \
  --timeout 30 \
  CONTAINER
```

This gives the process up to 30 seconds after the initial stop signal before Docker forcefully terminates it.

Do not choose a timeout randomly.

It should reflect:

```text
maximum reasonable request duration
job completion behavior
connection draining
application cleanup time
deployment requirements
```

---

# 28. `docker kill`

Compare:

```bash
docker kill CONTAINER
```

By default, `docker kill` sends:

```text
SIGKILL
```

This is not the same operational behavior as:

```bash
docker stop CONTAINER
```

Use:

```text
docker stop
```

for normal shutdown.

Reserve forceful termination for situations where it is actually necessary.

---

# 29. Send a Specific Signal

Docker can send a selected signal.

Example:

```bash
docker kill \
  --signal SIGTERM \
  CONTAINER
```

or:

```bash
docker kill \
  --signal SIGHUP \
  CONTAINER
```

Whether a process does anything useful with the signal depends on the application.

---

# 30. Dockerfile `STOPSIGNAL`

A Dockerfile can define the expected stop signal.

Example:

```dockerfile
STOPSIGNAL SIGTERM
```

This tells Docker which signal should normally be sent when stopping containers created from the image.

Most applications should not change this without a reason.

---

# 31. Runtime Stop Signal

You can override the image stop signal when creating a container:

```bash
docker run \
  --stop-signal SIGTERM \
  IMAGE
```

Again, do not change signals merely because the option exists.

Use the signal your application correctly handles.

---

# 32. Graceful Shutdown

A production application should normally have a deliberate shutdown path.

Example:

```text
SIGTERM received
      ↓
Stop accepting new requests
      ↓
Finish permitted in-flight work
      ↓
Close database connections
      ↓
Flush pending output
      ↓
Release resources
      ↓
Exit 0
```

This matters during:

* deployments;
* host shutdowns;
* container replacements;
* scaling;
* maintenance;
* application restarts.

---

# 33. Graceful Shutdown Example in Python

A simplified teaching example:

```python
import signal
import sys
import time

running = True

def shutdown(signum, frame):
    global running
    print(f"Received signal {signum}. Shutting down...")
    running = False

signal.signal(signal.SIGTERM, shutdown)
signal.signal(signal.SIGINT, shutdown)

print("Application started")

while running:
    time.sleep(1)

print("Cleanup complete")
sys.exit(0)
```

This demonstrates the concept.

Real application frameworks often provide their own lifecycle hooks and shutdown mechanisms.

Use the framework's supported production approach.

# 35. Exec Form Matters

Prefer:

```dockerfile
CMD ["python", "app.py"]
```

over shell-form commands such as:

```dockerfile
CMD python app.py
```

when you want the application to be the direct main process.

The exec form avoids an unnecessary shell wrapper.

Conceptually:

```text
Exec form

PID 1
└── python app.py
```

versus potentially:

```text
Shell form

PID 1
└── /bin/sh -c ...
    └── application
```

Shell wrappers can interfere with signal propagation if they are not designed to forward signals correctly.

# 36. PID 1 Signal Behavior

PID 1 has special signal semantics on Linux.

A process running as PID 1 should deliberately handle the termination signals relevant to the application.

Do not assume every program behaves correctly merely because:

```text
SIGTERM was sent.
```

Verify shutdown behavior.

Measure:


A properly behaving simple application should stop quickly.

If every stop takes the entire configured timeout before termination, investigate.

Possible cause:

```text
SIGTERM is not reaching or being handled by the real application.
```

# 38. CPU

CPU is the processing capacity used to execute instructions.

A container does not receive a dedicated CPU simply because it exists.

Without configured constraints, its processes compete for available host CPU according to the host scheduler.

Conceptually:

```text
Host CPU
│
├── Container A
├── Container B
├── Container C
└── Host Processes
```

---

# 39. Unlimited Does Not Mean Infinite

When Docker says a container has no configured CPU limit, it does not mean:

```text
infinite CPU
```

It means the container is not restricted by a Docker CPU quota beyond what the host scheduler and available hardware impose.

If the host has:

```text
4 CPUs
```

that is still finite capacity.

---

# 40. CPU Saturation

CPU saturation occurs when demand approaches or exceeds available processing capacity.

Symptoms may include:

* increased response latency;
* slower request processing;
* delayed background work;
* timeouts;
* high CPU percentages;
* queue growth;
* poor throughput;
* other containers receiving less CPU.

---

# 41. `--cpus`

Docker provides:

```text
--cpus
```

Example:

```bash
docker run \
  --cpus 1.0 \
  IMAGE
```

This limits the container to approximately one CPU worth of runtime.

A fractional value is valid.

Example:

```bash
docker run \
  --cpus 0.5 \
  IMAGE
```

---

# 42. What `--cpus 0.5` Means

It does not necessarily mean:

```text
The container permanently owns half of physical CPU 0.
```

It means Docker configures CPU scheduling constraints corresponding to approximately half of one CPU's available execution time.

CPU scheduling is controlled through Linux resource-control mechanisms.

---

# 43. CPU Pinning

Docker also supports:

```text
--cpuset-cpus
```

Example:

```bash
docker run \
  --cpuset-cpus="0,1" \
  IMAGE
```

This restricts execution to selected CPUs.

CPU pinning is more specialized.

Most beginner production workloads should first understand:

```text
--cpus
```

before attempting detailed CPU affinity tuning.

---

# 44. CPU Shares

Docker also supports relative CPU weighting through:

```text
--cpu-shares
```

This affects relative CPU priority during contention.

Do not confuse:

```text
CPU shares
```

with:

```text
hard CPU quota.
```

For straightforward container limits, `--cpus` is often easier to reason about.

# 46. Memory

Memory is working storage used by processes while they run.

Applications use memory for things such as:

* code;
* heaps;
* stacks;
* caches;
* buffers;
* loaded libraries;
* request data;
* connection state.

Memory is finite.

That makes uncontrolled memory consumption dangerous.

---

# 47. Containers Have No Memory Limit by Default

Unless configured otherwise, a container can potentially consume as much memory as the host allows.

This is dangerous on shared systems.

Imagine:

```text
Host RAM: 8 GB

Container A: 1 GB
Container B: 1 GB
Container C: 6+ GB
```

Container C can create serious host-wide pressure.

---

# 48. Hard Memory Limit

Use:

```text
--memory
```

or:

```text
-m
```

Example:

```bash
docker run \
  --memory 512m \
  IMAGE
```

This sets a hard memory limit.

The container cannot freely exceed that configured physical-memory constraint.

---

# 49. Memory Units

Docker accepts memory values using units such as:

```text
b
k
m
g
```

Examples:

```text
256m
512m
1g
2g
```

Always confirm the exact resource configuration through inspection.

---

# 50. Inspect Memory Limit

Run:

```bash
docker inspect \
  --format '{{.HostConfig.Memory}}' \
  CONTAINER
```

Docker reports the value in bytes.

If you configured:

```text
256m
```

you should see the corresponding byte value.

---

# 51. Memory Reservation

Docker also supports:

```text
--memory-reservation
```

This is a soft memory limit.

Example:

```bash
docker run \
  --memory 512m \
  --memory-reservation 256m \
  IMAGE
```

Conceptually:

```text
256 MB
soft reservation/pressure target

512 MB
hard memory ceiling
```

---

# 52. Hard Limit vs Reservation

Think:

```text
--memory
→ hard maximum
```

while:

```text
--memory-reservation
→ soft limit used under memory pressure/contention
```

A reservation does not guarantee that the application will never exceed that value.

That distinction is extremely important.

---

# 53. Reservation Must Be Lower Than Hard Limit

If both are used meaningfully:

```text
memory reservation
<
memory hard limit
```

Example:

```text
reservation = 256 MB
hard limit = 512 MB
```

not:

```text
reservation = 1 GB
hard limit = 512 MB
```

---

# 54. Why Use a Reservation?

Suppose an application normally consumes:

```text
200 MB
```

but occasionally reaches:

```text
400 MB
```

You might configure:

```text
reservation = 256 MB
hard limit = 512 MB
```

The reservation represents a softer pressure-management target while the hard limit establishes an upper boundary.

Actual values must come from measurements.

---

# 55. Memory Swap

Docker also has:

```text
--memory-swap
```

Its behavior depends on:

```text
--memory
```

and host swap configuration.

Swap is disk-backed memory and is much slower than RAM.

Do not treat swap as free extra RAM.

For latency-sensitive workloads, heavy swapping can seriously damage performance.

---

# 57. Out of Memory

OOM means:

```text
Out Of Memory
```

Memory exhaustion can occur at:

```text
container level
```

or:

```text
host level
```

depending on constraints and system conditions.

Linux has mechanisms for responding when memory becomes critically scarce.

---

# 58. The OOM Killer

When Linux cannot satisfy critical memory requirements, the kernel may kill processes to recover memory.

This is commonly associated with:

```text
OOM killer
```

In containerized environments, a container process exceeding a hard memory limit can be killed because of that limit.

---

# 59. `OOMKilled`

Docker records whether a container was killed because of an out-of-memory condition.

Inspect:

```bash
docker inspect \
  --format '{{.State.OOMKilled}}' \
  CONTAINER
```

Possible result:

```text
true
```

That is powerful evidence.

---

# 60. Why `OOMKilled` Matters

Imagine:

```text
Application suddenly disappeared.
```

A beginner might say:

```text
Docker crashed.
```

An evidence-based investigation asks:

```text
Was the container running?

What was the exit code?

Was OOMKilled true?

What was the memory limit?

What did docker stats show?

What do application logs show?

Did the host experience memory pressure?
```

---

# 61. Inspect Exit Information

Run:

```bash
docker inspect \
  --format 'Status={{.State.Status}} ExitCode={{.State.ExitCode}} OOMKilled={{.State.OOMKilled}} Error={{.State.Error}}' \
  CONTAINER
```

Representative output:

```text
Status=exited ExitCode=137 OOMKilled=true Error=
```

Do not diagnose OOM from exit code alone.

Check:

```text
OOMKilled
```

and the surrounding evidence.

---

# 62. Exit Code 137

You will often encounter:

```text
137
```

when a process was terminated by SIGKILL.

Because:

```text
128 + signal number 9
= 137
```

SIGKILL can happen for more than one reason.

Therefore:

```text
ExitCode 137
```

does not by itself prove:

```text
OOM.
```

Check:

```text
.State.OOMKilled
```

and other evidence.

Create a controlled memory allocation script.

Project:

```text
memory-lab/
├── Dockerfile
```

`memory.py`:

```python
import time

blocks = []

print("Memory pressure lab starting", flush=True)

while True:
    blocks.append(bytearray(10 * 1024 * 1024))
    print(
        f"Allocated approximately {len(blocks) * 10} MB",
        flush=True
    )
    time.sleep(0.5)
```

# 67. What Are cgroups?

cgroups means:

```text
control groups
```

They are Linux kernel mechanisms used to organize, account for, and constrain resources used by groups of processes.

Docker relies on cgroups for resource management.

Conceptually:

```text
Container Processes
        ↓
      cgroup
        ↓
+------------------+
| CPU controls     |
| Memory controls  |
| PID controls     |
| Resource stats   |
+------------------+
        ↓
Linux Kernel
```

When you run:

```bash
  --cpus 1 \
  IMAGE
```

Conceptually:

```text
Docker CLI
   ↓
Docker Engine
   ↓
Container Runtime
   ↓
Linux cgroups
   ↓
Kernel enforces limits
```

# 71. PID Resource Limits

Processes are resources too.

Docker supports:

```text

```

```text

↓
creates child process
↓
child creates another
↓
continues repeatedly
↓

```

PID limits reduce the blast radius.

# 73. Restart Policies

Applications sometimes exit.

The question becomes:

```text
Should Docker automatically restart the container?
```

Docker provides restart policies.

Main standalone-container policies include:

```text
no
on-failure
always
unless-stopped
```

---

# 74. `no`

Default:

```text
--restart no
```

Docker does not automatically restart the container because it exited.

Use when automatic restart is not desired.

---

# 75. `on-failure`

Example:

```bash
docker run \
  --restart on-failure \
  IMAGE
```

Docker restarts the container when it exits with a non-zero status.

You can optionally limit retries:

```bash
docker run \
  --restart on-failure:5 \
  IMAGE
```

---

# 76. `always`

Example:

```bash
docker run \
  --restart always \
  IMAGE
```

Docker attempts to keep the container running according to the restart-policy semantics.

If manually stopped, it does not immediately restart simply to fight the operator. Its behavior after daemon restart differs from `unless-stopped`.

Understand the documented semantics before choosing it.

---

# 77. `unless-stopped`

Example:

```bash
docker run \
  --restart unless-stopped \
  IMAGE
```

This behaves similarly to `always`, but preserves an intentional stopped state across Docker daemon restarts.

It is commonly useful for long-running standalone services.

---

# 78. Restart Policies Do Not Fix Broken Applications

Bad mental model:

```text
Application crashes
↓
Restart automatically
↓
Problem solved
```

Better:

```text
Application crashes
↓
Restart may restore availability
↓
Investigate why it crashed
```

A restart policy is a recovery mechanism.

It is not root-cause remediation.

---

```text
↓

↓

↓

↓

↓
```

# 82. Running Does Not Mean Healthy

Consider a web application.

Its process is alive.

Docker reports:

```text
Up
```

But the application:

* cannot reach its database;
* is deadlocked;
* cannot answer requests;
* has exhausted worker threads;
* has corrupted internal state.

Docker can still see the main process running.

Therefore:

```text
process alive
```

is not enough.

# 83. Health Checks

Docker supports health checks.

A health check answers:

```text
Is the application actually functioning according to a test we define?
```

This is different from:

```text
Is PID 1 still alive?
```

---

# 84. Dockerfile `HEALTHCHECK`

Example:

```dockerfile
HEALTHCHECK \
  --interval=30s \
  --timeout=3s \
  --start-period=10s \
  --retries=3 \
  CMD curl --fail http://localhost:8080/health || exit 1
```

This tells Docker to periodically run the command.

A zero exit status means success.

A non-zero status indicates failure.

---

# 85. Health Check Options

Important options include:

```text
--interval
--timeout
--start-period
--start-interval
--retries
```

Support for newer options such as `--start-interval` depends on Docker/Engine API versions.

Use only options supported by your target environment.

---

# 86. Health Check States

A container with a configured health check can move through states such as:

```text
starting
↓
healthy
```

or:

```text
starting
↓
healthy
↓
unhealthy
```

The container may still be:

```text
running
```

while health status is:

```text
unhealthy
```

This distinction is critical.

---

# 87. Starting

Immediately after startup, an application may need time to:

* load configuration;
* initialize caches;
* establish connections;
* run initialization;
* warm up;
* start workers.

The health state can initially be:

```text
starting
```

This avoids treating normal initialization as immediate failure when a suitable start period is configured.

---

# 88. Healthy

A successful health check results in:

```text
healthy
```

This means:

```text
The configured health command is succeeding.
```

It does not mean:

```text
The entire distributed system is perfect.
```

Health is only as meaningful as the check you design.

---

# 89. Unhealthy

After the configured number of consecutive failed checks, Docker can mark the container:

```text
unhealthy
```

Again:

```text
unhealthy
```

does not necessarily mean:

```text
container process exited.
```

The process may still be running.

```text

```

fail when the database fails?

Sometimes yes.

Sometimes no.

```text

```

Docker Engine's basic container health check is not the same thing as Kubernetes' separate liveness/readiness/startup probe model.

Do not mix the concepts.

`app.py`:

```python
from http.server import BaseHTTPRequestHandler, HTTPServer


class Handler(BaseHTTPRequestHandler):

    def do_GET(self):

        if self.path == "/health":
            body = b'{"status":"ok"}'

            self.send_response(200)
            self.send_header(
                "Content-Type",
                "application/json"
            )
            self.send_header(
                "Content-Length",
                str(len(body))
            )
            self.end_headers()

            self.wfile.write(body)

        else:
            self.send_response(404)
            self.end_headers()


server = HTTPServer(
    ("0.0.0.0", 8080),
    Handler
)

print(
    "Server listening on port 8080",
    flush=True
)

server.serve_forever()
```

# 120. File Descriptors

Linux processes interact with many resources through:

```text
file descriptors
```

A file descriptor is a small integer representing an open resource.

Examples include:

* files;
* network sockets;
* pipes;
* devices.

Conceptually:

```text
Process
│
├── FD 0 → stdin
├── FD 1 → stdout
├── FD 2 → stderr
├── FD 3 → file
├── FD 4 → network socket
└── FD 5 → database connection socket
```

---

# 121. Why File Descriptors Matter

A web server handling many network connections needs file descriptors.

A process can eventually reach its configured file-descriptor limit.

Then operations can fail.

Common symptoms include:

```text
Too many open files
```

Possible effects:

* cannot accept connections;
* cannot open log files;
* cannot connect to dependencies;
* cannot open configuration/data files.

---

# 122. Check Limits

Inside a suitable Linux container:

```bash

```

may show the current open-file limit for the shell/process context.

Example:

```text

```

or another value.

The actual value depends on the environment.

---

# 123. `--ulimit`

Docker supports runtime ulimit configuration.

Example:

```bash

  IMAGE
```

Do not copy this number blindly.

First determine:

* application requirements;
* expected concurrency;
* host capacity;
* operating-system limits;
* database/network constraints.

Increasing a limit does not fix a file-descriptor leak.

# 124. File Descriptor Leak

Suppose application code:

```text
opens file/socket
↓
uses it
↓
never closes it
↓
repeats
```

Eventually:

```text
open descriptors
↑
↑
↑
```

until the process reaches its limit.

Raising the limit may only delay failure.

The correct fix is usually:

```text
find the leak
↓
fix lifecycle management
↓
set appropriate limit
↓
monitor
```

# 132. Zombie Processes

A zombie process is a process that has exited but whose parent has not yet collected its termination status.

Conceptually:

```text
Parent
  ↓
creates child
  ↓
Child exits
  ↓
Parent should reap child
```

If the parent fails to reap it:

```text
Exited child
↓
Zombie entry remains
```

---

# 133. Zombies Do Not Mean Walking Processes

A zombie process is not actively executing application code.

It has already terminated.

What remains is process-table information waiting for the parent to collect the child's exit status.

---

# 134. Why Zombies Matter

A few temporary zombie processes may not be catastrophic.

But an application that continuously creates children and never reaps them can accumulate process-table entries.

Over time, this can contribute to:

```text
process exhaustion
```

and operational instability.

---

# 135. PID 1 and Reaping

On Linux, PID 1 has special responsibility for adopted orphan processes.

This is one reason container PID 1 behavior matters.

Not every application is designed to behave like an init system.

If your application spawns subprocesses, process reaping needs careful consideration.

---

# 136. Init Processes

Traditional operating systems normally have an init process as PID 1.

Among its responsibilities are:

```text
signal-related process lifecycle behavior
child-process reaping
```

Containers often run the application directly as PID 1.

That is usually desirable.

But some applications need help with PID 1 responsibilities.

---

# 137. Docker `--init`

Docker provides:

```text
--init
```

Example:

```bash
docker run \
  --init \
  IMAGE
```

This inserts a small init process into the container.

Its job includes:

```text
forwarding signals
reaping child processes
```

---

# 138. Architecture Without `--init`

```text
Container
│
└── PID 1
    Application
      │
      ├── Child A
      └── Child B
```

The application itself must correctly manage child processes.

---

# 139. Architecture With `--init`

Conceptually:

```text
Container
│
└── PID 1
    Init
      │
      └── Application
            │
            ├── Child A
            └── Child B
```

The init process can handle reaping and signal forwarding.

---

# 140. When `--init` Is Useful

Consider `--init` when the application:

* launches child processes;
* does not reliably reap children;
* has problematic PID 1 signal behavior;
* uses scripts/tools that create subprocesses.

Do not add an init process because:

```text
production containers must always have one.
```

Understand the workload.

# 160. Application

Create:

```text
app.py
```

with:

```python
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
import hashlib
import json
import os
import signal
import sys
import time


running = True


def shutdown(signum, frame):
    global running

    print(
        f"Received signal {signum}",
        flush=True
    )

    print(
        "Beginning graceful shutdown",
        flush=True
    )

    running = False

    server.shutdown()


class Handler(BaseHTTPRequestHandler):

    def send_json(self, status, payload):

        body = json.dumps(payload).encode()

        self.send_response(status)

        self.send_header(
            "Content-Type",
            "application/json"
        )

        self.send_header(
            "Content-Length",
            str(len(body))
        )

        self.end_headers()

        self.wfile.write(body)

    def do_GET(self):

        if self.path == "/health":

            self.send_json(
                200,
                {
                    "status": "ok",
                    "pid": os.getpid()
                }
            )

            return

        if self.path == "/cpu":

            value = b"veriqta-runtime-lab"

            for _ in range(500000):
                value = hashlib.sha256(value).digest()

            self.send_json(
                200,
                {
                    "status": "cpu-work-complete"
                }
            )

            return

        if self.path == "/memory":

            data = [
                bytearray(1024 * 1024)
                for _ in range(50)
            ]

            time.sleep(2)

            self.send_json(
                200,
                {
                    "status": "memory-work-complete",
                    "allocated_blocks": len(data)
                }
            )

            return

        self.send_json(
            404,
            {
                "error": "not found"
            }
        )


server = ThreadingHTTPServer(
    ("0.0.0.0", 8080),
    Handler
)


signal.signal(
    signal.SIGTERM,
    shutdown
)

signal.signal(
    signal.SIGINT,
    shutdown
)


print(
    "Runtime lab listening on port 8080",
    flush=True
)


try:
    server.serve_forever()

finally:

    server.server_close()

    print(
        "Runtime lab stopped cleanly",
        flush=True
    )
```

This is an educational runtime lab, not a production web server.

# 195. Final Mental Model

A production container is not:

```text
Image
↓
docker run
↓
Finished
```

The real runtime model is:

```text
IMAGE
   ↓
CONTAINER CREATED
   ↓
PID NAMESPACE
   ↓
PID 1 STARTS
   ↓
CHILD PROCESSES / THREADS
   ↓
APPLICATION BEGINS WORK
   ↓
CPU + MEMORY + PIDS + FILE DESCRIPTORS
   ↓
CGROUP RESOURCE CONTROL
   ↓
HEALTH CHECKS
   ↓
RUNTIME METRICS
   ↓
LOAD
   ↓
RESOURCE PRESSURE
   ↓
NORMAL OPERATION
       OR
DEGRADATION
       OR
FAILURE
   ↓
LOGS + METRICS + STATE + EVENTS
   ↓
ROOT CAUSE
   ↓
RECOVERY
```

When shutdown begins:

```text
Docker
   ↓
SIGTERM
   ↓
PID 1
   ↓
Application stops accepting work
   ↓
Active work finishes
   ↓
Connections close
   ↓
Resources released
   ↓
Process exits
```

If that does not happen before the timeout:

```text
SIGKILL
   ↓
Immediate termination
```

And when resource pressure occurs:

```text
Load
   ↓
CPU / Memory / Processes / FDs increase
   ↓
Resource limit approached
   ↓
Latency / errors / pressure
   ↓
Possible failure
   ↓
Evidence
   ↓
Diagnosis
   ↓
Right-size or fix application
   ↓
Retest
```

The core lesson of Part 14 is:

```text
A container being "Up" tells you very little about whether the workload is operating correctly.
```

A production engineer must understand:

```text
Processes
+
Signals
+
Resources
+
Health
+
Metrics
+
Failure Evidence
+
Recovery
```

The investigation loop is:

```text
Load
→ Resource Pressure
→ Failure
→ Evidence
→ Limit
→ Recover
→ Verify
```

That is how you move from simply running containers to understanding container runtime behavior.
