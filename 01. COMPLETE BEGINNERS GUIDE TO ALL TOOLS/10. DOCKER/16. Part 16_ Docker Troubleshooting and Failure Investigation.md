# Part 16: Docker Troubleshooting and Failure Investigation

## Diagnose Docker Failures Systematically Instead of Guessing

A container fails.

What do you do?

A beginner often starts doing this:

```text
restart container
change Dockerfile
rebuild image
change port
delete container
recreate container
restart Docker
change permissions
search the error online
try another command
```

Eventually something may work.

But you still may not know:

```text
what failed
why it failed
which layer failed
whether your change actually fixed the root cause
whether the same failure will happen again
```

That is not troubleshooting.

That is experimentation without a method.

Production troubleshooting should look like this:

```text
Symptom
   ↓
Container State
   ↓
Logs
   ↓
Inspect
   ↓
Process
   ↓
Network
   ↓
Storage
   ↓
Resources
   ↓
Configuration
   ↓
Root Cause
   ↓
Fix
   ↓
Verify
```

This investigation model is the foundation of Part 16.

By the end of this part, when someone says:

```text
"The Docker application is down."
```

you should not immediately restart Docker.

You should begin asking:

```text
What exactly is the symptom?

Does the container exist?

Is it running?

Did it exit?

Is it restarting?

What is the exit code?

Was it OOMKilled?

What do the logs show?

What process is actually running?

What ports are published?

What networks is it connected to?

Can DNS resolve the dependency?

Are the expected mounts present?

Is the disk full?

Are CPU or memory exhausted?

Are environment variables correct?

What changed?

What evidence proves the root cause?
```

That is the difference between:

```text
using Docker
```

and:

```text
operating Docker systems.
```

# 2. Troubleshooting Is Evidence Collection

Imagine this symptom:

```text
The website does not open.
```

That tells us almost nothing.

Possible causes include:

```text
container not running
application process crashed
wrong host port
wrong container port
application bound only to localhost
firewall problem
Docker network problem
DNS failure
dependency failure
health failure
CPU exhaustion
memory exhaustion
disk full
incorrect configuration
```

Therefore:

```text
SYMPTOM ≠ ROOT CAUSE
```

A symptom tells you what someone observed.

Your job is to discover the mechanism that caused it.

# 3. The VERIQTA Docker Investigation Model

Use this sequence:

```text
SYMPTOM
   ↓
CONTAINER STATE
   ↓
LOGS
   ↓
INSPECT
   ↓
PROCESS
   ↓
NETWORK
   ↓
STORAGE
   ↓
RESOURCES
   ↓
CONFIGURATION
   ↓
ROOT CAUSE
   ↓
FIX
   ↓
VERIFY
```

Do not treat this as a rigid rule that every incident requires every step.

It is a mental framework.

The evidence may identify the problem early.

But this sequence prevents random troubleshooting.

---

# 4. Step 1: Define the Symptom

Bad incident description:

```text
Docker is broken.
```

Better:

```text
The frontend returns connection refused on host port 8080.
```

Better:

```text
The API container starts, exits with code 1 within two seconds,
and logs report that DB_HOST is missing.
```

Precise symptoms narrow the search.

# 5. Questions to Ask First

Ask:

```text
What exactly failed?

When did it begin?

Was it ever working?

What changed?

Is one container affected or several?

Is one host affected?

Is the failure constant or intermittent?

Can it be reproduced?

What was the last known working state?
```

Especially important:

```text
What changed?
```

Examples:

```text
new image
new Dockerfile
new Compose file
new environment variable
new secret
new bind mount
new volume
new host
new Docker version
new application release
new network configuration
```

# 6. Step 2: Check Container State

Start with:

```bash
docker ps
```

This shows running containers.

Then:

```bash
docker ps -a
```

This includes stopped containers.

You may discover:

```text
Up
Exited
Restarting
Created
Paused
```

The state immediately changes your investigation.

# 7. Why `docker ps -a` Matters

Suppose:

```bash
docker ps
```

shows nothing.

A beginner might conclude:

```text
The container does not exist.
```

But:

```bash
docker ps -a
```

may show:

```text
veriqta-api    Exited (1) 8 seconds ago
```

Now you know:

```text
container exists
↓
container started
↓
main process exited
```

That is much more useful.

# 11. Step 5: Inspect Processes

For a running container:

```bash

```

Example:

```bash

```

You can also enter the container when appropriate:

```bash

  -it \
```

Check:


# 16. Step 10: Identify Root Cause

Root cause should explain the evidence.

Bad:

```text
Docker had a problem.
```

Better:

```text
The API could not reach PostgreSQL.
```

Better:

```text
The API used DB_HOST=localhost.

Inside the API container, localhost referred to the API container itself,
not the PostgreSQL container.

The application therefore attempted to connect to PostgreSQL on
127.0.0.1:5432 and received connection refused.
```

That explains the mechanism.

---

# 17. Step 11: Fix

A fix should target the root cause.

For the previous example:

```text
DB_HOST=postgres
```

where:

```text
postgres
```

is the Docker/Compose service name reachable through Docker DNS.

---

# 18. Step 12: Verify

Never stop at:

```text
I changed it.
```

Verify:

```text
container running
health check passing
dependency reachable
application request successful
logs clean
resource behavior expected
failure no longer reproducible
```

The troubleshooting cycle ends with evidence.

# 19. Failure 1: Container Exits Immediately

Run:

```bash
docker run \
  --name exit-lab \
  alpine \
  sh -c 'echo "Starting"; exit 1'
```

Now:

```bash
docker ps
```

The container is gone from the running list.

Check:

```bash
docker ps -a
```

You should see something similar to:

```text
Exited (1)
```

---

# 20. Why Containers Exit

A container normally lives as long as its main process lives.

Mental model:

```text
Container starts
     ↓
PID 1 starts
     ↓
PID 1 runs
     ↓
PID 1 exits
     ↓
Container stops
```

A container is not automatically a permanent mini-server.

---

# 22. Common Immediate-Exit Causes

Examples:


# 23. Failure 2: Container Continuously Restarts

Restart loops usually involve:

```text
application exits
+
restart policy restarts it
```

Example architecture:

```text
Start
 ↓
Crash
 ↓
Restart Policy
 ↓
Start
 ↓
Crash
 ↓
Restart
```

---

# 24. Detect Restart Loop

Run:

```bash
docker ps
```

You may see:

```text
Restarting
```

Inspect restart count:

```bash
docker inspect \
  --format '{{.RestartCount}}' \
  CONTAINER
```

Then inspect logs:

```bash
docker logs \
  --tail 100 \
  CONTAINER
```

---

# 25. Do Not Blame the Restart Policy

The restart policy usually did not cause the original crash.

It exposed it repeatedly.

Investigate:

```text
Why does PID 1 exit?
```

Then decide whether the restart policy is appropriate.

# 28. Inspect Published Ports

Run:

```bash
docker port CONTAINER
```

Example:

```bash
docker port veriqta-web
```

You may see:

```text
80/tcp -> 127.0.0.1:8080
```

Meaning:

```text
Host 127.0.0.1:8080
        ↓
Container port 80
```

---

# 29. Wrong Port Mapping

Suppose application listens on:

```text
container port 5000
```

but you run:

```bash
docker run \
  -p 8080:8000 \
  IMAGE
```

Docker forwards:

```text
host 8080
↓
container 8000
```

But nothing listens on:

```text
8000
```

Result:

```text
application inaccessible
```

---

# 30. Correct Port Mapping

If application listens on:

```text
5000
```

use:

```bash
docker run \
  -p 8080:5000 \
  IMAGE
```

Mental model:

```text
-p HOST_PORT:CONTAINER_PORT
```

Not:

```text
application port : host port
```

---

# 31. Verify the Application Port

Inside the container, depending on installed tools:

```bash
docker exec \
  CONTAINER \
  ss -lnt
```

But minimal images may not contain `ss`.

You can instead:

```text
inspect application configuration
inspect application logs
use an appropriate diagnostic container
```

Do not install random debugging packages into a production container merely to investigate it unless your operational process explicitly permits it.

---

# 32. Application Binding Problem

Suppose the application inside the container binds to:

```text
127.0.0.1:5000
```

That means:

```text
loopback interface inside container
```

Publishing port 5000 does not automatically make a process bound only to container loopback reachable externally.

Containerized servers commonly need to listen on:

```text
0.0.0.0
```

when they should accept traffic through the container network interface.

---

# 33. Failure 4: Connection Refused

`Connection refused` usually means:

```text
you reached the destination host
but nothing accepted the connection on that port
```

Possible causes:

```text
service not running
wrong port
service bound to wrong address
service crashed
dependency still starting
wrong destination
```

It is different from:

```text
DNS resolution failure
```

and different from:

```text
connection timeout
```

Those symptoms suggest different investigation paths.

---

# 34. Connection Refused Investigation

Follow:

```text
Destination correct?
↓
DNS resolves?
↓
Port correct?
↓
Process running?
↓
Process listening?
↓
Correct interface?
↓
Network path valid?
```

Do not jump directly to:

```text
Docker networking is broken.
```

---

# 35. Failure 5: DNS Failure

Suppose backend connects to:

```text
postgres
```

but receives:

```text
name or service not known
```

or another resolution-related error.

Investigate:

```text
Are both containers on the same user-defined network?

Is the hostname/service name correct?

Does the target container exist?

Is Docker DNS available on that network?
```

A temporary diagnostic container can be extremely useful.

Example:

```bash
docker run \
```

# 38. Do Not Hard-Code Container IPs

A container IP may change when the container is recreated.

Prefer:

```text
service names
container names where appropriate
network aliases
```

over:

```text
172.18.0.7
```

for normal service discovery.

# 39. Failure 6: Containers Cannot Communicate

Architecture:

```text
Frontend
   ↓
Backend
   ↓
Database
```

Suppose:

```text
frontend → backend
```

fails.

```text

```

# 40. Internal Port vs Published Port

Suppose:

```text
backend listens on 5000
```

and host mapping is:

```text
8081:5000
```

Another container on the same Docker network normally connects to:

```text
backend:5000
```

not:

```text
backend:8081
```

Why?

Because:

```text
8081
```

is the host-published port.

Container-to-container communication uses the destination container's listening port.

```bash
docker build \
```

# 46. Read Build Output From the First Relevant Error

Do not focus only on:

```text
ERROR: failed to solve
```

at the bottom.

That may be a summary.

Look upward for the build step that actually failed.

Example:

```text
RUN npm ci
```

then:

```text
npm error ...
```

That application/package error may be the actual clue.

---

# 47. Identify the Failed Dockerfile Instruction

Build output identifies stages and instructions.

Ask:

```text
Which stage failed?

Which instruction failed?

What command executed?

What files existed at that moment?

What working directory was active?

What network access was required?
```

This makes build debugging systematic.

---

# 48. Build Context

If you run:

```bash
docker build .
```

then:

```text
.
```

is the build context.

A Dockerfile cannot simply `COPY` arbitrary files from anywhere on your machine.

The files must be available through the build context or another supported build source/mount mechanism.

---

# 49. Missing Build File

Project:

```text
project/
├── Dockerfile
└── app/
    └── main.py
```

Wrong:

```dockerfile
COPY main.py /app/main.py
```

because:

```text
main.py
```

is not at the root of the build context.

Correct:

```dockerfile
COPY app/main.py /app/main.py
```

assuming:

```bash
docker build .
```

from `project/`.

---

# 50. `.dockerignore` Can Cause Missing Files

Suppose:

```text
.dockerignore
```

contains:

```text
config/
```

but Dockerfile contains:

```dockerfile
COPY config/app.conf /app/app.conf
```

The build may fail because the file was excluded from the context.

Therefore investigate:

```text
file exists?
↓
correct context?
↓
correct path?
↓
excluded by .dockerignore?
```

---

# 51. Failure 9: Build Cache Confusion

Symptom:

```text
I changed something but Docker keeps using the old result.
```

Do not immediately assume Docker is broken.

Understand the build cache.

Docker reuses build results when the relevant instruction and its dependencies still match cached results.

When a layer becomes invalid, downstream layers must be rebuilt.

---

# 52. Observe Cache Behavior

Build:

```bash
docker build \
  --progress=plain \
  -t cache-lab .
```

Build again.

You may see cached steps.

Now change a source file and rebuild.

Observe which steps rebuild.

---

# 53. Cache-Friendly Dockerfile

Less efficient:

```dockerfile
FROM node:22-alpine

WORKDIR /app

COPY . .

RUN npm ci

CMD ["node", "server.js"]
```

A source-code change can invalidate the `COPY` layer and therefore force:

```text
npm ci
```

to run again.

---

# 54. Better Layer Ordering

```dockerfile
FROM node:22-alpine

WORKDIR /app

COPY package.json package-lock.json ./

RUN npm ci

COPY . .

CMD ["node", "server.js"]
```

Now ordinary source changes do not necessarily invalidate the dependency-installation layer.

This is build engineering, not merely troubleshooting.

---

# 55. Build Without Cache

For diagnosis:

```bash
docker build \
  --no-cache \
  -t veriqta-app:test \
  .
```

Compose:

```bash
docker compose build \
  --no-cache
```

But:

```text
--no-cache
```

should not become your permanent response to every build issue.

Understand why cache behavior differs first.

---

# 56. Pull Fresh Base Image

Cache and base-image freshness are separate concerns.

When appropriate:

```bash
docker build \
  --pull \
  -t veriqta-app:test \
  .
```

can request a newer referenced base image.

You can combine diagnostic options where justified.

---

# 57. BuildKit Cache Mount Confusion

A BuildKit cache mount such as:

```dockerfile
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install -r requirements.txt
```

creates persistent build cache for the package manager.

It is not:

```text
application data
```

and is not automatically:

```text
part of the final image.
```

Do not confuse:

```text
build cache
container filesystem
volume data
```

They solve different problems.

# 63. Absolute vs Relative Paths

Relative:

```text
./config/app.json
```

depends on current working directory.

Absolute:

```text
/app/config/app.json
```

does not.

This does not mean every application should use absolute paths everywhere.

It means you must understand what directory relative paths are relative to.

---

# 64. Failure 12: Permission Denied

Symptom:

```text
Permission denied
```

Possible causes:

```text
wrong file owner
wrong directory owner
missing execute bit
container runs as non-root
bind-mounted host permissions
volume ownership
read-only filesystem
SELinux policy
AppArmor restrictions
dropped capability
```

Do not solve every permission problem with:

```text
chmod 777
```

---

# 65. Why `chmod 777` Is Usually a Bad Shortcut

`777` gives:

```text
owner: read/write/execute
group: read/write/execute
others: read/write/execute
```

That may hide the real ownership problem and unnecessarily weaken security.

Instead ask:

```text
Which user runs the process?

Which UID/GID?

Who owns the file?

Which permission is actually required?
```

---

# 66. Inspect Container User

Run:

```bash
docker inspect \
  --format '{{.Config.User}}' \
  CONTAINER
```

An empty result often means the image did not explicitly configure a non-root user and the runtime default applies.

Also inspect from inside where possible:

```bash
docker exec \
  CONTAINER \
  id
```

---

# 67. Inspect File Ownership

Inside the container:

```bash
ls -ln /app
```

Numeric IDs can be especially useful because Linux permissions ultimately use:

```text
UID
GID
```

not merely display names.

---

# 68. `COPY --chown`

Part 11 introduced:

```dockerfile
COPY --chown=appuser:appgroup . /app
```

This can ensure application files have appropriate ownership during image construction.

It is usually better than starting the container as root and changing ownership every time the container starts.

---

# 69. Bind Mount Permissions

Suppose:

```bash
docker run \
  -v "$PWD/data:/app/data" \
  IMAGE
```

The application process inside the container must still interact with permissions associated with the mounted host files.

The container cannot ignore host filesystem security simply because Docker mounted the path.

---

# 70. SELinux Context

On SELinux-enabled hosts, Unix ownership/mode bits may look correct while access is still denied because of security labels.

Therefore:

```text
permission denied
```

may involve:

```text
UID/GID
mode bits
read-only mount
SELinux
AppArmor
capabilities
```

Troubleshoot the actual mechanism.

Do not disable host security controls globally just to make a container start.

# 71. Failure 13: Volume Data Missing

Symptom:


Do not panic and immediately create another volume.

First determine:

```text

```



# 73. Volume Mounted to Wrong Path

Suppose PostgreSQL writes data to:

```text

```

but your volume is mounted at:

```text
/some/other/path
```

Then your volume may remain nearly empty while the database writes into the container writable layer.

Deleting the container could then remove that data.

Always verify the application's actual data path for the exact image/version you use.

# 74. Named Volume Identity

These may not necessarily refer to the same actual Compose-created volume:

```text

```

and:

```text
projectB_db-data
```

Compose project naming affects generated resource names.

If your project identity changes, you may accidentally create a new empty volume and think the original data disappeared.

Investigate before deleting anything.

---

# 75. Never Delete Storage During Investigation

Avoid:

```bash

```

or:

```bash

```

while investigating missing data unless you fully understand what will be deleted.

Troubleshooting should preserve evidence.

# 76. Failure 14: Bind Mount Hides Container Files

This is a classic Docker failure.

Suppose image contains:

```text
/app/
├── server.py
├── config.json
└── static/
```

Then you run:

```bash
docker run \
  -v "$PWD:/app" \
  IMAGE
```

If the host directory contains only:

```text
README.md
```

then inside the running container `/app` may appear to contain only the mounted host content.

The image files have not necessarily been deleted.

They are:

```text
obscured by the mount.
```

---

# 77. Mental Model for Mount Obscuring

Before mount:

```text
Container /app
├── server.py
├── config.json
└── static/
```

Host:

```text
Host ./project
└── README.md
```

After bind mount:

```text
Host ./project
        ↓
mounted on
        ↓
Container /app
        ↓
README.md visible
```

The original `/app` contents are hidden while that mount exists.

---

# 78. Diagnose Hidden Files

Inspect mounts:

```bash
docker inspect \
  --format '{{json .Mounts}}' \
  CONTAINER
```

Then create a container without the bind mount:

```bash
docker run \
  --rm \
  IMAGE \
  ls -la /app
```

If files appear there:

```text
image contains files
mount hides files
```

Root cause identified.

---

# 79. Fix Bind-Mount Obscuring

Possible fixes:

```text
mount correct host directory
mount a narrower subdirectory
mount configuration to a specific file
remove unnecessary bind mount
use a named volume where appropriate
```

Do not rebuild the image if the image itself is correct.

# 117. Docker Group Security Warning

Adding a user to the:

```text
docker
```

group is not a trivial permission change.

Docker's documentation warns that membership effectively provides root-level privileges on the host.

Therefore:

```text

```

is not a safe general solution.

Understand the trust implications.

# 118. Socket Mount Risk


Do not mount the Docker socket into arbitrary containers.

Part 13 covered this security boundary.

# 124. Port Collision in Compose

Two services cannot normally bind the same host IP and host port simultaneously.

Example:

```yaml
services:

  app1:
    ports:
      - "8080:80"

  app2:
    ports:
      - "8080:80"
```

The second binding may fail because host port:

```text
8080
```

is already occupied.

## Habit 2

Problem:


## Habit 3

```text

```

Problem:

```text

```

## Habit 4


Problem:

## Habit 5

# 152. Change One Variable at a Time

Suppose application cannot reach database.

Do not simultaneously:

```text
change network
change port
change password
change image
restart Docker
rebuild application
```

If it works afterward, you still do not know why.

Instead:

```text
form hypothesis
↓
change one relevant variable
↓
test
↓
observe
```

# 153. Root Cause vs Trigger

These can differ.

Example:

```text
Trigger:
traffic doubled.

Root cause:
application retained request objects indefinitely and eventually exceeded memory limit.
```

Traffic exposed the defect.

Traffic itself may not be the underlying engineering failure.

# 154. Root Cause vs Contributing Factor

Example:

```text
Root cause:
wrong database hostname.

Contributing factor:
health check did not test database connectivity.

Contributing factor:
deployment pipeline had no integration test.

Contributing factor:
alert did not fire for 12 minutes.
```

Good incident investigation can identify more than one improvement.

```text
users no longer receive HTTP 502
```

not merely:

Running is not the same as functional.

```text
What do its logs say?

```

# 163. Final Troubleshooting Mental Model

When something fails, do not begin with:

```text
What command can I try?
```

Begin with:

```text
What evidence do I have?
```

Then follow:

```text
SYMPTOM
   ↓
What exactly is broken?
   ↓
CONTAINER STATE
   ↓
Does it exist?
Running?
Exited?
Restarting?
Unhealthy?
   ↓
LOGS
   ↓
What did the application report?
   ↓
INSPECT
   ↓
What did Docker actually configure?
   ↓
PROCESS
   ↓
What is PID 1 doing?
What processes exist?
   ↓
NETWORK
   ↓
Ports?
DNS?
Networks?
Connectivity?
   ↓
STORAGE
   ↓
Mounts?
Volumes?
Files?
Permissions?
Disk?
   ↓
RESOURCES
   ↓
CPU?
Memory?
OOM?
PIDS?
   ↓
CONFIGURATION
   ↓
Environment?
Command?
Working directory?
Image?
Platform?
Compose?
   ↓
CORRELATE
   ↓
Which evidence explains the symptom?
   ↓
ROOT CAUSE
   ↓
What mechanism actually produced the failure?
   ↓
FIX
   ↓
Change the mechanism.
   ↓
VERIFY
   ↓
Re-test the original symptom.
```

The most important rule in this entire part is:

```text
Do not troubleshoot Docker by guessing.

Troubleshoot Docker by reducing uncertainty with evidence.
```

A strong engineer does not simply know more Docker commands.

A strong engineer knows:

```text
which question to ask
↓
which evidence to collect
↓
which layer to investigate
↓
how to test a hypothesis
↓
how to identify root cause
↓
how to verify recovery
```

That is Docker failure investigation.
