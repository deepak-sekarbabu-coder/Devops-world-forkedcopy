# Part 8: Docker Networking: How Containers Communicate

## Internet → Host Port → Docker NAT/Bridge → Container Port → Application

A container can run perfectly and still be useless if nobody can reach it.

Imagine you start an Nginx container:

```bash
docker run -d --name web nginx
```

Docker reports that the container is running.

You check:

```bash
docker ps
```

and see Nginx.

But opening:

```text
http://localhost
```

in your browser may not reach that container.

Why?

Because:

```text
Application running
```

does not automatically mean:

```text
Application published to the host
```

or:

```text
Application reachable from the Internet
```

Networking determines how traffic reaches containers and how containers communicate with each other.

By the end of this part, you should understand:

* Why containers need networking
* Network namespaces
* Container IP addresses
* Docker network drivers
* Docker bridge networking
* The default bridge
* User-defined bridge networks
* Virtual Ethernet interfaces
* The Docker bridge interface
* NAT
* Port publishing
* Host ports
* Container ports
* `EXPOSE`
* DNS
* Container-name resolution
* Container-to-container communication
* Network isolation
* Host networking
* None networking
* Overlay networking concepts
* Creating networks
* Connecting and disconnecting containers
* Inspecting networks
* Troubleshooting failed connectivity

Most importantly, you should be able to reason through:

```text
Client
  ↓
Host
  ↓
Docker networking
  ↓
Container
  ↓
Application
```

instead of randomly changing ports until something works.

---

# 1. Why Containers Need Networking

Most useful applications communicate with something else.

A web application may need to communicate with:

```text
Browser
Database
Cache
API
Message queue
Monitoring system
External service
```

For example:

```text
Browser
   ↓
Frontend
   ↓
Backend API
   ↓
Database
```

If these components run in different containers, they need a way to exchange network traffic.

---

# 2. A Real Multi-Container Example

Imagine:

```text
Frontend Container
Backend Container
PostgreSQL Container
Redis Container
```

The frontend needs:

```text
Backend
```

The backend needs:

```text
PostgreSQL
Redis
External APIs
```

Users need:

```text
Frontend
```

But users probably should **not** directly access:

```text
PostgreSQL
Redis
```

Networking therefore solves two problems:

```text
Connectivity
+
Isolation
```

Good networking is not simply:

> Make everything reachable.

It is:

> Make the correct services reachable by the correct systems.

---

# 3. Networking Questions Every Engineer Should Ask

For any containerized service, ask:

```text
Who initiates the connection?

What destination are they trying to reach?

Which hostname or IP are they using?

Which port are they using?

Which network contains the destination?

Is the application listening?

Which interface is it listening on?

Is the port published?

Does DNS resolve correctly?

Is routing available?

Is traffic intentionally isolated?

Is a firewall or security policy blocking it?
```

These questions will become your troubleshooting framework.

---

# 4. First Networking Mental Model

Consider:

```text
Internet
   ↓
Docker Host
   ↓
Container
   ↓
Application
```

The application may listen on:

```text
port 80
```

inside the container.

But that does not automatically mean the host listens on port 80 for that container.

These are different networking contexts.

---

# 5. What Is a Network Namespace?

Linux provides a feature called a:

```text
network namespace
```

A network namespace gives processes an isolated view of networking resources.

A namespace can have its own:

```text
Network interfaces
IP addresses
Routing table
Loopback interface
Ports
Network-related state
```

Docker uses Linux network namespaces as part of container networking isolation.

---

# 6. Why Network Namespaces Matter

Without network isolation, every container process would simply share the host networking environment directly.

Instead, Docker can create something conceptually like:

```text
Host Network Namespace
│
├── eth0
├── host IP
└── host routes


Container A Network Namespace
│
├── eth0
├── container IP
└── container routes


Container B Network Namespace
│
├── eth0
├── different container IP
└── container routes
```

Each container can behave as though it has its own network environment.

---

# 7. Network Namespace Does Not Mean a Separate Physical Network Card

A container does not normally receive a physical Ethernet adapter.

Instead, Linux networking creates virtual networking components.

Docker combines technologies such as:

```text
Network namespaces
Virtual Ethernet interfaces
Linux bridges
Routing
NAT
Firewall/netfilter rules
```

to create container connectivity.

---

# 8. Container IP Addresses

On bridge networks, containers commonly receive their own IP addresses within Docker-managed network subnets.

Example:

```text
Docker Network:
172.18.0.0/16

Container A:
172.18.0.2

Container B:
172.18.0.3

Container C:
172.18.0.4
```

These are example addresses only.

Do not assume Docker will always use those exact values.

Inspect the actual environment.

---

# 9. Container IP Addresses Are Usually Not Application Configuration

A common beginner mistake is hardcoding:

```text
172.18.0.3
```

into application configuration.

That is fragile.

Containers can be:

```text
Removed
Recreated
Moved
Reconnected
Assigned different addresses
```

A better approach on user-defined Docker networks is usually to use DNS names such as:

```text
database
```

rather than hardcoded container IPs.

We will prove this later.

---

# 14. What Is a Network Driver?

A network driver determines how Docker implements a network's connectivity model.

For example:

```text
bridge
→ isolated networking between containers on a Docker host

host
→ container uses the host networking namespace/model directly on supported platforms

none
→ container has networking effectively disabled except loopback/basic namespace state

overlay
→ networking designed to connect containers/services across multiple Docker hosts in swarm-style environments
```

Do not treat all Docker networks as the same thing with different names.

The driver changes the networking behavior.

---

# 15. Docker Bridge Networking

The bridge driver is Docker's common networking model for containers running on one Docker host.

Conceptually:

```text
Container A
    │
    │
Container A virtual interface
    │
    ↓
Linux Bridge
    ↑
    │
Container B virtual interface
    │
    │
Container B
```

The bridge acts like a virtual Layer 2 networking component connecting interfaces on the host.

---

# 16. What Is a Network Bridge?

A physical Ethernet switch connects devices on a network.

A Linux bridge performs a similar conceptual role for virtual interfaces.

Simplified:

```text
Container A ──┐
              │
Container B ──┼── Linux Bridge
              │
Container C ──┘
```

Docker configures bridge networking so connected containers can exchange traffic according to the network's rules and configuration.

---

# 17. The Default Docker Bridge

On native Linux Docker Engine, Docker commonly creates a default bridge network named:

```text
bridge
```

and a Linux bridge interface commonly called:

```text
docker0
```

You can inspect Docker's network:

```bash
docker network inspect bridge
```

On Linux, you may inspect host interfaces with:

```bash
ip addr
```

and potentially see:

```text
docker0
```

---

# 18. `docker0`

Conceptually:

```text
Host
│
├── eth0
│    ↓
│  outside network
│
└── docker0
     │
     ├── container A
     ├── container B
     └── container C
```

`docker0` is associated with Docker's default bridge networking on native Linux.

Do not assume every custom Docker bridge network simply uses `docker0`.

User-defined bridge networks have their own Linux networking structures.

---

# 19. Docker Desktop Difference

On macOS and Windows, Docker Desktop runs Linux containers through a Linux virtualized environment.

Therefore, Docker networking is not identical to native Linux host networking.

For example, you should not assume that:

```text
docker0
```

will appear as a normal macOS or Windows host interface exactly as it does on a Linux Docker host.

The conceptual networking model still matters, but implementation boundaries differ.

---

# 20. What Is veth?

Linux commonly connects network namespaces using:

```text
virtual Ethernet pairs
```

often abbreviated:

```text
veth
```

Think of a veth pair as a virtual cable with two ends.

Traffic entering one end can emerge from the other.

---

# 21. veth Mental Model

Conceptually:

```text
Container Network Namespace
        │
        │ eth0
        │
    [veth end]
        ║
        ║ virtual link
        ║
    [veth end]
        │
        ↓
    Linux Bridge
```

One end appears inside the container namespace, commonly as:

```text
eth0
```

The peer exists on the host side and connects into the bridge architecture.

---

# 22. Multiple Containers on a Bridge

Now:

```text
Container A
  eth0
    │
  veth
    │
    ├────────────┐
                 ↓
             Bridge
                 ↑
    ├────────────┘
    │
  veth
    │
  eth0
Container B
```

This provides the basic virtual connectivity needed for containers on the same bridge network.

---

# 23. Container Networking Path

Suppose:

```text
Container A
```

sends traffic to:

```text
Container B
```

on the same user-defined bridge.

Simplified path:

```text
Application A
     ↓
Container A network namespace
     ↓
Container A eth0
     ↓
veth pair
     ↓
Linux bridge
     ↓
Container B veth
     ↓
Container B eth0
     ↓
Application B
```

This is much more useful than thinking:

> Docker magically connects containers.

---

# 24. Default Bridge vs User-Defined Bridge

Docker provides the default:

```text
bridge
```

but you can create your own bridge networks.

Example:

```bash
docker network create app-network
```

By default, Docker creates a bridge network for this command unless another driver is specified.

Check:

```bash
docker network ls
```

You should see:

```text
app-network
```

---

# 25. Why User-Defined Bridge Networks Matter

User-defined bridge networks provide better application organization and service discovery than relying on the legacy/default bridge behavior.

They allow you to create:

```text
frontend-network
backend-network
database-network
monitoring-network
```

depending on architecture.

More importantly for normal application stacks, containers on a user-defined bridge network can use Docker's embedded DNS/service discovery behavior to resolve container names or aliases.

# 31. Container Name Resolution

On a user-defined network, Docker provides DNS-based name resolution for connected containers.

This means:

```text
web-one
```

can reach:

```text
web-two
```

by name rather than hardcoding its current IP address.

Architecture:

```text
web-one
   │
   │ asks for "web-two"
   ↓
Docker DNS
   ↓
web-two network address
   ↓
web-two
```

---

# 32. Why DNS Is Better Than Hardcoded IPs

Imagine:

```text
database = 172.20.0.3
```

Your backend configuration says:

```text
DB_HOST=172.20.0.3
```

The database container is recreated.

Its address becomes:

```text
172.20.0.7
```

Your application configuration breaks.

Instead:

```text
DB_HOST=database
```

Docker's service discovery can resolve the name to the current network address.

This is much more appropriate for replaceable containers.

---

# 33. What Is DNS?

DNS means:

```text
Domain Name System
```

At a high level, DNS translates names into network addresses.

Internet example:

```text
example.com
      ↓
DNS
      ↓
IP address
```

Docker networking uses DNS/service discovery concepts internally too.

Example:

```text
database
    ↓
Docker DNS
    ↓
container address
```

---

# 34. Docker Embedded DNS

On user-defined networks, Docker provides embedded DNS behavior to containers.

Applications can use container names and network aliases instead of manually tracking IP addresses.

This becomes extremely important in Part 9:

```text
Frontend
   ↓
backend

Backend
   ↓
database
```

rather than:

```text
Frontend
   ↓
172.x.x.x

Backend
   ↓
172.x.x.x
```

# 37. Important: Internal Connectivity vs External Connectivity

These are different problems.

## Internal

```text

    ↓
Docker Network
    ↓
Container B
```

## External

```text
Browser
   ↓
Host
   ↓
Published Port
   ↓
Container
```

Do not confuse them.

# 38. Container Ports

An application inside a container listens on a port.

Nginx normally listens on:

```text
80
```

inside the container.

That is the:

```text
container port
```

Conceptually:

```text
Nginx process
    ↓
Container port 80
```

---

# 39. Host Ports

Your Docker host also has its own network namespace and ports.

Examples:

```text
Host port 22
Host port 80
Host port 443
Host port 8080
```

A host port and container port are not automatically the same thing.

---

# 40. Host Port vs Container Port

Suppose you run:

```bash
docker run -d \
  --name public-web \
  -p 8080:80 \
  nginx
```

This means:

```text
Host port 8080
       ↓
Container port 80
```

Not:

```text
Container port 8080
       ↓
Host port 80
```

The order matters.

Remember:

```text
-p HOST_PORT:CONTAINER_PORT
```

---

# 41. Full Published-Port Architecture

For:

```bash
docker run -d \
  --name public-web \
  -p 8080:80 \
  nginx
```

traffic looks conceptually like:

```text
Browser
   │
   │ http://host:8080
   ↓
Docker Host
   │
   │ host port 8080
   ↓
Docker networking / NAT
   ↓
Container network
   │
   │ container port 80
   ↓
Nginx
```

This is the core Part 8 architecture:

```text
Internet
   ↓
Host Port
   ↓
Docker NAT / Bridge
   ↓
Container Port
   ↓
Application
```

---

# 42. What Is Port Publishing?

Port publishing tells Docker to make a container port reachable through a port/address on the Docker host.

Syntax:

```bash
-p HOST_PORT:CONTAINER_PORT
```

Example:

```bash
-p 8080:80
```

means:

```text
connections reaching the configured host port 8080
       ↓
forward toward
       ↓
container port 80
```

---

# 43. Verify Published Ports

Run:

```bash
docker ps
```

You may see something similar to:

```text
0.0.0.0:8080->80/tcp
```

Depending on environment, IPv6 information may also appear.

You can also run:

```bash
docker port public-web
```

Typical output:

```text
80/tcp -> 0.0.0.0:8080
```

---

# 44. Test the Published Port

On the Docker host:

```bash
curl http://localhost:8080
```

or open:

```text
http://localhost:8080
```

in a browser.

You should receive the Nginx page.

---

# 45. What Is NAT?

NAT means:

```text
Network Address Translation
```

At a high level, NAT allows network addresses and/or ports to be translated as traffic crosses networking boundaries.

Docker uses Linux networking and netfilter/NAT mechanisms as part of bridge networking and port publishing on Linux.

Simplified:

```text
Host:8080
    ↓
translation / forwarding
    ↓
Container-IP:80
```

---

# 46. Why NAT Is Useful Here

Your container may have an internal address such as:

```text
172.20.0.5
```

But an external client does not need to know or directly route to that internal container address.

Instead:

```text
Client
  ↓
Host IP:8080
  ↓
Docker networking
  ↓
172.20.0.5:80
```

The Docker host becomes the externally reachable entry point.

---

# 47. NAT Is Not the Application

If:

```text
host port 8080
```

correctly forwards to:

```text
container port 80
```

but Nginx is not listening on port 80, the application still fails.

Networking cannot make a nonexistent listener respond.

You need all layers:

```text
Published host port
      ↓
Network path
      ↓
Correct container port
      ↓
Application actually listening
```

---

# 48. The Application Must Listen on the Correct Interface

This becomes especially important with custom applications.

Suppose a Python web application listens on:

```text
127.0.0.1:5000
```

inside the container.

`127.0.0.1` means loopback within that container's network namespace.

Other network interfaces may not be able to reach the service.

For containerized applications, servers commonly need to listen on:

```text
0.0.0.0
```

inside the container when they should accept traffic arriving through the container network.

---

# 49. `127.0.0.1` vs `0.0.0.0`

Simplified:

```text
127.0.0.1
→ loopback only

0.0.0.0
→ listen on all appropriate IPv4 interfaces
```

Suppose your app reports:

```text
Listening on 127.0.0.1:5000
```

and Docker publishes:

```bash
-p 5000:5000
```

The mapping may exist, but the application binding can still prevent expected external access.

This is a classic container networking failure.

---

# 50. `localhost` Inside a Container

Another extremely important rule:

Inside Container A:

```text
localhost
```

normally refers to:

```text
Container A itself
```

not:

```text
Container B
```

and not generally:

```text
the Docker host
```

Therefore, if Backend and Database are separate containers:

```text
DB_HOST=localhost
```

inside Backend usually means:

```text
Look for PostgreSQL inside Backend itself.
```

That is wrong if PostgreSQL is running in another container.

---

# 51. Correct Multi-Container Addressing

Architecture:

```text
backend container
      │
      │ DB_HOST=database
      ↓
Docker DNS
      ↓
database container
```

Instead of:

```text
DB_HOST=localhost
```

use the network-resolvable service/container name:

```text
DB_HOST=database
```

when appropriate.

This single concept solves many beginner failures.

---

# 52. What Does `EXPOSE` Mean?

In a Dockerfile you may see:

```dockerfile
EXPOSE 80
```

This documents that the image/application expects to use port:

```text
80
```

But `EXPOSE` does **not** by itself publish that port on the Docker host.

This distinction is critical.

---

# 53. `EXPOSE` vs `-p`

Dockerfile:

```dockerfile
EXPOSE 80
```

means roughly:

```text
This image declares/documentation metadata that the application uses port 80.
```

Runtime:

```bash
docker run -p 8080:80 image
```

means:

```text
Publish host port 8080 to container port 80.
```

Therefore:

```text
EXPOSE
≠
publish to host
```

---

# 54. Prove `EXPOSE` Does Not Publish a Port

The Nginx image declares its expected web port.

Run:

```bash
docker run -d \
  --name expose-test \
  nginx
```

Then:

```bash
docker ps
```

You may see:

```text
80/tcp
```

but not:

```text
0.0.0.0:8080->80/tcp
```

The first indicates container port metadata.

The second indicates a published host mapping.

These are different.

---

# 55. Publishing to a Specific Host Address

You may encounter:

```bash
-p 127.0.0.1:8080:80
```

This binds the published port specifically to host loopback rather than broadly to all host interfaces.

Conceptually:

```text
127.0.0.1:8080
       ↓
container:80
```

This can be useful when a service should only be reachable locally on the Docker host.

---

# 56. Security Implication of Port Publishing

Publishing:

```bash
-p 8080:80
```

can expose a service through host interfaces depending on Docker and host networking configuration.

Do not assume:

```text
"I only wanted to test it"
```

means:

```text
"Nobody else can reach it."
```

Before publishing production ports, understand:

```text
Host interfaces
Firewall rules
Cloud security groups
Docker rules
Application authentication
TLS
Network exposure
```

---

# 57. Publishing Databases Carelessly

A common beginner command is:

```bash
docker run -p 5432:5432 postgres
```

This may make PostgreSQL reachable through the host.

But ask:

> Does the database need to be externally reachable?

In a multi-container application, often:

```text
Backend
   ↓
internal Docker network
   ↓
PostgreSQL
```

is enough.

You may not need:

```text
Internet
   ↓
PostgreSQL
```

Never publish ports merely because a tutorial does.

---

# 58. Internal Port Does Not Need Host Publication for Container Communication

Suppose:

```text
backend
```

and:

```text
database
```

share:

```text
app-network
```

Backend can connect to:

```text
database:5432
```

without publishing PostgreSQL's port to the host.

Architecture:

```text
Backend Container
      │
      │ database:5432
      ↓
Docker Network
      ↓
PostgreSQL Container
```

No:

```text
-p 5432:5432
```

is required for this internal communication.

---

# 59. Network Isolation

Docker networks can create connectivity boundaries.

Imagine:

```text
frontend-network

frontend
   │
backend
```

and:

```text
database-network

backend
   │
database
```

The frontend may not need direct access to the database.

The backend can join both networks.

---

# 60. Multi-Network Architecture

```text
                frontend-network
             ┌────────────────────┐
             │                    │
         Frontend ─────────── Backend
                                │
             └──────────────────┘
                                │
                                │ also connected
                                ↓
                 database-network
             ┌────────────────────┐
             │                    │
             │       Backend ─ Database
             │                    │
             └────────────────────┘
```

Now:

```text
Frontend → Backend
```

works.

And:

```text
Backend → Database
```

works.

But:

```text
Frontend → Database
```

# 78. Host Networking

Docker also provides:

```text
host
```

networking.

On supported Linux configurations, a container using host networking shares the host's network namespace rather than receiving the normal isolated bridge-network stack.

Example:

```bash
docker run --rm \
  --network host \
  nginx
```

Conceptually:

```text
Normal bridge mode:

Host network
   ↓
bridge
   ↓
container network namespace


Host mode:

Container process
   ↓
Host network namespace
```

---

# 79. Consequences of Host Networking

With host networking:

```text
Container network isolation is reduced.
```

The application uses host networking directly.

Therefore, normal:

```text
-p HOST:CONTAINER
```

port publishing is not used in the same way because there is no ordinary bridge/NAT boundary to publish across.

If Nginx listens on:

```text
port 80
```

it is using the host networking namespace's port 80.

---

# 80. Port Conflicts With Host Networking

Suppose the host already has:

```text
Apache listening on port 80
```

and a host-networked container tries to run Nginx on:

```text
port 80
```

They cannot both independently bind the same host address/port combination.

This is an important consequence of sharing the host network namespace.

---

# 81. When Might Host Networking Be Used?

Possible reasons can include specialized:

```text
Networking workloads
Monitoring tools
Performance-sensitive networking
Host-integrated services
Network diagnostic tools
```

But do not use it simply because bridge networking is confusing.

Using:

```text
--network host
```

to bypass a networking problem often hides the real misunderstanding rather than solving it.

---

# 82. Docker Desktop and Host Networking

Host networking behavior/support has historically differed between native Linux Docker Engine and Docker Desktop, and Docker Desktop capabilities evolve over time.

For production or platform-specific use, verify the behavior supported by the Docker version and operating environment you actually run.

Do not assume Linux networking details map perfectly onto macOS or Windows.

Possible uses include:


Again:

```text

```

applies to networking.

# 85. Overlay Networking Introduction

Bridge networking primarily solves:

```text
Container A
      ↓
same Docker host
      ↓
Container B
```

But what if:

```text
Container A
```

runs on:

```text
Host 1
```

and:

```text
Container B
```

runs on:

```text
Host 2
```

Now single-host bridge networking is not enough.

---

# 86. Overlay Concept

An overlay network provides a virtual network that can span multiple participating Docker hosts in orchestration contexts such as Docker Swarm.

Conceptually:

```text
Docker Host A
   │
Container A
   │
   └──────────────┐
                  │
            Overlay Network
                  │
   ┌──────────────┘
   │
Container B
   │
Docker Host B
```

The containers can participate in a logical network even though the hosts are physically separate.

---

# 87. Do Not Confuse Bridge and Overlay

```text
Bridge
→ primarily single-host container networking

Overlay
→ multi-host virtual networking in supported orchestrated environments
```

You do not need to build a Docker Swarm environment yet.

The important lesson is why overlay networking exists.

Later, when you learn Kubernetes networking, you will encounter related but different multi-host container networking problems and solutions.

# 88. Outbound Internet Access

Containers often need to initiate outbound connections.

Example:

```text

   ↓

   ↓

   ↓
Internet
```

An application may need to reach:

```text
External API
Package repository
Authentication provider
Cloud service
Remote database
```

Docker bridge networking commonly uses NAT/masquerading mechanisms to support outbound connectivity from private container addresses.

# 89. Container Private Address vs Internet Address

Suppose a container has:

```text

```

That private Docker-network address is not generally what an Internet service sees directly.

Conceptually:

```text
Container
172.18.0.5
   ↓

   ↓
Host/external network address
   ↓
Internet
```

This is another role NAT can play.

# 90. Container-to-Host Communication

Sometimes a container needs to contact a service running on the Docker host.

This requires careful platform-specific handling.

Do not blindly assume:

```text

```

will work.

Inside the container:

```text
localhost
```

usually means the container itself.

Docker Desktop commonly provides special mechanisms/names for host access, while native Linux approaches can differ.

Always verify the platform and intended architecture.

---

# 91. Networking Security Principle

A secure container architecture should ask:

```text
Does this service need Internet access?

Does this service need inbound host exposure?

Does it need to communicate with every container?

Does the database need a published port?

Does the cache need public access?

Can networks be segmented?

Can host binding be restricted?
```

Networking is a security control.

# 93. Troubleshooting Docker Networking Systematically

Do not begin with:

```text

Disable firewall

```

Instead follow:

```text
Observe
   ↓
Identify source
   ↓
Identify destination
   ↓
Check name resolution
   ↓
Check network membership
   ↓
Check routing/path
   ↓
Check application listener
   ↓
Check port mapping
   ↓
Check host/firewall controls
   ↓
Test hypothesis
   ↓
Fix root cause
   ↓
Verify
```

---

# 94. Troubleshooting Layer 1: Is the Container Running?

Start with:

```bash
docker ps
```

If missing:

```bash
docker ps -a
```

A stopped application cannot answer network requests.

Check:

```bash
docker logs <container>
```

Do not troubleshoot advanced networking before confirming the service exists.

---

# 95. Troubleshooting Layer 2: Is the Application Listening?

A container can be:

```text
running
```

while the application is:

```text
failed
not started
listening on wrong port
listening only on loopback
```

Inspect logs:

```bash
docker logs <container>
```

If diagnostic tools exist inside the container, commands such as:

```bash
ss -lntp
```

can show listening TCP sockets.

But minimal images may not contain `ss`.

Do not install random troubleshooting packages into a production container merely to diagnose it if safer external/debug methods are available.

---

# 96. Understand `ss -lntp`

Where available:

```bash
ss -lntp
```

means approximately:

```text
ss
→ inspect sockets

-l
→ listening sockets

-n
→ numeric addresses/ports

-t
→ TCP

-p
→ process information when permissions allow
```

Example:

```text
LISTEN ... 0.0.0.0:80 ...
```

suggests a process is listening on TCP port 80 across IPv4 interfaces.

---

# 97. Troubleshooting Layer 3: Is the Port Correct?

Suppose application logs say:

```text
Listening on port 5000
```

but Docker was started with:

```bash
-p 8080:80
```

Traffic becomes:

```text
Host 8080
   ↓
Container 80
```

while application listens on:

```text
Container 5000
```

Nothing useful is listening at the destination.

Correct mapping:

```bash
-p 8080:5000
```

---

# 98. Troubleshooting Layer 4: Is the Port Published?

Run:

```bash
docker ps
```

or:

```bash
docker port <container>
```

If you expect:

```text
Host:8080
```

but no published mapping exists, external host traffic cannot use that path.

Remember:

```text
EXPOSE
```

alone does not publish.

---

# 99. Troubleshooting Layer 5: Are the Containers on the Same Network?

Suppose Backend tries:

```text
database:5432
```

Check:

```bash
docker inspect backend
```

and:

```bash
docker inspect database
```

Compare:

```text
NetworkSettings.Networks
```

If they share no appropriate network, direct name-based communication will fail.

---

# 100. Troubleshooting Layer 6: Does DNS Resolve?

Use a diagnostic container on the same network:

```bash
docker run --rm \
  --network <network> \
  busybox \
  nslookup <container-name>
```

If DNS resolution fails, investigate:

```text
Network membership
Name spelling
Aliases
Container existence
Wrong network
```

Do not immediately replace the hostname with a hardcoded IP.

Fix the service-discovery problem.

---

# 101. Troubleshooting Layer 7: Can You Reach the Service?

For HTTP:

```bash
docker run --rm \
  --network <network> \
  busybox \
  wget -qO- http://service
```

For a service on another port:

```text
http://service:PORT
```

For non-HTTP services, use an appropriate protocol-aware client or connectivity test.

A successful DNS lookup only proves:

```text
name → address
```

It does not prove:

```text
application responds correctly
```

---

# 102. DNS Success Does Not Equal Application Success

These are different stages:

```text
DNS resolution
      ↓
Network route
      ↓
TCP connection
      ↓
Application protocol
      ↓
Application response
```

A failure can happen at any stage.

For example:

```text
Name resolves
but
Connection refused
```

means DNS is probably not your primary problem.

---

# 103. Understanding Connection Refused

Error:

```text
Connection refused
```

often suggests:

```text
Destination reachable enough to reject connection
but
nothing is listening on requested port
```

or a system is actively rejecting it.

Investigate:

```text
Correct port?
Application running?
Application listening?
Correct interface?
Correct destination?
```

---

# 104. Understanding Timeout

A timeout may suggest:

```text
Traffic dropped
Routing issue
Firewall
Security group
Wrong address
Service unreachable
Network path failure
```

This differs from an immediate:

```text
Connection refused
```

Error behavior gives clues.

Do not treat every connectivity error identically.

---

# 105. Understanding Name Resolution Failure

Example:

```text
bad address 'database'
```

or:

```text
Name or service not known
```

Possible causes:

```text
Wrong service name
Containers on different networks
Container missing
Incorrect DNS configuration
Wrong network alias
```

Start with service discovery and network membership.

---

# 106. Troubleshooting `localhost`

Scenario:

Backend logs:

```text
connect ECONNREFUSED 127.0.0.1:5432
```

Architecture:

```text
Backend Container
Database Container
```

Likely mistake:

```text
DB_HOST=localhost
```

Inside Backend, `localhost` means Backend.

Fix conceptually:

```text
DB_HOST=database
```

when both containers share a user-defined network and `database` is the correct resolvable name/alias.

# 107. Troubleshooting External Access

Suppose:

```bash

```

works on the host, but another machine cannot connect.

Docker may not be the only layer involved.

Investigate:

```text

Host firewall
Cloud firewall/security group
Routing
Network ACLs
Load balancer
Corporate network rules
Operating system firewall
```

Docker networking is one layer of the complete network path.

# 108. Cloud Networking Adds More Layers

Later, in AWS, the path may become:

```text

   ↓

   ↓

   ↓

   ↓

   ↓
```

# 137. Common Docker Networking Mistakes

## Mistake 1

Using:

```text
localhost
```

to reach another container.

### Better

Use the appropriate service/container name on a shared user-defined network.

---

## Mistake 2

Assuming:

```dockerfile
EXPOSE 80
```

publishes the application.

### Better

Use runtime port publishing when host access is required:

```bash
-p HOST_PORT:CONTAINER_PORT
```

---

## Mistake 3

Reversing ports.

Wrong mental model:

```text
-p CONTAINER:HOST
```

Correct:

```text
-p HOST:CONTAINER
```

---

## Mistake 4

Publishing every service.

### Better

Only publish services that actually require host/external access.

---

## Mistake 5

Hardcoding container IP addresses.

### Better

Use Docker DNS/service names on user-defined networks.

---

## Mistake 6

Putting every application on one network.

### Better

Design network membership around required communication paths.

---

## Mistake 7

Using host networking to avoid understanding bridge networking.

### Better

Diagnose the real networking issue.

---

## Mistake 8

Assuming a running container means a listening application.

### Better

Check logs and application listeners.

---

## Mistake 9

Using only `ping` to diagnose applications.

### Better

Test DNS, relevant TCP port, and actual application protocol.

---

## Mistake 10

Disabling firewalls as the first troubleshooting step.

### Better

Gather evidence and identify the blocked layer first.

# 145. Networking Troubleshooting Matrix

| Symptom                             | First things to investigate                        |
| ----------------------------------- | -------------------------------------------------- |
| Container name does not resolve     | Shared network, spelling, aliases, container state |
| Connection refused                  | Listener, target port, bind address                |
| Timeout                             | Routing, firewall, wrong destination, network path |
| Works internally but not from host  | Port publishing, bind address                      |
| Works on host but not remotely      | Host firewall, cloud networking, external routing  |
| Container cannot reach another      | Network membership, DNS, destination port          |
| `localhost` fails                   | Wrong networking assumption                        |
| App reachable on wrong port only    | Port mapping/config mismatch                       |
| Service disappears after recreation | Hardcoded IP or wrong network configuration        |
| Database publicly exposed           | Unnecessary port publication                       |

# 146. The Complete Networking Reasoning Model

When a request fails, ask in this order:

```text
1. Is the source application/process running?

2. Is the destination container running?

3. What hostname/address is being used?

4. Does that name resolve?

5. Are source and destination on compatible networks?

6. What destination port is being used?

7. Is the application listening on that port?

8. Which interface/address is it listening on?

9. Is host publication required?

10. If yes, is HOST_PORT:CONTAINER_PORT correct?

11. Is a host firewall blocking it?

12. Is cloud networking blocking it?

13. Is the application protocol itself failing?

14. What do the logs show?

15. After the fix, can you verify the entire path?
```

That is production troubleshooting.

Not:

```text
Restart everything.
```

# What You Should Now Understand

You should now understand that containers need networking to communicate with:

```text
Users
Other containers
Host services
External APIs
Internet services
```

Linux network namespaces provide isolated networking environments.

Containers on bridge networks commonly receive their own IP addresses.

Those IP addresses should usually not be hardcoded into application configuration.

Docker supports network drivers including:

```text
bridge
host
none
overlay
```

Bridge networking is the main single-host Docker networking model.

Linux bridges connect virtual container interfaces.

Virtual Ethernet pairs act like virtual links between network namespaces and host-side networking.

The default Docker bridge is commonly associated with:

```text
docker0
```

on native Linux Docker Engine.

User-defined bridge networks provide better application organization, isolation, and DNS-based service discovery.

Docker's embedded DNS allows containers on appropriate user-defined networks to communicate using names.

Inside a container:

```text
localhost
```

means that container itself.

It does not mean another container.

Container-to-container communication on a shared Docker network does not require host port publishing.

A container port belongs to the container's networking environment.

A host port belongs to the Docker host.

Port publishing uses:

```text
HOST_PORT:CONTAINER_PORT
```

Example:

```text
8080:80
```

means:

```text
Host 8080
→
Container 80
```

Docker uses networking/NAT mechanisms to forward published traffic.

`EXPOSE` does not publish a host port.

It provides image metadata/documentation about expected container ports.

An application must actually listen on the expected port.

An application listening only on:

```text
127.0.0.1
```

inside its container may not accept traffic arriving through the container's external interface.

Applications intended for container-network access commonly listen appropriately on:

```text
0.0.0.0
```

or equivalent interfaces according to the application's networking model.

Networks can isolate services.

A backend can belong to both:

```text
frontend-network
```

and:

```text
database-network
```

while the frontend has no direct network path to the database.

Containers can be attached using:

```bash
docker network connect
```

and detached using:

```bash
docker network disconnect
```

Host networking reduces normal network namespace isolation and uses host networking directly on supported environments.

None networking provides a highly isolated container networking model.

Overlay networks address multi-host container networking in supported orchestrated environments.

Network troubleshooting must distinguish:

```text
DNS
Routing
Network membership
TCP connectivity
Port mapping
Application listeners
Host firewall
Cloud networking
Application protocol
```

Most importantly, you should understand this architecture:

```text
Internet
   ↓
Host IP
   ↓
Host Port
   ↓
Docker Port Publishing / NAT
   ↓
Docker Bridge
   ↓
Container IP
   ↓
Container Port
   ↓
Application
```

And internal communication:

```text
Container A
   ↓
Service Name
   ↓
Docker DNS
   ↓
Container B IP
   ↓
Docker Bridge
   ↓
Container B Port
   ↓
Application B
```

# Part 8 Summary

Docker networking is not simply:

```text
container has Internet
```

It is an architecture composed of:

```text
Network namespaces
Container interfaces
veth pairs
Linux bridges
IP addresses
Routes
DNS
NAT
Port mappings
Network membership
Application listeners
Isolation boundaries
```

For internal application communication:

```text
Backend
   │
   │ database:5432
   ↓
Docker DNS
   ↓
Database address
   ↓
Docker bridge
   ↓
Database container
   ↓
PostgreSQL
```

For externally published traffic:

```text
Internet
   ↓
Docker Host
   ↓
Host Port
   ↓
Docker NAT / Port Publishing
   ↓
Bridge Network
   ↓
Container IP
   ↓
Container Port
   ↓
Application
```

The most important beginner rules are:

```text
Container IPs can change.
Use names where appropriate.

localhost means the current container.

HOST:CONTAINER is the port-mapping order.

EXPOSE does not publish a host port.

Internal container communication does not require host publication.

Not every service should be publicly exposed.

Containers must share an appropriate network to communicate directly by Docker service discovery.

A running container does not guarantee a healthy network service.

DNS success does not guarantee application success.

Troubleshoot networking layer by layer.
```

The final mental model is:

```text
WHO is connecting?
        ↓
WHAT name/address are they using?
        ↓
Can DNS resolve it?
        ↓
Do the systems share a network path?
        ↓
Which PORT is the destination?
        ↓
Is the application LISTENING there?
        ↓
Is PORT PUBLISHING required?
        ↓
Is NAT/routing correct?
        ↓
Are FIREWALL/CLOUD controls allowing it?
        ↓
Does the APPLICATION respond?
```

That is the foundation for Part 9, where networking, storage, environment configuration, and multiple containers come together as one application:

```text
Browser
   ↓
Frontend
   ↓
Backend / API
   ↓
Database
```

The learner will build that stack manually first, so every connection is understood before Docker Compose automates it.
