# Part 4: Docker Images: Layers, Tags, Pulling, and Image Management

In Part 3, you learned how to control containers throughout their lifecycle. You created, started, stopped, restarted, inspected, entered, monitored, and removed containers.

Now we need to understand the object every container begins with:

**the Docker image.**

This part answers an important question:

> When Docker creates a container, what exactly is it creating the container from?

The basic architecture is:

```text
Base Layer
    ↓
Dependency Layer
    ↓
Application Layer
    ↓
Container Writable Layer
```

By the end of this part, you should understand not only how to run:

```bash
docker pull nginx
```

but what Docker downloads, how image layers are stored and reused, why images are effectively immutable, how tags and digests differ, how multi-platform images work, and how to manage images safely.

---

# 1. What Is a Docker Image?

A Docker image is a packaged, read-only template used to create containers.

It contains the filesystem content and metadata needed to start a container.

Depending on the application, an image can contain:

* Application code
* Runtime
* Libraries
* System utilities
* Configuration defaults
* Files and directories
* Environment-variable defaults
* Startup command
* Working directory
* User configuration
* Port metadata
* Other image metadata

For example, an Nginx image contains what is needed to create an Nginx container.

Conceptually:

```text
Nginx Image
├── Filesystem content
├── Nginx software
├── Required libraries
├── Configuration
└── Startup metadata
```

Docker uses that image to create:

```text
Nginx Container
```

---

# 2. An Image Is Not a Running Application

This distinction is fundamental.

An image does not need to be running.

Think of it as a packaged template.

```text
IMAGE
Stored artifact/template

CONTAINER
Runtime instance created from image
```

For example:

```bash
docker pull nginx
```

downloads an image.

It does not automatically mean Nginx is now serving web requests.

But:

```bash
docker run nginx
```

creates and starts a container from the image.

Architecture:

```text
Registry
   ↓
Image
   ↓
docker run
   ↓
Container
   ↓
Running Process
```

---

# 3. Image vs Container

Suppose you have one image:

```text
nginx:1.27
```

You can create several containers from it:

```text
             nginx:1.27
                 │
        ┌────────┼────────┐
        ↓        ↓        ↓
      web-1    web-2    web-3
```

The image remains the common source.

Each container becomes its own runtime instance.

This is similar to:

```text
Image
→ blueprint/template

Container
→ instance created from blueprint
```

The analogy is useful, but remember that Docker images have specific filesystem layers and metadata. They are not merely abstract blueprints.

---

# 4. Why Images Exist

Imagine deploying an application manually.

You tell another engineer:

> Install Ubuntu, Python, these libraries, this package version, these files, these environment settings, and then start the application with this command.

That creates opportunities for inconsistency.

Machine A might have:

```text
Python 3.11
Library X 2.4
```

Machine B might have:

```text
Python 3.12
Library X 2.6
```

The application may behave differently.

Images help package the application's runtime filesystem and metadata into a repeatable artifact.

Instead of:

```text
Server
 ↓
Install manually
 ↓
Configure manually
 ↓
Copy code
 ↓
Hope everything matches
```

you can move toward:

```text
Source
 ↓
Build Image
 ↓
Test Image
 ↓
Store Image
 ↓
Deploy same artifact
```

That repeatability is one of the major reasons container images are useful.

---

# 5. Images and Reproducibility

Suppose CI builds:

```text
payment-api:2.4.1
```

That image can be tested.

If approved, the same image content can then move through environments.

Conceptually:

```text
Source Code
    ↓
Build
    ↓
Image
    ↓
Test
    ↓
Registry
    ↓
Staging
    ↓
Production
```

A strong deployment model tries to avoid rebuilding different artifacts for every environment.

Instead:

```text
Same artifact
+
Environment-specific runtime configuration
```

is often preferable.

This reduces the chance that:

```text
"What we tested"
```

is different from:

```text
"What we deployed"
```

---

# 6. The Immutable Image Concept

Docker images are treated as immutable artifacts.

Immutable means:

> You do not normally modify an existing image in place.

Suppose you have:

```text
myapp:1.0
```

and need to update the application.

The normal model is not:

```text
Open image
 ↓
Edit files inside it
 ↓
Save changes into same image object
```

Instead:

```text
Source v1
 ↓
Build
 ↓
Image A
```

Then after changes:

```text
Source v2
 ↓
Build
 ↓
Image B
```

You create a new image.

This supports predictable deployments and rollback.

---

# 7. Why Immutability Matters

Imagine production servers being manually modified.

```text
Server 1
→ package upgraded

Server 2
→ package not upgraded

Server 3
→ config manually changed

Server 4
→ nobody remembers what happened
```

This creates configuration drift.

With image-based deployments, the goal becomes:

```text
Desired image
      ↓
Deploy
      ↓
Replace old containers
```

rather than manually repairing each container.

This is an important DevOps principle:

> Prefer rebuilding and replacing artifacts over manually modifying runtime instances.

---

# 8. But Didn't We Modify a Container in Part 3?

Yes.

You created files inside a running container.

For example:

```bash
docker exec -it web sh
```

and then:

```bash
echo "VERIQTA" > /tmp/test.txt
```

You did **not** modify the underlying image.

You modified the container's writable filesystem layer.

This is one of the most important distinctions in Docker.

```text
Image Layers
READ-ONLY
     ↓
Container Writable Layer
READ-WRITE
```

---

# 9. Images Are Built From Layers

A Docker image is not normally one giant filesystem blob.

Images are constructed from layers.

Conceptually:

```text
Application Image
      │
      ├── Layer 4: Application
      ├── Layer 3: Dependencies
      ├── Layer 2: Runtime/packages
      └── Layer 1: Base filesystem
```

When Docker presents the image to a container, these layers appear together as a usable filesystem.

---

# 10. Our Main Architecture

Throughout this part, keep this architecture in mind:

```text
┌─────────────────────────────┐
│ Container Writable Layer    │
│ Runtime changes             │
├─────────────────────────────┤
│ Application Layer           │
│ Application files           │
├─────────────────────────────┤
│ Dependency Layer            │
│ Packages/libraries          │
├─────────────────────────────┤
│ Base Layer(s)               │
│ Base filesystem content     │
└─────────────────────────────┘
```

The lower image layers are read-only from the container's perspective.

The top container layer is writable.

---

# 11. Why Docker Uses Layers

Layers provide several benefits.

They can improve:

* Storage reuse
* Distribution efficiency
* Build caching
* Image construction
* Sharing common content between images

Imagine three application images all sharing some underlying content.

Without reuse:

```text
App A → copy everything
App B → copy everything
App C → copy everything
```

With content-addressed layers, common layers can be reused locally rather than stored repeatedly as independent copies.

Conceptually:

```text
          Shared Base Content
          /       |       \
         /        |        \
      App A     App B     App C
```

---

# 12. Simple Layer Example

Imagine an application image constructed conceptually like this:

```text
Layer 1
Base filesystem

Layer 2
Python runtime

Layer 3
Application dependencies

Layer 4
Application source
```

The resulting image appears as one filesystem when used.

```text
Layer 4 ┐
Layer 3 │
Layer 2 ├── Combined filesystem view
Layer 1 ┘
```

This layering becomes extremely important when we write Dockerfiles in Part 5.

---

# 13. Dockerfile Instructions and Layers

You have not yet learned Dockerfiles fully, but consider:

```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .

RUN pip install -r requirements.txt

COPY . .

CMD ["python", "app.py"]
```

Some build instructions create filesystem layers containing changes.

Conceptually:

```text
Base Python image
      ↓
Application working filesystem changes
      ↓
Dependencies installed
      ↓
Application files copied
      ↓
Final image
```

The exact layer behavior depends on the instruction and modern build system, but the central idea is:

> Image filesystem changes are represented as layers rather than repeatedly storing a complete new filesystem.

---

# 14. Read-Only Image Layers

When Docker creates a container from an image, the image layers are not meant to become freely writable by that container.

Think:

```text
Container
   ↓
Writable layer
──────────────
Image Layer C
Image Layer B
Image Layer A
```

The image layers remain read-only.

Changes made at runtime go into the container's writable layer.

This allows multiple containers to share the same image content.

---

# 15. Multiple Containers Sharing Image Layers

Suppose:

```text
nginx image
```

is stored locally.

You create:

```text
web-1
web-2
web-3
```

Conceptually:

```text
web-1 writable layer
        ↓
   nginx image
```

```text
web-2 writable layer
        ↓
   nginx image
```

```text
web-3 writable layer
        ↓
   nginx image
```

The containers can share the underlying read-only image content while maintaining separate runtime changes.

---

# 16. The Writable Container Layer

When Docker creates a container, it adds a writable layer above the image's read-only layers.

Architecture:

```text
┌──────────────────────────────┐
│ Container Writable Layer     │
│                              │
│ New files                    │
│ Modified files               │
│ Deletion metadata            │
├──────────────────────────────┤
│ Application Image Layer      │
├──────────────────────────────┤
│ Dependency Image Layer       │
├──────────────────────────────┤
│ Base Image Layer             │
└──────────────────────────────┘
```

Runtime filesystem changes happen in the writable layer.

---

# 17. What Happens When You Create a File?

Suppose inside the container you run:

```bash
echo "hello" > /tmp/hello.txt
```

That file did not exist in the image.

Docker's storage system records the new file in the writable container layer.

Conceptually:

```text
Writable Layer
└── /tmp/hello.txt

Image Layers
└── unchanged
```

The underlying image remains unchanged.

---

# 18. What Happens When You Modify an Existing File?

Suppose the image contains:

```text
/etc/example.conf
```

Your container modifies it.

The read-only image layer cannot simply be edited.

Instead, the storage driver uses a copy-on-write mechanism.

At a simplified level:

```text
Read-only image file
       ↓
Container attempts modification
       ↓
File becomes represented in writable layer
       ↓
Container modifies writable copy
```

The original image content remains unchanged.

---

# 19. Copy-on-Write

This behavior is called **copy-on-write**, often abbreviated:

```text
CoW
```

The principle is:

> Shared content can remain shared until a container needs to modify it.

Simplified example:

```text
Image
└── config.txt
       ↓
Container reads
       ↓
Use existing image content
```

But if the container modifies it:

```text
Image config.txt
       ↓
Copy-up / writable representation
       ↓
Container writable layer
       ↓
Modified config.txt
```

The exact mechanics depend on the storage driver, but this is the mental model you should remember.

---

# 20. Why Copy-on-Write Helps

Without this model, every container might need a complete independent copy of its image filesystem.

Imagine:

```text
1 GB image
×
100 containers
```

A naive design could require enormous duplication.

Layer sharing and copy-on-write allow common image content to remain shared while containers store their own changes separately.

This improves storage efficiency.

---

# 21. Deleting Files Inside a Container

Suppose an image contains:

```text
/app/example.txt
```

You enter the container and run:

```bash
rm /app/example.txt
```

The underlying read-only image layer is not rewritten.

The storage system represents that file as removed in the container's merged filesystem view.

The original image still contains its original data.

This is why creating another fresh container from the same image can make the file appear again.

---

# 22. Proving the Image Was Not Modified

Suppose:

```bash
docker run -d --name test1 nginx
```

You modify something inside `test1`.

Then remove it:

```bash
docker stop test1
docker rm test1
```

Create another:

```bash
docker run -d --name test2 nginx
```

The new container starts from the original image content.

Your runtime modification does not automatically become part of the Nginx image.

Architecture:

```text
                 nginx image
                 /         \
                /           \
           test1             test2
       writable A        writable B
```

Changes in A do not become image changes or automatically appear in B.

---

# 23. OverlayFS

On Linux, Docker commonly uses storage mechanisms based on OverlayFS, often through the `overlay2` storage driver.

OverlayFS allows multiple filesystem layers to be combined into a unified view.

At a simplified level:

```text
Upper Layer
Container changes

Lower Layers
Image content

      ↓

Merged View
What the container sees
```

You interact with the merged filesystem rather than manually navigating each layer.

---

# 24. OverlayFS Mental Model

Imagine:

```text
Lower layer:
A.txt
B.txt
C.txt
```

Upper writable layer:

```text
B.txt modified
D.txt added
```

The merged view might appear:

```text
A.txt
B.txt ← modified version
C.txt
D.txt
```

The user inside the container sees one filesystem.

They do not normally care which layer supplied each file.

---

# 25. Docker Storage Driver

Check:

```bash
docker info
```

On a Linux Docker Engine, you may see storage-driver information such as:

```text
Storage Driver: overlay2
```

The exact output depends on your operating system, Docker environment, and backend.

Docker Desktop adds additional virtualization/container-runtime layers on macOS and Windows, so do not assume every host exposes exactly the same low-level storage layout.

---

# 26. Do Not Manually Edit Docker's Storage Internals

You may eventually find Docker data under paths such as:

```text
/var/lib/docker
```

on Linux.

Do **not** manually modify layer files inside Docker's internal data directory.

Docker manages this state.

Manual changes can corrupt Docker's metadata or storage.

Use Docker commands and supported APIs.

---

# 27. Image Repositories

Now we need to separate three concepts:

```text
Registry
Repository
Tag
```

A **registry** stores and distributes images.

A **repository** is a named collection of related image versions within a registry/namespace.

A **tag** identifies a particular named reference within that repository.

Example:

```text
nginx:1.27
```

Here:

```text
nginx
→ repository

1.27
→ tag
```

If a registry hostname is omitted, Docker uses its configured/default registry behavior, commonly Docker Hub for standard public image references.

---

# 28. Fully Qualified Image Names

An image reference can be more complete.

For example:

```text
registry.example.com/team/payment-api:2.4.1
```

Conceptually:

```text
registry.example.com
→ registry

team
→ namespace/project

payment-api
→ repository

2.4.1
→ tag
```

Different registries organize namespaces/projects somewhat differently, but this model is useful.

---

# 29. Image Tags

A tag is a human-readable reference associated with image content.

Examples:

```text
nginx:1.27
nginx:stable
myapp:1.0
myapp:2.0
payment-api:2026-09-17
```

Tags help humans and automation refer to images.

---

# 30. Tags Are Not Copies

Suppose the same image content has:

```text
myapp:1.0
myapp:stable
```

Those two tags can refer to the same image content.

Conceptually:

```text
myapp:1.0 ─────┐
               ├── Image
myapp:stable ──┘
```

Creating another tag does not necessarily duplicate all image data.

A tag is primarily a reference.

---

# 31. The `latest` Tag

You will frequently see:

```text
nginx:latest
```

Beginners often misunderstand `latest`.

`latest` does **not** mean:

> Docker dynamically searches the entire internet and mathematically determines the newest possible software release.

`latest` is simply a tag named:

```text
latest
```

Its meaning depends on how the image publisher manages that repository.

---

# 32. What Happens When You Omit the Tag?

If you run:

```bash
docker pull nginx
```

Docker normally interprets the reference as:

```text
nginx:latest
```

Similarly:

```bash
docker run nginx
```

normally uses:

```text
nginx:latest
```

if no tag or digest is specified.

This convenience can become risky when reproducibility matters.

---

# 33. Why `latest` Can Be Dangerous

Suppose production deploys:

```text
myapp:latest
```

On Monday, `latest` refers to one image.

Later, CI publishes a new image and moves the `latest` tag.

Now:

```text
myapp:latest
```

can refer to different content.

That means two deployments using the same textual tag can potentially retrieve different image versions.

Conceptually:

```text
Monday
latest → Image A

Friday
latest → Image B
```

The label stayed the same.

The content changed.

---

# 34. Mutable References

Tags are generally mutable references.

That means a registry can allow:

```text
production → Image A
```

and later:

```text
production → Image B
```

This is convenient for workflows such as:

```text
dev
staging
stable
latest
```

but weaker for exact reproducibility.

---

# 35. Better Versioning

Instead of relying only on:

```text
myapp:latest
```

you may use:

```text
myapp:2.4.1
```

or:

```text
myapp:git-a84f93c
```

or another controlled tagging strategy.

Then deployment records can clearly state which named build was intended.

For stronger immutability, you can use digests.

---

# 36. Image IDs

Docker assigns locally stored image content an image ID.

Run:

```bash
docker image ls
```

or:

```bash
docker images
```

You may see:

```text
REPOSITORY   TAG      IMAGE ID       CREATED        SIZE
nginx        latest   abc123...      ...            ...
```

The exact values will vary.

The image ID identifies the local image object/content.

---

# 37. Inspect an Image ID

You can use:

```bash
docker image inspect nginx:latest
```

The output contains detailed JSON.

You may see fields relating to:

```text
Id
RepoTags
RepoDigests
Architecture
Os
Config
RootFS
Metadata
```

The exact output varies by image and Docker version.

---

# 38. Image Digests

A digest is a content-addressed cryptographic identifier.

You may see something resembling:

```text
nginx@sha256:abc123...
```

The digest is fundamentally different from a mutable tag.

Conceptually:

```text
TAG
nginx:stable
→ human-friendly reference
→ can potentially move
```

versus:

```text
DIGEST
nginx@sha256:...
→ content-addressed reference
→ identifies specific registry content
```

---

# 39. Tags vs Digests

This distinction is essential.

### Tag

```text
myapp:2.4
```

Human-readable.

Potentially mutable.

### Digest

```text
myapp@sha256:7f...
```

Content-addressed.

Designed to identify specific content.

Architecture:

```text
myapp:production
       ↓
Tag can move
       ↓
Image A today
Image B later
```

versus:

```text
myapp@sha256:XYZ
       ↓
Specific content
```

---

# 40. Why Digests Matter in Production

Suppose you need to know exactly what was deployed during an incident.

If the deployment record says:

```text
myapp:latest
```

but `latest` has since moved, investigation becomes harder.

If the record contains an immutable digest:

```text
myapp@sha256:...
```

you have a stronger reference to the exact artifact.

This is valuable for:

* Reproducibility
* Auditing
* Incident investigation
* Supply-chain controls
* Deployment verification
* Rollbacks

---

# 41. Tag and Digest Can Work Together

You might select a version using a tag:

```text
myapp:2.4.1
```

and record or deploy the resolved content digest.

Conceptually:

```text
Human selection
myapp:2.4.1
      ↓
Registry resolves
      ↓
sha256:...
      ↓
Exact artifact
```

This provides readable versioning while preserving exact artifact identity.

---

# 42. Pulling Images

To download an image:

```bash
docker pull nginx
```

Remember:

```text
nginx
```

normally implies:

```text
nginx:latest
```

You can explicitly request:

```bash
docker pull nginx:latest
```

or a specific available tag:

```bash
docker pull nginx:<version>
```

Use a version that actually exists in the repository.

---

# 43. What Happens During `docker pull`?

Simplified flow:

```text
Docker CLI
   ↓
Docker Daemon / Engine
   ↓
Registry
   ↓
Resolve image reference
   ↓
Retrieve manifest information
   ↓
Select appropriate platform content
   ↓
Download missing layers
   ↓
Verify content
   ↓
Store image locally
```

Because layers can be shared, Docker may not need to download every layer every time.

---

# 44. Understanding Pull Output

During a pull, you may see messages resembling:

```text
Pulling fs layer
Downloading
Verifying Checksum
Download complete
Pull complete
Already exists
```

The exact presentation can change.

The important concept is:

```text
Image
≠
one arbitrary download file
```

Docker retrieves the metadata and filesystem content needed for the selected image/platform.

---

# 45. `Already exists`

Suppose another local image already uses a required layer.

Docker may report that content already exists.

Conceptually:

```text
New Image
├── Layer A ← already local
├── Layer B ← already local
└── Layer C ← download required
```

Docker can reuse the existing content.

This is one of the benefits of layered images.

---

# 46. Pulling a Specific Tag

Instead of:

```bash
docker pull nginx
```

use a controlled version when appropriate:

```bash
docker pull nginx:<specific-tag>
```

Before choosing a production tag, verify that it actually exists and understand what the publisher promises about that tag.

Do not invent version numbers and assume every repository follows the same scheme.

---

# 47. Pulling by Digest

You can also pull content using a digest:

```bash
docker pull nginx@sha256:<digest>
```

The digest must be valid for content in that registry/repository.

This provides exact content selection rather than relying on a mutable tag.

# 49. Searching Is Discovery, Not Trust

Finding an image does not mean:

> This image is safe.

A search result is only a discovery mechanism.

Before using an image, especially in production, investigate:

* Publisher
* Official status
* Documentation
* Update history
* Versioning
* Source provenance where available
* Security practices
* Base image
* Vulnerability posture
* Maintenance activity

Do not run random third-party images merely because their names look familiar.

# 50. Listing Local Images

Run:

```bash

```

```bash

```

Typical columns include:

```text
REPOSITORY

IMAGE ID
CREATED

```

This shows images known to the local Docker image store.

---

# 51. Understanding `CREATED`

Be careful when interpreting image creation time.

It generally relates to the image's build metadata, not necessarily the moment you pulled it.

If you pull an image today that was built weeks ago, its creation metadata may still show the earlier time.

---

# 52. Image Size

`docker image ls` displays image size information.

Do not interpret this too simplistically as:

> Every image consumes exactly this much additional physical disk space.

Layers can be shared between images.

For example:

```text
Image A
├── Shared layer
└── A-specific layer

Image B
├── Shared layer
└── B-specific layer
```

The shared layer does not need to be independently duplicated for each image in the local content store.

# 53. Inspecting Images

Use:

```bash
docker image inspect nginx:latest
```

This can reveal:

* Image ID
* Tags
* Digests
* Architecture
* OS
* Environment defaults
* Working directory
* Entrypoint
* Command
* Exposed-port metadata
* Filesystem-layer information
* Creation metadata

This is useful before running unfamiliar images.

---

# 54. Image Inspection vs Container Inspection

You learned:

```bash
docker inspect web
```

for a container.

Now:

```bash
docker image inspect nginx
```

for an image.

They answer different questions.

```text
IMAGE INSPECTION
What does the packaged artifact define?
```

```text
CONTAINER INSPECTION
How was this runtime instance configured, and what is its state?
```

---

# 55. Example: Image Command vs Container Command

An image might define:

```text
CMD ["nginx", "-g", "daemon off;"]
```

When a container is created, that command can become part of its runtime configuration unless overridden.

Conceptually:

```text
Image Metadata
      ↓
Container Creation
      ↓
Container Runtime Configuration
```

This is why understanding images helps you understand containers.

---

# 56. Image History

Run:

```bash
docker image history nginx
```

This displays the history associated with the image.

Depending on the image, you may see:

```text
IMAGE
CREATED
CREATED BY
SIZE
COMMENT
```

This can help you understand how an image was assembled.

---

# 57. Why Image History Is Useful

Suppose an image is unexpectedly large.

History may help reveal that a build step added significant data.

Example conceptually:

```text
Base image             80 MB
Install dependencies  +400 MB
Copy application       +20 MB
```

Now you know where to investigate.

Image history becomes particularly useful after you learn Dockerfiles.

---

# 58. History Is Not the Same as Full Source

Do not assume:

```bash
docker image history
```

will perfectly reconstruct the original Dockerfile, source repository, build secrets, or every build detail.

It provides useful build/history metadata.

It is not a guaranteed replacement for the original build source.

---

# 59. Tagging Images

Use:

```bash
docker tag SOURCE_IMAGE TARGET_IMAGE
```

Example:

```bash
docker tag myapp:1.0 myapp:stable
```

This does not rebuild the image.

Conceptually:

```text
             Image
            /     \
           /       \
    myapp:1.0    myapp:stable
```

Both references can initially point to the same local image.

---

# 60. Tagging for a Registry

Suppose you eventually want to push an image to a registry.

You may need a registry-qualified name:

```bash
docker tag myapp:1.0 registry.example.com/team/myapp:1.0
```

Conceptually:

```text
Local image
    ↓
Add registry-qualified reference
    ↓
Push that reference
```

We will cover registries deeply in Part 12.

---

# 61. Retagging Does Not Change Image Content

This is important.

If:

```bash
docker tag myapp:1.0 myapp:production
```

you did not modify:

```text
Application files
Libraries
Packages
Filesystem layers
```

You created another reference.

Think:

```text
Image content
   ↑
   ├── 1.0
   └── production
```

---

# 62. Removing an Image Tag

Suppose an image has:

```text
myapp:1.0
myapp:stable
```

If you run:

```bash
docker image rm myapp:stable
```

Docker may simply remove that reference while the underlying image remains reachable through:

```text
myapp:1.0
```

This is why output may say something like:

```text
Untagged
```

rather than immediately deleting every underlying layer.

---

# 63. Removing Images

Use:

```bash
docker image rm nginx:latest
```

or the shorthand:

```bash
docker rmi nginx:latest
```

Docker removes the reference and, when appropriate, unreferenced image data.

But Docker may refuse removal when the image is still required by existing containers.

---

# 64. Why Docker Sometimes Refuses to Remove an Image

Suppose:

```text
nginx image
   ↓
web container
```

Even if `web` is stopped, it still references the image.

Attempting to remove the image may cause a conflict.

Check:

```bash
docker ps -a
```

You may need to remove the dependent container first if it is safe:

```bash
docker rm web
```

Then:

```bash
docker image rm nginx
```

### Warning

Do not remove containers or images simply to make an error disappear.

First determine whether they are needed.

---

# 65. Force Removing Images

You may encounter:

```bash
docker image rm -f <image>
```

### Warning

`-f` means force.

Do not develop the habit:

```text
Docker refuses
   ↓
Add -f
```

Docker's refusal often protects you from deleting or untagging something still referenced.

Investigate first.

---

# 66. What Is a Dangling Image?

A dangling image is generally an image object/layer set that no longer has a repository tag pointing to it in the normal way.

You may see:

```text
REPOSITORY   TAG
<none>       <none>
```

A common scenario occurs during repeated builds.

Conceptually:

```text
myapp:latest → Image A
```

Build a new version:

```text
myapp:latest → Image B
```

Image A may become untagged/dangling if nothing else references it.

---

# 67. Why Dangling Images Appear

Imagine:

```text
Build 1
myapp:dev → Image A
```

Then:

```text
Build 2
myapp:dev → Image B
```

The tag moved.

If Image A has no remaining tag, it can become dangling.

Repeated development builds can accumulate such data.

---

# 68. Finding Dangling Images

Run:

```bash
docker image ls --filter dangling=true
```

This filters the local image list.

You may see untagged image objects.

Do not assume every untagged-looking object should immediately be deleted on every production host. Understand your build and deployment process first.

---

# 69. Dangling vs Unused

These terms should not be treated as identical.

A **dangling image** generally has no tag reference.

An **unused image** is broader.

An image may have a tag but still not be used by any container.

Conceptually:

```text
Dangling
→ no normal tag reference

Unused
→ not used by containers
→ may still have a tag
```

Therefore:

```text
All dangling images may be unused in a particular context,
but not every unused image is dangling.
```

---

# 70. Why Unused Images Accumulate

Development and CI systems frequently pull or build many versions:

```text
myapp:1.0
myapp:1.1
myapp:1.2
myapp:1.3
myapp:1.4
...
```

Over time:

```text
Old image layers
      ↓
Disk consumption
```

If nobody manages image lifecycle, Docker hosts can run low on disk space.

This can become a real production incident.

---

# 71. Inspect Docker Disk Usage

Use:

```bash
docker system df
```

This provides information about Docker disk usage.

You may see categories involving:

```text
Images
Containers
Local volumes
Build cache
```

This is a much better first step than blindly deleting data.

Troubleshooting principle:

```text
Disk problem
   ↓
Measure usage
   ↓
Identify category
   ↓
Determine what is safe to remove
   ↓
Clean deliberately
```

---

# 72. Image Pruning

Docker provides:

```bash
docker image prune
```

By default, this is used to remove dangling images that are safe for Docker to prune according to its rules.

Docker normally asks for confirmation.

Read the warning.

Do not automatically type `y` without understanding what is being removed.

---

# 73. Pruning More Aggressively

You may see:

```bash
docker image prune -a
```

`-a` expands cleanup beyond only dangling images to remove images not used by existing containers, according to Docker's pruning rules.

### Warning

This is more aggressive.

On a development laptop, that may simply mean images need to be pulled again.

On a production host, careless cleanup can remove cached rollback images or artifacts operators expected to remain locally available.

Understand the environment first.

---

# 74. `docker system prune`

You will also encounter:

```bash
docker system prune
```

This cleans multiple categories of unused Docker data according to the selected options.

It is broader than:

```bash
docker image prune
```

### Important

Do not use broad pruning as your first response to disk pressure.

Investigate:

```bash
docker system df
docker image ls
docker ps -a
docker volume ls
```

Then determine what is consuming space and what can safely be removed.

Volumes deserve particular care because they may contain persistent application data.

---

# 75. Safe Cleanup Reasoning

Use this model:

```text
Disk alert
   ↓
docker system df
   ↓
What is consuming space?
   ↓
Images?
Containers?
Volumes?
Build cache?
Logs?
   ↓
Which objects are actually unused?
   ↓
What rollback/recovery requirements exist?
   ↓
Clean specific objects
   ↓
Verify free space
   ↓
Prevent recurrence
```

Do not use:

```text
Disk alert
   ↓
docker system prune -a
   ↓
Hope
```

---

# 76. Architecture and Platform Differences

Not every container image can run natively on every CPU architecture.

Common CPU architectures include:

```text
amd64
arm64
```

You may also see other supported architectures depending on the image.

For example:

```text
Intel/AMD x86-64 machine
→ commonly linux/amd64
```

while many newer ARM-based systems use:

```text
linux/arm64
```

Apple Silicon Macs are a common developer example of ARM64 hosts.

---

# 77. Why Architecture Matters

Compiled binaries contain machine instructions for a target architecture.

A binary built for:

```text
amd64
```

cannot necessarily execute natively on:

```text
arm64
```

without compatibility/emulation mechanisms.

Therefore an image containing only AMD64 binaries may not run normally on an ARM64 host.

---

# 78. Platform Naming

Docker commonly expresses platform using:

```text
OS/ARCHITECTURE
```

Examples:

```text
linux/amd64
linux/arm64
```

Sometimes variants may also be involved.

The important idea is:

```text
Image compatibility
=
Operating system expectations
+
CPU architecture
+
runtime/platform support
```

---

# 79. Check Your Docker Architecture

Run:

```bash
docker info
```

Look for architecture information.

You can also inspect an image:

```bash
docker image inspect nginx
```

and examine fields such as:

```text
Architecture
Os
```

Do not assume your laptop's hardware architecture and the container platform selected by Docker are always identical when virtualization or emulation is involved.

---

# 80. Architecture Mismatch

A common failure pattern is:

```text
Developer builds image
      ↓
Image contains ARM64 binaries
      ↓
Production server expects AMD64
      ↓
Container fails or requires emulation
```

Possible symptoms can include errors resembling:

```text
exec format error
```

depending on what is incompatible.

When troubleshooting, ask:

```text
What architecture is the host?
What platform was the image built for?
Does the image support that platform?
Was emulation involved?
```

---

# 81. Multi-Platform Images

A single image name/tag can represent content for multiple platforms.

For example, conceptually:

```text
myapp:1.0
    ↓
Manifest/index
    ├── linux/amd64 → Image A
    └── linux/arm64 → Image B
```

The user writes:

```bash
docker pull myapp:1.0
```

Docker can select the appropriate platform-specific content.

---

# 82. Why Multi-Platform Images Matter

Modern development environments are mixed.

You may have:

```text
Developer laptop
→ ARM64

CI runner
→ AMD64

Production server
→ AMD64

Edge system
→ ARM64
```

A multi-platform publication strategy allows one logical release to support multiple architectures.

---

# 83. Multi-Platform Does Not Mean One Binary Runs Everywhere

This distinction matters.

A multi-platform image reference can point to **different platform-specific image manifests/content**.

Conceptually:

```text
myapp:2.0
      ↓
Multi-platform index
      │
      ├── amd64 build
      └── arm64 build
```

It does not necessarily mean one identical machine-code binary magically runs on every CPU.

---

# 84. Inspecting Multi-Platform Metadata

Modern Docker tooling can inspect registry image metadata.

For example:

```bash
docker buildx imagetools inspect nginx:latest
```

Depending on the image and tooling, this can show supported platform manifests.

You may see entries for platforms such as:

```text
linux/amd64
linux/arm64
```

and possibly others.

You do not need to master Buildx yet. We will use it more when discussing advanced builds.

---

# 85. Explicit Platform Selection

Docker supports platform selection in relevant commands.

For example:

```bash
docker pull --platform linux/amd64 <image>
```

or:

```bash
docker run --platform linux/amd64 <image>
```

This can be useful for testing or compatibility scenarios.

But do not force a platform merely to silence a warning.

Understand whether the application actually works correctly on that platform and whether emulation is being used.

---

# 86. Emulation Considerations

Docker Desktop environments can sometimes run containers built for another CPU architecture through emulation.

For example:

```text
ARM64 laptop
    ↓
Emulation
    ↓
AMD64 container
```

This can be convenient.

But it can introduce:

* Performance differences
* Compatibility problems
* Build differences
* Surprising behavior

A container working through emulation on a developer laptop does not prove the artifact is correctly built for the target production architecture.

---

# 87. Production Platform Discipline

A stronger pipeline explicitly understands its target.

For example:

```text
Source
 ↓
CI Build
 ↓
linux/amd64
linux/arm64
 ↓
Test each required platform
 ↓
Publish multi-platform release
 ↓
Registry
```

Do not discover architecture problems for the first time during deployment.

---

# 88. Official Images

Docker Hub includes images designated as Docker Official Images.

Examples commonly include repositories for technologies such as:

* Nginx
* Redis
* PostgreSQL
* Python
* Node
* Ubuntu

Official-image status has specific meaning within Docker Hub's publishing program.

It does **not** mean:

> Every version is automatically vulnerability-free forever.

It means the repository participates in Docker's official-image program and follows its processes.

---

# 89. Official Does Not Mean "No Security Work Required"

Suppose you use an official base image.

You still need to consider:

```text
Version
Patch level
Dependencies
Vulnerabilities
Configuration
Privileges
Secrets
Exposed services
Application code
Update strategy
```

Container security is a chain.

```text
Base Image
   ↓
Dependencies
   ↓
Application
   ↓
Configuration
   ↓
Runtime
   ↓
Host
```

A trusted starting point does not eliminate operational security responsibilities.

---

# 90. Choosing Trustworthy Base Images

When selecting a base image, ask:

**Who publishes it?**

Prefer known, maintained sources.

**Is it actively maintained?**

An abandoned image becomes increasingly risky.

**Does it support the architecture you need?**

Check AMD64, ARM64, or other target platforms.

**Can you choose a controlled version?**

Avoid unnecessary dependence on floating tags.

**How large is it?**

Smaller images can reduce unnecessary packages and attack surface, although smallest is not automatically best.

**Does it contain what the application needs?**

An image that is too minimal can complicate compatibility or operations.

**How is it patched?**

Understand the publisher's update process.

**Can you inspect its provenance/documentation?**

Know what you are deploying.

---

# 91. Avoid Random Images

Suppose search returns:

```text
randomuser/super-fast-nginx
```

Do not immediately deploy it because:

```text
It has a nice description.
```

Ask:

```text
Who created this?
Where is the source?
When was it last updated?
What is inside it?
Does it have known vulnerabilities?
Why do we need it instead of a maintained upstream image?
```

A container image can contain executable software.

Pulling and running an untrusted image should be treated as running untrusted software.

---

# 92. Pulling Is Different From Running

This security distinction matters.

```bash
docker pull suspicious/image
```

downloads content.

```bash
docker run suspicious/image
```

creates and executes a container workload from it.

Running unknown images creates greater risk because code is now executing in your environment.

Containers provide isolation, but containers are not a magical security boundary that makes malicious code harmless.

---

# 93. Base Image Trade-Off: Full vs Minimal

Suppose you need Python.

You might find variants conceptually like:

```text
python:<version>
python:<version>-slim
```

and other distributions/variants.

A fuller image may provide:

```text
More system utilities
More libraries
Easier debugging
Broader compatibility
```

A minimal image may provide:

```text
Smaller footprint
Fewer unnecessary packages
Potentially smaller attack surface
Faster transfers
```

But minimal images can introduce:

```text
Missing shell utilities
Missing debugging tools
Compatibility challenges
Additional build complexity
```

There is no universal rule:

> Smallest image always wins.

Choose based on application and operational requirements.

---

# 94. Alpine Images

You will often encounter Alpine Linux-based images because they can be small.

Example conceptually:

```text
node:<version>-alpine
```

But Alpine uses a different standard C library environment than many mainstream glibc-based Linux distributions.

Some applications or native dependencies may require additional work.

Therefore:

```text
Alpine
≠
automatically best
```

Evaluate:

```text
Size
Compatibility
Security maintenance
Dependencies
Debugging
Performance
Team knowledge
```

We will revisit this in advanced Dockerfile engineering.

---

# 95. Distroless and `scratch`

Later you will encounter extremely minimal production image approaches such as:

```text
distroless
```

and:

```dockerfile
FROM scratch
```

These can reduce unnecessary runtime content.

But they also affect troubleshooting and application requirements.

For example, a highly minimal image may not contain:

```text
bash
sh
curl
package manager
common diagnostic tools
```

That is not automatically a defect.

It may be intentional.

Production debugging then requires different operational techniques.

# 121. Troubleshooting: "I Changed the Container but the Image Didn't Change"

That is expected.

Architecture:

```text
Image
READ-ONLY
   ↓
Container
   ↓
Writable Layer
```

Runtime changes are not automatically written back into the original image.

If you want a new application image, the preferred workflow is:

```text
Change source/build definition
      ↓
Build new image
      ↓
Test
      ↓
Tag
      ↓
Deploy
```

Not:

```text
Enter container
      ↓
Manually change everything
      ↓
Treat container as build system
```

---

# 122. Troubleshooting: "My File Survived Restart"

Also expected.

```text
docker stop
docker start
```

use the same container.

Therefore:

```text
Same writable layer
```

remains.

But:

```text
docker rm
docker run
```

means:

```text
Old container removed
New container created
New writable layer
```

That distinction is central to Docker.

# 123. Troubleshooting: Tag Changed Unexpectedly

Suppose your deployment references:

```text
myapp:latest
```

and suddenly retrieves different content.

# What You Should Now Understand

Before moving to Part 5, you should be able to explain these points without memorized definitions:

* A Docker image is a packaged, read-only template/artifact used to create containers.
* A container is a runtime instance created from an image.
* One image can create many containers.
* Images are treated as immutable.
* Runtime changes do not modify the underlying image.
* Images contain filesystem layers and metadata.
* Image layers are read-only when used by containers.
* Containers receive their own writable layer.
* Copy-on-write allows shared image content to remain shared until modification requires writable representation.
* OverlayFS can combine lower image layers and an upper writable layer into a merged filesystem view.
* A registry stores and distributes images.
* A repository groups related image references.
* Tags are human-readable image references.
* `latest` is merely a tag.
* `latest` can move to different image content.
* Mutable tags can weaken deployment reproducibility.
* Image IDs identify locally stored image content.
* Digests provide content-addressed references.
* Tags and digests serve different purposes.
* Docker pulls image metadata and filesystem content from registries.
* Existing layers can be reused.
* `docker search` can discover Docker Hub repositories but does not establish trust.
* `docker image ls` lists local images.
* `docker image inspect` exposes image metadata.
* `docker image history` helps inspect image build/history information.
* `docker tag` creates another reference without rebuilding the image.
* Removing a tag does not necessarily remove underlying content.
* Existing containers can prevent image removal.
* Dangling images and unused images are related but not identical concepts.
* `docker image prune` can remove dangling images.
* `docker image prune -a` is more aggressive.
* `docker system df` should be used to understand Docker disk usage before broad cleanup.
* CPU architecture matters.
* `linux/amd64` and `linux/arm64` are different target platforms.
* Multi-platform image references can provide platform-specific image content under one logical tag.
* Emulation can hide architecture problems during development.
* Official images are useful trusted starting points, but they are not automatically vulnerability-free.
* Base-image selection requires consideration of maintenance, security, compatibility, architecture, size, and operational requirements.
* Running an unknown image means executing unknown software and should be treated accordingly.

# Part 4 Summary

You began with a simple question:

> What is a container actually created from?

The answer is now much deeper than simply:

> An image.

You should visualize:

```text
Registry
   ↓
Repository
   ↓
Tag / Digest
   ↓
Image
   ↓
Read-Only Layers

┌─────────────────────────────┐
│ Application Layer           │
├─────────────────────────────┤
│ Dependency Layer            │
├─────────────────────────────┤
│ Runtime/Base Layer(s)       │
└─────────────────────────────┘
```

Then Docker creates a container:

```text
Image
   ↓
Add Writable Layer
   ↓

┌─────────────────────────────┐
│ Container Writable Layer    │
├─────────────────────────────┤
│ Application Layer           │
├─────────────────────────────┤
│ Dependency Layer            │
├─────────────────────────────┤
│ Base Layer                  │
└─────────────────────────────┘
```

The image remains stable.

The container receives runtime changes.

Copy-on-write and layered filesystems make this model efficient.

Registries distribute the artifacts.

Repositories organize them.

Tags give humans convenient names.

Digests provide exact content identity.

Platform metadata ensures the correct architecture-specific image can be selected.

And image lifecycle management ensures old artifacts do not silently consume the Docker host forever.

The full mental model is now:

```text
Trusted Source
      ↓
Build
      ↓
Image Layers
      ↓
Tag
      ↓
Registry
      ↓
Pull
      ↓
Verify / Inspect
      ↓
Container
      ↓
Writable Runtime Layer
```
