# Part 3: Container Lifecycle and Essential Docker Commands

In Part 1, you learned what containers, images, registries, Docker Engine, namespaces, cgroups, and layered filesystems are.

In Part 2, you built the Docker environment and learned how the CLI communicates with the Docker daemon:

```text
Developer
   ↓
Docker CLI
   ↓
Docker API
   ↓
Docker Daemon
   ↓
Container Runtime
   ↓
Container
```

Now we move from understanding Docker to **controlling containers confidently**.

This part is extremely important because these commands become everyday tools in development, DevOps, CI/CD, troubleshooting, and production operations.

By the end, you should understand this lifecycle rather than simply memorize commands:

# 1. Start With the Correct Mental Model

A Docker container has a lifecycle.

It is not simply:

```text
Container exists
or
Container does not exist
```

A container can exist in different states.

Common states include:

```text
created
running
paused
restarting
exited
dead
```

You will most frequently work with:

```text
Created
Running
Paused
Stopped/Exited
Removed
```

Consider:

```text
Docker Image
     ↓
docker create
     ↓
Created Container
     ↓
docker start
     ↓
Running Container
     ↓
docker stop
     ↓
Stopped Container
     ↓
docker start
     ↓
Running Again
```

Eventually:

```text
Stopped Container
       ↓
docker rm
       ↓
Removed
```

Once removed, that particular container no longer exists.

The image can still remain.

---

# 2. Image Lifecycle vs Container Lifecycle

Do not confuse these two.

Suppose you have:

```text
nginx:latest
```

locally.

That is an image.

From that image you can create:

```text
nginx:latest
     │
     ├── web-1
     ├── web-2
     └── web-3
```

These are three independent containers.

You can stop `web-1`:

```text
web-1 → stopped
web-2 → running
web-3 → running
```

without deleting the image.

You can remove `web-1`:

```text
web-1 → removed
```

and the image still exists.

This distinction should become automatic:

```text
IMAGE
Template

CONTAINER
Instance created from template
```

---

# 3. Container IDs

Every Docker container receives a unique identifier.

When you create a container:

```bash
docker create nginx
```

Docker returns something resembling:

```text
6a41f9c273d8...
```

That long value is the container ID.

You usually do not need to type the entire ID.

Docker accepts a sufficiently unique shortened ID in many commands.

For example, if:

```bash
docker ps
```

shows:

```text
CONTAINER ID
6a41f9c273d8
```

you may be able to use:

```bash
docker stop 6a41f9c273d8
```

or simply:

```bash
docker stop 6a41
```

provided that prefix uniquely identifies one container.

---

# 4. Container Names

IDs are useful for Docker internally, but humans generally prefer names.

Instead of:

```bash
docker logs 6a41f9c273d8
```

you can use:

```bash
docker logs web
```

if the container is named `web`.

Names make operational commands much easier to understand.

Compare:

```bash
docker restart 91c84d7b32ab
```

with:

```bash
docker restart payment-api
```

The second tells you much more about what you are touching.

---

# 5. Automatically Generated Container Names

If you do not specify a name, Docker normally generates one.

For example:

```bash
docker run nginx
```

might create a name such as:

```text
hopeful_turing
```

or another automatically generated combination.

These names are convenient for experimentation, but predictable names are usually better for labs and manual administration.

---

# 6. Naming a Container

Use:

```bash
docker run --name veriqta-web nginx
```

Breakdown:

```text
docker
→ Docker CLI

run
→ create and start a new container

--name
→ assign a container name

veriqta-web
→ chosen container name

nginx
→ image
```

Architecture:

```text
nginx Image
     ↓
docker run
     ↓
Container
Name: veriqta-web
```

Container names must be unique among existing containers on that Docker daemon.

If `veriqta-web` already exists, attempting to create another container with the same name causes a conflict.

---

# 7. Creating Containers With `docker create`

The command:

```bash
docker create nginx
```

creates a container without starting it.

Think:

```text
Image
 ↓
docker create
 ↓
Container created
 ↓
Process NOT started
```

Example:

```bash
docker create --name veriqta-web nginx
```

Docker returns a container ID.

Now:

```bash
docker ps
```

will not normally show it because `docker ps` shows running containers by default.

Use:

```bash
docker ps -a
```

and you should find:

```text
veriqta-web
```

in a created state.

---

# 8. Why Would You Use `docker create`?

Most of the time, beginners use:

```bash
docker run
```

because they want to create and immediately start a container.

But separating creation and startup is useful for understanding Docker's lifecycle and can be useful when you want to prepare a container before starting it.

Think:

```text
docker create
→ prepare container

docker start
→ start existing container
```

---

# 9. Running Containers With `docker run`

`docker run` is one of Docker's most important commands.

At a simplified level:

```text
docker run
=
docker create
+
docker start
```

For example:

```bash
docker run nginx
```

means:

```text
Find nginx image
      ↓
If missing, pull it
      ↓
Create new container
      ↓
Configure container
      ↓
Start main process
```

This creates a **new container**.

That word "new" matters.

---

# 10. `docker run` Does Not Mean "Start My Existing Container"

Suppose you run:

```bash
docker run --name web nginx
```

Then stop it:

```bash
docker stop web
```

If you want that same container again, use:

```bash
docker start web
```

Do not run:

```bash
docker run --name web nginx
```

again.

Why?

Because `docker run` tries to create another new container.

But the name `web` already belongs to the stopped container.

You may receive a name-conflict error.

Remember:

```text
docker run
→ create NEW container + start it

docker start
→ start EXISTING container
```

---

# 11. Foreground Mode

Run:

```bash
docker run --name web nginx
```

Without detached mode, the container normally remains attached to your terminal's foreground.

Conceptually:

```text
Terminal
   ↕
Container
   ↓
Nginx
```

Your terminal is attached to the container's output streams.

You may see logs appear directly.

This is useful when:

```text
Testing applications
Watching startup output
Debugging
Running short-lived commands
```

But for a long-running web server, you often want your terminal back.

That is where detached mode helps.

---

# 12. Detached Mode

Run:

```bash
docker run -d --name web nginx
```

`-d` means:

**detached mode**

Conceptually:

```text
Terminal
   ↓
docker run -d
   ↓
Container starts
   ↓
Terminal returns to you

Container continues running
```

Docker usually prints the new container ID.

Then your shell prompt returns.

Verify:

```bash
docker ps
```

You should see `web` running.

---

# 13. Detached vs Foreground

Remember:

```text
Foreground
Terminal remains attached to container output
```

versus:

```text
Detached
Container runs without occupying your terminal session
```

Example foreground:

```bash
docker run nginx
```

Example detached:

```bash
docker run -d nginx
```

Detached mode does **not** mean the container runs without a process.

It means your terminal is not continuously attached to the container's standard streams.

---

# 14. Listing Running Containers

Run:

```bash
docker ps
```

You may see columns such as:

```text
CONTAINER ID
IMAGE
COMMAND
CREATED
STATUS
PORTS
NAMES
```

Each column tells you something useful.

`CONTAINER ID` identifies the container.

`IMAGE` shows what image created it.

`COMMAND` indicates the configured command/process.

`CREATED` indicates when it was created.

`STATUS` tells you its current state.

`PORTS` shows relevant published/exposed port information.

`NAMES` shows the human-readable name.

---

# 15. Structured Form of `docker ps`

You may also use:

```bash
docker container ls
```

Conceptually:

```text
docker container ls
```

and:

```text
docker ps
```

both list running containers.

The structured form helps reveal the object model:

```text
docker container ...
docker image ...
docker network ...
docker volume ...
```

In real environments, you will see both forms.

---

# 16. Listing All Containers

Run:

```bash
docker ps -a
```

`-a` means all containers.

This includes containers that are:

```text
Running
Stopped
Exited
Created
```

This distinction is crucial during troubleshooting.

Suppose:

```bash
docker ps
```

does not show your application.

Do not immediately conclude:

> Docker deleted it.

Run:

```bash
docker ps -a
```

The container may simply have exited.

---

# 17. Running vs Stopped Containers

Consider:

```text
web       Up 20 minutes
database  Exited (0) 5 minutes ago
api       Exited (1) 30 seconds ago
```

These states tell different stories.

`web` is currently running.

`database` stopped with exit code `0`.

`api` stopped with exit code `1`.

Exit codes become important shortly.

---

# 18. Starting an Existing Container

Suppose:

```bash
docker ps -a
```

shows:

```text
veriqta-web    Exited
```

Start it:

```bash
docker start veriqta-web
```

Breakdown:

```text
docker
→ Docker CLI

start
→ start existing container

veriqta-web
→ target
```

Verify:

```bash
docker ps
```

You should now see it running.

---

# 19. Starting Multiple Containers

Docker commands can often accept multiple container identifiers.

For example:

```bash
docker start web api redis
```

This asks Docker to start the three existing containers.

Similarly:

```bash
docker stop web api redis
```

can stop them.

Be especially careful when operating on multiple production containers.

Always verify the target names first.

---

# 20. Stopping Containers

Run:

```bash
docker stop web
```

Docker attempts a graceful stop.

At a simplified level:

```text
docker stop
    ↓
Termination request
    ↓
Main container process
    ↓
Opportunity to shut down
    ↓
Container stops
```

On Linux workloads, this commonly involves sending a termination signal such as `SIGTERM`, followed by a forceful signal if the process does not stop within the configured timeout.

The exact behavior can depend on image/container configuration and Docker options.

---

# 21. Why Graceful Shutdown Matters

Imagine a database container is writing data.

A graceful shutdown can allow the application to:

```text
Finish current work
Flush buffers
Close connections
Write state
Release resources
Exit cleanly
```

Abruptly terminating processes can cause incomplete work or other problems.

This is why:

```bash
docker stop
```

and:

```bash
docker kill
```

should not be treated as identical.

---

# 22. Restarting Containers

Run:

```bash
docker restart web
```

This stops and then starts the container.

Conceptually:

```text
Running
   ↓
Stop
   ↓
Stopped
   ↓
Start
   ↓
Running
```

Verify:

```bash
docker ps
```

Restarting can be useful after certain application conditions, but it should not become your default troubleshooting strategy.

A container repeatedly needing restarts usually deserves investigation.

---

# 23. Do Not Use Restart as Root-Cause Analysis

Suppose an API stops responding.

A weak troubleshooting approach is:

```text
Application broken
      ↓
Restart container
      ↓
Works again
      ↓
Done
```

You still do not know why it failed.

A stronger approach is:

```text
Observe symptom
      ↓
Check state
      ↓
Read logs
      ↓
Inspect process/resources/configuration
      ↓
Determine likely cause
      ↓
Mitigate
      ↓
Verify
      ↓
Prevent recurrence
```

Restarting can be a mitigation.

It is not automatically a root-cause analysis.

---

# 24. Pausing Containers

Docker can pause processes inside a running container.

Run:

```bash
docker pause web
```

Conceptually:

```text
Running Processes
       ↓
Pause
       ↓
Processes suspended
```

The container still exists.

Its processes have not been removed.

They are temporarily suspended.

Check:

```bash
docker ps
```

The status should indicate that the container is paused.

---

# 25. Unpausing Containers

Resume:

```bash
docker unpause web
```

Conceptually:

```text
Paused
   ↓
Unpause
   ↓
Running
```

Pausing is different from stopping.

```text
PAUSE
Processes remain but execution is suspended.

STOP
Main process is terminated gracefully and container becomes stopped.
```

This distinction matters.

---

# 26. Killing Containers

Run:

```bash
docker kill web
```

By default, Docker sends a forceful termination signal to the container's main process, commonly `SIGKILL` for Linux containers.

Conceptually:

```text
Running
   ↓
docker kill
   ↓
Immediate termination
   ↓
Exited
```

This is much more abrupt than a normal graceful stop.

---

# 27. `docker stop` vs `docker kill`

Remember:

```text
docker stop
→ asks application to terminate gracefully first
```

versus:

```text
docker kill
→ by default forcefully terminates it
```

Use `docker kill` when forceful termination is actually required.

Do not use it merely because it sounds faster.

---

# 28. Sending Specific Signals With `docker kill`

Despite its name, `docker kill` can send signals other than the default.

For example:

```bash
docker kill --signal=SIGHUP web
```

Some applications interpret `SIGHUP` as a request to reload configuration.

Whether this works depends entirely on the application.

Do not send arbitrary signals to production applications without understanding how they respond.

---

# 29. Removing Containers

Stopped containers continue to consume some metadata/storage resources.

Remove a stopped container:

```bash
docker rm web
```

Afterward:

```bash
docker ps -a
```

should no longer show it.

Remember:

```text
Stop
≠
Remove
```

Stopping changes runtime state.

Removing deletes that container object and its writable container layer.

---

# 30. Removing Running Containers

If you try:

```bash
docker rm web
```

while `web` is running, Docker normally refuses.

You should generally:

```bash
docker stop web
docker rm web
```

There is also a force option:

```bash
docker rm -f web
```

This forcefully removes a running container.

### Warning

Do not casually use:

```bash
docker rm -f
```

on important workloads.

It combines destructive actions and can abruptly terminate the application.

Use deliberate stop-and-remove workflows unless force is genuinely required.

---

# 31. Automatically Removing Containers

For temporary containers, use:

```bash
docker run --rm hello-world
```

`--rm` means:

> Automatically remove this container after it exits.

Flow:

```text
Create
 ↓
Start
 ↓
Process runs
 ↓
Process exits
 ↓
Container automatically removed
```

This is useful for:

```text
Temporary commands
Tests
Build utilities
Disposable labs
One-off tools
```

---

# 32. Why `--rm` Is Useful

Without automatic removal, repeated experiments can leave many stopped containers:

```text
Exited container
Exited container
Exited container
Exited container
...
```

With:

```bash
docker run --rm ...
```

temporary containers clean themselves up when they finish.

But do not use `--rm` when you expect to inspect the stopped container afterward.

Once it is automatically removed, its container metadata is gone.

---

# 33. Executing Commands Inside a Running Container

One of the most useful Docker commands is:

```bash
docker exec
```

It runs an additional command inside an **already running container**.

For example:

```bash
docker exec web nginx -v
```

Conceptually:

```text
Running Container
      │
      ├── Main Process: nginx
      │
      └── New exec process: nginx -v
```

`docker exec` does not create a new container.

It creates another process inside the existing container's environment.

---

# 34. `docker run` vs `docker exec`

This distinction is essential.

```bash
docker run nginx
```

means:

> Create a new container from the Nginx image and start it.

While:

```bash
docker exec web <command>
```

means:

> Run an additional command inside the already-running `web` container.

Think:

```text
docker run
IMAGE → NEW CONTAINER
```

versus:

```text
docker exec
EXISTING RUNNING CONTAINER → NEW PROCESS INSIDE IT
```

---

# 35. Interactive Terminals

You will often see:

```bash
docker exec -it web sh
```

Let's break it down.

```text
docker
→ Docker CLI

exec
→ execute command in running container

-i
→ keep standard input open

-t
→ allocate a pseudo-terminal

web
→ container

sh
→ shell to execute
```

Combined:

```text
-it
```

gives you an interactive terminal-like session.

---

# 36. `sh` vs `bash`

Many tutorials use:

```bash
docker exec -it container bash
```

But not every image contains Bash.

Minimal images may contain only:

```text
/bin/sh
```

So:

```bash
docker exec -it web sh
```

may work where:

```bash
docker exec -it web bash
```

fails.

This teaches an important container principle:

> Do not assume a container contains every utility available on your host.

Images can intentionally be minimal.

---

# 37. Entering a Container

Suppose we have:

```bash
docker run -d --name web nginx
```

Enter it:

```bash
docker exec -it web sh
```

Your prompt changes because you are now running a shell process inside the container.

Try:

```bash
pwd
```

Then:

```bash
ls
```

Then:

```bash
hostname
```

Then:

```bash
cat /etc/os-release
```

You are viewing the container's environment.

Remember:

```text
Host shell
   ↓
docker exec
   ↓
Container namespace/filesystem environment
   ↓
Shell process
```

---

# 38. Leaving an `exec` Shell

If you entered using:

```bash
docker exec -it web sh
```

you can normally exit the shell with:

```bash
exit
```

This terminates the shell process you created with `docker exec`.

It does **not** necessarily stop the container's main process.

Conceptually:

```text
Container
├── Main nginx process ← still running
└── sh process ← exits
```

So after:

```bash
exit
```

check:

```bash
docker ps
```

The Nginx container should still be running.

---

# 39. Modifying a Running Container

Enter:

```bash
docker exec -it web sh
```

Create a file:

```bash
echo "VERIQTA Docker Lab" > /tmp/veriqta.txt
```

Breakdown:

```text
echo
→ output text

"VERIQTA Docker Lab"
→ text

>
→ redirect output into file

/tmp/veriqta.txt
→ destination
```

Verify:

```bash
cat /tmp/veriqta.txt
```

Expected:

```text
VERIQTA Docker Lab
```

Now exit:

```bash
exit
```

The file belongs to that container's writable filesystem layer.

---

# 40. Stop and Restart After Modification

Stop:

```bash
docker stop web
```

Restart:

```bash
docker start web
```

Enter again:

```bash
docker exec -it web sh
```

Check:

```bash
cat /tmp/veriqta.txt
```

The file should normally still exist.

Why?

Because you stopped and restarted the **same container**.

You did not remove it.

This is a crucial distinction.

```text
Stop container
→ writable layer remains

Remove container
→ writable layer is removed
```

---

# 41. Why This Is Not Persistent Storage

You may now think:

> My file survived restart, so container storage is persistent.

Be careful.

It persisted across a **container restart**.

It does not survive removal of that container's writable layer.

If you:

```bash
docker rm web
```

and create a brand-new container:

```bash
docker run -d --name web nginx
```

the new container will not automatically contain:

```text
/tmp/veriqta.txt
```

That file belonged to the old container.

Persistent application data will be handled properly with:

```text
Docker volumes
Bind mounts
```

later in the series.

---

# 42. `docker attach`

Docker provides:

```bash
docker attach web
```

This attaches your terminal to the existing container's main process streams.

Conceptually:

```text
Terminal
   ↓
docker attach
   ↓
Existing Main Container Process
```

This is different from:

```bash
docker exec -it web sh
```

---

# 43. `docker attach` vs `docker exec`

This distinction causes confusion.

### `docker attach`

Attaches to the container's existing main process.

```text
Terminal
   ↓
Existing Process
```

### `docker exec`

Creates an additional process inside the running container.

```text
Container
├── Existing main process
└── New exec process
```

For troubleshooting, engineers often prefer:

```bash
docker exec -it web sh
```

because it opens a separate shell without replacing or directly controlling the main process.

---

# 44. Be Careful When Attached

When attached to a container, keyboard input may be sent directly to the container's main process.

Depending on how the container was started and configured, actions such as sending interrupt signals can affect the main process.

Do not casually experiment with `docker attach` against important production containers.

For inspection, `docker logs` and `docker exec` are often safer starting points.

---

# 45. Detaching Without Stopping

For containers that support the normal Docker detach-key sequence, the default sequence is commonly:

```text
Ctrl+P
Ctrl+Q
```

This detaches your terminal while leaving the container running.

Do not confuse:

```text
Detach
```

with:

```text
Stop
```

Detach:

```text
Terminal disconnects
Container continues
```

Stop:

```text
Container's main process terminates
```

---

# 46. Container Logs

Run:

```bash
docker logs web
```

This retrieves logs captured by Docker's configured logging mechanism from the container's standard output and standard error streams.

Conceptually:

```text
Application
   ↓
stdout / stderr
   ↓
Docker logging driver
   ↓
docker logs
   ↓
Engineer
```

Logs are one of your first troubleshooting tools.

---

# 47. Why Logs Matter

Suppose:

```bash
docker ps -a
```

shows:

```text
api    Exited (1)
```

The next question is:

> Why did the process exit?

Run:

```bash
docker logs api
```

You might discover:

```text
Database connection refused
```

or:

```text
Missing environment variable
```

or:

```text
Permission denied
```

or:

```text
Configuration syntax error
```

Now you have evidence.

---

# 48. Following Logs in Real Time

Run:

```bash
docker logs -f web
```

`-f` means:

**follow**

Instead of printing existing logs and immediately returning, Docker continues showing new log entries.

Conceptually:

```text
Application produces log
       ↓
Docker captures it
       ↓
Terminal displays it
       ↓
Wait for next log
```

This is useful when reproducing a problem.

For example:

```text
Terminal 1
docker logs -f api
```

Then in another terminal:

```text
Send request to API
```

Watch what happens in the logs.

---

# 49. Showing Recent Logs

Containers may have large logs.

Instead of displaying everything:

```bash
docker logs --tail 50 web
```

This requests the most recent 50 lines.

You can combine options:

```bash
docker logs -f --tail 50 web
```

Meaning:

```text
Show recent 50 lines
then
continue following new logs
```

This is extremely useful in troubleshooting.

---

# 50. Timestamps in Logs

You can request timestamps:

```bash
docker logs -t web
```

Timestamps help correlate container events with:

```text
Application errors
Load balancer failures
Database problems
Deployments
Monitoring alerts
User reports
```

In production incidents, time correlation matters.

---

# 51. Inspecting Containers

Run:

```bash
docker inspect web
```

Docker returns detailed JSON describing the container.

This can include:

```text
Container ID
Created time
State
Image
Command
Environment
Mounts
Network settings
Port configuration
Restart policy
Resource settings
```

Think of `inspect` as:

> Show me how Docker sees and has configured this object.

---

# 52. Inspecting Specific Information

The full JSON can be overwhelming.

Docker supports formatted inspection using Go templates.

For example:

```bash
docker inspect -f '{{.State.Status}}' web
```

This requests the container's state status.

You might receive:

```text
running
```

Another useful example:

```bash
docker inspect -f '{{.State.ExitCode}}' web
```

This retrieves the exit code stored in the container state.

You do not need to master Go templates yet.

Just know that `inspect` can be filtered.

# 54. Monitoring One Container

Instead of every running container:

```bash
docker stats web
```

# 62. Port Publishing Basics

A web application can run correctly inside a container and still be inaccessible from your host.

Suppose Nginx listens on:

```text
Container port 80
```

Run:

```bash
docker run -d --name web nginx
```

Nginx is running.

But you have not explicitly published a host port.

To publish one:

```bash
docker run -d --name web -p 8080:80 nginx
```

---

# 63. Understanding `-p 8080:80`

This is one of Docker's most important syntax patterns.

```text
8080:80
  ↑   ↑
host container
```

Meaning:

```text
Host Port 8080
      ↓
Container Port 80
```

Architecture:

```text
Browser
   ↓
localhost:8080
   ↓
Host Port 8080
   ↓
Docker Port Publishing
   ↓
Container Port 80
   ↓
Nginx
```

Then you can usually visit:

```text
http://localhost:8080
```

on your local machine.

---

# 64. Host Port vs Container Port

Do not confuse them.

If the application listens on port 80 inside the container:

```text
Container
└── Nginx :80
```

you can map another host port:

```bash
-p 8080:80
```

or:

```bash
-p 9090:80
```

The application still listens on port 80 **inside** the container.

Only the host-side entry point changed.

---

# 65. Two Containers Using the Same Internal Port

This is possible:

```bash
docker run -d --name web1 -p 8081:80 nginx
docker run -d --name web2 -p 8082:80 nginx
```

Architecture:

```text
Host
├── :8081 → web1:80
└── :8082 → web2:80
```

Both containers use internal port 80.

But they use different host ports.

This is a fundamental reason containerized applications can coexist on one host.

---

# 66. Host Port Conflicts

What if you run:

```bash
docker run -d --name web1 -p 8080:80 nginx
```

then try:

```bash
docker run -d --name web2 -p 8080:80 nginx
```

The second container cannot normally bind the same host IP/port combination already in use.

You may see an error indicating the port is already allocated or cannot be bound.

Troubleshooting:

```text
Port binding failed
      ↓
Which host port?
      ↓
Is another container using it?
      ↓
docker ps
```

You can also inspect host networking tools, which we will cover later.

---

# 67. Publishing Ports and Security

Be careful with port publishing.

Publishing a port can make an application reachable beyond the container network and, depending on host binding, firewall rules, cloud security groups, and environment, potentially beyond the host itself.

In cloud environments, think:

```text
Internet
   ↓
Security Group / Firewall
   ↓
Host Port
   ↓
Docker Published Port
   ↓
Container
```

Do not publish databases, administrative interfaces, or internal services publicly without understanding the exposure.

Docker networking gets a full dedicated part later.

# 72. Exit Codes

When a process finishes, it returns an exit code.

A general Unix convention is:

```text
0
→ success

non-zero
→ some form of failure or special condition
```

The exact meaning of non-zero codes depends on the application.

For containers, the main process's exit code becomes extremely useful.

Run:

```bash
docker ps -a
```

You may see:

```text
Exited (0)
```

or:

```text
Exited (1)
```

---

# 73. Exit Code 0

Conceptually:

```text
Exited (0)
```

usually means the main process completed successfully.

For example:

```bash
docker run hello-world
```

prints its message and exits normally.

The container stopping is not automatically an error.

Some containers are intended to run short jobs.

---

# 74. Non-Zero Exit Codes

Suppose:

```text
api    Exited (1)
```

This suggests the main process returned a non-zero exit code.

But:

```text
Exit code 1
```

alone does not tell you the exact root cause.

Investigate:

```bash
docker logs api
```

and:

```bash
docker inspect api
```

You might discover:

```text
Configuration missing
File unavailable
Permission denied
Dependency unavailable
Application crash
```

---

# 75. Inspecting Exit Codes

You can retrieve the stored exit code:

```bash
docker inspect -f '{{.State.ExitCode}}' app
```

You can also inspect:

```bash
docker inspect app
```

and find state information.

This is particularly useful in automated troubleshooting and CI/CD.

---

# 76. Important Exit Code: 137

You may encounter:

```text
Exited (137)
```

A process exiting with 137 often indicates termination by `SIGKILL` because:

```text
128 + 9 = 137
```

where signal 9 is `SIGKILL`.

One possible cause is an out-of-memory kill, but **137 does not by itself prove OOM**.

Investigate container state:

```bash
docker inspect <container>
```

Look for evidence such as:

```text
OOMKilled
```

Also examine:

```text
Host memory
Container memory limits
Application behavior
Kernel/system logs
```

This is evidence-based troubleshooting.

# 77. Restart Policies

What happens if a container crashes?

By default, Docker does not necessarily keep restarting every container forever.

Docker provides restart policies.

Common policies include:

```text
no
on-failure
always
unless-stopped
```

They control whether Docker attempts to restart a container after particular stop/failure conditions.

---

# 78. Default Restart Policy: `no`

The default is generally:

```text
no
```

Meaning Docker does not automatically restart the container simply because its process exits.

Example:

```bash
docker run -d --name web nginx
```

If the process fails, the container may remain stopped.

---

# 79. `on-failure`

Example:

```bash
docker run -d \
  --name app \
  --restart on-failure \
  myapp
```

This asks Docker to restart the container when the process exits unsuccessfully according to the policy's semantics.

You can also encounter retry limits, for example:

```bash
--restart on-failure:5
```

This limits restart attempts.

This can be useful for transient failures.

But repeated restarts can also hide a broken application if nobody investigates.

---

# 80. `always`

Example:

```bash
docker run -d \
  --name web \
  --restart always \
  nginx
```

This configures Docker to keep the container running according to the `always` restart-policy behavior, including daemon restart scenarios, subject to Docker's documented policy semantics.

This may be appropriate for certain long-running services.

But:

```text
Restart policy
≠
Application health management
```

A process can be running while the application is unhealthy.

---

# 81. `unless-stopped`

Example:

```bash
docker run -d \
  --name web \
  --restart unless-stopped \
  nginx
```

This behaves similarly to `always` in many situations but preserves an explicit stopped state across relevant daemon restart scenarios according to Docker's restart-policy rules.

You do not need to memorize every edge case yet.

Understand the purpose:

```text
Restart policy
→ Tell Docker when it should automatically restart a container.
```

---

# 82. Restart Loops

A restart policy can create a situation like:

```text
Application starts
      ↓
Crashes
      ↓
Docker restarts
      ↓
Application starts
      ↓
Crashes
      ↓
Docker restarts
      ↓
...
```

This is a restart loop.

If you see:

```text
Restarting
```

do not simply wait.

Investigate:

```bash
docker ps
docker logs <container>
docker inspect <container>
```

Common causes include:

```text
Missing environment variable
Bad startup command
Database unavailable
Permission problem
Configuration error
Missing file
Application crash
```

---

# 83. Updating a Restart Policy

You can update the restart policy of an existing container:

```bash
docker update --restart unless-stopped web
```

This introduces another useful command:

```text
docker update
```

which modifies supported runtime configuration for existing containers.

Our focus remains lifecycle commands, but you should know you do not necessarily need to recreate a container merely to change every supported setting.

# 87. Troubleshooting Scenario: Container Won't Stop

You run:

```bash

```

but the application does not terminate as expected.

Investigate before immediately forcing it.

Questions:

```text

What is PID 1?
Is graceful shutdown stuck?
Is the application waiting on something?
How long is the stop timeout?
```

If force is necessary:

```bash
docker kill app
```

may terminate it.

But document why graceful shutdown failed.

In production, improper signal handling can become a deployment reliability problem.

You run:

```bash

```

> docker exec is broken.

Try to understand the image.

Try:

```bash

```

If that works:

```text
docker exec ✓
Container ✓
bash missing
sh available
```

You identified the actual problem.

# 89. Troubleshooting Scenario: `docker exec` Says Container Is Not Running

`docker exec` operates on a running container.

If:

```bash
docker ps -a
```

shows:

```text
Exited
```

you cannot use normal `docker exec` to start a shell inside that stopped container.

Instead investigate:

```bash
docker logs app
docker inspect app
```

Then determine why its main process failed.

You may start the existing container if appropriate:

```bash
docker start app
```

But if it immediately exits again, logs and configuration are more important than repeatedly starting it.

# 90. Troubleshooting Scenario: Port Already Allocated

You run:

```bash

```

and receive a port binding error.

Check:

```bash

```

Look for another container publishing:

```text

```

or equivalent.

Reasoning:

```text

       ↓
Host port required
       ↓
Host port already occupied
       ↓

```

Possible fix in a lab:

```bash

```

But in production, determine why the expected port is occupied before changing architecture.

# 91. Troubleshooting Scenario: File Vanished

You entered a container and created:

```text
/tmp/test.txt
```

Then you stopped and removed the container.

Later you created a new container from the same image.

The file is missing.

Why?

```text
Old Container
├── Image layers
└── Writable layer
       └── /tmp/test.txt
```

When you removed the old container:

```text
Writable layer removed
```

The new container gets:

```text
Same image
+
New writable layer
```

Therefore the file does not return.

This is expected behavior.

# 94. Production Thinking: Containers Should Be Replaceable

Entering a production container and manually changing files can be useful for diagnosis, but it should generally not become your deployment process.

Bad operational model:

```text
Production container
      ↓
docker exec
      ↓
Install package manually
      ↓
Edit application
      ↓
Hope nobody replaces container
```

Better model:

```text
Source
 ↓
Change
 ↓
Build new image
 ↓
Test
 ↓
Deploy new container
```

Containers should generally be treated as replaceable runtime instances.

# What You Should Now Understand

Before moving to Part 4, you should be able to explain and use these concepts confidently:

* Containers have lifecycle states.
* Images and containers are different objects.
* Every container receives an ID.
* Containers can also have human-readable names.
* `docker create` creates a container without starting it.
* `docker run` creates and starts a new container.
* `docker start` starts an existing container.
* `docker ps` lists running containers.
* `docker ps -a` includes stopped containers.
* Detached mode returns control of your terminal while the container continues running.
* Foreground mode keeps your terminal attached to the container's standard streams.
* `docker stop` attempts graceful termination.
* `docker kill` provides signal-based forceful termination by default.
* `docker restart` stops and starts an existing container.
* `docker pause` suspends container processes.
* `docker unpause` resumes them.
* `docker rm` removes a container.
* `--rm` automatically removes a container after it exits.
* `docker exec` creates an additional process inside a running container.
* `docker attach` attaches to the existing main process.
* `-it` is commonly used for interactive terminal sessions.
* Not every image contains Bash.
* `docker logs` retrieves container output handled by Docker's logging mechanism.
* `docker logs -f` follows new logs.
* `docker inspect` exposes detailed state and configuration.
* `docker stats` shows live resource usage.
* `docker top` shows container processes.
* `docker cp` transfers files between host and container.
* `-p HOST:CONTAINER` publishes a container port.
* `-e` supplies environment variables.
* Environment variables should not automatically be treated as secure secret storage.
* Exit code `0` generally indicates successful completion.
* Non-zero exit codes require interpretation.
* Exit code 137 can indicate `SIGKILL`, but you need additional evidence before concluding OOM.
* Restart policies determine when Docker automatically restarts containers.
* Restart loops should be investigated, not ignored.
* A container's writable layer survives stop/start but disappears when that container is removed.
* Manual production changes inside containers are generally not a durable deployment strategy.

# Knowledge Check Answers

**1.** An image is the packaged template. A container is an instance created from that image.

**2.** It creates a new container without starting its main process.

**3.** `docker run` creates a new container and starts it.

**4.** `docker run` creates a new container. `docker start` starts the existing container.

**5.** Detached mode. The container runs while the Docker client returns control of your terminal.

**6.** `docker ps` lists running containers by default. `docker ps -a` includes stopped and other non-running containers.

**7.** The ID is Docker's unique identifier for the container. The name is a human-readable identifier that can be assigned or automatically generated.

**8.** `docker stop` normally attempts graceful termination first. `docker kill` sends a specified signal, using forceful termination by default for typical Linux containers.

**9.** Its processes are temporarily suspended without removing the container.

**10.** No. A stopped container still exists.

**11.** It automatically removes the container when the container exits.

**12.** It runs an additional command/process inside an already-running container.

**13.** `-i` keeps standard input open and `-t` allocates a pseudo-terminal, commonly enabling an interactive terminal session.

**14.** The image may not contain Bash. A smaller shell such as `sh` may be available instead.

**15.** `attach` connects to the existing main process's streams. `exec` starts an additional process inside the running container.

**16.** It displays existing logs and continues following new log output.

**17.** It provides detailed Docker configuration and state information for the container.

**18.** `docker stats` shows resource usage. `docker top` shows processes associated with the container.

**19.** It copies `/tmp/test.txt` from the `app` container to the current host directory.

**20.** Host port `8080` is published to container port `80`.

```text
Host :8080
   ↓
Container :80
```

**21.** It supplies an environment variable to the container.

**22.** Successful process completion by general Unix convention.

**23.** No. It commonly corresponds to termination by `SIGKILL`. OOM is one possible reason, but you need additional evidence such as the container's OOM state and host/resource information.

**24.** A restart policy tells Docker under which conditions it should automatically restart a container.

**25.** Restarting uses the same container and therefore preserves its writable layer. Removing the container removes that container-specific writable layer. A newly created container receives a new writable layer.
