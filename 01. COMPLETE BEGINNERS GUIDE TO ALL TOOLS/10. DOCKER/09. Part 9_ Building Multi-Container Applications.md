# Part 9: Building Multi-Container Applications

## Move Beyond One Isolated Container

Up to this point, you have learned how to work with individual containers.

You can take an application, build an image, create a container, publish a port, attach storage, and connect containers to Docker networks.

But most real applications are not one process running inside one container.

A typical application may contain:

```text
Browser
   ↓
Frontend
   ↓
Backend / API
   ↓
Database
```

Each component has a different responsibility.

Instead of placing everything inside one large container, we can run the components separately:

```text
Browser
   ↓
Frontend Container
   ↓
Backend/API Container
   ↓
Database Container
```

This introduces a new challenge.

The containers must work together as one application.

They need:

* networking;
* service discovery;
* runtime configuration;
* internal ports;
* external ports;
* persistent storage;
* startup coordination;
* health checks;
* logging;
* troubleshooting.

In this part, you will build the complete stack manually.

You will not use Docker Compose yet.

That is intentional.

Before Docker Compose automates multi-container applications, you need to understand exactly what it will be automating.

# 3. Why Applications Use Multiple Containers

Consider a web application containing:

```text
Frontend
Backend
Database
```

Each component performs a different job.

The frontend presents information to users.

The backend performs application logic.

The database stores persistent information.

You could attempt to install all three inside one container:

```text
One Container
├── Nginx
├── Python
├── Flask
├── PostgreSQL
└── Application
```

That might work technically.

But it creates unnecessary coupling.

Suppose you need to upgrade PostgreSQL.

Why should the frontend need replacement?

Suppose you change the frontend.

Why should the database be recreated?

Suppose the backend crashes.

Why should PostgreSQL stop?

Separating components allows each one to have its own lifecycle.

A cleaner design is:

```text
Frontend Container
        |
        v
Backend Container
        |
        v
Database Container
```

---

# 4. One Concern Per Container

A useful container design principle is:

```text
One primary concern per container
```

This does not mean that a container can literally contain only one operating-system process in every possible situation.

It means the container should normally have one clear responsibility.

For our application:

| Container | Primary Responsibility                         |
| --------- | ---------------------------------------------- |
| Frontend  | Serve the web interface and proxy API requests |
| Backend   | Execute application logic and expose an API    |
| Database  | Store application data                         |

This creates clear boundaries.

---

# 5. Benefits of Separating Components

Separating components gives us several advantages.

## Independent replacement

If the backend changes:

```text
Replace Backend
```

without deliberately replacing:

```text
Database
```

## Independent scaling

If the backend becomes busy, an architecture can eventually support:

```text
             ┌→ Backend 1
Frontend → LB
             └→ Backend 2
```

without creating multiple databases unnecessarily.

## Easier troubleshooting

If PostgreSQL fails, you investigate the database component.

If Nginx fails, you investigate the frontend component.

## Better security boundaries

The database does not need to be exposed directly to users.

## Cleaner image design

Each image contains only what its component requires.

---

# 6. Multi-Container Does Not Automatically Mean Microservices

Do not confuse:

```text
multi-container application
```

with:

```text
microservices architecture
```

A three-container application containing frontend, backend, and database is a multi-container application.

Microservices introduce additional architectural concerns such as:

* service boundaries;
* independent ownership;
* independent deployment;
* distributed data;
* API contracts;
* service discovery;
* resilience;
* distributed tracing;
* asynchronous communication.

Our goal here is simpler.

We are learning how several containers communicate as one application.

# 9. External Communication vs Internal Communication

This distinction is fundamental.

## External communication

Communication enters Docker from outside the application.

Example:

```text
Browser
   ↓
Host
   ↓
Frontend Container
```

## Internal communication

Containers communicate with other containers.

Example:

```text
Frontend
   ↓
Backend
```

and:

```text
Backend
   ↓
Database
```

These paths do not all require host-published ports.

---

# 10. Our Port Design

We will use:

| Service    | Container Port | Host Port | Public to Host? |
| ---------- | -------------: | --------: | --------------- |
| Frontend   |             80 |      8080 | Yes             |
| Backend    |           5000 |      None | No              |
| PostgreSQL |           5432 |      None | No              |

Therefore:

```text
Browser
   ↓
localhost:8080
   ↓
Frontend:80
   ↓
Backend:5000
   ↓
Database:5432
```

Only the frontend needs to be published to the host.

---

# 11. Why Backend Does Not Need a Published Port

The browser does not communicate directly with the backend in our architecture.

The frontend proxies API requests to it.

Therefore this is unnecessary:

```bash
-p 5000:5000
```

The backend can still listen on:

```text
5000
```

inside the Docker network.

---

# 12. Why PostgreSQL Does Not Need a Published Port

PostgreSQL listens on:

```text
5432
```

But the backend is the component that needs PostgreSQL.

The backend can communicate with PostgreSQL directly through Docker networking.

Therefore we do not need:

```bash
-p 5432:5432
```

for this application.

This reduces unnecessary host exposure.

---

# 13. Published Ports vs Container Ports

Suppose you run:

```bash
docker run -p 8080:80 nginx
```

The syntax is:

```text
HOST_PORT:CONTAINER_PORT
```

Therefore:

```text
8080:80
```

means:

```text
Host Port 8080
      ↓
Container Port 80
```

Nginx still listens on port:

```text
80
```

inside the container.

Docker forwards traffic from host port 8080.

---

# 14. `EXPOSE` Does Not Publish a Port

A Dockerfile might contain:

```dockerfile
EXPOSE 5000
```

This does not make port 5000 accessible from the host.

`EXPOSE` documents the port that the application is expected to use.

Actual publishing requires something such as:

```bash
-p 5000:5000
```

Therefore:

```text
EXPOSE
≠
publish
```

---

# 15. The `localhost` Problem

This is one of the most important concepts in multi-container applications.

Suppose the backend tries:

```text
localhost:5432
```

to connect to PostgreSQL.

Will that reach the database container?

No.

Inside the backend container:

```text
localhost
```

means:

```text
the backend container itself
```

It does not mean:

```text
the Docker host
```

and it does not mean:

```text
another container
```

---

# 16. `localhost` Depends on Where You Are

From your host:

```text
localhost
=
your host
```

From the frontend container:

```text
localhost
=
frontend container
```

From the backend container:

```text
localhost
=
backend container
```

From the database container:

```text
localhost
=
database container
```

Therefore:

```text
Backend → localhost:5432
```

means:

```text
Backend → Backend:5432
```

That is not where PostgreSQL is running.


Then the backend can use:


# 18. Docker DNS

Docker provides embedded DNS/name resolution for containers on appropriate user-defined networks.

This allows:

```text
veriqta-backend
```

to find:

```text
veriqta-db
```

without hardcoding a container IP address.

The backend can use:

```text
DB_HOST=veriqta-db
```

Docker resolves that name to the current network address.

---

# 19. Why Not Use Container IP Addresses?

You could inspect a container and see an address such as:

```text
172.18.0.4
```

You might be tempted to configure:

```text
DB_HOST=172.18.0.4
```

Do not design your application around this.

Containers are replaceable.

If the database container is recreated, it may receive another IP address.

Instead:

```text
DB_HOST=veriqta-db
```

gives us a service identity.

---

# 20. Docker DNS Mental Model

Think:

```text
Backend asks:

"Where is veriqta-db?"

        ↓

Docker DNS

        ↓

Current network address

        ↓

PostgreSQL
```

Your application uses a meaningful service name rather than infrastructure-specific addresses.

# 28. Backend Application

Create:

```text
backend/app.py
```

Add:

```python
import os
import time

import psycopg
from flask import Flask, jsonify, request


app = Flask(__name__)


DB_HOST = os.getenv("DB_HOST", "veriqta-db")
DB_PORT = os.getenv("DB_PORT", "5432")
DB_NAME = os.getenv("DB_NAME", "veriqta")
DB_USER = os.getenv("DB_USER", "veriqta")
DB_PASSWORD = os.getenv("DB_PASSWORD")


def get_connection():
    if not DB_PASSWORD:
        raise RuntimeError("DB_PASSWORD is not configured")

    return psycopg.connect(
        host=DB_HOST,
        port=DB_PORT,
        dbname=DB_NAME,
        user=DB_USER,
        password=DB_PASSWORD,
    )


def wait_for_database():
    attempts = 20

    for attempt in range(1, attempts + 1):
        try:
            with get_connection() as connection:
                with connection.cursor() as cursor:
                    cursor.execute("SELECT 1")
                    cursor.fetchone()

            print("Database is ready.", flush=True)
            return

        except Exception as error:
            print(
                f"Database not ready "
                f"({attempt}/{attempts}): "
                f"{type(error).__name__}",
                flush=True,
            )

            time.sleep(2)

    raise RuntimeError(
        "Database did not become ready in time"
    )


def initialize_database():
    with get_connection() as connection:
        with connection.cursor() as cursor:
            cursor.execute(
                """
                CREATE TABLE IF NOT EXISTS tasks (
                    id SERIAL PRIMARY KEY,
                    title TEXT NOT NULL
                )
                """
            )

        connection.commit()


@app.route("/health")
def health():
    try:
        with get_connection() as connection:
            with connection.cursor() as cursor:
                cursor.execute("SELECT 1")
                cursor.fetchone()

        return jsonify(
            status="healthy",
            database="reachable",
        ), 200

    except Exception:
        return jsonify(
            status="unhealthy",
            database="unreachable",
        ), 503


@app.route("/tasks", methods=["GET"])
def get_tasks():
    with get_connection() as connection:
        with connection.cursor() as cursor:
            cursor.execute(
                "SELECT id, title FROM tasks ORDER BY id"
            )

            rows = cursor.fetchall()

    return jsonify(
        [
            {
                "id": row[0],
                "title": row[1],
            }
            for row in rows
        ]
    )


@app.route("/tasks", methods=["POST"])
def create_task():
    data = request.get_json(silent=True) or {}

    title = data.get("title", "").strip()

    if not title:
        return jsonify(
            error="title is required"
        ), 400

    with get_connection() as connection:
        with connection.cursor() as cursor:
            cursor.execute(
                """
                INSERT INTO tasks (title)
                VALUES (%s)
                RETURNING id
                """,
                (title,),
            )

            task_id = cursor.fetchone()[0]

        connection.commit()

    return jsonify(
        id=task_id,
        title=title,
    ), 201


if __name__ == "__main__":
    wait_for_database()
    initialize_database()

    app.run(
        host="0.0.0.0",
        port=5000,
    )
```

# 30. Why `0.0.0.0` Matters

Flask runs with:

```python
host="0.0.0.0"
```

Inside a container, binding only to:

```text
127.0.0.1
```

would make the application listen only on the container's loopback interface.

Other containers would not be able to reach it through the container's network interface.

Binding to:

```text
0.0.0.0
```

allows Flask to listen on the container's available interfaces.

Many applications express database configuration as one connection string.

A PostgreSQL URL commonly looks like:

```text

```

For our architecture:

```text

```

Breaking it apart:

```text
postgresql://
    |
    └── protocol

veriqta
    |
    └── username

<password>
    |
    └── password

veriqta-db
    |
    └── database host

5432
    |
    └── database port

veriqta
    |
    └── database name
```

Environment variables are useful, but they should not be treated as a perfect production secret-management system.

# 41. Container Storage vs Persistent Storage

Without a volume:

```text
Database
   ↓
Container Writable Layer
```

Remove the container and data stored only in that layer disappears with it.

With a volume:

```text
Database Container
       |
       v
Named Volume
       |
       v
Persistent Data
```

The container can be replaced while the volume remains.

---

# 42. Persistence Is Not Backup

This distinction is critical.

A volume protects data from normal container replacement.

It does not automatically protect against:

* disk failure;
* host failure;
* accidental volume deletion;
* corruption;
* malicious deletion;
* disaster.

Therefore:

```text
Persistence
≠
Backup
```

# 49. Started Does Not Mean Ready

A database container can be running while PostgreSQL is still initializing.

For example:

```text
00:00 Database container starts
00:01 Backend container starts
00:05 PostgreSQL becomes ready
```

At `00:01`:

```text
Database container
=
running
```

but:

```text
PostgreSQL
=
not ready
```

This is why:

```text
running
≠
ready
```

# 50. Backend Retry Logic

Our backend uses:

```python
wait_for_database()
```

before initializing its table.

It retries the connection instead of assuming the database is instantly available.

This introduces production concepts such as:

* retry;
* timeout;
* readiness;
* backoff.

Our retry is intentionally simple for learning.

Production retry strategies require more careful design.

# 64. Create Nginx Configuration

Create:

```text
frontend/nginx.conf
```

Add:

```nginx
server {
    listen 80;

    server_name _;

    root /usr/share/nginx/html;

    index index.html;


    location / {
        try_files $uri $uri/ /index.html;
    }


    location /api/ {
        proxy_pass http://veriqta-backend:5000/;

        proxy_http_version 1.1;

        proxy_set_header Host $host;

        proxy_set_header X-Real-IP $remote_addr;

        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

        proxy_set_header X-Forwarded-Proto $scheme;
    }


    location = /health {
        access_log off;

        add_header Content-Type text/plain;

        return 200 'healthy\n';
    }
}
```

# 65. Understand the Proxy

Browser requests:

```text
/api/tasks
```

Nginx forwards the request to:

```text

```

With this `proxy_pass` form, the `/api/` prefix is replaced by `/` for the upstream request.

Therefore:

```text
Browser
   ↓
Frontend Nginx
   ↓
Docker DNS
   ↓
Backend
```

# 97. Failure Types Matter

Different symptoms imply different investigations.

## Name resolution failure

```text
Cannot find the service
```

Investigate:

* hostname;
* Docker DNS;
* network membership.

## Connection refused

```text
Destination can be reached, but expected service is not accepting the connection
```

Investigate:

* process;
* port;
* readiness;
* listening address.

## Authentication failure

```text
Service was reached but rejected credentials
```

Investigate:

* username;
* password;
* database;
* authentication configuration.

Do not treat every network-looking failure as the same problem.

At the beginning of this part, Docker may have looked like:

```text

↓
```

You now need a larger mental model:

```text
                          USER
                            |
                            v
                         BROWSER
                            |
                            |
                  Host 127.0.0.1:8080
                            |
                            v
                 +--------------------+
                 |     FRONTEND       |
                 |       Nginx        |
                 |        :80         |
                 +----------+---------+
                            |
                    frontend network
                            |
                            v
                 +--------------------+
                 |      BACKEND       |
                 |       Flask        |
                 |       :5000        |
                 +----------+---------+
                            |
                     backend network
                            |
                            v
                 +--------------------+
                 |      DATABASE      |
                 |     PostgreSQL     |
                 |       :5432        |
                 +----------+---------+
                            |
                            v
                 +--------------------+
                 |   DOCKER VOLUME    |
                 |  Persistent Data   |
                 +--------------------+
```

Docker DNS allows:

```text
Frontend
↓
veriqta-backend
```

and:

```text
Backend
↓
veriqta-db
```

The frontend is externally reachable.

The backend is internal.

The database is internal.

The database data lives independently from the disposable database container.

Runtime configuration tells the containers how to find their dependencies.

Health checks tell us whether services are actually working.

Logs provide evidence when they are not.

Networks define communication paths.

Volumes define persistent data paths.

This is the foundation of a multi-container application.
