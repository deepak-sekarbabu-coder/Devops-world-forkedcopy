# Part 18: Docker on AWS: EC2, VPC, Security Groups, ECR, and Load Balancing

## From a Docker Image to a Real Cloud Deployment

Up to this point, you have learned how to:

* build Docker images;
* run containers;
* create Docker networks;
* persist data;
* troubleshoot containers;
* secure images and containers;
* observe runtime behavior;
* automate builds through CI/CD;
* push images to registries.

Now Docker leaves the laptop.

We are going to place it inside real cloud infrastructure.

Our target architecture is:

```text

Load Balancer Security Group
   ↓
AWS VPC
   ↓

   ↓
```

```text

↓
```

# 2. Docker Is Not Cloud Infrastructure

This distinction is fundamental.

Docker answers questions such as:

```text
How do I package the application?

How do I run it consistently?

What dependencies does it need?

What port does it listen on?

How do I isolate the process?
```

AWS infrastructure answers different questions:

```text
Where does the container run?

How does traffic reach it?

Who can reach it?

How does the server access the internet?

Where is the image stored?

How do multiple servers receive traffic?

How is the infrastructure monitored?

How does DNS reach the application?
```

Docker gives us:

```text
Application
↓
Image
↓
Container
```

AWS gives us:

```text
Network
Compute
Identity
Storage
Load Balancing
DNS
Monitoring
```

Together:

```text
AWS Infrastructure
       ↓
EC2
       ↓
Docker
       ↓
Container
       ↓
Application
```

```text

```

```text

↓
Virtual Compute
↓
EC2 Instance
↓
Operating System
↓
Docker Engine
↓

```

An EC2 instance can run:

```text

Nginx

```

Therefore:

```text

```

# 7. Region

AWS infrastructure is organized geographically into Regions.

A Region might conceptually be:

```text
AWS Region
├── Availability Zone A
├── Availability Zone B
└── Availability Zone C
```

Resources often belong to a particular Region.

For example:

```text
EC2 instance
ECR repository
ALB
VPC
```

are used within regional architecture.

Always verify which Region your console and CLI are using.

# 8. Region Mistake

A common beginner mistake:

```text

↓
Open EC2 console in Region B
↓
Cannot find expected resources
```

You may simply be looking at a different Region.

Always check:

```text

```

before troubleshooting further.

# 9. Availability Zones

A Region contains multiple Availability Zones.

Conceptually:

```text
Region
│
├── AZ-A
│   └── Subnet A
│
├── AZ-B
│   └── Subnet B
│
└── AZ-C
    └── Subnet C
```

A subnet exists entirely within one Availability Zone.

For resilient architectures, workloads are commonly distributed across multiple Availability Zones.

# 14. What Is a VPC?

VPC means:

```text
Virtual Private Cloud
```

A VPC is a logically isolated virtual network in AWS where you place resources.

Conceptually:

```text
AWS
└── VPC
    ├── Subnet
    ├── EC2
    ├── Load Balancer
    ├── Route Tables
    └── Security Groups
```

The VPC defines the networking boundary for our application architecture.

---

# 15. VPC CIDR

When creating a VPC, you define an IP address range.

Example:

```text
10.0.0.0/16
```

This is CIDR notation.

You do not need advanced subnet mathematics yet, but understand:

```text
VPC
10.0.0.0/16
```

provides address space from which subnet ranges can be created.

---

# 16. Example VPC

We can design:

```text
VPC
10.0.0.0/16
```

Then create:

```text
Public Subnet A
10.0.1.0/24

Public Subnet B
10.0.2.0/24

Private Subnet A
10.0.11.0/24

Private Subnet B
10.0.12.0/24
```

This gives us a foundation for a multi-AZ design.

---

# 17. What Is a Subnet?

A subnet is a range of IP addresses inside a VPC.

Resources are launched into subnets.

Example:

```text
VPC
10.0.0.0/16
│
├── Subnet A
│   10.0.1.0/24
│
└── Subnet B
    10.0.2.0/24
```

Each subnet belongs to one Availability Zone.

---

# 18. Public Subnet

A public subnet has a route to an Internet Gateway.

Conceptually:

```text
Public Subnet
↓
Route Table
↓
Internet Gateway
↓
Internet
```

But simply placing an EC2 instance in a public subnet does not automatically guarantee public reachability.

You must also consider:

```text
public IPv4 address
route table
security group
network configuration
application listener
```

---

# 19. Private Subnet

A private subnet does not have a direct route to an Internet Gateway.

Conceptually:

```text
Internet
   X
   │
Private Subnet
```

For outbound internet access, private-subnet resources may use infrastructure such as:

```text
NAT Gateway
```

depending on architecture.

---

# 20. Beginner Lab vs Production Architecture

For initial learning, we may use:

```text
Internet
↓
ALB
↓
EC2 in public subnet
```

because it makes SSH and troubleshooting easier.

A stronger production architecture often moves application servers into private subnets:

```text
Internet
↓
Public ALB
↓
Private EC2 Instances
```

This reduces direct internet exposure of application servers.

---

# 21. Production-Oriented VPC Architecture

A stronger architecture:

```text
                         Internet
                            │
                            ▼
                     Internet Gateway
                            │
               ┌────────────┴────────────┐
               │                         │
        Public Subnet A           Public Subnet B
               │                         │
               └────────── ALB ──────────┘
                            │
               ┌────────────┴────────────┐
               │                         │
       Private Subnet A          Private Subnet B
               │                         │
             EC2-1                     EC2-2
               │                         │
            Docker                    Docker
               │                         │
         App Container            App Container
```

This is much closer to a real highly available deployment.

# 22. Internet Gateway

An Internet Gateway is attached to a VPC and enables communication between the VPC and the internet when routing and resource addressing are configured appropriately.

Conceptually:

```text
Internet
↓
Internet Gateway
↓
VPC
```

The Internet Gateway is not a Docker component.

It belongs to AWS networking.

---

# 23. Internet Gateway Does Not Automatically Expose Everything

Attaching an Internet Gateway does not mean:

```text
every server is now publicly reachable.
```

Traffic still depends on:

```text
subnet routing
public addressing
security groups
network ACLs where relevant
operating-system firewall
application binding
Docker port publishing
```

Think in layers.

---

# 24. Route Tables

A route table determines where network traffic is directed.

Each subnet is associated with a route table.

Conceptually:

```text
Destination
→ Target
```

Example:

```text
10.0.0.0/16
→ local

0.0.0.0/0
→ Internet Gateway
```

The local route allows communication within the VPC address range.

The default route can send internet-bound IPv4 traffic toward an Internet Gateway for a public subnet.

---

# 25. Public Route Table

Conceptual public route table:

```text
Destination       Target

10.0.0.0/16       local
0.0.0.0/0         igw-xxxxxxxx
```

Associated with:

```text
public subnet A
public subnet B
```

---

# 26. Private Route Table

Conceptually:

```text
Destination       Target

10.0.0.0/16       local
```

If private instances require outbound IPv4 internet access through a NAT Gateway, the private route table might contain:

```text
0.0.0.0/0
→ NAT Gateway
```

That is different from routing directly to an Internet Gateway.

---

# 27. Route Tables Are Not Firewalls

A route answers:

```text
Where should this packet go?
```

A Security Group answers:

```text
Is this traffic allowed?
```

Do not confuse:

```text
routing
```

with:

```text
filtering.
```

You may have a correct route and still be blocked by security controls.

---

# 28. Security Groups

A Security Group acts as a virtual firewall for associated AWS resources.

Rules specify things such as:

```text
protocol
port
source
destination
```

For EC2, Security Groups control allowed inbound and outbound traffic.

---

# 29. Security Groups Are Stateful

Security Groups are stateful.

If an allowed connection is established, return traffic for that connection is automatically allowed.

This differs from stateless filtering models.

For now remember:

```text
Security Group
=
stateful network access control
```

---

# 30. Our Security Group Architecture

Create separate Security Groups.

## ALB Security Group

Allow:

```text
Internet
→ 80 HTTP
→ 443 HTTPS
```

as appropriate.

## EC2 Application Security Group

Allow:

```text
ALB Security Group
→ application host port
```

For administration, if using SSH:

```text
trusted administrator IP
→ 22
```

Not:

```text
entire internet
→ 22
```

unless an isolated learning scenario explicitly requires it temporarily.

---

# 31. Security Group Referencing

A strong pattern is:

```text
EC2 Application SG
Inbound:

Source:
ALB Security Group

Port:
8080
```

Instead of:

```text
0.0.0.0/0
→ 8080
```

Now the application server accepts application traffic from the load balancer rather than directly from the entire internet.

---

# 32. Why This Matters

Weak:

```text
Internet
↓
EC2:8080
```

Better:

```text
Internet
↓
ALB:443
↓
EC2:8080
```

The EC2 Security Group trusts:

```text
ALB Security Group
```

not:

```text
everyone.
```

---

```text

```

Docker publishes:

```text

→

```

AWS sees:

```text

```

```text

```

```text

↓

↓

↓

↓

```

# 35. EC2 Key Pairs

Conceptually:

```text

     ↓

     ↓

```

# 36. SSH Access

Generic syntax:

```bash
ssh \
  -i /path/to/key.pem \
  USER@EC2_PUBLIC_DNS
```

The username depends on the AMI.

Do not blindly assume:

```text
ubuntu
```

or:

```text
ec2-user
```

Verify the username for your selected AMI.

---

# 37. Protect the Private Key

On Linux/macOS, SSH may reject an overly permissive private key.

A common permission setting is:

```bash
chmod 400 key.pem
```

Then connect:

```bash
ssh \
  -i key.pem \
  USER@HOST
```

Never:

```text
commit key.pem to Git
email it around
store it in Docker image
put it in public repository
```

---

# 38. SSH Security Group Rule

For a learning EC2 instance:

```text
Type:
SSH

Protocol:
TCP

Port:
22

Source:
your trusted public IP/32
```

Avoid casually using:

```text
0.0.0.0/0
```

for SSH.

That exposes the SSH service to the entire IPv4 internet.

# 50. Application Binding

A common failure occurs when the application listens only on:

```text
127.0.0.1
```

inside the container.

For externally reachable container services, applications commonly need to listen on:

```text
0.0.0.0
```

inside the container.

Example:

```text
0.0.0.0:5000
```

Docker can then forward traffic to it.

# 51. Publishing Does Not Open AWS Firewall

Running:

```bash

  -p 8080:5000 \
  IMAGE
```

does not automatically modify the EC2 Security Group.

Docker says:

```text
host port 8080
→ container port 5000
```

AWS still decides whether network traffic can reach EC2 port 8080.

# 60. Least Privilege for ECR

An application server that only needs to pull an image does not need:

```text

```

It needs only the actions required for its deployment workflow.

Apply:

```text

```

Your CI pipeline may need push permissions.

Your EC2 host may need pull permissions.

These are different responsibilities.

Conceptually:

## CI

Needs:

```text

```

## EC2

Needs:

```text

```

Do not automatically give both identities identical permissions.

# 62. ECR Authentication

Docker itself does not directly speak IAM authentication.

AWS provides ECR authentication mechanisms.

A common AWS CLI flow is:

```bash
aws ecr get-login-password \
  --region REGION \
| docker login \
    --username AWS \
    --password-stdin \
    ACCOUNT_ID.dkr.ecr.REGION.amazonaws.com
```

The authorization token obtained through this mechanism is temporary.

Do not hard-code it.

---

# 63. Verify AWS Identity First

Before troubleshooting ECR authentication:

```bash
aws sts get-caller-identity
```

This helps answer:

```text
Which AWS identity am I currently using?
```

On EC2 with an instance role, you should see identity information associated with that role.

If AWS identity itself is wrong, ECR login troubleshooting should begin there.

# 76. Health Checks

The ALB checks whether targets are healthy.

Suppose the application exposes:

```text

```

Configure:

```text

HTTP

Port:
traffic port

```

The ALB periodically requests the health endpoint.

Healthy target:

```text

↓

↓
successful expected response
↓

```

Unhealthy target:

```text
health check repeatedly fails
↓
```

# 77. Good Health Endpoint

A useful basic health endpoint should be:

```text

predictable
low-cost
```

Do not make a simple liveness-style health endpoint perform huge database queries or expensive external calls.

Different health-check designs answer different questions.

# 78. Container Health vs ALB Health

Docker can have:

```text

```

```text
Target Group Health Check
```

They are different systems.

Possible situation:

```text

ALB:
unhealthy
```

Why?

Perhaps:

```text

wrong health path
Security Group blocks ALB
application bound incorrectly
ALB expects different status code
```

Never assume one health system proves the other.

# 198. Final Mental Model

When a user enters:

```text
https://app.example.com
```

do not think:

```text
The request goes to Docker.
```

Think:

```text
1. DNS

app.example.com
↓
Route 53 resolves the application endpoint

2. LOAD BALANCING

Client connects to
Application Load Balancer :443

3. TLS

ALB handles HTTPS
using configured certificate/security policy

4. ROUTING

ALB listener/rule
↓
Target Group

5. HEALTH

ALB selects an eligible healthy target

6. AWS NETWORK SECURITY

ALB Security Group
+
EC2 Security Group
permit required traffic

7. COMPUTE

Request reaches
EC2 :8080

8. CONTAINER NETWORKING

Docker published port
8080
↓
5000

9. CONTAINER

Request enters
application container

10. APPLICATION

Application processes request

11. RESPONSE

Application
↓
Container
↓
EC2
↓
ALB
↓
Client
```

Deployment is a separate path:

```text
Developer
↓
Git
↓
CI/CD
↓
Test
↓
Docker Build
↓
Security Scan
↓

EC2 IAM Role
↓
ECR Authentication
↓
Docker Pull
↓
Docker Run
↓
Health Verification
↓
ALB Target
↓
Production Traffic
```

```text
Application
+
Container
+
EC2
+
ALB
↓
Logs
Metrics

↓
CloudWatch / Observability
↓
Engineer
```

And security surrounds every path:

```text
Security Groups

Private Networking

+
Image Security
+
Host Security
+
Least Privilege
```

The final architecture is therefore not:

```text
EC2 runs Docker.
```

It is:

```text
                    INTERNET
                       │
                       ▼
                    DNS
                       │
                       ▼
                  ROUTE 53
                       │
                       ▼
               LOAD BALANCER
                       │
                       ▼
                TARGET GROUP
                       │
             HEALTHY TARGETS ONLY
                       │
          ┌────────────┴────────────┐
          ▼                         ▼
        EC2-1                     EC2-2
          │                         │
       Docker                    Docker
          │                         │
      Container                 Container
          │                         │
      Application               Application
```

while the software arrives through:

```text
SOURCE CODE
    ↓
CI/CD
    ↓
TEST
    ↓
BUILD
    ↓
SCAN
    ↓

    ↓
AMAZON ECR
    ↓
IAM-AUTHORIZED PULL
    ↓
EC2
    ↓
DOCKER
    ↓
CONTAINER
```

The production engineer must understand both paths.

The request path explains:

```text
How users reach the software.
```

The deployment path explains:

```text
How software reaches the servers.
```

The observability path explains:

```text
How engineers know whether the system works.
```

The security path explains:

```text
Who and what is allowed to interact with each layer.
```

That is Docker on AWS.
