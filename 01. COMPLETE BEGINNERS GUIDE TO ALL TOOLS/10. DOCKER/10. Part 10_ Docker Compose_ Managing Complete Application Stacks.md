# Part 10: Docker Compose: Managing Complete Application Stacks

## Turn the Previous Architecture Into a Reproducible Environment

In Part 9, you manually built a multi-container application:

```text
Browser
   ↓
Frontend
   ↓
Backend/API
   ↓
Database
```

You created networks manually.

You created a volume manually.

You built images manually.

You started containers individually.

You connected the backend to multiple networks.

You supplied environment variables using long `docker run` commands.

You checked logs one container at a time.

You manually remembered which container depended on which service.

That was intentional.

Before using automation, you needed to understand what was being automated.

Now we are going to take this:

```text

        ↓
```


Our target becomes:

```text

+-----------------------------+
| Complete Application Stack  |
+-----------------------------+
        |
        +--> Frontend
        |
        +--> Backend/API
        |

        |
        +--> Networks
        |
        +--> Persistent Volume
```

This is where multi-container Docker starts becoming reproducible.

# 3. What Is Docker Compose?

Docker Compose is a tool for defining and running applications made from multiple containers.

Instead of expressing the application as many separate shell commands, you describe the desired application configuration in YAML.

A typical Compose file might describe:

```text
Application
├── Services
│   ├── frontend
│   ├── backend
│   └── database
│
├── Networks
│   ├── frontend-network
│   └── backend-network
│
└── Volumes
    └── db-data
```

Then:

```bash
docker compose up
```

uses that definition to create and start the application.

---

# 4. Why Docker Compose Exists

Consider our Part 9 application.

To reproduce it manually, another engineer would need to know:

* which images to build;
* where the Dockerfiles are;
* which containers to create;
* what to name them;
* which ports to publish;
* which environment variables to set;
* which volume to create;
* where to mount the volume;
* which networks to create;
* which service belongs to which network;
* which services depend on other services;
* which health checks to perform.

If all you send them is:

```text
Run the frontend, backend and PostgreSQL containers.
```

that is not enough.

There are too many details.

# 5. The Reproducibility Problem

Imagine Engineer A manually creates:

```text
frontend
backend
database
```

Engineer B tries to recreate it tomorrow.

Engineer B accidentally:

* publishes the database;
* forgets the persistent volume;
* uses a different network;
* forgets one environment variable;
* starts the backend with the wrong hostname.

Now the two engineers do not actually have the same environment.

Compose helps turn those runtime decisions into version-controlled configuration.

# 6. From Imperative Commands to Declarative Configuration

Manual Docker is largely command-driven.

You say:

```text
Create this network.

Create this volume.

Run this database.

Run this backend.

Connect backend to this network.

Run this frontend.
```

Compose lets you describe:

```text
I want:

these services,
with these images,
on these networks,
with these volumes,
using these environment settings,
with these health checks.
```

Docker Compose works from that desired definition.

---

# 7. Docker Compose Is Not Kubernetes

Do not confuse:

```text
Docker Compose
```

with:

```text
Kubernetes
```

Compose is extremely useful for:

* local development;
* learning;
* testing;
* integration environments;
* CI jobs;
* demos;
* small controlled deployments;
* reproducible multi-container environments.

Kubernetes solves a much larger orchestration problem involving concepts such as:

* clusters;
* scheduling;
* desired replica management;
* rolling updates;
* service abstractions;
* self-healing;
* advanced deployment control;
* cluster-level orchestration.

Compose is not a replacement for every production orchestrator.

But it is an important tool for understanding and operating multi-container Docker applications.

# 21. Service Names

In:

```yaml

  backend:
    ...
```

```text

```

Other services on a shared Compose network can use that service name for discovery.

Therefore, instead of the Part 9 hostname:

```text

```

```text

```

Similarly:

```text

```

# 22. Service Names and Container Names Are Not the Same Concept

This distinction matters.

A Compose service may be named:

```text
backend
```

while Compose creates a runtime container with a generated project/service-based name.

Your application should normally reason about the service identity:

```text
backend
```

rather than depending on a manually fixed container name.

This also matters if a service is ever scaled to multiple containers.

# 25. `build`

For source code that has a Dockerfile, Compose can build the image.

Example:

```yaml
services:
  backend:
    build:
      context: ./backend
```

This tells Compose:

```text
Use ./backend as the build context.
```

Docker then looks for the default Dockerfile within that context unless another Dockerfile is configured.

---

# 26. `build` vs `image`

You may encounter:

```yaml
image: nginx:alpine
```

or:

```yaml
build:
  context: ./backend
```

Conceptually:

```text
image
→ use/reference an image
```

while:

```text
build
→ build an image from source/build instructions
```

A service can also have both `build` and `image` for workflows where the locally built image should receive a particular image name/tag.

# 38. `.env` and Container Environment Are Different Concepts

This is an important distinction.

A Compose `.env` file is commonly used for interpolation.

For example:

```text

```

combined with:



# 56. Health Checks

A health check gives Docker a command that tests whether the workload meets a defined health condition.

A PostgreSQL health check can use:

```bash
pg_isready
```

For example:

```yaml
healthcheck:
  test:
    - CMD-SHELL
    - pg_isready -U "$$POSTGRES_USER" -d "$$POSTGRES_DB"
  interval: 5s
  timeout: 5s
  retries: 10
  start_period: 10s
```

---

# 57. Why `$$` Appears in the Health Check

Compose performs variable interpolation.

Inside this command we want the shell inside the container to evaluate:

```text
$POSTGRES_USER
```

rather than Compose replacing it from the host-side interpolation environment first.

In Compose YAML, `$$` can be used to produce a literal `$`.

Therefore:

```text
$$POSTGRES_USER
```

allows the variable to be evaluated inside the container.

This distinction prevents a very common configuration mistake.

---

# 58. Health Check Components

Consider:

```yaml
healthcheck:
  test:
    - CMD-SHELL
    - pg_isready -U "$$POSTGRES_USER" -d "$$POSTGRES_DB"
  interval: 5s
  timeout: 5s
  retries: 10
  start_period: 10s
```

`test` defines the health command.

`interval` controls how frequently it runs.

`timeout` limits how long one check may take.

`retries` controls how many consecutive failures are tolerated before unhealthy status.

`start_period` gives startup time before failures are treated normally for health evaluation.

Choose real values based on application behavior rather than copying arbitrary production numbers.

# 61. Backend Health Check


```yaml
  retries: 5
  start_period: 10s
```

The check runs inside the backend container.

```text
Database becomes healthy
↓
Backend starts
↓
Backend becomes healthy
↓
Frontend starts
```

This gives the startup process better dependency awareness.

---

# 63. Dependency Health Does Not Eliminate Runtime Failures

Suppose everything starts correctly.

Later:

```text
Database crashes
```

A startup dependency declaration does not magically make the whole application resilient.

The backend still needs sensible runtime behavior.

Production applications may need:

* retries;
* reconnect logic;
* timeouts;
* circuit breaking where appropriate;
* monitoring;
* alerts;
* recovery procedures.

`depends_on` is not a complete resilience strategy.

---

# 64. Restart Policies

Containers can exit unexpectedly.

Compose lets you define a restart policy such as:

```yaml
restart: unless-stopped
```

Other policies include:

```text
no
always
on-failure
unless-stopped
```

The exact choice should match the workload and operating model.

---

# 65. Restart Policies Are Not Self-Healing Applications

Suppose backend repeatedly crashes because:

```text
configuration is invalid
```

A restart policy may simply produce:

```text
start
crash
restart
crash
restart
crash
```

That is not a healthy system.

Always investigate repeated restarts.

# 107. Environment Interpolation Example

Add:

```text
APP_PORT=8080
```

to `.env`.

Then change:

```yaml
ports:
  - "127.0.0.1:8080:80"
```

to:

```yaml
ports:
  - "127.0.0.1:${APP_PORT}:80"
```

Now the host port can be selected through interpolation.

---

# 108. Provide a Default Value

You can use interpolation with a default.

For example:

```yaml
ports:
  - "127.0.0.1:${APP_PORT:-8080}:80"
```

Conceptually:

```text
If APP_PORT exists:
    use it
otherwise:
    use 8080
```

This is useful for safe non-secret defaults.

---

# 109. Required Values

For values that must not silently fall back, use required-value syntax.

Example:

```yaml
POSTGRES_PASSWORD: ${DB_PASSWORD:?DB_PASSWORD must be set}
```

Now missing configuration becomes an explicit error rather than an accidental runtime surprise.

# 113. Secrets Considerations

A file like:

```text
.env
```

is convenient.

It is not automatically a secure enterprise secret-management system.

Sensitive information may need stronger controls for production, including:

* restricted permissions;
* secret managers;
* controlled injection;
* credential rotation;
* auditing;
* CI/CD secret stores;
* cloud-native identity/secret systems.

---

# 114. Compose `secrets`

Compose also has a `secrets` model.

A conceptual definition can look like:

```yaml
services:
  some-service:
    secrets:
      - some-secret

secrets:
  some-secret:
    file: ./some-secret.txt
```

This can make a secret available to the service as a mounted secret file according to the Compose model/runtime support.

However, do not assume that merely declaring a local secret file solves:

* secure secret storage;
* rotation;
* access governance;
* audit;
* production distribution.

The source file itself must still be protected.

---

# 115. Application Must Know How to Consume the Secret

Our current backend expects:

```text
DB_PASSWORD
```

as an environment variable.

If you switch to a file-based secret, the application must be designed to read the value from the file, or an entrypoint/configuration layer must deliberately bridge that mechanism.

Infrastructure configuration and application configuration must agree.

# 127. Service Scaling Context

Compose can run multiple containers for a service in certain workflows.

For example, you may encounter:

```bash

  -d \
  --scale backend=3
```

Conceptually:

```text
backend service
├── backend instance
├── backend instance
└── backend instance
```

---

# 128. Scaling Limitations

Suppose every backend replica tries to publish:

```text
5000:5000
```

on the same host.

Only one process/container can normally bind the same host address/port combination.

This is one reason internal services are often not individually published when replicas sit behind a routing/load-balancing layer.

---

# 129. Multiple Replicas Need Traffic Distribution

Three backend containers are not useful simply because three processes exist.

You need to answer:

```text
Who sends requests to them?

How are requests distributed?

What happens when one fails?

How is health considered?

Does the application store local session state?

Can all replicas safely use the same database?
```

Scaling is an architecture problem, not merely a replica count.

---

# 130. Compose Scaling Is Not Cluster Scheduling

A normal local Compose project operates against a Docker environment/host.

It does not automatically give you:

```text
multi-node cluster scheduling
automatic cross-host failover
production-grade cluster orchestration
```

Do not confuse:

```text
three containers on one host
```

with:

```text
high availability across infrastructure failure domains
```

# 147. Troubleshooting Workflow

When a Compose application fails, use a disciplined sequence.

```text
1. Validate configuration
        ↓
2. Inspect service state
        ↓
3. Inspect logs
        ↓
4. Check health
        ↓
5. Check networks
        ↓
6. Check runtime configuration
        ↓
7. Check storage
        ↓
8. Check host resources/ports
        ↓
9. Identify root cause
        ↓
10. Fix
        ↓
11. Recreate only what is needed
        ↓
12. Verify end to end
```

# 156. Common Mistake: Running From the Wrong Directory

If Compose cannot find your file, check:

```bash
pwd
```

Then:

```bash
ls
```

You should be in the project directory containing:

```text

```

Alternatively, explicitly specify a file with:

# 157. Common Mistake: Using `localhost` Between Services

Wrong:

```yaml
environment:
  DB_HOST: localhost
```

Correct:

```yaml
environment:
  DB_HOST: database
```

because:

```text
localhost inside backend
=
backend itself
```

---

# 158. Common Mistake: Publishing Every Service

You do not need:

```yaml
backend:
  ports:
    - "5000:5000"

database:
  ports:
    - "5432:5432"
```

for this architecture.

The services communicate internally.

Only publish what external clients actually need.

---

# 159. Common Mistake: Treating `depends_on` as Runtime Recovery

`depends_on` helps model startup relationships.

It does not guarantee that a dependency remains available forever.

Applications still need appropriate runtime resilience.

---

# 160. Common Mistake: Hardcoding Secrets

Bad:

```yaml
POSTGRES_PASSWORD: MyRealProductionPassword
```

especially in a file committed to Git.

Keep sensitive values outside public source-controlled configuration and use appropriate secret management.

---

# 161. Common Mistake: Committing `.env`

Add:

```text
.env
```

to:

```text
.gitignore
```

But remember:

```text
.gitignore
```

does not remove secrets that were already committed.

If a real secret reaches Git history, treat it as compromised and rotate it.

---

# 162. Common Mistake: Confusing `.env` and `env_file`

Remember:

```text
.env
```

commonly participates in Compose interpolation.

```yaml
env_file:
```

supplies variables to a service container.

They are related configuration mechanisms, but they are not conceptually identical.

---

# 163. Common Mistake: Assuming Restart Rebuilds

This:

```bash
docker compose restart backend
```

does not mean:

```text
rebuild backend image from changed source
```

For image-baked code changes, rebuild.

---

# 164. Common Mistake: Using `down -v` Casually

This:

```bash
docker compose down -v
```

can destroy named-volume data.

Never make destructive cleanup your default troubleshooting strategy.

---

# 165. Common Mistake: Fixed Container Names Everywhere

Do not add:

```yaml
container_name:
```

simply to make the output look familiar.

Compose service names already provide useful service identity.

Fixed container naming can also conflict with scaling and project isolation goals.

---

# 166. Common Mistake: Assuming Compose Means Production-Ready

A Compose stack can be perfectly valid while still lacking:

* TLS;
* backups;
* centralized monitoring;
* secret management;
* resource governance;
* host hardening;
* redundancy;
* disaster recovery;
* patching;
* external load balancing;
* deployment automation.

Compose describes and operates the application stack.

It does not solve every production responsibility.

Our architecture intentionally keeps:


Only:

# 169. Docker Socket Warning

Access to the Docker daemon/socket is highly privileged.

Do not casually mount:

```text
/var/run/docker.sock
```

into containers.

A workload with powerful Docker API access can potentially gain extensive control over Docker and the host environment.

Treat Docker daemon access as privileged administrative capability.

# 170. Image Versioning

For learning we use examples such as:


Production environments should use an intentional image-versioning strategy.

Avoid uncontrolled changes.

For stronger immutability, organizations may pin images more precisely, including by digest where appropriate.

```text

restore testing
recovery objectives
```

A backup that has never been restored is not proven recovery.

# 174. Development Bind Mounts

During development, you may eventually mount source code:

```yaml

  - ./backend:/app
```

This can make local iteration faster.

But understand the difference between:

```text
source copied into image
```

and:

```text
host directory mounted over container path
```

A bind mount can hide files that were originally present at the target path inside the image.

Use development mounts deliberately.

# 175. Development and Production Are Different

```text
immutable artifacts
controlled configuration
recovery
monitoring
```

Do not blindly deploy a development configuration as production.

# 183. Final Compose File With Configurable Port

```yaml

  database:

    environment:
      POSTGRES_DB: veriqta
      POSTGRES_USER: veriqta
      POSTGRES_PASSWORD: ${DB_PASSWORD:?DB_PASSWORD must be set}

    volumes:
      - db-data:/var/lib/postgresql/data

    networks:
      - backend-network

    healthcheck:
      test:
        - CMD-SHELL
        - pg_isready -U "$$POSTGRES_USER" -d "$$POSTGRES_DB"
      interval: 5s
      timeout: 5s
      retries: 10
      start_period: 10s

    build:
      context: ./backend

    environment:

      DB_PORT: "5432"
      DB_NAME: veriqta
      DB_USER: veriqta
      DB_PASSWORD: ${DB_PASSWORD:?DB_PASSWORD must be set}

    networks:
      - frontend-network
      - backend-network

    depends_on:
      database:
        condition: service_healthy

    healthcheck:
      test:
        - CMD
        - python
        - -c
        - >-
          import urllib.request;
          urllib.request.urlopen(
              'http://127.0.0.1:5000/health',
              timeout=3
          )
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 10s

    restart: unless-stopped


  frontend:
    build:
      context: ./frontend

    ports:
      - "127.0.0.1:${APP_PORT:-8080}:80"

    networks:
      - frontend-network

    depends_on:
      backend:
        condition: service_healthy

    restart: unless-stopped


volumes:
  db-data:


networks:
  frontend-network:
  backend-network:
```
