# Part 7: Docker Storage: Volumes, Bind Mounts, and Persistent Data

## Container → Volume → Persistent Database Data

In the previous parts, you learned how to build images and run real applications inside containers.

Now consider a database container.

You start PostgreSQL:

```bash
docker run -d \
  --name postgres-db \
  -e POSTGRES_PASSWORD=training-password \
  postgres
```

Your application writes:

```text
Users
Orders
Payments
Application records
```

to the database.

Everything appears to work.

Then someone removes the container:

```bash
docker rm -f postgres-db
```

You create another PostgreSQL container.

The database records are gone.

Why?

Because a container's writable filesystem is not where important persistent application data should live.

This part teaches how Docker storage works and how to separate:

```text
Replaceable container
```

from:

```text
Persistent data
```

The architecture we want is:

```text
Application / Database Container
             │
             │ reads and writes
             ↓
        Docker Volume
             │
             │ survives container replacement
             ↓
       Persistent Data
```

By the end of this part, you should understand:

* Container writable layers
* Ephemeral container storage
* Persistent data
* Docker volumes
* Named volumes
* Anonymous volumes
* Bind mounts
* tmpfs mounts
* Mount syntax
* Volume lifecycle
* Sharing storage
* Read-only mounts
* Permissions and ownership
* Database persistence
* Backup and restore
* Removing and pruning volumes
* Storage troubleshooting
* Production storage thinking

---

# 1. Start With the Fundamental Problem

Containers are designed to be replaceable.

Consider:

```text
Image
  ↓
Container A
```

You might eventually replace Container A with Container B because of:

```text
Application update
Security patch
Configuration change
Deployment
Container failure
Host maintenance
Scaling
Rollback
```

A good containerized system should expect containers to disappear.

But some data cannot disappear.

Examples:

```text
Database records
Uploaded files
Generated reports
User content
Persistent application state
```

Therefore:

```text
Container lifecycle
```

and:

```text
Data lifecycle
```

must not be treated as the same thing.

---

# 2. Remember the Container Filesystem Model

From Part 4, you learned that an image is composed of read-only image layers.

When Docker creates a container, it adds a writable layer.

Conceptually:

```text
Container Writable Layer
────────────────────────

Application Layer
────────────────────────

Dependency Layer
────────────────────────

Base Image Layer
────────────────────────
```

The image layers remain read-only.

The container writes filesystem changes into its writable layer.

---

# 3. What Is the Container Writable Layer?

The container writable layer is the filesystem layer where changes made by that container are recorded when those paths are not backed by another mount.

Suppose the image contains:

```text
/app/config.txt
```

A container modifies it.

Or the application creates:

```text
/app/output.txt
```

Those changes belong to that container's writable filesystem layer.

Conceptually:

```text
Image
│
├── /app/application
├── /etc/...
└── runtime files
        ↓
Container created
        ↓
Writable Layer
        ↓
new files
modified files
deleted-file metadata
```

---

# 4. The Writable Layer Belongs to the Container

This is the crucial point.

Suppose:

```text
Image: myapp:1.0
```

creates:

```text
Container A
```

Container A writes:

```text
/data/customer.txt
```

into its writable layer.

You remove Container A:

```bash
docker rm container-a
```

That container's writable layer is removed with it.

Creating:

```text
Container B
```

from the same image does not magically restore Container A's writable filesystem.

Container B starts from the image again.

---

# 5. Demonstration: Data Disappears With the Container

Run:

```bash
docker run -it --name storage-test alpine sh
```

Inside the container:

```sh
echo "VERIQTA persistent data test" > /data.txt
```

Verify:

```sh
cat /data.txt
```

Expected:

```text
VERIQTA persistent data test
```

Exit:

```sh
exit
```

The container is stopped but still exists.

Check:

```bash
docker ps -a
```

Restart it:

```bash
docker start storage-test
```

Then:

```bash
docker exec storage-test cat /data.txt
```

The file still exists.

This teaches an important distinction.

Stopping a container does **not** remove its writable layer.

---

# 6. Stopping Is Not Removing

The lifecycle looks like:

```text
Running Container
       ↓
docker stop
       ↓
Stopped Container
       ↓
Writable layer still exists
```

But:

```text
Stopped Container
       ↓
docker rm
       ↓
Container removed
       ↓
Writable layer removed
```

So saying:

> Container data disappears when a container stops

would be incorrect.

More accurately:

> Data stored only in the container writable layer is tied to that container and is normally lost when that container is removed.

---

# 7. Prove It

Remove the container:

```bash
docker rm storage-test
```

Create another:

```bash
docker run -d --name storage-test-2 alpine sleep 3600
```

Try:

```bash
docker exec storage-test-2 cat /data.txt
```

You should receive an error similar to:

```text
cat: can't open '/data.txt': No such file or directory
```

Why?

Because:

```text
Container 1 writable layer
        ≠
Container 2 writable layer
```

---

# 8. What Is Ephemeral Container Storage?

Ephemeral means:

> Temporary and tied to the lifecycle of something that can be replaced.

The container writable layer is appropriate for some temporary data.

Examples may include:

```text
Temporary processing files
Caches that can be recreated
Transient runtime artifacts
Disposable test output
```

But it is usually the wrong place for data that must survive container replacement.

---

# 9. What Is Persistent Data?

Persistent data is data that needs to outlive a particular container instance.

Examples:

```text
Database records
User uploads
Application-generated documents
Persistent service state
```

Architecture:

```text
Container A
     │
     ↓
Persistent Storage
     ↑
     │
Container B
```

Container A can disappear.

Container B can replace it.

The data remains available.

---

# 10. Separate Compute From Data

A useful container engineering model is:

```text
Container
=
Replaceable compute/runtime
```

while:

```text
Persistent storage
=
Longer-lived data
```

For example:

```text
PostgreSQL Container
        │
        ↓
PostgreSQL Data Directory
        │
        ↓
Persistent Volume
```

Now the PostgreSQL process can be replaced independently of its database files.

---

# 11. Docker's Main Storage Choices

For local Docker storage, three major mechanisms are:

```text
1. Volumes
2. Bind mounts
3. tmpfs mounts
```

They solve different problems.

A simplified comparison:

| Storage    | Managed by | Typical purpose               | Survives container removal?    |
| ---------- | ---------- | ----------------------------- | ------------------------------ |
| Volume     | Docker     | Persistent application data   | Yes, unless volume removed     |
| Bind mount | Host/user  | Direct host-file access       | Yes, because host files remain |
| tmpfs      | Memory     | Temporary sensitive/fast data | No                             |

Do not choose based only on which command looks easiest.

Choose according to the data's lifecycle and purpose.

---

# 12. What Is a Docker Volume?

A Docker volume is Docker-managed storage that exists independently from an individual container.

Conceptually:

```text
Docker Host
│
├── Container A
│      │
│      └──────────┐
│                 ↓
│          Docker Volume
│                 ↑
│      ┌──────────┘
│      │
└── Container B
```

A volume can remain after containers using it are removed.

That is exactly what we need for persistent data.

---

# 13. Container vs Volume Lifecycle

Without a volume:

```text
Container
    │
    ├── Application
    └── Writable Data

docker rm
    ↓

Container + writable data removed
```

With a volume:

```text
Container
    │
    ├── Application
    │
    └── /data
          │
          ↓
       Volume

docker rm container
          ↓
Container removed
          ↓
Volume remains
          ↓
Data remains
```

This separation is fundamental.

# 17. The Volume Mountpoint

On a native Linux Docker Engine installation using the local driver, Docker commonly stores local-volume data under Docker's data root, often in an area such as:

```text
/var/lib/docker/volumes/
```

But do not build application workflows around manually editing Docker's internal storage directories.

On Docker Desktop, Docker runs inside a Linux virtualized environment, so the physical storage location is not simply an ordinary macOS or Windows host directory you should manipulate directly.

Treat Docker-managed volumes through Docker interfaces.

Use:

```bash
docker volume inspect
```

instead of guessing paths.

---

# 18. Mounting a Named Volume

Create a container:

```bash
docker run -d \
  --name volume-lab \
  --mount source=veriqta-data,target=/data \
  alpine \
  sleep 3600
```

Break down:

```text
--mount
→ configure a mount

source=veriqta-data
→ use the named volume

target=/data
→ make it available at /data inside the container
```

Architecture:

```text
Container
│
└── /data
      │
      ↓
veriqta-data Volume
```

---

# 19. Write Data Into the Volume

Run:

```bash
docker exec volume-lab \
  sh -c 'echo "VERIQTA storage lab" > /data/message.txt'
```

Verify:

```bash
docker exec volume-lab cat /data/message.txt
```

Expected:

```text
VERIQTA storage lab
```

---

# 20. Remove the Container

Remove:

```bash
docker rm -f volume-lab
```

Now check:

```bash
docker volume ls
```

You should still see:

```text
veriqta-data
```

The container is gone.

The volume is not.

---

# 21. Attach the Volume to a New Container

Run:

```bash
docker run --rm \
  --mount source=veriqta-data,target=/data \
  alpine \
  cat /data/message.txt
```

Expected:

```text
VERIQTA storage lab
```

This proves:

```text
Container A
   ↓
writes data
   ↓
Volume
   ↓
Container A removed
   ↓
Volume remains
   ↓
Container B
   ↓
reads same data
```

That is persistent container storage.

---

# 22. `--mount` vs `-v`

Docker provides multiple mount syntaxes.

You will commonly encounter:

```bash
--mount
```

and:

```bash
-v
```

or:

```bash
--volume
```

Named volume using `--mount`:

```bash
docker run \
  --mount source=veriqta-data,target=/data \
  alpine
```

Equivalent common short syntax:

```bash
docker run \
  -v veriqta-data:/data \
  alpine
```

---

# 23. Understanding `-v`

Syntax:

```text
-v SOURCE:TARGET
```

Example:

```bash
-v veriqta-data:/data
```

means:

```text
SOURCE
veriqta-data

TARGET
/data
```

Architecture:

```text
veriqta-data
     ↓
Container /data
```

---

# 24. Which Syntax Should Beginners Learn?

Learn both because you will see both in real environments.

For teaching and complex configurations, `--mount` is often easier to read because it explicitly names properties:

```text
source=
target=
readonly
```

For example:

```bash
docker run \
  --mount type=volume,source=veriqta-data,target=/data \
  alpine
```

is very explicit.

But:

```bash
-v veriqta-data:/data
```

is extremely common.

You must be comfortable reading both.

# 25. Named Volumes

A named volume has a human-defined name.

Example:

```bash
docker volume create postgres-data
```

Then:

```bash
docker run \
  --mount source=postgres-data,target=/var/lib/postgresql/data \
  postgres
```

Named volumes are useful because they are easy to:

```text
Identify
Inspect
Reuse
Back up
Restore
Manage
Reference
```

---

# 26. Anonymous Volumes

Docker can also create volumes without a meaningful user-assigned name.

For example:

```bash
docker run \
  -v /data \
  alpine
```

Docker can create an anonymous volume for:

```text
/data
```

Its identifier may look like a long generated string.

Conceptually:

```text
Container /data
      ↓
Docker-created anonymous volume
      ↓
random/generated volume identifier
```

---

# 27. Why Anonymous Volumes Can Become Confusing

Imagine repeatedly creating containers that create anonymous volumes.

Eventually:

```bash
docker volume ls
```

may contain many difficult-to-identify volumes.

You may ask:

```text
Which one belongs to which old container?

Does this contain important data?

Can I delete it?
```

For important manually managed persistent data, named volumes are usually easier to operate.

---

# 28. Anonymous Does Not Mean Temporary

This is an important distinction.

Anonymous volume does **not** automatically mean:

```text
Delete this volume when the container disappears.
```

A volume can outlive a container.

However, certain container-removal workflows can remove associated anonymous volumes when explicitly requested.

Never assume a volume is gone simply because the container is gone.

Check:

```bash
docker volume ls
```

---

# 29. `docker run --rm` and Anonymous Volumes

When using:

```bash
docker run --rm ...
```

Docker automatically removes the container when it exits.

Anonymous volumes created for that container can also be removed as part of this lifecycle.

Named volumes are not treated the same way merely because `--rm` is used.

This distinction is another reason to understand the exact storage type you created.

---

# 30. What Is a Bind Mount?

A bind mount maps a specific host filesystem path directly into a container.

Example host directory:

```text
/home/ann/project
```

mounted at:

```text
/app
```

inside a container.

Architecture:

```text
Host Filesystem
/home/ann/project
       │
       ↓
    Bind Mount
       │
       ↓
Container
/app
```

Unlike a Docker-managed volume, you choose the host path directly.

---

# 31. Bind Mount Example

Suppose:

```text
Host:
~/veriqta-bind-lab/
```

Create it:

```bash
mkdir -p ~/veriqta-bind-lab
```

Create a file:

```bash
echo "Hello from host" > ~/veriqta-bind-lab/message.txt
```

Run:

```bash
docker run --rm \
  --mount type=bind,source="$HOME/veriqta-bind-lab",target=/data \
  alpine \
  cat /data/message.txt
```

Expected:

```text
Hello from host
```

The container is reading a host file.

---

# 32. Modify a Bind-Mounted File From the Container

Run:

```bash
docker run --rm \
  --mount type=bind,source="$HOME/veriqta-bind-lab",target=/data \
  alpine \
  sh -c 'echo "Modified by container" >> /data/message.txt'
```

Now on the host:

```bash
cat ~/veriqta-bind-lab/message.txt
```

You should see the new content.

Why?

Because:

```text
Container /data/message.txt
```

and:

```text
Host ~/veriqta-bind-lab/message.txt
```

refer to the same mounted underlying host file.

---

# 33. Common Bind Mount Use Cases

Bind mounts are particularly useful during development.

For example:

```text
Developer edits:
./src/app.js

        ↓ bind mount

Container sees:
/app/src/app.js
```

This lets developers modify source code without rebuilding the image for every small development change, when the development runtime supports that workflow.

Bind mounts are also useful when a container intentionally needs host-provided:

```text
Configuration
Source code
Certificates
Specific files
Development assets
```

But direct host access creates security and portability considerations.

---

# 34. Volumes vs Bind Mounts

A simplified comparison:

| Feature                              | Volume     | Bind mount |
| ------------------------------------ | ---------- | ---------- |
| Managed by Docker                    | Yes        | No         |
| User chooses exact host path         | Usually no | Yes        |
| Good for persistent application data | Yes        | Sometimes  |
| Common for development source code   | Sometimes  | Yes        |
| Host filesystem coupling             | Lower      | Higher     |
| Easy Docker lifecycle management     | Yes        | Less       |
| Direct host-file access              | Indirect   | Yes        |

A useful beginner rule:

```text
Persistent application data
→ usually start by considering a volume

Direct access to specific host files
→ consider a bind mount
```

Production architecture may use external/cloud storage instead of either.

---

# 35. Bind Mounts and Portability

Suppose a container requires:

```text
/Users/ann/project/config
```

on the host.

That exact path may not exist on:

```text
Linux server
CI runner
Another developer's laptop
Cloud VM
```

This creates host coupling.

Volumes reduce the need for your application configuration to depend on a particular user-created host path.

---

# 36. Bind Mounts Can Hide Existing Container Files

This is one of the most important storage troubleshooting concepts.

Suppose the image contains:

```text
/app/
├── app.py
└── config.json
```

You bind mount an empty host directory:

```text
Host:
./empty/
```

onto:

```text
/app
```

inside the container.

The mounted directory obscures the files that were already visible at that mount location.

Conceptually:

```text
Image contains:

/app/app.py
/app/config.json

Then mount:

Host ./empty
      ↓
Container /app

Visible /app now comes from mount.
```

The original image files have not necessarily been destroyed.

They are hidden behind the mount for that container.

---

# 37. Classic Symptom

You build an image successfully.

Then run it with:

```bash
docker run \
  -v "$(pwd)":/app \
  myimage
```

The application reports:

```text
File not found
Module not found
Dependency missing
```

You inspect the image and know the files existed during the build.

Possible cause:

> The bind mount is hiding files that came from the image.

Always inspect mounts when files mysteriously disappear at runtime.

---

# 38. What Is `tmpfs`?

A `tmpfs` mount stores data in host memory rather than persisting it as normal disk-backed container storage.

Conceptually:

```text
Container
    │
    ↓
tmpfs mount
    │
    ↓
Host memory
```

When the container/mount goes away, the data does not provide persistent storage.

---

# 39. Why Use `tmpfs`?

Possible use cases include temporary data that should not persist to ordinary disk-backed container storage.

Examples:

```text
Temporary runtime files
Short-lived sensitive information
Transient application state
```

But `tmpfs` consumes memory.

It is not a replacement for persistent storage.

---

# 40. tmpfs Example

Run:

```bash
docker run -d \
  --name tmpfs-lab \
  --mount type=tmpfs,destination=/temporary \
  alpine \
  sleep 3600
```

Write:

```bash
docker exec tmpfs-lab \
  sh -c 'echo "temporary data" > /temporary/message.txt'
```

Verify:

```bash
docker exec tmpfs-lab cat /temporary/message.txt
```

Now remove the container:

```bash
docker rm -f tmpfs-lab
```

Create another container with a new tmpfs mount.

The old file is not persistent data.

# 42. Volume Lifecycle

A named volume has its own lifecycle.

Typical flow:

```text
Create
  ↓
Mount
  ↓
Write
  ↓
Container removed
  ↓
Volume remains
  ↓
Mount into replacement container
  ↓
Continue using data
  ↓
Backup
  ↓
Eventually remove deliberately
```

This lifecycle is different from the container lifecycle.

# 45. Mounting One Volume Into Different Containers

Create:

```bash
docker volume create shared-data
```

Container A:

```bash
docker run -d \
  --name writer \
  --mount source=shared-data,target=/shared \
  alpine \
  sleep 3600
```

Write:

```bash
docker exec writer \
  sh -c 'echo "Created by writer" > /shared/message.txt'
```

Container B:

```bash
docker run --rm \
  --mount source=shared-data,target=/shared \
  alpine \
  cat /shared/message.txt
```

Expected:

```text
Created by writer
```

Both containers accessed the same volume.

---

# 46. Does Sharing a Volume Automatically Make an Application Safe?

No.

This is extremely important.

Just because Docker lets multiple containers mount the same storage does not mean the application can safely support concurrent access.

For example:

```text
Container A
     ↓
same files
     ↑
Container B
```

can create:

```text
File locking problems
Concurrent-write corruption
Application-level race conditions
Database corruption
Unexpected state
```

The application and storage system must support the access pattern.

Docker merely provides the mount.

---

# 47. Read-Only Mounts

Sometimes a container should read data but never modify it.

Example:

```bash
docker run --rm \
  --mount type=bind,source="$HOME/veriqta-bind-lab",target=/config,readonly \
  alpine \
  cat /config/message.txt
```

The container can read:

```text
/config/message.txt
```

but should not be able to modify files through that mount.

---

# 48. Read-Only `-v` Syntax

You may also see:

```bash
-v "$HOME/veriqta-bind-lab:/config:ro"
```

Here:

```text
ro
=
read-only
```

Compare:

```text
rw
=
read-write
```

Read-write is commonly the default.

---

# 49. Why Read-Only Matters

Suppose a container only needs to read:

```text
Configuration
Certificates
Reference data
Static assets
```

Why give it write permission?

Security principle:

```text
Least privilege
```

applies to storage too.

If the application only needs:

```text
read
```

do not automatically grant:

```text
read + write
```

---

# 50. Storage Permissions

Mounting storage does not eliminate Linux filesystem permissions.

Suppose the volume contains a directory owned by:

```text
UID 999
```

but your application runs as:

```text
UID 1001
```

The application may receive:

```text
Permission denied
```

The mount exists.

The storage is present.

But the process lacks filesystem permission.

---

# 51. Ownership Matters More Than Usernames

Inside Linux filesystems, ownership is fundamentally represented by numeric:

```text
UID
GID
```

Usernames are human-readable mappings.

This creates an important container issue.

Host:

```text
UID 1000 = ann
```

Container:

```text
UID 1000 = appuser
```

The names differ.

The numeric identity may be the same.

Or the opposite can happen:

```text
Host user "ann" = UID 1000
Container user "ann" = UID 2000
```

Matching names do not guarantee matching filesystem identity.

When debugging permissions, inspect numeric IDs.

---

# 52. Check Container Identity

Run:

```bash
docker exec <container> id
```

Example:

```text
uid=1001(appuser) gid=1001(appuser)
```

Inspect mounted directory:

```bash
docker exec <container> ls -ldn /data
```

The:

```text
-n
```

option tells `ls` to show numeric UID/GID values.

Now compare:

```text
Process UID/GID
vs
Directory UID/GID and permissions
```

---

# 53. Permission Troubleshooting Model

When you see:

```text
Permission denied
```

do not immediately run:

```bash
chmod 777 ...
```

That is poor troubleshooting.

Instead:

```text
1. Which process failed?
2. Which UID/GID runs it?
3. Which path was accessed?
4. Is the path actually mounted?
5. Who owns the file/directory?
6. What are the permission bits?
7. Is the mount read-only?
8. Does SELinux/AppArmor or another security control matter?
9. What access does the application actually require?
10. Apply the smallest correct fix.
```

---

# 54. Why `chmod 777` Is Usually the Wrong First Fix

`777` gives:

```text
Owner: read + write + execute
Group: read + write + execute
Others: read + write + execute
```

For many application directories, this grants far more access than necessary.

The correct fix may instead be:

```text
Correct owner
Correct group
Correct UID/GID
Specific directory mode
Read-only mount
Application-specific writable directory
```

Permissions should solve the actual requirement, not erase security boundaries.

---

# 55. Host Paths and Bind Mount Permissions

Bind mounts directly expose host filesystem permissions.

Suppose:

```text
Host directory:
/srv/veriqta-data

Owner:
root:root

Mode:
700
```

and the container application runs as:

```text
UID 1001
```

The container may not be able to access the directory.

This is not necessarily a Docker failure.

It may be normal Linux permission enforcement.

---

# 56. Docker Desktop Considerations

On macOS and Windows, Docker Desktop uses a Linux environment underneath Docker containers.

Bind mounts cross the boundary between:

```text
macOS / Windows host
```

and:

```text
Linux container environment
```

This can introduce differences involving:

```text
Filesystem performance
Case sensitivity
File permissions
Line endings
Path syntax
File-sharing configuration
```

Do not assume a bind-mount behavior observed on native Linux will be identical in every detail on Docker Desktop.

# 71. File-Level Volume Backup Lab

For generic file data, one common Docker technique is to mount the source volume into a temporary helper container and mount a host backup directory separately.

First create:

```bash
mkdir -p "$HOME/veriqta-backups"
```

Suppose the volume is:

```text
veriqta-data
```

and contains files under its root.

You can create a tar archive:

```bash
docker run --rm \
  --mount source=veriqta-data,target=/source,readonly \
  --mount type=bind,source="$HOME/veriqta-backups",target=/backup \
  alpine \
  tar -czf /backup/veriqta-data.tar.gz -C /source .
```

---

# 72. Understand the Backup Command

Architecture:

```text
Docker Volume
veriqta-data
      │
      ↓
Temporary Alpine Container
/source
      │
      │ tar creates archive
      ↓
/backup
      │
      ↓
Host Directory
~/veriqta-backups
```

The source is mounted:

```text
readonly
```

because the backup process only needs to read it.

---

# 73. Understand `tar`

Command:

```bash
tar -czf /backup/veriqta-data.tar.gz -C /source .
```

Important options:

```text
-c
→ create archive

-z
→ gzip compression

-f
→ archive filename follows

-C /source
→ change to /source before archiving

.
→ archive contents of current directory
```

Result:

```text
~/veriqta-backups/veriqta-data.tar.gz
```

on the host.

---

# 74. Verify the Backup

On the host:

```bash
ls -lh "$HOME/veriqta-backups"
```

Inspect archive contents:

```bash
tar -tzf "$HOME/veriqta-backups/veriqta-data.tar.gz"
```

Do not call something a backup merely because a command exited successfully.

Verify the artifact exists and contains expected data.


Restore:

```bash
docker run --rm \
  --mount source=veriqta-restored-data,target=/restore \
```

```bash

  --mount source=veriqta-restored-data,target=/data,readonly \
```


```text
  ↓

  ↓
Restore
  ↓

```

# 77. Database Backups Need Database Awareness

Do not blindly assume filesystem-level copying is always the correct backup method for a running database.

Databases maintain:

```text
Memory state
Transaction logs
Data files
Indexes
Write-ahead logs
Locks
Consistency guarantees
```

Copying files while a database is actively writing may create an inconsistent backup depending on the database and backup method.

For databases, use database-supported backup mechanisms unless you have a carefully designed storage snapshot strategy.

# 78. PostgreSQL Logical Backup

```text

```


# 79. Important Redirection Detail

In:


the:

```text

```

is normally interpreted by your **host shell**, not inside the container.

Flow:

```text
pg_dump inside container
       ↓
stdout
       ↓
docker exec
       ↓
host shell
       ↓
backup.sql
```

Understanding where redirection occurs prevents a lot of confusion.

# 103. Docker Socket Warning

Do not mount:

```text
/var/run/docker.sock
```

into an arbitrary container simply because a tutorial tells you to.

Example:

```bash
-v /var/run/docker.sock:/var/run/docker.sock
```

can give a container powerful control over Docker on the host.

That can effectively become host-level control in many configurations.

A storage mount is not harmless merely because it looks like a file path.

Understand the security impact of every mount.

# 104. Mounting the Host Root Is Dangerous

Avoid careless commands such as:

```bash
-v /:/host
```

especially with writable access.

This can expose the host filesystem to the container.

A compromised or buggy process could potentially alter critical host files.

Principle:

```text
Mount only what is required.
Give only required access.
Prefer read-only when write access is unnecessary.
```

# What You Should Now Understand

You should now understand that Docker images contain read-only image layers and containers receive a writable layer.

The container writable layer belongs to that specific container.

Stopping a container does not automatically delete its writable data.

Removing the container normally removes its writable layer.

Important data therefore should not depend on a replaceable container's writable layer.

Persistent data has a lifecycle independent from a particular container.

Docker volumes provide Docker-managed storage that can outlive containers.

Named volumes have user-defined names and are easier to identify and manage.

Anonymous volumes are Docker volumes without a meaningful user-assigned name.

Anonymous does not automatically mean disposable.

Bind mounts map specific host paths directly into containers.

Bind mounts are especially useful for development and deliberate host-file access.

Bind mounts can obscure files that already existed at the container mount destination.

tmpfs provides temporary memory-backed storage rather than persistent disk storage.

`--mount` and `-v` can both configure mounts, but their syntax differs.

Read-only mounts implement least privilege when applications do not need write access.

Filesystem permissions still apply to mounted storage.

UID and GID relationships matter when diagnosing permission problems.

`chmod 777` is not a proper default solution.

A Docker volume can be mounted into more than one container, but that does not guarantee that concurrent application access is safe.

Database data should be stored outside the replaceable container writable layer.

A replacement database container can mount the same persistent volume and recover access to existing data, provided the database version and storage format are compatible.

Persistence is not backup.

A volume can survive container removal while still being vulnerable to deletion, corruption, host loss, or application mistakes.

Database backups should generally use database-aware mechanisms or properly designed snapshot procedures.

Backups must be verified.

Restore procedures must be tested.

Volumes can be removed with `docker volume rm`.

Unused volumes can be pruned with `docker volume prune`, but pruning persistent storage without understanding it can cause permanent data loss.

`docker inspect` is essential for diagnosing actual mount configuration.

`docker volume inspect` provides volume information.

`docker system df` helps investigate Docker disk consumption.

Production storage requires consideration of persistence, backup, restore, capacity, permissions, security, upgrades, and host failure.

Most importantly:

```text
Container
=
replaceable runtime

Persistent storage
=
data that must survive that runtime
```

# Part 7 Summary

The entire part can be reduced to one architecture:

```text
Container
    │
    │ reads/writes
    ↓
Persistent Volume
    │
    ↓
Durable Data
```

The container can be:

```text
Stopped
Started
Failed
Removed
Rebuilt
Replaced
Upgraded
```

while properly designed persistent data remains independent.

You learned the four important storage relationships:

```text
Container Writable Layer
→ container-specific filesystem changes

Docker Volume
→ Docker-managed persistent storage

Bind Mount
→ direct host filesystem access

tmpfs
→ temporary memory-backed storage
```

You also learned that production storage is much more than:

```text
-v something:/data
```

Real storage engineering requires:

```text
Persistence
Permissions
Ownership
Least privilege
Capacity
Backup
Restore
Database consistency
Version compatibility
Security
Host-failure planning
Troubleshooting
```

The most important transformation is:

```text
BAD MENTAL MODEL

Container
   ↓
"My important data lives here forever."
```

Replace it with:

```text
CORRECT MENTAL MODEL

Replaceable Container
        │
        ↓
Persistent Storage
        │
        ↓
Durable Application Data
```

```text
Application
     ↓
Database Container
     ↓
Database Data Directory
     ↓
Persistent Volume
     ↓
Database Files
     ↓
Independent Backup
```

That distinction between **runtime and state** is one of the foundations of production container engineering.
