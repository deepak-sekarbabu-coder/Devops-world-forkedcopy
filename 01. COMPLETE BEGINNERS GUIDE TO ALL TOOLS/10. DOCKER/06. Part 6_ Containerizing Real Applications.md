# Part 6: Containerizing Real Applications

## From Source Code to a Running Application Container

In Part 5, you learned how Dockerfiles work.

You learned instructions such as:

```text
FROM
WORKDIR
COPY
RUN
ENV
EXPOSE
USER
CMD
ENTRYPOINT
HEALTHCHECK
```

Now we will use those instructions for their real purpose:

```text
taking an application
and turning it into a runnable container image.
```

The basic journey is:

```text
Source Code
↓
Dependencies
↓
Dockerfile
↓
docker build
↓
Image
↓
docker run
↓
Container
↓
Browser / API Client
```

By the end of this part, you will containerize three different types of applications:

```text
Node.js API
Python API
Static Website with Nginx
```

You will also learn what happens when those containers fail.

This part is not about memorizing Dockerfile instructions.

It is about learning how to look at an application and answer:

```text
What does this application need to run?

What runtime does it require?

What dependencies does it require?

What files belong in the image?

What files should stay outside the image?

What port does it listen on?

How should configuration reach it?

How should it log?

What process should Docker start?

What user should run that process?

How should Docker determine whether it is healthy?

How should the application stop?

What evidence should I collect when it fails?
```

That is application containerization.

---

# 1. What Does Containerizing an Application Mean?

Suppose a developer gives you an application.

The source directory might contain:

```text
application/
├── app.py
├── requirements.txt
└── README.md
```

The source code alone is usually not enough to run it.

The application may also require:

```text
Python
Flask
environment variables
configuration
network ports
operating-system libraries
```

Without Docker, another engineer may need instructions such as:

```text
Install Python.

Install pip.

Install the dependencies.

Set environment variables.

Start the application.

Make sure the correct Python version is installed.
```

That creates opportunities for differences between machines.

Containerization moves much of that runtime definition into an image.

```text
Source Code
+
Runtime
+
Application Dependencies
+
Runtime Configuration Defaults
+
Startup Definition
↓
Container Image
```

Running the image creates a container.

# 5. Build Dependencies vs Runtime Dependencies

This distinction is extremely important.

An application may require tools while being built that it does not require while running.

Example:

```text
Build Stage

compiler
package manager
source code
development headers
build tools
```

But runtime may only require:

```text
compiled application
runtime libraries
configuration
```

Therefore:

```text
Build Dependencies
≠
Runtime Dependencies
```

This becomes especially important when you learn advanced multi-stage builds in Part 11.

Ask:

```text
How can I prove the application is actually functioning?
```

Not merely:

```text
Is the process running?
```

```text
/health
```

or:

```text
/healthz
```

# 12. Shutdown Behavior

Ask:

```text
What happens when the application receives SIGTERM?
```

A well-behaved application should normally:

```text
receive termination signal
↓
stop accepting new work
↓
finish or safely terminate current work
↓
release resources
↓
exit
```

That is graceful shutdown.

# 13. Preparing an Application for Containerization

Before writing a Dockerfile, clean the application structure.

A good project should clearly separate:

```text
source code
dependency definitions
configuration
tests
generated files
secrets
build output
```

For example:

```text
my-app/
├── src/
├── tests/
├── package.json
├── package-lock.json
├── Dockerfile
├── .dockerignore
├── .gitignore
└── README.md
```

Avoid chaotic structures where:

```text
source
secrets
logs
temporary files
dependencies
build artifacts
```

are all mixed together.

---

# 14. Never Put Secrets in the Application Source

Do not write:

```python
DATABASE_PASSWORD = "supersecret123"
```

Do not write:

```javascript
const API_KEY = "real-production-key";
```

Do not copy `.env` files containing secrets into images.

Remember:

```text
Image
↓
Registry
↓
Developer Machine
↓
CI System
↓
Production Server
```

Images travel.

Secrets embedded in them travel too.


# 16. Choosing a Base Image

Every normal Dockerfile begins from some base stage.

Example:

```dockerfile
FROM python:3.13-slim
```

or:

```dockerfile
FROM node:24-bookworm-slim
```

or:

```dockerfile
FROM nginx:alpine
```

The base image determines much of the runtime environment.

---

# 17. Base Image Selection Questions

Ask:

```text
Is the image maintained?

Is it from a trusted source?

Does it contain the required runtime?

Which operating-system family does it use?

Does the application require native libraries?

Is the architecture supported?

How large is it?

How often is it patched?

Does the team understand how to operate it?
```

Do not choose an image only because it is small.

---

# 18. Smaller Is Not Automatically Better

You might see:

```text
full distribution
slim image
Alpine
distroless
scratch
```

Each has trade-offs.

A very small image can reduce unnecessary content.

But it can also make:

```text
compatibility
debugging
native dependencies
certificate handling
operational investigation
```

more difficult.

Choose deliberately.

---

# 19. Version Tags

Avoid blindly relying on:

```dockerfile
FROM python:latest
```

or:

```dockerfile
FROM node:latest
```

because the runtime behind the tag can change.

Prefer an intentionally selected version.

For example:

```dockerfile
FROM python:3.13-slim
```

For stronger production reproducibility, teams may pin images more precisely, including by digest.

We explore this more deeply later.

# 23. Why package-lock.json Matters

`package.json` describes dependency requirements.

`package-lock.json` records the resolved dependency tree.

For reproducible automated installations, we can use:

```bash
npm ci
```

instead of:

```bash
npm install
```

inside the image build when a valid lock file exists.

# 24. Create the Node.js Application

Create:

```text
server.js
```

```javascript
const express = require("express");

const app = express();

const port = Number(process.env.PORT || 3000);
const appEnv = process.env.APP_ENV || "development";

app.get("/", (req, res) => {
  res.json({
    application: "VERIQTA Node Container",
    environment: appEnv
  });
});

app.get("/health", (req, res) => {
  res.status(200).json({
    status: "healthy"
  });
});

const server = app.listen(port, "0.0.0.0", () => {
  console.log(`application listening on port ${port}`);
});

function shutdown(signal) {
  console.log(`${signal} received, starting graceful shutdown`);

  server.close((error) => {
    if (error) {
      console.error("shutdown error", error);
      process.exit(1);
    }

    console.log("HTTP server closed");
    process.exit(0);
  });

  setTimeout(() => {
    console.error("graceful shutdown timed out");
    process.exit(1);
  }, 10000).unref();
}

process.on("SIGTERM", () => shutdown("SIGTERM"));
process.on("SIGINT", () => shutdown("SIGINT"));
```

---

# 25. Understand the Application

This line:

```javascript
const port = Number(process.env.PORT || 3000);
```

means:

```text
Use PORT environment variable if supplied.

Otherwise use 3000.
```

This is runtime configuration.

---

# 26. Why 0.0.0.0 Matters

The application listens on:

```text
0.0.0.0
```

not:

```text
127.0.0.1
```

inside the container.

Why?

Because:

```text
127.0.0.1
```

inside the container refers to that container's own loopback interface.

Listening on:

```text
0.0.0.0
```

allows the process to accept traffic arriving through the container's network interfaces.


```bash

```

# 28. Graceful Shutdown

The application listens for:

```text
SIGTERM
SIGINT
```

When Docker stops the container, the application should have an opportunity to close cleanly.

The important path is:

```text
docker stop
↓
termination signal
↓
Node.js process
↓
server.close()
↓
existing connections finish
↓
process exits
```

# 31. Read the Dockerfile Line by Line

```dockerfile
FROM node:24-bookworm-slim
```

provides the Node.js runtime.

---

```dockerfile
WORKDIR /app
```

creates/selects the application working directory.

Subsequent relative operations happen relative to:

```text
/app
```

---

```dockerfile
COPY package.json package-lock.json ./
```

copies dependency metadata first.

Why before application source?

Because dependency installation can remain cached when application source changes but dependency files do not.

---

```dockerfile
RUN npm ci --omit=dev
```

installs production dependencies from the lock file.

---

```dockerfile
COPY --chown=node:node server.js ./
```

copies the application source and assigns ownership.

---

```dockerfile
USER node
```

means the runtime process does not intentionally run as root.

---

```dockerfile
EXPOSE 3000
```

documents the intended container port.

It does not publish that port to your host.

---

```dockerfile
CMD ["node", "server.js"]
```

defines the default startup command.

# 40. Add a Node Health Check

We deliberately avoid assuming that tools such as `curl` exist inside every runtime image.

Node itself is available, so we can perform the health request using Node.

Add before `CMD`:

```dockerfile
HEALTHCHECK \
  --interval=30s \
  --timeout=3s \
  --start-period=5s \
  --retries=3 \
  CMD ["node", "-e", "fetch('http://127.0.0.1:3000/health').then(r=>{if(!r.ok)process.exit(1)}).catch(()=>process.exit(1))"]
```

Rebuild:

```bash
docker build -t veriqta-node-app:1.1 .
```

Replace the old container:

```bash
docker rm -f veriqta-node
```

Run:

```bash
docker run \
  --name veriqta-node \
  -p 3000:3000 \
  -e APP_ENV=production \
  -d \
  veriqta-node-app:1.1
```

# 42. Running Does Not Mean Healthy

A container can be:

```text
running
```

while its application is:

```text
broken
```

That is why these are different questions:

```text
Is the process alive?

Is the application functioning?
```

# 43. Health Check Exit Codes

Conceptually:

```text
0
=
healthy check

1
=
failed check
```

Docker records health results and eventually changes the container health status according to the configured health-check thresholds.

---

# 44. Health Does Not Automatically Restart Standalone Containers

Important:

```text
unhealthy
```

does not mean standalone Docker automatically replaces or restarts the container merely because its health check failed.

Health is a signal.

Higher-level systems may use that signal for operational decisions.

```text

```

```text

↓
PID 1
```



---

# 47. Why PID 1 Matters

PID 1 has special responsibilities and behavior on Linux.

For containerized applications, important concerns include:

```text
signal handling
child process handling
shutdown
```

This is one reason startup commands matter.

---

# 48. Exec Form vs Shell Form

Preferred for many application startup commands:

```dockerfile
CMD ["node", "server.js"]
```

This is exec form.

Compare:

```dockerfile
CMD node server.js
```

which is shell form.

Shell form normally introduces a shell:

```text
/bin/sh -c "node server.js"
```

That can change process and signal behavior.

For straightforward application processes, exec form is usually preferable.

# 50. Failure Lab: Wrong Port

Remove the old container:

```bash
docker rm -f veriqta-node
```

Run:

```bash
docker run \
  --name veriqta-node \
  -p 8080:3000 \
  -d \
  veriqta-node-app:1.1
```

Now try:

```bash
curl http://127.0.0.1:3000/
```

It fails.

Why?

Because the host mapping is:

```text
Host 8080
↓
Container 3000
```

Correct request:

```bash
curl http://127.0.0.1:8080/
```

Lesson:

```text
container port
≠
host port
```

# 55. ENV vs -e

Dockerfile:

```dockerfile
ENV APP_ENV=production
```

provides an image default.

Runtime:

```bash
docker run -e APP_ENV=staging ...
```

can override it.

Think:

```text
Image Default
↓
Runtime Override
```

---

# 56. Environment Variables Are Not a Secret Vault

This:

```bash
docker run \
  -e DATABASE_PASSWORD=secret \
  ...
```

does not magically turn the value into a secure secret-management system.

Environment values may be exposed through:

```text
process/container configuration
debugging
logs
automation mistakes
inspection access
```

Sensitive production configuration requires deliberate secret management.

# 59. Python Application

```text

```

```python
import os
import signal
import sys

from fastapi import FastAPI

app = FastAPI()

APP_ENV = os.getenv("APP_ENV", "development")


@app.get("/")
def root():
    return {
        "application": "VERIQTA Python Container",
        "environment": APP_ENV,
    }


@app.get("/health")
def health():
    return {
        "status": "healthy",
    }


def handle_shutdown(signum, frame):
    print(
        f"signal {signum} received, shutting down",
        flush=True,
    )
    sys.exit(0)


signal.signal(signal.SIGTERM, handle_shutdown)
signal.signal(signal.SIGINT, handle_shutdown)
```

```dockerfile
HEALTHCHECK \
  --interval=30s \
  --timeout=3s \
  --start-period=5s \
  --retries=3 \

  "-m",
  "uvicorn",
  "app:app",
  "--host",
  "0.0.0.0",

]
```

# 63. Why PYTHONDONTWRITEBYTECODE?

```dockerfile
ENV PYTHONDONTWRITEBYTECODE=1
```

prevents Python from writing `.pyc` bytecode files in normal operation.

This can keep the container filesystem cleaner for this style of deployment.

---

# 64. Why PYTHONUNBUFFERED?

```dockerfile
ENV PYTHONUNBUFFERED=1
```

helps application output appear promptly in container logs rather than being delayed by output buffering.

That improves operational visibility.

---

# 65. Why --no-cache-dir?

```bash

```

prevents pip's download cache from being retained unnecessarily in this image layer.

It does not mean Docker's own build cache is disabled.

Those are different caches.

```text

```

```text

```

and tries to write there.

# 104. Liveness vs Readiness Thinking

Even though standalone Docker exposes a general health status rather than Kubernetes-style separate probes, understand the concepts.


```text

```

These are not always identical.

# 106. Graceful Shutdown

Containers are temporary.

Applications must expect to stop.

Reasons include:

```text
deployment
scaling
host maintenance
manual stop
failure recovery
orchestration
```

Therefore shutdown is part of application design.

---

# 107. docker stop

When you run:

```bash
docker stop CONTAINER
```

Docker sends the container's configured stop signal to PID 1.

The default stop signal is normally:

```text
SIGTERM
```

unless configured otherwise.

Docker waits for the applicable timeout.

If the process does not exit, Docker can force termination.

---

# 108. SIGTERM vs SIGKILL

Conceptually:

```text
SIGTERM
=
please terminate
```

The application can handle it.

```text
SIGKILL
=
terminate immediately
```

The process cannot catch SIGKILL to perform normal cleanup.

Therefore graceful applications should respond correctly to termination signals before forced termination becomes necessary.

---

# 109. STOPSIGNAL

Dockerfile supports:

```dockerfile
STOPSIGNAL SIGTERM
```

This defines the image's intended stop signal.

You do not need to add it merely to restate the default unless doing so adds clarity or the application requires another signal.

---

# 110. Graceful Shutdown Example

Imagine an application processing a request.

Bad shutdown:

```text
request executing
↓
container terminated immediately
↓
work interrupted
```

Graceful shutdown:

```text
SIGTERM
↓
stop accepting new work
↓
finish current work
↓
close connections
↓
flush necessary state
↓
exit
```

# 111. PID 1 and Startup Commands

Suppose Dockerfile contains:

```dockerfile
CMD ["python", "app.py"]
```

Then Python can become PID 1 directly.

But:

```dockerfile
CMD python app.py
```

typically introduces:

```text
/bin/sh -c
```

The resulting process hierarchy differs.

That can matter for signals.

# 112. Shell Wrapper Problem

Suppose:

```dockerfile
CMD ["./start.sh"]
```

and `start.sh` contains:

```sh

python app.py
```

Then:

```text
shell
↓
python
```

may remain.

A better script may end with:

```sh
exec python app.py
```

Then the shell is replaced by the application process.

---

# 113. exec in Startup Scripts

Example:

```sh
#!/bin/sh

set -e

echo "starting application"

exec python app.py
```

The important line is:

```text
exec
```

It replaces the shell process with the application process.

This helps preserve cleaner signal behavior.

This places a small init process inside the container to help with:
