## Learn How Images Move Between Developers, CI/CD, Servers, and Cloud Environments

In Part 11, you learned how to transform a development-style Docker image into a professionally engineered production image.

You learned about:

* multi-stage builds;

* runtime stages;
* smaller production images;
* BuildKit;
* cache optimization;
* non-root execution;
* image metadata;
* versioning;

But we still have an important problem.

For example:

```text
Developer Laptop
      |
      | docker build
      v
Docker Image
      |
      ?
      |
      v
Production Server
```

How does the image reach the server?

You could try to manually copy image files between machines.

That would quickly become difficult to manage.

Instead, container environments normally use an image registry.

The workflow becomes:


# 2. The Problem Registries Solve

Imagine you build:

```text
veriqta-api:1.0.0
```

on your laptop.

Run:

```bash
docker image ls
```

You can see the image.

Now connect to another Linux server and run:

```bash
docker image ls
```

The image is not there.

Why?

Because Docker images are not automatically synchronized between Docker hosts.

Your laptop has its own local image store.

The server has another.

Conceptually:

```text
Developer Docker Host

Local Image Store
├── nginx
├── postgres
└── veriqta-api:1.0.0


Production Docker Host

Local Image Store
├── nginx
└── redis
```

The production host does not magically know about:

```text
veriqta-api:1.0.0
```

We need a distribution mechanism.

That mechanism is usually a registry.

---

# 3. What Is a Container Registry?

A container registry is a service that stores and distributes container images and related OCI artifacts.

Conceptually:

```text
                    Registry

          ┌───────────────────────┐
          │                       │
Push ---> │   Stored Images       │ ---> Pull
          │                       │
          └───────────────────────┘
```

Developers and CI/CD systems push images.

Servers and deployment platforms pull images.

---

# 4. Registry Mental Model

Think of a registry as a distribution center.

```text
Developer
   |
   | build
   v
Image
   |
   | push
   v
+-----------------------+
| Container Registry    |
|                       |
| app:1.0.0             |
| app:1.1.0             |
| app:2.0.0             |
+-----------------------+
   |
   | pull
   v
Production Server
```

The registry gives multiple systems a common place from which images can be distributed.

---

# 5. Registry vs Repository

These terms are frequently confused.

A:

```text
registry
```

is the service hosting container image repositories.

A:

```text
repository
```

is a logical collection of related image versions.

Conceptually:

```text
Registry
│
├── Repository: frontend
│   ├── 1.0.0
│   ├── 1.1.0
│   └── 2.0.0
│
├── Repository: api
│   ├── 1.0.0
│   ├── 1.1.0
│   └── 1.2.0
│
└── Repository: worker
    ├── 1.0.0
    └── 1.1.0
```

The registry contains repositories.

Repositories contain image versions/references.

---

# 6. Registry Is Not the Same as Git Repository

Another important distinction:

```text
Git repository
```

contains source code and source history.

```text
Container image repository
```

stores container images/artifacts.

For example:

```text
GitHub Repository
      |
      | source code
      v
Docker Build
      |
      | creates
      v
Container Image
      |
      | push
      v
Container Registry Repository
```

Do not confuse the two simply because both use the word:

```text
repository
```

# 7. Example Registry Architecture

Imagine an organization called:

```text
veriqta
```

Its registry might conceptually contain:

```text
Registry
│
├── veriqta/frontend
│   ├── 1.0.0
│   ├── 1.1.0
│   └── latest
│
├── veriqta/api

│   ├── 1.1.0
│   └── latest
```

# 8. Registry Architecture at a Deeper Level

A modern registry does not simply store:

```text
app.tar
```

as one giant file.

Images are composed from OCI/Docker image structures such as:

```text
Image
├── Manifest
├── Configuration
└── Layers
```

The registry stores and serves these content objects.

Conceptually:

```text
Client
  |
  | request manifest
  v
Registry
  |
  +--> Manifest
  |
  +--> Config
  |
  +--> Layer A
  |
  +--> Layer B
  |
  +--> Layer C
```

This helps explain why Docker may report:

```text
Layer already exists
```

during a push.

---

# 9. Layers Can Be Reused

Suppose two image versions share most layers:

```text
app:1.0
├── Base layer A
├── Dependency layer B
└── Application layer C

app:1.1
├── Base layer A
├── Dependency layer B
└── Application layer D
```

The registry does not necessarily need another independent copy of every unchanged layer.

Content-addressed storage enables reuse.

This is one reason image layers matter beyond local builds.

# 10. Public Registries

A public registry allows images or repositories to be accessible publicly according to the registry's rules.

Examples include public images such as:

```text
nginx
redis
postgres
ubuntu
```

When you run:

```bash
docker pull nginx
```

Docker retrieves an image from a registry.

For an unqualified image such as this, Docker's normal default registry behavior points to Docker Hub.

---

# 11. Private Registries

A private registry restricts access.

For example:

```text
company-api
payment-service
internal-worker
proprietary-application
```

may not be appropriate for public distribution.

Access may require:

```text
authentication
+
authorization
```

---

# 12. Authentication vs Authorization

Remember this distinction.

Authentication asks:

```text
Who are you?
```

Authorization asks:

```text
What are you allowed to do?
```

For example:

```text
Developer Alice
    ↓
authenticated
    ↓
Can pull api
Can push api
Cannot delete production images
```

Another user:

```text
Deployment Server
    ↓
authenticated
    ↓
Can pull production images
Cannot push
Cannot delete
```

This is least privilege.

---

# 13. Public vs Private Does Not Mean Secure vs Insecure

A public image is not automatically insecure.

A private image is not automatically secure.

Visibility and security are different concepts.

A private repository can still contain:

* vulnerable packages;
* malicious dependencies;
* embedded secrets;
* insecure configuration.

A public repository can contain a properly engineered image intended for public use.

# 24. Tags

A tag is a human-readable reference associated with image content.

Examples:

```text
1.0.0
1.1.0
2.0.0
latest
main
staging
production
build-481
sha-a74c91f
```

Tags can communicate different things depending on your strategy.

---

# 25. Tags Are Not Separate Images by Definition

Suppose:

```text
app:1.0.0
```

and:

```text
app:production
```

both point to the same image content.

You have two tags referring to the same underlying image.

Conceptually:

```text
app:1.0.0 -------+
                 |
                 v
             Image A
                 ^
                 |
app:production --+
```

# 26. Tag an Existing Image

Suppose:

```bash

```

shows:

```text

```

```bash
docker tag \
  veriqta-registry-lab:1.0.0 \
  YOUR_DOCKERHUB_USERNAME/veriqta-registry-lab:1.0.0
```

Replace:

```text
YOUR_DOCKERHUB_USERNAME
```

with your real namespace.

---

# 27. Verify the Tag

Run:

```bash
docker image ls
```

You may see both:

```text
veriqta-registry-lab:1.0.0
```

and:

```text
YOUR_DOCKERHUB_USERNAME/veriqta-registry-lab:1.0.0
```

# 28. `docker tag` Does Not Push

This is important.

Running:

```bash
docker tag ...
```

does not upload anything.

It creates another local image reference.

Workflow:

```text
Build
  ↓
Local Image
  ↓
docker tag
  ↓
Registry-Compatible Local Reference
  ↓
docker push
  ↓
Remote Registry
```

# 29. Authentication

Before pushing to a private or authenticated registry workflow, the Docker client must authenticate appropriately.

For Docker Hub:

```bash
docker login
```

Modern Docker login behavior may use an interactive web/device flow for Docker Hub depending on your Docker CLI and options.

Follow the prompts presented by your actual client.

---

# 30. Login to a Specific Registry

For another registry:

```bash
docker login REGISTRY_HOST
```

Example pattern:

```bash
docker login registry.example.com
```

The registry hostname tells Docker where the credentials apply.

---

# 31. Username Login

Where supported and appropriate, you may explicitly provide a username:

```bash
docker login \
  --username YOUR_USERNAME
```

The client then obtains the credential through the supported login flow.

Avoid placing passwords directly in shell command history.

---

# 32. `--password-stdin`

For non-interactive environments, Docker supports reading a password/token from standard input.

Pattern:

```bash
printf '%s' "$REGISTRY_TOKEN" |
docker login \
  --username "$REGISTRY_USER" \
  --password-stdin \
  REGISTRY_HOST
```

This is preferable to putting a secret directly into the command arguments.

But the environment variable itself still needs secure handling.

---

```text
CI secret store

```

not:

```text
Dockerfile

```

Conceptually:

```text

       ↓

       ↓

       ↓

```

# 34. Docker Credential Storage

Docker may use:

* native credential stores;
* credential helpers;
* Docker configuration.

Credential behavior depends on your platform and configuration.

Inspect:

```text
~/.docker/config.json
```

carefully if troubleshooting.

Do not publish this file.

Do not assume it is safe merely because you cannot immediately see a plain-text password.

---

# 35. Never Commit Docker Credentials

Do not commit:

```text
~/.docker/config.json
```

to Git.

Do not copy authentication files into images.

Do not put registry tokens in:

```dockerfile
ENV REGISTRY_PASSWORD=...
```

Do not place them in:

```dockerfile
ARG REGISTRY_PASSWORD=...
```

Credentials belong in credential-management systems.

---

# 36. Verify Login

After a successful authentication flow, the Docker client should report success.

You can then test an operation appropriate to your permissions.

Authentication success does not guarantee:

```text
push authorization
```

for every repository.

You may authenticate successfully but still lack permission to push.

---

# 37. Logout

Use:

```bash
docker logout
```

for Docker Hub/default registry context.

For a specific registry:

```bash
docker logout REGISTRY_HOST
```

This removes the Docker client's stored login credentials for that registry from its configured credential mechanism.

---

# 38. Login Failure Troubleshooting

If login fails, investigate:

```text
Correct registry hostname?
Correct username?
Correct token/password?
Token expired?
Correct token permissions?
Account authorized?
Network reachable?
DNS working?
Proxy interfering?
TLS certificate trusted?
```

Do not solve authentication failures by disabling TLS verification.

# 39. Push an Image

Once the image is correctly tagged:

```bash
docker push \
  YOUR_DOCKERHUB_USERNAME/veriqta-registry-lab:1.0.0
```

Docker uploads the required image content to the registry.

---

# 40. Representative Push Output

You may see output conceptually similar to:

```text
The push refers to repository [...]
layer-a: Pushed
layer-b: Pushed
layer-c: Layer already exists
1.0.0: digest: sha256:...
```

Exact output differs.

Pay attention to the final digest.

---

# 41. What Happened During Push?

Conceptually:

```text
Local Image
    ↓
Read Manifest
    ↓
Identify Layers
    ↓
Contact Registry
    ↓
Authenticate/Authorize
    ↓
Check Existing Content
    ↓
Upload Missing Content
    ↓
Publish Manifest
    ↓
Associate Tag
```

This is more accurate than thinking:

```text
Docker copied one giant image file.
```

---

# 42. `Layer already exists`

If Docker says:

```text
Layer already exists
```

that is normally not an error.

The registry already contains that content.

Docker does not need to upload it again.

---

# 49. Image Versions

Production systems need a way to identify releases.

Suppose you release:

```text
1.0.0
1.1.0
1.1.1
2.0.0
```

Each release can have its own image reference.

Example:

```text
veriqta-api:1.0.0
veriqta-api:1.1.0
veriqta-api:1.1.1
veriqta-api:2.0.0
```

---

# 50. Semantic Versioning Concept

Semantic Versioning commonly uses:

```text
MAJOR.MINOR.PATCH
```

Example:

```text
2.4.7
```

Conceptually:

```text
2 = major
4 = minor
7 = patch
```

Semantic versioning has defined compatibility semantics when a project follows the SemVer specification.

Do not call a tag "semantic versioning" merely because it contains three numbers if the project does not actually follow SemVer rules.

---

# 51. Multiple Useful Tags

One image might intentionally receive multiple tags.

Example:

```text
app:2.4.7
app:2.4
app:2
```

possibly:

```text
app:latest
```

depending on policy.

Conceptually:

```text
2.4.7 ----+
2.4 ------+
2 --------+--> Same Image
latest ---+
```

But remember:

these tags can later be moved unless the registry prevents it.

---

# 52. The Problem With `latest`

`latest` is not:

```text
most secure
```

It is not inherently:

```text
newest production release
```

It is not:

```text
magic
```

It is simply a tag.

If you run:

```bash
docker pull myapp:latest
```

you are asking for whatever content the registry currently associates with that tag.

---

# 53. Why `latest` Can Be Dangerous in Production

Imagine Monday:

```text
latest → Image A
```

Tuesday:

```text
latest → Image B
```

Your deployment manifest still says:

```text
myapp:latest
```

but its meaning changed.

That makes reasoning about exact deployments harder.

---

# 54. Mutable Tags

A mutable tag can be moved to different image content.

Conceptually:

```text
Monday

production
    ↓
Image A
```

Later:

```text
Friday

production
    ↓
Image B
```

The tag remained:

```text
production
```

but the artifact changed.

---

# 55. Immutable References

For high-confidence deployments, we want a reference that identifies exact content.

Image digests provide this.

Example:

```text
myapp@sha256:abc123...
```

Conceptually:

```text
Tag
↓
Human-friendly pointer
↓
May move
```

versus:

```text
Digest
↓
Content-addressed identity
↓
Exact image content
```

---

# 56. Image Digest

After a pull or push, Docker may show:

```text
Digest: sha256:...
```

The digest identifies image content through a cryptographic hash.

This gives you a much stronger answer to:

```text
Which exact image are we deploying?
```

---

# 57. Pull by Digest

Pattern:

```bash
docker pull \
  repository@sha256:DIGEST
```

For example:

```bash
docker pull \
  YOUR_DOCKERHUB_USERNAME/veriqta-registry-lab@sha256:YOUR_DIGEST
```

Use a real digest returned by your registry.

Do not copy a fake placeholder digest.

---

# 58. Run by Digest

You can also run an exact digest reference:

```bash
docker run \
  --rm \
  repository@sha256:DIGEST
```

This avoids relying on the current meaning of a mutable tag.

---

# 59. Tag for Humans, Digest for Exactness

A useful mental model:

```text
Tag
→ What release do humans call this?
```

```text
Digest
→ What exact content is this?
```

Both are useful.

They solve different problems.

---

# 60. Production Deployment Strategy

A deployment pipeline might record:

```text

2.4.7

a83f1d2

registry.example.com/api:2.4.7
```

# 61. Artifact Identity

Think about:

```text
Git Commit
    ↓
Build
    ↓
Image
    ↓
Digest
    ↓
Deployment
```

This creates a traceability chain.

During an incident you can ask:

```text
Which Git commit produced this image?

Which image digest is running?

When was it built?

Which pipeline built it?

Which environment deployed it?
```

---

# 62. Immutable Deployment Reference

An immutable deployment strategy can use:

```text
registry/repository@sha256:...
```

rather than only:

```text
registry/repository:production
```

This prevents the meaning of the deployment reference from changing simply because a tag moves.

---

# 63. Tags Still Matter

Digest-based deployment does not make tags useless.

Tags remain valuable for:

```text
human readability
release discovery
version grouping
workflow organization
```

A mature workflow often uses both.

```text
Environment pointer:
staging

Moving convenience tag:
latest
```

Each tag communicates something different.

Do not mix meanings without a documented convention.

# 65. Git SHA Tags

A CI pipeline can create:

```text
api:sha-a3f91d8
```

This provides a useful connection between source revision and image.

However, remember:

```text
tag
```

can still be mutable unless your registry policy prevents replacement.

The Git SHA text itself does not magically make a registry tag immutable.

# 66. Build Number Tags

```text

```

This is useful when your CI system has unique build numbers.

A release record could then contain:

# 67. Do Not Rebuild the Same Release for Each Environment

```text
    ↓

    ↓

    ↓

```

not:

```text

    ↓

```

If you rebuild, you may create different content.

The artifact that passed testing should ideally be the artifact promoted.

# 71. CI Registry Credentials



access.

# 75. Authentication Failure vs Authorization Failure



Troubleshooting differs.

```text

```

```bash

  myapp:1.0 \
```

# 94. Registry Cleanup


# 95. Why Cleanup Is Not Simply "Delete Old Images"

An old image may still be:


Blind deletion can break recovery.

Cleanup requires policy.

# 96. Retention Questions


The exact policy depends on the organization.

# 197. Final Mental Model

Before registries, your image exists here:

```text
Developer Laptop
      ↓
Local Docker Engine
      ↓
Local Image
```

That is not enough for distributed software delivery.

A registry creates:

```text
Developer
    |
    | docker build
    v
Local Image
    |
    | tag
    v
Versioned Image Reference
    |
    | authenticate
    v
Registry
    |
    | push
    v
Stored Artifact
    |
    | digest
    v
Exact Artifact Identity
    |
    | pull
    v
Linux/Cloud Server
    |
    | docker run
    v
Application
```

Now add CI/CD:

```text
Developer
    ↓
Git
    ↓
GitHub
    ↓
CI/CD
    ↓
Test
    ↓
Docker Build
    ↓
Version
    ↓
Registry Authentication
    ↓
Push
    ↓
Container Registry
    ↓
Image Digest
    ↓
Deployment System
    ↓
Pull
    ↓
Server
    ↓
Container
    ↓
Application
```

And the production principle becomes:

```text
Source Revision
      ↓
Build Once
      ↓
Test
      ↓
Version
      ↓
Push
      ↓
Record Digest
      ↓
Promote Same Artifact
      ↓
Deploy
      ↓
Verify
```

This is the shift from:

```text
"I built a Docker image."
```

to:

```text
"I can distribute and identify a production container artifact."
```
