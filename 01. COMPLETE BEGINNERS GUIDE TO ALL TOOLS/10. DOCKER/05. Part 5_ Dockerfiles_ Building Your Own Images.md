# Part 5: Dockerfiles: Building Your Own Images

## From Application Source to a Reproducible Docker Image

In Part 4, you learned what Docker images actually are.

You learned that an image contains read-only filesystem layers and metadata, and that Docker creates a container by placing a writable container layer above those image layers.

The architecture looked like this:

```text
Base Layer
    ↓
Dependency Layer
    ↓
Application Layer
    ↓
Container Writable Layer
```

Until now, however, most of the images you have used were built by someone else.

You pulled images such as:

```bash
docker pull nginx
```

and:

```bash
docker pull redis
```

Then Docker created containers from them.

Now we change roles.

You are going to become the image builder.

The workflow becomes:

```text
Application Source
        ↓
Dockerfile
        ↓
docker build
        ↓
Docker Image
        ↓
docker run
        ↓
Container
        ↓
Running Application
```

This is one of the most important transitions in learning Docker.

By the end of this part, you should be able to take a small application, create a Dockerfile for it, build an image, inspect that image, run containers from it, understand how Docker's build cache works, and troubleshoot common Dockerfile problems.

---

# 1. The Problem We Are Trying to Solve

Suppose you create a Python application.

Your project contains:

```text
veriqta-app/
├── app.py
└── requirements.txt
```

Your application requires:

```text
Python
Flask
Application source code
```

Without Docker, another engineer might need instructions such as:

```text
1. Install Python 3.12.
2. Install pip.
3. Create a directory.
4. Copy the application.
5. Install dependencies.
6. Configure the environment.
7. Start the application.
```

This introduces several possible problems.

The other engineer might install:

```text
Python 3.11
```

instead of:

```text
Python 3.12
```

They might forget a dependency.

They might start the application from the wrong directory.

They might use a different startup command.

They might configure the environment differently.

You want a repeatable build process.

Instead of manually describing the runtime environment, you can define it in a Dockerfile.

---

# 2. What Is a Dockerfile?

A Dockerfile is a text file containing instructions Docker can use to build an image.

A simple Dockerfile might look like:

```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .

RUN pip install --no-cache-dir -r requirements.txt

COPY app.py .

EXPOSE 5000

CMD ["python", "app.py"]
```

Do not worry if every line is not yet clear.

By the end of this part, you will understand every instruction.

The Dockerfile describes things such as:

```text
Which base image should I start from?

What files should be copied into the image?

What dependencies should be installed?

What directory should commands run from?

What environment variables should exist?

Which user should run the application?

What command should run when the container starts?
```

The important mental model is:

```text
Dockerfile
=
Image build instructions
```

---

# 3. Dockerfile vs Image vs Container

Do not confuse these three objects.

```text
Dockerfile
    ↓
Build instructions

Image
    ↓
Built artifact

Container
    ↓
Runtime instance
```

The relationship is:

```text
Dockerfile
    │
    │ docker build
    ↓
Image
    │
    │ docker run
    ↓
Container
```

For example:

```text
Dockerfile
    ↓
veriqta-api:1.0
    ↓
veriqta-api-container
```

The Dockerfile itself is not the image.

The image is not the container.

---

# 4. A Dockerfile Is Usually Stored With the Application

A common project structure is:

```text
veriqta-app/
├── Dockerfile
├── app.py
├── requirements.txt
└── README.md
```

The Dockerfile is commonly placed at the root of the application repository.

That is not an absolute requirement, but it is a very common convention.

---

# 5. The Basic Docker Build Workflow

Imagine:

```text
veriqta-app/
├── Dockerfile
├── app.py
└── requirements.txt
```

You enter the directory:

```bash
cd veriqta-app
```

Then build:

```bash
docker build -t veriqta-app:1.0 .
```

Docker reads the Dockerfile and build context.

It produces an image:

```text
veriqta-app:1.0
```

Then:

```bash
docker run veriqta-app:1.0
```

creates a container from that image.

Architecture:

```text
Application Files
       +
Dockerfile
       ↓
docker build
       ↓
Docker Engine / BuildKit
       ↓
Image Layers + Metadata
       ↓
veriqta-app:1.0
       ↓
docker run
       ↓
Container
```

---

# 6. Understanding `docker build`

The basic syntax is:

```bash
docker build [OPTIONS] PATH
```

A very common command is:

```bash
docker build -t veriqta-app:1.0 .
```

Break it down.

## `docker`

The Docker CLI.

## `build`

Tells Docker you want to build an image.

## `-t`

Short for:

```text
--tag
```

It assigns a name/tag to the resulting image.

## `veriqta-app:1.0`

The image repository name and tag.

```text
Repository: veriqta-app
Tag:        1.0
```

## `.`

This is extremely important.

The dot means:

> Use the current directory as the build context.

The dot is not meaningless punctuation.

It tells Docker which filesystem tree is available to the build.

---

# 7. What Is the Docker Build Context?

The build context is the set of files and directories made available to the Docker build process.

Suppose you have:

```text
veriqta-app/
├── Dockerfile
├── app.py
├── requirements.txt
├── README.md
├── tests/
└── .git/
```

You run:

```bash
docker build -t veriqta-app:1.0 .
```

The final:

```text
.
```

means:

```text
Current directory
=
build context
```

Docker's builder can use files from that context when processing instructions such as `COPY` and `ADD`.

---

# 8. Why Build Context Matters

Suppose your project directory contains:

```text
project/
├── Dockerfile
├── app.py
└── secret.txt
```

If you use:

```bash
docker build .
```

the project directory becomes the build context unless exclusions are applied.

That matters for:

* Build performance
* Security
* Cache behavior
* Image construction
* Accidental file inclusion

You should not casually make your entire home directory the build context.

Bad example:

```bash
cd ~
docker build .
```

Your home directory might contain:

```text
SSH keys
Downloads
Documents
Credentials
Cloud configuration
Git repositories
Large files
Personal data
```

Even though modern builders optimize how context is transferred and not every context file automatically becomes an image layer, unnecessarily exposing sensitive or huge directories to the build is poor practice.

Use the smallest sensible build context.

---

# 9. Build Context Is Not Automatically Copied Into the Image

This is another important distinction.

If your build context contains:

```text
Dockerfile
app.py
README.md
tests/
```

that does not automatically mean all those files become part of the final image.

Instructions such as:

```dockerfile
COPY app.py /app/app.py
```

determine which files are copied.

The context answers:

> What files may the builder access?

`COPY` answers:

> Which of those files should be placed into the image?

---

# 10. Files Outside the Build Context

Suppose:

```text
/home/ann/
├── secrets.txt
└── project/
    ├── Dockerfile
    └── app.py
```

You run:

```bash
cd /home/ann/project
docker build .
```

The context is:

```text
/home/ann/project
```

Trying to use:

```dockerfile
COPY ../secrets.txt /app/
```

is not a valid way to reach outside the build context.

This restriction helps make builds bounded and predictable.

---

# 11. Dockerfile Syntax

Dockerfiles generally contain instructions in this form:

```dockerfile
INSTRUCTION arguments
```

For example:

```dockerfile
FROM python:3.12-slim
```

```dockerfile
WORKDIR /app
```

```dockerfile
COPY app.py .
```

Dockerfile instruction names are conventionally written in uppercase.

For example:

```text
FROM
RUN
COPY
CMD
```

This makes Dockerfile instructions easy to distinguish from arguments and shell commands.

---

# 12. Dockerfile Comments

Comments begin with:

```text
#
```

Example:

```dockerfile
# Use Python as the base image
FROM python:3.12-slim
```

Comments should explain useful reasoning.

Avoid obvious comments such as:

```dockerfile
# Copy app.py
COPY app.py .
```

A more useful comment would be:

```dockerfile
# Copy dependency metadata separately so dependency installation can remain cached
COPY requirements.txt .
```

Good comments explain:

```text
Why
```

not merely:

```text
What the next line visibly says
```

---

# 13. `FROM`

`FROM` defines the base image used for a build stage.

Example:

```dockerfile
FROM python:3.12-slim
```

This means:

> Start this build stage from the filesystem and metadata provided by the specified Python image.

Architecture:

```text
python:3.12-slim
        ↓
Base Image
        ↓
Your Build Instructions
        ↓
Your Application Image
```

---

# 14. Why We Need a Base Image

Your application usually needs an environment.

A Python application may need:

```text
Linux userspace
Python runtime
Supporting libraries
```

Rather than constructing everything manually from nothing, you can start from:

```dockerfile
FROM python:3.12-slim
```

A Node application might use:

```dockerfile
FROM node:<version>
```

An Nginx-based application might use:

```dockerfile
FROM nginx:<version>
```

Choose versions that actually exist and meet your application's requirements.

---

# 15. `FROM` and Image Trust

Remember Part 4.

Do not select a base image only because its name looks correct.

Consider:

```text
Publisher
Maintenance
Version
Security updates
Architecture support
Size
Compatibility
Documentation
```

The base image becomes part of your software supply chain.

Architecture:

```text
Base Image
    ↓
Dependencies
    ↓
Application
    ↓
Final Image
```

A problem in the base can affect everything above it.

---

# 16. Avoid Blind Dependence on `latest`

You could write:

```dockerfile
FROM python:latest
```

but now your build depends on whatever content the `latest` tag resolves to when Docker resolves that reference.

A later build may therefore start from different content.

For learning, `latest` may sometimes be convenient.

For controlled builds, choose deliberate versions and consider digest pinning where exact reproducibility is required.

---

# 17. `RUN`

`RUN` executes a command while Docker is building the image.

Example:

```dockerfile
RUN pip install flask
```

This does **not** mean:

> Run this every time the container starts.

It means:

> Execute this during image construction and capture the resulting filesystem changes in the build result.

This distinction is critical.

---

# 18. Build-Time vs Runtime

Consider:

```dockerfile
RUN pip install flask
```

This occurs during:

```bash
docker build
```

But:

```dockerfile
CMD ["python", "app.py"]
```

defines a default command associated with containers created from the resulting image.

Think:

```text
RUN
→ build time

CMD / ENTRYPOINT
→ container runtime defaults/behavior
```

---

# 19. Example of `RUN`

Suppose:

```dockerfile
FROM python:3.12-slim

RUN pip install flask
```

Docker conceptually does:

```text
Start from Python image
       ↓
Execute pip install flask
       ↓
Filesystem changes occur
       ↓
Record resulting build layer/state
```

The resulting image now includes the installed package.

---

# 20. `RUN` Shell Form

You can write:

```dockerfile
RUN pip install flask
```

This is shell form.

Conceptually, Docker executes the command through the default shell for that image/platform.

On a typical Linux image, that commonly resembles:

```text
/bin/sh -c "pip install flask"
```

The exact shell behavior depends on the image/platform.

---

# 21. `RUN` Exec Form

`RUN` can also use JSON-array syntax:

```dockerfile
RUN ["executable", "argument1", "argument2"]
```

For example:

```dockerfile
RUN ["python", "--version"]
```

This avoids an intermediate shell unless the executable itself invokes one.

Shell and exec forms have different behavior involving:

* Shell expansion
* Environment-variable handling
* Pipes
* Redirection
* Signal behavior in runtime instructions

We will examine this carefully later.

---

# 22. Package Installation With `RUN`

A Debian-based image may use:

```dockerfile
RUN apt-get update && apt-get install -y curl
```

Break it down.

### `apt-get update`

Refreshes package index metadata.

### `&&`

Run the next command only if the previous command succeeds.

### `apt-get install`

Installs packages.

### `-y`

Automatically answers yes to package-manager confirmation prompts.

### `curl`

The package being installed.

In production Dockerfiles, package installation should be deliberate. Do not install debugging tools merely because you might someday use them.

---

# 23. Why `apt-get update` and `apt-get install` Are Often Combined

You may see:

```dockerfile
RUN apt-get update && \
    apt-get install -y curl
```

rather than:

```dockerfile
RUN apt-get update
RUN apt-get install -y curl
```

One reason is build-cache correctness.

If package index refresh and installation are split carelessly, Docker may reuse an old cached package-index step while later package requirements change.

Combining related package-manager operations can make the build more predictable.

A common pattern also removes package-manager cache data afterward when appropriate:

```dockerfile
RUN apt-get update && \
    apt-get install -y --no-install-recommends curl && \
    rm -rf /var/lib/apt/lists/*
```

Do not memorize this blindly.

Understand each part.

`--no-install-recommends` tells APT not to automatically install recommended packages that are not strict dependencies.

The cleanup removes downloaded package-list metadata that is no longer needed in the resulting runtime filesystem.

---

# 24. `COPY`

`COPY` copies files or directories from the build context into the image.

Syntax:

```dockerfile
COPY <source> <destination>
```

Example:

```dockerfile
COPY app.py /app/app.py
```

Meaning:

```text
Build context:
app.py

        ↓ COPY

Image filesystem:
/app/app.py
```

---

# 25. `COPY` With `WORKDIR`

If the Dockerfile contains:

```dockerfile
WORKDIR /app
```

then:

```dockerfile
COPY app.py .
```

means:

> Copy `app.py` into the current working directory inside the image.

Result:

```text
/app/app.py
```

The dot here refers to the destination working directory in the image.

Do not confuse it with the final dot in:

```bash
docker build .
```

They appear similar but mean different things.

---

# 26. Copying Multiple Files

You can write:

```dockerfile
COPY app.py requirements.txt /app/
```

Or, after:

```dockerfile
WORKDIR /app
```

you might use:

```dockerfile
COPY app.py requirements.txt ./
```

For larger projects you will often see:

```dockerfile
COPY . .
```

Meaning:

```text
Copy content from the build context
into the current image working directory
subject to Docker build rules and .dockerignore
```

This is convenient, but it must be used carefully.

---

# 27. Why `COPY . .` Can Be Dangerous

Suppose your project contains:

```text
project/
├── Dockerfile
├── app.py
├── .env
├── private-key.pem
├── tests/
├── node_modules/
└── .git/
```

Then blindly using:

```dockerfile
COPY . .
```

could copy files you never intended to place in the image unless they are excluded.

Potential consequences:

* Secrets in images
* Larger images
* Slower builds
* Cache invalidation
* Unnecessary source history
* Security exposure

This is one reason `.dockerignore` matters.

---

# 28. `ADD`

`ADD` also places content into an image, but it has additional capabilities beyond basic local copying.

For example, `ADD` can automatically extract recognized local tar archives.

It can also support remote sources in specific forms/features depending on the builder.

Because it has extra behavior, beginners sometimes use it when they only need ordinary file copying.

General rule:

> Prefer `COPY` when you simply need to copy local files.

Use `ADD` when you intentionally need its additional semantics.

---

# 29. `COPY` vs `ADD`

For ordinary application files:

```dockerfile
COPY app.py /app/
```

is usually clearer than:

```dockerfile
ADD app.py /app/
```

Why?

Because `COPY` communicates exactly what you intend:

```text
Copy this file.
```

`ADD` has additional behavior.

A good Dockerfile should make intent obvious.

---

# 30. `WORKDIR`

`WORKDIR` sets the working directory for subsequent relevant Dockerfile instructions and for the container's default working directory.

Example:

```dockerfile
WORKDIR /app
```

Then:

```dockerfile
COPY app.py .
```

copies to:

```text
/app/app.py
```

And:

```dockerfile
RUN pwd
```

would run from:

```text
/app
```

unless changed later.

---

# 31. Why `WORKDIR` Is Better Than Repeated `cd`

Avoid:

```dockerfile
RUN cd /app && pip install -r requirements.txt
```

followed by another instruction expecting to remain in `/app`.

Each `RUN` instruction is its own build step. A shell's `cd` does not establish a permanent Dockerfile working directory for later instructions.

Instead:

```dockerfile
WORKDIR /app
```

Then:

```dockerfile
RUN pip install -r requirements.txt
```

This clearly establishes the intended directory.

---

# 32. `WORKDIR` Can Create the Directory

If the directory does not already exist, Docker can create it.

For example:

```dockerfile
WORKDIR /opt/veriqta/app
```

You do not necessarily need:

```dockerfile
RUN mkdir -p /opt/veriqta/app
```

first.

---

# 33. `CMD`

`CMD` defines the default command or arguments for a container created from the image.

Example:

```dockerfile
CMD ["python", "app.py"]
```

When you run:

```bash
docker run veriqta-app:1.0
```

Docker can use that configured command.

Conceptually:

```text
Image
└── CMD ["python", "app.py"]
        ↓
docker run
        ↓
python app.py
```

---

# 34. `CMD` Does Not Run During the Build

This is a frequent beginner mistake.

`RUN`:

```dockerfile
RUN pip install -r requirements.txt
```

happens while building.

`CMD`:

```dockerfile
CMD ["python", "app.py"]
```

does not start your application during `docker build`.

It defines runtime metadata/default behavior.

---

# 35. Overriding `CMD`

Suppose the image contains:

```dockerfile
CMD ["python", "app.py"]
```

Running:

```bash
docker run veriqta-app:1.0
```

uses the default.

But:

```bash
docker run veriqta-app:1.0 python --version
```

can replace the image's default `CMD` command/arguments, depending on how `ENTRYPOINT` is configured.

This makes `CMD` useful for defaults that users may override.

---

# 36. `ENTRYPOINT`

`ENTRYPOINT` configures the executable that the container is intended to run.

Example:

```dockerfile
ENTRYPOINT ["python", "app.py"]
```

Now the image behaves more like a dedicated executable.

Conceptually:

```text
docker run image
      ↓
ENTRYPOINT
      ↓
python app.py
```

But the most useful understanding comes from comparing `ENTRYPOINT` with `CMD`.

---

# 37. `CMD` vs `ENTRYPOINT`

A useful mental model is:

```text
ENTRYPOINT
→ What executable should this container fundamentally run?

CMD
→ What default command or arguments should be supplied?
```

This is simplified, but useful.

For example:

```dockerfile
ENTRYPOINT ["python"]
CMD ["app.py"]
```

Running:

```bash
docker run myimage
```

effectively produces:

```text
python app.py
```

But:

```bash
docker run myimage --version
```

can result in:

```text
python --version
```

because runtime arguments replace the `CMD` portion while the exec-form `ENTRYPOINT` remains.

---

# 38. Another `ENTRYPOINT` + `CMD` Example

Dockerfile:

```dockerfile
ENTRYPOINT ["ping"]
CMD ["localhost"]
```

Conceptually:

```bash
docker run myimage
```

becomes:

```text
ping localhost
```

while:

```bash
docker run myimage example.com
```

becomes:

```text
ping example.com
```

The `ENTRYPOINT` remains:

```text
ping
```

The default argument:

```text
localhost
```

is replaced.

This is a useful pattern for images designed to behave like command-line tools.

---

# 39. Can `ENTRYPOINT` Be Overridden?

Yes.

Docker provides:

```bash
docker run --entrypoint <command> <image>
```

Example:

```bash
docker run --entrypoint sh myimage
```

This can be useful for debugging when the image contains a shell.

But highly minimal images may not contain `sh`.

---

# 40. Shell Form vs Exec Form

Several Dockerfile instructions can use different forms.

For `CMD`:

Shell form:

```dockerfile
CMD python app.py
```

Exec form:

```dockerfile
CMD ["python", "app.py"]
```

For `ENTRYPOINT`:

Shell form:

```dockerfile
ENTRYPOINT python app.py
```

Exec form:

```dockerfile
ENTRYPOINT ["python", "app.py"]
```

These are not merely stylistic differences.

---

# 41. Exec Form

Exec form uses JSON-array syntax:

```dockerfile
CMD ["python", "app.py"]
```

The first element is the executable.

The remaining elements are arguments.

Conceptually:

```text
Executable:
python

Argument:
app.py
```

Docker can start the executable directly rather than automatically wrapping it in a shell.

For long-running application processes, exec form is usually preferred.

---

# 42. Why Exec Form Matters for Signals

Containers need to respond correctly to operating-system signals.

For example:

```text
docker stop
      ↓
SIGTERM
      ↓
Main container process
      ↓
Graceful shutdown
```

If your application process is directly the main process, signal behavior is generally clearer.

With careless shell-form runtime commands, an intermediate shell may become PID 1 and signal forwarding can behave differently.

We will explore PID 1 and signals deeply in Part 14.

For now remember:

> Prefer exec form for `CMD` and `ENTRYPOINT` when running application processes unless you specifically need shell behavior.

---

# 43. When Shell Form Is Useful

Shell form is useful when you intentionally need shell features such as:

```text
Variable expansion
Pipes
Redirection
Command chaining
Globbing
```

For example:

```dockerfile
RUN echo "hello" > /tmp/message.txt
```

uses shell redirection.

Exec form does not automatically interpret:

```text
>
|
&&
*
```

as shell syntax.

If you need a shell explicitly, you can invoke one intentionally.

---

# 44. Environment Variable Expansion and Exec Form

Suppose:

```dockerfile
ENV NAME=VERIQTA
```

Then shell-form behavior can expand:

```text
$NAME
```

through a shell.

But exec form does not automatically perform shell variable expansion simply because `$NAME` appears in a JSON string.

This is another reason to understand whether a shell is involved.

Do not memorize:

```text
Exec good
Shell bad
```

Instead understand:

```text
Do I need shell semantics?
Do I need direct process execution?
```

---

# 45. `ENV`

`ENV` sets environment variables in the image.

Example:

```dockerfile
ENV APP_ENV=production
```

Containers created from the image can inherit this default.

Inside the container:

```bash
echo "$APP_ENV"
```

might produce:

```text
production
```

depending on the shell and runtime environment.

---

# 46. Why Applications Use Environment Variables

Applications often need configuration such as:

```text
Environment name
Logging level
API endpoint
Feature configuration
Port
Database host
```

Instead of hardcoding:

```python
environment = "production"
```

the application may read:

```text
APP_ENV
```

This allows the same application image to run with different runtime configuration.

Architecture:

```text
Same Image
   │
   ├── APP_ENV=development
   │
   ├── APP_ENV=staging
   │
   └── APP_ENV=production
```

This supports artifact reuse across environments.

---

# 47. Overriding `ENV` at Runtime

Suppose the Dockerfile contains:

```dockerfile
ENV APP_ENV=development
```

You can override it:

```bash
docker run -e APP_ENV=production myimage
```

Here:

```text
-e
```

sets an environment variable for that container.

Now:

```text
APP_ENV=production
```

overrides the image default for that runtime instance.

---

# 48. Do Not Put Secrets in `ENV` Instructions

Bad example:

```dockerfile
ENV DATABASE_PASSWORD=SuperSecretPassword
```

Do not bake secrets into Dockerfiles or images.

Why?

Image metadata and build history can expose information, and the image may be distributed to:

```text
Developer machines
Registries
CI systems
Production hosts
Other environments
```

Secrets require dedicated runtime secret-management approaches.

We will discuss this more deeply in Part 13.

---

# 49. `ARG`

`ARG` defines a build-time variable.

Example:

```dockerfile
ARG APP_VERSION=1.0
```

You can use it during the build.

Example:

```dockerfile
ARG APP_VERSION=1.0

RUN echo "Building version ${APP_VERSION}"
```

Then:

```bash
docker build \
  --build-arg APP_VERSION=2.0 \
  -t myapp:2.0 .
```

---

# 50. `ARG` vs `ENV`

This distinction is extremely important.

```text
ARG
→ primarily build-time input

ENV
→ image/container environment configuration
```

Example:

```dockerfile
ARG BUILD_VERSION
ENV APP_VERSION=$BUILD_VERSION
```

Now the build argument is used to establish an environment variable in the resulting image.

But be careful:

> Neither `ARG` nor `ENV` should be treated as a secure secret-storage mechanism.

Build arguments can appear in build metadata/history or otherwise leak through build processes.

Use proper BuildKit secret mechanisms for sensitive build-time credentials.

---

# 51. Build Arguments

Suppose:

```dockerfile
ARG PYTHON_VERSION=3.12
FROM python:${PYTHON_VERSION}-slim
```

Build normally:

```bash
docker build -t myapp:default .
```

The default is:

```text
PYTHON_VERSION=3.12
```

Or:

```bash
docker build \
  --build-arg PYTHON_VERSION=<supported-version> \
  -t myapp:custom .
```

The exact version must correspond to a valid base image tag.

# 52. Why Build Arguments Are Useful

# 53. `EXPOSE`

`EXPOSE` documents the network port the application is expected to listen on.

Example:

```dockerfile
EXPOSE 5000
```

This communicates:

```text
This image's application expects to listen on port 5000.
```

But:

```dockerfile
EXPOSE 5000
```

does **not** automatically publish port 5000 to your host.

This is a major beginner misunderstanding.

---

# 54. `EXPOSE` vs `-p`

Dockerfile:

```dockerfile
EXPOSE 5000
```

documents image/container port intent.

Runtime:

```bash
docker run -p 8080:5000 myimage
```

publishes:

```text
Host port 8080
        ↓
Container port 5000
```

Architecture:

```text
Browser
   ↓
localhost:8080
   ↓
Docker Port Publishing
   ↓
Container:5000
   ↓
Application
```

`EXPOSE` and `-p` are related but not equivalent.

# 55. `USER`

`USER` sets which user subsequent relevant instructions or the container process should use.

Example:

```dockerfile
USER appuser
```

This is important because containers frequently default to root unless the image config changes it.

Running everything as root increases potential impact if the application is compromised.

Security principle:

```text
Least privilege
```

means:

> Give the process only the permissions it actually requires.

---

# 56. Creating a Non-Root User

The exact command depends on the Linux distribution in your base image.

For a Debian-based image, a simple example could be:

```dockerfile
RUN useradd --create-home appuser
```

Then:

```dockerfile
USER appuser
```

But you must also consider filesystem ownership.

If the application needs access to:

```text
/app
```

the user must have the necessary permissions.

---

# 57. Permissions Matter With `USER`

Imagine:

```text
/app
owner: root
```

Then:

```dockerfile
USER appuser
```

The application tries to write:

```text
/app/output.log
```

It may receive:

```text
Permission denied
```

The correct solution is not automatically:

```text
Run everything as root.
```

Instead investigate:

```text
Who owns the directory?
Who is the process running as?
Does the process need write access?
Where should writable application data actually live?
```

This is production reasoning.

---

Example:

```dockerfile

```

This can help avoid unnecessary later ownership changes.

We will explore image optimization and ownership patterns more deeply in Part 11.

# 63. `HEALTHCHECK`

`HEALTHCHECK` tells Docker how to test whether a running container's application is functioning according to a defined check.

Example:

```dockerfile
HEALTHCHECK --interval=30s --timeout=3s \
  CMD curl -f http://localhost:5000/health || exit 1
```

This is more meaningful than merely asking:

```text
Is the process still running?
```

A process can exist while the application is broken.

---

# 64. Running vs Healthy

Imagine:

```text
Python process
→ running
```

but:

```text
HTTP server
→ cannot answer requests
```

Docker may consider the container process running.

A health check can provide additional application-health information.

Conceptually:

```text
Container Process
      ↓
Running
      ↓
Health Check
      ↓
Application responds?
      ↓
Healthy / Unhealthy
```

---

# 65. Health Check Exit Codes

At a high level, Docker health checks use exit status to determine the result.

Normally:

```text
0
→ healthy result

1
→ unhealthy result
```

Docker tracks repeated health-check results and updates container health state according to the configured behavior.

---

# 66. Health Check Options

You may encounter:

```text
--interval
--timeout
--retries
--start-period
```

Example:

```dockerfile
HEALTHCHECK \
  --interval=30s \
  --timeout=3s \
  --start-period=10s \
  --retries=3 \
  CMD curl -f http://localhost:5000/health || exit 1
```

### `--interval`

How often the health check runs.

### `--timeout`

How long Docker waits for a health-check attempt.

### `--start-period`

Provides initialization time before failures begin counting normally toward unhealthy status.

### `--retries`

How many consecutive failures are required before Docker marks the container unhealthy.

Choose values based on actual application behavior rather than copying arbitrary numbers.

---

# 67. Health Check Dependencies

If your health check uses:

```text
curl
```

then the image must contain `curl`.

This sounds obvious, but it causes real failures.

A minimal image may not have:

```text
curl
wget
bash
```

Your health check must use tools actually available inside the image.

# 73. Why `0.0.0.0` Matters

means:

This is a common containerized web-application mistake.

`.dockerignore` tells Docker which files/directories should be excluded from the build context sent/used by the builder.

```text
.gitignore
```

Example:

```text

.git
.env
```

This can improve:

* Build speed
* Context size
* Security
* Cache stability
* Image hygiene

# 85. Why `.dockerignore` Matters for Security

Suppose:

```text
.env
```

```text

API_KEY=...
```


But it is not a replacement for proper secret management.

Secrets should not live carelessly in your build directory in the first place.

# 98. Build Cache

Docker does not necessarily execute every build operation from scratch every time.

Modern Docker builders use build cache.

Suppose:

```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .

RUN pip install --no-cache-dir -r requirements.txt

COPY app.py .
```

You build once.

Then build again without changing anything.

Docker may report steps as cached.

Conceptually:

```text
Instruction
    ↓
Has valid reusable build result?
    ↓
Yes
    ↓
Reuse cache
```

This can dramatically speed up builds.

---

# 99. Why Build Cache Matters

Imagine dependency installation takes:

```text
4 minutes
```

but copying changed application code takes:

```text
1 second
```

If application code changes but dependencies do not, you would prefer:

```text
Reuse dependency layer/result
        ↓
Copy new source
        ↓
Continue build
```

rather than:

```text
Reinstall every dependency
every time source changes
```

This is why Dockerfile ordering matters.

---

# 100. Poor Layer Ordering

Consider:

```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY . .

RUN pip install --no-cache-dir -r requirements.txt

CMD ["python", "app.py"]
```

Suppose you change only:

```text
README.md
```

or:

```text
app.py
```

The:

```dockerfile
COPY . .
```

step's inputs changed.

That can invalidate the cached result for that step and downstream steps.

Then:

```dockerfile
RUN pip install ...
```

may need to run again.

This wastes time.

---

# 101. Better Layer Ordering

Instead:

```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .

RUN pip install --no-cache-dir -r requirements.txt

COPY app.py .

CMD ["python", "app.py"]
```

Now:

```text
requirements.txt unchanged
       ↓
Dependency installation can remain cached

app.py changed
       ↓
Only later source-copy result needs rebuilding
```

This is a major Dockerfile optimization principle.

---

# 102. General Layer Ordering Principle

Place:

```text
Stable instructions
```

earlier.

Place:

```text
Frequently changing instructions
```

later.

Conceptually:

```text
Base Image
    ↓
System Dependencies
    ↓
Application Dependencies
    ↓
Application Source
    ↓
Frequently Changing Content
```

This is not an absolute rule.

Correctness and security come first.

But it is a strong starting point.

---

# 103. Cache Invalidation

Cache invalidation means Docker determines that a previous cached build result can no longer be reused for a step.

Common reasons include:

```text
Dockerfile instruction changed
Input file changed
Build argument changed
Parent build result changed
Base image resolution changed when refreshed
Relevant build metadata changed
Cache deliberately disabled
```

Once an earlier step must be rebuilt, later steps often need to be reconsidered/rebuilt because their parent state has changed.

# 107. Refreshing Base Images

A subtle point:

Even if your Dockerfile says:

```dockerfile
FROM python:3.12-slim
```

the tag may point to newer content in the registry over time.

A normal cached build may continue using locally/cached resolved content depending on build state.

When you intentionally want to check for a newer base image, modern Docker supports:

```bash
docker build --pull -t veriqta-docker-app:1.0 .
```

This asks the builder to attempt to pull a newer version of referenced base images.

For exact reproducibility, digest pinning provides stronger identity.

For security patching, teams also need a deliberate base-image refresh/rebuild strategy.

These goals must be balanced intentionally.

Beginners sometimes think:


```text

Which build step depends on it?
Should that step's cache remain valid?
```

This is much better than blindly deleting all Docker state.

# 126. Multiple `CMD` Instructions

Do not write:

```dockerfile
CMD ["echo", "first"]
CMD ["echo", "second"]
```

and expect both to execute sequentially.

Only the final effective `CMD` is used as the image's `CMD`.

If you need multiple startup actions, design the startup process deliberately.

Do not stack multiple `CMD` lines expecting them to behave like multiple `RUN` instructions.

---

# 127. Multiple `RUN` Instructions

This is different.

You can write:

```dockerfile
RUN echo "one"
RUN echo "two"
```

Both execute during the build.

They are separate build instructions.

So:

```text
RUN
RUN
RUN
```

can all execute.

But:

```text
CMD
CMD
CMD
```

does not mean run three startup commands.

# 128. Common Mistake: Using `RUN` to Start the Application

Wrong mental model:

```dockerfile

```

If the application starts a long-running server, the build may hang because Docker is trying to execute the server during image construction.

You generally want:

```dockerfile
CMD ["python", "app.py"]
```

for runtime.

Remember:

```text
RUN
→ construct image

CMD / ENTRYPOINT
→ configure runtime
```

# 134. Common Mistake: Secrets Copied Into the Image

# 135. Why Deleting a Secret Later Is Not Enough

Bad example:

```dockerfile
COPY secret.txt /app/
RUN use-secret-somehow
RUN rm /app/secret.txt
```

The final merged filesystem may no longer show the file.

But earlier image layers may still contain the secret content.

Layer model:

```text
Layer 1
COPY secret.txt

Layer 2
Use secret

Layer 3
Delete visible file
```

The secret may remain recoverable from earlier layer content.

Never intentionally copy secrets into ordinary image layers.

# What You Should Now Understand

Before moving to Part 6, you should be able to explain all of these without simply repeating definitions.

A Dockerfile is a text-based build definition used to create Docker images.

The Dockerfile is not the image.

The image is not the container.

The build context determines which local files are available to the build.

The final dot in:

```bash
docker build .
```

means the current directory is the build context.

`.dockerignore` excludes unnecessary or sensitive files from the build context.

`FROM` selects the base image for a build stage.

`RUN` executes commands while building the image.

`COPY` copies files from the build context.

`ADD` has additional behavior and should not replace `COPY` without a reason.

`WORKDIR` establishes the working directory.

`CMD` defines default runtime command/arguments.

`ENTRYPOINT` defines the primary executable behavior.

`ENTRYPOINT` and `CMD` can work together.

Shell form invokes shell semantics.

Exec form directly specifies executable and arguments and is generally preferred for long-running application processes.

`ENV` defines environment defaults that persist into image/container configuration.

`ARG` defines build-time inputs.

`ARG` and `ENV` are not secure secret-management mechanisms.

`EXPOSE` documents the intended container port.

`EXPOSE` does not publish a host port.

`USER` helps run applications with least privilege.

Filesystem ownership must match runtime permissions.

`LABEL` adds metadata.

`VOLUME` declares a mount point intended for externally managed/persistent storage.

`HEALTHCHECK` defines how Docker should assess application health.

A running process does not necessarily mean a healthy application.

`docker build` creates images.

`-t` assigns image tags.

BuildKit can reuse cached build results.

Cache invalidation happens when relevant build inputs change.

Dockerfile instruction ordering affects cache efficiency.

Stable dependency steps are often placed before frequently changing source-code copies.

`docker image inspect` reveals resulting image configuration.

`docker image history` helps investigate how build steps contributed to the image.

Successful build does not guarantee successful runtime.

Container applications often need to listen on `0.0.0.0`.

Secrets should never be casually copied into image layers.

Deleting a secret in a later layer does not guarantee its removal from earlier image content.

Production Dockerfiles should be version-controlled, reviewed, tested, scanned, and treated as part of the software delivery system.
