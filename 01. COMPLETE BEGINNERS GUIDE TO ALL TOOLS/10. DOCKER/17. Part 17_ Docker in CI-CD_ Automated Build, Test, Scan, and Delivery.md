# Part 17: Docker in CI/CD: Automated Build, Test, Scan, and Delivery

## Connect Docker to Modern DevOps Delivery

Until now, you have mostly performed Docker operations yourself:

```text
write code
↓
docker build
↓
docker run
↓
docker logs
↓
docker inspect
↓
test
↓
push image
```

That is useful while learning.

It is not enough for a professional software delivery process.

Imagine a team with 20 developers.

Every developer manually:

```text
builds differently
tags differently
tests differently
scans differently
pushes differently
deploys differently
```

Soon you have:

```text
unreproducible builds
untested images
incorrect tags
missing security scans
unknown production versions
manual mistakes
deployment confusion
```

Modern DevOps replaces much of that manual process with a pipeline.

Our target architecture is:

```text
Git Push
   ↓
CI
   ↓
Test
   ↓
Build Image
   ↓
Scan
   ↓
Registry
   ↓
Deploy
```

A more complete version looks like:

```text
Developer
   ↓
Git Repository
   ↓
Push / Pull Request
   ↓
CI Runner
   ↓
Checkout Source
   ↓
Automated Tests
   ↓
Docker Build
   ↓
Image Tagging
   ↓
Security Scan
   ↓
Registry Authentication
   ↓
Push Immutable Image
   ↓
Deployment Handoff
   ↓
Staging
   ↓
Verification
   ↓
Production
```

The central principle of this part is:

```text
Build once.
Test it.
Scan it.
Identify it immutably.
Promote the same artifact.
Deploy it.
```

Not:

```text
build development image
↓
rebuild staging image
↓
rebuild production image
```

We want the artifact that passed our controls to be the artifact that eventually reaches production.

# 2. Before CI/CD

Imagine Anne develops an API.

She runs:

```bash
docker build \
  -t veriqta-api:latest \
  .
```

Then:

```bash
docker run \
  veriqta-api:latest
```

Everything works.

She tells another engineer:

```text
The image works.
```

But what exactly does that mean?

Questions immediately appear:

```text
Which commit was built?

Which Dockerfile was used?

Were tests run?

Which tests?

Did they pass?

Was the image scanned?

Which dependencies were installed?

Who built it?

When was it built?

Was it pushed to the registry?

Is production running that exact image?

Can we reproduce it?
```

Manual builds make those questions harder to answer consistently.

CI/CD creates a repeatable delivery process.

---

# 3. What CI Means

CI means:

```text
Continuous Integration
```

Developers frequently integrate code into shared version control.

Automated systems validate those changes.

A simplified workflow:

```text
Developer
   ↓
Git Push
   ↓
CI Starts
   ↓
Tests
   ↓
Build
   ↓
Validation
```

The objective is to detect problems early.

Examples:

```text
test failure
build failure
dependency failure
Dockerfile failure
security-policy failure
```

before an invalid change progresses toward production.

---

# 4. What CD Means

CD can refer to related practices:

```text
Continuous Delivery
```

and:

```text
Continuous Deployment
```

They are not identical.

Continuous Delivery generally means software remains in a deployable state and deployment may include an approval or other controlled action.

Continuous Deployment goes further and automatically releases qualifying changes to production.

A company may use:

```text
CI
+
automated delivery to staging
+
manual production approval
```

and still have a mature delivery process.

Automation does not mean removing every control.

---

# 5. Why CI/CD Uses Containers

Containers are useful in CI/CD because they help provide:

```text
consistent environments
isolated dependencies
repeatable builds
portable execution
clean runner environments
versioned build tools
reproducible testing
deployable artifacts
```

Suppose one developer uses:

```text
Python 3.x
```

another uses another version, while the CI server has something different again.

Tests may behave differently.

A container can define the environment explicitly.

Example:

```dockerfile
FROM python:<TESTED_VERSION>
```

Now the build environment becomes part of the project's version-controlled definition.

For a public repository, replace placeholders with versions you have tested and intentionally support.

---

# 6. The "Works on the CI Server" Problem

Containers do not magically guarantee reproducibility.

You can still create inconsistent pipelines through:

```text
mutable image tags
unpinned dependencies
different build arguments
hidden runner state
different architectures
different secrets
external services
non-deterministic package downloads
different caches
```

Therefore Docker helps reproducibility.

It does not eliminate engineering responsibility.

# 7. CI Runner Environments

A CI runner is the machine or execution environment that performs pipeline work.

Conceptually:

```text
Git Platform
    ↓
Job Assigned
    ↓
CI Runner
    ↓
Commands Execute
```

A runner might be:

```text
virtual machine
cloud-hosted runner
self-hosted machine
container
Kubernetes pod
Jenkins agent
```

The exact architecture depends on the CI system.

---

# 8. Runner Lifecycle

A hosted runner often behaves conceptually like:

```text
Job Requested
↓
Runner Prepared
↓
Repository Checked Out
↓
Dependencies/Tools Prepared
↓
Tests Executed
↓
Image Built
↓
Artifacts Published
↓
Runner Discarded
```

This is valuable because persistent state from an engineer's laptop is less likely to affect the build.

---

# 9. Ephemeral vs Persistent Runners

## Ephemeral Runner

Created or assigned for a job and then discarded.

Advantages:

```text
cleaner state
better isolation
less configuration drift
```

## Persistent Runner

Reused across jobs.

Advantages may include:

```text
local caching
special hardware
private network access
custom tooling
```

But persistent runners require stronger operational discipline because state can survive between jobs.

---

# 10. CI Runner Security Boundary

Never think:

```text
It's only CI.
```

A runner may have access to:

```text
source code
registry credentials
cloud credentials
deployment keys
signing systems
internal networks
production deployment permissions
```

Compromising a privileged CI runner can become a supply-chain compromise.

Part 13's least-privilege principles apply directly to CI/CD.

# 14. Application

Create:

```text
app/main.py
```

Example:

```python
from flask import Flask, jsonify

app = Flask(__name__)


@app.get("/")
def index():
    return jsonify(
        service="veriqta-api",
        status="running"
    )


@app.get("/health")
def health():
    return jsonify(status="healthy"), 200

    app.run(
        host="0.0.0.0",
        port=5000
    )
```

For a learning lab this is enough.

For production, use an appropriate production WSGI server rather than treating Flask's built-in development server as the final production runtime.

```text

```

```python

    client = app.test_client()

    assert response.get_json()["status"] == "healthy"
```

Now CI has something meaningful to validate.

# 19. Dockerfile

Create:

```text
Dockerfile
```

Example:

```dockerfile
FROM python:<TESTED_VERSION>-slim AS test

WORKDIR /app

COPY requirements.txt requirements-dev.txt ./

RUN pip install \
    --no-cache-dir \
    -r requirements-dev.txt

COPY app ./app
COPY tests ./tests

RUN pytest -q


FROM python:<TESTED_VERSION>-slim AS runtime

WORKDIR /app

RUN groupadd \
        --system \
        appgroup \
    && useradd \
        --system \
        --gid appgroup \
        --home-dir /app \
        appuser

COPY requirements.txt ./

RUN pip install \
    --no-cache-dir \
    -r requirements.txt

COPY --chown=appuser:appgroup app ./app

USER appuser

EXPOSE 5000

CMD [
  "gunicorn",
  "--bind",
  "0.0.0.0:5000",
  "app.main:app"
]
```

This introduces an important CI pattern:

```text
test stage
↓
runtime stage
```

Tests are part of the image build process.

# 24. Automated Image Builds

Instead of an engineer manually running:

```bash
docker build .
```

the CI system runs it.

Example:

```bash
docker build \
  -t IMAGE_NAME:TAG \
  .
```

This provides consistency because:

```text
same pipeline definition
same build procedure
same automated gates
```

are applied repeatedly.

---

# 25. Build Failure Handling

Suppose Docker build fails.

The pipeline should normally stop.

Correct flow:

```text
Build
  ↓
FAILED
  ↓
Pipeline Failed
  ↓
Do Not Publish
```

Not:

```text
Build failed
↓
ignore
↓
deploy anyway
```

A failed required stage should prevent later protected stages from running.

---

# 26. Fail Fast

Suppose your pipeline contains:

```text
Test
Build
Scan
Push
Deploy
```

If tests fail:

```text
Test FAILED
↓
STOP
```

There is usually no reason to deploy the candidate.

The pipeline becomes an automated decision system:

```text
pass
→ continue

fail
→ stop
```

---

# 27. Running Tests Inside Containers

One pattern:

```bash
docker build \
  --target test \
  -t veriqta-api:test \
  .
```

Because the test stage contains:

```dockerfile
RUN pytest -q
```

a failing test makes the build fail.

---

# 28. Alternative Test Pattern

You could build a test image:

```bash
docker build \
  --target test \
  -t veriqta-api:test \
  .
```

and run tests as the container command.

For example, depending on Dockerfile design:

```bash
docker run \
  --rm \
  veriqta-api:test \
  pytest -q
```

Both patterns can be valid.

Choose deliberately.

---

# 29. Why Test Inside Containers?

It helps align:

```text
test runtime
```

with:

```text
declared application/build environment.
```

This reduces differences such as:

```text
developer has Python A
CI has Python B
production image has Python C
```

---

# 30. Tests Should Not Depend on Hidden Runner State

Bad CI:

```text
runner already happens to have package X installed
```

Better:

```text
required tools are declared
```

through:

```text
container image
Dockerfile
pipeline setup
package lockfile
tool configuration
```

The pipeline should be reproducible from its definitions.

# 31. Image Tagging Strategy

A CI image needs an identity.

Weak:

```text
veriqta-api:latest
```

Better:

```text
veriqta-api:main
```

Better:

```text
veriqta-api:a1b2c3d
```

Release:

```text
veriqta-api:1.4.0
```

Tags serve different purposes.

---

# 32. `latest` Is Not a Version

A tag such as:

```text
latest
```

is just a tag.

It does not guarantee:

```text
newest
stable
production-approved
secure
```

Its meaning depends on your publishing process.

Never use the word `latest` as evidence of what code is running.

---

# 33. Commit SHA Tags

Every Git commit has an identifier.

Example:

```text
4f3e2d19...
```

A CI pipeline can tag an image using that commit:

```text
registry.example.com/veriqta/api:4f3e2d19
```

This creates traceability:

```text
Image Tag
   ↓
Git Commit
```

---

# 34. Why Commit SHA Tags Are Powerful

Imagine production fails.

You inspect the running image:

```text
veriqta-api:4f3e2d19
```

Now you can identify:

```text
exact source commit
pipeline run
build logs
test results
security scan
deployment event
```

That is far stronger than:

```text
production is running latest.
```

---

# 35. Full SHA vs Short SHA

A full Git SHA provides the strongest direct identifier.

Short SHAs are easier for humans to read but need enough characters to remain unambiguous in the repository.

A pipeline may use:

```text
full SHA in metadata/digest records
```

and:

```text
short SHA as a convenient tag.
```

---

# 36. Branch Tags

You might publish:

```text
veriqta-api:main
```

or:

```text
veriqta-api:develop
```

These are useful convenience references.

But they are mutable.

Today:

```text
main → commit A
```

Tomorrow:

```text
main → commit B
```

Therefore branch tags should not be your only deployment identity.

---

# 37. Pull Request Images

Some organizations build images for pull requests.

Example concept:

```text
veriqta-api:pr-142
```

This can support:

```text
integration testing
preview environments
security scanning
QA
```

But decide carefully whether untrusted pull-request builds are allowed to:

```text
access secrets
push images
access internal networks
deploy
```

Usually those permissions should be tightly restricted.

---

# 38. Release Tags

Suppose Git release tag is:

```text
v1.4.2
```

The image might receive:

```text
veriqta-api:1.4.2
```

You might additionally publish convenience tags such as:

```text
1.4
1
```

depending on your versioning policy.

But understand:

```text
1.4.2
```

may remain fixed while:

```text
1.4
```

may move when `1.4.3` appears.

# 39. Semantic Versioning

A common release scheme is:

```text
MAJOR.MINOR.PATCH
```

Example:

```text
2.7.3
```

Conceptually:

```text
MAJOR
breaking/incompatible changes

MINOR
backward-compatible features

PATCH
backward-compatible fixes
```

Whether your project follows Semantic Versioning exactly is a project governance decision.

Do not label a scheme SemVer unless you actually follow its rules.

# 45. Weak Promotion Model

Avoid:

```text
Commit
↓
Build development image
↓
test
↓
rebuild staging image
↓
test
↓
rebuild production image
```

Why?

Because each rebuild may produce something different.

You may end up deploying an artifact that was not exactly the one you tested.

---

# 46. Better Promotion Model

```text
Commit
↓
Build Image Once
↓
Test
↓
Scan
↓
Publish
↓
Deploy Same Digest to Development
↓
Promote Same Digest to Staging
↓
Promote Same Digest to Production
```

Configuration may differ by environment.

Artifact content should not need to.

# 47. Development vs Staging vs Production

## Development

Used for active development and integration.

May use:

```text
development configuration
test services
debug tooling
frequent deployments
```

## Staging

Should resemble production sufficiently to validate release behavior.

May use:

```text
production-like topology
production-like configuration structure
release candidate artifact
integration tests
```

## Production

Serves real workloads/users.

Requires stronger:

```text
access control

observability

```

# 48. Same Image, Different Configuration

Prefer:

```text
same image
+
environment-specific runtime configuration
```

Example:

```text
IMAGE:
veriqta-api@sha256:XYZ
```

Development:

```text
DATABASE_HOST=dev-db
```

Staging:

```text
DATABASE_HOST=staging-db
```

Production:

```text
DATABASE_HOST=prod-db
```

The image does not need to be rebuilt merely because the database endpoint changes.

---

# 49. Do Not Bake Production Secrets Into Images

Bad:

```dockerfile
ENV DATABASE_PASSWORD=SuperSecretPassword
```

Bad:

```dockerfile
COPY production.env /app/.env
```

Bad:

```dockerfile
RUN echo "$TOKEN" > /app/token.txt
```

Secrets copied into image layers can persist in image history/content even if removed in a later layer.

---

# 50. Secrets in Pipelines

CI systems provide secret-storage mechanisms.

Examples of secret categories:

```text
registry token
cloud credential
deployment credential
signing credential
API token
```

The pipeline should retrieve secrets only when required.

---

# 51. Pipeline Secret Principles

Use:

```text
least privilege
short-lived credentials where possible
environment-scoped access
secret masking
rotation
auditability
```

Avoid:

```text
hard-coded passwords
committed tokens
secrets in Dockerfiles
secrets in image tags
secrets printed to logs
secrets passed unnecessarily between jobs
```

---

# 52. Build Arguments Are Not Secret Storage

This is not a safe secret strategy:

```bash
docker build \
  --build-arg API_TOKEN="$API_TOKEN" \
  .
```

Part 11 introduced BuildKit secret mounts.

If a build genuinely requires a secret, use an appropriate secret mechanism rather than treating ordinary build arguments as confidential storage.

---

# 53. BuildKit Secrets in CI

Dockerfile syntax can use:

```dockerfile
RUN --mount=type=secret,id=TOKEN \
    some-command
```

The pipeline supplies the secret at build time.

Conceptually:

```text
CI Secret Store
     ↓
BuildKit Secret Mount
     ↓
One Build Instruction
     ↓
Not intentionally copied into image
```

Still inspect your build carefully.

A command can accidentally copy or print a secret.

BuildKit cannot protect you from an application command deliberately leaking it.

---

# 54. Registry Authentication

Before CI pushes an image, it usually authenticates to the target registry.

Conceptually:

```text
CI Runner
   ↓
Credential
   ↓
Registry Authentication
   ↓
Authorized Push
```

The credential should have only the permissions required.

---

# 55. Registry Credential Scope

A CI build that only pushes to:

```text
veriqta/api
```

does not necessarily need administrative access to every repository in the registry.

Apply:

```text
least privilege
```

to registry credentials.

---

# 56. Do Not Expose Registry Passwords

Avoid commands that expose passwords unnecessarily.

For command-line login, a pattern such as:

```bash
printf '%s' "$REGISTRY_TOKEN" \
  | docker login \
      --username "$REGISTRY_USERNAME" \
      --password-stdin \
      REGISTRY
```

avoids putting the secret directly into the command argument.

CI-native registry authentication actions/plugins may provide even better integration.

---

# 57. Push to Registry

Once authenticated:

```bash
docker push \
  REGISTRY/REPOSITORY:TAG
```

Example concept:

```text
registry.example.com/veriqta/api:sha-abc123
```

After push:

```text
Registry
├── image
├── tag
└── digest
```

The registry becomes the distribution point.

---

# 58. Pipeline Before Registry Push

A good pipeline should not push every broken candidate as though it were approved.

A basic flow:

```text
Checkout
↓
Test
↓
Build
↓
Scan
↓
PASS?
├── No → Stop
└── Yes
      ↓
     Push
```

Your organization's exact policy may differ.

```text
   ↓

   ↓

   ↓
```

# 60. What Image Scanners Look For

A scanner may inspect:

```text
operating-system packages
language dependencies
known CVEs
package versions
base image
SBOM/package inventory
```

A vulnerability result is not automatically equivalent to:

```text
the application is exploitable.
```

# 101. Complete GitHub Actions Learning Workflow

A more complete conceptual workflow:

```yaml
name: Docker Delivery

on:
  pull_request:
  push:
    branches:
      - main
    tags:
      - "v*"

permissions:
  contents: read

jobs:

  docker:

    runs-on: ubuntu-latest

    steps:

      - name: Checkout
        uses: actions/checkout@<PINNED_VERSION_OR_SHA>

      - name: Set up Buildx
        uses: docker/setup-buildx-action@<PINNED_VERSION_OR_SHA>

      - name: Build test stage
        uses: docker/build-push-action@<PINNED_VERSION_OR_SHA>
        with:
          context: .
          target: test
          push: false
          cache-from: type=gha
          cache-to: type=gha,mode=max

      - name: Login to registry
        if: github.event_name != 'pull_request'
        uses: docker/login-action@<PINNED_VERSION_OR_SHA>
        with:
          username: ${{ vars.REGISTRY_USERNAME }}
          password: ${{ secrets.REGISTRY_TOKEN }}

      - name: Generate Docker metadata
        id: meta
        uses: docker/metadata-action@<PINNED_VERSION_OR_SHA>
        with:
          images: YOUR_REGISTRY/YOUR_REPOSITORY
          tags: |
            type=sha
            type=ref,event=branch
            type=semver,pattern={{version}}

      - name: Build and push runtime image
        uses: docker/build-push-action@<PINNED_VERSION_OR_SHA>
        with:
          context: .
          push: ${{ github.event_name != 'pull_request' }}
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

This is a learning template.

Before placing it in a production repository:

```text
choose registry
pin actions
configure permissions
configure credentials
add scanning
define promotion policy
define deployment
test workflow
```

# 191. Final Mental Model

Do not think of Docker CI/CD as:

```text
GitHub runs docker build.
```

Think of the entire system:

```text
SOURCE
   ↓
Developer creates change
   ↓
Git records exact revision
   ↓
TRIGGER
   ↓
CI receives event
   ↓
RUNNER
   ↓
Controlled execution environment
   ↓
TEST
   ↓
Does the application behave correctly?
   ↓
BUILD
   ↓
Create container artifact
   ↓
IDENTIFY
   ↓
Commit SHA
Version
Metadata
   ↓
SCAN
   ↓
Does artifact satisfy required security policy?
   ↓
AUTHENTICATE
   ↓
Can CI securely access registry?
   ↓
PUBLISH
   ↓
Push artifact
   ↓
REGISTRY
   ↓
Store and distribute image
   ↓
DIGEST
   ↓
Identify exact immutable artifact
   ↓
PROMOTION
   ↓
Move same artifact through environments
   ↓
DEPLOYMENT HANDOFF
   ↓
Deployment system receives exact reference
   ↓
RUN
   ↓
Target environment starts image
   ↓
VERIFY
   ↓
Health
Logs
Application
Correct digest
   ↓
SUCCESS
```

If verification fails:

```text
Failed Release
↓
Identify Previous Known-Good Digest
↓
Rollback / Recovery
↓
Verify
```

The most important principles from Part 17 are:

```text
AUTOMATE THE REPEATABLE WORK.

TEST BEFORE RELEASE.

BUILD ONCE.

SCAN THE ARTIFACT.

DO NOT PUT SECRETS IN THE IMAGE.

TAG FOR TRACEABILITY.

USE DIGESTS FOR IMMUTABLE IDENTITY.

PROMOTE THE SAME ARTIFACT.

VERIFY AFTER DEPLOYMENT.

KEEP A KNOWN-GOOD ROLLBACK ARTIFACT.
```

The final pipeline is:

```text
Git Push
   ↓
CI
   ↓
Test
   ↓
Build Image
   ↓
Scan
   ↓
Registry
   ↓
Deploy
```

But a production engineer sees more than seven boxes.

They see:

```text
source identity
trust boundaries
runner security
test evidence
build reproducibility
cache behavior
artifact identity
security evidence
registry permissions
immutable promotion
deployment control
runtime verification
rollback capability
```

That is Docker in modern CI/CD.
