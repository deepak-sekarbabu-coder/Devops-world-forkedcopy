# Part 19: Production Docker Engineering and Operations

## From Running Containers to Operating Production Systems

A container running successfully on your laptop is not a production system.

A Dockerfile that builds successfully is not a production deployment.

A server with `docker run` commands is not automatically production-ready.

Production engineering begins when you must answer questions such as:

* What happens when the application crashes?
* What happens when the Docker host reboots?
* What happens when memory is exhausted?
* What happens when the disk fills?
* What happens when an image contains a vulnerability?
* What happens when a deployment fails?
* How do we roll back?
* Where are secrets stored?
* Where is persistent data stored?
* How is that data backed up?
* Have we tested restoration?
* How do users reach the application securely?
* How do we patch the host?
* How do we know the application is healthy?
* How do we know when it is unhealthy?
* What happens when one Docker host disappears?
* How much traffic can the system actually handle?
* Who responds when something breaks?
* When has the architecture become too large for one Docker host or Docker Compose?

These are production questions.

This part bridges:

```text
Docker Tutorial
↓
Working Container
↓
Production Engineering
↓
Reliable Operations
```

Our architecture is:

```text
Users
  ↓
DNS
  ↓
TLS / Load Balancer
  ↓
Docker Host(s)
  ↓
Application Containers
  ↓
Data Services
  ↓
Observability
```

But production operation surrounds the entire architecture:

```text
                    Users

             ┌────────┴────────┐

             ▼                 ▼
        Containers        Containers

             └────────┬────────┘
                      ▼

                      │

Around everything:

Security
```

# 2. Development and Production Are Different Environments

During development, the priority is usually:

```text
speed
feedback
debugging
convenience
```

In production, priorities change:

```text
reliability
security
predictability
recoverability
observability
performance
availability
controlled change
```

This changes how containers should be configured.

---

# 3. Development Container Example

A development environment might use:

```yaml
services:
  api:
    build: .
    volumes:
      - ./src:/app/src
    environment:
      APP_ENV: development
      DEBUG: "true"
    ports:
      - "5000:5000"
```

This is convenient.

The source code is mounted directly into the container.

Debugging may be enabled.

The developer can change code and immediately observe the result.

That does not mean this is appropriate for production.

---

# 4. Why Development Bind Mounts Can Be Wrong for Production

Development:

```text
Host Source Code
↓
Bind Mount
↓
Container
```

Changing the host files changes what the container sees.

That is useful locally.

Production should generally prefer:

```text
Git Commit
↓
CI Build
↓
Immutable Image
↓
Registry
↓
Deployment
```

Application code should normally be part of the tested image.

Otherwise the deployed artifact can be changed independently of the image that passed CI.

---

# 5. Production Container Principle

Production should move toward:

```text
Build once
↓
Test once
↓
Scan once
↓
Publish artifact
↓
Promote same artifact
↓
Deploy exact artifact
```

Not:

```text
Build something different
for every environment.
```

---

# 6. Development vs Production

| Area         | Development                | Production                    |
| ------------ | -------------------------- | ----------------------------- |
| Code         | Often bind-mounted         | Built into image              |
| Debugging    | Often enabled              | Restricted                    |
| Logging      | Verbose                    | Controlled/structured         |
| Secrets      | Local convenience possible | Managed securely              |
| Image tag    | Flexible                   | Versioned/immutable           |
| Resources    | Often unrestricted         | Planned and limited           |
| Ports        | Convenient exposure        | Minimal exposure              |
| TLS          | Sometimes omitted          | Expected for external traffic |
| Restart      | Manual acceptable          | Defined behavior              |
| Health       | Basic                      | Explicitly monitored          |
| Backups      | Often unnecessary          | Required for critical state   |
| Monitoring   | Minimal                    | Centralized                   |
| Rollback     | Rebuild/retry              | Planned                       |
| Security     | Developer-oriented         | Hardened                      |
| Availability | One instance often fine    | Based on service requirements |

# 7. Production Image Standards

A production image should be intentionally engineered.

A useful baseline includes:

```text
Trusted base image
Pinned dependencies
Minimal runtime contents
Multi-stage build where useful
Non-root user
No embedded secrets
Correct ownership
Only runtime dependencies
Known application version
Useful metadata
Health behavior understood
Vulnerability scanning
SBOM where required
Reproducible build process
```

---

# 8. Example Production Dockerfile

Suppose we have a Python application.

```dockerfile
FROM python:3.13-slim AS builder

WORKDIR /build

COPY requirements.txt .

RUN pip install \
    --no-cache-dir \
    --prefix=/install \
    -r requirements.txt


FROM python:3.13-slim AS runtime

WORKDIR /app

COPY --from=builder /install /usr/local

COPY --chown=10001:10001 app.py .

USER 10001:10001

EXPOSE 5000

CMD ["python", "app.py"]
```

This demonstrates several production concepts:

```text
multi-stage build
separate build/runtime stages
minimal runtime content
non-root execution
explicit working directory
known application port
exec-form startup command
```

In a real application, pin and test dependency versions and use an appropriate production application server for your framework and workload.

# 9. What Should Not Be in the Production Image?

Avoid including unnecessary:

```text
source-control metadata
local credentials
SSH private keys
cloud credentials
database passwords
development tools
editor files
test artifacts
large caches
temporary files
debug packages
unneeded compilers
```

Every unnecessary component can increase:

```text
image size
attack surface
build time
pull time
maintenance burden
```

```text

.env
.env.*
*.pem
*.key
__pycache__/
.pytest_cache/
```

# 11. Production Images Should Be Traceable

An engineer should be able to answer:

```text
Which source commit created this image?

Which pipeline built it?

When was it built?

Which dependencies are inside it?

Which registry contains it?

Which digest is deployed?

Which environments use it?
```

If nobody can answer these questions during an incident, deployment traceability is weak.

---

# 12. Versioning

Avoid making production depend entirely on:

```text
latest
```

A better tagging strategy might include:

```text
1.8.4
sha-a1b2c3d
release-2026-09-20
```

The exact scheme depends on your release process.

But a tag is still a reference that can potentially be moved unless your registry prevents it.

For strongest artifact identity, use the digest.

---

# 13. Image Digest

Example:

```text
registry.example.com/veriqta-api@sha256:abc123...
```

A digest identifies image content.

Production traceability becomes:

```text
Git Commit
↓
CI Pipeline
↓
Image
↓
Registry
↓
Digest
↓
Production Deployment
```

# 14. Immutable Deployment

Immutable deployment means you replace the deployed artifact rather than modifying it in place.

Weak pattern:

```text
SSH into production
↓
edit application file
↓
restart container
```

Better:

```text
Change source
↓
Commit
↓
CI
↓
Test
↓
Build new image
↓
Scan
↓
Push
↓
Deploy new image
```

The old artifact remains identifiable.

The new artifact remains identifiable.

---

# 15. Why Immutability Matters

Suppose an engineer enters a running container:

```bash
docker exec -it api sh
```

and manually edits:

```text
/app/config.py
```

Production may work temporarily.

But now:

```text
running container
≠
registry image
```

and:

```text
running container
≠
Git
```

The next restart removes the manual change.

This is configuration drift.

---

# 16. Production Rule

Use:

```text
docker exec
```

for:

```text
diagnostics
inspection
controlled operational tasks
```

not as the normal application deployment system.

---

# 17. Configuration Management

Applications need configuration.

Examples:

```text
APP_ENV
LOG_LEVEL
DATABASE_HOST
DATABASE_PORT
DATABASE_NAME
CACHE_HOST
API_ENDPOINT
FEATURE_FLAG
```

The image should usually remain:

```text
environment-independent
```

while configuration changes by environment.

# 18. Image vs Configuration

Prefer:

```text
Same Image
├── Development Configuration
├── Staging Configuration
└── Production Configuration
```

rather than:

```text
development image
staging image
production image
```

built independently from the same source.

The exact deployment system may differ, but the principle is:

```text
promote the tested artifact.
```

# 19. Runtime Environment Variables

Example:

```bash
docker run \
  -d \
  --name api \
  -e APP_ENV=production \
  -e LOG_LEVEL=info \

```

This separates:

```text
application artifact
```

from:

```text
environment-specific configuration.
```

# 20. Environment Variables Are Not a Secret Vault

Environment variables are convenient.

But sensitive values require additional care.

Secrets include:

```text
database passwords
API keys
private keys
access tokens
cloud credentials
signing keys
```

Do not confuse:

```text
configuration
```

with:

```text
secret management.
```

---

# 21. Secrets Management

Production secret management should answer:

```text
Where is the secret stored?

Who may retrieve it?

How is access authenticated?

How is access audited?

How is it rotated?

What happens when it leaks?

How does the application receive it?

Does it appear in logs?

Does it appear in image history?
```

---

# 22. Never Bake Secrets into Images

Never:

```dockerfile
ENV DATABASE_PASSWORD=SuperSecretPassword
```

Never:

```dockerfile
COPY production-key.pem /app/key.pem
```

Never:

```dockerfile
RUN echo "token123" > /app/token
```

An image can move through:

```text
developer machines
CI systems
registries
production servers
caches
backups
```

A secret inside an image can travel with it.

---

# 23. Secrets Architecture

A stronger pattern:

```text
Application Container
↓
Authorized Runtime Identity
↓
Secret Management System
↓
Secret
```

Depending on environment, examples include:

```text
AWS Secrets Manager
AWS Systems Manager Parameter Store
HashiCorp Vault
orchestration-platform secret mechanisms
```

The product choice matters less than understanding the security model.

---

# 24. Secret Rotation

A production secret should not be assumed permanent.

You need to know:

```text
Can it be rotated?

Does the application need restart?

Can old credentials be revoked?

How quickly can a compromised credential be replaced?
```

Secret rotation is an operational process, not just a storage decision.

# 25. Resource Limits

A container without resource planning can compete aggressively for host resources.

Consider:

```text
CPU
memory
PIDs
file descriptors
disk
network
```

Resource planning protects both:

```text
the application
```

and:

```text
neighboring workloads.
```

---

# 26. CPU Limit

Example:

```bash
docker run \
  -d \
  --cpus="1.5" \
  IMAGE
```

This limits the container's CPU allocation using Docker's resource-control mechanisms.

It does not mean:

```text
pin this container permanently to CPU core 1.5.
```

It represents CPU quota.

---

# 27. Memory Limit

Example:

```bash
docker run \
  -d \
  --memory="512m" \
  IMAGE
```

Now the container has a configured memory ceiling.

But do not choose:

```text
512 MB
```

because a tutorial used it.

Measure the application.

---

# 28. Resource Planning Workflow

Use:

```text
Observe
↓
Load Test
↓
Measure
↓
Establish Baseline
↓
Set Requests/Limits or Host Allocation
↓
Test Under Pressure
↓
Monitor
↓
Adjust
```

Production resource values should be evidence-based.

---

# 29. Memory Reservation

Docker can also configure a soft memory reservation.

Conceptually:

```text
reservation
=
soft constraint under host contention

limit
=
harder upper boundary
```

Exact behavior depends on host kernel and configuration.

Do not confuse reservations with guarantees.

---

# 30. OOM Conditions

If memory becomes unavailable or a container exceeds its effective memory constraints, processes may be killed.

Evidence may include:

```text
OOMKilled
```

Check:

```bash
docker inspect CONTAINER
```

and:

```bash
docker stats --no-stream
```

Also inspect the host.

An OOM event is evidence.

Do not immediately increase memory without understanding why memory usage grew.

---

# 31. Restart Behavior

Production containers need defined restart behavior.

Docker supports restart policies such as:

```text
no
on-failure
always
unless-stopped
```

Example:

```bash
docker run \
  -d \
  --restart unless-stopped \
  IMAGE
```

---

# 32. Restart Policy Is Not High Availability

Suppose:

```text
container crashes
↓
Docker restarts it
```

Useful.

But suppose:

```text
entire Docker host dies
```

The restart policy on that dead host cannot move the workload elsewhere.

Therefore:

```text
restart policy
≠
high availability
```

---

# 33. Restart Loops

A restart policy can hide repeated application failure.

Example:

```text
Start
↓
Crash
↓
Restart
↓
Crash
↓
Restart
↓
Crash
```

Always monitor:

```text
restart count
exit code
logs
health
```

A restarting container is not necessarily a recovered container.

---

# 34. Inspect Restart Count

Run:

```bash
docker inspect \
  --format '{{.RestartCount}}' \
  CONTAINER
```

If unexpectedly high:

```text
investigate.
```

---

# 35. Health Checks

A running process does not guarantee a working service.

You need to distinguish:

```text
process exists
```

from:

```text
service can perform its intended function.
```

---

# 36. Docker Health Check

Example:

```dockerfile
HEALTHCHECK \
  --interval=30s \
  --timeout=3s \
  --start-period=10s \
  --retries=3 \
  CMD curl --fail http://127.0.0.1:5000/health || exit 1
```

Use only if the image actually contains the health-check tool.

A minimal image may not contain `curl`.

---

# 37. Health States

Docker health can report:

```text
starting
healthy
unhealthy
```

Inspect:

```bash
docker inspect CONTAINER
```

or:

```bash
docker ps
```

when a health check is configured.

---

# 38. Health Check Design

Do not create a health endpoint that performs:

```text
huge database query
slow third-party API request
expensive computation
```

every few seconds.

Health checks themselves consume resources.

Design them intentionally.

---

# 39. Liveness vs Readiness Thinking

Even when using plain Docker, understand the distinction conceptually.

Liveness:

```text
Is the process/service alive enough to continue?
```

Readiness:

```text
Should this instance receive traffic now?
```

A service can be:

```text
alive
```

but:

```text
not ready.
```

This becomes especially important in orchestration systems.

---

# 40. Graceful Shutdown

Production applications should not assume they will run forever.

Containers may stop because of:

```text
deployment
host maintenance
scaling
operator action
failure recovery
```

Your application should handle termination correctly.

---

# 41. Docker Stop

When you run:

```bash
docker stop api
```

Docker initiates a graceful stop process.

The application should respond to the termination signal, finish appropriate in-flight work, close resources, and exit within the allowed period.

If it does not stop, Docker can eventually force termination.

---

# 42. SIGTERM

A common graceful-termination signal is:

```text
SIGTERM
```

Your application should normally treat it as:

```text
prepare to terminate.
```

Possible shutdown work:

```text
stop accepting new work
finish safe in-flight requests
close database connections
flush necessary buffers
release resources
exit
```

---

# 43. SIGKILL

SIGKILL cannot be handled by the application.

It means:

```text
terminate immediately.
```

Therefore:

```text
SIGTERM
→ graceful opportunity

SIGKILL
→ forced termination
```

Design the application to use the graceful opportunity.

---

# 44. PID 1 Matters

Inside the container, the main process has special responsibility as PID 1.

Poor process behavior can cause:

```text
signal-handling problems
zombie processes
shutdown problems
```

Use exec-form startup commands where appropriate.

Prefer:

```dockerfile
CMD ["python", "app.py"]
```

over unnecessary shell wrapping:

```dockerfile
CMD python app.py
```

when direct execution is suitable.

---

# 45. Init Process

For applications that may create child processes, Docker can provide a small init process.

Example:

```bash
docker run \
  --init \
  IMAGE
```

This can help with:

```text
signal forwarding
child-process reaping
```

Do not add an init process blindly.

Understand the application's process model first.

---

# 46. Test Graceful Shutdown

Run the application.

Start a request.

Then:

```bash
docker stop api
```

Observe:

```text
application logs
request behavior
exit timing
exit code
```

Ask:

```text
Was the request lost?

Did the app close cleanly?

Did it receive the expected signal?

Did it require forced termination?
```

Production behavior should be tested, not assumed.

# 47. Logging

Production applications should normally write operational logs to:

```text
stdout
stderr
```

rather than depending only on arbitrary files inside the container.

This works naturally with Docker logging.

---

# 48. Good Application Logs

Useful logs include context such as:

```text
timestamp
severity
service
request ID
correlation ID
operation
result
duration
error type
```

Avoid logging:

```text
passwords
access tokens
private keys
full sensitive payloads
unnecessary personal information
```

---

# 49. Structured Logging

Instead of:

```text
something broke
```

prefer structured information such as:

```json
{
  "level": "error",
  "service": "payments-api",
  "request_id": "req-123",
  "operation": "create_payment",
  "error": "database_timeout"
}
```

Structured logs are easier for machines and engineers to query.

---

# 50. Docker Logs

Basic inspection:

```bash
docker logs api
```

Recent output:

```bash
docker logs \
  --tail 100 \
  api
```

Follow:

```bash
docker logs \
  --follow \
  api
```

Add timestamps where useful:

```bash
docker logs \
  --timestamps \
  api
```

---

# 51. Logging Driver

Docker supports logging drivers.

Check current daemon default:

```bash
docker info \
  --format '{{.LoggingDriver}}'
```

Do not assume every environment uses the same logging driver.

---

# 52. Log Rotation

Unbounded logs can consume the host disk.

A production system needs:

```text
rotation
retention
centralization
monitoring
```

If using `json-file`, rotation can be configured.

Example daemon configuration:

```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}
```

The exact limits should be chosen based on operational requirements.

---

# 53. Local Logging Driver

Docker's `local` logging driver is another option designed for efficient local log storage and includes rotation behavior.

Do not select a logging driver simply because it sounds better.

Consider:

```text
operational tooling
compatibility
retention
central collection
performance
failure behavior
```

---

# 54. Centralized Logging

```text
Application

stdout/stderr
↓
Docker Logging
```

# 59. Alerting

Do not alert on everything.

Good alerts should represent:

```text
real user impact
imminent risk
required operator action
```

Examples might include:

```text
persistent high error rate
all healthy instances lost
disk nearly exhausted
backup failure
certificate expiry approaching
persistent memory pressure
critical dependency unavailable
```

---

# 60. Persistent Storage

Containers are replaceable.

Critical data often is not.

Separate:

```text
application lifecycle
```

from:

```text
data lifecycle.
```

---

# 61. Container Writable Layer

Do not rely on the writable container layer for important persistent data.

If the container is removed:

```text
container writable state
```

can disappear with it.

Use appropriate persistent storage.

---

# 62. Docker Volumes

Example:

```bash
docker volume create postgres-data
```

Run:

```bash
docker run \
  -d \
  --name postgres \
  -v postgres-data:/var/lib/postgresql/data \
  IMAGE
```

The exact internal path depends on the image/version.

Always verify official image documentation.

---

# 63. Volume Is Not Backup

This is one of the most important production rules.

```text
Persistent volume
≠
backup
```

A volume can survive container deletion.

But it can still be affected by:

```text
host loss
disk corruption
operator error
application corruption
malicious deletion
filesystem failure
```

---

# 64. Backup

A backup should create a recoverable copy of important state.

Depending on workload, backup may involve:

```text
database-native backup
filesystem snapshot
volume snapshot
object storage
managed-service backup
```

Do not assume copying raw database files while the database is actively writing creates a valid backup.

Use workload-appropriate procedures.

---

# 65. Restore Is More Important Than Backup Creation

A backup that cannot be restored is operationally useless.

You need:

```text
backup schedule
retention policy
restore procedure
restore testing
recovery ownership
recovery objectives
```

---

# 66. RPO

Recovery Point Objective asks:

```text
How much data can we afford to lose?
```

Example:

```text
RPO = 15 minutes
```

means the recovery strategy should be designed around no more than approximately that amount of data loss under the defined scenario.

---

# 67. RTO

Recovery Time Objective asks:

```text
How long can recovery take?
```

Example:

```text
RTO = 30 minutes
```

means the recovery process is designed to restore the required service within that target.

RPO and RTO are business decisions translated into engineering requirements.

---

# 68. Restore Drill

A production team should periodically test:

```text
Backup
↓
Restore into safe environment
↓
Validate data
↓
Start application
↓
Verify application
↓
Record restore duration
```

Do not wait for disaster to discover that the backup is incomplete.

---

# 69. Network Isolation

Do not place every container on one unrestricted network without considering communication requirements.

Suppose:

```text
Frontend
Backend
Database
```

A better design may use:

```text
frontend-network
backend-network
```

with:

```text
Frontend
↕
Backend
```

and:

```text
Backend
↕
Database
```

while preventing direct frontend-to-database communication.

---

# 70. Example Network Segmentation

Create:

```bash
docker network create frontend-network
```

and:

```bash
docker network create backend-network
```

Connect:

```text
Frontend
→ frontend-network

Backend
→ frontend-network
→ backend-network

Database
→ backend-network
```

```text

```

# 81. Zero-Downtime Is a Strong Claim

```text

```

```text

```

```text

```

# 82. Why Simple Replacement Causes Downtime

Suppose production has one container:

```text

```

You run:

```text

remove api-v1
start api-v2
```

There is a period where:

```text

```

That creates downtime.

# 83. Minimal-Downtime Principle

Instead:

```text

↓

↓
Send traffic to new version
↓
Stop old version
```

This is the foundation of safer deployments.

# 106. Docker Daemon Configuration

# 107. Validate Configuration Changes

```text

```

# 108. Duplicate Daemon Options

Docker can receive configuration from:

```text

```

and daemon startup flags.

# 110. Live Restore

Docker supports:

```text
live-restore
```

for standalone Linux container scenarios.

It can allow containers to continue running while the Docker daemon becomes temporarily unavailable under supported conditions.

Example:

```json
{
  "live-restore": true
}
```

This can reduce disruption during some daemon maintenance events.

It is not a replacement for:

```text
multiple hosts
orchestration
application redundancy
```

---

# 111. Live Restore Limitation

Think:

```text
Docker daemon unavailable
↓
existing container processes may continue
```

But:

```text
host destroyed
```

cannot be solved by live restore.

Again:

```text
daemon resilience
≠
host resilience.
```

# 112. Docker Socket Security

The Docker Unix socket is commonly:

```text
/var/run/docker.sock
```

Access to it is extremely powerful.

Do not casually mount:

```text
/var/run/docker.sock
```

inside containers.

A workload controlling the Docker daemon may gain broad control over the host.

# 113. Docker Group Security

Membership in the Docker group can effectively provide highly privileged host access.

Therefore:

```text

```

is an administrative security decision.

Do not add every application user to the Docker group for convenience.

# 114. Rootless Docker

This can reduce certain risks associated with a rootful daemon.

But:

```text

≠

```

You still need:

```text

```

# 121. Headroom

Suppose:

```text

```



```text

```

the surviving host cannot absorb the workload.

Redundancy without spare capacity may not provide useful resilience.
