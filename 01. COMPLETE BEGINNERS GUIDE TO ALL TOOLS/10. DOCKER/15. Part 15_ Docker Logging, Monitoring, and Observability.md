# Part 15: Docker Logging, Monitoring, and Observability

## Learn How Engineers Understand Container Behavior Without Guessing

A container fails at 2:13 a.m.

Users report:

```text
"The application is slow."
```

You SSH into the server.

The container is running.

Now what?

You could restart it.

You could guess that memory is the problem.

You could blame the network.

You could increase CPU.

You could rebuild the image.

You could restart Docker.

Or you could collect evidence.

Production engineering should follow the second approach.

The purpose of logging, monitoring, and observability is to help you answer:

```text
What happened?
When did it happen?
Where did it happen?
What changed?
What was the system doing?
What evidence supports the diagnosis?
```

This part moves us from:

```text
Something is wrong.
```

to:

```text
At 14:03:21,
API latency increased,
container CPU reached its configured limit,
CPU throttling increased,
health checks began failing,
HTTP 500 errors appeared in application logs,
and the problem began immediately after deployment version 2.4.1.
```

That is evidence.

The architecture for this part is:

```text
Container
   ↓
Logs / Metrics / Events
   ↓
Collector
   ↓
Monitoring Platform
   ↓
Engineer
```

A more complete version is:

```text
                    ┌───────────────┐
                    │   Container   │
                    └───────┬───────┘
                            │
          ┌─────────────────┼─────────────────┐
          │                 │                 │
          ↓                 ↓                 ↓
        Logs             Metrics           Events
          │                 │                 │
          └─────────────────┼─────────────────┘
                            ↓
                       Collectors
                            ↓
                  Storage / Monitoring
                            ↓
                Query / Dashboard / Alert
                            ↓
                         Engineer
                            ↓
                     Investigation
                            ↓
                       Root Cause
```

The central lesson is simple:

```text
Do not guess.

Observe.
Measure.
Correlate.
Verify.
```

# 2. What Is Observability?

Observability is your ability to understand the internal behavior of a system from the information the system exposes.

Imagine a containerized application.

You cannot physically look inside the CPU and watch instructions execute.

Instead, the system exposes signals.

For example:

```text
Application logs
Container metrics
Health status
Docker events
HTTP metrics
Runtime state
```

From those signals, you investigate what happened.

Conceptually:

```text
Internal System Behavior
          ↓
   Observable Signals
          ↓
 Logs + Metrics + Events
          ↓
       Engineer
          ↓
Understanding
```

---

# 3. Monitoring vs Observability

The terms are related but are not identical.

Monitoring often asks predefined questions:

```text
Is CPU above 80%?

Is memory above the threshold?

Is the service healthy?

How many requests failed?
```

Observability supports investigation when you may not know the question beforehand.

Example:

```text
Why did checkout latency suddenly increase only for one application version?
```

A monitoring system might tell you:

```text
Latency is high.
```

Observability helps you investigate:

```text
when it began
which containers were affected
which version was running
what the CPU was doing
what memory was doing
what errors appeared
whether dependencies failed
whether a deployment occurred
```


# 11. stdout and stderr

Linux processes normally begin with three standard streams:

```text
stdin
stdout
stderr
```

Their conventional file descriptors are:

```text
0 = stdin
1 = stdout
2 = stderr
```

For container logging, the two most important are:

```text
stdout
stderr
```

---

# 12. stdout

stdout means:

```text
standard output
```

Applications can write normal output there.

Example:

```python
print("Application started")
```

By default, Python's `print()` writes to stdout.

---

# 13. stderr

stderr means:

```text
standard error
```

Applications can use it for errors and diagnostics.

Example:

```python
import sys

print(
    "Database connection failed",
    file=sys.stderr
)
```

This writes to stderr.

---

# 14. Why stdout and stderr Matter in Containers

Traditional applications may write logs directly to files such as:

```text
/var/log/myapp/application.log
```

That is possible inside containers.

But a common container pattern is:

```text
Application
    ↓
stdout / stderr
    ↓
Container runtime
    ↓
Logging driver
    ↓
Log destination
```

This separates:

```text
application produces logs
```

from:

```text
platform decides where logs go.
```



```bash

  veriqta-log-test
```

# 17. Application Logging

Docker cannot invent useful application logs for you.

Your application must emit meaningful information.

Bad logging:

```text
Error
```

Better:

```text
Database connection failed
```

Much better:

```text
2026-09-20T12:14:31Z ERROR database_connection_failed host=postgres port=5432 attempt=3
```

The goal is useful context without exposing secrets.

---

# 18. What Useful Application Logs Should Contain

Depending on the system, useful fields can include:

```text

service
event
request ID

HTTP method
path
status code
duration

deployment version

```

Never blindly include every available value.

# 19. Do Not Log Secrets

Do not write values such as:

```text
passwords
API keys
access tokens
session tokens
private keys
database passwords
authorization headers
full sensitive request bodies
```

into logs.

Logs often leave the application host.

They may be:

```text
collected
forwarded
stored
searched
backed up
retained
viewed by operators
```

Treat logs as sensitive operational data.

# 20. Log Levels

Applications commonly use levels such as:

```text
DEBUG
INFO
WARN
ERROR
CRITICAL
```

Exact names depend on the logging framework.

A useful mental model:

```text
DEBUG
Detailed diagnostic information

INFO
Normal significant application activity

WARN
Something unusual happened but operation may continue

ERROR
An operation failed

CRITICAL
A severe failure threatens major application operation
```

---

# 21. Do Not Use ERROR for Everything

If every normal event is logged as:

```text
ERROR
```

then:

```text
ERROR
```

stops being useful.

Likewise, if production logs contain massive DEBUG output unnecessarily, you can create:

```text
noise
storage cost
performance overhead
security exposure
disk pressure
```

Logging is engineering.

Logs need timestamps.

Bad:

```text

```

Better:

```text

```

Without timestamps, correlation becomes extremely difficult.

# 24. Structured Logging

Human-readable logs might look like:


```text

```

# 25. Correlation IDs

Imagine one user request travels through:

```text
Frontend
   ↓
API
   ↓
Payment Service
   ↓
Database
```

Each service creates logs.

How do you know which logs belong to the same request?

One solution is a:

```text
correlation ID
```

Example:

```text
request_id=9f2a71
```

Then:

```text
Frontend:
request_id=9f2a71 request received

API:
request_id=9f2a71 processing checkout

Payment:
request_id=9f2a71 payment authorized

Database:
request_id=9f2a71 order stored
```

Now the request can be followed across services.

# 27. Follow Logs

Use:

```bash
docker logs \
  --follow \
  CONTAINER
```

Short form:

```bash
docker logs \
  -f \
  CONTAINER
```

This continues streaming new log output.

```text
Ctrl+C
```

That stops your local log-following command.

It does not stop the container.

# 33. Docker Logging Drivers

Docker supports different:

```text
logging drivers
```

A logging driver controls how container stdout/stderr messages are handled.

Conceptually:

```text
Application
    ↓
stdout/stderr
    ↓
Docker
    ↓
Logging Driver
    ↓
Destination
```

Different drivers can send logs to different destinations.

---

# 34. Check the Docker Daemon's Default Logging Driver

Run:

```bash
docker info \
  --format '{{.LoggingDriver}}'
```

A common result is:

```text
json-file
```

Docker Engine currently uses `json-file` as its default logging driver unless configured otherwise.

---

# 35. Inspect a Container's Logging Driver

Run:

```bash
docker inspect \
  --format '{{.HostConfig.LogConfig.Type}}' \
  CONTAINER
```

Example result:

```text
json-file
```

Do not assume every container uses the daemon default.

A container can have its own configured logging driver.

---

# 36. `json-file`

Docker's default:

```text
json-file
```

driver stores container log messages in JSON-formatted files managed by Docker.

Conceptually:

```text
stdout/stderr
     ↓
Docker
     ↓
json-file driver
     ↓
Docker-managed JSON log
```

---

# 37. Important Warning About Docker Log Files

Do not treat Docker's internal log files as application files that your own scripts should directly manipulate.

Avoid patterns such as:

```text
open Docker's internal log file
edit it
truncate it manually
move it manually
```

Docker manages those files.

Use supported logging configuration and tools.

---

# 38. The `json-file` Disk Problem

A container can generate enormous quantities of logs.

Imagine:

```text
10 KB/sec
100 KB/sec
1 MB/sec
```

running continuously.

Without rotation, log files can continue growing.

Eventually:

```text
Container logs
      ↓
Docker host filesystem
      ↓
Disk usage grows
      ↓
Disk becomes full
      ↓
Applications fail
```

This is a real production failure mode.

---

# 39. Log Rotation

Log rotation prevents one active log file from growing forever.

A simplified model:

```text
container.log
     ↓ reaches configured size
container.log.1
     ↓
new container.log begins
```

With retention limits, older rotated files are eventually removed.

---

# 40. `json-file` Rotation

Docker supports options including:

```text
max-size
max-file
```

Example daemon configuration:

```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}
```

Meaning:

```text
max-size
Rotate when the current log reaches the configured size.

max-file
Keep only the configured number of rotated log files.
```

These are example lab values, not universal production recommendations.

---

# 41. Docker Daemon Configuration

On a standard Linux Docker Engine installation, daemon configuration is commonly managed through:

```text
/etc/docker/daemon.json
```

For example:

```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}
```

Docker Desktop manages daemon configuration through its Docker Engine settings interface.

Platform details can differ.

Always use the configuration mechanism documented for your installation.

---

# 42. Restart Required

After changing daemon logging configuration, restart Docker according to your operating system and installation method.

For a systemd-managed Linux Docker Engine, that commonly means:

```bash
sudo systemctl restart docker
```

Important:

Changing the daemon's default logging driver does not retroactively change the logging configuration of existing containers.

Newly created containers use the new default.

# 44. Per-Container Logging Driver

You can select a logging driver when creating a container.

Example:

```bash

  --log-driver local \

```

---

# 45. The `local` Logging Driver

Docker also provides:

```text
local
```

The local driver stores logs in a Docker-managed custom format optimized for lower overhead.

Importantly, the local driver performs log rotation by default.

Docker currently recommends considering the `local` driver for general non-Kubernetes Docker Engine use because it helps prevent uncontrolled disk consumption and uses a more efficient storage format.

---

# 46. Why `local` Can Be Useful

Compare conceptually:

```text
json-file
    ↓
JSON formatted storage
    ↓
No rotation by default
```

with:

```text
local
    ↓
Docker-optimized storage
    ↓
Rotation enabled by default
```

That does not mean:

```text
local is automatically correct for every production system.
```

Your architecture may forward logs to an external platform instead.

---

# 48. Logging Driver `none`

```text

```


# 58. Blocking vs Non-Blocking Log Delivery

Docker supports logging delivery modes.

Conceptually:

```text
blocking
```

means the application can experience backpressure if the logging path cannot keep up.

Docker also supports:

```text
non-blocking
```

delivery with an intermediate buffer.

---

# 59. Why Logging Backpressure Matters

Imagine:

```text
Application
    ↓
writes stdout
    ↓
Logging destination slow
    ↓
logging path blocks
    ↓
application output blocks
```

Logging infrastructure can affect application behavior.

This is why logging is part of production architecture, not merely debugging convenience.

---

# 60. Non-Blocking Trade-Off

Non-blocking mode can prevent application log writes from blocking on the logging driver.

But buffers are finite.

If the buffer fills:

```text
new log messages may be dropped
```

So the trade-off becomes:

```text
blocking
→ protect log delivery
→ application may experience backpressure

non-blocking
→ protect application from log backpressure
→ logs may be dropped under pressure
```

There is no free solution.

---

# 61. Disk Exhaustion From Logs

Consider:

```text

```

```text

```

The host cannot magically store it.

Possible consequences:

```text

application errors
database problems
Docker failures
image pulls fail

host instability
```

# 64. Do Not Delete Random Docker Files

If disk usage is high, do not begin with:

```bash

```

That can damage Docker state and workloads.

Investigate first.

Use supported cleanup and retention mechanisms.

# 65. Logging Retention Is a Production Requirement

Decide:

```text
How much logging do we generate?

How long should logs be retained?
```

# 86. What Is Prometheus?

Prometheus is an open-source monitoring and alerting toolkit designed around time-series metrics.

The basic model is:

```text
Target
   ↓
/metrics
   ↑
Prometheus scrapes
   ↓
Time-Series Database
   ↓
PromQL Queries
   ↓
Dashboards / Alerts
```

Prometheus stores metrics together with timestamps and labels.

---

# 87. What Is a Time Series?

Suppose CPU is recorded every few seconds:

```text
14:00:00  12%
14:00:15  15%
14:00:30  18%
14:00:45  42%
14:01:00  87%
```

That sequence is:

```text
a measurement changing over time
```

which is the fundamental idea behind time-series monitoring.

---

# 88. Prometheus Labels

Prometheus metrics can contain labels.

Conceptually:

```text
http_requests_total{
  service="api",
  method="GET",
  status="500"
}
```

Labels allow the same metric to be divided across dimensions.

You might ask:

```text
error requests for API
```

or:

```text
GET requests
```

or:

```text
requests returning 500
```

---

# 89. Prometheus Pull Model

Prometheus commonly collects metrics by:

```text
scraping
```

HTTP metrics endpoints.

Conceptually:

```text
Application / Exporter
        ↓
      /metrics
        ↑
    Prometheus
```

Prometheus periodically requests the endpoint and stores the returned samples.

---

# 90. Example Metrics Endpoint

A metrics endpoint may return text resembling:

```text
http_requests_total{method="GET",status="200"} 1842

http_requests_total{method="GET",status="500"} 14

http_request_duration_seconds_sum 81.4
```

Prometheus understands its exposition format and stores the time-series samples.

---

# 91. Prometheus Is Not a Log Store

Do not confuse:

```text
Prometheus
```

with:

```text
central log storage.
```

Prometheus is primarily for metrics.

Logs and metrics solve different problems.

Example:

```text

500 errors increased from 1% to 15%.

Log:

```

Together they are more powerful.

# 145. Cardinality Awareness

Prometheus labels are powerful.

But creating unbounded label values can cause serious problems.

Bad conceptual label:

```text
user_id="<every individual user>"
```

or:

```text
request_id="<unique request>"
```

on a metric.

That can create huge numbers of unique time series.

Request IDs belong naturally in logs/traces, not usually as unbounded Prometheus metric labels.

```text

event-oriented
useful for debugging
contain contextual messages
```

Do not force one to replace the other.

# 150. Alerting

Monitoring becomes more useful when systems can notify engineers about important conditions.

Example:

```text
memory approaching dangerous level
```

or:

```text
error rate exceeds expected threshold
```

or:

```text
service becomes unavailable
```

But alerting requires careful design.

---

# 151. Bad Alert

Bad:

```text
CPU > 50%
```

Why 50%?

For how long?

Which service?

Does it affect users?

Is 50% abnormal?

Without context, the alert may create noise.

---

# 152. Better Alert Thinking

A better design asks:

```text
What condition indicates a real operational problem?

How long must it persist?

What service is affected?

What is the user impact?

What should the engineer inspect?

What runbook applies?
```

Alerts should lead toward action.

---

# 153. Alert Fatigue

If engineers receive:

```text
100 meaningless alerts every day
```

they begin ignoring alerts.

This is:

```text
alert fatigue
```

A monitoring system that constantly cries wolf becomes less useful during real incidents.

# 201. Final Mental Model

Without observability:

```text
User reports problem
       ↓
Engineer guesses
       ↓
Restart
       ↓
Maybe problem disappears
       ↓
Root cause unknown
```

With observability:

```text
User reports problem
       ↓
Establish exact time
       ↓
Inspect container state
       ↓
Inspect application logs
       ↓
Inspect metrics
       ↓
Inspect health
       ↓
Inspect Docker events
       ↓
Inspect configuration
       ↓
Correlate evidence
       ↓
Form hypothesis
       ↓
Test hypothesis
       ↓
Find root cause
       ↓
Fix
       ↓
Verify
```

The complete architecture is:

```text
                         CONTAINER
                            │
             ┌──────────────┼──────────────┐
             │              │              │
             ↓              ↓              ↓
            LOGS          METRICS         EVENTS
             │              │              │
             ↓              ↓              ↓
          DRIVER         COLLECTOR       DOCKER
             │              │              │
             ↓              ↓              │
        LOG BACKEND      PROMETHEUS         │
             │              │              │
             │              ↓              │
             │           GRAFANA            │
             │              │              │
             └──────────────┼──────────────┘
                            ↓
                         ENGINEER
                            ↓
                        CORRELATE
                            ↓
                        UNDERSTAND
                            ↓
                       ROOT CAUSE
                            ↓
                           FIX
                            ↓
                         VERIFY
```

The central lesson of Part 15 is:

```text
A production engineer should not need to guess what a container was doing.
```

Build systems that leave evidence.

Use:

```text
Logs
+
Metrics
+
Events
+
Health
+
Runtime State
+
Time
+
Context
```

Then:

```text
Observe
↓
Measure
↓
Correlate
↓
Diagnose
↓
Fix
↓
Verify
```

That is the foundation of Docker observability.
