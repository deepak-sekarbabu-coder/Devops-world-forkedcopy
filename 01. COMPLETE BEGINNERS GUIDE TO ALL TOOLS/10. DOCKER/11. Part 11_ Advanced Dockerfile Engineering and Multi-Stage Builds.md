# Part 11: Advanced Dockerfile Engineering and Multi-Stage Builds

## Move From "It Runs" to Professionally Engineered Images

Up to this point, you have learned how to create Docker images that work.

You can write a Dockerfile.

You understand instructions such as:

```dockerfile
FROM
WORKDIR
COPY
RUN
ENV
EXPOSE
USER
CMD
ENTRYPOINT
```

You can build an image:

```bash
docker build -t myapp:1.0 .
```

You can run it:

```bash
docker run myapp:1.0
```

You have also used those images in multi-container applications and Docker Compose.

That is an important foundation.

But a Dockerfile can successfully build an application and still be poorly engineered.

A working image might:

* be much larger than necessary;
* contain compilers that production never needs;
* contain package-manager caches;
* contain source files that should not be present;
* run as root;
* rebuild dependencies unnecessarily;
* expose credentials during the build;
* use floating dependency versions;
* produce inconsistent builds;
* contain development tools;
* have poor file ownership;
* support only one CPU architecture;
* contain unnecessary operating-system utilities;
* increase the application's attack surface.

So Part 11 asks a different question.

Not:

```text
Can we build an image?
```

But:

```text
Can we engineer the image properly?
```

Our transformation is:

```text
Large Development Image
        ↓
Analyze Dockerfile
        ↓
Optimize Build Context
        ↓
Optimize Layers
        ↓
Optimize Cache
        ↓
Separate Build Dependencies
        ↓
Multi-Stage Build
        ↓
Builder Stage
        ↓
Runtime Stage
        ↓
Remove Development Tooling
        ↓
Run as Non-Root
        ↓
Protect Build Secrets
        ↓
Add Metadata
        ↓
Test Multiple Platforms
        ↓
Small Production Image
```

By the end of this part, you should be able to look at a Dockerfile and evaluate it as an engineer rather than simply asking whether `docker build` succeeds.

# 2. Why Dockerfile Engineering Matters

Consider two Docker images.

Image A:

```text
1.4 GB
```

Image B:

```text
180 MB
```

Both run the same application.

Does that automatically mean Image B is better?

Not necessarily.

Size is only one engineering property.

But the difference should make you investigate.

Ask:

```text
Why is Image A so large?

What is inside it?

Does production need those files?

Does it contain compilers?

Does it contain development packages?

Does it contain caches?

Does it contain test tools?

Does it contain source code unnecessarily?

Does it run as root?

Are its dependencies reproducible?

How long does it take to build?

How long does it take to transfer?

How large is its attack surface?
```

Professional Dockerfile engineering is about deliberately controlling these characteristics.

# 7. Create the Application

Create:

```text
main.go
```

with:

```go
package main

import (
	"encoding/json"
	"log"
	"net/http"
	"os"
	"runtime"
)

type response struct {
	Message      string `json:"message"`
	Version      string `json:"version"`
	Architecture string `json:"architecture"`
}

func main() {
	version := os.Getenv("APP_VERSION")

	if version == "" {
		version = "development"
	}

	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "application/json")

		data := response{
			Message:      "VERIQTA advanced Dockerfile lab",
			Version:      version,
			Architecture: runtime.GOARCH,
		}

		if err := json.NewEncoder(w).Encode(data); err != nil {
			log.Printf("failed to encode response: %v", err)
		}
	})

	http.HandleFunc("/health", func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)

		if _, err := w.Write([]byte("healthy\n")); err != nil {
			log.Printf("failed to write health response: %v", err)
		}
	})

	log.Println("starting application on :8080")

	if err := http.ListenAndServe(":8080", nil); err != nil {
		log.Fatal(err)
	}
}
```

# 16. Layers Revisited

Docker images are constructed from layers.

Conceptually:

```text

   ↓
WORKDIR
   ↓
COPY
   ↓
RUN build
   ↓
Final Image
```

Some Dockerfile instructions contribute filesystem changes to the image.

Build efficiency depends heavily on understanding these layers and cache relationships.

# 18. Layer Optimization Does Not Mean "One Giant RUN"

You may encounter advice saying:

```text
combine everything into one RUN instruction
```

That is too simplistic.

Sometimes combining package-manager operations is important.

For example:

```dockerfile
RUN apt-get update \
    && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*
```

keeps related package operations together.

But readability, cache behavior, maintainability, and correctness still matter.

Do not create unreadable Dockerfiles merely to minimize instruction count.

---

# 19. Build Cache

Docker can reuse results from previous builds.

Suppose you build:

```text
Step A
Step B
Step C
Step D
```

and the inputs affecting Step C change.

Conceptually:

```text
A → cached
B → cached
C → rebuild
D → rebuild
```

The exact cache rules depend on the instruction and inputs.

This means Dockerfile ordering matters.

---

# 20. Cache Optimization

A useful principle is:

```text
stable expensive steps
        ↓
earlier

frequently changing steps
        ↓
later
```

Why?

Because changes invalidate relevant cache and downstream build work.

---

# 21. A Poor Cache Pattern

Our original Dockerfile says:

```dockerfile
COPY . .

RUN go build -o server .
```

Suppose you change only:

```text
README.md
```

Because:

```dockerfile
COPY . .
```

depends on the entire included build context, that change can invalidate the copy step and downstream build step.

That may trigger unnecessary rebuilding.

---

# 22. Better Dependency Ordering

For ecosystems with dependency manifest files, copy dependency metadata separately.

Conceptually:

```dockerfile
COPY dependency-files .

RUN install-dependencies

COPY application-source .

RUN build
```

Now application source changes do not necessarily invalidate the dependency-resolution layer.

---

# 23. Go Cache-Friendly Pattern

For Go:

```dockerfile
COPY go.mod ./

RUN go mod download

COPY . .

RUN go build -o server .
```

If dependencies do not change, Docker can potentially reuse the dependency-related cache.

Our tiny project currently has no external module dependency, but the pattern becomes important in real projects.

---

# 24. Node.js Equivalent

A common Node pattern is:

```dockerfile
COPY package.json package-lock.json ./

RUN npm ci

COPY . .

RUN npm run build
```

rather than:

```dockerfile
COPY . .

RUN npm install
```

before every source change.

---

# 25. Python Equivalent

A common Python pattern might be:

```dockerfile
COPY requirements.txt .

RUN pip install -r requirements.txt

COPY . .
```

Again:

```text
dependency definition
```

changes less frequently than:

```text
application source
```

in many projects.

# 35. Build Cache Mounts

Normal build cache can reuse complete build steps.

BuildKit cache mounts solve a related problem.

Suppose a package-install step must rerun.

Without a package cache, dependencies may need to be downloaded again.

A cache mount can preserve the package manager's cache between builds.

Conceptually:

```text
Build 1
↓
Download packages
↓
Cache packages

Build 2
↓
Step must rerun
↓
Reuse package cache
↓
Download only what is missing
```

---

# 36. Cache Mount Syntax

A BuildKit cache mount uses:

```dockerfile
RUN --mount=type=cache,target=PATH COMMAND
```

For example, Docker documents Python package caching patterns such as:

```dockerfile
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install -r requirements.txt
```

The cache mount assists the build.

It is not automatically part of the final runtime filesystem.

---

# 37. Go Build Cache Mounts

Go commonly benefits from caching:

```text
module downloads
compiler/build cache
```

For example:

```dockerfile
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    go build -o /out/server .
```

Now repeated builds can reuse cached build data.

---

# 38. Cache Mounts Are Not Runtime Volumes

Do not confuse:

```text
BuildKit cache mount
```

with:

```text
Docker runtime volume
```

Build cache mounts exist to improve build execution.

Runtime volumes exist for container runtime storage.

Different lifecycle.

Different purpose.

---

# 39. Cache Mounts Are Not Image Data

A cache mount does not mean:

```text
copy this cache into my production image
```

Its purpose is to accelerate the build operation.

This distinction is extremely useful.

You can cache large dependency downloads without deliberately carrying the entire package cache into the runtime image.

# 40. Multi-Stage Builds

Now we reach the central concept of this part.

A multi-stage Dockerfile contains multiple:

```dockerfile
FROM
```

instructions.

Each begins another build stage.

Example:

```dockerfile
FROM golang:1.24 AS builder

...

FROM debian:bookworm-slim AS runtime

...
```

We now have:

```text
Stage 1
Builder

Stage 2
Runtime
```

---

# 41. Why Multi-Stage Builds Exist

Consider what compilation needs:

```text
compiler
source code
development libraries
package managers
build tools
test tools
```

Now consider what the running application may need:

```text
compiled binary
runtime libraries
certificates
configuration
```

Those lists are not necessarily the same.

Multi-stage builds let us separate them.

---

# 42. Builder Stage

The builder stage exists to produce artifacts.

For our Go application:

```text
Go source
     ↓
Go compiler
     ↓
Build process
     ↓
server binary
```

The compiler is required while building.

It is not required for the final application process.

---

# 43. Runtime Stage

The runtime stage exists to run the application.

It may contain only:

```text
runtime base
application artifact
runtime dependencies
configuration
non-root identity
metadata
```

This is fundamentally different from shipping the complete development environment.

---

# 44. First Multi-Stage Dockerfile

Replace the original Dockerfile with:

```dockerfile
# syntax=docker/dockerfile:1

FROM golang:1.24 AS builder

WORKDIR /src

COPY go.mod ./

RUN go mod download

COPY . .

RUN CGO_ENABLED=0 \
    go build \
    -trimpath \
    -o /out/server \
    .

FROM debian:bookworm-slim AS runtime

WORKDIR /app

COPY --from=builder /out/server /app/server

EXPOSE 8080

CMD ["/app/server"]
```

---

# 45. Read the Dockerfile Slowly

First:

```dockerfile
FROM golang:1.24 AS builder
```

means:

```text
Create a stage
using Go image
named builder
```

Then:

```dockerfile
FROM debian:bookworm-slim AS runtime
```

starts another stage.

The final image is based on the final target stage unless another target is explicitly selected.

---

# 46. Naming Stages

We used:

```dockerfile
AS builder
```

and:

```dockerfile
AS runtime
```

Stage names make Dockerfiles easier to understand.

Instead of thinking:

```text
stage 0
stage 1
```

we think:

```text
builder
runtime
```

This also makes cross-stage copying readable.

---

# 47. `COPY --from`

The critical line is:

```dockerfile
COPY --from=builder /out/server /app/server
```

Meaning:

```text
builder stage
/out/server
        ↓
copy
        ↓
runtime stage
/app/server
```

Only the artifact we choose is transferred.

The entire builder filesystem is not copied.

---

# 48. What Stays Behind?

The final runtime image does not automatically contain:

```text
Go compiler
Go source tree
builder package cache
builder intermediate files
builder development tools
```

Those remain outside the final runtime stage unless explicitly copied.

This is the power of multi-stage builds.

# 52. Dependency Separation

The core principle is:

```text
Build Dependencies
≠
Runtime Dependencies
```

Examples of build dependencies:

```text
compiler
linker
header files
source code
development package
test framework
asset compiler
```

Examples of runtime dependencies:

```text
application binary
runtime library
CA certificates
timezone data when needed
configuration
```

A production image should contain what the application actually needs to run.

---

# 53. Python Multi-Stage Concept

Python is interpreted, but multi-stage builds can still help.

A builder stage might:

```text
compile wheels
install build dependencies
compile native extensions
```

A runtime stage can receive only the resulting runtime environment.

Conceptually:

```dockerfile
FROM python:3.13-slim AS builder

WORKDIR /build

COPY requirements.txt .

RUN pip wheel \
    --wheel-dir /wheels \
    -r requirements.txt

FROM python:3.13-slim AS runtime

COPY --from=builder /wheels /wheels

RUN pip install \
    --no-cache-dir \
    /wheels/*

COPY app /app

WORKDIR /app

CMD ["python", "app.py"]
```

Real Python dependency handling may require additional care depending on native extensions and wheel availability.

---

# 54. Node.js Multi-Stage Concept

A frontend build may require:

```text
Node.js
npm
TypeScript compiler
bundler
development dependencies
```

but production may only need static assets served by Nginx.

Example:

```dockerfile
FROM node:24 AS builder

WORKDIR /app

COPY package.json package-lock.json ./

RUN npm ci

COPY . .

RUN npm run build

FROM nginx:alpine AS runtime

COPY --from=builder \
    /app/dist \
    /usr/share/nginx/html
```

Transformation:

```text
Node development environment
        ↓
build static assets
        ↓
Nginx runtime
```

The Node toolchain does not need to be in the final Nginx image.

and:

```text
operational familiarity
```

But verify your application's actual requirements.

---

# 61. Alpine Linux

Alpine is a small Linux distribution commonly used for containers.

Example:

```dockerfile
FROM alpine:3.22
```

Its small base size is attractive.

But small does not automatically mean correct for every workload.

---

# 62. Alpine Trade-Offs

A major technical difference is that Alpine commonly uses:

```text
musl libc
```

rather than the:

```text
glibc
```

environment common in distributions such as Debian and Ubuntu.

This can affect software compatibility.

Potential issues include:

* native dependencies;
* precompiled binaries expecting glibc;
* Python wheels;
* performance characteristics for particular workloads;
* debugging/tool availability.

Do not choose Alpine only because:

```text
the image is smaller
```

Choose it when the application and operating model are compatible with it.

---

# 63. Alpine Can Increase Build Complexity

A package that installs easily on Debian might require compilation on Alpine.

Then your supposedly simple small image may need:

```text
compiler
headers
development packages
native build troubleshooting
```

Image engineering is about the complete system, not a single size number.

---

# 64. Distroless Images

Distroless images are designed to contain primarily the application and its runtime dependencies rather than a full general-purpose Linux distribution environment.

They typically omit many familiar tools.

For example, you may not have:

```text
shell
package manager
curl
common troubleshooting utilities
```

This can reduce unnecessary runtime components.

It also changes how you debug.

---

# 65. Distroless Operational Trade-Off

Imagine a production incident.

An engineer tries:

```bash
docker exec -it container sh
```

A distroless image may not contain:

```text
sh
```

That is not automatically a defect.

It is part of the design.

But your operational model must account for it.

You may need:

* external observability;
* debug containers;
* separate debug images;
* platform-level troubleshooting;
* logs and metrics;
* ephemeral debugging tooling where supported.

---

# 66. `scratch`

Docker provides:

```dockerfile
FROM scratch
```

`scratch` represents an empty starting point.

No shell.

No package manager.

No normal filesystem utilities.

Nothing except what you explicitly add.

---

# 67. Scratch Example

A statically compiled Go binary can sometimes run from:

```dockerfile
FROM scratch

COPY server /server

ENTRYPOINT ["/server"]
```

This can produce an extremely small runtime image.

But the application must be compatible with such an environment.

---

# 68. What Scratch Does Not Give You

Scratch does not automatically provide:

```text
CA certificates
timezone data
passwd database
shell
debug tools
package manager
shared libraries
```

If your application requires something, you must supply it deliberately.

---

# 69. HTTPS and CA Certificates

Suppose your application calls:

```text
https://api.example.com
```

TLS certificate verification may require a trusted CA certificate bundle.

If your scratch image lacks it, HTTPS requests may fail.

A tiny image that cannot perform its required function is not optimized.

It is broken.

---

# 70. Static vs Dynamic Binaries

A binary may depend on shared libraries.

Check a Linux binary with:

```bash
ldd BINARY
```

when the relevant environment/tools are available.

A statically linked binary has different runtime requirements from a dynamically linked one.

Do not assume every compiled binary can simply be copied into `scratch`.

---

# 71. Build a Scratch Runtime

Our Go build uses:

```text
CGO_ENABLED=0
```

which helps produce a binary suitable for a minimal pure-Go runtime in this lab.

Try:

```dockerfile
# syntax=docker/dockerfile:1

FROM golang:1.24 AS builder

WORKDIR /src

COPY go.mod ./

RUN go mod download

COPY . .

RUN CGO_ENABLED=0 \
    go build \
    -trimpath \
    -ldflags="-s -w" \
    -o /out/server \
    .

FROM scratch AS runtime

COPY --from=builder /out/server /server

EXPOSE 8080

ENTRYPOINT ["/server"]
```

Build:

```bash
docker build \
  -t veriqta-dockerfile-lab:scratch \
  .
```

```bash
docker run \
```

```bash
curl --fail http://127.0.0.1:8080/health
```

```bash
curl http://127.0.0.1:8080/
```

---

# 75. Reproducible Builds

A reproducible build means you deliberately control the inputs required to produce the artifact.

At a practical beginner level, this means controlling things such as:

```text
base image
application source
dependency versions
build configuration
compiler/runtime version
build arguments
architecture
```

The goal is to reduce:

```text
same source today
→ one result

same source tomorrow
→ unexpectedly different result
```

---

# 76. Floating Tags Reduce Reproducibility

Consider:

```dockerfile
FROM golang:latest
```

What does `latest` mean six months from now?

Potentially something different.

Now compare:

```dockerfile
FROM golang:1.24
```

This is more controlled.

But even version tags can move as image maintainers publish updates within that tag.

For stronger immutability, images can be pinned by digest.

---

# 77. Image Digests

An image reference can include a digest:

```text
image@sha256:...
```

A digest identifies content more precisely than a mutable tag.

Conceptually:

```text
tag
→ human-friendly reference that may move
```

```text
digest
→ content-addressed identity
```

---

# 78. Pinning Trade-Off

Pinning a digest improves reproducibility.

But it also means:

```text
security update published upstream
```

does not magically update your pinned image.

You need an update process.

Good engineering combines:

```text
controlled versions
+
dependency monitoring
+
planned updates
+
testing
```

not:

```text
pin forever and forget
```

---

# 79. Dependency Pinning

The same principle applies inside the application.

Examples:

```text
Python requirements
npm lock files
Go modules
Maven dependencies
OS packages
```

A reproducible container build depends on more than the Dockerfile.

The entire dependency chain matters.

---

# 80. Lock Files

Examples include:

```text
package-lock.json
poetry.lock
uv.lock
go.sum
Gemfile.lock
```

depending on ecosystem.

These files help make dependency resolution more deterministic.

Do not casually omit lock files from production build contexts.

---

# 81. Build Timestamps and Reproducibility

Even with pinned dependencies, artifacts may contain:

* timestamps;
* random identifiers;
* generated metadata;
* build-machine differences;
* compiler-specific variation.

Perfect byte-for-byte reproducibility is a deeper topic.

For now, understand:

```text
reproducibility is an engineering goal
```

not simply:

```text
I pinned one FROM tag
```

---

# 82. Non-Root Execution

A major runtime security principle is:

```text
do not run as root unless the application genuinely requires it
```

Containers do not create a magical security boundary that makes root irrelevant.

---

# 83. Check Current Runtime User

For an image with a shell, you might run:

```bash
docker run \
  --rm \
  IMAGE \
  id
```

Or inspect image configuration:

```bash
docker image inspect IMAGE
```

Look for the configured user.

If no non-root user is configured, many images default to root.

---

# 84. Create a Non-Root User

For a Debian-based runtime, one pattern is:

```dockerfile
RUN groupadd \
      --system \
      app \
    && useradd \
      --system \
      --gid app \
      --home-dir /app \
      app
```

Then:

```dockerfile
USER app
```

Exact user-management commands differ by base distribution.

Do not copy Debian commands into Alpine and assume they are identical.

---

# 85. File Ownership Problem

Suppose:

```text
/app
```

belongs to root.

Then you switch to:

```dockerfile
USER app
```

If the application must write to `/app`, it may fail.

This is a common production failure.

Security changes must be tested.

---

# 86. `COPY --chown`

Dockerfile `COPY` can set ownership while copying files.

Example:

```dockerfile
COPY --chown=app:app \
  --from=builder \
  /out/server \
  /app/server
```

This avoids a separate ownership-changing layer in many cases and makes ownership explicit.

---

# 87. Non-Root Runtime Example

A Debian-based runtime could be:

```dockerfile
FROM debian:bookworm-slim AS runtime

RUN groupadd \
      --system \
      app \
    && useradd \
      --system \
      --gid app \
      --home-dir /app \
      app

WORKDIR /app

COPY --chown=app:app \
  --from=builder \
  /out/server \
  /app/server

USER app

EXPOSE 8080

ENTRYPOINT ["/app/server"]
```

---

# 88. Verify Non-Root Execution

Build:

```bash
docker build \
  -t veriqta-dockerfile-lab:nonroot \
  .
```

Run:

```bash
docker run \
  --rm \
  veriqta-dockerfile-lab:nonroot \
  id
```

This only works if your image entrypoint/command arrangement allows replacing the command and the runtime contains `id`.

Another reliable approach is:

```bash
docker inspect \
  veriqta-dockerfile-lab:nonroot
```

and inspect the configured user.

Then run the application and verify functionality.

---

# 89. Non-Root and Ports

On Linux, privileged-port behavior historically matters for low ports.

Using an application port such as:

```text
8080
```

is a common container pattern.

A reverse proxy or platform can publish external:

```text
80
443
```

while the application listens internally on an unprivileged port.

---

# 90. Non-Root Is Not Complete Container Security

Running as non-root is valuable.

But security also involves:

* Linux capabilities;
* seccomp;
* AppArmor/SELinux where applicable;
* read-only filesystems;
* secrets;
* image provenance;
* dependency security;
* host security;
* Docker daemon security;
* network controls;
* runtime configuration.

Do not reduce container security to one `USER` instruction.

---

# 91. Build Arguments

Docker supports:

```dockerfile
ARG
```

Example:

```dockerfile
ARG APP_VERSION=development
```

Then:

```bash
docker build \
  --build-arg APP_VERSION=1.2.3 \
  .
```

Build arguments are useful for non-secret build-time configuration.

---

# 92. `ARG` vs `ENV`

Mental model:

```text
ARG
→ build-time variable
```

```text
ENV
→ environment variable persisted into the image/runtime configuration unless overridden
```

Their scope and behavior differ.

Do not use them interchangeably.

---

# 93. Build Arguments Are Not Secret Storage

Never think:

```dockerfile
ARG API_TOKEN
```

means:

```text
secure secret
```

Build arguments and environment variables are not appropriate mechanisms for securely passing sensitive credentials into builds.

Sensitive build credentials should use BuildKit secret mechanisms.

---

# 94. Why Build Secrets Matter

Imagine your build must download a private dependency.

You need:

```text
temporary authentication
```

during:

```text
build
```

But you do not want:

```text
credential
```

inside:

```text
final image
```

The desired lifecycle is:

```text
Secret exists outside build
        ↓
Temporarily mounted for one build step
        ↓
Used to authenticate
        ↓
Build step finishes
        ↓
Secret mount disappears
```

---

# 95. BuildKit Secret Mount

Dockerfile syntax:

```dockerfile
RUN --mount=type=secret,id=api_token \
    COMMAND
```

The secret is made temporarily available to that build step.

By default, a secret mount is commonly available under:

```text
/run/secrets/<id>
```

---

# 96. Pass a Secret to the Build

Suppose you have a local disposable lab file:

```text
token.txt
```

You could pass it with:

```bash
docker build \
  --secret id=api_token,src=token.txt \
  .
```

Then a Dockerfile step can consume:

```text
/run/secrets/api_token
```

during that `RUN`.

Do not use a real production credential for a learning exercise.

---

# 97. Safe Secret Lab

Create:

```text
token.txt
```

containing:

```text
temporary-lab-token
```

Make sure it is excluded from Git and the normal build context where appropriate.

Dockerfile:

```dockerfile
# syntax=docker/dockerfile:1

FROM alpine:3.22 AS secret-test

RUN --mount=type=secret,id=api_token \
    test -s /run/secrets/api_token
```

Build:

```bash
docker build \
  --secret id=api_token,src=token.txt \
  --target secret-test \
  .
```

The step verifies that the secret exists without printing it.

---

# 98. Never Print Build Secrets

Bad:

```dockerfile
RUN --mount=type=secret,id=api_token \
    cat /run/secrets/api_token
```

That can expose the secret in build output.

The point of secret handling is not merely:

```text
secret absent from final filesystem
```

You must also avoid leaking it through:

* logs;
* generated files;
* copied artifacts;
* shell tracing;
* error output.

---

# 99. Secret Mount Does Not Prevent Your Application From Leaking It

If you do:

```text
read secret
↓
write secret into artifact
↓
copy artifact to runtime
```

you have still leaked it.

BuildKit protects how the secret is supplied.

You are responsible for how the build process uses it.

---

# 100. Build Arguments vs Build Secrets

Use:

```text
ARG
```

for non-sensitive build configuration such as:

```text
version label
feature selection
build mode
```

Use:

```text
secret mount
```

for sensitive values such as:

```text
private package token
temporary API credential
private repository authentication
```

Never use convenience as an excuse to put secrets into build arguments.

---

# 101. SSH Build Mounts

BuildKit also supports SSH mounts for workflows that need SSH authentication during a build.

Conceptually:

```text
SSH agent/key access
↓
temporary build mount
↓
private Git operation
↓
not copied into final image
```

This is preferable to copying private SSH keys into the image.

---

# 102. Never COPY Private Keys Into an Image

Bad:

```dockerfile
COPY id_rsa /root/.ssh/id_rsa
```

Even if you later delete it:

```dockerfile
RUN rm /root/.ssh/id_rsa
```

you must understand that image layers and build history make "copy then delete later" an unsafe secret-handling pattern.

Do not put private keys into normal image layers.

# 109. OCI Concepts

OCI stands for:

```text
Open Container Initiative
```

At a beginner level, understand that modern container ecosystems share specifications around areas such as:

```text
image format

distribution
```

Docker participates in this broader container ecosystem.

A container image is not merely:

```text
one giant filesystem archive
```

It has structured content and metadata.

# 110. OCI Image Mental Model

Conceptually:

```text
Image
├── Manifest
├── Configuration
└── Layers
```

The manifest references:

```text
configuration
+
filesystem layers
```

The configuration contains information such as runtime configuration and metadata.

# 111. Content Addressing

Container image components are commonly identified by cryptographic digests.

This helps provide content-addressed identity.

That is why you encounter:

```text
sha256:...
```

when inspecting images and registries.

---

# 112. Tags vs Digests

Remember:

```text
myapp:1.0
```

is a tag reference.

```text
myapp@sha256:...
```

is a digest reference.

Tags are convenient for humans.

Digests provide stronger content identity.

# 113. Multi-Platform Images

Your development laptop may be:

```text
linux/amd64
```

or:

```text
linux/arm64
```

Cloud servers may use different CPU architectures.

A single-platform image contains an image variant for one target platform.

A multi-platform image can represent multiple variants under one image reference.

# 114. Example Platforms

Common examples include:

```text

linux/arm64
```

You may also encounter others.

Do not assume:

```text
Linux container
```

means:

```text
works on every CPU architecture
```

# 115. Multi-Platform Image Mental Model

# 122. Emulation

Conceptually:

```text
ARM host
↓
emulation
↓

```

or vice versa.

This is convenient.

But emulation can be much slower for compute-heavy work.

---

# 123. Native Multi-Platform Builders

Another strategy is:

```text
amd64 builder
+
arm64 builder
```

Each builds natively for its platform.

This can be faster and more representative for heavy compilation workloads.

# 124. Cross-Compilation

Some languages support cross-compilation.

Go is a good example.

BuildKit provides predefined platform arguments including concepts such as:

```text
BUILDPLATFORM
TARGETPLATFORM
TARGETOS
TARGETARCH
```

These can be used in multi-stage builds.

---

# 125. Cross-Compilation Dockerfile

For our Go application:

```dockerfile
# syntax=docker/dockerfile:1

FROM --platform=$BUILDPLATFORM golang:1.24 AS builder

ARG TARGETOS
ARG TARGETARCH

WORKDIR /src

COPY go.mod ./

RUN go mod download

COPY . .

RUN CGO_ENABLED=0 \
    GOOS=$TARGETOS \
    GOARCH=$TARGETARCH \
    go build \
    -trimpath \
    -ldflags="-s -w" \
    -o /out/server \
    .

FROM scratch AS runtime

COPY --from=builder /out/server /server

EXPOSE 8080

ENTRYPOINT ["/server"]
```

---

# 126. Why `$BUILDPLATFORM`?

This line:

```dockerfile
FROM --platform=$BUILDPLATFORM golang:1.24 AS builder
```

means the compiler stage can run using the builder's native platform.

Then Go cross-compiles for:

```text
TARGETOS
TARGETARCH
```

This can avoid emulating the entire compilation stage when the language supports cross-compilation.

# 130. Build Cache vs Runtime Image Size

```text
build faster
```

```text
runtime image smaller
```


```text
first build faster
```

Always identify the metric you are improving.

# 131. External Build Cache

CI systems often start on fresh workers.

A local build cache may disappear between jobs.

BuildKit supports cache import/export mechanisms that can allow builds to reuse cache from external storage, including registry-backed cache patterns.

Conceptually:

```text
CI Build 1
↓
Export build cache
↓
Registry/cache backend
↓
CI Build 2
↓
Import build cache
↓
Faster rebuild
```

This becomes important in CI/CD.

---

# 132. Cache Is Not an Artifact Registry

Build cache exists to accelerate builds.

A release image exists to deploy.

Do not confuse:

```text
build cache
```

with:

```text
versioned production artifact
```

They have different lifecycle and retention requirements.

# 133. Optimized Dockerfile

Now combine several concepts:

```dockerfile
# syntax=docker/dockerfile:1

FROM --platform=$BUILDPLATFORM golang:1.24 AS builder

ARG TARGETOS
ARG TARGETARCH

WORKDIR /src

COPY go.mod ./

RUN --mount=type=cache,target=/go/pkg/mod \
    go mod download

COPY . .

RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 \
    GOOS=$TARGETOS \
    GOARCH=$TARGETARCH \
    go build \
    -trimpath \
    -ldflags="-s -w" \
    -o /out/server \
    .

FROM scratch AS runtime

ARG APP_VERSION=development
ARG VCS_REF=unknown

LABEL org.opencontainers.image.title="VERIQTA Advanced Dockerfile Lab"
LABEL org.opencontainers.image.description="Multi-stage Docker image engineering lab"
LABEL org.opencontainers.image.version=$APP_VERSION
LABEL org.opencontainers.image.revision=$VCS_REF

COPY --from=builder /out/server /server

EXPOSE 8080

ENTRYPOINT ["/server"]
```

---

# 134. What This Dockerfile Achieves

Builder stage:

```text
uses Go toolchain
downloads dependencies
uses build caches
compiles application
creates binary
```

Runtime stage:

```text
starts empty
receives only binary
contains metadata
runs application
```

Transformation:

# 135. Where Is `USER` in the Scratch Example?

A scratch image has no user database by default.

A numeric user can be configured:

```dockerfile

```

if the application does not need filesystem ownership entries or privileges incompatible with that identity.

For our HTTP server on port 8080, a numeric non-root identity is suitable.

Add before `ENTRYPOINT`:

```dockerfile
USER 65532:65532
```

Then rebuild and test.

# 167. Final Multi-Target Dockerfile

A more complete learning example:

```dockerfile
# syntax=docker/dockerfile:1

FROM --platform=$BUILDPLATFORM golang:1.24 AS base

WORKDIR /src

COPY go.mod ./

RUN --mount=type=cache,target=/go/pkg/mod \
    go mod download


FROM base AS development

COPY . .

CMD ["go", "run", "."]


FROM base AS test

COPY . .

RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    go test ./...


FROM base AS builder

ARG TARGETOS
ARG TARGETARCH

COPY . .

RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 \
    GOOS=$TARGETOS \
    GOARCH=$TARGETARCH \
    go build \
    -trimpath \
    -ldflags="-s -w" \
    -o /out/server \
    .


FROM scratch AS production

ARG APP_VERSION=development
ARG VCS_REF=unknown

LABEL org.opencontainers.image.title="VERIQTA Advanced Dockerfile Lab"
LABEL org.opencontainers.image.description="Advanced Dockerfile engineering example"
LABEL org.opencontainers.image.version=$APP_VERSION
LABEL org.opencontainers.image.revision=$VCS_REF

COPY --from=builder /out/server /server

USER 65532:65532

EXPOSE 8080

ENTRYPOINT ["/server"]
```

# 179. Common Beginner Mistakes

Avoid these:

1. Using `latest` everywhere without understanding the consequence.
2. Copying the entire repository before dependency installation.
3. Forgetting `.dockerignore`.
4. Shipping compilers in production unnecessarily.
5. Assuming Alpine is always best.
6. Assuming scratch works for every binary.
7. Assuming small means secure.
8. Running everything as root.
9. Switching to non-root without fixing ownership.
10. Using `ARG` for passwords.
11. Printing build secrets.
12. Copying SSH private keys into build layers.
13. Assuming deleting a secret in a later layer makes the earlier mistake safe.
14. Ignoring architecture.
15. Building ARM images for AMD64 production without a plan.
16. Destroying cache on every build.
17. Treating `--no-cache` as a permanent solution.
18. Copying unnecessary test artifacts into production.
19. Using huge base images without knowing why.
20. Optimizing image size until debugging/reliability becomes worse without an alternative operational plan.

# 206. Advanced Dockerfile Cheat Sheet

## Build

```bash
docker build \
  -t app:1.0 \
  .
```

## Plain Build Output

```bash
docker build \
  --progress=plain \
  -t app:1.0 \
  .
```

## Build Without Normal Cache Reuse

```bash
docker build \
  --no-cache \
  -t app:1.0 \
  .
```

## Build Specific Stage

```bash
docker build \
  --target builder \
  -t app:builder \
  .
```

## Build Argument

```bash
docker build \
  --build-arg APP_VERSION=1.0.0 \
  -t app:1.0.0 \
  .
```

## Build Secret

```bash
docker build \
  --secret id=api_token,src=token.txt \
  .
```

## Dockerfile Secret Mount

```dockerfile
RUN --mount=type=secret,id=api_token \
    COMMAND
```

## Cache Mount

```dockerfile
RUN --mount=type=cache,target=/path/to/cache \
    COMMAND
```

## Multi-Stage Build

```dockerfile
FROM builder-image AS builder

RUN build-command

FROM runtime-image AS runtime

COPY --from=builder /artifact /artifact
```

## Copy With Ownership

```dockerfile
COPY --chown=user:group \
  source \
  destination
```

## Non-Root User

```dockerfile
USER app
```

or an appropriate numeric identity:

```dockerfile
USER 65532:65532
```

## Image Labels

```dockerfile
LABEL org.opencontainers.image.title="Application"
```

## Image Inspect

```bash
docker image inspect IMAGE
```

## Image History

```bash
docker history IMAGE
```

## Image Size

```bash
docker image ls IMAGE
```

## Buildx Version

```bash
docker buildx version
```

## List Builders

```bash
docker buildx ls
```

## Inspect Builder

```bash
docker buildx inspect --bootstrap
```

## Create Builder

```bash
docker buildx create \
  --name mybuilder \
  --driver docker-container \
  --use
```

## Multi-Platform Build

```bash
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  -t REGISTRY/IMAGE:TAG \
  --push \
  .
```

## Single Platform and Load Locally

```bash
docker buildx build \
  --platform linux/amd64 \
  -t app:test \
  --load \
  .
```

## Inspect Published Multi-Platform Image

```bash
docker buildx imagetools inspect \
  REGISTRY/IMAGE:TAG
```

# 207. Final Mental Model

A beginner Dockerfile often looks like this conceptually:

```text
Base Development Image
        ↓
Install Everything
        ↓
Copy Everything
        ↓
Build
        ↓
Run
```

The result may contain:

```text
Production Image
├── compiler
├── source code
├── build dependencies
├── development dependencies
├── package caches
├── debugging utilities
├── application
└── runtime dependencies
```

Advanced Dockerfile engineering changes the model:

```text
                    BUILD ENVIRONMENT

Source
  |
  v
Dependency Metadata
  |
  v
Cached Dependencies
  |
  v
Builder
  |
  +--> Compiler
  +--> Build Tools
  +--> Source
  +--> Tests
  +--> Build Cache
  |
  v
Production Artifact
  |
  | COPY --from
  v

                    RUNTIME ENVIRONMENT

Minimal Runtime
  |
  +--> Required Runtime Files
  +--> Application Artifact
  +--> Non-Root Identity
  +--> OCI Metadata
  |
  v
Production Image
```

And for multiple platforms:

```text
                         Source
                           |
                           v
                       BuildKit
                           |
                 +---------+---------+
                 |                   |
                 v                   v
            linux/amd64          linux/arm64
                 |                   |
                 v                   v
             Manifest            Manifest
                 \                   /
                  \                 /
                   +-------+-------+
                           |
                           v
                    Multi-Platform
                      Image Index
                           |
                           v
                        Registry
```

The final transformation is:

```text
Large Development Image
        ↓
Understand Layers
        ↓
Reduce Build Context
        ↓
Optimize Cache
        ↓
Use BuildKit
        ↓
Separate Dependencies
        ↓
Builder Stage
        ↓
Test Stage
        ↓
Production Artifact
        ↓
Minimal Runtime Stage
        ↓
Non-Root Execution
        ↓
Controlled Metadata
        ↓
Reproducible Versioning
        ↓
Multi-Platform Build
        ↓
Small Production Image
```

That is the difference between:

```text
"I know how to write a Dockerfile."
```

and:

```text
"I know how to engineer a Docker image."
```
