# Part 6: Terraform Workflow: Init, Plan, Apply, Destroy, and Change Management

## Understand Terraform's Operational Lifecycle

Writing Terraform configuration is only half of Terraform engineering.

The other half is operating it safely.

You need to understand what happens between:

```text
"I changed main.tf"
```

and:

```text
"The infrastructure changed."
```

That journey is the Terraform workflow.

The core workflow is:

```text
Write
↓
Format
↓
Validate
↓
Initialize
↓
Plan
↓
Review
↓
Apply
↓
Verify
```

And when infrastructure changes later:

```text
Existing Infrastructure
↓
Change Configuration
↓
Format
↓
Validate
↓
Plan Again
↓
Review Difference
↓
Apply
↓
Verify
```

Terraform is not meant to be:

```text
Edit
↓
Hope
↓
Apply
```

The operational mindset should be:

```text
Declare
↓
Check
↓
Preview
↓
Review
↓
Execute
↓
Verify
```

By the end of this part, you should understand:

* `terraform init`
* initialization
* provider installation
* module installation
* backend initialization
* `terraform fmt`
* `terraform validate`
* `terraform plan`
* execution plans
* reading plans
* create
* update
* replace
* destroy
* values known after apply
* `terraform apply`
* approval
* saved plan files
* applying saved plans
* `terraform destroy`
* `-destroy`
* `terraform show`
* `terraform output`
* `terraform console`
* `terraform providers`
* Terraform state introduction
* exit codes
* automation considerations
* non-interactive execution
* plan-before-apply discipline
* reviewing destructive changes
* change control
* safe infrastructure modification

Most importantly, you should understand why each stage exists.

# 1. The Terraform Operational Mental Model

Imagine an engineer wants to create infrastructure.

The engineer writes:

```hcl
resource "local_file" "application" {
  filename = "${path.module}/application.conf"
  content  = "environment=development"
}
```

Terraform does not immediately create the file.

There are several stages between configuration and infrastructure.

```text
Terraform Configuration
↓
Initialization
↓
Validation
↓
Planning
↓
Execution Plan
↓
Human / Automated Review
↓
Apply
↓
Provider
↓
Infrastructure
↓
State Updated
↓
Verification
```

Each stage answers a different question.

| Stage      | Main Question                                    |
| ---------- | ------------------------------------------------ |
| Write      | What infrastructure do I want?                   |
| Format     | Is the configuration consistently formatted?     |
| Validate   | Is the configuration internally valid?           |
| Initialize | Does Terraform have what it needs to operate?    |
| Plan       | What would Terraform change?                     |
| Review     | Are those changes actually what I intended?      |
| Apply      | Execute the approved changes                     |
| Verify     | Did the resulting infrastructure work correctly? |

Do not collapse these mentally into one operation.

---

# 2. The Core Workflow

The workflow we will use throughout this course is:

```text
Write
↓
terraform fmt
↓
terraform validate
↓
terraform init
↓
terraform plan
↓
Review
↓
terraform apply
↓
Verify
```

There is one practical detail.

On a completely new working directory, `terraform init` must happen before commands such as `terraform validate` can fully validate configurations that depend on providers or modules.

Therefore, a practical first-run workflow is often:

```text
Write
↓
terraform fmt
↓
terraform init
↓
terraform validate
↓
terraform plan
↓
Review
↓
terraform apply
↓
Verify
```

After initialization, your normal edit cycle can look like:

```text
Change Configuration
↓
terraform fmt
↓
terraform validate
↓
terraform plan
↓
Review
↓
terraform apply
↓
Verify
```

If provider requirements, module sources, or backend configuration change, run `terraform init` again.

The important lesson is not memorizing one rigid command order.

The important lesson is understanding the dependency:

```text
Commands that need providers/modules/backend initialization
↓
require an initialized working directory
```

# 4. `versions.tf`

Create:

```hcl
terraform {
  required_version = ">= 1.10.0, < 2.0.0"

  required_providers {
    local = {
      source  = "hashicorp/local"
      version = ">= 2.5.0, < 3.0.0"
    }
  }
}
```

This declares:

```text
Terraform version requirement
+
Provider requirement
```

It does not itself install the provider.

That happens during initialization.

---

# 5. `variables.tf`

Create:

```hcl
variable "environment" {
  type        = string
  description = "Environment represented by the generated configuration."
  default     = "development"

  validation {
    condition = contains(
      ["development", "staging", "production"],
      var.environment
    )

    error_message = "Environment must be development, staging, or production."
  }
}

variable "application_port" {
  type        = number
  description = "Application listening port."
  default     = 8080
}
```

---

# 6. `main.tf`

Create:

```hcl
resource "local_file" "application" {
  filename = "${path.module}/application.conf"

  content = <<-EOT
    application=veriqta
    environment=${var.environment}
    port=${var.application_port}
    managed_by=Terraform
  EOT
}
```

---

# 7. `outputs.tf`

Create:

```hcl
output "configuration_file" {
  description = "Path to the Terraform-managed application configuration."
  value       = local_file.application.filename
}

output "environment" {
  description = "Configured environment."
  value       = var.environment
}

output "content_hash" {
  description = "SHA-256 hash of the managed configuration content."
  value       = sha256(local_file.application.content)
}
```

Do not run `apply` yet.

We will move through the lifecycle properly.

# 8. `terraform fmt`

Start with:

```bash
terraform fmt
```

`fmt` reformats Terraform configuration into Terraform's canonical style.

Think:

```text
Messy HCL
↓
terraform fmt
↓
Consistently Formatted HCL
```

It improves:

* indentation
* alignment
* spacing
* readability
* consistency

---

# 9. `fmt` Is Not Validation

This distinction matters.

```text
terraform fmt
```

asks:

```text
"Can this configuration be formatted consistently?"
```

It does not prove:

```text
"The infrastructure design is correct."
```

It does not prove:

```text
"The provider credentials work."
```

It does not prove:

```text
"The resource can actually be created."
```

Formatting and correctness are different concerns.

---

# 10. Formatting Multiple Files

Run:

```bash
terraform fmt
```

Terraform formats eligible configuration files in the current directory.

For recursive formatting:

```bash
terraform fmt -recursive
```

This is useful when a repository contains nested modules.

---

# 11. Checking Formatting Without Changing Files

In automation, you may want to check formatting rather than rewrite files.

Use:

```bash
terraform fmt -check
```

Or recursively:

```bash
terraform fmt -check -recursive
```

Mental model:

```text
Developer Machine
↓
terraform fmt
↓
fix formatting

CI Pipeline
↓
terraform fmt -check
↓
fail if formatting is wrong
```

---

# 12. Why Formatting Matters in Teams

Without standard formatting:

```text
Engineer A style
+
Engineer B style
+
Engineer C style
↓
Noisy Git diffs
↓
Harder code review
```

With formatting:

```text
Terraform Standard Formatting
↓
Cleaner Diffs
↓
Review Focuses on Infrastructure Changes
```

You want reviewers discussing:

```text
"Why is this security group open?"
```

not:

```text
"Why are there three spaces here?"
```

# 13. `terraform init`

Now initialize the working directory:

```bash
terraform init
```

This is one of Terraform's most important commands.

Mental model:

```text
Terraform Configuration
↓
terraform init
↓
Working Directory Prepared
↓
Terraform Can Operate
```

Initialization prepares Terraform to work with the configuration.

---

# 14. What `terraform init` Actually Does

Depending on the configuration, initialization can perform several tasks:

```text
terraform init
│
├── Initialize Backend
│
├── Discover Provider Requirements
│
├── Download / Install Providers
│
├── Download Modules
│
├── Prepare .terraform/
│
└── Update Dependency Lock Information
```

Not every project uses remote modules or a custom backend.

But the command prepares whatever the current configuration requires.

---

# 15. Initialization Is Per Working Directory

Suppose you clone:

```text
terraform-production-infrastructure/
```

from Git.

The repository normally should not contain downloaded provider binaries inside:

```text
.terraform/
```

So after cloning:

```bash
git clone ...
cd terraform-production-infrastructure
terraform init
```

Initialization prepares your local copy.

---

# 16. `.terraform/`

After initialization you will usually see:

```text
.terraform/
```

Terraform uses this working directory data for items such as downloaded providers and modules.

Do not treat it as source code.

It is normally excluded from Git.

Example:

```gitignore
.terraform/
```

---

# 17. `.terraform.lock.hcl`

You should also see:

```text
.terraform.lock.hcl
```

This is different from:

```text
.terraform/
```

The lock file records provider dependency selections and checksums.

A normal version-controlled Terraform project generally commits:

```text
.terraform.lock.hcl
```

to Git.

Mental model:

```text
required_providers
↓
Allowed Versions
↓
terraform init
↓
Selected Provider Version
↓
.terraform.lock.hcl
```

---

# 18. Provider Installation

Suppose your configuration declares:

```hcl
required_providers {
  local = {
    source  = "hashicorp/local"
    version = ">= 2.5.0, < 3.0.0"
  }
}
```

Terraform needs the provider plugin.

During:

```bash
terraform init
```

Terraform resolves and installs an appropriate provider version consistent with:

```text
version constraints
+
dependency lock file
```

---

# 19. Provider Installation Mental Model

```text
Terraform Configuration
↓
required_providers
↓
Provider Source Address
↓
Version Constraint
↓
Dependency Lock Selection
↓
Provider Package
↓
Installed for Working Directory
```

Terraform CLI itself does not contain the implementation for every cloud resource.

Providers supply that integration.

---

# 20. Provider Installation Failure

You might encounter:

```text
Failed to install provider
```

Possible causes include:

```text
No internet connectivity
DNS problems
Proxy restrictions
Firewall restrictions
Invalid provider source
Impossible version constraint
Registry unavailable
Certificate/TLS problems
Provider unavailable for your platform
```

Do not immediately delete everything.

Read the error.

Ask:

```text
Can Terraform reach the provider source?

Is the provider address correct?

Can the requested version exist?

Is a lock-file constraint involved?

Is the network blocking access?
```

---

# 21. Module Installation

Terraform configurations can reference modules.

Conceptually:

```hcl
module "network" {
  source = "..."
}
```

When modules come from remote sources, initialization retrieves the required module packages.

Mental model:

```text
Terraform Configuration
↓
Module Blocks
↓
terraform init
↓
Module Sources Retrieved
↓
Modules Available
```

We will study modules deeply in Part 10.

For now understand:

```text
terraform init
```

is responsible for initializing module dependencies as part of normal setup.

# 22. Backend Initialization

Terraform also initializes the configured backend.

A backend determines where Terraform stores and interacts with state.

For a basic project without another backend configured, Terraform uses the local backend.

Later you might use remote state.

Conceptually:

```text
Terraform CLI
↓
Backend
↓
Terraform State
```

Initialization establishes that relationship.

---

# 23. Backend Mental Model

```text
Configuration
↓
Backend Configuration
↓
terraform init
↓
Backend Initialized
↓
Terraform Can Read/Write State
```

This becomes critical when we reach:

```text
remote state
team collaboration

production infrastructure
```

# 24. Reinitialization

You do not run `terraform init` only once forever.

Reinitialization may be needed when you change:

```text
provider requirements
module sources
module version constraints
backend configuration
```

Simply run:

```bash
terraform init
```

again.

Initialization is designed to be safe to run repeatedly.

---

# 25. Common Reinitialization Message

Terraform may tell you:

```text
Initialization required
```

Do not fight the tool.

Read why initialization is required.

Then, if appropriate:

```bash
terraform init
```

---

# 26. Provider Upgrade

There is an important difference between normal initialization and intentionally upgrading dependency selections.

Normal:

```bash
terraform init
```

Upgrade allowed dependencies:

```bash
terraform init -upgrade
```

Do not automatically use:

```text
-upgrade
```

everywhere.

An upgrade can change selected provider versions within the configured constraints.

That is an infrastructure dependency change and deserves review.

---

# 27. Backend Reconfiguration

Backend changes can require special initialization options such as:

```bash
terraform init -reconfigure
```

or migration workflows.

Do not casually run backend migration options against production state without understanding what is happening.

Backend changes involve Terraform's record of managed infrastructure.

We will cover them deeply later.

```bash
terraform validate
```

This checks whether the configuration is syntactically valid and internally consistent.

```text
Terraform Configuration
↓
```

# 30. What Validation Can Catch

Examples include:

```text
Invalid HCL syntax
Invalid argument structure
Invalid references
Incorrect resource configuration structure
Type-related configuration problems
Missing required configuration elements
Some provider-schema-related problems
```

---

# 31. What Validation Does Not Prove

A successful:

```bash
terraform validate
```

does not prove:

```text
AWS credentials work
IAM permissions are sufficient
resource quota exists
network design is correct
infrastructure is secure
infrastructure is affordable
the application will work
the plan contains no destructive actions
```

Validation answers a narrower question:

```text
Is this Terraform configuration internally valid enough to proceed?
```

# 34. What Is `terraform plan`?

Run:

```bash
terraform plan
```

Terraform creates an execution plan.

An execution plan describes the actions Terraform proposes to make.

Think:

```text
Current Infrastructure
+
Current State
+
Desired Configuration
↓
Terraform Planning
↓
Proposed Changes
```

---

# 35. Plan Does Not Normally Apply the Changes

This is fundamental.

```bash
terraform plan
```

does not normally perform the proposed infrastructure changes.

It previews them.

Mental model:

```text
terraform plan
↓
"What would happen?"
```

versus:

```text
terraform apply
↓
"Perform it."
```

Never confuse the two.

---

# 36. How Terraform Builds a Normal Plan

Conceptually:

```text
Configuration
+
Prior State
+
Current Remote Objects
↓
Terraform Refresh / Read
↓
Comparison
↓
Dependency Graph
↓
Proposed Actions
↓
Execution Plan
```

Terraform evaluates what actions are necessary to make managed infrastructure match the configuration.

---

# 37. Desired State Revisited

Suppose current infrastructure is:

```text
application port = 8080
```

You change configuration to:

```text
application port = 9090
```

Terraform asks:

```text
Current
8080

Desired
9090

Difference?
Yes

Required Action?
Update relevant managed object
```

This is reconciliation.

---

# 38. Reading Terraform Plans

Do not train yourself to jump directly to:

```text
Plan: 5 to add, 1 to change, 0 to destroy.
```

Read the resource-level changes.

A plan is evidence.

Review:

```text
Which resources?

Which attributes?

Why?

Create?

Update?

Replace?

Destroy?

Any unexpected resources?

Any sensitive implications?

Any values unknown until apply?
```

---

# 39. Plan Symbols

Terraform plan output uses symbols to indicate proposed actions.

Common concepts include:

```text
+ create

~ update in-place

- destroy

-/+ destroy and then create replacement

+/- create replacement and then destroy old object
```

The exact presentation can vary depending on the operation and lifecycle behavior.

Do not memorize only colors.

CI logs may have colors disabled.

Read the symbols and text.

---

# 40. Create

A creation appears conceptually as:

```text
+ resource
```

Meaning:

```text
Resource absent
+
Configuration requests it
↓
Create
```

For our first lab:

```text
local_file.application
```

does not yet exist in Terraform state.

Terraform should propose creation.

---

# 41. Creation Mental Model

```text
Configuration
↓
Resource Declared

State
↓
No Managed Instance

Infrastructure
↓
No Corresponding Managed Object

Plan
↓
Create
```

---

# 42. Update In Place

Some changes can be performed without replacing the resource.

Conceptually:

```text
~ update in-place
```

Meaning:

```text
Existing Resource
↓
Attribute Changes
↓
Provider Supports Update
↓
Modify Existing Object
```

Example in cloud infrastructure could be modifying a supported tag or setting.

Whether an attribute supports in-place updates depends on the provider resource schema and remote API behavior.

---

# 43. Replacement

Some changes cannot be applied to an existing remote object.

Terraform may need:

```text
Old Resource
↓
Destroy
+
New Resource
↓
Create
```

This is replacement.

Plan output can indicate:

```text
must be replaced
```

Replacement deserves special attention.

---

# 44. Why Replacement Matters

Replacement can cause:

```text
downtime
new identifiers
new IP addresses
new hostnames
data loss
dependency changes
service interruption
cost overlap
```

depending on the resource.

Therefore:

```text
1 to replace
```

is not merely a technical detail.

It can be an operational event.

---

# 45. Destroy

A plan can propose destruction when Terraform determines a managed resource should no longer exist.

Common reasons include:

```text
resource removed from configuration
count/for_each changes
explicit destroy mode
replacement
certain lifecycle changes
```

A destruction appears conceptually as:

```text
- destroy
```

Stop and understand every destruction before production apply.

---

# 46. Destruction Is Not Always a Problem

Sometimes destruction is exactly intended.

Examples:

```text
temporary development environment
retired service
obsolete resource
replacement
lab cleanup
```

The rule is not:

```text
Never destroy.
```

The rule is:

```text
Never destroy without understanding why.
```

---

# 47. Known After Apply

You will often see something like:

```text
(known after apply)
```

This means Terraform cannot determine the final value during planning.

Example:

```text
Resource ID
↓
assigned by provider/API during creation
↓
not yet available
```

Therefore:

```text
id = (known after apply)
```

---

# 48. Unknown Does Not Mean Error

Beginners sometimes see:

```text
known after apply
```

and think Terraform failed.

It did not.

It means:

```text
The value depends on an operation that has not happened yet.
```

---

# 49. Known vs Unknown Values

Example:

```text
instance_type = "t3.micro"
```

may be known because it comes directly from configuration.

But:

```text
instance_id
public_ip
generated identifier
```

may depend on infrastructure creation.

Therefore:

```text
Known Before Apply
+
Unknown Until Apply
```

can coexist in the same plan.

---

# 50. Plan Summary

At the end, Terraform summarizes proposed resource actions.

Example:

```text
Plan: 1 to add, 0 to change, 0 to destroy.
```

Interpretation:

```text
Create = 1
Update = 0
Destroy = 0
```

But again:

```text
summary
≠
complete review
```

Read the actual resource changes.

# 51. Plan Review Checklist

Before apply, ask:

```text
[ ] Is this the correct environment?

[ ] Is this the correct account/subscription/project?

[ ] Is this the correct region?

[ ] Is this the correct Terraform state?

[ ] Are the expected resources changing?

[ ] Are unexpected resources changing?

[ ] Are any resources being destroyed?

[ ] Are any resources being replaced?

[ ] Could replacement cause downtime?

[ ] Could data be lost?

[ ] Are network rules becoming more permissive?

[ ] Are IAM permissions expanding?

[ ] Are public endpoints being created?

[ ] Are expensive resources being created?

[ ] Are tags correct?

[ ] Are names correct?

[ ] Are outputs reasonable?

[ ] Does the plan match the change request?
```

This is infrastructure review.

# 52. `terraform apply`

After reviewing:

```bash
terraform apply
```

Without a saved plan file, Terraform creates a fresh execution plan and asks for approval before executing it.

Mental model:

```text
terraform apply
↓
Generate Plan
↓
Show Plan
↓
Request Approval
↓
Execute
```

---

# 53. Why Apply Creates Another Plan

Suppose you ran:

```bash
terraform plan
```

at 10:00.

Then:

```bash
terraform apply
```

at 10:20.

The world may have changed.

Therefore, an ordinary `terraform apply` creates its own plan rather than blindly treating your earlier unsaved speculative plan as executable.

If you want to apply a specific reviewed plan, use a saved plan file.

---

# 54. Apply Approval

Interactive apply asks for confirmation.

You normally must enter:

```text
yes
```

This approval barrier is intentional.

It gives you a final opportunity to inspect what Terraform proposes.

Do not develop the habit:

```text
terraform apply
↓
immediately type yes
↓
then read
```

The correct order is:

```text
Read
↓
Understand
↓
Approve
```

# 56. Apply Does Not Mean Success Until You Verify

Terraform might report:

```text

```

That means Terraform completed its intended infrastructure operations.

It does not necessarily mean:

```text

```

Terraform verifies infrastructure operations at its layer.

You must verify the actual service.

# 61. Change Management Begins

# 154. Do Not Use `-target` as Normal Workflow
