# Part 17: Terraform Testing, Validation, Import, Drift, and Troubleshooting

## Learn How to Prove Infrastructure Code Works and Investigate When It Does Not

Writing Terraform is only one part of infrastructure engineering.

Production Terraform must answer harder questions:

```text
Is the configuration formatted correctly?

Is it syntactically valid?

Are the variables valid?

Does the provider accept the configuration?

What exactly will Terraform change?

Does the module behave as expected?

Does the infrastructure satisfy our security rules?

What happens when infrastructure already exists?

What happens when someone changes AWS manually?

What happens when an apply fails halfway through?

How do we know whether the problem is Terraform, AWS, IAM, state, networking, or our configuration?
```

That is what Part 17 teaches.

The central troubleshooting model for this chapter is:

```text
Symptom
↓
Configuration
↓
Validation
↓
Plan
↓
State
↓
Provider
↓
Credentials
↓
Cloud API
↓
Real Resource
↓
Root Cause
↓
Fix
↓
Plan Again
↓
Apply
↓
Verify
```

Do not troubleshoot Terraform by randomly changing code.

Follow the evidence.

---

# 2. Formatting Is Not Validation

Consider:

```bash
terraform fmt
```

It answers:

```text
"Is this Terraform configuration formatted according to Terraform's canonical style?"
```

It does not answer:

```text
"Will this infrastructure work?"
```

Likewise:

```bash
terraform validate
```

does not prove:

```text
"AWS will successfully create everything."
```

And:

```bash
terraform plan
```

does not prove:

```text
"The deployed application will respond correctly to users."
```

Every tool has a boundary.

---

# 3. The Complete Verification Mental Model

```text
terraform fmt
↓
Is the code consistently formatted?

terraform validate
↓
Is the configuration internally valid?

Variable Validation
↓
Are the supplied inputs acceptable?

Provider Validation
↓
Does the provider accept the configuration structure?

terraform plan
↓
What does Terraform intend to change?

terraform test
↓
Does the configuration behave as expected?

Static Analysis
↓
Are there structural/code-quality problems?

Security Scan
↓
Are there known infrastructure security problems?

Policy Check
↓
Does the change comply with organizational rules?

terraform apply
↓
Can the infrastructure actually be created?

Runtime Verification
↓
Does the resulting infrastructure actually work?
```

You need multiple layers.

---

# 4. Start with `terraform fmt`

Terraform configuration is written in HCL.

Different engineers might initially write:

```hcl
resource "aws_instance" "app" {
instance_type="t3.micro"
ami=data.aws_ami.app.id
tags={Name="app"}
}
```

Terraform can understand the structure, but it is difficult to read.

Run:

```bash
terraform fmt
```

Terraform rewrites supported configuration into its canonical style.

The result resembles:

```hcl
resource "aws_instance" "app" {
  instance_type = "t3.micro"
  ami           = data.aws_ami.app.id

  tags = {
    Name = "app"
  }
}
```

Formatting improves consistency.

---

# 5. Why Formatting Matters

Infrastructure code is reviewed by humans.

Humans need to quickly recognize:

```text
Resources

Variables

Dependencies

IAM permissions

Security-group rules

Lifecycle settings

Provider changes

Potential destructive changes
```

Consistent formatting removes unnecessary visual noise.

---

# 6. Format the Current Directory

Run:

```bash
terraform fmt
```

Terraform formats Terraform configuration files in the current directory.

If Terraform modifies files, it normally prints their names.

Example:

```text
main.tf
variables.tf
```

---

# 7. Format Recursively

For a repository containing nested Terraform modules:

```bash
terraform fmt -recursive
```

This is useful for structures such as:

```text
terraform/
├── modules/
│   ├── network/
│   ├── compute/
│   └── load-balancer/
└── environments/
    ├── dev/
    ├── staging/
    └── production/
```

---

# 8. Formatting in CI

CI usually should not silently rewrite code.

Instead, check whether formatting is correct:

```bash
terraform fmt -check -recursive
```

Conceptually:

```text
Terraform Code
↓
terraform fmt -check
├── Correct → Continue
└── Incorrect → Fail CI
```

The developer fixes formatting before merge.

---

# 9. View Formatting Differences

You can use:

```bash
terraform fmt -check -diff -recursive
```

to help identify formatting differences.

This is useful in CI logs.

---

# 10. Formatting Failure Workflow

If:

```bash
terraform fmt -check -recursive
```

fails:

```text
Do not investigate AWS.

Do not investigate IAM.

Do not investigate state.
```

The failure is much earlier.

Run:

```bash
terraform fmt -recursive
```

Review the changes.

Then run:

```bash
terraform fmt -check -recursive
```

again.

# 11. `terraform validate`

After formatting, validate the configuration.

Run:

```bash
terraform validate
```

Terraform checks whether the configuration is syntactically valid and internally consistent.

---

# 12. What Validation Can Detect

Examples include:

```text
Invalid HCL syntax

Unsupported arguments

Invalid resource references

Incorrect attribute names

Incorrect value types

Invalid module arguments

Some provider-schema violations

Invalid expressions

Missing required configuration
```

---

# 13. Example Invalid Reference

Suppose:

```hcl
output "instance_id" {
  value = aws_instance.application.id
}
```

but your actual resource is:

```hcl
resource "aws_instance" "app" {
  # ...
}
```

Terraform cannot find:

```text
aws_instance.application
```

Validation or planning can identify the invalid reference.

Correct:

```hcl
output "instance_id" {
  value = aws_instance.app.id
}
```

---

# 14. Validation Requires Initialization

Terraform needs referenced providers and modules available before full validation.

A normal workflow is:

```bash
terraform init
terraform validate
```

For CI or reusable-module validation where you do not want Terraform to initialize the configured backend:

```bash
terraform init -backend=false
terraform validate
```

This is useful because configuration validation itself does not need to contact your remote backend.

---

# 15. What `terraform validate` Does Not Prove

A successful validation does not prove:

```text
AWS credentials work

IAM permissions are sufficient

The AWS account is correct

The selected region contains the resource

A subnet actually exists

An AMI still exists

A resource name is globally available

An AWS quota has capacity

An application will boot successfully

A security group allows required traffic
```

Validation is primarily configuration validation.

---

# 16. Validation vs Planning

Think:

```text
terraform validate
↓
Can this configuration make sense independently?
```

versus:

```text
terraform plan
↓
What does this configuration mean for this actual environment?
```

Planning has more context.

---

# 17. Provider Validation

Terraform providers define schemas for resources and data sources.

The AWS provider knows that an EC2 resource supports certain arguments and expects certain value types.

Conceptually:

```text
Terraform Configuration
↓
AWS Provider Schema
↓
Provider Validation
```

---

# 18. Provider Validation Example

Suppose you write an argument that the installed provider version does not support.

Terraform may report something similar to:

```text
Unsupported argument
```

This tells you something important.

The problem may not be:

```text
AWS rejected the API request.
```

Terraform may not have reached AWS at all.

The provider rejected the configuration first.

---

# 19. Provider Validation Has Boundaries

Provider configuration validation can happen without a configured remote API client.

Other checks require planning or applying because they depend on:

```text
Credentials

Remote API data

Existing infrastructure

Computed values

Provider runtime behavior
```

Therefore:

```text
Provider schema accepted configuration
```

does not mean:

```text
AWS API will accept operation.
```

---

# 20. Variable Validation

Variables should reject invalid input as early as possible.

Example:

```hcl
variable "environment" {
  type        = string
  description = "Deployment environment."

  validation {
    condition = contains(
      ["dev", "staging", "production"],
      var.environment
    )

    error_message = "environment must be dev, staging, or production."
  }
}
```

Now:

```text
environment = "banana"
```

fails early.

That is better than allowing invalid configuration to propagate deep into infrastructure creation.

---

# 21. Validation Error Messages Matter

Bad:

```text
Invalid value.
```

Better:

```text
environment must be dev, staging, or production.
```

A good validation error tells the user:

```text
What is wrong?

What values are acceptable?

How can I fix it?
```

---

# 22. Preconditions

Terraform also supports preconditions.

A precondition expresses something that must be true before Terraform proceeds with the relevant operation.

Conceptually:

```text
Resource
↓
Precondition
↓
Requirement True?
├── Yes → Continue
└── No  → Stop
```

Use preconditions when infrastructure assumptions should be enforced close to the resource or output they protect.

---

# 23. Postconditions

Postconditions verify assumptions about a resource after Terraform evaluates the relevant resource operation.

Conceptually:

```text
Resource Result
↓
Postcondition
↓
Expected Condition?
├── Yes → Continue
└── No  → Report Failure
```

They help encode infrastructure expectations.

---

# 24. Check Blocks

Terraform also supports `check` blocks for broader validation.

The important distinction is:

```text
Validation
↓
Conditions required for correct configuration/operation
```

versus:

```text
Tests
↓
Explicit test scenarios executed with terraform test
```

Do not treat all validation mechanisms as interchangeable.

---

# 25. `terraform plan`

After formatting and validation:

```bash
terraform plan
```

Terraform creates an execution plan.

The plan answers:

```text
Given:

Configuration
+
Current State
+
Current Remote Infrastructure

What changes would Terraform propose?
```

---

# 26. Terraform Plan Mental Model

```text
Configuration
        ↓
        │
State ──┼→ Terraform Plan
        │
Real Infrastructure
        ↓

Proposed Changes
```

Terraform normally refreshes its understanding of managed remote resources before calculating the proposed changes.

---

# 27. Plan Symbols

Terraform plan output commonly represents actions such as:

```text
+   create

~   update in place

-   destroy

-/+ replace
```

Learn to read these.

A production engineer should never look only at:

```text
Plan: 12 to add, 4 to change, 1 to destroy.
```

You need to understand which 17 resource actions are involved.

---

# 28. Replacement Is Important

Suppose Terraform shows:

```text
-/+
```

This means Terraform plans to replace a resource.

That can mean:

```text
Destroy old resource
+
Create replacement
```

or a lifecycle-controlled variation.

Replacement may cause:

```text
Downtime

IP changes

Instance changes

Storage implications

DNS changes

Dependency changes
```

Never treat replacement as a normal update without investigation.

---

# 29. Plan Review

Before apply, ask:

```text
What is being created?

What is changing?

What is being destroyed?

What is being replaced?

Why?

Is this expected?

Are IAM permissions changing?

Are network paths changing?

Are security groups changing?

Is persistent storage affected?

Is state architecture changing?

Is DNS changing?

Could users experience downtime?
```

---

# 30. Save a Plan

For controlled workflows:

```bash
terraform plan -out=tfplan
```

Review:

```bash
terraform show tfplan
```

Then apply that saved plan:

```bash
terraform apply tfplan
```

This is useful because the reviewed plan becomes the plan being applied, subject to Terraform's normal safeguards and environment assumptions.

Protect saved plans because they may contain sensitive information.

---

# 31. Plan Review Is a Security Control

Imagine:

```text
Code change:
1 line
```

but the plan says:

```text
17 resources to destroy
```

That is evidence that the infrastructure effect is much larger than the code diff suggests.

Stop.

Investigate.

---

# 32. Plan Review Is Also a Troubleshooting Tool

If you expected:

```text
1 EC2 instance update
```

but Terraform proposes:

```text
destroy VPC

destroy subnets

replace instances

replace load balancer
```

the plan is telling you your mental model is wrong.

Do not apply to "see what happens."

# 33. Terraform Native Tests

Terraform has a native testing framework.

Terraform test files use:

```text
.tftest.hcl
```

or:

```text
.tftest.json
```

The native testing framework is available in Terraform 1.6 and later.

---

# 34. Default Test Directory

A common structure is:

```text
module/
├── main.tf
├── variables.tf
├── outputs.tf
└── tests/
    ├── basic.tftest.hcl
    └── validation.tftest.hcl
```

Terraform's default test directory is:

```text
tests/
```

Test files may also exist in the root configuration directory.

---

# 35. First Terraform Test

Suppose a module has:

```hcl
variable "environment" {
  type = string
}

locals {
  name = "veriqta-${var.environment}"
}

output "name" {
  value = local.name
}
```

Create:

```text
tests/naming.tftest.hcl
```

with:

```hcl
run "development_name" {
  command = plan

  variables {
    environment = "dev"
  }

  assert {
    condition     = output.name == "veriqta-dev"
    error_message = "Expected the generated name to be veriqta-dev."
  }
}
```

---

# 36. Run Terraform Tests

From the root configuration directory:

```bash
terraform test
```

Terraform discovers the test files and executes the test runs.

Expected style of result:

```text
tests/naming.tftest.hcl... pass

Success!
```

Exact output can vary by Terraform version and test structure.

---

# 37. The `run` Block

A Terraform test contains one or more:

```hcl
run "name" {
  # ...
}
```

Each run represents a Terraform test execution.

Example:

```hcl
run "production_name" {
  command = plan

  variables {
    environment = "production"
  }

  assert {
    condition     = output.name == "veriqta-production"
    error_message = "Production name is incorrect."
  }
}
```

---

# 38. Test Commands

A run can use:

```hcl
command = plan
```

or the default apply behavior.

These test different things.

---

# 39. Plan-Based Tests

Use:

```hcl
command = plan
```

when you can verify behavior without creating real infrastructure.

This is useful for testing:

```text
Naming

Conditional resources

Calculated values

Input behavior

Resource configuration

Module logic
```

Plan-based tests are often cheaper and faster.

---

# 40. Apply-Based Tests

By default, Terraform test runs use apply behavior.

That means Terraform may create real infrastructure.

This is closer to integration testing.

Conceptually:

```text
terraform test
↓
Create Test Infrastructure
↓
Evaluate Assertions
↓
Destroy Test Infrastructure
```

This can incur:

```text
Cloud cost

API calls

Quota usage

Real resource creation
```

Use dedicated test environments.

---

# 41. Test Cleanup Matters

Terraform attempts to destroy test infrastructure it created.

But you must still think operationally.

What happens if:

```text
The test process crashes?

Credentials expire?

Provider fails?

AWS refuses deletion?

Network connectivity disappears?
```

Test infrastructure can remain behind.

Use:

```text
Dedicated accounts

Strong naming

Tags

Cost monitoring

Cleanup checks
```

for real cloud integration tests.

---

# 42. Assertions

An assertion asks:

```text
Is this condition true?
```

Example:

```hcl
assert {
  condition     = output.name == "veriqta-dev"
  error_message = "Unexpected application name."
}
```

If:

```text
condition = true
```

the assertion passes.

If:

```text
condition = false
```

the assertion fails and Terraform displays the error message.

---

# 43. Good Assertions

Good assertions test meaningful behavior.

Examples:

```text
Does the module generate the correct name?

Does production use the expected capacity?

Is encryption enabled?

Does the output expose the expected endpoint?

Is a resource created when a feature is enabled?

Is a resource omitted when the feature is disabled?
```

---

# 44. Weak Assertions

Avoid tests that merely repeat Terraform syntax without proving useful behavior.

A test suite should protect:

```text
Module contracts

Security expectations

Important defaults

Conditional behavior

Critical outputs

Infrastructure assumptions
```

---

# 45. Test Variable Scenarios

A module can be tested with several input combinations.

Example:

```text
Development
Staging
Production
```

Each test can supply different variables.

This is especially useful for reusable modules.

```text
modules/
└── compute/
    ├── main.tf
    ├── variables.tf
    ├── outputs.tf
```

```text
Expected outputs

Tags
```

The goal is to protect the module's interface and behavior.

```text
↓
```

# 48. Provider Mocking

Terraform 1.7+ supports provider mocking in Terraform tests.

This is extremely useful when you want to test module logic without creating real cloud infrastructure.

Example concept:

```hcl
mock_provider "aws" {}
```

Now tests can work against the AWS provider schema while Terraform generates mock values for computed attributes.

---

# 49. Why Mock Providers?

Without mocking:

```text
Test
↓
AWS Credentials
↓
AWS API
↓
Real Resources
↓
Cost
```

With appropriate mocking:

```text
Test
↓
Mock AWS Provider
↓
Simulated Provider Data
↓
Assertions
```

This is useful for unit-style testing.

---

# 50. Mocking Has Limits

A mock provider cannot prove:

```text
AWS accepts the API call

IAM permissions are correct

The subnet routes correctly

The EC2 instance actually boots

The ALB health check actually passes

The application actually responds
```

Mocking tests Terraform logic.

Real integration tests test real provider/API behavior.

You may need both.

---

# 51. Testing Pyramid for Terraform

Think:

```text
                    Real Cloud Tests
                   /                \
                  /   Fewer, slower  \
                 /     expensive      \
                /______________________\
               /                        \
              /    Terraform Tests       \
             /      with mocks            \
            /______________________________\
           /                                \
          / fmt + validate + static analysis \
         /____________________________________\
```

Run cheap tests frequently.

Use expensive integration tests selectively.

---

# 52. Test One File

For targeted troubleshooting, Terraform supports filtering test files.

Example:

```bash
terraform test -filter=tests/naming.tftest.hcl
```

This is useful when a repository has many test files.

---

# 53. Testing vs Validation

Use validation when something should always be true during normal Terraform operation.

Use tests when you want to execute explicit scenarios.

Example:

```text
Variable validation:
Environment must be dev/staging/production.
```

Test:

```text
When environment = production,
the module should create three application instances.
```

Different purpose.

# 54. Static Analysis

# 55. Static Analysis Is Broader Than `terraform validate`

# 60. Existing Infrastructure

So far, much of our Terraform journey assumed:

```text
Terraform creates resource
↓
Terraform records resource in state
↓
Terraform manages resource
```

But real organizations often already have infrastructure.

For example:

```text
EC2 created manually

VPC created years ago

Route 53 zone created before Terraform

S3 bucket created by another team

IAM role created through AWS Console
```

How do you bring that infrastructure under Terraform?

Import.

---

# 61. What Import Means

Terraform import connects:

```text
Existing Remote Resource
```

to:

```text
Terraform Resource Address
```

through:

```text
Terraform State
```

Conceptually:

```text
Existing AWS Resource
↓
Import
↓
Terraform State Binding
↓
Terraform Configuration
```

---

# 62. Import Does Not Recreate the Resource

Suppose EC2 already exists:

```text
i-0123456789abcdef0
```

Import does not mean:

```text
Destroy instance
↓
Create new Terraform instance
```

The goal is:

```text
Tell Terraform:
"This existing object belongs to this Terraform resource address."
```

---

# 63. Import Requires Care

Terraform expects one remote object to be associated with one resource address.

Do not intentionally import the same remote object into several addresses.

You can create confusing and unsafe state behavior.

---

# 64. Two Main Import Approaches

You will commonly encounter:

```text
CLI Import
```

and:

```text
Configuration-Driven Import
```

using `import` blocks.

Modern Terraform workflows often benefit from configuration-driven import because import becomes reviewable in the normal plan/apply workflow.

---

# 65. CLI Import

General syntax:

```bash
terraform import ADDRESS ID
```

Example concept:

```bash
terraform import aws_instance.app i-0123456789abcdef0
```

The exact import ID depends on the resource type.

Always check the current provider documentation.

---

# 66. CLI Import Requires Configuration

Before a normal CLI import, create the destination resource configuration.

Example:

```hcl
resource "aws_instance" "app" {
  # Configuration that should eventually describe
  # the existing EC2 instance.
}
```

Then:

```bash
terraform import aws_instance.app i-0123456789abcdef0
```

CLI import imports the object into state.

It does not automatically generate the complete desired Terraform configuration.

---

# 67. After Import

Do not stop after:

```text
Import successful!
```

Immediately run:

```bash
terraform plan
```

Why?

Because Terraform now compares:

```text
Your Configuration
```

against:

```text
Imported Real Resource
```

If they do not match, Terraform may propose changes.

---

# 68. Dangerous Import Mistake

Imagine:

```text
Existing Production Resource
↓
Import
↓
Incomplete Terraform Configuration
↓
terraform plan
↓
Unexpected Changes
```

Then someone runs:

```bash
terraform apply
```

without reviewing the plan.

Terraform may modify the production resource to match the incomplete configuration.

Import is not finished until the post-import plan is understood.

---

# 69. Import Workflow

Use:

```text
Identify Resource
↓
Identify Correct Terraform Resource Type
↓
Read Provider Import Documentation
↓
Determine Import ID
↓
Write Configuration
↓
Import
↓
Inspect State
↓
Run Plan
↓
Compare Configuration to Reality
↓
Adjust Configuration
↓
Plan Again
↓
Repeat Until Expected
↓
Manage Normally
```

# 70. Configuration-Driven Import

Terraform supports `import` blocks.

Example:

```hcl
import {
  to = aws_instance.app
  id = "i-0123456789abcdef0"
}
```

and a matching resource:

```hcl
resource "aws_instance" "app" {
  # ...
}
```

The `to` address identifies where the remote resource should be bound.

The `id` identifies the remote object according to the provider's import format.

---

# 71. Why Import Blocks Are Useful

Import blocks can be:

```text
Stored in Git

Reviewed

Planned

Applied

Used in CI/CD
```

This makes importing infrastructure more compatible with normal infrastructure change management.

# 72. Import Block Workflow

```text

↓
Write Import Block
↓
terraform plan
↓
Review Import
↓
terraform apply
↓

↓
```

---

# 73. Import Blocks Can Stay

After successful import, you can remove an import block or keep it as an historical record.

Terraform does not continually re-import an already managed resource on every apply simply because the import block remains.

Your repository standards should define whether import blocks are retained.

# 74. Import into Modules

Imports can target resource addresses inside modules.

Conceptually:

```text

```

This is useful when the imported infrastructure belongs inside your established module architecture.

Do not flatten your repository structure merely because you are importing existing infrastructure.

# 75. Import and `for_each`

Modern import blocks support `for_each`.

This can help with multiple known resources.

But do not start with advanced bulk import patterns before understanding single-resource import.

First understand:

```text

↓
One Terraform address
```

Then scale the process.

# 83. Drift

Drift occurs when managed real infrastructure changes outside the expected Terraform workflow and no longer matches Terraform's previous recorded understanding/configuration.

Example:

```text
Terraform:
Security Group allows port 443
```

Someone manually changes AWS:

```text
Security Group allows port 443
+
port 22 from 0.0.0.0/0
```

Terraform code did not change.

The real infrastructure did.

That is drift.

---

# 84. Three-Way Terraform Model

Terraform constantly reasons about:

```text
Configuration
↕
State
↕
Real Infrastructure
```

These three can disagree.

Understanding which one differs is essential.

---

# 85. Drift Example

Configuration:

```text
Instance Type:
t3.micro
```

State from last apply:

```text
Instance Type:
t3.micro
```

Someone changes EC2 manually:

```text
Instance Type:
t3.small
```

Now:

```text
Configuration = t3.micro

State = previously t3.micro

Reality = t3.small
```

A normal Terraform plan refreshes remote information and can detect the difference.

---

# 86. Out-of-Band Changes

An out-of-band change means a change performed outside the normal Terraform workflow.

Examples:

```text
AWS Console change

AWS CLI change

Manual API call

Emergency script

Another automation system

Another Terraform state managing the same resource
```

Out-of-band changes are not automatically malicious or wrong.

Sometimes incident response requires them.

But they must eventually be reconciled.

---

# 87. Why Drift Is Dangerous

Drift can cause:

```text
Unexpected Terraform plans

Security gaps

Configuration confusion

Incident-response mistakes

Unexpected replacement

Hidden production differences

Incorrect documentation

Future apply surprises
```

Your repository stops being a reliable representation of infrastructure.

---

# 88. Detecting Drift with Normal Plan

A normal:

```bash
terraform plan
```

refreshes managed resources in memory before calculating changes unless refresh is explicitly disabled.

Terraform may report:

```text
Objects have changed outside of Terraform
```

and then show what it proposes to do.

---

# 89. `-refresh=false`

Terraform can plan without refreshing remote objects:

```bash
terraform plan -refresh=false
```

This can reduce API calls and speed certain workflows.

But it means Terraform may ignore real-world changes.

Do not use it casually for drift investigation.

If you are investigating drift, you generally need current remote information.

---

# 90. Refresh-Only Planning

Use:

```bash
terraform plan -refresh-only
```

to inspect how Terraform's state would need to change to reflect the current remote infrastructure without proposing normal configuration-driven infrastructure changes.

Think:

```text
Real Infrastructure
↓
Compare to State
↓
Show State Reconciliation
```

---

# 91. Refresh-Only Does Not Fix Infrastructure

This is critical.

```bash
terraform plan -refresh-only
```

does not mean:

```text
Make AWS match Terraform code.
```

It means:

```text
Show how state differs from current remote reality.
```

---

# 92. Apply Refresh-Only

If you deliberately want Terraform state to accept current remote values:

```bash
terraform apply -refresh-only
```

After review and approval, Terraform updates state/output values without making normal changes to remote resources.

Use this carefully.

---

# 93. `terraform refresh` Is Deprecated

Older material may teach:

```bash
terraform refresh
```

Current Terraform guidance prefers:

```bash
terraform plan -refresh-only
```

followed, when appropriate, by:

```bash
terraform apply -refresh-only
```

The older `terraform refresh` command can update state without giving you the same review-first workflow.

Do not build new operational procedures around the deprecated command.

---

# 94. Drift Decision

After detecting drift, you have a decision.

Was the out-of-band change:

```text
Desired?
```

or:

```text
Undesired?
```

---

# 95. Reject Drift

Suppose someone manually changed:

```text
Security Group:
443 only
```

to:

```text
443
+
22 from anywhere
```

and this was unauthorized.

Your desired configuration remains:

```text
443 only
```

A normal Terraform plan should show how Terraform would reconcile the resource toward configuration.

After review:

```bash
terraform apply
```

can restore the intended Terraform-managed configuration.

---

# 96. Accept Drift

Suppose an emergency response legitimately changed:

```text
Instance capacity:
2 → 4
```

and the organization decides that 4 should become the new desired state.

Then update Terraform configuration:

```text
desired_capacity = 4
```

and reconcile state/configuration deliberately.

The goal becomes:

```text
Configuration = Reality
```

not merely:

```text
State = Reality
```

```text
Drift Detected
↓
Was Change Authorized?
├── No
│   ↓
│   Keep Desired Configuration
│   ↓
│   Plan
│   ↓
│   Apply Terraform Configuration
│   ↓
│   Restore Intended Infrastructure
│
└── Yes
    ↓

    ↓
```

Bad:

```text

↓

↓

```

You have only told Terraform:

```text

```

You have not necessarily made configuration agree with reality.

The next normal plan may still propose changes.

# 107. Dependency Failures

Terraform builds a dependency graph.

Suppose:

```text

↓
Subnet
↓

```

If subnet creation fails, EC2 may not be created.

This is expected.

Terraform cannot create a resource whose required dependency does not exist.

# 108. Dependency Failure Investigation

If EC2 fails because subnet failed:

```text
Do not start with EC2.
```

Follow the dependency chain upward.

```text

↓
Subnet unavailable
↓
Why did subnet fail?
↓
VPC?
CIDR?
Permissions?
Quota?
Region?
```

Fix the earliest meaningful failure.

# 109. Read Errors from the Top of the Dependency Chain

```text
↓

↓

↓

↓

```

You may see many failures.

But there may be only one root cause.

# 131. Partial Failures

Terraform apply is not a database transaction.

If Terraform plans:

```text

```

and resource 7 fails, the first 6 may already exist.

Terraform does not necessarily roll everything back.

This is one of the most important production Terraform lessons.

---

# 132. Terraform Apply Is Not Atomic

Do not think:

```text
Apply succeeds
OR
Nothing changes.
```

Think:

```text
Apply starts
↓
Some resources succeed
↓
Some resources fail
↓
State records successful operations where possible
↓
Infrastructure may be partially changed
```

That is a partial failure.

# 143. Root-Cause Investigation

Root cause is:

```text

```

Not merely:

```text

```

```text

```

```text

↓

↓
Package installation failed
↓
Repository could not be reached
↓
Private subnet has no required egress path
```

Root cause:

```text
Missing required network egress
```

not:

```text
Terraform is broken.
```

# 153. Do Not Drown in Logs

TRACE output can contain thousands of lines.

Start with:

```text
Exact error time

Resource address

Provider name

API operation

Request ID

HTTP status

Error code
```

Search around those events.

Logs are evidence, not reading material.

---

# 154. Troubleshooting Method

Use this exact model:

```text
Symptom
↓
Configuration
↓
Validation
↓
Plan
↓
State
↓
Provider
↓
Credentials
↓
Cloud API
↓
Real Resource
↓
Root Cause
↓
Fix
↓
Plan Again
↓
Apply
↓
Verify
```

Now we will break it down.

---

# 155. Step 1: Symptom

Write down exactly what failed.

Bad:

```text
Terraform doesn't work.
```

Good:

```text
terraform apply fails while creating aws_instance.app with an AWS UnauthorizedOperation error.
```

Specific symptoms produce faster investigations.

---

# 156. Step 2: Configuration

Inspect the relevant Terraform.

Ask:

```text
Is the resource configured correctly?

Are variables correct?

Are references correct?

Is the provider correct?

Is the region correct?

Is the module receiving correct inputs?
```

Do not edit yet.

Observe first.

---

# 157. Step 3: Validation

Run:

```bash
terraform fmt -check -recursive
terraform validate
```

If validation fails, fix configuration before investigating AWS runtime behavior.

---

# 158. Step 4: Plan

Run:

```bash
terraform plan
```

Ask:

```text
Does Terraform understand the change I intended?

What actions are proposed?

Is there replacement?

Is there destruction?

Is there drift?
```

If the plan itself is wrong, do not apply.

---

# 159. Step 5: State

Inspect:

```bash
terraform state list
```

and:

```bash
terraform state show ADDRESS
```

Ask:

```text
Does Terraform track the object?

At which address?

Does the state ID match the real object?

Am I using the correct state?
```

---

# 160. Step 6: Provider

Check:

```bash
terraform providers
```

Ask:

```text
Correct provider?

Correct version?

Correct provider configuration?

Correct aliases?

Correct region?

Recent provider upgrade?
```

---

# 161. Step 7: Credentials

For AWS:

```bash
aws sts get-caller-identity
```

Ask:

```text
Correct account?

Correct role?

Session valid?

OIDC role correct?

Credentials expired?
```

---

# 162. Step 8: Cloud API

Read the actual AWS error.

Examples:

```text
AccessDenied

InvalidParameter

ResourceAlreadyExists

LimitExceeded

Throttling

InvalidSubnetID.NotFound
```

The cloud API is often telling you exactly what it rejected.

---

# 163. Step 9: Real Resource

Inspect AWS directly.

Use:

```text
AWS Console

AWS CLI

CloudWatch

Service-specific APIs
```

depending on the problem.

Ask:

```text
Does the resource exist?

What state is it in?

What configuration does AWS report?

Is it healthy?

Did it partially create?
```

---

# 164. Step 10: Root Cause

Do not fix until you can state:

```text
The failure occurred because...
```

Example:

```text
The EC2 creation failed because the Terraform CI role does not have ec2:RunInstances permission in the production account.
```

That is a root-cause statement.

---

# 165. Step 11: Fix

Apply the smallest correct fix.

Do not change:

```text
IAM

Provider version

Terraform version

Region

Resource configuration

State
```

all at once.

One controlled fix preserves evidence.

---

# 166. Step 12: Plan Again

Always:

```bash
terraform plan
```

after changing configuration or recovering from a failed apply.

Do not assume the original plan is still valid.

---

# 167. Step 13: Apply

After reviewing the new plan:

```bash
terraform apply
```

or apply the approved saved plan according to your workflow.

---

# 168. Step 14: Verify

Verification should happen at multiple levels.

```text
Terraform
↓
Cloud Resource
↓
Application
```

Example:

```text
terraform output
↓
aws ec2 describe-instances
↓
Application health endpoint
```

Success means more than:

```text
Apply complete!
```

# 169. Troubleshooting Matrix

| Symptom                                | Likely Investigation Area             |
| -------------------------------------- | ------------------------------------- |
| HCL parse error                        | Configuration                         |
| Unsupported argument                   | Provider schema/version               |
| Invalid variable                       | Variable input/validation             |
| Undeclared resource                    | Reference                             |
| No valid credentials                   | Authentication                        |
| AccessDenied                           | Authorization                         |
| Resource already exists                | Conflict/import/ownership             |
| Quota exceeded                         | Cloud service limits                  |
| Timeout                                | Provider/cloud/resource health        |
| Unexpected replacement                 | Plan/state/configuration              |
| Unexpected drift                       | Out-of-band changes                   |
| Resource missing from state            | Import/state/incorrect environment    |
| Resource in state but missing remotely | Drift/deletion/wrong provider context |
| Apply failed halfway                   | Partial failure                       |
| ALB unhealthy                          | Runtime/network/application           |
| SSH timeout                            | Network/SG/routing/instance           |
| Provider crash                         | Provider/plugin investigation         |

# 170. Troubleshooting Scenario: Wrong AWS Region

Symptom:

```text
Terraform says resource does not exist.
```

State contains the resource ID.

Check:

```text
Provider region.
```

If Terraform is looking in:

```text
us-east-1
```

but the resource exists in:

```text
us-west-2
```

Terraform's remote view is wrong for that resource.

Do not immediately remove it from state.

Fix the provider/region context first.

---

# 171. Troubleshooting Scenario: Wrong AWS Account

Symptom:

```text
Terraform proposes creating almost everything.
```

But production already exists.

Run:

```bash
aws sts get-caller-identity
```

You may discover:

```text
Expected:
Production account

Actual:
Development account
```

Stop.

Do not apply.

---

# 172. Troubleshooting Scenario: Existing Resource Conflict

Symptom:

```text
ResourceAlreadyExists
```

Investigation:

```text
Does resource already exist?

Who created it?

Is it in another state?

Should current Terraform own it?

Should it be imported?

Should it be referenced with a data source?
```

Ownership first.

Action second.

---

# 173. Troubleshooting Scenario: Failed Import

Symptom:

```text
Cannot import non-existent remote object
```

Check:

```text
Import ID

Region

Account

Provider alias

Resource type

Provider import documentation
```

The resource may exist, but Terraform may be looking in the wrong context.

---

# 174. Troubleshooting Scenario: Post-Import Replacement

You import EC2 successfully.

Then:

```bash
terraform plan
```

shows:

```text
must be replaced
```

Stop.

Determine which argument forces replacement.

Your written configuration may not accurately describe the existing instance.

Do not apply until the replacement is understood and intentional.

---

# 175. Troubleshooting Scenario: Manual Security-Group Change

Someone opens a port manually.

Run:

```bash
terraform plan -refresh-only
```

Observe the drift.

Then decide:

```text
Unauthorized?
→ Revert through normal Terraform configuration.

Authorized and permanent?
→ Update configuration and reconcile deliberately.
```

Do not merely refresh state and forget the configuration.

---

# 176. Troubleshooting Scenario: Partial Apply

Terraform reports:

```text
3 added, then error.
```

Check:

```bash
terraform state list
```

Then inspect AWS.

Determine which resources exist.

Fix the error.

Run:

```bash
terraform plan
```

again.

Terraform should calculate from the new current condition.

---

# 177. Troubleshooting Scenario: Expired Credentials

Symptom:

```text
ExpiredToken
```

Do not modify IAM policies.

The identity may have adequate authorization.

Its session is simply expired.

Reauthenticate using the appropriate mechanism.

Then verify:

```bash
aws sts get-caller-identity
```

and retry the plan.

---

# 178. Troubleshooting Scenario: AccessDenied

Symptom:

```text
AccessDenied
```

Do not immediately regenerate credentials.

Authentication may already be working.

Find:

```text
Identity

Denied action

Target resource

Relevant IAM controls
```

Then apply least privilege.

---

# 179. Troubleshooting Scenario: Provider Upgrade

Yesterday:

```text
terraform plan
```

worked.

Today provider version changed and validation fails.

Check:

```text
.terraform.lock.hcl

required_providers

terraform providers
```

Determine whether the provider upgrade was intentional.

Read the provider release/upgrade documentation.

Do not randomly downgrade without understanding the compatibility issue.

---

# 180. Troubleshooting Scenario: Module Test Failure

Test says:

```text
Expected production capacity = 3
Actual = 2
```

Investigate:

```text
Test variables

Module variables

Locals

Conditional logic

Resource arguments

Outputs
```

A failing test may have caught a real regression before deployment.

That is exactly what you want.

# 181. Troubleshooting Scenario: Test Leaves Resources

Integration test fails before cleanup completes.

Investigate:

```text
Test output

Terraform test state behavior

AWS resources

Tags

Credentials

Deletion permissions
```

Clean up safely.

Then improve the test environment and cleanup controls.

# 183. `versions.tf`

```hcl
terraform {
  required_version = ">= 1.7.0"

  required_providers {
    aws = {
      source = "hashicorp/aws"
    }
  }
}
```

Why 1.7+ for this lab?

Because we will demonstrate provider mocking.

For a real production repository, also establish and test an intentional AWS provider version policy rather than leaving provider selection unconstrained.

---

# 184. `variables.tf`

```hcl
variable "environment" {
  description = "Deployment environment."
  type        = string

  validation {
    condition = contains(
      ["dev", "staging", "production"],
      var.environment
    )

    error_message = "environment must be dev, staging, or production."
  }
}

variable "instance_type" {
  description = "EC2 instance type."
  type        = string
  default     = "t3.micro"
}
```

---

# 185. `locals.tf`

```hcl
locals {
  application_name = "veriqta-${var.environment}"

  common_tags = {
    Application = "veriqta"
    Environment = var.environment
    ManagedBy   = "Terraform"
  }
}
```

---

# 186. `main.tf`

For this learning project:

```hcl
resource "aws_instance" "app" {
  ami           = "ami-00000000000000000"
  instance_type = var.instance_type

  tags = merge(
    local.common_tags,
    {
      Name = local.application_name
    }
  )
}
```

The AMI value is intentionally a fake placeholder because the unit-style test will mock the AWS provider.

Do not attempt a real AWS apply with this placeholder.

# 188. `tests/application.tftest.hcl`

```hcl
mock_provider "aws" {}

run "development_configuration" {
  command = plan

  variables {
    environment   = "dev"
    instance_type = "t3.micro"
  }

  assert {
    condition     = output.application_name == "veriqta-dev"
    error_message = "Development application name is incorrect."
  }

  assert {
    condition     = output.instance_type == "t3.micro"
    error_message = "Development instance type is incorrect."
  }
}

run "production_configuration" {
  command = plan

  variables {
    environment   = "production"
    instance_type = "t3.small"
  }

  assert {
    condition     = output.application_name == "veriqta-production"
    error_message = "Production application name is incorrect."
  }

  assert {
    condition     = output.instance_type == "t3.small"
    error_message = "Production instance type is incorrect."
  }
}
```


# 200. What Each Stage Prevents

| Stage               | Main Purpose                      |
| ------------------- | --------------------------------- |
| `fmt`               | Formatting inconsistency          |
| `validate`          | Invalid Terraform configuration   |
| Variable validation | Invalid input                     |
| Provider validation | Provider-schema/config problems   |
| `test`              | Behavioral regressions            |
| Static analysis     | Structural/code-quality issues    |
| Security scan       | Known insecure configurations     |
| Policy              | Organization-rule violations      |
| Plan                | Unexpected infrastructure changes |
| Review              | Human design/change errors        |
| Apply               | Actual infrastructure convergence |
| Verification        | Runtime/deployment problems       |
| Drift detection     | Out-of-band divergence            |

No stage replaces all the others.

# 201. Beginner Mistakes

## Mistake 1

```text
terraform validate passed, so deployment will work.
```

Wrong.

Validation does not prove remote API success.

---

## Mistake 2

```text
terraform plan succeeded, so application works.
```

Wrong.

Plan does not prove runtime health.

---

## Mistake 3

```text
Import succeeded, so I can immediately apply.
```

Dangerous.

Run and review a post-import plan.

---

## Mistake 4

```text
Drift exists, so run refresh-only apply.
```

Not automatically.

First decide whether reality or configuration should win.

---

## Mistake 5

```text
Apply failed, so nothing changed.
```

Wrong.

Terraform applies can partially succeed.

---

## Mistake 6

```text
AccessDenied means credentials are invalid.
```

Not necessarily.

You may be authenticated but unauthorized.

---

## Mistake 7

```text
Timeout means resource does not exist.
```

Not necessarily.

Inspect the remote system.

---

## Mistake 8

```text
The last error is always the root cause.
```

Wrong.

Downstream failures may originate from an earlier dependency.

---

## Mistake 9

```text
TRACE logging should always be enabled.
```

Wrong.

It is noisy and potentially sensitive.

---

## Mistake 10

```text
Scanner passed, therefore infrastructure is safe.
```

Wrong.

Scanning is one layer.

```text
    ↓

└── Yes
    ↓

├── No → Fix credentials
└── Yes
    ↓
Does identity have permission?
├── No → Fix authorization using least privilege
└── Yes
    ↓
Does cloud API accept operation?
├── No → Investigate API error/quota/conflict/parameters
└── Yes
    ↓
Did resource create?
├── No → Investigate provider/cloud operation
└── Yes
    ↓
Is resource healthy?
├── No → Investigate network/runtime/application
└── Yes
    ↓
Verify complete system
```

# 216. Final Production Rules

```text
FORMAT BEFORE REVIEW

VALIDATE BEFORE PLAN

TEST IMPORTANT BEHAVIOR

SCAN BEFORE DEPLOYMENT

REVIEW THE PLAN

NEVER BLINDLY APPLY AN IMPORTED RESOURCE

TREAT GENERATED CONFIGURATION AS A STARTING POINT

EXPECT DRIFT

INVESTIGATE DRIFT BEFORE ACCEPTING IT

USE REFRESH-ONLY INSTEAD OF THE DEPRECATED REFRESH WORKFLOW

NEVER ASSUME A FAILED APPLY CHANGED NOTHING

TERRAFORM APPLY IS NOT ATOMIC

CHECK STATE AFTER PARTIAL FAILURES

CHECK REAL INFRASTRUCTURE AFTER TIMEOUTS

SEPARATE AUTHENTICATION FROM AUTHORIZATION

READ CLOUD API ERRORS

FOLLOW DEPENDENCIES UPSTREAM

USE DEBUG LOGGING ONLY WHEN NEEDED

PROTECT DEBUG LOGS

IDENTIFY ROOT CAUSE BEFORE FIXING

MAKE THE SMALLEST CORRECT FIX

PLAN AGAIN AFTER FAILURE

VERIFY AFTER APPLY
```

The goal is not merely:

```text
Terraform code that passes syntax checks.
```

The goal is:

```text
Infrastructure code whose behavior you can prove,
whose existing resources you can adopt safely,
whose drift you can detect and reconcile,
and whose failures you can investigate systematically.
```

That is the difference between writing Terraform and operating Terraform professionally.
