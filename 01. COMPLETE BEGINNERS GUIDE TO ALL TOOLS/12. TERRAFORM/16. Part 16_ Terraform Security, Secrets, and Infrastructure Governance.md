# Part 16: Terraform Security, Secrets, and Infrastructure Governance

## Treat Terraform as Privileged Production Tooling

Terraform is more than a tool for creating infrastructure.

Terraform can create, modify, and destroy:

```text
Networks
Servers
Load balancers
Databases
IAM roles
Security groups
DNS records
Storage
Encryption configuration
Logging
Monitoring
Production infrastructure
```

That means Terraform often has powerful access to your cloud environment.

If an attacker gains control of:

```text
Terraform credentials
Terraform state
Terraform CI/CD identity
Terraform dependencies
Terraform source code
```

the attacker may gain a path into your infrastructure.

The security model therefore cannot stop at:

```text
"Do not commit passwords to Git."
```

You need to secure the entire Terraform path.

---

# 1. The Security Path

This is the security architecture for this chapter:

```text
Developer
↓
Terraform Code
↓
Dependencies
↓
CI/CD Identity
↓
Terraform State
↓
Provider
↓
Cloud API
↓
Infrastructure
```

Every arrow is a trust boundary.

Every component can introduce risk.

Think of Terraform security as a chain:

```text
Developer Identity
        ↓
Source Repository
        ↓
Terraform Configuration
        ↓
Providers + Modules
        ↓
CI/CD Runner
        ↓
Cloud Credentials
        ↓
Terraform State
        ↓
Cloud Provider API
        ↓
Production Infrastructure
```

If one critical link is compromised, the infrastructure may be compromised.

---

# 2. The Terraform Security Model

Terraform does not independently create AWS infrastructure.

Terraform uses providers.

For AWS:

```text
Terraform
↓
AWS Provider
↓
AWS Credentials
↓
AWS APIs
↓
AWS Resources
```

Terraform can only perform actions that the identity used by the AWS provider is authorized to perform.

This means:

```text
Terraform capability
=
AWS identity permissions
```

If Terraform runs with:

```text
AdministratorAccess
```

then Terraform effectively has administrator-level capability.

If Terraform runs with a narrowly scoped IAM role, its capability is restricted to that role.

This is why identity design is central to Terraform security.

---

# 3. Terraform Is Privileged Tooling

Suppose Terraform can manage:

```text
IAM
VPC
Security Groups
EC2
Route 53
S3
KMS
RDS
```

Then a compromised Terraform identity could potentially:

```text
Open firewall rules

Create privileged IAM roles

Replace instances

Modify DNS

Delete infrastructure

Change encryption configuration

Read or alter sensitive infrastructure
```

Treat Terraform with the same seriousness as other privileged administrative tooling.

---

# 4. Terraform Security Has Several Layers

We will divide Terraform security into these layers:

```text
1. Human identity
2. Source-code security
3. Credential security
4. Dependency security
5. State security
6. Infrastructure security
7. CI/CD security
8. Policy enforcement
9. Security scanning
10. Change governance
```

A mature Terraform environment protects all of them.

---

# 5. Layer 1: Developer Security

Developers should not casually possess permanent credentials with unrestricted production access.

Bad model:

```text
Developer Laptop
↓
Permanent AWS Administrator Keys
↓
Production
```

Better model:

```text
Developer
↓
Authenticated Identity
↓
Temporary Role
↓
Restricted Permissions
↓
Approved Environment
```

For production, you may go further:

```text
Developer
↓
Pull Request
↓
Review
↓
CI/CD
↓
Production Deployment Role
↓
AWS
```

The developer proposes the change.

The controlled pipeline performs the production change.

---

# 6. Provider Credentials

Terraform providers need credentials to interact with remote systems.

For AWS, the AWS provider needs an AWS identity.

Credentials can come from supported AWS credential mechanisms rather than being embedded directly in Terraform configuration.

Do not write:

```hcl
provider "aws" {
  region     = "us-east-1"
  access_key = "..."
  secret_key = "..."
}
```

This creates unnecessary exposure.

Credentials may leak through:

```text
Git history

Pull requests

Code review systems

Backups

Screenshots

Logs

Developer laptops

Copied files
```

---

# 7. Better AWS Provider Configuration

A provider configuration should usually look more like:

```hcl
provider "aws" {
  region = var.aws_region
}
```

Authentication is supplied externally.

The exact method depends on the execution environment.

Examples include:

```text
AWS CLI profiles

AWS IAM Identity Center sessions

Environment variables

IAM roles

EC2 instance roles

CI/CD role assumption

OIDC federation

Temporary STS credentials
```

---

# 8. AWS Credentials

AWS credentials may include:

```text
Access key ID

Secret access key

Session token
```

Long-lived IAM user access keys are particularly sensitive because they can remain useful until revoked or expired by policy.

Temporary credentials are preferable for many modern workflows.

Temporary credentials expire.

That reduces the useful lifetime of stolen credentials.

---

# 9. Credential Lifetime

Compare:

```text
Long-Lived Credential
↓
Leaked
↓
Potentially Useful Until Revoked
```

with:

```text
Temporary Credential
↓
Leaked
↓
Expires Automatically
```

Expiration does not make temporary credentials harmless.

It reduces exposure duration.

---

# 10. Verify Your AWS Identity

Before running Terraform:

```bash
aws sts get-caller-identity
```

Inspect:

```text
Account

Arn

UserId
```

Ask:

```text
Am I in the expected AWS account?

Am I using the expected role?

Am I operating in the correct environment?
```

This simple check can prevent serious mistakes.

---

# 11. Never Guess Your Active Identity

Do not assume:

```text
"I authenticated yesterday, so this must still be the dev role."
```

Verify.

Especially before:

```text
terraform apply

terraform destroy

terraform import

terraform state rm

terraform state mv

terraform apply -replace=...
```

---

# 12. IAM Least Privilege

Least privilege means giving an identity only the permissions it needs to perform its job.

Bad:

```text
Terraform CI Role
↓
AdministratorAccess
↓
Entire AWS Account
```

Better:

```text
Terraform Network Role
↓
Required Network Permissions
```

or:

```text
Terraform Application Role
↓
Required Application Infrastructure Permissions
```

The correct boundary depends on your architecture.

---

# 13. Why Terraform Permissions Can Be Difficult

Terraform may need several API actions for a resource.

It may need to:

```text
Create

Read

Update

Delete

Tag

Describe

List
```

resources.

Therefore least privilege for Terraform is not simply:

```text
Allow Create
```

Terraform also needs enough read permissions to refresh state and build plans.

Design permissions based on actual Terraform operations.

---

# 14. Least Privilege Is Iterative

A practical process is:

```text
Define Required Infrastructure
↓
Determine Required AWS Actions
↓
Create Restricted Role
↓
Test Plan
↓
Test Apply
↓
Observe AccessDenied
↓
Determine Whether Permission Is Legitimately Required
↓
Adjust Carefully
↓
Retest
```

Do not respond to every `AccessDenied` by attaching:

```text
AdministratorAccess
```

Understand why Terraform needs the permission.

```text

```

```text
Staging Terraform Role
↓
Staging Account
```

```text
Production Terraform Role
```

# 16. Separate Roles by Responsibility

Larger organizations may also separate:


# 17. CI/CD Identities

Terraform automation requires a machine identity.

Bad architecture:

```text
Engineer creates AWS access key
↓
Copies key into CI secret
↓
CI uses same permanent key for years
```

Problems include:

```text
Long credential lifetime

Difficult rotation

Shared identity

Poor attribution

Large impact if stolen
```

A stronger approach uses temporary credentials.

---

# 18. Short-Lived Credentials

Short-lived credentials exist only for a limited period.

A CI system can:

```text
Authenticate
↓
Assume Role
↓
Receive Temporary Credentials
↓
Run Terraform
↓
Credentials Expire
```

The pipeline does not need a permanent AWS secret stored forever.

---

# 19. OIDC Concepts

OIDC means:

```text
OpenID Connect
```

In a CI/CD context, OIDC can allow a trusted CI platform to prove the identity of a workflow to AWS.

Conceptually:

```text
CI Workflow
↓
OIDC Token
↓
AWS Trust Policy
↓
AWS STS
↓
Temporary Role Credentials
↓
Terraform
```

Instead of:

```text
CI
↓
Stored Permanent AWS Access Key
```

---

# 20. OIDC Trust

OIDC does not mean:

```text
Any workflow can access AWS.
```

AWS role trust should restrict which identities can assume the role.

Depending on the CI provider, trust conditions can restrict things such as:

```text
Organization

Repository

Branch

Environment

Workflow identity
```

The exact claims and trust-policy syntax depend on your identity provider.

---

# 21. OIDC Security Model

Think:

```text
Who issued this token?

Which repository requested it?

Which workflow requested it?

Which branch or environment?

Which AWS role may it assume?

What permissions does that role have?
```

OIDC removes the need for certain long-lived credentials.

It does not remove the need for careful authorization.

---

# 22. CI/CD Identity Architecture

A production pattern might look like:

```text
Git Repository
↓

↓
Review
↓
CI Workflow
↓
OIDC
↓
AWS STS
↓
Production Terraform Role
↓
Temporary Credentials

```

The role should still follow least privilege.

# 24. Secrets in Terraform

Terraform often encounters sensitive information.

Examples:

```text
Database passwords

API keys

OAuth secrets

Tokens

Private keys

Certificates

Service credentials

Application secrets
```

You need to understand how Terraform handles these values.

---

# 25. Sensitive Variables

Terraform variables can be marked:

```hcl
variable "database_password" {
  type      = string
  sensitive = true
}
```

This tells Terraform that the value is sensitive.

Terraform will redact the value in normal CLI output where appropriate.

Instead of:

```text
password = "SuperSecretPassword"
```

you may see:

```text
(sensitive value)
```

That is useful.

But there is a critical limitation.

---

# 26. `sensitive = true` Does Not Mean "Never Stored"

This is one of the most important Terraform security lessons.

```text
sensitive = true
```

primarily controls disclosure in user interfaces and CLI output.

It does not automatically mean:

```text
Value is absent from state
```

If Terraform needs the value as part of normal managed-resource state, it can still be stored there.

Therefore:

```text
Sensitive
≠
Not Stored
```

Remember this.

---

# 27. Sensitive Variable Mental Model

```text
sensitive = true
↓
Redact from normal display
```

Not:

```text
sensitive = true
↓
Cryptographically remove value from Terraform
```

State still needs protection.

---

# 28. Sensitive Outputs

Outputs can also be marked sensitive.

Example:

```hcl
output "database_password" {
  value     = var.database_password
  sensitive = true
}
```

Terraform avoids displaying the value normally.

But again:

```text
Sensitive Output
≠
Value Automatically Removed from State
```

---

# 29. Sensitive Propagation

If an expression depends on a sensitive value, Terraform often propagates sensitivity.

Conceptually:

```text
Sensitive Variable
↓
Local
↓
Resource Argument
↓
Output
```

Terraform attempts to avoid accidentally displaying the resulting sensitive value.

But you still need secure state handling.

---

# 30. Secrets in State

Terraform state may contain:

```text
Resource attributes

Identifiers

Configuration values

Generated values

Sensitive values
```

depending on the provider and resources involved.

This makes state a potentially sensitive asset.

Treat:

```text
terraform.tfstate
```

as sensitive production data.

---

# 31. State Can Be More Sensitive Than Source Code

Your Terraform source might contain:

```hcl
password = var.database_password
```

No password is visible.

But state may contain the actual value.

Therefore:

```text
Git Repository
```

and:

```text
Terraform State
```

have different security characteristics.

State often deserves stricter access.

---

# 32. State Access Is Data Access

If a person can read Terraform state, ask:

```text
What infrastructure information can they see?

Are credentials present?

Are secrets present?

Are private addresses present?

Are resource identifiers present?

Are policy documents present?

Are database details present?
```

Do not grant state read access casually.

---

# 33. Modern Terraform: Ephemeral Values

Modern Terraform provides mechanisms for temporary values that should not persist in state or plan files.

Terraform 1.10 introduced support for ephemeral variables and related ephemeral constructs.

Example:

```hcl
variable "api_token" {
  type      = string
  sensitive = true
  ephemeral = true
}
```

An ephemeral value is available during the operation but omitted from state and plan files.

---

# 34. Sensitive vs Ephemeral

Understand the difference:

```text
sensitive = true
```

means:

```text
Hide/redact value from normal display
```

while:

```text
ephemeral = true
```

means, in supported contexts:

```text
Do not persist the value in Terraform state or plan
```

They solve different problems.

---

# 35. Sensitive + Ephemeral

For eligible temporary secrets, you may see:

```hcl
variable "api_token" {
  type      = string
  sensitive = true
  ephemeral = true
}
```

This combines:

```text
Redaction
+
Non-persistence
```

But ephemeral values have restrictions on where they can be used.

You cannot simply mark every Terraform value ephemeral.

---

# 36. Write-Only Arguments

Terraform 1.11+ supports provider-defined write-only resource arguments.

These are designed for values such as:

```text
Passwords

Tokens

API keys
```

that a provider needs during an operation but Terraform does not need to persist.

A provider may expose an argument such as:

```text
password_wo
```

with an associated version argument.

The exact write-only arguments available depend on the provider and resource.

---

# 37. Why Write-Only Arguments Matter

Traditional flow:

```text
Secret
↓
Terraform Resource Argument
↓
Provider
↓
State May Retain Value
```

Write-only flow:

```text
Secret
↓
Write-Only Argument
↓
Provider
↓
Remote API
```

without Terraform persisting that write-only value in its plan or state.

Use these capabilities where your Terraform and provider versions support them.

---

# 38. Do Not Invent Write-Only Support

Never assume:

```text
Every password argument is write-only.
```

It is not.

Check the current provider documentation.

Provider support determines whether a particular resource argument is write-only.

---

# 39. `.tfvars` Security

Terraform variable files are convenient:

```text
terraform.tfvars

production.tfvars

secret.tfvars
```

But a `.tfvars` file is still a file.

If it contains:

```hcl
database_password = "..."
api_token         = "..."
```

then the secrets exist in plaintext in that file unless another external protection is involved.

---

# 40. Dangerous `.tfvars` Pattern

```text
production.tfvars
↓
Contains Secrets
↓
Committed to Git
↓
Git History Retains Secrets
```

Deleting the file later does not automatically erase it from repository history.

Prevent the exposure in the first place.

---

# 41. `.gitignore`

A basic Terraform `.gitignore` may include:

```gitignore
.terraform/

*.tfstate
*.tfstate.*

*.tfplan

crash.log
crash.*.log

*.tfvars
*.tfvars.json
```

But there is nuance.

Some teams intentionally commit non-sensitive variable files.

For example:

```text
dev.tfvars
```

might contain only:

```text
instance_type

region

capacity

CIDR
```

and no secrets.

So do not blindly assume every `.tfvars` file must always be ignored.

Classify the contents.

---

# 42. Do Not Ignore the Lock File

Normally do not add:

```text
.terraform.lock.hcl
```

to `.gitignore`.

The dependency lock file should normally be committed.

It records selected provider versions and package checksums.

We will return to this later.

---

# 43. Environment Variables

Terraform variables can be supplied using:

```text
TF_VAR_<name>
```

Example concept:

```bash
export TF_VAR_api_token="..."
```

Terraform can then populate:

```hcl
variable "api_token" {
  type      = string
  sensitive = true
}
```

This avoids writing the secret directly into a `.tfvars` file.

But environment variables are not magically safe.

---

# 44. Environment Variable Risks

Secrets in environment variables may still be exposed through:

```text
CI configuration

Debug logging

Shell history depending on how they are set

Child processes

Process inspection in some environments

Accidental echo commands

Crash diagnostics
```

Use secure secret injection mechanisms in CI/CD systems.

Do not print secrets.

---

# 45. Environment Variables for AWS Credentials

AWS tooling commonly recognizes credential-related environment variables.

Examples include:

```text
AWS_ACCESS_KEY_ID

AWS_SECRET_ACCESS_KEY

AWS_SESSION_TOKEN

AWS_REGION
```

Temporary credentials may be injected this way during a CI run.

Do not commit these values into source code.

---

# 46. Secret Managers

A better secret architecture often separates:

```text
Infrastructure Code
```

from:

```text
Secret Value
```

Conceptually:

```text
Terraform
↓
Creates/References Secret Infrastructure

Secret Manager
↓
Stores Secret Value

Application
↓
Retrieves Secret at Runtime
```

This can reduce unnecessary secret handling by Terraform.

---

# 47. Important Secret-Manager Trap

Simply storing a secret in a secret manager does not automatically prevent Terraform from seeing or storing it.

Example concept:

```hcl
data "aws_secretsmanager_secret_version" "database" {
  secret_id = "production/database"
}
```

If Terraform reads the secret value and then uses it in a normal state-persisted argument, that value can still become part of Terraform's sensitive data path.

Therefore:

```text
Secret Manager
≠
Automatic State Exclusion
```

Design the flow carefully.

---

# 48. Better Runtime Secret Pattern

Where possible:

```text
Terraform
↓
Creates IAM Permission
↓
Creates/References Secret Identifier
↓
Application Starts
↓
Application Authenticates with IAM Role
↓
Application Retrieves Secret at Runtime
```

Terraform manages access.

The application retrieves the value.

Terraform does not necessarily need to know the plaintext secret.

---

# 49. AWS Secrets Manager

AWS Secrets Manager is purpose-built for secrets such as:

```text
Database credentials

API keys

OAuth tokens

Application credentials

Other secrets
```

It integrates with:

```text
IAM

AWS KMS

Rotation mechanisms

Auditing
```

and can support automated secret rotation for supported patterns.

---

# 50. Secrets Manager Mental Model

```text
Application
↓
IAM Role
↓
Secrets Manager API
↓
Authorized Secret
↓
Secret Value
```

The application does not need a password embedded in its Terraform source.

---

# 51. Secrets Manager Encryption

Secrets Manager encrypts secret values at rest using AWS KMS-based encryption.

Access therefore involves more than:

```text
"Can I find the secret?"
```

You need to consider:

```text
Secrets Manager permissions

KMS permissions where applicable

Resource policies

Identity policies
```

---

# 52. Secret Rotation

A major advantage of Secrets Manager is rotation capability.

Conceptually:

```text
Old Credential
↓
Rotation Process
↓
New Credential
↓
Secret Updated
↓
Application Uses New Credential
```

Rotation reduces reliance on indefinitely static secrets.

---

# 53. SSM Parameter Store

AWS Systems Manager Parameter Store stores configuration values called parameters.

Common uses include:

```text
Environment configuration

AMI IDs

Endpoints

Resource identifiers

Feature configuration

Some encrypted values
```

Parameter types include:

```text
String

StringList

SecureString
```

---

# 54. `SecureString`

For sensitive parameter values, Parameter Store supports:

```text
SecureString
```

which uses AWS KMS encryption.

Do not put sensitive information into ordinary plaintext parameter types when encryption is required.

---

# 55. Secrets Manager vs Parameter Store

A simplified mental model:

```text
Secrets Manager
→ Purpose-built secret lifecycle management
```

```text
Parameter Store
→ Configuration management with optional secure values
```

AWS recommends Secrets Manager for credentials and other secrets when you need capabilities such as:

```text
Automatic rotation

Purpose-built secret management

Cross-account secret use

Fine-grained secret auditing
```

Parameter Store is often appropriate for configuration data and simpler parameter-management use cases.

---

# 56. Do Not Turn This Into a Religious Rule

Do not say:

```text
"All sensitive values must always use Secrets Manager."
```

Architecture depends on requirements.

Ask:

```text
Does it need rotation?

Is it a credential?

Who retrieves it?

Does it need cross-account access?

What audit requirements exist?

What is the cost model?

How will it be updated?

How will applications authenticate?
```

Choose deliberately.

# 57. State Security

State is one of the most important Terraform security assets.

Protect it with:

```text
Remote storage

Encryption

Access control

Versioning

Locking

Auditability

Backup/recovery

Restricted administrative access
```

Part 14 covered backend mechanics.

Now we focus on security.

---

# 58. Local State Risk

Local state:

```text
terraform.tfstate
```

may exist on:

```text
Developer laptops

CI workspaces

Backups

File synchronization systems
```

If the machine is compromised, the state may be exposed.

Production teams generally benefit from controlled remote state.

---

# 59. Remote State Security Architecture

For AWS:

```text
Terraform
↓
Authenticated Identity
↓
S3 Backend
↓
Encrypted State Object
```

Access should be controlled using IAM and bucket policies as appropriate.

---

# 60. Backend Encryption

Your remote backend should protect state at rest.

For an S3 backend, design:

```text
S3 encryption

HTTPS/TLS transport

IAM access

Bucket policy

Versioning

Locking
```

according to your organization's requirements.

Encryption does not replace access control.

---

# 61. Encryption Is Not Authorization

Suppose the state is encrypted at rest.

But an IAM principal has:

```text
s3:GetObject
```

and any required decryption capability.

That principal may still retrieve the state.

Therefore:

```text
Encrypted
≠
Unreadable to Authorized Principal
```

You still need least-privilege access.

---

# 62. Backend Access Control

Ask:

```text
Who can read development state?

Who can modify development state?

Who can read production state?

Who can modify production state?

Can CI read production state?

Can developers directly modify it?

Can security administrators recover old versions?
```

Do not give every engineer universal state access by default.

---

# 63. Example State Access Architecture

```text
Developers
↓
Dev State

Staging CI Role
↓
Staging State

Production CI Role
↓
Production State
```

Production state may have stronger controls.

---

# 64. State Read and State Write Are Different Risks

Read access can expose:

```text
Sensitive values

Infrastructure metadata

Resource IDs

Network details
```

Write access can be even more dangerous because corrupted or malicious state may affect future Terraform behavior.

Protect both.

---

# 65. State Versioning

Enable versioning for production S3 state buckets.

Why?

Suppose:

```text
Current State
↓
Accidentally Overwritten or Corrupted
```

Versioning can provide older object versions for recovery.

Versioning is not a replacement for correct operations.

It is a recovery layer.

---

# 66. State Locking

State locking helps prevent concurrent Terraform operations from modifying the same state simultaneously.

For modern S3 backend configurations:

```hcl
terraform {
  backend "s3" {
    bucket       = "YOUR-STATE-BUCKET"
    key          = "production/platform/terraform.tfstate"
    region       = "us-east-1"
    encrypt      = true
    use_lockfile = true
  }
}
```

The backend identity needs appropriate permissions for both the state object and lock file.

---

# 67. State Security Checklist

```text
□ Remote backend

□ Encryption at rest

□ TLS in transit

□ Restricted IAM

□ Restricted bucket policy

□ State locking

□ Versioning

□ Logging/auditing where required

□ Separate production state

□ Recovery procedure

□ No state committed to Git

□ No state copied casually

□ No state printed into public CI logs
```

---

# 68. Terraform Plan Files Are Sensitive Too

Do not secure state while ignoring:

```text
tfplan
```

Saved Terraform plans may contain sensitive values.

Likewise:

```bash
terraform show -json tfplan
```

may produce JSON containing sensitive data.

Treat plan artifacts carefully.

---

# 69. Plan Artifact Security

If CI stores Terraform plans:

```text
CI
↓
Plan Artifact
```

control:

```text
Who can download it?

How long is it retained?

Is storage encrypted?

Are logs exposing values?

Can forks access it?

Can untrusted jobs retrieve it?
```

Plan files are not harmless build artifacts.

---

# 70. Provider Trust

Providers are executable plugins.

Terraform downloads provider packages and executes them.

A provider can interact with:

```text
Terraform values

Credentials

Remote APIs

Resource data
```

Therefore provider selection is a supply-chain security decision.

---

# 71. Provider Source Address

Declare explicit provider sources.

Example:

```hcl
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}
```

The exact version constraint should reflect the version your project has tested.

Do not blindly copy this example into an existing repository.

The important idea is:

```text
Explicit Source
+
Intentional Version Constraint
```

---

# 72. Provider Version Constraints

Without an intentional constraint, dependency upgrades may be less predictable.

Example:

```hcl
version = "~> 6.0"
```

means your configuration accepts versions according to that Terraform version-constraint rule.

Other examples include:

```hcl
>= 6.0
```

or:

```hcl
>= 6.0, < 7.0
```

Choose constraints deliberately.

---

# 73. Root Module vs Reusable Module Constraints

Reusable modules often declare the minimum provider version they support without unnecessarily constraining consumers.

Root modules can usually impose tighter tested constraints because they represent an actual deployable system.

The exact policy depends on your release strategy.

---

# 74. Dependency Lock File

Terraform creates:

```text
.terraform.lock.hcl
```

for dependency selections.

The lock file records selected provider versions and package checksums.

Commit it to version control.

---

# 75. Why Commit the Lock File?

Without a committed lock file:

```text
Developer A
↓
terraform init
↓
Provider Version X
```

and later:

```text
CI
↓
terraform init
↓
Provider Version Y
```

could occur if constraints permit a newer version.

With a lock file:

```text
Repository
↓
Selected Provider Version
+
Checksums
↓
Developers and CI
```

receive more consistent provider selection.

---

# 76. Lock File Is Not a Provider Allowlist by Itself

The lock file improves repeatability and integrity checking.

But you still need:

```text
Trusted provider source

Code review

Version constraints

Controlled upgrades
```

Do not treat the lock file as your entire supply-chain security program.

---

# 77. Provider Checksums

The lock file includes hashes Terraform can use to verify provider packages.

Conceptually:

```text
Provider Download
↓
Checksum Verification
↓
Expected?
├── Yes → Continue
└── No  → Error
```

This helps detect a provider package that does not match the expected recorded package hashes.

---

# 78. Provider Upgrade Workflow

Do not casually run:

```bash
terraform init -upgrade
```

against production code and immediately apply.

A safer flow is:

```text
Change Provider Constraint if Needed
↓
Run Upgrade Intentionally
↓
Review Lock File Change
↓
Read Provider Release Notes
↓
terraform validate
↓
Run Tests
↓
terraform plan
↓
Security Scan
↓
Review
↓
Test Lower Environment
↓
Promote
```

Provider upgrades are infrastructure changes.

# 81. Pinning Module Versions

For Terraform Registry modules, use intentional version constraints.

Example concept:

```hcl
module "example" {
  source  = "namespace/module/provider"
  version = "x.y.z"
}
```

For Git modules, use an intentional Git reference where appropriate.

Avoid blindly tracking mutable development branches for production infrastructure.

# 82. Important Lock-File Limitation

Terraform's dependency lock file currently tracks provider selections.

It does not lock remote module selections in the same way.

Therefore module versioning must be designed explicitly.

Do not assume:

```text
.terraform.lock.hcl
```

locks everything Terraform downloads.

```text
↓

↓
```


# 87. Policy as Code Is Not Terraform Validation

```text

```

```text

```

Those are different questions.

A configuration can be:

```text

```

```text

```

# 173. Security Troubleshooting: Backend Access Denied

Terraform cannot read state.

Check:

```text
AWS identity

S3 bucket

State key

s3:ListBucket

s3:GetObject

KMS access if relevant

Bucket policy

Organization controls
```

```text

```

# 174. Security Troubleshooting: Lock Permission Failure

Check:

```text
State object permissions

Lock-file object permissions

Bucket path

IAM conditions
```

The lock file is part of the backend security design.

# 175. Security Troubleshooting: Provider Checksum Error

Symptom:

```text
Provider package does not match recorded checksums.
```

Do not simply delete the lock file automatically.

Investigate:

```text
Was the provider intentionally upgraded?

Did platform architecture change?

Was a provider mirror introduced?

Did the lock file change?

Is the provider source correct?

Is the package trusted?
```

Checksum errors are security-relevant signals.

# 189. Final Mental Model

Do not think:

```text
Terraform Security
=
Hide Passwords
```

Think:

```text
Terraform Security
=
IDENTITY
+
CREDENTIALS
+
SECRETS
+
STATE
+
DEPENDENCIES
+
CODE
+
POLICY
+
REVIEW
+
CI/CD
+
CLOUD PERMISSIONS
+
RECOVERY
```

Terraform security starts before:

```bash
terraform plan
```

and continues after:

```bash
terraform apply
```

The complete trust path is:

```text
Developer
↓
Terraform Code
↓
Dependencies
↓
CI/CD Identity
↓
Terraform State
↓
Provider
↓
Cloud API
↓
Infrastructure
```

Every component needs protection.

The most important rules from this chapter are:

```text
DO NOT HARD-CODE CLOUD CREDENTIALS

PREFER SHORT-LIVED CREDENTIALS

USE LEAST PRIVILEGE

TREAT STATE AS SENSITIVE

UNDERSTAND THAT sensitive = true DOES NOT REMOVE VALUES FROM STATE

USE EPHEMERAL/WRITE-ONLY FEATURES WHERE SUPPORTED AND APPROPRIATE

KEEP SECRETS OUT OF GIT

PREFER RUNTIME SECRET RETRIEVAL WHERE PRACTICAL

PROTECT PLAN ARTIFACTS

TRUST PROVIDERS DELIBERATELY

TRUST MODULES DELIBERATELY

CONSTRAIN DEPENDENCIES

COMMIT THE PROVIDER LOCK FILE

SCAN TERRAFORM

SCAN FOR SECRETS

ENFORCE INFRASTRUCTURE POLICY

REVIEW THE CODE

REVIEW THE PLAN

PROTECT PRODUCTION

CONTROL DESTRUCTIVE CHANGES

VERIFY AFTER APPLY
```

The goal is not:

```text
Terraform that successfully deploys.
```

The goal is:

```text
Terraform that can be trusted to deploy production infrastructure safely.
```

That is the difference between using Terraform as a configuration tool and operating Terraform as privileged production infrastructure.
