# Part 1: Terraform Foundations and Infrastructure as Code

## Build the Mental Model Before Writing Infrastructure

Terraform becomes much easier when you understand the problem it was designed to solve.

A common beginner mistake is to start with this:

```hcl
resource "aws_instance" "example" {
  # ...
}
```

and immediately try to memorize Terraform syntax.

That is not where we are going to start.

Before writing infrastructure, you need to understand:

```text
What infrastructure is

How infrastructure was traditionally created

Why manual infrastructure becomes difficult

What Infrastructure as Code changes

What declarative infrastructure means

What desired state means

Why Terraform needs providers

What Terraform resources represent

Why Terraform maintains state

What modules are

What the Terraform Registry provides

What happens during plan

What happens during apply

Where Terraform belongs in a real engineering environment
```

Our first mental model is:

```text
Engineer
↓
Terraform Configuration
↓
Terraform CLI
↓
Provider
↓
Cloud / Service API
↓
Infrastructure
```

And the operational lifecycle we will gradually build throughout this series is:

```text
Write
↓
Initialize
↓
Plan
↓
Review
↓
Apply
↓
Infrastructure
↓
Change Configuration
↓
Plan Again
↓
Review Again
↓
Apply Again
```

By the end of Part 1, you should be able to explain this entire process without memorizing definitions.

# 3. Infrastructure Before Infrastructure as Code

Historically, infrastructure was often provisioned manually.

An engineer might:

```text
buy a physical server
↓
rack the server
↓
connect networking
↓
install an operating system
↓
configure storage
↓
configure networking
↓
install application dependencies
↓
deploy the application
```

Provisioning infrastructure could take considerable time.

Cloud computing changed much of this.

Instead of physically installing a server, an engineer could request one through a cloud platform.

For example:

```text
Engineer
↓
AWS Management Console
↓
Launch EC2 Instance
↓
Virtual Server Exists
```

This was dramatically faster.

But another problem remained.

The process could still be manual.

# 6. What Is Wrong with Clicking?

Nothing is inherently wrong with using a cloud console.

The problem appears when manual actions become the primary mechanism for managing important infrastructure.

Imagine two engineers.

Engineer A creates staging.

Engineer B creates production.

Engineer A chooses:

```text
Instance type: A
Disk size: 30 GB
Security rule: X
Tagging: Y
```

Engineer B accidentally chooses:

```text
Instance type: B
Disk size: 40 GB
Security rule: Z
Tagging: missing
```

Now:

```text
Staging
≠
Production
```

Maybe intentionally.

Maybe accidentally.

Without a defined source of configuration, it can become difficult to tell.

# 11. Infrastructure as Code

Infrastructure as Code is commonly abbreviated:

```text
IaC
```

The central idea is simple:

```text
Infrastructure configuration
is represented in machine-readable files
instead of depending primarily on manual actions.
```

Instead of only clicking:

```text
Create network
Create subnet
Create server
Create firewall rule
```

you define infrastructure in code/configuration.

Conceptually:

```hcl
resource "cloud_network" "main" {
  # desired configuration
}

resource "cloud_server" "app" {
  # desired configuration
}
```

The exact syntax is not important yet.

The mental shift is.



# 22. Declarative Thinking

A declarative approach focuses on the desired end state.

Conceptually:

```text
I want:

one VPC

two subnets

two application servers

one load balancer
```

Terraform determines how to move managed infrastructure toward that declared configuration.

You describe:

```text
WHAT
```

rather than manually scripting every low-level:

```text

```

---

# 23. Declarative Does Not Mean No Logic Exists

Terraform still has to perform operations.

Cloud APIs still require calls such as:

```text
Create
Read
Update

```

The difference is that you usually do not manually specify the complete sequence.

Terraform and its providers determine required operations based on:

```text

provider behavior
resource relationships

```

# 24. Desired State

Desired state is one of the most important concepts in Terraform.

Suppose your configuration says:

```text
Application Servers = 3
```

Your intended infrastructure is therefore:

```text
3 servers
```

If the managed infrastructure currently has:

```text
2 servers
```

Terraform can identify that the current managed state does not match the desired configuration.

Conceptually:

```text
Desired
3

Current
2

Difference
+1
```

The plan can propose the required change.

---

# 25. Desired State Mental Model

Think:

```text
Configuration
=
What I want
```

```text
State + Provider Observations
=
What Terraform knows about managed infrastructure
```

```text
Plan
=
Proposed changes needed to reconcile the difference
```

Then:

```text
Apply
=
Execute approved changes
```

This model will become more precise as we learn Terraform state.

---

# 26. Desired State Is Not Continuous Reconciliation

This distinction matters.

Terraform is declarative, but Terraform CLI is not normally a continuously running controller constantly correcting your infrastructure.

The normal model is:

```text
Run Terraform
↓
Terraform evaluates configuration/state/infrastructure
↓
Terraform proposes or performs changes
↓
Terraform exits
```

If infrastructure changes afterward, Terraform does not automatically wake up and repair it unless some external automation runs Terraform again.

This differs from continuously reconciling systems such as Kubernetes controllers.

# 29. What Is Terraform?

Terraform is an Infrastructure as Code tool created by HashiCorp.

It allows engineers to define and manage infrastructure using human-readable configuration files.

Terraform can manage infrastructure across many categories, including:

```text
cloud computing
networking
storage
DNS
Kubernetes-related resources
SaaS platforms
monitoring platforms
source-control platforms
```

Terraform is not limited to AWS.

# 30. Terraform Is Not AWS

This distinction is critical.

```text

=

```

```text
Terraform
=

```

Terraform can manage AWS through the AWS provider.

But Terraform can also interact with many other services through other providers.

# 32. Why Terraform Was Created

Cloud infrastructure created a new engineering problem.

Infrastructure became programmable through APIs.

That was powerful.

But organizations still needed a consistent way to:

```text

change infrastructure
reuse infrastructure patterns
review infrastructure changes
manage multiple providers
automate infrastructure lifecycle
```

Terraform was designed around this infrastructure-as-code problem.

# 45. What Is State?

Terraform needs to keep track of infrastructure it manages.

That tracking information is called:

```text
Terraform state
```

State is one of the most important Terraform concepts.

---

# 46. Why State Exists

Suppose your configuration contains:

```text
Server "web"
```

Terraform creates a real server.

The cloud platform might assign it an ID such as:

```text
server-123456
```

Terraform needs to remember the relationship:

```text
Terraform Resource
web
↓
Real Infrastructure Object
server-123456
```

State helps maintain this mapping.

---

# 47. State Mental Model

Think:

```text
Terraform Configuration
        ↓
     Desired
        ↓
Terraform State
        ↕
Managed Infrastructure
```

State helps Terraform understand which real objects correspond to which resource instances in your configuration.

---

# 48. State Is Important Data

A beginner might think:

```text
terraform.tfstate
=
some temporary cache
```

That is dangerous thinking.

State can contain:

```text
resource identifiers

relationships
configuration-derived values

```

Production state requires careful protection.

# 49. Do Not Casually Edit State

Do not treat Terraform state like a normal text file you should casually modify.

```text

terraform state rm
```

But state operations must be understood before they are used.

```text

+

+
```


```text

            /      |       \

```

Inputs can allow controlled variation.

# 52. Root Module

Every Terraform configuration has a root module.

The directory where Terraform is being run contains the root module configuration.

For example:

```text

├── outputs.tf
└── versions.tf
```

That configuration forms the root module.

Formatting improves consistency.

---

# 64. Step 5: Validate

Terraform provides:

```bash
terraform validate
```

This checks whether the configuration is syntactically valid and internally consistent within its validation scope.

Important:

```text
Validation success
does not mean
the infrastructure deployment will succeed.
```

Cloud permissions, quotas, invalid remote values, conflicts, and other runtime conditions can still cause failure.

---

# 65. Step 6: Plan

The command:

```bash
terraform plan
```

asks Terraform to calculate proposed infrastructure changes.

Conceptually:

```text

+
State
+

+
Infrastructure Observations
↓
Terraform
↓
Execution Plan
```

---

# 66. What a Plan Tells You

A plan may propose:

```text

update
replace
destroy
```

Before applying, the engineer should understand:

```text
What will change?

Why?

Is anything being destroyed?

Is replacement expected?

Is this the intended environment?

Are these changes safe?
```

Never develop the habit:

```text
terraform plan
↓
ignore output
↓
terraform apply
```

The plan is part of the safety workflow.

---

# 67. Step 7: Review

Terraform can calculate a plan.

Terraform does not know your business intent.

Terraform may correctly determine:

```text

```

but only your team can determine whether:

```text

```

Technical correctness and operational approval are different.

# 72. Terraform Dependency Thinking

Suppose infrastructure contains:

```text
VPC
↓
Subnet
↓
EC2 Instance
```

The subnet requires the VPC.

The EC2 instance requires the subnet.

Terraform builds relationships between resources from references and other dependency information.

This allows Terraform to determine operation ordering.

You do not normally need to write:

```text
Step 1: create VPC

Step 2: wait

Step 3: create subnet

Step 4: wait

Step 5: create instance
```

Terraform's dependency graph handles much of this.

# 74. Parallelism

If two resources do not depend on one another, Terraform may perform operations concurrently.

For example:

```text
        VPC
       /   \
      ↓     ↓
Subnet A   Subnet B
```

After the VPC exists, the two independent subnet operations may be able to proceed without waiting for each other.

This is another reason Terraform needs a resource graph rather than treating configuration as a simple top-to-bottom shell script.

# 75. File Order Is Not Infrastructure Order

A very important beginner lesson:

Terraform does not normally create resources according to the visual order of `.tf` files.

You might have:

```text

```

Terraform evaluates the configuration as a whole module and determines dependencies from references and other rules.

Do not think:

```text

```

Terraform configuration is not a sequence of shell scripts.

Terraform should no longer look like:

```text
a collection of strange .tf files
```

Think of the complete system:

```text
                    ENGINEER
                       │
                       ▼
             DESIRED INFRASTRUCTURE
                       │
                       ▼
            TERRAFORM CONFIGURATION
                       │
                       ▼
                 TERRAFORM CLI
                       │
          ┌────────────┼────────────┐
          │            │            │
          ▼            ▼            ▼
    CONFIGURATION    STATE      DEPENDENCIES
          │            │            │
          └────────────┼────────────┘
                       │
                       ▼
                      PLAN
                       │
                       ▼
                     REVIEW
                       │
                       ▼
                     APPLY
                       │
                       ▼
                    PROVIDER
                       │
                       ▼
                       API
                       │
                       ▼
              REAL INFRASTRUCTURE
```

Then infrastructure changes:

```text
Requirement Changes
↓
Configuration Changes
↓
Terraform Evaluates Difference
↓
Plan
↓
Engineer Reviews
↓
Apply
↓
Provider Calls API
↓
Infrastructure Changes
↓
State Updated
↓
Verify
```

That is the foundation of Terraform.
