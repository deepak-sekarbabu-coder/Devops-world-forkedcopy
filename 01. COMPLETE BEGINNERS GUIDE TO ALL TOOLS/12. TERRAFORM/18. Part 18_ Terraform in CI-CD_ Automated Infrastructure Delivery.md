# Part 18: Terraform in CI/CD: Automated Infrastructure Delivery

## Move Terraform from an Engineer's Laptop into Controlled Delivery Pipelines

Up to this point, you can run Terraform yourself:

```text
Engineer
↓
Terminal
↓
terraform plan
↓
terraform apply
↓
Infrastructure
```

That works for learning.

It is not enough for serious production infrastructure.

Production infrastructure needs:

```text
Review

Repeatability

Authentication

Authorization

Security scanning

Policy enforcement

Approvals

Audit trails

Controlled execution

State locking

Failure handling

Verification
```

The next step is moving Terraform into CI/CD.

Our production delivery model becomes:

```text
Git Push
↓
CI
↓
terraform fmt -check
↓
terraform init
↓
terraform validate
↓
Security Scan
↓
Policy Checks
↓
terraform plan
↓
Plan Review
↓
Approval
↓
terraform apply
↓
Infrastructure Verification
```

This chapter teaches how that system works and, more importantly, why each control exists.

---

# 1. What CI/CD Means for Terraform

CI/CD is commonly associated with application delivery.

For an application:

```text
Developer
↓
Git
↓
Build
↓
Test
↓
Package
↓
Deploy
```

Terraform changes the thing being delivered.

Instead of primarily delivering application code, Terraform delivers infrastructure changes.

```text
Engineer
↓
Terraform Code
↓
Git
↓
CI/CD
↓
Cloud API
↓
Infrastructure
```

The pipeline may create or modify:

```text
VPCs

Subnets

Security Groups

IAM roles

EC2 instances

Load balancers

DNS records

Auto Scaling Groups

Storage

Databases

Monitoring resources
```

This makes Terraform CI/CD extremely powerful.

It also makes mistakes extremely consequential.

---

# 2. Why Terraform Belongs in CI/CD

Imagine an organization where every engineer runs:

```bash
terraform apply
```

from a laptop.

Engineer A has:

```text
Terraform version A

AWS credentials A

Provider cache A

Environment variables A
```

Engineer B has:

```text
Terraform version B

AWS credentials B

Provider cache B

Environment variables B
```

Someone else may forget:

```text
terraform plan
```

and run an apply directly.

Another engineer may use the wrong AWS account.

Another may have stale credentials.

Another may apply code that was never reviewed.

The problem is not Terraform itself.

The problem is uncontrolled execution.

---

# 3. Centralize Infrastructure Delivery

A CI/CD pipeline provides a controlled execution environment.

```text
Engineers
   ↓
Git Repository
   ↓
Pull Request
   ↓
Automated Checks
   ↓
Plan
   ↓
Review
   ↓
Approval
   ↓
Controlled Runner
   ↓
AWS
```

Now the team can define:

```text
Which code can deploy

Which branch can deploy

Who can approve

Which Terraform version runs

Which provider versions run

Which AWS role is used

Which tests must pass

Which security rules must pass

Which plan is approved

Which environment may be changed
```

---

# 4. Infrastructure as Code Review

Terraform is infrastructure expressed as code.

Therefore infrastructure changes should be reviewed as code.

Instead of:

```text
Engineer opens AWS Console
↓
Changes security group
↓
Nobody reviews it
```

use:

```text
Engineer edits Terraform
↓
Creates Pull Request
↓
Team reviews code
↓
Pipeline generates plan
↓
Team reviews infrastructure effect
↓
Approved change is applied
```

This gives you two important reviews:

```text
Code Review
+
Plan Review
```

They are not the same.

---

# 5. Code Review vs Plan Review

Code review asks:

```text
Is this Terraform understandable?

Is the architecture sensible?

Are modules being used correctly?

Are variables appropriate?

Are secrets handled correctly?

Does this follow repository standards?
```

Plan review asks:

```text
What will Terraform actually do?

What will be created?

What will change?

What will be replaced?

What will be destroyed?
```

You need both.

---

# 6. A Tiny Code Change Can Have a Large Infrastructure Effect

Suppose a pull request changes:

```hcl
instance_type = "t3.micro"
```

to:

```hcl
instance_type = "t3.small"
```

That may be straightforward.

But another one-line change might alter:

```text
for_each keys

resource names

module paths

CIDR ranges

lifecycle behavior

provider aliases
```

and cause many replacements.

Therefore:

```text
Git Diff
≠
Infrastructure Effect
```

The Terraform plan shows the infrastructure effect.

# 7. Pull Requests

A strong Terraform workflow begins with a branch.

Example:

```bash
git checkout -b feature/increase-app-capacity
```

Change Terraform.

Then:

```bash
git add .
git commit -m "Increase application capacity"
git push origin feature/increase-app-capacity
```

Create a pull request.

The pull request becomes the review boundary.

# 8. Pull Request Workflow

# 9. Why Pull Requests Matter

A pull request provides:

```text
Change history

Code diff

Review comments

Automated checks

Approval record

Merge history

Commit SHA
```

That creates an auditable infrastructure change process.

# 10. Branch Protection

Without branch protection:

```text
Engineer
↓
Push directly to main
↓
Production pipeline
```

That can bypass review.

Protected branches can require controls such as:

```text
Pull requests

Required reviewers

Required CI checks

Successful Terraform validation

Successful security scanning

Successful plan generation

Up-to-date branches
```

The exact protection model depends on your Git platform.

---

# 11. Production Branch Mental Model

A common model is:

```text
Feature Branch
↓
Pull Request
↓
Checks
↓
Review
↓
Merge
↓
main
↓
Production Deployment Workflow
```

Do not treat:

```text
main
```

as simply another development branch.

In infrastructure repositories, it often represents approved desired infrastructure.

# 12. What Is a Pipeline Runner?

A runner is the machine or execution environment that runs pipeline commands.

Conceptually:

```text
CI Platform
↓
Runner
↓
Shell
↓
Terraform CLI
↓
Provider
↓
AWS API
```

The runner might be:

```text
Hosted virtual machine

Self-hosted server

Container

Kubernetes worker

Ephemeral build agent
```

---

# 13. The Runner Is Security-Sensitive

The runner may have access to:

```text
Terraform code

Terraform state

Plan files

AWS credentials

OIDC tokens

Provider binaries

Pipeline logs

Deployment permissions
```

A compromised runner can become a cloud compromise.

Treat Terraform runners as privileged systems.

---

# 14. Ephemeral Runners

Where practical, ephemeral runners are useful.

Conceptually:

```text
Job Starts
↓
Fresh Runner
↓
Execute Pipeline
↓
Job Ends
↓
Runner Destroyed
```

This reduces persistence of:

```text
Credentials

Temporary files

Plan files

Provider artifacts

Logs

Workspace data
```

But ephemeral execution also means dependencies may need downloading each time unless carefully cached.

---

# 15. Terraform Installation in CI

Your pipeline needs a Terraform CLI version.

Do not casually use:

```text
whatever Terraform version happens to be installed
```

The repository should define a compatible Terraform version.

Example:

```hcl
terraform {
  required_version = ">= 1.10, < 2.0"
}
```

Your CI tooling should install a version that satisfies that constraint.

---

# 16. Why Terraform Version Control Matters

Imagine:

```text
Laptop:
Terraform version X
```

but:

```text
CI:
Terraform version Y
```

Different versions may have different:

```text
Features

Validation behavior

State behavior

CLI behavior

Language capabilities
```

Consistency reduces surprises.

---

# 17. Verify Terraform in CI

The pipeline should be able to run:

```bash
terraform version
```

This provides useful evidence in logs.

You should know exactly which Terraform binary performed a deployment.

---

# 18. Provider Versions Matter Too

Terraform Core is only part of the system.

Remember:

```text
Terraform CLI
↓
Provider Plugin
↓
AWS API
```

Your AWS provider version can affect:

```text
Resource schemas

Arguments

Defaults

Behavior

Bug fixes

Deprecations
```

That is why provider constraints and the dependency lock file matter.

---

# 19. Commit `.terraform.lock.hcl`

For normal Terraform repositories:

```text
.terraform.lock.hcl
```

should generally be committed.

It records provider selections and checksums.

Conceptually:

```text
required_providers
↓
Version Constraints
↓
terraform init
↓
Dependency Lock File
↓
Repeatable Provider Selection
```

Do not routinely regenerate dependency choices unpredictably during every deployment.

---

# 20. `terraform init` in CI

Before Terraform can validate, plan, or apply a normal initialized working directory:

```bash
terraform init
```

is required.

In automation, commonly use:

```bash
terraform init -input=false
```

`-input=false` prevents Terraform from waiting for interactive input.

CI should not sit indefinitely waiting for a human terminal response.

---

# 21. What `terraform init` Does in CI

Initialization can prepare:

```text
Backend

Providers

Modules

Working directory metadata
```

Conceptually:

```text
Fresh Runner
↓
Repository Checkout
↓
terraform init
↓
Backend Initialized
+
Providers Installed
+
Modules Downloaded
↓
Working Directory Ready
```

---

# 22. Never Use `terraform init -upgrade` Automatically Without Intent

Normal deployment:

```bash
terraform init
```

is different from:

```bash
terraform init -upgrade
```

`-upgrade` tells Terraform to consider newer provider/module selections allowed by configured constraints rather than simply honoring existing selections where applicable.

Do not combine:

```text
Infrastructure Change
+
Unexpected Dependency Upgrade
```

unless that upgrade is deliberate and reviewed.

Dependency upgrades should be explicit changes.

---

# 23. Provider Caching

Provider binaries can be large.

Without caching:

```text
Pipeline 1
↓
Download AWS Provider

Pipeline 2
↓
Download AWS Provider Again

Pipeline 3
↓
Download AWS Provider Again
```

This consumes:

```text
Time

Bandwidth

Registry requests
```

Terraform supports provider plugin caching.

---

# 24. Terraform Plugin Cache

A Terraform CLI configuration can contain:

```hcl
plugin_cache_dir = "$HOME/.terraform.d/plugin-cache"
```

Alternatively, an environment variable can specify the cache:

```bash
export TF_PLUGIN_CACHE_DIR="$HOME/.terraform.d/plugin-cache"
```

The directory must exist.

Example:

```bash
mkdir -p "$HOME/.terraform.d/plugin-cache"
```

---

# 25. Provider Cache Mental Model

Without cache:

```text
terraform init
↓
Provider Registry
↓
Download Provider
↓
.terraform/
```

With cache:

```text
terraform init
↓
Plugin Cache
├── Found → Reuse
└── Missing → Download → Cache → Working Directory
```

---

# 26. Important Provider Cache Warning

Do not treat Terraform's plugin cache as a concurrency-safe shared database.

If many CI jobs simultaneously write to the same plugin cache, behavior can be problematic.

Design CI caching around your CI platform's supported cache mechanisms and Terraform's documented behavior.

Also remember:

```text
Cache
≠
Dependency Lock File
```

The cache improves installation efficiency.

The lock file controls dependency selection and integrity information.

---

# 27. First Pipeline Check: Formatting

CI should not normally rewrite submitted Terraform.

Instead:

```bash
terraform fmt -check -recursive
```

This asks:

```text
Is the committed Terraform already correctly formatted?
```

If not:

```text
Fail the pipeline.
```

The developer runs:

```bash
terraform fmt -recursive
```

locally and commits the corrected formatting.

---

# 28. Why `fmt -check` Instead of `fmt`

Bad CI behavior:

```text
Developer commits badly formatted code
↓
CI silently rewrites it
↓
Pipeline continues
```

Better:

```text
Developer commits badly formatted code
↓
CI reports failure
↓
Developer fixes source
↓
Correct code enters repository
```

The repository should contain the canonical source.

---

# 29. Validation

After initialization:

```bash
terraform validate
```

The pipeline should fail if the configuration is invalid.

Typical early pipeline:

```text
Checkout
↓
Install Terraform
↓
terraform fmt -check
↓
terraform init
↓
terraform validate
```

---

# 30. Tests

From Part 17, mature repositories can also run:

```bash
terraform test
```

This can validate module behavior before infrastructure deployment.

Be careful:

```text
terraform test
```

can create real infrastructure depending on test design.

Mocked or plan-based tests are different from real integration tests.

---

# 31. Security Scanning

Terraform can be valid and still insecure.

Example:

```text
Security Group
↓
SSH
↓
0.0.0.0/0
```

Terraform may accept it.

Your security controls may not.

Pipeline:

```text
terraform validate
↓
Security Scan
```

Possible tools include:

```text
tfsec

Checkov

Trivy
```

---

# 32. Example Security Commands

Depending on the tools your organization installs:

```bash
tfsec .
```

or:

```bash
checkov -d .
```

or:

```bash
trivy config .
```

Pin and manage scanner versions deliberately in real pipelines.

Do not depend blindly on an unversioned latest release.

---

# 33. Security Scan Mental Model

```text
Terraform Code
↓
Security Scanner
↓
Known Misconfiguration Rules
↓
Pass / Fail / Warning
```

Examples may include:

```text
Public storage

Unencrypted storage

Overly broad network access

Weak logging configuration

Unsafe IAM

Missing encryption

Dangerous defaults
```

---

# 34. Security Scanner Limitations

Passing a scanner does not prove:

```text
Infrastructure is secure.
```

A scanner may not understand:

```text
Business context

Runtime behavior

Novel attack paths

Organizational architecture

Application vulnerabilities

Every provider feature
```

Scanning is one control.

---

# 35. Policy Checks

Security scanning asks:

```text
Does this resemble a known security problem?
```

Policy asks:

```text
Does this infrastructure comply with our organization's rules?
```

Examples:

```text
Production resources must have Owner tags.

Only approved AWS regions are permitted.

Production storage must be encrypted.

Internet-facing SSH is forbidden.

Only approved modules may be used.

Production resources require backup settings.
```

---

# 36. Policy as Code

Instead of documenting policies only in PDFs:

```text
Policy Document
↓
Engineer remembers rule
```

organizations can encode certain rules:

```text
Terraform Change
↓
Policy Engine
↓
Evaluate
↓
Allow / Deny / Warn
```

This is Policy as Code.

The exact tool depends on the organization.

---

# 37. Automated Terraform Planning

Once checks pass:

```bash
terraform plan -input=false
```

can produce a speculative plan.

For a plan intended for later application:

```bash
terraform plan -input=false -out=tfplan
```

Now:

```text
tfplan
```

is a saved binary plan file.

---

# 38. Saved Plans

Saved plans are especially useful for controlled automation.

```text
terraform plan -out=tfplan
↓
Review
↓
Approval
↓
terraform apply tfplan
```

This connects:

```text
What was reviewed
```

to:

```text
What Terraform executes
```

more strongly than simply running a brand-new unreviewed apply plan.

---

# 39. Applying a Saved Plan

Use:

```bash
terraform apply tfplan
```

Terraform executes the saved plan without asking for an additional interactive approval.

Therefore your CI/CD system's approval gate becomes extremely important.

Conceptually:

```text
Plan
↓
Human/Policy Approval
↓
Apply Saved Plan
```

The approval should happen before the apply job receives permission to proceed.

---

# 40. Saved Plans Are Sensitive

A saved Terraform plan is not just harmless build output.

It can contain:

```text
Resource values

Infrastructure details

Sensitive configuration

Potential secret material
```

Treat plan artifacts as sensitive.

Do not:

```text
Publish them publicly

Attach them to public releases

Store them indefinitely without controls
```

---

# 41. Human-Readable Plan

You can inspect a saved plan:

```bash
terraform show tfplan
```

For machine processing:

```bash
terraform show -json tfplan
```

Be careful.

JSON plan output can expose sensitive values.

Redaction in normal human-readable output does not mean secret values are absent from underlying machine-readable artifacts.

---

# 42. Plan Artifacts

CI systems can preserve:

```text
tfplan
```

between jobs.

Example:

```text
Plan Job
↓
tfplan
↓
Protected Artifact Storage
↓
Approval
↓
Apply Job
↓
Download tfplan
↓
terraform apply tfplan
```

This requires careful artifact security.

---

# 43. Artifact Integrity

A strong design needs confidence that:

```text
Approved Plan
=
Applied Plan
```

At minimum, bind the plan to:

```text
Commit SHA

Environment

Terraform version

Provider lock file

Pipeline run
```

Do not let an arbitrary plan file be substituted after approval.

---

# 44. Pull-Request Plans

For pull requests, Terraform commonly generates a speculative plan.

```text
Pull Request
↓
Terraform Plan
↓
Reviewer Reads Plan
```

This gives reviewers infrastructure context before merge.

But remember:

```text
PR Plan
≠
Guaranteed Future Production Plan
```

---

# 45. Why PR Plans Can Become Stale

Suppose PR A generates:

```text
Plan A
```

Then another change reaches production.

Now infrastructure has changed.

The original PR plan may no longer represent the final production action.

Therefore production workflows should generate or validate the final plan against the current production state before applying.

---

# 46. Speculative vs Applyable Plans

Think:

```text
Pull Request Plan
↓
"What would this change likely do now?"
```

versus:

```text
Final Saved Deployment Plan
↓
"This is the reviewed plan intended for execution."
```

Do not confuse them.

---

# 47. Plan Review

Reviewers should inspect:

```text
Creates

Updates

Replacements

Destructions

IAM changes

Network changes

Security-group changes

DNS changes

Storage changes

Database changes

State-related changes
```

A pipeline saying:

```text
Plan succeeded
```

is not sufficient.

The content matters.

---

# 48. Destructive Change Review

Pay special attention to:

```text
destroy

replace
```

Questions:

```text
Why is this being destroyed?

Is data stored there?

Will replacement cause downtime?

Will the address change?

Will dependencies recreate?

Is this expected?

Is there a migration plan?
```

Production approval should not be a ceremonial click.

---

# 49. CI Credentials

Terraform needs permission to communicate with AWS.

Historically, teams often stored:

```text
AWS_ACCESS_KEY_ID

AWS_SECRET_ACCESS_KEY
```

as CI secrets.

That works technically.

It is generally not the preferred modern architecture for supported CI systems.

---

# 50. The Long-Lived Credential Problem

Long-lived cloud credentials create risks:

```text
Credential theft

Secret leakage

Rotation burden

Credentials forgotten in CI

Credentials copied between systems

Unclear ownership

Long exposure window
```

A better approach is temporary credentials.

---

# 51. OIDC

OpenID Connect allows a CI platform to prove its identity to AWS.

Conceptually:

```text
CI Job
↓
OIDC Token
↓
AWS IAM Trust Policy
↓
Assume IAM Role
↓
Temporary AWS Credentials
↓
Terraform
↓
AWS API
```

No permanent AWS access key needs to be stored in the CI repository secrets for this flow.

---

# 52. GitHub Actions OIDC

With GitHub Actions:

```text
GitHub Workflow
↓
GitHub OIDC Provider
↓
AWS STS
↓
IAM Role
↓
Temporary Credentials
```

The AWS account trusts GitHub's OIDC provider under specific conditions.

Those conditions are extremely important.

---

# 53. OIDC Does Not Mean Trust Every Workflow

Bad trust:

```text
Any repository
↓
Production AWS Role
```

Better trust can constrain:

```text
Organization

Repository

Branch

Environment

Audience
```

The trust policy should be as narrow as practical.

---

# 54. GitHub Workflow OIDC Permission

A GitHub Actions workflow using OIDC needs permission to request an identity token.

Conceptually:

```yaml
permissions:
  contents: read
  id-token: write
```

`id-token: write` does not itself grant AWS permissions.

It allows the workflow to request an OIDC token.

AWS still decides whether the token may assume a particular IAM role.

---

# 55. AWS Role Permissions

After successful federation:

```text
GitHub Identity
↓
Assume AWS Role
↓
Temporary Session
```

The IAM role defines what Terraform can do.

Apply least privilege.

Do not automatically give Terraform:

```text
AdministratorAccess
```

because it is convenient.

---

# 56. Plan and Apply Identities

Advanced environments may use different permissions.

For example:

```text
PR Plan Role
↓
Read-heavy / planning permissions
```

and:

```text
Production Apply Role
↓
Approved infrastructure mutation permissions
```

Exact permission design depends on the infrastructure Terraform manages.

Some providers need substantial read permissions even for planning.

Test your actual provider behavior.

---

# 57. CI/CD Identity Mental Model

```text
Human Engineer
↓
Git Identity
↓
Pull Request
↓
CI Workload Identity
↓
AWS IAM Role
↓
AWS API
```

Do not confuse:

```text
Who authored the change?
```

with:

```text
Which machine identity applied the change?
```

Both should be auditable.

---

# 58. Remote State Is Mandatory for Serious Team Automation

CI runners are often ephemeral.

If state exists only on:

```text
Runner filesystem
```

then after the job:

```text
Runner disappears
↓
State disappears
```

That is unacceptable.

CI/CD needs durable shared state.

---

# 59. Remote State Architecture

From Part 14:

```text
Engineer A ─┐
            │
Engineer B ─┼→ Remote Backend → Terraform State
            │
CI/CD ──────┘
```

Now CI and engineers operate against the same authoritative state location for that root module/environment.

---

# 60. State Access Must Be Restricted

The CI role may need access to:

```text
Read state

Write state

Acquire/release locking mechanism

Read backend metadata
```

depending on backend architecture.

State can contain sensitive information.

Backend permissions are production permissions.

---

# 61. State Locking

Terraform locking protects state from concurrent mutation when the backend supports locking.

Without locking:

```text
Pipeline A
↓
Modify Infrastructure

Pipeline B
↓
Modify Same Infrastructure
```

at the same time.

This can cause dangerous state races.

---

# 62. State Locking Is One Layer

Locking protects Terraform state operations.

But pipeline-level concurrency protection is also useful.

Think:

```text
CI Concurrency Control
+
Terraform State Lock
```

not:

```text
One replaces the other.
```

---

# 63. Concurrent Pipeline Protection

Suppose two commits reach production close together.

Bad:

```text
Commit A → Apply
                 ↘
                  Production State
                 ↗
Commit B → Apply
```

Better:

```text
Commit A
↓
Apply
↓
Complete
↓
Commit B
↓
Re-plan if required
↓
Apply
```

Serialize deployments that mutate the same Terraform state.

---

# 64. Concurrency Scope Matters

You do not necessarily need to serialize all Terraform pipelines globally.

You need to protect shared state boundaries.

Example:

```text
dev-network state
```

can potentially deploy independently from:

```text
production-application state
```

if they are genuinely independent.

Think in terms of:

```text
State Boundary
=
Concurrency Boundary
```

---

# 65. Never Solve Lock Contention with `-lock=false`

Terraform supports:

```bash
terraform plan -lock=false
```

or similar options.

Do not make this your normal CI solution.

Disabling locking when multiple actors can modify the same state is dangerous.

Fix the concurrency architecture.

---

# 66. Lock Timeout

Automation may use an intentional lock wait:

```bash
terraform plan -lock-timeout=5m
```

for example.

This tells Terraform to wait for a lock for a defined period instead of failing immediately.

Choose values appropriate to your deployment environment.

Do not use enormous waits to hide broken pipelines.

---

# 67. Production Approval

Production should generally require stronger controls than development.

Example:

```text

↓

```

Production may require:

```text

↓
Review
↓
Protected Environment
↓
```

Your risk model determines the exact policy.

# 68. Environment Protection

CI platforms can protect deployment environments.

```text

↓
production Environment
↓
```

# 69. Environment Protection and OIDC

```text

↓
AWS Trust Condition
↓

```

Now branch controls, environment controls, and AWS identity controls reinforce each other.

```text
↓

↓
Verify
```

Do not automatically assume that the old pull-request plan is still current.

The apply stage should have:


# 72. Non-Interactive Automation

CI should not depend on terminal prompts.

Common automation flags include:

```bash
terraform init -input=false
```

and:

```bash
terraform plan -input=false -out=tfplan
```

Then:

```bash
terraform apply tfplan
```

Applying a saved plan does not prompt for approval.

The CI approval gate should already have authorized execution.

---

# 73. `-auto-approve`

Terraform also supports:

```bash
terraform apply -auto-approve
```

This skips interactive approval.

That does not mean:

```text
Production no longer needs approval.
```

It means Terraform itself is not providing the human gate.

Your CI/CD system must provide the appropriate control.

For controlled production, saved-plan workflows are often easier to reason about because you can approve the actual plan artifact.

# 76. Example Pull-Request Workflow

A simplified teaching example:

```yaml

  pull_request:
    paths:
      - "environments/production/**"
      - "modules/**"

permissions:
  contents: read
  id-token: write

jobs:
  terraform:
    runs-on: ubuntu-latest

    defaults:
      run:
        working-directory: environments/production

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v5
        with:
          role-to-assume: ${{ vars.AWS_PLAN_ROLE_ARN }}
          aws-region: us-east-1

      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: "<PINNED_TERRAFORM_VERSION>"

      - name: Terraform Format
        run: terraform fmt -check -recursive

      - name: Terraform Init
        run: terraform init -input=false

      - name: Terraform Validate
        run: terraform validate

      - name: Terraform Plan
        run: terraform plan -input=false
```

Replace:

```text

```

# 80. GitHub Actions Concurrency

Concurrency controls help prevent multiple production deployments from racing.

Conceptually:

```yaml

  group: terraform-production
  cancel-in-progress: false
```

For infrastructure applies, cancellation itself needs careful consideration.

Do not casually terminate a Terraform apply merely because a newer commit arrived.

A partially interrupted infrastructure operation requires investigation.

# 81. Why `cancel-in-progress: false` Can Be Safer for Applies

Application pipelines often prefer:

```text

↓
```

Terraform is different.

```text
Created resources

Changed IAM

Modified networking

Updated state
```

Killing it can leave partial progress.

Infrastructure deployment needs more deliberate cancellation behavior.

# 95. Failure Handling


Each stage needs a different response.

---

# 96. Failure Before Apply

If:

```text
fmt fails
```

nothing should deploy.

If:

```text
validate fails
```

nothing should deploy.

If:

```text
security scan fails
```

nothing should deploy according to your policy.

If:

```text
plan fails
```

nothing should deploy.

These are safe failures because infrastructure mutation has not begun.

---

# 97. Failure During Apply

This is different.

Remember Part 17:

```text
Terraform Apply
≠
Atomic Transaction
```

Some resources may already have changed.

Pipeline:

```text
Apply Starts
↓
Resource A succeeds
↓
Resource B succeeds
↓
Resource C fails
↓
Pipeline fails
```

Do not assume infrastructure returned automatically to its previous condition.

---

# 98. Failed Apply Response

Use:

```text
Apply Failure
↓
Stop Further Automatic Deployment
↓
Read Terraform Error
↓
Inspect State
↓
Inspect AWS
↓
Determine Partial Changes
↓
Find Root Cause
↓
Fix
↓
Generate New Plan
↓
Review
↓
Apply
↓
Verify
```

Do not automatically run:

```bash
terraform destroy
```

as failure recovery.

---

# 99. Failure During Verification

Another important case:

```text
terraform apply
↓
Success
↓
Application Verification
↓
Failure
```

Terraform succeeded from an infrastructure perspective.

The application may still be unhealthy.

Examples:

```text
ALB targets unhealthy

Application service failed

DNS incorrect

TLS issue

Database connection failure

Security-group path wrong
```

Your pipeline should distinguish:

```text
Infrastructure Apply Failure
```

from:

```text
Post-Deployment Verification Failure
```

# 100. Infrastructure Verification

After apply, verify at several levels.

```text
Terraform
↓
Cloud
↓
Network
↓
Application
```

Terraform:

```bash

```

Cloud:

```bash

```

plus appropriate service-specific AWS CLI checks.

Application:

```bash
curl -f https://example.com/health
```

when appropriate.

# 101. Verification Should Be Specific

Bad:

```text

```

Better:

```text

ALB exists.

Target group reports healthy targets.

Expected application health endpoint returns success.
```

Production success is a system property.

# 107. Rollback in Application Delivery

Application rollback often looks like:

```text
Version 2 deployed
↓
Problem
↓
Redeploy Version 1
```

Example:

```text
app:v2
↓
rollback
↓
app:v1
```

Infrastructure is not always that simple.

---

# 108. Terraform Rollback Reality

Terraform has no universal:

```bash
terraform rollback
```

command that magically returns infrastructure to its previous safe condition.

Why?

Because infrastructure changes have side effects.

---

# 109. Infrastructure Is Stateful

Suppose Terraform:

```text
Deletes database
```

and later you revert Git.

The old Terraform code may say:

```text
Create database
```

But creating a new database does not automatically restore deleted data.

Therefore:

```text
Code Rollback
≠
State Rollback
≠
Data Recovery
```

---

# 110. Git Revert Is Not Infrastructure Rollback

You can revert a Terraform commit.

Example:

```bash
git revert <commit>
```

That changes desired configuration.

Then:

```bash
terraform plan
```

shows what Terraform would do.

But the result may not reconstruct the exact previous infrastructure state.

---

# 111. Example: EC2 Replacement

Change:

```text
AMI A
↓
AMI B
```

causes replacement.

You revert code to:

```text
AMI A
```

Terraform may replace the instance again.

That is a new infrastructure operation.

It is not a time machine.

---

# 112. Example: Database Destruction

Before:

```text
Database
+
Data
```

Terraform destroys it.

Reverting configuration may recreate:

```text
Database
```

but not necessarily:

```text
Original Data
```

Data recovery depends on:

```text
Backups

Snapshots

Replication

Restore procedures
```

not Git alone.

---

# 113. Example: DNS

A Terraform change modifies DNS.

Reverting Terraform can restore the previous record configuration.

But DNS clients may have cached the changed record according to TTL behavior.

Infrastructure rollback may therefore have delayed effects.

---

# 114. Example: Security Group

Terraform accidentally closes an application port.

Reverting configuration may reopen it quickly.

This is relatively reversible.

Infrastructure changes have different reversibility classes.

---

# 115. Classify Changes by Reversibility

Before production apply, consider:

```text
Easily Reversible

Replacement Required

Potential Downtime

Data-Affecting

Externally Cached

Security-Sensitive

Irreversible Without Backup
```

This improves plan review.

---

# 116. Terraform Recovery Model

Instead of assuming rollback:

```text
Failure
↓
Understand Current Reality
↓
Determine Desired Recovery State
↓
Write/Restore Correct Configuration
↓
Plan
↓
Review
↓
Apply
↓
Verify
```

Sometimes recovery means:

```text
Revert code
```

Sometimes:

```text
Forward fix
```

Sometimes:

```text
Restore backup
```

Sometimes:

```text
Import/reconcile state
```

Sometimes a combination.

---

# 117. Forward Fix

A forward fix means:

```text
Current Infrastructure
↓
New Corrective Change
↓
Desired Infrastructure
```

Instead of trying to reproduce an exact past deployment.

Forward fixes are often more appropriate when the infrastructure has already changed in ways that cannot simply be reversed.

---

# 118. Rollback Planning

For risky changes, plan recovery before apply.

Ask:

```text
What could fail?

What is reversible?

What requires replacement?

What contains data?

What backup exists?

How do we restore?

What is the expected downtime?

Who decides whether to recover or continue?
```

This is production engineering.

# 166. Final Production Rules

```text
TERRAFORM CHANGES GO THROUGH VERSION CONTROL

USE PULL REQUESTS

PROTECT PRODUCTION BRANCHES

REVIEW CODE AND PLAN

PIN AND CONTROL TOOLING

COMMIT THE DEPENDENCY LOCK FILE

USE terraform fmt -check IN CI

INITIALIZE BEFORE VALIDATION AND PLANNING

DO NOT UPGRADE PROVIDERS ACCIDENTALLY

CACHE PROVIDERS CAREFULLY

SCAN INFRASTRUCTURE CODE

ENFORCE IMPORTANT POLICIES

GENERATE PLANS BEFORE APPLY

PROTECT SAVED PLAN ARTIFACTS

REVIEW DESTRUCTIVE CHANGES

USE REMOTE STATE

KEEP STATE ACCESS RESTRICTED

KEEP STATE LOCKING ENABLED

SERIALIZE PIPELINES THAT SHARE STATE

PREFER SHORT-LIVED CLOUD CREDENTIALS

USE OIDC WHERE APPROPRIATE

NARROW OIDC TRUST CONDITIONS

USE LEAST-PRIVILEGE CI ROLES

SEPARATE ENVIRONMENT IDENTITIES

PROTECT PRODUCTION ENVIRONMENTS

DO NOT EXPOSE PRODUCTION CREDENTIALS TO UNTRUSTED PR CODE

DO NOT PRINT SECRETS

TREAT PIPELINE LOGS AS SENSITIVE

DO NOT ASSUME FAILED APPLY MEANS NOTHING CHANGED

VERIFY INFRASTRUCTURE AFTER APPLY

VERIFY APPLICATION HEALTH AFTER APPLY

INVESTIGATE DRIFT BEFORE RECONCILING IT

DO NOT TREAT GIT REVERT AS A MAGIC INFRASTRUCTURE ROLLBACK

PLAN RECOVERY BEFORE HIGH-RISK CHANGES

MAKE THE PIPELINE BORING, REPEATABLE, AND AUDITABLE
```

The final production delivery model is:

```text
Git Push
↓
CI
↓
terraform fmt -check
↓
terraform init
↓
terraform validate
↓
terraform test
↓
Security Scan
↓
Policy Checks
↓
terraform plan
↓
Plan Review
↓
Approval
↓
terraform apply
↓
Infrastructure Verification
↓
Application Verification
↓
Monitoring
```

The goal is no longer:

```text
Can I run Terraform?
```

The goal is:

```text
Can a team deliver infrastructure repeatedly,
securely,
reviewably,
with short-lived identity,
controlled state,
clear approvals,
failure recovery,
and evidence that production actually works?
```

That is Terraform infrastructure delivery.
