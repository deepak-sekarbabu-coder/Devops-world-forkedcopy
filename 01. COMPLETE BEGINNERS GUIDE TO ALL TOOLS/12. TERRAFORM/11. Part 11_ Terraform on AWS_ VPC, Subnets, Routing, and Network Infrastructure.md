# Part 11: Terraform on AWS: VPC, Subnets, Routing, and Network Infrastructure

## Start Building Substantial Cloud Infrastructure

You have reached an important transition in this Terraform series.

Until now, much of the focus has been on learning Terraform itself:

```text
Providers
Resources
Variables
Outputs
State
Dependencies
Functions
Expressions
Modules
```

Now we begin using those skills to build substantial AWS infrastructure.

The first thing we need is not an EC2 instance.

It is the network the EC2 instance will live inside.

We are going to build toward:

```text
AWS
↓
VPC
├── Public Subnet A
├── Public Subnet B
├── Private Subnet A
└── Private Subnet B
```

The networking path is:

```text
Internet
↓
Internet Gateway
↓
VPC
↓
Route Tables
↓
Public / Private Subnets
↓
Security Boundaries
```

By the end of this part, you should understand not only how to create AWS networking with Terraform, but also why each component exists, how packets move through the architecture, how to verify the network from Terraform and AWS, and how to diagnose common failures.

# 1. Before Terraform: Understand the Network

Do not begin with:

```hcl
resource "aws_vpc" ...
```

Begin with the architecture.

Imagine an application consisting of:

```text
Users
↓
Load Balancer
↓
Application Servers
↓
Database
```

You probably do not want every component directly exposed to the internet.

A more realistic design is:

```text
                    INTERNET
                        │
                        ▼
                INTERNET GATEWAY
                        │
                        ▼
              ┌───────────────────┐
              │        VPC        │
              │                   │
              │  Public Subnets   │
              │  ┌─────┐ ┌─────┐ │
              │  │ AZ A│ │ AZ B│ │
              │  └─────┘ └─────┘ │
              │                   │
              │  Private Subnets  │
              │  ┌─────┐ ┌─────┐ │
              │  │ AZ A│ │ AZ B│ │
              │  └─────┘ └─────┘ │
              │                   │
              └───────────────────┘
```

Later we can place infrastructure such as:

```text
Public Subnets
↓
Internet-facing load balancers
NAT gateways when required

Private Subnets
↓
Application servers
Internal services
Databases where appropriate
```

This separation is one of the foundations of cloud network architecture.

---

# 2. What Is Amazon VPC?

VPC means:

```text
Virtual Private Cloud
```

A VPC is a logically isolated virtual network inside AWS.

Think of it as:

```text
Your AWS Network Boundary
```

Within a VPC, you control important networking decisions including:

```text
IP address ranges
Subnets
Routing
Internet connectivity
Security boundaries
Network interfaces
Gateway connectivity
```

Mental model:

```text
AWS Region
└── VPC
    ├── Subnets
    ├── Route Tables
    ├── Internet Gateway
    ├── Security Groups
    └── Workloads
```

---

# 3. A VPC Is Regional

A VPC belongs to one AWS Region.

For example:

```text
AWS
└── us-east-1
    └── VPC
```

The VPC can span multiple Availability Zones inside that Region.

This distinction matters:

```text
Region
↓
contains Availability Zones

VPC
↓
spans Availability Zones in that Region

Subnet
↓
belongs to exactly one Availability Zone
```

Do not think of a subnet as spanning multiple Availability Zones.

It does not.

---

# 4. AWS Regions

AWS operates infrastructure in geographic areas called Regions.

Examples include:

```text
us-east-1
us-west-2
eu-west-1
```

A Region affects:

```text
latency
service availability
cost
compliance requirements
data residency
disaster-recovery strategy
```

Your Terraform AWS provider needs to know which Region it should operate in.

Example:

```hcl
provider "aws" {
  region = "us-east-1"
}
```

This means:

```text
Terraform
↓
AWS Provider
↓
AWS APIs in us-east-1
```

---

# 5. Availability Zones

A Region contains multiple Availability Zones.

Conceptually:

```text
Region
├── Availability Zone A
├── Availability Zone B
└── Availability Zone C
```

An Availability Zone represents one or more discrete data centers with independent infrastructure characteristics.

AWS designs Availability Zones to support fault isolation while providing high-bandwidth, low-latency connectivity between AZs in a Region.

For production workloads, spreading infrastructure across multiple Availability Zones helps reduce dependence on a single AZ.

# 6. Our Multi-AZ Architecture

We will design:

```text
VPC: 10.0.0.0/16

Availability Zone A
├── Public Subnet A
└── Private Subnet A

Availability Zone B
├── Public Subnet B
└── Private Subnet B
```

Example CIDRs:

```text
VPC
10.0.0.0/16

Public A
10.0.1.0/24

Public B
10.0.2.0/24

Private A
10.0.11.0/24

Private B
10.0.12.0/24
```

Architecture:

```text
                    VPC 10.0.0.0/16
                           │
              ┌────────────┴────────────┐
              │                         │
             AZ A                      AZ B
              │                         │
      ┌───────┴────────┐        ┌───────┴────────┐
      │                │        │                │
Public A          Private A   Public B       Private B
10.0.1.0/24      10.0.11/24  10.0.2.0/24   10.0.12/24
```

---

# 7. What Is CIDR?

CIDR means:

```text
Classless Inter-Domain Routing
```

You will see values such as:

```text
10.0.0.0/16
10.0.1.0/24
172.16.0.0/16
192.168.10.0/24
```

CIDR describes an IP address range.

For this chapter, the most important thing to understand is:

```text
VPC CIDR
↓
Large network range

Subnet CIDRs
↓
Smaller non-overlapping ranges
inside the VPC range
```

Example:

```text
VPC
10.0.0.0/16

contains

10.0.1.0/24
10.0.2.0/24
10.0.11.0/24
10.0.12.0/24
```

---

# 8. `/16` and `/24`

You do not need to become a network engineer before using Terraform, but you need a working understanding.

An IPv4 address contains 32 bits.

The prefix length indicates how many bits identify the network portion.

Conceptually:

```text
10.0.0.0/16
```

provides a much larger address range than:

```text
10.0.1.0/24
```

A `/16` IPv4 block contains:

```text
65,536 addresses
```

A `/24` contains:

```text
256 addresses
```

AWS reserves several addresses within each subnet, so not every address in a subnet CIDR is available for resources.

The important design lesson is:

```text
Choose a VPC CIDR large enough
for future subnet growth.
```

---

# 9. Avoid Overlapping CIDRs

Suppose:

```text
VPC A
10.0.0.0/16

VPC B
10.0.0.0/16
```

Later you want to connect them.

You now have an addressing conflict.

The same destination address could exist in both networks.

Network planning should therefore consider future:

```text
VPC peering
Transit Gateway
VPN
Direct Connect
multi-account architecture
on-premises connectivity
```

Avoid careless CIDR allocation.

---

# 10. What Is a Subnet?

A subnet is a range of IP addresses inside a VPC.

Example:

```text
VPC
10.0.0.0/16

Subnet
10.0.1.0/24
```

AWS resources such as EC2 instances are launched into subnets.

A subnet belongs entirely to one Availability Zone.

Example:

```text
Public Subnet A
10.0.1.0/24
AZ A
```

and:

```text
Public Subnet B
10.0.2.0/24
AZ B
```

---

# 11. Public vs Private Subnets

This distinction is frequently misunderstood.

A subnet is not public simply because its name contains:

```text
public
```

A subnet is public when its routing provides a path to an Internet Gateway.

For IPv4, a common public-subnet route is:

```text
Destination
0.0.0.0/0

Target
Internet Gateway
```

A private subnet does not have a direct route to the Internet Gateway.

Therefore:

```text
Subnet Name
≠
Subnet Type

Routing
=
Subnet Connectivity Behavior
```

---

# 12. Public Subnet Mental Model

```text
EC2 / Resource
↓
Public Subnet
↓
Public Route Table
↓
0.0.0.0/0
↓
Internet Gateway
↓
Internet
```

For direct IPv4 internet communication, the resource also needs an appropriate public IPv4 address or Elastic IP and security controls that permit the required traffic.

The Internet Gateway alone does not make every resource publicly reachable.

---

# 13. Private Subnet Mental Model

Without outbound internet connectivity:

```text
Private Resource
↓
Private Subnet
↓
Private Route Table
↓
No Internet Gateway Route
```

If outbound internet access is needed through a public NAT gateway:

```text
Private Resource
↓
Private Subnet
↓
Private Route Table
↓
NAT Gateway
↓
Public Subnet
↓
Internet Gateway
↓
Internet
```

The internet cannot simply initiate arbitrary connections back through the NAT gateway to private instances.

Terraform communicates with AWS using the AWS provider.

Your provider requirement might look like:

```hcl
terraform {
  required_providers {
    aws = {
      source = "hashicorp/aws"
    }
  }
}
```

Then configure it:

```hcl
provider "aws" {
  region = var.aws_region
}
```

Flow:

```text
Terraform Configuration
↓
Terraform Core
↓
AWS Provider
↓
AWS API
↓
AWS Infrastructure
```

---

# 15. Do Not Invent Provider Versions

For a real project, select a currently supported AWS provider release and define an intentional version constraint.

Example shape:

```hcl
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "<reviewed-compatible-constraint>"
    }
  }
}
```

The important production lesson is:

```text
Do not blindly copy
an old provider version
from an old tutorial.
```

Check the current provider release and compatibility requirements before pinning it.

# 16. AWS Authentication

Terraform needs authorization to call AWS APIs.

Conceptually:

```text
Terraform
↓
AWS Provider
↓
AWS Credentials
↓
AWS Identity
↓
IAM Permissions
↓
AWS API
```

Two separate questions exist:

```text
AUTHENTICATION
Who are you?

AUTHORIZATION
What are you allowed to do?
```

You may successfully authenticate but still receive:

```text
AccessDenied
```

because your identity lacks permission for an operation.

---

# 17. Never Hardcode AWS Credentials in Terraform

Do not write:

```hcl
provider "aws" {
  access_key = "..."
  secret_key = "..."
}
```

especially in committed Terraform source.

Why?

Because credentials can leak through:

```text
Git history
repositories
code review
screenshots
logs
backups
copied files
```

Use supported AWS credential mechanisms instead.

---

# 18. Common Authentication Approaches

Depending on your environment, the AWS provider can work with mechanisms such as:

```text
AWS CLI/shared configuration profiles
environment variables
IAM roles
temporary credentials
AWS IAM Identity Center workflows
workload identities in automated environments
```

For local development, you may already have AWS CLI credentials or a configured profile.

For production automation, prefer short-lived credentials and role-based access rather than long-lived static keys.

# 19. Verify AWS Identity First

Before Terraform creates anything, verify the identity you are using.

Run:

```bash
aws sts get-caller-identity
```

You should receive information conceptually like:

```json
{
  "UserId": "...",
  "Account": "...",
  "Arn": "..."
}
```

Verify:

```text
Correct AWS account?

Correct identity?

Expected role?

Expected environment?
```

This is one of the simplest ways to avoid deploying into the wrong AWS account.

# 20. Verify AWS Region

Run:

```bash
aws configure get region
```

# 22. Discover Availability Zones

Instead of hardcoding every AZ name, Terraform can query AWS.

Example:

```hcl
data "aws_availability_zones" "available" {
  state = "available"
}
```

Then:

```hcl
data.aws_availability_zones.available.names
```

returns available AZ names for the configured Region.

This combines what you learned in Part 9 with real AWS infrastructure.

# 23. Important Availability Zone Detail

Availability Zone names can be mapped differently between AWS accounts.

For example, one account's:

```text
us-east-1a
```

does not necessarily represent the same physical AZ as another account's `us-east-1a`.

For advanced cross-account architecture, AWS Availability Zone IDs provide a more consistent identity.

For this beginner project, we will use available AZ names from the current account.

# 27. Use Common Tags

Instead of repeating:

```hcl
Environment = var.environment
Project     = var.project_name
ManagedBy   = "Terraform"
```

everywhere, define:

```hcl
locals {
  common_tags = {
    Environment = var.environment
    Project     = var.project_name
    ManagedBy   = "Terraform"
  }
}
```

Then:

```hcl
tags = merge(
  local.common_tags,
  {
    Name = "${var.project_name}-${var.environment}-vpc"
  }
)
```

This improves consistency.

# 28. Create Public Subnet A

```hcl
resource "aws_subnet" "public_a" {
```

```text

↓
```

# 35. What an Internet Gateway Does

An Internet Gateway provides a VPC routing target for internet-routable traffic.

It is:

```text
managed by AWS
horizontally scaled
redundant
highly available
```

You do not:

```text
patch it
SSH into it
size an EC2 instance for it
```

AWS operates it.

---

# 36. Attaching an Internet Gateway Is Not Enough

This:

```text
Internet
↓
Internet Gateway
↓
VPC
```

does not automatically mean:

```text
Every subnet has internet access.
```

Routing still determines where traffic goes.

You need:

```text
Public Subnet
↓
Route Table
↓
0.0.0.0/0
↓
Internet Gateway
```

---

# 37. Route Tables

A route table contains routing rules.

Each rule answers:

```text
If traffic is going to DESTINATION,
send it to TARGET.
```

Example:

```text
Destination       Target

10.0.0.0/16       local
0.0.0.0/0         igw-...
```

Interpretation:

```text
Traffic for VPC network
↓
stay local

Everything else
↓
Internet Gateway
```

---

# 38. Local Route

AWS automatically adds a local route for the VPC CIDR.

For:

```text
10.0.0.0/16
```

you will see conceptually:

```text
Destination       Target

10.0.0.0/16       local
```

This enables communication between appropriate resources inside the VPC, subject to security controls and routing behavior.

You do not normally create this local route yourself.

---

# 39. Create Public Route Table

```hcl
resource "aws_route_table" "public" {
  vpc_id = aws_vpc.main.id

  tags = merge(
    local.common_tags,
    {
      Name = "${var.project_name}-${var.environment}-public-rt"
    }
  )
}
```

At this point, it exists.

But it does not yet have our internet route.

---

# 40. Create Internet Route

```hcl
resource "aws_route" "public_internet" {
  route_table_id         = aws_route_table.public.id
  destination_cidr_block = "0.0.0.0/0"
  gateway_id             = aws_internet_gateway.main.id
}
```

Read it literally:

```text
For destination:

0.0.0.0/0

send traffic to:

Internet Gateway
```

`0.0.0.0/0` effectively means:

```text
all IPv4 destinations
not matched by a more specific route
```

---

# 41. Route Specificity

AWS routing uses the most specific matching route.

Suppose:

```text
10.0.0.0/16 → local
0.0.0.0/0   → Internet Gateway
```

Traffic for:

```text
10.0.12.20
```

matches the VPC-local route more specifically.

Traffic for:

```text
8.8.8.8
```

matches:

```text
0.0.0.0/0
```

and therefore uses the Internet Gateway route.

---

# 42. Route-Table Associations

Creating a route table does not automatically make a particular subnet use it.

You associate them.

Public A:

```hcl
resource "aws_route_table_association" "public_a" {
  subnet_id      = aws_subnet.public_a.id
  route_table_id = aws_route_table.public.id
}
```

Public B:

```hcl
resource "aws_route_table_association" "public_b" {
  subnet_id      = aws_subnet.public_b.id
  route_table_id = aws_route_table.public.id
}
```

Now:

```text
Public A ─┐
          ├── Public Route Table
Public B ─┘
               │
               ▼
          Internet Gateway
```

---

# 43. Why Explicit Associations Matter

Every subnet must use a route table.

If you do not explicitly associate a subnet with a custom route table, AWS uses the VPC's main route table.

Relying accidentally on the main route table can make network behavior harder to reason about.

A clear infrastructure design explicitly associates subnets with the intended route tables.

---

# 44. Private Route Table

Create:

```hcl
resource "aws_route_table" "private" {
  vpc_id = aws_vpc.main.id

  tags = merge(
    local.common_tags,
    {
      Name = "${var.project_name}-${var.environment}-private-rt"
    }
  )
}
```

Initially, it contains the VPC local route.

We deliberately do not add:

```text
0.0.0.0/0 → Internet Gateway
```

because then it would not behave as the private routing design we intend.

---

```hcl
resource "aws_route_table_association" "private_a" {
  subnet_id      = aws_subnet.private_a.id
  route_table_id = aws_route_table.private.id
}

  subnet_id      = aws_subnet.private_b.id
```

Architecture:

```text
Private A ─┐
           ├── Private Route Table
Private B ─┘
```

With no default route to an Internet Gateway, these subnets do not have direct internet routing.

# 47. What Makes Our Public Subnets Public?

Three important pieces work together:

```text
1. Route to Internet Gateway

2. Public IPv4 addressing for resources that need direct IPv4 internet access

3. Security rules allowing the intended traffic
```

Therefore:

```text
Public Subnet
≠
Everything Inside Is Publicly Reachable
```

That distinction matters.

---

# 48. Public IPv4 Addressing

An EC2 instance normally has a private IP address inside the VPC.

For direct IPv4 communication with the internet through an Internet Gateway, it also needs a public IPv4 address or Elastic IP.

Conceptually:

```text
Internet
↓
Public IPv4 Address
↓
Internet Gateway translation
↓
Private IPv4 Address
↓
EC2 Network Interface
```

---

# 49. Automatic Public IP Assignment

For public subnets:

```hcl
map_public_ip_on_launch = true
```

can enable automatic public IPv4 assignment for supported launches into that subnet.

For private subnets:

```hcl
map_public_ip_on_launch = false
```

is appropriate for our architecture.

Do not use public IP assignment as your only definition of subnet public/private status.

Routing is fundamental.

---

# 50. Elastic IP Addresses

An Elastic IP address is a static public IPv4 address allocated to your AWS account for supported uses.

Conceptually:

```text
AWS Account
↓
Elastic IP Allocation
↓
Association with supported resource
```

Elastic IPs are often used where a stable public IPv4 address is required.

One important example is a public NAT Gateway.

---

# 51. NAT Gateway Concept

Suppose private EC2 instances need to:

```text
download OS updates

install packages

call external APIs

reach public repositories
```

You may want:

```text
Outbound internet access
```

without:

```text
direct unsolicited inbound internet access
```

A public NAT Gateway can provide that IPv4 egress path.

---

# 52. NAT Architecture

```text
Private Instance
↓
Private Subnet
↓
Private Route Table
↓
0.0.0.0/0 → NAT Gateway
↓
NAT Gateway in Public Subnet
↓
Public Route Table
↓
Internet Gateway
↓
Internet
```

Return traffic flows back through the NAT translation to the initiating private resource.

---

# 53. NAT Gateway Must Be Properly Positioned

For a public NAT Gateway used for internet egress:

```text
NAT Gateway
↓
Public Subnet
↓
Route Table with Internet Gateway route
```

The NAT Gateway also uses an Elastic IP.

Architecture:

```text
Private Workload
↓
NAT Gateway
↓
Elastic IP
↓
Internet Gateway
↓
Internet
```

# 55. We Will Not Create NAT Gateways in the Default Beginner Lab

Why?

Cost.

NAT Gateways are billable resources.

For learning the fundamental routing model, we can first create:

```text

```

without creating NAT Gateways.

This lets you understand private subnet isolation without unnecessarily leaving billable NAT infrastructure running.

---

# 56. Production NAT Design

For production multi-AZ systems where private workloads require NAT-based internet egress, a common resilient design is:

```text
AZ A
Public A
└── NAT Gateway A

Private A
└── route → NAT A


AZ B
Public B
└── NAT Gateway B

Private B
└── route → NAT B
```

Architecture:

```text
Private A → NAT A → IGW
Private B → NAT B → IGW
```

This reduces cross-AZ dependency for outbound connectivity.

---

# 57. Why Not One NAT Gateway for Everything?

You technically can route private subnets in multiple AZs through one NAT Gateway.

But consider:

```text
Private A ─┐
           ├── NAT A
Private B ─┘
```

If NAT A's Availability Zone becomes unavailable, private workloads in the other AZ that depend on it can lose that egress path.

Cross-AZ routing can also have cost implications.

For resilient production designs, AWS recommends NAT gateways in each active AZ when NAT-based egress is required.

---

# 58. NAT Is Not Automatically Required

Do not think:

```text
Private Subnet
=
Must Have NAT Gateway
```

Some private workloads may not require general internet access.

Other architectures may use:

```text
VPC endpoints
private service connectivity
proxies
centralized egress
other network architectures
```

Always design according to requirements.

---

# 59. Security Groups

Routing determines:

```text
Where can packets go?
```

Security Groups help determine:

```text
Which traffic is allowed
to and from associated resources?
```

Security Groups are stateful virtual firewalls associated with supported AWS resources, especially network interfaces.

They contain:

```text
Inbound rules
Outbound rules
```

---

# 60. Inbound Rules

Inbound rules control traffic arriving at the protected resource.

Example concept:

```text
Allow HTTPS
TCP
Port 443
From approved source
```

Terraform resources and syntax can vary with provider design and version, so always verify the currently supported AWS provider pattern.

A conceptual security rule is:

```text
Protocol: TCP
Port: 443
Source: approved CIDR or another Security Group
```

---

# 61. Outbound Rules

Outbound rules control traffic leaving resources associated with the Security Group.

Example:

```text
Application Server
↓
HTTPS
↓
External API
```

The outbound rules must allow the required traffic.

Do not treat:

```text
allow all outbound
```

as a universal security law.

It may be appropriate in some environments and inappropriate in others.

---

# 62. Security Groups Are Stateful

If an inbound connection is allowed, response traffic is automatically allowed through the stateful Security Group mechanism.

This differs from stateless packet filtering models.

You will explore security architecture more deeply as we add EC2 and load balancers.

---

# 63. Create a Basic Application Security Group

For this network lab:

```hcl
resource "aws_security_group" "application" {
  name        = "${var.project_name}-${var.environment}-application-sg"
  description = "Security group for application workloads"
  vpc_id      = aws_vpc.main.id

  tags = merge(
    local.common_tags,
    {
      Name = "${var.project_name}-${var.environment}-application-sg"

  )

```

---

# 64. Avoid Dangerous Beginner Rules

You may see tutorials use:

```text
0.0.0.0/0
```

for:

```text
SSH
RDP
databases
administrative ports
```

without explanation.

Do not learn that habit.

For example:

```text
SSH 22
from 0.0.0.0/0
```

means:

```text
Attempted SSH traffic can come
from anywhere on the IPv4 internet.
```

That may be inappropriate and risky.

Use the smallest source range or, preferably, architecture-specific access mechanism that satisfies the requirement.

# 65. Security Boundary Architecture

Later we may build:

```text
Internet
↓
Load Balancer Security Group
↓
Application Security Group
↓
Application
```

Instead of:

```text
Internet
↓
Application directly
```

That allows us to express relationships such as:

```text
Only load balancer traffic
can reach application port.
```

That is stronger than opening application ports globally.

# 67. Multi-AZ Design

Our architecture:

```text
                 REGION
                   │
         ┌─────────┴─────────┐
         │                   │
        AZ A                AZ B
         │                   │
    ┌────┴────┐         ┌────┴────┐
    │         │         │         │
```

```text

+
```

# 147. Security Groups vs Network ACLs

Security Groups and Network ACLs are different mechanisms.

At a high level:

```text
Security Groups
↓
resource/network-interface-oriented
stateful
allow rules
```

```text
Network ACLs
↓
subnet boundary
stateless
allow and deny rules
```

We are not deeply configuring NACLs in this chapter.

Do not modify default NACL behavior casually before understanding the implications.


Verify Internet Gateway:

```text
What traffic must leave?
```

# 156. Final Architecture

The network you now understand is:

```text
                              INTERNET
                                  │
                                  ▼
                         INTERNET GATEWAY
                                  │
                                  ▼
                    ┌────────────────────────┐
                    │          VPC           │
                    │      10.0.0.0/16       │
                    │                        │
             ┌──────┴──────┐          ┌──────┴──────┐
             │    AZ A     │          │    AZ B     │
             │             │          │             │
             │ Public A    │          │ Public B    │
             │10.0.1.0/24  │          │10.0.2.0/24  │
             │      │      │          │      │      │
             │ Private A   │          │ Private B   │
             │10.0.11.0/24 │          │10.0.12.0/24 │
             └─────────────┘          └─────────────┘
```

Routing:

```text
PUBLIC SUBNETS

Public A ─┐
          ├── Public Route Table
Public B ─┘
               │
               ├── VPC CIDR → local
               │
               └── 0.0.0.0/0 → Internet Gateway
```

Private routing in the base lab:

```text
PRIVATE SUBNETS

Private A ─┐
           ├── Private Route Table
Private B ─┘
                │
                └── VPC CIDR → local
```

Optional production-style NAT architecture:

```text
AZ A

Private A
↓
Private Route Table A
↓
NAT Gateway A
↓
Public A
↓
Internet Gateway


AZ B

Private B
↓
Private Route Table B
↓
NAT Gateway B
↓
Public B
↓
Internet Gateway
```

The full mental model is:

```text
AWS REGION
↓
VPC
↓
CIDR ADDRESS SPACE
↓
AVAILABILITY ZONES
↓
SUBNETS
↓
ROUTE TABLE ASSOCIATIONS
↓
ROUTES
↓
GATEWAYS
↓
SECURITY BOUNDARIES
↓
WORKLOADS
```

And for Terraform:

```text
Variables
↓
AWS Provider
↓
VPC
↓
Subnets
↓
Internet Gateway
↓
Route Tables
↓
Routes
↓
Associations
↓
Security Groups
↓
Outputs
↓
Verification
```

The networking principle to remember is:

```text
A RESOURCE CAN COMMUNICATE
ONLY WHEN THE COMPLETE PATH WORKS.
```

That path may involve:

```text
Addressing
+
Subnet
+
Routing
+
Gateway
+
Security Controls
+
Destination
+
Application
```

If one layer is wrong, communication can fail.

```text

```
