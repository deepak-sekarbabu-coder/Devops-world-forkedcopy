# Part 14: Remote State, Backends, Locking, and Team Collaboration

## Move Beyond Local Terraform State

In Part 7, you learned one of Terraform's most important concepts:

```text
Configuration
     ↓
   State
     ↕
Real Infrastructure
```

Terraform state is how Terraform remembers the relationship between your configuration and the infrastructure it manages.

So far, however, we have mostly treated state as something belonging to one engineer working from one computer.

That stops being sufficient when Terraform becomes a team tool.

Imagine this:

```text
Engineer A
│
├── Terraform Configuration
└── terraform.tfstate
```

That can work for a personal lab.

Now add another engineer:

```text
Engineer A
└── terraform.tfstate

Engineer B
└── ???
```

Which state is correct?

Now add CI/CD:

```text
Engineer A
Engineer B
CI/CD Pipeline
```

All three may need to manage the same infrastructure.

You need:

```text
Engineer A ─┐
            │
Engineer B ─┼──→ Remote Backend ──→ Terraform State
            │
CI/CD ──────┘
```

And once multiple actors can access the same state, you also need to think about:

```text
Storage
+
Access Control
+
Encryption
+
Locking
+
Backups
+
Versioning
+
State Isolation
+
Recovery
+
Concurrent Operations
+
Team Workflow
```

That is what Part 14 is about.

---

# 1. The Problem We Are Solving

Imagine Anne creates production infrastructure:

```text
VPC
↓
Subnets
↓
ALB
↓
Auto Scaling Group
↓
EC2
```

Terraform records those resources in:

```text
terraform.tfstate
```

The state exists on Anne's laptop.

Another engineer clones the repository.

They receive:

```text
main.tf
variables.tf
outputs.tf
modules/
```

But correctly, Git does not contain:

```text
terraform.tfstate
```

The second engineer therefore does not automatically possess the state Terraform needs for that managed infrastructure.

We need a shared state location.

---

# 2. Local State Mental Model

By default, Terraform uses the local backend.

Conceptually:

```text
Terraform CLI
↓
Local Backend
↓
terraform.tfstate
↓
Your Computer
```

No explicit backend block is required for this default behavior.

---

# 3. What Is the Local Backend?

The local backend stores Terraform state on the local filesystem.

Typical structure:

```text
terraform-project/
├── main.tf
├── variables.tf
├── outputs.tf
├── terraform.tfstate
└── terraform.tfstate.backup
```

Terraform can also use local filesystem locking mechanisms for local state.

For one engineer learning Terraform, this is convenient.

For a team managing shared infrastructure, it creates serious limitations.

---

# 4. Why Local State Is Convenient

Local state requires almost no setup.

You can:

```bash
terraform init
terraform plan
terraform apply
```

and Terraform manages state locally.

Advantages for learning include:

```text
Simple

No remote storage required

No additional cloud resources

Easy to inspect

Easy to understand
```

That is why we started there.

---

# 5. Why Local State Becomes Dangerous for Teams

Suppose:

```text
Engineer A
↓
terraform.tfstate
```

and:

```text
Engineer B
↓
terraform.tfstate
```

now exist independently.

Engineer A applies:

```text
Create ALB
```

Her state changes.

Engineer B's local copy does not automatically know about that state update.

Now Engineer B runs Terraform using stale or separate state.

You have lost the idea of:

```text
One authoritative state
```

---

# 6. Problems With Local State in Team Environments

Local state creates problems around:

```text
Sharing

Consistency

Concurrent operations

Access control

Backup

Recovery

Automation

Security

Auditability

Availability
```

The central question becomes:

> Where is the authoritative Terraform state?

For teams, the answer should generally not be:

```text
Someone's laptop
```

---

# 7. Never Solve This by Committing State to Git

A beginner may think:

```text
Engineer A
↓
Git
↓
Engineer B
```

therefore:

```text
Commit terraform.tfstate
```

Do not use Git as a substitute for a proper Terraform state backend.

State can contain sensitive infrastructure information.

Git also does not provide Terraform's backend locking semantics.

You could create:

```text
Engineer A applies
↓
State changes

Engineer B applies
↓
State changes

Git merge conflict
```

Terraform state is not a normal collaborative source file.

---

# 8. What Is a Terraform Backend?

A backend determines where Terraform stores state and, depending on the backend, how Terraform coordinates access to that state.

Mental model:

```text
Terraform CLI
↓
Backend
↓
State Storage
```

The backend is not the AWS provider.

These are different responsibilities.

---

# 9. Provider vs Backend

Do not confuse:

```text
AWS Provider
```

with:

```text
S3 Backend
```

The AWS provider manages AWS infrastructure resources.

```text
Terraform
↓
AWS Provider
↓
AWS APIs
↓
VPC / EC2 / ALB / IAM
```

The S3 backend stores Terraform state.

```text
Terraform
↓
S3 Backend
↓
S3 Bucket
↓
Terraform State
```

They solve completely different problems.

---

# 10. Provider and Backend Together

A Terraform run might therefore look like:

```text
                    ┌──→ S3 Backend
                    │      ↓
Terraform CLI ──────┤   State File
                    │
                    └──→ AWS Provider
                           ↓
                        AWS APIs
                           ↓
                     Infrastructure
```

Terraform uses the backend to remember.

Terraform uses the provider to manage.

---

# 11. Backend Responsibilities

Depending on backend type and capabilities, a backend can provide:

```text
State storage

Remote state access

State locking

Team collaboration support

Authentication integration
```

Not every backend supports every feature.

Always check the documentation for the backend you use.

---

# 12. Backend Configuration

A backend is declared inside:

```hcl
terraform {
}
```

Example:

```hcl
terraform {
  backend "s3" {
    bucket       = "veriqta-terraform-state"
    key          = "production/network/terraform.tfstate"
    region       = "us-east-1"
    use_lockfile = true
    encrypt      = true
  }
}
```

This tells Terraform:

```text
Backend Type
=
S3
```

and:

```text
State Location
=
s3://veriqta-terraform-state/production/network/terraform.tfstate
```

Conceptually.

---

# 13. Important Backend Configuration Limitation

Backend configuration is processed very early.

You cannot write:

```hcl
variable "state_bucket" {
  type = string
}

terraform {
  backend "s3" {
    bucket = var.state_bucket
  }
}
```

Backend blocks cannot use normal Terraform named values such as:

```text
Input variables

Locals

Data sources

Resource attributes
```

This surprises many beginners.

---

# 14. Why Backend Configuration Is Special

Terraform needs to know:

```text
Where is my state?
```

before it can perform normal evaluation against that state.

Conceptually:

```text
Start Terraform
↓
Initialize Backend
↓
Locate State
↓
Initialize Providers/Modules
↓
Evaluate Infrastructure
```

The backend therefore exists at a special initialization layer.

---

# 15. Partial Backend Configuration

You do not need to hardcode every backend setting directly into the Terraform source.

For example:

```hcl
terraform {
  backend "s3" {}
}
```

Then initialization can supply configuration separately.

Example:

```bash
terraform init \
  -backend-config="bucket=veriqta-terraform-state" \
  -backend-config="key=production/network/terraform.tfstate" \
  -backend-config="region=us-east-1" \
  -backend-config="use_lockfile=true"
```

Or use a backend configuration file.

---

# 16. Backend Configuration File

Example:

```text
backend/
├── dev.s3.tfbackend
├── staging.s3.tfbackend
└── prod.s3.tfbackend
```

Example `prod.s3.tfbackend`:

```hcl
bucket       = "veriqta-terraform-state"
key          = "production/network/terraform.tfstate"
region       = "us-east-1"
use_lockfile = true
encrypt      = true
```

Initialize with:

```bash
terraform init \
  -backend-config=backend/prod.s3.tfbackend
```

---

# 17. Do Not Put Backend Credentials in Backend Files

Avoid:

```hcl
access_key = "..."
secret_key = "..."
```

in files.

Prefer AWS authentication mechanisms such as:

```text
Environment credentials

AWS shared configuration

IAM roles

AWS IAM Identity Center

Short-lived credentials

OIDC for CI/CD

AssumeRole
```

Backend configuration can be persisted into Terraform's working data, so secrets should not be casually embedded there.

---

# 18. What Is Remote State?

Remote state means the authoritative state is stored somewhere other than the engineer's ordinary local state file.

Conceptually:

```text
Engineer Laptop
↓
Terraform
↓
Remote Backend
↓
Authoritative State
```

Another engineer uses:

```text
Engineer B
↓
Terraform
↓
Same Remote Backend
↓
Same Authoritative State
```

CI/CD can use:

```text
Pipeline
↓
Terraform
↓
Same Remote Backend
↓
Same Authoritative State
```

Now everyone coordinates around the same state.

---

# 19. Remote State Architecture

```text
Engineer A ───────┐
                  │
Engineer B ───────┼────→ Remote Backend
                  │             │
CI/CD Pipeline ───┘             │
                                ▼
                         Terraform State
                                │
                                ▼
                        Managed Resources
```

This is the architecture to remember.

---

# 20. Remote State Does Not Mean Public State

"Remote" means:

```text
Not ordinary local-only state
```

It does not mean:

```text
Publicly accessible
```

Production state should be tightly protected.

---

# 21. Why S3?

For AWS-based Terraform environments, Amazon S3 is a common backend choice.

Architecture:

```text
Terraform
↓
S3 Backend
↓
S3 Bucket
↓
State Object
```

Example:

```text
Bucket:
veriqta-terraform-state

Key:
production/network/terraform.tfstate
```

---

# 22. S3 Backend Mental Model

```text
S3 Bucket
│
└── production/
    └── network/
        └── terraform.tfstate
```

The bucket is the storage container.

The key identifies the state object's path.

---

# 23. S3 Backend Configuration

Example:

```hcl
terraform {
  backend "s3" {
    bucket       = "veriqta-terraform-state"
    key          = "production/platform/terraform.tfstate"
    region       = "us-east-1"
    use_lockfile = true
    encrypt      = true
  }
}
```

Read this line by line.

---

# 24. `bucket`

```hcl
bucket = "veriqta-terraform-state"
```

This identifies the S3 bucket containing state.

S3 bucket names must be globally unique.

Your real bucket name may therefore include organizational or account-specific naming.

Example:

```text
veriqta-123456789012-tfstate
```

---

# 25. `key`

```hcl
key = "production/platform/terraform.tfstate"
```

This identifies the state object's path inside the bucket.

Think:

```text
Bucket
↓
production/
↓
platform/
↓
terraform.tfstate
```

The key is extremely important because it helps determine:

```text
Which infrastructure stack does this state represent?
```

---

# 26. `region`

```hcl
region = "us-east-1"
```

This identifies the AWS Region where the backend bucket exists.

Do not assume the backend bucket must be in the same region as every infrastructure resource managed by the configuration.

Backend location and resource location are separate concerns.

---

# 27. `encrypt`

```hcl
encrypt = true
```

enables S3 server-side encryption behavior supported by the backend configuration.

State deserves encryption because state may contain sensitive information.

---

# 28. Encryption Is Not Access Control

Encryption answers:

```text
How is stored data protected cryptographically?
```

IAM answers:

```text
Who can access it?
```

You need both.

```text
Encryption
+
Access Control
```

not one or the other.

---

# 29. State Encryption With AWS KMS

The S3 backend can also use an AWS KMS key.

Conceptual example:

```hcl
terraform {
  backend "s3" {
    bucket       = "veriqta-terraform-state"
    key          = "production/platform/terraform.tfstate"
    region       = "us-east-1"
    encrypt      = true
    kms_key_id   = "arn:aws:kms:us-east-1:123456789012:key/..."
    use_lockfile = true
  }
}
```

If you configure a KMS key, Terraform's identity also needs the necessary KMS permissions.

That may include operations such as:

```text
kms:Encrypt

kms:Decrypt

kms:GenerateDataKey
```

depending on the operation and configuration.

---

# 30. Modern S3 State Locking

Modern Terraform S3 backends support S3-based state locking.

Enable it with:

```hcl
use_lockfile = true
```

This is an important change from older Terraform tutorials.

---

# 31. The Old DynamoDB Pattern

You may find tutorials showing:

```text
S3
+
DynamoDB
```

where:

```text
S3
=
State Storage
```

and:

```text
DynamoDB
=
State Locking
```

That was a widely used architecture.

Modern Terraform supports S3 lockfile-based locking directly.

DynamoDB-based S3 backend locking is deprecated.

Do not teach the older DynamoDB design as the preferred modern architecture.

---

# 32. Modern Architecture

Use:

```text
Terraform
↓
S3 Backend
├── State Object
└── Lock File
```

with:

```hcl
use_lockfile = true
```

instead of automatically building:

```text
Terraform
├── S3 State
└── DynamoDB Lock Table
```

for a new deployment.

---

# 33. Why State Locking Exists

Imagine:

```text
Engineer A
↓
terraform apply
```

at the same time:

```text
Engineer B
↓
terraform apply
```

Both operate on:

```text
Same State
```

Without coordination, you risk conflicting state writes.

Locking provides:

```text
One state-changing operation at a time
```

for the same state, when supported and enabled.

---

# 34. Locking Mental Model

```text
Engineer A
↓
Acquire Lock
↓
Read State
↓
Apply Changes
↓
Write State
↓
Release Lock
```

Meanwhile:

```text
Engineer B
↓
Attempts Lock
↓
Lock Already Held
↓
Wait / Fail According to Command Behavior
```

Engineer B should not simply start writing to the same state.

---

# 35. Locking Protects State

State locking primarily protects against:

```text
Concurrent writers
```

It does not magically prevent:

```text
Bad Terraform code

Wrong resource deletion

Incorrect IAM permissions

Unsafe architecture

Poor plan review
```

Locking solves one specific coordination problem.

---

# 36. Lock File

With:

```hcl
use_lockfile = true
```

the S3 backend uses a lock file associated with the state.

If the state key is:

```text
production/platform/terraform.tfstate
```

the lock file is associated with that state path and uses the `.tflock` form expected by the backend.

Your IAM policy must therefore account for both:

```text
State object
```

and:

```text
Lock object
```

---

# 37. S3 Permissions for State

For a basic S3 backend without workspaces, Terraform commonly needs permissions including:

```text
s3:ListBucket
```

on the appropriate bucket scope, and:

```text
s3:GetObject

s3:PutObject
```

for the state object.

Terraform does not require `s3:DeleteObject` merely to manage the normal state object.

---

# 38. S3 Permissions for the Lock File

When:

```hcl
use_lockfile = true
```

Terraform needs appropriate permissions for the lock object.

These include:

```text
s3:GetObject

s3:PutObject

s3:DeleteObject
```

on the lock file.

The lock needs to be created, inspected, and removed as operations acquire and release it.

---

# 39. Least-Privilege State Access

Do not grant:

```text
s3:*
```

on:

```text
*
```

simply because Terraform needs state.

Instead think:

```text
Terraform Production Role
↓
Specific State Bucket
↓
Specific State Prefix/Object
↓
Required Actions Only
```

This is especially important for production state.

---

# 40. State IAM Architecture

```text
Engineer
↓
Assume Terraform Role
↓
IAM Policy
↓
S3 State Bucket
├── Read State
├── Write State
└── Manage Lock File
```

CI/CD should use an appropriately scoped role as well.

---

# 41. State Read Access Is Sensitive

A dangerous assumption is:

```text
Read-only state access is harmless.
```

Not necessarily.

State may contain:

```text
Resource identifiers

Infrastructure addresses

Configuration values

Potential secrets

Database information

Service endpoints

Other sensitive attributes
```

Treat state read access as privileged.

---

# 42. State Write Access Is Even More Powerful

A user able to write Terraform state can affect Terraform's understanding of infrastructure ownership.

State write access should therefore be highly controlled.

Ask:

```text
Who can read production state?

Who can write production state?

Who can acquire/release locks?

Who can run production applies?

Who can restore old versions?
```

These are governance questions.

---

# 43. Bucket Security

A production state bucket should normally consider:

```text
Block Public Access

Encryption

Versioning

Least-privilege IAM

Restricted bucket policy

Logging/auditing where required

Recovery procedures

Lifecycle decisions
```

State should never intentionally be public.

---

# 44. Enable S3 Versioning

Versioning is one of the most important protections for an S3 state bucket.

Conceptually:

```text
terraform.tfstate
├── Version 1
├── Version 2
├── Version 3
└── Version 4
```

If the current object is accidentally overwritten or damaged, older versions may help recovery.

HashiCorp strongly recommends bucket versioning for S3 state recovery.

---

# 45. Versioning Is Not the Same as Terraform State Serial

Do not confuse:

```text
S3 Object Versioning
```

with:

```text
Terraform State Serial
```

S3 versioning keeps historical object versions.

Terraform's state serial is part of Terraform's own state snapshot consistency model.

Different concepts.

---

# 46. State Backup Strategy

A production state strategy may include:

```text
S3 Versioning

Controlled state pulls for emergency backup

Bucket protection

Documented restore procedure

Access auditing

Cross-account or organizational backup strategy where required
```

Do not wait for a state incident before deciding how recovery works.

---

# 47. Remote State Is Still Critical Data

A remote backend does not make state disposable.

Wrong mental model:

```text
It's in S3.
We can always regenerate it.
```

Better:

```text
State is critical control-plane data.
Protect it.
```

---

# 48. Backend Bootstrap Problem

Now we encounter an interesting question.

You want Terraform to use:

```text
S3 Bucket
```

for state.

But you also want Terraform to create:

```text
S3 Bucket
```

How can Terraform use the bucket before the bucket exists?

This is the backend bootstrap problem.

---

# 49. Circular Bootstrap Problem

Imagine:

```hcl
terraform {
  backend "s3" {
    bucket = "veriqta-terraform-state"
  }
}

resource "aws_s3_bucket" "state" {
  bucket = "veriqta-terraform-state"
}
```

Terraform needs the backend during initialization.

But the resource is created only after initialization and planning/applying.

Conceptually:

```text
Need Backend
↓
Backend Bucket Does Not Exist
↓
Need Terraform Apply
↓
Terraform Apply Needs Initialized Backend
```

That is the bootstrap problem.

---

# 50. Common Bootstrap Solution

Use a small separate bootstrap process.

For example:

```text
bootstrap/
└── Terraform configuration
    ↓
Creates
    ↓
State S3 Bucket
```

Initially, bootstrap state may itself be local or managed through an organizational provisioning process.

After the bucket exists:

```text
main infrastructure
↓
S3 Backend
↓
Remote State
```

---

# 51. Bootstrap Architecture

```text
BOOTSTRAP LAYER
↓
Create State Bucket
↓
Enable Versioning
↓
Configure Encryption
↓
Configure Security
↓
State Backend Ready
```

Then:

```text
APPLICATION INFRASTRUCTURE
↓
Uses Remote Backend
↓
Stores State in Bootstrap-Created Bucket
```

---

# 52. Keep Bootstrap Small

The bootstrap layer should not become:

```text
Everything in AWS
```

Its purpose is to create foundational state infrastructure and related prerequisites.

Keep its responsibility narrow and well documented.

---

# 53. Example Bootstrap Project

```text
terraform-bootstrap/
├── versions.tf
├── providers.tf
├── variables.tf
├── state-bucket.tf
├── outputs.tf
└── README.md
```

Its job might be:

```text
Create S3 state bucket

Enable versioning

Configure encryption

Block public access

Apply appropriate bucket policy
```

Then the main infrastructure consumes that backend.

---

# 54. State Naming

State paths should be deliberate.

Bad:

```text
state.tfstate
```

for everything.

Better:

```text
production/network/terraform.tfstate
```

or:

```text
production/platform/terraform.tfstate
```

or:

```text
dev/application/terraform.tfstate
```

The path should communicate ownership and scope.

---

# 55. State Naming Mental Model

A useful pattern is:

```text
Environment
/
System or Stack
/
terraform.tfstate
```

Example:

```text
dev/network/terraform.tfstate

dev/application/terraform.tfstate

staging/network/terraform.tfstate

staging/application/terraform.tfstate

production/network/terraform.tfstate

production/application/terraform.tfstate
```

---

# 56. State Isolation

Do not put unrelated infrastructure into one giant state without considering blast radius.

Imagine:

```text
ONE STATE
├── Production VPC
├── Production Database
├── Production Kubernetes
├── Production DNS
├── Development VPC
├── Development Database
├── Security Tooling
└── Shared Services
```

One state operation now touches a huge ownership boundary.

---

# 57. Why State Isolation Matters

State boundaries affect:

```text
Blast radius

Access control

Lock contention

Team ownership

Deployment frequency

Failure impact

Recovery

Plan size

Operational independence
```

State architecture is part of infrastructure architecture.

---

# 58. Environment State Separation

Development and production should not accidentally share one state.

Bad:

```text
terraform.tfstate
├── Dev Resources
└── Prod Resources
```

Better:

```text
Dev State
↓
Dev Resources
```

and:

```text
Prod State
↓
Prod Resources
```

---

# 59. Example Environment Separation

```text
S3 Bucket
│
├── dev/
│   ├── network/
│   │   └── terraform.tfstate
│   └── application/
│       └── terraform.tfstate
│
├── staging/
│   ├── network/
│   │   └── terraform.tfstate
│   └── application/
│       └── terraform.tfstate
│
└── production/
    ├── network/
    │   └── terraform.tfstate
    └── application/
        └── terraform.tfstate
```

Each state has a distinct purpose.

---

# 60. Separate AWS Accounts

Mature organizations often also isolate environments using AWS accounts.

Example:

```text
AWS Organization
├── Development Account
├── Staging Account
└── Production Account
```

Then Terraform identities can be scoped accordingly.

This gives stronger isolation than merely changing variable files.

---

# 61. State Separation Is Not Just File Organization

These:

```text
dev.tfvars

prod.tfvars
```

do not automatically mean:

```text
Separate State
```

If both runs use the same backend key:

```text
production/platform/terraform.tfstate
```

they still use the same state.

Always reason separately about:

```text
Configuration Variables
```

and:

```text
State Location
```

---

# 62. State Identity Checklist

Before running Terraform, know:

```text
Which environment am I in?

Which AWS account am I targeting?

Which AWS region am I targeting?

Which backend bucket am I using?

Which backend key am I using?

Which state will this operation modify?
```

If you cannot answer those questions, do not run a production apply.

# 63. Migrating Local State to S3

Suppose you currently have:

```text
terraform.tfstate
```

locally.

You add:

```hcl
terraform {
  backend "s3" {
    bucket       = "veriqta-terraform-state"
    key          = "production/platform/terraform.tfstate"
    region       = "us-east-1"
    use_lockfile = true
    encrypt      = true
  }
}
```

Terraform detects that backend configuration has changed during initialization.

---

# 64. Backend Migration

Use:

```bash
terraform init -migrate-state
```

when intentionally migrating existing state to the newly configured backend.

Conceptually:

```text
Local State
↓
terraform init -migrate-state
↓
S3 Backend
↓
Remote State
```

The objective is:

```text
Move the existing state
```

not:

```text
Create a new empty state and forget the infrastructure
```

---

# 65. Before Migrating State

Do not immediately type the migration command.

First:

```text
1. Verify current state

2. Back up current state

3. Verify backend bucket

4. Verify backend permissions

5. Verify target key

6. Verify encryption

7. Verify versioning

8. Verify locking configuration

9. Ensure no one else is running Terraform

10. Review migration plan
```

State migration deserves change-control discipline.

---

# 66. Safe Migration Lab

Start from an existing disposable local-state project.

Verify:

```bash
terraform state list
```

Create an emergency backup:

```bash
terraform state pull > pre-migration-state.json
```

Protect that file because it contains state data.

Then add the S3 backend configuration.

Run:

```bash
terraform init -migrate-state
```

Follow Terraform's migration prompts carefully.

---

# 67. Verify Migration

After migration:

```bash
terraform state list
```

should still show the managed resources.

Then:

```bash
terraform plan
```

Ideally, if nothing else changed:

```text
No infrastructure changes
```

This is an important verification.

---

# 68. Verify the S3 Object

Use AWS CLI:

```bash
aws s3api head-object \
  --bucket <STATE_BUCKET> \
  --key production/platform/terraform.tfstate
```

Or inspect the bucket through the AWS Console.

Verify:

```text
Object exists

Expected key

Encryption

Versioning on bucket

Correct access
```

Do not casually download and distribute production state.

---

# 69. Backend Reconfiguration

Sometimes the backend configuration changes, but you do not intend to migrate state.

Terraform provides:

```bash
terraform init -reconfigure
```

This tells Terraform to disregard previously initialized backend configuration and initialize using the new configuration.

---

# 70. `-migrate-state` vs `-reconfigure`

Think:

```text
-migrate-state
=
Backend changed AND move existing state
```

```text
-reconfigure
=
Forget cached backend initialization and initialize backend configuration again
```

These are not interchangeable intentions.

---

# 71. Dangerous Reconfiguration Scenario

Suppose the old backend is:

```text
production/platform/terraform.tfstate
```

You accidentally reconfigure to:

```text
production/platform-new/terraform.tfstate
```

which is empty.

Terraform may now see:

```text
Configuration
+
Empty State
```

and conclude:

```text
Resources need creation
```

even though real infrastructure already exists.

That can be extremely dangerous.

---

# 72. Backend Change Verification

After any backend change, always run:

```bash
terraform state list
```

then:

```bash
terraform plan
```

If Terraform suddenly proposes creating your entire environment again:

```text
STOP
```

Do not apply.

Investigate state location first.

---

# 73. Wrong-State Symptom

One of the most important Terraform incident patterns is:

```text
Expected:
No changes

Actual:
Plan wants to create 87 resources
```

Possible cause:

```text
Wrong state
```

Check:

```text
Backend bucket

Backend key

Workspace

Environment

AWS account

State contents
```

before changing configuration.

---

# 74. Concurrent Terraform Runs

Now imagine:

```text
Engineer A
↓
terraform apply
```

while CI/CD starts:

```text
CI
↓
terraform apply
```

against the same state.

Without proper locking:

```text
Two writers
↓
Potential conflicting state operations
```

With locking:

```text
First writer
↓
Lock

Second writer
↓
Cannot acquire lock
```

This is why locking is essential for collaborative state.

---

# 75. Lock Acquisition

For operations that can write state, Terraform automatically attempts state locking when the backend supports and enables it.

You normally do not manually create the lock.

Terraform manages:

```text
Acquire
↓
Operate
↓
Release
```

---

# 76. Lock Failure

You may encounter an error indicating Terraform could not acquire the state lock.

Possible causes include:

```text
Another engineer is applying

CI/CD is running

Previous process crashed

Network interruption

Permissions problem

Stale lock

Backend problem
```

Do not immediately force-unlock.

First determine why the lock exists.

---

# 77. Correct Lock Investigation

Ask:

```text
Is another Terraform process running?

Is CI/CD currently applying?

Did someone's terminal disconnect?

Did a previous Terraform process crash?

Is the lock actually stale?

Do I recognize the lock owner?

Is the backend reachable?

Does IAM allow lock operations?
```

Only then decide what to do.

---

# 78. Lock Timeout

Some Terraform commands support waiting for a lock using:

```bash
-lock-timeout=<duration>
```

Example:

```bash
terraform apply -lock-timeout=5m
```

This can be useful when another legitimate operation is expected to finish shortly.

Waiting is often safer than trying to override coordination.

---

# 79. Do Not Normalize `-lock=false`

Terraform commands may support:

```bash
-lock=false
```

But disabling locking is not a normal solution to lock contention.

Bad workflow:

```text
Lock error
↓
Use -lock=false
↓
Run anyway
```

You just removed the protection that told you another writer may exist.

---

# 80. Force Unlock

Terraform provides:

```bash
terraform force-unlock <LOCK_ID>
```

This manually removes a Terraform state lock.

It exists for situations where automatic unlocking failed and the lock is genuinely stale.

---

# 81. Why Force Unlock Is Dangerous

Suppose Engineer A is genuinely still running:

```text
terraform apply
```

Engineer B sees the lock and runs:

```bash
terraform force-unlock <LOCK_ID>
```

Now Engineer B starts another apply.

You may have:

```text
Engineer A
↓
Writing State

Engineer B
↓
Writing Same State
```

The lock existed to prevent exactly this.

---

# 82. Rule for Force Unlock

Use force unlock only when you have established that:

```text
The lock is stale
```

and:

```text
No active Terraform process legitimately owns it
```

HashiCorp specifically warns against unlocking state held by another active process.

---

# 83. Lock ID

Terraform requires the unique lock ID for force unlock.

Example:

```bash
terraform force-unlock 12345678-abcd-...
```

The ID helps ensure you target the intended lock.

Do not treat it as permission to bypass investigation.

---

# 84. Lock Failure Troubleshooting Flow

```text

↓
Identify Lock Owner
↓
Check Human Runs
↓
Check CI/CD
↓
Check Previous Failure
↓
Confirm Whether Active
├── Active
│   ↓
│   Wait
│
└── Stale
    ↓

    ↓
```

```text
├── Previous Version
├── Older Version
└── Older Version
```

You may be able to recover a previous known-good state version.


# 89. Why Restoring Old State Can Be Dangerous

Suppose:

```text
State Version 10
```

was created Monday.

Tuesday Terraform created:

```text

```

and wrote:

```text
State Version 11
```

If you restore Version 10 blindly:

```text

```

but:

```text

```

Your state and infrastructure diverge.

Recovery requires reasoning, not just file restoration.

```bash

```


```text

```

Secure it accordingly.

# 91. `terraform state push`

Terraform also provides:

```bash
terraform state push
```

This can overwrite remote state.

This is a high-risk recovery tool.

Do not use it as a routine workflow.

---

# 92. Why `state push` Is Dangerous

You are effectively saying:

```text

```

If the snapshot is stale or wrong:

```text
Terraform's understanding
≠
Infrastructure reality
```

Terraform includes some safeguards involving state lineage and serial, but manual state push remains a dangerous operation.

Prefer:

```text

↓

↓

↓
Plan
↓

```

over:

```text

```

# 94. Remote State Data

Now we reach a different meaning of "remote state."

Suppose you intentionally split infrastructure:

```text
Network Stack
↓
network/terraform.tfstate
```

and:

```text
Application Stack
↓
application/terraform.tfstate
```

The application needs:

```text
VPC ID

Private Subnet IDs
```

from the network stack.

How can one Terraform configuration consume selected information from another state?

---

# 95. `terraform_remote_state`

Terraform provides the built-in:

```text
terraform_remote_state
```

data source.

Example:

```hcl
data "terraform_remote_state" "network" {
  backend = "s3"

  config = {
    bucket = "veriqta-terraform-state"
    key    = "production/network/terraform.tfstate"
    region = "us-east-1"
  }
}
```

Then another configuration can consume root outputs.

---

# 96. Network Outputs

The network stack might expose:

```hcl
output "vpc_id" {
  value = aws_vpc.main.id
}

output "private_subnet_ids" {
  value = [
    aws_subnet.private_a.id,
    aws_subnet.private_b.id
  ]
}
```

These are root module outputs.

---

# 97. Application Consumption

The application stack can use:

```hcl
data.terraform_remote_state.network.outputs.vpc_id
```

and:

```hcl
data.terraform_remote_state.network.outputs.private_subnet_ids
```

Conceptually:

```text
Network State
↓
Root Outputs
↓
terraform_remote_state
↓
Application Configuration
```

---

# 98. Cross-Stack Dependency

Architecture:

```text
NETWORK STACK
├── VPC
├── Subnets
└── Routes
       │
       ▼
Network State
       │
       ▼
Root Outputs
       │
       ▼
APPLICATION STACK
├── ALB
├── ASG
└── EC2
```

This lets us separate state while still sharing required information.

---

# 99. Root Outputs Only

`terraform_remote_state` exposes:

```text
Root module outputs
```

If a child module contains:

```hcl
output "vpc_id" {
  value = aws_vpc.main.id
}
```

but the root module does not expose it, another stack cannot simply consume it as a root remote-state output.

The root must explicitly output the value.

---

# 100. Remote State Data Security Warning

This is extremely important.

You may expose only:

```text
vpc_id
```

through an output.

But a principal using `terraform_remote_state` must generally have access to the underlying state snapshot.

That state may contain far more information than the output itself.

Therefore:

```text
terraform_remote_state
```

is convenient, but it creates a security coupling.

---

# 101. Do Not Assume Output-Level Access Control

Wrong mental model:

```text
Application team can read only vpc_id.
```

If access is implemented through raw state access, the underlying credentials may permit reading the entire state object.

The output interface does not automatically make the underlying state file non-sensitive.

---

# 102. Alternative Cross-Stack Sharing

For some architectures, it is better to publish selected values to a separate system.

Examples might include:

```text
AWS Systems Manager Parameter Store

DNS

Service discovery

Secrets systems for appropriate secrets

Other purpose-built configuration stores
```

Then consumers can receive only what they need.

Conceptually:

```text
Network Stack
↓
Publish VPC/Subnet Information
↓
Controlled External Store
↓
Application Stack
```

This can reduce direct state-sharing permissions.

---

# 103. State Coupling

Cross-stack remote state introduces dependency:

```text
Application
↓
depends on
↓
Network State Output Contract
```

If network engineers rename:

```hcl
output "private_subnet_ids"
```

the application configuration may break.

Treat shared outputs like an interface.

---

# 104. Output Contract

Good shared outputs should be:

```text
Intentional

Documented

Stable

Minimal

Non-sensitive where possible

Owned
```

Do not expose fifty internal implementation details simply because another state can read them.


State isolation should improve architecture, not create hundreds of tiny unmanaged fragments.

# 169. Troubleshooting Matrix

| Symptom                                | Likely Area     | Investigate                              |
| -------------------------------------- | --------------- | ---------------------------------------- |
| Backend initialization fails           | Backend config  | Bucket, region, credentials              |
| Access denied reading state            | IAM             | `GetObject`, bucket policy, role         |
| Access denied writing state            | IAM             | `PutObject`, KMS permissions             |
| Cannot acquire lock                    | Locking         | Active run, lock permissions, stale lock |
| Cannot delete lock                     | IAM             | Lock object's `DeleteObject` permission  |
| Terraform wants to recreate everything | Wrong state     | Bucket, key, workspace, migration        |
| State disappears after backend change  | Reconfiguration | Correct backend identity                 |
| Remote state output missing            | Output contract | Root output exists?                      |
| Consumer cannot read remote state      | Permissions     | State object access                      |
| State cannot decrypt                   | Encryption      | KMS permissions/key                      |
| State overwritten                      | Recovery        | S3 versions/backups                      |
| Apply succeeded but state write failed | Backend failure | Preserve emergency state, stop writes    |
| CI and engineer collide                | Workflow        | Same state, locking, apply ownership     |

```text
            │             │             │
         Engineer      Engineer        CI/CD
            │             │             │
            └─────────────┼─────────────┘
                          │
                          ▼
                    REMOTE BACKEND
                          │
                 ┌────────┼────────┐
                 │        │        │
                 ▼        ▼        ▼
               STATE    LOCK    VERSIONS
                 │
                 ▼
              TERRAFORM
                 │
                 ▼
           INFRASTRUCTURE
```

The rule to remember is:

```text
REMOTE
does not automatically mean
SAFE.
```

Production state needs:

```text
REMOTE STORAGE
+
ENCRYPTION
+
LEAST-PRIVILEGE ACCESS
+
LOCKING
+
VERSIONING
+
BACKUPS
+
STATE ISOLATION
+
RECOVERY PROCEDURES
+
CONTROLLED TEAM WORKFLOWS
```

And for a modern AWS S3 backend:

```text
S3
↓
State Storage
+
S3 Lock File
+
Bucket Versioning
+
Encryption
+
IAM
```

is the core model.

Do not automatically add DynamoDB because an old tutorial tells you to.

For new S3 backend designs, understand the modern locking model:

```hcl
use_lockfile = true
```

Most importantly:

```text
Terraform State
=
Critical Infrastructure Control Data
```

Treat it with the same seriousness you give production infrastructure.
