# 1. What Is Amazon EC2?

EC2 means:

```text
Elastic Compute Cloud
```

Amazon EC2 provides virtual compute instances in AWS.

A simple mental model is:

```text
Physical AWS Infrastructure
↓
AWS Virtualization Platform
↓
EC2 Instance
↓
```

An EC2 instance can run workloads such as:


Terraform can create, configure, modify, replace, and destroy these instances.

# 4. What Is an AMI?

AMI means:

```text
Amazon Machine Image
```

An AMI is a template used to launch EC2 instances.

It can define the starting environment, including:

```text
Operating system
Root-volume snapshot information
Architecture
Boot configuration
Image metadata
```

Examples include images for:

```text
Amazon Linux
Ubuntu
Red Hat Enterprise Linux
Windows Server
Custom organizational images
```

Conceptually:

```text
AMI
↓
Launch
↓
EC2 Instance
```

---

# 5. AMI Is Not the Running Instance

Do not confuse:

```text
AMI
```

with:

```text
EC2 Instance
```

The AMI is the starting image.

The instance is the running compute resource created from that image.

Mental model:

```text
AMI
=
Template

EC2
=
Running instance created from template
```

---

# 6. AMIs Are Regional

AMI IDs are Region-specific.

An AMI ID valid in:

```text
us-east-1
```

should not be assumed to represent the same image in:

```text
us-west-2
```

This is one reason blindly hardcoding an AMI ID copied from a tutorial can fail.

---

# 7. Why Hardcoded AMI IDs Become a Problem

You might see:

```hcl
ami = "ami-0123456789abcdef0"
```

That could work today in one Region.

But later:

```text
The AMI may be deprecated

A newer patched image may exist

The ID may not exist in another Region

The architecture may not match

The owner may not be who you expect
```

For appropriate workloads, Terraform data sources can discover images dynamically.

---

# 8. AMI Data Sources

Terraform can query AWS for an AMI.

Conceptually:

```text
Terraform
↓
AWS Provider
↓
Describe Images API
↓
Filters
↓
Matching AMIs
↓
Selected AMI ID
↓
EC2
```

This is another real use of Part 9's data-source concepts.

---

# 9. Example AMI Lookup

A common pattern is:

```hcl
data "aws_ami" "application" {
  most_recent = true

  owners = ["<TRUSTED_OWNER_ID>"]

  filter {
    name   = "name"
    values = ["<EXPECTED_IMAGE_NAME_PATTERN>"]
  }

  filter {
    name   = "architecture"
    values = ["x86_64"]
  }

  filter {
    name   = "virtualization-type"
    values = ["hvm"]
  }

  filter {
    name   = "root-device-type"
    values = ["ebs"]
  }
}
```

Then:

```hcl
ami = data.aws_ami.application.id
```

The exact image owner and name pattern should be taken from the operating-system publisher's current documentation rather than guessed.

---

# 10. Why Filter by Owner?

Suppose you search only by:

```text
ubuntu*
```

or another broad image name.

Someone else could publish an image with a similar name.

A stronger lookup includes:

```text
Trusted owner
+
Expected name pattern
+
Architecture
+
Virtualization type
+
Other required characteristics
```

Do not choose an AMI based only on a friendly-looking name.

---

# 11. `most_recent = true`

This tells Terraform to select the most recent image matching the filters.

That is convenient, but understand the trade-off.

If a newer AMI appears:

```text
Data-source result changes
↓
AMI argument can change
↓
Terraform may propose replacing the instance
```

Therefore:

```text
Latest matching image
```

and:

```text
Perfectly reproducible deployment
```

are not always the same goal.



# 18. Place the Instance in a Subnet

Example:

```hcl
subnet_id = aws_subnet.private_a.id
```

```text
VPC
↓
Private Subnet A

```

---

# 19. Public vs Private EC2 Instances

A public instance typically has:

```text
Subnet with route to Internet Gateway
+
Public IPv4 address or Elastic IP
+
Security rules allowing intended inbound traffic
```

A private instance typically has:

```text
Private IP
+
No direct public IPv4 exposure
+
No direct route from its subnet to Internet Gateway
```

Private instances may still have outbound connectivity through architectures such as:

```text
NAT Gateway
VPC endpoints
Proxy
Centralized egress
```

---

# 20. Public Does Not Mean Automatically Reachable

Suppose an instance has:

```text
Public IPv4 address
```

but its Security Group blocks SSH.

You still cannot SSH to it.

Or suppose:

```text
Security Group allows SSH
```

but there is no route to an Internet Gateway.

You still cannot reach it from the internet.

Connectivity requires the complete path.

---

# 21. Public Instance Connectivity Path

```text
Administrator
↓
Internet
↓
Public IPv4 / Elastic IP
↓
Internet Gateway
↓
Public Route Table
↓
Public Subnet
↓
Security Group
↓
EC2 Network Interface
↓
SSH Service
```

If SSH fails, investigate this path.

Do not immediately regenerate keys.

---

# 22. Private Instance Connectivity Path

A private instance might be reached through:

```text
VPN

AWS Systems Manager

Bastion architecture

Private connectivity

Administrative network

Other controlled access path
```

A production private instance does not automatically need a public IP merely because an engineer needs administration access.

---

# 23. Security Groups Revisited

A Security Group is a stateful virtual firewall associated with supported AWS resources such as EC2 network interfaces.

For EC2, think:

```text
Network Route
↓
Security Group
↓
EC2
```

A route determines where traffic can travel.

The Security Group determines whether permitted traffic can reach or leave the associated resource.

---

# 24. Application Security Group

Create:

```hcl
resource "aws_security_group" "application" {
  name        = "${local.name_prefix}-application-sg"
  description = "Security group for application instances"
  vpc_id      = aws_vpc.main.id

  tags = merge(
    local.common_tags,
    {
      Name = "${local.name_prefix}-application-sg"
    }
  )
}
```

This creates the group.

Rules should be created according to actual communication requirements.

---

# 25. Security Group Rules

Modern configurations can manage rules as separate resources.

Conceptually:

```text
Application SG
├── Inbound application rule
└── Outbound required traffic
```

A rule answers questions such as:

```text
Direction?
Protocol?
Port?
Source or destination?
Why is it required?
```

---

# 26. Never Default to Open SSH

A common beginner tutorial uses:

```text
TCP 22
Source 0.0.0.0/0
```

That means SSH connection attempts can originate from anywhere on the IPv4 internet.

Do not learn this as a default.

For a temporary public SSH lab, use a deliberately restricted source CIDR that you control.

For production, consider controlled administrative mechanisms such as Systems Manager or private connectivity rather than automatically exposing SSH.

---

# 27. Example Restricted SSH Variable

```hcl
variable "admin_cidr" {
  type        = string
  description = "Trusted IPv4 CIDR permitted to reach SSH in the temporary public SSH lab."
  default     = null
  nullable    = true
}
```

Do not default this to:

```text
0.0.0.0/0
```

Make broad exposure a conscious decision, not an accidental default.

# 28. SSH Concepts

SSH means:

```text
Secure Shell
```

It provides encrypted remote access to supported systems.

Simplified flow:

```text
SSH Client
↓
Network Path
↓
TCP 22
↓
SSH Server
↓
Authentication
↓
Remote Shell
```

SSH failure can therefore originate from:

```text
networking
routing
Security Groups
wrong IP
wrong username
wrong key
file permissions
SSH daemon
operating-system configuration
```

---

# 29. EC2 Key Pairs

AWS EC2 key pairs are commonly used for SSH public-key authentication.

The concept is:

```text
Private Key
↓
kept securely by you

Public Key
↓
placed where the EC2 guest can use it
```

You authenticate using the private key.

Do not share or commit the private key.

---

# 30. Terraform and Key Pairs

Terraform can register a public key with AWS:

```hcl
resource "aws_key_pair" "admin" {
  key_name   = "${local.name_prefix}-admin"
  public_key = file(var.public_key_path)

  tags = local.common_tags
}
```

Then:

```hcl
key_name = aws_key_pair.admin.key_name
```

Important:

Terraform is registering the public key.

Your private key should remain securely controlled outside the Terraform configuration.

---

# 31. Never Put a Private SSH Key in Terraform Code

Do not do this:

```hcl
private_key = <<EOF
-----BEGIN PRIVATE KEY-----
...
EOF
```

That can leak through:

```text
Git
Terraform files
logs
backups
code review
state depending on usage
CI artifacts
```

Keep private keys out of infrastructure source code.

---

# 32. Generating an SSH Key Locally

For a temporary lab, one approach is:

```bash
ssh-keygen -t ed25519 -f ~/.ssh/veriqta-terraform-lab
```

This creates conceptually:

```text
~/.ssh/veriqta-terraform-lab
↓
Private key

~/.ssh/veriqta-terraform-lab.pub
↓
Public key
```

Protect the private key.

---

# 33. Private Key Permissions

On Linux/macOS, SSH may reject an overly permissive private key.

For example:

```bash
chmod 600 ~/.ssh/veriqta-terraform-lab
```

The principle is:

```text
Private key
↓
Only authorized local user should be able to read it
```

---

# 34. SSH Username Depends on the AMI

Do not assume every EC2 instance uses:

```text
ubuntu
```

or:

```text
ec2-user
```

The default login username depends on the operating-system image.

Always check the publisher's documentation for the selected AMI.

A correct key with the wrong username can still produce:

```text
Permission denied
```

# 35. IAM

IAM means:

```text
Identity and Access Management
```

IAM controls access to AWS APIs and resources.

For our EC2 workload, the key question is:

```text
What AWS actions should the application running on this EC2 instance be allowed to perform?
```

Examples might include:

```text
Read one S3 bucket

Write logs

Read one secret

Publish to one queue

Read a configuration parameter
```

---

# 36. Never Put AWS Access Keys on the Instance Unless There Is a Very Specific Reason

A bad pattern is:

```text
Create IAM user
↓
Create long-lived access key
↓
Copy key onto EC2
↓
Application reads key from file
```

Instead, EC2 applications should generally use an IAM role.

---

# 37. IAM Role Mental Model

```text
EC2
↓
IAM Role
↓
Temporary AWS Credentials
↓
AWS API
```

The application does not need a long-lived AWS access key embedded in configuration.

AWS can provide temporary role credentials to the instance.

---

# 38. IAM Role Has Two Important Sides

Think of an IAM role as answering:

```text
1. WHO MAY ASSUME THIS ROLE?

2. WHAT MAY THE ROLE DO?
```

The first is controlled through the role's trust policy.

The second comes from permission policies.

---

# 39. EC2 Trust Policy

For EC2, the trust relationship allows the EC2 service to assume the role.

Terraform can generate the JSON safely:

```hcl
data "aws_iam_policy_document" "ec2_assume_role" {
  statement {
    effect = "Allow"

    actions = [
      "sts:AssumeRole"
    ]

    principals {
      type = "Service"

      identifiers = [
        "ec2.amazonaws.com"
      ]
    }
  }
}
```

Then:

```hcl
resource "aws_iam_role" "application" {
  name               = "${local.name_prefix}-application-role"
  assume_role_policy = data.aws_iam_policy_document.ec2_assume_role.json

  tags = local.common_tags
}
```

---

# 40. Trust Policy Is Not Application Permission

This:

```text
EC2 may assume the role
```

does not automatically mean:

```text
Role may access S3
```

Those are separate policies.

Mental model:

```text
Trust Policy
↓
Who can become the role?

Permission Policy
↓
What can the role do after assuming it?
```

---

# 41. IAM Policies

An IAM permission policy contains statements describing allowed or denied AWS actions and resources.

Conceptually:

```json
{
  "Effect": "Allow",
  "Action": "...",
  "Resource": "..."
}
```

The important questions are:

```text
Which action?

On which resource?

Under which conditions?

Why does the application need it?
```

---

# 42. Least Privilege

Least privilege means:

```text
Grant only the permissions required
to perform the intended task.
```

Bad example:

```text
Action: "*"
Resource: "*"
```

simply because it makes an error disappear.

A better troubleshooting question is:

```text
Which exact API call failed?

Which exact permission is required?

Which exact resource should be accessible?
```

---

# 43. Example Permission Model

Suppose an application only needs to read objects from:

```text
arn:aws:s3:::example-app-config/*
```

The intended model is:

```text
Application Role
↓
Allow required S3 read action
↓
Only required bucket objects
```

not:

```text
AdministratorAccess
```

---

# 44. Instance Profiles

This is one of the most confusing EC2 IAM concepts.

An EC2 instance does not directly consume an IAM role in the same way you may imagine from the console.

EC2 uses an:

```text
Instance Profile
```

as the container through which the IAM role is associated with the instance.

Mental model:

```text
IAM Role
↓
Instance Profile
↓
EC2 Instance
```

---

# 45. Role vs Instance Profile

Remember:

```text
IAM ROLE
=
Permissions identity
```

```text
INSTANCE PROFILE
=
Container used to pass the IAM role to EC2
```

They are related but not conceptually identical.

When using Terraform or AWS APIs, you should understand both resources.

---

# 46. Create an Instance Profile

```hcl
resource "aws_iam_instance_profile" "application" {
  name = "${local.name_prefix}-application-profile"
  role = aws_iam_role.application.name

  tags = local.common_tags
}
```

Then EC2 receives:

```hcl
iam_instance_profile = aws_iam_instance_profile.application.name
```

Terraform now sees:

```text
IAM Role
↓
Instance Profile
↓
EC2
```

---

# 47. `iam:PassRole`

The identity running Terraform may need permission to pass the intended IAM role to EC2.

This is different from:

```text
The permissions the EC2 role itself has.
```

There are two identities:

```text
Terraform execution identity
↓
Creates/configures EC2

EC2 application role
↓
Used by software running on EC2
```

Do not confuse them.

---

# 48. Instance Metadata

EC2 exposes instance-specific information through the:

```text
Instance Metadata Service
```

commonly abbreviated:

```text
IMDS
```

Applications and software on the instance can use metadata for information related to the running instance.

Examples can include:

```text
Instance identity information
Networking information
IAM role credentials
Other instance metadata
```

---

# 49. Instance Metadata Is Security-Sensitive

Metadata can expose temporary credentials associated with the EC2 role.

Therefore:

```text
IMDS security
matters.
```

A vulnerable application that can be tricked into accessing metadata can create serious security consequences.

---

# 50. IMDSv2

Modern EC2 deployments should understand Instance Metadata Service Version 2.

IMDSv2 uses a session-oriented request model involving a token.

At a high level:

```text
Process
↓
Request metadata token
↓
Use token
↓
Request metadata
```

This adds protections compared with older metadata access patterns.

---

# 51. Require IMDSv2

An EC2 configuration can deliberately require token use.

Example:

```hcl
metadata_options {
  http_endpoint = "enabled"
  http_tokens   = "required"
}
```

This means metadata requests must use the IMDSv2 token mechanism.

Before enforcing it on legacy workloads, verify that the software accessing metadata supports the required behavior.

---

# 52. Metadata Hop Limit

Metadata options also include controls such as the response hop limit.

This becomes particularly relevant when software runs inside container networking layers on an EC2 host.

Do not change metadata hop settings blindly.

Understand the runtime architecture first.

---

# 53. User Data

User data allows you to provide initialization instructions to an EC2 instance.

Conceptually:

```text
EC2 Launch
↓
Operating System Boots
↓
Initialization System
↓
User Data
↓
Bootstrap Actions
↓
Application Environment
```

This is useful for initial configuration.

---

# 54. What Is Bootstrapping?

Bootstrapping means preparing a new machine so it can perform its intended role.

Examples:

```text
Install packages

Create directories

Write configuration

Start services

Register with systems

Install monitoring agents

Prepare application runtime
```

---

# 55. Simple User-Data Script

Example:

```bash
#!/bin/bash
set -euxo pipefail

dnf install -y nginx

cat > /usr/share/nginx/html/index.html <<'EOF'
<h1>VERIQTA Terraform EC2 Lab</h1>
<p>This server was bootstrapped through EC2 user data.</p>
EOF

systemctl enable nginx
systemctl start nginx
```

The exact package manager and service commands depend on the selected operating system.

Never copy bootstrap commands from one distribution and assume they work on another.

---

# 56. Terraform User Data

Instead of placing a long script directly inside the resource, store it separately.

Project:

```text
scripts/
└── bootstrap.sh
```

Then:

```hcl
user_data = file("${path.module}/scripts/bootstrap.sh")
```

This is easier to read and maintain.

---

# 57. User Data Is Not a Secret Store

Do not put sensitive credentials directly into user data.

Avoid:

```bash
export AWS_ACCESS_KEY_ID="..."
export AWS_SECRET_ACCESS_KEY="..."
export DATABASE_PASSWORD="..."
```

User data should not be treated as a secure secret-management mechanism.

Use appropriate IAM and secrets-management patterns instead.

---

# 58. Cloud-Init

Many Linux cloud images use:

```text
cloud-init
```

during boot.

Cloud-init can process initialization configuration and user data.

Conceptually:

```text
Instance boots
↓
cloud-init
↓
Reads configuration/user data
↓
Performs initialization stages
↓
Machine becomes configured
```

---

# 59. Shell Script vs Cloud-Config

User data can often be supplied as:

```text
Shell script
```

or supported cloud-init formats such as:

```text
#cloud-config
```

Example conceptual cloud-config:

```yaml
#cloud-config
packages:
  - nginx

runcmd:
  - systemctl enable nginx
  - systemctl start nginx
```

Exact behavior depends on the AMI and its cloud-init configuration.

---

# 60. User Data Usually Runs During Initial Launch

A critical beginner misunderstanding is:

```text
I changed user_data in Terraform,
therefore the existing server will simply rerun the script exactly as if it were new.
```

Do not assume that.

Cloud-init behavior and Terraform replacement behavior must be understood separately.

Bootstrap scripts should be designed with instance lifecycle in mind.

---

# 61. Bootstrap Scripts Should Be Idempotent Where Practical

If a script might execute more than once, try to make repeated execution safe.

Bad:

```text
Run once successfully
↓
Run again
↓
Corrupt configuration
```

Better:

```text
Check state
↓
Create/update safely
↓
Start required service
↓
Verify
```

This is another form of infrastructure engineering.

---

# 62. Bootstrap Failure Does Not Necessarily Mean EC2 Creation Failed

Terraform may report:

```text
EC2 instance created
```

while your application is broken.

Why?

Because AWS successfully created the EC2 resource.

But inside the instance:

```text
package installation failed

repository unavailable

script syntax failed

service failed

wrong package manager

configuration invalid
```

Terraform cannot automatically interpret every guest-operating-system bootstrap failure.

---

# 63. EBS

EBS means:

```text
Elastic Block Store
```

EBS provides block storage commonly used by EC2.

Mental model:

```text
EC2
↓
EBS Volume
↓
Block Storage
```

An EBS volume behaves more like a disk device than an object-storage bucket.

---

# 64. Root Volume

Most EBS-backed EC2 instances have a root volume containing:

```text
Operating system

Installed software

System files

Application files depending on design
```

The root volume is created as part of launching the instance.

---

# 65. Configure the Root Volume

Example:

```hcl
root_block_device {
  volume_type           = "gp3"
  volume_size           = 10
  encrypted             = true
  delete_on_termination = true
}
```

Understand each setting.

---

# 66. `volume_type`

Example:

```hcl
volume_type = "gp3"
```

This selects an EBS volume type.

Different EBS types have different:

```text
Performance characteristics
IOPS behavior
Throughput behavior
Use cases
Cost
```

Do not choose based only on familiarity.

---

# 67. `volume_size`

Example:

```hcl
volume_size = 10
```

This represents the requested volume size in GiB for the root block device.

Remember:

```text
EBS volume size
```

and:

```text
Filesystem size visible inside Linux
```

are related but not always operationally identical during later resizing workflows.

---

# 68. Encryption

Use:

# 73. Attachment Does Not Automatically Create a Filesystem

This is critical.

Terraform can attach the block device.

That does not necessarily:

```text
format it

create a filesystem

mount it

add it to /etc/fstab

create application directories
```

Those are guest-operating-system operations.

Mental model:

```text
AWS Attachment
↓
Block Device Visible to OS
↓
Partition/Filesystem if needed
↓
Mount
↓
Application Uses Storage
```

---

# 74. Device Names Can Be Confusing

The device name requested through AWS and the device name visible inside Linux may differ depending on the instance platform and block-device implementation.

Do not blindly assume:

```text
/dev/sdf
```

will always appear exactly as:

```text
/dev/sdf
```

inside the guest.

Inspect with tools such as:

```bash
lsblk
```

before formatting anything.

Formatting the wrong disk can destroy data.

# 75. Elastic IP

An Elastic IP provides a stable public IPv4 allocation.

Architecture:

```text
Internet
↓
Elastic IP
↓
EC2 / Network Interface
```

A normal automatically assigned public IPv4 address may change across some lifecycle events.

An Elastic IP can provide stable public addressing when that is actually required.

# 76. Do Not Use Elastic IPs Automatically

Ask:

```text

```

Modern architectures often place instances behind:

```text

DNS
Auto Scaling
Private networking
```

rather than treating individual EC2 IP addresses as permanent application endpoints.

Elastic/public IPv4 addresses can also have cost implications.

---

# 96. Why `set -euxo pipefail`?

In Bash:

```text
-e
Exit when a command fails in many normal contexts.

-u
Treat unset variables as errors.

-x
Print commands as they execute.

-o pipefail
Make pipeline failures easier to detect.
```

This can make bootstrap failures easier to diagnose.

Be careful with `-x` if commands might expose sensitive values in logs.

Never echo secrets into bootstrap logs.

# 134. AMI Changes Commonly Matter Greatly

Changing the AMI represents changing the base machine image.

Break the system down:

```text

↓
Did provider authenticate?
↓
Was AWS authorization sufficient?
↓
Did AWS create EC2?
↓
Did EC2 enter running state?
↓
Is the AMI correct?
↓
Is the network path correct?
↓
Is the Security Group correct?
↓
Is IAM attached correctly?
↓
Did cloud-init run?
↓
Did software install?
↓
Did the service start?
↓
Is the service listening?
↓
Can the client reach it?
↓
Does the application behave correctly?
```

Every layer produces evidence.

Use the evidence.
