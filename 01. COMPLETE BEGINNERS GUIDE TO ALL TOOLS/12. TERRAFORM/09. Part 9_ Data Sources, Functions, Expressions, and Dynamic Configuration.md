# Part 9: Data Sources, Functions, Expressions, and Dynamic Configuration

## Move From Static Terraform to Flexible Infrastructure Definitions

Up to this point, you have learned how Terraform can:

* define infrastructure
* configure providers
* create resources
* accept variables
* produce outputs
* maintain state
* understand dependencies
* manage multiple resource instances
* control resource lifecycle

Now we move into one of the areas that makes Terraform genuinely powerful.

Instead of writing configurations where every value is manually hardcoded, Terraform can:

* query existing infrastructure
* discover information from cloud providers
* transform input data
* filter collections
* combine maps and lists
* calculate values
* choose values conditionally
* load files
* render templates
* normalize inconsistent input
* generate repeated nested configuration
* test expressions interactively

The core mental model for this part is:

```text
Variables
+
Data Sources
+
Functions
+
Expressions
↓
Dynamic Infrastructure Configuration
```

A more complete version is:

```text
User Input
        │
        ▼
   Variables
        │
        ├──────────────┐
        │              │
        ▼              ▼
  Data Sources      Local Values
        │              │
        └──────┬───────┘
               ▼
        Expressions
               │
               ▼
          Functions
               │
               ▼
     Transformed Values
               │
               ▼
       Resources / Modules
               │
               ▼
      Infrastructure
```

The goal is not to make Terraform clever for the sake of being clever.

The goal is to make configuration:

* reusable
* portable
* maintainable
* predictable
* easier to operate
* less dependent on copied IDs
* adaptable to different environments

The most important rule throughout this chapter is:

```text
Dynamic does not automatically mean better.

The best Terraform configuration is dynamic enough
to remove unnecessary repetition and hardcoding,
but simple enough that another engineer can still
understand the infrastructure.
```

---

# 1. The Problem With Completely Static Configuration

Imagine this:

```hcl
resource "aws_instance" "application" {
  ami               = "ami-0123456789abcdef0"
  availability_zone = "us-east-1a"
  subnet_id         = "subnet-0123456789abcdef0"
  instance_type     = "t3.micro"
}
```

This might work.

But ask:

```text
Where did the AMI ID come from?

Does that AMI exist in another region?

What happens when a newer AMI becomes available?

Does this subnet exist in staging?

Does it exist in another AWS account?

Is us-east-1a appropriate everywhere?

Who updates these values?

How do we know they are still correct?
```

Hardcoded infrastructure identifiers create coupling between configuration and one particular environment.

A more flexible design might discover some of these values.

For example:

```text
Terraform
↓
Ask AWS for information
↓
Receive existing infrastructure metadata
↓
Use returned values
↓
Build new infrastructure
```

That is where data sources begin.

---

# 2. What Is a Data Source?

A Terraform **data source** allows Terraform to retrieve information.

Think:

```text
Managed Resource
=
Terraform manages an object

Data Source
=
Terraform reads information
```

A data source can query information exposed by a provider.

Examples might include:

```text
Current AWS account information

Available AWS Availability Zones

Existing VPC

Existing subnet

Existing AMI

Existing IAM information

Existing DNS zone

Existing secrets metadata

Existing cloud resources
```

The exact data sources available depend on the provider.

---

# 3. Managed Resources vs Data Sources

This distinction is fundamental.

## Managed Resource

Example:

```hcl
resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
}
```

Terraform manages the lifecycle of this object.

Conceptually:

```text
Terraform
↓
CREATE VPC
↓
READ VPC
↓
UPDATE VPC
↓
DELETE VPC
```

## Data Source

Conceptually:

```hcl
data "aws_vpc" "existing" {
  # lookup criteria
}
```

Terraform asks AWS:

```text
"Find this existing VPC and give me information about it."
```

Terraform is not declaring:

```text
"Create this VPC."
```

The operation is fundamentally read-oriented.

---

# 4. The Difference in One Diagram

```text
MANAGED RESOURCE

Terraform Configuration
        ↓
resource
        ↓
Provider
        ↓
Cloud API
        ↓
Create / Read / Update / Delete
        ↓
Infrastructure
```

Compare that with:

```text
DATA SOURCE

Terraform Configuration
        ↓
data
        ↓
Provider
        ↓
Cloud API
        ↓
Read / Query
        ↓
Existing Information
```

---

# 5. Data Source Syntax

General structure:

```hcl
data "<TYPE>" "<LOCAL_NAME>" {
  # query arguments
}
```

Example:

```hcl
data "aws_vpc" "existing" {
  # lookup criteria
}
```

The first label:

```text
aws_vpc
```

is the data source type.

The second:

```text
existing
```

is the local name you chose.

---

# 6. Referencing Data Source Results

Managed resource reference:

```hcl
aws_vpc.main.id
```

Data source reference:

```hcl
data.aws_vpc.existing.id
```

Mental model:

```text
data
↓
This is queried data

aws_vpc
↓
Data source type

existing
↓
Local name

id
↓
Returned attribute
```

Therefore:

```hcl
data.aws_vpc.existing.id
```

means:

> Give me the `id` returned by the `aws_vpc` data source named `existing`.

---

# 7. Data Sources Do Not Import Resources

This is an important beginner distinction.

Suppose AWS already contains:

```text
vpc-123456
```

and you query it with a data source.

That does not mean Terraform now manages the VPC lifecycle.

Terraform knows information about it.

That is different from importing it into Terraform resource management.

Think:

```text
DATA SOURCE
↓
Read existing object

IMPORT
↓
Bind existing object to a managed resource address
```

These solve different problems.

Import is covered more deeply later in this series.

---

# 8. Why Data Sources Are Useful

Without data source:

```hcl
vpc_id = "vpc-0123456789abcdef0"
```

With data source:

```hcl
vpc_id = data.aws_vpc.existing.id
```

The second configuration expresses:

```text
Find the VPC matching my criteria
↓
Get its ID
↓
Use that ID
```

instead of:

```text
Use this copied ID forever.
```

---

# 9. Data Source Read Timing

Terraform generally attempts to read data sources during planning when enough information is available.

Conceptually:

```text
terraform plan
↓
Evaluate Configuration
↓
Read Required Data
↓
Calculate Plan
```

But sometimes a data source depends on information that is not known until apply.

Then Terraform may defer the data-source read.

Conceptually:

```text
Resource must change
↓
Required lookup argument is unknown
↓
Data source cannot be fully queried during plan
↓
Read deferred until apply
```

You may see values represented as:

```text
(known after apply)
```

This is not automatically an error.

It means Terraform does not yet have enough information to calculate that value.

---

# 10. Data Sources Participate in Dependency Reasoning

Suppose:

```text
Managed VPC
↓
VPC ID
↓
Data Source Query
```

If the query requires a value from a resource that is being created or changed, Terraform must respect that relationship.

Remember Part 8:

```text
Terraform
does not execute files top to bottom.

Terraform builds relationships.
```

The same principle applies here.

# 11. Looking Up AWS Account Information

A useful AWS concept is discovering information about the identity Terraform is currently using.

Conceptually:

```hcl
data "aws_caller_identity" "current" {}
```

This can expose information about the AWS identity/account associated with the current provider credentials.

You can then use returned attributes in your configuration.

For example, conceptually:

```hcl
output "aws_account_id" {
  value = data.aws_caller_identity.current.account_id
}
```

This is useful when:

```text
building ARNs

checking account context

creating account-aware naming

verifying deployments

supporting multiple AWS accounts
```

---

# 12. Why Account Discovery Matters

Imagine accidentally running production Terraform with development AWS credentials.

Hardcoding:

```text
123456789012
```

does not prove which account Terraform is actually authenticated against.

A caller identity query lets Terraform obtain information about the active AWS identity.

Operationally, you should always understand:

```text
Which credentials am I using?

Which AWS account do they belong to?

Which provider alias is active?

Which region is configured?

What permissions does this identity have?
```

Dynamic discovery does not replace operational verification.

---

# 13. Availability Zone Discovery

A region can contain multiple Availability Zones.

Instead of permanently hardcoding:

```text
us-east-1a
us-east-1b
us-east-1c
```

Terraform can query available zones through an AWS data source.

Conceptually:

```hcl
data "aws_availability_zones" "available" {
  state = "available"
}
```

Then you can consume returned zone information.

Conceptually:

```hcl
data.aws_availability_zones.available.names
```

This might produce a collection similar to:

```text
[
  "us-east-1a",
  "us-east-1b",
  "us-east-1c",
  ...
]
```

The actual returned zones depend on the account, region, provider behavior, and current AWS environment.

Never assume the example list is universal.

---

# 14. Using Discovered Availability Zones

Suppose:

```hcl
data "aws_availability_zones" "available" {
  state = "available"
}
```

You might use:

```hcl
availability_zone = data.aws_availability_zones.available.names[0]
```

This means:

```text
Query available zones
↓
Receive names collection
↓
Take first element
↓
Use it for resource configuration
```

But be careful.

Indexing into discovered infrastructure data creates assumptions.

Ask:

```text
Is the ordering stable enough for my architecture?

Do I actually need the first zone?

Should zones be selected explicitly?

Could account-specific zone mappings matter?

Would stable keys produce a better design?
```

Dynamic does not remove architecture decisions.

# 15. AMI Lookup Concepts

AMI IDs are regional.

An AMI ID valid in:

```text
us-east-1
```

may not represent the same image in:

```text
us-west-2
```

Hardcoding AMI IDs therefore reduces portability.

Terraform can query AWS for an AMI matching criteria.

Conceptually:

```hcl
data "aws_ami" "application" {
  # ownership criteria
  # filters
  # selection behavior
}
```

Then:

```hcl
ami = data.aws_ami.application.id
```

The architecture becomes:

```text
AMI Requirements
↓
AWS AMI Query
↓
Matching AMI
↓
AMI ID
↓
EC2 Resource
```

---

# 16. AMI Lookup Safety

Dynamic AMI lookup requires careful filtering.

A dangerous conceptual query is:

```text
"Give me some Linux AMI."
```

Production infrastructure should know:

```text
Who owns the image?

Which operating system?

Which architecture?

Which image family?

Which naming pattern?

Should the newest matching image be selected?

Could a new image unexpectedly change future deployments?
```

A lookup that is too broad can produce unintended infrastructure changes.

Dynamic discovery should be precise.

# 17. Existing VPC Lookup

Suppose another team manages the network.

Your Terraform configuration manages only application infrastructure.

Architecture:

```text
Network Team
↓
Existing VPC
↓
Application Terraform
↓
Query VPC
↓
Use VPC ID
↓
Create Application Resources
```

You might query the existing VPC rather than recreating or importing it.

Conceptually:

```hcl
data "aws_vpc" "shared" {
  # identifying criteria
}
```

Then:

```hcl
vpc_id = data.aws_vpc.shared.id
```

---

# 18. Existing Subnet Lookup

The same idea applies to subnets.

Conceptually:

```hcl
data "aws_subnet" "application" {
  # identifying criteria
}
```

Then:

```hcl
subnet_id = data.aws_subnet.application.id
```

Architecture:

```text
Existing VPC
↓
Existing Subnet
↓
Terraform Data Source
↓
Subnet ID
↓
EC2 / Load Balancer / Other Resource
```

---

# 19. Lookup Criteria Must Be Reliable

Do not build infrastructure around ambiguous searches.

Suppose multiple VPCs share:

```text
Environment = production
```

A query that assumes exactly one match may fail or select something unintended depending on the data source behavior.

Good lookup design uses criteria that reliably identify the intended object.

Ask:

```text
Could this query return zero matches?

Could it return multiple matches?

Are tags unique?

Are names guaranteed unique?

Could another team rename the object?

Is the account correct?

Is the region correct?
```

Data-source troubleshooting often begins here.

---

# 20. Data Source Troubleshooting

When a lookup fails, investigate systematically:

```text
Data Source Error
↓
Correct Provider?
↓
Correct AWS Account?
↓
Correct Region?
↓
Correct Credentials?
↓
Correct Permissions?
↓
Correct Filters?
↓
Does Object Exist?
↓
Zero Matches?
↓
Multiple Matches?
↓
Unknown Input Value?
```

Do not immediately rewrite the entire configuration.

# 21. Expressions

A Terraform **expression** computes or refers to a value.

Simple expression:

```hcl
"production"
```

Reference expression:

```hcl
var.environment
```

Arithmetic expression:

```hcl
var.base_port + 1
```

Conditional expression:

```hcl
var.environment == "production" ? "t3.large" : "t3.micro"
```

Function call:

```hcl
upper(var.environment)
```

For expression:

```hcl
[
  for name in var.services :
  upper(name)
]
```

Expressions are the language Terraform uses to turn input data into configuration values.

---

# 22. Expressions Are Not Statements

Terraform is declarative.

You are usually not writing:

```text
Step 1
then
Step 2
then
Step 3
```

Instead you describe values and relationships.

Example:

```hcl
name = "${var.application}-${var.environment}"
```

Terraform evaluates the expression to produce the value.

---

# 23. Expression Mental Model

```text
Input Values
↓
Expression
↓
Evaluation
↓
Resulting Value
↓
Resource Argument
```

Example:

```text
application = "api"
environment = "production"

↓ expression ↓

"${var.application}-${var.environment}"

↓ result ↓

"api-production"
```

---

# 24. Conditional Expressions

Terraform conditional syntax:

```hcl
condition ? true_value : false_value
```

Example:

```hcl
var.environment == "production" ? "t3.large" : "t3.micro"
```

Read it as:

```text
Is environment production?

YES
↓
t3.large

NO
↓
t3.micro
```

---

# 25. Conditional Example

```hcl
locals {
  instance_type = var.environment == "production" ? "t3.large" : "t3.micro"
}
```

If:

```text
environment = production
```

result:

```text
t3.large
```

Otherwise:

```text
t3.micro
```

---

# 26. Conditions Must Produce Boolean Results

The condition before `?` must resolve to:

```text
true
```

or:

```text
false
```

Examples:

```hcl
var.environment == "production"
```

```hcl
var.replica_count > 1
```

```hcl
var.enable_monitoring
```

```hcl
contains(["dev", "staging", "prod"], var.environment)
```

---

# 27. Conditional Result Types

Terraform must determine a consistent result type.

For example:

```hcl
var.enabled ? "yes" : "no"
```

Both results are strings.

Clear.

But mixing unrelated types can cause conversion or type errors.

Avoid clever expressions such as:

```text
true branch = object

false branch = unrelated primitive
```

unless the receiving context intentionally supports that shape.

Readable type consistency is better.

---

# 28. Nested Conditionals

Terraform allows nested conditional expressions.

Example:

```hcl
var.environment == "production" ? "large" : var.environment == "staging" ? "medium" : "small"
```

This works.

But ask:

```text
Can another engineer understand this immediately?
```

Often a map is clearer:

```hcl
locals {
  instance_types = {
    production = "large"
    staging    = "medium"
    development = "small"
  }
}
```

Then:

```hcl
local.instance_types[var.environment]
```

Do not use dynamic syntax merely because you can.

---

# 29. For Expressions

A `for` expression transforms collections.

Basic list form:

```hcl
[
  for item in collection :
  expression
]
```

Example:

```hcl
[
  for name in ["api", "worker", "frontend"] :
  upper(name)
]
```

Result:

```text
[
  "API",
  "WORKER",
  "FRONTEND"
]
```

---

# 30. For Expression Mental Model

```text
Input Collection
↓
Visit Each Element
↓
Transform Element
↓
Build New Collection
```

Example:

```text
api
worker
frontend

↓ upper() ↓

API
WORKER
FRONTEND
```

---

# 31. For Expressions Do Not Create Resources

This distinction matters.

A `for` expression:

```hcl
[
  for name in var.services :
  upper(name)
]
```

creates a **value**.

`for_each`:

```hcl
resource "example" "service" {
  for_each = var.services
}
```

creates multiple **resource instances**.

Remember:

```text
for expression
↓
Transforms values

for_each
↓
Creates multiple block instances
```

---

# 32. For Expression With Index

For lists and tuples, you can capture the index.

Example:

```hcl
[
  for index, name in var.services :
  "${index}-${name}"
]
```

If:

```text
["api", "worker"]
```

result:

```text
[
  "0-api",
  "1-worker"
]
```

---

# 33. For Expression With Maps

Input:

```hcl
variable "ports" {
  default = {
    api      = 8080
    frontend = 3000
    worker   = 9000
  }
}
```

Transform into strings:

```hcl
[
  for name, port in var.ports :
  "${name}:${port}"
]
```

Conceptual result:

```text
[
  "api:8080",
  "frontend:3000",
  "worker:9000"
]
```

---

# 34. Producing a Map With a For Expression

Use:

```hcl
{
  for item in collection :
  key_expression => value_expression
}
```

Example:

```hcl
{
  for name in var.services :
  name => upper(name)
}
```

Result:

```text
{
  api      = "API"
  frontend = "FRONTEND"
  worker   = "WORKER"
}
```

---

# 35. Filtering With For Expressions

You can add:

```hcl
if condition
```

Example:

```hcl
[
  for service in var.services :
  service.name
  if service.enabled
]
```

Mental model:

```text
Every Service
↓
Is Enabled?
├── Yes → Include
└── No  → Exclude
```

---

# 36. Transform and Filter Together

Example:

```hcl
[
  for service in var.services :
  upper(service.name)
  if service.enabled
]
```

This performs:

```text
Input
↓
Filter Enabled Services
↓
Transform Names
↓
Return New Collection
```

# 47. `lookup`

Syntax:

```hcl
lookup(map, key, default)
```

Example:

```hcl
lookup(
  {
    development = "t3.micro"
    production  = "t3.large"
  },
  var.environment,
  "t3.micro"
)
```

If:

```text
environment = production
```

result:

```text
t3.large
```

If the key does not exist:

```text
t3.micro
```

because that is the supplied fallback.

---

# 48. Native Map Indexing vs `lookup`

Direct:

```hcl
local.instance_types[var.environment]
```

With fallback:

```hcl
lookup(
  local.instance_types,
  var.environment,
  "t3.micro"
)
```

Use direct indexing when the key must exist.

Use `lookup` when a missing key has a legitimate fallback.

Do not silently hide configuration errors with defaults when the key should actually be mandatory.

---

# 49. `merge`

`merge` combines maps or objects.

Example:

```hcl
locals {
  common_tags = {
    ManagedBy = "Terraform"
    Project   = "VERIQTA"
  }

  environment_tags = {
    Environment = var.environment
  }

  tags = merge(
    local.common_tags,
    local.environment_tags
  )
}
```

Result conceptually:

```text
ManagedBy   = Terraform
Project     = VERIQTA
Environment = production
```

---

# 50. Merge Precedence

If maps contain the same key, later arguments take precedence.

Example:

```hcl
merge(
  {
    Environment = "development"
  },
  {
    Environment = "production"
  }
)
```

Result:

```text
Environment = production
```

Therefore ordering matters.

---

# 51. Practical Tagging Pattern

```hcl
locals {
  mandatory_tags = {
    ManagedBy   = "Terraform"
    Project     = var.project
    Environment = var.environment
  }

  tags = merge(
    var.additional_tags,
    local.mandatory_tags
  )
}
```

Here mandatory tags come last.

That means a caller cannot accidentally override them through `additional_tags`.

If you reverse the order:

```hcl
merge(
  local.mandatory_tags,
  var.additional_tags
)
```

then caller-provided values can override matching keys.

Neither approach is universally correct.

Choose intentionally.

---

# 52. `concat`

`concat` combines lists.

Example:

```hcl
concat(
  ["api", "worker"],
  ["frontend", "admin"]
)
```

Result:

```text
[
  "api",
  "worker",
  "frontend",
  "admin"
]
```

---

# 53. `concat` Does Not Automatically Remove Duplicates

Example:

```hcl
concat(
  ["api", "worker"],
  ["worker", "frontend"]
)
```

can produce:

```text
[
  "api",
  "worker",
  "worker",
  "frontend"
]
```

If uniqueness matters, transform further.

For example:

```hcl
toset(
  concat(
```

# 55. Why `flatten` Matters in Infrastructure

Suppose:

```text
VPC A
├── Subnet A1
└── Subnet A2

VPC B
├── Subnet B1
└── Subnet B2
```

Your variable may naturally represent:

```text
Map of VPCs
↓
Each VPC contains subnets
```

But resource creation may need:

```text
One collection
↓
One element per subnet
```

A common transformation becomes:

```text
Nested Structure
↓
for expression
↓
Nested Lists
↓
flatten
↓
Flat Collection
↓
for_each
```

This is a major real-world Terraform pattern.

# 73. Important `file()` Limitation

Terraform functions do not participate in the dependency graph.


is designed for files that already exist when Terraform begins the run.

```text

↓

```

and expect `file()` itself to create dependency ordering.

That is not how Terraform functions work.

# 79. `try`

`try` evaluates expressions in order and returns the first one that does not produce a dynamic error.

Example:

```hcl
try(
  local.configuration.application.port,
  8080
)
```

Mental model:

```text
Try First Expression
↓
Works?
├── Yes → Return It
└── No
    ↓
Try Next Expression
```

---

# 80. Good Use of `try`

Suppose decoded external data may omit an optional field.

Example:

```hcl
locals {
  raw_configuration = yamldecode(
    file("${path.module}/config.yaml")
  )

  normalized_configuration = {
    name = tostring(
      try(local.raw_configuration.name, "application")
    )

    port = tonumber(
      try(local.raw_configuration.port, 8080)
    )
  }
}
```

Now the rest of your Terraform configuration can use:

```hcl
local.normalized_configuration.name
```

and:

```hcl
local.normalized_configuration.port
```

without repeating error-handling logic everywhere.

---

# 81. Normalize Once

A strong pattern is:

```text
Raw Input
↓
Normalization Local
↓
Predictable Structure
↓
Rest of Configuration
```

Instead of:

```text
try(...)
try(...)
try(...)
try(...)
```

throughout every resource.

Centralize normalization.

This keeps the rest of the configuration readable.

---

# 82. `try` Does Not Catch Every Possible Error

Do not think:

```text
try()
=
make broken Terraform valid
```

It is designed to catch certain dynamic evaluation errors.

It cannot magically rescue:

```text
invalid syntax

undeclared top-level references

fundamentally invalid expressions
```

Use it for predictable normalization and fallback behavior.

---

# 83. `can`

`can` evaluates an expression and returns:

```text
true
```

if evaluation succeeds, or:

```text
false
```

for certain dynamic evaluation errors.

Example:

```hcl
can(local.configuration.port)
```

Possible result:

```text
true
```

or:

```text
false
```

---

# 84. Good Use of `can`

`can` is particularly useful in validation.

Example concept:

```hcl
validation {
  condition = can(
    formatdate("", var.timestamp)
  )

  error_message = "timestamp must be a valid RFC 3339 timestamp."
}
```

Mental model:

```text
Can Terraform evaluate this?
↓
Yes → true
No  → false
```

For ordinary fallback values elsewhere, `try` is often clearer.

---

# 85. `try` vs `can`

Use:

```text
try
```

when you need:

```text
a fallback value
```

Use:

```text
can
```

when you need:

```text
a boolean telling you whether evaluation succeeds
```

Example:

```hcl
try(local.config.port, 8080)
```

returns a value.

Example:

```hcl
can(local.config.port)
```

returns:

```text
true / false
```

---

# 86. `coalesce`

`coalesce` returns the first argument that is neither:

```text
null
```

nor an empty string.

Example:

```hcl
coalesce(
  var.application_name,
  "default-application"
)
```

If:

```text
application_name = null
```

result:

```text
default-application
```

---

# 87. `coalesce` With Multiple Candidates

Example:

```hcl
coalesce(
  var.custom_name,
  var.default_name,
  "application"
)
```

Terraform checks from left to right.

Conceptually:

```text
custom_name usable?
├── Yes → return
└── No
    ↓
default_name usable?
├── Yes → return
└── No
    ↓
"application"
```

---

# 88. `coalesce` Is Not `try`

These solve different problems.

`coalesce` handles:

```text
null
empty string
```

`try` handles:

```text
dynamic expression errors
```

Example:

```hcl
coalesce(var.name, "default")
```

is not the same problem as:

```hcl
try(local.config.name, "default")
```

Choose based on the failure mode.

# 89. Combining Functions

Terraform becomes powerful when simple functions are composed.

Example:

```hcl
lower(
  replace(
    "${var.application}-${var.environment}",
    "_",
    "-"
  )
)
```

But avoid deeply nested expressions when readability suffers.

Better:

```hcl
locals {
  raw_name = "${var.application}-${var.environment}"

  normalized_name = lower(
    replace(local.raw_name, "_", "-")
  )
}
```

Readability is an engineering requirement.

# 90. Dynamic Blocks

Terraform resources sometimes contain repeatable nested blocks.

Conceptual example:

```hcl
resource "example_resource" "application" {
  rule {
    # ...
  }

  rule {
    # ...
  }

  rule {
    # ...
  }
}
```

If the number of nested `rule` blocks depends on input data, manually writing them may not scale.

A `dynamic` block can generate repeated nested blocks.

---

# 91. Dynamic Block Mental Model

```text
Collection
↓
dynamic block
↓
One Nested Block Per Element
```

This is different from:

```text
for_each on a resource
```

which creates multiple resource instances.

Think:

```text
resource for_each
↓
multiple resources

dynamic block
↓
multiple nested blocks inside one resource
```

---

# 92. Dynamic Block Syntax

General pattern:

```hcl
dynamic "SETTING" {
  for_each = COLLECTION

  content {
    # nested block arguments
  }
}
```

Conceptually:

```hcl
dynamic "rule" {
  for_each = var.rules

  content {
    port     = rule.value.port
    protocol = rule.value.protocol
  }
}
```

The exact nested block name and supported arguments depend on the provider resource schema.

Always check provider documentation.

---

# 93. Dynamic Block Iterator

By default, the iterator name is the dynamic block label.

Example:

```hcl
dynamic "rule" {
  for_each = var.rules

  content {
    port = rule.value.port
  }
}
```

Here:

```text
rule
```

acts as the iterator.

It provides access similar to:

```text
key
value
```

depending on the collection.

---

# 94. Explicit Iterator

For readability, you can specify an iterator.

Example:

```hcl
dynamic "rule" {
  for_each = var.rules
  iterator = current_rule

  content {
    port     = current_rule.value.port
    protocol = current_rule.value.protocol
  }
}
```

This can make deeply nested dynamic configuration easier to understand.

---

# 95. When Dynamic Blocks Are Appropriate

Dynamic blocks are useful when:

```text
a resource supports repeatable nested blocks

the number of nested blocks depends on input

the blocks follow the same structure

manual duplication would be significant
```

Example architecture:

```text
One Resource
↓
Variable Number of Nested Rules
├── Rule A
├── Rule B
├── Rule C
└── Rule D
```

---

# 96. When Dynamic Blocks Reduce Readability

Do not transform:

```hcl
rule {
  port = 80
}

rule {
  port = 443
}
```

into a complicated abstraction merely to remove six lines.

Dynamic blocks can make configuration harder to understand.

Bad pattern:

```text
dynamic
inside dynamic
inside complex for expression
using flatten
using merge
using try
using conditional logic
```

until nobody can tell what infrastructure is produced.

Terraform should remain reviewable.

---

# 97. Dynamic Block Rule

Use this question:

```text
Does the abstraction make the infrastructure
easier or harder to understand?
```

If harder:

```text
write the explicit blocks.
```

A few repeated lines can be better than a clever abstraction.

---

# 98. Dynamic Blocks Cannot Generate Everything

Dynamic blocks generate repeatable nested blocks.

They are not a replacement for every Terraform language feature.

Do not use them to generate meta-arguments such as lifecycle configuration in arbitrary ways.

Terraform must evaluate certain language-level behavior before ordinary dynamic expression processing.

Think:

```text
dynamic
=
nested configuration generation

not
=
general Terraform code generator
```

# 150. Dynamic Block Practical Pattern

Suppose a provider resource supports repeatable nested configuration blocks called `setting`.

Input:

```hcl
variable "settings" {
  type = map(object({
    value = string
  }))

  default = {
    logging = {
      value = "enabled"
    }

    monitoring = {
      value = "enabled"
    }
  }
}
```

Conceptual resource:

```hcl
resource "example_service" "application" {
  name = var.application_name

  dynamic "setting" {
    for_each = var.settings

    content {
      name  = setting.key
      value = setting.value.value
    }
  }
}
```

Result conceptually:

```text
Application Resource
├── setting logging
└── setting monitoring
```

Use the actual nested-block schema from the provider documentation when implementing a real resource.

# 152. Common Mistake: Overusing Data Sources

Not every value should be discovered dynamically.

Sometimes explicit configuration is better.

Example:

```text
Production must deploy specifically to these approved subnet IDs.
```

Explicit input may be safer than:

```text
"Find whatever subnet happens to match this broad tag."
```

Use discovery when discovery represents the architecture.

Do not use it merely to avoid writing values.

---

# 153. Common Mistake: Broad AMI Lookup

Problem:

```text
Select newest image
with vague filter.
```

A new image appears.

Future deployment now uses a different image.

This might be intended.

It might also be an uncontrolled infrastructure change.

Production design should decide:

```text
Should AMI updates be automatic?

Should they be explicitly promoted?

Should image IDs be pinned?

Who approves new images?

How are they tested?
```

Terraform cannot make governance decisions for you.

---

# 154. Common Mistake: Assuming Data Sources Are Managed Resources

A data source does not mean Terraform owns the object.

If another team deletes the VPC you queried:

```text
Terraform data source
```

cannot restore it simply because it previously read it.

Ownership matters.

```text
↓

↓

↓
```

# 156. Common Mistake: Giant Expressions

Bad:

```hcl
value = lower(replace(coalesce(try(local.raw.application.name, var.application_name), "application"), "_", "-"))
```

Technically possible.

Operationally unpleasant.

Better:

```hcl
locals {
  raw_application_name = try(
    local.raw.application.name,
    var.application_name
  )

  selected_application_name = coalesce(
    local.raw_application_name,
    "application"
  )

  normalized_application_name = lower(
    replace(
      local.selected_application_name,
      "_",
      "-"
    )
  )
}
```

Terraform is maintained by humans.

Optimize for comprehension.

---

# 157. Common Mistake: Using `try` Everywhere

Bad:

```hcl
try(...)
```

on every reference.

This can hide real configuration mistakes.

Use `try` where optional or inconsistent data is genuinely expected.

A missing value that should always exist should often produce an error.

# 158. Common Mistake: Using `can` as General Error Suppression

`can` is especially useful for validation-style checks.

Do not build entire configurations around:

```text
Can this fail?

If yes, silently continue.
```

Infrastructure errors should often remain visible.

# 159. Common Mistake: Converting Everything to Strings

These are not equivalent:

```text

```

and:

```text

```

in every context.

Likewise:

```text

```

and:


Preserve meaningful types.

# 174. Production Design Pattern: Discover, Normalize, Consume

One of the strongest patterns from this chapter is:

```text
DISCOVER
↓
Data Sources / Files / Inputs

NORMALIZE
↓
Locals / try / conversion / merge

TRANSFORM
↓
for / flatten / conditional / functions

CONSUME
↓
Resources / Modules / Outputs
```

This gives you a clean architecture.

---

# 175. Production Design Pattern: Keep Resources Simple

Instead of:

```hcl
resource "example" "application" {
  name = lower(replace(coalesce(try(...))))
}
```

prefer:

```hcl
locals {
  application_name = ...
}
```

then:

```hcl
resource "example" "application" {
  name = local.application_name
}
```

Resources should read like infrastructure.

Transformation complexity belongs in well-named local values.

---

# 176. Production Design Pattern: Stable Keys

Transform collections into meaningful maps before `for_each`.

Example:

```text
Nested Raw Input
↓
flatten
↓
for expression
↓
Map With Stable Keys
↓
for_each
```

A stable key might be:

```text
vpc-name.subnet-name
```

rather than:

```text
0
1
2
3
```

The correct key depends on your architecture.

---

# 177. Production Design Pattern: Separate Discovery From Ownership

Example:

```text
Networking Repository
↓
Owns VPC

Application Repository
↓
Queries VPC

Application Repository
↓
Owns EC2 / ALB / Application Resources
```

This makes ownership boundaries explicit.

Do not accidentally manage the same infrastructure object from multiple Terraform states.

---

# 178. Production Design Pattern: Pin Critical Decisions

Dynamic does not mean:

```text
Always use whatever is newest.
```

For critical production infrastructure, consider which values should be:

```text
discovered

calculated

explicitly selected

version-controlled

promoted through environments
```

Example:

```text
Availability zones
→ discovery may make sense

Production application version
→ explicit promotion may make sense

Base AMI
→ organization-specific governance decision
```

# 183. The Most Important Rules From Part 9

```text
RULE 1

Resources manage infrastructure.

Data sources read information.
```

```text
RULE 2

A data source does not automatically
take ownership of an existing resource.
```

```text
RULE 3

Dynamic discovery should be deterministic.

Avoid ambiguous lookups.
```

```text
RULE 4

Expressions calculate values.

They do not create infrastructure by themselves.
```

```text
RULE 5

for expressions transform collections.

for_each creates multiple instances.
```

```text
RULE 6

Use functions to clarify transformations,
not to make configuration clever.
```

```text
RULE 7

Normalize complicated input once.

Do not repeat error handling everywhere.
```

```text
RULE 8

Use lookup when a missing map key
has a legitimate fallback.

Use direct indexing when absence
should be an error.
```

```text
RULE 9

merge order matters.

Later duplicate keys win.
```

```text
RULE 10

flatten is powerful when converting
nested infrastructure models into
collections suitable for iteration.
```

```text
RULE 11

Stable resource identity still matters
after transforming collections.
```

```text
RULE 12

try is for controlled fallback behavior.

It is not a universal error suppressor.
```

```text
RULE 13

can is particularly useful
for validation-style checks.
```

```text
RULE 14

coalesce handles null or empty values.

try handles dynamic evaluation errors.

They solve different problems.
```

```text
RULE 15

file() and templatefile() work with
files that already exist when the run begins.
```

```text
RULE 16

Dynamic blocks generate nested blocks.

They do not replace resource-level
count or for_each.
```

```text
RULE 17

Do not use dynamic blocks
when explicit configuration is clearer.
```

```text
RULE 18

Use terraform console
before guessing how a complex expression behaves.
```

```text
RULE 19

Dynamic infrastructure should still
be predictable infrastructure.
```

```text
RULE 20

Readable Terraform is better
than clever Terraform.
```

# 184. Final Mental Model

You began this chapter with static configuration:

```text
Hardcoded Values
↓
Terraform
↓
Infrastructure
```

You can now build:

```text
                VARIABLES
                    │
                    ▼
              USER INTENT
                    │
        ┌───────────┴───────────┐
        │                       │
        ▼                       ▼
  DATA SOURCES              FILE DATA
        │                       │
        ▼                       ▼
 EXISTING CLOUD DATA      JSON / YAML /
                         TEMPLATE CONTENT
        │                       │
        └───────────┬───────────┘
                    ▼
                 LOCALS
                    │
                    ▼
          FUNCTIONS + EXPRESSIONS
                    │
          ┌─────────┼─────────┐
          ▼         ▼         ▼
      CONDITIONAL   FOR     CONVERSION
          │      EXPRESSIONS    │
          └─────────┼───────────┘
                    ▼
             NORMALIZED DATA
                    │
          ┌─────────┼──────────┐
          ▼         ▼          ▼
        merge     flatten   templatefile
          │         │          │
          └─────────┼──────────┘
                    ▼
         DYNAMIC CONFIGURATION
                    │
                    ▼
            RESOURCES / MODULES
                    │
                    ▼
             INFRASTRUCTURE
```

The key progression is:

```text
STATIC VALUES
↓
VARIABLE INPUT
↓
DISCOVERED DATA
↓
EXPRESSIONS
↓
FUNCTIONS
↓
TRANSFORMED COLLECTIONS
↓
NORMALIZED CONFIGURATION
↓
DYNAMIC NESTED CONFIGURATION
↓
REUSABLE INFRASTRUCTURE
```

But the production lesson is even more important:

```text
Dynamic Terraform
does not mean
maximum abstraction.
```

It means:

```text
Discover what should be discovered.

Make explicit what should be explicit.

Normalize what needs normalization.

Transform data intentionally.

Preserve stable resource identity.

Keep infrastructure ownership clear.

Keep expressions understandable.

Keep configuration reviewable.
```

The final mental model for Part 9 is:

```text
Variables
+
Data Sources
+
Functions
+
Expressions
+
Templates
+
Careful Dynamic Blocks
↓
Flexible
Predictable
Readable
Infrastructure Configuration
```

That foundation prepares you for the next major Terraform concept:

```text
Reusable Infrastructure
↓
Modules
```
