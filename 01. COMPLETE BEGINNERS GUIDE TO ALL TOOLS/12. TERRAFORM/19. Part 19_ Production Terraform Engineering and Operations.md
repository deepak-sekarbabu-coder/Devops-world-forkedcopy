# Part 19: Production Terraform Engineering and Operations

## Bridge the Gap Between Terraform Tutorials and Real Infrastructure Engineering

By this point, you know how to write Terraform.

You know how to:

* create resources
* configure providers
* use variables and outputs
* work with state
* build modules
* provision AWS infrastructure
* use remote backends
* test Terraform
* detect drift
* run Terraform through CI/CD

Production engineering is where all of those skills must work together safely.

A tutorial asks:

> Can Terraform create this infrastructure?

Production engineering asks:

> Can we operate this infrastructure safely for years while multiple engineers, pipelines, environments, cloud accounts, providers, modules, incidents, upgrades, and business requirements change around it?

Those are very different questions.

A configuration can be technically valid and still be dangerous in production.

For example:

```text
terraform validate
        ↓
Success
```

does not tell you whether:

```text
The state architecture is safe

The IAM role is too powerful

The change will cause downtime

The module is maintainable

The production account is isolated

The plan contains a dangerous replacement

The infrastructure can be recovered

The cost is acceptable

The team knows who owns it
```

Production Terraform is therefore not simply Terraform syntax.

It is an operating model.

# 2. Production IaC Standards

Infrastructure as Code standards define how infrastructure code must be:

```text
Structured
Reviewed
Tested
Secured
Versioned
Deployed
Observed
Maintained
Recovered
Retired
```

Without standards, every Terraform repository evolves differently.

One team may have:

```text
modules/
environments/
tests/
```

Another may have:

```text
main.tf
main-new.tf
main-final.tf
main-final-v2.tf
```

One team pins providers.

Another automatically upgrades them.

One team uses remote state.

Another stores:

```text
terraform.tfstate
```

on a laptop.

Terraform works in all these situations.

Production engineering does not.

---

# 3. Example Production IaC Standard

An organization might establish rules such as:

```text
1. Production infrastructure must be version controlled.

2. Production changes must use pull requests.

3. Direct production applies from engineer laptops are prohibited
   except through documented emergency procedures.

4. Terraform formatting must pass automatically.

5. Terraform validation must pass automatically.

6. Security scanning must pass or have approved exceptions.

7. Policy checks must pass where required.

8. Terraform plans must be reviewed before production apply.

9. Destructive changes require explicit review.

10. Terraform and provider versions must be controlled.

11. Dependency lock files must be committed.

12. Production state must use an approved remote backend.

13. State access must be restricted.

14. State recovery must be documented.

15. Production environments must have defined isolation boundaries.

16. Production deployment identities must follow least privilege.

17. Long-lived cloud credentials should be avoided where practical.

18. Production changes must leave an audit trail.

19. Infrastructure must have documented ownership.

20. Production infrastructure must be monitored after deployment.
```

Your organization may use different rules.

The important idea is that production behavior should be deliberate.

---

# 4. Automate Standards Where Possible

Do not rely entirely on documentation.

Weak:

```text
README:
"Remember to format Terraform."
```

Better:

```bash
terraform fmt -check -recursive
```

inside CI.

Weak:

```text
"Please don't create publicly exposed storage."
```

Better:

```text
Terraform Code
      ↓
Security Scanner
      ↓
Policy Engine
      ↓
Code Review
```

Use automation for deterministic rules.

Use humans for judgment.

# 10. Giant Module Anti-Pattern

Imagine:

```text
module "platform" {
    ...
}
```

and it manages:

```text
VPC
Subnets
Route tables
NAT
IAM
EC2
ALB
RDS
Route 53
S3
CloudWatch
Secrets
```

One module now controls almost the entire platform.

Potential problems:

```text
Huge blast radius

Difficult ownership

Difficult testing

Large interfaces

Slow plans

Tightly coupled releases

Difficult upgrades
```

---

# 11. Tiny Module Anti-Pattern

The opposite is also harmful:

```text
module-vpc/
module-subnet/
module-route-table/
module-route/
module-route-association/
module-tag/
```

Now every Terraform primitive has become an abstraction.

Engineers spend more time navigating module wrappers than understanding infrastructure.

The goal is not:

```text
Maximum abstraction
```

The goal is:

```text
Useful abstraction.
```

---

# 12. Module Design Questions

Before creating a module ask:

```text
Does this represent a reusable capability?

Does it have a coherent lifecycle?

Does it have a clear owner?

Will multiple consumers use it?

Can its interface remain understandable?

Can it be tested independently?

Would abstraction reduce duplication?

Or are we abstracting simply because we can?
```

# 13. Terraform Version Management

Terraform itself changes.

New versions may introduce:

```text
Features

Validation behavior

Language capabilities

Deprecations

State behavior

CLI behavior
```

Production repositories should therefore define supported Terraform versions.

Example:

```hcl
terraform {
  required_version = ">= 1.10, < 2.0"
}
```

This is an example policy.

Choose constraints based on versions your organization has tested.

---

# 14. Why Terraform Version Control Matters

Without version management:

```text
Engineer A
Terraform version X

Engineer B
Terraform version Y

CI
Terraform version Z
```

Now behavior may differ between:

```text
Laptop
CI
Production deployment
```

A better model is:

```text
Approved Terraform Version
          ↓
     ┌────┼────┐
     ↓    ↓    ↓
Developer CI  Automation
```

The goal is reproducibility.

# 16. Provider Versioning

Terraform Core does not directly implement AWS resources.

The architecture is:

```text
Terraform Core
      ↓
AWS Provider
      ↓
AWS API
```

The provider translates Terraform operations into provider-specific API operations.

Providers are separately versioned software dependencies.

---

# 17. Why Provider Upgrades Matter

Provider releases may change:

```text
Schemas

Validation

Resource behavior

Defaults

Deprecations

Bug fixes

State migrations

Supported cloud capabilities
```

Therefore:

```text
Provider Upgrade
=
Infrastructure Change
```

Treat it accordingly.

---

# 18. Provider Version Constraints

Example:

```hcl
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}
```

The exact version policy depends on your environment.

The important principle is:

```text
Do not silently accept arbitrary provider versions.
```

---

# 19. Dependency Lock File

Terraform creates:

```text
.terraform.lock.hcl
```

The dependency lock file records selected provider versions and checksums.

It should normally be committed to version control.

Do not normally place it in:

```text
.gitignore
```

---

# 20. Why the Lock File Matters

Suppose the configuration allows:

```text
AWS Provider
>= 6.0
```

Without a previously selected locked version, different initialization times could potentially select different compatible provider releases.

The lock file creates consistency:

```text
Provider Constraint
      ↓
terraform init
      ↓
Provider Selected
      ↓
.terraform.lock.hcl
      ↓
Future Initialization
      ↓
Previously Selected Provider
```

unless you intentionally upgrade it.

---

# 21. Provider Constraints and Lock Files Solve Different Problems

Constraint:

```text
Which versions are acceptable?
```

Lock file:

```text
Which compatible provider version did this configuration select?
```

You generally need both concepts.

---

# 22. Important Lock-File Limitation

The Terraform dependency lock file currently tracks provider dependencies.

Do not assume:

```text
.terraform.lock.hcl
=
Provider versions
+
Module versions
+
Every dependency
```

Remote modules require their own deliberate version strategy.

---

# 23. Review Lock-File Changes

Suppose a pull request changes:

```text
.terraform.lock.hcl
```

Ask:

```text
Was a provider intentionally upgraded?

Did a provider constraint change?

Was terraform init -upgrade run?

Did a new provider appear?

Are the provider source addresses expected?

Why did checksums change?
```

Dependency changes deserve review.

---

# 24. Do Not Upgrade Providers Accidentally

Avoid making every pipeline run:

```bash
terraform init -upgrade
```

without reason.

That can combine:

```text
Infrastructure Change
+
Provider Upgrade
```

into one deployment.

Prefer explicit dependency upgrades.

# 25. State Boundaries

State boundaries are one of the most important production architecture decisions.

Do not automatically place everything into:

```text
production.tfstate
```

Imagine one state containing:

```text
Production network

Production databases

IAM

DNS

Applications

Monitoring

Shared services
```

One Terraform operation now has a very large operational scope.

---

# 26. State Boundary Mental Model

A state boundary answers:

```text
What changes together?

What locks together?

What can fail together?

What permissions are needed together?

Who owns these resources?

How large is one Terraform operation?
```

State architecture is therefore part of system architecture.

---

# 27. Blast Radius

Blast radius means:

> How much infrastructure could be affected if this change goes wrong?

Example:

```text
One application
```

has a smaller potential blast radius than:

```text
Entire production platform.
```

---

# 28. Blast-Radius Reduction

Possible techniques include:

```text
Separate environments

Separate state

Separate AWS accounts

Separate regions

Separate root modules

Separate deployment roles

Separate pipelines

Clear ownership
```

But excessive fragmentation also creates complexity.

The goal is:

```text
Small enough to control risk
+
Large enough to operate sensibly.
```

---

Instead of:

```text
production.tfstate
```

an organization might use:

```text
production/network

production/data

production/observability
```

Whether those exact boundaries are correct depends on:

```text
Lifecycle

```

# 30. Environment Isolation

Development, staging, and production should have deliberate boundaries.

Conceptually:

```text
Development
├── State
├── Credentials
├── Resources
└── Pipeline

Staging
├── State
├── Credentials
├── Resources
└── Pipeline

Production
├── State
├── Credentials
├── Resources
└── Pipeline
```

Production should not merely mean:

```text
environment = "prod"
```

while every other security and operational boundary remains shared.

---

# 31. Account Isolation

AWS organizations commonly use separate accounts for stronger environment isolation.

Example:

```text
AWS Organization
│
├── Development Account
│
├── Staging Account
│
└── Production Account
```

Potential benefits:

```text
Credential isolation

Policy boundaries

Reduced accidental cross-environment access

Independent quotas

Clearer billing

Reduced blast radius
```

---

# 32. Account Isolation Is Not Enough

Separate accounts protect production from many development mistakes.

They do not protect production from every production mistake.

A production role can still destroy production infrastructure.

You still need:

```text
IAM

Review

Approval

State isolation

Backups

Recovery

Monitoring
```

---

# 33. Region Isolation

Multi-region infrastructure introduces another boundary.

Example:

```text
Production
├── us-east-1
└── us-west-2
```

Ask:

```text
Should these regions deploy independently?

Should they use separate state?

Should one region's lock block another?

Do they have separate failure domains?

Do they have separate owners?

Can one region be changed without touching the other?
```

---

# 34. Provider Aliases Do Not Equal Isolation

Terraform can configure:

```hcl
provider "aws" {
  region = "us-east-1"
}

provider "aws" {
  alias  = "secondary"
  region = "us-west-2"
}
```

That solves provider targeting.

It does not automatically solve:

```text
State isolation

IAM isolation

Deployment isolation

Blast-radius isolation
```

Those remain architectural decisions.

---

# 35. Remote State

Production Terraform should generally use an approved remote state system rather than relying on an engineer's local state file.

Conceptually:

```text
Engineer ─────┐
              │
CI/CD ────────┼──→ Remote Backend
              │         │
Recovery ─────┘         ↓
                       State
```

Benefits include:

```text
Shared access

Centralized authorization

Durability

Automation

Locking where supported

Recovery options
```

---

# 36. Treat State as Production Data

Terraform state contains Terraform's mapping between configuration addresses and real infrastructure.

Example:

```text
aws_vpc.production
        ↓
vpc-0123456789abcdef
```

State may also contain:

```text
Resource identifiers

Network information

Generated values

Provider-returned attributes

Sensitive values
```

State is not a disposable cache.

---

# 37. State Security

Protect remote state with:

```text
Encryption

Restricted access

Audit logging where available

Versioning / backup strategy

Controlled write permissions
```

The exact controls depend on the backend.

---

# 38. State Backup

State backup protects Terraform's management information.

For an S3-based design, a recovery strategy commonly includes:

```text
S3 versioning

Encryption

Restricted IAM

Recovery procedures
```

Do not wait for a state incident before deciding how recovery works.

---

# 39. State Backup Is Not Application Backup

This distinction is critical:

```text
Terraform State Backup
≠
Database Backup
```

State tells Terraform about infrastructure.

It does not automatically preserve:

```text
Customer records

Application files

Database contents

Business data
```

Those require their own backup strategies.

---

# 40. State Recovery

A safe state-recovery mindset is:

```text
Incident
↓
Stop Terraform Writes
↓
Preserve Evidence
↓
Inspect Infrastructure
↓
Inspect Current State
↓
Locate Recovery Data
↓
Determine Correct Recovery Point
↓
Recover Carefully
↓
Plan
↓
Reconcile
↓
Verify
```

Do not blindly restore yesterday's state.

---

# 41. Why Blind Restoration Is Dangerous

Imagine:

```text
09:00
State backup exists

10:00
New production resource created

10:30
State damaged

10:40
Restore 09:00 state
```

Now:

```text
AWS
contains new resource
```

while:

```text
Restored State
does not know it exists.
```

You have created another state/reality mismatch.

---

# 42. State Locking

When the configured backend supports locking, Terraform automatically locks state during operations that could write it.

Conceptually:

```text
Pipeline A
↓
Acquire State Lock
↓
Apply
↓
Write State
↓
Release Lock
```

Meanwhile:

```text
Pipeline B
↓
Attempts Lock
↓
Cannot Acquire
↓
Wait / Fail
```

This prevents concurrent writers from corrupting shared state.

---

# 43. Never Normalize `-lock=false`

Terraform may allow commands such as:

```bash
terraform apply -lock=false
```

Do not use that as a routine solution to lock problems.

A lock may be telling you:

```text
Another process is modifying production.
```

Investigate.

---

# 44. Force Unlock

Terraform provides:

```bash
terraform force-unlock LOCK_ID
```

This is a recovery command.

Use it only after confirming that the lock is stale and no legitimate process still owns it.

Conceptually:

```text
Lock Failure
↓
Identify Lock Holder
↓
Check Pipelines
↓
Check Engineers
↓
Confirm Process Ended
↓
Force Unlock if Necessary
```

Never:

```text
Lock exists
↓
Immediately force-unlock
```

---

# 45. IAM Least Privilege

Terraform may have permission to:

```text
Create VPCs

Modify IAM

Delete compute

Change DNS

Create databases

Delete storage

Modify security groups
```

Terraform deployment identities are therefore highly privileged identities.

---

# 46. Avoid Permanent Administrator Credentials

A convenient setup might be:

```text
CI
↓
AWS Access Key
↓
AdministratorAccess
```

This is easy.

It also creates a large security risk.

Prefer:

```text
CI
↓
Federated Identity
↓
Scoped AWS Role
↓
Temporary Credentials
```

where practical.

---

# 47. Separate Human Identity from CI Identity

Prefer:

```text
Engineer
↓
Git
↓
Pull Request
```

and:

```text

↓

```

rather than:

```text
Engineer Laptop
```

# 49. OIDC

OIDC federation can allow supported CI systems to authenticate to AWS without permanently storing long-lived AWS access keys.

Conceptually:

```text
CI/CD Platform
      ↓
OIDC Token
      ↓
AWS STS
      ↓
Assume IAM Role
      ↓
Temporary Credentials
      ↓
Terraform
```

---

# 50. OIDC Does Not Remove Authorization

Bad trust model:

```text
Any repository
↓
Production AWS Role
```

Better:

```text
Expected CI provider
+
Expected repository
+
Expected branch/environment
+
Expected token conditions
↓
Production Role
```

OIDC solves credential federation.

You must still design trust correctly.

---

# 51. Secrets Management

Do not hardcode secrets:

```hcl
database_password = "SuperSecret123!"
```

Do not commit secret values into Git-backed:

```text
terraform.tfvars
```

Production secrets should use approved secret-management patterns.

---

# 52. `sensitive` Does Not Mean Secret-Free State

Example:

```hcl
variable "database_password" {
  type      = string
  sensitive = true
}
```

`sensitive = true` can prevent normal Terraform CLI output from displaying the value.

It does not automatically remove the underlying value from Terraform state when Terraform needs to store it.

Therefore:

```text
Sensitive
≠
Not Stored
```

---

# 53. Better Secret Architecture

Where possible:

```text
Secret Manager
      ↓
Runtime Application
```

is preferable to unnecessarily routing secret values through:

```text
Secret
↓
Terraform
↓
State
↓
Application
```

Reduce the number of systems that handle secret material.

# 54. Change Review

Before production change approval, answer:

```text
What is changing?

Why is it changing?

Which environment?

Which account?

Which region?

Which state?

Which resources?

Could anything be destroyed?

Could anything be replaced?

Could downtime occur?

Could data be lost?

Could security posture change?

Could cost increase?

```

---

# 55. Code Review and Plan Review Are Different

Code review asks:

```text
Is this Terraform well designed?
```

Plan review asks:

```text
What will Terraform actually attempt to do?
```

You need both.

---

# 56. Plan Review

Terraform plan actions commonly communicate operations such as:

```text
+     Create

~     Update in place

-/+   Replace

-     Destroy
```

Do not review only:

```text
Plan: 5 to add, 2 to change, 1 to destroy.
```

Find the exact resources.

---

# 57. Replacement Is Destructive

A replacement means an existing object will be destroyed as part of creating its replacement, though lifecycle ordering may vary.

Therefore:

```text
-/+
```

deserves special attention.

Ask:

```text
Why is replacement required?

Is the resource stateful?

Can old and new coexist?

Could this cause downtime?

How will traffic move?

What happens to persistent data?
```

---

# 58. Approval Workflows

A mature production pipeline may use:

```text
Pull Request
↓
Automated Checks
↓
Plan
↓
Engineer Review
↓
Production Approval
↓

```

High-risk changes may require additional review.

For example:

```text

↓

+

```

according to organizational policy.

---

# 59. Destructive-Change Controls

Possible controls include:

```text
Plan inspection

Approval gates

Policy as Code

Cloud deletion protection

Terraform lifecycle controls

Backups

Environment protections

Restricted IAM

Separate destroy workflows
```

No single control is enough for every resource.

---

# 60. `prevent_destroy`

Terraform supports:

```hcl
lifecycle {
  prevent_destroy = true
}
```

Example:

```hcl
resource "aws_db_instance" "production" {
  # configuration

  lifecycle {
    prevent_destroy = true
  }
}
```

Terraform will reject a plan that would destroy the resource while this lifecycle rule remains applicable in the configuration.

---

# 61. `prevent_destroy` Is Not a Backup

Do not think:

```text
prevent_destroy = true
↓
Database cannot disappear.
```

It does not replace:

```text
Database backups

Cloud-native deletion protection

IAM controls

Recovery procedures
```

It is one Terraform-side guardrail.

---

# 62. Important `prevent_destroy` Limitation

The lifecycle rule must remain in the resource configuration.

If the entire resource block is removed from configuration, Terraform no longer has that lifecycle rule available to prevent the resulting destroy operation.

That is why production protection must use multiple layers.

---

# 63. Lifecycle Design

Important lifecycle concepts include:

```text
create_before_destroy

prevent_destroy

ignore_changes

replace_triggered_by
```

Use lifecycle behavior deliberately.

Do not use it merely to silence Terraform.

---

# 64. `create_before_destroy`

Example:

```hcl
lifecycle {
  create_before_destroy = true
}
```

Conceptually:

```text
Existing Resource
↓
Create Replacement
↓
Update Dependency Graph
↓
Destroy Previous Resource
```

This can help reduce downtime.

It does not guarantee zero downtime.

---

# 65. Why `create_before_destroy` May Not Be Enough

The cloud API may prohibit two resources with the same:

```text
Name

IP

DNS identity

Unique identifier
```

Or your application architecture may not support simultaneous versions.

Lifecycle configuration cannot compensate for an architecture that requires downtime.

---

# 66. Zero Downtime Is an Architecture Property

This is one of the most important lessons in the chapter.

Terraform cannot magically make:

```text
One server
↓
Destroyed
↓
New server
```

zero downtime.

Minimal-downtime infrastructure requires architecture such as:

```text
Redundancy

Load balancing

Health checks

Multiple instances

Multiple Availability Zones

Traffic shifting

Externalized application state
```

---

# 67. Single-Instance Architecture

```text
Users
  ↓
EC2 A
```

If EC2 A must be replaced:

```text
Users
  ↓
X
```

until the replacement becomes healthy.

---

# 68. Redundant Architecture

```text
               ┌── EC2 A
Users → ALB ───┤
               └── EC2 B
```

Now one instance can potentially be replaced while the other continues serving traffic.

This is why production architecture matters more than a lifecycle flag.

---

# 69. Blue/Green Infrastructure

Blue/green deployment maintains two environments or fleets.

```text
BLUE
Current Production

GREEN
New Version
```

Initially:

```text
Users
↓
Blue

Green
↓
Testing
```

After Green passes verification:

```text
Users
↓
Green

Blue
↓
Temporary Standby
```

---

# 70. Blue/Green Benefits

Potential benefits:

```text
Pre-production verification

Reduced deployment risk

Fast traffic reversal

Reduced replacement downtime

Clear environment comparison
```

Potential costs:

```text
Duplicate infrastructure

Higher cloud cost

More routing complexity

More state complexity

Database compatibility challenges
```

---

# 71. Terraform Blue/Green Example

Terraform might manage:

```text
ALB
│
├── Blue Target Group
│   └── Blue Compute Fleet
│
└── Green Target Group
    └── Green Compute Fleet
```

Traffic can then be shifted through listener/routing configuration.

Exact implementation depends on the architecture.

---

# 72. Blue/Green Does Not Solve Database Migration Automatically

Imagine:

```text
Blue Application
↓
Database Schema v1
```

Green requires:

```text
Database Schema v2
```

If Schema v2 breaks Blue, instant traffic rollback may no longer be possible.

Application, database, and infrastructure deployment strategies must be compatible.

---

# 73. Drift Management

Drift occurs when real infrastructure differs from Terraform's expected configuration/state relationship.

Example:

```text
Terraform:
instance_type = "t3.small"

AWS:
instance_type = "t3.large"
```

Someone or something changed the resource outside the expected Terraform workflow.

---

# 74. Sources of Drift

```text
AWS Console changes

AWS CLI changes

Emergency fixes

Other automation

Cloud service behavior

External controllers

Deleted resources

Manual troubleshooting

Incorrect ownership boundaries
```

---

# 75. Detecting Drift

A normal Terraform plan refreshes its understanding of managed remote objects before comparing configuration unless refresh behavior is deliberately disabled.

Scheduled planning can therefore be used as part of drift detection.

Example:

```text
Scheduled Pipeline
↓
terraform init
↓
terraform plan
↓
Unexpected Difference?
├── No → Record Result
└── Yes → Investigate
```

Do not automatically apply every drift plan.

---

# 76. Drift Investigation

Use:

```text
Detect
↓
Identify Resource
↓
Identify Difference
↓
Determine Actor
↓
Determine Reason
↓
Determine Desired Authority
```

Then decide:

```text
Terraform configuration is correct
↓
Restore infrastructure
```

or:

```text
External change is correct
↓
Update Terraform
```

---

# 77. Refresh-Only Planning

When intentional out-of-band changes need to be examined from the state perspective, Terraform supports:

```bash
terraform plan -refresh-only
```

This allows you to inspect changes to Terraform's recorded understanding without planning normal configuration-driven infrastructure modifications.

Do not confuse:

```text
Refresh State
```

with:

```text
Make Infrastructure Match Configuration.
```

They solve different problems.

---

# 78. Emergency Drift

Sometimes an engineer must change infrastructure manually during an incident.

Example:

```text

↓
Engineer modifies security group
↓
Service restored
```

That may be justified.

After the incident:

```text
Emergency Change
↓
Document
↓
Update Terraform if change should remain
↓
Plan
↓
Review
↓
Re-establish desired-state ownership
```

Do not leave emergency drift indefinitely.

# 82. Safe Import Workflow

```text

↓

↓

↓

↓

↓

↓

↓

↓

↓

↓

↓
```

# 84. Infrastructure Refactoring

Infrastructure code eventually needs restructuring.

Example:

Before:

```hcl
resource "aws_vpc" "main" {
  # ...
}
```

After:

```text
module.network.aws_vpc.main
```

The real VPC did not conceptually change.

But its Terraform address did.

---

# 85. Terraform Addresses Are Identity

Terraform may track:

```text
aws_vpc.main
```

If you move it into a module:

```text
module.network.aws_vpc.main
```

Terraform sees a different address unless you explicitly describe the move.

Without state-aware refactoring, Terraform may plan:

```text
Destroy old address
+
Create new address
```

---

# 86. `moved` Blocks

Terraform provides `moved` blocks for state-aware refactoring.

Example:

```hcl
moved {
  from = aws_vpc.main
  to   = module.network.aws_vpc.main
}
```

Mental model:

```text
Old Terraform Address
↓
Same Managed Object
↓
New Terraform Address
```

---

# 87. Safe Refactoring Workflow

```text
Understand Existing State
↓
Design New Structure
↓
Add moved Blocks
↓
terraform plan
↓
Inspect Every Change
↓
Confirm No Unwanted Replacement
↓
Review
↓
Apply
↓
Verify State
↓
Verify Infrastructure
```

Refactoring Terraform is not merely moving text between files.

---

# 88. `count` to `for_each` Refactoring

Before:

```text
aws_instance.app[0]
aws_instance.app[1]
```

After:

```text
aws_instance.app["api"]
aws_instance.app["worker"]
```

Those are different Terraform addresses.

A seemingly harmless code cleanup can therefore cause replacements if identity migration is not handled correctly.

# 178. Knowledge Check

## Question 1

Why should `.terraform.lock.hcl` normally be committed?

### Answer

Because it records selected provider versions and checksums, helping engineers and automation use consistent provider selections and allowing dependency changes to be reviewed.

---

## Question 2

Does `.terraform.lock.hcl` currently lock remote module versions?

### Answer

No. Provider dependencies are tracked in the dependency lock file. Remote module versioning needs its own deliberate constraints or immutable source strategy.

---

## Question 3

Why is one enormous state file risky?

### Answer

It increases blast radius, permission scope, lock contention, operational coupling, and the number of resources potentially affected by one Terraform operation.

---

## Question 4

Why is `prevent_destroy` not a backup system?

### Answer

It is a Terraform lifecycle guardrail. It does not preserve application data and does not protect against every deletion path.

---

## Question 5

What does `moved` solve?

### Answer

It tells Terraform that a managed object's address has changed, helping preserve resource identity during refactoring rather than treating the new address as an unrelated resource.

---

## Question 6

Why should you not automatically force-unlock state?

### Answer

The lock may belong to an active Terraform process. Removing it could allow concurrent writers and risk state corruption.

---

## Question 7

Does a failed `terraform apply` mean nothing changed?

### Answer

No. Terraform may successfully create, update, or destroy resources before another operation fails.

---

## Question 8

Why should production provider upgrades be deliberate?

### Answer

Provider versions can change schemas, validation, resource behavior, defaults, state migrations, and API interactions.

---

## Question 9

Why is `sensitive = true` not sufficient secret protection?

### Answer

It primarily controls Terraform's display behavior. Sensitive values may still exist in state depending on how they are used.

---

## Question 10

Why is zero downtime not simply a Terraform feature?

### Answer

Because zero or minimal downtime depends primarily on architecture: redundancy, load balancing, health checks, traffic management, replaceable compute, compatible data changes, and similar design decisions.

---

## Question 11

What should happen after emergency manual infrastructure changes?

### Answer

The team should document the change, determine the correct desired state, reconcile Terraform configuration/state with reality, review a new plan, and restore Terraform as the authoritative management path.

---

## Question 12

What is the difference between code review and plan review?

### Answer

Code review evaluates the Terraform design and implementation. Plan review evaluates what Terraform intends to do to real infrastructure.

---

## Question 13

Why should state recovery be followed by `terraform plan`?

### Answer

Because restored state may not perfectly represent current infrastructure. A plan helps reveal differences that must be understood and reconciled.

---

## Question 14

Why should Terraform debug logs be protected?

### Answer

Verbose Terraform and provider logs can contain sensitive infrastructure or operational information.

---

## Question 15

What is the main goal of production Terraform engineering?

### Answer

Not merely to create infrastructure, but to make infrastructure changes reproducible, secure, reviewable, recoverable, observable, maintainable, auditable, and operationally safe.
