# Part 5: Variables, Outputs, Locals, and Configuration Design

## Stop Hardcoding Infrastructure

In the previous parts, you learned how Terraform works, how to write HCL, and how providers and resources connect Terraform to real infrastructure.

Now we need to fix one of the biggest problems in beginner Terraform configurations:

```text
Hardcoding everything.
```

A beginner configuration often starts like this:

```hcl
resource "local_file" "application" {
  filename = "veriqta-development.conf"

  content = <<-EOT
    application=veriqta
    environment=development
    region=us-east-1
    owner=platform-team
  EOT
}
```

It works.

But what happens when you need:

```text
development
staging
production
```

Or:

```text
us-east-1
us-west-2
eu-west-1
```

Or another application?

Or another team?

Copying and editing the entire Terraform configuration is not a good design.

Instead, we separate:

```text
What changes
```

from:

```text
How the infrastructure is built
```

Terraform gives us three fundamental tools for this:

```text
Input Variables
↓
Accept values into the configuration

Locals
↓
Transform, combine, and reuse values internally

Outputs
↓
Expose useful results from the configuration
```

The core architecture for this part is:

```text
Input Variables
↓
Terraform Configuration
↓
Resources
↓
Outputs
```

A more complete mental model is:

```text
External Configuration
↓
Input Variables
↓
var.*
↓
Local Transformations
↓
local.*
↓
Resources
↓
Provider
↓
Infrastructure
↓
Resource Attributes
↓
Outputs
↓
Consumers / Engineers / Automation
```

By the end of Part 5, you should understand:

```text
Input variables
variable blocks
Variable types
Default values
Required variables
Descriptions
Validation
Nullable values
Sensitive variables
Variable precedence

CLI variables
-var
-var-file

Variable definition files
terraform.tfvars
.tfvars
.auto.tfvars

Environment variables
TF_VAR_*

Outputs
output blocks
Sensitive outputs

Locals
locals blocks

When to use variables
When to use locals
When to use outputs

Hardcoding problems
Environment-specific configuration
Naming conventions
Tagging strategy
Configuration composition
```

Most importantly, you should be able to take a configuration full of hardcoded values and redesign it into something reusable, understandable, and safer.

---

# 1. The Hardcoding Problem

Consider:

```hcl
resource "local_file" "application" {
  filename = "veriqta-production.conf"

  content = <<-EOT
    application=veriqta
    environment=production
    region=us-east-1
    owner=platform-team
    cost_center=engineering
  EOT
}
```

Several values are embedded directly in the implementation:

```text
veriqta
production
us-east-1
platform-team
engineering
```

That means changing the deployment requires changing Terraform source code.

---

# 2. Why Hardcoding Becomes a Problem

Hardcoding can cause:

```text
duplication
inconsistent naming
configuration drift
copy-and-paste errors
environment mistakes
difficult reuse
harder code review
larger pull requests
poor module interfaces
```

Imagine three environments.

You could create:

```text
development/main.tf
staging/main.tf
production/main.tf
```

and copy almost everything.

Soon:

```text
development
↓
updated

staging
↓
slightly different

production
↓
forgotten change
```

Now the configurations drift apart.

---

# 3. Configuration vs Values

A better design separates:

```text
Infrastructure Logic
```

from:

```text
Environment Values
```

Example:

```hcl
resource "local_file" "application" {
  filename = "${var.application_name}-${var.environment}.conf"

  content = <<-EOT
    application=${var.application_name}
    environment=${var.environment}
    region=${var.region}
  EOT
}
```

Now:

```text
Terraform logic
↓
stays mostly stable

Input values
↓
can change
```

---

# 4. The Three Value Roles

A useful mental model is:

```text
VARIABLE
↓
Value comes from outside the module

LOCAL
↓
Value is calculated or organized inside the module

OUTPUT
↓
Value is exposed outside the module
```

Think:

```text
INPUT
↓
PROCESS
↓
OUTPUT
```

Terraform version:

```text
variable
↓
resources + locals
↓
output
```

---

# 5. What Is an Input Variable?

An input variable allows a Terraform module to receive a value from outside itself.

Example:

```hcl
variable "environment" {
  type = string
}
```

Terraform can now reference:

```hcl
var.environment
```

Think of the variable as part of the module's interface.

```text
Caller
↓
environment = "production"
↓
variable "environment"
↓
var.environment
↓
Terraform Configuration
```

---

# 6. Variable Block Syntax

General structure:

```hcl
variable "VARIABLE_NAME" {
  type        = TYPE
  description = "DESCRIPTION"
  default     = VALUE
}
```

Not every argument is required.

A simple variable can be:

```hcl
variable "environment" {
  type = string
}
```

---

# 7. Variable Name

The label:

```hcl
variable "environment" {
}
```

creates a variable named:

```text
environment
```

Reference it using:

```hcl
var.environment
```

Notice:

```text
variable
```

is used when declaring it.

```text
var
```

is used when referencing it.

---

# 8. Variable Reference

Declaration:

```hcl
variable "application_name" {
  type = string
}
```

Reference:

```hcl
var.application_name
```

Example:

```hcl
resource "local_file" "application" {
  filename = "${var.application_name}.conf"
  content  = var.application_name
}
```

```hcl
var.application_port
```

```hcl
var.monitoring_enabled
```

```hcl
availability_zones = [
```

Example:

```hcl

  type = set(string)
}
```

Do not depend on:

```text

index 1
index 2
```

with a set the way you would with a list.

# 15. Map Variable

Example:


```hcl

  Environment = "production"
```

```hcl

```


# 16. Object Variable

Objects are useful when several related values belong together.

Example:

```hcl
variable "application" {
  type = object({
    name        = string
    environment = string
    port        = number
    monitoring  = bool
  })
}
```

Value:

```hcl
application = {
  name        = "veriqta-api"
  environment = "production"
  port        = 8080
  monitoring  = true
}
```

References:

```hcl
var.application.name
var.application.environment
var.application.port
var.application.monitoring
```

---

# 17. Why Types Matter

Without clear types, configuration interfaces become harder to understand.

Compare:

```hcl
variable "configuration" {
}
```

with:

```hcl
variable "configuration" {
  type = object({
    environment = string
    region      = string
    replicas    = number
  })
}
```

The second communicates expectations immediately.

Type constraints also allow Terraform to reject incompatible values.

---

# 18. Type Constraint Mental Model

```text
External Value
↓
Variable
↓
Type Constraint
↓
Compatible?
├── Yes → Continue
└── No  → Error
```

This catches mistakes before infrastructure changes occur.

---

# 19. Default Values

A variable can have a default:

```hcl
variable "environment" {
  type        = string
  description = "Deployment environment."
  default     = "development"
}
```

If no value is supplied:

```text
development
```

is used.

---

# 20. Required Variables

A variable without a default is generally required.

Example:

```hcl
variable "project_name" {
  type        = string
  description = "Name of the project."
}
```

Because there is no:

```hcl
default = ...
```

the caller must provide a value.

Mental model:

```text
Default exists
↓
Input may be omitted

No default
↓
Input must be supplied
```

---

# 21. When to Use Defaults

Defaults are appropriate when there is a genuinely safe and sensible default.

Example:

```hcl
variable "monitoring_enabled" {
  type        = bool
  description = "Whether monitoring is enabled."
  default     = true
}
```

But be careful with values such as:

```text
production account
production region
critical network CIDR
database deletion behavior
security-sensitive settings
```

A default can accidentally hide an important decision.

---

# 22. Bad Default Example

Imagine:

```hcl
variable "environment" {
  type    = string
  default = "production"
}
```

A developer forgets to provide an environment.

Terraform silently uses:

```text
production
```

That may be dangerous.

For important environment selection, requiring an explicit value may be better.

---

# 23. Variable Descriptions

Use:

```hcl
description = "..."
```

Example:

```hcl
variable "aws_region" {
  type        = string
  description = "AWS region where application infrastructure is deployed."
}
```

Descriptions should explain:

```text
what the value represents
why it exists
expected format where useful
important constraints
```

---

# 24. Poor Description

Avoid:

```hcl
description = "Region"
```

Better:

```hcl
description = "AWS region where the application's regional infrastructure is deployed."
```

A future engineer should not have to reverse-engineer the purpose.

---

# 25. Variable Validation

Type constraints answer:

```text
What kind of value is this?
```

Validation answers:

```text
Is this particular value acceptable?
```

Example:

```hcl
variable "environment" {
  type        = string
  description = "Deployment environment."

  validation {
    condition = contains(
      ["development", "staging", "production"],
      var.environment
    )

    error_message = "Environment must be development, staging, or production."
  }
}
```

---

# 26. Validation Mental Model

```text
Input
↓
Type Check
↓
Validation Rule
↓
Valid?
├── Yes → Continue
└── No  → Show error_message
```

---

# 27. Why Validation Matters

Without validation:

```text
prod
production
prd
PROD
Production
```

could all appear in different environments.

Then your:

```text
tags
names
policies
monitoring
automation
```

may become inconsistent.

Validation creates a controlled interface.

---

# 28. Numeric Validation

Example:

```hcl
variable "application_port" {
  type        = number
  description = "TCP port used by the application."

  validation {
    condition = (
      var.application_port >= 1 &&
      var.application_port <= 65535
    )

    error_message = "Application port must be between 1 and 65535."
  }
}
```

---

# 29. String Validation

Example:

```hcl
variable "project_name" {
  type        = string
  description = "Project name used in resource naming."

  validation {
    condition     = length(trimspace(var.project_name)) >= 3
    error_message = "Project name must contain at least three non-whitespace characters."
  }
}
```

---

# 30. Validation Should Protect Real Constraints

Do not add complicated validation just because Terraform supports it.

Use validation for meaningful rules such as:

```text
supported environments
allowed regions
valid port range
approved instance families
required naming patterns
acceptable CIDR structures
minimum/maximum sizes
organizational conventions
```

---

# 31. Nullable Variables

Terraform variables support:

```hcl
nullable = true
```

or:

```hcl
nullable = false
```

By default, input variables are nullable.

That means `null` can be accepted unless you explicitly prevent it.

---

# 32. What Does `null` Mean?

`null` generally represents:

```text
absence of a value
```

It can allow Terraform or a provider to behave as though a value was omitted, depending on the surrounding expression or argument.

Example:

```hcl
variable "description" {
  type     = string
  default  = null
  nullable = true
}
```

Now:

```text
null
```

is an intentional allowed value.

---

# 33. Non-Nullable Variable

Example:

```hcl
variable "environment" {
  type        = string
  description = "Deployment environment."
  nullable    = false
}
```

This means:

```text
null is not an acceptable final value.
```

---

# 34. Default and Null Are Different

Consider:

```hcl
variable "environment" {
  type     = string
  default  = "development"
  nullable = true
}
```

If no value is provided:

```text
development
```

is used.

But if the caller explicitly provides:

```hcl
environment = null
```

then `null` can be the value because the variable is nullable.

If that behavior is undesirable:

```hcl
nullable = false
```

can prevent it.

---

# 35. Sensitive Variables

Some input values are sensitive.

Examples:

```text
passwords
API tokens
private credentials
secret strings
database credentials
```

Terraform supports:

```hcl
sensitive = true
```

Example:

```hcl
variable "database_password" {
  type        = string
  description = "Database administrator password."
  sensitive   = true
}
```

---

# 36. What `sensitive = true` Actually Does

It tells Terraform to redact the value in normal CLI/UI presentation where Terraform honors sensitivity.

Instead of showing the value, Terraform may show:

```text
(sensitive value)
```

But this is extremely important:

```text
sensitive
does not automatically mean
not stored
```

Sensitive values can still be stored in:

```text
Terraform state
saved plan files
```

depending on how they are used.

Protect Terraform state accordingly.

---

# 37. Sensitive Does Not Mean Secret Storage

Do not think:

```text
sensitive = true
↓
Terraform encrypted my password
```

That is not what the setting means.

Think:

```text
sensitive = true
↓
Terraform should redact normal presentation
```

State security remains your responsibility.

---

# 38. Current Terraform: Ephemeral Sensitive Inputs

Modern Terraform also supports ephemeral input variables.

For example:

```hcl
variable "api_token" {
  type        = string
  description = "Short-lived API token."
  sensitive   = true
  ephemeral   = true
}
```

An ephemeral value is omitted from Terraform state and plan files.

However, ephemeral values have restrictions on where they can be used.

Do not replace every normal variable with an ephemeral variable.

Use it when the value is temporary and the consuming context supports ephemeral values.

# 39. Variable Values Must Come From Somewhere

A root-module variable can receive values from sources such as:

```text
default value
environment variable
terraform.tfvars
terraform.tfvars.json
*.auto.tfvars
*.auto.tfvars.json
-var-file
-var
HCP Terraform configuration
```

When multiple sources provide the same variable, precedence matters.

---

# 40. Variable Precedence

For normal Terraform CLI root-module variable assignment, a useful precedence model from lower to higher is:

```text
Variable Default
↓
TF_VAR_* Environment Variables
↓
terraform.tfvars
↓
terraform.tfvars.json
↓
*.auto.tfvars / *.auto.tfvars.json
↓
-var / -var-file
```

Later sources override earlier sources when the same variable receives multiple values.

When several command-line options are supplied, their order also matters.

HCP Terraform has additional behavior that should be considered when using that platform.

---

# 41. Why Precedence Matters

Suppose:

```hcl
variable "environment" {
  default = "development"
}
```

Your shell has:

```text
TF_VAR_environment=staging
```

Your:

```text
terraform.tfvars
```

contains:

```hcl
environment = "production"
```

Then the `.tfvars` value has higher precedence than the environment variable in the normal CLI precedence chain.

If you then run:

```bash
terraform plan -var="environment=testing"
```

the command-line value takes precedence.

---

# 42. Never Debug Variable Values by Guessing

When Terraform appears to use an unexpected value, investigate:

```text
default
↓
TF_VAR_*
↓
terraform.tfvars
↓
terraform.tfvars.json
↓
.auto.tfvars files
↓
-var-file
↓
-var
```

Ask:

```text
Where did this value actually come from?
```

# 43. Command-Line Variables With `-var`

Example:

```bash
terraform plan -var="environment=staging"
```

Another:

```bash
terraform apply -var="environment=staging"
```

Multiple values:

```bash
terraform plan \
  -var="environment=staging" \
  -var="application_port=8080"
```

---

# 44. When `-var` Is Useful

`-var` can be useful for:

```text
quick experiments
temporary overrides
CI/CD inputs
testing a configuration
one-off plans
```

But a huge command such as:

```text
terraform plan -var=... -var=... -var=... -var=...
```

quickly becomes difficult to manage.

For groups of configuration values, variable files are often cleaner.

Common extensions:


```text

```

# 47. Environment-Specific Variable Files

A common learning pattern is:

```text
environments/
├── development.tfvars
├── staging.tfvars

```

```hcl
# environments/development.tfvars

```

Production:


Same Terraform logic.

Different input values.

```text
          │
```

---

# 49. `terraform.tfvars`

Terraform automatically loads:

```text
terraform.tfvars
```

when present in the working directory.

Example:

```hcl
project_name = "veriqta"
environment  = "development"
```

You do not need:

```bash
-var-file="terraform.tfvars"
```

for Terraform to discover that standard filename.

---

# 50. `terraform.tfvars.json`

Terraform also automatically recognizes:

```text
terraform.tfvars.json
```

Example:

```json
{
  "project_name": "veriqta",
  "environment": "development"
}
```

HCL `.tfvars` files are generally more natural for humans writing Terraform.

JSON can be useful when another system generates the configuration.

---

# 51. `.auto.tfvars`

Files ending in:

```text
.auto.tfvars
```

are automatically loaded.

Example:

```text
01-global.auto.tfvars
20-environment.auto.tfvars
```

Terraform loads automatic variable files in lexical filename order.

Therefore naming can affect precedence among those files.

---

# 52. `.auto.tfvars.json`

Terraform also supports:

```text
*.auto.tfvars.json
```

These are automatically loaded similarly.

---

# 53. Be Careful With Too Many Automatic Files

A directory like:

```text
01-global.auto.tfvars
10-team.auto.tfvars
20-region.auto.tfvars
30-environment.auto.tfvars
40-secret.auto.tfvars
50-override.auto.tfvars
```

may technically work.

But now an engineer has to hunt through many files to discover:

```text
Why is this value production?
```

Automation should not destroy readability.

Use a clear configuration strategy.

---

# 54. `TF_VAR_*` Environment Variables

Terraform can read root-module variable values from environment variables using:

```text
TF_VAR_VARIABLE_NAME
```

Example variable:

```hcl
variable "environment" {
  type = string
}
```

Environment variable:

```text
TF_VAR_environment
```

---

# 55. Linux/macOS Example

```bash
export TF_VAR_environment="development"
terraform plan
```

Terraform can use:

```text
development
```

for:

```hcl
var.environment
```

---

# 56. PowerShell Example

```powershell
$env:TF_VAR_environment = "development"
terraform plan
```

Remove it later:

```powershell
Remove-Item Env:TF_VAR_environment
```

---

# 57. Environment Variables and CI/CD

Environment variables can be useful in automation.

Conceptually:

```text
CI Secret / Pipeline Variable
↓
TF_VAR_database_password
↓
Terraform Variable
```

But remember:

```text
TF_VAR_*
```

does not automatically mean:

```text
secret will never enter Terraform state
```

The final storage behavior depends on how the value is used.

---

# 58. Do Not Commit Secrets in `.tfvars`

Bad:

```text
production.tfvars
```

containing:

```hcl
database_password = "RealProductionPassword123!"
```

then committed to Git.

Even if:

```hcl
variable "database_password" {
  sensitive = true
}
```

the Git file still contains the plaintext secret.

`sensitive` cannot undo that.

---

# 59. `.gitignore` Strategy

A learning project might use:

```gitignore
.terraform/
*.tfstate
*.tfstate.*
crash.log
crash.*.log
*.tfplan

*.tfvars
*.tfvars.json
```

But this creates another question:

```text
How do we commit non-secret example configuration?
```

One pattern is:

```text
development.tfvars.example
```

or another documented example file that contains no secrets.

Your team's policy should be explicit.

---

# 60. Not Every `.tfvars` File Is Secret

A file containing:

```hcl
environment = "development"
region      = "us-east-1"
```

is not inherently secret.

The reason many teams ignore `.tfvars` broadly is to reduce the chance of accidentally committing sensitive environment-specific values.

Choose a deliberate repository policy rather than blindly copying `.gitignore`.

# 62. `versions.tf`

Create:

```hcl
terraform {
  required_version = ">= 1.10.0, < 2.0.0"

  required_providers {
    local = {
      source  = "hashicorp/local"
      version = ">= 2.5.0, < 3.0.0"
    }
  }
}
```

Do not assume the newest available provider version from a tutorial.

Allow Terraform to resolve a compatible version and inspect:

```text
.terraform.lock.hcl
```

after initialization.

# 63. `variables.tf`

Create:

```hcl
variable "project_name" {
  type        = string
  description = "Project name used in generated resource names."
  nullable    = false

  validation {
    condition     = length(trimspace(var.project_name)) >= 3
    error_message = "Project name must contain at least three non-whitespace characters."
  }
}

variable "environment" {
  type        = string
  description = "Deployment environment."
  nullable    = false

  validation {
    condition = contains(
      ["development", "staging", "production"],
      var.environment
    )

    error_message = "Environment must be development, staging, or production."
  }
}

variable "application_port" {
  type        = number
  description = "Port used by the application."
  default     = 8080

  validation {
    condition = (
      var.application_port >= 1 &&
      var.application_port <= 65535
    )

    error_message = "Application port must be between 1 and 65535."
  }
}

variable "monitoring_enabled" {
  type        = bool
  description = "Whether monitoring is enabled."
  default     = true
}

variable "owner" {
  type        = string
  description = "Team responsible for the application."
  default     = "platform-team"
}

variable "cost_center" {
  type        = string
  description = "Cost allocation identifier."
  default     = "engineering"
}
```

# 68. What Is a Local Value?

A local value gives a name to an expression used inside a Terraform module.

Declaration:

```hcl
locals {
  resource_name = "${var.project_name}-${var.environment}"
}
```

Reference:

```hcl
local.resource_name
```

Notice:

```text
locals
```

is plural when declaring the block.

```text
local
```

is singular when referencing a value.

---

# 69. Variable vs Local

This distinction is fundamental.

Variable:

```text
Value enters the module.
```

Local:

```text
Value is created or transformed inside the module.
```

Example:

```hcl
variable "project_name" {
  type = string
}

variable "environment" {
  type = string
}

locals {
  resource_name = "${var.project_name}-${var.environment}"
}
```

Inputs:

```text
veriqta
production
```

Internal derived value:

```text
veriqta-production
```

---

# 70. When to Use a Variable

Use a variable when the caller should be able to decide the value.

Examples:

```text
environment
region
instance size
network CIDR
application name
replica count
feature toggle
approved configurable port
```

Ask:

```text
Should someone deploying this configuration be able to choose this?
```

If yes, it may belong as an input variable.

---

# 71. When Not to Use a Variable

Do not make every string configurable.

Bad design can look like:

```text
50 variables
↓
caller must understand implementation details
↓
module becomes difficult to use
```

If a value is an internal implementation detail that should remain consistent, a local may be better.

---

# 72. When to Use a Local

Use locals when:

```text
a value is derived from inputs
an expression is repeated
a naming convention should be centralized
tags need to be composed
complex expressions need readable names
internal configuration should be calculated
```

Example:

```hcl
locals {
  resource_prefix = "${var.project_name}-${var.environment}"
}
```

---

# 73. When Not to Use a Local

Do not create a local merely to rename every variable.

Unnecessary:

```hcl
locals {
  project_name = var.project_name
  environment  = var.environment
  port         = var.application_port
}
```

Then:

```hcl
local.project_name
```

adds little value.

It introduces another level of indirection.

Use locals when they improve clarity.

# 78. Why Locals Improve Configuration Design

Without locals:


Repeated across:

```text

```

If naming changes, you edit ten locations.

With a local:


```hcl

```

Change once.

Reuse everywhere.

# 87. Tagging Strategy

Cloud tags are metadata associated with resources that support them.

Common examples:

```text

```

# 88. Centralize Common Tags

Instead of repeating:

```hcl
tags = {
  Project     = var.project_name
  Environment = var.environment
  Owner       = var.owner
  ManagedBy   = "Terraform"
}
```

on every resource, create:

```hcl
locals {
  common_tags = {
    Project     = var.project_name
    Environment = var.environment
    Owner       = var.owner
    ManagedBy   = "Terraform"
  }
}
```

Then reuse:

```hcl
tags = local.common_tags
```

where the provider resource supports tags.

---

# 89. Resource-Specific Tags

Sometimes you need common tags plus resource-specific tags.

Use:

```hcl
merge()
```

Example:

```hcl
tags = merge(
  local.common_tags,
  {
    Name      = "${local.resource_prefix}-api"
    Component = "api"
  }
)
```

Concept:

```text
Common Tags
+
Resource Tags
↓
Final Tag Map
```

---

# 90. Tagging Conflict

Suppose:

```hcl
local.common_tags
```

contains:

```hcl
Component = "shared"
```

and later:

```hcl
merge(
  local.common_tags,
  {
    Component = "api"
  }
)
```

The later map wins for the duplicate key.

Understand merge order.

Do not accidentally override governance tags.

# 91. Tagging Strategy Should Be Documented

A team should decide:

```text

Which are optional?

Who owns tag values?

Which values are validated?

Which tags are inherited?

Which tags may resources override?

How are cost tags handled?

How are ownership tags handled?
```

Terraform can help enforce consistency.

# 94. Avoid Giant Environment Conditionals

This is technically possible:

```hcl
instance_type = var.environment == "production" ? "large" : "small"
```

A few controlled conditions can be useful.


Use explicit variables, locals, maps, modules, or separate architecture where appropriate.

# 95. Environment Configuration Maps

Sometimes environment behavior can be represented as a map.

Example:

```hcl
locals {
  environment_settings = {
    development = {
      monitoring = false
      replicas   = 1
    }

    staging = {
      monitoring = true
      replicas   = 2
    }

    production = {
      monitoring = true
      replicas   = 3
    }
  }

  current_settings = local.environment_settings[var.environment]

```

Then:

```hcl
local.current_settings.replicas
```

selects the value for the chosen environment.

# 96. Do Not Hide Important Decisions

The previous pattern can be useful.

But imagine a giant map containing:

```text

```

Now changing production requires digging through internal implementation code.

Ask whether the value should instead be:

```text

```

Configuration design is about clarity, not cleverness.


If the explicitly supplied command-line variable file also defines `owner`, its command-line source has higher precedence.

For a clearer experiment, temporarily remove `owner` from the explicit variable file or use a variable not defined there.

The goal is to understand source precedence, not memorize an artificial result.

# 133. Failure Lab: Sensitive Value Propagation

Suppose:

```hcl
variable "demo_secret" {
  type      = string
  sensitive = true
}
```

Then:

```hcl
locals {
  combined_value = "prefix-${var.demo_secret}"
}
```

Terraform propagates sensitivity through expressions referencing sensitive values.

If you try to expose that through a normal output, Terraform can require the output to be marked sensitive.

This helps prevent accidental disclosure.

# 134. Do Not Use `nonsensitive()` Casually

Terraform has:

```hcl
nonsensitive(...)
```

for explicitly removing the sensitive marking from a value when you know the resulting value is safe to reveal.

This is not:

```text
decrypt secret safely
```

It means:

```text
I am explicitly telling Terraform this value may be displayed.
```

Use it only when you fully understand the data.

# 142. Configuration File Organization

Terraform loads all `.tf` files in a module directory as one configuration.

Files such as:

```text
variables.tf
locals.tf
main.tf
outputs.tf
providers.tf
versions.tf
```

are organizational conventions.

Terraform does not execute:

```text
variables.tf first
then locals.tf
then main.tf
```

because of filenames.

The configuration is evaluated as a whole according to Terraform's dependency model.

Splitting helps humans.

Example:

```text

↓

providers.tf
↓
provider configuration

variables.tf
↓
input interface

locals.tf
↓
internal derived values

main.tf
↓
primary resources

outputs.tf
↓
output interface
```

This is about readability, not execution order.

is usually unnecessary.

Balance organization and discoverability.

# 205. Variables vs Locals vs Outputs

| Construct | Purpose                     | Direction     |
| --------- | --------------------------- | ------------- |
| Variable  | Accept configurable value   | Into module   |
| Local     | Derive/reuse internal value | Inside module |
| Output    | Expose useful result        | Out of module |

```text
Variable
↓
Input

Local
↓
Internal composition

Output
↓
Exported result
```

```text
     ↓

     ↓
```

# 213. Security Scenario

A developer creates:

```hcl
variable "database_password" {
  type      = string
  sensitive = true
}
```

Then commits:

```hcl
database_password = "RealPassword123!"
```

to:

```text
production.tfvars
```

Question:

```text
Is the secret safe because the variable is sensitive?
```

Answer:

```text
No.
```

`sensitive` controls Terraform's presentation behavior.

It does not remove the secret from the committed file.

The credential is now exposed through source control.

It should be rotated and removed using the repository's secret-remediation process.
