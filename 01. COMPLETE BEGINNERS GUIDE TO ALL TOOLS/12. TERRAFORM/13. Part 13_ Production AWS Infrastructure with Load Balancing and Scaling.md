# Part 13: Production AWS Infrastructure with Load Balancing and Scaling

## Build Infrastructure That Resembles a Real Application Platform

In Part 12, we built this:

```text
Terraform
↓
AWS Provider
↓
VPC
↓
Subnet
↓
Security Group
↓
IAM Role
↓
EC2
↓
Application
```

That taught us how to provision compute safely.

But there is a major problem.

A single EC2 instance is still a single compute endpoint.

If that instance:

* crashes
* becomes unhealthy
* needs replacement
* reaches capacity
* sits in an unavailable Availability Zone
* fails during deployment

the application can become unavailable.

Production architecture needs another layer.

We want to move toward:

```text
Users
↓
DNS
↓
HTTPS
↓
Application Load Balancer
↓
Target Group
↓
Auto Scaling Group
↓
EC2 Instances
↓
Application
```

And physically across AWS:

```text
                           INTERNET
                              │
                              ▼
                         ROUTE 53
                              │
                              ▼
                            HTTPS
                              │
                              ▼
                  APPLICATION LOAD BALANCER
                     PUBLIC SUBNETS
                    /              \
                   /                \
          Public Subnet A      Public Subnet B
                 │                  │
                 └────────┬─────────┘
                          │
                          ▼
                     TARGET GROUP
                          │
                 ┌────────┴────────┐
                 │                 │
                 ▼                 ▼
              EC2 A             EC2 B
          Private Subnet A   Private Subnet B
                 │                 │
                 └────────┬────────┘
                          │
                          ▼
                     APPLICATION
```

The important architectural change is:

```text
Internet
↓
Load Balancer
↓
Private Application Instances
```

instead of:

```text
Internet
↓
Individual EC2 Instance
```

That distinction matters.

---

# 1. The Problem With One EC2 Instance

Imagine your application runs on:

```text
EC2 A
```

Users connect directly to it.

Architecture:

```text
Users
↓
Public IP
↓
EC2 A
↓
Application
```

What happens when EC2 A fails?

```text
EC2 A fails
↓
Application unavailable
```

What happens when traffic exceeds its capacity?

```text
Traffic increases
↓
EC2 overloaded
↓
Slow responses
↓
Errors
↓
Possible outage
```

What happens when the Availability Zone experiences a problem?

Again:

```text
Application unavailable
```

A more resilient platform needs:

```text
Multiple instances
+
Multiple Availability Zones
+
Traffic distribution
+
Health detection
+
Automatic replacement
+
Capacity management
```

---

# 2. Production Platform Mental Model

Think of the platform as several separate responsibilities.

```text
DNS
↓
Find the application

TLS
↓
Protect client connection

Load Balancer
↓
Accept and distribute traffic

Target Group
↓
Track application targets and health

Auto Scaling Group
↓
Maintain desired compute capacity

↓
Define how new EC2 instances are created

EC2
↓

```

Each component solves a different problem.

# 3. Our Architecture

We will build toward:

```text
Users
↓
Route 53
↓
HTTPS :443
↓
Application Load Balancer
├── Public Subnet A
└── Public Subnet B
↓
Target Group
↓
Application Security Group
↓
Auto Scaling Group
├── EC2 A → Private Subnet A
└── EC2 B → Private Subnet B
↓
Application
```

The application instances do not need public IPv4 addresses merely to receive traffic from the ALB.

---

# 4. What Is Load Balancing?

Load balancing distributes incoming traffic across multiple application targets.

Without load balancing:

```text
Users
↓
EC2 A
```

With load balancing:

```text
              ┌── EC2 A
Users → ALB ──┼── EC2 B
              └── EC2 C
```

The user does not need to know:

```text
which EC2 instance
```

handled the request.

The user talks to the load balancer.

---

# 5. Elastic Load Balancing

AWS provides Elastic Load Balancing.

Different load balancer types exist for different requirements.

In this chapter we use:

```text
Application Load Balancer
```

commonly abbreviated:

```text
ALB
```

---

# 6. What Is an Application Load Balancer?

An Application Load Balancer operates at the application layer and is designed for HTTP and HTTPS workloads.

It can make routing decisions using application-level information.

Conceptually:

```text
HTTP/HTTPS Request
↓
Application Load Balancer
↓
Listener
↓
Listener Rule
↓
Target Group
↓
Healthy Target
```

---

# 7. Why Use an ALB?

An ALB provides capabilities such as:

```text
HTTP traffic distribution
HTTPS termination
Health-aware routing
Host-based routing
Path-based routing
Multiple target groups
Integration with Auto Scaling
Multiple Availability Zones
AWS Certificate Manager integration
Security Groups
```

This gives us a much stronger application entry point than a public EC2 address.

---

# 8. ALB Architecture

```text
Internet
↓
Application Load Balancer
├── Listener :80
└── Listener :443
        ↓
   Listener Rules
        ↓
   Target Group
        ↓
Healthy EC2 Targets
```

Do not think of the ALB as simply:

```text
a public IP
```

Think of it as a managed application traffic layer.

# 9. Internet-Facing vs Internal Load Balancer

An ALB can be created with different exposure models.

For our public web application:

```text
Internet-Facing ALB
```

is appropriate.

Architecture:

```text
Internet
↓
Public ALB
↓
Private Application Instances
```

For an internal service:

```text
Internal ALB
↓
Private Backend Services
```

may be appropriate.

# 10. Public Load Balancer Does Not Mean Public EC2

This distinction is extremely important.

You can have:

```text
PUBLIC
Application Load Balancer
```

while the application servers are:

```text
PRIVATE
EC2 Instances
```

Architecture:

```text
Internet
      │
      ▼
┌──────────────────────────────┐
│       PUBLIC SUBNETS         │
│                              │
│    Application Load          │
│       Balancer               │
└─────────────┬────────────────┘
              │
              ▼
┌──────────────────────────────┐
│       PRIVATE SUBNETS        │
│                              │
│   EC2 A          EC2 B       │
│                              │
└──────────────────────────────┘
```

This reduces direct exposure of application compute.

# 11. Multiple Availability Zones

Production workloads should consider failure domains.

Instead of:

```text
Availability Zone A
└── Everything
```

use:

```text
Region
├── Availability Zone A
└── Availability Zone B
```

Our architecture becomes:

```text
                    ALB
                  /     \
                 /       \
               AZ A      AZ B
                │          │
              EC2 A      EC2 B
```

---

# 12. Why Multiple Availability Zones?

Suppose:

```text
EC2 A
```

fails.

Traffic can still reach:

```text
EC2 B
```

Suppose an Availability Zone has a significant problem.

A properly designed multi-AZ application may continue serving through capacity in another AZ.

Multi-AZ design does not magically make every application highly available, but it removes a major single-zone dependency.

# 15. Application Load Balancer Resource

Terraform uses:

```hcl
resource "aws_lb" "application" {
  name               = "${local.name_prefix}-alb"
  internal           = false
  load_balancer_type = "application"

  security_groups = [
    aws_security_group.alb.id
  ]

  subnets = [
    aws_subnet.public_a.id,
    aws_subnet.public_b.id
  ]

  tags = merge(
    local.common_tags,
    {
      Name = "${local.name_prefix}-alb"
    }
  )
}
```

Read it as architecture.

---

# 16. `internal = false`

```hcl
internal = false
```

means we are creating an internet-facing load balancer.

Conceptually:

```text

↓
ALB
```

```hcl
internal = true
```

would represent a different accessibility model.

# 19. ALB Security Group

The load balancer needs its own Security Group.

Do not reuse one giant Security Group for everything.

Create:

```hcl
resource "aws_security_group" "alb" {
  name        = "${local.name_prefix}-alb-sg"
  description = "Security group for the public application load balancer"
  vpc_id      = aws_vpc.main.id

  tags = merge(
    local.common_tags,
    {
      Name = "${local.name_prefix}-alb-sg"
    }
  )
}
```

---

# 20. Security Group Architecture

```text
Internet
↓

```

```text

EC2
```

# 21. HTTPS Inbound Rule

For a public HTTPS application:

```text

↓

↓

```

Conceptually:

```text

TCP 443

```

For a genuinely public website, the intended clients may be the public internet.

# 27. What Is a Listener?

A listener checks for incoming connection requests using a configured:

```text
Protocol
+
Port
```

Examples:

```text
HTTP :80

HTTPS :443
```

The listener then applies routing rules.

---

# 28. Listener Mental Model

```text
Client Request
↓
ALB
↓
Listener
↓
Rule
↓
Action
↓
Target Group
```

A load balancer without the required listener cannot process that intended client traffic.

---

# 29. HTTP Listener

A simple HTTP listener could forward traffic:

```hcl
resource "aws_lb_listener" "http" {
  load_balancer_arn = aws_lb.application.arn
  port              = 80
  protocol          = "HTTP"

  default_action {
    type             = "forward"
    target_group_arn = aws_lb_target_group.application.arn
  }
}
```

For a production HTTPS site, however, we usually want HTTP redirected to HTTPS instead.

---

# 30. HTTP-to-HTTPS Redirect

Example:

```hcl
resource "aws_lb_listener" "http" {
  load_balancer_arn = aws_lb.application.arn
  port              = 80
  protocol          = "HTTP"

  default_action {
    type = "redirect"

    redirect {
      port        = "443"
      protocol    = "HTTPS"
      status_code = "HTTP_301"
    }
  }
}
```

Traffic becomes:

```text
http://app.example.com
↓
ALB :80
↓
301 Redirect
↓
https://app.example.com
```

# 31. What Is a Target Group?

A target group represents destinations that receive traffic from the load balancer.

Architecture:

```text
ALB
↓
Listener
↓
Target Group
├── Target A
├── Target B
└── Target C
```

The target group also defines how AWS evaluates target health.

---

# 32. Target Types

Depending on architecture, ALB target groups can work with supported target types such as:

```text
Instance
IP
Lambda
```

For our EC2 Auto Scaling architecture, we use:

```text
instance
```

---

# 33. Target Group Resource

Example:

```hcl
resource "aws_lb_target_group" "application" {
  name        = "${local.name_prefix}-tg"
  port        = 8080
  protocol    = "HTTP"
  vpc_id      = aws_vpc.main.id
  target_type = "instance"

  health_check {
    enabled             = true
    path                = "/health"
    protocol            = "HTTP"
    port                = "traffic-port"
    healthy_threshold   = 2
    unhealthy_threshold = 3
    timeout             = 5
    interval            = 30
    matcher             = "200"
  }

  tags = merge(
    local.common_tags,
    {
      Name = "${local.name_prefix}-tg"
    }
  )
}
```

The exact thresholds should be chosen for the application's behavior, not copied blindly.

# 35. TLS Termination

The client connection is:

```text
Client
↓
HTTPS
↓
ALB
```

The ALB decrypts the HTTPS connection.

Then it can forward:

```text
HTTP
```

to the backend.

Architecture:

```text
Client
   │
 HTTPS
   │
   ▼
  ALB
   │
 HTTP
   │
   ▼
 EC2
```

Some security requirements may call for encryption between the load balancer and targets too. That is a separate design decision.

---

# 36. What Is a Health Check?

The load balancer needs to know:

```text
Can this target successfully serve traffic?
```

It sends periodic health-check requests.

Example:

```text
GET /health
```

If the target repeatedly responds according to the configured success criteria:

```text
Healthy
```

If it repeatedly fails:

```text
Unhealthy
```

---

# 37. Health Check Flow

```text
ALB
↓
Target Group Health Check
↓
EC2
↓
Application
↓
/health
↓
HTTP response
```

The load balancer uses this information to determine which registered targets should receive traffic.

---

# 38. A Running EC2 Instance Is Not Necessarily a Healthy Application

This distinction is critical.

AWS may report:

```text
EC2
RUNNING
```

while:

```text
Application
BROKEN
```

Examples:

```text
Process crashed

Wrong port

Database unavailable

Bad configuration

Application startup failed

Health endpoint returning 500
```

Therefore:

```text
EC2 running
≠
Application healthy
```

---

# 39. Health Endpoint

A useful application might expose:

```text
/health
```

For example:

```text
GET /health
↓
200 OK
```

when the application is able to serve requests.

Do not make health checks unnecessarily expensive.

---

# 40. Health Check Design

Ask:

```text
What does healthy mean?

Process running?

HTTP server responding?

Application initialized?

Critical dependencies available?

Can this instance safely receive user traffic?
```

A health endpoint should reflect the type of health the load balancer needs to know.

---

# 41. Bad Health Check

Suppose:

```text
/health
```

always returns:

```text
200
```

even when the application cannot serve users.

Then:

```text
ALB thinks target healthy
↓
Traffic routed
↓
Users receive errors
```

Your health check is not useful.

---

# 42. Overly Strict Health Check

The opposite can also happen.

Suppose health depends on ten external systems.

One noncritical dependency briefly fails.

Every instance reports unhealthy.

The ALB removes all targets.

Your health check may have amplified the outage.

Health-check design requires judgment.

---

# 43. Target Health States

Targets can move through states related to registration and health.

The important beginner mental model is:

```text
Register
↓
Initial health evaluation
↓
Healthy
↓
Receives traffic
```

or:

```text
Registered
↓
Health checks fail
↓
Unhealthy
↓
Not used for normal routing
```

---

# 44. Target Registration

With individual EC2 resources, you can explicitly register instances.

But once we introduce an Auto Scaling Group, we generally want:

```text
Auto Scaling Group
↓
Target Group
```

integration.

Then instances launched by the ASG can be registered automatically.

---

# 45. Why Manual Target Registration Is Wrong for Auto Scaling

Imagine manually registering:

```text
EC2 A
EC2 B
```

Then Auto Scaling terminates EC2 A and launches:

```text
EC2 C
```

Your static registration model becomes stale.

Better:

```text
Auto Scaling Group
↓
Target Group integration
↓
Instances automatically enter/leave target group
```

The platform manages membership dynamically.

# 46. Multiple EC2 Instances

```text
aws_instance.application
```

# 47. What Is a Launch Template?

A Launch Template defines how EC2 instances should be launched.

Think:

```text
Launch Template
=
EC2 blueprint
```

It can describe things such as:

```text
AMI

Instance type

IAM instance profile

Security Groups

User data

Storage configuration

Metadata options

Tags
```

---

# 48. Why Not Create Every EC2 Instance Manually?

You could write:

```text
EC2 A
EC2 B
EC2 C
EC2 D
```

as separate resources.

But then:

```text
Who replaces failed instances?

Who adjusts fleet size?

Who launches new capacity?

Who removes capacity?

Who maintains desired count?
```

Auto Scaling solves those fleet-management problems.

---

# 49. Launch Template Mental Model

```text
Launch Template
↓
Defines Instance Configuration
↓
Auto Scaling Group
↓
Launches EC2 Instances
```

The Launch Template does not mean:

```text
one EC2 instance
```

It defines how instances should be created.

---

# 50. Launch Template Resource

Example:

```hcl
resource "aws_launch_template" "application" {
  name_prefix   = "${local.name_prefix}-app-"
  image_id      = data.aws_ami.application.id
  instance_type = var.instance_type

  vpc_security_group_ids = [
    aws_security_group.application.id
  ]

  iam_instance_profile {
    name = aws_iam_instance_profile.application.name
  }

  metadata_options {
    http_endpoint = "enabled"
    http_tokens   = "required"
  }

  user_data = base64encode(
    file("${path.module}/scripts/bootstrap.sh")
  )

  block_device_mappings {
    device_name = var.root_device_name

    ebs {
      volume_type           = "gp3"
      volume_size           = var.root_volume_size
      encrypted             = true
      delete_on_termination = true
    }
  }

  tag_specifications {
    resource_type = "instance"

    tags = merge(
      local.common_tags,
      {
        Name = "${local.name_prefix}-application"
      }
    )
  }
}
```

---

# 51. Launch Template User Data

Notice:

```hcl
user_data = base64encode(
  file("${path.module}/scripts/bootstrap.sh")
)
```

Launch Template user data is supplied in the encoded form expected by the API/provider interface.

Do not confuse this with the exact syntax used by every other EC2-related Terraform resource.

# 52. Launch Template Versions

Conceptually:


This is useful because infrastructure teams can reason about which configuration new instances should launch from.

# 53. Auto Scaling Concepts

Auto Scaling is about maintaining and adjusting compute capacity.

Think:

```text
Required Capacity
↓
Auto Scaling Group
↓
EC2 Fleet
```

The Auto Scaling Group can:

```text
Launch instances

Terminate instances

Maintain desired capacity

Replace unhealthy capacity

Distribute capacity across configured subnets/AZs

Scale capacity according to policies
```

---

# 54. What Is an Auto Scaling Group?

An Auto Scaling Group, or ASG, manages a collection of EC2 instances as a group.

Instead of:

```text
Manage EC2 A manually

Manage EC2 B manually

Manage EC2 C manually
```

you manage:

```text
Application ASG
```

The ASG manages the fleet.

---

# 55. ASG Mental Model

```text
Launch Template
↓
Auto Scaling Group
↓
Desired Capacity
↓
EC2 Instances
↓
Target Group
↓
ALB
```

---

# 56. Minimum Capacity

Example:

```text
min_size = 2
```

This means the group should not normally scale below two instances under its configured scaling behavior.

Conceptually:

```text
Minimum
=
lower capacity boundary
```

---

# 57. Desired Capacity

Example:

```text
desired_capacity = 2
```

This represents the capacity the group currently attempts to maintain.

Conceptually:

```text
Desired
=
current intended fleet size
```

---

# 58. Maximum Capacity

Example:

```text
max_size = 6
```

This defines the upper scaling boundary.

Conceptually:

```text
Maximum
=
upper capacity boundary
```

---

# 59. Capacity Relationship

A normal configuration satisfies:

```text
Minimum
≤
Desired
≤
Maximum
```

Example:

```text
Min     = 2
Desired = 2
Max     = 6
```

The fleet begins around:

```text
2 instances
```

and scaling policies may later move capacity within the configured limits.

---

# 60. Why Minimum Capacity Matters

Suppose:

```text
min_size = 1
```

Then your multi-AZ architecture could shrink to one instance.

That may undermine your availability objective.

For an architecture intended to maintain at least one application instance across two failure domains, a minimum of two may be more appropriate, though actual production requirements depend on workload design.

---

# 61. Why Maximum Capacity Matters

Without intentional upper bounds, scaling can have:

```text
Cost consequences

Service quota implications

Downstream capacity implications

Operational consequences
```

Scaling is not:

```text
infinite servers for free.
```

---

# 62. ASG Resource

Example:

```hcl
resource "aws_autoscaling_group" "application" {
  name = "${local.name_prefix}-asg"

  min_size         = var.asg_min_size
  desired_capacity = var.asg_desired_capacity
  max_size         = var.asg_max_size

  vpc_zone_identifier = [
    aws_subnet.private_a.id,
    aws_subnet.private_b.id
  ]

  target_group_arns = [
    aws_lb_target_group.application.arn
  ]

  health_check_type         = "ELB"
  health_check_grace_period = 300

  launch_template {
    id      = aws_launch_template.application.id
    version = aws_launch_template.application.latest_version
  }
}
```

Review current provider behavior and your deployment strategy before choosing how Launch Template versions should be referenced in a long-lived production environment.

---

# 63. `vpc_zone_identifier`

This specifies where Auto Scaling can launch the instances.

We use:

```hcl
vpc_zone_identifier = [
  aws_subnet.private_a.id,
  aws_subnet.private_b.id
]
```

Architecture:

```text

├── Private Subnet A
└── Private Subnet B
```

The application fleet therefore spans the intended Availability Zones.

```text
↓
```

the application instances do not need to be directly internet-facing.

This is a major improvement over the Part 12 learning architecture.

# 67. ASG Health Checks

EC2 health and load-balancer health are related but different.

EC2-level health asks approximately:

```text
Is the instance functioning as EC2 infrastructure?
```

Load-balancer health asks:

```text
Can the registered target serve the configured application health check?
```

For application platforms, load-balancer health information can be important for replacement decisions.

---

# 68. Health Check Grace Period

A new instance may require time to:

```text
Boot

Run cloud-init

Install packages

Start application

Warm caches

Become ready
```

If health replacement begins too aggressively, the ASG may terminate instances before they have had reasonable startup time.

A grace period provides startup allowance.

---

# 69. Do Not Hide Slow Broken Bootstrapping With Huge Grace Periods

Bad:

```text
Application takes 30 minutes because bootstrap is broken
↓
Set grace period to 60 minutes
```

Better:

```text
Measure startup

Investigate bottleneck

Improve image/bootstrap

Set realistic grace period
```

Configuration should not hide operational defects.

# 70. Scaling Concepts

Scaling means adjusting capacity according to workload requirements.

Two fundamental directions are:

```text
Scale Out
=
Add instances
```

```text
Scale In
=
Remove instances
```

---

# 71. Horizontal Scaling

Our architecture uses horizontal scaling.

```text
2 instances
↓
4 instances
```

rather than only making one machine larger.

This is:

```text
Scale Out
```

The reverse:

```text
4
↓
2
```

is:

```text
Scale In
```

---

# 72. Vertical Scaling

Vertical scaling means changing the capacity of an individual server.

Example:

```text
t3.micro
↓
larger instance type
```

This can still be useful.

But Auto Scaling Groups primarily give us a strong horizontal fleet model.

---

# 73. Scaling Is Not the Same as High Availability

You can have:

```text
10 instances
```

all in one failure domain.

That is capacity.

It is not necessarily resilient architecture.

Similarly:

```text
2 instances across 2 AZs
```

may improve availability but not handle huge traffic.

Think separately about:

```text
Capacity

Availability

Resilience

Performance
```

---

# 74. Scaling Policies

Auto Scaling can use policies to adjust capacity.

Common concepts include:

```text
Target tracking

Step scaling

Simple scaling

Scheduled scaling

Predictive scaling
```

We will focus first on the mental model rather than attempting every strategy.

---

# 75. Target Tracking Concept

Suppose you want:

```text
Average CPU around a target
```

or another supported metric target.

Conceptually:

```text
Metric rises above desired level
↓
ASG adds capacity

Metric falls
↓
ASG may remove capacity
```

---

# 76. Request-Based Scaling

For ALB-backed applications, request-related metrics can also be useful.

Conceptually:

```text
Requests per target increase
↓
More instances
↓
Requests distributed across larger fleet
```

This can sometimes map more directly to application load than CPU.

Metric choice should reflect actual workload behavior.

---

# 77. Scaling Policy Example

A conceptual target-tracking resource might look like:

```hcl
resource "aws_autoscaling_policy" "cpu" {
  name                   = "${local.name_prefix}-cpu-scaling"
  autoscaling_group_name = aws_autoscaling_group.application.name
  policy_type            = "TargetTrackingScaling"

  target_tracking_configuration {
    predefined_metric_specification {
      predefined_metric_type = "ASGAverageCPUUtilization"
    }

    target_value = 60.0
  }
}
```

Do not blindly use 60% CPU for every application.

The correct metric and target require workload testing.

---

# 78. Why CPU Is Not Always Enough

Suppose your application is:

```text
Memory constrained
```

but CPU remains:

```text
20%
```

CPU-based scaling may never react.

Or suppose your application spends time waiting on:

```text
external APIs
```

CPU may again be a poor capacity signal.

Production scaling requires useful metrics.

---

# 79. Scaling Can Cause Downstream Problems

Imagine:

```text
2 application instances
↓
20 application instances
```

Each opens:

```text
50 database connections
```

Now:

```text
100 connections
↓
1000 connections
```

Your application tier scaled successfully.

Your database may not.

Scaling one layer changes pressure on other layers.

---

# 80. Scale-In Safety

Scaling out is usually easier to reason about.

Scaling in means:

```text
Terminate capacity
```

Questions include:

```text
Are requests still running?

Are jobs executing?

Are sessions local?

Is data stored locally?

Does deregistration have enough time?

Can instances terminate safely?
```

Production applications should be designed for replaceable compute.

---

# 81. Stateless Application Principle

Auto Scaling works best when application instances are replaceable.

Prefer:

```text
Request
↓
Any healthy instance
```

rather than:

```text
User must always return to EC2 A
because critical state lives there.
```

State should generally live in appropriate external systems.

---

# 82. Application State

Examples of state that may need external systems:

```text
User sessions

Uploaded files

Database records

Shared cache

Queues

Application secrets
```

Do not depend on an individual Auto Scaling instance surviving forever.

```text

↓

↓

```

Part 13:

```text

↓

```

```text

```

It maps human-friendly names to network destinations.

Instead of users remembering:

```text

```

they use:

```text

```

---

# 85. DNS Mental Model

```text

↓
DNS lookup
↓
Route 53
↓
ALB destination
↓
Application
```

DNS helps users locate the service.

---

# 86. Route 53

Amazon Route 53 is AWS's DNS service.

It can manage:

```text

Routing policies

Health-aware DNS architectures

Domain registration capabilities
```

For our architecture, we mainly need:

```text

+

```

---

# 87. Hosted Zone

A hosted zone contains DNS records for a domain.

Example:

```text
example.com
```

could contain:

```text

api.example.com

www.example.com
```

---

# 88. Route 53 Alias to ALB

Instead of pointing users to the long AWS-generated ALB hostname, create:

```text
app.example.com
↓
Route 53 Alias
↓
Application Load Balancer
```

This gives the application a stable human-readable DNS name.

---

# 89. Route 53 Terraform Concept

If Terraform manages the hosted zone:

```hcl
resource "aws_route53_record" "application" {
  zone_id = aws_route53_zone.primary.zone_id
  name    = "app.${var.domain_name}"
  type    = "A"

  alias {
    name                   = aws_lb.application.dns_name
    zone_id                = aws_lb.application.zone_id
    evaluate_target_health = true
  }
}
```

If the hosted zone already exists and is owned elsewhere, it may be consumed as an input or data source instead.

Do not casually create duplicate public hosted zones.

---

# 90. Alias vs CNAME Mental Model

For AWS load balancers, Route 53 alias records provide AWS-specific DNS integration.

A useful architecture is:

```text
app.example.com
↓
Alias
↓
ALB DNS name
```

Alias records can also be used at a zone apex where a traditional CNAME is not appropriate.

---

# 91. DNS Does Not Encrypt Traffic

This:

```text

```

solves naming.

```text

```

```text

```

For web traffic:


# 94. Certificate Purpose

A server certificate helps the client establish that it is communicating with the intended domain endpoint.

The certificate contains information including:

```text

Issuer

Validity information

Digital signature
```

The browser validates the certificate chain and domain relationship as part of TLS.

# 95. AWS Certificate Manager

AWS Certificate Manager is commonly abbreviated:

```text

```

ACM manages certificates that integrate with AWS services such as Application Load Balancers.

Architecture:

```text

↓

↓
```

---

# 96. ACM Certificate

Conceptual Terraform:

```hcl
resource "aws_acm_certificate" "application" {
  domain_name       = "app.${var.domain_name}"
  validation_method = "DNS"

  lifecycle {
    create_before_destroy = true
  }

  tags = local.common_tags
}
```

Requesting the certificate does not necessarily mean it is immediately ready for use.

The domain must be validated.

---

# 97. DNS Validation

With DNS validation:

```text

↓

↓

↓

↓
```

# 98. Certificate Validation Record Concept

A common pattern uses ACM-provided domain validation options to create Route 53 records.

The exact implementation deserves careful Terraform expression handling because certificate validation options are collection values.

Conceptually:

```text

↓

↓

↓

```

---

# 99. Certificate Must Match Domain

If users connect to:

```text
app.example.com
```

the certificate must be valid for:

```text
app.example.com
```

or otherwise cover that hostname through a valid certificate name pattern.

A certificate for an unrelated domain will not produce a valid browser TLS experience.

# 100. HTTPS Listener

After the certificate is issued:

```hcl
resource "aws_lb_listener" "https" {
  load_balancer_arn = aws_lb.application.arn

  port     = 443
  protocol = "HTTPS"

  certificate_arn = aws_acm_certificate_validation.application.certificate_arn

  default_action {
    type             = "forward"
    target_group_arn = aws_lb_target_group.application.arn
  }
}
```

A production configuration should also deliberately choose and maintain an appropriate ELB security policy rather than ignoring TLS policy decisions.

# 187. The Production Engineering Mindset

A beginner asks:

```text
Is my EC2 instance running?
```

A production engineer asks:

```text
Can users resolve the service?

Can users establish TLS?

Can the load balancer accept traffic?

Does the listener route correctly?

Are healthy targets available?

Are targets spread across failure domains?

Can unhealthy instances be removed?

Can failed capacity be replaced?

Can the fleet scale?

Can the fleet scale back down safely?

Are application instances private?

Are Security Group relationships minimal?

Is state externalized?

Can instances be replaced without losing data?

Can I observe health?

Can I investigate failures?

Can I control cost?

Can I deploy changes safely?
```

That is the transition Part 13 is meant to create.

You are no longer thinking:

```text
How do I create an EC2 instance?
```

You are thinking:

```text
How do I build and operate an application platform?
```

The architecture you should now remember is:

```text
Users
↓
Route 53
↓
HTTPS
↓
Application Load Balancer
↓
Target Group
↓
Auto Scaling Group
↓
EC2 Instances
↓
Application
```

And the production principle behind it is:

```text
PUBLIC ENTRY POINT
+
PRIVATE COMPUTE
+
MULTIPLE AVAILABILITY ZONES
+
HEALTH-AWARE ROUTING
+
REPLACEABLE INSTANCES
+
CONTROLLED SCALING
+
TLS
+
DNS
=
A MUCH STRONGER APPLICATION PLATFORM
```
