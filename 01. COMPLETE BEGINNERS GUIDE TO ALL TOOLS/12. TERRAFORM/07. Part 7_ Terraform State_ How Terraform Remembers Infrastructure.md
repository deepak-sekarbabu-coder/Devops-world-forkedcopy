# Part 7: Terraform State: How Terraform Remembers Infrastructure

## One of the Most Important Concepts in Terraform

You can understand:

* HCL
* variables
* providers
* resources
* `terraform plan`
* `terraform apply`

and still be dangerous with Terraform if you do not understand state.

State is how Terraform remembers the relationship between the code you wrote and the infrastructure that actually exists.

The core mental model for this entire part is:

```text
Terraform Configuration
↓
Terraform State
↕
Real Infrastructure
```

A more complete version is:

```text
CONFIGURATION
What you want
        ↓
     TERRAFORM
    ↙         ↘
 STATE  ↔  PROVIDER/API
What Terraform   ↓
remembers     REAL INFRASTRUCTURE
              What exists
```

Terraform must answer questions such as:

```text
Which AWS EC2 instance belongs to this resource block?

Which VPC is Terraform managing?

What is its cloud resource ID?

Which provider configuration created it?

What attributes did Terraform last observe?

Has someone changed the resource manually?

Was a Terraform resource renamed?

Was it moved into a module?

Should Terraform update an existing object or create another one?
```

State helps Terraform answer those questions.

By the end of this part, you should understand:

* what Terraform state is
* why Terraform requires state

* why production state belongs in secure infrastructure

Most importantly, you should be able to look at:

```text
Configuration
State
Real Infrastructure
```

and explain the relationship among all three.

# 1. Start With the Problem State Solves

Imagine you write:

```hcl
resource "aws_instance" "application" {
  ami           = "ami-example"
  instance_type = "t3.micro"
}
```

Terraform sends a request to AWS.

AWS creates an EC2 instance.

Imagine AWS returns:

```text
i-0a123456789example
```

Now you close your terminal.

Tomorrow you return and change:

```hcl
instance_type = "t3.small"
```

Terraform has a fundamental problem.

How does it know that:

```text
aws_instance.application
```

means:

```text
i-0a123456789example
```

rather than some other EC2 instance?

Terraform needs a persistent mapping.

Conceptually:

```text
Terraform Address
aws_instance.application
        ↓
Terraform State
        ↓
Remote Object Identity
i-0a123456789example
        ↓
AWS EC2 Instance
```

That mapping is one of the most important jobs of Terraform state.

---

# 2. What Is Terraform State?

Terraform state is Terraform's persistent record of the infrastructure objects it manages and their relationship to your Terraform configuration.

Think of it as Terraform's memory.

But be precise.

State is not simply:

```text
a list of resources
```

It contains information Terraform needs to manage those resources over time.

Conceptually:

```text
Terraform State
│
├── Resource bindings
├── Remote object identities
├── Resource attributes
├── Provider-related metadata
├── Dependency-related metadata
├── Output information
└── Other Terraform bookkeeping
```

Terraform uses this information when determining what actions should happen next.

---

# 3. State Is Not the Infrastructure

This distinction is critical.

Suppose state contains:

```text
aws_instance.application
↓
i-1234567890
```

The state entry is not the EC2 instance.

It is Terraform's record of that instance.

Think:

```text
State
=
Record

Infrastructure
=
Actual Object
```

Deleting a state binding does not necessarily delete the infrastructure.

Deleting infrastructure does not necessarily immediately remove its old information from an existing state snapshot.

These are different things.

---

# 4. Three Worlds Terraform Must Reconcile

Terraform works across three major representations.

## World 1: Configuration

Example:

```hcl
resource "aws_instance" "application" {
  instance_type = "t3.micro"
}
```

This represents:

```text
DESIRED CONFIGURATION
```

What you are declaring Terraform should manage.

---

## World 2: State

Conceptually:

```text
aws_instance.application
↓
remote ID = i-123456
↓
known attributes
↓
provider relationship
```

This represents:

```text
TERRAFORM'S PERSISTED KNOWLEDGE
```

---

## World 3: Real Infrastructure

AWS may currently contain:

```text
EC2 instance
ID: i-123456
Type: t3.small
```

This represents:

```text
REALITY
```

Terraform must reconcile these worlds.

# 6. Why Terraform Needs State

There are several important reasons.

Terraform needs state for:

1. resource mapping
2. remote object identity
3. metadata
4. dependency information
5. cached resource attributes
6. efficient planning
7. collaboration and synchronization
8. detecting and reconciling infrastructure changes

The most important is resource mapping.

---

# 7. Resource Mapping

Suppose configuration contains:

```hcl
resource "aws_security_group" "web" {
  name = "web-security-group"
}
```

Terraform needs to know:

```text
aws_security_group.web
```

corresponds to:

```text
sg-0123456789example
```

in AWS.

Conceptually:

```text
Terraform Resource Address
aws_security_group.web
        ↓
State Binding
        ↓
AWS Resource ID
sg-0123456789example
        ↓
Actual Security Group
```

Without that mapping Terraform would have difficulty determining which existing remote object it owns.

---

# 8. Why Terraform Cannot Simply Search by Name

You might ask:

> Why not just search AWS for a resource named `web-security-group`?

Because names are not reliable universal identities.

Possible problems:

```text
Multiple resources can share names

Some resources do not have names

Names may change

Different providers identify resources differently

Some APIs use generated IDs

Not every platform supports Terraform-specific tags

Tags may be modified

Resources can exist before Terraform manages them
```

Terraform therefore maintains its own mapping.

---

# 9. Resource Bindings

A state binding connects:

```text
Terraform Resource Instance
↓
Remote Infrastructure Object
```

Example:

```text
aws_instance.application
↓
i-0123456789abcdef0
```

This tells Terraform:

> When configuration refers to `aws_instance.application`, this is the remote object currently associated with it.

That relationship is fundamental.

---

# 10. One-to-One Mapping

Terraform normally expects:

```text
One Terraform resource instance
↕
One remote object
```

Conceptually:

```text
aws_instance.application
        ↕
i-0123456789
```

Not:

```text
aws_instance.application
       ↘
        i-123

aws_instance.other
       ↗
```

Both Terraform addresses should not independently claim the same remote object.

Ambiguous ownership can lead to unpredictable management behavior.

---

# 11. Resource IDs

Providers typically use some remote identifier to identify managed objects.

Examples might include:

```text
EC2
i-0123456789abcdef0

Security Group
sg-0123456789abcdef0

VPC
vpc-0123456789abcdef0
```

Other platforms use different identity schemes.

Terraform stores the identity information needed by the provider so the object can be read, updated, or destroyed later.

Mental model:

```text
Terraform Address
↓
State Binding
↓
Provider-Specific Identity
↓
Remote API
↓
Object
```

---

# 12. Resource Address vs Resource ID

Do not confuse these.

Terraform address:

```text
aws_instance.application
```

Remote ID:

```text
i-0123456789abcdef0
```

They serve different purposes.

```text
Terraform Address
=
Where the object exists in Terraform's configuration/state model

Remote ID
=
How the provider identifies the real object
```

---

# 13. Resource Attributes in State

State can contain attributes associated with managed resources.

For an infrastructure resource these might conceptually include:

```text
ID
name
region
IP address
ARN
tags
subnet
security groups
configuration values
provider-computed values
```

Why?

Because Terraform needs information about managed objects when reasoning about future changes.

---

# 14. Computed Attributes

Remember from Part 4:

```text
Required
Optional
Computed
```

Some values are not known until the provider creates or reads the resource.

For example:

```text

resource ID

ARN
```

Terraform may learn these after interacting with the provider.

Those values can then become part of Terraform's state knowledge.

---

# 15. State as Cached Information

Terraform state also acts partly as a cache of resource attribute information.

Conceptually:

```text
Remote Resource
↓
Provider Reads Attributes
↓
Terraform
↓
State Representation
```

This allows Terraform to retain useful information about managed objects between operations.

But remember:

```text
State
≠
Guaranteed current reality forever
```

Infrastructure can change outside Terraform.

That leads to drift.

# 16. Desired Configuration

Configuration answers:

```text
What should Terraform manage?
```

Example:

```hcl
resource "local_file" "application" {
  filename = "${path.module}/application.conf"
  content  = "environment=production"
}
```

Desired configuration says:

```text
A file should exist
with this path
and this content.
```

# 17. Real Infrastructure

Reality answers:

```text
What actually exists right now?
```

Maybe the file contains:

```text
environment=staging
```

because someone manually changed it.

Now:

```text
Configuration
environment=production

Reality
environment=staging
```

There is a difference.

# 18. State Representation

State might remember the resource and its previously observed values.

Conceptually:

```text

```

Terraform can use provider reads during planning to determine whether reality has changed.

# 29. State JSON Structure Concepts

For learning purposes, you may inspect a lab state file.

Do not modify it.

Linux/macOS:

```bash
cat terraform.tfstate
```

PowerShell:

```powershell
Get-Content .\terraform.tfstate
```

You will see JSON.

Conceptually, a state snapshot contains information such as:

```text
Terraform metadata
↓
Outputs
↓
Resources
↓
Resource instances
↓
Attributes
↓
Provider relationships
```

A simplified conceptual example might look like:

```json
{
  "version": 4,
  "terraform_version": "...",
  "serial": 1,
  "lineage": "...",
  "outputs": {},
  "resources": []
}
```

Do not build operational procedures around hand-editing its internal fields.

# 30. State Snapshot Concepts

You may encounter concepts such as:

```text
version
terraform_version
serial
lineage
outputs
resources
instances
attributes
provider references
```

For a beginner, understand them conceptually.

### Version

Represents the state format version.

### Terraform version

Indicates Terraform version information associated with the snapshot.

### Serial

Helps identify state snapshot progression.

### Lineage

Helps identify the state lineage.

### Outputs

Stores root output values.

### Resources

Contains managed resource/data representation.

### Instances

Represents specific resource instances.

### Attributes

Contains known resource values.

Do not memorize internal JSON fields as an API contract.

Use Terraform's supported CLI interfaces.

# 39. State Backups

When using local state, you may encounter:

```text

```

Terraform can retain the previous state snapshot as a backup when it writes a new one.

Think:

```text
Previous State
↓
terraform.tfstate.backup

Current State
↓
terraform.tfstate
```

This provides a recovery aid.

It is not a complete enterprise backup strategy.

# 40. State Modification Commands and Backups

Terraform state commands that modify state create backups.

Examples include operations such as:

```text
terraform state mv
terraform state rm
```

This is intentional.

State modification is high impact.

Terraform preserves a backup so there is a recovery point.

Do not interpret this as permission to perform state operations casually.

# 45. `sensitive = true` Does Not Automatically Remove a Value From State

This is one of the most important Terraform security lessons.

Suppose:

```hcl
variable "database_password" {
  type      = string
  sensitive = true
}
```

Marking the value sensitive helps Terraform redact it from normal CLI/UI presentation in appropriate contexts.

It does not automatically mean:

```text
Password is absent from state.
```

Traditional sensitive values can still be stored in state.

Therefore:

```text
Sensitive Redaction
≠
State Encryption
≠
Secret Omission
```

These are different concepts.

---

# 46. Modern Terraform and Values Omitted From State

Modern Terraform also provides mechanisms such as ephemeral values and provider-supported write-only arguments for certain workflows.

Those mechanisms can help prevent particular values from being persisted in state or plan data when used correctly.

However:

```text
not every provider argument supports this
```

and:

```text
sensitive = true
```

alone should not be interpreted as removing a value from state.

Always check the provider/resource documentation.

# 47. Never Commit State to Git

A normal Terraform `.gitignore` should protect local state artifacts.

Example:

```gitignore
.terraform/
*.tfstate
*.tfstate.*
*.tfplan
```

Why?

Because Git repositories are designed to preserve history.

If you accidentally commit a secret-bearing state file and later delete it:

```text
Deleted From Current Branch
≠
Automatically Removed From Git History
```

Do not use Git as a Terraform state backend.

# 54. Rename Problem

Suppose you originally wrote:

```hcl
resource "local_file" "application" {
  filename = "${path.module}/application.conf"
  content  = "managed by Terraform"
}
```

State contains:

```text
local_file.application
```

You rename the block:

```hcl
resource "local_file" "service" {
  filename = "${path.module}/application.conf"
  content  = "managed by Terraform"
}
```

Terraform sees:

```text
Old address disappeared:
local_file.application

New address appeared:
local_file.service
```

Without refactoring information Terraform may interpret this as:

```text
Destroy old
+
Create new
```

even though you intended only:

```text
Rename Terraform label
```

---

# 55. Resource Identity and Renaming

Humans see:

```text
application
↓
service

Just a rename
```

Terraform sees:

```text
local_file.application
≠
local_file.service
```

Resource addresses are part of Terraform's identity model.

Therefore refactoring Terraform code requires care.

---

# 56. Moving State Manually

One way to tell Terraform about the rename is:

```bash
terraform state mv \
  local_file.application \
  local_file.service
```

Conceptually:

```text
BEFORE

local_file.application
↓
Existing Managed Object


STATE MOVE


AFTER

local_file.service
↓
Same Existing Managed Object
```

No intentional infrastructure replacement is required just because the Terraform address changed.

Modern Terraform provides a configuration-driven way to declare resource address changes.

This tells Terraform:

```text

local_file.service.
```

# 63. Why `moved` Blocks Are Powerful

A manual:

```bash
terraform state mv
```

changes a particular state directly.

A:

```hcl

  ...
}
```

block records the refactoring intent in configuration.

This is especially valuable for:

```text
teams
modules
shared repositories
versioned infrastructure code
repeatable upgrades
multiple state instances using the same configuration
```


# 75. State Refresh

Infrastructure can change outside Terraform.

Terraform therefore needs a way to update its understanding of real infrastructure.

This is called refreshing state information.

Conceptually:

```text
Prior State
↓
Provider Read
↓
Real Infrastructure
↓
Updated Observed Values
```

---

# 76. Refresh During Plan

Normal:

```bash
terraform plan
```

performs provider reads as part of the planning process unless refresh behavior is explicitly disabled.

Conceptually:

```text
Existing State
↓
Provider Reads Real Objects
↓
In-Memory Refreshed View
↓
Compare Against Configuration
↓
Plan
```

This is how Terraform can detect many out-of-band changes.

---

# 77. Refresh During Apply

Normal apply behavior also works with refreshed infrastructure information as part of determining and executing changes.

The important mental model:

```text
Terraform does not blindly trust an old state snapshot forever.
```

It normally communicates with providers to learn about managed objects before deciding what should change.

---

# 78. Refresh-Only Planning

If you want to inspect changes between state and reality without proposing configuration-driven infrastructure modifications, use:

```bash
terraform plan -refresh-only
```

Mental model:

```text
State
↕
Real Infrastructure

but

Do not propose changing infrastructure to match configuration
```

Instead, inspect how Terraform's state knowledge would change to reflect the real objects.

---

# 79. Refresh-Only Apply

After reviewing a refresh-only plan, you can use:

```bash
terraform apply -refresh-only
```

This can update Terraform state and root output values to reflect changes observed in real infrastructure without changing the infrastructure itself.

Use it deliberately.

You are effectively saying:

```text
"Accept these observed external changes into Terraform's state knowledge."
```

That may or may not be what you actually want.

---

# 80. Why Refresh-Only Is Safer Than Blind Refresh

You may encounter the older command:

```bash
terraform refresh
```

Current Terraform guidance favors refresh-only plan/apply workflows because you can inspect the proposed state updates before committing them.

Better operational pattern:

```text
terraform plan -refresh-only
↓
Review
↓
terraform apply -refresh-only
```

rather than immediately changing state without a reviewable plan.

# 81. Drift

Drift occurs when real infrastructure no longer matches Terraform's expected managed configuration/state relationship.

Example:

```text
Terraform Configuration
instance_type = t3.micro

Terraform-managed resource was created
as t3.micro

Engineer manually changes AWS
to t3.small
```

Now:

```text
Configuration
t3.micro

Reality
t3.small
```

That difference is drift.

---

# 82. How Drift Happens

Common causes:

```text
manual console changes
CLI changes
another automation system
emergency production changes
provider-side defaults changing
external controllers
cloud service behavior
configuration managed outside Terraform
```

Not all out-of-band change is malicious.

Sometimes emergency work requires manual intervention.

But Terraform still needs reconciliation afterward.

```text
↓
Provider
↓
Read Real Infrastructure
↓
Difference Detected
↓
Plan
```

Terraform may then propose:

```text
Change infrastructure back to configuration
```

or show other relevant differences depending on the situation.

# 88. State Locking

Imagine:

```text
Engineer A
↓
terraform apply

Engineer B
↓
terraform apply

at the same time
```

Both operations may attempt to update the same state.

This creates a concurrency problem.

State locking helps prevent multiple writers from modifying the same state simultaneously.

---

# 89. Locking Mental Model

Without locking:

```text
Engineer A ─┐
            ├──→ STATE
Engineer B ─┘
```

Potential conflict.

With locking:

```text
Engineer A
↓
Acquire Lock
↓
STATE
↓
Release Lock

Engineer B
↓
Wait / Fail to Acquire
↓
Try Later
```

---

# 90. Terraform State Locking Behavior

If the configured backend supports locking, Terraform automatically attempts to lock state for operations that can write it.

You normally do not manually lock state before every apply.

Terraform handles the lock lifecycle.

Conceptually:

```text
Operation Starts
↓
Acquire Lock
↓
Read / Modify State
↓
Persist State
↓
Release Lock
```

---

# 91. Not Every Backend Has the Same Locking Behavior

State storage and state locking depend on backend capabilities.

Therefore never assume:

```text
Remote State
=
Automatically Safe Concurrency
```

Check the backend documentation.

Part 14 will cover remote backends and locking deeply.

---

# 92. Never Casually Disable Locking

You may encounter:

```text
-lock=false
```

Do not use it simply because:

```text
"The lock is annoying."
```

The lock exists to protect state consistency.

Disabling locking while another operation is active can allow concurrent writers.

That can damage state.

---

# 93. Force Unlock

Terraform provides:

```bash
terraform force-unlock LOCK_ID
```

for exceptional cases where automatic unlocking failed.

Do not use:

```text
force-unlock
```

because:

```text
"I want my apply to run now."
```

First verify that no legitimate Terraform operation still owns the lock.

---

# 94. Lock Troubleshooting

If state is locked:

```text
State Lock Error
↓
Read Lock Information
↓
Identify Operation
↓
Identify Owner
↓
Determine Whether Operation Is Still Running
├── Yes → Do Not Unlock
└── No
    ↓
Confirm Lock Is Stale
↓
Follow Recovery Procedure
↓
Force Unlock Only If Appropriate
```

# 167. Final State Mental Model

At the beginning you learned:

```text
Terraform Configuration
↓
Terraform State
↕
Real Infrastructure
```

Now expand it:

```text
              TERRAFORM CONFIGURATION
                 Desired State
                       │
                       │
                       ▼
                 TERRAFORM CORE
                       │
          ┌────────────┴────────────┐
          │                         │
          ▼                         ▼
   TERRAFORM STATE              PROVIDER
          │                         │
          │                         ▼
          │                     REMOTE API
          │                         │
          └──────────↔──────────────┘
                                    │
                                    ▼
                           REAL INFRASTRUCTURE
```

Terraform configuration tells Terraform:

```text
WHAT YOU WANT
```

State tells Terraform:

```text
WHAT IT MANAGES
AND HOW THAT MAPS TO REAL OBJECTS
```

Providers tell Terraform:

```text
WHAT EXISTS RIGHT NOW
```

Planning determines:

```text
WHAT MUST CHANGE
```

Apply performs:

```text
THE APPROVED CHANGE
```

Then state records the resulting management relationship.

# 168. The Rule to Remember

If you remember only one thing from Part 7:

```text
Terraform state is not a disposable cache.

It is Terraform's ownership and identity map
for managed infrastructure.
```

Therefore:

```text
DO NOT
casually edit it

DO NOT
casually delete it

DO NOT
commit it to Git

DO NOT
disable locking because it is inconvenient

DO NOT
remove bindings you do not understand

DO NOT
restore backups blindly

DO NOT
apply when state suddenly looks wrong
```

Instead:

```text
PROTECT IT
↓
BACK IT UP
↓
CONTROL ACCESS
↓
LOCK IT
↓
INSPECT IT
↓
VERSION IT
↓
RECOVER IT DELIBERATELY
↓
CHANGE BINDINGS SAFELY
```

And always return to the state triangle:

```text
              CONFIGURATION
               What I want
                  / \
                 /   \
                /     \
               /       \
              /         \
             /           \
          STATE ←────→ REALITY
       What Terraform   What actually
         remembers        exists
```

When those three disagree:

```text
STOP
↓
UNDERSTAND WHY
↓
DECIDE WHICH REPRESENTATION SHOULD BE AUTHORITATIVE
↓
RECONCILE SAFELY
↓
PLAN
↓
REVIEW
↓
VERIFY
```

That is how Terraform engineers treat state.

Not as a mysterious JSON file.

As critical infrastructure data.
