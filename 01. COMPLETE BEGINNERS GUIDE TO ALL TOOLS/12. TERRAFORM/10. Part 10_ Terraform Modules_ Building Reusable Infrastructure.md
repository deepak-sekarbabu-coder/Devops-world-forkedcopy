# Part 10: Terraform Modules: Building Reusable Infrastructure

## Move From Individual Files to Reusable Infrastructure Components

Up to this point, you have learned how to build Terraform configurations using:

* providers
* resources
* variables
* outputs
* locals
* state
* dependencies
* lifecycle rules
* `count`
* `for_each`
* data sources
* expressions
* functions
* dynamic configuration

You can already build significant infrastructure.

But a new problem appears as infrastructure grows.

Imagine that your root configuration contains:

```text
VPC
Subnets
Route tables
Internet gateway
NAT gateway
Security groups
EC2 instances
IAM roles
Load balancer
Target groups
Listeners
DNS
Monitoring
```

Now imagine repeating similar infrastructure for:

```text
development
staging
production
```

Then another application needs the same network pattern.

Then another team needs the same EC2 pattern.

Then another repository needs the same load balancer design.

Copying the same Terraform repeatedly is not a sustainable infrastructure strategy.

This is where modules become important.

The central mental model for this chapter is:

```text
INPUTS
   ↓
MODULE
   ↓
RESOURCES
   ↓
OUTPUTS
```

At a larger architectural level:

```text
                    ROOT MODULE
                         │
          ┌──────────────┼──────────────┐
          │              │              │
          ▼              ▼              ▼
      VPC MODULE    SECURITY MODULE   EC2 MODULE
          │              │              │
          └──────────────┼──────────────┘
                         │
                         ▼
                LOAD BALANCER MODULE
```

The architecture we will build toward is:

```text
Root Module
├── VPC Module
├── EC2 Module
├── Security Module
└── Load Balancer Module
```

But there is an important lesson:

```text
Modules are not just folders.

Modules are infrastructure abstractions
with defined interfaces and ownership boundaries.
```

---

# 1. The Problem Modules Solve

Suppose you create this network:

```hcl
resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
}

resource "aws_subnet" "public_a" {
  vpc_id     = aws_vpc.main.id
  cidr_block = "10.0.1.0/24"
}

resource "aws_subnet" "public_b" {
  vpc_id     = aws_vpc.main.id
  cidr_block = "10.0.2.0/24"
}

resource "aws_internet_gateway" "main" {
  vpc_id = aws_vpc.main.id
}
```

Later you need another VPC.

You could copy everything.

Then change:

```text
CIDR blocks
names
tags
Availability Zones
```

Then you need a third VPC.

Copy again.

Soon you have:

```text
network-a/
network-b/
network-c/
network-d/
```

containing nearly identical Terraform.

That creates:

```text
duplication
↓
configuration drift
↓
inconsistent fixes
↓
maintenance overhead
↓
operational risk
```

Suppose you discover a networking mistake.

Without modules:

```text
Fix development
Fix staging
Fix production
Fix application A
Fix application B
Fix application C
```

With an appropriately designed reusable module:

```text
Improve Module
↓
Release New Module Version
↓
Review Upgrade
↓
Consumers Adopt Version
```

That is a much stronger engineering model.

---

# 2. What Is a Terraform Module?

A Terraform module is a collection of Terraform configuration files kept together as one logical configuration unit.

At the filesystem level:

```text
my-module/
├── main.tf
├── variables.tf
└── outputs.tf
```

Those `.tf` files together form one module.

A module commonly contains:

```text
Input Variables
      ↓
Resources
      ↓
Outputs
```

It may also contain:

```text
locals

data sources

provider requirements

module calls

moved blocks

checks

other Terraform configuration
```

A useful mental model is:

```text
MODULE
=
Reusable Infrastructure Component
```

For example:

```text
VPC Module
```

could represent:

```text
VPC
+
Subnets
+
Route Tables
+
Internet Gateway
+
Associations
```

The caller does not necessarily need to understand every implementation detail.

The caller interacts with the module's interface.

---

# 3. Every Terraform Configuration Already Has a Module

You have actually been using modules throughout this series.

When you run:

```bash
terraform plan
```

inside a directory containing:

```text
main.tf
variables.tf
outputs.tf
```

those files collectively form a module.

Specifically, they form the:

```text
ROOT MODULE
```

So modules are not an optional Terraform feature added later.

Terraform configurations are fundamentally organized around modules.

---

# 4. Root Module

The **root module** is the module Terraform starts from for a particular configuration.

For Terraform CLI, this is normally the working directory where Terraform is operating.

Example:

```text
production/
├── main.tf
├── variables.tf
├── outputs.tf
├── providers.tf
└── versions.tf
```

If Terraform operates from:

```text
production/
```

then those Terraform files form the root module.

Mental model:

```text
terraform plan
      ↓
Root Module
      ↓
Terraform evaluates configuration
```

---

# 5. Files Do Not Create Separate Modules

This is extremely important.

Suppose:

```text
production/
├── main.tf
├── network.tf
├── compute.tf
├── security.tf
└── outputs.tf
```

These are **not five modules**.

They are five files belonging to:

```text
ONE MODULE
```

Terraform effectively evaluates the `.tf` configuration files in the directory together.

Therefore:

```text
main.tf
network.tf
compute.tf
```

are organizational choices for humans.

They do not create infrastructure execution boundaries.

---

# 6. Directories Matter

Suppose:

```text
project/
├── main.tf
└── modules/
    └── network/
        ├── main.tf
        ├── variables.tf
        └── outputs.tf
```

The Terraform files inside:

```text
project/
```

form one module.

The Terraform files inside:

```text
project/modules/network/
```

form another module.

Terraform does not automatically include nested directories.

The root module must explicitly call the child module.

---

# 7. Child Modules

A module called by another module is called a:

```text
CHILD MODULE
```

Example:

```hcl
module "network" {
  source = "./modules/network"
}
```

Architecture:

```text
Root Module
     │
     │ calls
     ▼
Network Module
```

The network module is a child module of the root module.

---

# 8. Modules Can Call Modules

A child module can itself call another module.

Example:

```text
Root Module
    ↓
Application Module
    ↓
Compute Module
```

Terraform supports this.

But support does not mean you should create arbitrarily deep trees.

A configuration like:

```text
Root
 ↓
Module A
 ↓
Module B
 ↓
Module C
 ↓
Module D
 ↓
Module E
```

can become difficult to:

```text
understand
debug
upgrade
reuse
trace dependencies through
```

Prefer relatively flat composition when practical.

---

# 9. Root vs Child Module

Think:

```text
ROOT MODULE

Where the deployment is assembled.
```

versus:

```text
CHILD MODULE

Reusable component called by another module.
```

Example:

```text
production/
│
├── Root Module
│
├── calls → VPC Module
├── calls → Security Module
├── calls → EC2 Module
└── calls → Load Balancer Module
```

# 10. Why Modules Exist

Modules solve several related problems.

## Repetition

Instead of:

```text
copy
paste
edit
copy
paste
edit
```

you can reuse an infrastructure definition.

## Standardization

A module can establish organizational defaults and patterns.

## Abstraction

Instead of thinking:

```text
aws_vpc
aws_subnet
aws_route_table
aws_route
aws_route_table_association
aws_internet_gateway
```

the caller can think:

```text
application network
```

## Maintainability

Infrastructure logic can live in one reusable component.

## Composition

Larger architectures can be assembled from smaller components.

## Governance

Organizations can encode approved patterns into reusable modules.

---

# 11. Modules Raise the Level of Abstraction

Providers expose low-level resource types.

For example:

```text
aws_vpc
aws_subnet
aws_route_table
aws_instance
aws_lb
aws_security_group
```

A good module can combine those primitives into an architectural concept.

Example:

```text
Provider Resources
      ↓
VPC
Subnets
Routes
Gateway
      ↓
NETWORK MODULE
```

Now the root configuration can express architecture rather than every low-level implementation detail.

---

# 12. Modules Are Not Functions

It can be useful to compare modules conceptually to functions:

```text
Inputs
↓
Module
↓
Outputs
```

But do not take the analogy too far.

A module can:

```text
manage resources

contain data sources

maintain resource addresses in state

call child modules

have dependencies

create infrastructure lifecycle effects
```

It is not simply a pure programming-language function.

---

# 13. The Module Interface

Think of a module as having a contract.

```text
CALLER
   │
   │ inputs
   ▼
┌───────────────┐
│    MODULE     │
│               │
│ implementation│
└───────────────┘
   │
   │ outputs
   ▼
CALLER
```

The interface consists primarily of:

```text
INPUT VARIABLES
+
OUTPUT VALUES
```

This is one of the most important module-design concepts.

---

# 14. Module Inputs

A child module accepts values through variables.

Inside:

```text
modules/network/variables.tf
```

you might define:

```hcl
variable "vpc_cidr" {
  type        = string
  description = "CIDR block for the VPC."
}

variable "environment" {
  type        = string
  description = "Deployment environment."
}

variable "tags" {
  type        = map(string)
  description = "Tags applied to supported resources."
  default     = {}
}
```

These variables define part of the module interface.

---

# 15. Required Module Inputs

This variable:

```hcl
variable "vpc_cidr" {
  type = string
}
```

has no default.

Therefore the caller must normally supply it.

Example:

```hcl
module "network" {
  source = "./modules/network"

  vpc_cidr = "10.0.0.0/16"
}
```

---

# 16. Optional Inputs

This:

```hcl
variable "enable_nat_gateway" {
  type        = bool
  description = "Whether the module should create a NAT gateway."
  default     = false
}
```

provides a default.

The caller can omit it:

```hcl
module "network" {
  source = "./modules/network"

  vpc_cidr = "10.0.0.0/16"
}
```

or override it:

```hcl
module "network" {
  source = "./modules/network"

  vpc_cidr           = "10.0.0.0/16"
  enable_nat_gateway = true
}
```

---

# 17. Inputs Should Be Typed

Avoid:

```hcl
variable "config" {}
```

when you know the expected shape.

Prefer:

```hcl
variable "subnets" {
  type = map(object({
    cidr_block        = string
    availability_zone = string
  }))
}
```

Typed interfaces make modules easier to:

```text
understand
validate
document
test
consume
```

---

# 18. Validate Important Inputs

Example:

```hcl
variable "environment" {
  type        = string
  description = "Deployment environment."

  validation {
    condition = contains(
      ["development", "staging", "production"],
      var.environment
    )

    error_message = "environment must be development, staging, or production."
  }
}
```

A reusable module should reject invalid inputs early when the module can express a meaningful constraint.

---

# 19. Do Not Expose Every Internal Detail

Suppose a module internally creates:

```text
VPC
Subnets
Route Table
Internet Gateway
Route Associations
```

You do not automatically need variables for every possible argument of every resource.

Bad interface:

```text
vpc_enable_dns_support
vpc_enable_dns_hostnames
route_table_name
gateway_name
route_name
route_destination
association_mode
...
```

Eventually the module becomes a thin forwarding layer around provider resources.

A module should expose meaningful architectural decisions.

---

# 20. Module Outputs

Modules return values using outputs.

Inside:

```text
modules/network/outputs.tf
```

you might define:

```hcl
output "vpc_id" {
  description = "ID of the VPC created by this module."
  value       = aws_vpc.main.id
}
```

The caller can reference:

```hcl
module.network.vpc_id
```

Mental model:

```text
Network Module
↓
creates VPC
↓
VPC ID
↓
output "vpc_id"
↓
module.network.vpc_id
↓
Caller
```

---

# 21. Output Syntax Across Module Boundaries

Inside child module:

```hcl
output "vpc_id" {
  value = aws_vpc.main.id
}
```

Caller:

```hcl
module "network" {
  source = "./modules/network"

  vpc_cidr = "10.0.0.0/16"
}
```

Reference:

```hcl
module.network.vpc_id
```

Pattern:

```text
module
.
MODULE CALL NAME
.
OUTPUT NAME
```

---

# 22. Outputs Are the Module's Public Results

Suppose the network module internally contains:

```hcl
resource "aws_vpc" "main" {
  # ...
}
```

The root module should not attempt:

```hcl
aws_vpc.main.id
```

because that resource belongs to a different module namespace.

Instead, the child exposes:

```hcl
output "vpc_id" {
  value = aws_vpc.main.id
}
```

and the caller uses:

```hcl
module.network.vpc_id
```

That is module encapsulation.

---

# 23. Do Not Output Everything

A module with 70 internal resources does not necessarily need 200 outputs.

Expose values that callers legitimately need.

Examples:

```text
VPC ID
Subnet IDs
Load balancer DNS name
Security group ID
Application endpoint
IAM role ARN
```

Do not expose internal implementation details without a reason.

---

# 24. Module Structure

A simple reusable module commonly uses:

```text
network/
├── main.tf
├── variables.tf
└── outputs.tf
```

A more complete reusable module might use:

```text
terraform-aws-network/
├── README.md
├── LICENSE
├── versions.tf
├── main.tf
├── variables.tf
├── outputs.tf
├── modules/
│   └── ...
├── examples/
│   └── ...
└── tests/
    └── ...
```

Terraform does not require most of these filenames.

They are conventions that make modules easier for humans and tooling to understand.

---

# 25. Recommended File Responsibilities

## `main.tf`

Primary module implementation.

Example:

```text
resources
data sources
child module calls
```

## `variables.tf`

Input variable declarations.

## `outputs.tf`

Output declarations.

## `versions.tf`

Terraform and provider requirements.

## `README.md`

Human-facing module documentation.

## `examples/`

Runnable or illustrative usage.

## `tests/`

Terraform tests when used.

---

# 26. Files Inside One Module Are Evaluated Together

Do not think:

```text
variables.tf
↓
main.tf
↓
outputs.tf
```

Terraform does not execute those files sequentially.

Think:

```text
variables.tf ─┐
main.tf      ─┼─→ ONE MODULE CONFIGURATION
outputs.tf   ─┤
versions.tf  ─┘
```

The filenames organize the code for humans.

Relationships determine Terraform behavior.

# 29. Child Module Logic

Create:

```text
modules/naming/main.tf
```

```hcl
locals {
  normalized_application = lower(
    replace(var.application, "_", "-")
  )

  normalized_environment = lower(
    replace(var.environment, "_", "-")
  )

  resource_prefix = "${local.normalized_application}-${local.normalized_environment}"
}
```

---

# 30. Child Module Output

Create:

```text
modules/naming/outputs.tf
```

```hcl
output "resource_prefix" {
  description = "Normalized resource naming prefix."
  value       = local.resource_prefix
}
```

The module now has this contract:

```text
INPUTS

application
environment

      ↓

NAMING MODULE

      ↓

OUTPUT

resource_prefix
```

# 36. Local Modules

A local module uses a filesystem path.

Example:

```hcl
module "network" {
  source = "./modules/network"
}
```

Possible relative path:

```hcl
source = "../shared/network"
```

Local modules are useful when:

```text
developing modules

keeping related modules in one repository

testing module changes

building repository-specific components
```

---

# 37. Local Module Source Paths

The `source` argument must identify where Terraform obtains the module.

For local modules:

```hcl
source = "./modules/network"
```

The leading:

```text
./
```

makes the local-path intention explicit.

Do not treat `source` as an ordinary computed expression.

Module source selection must be resolvable as module installation configuration.

---

# 38. Module Source

The `source` argument answers:

```text
Where does this module's configuration come from?
```

Terraform supports several module source mechanisms, including:

```text
local filesystem

Terraform Registry

private registries

Git repositories

GitHub

other supported remote package locations
```

Different source types have different version-selection mechanisms.

---

# 39. Registry Modules

Terraform's public Registry contains reusable modules.

Registry source syntax follows:

```text
NAMESPACE/NAME/PROVIDER
```

Example shape:

```hcl
module "example" {
  source = "namespace/name/aws"
}
```

A real module must be selected from an actual registry entry.

Do not invent module addresses.

---

# 40. Registry Module Version

Registry modules support the `version` argument.

Example shape:

```hcl
module "example" {
  source  = "namespace/name/aws"
  version = "~> 5.0"
}
```

The exact acceptable version should be selected from the real module's available releases and compatibility requirements.

Do not blindly copy version numbers from tutorials.

---

# 41. Why Constrain Module Versions?

Imagine:

```hcl
module "network" {
  source = "organization/network/aws"
}
```

with no deliberate version strategy.

A future module release could change:

```text
defaults
outputs
resource behavior
requirements
interfaces
```

Production infrastructure should not accidentally consume breaking module changes.

Use intentional version constraints where the source mechanism supports them.

---

# 42. Module Versions Are Not Provider Versions

These are separate dependencies.

Provider requirement:

```hcl
terraform {
  required_providers {
    aws = {
      source = "hashicorp/aws"
    }
  }
}
```

Module call:

```hcl
module "network" {
  source  = "organization/network/aws"
  version = "~> 3.0"
}
```

Think:

```text
Terraform Module
↓
Reusable Terraform Configuration

Terraform Provider
↓
Plugin communicating with external API
```

Do not confuse their version lifecycles.

---

# 43. Git Modules

Terraform can retrieve modules from Git repositories.

General form:

```hcl
module "network" {
  source = "git::https://example.com/organization/terraform-network.git"
}
```

For a real repository, use its actual supported Git URL.

Terraform uses Git to retrieve the module package.

---

# 44. Selecting a Git Revision

Git-based module sources can use Git references.

Conceptually:

```hcl
module "network" {
  source = "git::https://example.com/organization/terraform-network.git?ref=v1.2.0"
}
```

The `ref` can correspond to an appropriate Git reference such as a tag, branch, or commit accepted by the Git retrieval mechanism.

For production use, prefer a deliberate immutable or release-oriented reference rather than unintentionally following a moving development branch.

---

# 45. Registry `version` vs Git `ref`

Registry:

```hcl
module "network" {
  source  = "organization/network/aws"
  version = "~> 2.0"
}
```

Git:

```hcl
module "network" {
  source = "git::https://example.com/network.git?ref=v2.1.0"
}
```

Remember:

```text
Registry Module
↓
version argument

Git Module
↓
Git ref in source
```

The Terraform `version` argument is specifically for registry modules.

# 47. Calling Modules

General structure:

```hcl
module "NAME" {
  source = "SOURCE"

  input_a = value
  input_b = value
}
```

Example:

```hcl
module "network" {
  source = "./modules/network"

  vpc_cidr    = "10.0.0.0/16"
  environment = "production"
}
```

The module label:

```text
network
```

becomes part of its Terraform address.

---

# 48. Module Address

A module call:

```hcl
module "network" {
  # ...
}
```

is referenced as:

```text
module.network
```

Output:

```text
module.network.vpc_id
```

A resource inside that module appears conceptually in state under an address such as:

```text
module.network.aws_vpc.main
```

Module boundaries therefore affect Terraform resource addresses.

This becomes very important during refactoring.

---

# 49. Passing Variables Into Modules

Root:

```hcl
variable "environment" {
  type = string
}
```

Module call:

```hcl
module "network" {
  source = "./modules/network"

  environment = var.environment
}
```

Flow:

```text
Root Input Variable
↓
var.environment
↓
Module Argument
↓
Child Input Variable
↓
Child Resources
```

---

# 50. Inputs Can Come From More Than Root Variables

A module argument can use appropriate Terraform expressions.

For example:

```hcl
module "compute" {
  source = "./modules/compute"

  environment = var.environment
  vpc_id      = module.network.vpc_id
}
```

Here:

```text
environment
```

comes from a root variable.

But:

```text
vpc_id
```

comes from another module.

That is module composition.

---

# 51. Returning Outputs

Child:

```hcl
output "vpc_id" {
  value = aws_vpc.main.id
}
```

Root:

```hcl
module.network.vpc_id
```

That output can feed another module:

```hcl
module "security" {
  source = "./modules/security"

  vpc_id = module.network.vpc_id
}
```

Architecture:

```text
Network Module
↓
vpc_id
↓
Security Module
```

Terraform sees the reference and understands the dependency.

---

# 52. Module Composition

Module composition means building larger infrastructure by connecting modules through their interfaces.

Example:

```text
VPC Module
    │
    ├── vpc_id ───────────────┐
    │                         │
    └── subnet_ids ──────┐    │
                         │    │
                         ▼    ▼
                      EC2 Module
                         │
                         ▼
                  instance IDs
```

Another connection:

```text
VPC Module
↓
vpc_id
↓
Security Module
↓
security_group_id
↓
EC2 Module
```

Modules become building blocks.

---

# 53. Flat Module Composition

Prefer architecture like:

```text
                    ROOT
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
     Network      Security      Compute
        │            │            │
        └────outputs─┴──inputs────┘
```

rather than unnecessarily deep:

```text
Root
↓
Application
↓
Platform
↓
Compute
↓
Instance
↓
Network Helper
```

Flat composition keeps dependencies visible to the root module.

---

# 54. Why the Root Module Is a Good Composer

Consider:

```hcl
module "network" {
  source = "./modules/network"
}

module "security" {
  source = "./modules/security"

  vpc_id = module.network.vpc_id
}

module "compute" {
  source = "./modules/compute"

  subnet_ids       = module.network.private_subnet_ids
  security_group_id = module.security.application_security_group_id
}
```

A reader can immediately see:

```text
Network
↓
Security

Network + Security
↓
Compute
```

The architecture is visible.

That is valuable.

---

# 55. Module Dependencies Are Usually Implicit

This:

```hcl
vpc_id = module.network.vpc_id
```

creates a dependency through a reference.

You generally do not need:

```hcl
depends_on = [module.network]
```

when normal data references already express the dependency.

Remember Part 8:

```text
Prefer real references.

Use explicit depends_on
for hidden dependencies.
```

The same principle applies to modules.

---

# 56. Module Boundaries

Choosing module boundaries is one of the hardest parts of Terraform design.

A module boundary should usually represent a meaningful infrastructure concept or ownership boundary.

Possible modules:

```text
network

application-load-balancer

database

application-stack

observability

identity integration
```

A bad module boundary often exists merely because:

```text
"there are several lines of Terraform here."
```

Line count is not architecture.

---

# 57. Resource Ownership

A critical rule:

```text
One resource should have one clear Terraform owner.
```

Suppose:

```text
Network Module
```

creates:

```text
aws_vpc.main
```

Then the VPC belongs to that module's resource address.

Do not also define the same VPC as a managed resource in:

```text
Root Module
```

or:

```text
Security Module
```

Trying to manage the same remote object from multiple independent resource addresses or states creates dangerous ownership conflicts.

---

# 58. Ownership Mental Model

```text
Remote Infrastructure Object
            │
            ▼
One Terraform Resource Address
            │
            ▼
One State Ownership Relationship
```

For modules:

```text
VPC Module
↓
owns VPC lifecycle

Security Module
↓
consumes VPC ID

Compute Module
↓
consumes subnet IDs

Load Balancer Module
↓
consumes VPC + subnet information
```

Consumption is not ownership.

---

# 59. Good Module Boundary Example

Network module owns:

```text
VPC
Subnets
Route Tables
Routes
Internet Gateway
Route Associations
```

Outputs:

```text
vpc_id
public_subnet_ids
private_subnet_ids
```

Security module receives:

```text
vpc_id
```

and owns:

```text
Application Security Group
Load Balancer Security Group
```

Compute module receives:

```text
subnet IDs
security group IDs
```

and owns:

```text
EC2 / Launch Template / Compute Resources
```

This can be a clean ownership model.

---

# 60. Module Interface Design

A module interface should answer:

```text
What must the caller provide?

What may the caller customize?

What does the module guarantee?

What does the module create?

What values does it return?

What assumptions does it make?
```

That is much more important than simply placing resources into a directory.

---

# 61. Good Input Design

Prefer meaningful inputs:

```hcl
variable "vpc_cidr" {
  type = string
}

variable "public_subnets" {
  type = map(object({
    cidr_block        = string
    availability_zone = string
  }))
}

variable "tags" {
  type    = map(string)
  default = {}
}
```

The interface communicates infrastructure intent.

---

# 62. Avoid Exposing Provider Implementation Everywhere

Suppose your module contains 20 AWS resource arguments.

Do not automatically expose all 20 as variables.

That creates:

```text
Caller
↓
100 configuration switches
↓
Module
↓
Almost no opinion
```

The abstraction becomes weak.

A good module usually has intentional defaults and meaningful customization points.

---

# 63. But Avoid Overly Opinionated Modules Too

The opposite failure also exists.

Example:

```text
Module always uses:

10.0.0.0/16
exactly 2 subnets
us-east-1 only
fixed names
fixed tags
fixed instance type
fixed security rules
```

Such a module may be impossible to reuse.

Balance:

```text
Useful Defaults
+
Clear Inputs
+
Intentional Constraints
=
Practical Reusability
```

---

# 64. Reusability

Reusable does not mean:

```text
supports every possible architecture
```

A module that attempts to support every conceivable use case can become impossible to understand.

Better:

```text
Clear Purpose
+
Stable Interface
+
Reasonable Flexibility
+
Predictable Behavior
```

A production-grade module should know what problem it solves.

---

# 65. Avoid Giant Modules

Imagine:

```text
module "everything" {
  # VPC
  # IAM
  # EC2
  # database
  # DNS
  # monitoring
  # backups
  # Kubernetes
  # CDN
  # queues
  # storage
  # security
}
```

This can create:

```text
huge blast radius

complex plans

hundreds of inputs

hundreds of outputs

difficult testing

difficult ownership

difficult upgrades

limited reuse
```

Do not build a giant module simply because modules can contain many resources.

---

# 66. Signs a Module Is Too Large

Ask:

```text
Does it represent several unrelated architectural concepts?

Do different teams own different parts?

Can parts change independently?

Does it have dozens of unrelated switches?

Does every consumer use only half the module?

Is testing becoming difficult?

Does changing networking force a module release containing unrelated compute changes?
```

If yes, reconsider the boundary.

---

# 67. Avoid Overly Fragmented Modules

The opposite extreme:

```text
vpc-module
subnet-module
route-module
route-table-module
gateway-module
tag-module
name-module
security-group-rule-module
```

can create excessive abstraction.

Now a simple VPC architecture requires coordinating ten modules.

That can be worse than writing the resources directly.

---

# 68. Thin Wrapper Modules

Be suspicious of a module that merely does:

```hcl
resource "aws_instance" "this" {
  ami           = var.ami
  instance_type = var.instance_type
  subnet_id     = var.subnet_id
}
```

with every provider argument simply forwarded from a variable.

Ask:

```text
What architectural concept did this module add?
```

If the answer is:

```text
none
```

the module may not be useful.

Use the resource directly unless the wrapper adds meaningful policy, standards, composition, or abstraction.

---

# 69. The Module Size Balance

Think:

```text
TOO LARGE
Everything Module
     │
     ▼
Hard to reuse

GOOD BOUNDARY
Architectural Component
     │
     ▼
Reusable + Understandable

TOO SMALL
Thin Resource Wrapper
     │
     ▼
Abstraction Overhead
```

Your goal is the middle.

---

# 70. Module Composition Example

We want:

```text
Root Module
├── VPC Module
├── Security Module
├── EC2 Module
└── Load Balancer Module
```

Dependency architecture:

```text
                 ROOT MODULE
                      │
                      ▼
                  VPC MODULE
                 /          \
                /            \
          vpc_id          subnet_ids
              │               │
              ▼               │
       SECURITY MODULE         │
              │               │
              ▼               │
      security_group_id       │
              │               │
              └──────┐   ┌────┘
                     ▼   ▼
                   EC2 MODULE
                       │
                       ▼
                 instance IDs
                       │
                       ▼
              LOAD BALANCER MODULE
```

This makes the architecture explicit.

# 76. Root Module Composition

Conceptually:

```hcl
module "vpc" {
  source = "./modules/vpc"

  vpc_cidr = var.vpc_cidr
  tags     = local.common_tags
}

module "security" {
  source = "./modules/security"

  vpc_id           = module.vpc.vpc_id
  application_port = var.application_port
  tags             = local.common_tags
}

module "ec2" {
  source = "./modules/ec2"

  subnet_ids = module.vpc.private_subnet_ids

  security_group_ids = [
    module.security.application_security_group_id
  ]

  instance_type = var.instance_type
  tags          = local.common_tags
}
```

Notice what the root module is doing.

It is not merely creating resources.

It is **composing architecture**.

---

# 77. Read the Architecture From the Code

This:

```hcl
vpc_id = module.vpc.vpc_id
```

tells you:

```text
Security depends on Network.
```

This:

```hcl
subnet_ids = module.vpc.private_subnet_ids
```

tells you:

```text
Compute runs in subnets owned by Network.
```

This:

```hcl
security_group_ids = [
  module.security.application_security_group_id
]
```

tells you:

```text
Compute consumes controls owned by Security.
```

Well-designed module composition makes architecture visible.

---

# 78. Module Outputs Can Return Complex Values

You are not limited to strings.

A module can output:

```text
strings
numbers
booleans
lists
sets
maps
objects
tuples
```

Example:

```hcl
output "subnets" {
  value = {
    public  = aws_subnet.public
    private = aws_subnet.private
  }
}
```

But expose only what makes sense as a stable interface.

---

# 79. Prefer Useful Structured Outputs

Instead of creating:

```text
public_subnet_1_id
public_subnet_2_id
public_subnet_3_id
```

consider:

```hcl
output "public_subnet_ids" {
  value = [
    for subnet in aws_subnet.public :
    subnet.id
  ]
}
```

or a map keyed by stable identities when that better fits the architecture.

This makes the module easier to scale.

---

# 80. Sensitive Module Outputs

If a module output contains sensitive information:

```hcl
output "sensitive_value" {
  value     = some_resource.example.secret
  sensitive = true
}
```

Remember:

```text
sensitive = true
```

primarily controls display behavior.

It does not mean the value disappears from Terraform state.

Module consumers must still protect state appropriately.

---

# 81. Provider Configuration and Modules

Reusable child modules should normally declare which providers they require.

But provider configurations are generally supplied from the calling configuration rather than hardcoded into reusable child modules.

This keeps modules composable.

Think:

```text
Root Module
↓
Configures Provider
↓
Child Modules
↓
Use Appropriate Provider Configuration
```

Provider alias and explicit provider-passing scenarios can be used when the architecture requires multiple provider configurations.

---

# 82. Module `providers` Mapping

A module call supports provider mapping.

Conceptual example:

```hcl
module "regional_network" {
  source = "./modules/network"

  providers = {
    aws = aws.secondary
  }
}
```

This allows the caller to decide which provider configuration the child module uses.

This is useful for:

```text
multiple AWS regions

multiple AWS accounts

aliased provider configurations
```

The reusable module should not need to know the caller's entire provider topology.

---

# 83. Module `count`

Modules can use:

```hcl
count
```

Example:

```hcl
module "optional_monitoring" {
  count = var.enable_monitoring ? 1 : 0

  source = "./modules/monitoring"
}
```

Now the module itself can have multiple or conditional instances.

But remember the addressing implications.

With `count`, references may become indexed.

---

# 84. Module `for_each`

Modules also support:

```hcl
for_each
```

Example:

```hcl
module "application" {
  for_each = var.applications

  source = "./modules/application"

  application_name = each.key
  configuration    = each.value
}
```

Addresses become conceptually:

```text
module.application["api"]
module.application["frontend"]
module.application["worker"]
```

This can be extremely powerful for reusable infrastructure patterns.

---

# 85. Stable Module Identity

Everything you learned about stable resource identity in Part 8 applies to modules too.

Prefer:

```text
module.application["api"]
```

over unstable numeric identities when application names are the natural stable keys.

Do not casually change module `for_each` keys.

That changes Terraform addresses.

---

# 86. Nested Modules

A reusable module can contain child modules.

Structure:

```text
terraform-aws-platform/
├── main.tf
├── variables.tf
├── outputs.tf
└── modules/
    ├── network/
    ├── compute/
    └── security/
```

This can be appropriate for a reusable package with internal subcomponents.

But use it deliberately.

---

# 87. Public vs Internal Nested Modules

A useful module-repository convention is:

```text
modules/
```

for nested modules.

If nested modules are intended for external consumption, document them clearly.

If they exist only as implementation details, avoid encouraging callers to depend directly on unstable internals.

Your public module interface should be intentional.

---

# 88. Avoid Deeply Nested Module Trees

Prefer:

```text
Root
├── Network
├── Security
├── Compute
└── Load Balancer
```

over:

```text
Root
└── Platform
    └── Application
        └── Compute
            └── Network
                └── Security
```

unless the architecture genuinely requires that hierarchy.

Deep trees hide dependencies.

---

# 89. Module Versioning

Once multiple consumers depend on a module, changing it becomes an API-management problem.

Imagine version:

```text
v1.0.0
```

expects:

```text
vpc_cidr
environment
```

Then you remove `vpc_cidr`.

Existing consumers may break.

Module interfaces should therefore be treated carefully.

---

# 90. Semantic Versioning Concept

A common release model uses:

```text
MAJOR.MINOR.PATCH
```

Conceptually:

```text
1.0.0
```

A typical semantic-versioning interpretation is:

```text
PATCH
↓
backward-compatible fixes

MINOR
↓
backward-compatible functionality

MAJOR
↓
breaking changes
```

Actual release policy should be documented by the module owner.

---

# 91. What Can Be a Breaking Module Change?

Examples include:

```text
removing an input

renaming an input

changing required input type incompatibly

removing an output

renaming an output

changing output structure incompatibly

changing resource addresses without migration

changing defaults with major infrastructure consequences

changing resource ownership

changing provider requirements incompatibly
```

Not all breaking changes are syntax changes.

Infrastructure behavior matters.

---

# 92. Version Module Interfaces, Not Just Files

Think:

```text
MODULE VERSION
=
Interface
+
Behavior
+
Resource Address Structure
+
Provider Compatibility
+
Infrastructure Semantics
```

Changing:

```text
main.tf
```

is not automatically significant.

Changing how consumers interact with the module can be.

---

# 93. Documentation

A reusable module without documentation creates unnecessary operational risk.

At minimum, a user should be able to answer:

```text
What does this module create?

What problem does it solve?

What does it not create?

What inputs are required?

What outputs are returned?

Which Terraform versions are supported?

Which provider versions are supported?

What permissions are required?

What assumptions does it make?

What does it cost?

How do I use it?

How do I upgrade it?

Are there destructive behaviors?
```

# 96. Document Inputs Properly

Bad:

```hcl
variable "subnets" {
  type = map(string)

```

Better:

```hcl
variable "subnets" {

```

```text
expected format
meaning
constraints
examples
defaults
security implications
```

when necessary.

# 97. Document Outputs

Example:

```hcl
output "vpc_id" {
```

```text
humans

documentation tooling

registry users

future maintainers
```

# 98. Examples

Reusable modules should include examples.

Structure:

```text
examples/
├── basic/
│   └── main.tf
├── complete/
│   └── main.tf
└── multi-region/
    └── main.tf
```

Not every module needs all three.

Use examples that teach realistic supported usage.

---

# 99. Basic Example

A basic example should answer:

```text
What is the minimum useful way
to use this module?
```

Example:

```hcl
module "network" {
  source = "../../"

  vpc_cidr = "10.0.0.0/16"
}
```

For a distributed module, published examples should show the external source form where appropriate rather than teaching consumers to depend on repository-relative paths.

---

# 100. Complete Example

A complete example might demonstrate:

```text
custom subnet configuration

tags

optional features

multiple Availability Zones

security integration

outputs
```

The example should still remain understandable.

Do not turn examples into undocumented production systems.

# 101. Examples Are Part of the User Experience

Consumers commonly begin with:

```text
↓
Copy
↓
```

# 102. Testing Modules

Reusable infrastructure should be tested.

At minimum, your development workflow should include:

```bash
terraform fmt -check
terraform init
terraform validate
terraform plan
```

But reusable modules can go further with Terraform's testing framework.

---

# 103. Terraform Test Files

Terraform test files use:

```text
.tftest.hcl
```

or:

```text
.tftest.json
```

A common structure:

```text
module/
├── main.tf
├── variables.tf
├── outputs.tf
└── tests/
    └── basic.tftest.hcl
```

Run:

```bash
terraform test
```

---

# 104. Simple Module Test Concept

Conceptually:

```hcl
run "valid_configuration" {
  command = plan

  variables {
    environment = "development"
  }

  assert {
    condition     = output.some_value != ""
    error_message = "Expected the module to produce a non-empty value."
  }
}
```

Use assertions that verify meaningful module behavior.

Do not create tests merely to increase test count.

---

# 105. Plan-Based Tests

A test can use:

```hcl
command = plan
```

This is useful when you want to verify configuration logic without intentionally creating the infrastructure during that run.

Examples:

```text
input validation

calculated outputs

resource configuration

conditional behavior
```

depending on what can be known during planning.

---

# 106. Apply-Based Tests

Terraform tests use apply behavior by default unless configured otherwise.

Apply-based testing can validate behavior that requires real infrastructure.

But remember:

```text
Real Infrastructure
=
permissions
+
time
+
cost
+
cleanup
+
cloud limits
+
failure possibilities
```

Treat infrastructure tests as real infrastructure operations.

---

# 107. Provider Mocking

Modern Terraform testing also supports provider mocking for suitable test scenarios.

This can help test module logic without creating every real remote object.

But mocks are not a complete substitute for integration testing.

Think:

```text
Mock / Plan-Oriented Tests
↓
Fast Logic Feedback

Real Infrastructure Tests
↓
Actual Provider + API Behavior
```

A mature module may use both.

---

# 108. What Should a Module Test?

Useful module tests might verify:

```text
required naming

tag composition

input validation

optional-resource behavior

resource counts

expected outputs

security defaults

environment-specific configuration

relationships between resources
```

Tests should protect the module's contract.

---

# 109. Module Test Pyramid

Conceptually:

```text
            Real Infrastructure
             Integration Tests
                  /\
                 /  \
                /    \
               /      \
              /        \
        Plan / Mock Tests
            /            \
           /              \
          /                \
   fmt + validate + static checks
```

Use the appropriate level for the risk being tested.

# 111. Terraform Registry

A registry provides module discovery and distribution.

Registry-hosted modules can provide:

```text
discoverability
```

```text

```

Examples of the pattern:

```text

```

The actual repository name should accurately describe the module.

# 113. Public Registry Release Tags

```text

```

or:

```text
v1.0.0
```

A module intended for registry publication should have an intentional release and compatibility process.

Do not treat every commit as a production release.

# 115. Evaluate Third-Party Modules Before Using Them

Do not use a public module merely because it exists.

Review:

```text
Who maintains it?

Is it actively maintained?

What resources does it create?

What provider versions does it support?

What permissions does it need?

What defaults does it choose?

What security assumptions exist?

What does an upgrade change?

How complex is it?

Is its interface stable?

Can your team operate it?
```

A module is code that can create, modify, and destroy infrastructure.

Treat dependencies accordingly.

# 117. Module Refactoring

Suppose your original root module contains:

```hcl
resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
}
```

Its address is:

```text
aws_vpc.main
```

You decide to move it into:

```text
module.network
```

Its new address becomes conceptually:

```text
module.network.aws_vpc.main
```

Terraform sees different addresses.

Without migration information, Terraform may interpret this as:

```text
Old Resource Removed
+
New Resource Added
```

That can be dangerous.

---

# 118. Refactoring Is a State-Identity Problem

Remember Part 7:

```text
Terraform Configuration
↓
Resource Address
↓
State Binding
↓
Real Infrastructure
```

Moving code into a module changes the resource address.

Therefore module refactoring must preserve the relationship between:

```text
old address
```

and:

```text
new address
```

when the same real infrastructure should remain managed.

---

# 119. `moved` Blocks for Module Refactoring

Conceptually:

```hcl
moved {
  from = aws_vpc.main
  to   = module.network.aws_vpc.main
}
```

This tells Terraform:

```text
The object formerly known as:

aws_vpc.main

is now represented by:

module.network.aws_vpc.main
```

This allows Terraform to reinterpret the address change rather than automatically treating it as replacement.

Always inspect the resulting plan.

---

# 121. Refactoring Failure Scenario

Suppose you have:


```text

        │
        ├── Development Root
        ├── Staging Root
        └── Production Root
```

# 127. Do Not Put Environment-Specific Secrets in Modules

A reusable module should not contain:

```text
production passwords

access keys

private keys

environment secrets
```

Inputs may reference secure secret mechanisms where appropriate.

But reusable source code should not become a secret store.

# 128. Module Security

Review module interfaces for:

```text
secrets

credentials

IAM permissions

public network exposure

security group rules

encryption

logging

dangerous defaults

```

A reusable module can spread a security mistake across many environments very quickly.

# 129. Secure Defaults

Suppose a module exposes:

```hcl
variable "allow_public_access" {
  type    = bool
  default = false
}
```

A secure default may be appropriate.

Compare:

```text
Default = private
Explicit decision required for public
```

versus:

```text
Default = public
Engineer must remember to secure it
```

Module defaults are architecture decisions.

# 130. Common Mistake: Copying Modules Instead of Reusing Them

Bad:

```text
modules/
├── network-dev/
├── network-staging/
└── network-prod/
```

with nearly identical code.

You have recreated the duplication problem inside the module directory.

Better when architecture is genuinely shared:

```text
modules/
└── network/
```

with environment-specific inputs supplied by callers.

---

# 131. Common Mistake: Hardcoding Environment Values Inside Module

Bad:

```hcl
resource "aws_vpc" "main" {
  cidr_block = "10.99.0.0/16"

  tags = {
    Environment = "production"
  }
}
```

inside a supposedly reusable module.

Better:

```hcl
resource "aws_vpc" "main" {
  cidr_block = var.vpc_cidr

  tags = merge(
    var.tags,
    {
      Environment = var.environment
    }
  )
}
```

when those values genuinely belong in the interface.

---

# 132. Common Mistake: Too Many Inputs

A module with:

```text
150 variables
```

may be trying to represent too many architectures.

Ask:

```text
Is this one module or five modules?

Are we exposing provider implementation details?

Should some values be grouped into typed objects?

Are some options unnecessary?

Should separate use cases have separate modules?
```

More configurability is not automatically better.

---

# 133. Common Mistake: One Giant Object Input

The opposite can also hurt readability.

Example:

```hcl
variable "everything" {
  type = any
}
```

Now nobody knows the interface without reading implementation code.

Prefer explicit, typed, documented inputs.

If using structured objects, define their shape.

---

# 134. Common Mistake: `type = any` Everywhere

`any` may seem flexible.

But it can weaken:

```text
validation

documentation

editor assistance

error quality

interface clarity
```

Use precise types whenever the module knows the expected structure.

---

# 135. Common Mistake: Exposing Internal Resources Through Outputs

Suppose an output exposes an entire complex resource object merely because it is convenient.

Now consumers begin depending on internal attributes.

Later you change the internal implementation.

Consumers break.

Outputs become part of your interface.

Expose intentionally.

---

# 136. Common Mistake: Hiding Important Architecture

Too much abstraction can make this:

```text
module "platform" {
  source = "..."
}
```

create:

```text
VPC
Kubernetes
database
IAM
DNS
monitoring
load balancer
storage
```

without the caller understanding the consequences.

Abstraction should reduce unnecessary complexity.

It should not hide critical operational behavior.

---

# 137. Common Mistake: Deep Nesting

Symptom:

```text
Error occurs in:

module.platform
.module.application
.module.compute
.module.instance
.module.network_helper
```

Deep module nesting increases debugging complexity.

Prefer flatter composition unless deeper nesting adds real architectural value.

---

# 138. Common Mistake: Unconstrained Remote Dependencies

Using a remote reusable module without a deliberate version/reference strategy can introduce unpredictable upgrades.

Production module consumption should be reviewable.

Think:

```text
Module Update
↓
Review Release
↓
Update Constraint / Ref
↓
terraform init
↓
Plan
↓
Review
↓
Test
↓
Apply
```

not:

```text
Remote code changed
↓
Surprise
```

---

# 139. Common Mistake: Editing Downloaded Module Cache

Terraform installs remote modules into its working data directory.

Do not treat downloaded module copies as your editable source of truth.

If you need to modify a module:

```text
change the actual module source
```

or:

```text
fork / develop a controlled version
```

as appropriate.

Do not manually patch cached dependencies and expect a reproducible workflow.

---

# 140. Common Mistake: Forgetting `terraform init`

After adding or changing module source/version information, run:

```bash
terraform init
```

Terraform must install or update module dependencies.

If necessary for an intentional module update:

```bash
terraform init -upgrade
```

can participate in the upgrade workflow.

Always review what dependency changes you are introducing.

```text

root/main.tf
```

```hcl
source = "./modules/network"
```

Terraform expects that path relative to the calling module.

# 143. Troubleshooting: Unsupported Argument

Suppose caller:

```hcl
module "network" {
  source = "./modules/network"

  cidr = "10.0.0.0/16"
}
```

but child defines:

```hcl
variable "vpc_cidr" {
  type = string
}
```

The interface does not contain:

```text
cidr
```

Use:

```hcl
vpc_cidr = "10.0.0.0/16"
```

Module input names must match the child module's declared interface.

---

# 144. Troubleshooting: Missing Required Argument

Child:

```hcl
variable "vpc_cidr" {
  type = string
}
```

Caller:

```hcl
module "network" {
  source = "./modules/network"
}
```

No default exists.

The caller must provide the required input.

Fix:

```hcl
module "network" {
  source = "./modules/network"

  vpc_cidr = "10.0.0.0/16"
}
```

---

# 145. Troubleshooting: Unsupported Attribute

Suppose:

```hcl
module.network.vpc_identifier
```

but module output is:

```hcl
output "vpc_id" {
  value = aws_vpc.main.id
}
```

Correct reference:

```hcl
module.network.vpc_id
```

Check the module's outputs.

Do not guess output names.

# 146. Troubleshooting: Wrong Module Version

```text
missing output

changed type

provider compatibility error
```

Check:

```text

release notes

Terraform requirements

provider requirements
```

# 147. Troubleshooting: Git Authentication

Private Git module sources may require authentication.

Terraform's Git retrieval relies on Git configuration and available credentials.

Investigate:

```text
Can Git access the repository?

Is SSH configured?

Is the HTTPS credential available?

Does CI have access?

Is the repository path correct?

Is the ref valid?
```

Avoid embedding long-lived secrets directly into module source URLs.

# 148. Troubleshooting: Unexpected Resource Replacement After Refactoring

STOP.

Inspect:

```bash
terraform plan
```

Then investigate:

```text
Old Resource Address
↓
New Resource Address
↓
State Binding
↓
```

# 149. Practical Lab: Build a Reusable Tag Module

This is intentionally small for learning module mechanics.

Structure:

```text
module-lab/
├── main.tf
├── variables.tf
├── outputs.tf
└── modules/
    └── tags/
        ├── variables.tf
        ├── main.tf
        └── outputs.tf
```

Child `variables.tf`:

```hcl
variable "application" {
  type = string
}

variable "environment" {
  type = string
}

variable "additional_tags" {
  type    = map(string)
  default = {}
}
```

---

# 150. Tag Module Logic

Child `main.tf`:

```hcl
locals {
  required_tags = {
    ManagedBy   = "Terraform"
    Application = var.application
    Environment = var.environment
  }

  tags = merge(
    var.additional_tags,
    local.required_tags
  )
}
```

Child `outputs.tf`:

```hcl
output "tags" {
  description = "Combined required and caller-provided tags."
  value       = local.tags
}
```

---

# 151. Call Tag Module

Root:

```hcl
module "tags" {
  source = "./modules/tags"

  application = var.application
  environment = var.environment

  additional_tags = {
    Owner      = "Platform"
    CostCenter = "Engineering"
  }
}
```

Root output:

```hcl
output "tags" {
  value = module.tags.tags
}
```

Run:

```bash
terraform fmt -recursive
terraform init
terraform validate
terraform plan
terraform apply
terraform output
```

Observe the input/output boundary.

---

# 152. Important Design Discussion About the Tag Lab

Would I automatically create a dedicated tag module like this in every production repository?

No.

Why?

Because:

```text
merge()
+
locals
```

may already solve the problem more clearly.

The lab exists to teach module mechanics.

This illustrates an important lesson:

```text
Something being possible as a module
does not mean it should be a module.
```

# 170. Part 10 Cheat Sheet

## Local Module

```hcl
module "network" {
  source = "./modules/network"
}
```

## Pass Input

```hcl
module "network" {
  source = "./modules/network"

  vpc_cidr = var.vpc_cidr
}
```

## Child Variable

```hcl
variable "vpc_cidr" {
  type        = string
  description = "CIDR block for the VPC."
}
```

## Child Output

```hcl
output "vpc_id" {
  description = "ID of the VPC."
  value       = aws_vpc.main.id
}
```

## Reference Module Output

```hcl
module.network.vpc_id
```

## Compose Modules

```hcl
module "security" {
  source = "./modules/security"

  vpc_id = module.network.vpc_id
}
```

## Registry Module Pattern

```hcl
module "example" {
  source  = "namespace/name/provider"
  version = "~> 1.0"
}
```

Use an actual published module and compatible version.

## Git Module Pattern

```hcl
module "example" {
  source = "git::https://example.com/organization/module.git?ref=v1.0.0"
}
```

## Git Subdirectory Pattern

```text
git::https://example.com/repository.git//modules/network?ref=v1.0.0
```

## Module With `for_each`

```hcl
module "application" {
  for_each = var.applications

  source = "./modules/application"

  application_name = each.key
}
```

## Provider Mapping

```hcl
module "network" {
  source = "./modules/network"

  providers = {
    aws = aws.secondary
  }
}
```

## Resource Moved Into Module

```hcl
moved {
  from = aws_vpc.main
  to   = module.network.aws_vpc.main
}
```

Always confirm the actual addresses and review the plan.

## Module Test

```bash
terraform test
```

```text
Design Boundary
↓
Define Inputs
↓
Build Resources
↓
Define Outputs
↓
Document
↓
Create Examples
↓
Test
↓
Version
↓
Publish / Consume
↓
Upgrade Carefully
```

# 171. The Most Important Rules From Part 10

```text
RULE 1

Every Terraform configuration already has a root module.
```

```text
RULE 2

Multiple .tf files in the same directory
do not create multiple modules.
```

```text
RULE 3

A module should represent a meaningful
infrastructure abstraction.
```

```text
RULE 4

Inputs and outputs form the module's interface.
```

```text
RULE 5

Do not expose every provider argument
just because you can.
```

```text
RULE 6

Do not output every internal detail.
```

```text
RULE 7

Resource ownership must remain clear.
```

```text
RULE 8

Consuming another module's output
does not transfer ownership of its resources.
```

```text
RULE 9

Prefer composition over unnecessary deep nesting.
```

```text
RULE 10

Avoid giant everything modules.
```

```text
RULE 11

Avoid tiny modules that merely wrap
individual resources without adding value.
```

```text
RULE 12

Reusable does not mean
infinitely configurable.
```

```text
RULE 13

Typed, documented interfaces
are easier to operate.
```

```text
RULE 14

Module versions and provider versions
are different dependencies.
```

```text
RULE 15

Remote module updates should be intentional.
```

```text
RULE 16

README files and examples
are part of module quality.
```

```text
RULE 17

Reusable infrastructure should be tested.
```

```text
RULE 18

Moving a resource into a module
changes its Terraform address.
```

```text
RULE 19

Module refactoring is also
state and identity refactoring.
```

```text
RULE 20

Always review the plan after refactoring.
```

```text
RULE 21

Stable identity matters for
module count and for_each too.
```

```text
RULE 22

A module is not good because it is clever.

It is good because its purpose,
interface, ownership, and behavior are clear.
```

# 172. Final Mental Model

Before modules:

```text
ROOT CONFIGURATION
│
├── VPC resources
├── Subnet resources
├── Route resources
├── Security resources
├── EC2 resources
├── Load balancer resources
└── Many implementation details
```

After thoughtful modularization:

```text
                       ROOT MODULE
                            │
                            │
            ┌───────────────┼───────────────┐
            │               │               │
            ▼               ▼               ▼
       VPC MODULE      SECURITY MODULE   EC2 MODULE
            │               │               │
            │ outputs       │ outputs       │ outputs
            └──────────┬────┴─────┬─────────┘
                       │          │
                       ▼          ▼
                    MODULE COMPOSITION
                           │
                           ▼
                  LOAD BALANCER MODULE
                           │
                           ▼
                    INFRASTRUCTURE
```

The data flow becomes:

```text
Environment Configuration
          ↓
     Root Variables
          ↓
      Root Module
          ↓
 ┌────────┼────────┐
 ↓        ↓        ↓
Module   Module   Module
Inputs   Inputs   Inputs
 ↓        ↓        ↓
Resources Resources Resources
 ↓        ↓        ↓
Outputs  Outputs  Outputs
 └────────┼────────┘
          ↓
 Module Composition
          ↓
 Complete Infrastructure
```

The design progression is:

```text
INDIVIDUAL RESOURCES
↓
RELATED RESOURCES
↓
ARCHITECTURAL COMPONENT
↓
CLEAR MODULE BOUNDARY
↓
INPUT INTERFACE
↓
IMPLEMENTATION
↓
OUTPUT INTERFACE
↓
COMPOSITION
↓
TESTING
↓
VERSIONING
↓
REUSE
```

The final lesson is:

```text
A Terraform module is not merely
a folder containing Terraform files.

A good module is a deliberately designed
infrastructure component with:

clear purpose
+
clear ownership
+
clear inputs
+
clear outputs
+
safe defaults
+
predictable behavior
+
documentation
+
tests
+
controlled versioning
```

And the architecture to remember is:

```text
Root Module
├── VPC Module
├── Security Module
├── EC2 Module
└── Load Balancer Module
```

with relationships expressed through:

```text
Module Outputs
        ↓
Module Inputs
        ↓
Terraform Dependency Graph
        ↓
Infrastructure
```

That is the transition from:

```text
"I can write Terraform resources."
```

to:

```text
"I can design reusable Terraform infrastructure components."
```

The next step is where these reusable components begin creating a real cloud foundation:

```text
Part 11

VPC, Subnets, Routing, and Network Infrastructure
```
