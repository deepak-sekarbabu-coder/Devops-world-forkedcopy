# 1. What Is HCL?

HCL stands for:

```text
HashiCorp Configuration Language
```

HCL is a configuration language created by HashiCorp.

Terraform's native configuration syntax is based on HCL.

Terraform files commonly look like:

```hcl
resource "local_file" "example" {
  filename = "example.txt"
  content  = "Hello Terraform"
}
```

At first, this may resemble a programming language.

But Terraform configuration is primarily declarative.

You describe:

```text
what you want
```

rather than writing every procedural step required to create it.

---

# 2. HCL and Terraform Are Not Exactly the Same Thing

This distinction matters.

HCL provides underlying language syntax.

Terraform defines the meaning of Terraform-specific constructs.

Think:

```text
HCL
↓
Language/Syntax Foundation
↓
Terraform Configuration Language
↓
Terraform-Specific Concepts
↓
Providers
Resources
Variables
Data Sources
Modules
Outputs
```

Other HashiCorp tools can also use HCL-based configuration.

Therefore:

```text
HCL
≠
Terraform itself
```

Terraform uses HCL syntax to express Terraform configuration.

---

# 3. Terraform Configuration Is Declarative

Consider:

```hcl
resource "local_file" "message" {
  filename = "message.txt"
  content  = "Hello"
}
```

You are not saying:

```text
Step 1: Open filesystem API
Step 2: Create file descriptor
Step 3: Allocate file
Step 4: Write bytes
Step 5: Close file
```

You are describing a desired resource.

Terraform and the provider determine how to reconcile reality with that declaration.

Think:

```text
Configuration
↓
Desired State
↓
Terraform
↓
Provider
↓
API/System
↓
Real Resource
```

---

# 4. The Three Core Pieces of Terraform Syntax

A useful beginner mental model is:

```text
Blocks
Arguments
Expressions
```

Example:

```hcl
resource "local_file" "message" {
  filename = "message.txt"
}
```

Here:

```text
resource "local_file" "message" {
    ...
}
```

is a block.

Inside it:

```hcl
filename = "message.txt"
```

is an argument assignment.

And:

```hcl
"message.txt"
```

is an expression producing a string value.

---

# 5. Generic Block Syntax

A Terraform block can conceptually look like:

```hcl
block_type "label_one" "label_two" {
  argument_name = expression
}
```

Not every block has two labels.

Some have:

```text
zero labels
one label
two labels
```

depending on the block type.

---

# 6. Resource Block Anatomy

Example:

```hcl
resource "local_file" "welcome" {
  filename = "welcome.txt"
  content  = "Hello"
}
```

Break it apart:

```text
resource
```

Block type.

```text
local_file
```

First block label.

```text
welcome
```

Second block label.

Then:

```hcl
{
  filename = "welcome.txt"
  content  = "Hello"
}
```

is the block body.

---

# 7. What Does the `resource` Block Type Mean?

A `resource` block declares a managed resource.

General form:

```hcl
resource "RESOURCE_TYPE" "LOCAL_NAME" {
  # configuration
}
```

For example:

```hcl
resource "local_file" "welcome" {
  filename = "welcome.txt"
}
```

The resource type is:

```text
local_file
```

The Terraform-local name is:

```text
welcome
```

Together they form the resource address:

```text
local_file.welcome
```

---

# 8. Block Labels

Labels identify or qualify a block.

Consider:

```hcl
resource "local_file" "welcome" {
}
```

The labels are:

```text
local_file
welcome
```

They do different jobs.

`local_file` tells Terraform which resource type is being declared.

`welcome` gives this particular resource a name inside the module.

---

# 9. Resource Names Are Terraform Names

The name:

```text
welcome
```

is not necessarily the name of the real infrastructure object.

For example:

```hcl
resource "local_file" "welcome" {
  filename = "production-message.txt"
}
```

Terraform knows the resource as:

```text
local_file.welcome
```

The actual file is:

```text
production-message.txt
```

Do not confuse Terraform addresses with real-world resource names.

---

# 10. Arguments

An argument assigns a value to a named configuration setting.

General form:

```hcl
name = expression
```

Example:

```hcl
filename = "welcome.txt"
```

Here:

```text
filename
```

is the argument name.

```text
"welcome.txt"
```

is the expression.

The expression evaluates to a value.

---

# 11. Argument vs Attribute

These words are easy to confuse.

A useful distinction is:

```text
Argument
=
A value you provide as configuration input
```

Example:

```hcl
filename = "welcome.txt"
```

An attribute commonly refers to a named value exposed by an object, such as a resource value you can read.

Conceptually:

```text
You configure arguments
↓
Provider performs operation
↓
Resource can expose attributes
↓
Other expressions can reference those attributes
```

Provider documentation tells you which arguments and attributes a resource supports.

---

# 12. Expressions

An expression produces a value.

The simplest expression is a literal:

```hcl
"hello"
```

Another:

```hcl
42
```

Another:

```hcl
true
```

Expressions can also be more complex:

```hcl
var.environment
```

or:

```hcl
var.environment == "production"
```

or:

```hcl
var.environment == "production" ? 3 : 1
```

Terraform evaluates expressions to produce values.

---

# 13. Literal Expressions

A literal expression directly represents a value.

Examples:

```hcl
"production"
```

```hcl
100
```

```hcl
true
```

```hcl
null
```

```hcl
["web", "api", "database"]
```

```hcl
{
  environment = "production"
  owner       = "platform"
}
```

---

# 14. Identifiers

Terraform uses identifiers for many names.

Examples include:

```hcl
environment
```

```hcl
instance_count
```

```hcl
production_servers
```

Names should be descriptive.

Prefer:

```hcl
instance_count
```

over:

```hcl
x
```

Prefer:

```hcl
application_subnets
```

over:

```hcl
stuff
```

Infrastructure code is maintained by humans.

Readable naming matters.

---

# 15. Naming Style

Terraform style commonly uses underscores:

```hcl
instance_count
```

```hcl
application_name
```

```hcl
private_subnets
```

For resource names, prefer meaningful nouns.

Example:

```hcl
resource "local_file" "application_config" {
}
```

rather than:

```hcl
resource "local_file" "local_file_resource_one" {
}
```

Avoid repeating information already provided by the resource type.

# 16. Primitive Values

Terraform's main primitive value types are:

```text
string
number
bool
```

There is also the special value:

```text
null
```

We will examine each.

---

# 17. Strings

A string represents text.

Example:

```hcl
"hello"
```

Another:

```hcl
"production"
```

Another:

```hcl
"us-east-1"
```

Strings are normally surrounded by double quotes.

---

# 18. String Examples in Terraform

```hcl
variable "environment" {
  type    = string
  default = "development"
}
```

Another:

```hcl
resource "local_file" "example" {
  filename = "example.txt"
  content  = "Terraform created this file."
}
```

---

# 19. String Escape Sequences

Inside quoted strings, escape sequences can represent special characters.

For example:

```hcl
"Line one\nLine two"
```

`\n` represents a newline.

Result:

```text
Line one
Line two
```

A tab can be represented using:

```text
\t
```

A literal double quote inside a quoted string can be escaped.

Example:

```hcl
"Terraform says \"hello\"."
```

---

# 20. String Interpolation

Terraform strings can include expressions.

Example:

```hcl
"Environment: ${var.environment}"
```

If:

```hcl
var.environment
```

equals:

```text
production
```

the resulting string becomes:

```text
Environment: production
```

---

# 21. Prefer Direct References When You Do Not Need a String Template

Suppose an argument expects a string.

Instead of:

```hcl
name = "${var.application_name}"
```

prefer:

```hcl
name = var.application_name
```

when you are simply forwarding the value.

Interpolation is useful when combining text and expressions:

```hcl
name = "${var.application_name}-${var.environment}"
```

---

# 22. Numbers

Numbers are written without quotes.

Example:

```hcl
3
```

Another:

```hcl
80
```

Another:

```hcl
3.5
```

Do not confuse:

```hcl
3
```

with:

```hcl
"3"
```

The first is a number.

The second is a string.

---

# 23. Number Example

```hcl
variable "instance_count" {
  type    = number
  default = 3
}
```

Another:

```hcl
locals {
  minimum_instances = 2
  maximum_instances = 10
}
```

---

# 24. Booleans

Boolean values are:

```hcl
true
```

and:

```hcl
false
```

They are not strings.

Correct:

```hcl
enabled = true
```

Different type:

```hcl
enabled = "true"
```

The first is a boolean.

The second is text.

---

# 25. Boolean Example

```hcl
variable "enable_monitoring" {
  type    = bool
  default = true
}
```

Later you might use it in an expression:

```hcl
var.enable_monitoring ? "monitoring-enabled" : "monitoring-disabled"
```

---

# 26. Null

Terraform supports:

```hcl
null
```

`null` represents absence or omission.

Example:

```hcl
variable "optional_description" {
  type    = string
  default = null
}
```

In many argument contexts, assigning `null` behaves similarly to omitting the argument, allowing the receiving construct to use its default behavior where applicable.

---

# 27. Why `null` Is Useful

Suppose an argument should only be configured in production.

Conceptually:

```hcl
some_argument = var.environment == "production" ? "production-value" : null
```

Meaning:

```text
Production
↓
Use configured value

Other environment
↓
Do not provide meaningful value
```

Exact behavior still depends on the receiving argument.

---

# 28. Collection and Structural Values

Terraform also works with more complex values.

Important categories include:

```text
list
set
map
tuple
object
```

These are essential for real infrastructure.

---

# 29. Lists

A list represents an ordered sequence of values of a consistent element type.

Example:

```hcl
[
  "web",
  "api",
  "database",
]
```

Order matters.

Conceptually:

```text
index 0 → web
index 1 → api
index 2 → database
```

---

# 30. List Type Constraint

Example:

```hcl
variable "availability_zones" {
  type = list(string)

  default = [
    "us-east-1a",
    "us-east-1b",
  ]
}
```

This says:

```text
The variable expects a list
whose elements are strings.
```

---

# 31. Indexing a List

Given:

```hcl
locals {
  environments = [
    "development",
    "staging",
    "production",
  ]
}
```

You can access:

```hcl
local.environments[0]
```

Result:

```text
development
```

Remember:

```text
Terraform indexes start at 0.
```

Therefore:

```text
0 → development
1 → staging
2 → production
```

---

# 32. Index Out of Range

If the list has three elements:

```hcl
[
  "development",
  "staging",
  "production",
]
```

valid indexes are:

```text
0
1
2
```

Trying:

```hcl
local.environments[3]
```

attempts to access a nonexistent fourth element and produces an error when Terraform can evaluate it.

---

# 33. Sets

A set is a collection of unique values without meaningful ordering.

Example type:

```hcl
set(string)
```

Conceptually:

```text
{
  web
  api
  database
}
```

Important:

```text
Sets are unordered.
```

Therefore, you should not think:

```text
index 0
index 1
index 2
```

for a set.

---

# 34. Creating a Set

Terraform does not have a distinct literal syntax that inherently means "set."

A common way to create one is:

```hcl
toset([
  "web",
  "api",
  "database",
])
```

The function:

```text
toset()
```

converts a compatible collection into a set.

---

# 35. Duplicate Values in Sets

Consider:

```hcl
toset([
  "web",
  "api",
  "web",
])
```

A set contains unique values.

The duplicate:

```text
web
```

does not represent a second distinct element.

This property makes sets useful for some `for_each` patterns later.

---

# 36. Lists vs Sets

List:

```text
Ordered
Indexed
Can represent duplicate elements
```

Set:

```text
Unordered
Not indexed by position
Unique elements
```

Choose based on the meaning of the data.

Do not choose only because one syntax looks easier.

---

# 37. Maps

A map associates keys with values of a consistent element type.

Example:

```hcl
{
  development = "small"
  staging     = "medium"
  production  = "large"
}
```

You retrieve a value using its key.

---

# 38. Map Type Constraint

Example:

```hcl
variable "instance_sizes" {
  type = map(string)

  default = {
    development = "small"
    staging     = "medium"
    production  = "large"
  }
}
```

Meaning:

```text
Map
↓
String keys
↓
String values
```

---

# 39. Accessing Map Values

Given:

```hcl
local.instance_sizes
```

you can access:

```hcl
local.instance_sizes["production"]
```

Result:

```text
large
```

For fixed keys that are valid identifiers, attribute-style access may sometimes work:

```hcl
local.instance_sizes.production
```

For maps with arbitrary keys, bracket notation is clearer and safer:

```hcl
local.instance_sizes["production"]
```

---

# 40. Objects

An object contains named attributes that can have different types.

Example:

```hcl
{
  name       = "payments-api"
  port       = 8080
  monitoring = true
}
```

Here:

```text
name
```

is a string.

```text
port
```

is a number.

```text
monitoring
```

is a boolean.

---

# 41. Object Type Constraint

Example:

```hcl
variable "application" {
  type = object({
    name       = string
    port       = number
    monitoring = bool
  })
}
```

A valid value might be:

```hcl
{
  name       = "payments-api"
  port       = 8080
  monitoring = true
}
```

---

# 42. Accessing Object Attributes

Given:

```hcl
var.application
```

you can access:

```hcl
var.application.name
```

```hcl
var.application.port
```

```hcl
var.application.monitoring
```

This is attribute access.

---

# 43. Maps vs Objects

They can look similar:

```hcl
{
  key = "value"
}
```

But conceptually they serve different purposes.

Map:

```text
Collection of values with a common element type
identified by keys
```

Object:

```text
Structured value with a defined set of named attributes,
potentially with different types
```

Example map:

```hcl
map(string)
```

Example object:

```hcl
object({
  name    = string
  port    = number
  enabled = bool
})
```

---

# 44. Tuples

A tuple is an ordered sequence where each position can have its own expected type.

Example:

```hcl
[
  "web",
  8080,
  true,
]
```

Conceptually:

```text
position 0 → string
position 1 → number
position 2 → bool
```

A tuple type could be:

```hcl
tuple([
  string,
  number,
  bool,
])
```

---

# 45. Lists vs Tuples

List:

```text
Ordered collection
Elements share a common element type
```

Tuple:

```text
Ordered structural value
Each position can have its own type
```

Example list:

```hcl
["web", "api", "database"]
```

Example tuple:

```hcl
["web", 8080, true]
```

---

# 46. Complex Types Are Context Sensitive

You will sometimes see Terraform automatically convert between related complex types when possible.

Examples can include:

```text
tuple ↔ list
object ↔ map
set ↔ list
```

But conversion can alter important properties such as ordering or discard attributes depending on the target type.

Do not rely on accidental conversion without understanding the receiving type constraint.

---

# 47. Comments

Terraform supports several comment syntaxes.

Preferred Terraform style:

```hcl
# This is a comment
```

Terraform also recognizes:

```hcl
// This is a comment
```

and:

```hcl
/*
This is a
multi-line comment.
*/
```

HashiCorp's style guidance prefers:

```text
#
```

for normal comments.

---

# 48. Good Comments

Bad:

```hcl
# Set filename
filename = "app.txt"
```

The code already tells us that.

Better:

```hcl
# This file is consumed by the legacy bootstrap process.
filename = "app.txt"
```

Good comments explain:

```text
why
constraints
non-obvious decisions
operational context
```

not obvious syntax.

---

# 49. Do Not Use Comments to Rescue Bad Naming

Instead of:

```hcl
# Number of application instances
variable "x" {
  type = number
}
```

prefer:

```hcl
variable "application_instance_count" {
  type = number
}
```

Readable code reduces the need for explanatory comments.

---

# 50. Multi-Line Strings

You can include newline escape sequences:

```hcl
content = "Line one\nLine two\nLine three\n"
```

For short strings this may be fine.

For larger multi-line text, Terraform provides heredoc syntax.

---

# 51. Heredoc Syntax

Example:

```hcl
content = <<EOT
Line one
Line two
Line three
EOT
```

Everything between the opening and closing marker becomes part of the string.

`EOT` is a delimiter name.

You could choose another valid identifier.

For example:

```hcl
content = <<CONFIG
environment=production
logging=enabled
CONFIG
```

---

# 52. Indented Heredoc

Terraform also supports an indented heredoc form using:

```text
<<-
```

Example:

```hcl
content = <<-EOT
  environment=production
  logging=enabled
EOT
```

Terraform can remove common leading indentation according to heredoc rules.

This is useful when multi-line content appears inside an indented block.

---

# 53. Heredoc Interpolation

Expressions can appear inside template strings.

Example:

```hcl
locals {
  environment = "production"

  message = <<-EOT
    Application environment: ${local.environment}
    Managed by Terraform.
  EOT
}
```

The resulting string incorporates the value of:

```hcl
local.environment
```

---

# 54. Expressions Can Be More Than Literals

Consider:

```hcl
instance_count = 3
```

`3` is a literal expression.

Now:

```hcl
instance_count = var.instance_count
```

This expression references another value.

Now:

```hcl
instance_count = var.environment == "production" ? 3 : 1
```

This expression computes a value.

Terraform expressions are one of the most powerful parts of the language.

---

# 55. References

A reference retrieves another named value.

Common Terraform reference families include:

```text
var.
local.
resource type + name
data.
module.
path.
terraform.
```

We will focus on the most important beginner references first.

---

# 56. Variable References

Input variables are declared using:

```hcl
variable "environment" {
  type    = string
  default = "development"
}
```

Reference the value using:

```hcl
var.environment
```

Mental model:

```text
variable "environment"
↓
var.environment
```

---

# 57. Variable Reference Example

```hcl
variable "filename" {
  type    = string
  default = "application.txt"
}

resource "local_file" "application" {
  filename = var.filename
  content  = "Managed by Terraform."
}
```

The resource no longer hardcodes:

```text
application.txt
```

It obtains it from:

```hcl
var.filename
```

---

# 58. Local Values

Local values allow you to assign names to expressions for reuse within a module.

Example:

```hcl
locals {
  environment = "development"
  application = "veriqta-api"
}
```

Reference them with:

```hcl
local.environment
```

and:

```hcl
local.application
```

Notice:

```text
locals
```

is the block name.

But references use:

```text
local.
```

singular.

---

# 59. Local Reference Example

```hcl
locals {
  application = "veriqta-api"
  environment = "development"
  full_name   = "${local.application}-${local.environment}"
}
```

Then:

```hcl
local.full_name
```

evaluates to:

```text
veriqta-api-development
```

---

# 60. Variables vs Locals

Input variable:

```text
Input to the module
```

Local value:

```text
Internal reusable expression/value
inside the module
```

Think:

```text
Outside
↓
Variable
↓
Module
↓
Local Computation
↓
Resources
```

---

# 61. Resource References

Suppose:

```hcl
resource "local_file" "application" {
  filename = "application.txt"
  content  = "Hello"
}
```

The resource address is:

```text
local_file.application
```

Attributes exposed by that resource can be referenced using:

```text
RESOURCE_TYPE.RESOURCE_NAME.ATTRIBUTE
```

Conceptually:

```hcl
local_file.application.id
```

The exact available attributes depend on the resource schema.

Never invent resource attributes.

Check provider documentation.

---

# 62. Resource References Create Dependencies

Suppose resource B references an attribute from resource A.

Conceptually:

```hcl
resource "example_a" "first" {
}

resource "example_b" "second" {
  value = example_a.first.some_attribute
}
```

Terraform can infer:

```text
second depends on first
```

because the expression creates a dependency.

This is extremely important.

Terraform configuration order is not simply top-to-bottom execution.

References help Terraform construct a dependency graph.

---

# 63. Dependency Mental Model

Do not think:

```text
Line 1
↓
Line 2
↓
Line 3
```

Think:

```text
Configuration
↓
References
↓
Dependency Graph
↓
Execution Order
```

This is a major shift from shell scripting.

---

# 64. Data Sources

A data source reads information rather than declaring a managed resource lifecycle.

Generic syntax:

```hcl
data "RESOURCE_TYPE" "NAME" {
}
```

Reference pattern:

```text
data.RESOURCE_TYPE.NAME.ATTRIBUTE
```

Example shape:

```hcl
data "example_type" "current" {
}

locals {
```

# 76. Operator Precedence

Terraform has an order of operations.

For example:

```hcl

```

is interpreted as:

```text

```

not:

```text
(1 + 2) * 3
```

When an expression could be confusing, use parentheses.

Readable:

```hcl
(var.minimum + var.extra) * var.replica_count
```

Do not make maintainers mentally reconstruct complex precedence rules unnecessarily.

# 77. Conditional Expressions

Terraform supports conditional expressions.

Syntax:

```text
condition ? true_value : false_value
```

Example:

```hcl

```

Meaning:

```text
Is environment production?
├── Yes → 3
└── No  → 1
```

---

# 78. Conditional Example

```hcl

  type    = string
  default = "development"
}

  instance_count = var.environment == "production" ? 3 : 1
}
```

If:

```text
environment = production
```

then:

```text
instance_count = 3
```

Otherwise:

```text
instance_count = 1
```

# 79. Conditional Branch Types

Terraform needs to determine a consistent result type for conditional expressions.

For example:

```hcl
condition ? "enabled" : "disabled"
```

is straightforward because both branches are strings.

Mixing incompatible result types can cause errors or conversions you did not intend.

Prefer clear, type-consistent branches.

# 81. For Expressions

A `for` expression transforms one collection into another.

Suppose:

```hcl
locals {
  environments = [
    "development",
    "staging",
    "production",
  ]
}
```

You could write:

```hcl
[
  for environment in local.environments :
  upper(environment)
]
```

Result:

```hcl
[
  "DEVELOPMENT",
  "STAGING",
  "PRODUCTION",
]
```

---

# 82. Read a For Expression Slowly

Take:

```hcl
[
  for environment in local.environments :
  upper(environment)
]
```

Read it as:

```text
For each environment
in local.environments

take the environment
↓
convert it to uppercase
↓
place the result into a new collection
```

Do not try to memorize the punctuation before understanding the transformation.

---

# 83. For Expressions with Maps

Suppose:

```hcl
locals {
  ports = {
    web = 80
    api = 8080
  }
}
```

A map-oriented `for` expression can use both key and value.

Example:

```hcl
{
  for service, port in local.ports :
  service => "port-${port}"
}
```

Conceptual result:

```hcl
{
  web = "port-80"
  api = "port-8080"
}
```

---

# 84. Filtering with For Expressions

For expressions can include filtering conditions.

Example:

```hcl
locals {
  ports = [
    80,
    443,
    8080,
    8443,
  ]

  high_ports = [
    for port in local.ports :
    port
    if port > 1024
  ]
}
```

Result:

```hcl
[
  8080,
  8443,
]
```

---

# 85. Splat Expressions

Splat expressions provide a concise way to retrieve the same attribute from each element in a collection of similar objects.

Suppose conceptually:

```hcl
local.servers
```

contains:

```hcl
[
  {
    name = "web-1"
    ip   = "10.0.1.10"
  },
  {
    name = "web-2"
    ip   = "10.0.1.11"
  },
]
```

You can use:

```hcl
local.servers[*].ip
```

Result:

```hcl
[
  "10.0.1.10",
  "10.0.1.11",
]
```

---

# 86. Splat Mental Model

Think:

```text
Collection of objects
↓
[*]
↓
Get same attribute from each
↓
New collection
```

Example:

```hcl
local.servers[*].name
```

produces the names.

---

# 87. Equivalent For Expression

A splat such as:

```hcl
local.servers[*].ip
```

is conceptually similar to:

```hcl
[
  for server in local.servers :
  server.ip
]
```

The `for` expression is more general.

The splat form is concise for straightforward attribute extraction.

# 97. Why Type Constraints Matter

Without clear constraints, it is harder to understand what a module expects.


# 98. The `any` Type Constraint

Terraform supports:

```hcl
type = any
```

This means Terraform can accept a suitable single type determined from the provided value.

Do not automatically use `any` because you are unsure which type to declare.

Prefer precise type constraints when your module has a known contract.

# 99. Type Conversion

Terraform can automatically convert compatible values in some contexts.

For example, if a receiving type requires a string, Terraform can sometimes convert a number or boolean to its string representation.

Likewise, valid textual representations can sometimes be converted to numbers or booleans when a receiving type requires them.

But relying heavily on implicit conversion makes code harder to reason about.

Prefer giving Terraform the type you actually intend.

# 102. Dynamic Values

The phrase "dynamic value" can mean a value determined from other configuration or runtime information rather than hardcoded literally.

For example:

```hcl
locals {
  filename = "${var.application}-${var.environment}.txt"
}
```

The final value depends on:

```text
var.application
+
var.environment
```

This is more dynamic than:

```hcl
filename = "app.txt"
```

Do not confuse the general idea of dynamic values with Terraform's separate `dynamic` block feature.

---

# 103. Known Values

Some values are known during planning.

Example:

```hcl
variable "environment" {
  type    = string
  default = "development"
}
```

Terraform already knows:

```text
development
```

when evaluating the configuration.

---

# 104. Unknown Values During Planning

Some values cannot be known until a provider creates or reads something.

Imagine:

```hcl
resource "example_server" "application" {
}
```

and the remote platform assigns an ID only when the server is created.

During planning Terraform may represent:

```text
server ID
```

as:

```text
known after apply
```

This does not mean Terraform is confused.

It means the value genuinely does not exist yet.

---

# 105. Unknown Value Mental Model

Think:

```text
Configuration
↓
Plan
↓
Some values known now
+
Some values determined by provider/API later
↓
Apply
↓
Remote system creates resource
↓
Generated values become known
↓
State updated
```

---

# 106. Unknown Values Propagate

Suppose:

```text
A = unknown until apply
```

and:

```text
B = "server-${A}"
```

Then B may also be unknown during planning.

Terraform tracks these unknown values through expressions.

This allows Terraform to produce a useful plan without inventing fake values.

---

# 107. Unknown Is Not Null

This distinction is critical.

```text
null
```

means:

```text
absence/no value
```

An unknown value means:

```text
a value exists conceptually,
but Terraform cannot know it yet
```

Therefore:

```text
null
≠
unknown
```

---

# 108. Sensitive Values

Some values should not be displayed normally in Terraform CLI/UI output.

Examples can include:

```text
passwords
tokens
API keys
private material
sensitive connection information
```

Terraform allows values to be marked:

```hcl
sensitive = true
```

in supported declarations such as variables and outputs.

---

# 109. Sensitive Variable Example

```hcl
variable "database_password" {
  type      = string
  sensitive = true
}
```

This tells Terraform to treat the variable value as sensitive for display purposes.

---

# 110. Sensitive Output Example

```hcl
output "database_password" {
  value     = var.database_password
  sensitive = true
}
```

Terraform can redact the value from normal CLI output.

But this introduces an extremely important security lesson.

---

# 111. Sensitive Does Not Automatically Mean Absent from State

Marking something:

```hcl
sensitive = true
```

primarily controls disclosure in normal Terraform output and UI contexts.

Sensitive values can still be stored in Terraform state depending on how they are used.

Therefore:

```text
Sensitive
≠
Encrypted automatically
```

and:

```text
Sensitive
≠
Never stored
```

Protect Terraform state accordingly.

---

# 112. Ephemeral Values: Modern Terraform Context

Modern Terraform also provides mechanisms for values that should be omitted from state and plan files in supported contexts.

These are referred to as:

```text
ephemeral values
```

This is different from merely marking a value:

```text
sensitive
```

Mental model:

```text
Sensitive
↓
Redact normal display

Ephemeral
↓
Omit supported value from state/plan persistence
```

We will cover secret management and ephemeral values in greater depth when the series reaches security and production state handling.

---

# 113. Do Not Hardcode Secrets

Bad:

```hcl
variable "database_password" {
  default = "SuperSecretPassword123"
}
```

especially when committed to Git.

Better designs use appropriate secret-delivery mechanisms and controlled input paths.

Marking a hardcoded Git secret as sensitive does not erase it from Git history.

```text
var.application_name
┐
├─→ local.full_name
┘
var.environment
↓
"development"

local.full_name
↓
local.application.name
↓
Heredoc interpolation
↓
File content
```

```text

↓
var.enable_monitoring
↓
Conditional Expression
↓
"enabled"
↓
File content
```

```text
↓

↓
```

# 150. Configuration Organization

Terraform can read multiple `.tf` files in a module directory.

A common beginner organization is:

```text
project/
├── versions.tf
├── providers.tf
├── variables.tf
├── locals.tf
├── main.tf
├── outputs.tf
└── README.md
```

These filenames help humans navigate the configuration.

Terraform evaluates the module configuration together.

---

# 151. What Goes in `versions.tf`?

A common convention is:

```hcl
terraform {
  required_version = ">= 1.16.0, < 2.0.0"

  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "2.8.0"
    }
  }
}
```

This keeps Terraform/provider requirements easy to find.

---

# 152. What Goes in `providers.tf`?

Provider configuration commonly goes here.

Generic example:

```hcl
provider "example" {
  # provider-specific configuration
}
```

Not every provider requires explicit arguments.

Later the AWS provider configuration will become important.

---

# 153. What Goes in `variables.tf`?

Input variable declarations.

Example:

```hcl
variable "environment" {
  description = "Deployment environment."
  type        = string
  default     = "development"
}
```

---

# 154. What Goes in `locals.tf`?

Reusable internal expressions.

Example:

```hcl
locals {
  name = "${var.application_name}-${var.environment}"
}
```

Not every project requires a dedicated `locals.tf`.

Use organization that improves readability rather than creating files merely to follow a pattern.

---

# 155. What Goes in `main.tf`?

Often the primary resources and module calls.

But:

```text
main.tf
```

has no magical execution priority.

It is a human organizational convention.

Large modules often split resources by logical concern.

For example:

```text
network.tf
compute.tf
security.tf
database.tf
```

---

# 156. What Goes in `outputs.tf`?

Output declarations.

Example:

```hcl
output "application_name" {
  description = "Computed application name."
  value       = local.full_name
}
```

Outputs allow a root module to display useful information and allow child modules to expose values to their callers.

---

# 157. Do Not Over-Split Tiny Projects

A project containing one resource does not necessarily need:

```text
15 Terraform files
```

Organization should improve comprehension.

A useful principle:

```text
Small module
↓
Simple organization

Growing module
↓
Logical separation
```

Avoid both extremes:

```text
everything in one enormous file
```

and:

```text
one tiny block per file
```

without reason.

---

# 158. Terraform Formatting Conventions

Readable Terraform usually follows consistent conventions:

```text
consistent indentation
blank lines between top-level blocks
clear names
descriptive variables
descriptive outputs
limited unnecessary comments
logical resource grouping
canonical formatting
```

Use:


# 175. Common Beginner Mistake: Everything Is a String

Wrong mental model:

```text
Everything between = signs is text.
```

No.

These are different:

```hcl
"8080"
```

```hcl
8080
```

```hcl
true
```

```hcl
"true"
```

```hcl
null
```

Terraform has a real type system.

---

# 176. Common Beginner Mistake: Quoting References

Wrong:

```hcl
filename = "var.filename"
```

That produces literal text:

```text
var.filename
```

It does not reference the variable.

Correct:

```hcl
filename = var.filename
```

---

# 177. Common Beginner Mistake: Treating Terraform Like a Shell Script

Do not assume:

```text
first block
runs first

second block
runs second

third block
runs third
```

Terraform uses references and dependencies to determine relationships.

Think:

```text
Dependency Graph
```

not:

```text
Script Line Order
```

---

# 178. Common Beginner Mistake: Hardcoding Everything

Beginner configuration often becomes:

```hcl
name        = "veriqta-api-production"
environment = "production"
port        = 8080
owner       = "platform"
```

Some literal values are perfectly appropriate.

But repeated or environment-specific values often belong in:

```text
variables
locals
maps
objects
module inputs
```

depending on the design.

Do not replace every literal with a variable either.

Use abstraction when it improves the configuration.

---

# 179. Common Beginner Mistake: Making Everything a Variable

This is also bad:

```hcl
variable "managed_by_value" {
  default = "Terraform"
}
```

if the value is a fixed implementation detail that callers should never control.

Variables define module inputs.

Ask:

```text
Should a caller actually control this?
```

If not, it may not belong in an input variable.

---

# 180. Common Beginner Mistake: Excessive Locals

Locals improve readability when they:

```text
remove meaningful repetition
name a complex expression
derive useful values
centralize internal calculations
```

They hurt readability when every trivial expression is wrapped in another name.

Do not create:

```text
reference
↓
local
↓
another local
↓
another local
↓
resource
```

without a good reason.

---

# 181. Common Beginner Mistake: Depending on Set Order

A set is unordered.

Do not write logic that assumes:

```text
first set item
second set item
third set item
```

If order matters, use an ordered collection.

---

# 182. Common Beginner Mistake: Ignoring Unknown Values

Seeing:

```text
known after apply
```

does not automatically mean something is broken.

Ask:

```text
Is this value generated by the provider/API during creation?
```

If yes, an unknown planning value may be completely normal.

---

# 183. Common Beginner Mistake: Believing Sensitive Means Secure Storage

This is dangerous.

```hcl
sensitive = true
```

does not magically make state harmless.

State may contain sensitive material.

Therefore later production Terraform requires:

```text
protected backend
access controls
encryption
state locking
least privilege
secret management
```

---

# 184. Common Beginner Mistake: Editing Generated Files

Do not manually edit:

```text
.terraform.lock.hcl
```

as normal dependency-management workflow.

Do not manually modify:

```text
terraform.tfstate
```

to "fix" infrastructure.

Do not modify provider binaries inside:

```text
.terraform/
```

Use Terraform's supported commands and workflows.

# 196. Troubleshooting Matrix

| Symptom                    | Likely Area          | First Investigation                            |
| -------------------------- | -------------------- | ---------------------------------------------- |
| Unexpected token           | HCL syntax           | Check line and surrounding braces/quotes       |
| Undeclared variable        | Reference            | Check `variable` declaration and spelling      |
| Unsupported attribute      | Attribute access     | Inspect actual object/resource schema          |
| Invalid index              | Collection access    | Inspect collection length/keys                 |
| Type mismatch              | Type system          | Compare actual and required types              |
| Cycle detected             | Dependency graph     | Trace references                               |
| Provider unavailable       | Initialization       | Run/check `terraform init`                     |
| `known after apply`        | Computed value       | Determine whether provider creates value later |
| Sensitive value hidden     | Sensitivity          | Inspect declaration and propagation            |
| Formatting check fails     | Style                | Run `terraform fmt`                            |
| Unexpected resource change | Expression/reference | Trace value dependencies and plan              |
| Manual resource changed    | Drift                | Compare configuration, state, and reality      |
