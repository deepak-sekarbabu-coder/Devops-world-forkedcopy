# Part 8: Resource Dependencies, Lifecycle, and Meta-Arguments

## Learn How Terraform Determines Infrastructure Order and Behavior

One of the biggest mistakes beginners make with Terraform is assuming that Terraform reads a file from top to bottom and creates resources in the same order they appear.

It does not.

You can write:

```hcl
resource "aws_instance" "application" {
  # ...
}

resource "aws_subnet" "application" {
  # ...
}

resource "aws_vpc" "main" {
  # ...
}
```

and the position of those blocks in the file does not tell Terraform:

```text
EC2 first
↓
Subnet second
↓
VPC third
```

Terraform analyzes relationships between objects and builds a **dependency graph**.

If the EC2 instance references the subnet, and the subnet references the VPC, Terraform understands:

```text
VPC
↓
Subnet
↓
EC2
```

even if the blocks appear in a completely different order.

This is one of Terraform's most important architectural ideas.

In this part, you will learn:

* dependency graphs
* implicit dependencies
* explicit dependencies
* resource references
* `depends_on`
* dependency graph reasoning
* parallel resource creation
* resource replacement
* meta-arguments
* `count`
* `for_each`
* `provider`
* `lifecycle`
* `create_before_destroy`
* `prevent_destroy`
* `ignore_changes`
* `replace_triggered_by`
* preconditions
* postconditions
* resource addressing with `count`
* resource addressing with `for_each`
* `count` versus `for_each`
* stable resource identity
* common dependency mistakes
* circular dependencies
* lifecycle misuse

The architecture we will build toward is:

```text
VPC
↓
Subnet
↓
Security Group
↓
EC2
```

But the deeper lesson is:

```text
Terraform does not ask:

"What resource appears first in the file?"

Terraform asks:

"What depends on what?"
```

# 1. The Core Mental Model

Before learning syntax, remember this:

```text
Terraform Configuration
↓
References and Relationships
↓
Dependency Graph
↓
Execution Plan
↓
Safe Ordering
+
Parallelism Where Possible
↓
Infrastructure
```

Terraform's job is not merely to execute HCL.

Terraform must determine:

```text
What already exists?

What needs to be created?

What needs to change?

What needs replacement?

What must happen first?

What can happen simultaneously?

What must wait?

What must be destroyed first?

What relationships exist between resources?
```

The dependency graph helps Terraform answer these questions.

---

# 2. Why Infrastructure Has Dependencies

Imagine you are building this AWS environment:

```text
VPC
↓
Subnet
↓
EC2 Instance
```

An EC2 instance needs a subnet.

A subnet needs a VPC.

Therefore:

```text
EC2 depends on Subnet

Subnet depends on VPC
```

The correct creation sequence is:

```text
1. VPC
2. Subnet
3. EC2
```

Terraform needs to understand those relationships before it can safely interact with AWS.

---

# 3. A More Realistic Architecture

Consider:

```text
                     VPC
                      │
             ┌────────┴────────┐
             │                 │
          Subnet         Security Group
             │                 │
             └────────┬────────┘
                      │
                     EC2
```

The subnet and security group both require the VPC.

The EC2 instance requires both the subnet and security group.

Therefore Terraform can reason:

```text
Create VPC
↓
┌─────────────────────┐
│                     │
Create Subnet    Create Security Group
│                     │
└──────────┬──────────┘
           ↓
        Create EC2
```

Notice something important.

The subnet and security group do not necessarily depend on each other.

Therefore Terraform may create them in parallel.

That is dependency-graph execution.

---

# 4. What Is a Dependency Graph?

A dependency graph is Terraform's internal representation of relationships among configuration objects.

Think of resources as:

```text
nodes
```

and dependencies as:

```text
edges
```

For example:

```text
[VPC]
  |
  v
[Subnet]
  |
  v
[EC2]
```

Terraform understands:

```text
Subnet requires VPC

EC2 requires Subnet
```

Terraform therefore cannot safely create the EC2 instance before its required subnet exists.

---

# 5. Graph Terminology

You do not need graph theory to use Terraform, but a few terms help.

## Node

An object Terraform needs to reason about.

Conceptually:

```text
aws_vpc.main
aws_subnet.application
aws_instance.application
```

## Edge

A dependency relationship.

Example:

```text
aws_subnet.application
depends on
aws_vpc.main
```

Graphically:

```text
VPC
↓
Subnet
```

## Upstream dependency

Something another object depends on.

Example:

```text
VPC
```

is upstream of:

```text
Subnet
```

## Downstream dependent

Something that depends on an upstream object.

Example:

```text
Subnet
```

is downstream of:

```text
VPC
```

# 6. Terraform Does Not Execute Files Top to Bottom

Suppose `main.tf` contains:

```hcl
resource "aws_instance" "application" {
  ami           = "ami-example"
  instance_type = "t3.micro"
  subnet_id     = aws_subnet.application.id
}

resource "aws_subnet" "application" {
  vpc_id     = aws_vpc.main.id
  cidr_block = "10.0.1.0/24"
}

resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
}
```

A programming-language mindset might suggest:

```text
Line 1
↓
Line 2
↓
Line 3
```

Terraform instead sees:

```text
aws_vpc.main
↓
aws_subnet.application
↓
aws_instance.application
```

Why?

Because of these references:

```hcl
vpc_id = aws_vpc.main.id
```

and:

```hcl
subnet_id = aws_subnet.application.id
```

The references reveal the relationships.

---

# 7. File Names Do Not Define Dependency Order

These files:

```text
01-ec2.tf
02-subnet.tf
03-vpc.tf
```

do not force:

```text
EC2
↓
Subnet
↓
VPC
```

Likewise, renaming them:

```text
01-vpc.tf
02-subnet.tf
03-ec2.tf
```

does not create the dependencies.

Terraform evaluates the module configuration as a whole.

Use file organization for humans.

Use references for Terraform relationships.

# 8. Resource References

You learned references earlier.

Example:

```hcl
aws_vpc.main.id
```

Break it down:

```text
aws_vpc
↓
Resource Type

main
↓
Resource Name

id
↓
Resource Attribute
```

The full reference:

```hcl
aws_vpc.main.id
```

means:

> Give me the `id` attribute of the resource instance represented by `aws_vpc.main`.

But references do more than retrieve values.

They can also create dependencies.

---

# 9. Implicit Dependencies

An **implicit dependency** is a dependency Terraform can infer automatically from expressions and references.

Example:

```hcl
resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
}

resource "aws_subnet" "application" {
  vpc_id     = aws_vpc.main.id
  cidr_block = "10.0.1.0/24"
}
```

This:

```hcl
vpc_id = aws_vpc.main.id
```

tells Terraform:

```text
Subnet needs VPC ID
↓
VPC must exist before subnet can be created
```

You do not need:

```hcl
depends_on = [aws_vpc.main]
```

because Terraform already knows.

---

# 10. Why Implicit Dependencies Are Preferred

Suppose you write:

```hcl
subnet_id = aws_subnet.application.id
```

Terraform knows:

```text
EC2 needs one specific value:
Subnet ID
```

That gives Terraform precise information.

Terraform can reason about:

```text
which resource

which attribute

which relationship

when the value becomes available
```

This is usually better than manually forcing ordering.

The preferred rule is:

```text
If a real data reference naturally expresses the dependency,
use the reference.
```

---

# 11. Build the Basic AWS Graph

Consider:

```hcl
resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"

  tags = {
    Name = "veriqta-main-vpc"
  }
}

resource "aws_subnet" "application" {
  vpc_id            = aws_vpc.main.id
  cidr_block        = "10.0.1.0/24"
  availability_zone = "us-east-1a"

  tags = {
    Name = "veriqta-application-subnet"
  }
}

resource "aws_security_group" "application" {
  name        = "veriqta-application-sg"
  description = "Security group for application instances"
  vpc_id      = aws_vpc.main.id
}

resource "aws_instance" "application" {
  ami           = var.ami_id
  instance_type = "t3.micro"
  subnet_id     = aws_subnet.application.id

  vpc_security_group_ids = [
    aws_security_group.application.id
  ]

  tags = {
    Name = "veriqta-application"
  }
}
```

Terraform can derive:

```text
                       aws_vpc.main
                         /       \
                        /         \
                       v           v
       aws_subnet.application   aws_security_group.application
                       \           /
                        \         /
                         v       v
                    aws_instance.application
```

That graph comes from references.

# 12. Dependency Graph Reasoning

Read Terraform configuration by asking:

```text
What values does this resource consume?

Where do those values come from?

Which resources produce those values?

What must exist before this resource can be configured?

Which resources are independent?
```

For:

```hcl
subnet_id = aws_subnet.application.id
```

reason:

```text
EC2
needs
Subnet ID
↓
Subnet must be available
↓
EC2 depends on subnet
```

For:

```hcl
vpc_id = aws_vpc.main.id
```

reason:

```text
Subnet
needs
VPC ID
↓
Subnet depends on VPC
```

---

# 13. Dependency Graphs Affect Destruction Too

Dependencies are not only about creation.

Creation:

```text
VPC
↓
Subnet
↓
EC2
```

Destruction generally must respect the inverse relationship.

Conceptually:

```text
EC2
↓
Subnet
↓
VPC
```

You cannot normally delete a VPC while resources inside it still depend on it.

Terraform uses dependency information when planning destruction as well as creation and updates.

---

# 14. Parallel Resource Creation

Terraform does not unnecessarily serialize independent work.

Suppose:

```text
          VPC
         /   \
        /     \
       v       v
Subnet A     Subnet B
```

Both subnets depend on the VPC.

But:

```text
Subnet A
```

does not depend on:

```text
Subnet B
```

Once the VPC is available, Terraform can potentially process both concurrently.

Conceptually:

```text
Create VPC
↓
┌─────────────────────────┐
│                         │
Create Subnet A     Create Subnet B
│                         │
└─────────────────────────┘
```

This is one reason dependency accuracy matters.

---

# 15. Unnecessary Dependencies Reduce Parallelism

Imagine:

```hcl
resource "aws_subnet" "b" {
  depends_on = [aws_subnet.a]

  # ...
}
```

even though Subnet B does not actually depend on Subnet A.

You just told Terraform:

```text
Subnet A
↓
Subnet B
```

Terraform can no longer treat them as independent.

Instead of:

```text
VPC
↓
┌──────────────┐
Subnet A    Subnet B
└──────────────┘
```

you forced:

```text
VPC
↓
Subnet A
↓
Subnet B
```

Unnecessary dependencies can:

```text
reduce parallelism

make plans more conservative

increase unknown values

make infrastructure relationships harder to understand
```

---

# 16. Explicit Dependencies

Sometimes a real dependency exists but Terraform cannot infer it from a data reference.

This is called a hidden dependency.

That is where:

```hcl
depends_on
```

becomes useful.

---

# 17. `depends_on`

Basic syntax:

```hcl
resource "example_resource" "downstream" {
  depends_on = [
    example_resource.upstream
  ]
}
```

Mental model:

```text
Upstream Resource
↓
Complete required operations
↓
Downstream Resource
```

Use `depends_on` when the downstream object depends on the **behavior or side effect** of another object but does not consume one of its attributes in a way Terraform can infer.

---

# 18. Hidden Dependency Example

Imagine:

```text
IAM Policy
↓
Permission becomes available
↓
Application resource requires that permission
```

The application may not reference:

```text
aws_iam_role_policy.application.id
```

directly.

Yet the policy must exist before the application operation succeeds.

Terraform cannot infer a relationship that is not represented in configuration expressions.

You might therefore use:

```hcl
depends_on = [
  aws_iam_role_policy.application
]
```

This explicitly adds the missing edge.

---

# 19. `depends_on` Is Not a General Ordering Tool

Do not think:

```text
"I want this resource first."

↓ therefore ↓

depends_on
```

Instead ask:

```text
"Does a real dependency exist that Terraform cannot infer?"
```

If yes:

```text
depends_on
```

may be appropriate.

If no:

```text
do not manufacture a dependency.
```

---

# 20. Why `depends_on` Should Be Used Sparingly

Explicit dependencies can make Terraform's plans more conservative.

Terraform may know less precisely which particular value causes the relationship.

This can result in more values becoming:

```text
(known after apply)
```

than would be necessary with direct expression references.

Especially avoid broad dependencies such as:

```hcl
module "application" {
  depends_on = [
    module.network
  ]
}
```

unless the entire module relationship is genuinely required.

A precise reference is generally better.

---

# 21. Implicit vs Explicit Dependencies

| Dependency | How Created          | Preferred?          |
| ---------- | -------------------- | ------------------- |
| Implicit   | Expression/reference | Yes, when possible  |
| Explicit   | `depends_on`         | Only when necessary |

Example implicit:

```hcl
vpc_id = aws_vpc.main.id
```

Example explicit:

```hcl
depends_on = [
  aws_iam_role_policy.application
]
```

Rule:

```text
Use data flow to express dependencies first.

Use depends_on for hidden dependencies.
```

---

# 22. Dependency Mistake: Redundant `depends_on`

Bad:

```hcl
resource "aws_subnet" "application" {
  vpc_id = aws_vpc.main.id

  depends_on = [
    aws_vpc.main
  ]
}
```

The reference already creates the dependency.

The explicit dependency adds no useful information.

Better:

```hcl
resource "aws_subnet" "application" {
  vpc_id = aws_vpc.main.id
}
```

---

# 23. Dependency Mistake: Depending on Everything

Bad:

```hcl
depends_on = [
  aws_vpc.main,
  aws_subnet.public,
  aws_subnet.private,
  aws_security_group.application,
  aws_iam_role.application,
  aws_iam_role_policy.application,
  aws_cloudwatch_log_group.application
]
```

Do not use `depends_on` as:

```text
"Just in case."
```

Every dependency should have a reason.

---

# 24. Circular Dependencies

A circular dependency occurs when objects depend on each other in a cycle.

Example:

```text
Resource A
↓
Resource B
↓
Resource C
↓
Resource A
```

Terraform cannot determine a valid starting point.

---

# 25. Simple Circular Dependency

Conceptually:

```hcl
resource "example_a" "a" {
  value = example_b.b.id
}

resource "example_b" "b" {
  value = example_a.a.id
}
```

Terraform sees:

```text
A needs B

B needs A
```

Question:

```text
Which one should Terraform create first?
```

Answer:

```text
Neither can be created first under that dependency model.
```

Terraform reports a cycle.

---

# 26. Why Circular Dependencies Happen

Common causes include:

```text
two resources referencing each other's computed values

unnecessary depends_on relationships

modules depending on each other

security resources referencing each other incorrectly

overly coupled architecture

trying to configure two sides of a relationship simultaneously
```

The solution is usually not:

```text
force Terraform harder.
```

The solution is:

```text
redesign the dependency relationship.
```

---

# 27. Breaking a Dependency Cycle

Ask:

```text
Does A really need B during creation?

Does B really need A during creation?

Can one relationship be represented by a separate resource?

Can configuration be split into stages?

Can an attachment/association resource connect them later?

Did I add an unnecessary depends_on?
```

Sometimes the provider exposes a separate resource specifically to model a relationship after both primary resources exist.

---

# 28. Meta-Arguments

A normal resource argument belongs to the provider.

Example:

```hcl
instance_type = "t3.micro"
```

The AWS provider defines that behavior.

A **meta-argument** belongs to Terraform's language and changes how Terraform manages the block.

Examples:

```text
count
for_each
depends_on
provider
lifecycle
```

Mental model:

```text
Provider Arguments
↓
"What should this infrastructure object look like?"

Meta-Arguments
↓
"How should Terraform manage this object?"
```

# 29. `count`

By default:

```hcl
resource "aws_instance" "application" {
  # ...
}
```

represents one resource instance.

If you want three similar instances:

```hcl
resource "aws_instance" "application" {
  count = 3

  ami           = var.ami_id
  instance_type = "t3.micro"
}
```

Terraform creates:

```text
aws_instance.application[0]
aws_instance.application[1]
aws_instance.application[2]
```

---

# 30. `count.index`

Inside a block using `count`, Terraform provides:

```hcl
count.index
```

Indices begin at:

```text
0
```

Example:

```hcl
resource "aws_instance" "application" {
  count = 3

  ami           = var.ami_id
  instance_type = "t3.micro"

  tags = {
    Name = "application-${count.index}"
  }
}
```

Conceptually:

```text
Instance 0
Name = application-0

Instance 1
Name = application-1

Instance 2
Name = application-2
```

---

# 31. Resource Addresses With `count`

Without `count`:

```text
aws_instance.application
```

With `count`:

```text
aws_instance.application[0]
aws_instance.application[1]
aws_instance.application[2]
```

The index becomes part of the resource instance address.

This matters enormously for state.

Remember Part 7:

```text
Terraform Address
↕
State Binding
↕
Real Object
```

With `count`, the numeric index participates in identity.

---

# 32. Referencing a Counted Resource

Specific instance:

```hcl
aws_instance.application[0].id
```

Another:

```hcl
aws_instance.application[1].id
```

Conceptually:

```text
Resource Block
aws_instance.application

Instances
├── [0]
├── [1]
└── [2]
```

---

# 33. Conditional Creation With `count`

A common pattern:

```hcl
resource "aws_instance" "bastion" {
  count = var.create_bastion ? 1 : 0

  ami           = var.ami_id
  instance_type = "t3.micro"
}
```

If:

```text
create_bastion = true
```

then:

```text
count = 1
```

If:

```text
create_bastion = false
```

then:

```text
count = 0
```

This conditionally creates the resource.

---

# 34. Important `count` Requirement

Terraform must know the value of `count` before it begins remote resource operations.

Therefore this is conceptually problematic:

```hcl
count = some_resource.generated_number
```

if that number is unknown until after apply.

Terraform needs to construct the instance graph before creating infrastructure.

Think:

```text
Terraform must know:

How many instances exist?

before:

creating those instances.
```

---

# 35. The Identity Problem With `count`

Suppose:

```hcl
variable "servers" {
  default = [
    "api",
    "worker",
    "frontend"
  ]
}
```

You create:

```hcl
resource "aws_instance" "server" {
  count = length(var.servers)

  tags = {
    Name = var.servers[count.index]
  }
}
```

Addresses:

```text
aws_instance.server[0] → api
aws_instance.server[1] → worker
aws_instance.server[2] → frontend
```

Now remove:

```text
api
```

from the beginning.

List becomes:

```text
worker
frontend
```

Now indices become:

```text
[0] → worker
[1] → frontend
```

The identities shifted.

That can produce unnecessary changes.

---

# 36. Stable Resource Identity

This introduces one of the most important concepts in this part:

```text
Stable Resource Identity
```

Terraform needs a stable way to identify instances over time.

With `count`:

```text
identity
=
numeric index
```

With `for_each`:

```text
identity
=
map key or set member
```

If your real-world objects have meaningful stable names, `for_each` often models them better.

---

# 37. `for_each`

Example:

```hcl
resource "aws_instance" "server" {
  for_each = {
    api      = "t3.micro"
    worker   = "t3.small"
    frontend = "t3.micro"
  }

  ami           = var.ami_id
  instance_type = each.value

  tags = {
    Name = each.key
  }
}
```

Terraform creates:

```text
aws_instance.server["api"]

aws_instance.server["worker"]

aws_instance.server["frontend"]
```

These keys are meaningful identities.

---

# 38. `each.key`

Inside a `for_each` block:

```hcl
each.key
```

represents the current key.

Example:

```text
api
worker
frontend
```

---

# 39. `each.value`

If `for_each` uses a map:

```hcl
for_each = {
  api    = "t3.micro"
  worker = "t3.small"
}
```

then:

```text
each.key
↓
api

each.value
↓
t3.micro
```

and:

```text
each.key
↓
worker

each.value
↓
t3.small
```

---

# 40. Resource Addresses With `for_each`

Given:

```hcl
for_each = {
  api    = "t3.micro"
  worker = "t3.small"
}
```

addresses become:

```text
aws_instance.server["api"]

aws_instance.server["worker"]
```

Compare with `count`:

```text
aws_instance.server[0]

aws_instance.server[1]
```

The distinction is fundamental.

---

# 41. Why `for_each` Often Gives Better Identity

Suppose:

```text
api
worker
frontend
```

exist.

Remove:

```text
worker
```

With stable keys, Terraform can understand:

```text
aws_instance.server["api"]
↓
still api

aws_instance.server["frontend"]
↓
still frontend

aws_instance.server["worker"]
↓
removed
```

The identities of the remaining objects do not shift simply because one key disappeared.

---

# 42. `for_each` With a Set

Terraform can also use a set of strings.

Example:

```hcl
variable "environments" {
  type = set(string)

  default = [
    "development",
    "staging",
    "production"
  ]
}
```

Then:

```hcl
resource "terraform_data" "environment" {
  for_each = var.environments

  input = each.value
}
```

For a set of strings:

```text
each.key
=
each.value
```

Each set member identifies one instance.

---

# 43. Lists Are Not Automatically Sets

If you have:

```hcl
var.environments
```

as a list, you may need:

```hcl
toset(var.environments)
```

for `for_each`.

Example:

```hcl
for_each = toset(var.environments)
```

Remember:

```text
List
↓
ordered
duplicates possible

Set
↓
unordered identity collection
duplicates removed
```

Do not convert blindly if ordering or duplicate entries matter to your design.

---

# 44. `for_each` Values Must Be Known

Like `count`, Terraform must know `for_each` instance identities before performing remote resource operations.

Terraform cannot build the graph if the keys themselves are unknown until after apply.

Bad conceptual design:

```text
Create Resource A
↓
API generates unpredictable values
↓
Use those unknown values as for_each keys
```

Terraform needs instance keys earlier.

---

# 45. Sensitive Values Cannot Be `for_each` Keys

Do not use sensitive values as `for_each` instance identities.

Terraform exposes instance keys in:

```text
plans
state addresses
CLI output
```

Therefore keys are not appropriate places for secrets.

Bad:

```text
aws_instance.server["super-secret-password"]
```

Resource identity should never reveal sensitive information.

---

# 46. `count` vs `for_each`

Use `count` when:

```text
instances are nearly identical

numeric identity makes sense

you simply need N copies

individual keys are not meaningful
```

Use `for_each` when:

```text
instances have meaningful identities

different instances need different values

you have a map

you have a set of strings

stable keys matter
```

---

# 47. Count vs For-Each Example

Requirement:

```text
Create exactly 3 identical temporary workers.
```

Reasonable:

```hcl
count = 3
```

Requirement:

```text
Create:
api
worker
frontend
```

Better modeled as:

```hcl
for_each = {
  api      = {...}
  worker   = {...}
  frontend = {...}
}
```

The second collection represents named infrastructure objects.

---

# 48. Count vs For-Each Decision Table

| Question                                                 |   `count` | `for_each` |
| -------------------------------------------------------- | --------: | ---------: |
| Need N nearly identical instances?                       | Excellent |   Possible |
| Meaningful names/keys?                                   |      Weak |  Excellent |
| Numeric identity acceptable?                             |       Yes |    No need |
| Different configuration per object?                      |   Awkward |  Excellent |
| Removing middle item should preserve others' identities? |   Riskier |     Better |
| Uses `count.index`?                                      |       Yes |         No |
| Uses `each.key` / `each.value`?                          |        No |        Yes |

---

# 49. Never Use `count` and `for_each` Together on the Same Block

This is invalid:

```hcl
resource "aws_instance" "application" {
  count = 3

  for_each = var.servers

  # ...
}
```

Choose one instance model.

Ask:

```text
What is the identity of these objects?
```

That usually tells you which one to use.

---

# 50. Changing From `count` to `for_each`

Be careful.

Before:

```text
aws_instance.server[0]
aws_instance.server[1]
```

After:

```text
aws_instance.server["api"]
aws_instance.server["worker"]
```

Terraform addresses changed.

Remember Part 7:

```text
Address Change
↓
Potential State Identity Change
↓
Potential Replacement
```

A production migration may require:

```text
moved blocks
```

or carefully controlled state migration.

Do not casually change the instance model.

# 51. The `provider` Meta-Argument

Normally Terraform selects the default provider configuration associated with the resource type.

Example:

```hcl
resource "aws_instance" "application" {
  # uses default AWS provider configuration
}
```

But suppose:

```hcl
provider "aws" {
  region = "us-east-1"
}

provider "aws" {
  alias  = "west"
  region = "us-west-2"
}
```

You can explicitly select:

```hcl
resource "aws_instance" "west_application" {
  provider = aws.west

  ami           = var.west_ami_id
  instance_type = "t3.micro"
}
```

---

# 52. `provider` Is a Reference, Not a String

Correct:

```hcl
provider = aws.west
```

Not:

```hcl
provider = "aws.west"
```

Terraform needs to resolve provider configuration while constructing its graph.

---

# 53. Provider Dependency

A resource has an implicit dependency on its associated provider configuration.

Conceptually:

```text
AWS Provider Configuration
↓
aws_instance.application
```

Terraform cannot manage an AWS resource before the AWS provider is properly configured.

# 54. Multiple Region Architecture

Example:

```text
Terraform
│
├── aws default
│   └── us-east-1
│       └── Resources
│
└── aws.west
    └── us-west-2
        └── Resources
```

Configuration:

```hcl
provider "aws" {
  region = "us-east-1"
}

provider "aws" {
  alias  = "west"
  region = "us-west-2"
}
```

Resources can then explicitly select the required provider configuration.

# 55. The `lifecycle` Meta-Argument

Terraform normally decides whether a resource should be:

```text
created

updated in place

replaced

destroyed
```

based on:

```text
configuration
state
provider schema
real infrastructure
```

The `lifecycle` block lets you customize some of Terraform's lifecycle behavior.

Example:

```hcl
resource "example_resource" "application" {
  # ...

  lifecycle {
    create_before_destroy = true
  }
}
```

---

# 56. Resource Lifecycle

The basic lifecycle is:

```text
Create
↓
Read
↓
Update
↓
Read
↓
Destroy
```

But infrastructure changes are not always simple updates.

Suppose you change an argument the provider cannot update in place.

Terraform may need:

```text
Destroy Old
↓
Create New
```

or, with appropriate lifecycle behavior:

```text
Create New
↓
Switch
↓
Destroy Old
```

This is resource replacement.

---

# 57. Update vs Replacement

Suppose:

```hcl
instance_type = "t3.micro"
```

changes to:

```hcl
instance_type = "t3.small"
```

Depending on the resource/provider behavior, this may be updateable.

But another property may be immutable through the remote API.

Then Terraform may show:

```text
-/+
```

or otherwise indicate replacement.

Mental model:

```text
UPDATE
Existing Object
↓
Modify Same Object

REPLACEMENT
Existing Object
↓
Destroy/Create relationship
↓
New Object Identity
```

Always read the plan.

---

# 58. Why Replacement Matters

Replacement may change:

```text
resource ID

IP address

hostname

disk association

availability

dependent resources

application connectivity
```

Therefore:

```text
"1 to replace"
```

can be far more important than:

```text
"1 to change"
```

---

# 59. `create_before_destroy`

Terraform's default replacement behavior for many resources is conceptually:

```text
Old Resource
↓
Destroy
↓
Create Replacement
```

That may create downtime.

`create_before_destroy` asks Terraform to reverse replacement ordering:

```text
Old Resource Exists
↓
Create Replacement
↓
Replacement Ready
↓
Destroy Old Resource
```

Syntax:

```hcl
lifecycle {
  create_before_destroy = true
}
```

---

# 60. `create_before_destroy` Example

```hcl
resource "aws_instance" "application" {
  ami           = var.ami_id
  instance_type = "t3.micro"

  lifecycle {
    create_before_destroy = true
  }
}
```

When replacement is necessary, Terraform attempts to create the new object before destroying the old one.

But this is not magic zero downtime.

---

# 61. `create_before_destroy` Constraints

Suppose both old and new resources require the exact unique name:

```text
production-database
```

The remote platform may reject:

```text
Create second resource named production-database
```

because the old one still exists.

Therefore:

```text
create_before_destroy = true
```

only works when the platform and resource design allow both objects to coexist temporarily.

You must understand:

```text
naming constraints

quotas

IP allocation

storage behavior

dependencies

cost

traffic routing
```

---

# 62. `create_before_destroy` Is Not Zero-Downtime Deployment

It changes replacement ordering.

It does not automatically:

```text
wait for application health

move user traffic

migrate database data

update DNS safely

drain connections

verify application readiness

roll back failed deployment
```

Those require architecture beyond a lifecycle flag.

---

# 63. Dependency Propagation With `create_before_destroy`

This is an advanced but important detail.

Lifecycle behavior affects Terraform's dependency graph.

When `create_before_destroy` is necessary on a resource, Terraform may need compatible replacement ordering on dependencies to avoid impossible graph cycles.

Terraform can propagate `create_before_destroy` behavior through dependencies and record relevant behavior in state.

This is why lifecycle rules should not be treated as isolated cosmetic settings.

They affect graph construction.

---

# 64. `prevent_destroy`

For certain critical resources, you may want Terraform to reject plans that would destroy them.

Example:

```hcl
resource "aws_db_instance" "production" {
  # ...

  lifecycle {
    prevent_destroy = true
  }
}
```

Now a plan requiring destruction of that managed object will be rejected while this lifecycle rule is present.

---

# 65. Good Uses of `prevent_destroy`

Potential candidates:

```text
production databases

critical persistent storage

important stateful services

resources that are extremely expensive to reconstruct
```

But do not automatically add it everywhere.

---

# 66. `prevent_destroy` Is Not an External Deletion Lock

Very important:

```text
prevent_destroy
```

protects against certain Terraform plans that would destroy the managed object.

It does not stop:

```text
AWS administrator deleting resource manually

another Terraform configuration

another automation platform

cloud console deletion

external API deletion
```

It is Terraform lifecycle protection.

Not universal infrastructure protection.

---

# 67. Critical `prevent_destroy` Limitation

The lifecycle rule must exist in configuration.

If you remove the entire resource block from configuration, the lifecycle rule disappears with it.

Do not think:

```text
"I added prevent_destroy once, therefore Terraform can never destroy this resource."
```

That is incorrect.

Use platform-level deletion protection and organizational controls where appropriate in addition to Terraform safeguards.

---

# 68. `prevent_destroy` Can Block Legitimate Work

Suppose a database truly needs replacement.

Terraform may refuse because:

```hcl
prevent_destroy = true
```

That is the intended behavior.

Someone must deliberately review the protection and determine how the change should proceed.

Therefore:

```text
prevent_destroy
=
guardrail

not
=
permanent immortality
```

---

# 69. `ignore_changes`

Normally Terraform compares configuration with the real resource and attempts to reconcile differences.

Example:

```hcl
tags = {
  Environment = "production"
}
```

If another system changes a managed value, Terraform may propose restoring the configured value.

Sometimes another system legitimately manages a particular attribute.

`ignore_changes` can tell Terraform:

> Consider this attribute during creation, but ignore later changes to it when planning updates.

---

# 70. `ignore_changes` Example

```hcl
resource "example_resource" "application" {
  # ...

  lifecycle {
    ignore_changes = [
      tags
    ]
  }
}
```

Conceptually:

```text
Terraform creates resource
↓
Tags exist
↓
External system modifies tags
↓
Terraform observes difference
↓
Configured ignored attribute
↓
No update solely to restore that ignored change
```

---

# 71. Attribute-Level Ignoring

Prefer narrow scope where possible.

Instead of ignoring an entire complex attribute unnecessarily, target the part actually managed elsewhere when the resource schema and syntax allow it.

The design question is:

```text
Who owns this attribute?
```

If Terraform owns it:

```text
do not ignore it casually.
```

If another system owns it:

```text
document that ownership clearly.
```

---

# 72. Lifecycle Misuse: Hiding Drift

A dangerous pattern:

```text
Terraform plan keeps showing a difference.
↓
I do not understand why.
↓
Add ignore_changes.
↓
Difference disappears.
```

That is not troubleshooting.

You may have hidden:

```text
security drift

configuration errors

manual production changes

provider behavior

real architecture problems
```

First understand the drift.

Then decide whether shared ownership is intentional.

---

# 73. `ignore_changes = all`

Terraform supports broad ignore behavior for managed resource changes in appropriate lifecycle configuration.

This is extremely powerful and should be used with great caution.

Conceptually:

```text
Terraform can create/destroy the resource
but stops managing ordinary attribute updates.
```

Ask:

```text
Why is Terraform managing this resource if it intentionally ignores almost everything about its ongoing configuration?
```

There are valid edge cases.

But it should never be your default.

---

# 74. `replace_triggered_by`

Sometimes Resource B should be replaced whenever Resource A changes in a particular way.

Example concept:

```text
Application Package Resource Changes
↓
Server Must Be Replaced
```

The server's own provider arguments might not otherwise force replacement.

Terraform provides:

```hcl
lifecycle {
  replace_triggered_by = [
    some_resource.example
  ]
}
```

---

# 75. `replace_triggered_by` Mental Model

Normal dependency:

```text
A changes
↓
B may use A's new value
↓
B updates if necessary
```

Replacement trigger:

```text
A changes
↓
Terraform deliberately replaces B
```

These are not the same.

---

# 76. Attribute-Level Replacement Trigger

You can target a managed resource or relevant resource attribute.

Conceptually:

```hcl
lifecycle {
  replace_triggered_by = [
    example_resource.configuration.version
  ]
}
```

If that referenced managed attribute changes in a way that satisfies the lifecycle rule, Terraform plans replacement of the resource containing the rule.

Use this only when replacement is actually required.

---

# 77. `replace_triggered_by` and Plain Values

`replace_triggered_by` is based on planned changes to managed resources.

You cannot simply put an arbitrary local or input variable there and expect it to act as a resource change.

For cases where a plain value should indirectly trigger replacement, Terraform's built-in `terraform_data` resource can represent that value as a managed resource.

Example:

```hcl
resource "terraform_data" "application_version" {
  input = var.application_version
}

resource "example_resource" "application" {
  # ...

  lifecycle {
    replace_triggered_by = [
      terraform_data.application_version
    ]
  }
}
```

Mental model:

```text
Variable Changes
↓
terraform_data Changes
↓
Replacement Trigger Observed
↓
Application Resource Replaced
```

---

# 78. Lifecycle Rules Change Graph Behavior

Remember:

```text
lifecycle
```

does not merely add annotations.

Rules such as:

```text
create_before_destroy
replace_triggered_by
```

can change Terraform's dependency and replacement graph.

That is why Terraform must process lifecycle behavior early.

Lifecycle configuration is infrastructure behavior.

---

# 79. Preconditions

Terraform lets you define custom conditions that must be true for an operation to proceed.

A **precondition** asks:

```text
Before Terraform proceeds with this resource,
is this assumption valid?
```

Example concept:

```text
Only deploy production workloads
using an approved instance class.
```

---

# 80. Precondition Example

```hcl
resource "aws_instance" "application" {
  ami           = var.ami_id
  instance_type = var.instance_type

  lifecycle {
    precondition {
      condition     = startswith(var.instance_type, "t3.")
      error_message = "The application instance must use an approved t3 instance type."
    }
  }
}
```

If the condition is false, Terraform stops with the custom error.

---

# 81. Why Preconditions Matter

Without a precondition:

```text
Input
↓
Provider/API
↓
Maybe error later
```

With a precondition:

```text
Input
↓
Terraform checks architecture assumption
↓
Fail early with meaningful message
```

This can make modules and infrastructure configuration safer.

---

# 82. Preconditions Are Different From Variable Validation

Variable validation asks:

```text
Is this variable value acceptable in general?
```

Resource preconditions can ask:

```text
Given this resource and other available information,
is it valid to proceed?
```

Choose the validation layer that best represents the rule.

---

# 83. Preconditions With Multiple Instances

Terraform evaluates resource preconditions after evaluating `count` and `for_each`.

Therefore a precondition can reason about an individual instance.

Example concept:

```hcl
resource "terraform_data" "environment" {
  for_each = var.environments

  input = each.value

  lifecycle {
    precondition {
      condition     = each.key != ""
      error_message = "Environment keys must not be empty."
    }
  }
}
```

Each instance gets its own condition evaluation.

---

# 84. Postconditions

A **postcondition** asks:

```text
After Terraform has evaluated/read the resource,
does the resulting resource satisfy this requirement?
```

This is useful when a condition depends on resource attributes that are known after the provider has read or created the object.

---

# 85. Postcondition Mental Model

```text
Terraform creates/reads resource
↓
Provider returns attributes
↓
Evaluate postcondition
↓
True
├── Continue
└── False
    ↓
    Report failure
    ↓
    Prevent dependent operations from proceeding
```

---

# 86. Postcondition Example

Conceptually:

```hcl
resource "example_service" "application" {
  # ...

  lifecycle {
    postcondition {
      condition     = self.status == "ready"
      error_message = "The application service did not reach the required ready state."
    }
  }
}
```

The exact attributes available depend on the resource/provider schema.

Do not invent attributes.

Always check provider documentation.

---

# 87. The `self` Object

Inside appropriate lifecycle conditions, `self` refers to the current resource instance.

Conceptually:

```text
self
↓
this resource instance
```

This allows a postcondition to evaluate its resulting attributes.

---

# 88. Postconditions Can Affect Dependents

Imagine:

```text
Database
↓
Application
```

The database is created.

But a postcondition determines that the database does not satisfy a required property.

Terraform can prevent downstream dependent operations from proceeding.

This allows architectural assumptions to become executable checks.

---

# 89. Preconditions vs Postconditions

| Check         | Question                                          |
| ------------- | ------------------------------------------------- |
| Precondition  | Is it safe/valid to proceed?                      |
| Postcondition | Did the resulting object satisfy the requirement? |

Mental model:

```text
PRECONDITION
↓
Before resource operation proceeds

RESOURCE OPERATION
↓
Create/Read/Update

POSTCONDITION
↓
Validate resulting object
```

Now build the intended mental model:

```text
                         VPC
                          │
             ┌────────────┴────────────┐
             │                         │
             ▼                         ▼
          Subnet                Security Group
             │                         │
             └────────────┬────────────┘
                          ▼

```


# 91. Complete Example

```hcl

    Name = "veriqta-main-vpc"
  }
}

  vpc_id            = aws_vpc.main.id

  }
}

  name        = "veriqta-application-sg"
  description = "Security group for the application"

    }
  }

```

```text

```

for these ordinary relationships.

# 115. Common Dependency Mistakes

## Mistake 1: Depending on File Order

```text
"I put the VPC above the subnet."
```

That is not a Terraform dependency.

Use references.

---

## Mistake 2: Adding `depends_on` Everywhere

This hides the real data relationships and makes the graph unnecessarily conservative.

---

## Mistake 3: Forgetting Hidden Dependencies

Sometimes a resource depends on behavior rather than a referenced value.

That is where explicit dependency can be justified.

---

## Mistake 4: Creating Circular Dependencies

```text
A needs B
B needs A
```

Terraform cannot invent a valid starting point.

---

## Mistake 5: Using `count` for Meaningfully Named Objects

If identities are:

```text
api
worker
frontend
```

numeric indices may be a poor representation.

---

## Mistake 6: Using Unstable `for_each` Keys

Do not derive keys from values that change frequently.

Changing a key changes the resource address.

---

## Mistake 7: Changing `count` to `for_each` Without Migration Planning

Addresses change.

State identity matters.

---

## Mistake 8: Using `ignore_changes` to Silence Every Drift

You may hide a real problem.

---

## Mistake 9: Assuming `prevent_destroy` Protects Against All Deletion

It does not protect against external deletion and has important configuration limitations.

---

## Mistake 10: Assuming `create_before_destroy` Means Zero Downtime

It only changes replacement ordering.

---

## Mistake 11: Using `replace_triggered_by` for Convenience

Replacement is expensive and disruptive.

Trigger it only when the architecture requires a new object.

---

## Mistake 12: Ignoring Replacement Symbols in Plans

Replacement can have much greater consequences than an in-place update.

# 116. Lifecycle Misuse Scenario

Engineer sees:

```text
Terraform wants to update tags every run.
```

Instead of investigating, they add:

```hcl
lifecycle {
  ignore_changes = [
    tags
  ]
}
```

Plan becomes clean.

But the real cause was:

```text
external automation was removing mandatory security tags.
```

Now Terraform no longer repairs them.

The lifecycle rule hid the evidence.

Correct workflow:

```text
Unexpected Difference
↓
Investigate Owner
↓
Understand Cause
↓
Decide Desired Ownership
↓
Only Then Configure Lifecycle
```

# 117. `prevent_destroy` Misuse Scenario

Engineer adds:

```hcl
prevent_destroy = true
```

to every resource.

Now routine infrastructure evolution becomes difficult.

Terraform cannot perform necessary replacements.

Guardrails should correspond to risk.

Better:

```text

↓
normally reproducible

Production Database
↓
potentially high-risk destruction

Persistent Critical Storage
↓
potentially high-risk destruction
```

Use controls intentionally.

# 118. `create_before_destroy` Misuse Scenario

Engineer adds:

```hcl
create_before_destroy = true
```

everywhere.

During replacement, AWS refuses because:

```text
resource name already exists
```

or account quotas prevent both copies from existing.

Lesson:

```text
Lifecycle Rules
must match
Platform Reality
```

Terraform cannot override remote API constraints.

# 122. Production Scenario: Multi-AZ Application

```text
                         VPC
                          │
             ┌────────────┴────────────┐
             │                         │

             │                         │
             └────────────┬────────────┘
                          │
```


```hcl

      cidr = "10.0.1.0/24"

  }
}
```

```text
[0]
[1]
```

Dependency design is production engineering.

```text
RULE 1

Terraform does not execute infrastructure
from top to bottom.
```

```text
RULE 2

References create most dependencies automatically.
```

```text
RULE 3

Prefer implicit dependencies over depends_on.
```

```text
RULE 4

Use depends_on only for real hidden dependencies.
```

```text
RULE 5

Independent resources can be processed in parallel.
```

```text
RULE 6

Resource identity matters more than convenient syntax.
```

```text
RULE 7

Use count when numeric identity makes sense.
```

```text
RULE 8

Use for_each when stable meaningful keys make sense.
```

```text
RULE 9

Changing resource addresses can affect state identity.
```

```text
RULE 10

Lifecycle rules change infrastructure behavior.
They are not decorations.
```

```text
RULE 11

Do not use ignore_changes to hide problems.
```

```text
RULE 12

Do not assume create_before_destroy means zero downtime.
```

```text
RULE 13

Do not assume prevent_destroy protects a resource
outside Terraform.
```

```text
RULE 14

Read replacements as potential blast-radius events.
```

```text
RULE 15

When Terraform reports a cycle,
fix the architecture rather than trying to force an order.
```

# 137. Final Mental Model

You started with:

```text
VPC
↓
Subnet
↓
Security Group
↓
EC2
```

But real dependency reasoning is closer to:

```text
                         VPC
                          │
             ┌────────────┴────────────┐
             │                         │
             ▼                         ▼
          Subnet                Security Group
             │                         │
             └────────────┬────────────┘
                          ▼
                         EC2
```

Terraform sees:

```text
References
↓
Dependencies
↓
Graph
↓
Ordering
+
Parallelism
↓
Lifecycle Rules
↓
Create / Update / Replace / Destroy
↓
Provider
↓
Cloud API
↓
Infrastructure
```

And when multiple instances exist:

```text
Resource Block
↓
count
├── [0]
├── [1]
└── [2]
```

or:

```text
Resource Block
↓
for_each
├── ["api"]
├── ["frontend"]
└── ["worker"]
```

Those addresses become part of Terraform's infrastructure identity model.

The final lesson is:

```text
Terraform configuration is not a script.

It is a description of infrastructure objects
and the relationships between them.
```

Terraform uses those relationships to construct a graph.

The graph determines:

```text
what must happen first

what can happen together

what must wait

what depends on what

what can be replaced

what must be protected

what must be recreated

what can be destroyed safely
```

Once you understand the graph, `count`, `for_each`, and lifecycle behavior stop looking like isolated Terraform features.

They become parts of the same system:

```text
IDENTITY
+
RELATIONSHIPS
+
DEPENDENCIES
+
LIFECYCLE
=
HOW TERRAFORM MANAGES INFRASTRUCTURE
```

That is the foundation you need before moving into more dynamic Terraform configuration.
