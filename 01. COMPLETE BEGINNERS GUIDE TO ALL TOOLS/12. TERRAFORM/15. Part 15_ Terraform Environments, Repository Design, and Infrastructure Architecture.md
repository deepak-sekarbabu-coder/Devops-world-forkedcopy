# Part 15: Terraform Environments, Repository Design, and Infrastructure Architecture

## Learn How Real Terraform Repositories Are Organized

By now, you know how to build substantial infrastructure with Terraform.

You have learned about:

```text
Providers
Resources
Variables
Outputs
Locals
State
Dependencies
Modules
AWS networking
EC2
IAM
Load balancing
Auto Scaling
Remote state
State locking
```

But another problem appears as soon as Terraform moves beyond a small project:

```text
Where does everything go?
```

Imagine your company has:

```text
Development

Staging

Production
```

Each environment needs:

```text
VPC
Subnets
Security Groups
Load Balancers
Compute
IAM
DNS
Monitoring
```

You could create three completely independent sets of Terraform code:

```text
dev/
staging/
production/
```

and copy everything three times.

That works initially.

Then someone fixes a networking problem in production but forgets to update staging.

Someone adds a security rule to development but copies it incorrectly into production.

Someone changes an EC2 configuration in one directory but not the others.

Soon:

```text
Dev Code
≠
Staging Code
≠
Production Code
```

even though they are supposed to represent the same architecture.

The opposite extreme is also dangerous.

You could place:

```text
Every account
Every region
Every environment
Every application
Every network
Every database
```

inside one enormous Terraform configuration and one enormous state.

Now one mistake can affect everything.

Part 15 teaches how to find the balance.

The central problem is:

```text
REUSE
without
COUPLING EVERYTHING TOGETHER
```

The architecture we want is closer to:

```text
                  REUSABLE MODULES
                         │
          ┌──────────────┼──────────────┐
          │              │              │
          ▼              ▼              ▼
      Development      Staging       Production
          │              │              │
          ▼              ▼              ▼
      Dev State      Staging State    Prod State
          │              │              │
          ▼              ▼              ▼
    Dev AWS Account   Stage Account   Prod Account
```

The same infrastructure patterns can be reused.

But environments remain operationally isolated.

---

# 1. The Architecture We Are Building

A practical Terraform repository might begin like this:

```text
terraform/
├── modules/
│   ├── network/
│   ├── compute/
│   └── load-balancer/
│
└── environments/
    ├── dev/
    ├── staging/
    └── production/
```

The `modules/` directory contains reusable infrastructure components.

The `environments/` directory contains deployable root modules.

Conceptually:

```text
Reusable Modules
      │
      ├──────────────┐
      │              │
      ▼              ▼
Environment      Environment
Root Module      Root Module
      │              │
      ▼              ▼
Separate State   Separate State
      │              │
      ▼              ▼
Infrastructure   Infrastructure
```

This distinction is fundamental:

```text
modules/
=
Reusable building blocks
```

while:

```text
environments/
=
Actual deployments
```

---

# 2. What Is an Environment?

An environment is an isolated deployment context representing a particular stage, purpose, customer, region, account, or operational boundary.

Common application environments include:

```text
Development

Testing

QA

Staging

Production
```

In this part, we will focus on:

```text
Development
Staging
Production
```

---

# 3. Development Environment

Development is where engineers can safely develop and test infrastructure changes.

Typical characteristics:

```text
Lower cost

Smaller capacity

More frequent changes

Less restrictive deployment process

Disposable resources where appropriate

Synthetic or non-production data

Reduced redundancy where acceptable
```

Example:

```text
Development
├── 1 NAT Gateway
├── Smaller instances
├── Lower Auto Scaling capacity
└── Development DNS
```

The exact architecture depends on the organization.

Development should still follow security standards.

"Development" does not mean:

```text
Security does not matter.
```

---

# 4. Staging Environment

Staging is usually designed to resemble production closely enough to validate changes before production deployment.

Conceptually:

```text
Development
↓
Staging
↓
Production
```

Staging might use:

```text
Same architecture

Same Terraform modules

Similar networking

Same deployment process

Same application topology
```

while using:

```text
Lower capacity

Different DNS

Different credentials

Different state

Different account

Non-production data
```

The goal is confidence before production.

---

# 5. Production Environment

Production serves real users or business workloads.

Production usually requires stronger controls around:

```text
Availability

Security

Access

Change approval

Backups

Recovery

Monitoring

Capacity

Auditability

Cost

Incident response
```

Production should not simply be:

```text
development but bigger
```

Some production requirements are architectural.

Examples:

```text
Multi-AZ deployment

Higher minimum capacity

Stricter IAM

Protected state

Production certificates

Production DNS

Stronger logging

Backup requirements

Deletion protection where appropriate
```

---

# 6. Environment Differences

Suppose all environments use the same application platform.

You might have:

| Setting            | Development | Staging  | Production |
| ------------------ | ----------- | -------- | ---------- |
| VPC                | Yes         | Yes      | Yes        |
| Availability Zones | 2           | 2        | 3          |
| Instance size      | Small       | Medium   | Larger     |
| Minimum instances  | 1           | 2        | 3          |
| Maximum instances  | 2           | 4        | 10         |
| HTTPS              | Yes         | Yes      | Yes        |
| Monitoring         | Basic       | Strong   | Strong     |
| Backups            | Limited     | Enabled  | Strong     |
| State              | Separate    | Separate | Separate   |
| AWS account        | Dev         | Staging  | Production |

The architecture is related.

The configuration values differ.

That is where reusable Terraform design becomes valuable.

---

# 7. Environment Management

Environment management means deciding how Terraform represents and separates environments.

You need to decide:

```text
Where does environment-specific configuration live?

Where does shared infrastructure logic live?

Where is each environment's state?

Which AWS account does each environment use?

Which region does each environment use?

Who can access each environment?

Who can apply changes?

How are differences represented?

How are changes promoted?
```

Environment management is therefore more than:

```text
dev.tfvars
prod.tfvars
```

It is an architecture problem.

---

# 8. The Four Isolation Questions

For every environment, ask:

```text
1. Configuration isolation
   What code/configuration defines this environment?

2. State isolation
   Where is its Terraform state?

3. Credential isolation
   Which identity can access it?

4. Infrastructure isolation
   Which account/region/network contains it?
```

A strong environment design considers all four.

---

# 9. Environment Isolation

Environment isolation means reducing the chance that:

```text
Development change
↓
Accidentally affects
↓
Production
```

Isolation can exist at several layers:

```text
Repository
↓
Directory
↓
Root Module
↓
Backend
↓
State
↓
Credentials
↓
AWS Account
↓
Region
↓
Network
↓
Resources
```

The stronger the isolation requirement, the more of these boundaries may need separation.

---

# 10. State Isolation Is Essential

At minimum, environments that must be independently managed should not accidentally share the same state.

Bad:

```text
terraform.tfstate
├── Development resources
├── Staging resources
└── Production resources
```

Better:

```text
Development
↓
Development State
```

```text
Staging
↓
Staging State
```

```text
Production
↓
Production State
```

This reduces blast radius.

---

# 11. What Is Blast Radius?

Blast radius describes how much infrastructure can potentially be affected by one mistake, failure, credential, state operation, or Terraform change.

Imagine one state contains:

```text
Dev
Staging
Production
Networking
Databases
Applications
DNS
Security
```

A dangerous change may have a very large blast radius.

If infrastructure is separated deliberately:

```text
Production Network State

Production Application State

Development Network State

Development Application State
```

the scope of an individual Terraform operation can be smaller.

---

# 12. Blast Radius Mental Model

```text
Larger State
↓
More Resources Managed Together
↓
Potentially Larger Change Surface
```

But do not conclude:

```text
One resource per state
```

That creates a different problem.

You need useful boundaries.

---

# 13. State Boundary Question

Ask:

> Should these resources normally be planned, changed, secured, owned, and recovered together?

If yes, placing them in the same state may make sense.

If no, consider separation.

---

# 14. Environment Management Strategies

There are several common approaches.

### Approach 1

Directory-based environments.

```text
environments/
├── dev/
├── staging/
└── production/
```

### Approach 2

One configuration plus environment variable files.

```text
main.tf
variables.tf

dev.tfvars
staging.tfvars
production.tfvars
```

### Approach 3

Terraform CLI workspaces.

```text
default
dev
staging
production
```

### Approach 4

A combination.

For example:

```text
Separate account directories
+
Reusable modules
+
Variable files
```

No single approach fits every infrastructure estate.

---

# 15. Directory-Based Environments

A directory-based design gives each environment its own root module.

Example:

```text
terraform/
├── modules/
│   ├── network/
│   ├── compute/
│   └── load-balancer/
│
└── environments/
    ├── dev/
    │   ├── backend.tf
    │   ├── main.tf
    │   ├── variables.tf
    │   ├── outputs.tf
    │   └── terraform.tfvars
    │
    ├── staging/
    │   ├── backend.tf
    │   ├── main.tf
    │   ├── variables.tf
    │   ├── outputs.tf
    │   └── terraform.tfvars
    │
    └── production/
        ├── backend.tf
        ├── main.tf
        ├── variables.tf
        ├── outputs.tf
        └── terraform.tfvars
```

Each environment directory is a Terraform root module.

---

# 16. Root Modules in This Architecture

Remember:

```text
Every Terraform working directory
=
Root Module
```

Therefore:

```text
environments/dev/
```

is one root module.

```text
environments/staging/
```

is another.

```text
environments/production/
```

is another.

They can all call the same reusable child modules.

---

# 17. Shared Modules

Example:

```text
modules/network/
```

may create:

```text
VPC

Public subnets

Private subnets

Internet Gateway

Route tables

NAT infrastructure
```

Then:

```text
modules/compute/
```

might create:

```text
Launch Template

Auto Scaling Group

IAM instance profile
```

And:

```text
modules/load-balancer/
```

might create:

```text
ALB

Target Group

Listeners

Health checks
```

These modules do not represent environments themselves.

They represent reusable infrastructure capabilities.

---

# 18. Environment Root Module

The environment root module composes those capabilities.

Example:

```hcl
module "network" {
  source = "../../modules/network"

  name       = "veriqta-dev"
  cidr_block = "10.10.0.0/16"
}

module "compute" {
  source = "../../modules/compute"

  name       = "veriqta-dev"
  vpc_id     = module.network.vpc_id
  subnet_ids = module.network.private_subnet_ids
}

module "load_balancer" {
  source = "../../modules/load-balancer"

  name       = "veriqta-dev"
  vpc_id     = module.network.vpc_id
  subnet_ids = module.network.public_subnet_ids
}
```

The root module acts as the composition layer.

---

# 19. Architecture

```text
DEV ROOT MODULE
│
├── Network Module
│
├── Compute Module
│
└── Load Balancer Module
```

Then:

```text
STAGING ROOT MODULE
│
├── Network Module
│
├── Compute Module
│
└── Load Balancer Module
```

Then:

```text
PRODUCTION ROOT MODULE
│
├── Network Module
│
├── Compute Module
│
└── Load Balancer Module
```

Same building blocks.

Different deployments.

---

# 20. Why This Reduces Copy-Paste

Without modules:

```text
dev/network.tf
staging/network.tf
production/network.tf
```

might contain hundreds of almost identical lines.

With modules:

```text
modules/network/
```

contains the implementation once.

Each environment passes its configuration.

```text
Shared Logic
+
Environment Inputs
=
Environment Infrastructure
```

---

# 21. Environment Inputs

Development:

```hcl
module "compute" {
  source = "../../modules/compute"

  instance_type = "t3.micro"
  min_size      = 1
  desired_size  = 1
  max_size      = 2
}
```

Production:

```hcl
module "compute" {
  source = "../../modules/compute"

  instance_type = "t3.large"
  min_size      = 3
  desired_size  = 3
  max_size      = 10
}
```

Same module.

Different configuration.

---

# 22. Directory-Based Environment Advantage

Directory-based environments make boundaries visible.

A developer can see:

```text
environments/
├── dev/
├── staging/
└── production/
```

and immediately understand:

```text
These are separate deployment roots.
```

Each can have:

```text
Separate backend

Separate state

Separate provider configuration

Separate account

Separate region

Separate variables

Separate permissions
```

---

# 23. Directory-Based Environment Trade-Off

The danger is duplication.

You may eventually have:

```text
dev/main.tf
staging/main.tf
production/main.tf
```

that look nearly identical.

That is not automatically bad.

Small amounts of duplication at the composition layer can improve clarity.

The goal is not:

```text
Zero duplicated lines at any cost.
```

The goal is:

```text
Maintainable infrastructure architecture.
```

---

# 24. Variable-File Approach

Another approach is:

```text
terraform/
├── main.tf
├── variables.tf
├── outputs.tf
├── providers.tf
├── dev.tfvars
├── staging.tfvars
└── production.tfvars
```

Then:

```bash
terraform plan -var-file=dev.tfvars
```

or:

```bash
terraform plan -var-file=production.tfvars
```

---

# 25. Example Variable Files

`dev.tfvars`:

```hcl
environment   = "dev"
instance_type = "t3.micro"
min_size      = 1
max_size      = 2
```

`production.tfvars`:

```hcl
environment   = "production"
instance_type = "t3.large"
min_size      = 3
max_size      = 10
```

This is simple.

But there is an important danger.

---

# 26. Variable Files Do Not Create State Isolation

Running:

```bash
terraform apply -var-file=dev.tfvars
```

and later:

```bash
terraform apply -var-file=production.tfvars
```

does not automatically create separate states.

If both operations use the same backend state:

```text
terraform.tfstate
```

then Terraform sees:

```text
One state
```

with different desired values.

You may accidentally transform development infrastructure into production configuration rather than create a separate production environment.

---

# 27. Critical Mental Model

```text
Variable Files
=
Configuration Values
```

They are not:

```text
State Boundaries
```

Environment configuration and environment state must be designed separately.

---

# 28. When Variable Files Are Useful

Variable files are useful when:

```text
Same root configuration
+
Same architectural shape
+
Different values
```

For example:

```text
Region

Instance type

CIDR ranges

Capacity

Feature flags

Naming

Tags
```

But state isolation must still be solved separately.

---

# 29. Variable Files Inside Environment Directories

You can combine approaches.

Example:

```text
environments/
└── production/
    ├── backend.tf
    ├── main.tf
    ├── variables.tf
    ├── outputs.tf
    ├── us-east-1.tfvars
    └── eu-west-1.tfvars
```

But again:

```text
different tfvars
```

does not inherently mean:

```text
different state
```

You must deliberately design backend/state separation.

# 34. Workspace Mental Model

Suppose one directory contains:

```text
main.tf
variables.tf
outputs.tf
```

CLI workspaces allow:

```text
Same Configuration
│
├── default state
├── dev state
├── staging state
└── production state
```

Each workspace has separate state data.

---

# 35. Important: Workspaces Do Not Duplicate Configuration

Workspaces separate:

```text
State
```

They do not create:

```text
Different Terraform source trees
```

You still have:

```text
Same Configuration
```

running against different state instances.

---

# 36. `terraform.workspace`

Terraform exposes the selected CLI workspace name as:

```hcl
terraform.workspace
```

Example:

```hcl
locals {
  environment = terraform.workspace
}
```

You could use it in naming:

```hcl
tags = {
  Environment = terraform.workspace
}
```

Or:

```hcl
name = "veriqta-${terraform.workspace}"
```

---

# 37. Workspace-Based Configuration

You might see:

```hcl
locals {
  instance_types = {
    dev        = "t3.micro"
    staging    = "t3.medium"
    production = "t3.large"
  }

  instance_type = local.instance_types[terraform.workspace]
}
```

This can work for simple cases.

But complexity can grow quickly.

---

# 38. Workspace Conditional Explosion

Imagine:

```hcl
instance_type = terraform.workspace == "production" ? "t3.large" : "t3.micro"
```

Then:

```hcl
nat_gateway_count = terraform.workspace == "production" ? 3 : 1
```

Then:

```hcl
enable_backup = terraform.workspace == "production"
```

Then:

```hcl
enable_waf = terraform.workspace == "production"
```

Then:

```hcl
log_retention = terraform.workspace == "production" ? 365 : 7
```

Soon your configuration becomes:

```text
If dev...
If staging...
If production...
```

everywhere.

That makes infrastructure harder to reason about.

---

# 39. CLI Workspace Limitations

CLI workspaces are not strong environment-isolation boundaries by themselves.

They share the same Terraform configuration and backend configuration.

HashiCorp explicitly warns that CLI workspaces are not appropriate for deployments requiring separate:

```text
Credentials

Access controls
```

and they are not intended as a general mechanism for system decomposition.

---

# 40. Workspace Mistake

Imagine:

```text
Workspace: dev
```

You intend to run:

```bash
terraform apply
```

Then someone selects:

```bash
terraform workspace select production
```

and forgets.

Now the same working directory points at production state.

That is an operational risk.

---

# 41. Workspace State Separation Does Not Equal Full Isolation

Workspaces can provide:

```text
Separate State
```

but may still share:

```text
Backend

Credentials

Code

Working directory

Operational workflow
```

Therefore:

```text
Workspace Separation
≠
Complete Environment Isolation
```

---

# 42. When CLI Workspaces Are Useful

CLI workspaces can be useful when deployments are:

```text
Structurally similar

Using the same configuration

Using the same backend

Using similar access patterns

Short-lived

Low-risk

Not requiring strong credential separation
```

Examples might include:

```text
Temporary development copies

Feature environments

Testing environments

Repeated non-production deployments
```

depending on organizational design.

---

# 43. When Separate State and Root Modules Are Preferable

Prefer stronger separation when environments require:

```text
Different credentials

Different AWS accounts

Different security boundaries

Different backend permissions

Different operational ownership

Different lifecycle

Different compliance requirements

Independent deployment

Reduced blast radius
```

Production often falls into this category.

---

# 44. CLI Workspaces vs HCP Terraform Workspaces

Do not confuse them.

```text
Terraform CLI Workspace
```

and:

```text
HCP Terraform Workspace
```

are different concepts.

CLI workspaces are primarily separate state instances within one Terraform working directory/backend model.

HCP Terraform workspaces are a broader remote execution and configuration concept.

This part focuses on Terraform CLI architecture.

# 49. S3 Backend and CLI Workspaces

When using the S3 backend, the default workspace state uses the configured key.

For non-default workspaces, Terraform uses workspace-specific state paths under the configured workspace key prefix.

Therefore the backend can contain multiple workspace states.

Do not manually invent assumptions about those paths. Understand your backend configuration before modifying or recovering workspace state.

```text
        ├── main.tf
        ├── variables.tf
        ├── locals.tf
        ├── outputs.tf
        └── terraform.tfvars
```

This is understandable even before reading the Terraform code.

That is good architecture.

---

# 54. File Organization

A useful convention is:

```text
backend.tf
```

for backend configuration.

```text
terraform.tf
```

for Terraform and provider requirements.

```text
providers.tf
```

for provider configurations.

```text
variables.tf
```

for inputs.

```text
locals.tf
```

for local values.

```text
outputs.tf
```

for outputs.

```text
main.tf
```

for primary resources/module calls.

As configurations grow, logical files such as:

```text
network.tf
compute.tf
iam.tf
dns.tf
```

may improve navigation.

Terraform evaluates the `.tf` files in a module together. Splitting blocks across files is mainly for maintainability.

---

# 55. Monorepo

A monorepo stores multiple Terraform components or infrastructure configurations in one repository.

Example:

```text
company-infrastructure/
├── modules/
├── environments/
├── platform/
├── networking/
├── security/
└── observability/
```

Potential advantages:

```text
Central visibility

Atomic cross-component changes

Shared standards

Easy discovery

Single source-control location
```

Potential disadvantages:

```text
Large repository

Complex CI/CD

Broad repository access

Many teams changing one codebase

Harder change targeting

Potential ownership ambiguity
```

---

# 56. Monorepo Does Not Mean One State

This distinction is critical.

You can have:

```text
One Git Repository
```

with:

```text
20 Terraform States
```

Repository boundaries and state boundaries are separate decisions.

Example:

```text
one repository
│
├── environments/dev/network/
│   └── State A
│
├── environments/dev/application/
│   └── State B
│
├── environments/prod/network/
│   └── State C
│
└── environments/prod/application/
    └── State D
```

---

# 57. Multi-Repository Architecture

Instead of one repository, an organization may use:

```text
terraform-network-modules

terraform-compute-modules

production-network

production-platform

application-infrastructure
```

Different repositories can have:

```text
Different owners

Different permissions

Different release cycles

Different pipelines

Different versioning
```

---

# 58. Multi-Repository Advantages

Potential benefits:

```text
Clear ownership

Granular access control

Independent deployment

Independent versioning

Smaller repositories

Separate release lifecycles
```

This can work well for large organizations.

---

# 59. Multi-Repository Trade-Offs

Costs include:

```text
More repositories

More dependency management

Module version coordination

Cross-repository changes

Harder global discovery

More CI/CD configuration
```

There is no universal winner.

Repository design should reflect team and infrastructure boundaries.

---

# 60. Monorepo vs Multi-Repo

| Question                | Monorepo                   | Multi-Repo                |
| ----------------------- | -------------------------- | ------------------------- |
| Discovery               | Central                    | Distributed               |
| Access control          | Often broader              | More granular             |
| Cross-component changes | Easier                     | More coordination         |
| Module versioning       | Can use local modules      | Usually explicit versions |
| CI complexity           | Change detection important | Smaller pipelines         |
| Ownership               | Must be clearly defined    | Often repository-based    |
| Repository count        | Lower                      | Higher                    |

The right answer depends on the organization.

---

# 61. Shared Module Repository Pattern

A larger organization may separate reusable modules from live infrastructure.

Example:

```text
terraform-aws-network/
terraform-aws-compute/
terraform-aws-load-balancer/
```

and:

```text
company-live-infrastructure/
```

Then live infrastructure consumes versioned modules.

Conceptually:

```text
Module Repository
↓
Versioned Release
↓
Environment Root Module
↓
Infrastructure
```

---

# 62. Why Separate Reusable Modules?

Reusable modules often have a different lifecycle from live environments.

A network module might be:

```text
v1.0.0
v1.1.0
v2.0.0
```

Production can intentionally consume one version while development tests another.

That provides controlled upgrades.

---

# 63. Local Modules in a Monorepo

For a smaller organization:

```hcl
module "network" {
  source = "../../modules/network"
}
```

can be perfectly reasonable.

The module and environment change together.

This simplifies module distribution.

But independent module versioning becomes harder.

---

# 64. Root Modules vs Shared Modules

Keep this distinction clear:

```text
Shared Module
=
Reusable infrastructure implementation
```

```text
Root Module
=
Deployable composition
```

For example:

```text
modules/network/
```

knows how to create a network.

But:

```text
environments/production/
```

knows:

```text
Which network module

Which CIDR

Which region

Which account

Which capacity

Which tags

Which other modules
```

That is environment architecture.

---

# 65. Environment Modules

Sometimes teams create modules representing an entire application platform.

Example:

```text
modules/application-platform/
├── network
├── compute
├── load balancer
└── monitoring
```

Be careful.

This can become a giant module.

A better approach is often:

```text
Root Module
├── Network Module
├── Compute Module
├── Load Balancer Module
└── Monitoring Module
```

with the root composing them.

Keep module trees relatively flat when practical.

---

# 66. Module Composition

Example:

```hcl
module "network" {
  source = "../../modules/network"

  cidr_block = var.vpc_cidr
}

module "load_balancer" {
  source = "../../modules/load-balancer"

  vpc_id     = module.network.vpc_id
  subnet_ids = module.network.public_subnet_ids
}

module "compute" {
  source = "../../modules/compute"

  vpc_id     = module.network.vpc_id
  subnet_ids = module.network.private_subnet_ids
}
```

Architecture:

```text
             Root Module
                  │
          ┌───────┴───────┐
          ▼               ▼
       Network         Consumers
          │
      ┌───┴────┐
      ▼        ▼
    Compute    ALB
```

The root module controls composition.

---

# 67. Avoid Deep Module Trees

Be cautious with:

```text
Root
↓
Platform Module
↓
Application Module
↓
Compute Module
↓
Instance Module
↓
Disk Module
```

Understanding ownership and dependencies becomes harder.

Prefer flatter composition where possible.

# 68. Infrastructure Ownership

Every infrastructure component should have an identifiable owner.

Examples:

```text
Network
→ Platform/Network Team

IAM Baselines
→ Security/Platform Team

Application Infrastructure
→ Application Team

Shared Observability
→ Platform/SRE Team
```

Terraform repository architecture should make this ownership visible.

---

# 69. Ownership Questions

For every root module, ask:

```text
Who owns this configuration?

Who reviews changes?

Who can plan?

Who can apply?

Who owns the state?

Who handles incidents?

Who upgrades modules?

Who pays for resources?

Who approves destructive changes?
```

If nobody can answer, the infrastructure has an ownership problem.

# 70. Team Boundaries

Do not automatically make repository boundaries equal team boundaries.

But consider alignment.

Example:

```text

↓

↓

```

```text

↓

↓

```

```text

↓

↓

```

Interfaces connect them.

# 71. State Boundaries and Ownership

Suppose the network team owns:

```text

```

and application teams own:

```text

```


This reflects organizational ownership.

# 72. Avoid State Boundaries Based Only on File Size

Do not split state merely because:

```text

```

File organization and state architecture are different.

```text

```

into:

```text

```

without creating multiple states.

# 74. Account Separation

One of the strongest AWS environment boundaries is separate AWS accounts.

Example:

```text
AWS Organization
│
├── Development Account
├── Staging Account
├── Production Account
├── Security Account
└── Shared Services Account
```

This creates stronger isolation than merely using different tags.

# 75. Why Separate Accounts?

Account separation can improve:

```text
Access control

Billing visibility

Service quota isolation

Security boundaries

Blast radius

Auditability

Environment separation
```

A mistake in development credentials is less likely to directly provide production access if accounts and IAM are designed correctly.

# 76. Account Separation Architecture

```text
Terraform
│
├── Dev Identity
│   ↓
│   Development AWS Account
│
├── Staging Identity
│   ↓
│   Staging AWS Account
│

    ↓
```

# 77. Provider Configuration and Accounts

```hcl
  }

```

The exact authentication architecture depends on your organization.

# 78. Account IDs as Safety Checks

A mature Terraform design can validate assumptions about the AWS account.

Conceptually:

```text

Production Account

Actual:
Development Account

```

Provider capabilities and organizational policy can help create these guardrails.

The goal is to prevent:

```text

+
Wrong Account
=
Production Incident
```


This becomes difficult to operate.

Define naming rules.

# 84. Naming Model

```text

```

For example:

# 85. Keep Names Understandable

Avoid names that require a decoding manual for every engineer.

Bad:

```text

```


# 86. Naming Locals

You can centralize naming logic.

Example:

```hcl

  name_prefix = "${var.application}-${var.environment}"
```

```hcl

```

This reduces naming drift.

# 87. Naming Module

Be cautious about creating a huge abstraction purely to construct names.

A few clear locals may be easier to understand than a complicated naming framework.

Remember:

```text
Abstraction should reduce complexity.
```

If it increases complexity, reconsider it.

# 92. Tagging Is Not Security Isolation

# 93. Configuration Reuse

Good reuse means:

```text
↓

```

```text

↓

↓

```

# 94. What Should Be Reused?

Good module candidates often represent cohesive capabilities.

Examples:

```text

Database platform

Logging configuration

```

The exact boundary depends on ownership and lifecycle.

# 95. Avoid Copy-Paste Infrastructure

Imagine:

```text
dev/
└── 700 lines

staging/
└── copied 700 lines

production/
└── copied 700 lines
```

A security fix now requires three changes.

Someone will eventually forget one.

That creates configuration drift in source code itself.

---

# 96. Refactor Repeated Logic

Repeated implementation:

```text
dev VPC code
staging VPC code
production VPC code
```

can become:

```text
modules/network/
```

Then each root module calls it.

Environment-specific decisions remain outside.

---

# 97. But Do Not Eliminate Every Duplicate Line

Suppose all environments contain:

```hcl
module "network" {
  source = "../../modules/network"
}
```

That duplication is harmless.

Trying to eliminate those three lines by creating another abstraction may make the system harder to understand.

---

# 98. Avoid Over-Abstraction

Terraform engineers often discover modules and start turning everything into a module.

You may see:

```text
Module for one security group

Module for one IAM statement

Module for one route

Module for one tag

Module for one subnet

Module for one output
```

This is not automatically good architecture.

---

# 99. Abstraction Cost

Every module adds:

```text
Interface

Inputs

Outputs

Documentation

Versioning

Testing

Dependency management

Upgrade considerations

Debugging layers
```

A module should earn that complexity.

---

# 100. Abstraction Test

Before creating a module, ask:

```text
Is this a meaningful infrastructure capability?

Will it be reused?

Does it enforce a useful standard?

Does it hide unnecessary repetition?

Does it have a coherent lifecycle?

Can I describe its responsibility clearly?
```

If not, a normal resource block may be better.

---

# 101. Avoid Giant Modules

The opposite problem is:

```text
module "everything" {
}
```

that creates:

```text
VPC
DNS
EC2
IAM
Database
ALB
Monitoring
Secrets
Queues
Storage
CDN
Backups
```

Now everything changes together.

The module has too many responsibilities.

---

# 102. Giant Module Symptoms

Warning signs include:

```text
100+ input variables

Dozens of unrelated outputs

Many conditional resources

Many feature toggles

Different teams owning different pieces

Huge plan output

Every change affects the module

Difficult testing

Difficult upgrades
```

Split around meaningful boundaries.

---

# 103. Overly Fragmented Module Symptoms

The opposite warning signs:

```text
Every resource has its own module

Root module has hundreds of module calls

Simple relationships require many outputs

Debugging requires opening ten repositories

Module interfaces are larger than implementations
```

That is also poor architecture.

---

# 104. Balance

Aim for:

```text
Cohesive Modules
+
Clear Root Composition
+
Explicit Dependencies
+
Independent State Where Needed
```

Not:

```text
Maximum Number of Modules
```

and not:

```text
Everything in One Module
```

---

# 105. Environment Architecture Pattern

A strong pattern is:

```text
Environment Root Module
│
├── Network Module
├── Security Module
├── Compute Module
├── Load Balancer Module
└── Observability Module
```

The root module understands the environment.

Each child module understands its responsibility.

# 145. Architecture Smell: Environment Logic Everywhere

Bad:

```hcl
if production...

if staging...

if dev...
```

inside dozens of modules.

This means environment policy has leaked throughout the implementation.

Prefer:

```text
Environment Root
↓
Chooses Inputs
↓
Reusable Module
```

# 146. Better Module Interface

Instead of:

```hcl
variable "environment" {}

resource "..." "example" {
  size = var.environment == "production" ? 10 : 1
}
```

consider letting the root decide:

```hcl
variable "desired_capacity" {
  type = number
}
```

Then:

```text
Dev Root
desired_capacity = 1
```

and:

```text
Production Root
desired_capacity = 10
```

The module receives intent.

The environment root owns environment policy.

---

# 147. Why This Is Better

The module becomes reusable for:

```text
Development

Production

Performance testing

Disaster recovery

Another application
```

without hardcoding knowledge of those environment names.

That is cleaner abstraction.

# 191. Final Repository Architecture

We began with:

```text
terraform/
├── main.tf
├── variables.tf
└── outputs.tf
```

That is fine for learning.

A more realistic architecture becomes:

```text
terraform/
│
├── README.md
│
├── modules/
│   │
│   ├── network/
│   │   ├── main.tf
│   │   ├── variables.tf
│   │   ├── outputs.tf
│   │   └── README.md
│   │
│   ├── compute/
│   │   ├── main.tf
│   │   ├── variables.tf
│   │   ├── outputs.tf
│   │   └── README.md
│   │
│   └── load-balancer/
│       ├── main.tf
│       ├── variables.tf
│       ├── outputs.tf
│       └── README.md
│
└── environments/
    │
    ├── dev/
    │   ├── backend.tf
    │   ├── terraform.tf
    │   ├── providers.tf
    │   ├── variables.tf
    │   ├── locals.tf
    │   ├── main.tf
    │   └── outputs.tf
    │
    ├── staging/
    │   ├── backend.tf
    │   ├── terraform.tf
    │   ├── providers.tf
    │   ├── variables.tf
    │   ├── locals.tf
    │   ├── main.tf
    │   └── outputs.tf
    │
    └── production/
        ├── backend.tf
        ├── terraform.tf
        ├── providers.tf
        ├── variables.tf
        ├── locals.tf
        ├── main.tf
        └── outputs.tf
```

The architecture becomes:

```text
                    GIT REPOSITORY
                          │
                          ▼
                   REUSABLE MODULES
                          │
          ┌───────────────┼───────────────┐
          │               │               │
          ▼               ▼               ▼
         DEV           STAGING       PRODUCTION
      ROOT MODULE      ROOT MODULE      ROOT MODULE
          │               │               │
          ▼               ▼               ▼
      DEV STATE       STAGE STATE      PROD STATE
          │               │               │
          ▼               ▼               ▼
      DEV ACCOUNT     STAGE ACCOUNT    PROD ACCOUNT
```

And as infrastructure grows:

```text
Organization
│
├── Development
│   ├── Region
│   │   ├── Network State
│   │   └── Application State
│
├── Staging
│   ├── Region
│   │   ├── Network State
│   │   └── Application State
│
└── Production
    ├── Region A
    │   ├── Network State
    │   └── Application State
    │
    └── Region B
        ├── Network State
        └── Application State
```

This creates explicit:

```text
Environment Boundaries

State Boundaries

Account Boundaries

Region Boundaries

Ownership Boundaries

Module Boundaries
```

without giving up configuration reuse.

# 193. Final Mental Model

Do not think:

```text
Terraform Repository
=
A Folder Full of .tf Files
```

Think:

```text
Terraform Architecture
│
├── Reusable Modules
│
├── Root Modules
│
├── Environments
│
├── State Boundaries
│
├── Account Boundaries
│
├── Region Boundaries
│
├── Team Ownership
│
├── Naming Standards
│
├── Tagging Standards
│
└── Deployment Boundaries
```

The central design principle is:

```text
REUSE WHAT SHOULD BE SHARED

ISOLATE WHAT SHOULD FAIL INDEPENDENTLY
```

Development, staging, and production may use the same infrastructure modules.

That does not mean they should share:

```text
State

Credentials

AWS accounts

Deployment permissions

Operational blast radius
```

Similarly:

```text
Separate State
```

does not automatically require:

```text
Separate Repository
```

and:

```text
Separate Repository
```

does not automatically provide:

```text
Separate State
```

Keep these architecture dimensions separate in your mind:

```text
CODE
STATE
CREDENTIALS
ACCOUNT
REGION
OWNERSHIP
DEPLOYMENT
```

Then decide deliberately where each boundary belongs.

A strong Terraform architecture therefore looks like:

```text
                    SHARED MODULES
                         │
             ┌───────────┼───────────┐
             │           │           │
             ▼           ▼           ▼
            DEV       STAGING       PROD
             │           │           │
             ▼           ▼           ▼
         ROOT MODULE  ROOT MODULE  ROOT MODULE
             │           │           │
             ▼           ▼           ▼
         DEV STATE    STAGE STATE   PROD STATE
             │           │           │
             ▼           ▼           ▼
        DEV ACCOUNT  STAGE ACCOUNT PROD ACCOUNT
```

with:

```text
CLEAR OWNERSHIP
+
CONSISTENT NAMING
+
CONSISTENT TAGGING
+
CONTROLLED REUSE
+
SMALLER BLAST RADIUS
+
EXPLICIT ENVIRONMENT BOUNDARIES
```

That is the transition from:

```text
I know how to write Terraform.
```

to:

```text
I know how to organize Terraform infrastructure.
```
