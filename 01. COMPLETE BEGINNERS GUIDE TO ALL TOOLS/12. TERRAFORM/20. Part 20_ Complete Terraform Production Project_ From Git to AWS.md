# 5. Domain Requirement

The full Route 53 + ACM + HTTPS stage requires a domain you control or an appropriate existing DNS setup.

Do not buy a domain merely to complete the earlier stages.

Build progressively:

```text
Stage 1
ALB HTTP endpoint

Stage 2
Domain

Stage 3
ACM certificate

Stage 4
HTTPS

Stage 5
HTTP → HTTPS redirect
```

This keeps DNS and TLS from blocking the rest of the project.

---

# 6. NAT Design Decision

Private EC2 instances frequently need outbound access for:

```text
Package installation

Application dependencies

AWS APIs

Monitoring agents

Updates
```

A common architecture uses NAT for IPv4 outbound connectivity.

But NAT Gateway creates cost.

Therefore this project teaches NAT architecture without blindly forcing every learner to keep a NAT Gateway running.

You will explicitly decide between:

```text
NAT Gateway

AWS service endpoints where applicable

Prebuilt AMIs

Other controlled egress architecture
```

The final architecture must explain your decision.

# PHASE 04: REMOTE-STATE BOOTSTRAP

# 26. The Bootstrap Problem

Terraform needs remote state.

But Terraform can also create the S3 bucket that stores remote state.

That creates a question:

```text
Where does Terraform store state
while creating the place
where Terraform state will live?
```

This is the bootstrap problem.

---

# 27. Create Bootstrap Configuration

Create:

```text
bootstrap/state/
```

This configuration creates the remote-state infrastructure.

At minimum, design:

```text
S3 State Bucket
↓
Versioning
↓
Encryption
↓
Public Access Protection
↓
Restricted IAM
```

The bootstrap configuration initially has its own local state.

Treat it carefully.

---

# 28. State Bucket Requirements

The bucket should have:

```text
Unique name

Versioning enabled

Server-side encryption

Public access blocked

Restricted access
```

Why versioning?

Because accidental state overwrite or deletion is an incident you need the ability to recover from.

---

# 29. S3 State Locking

For the project backend you will use native S3 lockfile locking:

```hcl
terraform {
  backend "s3" {
    bucket       = "YOUR-STATE-BUCKET"
    key          = "dev/terraform.tfstate"
    region       = "YOUR-REGION"
    encrypt      = true
    use_lockfile = true
  }
}
```

Do not use a bucket name copied from this guide.

S3 bucket names must be globally unique.

---

# 30. State Architecture

Design:

```text
S3 State Bucket
│
├── dev/terraform.tfstate
├── staging/terraform.tfstate
└── production/terraform.tfstate
```

Each environment has a separate state object.

Later you may decide that a larger system needs even smaller state boundaries.

# 38. Use `for_each`

Rather than manually creating:

```text
public_subnet_a
public_subnet_b
private_subnet_a
private_subnet_b
```

design stable keys:

```hcl
public_subnets = {
  a = "10.20.1.0/24"
  b = "10.20.2.0/24"
}
```

Then use:

```hcl
for_each = var.public_subnets
```

Now Terraform addresses can resemble:

```text
aws_subnet.public["a"]
aws_subnet.public["b"]
```

This is usually easier to reason about than positional identity.

# FINAL KNOWLEDGE CHECK

# 176. State

### Question

Where is production Terraform state stored?

### Strong Answer

In the approved remote backend, using an environment-specific S3 object key rather than an engineer's local filesystem.

---

### Question

Why enable S3 versioning?

### Strong Answer

To provide recovery options after accidental state deletion or overwrite.

---

### Question

Why enable state locking?

### Strong Answer

To prevent concurrent Terraform writers from modifying the same state simultaneously.

---

# 177. Identity

### Question

How does GitHub Actions authenticate to AWS?

### Strong Answer

Through OIDC federation to AWS STS, which allows an authorized workflow identity to assume an IAM role and receive temporary credentials.

---

### Question

Why avoid permanent AWS keys in CI?

### Strong Answer

Long-lived credentials create persistent secret-management and compromise risk. Federated short-lived credentials reduce that exposure.

---

# 178. Networking

### Question

Why is the ALB public while EC2 is private?

### Strong Answer

Users need to reach the public application entry point, but application instances do not need direct internet exposure. The ALB receives public traffic and forwards permitted traffic to private application instances.

---

# 179. Security Groups

### Question

Why should the application security group reference the ALB security boundary instead of allowing the entire internet?

### Strong Answer

Because the intended traffic path is ALB to application. Restricting the source reduces unnecessary exposure.

---

# 180. State

### Question

Does `sensitive = true` guarantee a secret will not exist in Terraform state?

### Strong Answer

No. Sensitive marking controls disclosure in Terraform's normal interface but does not automatically remove the underlying value from state when Terraform needs to persist it.

---

# 181. Lock File

### Question

Why commit `.terraform.lock.hcl`?

### Strong Answer

It records selected provider versions and checksums so dependency selections can remain consistent and provider changes can be reviewed.

---

# 182. Modules

### Question

Why use modules?

### Strong Answer

To create meaningful reusable infrastructure interfaces with clear inputs, outputs, responsibilities, and ownership rather than repeatedly copying infrastructure code.

---

# 183. Failed Apply

### Question

Terraform apply failed. Should you immediately rerun it?

### Strong Answer

No. First inspect the error, state, and real infrastructure to determine what already succeeded and what failed. Then correct the root cause, generate a new plan, review it, and proceed deliberately.

---

# 184. Drift

### Question

Terraform detects a manual change. Should Terraform automatically revert it?

### Strong Answer

Not before investigation. Determine why the change occurred and which configuration represents the correct desired state.

---

# 185. Import

### Question

Does importing a resource guarantee the Terraform configuration matches it?

### Strong Answer

No. Import establishes a state binding. The configuration and resulting plan must still be reviewed and reconciled.

---

# 186. Refactoring

### Question

Why might moving a resource into a module cause an unexpected destroy/create plan?

### Strong Answer

Because its Terraform address changed. Terraform resource identity is associated with its address, so the refactor may require a `moved` block or another appropriate state-aware migration.

---

# 187. Production Verification

### Question

Terraform says:

```text
Apply complete!
```

Is deployment finished?

### Strong Answer

Terraform's operation finished. Production verification must still prove that AWS infrastructure, networking, health checks, application behavior, DNS, TLS, and monitoring are functioning as intended.
