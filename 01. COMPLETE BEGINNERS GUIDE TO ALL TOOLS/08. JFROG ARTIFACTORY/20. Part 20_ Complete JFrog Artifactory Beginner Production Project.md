# Part 20: Complete JFrog Artifactory Beginner Production Project

Parts 1 through 19 taught individual pieces of JFrog Artifactory.

Now those pieces become one system.

You are going to build a small application delivery environment that follows a simplified production workflow:

```text
Developer
↓
Git Repository
↓
CI Pipeline
↓
Build + Test
↓
JFrog Artifactory
├── Dependencies
├── Application Artifact
├── Container Image
└── Build Metadata
↓
Promotion
↓
Kubernetes
↓
Application
```

This project is intentionally larger than the previous labs.

You will:

* Design repositories.
* Configure dependency resolution.
* Establish users and permissions.
* Build an application.
* Resolve dependencies through Artifactory.
* Create a versioned artifact.
* Publish it.
* Publish Build Info.
* Build a container image.
* Push the image to Artifactory.
* Connect CI/CD.
* Promote a tested release.
* Deploy to Kubernetes.
* Verify exactly what was deployed.
* Trace it back to Git and CI.
* Roll it back.
* Break selected parts of the system.
* Diagnose the failures.
* Inspect logs.
* Apply cleanup and retention concepts.
* Review security.
* Document the complete lifecycle.

This is where Artifactory stops being:

```text
A place where we upload files.
```

and becomes:

```text
A controlled boundary between
software creation and software deployment.
```

# 2. The Production Story

Imagine VERIQTA has a small internal API.

Developers work on:

```text
veriqta-status-api
```

They commit code to Git.

A CI pipeline:

```text
Checks out code
↓
Resolves dependencies
↓
Compiles
↓
Tests
↓
Packages JAR
↓
Publishes JAR
↓
Publishes Build Info
↓
Builds container image
↓
Pushes image
```

The application is then tested.

The approved version is promoted.

Kubernetes retrieves the approved image.

The same tested binary moves toward production.

---

# 3. The Central Rule

Throughout this project:

```text
BUILD ONCE
↓
TEST
↓
PROMOTE
↓
DEPLOY MANY
```

Do not:

```text
Build DEV artifact
↓
Rebuild TEST artifact
↓
Rebuild STAGING artifact
↓
Rebuild PRODUCTION artifact
```

That creates different binaries.

Instead:

```text
Git Commit
↓
Build #42
↓
Artifact
↓
Test
↓
Approve
↓
Promote
↓
Deploy
```

The artifact that passed testing should be the artifact you deploy.

# 9. Why Separate Development and Release Repositories?

Development artifacts have different lifecycle characteristics from approved releases.

Development:

```text
Frequent
Shorter retention
Produced by CI
May contain pre-release versions
```

Release:

```text
Approved
Longer retention
Immutable
Used for deployment
```

This gives us a clean conceptual boundary.

# 23. Authentication vs Authorization

Remember:

```text
Authentication
↓
Who are you?

Authorization
↓
What can you do?
```

Our CI service identity may authenticate successfully but still receive:

```text
403
```

if it lacks deployment permission.

That distinction becomes important during our failure labs.

---

# 24. Secure Authentication

Prefer scoped tokens or other supported secure authentication mechanisms over embedding passwords.

Do not write:

```text

```

inside:

```text
pom.xml
Dockerfile
Git repository
CI workflow
Kubernetes manifest
```

Secrets belong in secure secret-management mechanisms.

# 31. Configure Dependency Resolution Through Artifactory

The goal is:

```text
Maven
↓
Artifactory
↓
Maven Central
```

not:

```text
Maven
────────────→ Maven Central
```

Create or configure:

```text
~/.m2/settings.xml
```

using the Maven virtual repository URL generated by your JFrog environment.

Conceptually:

```xml
<settings>
    <mirrors>
        <mirror>
            <id>veriqta-artifactory</id>
            <name>VERIQTA Artifactory</name>
            <url>YOUR_ARTIFACTORY_MAVEN_VIRTUAL_URL</url>
            <mirrorOf>*</mirrorOf>
        </mirror>
    </mirrors>
</settings>
```

Do not blindly hardcode credentials into this file.

Use the authentication method appropriate for your environment.

# 43. Why Build Info Matters

Months later, imagine production runs:

```text
veriqta-status-api:1.0.0
```

Security discovers a vulnerable library.

You need to answer:

```text
Which dependencies were used?

Which build created this image?

Which artifact did it contain?

Which Git commit produced it?

Which environments received it?
```

Without traceability, these questions become forensic archaeology.

```yaml

      - name: Build and test
        run: mvn clean package
```

# 59. Never Put Secrets in the Workflow

Bad:

```yaml
env:
  JFROG_TOKEN: abc123-secret-token
```

if the literal secret is committed to Git.

Instead use the CI platform's secret storage.

Conceptually:

```yaml
env:
  JFROG_TOKEN: ${{ secrets.JFROG_TOKEN }}
```

The repository stores only the reference.

The secret value remains in the CI secret system.

# 64. Promotion Boundary

```text
↓

↓
```

# 65. Promote the JAR

Development:

```text
veriqta-generic-dev-local/
└── veriqta-status-api/
    └── 1.0.0/
        └── veriqta-status-api-1.0.0.jar
```

Release:

```text
veriqta-generic-release-local/
└── veriqta-status-api/
    └── 1.0.0/
        └── veriqta-status-api-1.0.0.jar
```

The important rule:

```text
Checksum before promotion
=
Checksum after promotion
```

If the bytes changed, you did not promote the same artifact.

# 66. Promotion Approaches

Organizations may use:

```text
Repository-based promotion
```

such as:

```text
DEV repo
↓
RELEASE repo
```

or metadata/property-driven lifecycle states:

```text
release-status=candidate
↓
release-status=tested
↓
release-status=approved
```

More advanced JFrog environments may also use dedicated release-management capabilities.

For this beginner project, understand the principle:

```text
Promotion changes lifecycle status.

Promotion should not rebuild the binary.
```

---

# 67. Copy vs Move

If promotion uses repository operations, decide deliberately whether to:

```text
COPY
```

or:

```text
MOVE.
```

Copy:

```text
DEV retains reference
+
RELEASE receives reference
```

Move:

```text
Artifact leaves DEV
+
appears in RELEASE
```

The correct policy depends on your lifecycle and retention model.

Do not choose randomly.
