# 2. Before We Begin: Artifact vs Package

You will see both terms frequently.

They are related, but they are not always identical.

An artifact is a file or binary produced, stored, or consumed during software delivery.

Examples:

```text
application.jar
application.war
application.zip
library.whl
package.tgz
```

A package is usually a software distribution unit understood by a package ecosystem.

Examples:

```text
npm package
Python package
Maven package
NuGet package
Helm chart
```

A package may consist of one or more artifacts plus metadata.

For this lab:

```text
veriqta-demo-1.0.0.zip
```

is our artifact.

Because we are using a Generic repository, Artifactory primarily treats it as a generic binary rather than as an npm, Maven, PyPI, or other ecosystem-specific package.

Keep that distinction in mind when we later discuss package information.

# 15. Understand Version `1.0.0`

Our artifact is:

```text
veriqta-demo-1.0.0.zip
```

The version is:

```text
1.0.0
```

A common versioning approach is Semantic Versioning:

```text
MAJOR.MINOR.PATCH
```

For example:

```text
1.0.0
```

can be read as:

```text
Major: 1
Minor: 0
Patch: 0
```

Later versions might be:

```text
1.0.1
1.1.0
2.0.0
```

Do not assume every package ecosystem or organization follows Semantic Versioning, but it is a useful model for this lab.

* Reproducibility
* Auditing
* Deployment consistency
* Troubleshooting

# 29. What Is a Checksum?

A checksum is a value calculated from file content.

It can act like a content fingerprint.

Conceptually:

```text
File Content
↓
Hash Algorithm
↓
Checksum
```

If the content changes, the calculated checksum will normally change.

For example:

```text
Original Artifact
↓
SHA-256
↓
abc123...
```

If someone changes even a small amount of the artifact:

```text
Modified Artifact
↓
SHA-256
↓
different value
```

The exact values are much longer than this simplified example.

---

# 30. Common Checksum Algorithms

You may encounter:

```text
MD5
SHA-1
SHA-256
```

For modern integrity verification, SHA-256 is generally preferable to MD5 or SHA-1.

MD5 and SHA-1 may still appear in artifact-management systems for identification, compatibility, or legacy purposes, but they should not be treated as modern cryptographic security guarantees.

For our verification lab, use:

```text
SHA-256
```

---

# 31. Checksum Is Not Encryption

A common beginner mistake is to think a checksum hides the file.

It does not.

Encryption:

```text
Data
↓
Encryption
↓
Unreadable ciphertext without appropriate key
```

Hashing/checksum:

```text
Data
↓
Hash Function
↓
Fixed-size digest
```

A checksum helps us compare content.

It does not encrypt the artifact.

---

# 32. Checksum Is Not a Digital Signature

Another important distinction.

A matching checksum can help answer:

```text
Is this downloaded content identical to the content used to calculate this checksum?
```

It does not automatically answer:

```text
Who created this artifact?
Can I cryptographically prove the publisher's identity?
Should I trust this artifact?
```

Digital signatures and trusted provenance address different security questions.

We will keep this lab focused on integrity verification.

Because you are working on a MacBook, you can use:



# 41. Do Properties Change the Artifact Checksum?

Normally, adding Artifactory metadata such as properties does not mean modifying the actual ZIP file bytes.

Conceptually:

```text
Binary
↓
unchanged

Repository Metadata
↓
updated
```

Therefore, the artifact's content checksum should remain tied to the binary content.

This is an important separation between:

```text
Artifact content
```

and:

```text
Artifact metadata
```

```text
        │
        ↓
Local SHA-256
        │
        ↓
Compare
```

If:

```text
Artifactory checksum
=
Downloaded checksum
```

the integrity comparison succeeds.

---

# 47. Troubleshooting: Checksum Does Not Match

Problem:

```text
Expected SHA-256
≠
Downloaded SHA-256
```

Do not continue to deployment.

Investigate.

Possible causes include:

* Wrong file downloaded
* Wrong version downloaded
* Comparing against the wrong recorded checksum
* File modified after download
* Local filename reused for different content
* Incomplete or corrupted transfer
* Artifact overwritten at some point
* Human copy/paste mistake

Check:

```bash
pwd
```

Then:

```bash
ls -lh
```

Confirm you are calculating the checksum for the correct file.

Then calculate it again.

If the mismatch remains, retrieve the artifact again and investigate the repository state.

# 54. Understanding Versions

A version identifies a particular release or state of an artifact or package.

For our lab:

```text
1.0.0
```

and:

```text
1.1.0
```

represent different builds/releases.

If production currently uses:

```text
1.0.0
```

and you later deploy:

```text
1.1.0
```

you need to know exactly which artifact belongs to each version.

That is one reason artifact repositories matter.

---

# 55. Retrieving a Specific Version

Suppose a deployment requires:

```text
1.0.0
```

You should retrieve:

```text
veriqta-demo/1.0.0/veriqta-demo-1.0.0.zip
```

not:

```text
whatever is newest
```

A specific version produces a specific target.

Conceptually:

```text
Deployment
↓
Request 1.0.0
↓
Artifactory
↓
Return 1.0.0
```

That is deterministic.

---

# 56. What Does Deterministic Mean Here?

Deterministic means the same explicit input should lead to the intended known artifact.

If deployment configuration says:

```text
veriqta-demo version 1.0.0
```

then you know what it is requesting.

Compare that with:

```text
veriqta-demo latest
```

What does `latest` mean tomorrow?

It may no longer mean the same artifact.

---

# 57. `latest` vs Explicit Version

Suppose today:

```text
latest
↓
1.0.0
```

Tomorrow:

```text
latest
↓
1.1.0
```

Next month:

```text
latest
↓
2.0.0
```

A deployment configured only as:

```text
latest
```

may retrieve different content at different times.

An explicit version:

```text
1.0.0
```

means:

```text
retrieve 1.0.0
```

This supports reproducibility.

---

# 58. Why Explicit Versions Matter

Imagine production fails.

Someone asks:

> Which artifact was deployed?

Bad answer:

```text
latest
```

That may not tell you which binary actually ran.

Better:

```text
veriqta-demo-1.1.0.zip
SHA-256: <recorded checksum>
```

Now you have an identifiable artifact.

Explicit versions support:

* Rollback
* Auditing
* Reproducibility
* Incident investigation
* Release tracking
* Change management

---

# 59. Why `latest` Is Not Always Wrong

There are cases where moving tags, aliases, pointers, or development conventions are useful.

For example, a development environment may intentionally track a changing artifact.

The important lesson is not:

```text
Never use latest.
```

It is:

```text
Understand whether you require a fixed artifact or a moving reference.
```

For controlled production deployments, explicit immutable versions or other immutable identifiers are generally much safer.

---

# 60. Artifact Immutability Revisited

From Part 1:

```text
Artifact immutability
```

means that once a particular release artifact has been published, you should generally avoid silently replacing its content while keeping the same identity.

Bad:

```text
veriqta-demo-1.0.0.zip
↓
Content A

later

veriqta-demo-1.0.0.zip
↓
Content B
```

Now:

```text
Version 1.0.0
```

does not uniquely tell us what content existed.

Better:

```text
Content A
↓
1.0.0

Changed Content
↓
1.0.1
```

---

# 61. Version + Checksum

Versioning and checksums answer different questions.

Version:

```text
Which release is this?
```

Checksum:

```text
Does this content match the expected bytes?
```

Together:

```text
Version:
1.0.0

SHA-256:
<checksum>
```

provide stronger identification than either one alone.

# 62. Step 10: Copy an Artifact

Artifactory can copy artifacts from one repository path to another location, subject to permissions and repository compatibility.

Conceptually:

```text
Source
↓
Copy
↓
Source remains
+
Destination created
```

For example:

```text
veriqta-demo/1.0.0/veriqta-demo-1.0.0.zip
```

could be copied to a lab path such as:

```text
archive-test/veriqta-demo/1.0.0/veriqta-demo-1.0.0.zip
```

The original remains.

---

# 63. Copy vs Move

This distinction is critical.

Copy:

```text
A
↓
Copy
↓
A + B
```

Move:

```text
A
↓
Move
↓
B
```

After a copy:

```text
Source exists
Destination exists
```

After a move:

```text
Old source no longer exists
Destination exists
```

Never treat these operations as interchangeable.

# 64. Safe Copy Exercise

Before copying, record the source:



Original:

```text

```

Copy:

```text
archive-test/veriqta-demo/1.0.0/veriqta-demo-1.0.0.zip
```

Do not assume the operation succeeded because the UI displayed a notification.

Browse both paths.

---

# 65. Verify a Copied Artifact

Inspect the checksums.

If the binary was copied without content modification, the SHA-256 should correspond to the same content.

Conceptually:

```text
Original Binary
↓
SHA-256 A

Copied Binary
↓
SHA-256 A
```

Same content:

```text
same SHA-256
```

This is another practical use of checksums.

For a safe lab exercise, move the copied artifact, not your primary artifact.

Source:

```text

```

Destination:

```text

No longer present
```

Destination:

```text
Present
```

Your original artifact under:

```text

```

should remain untouched because we moved only the test copy.

# 67. Why Move Operations Need Care

Paths may be used by:

* CI/CD pipelines
* Deployment scripts
* Package managers
* Automation
* Documentation
* Other teams
* Release processes

Suppose a deployment expects:

```text
releases/payment-api/4.0.0/payment-api-4.0.0.zip
```

You move it to:

```text
old/payment-api/4.0.0/payment-api-4.0.0.zip
```

The deployment may fail.

So before moving production artifacts, ask:

```text
Who consumes this path?
```

# 68. Step 12: Delete an Artifact Safely

Deletion is destructive.

Do not practice deletion on your only copy of:

```text
veriqta-demo-1.0.0.zip
```

Instead, delete the test copy we moved.

Target:

```text
moved-test/veriqta-demo/1.0.0/veriqta-demo-1.0.0.zip
```

Before deleting, verify:

1. This is the test copy.
2. The original still exists.
3. You are in the correct repository.
4. You selected the correct path.
5. Nothing important depends on the test copy.

Then perform the delete operation.

---

# 69. Safe Deletion Reasoning

Before deletion, use:

```text
IDENTIFY
↓
VERIFY
↓
CHECK DEPENDENCIES
↓
CONFIRM BACKUP/RETENTION REQUIREMENTS
↓
DELETE
↓
VERIFY
```

Never use:

```text
I think this is the right file
↓
Delete
```

Production artifact deletion should normally be governed by permissions, retention policies, and organizational procedures.

---

# 70. Verify Deletion

After deleting, browse:

```text
moved-test/veriqta-demo/1.0.0/
```

Confirm the test artifact is gone.

Then verify:

```text
veriqta-demo/1.0.0/veriqta-demo-1.0.0.zip
```

still exists.

This confirms you deleted only the intended test copy.

# 71. Why Deleting a File Is Different From Creating a New Version

Suppose:

```text
1.0.0
```

has a problem.

Do not automatically think:

```text
Delete 1.0.0
↓
Replace it silently
```

A safer release model may be:

```text
1.0.0
↓
Known bad/recalled

1.0.1
↓
Corrected release
```

The exact process depends on organizational policy and package ecosystem, but preserving release history can be important for traceability.

# 72. Basic Cleanup Awareness

Artifact repositories grow.

Imagine CI creates:

```text
Build 1
Build 2
Build 3
...
Build 10,000
```

Each build may produce:

```text
Binaries
Metadata
Packages
Build information
```

Storage consumption increases.

Eventually, organizations need cleanup and retention policies.

But cleanup must not mean:

```text
Delete old-looking things randomly.
```

---

# 73. What Cleanup Policies Might Consider

Depending on the environment, cleanup decisions might consider:

* Artifact age
* Number of versions
* Last download time
* Build status
* Release status
* Repository purpose
* Package type
* Properties
* Retention requirements
* Legal requirements
* Production dependencies
* Rollback requirements

For example:

```text
Development snapshots
↓
Shorter retention

Production releases
↓
Longer controlled retention
```

The exact policy belongs to the organization.

---

# 74. Why "Old" Does Not Mean "Unused"

Imagine production is still running:

```text
payment-api-2.7.4
```

The artifact was created one year ago.

A naive cleanup rule says:

```text
Older than 180 days
↓
Delete
```

Now production still runs that version, but the repository no longer contains the artifact required for:

* Rebuilding an environment
* Disaster recovery
* Rollback
* Investigation

Age alone is not enough context.

---

# 75. Cleanup and Rollback

Suppose:

```text
Current production:
4.2.0

Previous stable:
4.1.3
```

A new deployment fails.

You may need:

```text
4.1.3
```

for rollback.

If cleanup deleted it without understanding release policy, recovery becomes harder.

This is why artifact lifecycle management is an operational concern, not housekeeping.

---

# 76. Search Before You Delete

Before deleting an artifact, investigate:

```text
What is it?
Which version?
Which repository?
Which builds reference it?
When was it last used?
Is it a production release?
Is it required for rollback?
Is it retained for compliance?
Are there other copies?
```

Not every question will be available from the same interface or metadata source, but this is the reasoning you should develop.

# 77. Troubleshooting: Upload Fails

Problem:

```text
Upload
↓
Failure
```

Possible causes:

* Wrong repository
* No deploy permission
* Repository does not exist
* Incorrect path
* Authentication/session problem
* Repository configuration restriction
* Network problem
* Storage/service problem

Investigate systematically.

First:

```text
Am I authenticated?
```

Then:

```text
Am I uploading to the correct repository?
```

Then:

```text
Do I have deploy permission?
```

Then:

```text
Is the repository Local and appropriate for this artifact?
```

Then inspect the error returned by Artifactory.

Do not repeatedly click Upload without reading the error.

# 78. Troubleshooting: 401 vs 403

These HTTP responses often confuse beginners.

A simplified mental model:

```text
401 Unauthorized
↓
Authentication problem or authentication required
```

```text
403 Forbidden
↓
Identity may be known, but operation is not permitted
```

Real authentication systems can have additional nuance, but this distinction is useful.

Ask:

```text
401
→ Did authentication succeed?

403
→ Does this identity have permission?
```

---

# 79. Troubleshooting: 404

A `404 Not Found` generally means the requested resource was not found from the requester's perspective.

Possible reasons:

* Wrong repository key
* Wrong path
* Wrong filename
* Wrong version
* Artifact deleted
* URL typo
* Repository endpoint incorrect
* Access rules may affect visibility in some setups

Start with the exact requested path.

Example:

```text
Expected:
veriqta-demo/1.0.0/veriqta-demo-1.0.0.zip

Requested:
veriqta-demo/1.0/veriqta-demo-1.0.0.zip
```

Those are different paths.

---

# 80. Troubleshooting: Uploaded to the Wrong Folder

Suppose you intended:

```text
veriqta-demo/1.0.0/veriqta-demo-1.0.0.zip
```

but uploaded:

```text
veriqta-demo/veriqta-demo-1.0.0.zip
```

Do not upload another copy immediately without understanding the state.

You can:

1. Confirm the current artifact.
2. Confirm the desired destination.
3. Move it if appropriate.
4. Verify the destination.
5. Verify the old location is gone.
6. Check whether anything already references the old path.

For a brand-new lab artifact, this is simple.

For production, moving an artifact can affect consumers.

---

# 81. Troubleshooting: Wrong Version Downloaded

Problem:

You expected:

```text
1.0.0
```

but downloaded:

```text
1.1.0
```

Investigate:

```text
Which repository?
↓
Which path?
↓
Which filename?
↓
Which checksum?
```

Do not trust the filename alone if the integrity of the deployment matters.

Verify the expected version and checksum.

---

# 82. Troubleshooting: Artifact Appears Twice

Possible causes:

* You copied it
* It exists in multiple paths
* It exists in multiple repositories
* Different versions have similar names
* You are viewing both package and artifact representations
* A remote cache contains a resolved copy

Before deleting a "duplicate," determine:

```text
Repository
Path
Version
Checksum
Purpose
```

Two artifacts with the same filename are not necessarily redundant.

---

# 83. Troubleshooting: Copy Fails

Possible causes:

* No read permission on source
* No deploy permission on destination
* Wrong destination
* Repository restrictions
* Package-type incompatibility
* Artifact does not exist
* Path conflict
* Service problem

Investigate:

```text
Can I read source?
↓
Does source exist?
↓
Does destination exist?
↓
Can I write destination?
↓
Is this copy operation valid?
```

---

# 84. Troubleshooting: Move Fails

Remember that a move logically combines:

```text
Create at destination
+
Remove from source
```

Permissions and repository constraints matter.

Check:

* Source path
* Destination path
* Source permissions
* Destination permissions
* Repository compatibility
* Existing destination artifact
* Error response

Do not delete the source manually just because the move failed.

You could lose the artifact.

---

# 85. Troubleshooting: Delete Is Not Allowed

This is often a good thing.

You may have:

```text
Read permission
Deploy permission
```

but not:

```text
Delete permission
```

Least privilege means users should receive only the permissions needed for their role.

A developer who can upload a development artifact does not automatically need the power to delete production releases.

# 86. Troubleshooting Model for Artifact Operations

Use this process:

```text
Observe
↓
Identify operation
↓
Identify repository
↓
Identify exact path
↓
Identify artifact/version
↓
Check authentication
↓
Check permissions
↓
Read returned error
↓

↓

↓

↓

↓

```

For example:

```text

```

This is troubleshooting.

Randomly clicking buttons is not.

# 100. Repository Organization and Automation

Why did we choose:

```text
veriqta-demo/1.0.0/veriqta-demo-1.0.0.zip
```

instead of:

```text
folder23/demo.zip
```

Because predictable structure enables automation.

A pipeline can construct a path from variables.

Conceptually:

```text
APPLICATION=veriqta-demo
VERSION=1.0.0
```

Then:

```text
$APPLICATION/$VERSION/$APPLICATION-$VERSION.zip
```

becomes:

```text
veriqta-demo/1.0.0/veriqta-demo-1.0.0.zip
```

Humans can understand it.

Automation can construct it.

That is good repository design.

# 101. Security: Do Not Hardcode Credentials

Although this lab used the web UI, later uploads and downloads will happen through:

* JFrog CLI
* REST APIs
* Package managers
* CI/CD pipelines

Do not write:

```text
username=admin
password=my-secret-password
```

inside scripts committed to Git.

Use appropriate:

* Access tokens
* Secret stores
* CI/CD secret variables
* Environment variables where appropriate
* Short-lived credentials where supported
* Least-privilege service identities

Credential management becomes increasingly important when artifact operations become automated.

---

# 102. Security: Verify Before Deploying

A basic secure delivery mindset is:

```text
Retrieve
↓
Verify identity/version
↓
Verify integrity
↓
Apply security/release controls
↓
Deploy
```

not:

```text
Download random latest file
↓
Run in production
```

Artifact repositories give you infrastructure for controlled software distribution, but good processes still matter.

---

# 103. Security: Restrict Delete Permission

Deletion can cause serious operational problems.

Consider separate capabilities:

```text
Read
Deploy
Manage
Delete
Administer
```

A user may need:

```text
Read + Deploy
```

without needing:

```text
Delete everything
```

Apply least privilege.

---

# 104. Security: Do Not Trust a Filename

A file named:

```text
payment-api-5.0.0.zip
```

does not prove it contains the correct software.

The filename is a label.

Use additional evidence:

```text
Repository
Path
Version
Checksum
Build information
Provenance/signature where applicable
Security scan status
```

Production trust should never depend only on a filename.

# 106. Knowledge Check Answers

### Answer 1

Because `veriqta-demo` is an artifact we produced ourselves. Local repositories are used for artifacts directly published into our Artifactory environment.

### Answer 2

The repository is the artifact-management boundary. The artifact path identifies where the artifact exists inside that repository.

### Answer 3

The filesystem path identifies a location on your computer. The repository path identifies a logical location inside Artifactory.

### Answer 4

A structured path makes versions easier to browse, retrieve, automate, manage, and clean up.

### Answer 5

Metadata is information describing the artifact, such as its name, path, size, checksums, properties, and other associated information.

### Answer 6

A checksum is a value calculated from file content that can be used as a content fingerprint.

### Answer 7

It helps verify that the content you have matches the content represented by the expected SHA-256 value.

### Answer 8

No. Hashing and encryption solve different problems.

### Answer 9

No. Integrity verification is not the same as cryptographic publisher authentication.

### Answer 10

A key-value metadata attribute associated with an artifact or path in Artifactory.

### Answer 11

No. The property changes repository metadata rather than the binary's contents.

### Answer 12

Artifact information describes a particular stored file. Package information represents ecosystem-aware information about a package and its versions or associated artifacts.

### Answer 13

Repositories can contain huge numbers of artifacts. Search lets engineers find artifacts using known information without manually browsing every path.

### Answer 14

Copy keeps the source and creates a destination copy. Move changes the location so the original source location no longer contains that artifact.

### Answer 15

Other systems may depend on the artifact for deployment, rollback, rebuilding, auditing, or disaster recovery.

### Answer 16

The same version identifier would refer to different binary contents at different times, weakening reproducibility and traceability.

### Answer 17

Because `1.0.0` identifies a fixed intended version, while `latest` can point to different content over time.

### Answer 18

Stop, verify the path, filename, version, expected checksum, and downloaded content. Do not deploy until the mismatch is understood.

### Answer 19

The deleted version may be the exact previous stable artifact required to restore production.

### Answer 20

Verify the resulting repository state, including the repository, path, version, artifact, and relevant metadata or checksum.
