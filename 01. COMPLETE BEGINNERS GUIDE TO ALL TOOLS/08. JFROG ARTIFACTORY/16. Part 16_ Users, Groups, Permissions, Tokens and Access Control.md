# Part 16: Users, Groups, Permissions, Tokens and Access Control

In Part 15, you built a controlled release lifecycle:

```text
Build Once
↓
DEV
↓
TEST
↓
STAGING
↓
PRODUCTION
```

You also learned that different systems should have different responsibilities.

For example:

```text
Developer
↓
Creates source code

CI Pipeline
↓
Builds and publishes candidates

Release Automation
↓
Promotes approved artifacts

Production
↓
Retrieves approved releases
```

That immediately creates a security question:

```text
Should all of them have the same Artifactory permissions?
```

No.

A developer who only needs to download dependencies should not automatically be able to delete production artifacts.

A CI pipeline that publishes development builds should not automatically have administrator access.

A Kubernetes cluster that only needs to pull container images should not need permission to upload them.

This is the foundation of access control.

Our security architecture becomes:

```text
Identity
↓
Authentication
↓
Authorization
↓
Permissions
↓
Repository Action
↓
Audit
```

Examples:

```text
Developer
↓
Authenticates
↓
READ dependencies
↓
Artifactory
```

```text
CI Pipeline
↓
Authenticates with token
↓
READ dependencies
+
DEPLOY build artifacts
↓
Development Repository
```

```text
Production Runtime
↓
Authenticates
↓
READ approved artifacts
↓
Release Repository
```

The goal of this part is not simply to learn where the Users or Permissions screen is.

You need to understand how to design access safely.

---

# 1. The Fundamental Security Question

Whenever something accesses Artifactory, ask four questions:

```text
WHO are you?

HOW did you prove it?

WHAT are you allowed to do?

WHERE are you allowed to do it?
```

For example:

```text
WHO:
CI pipeline

HOW:
Access token

WHAT:
Read + deploy

WHERE:
veriqta-dev-local
```

Compare that with:

```text
WHO:
Production Kubernetes workload

HOW:
Registry credential/token

WHAT:
Read only

WHERE:
veriqta-docker-release
```

These identities should not automatically share credentials.

---

# 2. Authentication vs Authorization

These two terms are fundamental.

## Authentication

Authentication answers:

```text
Who are you?
```

Examples:

```text
Username + password
Access token
Identity provider login
API credential
```

Authentication establishes identity.

## Authorization

Authorization answers:

```text
What are you allowed to do?
```

Examples:

```text
Read repository A
Deploy to repository B
Delete from repository C
Manage project D
```

Authorization happens after identity is known.

Think:

```text
Authentication
↓
Identity established
↓
Authorization
↓
Permission evaluated
↓
Allow or deny
```

---

# 3. Simple Authentication Example

Suppose Ann logs into the JFrog Platform.

Authentication determines:

```text
Is this really the account claiming to be Ann?
```

If authentication succeeds, JFrog now has an identity.

But that does not mean:

```text
Ann can do everything.
```

Authorization still determines whether that identity can perform a requested action.

---

# 4. Simple Authorization Example

Suppose the authenticated user requests:

```text
DELETE
veriqta-release-local/veriqta-api/4.2.0/
```

JFrog evaluates whether that identity has sufficient permission.

Possible result:

```text
Authenticated:
YES

Authorized to delete:
NO
```

The request should be denied.

This is an important distinction.

You can be:

```text
Successfully authenticated
```

and still receive:

```text
403 Forbidden
```

because you are not authorized for the requested operation.

---

# 5. Authentication Failure vs Authorization Failure

A useful beginner mental model:

```text
401
↓
Who are you?
Authentication problem

403
↓
I know who you are,
but you cannot do this.
Authorization problem
```

This is not a universal diagnostic rule for every proxy, application, or configuration, but it is an extremely useful starting point.

Do not respond to every access failure by generating a new token.

First determine which security layer failed.

---

# 6. Identity Types

Artifactory may be accessed by different kinds of actors.

Human identities:

```text
Developer
Platform Engineer
SRE
Release Engineer
Security Engineer
Administrator
Auditor
```

Machine identities:

```text
Jenkins
GitHub Actions
GitLab CI
Build agents
Deployment pipelines
Kubernetes
Automation scripts
Terraform
Monitoring systems
```

The important distinction:

```text
Human
≠
Automation
```

Do not design all access around personal user accounts.

---

# 7. Users

A user represents an individual identity within the access-control system.

Example:

```text
User:
ann

Groups:
developers
platform-engineering
```

The user may receive permissions:

```text
Directly
```

or indirectly through:

```text
Groups
Projects
Permission assignments
```

For larger environments, group-based access is generally easier to manage than assigning everything individually.

---

# 8. Why Individual Permissions Become Difficult

Imagine:

```text
100 developers
```

Each needs access to:

```text
veriqta-maven
veriqta-npm
veriqta-pypi
veriqta-docker
```

You could configure every user separately.

But when someone joins:

```text
Configure four permissions.
```

When someone changes team:

```text
Modify several permissions.
```

When someone leaves:

```text
Find every permission assignment.
```

This becomes difficult to maintain.

Groups solve much of this problem.

---

# 9. Groups

A group represents a collection of users who share a role or access requirement.

Examples:

```text
developers
qa-engineers
release-engineers
platform-engineers
security-team
artifact-admins
```

Then:

```text
User
↓
Group
↓
Permission
↓
Repository
```

Example:

```text
ann
↓
developers
↓
Read
↓
veriqta-maven
```

---

# 10. Group-Based Access

Suppose:

```text
developers
```

can:

```text
READ:
veriqta-maven
veriqta-npm
veriqta-pypi
```

When a new developer joins:

```text
Add user
↓
Add to developers group
↓
Access inherited
```

You do not need to rebuild every repository permission manually.

---

# 11. Role-Based Thinking

Before creating groups, think about responsibilities.

Example:

```text
Developers
↓
Consume dependencies
Publish development artifacts

Release Engineers
↓
Promote approved releases

Production Runtime
↓
Read production artifacts

Security
↓
Inspect artifacts and metadata

Administrators
↓
Manage platform
```

Then map those responsibilities to permissions.

Do not start with:

```text
Who should get admin?
```

Start with:

```text
What exact tasks must each role perform?
```

---

# 12. Projects and Access Boundaries

JFrog Projects provide another organizational boundary.

Conceptually:

```text
JFrog Platform
├── Project A
│   ├── Repositories
│   ├── Builds
│   └── Users/roles/resources
│
└── Project B
    ├── Repositories
    ├── Builds
    └── Users/roles/resources
```

Projects can help organizations separate teams, applications, business units, or environments.

---

# 13. Why Projects Matter

Suppose one JFrog Platform serves:

```text
Payments Team
Analytics Team
Infrastructure Team
```

Without clear boundaries, everything can become one giant collection of:

```text
Repositories
Users
Builds
Permissions
Tokens
```

Projects can help establish ownership and boundaries.

Conceptually:

```text
Payments Project
↓
Payments resources

Analytics Project
↓
Analytics resources
```

---

# 14. Project Boundary Is Not a Substitute for Permission Design

Do not assume:

```text
We created projects
↓
Security solved.
```

You still need to determine:

```text
Who belongs to the project?

What roles do they have?

Which repositories belong there?

What actions can they perform?

Which automation identities need access?
```

Projects organize security boundaries.

Permissions still enforce allowed actions.

---

# 15. Permissions

A permission describes what an identity may do against a resource.

Conceptually:

```text
Identity
+
Resource
+
Action
=
Permission decision
```

For example:

```text
developers
+
veriqta-maven
+
read
=
allowed
```

But:

```text
developers
+
veriqta-release-local
+
delete
=
denied
```

---

# 16. Permission Targets

In Artifactory, permission targets are used to define access to selected repositories and paths for selected users and groups.

Think:

```text
Permission Target
├── Which repositories?
├── Which users?
├── Which groups?
└── Which actions?
```

Example conceptual permission:

```text
Name:
dev-artifact-access

Repositories:
veriqta-dev-local

Group:
developers

Permissions:
read
deploy
```

Another:

```text
Name:
production-read

Repositories:
veriqta-release-local

Group:
developers

Permissions:
read
```

Now developers can consume releases without being allowed to overwrite them.

---

# 17. Repository-Level Access

Repository permissions answer questions such as:

```text
Can this identity read this repository?

Can it publish?

Can it overwrite?

Can it delete?

Can it manage repository content?
```

Different repositories can have different security boundaries.

Example:

```text
veriqta-dev-local
↓
CI can write

veriqta-release-local
↓
CI cannot write directly

Release automation
↓
Can promote into release
```

This reinforces the lifecycle from Part 15.

---

# 18. Read Permission

Read access generally allows an identity to retrieve or inspect permitted artifact content.

Examples:

```text
pip install
npm install
mvn dependency resolution
docker pull
helm pull
JFrog CLI download
```

Conceptually:

```text
Consumer
↓
READ
↓
Repository
```

A runtime system often needs only this.

---

# 19. Read-Only Production Consumers

Suppose Kubernetes needs:

```text
veriqta-api:4.2.0
```

from Artifactory.

Kubernetes needs:

```text
Pull image
```

It does not need:

```text
Push image
Delete image
Create repository
Change users
Modify permissions
```

Therefore:

```text
Kubernetes credential
↓
READ
↓
Production container repository
```

is much safer than:

```text
Kubernetes credential
↓
Administrator
```

---

# 20. Deploy/Write Permission

Build systems need to publish artifacts.

Conceptually:

```text
CI
↓
Build
↓
Artifact
↓
DEPLOY/WRITE
↓
Development Repository
```

Example:

```text
Jenkins
↓
veriqta-maven-snapshot-local
```

or:

```text
GitHub Actions
↓
veriqta-docker-dev-local
```

The build identity needs sufficient permission to publish.

It does not automatically need permission to delete or administer the repository.

---

# 21. Write Access Should Be Scoped

Bad:

```text
CI Pipeline
↓
Write every repository
```

Better:

```text
Frontend CI
↓
Write frontend development repositories

Backend CI
↓
Write backend development repositories
```

Even better where operationally practical:

```text
Specific pipeline identity
↓
Specific required repositories
↓
Specific required actions
```

This reduces blast radius.

---

# 22. Delete Permission

Delete is significantly more dangerous.

Consider:

```text
DELETE
veriqta-release-local/veriqta-api/4.1.3
```

That release might be:

```text
Current rollback target
```

Deleting it could damage recovery capability.

Therefore delete permission should be much more restricted than read access.

---

# 23. Why Delete Is Operationally Sensitive

Deletion can affect:

```text
Rollback
Autoscaling
New Kubernetes Pods
Historical builds
Audit
Incident investigation
Dependency resolution
Disaster recovery
```

Remember Part 15:

```text
Artifact retention
=
Reliability concern
```

Therefore:

```text
Who can delete?
```

is a serious production question.

---

# 24. Manage/Admin Permissions

Administrative capabilities can include powerful operations involving:

```text
Repositories
Users
Groups
Permissions
Security configuration
Platform settings
```

These privileges should be restricted.

Do not think:

```text
Engineer needs Artifactory
↓
Give administrator.
```

Instead:

```text
What exact operation is required?
```

Then grant the smallest permission set that enables it.

---

# 25. Least Privilege

Least privilege means:

> Give an identity only the access required to perform its legitimate function.

Example:

```text
Developer
↓
Read dependencies
Publish development artifacts
```

does not imply:

```text
Delete production releases.
```

Similarly:

```text
Deployment pipeline
↓
Read production releases
```

does not imply:

```text
Manage users.
```

---

# 26. Least Privilege Is About Blast Radius

Suppose a CI credential is stolen.

Credential A:

```text
Administrator
```

Potential impact:

```text
Every repository
Every artifact
Security configuration
Potentially broad platform control
```

Credential B:

```text
Read:
dependencies

Write:
veriqta-dev-local
```

Potential impact is much smaller.

This is blast-radius reduction.

---

# 27. Security Architecture

A mature architecture could look like:

```text
Developers
↓
Read dependencies
↓
Publish DEV artifacts

CI
↓
Read dependencies
↓
Write DEV

Test Automation
↓
Read DEV

Release Automation
↓
Read validated candidates
↓
Promote approved releases

Production
↓
Read RELEASE

Administrators
↓
Platform management
```

Each identity has a purpose.

---

# 28. Separation of Duties

Separation of duties means important operations are not unnecessarily concentrated in one identity.

Bad:

```text
CI
├── Build
├── Test
├── Approve itself
├── Modify production repository
├── Delete old releases
├── Change permissions
└── Administer Artifactory
```

A compromise of that pipeline becomes extremely powerful.

Better:

```text
CI
↓
Build + publish candidate

Release Process
↓
Validate + approve

Release Automation
↓
Promote

Production
↓
Read approved release
```

---

# 29. Developers vs Deployment Automation

Developers may need:

```text
Read dependencies
Publish development builds
Inspect artifacts
```

Deployment automation may need:

```text
Read approved release artifacts
Deploy them to runtime environments
```

These are different roles.

Do not automatically share:

```text
Username
Password
Token
```

between them.

---

# 30. Human Credentials vs Machine Credentials

A developer authenticates as:

```text
Human identity
```

Automation should authenticate as:

```text
Machine/service identity
```

Bad:

```text
Jenkins
↓
Ann's personal token
```

Why?

If Ann:

```text
Changes team
Leaves company
Loses access
Rotates token
```

the pipeline may fail.

It also makes auditing confusing.

---

# 31. Service Accounts

A service account is a non-human identity used by automation or a service.

Examples:

```text
ci-veriqta-api
release-veriqta-api
k8s-prod-puller
artifact-cleanup
```

Each name communicates purpose.

A service identity should have:

```text
Clear owner
Clear purpose
Limited permissions
Credential lifecycle
Rotation process
Auditability
```

---

# 32. Good Service Identity Design

Instead of:

```text
automation
```

consider:

```text
ci-payment-api
```

Instead of:

```text
service-user
```

consider:

```text
release-payment-api
```

Names should help operators understand:

```text
What is this identity for?
```

---

# 33. One Giant Automation Account

Bad architecture:

```text
jfrog-automation
↓
Used by:
Jenkins
GitHub Actions
Kubernetes
Terraform
Cleanup jobs
Release pipeline
Developers
```

If that credential leaks:

```text
Everything is exposed.
```

It is also difficult to determine which system performed an action.

---

# 34. Better Automation Separation

```text
ci-backend
↓
Build permissions

release-backend
↓
Promotion permissions

k8s-prod
↓
Read-only production image access

cleanup-service
↓
Controlled cleanup permissions
```

Now:

```text
Credential compromise
↓
Smaller blast radius
```

and:

```text
Audit log
↓
More meaningful identity
```

---

# 35. Access Tokens

An access token is a credential used to authenticate requests.

Instead of repeatedly providing:

```text
Username + password
```

automation can use:

```text
Access token
```

Tokens are particularly useful for:

```text
CLI
REST API
CI/CD
Automation
Package clients
```

depending on the supported integration.

---

# 36. Token Is Still a Secret

Do not think:

```text
Token
=
Safe to publish
```

A token can authorize actions.

Therefore:

```text
Token
=
Secret
```

Treat it like sensitive authentication material.

Do not:

```text
Commit it to Git
Paste it into README
Print it into CI logs
Put it into screenshots
Send it through public chat
Hardcode it into Dockerfiles
```

---

# 37. Token Scope

A token should be limited to the access required by its use case.

Conceptually:

```text
Token
↓
Identity
↓
Allowed scope
↓
Required repository operations
```

Avoid:

```text
Token
↓
Everything
```

when the workload only needs:

```text
Read one repository.
```

---

# 38. Token Expiration

Tokens should generally have an intentional lifetime.

Example:

```text
Created
↓
Valid
↓
Expires
↓
No longer accepted
```

Expiration limits how long a stolen credential can remain useful.

But expiration also creates an operational responsibility:

```text
Who rotates it?

How is the new credential distributed?

Will the pipeline fail when it expires?
```

---

# 39. Very Long-Lived Tokens

Long-lived credentials reduce rotation frequency but increase risk.

If a token is stolen and remains valid for years:

```text
Attacker has a long opportunity window.
```

Security design balances:

```text
Operational reliability
+
Credential lifetime
+
Automated rotation
+
Risk
```

Do not simply choose the longest expiration because it is convenient.

---

# 40. Very Short-Lived Tokens

Very short-lived credentials can improve security but require suitable automation.

If a token expires every hour while your system has no automatic renewal mechanism:

```text
Pipeline failures
```

may become common.

The goal is not:

```text
Shortest possible token
```

The goal is:

```text
Appropriate credential lifetime
+
Reliable lifecycle management.
```

---

# 41. Token Lifecycle

Think about credentials as lifecycle-managed objects:

```text
Create
↓
Store securely
↓
Use
↓
Monitor
↓
Rotate
↓
Revoke
↓
Audit
```

Do not stop at:

```text
Create token.
```

---

# 42. Revocation

Suppose a token appears in:

```text
Public Git repository
CI log
Screenshot
Support ticket
Chat message
```

Treat the token as potentially compromised.

Do not merely:

```text
Delete the visible text.
```

The credential may already have been copied.

Safer response:

```text
Revoke token
↓
Issue replacement
↓
Update secret store
↓
Check logs
↓
Investigate usage
```

---

# 43. Token Rotation

Rotation means replacing an existing credential with a new one.

Conceptually:

```text
Token A
↓
Create Token B
↓
Update consumer
↓
Verify Token B
↓
Revoke Token A
```

This overlap can reduce downtime where the platform and security policy permit it.

---

# 44. Rotation Should Be Tested

Do not discover on expiration day that nobody knows:

```text
Where the credential is stored.
```

Document:

```text
Owner
Location
Consumers
Expiration
Rotation procedure
Verification procedure
Emergency revocation procedure
```

---

# 45. API Authentication

Artifactory is frequently accessed through APIs.

Conceptually:

```text
Automation
↓
HTTP Request
↓
Authentication Credential
↓
JFrog Platform
↓
Authorization Check
↓
Response
```

An access token is commonly sent through an HTTP authorization mechanism.

For example, an API request may conceptually use:

```text
Authorization: Bearer <TOKEN>
```

The exact endpoint and supported authentication method should always match the JFrog service and API you are calling.

---

# 46. Safe curl Pattern

Avoid:

```bash
curl -H "Authorization: Bearer MY_REAL_SECRET_TOKEN" ...
```

in reusable scripts.

A better conceptual pattern:

```bash
export JFROG_TOKEN="..."
```

then:

```bash
curl \
  -H "Authorization: Bearer ${JFROG_TOKEN}" \
  "https://YOUR-JFROG-HOST/artifactory/api/system/ping"
```

What happens:

```text
curl
↓
Sends HTTP request

-H
↓
Adds HTTP header

Authorization: Bearer
↓
Provides authentication credential
```

But be careful.

Environment variables are convenient, not magical secret vaults.

Use your CI/CD platform's secret-management capabilities for real automation.

---

# 47. Never Print the Token to Verify It

Bad:

```bash
echo "$JFROG_TOKEN"
```

That may expose the credential in:

```text
Terminal history
Screen recording
CI logs
Support output
```

Instead check whether it exists:

```bash
if [ -n "${JFROG_TOKEN:-}" ]; then
  echo "JFROG_TOKEN is set"
else
  echo "JFROG_TOKEN is not set"
fi
```

This verifies presence without displaying the value.

# 48. JFrog CLI Authentication

From earlier parts, you learned that JFrog CLI can use configured server identities.

Conceptually:

```text
JFrog CLI
↓
Server Configuration
├── URL
└── Authentication
↓
JFrog Platform
```

You might configure:

```bash
jf config add
```

and follow the interactive configuration.

Then inspect configured server entries:

```bash
jf config show
```

The goal is to avoid manually placing credentials in every command.

---

# 49. Server IDs

A JFrog CLI server ID is a local configuration name.

Example:

```text
veriqta-lab
```

It is not necessarily:

```text
JFrog username
repository name
project name
```

It is a convenient identifier for a configured JFrog Platform connection.

Then commands can reference:

```bash
--server-id=veriqta-lab
```

where supported.

---

# 50. Test CLI Authentication

A useful connectivity/authentication test is:

```bash
jf rt ping --server-id=veriqta-lab
```

Conceptually:

```text
CLI
↓
Uses veriqta-lab configuration
↓
Contacts Artifactory
↓
Verifies reachability
```

If it fails, do not immediately assume:

```text
Token is wrong.
```

Possible causes include:

```text
Wrong URL
DNS
TLS
Proxy
Network
Expired token
Invalid token
Server configuration
```

Investigate systematically.

---

# 51. CLI Configuration on Shared Machines

Be careful when configuring credentials on:

```text
Shared build agent
Shared server
Shared developer workstation
```

Ask:

```text
Who can access the CLI configuration?

Who owns the process?

Can another user read credentials?

Should this machine retain long-lived credentials?
```

Local configuration security matters.

---

# 52. CI/CD Credentials

A CI pipeline might need to:

```text
Download dependencies
Upload build artifacts
Publish Build Info
Retrieve deployment artifacts
Promote releases
```

But those operations do not necessarily belong to the same credential.

For example:

```text
Build Pipeline Token
↓
Read dependencies
Write DEV

Release Pipeline Token
↓
Read candidate
Promote release

Deployment Token
↓
Read RELEASE
```

---

# 53. Do Not Hardcode CI Credentials

Bad:

```yaml
env:
  JFROG_TOKEN: "eyJ..."
```

if that pipeline file is committed to source control.

The token becomes part of:

```text
Git history
Pull requests
Repository clones
Backups
```

Instead use:

```text
CI Secret Store
↓
Secret injected at runtime
↓
Pipeline process
```

# 54. GitHub Actions Concept

Conceptually:

```text
GitHub Actions Secret
↓
Workflow
↓
JFrog CLI/API
↓
Artifactory
```

The workflow references the secret without placing the actual credential in the repository.

The same principle applies to:

```text

```

# 55. Jenkins Concept

A Jenkins architecture might look like:

```text
Jenkins Credentials Store
↓
Pipeline
↓
Temporary credential exposure to required step
↓
JFrog
```

```text
Jenkinsfile
↓
Hardcoded password/token
```

because Jenkinsfiles are commonly stored in Git.

# 56. Secrets Management

Secrets management means controlling sensitive values such as:

```text
Tokens
Passwords
Private keys
API credentials
Certificates
```

A good secrets system helps with:

```text
Secure storage
Controlled retrieval
Access policy
Rotation
Auditability
```

---

# 57. Secret Storage Hierarchy

Bad:

```text
README
```

Better:

```text
Environment variable
```

Better for production:

```text
CI secret store
Dedicated secret-management system
Workload identity or short-lived credential mechanism where supported
```

The exact design depends on the platform.

---

# 58. Environment Variables Are Not Secret Management by Themselves

This is important.

Developers often think:

```text
I moved the password into an environment variable.
↓
Security solved.
```

No.

Environment variables solve:

```text
Hardcoding problem
```

partially.

They do not automatically solve:

```text
Secure storage
Access control
Rotation
Audit
Process exposure
Logging mistakes
```

They are one delivery mechanism.

---

# 59. Secrets in Shell History

Suppose you type:

```bash
export JFROG_TOKEN="real-secret-value"
```

Depending on shell configuration, that command can remain in shell history.

Safer workflows use secure secret injection rather than manually typing long-lived production credentials.

For temporary labs, understand the risk and clean up appropriately.

---

# 60. Secrets in Process Arguments

Be careful with:

```bash
some-command --token "$JFROG_TOKEN"
```

Some operating systems and diagnostic tools may expose process command-line arguments.

Prefer supported authentication/configuration mechanisms that avoid unnecessarily placing secrets directly in command arguments.

---

# 61. Secrets in Logs

A pipeline can accidentally do:

```bash
set -x
```

Then shell commands may be echoed.

If commands contain credentials:

```text
Secret
↓
CI Log
```

That is dangerous.

Before enabling shell tracing, understand what values can be printed.

---

# 62. Secret Masking Is Not a Complete Defense

CI platforms often mask known secret values.

Useful?

Yes.

Perfect?

No.

Secrets can still leak through:

```text
Encoding
Transformation
Partial output
Debug tools
Generated configuration
Artifacts
Third-party commands
```

Do not rely on masking as the primary security control.

---

# 63. Administrator Credentials in Pipelines

One of the most important rules in this part:

```text
DO NOT USE ARTIFACTORY ADMINISTRATOR CREDENTIALS
IN NORMAL CI/CD PIPELINES.
```

A build pipeline usually needs something like:

```text
Read dependencies
Write build output
Publish metadata
```

It does not need:

```text
Create administrators
Modify permissions
Delete every repository
Change global platform configuration
```

---

# 64. Why Admin Credentials Are Dangerous

CI systems execute:

```text
Build scripts
Third-party actions/plugins
Package-manager scripts
Repository-controlled code
```

If the pipeline contains administrator credentials, malicious or compromised code may attempt to steal them.

Then:

```text
Compromised Build
↓
Admin Credential
↓
Broad Artifactory Compromise
```

Least privilege limits this risk.


If everything is dumped into:

A predictable structure such as:

```text

├── analytics/
└── platform/
```

can make access boundaries easier to reason about.

Repository design and security design are connected.


# 81. Credential Rotation Strategy

A simple rotation workflow:

```text
Identify credential
↓
Create replacement
↓
Update secret store
↓
Restart/reload consumer if required
↓
Test authentication
↓
Test authorization
↓
Revoke old credential
↓
Audit
```

Do not revoke first unless emergency compromise requires immediate revocation.

Otherwise you may create avoidable downtime.

```text
↓

↓
Issue replacement
↓
Update consumers
↓

↓

↓
```

Security may take priority over availability during confirmed compromise.

# 87. Failed Authentication Monitoring

Repeated authentication failures may mean:

```text

Wrong secret

Old credential after rotation
Attack attempt
```

Context matters.

---

# 88. Common Access Failure: 401

Problem:

```text
401 Unauthorized
```

What beginner sees:

```text
Request rejected.
```

Possible causes:

```text
Missing credential
Invalid token
Expired token
Wrong authentication method
Wrong server configuration
```

Investigation:

```text
Is credential present?

Is it expired?

Is the request using the correct server?

Did rotation recently occur?

Does CLI configuration point to the correct instance?
```

Fix the authentication problem.

Do not grant administrator permissions.

---

# 89. Common Access Failure: 403

Problem:

```text
403 Forbidden
```

What beginner sees:

```text
Login appears valid,
but action fails.
```

Possible cause:

```text
Identity authenticated
but lacks required authorization.
```

Example:

```text
CI can READ
but cannot DEPLOY.
```

Investigation:

```text
Which identity?

Which repository?

Which path?

Which operation?

Which permission target/group applies?
```

Fix the minimum missing authorization.

Do not immediately make the identity admin.

---

# 90. Common Access Failure: Read Works, Upload Fails

Symptom:

```text
Download:
SUCCESS

Upload:
403
```

Likely interpretation:

```text
Read permission:
YES

Deploy/write permission:
NO
```

This can be intentional.

If the workload should publish, add only the required publication permission.

---

# 91. Common Access Failure: Upload Works, Delete Fails

Symptom:

```text
Upload:
SUCCESS

Delete:
403
```

This may mean:

```text
Deploy permission:
YES

Delete permission:
NO
```

Again, this can be correct least-privilege behavior.

Do not treat every denied operation as broken configuration.

---

# 92. Common Access Failure: Works for Developer, Fails in CI

Developer laptop:

```text
SUCCESS
```

CI:

```text
401
```

Possible causes:

```text
Developer has personal credentials
CI secret missing
CI token expired
Secret variable name incorrect
Wrong server ID
Wrong URL
Secret not available in that pipeline context
```

Do not conclude:

```text
Artifactory is down.
```

Compare identities and environments.

# 93. Common Access Failure: CI Can Upload to DEV but Not RELEASE

```text

↓

↓
```

```text

```

when writing RELEASE.

# 95. Common Access Failure: Wrong Repository

instead of:


# 100. Access Troubleshooting Framework

Use:

```text
Request fails
↓
Identify exact identity
↓
Identify exact endpoint
↓
Identify exact repository/path
↓
Identify exact operation
↓
Authentication successful?
├── NO → investigate credential
└── YES
     ↓

├── NO → inspect permissions/groups/projects
└── YES
     ↓
Inspect repository/path/configuration
```

Do not randomly change permissions.

# 101. The Dangerous Troubleshooting Shortcut

A common beginner response:

```text
403
↓
Make user admin
↓
Works
```

This does not mean:

```text
Admin was required.
```

It means:

```text
Admin includes the missing permission.
```

You still need to identify the minimum permission required.

Then remove unnecessary privilege.

---

# 102. Permission Troubleshooting Method

Use:

```text
1. Identify failing action

2. Identify authenticated identity

3. Identify target repository

4. Identify target path

5. Identify required permission

6. Inspect direct permissions

7. Inspect group membership

8. Inspect project boundary

9. Test smallest safe change

10. Retry

11. Verify unrelated access was not accidentally granted
```

# 103. Never Troubleshoot by Granting Everything Permanently

Temporary broad access can easily become permanent.

Example:

```text

↓
Pipeline works
↓
Nobody removes it
↓
Six months later
↓
Pipeline still admin
```

Avoid this operational pattern.

# 110. Compromised Developer Scenario


```text

```

```text

↓

```

```text
Modify permissions
```

# 112. Compromised Production Credential Scenario


```text

```

the compromise becomes far more severe.

# 113. Credential Exposure Through Source Control


```text

↓
```


# 165. Final Security Architecture

Your complete security model should now look like:

```text
                         JFROG PLATFORM
                               │
                Authentication + Authorization
                               │
         ┌─────────────────────┼──────────────────────┐
         │                     │                      │
     DEVELOPERS               CI               RELEASE SYSTEM
         │                     │                      │
       READ                READ + WRITE         CONTROLLED
         │                     │                 PROMOTION
         │                     │                      │
         └──────────────┐      │      ┌───────────────┘
                        ↓      ↓      ↓
                    ARTIFACTORIES
                         │
                         │
                    RELEASE REPO
                         │
                         ↓
                 PRODUCTION RUNTIME
                         │
                      READ ONLY
```

Outside the ordinary artifact flow:

```text
Administrators
↓
Platform Management

Auditors
↓
Appropriate Read/Audit Access
```

The security logic is:

```text
IDENTITY
↓
AUTHENTICATE
↓
AUTHORIZE
↓
APPLY LEAST PRIVILEGE
↓
PERFORM ACTION
↓
AUDIT
```

And the credential lifecycle is:

```text
CREATE
↓
STORE SECURELY
↓
USE
↓
MONITOR
↓
ROTATE
↓
REVOKE
↓
AUDIT
```

The most important lesson from Part 16 is:

```text
A credential should not answer:
"What might this system ever want to do?"

It should answer:
"What does this identity actually need to do?"
```

That means:

```text
Developer
≠
CI
≠
Release Automation
≠
Production Runtime
≠
Administrator
```

Different responsibilities should have different access boundaries.

The final production principle is:

```text
AUTHENTICATE EVERY IDENTITY
↓
AUTHORIZE ONLY REQUIRED ACTIONS
↓
USE DEDICATED MACHINE IDENTITIES
↓
PROTECT TOKENS AS SECRETS
↓
ROTATE CREDENTIALS
↓
KEEP ADMIN CREDENTIALS OUT OF PIPELINES
↓
AUDIT IMPORTANT ACCESS
↓
CONTINUOUSLY REMOVE UNNECESSARY PRIVILEGE
```

This is how Artifactory changes from simply being a protected file server into a properly controlled part of the software supply chain.
