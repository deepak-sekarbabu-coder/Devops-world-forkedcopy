# 1. What Is a CLI?

Before discussing JFrog CLI, understand the general term.

CLI means:

```text
Command-Line Interface
```

A CLI lets you interact with software by typing commands into a terminal.

For example:

```bash
git status
```

uses the Git CLI.

```bash
docker ps
```

uses the Docker CLI.

```bash
kubectl get pods
```

uses the Kubernetes CLI.

Similarly:

```bash
jf rt search ...
```

uses JFrog CLI to interact with Artifactory.

Instead of:

```text
Open browser
↓
Navigate menus
↓
Click buttons
```

you can perform operations from:

```text
Terminal
↓
Command
↓
Result
```

This matters because commands can be repeated, documented, scripted, and placed into CI/CD pipelines.

---

# 2. What Is JFrog CLI?

JFrog CLI is JFrog's command-line client for interacting with JFrog products and services.

The executable is:

```text
jf
```

You will therefore see commands beginning with:

```bash
jf
```

For Artifactory operations, a common command structure is:

```bash
jf rt <command>
```

Here:

```text
jf
↓
JFrog CLI executable

rt
↓
Artifactory command group

<command>
↓
Operation to perform
```

For example:

```bash
jf rt search "veriqta-generic-local/veriqta-demo/*"
```

This asks JFrog CLI to search Artifactory.

# 8. What If `jf` Is Not Found?

You may see something similar to:

```text
command not found: jf
```

That means your shell cannot currently find a `jf` executable through its command search path.

Possible reasons include:

* JFrog CLI is not installed
* It was installed somewhere outside your `PATH`
* Installation failed
* Your terminal session has not picked up a changed environment
* You installed it under a different setup

Do not immediately assume Artifactory is broken.

The failure is currently local:

```text
Terminal
↓
Cannot locate jf
```

Artifactory has not even been contacted yet.

This distinction is important for troubleshooting.

# 10. Understanding `PATH`

When you type:

```bash
jf
```

your shell needs to locate the executable.

The `PATH` environment variable contains directories the shell searches for commands.

Display it:

```bash
echo "$PATH"
```

You may see directories separated by colons.

For example:

```text
/usr/local/bin:/usr/bin:/bin:...
```

On Apple Silicon Macs, Homebrew commonly installs commands under paths involving:

```text
/opt/homebrew/bin
```

The exact environment depends on your system.

You can ask your shell where `jf` is located:

```bash
which jf
```

or:

```bash
command -v jf
```

Possible result:

```text
/opt/homebrew/bin/jf
```

Now you know which executable runs when you type:

```bash
jf
```

# 19. Authentication

Authentication answers:

```text
Who are you?
```

Artifactory must know which identity is making a request.

Your identity may then be checked against permissions.

Remember:

```text
Authentication
↓
Who are you?

Authorization
↓
What are you allowed to do?
```

A valid credential does not mean you can upload, move, or delete every artifact.

# 20. Access Tokens

Access tokens are commonly used for machine and CLI authentication.

Conceptually:

```text
Identity
↓
Token issued
↓
CLI presents token
↓
JFrog validates token
↓
Permissions evaluated
```

A token is sensitive.

Treat it like a credential.

Do not:

* Post it online
* Put it in screenshots
* Paste it into tutorials
* Commit it to Git
* Store it in public repositories
* Send it through insecure chat channels
* Hardcode it into scripts unnecessarily

---

# 21. Why Tokens Are Better Than Hardcoded Passwords

Bad:

```bash
PASSWORD="MyRealPassword123"
```

committed inside a script.

Worse:

```text
Git repository
↓
Script
↓
Production password
```

Once committed, a secret may remain recoverable from Git history even if the visible line is later removed.

Prefer mechanisms designed for secret handling.

In CI/CD, this normally means storing the token in the platform's secret-management mechanism and exposing it to the job only when required.

# 22. Environment Variables

An environment variable is a named value available to a running shell or process.

Example:

```bash
export VERIQTA_VERSION="2.0.0"
```

Now:

```bash
echo "$VERIQTA_VERSION"
```

returns:

```text
2.0.0
```

Environment variables are useful in automation because scripts can receive changing values without rewriting the script.

For example:

```text
VERSION
REPOSITORY
SERVER_ID
BUILD_NUMBER
```

---

# 23. Environment Variables and Secrets

You might use an environment variable for a token in controlled circumstances.

Conceptually:

```bash
export JFROG_ACCESS_TOKEN="..."
```

But understand an important point:

Environment variables are not magically secure.

Secrets may still be exposed through:

* Shell history
* Debug output
* Process environments
* CI logs
* Misconfigured scripts
* Accidental `echo`
* Diagnostic tools

The safer principle is:

```text
Secret
↓
Secure secret store
↓
Injected only when needed
↓
Never printed
```

Do not confuse convenience with security.

---

# 24. Never Print Secrets During Troubleshooting

Avoid:

```bash
echo "$JFROG_ACCESS_TOKEN"
```

especially in shared terminals, screen recordings, CI/CD logs, or screenshots.

Instead, if you only need to determine whether a variable exists, use a check that does not reveal the value.

For example:

```bash
if [ -n "$JFROG_ACCESS_TOKEN" ]; then
  echo "Token variable is set"
else
  echo "Token variable is not set"
fi
```

Here:

```text
-n
↓
Tests whether the string is non-empty
```

The secret itself is never printed.

# 34. Exit Status

Command-line programs normally return an exit status to the shell.

A common convention is:

```text
0
↓
Success

Non-zero
↓
Some form of failure
```

After a command, you can inspect the most recent exit status in shells such as Bash or Zsh:

```bash
echo $?
```

For example:

```bash

```

If the first command succeeds, you will commonly see:

```text
0
```

Do not rely only on human-readable output when writing automation.

Exit status lets scripts determine whether they should continue.

# 36. What Is a Wildcard?

A wildcard represents variable text in a pattern.

The most common wildcard you will encounter is:

```text
*
```

For example:

```text
veriqta-demo/*
```

means:

```text
veriqta-demo/
↓
match content fitting the remainder of the pattern
```

Wildcards are powerful.

They are also dangerous when used with destructive commands.

---

# 37. Why Quotes Matter With Wildcards

Suppose you run:

```bash
jf rt search veriqta-generic-local/veriqta-demo/*
```

Your shell may attempt to interpret `*` before JFrog CLI receives it.

Using:

```bash
jf rt search "veriqta-generic-local/veriqta-demo/*"
```

helps ensure the pattern is passed to JFrog CLI as intended.

This is a general shell concept:

```text
Shell expansion
vs
Application pattern interpretation
```

You need to know which tool should process the wildcard.

---

# 43. The Danger of Broad Wildcards

Suppose you intend to upload:

```text
build/*.zip
```

but use an overly broad pattern:

```text
*
```

You may accidentally include:

* Logs
* Temporary files
* Secrets
* Configuration files
* Credentials
* Source files
* Unwanted build output

Before bulk operations:

```text
Understand pattern
↓
Inspect matching files
↓
Run operation
↓
Verify
```

Never assume your wildcard means what you intended.

# 44. Recursive Operations

Recursive operations work across nested directory structures.

Suppose:

```text
release/
├── app/
│   └── application.zip
├── scripts/
│   └── deploy.sh
└── configs/
    └── app.conf
```

A recursive operation may process content under several levels.

Conceptually:

```text
release/
↓
Walk through subdirectories
↓
Process matching files
```

Recursive operations are useful for directory trees.

They also increase the blast radius of mistakes.

---

# 45. What Is Blast Radius?

Blast radius means:

```text
How much could be affected if this operation is wrong?
```

Compare:

```text
Delete one explicit artifact
```

with:

```text
Recursively delete everything matching *
```

The second operation has a much larger blast radius.

Safe automation tries to reduce unnecessary blast radius.

# 50. Delete With JFrog CLI

Deletion is where wildcards become particularly dangerous.

Our safe target is only the test artifact:

```text
veriqta-generic-local/cli-move-test/veriqta-demo/2.0.0/veriqta-demo-2.0.0.zip
```

Before deleting it, search for the exact path:

```bash
jf rt search "veriqta-generic-local/cli-move-test/veriqta-demo/2.0.0/veriqta-demo-2.0.0.zip" --server-id=veriqta-lab
```

Confirm the match.

Only then perform the deletion using:

```bash
jf rt delete "veriqta-generic-local/cli-move-test/veriqta-demo/2.0.0/veriqta-demo-2.0.0.zip" --server-id=veriqta-lab
```

Depending on CLI version and settings, destructive operations may request confirmation unless configured otherwise.

Read prompts carefully.

---

# 51. Never Start With a Broad Delete

Do not learn deletion using something like:

```bash
jf rt delete "veriqta-generic-local/*"
```

That pattern could affect a large portion of the repository.

The safer workflow is:

```text
Write intended pattern
↓
SEARCH with pattern
↓
Inspect matches
↓
Narrow if necessary
↓
DELETE only after confirmation
↓
SEARCH again
↓
Verify expected state
```

This is one of the most important habits in this part.

---

# 52. Search Before Delete

Suppose you want to delete:

```text
veriqta-generic-local/temp-builds/*
```

First:

```bash
jf rt search "veriqta-generic-local/temp-builds/*" --server-id=veriqta-lab
```

Inspect every match.

Only when you are confident that the selection is correct should you consider using the same intended pattern for deletion.

This pattern is useful beyond JFrog:

```text
READ/SEARCH
BEFORE
WRITE/DELETE
```

# 60. File Specifications

Simple CLI commands work well for simple operations.

But operations eventually become more complicated.

You may need to say:

```text
Find artifacts from this repository
↓
Only under this path
↓
Match these patterns
↓
Exclude these files
↓
Attach these properties
↓
Place them in this target structure
```

Long command lines can become difficult to read and maintain.

JFrog CLI supports File Specs.

---

# 61. What Is a File Spec?

A File Spec is a JSON document describing files or artifacts that a JFrog CLI operation should process.

Instead of putting every rule directly on the command line, you define the selection and behavior in structured JSON.

Conceptually:

```text
Command line
↓
Read File Spec
↓
Understand artifact selection
↓
Perform operation
```

A File Spec can help make complex operations more structured and repeatable.

---

# 62. Why File Specs Exist

Compare a simple command:

```bash
jf rt upload "build/*.zip" "repo/releases/"
```

This is easy to understand.

Now imagine:

* Multiple patterns
* Exclusions
* Properties
* Recursive matching
* Target layouts
* Build-specific filtering

The command becomes harder to maintain.

A File Spec lets you move selection logic into a structured file.

---

# 63. JSON From Zero

Before using File Specs, understand JSON.

JSON means:

```text
JavaScript Object Notation
```

It is a text format for structured data.

A simple JSON object:

```json
{
  "application": "veriqta-demo",
  "version": "2.0.0"
}
```

The basic pattern is:

```text
"key": "value"
```

Example:

```json
"application": "veriqta-demo"
```

Key:

```text
application
```

Value:

```text
veriqta-demo
```

JSON syntax matters.

---

# 64. JSON Syntax Basics

JSON uses:

```text
{ }
↓
Objects
```

```text
[ ]
↓
Arrays
```

```text
:
↓
Separates key from value
```

```text
,
↓
Separates entries
```

Strings use double quotes:

```json

```

Incorrect JSON can cause the File Spec operation to fail before Artifactory is even queried.

# 69. File Spec Safety

A File Spec can match many artifacts.

That means it can also make a large mistake consistently.

Before running destructive File Specs:

* Review the pattern
* Review repository names
* Review exclusions
* Review recursive behavior
* Review destination
* Test against a safe repository
* Search first where possible

Automation does not make an unsafe operation safe.

It makes it repeatable.

If the operation is wrong, automation can repeat the mistake faster.

# 70. Scripting With JFrog CLI

Now we can begin combining commands.

Suppose you repeatedly:

1. Build an artifact
2. Calculate its checksum
3. Upload it
4. Search to verify it exists

A script can automate that workflow.

Create:

```text
publish.sh
```

Example:

```bash
#!/usr/bin/env bash

set -e

VERSION="2.2.0"
ARTIFACT="veriqta-demo-${VERSION}.zip"
REPOSITORY="veriqta-generic-local"
SERVER_ID="veriqta-lab"

echo "Publishing ${ARTIFACT}"

shasum -a 256 "$ARTIFACT"

jf rt upload \
  "$ARTIFACT" \
  "${REPOSITORY}/veriqta-demo/${VERSION}/" \
  --server-id="$SERVER_ID"

jf rt search \
  "${REPOSITORY}/veriqta-demo/${VERSION}/${ARTIFACT}" \
  --server-id="$SERVER_ID"

echo "Artifact publication workflow completed."
```

Do not run this blindly.

Understand every line first.

---

# 71. Understanding the Shebang

The first line:

```bash
#!/usr/bin/env bash
```

is commonly called a shebang.

It tells the operating system which interpreter should execute the script.

Here:

```text
env
↓
Locate Bash in the environment
```

Then:

```text
bash
↓
Execute script using Bash
```

This is common in portable shell scripts.

---

# 72. Understanding `set -e`

The line:

```bash
set -e
```

tells Bash to exit in many situations where a command returns a non-zero status.

The intention is:

```text
Command fails
↓
Do not blindly continue through the rest of the deployment workflow
```

This is useful, but beginners should know that shell error handling has nuances.

`set -e` is not a complete error-handling strategy for every script.

For our beginner example, it introduces the principle:

```text
Failure
↓
Stop instead of pretending everything succeeded
```

---

# 73. Variables in the Script

We define:

```bash
VERSION="2.2.0"
```

Then:

```bash
ARTIFACT="veriqta-demo-${VERSION}.zip"
```

`${VERSION}` is expanded.

Therefore:

```text
veriqta-demo-${VERSION}.zip
```

becomes:

```text
veriqta-demo-2.2.0.zip
```

This allows the version to be changed in one place.

---

# 74. Why Variables Matter

Without variables:

```bash
jf rt upload "veriqta-demo-2.2.0.zip" "veriqta-generic-local/veriqta-demo/2.2.0/"
```

Then another line:

```bash
jf rt search "veriqta-generic-local/veriqta-demo/2.2.0/veriqta-demo-2.2.0.zip"
```

The version appears repeatedly.

If someone updates one occurrence but forgets another, the script becomes inconsistent.

Variables reduce that risk.

---

# 75. Quote Your Variables

Prefer:

```bash
"$ARTIFACT"
```

instead of:

```bash
$ARTIFACT
```

Quoting protects values from unwanted word splitting and certain shell expansions.

This matters when values unexpectedly contain spaces or special characters.

Safe shell scripting requires understanding the shell, not just JFrog CLI.

---

# 76. A Better Script: Check That the Artifact Exists

Before upload:

```bash
if [ ! -f "$ARTIFACT" ]; then
  echo "ERROR: Artifact not found: $ARTIFACT"
  exit 1
fi
```

Break it down.

```text
-f
↓
Tests whether the path is a regular file
```

```text
!
↓
Negates the test
```

Therefore:

```text
if file does NOT exist
↓
Print error
↓
Exit
```

This prevents the script from continuing with an invalid local source.

---

# 77. Safer Publishing Script

A stronger beginner version:

```bash
#!/usr/bin/env bash

set -e

VERSION="${VERSION:-2.2.0}"
ARTIFACT="veriqta-demo-${VERSION}.zip"
REPOSITORY="veriqta-generic-local"
SERVER_ID="veriqta-lab"
TARGET="${REPOSITORY}/veriqta-demo/${VERSION}/"

if [ ! -f "$ARTIFACT" ]; then
  echo "ERROR: Artifact not found: $ARTIFACT"
  exit 1
fi

echo "Artifact: $ARTIFACT"
echo "Target: $TARGET"

echo "Calculating SHA-256..."
shasum -a 256 "$ARTIFACT"

echo "Uploading artifact..."
jf rt upload \
  "$ARTIFACT" \
  "$TARGET" \
  --server-id="$SERVER_ID"

echo "Verifying artifact..."
jf rt search \
  "${TARGET}${ARTIFACT}" \
  --server-id="$SERVER_ID"

echo "Completed successfully."
```

This script still belongs in a lab before being treated as production automation.

---

# 78. `${VERSION:-2.2.0}` Explained

This expression:

```bash
VERSION="${VERSION:-2.2.0}"
```

means roughly:

```text
If VERSION already has a usable value
↓
Use it

Otherwise
↓
Use 2.2.0
```

You can therefore run:

```bash
VERSION="2.3.0" ./publish.sh
```

and the script can use:

```text
2.3.0
```

instead of its default.

This is one example of making scripts reusable.

---

# 79. Make the Script Executable

A new shell script may not have execute permission.

Inspect:

```bash
ls -l publish.sh
```

You may need:

```bash
chmod +x publish.sh
```

`chmod` changes file permissions.

`+x` adds execute permission.

Then:

```bash
./publish.sh
```

The `./` means:

```text
Run publish.sh from the current directory
```

Do not use `chmod 777` simply because a script does not execute.

Grant only the permissions required.

# 80. Safe Automation Practices

Before automating artifact operations, follow several principles.

## Use explicit repository names

Good:

```text
veriqta-generic-local
```

Risky:

```text
Whatever repository happens to be default
```

## Use explicit versions

Good:

```text
2.2.0
```

Riskier for controlled releases:

```text

```

## Verify source files

Do not upload a filename that you merely assume exists.

## Search before destructive operations

Especially before:

```text
delete
move
```

## Avoid broad wildcards

Especially in production.

## Never hardcode secrets

Use approved secret-management mechanisms.

## Check command failures

Automation must not silently continue after critical failures.

## Verify after writes

Upload:

```text
Upload
↓
Search/inspect
↓
Confirm
```

Move:

```text
Move
↓
Check source
↓
Check destination
```

Delete:

```text
Delete
↓
Confirm target gone
↓
Confirm unrelated artifacts remain
```

# 107. Troubleshooting Decision Tree

When a JFrog CLI command fails, use:

```text
Did `jf` run?
│
├── NO
│   ↓
│   Installation / PATH
│
└── YES
    ↓
Does server configuration exist?
│
├── NO
│   ↓
│   Configure server
│
└── YES
    ↓
Can Artifactory be reached?
│
├── NO
│   ↓
│   URL / DNS / network / TLS / service
│
└── YES
    ↓
Did authentication succeed?
│
├── NO
│   ↓
│   Credentials / token
│
└── YES
    ↓
Is operation authorized?
│
├── NO
│   ↓
│   Permissions
│
└── YES
    ↓
Does source exist?
│
├── NO
│   ↓
│   Local path / repository path
│
└── YES
    ↓
Does pattern match what you intended?
│
├── NO
│   ↓
│   Pattern / wildcard / recursion
│
└── YES
    ↓
Inspect operation-specific error
```

This is much better than changing five things simultaneously.

# 108. Do Not Troubleshoot by Random Modification

Bad troubleshooting:

```text
Upload failed
↓
Change token
↓
Change repository
↓
Change URL
↓
Reinstall CLI
↓
Change permissions
↓
Try again
```

Now you do not know what fixed or broke the system.

Better:

```text
Observe exact error
↓
Identify layer
↓
Test one hypothesis
↓
Collect evidence
↓
Make one relevant change
↓
Verify
```

This reasoning applies far beyond Artifactory.
