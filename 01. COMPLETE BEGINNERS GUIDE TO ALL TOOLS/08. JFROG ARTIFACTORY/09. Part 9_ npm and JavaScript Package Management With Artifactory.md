# Part 9: npm and JavaScript Package Management With Artifactory

In Part 8, you learned how Maven and Gradle interact with Artifactory.

The central pattern was:

```text
Dependencies
↓
Artifactory
↓
Build Tool
↓
Application Build
↓
Artifact
↓
Artifactory
```

Now we will apply the same idea to JavaScript.

Instead of:

```text
Java
↓
Maven / Gradle
↓
JAR
```

we will work with:

```text
JavaScript Project
↓
npm
↓
npm Packages
```

Artifactory can sit between developers or CI systems and both private and public npm packages:

```text
JavaScript Project
↓
npm
↓
Artifactory
├── Private Packages
└── Cached Public Packages
```

By the end of this part, you should understand how npm packages are identified, installed, cached, published, versioned, secured, and troubleshot through Artifactory.

---

# 1. Start From Zero: What Is JavaScript?

JavaScript is a programming language used extensively for web applications, backend services, command-line tools, automation, build systems, and many other applications.

A very small JavaScript program could contain:

```javascript
console.log("Hello from VERIQTA");
```

Save it as:

```text
app.js
```

If Node.js is installed, you can run:

```bash
node app.js
```

Expected output:

```text
Hello from VERIQTA
```

But real applications rarely contain only code written by one developer.

They depend on other software.

For example, a Node.js backend application might need:

* Express for HTTP server functionality
* Axios for HTTP requests
* Lodash for utility functions
* Jest for testing
* ESLint for code analysis

Instead of manually downloading these libraries, JavaScript developers commonly use a package manager.

One of the most important is npm.

---

# 2. What Is Node.js?

Before understanding npm, distinguish Node.js from npm.

Node.js is a JavaScript runtime.

It allows JavaScript to execute outside the browser.

Conceptually:

```text
JavaScript Source
↓
Node.js Runtime
↓
Application Executes
```

Check whether Node.js is installed:

```bash
node --version
```

or:

```bash
node -v
```

Example:

```text
v22.x.x
```

Your exact version may differ.

The important point is that:

```text
Node.js
≠
npm
```

They are related, but they solve different problems.

---

# 3. What Is npm?

npm is commonly used as the package manager for the Node.js and JavaScript ecosystem.

It also refers to the broader npm ecosystem and public registry.

As a command-line package manager, npm can:

* Initialize projects
* Install dependencies
* Remove dependencies
* Update dependencies
* Run scripts
* Manage package metadata
* Publish packages
* Interact with package registries

Conceptually:

```text
JavaScript Project
↓
npm
├── Install dependencies
├── Track dependencies
├── Run scripts
├── Package modules
└── Publish packages
```

Check npm:

```bash
npm --version
```

or:

```bash
npm -v
```

---

# 4. Node.js vs npm vs Artifactory

Keep these roles separate.

## Node.js

Executes JavaScript.

## npm

Manages JavaScript packages and project dependencies.

## Artifactory

Stores, proxies, caches, and distributes packages.

The relationship is:

```text
Developer
↓
JavaScript Project
↓
npm
↓
Artifactory
↓
Packages
```

For application execution:

```text
JavaScript
↓
Node.js
↓
Running Application
```

# 5. What Is a Package?

A package is a distributable unit of software and associated metadata.

An npm package commonly contains:

```text
Package
├── JavaScript files
├── package.json
├── README
├── license information
└── Other required resources
```

Packages can be:

```text
Public
```

or:

```text
Private
```

Public packages may be available from the public npm registry.

Private packages may be stored in an organization's Artifactory environment.

---

# 6. Package vs Dependency

These words are related but not identical.

A package is a distributable software unit.

A dependency is a package that another project requires.

For example:

```text
express
```

is a package.

If your application requires Express:

```text
Your Application
↓
Depends on
↓
Express
```

then Express is a dependency of your application.

# 7. What Is a Package Manager?

A package manager helps automate package operations.

Instead of:

```text
Open website
↓
Find ZIP
↓
Download ZIP
↓
Extract ZIP
↓
Copy files
↓
Hope dependencies exist
```

you can use:

```bash
npm install express
```

npm determines what needs to be retrieved and installs the dependency according to the project's configuration.

---

# 8. What Is a Package Registry?

A package manager and package registry are not the same thing.

## Package manager

Example:

```text
npm
```

Runs on your machine or CI environment and performs package operations.

## Package registry

Stores and serves package information and package content.

Conceptually:

```text
npm
↓
Package Registry
↓
Package
```

Artifactory can provide npm registry endpoints.

So:

```text
npm
↓
Artifactory npm Repository
```

is a package-manager-to-registry relationship.

---

# 9. What Is the Public npm Registry?

The npm ecosystem has a public registry containing a large number of publicly available JavaScript packages.

Without Artifactory, a project might resolve packages like this:

```text
Developer
↓
npm
↓
Public npm Registry
```

With Artifactory:

```text
Developer
↓
npm
↓
Artifactory
↓
Public npm Registry
```

Artifactory becomes an intermediary between your build environment and the public package source.

---

# 10. Why Put Artifactory Between npm and the Public Registry?

There are several reasons:

* Centralized dependency access
* Dependency caching
* Reduced repeated upstream retrieval
* Repository governance
* Better visibility
* Consistent developer and CI configuration
* Private and public packages through a controlled repository layer
* Reduced direct dependency on public registry availability for already cached content

Instead of:

```text
Developer 1 → Public Registry
Developer 2 → Public Registry
CI Runner 1 → Public Registry
CI Runner 2 → Public Registry
```

you can use:

```text
Developers
+
CI Runners
↓
Artifactory
↓
Approved Upstream Registry
```

This is similar to the Maven architecture you learned in Part 8.

# 16. What Did npm install Actually Do?

When you ran:

```bash

```

Conceptually:

```text

↓

↓

↓

↓

↓

↓

↓
Update package.json
↓

```

Several important things just happened.

# 18. Direct and Transitive Dependencies

Suppose:

```text
Your Application
↓
Package A
```

Package A depends on:

```text
Package B
Package C
```

Then:

```text
Your Application
├── Package A
│   ├── Package B
│   └── Package C
```

Package A is a direct dependency.

Packages B and C are transitive dependencies from the perspective of your application.

This is the same fundamental dependency concept you encountered with Maven.

# 20. What Is package-lock.json?

After installing dependencies, npm normally creates:

```text
package-lock.json
```

This file records the resolved dependency tree in detail.

A beginner might ask:

"If package.json already lists dependencies, why do I need package-lock.json?"

Because they serve different purposes.

---

# 21. package.json vs package-lock.json

Think of:

```text
package.json
```

as describing the project's dependency requirements and metadata.

Think of:

```text
package-lock.json
```

as recording the concrete resolved dependency graph used by npm.

For example, `package.json` might allow a compatible range:

```json
"express": "^5.1.0"
```

The lockfile records specific resolved package information.

Conceptually:

```text
package.json
↓
What versions are acceptable?

package-lock.json
↓
What dependency graph was actually resolved?
```

---

# 22. Why the Lockfile Matters

Suppose two developers install the same project at different times.

Without a lockfile, compatible version ranges could potentially resolve differently as new package versions appear.

That can lead to:

```text
Developer A
↓
Dependency version X

Developer B
↓
Dependency version Y
```

A lockfile improves deterministic dependency installation by recording exact resolution information.

This is especially important for:

* Teams
* CI/CD
* Reproducible builds
* Troubleshooting
* Dependency auditing

---

# 23. Should package-lock.json Be Committed to Git?

For applications, it is commonly appropriate to commit `package-lock.json` so the project retains its resolved dependency information.

A normal application repository might therefore contain:

```text
veriqta-app/
├── index.js
├── package.json
├── package-lock.json
└── .gitignore
```

while excluding:

```text
node_modules/
```

from Git.

---

# 24. Why node_modules Usually Does Not Belong in Git

`node_modules` can be:

* Large
* Generated
* Reconstructed from dependency metadata
* Environment-sensitive in some situations
* Full of third-party files

Instead of committing it:

```text
Git
↓
package.json
+
package-lock.json
```

then:

```text
npm
↓
Install dependencies
↓
node_modules
```

This is much cleaner.

A `.gitignore` commonly contains:

```text
node_modules/
```

---

# 25. npm install vs npm ci

This distinction is important for DevOps engineers.

## npm install

Commonly used during normal development and dependency changes.

It can update dependency resolution and the lockfile when appropriate.

## npm ci

Designed for clean, reproducible installation based on the lockfile.

A CI pipeline often uses:

```bash
npm ci
```

rather than:

```bash
npm install
```

for an application with a valid lockfile.

---

# 26. What npm ci Does

Conceptually:

```text
package.json
+
package-lock.json
↓
npm ci
↓
Clean dependency installation
↓
Exact lockfile-driven dependency tree
```

It expects the package metadata and lockfile to be consistent.

If they disagree, `npm ci` can fail instead of silently changing the lockfile.

That behavior is useful in CI because unexpected dependency drift should not be hidden.

# 31. Local npm Repository

An Artifactory local npm repository stores packages published directly into your Artifactory environment.

Example:

```text
veriqta-npm-local
```

It could contain:

```text
@veriqta/logger
@veriqta/config
@veriqta/api-client
```

These packages may never be published publicly.

They can remain private to your organization.

---

# 32. Remote npm Repository

An Artifactory remote npm repository proxies an upstream npm registry.

Conceptually:

```text
npm Client
↓
Artifactory Remote Repository
↓
Public npm Registry
```

When a package is requested, Artifactory can retrieve and cache it according to repository behavior.

---

# 33. Virtual npm Repository

A virtual repository combines multiple repositories behind one logical endpoint.

For example:

```text
                    npm
                     ↓
              veriqta-npm
              Virtual Repo
               /        \
              /          \
             ↓            ↓
veriqta-npm-local      npm-remote
Private Packages           ↓
                     Public Registry
```

Now developers can use:

```text
veriqta-npm
```

rather than configuring separate endpoints for private and public packages.

---

# 34. Why the Virtual Repository Is Useful

Suppose your project requires:

```text
@veriqta/logger
express
```

`@veriqta/logger` is private.

`express` is public.

Without a unified repository architecture, npm configuration can become more complicated.

With Artifactory:

```text
npm
↓
veriqta-npm
├── @veriqta/logger
│   ↓
│   Local Repository
│
└── express
    ↓
    Remote Repository
    ↓
    Public Registry
```

From the developer's perspective, both are dependencies.

Artifactory determines where they are resolved.

---

# 35. Dependency Caching

Suppose the first developer requests a public package.

Flow:

```text
Developer 1
↓
npm
↓
Artifactory Virtual
↓
Remote Repository
↓
Not Cached
↓
Public Registry
↓
Package Download
↓
Artifactory Cache
↓
Developer
```

Later:

```text
Developer 2
↓
npm
↓
Artifactory
↓
Cached Package
↓
Developer
```

This is the same remote-caching principle you learned with Maven.

---

# 36. Cached Does Not Mean Every Package Works Offline

Suppose:

```text
express
```

was previously cached.

Another package:

```text
some-new-package
```

was never requested.

If upstream access disappears:

```text
express
↓
Potentially available from cache
```

but:

```text
some-new-package
↓
May fail because Artifactory never retrieved it
```

Artifactory cannot serve content it does not possess.

# 41. Understanding npm Authentication

Private repositories generally require authentication.

The conceptual flow is:

```text
npm
↓
Request
+
Credentials / Token
↓
Artifactory
↓
Authenticate Identity
↓
Check Permissions
↓
Allow or Deny
```

Authentication answers:

```text
Who are you?
```

Authorization answers:

```text
What are you allowed to do?
```

Keep those concepts separate.

---

# 42. Do Not Hardcode Real Tokens

A dangerous `.npmrc` might expose a reusable credential directly.

Do not commit real authentication tokens to Git.

A safer conceptual approach uses secret injection.

For example, an environment variable might be supplied by the shell or CI system:

```bash
export JFROG_TOKEN="your-token"
```

and referenced by appropriate npm configuration.

The exact authentication syntax should follow the configuration generated or documented for your JFrog environment.

The security principle is more important than memorizing one token format:

```text
Secret
↓
Secure secret source
↓
Runtime configuration
↓
npm
```

not:

```text
Secret
↓
Git repository
```

---

# 43. Check Whether an Environment Variable Exists Safely

Do not run:

```bash
echo "$JFROG_TOKEN"
```

in shared CI logs.

Instead:

```bash
test -n "$JFROG_TOKEN" && echo "JFROG_TOKEN is set"
```

This confirms presence without displaying the secret.

You can also use:

```bash
echo "${JFROG_TOKEN:+JFROG_TOKEN is set}"
```

The goal is:

```text
Verify secret injection
≠
Print secret
```

# 50. What Is an npm Scope?

A package can be scoped.

For example:

```text
@veriqta/logger
```

The structure is:

```text
@scope/package
```

Here:

```text
@veriqta
↓
Scope
```

and:

```text
logger
↓
Package name
```

Scopes are useful for organizing packages under a namespace.

Examples:

```text
@veriqta/logger
@veriqta/config
@veriqta/api-client
@veriqta/observability
```

---

# 51. Why Scoped Packages Are Useful

Imagine several organizations create packages called:

```text
logger
```

Without scopes:

```text
logger
logger
logger
```

Names collide.

With scopes:

```text
@veriqta/logger
@company-a/logger
@company-b/logger
```

The namespace makes ownership and organization clearer.

Scopes can also be used with scope-specific registry configuration.

# 59. Version Ranges

npm dependencies often use version ranges.

Examples include:

```text
1.2.3
^1.2.3
~1.2.3
```

These do not all mean the same thing.

---

# 60. Exact Version

```text
1.2.3
```

means:

```text
Use version 1.2.3
```

This is the narrowest of these examples.

---

# 61. Caret Range

```text
^1.2.3
```

generally allows compatible updates without changing the leftmost non-zero component.

For a stable `1.x` package, this commonly means versions:

```text
>=1.2.3
<2.0.0
```

But zero-major versions require more careful interpretation.

Do not simplify `^` to "always any minor version" because that is not universally accurate.

---

# 62. Tilde Range

```text
~1.2.3
```

generally allows patch-level updates within the specified minor line:

```text
>=1.2.3
<1.3.0
```

This is narrower than:

```text
^1.2.3
```

for a normal `1.x` package.

---

# 63. Why Version Ranges Matter

Suppose:

```json
"dependencies": {
  "@veriqta/logger": "^1.0.0"
}
```

The project may accept a compatible `1.x` version according to npm's semver rules.

But the lockfile records the concrete resolution used.

This brings us back to:

```text
package.json
↓
Allowed dependency requirement

package-lock.json
↓
Concrete resolved dependency graph
```

# 105. Never Commit npm Tokens

```text

↓

↓
Prevent recurrence
```

# 117. Common Beginner Mistakes

Avoid these mistakes:

1. Thinking Node.js and npm are the same thing.
2. Thinking npm is the public registry itself.
3. Confusing a package manager with a package repository.
4. Not understanding `package.json`.
5. Ignoring `package-lock.json`.
6. Deleting the lockfile whenever installation fails.
7. Committing `node_modules` to Git without a specific reason.
8. Not understanding direct and transitive dependencies.
9. Assuming one installed dependency means one downloaded package.
10. Configuring npm to bypass Artifactory unintentionally.
11. Publishing private packages to the wrong registry.
12. Hardcoding tokens in `.npmrc`.
13. Committing real tokens to Git.
14. Giving CI administrator permissions.
15. Confusing authentication with authorization.
16. Treating every 404 as proof that Artifactory is down.
17. Ignoring the requested package version.
18. Misspelling package scopes.
19. Confusing npm's client cache with Artifactory's remote cache.
20. Assuming Artifactory has every public package cached.
21. Treating version ranges as exact versions.
22. Ignoring lockfile changes in pull requests.
23. Using `npm install` blindly in reproducible CI workflows.
24. Assuming a successful local build proves CI is configured correctly.
25. Publishing the same release version with different content.
26. Copying private package source between projects instead of using versioned packages.
27. Ignoring package lifecycle scripts and supply-chain risk.
28. Running `npm publish` without verifying the target registry.
29. Using public registries directly when organizational policy requires Artifactory.
30. Blaming application code for repository connectivity failures.
31. Deleting every cache before gathering evidence.
32. Ignoring verbose npm output.
33. Printing tokens into CI logs while troubleshooting.
34. Treating `package.json`, `package-lock.json`, and `node_modules` as interchangeable.
35. Failing to verify packages in Artifactory after publishing.
