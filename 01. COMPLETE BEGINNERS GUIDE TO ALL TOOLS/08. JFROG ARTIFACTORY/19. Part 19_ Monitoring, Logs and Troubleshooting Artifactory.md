# Part 19: Monitoring, Logs and Troubleshooting Artifactory

In Part 18, you moved from being an Artifactory user to thinking like an Artifactory operator.

You learned to care about:

* Storage
* Database health
* Backups
* Restore
* Cleanup
* Retention
* High availability
* Capacity
* Upgrades
* Operational runbooks

Now we move to one of the most important production skills:

# Troubleshooting

When Artifactory fails, beginners often do this:

```text
Something failed
↓
Retry
↓
Retry again
↓
Restart something
↓
Change random configuration
↓
Retry
```

Sometimes the problem disappears.

But you still do not know:

* What failed
* Why it failed
* Whether it will happen again
* Whether your change actually fixed it
* Whether you created another problem

Production engineers need a different model:

```text
SYMPTOM
↓
LOGS + STATE
↓
EVIDENCE
↓
HYPOTHESIS
↓
DIAGNOSTIC TEST
↓
ROOT CAUSE
↓
FIX
↓
VERIFY
↓
PREVENT
```

This is the troubleshooting model for Part 19.

---

# 1. Troubleshooting Is Not Guessing

Suppose a Jenkins pipeline reports:

```text
ERROR: Failed to upload artifact
```

A beginner may immediately think:

```text
Artifactory is down.
```

But many completely different failures can produce an upload problem.

For example:

```text
Wrong repository
Expired token
Insufficient permission
Disk full
Database problem
TLS failure
DNS failure
Network timeout
Proxy problem
Wrong URL
Artifact path error
Repository configuration problem
```

Therefore:

```text
SYMPTOM
≠
ROOT CAUSE
```

The symptom is merely what you observed.

---

# 2. Symptoms vs Root Causes

Imagine:

```text
Docker pull failed.
```

That is a symptom.

Possible root causes:

```text
Image does not exist
Wrong tag
Wrong repository
Token expired
User lacks permission
DNS failure
TLS certificate problem
Artifactory unavailable
Remote Docker registry unavailable
Remote cache miss
Proxy failure
Network timeout
```

You must narrow possibilities using evidence.

# 3. The VERIQTA Troubleshooting Model

Use this throughout the chapter:

```text
SYMPTOM
↓
LOGS + STATE
↓
EVIDENCE
↓
HYPOTHESIS
↓
DIAGNOSTIC TEST
↓
ROOT CAUSE
↓
FIX
↓
VERIFY
↓

```

Let's understand every step.

---

# 4. Step 1: Symptom

Describe exactly what happened.

Bad:

```text
Artifactory doesn't work.
```

Better:

```text
Jenkins cannot upload
payment-api-4.2.1.jar
to libs-release-local.
```

Even better:

```text
Jenkins receives HTTP 403 while uploading
payment-api-4.2.1.jar to libs-release-local.

Manual downloads from the same Artifactory instance still succeed.
```

Specific symptoms reduce the search space.

---

# 5. Step 2: Logs + State

Collect evidence.

Examples:

```text
Artifactory logs
Client output
HTTP status code
JFrog CLI output
CI logs
Docker output
Package-manager output
Disk usage
Database health
Network state
DNS results
TLS information
```

Do not change the system yet.

First understand its current state.

---

# 6. Step 3: Evidence

Evidence is something observable.

Example:

```text
jf rt ping
↓
OK
```

That tells us something important:

```text
The configured client can reach Artifactory.
```

Another example:

```text
Upload
↓
403
```

Now we know:

```text
The request reached an HTTP service
and was explicitly rejected.
```

That is very different from:

```text
Connection timed out.
```

---

# 7. Step 4: Hypothesis

A hypothesis is a possible explanation.

Example:

```text
Evidence:
Upload returns 403.

Hypothesis:
CI service account lacks deploy permission.
```

Now test it.

Do not immediately grant administrator permissions.

---

# 8. Step 5: Diagnostic Test

Test the smallest thing that proves or disproves your hypothesis.

For example:

```text
Check permission target
```

or attempt a controlled upload using the same CI identity.

If the identity has:

```text
Read
```

but not:

```text
Deploy/Write
```

the hypothesis becomes much stronger.

---

# 9. Step 6: Root Cause

Root cause answers:

```text
Why did the failure occur?
```

Example:

```text
CI service account was moved to a new group.

The new group had read permission
but not deploy permission
for libs-release-local.
```

That is better than:

```text
403 happened.
```

---

# 10. Step 7: Fix

Fix the actual cause.

Example:

```text
Grant the CI deployment group the required
deploy permission on the correct repository.
```

Do not:

```text
Give the CI account administrator access.
```

That may hide the symptom while violating least privilege.

---

# 11. Step 8: Verify

Repeat the original operation.

```text
CI
↓
Upload
↓
Success
```

Then confirm the artifact actually exists.

A configuration change is not proof of resolution.

---

# 12. Step 9: Prevent

Ask:

```text
How do we stop this happening again?
```

Possibilities:

```text
Permission testing
Monitoring
Alerting
Configuration review
Token-expiration monitoring
Capacity alerts
CI validation
Documentation
Runbooks
```

Troubleshooting should improve the system.

```text
Can I reach Artifactory at all?
```

Then:

```text
Can Artifactory respond?
```

Then:



```text

```

# 15. Artifactory Logs

Logs are one of your most important sources of evidence.

Current JFrog Platform documentation places active service logs under:

```text
$JFROG_HOME/<product>/var/log
```

For Artifactory this commonly means a location such as:

```text
$JFROG_HOME/artifactory/var/log/
```

JFrog service logs follow service-oriented names such as:

```text
artifactory-service.log
artifactory-request.log
router-request.log
```

The exact files available depend on platform version, services, configuration, and deployment model.

Do not memorize one filename and assume every problem belongs there.

---

# 16. Application / Service Logs

A key Artifactory log is:

```text
artifactory-service.log
```

Think of this as a major application-level diagnostic source.

It can contain information related to:

```text
Startup
Shutdown
Errors
Exceptions
Repository operations
Database problems
Internal service failures
Configuration issues
```

When the platform itself appears unhealthy, this is often one of the first logs to inspect.

---

# 17. Request Logs

Another critical source is:

```text
artifactory-request.log
```

This records incoming requests handled by Artifactory.

Current JFrog documentation describes fields including information such as:

```text
Timestamp
Trace ID
Remote address
Username
HTTP method
Request URL
Return status
Request size
Response size
Request duration
User agent
```

This makes request logs extremely useful.

---

# 18. Why Request Logs Matter

Suppose a user reports:

```text
Downloading an artifact fails.
```

You can search for the request.

You might discover:

```text
GET
/libs-release-local/payment/4.2.0/payment.jar
403
```

Now you know:

```text
Request reached Artifactory
↓
Artifactory processed request
↓
Returned 403
```

This moves you away from:

```text
Maybe DNS?
Maybe firewall?
Maybe Artifactory is offline?
```

toward authorization investigation.

---

# 19. Trace IDs

Modern distributed systems often attach identifiers to requests.

JFrog logs include trace IDs that can help correlate activity across logs.

Conceptually:

```text
Client Request
↓
Trace ID: ABC123
↓
Router Log
↓
Artifactory Request Log
↓
Service Log
```

Instead of searching thousands of unrelated entries, you can follow the same request.

This is a powerful troubleshooting technique.

---

# 20. Outbound Request Logs

Remote repositories introduce another direction.

Remember Part 17:

```text
Developer / CI
↓
Artifactory
↓
Remote Repository
↓
External Registry
```

Artifactory itself may make outbound requests.

Current JFrog troubleshooting guidance identifies:

```text
artifactory-request-out.log
```

as an important source for inspecting outbound requests from Artifactory.

This becomes especially useful for:

```text
Maven Central
npm registry
PyPI
Docker Hub
Other upstream repositories
```

---

# 21. Incoming vs Outgoing Requests

Think:

```text
CLIENT
↓
artifactory-request.log
↓
ARTIFACTORY
↓
artifactory-request-out.log
↓
UPSTREAM
```

This distinction is extremely useful.

Suppose:

```text
npm install
↓
fails
```

Incoming request may succeed into Artifactory.

But outbound request to the public registry may fail.

Without checking both directions, you might blame the client.

They can help answer questions such as:

```text

```

These logs can be useful for:


# 23. Access and Security Logs

Authentication and security-related activity may involve JFrog Access service logs.

These become useful when investigating:



# 24. Reading Logs Safely

A common Linux/macOS tool is:

```bash
tail
```

Example:

```bash
tail -n 100 artifactory-service.log
```

What does this mean?

`tail`

Displays the end of a file.

`-n 100`

Displays the last 100 lines.

This is useful because recent errors are often near the end.

---

# 25. Follow a Log Live

You may use:

```bash
tail -f artifactory-service.log
```

`-f` means:

```text
follow
```

The terminal waits and prints new lines as they are written.

This can be useful during a controlled reproduction:

```text
Terminal 1
↓
tail -f log

Terminal 2
↓
Perform failing request
```

Now you can observe what happens.

Press:

```text
Ctrl+C
```

to stop following the log.

---

# 26. Search Logs

Suppose you know the error occurred around:

```text
403
```

You might use:

```bash
grep '403' artifactory-request.log
```

`grep` searches text.

But be careful.

A production log may contain millions of entries.

Searching only:

```text
403
```

may produce too much noise.

Better identifiers include:

```text
Username
Repository
Artifact path
Trace ID
Timestamp
```

---

# 27. Example

```bash
grep 'payment-api-4.2.1.jar' artifactory-request.log
```

Now you are searching for the exact artifact involved.

You could then extract its trace ID and inspect related entries.

---

# 28. Logs Can Contain Sensitive Information

Do not casually:

```text
Copy entire production logs
↓
Paste into public forum
```

Logs may contain:

```text
Usernames
Internal URLs
Repository names
Package names
IP addresses
Tokens or headers in some circumstances
Internal architecture information
```

Sanitize logs before sharing them externally.

# 29. Service Health

Before investigating one artifact, determine whether Artifactory itself is healthy.

A simple test is:

```bash
jf rt ping
```

With a configured JFrog CLI server, successful output is typically:

```text
OK
```

Current JFrog CLI documentation continues to support `jf rt ping` for checking Artifactory connectivity.

---

# 30. Using a Specific Server Configuration

If you have multiple JFrog CLI configurations:

```bash
jf config show
```

Then:

```bash
jf rt ping --server-id=veriqta-lab
```

This explicitly chooses:

```text
veriqta-lab
```

rather than accidentally testing another server.

---

# 31. What Ping Proves

If:

```bash
jf rt ping
```

returns:

```text
OK
```

you have useful evidence that the configured Artifactory endpoint is reachable.

But it does not prove:

```text
Every repository works
Every user has permission
Every remote upstream works
Every Docker image exists
Storage has sufficient capacity
```

A health test answers a specific question.

Do not overinterpret it.

---

# 32. REST API Health Check

Artifactory exposes a system ping endpoint.

Conceptually:

```text
/artifactory/api/system/ping
```

A successful response is:

```text
OK
```

You may test it using curl against the correct Artifactory URL for your environment.

For example:

```bash
curl -i https://artifactory.example.com/artifactory/api/system/ping
```

`curl`

Makes an HTTP request.

`-i`

Includes HTTP response headers.

The hostname above is only an example.

---

# 33. Using JFrog CLI With Artifactory REST APIs

JFrog CLI provides:

```bash
jf rt curl
```

For example:

```bash
jf rt curl -s /api/system/ping
```

Here:

`jf`

Runs JFrog CLI.

`rt`

Targets Artifactory functionality.

`curl`

Runs an Artifactory REST request using the configured JFrog server.

`-s`

Suppresses curl's progress meter.

Expected body:

```text
OK
```

---

# 34. Important JFrog CLI Scripting Detail

Current JFrog documentation notes an important behavior:

```text
jf rt curl
```

can return shell exit code:

```text
0
```

even when the HTTP response itself is:

```text
401
403
5xx
```

Therefore a CI script should not assume:

```text
exit code 0
=
HTTP success
```

When automating REST checks, inspect the HTTP response/status as well.

This is a perfect example of why operators must understand tool behavior instead of blindly scripting commands.

---

# 35. Readiness vs Liveness

Production platforms often distinguish:

```text
Liveness
```

from:

```text
Readiness.
```

Conceptually:

### Liveness

```text
Is this service alive?
```

### Readiness

```text
Is this service ready to receive traffic?
```

A process can technically be running while still not being ready to serve production requests correctly.

JFrog provides health-check mechanisms intended for load balancers and orchestration systems.

# 36. System Health

Application health is only one layer.

Check:

```text
CPU
Memory
Disk
Filesystem
Network
Database
Processes
```

On Linux:

```bash
uptime
```

can show system uptime and load averages.

---

# 37. Memory

A common Linux command:

```bash
free -h
```

`free`

Shows memory information.

`-h`

Displays human-readable units.

Example:

```text
              total   used   free
Mem:            32G    25G     2G
```

Do not immediately conclude:

```text
Only 2 GB free means memory problem.
```

Linux uses memory for caching.

Interpret memory using the complete system context.

---

# 38. Disk Space

A critical command:

```bash
df -h
```

`df`

Reports filesystem disk-space usage.

`-h`

Uses human-readable units.

Example:

```text
Filesystem      Size  Used Avail Use%
/dev/xvda1       50G   49G    1G  98%
```

Now you have strong evidence of a capacity problem.

---

# 39. Inodes

Sometimes:

```text
df -h
```

shows free space, but writes still fail.

On filesystems where inode exhaustion is relevant, check:

```bash
df -i
```

A filesystem can have byte capacity remaining but lack available inodes for additional filesystem objects.

Whether this matters depends on your storage architecture.

```text
DATABASE
+
FILESTORE
```

Storage troubleshooting should ask:

```text
Is storage mounted?

Is it full?

Is latency high?

Is object storage reachable?
```

# 41. Storage Failure Example

Symptom:

```text
Downloads work.

Uploads fail.
```

Interesting.

Possible explanation:

```text

↓
New writes failing
```

Now investigate:

```text

Storage capacity
Storage availability
Database writes
Repository permissions
```

# 43. Database Troubleshooting Questions

Ask:

```text

```

# 44. Never Jump Straight to the Database

Suppose:

```text
One developer receives 403.
```

The database is probably not your first investigation target.

Why?

Because:

```text
403
```

already suggests the request reached the HTTP application and was rejected based on access rules.

Start with the evidence closest to the symptom.

---

# 45. Network Connectivity

Network failures often produce different symptoms from HTTP authorization failures.

Examples:

```text
Connection timed out
Connection refused
Connection reset
No route to host
```

These are not the same.

---

# 46. Connection Timeout

A timeout often means:

```text
Client attempted connection
↓
No useful response before timeout
```

Possible causes:

```text
Firewall silently dropping traffic
Wrong IP
Wrong port
Service unreachable
Routing issue
Network path failure
```

---

# 47. Connection Refused

This often means:

```text
Client reached destination
↓
Connection actively rejected
```

Possible causes:

```text
No service listening
Wrong port
Service stopped
Firewall rejection
```

---

# 48. Connection Reset

This means a connection existed but was abruptly terminated.

Possible sources:

```text
Server
Load balancer
Firewall
Proxy
Network device
```

Again:

```text
timeout
≠
refused
≠
reset
```

The error wording is evidence.

# 49. DNS

Before blaming Artifactory, verify the hostname.

On macOS/Linux:

```bash
nslookup artifactory.example.com
```

or:

```bash
dig artifactory.example.com
```

These query DNS.

You are asking:

```text
What IP address does this hostname resolve to?
```

---

# 50. DNS Failure Example

CI reports:

```text
Could not resolve host:
artifactory.example.com
```

The failure happened before the request could reach Artifactory.

Troubleshooting path:

```text
CI Runner
↓

↓
Resolver
↓
Hostname
```

# 51. Compare Environments

Suppose:


Differences may include:


Do not conclude:


# 52. TLS and Certificate Problems

HTTPS introduces TLS.

Common failures include:

```text
Expired certificate
Hostname mismatch
Untrusted certificate authority
Incomplete certificate chain
Wrong protocol
TLS interception
Proxy certificate problem
```

A client might report:

```text
certificate verify failed
```

or:

```text
unable to get local issuer certificate
```

or:

```text
certificate has expired
```

Read the actual message.

---

# 53. Test HTTPS Verbosely

A useful diagnostic command:

```bash
curl -v https://artifactory.example.com/
```

`-v`

means verbose.

It can show information about:

```text
DNS
Connection
TLS handshake
HTTP request
HTTP response
```

This makes `curl -v` extremely useful for network/TLS troubleshooting.

---

# 54. Do Not Normalize `-k`

You may see:

```bash
curl -k https://...
```

`-k` disables normal TLS certificate verification.

It can occasionally be used as a controlled diagnostic comparison, but it should not become the permanent solution.

If:

```text
curl fails normally
```

but:

```text
curl -k succeeds
```

you have evidence pointing toward certificate trust or validation.

The correct production fix is normally to repair certificate trust/configuration.

Not to disable security.

---

# 55. Authentication vs Authorization

Remember Part 16.

Authentication:

```text
Who are you?
```

Authorization:

```text
What are you allowed to do?
```

This distinction is essential during troubleshooting.

---

# 56. HTTP 401

Generally:

```text
401 Unauthorized
```

usually points toward authentication.

Examples:

```text
Missing credentials
Invalid token
Expired token
Malformed token
Wrong username/password
Identity problem
```

Ask:

```text
Are credentials being sent?

Are they valid?

Did token expire?

Did CI secret change?

Is this the correct Artifactory server?
```

---

# 57. HTTP 403

Generally:

```text
403 Forbidden
```

means the request is understood, but access is not permitted.

Think:

```text
Authenticated
↓
Not authorized
```

Possible causes:

```text
Missing read permission
Missing deploy/write permission
Repository restriction
Project boundary
Permission target
Remote-cache permission issue
```

---

# 58. Do Not Fix 403 With Administrator Access

Bad troubleshooting:

```text
403
↓
Give admin
↓
Works
↓
Done
```

You have only proved:

```text
Permissions matter.
```

You have not implemented a safe fix.

Instead identify the exact required permission.

---

# 59. HTTP 404

```text
404 Not Found
```

can indicate:

```text
Wrong repository
Wrong path
Wrong package version
Wrong tag
Artifact missing
Incorrect routing
```

Do not automatically interpret 404 as:

```text
Artifactory is down.
```

A server returning 404 is clearly responding.

---

# 60. HTTP 400

```text
400 Bad Request
```

often indicates the request itself is invalid.

Possible causes:

```text
Malformed request
Invalid API body
Bad syntax
Unsupported parameter
Incorrect package-manager request
```

Inspect the response body and request details.

---

# 61. HTTP 409

```text
409 Conflict
```

may indicate a state conflict.

The exact meaning depends on the operation.

Possible examples include:

```text
Artifact/version conflict
Repository state conflict
Operation incompatible with current state
```

Always inspect the response body rather than troubleshooting solely from the number.

---

# 62. HTTP 429

```text
429 Too Many Requests
```

indicates rate limiting or request throttling somewhere in the request path.

Possible source:

```text
JFrog service
Proxy
Gateway
External upstream
```

Identify who actually returned the response.

---

# 63. HTTP 5xx

Examples:

```text
500
502
503
504
```

These usually push investigation toward server-side or upstream infrastructure.

But they are not interchangeable.

---

# 64. HTTP 500

```text
500 Internal Server Error
```

indicates an unexpected server-side failure.

Check:

```text
Service logs
Trace ID
Database
Storage
Application exceptions
```

---

# 65. HTTP 502

```text
502 Bad Gateway
```

commonly means an intermediary received an invalid response from an upstream service.

Possible architecture:

```text
Client
↓
Load Balancer
↓
Router
↓
Artifactory
```

or:

```text
Artifactory
↓
Proxy
↓
External Registry
```

Find which gateway returned it.

---

# 66. HTTP 503

```text
503 Service Unavailable
```

can indicate:

```text
Service unavailable
Maintenance
Overload
Dependency unavailable
Unready backend
```

Check service health and dependencies.

---

# 67. HTTP 504

```text
504 Gateway Timeout
```

means a gateway waited too long for an upstream response.

Possible causes:

```text
Slow Artifactory
Slow database
Slow storage
Slow external registry
Network delay
Proxy timeout
```

Do not simply increase timeout without investigating why the operation is slow.

# 70. Upload Troubleshooting Sequence

Start:

```text
1. Capture exact error.

2. Capture HTTP status.

3. Verify Artifactory health.

4. Verify target repository.

5. Verify credentials.

6. Verify deploy/write permission.

7. Inspect request log.
```

7. Treating every 5xx as an Artifactory bug.

8. Ignoring the load balancer.

9. Ignoring proxies.

10. Ignoring DNS.

11. Disabling TLS verification permanently.

12. Giving administrator access to fix 403.

13. Rotating credentials without proving authentication is the problem.

14. Checking database before verifying the path.

15. Checking storage before verifying the artifact exists.

16. Ignoring client configuration.

17. Ignoring CI environment differences.

18. Assuming local success proves CI success.

19. Assuming UI success proves artifact transfer works.

20. Assuming `jf rt ping` proves every repository works.

21. Assuming shell exit code from every command represents HTTP success.

22. Ignoring outbound request logs for remote repositories.

23. Ignoring trace IDs.

24. Searching giant logs without narrowing by time/user/path.

25. Sharing sensitive logs publicly.

26. Running destructive API calls during investigation.

27. Deleting cache randomly.

28. Deleting production artifacts to fix disk pressure.

29. Ignoring filesystem capacity.

30. Ignoring database capacity.

31. Ignoring log-disk capacity.

32. Ignoring certificate expiration.

33. Ignoring token expiration.

34. Ignoring repository permissions.

35. Ignoring virtual repository composition.

36. Ignoring package version typos.

37. Ignoring Docker tag mistakes.

```text

WHO?

Laptop, CI, Kubernetes, all environments?

WHEN?
Exact time.

WHAT CHANGED?

HTTP?

SCOPE?

HEALTH?

DEPENDENCIES?

HYPOTHESIS?
What evidence-based explanation fits?

What smallest test proves it?

Correct root cause.

VERIFY?
Repeat original operation.

```

# 166. What You Should Now Understand

You should now understand:

* Artifactory troubleshooting must be evidence-driven.
* A symptom is not a root cause.
* Logs provide request and application evidence.
* Request logs show incoming HTTP activity.
* Outbound logs help investigate remote repository traffic.
* Trace IDs help correlate requests.
* Artifactory service logs help diagnose application problems.
* Access/security logs matter for identity failures.
* `jf rt ping` can establish basic connectivity.
* REST health endpoints provide targeted service checks.
* Readiness and liveness answer different health questions.
* Storage, database, network and DNS are separate failure domains.
* TLS errors should be diagnosed rather than bypassed.
* 401 and 403 represent different troubleshooting directions.
* 404 often points toward identity/path/version problems.
* 5xx responses require server/upstream investigation.
* Failed uploads and downloads have different diagnostic paths.
* Package managers introduce client configuration and cache behavior.
* Docker failures require checking registry, repository, image, tag, manifest and authentication.
* Cached vs uncached dependencies are powerful diagnostic comparisons.
* Local vs CI behavior helps isolate environment differences.
* Small vs large transfers can expose network/proxy issues.
* Disk problems can affect Artifactory without complete outage.
* JFrog CLI can be used for controlled diagnostic testing.
* REST APIs can provide precise health and repository checks.
* Blind restarts can destroy evidence.
* Every fix must be verified using the original workflow.
* Serious incidents should end with prevention.
