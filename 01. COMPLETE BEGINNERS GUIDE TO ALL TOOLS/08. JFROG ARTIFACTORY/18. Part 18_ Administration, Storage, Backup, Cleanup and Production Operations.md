```text
           ┌───────────┴───────────┐
```

# 9. What Is the Filestore?

The filestore is where Artifactory stores binary content.

Examples:

```text
JAR
ZIP
Docker layers
npm package archives
Python packages
Helm charts
Generic artifacts
```

Conceptually:

```text
Logical Repository Path
↓
Metadata
↓
Binary Content
↓
Filestore
```

Artifactory uses checksum-based binary storage concepts rather than treating every repository path as a completely unrelated physical file.

This allows storage optimization and deduplication where identical binary content is referenced multiple times.

---

# 10. Logical Path vs Physical Storage

Suppose you see:

```text
libs-release-local/
└── com/veriqta/api/1.0.0/api-1.0.0.jar
```

That is the logical repository path.

Do not assume the filestore simply contains:

```text
libs-release-local/com/veriqta/api/...
```

as ordinary folders.

Artifactory separates:

```text
Logical repository metadata
```

from:

```text
Physical binary storage.
```

This distinction matters during backup and recovery.

---

# 11. Checksum-Based Storage

Artifactory can identify binary content using checksums.

Imagine:

```text
Repository A
↓
artifact.zip
↓
SHA = ABC
```

and:

```text
Repository B
↓
another-name.zip
↓
SHA = ABC
```

If the bytes are identical, checksum-based storage can reduce unnecessary physical duplication.

Conceptually:

```text
Logical Path A ───┐
                  ├──→ Binary ABC
Logical Path B ───┘
```

But remember:

```text
Deduplication
≠
Unlimited storage.
```

Unique artifacts still consume storage.

---

# 12. The Database Dependency

The database is essential.

It stores important information used to make sense of repository content and platform state.

Conceptually:

```text
DATABASE
├── Repository metadata
├── Artifact metadata
├── Paths
├── Properties
├── Build information
├── Security/configuration-related state
└── Other platform data
```

The exact data model is internal implementation detail.

The operational lesson is:

```text
Database loss
=
Major Artifactory failure.
```

JFrog's current backup guidance explicitly warns that a filestore alone is insufficient because, without the database, the checksum-named binaries cannot simply be reconstructed into their logical repository state.

# 40. Garbage Collection Concepts

Deleting a logical repository path does not always mean binary storage is instantly reclaimed.

Because Artifactory uses checksum-based storage, binary content may have:

```text
multiple logical references
```

or become:

```text
unreferenced
```

after deletion.

Conceptually:

```text
Artifact Path
↓
Deleted
↓
Binary still referenced elsewhere?
├── YES → Keep binary
└── NO → Binary becomes orphan candidate
```

Garbage collection later reclaims binary content that is no longer referenced.

---

# 41. Why Garbage Collection Exists

Imagine:

```text
Repo A → Binary ABC
Repo B → Binary ABC
```

Delete Repo A reference.

Should Artifactory immediately delete:

```text
Binary ABC?
```

No.

Repo B still needs it.

Therefore:

```text
Logical deletion
```

and:

```text
Physical binary reclamation
```

are separate lifecycle operations.

---

# 42. Storage May Not Drop Immediately After Deletion

An administrator deletes:

```text
500 GB of artifacts
```

Then checks disk:

```text
Only 50 GB recovered.
```

Possible reason:

```text
Some binaries remain referenced
```

or:

```text
Physical cleanup/garbage-collection process has not reclaimed unreferenced binaries yet.
```

Do not assume deletion failed solely because filesystem usage did not instantly drop.

---

# 43. Do Not Manually Delete Filestore Files

This is a critical rule.

Never casually run:

```bash
rm -rf <filestore-files>
```

to free storage.

Why?

You can create:

```text
Database says artifact exists
↓
Filestore binary missing
↓
Repository corruption/inconsistency
```

Always use supported Artifactory lifecycle/cleanup mechanisms.

---

# 44. The Database Is Not a Cleanup Shortcut Either

Similarly:

```text
DELETE FROM ...
```

directly against Artifactory database tables is not a normal cleanup method.

The application expects its metadata model to remain consistent.

Use supported:

```text
JFrog APIs
CLI
Cleanup Policies
Administration mechanisms
```

rather than modifying internal database state manually.

# 45. Backup Fundamentals

A backup exists for one reason:

```text
RECOVERY.
```

If you cannot restore it:

```text
Backup value
=
uncertain.
```

Therefore the lifecycle is:

```text
BACK UP
↓
VERIFY
↓
PROTECT
↓
TEST RESTORE
↓
DOCUMENT RECOVERY
```

Not simply:

```text
Create backup file.
```

---

# 46. What Must Be Protected?

A production backup strategy should consider:

```text
Database
Filestore
Critical configuration
Encryption/security material required for recovery
```

JFrog's current documentation recommends backing up the database and filestore and preserving the required Artifactory configuration. For large installations, it specifically recommends backing up the database, filestore, and Artifactory home components separately, and coordinating database and filestore backup timing.

---

# 47. Why Timing Matters

Suppose:

```text
10:00
Database backup taken

12:00
Filestore backup taken
```

During those two hours:

```text
10,000 artifacts uploaded
5,000 artifacts deleted
Repositories modified
```

Now your backups may represent different points in time.

Consistency becomes harder.

JFrog's current backup guidance recommends taking the database snapshot before the filestore copy and performing the operations close together.

The exact backup technique depends on your architecture.

# 53. Recovery Point Objective

RPO means:

```text
Recovery Point Objective
```

It answers:

```text
How much data can we afford to lose?
```

Example:

```text
RPO = 1 hour
```

means the organization aims to lose no more than roughly one hour of data during a disaster.

This influences backup frequency and replication design.

---

# 54. Recovery Time Objective

RTO means:

```text
Recovery Time Objective
```

It answers:

```text
How long can the service remain unavailable?
```

Example:

```text
RTO = 2 hours
```

means recovery architecture should aim to restore service within that window.

---

# 55. RPO and RTO Drive Architecture

If Artifactory is low criticality:

```text
RPO = 24 hours
RTO = 24 hours
```

a simple backup architecture may be sufficient.

If Artifactory supports global production deployment:

```text
RPO = minutes
RTO = minutes
```

you likely need more sophisticated:


The broader principle is:

```text
Do not let one infrastructure failure destroy both production and every backup.
```

# 128. Backup Isolation

If production administrator credentials can instantly delete:

```text
Production
+
Every backup
```

a compromised account has enormous power.

Where practical, backup systems should have:

```text
Separate controls
Limited deletion
Retention protection
Auditability
```

This helps against both mistakes and security incidents.

# 129. Cleanup and Backup Are Not Opposites

You may think:

```text
We'll delete aggressively because backups exist.
```

Bad idea.

Restoring ordinary artifacts from backup is operationally expensive.

Backups are for recovery.

Retention policies should keep operationally required content available directly.

```text
Archive tier

Delete
```
