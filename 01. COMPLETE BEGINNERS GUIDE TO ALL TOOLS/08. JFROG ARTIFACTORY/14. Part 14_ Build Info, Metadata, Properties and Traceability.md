# Part 14: Build Info, Metadata, Properties and Traceability

In Part 13, you built this delivery chain:

```text
Developer
↓
Git
↓
CI
↓
Build + Test
↓
Artifactory
↓
Deploy
↓
Application
```

You also learned one of the most important principles in software delivery:

```text
BUILD ONCE
↓
DEPLOY MANY
```

But this creates another question.

Suppose production is currently running:

```text
veriqta-api-3.2.0.tar.gz
```

Where did that file come from?

You need more than:

```text
It came from Artifactory.
```

You should be able to determine:

```text
Which Git repository?

Which Git commit?

Which branch or tag?

Which CI pipeline?

Which build number?

Which dependencies?

Which build tools?

Which artifacts were generated?

Which checksum identifies the binary?

When was it created?

Which properties describe it?

Which release used it?

Which environment is running it?
```

That is the purpose of traceability.

Our core architecture is:

```text
Git Commit
↓
CI Build
↓
Build Info
↓
Artifact
↓
Deployment
```

A more complete version is:

```text
SOURCE
│
├── Git Repository
├── Git Commit
├── Branch / Tag
└── Pull Request
        ↓
CI BUILD
│
├── Pipeline
├── Build Name
├── Build Number
├── Build Environment
└── Build Tool
        ↓
BUILD INFO
│
├── Modules
├── Dependencies
├── Generated Artifacts
├── Environment Metadata
└── Source Information
        ↓
ARTIFACTORY
│
├── Repository
├── Path
├── Properties
├── Checksums
└── Artifact Metadata
        ↓
RELEASE
        ↓
DEPLOYMENT
        ↓
RUNNING APPLICATION
```

The objective of this part is simple:

**You should be able to start anywhere in this chain and investigate backward or forward.**

For example:

```text
Production
↓
Artifact
↓
Build
↓
Commit
```

or:

```text
Commit
↓
Build
↓
Artifact
↓
Deployment
```

That capability is extremely valuable in production engineering.

---

# 1. Why Binary Traceability Matters

Imagine an engineer asks:

> Which version is production running?

Someone answers:

```text
3.2.0
```

That is useful.

But it is not enough.

Suppose Artifactory contains:

```text
veriqta-api-3.2.0.tar.gz
```

You now need to know:

```text
Which source produced it?
```

Perhaps:

```text
Git commit:
5b72c91
```

Then:

```text
Which pipeline execution built it?
```

Perhaps:

```text
Build:
842
```

Then:

```text
What dependencies did build 842 use?
```

Then:

```text
Which exact binary did build 842 produce?
```

Then:

```text
Was that exact binary deployed?
```

This gives us:

```text
Commit 5b72c91
↓
Build 842
↓
Artifact
↓
Checksum ABC
↓
Production
```

That is binary traceability.

---

# 2. What Is a Binary?

A binary is generally a built software artifact rather than the original source code.

Examples include:

```text
JAR
WAR
ZIP
TAR.GZ
Wheel
npm package
Compiled executable
Container image
```

Even though container images are structured differently from a single archive file, the same traceability principle applies.

You want to know:

```text
What exact software content is this?
```

and:

```text
Where did it come from?
```

---

# 3. Source Code Is Not the Final Artifact

Suppose Git contains:

```text
commit abc123
```

That commit is source identity.

But production may actually run:

```text
veriqta-api-3.2.0.jar
```

or:

```text
veriqta-api:3.2.0
```

The relationship must be established:

```text
Git Commit abc123
↓
Build Process
↓
Artifact
```

Without that relationship, finding source code does not necessarily prove which binary is running.

---

# 4. Why the Filename Is Not Enough

Suppose you see:

```text
veriqta-api-3.2.0.tar.gz
```

The filename tells you:

```text
Application:
veriqta-api

Version:
3.2.0
```

assuming your naming convention is trustworthy.

But it does not inherently tell you:

```text
Git commit
Build number
Pipeline
Dependencies
Build environment
Checksum
Testing status
Release status
```

Worse, if overwrites are allowed, two completely different files could have been given the same filename at different times.

Therefore:

```text
Filename
≠
Complete Provenance
```

---

# 5. What Is Provenance?

In software delivery, provenance describes the origin and history of software.

Think:

```text
Where did this come from?
```

For an artifact, provenance may involve:

```text
Source repository
↓
Source revision
↓
Build system
↓
Build execution
↓
Dependencies
↓
Generated artifact
↓
Repository
↓
Release
↓
Deployment
```

Traceability lets engineers investigate this provenance.

---

# 6. Traceability Works in Two Directions

## Forward Traceability

Start from source:

```text
Git Commit
↓
Build
↓
Artifact
↓
Release
↓
Deployment
```

Question:

```text
Where did this change eventually go?
```

---

## Backward Traceability

Start from production:

```text
Deployment
↓
Artifact
↓
Build
↓
Git Commit
```

Question:

```text
Where did this running software come from?
```

Both directions matter.

# 7. A Real Production Question

Imagine an incident.

At 14:32 UTC:

```text
HTTP 500 errors increase.
```

You discover production is running:

```text
veriqta-api 3.2.0
```

Your investigation could become:

```text
Production
↓
Version 3.2.0
↓
Image Digest sha256:ABC
↓
Artifactory
↓
Build 842
↓
Commit 5b72c91
↓
Code changes
```

You may also inspect:

```text
Dependencies used by build 842
```

and compare them with:

```text
Dependencies used by previous build 817
```

Now your investigation is evidence-driven.

# 8. What Is Build Info?

JFrog Build Info is metadata describing a software build and its relationship to things such as:

```text
Build identity
Modules
Dependencies
Generated artifacts
Source information
Environment information
```

Conceptually:

```text
BUILD INFO
│
├── Build Name
├── Build Number
├── Source Context
├── Modules
│   ├── Dependencies
│   └── Artifacts
└── Additional Build Metadata
```

It creates a relationship between:

```text
The build process
```

and:

```text
The binaries produced by that process.
```

---

# 9. Artifact vs Build Info

Do not confuse them.

Artifact:

```text
veriqta-api-3.2.0.jar
```

Build Info:

```text
Information describing the build that produced it
```

Conceptually:

```text
Build Info
↓
Build 842
├── Dependency A
├── Dependency B
├── Dependency C
└── Generated Artifact
    └── veriqta-api-3.2.0.jar
```

The artifact is the software output.

Build Info describes the build context and relationships.

---

# 10. Why Build Info Exists

Without Build Info, you may have:

```text
Artifactory
└── veriqta-api-3.2.0.jar
```

You know the artifact exists.

But your investigation may require manually reconstructing:

```text
Which Jenkins build?
Which GitHub Actions run?
Which dependencies?
Which source?
Which other outputs?
```

Build Info helps preserve these relationships.

---

# 11. Build Name

A build needs an identity.

Example:

```text
veriqta-api
```

This can be the build name.

Conceptually:

```text
Build Name:
veriqta-api
```

The build name identifies a logical build or pipeline over time.

---

# 12. Build Number

Each execution needs another identifier.

For example:

```text
Build Name:
veriqta-api

Build Number:
842
```

Now we have:

```text
veriqta-api / 842
```

This identifies a specific build execution.

---

# 13. Build Name + Build Number

Think of:

```text
Build Name
+
Build Number
=
Specific Build Execution
```

For example:

```text
veriqta-api / 842
```

Different execution:

```text
veriqta-api / 843
```

Different application:

```text
payment-service / 842
```

Build number alone may not be globally meaningful.

Build name provides context.

---

# 14. Build Number vs Version

This remains important.

```text
Build Number:
842
```

does not necessarily mean:

```text
Application Version:
842
```

You might have:

```text
Application:
veriqta-api

Version:
3.2.0

Build Name:
veriqta-api

Build Number:
842
```

These represent different dimensions.

---

# 15. Build Number vs Git Commit

Likewise:

```text
Build Number:
842
```

and:

```text
Git Commit:
5b72c91
```

are not interchangeable.

Build number answers:

```text
Which build execution?
```

Commit answers:

```text
Which source revision?
```

Together:

```text
Commit 5b72c91
↓
Build 842
```

is much more useful.

# 16. Build History

Over time, your build history might look like:

```text
veriqta-api

↓
Failed

Build 840
↓
Passed
↓
Artifact 3.1.9

Build 841
↓
Passed
↓
Candidate 3.2.0-rc.1

Build 842
↓
Passed
↓

```

```text

```

---

# 17. Build History Is Not Git History

Git history describes:

```text
Source changes
```

Build history describes:

```text
Build executions
```

They overlap but are not identical.

One commit may be built several times.

For example:

```text
Commit abc123
├── Build 840
├── Build 841
└── Build 842
```

Perhaps because:

```text
A build was retried
Different build configuration was used
A previous run failed
Different pipeline conditions applied
```

Therefore:

```text
Git History
≠
Build History
```

# 18. Modules

A build may contain one or more logical modules.

Suppose you have:

```text
veriqta-platform
```

with:

```text
api
worker
shared-library
```

Conceptually:

```text
Build:
veriqta-platform / 105

Modules:
├── api
├── worker
└── shared-library
```

Each module can have its own:

```text
Dependencies
Generated artifacts
```

---

# 19. Why Modules Matter

Imagine a Maven multi-module project:

```text
veriqta-platform/
├── pom.xml
├── shared/
│   └── pom.xml
├── api/
│   └── pom.xml
└── worker/
    └── pom.xml
```

The build may generate:

```text
shared-1.0.0.jar
api-1.0.0.jar
worker-1.0.0.jar
```

Rather than treating the build as an unexplained collection of files, modules help represent logical relationships.

---

# 20. Module Mental Model

```text
BUILD
└── Module
    ├── Dependencies
    │   ├── dependency-a
    │   ├── dependency-b
    │   └── dependency-c
    │
    └── Artifacts
        ├── artifact-a
        └── artifact-b
```

A build may contain:

```text
one module
```

or:

```text
multiple modules.
```

# 21. Dependencies

A dependency is something the build consumes.

For example, a Java build might consume:

```text
Spring libraries
Jackson libraries
Internal company libraries
Testing libraries
```

An npm build might consume:

```text
React
Express
Internal npm packages
```

A Python build might consume:

```text
requests
FastAPI
Internal Python packages
```

Conceptually:

```text
DEPENDENCIES
↓
BUILD
↓
GENERATED ARTIFACTS
```

---

# 22. Dependency Traceability

Suppose production has a security issue.

Security tells you:

```text
Library X version 4.2.1 is vulnerable.
```

Now you want to ask:

```text
Which builds used Library X 4.2.1?
```

Then:

```text
Which artifacts came from those builds?
```

Then:

```text
Which of those artifacts reached production?
```

That becomes:

```text
Vulnerable Dependency
↓
Affected Build
↓
Affected Artifact
↓
Affected Deployment
```

This is one reason dependency traceability matters.

---

# 23. Direct vs Transitive Dependencies

Remember from Maven/npm/Python discussions:

A direct dependency is explicitly declared by your project.

Example:

```text
Your Application
↓
Library A
```

A transitive dependency arrives through another dependency:

```text
Your Application
↓
Library A
↓
Library B
```

Your application may never explicitly declare:

```text
Library B
```

but it can still become part of the dependency graph.

That matters during security and production investigations.

# 24. Generated Artifacts

Build Info can represent outputs produced by a build.

For example:

```text
Build:
veriqta-api / 842

Generated Artifact:
veriqta-api-3.2.0.jar
```

A build could generate multiple artifacts:

```text
veriqta-api-3.2.0.jar
veriqta-api-3.2.0-sources.jar
veriqta-api-3.2.0.pom
```

or:

```text
frontend.tar.gz
backend.tar.gz
migration-bundle.zip
```

depending on the build.

# 25. Dependency vs Generated Artifact


```text

     ↓
```

# 28. Why Environment Information Matters

Suppose:

```text

↓
Succeeded

Build 843
↓
Failed
```

Source commit:

```text

```

Dependencies:

```text
Same
```

But:

```text

Build 843:
Java 21
```

Now you have a possible explanation.

Without environment context:

```text

```

# 29. Environment Metadata Can Be Sensitive

Do not conclude:

```text

```

Environment variables may contain:

```text
Passwords
Tokens
API keys
Cloud credentials
Database credentials
Private endpoints
Internal infrastructure information
```

Do not blindly capture every environment variable.

Traceability must not become credential leakage.

# 31. Metadata

Metadata means:

```text
Data describing other data.
```

For an artifact, the binary itself might be:

```text
veriqta-api-3.2.0.tar.gz
```

Metadata could describe:

```text
Name
Version
Repository
Path
Size
Checksum
Creation time
Properties
Build association
Package information
```

The binary is the content.

Metadata describes the content and its context.

# 32. Metadata vs Properties

Properties are one mechanism for attaching custom metadata to artifacts.

For example:

```text
application=veriqta-api
environment=staging
release-status=approved
team=platform
```

Think:

```text
Metadata
↓
Broad concept

Properties
↓
Custom key/value metadata attached to artifacts
```

Not all metadata is necessarily an Artifactory property.

---

# 33. Property Structure

A property commonly follows:

```text
key=value
```

For example:

```text
application=veriqta-api
```

Key:

```text
application
```

Value:

```text
veriqta-api
```

Other examples:

```text
version=3.2.0
build-number=842
git-commit=5b72c91
release-status=candidate
```

---

# 34. Why Properties Matter

Imagine 100,000 artifacts.

Browsing manually:

```text
Repository
↓
Folder
↓
Folder
↓
Folder
↓
Maybe this one?
```

does not scale well.

Properties allow questions such as:

```text
Find artifacts where:

application = veriqta-api
AND
release-status = approved
```

Properties make artifacts searchable by meaning rather than only location.

---

# 35. Good Property Design

Useful properties should answer operational questions.

Examples:

```text
application
version
build-number
git-commit
release-status
```

Possibly:

```text
team
service
component
```

depending on organizational needs.

Avoid turning properties into an uncontrolled dumping ground.

---

# 36. Property Naming Consistency

Bad:

```text
build=842
build_number=843
build-number=844
buildNumber=845
```

Now searches become unnecessarily difficult.

Better:

```text
build-number=842
build-number=843
build-number=844
```

Define conventions.

---

# 37. Do Not Put Secrets in Properties

Never:

```text
database-password=...
api-token=...
private-key=...
```

Properties are metadata, not secret storage.

Use approved secret-management systems for secrets.

---

# 38. Properties vs Version

Do not replace proper versioning with properties.

Bad:

```text
artifact:
veriqta-api.tar.gz

property:
version=3.2.0
```

while repeatedly overwriting the same binary path.

Better:

```text
veriqta-api/3.2.0/veriqta-api-3.2.0.tar.gz
```

plus:

```text
version=3.2.0
```

as searchable metadata if useful.

Repository structure and metadata should reinforce each other.

---

# 39. Properties vs Build Info

Another important distinction:

```text
Properties
↓
Custom metadata attached to artifact/repository items

Build Info
↓
Structured information about a build and its relationships
```

Properties might tell you:

```text
build-number=842
```

Build Info can tell you more about:

```text
Build 842
├── Modules
├── Dependencies
└── Artifacts
```

They complement each other.

# 40. Checksums

A checksum is a calculated fingerprint of content.

For example:

```text
SHA-256
```

Suppose:

```text
veriqta-api-3.2.0.tar.gz
```

produces:

```text
SHA-256:
abc123...
```

If one byte changes, the checksum should normally change dramatically.

---

# 41. Why Checksums Matter for Traceability

Filename:

```text
veriqta-api-3.2.0.tar.gz
```

can be reused.

Checksum:

```text
sha256:abc123...
```

identifies the content much more precisely.

Therefore:

```text
Version
+
Checksum
```

provides stronger artifact identity than version alone.

---

# 42. Calculate SHA-256 on macOS

On macOS:

```bash
shasum -a 256 veriqta-api-3.2.0.tar.gz
```

Breakdown:

```text
shasum
↓
Checksum utility

-a
↓
Select algorithm

256
↓
SHA-256

filename
↓
File being hashed
```

---

# 43. Calculate SHA-256 on Linux

Many Linux systems provide:

```bash
sha256sum veriqta-api-3.2.0.tar.gz
```

Example output:

```text
abc123...  veriqta-api-3.2.0.tar.gz
```

The left side is the checksum.

---

# 44. Checksum Is Not Encryption

A checksum does not hide file contents.

```text
Checksum
≠
Encryption
```

Encryption:

```text
Protects confidentiality
```

Checksum:

```text
Helps identify/verify content
```

Do not confuse them.

---

# 45. Checksum Is Not a Digital Signature

A checksum can show:

```text
Content changed
```

if you have a trusted expected checksum.

But a checksum by itself does not prove:

```text
Who produced the file.
```

Cryptographic signing and provenance systems address different trust questions.

For now remember:

```text
Checksum
↓
Content identity/integrity verification

Signature
↓
Authenticity/integrity relationship based on cryptographic identity
```

---

# 46. Container Digests

Container images have similar content-addressable identity concepts.

You may deploy:

```text
veriqta-api:3.2.0
```

but stronger identity can include:

```text
sha256:...
```

The tag is human-friendly.

The digest identifies immutable image content.

Conceptually:

```text
Tag:
3.2.0

Digest:
sha256:ABC
```

This connects Part 14 directly to Part 11 and Part 12.

# 49. Build Info Collection

In a JFrog CLI workflow, artifact operations can be associated with a:

```text

```

and:

```text
Build Number
```

Conceptually:

```text

+
Build Name
+
Build Number
↓
Artifact associated with build context
```

The exact command flags can depend on your installed JFrog CLI version and workflow.

Before implementation, inspect:

```bash

```

and:

```bash

```

# 50. Publishing Build Info

Conceptually:

```text
Build executes
↓
Dependencies collected
↓
Artifacts collected
↓
Build context collected
↓
Build Info published
```

A command pattern you may encounter is:

```bash

  842 \
  --server-id=veriqta-ci
```

Conceptually:

```text
jf
↓
JFrog CLI

rt
↓
Artifactory command group

build-publish
↓
Publish collected Build Info

veriqta-api
↓
Build name

842
↓
Build number
```

Always verify exact syntax against the CLI version used in your environment.

---

# 51. Build Info Should Be Published After Relevant Operations

Conceptually:

```text
Resolve Dependencies
↓
Build
↓
Generate Artifacts
↓
Upload
↓
Collect Relationships
↓
Publish Build Info
```

If you publish Build Info before the relevant artifact/dependency information has been associated, your record may be incomplete.

Think of Build Info as the final description of that build execution.

# 86. Understand the Pipeline

This:

```bash
shasum -a 256 FILE | awk '{print $1}'
```

does two operations.

First:

```bash
shasum -a 256 FILE
```

might output:

```text
abc123...  FILE
```

The pipe:

```text
|
```

sends that output to:

```bash
awk '{print $1}'
```

`awk` prints the first whitespace-separated field.

Result:

```text
abc123...
```

Now:

```text
CHECKSUM
```

contains only the SHA-256 value.


as an artifact property.

Be careful.

If the same artifact is deployed simultaneously to:

```text
Development
Staging
Production
```

a single property may not accurately model deployment history.

Artifact properties are useful metadata.

A deployment/release system is often better suited to representing actual deployment events and environment history.

Choose the right metadata location for the question being answered.

---

# 118. Artifact Metadata Is Not Deployment State

This deserves emphasis.

Artifact:

```text
veriqta-api 3.2.0
```

may exist independently of deployment.

Deployment state answers:

```text
Where is 3.2.0 currently running?
```

Those are different concerns.

Do not overload artifact properties until they become an unreliable deployment database.

# 119. Traceability Design Principles

A strong design should aim for:

```text
Unique identity
Accurate metadata
Automated collection
Immutable releases
Dependency visibility
Build association

Deployment association
Searchability
Least privilege
No secrets in metadata
```

These reinforce one another.

# 120. Traceability Anti-Patterns

Avoid:

```text
latest.zip
```

Avoid:

```text
latest container tag as sole identity
```

Avoid:

```text
manual uploads with no build information
```

Avoid:

```text
reusing release versions for different binaries
```

Avoid:

```text
manually typing Git commits
```

Avoid:

```text
one metadata property trying to represent everything
```

Avoid:

```text
capturing all environment variables including secrets
```

Avoid:

```text
deleting build history without understanding retention requirements
```

Avoid:

```text
assuming filenames prove provenance
```

---

# 121. Build History Retention

Build history can become large.

Organizations therefore need retention policies.

But deleting old build records can affect your ability to answer:

```text
Which build produced this old release?
```

or:

```text
Which dependencies were used?
```

Retention should consider:

```text
Rollback
Incident investigation
Audit requirements
Security investigations
Release lifecycle
Storage
Compliance
```

Do not choose retention solely because:

```text
old = useless.
```

---

# 122. Artifact Retention vs Build Info Retention

These are related but distinct.

You may retain:

```text
Artifact
```

while deleting:

```text
Build Info
```

Then you still have the binary but may lose useful provenance.

Or you may retain metadata while deleting artifacts, reducing rollback capability.

Design lifecycle policies deliberately.

---

# 123. Build Info and Reproducibility

Build Info can improve reproducibility by recording information about:

```text
Dependencies
Build environment
Source
Outputs
```

But Build Info alone does not guarantee:

```text
Perfect reproducible build.
```

A truly reproducible build also depends on controlling things such as:

```text
Build tool versions
Dependency versions
Base images
External downloads
Timestamps
Environment
Compiler behavior
Network resources
Generated content
```

Traceability and reproducibility are related but not identical.

---

# 124. Traceability vs Reproducibility

Traceability asks:

```text
What produced this artifact?
```

Reproducibility asks:

```text
Can we produce the same artifact again from the same defined inputs?
```

Both matter.

But do not confuse them.

---

# 125. Traceability vs Observability

Observability asks questions about runtime behavior:

```text
What is the application doing?
Why is it slow?
Why is it failing?
```

Traceability asks:

```text
What software is this?
Where did it come from?
```

During incidents they work together:

```text
Observability
↓
Identifies failing service/version

Traceability
↓
Identifies artifact/build/source
```

---

# 126. Traceability vs Logging

Logs might tell you:

```text
Application version 3.2.0 started.
```

Traceability can connect:

```text
3.2.0
↓
Artifact
↓
Build
↓
Commit
```

Logs are runtime evidence.

Build Info and artifact metadata are software supply-chain evidence.

---

# 127. Traceability vs Monitoring

Monitoring might show:

```text
Error rate increased after 14:32.
```

Deployment data might show:

```text
3.2.0 deployed at 14:30.
```

Traceability shows:

```text
3.2.0
↓
Build 842
↓
Commit 5b72c91
```

Now:

```text
Monitoring
+
Deployment history
+
Artifact traceability
```

creates a strong investigation path.

---

# 128. Traceability and Root Cause Analysis

Suppose:

```text
Incident
↓
New release suspected
```

A weak RCA says:

```text
The deployment caused the incident.
```

A stronger investigation asks:

```text
Which deployment?
Which artifact?
Which build?
Which dependency?
Which source change?
What evidence connects it to the failure?
```

Traceability gives you the chain needed to investigate the actual cause.

---

# 129. Traceability Does Not Prove Causation

This is important.

Suppose:

```text
Deployment 3.2.0
```

happens at:

```text
14:30
```

and errors start at:

```text
14:31.
```

Traceability proves:

```text
what was deployed.
```

It does not automatically prove:

```text
the deployment caused the errors.
```

Perhaps:

```text
Database failed
Network changed
Certificate expired
Traffic spiked
External API failed
```

Use traceability as evidence, not as a substitute for investigation.

Your final project is to prove the complete origin of a fictional production release.

Assume production reports:

```text

Exactly where did 4.0.0 come from?
```

```text
veriqta-api
```

# 138. Final Traceability Architecture

By the end of Part 14, this should no longer look abstract:

```text
                           SOURCE
                              │
                     Git Repository
                              ↓
                         Git Commit
                              ↓
                         CI PIPELINE
                              │
                   ┌──────────┼──────────┐
                   ↓          ↓          ↓
              Build Name   Build No.   Environment
                   └──────────┼──────────┘
                              ↓
                         BUILD INFO
                              │
                 ┌────────────┼────────────┐
                 ↓            ↓            ↓
              Modules    Dependencies   Artifacts
                 │            ↓            │
                 │          INPUT          │
                 │                         ↓
                 └────────────────────── OUTPUT
                                           ↓
                                      ARTIFACTORY
                                           │
                          ┌────────────────┼────────────────┐
                          ↓                ↓                ↓
                     Repository        Properties       Checksum
                          │                │                │
                          └────────────────┼────────────────┘
                                           ↓
                                        RELEASE
                                           ↓
                                       DEPLOYMENT
                                           ↓
                                  RUNNING APPLICATION
```

You should now understand the complete traceability question:

```text
WHAT IS RUNNING?
↓
WHICH EXACT ARTIFACT?
↓
WHICH CHECKSUM OR DIGEST?
↓
WHERE IS IT STORED?
↓
WHICH BUILD PRODUCED IT?
↓
WHAT DID THAT BUILD CONSUME?
↓
WHICH SOURCE COMMIT DID IT BUILD?
```

And in the opposite direction:

```text
GIT COMMIT
↓
WHICH BUILD USED IT?
↓
WHAT ARTIFACT DID THAT BUILD PRODUCE?
↓
WHAT IS THE ARTIFACT'S IMMUTABLE IDENTITY?
↓
WAS IT RELEASED?
↓
WHERE WAS IT DEPLOYED?
```

The final mental model is:

```text
Git Commit
↓
CI Build
↓
Build Info
↓
Artifact
↓
Deployment
```

with Build Info providing the critical middle layer:

```text
                    BUILD INFO
                         │
        ┌────────────────┼────────────────┐
        ↓                ↓                ↓
     SOURCE          DEPENDENCIES      ARTIFACTS
        ↓                ↓                ↓
   What changed?    What went in?     What came out?
```

That gives engineers the ability to answer one of the most important questions in modern software delivery:

**Exactly where did this binary come from, what went into it, and where did it go?**

That is artifact traceability.
