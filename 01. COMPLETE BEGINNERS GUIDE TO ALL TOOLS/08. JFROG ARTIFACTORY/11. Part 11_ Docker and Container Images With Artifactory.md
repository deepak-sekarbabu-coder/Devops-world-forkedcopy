# 1. Container Recap

Before working with Artifactory, we need a clear understanding of containers.

A container is a running isolated process created from a container image.

Conceptually:

```text
Container Image
↓
docker run
↓
Running Container
```

A container can contain:

* Your application
* Runtime libraries
* Operating-system userspace components
* Configuration defaults
* Application dependencies
* Executables

For example:

```text
Python Application
+
Python Runtime
+
Python Dependencies
+
Application Files
↓
Container Image
↓
Running Container
```

Docker's documentation describes an image as a standardized package containing files, binaries, libraries, and configuration needed for a container.

---

# 2. Image vs Container

This distinction is fundamental.

## Image

A packaged template.

Example:

```text
veriqta-api:1.0.0
```

## Container

A running instance created from that image.

Conceptually:

```text
IMAGE

veriqta-api:1.0.0
↓
Stored artifact
```

Then:

```text
CONTAINER

docker run veriqta-api:1.0.0
↓
Running process
```

One image can create many containers.

```text
veriqta-api:1.0.0
├── Container A
├── Container B
├── Container C
└── Container D
```

This is similar to:

```text
Class
↓
Objects
```

as a conceptual analogy, though containers and object-oriented programming are technically different systems.

Imagine deploying an application manually.

You might need to install:

```text
Operating system packages
Runtime
Application libraries

Configuration
Startup scripts
```

The production server might differ from development.

You get:

```text
Developer Laptop
↓
Works

Production Server
↓
Fails
```

Containers improve consistency by packaging the application environment into an image.

Conceptually:

```text
Build Image Once
↓
Store Image
↓
Run Same Image
├── Test
├── Staging
└── Production
```

This aligns strongly with a principle you learned earlier:

```text
BUILD ONCE
↓
TEST THAT ARTIFACT
↓
PROMOTE THAT ARTIFACT
↓
DEPLOY THAT ARTIFACT
```

```text

↓

↓

↓
Version

Store
↓
```

That means the same questions apply:

# 6. Check Docker

On your MacBook, run:

```bash

```

You may see something like:

```text

```


# 7. What Is a Dockerfile?

A Dockerfile is a text file containing instructions for building a container image.

Example:

```dockerfile
FROM python:3.13-slim

WORKDIR /app

COPY app.py .

CMD ["python", "app.py"]
```

The build process reads this file and creates an image.

Conceptually:

```text
Dockerfile
+
Application Files
↓
Docker Build
↓
Container Image
```

---

# 8. Understanding `FROM`

Consider:

```dockerfile
FROM python:3.13-slim
```

This means:

```text
Start our image
↓
Using an existing Python image as a base
```

Your application image does not need to build an operating system and Python runtime from zero.

Instead:

```text
Python Base Image
↓
Add Our Application
↓
Our Image
```

This is extremely common.

# 9. Base Images

A base image is the image used as the starting point for another image.

Examples might include:

```text
ubuntu

```

For example:

```dockerfile

```

means:

```text

↓

```

Base images are therefore dependencies.

This is important.

Your Docker build has dependencies just like:



```text

```

Artifactory can proxy that dependency too.

# 10. Image Layers

Container images are composed of layers.

Each layer represents filesystem changes created during image construction. Docker's documentation describes layers as immutable filesystem changes that can add, modify, or remove files.

Consider:

```dockerfile
FROM python:3.13-slim

WORKDIR /app

COPY requirements.txt .

RUN pip install -r requirements.txt

COPY . .

CMD ["python", "app.py"]
```

Conceptually:

```text
Layer 1
Python base image

Layer 2
Working directory

Layer 3
requirements.txt

Layer 4
Installed Python dependencies

Layer 5
Application source
```

The resulting image is built from these layers.

---

# 11. Why Layers Matter

Suppose two images use the same Python base image.

```text
Application A
↓
python:3.13-slim
↓
App A layers
```

and:

```text
Application B
↓
python:3.13-slim
↓
App B layers
```

Shared layers can be reused.

This can improve:

* Build efficiency
* Storage efficiency
* Network transfer
* Image distribution

Docker's layer model allows previously existing layers to be reused rather than recreating everything for every image.

---

# 12. Layers Are Immutable

Once an image layer is created, you do not edit that layer in place.

Instead:

```text
Existing Image
↓
Add New Layer
↓
New Image
```

This is why image-building behavior is often described as immutable.

You create new image content rather than modifying a released container image directly.

---

# 13. Containers Add Writable State

Images are primarily immutable templates.

When a container runs:

```text
Image Layers
↓
Read-only foundation

+
Container writable layer
↓
Runtime changes
```

If the running application creates temporary files, those runtime changes do not rewrite the original image layers.

This is another reason you should not "fix production" by modifying a running container and assuming the change has become part of your release artifact.

---

# 14. Bad Production Practice: Fixing Running Containers Manually

Suppose:

```text
veriqta-api:1.0.0
↓
Production Container
```

has a problem.

An engineer enters the container:

```bash
docker exec -it ...
```

changes a file manually, and production starts working.

But:

```text
Original Image
↓
Still broken
```

If Kubernetes restarts the container:

```text
New Container
↓
Created from original image
↓
Manual fix disappears
```

Correct workflow:

```text
Fix Source
↓
Build New Image
↓
Test
↓
Publish New Version
↓
Deploy
```

# 15. What Is a Container Registry?

A container registry stores and distributes container images.

Examples conceptually include:

```text
Docker Hub
JFrog Artifactory
Private registries
Cloud provider registries
```

Docker describes a registry as a centralized location that stores and manages container images.

Architecture:

```text
Docker Client
↓
Registry
↓
Image Repository
↓
Image Versions
```

---

# 16. Registry vs Repository

These terms are often confused.

## Registry

The system/service that stores container image repositories.

## Repository

A collection of related images, usually distinguished by tags.

For example:

```text
Registry
└── veriqta-api
    ├── 1.0.0
    ├── 1.1.0
    └── 2.0.0
```

Docker documentation distinguishes the registry as the centralized image store and repositories as collections of related images inside it.

---

# 17. Artifactory Makes the Word "Repository" More Confusing

JFrog explicitly notes that Docker and Artifactory both use the word repository differently.

In Docker terminology:

```text
Docker Repository
↓
Collection of related tagged images
```

In Artifactory:

```text
Artifactory Docker Repository
↓
Repository object that can host many Docker image repositories
```

For example:

```text
Artifactory Repository:
veriqta-docker-local

Inside it:
├── payment-api
├── notification-service
├── web-app
└── worker
```

JFrog's current Docker documentation explicitly warns about this terminology difference.

---

# 18. What Is Docker Hub?

Docker Hub is Docker's public image registry/service.

Without Artifactory:

```text
docker pull nginx
↓
Docker Hub
```

By default, when no registry hostname is specified in a Docker image name, Docker commonly resolves against Docker Hub. Docker's current image naming documentation describes Docker Hub's `docker.io` registry as the default when no host is supplied.

For example:

```bash
docker pull nginx
```

is conceptually equivalent to requesting an image under Docker Hub's default namespace.

---

# 19. Docker Hub vs Artifactory

Docker Hub can provide:

```text
Public images
Public repositories
Private repositories depending on account/service
Official images
Publisher images
```

Artifactory can provide an organization's controlled registry layer.

Architecture:

```text
Developers
+
CI
+
Kubernetes
↓
Artifactory
├── Internal Images
└── Proxied External Images
    ↓
    Docker Hub
```

The important point is not:

```text
Docker Hub OR Artifactory
```

Instead, many organizations use:

```text
Docker Hub
↓
Artifactory Remote Repository
↓
Internal Clients
```

Artifactory becomes the controlled gateway.

# 20. Why Proxy Docker Hub Through Artifactory?

Reasons include:

* Centralized image access
* Caching
* Internal image hosting
* Access control
* Reduced repeated upstream downloads
* CI/CD integration
* Traceability
* Repository policy
* Central client configuration

JFrog currently supports local, remote, and virtual Docker repositories, including remote repositories that proxy external registries such as Docker Hub.

# 27. What Is a Tag?

A tag is a human-readable identifier associated with an image.

Examples:

```text
1.0.0
1.1.0
dev
staging
production
latest
```

For example:

```text
veriqta-api:1.0.0
```

means:

```text
Repository/Image:
veriqta-api

Tag:
1.0.0
```

Tags help humans identify versions or variants.

---

# 28. `latest` Is Just a Tag

This is extremely important.

Many beginners think:

```text
latest
↓
Automatically means newest image
```

That is incorrect.

`latest` is simply the default tag name Docker uses when no explicit tag is supplied in many Docker CLI contexts. Docker's current documentation states that if no tag is specified, `latest` is used by default.

It does not mean:

```text
highest semantic version
```

or:

```text
most recently approved production release
```

unless your own automation deliberately makes it mean that.

---

# 29. Why `latest` Can Be Dangerous

Suppose Monday:

```text
latest
↓
Image A
```

Tuesday:

```text
latest
↓
Image B
```

Wednesday:

```text
latest
↓
Image C
```

Now a deployment configuration contains:

```text
veriqta-api:latest
```

Question:

```text
Which exact image was deployed Tuesday?
```

The tag alone may no longer provide enough evidence.

This is why production systems should use stronger image identity practices.

---

# 30. What Is an Image Digest?

Container images can also be identified by a content digest.

A digest commonly looks like:

```text
sha256:abcd1234...
```

Conceptually:

```text
Image Content
↓
Cryptographic Hash
↓
Digest
```

Unlike a mutable tag:

```text
production
```

a digest identifies content.

Conceptually:

```text
veriqta-api:production
↓
Can potentially point to different image content over time
```

while:

```text
veriqta-api@sha256:...
↓
Specific image content
```

---

# 31. Tag vs Digest

Compare:

```text
TAG

veriqta-api:1.0.0
```

with:

```text
DIGEST

veriqta-api@sha256:abcdef...
```

A tag is:

```text
Human-readable reference
```

A digest is:

```text
Content-addressed identity
```

A tag can potentially be moved.

A digest changes when the referenced content changes.

---

# 32. Production Principle

A strong production pattern is:

```text
Human-friendly version
+
Immutable digest
```

For example:

```text
Version:
1.4.2

Digest:
sha256:abc...
```

Then:

```text
Release System
↓
1.4.2
↓
Verified digest
↓
Deployment
```

This gives you human readability and stronger immutable identity.

The general structure is:

```bash

```

```text

```

---

# 37. Username and Token

Authentication may use:

```text
Username
+
Access Token / Credential
```

Do not put your token directly into:

```text
Dockerfile
```

or:

```text
Git repository
```

or:

```text
shell script committed to Git
```

A container-registry credential is a secret.

Treat it accordingly.

---

# 38. Avoid Passwords on the Command Line

A command like:

```bash
docker login registry.example.com -u user -p supersecret
```

can expose the credential through shell history or process inspection.

A safer automation pattern is:

```bash
printf '%s' "$REGISTRY_TOKEN" | docker login registry.example.com \
  --username "$REGISTRY_USER" \
  --password-stdin
```

Conceptually:

```text
Secret Store
↓
Environment
↓
Standard Input
↓
docker login
```

This avoids placing the secret directly in the command argument list.

---

# 39. Check Login Without Printing Secrets

After login, test with a harmless operation such as:

```bash
docker pull <known-image>
```

or inspect Docker's authenticated behavior.

Do not verify a token by printing it:

```bash
echo "$REGISTRY_TOKEN"
```

Use:

```bash
test -n "$REGISTRY_TOKEN" && echo "Registry token is set"
```

when you only need to confirm the variable exists.

---

# 40. Docker Credential Storage

Docker stores login configuration according to Docker client configuration and credential-helper settings.

A Docker configuration file commonly exists under:

```text
~/.docker/config.json
```

Do not casually copy this file into:

* Git
* CI artifacts
* Shared drives
* Docker images

It may contain credential-related configuration.

# 44. Understand Every Dockerfile Instruction

## `FROM`

```dockerfile
FROM python:3.13-slim
```

Selects the base image.

## `WORKDIR`

```dockerfile
WORKDIR /app
```

Sets the working directory for subsequent instructions and runtime operations where applicable.

## `COPY`

```dockerfile
COPY app.py .
```

Copies the local application file into the image.

Because the working directory is:

```text
/app
```

the result is:

```text
/app/app.py
```

## `CMD`

```dockerfile
CMD ["python", "app.py"]
```

defines the default command that runs when a container starts from this image, unless overridden.

# 45. The Build Context

Run:

```bash
docker build .
```

The final:

```text
.
```

means:

```text
Current directory
↓
Docker build context
```

Docker's documentation describes this final path as the build context where Docker finds the Dockerfile and files referenced by the build.

This is important because Docker cannot normally copy arbitrary files from outside the build context using a simple Dockerfile `COPY`.

---

# 46. Build With a Tag

Instead of building an anonymous image, use:

```bash

```

```text
docker
↓
Docker CLI

build
↓
Build image

-t
↓
Assign tag/name

veriqta-container-demo:1.0.0
↓
Image name + tag

.
↓
Build context
```

Docker's `-t`/`--tag` option assigns the image reference during the build.

# 51. Images and Image IDs

Docker may show an image ID.

Example:

```text
IMAGE ID
abc123...
```

The image ID identifies local image content/state, but registry workflows increasingly rely on content digests to identify pushed image manifests.

Do not confuse:

```text
Image ID
```

with:

```text
Registry Digest
```

They are related to content identity but serve different contexts.

# 52. Tagging an Existing Image

Suppose we built:

```text
veriqta-container-demo:1.0.0
```

Now we need to prepare it for our Artifactory registry.

Use:

```bash
docker tag \
  veriqta-container-demo:1.0.0 \
  <ARTIFACTORY-IMAGE-REFERENCE>:1.0.0
```

For example, depending on your environment, the destination reference may conceptually resemble:

```text
company.jfrog.io/veriqta-docker-local/veriqta-container-demo:1.0.0
```

Do not blindly use this exact syntax without checking your Artifactory Docker URL format.

# 53. What `docker tag` Actually Does

`docker tag` does not rebuild the image.

Conceptually:

```text
Image Content
↓
Reference A

+
Reference B
```

For example:

```text
veriqta-container-demo:1.0.0
```

and:

```text
registry/veriqta-container-demo:1.0.0
```

can reference the same underlying local image content.

This is important.

Tagging is:

```text
Naming
```

not:

```text
Rebuilding
```

# 54. Why the Registry Host Is Part of the Image Name


with:

```text

```

The second explicitly identifies the registry host.

Docker's documented image name format includes the registry host as an optional first component.

For pushing to Artifactory, your image reference must identify the correct registry/repository endpoint according to your JFrog configuration.

```text

↓
```

# 67. Why Base Images Are Dependencies

A Dockerfile may contain:

```dockerfile
FROM python:3.13-slim
```

Your image depends on that base image.

If the base image changes:

```text
Our Application Code
↓
Same

Base Image
↓
Different
```

the resulting image may differ.

Therefore base-image identity is part of build reproducibility.

---

# 68. Mutable Base Tags

Suppose your Dockerfile says:

```dockerfile
FROM python:3.13-slim
```

A tag may eventually be updated by the upstream publisher.

Two builds at different times could potentially retrieve different content under a mutable tag.

Conceptually:

```text
Build Monday
↓
python:3.13-slim
↓
Digest A

Build Later
↓
python:3.13-slim
↓
Digest B
```

This matters for highly reproducible builds.

---

# 69. Pinning Base Images by Digest

A stronger reproducibility pattern can use:

```dockerfile
FROM python:3.13-slim@sha256:...
```

Conceptually:

```text
Human-readable tag
+
Immutable digest
```

This gives developers context while pinning exact image content.

However, pinned base images must still be updated deliberately when security patches are needed.

Immutability does not mean:

```text
Never update dependencies.
```

It means:

```text
Update deliberately
↓
Create new build
↓
Test
↓
Release
```

# 75. Do Not Build Separately for Every Environment

Bad:

```text
Git Commit
├── Build DEV image
├── Build STAGING image
└── Build PROD image
```

Now the production artifact may not be the one tested.

Better:

```text
Git Commit
↓
Build Image Once
↓
Development Validation
↓
Staging
↓
Production
```

Use environment-specific configuration at runtime where appropriate.

# 76. Do Not Bake Environment Secrets Into Images

Bad Dockerfile:

```dockerfile
ENV DB_PASSWORD=SuperSecretPassword
```

Bad:

```dockerfile
COPY production-secrets.env /app/
```

Why?

The secret can become embedded in image history/layers or otherwise distributed with the image.

Better architecture:

```text
Container Image
↓
Application

Runtime
↓
Secret Manager / Kubernetes Secret / Approved Mechanism
↓
Credentials
```

Container images and secret storage solve different problems.

---

# 77. Dockerfile Layers and Secrets

Suppose:

```dockerfile
COPY secret.txt /tmp/secret.txt
RUN use-secret
RUN rm /tmp/secret.txt
```

A beginner might think:

```text
Secret deleted
↓
Safe
```

But the secret may have existed in an earlier image layer.

This is why build secrets require appropriate Docker build-secret mechanisms rather than copying credentials into normal layers.

Never rely on a later `rm` instruction to erase a secret from earlier image history.


# 80. Build Cache

Docker can reuse previous build results.

Consider:

```dockerfile
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
```

If application source changes but:

```text
requirements.txt
```

does not, Docker may be able to reuse the dependency installation layer.

This can make builds faster.

---

# 81. Dockerfile Order Matters

Compare:

```dockerfile
COPY . .
RUN pip install -r requirements.txt
```

with:

```dockerfile
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
```

In many projects, the second can make better use of caching because ordinary source-code changes do not automatically invalidate the dependency installation layer.

This is an example of how Dockerfile structure affects build efficiency.

* Slower pulls
* More storage consumption
* Longer deployments

* Longer vulnerability scans

For example, a production application image often does not need:

```text
compilers
editors
debug packages
source-control tools
```

unless there is a specific runtime need.

# 89. Image Pull Policies

```text
↓
```

Bad:

```text

↓
```

* Time-based behavior
* Network dependencies
* Build tools

# 98. Retention

Container registries can grow quickly.

You may accumulate:

```text
build-1
build-2
build-3
...
build-5000
```

Development images may need shorter retention.

Release images may need longer retention.

Retention should consider:

* Current deployments
* Rollback requirements
* Compliance
* Active environments
* Release support windows
* Storage cost
* Audit requirements

Do not simply:

```text

```

without understanding what still references those images.

# 99. Image Garbage Collection Awareness

Container registries can contain shared layer data.

Deleting a tag does not necessarily mean every underlying binary layer is immediately physically erased.

Repository storage and garbage-collection behavior can be more complex because layers may be referenced by multiple manifests/images.

This is one reason registry cleanup should use supported repository lifecycle mechanisms rather than manually manipulating backend storage.

# 103. Troubleshooting: Login Fails

Command:

```bash
docker login <registry>
```

Investigate:

1. Correct registry host?
2. Correct repository URL/access method?
3. Username correct?
4. Token correct?
5. Token expired?
6. Network reachable?
7. TLS valid?
8. Is authentication expected at host or repository-path level for your configuration?

JFrog Docker URL formats vary by environment, so confirm the endpoint rather than guessing.

# 104. Troubleshooting: 401 Unauthorized

```text
Docker
↓
Registry
↓
Identity not authenticated successfully
```

Possible causes:

* Wrong credentials
* Missing credentials
* Expired token
* Wrong host
* Authentication configuration mismatch

Do not give the user more permissions yet.

401 usually means you should investigate authentication first.

# 105. Troubleshooting: 403 Forbidden

```text
Authentication
↓
Succeeded

↓
Not authorized
```


```text
↓
Allowed

↓
```

# 110. Troubleshooting: Push Goes to Docker Hub

This is a common beginner mistake.

Suppose:

```text
veriqta-api:1.0.0
```

has no explicit Artifactory host.

If you push under a normal Docker reference without the intended registry host, Docker may treat it as a Docker Hub reference.

Correct workflow:

```text

↓
Tag with Artifactory Registry Reference
↓
docker push exact Artifactory reference
```

Always inspect:

```bash
docker image ls
```

before pushing.

# 115. Troubleshooting Docker Hub Rate Limits

```text

↓

↓
Rate limit
```

the problem is not your application image.

# 141. Rollback

Suppose:

```text
4.7.3
```

causes an incident.

If:

```text
4.7.2
```

still exists with its original digest:

```text
Release Repository
├── 4.7.2 → sha256:AAA...
└── 4.7.3 → sha256:BBB...
```

rollback can intentionally deploy:

```text
4.7.2
```

or its exact digest.

This is far safer than:


And you should understand the two major Artifactory Docker flows.

## Dependency Flow

```text
Docker Hub
↓
Artifactory Remote Repository
↓
Artifactory Virtual Repository
↓
Docker Build
↓
Base Image
```

## Release Flow

```text
Source
↓
Docker Build
↓
Container Image
↓
Version + Digest
↓
Artifactory Local Repository
↓
Test / Approval
↓
Deployment
```

The central production rule from this part is:

```text
BUILD THE IMAGE ONCE
↓
IDENTIFY IT BY VERSION AND DIGEST
↓
TEST THAT IMAGE
↓
PROMOTE THAT IMAGE
↓
DEPLOY THAT IMAGE
```

Not:

```text
BUILD FOR DEV
↓
BUILD AGAIN FOR STAGING
↓
BUILD AGAIN FOR PRODUCTION
```

And not:

```text
DEPLOY :latest
↓
HOPE IT MEANS WHAT YOU THINK
```

A production container image should have an identity that you can trace:

```text
SOURCE COMMIT
↓
BUILD
↓
IMAGE
↓
VERSION
↓
DIGEST
↓
ARTIFACTORY
↓
DEPLOYMENT
```

That is the foundation of professional container-image management with JFrog Artifactory.
