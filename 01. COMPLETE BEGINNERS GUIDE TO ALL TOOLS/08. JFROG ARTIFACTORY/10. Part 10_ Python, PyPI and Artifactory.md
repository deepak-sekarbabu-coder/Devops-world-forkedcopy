# Part 10: Python, PyPI and Artifactory

Part 9 showed how npm uses Artifactory as a controlled registry layer for JavaScript packages. Python follows the same broad pattern, but the terminology and packaging formats are different.

The architecture for this part is:

```text
Python Code
↓
Python Package
↓
Build
↓
Wheel / Source Distribution
↓
Artifactory
↓
pip
↓
Application
```

By the end of this part, you should be able to explain how Python code becomes a distributable package, understand PyPI and `pip`, build your own package, publish it to an Artifactory local PyPI repository, proxy public packages through a remote repository, consume everything through a virtual repository, and troubleshoot common Python package failures.

# 2. Python Code Is Not Automatically a Python Package

Suppose you create:

```text
calculator.py
```

containing:

```python
def add(a, b):
    return a + b
```

This is Python source code.

It is not automatically a package that other teams can retrieve from a package repository.

There is a lifecycle:

```text
Python Source
↓
Organize Project
↓
Add Package Metadata
↓
Build
↓
Distribution Files
↓
Publish
↓
Package Repository
↓
Install
```

Artifactory becomes important near the publishing, storage, and distribution stages.

# 3. Modules vs Packages

This distinction is important.

## Module

A Python module is typically a Python source file that can be imported.

Example:

```text
calculator.py
```

Contents:

```python
def add(a, b):
    return a + b
```

Another Python file can use it:

```python
import calculator

print(calculator.add(2, 3))
```

Conceptually:

```text
calculator.py
↓
Python Module
```

## Package

A Python package organizes importable Python code under a package namespace, often across multiple modules.

For example:

```text
veriqta_tools/
├── __init__.py
├── logger.py
└── config.py
```

Conceptually:

```text
veriqta_tools
├── logger module
└── config module
```

A developer might use:

```python
from veriqta_tools.logger import log
```

There is another important distinction.

A Python package used by Python's import system and a distributable project uploaded to a package index are related concepts, but they are not exactly the same thing.

A distribution can contain one or more import packages or modules.

For example:

```text
Distribution project
↓
veriqta-tools
↓
Contains
↓
veriqta_tools/
```

This distinction becomes important when working with PyPI and Artifactory.

# 4. What Is Python Packaging?

Python packaging is the process of preparing Python software so it can be distributed and installed consistently.

Instead of manually doing this:

```text
Developer A
↓
Copies logger.py
↓
Emails it to Developer B
↓
Developer B copies it into application
↓
Developer C has another copy
```

we want:

```text
Logger Source
↓
Package
↓
Version
↓
Artifactory
↓
pip install
↓
Applications
```

For example:

```text
veriqta-tools 1.0.0
```

can become a reusable, versioned software distribution.

---

# 5. Why Package Python Code?

Imagine your organization has ten Python applications.

All ten require the same internal logging code.

Bad approach:

```text
Application A → copied logger.py
Application B → copied logger.py
Application C → copied logger.py
...
```

Eventually:

```text
App A → logger version 1
App B → modified copy
App C → old copy
App D → nobody knows
```

A package-based approach is:

```text
veriqta-tools
↓
Version 1.0.0
↓
Artifactory
├── Application A
├── Application B
├── Application C
└── Application D
```

Applications can deliberately declare which version they need.

# 6. What Is PyPI?

PyPI stands for the Python Package Index.

It is the main public package index used by the Python ecosystem.

It contains publicly distributed Python projects.

Conceptually:

```text
Python Developer
↓
pip
↓
PyPI
↓
Public Python Package
```

You might install a public package with:

```bash
python3 -m pip install requests
```

The `requests` project provides a widely used Python HTTP client library.

Without Artifactory, the flow can be:

```text
Developer
↓
pip
↓
Public PyPI
```

With Artifactory:

```text
Developer
↓
pip
↓
Artifactory
↓
PyPI
```

# 12. What Is a Python Virtual Environment?

A virtual environment gives a Python project an isolated environment for installed packages.

Without isolation:

```text

├── Project A dependencies
├── Project B dependencies
└── Project C dependencies
```

This can create conflicts.

Instead:

```text

↓

↓
Dependencies A

Project B
↓
Virtual Environment B
↓
Dependencies B
```

For example:

```text
Project A → package-x 1.x
Project B → package-x 2.x
```

They can be isolated from one another.

# 15. Dependencies in Python

A Python project can depend on other Python distributions.

Suppose:

```text
Your Application
↓
requests
```

But `requests` itself has dependencies.

Conceptually:

```text
Your Application
↓
requests
├── Dependency A
├── Dependency B
├── Dependency C
└── Dependency D
```

The exact dependency set can change across package versions.

Therefore:

```text
One direct dependency
≠
One installed distribution
```

This is the same dependency-tree concept you encountered with Maven and npm.

---

# 16. Direct vs Transitive Dependencies

Suppose your application explicitly requires:

```text
package-a
```

and `package-a` requires:

```text
package-b
```

Then:

```text
Application
↓
package-a
↓
package-b
```

`package-a` is a direct dependency.

`package-b` is a transitive dependency from your application's perspective.

This matters during troubleshooting because the package producing an error may not appear directly in your application code.

---

# 17. Package Versions

Python packages have versions.

Examples:

```text
1.0.0
1.0.1
1.2.0
2.0.0
```

An application may require an exact version:

```text
requests==2.x.x
```

or a range, depending on the dependency specification.

Do not copy arbitrary example version numbers into production configurations.

Always verify what your project actually requires.

---

# 18. Why Versions Matter

Imagine:

```text
Application A
↓
veriqta-tools 1.0.0
```

Then the internal package changes.

A new release becomes:

```text
veriqta-tools 1.1.0
```

Application A can continue using:

```text
1.0.0
```

while another application adopts:

```text
1.1.0
```

This creates controlled evolution.

Without versions:

```text
"latest file"
↓
Changed repeatedly
↓
Nobody knows what was deployed
```

That destroys traceability.

# 19. Requirements Files

Python projects commonly use requirements files to declare dependencies.

Example:

```text
requirements.txt
```

Contents might include:

```text
requests==<chosen-version>
```

Install:

```bash
python -m pip install -r requirements.txt
```

The `-r` option tells pip to read requirements from the specified file.

Conceptually:

```text
requirements.txt
↓
pip
↓
Resolve dependencies
↓
Install
```

---

# 20. Exact Versions vs Version Ranges

An exact requirement:

```text
package-name==1.2.3
```

means:

```text
Install 1.2.3
```

A range might look like:

```text
package-name>=1.2,<2
```

which means:

```text
At least 1.2
but
less than 2
```

These choices affect reproducibility.

Broad ranges provide flexibility.

Exact versions provide stronger control over the direct version requested.

However, fully reproducible dependency management requires considering the complete dependency graph, not only one direct requirement.

# 21. Source Code vs Distribution

Suppose we create:

```text
veriqta_tools/
└── logger.py
```

That is source code.

To distribute the project through a package repository, we build distribution artifacts.

Two important Python distribution formats are:

```text
Wheel
```

and:

```text
Source Distribution
```

often shortened to:

```text
sdist
```

---

# 22. What Is a Wheel?

A wheel is a built distribution format for Python packages.

Wheel files use:

```text
.whl
```

For example, a package build might produce something resembling:

```text
veriqta_tools-1.0.0-py3-none-any.whl
```

The filename carries information about the distribution.

At a high level:

```text
Python Project
↓
Build
↓
Wheel
↓
pip
↓
Installation
```

Wheels can make installation easier because pip can install the prepared distribution without rebuilding the project from source in the same way an sdist may require.

---

# 23. What Is a Source Distribution?

A source distribution contains the source material needed to distribute and potentially build/install the project.

It commonly uses a compressed archive such as:

```text
.tar.gz
```

Conceptually:

```text
Python Project
↓
Build sdist
↓
Source Archive
↓
pip
↓
Build/install process
```

You may see:

```text
veriqta_tools-1.0.0.tar.gz
```

---

# 24. Wheel vs Source Distribution

At a beginner level:

```text
Wheel
↓
Built distribution
↓
Usually easier/faster for pip to install when compatible
```

while:

```text
Source Distribution
↓
Source-based distribution
↓
May require build steps on installation
```

This matters because an installation failure can sometimes be caused by pip being unable to use an appropriate wheel and falling back to building from source.

---

# 25. Why Source Builds Can Fail

Suppose a package contains native code.

If pip must build it from source, the environment may need:

* A compiler
* Development headers
* System libraries
* Build tooling
* Compatible Python headers

Therefore:

```text
Package exists
↓
Download succeeds
↓
Build fails
```

is possible.

Do not automatically blame Artifactory.

The repository may have successfully delivered the distribution.

The failure may happen later during the local build stage.

---

# 26. Understanding the Installation Stages

This distinction is extremely important for troubleshooting:

```text
pip
↓
Find package
↓
Resolve version
↓
Download distribution
↓
Build if required
↓
Install
↓
Import/use
```

A failure at:

```text
Find package
```

is different from:

```text
Build package
```

which is different from:

```text
Import package
```

Always identify the failure stage.

# 27. What Is `pyproject.toml`?

Modern Python projects commonly use:

```text
pyproject.toml
```

for project and build configuration.

TOML is a configuration format.

A basic project might contain:

```text
veriqta-python-tools/
├── pyproject.toml
└── src/
    └── veriqta_tools/
        ├── __init__.py
        └── logger.py
```

The `pyproject.toml` file can describe:

* Build system
* Project name
* Version
* Description
* Python requirements
* Dependencies
* Other project metadata

---

# 28. Why `pyproject.toml` Exists

Packaging tools need structured information.

They need answers such as:

```text
What is this project called?
What version is it?
Which build backend should build it?
Which Python versions does it support?
What dependencies does it require?
```

`pyproject.toml` provides standardized configuration for modern Python project tooling.

---

# 29. TOML Basics

A simple TOML section looks like:

```toml
[project]
name = "veriqta-tools"
version = "1.0.0"
```

Here:

```text
[project]
```

starts a table/section.

Then:

```text
name = "veriqta-tools"
```

assigns a value to `name`.

And:

```text
version = "1.0.0"
```

assigns the project version.

TOML syntax is not YAML.

Do not mix indentation or syntax rules between configuration formats.

---

# 34. Understanding `[build-system]`

This section:

```toml
[build-system]
```

describes how the project should be built.

We specify:

```toml
requires = ["setuptools"]
```

which tells build tooling that setuptools is required for the build environment.

Then:

```toml
build-backend = "setuptools.build_meta"
```

identifies the build backend.

Conceptually:

```text
Python Project
↓
Build Frontend
↓
Build Backend
↓
Wheel / sdist
```

---

# 35. Build Frontend vs Build Backend

This can confuse beginners.

A build frontend is a tool you invoke to request a build.

A build backend performs the packaging work according to the project configuration.

For this lab we will use:

```text
python -m build
```

The `build` tool acts as the frontend.

Our configured backend is:

```text
setuptools.build_meta
```

Conceptually:

```text
Developer
↓
python -m build
↓
Build frontend
↓
setuptools build backend
↓
Distribution files
```

```text

```

might contain:

```text

```

```text

↓
Publish
↓

```

---

# 44. Remote PyPI Repository

A remote PyPI repository proxies an upstream package source such as public PyPI.

Conceptually:

```text
pip
↓
Artifactory
↓
pypi-remote
↓
Public PyPI
```

When a requested public package is not cached:

```text
Request
↓
Artifactory Remote Repository
↓
Upstream PyPI
↓
Download
↓
Cache
↓
Return to pip
```

---

# 45. Virtual PyPI Repository

A virtual repository provides one logical endpoint over multiple repositories.

Architecture:

```text
                     pip
                      ↓
                veriqta-pypi
                 Virtual Repo
                 /          \
                ↓            ↓
veriqta-pypi-local       pypi-remote
Private Packages              ↓
                           Public PyPI
```

Now applications do not need to understand the physical repository topology.

They can use:

```text
veriqta-pypi
```

for dependency consumption.

---

# 46. Why Virtual Repositories Matter

Suppose an application requires:

```text
veriqta-tools
```

and:

```text
requests
```

One is private.

One is public.

Without a unified architecture:

```text
Where do I find veriqta-tools?
Where do I find requests?
Which index wins?
How should CI be configured?
```

With Artifactory:

```text
pip
↓
veriqta-pypi
├── veriqta-tools
│   ↓
│   Local
│
└── requests
    ↓
    Remote
    ↓
    Public PyPI
```

One controlled repository layer handles both.

---

# 47. Why This Is Better Than Bypassing Artifactory

Consider:

```text

Developer B → PyPI
CI Runner A → PyPI
CI Runner B → PyPI
Production Build → PyPI
```

versus:

```text
Developers
+
CI
↓
Artifactory
↓
Controlled upstream access
```

Artifactory provides capabilities such as:

* Central repository configuration
* Caching
* Private package hosting
* Access control
* Metadata
* Traceability
* Consistent client endpoints
* Integration with the wider JFrog platform

# 73. Dependency Resolution

Suppose:

```text
Application
├── veriqta-tools
└── package-a
```

```text

↓

```

```text

```

Now the resolver has incompatible requirements.

Conceptually:

```text
Dependency A
↓
package-b >= 2

Dependency C
↓
package-b < 2

↓
Resolution failure
```

This is not necessarily an Artifactory failure.

Artifactory can successfully provide package metadata while pip correctly determines that no compatible dependency set exists.

The resolver is protecting you from installing an internally inconsistent dependency set.

# 106. Dependency Confusion Awareness

Imagine your organization uses a private package called:

```text
veriqta-internal-auth
```

If package resolution is configured carelessly across private and public indexes, an attacker might attempt to publish a package with a confusing or matching name/version to a public repository.

This class of risk is one reason repository resolution design matters.

A safer architecture emphasizes deliberate, controlled repository configuration:

```text
pip
↓
Controlled Artifactory Virtual Repository
↓
Defined repository resolution
```

rather than casually combining unrelated indexes.

# 107. Be Careful With `--extra-index-url`

pip supports additional indexes, but careless use can introduce unexpected package-selection behavior.

Do not think:

```text
Private index
+
Public index
↓
pip will always prefer my private package
```

as a guaranteed security model.

For enterprise use, design repository resolution intentionally, often by using Artifactory as the controlled aggregation/proxy layer.

This reduces the need for clients to make trust decisions across multiple independent package indexes.

# 108. Least Privilege

A normal application build may need:

```text

```

It does not automatically need:

```text
Publish
Delete
Administer repositories
Manage users
```

A release pipeline may need:

```text

+

```

Separate responsibilities:

```text
Build Identity
↓
Read

Release Identity
↓
Read + Publish

Administrator
↓
Repository Administration
```

Do not use administrator credentials in ordinary CI pipelines.
