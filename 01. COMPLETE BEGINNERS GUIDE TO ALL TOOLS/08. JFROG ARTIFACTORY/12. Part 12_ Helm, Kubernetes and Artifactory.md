# Part 12: Helm, Kubernetes and Artifactory

In Part 11, you learned how an application moves through this lifecycle:

```text
Source
↓
Docker Build
↓
Container Image
↓
Artifactory
↓
Deployment
```

Now we need to answer the next question:

**How does Kubernetes know what to deploy, how to deploy it, and where to retrieve the container image?**

A container image contains the application runtime artifact.

But Kubernetes also needs deployment instructions.

For example:

```text
Which image should run?

How many replicas?

Which ports should be exposed?

What CPU and memory should the container receive?

Which environment variables are required?

Which Service should expose the Pods?

Which health checks should Kubernetes perform?

Which registry credentials are required?

How should the application be upgraded?
```

This introduces another important artifact:

```text
Helm Chart
```

Our application delivery model now becomes:

```text
                    Application
                        ↓
              ┌─────────┴─────────┐
              ↓                   ↓
         Docker Image         Helm Chart
              ↓                   ↓
         Artifactory          Artifactory
              └─────────┬─────────┘
                        ↓
                    Kubernetes
                        ↓
                       Pods
```

This part connects:

```text
Application Packaging
+
Artifact Management
+
Container Registries
+
Helm
+
Kubernetes
+
Deployment
```

By the end, you should understand how Artifactory becomes part of a complete Kubernetes software-delivery workflow.

---

# 1. What Kubernetes Actually Needs

Kubernetes does not normally build your application.

This is one of the first concepts to understand.

Kubernetes consumes artifacts that were already produced.

A simplified pipeline is:

```text
Developer
↓
Git
↓
CI Pipeline
↓
Build
↓
Test
↓
Container Image
↓
Artifact Registry
↓
Kubernetes
```

Kubernetes receives instructions describing:

```text
Run this image
Using this configuration
With this number of replicas
Expose it this way
Apply these health checks
Use these resources
```

Kubernetes then attempts to make the cluster match that desired state.

---

# 2. Kubernetes Is Not Your Artifact Repository

Do not think:

```text
Build Image
↓
Store Image Inside Kubernetes
```

Kubernetes is not normally the permanent storage location for application container images.

Instead:

```text
Build
↓
Registry
↓
Kubernetes retrieves image
↓
Node runs container
```

For our architecture:

```text
Build
↓
JFrog Artifactory
↓
Kubernetes
↓
Container Runtime
↓
Container
```

Artifactory stores and distributes the image.

Kubernetes orchestrates workloads created from that image.

---

# 3. Two Major Artifact Requirements

For the workflow in this part, we primarily care about two artifact categories.

## Artifact 1: Container Image

Example:

```text
veriqta-api:2.4.1
```

Contains:

```text
Application
Runtime
Libraries
Filesystem content
Container configuration
```

## Artifact 2: Deployment Package

In this part, that will be a Helm chart.

Example:

```text
veriqta-api
Chart version: 1.3.0
```

It contains Kubernetes deployment templates and associated configuration defaults.

So:

```text
APPLICATION ARTIFACT
↓
Container Image

DEPLOYMENT ARTIFACT
↓
Helm Chart
```

Do not confuse them.

---

# 4. Container Images and Kubernetes Manifests

Without Helm, Kubernetes configuration is commonly written as YAML manifests.

Example:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: veriqta-api
spec:
  replicas: 2
  selector:
    matchLabels:
      app: veriqta-api
  template:
    metadata:
      labels:
        app: veriqta-api
    spec:
      containers:
        - name: veriqta-api
          image: registry.example.com/veriqta-api:2.4.1
          ports:
            - containerPort: 8080
```

This describes a Kubernetes Deployment.

---

# 5. Understanding the Manifest

Let's break it down.

## `apiVersion`

```yaml
apiVersion: apps/v1
```

Tells Kubernetes which API version defines this resource.

## `kind`

```yaml
kind: Deployment
```

Tells Kubernetes which resource type we want.

In this case:

```text
Deployment
```

## `metadata`

```yaml
metadata:
  name: veriqta-api
```

Names the Kubernetes object.

## `replicas`

```yaml
replicas: 2
```

Requests two Pod replicas.

Conceptually:

```text
Deployment
↓
ReplicaSet
↓
Pod 1
Pod 2
```

## `containers`

```yaml
containers:
```

Defines the containers inside each Pod.

## `image`

```yaml
image: registry.example.com/veriqta-api:2.4.1
```

Tells Kubernetes which container image should be used.

That line creates the connection between:

```text
Kubernetes
↓
Container Registry
```

---

# 6. Kubernetes Image Retrieval

When Kubernetes schedules a Pod:

```text
Deployment
↓
Pod Required
↓
Scheduler selects Node
↓
Node's kubelet
↓
Container Runtime
↓
Registry
↓
Pull Image
↓
Create Container
↓
Start Application
```

If the image is stored in Artifactory:

```text
Kubernetes Node
↓
Artifactory
↓
Container Image
↓
Node
↓
Pod
```

This means Artifactory availability, registry authentication, network access, repository permissions, and the image reference can all affect Pod startup.

---

# 7. Kubernetes Does Not Magically Find Your Image

Suppose your image exists as:

```text
company.jfrog.io/veriqta-docker-release/veriqta-api:2.4.1
```

but your Deployment says:

```yaml
image: veriqta-api:2.4.1
```

Those references may not mean the same thing.

The Kubernetes node needs the correct registry image reference.

Conceptually:

```text
Registry Host
+
Repository/Path
+
Image Name
+
Tag or Digest
```

must identify the intended artifact.

---

# 8. Why Deployment Manifests Need Version Control

Imagine this manifest:

```yaml
image: veriqta-api:latest
```

Later somebody changes:

```text
latest
```

to another image.

Your Git history may still show:

```yaml
image: veriqta-api:latest
```

for both deployments.

That makes it harder to answer:

```text
Which exact image was deployed?
```

A stronger manifest might use:

```yaml
image: registry.example.com/veriqta-api:2.4.1
```

Stronger still, when exact content identity is required:

```yaml
image: registry.example.com/veriqta-api@sha256:...
```

Now deployment configuration becomes part of artifact traceability.

---

# 9. Why Plain Kubernetes YAML Becomes Difficult

Imagine one application needs:

```text
Deployment
Service
ConfigMap
Ingress
ServiceAccount
HorizontalPodAutoscaler
NetworkPolicy
PodDisruptionBudget
```

Now imagine:

```text
20 applications
×
multiple environments
```

You may end up maintaining many YAML files with repeated values.

For example:

```text
development
↓
1 replica

staging
↓
2 replicas

production
↓
5 replicas
```

Or:

```text
development image
staging image
production image
```

Copying entire manifest directories for every environment can become difficult to maintain.

This is one reason Helm exists.

---

# 10. What Is Helm?

Helm is a package manager for Kubernetes.

Conceptually:

```text
Kubernetes YAML
+
Templates
+
Default Values
+
Chart Metadata
↓
Helm Chart
```

Helm helps package, configure, install, upgrade, and manage Kubernetes applications.

Instead of manually maintaining many almost-identical manifests, Helm allows you to create reusable templates.

---

# 11. Helm and the Package Managers You Already Know

You have already encountered:

```text
Java
↓
Maven

JavaScript
↓
npm

Python
↓
pip

Kubernetes
↓
Helm
```

The comparison is not perfect because Helm packages Kubernetes deployment definitions rather than ordinary application libraries.

But it provides a useful mental model.

---

# 12. What Is a Helm Chart?

A Helm chart is a package containing files required to describe a Kubernetes application.

A simple chart might look like:

```text
veriqta-api/
├── Chart.yaml
├── values.yaml
└── templates/
    ├── deployment.yaml
    └── service.yaml
```

Each file has a role.

---

# 13. `Chart.yaml`

Example:

```yaml
apiVersion: v2
name: veriqta-api
description: Helm chart for the VERIQTA API
type: application
version: 1.0.0
appVersion: "2.4.1"
```

This contains metadata about the chart.

---

# 14. `name`

```yaml
name: veriqta-api
```

The chart's name.

---

# 15. `version`

```yaml
version: 1.0.0
```

This is the **chart version**.

It identifies the version of the Helm chart package.

---

# 16. `appVersion`

```yaml
appVersion: "2.4.1"
```

This describes the version of the application represented by the chart.

This introduces an extremely important distinction.

```text
Chart Version
≠
Application Version
```

They may happen to match, but they describe different things.

---

# 17. Chart Version vs Application Version

Example:

```text
Chart Version:
1.3.0

Application Version:
2.4.1
```

Why?

Perhaps:

```text
Application code
↓
Did not change

Kubernetes configuration
↓
Changed
```

For example, you changed:

```text
CPU limits
Memory limits
Health probes
Service configuration
Ingress
Pod security configuration
```

The chart may need a new version even though the application image did not change.

---

# 18. Container Image Version Is Another Identity

Now we potentially have:

```text
Application Version:
2.4.1

Container Image Tag:
2.4.1

Container Image Digest:
sha256:...

Helm Chart Version:
1.3.0
```

These identifiers serve different purposes.

A production release record might therefore contain:

```text
Application:
veriqta-api

Git Commit:
abc1234

Build:
842

Image:
veriqta-api:2.4.1

Image Digest:
sha256:...

Helm Chart:
veriqta-api

Chart Version:
1.3.0
```

This is much stronger than:

```text
We deployed the latest version.
```

---

# 19. `values.yaml`

Helm charts commonly use:

```text
values.yaml
```

for default configuration values.

Example:

```yaml
replicaCount: 2

image:
  repository: registry.example.com/veriqta-api
  tag: "2.4.1"
  pullPolicy: IfNotPresent

service:
  type: ClusterIP
  port: 80
```

The template can refer to these values.

---

# 20. Helm Templates

Example:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}
spec:
  replicas: {{ .Values.replicaCount }}
  template:
    spec:
      containers:
        - name: veriqta-api
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
```

Do not panic about the braces.

```text
{{ ... }}
```

is Helm template syntax.

Helm replaces template expressions with values when rendering Kubernetes manifests.

---

# 21. Template Rendering

Suppose:

```yaml
replicaCount: 3

image:
  repository: registry.example.com/veriqta-api
  tag: "2.4.1"
```

The template:

```yaml
replicas: {{ .Values.replicaCount }}
```

becomes:

```yaml
replicas: 3
```

And:

```yaml
image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
```

becomes:

```yaml
image: "registry.example.com/veriqta-api:2.4.1"
```

Conceptually:

```text
Chart Templates
+
Values
↓
Helm Rendering
↓
Kubernetes YAML
```

# 22. Helm Does Not Replace Kubernetes

Helm does not become your Kubernetes cluster.

Helm produces/manages Kubernetes resources.

Conceptually:

```text
Helm Chart
↓
Helm
↓
Rendered Kubernetes Resources
↓
Kubernetes API
↓
Cluster
```

You still need to understand Kubernetes concepts.

If a Pod fails, knowing Helm alone is not enough.

```text

```

# 40. OCI Fundamentals

You will increasingly encounter:

```text
OCI
```

OCI means:

```text
Open Container Initiative
```

OCI defines specifications used across the container ecosystem.

Container registries are increasingly capable of storing more than conventional container images.

Helm supports storing and distributing charts using OCI-compatible registries.

Conceptually:

```text
OCI Registry
├── Container Images
└── Helm Charts
```

This can simplify artifact distribution architectures.

---

# 41. Traditional Helm vs OCI-Based Helm

You may encounter two broad patterns.

## Traditional Helm Repository

```text
Helm Client
↓
Helm Repository
↓
Chart Archive
```

## OCI Registry

```text
Helm Client
↓
OCI Registry
↓
Chart Artifact
```

Modern Helm workflows increasingly use OCI registries.

The commands and references differ, so do not mix traditional repository commands with OCI commands blindly.

---

# 42. Why OCI Matters to Artifactory

Artifactory already operates as a registry for container artifacts.

OCI support allows modern registry workflows to handle other OCI-compatible artifacts such as Helm charts where supported.

Conceptually:

```text
JFrog Platform
├── Docker / OCI Images
└── Helm / OCI Artifacts
```

Your organization may therefore choose a traditional Helm repository model, an OCI-based model, or a combination depending on platform design and compatibility requirements.

# 44. OCI Helm Workflow

```text
↓
```

# 45. Authenticate for OCI Helm Operations

Helm provides registry authentication commands for OCI registries.

Conceptually:

```bash

```

This authenticates Helm to the registry.

A secure automation approach should avoid exposing passwords or tokens in:

```text
Git
Shell history
CI logs
Helm values
Dockerfiles
```

The same secret-management principles from previous parts still apply.

# 48. Retrieve a Chart

For an OCI workflow, retrieval conceptually looks like:



# 50. Helm Release

The word:

```text
Release
```

has a specific meaning in Helm.

For example:

```bash

```

Here:

```text
Chart
↓
Package/template definition

Release
↓
Installed instance of that chart
```

You can install the same chart multiple times using different release names.

# 62. Creating a Registry Secret

A common command is:


# 63. `kubectl`

# 65. `docker-registry`

# 66. Secret Name

```text

```

is the Kubernetes Secret name.

The Pod later references this exact name.

# 67. `--docker-server`


### Security warning

* Process inspection

# 87. `imagePullPolicy`

A container specification may include:

```yaml
imagePullPolicy: IfNotPresent
```

Common values include:

```text
Always
IfNotPresent
Never
```

## `Always`

Kubernetes attempts to resolve/pull according to the image reference whenever the container starts, while still benefiting from local layer caching where applicable.

## `IfNotPresent`

Use a locally available image if present; otherwise pull it.

## `Never`

Do not pull. The image must already exist on the node.

This setting interacts with tag and digest strategies.

is easier to reason about.

# 94. `ImagePullBackOff`

One of the most common Kubernetes errors is:

```text
ImagePullBackOff
```

A beginner may think:

```text
My application crashed.
```

Not necessarily.

The container may never have started.

Conceptually:

```text
Pod Created
↓
Node Tries to Pull Image
↓
Image Pull Fails
↓
Kubernetes Retries
↓
Backoff
↓
ImagePullBackOff
```

---

# 95. What Does "BackOff" Mean?

Kubernetes does not necessarily retry a failed operation continuously at full speed.

After repeated failures, it waits increasingly between attempts.

Conceptually:

```text
Pull
↓
Fail
↓
Wait
↓
Retry
↓
Fail
↓
Wait Longer
↓
Retry
```

Hence:

```text
ImagePullBackOff
```

means Kubernetes is backing off repeated image-pull attempts.

---

# 96. `ErrImagePull`

You may first see:

```text
ErrImagePull
```

Then later:

```text

```

Conceptually:

```text
ErrImagePull
↓
Immediate pull failure

ImagePullBackOff
↓
Repeated failures now subject to retry backoff
```

The important question is:

**Why did the image pull fail?**

# 119. `ImagePullBackOff` vs `CrashLoopBackOff`

These are very different.

## `ImagePullBackOff`

```text
Registry
↓
Image cannot be retrieved
↓
Container never starts successfully
```

## `CrashLoopBackOff`

```text
Image retrieved
↓
Container starts
↓
Application/process crashes
↓
Kubernetes restarts it
↓
Repeated crash
```

Troubleshooting must begin at different layers.
