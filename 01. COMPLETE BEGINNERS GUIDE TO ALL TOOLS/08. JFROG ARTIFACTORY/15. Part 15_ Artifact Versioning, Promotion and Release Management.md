# Part 15: Artifact Versioning, Promotion and Release Management

In the previous parts, you learned how to:

```text
Build software
↓
Create artifacts
↓
Publish them to Artifactory
↓
Attach metadata
↓
Link artifacts to builds
↓
Trace artifacts back to source
```

Now we move into a different problem.

Suppose CI produces:

```text
veriqta-api 4.2.0
```

and Artifactory stores it successfully.

That does not automatically mean:

```text
The artifact is ready for production.
```

A production release usually moves through several lifecycle stages.

For example:

```text
Development
↓
Testing
↓
Staging
↓
Production
```

The central rule of this part is:

```text
BUILD ONCE
↓
VERIFY
↓
PROMOTE
↓
DEPLOY MANY
```

Not:

```text
BUILD FOR DEV
↓
BUILD AGAIN FOR TEST
↓
BUILD AGAIN FOR STAGING
↓
BUILD AGAIN FOR PROD
```

Our architecture is:

```text
Build Once
↓
DEV
↓
TEST
↓
STAGING
↓
PRODUCTION
```

with:

```text
THE SAME VERIFIED ARTIFACT
```

moving through the lifecycle.

* Development artifacts

# 1. Storing an Artifact Is Not the Same as Releasing It

Suppose CI generates:

```text
veriqta-api-4.2.0.tar.gz
```

and uploads it to Artifactory.

At that point, you know:

```text
Artifact exists.
```

You do not necessarily know:

```text
Tests passed.

Security validation passed.

Integration testing passed.

Operations approved it.

It is production-ready.

It is currently deployed.
```

Artifact existence and release readiness are separate states.

Think:

```text
BUILD OUTPUT
↓
CANDIDATE
↓
VALIDATED
↓
APPROVED
↓
RELEASED
↓
DEPLOYED
```

A good release-management process makes those states explicit.

---

# 2. What Is an Artifact Lifecycle?

An artifact lifecycle describes the stages an artifact passes through from creation until eventual retirement.

Example:

```text
Build
↓
Development
↓
Testing
↓
Staging
↓
Production
↓
Retained for rollback
↓
Archived or deleted
```

Not every organization uses exactly these stages.

You may encounter:

```text
snapshot
candidate
QA
UAT
pre-production
release
production
deprecated
archived
```

The names can differ.

The important question is:

```text
What does each state mean?
```

---

# 3. Development Artifacts

A development artifact is usually created during active engineering work.

Examples:

```text
veriqta-api-4.3.0-dev.41.tar.gz
veriqta-api-4.3.0-rc.1.tar.gz
my-library-2.0.0-SNAPSHOT.jar
```

Development artifacts may be:

* Created frequently
* Short-lived
* Not production-approved
* Used for testing
* Replaced by newer candidates
* Retained for less time than releases

Conceptually:

```text
Developer Change
↓
CI Build
↓
Development Artifact
↓
Testing
```

---

# 4. Development Does Not Mean Unimportant

Do not think:

```text
Development artifact
=
random disposable file
```

Even development artifacts can require:

```text
Version
Build number
Commit
Checksum
Metadata
Repository
```

because engineers may need to answer:

```text
Which candidate failed?

Which build introduced this bug?

Which artifact passed integration testing?
```

Development artifacts still benefit from traceability.

---

# 5. Snapshot Concept

You may encounter:

```text
SNAPSHOT
```

especially in Maven ecosystems.

For example:

```text
4.3.0-SNAPSHOT
```

Conceptually, this represents:

```text
Development toward 4.3.0
```

rather than:

```text
Final immutable 4.3.0 release.
```

Snapshot semantics can be package-system specific.

Do not assume every ecosystem treats:

```text
SNAPSHOT
```

the same way Maven does.

---

# 6. Maven Snapshot Reminder

In Maven:

```text
4.3.0-SNAPSHOT
```

can represent a changing development version.

Repository systems may internally store timestamped snapshot builds.

Conceptually:

```text
4.3.0-SNAPSHOT
↓
Development stream
↓
Build A
Build B
Build C
```

whereas:

```text
4.3.0
```

should normally identify one release.

---

# 7. Snapshot vs Release

A useful mental model:

```text
SNAPSHOT
↓
Development
↓
May evolve

RELEASE
↓
Published milestone
↓
Should remain stable
```

Do not treat:

```text
4.3.0
```

like:

```text
whatever today's build happens to contain.
```

A release version needs durable meaning.

---

# 8. Release Artifacts

A release artifact is a versioned artifact that has reached a defined release state.

Examples:

```text
veriqta-api-4.2.0.tar.gz
veriqta-api:4.2.0
com.veriqta:shared-utils:2.1.0
@veriqta/logger@3.4.0
veriqta-tools 1.8.2
```

A release should ideally have:

```text
Stable version
Stable checksum/digest
Build provenance
Approval history
Known source
Known dependencies
Known release status
```

---

# 9. Release Identity

A release is stronger when you can describe:

```text
Application:
veriqta-api

Version:
4.2.0

Build:
901

Commit:
f14c2a1

Artifact:
veriqta-api-4.2.0.tar.gz

SHA-256:
ABC...

Release Status:
approved
```

For a container:

```text
Image:
veriqta-api:4.2.0

Digest:
sha256:XYZ...
```

This is much more useful than:

```text
Production build
```

---

# 10. Semantic Versioning

Semantic Versioning commonly uses:

```text
MAJOR.MINOR.PATCH
```

For example:

```text
4.2.1
```

Breakdown:

```text
4
↓
MAJOR

2
↓
MINOR

1
↓
PATCH
```

---

# 11. MAJOR Version

A major version increase often indicates incompatible or breaking changes.

Example:

```text
4.8.2
↓
5.0.0
```

Conceptually:

```text
Existing consumers may need changes.
```

---

# 12. MINOR Version

A minor version increase commonly indicates new backward-compatible functionality.

Example:

```text
4.2.0
↓
4.3.0
```

Conceptually:

```text
New capability
+
existing compatible behavior retained
```

---

# 13. PATCH Version

A patch increase commonly indicates backward-compatible fixes.

Example:

```text
4.2.0
↓
4.2.1
```

Conceptually:

```text
Bug fix
```

---

# 14. Semantic Versioning Is a Contract

Do not think:

```text
SemVer
=
pretty numbering.
```

It communicates expectations.

For example:

```text
2.4.1
```

suggests something different from:

```text
3.0.0
```

Versioning should reflect release behavior and compatibility policy.

---

# 15. Pre-Release Versions

Semantic Versioning also supports pre-release identifiers.

Examples:

```text
4.3.0-alpha.1
4.3.0-beta.2
4.3.0-rc.1
```

A useful lifecycle could be:

```text
4.3.0-dev.51
↓
4.3.0-rc.1
↓
4.3.0-rc.2
↓
4.3.0
```

The exact naming convention should be consistent across your organization.

---

# 16. Release Candidate

A release candidate represents software believed to be close to the final release.

Example:

```text
4.3.0-rc.1
```

Conceptually:

```text
Built
↓
Candidate
↓
Integration Test
↓
Staging
↓
Approval
↓
Release
```

But be careful.

If:

```text
4.3.0-rc.1
```

is tested and then:

```text
4.3.0
```

is created by rebuilding source again, you may have changed the artifact.

This brings us back to promotion.

---

# 17. Immutable Releases

An immutable release means:

```text
Once released
↓
Its content does not change.
```

Suppose:

```text
veriqta-api 4.2.0
```

has:

```text
SHA-256 = ABC
```

Tomorrow, `4.2.0` should still mean:

```text
SHA-256 = ABC
```

Not:

```text
SHA-256 = XYZ
```

after somebody rebuilds and overwrites it.

---

# 18. Why Immutability Matters

Without immutability:

```text
4.2.0 on Monday
↓
Artifact A

4.2.0 on Friday
↓
Artifact B
```

Now:

```text
Which 4.2.0 ran in production?
```

becomes difficult.

With immutability:

```text
4.2.0
↓
Always Artifact A
```

and a fix becomes:

```text
4.2.1
```

not:

```text
overwrite 4.2.0.
```

---

# 19. Immutable Does Not Mean Never Change Software

It means:

```text
Do not mutate an existing release identity.
```

To change the software:

```text
Old:
4.2.0

Fix:
4.2.1
```

Then:

```text
4.2.0
↓
Old release preserved

4.2.1
↓
New release
```

This preserves history.

---

# 20. Build Once, Promote Many

The central production architecture:

```text
Git Commit
↓
Build Once
↓
Artifact A
↓
DEV
↓
TEST
↓
STAGING
↓
PRODUCTION
```

Every environment receives:

```text
Artifact A
```

not:

```text
Artifact A
Artifact B
Artifact C
Artifact D
```

---

# 21. Why Teams Promote Instead of Rebuild

Suppose staging tests:

```text
Artifact A
```

and approves it.

If production rebuilds:

```text
Artifact B
```

then:

```text
Artifact B
```

did not pass the exact staging test.

Even if source is identical, differences may come from:

```text
Dependency resolution
Compiler version
Base image
Build container
Timestamp
External downloads
Package-manager state
Architecture
Network behavior
Build scripts
```

Therefore:

```text
Promote tested binary
```

is safer than:

```text
Recreate supposedly equivalent binary.
```

---

# 22. Build Once Does Not Mean One File for Everything

Different artifact types may be created in one release pipeline.

For example:

```text
Build
├── JAR
├── Container Image
├── SBOM
└── Helm Chart
```

The principle means:

```text
Do not rebuild the same release artifact independently for every environment.
```

Your release can contain several coordinated artifacts.

---

# 23. Environment Lifecycle

A simple lifecycle:

```text
DEV
↓
TEST
↓
STAGING
↓
PRODUCTION
```

What should change?

Usually:

```text
Configuration
Secrets
Infrastructure
Scaling
Endpoints
Feature flags
```

What should not change?

```text
Artifact content
```

---

# 24. Development Stage

DEV may provide:

```text
Early validation
Developer testing
Basic integration
Smoke testing
```

The artifact is still:

```text
Candidate
```

unless your process says otherwise.

---

# 25. Testing Stage

TEST may perform:

```text
Integration tests
Functional tests
Regression tests
Security checks
Performance checks
```

depending on the application.

The candidate becomes more trusted.

---

# 26. Staging Stage

STAGING should resemble production closely enough to provide meaningful confidence.

Possible checks:

```text
End-to-end testing
Deployment validation
Configuration validation
Operational testing
Production-like traffic simulation
Release readiness
```

The important principle:

```text
The staging artifact
=
The intended production artifact.
```

---

# 27. Production Stage

PRODUCTION is the operational release state.

Before entering production, you should ideally know:

```text
Artifact identity
Version
Checksum/digest
Build
Source
Approval state
Rollback target
```

Production should not receive:

```text
an untraceable rebuild.
```

---

# 28. Promotion

Promotion means advancing an existing artifact through the release lifecycle.

For example:

```text
Candidate
↓
Validated
↓
Approved
↓
Production-ready
```

Promotion may be represented in several ways.

Two common conceptual models are:

```text
Repository-based promotion
```

and:

```text
Property/metadata-based promotion
```

---

# 29. Repository-Based Promotion

Suppose you have:

```text
veriqta-generic-dev-local
veriqta-generic-test-local
veriqta-generic-stage-local
veriqta-generic-release-local
```

Lifecycle:

```text
DEV Repository
↓
TEST Repository
↓
STAGE Repository
↓
RELEASE Repository
```

The artifact physically/logically moves or copies between repository locations.

---

# 30. Repository-Based Architecture

```text
Build
↓
veriqta-dev-local
↓
Tests Pass
↓
veriqta-test-local
↓
Staging Validation
↓
veriqta-stage-local
↓
Approval
↓
veriqta-release-local
↓
Production
```

This makes lifecycle state visible from repository location.

---

# 31. Advantages of Repository-Based Promotion

Possible advantages include:

```text
Clear separation
Different permissions
Different retention
Simple operational model
Easy visibility
Release repository can be locked down
```

For example:

```text
CI
↓
Can write DEV

Release Pipeline
↓
Can promote

Production
↓
Can read RELEASE
```

---

# 32. Risks of Too Many Repositories

Do not automatically create:

```text
dev
dev2
qa
qa2
test
testing
pretest
prestage
staging
preprod
production
final
```

Repository sprawl creates:

```text
Operational complexity
Permission complexity
Naming confusion
Promotion complexity
Maintenance overhead
```

Use lifecycle boundaries that solve real needs.

---

# 33. Property-Based Promotion

Another model keeps the artifact in one repository or fewer repositories while changing metadata.

For example:

```text
release-status=development
```

then:

```text
release-status=tested
```

then:

```text
release-status=staging-approved
```

then:

```text
release-status=production-approved
```

The binary path remains the same.

The lifecycle metadata changes.

---

# 34. Property-Based Architecture

```text
Artifact
↓
release-status=dev
↓
Testing
↓
release-status=tested
↓
Staging
↓
release-status=approved
↓
Production
```

No binary movement is required.

---

# 35. Advantages of Property-Based Promotion

Possible advantages:

```text
Less artifact copying
Fewer repositories
Metadata-driven automation
Searchable lifecycle state
Clear binary identity
```

However, lifecycle policy must be carefully designed.

---

# 36. Risks of Property-Based Promotion

If properties can be changed too freely:

```text
release-status=dev
↓
Someone manually changes
↓
release-status=production
```

without validation.

Therefore lifecycle state needs:

```text
Permissions
Automation
Approval rules
Auditability
```

Properties are powerful but should not become uncontrolled labels.

---

# 37. Repository vs Property Promotion

A simplified comparison:

| Approach         | Lifecycle represented by |
| ---------------- | ------------------------ |
| Repository-based | Artifact location        |
| Property-based   | Metadata/state           |
| Hybrid           | Both                     |

A hybrid model might use:

```text
Development Repository
↓
Release Repository
```

while properties within them represent:

```text
candidate
validated
approved
```

---

# 38. Which Approach Is Better?

There is no universal answer.

Consider:

```text
Security boundaries
Retention requirements
Scale
Package type
Operational simplicity
Regulatory needs
Permission model
Release tooling
```

The design should support your organization's lifecycle clearly.

---

# 39. Copy vs Move

When promoting repository-based artifacts, you may:

```text
COPY
```

or:

```text
MOVE
```

These have different lifecycle implications.

---

# 40. Copy Promotion

Conceptually:

```text
DEV
↓
Artifact A

COPY
↓
RELEASE
↓
Artifact A

DEV still has Artifact A
```

Now two repository paths refer to the same logical release content.

This can help preserve:

```text
Candidate history
Auditability
Testing evidence
```

depending on design.

---

# 41. Move Promotion

Conceptually:

```text
DEV
↓
Artifact A

MOVE
↓
RELEASE
↓
Artifact A

DEV no longer contains Artifact A
```

This can make lifecycle state more exclusive.

Example:

```text
If it is RELEASE
it is no longer DEV.
```

---

# 42. Copy vs Move Questions

Before choosing, ask:

```text
Should old lifecycle location remain browsable?

Do tests refer to the old path?

Do we need full promotion history?

Should one artifact exist in several states simultaneously?

Does retention differ?

What do permissions require?

What does rollback need?
```

Do not choose based only on which command is easier.

---

# 43. Content Identity Must Remain Stable

Whether you copy or move:

```text
Candidate SHA-256
=
Promoted SHA-256
```

If they differ:

```text
STOP
```

Because now you may have created:

```text
a different artifact
```

rather than promoting the tested one.

---

# 44. Promotion Verification

After promotion, verify:

```text
Source artifact exists
Destination artifact exists
Expected version
Expected checksum
Expected build association
Expected properties
Expected repository
```

Do not assume:

```text
copy command succeeded
=
release is correct.
```

Verify.

---

# 45. Release Approval Concepts

Promotion often requires evidence.

For example:

```text
Unit tests passed
Integration tests passed
Security scan passed
Change approved
Staging healthy
Operational checks passed
```

Then:

```text
Release Approval
↓
Production Promotion
```

The approval can be:

```text
Automated
Manual
Policy-based
Combination
```

depending on risk and organization.

---

# 46. Approval Is Not Just a Button

A release-approval process should answer:

```text
What is being approved?

Which version?

Which checksum/digest?

Which test evidence?

Which build?

Which commit?

Which environment was tested?

Who or what approved it?
```

Approval without artifact identity is weak.

---

# 47. Weak Approval

Example:

```text
Approve latest build?
```

Problem:

```text
What does latest mean?
```

Better:

```text
Approve:
veriqta-api 4.2.0
Build 901
SHA-256 ABC
```

Now approval applies to one identifiable artifact.

---

# 48. Automated Release Gates

A pipeline can require:

```text
Tests = PASS
Security Policy = PASS
Artifact Exists = YES
Checksum Verified = YES
Staging Health = PASS
```

before production.

Conceptually:

```text
Candidate
↓
Gate 1
↓
Gate 2
↓
Gate 3
↓
Approved Release
```

If a required gate fails:

```text
No promotion.
```

---

# 49. Manual Approval

Some environments require a person to approve production deployment.

That person should not have to guess what they are approving.

A useful approval view includes:

```text
Application
Version
Build
Commit
Artifact
Checksum/digest
Test results
Staging result
Change information
```

---

# 50. Approval vs Deployment

Approval means:

```text
Artifact may proceed.
```

Deployment means:

```text
Artifact is actually applied to an environment.
```

These are different events.

A release can be:

```text
Approved
```

but not yet:

```text
Deployed.
```

---

# 51. Release Status vs Deployment Status

Example:

```text
Artifact Status:
production-approved
```

but:

```text
Deployment Status:
not deployed
```

or:

```text
Deployment Status:
deployed to production
```

Do not confuse approval metadata with actual runtime state.

---

# 52. Rollback

Rollback means returning to a previously known release state.

Suppose:

```text
Current:
4.2.0

Previous:
4.1.3
```

If `4.2.0` fails:

```text
4.2.0
↓
Rollback
↓
4.1.3
```

A good rollback uses the original `4.1.3` artifact.

---

# 53. Do Not Rebuild for Rollback

Bad:

```text
Need 4.1.3
↓
Checkout old Git tag
↓
Build today
↓
Deploy
```

Why?

Today's build could differ.

Better:

```text
Need 4.1.3
↓
Retrieve original approved artifact
↓
Verify checksum
↓
Deploy
```

This preserves release identity.

---

# 54. Previous Version Retrieval

A rollback process needs to know:

```text
Which version was previously healthy?
```

That requires:

```text
Deployment history
Artifact retention
Release traceability
Version history
```

A useful release record:

```text
Current:
4.2.0
Build 901
SHA-256 NEW

Previous:
4.1.3
Build 882
SHA-256 OLD
```

---

# 55. Rollback Is Not Always Safe

Rolling back software can fail if:

```text
Database schema changed
Data format changed
API compatibility changed
Feature flags changed
Infrastructure changed
Secrets changed
External systems changed
```

Therefore:

```text
Artifact exists
```

does not automatically mean:

```text
Rollback is operationally safe.
```

Release design should consider backward compatibility.

---

# 56. Rollback vs Roll Forward

Sometimes the better response is:

```text
Roll forward
```

with a fix.

For example:

```text
4.2.0 broken
↓
4.2.1 fix
```

instead of:

```text
4.2.0
↓
4.1.3
```

The choice depends on:

```text
Failure type
Data compatibility
Time to fix
Risk
Operational policy
```

Artifact management should support both options.

---

# 57. Retention Concepts

Artifact repositories grow over time.

Suppose CI creates:

```text
100 development builds/day
```

After a year:

```text
36,500 development artifacts
```

Storage can grow significantly.

You need retention policies.

---

# 58. Retention Is Different by Artifact Type

You may retain:

```text
Development artifacts
↓
Shorter period

Release candidates
↓
Medium period

Production releases
↓
Longer period
```

because their operational value differs.

---

# 59. Development Retention

You might retain:

```text
Last N development builds
```

or:

```text
Development builds for X days
```

because most become irrelevant quickly.

But retain enough to support:

```text
Current debugging
Active testing
Recent regression investigation
```

---

# 60. Release Retention

Release artifacts often need longer retention.

Why?

```text
Rollback
Incident analysis
Security investigation
Audit
Customer support
Disaster recovery
Compliance
```

Deleting a production release too early can create operational risk.

---

# 61. Retention and Running Workloads

Suppose Kubernetes currently runs:

```text
veriqta-api:4.1.3
```

You delete the image from Artifactory.

Existing Pods may continue running.

Then a node fails.

Kubernetes schedules a replacement Pod.

It requests:

```text
4.1.3
```

Artifactory:

```text
Image not found
```

Result:

```text
ImagePullBackOff
```

Retention directly affects recoverability.

---

# 62. Retention and Autoscaling

Existing Pods:

```text
3
```

Traffic increases.

Autoscaling needs:

```text
6
```

Three new Pods need the image.

If the artifact was deleted:

```text
Scaling fails.
```

Therefore retention is part of reliability engineering.

---

# 63. Retention Policy Questions

Ask:

```text
Is artifact deployed anywhere?

Is artifact approved for rollback?

Is artifact under investigation?

Is artifact required by audit policy?

Is artifact still referenced by active release?

How old is artifact?

Is it a development candidate?

Is it superseded?

What storage cost does it create?
```

Do not delete based only on age.

---

# 64. Artifact Retention vs Metadata Retention

You can have:

```text
Artifact deleted
Build Info retained
```

or:

```text
Artifact retained
Build Info deleted
```

Both create different limitations.

For strong historical traceability and rollback, important releases may require retention of both.

---

# 65. Preventing Accidental Overwrite

Imagine release:

```text
4.2.0
```

already exists.

A new CI run accidentally tries to publish another:

```text
4.2.0
```

with different bytes.

A mature release design should stop this.

---

# 66. Why Overwrites Are Dangerous

Suppose Monday:

```text
4.2.0
↓
SHA-256 ABC
```

Friday:

```text
4.2.0
↓
SHA-256 XYZ
```

Now questions become impossible to answer reliably:

```text
Which 4.2.0 did customer A receive?

Which 4.2.0 was scanned?

Which 4.2.0 was approved?

Which 4.2.0 is in production?
```

Immutability prevents this ambiguity.

---

# 67. Preventing Overwrite Through Repository Policy

Possible controls include:

```text
Release repository permissions
No redeploy/overwrite policy
Immutable tags
Pipeline checks
Unique version enforcement
Promotion-only production path
```

The exact technical control depends on package type and repository configuration.

The design goal:

```text
Existing release version
↓
Cannot silently become different content.
```

---

# 68. Preventing Overwrite in the Pipeline

Before publishing:

```text
Does version already exist?
```

If yes:

```text
Stop.
```

unless your policy explicitly allows that artifact type to be mutable.

Conceptually:

```text
Version 4.2.0 requested
↓
Check release repository
↓
Already exists?
├── YES → FAIL
└── NO → Publish
```

---

# 69. Development Artifacts May Be More Mutable

A development lifecycle may allow:

```text

```

or temporary mutable aliases.

But release lifecycle should become increasingly strict.

Example:

```text

↓
Flexible

candidate
↓
Controlled

release
↓
Immutable
```

This is a useful trust progression.

# 70. Mutable Alias vs Immutable Release

For containers:

```text

staging
production
```

may be moving aliases.

But:

```text
4.2.0
```

should be stable.

Even stronger:

```text
sha256:ABC
```

is immutable content identity.

Conceptually:

```text
production
↓
Currently points to
↓
4.2.0
↓
sha256:ABC
```

# 71. Artifact Promotion With Version Names

Suppose development artifact:

```text
4.3.0-rc.1
```

passes everything.

Should final release be:

```text
4.3.0
```

This creates a subtle question.

If creating `4.3.0` means rebuilding:

```text

```

because now it is different.

A stronger release system should promote the tested binary content while assigning the final release identity through a controlled process appropriate to the package format and release tooling.

The key question is always:

```text

```

# 82. Release Lifecycle Design

A useful lifecycle could be:

```text
BUILT
↓
CANDIDATE
↓
TESTED
↓
STAGING-APPROVED
↓
PRODUCTION-APPROVED
↓
DEPLOYED
↓
RETIRED
```

But your organization may use fewer stages.

Each state must have:

```text
Meaning
Entry conditions
Exit conditions
Permissions
Automation
Retention policy
```

---

# 83. Do Not Create Meaningless Lifecycle States

Bad:

```text
candidate
ready
almost-ready
nearly-final
final-candidate
final
really-final
production-final
```

If engineers cannot explain the difference, the lifecycle is too complicated.

Prefer a small number of meaningful states.

---

# 84. Example State Definition

## BUILT

Entry:

```text
CI build succeeded.
```

## TESTED

Entry:

```text
Required automated tests passed.
```

## STAGING-APPROVED

Entry:

```text
Staging deployment and validation succeeded.
```

## PRODUCTION-APPROVED

Entry:

```text
All required release gates passed.
```

## DEPLOYED

Entry:

```text
Production deployment completed and verified.
```

Now lifecycle labels have operational meaning.

---

# 85. State Transitions

A controlled lifecycle should define allowed transitions.

Example:

```text
BUILT
↓
TESTED
↓
STAGING-APPROVED
↓
PRODUCTION-APPROVED
↓
DEPLOYED
```

Maybe:

```text
TESTED
↓
REJECTED
```

is also allowed.

But:

```text
BUILT
↓
DEPLOYED
```

may be forbidden.

This is release governance.

---

# 86. Promotion Permissions

A build identity may be allowed to:

```text
Publish candidates
```

but not:

```text
Promote production releases.
```

A release identity may be allowed to:

```text
Promote approved artifacts
```

Production runtime may only:

```text
Read releases.
```

This creates separation of duties.

# 93. Release Manifest Benefits


# 94. Rollback Manifest

Previous release:

```text

```

has its own manifest.

Rollback can simply resolve:

```text

↓

```

instead of manually hunting through repositories.

# 95. Release Retention by Manifest


```text

Artifact may still be valid

Runtime failure
↓
Artifact deployed but unhealthy
```

Do not confuse these.

# 140. Promotion Failure Is Not Build Failure

Suppose:

```text
Build passed
Tests passed
Promotion failed due 403
```

The artifact is not broken.

The likely problem is:

```text
Authorization
```

Fix the release pipeline permission.

Do not rebuild.

---

# 141. Deployment Failure Is Not Promotion Failure

Suppose release artifact exists correctly.

Deployment fails because:

```text
Kubernetes imagePullSecret invalid
```

Do not re-promote artifact.

Artifact lifecycle may be correct.

Runtime deployment configuration is wrong.

# 144. Common Beginner Mistakes

1. Treating uploaded artifacts as automatically production-ready.

2. Rebuilding for every environment.

3. Confusing development artifacts with releases.

4. Treating snapshots like immutable releases.

5. Overwriting release versions.

6. Using `latest` as the only identity.

7. Promoting by filename without checksum verification.

8. Assuming copy and move have identical lifecycle effects.

9. Creating too many repositories.

10. Creating too many meaningless lifecycle states.

11. Using properties without access controls.

12. Treating a property as proof that testing happened.

13. Manually promoting random binaries.

14. Approving a release without identifying the artifact.

15. Deleting previous production versions too early.

16. Rebuilding old releases for rollback.

17. Assuming rollback is always safe.

18. Deleting images still referenced by running Kubernetes workloads.

19. Using wildcards that promote multiple artifacts.

20. Allowing CI to write directly to production release repositories without controls.

21. Giving build identities administrator permissions.

22. Confusing artifact approval with actual deployment.

23. Confusing version history with deployment history.

24. Forgetting Helm charts or database migrations are also release artifacts.

25. Promoting part of a multi-artifact release and ignoring failures.

26. Treating production aliases as immutable versions.

27. Failing to preserve promotion history.

28. Using age alone for retention decisions.

29. Failing to verify promoted artifact checksums.

30. Forgetting that configuration can change behavior even when the binary remains identical.

# 149. Final Release Architecture

You should now see release management as this:

```text
                         SOURCE
                           ↓
                        Git Commit
                           ↓
                        CI Build
                           ↓
                   Generate Artifact
                           ↓
                 Version + Checksum
                           ↓
                        DEV
                           ↓
                    Basic Testing
                           ↓
                       PROMOTE
                           ↓
                        TEST
                           ↓
                 Integration Testing
                           ↓
                       PROMOTE
                           ↓
                       STAGING
                           ↓
                  Production Validation
                           ↓
                    RELEASE APPROVAL
                           ↓
                       PROMOTE
                           ↓
                     PRODUCTION
                           ↓
                    Runtime Verification
                           ↓
                    Release Retention
                           ↓
                  Rollback if Required
```

At every stage:

```text
ARTIFACT CONTENT
=
THE SAME
```

For a generic artifact:

```text
SHA-256 DEV
=
SHA-256 TEST
=
SHA-256 STAGING
=
SHA-256 PROD
```

For a container:

```text
DIGEST DEV
=
DIGEST TEST
=
DIGEST STAGING
=
DIGEST PROD
```

That is the strongest evidence that:

```text
THE THING YOU TESTED
=
THE THING YOU RELEASED
```

The central rule from Part 15 is:

```text
BUILD ONCE
↓
IDENTIFY EXACTLY
↓
TEST
↓
PROMOTE
↓
VERIFY IDENTITY
↓
APPROVE
↓
DEPLOY
↓
RETAIN FOR ROLLBACK
```

Not:

```text
BUILD
↓
TEST
↓
REBUILD
↓
STAGING
↓
REBUILD
↓
PRODUCTION
```

A mature artifact repository is therefore not simply a place where release files accumulate.

It becomes part of a controlled release lifecycle:

```text
DEVELOPMENT
↓
VALIDATION
↓
PROMOTION
↓
APPROVAL
↓
PRODUCTION
↓
ROLLBACK
↓
RETENTION
```

while preserving one critical guarantee:

**the artifact that reaches production is the same verified artifact that passed through the release process.**
