# 1. Start With the Software Delivery Problem

Imagine that a development team creates a web application.

The developers write source code. Eventually, that code needs to run somewhere.

It might run on:

* A Linux server
* An Amazon EC2 instance
* A virtual machine
* A container
* Kubernetes
* A cloud platform
* An internal data center

The source code itself is not always what gets deployed.

Many applications first go through a build or packaging process.

For example:

Source Code
↓
Compile
↓
Test
↓
Package
↓
Deployable Artifact

The result might be:

```text
payment-service-1.0.0.jar
```

or:

```text
customer-api-2.4.1.zip
```

or a container image such as:

```text
customer-api:2.4.1
```

The team now has something that can be delivered or deployed.

That output is an artifact.

But another question immediately appears:

Where should the team store it?

A developer's laptop is not a reliable production storage system.

Email is not an artifact management system.

Slack is not an artifact management system.

A random shared folder is not a reliable artifact management system.

Git is primarily designed to manage source code and other version-controlled files, not to serve as the main repository for large generated build outputs.

A DevOps team therefore needs somewhere specifically designed to store, organize, retrieve, secure, version, and manage software artifacts.

That is the problem artifact repositories solve.

---

# 2. What Is Source Code?

Source code is the human-readable set of instructions developers create to build software.

For example, a developer might write Python:

```python
def calculate_total(price, quantity):
    return price * quantity

print(calculate_total(20, 3))
```

Or Java:

```java
public class Application {
    public static void main(String[] args) {
        System.out.println("Application started");
    }
}
```

Source code can be written in languages such as:

* Java
* Python
* JavaScript
* TypeScript
* C#
* Go
* C
* C++
* Rust

Developers normally store source code in a version control system.

Git is the most common example.

A typical flow might be:

```text
Developer
    ↓
Source Code
    ↓
Git
    ↓
GitHub
```

Git tracks changes to the source code.

For example:

Developer A changes:

```text
payment.py
```

Developer B changes:

```text
database.py
```

Git can record:

* What changed
* Who changed it
* When it changed
* Which commit contains the change
* Which branch contains it
* How versions of the source relate to one another

This makes Git extremely useful for source code management.

But source code and a deployable artifact are not necessarily the same thing.

That distinction is fundamental to understanding Artifactory.

---

# 3. Source Code vs Build Output

Suppose a developer has a Java project.

The project may contain:

```text
payment-service/
├── src/
│   └── main/
│       └── java/
├── pom.xml
├── README.md
└── .gitignore
```

These files represent the project's source and build configuration.

After running a build command such as:

```bash
mvn package
```

Maven may create:

```text
target/payment-service-1.0.0.jar
```

The JAR file is build output.

So:

```text
Source Code
    ↓
Build
    ↓
Build Output
```

More specifically:

```text
Java Source
    ↓
Maven
    ↓
payment-service-1.0.0.jar
```

The developer works primarily with the source.

The deployment process can work with the resulting artifact.

This gives us two different things:

| Source Code                        | Build Output                                            |
| ---------------------------------- | ------------------------------------------------------- |
| Written and modified by developers | Generated or packaged from a build process              |
| Usually stored in Git              | Commonly stored in an artifact repository               |
| Represents software instructions   | Represents a built or packaged software deliverable     |
| Changes through commits            | Commonly identified through versions and build metadata |
| Example: `Application.java`        | Example: `application-1.0.0.jar`                        |

Not every artifact must be compiled.

For example, a ZIP archive can package scripts, configuration, templates, or other files.

The important idea is that an artifact is an output that the software delivery process needs to store and manage.

---

# 4. What Is a Build?

A build is the process of turning source code and related inputs into a usable software output.

The exact process depends on the technology.

A build might involve:

```text
Source Code
↓
Download Dependencies
↓
Compile
↓
Run Tests
↓
Package
↓
Artifact
```

Some languages require compilation.

Others do not.

For example, Java source code is normally compiled into bytecode before packaging.

A Python application may not require the same compilation process, but a Python library can still be packaged into a wheel.

A JavaScript library may be packaged and published as an npm package.

A containerized application may eventually be packaged into a container image.

Therefore, "build" should not be interpreted only as "compile."

A build pipeline can include:

* Dependency resolution
* Compilation
* Testing
* Static analysis
* Packaging
* Metadata generation
* Container image creation
* Publishing

# 5. What Is a Build Tool?

A build tool automates parts of the build process.

Examples include:

* Maven
* Gradle
* npm
* MSBuild
* dotnet CLI
* Make
* various language-specific packaging tools

For a Java project using Maven:

```bash
mvn package
```

Maven reads the project's configuration, resolves required dependencies, performs configured build steps, and packages the result.

A simplified flow is:

```text
Developer
↓
Java Source Code
↓
Maven
↓
JAR
```

Later, we can add an artifact repository:

```text
Developer
↓
Java Source Code
↓
Maven
↓
JAR
↓
Artifactory
```

# 6. What Is an Artifact?

An artifact is a file, package, image, or other software output produced or managed as part of the software build and delivery process.

Examples include:

```text
payment-service-1.0.0.jar
```

```text
customer-portal-3.1.0.war
```

```text
release-4.5.2.zip
```

```text
veriqta-utils-1.3.0.tgz
```

A Python wheel might look like:

```text
veriqta_tools-1.0.0-py3-none-any.whl
```

A container image could be identified as:

```text
payment-api:1.8.0
```

A Helm chart package might look like:

```text
payment-api-1.8.0.tgz
```

Artifacts are important because software delivery is not only about creating code.

Teams must be able to identify exactly what was built and what should be deployed.

# 7. How Source Code Becomes an Artifact

Consider a Java application.

A developer writes:

```text
PaymentService.java
```

The code is committed to Git.

The repository might contain:

```text
payment-service/
├── src/
├── pom.xml
├── README.md
└── .gitignore
```

The build process begins.

Maven may:

1. Read `pom.xml`.
2. Resolve required dependencies.
3. Compile the source.
4. Run configured tests.
5. Package the application.
6. Produce a JAR.

The result might be:

```text
payment-service-1.0.0.jar
```

Now the flow looks like:

```text
Developer
↓
Source Code
↓
Git
↓
Build Tool
↓
Artifact
```

If Artifactory is introduced:

```text
Developer
↓
Source Code
↓
Git
↓
Build Tool
↓
Artifact
↓
Artifactory
```

The artifact can later be retrieved for testing or deployment.

# 8. Common Types of Artifacts

Different technology ecosystems create and consume different artifact formats.

Understanding the major ones will make Artifactory easier to understand.

## 8.1 JAR

JAR means Java Archive.

A JAR packages Java classes and related resources.

Example:

```text
payment-service-1.0.0.jar
```

You may see a Java workflow such as:

```text
Java Source
↓
Maven
↓
JAR
↓
Artifact Repository
```

A runnable JAR may be executed with:

```bash
java -jar payment-service-1.0.0.jar
```

Here:

* `java` starts the Java runtime.
* `-jar` tells Java to execute a JAR.
* `payment-service-1.0.0.jar` is the artifact being executed.

---

# 9. WAR

WAR commonly means Web Application Archive.

It is traditionally used to package Java web applications for deployment to compatible application servers or servlet containers.

Example:

```text
customer-portal-2.0.0.war
```

A traditional workflow could be:

```text
Java Web Application
↓
Build
↓
WAR
↓
Artifact Repository
↓
Application Server
```

JARs are now common for self-contained Java services, but WAR files remain important in many enterprise environments.

---

# 10. ZIP

ZIP is a general-purpose archive format.

A team might package an application release as:

```text
billing-service-3.4.0.zip
```

The archive might contain:

```text
billing-service/
├── bin/
├── config/
├── scripts/
└── README.txt
```

ZIP artifacts are useful when the software does not belong to a specific package ecosystem or when multiple files need to be distributed together.

---

# 11. TAR and TAR.GZ

TAR stands for tape archive.

It groups multiple files into one archive.

You may see:

```text
application-1.0.0.tar
```

or compressed:

```text
application-1.0.0.tar.gz
```

These formats are extremely common on Linux and Unix-like systems.

A release could look like:

```text
Application Files
↓
TAR Packaging
↓
application-1.0.0.tar.gz
↓
Artifact Repository
```

A simplified flow is:

# 15. Container Images

Container images are also software artifacts.

Suppose a team builds an application container:

```bash
docker build -t payment-api:1.0.0 .
```

The important pieces are:

* `docker build` tells Docker to build an image.
* `-t` assigns a name and tag.
* `payment-api` is the image name.
* `1.0.0` is the tag.
* `.` tells Docker to use the current directory as the build context.

The result is a container image.

Conceptually:

```text
Application
↓
Docker Build
↓
Container Image
↓
Container Registry
↓
Deployment
```

Artifactory can act as a registry for container images while also supporting many other package ecosystems.

Later we will examine image tags, digests, repository types, authentication, pushing, pulling, and Kubernetes usage.

# 16. Helm Charts

Helm is a package manager commonly used with Kubernetes.

A Helm chart packages information required to describe and configure Kubernetes application deployment.

A packaged chart might look like:

```text

```

Conceptually:

```text
Kubernetes Templates
↓
Helm Chart
↓
Artifact Repository
↓
Kubernetes Deployment
```

A DevOps team might therefore manage both:

```text
Container Image
+
Helm Chart
```

for the same application release.

For example:

```text
payment-api:1.0.0
```

and:

```text
payment-api-1.0.0.tgz
```

The image contains the application runtime content.

The chart describes how the application should be installed or configured in Kubernetes.

# 17. Artifacts Are Not Just Application Releases

This is important.

When beginners hear "artifact," they often imagine only the final application.

Artifact repositories can manage many types of software packages and build outputs.

Depending on the ecosystem, these can include:

* Application packages
* Libraries
* Internal dependencies
* Container images
* Helm charts
* Generic archives
* Build outputs
* Release packages

For example, a company might create an internal library:

```text
company-auth-library-2.5.0.jar
```

Multiple applications could depend on it.

The artifact repository therefore becomes part of both application delivery and dependency management.

# 18. What Is a Dependency?

A dependency is external code, a library, package, module, or component that another application requires.

Suppose you build an application.

You probably do not write every capability yourself.

Your application may need libraries for:

* HTTP requests
* Logging
* Database communication
* JSON processing
* Authentication
* Testing
* Cryptography
* Web frameworks

Those libraries are dependencies.

Conceptually:

```text
Your Application
├── Dependency A
├── Dependency B
└── Dependency C
```

During a build, the build tool or package manager may need to retrieve them.

For example:

```text
Build Tool
↓
Package Repository
↓
Required Dependency
```

This creates another reason artifact repositories are important.

They do not only store what your organization creates.

They can also help control how external dependencies are retrieved.

---

# 19. What Is a Package Repository?

A package repository is a service or storage system from which packages can be published and retrieved using the conventions of a package ecosystem.

Examples of public package ecosystems include repositories and registries used by:

* Maven
* npm
* Python
* NuGet

A package repository answers questions such as:

```text
Where can I download version 2.3.0 of this package?
```

or:

```text
Where should I publish version 1.5.0 of our internal library?
```

A package repository is therefore storage and distribution infrastructure.

---

# 20. What Is a Package Manager?

A package manager is a tool that helps a system or project find, install, update, remove, publish, or otherwise work with software packages.

Examples include:

* npm
* pip
* NuGet tooling
* Maven, which also performs broader build and dependency-management functions
* Helm

A useful beginner distinction is:

```text
Package Manager = the client/tool working with packages
Package Repository = the place/service providing or storing packages
```

For example:

```text
pip
↓
Python Package Repository
↓
Python Package
```

Or:

```text
npm
↓
npm Repository
↓
JavaScript Package
```

When Artifactory is introduced:

```text
Package Manager
↓
Artifactory
↓
Package
```

The package manager and Artifactory are therefore not competing pieces of software.

They can work together.

---

# 21. Package Manager vs Package Repository

Consider a supermarket analogy.

The package repository is like the warehouse.

The package manager is like the mechanism that requests and retrieves the required item.

Technically:

| Package Manager                                        | Package Repository                    |
| ------------------------------------------------------ | ------------------------------------- |
| Runs commands for working with packages                | Stores or serves packages             |
| Requests dependencies                                  | Responds to package requests          |
| Usually operates on the developer or build environment | Usually operates as a server/service  |
| Understands package ecosystem conventions              | Organizes and distributes packages    |
| Example: pip                                           | Example: a PyPI-compatible repository |
| Example: npm client                                    | Example: an npm-compatible repository |

The flow becomes:

```text
Developer
↓
Package Manager
↓
Package Repository
↓
Package
```

# 22. What Is a Binary Repository?

The term "binary repository" is commonly used for a repository system designed to manage compiled binaries, packages, archives, container images, and other software artifacts.

Do not interpret "binary" too narrowly.

The repository may manage many artifact formats, not just traditional executable binary files.

A binary repository manager provides capabilities beyond simply placing files in a directory.

Depending on the platform and configuration, those capabilities can include:

* Storage
* Version organization
* Metadata
* Search
* Access control
* Package-manager integration
* Artifact retrieval
* Artifact publishing
* Remote dependency caching
* Build information
* Traceability
* Promotion workflows
* APIs
* Automation

This is the category in which Artifactory operates.

# 23. Why Not Just Put Everything in Git?

This is one of the most important beginner questions.

Git is excellent at managing source code and text-based configuration.

It provides:

* Commits
* Branches
* Diffs
* Merging
* Source history
* Collaboration

Generated build artifacts have different management requirements.

Suppose every build produces:

```text
application-1.0.0.jar
application-1.0.1.jar
application-1.0.2.jar
application-1.0.3.jar
```

Then container images, ZIP files, package archives, and other large generated files are also added.

Git repositories can become unnecessarily large.

Binary files also do not benefit from Git's line-oriented diffing in the way source files do.

More importantly, artifact management requires concepts such as:

* Package metadata
* Package-manager protocols
* Dependency resolution
* Repository layouts
* Artifact promotion
* Remote repository caching
* Artifact-level permissions
* Build metadata
* Release retention
* Container registry behavior

These are artifact-repository responsibilities.

A useful separation is:

```text
Git
↓
Source History

Artifactory
↓
Artifact History and Distribution
```

That does not mean a binary can never exist in Git.

It means Git should generally not be used as the organization's primary artifact repository.

---

# 24. What About Git LFS?

Git Large File Storage, or Git LFS, helps Git repositories handle certain large files differently from normal Git objects.

It can be useful for files that legitimately belong with the source project but are too large for normal Git storage.

That still does not turn Git into a full artifact repository manager.

An artifact repository addresses software distribution concerns such as:

* Package protocols
* Dependency resolution
* Package metadata
* Build information
* Promotion
* Repository permissions
* Remote caching
* Container image storage

So:

```text
Git LFS ≠ Artifact Repository Manager
```

They solve different problems.

# 25. The Problem With Manually Sharing Binaries

Imagine your team builds:

```text
payment-service-1.4.2.jar
```

A developer sends it to another engineer through chat.

That engineer saves it locally.

Someone else copies it to a shared drive.

Another person renames it:

```text
payment-service-final.jar
```

Then someone creates:

```text
payment-service-final2.jar
```

Later:

```text
payment-service-final-working.jar
```

Now ask:

Which one is production?

Who built it?

Which source commit produced it?

Which dependencies were used?

Was it tested?

Has the file been modified?

Which environment currently uses it?

Can we retrieve the previous release?

Can we prove the production artifact is the same one that passed testing?

Without disciplined artifact management, these questions become difficult.

# 26. The "Works on My Machine" Artifact Problem

Suppose Developer A builds:

```text
payment-service.jar
```

Developer B builds the same source and also gets:

```text
payment-service.jar
```

Are the two files definitely identical?

Not necessarily.

Differences can come from:

* Dependency versions
* Build-tool versions
* Environment differences
* Operating-system differences
* Build configuration
* Environment variables
* Generated timestamps
* Compiler versions
* Uncommitted source changes
* External files used during the build

This is why mature software delivery practices care about repeatability, provenance, and artifact identity.

# 27. Artifact Versioning

Artifact versioning gives releases identifiable versions.

Instead of:

```text
application.jar
```

use something such as:

```text
application-1.0.0.jar
```

Later:

```text
application-1.0.1.jar
application-1.1.0.jar
application-2.0.0.jar
```

One common approach is Semantic Versioning:

```text
MAJOR.MINOR.PATCH
```

Example:

```text
2.4.1
```

Conceptually:

```text
2 = major version
4 = minor version
1 = patch version
```

In a project following Semantic Versioning:

* MAJOR changes indicate incompatible API changes.
* MINOR changes add backward-compatible functionality.
* PATCH changes make backward-compatible fixes.

Not every organization follows Semantic Versioning, but every team needs a deliberate versioning strategy.

---

# 28. Why Artifact Versions Matter

Suppose production currently runs:

```text
payment-service-4.2.0.jar
```

A new release is:

```text
payment-service-4.3.0.jar
```

The new version causes a serious problem.

If the previous artifact remains safely stored, the team may be able to roll back to:

```text
payment-service-4.2.0.jar
```

Versioning therefore helps with:

* Release identification
* Deployment
* Rollback
* Troubleshooting
* Auditing
* Communication
* Traceability

Compare:

```text
Deploy the payment application.
```

with:

```text
Deploy payment-service 4.3.0.
```

The second instruction is much more precise.

# 29. What Is a Reproducible Build?

A reproducible build is a build process designed so that the same source and controlled build inputs can produce the same output.

Conceptually:

```text
Same Source
+
Same Dependencies
+
Same Build Configuration
+
Same Toolchain
+
Controlled Environment
↓
Same Build Result
```

This is harder than it sounds.

Imagine a build configuration asks for:

```text
some-library:latest
```

Today, `latest` might resolve to:

```text
3.1.0
```

Next month:

```text
3.2.0
```

The source code did not change, but the dependency did.

Now the build can behave differently.

This is one reason teams care about pinned dependencies, controlled repositories, checksums, immutable release artifacts, and traceable builds.

Artifact repositories are one component of a larger reproducible-build strategy.

They do not automatically make every build reproducible.

# 30. Dependency Management and Reproducibility

Consider:

```text
Application
├── Library A 1.2.0
├── Library B 4.1.3
└── Library C 2.0.1
```

The exact dependency versions matter.

If Library B silently changes from:

```text
4.1.3
```

to:

```text
4.2.0
```

the application may behave differently.

A controlled dependency workflow might look like:

```text
Build
↓
Artifactory
↓
Approved/Cached Dependency
↓
Build Continues
```

This provides a controlled point through which dependency retrieval can occur.

We will explore remote repositories and dependency caching much later in the series.

# 31. Artifact Immutability

Immutability means that once a particular released artifact has been created and accepted as a specific version, it should not silently change underneath that identity.

Suppose:

```text
payment-service-2.0.0.jar
```

passes testing.

The team deploys it to production.

A developer later makes a code change.

It would be dangerous to build different content and overwrite the existing artifact while still calling it:

```text
payment-service-2.0.0.jar
```

Now two different binaries have had the same release identity.

Instead, the new build should receive a new version according to the team's versioning policy.

For example:

```text
payment-service-2.0.1.jar
```

The principle is:

```text
Version 2.0.0
↓
Built
↓
Tested
↓
Released
↓
Do Not Silently Replace It
```

# 32. Why "Build Once, Deploy Many" Matters

Consider two approaches.

Bad workflow:

```text
Build for Development
↓
Rebuild for Testing
↓
Rebuild for Staging
↓
Rebuild for Production
```

Every rebuild creates another opportunity for something to change.

A stronger release model is:

```text
Build Once
↓
Store Artifact
↓
Test That Artifact
↓
Promote That Artifact
↓
Deploy That Artifact
```

Conceptually:

```text
Build
↓
payment-service-3.0.0.jar
↓
Development
↓
Testing
↓
Staging
↓
Production
```

The same artifact moves through the delivery lifecycle.

This gives the team greater confidence that the thing deployed to production is the thing that was tested.

# 33. Artifact Traceability

Traceability answers:

Where did this artifact come from?

Suppose you discover:

```text
payment-service-5.2.1.jar
```

running in production.

You may want to know:

* Which source repository produced it?
* Which Git commit produced it?
* Which CI build created it?
* When was it built?
* Which dependencies were used?
* Who or what published it?
* Which tests ran?
* Which version was deployed?
* Where else is it deployed?

Conceptually:

```text
Git Commit
↓
CI Build
↓
Artifact
↓
Repository
↓
Deployment
↓
Production
```

Traceability allows engineers to travel backward through that chain.

Production Problem
↓
Deployed Artifact
↓
Build
↓
Source Commit

This can dramatically improve incident investigation.

# 34. Checksums and Artifact Identity

A checksum is a value calculated from file contents using a hashing algorithm.

For example, an artifact repository can maintain checksum information for stored artifacts.

If a file changes, its cryptographic hash normally changes as well.

Conceptually:

```text
Artifact
↓
Hash Function
↓
Checksum
```

This helps systems verify artifact integrity and identify content.

For beginners, remember:

A filename tells you what someone called a file.

A checksum is derived from the file's actual contents.

These are not the same thing.

Two files could both be named:

```text
application-1.0.0.jar
```

while containing different data.

Their checksums would reveal that the content differs.

# 35. The Artifact Lifecycle

Artifacts do not simply appear in a repository and remain there forever.

They have a lifecycle.

A simplified lifecycle is:

```text
Create
↓
Build
↓
Test
↓
Publish
↓
Store
↓
Promote
↓
Deploy
↓
Operate
↓
Retain or Retire
```

Let's examine it.

## Stage 1: Create

Developers write source code.

## Stage 2: Build

A build tool processes the source and dependencies.

## Stage 3: Test

Automated tests and other checks may validate the software.

## Stage 4: Publish

The resulting artifact is uploaded to the artifact repository.

## Stage 5: Store

The repository preserves and organizes the artifact and associated information.

## Stage 6: Promote

A validated artifact may move through a release process or be marked for use in another stage.

## Stage 7: Deploy

The artifact is retrieved and deployed.

## Stage 8: Operate

The deployed software runs in an environment.

## Stage 9: Retain or Retire

Older artifacts may be retained for rollback, audit, or policy requirements, while obsolete artifacts may eventually be removed according to retention policies.

Later parts will turn this lifecycle into actual Artifactory workflows.

# 46. Why Dependency Caching Matters

Imagine 100 builds repeatedly need the same dependency.

Without a caching repository:

```text
Build 1 → Internet → Package
Build 2 → Internet → Package
Build 3 → Internet → Package
...
```

With a remote repository cache, the first request may retrieve the package from upstream.

Subsequent requests can potentially be served from Artifactory's cache.

Conceptually:

```text
First Request
Build
↓
Artifactory
↓
External Repository
↓
Cache Package

Later Request
Build
↓
Artifactory Cache
↓
Package
```

Benefits can include:

* Reduced repeated external downloads
* Faster dependency retrieval in many environments
* Better control over external dependency access
* Improved resilience when upstream availability changes, when the required package is already cached
* Centralized visibility into dependency consumption

This does not mean every external package will always remain available simply because Artifactory is present. Repository configuration and cache state still matter.

# 51. Beginner Mistakes to Avoid

## Mistake 1: "Artifactory is basically GitHub."

No.

GitHub's core role centers on source-code collaboration and Git hosting.

Artifactory's core role centers on package and artifact repository management.

## Mistake 2: "Artifacts are only JAR files."

No.

Artifacts can include many forms of packaged software, including container images, Helm charts, Python packages, npm packages, NuGet packages, and generic archives.

## Mistake 3: "Package manager and package repository mean the same thing."

No.

The package manager is the client/tool.

The repository stores or serves packages.

## Mistake 4: "Every build should replace the previous artifact."

Usually no for released artifacts.

Released artifacts should have deliberate identities and should not silently change.

## Mistake 5: "Production can just rebuild the source."

That weakens the build-once principle because the rebuilt output may differ from the artifact that was previously tested.

## Mistake 6: "Filename equals artifact identity."

Not necessarily.

Metadata, version information, checksums, build information, and other provenance data can also matter.

## Mistake 7: "Artifactory automatically makes builds reproducible."

No.

Artifactory can support controlled dependency and artifact management, but reproducibility also depends on the build process, environment, dependencies, toolchain, and configuration.

# 54. Troubleshooting Thinking: The Artifact Is Missing

Consider your first artifact-related incident.

A deployment says:

```text
Artifact not found
```

Do not immediately upload another random copy.

Use a troubleshooting process.

## Observe

What exactly failed?

```text
Artifact not found
```

## Identify What Was Requested

Was the deployment requesting:

```text
payment-api-1.0.0
```

or:

```text
payment-api-1.0.1
```

## Check the Repository

Does that exact version exist?

## Check the Path

Is the deployment looking in the correct repository and package path?

## Check Permissions

Can the deployment identity read the repository?

## Check the Build

Was the artifact successfully published?

## Form a Hypothesis

For example:

"The build succeeded, but the publishing stage failed."

## Test

Inspect the pipeline and repository.

## Fix

Correct the actual publishing or configuration problem.

## Verify

Run the retrieval/deployment again.

## Prevent

Improve pipeline validation so that a release cannot proceed if artifact publishing fails.

The reasoning pattern is:

```text
Symptom
↓
Evidence
↓
Hypothesis
↓
Test
↓
Root Cause
↓
Fix
↓
Verify
↓
Prevent
```

You will use this pattern repeatedly throughout the series.

### Answer 1

Source code contains the instructions developers create and modify. An artifact is a software output or package produced or managed for distribution, dependency use, testing, or deployment.

### Answer 2

Git is designed primarily for source version control. Generated binaries can be large, do not benefit from normal text diffs, and require package-management capabilities that Git does not provide as its primary function.

### Answer 3

A package manager is a client/tool that works with packages. A package repository stores and serves those packages.

### Answer 4

Versions allow teams to identify releases precisely, deploy specific software, troubleshoot changes, and roll back when necessary.

### Answer 5

An established release should not be silently replaced with different content while keeping the same release identity.

### Answer 6

Dependencies, build tools, environment variables, operating systems, configuration, toolchain versions, generated data, or other build inputs may differ.

### Answer 7

A dependency is external software, code, or a package that another application or build requires.

### Answer 8

It helps ensure that the artifact deployed later is the same artifact that was previously tested and validated.

### Answer 9

It helps determine the relationship between a deployed artifact and its source commit, build, dependencies, metadata, and deployment history.

Artifactory manages the artifact between the build and its later consumption or deployment.
