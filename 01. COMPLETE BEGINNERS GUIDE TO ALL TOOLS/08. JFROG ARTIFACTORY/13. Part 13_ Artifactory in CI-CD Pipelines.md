# Part 13: Artifactory in CI/CD Pipelines

In the previous parts, you learned how Artifactory can manage:

```text
Generic artifacts
Maven and Gradle packages
npm packages
Python packages
Container images
Helm charts
```

You also learned how individual engineers can upload, search, download, and manage artifacts.

But production software delivery should not depend on an engineer manually doing this:

```text
Build application
↓
Open browser
↓
Upload artifact
↓
Tell another engineer where it is
↓
Someone downloads it
↓
Someone deploys it
```

Once CI/CD enters the architecture, the workflow changes.

The pipeline becomes responsible for producing, testing, publishing, retrieving, promoting, and deploying artifacts in a controlled and repeatable way.

Our architecture becomes:

```text
Developer
↓
Git
↓
CI
↓
Build + Test
↓
Artifactory
↓
Deploy
↓
Application
```

But the real architecture is more detailed:

```text
Developer
↓
Git Commit
↓
CI Pipeline
↓
Checkout Source
↓
Resolve Dependencies
↓
Build
↓
Test
↓
Package
↓
Generate Version
↓
Publish Artifact
↓
Record Metadata
↓
Artifactory
↓
Deployment Pipeline
↓
Retrieve Exact Artifact
↓
Deploy
↓
Verify
↓
Application
```

This part teaches how those pieces fit together.

---

# 1. What Changes When CI/CD Is Introduced?

Before CI/CD, an engineer might manually run:

```bash
mvn package
```

or:

```bash
npm run build
```

or:

```bash
docker build ...
```

Then manually upload the resulting artifact.

With CI/CD:

```text
Git Event
↓
Pipeline Starts
↓
Pipeline Builds
↓
Pipeline Tests
↓
Pipeline Packages
↓
Pipeline Publishes
↓
Pipeline Records Result
```

The pipeline becomes the controlled build environment.

That matters because a production artifact should answer:

```text
Who produced this?

Which source commit produced it?

Which pipeline produced it?

Which build number?

Which dependencies were used?

Which tests passed?

When was it built?

What version is it?

Where is it stored?

Which environments received it?
```

Manual file sharing usually cannot answer these questions reliably.

A good CI/CD and Artifactory workflow can.

---

# 2. CI and CD Are Related but Different

You will often see:

```text
CI/CD
```

as though it is one concept.

It contains several related practices.

## Continuous Integration

CI focuses on integrating and validating software changes.

Typical CI work:

```text
Checkout
↓
Resolve Dependencies
↓
Compile/Build
↓
Unit Test
↓
Static Analysis
↓
Package
↓
Publish Artifact
```

The result should ideally be a deployable artifact.

---

# 3. Continuous Delivery

Continuous Delivery means software is kept in a deployable state and can move toward production through an automated release process, often with approvals or other controls where required.

Conceptually:

```text
CI
↓
Artifact
↓
Validation
↓
Staging
↓
Approval
↓
Production
```

---

# 4. Continuous Deployment

Continuous Deployment goes further.

A qualifying change can move automatically through the delivery process into production without a manual production approval step.

Conceptually:

```text
Commit
↓
Build
↓
Test
↓
Publish
↓
Validate
↓
Deploy Production
```

Whether this is appropriate depends on the organization, application, controls, risk, and testing maturity.

# 5. CI/CD Does Not Eliminate Artifact Management

A common beginner assumption is:

```text
We have Jenkins
therefore
we do not need Artifactory.
```

That misunderstands the roles.

Jenkins is primarily an automation/orchestration system.

Artifactory is an artifact repository and package-management platform.

Conceptually:

```text
Jenkins
↓
Performs Workflow

Artifactory
↓
Stores and Distributes Artifacts
```

Similarly:

```text
GitHub Actions
↓
Runs Workflow

Artifactory
↓
Stores and Distributes Artifacts
```

They complement each other.

---

# 6. Why Not Keep Everything in the CI Workspace?

Suppose Jenkins creates:

```text
target/veriqta-api-2.5.0.jar
```

The file exists in the Jenkins workspace.

But that workspace should not be treated as your long-term release repository.

Workspaces may be:

```text
Cleaned
Reused
Deleted
Recreated
Ephemeral
Bound to a particular agent
```

The artifact needs a controlled repository.

Therefore:

```text
CI Workspace
↓
Temporary Build Location

Artifactory
↓
Persistent Artifact Location
```

# 7. Artifactory as a Pipeline Boundary

This is one of the most important concepts in Part 13.

Think about the pipeline in two major phases:

```text
BUILD SIDE
↓
Source
↓
Build
↓
Test
↓
Package
↓
ARTIFACTORY
↓
DEPLOYMENT SIDE
↓
Retrieve
↓
Deploy
↓
Verify
```

Artifactory creates a durable boundary between:

```text
How software was built
```

and:

```text
Where software will be deployed.
```

---

# 8. Why This Boundary Matters

Without a repository boundary:

```text
CI Agent
↓
Build File
↓
Directly Copy to Server
```

Now the deployment may depend on:

```text
The original build agent
Its workspace
Its filesystem
Its network connection
Its temporary files
```

A better architecture is:

```text
Build Agent
↓
Artifact
↓
Artifactory
↓
Deployment System
↓
Target Environment
```

The deployment system does not need the original CI workspace.

It needs the artifact identity.

---

# 9. Build Once, Deploy Many

This is the central principle of this part.

Suppose your application passes through:

```text
Development
↓
Testing
↓
Staging
↓
Production
```

A poor workflow could do:

```text
Build for Development
↓
Deploy

Build Again for Testing
↓
Deploy

Build Again for Staging
↓
Deploy

Build Again for Production
↓
Deploy
```

Now you have four builds.

Even if they use the same source code, they are technically four different build events.

---

# 10. Why Rebuilding Is Dangerous

Imagine build 100 produced:

```text
veriqta-api-2.5.0.jar
```

and passed all testing.

Before production, the pipeline rebuilds it.

The second build might differ because of:

```text
Dependency changes
Build environment changes
Compiler changes
Base image changes
Timestamp-generated content
Network dependency changes
Configuration mistakes
Build tool changes
Unpinned dependencies
```

Now:

```text
Artifact Tested
≠
Artifact Deployed
```

That weakens confidence in your release.

---

# 11. Better Pattern

Build:

```text
ONE artifact
```

Then:

```text
Build Once
↓
Store
↓
Test
↓
Promote
↓
Deploy Development
↓
Deploy Testing
↓
Deploy Staging
↓
Deploy Production
```

The same artifact identity travels through the lifecycle.

Conceptually:

```text
Source Commit abc123
↓
Build 417
↓
Artifact 2.5.0
↓
SHA-256 XYZ
↓
Artifactory
├── Development
├── Testing
├── Staging
└── Production
```

The environments change.

The application artifact does not.

# 21. Credentials in Pipelines

CI/CD introduces a serious security problem:

**Machines need credentials.**

The pipeline may need credentials for:

```text
Git
Artifactory
Container registry
Cloud provider
Kubernetes
Signing service
Deployment system
```

Do not solve this by putting passwords directly in pipeline files.

Bad:

```groovy
ARTIFACTORY_PASSWORD = "MyPassword123"
```

Bad:

```yaml
env:
  ARTIFACTORY_TOKEN: "my-real-token"
```

Bad:

```bash
curl -u admin:password ...
```

especially when committed to Git.

---

# 22. Why Hardcoded Secrets Are Dangerous

Pipeline definitions usually live in source control.

Therefore:

```text
Secret in Pipeline File
↓
Git Commit
↓
Repository History
↓
Copies/Forks/Backups/Logs
```

Deleting the current line does not necessarily remove the secret from history.

Use the CI system's approved secret storage or an external secret-management system.

---

# 23. Secret Injection

A better pattern:

```text
Secret Store
↓
CI Platform
↓
Temporary Runtime Variable/File
↓
Build Step
↓
Artifactory
```

The pipeline definition references a secret identifier.

It does not contain the secret itself.

---

# 24. Least Privilege

Suppose CI only needs to publish to:

```text
veriqta-generic-dev
```

Do not give it:

```text
Artifactory administrator
```

Give it the minimum required permissions.

Conceptually:

```text
CI Build Identity
↓
Read Dependencies
+
Write Build Repository
```

A deployment identity might need:

```text
Read Release Repository
```

but not:

```text
Delete Packages
Create Users
Change Permissions
Administer Artifactory
```

---

# 25. Separate Pipeline Identities

Consider:

```text
Build Pipeline Identity
↓
Read dependencies
Write development artifacts

Release Pipeline Identity
↓
Promote approved artifacts

Deployment Identity
↓
Read production artifacts
```

This is stronger than:

```text
One administrator token
↓
Everything
```

If one credential is compromised, the blast radius is smaller.

---

# 26. Secret Masking Is Not the Same as Secret Security

CI systems may mask known secret values in logs.

For example:

```text
Token:
****
```

Useful.

But masking does not mean:

```text
The secret cannot leak.
```

A badly written script may:

```text
Transform secret
Encode secret
Write secret to file
Upload secret as artifact
Expose secret in generated configuration
```

Treat secret masking as one control, not your entire security strategy.

---

# 27. Avoid Shell Debugging Around Secrets

A shell can be configured to print commands as they execute.

For example:

```bash
set -x
```

This can be useful for debugging.

But it can expose expanded secret-bearing commands.

Do not casually enable verbose shell tracing in production pipelines that handle credentials.


# 49. Shell Exit Status

On Unix-like systems:

```text
0
↓
Success

Non-zero
↓
Failure
```

You can inspect the previous command's status interactively with:

```bash
echo $?
```

In CI, the runner normally uses command exit status to determine whether a step succeeded.

This is why scripts must fail correctly.

---

# 50. Dangerous Script

Bad:

```bash
mvn package
echo "Build completed"
exit 0
```

If Maven fails but the script ultimately forces:

```text
exit 0
```

the CI system may interpret the script as successful.

That can allow later stages to continue incorrectly.

Do not hide failures.

---

# 51. Safer Bash Behavior

You may see scripts start with:

```bash
#!/usr/bin/env bash

set -euo pipefail
```

This is common defensive Bash configuration.

Let's understand it.

---

# 52. `set -e`

```bash
set -e
```

generally tells Bash to exit when an unhandled command fails.

It can reduce accidental continuation after errors.

However, Bash error behavior has important context-dependent exceptions.

Do not treat `set -e` as a substitute for understanding your script's control flow.

---

# 53. `set -u`

```bash
set -u
```

treats use of unset variables as errors in many contexts.

Suppose:

```bash
echo "$ARTIFACTORY_TOKEN"
```

but the variable was never supplied.

Instead of silently becoming empty, the script can fail.

This helps catch configuration errors.

---

# 54. `pipefail`

Without appropriate pipeline failure handling:

```bash
command-that-fails | command-that-succeeds
```

can produce misleading success behavior depending on how the shell evaluates the pipeline.

With:

```bash
set -o pipefail
```

a failure within the pipeline can propagate appropriately.

Together:

```bash
set -euo pipefail
```

is common in CI Bash scripts.

But you must still deliberately handle commands that are expected to fail.

---

# 55. Verify the Artifact Exists

Before upload:

```bash
test -f "dist/veriqta-api-2.5.0.tar.gz"
```

`test -f` checks whether the path exists and is a regular file.

A more explicit script:

```bash
ARTIFACT="dist/veriqta-api-2.5.0.tar.gz"

if [ ! -f "$ARTIFACT" ]; then
  echo "ERROR: Expected artifact does not exist: $ARTIFACT"
  exit 1
fi
```

Now the pipeline refuses to publish something that was never built.

---

# 56. Verify the Artifact

You can also inspect:

```bash
ls -lh "$ARTIFACT"
```

and calculate a checksum.

On macOS:

```bash
shasum -a 256 "$ARTIFACT"
```

On many Linux systems:

```bash
sha256sum "$ARTIFACT"
```

The checksum gives you a content fingerprint.

# 57. Upload the Artifact

Conceptually:

```bash
jf rt upload \
  "dist/veriqta-api-2.5.0.tar.gz" \
  "veriqta-generic-dev/veriqta-api/2.5.0/" \
  --server-id=veriqta-ci
```

Breakdown:

```text
jf
↓
JFrog CLI

rt
↓
Artifactory-related command group

upload
↓
Upload operation

dist/...
↓
Local source

veriqta-generic-dev/...
↓
Artifactory destination

--server-id
↓
Configured JFrog server identity
```

# 58. Attach Properties

Conceptually:

```bash
jf rt upload \
  "dist/veriqta-api-2.5.0.tar.gz" \
  "veriqta-generic-dev/veriqta-api/2.5.0/" \
```

# 59. Do Not Hardcode Build 417

In a real pipeline:

```text
417
```

should come from the CI system.

Similarly:

```text
abc123
```

should come from Git.

The pipeline should derive metadata from the actual execution.

Conceptually:

```bash
BUILD_NUMBER="<CI_BUILD_NUMBER>"
GIT_COMMIT="$(git rev-parse HEAD)"
```

The exact environment variable names differ across CI systems.

# 63. What CI Should Hand to CD

CI should not tell CD:

```text
Go into my workspace and find the file.
```

It should provide artifact identity.

For example:

```text
Repository:
veriqta-generic-release

Path:
veriqta-api/2.5.0/veriqta-api-2.5.0.tar.gz

Version:
2.5.0

Checksum:
sha256:...
```

Or for containers:

```text
Image:
company.jfrog.io/veriqta-api:2.5.0

Digest:
sha256:...
```

The deployment system now has a stable contract.

# 64. Retrieving Deployment Artifacts

The deployment pipeline should retrieve the exact artifact.

Example:

```bash
jf rt download \
  "veriqta-generic-release/veriqta-api/2.5.0/veriqta-api-2.5.0.tar.gz" \
  "./release/" \
  --server-id=veriqta-ci
```

Then verify it.

The deployment pipeline should not run:

```bash
./build.sh
```

again.

---

# 65. Why CD Should Not Rebuild

CI already established:

```text
Source
↓
Build
↓
Tests
↓
Artifact
```

CD should establish:

```text
Approved Artifact
↓
Target Environment
↓
Deployment
↓
Verification
```

If CD rebuilds:

```text
CI Artifact
↓
Ignored

CD
↓
New Artifact
```

you have broken the chain.

---

# 66. Promotion

A candidate artifact might first live in:

```text
veriqta-generic-dev
```

After validation:

```text
Candidate
↓
Tests
↓
Approval
↓
Promotion
↓
veriqta-generic-release
```

The key rule:

**Promotion should preserve the artifact's content identity.**

If the candidate checksum is:

```text
sha256:ABC
```

the promoted release should still represent:

```text
sha256:ABC
```

Do not rebuild it during promotion.

# 67. Environment Promotion

Another model uses metadata or release-management controls rather than physically copying an artifact for every environment.

Conceptually:

```text
Artifact
↓
Candidate
↓
Approved for Development
↓
Approved for Staging
↓
Approved for Production
```

The exact mechanism depends on your JFrog architecture and release-management approach.

The universal principle remains:

```text
Promote identity/state
not source code rebuilds.
```

# 76. Beginner Jenkins Pipeline

# 77. Why Tests Come Before Publish

Bad:

```text
Build
↓
Publish
↓
Test
```

Now broken artifacts may already be sitting in a repository presented as valid candidates.

Better:

```text
Build
↓
Test
↓
Package/Verify
↓
Publish
```

Depending on the workflow, some integration tests may happen after publishing a candidate artifact. That can be valid.

But artifact lifecycle state should accurately represent what has been validated.

# 82. Jenkins Publishing Script

A reusable script might look conceptually like:

```bash
#!/usr/bin/env bash

set -euo pipefail

APP_NAME="veriqta-api"
VERSION="${VERSION:?VERSION is required}"
BUILD_NUMBER="${BUILD_NUMBER:?BUILD_NUMBER is required}"
SERVER_ID="veriqta-ci"

ARTIFACT="dist/${APP_NAME}-${VERSION}.tar.gz"
TARGET="veriqta-generic-dev/${APP_NAME}/${VERSION}/"

if [ ! -f "$ARTIFACT" ]; then
  echo "ERROR: Artifact not found: $ARTIFACT"
  exit 1
fi

GIT_COMMIT="$(git rev-parse HEAD)"

jf rt upload \
  "$ARTIFACT" \
  "$TARGET" \
  --props="application=${APP_NAME};version=${VERSION};build-number=${BUILD_NUMBER};git-commit=${GIT_COMMIT};stage=candidate" \
  --server-id="$SERVER_ID"

jf rt search \
  "${TARGET}${APP_NAME}-${VERSION}.tar.gz" \
  --server-id="$SERVER_ID"
```

Notice what is not inside the script:

```text
Artifactory password
Admin token
Production secret
```

# 83. `${VARIABLE:?message}`

This Bash syntax:

```bash
VERSION="${VERSION:?VERSION is required}"
```

means conceptually:

```text
If VERSION exists
↓
Use it

If VERSION is missing/unset
↓
Fail with message
```

This is useful in pipelines.

You want:

```text
Missing Version
↓
Pipeline Fails
```

not:

```text
Missing Version
↓
Upload to strange path
```

# 100. Pipeline Failure Handling

A pipeline must answer:

```text
What happens if a stage fails?
```

Suppose:

```text
Checkout
↓
Build
↓
Tests FAIL
```

The correct behavior is generally:

```text
Stop release flow
↓
Do not promote
↓
Report failure
```

Not:

```text
Tests fail
↓
Ignore
↓
Production
```

---

# 101. Fail Fast

If a required condition fails early, stop.

Examples:

```text
Required secret missing
Artifact missing
Build failed
Tests failed
Checksum mismatch
Upload failed
Required artifact cannot be retrieved
```

Do not continue hoping a later stage fixes an earlier failure.

---

# 102. But Preserve Evidence

Fail fast does not mean:

```text
Delete everything immediately.
```

You may need evidence such as:

```text
Logs
Test reports
Build output
Diagnostic data
Metadata
```

for troubleshooting.

A good pipeline:

```text
Fails safely
+
Preserves useful evidence
```

without accidentally publishing broken output as a release.

---

# 103. Retry Carefully

Some failures are transient:

```text
Temporary network problem
Temporary service unavailability
Rate limit
```

Retries can help.

But blindly retrying every failure is dangerous.

For example:

```text
403 Forbidden
```

is probably not fixed by retrying 50 times.

Likewise:

```text
Artifact not found
```

may indicate the wrong version.

Classify the failure first.

---

# 104. Idempotency

A useful automation concept is:

```text
Idempotency
```

Roughly, an operation is idempotent when safely repeating it leads to the intended state rather than creating uncontrolled duplicate effects.

Deployment and publishing workflows should consider:

```text
What happens if this job runs twice?
```

For immutable release versions:

```text
Second upload of different bytes
↓
Should not silently replace release
```

This is one reason immutability matters.

---

# 105. Duplicate Pipeline Runs

Imagine two pipelines both attempt:

```text
Release:
2.5.0
```

One comes from:

```text
Commit A
```

and another:

```text
Commit B
```

If both can overwrite:

```text
veriqta-api-2.5.0.tar.gz
```

your release identity is broken.

A version should map to one approved artifact identity.

The principle:

```text

```

# 120. Do Not Confuse CI Cache With Artifact Repository

CI systems may also provide caches.

For example:

```text

```

A cache and an artifact repository serve different purposes.

Cache:

```text
Performance optimization
Potentially disposable
```

Artifact repository:

```text
Controlled artifact system of record/distribution point
```

Do not make your production release depend only on an ephemeral CI cache.

# 145. Pull Request Security

Be especially careful with pipelines triggered from untrusted contributions.

A pull request may contain modified:

```text

Build files
Workflow-adjacent code
Tests
```

If that untrusted code receives powerful production credentials, an attacker may attempt to exfiltrate them.

```text
Untrusted Code
↓
Should Not Automatically Receive Powerful Secrets
```

Design CI permissions accordingly.

```text
↓

↓
```

```bash
  "$ARTIFACT" \
  "$TARGET" \
  --props="application=${APP_NAME};version=${VERSION};build-number=${BUILD_NUMBER};git-commit=${GIT_COMMIT};stage=candidate" \
  --server-id="$SERVER_ID"

jf rt search \
  "${TARGET}${APP_NAME}-${VERSION}.tar.gz" \
  --server-id="$SERVER_ID"

echo "Artifact publication verified."
EOF
```

# 189. Deployment Script

Create:

```bash
cat > scripts/deploy.sh <<'EOF'
#!/usr/bin/env bash

set -euo pipefail

VERSION="${VERSION:?VERSION is required}"

APP_NAME="veriqta-api"
SERVER_ID="veriqta-ci"

SOURCE="veriqta-generic-release/${APP_NAME}/${VERSION}/${APP_NAME}-${VERSION}.tar.gz"
DESTINATION="./release/"

mkdir -p release

echo "Retrieving release version $VERSION"

jf rt download \
  "$SOURCE" \
  "$DESTINATION" \
  --server-id="$SERVER_ID"

find release -type f
EOF
```
