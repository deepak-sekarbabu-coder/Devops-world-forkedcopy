# Part 4: Repository Types, Local, Remote, Virtual, and Federated

Repository types are one of the most important foundations in JFrog Artifactory.

If you misunderstand repositories, everything that comes later becomes harder.

You may know how to upload a file, but still not know:

* Where it should be uploaded
* Why that repository exists
* Whether Artifactory owns the artifact
* Whether the artifact came from somewhere else
* Whether a repository is only providing one endpoint over several repositories
* Why a dependency is available even when the public registry is temporarily unavailable
* Why developers normally should not configure every underlying repository individually
* Why the same repository may exist across several JFrog Platform Deployments

In Part 3, we prepared this environment:

```text
Computer
↓
JFrog Environment
↓
Repository
↓
First Artifact
```

But we intentionally stopped before uploading the artifact.

Why?

Because "repository" is not one single thing in Artifactory.

Artifactory has four major repository types:

```text
Local
Remote
Virtual
Federated
```

They solve different problems.

By the end of this part, you should understand the architecture:

```text
Developer
↓
Virtual Repository
├── Local Repository
└── Remote Repository
        ↓
Public Package Registry
```

You will also build a small repository structure and follow dependency requests through it.

---

# 1. Start From Zero: What Is a Repository?

A repository is an organized location through which software packages, artifacts, and related metadata are stored, resolved, or made available.

In simple terms:

```text
Repository
=
A controlled place for software artifacts
```

But in Artifactory, a repository can do more than physically store artifacts.

Depending on its type, a repository might:

* Store artifacts your organization produces
* Proxy another repository
* Cache dependencies downloaded from an external registry
* Combine several repositories behind one endpoint
* Synchronize artifacts with Artifactory environments at other sites

That is why we cannot define every Artifactory repository simply as:

> A folder containing files.

That definition is too limited.

A better mental model is:

```text
Artifactory Repository
↓
A logical artifact boundary
↓
With a specific purpose and behavior
```

---

# 2. The Four Repository Types

At the highest level:

```text
Artifactory
│
├── Local Repository
│
├── Remote Repository
│
├── Virtual Repository
│
└── Federated Repository
```

For a beginner, remember them like this:

| Repository | Main purpose                                                     |
| ---------- | ---------------------------------------------------------------- |
| Local      | Store artifacts your organization publishes                      |
| Remote     | Proxy and optionally cache artifacts from another repository     |
| Virtual    | Present multiple repositories through one logical endpoint       |
| Federated  | Synchronize repository content across JFrog Platform Deployments |

Do not memorize only this table.

We will now build the reasoning behind every type.

---

# 3. Why Does Artifactory Need Different Repository Types?

Imagine a development team building an application.

The application requires:

```text
Internal application code
+
Internal libraries
+
Open-source dependencies
```

The organization may produce:

```text
payment-service-1.0.0.jar
```

But the application might also depend on external software.

For example:

```text
Application
├── Internal package
├── Internal library
├── Framework
├── Logging library
└── Other third-party dependencies
```

Some artifacts belong to your organization.

Others belong to external publishers.

Artifactory needs to distinguish between them.

A simple architecture becomes:

```text
Internal Artifacts
↓
Local Repository

External Artifacts
↓
Remote Repository
```

Then Artifactory can place both behind:

```text
Virtual Repository
```

This produces:

```text
Developer
↓
Virtual Repository
├── Local Repository
└── Remote Repository
        ↓
External Registry
```

This architecture is central to Artifactory.

---

# 4. What Does "Resolve" Mean?

You will repeatedly encounter the word:

```text
resolve
```

Suppose your application requires dependency:

```text
library-x:2.4.0
```

Your build tool needs to find and retrieve it.

That process is dependency resolution.

Conceptually:

```text
Build Tool
↓
"I need library-x version 2.4.0"
↓
Repository
↓
Find package
↓
Download package
```

So when we say:

> Artifactory resolves an artifact

we mean Artifactory determines where the requested artifact is available and returns it to the requesting client when permitted.

---

# 5. Upload vs Download vs Resolution

Keep these terms separate.

## Upload

You send an artifact to Artifactory.

```text
Developer / CI
↓
Artifact
↓
Artifactory
```

## Download

You retrieve a known artifact.

```text
Artifactory
↓
Artifact
↓
Client
```

## Dependency resolution

A package manager or build tool determines which dependencies are needed and requests them from configured repositories.

```text
Build
↓
Dependency Requirement
↓
Repository
↓
Dependency Located
↓
Dependency Returned
```

Package managers often perform many requests during one build.

---

# 6. Repository Keys

Every repository needs an identifier.

In Artifactory, this is the repository key.

Example:

```text
veriqta-generic-local
```

JFrog currently defines the repository key as a mandatory unique identifier. A repository key cannot begin with a number or contain spaces or special characters.

Think:

```text
Repository:
VERIQTA Generic Local Repository

Repository Key:
veriqta-generic-local
```

The key becomes important because it appears in:

* URLs
* CLI operations
* API requests
* Configuration
* Permissions
* Automation
* Logs

---

# 7. Repository Key vs Repository Path

Do not confuse them.

Suppose:

```text
veriqta-generic-local/releases/payment-api/1.0.0/payment-api-1.0.0.zip
```

Break it down:

```text
veriqta-generic-local
↓
Repository key

releases/payment-api/1.0.0/
↓
Path inside repository

payment-api-1.0.0.zip
↓
Artifact
```

The complete logical location is:

```text
Repository
+
Path
+
Artifact
```

# 8. Repository Naming

Repository names should communicate purpose.

Bad names:

```text
repo1
repo2
test-new
final-repo
stuff
packages2
```

A better naming system tells an engineer something about the repository.

For example:

```text
veriqta-generic-local
```

Immediately suggests:

```text
veriqta
↓
Organization/project context

generic
↓
Package type

local
↓
Repository type
```

Another example:

```text
veriqta-npm-remote
```

means:

```text
VERIQTA
+
npm
+
Remote repository
```

---

# 9. A Practical Naming Pattern

A simple beginner naming convention is:

```text
<context>-<package-type>-<repository-type>
```

Examples:

```text
veriqta-generic-local
veriqta-generic-remote
veriqta-generic-virtual

veriqta-maven-local
veriqta-maven-remote
veriqta-maven-virtual

veriqta-npm-local
veriqta-npm-remote
veriqta-npm-virtual
```

Organizations may use more detailed conventions.

For example:

```text
team-package-environment-type
```

or:

```text
project-package-stage-location-type
```

Do not create complexity before you need it.

For a beginner lab:

```text
veriqta-generic-local
```

is much clearer than:

```text
vqt-generic-art-dev-use1-local-v2
```

# 10. Package Types

When creating a repository, Artifactory needs to know what package ecosystem it represents.

Examples include:

```text
Generic
Maven
Gradle
npm
PyPI
NuGet
Docker
Helm
Go
Debian
RPM
Cargo
Conan
```

JFrog currently requires the package type to be selected when a local repository is created, and it cannot simply be changed afterward.

Why?

Because different ecosystems behave differently.

For example:

```text
Maven
↓
Maven coordinates and metadata

npm
↓
npm registry behavior and metadata

PyPI
↓
Python package metadata

Docker
↓
Manifests + image layers

Generic
↓
Arbitrary file paths
```

Artifactory needs to understand the package ecosystem to provide the appropriate repository behavior.

---

# 11. Repository Type vs Package Type

This is a major beginner distinction.

Repository type answers:

```text
What does this repository do?
```

Examples:

```text
Local
Remote
Virtual
Federated
```

Package type answers:

```text
What package ecosystem does it serve?
```

Examples:

```text
Maven
npm
PyPI
Docker
Generic
```

Therefore:

```text
Repository Type:
Local

Package Type:
Maven
```

is valid.

So is:

```text
Repository Type:
Remote

Package Type:
Maven
```

and:

```text
Repository Type:
Virtual

Package Type:
Maven
```

These are different dimensions.

---

# 12. Why You Should Not Mix Package Types Carelessly

Suppose you are building a Maven architecture.

A sensible structure is:

```text
maven-local
maven-remote
maven-virtual
```

Your Maven virtual repository should aggregate Maven-compatible repositories.

JFrog recommends keeping a virtual repository within one package type rather than mixing unrelated package ecosystems.

Do not create:

```text
everything-virtual
├── Maven
├── npm
├── PyPI
├── Docker
└── Generic
```

and assume every package manager will understand it.

Package managers have ecosystem-specific expectations.

# 13. Local Repositories

Now we reach the first major repository type.

A local repository stores artifacts that are deployed directly into your Artifactory environment.

Think:

```text
Your Organization
↓
Produces Artifact
↓
Uploads Artifact
↓
Local Repository
```

Example:

Your team builds:

```text
payment-api-1.0.0.jar
```

Then publishes it:

```text
CI Pipeline
↓
payment-api-1.0.0.jar
↓
company-maven-local
```

That is a typical local repository use case.

---

# 14. Why Is It Called "Local"?

"Local" does not mean:

```text
stored on your laptop
```

It means the repository belongs to and is directly managed by this Artifactory environment rather than representing an upstream repository.

Conceptually:

```text
Local Repository
↓
Your Artifactory
↓
Your managed artifacts
```

---

# 15. What Goes Into a Local Repository?

Typical examples:

```text
Internal JARs
Internal npm packages
Internal Python packages
Internal NuGet packages
Application ZIP files
Helm charts
Container images
Release bundles
Other internal binaries
```

For our beginner lab:

```text
veriqta-demo-1.0.0.txt
```

can be stored in:

```text
veriqta-generic-local
```

# 16. Local Repository Flow

Imagine CI builds an application.

```text

↓
Git
↓
CI
↓
Build
↓
payment-api-1.0.0.jar
↓
Local Artifactory Repository
```

The artifact now becomes available for downstream processes.

For example:

```text
Local Repository

Testing

Deployment
```

The key point is:

```text
Your organization produced the artifact.
```

Suppose VERIQTA has an internal tool:

```text
veriqta-deploy-tool
```

The build produces:

```text
veriqta-deploy-tool-1.0.0.zip
```

A local Generic repository might contain:

```text
veriqta-generic-local/

    └── veriqta-deploy-tool/
```

# 18. Local Repositories and Versions

You might eventually have:

```text
veriqta-generic-local/
└── tools/
    └── deploy-tool/
        ├── 1.0.0/
        │   └── deploy-tool-1.0.0.zip
        ├── 1.1.0/
        │   └── deploy-tool-1.1.0.zip
        └── 2.0.0/
            └── deploy-tool-2.0.0.zip
```

Now Artifactory contains an artifact history.

That is much better than:

```text
deploy-tool-final.zip
deploy-tool-final2.zip
deploy-tool-final-real.zip
deploy-tool-use-this.zip
```

# 19. When Should You Use a Local Repository?

Use a local repository when your organization needs to publish and manage its own artifacts.

Examples:

```text
CI build output
Internal libraries
Internal packages
Release binaries
Internal Docker images
Private Helm charts
Application deployment packages
```

Think:

```text
We produced it
↓
Local repository
```

That rule is simple enough for now.

# 20. Remote Repositories

A remote repository solves a completely different problem.

Suppose your application needs a third-party dependency.

Without Artifactory:

```text
Developer
↓
Package Manager
↓
Internet
↓
Public Registry
```

For example:

```text
npm
↓
Public npm registry
```

or:

```text
Maven
↓
Maven Central
```

Artifactory can sit between your client and that upstream repository.

```text
Developer
↓
Artifactory Remote Repository
↓
Public Registry
```

The remote repository acts as a proxy.

JFrog explicitly describes remote repositories as proxies rather than mirrors. Artifacts are generally fetched on demand instead of Artifactory downloading an entire upstream repository when the remote repository is created.

---

# 21. What Is an Upstream Repository?

"Upstream" means the source repository that the Artifactory remote repository points toward.

Architecture:

```text
Developer
↓
Artifactory Remote Repository
↓
Upstream Repository
```

The upstream could be:

```text
Public package registry
Another Artifactory repository
Vendor repository
Internal repository at another location
```

For example:

```text
npmjs-remote
↓
npm public registry
```

or:

```text
maven-central-remote
↓
Maven Central
```

The remote repository does not become the original publisher.

It acts as an intermediary.

---

# 22. Dependency Proxying

Suppose your build requires:

```text
library-x:2.0.0
```

Instead of allowing the build to go directly to the internet:

```text
Build
↓
Internet
↓
Public Registry
```

you configure it to use Artifactory:

```text
Build
↓
Artifactory
↓
Remote Repository
↓
Public Registry
```

Artifactory proxies the request.

This is dependency proxying.

---

# 23. First Request Through a Remote Repository

Suppose dependency:

```text
library-x-2.0.0
```

has never been requested before.

The flow is approximately:

```text
Developer
↓
Requests library-x-2.0.0
↓
Remote Repository
↓
Check local cache
↓
Not cached
↓
Contact upstream
↓
Public Registry
↓
Download artifact
↓
Return through Artifactory
↓
Developer
```

When local storage of remote artifacts is enabled, Artifactory also caches the retrieved artifact.

---

# 24. What Is Caching?

Caching means storing a retrieved copy so future requests may be served locally.

First request:

```text
Developer
↓
Artifactory
↓
Cache Miss
↓
Internet
↓
Upstream
↓
Artifact
↓
Artifactory Cache
↓
Developer
```

Later request:

```text
Developer
↓
Artifactory
↓
Cache Hit
↓
Developer
```

The second request may no longer require downloading the binary again from the public source.

---

# 25. Cache Hit vs Cache Miss

You need these terms.

## Cache hit

Artifactory already has the requested cached content available.

```text
Request
↓
Cache
↓
FOUND
↓
Return artifact
```

## Cache miss

The requested content is not available in cache.

```text
Request
↓
Cache
↓
NOT FOUND
↓
Check upstream
```

This terminology appears across many computing systems, including:

* CPUs
* Browsers
* CDNs
* Databases
* Package repositories

---

# 26. Remote Repository Cache

A remote repository has an associated cache.

JFrog documents that each remote repository has a dedicated cache, typically represented with a name based on:

```text
<remote-repository>-cache
```

Artifacts successfully resolved through the remote repository can be stored there.

For example:

```text
maven-central-remote
```

may have a corresponding cache conceptually represented as:

```text
maven-central-remote-cache
```

You normally interact with the remote repository, not by manually treating its cache as your own deployment repository.

---

# 27. Remote Repository Is Not a Mirror

This is worth repeating.

When you create:

```text
maven-central-remote
```

Artifactory does not automatically download every artifact from Maven Central.

That would be enormous and unnecessary.

Instead:

```text
Remote created
↓
Cache initially empty
```

Then:

```text
Client requests package A
↓
Package A fetched
↓
Package A cached
```

Later:

```text
Client requests package B
↓
Package B fetched
↓
Package B cached
```

JFrog explicitly distinguishes this proxy-on-demand behavior from mirroring.

---

# 28. Why Cache Dependencies?

Caching provides several benefits.

## Reduced repeated external downloads

Without cache:

```text
Developer A → Internet
Developer B → Internet
CI Build 1 → Internet
CI Build 2 → Internet
CI Build 3 → Internet
```

With Artifactory:

```text
Developer A ─┐
Developer B ─┤
CI Build 1 ──┼→ Artifactory Cache → Upstream when needed
CI Build 2 ──┤
CI Build 3 ──┘
```

Once an artifact is cached, repeated binary retrieval can often be served internally.

---

# 29. Caching and Build Reliability

Suppose a build requires:

```text
dependency-x-4.2.1
```

The artifact has previously been resolved and cached.

If the upstream registry later experiences problems, the cached binary may still be available locally.

That can reduce dependency on external availability.

But do not misunderstand this.

Caching does not magically guarantee that every build will always work offline.

Metadata, uncached artifacts, cache configuration, package-manager behavior, and repository settings still matter.

JFrog notes that expired metadata caches combined with an unavailable upstream can still produce resolution failures in some scenarios.

---

# 30. Offline Behavior

Artifactory allows remote repositories to be placed into offline mode.

When a remote repository is offline:

```text
Client
↓
Remote Repository
↓
Cached Content Only
```

Artifactory does not attempt to retrieve new artifacts from the upstream.

JFrog documents that an offline remote repository serves only artifacts already available from its local cache.

This is useful when:

* An upstream is unavailable
* An organization intentionally disconnects external access
* You are diagnosing remote connectivity
* A secure network must operate without internet access

---

# 31. What Happens to an Uncached Artifact Offline?

Suppose:

```text
package-a
```

is cached.

But:

```text
package-b
```

has never been downloaded.

If the remote repository is offline:

```text
Request package-a
↓
Cache
↓
FOUND
↓
Success
```

But:

```text
Request package-b
↓
Cache
↓
NOT FOUND
↓
Cannot contact upstream
↓
Failure
```

This is why:

```text
Artifactory cache
```

does not mean:

```text
Complete copy of the internet.
```

---

# 32. Why Proxy Dependencies Instead of Going Directly to Public Registries?

A company could configure every developer and CI pipeline to use public registries directly.

But centralizing dependency access through Artifactory provides operational benefits.

It can give organizations:

* Central dependency access
* Caching
* Repository access control
* Consistent endpoints
* Better visibility
* Controlled upstream configuration
* Integration with security and governance processes

Architecture:

```text
Developers
CI
Build Servers
     │
     ↓
Artifactory
     │
     ↓
Approved Upstreams
```

Instead of:

```text
Developer A → random registry
Developer B → different registry
CI → another registry
Script → random URL
```

---

# 33. When Should You Use a Remote Repository?

Use a remote repository when Artifactory should proxy another repository.

Examples:

```text
Maven Central
npm registry
PyPI
Docker registry
Vendor package repository
Another Artifactory instance
```

Mental rule:

```text
Someone else hosts the upstream artifacts
↓
Remote repository
```

# 34. Do You Upload Internal Builds to a Remote Repository?

Normally, no.

This is a common beginner mistake.

Wrong mental model:

```text
Our application build
↓
Remote Repository
```

Correct:

```text
Our application build
↓
Local Repository
```

Remote:

```text
External/upstream dependency
↓
Remote Repository proxy/cache
```

Remember:

```text
Produced here
→ Local

Retrieved from upstream
→ Remote
```

# 35. Virtual Repositories

Now imagine your developer needs both:

```text
Internal packages
+
External packages
```

You have:

```text
company-maven-local
```

and:

```text
maven-central-remote
```

Should developers configure both individually?

They could.

But Artifactory provides a better abstraction:

```text
Virtual Repository
```

---

# 36. What Is a Virtual Repository?

A virtual repository aggregates other repositories behind one logical endpoint.

Architecture:

```text
Developer
↓
Virtual Repository
├── Local Repository
└── Remote Repository
```

The developer does not need to know which underlying repository contains the artifact.

They request it from the virtual repository.

Artifactory handles resolution across the repositories included in that virtual repository.

---

# 37. Repository Aggregation

Aggregation means presenting multiple repositories together.

Suppose:

```text
veriqta-maven-virtual
```

contains:

```text
veriqta-maven-local
maven-central-remote
```

The virtual repository becomes:

```text
veriqta-maven-virtual
├── veriqta-maven-local
└── maven-central-remote
```

The client configures:

```text
veriqta-maven-virtual
```

rather than separately configuring every repository.

---

# 38. Why Virtual Repositories Matter

Without a virtual repository:

```text
Developer
├── Configure internal repository
├── Configure Maven Central proxy
├── Configure another internal repository
└── Configure another approved upstream
```

With a virtual repository:

```text
Developer
↓
Configure one endpoint
```

Artifactory administrators can change the underlying repository composition without requiring every developer to completely redesign their client configuration.

That abstraction is extremely useful.

---

# 39. Virtual Repository Request Flow

Suppose the client requests:

```text
veriqta-common-1.0.0.jar
```

The virtual repository may find it in:

```text
veriqta-maven-local
```

Flow:

```text
Developer
↓
veriqta-maven-virtual
↓
veriqta-maven-local
↓
Artifact found
↓
Developer
```

Now suppose the client requests a third-party library.

Flow:

```text
Developer
↓
veriqta-maven-virtual
↓
Remote repository/cache
↓
If needed, upstream registry
↓
Artifact
↓
Developer
```

The developer still uses the same virtual endpoint.

---

# 40. Resolution Order Matters

A virtual repository does not randomly search everywhere.

Repository order and Artifactory's resolution behavior matter.

JFrog's repository-organization guidance describes virtual resolution broadly in this order:

```text
Local repositories
↓
Remote repository caches
↓
Remote repositories/upstreams
```

with repositories considered according to their configured ordering.

This is important.

If the same package/path can appear in multiple repositories, ordering can affect resolution behavior.

---

# 41. Why Put Local Repositories First?

Imagine:

```text
company-library-1.0.0
```

exists internally.

You generally want the organization's intended internal repository to be considered appropriately before unnecessarily going outside.

A virtual repository can centralize this resolution policy.

This also shows why repository architecture must be designed deliberately.

Do not aggregate repositories randomly.

---

# 42. Virtual Repository Does Not Necessarily Mean Another Physical Copy

A beginner may imagine:

```text
Local Repository
↓
Copy artifact into Virtual Repository

Remote Repository
↓
Copy artifact into Virtual Repository
```

That is the wrong mental model.

Think:

```text
Virtual Repository
=
Logical aggregation and endpoint
```

not:

```text
Virtual Repository
=
A folder containing duplicate copies of everything
```

The underlying local and remote repositories remain the repositories that store or proxy the artifacts.

---

# 43. Can You Deploy Through a Virtual Repository?

Virtual repositories can be configured with a default deployment repository.

JFrog exposes a "Default Deployment Repository" setting for virtual repositories.

Conceptually:

```text
Client
↓
Virtual Repository
↓
Default Deployment Repository
↓
Local Repository
```

For example:

```text
veriqta-maven-virtual
↓
Default Deployment Repository
↓
veriqta-maven-local
```

This lets the client potentially use a consistent virtual endpoint while Artifactory directs deployment to the configured local destination.

For beginners, however, it is still essential to understand where the artifact actually ends up.

---

# 44. When Should You Use a Virtual Repository?

Use a virtual repository when clients should access multiple compatible repositories through one endpoint.

Example:

```text
Development Maven Endpoint
↓
maven-virtual
├── internal-release-local
├── internal-snapshot-local
└── maven-central-remote
```

Mental rule:

```text
Many repositories
+
One client endpoint
=
Virtual repository
```

Now combine the three.

```text

                           ↓

                    /               \
```

# 50. Federated Repositories

The fourth repository type solves another problem.

Imagine VERIQTA becomes a large organization with teams in:

```text
New York
London
Lagos
Singapore
```

Suppose there are separate JFrog Platform Deployments.

You may want repositories at those sites to participate in a synchronized repository architecture.

This is where Federated repositories become relevant.

---

# 51. What Is a Federated Repository?

A Federated repository behaves similarly to a local repository from a developer's perspective, but it belongs to a Federation with corresponding repositories on other JFrog Platform Deployments.

JFrog describes Federated repositories as repositories that synchronize artifacts and metadata across distributed JFrog Platform Deployments using event-driven replication.

Conceptually:

```text
New York JFrog
↓
Federated Repository
↕
Federated Repository
↓
London JFrog
```

Changes can be synchronized between Federation members according to the configured mode.

---

# 52. What Is a JPD?

JFrog documentation uses:

```text
JPD
```

for:

```text
JFrog Platform Deployment
```

Think of a JPD as a deployed JFrog Platform environment.

For example:

```text
JPD New York

JPD London

JPD Singapore
```

A Federation can connect corresponding Federated repositories across multiple JPDs.

---

# 53. Federated Repository Architecture

Suppose we have:

```text
JPD A
New York
```

and:

```text
JPD B
London
```

Each contains a Federated repository:

```text
New York
veriqta-release-federated

↕ synchronization

London
veriqta-release-federated
```

Developer in New York publishes:

```text
app-2.0.0.zip
```

to the New York Federation member.

Artifactory can synchronize that change to the other Federation member.

---

# 54. Federated Repositories Are Not Virtual Repositories

Do not confuse these.

Virtual:

```text
One logical endpoint
↓
Aggregates underlying repositories
```

Federated:

```text
Repository at one JPD
↕
Synchronization
↕
Corresponding repository at another JPD
```

Virtual solves:

```text
aggregation
```

Federated solves:

```text
distributed synchronization
```

Very different problems.

---

# 55. Federated Repositories Are Not Remote Repositories

Remote:

```text
Artifactory
↓
Proxy
↓
Upstream repository
```

Federated:

```text
JFrog JPD A
↕
Synchronization
↕
JFrog JPD B
```

Remote repositories primarily retrieve from an upstream source.

Federated repositories participate in synchronized repository membership across JFrog environments.

---

# 56. Bidirectional Federation

By default, JFrog Federated repositories support bidirectional synchronization.

Conceptually:

```text
JPD A
↕
JPD B
```

Both sides can:

```text
Send
+
Receive
```

JFrog currently documents bidirectional mode as the default, while also supporting receiving-only topology patterns.

---

# 57. Receiving-Only Federation

There are scenarios where one member should receive changes without acting as another publishing source.

Conceptually:

```text
Primary
↓
Receiving Site
```

JFrog supports receiving-only members, with the corresponding source functioning as the transmitter for that relationship.

This can support architectures where a central source distributes content outward.

---

# 58. Federation Is Asynchronous

Do not assume:

```text
Upload at JPD A
=
Instantaneously present everywhere at the exact same nanosecond
```

JFrog describes Federation changes as asynchronously replicated between members.

So think:

```text
Change
↓
Replication event
↓
Synchronization
↓
Other member
```

There can be replication time.

This matters during troubleshooting.

---

# 59. Metadata and Binary Synchronization

Federation does more than copy a file.

JFrog's current architecture separates metadata replication and binary synchronization mechanisms.

Conceptually:

```text
Federation Event
├── Metadata synchronization
└── Binary synchronization
```

That matters because Artifactory artifacts are not merely naked binary files.

Remember Part 2:

```text
Artifact
+
Metadata
+
Properties
+
Checksums
```

Repository synchronization needs to preserve the repository state, not merely perform an uncontrolled file copy.

Common scenarios include:

## Distributed development teams

```text

↓
Local JPD

Team B
↓
Local JPD
```

with synchronized repository content.

## Multi-region architecture

```text

↕

↕
Region C
```

## Disaster recovery designs

A synchronized repository architecture can form part of a wider continuity or DR strategy.

JFrog specifically documents multi-region team use and production/DR scenarios as Federation use cases.

Federation still requires careful infrastructure design. It is not simply a checkbox that automatically solves every disaster-recovery concern.

# 66. Repository Selection

When deciding where something belongs, ask questions in order.

## Question 1

Who produced the artifact?

If your organization produced it:

```text

```

may be appropriate.

If another registry hosts it:

```text

```

may be appropriate.

## Question 2

Do clients need one endpoint across multiple repositories?

If yes:

```text
Virtual
```

## Question 3

Does the same repository need synchronized membership across JPDs?

If yes:

```text
Federated
```

```text
  │
  ↓

  │
  ├── YES
  │    ↓

  │
  └── NO
       ↓

       │
       ├── YES

       └── NO
```

# 74. Common Beginner Mistake: Thinking Remote Cache Is Permanent Source Control

A cache should not automatically be treated as the permanent authoritative source for every dependency.


# 75. Common Beginner Mistake: Assuming Cached Means Fresh

Suppose an upstream artifact changes.

You may assume:

```text
Cached artifact
=
Always latest upstream state
```

That is unsafe reasoning.

Cache behavior depends on:

* Package type
* Metadata
* Cache configuration
* Upstream checks
* Artifact immutability assumptions

JFrog notes that Artifactory generally assumes published artifacts are immutable, and Generic remote repositories do not simply refetch changed binaries automatically in every situation.

Prefer versioned immutable artifacts.

Imagine repeatedly replacing:

```text

=
```


Tomorrow:

```text

=

```

Now caching, traceability, rollback, and reproducibility become harder.

This connects directly to the immutability concepts from Part 1.


# 81. Security Consideration: Dependency Confusion

Suppose your organization uses an internal package:

```text
veriqta-security-lib
```

Now imagine a package with the same name appears in a public registry.

Poor dependency-resolution design can create risk if a build unexpectedly resolves the public package rather than the intended internal package.

This general class of problem is often called dependency confusion.

Repository design, package naming, resolution rules, permissions, and security controls matter.

Do not assume:

```text
same package name
=
same software
```

# 82. Security Consideration: Control Your Upstreams

Do not create remote repositories pointing to arbitrary sources simply because a developer asks.

An organization should know:

```text
Which external repositories are approved?
Who controls them?
What packages may enter?
How are dependencies scanned?
What happens if the upstream is compromised?
```

Artifactory provides a central point where those policies can be applied.

# 83. Security Consideration: Least Privilege

Not every user needs deployment permission everywhere.

Example:

```text
Developers
↓
Read from virtual repository
+
Deploy to development local repository
```

Production deployment might be limited to:

```text
CI/CD release identity
```

And deletion might be limited further.

Do not solve repository access problems by making everyone an administrator.

Possible cause:

You may be dealing with caching or artifact immutability behavior.

# 108. What You Should Now Understand

Before continuing, you should confidently understand:

## Repository

A logical artifact-management boundary in Artifactory.

## Repository Key

The unique identifier used to identify a repository.

## Package Type

The software ecosystem the repository serves.

## Local Repository

Stores artifacts directly published into your Artifactory environment.

## Remote Repository

Acts as a proxy to an upstream repository and can cache retrieved artifacts.

## Upstream Repository

The external or remote source behind a remote repository.

## Cache

Locally retained retrieved content that can reduce repeated upstream downloads.

## Cache Hit

The requested content is available from cache.

## Cache Miss

The requested content is not available from cache and may require upstream retrieval.

## Virtual Repository

Aggregates compatible repositories behind a single logical endpoint.

## Repository Aggregation

Combining repository resolution through a virtual repository.

## Federated Repository

A repository participating in synchronization with Federation members on other JFrog Platform Deployments.

## Repository Layout

The organization and interpretation of artifact paths inside a repository.

## Offline Remote Repository

A remote repository configured to stop contacting its upstream and rely on cached content.

# 112. Part 4 Final Architecture

The original architecture for this part was:

```text
Developer
↓
Virtual Repository
├── Local Repository
└── Remote Repository
↓
Public Package Registry
```

We can now expand it properly:

```text
                         Developer / CI
                               │
                               ↓
                       Package Manager
                               │
                               ↓
                       Virtual Repository
                        /              \
                       /                \
                      ↓                  ↓
             Local Repository      Remote Repository
                    │                    │
                    │                    ↓
                    │               Remote Cache
                    │                    │
                    │             Cache Miss?
                    │                    │
                    │                    ↓
                    │             Upstream Registry
                    │
                    ↓
            Internal Artifacts
```

And in a distributed organization:

```text
                        JFrog JPD A
                            │
                    Federated Repository
                            │
                            ↕
                   Asynchronous Sync
                            ↕
                    Federated Repository
                            │
                        JFrog JPD B
```

These four concepts should now be distinct in your mind:

```text
LOCAL
Our published artifacts

REMOTE
Proxy/cache for an upstream

VIRTUAL
One endpoint over multiple repositories

FEDERATED
Synchronized repository across JFrog deployments
```

That distinction is foundational.

From this point forward, when you see an artifact in Artifactory, you should begin asking:

```text
Which repository is this?

What type is it?

What package type is it?

Who produced the artifact?

Is this the authoritative internal copy?

Was it retrieved from upstream?

Is it cached?

Am I accessing it through a virtual repository?

Could it be synchronized from another JPD?
```

Once you can answer those questions, Artifactory stops looking like a collection of folders.

You begin seeing the repository architecture.

The next stage can now safely work with real artifact operations because you understand where an artifact belongs and why.
