# Part 7: Generic Repositories and Building a Complete Artifact Workflow

In Part 6, you moved artifact management away from manual browser operations and into JFrog CLI.

You learned the basic flow:

```text
Terminal
↓
JFrog CLI
↓
Artifactory
↓
Repository
↓
Artifact
```

You uploaded, searched, downloaded, copied, moved, and deleted artifacts. You also worked with explicit versions, properties, checksums, File Specs, authentication, and basic automation.

Now we will turn those individual operations into a complete artifact workflow.

The goal of this part is not simply:

```text
How do I upload a ZIP file?
```

The goal is to understand:

```text
What should we store?
↓
How should we package it?
↓
How should we name it?
↓
Where should development artifacts go?
↓
How do we identify exactly what was tested?
↓
How should a tested artifact become a release?
↓
How can deployment retrieve that exact release later?
```

We will deliberately use Generic repositories before introducing package-manager-specific repository types.

Our final workflow will be:

```text
Application Files
↓
Package
↓
veriqta-generic-dev
↓
Test
↓
Promote
↓
veriqta-generic-release
↓
Deploy
```

By the end of this part, you should understand not only how Generic repositories work, but how to design a small, traceable artifact lifecycle around them.

---

# 1. What Is a Generic Repository?

Artifactory supports repositories designed for particular package ecosystems.

Examples include repositories for technologies such as:

```text
Maven
npm
PyPI
NuGet
Docker
Helm
```

Those ecosystems have their own package formats, metadata, dependency rules, and client behavior.

But not every artifact belongs to a package ecosystem.

Sometimes you simply need to store a file.

For example:

```text
veriqta-api-1.0.0.zip
```

or:

```text
veriqta-worker-2.4.1.tar.gz
```

or:

```text
deployment-config-2026.09.08.tar.gz
```

A Generic repository provides a flexible repository for artifacts that do not need package-manager-specific behavior.

Think of it as:

```text
Generic Repository
↓
Repository-managed files
↓
Organized paths
↓
Versions
↓
Metadata
↓
Checksums
↓
Permissions
```

It is much more than an ordinary shared folder.

---

# 2. Why Is It Called Generic?

The word "Generic" means the repository is not tied to one specific package format or package manager.

For example:

```text
Maven Repository
↓
Understands Maven ecosystem conventions

npm Repository
↓
Designed for npm packages

PyPI Repository
↓
Designed for Python packages

Generic Repository
↓
General-purpose artifact storage
```

A Generic repository can therefore contain files such as:

```text
.zip
.tar
.tar.gz
.bin
.sh
.json
.yaml
.yml
.txt
```

and many other file types.

The important distinction is that Artifactory is managing them as generic artifacts rather than interpreting them through a specific package ecosystem.

---

# 3. Generic Does Not Mean Unstructured

This is an important beginner distinction.

Generic means:

```text
Not tied to a specific package ecosystem
```

It does not mean:

```text
Throw random files anywhere.
```

A badly designed Generic repository can become:

```text
generic-local/
├── app.zip
├── app-new.zip
├── app-final.zip
├── app-final2.zip
├── test.tar.gz
├── old.zip
├── latest.zip
└── config-new-final.yaml
```

Nobody can confidently answer:

* Which application does each file belong to?
* Which version is production?
* Which build created it?
* Which artifact was tested?
* Which artifact should be deployed?
* Which file is safe to delete?
* Is `app-final2.zip` newer than `app-new.zip`?
* Did somebody replace `latest.zip`?

Generic repositories still require deliberate organization.

---

# 4. When Are Generic Repositories Appropriate?

Generic repositories are appropriate when you have artifacts that do not need a package-manager-specific repository.

Common examples include:

* ZIP application distributions
* TAR archives
* TAR.GZ archives
* Compiled standalone binaries
* Internal command-line tools
* Installation packages
* Deployment bundles
* Configuration bundles
* Database migration bundles
* Static website bundles
* Generated documentation archives
* Infrastructure bundles
* Firmware or binary outputs
* Vendor binaries, where licensing permits internal storage
* Internal scripts packaged for distribution
* Release assets
* Other arbitrary files produced by build or delivery processes

The question to ask is:

```text
Does this artifact belong to a package ecosystem that Artifactory supports specifically?
```

If yes, the ecosystem-specific repository may be more appropriate.

If no, a Generic repository may be a good fit.

---

# 5. When Should You Not Automatically Use Generic?

Suppose your application produces:

```text
payment-service-1.4.0.jar
```

You technically have a file.

But if that JAR participates in a Maven or Gradle dependency ecosystem, a Maven repository is usually more appropriate than treating it as an arbitrary generic file.

Similarly:

```text
my-library-1.0.0.tgz
```

might physically be a compressed archive, but if it is an npm package, an npm repository is more appropriate.

The file extension alone does not determine the correct repository.

Ask:

```text
What ecosystem owns this artifact?
```

and:

```text
How will clients consume it?
```

---

# 6. Generic Repository vs Package Repository

Consider two artifacts.

Artifact A:

```text
veriqta-platform-tools-1.0.0.tar.gz
```

It is simply a collection of internal scripts and configuration templates.

A Generic repository may be appropriate.

Artifact B:

```text
com.veriqta:payment-api:1.0.0
```

It is a Java library consumed through Maven.

A Maven repository is more appropriate.

The difference is not simply:

```text
File vs package
```

The difference includes:

```text
How the artifact is produced
+
How it is described
+
How dependencies are resolved
+
How clients retrieve it
+
Which ecosystem conventions apply
```

---

# 7. ZIP Artifacts

ZIP is a common archive format.

A ZIP file combines one or more files and directories into a single archive.

Suppose an application directory contains:

```text
veriqta-demo/
├── bin/
│   └── start.sh
├── config/
│   └── application.yaml
├── public/
│   └── index.html
└── README.txt
```

You could package it as:

```text
veriqta-demo-1.0.0.zip
```

Now instead of moving four separate components around independently, you have one versioned artifact.

Conceptually:

```text
Application Files
↓
ZIP
↓
Single Artifact
```

---

# 8. Creating a ZIP Archive

From the parent directory:

```bash
zip -r veriqta-demo-1.0.0.zip veriqta-demo/
```

Break it down.

### `zip`

Runs the ZIP archive utility.

### `-r`

Means recursive.

It tells `zip` to include directories and their contents recursively.

### `veriqta-demo-1.0.0.zip`

The archive to create.

### `veriqta-demo/`

The directory being packaged.

The result is:

```text
veriqta-demo-1.0.0.zip
```

---

# 9. Verify a ZIP Before Publishing It

Do not immediately upload a newly created archive.

Inspect it:

```bash
unzip -l veriqta-demo-1.0.0.zip
```

`-l` lists the archive contents without extracting them.

You should verify that:

* Required application files exist
* Unexpected files are absent
* Secrets are absent
* Temporary files are absent
* Development-only files are absent where inappropriate
* Directory structure is correct

Then calculate a checksum:

```bash
shasum -a 256 veriqta-demo-1.0.0.zip
```

Our workflow becomes:

```text
Package
↓
Inspect contents
↓
Check for sensitive/unwanted files
↓
Calculate checksum
↓
Publish
```

---

# 10. TAR Archives

TAR stands historically for tape archive.

A TAR file groups files and directories into one archive.

Example:

```bash
tar -cvf veriqta-demo-1.0.0.tar veriqta-demo/
```

Important options:

```text
-c
Create an archive

-v
Verbose output

-f
Use the following archive filename
```

The resulting artifact is:

```text
veriqta-demo-1.0.0.tar
```

---

# 11. TAR.GZ Archives

TAR itself primarily creates an archive. Compression can then be added.

A very common Linux artifact format is:

```text
.tar.gz
```

This means:

```text
TAR archive
+
gzip compression
```

Create one:

```bash
tar -czvf veriqta-demo-1.0.0.tar.gz veriqta-demo/
```

Here:

```text
-z
↓
Use gzip compression
```

Inspect without extracting:

```bash
tar -tzvf veriqta-demo-1.0.0.tar.gz
```

Here:

```text
-t
↓
List archive contents
```

---

# 12. ZIP vs TAR.GZ

Both can package multiple files.

ZIP is common across many operating systems.

TAR.GZ is extremely common in Linux and Unix environments.

A simplified comparison:

| Format    | Typical use                        |
| --------- | ---------------------------------- |
| `.zip`    | General-purpose compressed archive |
| `.tar`    | Archive without gzip compression   |
| `.tar.gz` | TAR archive compressed with gzip   |

Do not choose a format simply because one looks more "DevOps."

Choose based on:

* Consumer requirements
* Operating environment
* Existing tooling
* Distribution conventions
* Compression requirements
* Organizational standards

---

# 13. Application Binaries

Not every artifact needs to be an archive.

A build process may produce an executable binary directly.

For example:

```text
veriqta-agent
```

or:

```text
veriqta-agent-linux-amd64
```

You could store it in a Generic repository:

```text
veriqta-generic-release/
└── veriqta-agent/
    └── 1.5.0/
        └── veriqta-agent-linux-amd64
```

If several platforms are supported:

```text
1.5.0/
├── veriqta-agent-linux-amd64
├── veriqta-agent-linux-arm64
└── veriqta-agent-darwin-arm64
```

The naming tells us more than:

```text
agent
```

---

# 14. Configuration Bundles

Sometimes deployment requires a collection of configuration files.

For example:

```text
config/
├── nginx.conf
├── logging.yaml
└── app-defaults.yaml
```

These could be packaged:

```text
veriqta-config-1.0.0.tar.gz
```

However, configuration artifacts require security judgment.

Do not package:

```text
passwords
private keys
API tokens
database credentials
cloud credentials
```

simply because Artifactory can store files.

A useful distinction is:

```text
Configuration
≠
Secret
```

For example:

```yaml
server:
  port: 8080
```

may be ordinary configuration.

But:

```yaml
database:
  password: SuperSecretPassword
```

contains a secret.

Secrets should normally come from an appropriate secret-management system rather than being baked into a release archive.

---

# 15. Release Bundles and Generic Files

The word "bundle" is often used broadly to describe a collection of files packaged for some operational purpose.

For example:

```text
veriqta-web-release-3.2.0.tar.gz
```

might contain:

```text
bin/
config/
static/
migrations/
manifest/
```

However, be careful with terminology.

JFrog also has platform features and product concepts that use terms such as release bundles in more specific ways.

In this beginner Generic repository section, when we say a generic deployment or release bundle, we mean:

```text
A packaged collection of files stored as a generic artifact
```

We are not yet teaching JFrog's more specialized release-management capabilities.

---

# 16. The Artifact Is the Unit We Move

This concept matters.

Suppose testing verifies:

```text
veriqta-demo-1.4.2.tar.gz
```

Deployment should ideally receive that exact tested artifact.

We do not want:

```text
Test source code
↓
Rebuild
↓
Create slightly different artifact
↓
Deploy different binary
```

Instead, a strong artifact workflow aims for:

```text
Build once
↓
Produce artifact
↓
Test artifact
↓
Promote same artifact
↓
Deploy same artifact
```

This principle is often summarized as:

```text
Build once, promote the same artifact.
```

---

# 17. Why Rebuilding for Each Environment Is Risky

Imagine:

```text
Commit abc123
↓
Build A
↓
Test
↓
Passed
```

Then before production:

```text
Commit abc123
↓
Build B
↓
Production
```

You may assume Build A and Build B are identical.

But differences can enter through:

* Dependency changes
* Build environment differences
* Build-tool versions
* Environment variables
* Generated timestamps
* External downloads
* Build configuration
* Nondeterministic build behavior

Now production may receive something that was not literally the artifact tested.

A safer flow is:

```text
Commit abc123
↓
Build
↓
Artifact X
↓
Test X
↓
Promote X
↓
Deploy X
```

# 18. Artifact Organization

A repository needs predictable structure.

Consider:

```text
veriqta-generic-release/
└── veriqta-demo/
    ├── 1.0.0/
    │   └── veriqta-demo-1.0.0.tar.gz
    ├── 1.1.0/
    │   └── veriqta-demo-1.1.0.tar.gz
    └── 2.0.0/
        └── veriqta-demo-2.0.0.tar.gz
```

This answers several questions immediately.

Application:

```text
veriqta-demo
```

Versions:

```text
1.0.0
1.1.0
2.0.0
```

Artifact for version `1.1.0`:

```text
veriqta-demo-1.1.0.tar.gz
```

Predictability matters.

---

# 19. Directory Structure

A useful generic path can follow:

```text
<repository>/<application>/<version>/<artifact>
```

Example:

```text
veriqta-generic-release/
└── payment-api/
    └── 2.4.1/
        └── payment-api-2.4.1.tar.gz
```

Another organization might include platform information:

```text
veriqta-generic-release/
└── veriqta-agent/
    └── 1.5.0/
        ├── linux-amd64/
        │   └── veriqta-agent
        └── linux-arm64/
            └── veriqta-agent
```

There is no universal path that fits every organization.

The important qualities are:

```text
Consistent
Predictable
Understandable
Automatable
Traceable
```

---

# 20. Naming Conventions

Compare:

```text
app.zip
```

with:

```text
veriqta-demo-2.3.1.zip
```

The second filename carries useful information.

A simple convention is:

```text
<application>-<version>.<extension>
```

Examples:

```text
veriqta-demo-1.0.0.zip
payment-api-2.4.1.tar.gz
deployment-tools-3.1.0.tar.gz
```

For platform-specific binaries:

```text
<application>-<version>-<os>-<architecture>
```

Example:

```text
veriqta-agent-1.5.0-linux-amd64
```

---

# 21. What Makes a Good Naming Convention?

A good convention should be:

* Predictable
* Machine-friendly
* Human-readable
* Consistent
* Version-aware
* Unambiguous

Avoid filenames such as:

```text
app-final.zip
app-final-new.zip
app-final-fixed.zip
app-final-fixed2.zip
release-latest-new.zip
```

Those names describe human confusion rather than release identity.

---

# 22. Semantic Versioning Introduction

One common versioning approach is Semantic Versioning.

A basic semantic version looks like:

```text
MAJOR.MINOR.PATCH
```

Example:

```text
2.4.1
```

Break it down:

```text
2
↓
MAJOR

4
↓
MINOR

1
↓
PATCH
```

The Semantic Versioning specification generally uses these components to communicate compatibility and change meaning for software with a defined public API.

At beginner level, remember the structure first:

```text
MAJOR.MINOR.PATCH
```

---

# 23. PATCH Version

Example:

```text
1.4.2
↓
1.4.3
```

A patch increment generally indicates backward-compatible bug fixes under Semantic Versioning.

For example:

```text
1.4.2
↓
Fix incorrect log rotation
↓
1.4.3
```

The public API contract has not gained incompatible behavior.

---

# 24. MINOR Version

Example:

```text
1.4.3
↓
1.5.0
```

A minor increment generally indicates backward-compatible functionality has been added.

For example:

```text
1.4.3
↓
Add optional health-check endpoint
↓
1.5.0
```

Existing consumers should not require incompatible changes under the SemVer contract.

---

# 25. MAJOR Version

Example:

```text
1.5.0
↓
2.0.0
```

A major increment generally indicates incompatible API changes.

For example:

```text
1.x
↓
Existing API contract

2.0.0
↓
Breaking API change
```

Consumers may need changes before upgrading.

---

# 26. Semantic Versioning Is a Contract

Do not simply increment numbers randomly.

If your team claims to use Semantic Versioning, the version communicates information.

The basic model is:

```text
Breaking change
↓
MAJOR

Backward-compatible feature
↓
MINOR

Backward-compatible bug fix
↓
PATCH
```

This becomes important when humans and automation choose artifacts.

---

# 27. Pre-release Versions

Semantic Versioning also allows pre-release identifiers.

Examples:

```text
2.0.0-alpha.1
2.0.0-beta.2
2.0.0-rc.1
```

`rc` often means:

```text
Release Candidate
```

For example:

```text
2.0.0-rc.1
```

communicates that the build is associated with version `2.0.0` but is not yet the normal final `2.0.0` release.

Pre-release versions sort with lower precedence than the corresponding normal version under SemVer rules.

---

# 28. Build Metadata

Semantic Versioning also supports build metadata after `+`.

Example:

```text
2.0.0+build.417
```

or:

```text
2.0.0+sha.abc123
```

This can carry build-related information.

However, do not create complicated version strings simply because the format permits them.

Your versioning strategy should remain understandable and useful.

---

# 29. Development vs Release Artifacts

Not every artifact produced by CI should immediately become a release.

During development, a team may generate many artifacts.

For example:

```text
Feature work
↓
Build
↓
Test
↓
Build
↓
Fix
↓
Build
↓
Test
```

These are development artifacts.

A release artifact represents a version that has passed the process required for release.

Conceptually:

```text
Development Artifact
↓
Testing / Validation
↓
Approved
↓
Release Artifact
```

---

# 30. Snapshot and Development Artifacts

Different ecosystems use the word "snapshot" differently.

For example, Maven has a specific SNAPSHOT version concept.

In a generic artifact workflow, we should not pretend a Generic repository automatically gives arbitrary files Maven's snapshot semantics.

Instead, think more generally:

```text
Development artifact
=
Artifact produced during ongoing development and validation
```

Examples could use identifiers such as:

```text
2.0.0-dev.17
2.0.0-rc.1
```

or a team-specific build identifier.

The exact convention should be deliberately defined.

# 31. Why Separate Development and Release Artifacts?

Imagine one repository:

```text
generic-local/
├── experimental-build-17.zip
├── test-build-18.zip
├── veriqta-demo-2.0.0.zip
├── failed-build-19.zip
├── production.zip
└── candidate.zip
```

Now ask:

```text
Which artifacts are trusted releases?
```

The repository does not make the answer obvious.

Instead, we can create:

```text
veriqta-generic-dev
```

and:

```text
veriqta-generic-release
```

The intent becomes clearer.

# 33. Does Moving an Artifact Make It Safe?

No.

This is critical.

A repository called:

```text
veriqta-generic-release
```

does not magically make its contents production-ready.

The release repository represents an organizational boundary.

Something else must establish whether an artifact has passed the required checks.

Those checks might include:

* Automated tests
* Integration tests
* Security scans
* Policy checks
* Manual approval
* Change-management requirements
* Deployment validation

Repository design supports the process.

It does not replace the process.

---

# 34. Development Repository Structure

Our development repository might contain:

```text
veriqta-generic-dev/
└── veriqta-demo/
    └── 2.0.0/
        ├── veriqta-demo-2.0.0-dev.17.tar.gz
        ├── veriqta-demo-2.0.0-dev.18.tar.gz
        └── veriqta-demo-2.0.0-rc.1.tar.gz
```

This allows multiple development artifacts to exist without overwriting one another.

That last point matters.

---

# 35. Never Make Every Build `latest.zip`

Suppose every CI build uploads:

```text
latest.zip
```

Build 417:

```text
latest.zip
```

Build 418:

```text
latest.zip
```

Build 419:

```text
latest.zip
```

Now someone asks:

```text
Which binary did QA test yesterday?
```

If `latest.zip` was repeatedly overwritten, the answer may be difficult or impossible to prove from the filename alone.

Instead:

```text
veriqta-demo-2.0.0-dev.417.tar.gz
veriqta-demo-2.0.0-dev.418.tar.gz
veriqta-demo-2.0.0-dev.419.tar.gz
```

Each artifact has a stable identity.

---

# 36. Explicit Versions vs `latest`

`latest` is convenient for humans.

It is often dangerous as the only identity for deployment.

Compare:

```text
GET latest
```

with:

```text
GET veriqta-demo-2.0.0.tar.gz
```

The first may mean something different tomorrow.

The second names a specific release.

For controlled deployment, prefer:

```text
Explicit version
↓
Exact artifact
↓
Known checksum
```

---

# 37. Artifact Immutability

An important release principle is:

```text
A released version should not silently change.
```

Suppose:

```text
veriqta-demo-2.0.0.tar.gz
```

has SHA-256:

```text
ABC...
```

QA approves it.

Production deploys it.

Later someone uploads different bytes using the same path and filename:

```text
veriqta-demo-2.0.0.tar.gz
```

Now the name says:

```text
2.0.0
```

but the content has changed.

That destroys confidence in the version.

---

# 38. Why Immutability Matters

A strong release identity should answer:

```text
Version 2.0.0
↓
Which exact bytes?
```

If those bytes can silently change:

```text
Version
≠
Stable identity
```

That harms:

* Traceability
* Rollbacks
* Auditing
* Incident investigation
* Reproducibility
* Deployment confidence

If release `2.0.0` needs a fix, create a new release according to your versioning policy, such as:

```text
2.0.1
```

rather than silently replacing `2.0.0`.

Repository permissions and deployment policies should support this principle.

# 39. Artifact Properties

We introduced properties earlier.

Now we will use them as part of artifact organization.

Suppose we upload:

```text
veriqta-demo-2.0.0-rc.1.tar.gz
```

We might associate properties such as:

```text
application=veriqta-demo
stage=development
status=candidate
team=platform
```

Properties add searchable information without requiring all information to be encoded into the filename.

---

# 40. Filename vs Path vs Properties

These serve different purposes.

Filename:

```text
veriqta-demo-2.0.0-rc.1.tar.gz
```

helps identify the artifact itself.

Path:

```text
veriqta-generic-dev/veriqta-demo/2.0.0/
```

provides repository organization.

Properties:

```text
application=veriqta-demo
status=candidate
```

provide additional metadata.

Together:

```text
Repository
+
Path
+
Filename
+
Properties
+
Checksum
=
Much stronger artifact identity
```

---

# 41. What Metadata Should You Store?

Useful metadata depends on the organization.

Possible examples include:

```text
application
version
team
environment
status
build-number
source-commit
pipeline
```

Do not add metadata simply because you can.

Ask:

```text
Will this help us search, trace, govern, deploy, or troubleshoot the artifact?
```

If not, it may be unnecessary.

---

# 42. Never Store Secrets as Properties

Do not use properties for:

```text
password=...
token=...
private-key=...
database-password=...
```

Metadata is not a substitute for a secret manager.

A good security rule is:

```text
Artifact metadata
↓
Describes artifact

Secret manager
↓
Protects secrets
```

# 43. Source Commit Traceability

Suppose Git commit:

```text
a1b2c3d
```

produces:

```text
veriqta-demo-2.0.0-rc.1.tar.gz
```

You want to preserve the relationship:

```text
Git Commit
↓
Build
↓
Artifact
```

Conceptually:

```text
source-commit=a1b2c3d
```

could help record that relationship as metadata.

Later, during an incident:

```text
Production artifact
```

Promotion means advancing an artifact through the software delivery lifecycle after it satisfies required criteria.

```text
↓

↓

↓
```

# 67. Do Not Rebuild During Promotion

Wrong:

```text
Candidate passes tests
↓
Return to source
↓
Build again
↓
Upload new artifact to release
```

Better:

```text
Candidate passes tests
↓
Promote the tested artifact
↓
Release repository
```

The principle is:

```text
Tested bytes
=
Released bytes
```

# 68. Candidate Name vs Final Release Name

Our candidate is:

```text
veriqta-demo-2.0.0-rc.1.tar.gz
```

Our desired final release is:

```text
veriqta-demo-2.0.0.tar.gz
```

This raises an important design question.

If the filename itself changes, we need a controlled operation that changes the path/name without rebuilding the binary content.

For this educational lab, we can copy the candidate artifact into the release repository under the final release path and then verify that the binary checksum remains identical.

The release process should be governed so that only approved artifacts can cross that boundary.

# 73. Updating Artifact Properties During Promotion

The release artifact should no longer describe itself as:

```text
status=candidate
```

The metadata should reflect its new lifecycle state.

For example:

```text
stage=release
status=approved
```

JFrog CLI supports operations for setting properties on artifacts.

A common pattern is:

```bash
jf rt set-props \
  "veriqta-generic-release/veriqta-demo/2.0.0/veriqta-demo-2.0.0.tar.gz" \
  "application=veriqta-demo;version=2.0.0;stage=release;status=approved" \
  --server-id=veriqta-lab
```

Before relying on a command or option in production automation, check the help for your installed CLI version:

```bash
jf rt set-props --help
```

This is a good operational habit because CLI capabilities and options can evolve.

# 74. Artifact State Should Be Evidence-Based

Do not set:

```text

```

simply because the upload succeeded.

Approval should correspond to evidence.

Conceptually:

```text

↓
Candidate
↓

↓
Required checks PASS
↓
Approval
↓

↓
Release
```

Metadata should describe reality.

It should not create reality.

# 76. Why Exact Retrieval Matters

Imagine production currently runs:

```text
2.0.0
```

Version:

```text
2.1.0
```

is released tomorrow.

If your deployment script says:

```text
download latest
```

then rerunning the script tomorrow may produce a different deployment.

If it says:

```text
download 2.0.0
```

the request remains stable.

This is deterministic deployment.

# 77. Rollbacks Become Easier

Suppose:

```text
2.1.0
```

causes a production problem.

If `2.0.0` still exists unchanged:

```text

├── 2.0.0
└── 2.1.0
```

the rollback can deliberately retrieve:

```text
2.0.0
```

Conceptually:

```text
2.1.0
↓
Incident
↓
Select known 2.0.0
↓
Download exact artifact
↓
Verify
↓
Redeploy
```

Versioned immutable artifacts make rollback more predictable.

# 78. Why Retention Policy Matters

If you delete every previous release immediately after deploying a new one, rollback becomes harder.

But storing everything forever may create:

* Storage growth
* Cost
* Repository clutter
* Compliance concerns
* Operational overhead

Therefore organizations need retention policies.

For example:

```text
Development artifacts
↓
Shorter retention

Release artifacts
↓
Longer retention
```

The exact policy depends on business, legal, technical, and operational requirements.

Do not randomly delete artifacts simply because they look old.

Many may no longer be needed.

A cleanup policy might consider:

* Artifact age
* Build status
* Release status
* References
* Legal requirements
* Current deployments
* Rollback needs
* Storage limits

Never design cleanup as:

```text

```

# 81. Least Privilege in Artifact Workflows

Least privilege means giving an identity only the permissions necessary for its job.

Bad:

```text

↓
Administrator access
↓
Every repository
```

Better:

```text

↓
Read dependencies
+
Write development artifacts

Release Pipeline
↓
Read development
+
Write/promote approved releases

Deployment Pipeline
↓
```

The principle is:

```text
Identity
↓
Only required actions
↓
Only required repositories
```

```text
↓

↓
```

Artifact storage and secret management solve different problems.

# 90. Troubleshooting: Artifact Went to the Wrong Repository

## Problem

A candidate appears in:

```text
veriqta-generic-release
```

instead of:

```text
veriqta-generic-dev
```

## Possible Cause

The upload target was wrong.

## Investigate

Inspect:

* CLI command
* Pipeline variables
* File Spec
* Repository environment variables
* Command output

## Fix

Do not simply copy it somewhere else and ignore the mistake.

Determine why the target was wrong.

Correct the automation.

Then handle the incorrectly published artifact according to repository policy.

## Prevention

Use explicit repository variables such as:

```bash
DEV_REPOSITORY="veriqta-generic-dev"

```

and protect release writes with permissions.

# 91. Troubleshooting: Same Version Has Different Checksums

## Problem

Two files both claim to be:

```text
veriqta-demo-2.0.0.tar.gz
```

but their SHA-256 values differ.

## Why This Matters

The same release identity now points to different bytes.

## Investigate

Ask:

1. Was the release rebuilt?
2. Was the artifact overwritten?
3. Did packaging change?
4. Was the file modified after download?
5. Are you comparing the correct paths?
6. Did promotion rename the same bytes or create a new archive?

## Fix

Do not choose one arbitrarily.

Identify which artifact was actually tested and approved.

Restore a trustworthy release state according to your organization's release process.

## Prevention

Use immutable release practices and restricted write permissions.

# 92. Troubleshooting: Candidate Passed but Release Fails

## Problem

The development candidate passed testing.

After promotion, the release behaves differently.

## Investigation

First compare checksums.

```text
Candidate checksum
vs
Release checksum
```

If different:

```text
The released bytes are not the tested bytes.
```

Investigate whether:

* The artifact was rebuilt
* It was repackaged
* Someone modified it
* The wrong candidate was promoted

If checksums match, investigate environmental differences:

* Configuration
* Secrets
* Network
* Runtime
* Permissions
* External dependencies
* Deployment procedure

This distinction is extremely useful:

```text
Same artifact, different behavior
↓
Investigate environment/runtime

Different artifact
↓
Investigate build/promotion chain
```

# 96. Troubleshooting: TAR Extracts Into an Unexpected Structure

## Problem

You expected:

```text
bin/
config/
public/
```

but extraction produces:

```text
veriqta-demo/
├── bin/
├── config/
└── public/
```

## Cause

The archive was created from:

```bash
tar -czvf artifact.tar.gz veriqta-demo/
```

so the top-level directory was included.

This is not necessarily wrong.

But consumers must know the archive layout.

## Lesson

Archive structure is part of the artifact contract.

Always inspect archives before publishing them.

# 98. Troubleshooting: Artifact Contains a Secret

## Problem

You inspect the archive and discover:

```text
config/production.env
```

containing a real credential.

## Action

Do not continue publishing or promoting the artifact.

Treat the credential as potentially exposed according to your organization's incident and secret-rotation procedures.

Removing the file from a later version does not automatically make an already exposed secret safe.

## Prevention

Add packaging exclusions and secret scanning where appropriate.

The build process should prevent sensitive files from entering release artifacts.

# 99. Common Beginner Mistakes

Avoid these:

1. Treating Generic repositories as random shared folders.
2. Uploading every file into the repository root.
3. Naming artifacts `final.zip`.
4. Overwriting the same release version.
5. Using `latest` as the only deployment identity.
6. Mixing development and release artifacts without a clear policy.
7. Rebuilding after testing instead of promoting the tested artifact.
8. Ignoring checksums.
9. Storing passwords in artifact properties.
10. Baking secrets into archives.
11. Giving CI administrator permissions.
12. Deleting old releases without understanding rollback requirements.
13. Assuming repository names enforce workflow automatically.
14. Publishing artifacts without inspecting their contents.
15. Testing only the original workspace rather than the stored artifact.
16. Using inconsistent paths between applications.
17. Treating every `.tar.gz` file as a Generic artifact without considering its package ecosystem.
18. Confusing generic deployment bundles with specialized JFrog release-management concepts.

Examples include ZIP distributions, TAR.GZ application bundles, standalone binaries, and configuration bundles without embedded secrets.

### Answer 4

If the JAR belongs to the Maven ecosystem and is consumed using Maven or Gradle dependency mechanisms, a Maven repository provides ecosystem-specific behavior.

### Answer 5

To verify required files are present and unwanted, temporary, or sensitive files are absent.

A compiled executable file that can be distributed and run on its intended platform.

### Answer 9

A consistent rule for naming artifacts so humans and automation can identify them predictably.
