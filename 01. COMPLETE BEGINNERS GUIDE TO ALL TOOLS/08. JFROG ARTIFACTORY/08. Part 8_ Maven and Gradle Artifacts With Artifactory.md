# Part 8: Maven and Gradle Artifacts With Artifactory

In Part 7, you built a complete artifact workflow around Generic repositories.

You learned this lifecycle:

```text
Application Files
↓
Package
↓
Development Repository
↓
Test
↓
Promote
↓
Release Repository
↓
Deploy
```

That taught an important principle:

```text
BUILD ONCE
↓
TEST THAT ARTIFACT
↓
PROMOTE THAT ARTIFACT
↓
DEPLOY THAT ARTIFACT
```

Now we will introduce something different.

Instead of treating an artifact simply as:

```text
veriqta-demo-1.0.0.tar.gz
```

we will enter a package ecosystem.

Specifically:

```text
Java
↓
Maven / Gradle
↓
JAR
↓
Maven Repository
↓
Artifactory
```

This introduces several new concepts:

* Packages
* Package coordinates
* POM files
* Dependency declarations
* Transitive dependencies
* Package repositories
* Dependency resolution
* Local Maven caches
* Remote repositories
* Virtual repositories
* Snapshot versions
* Release versions
* Publishing packages
* Dependency caching
* Maven authentication
* Gradle repository configuration
* Version conflicts

The final architecture for this part is:

```text
Java Source
↓
Maven / Gradle
↓
Compile
↓
Test
↓
Package
↓
JAR
↓
Artifactory
↓
Application Deployment
```

But there is another important flow.

Before Maven or Gradle can build your application, they may need dependencies:

```text
Maven Central
↓
Artifactory Remote Repository
↓
Artifactory Virtual Repository
↓
Maven / Gradle
↓
Java Build
```

So Artifactory participates in both directions:

```text
DEPENDENCIES
Artifactory
↓
Build

ARTIFACTS
Build
↓
Artifactory
```

Understanding these two directions is one of the most important lessons in this part.

# 1. Start With the Java Package Ecosystem

Imagine you are writing a Java application.

Your project might contain:

```text
veriqta-java-demo/
├── src/
│   ├── main/
│   │   └── java/
│   └── test/
│       └── java/
└── pom.xml
```

Inside the source directory are Java files.

For example:

```text
App.java
```

But a production Java project rarely contains only code written by your team.

Your application may also need external libraries.

For example, you may want:

* Logging libraries
* JSON libraries
* Testing libraries
* Database drivers
* HTTP clients
* Framework libraries

Instead of manually downloading every required JAR file, Java build tools can manage these dependencies.

Two of the most widely used tools are:

```text
Maven
Gradle
```

---

# 2. Source Code vs Dependency vs Artifact

These three concepts must remain separate.

## Source code

Code written by developers.

Example:

```java
public class App {
    public static void main(String[] args) {
        System.out.println("VERIQTA Java Demo");
    }
}
```

## Dependency

Software your application needs but that is typically developed and packaged separately.

Example:

```text
Jackson
JUnit
SLF4J
```

## Artifact

An output produced or consumed by the build.

A Java build commonly produces:

```text
.jar
```

For example:

```text
veriqta-java-demo-1.0.0.jar
```

The basic relationship is:

```text
Your Source Code
+
Dependencies
↓
Build Tool
↓
Compile
↓
Test
↓
Package
↓
JAR Artifact
```

---

# 3. What Is a JAR?

JAR stands for:

```text
Java Archive
```

A JAR is an archive format commonly used to package Java classes and associated resources.

For example:

```text
veriqta-java-demo-1.0.0.jar
```

might contain:

```text
META-INF/
com/
└── veriqta/
    └── demo/
        └── App.class
```

The `.class` file contains Java bytecode produced by compilation.

Conceptually:

```text
App.java
↓
Java Compiler
↓
App.class
↓
Packaging
↓
application.jar
```

---

# 4. Java Source Does Not Become a JAR Directly

A simplified Java build looks like:

```text
Java Source
↓
Compile
↓
Bytecode
↓
Test
↓
Package
↓
JAR
```

A build tool such as Maven or Gradle coordinates these steps.

That is why:

```text
Maven
```

is not simply:

```text
A JAR downloader
```

and Gradle is not simply:

```text
Another way to run Java
```

They are build automation systems.

Apache Maven is a build and project-management tool commonly used with Java projects.

Maven can help:

* Compile Java source
* Run tests
* Resolve dependencies
* Package applications
* Generate JARs
* Generate WARs
* Run plugins
* Publish artifacts
* Manage project metadata

A simplified Maven build is:

```text
Project
↓
pom.xml
↓
Maven
├── Resolve dependencies
├── Compile
├── Test
├── Package
└── Publish
```

```text

↓

↓
```

```text
↓

↓
```

The major difference is how projects and build logic are expressed and how the build systems operate internally.

```text

```

# 10. The Most Important Maven Concept: Coordinates

A file such as:

```text
library.jar
```

is not enough for reliable dependency management.

Maven identifies artifacts using coordinates.

Three foundational coordinate components are:

```text
groupId
artifactId
version
```

For example:

```text
groupId:
com.veriqta

artifactId:
veriqta-java-demo

version:
1.0.0
```

Together:

```text
com.veriqta:veriqta-java-demo:1.0.0
```

This identifies a specific version of a particular artifact.

---

# 11. Understanding groupId

Example:

```text
com.veriqta
```

`groupId` identifies the organizational or project namespace associated with the artifact.

Java projects commonly use reverse-domain-style naming.

For example:

```text
com.veriqta
org.example
io.company.platform
```

Why?

Because names such as:

```text
common
```

could be used by thousands of projects.

A namespace helps reduce collisions.

---

# 12. Understanding artifactId

Example:

```text
veriqta-java-demo
```

The `artifactId` identifies the particular project or module within the group.

For example:

```text
groupId:
com.veriqta

artifactId:
payment-api
```

Another project from the same organization might be:

```text
groupId:
com.veriqta

artifactId:
notification-service
```

Together:

```text
com.veriqta:payment-api
com.veriqta:notification-service
```

---

# 13. Understanding version

The version identifies a particular release or development version.

Examples:

```text
1.0.0
1.1.0
2.0.0
```

Maven also has an important snapshot convention:

```text
1.1.0-SNAPSHOT
```

We will examine snapshots shortly.

For now:

```text
groupId
+
artifactId
+
version
↓
Specific Maven artifact identity
```

# 14. Coordinates and Filenames

Suppose:

```text

artifactId = payment-api
version = 2.4.1
```

The JAR commonly becomes:

```text
payment-api-2.4.1.jar
```

But Maven coordinates provide more information than the filename alone.

They tell Maven how the artifact belongs within the package ecosystem.

# 15. Maven Repository Path Layout

Maven coordinates map naturally to repository paths.

Given:

```text
groupId:
com.veriqta

artifactId:
payment-api

version:
2.4.1
```

the repository path generally becomes:

```text
com/veriqta/payment-api/2.4.1/
```

Inside:

```text
payment-api-2.4.1.jar
payment-api-2.4.1.pom
```

So:

```text
com.veriqta
↓
com/veriqta

payment-api
↓
payment-api/

2.4.1
↓
2.4.1/
```

Result:

```text
com/
└── veriqta/
    └── payment-api/
        └── 2.4.1/
            ├── payment-api-2.4.1.jar
            └── payment-api-2.4.1.pom
```

This is one reason you should not randomly design paths inside a Maven repository the way you might with a Generic repository.

The ecosystem already has conventions.

# 16. What Is a POM?

POM stands for:

```text
Project Object Model
```

The project's POM is normally stored in:

```text
pom.xml
```

It describes important information about a Maven project.

A simple example:

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
         https://maven.apache.org/xsd/maven-4.0.0.xsd">

    <modelVersion>4.0.0</modelVersion>

    <groupId>com.veriqta</groupId>
    <artifactId>veriqta-java-demo</artifactId>
    <version>1.0.0</version>

</project>
```

# 17. Understanding the POM

The most important beginner lines are:

```xml
<groupId>com.veriqta</groupId>
```

This defines the group.

```xml
<artifactId>veriqta-java-demo</artifactId>
```

This identifies the project.

```xml
<version>1.0.0</version>
```

This identifies the version.

Together:

```text
com.veriqta:veriqta-java-demo:1.0.0
```

# 18. What Is a Dependency?

Suppose your application needs the Jackson Databind library.

Instead of downloading a random JAR and copying it into:

```text
lib/
```

you can declare it as a dependency.

For example:

```xml
<dependencies>
    <dependency>
        <groupId>com.fasterxml.jackson.core</groupId>
        <artifactId>jackson-databind</artifactId>
        <version>2.20.0</version>
    </dependency>
</dependencies>
```

The exact version here is only an example for learning. In real projects, choose versions based on compatibility, support, and security requirements.

Now Maven understands:

```text
My project
↓
Needs
↓
com.fasterxml.jackson.core
↓
jackson-databind
↓
specified version
```

---

# 19. Dependency Resolution

Declaring a dependency does not magically place it on your machine.

Maven must resolve it.

Conceptually:

```text
pom.xml
↓
Maven reads dependency
↓
Maven checks repositories
↓
Find package metadata
↓
Download required artifacts
↓
Use them during build
```

With Artifactory:

```text
pom.xml
↓
Maven
↓
Artifactory
↓
Repository
↓
Dependency
↓
Maven
↓
Build
```

This is called dependency resolution.

# 20. Direct and Transitive Dependencies

Suppose:

```text
Your Application
↓
Library A
```

Library A itself requires:

```text
Library B
```

You directly declared:

```text
Library A
```

That is a direct dependency.

Library B may become a transitive dependency.

Conceptually:

```text
Your Application
↓
Library A
↓
Library B
↓
Library C
```

Maven can resolve the dependency graph rather than forcing you to manually download every nested dependency.

# 21. Why Manual JAR Management Becomes Difficult

Without a dependency manager, a project might become:

```text
project/
├── src/
└── lib/
    ├── library-a.jar
    ├── library-b.jar
    ├── library-c.jar
    └── some-library-new-final.jar
```

Questions appear:

* Where did each JAR come from?
* Which version is it?
* Does it have dependencies?
* Is it vulnerable?
* Who updated it?
* Is it compatible?
* Which projects use it?

Dependency management provides structured answers to many of these problems.

# 22. What Is a Maven Repository?

A Maven repository stores artifacts and metadata using Maven-compatible conventions.

It can contain:

```text
JAR files
POM files
metadata
checksums
other Maven-associated artifacts
```

The repository supports operations such as:

```text
Resolve dependency
Publish package
Retrieve metadata
Select version
```

---

# 23. Maven Local Repository

Maven has a local repository on the developer or build machine.

By default, it is commonly:

```text
~/.m2/repository
```

Inspect it:

```bash
ls ~/.m2/repository
```

If Maven has already downloaded dependencies, you may see many directories.

This local repository acts as a local cache of dependencies and artifacts.

---

# 24. Why the Maven Local Repository Exists

Suppose Maven needs:

```text
library-a-1.0.0.jar
```

It downloads it.

Next time the build needs the same artifact, Maven may be able to use the locally cached copy rather than retrieving it again, subject to Maven's repository and update behavior.

Conceptually:

```text
Maven Build
↓
Check Local Repository
├── Found
│   ↓
│   Use cached artifact
│
└── Not available / update required
    ↓
    Resolve from configured repositories
```

---

# 25. Do Not Confuse Maven Local Repository With Artifactory Local Repository

This naming is confusing for beginners.

### Maven local repository

Usually:

```text
~/.m2/repository
```

It exists on a particular machine.

### Artifactory local repository

Exists on the Artifactory server.

It stores artifacts your organization publishes directly.

For example:

```text
libs-release-local
```

These are completely different things.

Remember:

```text
Maven Local Repository
↓
Developer/build machine

Artifactory Local Repository
↓
Central Artifactory server
```

---

# 26. Artifactory Maven Local Repository

An Artifactory local Maven repository can hold internally produced packages.

Example:

```text
veriqta-maven-release-local
```

It might contain:

```text
com/
└── veriqta/
    └── payment-api/
        └── 1.0.0/
            ├── payment-api-1.0.0.jar
            └── payment-api-1.0.0.pom
```

This artifact was produced by your organization rather than downloaded from an upstream public repository.

# 27. Artifactory Maven Remote Repository

Suppose developers need dependencies from Maven Central.

Without Artifactory:

```text
Developer
↓
Maven
↓
Maven Central
```

With an Artifactory remote repository:

```text
Developer
↓
Maven
↓
Artifactory Remote Repository
↓
Maven Central
```

The remote repository acts as a proxy for the upstream repository.

---

# 28. Why Proxy Maven Central Through Artifactory?

This provides useful capabilities such as:

* Centralized dependency access
* Caching
* Reduced repeated external downloads
* Central repository configuration
* Better visibility
* Organizational controls
* Resilience when previously cached artifacts are needed
* A central point for repository policy

Instead of every build reaching arbitrary public repositories directly:

```text
Developer 1 ──────→ Internet
Developer 2 ──────→ Internet
CI Runner 1 ──────→ Internet
CI Runner 2 ──────→ Internet
```

you can create:

```text
Developers
+
CI
↓
Artifactory
↓
Approved Upstream Repositories
```

---

# 29. Dependency Caching

Suppose Maven requests:

```text
example-library-1.0.0.jar
```

Artifactory checks its remote repository cache.

First request:

```text
Maven
↓
Artifactory
↓
Not cached
↓
Upstream
↓
Download
↓
Cache in Artifactory
↓
Return to Maven
```

Later request:

```text
Maven
↓
Artifactory
↓
Cached
↓
Return artifact
```

This is dependency caching.

---

# 30. Caching Does Not Mean "The Internet Is Never Needed Again"

Do not overgeneralize.

If a requested artifact has never been cached and the upstream repository is unavailable, Artifactory cannot invent that dependency.

Conceptually:

```text
Requested dependency
↓
Cached?
├── Yes → potentially serve cached content
└── No → upstream access may be required
```

This distinction becomes important during network outages.

---

# 31. Artifactory Maven Virtual Repository

A virtual repository provides one logical repository endpoint over multiple underlying repositories.

Suppose we have:

```text
veriqta-maven-release-local
maven-central-remote
```

A virtual repository could expose both through:

```text
veriqta-maven
```

Architecture:

```text
Maven
↓
veriqta-maven
├── veriqta-maven-release-local
└── maven-central-remote
    ↓
    Maven Central
```

The developer can configure one repository endpoint instead of manually managing several repository URLs.

# 32. Local, Remote and Virtual Maven Repositories Together

This is worth memorizing conceptually.

```text
                     ┌─────────────────────────┐
                     │    Maven / Gradle       │
                     └────────────┬────────────┘
                                  ↓
                     ┌─────────────────────────┐

                                  │
```

```text
Our packages
```


```text
Unified access point
```

# 33. Snapshot vs Release Versions

Maven has an important distinction between releases and snapshots.

Release:

```text
1.0.0
```

Snapshot:

```text
1.1.0-SNAPSHOT
```

A release version represents a fixed release identity.

A snapshot represents an in-development version that may be updated as development continues.

---

# 34. Understanding SNAPSHOT

Suppose developers are working toward:

```text
1.1.0
```

During development, the POM might contain:

```xml
<version>1.1.0-SNAPSHOT</version>
```

This communicates:

```text
This is development work toward 1.1.0.
It is not yet the final 1.1.0 release.
```

Unlike a release coordinate, a snapshot coordinate is expected to support changing development builds according to Maven snapshot behavior.

---

# 35. Why SNAPSHOT Is Different From Part 7's Generic Development Naming

In Part 7, we might have invented a generic artifact name such as:

```text
2.0.0-dev.17.tar.gz
```

That was our own Generic repository lifecycle convention.

Maven:

```text
1.1.0-SNAPSHOT
```

has ecosystem-specific meaning.

Artifactory understands Maven repository behavior and metadata.

This is exactly why using the correct repository package type matters.

---

# 36. Snapshot Repository

A team may create an Artifactory Maven repository specifically for snapshots:

```text
veriqta-maven-snapshot-local
```

and another for releases:

```text
veriqta-maven-release-local
```

Conceptually:

```text
1.1.0-SNAPSHOT
↓
Snapshot Repository

1.1.0
↓
Release Repository
```

This creates a clearer lifecycle boundary.

---

# 37. Release Immutability Still Matters

The same principle from Part 7 applies.

Bad:

```text
payment-api:1.0.0
↓
Publish bytes A
↓
Later overwrite
↓
Publish bytes B
```

Now:

```text
1.0.0
```

has lost stable meaning.

For released artifacts, prefer:

```text
1.0.0
↓
Stable release

Need a fix?
↓
1.0.1
```

Snapshot behavior is different because snapshots represent ongoing development.

# 44. Understand the Project Identity

Our project coordinates are:


# 56. Maven Mirror Concept

Organizations commonly configure Maven so repository requests are routed through an Artifactory virtual repository.

Conceptually:

```text
Maven requests repository
↓
Mirror configuration
↓
Artifactory virtual repository
```

A simplified `settings.xml` pattern may look like:

```xml
<settings>

    <mirrors>
        <mirror>
            <id>veriqta-artifactory</id>
            <name>VERIQTA Artifactory</name>
            <url>https://YOUR-JFROG-HOST/artifactory/veriqta-maven</url>
            <mirrorOf>*</mirrorOf>
        </mirror>
    </mirrors>

</settings>
```

Do not literally use:

```text
YOUR-JFROG-HOST
```

Replace it with the repository URL from your own Artifactory environment.

---

# 57. Understanding mirrorOf

This line:

```xml
<mirrorOf>*</mirrorOf>
```

means the mirror is intended to match repository requests broadly.

The exact mirror strategy should be designed deliberately for the organization.

At beginner level, understand the purpose:

```text
Instead of builds independently reaching repositories
↓
Route repository access through Artifactory
```

# 64. Configure a Deployment Repository

One approach uses Maven's `distributionManagement` in the POM.

Conceptual example:

```xml
<distributionManagement>

    <snapshotRepository>
        <id>veriqta-snapshots</id>
        <url>https://YOUR-JFROG-HOST/artifactory/veriqta-maven-snapshot-local</url>
    </snapshotRepository>

    <repository>
        <id>veriqta-releases</id>
        <url>https://YOUR-JFROG-HOST/artifactory/veriqta-maven-release-local</url>
    </repository>

</distributionManagement>
```

The IDs matter because Maven can associate them with credentials configured elsewhere.

---

# 65. Configure Authentication

Your `settings.xml` might contain server entries such as:

```xml
<servers>

    <server>
        <id>veriqta-snapshots</id>
        <username>${env.JFROG_USER}</username>
        <password>${env.JFROG_TOKEN}</password>
    </server>

    <server>
        <id>veriqta-releases</id>
        <username>${env.JFROG_USER}</username>
        <password>${env.JFROG_TOKEN}</password>
    </server>

</servers>
```

The important relationship is:

```text
distributionManagement ID
↓
Matches
↓
settings.xml server ID
```

If they do not match, Maven may not apply the credentials you expect.

---

# 66. Avoid Hardcoded Credentials

Do not write:

```xml
<username>admin</username>
<password>my-real-token</password>
```

into a POM committed to Git.

For a learning environment, environment variables can demonstrate separation:

```bash
export JFROG_USER="your-user"
export JFROG_TOKEN="your-token"
```

Then:

```xml
<username>${env.JFROG_USER}</username>
<password>${env.JFROG_TOKEN}</password>
```

In CI/CD, use the CI platform's secret-management capabilities or an appropriate secret-management system.

Also remember:

```text
Environment variable
≠
Automatically perfect secret security
```

It is simply better than hardcoding secrets into source-controlled files when used appropriately.

* Token
* Token validity
* Environment variables
* `settings.xml`
* Server IDs
* Repository URL
* CI secret injection

```text

↓
```

```text
↓
Requires appropriate write/deploy permission
```


A clean CI environment can expose dependencies your laptop accidentally hides.

# 98. Test Dependency Resolution More Carefully

If you suspect local cache is hiding a problem, investigate deliberately.

Do not immediately delete your entire:

```text
~/.m2/repository
```

Instead, you can inspect the specific dependency directory.

For example:

```bash
find ~/.m2/repository -path "*jackson-databind*" -print
```

For disposable labs, you can also use a separate temporary local repository:

```bash
mvn -Dmaven.repo.local=/tmp/veriqta-m2-test clean package
```

This forces that Maven invocation to use:

```text
/tmp/veriqta-m2-test
```

as its local repository.

This is often safer for troubleshooting than destroying your normal cache.

# 99. Troubleshooting: Artifactory Remote Repository Cannot Reach Upstream

Flow:

```text
Maven
↓
Artifactory
↓
Remote Repository
↓
Upstream
```

If the artifact is not cached and upstream access fails, dependency resolution may fail.

Possible causes:

* DNS problems
* Firewall rules
* Proxy configuration
* TLS problems
* Upstream outage
* Incorrect upstream URL
* Network restrictions

The correct investigation is not:

```text
Delete pom.xml
```

The failure is further downstream.

# 100. Troubleshooting: Cached Dependency Works During an Outage

Suppose Maven Central becomes temporarily unreachable.

Dependency A was already cached in Artifactory.

Dependency B was never cached.

You may observe:

```text
Dependency A
↓
Succeeds

Dependency B
↓
Fails
```

Why?

```text
A
↓
Artifactory already has it

B
↓
Requires upstream retrieval
```

This demonstrates the practical value and limits of remote caching.

# 101. Troubleshooting: Maven Cached a Failed Lookup

Maven may cache information about failed artifact resolution.

After fixing the repository, you may still see confusing behavior.

One troubleshooting option is:

```bash
mvn -U clean package
```

The `-U` option requests updated repository checks.

Do not automatically use it for every build.

Understand why you are using it.

# 102. Troubleshooting: Version Conflicts

Suppose:

```text
Your Application
├── Library A
│   └── Common Library 1.0
│
└── Library B
    └── Common Library 2.0
```

Now two dependency paths want different versions of the same library.

This is a dependency conflict.

Symptoms can include:

* Compilation problems
* Runtime errors
* Missing methods
* Unexpected behavior
* Class loading errors

---

# 103. Investigate Maven Version Conflicts

Run:

```bash
mvn dependency:tree
```

For more detail:

```bash
mvn dependency:tree -Dverbose
```

Depending on Maven/plugin versions, output detail may vary.

Search for the problematic library.

Your goal is to understand:

```text
Who introduced version 1?
Who introduced version 2?
Which version did Maven select?
```

Do not immediately exclude random dependencies.

# 104. Dependency Management

Maven supports dependency management to help control versions centrally within a project hierarchy.

Example:

```xml
<dependencyManagement>
    <dependencies>

        <dependency>
            <groupId>com.example</groupId>
            <artifactId>common-library</artifactId>
            <version>2.0.0</version>
        </dependency>

    </dependencies>
</dependencyManagement>
```

This is different from simply declaring:

```xml
<dependencies>
```

A beginner should remember:

```text
dependencies
↓
Declares dependencies the project uses

dependencyManagement
↓
Can define/manage dependency version information for consistent use
```

The exact behavior becomes especially important in multi-module and parent-POM designs.

---

# 105. Exclusions

Sometimes a transitive dependency must be excluded deliberately.

Example:

```xml
<dependency>
    <groupId>com.example</groupId>
    <artifactId>library-a</artifactId>
    <version>1.0.0</version>

    <exclusions>
        <exclusion>
            <groupId>com.example</groupId>
            <artifactId>problematic-library</artifactId>
        </exclusion>
    </exclusions>
</dependency>
```

Do not copy an exclusion merely to silence an error.

Understand why the transitive dependency exists and what replacing or removing it does.

# 108. Gradle Repository Ordering

A Gradle project can declare multiple repositories.

For example:

```groovy
repositories {
    maven {
        url = uri('https://YOUR-JFROG-HOST/artifactory/veriqta-maven')
    }

    mavenCentral()
}
```

But if your organization requires dependency traffic to pass through Artifactory, directly adding:

```groovy
mavenCentral()
```

may bypass that architecture.

A controlled environment might intentionally use only:

```text
Artifactory Virtual Repository
```

which itself proxies approved upstream sources.

Repository configuration is therefore part of supply-chain governance, not merely build syntax.

# 109. Why Direct Public Repository Access Can Be a Problem

Imagine:

```text

├── Maven Central
├── Random Repository A
├── Random Repository B
```

Now the organization has less centralized control over:

* Which repositories are approved
* What is cached
* What can be audited
* What is available to CI
* What external services builds depend on

A stronger pattern is:

```text

↓

↓
```

# 111. Do Not Put Artifactory Tokens in Git

Never commit files containing real tokens such as:

```text

gradle.properties with committed secrets
```

Deleting one line from the current file is not necessarily sufficient.

# 132. Common Beginner Mistakes

Avoid these:

1. Thinking Maven is only a dependency downloader.
2. Thinking Gradle is simply "new Maven."
3. Confusing source code with artifacts.
4. Confusing dependencies with build outputs.
5. Not understanding Maven coordinates.
6. Treating Maven repository paths like arbitrary folders.
7. Uploading Maven packages to Generic repositories without understanding the consequences.
8. Confusing Maven's local repository with an Artifactory local repository.
9. Confusing Artifactory remote repositories with Maven remote repositories conceptually.
10. Bypassing Artifactory with direct public repository definitions.
11. Hardcoding Artifactory credentials in `pom.xml`.
12. Committing tokens into Git.
13. Using snapshots as production releases without a deliberate policy.
14. Overwriting released versions.
15. Assuming `mvn install` publishes to Artifactory.
16. Assuming `mvn deploy` means application deployment.
17. Ignoring POM files.
18. Ignoring transitive dependencies.
19. Randomly deleting `~/.m2/repository` whenever Maven fails.
20. Ignoring the exact dependency coordinates in error messages.
21. Giving CI administrator permissions to fix 403 errors.
22. Assuming local build success proves repository configuration works.
23. Ignoring Java/JDK version mismatches.
24. Failing to verify that dependency traffic actually passes through Artifactory.
25. Assuming every JAR belongs in a Generic repository.
26. Using "latest" thinking instead of explicit package versions.
27. Ignoring dependency conflicts.
28. Excluding dependencies without understanding why they exist.
29. Confusing snapshot metadata with ordinary filenames.
30. Treating `BUILD SUCCESS` as proof that the package was published correctly.
