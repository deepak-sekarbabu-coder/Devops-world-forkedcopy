Do not confuse these.


```text
https://example.jfrog.io/artifactory
```

API endpoint:

```text
https://example.jfrog.io/artifactory/api/system/ping
```

Repository or artifact URLs can add repository and artifact information.

Conceptually:

```text

↓
Service
↓
Repository
↓
Path
↓

```

Understanding URL construction will save you many hours of troubleshooting later.

# 12. What Is an Endpoint?

An endpoint is a specific network-accessible location exposed by a service for a particular operation or resource.

For example:

```text
/artifactory/api/system/ping
```

is an API endpoint.

Its purpose is to answer a simple question:

```text
Is Artifactory responding?
```

A repository endpoint has a different purpose.

It may be used by:

```text
Maven
npm
pip
Docker
Helm
JFrog CLI
```

to publish or retrieve packages.

So:

```text
Platform URL
≠
API Endpoint
≠
Repository URL
```

They are related, but not interchangeable.

# 32. Passwords vs Access Tokens

A password authenticates a human account.

An access token can provide programmatic access according to the token's permissions, scope, lifetime, and associated identity.

For automation, access tokens are generally preferable to putting a personal password into scripts.

Bad:

```text
curl -u ann:MyRealPassword123 ...
```

Worse:

```text
git add script.sh
git commit
git push
```

where `script.sh` contains your real password.

Now your credential may be in Git history.

---

# 33. Never Hardcode Credentials

Do not write:

```bash
JFROG_TOKEN="eyJ..."
```

inside a script that you plan to commit.

Do not write:

```python
password = "MyRealPassword"
```

inside application source.

Do not put secrets directly in:

```text
Dockerfile
Jenkinsfile
GitHub workflow committed as plain text
README
Terraform code
Shell scripts
Git repository
```

A secret accidentally committed to Git may remain recoverable from repository history even after you delete the visible line.

If a real secret is exposed, treat it as compromised and rotate or revoke it.

---

# 34. Use Environment Variables

Environment variables let your shell or automation environment supply values without embedding them directly into source files.

For example:

```bash
export JFROG_URL="https://example.jfrog.io"
```

and:

```bash
export JFROG_ACCESS_TOKEN="YOUR_TOKEN"
```

Now your script can refer to:

```bash
$JFROG_URL
```

and:

```bash
$JFROG_ACCESS_TOKEN
```

instead of embedding the values repeatedly.

JFrog's current CLI authentication documentation shows this pattern, then passes those values into CLI configuration.

---

# 35. Important Environment Variable Detail

There is a subtle point beginners need to understand.

Setting:

```bash
export JFROG_URL="..."
export JFROG_ACCESS_TOKEN="..."
```

does not, by itself, mean every invocation of the standalone `jf` CLI automatically knows how to use those particular variables.

Current JFrog documentation says the CLI can receive environment-variable values through `jf config add` or command options. Some CI integrations, such as JFrog's setup action, recognize variables such as `JF_URL` and `JF_ACCESS_TOKEN` and configure the CLI for you.

For a beginner shell workflow, we can deliberately do:

```bash
export JFROG_URL="https://example.jfrog.io"
export JFROG_ACCESS_TOKEN="YOUR_TOKEN"
```

then:

```bash
jf config add veriqta-lab \
  --url="$JFROG_URL" \
  --access-token="$JFROG_ACCESS_TOKEN" \
  --interactive=false
```

This makes the relationship explicit.

---

# 36. Understanding `export`

Consider:

```bash
export JFROG_URL="https://example.jfrog.io"
```

Break it down.

`export`

Makes the variable available to processes launched from that shell.

`JFROG_URL`

The variable name.

`=`

Assigns a value.

`"https://example.jfrog.io"`

The value.

You can inspect it with:

```bash
echo "$JFROG_URL"
```

Expected output:

```text
https://example.jfrog.io
```

Do not run:

```bash
echo "$JFROG_ACCESS_TOKEN"
```

during screen sharing, recording, or in logs.

That could expose your token.

---

# 37. Environment Variables Are Not Magic Secret Storage

This distinction matters.

Environment variables help you avoid embedding credentials directly in code.

But they still need to be handled securely.

A secret can still leak through:

* Shell history
* Debug output
* CI logs
* Process inspection in some environments
* Screenshots
* Copy/paste
* Misconfigured pipeline logging

Production CI/CD systems should normally use their protected secret-management mechanisms.

For example:

```text
CI Secret Store
↓
Environment Variable at Runtime
↓
JFrog CLI
```

not:

```text
Git Repository
↓
Plaintext Token
```

# 41. What Is `PATH`?

`PATH` is an environment variable containing directories your shell searches for executable programs.

When you type:

```bash
jf
```

the shell needs to locate the `jf` executable.

Conceptually:

```text
You type:
jf

Shell:
Search PATH

Found?
├── Yes → Run JFrog CLI
└── No  → command not found
```

This is not an Artifactory-specific concept.

It is a fundamental command-line concept.

# 42. Configure JFrog CLI

Once JFrog CLI is installed, configure a server.

Example:

```bash
jf config add veriqta-lab \
  --url="$JFROG_URL" \
  --access-token="$JFROG_ACCESS_TOKEN" \
  --interactive=false
```

Break it down.

`jf`

Runs JFrog CLI.

`config`

Works with CLI server configuration.

`add`

Adds a server configuration.

`veriqta-lab`

Your local identifier for this JFrog server configuration.

`--url`

Specifies the JFrog Platform URL.

`--access-token`

Provides authentication.

`--interactive=false`

Prevents the interactive setup wizard.

JFrog documents this general configuration pattern for token-based CLI access.

---

# 46. What Does `jf rt ping` Actually Prove?

If:

```bash

```

returns:

```text
OK
```

you have evidence that:

* JFrog CLI runs
* CLI has a usable server configuration
* DNS/network connectivity works sufficiently
* TLS negotiation works sufficiently
* The Artifactory endpoint responds
* Authentication/configuration is sufficient for the ping operation

It does not prove:

* You can upload to every repository
* You can download every artifact
* Your CI/CD configuration works
* Every repository exists
* Every permission is correct

Connectivity and authorization to specific resources are separate questions.

# 48. Test DNS

```bash
nslookup example.jfrog.io
```

The exact output varies.

You are looking for evidence that the hostname resolves.

Another tool available on many Unix-like systems is:

```bash

```

You do not need to master DNS in this article.

You only need to understand:

```text
Hostname
↓
DNS
↓
IP Address
```

If DNS fails, Artifactory may be healthy while your computer cannot locate it.

# 53. Why Repository URLs Differ

Maven expects Maven repository behavior.

npm expects npm registry behavior.

Docker expects registry behavior.

PyPI clients expect Python package repository behavior.

Therefore:

```text

↓
Maven-Compatible Endpoint
```

```text
npm
↓
npm-Compatible Endpoint
```

```text
pip
↓
PyPI-Compatible Endpoint
```

```text
Docker
↓
Container Registry Endpoint
```

Artifactory supports multiple package ecosystems, but the clients do not all communicate identically.

# 81. Troubleshooting: 401 Unauthorized

Symptom:

```text

```

Meaning:

The request lacks valid authentication credentials or authentication failed.

JFrog's current troubleshooting guidance describes HTTP 401 this way.

Investigate:

```text

Is it expired?
Was it copied completely?

```

Do not solve 401 by immediately giving the user administrator permissions.

Authentication and authorization are different.
