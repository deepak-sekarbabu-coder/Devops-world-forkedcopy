# 1. What Is an External Dependency?

An external dependency is software your application requires but your organization did not necessarily create.

Suppose you write:

```python
import requests
```

Your application depends on the Python `requests` package.

Suppose a JavaScript application contains:

```javascript
const express = require("express");
```

It depends on the npm package:

```text
express
```

A Java application might depend on:

```text
Jackson
Spring Framework
JUnit
Log4j
```

A Dockerfile might contain:

```dockerfile
FROM python:3.13-slim
```

Now the build depends on an external container image.

Your source code may be entirely internal while your build still depends heavily on external software.

---

# 2. Modern Applications Are Dependency Graphs

Consider a small application.

You directly install:

```text
Package A
Package B
Package C
```

But Package A requires:

```text
D
E
F
```

Package B requires:

```text
G
H
```

Package G requires:

```text
I
J
K
```

Your real dependency structure becomes:

```text
Application
├── A
│   ├── D
│   ├── E
│   └── F
├── B
│   ├── G
│   │   ├── I
│   │   ├── J
│   │   └── K
│   └── H
└── C
```

This is a dependency graph.

You may intentionally select only three dependencies but indirectly consume many more.

That is why dependency management is also a software supply-chain problem.

---

# 3. Direct vs Transitive Dependencies

A direct dependency is something your application explicitly requests.

Example:

```text
Application
↓
Package A
```

A transitive dependency is required by another dependency.

Example:

```text
Application
↓
Package A
↓
Package B
```

Your application did not explicitly request Package B.

Package A did.

But Package B still becomes part of your software supply chain.

This distinction matters because vulnerabilities or malicious code can exist deep inside the dependency graph.

# 5. The Direct Internet Dependency Problem

Without a repository manager, every developer and CI runner might independently contact public services.

Architecture:

```text
Developer 1 ──────→ Public Registry
Developer 2 ──────→ Public Registry
Developer 3 ──────→ Public Registry
CI Runner 1 ──────→ Public Registry
CI Runner 2 ──────→ Public Registry
CI Runner 3 ──────→ Public Registry
```

This creates several problems.

You have:

```text
Many clients
Many internet connections
Many dependency requests
Many possible external sources
```

Operational questions become harder:

```text
Which external registries are being used?

Which dependencies entered the organization?

Were packages retrieved from approved sources?

What happens when an external registry is unavailable?

Can we stop developers from using an unwanted source?

Can we reuse already-downloaded packages?

Can we investigate dependency activity centrally?
```

Artifactory helps centralize this architecture.

```text

↓
```

```text
PyPI
```

Artifactory sits between the client and upstream source.

That gives Artifactory an opportunity to:


dependency requests.

# 10. Caching

Caching means Artifactory stores content retrieved through a remote repository so later requests can potentially be served locally.

First request:

```text
Developer A
↓
Artifactory
↓
Cache Miss
↓
External Registry
↓
Download dependency
↓
Store in remote cache
↓
Return dependency
```

Later request:

```text
Developer B
↓
Artifactory
↓
Cached dependency found
↓
Return dependency
```

No new upstream binary download may be required for that cached object.

---

# 11. What Is a Cache Hit?

A cache hit occurs when Artifactory can satisfy the requested content using its cache.

Conceptually:

```text
Request
↓
Cache lookup
↓
FOUND
↓
Return cached content
```

This is a:

```text
Cache Hit
```

---

# 12. What Is a Cache Miss?

A cache miss occurs when the required content is not available in cache in the needed form.

Conceptually:

```text
Request
↓
Cache lookup
↓
NOT FOUND
↓
Contact upstream
```

This is:

```text
Cache Miss
```

A cache miss is not automatically an error.

It is normal when a dependency is being requested for the first time.

# 14. Remote Repository Cache Is Separate From Client Cache

This distinction is extremely important.

A developer's machine may have its own cache.

Examples:

```text
Maven local repository
npm cache
pip cache
Docker local image cache
```

Artifactory has a different cache:

```text
Artifactory remote repository cache
```

Architecture:

```text
Developer Machine
│
├── Client Cache
│
↓
Artifactory
│
├── Remote Repository Cache
│
↓
External Registry
```

These are separate layers.




# 33. Dependency Confusion

Dependency confusion is a supply-chain attack pattern involving ambiguity between internal and external package namespaces.

Imagine your company internally uses:

```text
veriqta-payment-core
```

but that package is not supposed to exist publicly.

An attacker publishes a package with the same name to a public registry.

If your package-management configuration incorrectly prefers or selects the public version, a build may retrieve the attacker's package.

Conceptually:

```text
Application requests:
veriqta-payment-core
↓
Internal source?
External source?
↓
Incorrect resolution
↓
Malicious external package
```

That is the core dependency-confusion problem.

---

# 34. Dependency Confusion Is Not Simply a Version Problem

A common explanation is:

```text
Attacker publishes higher version
↓
Package manager chooses it
```

That can be part of some attacks.

But the broader problem is:

```text
Internal package namespace
+
External package source
+
Unsafe resolution behavior
=
Potential confusion
```

The exact mechanics depend on the package ecosystem and client configuration.

---

# 35. Protect Internal Package Namespaces

Defensive thinking includes:

```text

Appropriate package-manager configuration
```

For npm, organizations often use scoped internal packages such as:

```text

```

rather than generic public-looking names.

This does not replace repository security, but namespace discipline helps.

# 45. Package Block Concepts

A block-oriented model allows general package access but denies known unwanted content.

Conceptually:

```text
Dependency request
↓
Known blocked package/version?
├── YES → Reject
└── NO → Continue
```

Examples of reasons to block could include:

```text
Known malicious package
Unapproved license
Severe vulnerability
Deprecated package
Policy violation
Compromised version
```

The exact implementation may involve additional JFrog capabilities and organizational tooling, not merely a basic remote repository.

The important beginner concept is:

```text
Centralized dependency traffic
↓
Creates opportunity for centralized policy enforcement.
```

---

# 52. Remote Repository Behavior

A remote repository commonly performs several jobs:

```text
Receive client request
↓
Check cache
↓
Determine whether upstream access is needed
↓
Contact configured upstream when required
↓
Retrieve metadata/content
↓
Cache appropriate content
↓
Serve client
```

This is more sophisticated than a simple HTTP redirect.

# 53. Artifactory Is Not Merely Redirecting the Client

A redirect model would look like:

```text
Client
↓
Artifactory
↓
"Go download this from public registry."
```

That would provide little caching benefit.

Instead, proxy behavior is conceptually:

```text
Client
↓
Artifactory
↓
Artifactory obtains content
↓
Artifactory serves client
```

That is why Artifactory can cache the dependency.

```text
1.1.0
```

Later upstream adds:

```text
1.2.0
```

If Artifactory or another cache layer still holds earlier metadata temporarily, a client may not immediately see:

```text
1.2.0
```

This introduces the concept of:

```text
Stale metadata
```

---

# 56. Stale Metadata Does Not Mean Corrupted Artifact

These are different problems.

Stale metadata:

```text
Repository view is temporarily older than upstream state.
```

Corrupted binary:

```text
Artifact content itself is damaged or incorrect.
```

Do not confuse them.

---

# 57. Metadata Refresh Concepts

Repository systems balance:

```text
Freshness
vs
Performance
vs
Upstream traffic
```

If every metadata request always contacts upstream:

```text
Freshness improves
but
External dependency increases
```

If metadata is cached:

```text
Performance improves
but
There can be a freshness window
```

Repository cache settings control aspects of this behavior.

Do not randomly reduce every cache timeout to zero when troubleshooting.

---

# 58. Cache Expiration Concepts

A common beginner misunderstanding:

```text
Cache expiration
=
Binary immediately deleted.
```

Not necessarily.

Repository systems can use expiration values to determine when cached information should be checked or refreshed against upstream.

Binary cleanup and metadata refresh are separate concepts.

Always identify which cache setting you are investigating.

---

# 59. Positive and Negative Resolution Concepts

Suppose you request:

```text
package-x:1.0.0
```

and it exists.

That is a successful resolution.

Now request:

```text
package-x:99.99.99
```

and upstream says:

```text
Not Found
```

Repository managers may also temporarily remember failed lookup information to avoid repeatedly asking upstream for the same missing content.

This introduces:

```text
Negative caching
```

conceptually.

---

# 60. Why Negative Caching Exists

Imagine 1,000 builds repeatedly request a nonexistent artifact.

Without negative caching:

```text
1,000 requests
↓
1,000 upstream lookups
↓
1,000 not-found responses
```

With remembered failed resolution:

```text
Initial failed lookup
↓
Temporarily remember absence
↓
Reduce repeated upstream requests
```

This improves efficiency.

But it also creates a troubleshooting scenario.

---

# 61. Newly Published Artifact Still Appears Missing

Timeline:

```text
10:00
Client requests package 2.0.0
↓
Upstream says not found

10:02
Package 2.0.0 is published upstream

10:03
Client requests again
↓
Repository may still have recent not-found state
```

Depending on repository configuration and package behavior, the new package may not become visible immediately.

This is one reason cache behavior matters.

---

# 62. Do Not Immediately Delete the Entire Cache

A common troubleshooting reaction:

```text
Dependency missing
↓
Clear everything
```

That can:

```text
Increase upstream traffic
Destroy useful cached state
Create more cache misses
Make an outage worse
```

Investigate the specific dependency and metadata first.

---

# 63. Remote Repository Availability

```text

↓

↓

↓

↓

```

A failure at any layer can appear as:


# 64. Upstream Outage

Suppose PyPI is temporarily unavailable.

Architecture:

```text
pip
↓
Artifactory
↓
pypi-remote
↓
PyPI
       X
```

Previously cached packages may still be available.

Uncached packages may fail.

This is why an incident can produce:

```text
Project A builds
Project B fails
```

even though both use the same remote repository.

---

# 65. Upstream Outage Investigation

Ask:

```text
Is Artifactory healthy?

Is upstream healthy?

Can Artifactory reach upstream?

Is requested package cached?

Does another cached package resolve?

Is only one package failing?

Is metadata lookup failing?

Is DNS working?

Is TLS valid?

Is a proxy involved?
```

Do not begin by changing package versions.

---

# 66. Offline Behavior

A remote repository can be configured so that it does not make upstream requests while operating in an offline-style mode.

Conceptually:

```text
Client
↓
Remote Repository
↓
Cache only
```

If requested content is cached:

```text
SUCCESS
```

If not cached:

```text
FAIL
```

This can be useful in controlled situations, but understand the consequences.

---

# 67. Offline Does Not Mean Full Mirror

Again:

```text
Remote repository
≠
Complete upstream mirror
```

If you switch remote access offline before all required dependencies have been cached, builds requiring uncached dependencies can fail.

---

# 68. Dependency Pre-Warming Concept

Organizations with strict availability requirements sometimes ensure important dependencies have been resolved and cached before critical events.

Conceptually:

```text
Known build dependencies
↓
Resolve through Artifactory
↓
Cache
↓
Verify
```

This is sometimes called cache warming or pre-warming conceptually.

But it is not a substitute for:

```text
Dependency lockfiles
Version pinning
Release planning
Artifact retention
```

# 69. Reproducible Builds and External Dependencies

Suppose your dependency file says:

```text

```

Today:

```text
1.5
```

is selected.

Tomorrow:

```text
1.6
```

appears.

Now the same source code may build differently.

Artifactory caching alone does not solve this.

You also need appropriate dependency version management.

---

# 70. Version Pinning

More reproducible:

```text
Dependency
↓
Exact or controlled version
```

Less predictable:

```text
Dependency
↓
Whatever newest compatible version exists today
```

Exact strategy varies by ecosystem, but the principle is:

```text
Dependency identity should be intentional.
```

Use ecosystem-appropriate lockfiles and version controls where applicable.

---

# 71. Lockfiles

Examples include:

```text
package-lock.json
```

and other ecosystem-specific lock mechanisms.

A lockfile helps record the resolved dependency graph.

Architecture:

```text
Source
+
Dependency Definition
+
Lockfile
↓
Build
```

Artifactory then provides controlled access to those dependency artifacts.

These mechanisms complement each other.

---

# 72. Repository Control Does Not Replace Lockfiles

Artifactory controls:

```text
Where dependencies come through.
```

Lockfiles/version constraints control:

```text
Which dependencies should be selected.
```

You generally need both concepts.

---

# 73. Checksums and Dependency Integrity

Artifacts have checksums.

A checksum can help identify whether content matches expected binary data.

Recall:

```text
Artifact
↓
SHA-256
↓
Digest
```

If content changes:

```text
Checksum changes
```

This supports integrity and traceability.

But checksum alone does not tell you:

```text
Whether the software is trustworthy.
```

Malicious software can also have a perfectly valid checksum.

---

# 74. Integrity vs Trust

Integrity:

```text
Did these bytes change?
```

Trust:

```text
Should we use these bytes at all?
```

These are different questions.

Supply-chain security requires both.

---

```text
Which version was used?

```

The more traceability you maintain, the easier security investigations become.
