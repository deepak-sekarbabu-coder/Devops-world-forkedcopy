# 1. What Is the JFrog Platform?

JFrog Artifactory is not necessarily the entire JFrog environment.

It is one major component of the broader JFrog Platform.

The JFrog Platform is designed to support different stages of software development, artifact management, security, release management, and distribution.

JFrog currently describes the platform as a collection of component services that work across the CI/CD lifecycle, with Artifactory providing artifact and binary management as one of the central services.

A simplified conceptual platform might look like this:

```text
                JFrog Platform
                     |
        --------------------------------
        |              |               |
   Artifactory        Xray        Other Services
        |
 Artifact Management
```

For this beginner series, our primary focus is:

```text
JFrog Platform
      ↓
JFrog Artifactory
```

You do not need to master every JFrog product before learning Artifactory.

---

# 2. What Role Does Artifactory Play Inside the JFrog Platform?

Artifactory is responsible primarily for managing software packages and artifacts.

That includes things such as:

* JAR files
* WAR files
* ZIP archives
* TAR archives
* npm packages
* Python packages
* NuGet packages
* container images
* Helm charts
* generic binaries
* internal libraries
* build outputs

Conceptually:

```text
Build
↓
Artifact
↓
Artifactory
↓
Store
Organize
Search
Secure
Retrieve
Promote
Distribute
```

Other JFrog services may work with the artifacts Artifactory stores.

For example, another security component may scan an artifact.

But Artifactory remains the repository-management layer.

A beginner can easily imagine Artifactory as:


```text

...

...

```

Artifactory can expose artifact metadata such as repository, path, timestamps, size, checksums, and properties through its APIs.

That is why Artifactory is a repository manager rather than simply file storage.

# 8. What Is a REST API?

REST API means a programmatic interface that applications can use to communicate with a service over HTTP.

Instead of clicking a button, a client sends an HTTP request.

For example, conceptually:

```text
GET
```

might request information.

```text
PUT
```

might upload or create something.

```text
POST
```

might submit information or trigger an operation.

```text
DELETE
```

might delete something.

The exact meaning depends on the endpoint.

Artifactory provides REST APIs for many operations.

For example, artifact information can be retrieved through an endpoint containing a repository and artifact path.

# 16. Repository Path

An artifact path tells Artifactory where the artifact logically lives inside a repository.

Example:

```text
libs-release-local/com/veriqta/payment/1.0.0/payment-api-1.0.0.jar
```

Break it apart:

```text
libs-release-local
↓
Repository

com/veriqta/payment/1.0.0/
↓
Path

payment-api-1.0.0.jar
↓
Artifact
```

This logical path is what users and package managers see.

But this does not necessarily mean the binary is physically stored on disk using exactly that same directory structure.

That distinction becomes extremely important when we learn about checksum-based storage.

---

# 17. Logical Path vs Physical Storage

A beginner might assume:

```text
Repository path
=
Exact disk path
```

Artifactory does not have to work that way.

The user may see:

```text
libs-release-local/com/veriqta/payment/1.0.0/payment-api-1.0.0.jar
```

Internally, Artifactory can store the binary based on its checksum and use database mappings to connect that stored content with the logical repository path.

JFrog documents Artifactory as using checksum-based storage, where repository paths are mapped through the database to checksum-addressed binary content.

Conceptually:

```text
Logical Repository Path
↓
Database Mapping
↓
Checksum
↓
Stored Binary
```

This is one of the most important architecture concepts in Part 2.

# 21. Database Concepts

Artifactory needs a database.

Why?

Because a mature repository manager must remember much more than file contents.

The database can contain information and relationships describing repository content and platform state.

For example:

```text
Artifact Path
↓
Database Entry
↓
Checksum
↓
Metadata
```

The database can help Artifactory answer:

```text
Where is this artifact?
```

```text
Which repository contains it?
```

```text
Which checksum belongs to it?
```

```text
Which user created it?
```

```text
Which build references it?
```

In current self-hosted Artifactory architecture, JFrog recommends PostgreSQL, and its documentation describes a default model where metadata is stored in the database while artifacts are stored in a filestore.

---

# 22. Database Does Not Normally Mean "All Artifact Files"

This distinction matters.

The default architecture is conceptually:

```text
Database
↓
Metadata and Relationships

Filestore
↓
Artifact Binary Content
```

JFrog documentation describes this as the default and recommended model for self-hosted deployments.

Therefore:

```text
Database
≠
Filestore
```

They serve different roles.

---

# 23. What Is a Filestore?

The filestore is where Artifactory stores binary artifact content.

Conceptually:

```text
Artifactory
├── Database
│   └── Metadata
│
└── Filestore
    └── Binary Content
```

Depending on deployment architecture, storage may ultimately be backed by different storage technologies.

For beginners, the important distinction is:

```text
Database
↓
Describes and maps

Filestore
↓
Stores binary content
```

---

# 24. Checksum-Based Storage

This is one of the most interesting parts of Artifactory architecture.

Instead of treating every repository path as an independent physical copy of a file, Artifactory can identify stored content by checksum.

JFrog documents that Artifactory stores binaries using checksum-based storage and uses database mappings to connect repository paths to stored binary content.

Conceptually:

```text
Upload Artifact
↓
Calculate Checksum
↓
Store Binary by Checksum
↓
Create Database Mapping
↓
Expose Artifact at Repository Path
```

---

# 25. What Is a Checksum Again?

A checksum is a value calculated from file contents.

Suppose:

```text
payment-api-1.0.0.jar
```

produces:

```text
SHA-256:
abc123...
```

Now Artifactory has a content identity.

If another upload contains exactly the same bytes, it should produce the same cryptographic checksum.

Conceptually:

```text
File Content
↓
Hash Function
↓
Checksum
```

Artifactory stores checksum information including SHA-256 for artifact workflows and integrity checks.

---

# 26. Why Checksum-Based Storage Is Useful

Suppose the exact same file appears at two logical paths.

Path 1:

```text
dev-local/payment-api-1.0.0.jar
```

Path 2:

```text
release-local/payment-api-1.0.0.jar
```

A naive storage system could store:

```text
Copy 1
+
Copy 2
```

Artifactory's checksum-based model can instead maintain logical mappings that reference the same underlying binary when the content is identical.

Conceptually:

```text
Path A ───────┐
              ↓
         Same Checksum
              ↓
         One Binary
              ↑
Path B ───────┘
```

JFrog specifically documents that identical content can be stored once while multiple database mappings point to it.

This is called deduplication.

---

# 27. Deduplication

Deduplication means avoiding unnecessary duplicate storage of identical binary content.

Suppose:

```text
File A
Checksum:
XYZ
```

and:

```text
File B
Checksum:
XYZ
```

If the actual content is identical, Artifactory can avoid physically storing the same binary twice.

Conceptually:

```text
Repository Path 1
        \
         → Checksum XYZ → Stored Binary
        /
Repository Path 2
```

This saves storage and supports efficient repository operations.

---

# 28. Copy and Move Operations

Checksum-based storage also changes how you should think about copies and moves.

When Artifactory copies or moves an artifact logically, it may be able to update database references rather than physically copying large binaries byte-for-byte.

JFrog documents copy, move, and delete operations as being heavily database-driven in its checksum-based storage implementation.

That means:

```text
Logical Copy
↓
Database Mapping
```

rather than always:

```text
Read 5 GB File
↓
Copy 5 GB
↓
Write 5 GB Again
```

---

# 29. Checksum Deployment

Artifactory can also use checksum information during deployment.

Suppose you attempt to upload a binary that Artifactory already stores.

Artifactory can identify that the content already exists by checksum and avoid transferring the full binary again in supported workflows. JFrog exposes a checksum deployment API specifically for this purpose.

Conceptually:

```text
Client
↓
"I want to deploy content with checksum XYZ"
↓
Artifactory
↓
"Do I already have XYZ?"
      ↓
    Yes
      ↓
Create Logical Mapping
```

This can make artifact operations more efficient.

# 33. Authentication vs Authorization

These two concepts are different.

Authentication asks:

```text
Who are you?
```

Authorization asks:

```text
What are you allowed to do?
```

Example:

```text
User: ann
↓
Authentication
↓
Identity Verified
↓
Authorization
↓
Can read repository?
Can upload?
Can delete?
```

You can successfully authenticate but still receive:

```text
Permission denied
```

because authentication and authorization are different steps.

# 35. Permissions

Permissions determine what users or groups can do.

Examples include:

* Read artifacts
* Deploy artifacts
* Manage resources
* Delete artifacts
* Access builds

JFrog's current permission model supports fine-grained control across repositories, builds, release bundles, destinations, and related resources.

A simple flow is:

```text
Request
↓
Authenticate Identity
↓
Check Permissions
↓
Allowed?
    ↓
  Yes → Continue
    ↓
   No → Reject
```

---

# 36. Example Permission Scenario

Imagine:

```text
developer-group
```

should be able to:

```text
Read development artifacts
Upload development artifacts
```

but not:

```text
Delete production releases
```

You might conceptually configure:

```text
developers
↓

├── Read
└── Deploy

production-local
└── Read Only
```

Meanwhile:

```text
release-engineering
↓
production-local
├── Read
└── Deploy
```

This is least privilege.

Users receive only the access needed for their job.

# 44. Services Inside the JFrog Platform

Modern Artifactory is not simply one monolithic executable doing everything alone.

JFrog Platform deployments contain multiple services or microservices working together.

JFrog's current architecture documentation describes product nodes as running internal services alongside a Router service that handles API gateway and service discovery responsibilities.

A simplified architecture is:

```text
             JFrog Platform Node
                    |
        ----------------------------
        |           |              |
      Router      Access       Artifactory
        |
      Other Internal Services
```

You do not need to memorize every service yet.

But you should understand that the interface you see is backed by multiple cooperating components.

Think:


## Artifactory Service

## Access

## Frontend

Supports the unified web interface.

## Metadata Services

Support package and metadata-related processing.

## Other Platform Services

Support event handling, observability, topology, platform integration, and other functions.

The exact service set can vary by JFrog version and licensed platform configuration.

# 107. Suggested Answer

## Repository

```text
libs-release-local
```

## Artifact

```text
veriqta-orders-api-3.1.0.jar
```

## Repository Path

The logical location used to address the artifact.

## Metadata

Information such as:

```text
Repository
Path
Size
Checksum
Created date
Creator
Properties
Build association
```

## Filestore

Stores the binary content.

## Database

Stores mappings and metadata connecting the logical repository representation to underlying stored content.

## Checksum

Identifies artifact contents and supports integrity, deduplication, and efficient storage operations.

## Upload Checks

Potentially include:

```text
Authentication
Authorization
Repository validation
Path handling
Checksum processing
```

## Client

Could be:

```text
JFrog CLI
Maven
REST API
CI/CD integration
```

## Download

Artifactory resolves the repository path, checks permissions, finds the corresponding binary, and returns it.

# 109. Knowledge Check Answers

### Answer 1

The JFrog Platform is a collection of JFrog services used across software development, artifact management, security, and software delivery.

### Answer 2

Artifactory manages software packages and artifacts.

### Answer 3

No.

The web UI is one interface used to interact with the platform.

### Answer 4

JFrog CLI is a command-line client for interacting with JFrog services such as Artifactory.

### Answer 5

A REST API allows applications and automation to communicate programmatically with Artifactory over HTTP.

### Answer 6

A repository key is the unique identifier used for a repository.

### Answer 7

An artifact path is the logical location of an artifact within a repository.

### Answer 8

Metadata is information describing an artifact, package, build, or other object.

### Answer 9

Metadata describes the artifact.

The binary is the actual artifact content.

### Answer 10

The database stores metadata, mappings, relationships, and platform state required to manage repository objects.

### Answer 11

The filestore stores artifact binary content.

### Answer 12

Artifactory identifies and stores binaries based on their checksums and maps repository paths to that content.

### Answer 13

Deduplication means identical binary content does not need to be physically stored repeatedly.

### Answer 14

Authentication verifies identity.

### Answer 15

Authorization determines what the authenticated identity can do.

### Answer 16

A group is a collection of users used to simplify access management.

### Answer 17

A project is an organizational boundary grouping resources, members, roles, repositories, and builds.

### Answer 18

Build Info is structured metadata describing a build and its relationship to dependencies, artifacts, environment information, and source information.

### Answer 19

Router directs traffic to appropriate internal services and participates in service discovery.

### Answer 20

Ports identify network service endpoints on a machine.

### Answer 21

JFrog currently documents:

```text
8081
8082
```

as default external Artifactory ports in self-hosted Artifactory 7.x architecture.

### Answer 22

A client authenticates, receives authorization, identifies a repository path, transfers or identifies the binary, Artifactory handles checksum and storage processing, records mappings and metadata, and returns a response.

### Answer 23

Artifactory authenticates and authorizes the client, resolves the repository path, locates the corresponding stored binary, and returns it.

### Answer 24

If a remote repository is configured, Artifactory can contact the external package source, retrieve the dependency, cache it, and return it to the client.

### Answer 25

With self-hosted Artifactory, your organization operates the infrastructure.

With JFrog Cloud, JFrog operates the underlying service infrastructure.
