
# PART 1: HELM FOUNDATIONS AND KUBERNETES APPLICATION PACKAGING

## Goal

Understand **why Helm exists, what problem it solves, how it fits into Kubernetes, and what actually happens when Helm deploys an application**.

By the end of this part, you should not think of Helm as a mysterious command that installs software.

You should be able to explain this entire path:

```text
Application
↓
Kubernetes Resources
↓
Helm Chart
+
Configuration Values
↓
Helm Template Rendering
↓
Kubernetes Manifests
↓
Kubernetes API
↓
Kubernetes Resources
↓
Running Application
```

You will also install Helm, inspect a real chart, render a chart without deploying it, install your first Helm release, inspect what Helm created, and safely remove it.

---

# 1. Start With the Problem, Not the Tool

Before learning Helm commands, understand the problem Helm was designed to solve.

Imagine you have built a web application.

The application runs inside a container image:

```text
registry.example.com/myapp:1.0.0
```

Running that application properly in Kubernetes may require much more than one container.

You might need:

```text
Namespace
Deployment
Service
ConfigMap
Secret
Ingress
HorizontalPodAutoscaler
PodDisruptionBudget
ServiceAccount
NetworkPolicy
PersistentVolumeClaim
```

Your repository could therefore contain:

```text
kubernetes/
├── namespace.yaml
├── deployment.yaml
├── service.yaml
├── configmap.yaml
├── secret.yaml
├── ingress.yaml
├── hpa.yaml
└── pdb.yaml
```

Each file describes part of the application's desired Kubernetes state.

You might deploy them with:

```bash
kubectl apply -f kubernetes/
```

There is nothing inherently wrong with this.

Raw Kubernetes manifests are perfectly valid.

Helm does not exist because Kubernetes YAML is invalid.

Helm exists because managing increasingly large, configurable, versioned collections of Kubernetes manifests becomes difficult.

---

# 2. What Is a Kubernetes Manifest?

A Kubernetes manifest is normally a YAML or JSON document describing a Kubernetes API object.

For example:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: registry.example.com/web:1.0.0
          ports:
            - containerPort: 8080
```

This tells Kubernetes:

```text
I want a Deployment
named web
with 3 replicas
using this container image
and exposing container port 8080.
```

Kubernetes receives this desired state through its API.

Controllers then work toward making reality match that desired state.

Helm does not replace this Kubernetes model.

Helm ultimately produces Kubernetes manifests that Kubernetes understands.

That distinction is fundamental.

---

# 3. Kubernetes Can Already Deploy YAML, So Why Helm?

Suppose your application requires eight manifests.

For one environment, this may be manageable.

Now your organization introduces:

```text
Development
Staging
Production
```

Development requires:

```yaml
replicas: 1
```

Staging requires:

```yaml
replicas: 2
```

Production requires:

```yaml
replicas: 6
```

Production may also need different:

```text
CPU requests
Memory requests
CPU limits
Memory limits
Ingress hostname
Autoscaling settings
Storage sizes
Feature configuration
External service endpoints
```

You now have a configuration-management problem.

---

# 4. The First Temptation: Duplicate Everything

A beginner may create:

```text
kubernetes/
├── dev/
│   ├── deployment.yaml
│   ├── service.yaml
│   └── ingress.yaml
│
├── staging/
│   ├── deployment.yaml
│   ├── service.yaml
│   └── ingress.yaml
│
└── production/
    ├── deployment.yaml
    ├── service.yaml
    └── ingress.yaml
```

This works.

But notice what has happened.

The same application definition now exists three times.

Perhaps 90 percent of each Deployment is identical.

Only a few values differ.

That creates duplication.

---

# 5. The Repetition Problem

Consider these three environments.

Development:

```yaml
spec:
  replicas: 1
```

Staging:

```yaml
spec:
  replicas: 2
```

Production:

```yaml
spec:
  replicas: 6
```

Everything else might be identical.

If you maintain three complete Deployment manifests, every structural change must potentially be repeated three times.

Suppose you add:

```yaml
securityContext:
  runAsNonRoot: true
```

You now need to remember to update:

```text
dev/deployment.yaml
staging/deployment.yaml
production/deployment.yaml
```

Miss one and your environments drift.

Helm gives you another approach.

You can define the structure once and parameterize the differences.

Conceptually:

```yaml
spec:
  replicas: {{ .Values.replicaCount }}
```

Then:

Development:

```yaml
replicaCount: 1
```

Staging:

```yaml
replicaCount: 2
```

Production:

```yaml
replicaCount: 6
```

The structure is reusable.

The configuration changes.

---

# 6. Environment Differences

Real environments rarely differ only by replica count.

They may differ in:

```text
Replica count
Container image
Ingress hostname
TLS configuration
CPU requests
Memory requests
CPU limits
Memory limits
Autoscaling
Storage
Feature flags
Logging level
External API endpoints
Monitoring configuration
```

For example:

Development:

```text
replicas = 1
hostname = dev.example.com
autoscaling = disabled
logging = debug
```

Production:

```text
replicas = 6
hostname = app.example.com
autoscaling = enabled
logging = info
```

Helm allows a common chart to accept different configuration values.

---

# 7. Image Version Differences

Applications change over time.

Today:

```text
myapp:1.0.0
```

Next week:

```text
myapp:1.1.0
```

Later:

```text
myapp:1.2.0
```

With raw manifests, the image reference might be embedded directly:

```yaml
image: registry.example.com/myapp:1.0.0
```

A Helm chart can make image configuration explicit:

```yaml
image:
  repository: registry.example.com/myapp
  tag: "1.0.0"
```

The template can consume those values.

Later parts will also cover why production systems increasingly care about immutable image identity, including digest-based references.

---

# 8. Replica Differences

A development environment may need:

```text
1 Pod
```

Production may need:

```text
6 Pods
```

Instead of maintaining separate Deployment structures, Helm can expose:

```yaml
replicaCount: 6
```

as configuration.

---

# 9. Resource Differences

Development might use:

```yaml
resources:
  requests:
    cpu: 100m
    memory: 128Mi
```

Production might use:

```yaml
resources:
  requests:
    cpu: 500m
    memory: 512Mi
  limits:
    memory: 1Gi
```

Again:

```text
Same application structure
+
Different environment configuration
```

This is one of Helm's major strengths.

---

# 10. Configuration Differences

Imagine your application reads:

```text
LOG_LEVEL
API_ENDPOINT
FEATURE_X_ENABLED
```

Development might require:

```text
LOG_LEVEL=debug
```

Production:

```text
LOG_LEVEL=info
```

You do not necessarily want two completely different application packages.

You want:

```text
One reusable application definition
+
Environment-specific configuration
```

Helm is designed around this idea.

---

# 11. Large Manifest Collections

A production application can require many Kubernetes resources.

For example:

```text
Namespace
Deployment
Service
ConfigMap
ServiceAccount
Role
RoleBinding
Ingress
NetworkPolicy
HPA
PDB
ServiceMonitor
PersistentVolumeClaim
```

Now imagine:

```text
20 applications
×
10 Kubernetes resources
=
approximately 200 resource definitions
```

Then add:

```text
development
staging
production
```

The operational problem grows quickly.

Packaging related Kubernetes configuration into application-level units becomes useful.

That application-level package is what Helm calls a **chart**.

---

# 12. Application Distribution Problem

Suppose your team creates an application another team needs to deploy.

Without packaging, you might tell them:

```text
Download these 14 YAML files.

Edit deployment.yaml.

Change the image.

Edit ingress.yaml.

Change the hostname.

Edit resources.yaml.

Make sure the Service selector still matches.

Apply the files in Kubernetes.
```

That is not an ideal distribution model.

With Helm, you can provide a chart and expose intended configuration through values.

Conceptually:

```bash
helm install payments ./payments-chart \
  --set replicaCount=3
```

The user configures the application without manually rewriting every Kubernetes manifest.

---

# 13. Reusable Deployment Patterns

Suppose your organization has 40 microservices.

Every service should follow organizational standards such as:

```text
Standard labels
Resource requests
Resource limits
Health probes
Security contexts
ServiceAccounts
PodDisruptionBudgets
NetworkPolicies
Observability metadata
```

Reusable Helm chart patterns can help standardize how applications are packaged.

This does not automatically make every chart good.

A badly designed Helm chart can create just as much complexity as badly managed YAML.

But Helm gives teams tools for creating reusable packaging conventions.

---

# 14. Release Management Problem

Imagine deploying version 1 of an application.

Later you deploy version 2.

Then version 3 fails.

Operationally, you want to know:

```text
What is installed?

What chart was used?

What configuration was used?

What revision is this?

What changed?

Can we move back to a previous release revision?
```

Helm includes release-management functionality for installed charts.

This is another reason Helm is more than a templating engine.

---

# 15. So What Exactly Is Helm?

A useful beginner mental model is:

```text
Helm
=
Kubernetes Package Manager
+
Templating Engine
+
Release Manager
```

Each part matters.

---

# 16. Helm as a Kubernetes Package Manager

Operating systems have package-management ecosystems.

For example:

```text
apt
dnf
Homebrew
```

A package manager helps distribute and manage software packages.

Helm provides similar packaging concepts for Kubernetes applications.

Helm packages are called:

```text
Charts
```

A chart may describe everything needed to deploy an application or platform component into Kubernetes.

---

# 17. Helm as a Templating Engine

Helm charts commonly contain Kubernetes manifests with template expressions.

Instead of:

```yaml
replicas: 3
```

you might have:

```yaml
replicas: {{ .Values.replicaCount }}
```

Instead of:

```yaml
image: nginx:1.27
```

you might conceptually use:

```yaml
image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
```

Helm combines:

```text
Templates
+
Values
```

to produce ordinary Kubernetes manifests.

---

# 18. Helm as a Release Manager

When Helm installs a chart, it creates a **release**.

Helm tracks release information and provides commands for operations such as:

```text
Install
Inspect
Upgrade
View history
Rollback
Uninstall
```

Therefore:

```text
Chart
≠
Release
```

A chart is the package.

A release is an installed instance of that package.

Memorize this:

Suppose your chart contains:

```text

├── deployment.yaml
├── service.yaml
└── ingress.yaml
```

And your values contain:

```yaml

  repository: example/myapp
```

Helm combines them:

```text

```

and might render:

```text

```

---

# 21. Helm Does Not Run Your Containers

This distinction matters.

Helm does not:

```text
schedule Pods
run containers
manage kubelet
implement Services
perform container networking
provide persistent storage
replace Kubernetes controllers
```

Kubernetes performs those functions.

Helm helps define and manage the Kubernetes resources representing the application.

---

# 22. Helm vs Kubernetes

Use this simple explanation:

```text
Kubernetes
runs and manages workloads.

Helm
packages and manages Kubernetes application configuration.
```

Another way:

```text
Helm
↓
creates/manages Kubernetes resources
↓
Kubernetes
↓
reconciles those resources
↓
Containers run
```

---

# 23. Kubernetes Still Owns Reconciliation

Suppose Helm creates:

```yaml
kind: Deployment
spec:
  replicas: 3
```

Helm does not continuously ensure three Pods exist.

The Kubernetes Deployment controller does that.

The responsibility boundary is:

```text
Helm
creates or updates desired Kubernetes objects

Kubernetes controllers
continuously reconcile those objects
```

This distinction becomes especially important when we later discuss GitOps.

---

# 24. Helm Does Not Replace kubectl

You will continue using kubectl.

Typical workflow:

```text
Helm
↓
Install application

kubectl
↓
Inspect resources
↓
Describe failures
↓
Read events
↓
Read logs
```

For example:

```bash
helm list
```

shows Helm releases.

But:

```bash
kubectl get pods
```

shows Pods.

Both tools are useful for different layers.

# 25. Core Terminology

Before continuing, learn these terms:

```text
Chart
Release
Values
Templates
Repository
Dependency

```

We will now separate them carefully.

---

# 26. Chart

A **chart** is a Helm package.

It contains the information Helm needs to generate Kubernetes resources for an application, tool, or service.

A chart directory may eventually look like:

```text
my-chart/
├── Chart.yaml
├── values.yaml
├── charts/
└── templates/
```

Think:

```text
Chart
=
Reusable Kubernetes application package
```

---

# 27. A Chart Is Not a Running Application

This distinction is critical.

```text
Chart
=
Package

Release
=
Installed instance
```

A chart sitting in Git or an OCI registry is not running anything.

It becomes operational when Helm uses it to create a release in a Kubernetes cluster.

---

# 28. Release

A **release** is an installed instance of a chart.

Suppose you have:

```text
postgres-chart
```

You could install it as:

```text
orders-db
```

and again as:

```text
analytics-db
```

Same chart.

Different releases.

Conceptually:

```text
postgres chart
├── orders-db release
└── analytics-db release
```

---

# 29. Release Names Matter

Helm identifies installations using release names.

For example:

```bash
helm install my-web ./my-chart
```

Here:

```text
my-web
```

is the release name.

And:

```text
./my-chart
```

is the chart source.

Keep these concepts separate.

---

# 30. Values

**Values** are configuration inputs supplied to a chart.

Example:

```yaml
replicaCount: 3

image:
  repository: example/web
  tag: "1.0.0"

service:
  type: ClusterIP
  port: 80
```

Values allow the same chart to produce different rendered configuration.

---

# 31. Default Values

Charts commonly contain:

```text
values.yaml
```

This file provides default configuration.

For example:

```yaml
replicaCount: 1
```

A user can later override that value.

This gives us:

```text
Chart Defaults
+
User Configuration
↓
Final Values
```

The exact precedence rules will be taught in Part 4.

---

# 32. Templates

Templates are files that Helm processes to generate Kubernetes manifests.

For example:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}
spec:
  replicas: {{ .Values.replicaCount }}
```

Helm evaluates the template.

If:

```text
Release.Name = web
replicaCount = 3
```

the result might be:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
```

Kubernetes receives the rendered result.

It does not receive the Helm template expressions as Kubernetes configuration.

---

# 33. Template vs Rendered Manifest

Do not confuse them.

Template:

```yaml
replicas: {{ .Values.replicaCount }}
```

Rendered manifest:

```yaml
replicas: 3
```

Think:

```text
Template
+
Input
=
Output
```

In Helm:

```text
Helm Template
+
Values
=
Rendered Kubernetes Manifest
```

```text
Repository / Registry
↓

↓

↓

```

A chart can depend on another chart.

For example:

```text

↓

```

They also introduce:

# 36. Chart Version

A Helm chart has its own version.

Example:

```yaml
version: 2.4.0
```

This describes the version of the **chart package**.

You might modify:

```text
templates
values
labels
configuration structure
dependencies
```

and release a new chart version.

---

# 37. Application Version

A chart can also contain an application version.

Example:

```yaml
appVersion: "5.2.1"
```

This communicates the version of the application represented by the chart.

Important:

```text
Chart Version
≠
Application Version
```

They represent different things.

The chart version participates in chart packaging/versioning.

`appVersion` is informational metadata and does not control chart version calculations.

---

# 38. Example of Chart Version vs Application Version

Suppose:

```yaml
version: 3.1.0
appVersion: "8.4.2"
```

Interpret this as:

```text
Helm chart package version:
3.1.0

Application version described by the chart:
8.4.2
```

You could improve the chart without changing the underlying application.

For example:

```text
Add NetworkPolicy
Improve labels
Fix templates
Improve resource defaults
```

The chart version changes even if the application version does not.

---

# 39. Revision

A **revision** represents a release's history as Helm operations change it.

Conceptually:

```text
Release: payments

Revision 1
↓
Initial installation

Revision 2
↓
Upgrade

Revision 3
↓
Another upgrade
```

Helm can expose this history.

For example:

```bash
helm history payments
```

Revision history is what makes commands such as rollback meaningful.

---

# 40. Chart, Version, Release, Revision

Memorize the distinction:

```text
Chart
=
package

Chart Version
=
version of the package

Application Version
=
version of the application represented by the chart

Release
=
installed instance of the chart

Revision
=
versioned point in that release's Helm history
```

This distinction prevents enormous confusion later.

---

# 41. A Complete Example

Suppose you have:

```text
Chart:
payments

Chart version:
2.3.0

Application version:
5.7.1

Release:
payments-production

Revision:
4
```

This means:

```text
payments
is the package

2.3.0
is the chart package version

5.7.1
is the application's stated version

payments-production
is the installed release

4
is the current Helm release-history revision
```

# 42. Helm Architecture

Now understand how modern Helm communicates with Kubernetes.

The simplified architecture is:

```text
User
↓

↓
Helm Client / Library Logic
↓
Kubernetes API Server
↓

```

# 43. Helm Uses Kubernetes Access

Helm needs access to the Kubernetes cluster.

Conceptually:

```text
Helm
↓
Kubernetes client configuration
↓
Credentials / Identity
↓
Kubernetes API
↓
Authentication
↓
Authorization
↓
Allowed Kubernetes operations
```

Helm does not magically bypass Kubernetes security.

---

# 44. Kubernetes RBAC Still Matters

Suppose your Kubernetes identity cannot create Deployments.

Running:

```bash
helm install ...
```

does not grant you that ability.

If the chart attempts to create a Deployment, Kubernetes authorization can reject it.

Think:

```text
Helm requests operation
↓
Kubernetes API
↓
Authorization
↓
Allowed?
├── Yes → continue
└── No → Forbidden
```

This is important for production security.

---

# 45. Modern Helm Does Not Require Tiller

If you encounter old tutorials, you may see:

```text
Tiller
```

This is historical architecture.

Helm 2 used an in-cluster server component called Tiller.

Simplified:

```text
Helm 2 Client
↓
Tiller
↓
Kubernetes API
```

Modern Helm removed this architecture.

---

# 46. Why Tiller Matters Historically

Tiller was responsible for operations including release management and communication with Kubernetes.

But it also complicated security.

A badly or broadly privileged Tiller could effectively become a privilege-escalation path.

Modern Helm removed Tiller and relies on the Kubernetes security model associated with the user or automation invoking Helm.

# 48. Helm Release Information

Helm needs information about installed releases so it can answer questions such as:

```text
Which releases exist?

What revision is installed?

What values were used?

What manifest was associated with the release?

What happened during upgrades?
```

Modern Helm stores release information in the cluster, with Kubernetes Secrets being the normal storage mechanism.

This means Helm does not require a separate external database just to maintain standard release information.

# 50. Helm Rendering

One of Helm's most important capabilities is rendering.

Imagine:

```text
deployment.yaml template
+
service.yaml template
+
values.yaml
```

Helm processes the templates and creates ordinary Kubernetes YAML.

This can happen without installation.

The important command is:

```bash
helm template
```

This makes Helm much easier to understand.

You can inspect what Helm intends to produce before it touches the cluster.

Whenever Helm feels confusing, reduce the problem to:

```text
What chart am I using?

What values are entering it?

What templates are being processed?

What YAML is being rendered?

```

```text

↓

↓
Template
↓
Rendered Manifest
↓
Kubernetes API
↓
Resource
↓

↓

↓
```

This is different from manually running:

```bash
helm upgrade
```

from your laptop.

---

# 60. When Helm Helps

Helm becomes especially useful when you have:

```text
Many related Kubernetes resources

Repeated application patterns

Multiple environments

Configurable deployments

Reusable applications

Versioned application packages

Third-party Kubernetes software

Release lifecycle requirements

CI/CD integration

GitOps integration
```

---

# 61. When Helm May Be Too Much

Helm is not mandatory for every Kubernetes deployment.

Suppose your entire application is:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: hello
spec:
  containers:
    - name: hello
      image: example/hello:1.0.0
```

If there is:

```text
one manifest
one environment
almost no configuration
no packaging requirement
no reuse
```

turning it into a sophisticated Helm chart may create more complexity than value.

---

# 62. Complexity Has a Cost

Helm introduces concepts such as:

```text
Go templates
Values
Scope
Functions
Pipelines
Conditionals
Loops
Helpers
Dependencies
Release state
Chart versions
```

Those are useful when the problem justifies them.

They are overhead when the problem does not.

A good engineer does not ask:

```text
Can I use Helm?
```

They ask:

```text
Does Helm solve a real packaging or lifecycle problem here?
```

---

# 63. Raw YAML Is Not "Bad"

This is important.

Do not learn:

```text
Raw YAML = beginner
Helm = professional
```

That is false.

Raw manifests can be appropriate and production-grade.

Helm is a tool for packaging, parameterization, distribution, and release management.

Choose it when those capabilities solve your problem.

---


```text

↓
```

Helm introduces a generation and release-management layer.

Raw YAML can provide:

What you see is close to what Kubernetes receives.

# 68. Helm vs Kustomize

You will often hear Helm compared with Kustomize.

They overlap in one broad goal:

```text
Managing Kubernetes configuration
```

But they approach the problem differently.

---

# 69. Kustomize Mental Model

A simplified Kustomize mental model is:

```text
Base Kubernetes YAML
+
Overlays / Transformations
↓
Final Kubernetes YAML
```

Kustomize emphasizes customization of Kubernetes resources using bases, overlays, patches, and transformations.

---

# 70. Helm Mental Model

Helm is more naturally understood as:

```text
Chart
+
Values
+
Templates
↓
Rendered Kubernetes YAML
+
Release Lifecycle
```

Helm also provides packaging and release-management concepts beyond pure manifest customization.

---

# 71. Helm vs Kustomize Is Not a Religious War

Do not learn:

```text
Helm is always better
```

or:

```text
Kustomize is always better
```

Different teams have different requirements.

Some use:

```text
Helm only
```

Some:

```text
Kustomize only
```

Some:

```text
Helm + Kustomize
```

Some use GitOps tooling that can work with either.

The correct question is:

```text
What configuration model, packaging model,
release model, and operational workflow
does this system require?
```

# 134. SECURITY: VALUES ARE NOT AUTOMATICALLY SAFE

# 136. SECURITY: `--set` CAN LEAK DATA

# 137. SECURITY: CHARTS CAN REQUEST POWERFUL RESOURCES

# 138. SECURITY: HELM FOLLOWS YOUR KUBERNETES IDENTITY

Modern Helm does not need an all-powerful Tiller server.

Its Kubernetes operations are evaluated using Kubernetes access available to the caller.

Therefore the correct production principle is:

```text
Least privilege
```

not:

```text

because Helm needs it.
```

# 139. RELEASE STATE IS ALSO SENSITIVE

Helm release information may include rendered configuration and values relevant to the release.

# 154. KNOWLEDGE CHECK 1

What problem does Helm primarily help solve?

Answer:

Helm helps package, configure, distribute, and manage the release lifecycle of collections of Kubernetes resources.

---

# 155. KNOWLEDGE CHECK 2

Does Helm replace Kubernetes?

Answer:

No.

Helm creates and manages Kubernetes application configuration.

Kubernetes runs and reconciles the workloads.

---

# 156. KNOWLEDGE CHECK 3

What is a chart?

Answer:

A reusable Helm package containing metadata, default configuration, templates, and potentially dependencies needed to describe Kubernetes application resources.

---

# 157. KNOWLEDGE CHECK 4

What is a release?

Answer:

An installed instance of a chart managed by Helm.

---

# 158. KNOWLEDGE CHECK 5

Can one chart create multiple releases?

Answer:

Yes.

The same chart can be installed multiple times using different release identities, provided the resulting Kubernetes resources can coexist.

---

# 159. KNOWLEDGE CHECK 6

What are values?

Answer:

Configuration inputs used by a chart during template rendering.

---

# 160. KNOWLEDGE CHECK 7

What are templates?

Answer:

Files Helm processes using chart context and values to generate Kubernetes manifests.

---

# 161. KNOWLEDGE CHECK 8

What does `helm template` do?

Answer:

It renders a chart into Kubernetes manifests without installing the release into the cluster.

---

# 162. KNOWLEDGE CHECK 9

What is the difference between chart version and application version?

Answer:

The chart version identifies the version of the Helm package.

The application version identifies or describes the version of the application represented by the chart.

They are separate concepts.

---

# 163. KNOWLEDGE CHECK 10

What is a release revision?

Answer:

A numbered point in the Helm-managed history of a release created as release-changing operations occur.

---

# 164. KNOWLEDGE CHECK 11

Does modern Helm require Tiller?

Answer:

No.

Tiller belonged to Helm 2's client/server architecture and was removed from modern Helm architecture.

---

# 165. KNOWLEDGE CHECK 12

Where does modern Helm send Kubernetes operations?

Answer:

To the Kubernetes API using Kubernetes client access and the caller's relevant cluster identity and permissions.

---

# 166. KNOWLEDGE CHECK 13

Does `helm install` bypass Kubernetes RBAC?

Answer:

No.

Kubernetes authentication and authorization still apply.

---

# 167. KNOWLEDGE CHECK 14

Does successful rendering prove the application will run?

Answer:

No.

Rendering proves Helm could generate output.

Kubernetes validation, scheduling, image retrieval, container startup, probes, dependencies, and application behavior can still fail.

---

# 168. KNOWLEDGE CHECK 15

Does successful installation prove the application is healthy?

Answer:

No.

You must verify the resulting Kubernetes resources and application health.

---

# 169. KNOWLEDGE CHECK 16

Why inspect a chart before installing it?

Answer:

Because the chart can create resources affecting permissions, networking, storage, security, workloads, cluster scope, and application behavior.

---

# 170. KNOWLEDGE CHECK 17

What is the basic difference between Helm and Kustomize?

Answer:

A simplified distinction is:

```text
Helm
=
chart packaging
+
templating
+
values
+
release lifecycle

Kustomize
=
base Kubernetes resources
+
overlays/patches/transformations
```

Their capabilities and workflows can overlap, and either can be appropriate depending on the system.

---

# 171. KNOWLEDGE CHECK 18

When might Helm be unnecessary?

Answer:

When the deployment is extremely small, has little configuration variation, requires no packaging or reuse, and Helm's abstraction would cost more than it provides.

---

# 172. KNOWLEDGE CHECK 19

Should secrets simply be stored as plaintext values in Git?

Answer:

No.

A Helm values file is not automatically a secret-management system.

---

# 173. KNOWLEDGE CHECK 20

What should you inspect when Helm behaves unexpectedly?

Answer:

Start with:

```text
Chart
Values
Templates
Rendered YAML
Release information
Kubernetes resources
Events
Logs
Application state
```

and identify the first layer where actual state differs from expected state.
