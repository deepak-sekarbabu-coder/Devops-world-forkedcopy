# 1. Start With the Problem

You already understand containers.

Suppose you build:

```text
veriqta-web:1.0
```

and push it to ECR.

Now imagine your environment contains:

```text
20 applications
100 containers
Multiple servers
Multiple Availability Zones
Multiple development teams
Frequent deployments
Changing traffic
Failed containers
Failed servers
```

Managing everything manually becomes difficult.

You need a system that can answer:

```text
Where should each container run?

How many copies should exist?

What happens if one crashes?

What happens if a server fails?

How do applications find one another?

How does traffic reach them?

How do we deploy new versions?

How do we scale?

How do we manage configuration?

How do we manage storage?

How do we control access?
```

Kubernetes exists to solve many of these orchestration problems.

---

# 2. Kubernetes Refresher From Zero

Kubernetes is an open-source container orchestration system.

You will often see it abbreviated:

```text
K8s
```

The `8` represents the eight letters between:

```text
K
```

and:

```text
s
```

in Kubernetes.

Kubernetes manages containerized workloads across a collection of compute resources.

Instead of manually saying:

```text
Start this Docker container on Server 3.
```

you describe what you want.

For example:

```text
Run three copies of my web application.
```

Kubernetes works to maintain that desired state.

---

# 3. Kubernetes Is Not Docker

Docker and Kubernetes solve different problems.

Docker helps you:

```text
Build image
    |
    v
Run container
```

Kubernetes helps you:

```text
Run many containerized workloads
        |
        +-- Schedule them
        +-- Replace failures
        +-- Scale them
        +-- Network them
        +-- Expose them
        +-- Deploy new versions
```

A simplified workflow is:

```text
Application Code
      |
      v
Dockerfile
      |
      v
Docker Build
      |
      v
Container Image
      |
      v
Container Registry
      |
      v
Kubernetes
      |
      v
Running Workloads
```

# 5. Why EKS Exists

You can build and operate Kubernetes yourself.

But Kubernetes clusters require important infrastructure.

At the center is the:

```text
Kubernetes Control Plane
```

The control plane coordinates the cluster.

Operating this infrastructure yourself requires work involving:

* Availability
* Security
* Kubernetes API availability
* Control-plane components
* Certificates
* Upgrades
* Patching
* Monitoring
* Failure recovery
* Integration with infrastructure

EKS reduces part of this operational burden.

AWS manages the EKS Kubernetes control plane.

You still remain responsible for many things above and inside the cluster.

# 7. Kubernetes Cluster Architecture

A Kubernetes cluster has two major sides:

```text
Kubernetes Cluster
      |
      +-- Control Plane
      |
      +-- Worker Compute
```

The control plane manages the cluster.

Worker compute runs application workloads.

# 8. What Is the Control Plane?

The control plane is the management layer of Kubernetes.

Conceptually:

```text
Developer
    |
    | kubectl
    v
Kubernetes API
    |
    v
Control Plane
    |
    v
Cluster State
    |
    v
Worker Resources
```

You tell Kubernetes what you want through its API.

The control plane works to make the cluster match that desired state.

---

# 9. Important Kubernetes Control-Plane Components

At a foundational level, know these names:

```text
kube-apiserver
etcd
kube-scheduler
kube-controller-manager
```

You do not need to become a Kubernetes control-plane administrator in this EKS introduction.

But you should understand what they represent.

---

# 10. kube-apiserver

The Kubernetes API server is the main interface to the Kubernetes control plane.

When you run:

```bash
kubectl get pods
```

`kubectl` communicates with the Kubernetes API.

Conceptually:

```text
kubectl
   |
   v
Kubernetes API Server
   |
   v
Cluster
```

Other Kubernetes components also interact through the API.

---

# 11. etcd

`etcd` is the distributed key-value store Kubernetes uses for important cluster state.

Conceptually, Kubernetes needs to remember information such as:

```text
What workloads should exist?
What objects exist?
What configuration defines the cluster's desired state?
```

`etcd` is critical to Kubernetes.

In EKS, AWS manages the control-plane infrastructure, including the managed control-plane data-store responsibilities.

As an EKS beginner, you generally do not manually log into an etcd server and administer it like a self-managed cluster.

---

# 12. kube-scheduler

The scheduler helps determine where Pods should run.

Suppose Kubernetes needs to run:

```text
Pod A
```

and has suitable worker capacity:

```text
Worker 1
Worker 2
Worker 3
```

The scheduler evaluates placement requirements and selects an appropriate worker.

The decision can consider factors such as:

* Available resources
* Scheduling constraints
* Affinity
* Taints and tolerations
* Topology
* Resource requests

Those advanced scheduling concepts belong in deeper Kubernetes study.

For now remember:

```text
Scheduler
=
Helps decide where Pods run
```

---

# 13. kube-controller-manager

Kubernetes controllers continually compare desired state with actual state.

Suppose a Deployment requires:

```text
3 Pods
```

but only:

```text
2 Pods
```

are running.

Controllers participate in the process that works to restore the desired state.

The concept should look familiar from ECS.

```text
Desired = 3
Actual = 2

Kubernetes:
Something is missing.
```

The system works toward:

```text
Desired = 3
Actual = 3
```

# 15. What Are Worker Nodes?

Your applications need compute resources.

Traditionally in Kubernetes, these machines are called:

```text
worker nodes
```

A worker node provides compute capacity where Kubernetes workloads can run.

On EKS, worker capacity can come from different models.

A common model is:

```text
Amazon EC2
```

through EKS managed node groups.

EKS can also use other compute approaches, including Fargate for supported Kubernetes workloads.

This part will focus primarily on managed EC2 node groups because understanding nodes is fundamental to Kubernetes.

---

# 16. Worker Node Mental Model

Suppose your cluster contains three workers:

```text
EKS Cluster
 |
 +-- Worker Node A
 |
 +-- Worker Node B
 |
 +-- Worker Node C
```

Kubernetes schedules application workloads across them.

For example:

```text
Worker A
 |
 +-- Pod 1
 +-- Pod 4

Worker B
 |
 +-- Pod 2

Worker C
 |
 +-- Pod 3
```

---

# 17. Nodes Are Not Pods

Do not confuse:

```text
Node
```

with:

```text
Pod
```

A node is compute capacity.

A Pod is a Kubernetes workload unit that runs on worker compute.

Think:

```text
EC2 Worker Node
      |
      +-- Pod
      +-- Pod
      +-- Pod
```

---

# 18. What Runs on a Worker Node?

A Kubernetes worker environment includes components required to participate in the cluster and run Pods.

Two important concepts are:

```text
kubelet
```

and:

```text
container runtime
```

The kubelet is the node-level Kubernetes agent.

It helps ensure that the Pods assigned to the node are running as specified.

The container runtime performs the lower-level work required to run containers.

Modern Kubernetes does not require Docker Engine as its Kubernetes runtime.

This distinction matters.

Managed node groups simplify parts of EC2 worker-node provisioning and lifecycle management.

# 20. What a Managed Node Group Helps With

Managed node groups help with operations such as:

* Provisioning EKS-compatible worker instances
* Joining nodes to the cluster
* Node lifecycle management
* Updates

You still need to make decisions about:

* Instance types
* Capacity

* Security
* Kubernetes version compatibility
* Workload requirements
* Cost

Managed does not eliminate architecture decisions.

# 21. What Is a Pod?

The Pod is one of the most important Kubernetes concepts.

A Pod is the smallest deployable unit Kubernetes manages.

A Pod can contain:

```text
One container
```

or:

```text
Multiple tightly coupled containers
```

For most beginner applications:

```text
Pod
 |
 v
One Application Container
```

is a good starting mental model.

---

# 22. Why Doesn't Kubernetes Just Say Container?

Kubernetes manages more than an isolated container.

The Pod provides an execution context around one or more containers.

Containers in the same Pod can share certain resources, including network context.

Conceptually:

```text
Pod
 |
 +-- Container A
 |
 +-- Container B
```

The containers belong to one tightly coupled workload unit.

---

# 23. One Pod Usually Does Not Mean One Application Forever

Suppose your web application needs three replicas.

You generally do not put three copies of the application inside one Pod.

Instead:

```text
Pod A
 |
 +-- App Container

Pod B
 |
 +-- App Container

Pod C
 |
 +-- App Container
```

Each Pod represents a separate replica.

---

# 24. Pods Are Disposable

This is fundamental.

Do not think:

```text
This Pod is my permanent server.
```

Think:

```text
This Pod is a replaceable workload instance.
```

A Pod can:

* Fail
* Be terminated
* Be replaced
* Move to another node through recreation
* Receive a different IP address
* Disappear during deployments

Applications should be designed accordingly.

---

# 25. Do Not Depend on Pod IP Addresses

Suppose:

```text
Pod A
IP = 10.0.10.25
```

Pod A dies.

A replacement appears:

```text
Pod B
IP = 10.0.11.47
```

If your architecture depends on:

```text
10.0.10.25
```

permanently representing the application, it breaks.

Kubernetes provides abstractions such as:

```text
Services
```

to provide stable access to groups of Pods.

---

# 26. What Is a Deployment?

A Deployment is a Kubernetes workload controller commonly used for stateless applications.

A Deployment can describe:

```text
Which container image should run?
How many replicas should exist?
How should Pods be updated?
Which Pods belong to this workload?
```

For example:

```text
Deployment: veriqta-web
Replicas: 3
Image: veriqta-web:1.0
```

Kubernetes works to maintain three Pods.

---

# 27. Deployment Desired State

You declare:

```text
replicas: 3
```

Actual:

```text
Pod A
Pod B
Pod C
```

Pod B fails.

Actual becomes temporarily:

```text
Pod A
Pod C
```

The Deployment's underlying controllers work toward restoring:

```text
Pod A
Pod C
Pod D
```

Again:

```text
Desired state
→ reconciliation
```

---

# 28. Deployment, ReplicaSet, and Pod

A more accurate relationship is:

```text
Deployment
    |
    v
ReplicaSet
    |
    +-- Pod
    +-- Pod
    +-- Pod
```

The Deployment manages rollout behavior.

The ReplicaSet maintains the required Pod replicas.

Beginners usually interact primarily with the Deployment rather than manually creating ReplicaSets.

---

# 29. Why Not Create Pods Manually?

You can create a Pod directly.

But suppose it fails.

A standalone Pod does not provide the same workload-management behavior as a Deployment.

For a normal stateless web application, prefer:

```text
Deployment
→ ReplicaSet
→ Pods
```

rather than manually managing individual Pods.

---

# 30. What Is a Kubernetes Service?

Pods are replaceable and their IP addresses can change.

Applications need a stable way to communicate with a group of Pods.

A Kubernetes Service provides a stable network abstraction for selected Pods.

Conceptually:

```text
Client
   |
   v
Kubernetes Service
   |
   +--------+--------+
   |        |        |
   v        v        v
 Pod A    Pod B    Pod C
```

The Service identifies appropriate Pods through labels and selectors.

---

# 31. Kubernetes Service vs AWS Service

The word:

```text
Service
```

can become confusing.

In Kubernetes:

```text
Service
```

is a Kubernetes networking object.

In AWS:

```text
AWS service
```

can mean products such as EC2, S3, or EKS.

Do not confuse the two.

---

# 32. Important Kubernetes Service Types

At beginner level, understand:

```text
ClusterIP
NodePort
LoadBalancer
```

There are additional service and traffic-management patterns, but these three establish the foundation.

---

# 33. ClusterIP

`ClusterIP` is the default Kubernetes Service type.

It provides access primarily within the cluster.

Example:

```text
Frontend Pod
     |
     v
backend-service
     |
     v
Backend Pods
```

The frontend does not need to know every backend Pod IP.

It can communicate with the Service.

---

# 34. NodePort

`NodePort` exposes a Service through a port on cluster nodes.

Conceptually:

```text
Client
 |
 v
NodeIP:NodePort
 |
 v
Service
 |
 v
Pods
```

NodePort is important to understand because other exposure mechanisms can build on Kubernetes service networking concepts.

It is not normally the preferred final public architecture for a production AWS web application.

---

# 35. LoadBalancer Service

A Service with:

```yaml
type: LoadBalancer
```

asks the cloud integration to provision or integrate with external load-balancing infrastructure.

On AWS, this can result in AWS load-balancer resources depending on the cluster configuration and controller/integration being used.

Conceptually:

```text
Internet
   |
   v
AWS Load Balancer
   |
   v
Kubernetes Service
   |
   v
Pods
```

# 36. Ingress Concept

For HTTP and HTTPS applications, Kubernetes also has the concept of:

```text
Ingress
```

Ingress describes HTTP/HTTPS routing rules into the cluster.

For example:

```text
app.example.com
→ frontend service

api.example.com
→ API service
```

or:

```text
example.com/app
→ application service

example.com/api
→ API service
```

On AWS, an AWS load-balancer controller can translate supported Kubernetes resources into AWS load-balancing infrastructure.

This is an introductory EKS article, so we will not turn Ingress into a full course here.

---

# 37. Labels and Selectors

Kubernetes relies heavily on labels.

Suppose Pods have:

```yaml
labels:
  app: veriqta-web
```

A Service can select:

```yaml
selector:
  app: veriqta-web
```

Conceptually:

```text
Service selector:
app=veriqta-web
       |
       v
Find Pods with:
app=veriqta-web
       |
       +-- Pod A
       +-- Pod B
       +-- Pod C
```

If labels and selectors do not match, the Service may have no useful backend endpoints.

This causes a very common beginner failure.

# 42. Installing kubectl

```bash

```


# 43. What Is kubeconfig?

`kubectl` needs configuration telling it:

```text
Which cluster?
Which API endpoint?
Which credentials/authentication mechanism?
Which context?
```

This configuration is commonly stored in:

```text
~/.kube/config
```

This is called:

```text
kubeconfig
```

---

# 44. Kubernetes Context

A kubeconfig can contain information for multiple clusters.

A:

```text
context
```

combines the cluster and identity information `kubectl` should use.

Check contexts:

```bash
kubectl config get-contexts
```

Check the active context:

```bash
kubectl config current-context
```

This matters enormously.

Running a command against the wrong cluster can have serious consequences.

---

# 45. Always Check Your Context

Before changing Kubernetes resources:

```bash
kubectl config current-context
```

Then ask:

```text
Is this development?

Staging?

Production?

Which AWS account?

Which Region?

Which cluster?
```

Treat context verification as a safety habit.

# 50. Kubernetes Networking on AWS

Kubernetes has its own networking model.

AWS must integrate that model with:

```text
VPCs
Subnets
Elastic Network Interfaces
IP addresses
Security Groups
Route tables
Load balancers
```

One important EKS component is:

```text
Amazon VPC CNI
```

CNI means:

```text
Container Network Interface
```

---

# 51. What Is a CNI?

Kubernetes needs a mechanism for configuring Pod networking.

A CNI plugin handles container network connectivity according to the CNI specification.

On EKS, the Amazon VPC CNI plugin integrates Pod networking with AWS VPC networking.

At a beginner level, remember:

```text
Kubernetes Pod Networking
        |
        v
Amazon VPC CNI
        |
        v
AWS VPC Networking
```

---

# 52. Pod IP Addresses on EKS

With standard Amazon VPC CNI networking, Pods can receive IP addresses associated with the VPC networking environment.

This creates powerful integration with AWS networking.

But it also means:

```text
VPC IP address capacity matters.
```

A subnet does not contain unlimited addresses.

Large EKS clusters can experience IP exhaustion if subnet sizing is poor.

---

# 53. Why Subnet Planning Matters

Suppose you create a very small subnet.

Then you add:

```text
EC2 nodes
Pods
Load balancer networking
Other resources
```

Eventually there may not be enough available IP addresses.

Symptoms can include Pods failing to obtain networking.

This means the VPC design you learned earlier is directly relevant to EKS.

Kubernetes does not eliminate network planning.

---

# 54. EKS Across Availability Zones

A production-style EKS architecture normally considers multiple Availability Zones.

For example:

```text
VPC
 |
 +-- AZ A
 |    |
 |    +-- Private Subnet A
 |         |
 |         +-- Worker Nodes / Pods
 |
 +-- AZ B
      |
      +-- Private Subnet B
           |
           +-- Worker Nodes / Pods
```

This reduces dependency on a single Availability Zone.

---

# 55. Public and Private Subnets

A common architecture may use:

```text
Public Subnets
→ Internet-facing load balancers
→ NAT Gateways where required
```

and:

```text
Private Subnets
→ Worker nodes
→ Application Pods
```

Conceptually:

```text
Internet
   |
   v
Internet Gateway
   |
   v
AWS Load Balancer
   |
   v
Private Kubernetes Workloads
```

Do not assume Kubernetes workloads require public IP addresses simply because users access the application from the internet.

---

# 56. Worker Nodes in Private Subnets

A production-style design commonly places worker nodes in private subnets.

They can still require outbound connectivity for activities such as:

* Pulling container images
* Reaching AWS APIs
* Downloading required packages
* Communicating with external services

That connectivity may come from:

```text
NAT Gateway
```

and/or appropriate:

```text
VPC endpoints
```

depending on architecture.

---

# 57. EKS Control-Plane Endpoint Access

Your `kubectl` commands communicate with the EKS cluster's Kubernetes API endpoint.

EKS allows control over API endpoint accessibility.

Architectures may use public access, private access, or combinations according to requirements.

This has important implications.

If the API endpoint is private-only, your laptop cannot simply reach it from anywhere on the internet.

You need network connectivity into the appropriate VPC environment.

```text

Kubernetes authorization
```

```text
Who can authenticate to AWS?
```


# 59. AWS IAM Authentication

When you access EKS, AWS identity plays an important role in authenticating who you are.

For example, your AWS CLI may currently operate as:

```text

IAM role
AWS IAM Identity Center role/session
```

depending on your environment.

Check:

```bash

```

This tells you which AWS identity the CLI is using.

Always know which identity you are using.

# 60. Authentication vs Authorization

These words are related but different.

Authentication asks:

```text
Who are you?
```

Authorization asks:

```text
What are you allowed to do?
```

For EKS:

```text
AWS identity
→ authentication relationship
```

Then Kubernetes permissions determine what operations that identity can perform in the cluster.

# 61. Kubernetes RBAC

Kubernetes commonly uses:

```text
RBAC
```

which means:

```text
Role-Based Access Control
```

RBAC can define permissions such as:

```text
Can view Pods
Can create Deployments
Can delete Services
Can read resources in one namespace
```

A complete RBAC treatment belongs in the Kubernetes course.

For this EKS introduction, remember:

```text
AWS IAM identity
does not automatically mean
unlimited Kubernetes permissions.
```

# 62. EKS Access Management

Modern EKS supports cluster access management through EKS access entries and associated access policies, while Kubernetes RBAC remains relevant for Kubernetes authorization patterns.

Older EKS material may discuss:

```text
aws-auth ConfigMap
```

as the primary mechanism for mapping AWS identities.

You should recognize that name because you will encounter it in older tutorials and existing clusters.

But do not assume every modern EKS cluster should be managed using an old tutorial's access model.

# 63. Workload IAM Is a Different Problem

There is another IAM question:

```text
How does an application running inside a Pod access AWS services?
```

For example:

```text
Pod
 |
 v
Application
 |
 v
S3
```

Do not solve this by putting permanent AWS access keys into the container.

EKS supports mechanisms for associating AWS permissions with workloads, including EKS Pod Identity and other established IAM integration patterns.

The goal is:

```text
Pod workload
    |
    v
Approved AWS identity
    |
    v

```

# 64. Do Not Give Every Pod the Node's Permissions

A dangerous mental model is:

```text
All applications on this worker can use broad node permissions.
```

Instead, aim for workload-specific permissions.

For example:

```text

→ No S3 permission

Report Pod
→ Read one S3 bucket

Backup Pod
→ Write to one backup location
```

Apply least privilege.

# 99. Health Checks in Kubernetes

In Part 18 you learned that:

```text
Running
```

does not necessarily mean:

```text
Healthy
```

Kubernetes has health probes.

Important concepts include:

```text
startupProbe
livenessProbe
readinessProbe
```

These have different purposes.

---

# 100. Readiness Probe

A readiness probe answers:

```text
Is this container ready to receive traffic?
```

Suppose your application process starts but needs 15 seconds to initialize.

Without appropriate readiness handling, traffic may arrive too early.

A readiness probe helps Kubernetes decide whether the Pod should currently receive Service traffic.

---

# 101. Liveness Probe

A liveness probe asks:

```text
Is this container still functioning, or should Kubernetes restart it?
```

For example, a process may remain alive while becoming permanently stuck.

A liveness probe can detect configured failure conditions and trigger container restart behavior.

---

# 102. Startup Probe

A startup probe helps with applications that need significant startup time.

It effectively provides a startup-specific health check before normal liveness behavior takes over.

This can prevent a slow-starting application from being repeatedly killed by an overly aggressive liveness probe.

---

# 103. Probe Example

Suppose the application provides:

```text
/health
```

A simplified configuration might include:

```yaml
readinessProbe:
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 10
```

This means Kubernetes periodically requests:

```text
http://Pod-IP:8080/health
```

according to the configured timing.

---

# 104. Do Not Copy Probe Values Blindly

This:

```yaml
initialDelaySeconds: 5
```

is not universally correct.

An application that takes:

```text
45 seconds
```

to initialize may require a different probe design.

Probe timing should reflect real application behavior.

Bad health-check configuration can create outages by repeatedly restarting healthy-but-slow applications or routing traffic too early.
