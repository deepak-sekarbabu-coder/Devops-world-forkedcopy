# Part 18: Amazon ECS and Running Containers in Production

In Part 17, you learned how an application moves through this workflow:

```text
Application Code
      |
      v
Dockerfile
      |
      v
docker build
      |
      v
Container Image
      |
      v
Amazon ECR
```

You learned that Amazon ECR stores and distributes container images.

But storing an image is not the same as running an application.

We now need something that can take the image from ECR, start containers, keep them running, replace failed containers, scale them, connect them to networking, send traffic to them, and deploy new versions.

That is where container orchestration enters the picture.

In AWS, one major container orchestration service is Amazon Elastic Container Service, or Amazon ECS.

By the end of this part, you should understand the complete flow:

```text
Git / Code
    |
    v
Docker Build
    |
    v
Container Image
    |
    v
Amazon ECR
    |
    v
ECS Task Definition
    |
    v
ECS Service
    |
    v
Running ECS Tasks
    |
    v
Application Load Balancer
    |
    v
Users
```

The important relationship is:

```text
Docker
builds the image.

ECR
stores the image.

ECS
runs and manages containers from the image.

ALB
distributes application traffic to them.
```

---

# 1. The Problem After ECR

Suppose you pushed this image to ECR:

```text
123456789012.dkr.ecr.us-east-1.amazonaws.com/veriqta-web:1.0
```

The image exists.

But nothing is running yet.

No user can visit your application simply because the image exists in ECR.

Something must:

1. Obtain compute capacity.
2. Pull the image.
3. Create a container.
4. Allocate CPU.
5. Allocate memory.
6. Configure networking.
7. Start the application.
8. Monitor whether it remains healthy.
9. Restart or replace it when it fails.
10. Run multiple copies when necessary.
11. Connect the copies to a load balancer.
12. Deploy new versions safely.

You could manually do some of this.

For example:

```text
EC2
 |
 v
Install Docker
 |
 v
docker pull
 |
 v
docker run
```

But production systems quickly become more complicated.

---

# 2. Imagine Managing Containers Manually

Suppose your application needs ten containers.

You manually launch:

```text
Container 1
Container 2
Container 3
...
Container 10
```

Now Container 4 crashes.

Who notices?

Who replaces it?

Traffic increases.

You now need 20 containers.

Who launches the additional 10?

A server fails.

Three containers disappear.

Who recreates them elsewhere?

You release application version 2.

Who replaces version 1 without taking the whole application offline?

These are orchestration problems.

---

# 3. Why Container Orchestration Exists

Container orchestration is the coordination and management of containerized workloads.

An orchestrator helps answer questions such as:

```text
Which containers should run?

How many should run?

Where should they run?

How much CPU do they need?

How much memory do they need?

Which network should they use?

Which ports should they expose?

Which permissions do they need?

How should traffic reach them?

What happens when one fails?

How should they scale?

How should a new version replace an old version?
```

Instead of manually managing individual containers, you declare the desired state.

For example:

```text
I want 3 copies of my application running.
```

The orchestrator works to maintain that state.

---

# 4. Desired State

Desired state is one of the most important concepts in orchestration.

Suppose you tell ECS:

```text
Desired tasks = 3
```

The actual state is:

```text
Running tasks = 3
```

Everything is fine.

Then one task crashes:

```text
Desired = 3

Actual = 2
```

ECS detects the difference.

It can start a replacement.

Eventually:

```text
Desired = 3

Actual = 3
```

This is reconciliation.

The system continually works toward the desired state.

---

# 5. What Is Amazon ECS?

ECS stands for:

```text
Elastic Container Service
```

Amazon ECS is AWS's managed container orchestration service.

ECS helps you:

* Define container workloads.
* Run containers.
* Maintain desired numbers of tasks.
* Replace failed tasks.
* Integrate with AWS networking.
* Integrate with IAM.
* Integrate with ECR.
* Integrate with load balancers.
* Collect logs.
* Perform deployments.
* Scale services.

The basic relationship is:

```text
ECR
 |
 | Container Image
 v
ECS
 |
 v
Running Container Workload
```

---

# 6. ECS Is Not Docker

Docker and ECS have different responsibilities.

Docker can:

```text
Build images
Run containers
Inspect containers
Work with registries
```

ECS provides orchestration.

Think:

```text
Docker
    |
    v
Container technology
```

```text
ECS
    |
    v
Container orchestration on AWS
```

You will still use Docker to build images.

ECS can then run containers from those images.

# 9. What Is an ECS Cluster?

An ECS cluster is a logical grouping for ECS workloads and capacity.

You can think of it as an organizational boundary within which ECS services and tasks operate.

For example:

```text
production-cluster
```

could contain:

```text
frontend-service
backend-service
worker-service
```

Conceptually:

```text
production-cluster
 |
 +-- frontend-service
 |
 +-- backend-service
 |
 +-- worker-service
```

---

# 10. A Cluster Is Not Automatically a Server

A common beginner mistake is thinking:

```text
Cluster = EC2 server
```

That is incorrect.

A cluster is an ECS organizational and scheduling construct.

How the actual compute is provided depends on your ECS capacity model.

You might use:

```text
AWS Fargate
```

or EC2-backed ECS capacity.

We will examine both later.

---

# 11. What Is a Task Definition?

A task definition is a blueprint describing how ECS should run one or more containers together as a task.

It can specify things such as:

* Container image
* CPU
* Memory
* Container port
* Environment variables
* Logging
* IAM roles
* Health-related settings
* Startup commands
* Secrets references
* Network requirements
* Multiple container definitions

Think:

```text
Task Definition
=
Instructions for creating ECS tasks
```

---

# 12. Task Definition vs Dockerfile

Do not confuse them.

A Dockerfile answers:

```text
How should this container image be built?
```

A task definition answers:

```text
How should ECS run containers from an image?
```

The workflow is:

```text
Dockerfile
    |
    v
docker build
    |
    v
Image
    |
    v
ECR
    |
    v
Task Definition
    |
    v
ECS Task
```

---

# 13. What Is a Container Definition?

Inside a task definition, you define one or more containers.

A container definition may specify:

```text
Container name
Image
CPU
Memory
Ports
Environment variables
Logging
Secrets
Health check
Command
```

For example:

```text
Task Definition
 |
 +-- Container Definition
       |
       +-- Name: web
       +-- Image: ECR image
       +-- Port: 8080
       +-- CPU allocation
       +-- Memory allocation
       +-- Logging configuration
```

---

# 14. One Task Can Contain Multiple Containers

A task definition can contain multiple container definitions.

For example:

```text
Task
 |
 +-- Application Container
 |
 +-- Supporting Container
```

A supporting container might provide functionality such as:

* Log routing
* Monitoring
* Proxying
* Other tightly coupled functionality

However, beginners should not place unrelated applications inside the same task simply because ECS allows multiple containers.

Containers in one task should normally have a strong lifecycle relationship.

---

# 15. What Is an ECS Task?

A task is a running instantiation of a task definition.

Think:

```text
Task Definition
=
Blueprint
```

```text
Task
=
Running instance of that blueprint
```

This resembles the relationship:

```text
Container Image
→ Container
```

Likewise:

```text
Task Definition
→ ECS Task
```

---

# 16. Task Definition Revisions

Task definitions are versioned through revisions.

For example:

```text
veriqta-web:1
veriqta-web:2
veriqta-web:3
```

A new revision can be created when configuration changes.

For example:

```text
Revision 1
Image: veriqta-web:1.0
```

Later:

```text
Revision 2
Image: veriqta-web:1.1
```

This helps ECS deployments move workloads to updated definitions.

---

# 17. Task Definitions Should Be Treated Carefully

Task definitions can contain operational configuration.

They should not become a place where engineers casually hardcode:

```text
Passwords
Database credentials
API keys
Private tokens
```

Sensitive information requires proper secret-management practices.

We will cover that shortly.

---

# 18. What Is an ECS Service?

A service manages a desired number of tasks over time.

Suppose:

```text
Desired count = 3
```

The service tries to maintain:

```text
Task 1
Task 2
Task 3
```

If Task 2 fails:

```text
Task 1
Task 3
```

the service can launch a replacement:

```text
Task 1
Task 3
Task 4
```

The desired count returns to:

```text
3
```

---

# 19. Task vs Service

This is another critical distinction.

A task is:

```text
One running instance of a task definition
```

A service is:

```text
A controller that maintains tasks
```

For long-running applications, you commonly use a service.

For one-off or batch-style work, you may run standalone tasks.

---

# 20. Standalone Tasks

Not every container workload needs to run continuously.

You may need a container to:

```text
Process a batch
Perform a maintenance job
Run a migration
Execute a one-time operation
```

In those cases, a standalone ECS task may be appropriate.

For a continuously available web application:

```text
ECS Service
```

is generally the more relevant concept.

# 22. Where Does Compute Come From?

Containers require:

```text
CPU
Memory
Networking
Operating-system resources
```

ECS therefore needs compute capacity.

Two important ECS compute approaches are:

```text
AWS Fargate
```

and:

```text
Amazon EC2
```

The difference concerns who manages the underlying compute infrastructure.

---

# 23. What Is AWS Fargate?

AWS Fargate is a serverless compute engine used with container services such as ECS.

Serverless does not mean:

```text
Servers do not exist.
```

It means AWS manages more of the underlying server infrastructure for you.

With Fargate, you define the resources your task needs.

For example:

```text
CPU
Memory
Networking
Image
```

AWS provides the underlying compute capacity.

---

# 24. Fargate Mental Model

With Fargate:

```text
You manage:
Application
Container image
Task definition
Service
IAM
Networking
Scaling
Application configuration
```

AWS manages more of:

```text
Physical infrastructure
Underlying host capacity
Host operating-system management
```

This removes much of the host-management burden.

---

# 25. ECS on EC2

The other major model runs ECS tasks using EC2-based capacity.

Conceptually:

```text
ECS Cluster
 |
 +-- EC2 Instance
 |     |
 |     +-- ECS Tasks
 |
 +-- EC2 Instance
       |
       +-- ECS Tasks
```

You manage more of the compute layer.

That can include considerations such as:

* EC2 instance types
* Capacity
* Operating-system updates
* AMIs
* Instance scaling
* Host security
* Instance lifecycle
* Resource utilization

---

# 26. Fargate vs EC2

At a beginner level:

| Area                   | Fargate                      | EC2-backed ECS               |
| ---------------------- | ---------------------------- | ---------------------------- |
| Host management        | Mostly AWS-managed           | You manage EC2 hosts         |
| Task infrastructure    | Provisioned for tasks        | Tasks placed on EC2 capacity |
| EC2 patching           | Not your host responsibility | Your responsibility          |
| Capacity planning      | Reduced host planning        | Host capacity matters        |
| Infrastructure control | Less host-level control      | More host-level control      |
| Operational complexity | Generally lower              | Generally higher             |

Neither is automatically correct for every workload.

---

# 27. Why Start With Fargate?

For a beginner learning ECS, Fargate allows you to focus on:

```text
Container
Task Definition
Task
Service
Networking
IAM
ALB
Scaling
Deployment
```

without immediately adding:

```text
EC2 host management
ECS agent management
Host patching
Instance capacity planning
```

We will therefore use Fargate for our main beginner application.

# 28. ECS Networking

Networking is one of the most important ECS topics.

Your containers must communicate with:

* Users
* Load balancers
* Databases
* AWS APIs
* Other services
* External APIs where required

For Fargate, tasks commonly use the `awsvpc` network mode.

Each task receives networking through an Elastic Network Interface.

Conceptually:

```text
VPC
 |
 +-- Private Subnet
       |
       +-- ECS Task
             |
             +-- Private IP
```

# 29. ECS Lives Inside Your VPC Architecture

Remember Part 10:

```text
VPC
 |
 +-- Public Subnets
 |
 +-- Private Application Subnets
 |
 +-- Private Database Subnets
```

A common architecture is:

```text
Internet
   |
   v
Internet Gateway
   |
   v
Application Load Balancer
   |
   v
Private ECS Tasks
   |
   v
RDS
```

This is similar to the EC2 architecture you already learned.

The application compute changed from:

```text
EC2 application servers
```

```text
ECS tasks
```

The networking principles still matter.

---

# 30. Public vs Private ECS Tasks

A production-style web architecture often places:

```text
ALB
```

in public subnets and:

```text
ECS tasks
```

in private subnets.

Architecture:

```text
Internet
    |
    v
Internet Gateway
    |
    v
ALB
 / \
Public Subnet A
Public Subnet B
    |
    v
ECS Tasks
 / \
Private App Subnet A
Private App Subnet B
```

Users communicate with the ALB.

They do not normally need direct internet access to individual application tasks.

---

# 31. ECS Task Outbound Access

Private ECS tasks may still need outbound connectivity.

For example, they may need to:

* Pull container images.
* Reach AWS APIs.
* Download dependencies at startup.
* Contact external APIs.

Depending on your architecture, outbound access may use:

```text
NAT Gateway
```

or appropriate:

```text
VPC endpoints
```

and related AWS service connectivity.

Remember:

```text
Private subnet
does not mean
no network requirements.
```

---

# 32. Security Groups for ECS

Security Groups can control task traffic.

Suppose:

```text
ALB Security Group
```

allows:

```text
Inbound TCP 443
Source: Internet
```

Then:

```text
ECS Task Security Group
```

can allow:

```text
Inbound TCP 8080
Source: ALB Security Group
```

This is much safer than:

```text
ECS Task port 8080
Source: 0.0.0.0/0
```

when the tasks should only receive traffic from the ALB.

---

# 33. Security Group Chaining

The architecture becomes:

```text
Internet
   |
   | HTTPS 443
   v
ALB Security Group
   |
   | App Port 8080
   v
ECS Task Security Group
```

The ECS task does not need to trust the entire internet.

It trusts traffic from the load balancer's Security Group.

This is Security Group referencing.

---

# 34. Database Security

If the ECS application connects to RDS:

```text
ECS Task SG
    |
    | Database Port
    v
RDS SG
```

The RDS Security Group can allow database traffic from:

```text
ECS Task Security Group
```

rather than:

```text
0.0.0.0/0
```

The complete security chain becomes:

```text
Internet
   |
   v
ALB SG
   |
   v
ECS Task SG
   |
   v
RDS SG
```

# 35. IAM in ECS

ECS introduces an important IAM distinction.

You may encounter:

```text
Task execution role
```

and:

```text
Task role
```

They are not the same.

Understanding this distinction prevents many security and troubleshooting problems.

---

# 36. What Is the Task Execution Role?

The task execution role gives ECS and its supporting runtime mechanisms permission to perform operations needed to start and operate the task.

Examples can include:

```text
Pull image from ECR
Send logs to CloudWatch Logs
Retrieve referenced startup secrets when configured
```

Think:

```text
Task Execution Role
=
Permissions needed to launch/support the task
```

---

# 37. What Is the Task Role?

The task role is the IAM role that application code inside the task can use to access AWS services.

For example, your application might need to:

```text
Read an S3 object
Write to an SQS queue
Publish to SNS
Access DynamoDB
```

The task role provides those application-level AWS permissions.

Think:

```text
Task Role
=
Permissions used by the application
```

---

# 38. Execution Role vs Task Role

This distinction is critical:

```text
Execution Role
 |
 v
ECS needs AWS access to start/support the task
```

```text
Task Role
 |
 v
Application inside the task needs AWS access
```

Example:

```text
ECR pull
→ Execution Role
```

```text
Application reads S3
→ Task Role
```

Do not give the application unnecessary permissions simply because ECS needs them.

---

# 39. Least Privilege for ECS Tasks

Suppose your application only needs:

```text
s3:GetObject
```

from:

```text
my-application-assets
```

Do not give it:

```text
AdministratorAccess
```

Do not give it:

```text
s3:*
```

across every bucket without a reason.

The principle remains:

```text
Application
gets only the permissions
required for its job.
```

---

# 40. Why Task Roles Are Better Than Hardcoded Credentials

Do not put AWS credentials into:

```text
Dockerfile
Environment file committed to Git
Application source code
Container image
```

Instead, ECS tasks can receive temporary AWS credentials through the assigned task role.

Conceptually:

```text
ECS Task
    |
    v
IAM Task Role
    |
    v
Temporary AWS Credentials
    |
    v
Allowed AWS Service
```

This avoids distributing permanent access keys inside images.

---

# 41. Environment Variables

Applications frequently need configuration.

Examples:

```text
APP_ENV=production
LOG_LEVEL=info
API_BASE_URL=https://api.example.com
```

Environment variables allow configuration to be supplied at runtime.

This helps separate:

```text
Application image
```

from:

```text
Environment-specific configuration
```

---

# 42. Why Runtime Configuration Matters

Imagine using the same image in:

```text
Development
Staging
Production
```

You do not necessarily want three different images merely because:

```text
LOG_LEVEL
```

changes.

Instead:

```text
Same Image
   |
   +-- Development configuration
   |
   +-- Staging configuration
   |
   +-- Production configuration
```

This supports artifact consistency.

---

# 43. Not Every Environment Variable Is a Secret

These may be ordinary configuration:

```text
APP_ENV=production
LOG_LEVEL=info
FEATURE_MODE=standard
```

But these are sensitive:

```text
DATABASE_PASSWORD
API_TOKEN
PRIVATE_KEY
```

Do not treat all environment variables as equally safe.

---

# 44. Secrets Concepts

Sensitive configuration should be managed using appropriate secret-management systems.

AWS options can include:

```text
AWS Secrets Manager
```

and:

```text
AWS Systems Manager Parameter Store
```

depending on the use case.

ECS task definitions can reference secret values instead of hardcoding sensitive plaintext values directly into application configuration.

---

# 45. Secret Flow

Conceptually:

```text
Secrets Manager
      |
      v
ECS Task Startup
      |
      v
Application Container
```

The task receives the configured secret according to the ECS configuration and IAM permissions.

The secret should not be baked into:

```text
Docker image
```

or committed to:

```text
Git
```

---

# 46. Secret Security Still Requires Care

Using a secret manager does not make secrets impossible to expose.

Application developers still need to avoid:

```text
Logging secrets
Printing environment variables
Returning secrets in error messages
Including secrets in debugging output
```

Secret management is a complete lifecycle.

Think:

```text
Store securely
→ Grant access carefully
→ Retrieve securely
→ Use carefully
→ Rotate when required
→ Avoid logging
```

---

# 47. Logging in ECS

Containers produce application output.

For production troubleshooting, you need somewhere to collect it.

A common architecture is:

```text
ECS Task
    |
    v
Container stdout/stderr
    |
    v
CloudWatch Logs
```

The task definition can configure a logging driver such as:

```text
awslogs
```

to send container logs to CloudWatch Logs.

---

# 48. Why Centralized Logs Matter

Without centralized logs:

```text
Task A
Task B
Task C
```

each produces separate output.

If Task B crashes and disappears, troubleshooting can become difficult if logs were only available locally.

With centralized logging:

```text
Task A ──┐
Task B ──┼──> CloudWatch Logs
Task C ──┘
```

you can investigate application behavior centrally.

---

# 49. Log Groups and Log Streams

Remember Part 15.

CloudWatch Logs uses:

```text
Log Group
    |
    +-- Log Stream
    +-- Log Stream
    +-- Log Stream
```

An ECS application might use:

```text
/aws/ecs/veriqta-web
```

as a log group.

Different tasks can produce different log streams.

---

# 50. Application Logging Best Practice

Containerized applications generally work well when application logs are written to:

```text
stdout
```

and:

```text
stderr
```

The container platform can then collect them.

This is often preferable to depending only on files stored inside an ephemeral container filesystem.

---

# 51. Health Checks

Running does not always mean healthy.

Suppose:

```text
Container process exists.
```

But:

```text
Application cannot serve requests.
```

The container may technically be running while the application is unusable.

Health checks help determine whether the application is actually functioning.

---

# 52. Container Health Checks

A container health check can test something inside the task/container environment.

For example:

```text
curl http://localhost:8080/health
```

The application might return:

```text
200 OK
```

when healthy.

The exact health-check mechanism depends on your configuration.

---

# 53. Load Balancer Health Checks

An ALB target group can independently check targets.

For example:

```text
GET /health
```

Expected:

```text
HTTP 200
```

If a target repeatedly fails health checks, the ALB can stop routing normal traffic to it.

---

# 54. Container Health vs ALB Health

These are related but different.

```text
Container Health
```

asks:

```text
Does ECS/container runtime consider this container healthy?
```

```text
ALB Target Health
```

asks:

```text
Can the load balancer successfully reach the configured application health endpoint?
```

Both can help identify different failure conditions.

---

# 55. Designing a Health Endpoint

A simple application may expose:

```text
/health
```

For example:

```text
GET /health
```

returns:

```text
200 OK
```

A production health strategy requires thought.

If your health endpoint checks every external dependency and one minor dependency fails, you might accidentally cause all application instances to be removed from service.

Health-check design should match what "healthy enough to receive traffic" actually means.

---

# 56. Application Load Balancer Integration

For web applications, ECS commonly integrates with an Application Load Balancer.

Architecture:

```text
Users
   |
   v
Route 53
   |
   v
Application Load Balancer
   |
   v
Target Group
   |
   +-------------+
   |             |
   v             v
ECS Task A     ECS Task B
```

The ALB distributes requests across healthy ECS tasks.

---

# 57. Why Put an ALB in Front of ECS?

Without a load balancer, users would need some way to know where individual tasks are running.

But tasks are replaceable.

A task may stop.

Another may start with different networking information.

The ALB provides a stable entry point.

Users access:

```text
app.example.com
```

rather than individual task IP addresses.

---

# 58. ALB Traffic Flow

Suppose a user requests:

```text
https://app.example.com
```

The flow may be:

```text
User
 |
 v
DNS
 |
 v
ALB
 |
 v
Listener 443
 |
 v
Listener Rule
 |
 v
Target Group
 |
 v
Healthy ECS Task
 |
 v
Container Port 8080
 |
 v
Application
```

Every layer can become a troubleshooting point.

---

# 59. Target Groups

The ALB sends traffic to a target group.

For ECS with `awsvpc` networking, targets are commonly registered by IP address.

Conceptually:

```text
Target Group
 |
 +-- Task A private IP
 |
 +-- Task B private IP
 |
 +-- Task C private IP
```

As tasks are created and removed, ECS integrates with the load balancer to manage target registration.

# 62. ECS Across Availability Zones

High availability requires thinking about failure domains.

Suppose both tasks run in:


A stronger architecture distributes tasks across multiple Availability Zones when appropriate.


# 63. Service Desired Count

An ECS service has a desired number of tasks.

Example:

```text
Minimum operational requirement:
2 tasks
```

Then:

```text
Desired count = 2
```

ECS tries to maintain two tasks.

If one stops:

```text
Desired = 2
Actual = 1
```

ECS works to launch another.

---

# 64. Desired Count Is Not Auto Scaling

Do not confuse:

```text
Desired count
```

with:

```text
Automatic scaling
```

Desired count simply describes how many tasks the service currently wants.

Auto scaling can change the desired count automatically according to configured policies and metrics.

---

# 65. ECS Service Auto Scaling

Suppose normal traffic requires:

```text
2 tasks
```

Traffic increases.

A scaling policy determines that more capacity is required.

The desired count might change:

```text
2
→ 3
→ 4
→ 5
```

When demand decreases:

```text
5
→ 4
→ 3
→ 2
```

This is horizontal scaling.

---

# 66. Vertical vs Horizontal Scaling

Remember Part 12.

Vertical scaling means:

```text
Make each unit larger.
```

For ECS, this could mean increasing task CPU or memory.

Horizontal scaling means:

```text
Run more task instances.
```

For example:

```text
2 tasks
→
6 tasks
```

Web applications commonly benefit from horizontal scaling when designed appropriately.

---

# 67. Target Tracking Scaling

Target tracking tries to maintain a metric near a target value.

For example, conceptually:

```text
Maintain average CPU around 60%.
```

If CPU becomes consistently higher:

```text
Scale out
```

If sufficiently lower:

```text
Scale in
```

subject to the configured policy and limits.

---

# 68. Scaling Metrics

Possible scaling signals may include:

* CPU utilization
* Memory utilization
* ALB request-related metrics
* Custom application metrics

Do not automatically use CPU for every application.

Some workloads are constrained by:

```text
Memory
Network
Queue depth
Requests
External dependency capacity
```

The scaling signal should represent workload pressure.

---

# 69. Minimum and Maximum Capacity

A service scaling configuration can establish boundaries.

For example:

```text
Minimum tasks = 2
Maximum tasks = 10
```

Auto scaling can then adjust the desired count within those limits.

The minimum helps preserve baseline availability.

The maximum helps control runaway scaling and cost.

---

# 70. Scaling Does Not Fix Bad Applications

Suppose every request causes an expensive database query.

Traffic increases.

ECS adds more tasks.

Now:

```text
More tasks
→ More database connections
→ More database load
```

The database becomes overwhelmed.

Scaling the application tier does not automatically scale every dependency.

Always consider:

```text
ALB
 |
 v
ECS
 |
 v
RDS
```

as a complete system.

---

# 71. Stateless Application Design

Horizontal scaling works best when application instances do not depend on unique local state.

Suppose:

```text
Task A
```

stores a user's session only in local memory.

The next request goes to:

```text
Task B
```

Task B does not know about the session.

This creates problems.

Stateless application design tries to keep replaceable application instances interchangeable.


depending on the use case.

Do not assume the container's local filesystem is durable application storage.

Tasks can be replaced.

# 74. Rolling Deployments

Suppose your service currently runs:

```text
Image v1
```

You push:

```text
Image v2
```

to ECR and create a new task definition revision.

You want to deploy v2 without shutting down every v1 task at once.

A rolling deployment gradually replaces old tasks with new tasks.

Conceptually:

```text
Beginning:

v1
v1
v1
```

Then:

```text
v1
v1
v2
```

Then:

```text
v1
v2
v2
```

Finally:

```text
v2
v2
v2
```

Exact behavior depends on deployment configuration and health.

---

# 75. Why Health Checks Matter During Deployment

Imagine v2 contains a bug.

ECS starts:

```text
v2
```

but the ALB health check fails.

The new task should not become a normal healthy target.

Without useful health checks, a broken application may appear operational simply because its process started.

Health checks therefore participate in deployment safety.

---

# 76. Deployment Configuration

ECS services have deployment settings controlling how tasks are replaced.

Conceptually, ECS needs to answer:

```text
How many old tasks may stop?

How many extra new tasks may temporarily run?

When is a new task considered ready?

What should happen when deployment fails?
```

These settings affect:

* Availability
* Deployment speed
* Temporary capacity
* Failure behavior

---

# 77. Deployment Circuit Breaker Concept

ECS supports deployment failure detection mechanisms, including deployment circuit breaker functionality for applicable ECS rolling deployments.

Conceptually:

```text
Deploy v2
   |
   v
New tasks fail
   |
   v
Deployment cannot reach healthy state
   |
   v
Deployment marked failed
```

Rollback behavior can also be configured.

This is safer than endlessly attempting to deploy a broken revision without useful failure handling.

* Traffic patterns
* Large workloads
* Memory-intensive operations

```text
Reduce memory usage
Increase task memory
Scale workload differently
```

# 143. Problem: Tasks Cannot Reach RDS

# 164. ECS Production Security Principles

For production awareness:

* Keep application tasks private when public access is unnecessary.
* Expose applications through controlled entry points such as an ALB.
* Restrict task Security Groups.
* Use Security Group references.
* Use task roles instead of embedded AWS credentials.
* Apply least privilege.
* Store secrets outside images.
* Do not log secrets.
* Use trusted container images.
* Scan images.
* Use HTTPS for public applications.
* Keep deployment artifacts traceable.
* Centralize logs.
* Monitor health.
* Use multiple Availability Zones where appropriate.

Design tasks to be replaceable.

Use:

```text

Multiple Availability Zones

Service reconciliation
Auto scaling
Centralized logs
CloudWatch metrics
Controlled deployments
```

Avoid architectures where:

```text

=
Entire application outage
```

when the workload requires high availability.
