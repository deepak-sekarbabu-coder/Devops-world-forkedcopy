# Part 17: ECR, Docker Images, and AWS Container Registries

In the previous parts, you learned how AWS networking, EC2, load balancing, Auto Scaling, S3, RDS, CloudWatch, and Route 53 fit together.

Until now, you could think of an application as software installed directly on an EC2 instance.

Modern applications are also commonly packaged as containers.

Instead of manually installing an application and all of its runtime dependencies on every server, you can package the application into a container image.

That image can then be stored in a container registry.

In AWS, the primary managed container registry service is Amazon Elastic Container Registry, commonly called Amazon ECR.

The basic workflow is:

```text
Developer
    |
    v
Application Code
    |
    v
Dockerfile
    |
    v
docker build
    |
    v
Container Image
    |
    v
docker tag
    |
    v
Amazon ECR
```

Later, services such as ECS and EKS can retrieve those images and run containers from them.

The larger architecture becomes:

```text
Developer
    |
    v
Git Repository
    |
    v
CI/CD Pipeline
    |
    v
Docker Build
    |
    v
Container Image
    |
    v
Amazon ECR
    |
    +----------------+
    |                |
    v                v
   ECS              EKS
    |                |
    v                v
Containers       Containers
```

The important idea is:

```text
ECR stores container images.

ECR does not normally run your application.
```

That distinction will become important throughout this part.

---

# 1. What Is a Container?

Before learning ECR, you need to understand what ECR stores.

A container is an isolated process, or group of processes, running from a packaged filesystem and configuration.

Containers allow an application to run with the files, libraries, runtime, and configuration assumptions packaged into its image.

For example, imagine an application needs:

```text
Python
Application code
Python packages
Runtime files
```

Without containers, you might manually prepare a server:

```text
EC2
 |
 +-- Install Python
 |
 +-- Install dependencies
 |
 +-- Copy application
 |
 +-- Configure runtime
 |
 +-- Start application
```

With containers:

```text
Container Image
 |
 +-- Runtime
 +-- Dependencies
 +-- Application
 +-- Runtime instructions
```

You can use that image to start containers on compatible container infrastructure.

---

# 2. Why Containers Exist

Imagine three environments:

```text
Developer Laptop
Testing Server
Production Server
```

If each environment is configured manually, differences can appear.

For example:

```text
Developer:
Python 3.x
Package version A

Production:
Different Python release
Package version B
```

The application may work locally but fail in production.

Containers help package the application's runtime requirements consistently.

The goal is not:

```text
Every machine is identical.
```

The goal is closer to:

```text
The application artifact is built consistently
and runs using a defined container image.
```

---

# 3. Containers Are Not Virtual Machines

This distinction matters.

A virtual machine normally includes an entire guest operating system.

Conceptually:

```text
Physical Server
 |
 v
Hypervisor
 |
 +------------------+
 |                  |
 v                  v
VM 1               VM 2
 |
 +-- Guest OS
 +-- Libraries
 +-- Application
```

Containers work differently.

Conceptually:

```text
Host
 |
 v
Operating System Kernel
 |
 v
Container Runtime
 |
 +-----------+-----------+
 |           |           |
 v           v           v
Container A Container B Container C
```

Containers generally share the host kernel rather than each container carrying a separate guest kernel.

This makes containers relatively lightweight compared with full virtual machines.

---

# 4. Containers Still Need Infrastructure

Containers do not eliminate servers.

Some infrastructure must provide:

* CPU
* Memory
* Networking
* Storage
* Operating system functionality
* Container runtime functionality

For example:

```text
EC2
 |
 v
Container Runtime
 |
 v
Container
```

Or AWS can abstract more of the underlying compute depending on the service you choose.

This is why containers do not mean:

```text
No servers exist.
```

They mean:

```text
The application is packaged and executed using container technology.
```

# 7. Image vs Container

This is one of the most important container concepts.

An image is not the same thing as a container.

## Image

An image is the packaged artifact used to create containers.

Think:

```text
Image
=
Template/package
```

## Container

A container is a running, or stopped, instance created from an image.

Think:

```text
Container
=
Runtime instance of an image
```

A useful analogy is:

```text
Image = recipe

Container = meal created from recipe
```

The analogy is imperfect, but useful for beginners.

---

# 8. One Image Can Create Multiple Containers

Suppose you have:

```text
myapp:1.0
```

You can create multiple containers from it:

```text
              myapp:1.0
                  |
        +---------+---------+
        |         |         |
        v         v         v
 Container A Container B Container C
```

This becomes important when scaling applications.

ECS or Kubernetes may start many containers using the same image.

---

# 9. What Is a Dockerfile?

A Dockerfile is a text file containing instructions for building a container image.

A simple example:

```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .

RUN pip install --no-cache-dir -r requirements.txt

COPY . .

CMD ["python", "app.py"]
```

Do not blindly copy this.

Let's understand each instruction.

---

# 10. `FROM`

```dockerfile
FROM python:3.12-slim
```

`FROM` specifies the base image.

The base image provides the starting filesystem and runtime environment.

Here:

```text
python:3.12-slim
```

provides a lightweight Python environment.

Conceptually:

```text
Base Image
    |
    v
Your Changes
    |
    v
Final Image
```

---

# 11. `WORKDIR`

```dockerfile
WORKDIR /app
```

This establishes:

```text
/app
```

as the working directory for subsequent instructions.

Think of it similarly to changing into a directory before performing commands.

---

# 12. `COPY`

```dockerfile
COPY requirements.txt .
```

This copies:

```text
requirements.txt
```

from the Docker build context into the image's current working directory.

Later:

```dockerfile
COPY . .
```

copies application files into the image.

Be careful about what you copy.

You do not want secrets, unnecessary files, or development artifacts accidentally included.

A `.dockerignore` file can help control the build context.

---

# 13. `RUN`

```dockerfile
RUN pip install --no-cache-dir -r requirements.txt
```

`RUN` executes a command while the image is being built.

Here it installs Python dependencies.

This happens during:

```bash
docker build
```

It does not mean the command runs every time the container starts.

---

# 14. `CMD`

```dockerfile
CMD ["python", "app.py"]
```

`CMD` specifies the default command that runs when a container starts from the image, unless overridden.

So:

```text
Build time:
RUN

Container start:
CMD
```

Keep those concepts separate.

---

# 15. What Is a Container Image?

A container image is built from image layers.

Conceptually:

```text
Final Image
 |
 +-- Base image layer
 |
 +-- Dependency changes
 |
 +-- Application files
 |
 +-- Configuration metadata
```

Container registries store these image artifacts and associated metadata.

---

# 16. Image Layers

Docker images are generally composed of content-addressable filesystem layers and metadata.

When an image changes, Docker can often reuse unchanged layers.

Imagine:

```text
Layer 4: Application changes
Layer 3: Python dependencies
Layer 2: Runtime files
Layer 1: Base image
```

If only application code changes, some earlier layers may be reusable.

This can improve build and transfer efficiency.

---

# 17. Why Dockerfile Order Matters

Consider:

```dockerfile
COPY . .

RUN pip install -r requirements.txt
```

If any application file changes, Docker may need to rebuild later layers.

A commonly useful pattern is:

```dockerfile
COPY requirements.txt .

RUN pip install --no-cache-dir -r requirements.txt

COPY . .
```

Now dependency installation may remain cacheable when application files change but dependency definitions do not.

Dockerfile structure can therefore affect build speed.

# 21. What ECR Does

ECR provides capabilities such as:

* Container image repositories
* Image storage
* Authentication
* Authorization through IAM
* Image pushing
* Image pulling
* Image tags
* Image digests
* Image scanning

# 22. What ECR Does Not Do

ECR does not normally:

* Run your containers
* Load balance your application
* Replace ECS
* Replace EKS
* Replace EC2
* Build your application automatically merely because a repository exists

Think:

```text
ECR
=
Registry
```

not:

```text
ECR
=
Container orchestrator
```

# 23. ECR Repository

An ECR repository is a logical collection where related container images are stored.

For example:

```text
Repository:
veriqta-web
```

It may contain images identified by tags such as:

```text
veriqta-web:1.0.0
veriqta-web:1.1.0
veriqta-web:2026-09-06
veriqta-web:latest
```

These may represent different versions or references to image manifests.

---

# 24. Repository vs Registry

Do not confuse these.

Conceptually:

```text
ECR Registry
 |
 +-- Repository A
 |
 +-- Repository B
 |
 +-- Repository C
```

For example:

```text
AWS Account ECR Registry
 |
 +-- frontend
 |
 +-- backend
 |
 +-- worker
```

A repository organizes images for a particular application or component.

---

# 25. Private Repositories

ECR commonly uses private repositories for application images.

A private repository requires authorization.

This is important because your container images may contain:

* Proprietary application code
* Internal binaries
* Application configuration
* Company-specific dependencies

However, secrets should not be baked into images.

Private repository does not mean:

```text
It is safe to store passwords inside the image.
```

Do not do that.

---

# 26. ECR Repository URI

An ECR repository URI typically follows a structure similar to:

```text
ACCOUNT_ID.dkr.ecr.REGION.amazonaws.com/REPOSITORY
```

For example:

```text
123456789012.dkr.ecr.us-east-1.amazonaws.com/veriqta-web
```

The important pieces are:

```text
123456789012
→ AWS account ID

us-east-1
→ AWS Region

veriqta-web
→ Repository name
```

Your actual values will differ.

# 27. ECR Is Regional

For example:

```text
us-east-1
```

and:

```text

```


# 36. AWS Authentication vs Docker Authentication

This is a major beginner concept.

You may have two separate authentication contexts:

```text
AWS CLI authentication
```

and:

```text
Docker registry authentication
```

They are related, but not identical.

Your AWS CLI may be authenticated successfully while Docker still cannot push to ECR.

---

# 37. AWS CLI Authentication

The AWS CLI needs AWS credentials or an AWS authentication mechanism.

Depending on your environment, authentication may involve:

* IAM Identity Center
* IAM roles
* Temporary credentials
* Development credentials
* Other supported AWS credential providers

Avoid treating long-lived access keys as the default answer for every environment.

In AWS workloads and CI/CD systems, temporary role-based credentials are generally preferable.

---

# 38. Docker Authentication to ECR

Docker must authenticate to the ECR registry before pushing or pulling private images.

The common command is:

```bash
aws ecr get-login-password \
  --region us-east-1 \
| docker login \
  --username AWS \
  --password-stdin 123456789012.dkr.ecr.us-east-1.amazonaws.com
```

Let's break this down carefully.

---

# 39. `aws ecr get-login-password`

```bash
aws ecr get-login-password --region us-east-1
```

This retrieves an ECR authentication password for use by a container client.

You generally should not manually copy and paste the password around.

Instead, pipe it directly into Docker.

---

# 40. The Pipe

The symbol:

```text
|
```

is a shell pipe.

It sends the standard output of the command on the left into the standard input of the command on the right.

So:

```text
aws ecr get-login-password
        |
        v
docker login
```

This creates a workflow between two commands.

---

# 41. `docker login`

The second command is:

```bash
docker login \
  --username AWS \
  --password-stdin 123456789012.dkr.ecr.us-east-1.amazonaws.com
```

`docker login` authenticates Docker to a container registry.

`--username AWS` uses the username required for this ECR authentication flow.

`--password-stdin` tells Docker to read the password from standard input instead of placing it directly in the command.

The final value is the ECR registry hostname.

---

# 42. Expected Authentication Result

A successful authentication commonly produces:

```text
Login Succeeded
```

That means Docker has accepted credentials for the registry.

It does not prove that your IAM identity has permission to perform every repository action.

Authentication and authorization are different.

---

# 43. Authentication vs Authorization

Authentication asks:

```text
Who are you?
```

Authorization asks:

```text
What are you allowed to do?
```

For example:

```text
AWS knows your identity.
```

But that identity may not have:

```text
ecr:PutImage
```

permission.

Then your push can still fail.

Always distinguish:

```text
Authentication failure
```

from:

```text
Authorization failure
```

# 50. What Is the Build Context?

The final:

```text

```

is important.

It means:

```text
Use the current directory as the Docker build context.
```

Docker can access files in the build context for instructions such as:

```dockerfile
COPY app.py .
```

If the required file is outside the build context, the build cannot simply copy it using that path.

# 57. Local Image vs ECR Image Reference

Currently your image is:

```text
veriqta-web:1.0
```

ECR needs a fully qualified image reference such as:

```text
123456789012.dkr.ecr.us-east-1.amazonaws.com/veriqta-web:1.0
```

You therefore tag the local image with the ECR repository reference.

---

# 58. Tag the Image

Run:

```bash
docker tag \
  veriqta-web:1.0 \
  123456789012.dkr.ecr.us-east-1.amazonaws.com/veriqta-web:1.0
```

Replace:

```text
123456789012
```

with your account ID.

Replace the Region and repository name when necessary.

---

# 59. What `docker tag` Does

This command does not normally create a completely separate copy of all image data.

It creates another image reference pointing to the image.

Conceptually:

```text
Same Image
   |
   +-- veriqta-web:1.0
   |
   +-- 123456789012.dkr.ecr.us-east-1.amazonaws.com/veriqta-web:1.0
```

This new reference tells Docker which registry and repository should receive the image when you push it.

---

# 60. Anatomy of the ECR Image Reference

Consider:

```text
123456789012.dkr.ecr.us-east-1.amazonaws.com/veriqta-web:1.0
```

Breakdown:

```text
123456789012
→ AWS account

dkr.ecr
→ ECR Docker registry naming

us-east-1
→ Region

amazonaws.com
→ AWS domain

veriqta-web
→ Repository

1.0
→ Image tag
```

Understanding this structure makes troubleshooting much easier.

# 61. Push the Image

After authentication and tagging:

```bash
docker push \
  123456789012.dkr.ecr.us-east-1.amazonaws.com/veriqta-web:1.0
```

Docker begins uploading image content to ECR.

You may see individual layers being:

```text
Pushed
```

or:

```text
Layer already exists
```

The exact output varies.

---

# 62. Why Some Layers Already Exist

Container registries can reuse content that already exists.

Suppose two images share the same base layers.

ECR does not necessarily need every identical layer uploaded again.

Conceptually:

```text
Image A
 |
 +-- Layer 1
 +-- Layer 2
 +-- Layer 3

Image B
 |
 +-- Layer 1
 +-- Layer 2
 +-- Layer 4
```

Shared content can be reused.

```bash
docker run --rm -p 8080:8080 \
  123456789012.dkr.ecr.us-east-1.amazonaws.com/veriqta-web:1.0
```

Test:

```bash
curl http://localhost:8080
```

You have now completed:

```text
Build
→ Tag
→ Push
→ Pull
→ Run
```

---

# 66. What Is an Image Tag?

A tag is a human-readable reference associated with an image.

Examples:

```text
1.0
1.0.1
v2
prod
staging
latest
```

For example:

```text
veriqta-web:1.0
```

means:

```text
Repository/image name:
veriqta-web

Tag:
1.0
```

---

# 67. Understanding `latest`

Beginners often think:

```text
latest
=
Automatically newest image
```

That is not a safe mental model.

`latest` is simply a tag name that Docker commonly uses by default in some workflows when no explicit tag is provided.

It does not inherently mean:

```text
Newest by creation time
```

or:

```text
Safest production release
```

Treat it as a normal tag whose meaning depends on how your workflow manages it.

---

# 68. Why `latest` Can Be Problematic

Suppose production deploys:

```text
veriqta-web:latest
```

Monday:

```text
latest → Image A
```

Tuesday:

```text
latest → Image B
```

Now the same textual reference may identify different image content over time.

That can make:

* Auditing harder
* Rollbacks harder
* Reproducibility weaker
* Incident investigation harder

Production workflows often benefit from immutable version identifiers or image digests.

---

# 69. Better Tagging Strategies

Possible tags include:

```text
1.0.0
1.0.1
2.0.0
```

or commit-related tags:

```text
a1b2c3d
```

or build identifiers:

```text
build-1042
```

A CI/CD pipeline might create:

```text
veriqta-web:a1b2c3d
```

This creates a relationship between:

```text
Source code
→ Commit
→ Image
```

which improves traceability.

---

# 70. What Is an Image Digest?

A digest is a content-addressable identifier associated with image content or an image manifest.

It typically looks like:

```text
sha256:...
```

For example:

```text
sha256:abcdef123456...
```

A tag is human-friendly.

A digest provides a content-based immutable reference.

Conceptually:

```text
Tag:
1.0

Digest:
sha256:...
```

---

# 71. Tag vs Digest

Think:

```text
Tag
=
Human-readable pointer
```

```text
Digest
=
Content identity
```

A tag can potentially be moved to different content unless immutability controls prevent it.

A digest identifies specific content.

---

# 72. Why Digests Matter

Imagine:

```text
production
```

points to Image A.

Later someone retags:

```text
production
```

to Image B.

If your deployment records only:

```text
production
```

it can become difficult to determine exactly which image content ran at a particular time.

A digest gives much stronger identification.

---

# 73. Pull by Digest

An image can be referenced using a digest:

```text
REPOSITORY_URI@sha256:DIGEST
```

Conceptually:

```bash
docker pull \
  123456789012.dkr.ecr.us-east-1.amazonaws.com/veriqta-web@sha256:YOUR_DIGEST
```

Replace the placeholder with the actual digest.

This identifies exact image content rather than relying on a mutable tag.

---

# 74. Image Tag Mutability

ECR repositories can be configured with tag mutability behavior.

If tags are mutable, a tag can be associated with different image content later.

For example:

```text
v1
 |
 v
Image A
```

then later:

```text
v1
 |
 v
Image B
```

That may be undesirable for controlled release workflows.

Tag immutability can help prevent accidental overwriting of existing tags.

---

# 75. Why Immutability Helps

Suppose production approved:

```text
release-2026-09-06
```

If that tag can later be overwritten, the meaning of the release identifier changes.

With appropriate immutability controls:

```text
release-2026-09-06
```

remains tied to the originally pushed image.

This improves:

* Traceability
* Auditability
* Rollback confidence
* Deployment consistency

---

# 76. Image Scanning

Container images can contain software vulnerabilities.

Examples include vulnerable:

* Operating-system packages
* Runtime libraries
* Application dependencies

ECR supports image scanning capabilities that can help identify known vulnerabilities in image contents.

The exact scanning capabilities and configuration options can depend on the ECR scanning mode and AWS configuration.

The important beginner principle is:

```text
Building successfully
does not mean
secure.
```

---

# 77. What Image Scanning Does

Conceptually:

```text
Container Image
      |
      v
Vulnerability Scanner
      |
      v
Known Vulnerability Findings
      |
      v
Engineering Review
```

Scanning may identify issues associated with software packages in the image.

It does not prove that an image is completely secure.

---

# 78. Vulnerability Findings

A finding may contain information such as:

```text
Affected package
Vulnerability identifier
Severity
Description
Remediation information
```

Severity levels can help prioritize investigation.

But do not use:

```text
Critical = automatically exploitable
```

or:

```text
Low = always safe
```

as absolute rules.

Risk depends on context.

---

# 79. Responding to Vulnerabilities

Suppose your base image contains a vulnerable package.

A common remediation workflow is:

```text
Vulnerability found
       |
       v
Investigate package
       |
       v
Update dependency/base image
       |
       v
Rebuild image
       |
       v
Rescan
       |
       v
Test
       |
       v
Deploy corrected image
```

Do not manually modify a running production container and assume the problem is permanently solved.

Fix the source artifact and rebuild.

---

# 80. Containers Should Be Rebuilt, Not Hand-Patched

Suppose:

```text
Container A
```

has a vulnerable library.

You enter the container and manually upgrade it.

That changes one running container.

But the original image remains unchanged.

When ECS replaces the container:

```text
Original vulnerable image
        |
        v
New vulnerable container
```

The proper model is:

```text
Fix source
→ Build new image
→ Scan
→ Test
→ Push
→ Deploy
```

This is part of immutable infrastructure thinking.

---

# 81. Lifecycle Policies

As you continuously push images, repositories can accumulate many old images.

For example:

```text
build-1001
build-1002
build-1003
...
build-5000
```

Not every image needs to remain forever.

ECR lifecycle policies can automatically expire images based on defined rules.

---

# 82. Why Lifecycle Policies Matter

Without cleanup:

```text
CI/CD
 |
 v
Push
Push
Push
Push
Push
 |
 v
Growing ECR Repository
```

This can increase:

* Storage consumption
* Cost
* Repository clutter
* Operational complexity

Lifecycle policies allow intentional retention.

---

# 83. Lifecycle Policy Example

A lifecycle policy uses JSON.

A simplified example concept might look like:

```json
{
  "rules": [
    {
      "rulePriority": 1,
      "description": "Expire older untagged images",
      "selection": {
        "tagStatus": "untagged",
        "countType": "imageCountMoreThan",
        "countNumber": 20
      },
      "action": {
        "type": "expire"
      }
    }
  ]
}
```

This is only an example policy.

Understand and test lifecycle rules before applying them to important repositories.

---

# 84. Understanding the Lifecycle Rule

```text
rulePriority
```

determines rule evaluation priority.

```text
description
```

explains the rule's intent.

```text
tagStatus: untagged
```

targets untagged images.

```text
imageCountMoreThan
```

uses an image-count retention rule.

```text
countNumber: 20
```

keeps the relevant count threshold.

```text
expire
```

causes matching images to become eligible for expiration according to the policy.

Do not copy lifecycle policies into production without reviewing what they will remove.

---

# 85. Why Untagged Images Exist

Suppose:

```text
latest → Image A
```

Then you push new content under:

```text
latest → Image B
```

depending on repository tag behavior and manifest relationships, previous image content may remain without that tag.

Repositories can therefore accumulate untagged image artifacts.

Lifecycle policies can help clean these up intentionally.

---

# 86. Be Careful With Image Deletion

An old image may still matter because:

* Production still uses it
* A rollback depends on it
* An audit requires it
* A deployment references its digest
* Another environment still runs it

Never design lifecycle rules using only:

```text
Old = useless
```

Retention should reflect deployment and rollback requirements.

---

# 87. IAM and ECR

ECR uses AWS IAM for authorization.

IAM determines which identities can perform actions such as:

```text
Create repositories
Describe repositories
Authenticate
Push images
Pull images
Delete images
Change lifecycle policies
```

This allows you to apply least privilege.

---

# 88. Least Privilege

Least privilege means:

```text
Give an identity only the permissions required for its job.
```

For example:

A CI build system may need:

```text
Push image
```

An ECS execution role may need:

```text
Pull image
```

A developer may need:

```text
Push and pull development images
```

A read-only deployment system should not automatically receive:

```text
Delete repository
```

permissions.

---

# 89. Permissions Needed for Pushing

A typical ECR push workflow involves actions such as:

```text
ecr:GetAuthorizationToken
ecr:BatchCheckLayerAvailability
ecr:GetDownloadUrlForLayer
ecr:BatchGetImage
ecr:InitiateLayerUpload
ecr:UploadLayerPart
ecr:CompleteLayerUpload
ecr:PutImage
```

The exact policy should reflect the workflow.

Do not memorize the list without understanding the categories.

Conceptually:

```text
Authenticate
+
Check image/layers
+
Upload layers
+
Register image
```

---

# 90. Permissions Needed for Pulling

A pull workflow commonly needs capabilities related to:

```text
Authenticate
Check image manifest
Download image layers
```

Examples include:

```text
ecr:GetAuthorizationToken
ecr:BatchGetImage
ecr:GetDownloadUrlForLayer
```

and related repository access as required.

Again, design permissions for the actual workload.

---

# 91. Resource-Level Permissions

Where supported, repository-specific permissions can limit access.

Instead of:

```text
Every repository
```

a deployment identity may only need:

```text
veriqta-web
```

This follows least privilege.

---

# 92. Repository Policies

ECR also supports repository policies.

Repository policies can be useful for controlling repository access, including scenarios such as cross-account access.

Conceptually:

```text
IAM Identity Permissions
+
ECR Repository Policy
```

can both influence whether an operation is authorized.

This becomes important in multi-account AWS architectures.

---

# 93. Cross-Account ECR Concept

Imagine:

```text
AWS Account A
Development/Build
```

and:

```text
AWS Account B
Production
```

You may design controlled cross-account access.

For example:

```text
Build Account
     |
     v
ECR Repository
     |
     v
Production Workload
```

Cross-account container distribution requires careful IAM and repository-policy design.

Do not solve it by sharing permanent credentials.

---

# 94. Never Bake AWS Credentials Into an Image

Do not put:

```text
AWS_ACCESS_KEY_ID
AWS_SECRET_ACCESS_KEY
```

inside:

* Dockerfile
* Application source
* Image layer
* Git repository

For example, never do this:

```dockerfile
ENV AWS_ACCESS_KEY_ID=...
ENV AWS_SECRET_ACCESS_KEY=...
```

This can expose credentials in image metadata, layers, registries, build logs, and source history.

Use IAM roles and appropriate secret-management mechanisms instead.

---

# 95. Secrets and Docker Builds

Be careful with:

```dockerfile
COPY . .
```

If your project contains:

```text
.env
credentials
private-key.pem
```

they may accidentally enter the build context or image.

Use:

```text
.dockerignore
```

but also design the application so secrets are supplied at runtime through secure mechanisms rather than baked into images.

# 98. Build Once, Deploy the Same Artifact

```text

Promote the same tested artifact.
```


```text

```

even though the application source commit appears unchanged.

# 101. CI Authentication

A CI/CD system needs permission to push images.

Avoid manually placing permanent AWS credentials into pipeline scripts.

Prefer temporary credentials obtained through secure identity mechanisms, such as appropriately configured roles and federation.

Conceptually:

```text
CI Platform
 |
 v
Trusted Identity Relationship
 |
 v
Temporary AWS Credentials
 |
 v
ECR
```

The exact mechanism depends on the CI platform and AWS architecture.

# 102. CI Pipeline Pseudoflow

A pipeline may logically perform:

```text
1. Checkout source
2. Run tests
3. Determine image version
4. Authenticate to AWS
5. Authenticate Docker to ECR
6. Build image
7. Scan/check image
8. Tag image
9. Push image
10. Record digest
11. Deploy or promote artifact
12. Verify deployment
```

Notice that deployment verification comes after image creation.

A successful push does not prove a successful deployment.

```text
→ Verify repository

→ Verify authorization
```

Use container logs as evidence.



```text
Yes.

Maybe.

Maybe.
```

# 123. Container Image Security Basics

For beginner production awareness:

* Use trusted base images.
* Keep base images updated.
* Scan images.
* Pin important dependencies appropriately.
* Avoid unnecessary packages.
* Do not bake secrets into images.
* Avoid running as root when the application does not require it.
* Use least-privilege IAM.
* Control who can push images.
* Use intentional tagging.
* Consider tag immutability.
* Apply lifecycle policies carefully.
* Rebuild when vulnerabilities are fixed.
* Keep deployment traceability.

# 124. Why Running as Root Matters

Containers often run processes with a user identity.

If the application does not require root privileges, running as a non-root user reduces unnecessary privilege.

A Dockerfile can define a user.

For example, conceptually:

```dockerfile
RUN useradd --create-home appuser

USER appuser
```

But permissions on files and directories must be configured correctly.

Do not add `USER` blindly without testing whether the application can read and write what it needs.

# 157. Final Mental Model

Do not memorize ECR as:

```text
ECR = somewhere Docker images are stored.
```

Understand the complete artifact lifecycle.

It begins with source code:

```text
Developer
    |
    v
Source Code
    |
    v
Dockerfile
    |
    v
docker build
    |
    v
Container Image
```

The image is tested:

```text
Container Image
    |
    v
docker run
    |
    v
Running Container
    |
    v
Application Test
```

Then published:

```text
Tested Image
    |
    v
docker tag
    |
    v
ECR Image Reference
    |
    v
docker push
    |
    v
Amazon ECR
```

Then consumed:

```text
Amazon ECR
    |
    v
Authenticated Pull
    |
    v
ECS / EKS / EC2
    |
    v
Container
    |
    v
Application
```

In a CI/CD environment:

```text
Developer
    |
    v
Git Push
    |
    v
CI/CD Pipeline
    |
    +-- Test
    |
    +-- Build
    |
    +-- Scan
    |
    +-- Tag
    |
    +-- Authenticate
    |
    +-- Push
    |
    v
Amazon ECR
    |
    v
Immutable Image/Digest
    |
    v
Deployment Platform
    |
    v
Running Application
```

When something fails, locate the failing stage.

```text
Source
  |
  v
Build
  |
  v
Local Image
  |
  v
Authentication
  |
  v
Authorization
  |
  v
Tag
  |
  v
Push
  |
  v
ECR
  |
  v
Pull
  |
  v
Container Start
  |
  v
Application
```

If `docker build` fails, investigate the Dockerfile, build context, dependencies, and build environment.

If `docker push` fails, investigate the image reference, authentication, IAM authorization, account, Region, repository, and networking.

If `docker pull` fails, investigate the requested image, tag or digest, registry authentication, IAM, and network path.

If the image pulls successfully but the application crashes, ECR has already done its job. Investigate the container and application.

The key lesson is:

```text
Docker builds the artifact.

ECR stores and distributes the artifact.

IAM controls who can access the artifact.

Image scanning helps inspect the artifact.

Lifecycle policies manage artifact retention.

CI/CD automates the artifact workflow.

ECS or EKS runs workloads from the artifact.
```

You should now be able to look at:

```text
Developer
    |
    v
Docker Build
    |
    v
Container Image
    |
    v
Amazon ECR
```

and understand exactly what happens at every stage.

The next step is to take the image stored in ECR and run it as a managed AWS container workload using ECS and then understand where EKS and Kubernetes fit into the AWS container ecosystem.
