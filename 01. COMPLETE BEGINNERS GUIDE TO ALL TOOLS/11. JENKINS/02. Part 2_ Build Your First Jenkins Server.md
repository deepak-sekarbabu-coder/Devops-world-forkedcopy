# 2. Jenkins Prerequisites

Before installing software, always ask:

> What does this software require in order to run?

For Jenkins, the important beginner requirements are:

* A supported operating system.
* A supported Java runtime.
* Memory.
* Disk space.
* Network access where needed.
* A web browser.
* Administrative or `sudo` privileges for installation.
* An available TCP port.

The Jenkins documentation currently lists 256 MB RAM and 1 GB disk as minimums, while recommending considerably more for real usage. For a small team, Jenkins documents 4 GB or more of RAM and 50 GB or more of disk as a recommended configuration. Those numbers are not promises about what your particular workload needs. Build workloads can consume much more. ([Jenkins][2])

For our learning environment, the important point is simply:

```text
Enough CPU/RAM
      +
Disk space
      +
Supported Java
      +
Operating system
      +
Browser
      =
Environment capable of running Jenkins
```

# 3. Why Does Jenkins Need Java?

Jenkins is a Java application.

That means the operating system does not simply execute Jenkins directly like an ordinary native executable.

It uses a Java runtime.

Conceptually:

```text
Operating System
      ↓
Java Runtime
      ↓
Jenkins
```

When you run:

```bash
java -version
```

you are checking whether a Java runtime is available.

This is different from:

```bash
jenkins --version
```

or checking the Jenkins package.

Java is a dependency required by Jenkins itself.

---

# 4. JRE vs JDK

Beginners often encounter these terms:

```text
JRE
JDK
```

A JRE provides what is needed to run Java applications.

A JDK includes development tools used to develop Java software, along with the runtime capabilities.

For simply running the Jenkins controller, you do not need to become a Java developer.

Our Ubuntu installation will use:

```text
openjdk-21-jre
```

The Jenkins Linux installation documentation currently uses OpenJDK 21 in its Debian/Ubuntu instructions. ([Jenkins][3])

---

# 5. Supported Java Versions Matter

A common beginner mistake is thinking:

> I have Java installed, therefore Jenkins will work.

Not necessarily.

Imagine:

```text
Jenkins version
      ↓
requires supported Java versions
```

If your Java version is unsupported, Jenkins may refuse to start.

Current Jenkins LTS releases from the 2.555.1 line support Java 21 and Java 25. Jenkins' support matrix changes over time, which is why old tutorials telling you to install Java 8, 11, or even 17 can be wrong for a current installation. ([Jenkins][1])

For this guide:

```text
Java 21
```

is our baseline.

# 6. Jenkins LTS vs Weekly Releases

Before installing Jenkins, you need to know that Jenkins has two release lines.

## LTS

LTS means:

```text
Long-Term Support
```

Jenkins periodically selects a release for its LTS line.

This is the release line we will use.

## Weekly

Jenkins also publishes regular weekly releases containing newer changes.

Conceptually:

```text
Jenkins
│
├── LTS
│    └── Stability-oriented release line
│
└── Weekly
     └── Faster-moving release line
```

For a beginner lab, use LTS unless you have a specific reason to test a weekly release.

# 8. First Understand Linux Package Installation

Before copying commands, understand what we are about to do.

Ubuntu and Debian use a package-management system built around APT.

You will encounter:

```bash
apt
```

APT helps the operating system:

* Discover packages.
* Download packages.
* Install packages.
* Resolve dependencies.
* Upgrade packages.
* Remove packages.

For example:

```bash
sudo apt install package-name
```

means:

```text
sudo
 ↓
run with elevated privileges

apt
 ↓
package management tool

install
 ↓
requested operation

package-name
 ↓
software package to install
```

# 9. What Is `sudo`?

You will see:

```bash
sudo
```

frequently.

Installing system software modifies protected areas of Linux.

Ordinary users should not automatically have permission to modify them.

`sudo` allows an authorized user to execute a command with elevated privileges.

For example:

```bash
sudo apt update
```

does not mean "`sudo` is part of APT."

It means:

```text
sudo
   ↓
execute with elevated privileges

apt update
   ↓
command being executed
```

Do not automatically add `sudo` to every Linux command.

Use elevated privileges only when required.

# 16. What Is a Package Repository?

We are about to add the Jenkins package repository.

Before doing that, understand what a repository is in this context.

A package repository is a source from which your package manager can retrieve software packages and metadata.

APT already knows about Ubuntu or Debian repositories.

But Jenkins packages are distributed through Jenkins' own package repository.

Conceptually:

```text
APT
│
├── Operating-system repositories
│
└── Jenkins repository
         ↓
      Jenkins package
```

We need to tell APT:

1. Where the Jenkins repository is.
2. How to verify packages from that repository.

---

# 17. Why Repository Signing Matters

Installing software from the internet is a security-sensitive operation.

APT uses cryptographic signing to verify repository metadata and packages.

We therefore install the Jenkins repository signing key and configure the repository to use that key.

This helps the system verify that the packages came through the expected Jenkins package distribution process and were not silently replaced in transit.

---

# 18. Add the Jenkins LTS Repository

The Jenkins project's current Debian/Ubuntu LTS instructions use the following repository setup. ([Jenkins][3])

Run:

```bash
sudo wget -O /etc/apt/keyrings/jenkins-keyring.asc \
  https://pkg.jenkins.io/debian-stable/jenkins.io-2026.key
```

Let's understand this.

`wget` retrieves a file over the network.

`-O` tells `wget` where to write the downloaded content.

The destination is:

```text
/etc/apt/keyrings/jenkins-keyring.asc
```

This is a system location used for APT repository key material.

Now configure the repository:

```bash
echo "deb [signed-by=/etc/apt/keyrings/jenkins-keyring.asc]" \
  https://pkg.jenkins.io/debian-stable binary/ | sudo tee \
  /etc/apt/sources.list.d/jenkins.list > /dev/null
```

This creates:

```text
/etc/apt/sources.list.d/jenkins.list
```

That file tells APT about the Jenkins LTS repository.

---

# 19. Inspect What You Created

Inspect the repository file:


You should see the Jenkins repository entry.

This is important.

You now understand that:


On Debian/Ubuntu, the package does more than place a single file somewhere.

The Jenkins package configures Jenkins as a system service, creates a `jenkins` user, integrates with `systemd`, directs console logging through `systemd-journald`, and configures Jenkins to listen on port 8080 by default. ([Jenkins][3])

Conceptually:

```text

       ↓

       ↓

       ↓
jenkins system user
       ↓
Jenkins configuration
       ↓
Jenkins home
       ↓
Port 8080
```

Let's investigate those pieces.

# 24. What Is a Linux Service?

A server application usually needs to run without someone manually opening a terminal and leaving it running.

Examples include:

```text
SSH server
Web server
Database
Jenkins
```

Linux can run these as services.

Instead of:

```text
Open terminal
Run Jenkins
Never close terminal
```

we want the operating system to manage Jenkins.

Conceptually:

```text
Linux
 ↓
Service Manager
 ↓
Jenkins Service
```

On modern Ubuntu/Debian systems, that service manager is typically `systemd`.

---

# 25. What Is `systemd`?

`systemd` manages many operating-system services and startup activities.

The command-line tool you commonly use to interact with services is:

```bash
systemctl
```

The pattern is:

```text
systemctl ACTION SERVICE
```

Examples:

```bash
sudo systemctl start jenkins
```

```bash
sudo systemctl stop jenkins
```

```bash
sudo systemctl restart jenkins
```

```bash
sudo systemctl status jenkins
```

The important distinction:

```text
systemd
= service-management system

systemctl
= command used to control/query systemd
```

# 29. Enable Jenkins at Boot

Starting Jenkins means:

```text
Run Jenkins now.
```

```text
Configure Jenkins to start automatically during system boot.
```

These are related but different operations.

Run:

```bash

```

```bash

```

Expected result:

```text

```

---

# 30. Start vs Enable

Remember this distinction:

| Command                        | Meaning                                   |
| ------------------------------ | ----------------------------------------- |
| `systemctl start jenkins`      | Start Jenkins now                         |
| `systemctl stop jenkins`       | Stop Jenkins now                          |
| `systemctl restart jenkins`    | Stop and start Jenkins                    |
| `systemctl status jenkins`     | Inspect current service status            |
| `systemctl enable jenkins`     | Configure automatic startup at boot       |
| `systemctl disable jenkins`    | Remove automatic startup at boot          |
| `systemctl is-enabled jenkins` | Check boot-start configuration            |
| `systemctl is-active jenkins`  | Check whether service is currently active |

Try:

```bash
systemctl is-active jenkins
```

A healthy running service should return:

```text
active
```

# 31. Meet the `jenkins` Linux User

The package creates a system account named:

```text
jenkins
```

Check it:

```bash
id jenkins
```

You should see information about the account.

Why does Jenkins have its own user?

Because running every server process as:

```text
root
```

would give that process excessive privileges.

Instead:

```text
Jenkins process
      ↓
jenkins account
      ↓
limited permissions
```

This is an early example of least privilege.

Later, this becomes important when Jenkins needs access to:

* Files.
* Docker.
* SSH keys.
* Deployment directories.
* Build tools.

A file that your personal Linux user can access is not automatically accessible to the `jenkins` user.

Remember that.

It will explain many future permission errors.

# 32. Understand Port 8080

Jenkins is running.

But how does your browser reach it?

Through a network port.

By default, Jenkins listens on:

```text
8080
```

Think of an IP address as identifying a machine and a port as identifying a network service on that machine.

For example:

```text
Machine
│
├── Port 22    → SSH
├── Port 80    → commonly HTTP
├── Port 443   → commonly HTTPS
└── Port 8080  → Jenkins in our default setup
```

Therefore:

```text
http://localhost:8080
```

means:

```text
http
 ↓
use HTTP

localhost
 ↓
this computer

8080
 ↓
connect to TCP port 8080
```

---

# 33. Verify Port 8080 From the Terminal

Do not rely only on the browser.

Run:

```bash
sudo ss -ltnp | grep 8080
```

Let's break that down.

`ss` displays socket information.

`-l` asks for listening sockets.

`-t` asks for TCP sockets.

`-n` shows numeric addresses and ports.

`-p` requests process information.

`grep 8080` filters the output for `8080`.

If Jenkins is listening, you should see a matching listening socket.

Exact output varies.

The important idea is:

```text
Jenkins service running
        +
port 8080 listening
```

gives stronger evidence than simply assuming the service is reachable.

---

# 34. Localhost vs Remote Server

If Jenkins runs on the same computer as your browser, use:

```text
http://localhost:8080
```

But suppose Jenkins runs on another machine:

```text
Your Laptop
    ↓
Network
    ↓
Linux Server
    ↓
Jenkins
```

Then `localhost` in your laptop's browser refers to your laptop, not the remote Jenkins server.

You would need the server's reachable hostname or IP address, for example:

```text
http://server-address:8080
```

Whether that works also depends on:

* Firewall rules.
* Cloud security rules.
* Routing.
* Jenkins binding.
* Network accessibility.

We will handle cloud networking properly later in the course.

Do not expose port 8080 publicly just because it makes the lab easier.

# 36. The Initial Administrator Password

On the standard Linux package installation, the password is stored at:

```text
/var/lib/jenkins/secrets/initialAdminPassword
```

Retrieve it with:

```bash
sudo cat /var/lib/jenkins/secrets/initialAdminPassword
```

Jenkins' official installation documentation uses this location for Linux package installations. ([Jenkins][4])

You will see a long value.

Example only:

```text
e18f5a...
```

Do not copy the example.

Use the password generated by your Jenkins installation.

---

# 37. Why Do We Need `sudo` to Read It?

Try thinking about the security model.

This file contains sensitive information.

It should not be readable by every random user on the machine.

You can inspect its permissions:

```bash
sudo ls -l /var/lib/jenkins/secrets/initialAdminPassword
```

This reinforces an important principle:

```text
Sensitive Jenkins files
      ↓
restricted filesystem permissions
```

Do not change permissions to something insecure just because reading the file is inconvenient.

```text
Jenkins Web UI
      ↓
persistent configuration/state
      ↓
JENKINS_HOME
```

# 49. Why Jenkins Home Matters

Imagine the Jenkins server disappears.

What would you need to recover?

Possibly:

* Job definitions.
* Jenkins configuration.
* Plugin state.
* User-related configuration.
* Credentials-related state.
* Build information.
* Other Jenkins metadata.

Much of this lives under `JENKINS_HOME`.

We will study backup and recovery later.

For now:

> `/var/lib/jenkins` is not a disposable random folder on a production controller.

# 51. System-Level Jenkins Service Configuration

## Jenkins application state

Primarily associated with:


For our package installation:

```text
/var/lib/jenkins
```

## Linux service configuration

Associated with `systemd`.

Inspect it with:


```text

└── systemd
     └── starts Jenkins
           ↓
        Jenkins
           └── uses JENKINS_HOME
```

One layer controls how the process starts.

The other contains Jenkins application state.

# 52. Jenkins Logs

There may be many lines.

Do not try to memorize everything.

# 60. Restarting Jenkins Safely

In our empty learning installation, restarting Jenkins is simple.

# 61. What If Port 8080 Is Already Used?

Suppose Jenkins fails to start.

You inspect:

```bash
sudo systemctl status jenkins
```

and then:

```bash

```

Evidence suggests port 8080 cannot be used.

First investigate:

```bash
sudo ss -ltnp | grep :8080
```

Another application may already be listening.

The question becomes:

```text
Which process owns port 8080?
```

not:

```text
Why is Jenkins broken?
```

The root cause may be a port conflict.

# 62. Changing the Jenkins Port With systemd

Current Jenkins Linux documentation recommends using a `systemd` override when changing service settings such as the port. For example, if 8080 is occupied, Jenkins documents creating an override containing `JENKINS_PORT=8081`. ([Jenkins][3])

Run:

```bash
sudo systemctl edit jenkins
```

Add:

```ini
[Service]
Environment="JENKINS_PORT=8081"
```

Save and exit.

Then restart Jenkins:

```bash
sudo systemctl restart jenkins
```

Verify:

```bash
sudo systemctl status jenkins
```

Check the new port:

```bash
sudo ss -ltnp | grep 8081
```

Then access:

```text
http://localhost:8081
```

Do this only if you actually need a different port. There is no benefit in randomly changing ports during the basic lab.

---

# 63. Why Use a systemd Override?

You might wonder:

> Why not directly edit the packaged service file?

Because package-managed files may be replaced or changed during package upgrades.

Overrides allow you to keep local configuration separate from the vendor-supplied service definition.

Conceptually:

```text
Vendor service definition
        +
Local override
        ↓
Effective service configuration
```

This is a much better operational habit than randomly editing files under package-managed locations.

# 64. Firewall Considerations

A service listening on port 8080 does not automatically mean every other computer can reach it.

A firewall may block traffic.

On a local learning machine using:

```text
localhost
```

you may not need any firewall change.

On a remote Linux server, you may need an appropriate network rule.

But do not respond by blindly opening:

```text
8080 to the entire internet
```

That is especially dangerous for administrative systems.

A production design should intentionally control who can reach Jenkins.

# 65. First Jenkins Security Considerations

You now have a powerful automation server.

Treat it accordingly.

Jenkins may eventually gain access to:

```text
Source repositories
Cloud accounts
Container registries
SSH servers
Kubernetes clusters
Production environments
```

That means Jenkins can become a high-value target.

At minimum, understand these principles from day one.

### Do not expose Jenkins unnecessarily

A learning server does not need unrestricted internet exposure.

### Do not run everything as root

Our package runs Jenkins using the dedicated `jenkins` account.

Keep that separation.

### Use strong administrator credentials

Do not use trivial passwords.

### Keep Jenkins updated

Old server software can contain known vulnerabilities.

### Keep plugins controlled

Plugins are software too.

### Do not install random plugins

Every plugin adds code and maintenance responsibility.

### Do not hardcode secrets

Later we will use Jenkins Credentials properly.

### Use HTTPS for real remote environments

Our:

```text
http://localhost:8080
```

is a local learning setup.

Do not interpret it as a recommended internet-facing production architecture.

# 71. Image vs Container

Since Docker may be new to some learners:

```text

```

is the packaged template.

```text

```

is a running instance created from an image.

Think:

```text
Jenkins image
     ↓
docker run
     ↓
Jenkins container
```

The official Jenkins Docker documentation describes the image as the packaged application and the container as its running instance. ([Jenkins][7])

# 72. Jenkins Data in Docker

Containers should not be treated as permanent storage by default.

If your Jenkins container disappears and all important state existed only in its writable container layer, you could lose your Jenkins configuration.

Therefore, persistent storage is important.

Conceptually:

```text
Jenkins Container
       ↓
Persistent Volume
       ↓
/var/jenkins_home
```

The official Jenkins Docker examples persist `/var/jenkins_home` through a volume. ([Jenkins][7])

This is the container equivalent of understanding:

```text
JENKINS_HOME
```

on a normal installation.

# 94. Knowledge Check Answers

### Answer 1

Jenkins is a Java application and requires a supported Java runtime to execute.

### Answer 2

Jenkins depends on Java. Installing the dependency first avoids starting Jenkins without the runtime it needs.

### Answer 3

A package repository provides packages and package metadata to a package manager such as APT.

### Answer 4

Repository signing helps APT verify the software source and integrity/authenticity of repository metadata used during package installation.

### Answer 5

`systemd` is the service and system manager used by many modern Linux distributions.

### Answer 6

`systemctl` is a command-line interface used to inspect and control `systemd` units such as the Jenkins service.

### Answer 7

Starting Jenkins runs it now. Enabling Jenkins configures it to start automatically during system boot.

### Answer 8

It is the default TCP port on which our Jenkins HTTP service listens.

### Answer 9

`JENKINS_HOME` is Jenkins' main persistent application-data directory.

### Answer 10

For the standard Debian/Ubuntu package installation:

```text
/var/lib/jenkins
```

### Answer 11

Use the `systemd` journal, commonly through:

```bash
journalctl -u jenkins.service
```

### Answer 12

A dedicated service account limits Jenkins' operating-system privileges instead of unnecessarily running it as root.

### Answer 13

It can grant excessive filesystem permissions and create serious security problems instead of fixing the actual ownership or permission issue.

### Answer 14

Start with service status and logs, then investigate dependencies such as Java, port conflicts, disk space, configuration, and permissions according to the evidence.

### Answer 15

A firewall, routing problem, wrong hostname/IP, wrong port, cloud network rule, or similar network issue may prevent the client from reaching the service.

```text
Jenkins unavailable
       ↓
Is service active?
       │
   ┌───┴────┐
   │        │
  NO       YES
   │        │
   ↓        ↓
Check     Is port
logs      listening?
   │        │
   ↓     ┌──┴───┐
Java?    NO     YES
Port?     │      │
Config?   ↓      ↓
Disk?   Check   Check
Perms?  logs    network/client
```

More concretely:

```text
1. systemctl status jenkins
             ↓
2. journalctl -u jenkins.service
             ↓
3. java -version
             ↓
4. ss -ltnp
             ↓

             ↓

             ↓

             ↓
8. restart if required
             ↓
9. verify service
             ↓
10. verify port
             ↓
11. verify browser
```

This troubleshooting pattern is more important than memorizing any single Jenkins error.
