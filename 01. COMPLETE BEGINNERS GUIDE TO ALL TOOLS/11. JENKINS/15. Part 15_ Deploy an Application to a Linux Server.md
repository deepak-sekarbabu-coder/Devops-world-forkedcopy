# 1. What Is Deployment?

Deployment is the process of making a particular version of software available in a target environment.

That definition is deliberately broader than:

```text
copy files to server
```

A real deployment may involve:

```text
Select artifact
↓
Authenticate to target
↓
Retrieve artifact
↓
Apply configuration
↓
Start application
↓
Verify application
↓
Record deployed version
↓
Handle failure
```

For our containerized application:

```text
Deployment
=
Pull exact Docker image
+
Configure container
+
Start container
+
Verify health
```

---

# 2. Build Is Not Deployment

This distinction is essential.

## Build

Takes source code and produces an artifact.

```text
Source
↓
Build
↓
Artifact
```

## Deployment

Takes an artifact and makes it run in a target environment.

```text
Artifact
↓
Target Environment
↓
Running Application
```

Together:

```text
Source
↓
Build
↓
Artifact
↓
Deployment
↓
Running Application
```

---

# 3. Why Separate Build and Deployment?

Imagine Jenkins creates:

```text
docker.io/veriqta/veriqta-docker-app:105-a12b34c56d78
```

That image should not need to be rebuilt just because we want to run it somewhere else.

Instead:

```text
Build Once
↓
Store
↓
Deploy Same Artifact
```

The same image can move through:

```text
Development
↓
Staging
↓
Production
```

with environment-specific configuration supplied separately.


# 5. Jenkins Server and Deployment Server Are Different

Do not confuse:

```text
Jenkins Agent
```

with:

```text
Application Server
```

The Jenkins agent performs CI work.

For example:

```text
Checkout
Build
Test
Docker build
Registry push
```

The application server performs runtime work:

```text
Pull image
Run application
Serve traffic
Produce runtime logs
```

A realistic architecture separates those responsibilities.

Better:

```text

→ automation

→ artifact storage

→ application runtime
```

Separation improves:


# 13. What Is SSH?

SSH stands for:

```text
Secure Shell
```

SSH provides encrypted remote access to another machine.

Instead of physically sitting at the server, you can execute:

```bash
ssh user@server
```

Conceptually:

```text
Your Computer
   ↓
Encrypted SSH Connection
   ↓
Remote Linux Server
   ↓
Shell
```

Jenkins can use the same protocol.

Jenkins needs a way to tell the deployment server:

```text

Start this exact image.

```

SSH gives Jenkins a secure remote command channel.

Architecture:

```text
Jenkins
   ↓
SSH
   ↓

   ↓

```

# 20. SSH Authentication

The server needs to determine:

> Who is connecting?

SSH supports several authentication mechanisms.

For automated deployment, we will use:

```text
Public-key authentication
```

rather than interactive password entry.

---

# 21. Public and Private Keys

An SSH key pair contains:

```text
Private Key
Public Key
```

The private key must remain private.

The public key can be placed on servers you want the identity to access.

Mental model:

```text
Jenkins
Private Key
   │
   │ proves possession
   ▼
Linux Server
Public Key
```

---

# 22. Never Copy the Private Key to the Deployment Server

The deployment server needs the public key.

Not:

```text
private key
```

The private key belongs to the client identity.

For our architecture:

```text
Jenkins Credentials Store
→ private key

Linux Server
→ public key
```

# 23. Create a Dedicated Deployment User

Do not make Jenkins log in as:

```text
root
```

for ordinary application deployment.

Create a dedicated account.

On the deployment server:

```bash
sudo adduser deploy
```

Follow the prompts.

For automation, the important account is:

```text
deploy
```

---

# 24. Why a Dedicated User?

It provides clearer boundaries.

Instead of:

```text
Jenkins
→ root
→ can modify everything
```

we want:

```text
Jenkins
→ deploy
→ deployment-related permissions
```

This supports least privilege.

---

# 25. The Deployment User Still Needs Permissions

Our deployment process needs to run:

```text
docker pull
docker run
docker stop
docker rm
docker inspect
docker logs
```

The user therefore needs an authorized method of interacting with Docker.

One beginner lab approach is adding:

```text
deploy
```

to the Docker group.

For example:

```bash
sudo usermod -aG docker deploy
```

Then the user must start a new login session for group membership to take effect.

---

# 26. Important Docker Group Security Warning

Membership in the Docker group is highly privileged.

A user able to control the Docker daemon can often obtain capabilities effectively equivalent to root on the host.

Therefore:

```text
deploy in docker group
```

is convenient for our controlled lab, but it is not a trivial permission.

Treat that account as highly trusted.

In production, organizations may use more restrictive deployment architectures, rootless containers, orchestrators, controlled `sudo`, or deployment agents.

---

# 30. Create a Dedicated SSH Key Pair

Create the deployment key on a secure administrative machine.

Example:

```bash
ssh-keygen \
  -t ed25519 \
  -f jenkins-deploy-key \
  -C "jenkins-deployment"
```

You will get:

```text
jenkins-deploy-key
jenkins-deploy-key.pub
```

The first file is private.

The `.pub` file is public.

---

# 31. Protect the Private Key

Check:

```bash
ls -l jenkins-deploy-key*
```

The private key must not be publicly readable.

Never:

```bash
cat jenkins-deploy-key
```

into a public terminal recording, issue, README, chat, or repository.

Never commit it.

---

# 32. Install the Public Key on the Deployment Server

For the `deploy` account, create:

```text
/home/deploy/.ssh
```

if needed.

Run as the appropriate administrator:

```bash
sudo install \
  -d \
  -m 700 \
  -o deploy \
  -g deploy \
  /home/deploy/.ssh
```

Append the public key to:

```text
/home/deploy/.ssh/authorized_keys
```

Then ensure permissions:

```bash
sudo chown deploy:deploy \
  /home/deploy/.ssh/authorized_keys

sudo chmod 600 \
  /home/deploy/.ssh/authorized_keys
```

SSH can reject keys when ownership or permissions are unsafe.


# 35. Why Use a Credential ID?

The Jenkinsfile should contain:

```text
linux-deployment-ssh
```

not:

```text

...
```

The Pipeline references the secret.

It does not contain the secret.

# 36. SSH Agent Plugin

One practical Jenkins approach is the SSH Agent plugin.

It provides:

```groovy
sshagent(credentials: ['linux-deployment-ssh']) {
    sh '''
        ssh deploy@server hostname
    '''
}
```

The plugin requires `ssh-agent` to be available on the Jenkins agent executing the step and works with private-key credentials.

---

# 37. Alternative: `withCredentials`

You can also bind an SSH private key to a temporary file:

```groovy
withCredentials([
    sshUserPrivateKey(
        credentialsId: 'linux-deployment-ssh',
        keyFileVariable: 'SSH_KEY',
        usernameVariable: 'SSH_USER'
    )
]) {
    sh '''
        ssh -i "$SSH_KEY" "$SSH_USER@$DEPLOY_HOST" hostname
    '''
}
```

Jenkins documents this credential binding approach as well.

Be aware that secret files and environment bindings on shared multi-executor agents require careful isolation.

# 39. Authentication Is Only Half of SSH Security

Suppose Jenkins connects to:

```text
203.0.113.10
```

How does Jenkins know it is actually talking to the intended server?

This introduces:

```text
SSH host verification
```

---

# 40. Server Identity

SSH authenticates in both directions conceptually.

The server asks:

```text
Who are you?
```

The client proves its user identity.

But the client should also ask:

```text
Who is this server?
```

That is where SSH host keys matter.

---

# 41. First SSH Connection

When humans connect to a new SSH server, they often see something like:

```text
The authenticity of host ... can't be established.
...
Are you sure you want to continue connecting?
```

SSH is asking whether you trust the presented host key.

After acceptance, the key is normally recorded in:

```text
~/.ssh/known_hosts
```

---

# 42. What Is `known_hosts`?

`known_hosts` stores trusted SSH host-key information.

Conceptually:

```text
Hostname
↓
Expected Host Key
```

On future connections:

```text
Presented key
   ↓
Compare
   ↓
Known key
```

If they differ unexpectedly, SSH warns you.

---

# 43. Why Host Verification Matters

Without host verification, an attacker positioned between Jenkins and the deployment server could potentially impersonate the target.

The danger becomes:

```text
Jenkins
↓
Attacker pretending to be server
↓
Deployment commands / sensitive interactions
```

SSH host verification helps detect this.

---

# 44. Do Not Solve This With `StrictHostKeyChecking=no`

You will see examples online like:

```bash
ssh \
  -o StrictHostKeyChecking=no \
  deploy@server
```

This is convenient for disposable demos.

It weakens host identity verification and should not be the normal solution for production deployment.

Our project will create a controlled:

```text
known_hosts
```

file.

---

# 45. Obtain the Deployment Server Host Key Safely

The strongest principle is:

> Verify the server's SSH host-key fingerprint through a trusted path before trusting it.

On the deployment server itself, an administrator can inspect host-key fingerprints.

For example:

```bash
sudo ssh-keygen \
  -lf \
  /etc/ssh/ssh_host_ed25519_key.pub
```

Representative output includes a fingerprint.

Record it through your trusted administrative process.

---

# 46. `ssh-keyscan`

`ssh-keyscan` can retrieve a server's public host key:

```bash
ssh-keyscan YOUR_SERVER
```

But understand the limitation.

If you simply retrieve a key from an untrusted network and immediately trust whatever was returned, you have not independently proven the server's identity.

Use a trusted fingerprint or trusted provisioning source to verify it.

---

# 47. Create Jenkins `known_hosts`

On the Jenkins agent, we can maintain a controlled file such as:

```text
$WORKSPACE/.ssh/known_hosts
```

For a simple lab:

```bash
mkdir -p "$WORKSPACE/.ssh"
chmod 700 "$WORKSPACE/.ssh"

ssh-keyscan \
  -H \
  "$DEPLOY_HOST" \
  > "$WORKSPACE/.ssh/known_hosts"

chmod 600 \
  "$WORKSPACE/.ssh/known_hosts"
```

Then verify the captured fingerprint against the fingerprint obtained through your trusted path before relying on it.

For mature production automation, host keys are better provisioned from trusted configuration rather than dynamically trusting whatever a network scan returns during every deployment.

---

# 48. Use the Known Hosts File

SSH can be told explicitly:

```bash
ssh \
  -o BatchMode=yes \
  -o StrictHostKeyChecking=yes \
  -o UserKnownHostsFile="$KNOWN_HOSTS" \
  deploy@server \
  hostname
```

Important options:

```text
BatchMode=yes
→ do not prompt interactively

StrictHostKeyChecking=yes
→ reject unknown/unexpected hosts

UserKnownHostsFile=...
→ use the specified trusted host file
```

---

# 49. Why `BatchMode=yes`?

A Jenkins Pipeline cannot safely depend on an interactive prompt such as:

```text
Password:
```

or:

```text
Are you sure you want to continue connecting?
```

Automation should either:

```text
succeed non-interactively
```

or:

```text
fail clearly
```

---

# 50. First Remote Command

Once credentials and host verification are configured:

```groovy
sshagent(credentials: ['linux-deployment-ssh']) {
    sh '''
        ssh \
          -o BatchMode=yes \
          -o StrictHostKeyChecking=yes \
          -o UserKnownHostsFile="$KNOWN_HOSTS" \
          "$DEPLOY_USER@$DEPLOY_HOST" \
          hostname
    '''
}
```

Expected result:

```text
deployment-server-hostname
```

You have now proven:

```text

↓
SSH authentication
↓
Host verification
↓
Linux Server
```

---

# 56. Container Port vs Host Port

Suppose the application listens inside the container on:

```text
5000
```

Running:

```bash
docker run \
  -p 8080:5000 \
  image
```

means:

```text
Host Port 8080
      ↓
Container Port 5000
```

Users connect to:

```text
SERVER:8080
```

The application inside the container receives traffic on:

```text
5000
```

---

# 57. Port Publishing Syntax

The basic syntax is:

```text
-p HOST_PORT:CONTAINER_PORT
```

Example:

```bash
docker run \
  -p 8080:5000 \
  "$IMAGE"
```

Architecture:

```text
Client
↓
Linux Server :8080
↓
Docker Port Publishing
↓
Container :5000
↓
Application
```

---

# 58. Binding to All Interfaces

A command such as:

```bash
docker run \
  -p 8080:5000 \
  image
```

normally publishes the host port broadly according to Docker's networking behavior.

That may make it reachable beyond localhost depending on the server/network/firewall.

Do not expose ports accidentally.

---

# 59. Bind to Loopback When External Access Is Not Required

If only the server itself or a local reverse proxy needs direct access:

```bash
docker run \
  -p 127.0.0.1:8080:5000 \
  image
```

This binds the published port to loopback.

Architecture:

```text
External Client
   X
   │
127.0.0.1:8080
   ↓
Container :5000
```

This can be safer when a reverse proxy will handle external traffic.

---

# 60. Important Docker Firewall Warning

Docker manages firewall rules for container networking and published ports. Docker's official documentation warns that published container ports can interact with firewall tooling such as `ufw` in ways beginners may not expect. Do not assume a simple `ufw` rule necessarily controls Docker-published traffic the way you imagine.

This is extremely important in production.

---

# 61. Do Not Publish Unnecessary Ports

If the application only needs:

```text
8080
```

do not expose:

```text
database port
debug port
internal metrics port
administrative port
```

unless the architecture requires them and network controls are properly designed.

# 65. Private Registry Authentication


permission.

It usually does not need:

```text
push
delete
admin
```

This is an important least-privilege distinction from Part 14.

Use separate credentials where practical:

```text
Jenkins Publisher Credential
→ push

Deployment Pull Credential
→ pull
```

---

# 66. Do Not Reuse Administrator Registry Credentials

Bad:

```text
one registry administrator credential
↓
Jenkins
↓
deployment server
↓
developer machines
↓
everything
```

Better:

```text
CI Publisher
→ scoped write access

Deployment Server
→ scoped read access

Administrator
→ separate administrative identity
```

---

# 67. Registry Credentials on the Deployment Host

There are several architectural approaches.

For this beginner project, Jenkins can temporarily provide a pull credential during deployment.

The deployment server can:

```text
authenticate
↓
pull image
↓
logout
```

However, passing secrets through remote shell commands requires careful handling.

A stronger production design may use:

```text
cloud workload identity
instance identity
short-lived registry token
credential helper
host secret manager
orchestrator-managed image pull credentials
```

Part 16 will introduce cloud-specific identity concepts.

# 68. Keep Registry Secrets Out of SSH Arguments

Avoid commands such as:

```bash

  "docker login -u user -p SuperSecret registry"
```

The secret may appear in:

```text
process arguments
Pipeline logs
shell history
debugging output
```

We need a safer pattern.

---

# 69. Safer Remote Registry Login Pattern

One beginner pattern is to send the token through standard input to the remote `docker login --password-stdin`.

Conceptually:

```text
Jenkins Secret
↓
Standard Input
↓
SSH
↓
docker login --password-stdin
```

But shell quoting and Pipeline logging must be handled carefully.

Do not use Groovy string interpolation to insert the secret directly into a command.

# 70. Pull Before Changing the Running Application

A critical deployment principle:

> Do not stop the currently running application before proving that the new artifact can at least be retrieved.

Bad:

```text
Stop production
↓
Try to pull new image
↓
Registry unavailable
↓
Application remains down
```

Better:

```text
Pull new image
↓
Verify image exists locally
↓
Then replace application
```


```text
↓

↓

↓
```

# 91. Health Verification

A deployment is not successful merely because:

```bash
docker run
```

returned zero.

You must verify the application.

We need multiple levels.

---

# 92. Level 1: Container Exists

```bash
docker ps \
  --filter "name=^/veriqta-docker-app$"
```

This shows whether Docker reports the container as running.

But:

```text
container running
≠
application healthy
```

---

# 93. Level 2: Inspect Container State

```bash
docker inspect \
  veriqta-docker-app
```

For a simpler check:

```bash
docker inspect \
  --format '{{.State.Running}}' \
  veriqta-docker-app
```

Expected:

```text
true
```

Still not enough.

---

# 94. Level 3: Application Health Endpoint

Call:

```bash
curl \
  --fail \
  --silent \
  --show-error \
  http://127.0.0.1:8080/health
```

Expected response depends on the application.

For our example it may be:

```text
healthy
```

or a JSON response.

This proves the application can answer HTTP requests.

---

# 95. Level 4: External Verification

If the application should be reachable from outside the server, Jenkins or another monitoring point can call:

```text
http://SERVER:8080/health
```

provided:

```text
routing
firewall
port publishing
security policy
```

allow it.

This verifies more of the network path.

---

# 96. Retry Health Checks

Applications may need a few seconds to start.

Do not immediately declare failure after one request.

Use bounded retries.

Example:

```bash
attempt=1

while [ "$attempt" -le 15 ]; do
    if curl \
        --fail \
        --silent \
        --show-error \
        http://127.0.0.1:8080/health; then

        echo
        echo "Health check passed."
        exit 0
    fi

    attempt=$((attempt + 1))
    sleep 2
done

echo "Health check failed."
exit 1
```

Maximum wait:

```text
approximately 30 seconds
```

---

# 97. Why Bounded Retries?

Bad:

```text
retry forever
```

If the application will never become healthy, Jenkins could hang indefinitely.

Better:

```text
retry N times
↓
fail
↓
collect evidence
↓
rollback or alert
```

```bash
docker logs \
```


Follow interactively during manual investigation:


# 105. First `deploy.sh`

Create:

```text
scripts/deploy.sh
```

with:

```bash
#!/usr/bin/env bash

set -euo pipefail

IMAGE_REF="${1:?image reference required}"
CONTAINER_NAME="${2:-veriqta-docker-app}"
HOST_PORT="${3:-8080}"
CONTAINER_PORT="${4:-5000}"

echo "Deploying:"
echo "  Image: $IMAGE_REF"
echo "  Container: $CONTAINER_NAME"
echo "  Host port: $HOST_PORT"
echo "  Container port: $CONTAINER_PORT"

echo "Pulling image..."
docker pull "$IMAGE_REF"

echo "Verifying image..."
docker image inspect "$IMAGE_REF" >/dev/null

echo "Removing existing container if present..."
docker rm -f "$CONTAINER_NAME" >/dev/null 2>&1 || true

echo "Starting application..."
docker run \
  --name "$CONTAINER_NAME" \
  --detach \
  --restart unless-stopped \
  --publish "${HOST_PORT}:${CONTAINER_PORT}" \
  "$IMAGE_REF"

echo "Waiting for application..."

attempt=1

while [ "$attempt" -le 15 ]; do
    if curl \
        --fail \
        --silent \
        --show-error \
        "http://127.0.0.1:${HOST_PORT}/health"; then

        echo
        echo "Application is healthy."
        exit 0
    fi

    attempt=$((attempt + 1))
    sleep 2
done

echo "Application failed health verification."

echo "Container state:"
docker ps -a \
  --filter "name=^/${CONTAINER_NAME}$" || true

echo "Container logs:"
docker logs \
  --tail 100 \
  "$CONTAINER_NAME" || true

exit 1
```

---

# 106. Make the Script Executable

Run:

```bash
chmod +x scripts/deploy.sh
```

Verify:

```bash
ls -l scripts/deploy.sh
```

You should see executable permissions.

---

# 107. What `set -euo pipefail` Does

This is common defensive shell behavior.

## `-e`

Exit when an unhandled command fails.

## `-u`

Treat an unset variable as an error.

## `pipefail`

A pipeline can fail when one of its component commands fails rather than hiding certain failures behind the final command.

It is not magic.

You still need deliberate error handling where failure is expected.

---

# 108. Why `|| true` Appears

This line:

```bash
docker rm -f "$CONTAINER_NAME" \
  >/dev/null 2>&1 || true
```

means:

```text
Try to remove existing container.

If it does not exist:
continue.
```

That is intentional.

An absent old container is not a deployment failure.

---

# 109. Introduction to Idempotency

Idempotency means, approximately:

> Running the same operation repeatedly should converge on the same desired state rather than creating uncontrolled duplicates or breaking because it already ran.

Consider:

```bash
docker run \
  --name veriqta-docker-app \
  image
```

Run once:

```text
works
```

Run again:

```text
name conflict
```

That deployment is not safely repeatable.

---

# 110. More Idempotent Behavior

Our script performs:

```text
Pull desired image
↓
Remove existing named container if present
↓
Create desired named container
↓
Verify
```

Run it again with the same image:

```text
Pull desired image
↓
Replace same container
↓
Run same image
↓
Verify
```

It converges toward:

```text
veriqta-docker-app
running
with desired image
```

This is a beginner introduction to idempotency.

---

# 111. Idempotent Does Not Mean Perfect

Our script still:

```text
restarts the container every time
```

even when the desired version is already running.

A more sophisticated deployment tool might detect:

```text
desired image already active
```

and perform no replacement.

Idempotency exists on a spectrum of implementation quality.

The important beginner habit is:

```text
deployment scripts must understand existing state
```

On the server:

```bash
docker inspect \
```

Representative result:

```text
docker.io/veriqta/veriqta-docker-app:104-f00ba4123456
```

# 113. Record Previous Version Before Deployment

Before removing the old container:

```bash
PREVIOUS_IMAGE="$(
  docker inspect \
    --format '{{.Config.Image}}' \

```

Then:

```bash
if [ -n "$PREVIOUS_IMAGE" ]; then

fi
```

This gives us the foundation for rollback.

---

# 114. Rollback Fundamentals

Rollback means returning to a previously known-good application version after a failed deployment.

Example:

```text
Current:
104-good

Deploy:
105-new

105 fails

Rollback:
104-good
```

This is why Part 14 retention mattered.

If you deleted:

```text
104-good
```

from the registry, rollback becomes harder.

---

# 115. Rollback Is Not "Undo Git"

Deployment rollback is about runtime state.

You may use Git history to understand code history.

But the rollback artifact should ideally be:

```text
previously built
previously tested
previously stored
known-good image
```

not:

```text
old commit rebuilt during incident
```

---

# 116. Simple Rollback Sequence

If new deployment fails:

```text
Stop failed new container
↓
Remove failed container
↓
Pull previous image if needed
↓
Start previous image
↓
Health-check previous version
↓
Report deployment failure
```

Important:

```text
Rollback success
```

does not mean:

```text
new deployment succeeded
```

The Pipeline should still report that the attempted deployment failed.

---

# 117. Why?

Suppose version 105 fails but rollback to 104 succeeds.

The system is available again.

But:

```text
105
```

was not successfully deployed.

Jenkins should communicate that truth.

# 118. Improve the Deployment Script With Rollback

Use:

```bash
#!/usr/bin/env bash

set -euo pipefail

IMAGE_REF="${1:?image reference required}"
CONTAINER_NAME="${2:-veriqta-docker-app}"
HOST_PORT="${3:-8080}"
CONTAINER_PORT="${4:-5000}"
METADATA_DIR="${5:-/opt/veriqta/app}"

CURRENT_IMAGE_FILE="${METADATA_DIR}/current-image"
PREVIOUS_IMAGE_FILE="${METADATA_DIR}/previous-image"

mkdir -p "$METADATA_DIR"

echo "========================================"
echo "VERIQTA Deployment"
echo "========================================"
echo "Target image: $IMAGE_REF"
echo "Container: $CONTAINER_NAME"
echo "Host port: $HOST_PORT"
echo "Container port: $CONTAINER_PORT"

PREVIOUS_IMAGE="$(
  docker inspect \
    --format '{{.Config.Image}}' \
    "$CONTAINER_NAME" \
    2>/dev/null || true
)"

if [ -n "$PREVIOUS_IMAGE" ]; then
    echo "Currently running image: $PREVIOUS_IMAGE"

    printf '%s\n' \
      "$PREVIOUS_IMAGE" \
      > "$PREVIOUS_IMAGE_FILE"
else
    echo "No existing application container found."
fi

echo "Pulling target image..."

docker pull "$IMAGE_REF"

echo "Verifying target image..."

docker image inspect \
  "$IMAGE_REF" \
  >/dev/null

echo "Removing existing container..."

docker rm -f \
  "$CONTAINER_NAME" \
  >/dev/null 2>&1 || true

echo "Starting target image..."

docker run \
  --name "$CONTAINER_NAME" \
  --detach \
  --restart unless-stopped \
  --publish "${HOST_PORT}:${CONTAINER_PORT}" \
  --env APP_ENV=production \
  "$IMAGE_REF"

echo "Waiting for health verification..."

attempt=1
deployment_healthy=false

while [ "$attempt" -le 15 ]; do
    if curl \
        --fail \
        --silent \
        --show-error \
        "http://127.0.0.1:${HOST_PORT}/health" \
        >/dev/null; then

        deployment_healthy=true
        break
    fi

    echo "Health attempt ${attempt}/15 failed."

    attempt=$((attempt + 1))
    sleep 2
done

if [ "$deployment_healthy" = true ]; then
    echo "Deployment health check passed."

    printf '%s\n' \
      "$IMAGE_REF" \
      > "$CURRENT_IMAGE_FILE"

    echo "Current image recorded:"
    cat "$CURRENT_IMAGE_FILE"

    exit 0
fi

echo "Deployment health check failed."

echo "Failed container state:"

docker ps -a \
  --filter "name=^/${CONTAINER_NAME}$" || true

echo "Failed container logs:"

docker logs \
  --tail 100 \
  "$CONTAINER_NAME" || true

if [ -z "$PREVIOUS_IMAGE" ]; then
    echo "No previous image is available for rollback."
    exit 1
fi

echo "Attempting rollback to:"
echo "$PREVIOUS_IMAGE"

docker rm -f \
  "$CONTAINER_NAME" \
  >/dev/null 2>&1 || true

docker pull \
  "$PREVIOUS_IMAGE"

docker run \
  --name "$CONTAINER_NAME" \
  --detach \
  --restart unless-stopped \
  --publish "${HOST_PORT}:${CONTAINER_PORT}" \
  --env APP_ENV=production \
  "$PREVIOUS_IMAGE"

echo "Verifying rollback..."

attempt=1
rollback_healthy=false

while [ "$attempt" -le 15 ]; do
    if curl \
        --fail \
        --silent \
        --show-error \
        "http://127.0.0.1:${HOST_PORT}/health" \
        >/dev/null; then

        rollback_healthy=true
        break
    fi

    echo "Rollback health attempt ${attempt}/15 failed."

    attempt=$((attempt + 1))
    sleep 2
done

if [ "$rollback_healthy" = true ]; then
    echo "Rollback succeeded."

    printf '%s\n' \
      "$PREVIOUS_IMAGE" \
      > "$CURRENT_IMAGE_FILE"

    echo "Service restored to:"
    cat "$CURRENT_IMAGE_FILE"

    echo "New deployment failed even though rollback succeeded."

    exit 1
fi

echo "CRITICAL: deployment failed and rollback failed."

docker logs \
  --tail 100 \
  "$CONTAINER_NAME" || true

exit 1
```

```text
/opt/veriqta/app/deploy.sh
```

# 122. What Is `scp`?

`scp` copies files over SSH.

Basic syntax:

```bash
scp local-file user@server:/remote/path/
```

Example:

```bash
scp \
  scripts/deploy.sh \
  deploy@server:/opt/veriqta/app/deploy.sh
```

It uses SSH authentication and host verification concepts just like `ssh`.

---

# 123. Use Host Verification With `scp`

Use:

```bash
scp \
  -o BatchMode=yes \
  -o StrictHostKeyChecking=yes \
  -o UserKnownHostsFile="$KNOWN_HOSTS" \
  scripts/deploy.sh \
  "$DEPLOY_USER@$DEPLOY_HOST:/opt/veriqta/app/deploy.sh"
```

Do not secure `ssh` but leave `scp` trusting arbitrary hosts.

---

# 124. Verify the Copied Script

After copying:

```bash
ssh ... \
  'chmod 700 /opt/veriqta/app/deploy.sh'
```

Then:

```bash
ssh ... \
  'ls -l /opt/veriqta/app/deploy.sh'
```

This verifies the expected file exists.

# 125. Avoid Remote Shell Injection

This is important.

Suppose a user-controlled Jenkins parameter becomes:

```text
IMAGE_TAG
```

and you build a remote command by directly inserting it into shell text.

A malicious value could contain shell syntax.

Therefore:

```text
validate inputs
```

and avoid arbitrary user-controlled shell fragments.

Our image tag is generated from:

```text
Jenkins BUILD_NUMBER
+
Git commit SHA
```

rather than arbitrary shell text.

That is safer.

```text

DEPLOY_HOST
DEPLOY_USER
PORT
```

against expected forms where appropriate.

For example, the generated image tag should resemble:

```text
123-a1b2c3d4e5f6
```

Do not accept:

```text
whatever shell command someone types
```

as deployment configuration.

# 131. Remote Login Pattern

Within `withCredentials` and `sshagent`, a carefully quoted shell can stream the secret without embedding it in Groovy interpolation.

Conceptually:

```bash

ssh ... \
  "docker login ... --password-stdin"
```

Avoid enabling shell tracing.

Never echo the token for debugging.


rather than repeatedly transporting long-lived credentials.

# 138. Full Deployment Jenkinsfile

The following example extends the Part 14 workflow.

Replace:

```text
YOUR_DOCKERHUB_NAMESPACE
YOUR_LINUX_SERVER
```

with your actual lab values.

The Jenkins credentials expected are:

```text
dockerhub-veriqta-push
dockerhub-veriqta-pull
linux-deployment-ssh
linux-deployment-known-hosts
```

```groovy
pipeline {
    agent {
        label 'linux && docker'
    }

    options {
        timestamps()
        disableConcurrentBuilds()
        timeout(time: 60, unit: 'MINUTES')
        buildDiscarder(
            logRotator(
                numToKeepStr: '30',
                artifactNumToKeepStr: '20'
            )
        )
    }

    environment {
        REGISTRY_HOST = 'docker.io'
        IMAGE_NAMESPACE = 'YOUR_DOCKERHUB_NAMESPACE'
        IMAGE_NAME = 'veriqta-docker-app'

        DEPLOY_HOST = 'YOUR_LINUX_SERVER'
        DEPLOY_USER = 'deploy'
        DEPLOY_DIR = '/opt/veriqta/app'

        CONTAINER_NAME = 'veriqta-docker-app'
        HOST_PORT = '8080'
        CONTAINER_PORT = '5000'

        DOCKER_CONFIG = "${WORKSPACE}/.docker-ci"
    }

    stages {
        stage('Environment Verification') {
            steps {
                sh '''
                    set -eu

                    echo "=== Jenkins ==="
                    echo "Job: $JOB_NAME"
                    echo "Build: $BUILD_NUMBER"
                    echo "Node: $NODE_NAME"

                    echo
                    echo "=== Git ==="
                    git --version
                    git rev-parse HEAD

                    echo
                    echo "=== Docker ==="
                    docker version

                    echo
                    echo "=== SSH ==="
                    ssh -V
                    scp -V 2>&1 || true
                '''
            }
        }

        stage('Source Verification') {
            steps {
                sh '''
                    set -eu

                    test -f Dockerfile
                    test -f app.py
                    test -f requirements.txt
                    test -f tests/test_app.py
                    test -f scripts/deploy.sh

                    test -x scripts/deploy.sh

                    echo "Required source and deployment files are present."
                '''
            }
        }

        stage('Generate Version') {
            steps {
                script {
                    env.GIT_COMMIT_FULL = sh(
                        script: 'git rev-parse HEAD',
                        returnStdout: true
                    ).trim()

                    env.SHORT_SHA = sh(
                        script: 'git rev-parse --short=12 HEAD',
                        returnStdout: true
                    ).trim()

                    env.IMAGE_TAG =
                        "${env.BUILD_NUMBER}-${env.SHORT_SHA}"

                    env.IMAGE_REPOSITORY =
                        "${env.REGISTRY_HOST}/${env.IMAGE_NAMESPACE}/${env.IMAGE_NAME}"

                    env.FULL_IMAGE =
                        "${env.IMAGE_REPOSITORY}:${env.IMAGE_TAG}"
                }

                echo "Commit: ${env.GIT_COMMIT_FULL}"
                echo "Image: ${env.FULL_IMAGE}"
            }
        }

        stage('Build Image') {
            steps {
                sh '''
                    set -eu

                    docker build \
                      -t "$FULL_IMAGE" \
                      .
                '''
            }
        }

        stage('Test Image') {
            steps {
                sh '''
                    set -eu

                    docker run \
                      --rm \
                      "$FULL_IMAGE" \
                      pytest -v
                '''
            }
        }

        stage('Prepare Registry Authentication') {
            steps {
                sh '''
                    set -eu

                    rm -rf "$DOCKER_CONFIG"

                    umask 077
                    mkdir -p "$DOCKER_CONFIG"
                '''
            }
        }

        stage('Publish Image') {
            steps {
                withCredentials([
                    usernamePassword(
                        credentialsId: 'dockerhub-veriqta-push',
                        usernameVariable: 'REGISTRY_PUSH_USER',
                        passwordVariable: 'REGISTRY_PUSH_TOKEN'
                    )
                ]) {
                    sh '''
                        set -eu
                        set +x

                        printf '%s' "$REGISTRY_PUSH_TOKEN" |
                          docker login \
                            --username "$REGISTRY_PUSH_USER" \
                            --password-stdin

                        docker push "$FULL_IMAGE"

                        docker logout >/dev/null 2>&1 || true
                    '''
                }
            }
        }

        stage('Create Build Metadata') {
            steps {
                sh '''
                    set -eu

                    mkdir -p artifacts

                    cat > artifacts/build-info.txt <<EOF
Application=$IMAGE_NAME
JenkinsJob=$JOB_NAME
JenkinsBuild=$BUILD_NUMBER
GitCommit=$GIT_COMMIT_FULL
ImageRepository=$IMAGE_REPOSITORY
ImageTag=$IMAGE_TAG
ImageReference=$FULL_IMAGE
DeploymentHost=$DEPLOY_HOST
EOF
                '''

                archiveArtifacts(
                    artifacts: 'artifacts/build-info.txt',
                    fingerprint: true
                )
            }
        }

        stage('Deployment Preflight') {
            steps {
                withCredentials([
                    file(
                        credentialsId: 'linux-deployment-known-hosts',
                        variable: 'KNOWN_HOSTS'
                    )
                ]) {
                    sshagent(
                        credentials: ['linux-deployment-ssh']
                    ) {
                        sh '''
                            set -eu

                            echo "Testing SSH connectivity..."

                            ssh \
                              -o BatchMode=yes \
                              -o StrictHostKeyChecking=yes \
                              -o UserKnownHostsFile="$KNOWN_HOSTS" \
                              "$DEPLOY_USER@$DEPLOY_HOST" \
                              '
                                set -eu

                                echo "=== Deployment Host ==="
                                hostname

                                echo "=== Deployment User ==="
                                whoami

                                echo "=== Docker ==="
                                docker version

                                echo "=== Disk ==="
                                df -h /

                                echo "=== Existing Application ==="
                                docker ps -a \
                                  --filter "name=^/'"$CONTAINER_NAME"'$"
                              '
                        '''
                    }
                }
            }
        }

        stage('Install Deployment Script') {
            steps {
                withCredentials([
                    file(
                        credentialsId: 'linux-deployment-known-hosts',
                        variable: 'KNOWN_HOSTS'
                    )
                ]) {
                    sshagent(
                        credentials: ['linux-deployment-ssh']
                    ) {
                        sh '''
                            set -eu

                            ssh \
                              -o BatchMode=yes \
                              -o StrictHostKeyChecking=yes \
                              -o UserKnownHostsFile="$KNOWN_HOSTS" \
                              "$DEPLOY_USER@$DEPLOY_HOST" \
                              "mkdir -p '$DEPLOY_DIR'"

                            scp \
                              -o BatchMode=yes \
                              -o StrictHostKeyChecking=yes \
                              -o UserKnownHostsFile="$KNOWN_HOSTS" \
                              scripts/deploy.sh \
                              "$DEPLOY_USER@$DEPLOY_HOST:$DEPLOY_DIR/deploy.sh"

                            ssh \
                              -o BatchMode=yes \
                              -o StrictHostKeyChecking=yes \
                              -o UserKnownHostsFile="$KNOWN_HOSTS" \
                              "$DEPLOY_USER@$DEPLOY_HOST" \
                              "chmod 700 '$DEPLOY_DIR/deploy.sh'"

                            echo "Deployment script installed."
                        '''
                    }
                }
            }
        }

        stage('Remote Registry Login') {
            steps {
                withCredentials([
                    file(
                        credentialsId: 'linux-deployment-known-hosts',
                        variable: 'KNOWN_HOSTS'
                    ),
                    usernamePassword(
                        credentialsId: 'dockerhub-veriqta-pull',
                        usernameVariable: 'REGISTRY_PULL_USER',
                        passwordVariable: 'REGISTRY_PULL_TOKEN'
                    )
                ]) {
                    sshagent(
                        credentials: ['linux-deployment-ssh']
                    ) {
                        sh '''
                            set -eu
                            set +x

                            printf '%s' "$REGISTRY_PULL_TOKEN" |
                              ssh \
                                -o BatchMode=yes \
                                -o StrictHostKeyChecking=yes \
                                -o UserKnownHostsFile="$KNOWN_HOSTS" \
                                "$DEPLOY_USER@$DEPLOY_HOST" \
                                "docker login \
                                   --username '$REGISTRY_PULL_USER' \
                                   --password-stdin"
                        '''
                    }
                }
            }
        }

        stage('Deploy Exact Artifact') {
            steps {
                withCredentials([
                    file(
                        credentialsId: 'linux-deployment-known-hosts',
                        variable: 'KNOWN_HOSTS'
                    )
                ]) {
                    sshagent(
                        credentials: ['linux-deployment-ssh']
                    ) {
                        sh '''
                            set -eu

                            ssh \
                              -o BatchMode=yes \
                              -o StrictHostKeyChecking=yes \
                              -o UserKnownHostsFile="$KNOWN_HOSTS" \
                              "$DEPLOY_USER@$DEPLOY_HOST" \
                              "$DEPLOY_DIR/deploy.sh \
                               '$FULL_IMAGE' \
                               '$CONTAINER_NAME' \
                               '$HOST_PORT' \
                               '$CONTAINER_PORT' \
                               '$DEPLOY_DIR'"
                        '''
                    }
                }
            }
        }

        stage('Remote Deployment Verification') {
            steps {
                withCredentials([
                    file(
                        credentialsId: 'linux-deployment-known-hosts',
                        variable: 'KNOWN_HOSTS'
                    )
                ]) {
                    sshagent(
                        credentials: ['linux-deployment-ssh']
                    ) {
                        sh '''
                            set -eu

                            ssh \
                              -o BatchMode=yes \
                              -o StrictHostKeyChecking=yes \
                              -o UserKnownHostsFile="$KNOWN_HOSTS" \
                              "$DEPLOY_USER@$DEPLOY_HOST" \
                              '
                                set -eu

                                echo "=== Running Container ==="

                                docker ps \
                                  --filter "name=^/'"$CONTAINER_NAME"'$"

                                echo
                                echo "=== Running Image ==="

                                docker inspect \
                                  --format "{{.Config.Image}}" \
                                  "'"$CONTAINER_NAME"'"

                                echo
                                echo "=== Container State ==="

                                docker inspect \
                                  --format "{{.State.Status}}" \
                                  "'"$CONTAINER_NAME"'"

                                echo
                                echo "=== Health Endpoint ==="

                                curl \
                                  --fail \
                                  --silent \
                                  --show-error \
                                  "http://127.0.0.1:'"$HOST_PORT"'/health"

                                echo
                                echo "=== Deployment Metadata ==="

                                cat "'"$DEPLOY_DIR"'/current-image"
                              '
                        '''
                    }
                }
            }
        }

        stage('Verify Expected Version') {
            steps {
                withCredentials([
                    file(
                        credentialsId: 'linux-deployment-known-hosts',
                        variable: 'KNOWN_HOSTS'
                    )
                ]) {
                    sshagent(
                        credentials: ['linux-deployment-ssh']
                    ) {
                        script {
                            env.DEPLOYED_IMAGE = sh(
                                script: '''
                                    ssh \
                                      -o BatchMode=yes \
                                      -o StrictHostKeyChecking=yes \
                                      -o UserKnownHostsFile="$KNOWN_HOSTS" \
                                      "$DEPLOY_USER@$DEPLOY_HOST" \
                                      "docker inspect \
                                         --format '{{.Config.Image}}' \
                                         '$CONTAINER_NAME'"
                                ''',
                                returnStdout: true
                            ).trim()

                            if (env.DEPLOYED_IMAGE != env.FULL_IMAGE) {
                                error(
                                    "Deployment verification failed. " +
                                    "Expected ${env.FULL_IMAGE}, " +
                                    "but server reports ${env.DEPLOYED_IMAGE}"
                                )
                            }

                            echo "Exact deployed image verified."
                        }
                    }
                }
            }
        }
    }

    post {
        success {
            echo "Source-to-server delivery completed successfully."
            echo "Deployed image: ${env.FULL_IMAGE}"
        }

        failure {
            echo "Pipeline or deployment failed."

            withCredentials([
                file(
                    credentialsId: 'linux-deployment-known-hosts',
                    variable: 'KNOWN_HOSTS'
                )
            ]) {
                sshagent(
                    credentials: ['linux-deployment-ssh'],
                    ignoreMissing: true
                ) {
                    sh '''
                        if [ -n "${DEPLOY_HOST:-}" ]; then
                            ssh \
                              -o BatchMode=yes \
                              -o StrictHostKeyChecking=yes \
                              -o UserKnownHostsFile="$KNOWN_HOSTS" \
                              "$DEPLOY_USER@$DEPLOY_HOST" \
                              "
                                echo '=== Deployment Diagnostics ==='

                                docker ps -a \
                                  --filter 'name=^/$CONTAINER_NAME$' || true

                                echo

                                docker logs \
                                  --tail 100 \
                                  '$CONTAINER_NAME' || true
                              " || true
                        fi
                    '''
                }
            }
        }

        cleanup {
            sh '''
                rm -rf "${DOCKER_CONFIG:-}" || true
            '''

            withCredentials([
                file(
                    credentialsId: 'linux-deployment-known-hosts',
                    variable: 'KNOWN_HOSTS'
                )
            ]) {
                sshagent(
                    credentials: ['linux-deployment-ssh'],
                    ignoreMissing: true
                ) {
                    sh '''
                        if [ -n "${DEPLOY_HOST:-}" ]; then
                            ssh \
                              -o BatchMode=yes \
                              -o StrictHostKeyChecking=yes \
                              -o UserKnownHostsFile="$KNOWN_HOSTS" \
                              "$DEPLOY_USER@$DEPLOY_HOST" \
                              "docker logout >/dev/null 2>&1 || true" \
                              || true
                        fi
                    '''
                }
            }
        }
    }
}
```

# 175. Deployment Permissions

A deployment identity should be able to perform only what is required.

Our lab account needs:


It does not need:

# 176. Root Deployment Is Tempting

Beginners often solve permission problems with:

```text
just use root
```

This hides architecture problems.

If the Pipeline is compromised, root deployment credentials can turn a CI compromise into complete server compromise.

Use dedicated identities and controlled permissions.

# 177. But Docker Access Is Powerful Too

Do not fool yourself.

A user with unrestricted Docker daemon access is already highly privileged.

Therefore:

```text

```

should still be considered a sensitive account.

```text
root
```

# 181. Environment Configuration Strategy

A production application may require:

```text

```

and secrets:

```text

```

A useful classification:

| Configuration        | Sensitive? | Possible Location |
| -------------------- | ---------: | ----------------- |
| `APP_ENV=production` | Usually no | deployment config |
| `LOG_LEVEL=info`     | Usually no | deployment config |
| public service URL   | Usually no | deployment config |
| database hostname    |    Depends | controlled config |
| database password    |        Yes | secret manager    |
| API token            |        Yes | secret manager    |
| private key          |        Yes | secret manager    |

# 182. Do Not Bake Production Configuration Into the Image

Bad:

```dockerfile

```

Bad:

```dockerfile

```

if it contains secrets.

The image travels through:

```text
Registry
CI
Deployment hosts
Caches
```

Secrets should not become image layers.

```text
Developer
```

```text
↓
GitHub
↓
Jenkins
↓
Build
↓
Test
↓
Docker Image
↓
Version
↓
Registry
↓
SSH
↓
Linux Deployment Server
↓
Pull Exact Artifact
↓
Apply Environment Configuration
↓
Start Application
↓
Health Check
↓
Verify Exact Version
↓
Application Running
```

You have now crossed one of the most important boundaries in Jenkins.

Jenkins is no longer only:

```text
a build system
```

It is participating in:

```text
software delivery
```

But safe deployment requires several principles:

```text
Build once.

Store the artifact.

Deploy the exact artifact.

Use dedicated identities.

Verify the SSH server.

Use least privilege.

Pull before replacing.

Never confuse "container started" with "application healthy."

Record what was deployed.

Keep a previous known-good artifact.

Rollback when necessary.

Verify the rollback.

Design deployment so it can safely run again.
```

The complete mental model is:

```text
SOURCE
  ↓
BUILD
  ↓
TEST
  ↓
ARTIFACT
  ↓
REGISTRY
  ↓
DEPLOYMENT
  ↓
RUNTIME
  ↓
VERIFICATION
```

And when something fails:

```text
SYMPTOM
   ↓
FAILED LAYER
   ↓
EVIDENCE
   ↓
ROOT CAUSE
   ↓
FIX / ROLLBACK
   ↓
VERIFICATION
```

That troubleshooting model is as important as the deployment itself.
