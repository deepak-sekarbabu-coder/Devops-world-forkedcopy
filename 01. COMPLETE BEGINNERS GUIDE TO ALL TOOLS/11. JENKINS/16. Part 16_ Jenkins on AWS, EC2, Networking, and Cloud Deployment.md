# Part 16: Jenkins on AWS, EC2, Networking, and Cloud Deployment

## Learning Objective

In Part 15, we built our first genuine source-to-server Jenkins deployment:

```text
Developer
↓
GitHub
↓
Jenkins
↓
Build
↓
Test
↓
Docker Image
↓
Container Registry
↓
SSH
↓
Linux Server
↓
Application
```

That taught us the mechanics of deployment.

But there was one major abstraction:

> Where does the infrastructure actually come from?

In a real organization, the Jenkins controller, build agents, application servers, networks, disks, firewalls, identities, DNS records, and load balancers all have to exist somewhere.

In Part 16, we place our Jenkins knowledge inside realistic cloud infrastructure using AWS.

Our first infrastructure mental model becomes:

```text
Internet
   ↓
Internet Gateway
   ↓
VPC
   ↓
Route Table
   ↓
Public Subnet
   ↓
Security Group
   ↓
Jenkins EC2
```

Then our delivery architecture becomes:

```text
Developer
   ↓
GitHub
   ↓
Jenkins EC2
   ↓
Build / Test
   ↓
Container Registry
   ↓
Application EC2
   ↓
Docker
   ↓
Application
```

By the end of this Part, you should understand not only how to put Jenkins on an EC2 instance, but how that instance fits into an AWS network, how Jenkins communicates with another EC2 instance, why security groups matter, where IAM fits, what persists when an instance changes, and how the architecture can evolve toward private networking, DNS, load balancing, and more production-oriented cloud design.

AWS describes a VPC as a logically isolated virtual network, subnets as IP ranges within that VPC, security groups as virtual firewalls for resources such as EC2 instances, and internet gateways as VPC components used with routing to provide internet connectivity. ([AWS Documentation][1])

# 2. Before AWS: Understand the Layers

When something fails in cloud infrastructure, beginners often call everything:

```text
AWS problem
```

That is too broad.

Our system has layers:

```text
AWS Account
↓
Region
↓
VPC
↓
Subnet
↓
Route
↓
Security Group
↓
Network Interface
↓
EC2 Instance
↓
Linux
↓
Jenkins / Docker
↓
Application
```

Each layer solves a different problem.

If SSH fails, possible causes include:

```text
Wrong IP
↓
No route
↓
Security group blocks 22
↓
Instance is stopped
↓
SSH service is down
↓
Wrong Linux user
↓
Wrong SSH key
```

Strong cloud troubleshooting means identifying the failed layer.

---

# 3. AWS Account

AWS resources belong to an AWS account.

The account is an administrative and billing boundary.

Inside it you create resources such as:

```text
VPCs
EC2 instances
Security groups
IAM roles
EBS volumes
Load balancers
DNS records
```

Do not treat the AWS account's root user as an ordinary DevOps account.

AWS recommends using IAM mechanisms to control authentication and authorization rather than broadly sharing account credentials. ([AWS Documentation][2])

---

# 4. AWS Region

AWS infrastructure is organized into geographic Regions.

A Region is an AWS geographic area containing multiple Availability Zones.

Examples historically include names such as:

```text
us-east-1
us-west-2
eu-west-1
```

The exact Region you choose matters because resources, pricing, available services, latency, and compliance requirements can vary.

---

# 5. Region Mental Model

Think:

```text
AWS
│
├── Region A
│
│   ├── AZ A
│
│   ├── AZ B
│
│   └── AZ C
│
└── Region B
    ├── AZ A
    ├── AZ B
    └── AZ C
```

Resources are often Region-scoped or Availability-Zone-scoped.

Your EC2 instance exists in:

```text
one Region
+
one Availability Zone
```

at a time.

---

# 6. Choose One Region for the Lab

For this beginner project, keep all resources in one Region.

Do not accidentally create:

```text
VPC in Region A

EC2 in Region B

Security group in Region C
```

and then wonder why they cannot be selected together.

At the beginning of every AWS lab, check the currently selected Region in the AWS console.

---

# 7. Availability Zones

An Availability Zone, usually called an AZ, is a distinct infrastructure location within a Region.

Conceptually:

```text
Region
│
├── Availability Zone 1
├── Availability Zone 2
└── Availability Zone 3
```

AZs exist so architectures can distribute workloads rather than relying on one location.

---

# 8. Why Availability Zones Matter

Our beginner architecture might initially be:

```text
One Jenkins EC2
+
One Application EC2
+
One AZ
```

That teaches cloud fundamentals.

But it is not highly available.

A more mature application architecture could use:

```text
Availability Zone A
├── App Instance A

Availability Zone B
├── App Instance B

        ↑
   Load Balancer
```

If one AZ experiences problems, another application instance may remain available.

---

# 9. Jenkins and Availability

A single Jenkins controller on one EC2 instance is also a potential single point of failure.

If that EC2 instance becomes unavailable:

```text
GitHub
↓
Jenkins unavailable
↓
CI/CD unavailable
```

This does not necessarily mean the already-running application stops.

It means delivery automation may become unavailable.

That distinction matters.

---

# 10. What Is a VPC?

VPC means:

```text
Virtual Private Cloud
```

A VPC is your logically isolated virtual network in AWS. ([AWS Documentation][1])

Instead of immediately thinking:

```text
EC2 = server
```

think:

```text
VPC
↓
Network
↓
EC2 lives inside network
```

---

# 11. VPC Mental Model

A VPC might use an IPv4 range such as:

```text
10.0.0.0/16
```

Inside that address space, you create smaller subnet ranges.

Example:

```text
VPC
10.0.0.0/16

├── Public Subnet A
│   10.0.1.0/24
│
├── Public Subnet B
│   10.0.2.0/24
│
├── Private Subnet A
│   10.0.11.0/24
│
└── Private Subnet B
    10.0.12.0/24
```

You do not need to master subnet mathematics yet, but you need to understand the hierarchy.

---

# 12. CIDR Introduction

You will see notation such as:

```text
10.0.0.0/16
```

and:

```text
10.0.1.0/24
```

This is CIDR notation.

It describes an IP network range.

For this beginner Part, remember:

```text
10.0.0.0/16
→ large VPC address range

10.0.1.0/24
→ smaller subnet range inside it
```

Do not choose overlapping subnet ranges inside the same architecture.

---

# 13. What Is a Subnet?

A subnet is a range of IP addresses inside a VPC. EC2 instances are launched into subnets. AWS specifically recommends using subnets to separate tiers of an application and using private subnets for resources that should not be directly reachable from the internet. ([AWS Documentation][1])

Mental model:

```text
VPC
↓
Subnet
↓
EC2
```

---

# 14. A Subnet Belongs to One Availability Zone

A subnet does not stretch across multiple Availability Zones.

Example:

```text
VPC
│
├── Subnet A
│   └── AZ A
│
└── Subnet B
    └── AZ B
```

That matters when building multi-AZ architectures.

---

# 15. Public and Private Subnets

The words:

```text
public subnet
```

and:

```text
private subnet
```

do not simply mean:

```text
has public IP
```

The routing configuration is central.

AWS describes a subnet whose route table has a route to an internet gateway as a public subnet; without that route, it is private. ([AWS Documentation][3])

---

# 16. Public Subnet

Conceptually:

```text
Public Subnet
↓
Route Table
↓
0.0.0.0/0
↓
Internet Gateway
```

Instances may communicate with the internet when the required addressing, routes, and security controls are also present.

---

# 17. Private Subnet

Conceptually:

```text
Private Subnet
↓
No direct route to Internet Gateway
```

An instance in a private subnet does not receive direct internet connectivity merely because an internet gateway exists elsewhere in the VPC.

This is useful for:

```text
Application servers
Databases
Internal services
Build agents
```

that should not be directly exposed.

---

# 18. Beginner Lab vs Better Production Architecture

For learning, we can initially place:

```text
Jenkins EC2
Application EC2
```

in a public subnet.

That makes SSH and browser access easier to understand.

But a stronger production direction is:

```text
Internet
↓
Load Balancer / controlled administration
↓
Private resources
```

Do not confuse:

```text
easy beginner lab
```

with:

```text
ideal production topology
```

---

# 19. What Is a Route?

A route tells the network where traffic for a destination should go.

Think:

```text
Destination
→ Target
```

Example:

```text
10.0.0.0/16
→ local

0.0.0.0/0
→ Internet Gateway
```

---

# 20. What Is a Route Table?

A route table contains routes.

Conceptually:

| Destination   | Target           |
| ------------- | ---------------- |
| `10.0.0.0/16` | local            |
| `0.0.0.0/0`   | Internet Gateway |

The local route allows resources in the VPC address space to communicate according to networking and security controls.

The default route says:

```text
traffic not matched by a more specific route
→ Internet Gateway
```

for that public-subnet design.

---

# 21. Longest Prefix Match Concept

Route selection is based on the most specific matching route.

You do not need advanced routing knowledge yet.

But understand:

```text
route table
```

is not just a list processed randomly.

Networking systems choose the most appropriate matching route.

---

# 22. Internet Gateway

An Internet Gateway, or IGW, is attached to a VPC and can serve as a route target for internet-routable traffic. AWS notes that an internet gateway must be attached to the VPC and routing configured before it provides internet connectivity. ([AWS Documentation][3])

Mental model:

```text
Internet
   ↓
Internet Gateway
   ↓
VPC
```

---

# 23. An Internet Gateway Alone Is Not Enough

This is important.

Creating:

```text
Internet Gateway
```

does not automatically mean:

```text
EC2 can access internet
```

You also need the correct combination of:

```text
IGW attached to VPC
+
route
+
appropriate addressing
+
security group rules
+
network configuration
```

Cloud connectivity is a chain.

---

# 24. Internet Route

A common IPv4 public-subnet route is:

```text
0.0.0.0/0
→ Internet Gateway
```

`0.0.0.0/0` represents all IPv4 destinations not matched by a more specific route.

AWS documents this as the common internet-gateway route for a public subnet. ([AWS Documentation][3])

---

# 25. First Network Architecture

Our lab:

```text
Internet
   ↓
Internet Gateway
   ↓
VPC: 10.0.0.0/16
   ↓
Route Table
   │
   ├── 10.0.0.0/16 → local
   └── 0.0.0.0/0 → Internet Gateway
   ↓
Public Subnet: 10.0.1.0/24
```

Then:

```text
Public Subnet
├── Jenkins EC2
└── Application EC2
```

# 26. Security Groups

A Security Group is a virtual firewall associated with AWS resources such as EC2 instances.

It controls allowed:

```text
Inbound traffic
Outbound traffic
```

AWS security groups are stateful. Response traffic for allowed connections is automatically handled by the connection-tracking behavior. ([AWS Documentation][4])

---

# 27. Security Group Mental Model

```text
Network Traffic
↓
Security Group
↓
EC2 Network Interface
↓
Linux
↓
Application
```

A running service can still be unreachable if the Security Group does not allow the required traffic.

---

# 28. Security Groups Allow Traffic

Security Groups are primarily allow-rule based.

Example:

```text
Inbound:

TCP 22
Source: YOUR_ADMIN_IP/32

TCP 8080
Source: YOUR_ADMIN_IP/32
```

This means:

```text
your trusted source
→ SSH

your trusted source
→ Jenkins
```

It does not mean the entire internet is allowed.

---

# 29. Do Not Use `0.0.0.0/0` Everywhere

A common beginner shortcut is:

```text
SSH 22
Source: 0.0.0.0/0
```

That means:

```text
any IPv4 address
→ may attempt SSH
```

The Jenkins AWS tutorial itself warns that broad SSH access is unsafe for production and recommends limiting SSH to the appropriate client address range. ([Jenkins][5])

For this lab, use your actual trusted administration source where practical.

---

# 30. `/32` Means One IPv4 Address

Example:

```text
203.0.113.25/32
```

means one IPv4 address.

This is useful when allowing administrative access from one known public IP.

If your public IP changes, the Security Group rule may need updating.

---

# 31. Jenkins Security Group

Create a Security Group conceptually named:

```text
veriqta-jenkins-sg
```

Possible lab inbound rules:

| Port | Purpose               | Source                 |
| ---- | --------------------- | ---------------------- |
| 22   | SSH administration    | trusted admin IP `/32` |
| 8080 | Jenkins UI lab access | trusted admin IP `/32` |

Do not expose Jenkins 8080 to the whole internet merely because the browser otherwise cannot connect.

---

# 32. Application Security Group

Create:

```text
veriqta-app-sg
```

For deployment, SSH should ideally be allowed from the Jenkins Security Group rather than the whole internet.

Conceptually:

```text
Source:
veriqta-jenkins-sg

Port:
22
```

Then:

```text
Jenkins EC2
↓
SSH
↓
Application EC2
```

without granting every internet host SSH access.

---

# 33. Security Group Referencing

Security groups can be used as sources in other security-group rules in supported VPC configurations.

This is much stronger than hardcoding Jenkins's public IP for internal communication.

Architecture:

```text
Jenkins EC2
attached to:
veriqta-jenkins-sg

        ↓

Application EC2
attached to:
veriqta-app-sg

Inbound:
TCP 22
Source:
veriqta-jenkins-sg
```

Now the rule expresses architectural intent:

> Resources associated with the Jenkins Security Group may reach the application server's SSH port.

---

# 34. Application Port Rule

If the application must be directly accessible during the lab:

```text
TCP 8080
Source:
trusted test IP /32
```

Do not automatically use:

```text
0.0.0.0/0
```

Later a load balancer can become the allowed source instead.

---

# 35. Security Group vs Linux Firewall

These are different layers.

```text
AWS Security Group
↓
EC2
↓
Linux Firewall
↓
Application
```

Traffic may be allowed by AWS but blocked by Linux.

Or allowed by Linux but blocked by AWS.

Troubleshoot both layers when necessary.


```text

↓
```

# 42. EC2 Key Pair

An EC2 key pair can be used for SSH authentication when launching Linux instances.

AWS stores the public-key side for instance launch while you protect the private key material.

If you download:

```text
veriqta-aws-lab.pem
```

protect it.

On Linux/macOS:

```bash
chmod 400 veriqta-aws-lab.pem
```

The Jenkins AWS tutorial also uses restrictive permissions on downloaded private key files. ([Jenkins][5])

---

# 43. Never Commit the `.pem` File

Add patterns such as:

```text
*.pem
```

to local protection where appropriate.

But remember:

```text
.gitignore
```

is not a secret manager.

If the key is accidentally committed, removing the file from the latest commit is not enough.

Treat the credential as compromised and replace/revoke access appropriately.

# 44. Public IP Address

A public IPv4 address is internet-routable.

Conceptually:

```text
Internet
↓
Public IP
↓
EC2
```

It can be useful for:

```text
SSH administration
temporary lab access
public application traffic
```

But direct public addressing increases exposure and should be deliberate.

---

# 45. Private IP Address

An EC2 instance also has private addressing inside the VPC.

Example:

```text
10.0.1.25
```

Another instance in the VPC can often communicate using private addressing when routes and security rules allow it.

For Jenkins-to-application deployment, prefer:

```text
Jenkins private IP
→ Application private IP
```

when both are inside the VPC.

---

# 46. Why Use Private IP Internally?

Instead of:

```text
Jenkins
↓
Internet
↓
Application public IP
```

prefer:

```text
Jenkins
↓
VPC private networking
↓
Application private IP
```

for internal server-to-server communication.

Benefits include:

```text
less unnecessary public exposure
clearer architecture
internal traffic path
```

---

# 47. Public IP Stability

An automatically assigned public IPv4 address should not automatically be treated as a permanent endpoint.

Infrastructure changes such as stopping and starting an instance can affect public addressing depending on configuration.

If you need a stable public IPv4 endpoint, AWS provides mechanisms such as Elastic IP addresses, though public IPv4 addressing can have associated costs.

For production, DNS is usually preferable to embedding raw addresses everywhere.

---

# 48. DNS Introduction

DNS means:

```text
Domain Name System
```

It maps names to network destinations.

Instead of remembering:

```text
203.0.113.25
```

you might use:

```text
jenkins.example.com
```

or:

```text
app.example.com
```

Conceptually:

```text
Name
↓
DNS
↓
Address / AWS endpoint
```

---

# 49. AWS DNS

AWS provides DNS-related services, most notably:

```text
Amazon Route 53
```

You do not need Route 53 to understand Jenkins on EC2.

But mature infrastructure generally avoids teaching humans and applications to depend on changing raw IP addresses.

---

# 50. Internal DNS

Conceptually:

```text

↓

↓

```

For our beginner project, we can initially use the application's private IP and then discuss DNS as the next improvement.

# 86. IAM Introduction

IAM means:

```text
Identity and Access Management
```

IAM answers questions such as:

```text
Who or what is authenticated?

What AWS actions may it perform?

Which AWS resources may it access?
```

AWS describes IAM as the service used to control authentication and authorization for AWS resources. ([AWS Documentation][2])

---

# 87. IAM Is Not a Security Group

This distinction is fundamental.

Security Group:

```text
Can network traffic reach this resource?
```

IAM:

```text
Can this identity perform this AWS API action?
```

Example:

```text
Security Group
→ Can Jenkins reach port 22?

IAM
→ Can Jenkins call an EC2 API?
```

Different layers.

---

# 88. IAM Users

An IAM user represents an identity in an AWS account.

Historically, automation was often configured with long-lived:

```text
Access Key ID
Secret Access Key
```

attached to IAM users.

That pattern still exists, but long-lived credentials create rotation and leakage risk.

---

# 89. IAM Roles

An IAM role is an AWS identity with permissions that can be assumed.

For EC2, an IAM role can be attached to an instance through an instance profile.

Applications on that EC2 instance can then obtain temporary credentials through AWS's instance credential mechanisms instead of storing long-lived AWS access keys in files. AWS explicitly recommends IAM roles for applications running on EC2 where appropriate. ([AWS Documentation][2])

---

# 90. Why IAM Roles Matter for Jenkins

Suppose Jenkins needs AWS API access.

Bad:

```text
Jenkinsfile
↓
AWS_ACCESS_KEY_ID=...
AWS_SECRET_ACCESS_KEY=...
```

Better when supported:

```text
Jenkins EC2
↓
IAM Role
↓
Temporary AWS Credentials
↓
AWS API
```

This reduces long-lived static credential handling.

---

# 91. Example Jenkins IAM Needs

Depending on your future Pipeline, Jenkins might need to:

```text
Read ECR images
Push ECR images
Describe EC2 instances
Upload artifacts to S3
Trigger deployment services
```

Do not attach:

```text
AdministratorAccess
```

just because it makes the error disappear.

Grant the minimum AWS permissions required.
