# Part 14: Container Registries and Artifact Management

## Learning Objective

In Part 13, Jenkins successfully built, tested, ran, inspected, and verified a Docker image.

The architecture ended here:

```text
Git Push
   ↓
GitHub
   ↓
Jenkins Controller
   ↓
Docker-Capable Agent
   ↓
Test
   ↓
Docker Build
   ↓
Versioned Docker Image
```

There is an important problem.

That image currently exists only in the Docker environment where Jenkins built it.

If the Jenkins agent disappears, is replaced, loses its Docker storage, or is cleaned, the image may disappear with it.

Another server cannot automatically retrieve it.

A deployment system cannot reliably ask:

```text
Give me the exact image produced by Jenkins Build #84.
```

unless we store that image somewhere designed for artifact distribution.

Part 14 solves that problem.

We will extend the architecture to:

```text
Git Push
   ↓
GitHub
   ↓
Jenkins
   ↓
Test
   ↓
Docker Build
   ↓
Image Tag
   ↓
Registry Authentication
   ↓
Push
   ↓
Container Registry
```

Then another system can perform:

```text
Container Registry
   ↓
Pull Exact Image
   ↓
Verify Artifact
   ↓
Deploy
```

The learning objective is:

> Store CI build outputs as versioned, traceable, retrievable artifacts instead of leaving them on the Jenkins machine.

By the end of Part 14, you should be able to:

* explain what a build artifact is;
* distinguish source code from build artifacts;
* explain Jenkins archived artifacts;
* archive files from Jenkins builds;
* understand why Jenkins itself should not be treated as your universal artifact repository;
* explain what an artifact repository is;
* explain what a container registry is;
* understand Docker Hub;
* understand private registries;
* understand registry repositories;
* understand image naming;
* understand registry namespaces;
* understand image tags;
* explain why `latest` is weak for deployment traceability;
* generate versions from Jenkins builds;
* generate tags from Git commit SHAs;
* create multiple tags for one image;
* understand immutable artifact principles;
* authenticate Jenkins to a registry securely;
* use Jenkins credentials rather than plaintext passwords;
* push Docker images;
* pull exact Docker images;
* verify the exact artifact that was retrieved;
* understand image digests;
* distinguish mutable tags from immutable content identities;
* connect Git commits, Jenkins builds, image tags, and image digests;
* understand artifact retention;
* understand cleanup;
* avoid deleting artifacts still required for rollback;
* understand basic Nexus Repository concepts;
* understand basic JFrog Artifactory concepts;
* understand how CI artifacts move toward deployment.

Our final architecture will be:

```text
Developer
```

# 1. Start With the Problem

Suppose Jenkins Build #84 creates:

```text
veriqta-docker-app:84
```

The image exists on:

```text
Jenkins Docker Agent A
```

Now imagine the deployment server is:

```text
Application Server B
```

Server B needs the image.

But Docker images are normally stored locally by the Docker daemon that built or pulled them.

So:

```text
Agent A
├── veriqta-docker-app:84
├── veriqta-docker-app:83
└── veriqta-docker-app:82
```

does not automatically mean:

```text
Server B
├── veriqta-docker-app:84
└── available
```

It is not.

We need a distribution point.

---

# 2. The Wrong Architecture

A fragile architecture looks like:

```text
GitHub
   ↓
Jenkins
   ↓
Build Image
   ↓
Leave Image on Jenkins Agent
```

Then deployment somehow depends on that specific Jenkins machine.

Problems include:

* Jenkins agent replacement;
* local disk cleanup;
* disk failure;
* ephemeral agents;
* multiple build agents;
* multiple deployment servers;
* rollback requirements;
* artifact auditing;
* disaster recovery;
* release traceability.

The build machine should not be the only location of an important release artifact.

---

# 3. The Better Architecture

Instead:

```text
GitHub
   ↓
Jenkins
   ↓
Build
   ↓
Test
   ↓
Version
   ↓
Registry
```

Then:

```text
Registry
   ├── Version 81
   ├── Version 82
   ├── Version 83
   └── Version 84
```

A deployment system can request:

```text
Version 84
```

without depending on the Jenkins agent that created it.

# 4. What Is a Build Artifact?

A build artifact is an output produced by a build process that you want to preserve, distribute, inspect, test, deploy, or otherwise use later.

Examples include:

```text
Java:
application.jar
application.war

Python:
package.whl
package.tar.gz

Node.js:
distribution bundle
package archive

.NET:
compiled binaries

Native applications:
executables
libraries

Documentation:
generated documentation

Testing:
test reports
coverage reports

Containers:
Docker / OCI image
```

The important concept is:

```text
Source Code
   ↓
Build Process
   ↓
Build Artifact
```

---

# 5. Source Code Is Not the Same as a Build Artifact

Your Git repository may contain:

```text
app.py
Dockerfile
Jenkinsfile
requirements.txt
tests/
```

These are inputs.

The build produces:

```text
Docker Image
```

That is an output.

Architecture:

```text
Git Commit
   ↓
Source Files
   ↓
Jenkins Build
   ↓
Tests
   ↓
Docker Build
   ↓
Container Image
```

Do not confuse:

```text
source version
```

with:

```text
built artifact
```

Both need traceability.

---

# 6. Why Preserve Build Outputs?

Imagine Jenkins Build #105 passed every test.

Two weeks later, production needs to deploy that exact release.

A weak workflow says:

```text
Checkout the old commit
↓
Build it again
↓
Hope the result is equivalent
```

A stronger workflow says:

```text
Retrieve the artifact that Build #105 already created and validated
```

This supports the principle:

> Build once, test the artifact, store it, and promote that same artifact.

---

# 7. Why Rebuilding Later Can Be Dangerous

Even if source code has not changed, external build inputs may have changed.

Examples:

```text
Base image
Package repository
Dependency version
Operating-system packages
Build tooling
Compiler
Network source
Build environment
```

Suppose:

```dockerfile
FROM python:3.12-slim
```

resolves to different underlying content months later.

Or:

```text
requirements.txt
```

contains loosely constrained dependencies.

Rebuilding an old commit may not necessarily produce byte-for-byte identical output.

Preserving the validated artifact avoids depending on a future rebuild.

# 9. Two Artifact Concepts We Need

# 10. Jenkins Archived Artifacts

Jenkins can preserve files produced by a build.

For example:

```text
Build #20
├── application.jar
├── test-report.xml
└── package.zip
```

Pipeline can archive files using:

```groovy
archiveArtifacts
```

Example:

```groovy
post {
    success {
        archiveArtifacts artifacts: 'dist/*.whl',
                         fingerprint: true
    }
}
```

This tells Jenkins to preserve matching build outputs.

---

# 11. What `archiveArtifacts` Does

Suppose your workspace contains:

```text
workspace/
└── dist/
    └── veriqta_app-1.0.0-py3-none-any.whl
```

The workspace itself may later be deleted.

If Jenkins archives:

```text
dist/*.whl
```

the artifact is preserved with the Jenkins build record according to Jenkins storage and retention configuration.

Conceptually:

```text
Workspace
   ↓
archiveArtifacts
   ↓
Jenkins Build Record
   ↓
Archived Artifact
```

---

# 12. Why Archive Artifacts?

Archived artifacts can be useful for:

* build outputs;
* test evidence;
* generated reports;
* small packages;
* debugging evidence;
* downloadable build results;
* build-to-build traceability.

For example:

```text
Jenkins Job
   ↓
Build #45
   ↓
Artifacts
   ↓
test-report.zip
```

# 13. Practical Lab: Archive a File

Create a simple Pipeline stage:

```groovy
stage('Create Artifact') {
    steps {
        sh '''
            set -eu

            mkdir -p artifacts

            printf '%s\n' \
              "Application: veriqta-docker-app" \
              "Build: $BUILD_NUMBER" \
              "Commit: $(git rev-parse HEAD)" \
              > artifacts/build-info.txt
        '''
    }
}
```

Then:

```groovy
post {
    success {
        archiveArtifacts artifacts: 'artifacts/build-info.txt',
                         fingerprint: true
    }
}
```

Run the Pipeline.

# 15. Jenkins Fingerprinting

Jenkins can fingerprint supported archived files.

Example:

```groovy
archiveArtifacts artifacts: 'artifacts/build-info.txt',
                 fingerprint: true
```

A fingerprint helps Jenkins track files across builds/jobs in workflows where Jenkins fingerprinting is used.

The important beginner idea is:

```text
artifact
+
identity
+
build relationship
```

Do not confuse Jenkins file fingerprinting with Docker image digests.

They are different mechanisms.

# 16. Jenkins Archive vs Container Registry

Jenkins archived artifacts are useful.

But a Docker image is not normally distributed by:

```text
archiveArtifacts
```

as though it were simply:

```text
application.zip
```

Container images have their own distribution model.

That is what a container registry provides.

---

# 17. Could You Save a Docker Image as a File?

Technically, Docker supports commands such as:

```bash
docker save
```

which can export images into archive files.

For example:

```bash
docker save \
  -o veriqta-docker-app.tar \
  veriqta-docker-app:45
```

But using Jenkins file archives as your normal container distribution system is usually not the right architecture.

Container registries are designed specifically for storing and distributing container images.

# 19. Git Is Not Your Artifact Repository

Do not commit generated release binaries into Git merely because:

```text

```

Artifact repositories are designed for build outputs.

The architecture should generally remain:

```text
Git
→ Source

Artifact Repository
→ Built Outputs
```

# 20. What Is a Container Registry?

A container registry is a service designed to store and distribute container images and related OCI-compatible artifacts.

Conceptually:

```text
Docker Build
   ↓
Image
   ↓
Push
   ↓
Registry
   ↓
Store
   ↓
Pull
   ↓
Another Machine
```

---

# 21. Registry vs Repository

These terms can confuse beginners.

A **registry** is the larger service.

Inside the registry are **repositories**.

Conceptually:

```text
Registry
├── team-a/api
├── team-a/frontend
├── team-b/worker
└── veriqta/docker-app
```

A repository then contains tagged image manifests/versions.

For example:

```text
veriqta/docker-app
├── 101-a12b34c
├── 102-c56d78e
├── 103-f90a12b
└── latest
```

Docker Hub is a widely used hosted container registry service.

# 23. Public vs Private Repository

A public repository can generally be pulled by anyone, subject to service rules and rate limits.

A private repository requires authorization.

For a training application, you may choose a private repository if you do not want the image publicly accessible.

Do not publish proprietary code or sensitive images publicly merely to simplify a lab.


Conceptually:

```text

Repository:

```

Together:

```text
docker.io/veriqta/veriqta-docker-app:105-a1b2c3d4
```

---

# 27. Image Reference Mental Model

Think:

```text
REGISTRY/NAMESPACE/REPOSITORY:TAG
```

Example:

```text
docker.io/veriqta/veriqta-docker-app:105-a1b2c3d4
```

Not every registry uses the exact same organizational terminology or UI, but this mental model is useful.

---

# 28. Default Registry Behavior

When you write something like:

```bash
docker pull nginx
```

Docker applies default naming conventions, including Docker Hub defaults.

For CI/CD, prefer explicit naming where clarity matters.

Instead of relying entirely on implicit defaults:

```text
my-app:105
```

you may use:

```text
docker.io/mynamespace/my-app:105
```

or your organization's registry hostname.

---

# 29. Image Tags

A tag is a human-readable reference associated with image content.

Examples:

```text
1.0.0
1.0.1
105
105-a1b2c3d
main
staging
production
latest
```

Different tags communicate different meanings.

---

# 30. Mutable Tags

A tag can normally be moved to point to different image content unless registry policy prevents that behavior.

For example:

Today:

```text
latest
→ Image A
```

Tomorrow:

```text
latest
→ Image B
```

The string:

```text
latest
```

did not change.

The referenced image content did.

This is why tags should not automatically be treated as immutable identities.

---

# 31. The `latest` Problem

Suppose production deployment says:

```bash
docker pull veriqta/veriqta-docker-app:latest
```

What exact code is that?

Which Jenkins build?

Which Git commit?

Which image was tested?

Without additional metadata, you may not know confidently.

`latest` is convenient for humans.

It is weak as the sole release identity.

---

# 32. `latest` Does Not Mean "Newest Valid Production Release"

The tag:

```text
latest
```

has no magical knowledge of:

```text
testing
approval
production
security
stability
```

It is simply a tag.

If Jenkins pushes:

```text
latest
```

after every build, it may point to whatever was pushed most recently by that workflow.

Do not interpret it as:

```text
best
stable
approved
production
```

unless your release process deliberately defines and enforces such meaning.

# 33. Better CI Versioning

A simple strategy:

```text
BUILD_NUMBER
```

Example:

```text
veriqta-docker-app:105
```

This creates:

```text
Jenkins Build #105
↔
Image :105
```

Better traceability.

---

# 34. Commit SHA Tagging

Git provides a stronger connection to source code.

Full commit:

```bash
git rev-parse HEAD
```

Example:

```text
a12b34c56d78e90f...
```

Short version:

```bash
git rev-parse --short=12 HEAD
```

Example:

```text
a12b34c56d78
```

Then:

```text
veriqta-docker-app:a12b34c56d78
```

connects image to source.

---

# 35. Build Number + Commit SHA

A useful beginner strategy combines both:

```text
105-a12b34c56d78
```

Now:

```text
105
→ Jenkins Build

a12b34c56d78
→ Git Commit
```

Image:

```text
veriqta-docker-app:105-a12b34c56d78
```

This is easy for humans to investigate.

---

# 36. Generate the Version in Jenkins

Pipeline:

```groovy
stage('Generate Version') {
    steps {
        script {
            env.SHORT_SHA = sh(
                script: 'git rev-parse --short=12 HEAD',
                returnStdout: true
            ).trim()

            env.IMAGE_TAG = "${env.BUILD_NUMBER}-${env.SHORT_SHA}"
        }

        echo "Image tag: ${env.IMAGE_TAG}"
    }
}
```

If:

```text
BUILD_NUMBER = 105
SHORT_SHA = a12b34c56d78
```

then:

```text
IMAGE_TAG = 105-a12b34c56d78
```

---

# 37. Verify the Commit

Do not merely trust a variable.

Run:

```bash
git rev-parse HEAD
```

and:

```bash
git log -1 --oneline
```

This provides evidence about the source revision in the workspace.

# 38. Build the Versioned Image

Suppose:

```text
IMAGE_REPOSITORY
=
docker.io/veriqta/veriqta-docker-app
```

Build:

```bash
docker build \
  -t "$IMAGE_REPOSITORY:$IMAGE_TAG" \
  .
```

Result:

```text
docker.io/veriqta/veriqta-docker-app:105-a12b34c56d78
```

# 39. Multiple Tags Can Reference the Same Image

You can apply another tag:

```bash
docker tag \
  "$IMAGE_REPOSITORY:$IMAGE_TAG" \
  "$IMAGE_REPOSITORY:latest"
```

Now locally:

```text
105-a12b34c56d78
latest
```

may refer to the same image content.

Verify:

```bash
docker image ls "$IMAGE_REPOSITORY"
```

---

# 40. Should You Push `latest`?

You can.

But you do not have to.

For our core lab, the important deployment artifact is:

```text
BUILD_NUMBER-COMMIT_SHA
```

If you choose to maintain:

```text
latest
```

treat it as a convenience pointer, not as the authoritative immutable release identity.

---

# 41. Immutable Versions

The principle of immutable artifacts is:

> Once a release artifact has been created and identified, do not silently replace its content with a different build.

Suppose:

```text
105-a12b34c56d78
```

was produced and tested.

Do not later rebuild something different and reuse:

```text
105-a12b34c56d78
```

for unrelated content.

That destroys trust in the identifier.

---

# 42. Why Immutability Matters

Imagine an incident report says:

```text
Production deployed:
veriqta-docker-app:105-a12b34c56d78
```

If that tag can be silently overwritten with different image content, the identifier no longer proves what actually ran.

Immutability improves:

```text
Traceability
Rollback
Auditing
Incident investigation
Reproducibility
Release confidence
```

---

# 43. Tags vs Digests

Container registries provide a stronger content identity called a digest.

You may see:

```text
sha256:...
```

Conceptually:

```text
Tag
→ human-readable reference

Digest
→ content-addressed identity
```

Example:

```text
veriqta-docker-app:105-a12b34c56d78
```

may resolve to something like:

```text
sha256:abcdef...
```

The real digest will be much longer.

---

# 44. Why Digests Matter

A tag can normally move.

A content digest identifies specific image content/manifest data.

Conceptually:

```text
latest
→ can change

105-a12b34c56d78
→ should be treated as immutable by policy

sha256:...
→ content-addressed identity
```

This makes digests valuable for exact artifact verification and deployment pinning.

---

# 45. Inspect the Local Image ID

Before pushing:

```bash
docker image inspect \
  --format '{{.Id}}' \
  "$IMAGE_REPOSITORY:$IMAGE_TAG"
```

This shows the local image ID.

Do not assume this is interchangeable with every registry digest concept.

Local image IDs and registry manifest/index digests serve related but distinct roles.

# 46. Registry Authentication

Public image pulls may not always require authentication.

Image pushes do.

The registry must answer:

```text
Who are you?
```

and:

```text
Are you allowed to push here?
```

Architecture:

```text
Jenkins
   ↓
Credentials
   ↓
Registry Authentication
   ↓
Authorization
   ↓
Push
```

---

# 47. Authentication vs Authorization

These are different.

**Authentication** asks:

> Who are you?

**Authorization** asks:

> What are you allowed to do?

You can successfully authenticate and still receive:

```text
denied
unauthorized
forbidden
```

because the account lacks permission to push to that repository.

---

# 48. Never Put Registry Passwords in the Jenkinsfile

Bad:

```groovy
environment {
    DOCKER_PASSWORD = 'MyRealPassword123'
}
```

Bad:

```bash
docker login \
  -u myuser \
  -p MyRealPassword123
```

Bad:

```text
Git repository
└── registry-password.txt
```

Part 10 already established:

```text
Secrets
→ Jenkins Credentials Store

Jenkinsfile
→ Credential IDs / controlled bindings
```

Continue using that model.

# 49. Create Registry Credentials in Jenkins

For a Docker Hub lab, create a Jenkins credential.

Navigate conceptually to:

```text
Manage Jenkins
→ Credentials
→ appropriate credential store/domain
→ Add Credentials
```

Depending on your Jenkins configuration and plugin/UI version, exact menu wording may differ.

For username/token authentication, a common credential type is:

```text

```

```text

→ registry username

Password
→ registry access token or password as appropriate
```

Prefer a scoped access token where the registry supports it rather than using a broad personal password.

---

# 50. Credential ID

Give the credential a clear ID such as:

```text
dockerhub-veriqta-push
```

The Jenkinsfile should know:

```text
dockerhub-veriqta-push
```

It should not know:

```text
actual secret token
```

That separation is the point.

---

# 51. Least Privilege for Registry Credentials

The Jenkins credential should have only the permissions needed by the Pipeline.

If Jenkins only needs:

```text
push/pull one repository
```

do not give it unnecessary:

```text
organization administration
account administration
unrelated repositories
billing permissions
```

where your registry supports finer-grained permissions.

---

# 52. `docker login`

Manual syntax:

```bash
docker login
```

or for an explicit registry:

```bash
docker login REGISTRY_HOST
```

Interactive login is not ideal for Jenkins because Jenkins needs non-interactive automation.

---

# 53. Do Not Use `--password` Carelessly

Avoid:

```bash
docker login \
  --username "$USER" \
  --password "$PASSWORD"
```

Passing secrets directly as command arguments can create exposure risks.

Docker supports:

```text
--password-stdin
```

which is preferable for non-interactive CI authentication.

---

# 54. Secure Jenkins Login Pattern

Using Part 10's `withCredentials`:

```groovy
withCredentials([
    usernamePassword(
        credentialsId: 'dockerhub-veriqta-push',
        usernameVariable: 'REGISTRY_USER',
        passwordVariable: 'REGISTRY_TOKEN'
    )
]) {
    sh '''
        set +x

        printf '%s' "$REGISTRY_TOKEN" |
          docker login \
            --username "$REGISTRY_USER" \
            --password-stdin
    '''
}
```

Important:

```text
credentialsId
→ Jenkins credential reference

REGISTRY_USER
→ temporary environment variable

REGISTRY_TOKEN
→ temporary environment variable

--password-stdin
→ secret supplied through standard input
```

---

# 55. Why `set +x`?

Shell tracing can echo commands.

When secrets are involved, avoid unnecessary shell tracing.

Jenkins credential masking helps reduce accidental exposure, but masking is not a license to print secrets.

Never intentionally run:

```bash
echo "$REGISTRY_TOKEN"
```

---

# 56. Docker Login Stores Client Authentication State

A successful `docker login` normally updates Docker client authentication configuration for the current user, commonly under:

```text
~/.docker/config.json
```

depending on credential helper/configuration.

This matters on shared/static Jenkins agents.

Registry authentication state can persist beyond the immediate shell command unless managed appropriately.

---

# 57. Shared-Agent Security Concern

Suppose:

```text
Build A
→ docker login
```

and authentication state remains in the Jenkins agent user's Docker configuration.

Then:

```text
Build B
```

running as the same operating-system account may encounter that state.

This is one reason static shared agents require careful credential and workspace design.

---

# 58. `docker logout`

After publishing:

```bash
docker logout
```

or:

```bash
docker logout REGISTRY_HOST
```

can remove the login credentials for that registry from Docker's client configuration.

For Docker Hub:

```bash
docker logout
```

may be sufficient for the default registry context.

For explicit registries, use the registry hostname.

---

# 59. `docker logout` Is Good Hygiene, Not Complete Isolation

Logging out is useful.

But strong CI isolation may also require:

```text
Dedicated agent users
Ephemeral agents
Per-build Docker configuration directories
Credential helpers
Short-lived credentials
Separate trust zones
```

Production security should not depend only on remembering to call:

```bash
docker logout
```

---

# 60. A Cleaner Per-Build Docker Configuration

Docker respects:

```text
DOCKER_CONFIG
```

You can point it to a build-specific directory.

Conceptually:

```bash
export DOCKER_CONFIG="$WORKSPACE/.docker-ci"
mkdir -p "$DOCKER_CONFIG"
```

Then registry login state for that build is kept in:

```text
$WORKSPACE/.docker-ci
```

rather than the Jenkins user's normal:

```text
~/.docker
```

This can improve isolation on static agents.

# 61. Protect the Temporary Docker Config

Use:

```bash
umask 077
```

before creating sensitive files/directories where appropriate.

Example:

```bash
umask 077
mkdir -p "$DOCKER_CONFIG"
```

Then remove the temporary configuration during cleanup.

Never archive it.

Never commit it.

# 76. Pull by Digest

For exact content selection, container tooling supports digest references.



# 77. Tag Pull vs Digest Pull

### Tag pull

```text
repository:tag
```

Human-friendly.

But the tag may move.

### Digest pull

```text
repository@sha256:...
```

Content-specific.

For production deployments requiring strong reproducibility, digest pinning is valuable.

You can still retain human-readable tags for operational convenience.

# 101. Final Jenkinsfile

The following Jenkinsfile combines Part 13 and Part 14 concepts.

Replace:

```text
YOUR_DOCKERHUB_NAMESPACE
```

with your actual registry namespace.

Create the Jenkins credential:

```text
dockerhub-veriqta-push
```

before running the Pipeline.

```groovy
pipeline {
    agent {
        label 'linux && docker'
    }

    options {
        timestamps()
        disableConcurrentBuilds()
        timeout(time: 40, unit: 'MINUTES')
        buildDiscarder(
            logRotator(
                numToKeepStr: '30',
                artifactNumToKeepStr: '20'
            )
        )
    }

    environment {
        REGISTRY_HOST = 'docker.io'
        IMAGE_NAMESPACE = 'YOUR_DOCKERHUB_NAMESPACE'
        IMAGE_NAME = 'veriqta-docker-app'

        CONTAINER_PREFIX = 'veriqta-registry-test'

        DOCKER_CONFIG = "${WORKSPACE}/.docker-ci"
    }

    stages {
        stage('Environment Verification') {
            steps {
                sh '''
                    set -eu

                    echo "=== Jenkins ==="
                    echo "Job: $JOB_NAME"
                    echo "Build: $BUILD_NUMBER"
                    echo "Node: $NODE_NAME"

                    echo
                    echo "=== Host ==="
                    hostname
                    whoami
                    id

                    echo
                    echo "=== Docker ==="
                    docker version

                    echo
                    echo "=== Git ==="
                    git --version
                    git rev-parse HEAD
                '''
            }
        }

        stage('Source Verification') {
            steps {
                sh '''
                    set -eu

                    test -f Dockerfile
                    test -f .dockerignore
                    test -f app.py
                    test -f requirements.txt
                    test -f tests/test_app.py

                    echo "Required source files are present."
                '''
            }
        }

        stage('Generate Version') {
            steps {
                script {
                    env.GIT_COMMIT_FULL = sh(
                        script: 'git rev-parse HEAD',
                        returnStdout: true
                    ).trim()

                    env.SHORT_SHA = sh(
                        script: 'git rev-parse --short=12 HEAD',
                        returnStdout: true
                    ).trim()

                    env.IMAGE_TAG =
                        "${env.BUILD_NUMBER}-${env.SHORT_SHA}"

                    env.IMAGE_REPOSITORY =
                        "${env.REGISTRY_HOST}/${env.IMAGE_NAMESPACE}/${env.IMAGE_NAME}"

                    env.FULL_IMAGE =
                        "${env.IMAGE_REPOSITORY}:${env.IMAGE_TAG}"

                    env.CONTAINER_NAME =
                        "${env.CONTAINER_PREFIX}-${env.BUILD_NUMBER}"
                }

                echo "Git commit: ${env.GIT_COMMIT_FULL}"
                echo "Image tag: ${env.IMAGE_TAG}"
                echo "Image reference: ${env.FULL_IMAGE}"
            }
        }

        stage('Build Image') {
            steps {
                sh '''
                    set -eu

                    docker build \
                      -t "$FULL_IMAGE" \
                      .
                '''
            }
        }

        stage('Inspect Image') {
            steps {
                sh '''
                    set -eu

                    echo "=== Local Image ==="

                    docker image inspect \
                      --format 'ID={{.Id}}' \
                      "$FULL_IMAGE"

                    docker image history "$FULL_IMAGE"
                '''
            }
        }

        stage('Test Image') {
            steps {
                sh '''
                    set -eu

                    docker run \
                      --rm \
                      "$FULL_IMAGE" \
                      pytest -v
                '''
            }
        }

        stage('Runtime Smoke Test') {
            steps {
                sh '''
                    set -eu

                    docker rm -f "$CONTAINER_NAME" \
                      >/dev/null 2>&1 || true

                    docker run \
                      --name "$CONTAINER_NAME" \
                      -d \
                      -p 5000 \
                      "$FULL_IMAGE"

                    HOST_PORT="$(
                      docker port "$CONTAINER_NAME" 5000/tcp \
                      | head -n 1 \
                      | awk -F: '{print $NF}'
                    )"

                    test -n "$HOST_PORT"

                    attempt=1

                    while [ "$attempt" -le 15 ]; do
                        if curl \
                            --fail \
                            --silent \
                            --show-error \
                            "http://127.0.0.1:$HOST_PORT/health"; then

                            echo
                            echo "Pre-push health check passed."
                            exit 0
                        fi

                        attempt=$((attempt + 1))
                        sleep 2
                    done

                    echo "Pre-push health check failed."
                    docker logs "$CONTAINER_NAME" || true
                    exit 1
                '''
            }

            post {
                always {
                    sh '''
                        docker logs "$CONTAINER_NAME" \
                          >/dev/null 2>&1 || true

                        docker rm -f "$CONTAINER_NAME" \
                          >/dev/null 2>&1 || true
                    '''
                }
            }
        }

        stage('Prepare Docker Authentication') {
            steps {
                sh '''
                    set -eu

                    rm -rf "$DOCKER_CONFIG"

                    umask 077
                    mkdir -p "$DOCKER_CONFIG"
                '''
            }
        }

        stage('Registry Login') {
            steps {
                withCredentials([
                    usernamePassword(
                        credentialsId: 'dockerhub-veriqta-push',
                        usernameVariable: 'REGISTRY_USER',
                        passwordVariable: 'REGISTRY_TOKEN'
                    )
                ]) {
                    sh '''
                        set -eu
                        set +x

                        printf '%s' "$REGISTRY_TOKEN" |
                          docker login \
                            --username "$REGISTRY_USER" \
                            --password-stdin
                    '''
                }
            }
        }

        stage('Push Image') {
            steps {
                sh '''
                    set -eu

                    echo "Pushing versioned image:"
                    echo "$FULL_IMAGE"

                    docker push "$FULL_IMAGE"
                '''
            }
        }

        stage('Verify Registry Artifact') {
            steps {
                sh '''
                    set -eu

                    echo "=== Registry Artifact ==="

                    docker buildx imagetools inspect \
                      "$FULL_IMAGE"
                '''
            }
        }

        stage('Create Build Metadata') {
            steps {
                sh '''
                    set -eu

                    mkdir -p artifacts

                    cat > artifacts/build-info.txt <<EOF
Application=$IMAGE_NAME
JenkinsJob=$JOB_NAME
JenkinsBuild=$BUILD_NUMBER
GitCommit=$GIT_COMMIT_FULL
ImageRepository=$IMAGE_REPOSITORY
ImageTag=$IMAGE_TAG
ImageReference=$FULL_IMAGE
EOF

                    cat artifacts/build-info.txt
                '''

                archiveArtifacts(
                    artifacts: 'artifacts/build-info.txt',
                    fingerprint: true
                )
            }
        }

        stage('Pull Verification') {
            steps {
                sh '''
                    set -eu

                    echo "Removing local image reference before pull verification."

                    docker image rm "$FULL_IMAGE"

                    echo
                    echo "Pulling exact artifact from registry."

                    docker pull "$FULL_IMAGE"

                    echo
                    echo "Verifying pulled image."

                    docker image inspect "$FULL_IMAGE" \
                      >/dev/null

                    docker run \
                      --rm \
                      "$FULL_IMAGE" \
                      pytest -v
                '''
            }
        }

        stage('Verify Pulled Application') {
            steps {
                sh '''
                    set -eu

                    docker rm -f "$CONTAINER_NAME" \
                      >/dev/null 2>&1 || true

                    docker run \
                      --name "$CONTAINER_NAME" \
                      -d \
                      -p 5000 \
                      "$FULL_IMAGE"

                    HOST_PORT="$(
                      docker port "$CONTAINER_NAME" 5000/tcp \
                      | head -n 1 \
                      | awk -F: '{print $NF}'
                    )"

                    test -n "$HOST_PORT"

                    attempt=1

                    while [ "$attempt" -le 15 ]; do
                        if curl \
                            --fail \
                            --silent \
                            --show-error \
                            "http://127.0.0.1:$HOST_PORT/health"; then

                            echo
                            echo "Pulled artifact health check passed."
                            exit 0
                        fi

                        attempt=$((attempt + 1))
                        sleep 2
                    done

                    echo "Pulled artifact failed health verification."

                    docker logs "$CONTAINER_NAME" || true

                    exit 1
                '''
            }
        }
    }

    post {
        success {
            echo "Artifact publishing workflow completed successfully."
            echo "Published: ${env.FULL_IMAGE}"
        }

        failure {
            echo "Artifact publishing workflow failed."

            sh '''
                echo "=== Diagnostic Information ==="

                if [ -n "${CONTAINER_NAME:-}" ]; then
                    docker logs "$CONTAINER_NAME" || true
                fi

                if [ -n "${FULL_IMAGE:-}" ]; then
                    docker image inspect "$FULL_IMAGE" || true
                fi
            '''
        }

        cleanup {
            sh '''
                echo "=== Cleanup ==="

                if [ -n "${CONTAINER_NAME:-}" ]; then
                    docker rm -f "$CONTAINER_NAME" \
                      >/dev/null 2>&1 || true
                fi

                docker logout \
                  >/dev/null 2>&1 || true

                if [ -n "${DOCKER_CONFIG:-}" ]; then
                    rm -rf "$DOCKER_CONFIG"
                fi

                echo "Temporary container and Docker authentication state cleaned."
            '''
        }
    }
}
```

# 103. Important Note About `DOCKER_CONFIG`

The Pipeline uses:

# 182. Common Beginner Mistakes

## Mistake 1: Leaving images only on Jenkins

The build machine is not the artifact distribution architecture.

## Mistake 2: Using `latest` as the only version

Traceability is weak.

## Mistake 3: Hardcoding registry credentials

Secrets must stay out of source.

## Mistake 4: Printing the token

Masking is not a reason to expose secrets intentionally.

## Mistake 5: Using administrator credentials for CI

Use least privilege.

## Mistake 6: Assuming login means push permission

Authentication and authorization differ.

## Mistake 7: Pushing before tests

Publish validated artifacts according to your release process.

## Mistake 8: Rebuilding during pull verification

Verify the stored artifact, not a new build.

## Mistake 9: Not recording the Git commit

You lose source traceability.

## Mistake 10: Not recording the Jenkins build

You lose CI traceability.

## Mistake 11: Ignoring digests

Tags alone may be movable.

## Mistake 12: Reusing an immutable-style version for different content

This destroys artifact trust.

## Mistake 13: Keeping registry login state indefinitely on shared agents

Authentication state should be controlled.

## Mistake 14: Archiving `.docker/config.json`

This can expose authentication material.

## Mistake 15: Giving untrusted PRs publishing credentials

This creates a serious supply-chain risk.

## Mistake 16: Deleting every old image

You may destroy rollback capability.

## Mistake 17: Never deleting anything

Storage grows indefinitely.

## Mistake 18: Confusing Jenkins retention with registry retention

They are separate systems.

## Mistake 19: Blindly pruning the Docker agent

You may delete unrelated resources/cache.

## Mistake 20: Treating the registry as source control

The registry stores built artifacts, not your primary source history.
