# 1. Start With the Problem, Not Jenkins

Imagine you have built a web application.

The application lives on a Linux server.

A developer makes a change to the application.

How does that change reach the users?

Without automation, the process might look something like this:

```text
Developer
    ↓
Change application code
    ↓
Test code locally
    ↓
Send or upload code
    ↓
Log in to production server
    ↓
Copy new files
    ↓
Install dependencies
    ↓
Run tests
    ↓
Build application
    ↓
Stop old application
    ↓
Start new application
    ↓
Check application
    ↓
Tell team deployment finished
```

A person may perform almost every step.

That works.

But it introduces an important problem:

```text
Software delivery depends heavily on humans performing
the correct steps, in the correct order, every time.
```

Suppose one engineer remembers to run the tests.

Another forgets.

One engineer installs the correct dependencies.

Another installs a different version.

One engineer follows the deployment document.

Another skips a step because they have deployed the application many times before.

Eventually, something goes wrong.

This is one of the problems CI/CD systems attempt to solve.

---

# 2. What Is Jenkins?

Jenkins is an open-source automation server.

That sentence contains two important ideas.

First:

```text
automation
```

Second:

```text
server
```

Let's separate them.

## Automation

Automation means making a computer perform repeatable work instead of requiring a human to perform every step manually.

For example, instead of an engineer manually doing:

```text
download code
install dependencies
run tests
build application
create artifact
deploy application
```

an automated process can perform those operations.

Conceptually:

```text
Developer changes code
        ↓
Automation starts
        ↓
Download code
        ↓
Install dependencies
        ↓
Run tests
        ↓
Build
        ↓
Package
        ↓
Deploy
        ↓
Verify
```

The important point is not simply that automation is faster.

Automation also makes a process repeatable.

The same instructions can run again and again.

## Server

Jenkins is not merely a command that builds software.

It runs as a service and coordinates automation work.

Jenkins can:

* Receive requests.
* Detect events.
* Schedule work.
* Run commands.
* Coordinate other machines.
* Track build results.
* Store build history.
* Manage pipelines.
* Use credentials.
* Connect to external tools.
* Report whether automation succeeded or failed.

So a more useful beginner definition is:

> Jenkins is an automation server that coordinates repeatable software engineering tasks, particularly building, testing, packaging, and delivering software.

Jenkins is heavily associated with CI/CD, but Jenkins itself is a general automation system.

---

# 3. Why Does Jenkins Exist?

Software engineering involves many repetitive processes.

A developer might need to:

1. Retrieve source code.
2. Install dependencies.
3. Compile the application.
4. Run tests.
5. Perform quality checks.
6. Perform security checks.
7. Package the application.
8. Build a container image.
9. Upload an artifact.
10. Deploy the application.
11. Verify the deployment.
12. Notify the team.

Doing this manually becomes increasingly difficult as:

* The application grows.
* More developers join.
* Releases become more frequent.
* More environments appear.
* Testing increases.
* Infrastructure becomes more complicated.

Consider a team with ten developers.

If every developer manually performs a different version of the release process, consistency becomes difficult.

Jenkins allows the organization to describe the process and automate much of it.

Instead of:

```text
Engineer remembers deployment process
```

you move toward:

```text
Deployment process is defined
        ↓
Jenkins executes it consistently
```

That difference is fundamental.

---

# 4. The Problem Jenkins Helps Solve

Jenkins helps address several related problems.

## Problem 1: Repetitive manual work

If engineers repeatedly execute the same commands, those commands are candidates for automation.

For example:

```bash
npm install
npm test
npm run build
```

Running three commands once is easy.

Running them correctly across hundreds or thousands of software changes is different.

---

## Problem 2: Human error

Suppose the documented deployment procedure says:

```text
1. Download code
2. Install dependencies
3. Run tests
4. Build
5. Back up current release
6. Deploy
7. Restart service
8. Run health check
```

An engineer accidentally performs:

```text
1. Download code
2. Install dependencies
3. Build
4. Deploy
5. Restart
```

Tests and backup were skipped.

Automation helps make the process consistent.

It does not eliminate all errors. Engineers can still create incorrect automation.

But it reduces dependence on humans remembering repetitive procedures.

---

## Problem 3: Slow feedback

Imagine a developer creates a bug at 9:00 AM.

Nobody runs the full test suite until Friday.

The defect may remain hidden for days.

With CI, the workflow can become:

```text
Developer pushes change
        ↓
Pipeline starts
        ↓
Tests run
        ↓
Test fails
        ↓
Developer receives feedback
```

The developer discovers the problem much earlier.

---

## Problem 4: "It works on my machine"

A developer might say:

```text
It works on my laptop.
```

But the application fails elsewhere.

Why?

Possible causes include:

* Different dependency versions.
* Different operating systems.
* Missing environment variables.
* Different runtime versions.
* Different configuration.
* Uncommitted files.
* Different build procedures.

Automated build environments improve consistency.

They do not magically make all environments identical, but they make the build process much more controlled.

---

## Problem 5: No clear record of what happened

Manual deployments can create questions such as:

* Who deployed this?
* Which commit was deployed?
* Which tests ran?
* Did they pass?
* Which artifact was created?
* When did the deployment happen?
* Which step failed?

Automation systems provide execution history that helps answer these questions.

---

# 5. Manual Software Delivery Before CI/CD

Let's examine a fictional company called ShopNow.

ShopNow has a web application.

The application runs on a Linux server.

A simplified architecture looks like this:

```text
Customer
   ↓
Internet
   ↓
Linux Server
   ↓
ShopNow Application
```

A developer changes the checkout page.

Without CI/CD, deployment might work like this.

### Step 1: Developer changes code

```text
Developer Laptop
       ↓
Application Code
```

### Step 2: Developer tests locally

The developer runs tests on their own computer.

### Step 3: Developer sends the code

This could historically involve:

* ZIP files.
* FTP.
* SCP.
* Shared folders.
* Git.
* Email attachments in poorly controlled environments.

### Step 4: Someone accesses the server

For example:

```bash
ssh deployer@app-server
```

### Step 5: Files are updated

Perhaps:

```bash
git pull
```

or files are manually copied.

### Step 6: Dependencies are installed

For example:

```bash
npm install
```

### Step 7: Application is built

For example:

```bash
npm run build
```

### Step 8: Application is restarted

Perhaps:

```bash
sudo systemctl restart shopnow
```

### Step 9: Someone checks the application

They open a browser.

If the homepage loads, they may assume deployment succeeded.

But did checkout work?

Did the API work?

Did the database connection work?

Did logs contain errors?

A basic homepage check may not answer those questions.

---

# 6. The Manual Delivery Problem at Scale

Imagine this happens once per month.

It might be manageable.

Now imagine:

```text
20 developers
50 changes per day
multiple applications
development environment
test environment
staging environment
production environment
hundreds of automated tests
security checks
container builds
cloud deployments
```

Manual execution becomes increasingly unreliable and expensive.

This leads us to CI/CD.

# 7. What Is CI/CD?

CI/CD is commonly used as a combined term, but it represents separate practices.

At a high level:

```text
CI = continuously integrate and validate software changes

CD = make validated changes reliably deliverable or deploy them
```

A simplified workflow might look like:

```text
Developer
    ↓
Git
    ↓
CI
    ↓
Build
    ↓
Test
    ↓
Package
    ↓
CD
    ↓
Environment
```

Let's examine each concept separately.

---

# 8. Continuous Integration

Continuous Integration is commonly shortened to:

```text
CI
```

The core idea is that developers integrate changes frequently into a shared source-code repository, with automated validation used to detect problems quickly.

Imagine three developers:

```text
Developer A ─┐
Developer B ─┼──→ Shared Repository
Developer C ─┘
```

Every change can trigger automated checks.

For example:

```text
Developer
    ↓
Push code
    ↓
Repository
    ↓
CI starts
    ↓
Checkout code
    ↓
Install dependencies
    ↓
Build
    ↓
Test
    ↓
Report result
```

If something fails:

```text
Change
  ↓
CI Pipeline
  ↓
TEST FAILED
  ↓
Developer investigates
```

This creates rapid feedback.

## CI is not simply "Jenkins runs tests"

CI is a development practice.

Jenkins is one tool that can help implement that practice.

This distinction matters.

```text
Continuous Integration = engineering practice

Jenkins = automation technology that can implement CI
```

---

# 9. A Simple CI Example

Suppose our repository contains:

```text
shopnow/
├── src/
├── tests/
├── package.json
└── README.md
```

A developer pushes a change.

The CI process could perform:

```text
1. Download repository
2. Install dependencies
3. Run tests
4. Build application
5. Report success/failure
```

Conceptually:

```text
Git Push
   ↓
Jenkins
   ↓
Checkout
   ↓
Dependencies
   ↓
Tests
   ↓
Build
   ↓
Result
```

If tests fail, Jenkins should not pretend everything is fine.

The pipeline should fail.

That failure is useful information.

---

# 10. Why Frequent Integration Matters

Imagine Developer A works independently for three months.

Developer B also works independently for three months.

When their work is finally combined, there may be hundreds of conflicts and incompatible changes.

This is sometimes described as integration hell.

Frequent integration aims to detect incompatibilities earlier.

Instead of:

```text
Huge change
     ↓
Huge integration
     ↓
Huge problem
```

you aim for:

```text
Small change → Validate

Small change → Validate

Small change → Validate
```

Smaller feedback loops generally make problems easier to identify.

---

# 11. What Is Continuous Delivery?

Continuous Delivery extends beyond integration.

The goal is to keep software in a state where it can be released reliably.

A simplified process:

```text
Developer
    ↓
Commit
    ↓
Build
    ↓
Tests
    ↓
Quality checks
    ↓
Package
    ↓
Deploy to staging
    ↓
Verification
    ↓
Ready for production
```

Production release may still require a deliberate decision.

For example:

```text
Pipeline
   ↓
Build
   ↓
Test
   ↓
Staging
   ↓
Approval
   ↓
Production
```

The key point is that the software remains deployable.

---

# 12. What Is Continuous Deployment?

Continuous Deployment goes one step further.

Validated changes can automatically reach production without requiring a manual release approval for each change.

Example:

```text
Developer Push
      ↓
Automated Build
      ↓
Automated Tests
      ↓
Security Checks
      ↓
Artifact
      ↓
Deployment
      ↓
Production Verification
```

If all required controls succeed, deployment proceeds automatically.

This does not mean:

```text
push random code directly into production
```

A mature continuous deployment system can have extensive automated controls.

---

# 13. Continuous Delivery vs Continuous Deployment

These terms are often confused.

| Concept                | Main idea                                               |
| ---------------------- | ------------------------------------------------------- |
| Continuous Integration | Integrate and automatically validate changes frequently |
| Continuous Delivery    | Keep validated software ready for reliable release      |
| Continuous Deployment  | Automatically deploy qualifying changes to production   |

A simplified comparison:

```text
CONTINUOUS DELIVERY

Code
 ↓
Build
 ↓
Test
 ↓
Package
 ↓
Ready
 ↓
Human/controlled release decision
 ↓
Production
```

Compared with:

```text
CONTINUOUS DEPLOYMENT

Code
 ↓
Build
 ↓
Test
 ↓
Package
 ↓
Automated deployment controls
 ↓
Production
```

The difference is primarily what happens near the production release boundary.

# 14. What Does "CI/CD Pipeline" Mean?

A pipeline is an organized sequence of automated activities.

For example:

```text
Checkout
   ↓
Build
   ↓
Test
   ↓
Package
   ↓
Deploy
```

You can think of each major section as a stage.

For example:

```text
Pipeline
│
├── Stage: Checkout
├── Stage: Build
├── Stage: Test
├── Stage: Package
└── Stage: Deploy
```

Inside each stage are individual actions.

Those actions are often called steps.

For example:

```text
Stage: Test
│
├── Step: Install test dependencies
├── Step: Run unit tests
└── Step: Publish test results
```

This gives us:

```text
Pipeline
   ↓
Stages
   ↓
Steps
```

We will return to these terms shortly.

---

# 15. What Is an Automation Server?

An automation server coordinates automated tasks.

Imagine Jenkins receives an instruction:

```text
Build ShopNow
```

Jenkins needs to determine:

* What job or pipeline defines the work?
* Is a machine available to run it?
* Which machine should run it?
* Which code should be downloaded?
* Which credentials are needed?
* Which commands should execute?
* What happens if a command fails?
* What result should be recorded?

So Jenkins acts as an automation coordinator.

A simplified model:

```text
             ┌─────────────┐
             │   Jenkins   │
             │ Controller  │
             └──────┬──────┘
                    │
        ┌───────────┼───────────┐
        ↓           ↓           ↓
     Agent 1     Agent 2     Agent 3
        ↓           ↓           ↓
      Build        Test       Deploy
```

Do not worry if "controller" and "agent" are unfamiliar.

We will define them now.

---

# 16. Jenkins Architecture at Beginner Level

The two most important architectural concepts to learn first are:

```text
Controller
Agents
```

A simplified Jenkins environment can look like:

```text
Developer
    ↓
Git Repository
    ↓
Jenkins Controller
    ↓
Jenkins Agent
    ↓
Build / Test / Automation
```

The controller coordinates.

Agents perform assigned work.

That distinction becomes very important as Jenkins environments grow.

---

# 17. Jenkins Controller

The Jenkins controller is the central Jenkins process responsible for coordinating the Jenkins environment.

It handles responsibilities such as:

* Jenkins configuration.
* User interface.
* Job configuration.
* Pipeline coordination.
* Scheduling.
* Build queue management.
* Agent management.
* Credentials configuration.
* Plugin management.
* Build history.

Think of it as the coordinator.

```text
                  Jenkins Controller
                         │
             ┌───────────┼───────────┐
             ↓           ↓           ↓
          Agent A     Agent B     Agent C
```

The controller decides where eligible work should run.

## Important terminology note

Older Jenkins material may use the term:

```text
master
```

Modern Jenkins terminology uses:

```text
controller
```

Similarly, older documentation may use "slave" where modern terminology uses "agent."

When reading older tutorials, understanding these older terms helps, but use the current terminology in new documentation and designs.

---

# 18. Jenkins Agent

A Jenkins agent is a machine or execution environment connected to the Jenkins controller and available to execute work.

For example:

```text
Controller
    │
    ├── Linux Agent
    │      ↓
    │   Linux builds
    │
    ├── Windows Agent
    │      ↓
    │   Windows builds
    │
    └── Docker-capable Agent
           ↓
       Container builds
```

Agents can provide different environments and capabilities.

A Jenkins environment might eventually have:

```text
Agent 1 → Java builds

Agent 2 → Node.js builds

Agent 3 → Docker builds

Agent 4 → Integration testing
```

You do not need multiple agents to begin learning Jenkins.

Part 2 will start much more simply.

---

# 19. Why Separate the Controller From Build Work?

Imagine Jenkins has 100 builds to process.

If the same machine is responsible for:

* Jenkins administration.
* Web interface.
* Scheduling.
* Plugin operations.
* Every compilation.
* Every test.
* Every container build.

heavy workloads can affect the Jenkins controller itself.

There are also security and isolation concerns.

Production Jenkins environments commonly separate orchestration responsibilities from build execution rather than treating the controller as a general-purpose build machine.

For now, remember:

```text
Controller = coordinates

Agent = executes assigned work
```

---

# 20. What Is a Jenkins Job?

A job is a configured unit of work in Jenkins.

A job could mean:

```text
Run tests
```

or:

```text
Build application
```

or:

```text
Deploy application
```

or a larger automation process.

For example:

```text
Job Name:
shopnow-build

Purpose:
Build the ShopNow application
```

The job defines what Jenkins should do.

---

# 21. Job vs Build

These two words are easy to confuse.

A job is the definition.

A build is an execution of that definition.

Suppose we have:

```text
Job:
shopnow-test
```

You run it three times.

Jenkins may record:

```text
Build #1
Build #2
Build #3
```

Therefore:

```text
JOB
= instructions/configuration for work

BUILD
= one execution of those instructions
```

Analogy:

```text
Recipe = Job

Cooking the recipe tonight = Build
```

The recipe remains.

You can execute it repeatedly.

---

# 22. What Is a Jenkins Pipeline?

A Jenkins Pipeline represents an automated workflow, commonly expressed as a sequence of stages and steps.

For example:

```text
Pipeline: shopnow-ci

Checkout
   ↓
Build
   ↓
Test
   ↓
Package
```

Later, we will store pipeline definitions in a file called:

```text
Jenkinsfile
```

That allows the automation process to live alongside the application source code.

For now, concentrate on the mental model:

```text
Pipeline
   ↓
Stage
   ↓
Steps
```

---

# 23. What Is a Stage?

A stage is a logical section of a pipeline.

Example:

```text
Pipeline
│
├── Checkout
├── Build
├── Test
├── Package
└── Deploy
```

Each represents a meaningful phase.

Stages make the pipeline easier to understand and diagnose.

If Jenkins reports:

```text
Checkout  ✓
Build     ✓
Test      ✗
Package   -
Deploy    -
```

you immediately know the test stage failed.

Later stages may not have executed because of that failure.

---

# 24. What Is a Step?

A step is an individual operation performed inside a pipeline.

Example:

```text
Stage: Test
```

might contain:

```text
Step 1 → Run unit tests

Step 2 → Collect test results

Step 3 → Publish report
```

So:

```text
Pipeline
└── Stage
    └── Step
```

A more complete example:

```text
Pipeline
│
├── Stage: Checkout
│   └── Step: Download source code
│
├── Stage: Build
│   ├── Step: Install dependencies
│   └── Step: Compile application
│
├── Stage: Test
│   ├── Step: Run unit tests
│   └── Step: Publish test results
│
└── Stage: Package
    └── Step: Create artifact
```

---

# 25. Job, Build, Pipeline, Stage, and Step Together

This is worth understanding before continuing.

| Term     | Meaning                                     |
| -------- | ------------------------------------------- |
| Job      | A configured Jenkins task                   |
| Build    | One execution of a job                      |
| Pipeline | An automated workflow                       |
| Stage    | A logical phase of the pipeline             |
| Step     | An individual operation inside the pipeline |

Example:

```text
JOB
shopnow-pipeline
       │
       ↓
BUILD #42
       │
       ↓
PIPELINE
       │
       ├── STAGE: Checkout
       │      └── STEP: Get source code
       │
       ├── STAGE: Build
       │      └── STEP: Compile
       │
       └── STAGE: Test
              └── STEP: Run tests
```

# 26. What Is a Workspace?

When Jenkins executes work, it needs somewhere to place files.

That location is called a workspace.

Imagine Jenkins retrieves:

```text
shopnow/
├── src/
├── tests/
├── package.json
└── README.md
```

Jenkins needs a filesystem location where these files can exist while the job runs.

Conceptually:

```text
Jenkins Agent
     ↓
Workspace
     ↓
Source Code
     ↓
Build Files
     ↓
Test Files
```

Commands usually operate against files inside that working environment.

## Workspace is not the same as the Git repository

The remote Git repository might exist on GitHub.

The workspace contains a checked-out working copy used during execution.

Conceptually:

```text
GitHub Repository
       ↓
     checkout
       ↓
Jenkins Workspace
```

---

# 27. What Is an Artifact?

An artifact is an output produced by a software build or related process that you want to retain, distribute, or deploy.

Examples include:

```text
.jar
.war
.zip
.tar.gz
binary executable
package
container image
```

Suppose source code enters the pipeline:

```text
Source Code
    ↓
Build
    ↓
shopnow-1.4.0.jar
```

The `.jar` is a build artifact.

The important distinction is:

```text
Source code = input

Artifact = produced output
```

A mature delivery process tries to maintain traceability between source code and the exact artifact eventually deployed.

---

# 28. Why Artifacts Matter

Imagine you build version 1.4.

Tests pass.

Then you rebuild "the same" application later for production.

Could something have changed?

Potentially:

* Dependency versions.
* Build environment.
* External repositories.
* Tool versions.
* Build configuration.

A stronger pattern is often:

```text
Build once
    ↓
Test artifact
    ↓
Store artifact
    ↓
Promote same artifact
    ↓
Deploy
```

rather than repeatedly rebuilding different outputs for each environment.

You will explore artifact management later in the Jenkins series.

# 29. What Is a Jenkins Plugin?

Jenkins has a core system, but much of its ecosystem functionality comes through plugins.

Plugins extend Jenkins.

For example, plugins can help Jenkins integrate with technologies and provide features involving:

* Git.
* GitHub.
* Credentials.
* Pipeline functionality.
* Test reporting.
* Cloud environments.
* Notifications.
* Build tools.
* Authorization.

Conceptually:

```text
              Jenkins
                 │
        ┌────────┼────────┐
        ↓        ↓        ↓
       Git    Pipeline   Other
      Plugin   Plugin   Plugins
```

This extensibility is one reason Jenkins can support many different environments.

But plugins also introduce operational responsibilities.

Plugins must be:

* Selected carefully.
* Updated.
* Monitored for security issues.
* Checked for compatibility.
* Removed when unnecessary.

More plugins are not automatically better.

# 30. What Are Jenkins Credentials?

Automation frequently needs authentication.

For example, Jenkins may need to:

```text
Clone private repository
        ↓
Log in to container registry
        ↓
Connect to deployment server
        ↓
Access cloud platform
```

That may require:

* Username/password.
* Token.
* SSH private key.
* Secret text.
* Certificate.

These are credentials.

A dangerous approach would be putting secrets directly inside pipeline code:

```text
password = "SuperSecretPassword123"
```

Do not build systems this way.

Jenkins provides credential-management mechanisms so pipelines can refer to stored credentials without treating secrets like ordinary source code.

Conceptually:

```text
Jenkinsfile
    ↓
Credential ID
    ↓
Jenkins Credentials Store
    ↓
Secret provided only when needed
```

We will handle this properly in Part 10.

For now, remember:

> Secrets do not belong hardcoded in source code or Jenkinsfiles.

# 31. What Is a Trigger?

Something must tell Jenkins when work should begin.

That event or mechanism is a trigger.

Examples include:

### Manual trigger

Someone selects:

```text
Build Now
```

### Code event

```text
Developer pushes code
        ↓
GitHub
        ↓
Webhook
        ↓
Jenkins
```

### Schedule

For example:

```text
Run every night
```

### Source control polling

Jenkins periodically checks whether source code has changed.

Different triggers are appropriate for different workflows.

A useful mental model is:

```text
EVENT
  ↓
TRIGGER
  ↓
JOB / PIPELINE
  ↓
BUILD
```

---

# 32. What Is an Executor?

An executor represents a slot on a Jenkins node that can execute work.

Imagine an agent configured with two executors.

Conceptually:

```text
Agent
│
├── Executor 1 → Build A
│
└── Executor 2 → Build B
```

If both executors are occupied and another eligible build arrives:

```text
Build C
```

it may have to wait.

Which brings us to the build queue.

---

# 33. What Is the Jenkins Build Queue?

The build queue holds work waiting for an available execution opportunity.

Imagine:

```text
Agent
Executors: 2
```

Current activity:

```text
Executor 1 → Build #20

Executor 2 → Build #21
```

Then three more builds arrive:

```text
Build #22
Build #23
Build #24
```

They cannot all execute immediately on those two occupied executor slots.

Conceptually:

```text
BUILD QUEUE

#22
#23
#24
 ↓
waiting
 ↓
Executor becomes available
 ↓
Eligible build starts
```

The controller helps schedule queued work onto suitable available executors.

---

# 34. Controller, Agent, Executor, and Queue Together

Now we can connect the architecture.

```text
                     Jenkins Controller
                            │
                            │ schedules work
                            ↓
```

# 56. Failure Thinking Exercise

Consider this pipeline:

```text
Checkout
   ↓
Build
   ↓
Test
   ↓
Package
   ↓
Deploy
```

Suppose `Test` fails.

What should happen?

A poorly designed process might continue:

```text
Test ✗
  ↓
Package
  ↓
Deploy broken application
```

A safer pipeline normally prevents downstream deployment when a required validation stage fails:

```text
Checkout ✓
   ↓
Build ✓
   ↓
Test ✗
   ↓
STOP

Package SKIPPED
Deploy SKIPPED
```

A failed pipeline is therefore not necessarily a failed CI/CD system.

Sometimes failure means the system successfully prevented a bad change from progressing.

That is an important mindset.

# 57. Common Beginner Misunderstandings

### "Jenkins is a programming language."

No.

Jenkins is an automation server.

Pipeline definitions can involve Jenkins Pipeline syntax and Groovy-related constructs, but Jenkins itself is not a programming language.

### "Jenkins is Git."

No.

Git provides version control.

Jenkins automates workflows that can use Git.

### "Jenkins builds applications itself."

More precisely, Jenkins coordinates and executes build commands using the required tools.

For example:

```text
Jenkins → Maven → Java build
Jenkins → npm → Node.js build
Jenkins → Docker → image build
```

### "CI means deployment."

No.

CI primarily concerns frequent integration and automated validation.

Deployment belongs to the delivery/deployment side of the lifecycle.

### "Continuous Delivery and Continuous Deployment are identical."

No.

Continuous Delivery keeps software releasable and may retain a deliberate production release decision.

Continuous Deployment automatically releases qualifying changes into production.

### "Jenkins should store passwords in Jenkinsfiles."

No.

Never hardcode real credentials in pipeline source.

### "If the pipeline is green, the software must be perfect."

No.

A pipeline only verifies what you designed it to verify.

If you have poor tests, a green pipeline can still deliver defective software.

Automation cannot compensate for missing engineering controls.

# 58. Security From Day One

You have not installed Jenkins yet, but security thinking starts now.

A CI/CD server can become extremely powerful.

Imagine Jenkins eventually has credentials capable of accessing:

```text
GitHub
Container Registry
AWS
Production Servers
Kubernetes
Databases
```

If Jenkins is compromised, those integrations may increase the impact.

Therefore, Jenkins should be treated as sensitive infrastructure.

Begin with these principles:

1. Do not expose Jenkins unnecessarily to the public internet.
2. Do not hardcode secrets.
3. Use least privilege.
4. Limit administrative access.
5. Keep Jenkins maintained.
6. Keep plugins maintained.
7. Install only necessary plugins.
8. Separate risky workloads appropriately.
9. Back up important Jenkins state.
10. Log and monitor important activity.
11. Protect deployment credentials.
12. Do not treat a learning configuration as production-ready.

These ideas will become practical later.
