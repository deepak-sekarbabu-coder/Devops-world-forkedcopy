# Part 8: Jenkins Build Triggers and GitHub Webhooks

## Learning Objective

In Parts 6 and 7, you learned how to define a Jenkins Pipeline in a `Jenkinsfile`.

You can now build a workflow such as:

```text
GitHub
   ↓
Jenkinsfile
   ↓
Jenkins
   ↓
Build
   ↓
Test
   ↓
Package
```

But there is still an important weakness.

Someone may still need to open Jenkins and click:

```text
Build Now
```

That is useful while learning and troubleshooting, but Continuous Integration becomes much more useful when Jenkins can respond automatically to changes.

In this part, we will build:

```text
Developer
    ↓
Git Commit
    ↓
Git Push
    ↓
GitHub
    ↓
Webhook
    ↓
Jenkins
    ↓
Pipeline
```

By the end of Part 8, you should understand four major ways a Jenkins build can start:

```text
Manual Trigger
Scheduled Trigger
SCM Polling
Webhook/Event Trigger
```

You will configure each important method, compare them, deliberately break webhook delivery, and learn how to determine exactly where automatic triggering failed.

The expected outcome is:

> A developer pushes code to GitHub and Jenkins automatically detects the event and starts the appropriate Pipeline without someone clicking Build Now.

Jenkins currently supports Declarative Pipeline triggers including `cron` and `pollSCM`. For GitHub-integrated jobs, Jenkins documentation notes that a `triggers` directive may not be necessary when webhook-based integration is already present. ([Jenkins][1])

---

# 1. Start With the Problem

Imagine a development team with ten developers.

Every developer pushes code to GitHub.

But Jenkins only builds when somebody remembers to open Jenkins and click:

```text
Build Now
```

The workflow becomes:

```text
Developer
    ↓
Changes code
    ↓
Commits code
    ↓
Pushes to GitHub
    ↓
Remembers Jenkins exists
    ↓
Opens Jenkins
    ↓
Finds job
    ↓
Clicks Build Now
    ↓
Pipeline executes
```

There are several problems here.

A developer may forget.

Someone may push broken code and nobody starts the build.

Several commits may accumulate before CI runs.

The build may happen hours later.

The team loses the rapid feedback that CI is supposed to provide.

We want:

```text
Developer pushes code
        ↓
CI automatically responds
```

That is the central problem build triggers solve.

---

# 2. What Is a Jenkins Build Trigger?

A trigger is something that causes Jenkins to start a build.

Think:

```text
EVENT
  ↓
TRIGGER
  ↓
JENKINS JOB
  ↓
PIPELINE
```

The event might be:

```text
Human clicks button
Clock reaches scheduled time
Repository changes
GitHub sends webhook
Another Jenkins job completes
```

The important distinction is:

```text
Pipeline
=
what Jenkins should do
```

while:

```text
Trigger
=
when Jenkins should start doing it
```

Do not confuse the two.

---

# 3. Trigger vs Pipeline

Suppose your Jenkinsfile contains:

```groovy
pipeline {
    agent any

    stages {
        stage('Build') {
            steps {
                echo 'Building application'
            }
        }

        stage('Test') {
            steps {
                echo 'Testing application'
            }
        }
    }
}
```

This describes:

```text
WHAT TO DO
```

It does not necessarily determine:

```text
WHEN TO START
```

The Pipeline could be started:

```text
Manually

or

On a schedule

or

After SCM polling finds changes

or

After GitHub sends a webhook
```

The same Pipeline can therefore be triggered in different ways.

# 4. The Four Trigger Models We Need to Understand

For this part, use this mental model:

```text
                     Jenkins Pipeline
                           ↑
                           │
        ┌──────────────────┼──────────────────┐
        │                  │                  │
      Human              Clock              Git
        │                  │                  │
   Build Now             Cron         ┌──────┴──────┐
                                    Polling       Webhook
```

More simply:

| Method    | Who initiates detection? |
| --------- | ------------------------ |
| Manual    | Human                    |
| Scheduled | Jenkins clock/scheduler  |
| Poll SCM  | Jenkins                  |
| Webhook   | GitHub                   |

The distinction between the last two is especially important.

# 5. Manual Builds

You already know the simplest trigger:

```text
Jenkins Dashboard
      ↓
Job
      ↓
Build Now
```

A human initiates the build.

Conceptually:

```text
Human
  ↓
Jenkins
  ↓
Pipeline
```

This is a manual trigger.

---

# 6. Manual Builds Are Not Bad

Automatic triggering does not make manual builds useless.

Manual execution is useful for:

```text
Learning
Testing Pipeline changes
Troubleshooting
Re-running failed builds
Administrative jobs
Maintenance jobs
Controlled operations
Special one-time tasks
```

For example, if you are repairing a broken Jenkinsfile, manually triggering it several times may be completely appropriate.

The problem is relying on humans for routine CI detection.

If each commit requires:



# 8. How Can We Automate Builds?

One solution is time.

Instead of waiting for a person, tell Jenkins:

> Start this job according to a schedule.

# 9. Scheduled Builds

A scheduled build starts according to time rather than source-code activity.

Example:

```text
Every night
     ↓
2:00 AM
     ↓
Jenkins starts Pipeline
```

or:

```text
Every weekday
      ↓
Jenkins starts maintenance job
```

Typical use cases include:

```text
Nightly integration tests
Scheduled security scans
Dependency checks
Maintenance
Reports
Backups
Periodic validation
```

The important idea is:

```text
Scheduled build
=
run because of time
```

not:

```text
run because code changed
```

# 10. Jenkins `cron`

Declarative Pipeline supports:

```groovy
triggers {
    cron('...')
}
```

Example:

```groovy
pipeline {
    agent any

    triggers {
        cron('H 2 * * *')
    }

    stages {
        stage('Scheduled Build') {
            steps {
                echo 'This Pipeline was scheduled.'
            }
        }
    }
}
```

Jenkins' current Declarative syntax supports `cron` as one of its built-in Pipeline triggers. ([Jenkins][1])

---

# 11. What Is Cron?

Cron is a scheduling syntax commonly used on Unix-like systems.

Jenkins uses cron-style scheduling with some Jenkins-specific behavior.

A Jenkins cron expression normally contains five fields:

```text
MINUTE HOUR DAY-OF-MONTH MONTH DAY-OF-WEEK
```

or:

```text
MINUTE  HOUR  DOM  MONTH  DOW
```

Jenkins documents the fields as minute `0-59`, hour `0-23`, day of month `1-31`, month `1-12`, and day of week `0-7`, where both `0` and `7` represent Sunday. ([Jenkins][1])

---

# 12. Read Cron From Left to Right

Example:

```text
30 8 * * *
```

Break it apart:

```text
30
│
└── minute

8
│
└── hour

*
│
└── every day of month

*
│
└── every month

*
│
└── every day of week
```

Conceptually:

```text
08:30 every day
```

But Jenkins often recommends using its `H` syntax rather than forcing many jobs onto the exact same minute.

---

# 13. Cron Wildcard `*`

The asterisk means:

```text
all valid values
```

For example:

```text
* * * * *
```

conceptually represents every valid minute across all hours, dates, months, and weekdays.

Do not use schedules carelessly on a busy Jenkins controller.

A frequently triggered job can consume substantial build capacity.

---

# 14. Cron Ranges

A range uses:

```text
M-N
```

Example:

```text
1-5
```

in the weekday field represents Monday through Friday.

Example:

```text
H 9 * * 1-5
```

means approximately:

```text
once during the 9 AM hour
Monday through Friday
```

with the exact minute determined by Jenkins' hash behavior.

---

# 15. Cron Lists

A comma can specify multiple values.

Example:

```text
H H 1,15 * *
```

means run on:

```text
1st day of month
15th day of month
```

with hashed scheduling for the minute/hour portions.

---

# 16. Cron Step Values

You can also specify intervals.

Example:

```text
H/15 * * * *
```

means approximately every 15 minutes, with Jenkins choosing a stable hash-based offset.

Jenkins gives this as an example of using `H` to distribute scheduled load rather than having every job start at exactly the same minute. ([Jenkins][1])

---

# 17. Why Jenkins Has `H`

Suppose 500 Jenkins jobs all contain:

```text
0 0 * * *
```

At midnight:

```text
Job 1 ──────┐
Job 2 ──────┤
Job 3 ──────┤
...         ├→ Jenkins
Job 500 ────┘
```

They all attempt to start together.

That creates unnecessary load spikes.

Jenkins provides:

```text
H
```

for hash-based scheduling.

Conceptually:

```text
Job A → minute 04
Job B → minute 19
Job C → minute 37
Job D → minute 52
```

The actual values are derived deterministically rather than being freshly random every time.

Jenkins recommends `H` where possible to spread load across the available time range. ([Jenkins][1])

---

# 18. Useful Jenkins Cron Examples

Examples include:

```text
H * * * *
```

approximately once every hour.

```text
H/15 * * * *
```

approximately every 15 minutes.

```text
H H * * *
```

once per day at a hash-selected time.

```text
H H * * 1-5
```

once per weekday.

```text
H 2 * * *
```

once during the 2 AM hour.

Jenkins also supports aliases such as:

```text
@hourly
@daily
@weekly
@monthly
@midnight
```

and documents that these aliases use hash-based balancing. ([Jenkins][1])

# 19. Time Zones Matter

Do not assume:

```text
2 AM in Jenkins
=
2 AM where I am sitting
```

Scheduling depends on Jenkins' configured/runtime time context.

In distributed teams, ask:

```text
What timezone is Jenkins using?

What timezone did the engineer intend?

Is daylight-saving behavior relevant?

Does the job actually need an exact clock time?
```

Always verify scheduled behavior rather than assuming it.

# 24. Scheduled Build vs Source Change

Now consider this problem.

Your Jenkins job runs:

```text
every 15 minutes
```

But developers push code at:

```text
10:02
10:06
10:09
```

A simple scheduled build does not inherently mean:

> Build only when source code changed.

It means:

> Run according to time.

What we really want for CI is:

```text
Check source repository
        ↓
Has code changed?
        ↓
YES → Build
NO  → Do nothing
```

That introduces SCM polling.

---

# 25. What Is SCM?

SCM means:

```text
Source Code Management
```

In our project:

```text
Git
```

is the version-control system.

GitHub hosts the Git repository.

So:

```text
Developer
    ↓
Git
    ↓
GitHub Repository
```

Jenkins can inspect that repository for changes.

---

# 26. What Is Poll SCM?

Polling means Jenkins periodically asks:

> Has the source code changed?

Conceptually:

```text
Jenkins
   ↓
Check Git repository
   ↓
Compare repository state
   ↓
Any relevant changes?
   ├── NO → wait
   └── YES
         ↓
       Build
```

Jenkins Declarative Pipeline supports `pollSCM` with cron-style scheduling. If new SCM changes are detected, Jenkins re-triggers the Pipeline. ([Jenkins][1])

---

# 27. Scheduled Build vs Poll SCM

This difference must be clear.

## Scheduled build

```text
Time arrives
    ↓
Run Pipeline
```

Whether source changed or not.

## Poll SCM

```text
Time arrives
    ↓
Check repository
    ↓
Changed?
    ↓
YES → Run Pipeline
NO  → No build
```

So:

```text
cron
=
schedule execution
```

while:

```text
pollSCM
=
schedule source-change checks
```

---

# 28. Declarative `pollSCM`

Example:

```groovy
triggers {
    pollSCM('H/5 * * * *')
}
```

This means Jenkins periodically checks the configured SCM according to the schedule.

If it detects relevant source changes, it can trigger a build. ([Jenkins][1])

# 34. Why Polling Is Not Always Ideal

Suppose Jenkins checks every minute.

Most checks might find:

```text
No changes.
```

Conceptually:

```text
Jenkins → GitHub: Anything changed?
GitHub → Jenkins: No.

Jenkins → GitHub: Anything changed?
GitHub → Jenkins: No.

Jenkins → GitHub: Anything changed?
GitHub → Jenkins: No.
```

This works, but it can create unnecessary repeated checks.

A more event-driven model is:

```text
GitHub stays quiet
        ↓
Developer pushes
        ↓
GitHub tells Jenkins
```

That is a webhook.

---

# 35. What Is a Webhook?

A webhook is an HTTP-based notification sent by one system to another when an event occurs.

In our case:

```text
Developer
    ↓
Git Push
    ↓
GitHub
    ↓
HTTP POST
    ↓
Jenkins webhook endpoint
    ↓
Jenkins evaluates event
    ↓
Pipeline
```

GitHub describes webhooks as HTTP requests sent to a configured URL when subscribed events occur. ([GitHub Docs][3])

---

# 36. Polling vs Webhook

## Polling

```text
Jenkins
   ↓
GitHub
   ↓
Anything changed?
```

Jenkins initiates communication.

## Webhook

```text
GitHub
   ↓
Jenkins
   ↓
Something changed.
```

GitHub initiates communication.

This difference is fundamental.

---

# 37. Doorbell Analogy

Polling is like repeatedly opening your front door:

```text
Anyone there?

Anyone there?

Anyone there?

Anyone there?
```

A webhook is like a doorbell:

```text
Someone arrives
      ↓
Doorbell rings
      ↓
You respond
```

The analogy is useful because it captures the direction of communication.

---

# 38. What Is a GitHub Push Event?

Suppose you run:

```bash
git push
```

Git sends commits to the remote GitHub repository.

GitHub records the repository update.

If a webhook is subscribed to push events, GitHub can generate a webhook delivery for that event.

Conceptually:

```text
git push
   ↓
GitHub repository updated
   ↓
push event
   ↓
webhook delivery
```

---

# 39. Webhook Delivery Is Not the Same as a Jenkins Build

This distinction is critical.

```text
GitHub sent webhook successfully
```

does not automatically prove:

```text
Jenkins started correct Pipeline successfully
```

There are several layers:

```text
Git Push
   ↓
GitHub creates event
   ↓
GitHub sends webhook
   ↓
Network delivers HTTP request
   ↓
Jenkins endpoint receives request
   ↓
Jenkins/plugin matches repository/job
   ↓
Trigger decides build is needed
   ↓
Build enters queue
   ↓
Agent executes Pipeline
```

Failure can occur at any layer.

# 43. Jenkins GitHub Webhook Endpoint

For the Jenkins GitHub plugin, the conventional webhook endpoint is:

```text
<JENKINS_BASE_URL>/github-webhook/
```

For example:

```text
https://ci.example.com/github-webhook/
```

or if Jenkins is served under a context path:

```text
https://ci.example.com/jenkins/github-webhook/
```

The Jenkins GitHub plugin documents the general endpoint form as `$JENKINS_BASE_URL/github-webhook/`. ([Jenkins Plugins][4])

Notice the trailing slash:

```text
/github-webhook/
```

Use the endpoint format provided by your Jenkins integration rather than inventing one.

---

# 44. What Is an Endpoint?

An endpoint is a network location where a service accepts requests.

Think:

```text
GitHub
   ↓
HTTP request
   ↓
https://ci.example.com/github-webhook/
```

The path:

```text
/github-webhook/
```

tells Jenkins:

> This request is intended for the GitHub webhook integration.

---

# 45. Network Accessibility

This is one of the most important webhook concepts.

Suppose Jenkins is running on your laptop:

```text
http://localhost:8080
```

Can GitHub reach:

```text
http://localhost:8080/github-webhook/
```

from GitHub's servers?

No.

`localhost` from GitHub's perspective does not mean your computer.

GitHub explicitly does not support `localhost` or `127.0.0.1` as webhook destination URLs. ([GitHub Docs][5])

---

# 46. Understand `localhost`

When you type:

```text
http://localhost:8080
```

your browser interprets:

```text
localhost
=
this computer
```

But GitHub's infrastructure cannot use your browser's concept of localhost to reach your private Jenkins process.

So:

```text
Your browser
     ↓
localhost:8080
     ↓
Jenkins
```

may work perfectly while:

```text
GitHub
     ↓
localhost:8080
     ↓
FAIL
```

---

# 47. Private IP Addresses Have the Same Problem

Suppose Jenkins is:

```text
192.168.1.50:8080
```

That may be reachable from your home or office network.

But GitHub on the public internet usually cannot directly reach a private RFC1918 address.

Similarly:

```text
10.x.x.x
172.16.x.x - 172.31.x.x
192.168.x.x
```

are commonly private network ranges.

The webhook receiver needs an appropriate network path from GitHub to Jenkins or an approved intermediary.

---

# 48. Production Webhook Architecture

A more realistic architecture is:

```text
GitHub
   ↓
Internet
   ↓
DNS
   ↓
HTTPS
   ↓
Reverse Proxy / Load Balancer
   ↓
Jenkins
   ↓
/github-webhook/
```

For example:

```text
https://ci.example.com/github-webhook/
```

The external endpoint is reachable from GitHub while Jenkins itself can remain behind appropriate infrastructure controls.

---

# 49. Do Not Expose Jenkins Carelessly

A dangerous beginner reaction is:

> GitHub can't reach Jenkins, so I'll expose Jenkins directly to the entire internet.

Do not treat network exposure as a shortcut.

A production Jenkins environment requires consideration of:

```text
HTTPS
Authentication
Authorization
Firewall rules
Reverse proxy/load balancer
Patching
Plugin security
Admin-interface exposure
Secrets
Agent security
Logging
Backups
Monitoring
```

Webhook connectivity does not mean every Jenkins interface should be broadly accessible.

# 53. Why Is It Called "GITScm Polling" if We Are Using Webhooks?

This name can confuse beginners.

The GitHub webhook arrives first:

```text
GitHub
   ↓
Webhook
   ↓
Jenkins GitHub plugin
```

The plugin then identifies matching Git-backed jobs and invokes the Git plugin's polling logic to determine whether relevant changes exist.

So the flow is conceptually:

```text
GitHub webhook
      ↓
Jenkins receives event
      ↓
Matching Git SCM checked
      ↓
Change identified
      ↓
Build triggered
```

The Jenkins GitHub plugin documents this behavior explicitly. ([Jenkins Plugins][4])

# 54. Job Repository Configuration Must Match

Suppose your Jenkins job is configured for:

```text
https://github.com/example/application-a.git
```

but the webhook comes from:

```text
https://github.com/example/application-b.git
```

Jenkins should not blindly trigger Application A.

Repository matching matters.

Your configuration needs consistency between:

```text
GitHub repository
Jenkins SCM repository
```

# 60. The Ping Event

The ping is not:

```text
a developer code push
```

```text

```

# 61. Webhook Payloads

A webhook does not simply send:

```text
BUILD NOW
```

GitHub sends structured information describing the event.

For a push event, the payload contains information associated with the repository and the push.

Conceptually:

```json
{
  "ref": "refs/heads/main",
  "repository": {
    "name": "example-project"
  },
  "sender": {
    "login": "developer"
  }
}
```

This is deliberately simplified for teaching.

Actual GitHub webhook payloads contain more fields.

---

# 62. HTTP Request Structure

A webhook request contains:

```text
HTTP method
Headers
Request body
```

Conceptually:

```text
POST /github-webhook/

Headers:
    event type
    delivery ID
    signature information
    content information

Body:
    JSON event payload
```

Understanding this will make webhook troubleshooting much easier.

---

# 63. Important GitHub Webhook Headers

GitHub webhook deliveries can include headers such as:

```text
X-GitHub-Event
X-GitHub-Delivery
X-Hub-Signature-256
User-Agent
```

`X-GitHub-Event` identifies the event type, while `X-GitHub-Delivery` uniquely identifies the delivery. If a secret is configured, `X-Hub-Signature-256` carries the SHA-256 HMAC signature used for validation. ([GitHub Docs][7])

These are extremely useful when troubleshooting.

```text
      ↓

      ↓
```

When the automatic build does not happen, do not immediately:


```text

        ↓

        ↓

        ↓

        ↓

        ↓

        ↓

        ↓
```


```bash

```

# 82. Investigate Network Reachability

Ask:

```text
Is Jenkins endpoint internet reachable?

Is firewall allowing appropriate traffic?

Is reverse proxy running?

Is load balancer healthy?

Is correct port open?

Is DNS pointing to correct destination?

```

Do not assume:

```text

```

proves:

```text

```

Your laptop and GitHub may have completely different network paths.

# 83. Investigate HTTPS/TLS

A production endpoint should generally use HTTPS.

Webhook delivery can fail if the TLS setup is invalid.

Examples:

```text
Expired certificate
Invalid certificate chain
Self-signed certificate not trusted
Wrong hostname
Proxy misconfiguration
```

GitHub documents certificate-authentication failures as a webhook troubleshooting category and recommends checking the server certificate chain. ([GitHub Docs][5])

# 84. Webhook Timeouts

GitHub currently expects webhook receivers to respond promptly and documents a 10-second response window. If the server does not respond within that period, GitHub records a timeout. ([GitHub Docs][5])

For Jenkins integration, the webhook endpoint should acknowledge the event promptly rather than performing an entire application build inside the HTTP request.

The architecture should be:

```text
GitHub webhook
      ↓
Jenkins receives event
      ↓
Build queued
      ↓
HTTP response
```

while the actual build proceeds through Jenkins execution.

# 104. Duplicate Builds

Automatic triggering introduces another problem.

Suppose a push results in:

```text
Build #51
Build #52
```

for what appears to be the same source change.

Why?

Possible causes include:

```text
Webhook trigger enabled
+
Poll SCM enabled
```

or:

```text
Multiple GitHub webhooks
```

or:

```text
Duplicate jobs watching same repository
```

or:

```text
Webhook redelivery
```

or:

```text
Multiple pushes/commits
```

or:

```text
Multibranch/indexing behavior
```

Never assume Jenkins "randomly built twice."

Investigate build causes.

# 105. Webhook Plus Polling

Suppose the Jenkinsfile contains:

```groovy
triggers {
    pollSCM('H/5 * * * *')
}
```

and the job is also configured for GitHub webhook triggering.

Now there are potentially two mechanisms involved in source-change detection.

Jenkins' own Pipeline documentation notes that for Pipelines integrated with GitHub or similar source systems, explicit `triggers` configuration may not be necessary when webhook integration already exists. ([Jenkins][1])

For a simple GitHub CI workflow, choose your trigger architecture intentionally.

Do not enable everything "for reliability" without understanding interactions.

# 107. `disableConcurrentBuilds()` Does Not Solve Duplicate Triggering

From Part 7:

```groovy
options {

}
```

prevents overlapping executions of the same Pipeline.

It does not necessarily mean:

```text

```

You could still get:

```text

```

So distinguish:

```text

```

from:

```text

```

They are different problems.

# 109. Webhook Security

A webhook endpoint accepts requests from outside Jenkins' normal interactive UI flow.

That makes security important.

Questions include:

```text
Who can send requests?

How do we verify GitHub?

Is HTTPS used?

Are secrets protected?

Can arbitrary events trigger privileged work?

What credentials can the Pipeline access?

Can untrusted branches execute dangerous Jenkinsfiles?
```

Webhook security is bigger than simply hiding the URL.

---

# 110. HTTPS

Production webhook traffic should be protected in transit.

Architecture:

```text
GitHub
   ↓
HTTPS
   ↓
Jenkins endpoint
```

HTTPS helps protect against interception and tampering in transit and provides server authentication when certificates are configured correctly.

Do not treat:

```text
http://public-ip:8080
```

as an ideal production Jenkins architecture.

---

# 111. Webhook Secrets

GitHub supports a webhook secret.

The secret can be used to verify that the payload is associated with GitHub and was not modified in transit.

GitHub generates an HMAC signature and places the SHA-256 version in:

```text
X-Hub-Signature-256
```

when a webhook secret is configured. GitHub recommends validating this signature before processing webhook deliveries in systems that implement webhook verification. ([GitHub Docs][9])

---

# 112. Never Put Webhook Secrets in Git

Do not create:

```text
webhook-secret.txt
```

inside the repository.

Do not write:

```groovy
environment {
    WEBHOOK_SECRET = 'super-secret-value'
}
```

inside a Git-controlled Jenkinsfile.

Secrets should be managed through appropriate secure credential/configuration mechanisms.

Part 10 is dedicated to Jenkins credentials and secret handling.

---

# 113. High-Entropy Secrets

A webhook secret should not be:

```text
jenkins123
```

or:

```text
password
```

or:

```text
mygithubsecret
```

GitHub recommends a random, high-entropy value for webhook secrets. ([GitHub Docs][9])

Do not reuse important passwords as webhook secrets.

---

# 114. Do Not Log Secrets

When troubleshooting webhook authentication, do not print:

```text
Webhook secret
GitHub PAT
Private key
Jenkins credential
Authorization header
```

into:

```text
Console Output
Screenshots
README
Issue reports
Public repositories
```

Troubleshooting evidence should help you diagnose without creating a new security incident.

---

# 115. Webhook Secret vs GitHub Personal Access Token

These are different credentials.

## Webhook secret

Used to help validate webhook delivery authenticity/integrity.

## Personal access token

Can authenticate API/repository operations according to its permissions.

Do not use the terms interchangeably.

Conceptually:

```text
Webhook Secret
        ↓
Validate incoming event
```

versus:

```text
GitHub Token
        ↓
Authenticate permitted GitHub operations
```

# 116. Least Privilege

If Jenkins uses GitHub credentials, grant only the permissions needed for the required workflow.

A simple checkout job should not automatically receive organization-wide administrative privileges.

Think:

```text
Required operation
      ↓
Minimum necessary permission
```

not:

```text
Give admin because it is easier
```

---

# 117. Be Careful With Pull Requests From Untrusted Sources

Imagine:

```text
External contributor
       ↓
Pull Request
       ↓
Modifies Jenkinsfile
       ↓
Pipeline executes
       ↓
Privileged credentials available
```

This can become dangerous.

Production CI systems must carefully control what untrusted source changes can execute and which credentials/agents those builds can access.

We will discuss branch and pull-request workflows more deeply in Part 17.

For now remember:

> Source code that controls CI execution should itself be treated as executable code.

# 118. Webhook Payloads May Contain Untrusted Data

Values such as:

```text
Branch names
Commit messages
Usernames
PR titles
Repository metadata
```

should not automatically be treated as safe shell commands.

Never build shell commands from arbitrary webhook-derived strings without careful validation and quoting.

The same rule from Part 7 still applies:

```text
External input
≠
trusted shell syntax
```

# 119. Restrict Event Types

If the Pipeline only needs:

```text
push
```

do not subscribe to every GitHub event without a reason.

Benefits:

```text
Less noise
Fewer unnecessary requests
Simpler troubleshooting
Reduced attack surface
Clearer intent
```

GitHub recommends subscribing only to events the integration needs. ([GitHub Docs][6])

# 120. GitHub Delivery IDs

Every webhook delivery includes a unique:

```text
X-GitHub-Delivery
```

identifier. ([GitHub Docs][7])

This is useful operationally.

Instead of saying:

> The webhook around 10ish failed.

you can identify a specific delivery.

That helps correlate:

```text
GitHub delivery
     ↕
Proxy logs
     ↕
Jenkins logs
     ↕
Build
```

# 121. Webhook Deliveries May Not Arrive in Event Order

Do not design a fragile system that assumes every webhook will necessarily arrive in the exact order events occurred.

GitHub explicitly notes that webhook deliveries can arrive out of order and recommends using payload timestamps when event ordering matters. ([GitHub Docs][5])

This is an important production lesson:

```text
event-driven
```

does not automatically mean:

```text
perfectly ordered
```

---

# 122. Webhooks May Not Be Instantaneous

Webhooks are usually fast, but do not treat:

```text
not visible after one second
```

as proof of failure.

GitHub notes that webhook deliveries may take a few minutes to appear and can be delayed under some conditions. ([GitHub Docs][5])

Troubleshoot based on evidence rather than impatience.

# 127. Full Practical Jenkinsfile

For the final lab, we do not need a `pollSCM` trigger inside the Jenkinsfile if our chosen architecture is GitHub webhook-driven and the job/plugin integration handles the webhook trigger.

Use a Pipeline similar to:

```groovy
pipeline {
    agent any

    options {
        timestamps()
        disableConcurrentBuilds()
        timeout(time: 30, unit: 'MINUTES')
    }

    environment {
        APP_NAME = 'veriqta-calculator'
    }

    stages {
        stage('Trigger Information') {
            steps {
                echo "Job: ${env.JOB_NAME}"
                echo "Build: ${env.BUILD_NUMBER}"
                echo "Build URL: ${env.BUILD_URL}"
            }
        }

        stage('Source Information') {
            steps {
                sh '''
                    set -eu

                    echo "Workspace:"
                    pwd

                    echo "Current commit:"
                    git rev-parse HEAD

                    echo "Latest commit:"
                    git log -1 --oneline

                    echo "Current branch/ref information:"
                    git status --short --branch
                '''
            }
        }

        stage('Build') {
            steps {
                echo "Building ${env.APP_NAME}"

                sh '''
                    set -eu

                    test -f pyproject.toml
                    test -f requirements-dev.txt

                    rm -rf .venv build dist

                    python3 -m venv .venv
                    .venv/bin/python -m pip install --upgrade pip
                    .venv/bin/python -m pip install -r requirements-dev.txt
                '''
            }
        }

        stage('Test') {
            steps {
                sh '''
                    set -eu
                    .venv/bin/python -m pytest -v
                '''
            }
        }

        stage('Package') {
            steps {
                sh '''
                    set -eu

                    .venv/bin/python -m build

                    test -d dist

                    echo "Generated artifacts:"
                    ls -lh dist/
                '''

                archiveArtifacts artifacts: 'dist/*', fingerprint: true
            }
        }
    }

    post {
        success {
            echo "Build ${env.BUILD_NUMBER} succeeded."
        }

        failure {
            echo "Build ${env.BUILD_NUMBER} failed."
        }

        cleanup {
            sh '''
                rm -rf .venv build
            '''

            echo 'Temporary build files cleaned.'
        }
    }
}
```

The automatic trigger is provided by the GitHub/Jenkins integration rather than a redundant polling schedule in this Jenkinsfile.

# 137. Common Beginner Mistakes

### Mistake 1

Using:

```text
http://localhost:8080/github-webhook/
```

as the GitHub payload URL.

GitHub cannot directly use your computer's localhost. ([GitHub Docs][5])

### Mistake 2

Webhook configured but Jenkins trigger not enabled.

### Mistake 3

Correct webhook but wrong repository configured in Jenkins.

### Mistake 4

Push occurs on a branch Jenkins is not monitoring.

### Mistake 5

Both polling and webhook triggering are enabled without understanding why.

### Mistake 6

Assuming successful webhook delivery means successful Pipeline execution.

### Mistake 7

Exposing the entire Jenkins server insecurely just to make the webhook reachable.

### Mistake 8

Selecting every GitHub webhook event.

### Mistake 9

Putting webhook secrets or GitHub tokens into Git.

### Mistake 10

Changing several configurations simultaneously while troubleshooting.

### Mistake 11

Ignoring the Jenkins build queue.

### Mistake 12

Testing by repeatedly creating meaningless commits when webhook redelivery would be more appropriate.
