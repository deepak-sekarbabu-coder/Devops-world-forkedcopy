# Part 5: Build a Real Application With Jenkins

## Learning Objective

In Part 4, Jenkins stopped working with commands in isolation and started working with source-controlled code.

You built this:

```text
Developer
    ↓
Git
    ↓
GitHub
    ↓
Jenkins
    ↓
Workspace
```

Jenkins could retrieve a repository, select a branch, check out a specific commit, place the source code into a workspace, and execute commands against it.

But retrieving source code is not the same thing as building software.

That changes in Part 5.

Our new workflow is:

```text
Developer
    ↓
GitHub
    ↓
Jenkins
    ↓
Dependencies
    ↓
Build
    ↓
Test
    ↓
Artifact
```

We are going to build a small real application from source code, install its dependencies, run automated tests, generate a distributable artifact, and make Jenkins preserve that artifact after the build.

By the end of this part, you should understand Jenkins as a **software automation system**, not merely a web interface that runs shell commands.

You will understand:

* Dependencies.
* Dependency installation.
* Build tools.
* Jenkins tool configuration.
* Build environments.
* Working directories.
* Build commands.
* Test commands.
* Exit codes.
* Why builds fail.

* Artifact archiving.

* How Jenkins moves source code through a repeatable build process.

# 1. What Does "Build the Application" Actually Mean?

Beginners often hear:

> Jenkins builds the application.

But what does **build** actually mean?

There is no single command called "build software" that applies to every programming language.

A software build is a process that transforms source code and related inputs into something that can be tested, packaged, distributed, or deployed.

For one project:

```text
Source Code
    ↓
Compile
    ↓
Executable
```

For another:

```text
Source Code
    ↓
Install Dependencies
    ↓
Run Tests
    ↓
Package
```

For another:

```text
Java Source
    ↓
Maven
    ↓
Compile
    ↓
Test
    ↓
JAR
```

For another:

```text
Node.js Source
    ↓
npm install
    ↓
Tests
    ↓
npm run build
    ↓
dist/
```

For our application:

```text
Python Source
    ↓
Create Isolated Environment
    ↓
Install Dependencies
    ↓
Run Tests
    ↓
Package Application
    ↓
Distribution Artifact
```

The important idea is:

```text
Build
=
a defined transformation and validation process
```

not simply:

```text
Build
=
Jenkins clicked a button
```

---

# 2. Jenkins Does Not Know How to Build Every Application

This is one of the most important concepts in Jenkins.

Jenkins is an automation and orchestration system.

It does not automatically know how your application should be compiled, tested, or packaged.

Suppose Jenkins checks out:

```text
shop-api/
```

Jenkins cannot magically determine whether it should run:

```bash
mvn package
```

or:

```bash
npm run build
```

or:

```bash
dotnet build
```

or:

```bash
go build
```

or:

```bash
python -m build
```

You define the build process.

Jenkins automates it.

Think:

```text
Developer defines build process
            ↓
Jenkins executes build process
            ↓
Tools perform actual work
```

Jenkins coordinates tools rather than replacing them.


That is source code.

After building, we might produce:


Conceptually:

```text

   ↓

   ↓

```

This distinction matters enormously in CI/CD.

# 5. What Is a Build Artifact?

A build artifact is an output produced by a build that you intentionally want to retain or use later.

Examples include:

```text
application.jar
```

```text
application.war
```

```text
shop-api.zip
```

```text
myapp.exe
```

```text
package.whl
```

```text
test-report.xml
```

Not every file created during a build is an artifact.

A build may create hundreds of temporary files.

An artifact is an output we deliberately identify as important.

Our project will generate a Python wheel:

```text
dist/
└── veriqta_calculator-1.0.0-py3-none-any.whl
```

# 6. Compiled vs Interpreted Applications

Before building anything, we need to understand an important difference between programming-language execution models.

You will commonly hear:

```text
compiled language
```

and:

```text
interpreted language
```

The real world has hybrids and implementation details that make the distinction less absolute than beginner diagrams suggest, but the distinction is still useful for understanding build workflows.

---

# 7. Compiled Applications

A compiled application generally has source code transformed into another executable or intermediate representation before normal execution.

A simplified C example:

```text
C Source Code
    ↓
Compiler
    ↓
Machine Code
    ↓
Executable
```

Example:

```text
hello.c
   ↓
gcc
   ↓
hello
```

Java has a different model:

```text
Java Source
    ↓
javac
    ↓
Bytecode
    ↓
JVM
```

A Java project might eventually produce:

```text
application.jar
```

In CI:

```text
GitHub
   ↓
Jenkins
   ↓
Compiler / Build Tool
   ↓
Compiled Output
   ↓
Tests
   ↓
JAR
```

Compilation errors can therefore stop the build before tests even run.

---

# 8. Interpreted Applications

Languages such as Python are often described as interpreted languages.

A simplified beginner model is:

```text
Python Source
    ↓
Python Runtime
    ↓
Program Execution
```

We do not normally need a traditional native compilation step before executing a simple Python source file.

For example:

```bash
python3 app.py
```

can execute the program.

But this does **not** mean Python applications do not have build processes.

A Python application may still require:

```text
Dependencies
Tests
Packaging
Distribution metadata
Generated files
Wheel creation
```

Therefore:

```text
Interpreted
```

does not mean:

```text
No build process
```

# 10. What Is a Runtime?

A runtime provides the environment needed to execute software.

Our application is written in Python.

Therefore we need:

```text
Python runtime
```

A Java application needs a suitable Java runtime.

A Node.js application needs Node.js.

A .NET application needs the appropriate .NET runtime or SDK depending on the operation.

Jenkins itself running successfully does not mean every application runtime is installed.

Remember:

```text
Jenkins requires Java
```

but:

```text
Jenkins running Java
```

does not imply:

```text
Python exists
Node.js exists
Maven exists
Go exists
.NET exists
```

Each build environment needs the tools required by its workload.

# 11. Build Runtime vs Jenkins Runtime

This distinction is particularly important.

Our Jenkins controller uses Java:

```text
Operating System
    ↓
Java
    ↓
Jenkins
```

Our application uses Python:

```text
Jenkins Build
    ↓
Python
    ↓
Application
```

Therefore:

```text
Java
```

is required to run Jenkins.

And:

```text
Python
```

is required for our particular application build.

Do not confuse the two.

# 13. What Are Dependencies?

Applications rarely contain every piece of functionality they need.

They use external libraries and packages.

Suppose our application requires a testing framework.

Rather than writing an entire test framework ourselves, we can use:

```text
pytest
```

Our packaging process will also use:

```text
build
```

These are dependencies/tools our build needs.

Conceptually:

```text
Application Source
      ↓
Depends On
      ↓
External Packages
```

Dependency management answers questions such as:

```text
Which packages do we need?

Which versions?

Where do they come from?

How are they installed?
```

---

# 14. Why Dependency Versions Matter

Suppose your build simply requests:

```text
some-library
```

Today it receives:

```text
1.0
```

Next month it receives:

```text
2.0
```

If version 2.0 behaves differently, the same source code may produce different results.

This is one reason reproducible builds require controlled dependencies.

Conceptually:

```text
Same Source
+
Different Dependency
=
Potentially Different Build
```

Reproducibility requires controlling more than source code.

# 19. Build Environment

A build environment is the environment in which the build actually executes.

It includes more than the operating system.

Think:

```text
Build Environment
│
├── Operating system
├── Node
├── CPU architecture
├── Runtime version
├── Build tools
├── PATH
├── Environment variables
├── Filesystem
├── Permissions
├── Dependencies
└── Network access
```

Two builds using identical source code can behave differently if their environments differ.

For example:

```text
Environment A
Python 3.11
```

versus:

```text
Environment B
Python 3.14
```

or:

```text
Environment A
Dependency 2.1
```

versus:

```text
Environment B
Dependency 3.0
```

This is why environment consistency matters.

# 20. Why "Works on My Machine" Happens

Suppose a developer says:

```text

Package installed       Package missing

Writable directory      Permission denied
```

```text
      ↓
```

# 30. Understand the Application

This:

```python
def add(a, b):
    return a + b
```

defines a function called:

```text
add
```

It accepts two values:

```text
a
b
```

and returns their sum.

Likewise:

```python
def subtract(a, b):
    return a - b
```

returns the difference.

The division function contains an important validation:

```python
if b == 0:
    raise ValueError("Cannot divide by zero")
```

Instead of silently performing an invalid operation, it raises an error.

We will test this behavior.

```python
def test_add():

    assert multiply(3, 4) == 12


def test_divide():

    with pytest.raises(ValueError):
        divide(10, 0)
```

These are automated tests.

# 32. What Does a Test Actually Do?

Consider:

```python
def test_add():
    assert add(2, 3) == 5
```

The test executes:

```python
add(2, 3)
```

and expects:

```text
5
```

If the function returns `5`, the assertion succeeds.

If it returns something else, the assertion fails.

This matters because Jenkins can use the test command's exit code to decide whether the build should continue.

# 35. Understand `pyproject.toml`

This section:

```toml
[build-system]
```

describes the build system.

```toml
requires = ["setuptools>=68", "wheel"]
```

identifies packages needed by the build backend.

```toml
build-backend = "setuptools.build_meta"
```

selects the build backend.

Then:

```toml
[project]
```

contains project metadata.

```toml
name = "veriqta-calculator"
```

defines the package name.

```toml
version = "1.0.0"
```

defines its package version.

```toml
requires-python = ">=3.10"
```

states the supported Python requirement we are declaring for this project.

Finally:

```toml
[tool.pytest.ini_options]
```

configures pytest for our source layout.

# 39. Why Use `python -m pip`?

You will often see:

```bash

```

We are using:

```bash
python -m pip
```

because it explicitly runs the `pip` module associated with the selected Python interpreter.

That can reduce ambiguity when multiple Python installations exist.

Inside our virtual environment:

```text
python
   ↓
associated pip
   ↓
dependencies installed into environment
```

That is clearer than assuming an arbitrary `pip` command belongs to the intended Python.

# 49. What Does `set -eu` Do?

At the top we used:

```bash
set -eu
```

For this shell:

```text
-e
```

tells the shell to stop when an unhandled command failure occurs, subject to shell semantics.

```text
-u
```

treats use of an unset variable as an error.

This is useful because a build script should not quietly continue after an important failure.

For example:

```text
Tests fail
   ↓
Stop
   ↓
Do not pretend package build succeeded
```

Be aware that shell error handling has nuances, especially in compound commands and pipelines. For this simple build script, `set -eu` gives us useful fail-fast behavior.

| ------------------------------- | ----------------------------- | -------------------------------------- |

# 75. Build Reproducibility

Now we reach one of the most important topics in this part.

Suppose you run a build today.

Then run the same Git commit six months later.

Should you expect the same result?

Ideally, as much as practical:

```text
Same Source
+
Same Build Definition
+
Same Dependencies
+
Same Toolchain
+
Same Relevant Environment
=
Same Build Result
```

That is the idea behind build reproducibility.

Perfect bit-for-bit reproducibility is a deeper subject, but the beginner principle is simple:

```text
Builds should not depend on invisible accidents.
```

# 76. Sources of Non-Reproducibility

Builds can change because of:

* Unpinned dependency versions.
* Runtime upgrades.
* Compiler upgrades.
* Operating-system changes.
* Environment variables.
* Time/date behavior.
* Network resources.
* Mutable external downloads.
* Leftover workspace files.
* Globally installed packages.
* Changing build scripts.
* Architecture differences.

For example:

```text
Commit A
+
pytest latest
```

today may not mean the same environment as:

```text
Commit A
+
pytest latest
```

two years later.

# 80. Workspace Reuse

Jenkins workspaces may persist between builds.

Suppose Build #10 creates:

```text

```

Then Build #11 runs.

Unless something removes it, that file may still exist.

Now imagine Build #11 accidentally depends on it.

You could get:

```text

```

even though a clean environment would fail.

That is called workspace contamination.

# 81. Why Dirty Workspaces Are Dangerous

Imagine:

```text
   ↓

```

Build #2 finds:

```text

```

and succeeds.

On a new server:

```text
Fresh Workspace
   ↓
file absent
   ↓
build fails
```

Now you have:

> It works in Jenkins but not in a clean environment.

That is exactly what reproducible builds are supposed to prevent.

# 87. Manual Cleanup in Our Build

Even without a cleanup plugin, our project can remove known generated directories before creating them.

For example, near the start of the shell build:

```bash
rm -rf .venv build dist
```

```bash
find . -type d -name '__pycache__' -prune -exec rm -rf {} +
```



# 90. Why `test -d dist`?

We added:

```bash
test -d dist
```

This checks whether:

```text
dist
```

exists as a directory.

If it does:

```text
exit status 0
```

If it does not:

```text
non-zero exit status
```

Because our script stops on failure, a missing `dist/` directory fails the build.

This is verification.

We are no longer assuming:

```text
python -m build ran
therefore artifact definitely exists
```

We verify the expected output.

# 91. Verify the Artifact More Strictly

We can go further.

For example:

```bash
test -n "$(find dist -maxdepth 1 -type f -name '*.whl' -print -quit)"
```

This checks that at least one wheel exists.

But do not make beginner scripts unnecessarily clever.

A clearer version is:

```bash
WHEEL_FILE="$(find dist -maxdepth 1 -type f -name '*.whl' -print -quit)"

if [ -z "$WHEEL_FILE" ]; then
    echo "ERROR: Expected wheel artifact was not generated."
    exit 1
fi

echo "Wheel artifact: $WHEEL_FILE"
```

This is longer but easier to understand.

Readability matters in automation.

# 95. Why Not Delete Everything After Every Build?

You might ask:

> If dirty workspaces are dangerous, why not always delete everything?

Often, disposable or clean build environments are desirable.

But cleanup also has trade-offs.

Some builds benefit from caches for:

* Dependencies.
* Compilers.
* Package downloads.
* Build intermediates.

A completely cold build can be slower.

The engineering question becomes:

```text
What should be reproducible?
```

versus:

```text
What can safely be cached?
```

A cache should improve performance.

It should not become an undocumented source of correctness.

For this beginner project, favor clarity and clean behavior over sophisticated caching.

---

# 96. Build Environment vs Cache

Do not confuse:

```text
Required dependency
```

with:

```text
cached copy of dependency
```

The build definition should know how to obtain the dependency.

A cache may make that faster.

Conceptually:

```text
Build Definition
   ↓
Needs Dependency X
```

Cache:

```text
Do we already have X?
   ↓
Yes → reuse
No  → download
```

If deleting the cache permanently destroys your ability to understand how the build works, your build is too dependent on hidden state.

# 97. Why We Should Not Use `sudo` in the Build

Our Jenkins job does not need:

```bash
sudo pip install ...
```

and it should not use it.

The job creates:

```text
.venv/
```

inside its workspace.

Dependencies are installed there.

This means the build does not need administrator access to modify the machine's global Python installation.

That is a security improvement.

Think:

```text
Jenkins build
      ↓
workspace-local environment
```

rather than:

```text
Jenkins build
      ↓
root privileges
      ↓
modify entire server
```

Least privilege applies to build environments too.

# 98. Dependency Installation Is a Supply-Chain Boundary

When Jenkins runs:


it is retrieving and executing software from a package ecosystem.

That means dependency installation is security-sensitive.

Production concerns include:

* Trusted package sources.
* Dependency pinning.
* Vulnerability management.
* Package integrity.
* Typosquatting.
* Compromised upstream packages.
* Internal mirrors.
* Network controls.

We will not turn Part 5 into a full software supply-chain security course.

But remember:

```text
Dependency
=
code you are allowing into the build environment
```

Treat dependencies deliberately.

# 104. Why Dedicated Agents Matter

In Part 3, we noted that general build workloads should not normally be placed on the controller in a serious Jenkins deployment.

Now the reason becomes even clearer.

Our build:

* Executes repository-controlled code.
* Installs dependencies.
* Creates environments.
* Writes files.
* Consumes CPU.
* Consumes memory.
* Uses disk.
* Accesses the network.

That workload belongs naturally on controlled build agents.

Jenkins distinguishes the controller from nodes/agents that execute build work, which becomes especially important in distributed environments. ([Jenkins][7])

We will build agents properly in Part 12.

# 113. Common Failure: Artifact Archiving Finds Nothing

Suppose Jenkins is configured with:

```text
dist/*.jar
```

but your project creates:

```text
dist/*.whl
```

The archive pattern is wrong.

Jenkins' archive operation uses workspace-relative patterns and normally treats a missing expected artifact as a problem unless configured otherwise. ([Jenkins][4])

For our project:

```text
dist/*
```

is appropriate for the generated distribution files.

A more restrictive pattern could later be:

```text
dist/*.whl
```

if the wheel is the only artifact you intend to preserve.

# 114. Common Failure: Stale Artifact

But the old file remains in the workspace.

A badly designed job might mistakenly archive the old artifact.

This is exactly why workspace cleanliness matters.

A clean build should not be able to succeed because yesterday's output still exists.

# 123. Test the Generated Artifact

Generating a package is good.

### Answer 1

Building software means executing a defined process that transforms and validates source code and related inputs into tested, packaged, or otherwise usable outputs.

A compiled application has source transformed into another executable or intermediate form before normal execution.

Changing dependency versions can change build behavior even when source code does not change.

### Answer 9

A build tool automates tasks such as compilation, dependency processing, testing, packaging, or output generation.
