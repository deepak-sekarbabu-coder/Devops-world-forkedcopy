# Part 6: Jenkins Pipelines From Absolute Zero

## Learning Objective

In Part 5, you moved beyond simple Jenkins commands and built actual software.

Your Jenkins workflow became:

```text
Developer
    ↓
GitHub
    ↓
Jenkins
    ↓
Dependencies
    ↓
Build
    ↓
Test
    ↓
Artifact
```

That was a major step forward.

But there is still an important weakness in the way the job is configured.

Most of the automation instructions live inside the Jenkins web interface.

If someone asks:

> What exactly does this application's CI process do?

you may need to open Jenkins, find the job, select **Configure**, scroll through several sections, inspect build steps, inspect post-build actions, and mentally reconstruct the workflow.

That becomes difficult as automation grows.

In this part, we will move the build process into a file stored with the application:

```text
Jenkinsfile
```

Our architecture becomes:

```text
GitHub
    ↓
Jenkinsfile
    ↓
Jenkins Pipeline
```

More completely:

```text
Developer
    ↓
Git
    ↓
GitHub Repository
    ├── Application Source
    ├── Tests
    ├── Build Configuration
    └── Jenkinsfile
              ↓
           Jenkins
              ↓
           Pipeline
              ↓
      Build → Test → Package
```

This is the beginning of **Pipeline as Code**.

# 1. The Problem With Freestyle Jobs

Freestyle projects are useful.

You used them in Parts 3, 4, and 5 because they provide a simple way to learn Jenkins.

You can configure things through the web interface:

```text
Jenkins Dashboard
    ↓
New Item
    ↓
Freestyle Project
    ↓
Source Code Management
    ↓
Build Steps
    ↓
Post-build Actions
```

For a small job, that is convenient.

But imagine a real application with:

```text
Checkout
Build
Unit Tests
Integration Tests
Security Scan
Package
Artifact Archive
Container Build
Container Push
Staging Deployment
Smoke Test
Approval
Production Deployment
Verification
Notification
```

Trying to manage all of that through web forms becomes increasingly difficult.

---

# 2. A Freestyle Job Lives Mostly Inside Jenkins

Suppose your Part 5 job contains this build step:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m pytest -v
.venv/bin/python -m build
```

That configuration lives primarily in Jenkins.

Your Git repository may contain:

```text
veriqta-calculator/
├── README.md
├── pyproject.toml
├── requirements-dev.txt
├── src/
└── tests/
```

But it does not fully describe:

```text
How Jenkins should execute the CI workflow.
```

Someone cloning the repository can see the application.

They cannot necessarily see the complete Jenkins job configuration.

---

# 3. The Configuration Separation Problem

Your application is in Git:

```text
GitHub
    ↓
Application Code
```

But your automation is somewhere else:

```text
Jenkins
    ↓
Job Configuration
```

So you have:

```text
GitHub                    Jenkins

Application               Automation
Source Code               Job Configuration
Tests                     Build Steps
Build Config              Post-build Actions
```

Two important parts of the same delivery process are separated.

That creates several problems.

---

# 4. Problem 1: Poor Visibility

A developer opens the repository.

They can see:

```text
src/
tests/
pyproject.toml
```

But they cannot immediately see the Jenkins workflow.

They may need Jenkins access.

Then they must navigate through job configuration.

Pipeline as Code gives us:

```text
Repository
├── src/
├── tests/
├── pyproject.toml
└── Jenkinsfile
```

Now the repository itself explains much more of its automation.

---

# 5. Problem 2: Changes Are Harder to Review

Suppose someone changes a Freestyle job from:

```bash
python -m pytest
```

to:

```bash
python -m pytest || true
```

That change could hide test failures.

If the build definition lives only in Jenkins, reviewing that change through the same software-development workflow as application code is harder.

With a `Jenkinsfile`, the change can appear in Git:

```diff
- sh '.venv/bin/python -m pytest -v'
+ sh '.venv/bin/python -m pytest -v || true'
```

A reviewer can notice:

> Why are test failures being ignored?

That is a major benefit of treating automation as code.

---

# 6. Problem 3: Weak Change History

Git gives you:

```text
Who changed this?
When?
What changed?
Why?
Which commit?
```

For example:

```bash
git log
```

can show the history of the `Jenkinsfile`.

You can also inspect:

```bash
git diff
```

to understand changes.

The Jenkins documentation specifically identifies code review, iteration, audit history, and a shared source of truth as benefits of keeping a `Jenkinsfile` in source control. ([Jenkins][1])

---

# 7. Problem 4: Recreating the Job

Imagine your Jenkins environment is replaced.

You still have:

```text
GitHub Repository
```

If the entire build definition exists only as manually configured Jenkins settings, recreating it can involve reconstructing those settings.

If the important workflow is defined in:

```text
Jenkinsfile
```

you have a version-controlled description of the Pipeline.

This does not mean a `Jenkinsfile` backs up the whole Jenkins server.

It does not.

Jenkins still has configuration such as:

* Credentials.
* Nodes.
* Plugins.
* Security settings.
* Global tools.
* System configuration.

But the application's Pipeline logic can live with the application.

---

# 8. Problem 5: Complex Workflows Become Hard to Understand

Imagine a delivery process:

```text
Checkout
   ↓
Build
   ↓
Unit Tests
   ↓
Integration Tests
   ↓
Security Scan
   ↓
Package
   ↓
Deploy
```

That is naturally represented as a Pipeline.

Trying to model increasingly complex relationships through disconnected UI settings becomes harder to understand and maintain.

Jenkins Pipeline makes the delivery process a first-class concept. Jenkins describes Pipeline as a suite of plugins for modeling simple through complex delivery pipelines as code. ([Jenkins][2])

---

# 9. What Is Jenkins Pipeline?

A Jenkins Pipeline is a model of an automated software delivery process.

For example:

```text
Pipeline
│
├── Build
│
├── Test
│
└── Package
```

Or later:

```text
Pipeline
│
├── Checkout
├── Build
├── Unit Test
├── Integration Test
├── Security Scan
├── Package
├── Publish
├── Deploy Staging
├── Verify
└── Deploy Production
```

Each logical section can be represented as a stage.

Jenkins executes the Pipeline according to its definition.

---

# 10. What Is Pipeline as Code?

Pipeline as Code means defining the software delivery workflow using code stored in source control.

Instead of manually configuring:

```text
Build step 1
Build step 2
Build step 3
```

only through Jenkins UI forms, we write something like:

```groovy
pipeline {
    agent any

    stages {
        stage('Build') {
            steps {
                echo 'Building application'
            }
        }

        stage('Test') {
            steps {
                echo 'Testing application'
            }
        }

        stage('Package') {
            steps {
                echo 'Packaging application'
            }
        }
    }
}
```

That file can be committed to Git.

The Jenkins documentation calls the `Jenkinsfile` the foundation of Pipeline as Code because the Pipeline definition can be versioned and reviewed alongside the project. ([Jenkins][2])

---

# 11. What Is a Jenkinsfile?

A `Jenkinsfile` is a text file containing the definition of a Jenkins Pipeline.

The standard filename is:

```text
Jenkinsfile
```

Notice:

```text
Jenkinsfile
```

not:

```text
Jenkinsfile.txt
```

not:

```text
jenkinsfile
```

not:

```text
jenkins.yml
```

For our project, we will place it at the repository root:

```text
veriqta-calculator/
├── Jenkinsfile
├── README.md
├── pyproject.toml
├── requirements-dev.txt
├── src/
│   └── veriqta_calculator/
│       ├── __init__.py
│       └── calculator.py
└── tests/
    └── test_calculator.py
```

Jenkins supports another script path if configured, but a root-level `Jenkinsfile` is the normal starting point and the default path Jenkins expects when configuring Pipeline from SCM. ([Jenkins][3])

---

# 12. Why Store the Jenkinsfile With the Application?

Now one repository can contain:

```text
Application code
+
Tests
+
Build configuration
+
CI/CD workflow
```

For example:

```text
GitHub Repository
│
├── Application
├── Tests
├── Dependency Definitions
├── Packaging Configuration
└── Jenkinsfile
```

If the application changes in a way that requires the Pipeline to change, both changes can be reviewed together.

# 19. Two Jenkins Pipeline Syntaxes

Jenkins supports two major Pipeline syntaxes:

```text
Declarative Pipeline
```

and:

```text
Scripted Pipeline
```

Both can define Jenkins Pipelines, but they are structured differently. ([Jenkins][1])

For this beginner series, we will primarily use:

```text
Declarative Pipeline
```

because its structure makes the Pipeline easier to read and reason about while learning.

---

# 20. Declarative Pipeline

A basic Declarative Pipeline looks like:

```groovy
pipeline {
    agent any

    stages {
        stage('Build') {
            steps {
                echo 'Building application'
            }
        }
    }
}
```

Declarative Pipeline provides a defined structure.

You will commonly encounter:

```text
pipeline
agent
environment
options
parameters
triggers
tools
stages
stage
steps
when
post
```

We will not learn all of them in Part 6.

For now:

```text
pipeline
agent
stages
stage
steps
script
```

are our main focus.

---

# 21. Scripted Pipeline

A simple Scripted Pipeline might look like:

```groovy
node {
    stage('Build') {
        echo 'Building application'
    }

    stage('Test') {
        echo 'Testing application'
    }
}
```

Notice that it does not have the same:

```text
pipeline {
    agent
    stages {
        stage {
            steps {
```

structure.

Scripted Pipeline gives you a more direct Groovy-oriented programming model.

It is useful for understanding older Jenkinsfiles and some advanced workflows.

But we will not use it as our primary beginner syntax.

---

# 22. Declarative vs Scripted Pipeline

| Area                      | Declarative                            | Scripted                                 |
| ------------------------- | -------------------------------------- | ---------------------------------------- |
| Main outer structure      | `pipeline {}`                          | Often `node {}`                          |
| Structure                 | More opinionated                       | More programmatic                        |
| Beginner readability      | Usually easier                         | Usually requires more Groovy familiarity |
| Complex programming logic | Possible, but intentionally structured | More directly flexible                   |
| Common Jenkinsfile use    | Very common                            | Also supported                           |
| Our beginner track        | Primary                                | Introduction only                        |

Both are valid Jenkins Pipeline approaches. Jenkins describes Declarative as a more simplified and opinionated syntax, while Scripted provides the older Groovy-oriented model. ([Jenkins][4])

# 24. Understanding `pipeline`

The first line is:

```groovy
pipeline {
```

This starts the top-level Declarative Pipeline definition.

Conceptually:

```text
pipeline {
    everything defining this Pipeline
}
```

A valid Declarative Pipeline is enclosed in a `pipeline` block. ([Jenkins][4])

Think of it as:

```text
This is the boundary of my Jenkins Pipeline definition.
```

---

# 25. Understanding Curly Braces

You will repeatedly see:

```text
{
}
```

These curly braces define blocks.

For example:

```groovy
pipeline {
}
```

means:

```text
start pipeline block
...
end pipeline block
```

Then:

```groovy
stages {
}
```

means:

```text
start stages block
...
end stages block
```

Indentation helps humans see nesting.

The braces define the actual structure.

---

# 26. Understanding `agent`

Next:

```groovy
agent any
```

This tells Jenkins where the Pipeline should execute.

Remember from earlier parts:

```text
Jenkins Controller
       ↓
Node / Agent
       ↓
Executor
       ↓
Workspace
       ↓
Build Work
```

The official Jenkins documentation explains that `agent any` tells Jenkins to allocate an executor and workspace on an available agent/node for the Pipeline. ([Jenkins][1])

So:

```groovy
agent any
```

means approximately:

> Jenkins, run this Pipeline on any suitable available agent.

---

# 27. `agent any` Does Not Mean Any Computer on Earth

It means an available agent/node known to that Jenkins environment and suitable for the Pipeline.

For your current learning environment, that may still be the Jenkins machine itself.

Later we will configure dedicated agents.

Then we may use labels such as:

```groovy
agent {
    label 'linux'
}
```

But not yet.

For Part 6:

```groovy
agent any
```

is enough.

---

# 28. Why Does the Agent Matter?

A Pipeline needs somewhere to perform work.

If you run:

```groovy
sh 'python3 --version'
```

that command needs:

* A machine.
* An executor.
* A shell.
* Python.
* A filesystem.
* A workspace.

The `agent` tells Jenkins where Pipeline work can execute.

Think:

```text
Pipeline Definition
       ↓
Agent Allocation
       ↓
Executor
       ↓
Workspace
       ↓
Commands
```

---

# 29. Understanding `stages`

Next:

```groovy
stages {
```

This block contains the major phases of the Pipeline.

For example:

```groovy
stages {
    stage('Build') {
    }

    stage('Test') {
    }

    stage('Package') {
    }
}
```

Think:

```text
Pipeline
│
├── Build
├── Test
└── Package
```

`stages` is the container holding those major phases.

---

# 30. Understanding `stage`

A stage represents a meaningful phase of the delivery process.

For example:

```groovy
stage('Build')
```

or:

```groovy
stage('Test')
```

or:

```groovy
stage('Package')
```

A stage should normally describe a logical responsibility.

Good stage names include:

```text
Checkout
Build
Unit Test
Integration Test
Package
Security Scan
Deploy
Verify
```

Less useful stage names include:

```text
Stuff
Things
Step 1
Random Commands
```

Good stage names make the Pipeline understandable.

---

# 31. Why Stages Matter

Stages are not merely decoration.

They help humans understand:

```text
Where is the Pipeline now?

Which phase succeeded?

Which phase failed?

How long did each phase take?
```

Jenkins and Pipeline visualization features can use stages to present Pipeline progress and status. ([Jenkins][2])

Instead of:

```text
Build failed
```

you may see:

```text
Build       SUCCESS
Test        FAILURE
Package     NOT EXECUTED
```

That immediately gives you useful information.

---

# 32. Understanding `steps`

Inside a stage:

```groovy
stage('Build') {
    steps {
        echo 'Building application'
    }
}
```

`steps` contains the actual work Jenkins performs for that stage.

Conceptually:

```text
Stage
  ↓
Steps
  ↓
Actual Tasks
```

A stage describes:

```text
what phase are we in?
```

Steps describe:

```text
what should Jenkins actually do?
```

---

# 33. What Is a Pipeline Step?

A step is a basic unit of Pipeline work.

Examples include:

```groovy
echo 'Hello'
```

```groovy
sh 'python3 --version'
```

```groovy
checkout scm
```

```groovy
archiveArtifacts artifacts: 'dist/*'
```

Jenkins describes a step as the fundamental building block that tells Jenkins what to do at a particular point in the Pipeline. ([Jenkins][4])

---

# 34. `echo` Is a Jenkins Pipeline Step

Example:

```groovy
echo 'Hello from Jenkins'
```

This is not the same as writing:

```bash
echo "Hello from Jenkins"
```

inside a shell.

The first is a Jenkins Pipeline step.

The second is a shell command.

That distinction matters.

---

# 35. `sh` Is a Pipeline Step That Runs Shell Commands

For Linux/Unix-like agents:

```groovy
sh 'python3 --version'
```

means:

```text
Jenkins Pipeline
       ↓
sh step
       ↓
Shell
       ↓
python3 --version
```

Jenkins' documentation notes that `sh` executes shell commands on Unix-like environments and that a non-zero exit code normally causes the Pipeline to fail. ([Jenkins][1])

On Windows, a common equivalent is:

```groovy
bat 'python --version'
```

for Windows batch commands.

# 48. This Is Still Not a Real Build Yet

Our three stages currently use:

```groovy
echo
```

So:

```text
Build
```

does not actually build anything.

```text
Test
```

does not test anything.

```text
Package
```

does not package anything.

Stage names do not create behavior.

This:

```groovy
stage('Test') {
    steps {
        echo 'Testing'
    }
}
```

does not magically run tests.

# 54. Understand the Test Stage

```groovy
stage('Test') {
    steps {
        sh '''
            set -eu

            echo "Running automated tests"
```


# 85. Pipeline Validation

There are two broad problems a Jenkinsfile can have.

## Syntax/configuration problem

Jenkins cannot correctly interpret the Pipeline definition.

Example:

```groovy
pipline {
```

instead of:

```groovy
pipeline {
```

## Runtime problem

The Pipeline definition is valid, but something fails during execution.

Example:

```groovy
sh 'python999 --version'
```

The Jenkinsfile can be structurally valid.

But the command fails when executed.

This distinction is essential.

```text
    ↓

    ↓

    ↓
Syntax / validation failure
```

versus:

```text
Jenkinsfile
    ↓
Valid Pipeline
    ↓
Execution starts
    ↓
Command fails
    ↓
Runtime/build failure
```

Do not troubleshoot them the same way.

# 94. Basic Error Handling

By default, a failed `sh` step normally fails the Pipeline execution path.

Example:

```groovy
sh 'exit 1'
```

causes failure because the command returns a non-zero exit code. Jenkins' Jenkinsfile documentation specifically notes this behavior for `sh`. ([Jenkins][1])

This default is useful.

It means:

```text
Important command fails
      ↓
Jenkins notices
      ↓
Pipeline fails
```

Do not immediately suppress failures.

---

# 95. A Dangerous Beginner Pattern

You may see:

```groovy
sh 'pytest || true'
```

This means:

```text
run pytest
```

but if it fails:

```text
force shell command to continue successfully
```

That can hide real test failures.

For example:

```text
Tests fail
   ↓
|| true
   ↓
Shell returns success
   ↓
Jenkins thinks step succeeded
```

Do not use this casually.

A CI system that hides failures defeats its purpose.

# 96. Explicitly Creating a Pipeline Error

Jenkins provides an `error` step.

Example:

```groovy
pipeline {
    agent any

    stages {
        stage('Validate') {
            steps {

                    if (!applicationReady) {
                        error 'Application validation failed'
                    }
                }
            }
        }
    }
}
```

Here:

```groovy
error 'Application validation failed'
```

intentionally fails the Pipeline with a meaningful message.

This is useful when your Pipeline detects a condition that should prevent further execution.

```groovy
    steps {
        sh '''
            test -f pyproject.toml
            test -f requirements-dev.txt
        '''
    }
}
```

If either required file is missing, the stage fails.

A more descriptive version is:

```groovy
stage('Build') {
    steps {
        sh '''
            set -eu

            if [ ! -f pyproject.toml ]; then
                echo "ERROR: pyproject.toml is missing."
                exit 1
            fi

            if [ ! -f requirements-dev.txt ]; then
                echo "ERROR: requirements-dev.txt is missing."
                exit 1
            fi
        '''
    }
}
```

The second version provides better troubleshooting evidence.

# 99. Declarative `post` and Failure Handling

Declarative Pipeline also supports:

```groovy
post {
}
```

for actions that should run based on Pipeline or stage results.

For example:

```groovy
post {
    success {
        echo 'Pipeline succeeded'
    }

    failure {
        echo 'Pipeline failed'
    }

    always {
        echo 'Pipeline finished'
    }
}
```

Jenkins documents conditions including `always`, `success`, `failure`, `unstable`, and `changed`. ([Jenkins][1])

We will cover `post` more thoroughly in Part 7.

For now, understand the basic idea.

# 100. Add Basic `post` Handling

Our Pipeline can become:

```groovy
pipeline {
    agent any

    stages {
        stage('Build') {
            steps {
                echo 'Building'
            }
        }

        stage('Test') {
            steps {
                echo 'Testing'
            }
        }

        stage('Package') {
            steps {
                echo 'Packaging'
            }
        }
    }

    post {
        success {
            echo 'Pipeline completed successfully'
        }

        failure {
            echo 'Pipeline failed. Review the failed stage and console output.'
        }

        always {
            echo "Finished build ${env.BUILD_NUMBER}"
        }
    }
}
```

Now the Pipeline has basic result-aware behavior.

# 101. What Does `always` Mean?

This:

```groovy
post {
    always {
        echo 'Pipeline finished'
    }
}
```

means:

```text
Run this post action regardless of the final result.
```

Useful examples later include:

* Publishing test results.
* Cleanup.
* Collecting diagnostic information.

Do not use it to blindly deploy software after a failed Pipeline.

---

# 102. What Does `success` Mean?

```groovy
success {
    echo 'Pipeline completed successfully'
}
```

runs when the relevant Pipeline/post context meets the success condition.

This can later be used for:

* Success notifications.
* Reporting.
* Release-related follow-up actions.

---

# 103. What Does `failure` Mean?

```groovy
failure {
    echo 'Pipeline failed'
}
```

runs when the Pipeline meets the failure condition.

Later this might:

* Send notifications.
* Collect diagnostics.
* Create incident signals.
* Preserve useful logs.

For now, we simply print a meaningful message.

# 104. Scripted Pipeline Error Handling

Scripted Pipeline commonly uses Groovy constructs such as:

```text
try
catch
finally
```

Jenkins' documentation contrasts Declarative `post` handling with Scripted Pipeline's use of Groovy `try`/`catch`/`finally`. ([Jenkins][1])

Example for recognition only:

```groovy
node {
    try {
        stage('Test') {
            sh 'make test'
        }
    } catch (err) {
        echo 'Tests failed'
        throw err
    } finally {
        echo 'Pipeline execution finished'
    }
}
```

You do not need to master this yet.

The important lesson is that Declarative and Scripted Pipeline handle structure differently.

# 106. Common Failure: Jenkinsfile Not Found

## Symptom

Jenkins cannot locate the Pipeline definition.

## Possible causes

* Wrong Script Path.
* File not committed.
* Wrong branch.
* Filename mismatch.
* Repository checkout problem.

## Investigation

On GitHub, verify:

```text
Jenkinsfile
```

exists on the branch Jenkins builds.

Check Jenkins:

```text
Pipeline
→ Definition
→ Pipeline script from SCM
→ Script Path
```

If the file is in the repository root:

```text
Jenkinsfile
```

should be correct.

# 107. Common Failure: Wrong Capitalization

Suppose Git contains:

```text
jenkinsfile
```

but Jenkins expects:

```text
Jenkinsfile
```

On case-sensitive systems, these are different names.

Verify:

```bash
ls -la
```

and:

```bash
git ls-files
```

Do not assume the filename.

# 108. Common Failure: Jenkinsfile Was Never Committed

You create:

```text
Jenkinsfile
```

locally.

But forget:

```bash
git add Jenkinsfile
git commit
git push
```

Jenkins retrieves the repository from GitHub.

Your local uncommitted file does not exist there.

Verify:

```bash
git status
```

Then check GitHub.

A useful rule:

```text
Local file
≠
Repository file
```

until committed and pushed.

# 109. Common Failure: Wrong Branch

Suppose:

```text
main
```

does not contain the Jenkinsfile.

But:

```text
feature/pipeline
```

does.

If Jenkins is configured for:

```text
*/main
```

it will not magically use the Jenkinsfile from the feature branch.

Check:

```bash
git branch --show-current
```

and:

```bash
git log --oneline -- Jenkinsfile
```

Then verify Jenkins branch configuration.

# 110. Common Failure: Invalid Jenkinsfile Syntax

## Investigation

* Quotes.

For:

# 112. Common Failure: `sh` Not Appropriate for Windows

This:

```groovy
sh 'python3 --version'
```

assumes a Unix-like shell environment.

On a Windows build node, you may need:

```groovy
bat 'python --version'
```

Jenkins' Jenkinsfile documentation explicitly distinguishes `sh` for Unix/Linux-like systems from `bat` for Windows. ([Jenkins][1])

Pipeline code must match the execution environment.

# 113. Common Failure: Tool Missing

A Jenkinsfile may be perfectly valid:

```groovy

    agent any

    stages {
        stage('Build') {
            steps {
                sh 'python3 --version'
            }
        }
    }
}
```

but the Pipeline can still fail because:

```text

```

is unavailable on the agent.

That is:

```text
valid Pipeline syntax
+
invalid/missing runtime environment
```

Do not confuse Pipeline syntax validation with build-environment validation.

# 114. Common Failure: Tests Fail

Suppose:

```groovy

        sh '.venv/bin/python -m pytest -v'
```

pytest returns non-zero.

Your stage fails.

```text
   ↓

   ↓
Stop unsafe progression
```

```text
2. Find failed stage
      ↓

      ↓

      ↓

      ↓
```

# 137. A More Complete Beginner Jenkinsfile

After completing the labs, use this as the clean Part 6 version for the calculator application:

```groovy
pipeline {
    agent any

    stages {
        stage('Build') {
            steps {
                echo "Starting ${env.JOB_NAME} build ${env.BUILD_NUMBER}"

                sh '''
                    set -eu

                    echo "Workspace: $WORKSPACE"

                    if [ "$PWD" != "$WORKSPACE" ]; then
                        echo "ERROR: Unexpected working directory."
                        exit 1
                    fi

                    if [ ! -f pyproject.toml ]; then
                        echo "ERROR: pyproject.toml is missing."
                        exit 1
                    fi

                    if [ ! -f requirements-dev.txt ]; then
                        echo "ERROR: requirements-dev.txt is missing."
                        exit 1
                    fi

                    echo "Cleaning previous generated output"
                    rm -rf .venv build dist

                    echo "Verifying Python"
                    python3 --version

                    echo "Creating virtual environment"
                    python3 -m venv .venv

                    echo "Installing build dependencies"
                    .venv/bin/python -m pip install --upgrade pip
                    .venv/bin/python -m pip install -r requirements-dev.txt
                '''
            }
        }

        stage('Test') {
            steps {
                sh '''
                    set -eu

                    echo "Running automated tests"
                    .venv/bin/python -m pytest -v
                '''
            }
        }

        stage('Package') {
            steps {
                sh '''
                    set -eu

                    echo "Building package"
                    .venv/bin/python -m build

                    WHEEL_FILE="$(find dist -maxdepth 1 -type f -name '*.whl' -print -quit)"

                    if [ -z "$WHEEL_FILE" ]; then
                        echo "ERROR: Expected wheel artifact was not generated."
                        exit 1
                    fi

                    echo "Generated artifact:"
                    echo "$WHEEL_FILE"

                    ls -lh dist/
                '''

                archiveArtifacts artifacts: 'dist/*', fingerprint: true
            }
        }
    }

    post {
        success {
            echo 'Pipeline completed successfully.'
        }

        failure {
            echo 'Pipeline failed. Review the failed stage and console output.'
        }

        always {
            echo "Finished Jenkins build ${env.BUILD_NUMBER}."
        }
    }
}
```
