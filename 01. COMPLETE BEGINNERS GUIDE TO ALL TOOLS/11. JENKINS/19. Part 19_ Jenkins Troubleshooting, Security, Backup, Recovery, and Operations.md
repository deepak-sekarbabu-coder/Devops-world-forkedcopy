# Part 19: Jenkins Troubleshooting, Security, Backup, Recovery, and Operations

## Learning Objective

Up to this point, you have mainly used Jenkins as an engineer who needs Jenkins to perform work.

You have learned how to:

* install Jenkins;
* create jobs;
* connect Git and GitHub;
* build applications;
* write Jenkinsfiles;
* use parameters and environment variables;
* manage credentials;
* work with plugins;
* use agents;
* build Docker images;
* publish artifacts;
* deploy applications;
* run Jenkins in AWS;
* create Multibranch Pipelines;
* run tests;
* enforce quality and security gates;
* require approvals;
* verify deployments.

Now the responsibility changes.

Imagine that Jenkins has become important to your engineering organization.

Twenty teams depend on it.

Hundreds of builds run every day.

Production deployments go through it.

Jenkins contains credentials for:

* GitHub;
* container registries;
* deployment servers;
* cloud services;
* notification systems.

Then one morning:

```text
Developers
    ↓
GitHub
    ↓
Jenkins
    ↓
???
```

Nothing runs.

The queue keeps growing.

An agent is offline.

The controller disk is almost full.

A plugin was updated yesterday.

A deployment credential has expired.

One Pipeline has been running for three hours.

Someone asks:

> Is Jenkins down?

Another person asks:

> Can we still deploy production?

Another asks:

> When was the last successful backup?

And then someone asks the question that changes your role:

> Who owns Jenkins?

Part 19 is about becoming one of the engineers capable of answering that question.

The mental model changes from:

```text
I use Jenkins.
```

to:

```text
I operate Jenkins.
```

By the end of this part, you should be able to approach Jenkins problems systematically, protect the controller, manage access, investigate failures, control disk growth, maintain plugins and Java, back up Jenkins, restore it, monitor it, and plan for failure.

---

# 1. What Changes When Jenkins Becomes Important?

A beginner Jenkins installation might be:

```text
Developer
    ↓
Jenkins
    ↓
One Job
```

A production Jenkins environment may look more like:

```text
                        Users
                          ↓
                    Reverse Proxy
                          ↓
                  Jenkins Controller
                   /      |       \
                  /       |        \
             Agent 1   Agent 2   Agent 3
                ↓         ↓         ↓
             Builds     Tests     Docker
                  \       |       /
                   \      |      /
                    External Systems
                    /     |      \
                   /      |       \
               GitHub  Registry  Cloud
                         |
                    Deployments
                         |
                     Production
```

Jenkins is now part of your delivery infrastructure.

A failure can affect:

```text
development
testing
releases
deployments
incident fixes
security patches
production recovery
```

That means Jenkins needs operational engineering.

---

# 2. Jenkins Is a Production Service

Even if Jenkins does not directly serve your customers, it can still be production-critical infrastructure.

Consider:

```text
Customer Application
        ↑
   Deployment
        ↑
     Jenkins
```

If Jenkins is unavailable during an emergency, engineers may be unable to deploy the fix.

Therefore:

```text
Jenkins reliability
        ↓
Delivery reliability
        ↓
Operational capability
```

This does not mean Jenkins must never fail.

It means its failure modes must be understood and recoverable.

---

# 3. The Jenkins Operations Mental Model

When operating Jenkins, think in layers:

```text
Layer 1
Operating System

Layer 2
Java Runtime

Layer 3
Jenkins Service

Layer 4
Jenkins Core

Layer 5
Plugins

Layer 6
Controller Configuration

Layer 7
Agents

Layer 8
Tools
Git / Docker / Maven / Python / Node

Layer 9
Pipelines

Layer 10
External Systems
GitHub / Registry / Cloud / Deployment Targets

Layer 11
Applications Being Delivered
```

A failure at one layer may appear as a failure somewhere else.

Example:

```text
Pipeline says:

docker: command not found
```

That does not necessarily mean:

```text
Jenkins is broken.
```

It may mean:

```text
Docker missing from agent.
```

Operational troubleshooting starts by identifying the failing layer.

---

# 4. First Rule of Jenkins Troubleshooting

Do not begin with:

```text
Restart Jenkins.
```

Begin with:

```text
What exactly is failing?
```

Then ask:

```text
When did it start?

What changed?

Is one job affected?

Are all jobs affected?

Is one agent affected?

Are all agents affected?

Is Jenkins UI reachable?

Is the controller healthy?

Is the operating system healthy?

Is disk available?

Is memory available?

Is the network working?

Did credentials change?

Did a plugin change?

Did Java change?

Did Jenkins change?

Did the external service change?
```

---

# 5. Troubleshooting Scope

A powerful first classification is:

```text
ONE BUILD
    ↓
probably job/application-specific

ONE JOB
    ↓
probably job/configuration-specific

ONE AGENT
    ↓
probably agent-specific

ALL AGENTS
    ↓
controller/network/shared dependency

ALL JOBS
    ↓
controller/shared service problem

JENKINS UI DOWN
    ↓
controller/OS/Java/network/service
```

This dramatically reduces the search space.


# 9. Read the First Useful Error

Beginners often scroll to the bottom and see:

```text
Finished: FAILURE
```

That tells you almost nothing.

Search upward.

You may find:

```text
Permission denied
```

or:

```text
fatal: Authentication failed
```

or:

```text
No space left on device
```

or:

```text
docker: command not found
```

or:

```text
Connection timed out
```

That is much more useful.

---

# 10. Root Cause vs Final Error

Consider:

```text
ERROR: script returned exit code 1
Finished: FAILURE
```

The exit code is the Pipeline result.

It may not be the root cause.

Earlier:

```text
fatal: could not read Username for 'https://github.com'
```

That is closer to the root cause.

Learn to separate:

```text
symptom
↓
failure propagation
↓
root cause
```

---

# 11. Jenkins System Logs

The controller itself produces logs.

In the Jenkins UI:

```text
Manage Jenkins
→ System Log
```

Jenkins also supports log recorders that can collect logs for selected Java packages/components.

Use these when investigating:

```text
plugin behavior
agent communication
authentication
SCM integration
controller internals
```

Do not enable extremely verbose debugging across everything in production unless you have a reason.

Verbose logging can:

* create noise;
* consume disk;
* expose sensitive operational details;
* make useful events harder to identify.

---

# 12. Linux Jenkins Service Logs

For current Debian/RPM package-based Jenkins installations using systemd:

```bash
sudo journalctl -u jenkins.service
```

Recent entries:

```bash
sudo journalctl -u jenkins.service -n 100
```

Follow logs live:

```bash
sudo journalctl -u jenkins.service -f
```

Logs since today:

```bash
sudo journalctl -u jenkins.service --since today
```

Logs since a specific time:

```bash
sudo journalctl -u jenkins.service \
  --since "2026-09-20 08:00:00"
```

The exact date is only an example.

---

# 13. Jenkins Service Status

Run:

```bash
sudo systemctl status jenkins
```

You may see:

```text
Active: active (running)
```

or:

```text
Active: failed
```

This immediately answers:

> Is the Jenkins service process running?

It does not answer:

> Is Jenkins completely healthy?

A running process can still have operational problems.

---

# 14. Start, Stop, and Restart

On a systemd-managed Linux installation:

```bash
sudo systemctl start jenkins
```

Stop:

```bash
sudo systemctl stop jenkins
```

Restart:

```bash
sudo systemctl restart jenkins
```

Check afterward:

```bash
sudo systemctl status jenkins
```

Then:

```bash
sudo journalctl -u jenkins.service -n 100
```

Never assume restart succeeded.

Verify it.

---

# 15. Restart Is Not Troubleshooting

Suppose:

```text
Disk
100% full
```

Restarting Jenkins may:

```text
fail
```

or temporarily change symptoms without fixing anything.

Suppose:

```text
GitHub credential expired
```

Restarting Jenkins changes nothing.

Suppose:

```text
agent cannot reach controller
```

Restarting the controller may unnecessarily interrupt other work.

Restart only when evidence indicates restart is appropriate.

---

# 16. Safe Operational Restart

Before planned maintenance, consider:

```text
Stop accepting new work
↓
allow running work to reach safe state
↓
restart
↓
verify controller
↓
verify agents
↓
verify jobs
```

Jenkins provides "Prepare for Shutdown" and safe restart mechanisms for controlled maintenance.

Do not casually restart a busy production controller during active deployments.

# 18. Pipeline Failure Workflow

Use:

```text
1. Identify failed stage.

2. Open console output.

3. Find first meaningful error.

4. Identify failing command/component.

5. Determine execution node.

6. Reproduce safely where appropriate.

7. Check dependencies.

8. Fix root cause.

9. Re-run.

10. Verify.
```

# 23. Example Queue Problem

Jenkinsfile:

```groovy
agent {
    label 'docker-linux'
}
```

```text
agent-01
labels:
linux docker
```

There is no:

```text
docker-linux
```

label.

Result:

```text

```

or a message indicating no matching node.

Fix the label mismatch.

Do not increase executors blindly.

# 26. "Running" Does Not Mean "Making Progress"

Suppose:

```text

2 hours 14 minutes

```

Investigate.

Check:

```text

```

---

# 27. Use Pipeline Timeouts

Part 7 and Part 18 introduced:

```groovy
timeout(time: 20, unit: 'MINUTES') {
    sh './integration-tests.sh'
}
```

This prevents certain operations from waiting forever.

External calls should often have their own timeout too.

Example:

```bash
curl \
  --connect-timeout 5 \
  --max-time 30 \
  --fail \
  https://example.internal/health
```

Timeout values should reflect the actual system.

---

# 28. Do Not Kill Builds Without Understanding Them

If a build is performing:

```text
database migration
production deployment
artifact publication
infrastructure change
```

aborting it halfway may leave partial state.

Before stopping critical work, understand:

```text
Is the operation transactional?

Can it resume?

Is it idempotent?

Can it leave production inconsistent?

Is rollback required?
```

# 31. Check Whether Agent Is Reachable

From the controller or relevant management host:

```bash
ping AGENT_IP
```

Ping may be blocked, so failure does not automatically prove the host is unavailable.

For SSH-based agents:

```bash
ssh jenkins-agent@AGENT_IP
```

If SSH fails, determine whether the problem is:

```text
DNS
routing
firewall
port 22
SSH daemon
key
username
host verification
permissions
```

---

# 32. Check Agent Java

On the agent:

```bash
java -version
```

Do not assume any Java release works with every Jenkins version.

Jenkins has explicit Java support requirements.

Current Jenkins releases require supported modern Java versions, and the exact requirement depends on the Jenkins release line.

Always check the current Jenkins Java support policy before controller or agent upgrades.

---

# 33. Check Agent Disk

```bash
df -h
```

Also:

```bash
df -i
```

Why both?

`df -h` checks storage capacity.

`df -i` checks inode availability.

A filesystem can have free bytes but no free inodes.

Then creating new files fails.

---

# 34. Jenkins Node Monitoring

Jenkins monitors node conditions including areas such as:

```text
disk space
temporary disk space
swap
clock
response time
```

Depending on thresholds, Jenkins can take a node offline when a monitor detects an unsafe condition.

If an agent unexpectedly goes offline, inspect the node status before assuming network failure.

# 35. Failure Lab 1: Broken Agent

Goal:

Learn how Jenkins behaves when the required execution node disappears.

Start with:

```groovy
pipeline {
    agent {
        label 'docker'

    stages {
        stage('Agent Test') {
            steps {
                sh '''
                    hostname
                    whoami
                    pwd
                '''
            }
        }
    }
}
```

Confirm success.

Then deliberately take the Docker agent offline.

Run again.

Observe:

```text

↓
Queue
↓
No available matching agent
```

Investigate:

```text

label
executor availability
queue message
agent log
```

Re-run.

Verify success.

# 38. Find Large Directories

On Linux:

```bash
sudo du -xhd1 /var/lib/jenkins | sort -h
```

Depending on your `JENKINS_HOME`, change the path.

Then drill down:

```bash
sudo du -xhd1 /var/lib/jenkins/jobs | sort -h
```

Do not immediately delete the largest directory.

First identify what it contains.

# 42. Workspace Cleanup

Declarative Pipeline can use:

```groovy
post {
    cleanup {
        deleteDir()
    }
}
```

The Workspace Cleanup plugin also provides additional workspace-cleaning capabilities when installed.

But cleanup should be intentional.

Do not delete:

```text
needed diagnostics
required artifacts
reports not yet published
```

before they are collected.

Correct order:

```text
Failure
↓
Collect Evidence
↓
Publish Reports
↓
Archive Needed Diagnostics
↓
Cleanup
```

---

# 43. Build Retention

Keeping every build forever creates:

```text
disk growth
slow administration
large backups
unnecessary artifact retention
```

Declarative Pipeline can configure a build discarder.

Example:

```groovy
options {
    buildDiscarder(
        logRotator(
            numToKeepStr: '30',
            artifactNumToKeepStr: '10'
        )
    )
}
```

This is an example policy.

Your actual retention depends on:

```text
compliance
audit requirements
artifact strategy
release frequency
incident investigation needs
storage capacity
```

---

Part 14 matters here.

```text

≠

≠
```

These must be managed independently.

# 45. Failure Lab 2: Full Workspace

Do this only on a disposable lab agent.

Do not intentionally fill a production disk.

Create a controlled quota or small disposable filesystem if possible.

Simplified lab:

```bash
mkdir -p disk-lab
```

Create a test file:

```bash
dd if=/dev/zero \
   of=disk-lab/test-file.bin \
   bs=1M \
   count=100
```

Check:

```bash
du -sh disk-lab
```

The purpose is to observe growth, not actually exhaust your real host.

For a realistic lab, use a disposable VM with a deliberately small test volume.

Observe:

```text
disk monitor
workspace growth
build behavior
```

Then remove:

```bash
rm -rf disk-lab
```

Verify:

```bash
df -h
```

# 47. Identify Jenkins OS User

Run:

```bash
ps -ef | grep '[j]enkins'
```

or inspect:

```bash
systemctl status jenkins
```

On package installations, Jenkins commonly runs as a dedicated `jenkins` account.

---

# 48. Test As the Jenkins User

A common mistake:

```text
Command works when I run it.
```

But you ran it as:

```text
ubuntu
```

while Jenkins runs as:

```text
jenkins
```

Test the relevant permissions using the actual Jenkins execution identity.

For example:

```bash
sudo -u jenkins id
```

Then inspect access carefully.

---

# 49. Linux Permission Investigation

Check:

```bash
ls -ld /path/to/directory
```

and:

```bash
ls -l /path/to/file
```

Useful commands:

```bash
id
```

```bash
namei -l /path/to/file
```

`namei -l` can help inspect permissions across every path component.

---

# 50. Do Not Fix Permissions With `chmod 777`

This is one of the most dangerous beginner habits.

Bad:

```bash
chmod -R 777 /var/lib/jenkins
```

This grants far more access than necessary and can damage the intended security model.

Instead identify:

```text
required user
required group
required operation
required path
```

Then grant the minimum permission required.

# 58. Failure Lab 4: Invalid Credential

Create a disposable test credential.

Use it against a non-production test target.

Confirm the correct credential works.

Then reference an invalid credential ID:

```groovy
withCredentials([
    usernamePassword(
        credentialsId: 'does-not-exist',
        usernameVariable: 'USERNAME',
        passwordVariable: 'PASSWORD'
    )
]) {
    sh 'echo "Credential binding reached"'
}
```

Expected:

```text
credential lookup/binding failure
```

Restore the valid ID.

Re-run.

Verify.

Do not use real production credentials for failure labs.

# 88. Authentication vs Authorization


# 89. Dangerous Authorization Models

Settings equivalent to:

```text

```

are inappropriate for normal production Jenkins environments.

Similarly:

```text

→ full administration
```

may be dangerous when accounts are not restricted to fully trusted administrators.

Production Jenkins requires deliberate access control.

---

# 90. Matrix-Based Permissions

Matrix authorization allows permissions to be granted more granularly.

Conceptually:

| Identity       | Read | Build | Configure | Credentials | Admin |
| -------------- | ---: | ----: | --------: | ----------: | ----: |
| Developers     |  Yes |   Yes |   Limited |          No |    No |
| Release Team   |  Yes |   Yes |   Limited |     Limited |    No |
| Jenkins Admins |  Yes |   Yes |       Yes |         Yes |   Yes |
| Anonymous      |   No |    No |        No |          No |    No |

This is an example, not a universal policy.

Least privilege means:

# 94. Controller Isolation

Do not treat the Jenkins controller as a general-purpose build machine.

Part 12 introduced:

```text

→ coordination

→ workloads
```

Running untrusted builds on the built-in node increases risk.

A strong production pattern is:

```text

```

# 95. Builds Are Code Execution

A Jenkinsfile can contain:

```groovy

    commands
'''
```

That means someone who can modify a trusted Jenkinsfile may be able to execute commands on an agent.

If that agent has:

```text

Docker daemon access
cloud credentials
shared filesystem access
```

the impact may be substantial.

Pipeline source control is part of the security boundary.

# 96. Multibranch Security

Part 17 becomes security-critical.

Imagine:

```text

↓
Jenkinsfile modified
↓
Pipeline requests production credential
```

That must not automatically become:

```text
production compromise
```

Separate trusted and untrusted execution contexts.

Do not expose privileged credentials to arbitrary PR code.

---

# 97. CSRF Concepts

CSRF means:

```text
Cross-Site Request Forgery
```

Imagine an authenticated Jenkins administrator visits a malicious website.

Without CSRF protection, that website might attempt to make the browser submit an unwanted state-changing request to Jenkins using the administrator's authenticated session.

Jenkins protects against this using a token known as a:

```text
crumb
```

for applicable requests.

---

# 98. Jenkins Crumbs

Conceptually:

```text
User
↓
Jenkins session
↓
Crumb generated
↓
State-changing request
+
valid crumb
↓
accepted
```

A request without required protection can be rejected.

---

# 99. Do Not Disable CSRF Protection Casually

If an old integration breaks because of CSRF protection, the wrong response is:

```text
disable security
```

Investigate:

```text
Is integration outdated?

Can it use supported authentication?

Can it obtain a crumb?

Can it use an API token where appropriate?

Can the plugin be upgraded?
```

Jenkins strongly recommends keeping CSRF protection enabled.

---

# 100. API Tokens and Scripted Clients

Modern Jenkins scripted clients can authenticate using API tokens.

Depending on the authentication method, Jenkins documents different CSRF behavior for scripted requests.

Do not place API tokens directly in scripts committed to Git.

Use secure credential handling.

```text

AWS credential
database password
Slack token
SonarQube token
deployment credential
```

A Jenkins backup may therefore be security-sensitive even when it contains no application source code.

# 102. Secret Handling Rules

Never intentionally expose secrets through:

```text

print

artifact archives
JUnit reports
screenshots
```

# 103. Masking Is Not a Security Boundary

Jenkins credential masking can reduce accidental exposure in console output.

It does not make this safe:

```bash

```

Do not intentionally print secrets and depend on masking.

# 104. Credential Scope

Conceptually:

```text

→ many jobs may potentially use it

→ jobs in relevant folder

→ narrower exposure
```

The exact available scope depends on Jenkins and plugin configuration.

# 105. External Least Privilege


```text

```


# 121. Backup Consistency

Copying actively changing files can create consistency problems.


```text

↓
```


# 123. Backup Security

A Jenkins backup can contain enough information to compromise:

```text

registries
servers

```

Treat backups as sensitive assets.

Use:

```text

```

# 124. Important Jenkins Secret Material

Jenkins uses secret material under:

```text
$JENKINS_HOME/secrets
```

to protect encrypted data such as stored credentials.

Recovery planning must account for this material.

However, Jenkins documentation specifically recommends protecting the controller key separately from normal backups because possession of both backup data and the required key material can expose protected Jenkins information.

This is an important distinction:

```text
Recoverability
AND
Secret separation
```

must both be designed.

# 125. Never Publish JENKINS_HOME

```text
↓
```


---

# 129. RPO Introduction

RPO:

```text
Recovery Point Objective
```

It asks:

> How much recent data can we tolerate losing?

Example:

```text
backup every 24 hours
```

may imply potentially losing up to roughly one day of changes in a simple failure scenario.

If that is unacceptable, backup frequency or architecture must improve.

---

# 130. RTO Introduction

RTO:

```text
Recovery Time Objective
```

It asks:

> How quickly must Jenkins return after a disaster?

Example:

```text
Jenkins must return within 2 hours.
```

Then your recovery design must support that target.

---

# 131. RPO vs RTO

```text
RPO
→ how much data loss is tolerable?

RTO
→ how much downtime is tolerable?
```

Both should influence backup and disaster recovery design.

---

# 132. A Backup Is Not Proven Until Restored

A command returning:

```text
Backup completed successfully.
```

does not prove recovery works.

You need:

```text
restore test
```

A corrupted, incomplete, inaccessible, or incompatible backup is not useful during a disaster.
