# Part 18: Testing, Quality Gates, Notifications, and Pipeline Control

## Learning Objective

In Part 17, we changed Jenkins from a simple Pipeline runner into a branch-aware CI/CD system.

We built this model:

```text
Feature Branch
→ Build
→ Test
→ No Production Deployment

Pull Request
→ Build
→ Validate
→ Review
→ No Production Deployment

Main
→ Build
→ Test
→ Package
→ Deployment Eligibility
```

But there is still a dangerous assumption hiding inside that workflow:

```text
Code compiled successfully
=
software is safe to deploy
```

That is not true.

An application can compile successfully and still contain:

* failing tests;
* broken integration behavior;
* serious code-quality problems;
* vulnerable dependencies;
* security findings;
* missing test reports;
* failed quality gates;
* incorrect configuration;
* an unhealthy deployment.

A successful build only proves that the build operation succeeded.

It does not prove that the software should be released.

In this part, we change the Pipeline into a controlled delivery system:

```text
Code
↓
Jenkins
↓
Build
↓
Unit Test
↓
Integration Test
↓
Test Reports
↓
Quality Check
↓
Quality Gate
↓
Security Check
↓
Artifact
↓
Approval
↓
Deploy
↓
Verify
↓
Notify
```

The central rule for Part 18 is:

> Deployment is something software earns by passing required evidence.

Jenkins Pipeline is designed to model this kind of multi-stage continuous delivery process. Jenkins also supports recording test results, pausing for human input, conditionally executing stages, and running status-dependent `post` actions. ([Jenkins][1])

By the end of Part 18, you should be able to build a Pipeline that deliberately refuses deployment when required checks do not pass.

---

# 2. The Wrong CI/CD Mental Model

A beginner may initially think:

```text
git push
↓
Jenkins
↓
build
↓
deploy
```

This is automation.

It is not necessarily safe delivery.

Suppose:

```text
Build
SUCCESS

Unit Tests
17 FAILED

Dependency Scan
CRITICAL VULNERABILITY

Quality Gate
FAILED
```

and Jenkins still does:

```text
Deploy Production
SUCCESS
```

The Pipeline is automated, but badly controlled.

---

# 3. The Better Mental Model

We want:

```text
Change
↓
Evidence
↓
Decision
↓
Artifact
↓
Approval where required
↓
Deployment
↓
Verification
```

Each stage answers a different question.

| Stage            | Question                                        |
| ---------------- | ----------------------------------------------- |
| Build            | Can the software be produced?                   |
| Unit Test        | Do small pieces behave correctly?               |
| Integration Test | Do components work together?                    |
| Quality Check    | Does code satisfy defined quality rules?        |
| Security Check   | Are defined security risks present?             |
| Dependency Scan  | Are known vulnerable dependencies detected?     |
| Artifact         | What exact release candidate are we delivering? |
| Approval         | Is deployment authorized?                       |
| Deploy           | Can the artifact be installed successfully?     |
| Verify           | Is the deployed application actually healthy?   |
| Notify           | Who needs to know what happened?                |

No single stage answers all of those questions.

---

# 4. Build Success Is Not Delivery Success

Consider:

```text
Build
↓
SUCCESS
```

That only tells us the build command returned successfully.

For example:

```bash
docker build -t veriqta/app:test .
```

may succeed.

But the application inside the image could still:

```text
return wrong results
fail when connecting to database
contain vulnerable packages
fail quality requirements
crash after startup
return HTTP 500
```

Therefore:

```text
successful build
≠
successful delivery
```

---

# 5. Continuous Integration vs Continuous Delivery

A useful simplified model is:

```text
Continuous Integration
↓
integrate changes frequently
↓
build
↓
test
↓
validate
```

Continuous Delivery extends the process:

```text
validated software
↓
produce release candidate
↓
apply delivery controls
↓
keep software deployable
```

Continuous deployment goes further by automatically releasing qualifying changes according to the organization's policy.

Automation does not mean removing controls.

Good automation makes controls repeatable.

# 6. Tests Are Evidence

Testing should not be thought of as:

```text
something developers do before Jenkins
```

Instead:

```text
Developer tests locally
+
Jenkins tests independently
```

Local testing gives fast feedback.

CI testing gives repeatable independent evidence.

# 7. Test Pyramid Introduction

Applications can contain several levels of testing.

A simplified model:

```text
             /\
            /  \
           / E2E\
          /------\
         /Integration\
        /------------\
       /  Unit Tests  \
      /________________\
```

For this part we focus primarily on:


---

# 8. Unit Tests

A unit test checks a small piece of application behavior in isolation.

Suppose:

```python
def add(a, b):
    return a + b
```

A unit test could be:

```python
def test_add():
    assert add(2, 3) == 5
```

Question:

> Does this small function behave as expected?

---

# 9. Unit Test Characteristics

Good unit tests are commonly:

```text
small
fast
repeatable
isolated where practical
easy to run
easy to diagnose
```

Because they are fast, they are excellent early Pipeline gates.

---

# 10. Why Unit Tests Run Early

Suppose unit tests require:

```text
20 seconds
```

while integration tests require:

```text
10 minutes
```

If unit tests already prove the change is broken, there is little reason to consume expensive infrastructure running later checks.

Therefore:

```text
Build
↓
Fast Unit Tests
↓
More Expensive Checks
```

is often sensible.

---

# 11. Unit Tests in Jenkins

For our Python training application:

```bash
pytest tests/unit/
```

A successful run might produce:

```text
================ test session starts ================
collected 6 items

tests/unit/test_calculator.py ......             [100%]

================ 6 passed ===========================
```

Jenkins sees exit code:

```text
0
```

and the shell step succeeds.

---

# 12. Failed Unit Test

Suppose:

```python
def add(a, b):
    return a - b
```

The test:

```python
assert add(2, 3) == 5
```

fails.

`pytest` returns a non-zero exit status.

Jenkins normally interprets the shell step as failed.

Pipeline:

```text
Unit Test
↓
FAILED
↓
later normal stages do not continue
```

That is exactly what we want for a mandatory test.

---

# 13. Exit Codes Still Matter

Part 5 introduced this rule:

```text
0
→ success

non-zero
→ failure
```

Jenkins depends heavily on process exit status.

A tool that discovers a serious problem but still exits:

```text
0
```

may accidentally tell Jenkins:

```text
everything is okay
```

Therefore always understand the exit behavior of tools integrated into CI.

# 14. Integration Tests

Unit tests answer:

> Does this component work by itself?

Integration tests ask:

> Do components work together correctly?

Example architecture:

```text
Application
↓
Database
```

A unit test might mock the database.

An integration test might start a real test database and verify:

```text
Application
↓
Database connection
↓
INSERT
↓
SELECT
↓
expected result
```

---

# 15. Integration Test Examples

Integration tests may validate:

```text
API ↔ Database

Service A ↔ Service B

Application ↔ Redis

Application ↔ Message Queue

Application ↔ Filesystem

Application ↔ Object Storage

Application ↔ Authentication Service
```

They test boundaries between components.

---

# 16. Why Integration Tests Are Important

Imagine:

```text
Database module
PASS

Application module
PASS
```

independently.

But when combined:

```text
Application
↓
Database

FAILED
```

Possible causes:

```text
wrong hostname
wrong port
schema mismatch
authentication problem
API contract mismatch
serialization mismatch
timeout
network issue
```

Unit tests alone may not detect these.

---

# 17. Unit vs Integration Tests

| Unit Test                 | Integration Test                     |
| ------------------------- | ------------------------------------ |
| Small scope               | Multiple components                  |
| Usually fast              | Often slower                         |
| Often isolated            | Tests real interactions              |
| Few external dependencies | May require services                 |
| Easy to run frequently    | More setup                           |
| Detect logic defects      | Detect interface/integration defects |

You normally need both.

# 19. Example Integration Test Flow

Conceptually:

```text

↓

↓

↓

↓

↓
```

---

# 20. Integration Test Readiness

Bad:

```bash
docker run -d postgres
pytest tests/integration/
```

The test may start before PostgreSQL is ready.

Better architecture:

```text
start dependency
↓
wait/check health
↓
run test
```

Do not hide readiness problems with arbitrary long sleeps unless it is only a temporary lab simplification.

# 21. Test Reports

Console output is useful.

But this:

```text
500 lines of test output
```

is not the best long-term testing interface.

We want structured test reports.

Structured reports allow Jenkins to understand:

```text
number of tests
passed tests
failed tests
skipped tests
duration
failure details
historical trends
```

Jenkins provides test recording and visualization through plugins such as the JUnit plugin. ([Jenkins][2])

# 22. JUnit Is More Than Java

The name can confuse beginners.

JUnit began in the Java ecosystem, but Jenkins commonly consumes:

```text
JUnit XML
```

as a report format from many testing tools.

Python tools such as pytest can generate JUnit-compatible XML.

So:

```text
Python tests
↓
JUnit XML
↓
Jenkins JUnit Plugin
```

is completely reasonable.

---

# 23. Generate JUnit XML With pytest

Run:

```bash
pytest --junitxml=reports/unit-tests.xml tests/unit/
```

This tells pytest:

```text
run unit tests
+
write structured XML report
```

Directory:

```text
reports/
└── unit-tests.xml
```

---

# 24. Inspect the Report

Run:

```bash
ls -lh reports/
```

You should see:

```text
unit-tests.xml
```

You can inspect it:

```bash
head -n 20 reports/unit-tests.xml
```

You do not need to manually understand every XML field.

Jenkins will parse it.

---

# 25. Publish JUnit Results

In Jenkins:

```groovy
post {
    always {
        junit 'reports/*.xml'
    }
}
```

or at stage level:

```groovy
stage('Unit Tests') {
    steps {
        sh '''
            mkdir -p reports
            pytest --junitxml=reports/unit-tests.xml tests/unit/
        '''
    }

    post {
        always {
            junit 'reports/unit-tests.xml'
        }
    }
}
```

Jenkins's `junit` step records JUnit XML test reports and exposes test results in the build UI. By default, reported test failures can mark the build `UNSTABLE`. ([Jenkins][3])

---

# 26. Why `always` Matters

Suppose:

```text
pytest
↓
test fails
↓
shell step fails
```

We still want:

```text
test report
```

to be processed.

Therefore the report publication should run even when tests fail.

That is why:

```groovy
post {
    always {
        junit ...
    }
}
```

is useful.

---

# 27. But There Is an Important Detail

If the shell command terminates the stage immediately, make sure the test framework still created the report before exiting.

For pytest with:

```bash
pytest --junitxml=reports/unit-tests.xml
```

the report is normally generated as part of the test run.

Then Jenkins can publish it afterward.

---

# 28. Jenkins Test Results

After publication, Jenkins can show information such as:

```text
Tests: 25
Passed: 23
Failed: 2
Skipped: 0
```

It can also retain historical test information and trends. ([Jenkins][2])

This is much more useful than searching raw logs every time.

# 29. Test Reports Are Not Build Artifacts

Keep the concepts separate.

```text
JUnit report
→ structured test evidence
```

while:

```text
Docker image
→ deployable artifact
```

and:

```text
coverage report
→ test/quality evidence
```

```text

→ security evidence
```

They may all be produced by the same Pipeline, but they serve different purposes.

# 30. Missing Test Reports

Suppose you configured:

```groovy
junit 'reports/*.xml'
```

but the test command writes:

```text
test-results/results.xml
```

Jenkins cannot find the expected report.

Troubleshoot:

```bash
find . -name '*.xml' -type f
```

Then compare actual location with the Jenkins pattern.

---

# 31. Do Not Ignore Missing Reports

A Pipeline that says:

```text
tests ran
```

but produces no expected evidence should be investigated.

Possible causes:

```text
wrong path
test command never ran
test process crashed
report generation disabled
workspace changed
container report not copied out
permissions
```

# 32. Code Quality

```text

Are coding rules violated?

Are likely defects detectable statically?
```

This is not the same as testing.

# 38. What Is a Quality Gate?

A quality gate is a defined set of conditions that determines whether analyzed code satisfies the organization's required quality standard.

Conceptually:

```text
Analysis
↓
Rules / Metrics
↓
Quality Gate
↓
PASS
```

or:

```text
Analysis
↓
Rules / Metrics
↓
Quality Gate
↓
FAIL
↓
STOP DELIVERY
```

---

# 39. Example Quality Conditions

A team could define requirements around things such as:

```text
new bugs
new vulnerabilities
coverage
duplicated code
maintainability issues
reliability issues
security findings
```

The exact gate belongs to the organization's engineering and risk policy.

Do not copy arbitrary thresholds merely because another company uses them.

---

# 40. Why Quality Gates Matter

Without a gate:

```text
SonarQube detects problems
↓
report exists
↓
nobody looks
↓
deployment continues
```

That is reporting.

With a gate:

```text
SonarQube detects prohibited condition
↓
gate fails
↓
Pipeline refuses promotion
```

That is enforcement.

---

# 41. Reports vs Gates

This distinction is critical.

```text
Report
→ information
```

```text
Gate
→ decision
```

A dashboard full of red findings does not protect production if nobody or nothing acts on them.

# 44. Quality Analysis Failure vs Quality Gate Failure

These are different.

## Analysis failure

Example:

```text

```

## Gate failure

# 45. Security Checks

Examples:


# 46. Security Scanning Is Evidence, Not Proof

A green scanner means:

```text
the scanner did not find a blocking issue
under its configured rules
with the information available
```

It does not mean:

```text
the application has zero vulnerabilities
```

Security tools have:

```text
coverage limits
false positives
false negatives
configuration dependencies
database freshness dependencies
language/framework limitations
```

Treat results as evidence.

---

# 47. Shift-Left Security

A useful principle is:

```text
find problems earlier
```

Instead of:

```text

↓

↓
```

```text

↓

↓
```

# 62. Warning vs Failure

Suppose code coverage drops slightly.

Your policy might say:

```text
mark UNSTABLE
```

instead of:

```text
FAIL
```

But remember:

Jenkins can continue Pipeline execution after an `UNSTABLE` result unless you explicitly design behavior otherwise. Jenkins documents `skipStagesAfterUnstable()` as one Declarative option for skipping later stages once a build becomes unstable. ([Jenkins][6])

This distinction matters enormously.

# 63. Jenkins Build Status

Common Pipeline outcomes include:

```text
SUCCESS

UNSTABLE

FAILURE

ABORTED
```

There are other contextual statuses/conditions, but these are important beginner concepts.

---

# 64. SUCCESS

`SUCCESS` means the Pipeline completed according to its configured success criteria.

Conceptually:

```text
Build
PASS

Tests
PASS

Gates
PASS

Pipeline
SUCCESS
```

But remember:

Jenkins only enforces what you configured.

A poorly designed Pipeline can be green while important checks are missing.

---

# 65. FAILURE

`FAILURE` means something caused the build to fail.

Examples:

```text
compilation error
shell command non-zero
Docker build failure
mandatory security gate failure
deployment command failure
Jenkinsfile execution problem
```

Typical UI representation is red. ([Jenkins][7])

---

# 66. UNSTABLE

`UNSTABLE` is different from `FAILURE`.

It often means:

```text
Pipeline executed
but quality/test evidence did not meet the desired condition
```

Jenkins documents test failures as a common reason a Pipeline may become `UNSTABLE`; the JUnit publisher normally marks builds unstable when test failures are recorded. ([Jenkins][3])

Typical UI representation is yellow.

---

# 67. Why UNSTABLE Is Dangerous to Misunderstand

Suppose:

```text
Tests
↓
2 failures
↓
JUnit
↓
UNSTABLE
```

A beginner may think:

```text
not SUCCESS
→ Jenkins automatically stops everything
```

Not necessarily.

Jenkins documentation explicitly notes that Pipeline execution proceeds by default after an unstable result. ([Jenkins][6])

Therefore you must decide:

```text
Should unstable software deploy?
```

For our project:

```text
No.
```

Conceptually:

# 69. `currentBuild.currentResult`

Jenkins also exposes build-result information.

# 70. Marking a Build Unstable Deliberately

Jenkins provides:

```groovy
unstable('Quality warning threshold exceeded')
```

The `unstable` step marks the stage and overall build unstable and associates a message with the result. ([Jenkins][8])

Example:

```groovy
stage('Advisory Check') {
    steps {
        script {
            unstable('Advisory quality threshold exceeded')
        }
    }
}
```

Use this only when `UNSTABLE` matches your policy.

# 71. Do Not Hide Failures With `|| true`

Dangerous:

```bash

```

Now:

```text

↓

↓

```

Sometimes this technique is used deliberately so a report can still be published, but Jenkins's own documentation warns that later stages then need to understand the recorded build result. ([Jenkins][2])

For beginners, prefer clear failure behavior.

A Pipeline could remain waiting for a long time.

# 96. `post` Actions

Declarative Pipeline's:

```groovy
post
```

section runs actions according to Pipeline or stage completion status.

Jenkins currently documents conditions including:

```text
always
changed
fixed
regression
aborted
failure
success
unstable
unsuccessful
cleanup
```

([Jenkins][7])

---

# 97. Basic `post`

```groovy
post {
    always {
        echo 'Pipeline finished.'
    }

    success {
        echo 'Pipeline succeeded.'
    }

    failure {
        echo 'Pipeline failed.'
    }
}
```

Only the appropriate conditions execute.

---

# 98. `always`

```groovy
post {
    always {
        echo 'This runs regardless of result.'
    }
}
```

Useful for:

```text
publishing reports
collecting logs
cleanup
```

provided the required context/workspace still exists.

---

# 99. `success`

```groovy
success {
    echo 'Delivery workflow succeeded.'
}
```

Use for things such as:

```text
success notification
release record
post-success action
```

---

# 100. `failure`

```groovy
failure {
    echo 'Pipeline failed.'
}
```

Useful for:

```text
alerting
diagnostic collection
incident hooks
```

---

# 101. `unstable`

```groovy
unstable {
    echo 'Pipeline is unstable.'
}
```

Useful when test or quality evidence resulted in:

```text
UNSTABLE
```

rather than hard failure.

---

# 102. `changed`

`changed` runs when the completion status differs from the previous run. ([Jenkins][7])

Example:

```text
previous:
SUCCESS

current:
FAILURE
```

Status changed.

Or:

```text
previous:
FAILURE

current:
SUCCESS
```

Status changed.

---

# 103. `fixed`

`fixed` is useful when a Pipeline returns to success after previously being failed or unstable. ([Jenkins][7])

Conceptually:

```text
Yesterday:
FAILURE

Today:
SUCCESS

→ fixed notification
```

This is often more useful than emailing the team after every successful build.

---

# 104. `regression`

`regression` represents movement from a successful prior state to a non-successful state such as failure, unstable, or aborted according to Jenkins's documented Pipeline semantics. ([Jenkins][7])

That can be useful for alerting:

```text
healthy
↓
broken
```

---

# 105. `cleanup`

`cleanup` runs after other `post` conditions regardless of result. ([Jenkins][7])

Example:

```groovy
post {
    cleanup {
        deleteDir()
    }
}
```

This is useful when workspace cleanup should happen after reporting/notification actions.

---

# 106. Stage-Level `post`

`post` can also exist inside a stage.

Example:

```groovy
stage('Unit Tests') {
    steps {
        sh 'pytest --junitxml=reports/unit.xml tests/unit/'
    }

    post {
        always {
            junit 'reports/unit.xml'
        }
    }
}
```

Now test reporting belongs directly to the test stage.

---

# 107. Pipeline-Level `post`

At the end:

```groovy
post {
    failure {
        echo 'Notify team.'
    }

    success {
        echo 'Pipeline succeeded.'
    }

    cleanup {
        deleteDir()
    }
}
```

This handles overall Pipeline state.

---

# 108. Stage-Level vs Pipeline-Level Post

Think:

```text
Stage-level post
→ react to one stage
```

```text
Pipeline-level post
→ react to entire Pipeline
```

Example:

```text
Unit Test stage
→ publish unit test report
```

while:

```text
whole Pipeline
→ send final failure notification
```

# 118. First Test Pipeline

Start with:

```groovy
pipeline {
    agent any

    options {
        skipStagesAfterUnstable()
        timeout(time: 30, unit: 'MINUTES')
    }

    stages {
        stage('Setup') {
            steps {
                sh '''
                    python3 -m venv .venv
                    . .venv/bin/activate
                    python -m pip install --upgrade pip
                    pip install -r requirements-dev.txt
                    mkdir -p reports
                '''
            }
        }

        stage('Unit Tests') {
            steps {
                sh '''
                    . .venv/bin/activate
                    pytest -v \
                      --junitxml=reports/unit-tests.xml \
                      tests/unit/
                '''
            }

            post {
                always {
                    junit 'reports/unit-tests.xml'
                }
            }
        }

        stage('Integration Tests') {
            steps {
                sh '''
                    . .venv/bin/activate
                    pytest -v \
                      --junitxml=reports/integration-tests.xml \
                      tests/integration/
                '''
            }

            post {
                always {
                    junit 'reports/integration-tests.xml'
                }
            }
        }
    }

    post {
        cleanup {
            deleteDir()
        }
    }
}
```

# 149. Complete Controlled Pipeline

A simplified training Jenkinsfile now looks like:

```groovy
pipeline {
    agent any

    options {
        skipStagesAfterUnstable()
        timeout(time: 45, unit: 'MINUTES')
        disableConcurrentBuilds()
    }

    stages {
        stage('Build Context') {
            steps {
                script {
                    env.SHORT_SHA = sh(
                        script: 'git rev-parse --short=12 HEAD',
                        returnStdout: true
                    ).trim()
                }

                echo "Branch: ${env.BRANCH_NAME}"
                echo "Commit: ${env.SHORT_SHA}"
                echo "Build: ${env.BUILD_NUMBER}"
            }
        }

        stage('Setup') {
            steps {
                sh '''
                    python3 -m venv .venv
                    . .venv/bin/activate
                    python -m pip install --upgrade pip
                    pip install -r requirements-dev.txt
                    mkdir -p reports
                '''
            }
        }

        stage('Unit Tests') {
            steps {
                sh '''
                    . .venv/bin/activate
                    pytest -v \
                      --junitxml=reports/unit-tests.xml \
                      tests/unit/
                '''
            }

            post {
                always {
                    junit 'reports/unit-tests.xml'
                }
            }
        }

        stage('Integration Tests') {
            steps {
                sh '''
                    . .venv/bin/activate
                    pytest -v \
                      --junitxml=reports/integration-tests.xml \
                      tests/integration/
                '''
            }

            post {
                always {
                    junit 'reports/integration-tests.xml'
                }
            }
        }

        stage('Quality Check') {
            steps {
                sh './scripts/quality-check.sh'
            }
        }

        stage('Security Check') {
            steps {
                sh './scripts/security-check.sh'
            }
        }

        stage('Docker Build') {
            when {
                branch 'main'
            }

            steps {
                sh '''
                    docker build \
                      -t veriqta-controlled-delivery:${SHORT_SHA} \
                      .
                '''
            }
        }

        stage('Production Approval') {
            when {
                branch 'main'
            }

            steps {
                timeout(time: 30, unit: 'MINUTES') {
                    input message: "Deploy ${env.SHORT_SHA} to production?",
                          ok: 'Deploy'
                }
            }
        }

        stage('Deploy') {
            when {
                branch 'main'
            }

            steps {
                sh './scripts/deploy.sh'
            }
        }

        stage('Verify Deployment') {
            when {
                branch 'main'
            }

            steps {
                sh './scripts/verify.sh'
            }
        }
    }

    post {
        success {
            echo "SUCCESS: ${env.JOB_NAME} #${env.BUILD_NUMBER}"
        }

        unstable {
            echo "UNSTABLE: ${env.JOB_NAME} #${env.BUILD_NUMBER}"
        }

        failure {
            echo "FAILURE: ${env.JOB_NAME} #${env.BUILD_NUMBER}"
        }

        aborted {
            echo "ABORTED: ${env.JOB_NAME} #${env.BUILD_NUMBER}"
        }

        cleanup {
            deleteDir()
        }
    }
}
```

```text
↓

↓

↓
```

# 214. Final Architecture

At the end of Part 18, your Jenkins mental model should no longer be:

```text
Git Push
↓
Jenkins
↓
Deploy
```

It should be:

```text
                    Git Push
                       ↓
                    Jenkins
                       ↓
                     Build
                       ↓
                  Unit Tests
                       ↓
                 Test Evidence
                       ↓
               Integration Tests
                       ↓
                 Test Evidence
                       ↓
                Quality Analysis
                       ↓
                  Quality Gate
                  ↙          ↘
               FAIL          PASS
                ↓              ↓
              STOP      Security Analysis
                               ↓
                         Dependency Scan
                               ↓
                          Security Gate
                          ↙          ↘
                       FAIL          PASS
                        ↓              ↓
                      STOP       Immutable Artifact
                                      ↓
                               Delivery Conditions
                                      ↓
                                  Approval
                                ↙          ↘
                            REJECT          APPROVE
                              ↓                ↓
                            STOP             Deploy
                                               ↓
                                             Verify
                                           ↙        ↘
                                        FAIL        PASS
                                         ↓            ↓
                                      ALERT       SUCCESS
```

That is the major lesson of Part 18:

> A Pipeline should not ask only, "Can I deploy this?"

It should ask:

```text
Did it build?

Did the required tests pass?

What do the test reports prove?

Did the quality requirements pass?

Did the required security checks pass?

Do we know the exact artifact?

Is this source context allowed to deploy?

Has the required approval been given?

Did deployment succeed?

Is the application actually healthy?

Do the right people know the result?
```

When Jenkins can enforce those decisions, CI/CD becomes controlled software delivery rather than automatic deployment at any cost.
