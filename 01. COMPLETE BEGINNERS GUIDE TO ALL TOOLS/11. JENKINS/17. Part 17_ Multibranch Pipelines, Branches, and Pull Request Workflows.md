# Part 17: Multibranch Pipelines, Branches, and Pull Request Workflows

## Learning Objective

In Part 16, we moved Jenkins into realistic AWS infrastructure:

```text
Developer
↓
GitHub
↓
Jenkins EC2
↓
Build
↓
Test
↓
Container Registry
↓
Application EC2
↓
Application
```

That architecture works, but there is still an important problem.

Real engineering teams do not normally have every developer pushing every change directly to `main`.

Several engineers may be working at the same time:

```text
Developer A
↓
feature/user-login

Developer B
↓
feature/payment-api

Developer C
↓
bugfix/cart-total

Developer D
↓
docs/api-guide
```

Eventually, approved changes move into:

```text
main
```

Our Jenkins architecture therefore needs to understand branches.

Instead of maintaining one Jenkins job manually for every branch, we want Jenkins to discover branches and manage their Pipelines automatically.

Our new mental model is:

```text
Feature Branch ─┐
Bugfix Branch ──┼──→ Multibranch Jenkins Pipeline
Main Branch ────┘
                         │
                         ├── feature/login
                         │      ↓
                         │    Build
                         │      ↓
                         │    Test
                         │
                         ├── bugfix/cart
                         │      ↓
                         │    Build
                         │      ↓
                         │    Test
                         │
                         └── main
                                ↓
                              Build
                                ↓
                              Test
                                ↓
                             Package
                                ↓
                             Deploy
```

Jenkins Multibranch Pipeline is designed for this model. Jenkins can scan a repository, discover branches containing a `Jenkinsfile`, create and manage branch-specific Pipeline jobs, and expose branch information such as `BRANCH_NAME`. With an appropriate branch-source plugin, Jenkins can also discover and validate pull requests. ([Jenkins][1])

By the end of Part 17, you should understand how to build CI/CD around the way an engineering team actually uses Git.

# 1. What We Are Building

Our project will move from:

```text
Repository
↓
One Jenkins Pipeline
↓
Build everything the same way
```

to:

```text
GitHub Repository
│
├── main
│   └── Jenkinsfile
│
├── feature/user-profile
│   └── Jenkinsfile
│
├── feature/search
│   └── Jenkinsfile
│
└── bugfix/login-timeout
    └── Jenkinsfile

              ↓

      Jenkins Multibranch
              │
       Repository Scan
              │
       Branch Discovery
              │
    ┌─────────┼─────────┐
    ↓         ↓         ↓
 feature    bugfix     main
    ↓         ↓         ↓
 Build     Build      Build
 Test      Test       Test
    │         │         ↓
    │         │      Package
    │         │         ↓
    X         X      Deploy
```

The key policy will be:

```text
Feature branches
→ validate changes

Bugfix branches
→ validate fixes

Pull requests
→ validate proposed merge

Main
→ validate trusted integrated code
→ become eligible for deployment
```

Notice the wording:

> eligible for deployment.

Being on `main` should be one control in the deployment policy, not an excuse to remove every other production safeguard.

# 2. Why One Pipeline Job Becomes a Problem

Imagine five developers.

They create:

```text
feature/login
feature/payments
feature/search
bugfix/cart
bugfix/session-timeout
```

Without Multibranch Pipeline, you might manually create:

```text
login-pipeline
payments-pipeline
search-pipeline
cart-fix-pipeline
session-fix-pipeline
```

Then tomorrow:

```text
feature/profile
feature/notifications
bugfix/email
```

More Jenkins jobs.

Then branches are deleted.

Someone must clean Jenkins manually.

This does not scale well.

# 3. What Jenkins Should Understand

Jenkins should be able to ask:

```text
Which branches currently exist?

Which contain a Jenkinsfile?

Which pull requests exist?

Which branch is this build for?

What commit is being tested?

Should this branch deploy?

Should this branch only test?

Has this branch disappeared?

Should its Jenkins job eventually disappear?
```

That is what Multibranch Pipeline architecture helps solve.

# 4. Branch-Based Development

A Git branch is an independent line of development.

Suppose the repository begins:

```text
A ── B ── C
          ↑
         main
```

A developer wants to implement login improvements.

Instead of immediately modifying `main`, they create:

```text
A ── B ── C
          │
          └── D ── E
                  ↑
          feature/login
```

Another developer can simultaneously create:

```text
A ── B ── C
          │
          ├── D ── E
          │       ↑
          │ feature/login
          │
          └── F ── G
                  ↑
            bugfix/cart
```

Now several pieces of work can progress independently.

# 13. The Dangerous Alternative

Imagine this Pipeline:

```groovy
pipeline {
    agent any

    stages {
        stage('Build') {
            steps {
                sh './build.sh'
            }
        }

        stage('Deploy Production') {
            steps {
                sh './deploy-production.sh'
            }
        }
    }
}
```

Now imagine Jenkins discovers:

```text
feature/login
```

and executes that same Jenkinsfile.

Without a branch restriction:

```text
feature/login
↓
Build
↓
Deploy Production
```

That is exactly the behavior we do not want.

# 15. What Is a Multibranch Pipeline?

A Jenkins Multibranch Pipeline is a Jenkins project type that discovers eligible branches in a source repository and creates/manages branch-specific Pipeline jobs.

Jenkins's documentation describes Multibranch Pipeline as automatically discovering, managing, and executing Pipelines for branches that contain a `Jenkinsfile`. ([Jenkins][1])

Think:

```text
Traditional Pipeline

Jenkins Job
↓
one configured source/branch
↓
Pipeline
```

versus:

```text
Multibranch Pipeline
↓
Repository
↓
Discover branches
↓
Create branch jobs automatically
```

---

# 22. Branch Discovery

Branch discovery means Jenkins examines the repository and identifies branches that should become Jenkins branch jobs.

Conceptually:

```text
GitHub Repository
↓
Branch Source
↓
Repository Scan
↓
Discovery Rules
↓
Eligible Branches
↓
Jenkins Jobs
```

Discovery is not the same thing as executing a build.

---

# 23. Discovery vs Build

Keep these separate.

## Discovery

```text
Does this branch exist?

Does it match our discovery policy?

Does it contain the expected Jenkinsfile?
```

## Build

```text
Checkout branch
↓
Execute Jenkinsfile
↓
Build
↓
Test
↓
possibly deploy
```

A scan discovers.

A Pipeline build executes.

# 24. What Is Branch Indexing?

Branch indexing is Jenkins examining the branch source and reconciling what Jenkins knows with what currently exists in source control.

Conceptually:

```text
Jenkins
↓
Ask repository:
"What branches/PRs exist now?"
↓
Compare with Jenkins branch jobs
↓
Create/update/remove-or-orphan managed jobs as configured
```

Jenkins exposes scan/indexing operations for Multibranch projects. ([Jenkins][1])

---

# 26. Branch Deletion Example

Yesterday:

```text
main
feature/login
feature/search
```

The login work is merged and its Git branch is deleted.

Repository becomes:

```text

```

On a later scan, Jenkins sees that:

```text

```

no longer exists.

What happens to the corresponding Jenkins item/history depends on the configured orphaned-item strategy.

That is why branch cleanup needs deliberate configuration.

# 52. Automatic Checkout

A Multibranch Declarative Pipeline normally checks out the source associated with that branch automatically when using the standard Pipeline behavior.

The special Multibranch SCM context also supports:

```groovy
checkout scm
```

when an explicit checkout is needed. Jenkins documents `checkout scm` as checking out the specific SCM revision associated with the Jenkinsfile, including branch/PR contexts. ([Jenkins][2])

Do not blindly add multiple checkouts unless you intentionally disabled or changed the default checkout behavior.

---

# 53. Why `checkout scm` Is Important

Avoid hardcoding:

```groovy
git branch: 'main',
    url: '...'
```

inside a Multibranch Jenkinsfile that is supposed to test:

```text
feature/login
```

That could cause:

```text
Jenkins discovers feature/login
↓
Pipeline starts
↓
Pipeline manually checks out main
↓
Tests main instead of feature/login
```

You would think you tested the feature branch when you did not.

---

# 54. The Core Rule

In a Multibranch Pipeline:

> Test the revision Jenkins discovered for that branch or change request.

That is why SCM context matters.

# 99. Practical Safe Jenkinsfile

Our Pipeline can now become:

```groovy
pipeline {
    agent any

    options {
        disableConcurrentBuilds()
        timeout(time: 30, unit: 'MINUTES')

    stages {
        stage('Context') {
            steps {
                echo "Branch: ${env.BRANCH_NAME}"
                echo "Change ID: ${env.CHANGE_ID ?: 'none'}"
                echo "Change Target: ${env.CHANGE_TARGET ?: 'none'}"
                echo "Build Number: ${env.BUILD_NUMBER}"
            }
        }

        stage('Install Dependencies') {
            steps {
                sh '''

                    . .venv/bin/activate
                    python -m pip install --upgrade pip
                    pip install -r requirements.txt
                '''
            }
        }

        stage('Test') {
            steps {
                sh '''
                    . .venv/bin/activate
                    pytest -v
                '''
            }
        }

        stage('PR Validation') {
            when {
                changeRequest()
            }

            steps {
                echo 'This is a pull request validation build.'
            }
        }

        stage('Package') {
            when {
                branch 'main'
            }

            steps {
                echo 'Packaging trusted main branch.'
            }
        }

        stage('Deploy Production') {
            when {
                branch 'main'
            }

            steps {
                echo 'Production deployment is permitted only from main.'
            }
        }
    }

    post {
        always {
            deleteDir()
        }
    }
}
```

# 213. Multibranch Cheat Sheet

| -------------------- | ------------------------------------------------ |
| Branch               | Independent Git line of development              |

| Bugfix branch        | Temporary branch for a fix                       |
| Pull request         | Proposal to merge changes                        |
| Multibranch Pipeline | Jenkins project managing branch Pipelines        |
| Branch source        | SCM repository/provider Jenkins scans            |
| Discovery            | Finding eligible branches/PRs                    |
| Indexing             | Reconciling Jenkins with SCM state               |
| Jenkinsfile          | Pipeline-as-Code definition                      |
| `BRANCH_NAME`        | Current Multibranch branch context               |
| `CHANGE_ID`          | Change-request identifier when available         |
| `CHANGE_TARGET`      | Target branch of change request when available   |
| `when`               | Declarative stage condition                      |
| `branch 'main'`      | Run stage only for matching Multibranch branch   |
| `changeRequest()`    | Run stage for change-request context             |
| Orphaned item        | Jenkins branch item whose SCM branch disappeared |
| Build history        | Historical executions for a job                  |
| Commit SHA           | Strong source revision identifier                |
| Branch protection    | Repository controls around important branches    |
| Promotion            | Moving validated artifact through environments   |
