# Part 9: Parameters, Environment Variables, and Application Configuration

## Learning Objective

In Part 8, you made Jenkins respond automatically to source-code changes:

```text
Developer
    ↓
Git Push
    ↓
GitHub
    ↓
Webhook
    ↓
Jenkins
    ↓
Pipeline
```

That solved **when** the Pipeline should run.

Now we need to solve another problem:

> How should the same Pipeline behave differently depending on what we are trying to do?

A real CI/CD Pipeline may need to:

* build version `1.4.2` today and `1.4.3` tomorrow;
* deploy to development during testing;
* deploy to staging before release;
* deploy to production only under stricter conditions;
* optionally run a longer test suite;
* enable or disable a deployment;
* use different URLs or configuration for each environment;
* reject dangerous or invalid combinations before anything is deployed.

We do **not** want three almost-identical Jenkins jobs:

```text
my-app-development
my-app-staging
my-app-production
```

with three duplicated Jenkinsfiles that slowly become different from one another.

Instead, we want:

```text
                    Jenkins Pipeline
                           ↓
                  Controlled Inputs
                           ↓
              Environment Selection
                           ↓
                    Configuration
                           ↓
                        Build
                           ↓
                  Deployment Target
```

More concretely:

```text
                         Jenkins
                            ↓
            ┌───────────────┼───────────────┐
            │               │               │
      DEPLOY_ENV       APP_VERSION      RUN_TESTS
            │               │               │
            └───────────────┼───────────────┘
                            ↓
                      Validation
                            ↓
                     Configuration
                            ↓
                          Build
                            ↓
              development / staging / production
```

By the end of Part 9, you should be able to create **one configurable Jenkins Pipeline** whose behavior changes according to controlled inputs without duplicating the job.

Jenkins Declarative Pipeline supports build parameters through the `parameters` directive, exposes their values through the `params` object, and also exports parameter values as environment variables when the build begins. ([Jenkins][1])

---

# 1. Start With the Problem: Hardcoded Pipelines

Imagine this Jenkinsfile:

```groovy
pipeline {
    agent any

    stages {
        stage('Build') {
            steps {
                echo 'Building version 1.0.0'
            }
        }

        stage('Deploy') {
            steps {
                sh './deploy.sh production 1.0.0'
            }
        }
    }
}
```

It works.

But look carefully.

Two important decisions are buried directly inside the Pipeline:

```text
production
1.0.0
```

This means the Pipeline is effectively saying:

```text
ALWAYS deploy
        ↓
production
        ↓
version 1.0.0
```

What happens tomorrow when version `1.0.1` needs to be deployed?

Someone edits the Jenkinsfile.

What happens when you want staging?

Someone edits the Jenkinsfile.

What happens when you want development again?

Someone edits the Jenkinsfile again.

That is not a flexible design.

---

# 2. Configuration vs Pipeline Logic

A useful distinction is:

```text
Pipeline logic
=
what the delivery process does
```

while:

```text
Configuration
=
values that influence how the process behaves
```

For example:

```text
Pipeline Logic

Checkout
   ↓
Build
   ↓
Test
   ↓
Package
   ↓
Deploy
```

Configuration might include:

```text
DEPLOY_ENV = staging

APP_VERSION = 1.4.2

RUN_EXTENDED_TESTS = true

DEPLOY_APPLICATION = false
```

The workflow remains broadly the same.

The values change.

That is the foundation of configurable Pipelines.

---

# 3. Why Configuration Matters

Consider two designs.

## Design A: duplicated jobs

```text
app-development
      ↓
Development configuration

app-staging
      ↓
Staging configuration

app-production
      ↓
Production configuration
```

Each job contains nearly the same logic.

Soon you may have:

```text
Development Jenkinsfile
Staging Jenkinsfile
Production Jenkinsfile
```

A bug fix gets added to staging but forgotten in production.

A security improvement gets added to production but not development.

A new test stage exists in one job but not another.

Configuration duplication becomes Pipeline duplication.

---

# 4. Better Design: One Pipeline, Controlled Configuration

Instead:

```text
                    One Jenkinsfile
                          ↓
                    Parameters
                          ↓
                    Validation
                          ↓
                 Environment Config
                          ↓
                   Shared Pipeline
                          ↓
              Appropriate Destination
```

For example:

```text
DEPLOY_ENV
    │
    ├── development
    ├── staging
    └── production
```

The same Pipeline understands all three.

This is the main goal of Part 9.

---

# 5. What Is a Parameter?

A parameter is an input supplied to a build.

Think of a function:

```text
deploy(environment, version)
```

The logic stays the same.

The inputs change.

For Jenkins:

```text
Pipeline
   ↓
Parameters
   ↓
DEPLOY_ENV = staging
APP_VERSION = 2.3.1
RUN_TESTS = true
```

Those values become available while the Pipeline runs.

---

# 6. Parameters Answer Questions

A parameter usually answers a question.

For example:

```text
Which environment?
```

Answer:

```text
staging
```

Another:

```text
Which application version?
```

Answer:

```text
2.5.0
```

Another:

```text
Should extended tests run?
```

Answer:

```text
true
```

Therefore:

```text
Question
   ↓
Parameter
   ↓
Value
   ↓
Pipeline behavior
```

---

# 7. Declarative Pipeline `parameters`

Parameters are declared inside:

```groovy
parameters {

}
```

Example:

```groovy
pipeline {
    agent any

    parameters {
        string(
            name: 'APP_VERSION',
            defaultValue: '1.0.0',
            description: 'Application version to build'
        )
    }

    stages {
        stage('Show Configuration') {
            steps {
                echo "Application version: ${params.APP_VERSION}"
            }
        }
    }
}
```

The `parameters` directive belongs inside the top-level `pipeline` block and makes user-provided values available through `params`. ([Jenkins][2])

---

# 8. Understanding the String Parameter

Look at:

```groovy
string(
    name: 'APP_VERSION',
    defaultValue: '1.0.0',
    description: 'Application version to build'
)
```

There are three important pieces.

### `name`

```groovy
name: 'APP_VERSION'
```

This identifies the parameter.

We can later access:

```groovy
params.APP_VERSION
```

### `defaultValue`

```groovy
defaultValue: '1.0.0'
```

This is the initial/default value.

### `description`

```groovy
description: 'Application version to build'
```

This tells the person starting the build what the parameter means.

Good descriptions reduce operator mistakes.

---

# 9. Accessing Parameters

Suppose:

```text
APP_VERSION = 2.4.1
```

You can access it in Groovy:

```groovy
echo "Building ${params.APP_VERSION}"
```

Conceptually:

```text
params
  ↓
APP_VERSION
  ↓
2.4.1
```

Jenkins provides `params` as a Pipeline global containing defined parameters. ([Jenkins][2])

---

# 10. Parameters Are Also Exported to the Build Environment

Jenkins also exports build parameters as environment variables when the build starts. ([Jenkins][1])

Therefore a parameter such as:

```text
APP_VERSION
```

can be available to a POSIX shell command as:

```bash
$APP_VERSION
```

For example:

```groovy
sh '''
    echo "Building application version: $APP_VERSION"
'''
```

But inside Pipeline/Groovy logic, using:

```groovy
params.APP_VERSION
```

makes it clearer that the value originated as a build parameter.

---

# 11. String Parameters

A string parameter accepts text.

Examples:

```text
1.4.2
release-2026-09
customer-api
feature-login
```

Example:

```groovy
parameters {
    string(
        name: 'APP_VERSION',
        defaultValue: '1.0.0',
        description: 'Version of the application'
    )
}
```

String parameters are useful for values such as:

```text
Application version
Release identifier
Image tag
Git revision
Region name
Non-sensitive hostname
Artifact version
```

But there is an important problem.

Users can type almost anything.

---

# 12. String Parameters Need Validation

Suppose you expect:

```text
1.4.2
```

but someone enters:

```text
banana
```

Jenkins sees a string.

It does not automatically understand your business rules.

Or someone enters:

```text
production!!!!
```

Or:

```text
../../something
```

Or shell metacharacters.

The Pipeline must not assume:

```text
user input
=
valid input
```

This leads to parameter validation, which we will implement later.

---

# 13. Boolean Parameters

A Boolean represents two states:

```text
true
false
```

or conceptually:

```text
yes
no
```

Example:

```groovy
parameters {
    booleanParam(
        name: 'RUN_EXTENDED_TESTS',
        defaultValue: false,
        description: 'Run the optional extended test suite'
    )
}
```

This is useful when Pipeline behavior needs an on/off decision.

---

# 14. Boolean Parameters Are Better Than Text for Yes/No Decisions

You could create:

```groovy
string(
    name: 'RUN_TESTS',
    defaultValue: 'yes'
)
```

But now users could enter:

```text
YES
Yes
yes
true
1
y
banana
```

Your Pipeline has to interpret all of those.

Instead:

```groovy
booleanParam(
    name: 'RUN_TESTS',
    defaultValue: true
)
```

constrains the input to:

```text
true
false
```

Use a Boolean when the decision is genuinely binary.

---

# 15. Choice Parameters

Suppose your allowed environments are:

```text
development
staging
production
```

A string parameter would allow someone to type:

```text
prod
production
Production
PRODUCTION
prd
prodction
```

That is unnecessary ambiguity.

A choice parameter is safer:

```groovy
choice(
    name: 'DEPLOY_ENV',
    choices: ['development', 'staging', 'production'],
    description: 'Environment targeted by this build'
)
```

Now the user chooses from controlled values.

---

# 16. Why Choice Parameters Matter

Compare:

```text
Free text:

Environment: ___________________
```

with:

```text
Controlled selection:

Environment:
[ development ▼ ]
```

The second reduces:

```text
Typos
Unexpected values
Capitalization differences
Unsupported environments
Configuration ambiguity
```

For a small fixed set of valid values, a choice parameter is usually more appropriate than unrestricted text.

---

# 17. Our First Configurable Pipeline

Create:

```groovy
pipeline {
    agent any

    parameters {
        choice(
            name: 'DEPLOY_ENV',
            choices: ['development', 'staging', 'production'],
            description: 'Select the target environment'
        )

        string(
            name: 'APP_VERSION',
            defaultValue: '1.0.0',
            description: 'Application version'
        )

        booleanParam(
            name: 'RUN_EXTENDED_TESTS',
            defaultValue: false,
            description: 'Run the extended test suite'
        )
    }

    stages {
        stage('Configuration') {
            steps {
                echo "Environment: ${params.DEPLOY_ENV}"
                echo "Version: ${params.APP_VERSION}"
                echo "Extended tests: ${params.RUN_EXTENDED_TESTS}"
            }
        }
    }
}
```

Now we have three different parameter types.

---

# 18. Mental Model

Our Pipeline now receives:

```text
                   Jenkins Pipeline
                          ↓
       ┌──────────────────┼─────────────────┐
       │                  │                 │
 DEPLOY_ENV          APP_VERSION     RUN_EXTENDED_TESTS
       │                  │                 │
   choice              string            boolean
       │                  │                 │
   staging              2.1.0             true
       └──────────────────┼─────────────────┘
                          ↓
                     Pipeline
```

This is much more flexible than hardcoding values.

# 20. Parameter Definitions vs Parameter Values

Do not confuse these.

This:

```groovy
choice(
    name: 'DEPLOY_ENV',
    choices: ['development', 'staging', 'production']

```

defines the parameter.

This:

```text
DEPLOY_ENV = staging
```

is the value selected for a particular build.

Think:

```text
Definition
    ↓
What inputs are allowed?

Build
    ↓
Which value was selected?
```

# 24. What Is an Environment Variable?

An environment variable is a named value available to a process and usually inherited by processes it starts.

Conceptually:

```text
Process Environment

PATH=/usr/local/bin:/usr/bin:/bin
APP_NAME=veriqta-api
DEPLOY_ENV=staging
BUILD_NUMBER=52
```

Programs can inspect these values while running.

---

# 25. Why Environment Variables Are Useful

Instead of writing:

```python
api_url = "https://staging.example.com"
```

directly into application code, a program might read:

```text
API_URL
```

from its runtime environment.

Now:

```text
Development
API_URL=https://dev.example.com
```

while:

```text
Staging
API_URL=https://staging.example.com
```

and:

```text
Production
API_URL=https://api.example.com
```

The application can remain the same.

Its configuration changes.

# 26. Jenkins Environment Variables

Jenkins exposes many environment variables automatically.

Examples include:

```text
BUILD_NUMBER
BUILD_ID
BUILD_TAG
BUILD_URL
JOB_NAME
NODE_NAME
WORKSPACE
JENKINS_URL
```

Availability can depend on Jenkins configuration and execution context. Jenkins exposes Pipeline environment variables through the global `env` variable. ([Jenkins][2])

For example:

```groovy
echo "Build: ${env.BUILD_NUMBER}"
```

---

# 27. The `env` Global Variable

In a Jenkinsfile:

```groovy
env.BUILD_NUMBER
```

means:

```text
env
 ↓
Jenkins environment
 ↓
BUILD_NUMBER
```

Example:

```groovy
stage('Build Information') {
    steps {
        echo "Job: ${env.JOB_NAME}"
        echo "Build: ${env.BUILD_NUMBER}"
        echo "Workspace: ${env.WORKSPACE}"
    }
}
```

Jenkins documents `env` as a Pipeline global accessible throughout the Jenkinsfile. ([Jenkins][2])

---

# 28. Parameters vs Environment Variables

They are related but not identical concepts.

| Concept              | Purpose                                            |
| -------------------- | -------------------------------------------------- |
| Parameter            | Controlled input to a build                        |
| Environment variable | Named value available in the execution environment |

For example:

```text
Parameter:

APP_VERSION = 2.3.0
```

Jenkins can export that parameter into the build environment, allowing shell commands to use:

```bash
$APP_VERSION
```

At the same time, Jenkins automatically provides variables such as:

```bash
$BUILD_NUMBER
```

---

# 29. `params` vs `env`

Inside Jenkins Pipeline logic:

```groovy
params.APP_VERSION
```

clearly means:

> Give me the build parameter named APP_VERSION.

While:

```groovy
env.BUILD_NUMBER
```

means:

> Give me the environment variable BUILD_NUMBER.

This distinction improves readability.

# 33. Defining Your Own Environment Variables

Declarative Pipeline supports:

```groovy
environment {

}
```

Example:

```groovy
pipeline {
    agent any

    environment {
        APP_NAME = 'veriqta-api'
        TEAM_NAME = 'platform-engineering'
    }

    stages {
        stage('Information') {
            steps {
                echo "Application: ${env.APP_NAME}"
                echo "Team: ${env.TEAM_NAME}"
            }
        }
    }
}
```

An `environment` directive at Pipeline level applies to all Pipeline stages. A stage-level `environment` directive applies only within that stage. ([Jenkins][2])

# 34. Pipeline-Level Environment Variables

Example:

```groovy
pipeline {
    agent any

    environment {
        APP_NAME = 'veriqta-api'
    }

    stages {
        stage('Build') {
            steps {
                echo "${env.APP_NAME}"
            }
        }

        stage('Test') {
            steps {
                echo "${env.APP_NAME}"
            }
        }
    }
}
```

`APP_NAME` is available in both stages because it was defined at Pipeline scope.

Think:

```text
pipeline
│
├── environment
│     └── APP_NAME
│
├── Build
│     └── can access APP_NAME
│
└── Test
      └── can access APP_NAME
```

---

# 35. Stage-Level Environment Variables

You can narrow scope:

```groovy
stage('Deploy') {
    environment {
        DEPLOY_REGION = 'us-east-1'
    }

    steps {
        echo "Region: ${env.DEPLOY_REGION}"
    }
}
```

Conceptually:

```text
Pipeline
│
├── Build
│
├── Test
│
└── Deploy
      │
      └── DEPLOY_REGION
```

Keeping values scoped to where they are needed makes Pipelines easier to understand and can reduce unnecessary exposure, especially once credentials are involved.

# 36. What Does "Global Variable" Mean in Jenkins Pipeline?

This term can cause confusion because people use "global" casually.

Jenkins Pipeline provides global variables such as:

```text
env
params
currentBuild
```

For example:

```groovy
env.BUILD_NUMBER
params.DEPLOY_ENV
currentBuild.result
```

Jenkins' Pipeline documentation identifies `env`, `params`, and `currentBuild` among its default Pipeline globals. ([Jenkins][3])

These are different from creating:

```groovy
environment {
    APP_NAME = 'veriqta-api'
}
```

`APP_NAME` is an environment variable you defined.

`env` is a Jenkins Pipeline global through which environment variables can be accessed.

# 39. `printenv`

Linux provides:

```bash
printenv
```

which displays environment variables.

You could temporarily run:

```groovy
sh 'printenv'
```

Jenkins documentation uses `printenv` in environment examples. ([Jenkins][2])

But there is an important security warning.

---

# 40. Do Not Blindly Print Production Environments

Once a Pipeline contains credentials, indiscriminately dumping:

```bash
printenv
```

can become risky.

Even when Jenkins masks some credential values, masking should not be treated as a security boundary. Jenkins warns that a Pipeline capable of using a credential may also be capable of disclosing it. ([Jenkins][2])

Therefore:

```text
Learning environment with non-sensitive variables
        ↓
printenv may be useful
```

but:

```text
Production Pipeline containing secrets
        ↓
Do not dump everything casually
```

Print only the diagnostic values you actually need.

# 41. Runtime Configuration

Runtime configuration means values supplied or determined when software is being executed rather than permanently embedded in its source.

For example:

```text
Application code
       ↓
reads API_URL
       ↓
runtime provides:
https://staging.example.com
```

The same code could later run with:

```text
API_URL=https://api.example.com
```

without modifying the application's source code.

---

# 42. Why Runtime Configuration Matters in DevOps

Consider:

```text
Source Code
    ↓
Build
    ↓
Artifact
```

Ideally, environment-specific differences should not require rebuilding the application's source unnecessarily.

A common deployment goal is:

```text
Same tested artifact
        ↓
Development
        ↓
Staging
        ↓
Production
```

with appropriate configuration supplied at deployment/runtime.

This improves confidence because production receives the artifact that was previously tested rather than a separately modified build.

# 43. Development, Staging, and Production

These environments serve different purposes.

## Development

Used for active development and early testing.

Typical characteristics:

```text
Frequent changes
Lower-risk test data
Developer experimentation
Debugging
Less restrictive release process
```

## Staging

Used to validate a release in an environment designed to approximate important production behavior.

Typical purposes:

```text
Integration testing
Release validation
Pre-production checks
Deployment testing
Acceptance testing
```

## Production

The live environment serving real users or business workloads.

Typical requirements:

```text
Stricter controls
Higher reliability
Security
Monitoring
Backups
Auditing
Change control
Recovery planning
```

# 45. Environment Configuration Example

Suppose we have:

| Environment | URL                           | Log Level |
| ----------- | ----------------------------- | --------- |
| development | `https://dev.example.com`     | `DEBUG`   |
| staging     | `https://staging.example.com` | `INFO`    |
| production  | `https://example.com`         | `WARN`    |

These values are non-sensitive configuration.

Our Pipeline can map environment selection to configuration.

---

# 46. Mapping Environment to Configuration

A simple beginner implementation:

```groovy
stage('Configure') {
    steps {
        script {
            if (params.DEPLOY_ENV == 'development') {
                env.APP_URL = 'https://dev.example.com'
                env.LOG_LEVEL = 'DEBUG'
            } else if (params.DEPLOY_ENV == 'staging') {
                env.APP_URL = 'https://staging.example.com'
                env.LOG_LEVEL = 'INFO'
```

# 55. Parameter Validation

Validation asks:

> Does this input satisfy the rules required by the Pipeline?

For `APP_VERSION`, we might require:

```text
number.number.number
```

Examples:

```text
1.0.0
2.7.1
15.3.42
```

Invalid:

```text
hello
1
1.2
version-1
1.2.3.4
```

For this lab, we will intentionally use a simplified semantic-version pattern.

---

# 56. Validate an Application Version

Example:

```groovy
stage('Validate Parameters') {
    steps {
        script {
            if (!(params.APP_VERSION ==~ /^\d+\.\d+\.\d+$/)) {
                error(
                    "Invalid APP_VERSION '${params.APP_VERSION}'. " +
                    "Expected format: major.minor.patch, for example 1.4.2."
                )
            }
        }
    }
}
```

Important:

```groovy
error(...)
```

stops the Pipeline with a clear failure message.

That is better than allowing an invalid value to reach deployment.

---

# 57. Understand the Pattern

We used:

```text
^\d+\.\d+\.\d+$
```

At a beginner level:

```text
^
start of value
```

```text
\d+
one or more digits
```

```text
\.
literal dot
```

then the pattern repeats:

```text
digits.digits.digits
```

and:

```text
$
end of value
```

So:

```text
2.7.1
```

matches.

But:

```text
2.7
```

does not.

This is intentionally a simplified version rule, not a complete implementation of the full Semantic Versioning specification.

# 75. Good Parameter Design

Good:


Potentially poor:


```text

```

and Jenkins executes it.

That turns your Pipeline into an arbitrary remote command interface.

Avoid this design.

# 76. Parameters Are Untrusted Input

This is a critical security lesson.

Suppose:

```groovy
parameters {
    string(
        name: 'MESSAGE',
        defaultValue: 'hello'
    )
}
```

Then you write:

```groovy
sh "echo ${params.MESSAGE}"
```

If a user supplies shell syntax, unsafe Groovy interpolation can cause unintended command execution.

Jenkins explicitly warns that Groovy interpolation of user-controlled variables into `sh`, `bat`, PowerShell, and similar command steps can create command-injection vulnerabilities. ([Jenkins][2])

Therefore:

```text
Parameter
≠
trusted shell code
```

---

# 77. Safer Shell Expansion

Instead of interpolating user input into a Groovy command string:

```groovy
sh "echo ${params.MESSAGE}"
```

prefer designs where the shell receives a fixed script and reads the value from its environment:

```groovy
sh '''
    printf '%s\n' "$MESSAGE"
'''
```

Because build parameters are exported as environment variables, the shell can access `$MESSAGE`. ([Jenkins][2])

You should still validate inputs according to their intended format.

Quoting is not a replacement for validation.

```text
"Does this look okay?"
```

For example:

### Environment

Allowed:

```text

staging
production
```

Use a choice parameter.

### Version

Allowed:

```text

```

Validate format.

### Deploy

Allowed:

```text

```

Use Boolean.

### Region

If only two are supported:

```text

```

use a choice.

The more constrained the valid input domain is, the less reason there is to accept arbitrary text.

```text
major.minor.patch
```

### Rule 2

Only these environments exist:

```text
development
staging
production
```

The choice parameter already strongly constrains this.

### Rule 3

Production deployment requires:

```text
RUN_EXTENDED_TESTS = true
```

### Rule 4

Production cannot use a development URL.

### Rule 5

No secrets are stored in parameters or the Jenkinsfile.

# 99. Complete Jenkinsfile

Use:

```groovy
pipeline {
    agent any

    parameters {
        choice(
            name: 'DEPLOY_ENV',
            choices: ['development', 'staging', 'production'],
            description: 'Select the target environment'
        )

        string(
            name: 'APP_VERSION',
            defaultValue: '1.0.0',
            description: 'Application version in major.minor.patch format'
        )

        booleanParam(
            name: 'RUN_EXTENDED_TESTS',
            defaultValue: false,
            description: 'Run the optional extended test suite'
        )

        booleanParam(
            name: 'DEPLOY_APPLICATION',
            defaultValue: false,
            description: 'Deploy the application after successful tests'
        )
    }

    environment {
        APP_NAME = 'veriqta-api'
    }

    stages {
        stage('Validate Parameters') {
            steps {
                script {
                    if (!(params.APP_VERSION ==~ /^\d+\.\d+\.\d+$/)) {
                        error(
                            "Invalid APP_VERSION '${params.APP_VERSION}'. " +
                            "Expected major.minor.patch, for example 2.4.1."
                        )
                    }

                    if (
                        params.DEPLOY_ENV == 'production' &&
                        params.DEPLOY_APPLICATION &&
                        !params.RUN_EXTENDED_TESTS
                    ) {
                        error(
                            'Production deployment requires RUN_EXTENDED_TESTS=true.'
                        )
                    }
                }
            }
        }

        stage('Configure Environment') {
            steps {
                script {
                    if (params.DEPLOY_ENV == 'development') {
                        env.APP_URL = 'https://dev.example.com'
                        env.LOG_LEVEL = 'DEBUG'
                    } else if (params.DEPLOY_ENV == 'staging') {
                        env.APP_URL = 'https://staging.example.com'
                        env.LOG_LEVEL = 'INFO'
                    } else if (params.DEPLOY_ENV == 'production') {
                        env.APP_URL = 'https://example.com'
                        env.LOG_LEVEL = 'WARN'
                    } else {
                        error(
                            "Unsupported environment: ${params.DEPLOY_ENV}"
                        )
                    }
                }
            }
        }

        stage('Show Configuration') {
            steps {
                echo "Application: ${env.APP_NAME}"
                echo "Version: ${params.APP_VERSION}"
                echo "Environment: ${params.DEPLOY_ENV}"
                echo "Target URL: ${env.APP_URL}"
                echo "Log level: ${env.LOG_LEVEL}"
                echo "Extended tests: ${params.RUN_EXTENDED_TESTS}"
                echo "Deploy: ${params.DEPLOY_APPLICATION}"
                echo "Jenkins build: ${env.BUILD_NUMBER}"
            }
        }

        stage('Build') {
            steps {
                echo "Building ${env.APP_NAME} version ${params.APP_VERSION}"

                sh '''
                    set -eu

                    echo "Build environment:"
                    echo "Application: $APP_NAME"
                    echo "Version: $APP_VERSION"
                    echo "Deployment environment: $DEPLOY_ENV"
                    echo "Jenkins build: $BUILD_NUMBER"
                '''
            }
        }

        stage('Basic Tests') {
            steps {
                echo 'Running required basic tests.'

                sh '''
                    set -eu
                    echo "Basic tests passed."
                '''
            }
        }

        stage('Extended Tests') {
            when {
                expression {
                    params.RUN_EXTENDED_TESTS
                }
            }

            steps {
                echo 'Running extended test suite.'

                sh '''
                    set -eu
                    echo "Extended tests passed."
                '''
            }
        }

        stage('Deployment Preview') {
            when {
                expression {
                    params.DEPLOY_APPLICATION
                }
            }

            steps {
                echo "Deployment approved by configuration."
                echo "Application: ${env.APP_NAME}"
                echo "Version: ${params.APP_VERSION}"
                echo "Environment: ${params.DEPLOY_ENV}"
                echo "Target: ${env.APP_URL}"
            }
        }
    }

    post {
        success {
            echo "Build ${env.BUILD_NUMBER} completed successfully."
        }

        failure {
            echo "Build ${env.BUILD_NUMBER} failed."
        }

        always {
            echo 'Pipeline execution finished.'
        }
    }
}
```

# 114. Configuration Precedence

As systems become more advanced, the same setting may potentially come from multiple places:

```text
Application default
Jenkinsfile
Build parameter
Environment variable
Configuration file
Deployment platform
Secret manager
```

This creates an important question:

> Which source wins?

That is called configuration precedence.

For now, keep your Pipeline simple enough that precedence is obvious.

For example:

```text
DEPLOY_ENV
    ↓
parameter is source of selection
```

and:

```text
APP_URL
    ↓
Pipeline mapping is source
```

Avoid defining the same variable in five places.

# 115. Environment Variable Naming


This makes environment-style configuration visually recognizable.

Avoid:


# 117. Descriptions Should Prevent Mistakes

Bad:

```groovy
description: 'Version'
```

Better:

```groovy
description: 'Application version in major.minor.patch format, for example 2.4.1'
```

Bad:


Better:


# 118. Parameter Defaults Should Be Deliberate

Consider this ordering:

```groovy
choices: ['production', 'staging', 'development']
```

If the first choice becomes the default behavior in the interface, production is now the easiest selection.

For many workflows, a safer design might be:

```groovy
choices: ['development', 'staging', 'production']
```

The exact design depends on the organization, but defaults should be intentional.

# 119. Production Needs More Than a Parameter

Do not mistake:

```text
DEPLOY_ENV = production
```

for a complete production-control system.

Real production deployment may also require:

```text
Authorization
Approval
Protected branches
Quality gates
Security checks
Change controls
Deployment windows
Artifact provenance
Rollback
Monitoring
Audit evidence
```

Later parts will add more of these controls.

The parameter simply expresses intent.

It does not prove authorization.

# 120. Parameter vs Authorization

This distinction is critical.

```text
Parameter:
DEPLOY_ENV=production
```

means:

> The build requests production behavior.

It does **not** automatically mean:

> This user is authorized to deploy production.

Authorization is a separate security concern.

Never use a choice parameter as your only production security boundary.

# 121. Parameter vs Approval

Similarly:

```text
DEPLOY_APPLICATION=true
```

is not necessarily equivalent to:

```text
Production deployment approved by authorized person.
```

Later we will use Pipeline controls such as:

```groovy

```

for approval workflows.

# 124. Pipeline Readability

Compare:

```groovy
if (params.E == 'p' && params.D && params.T) {
```

with:

```groovy
if (
    params.DEPLOY_ENV == 'production' &&
    params.DEPLOY_APPLICATION &&
    params.RUN_EXTENDED_TESTS

```

The second is longer.

It is also far easier to understand.

Pipeline code is operational code.

People may need to understand it during an incident.

Optimize for clarity.

# 125. Comments Should Explain Why

Bad:

```groovy
// Check if production
if (params.DEPLOY_ENV == 'production') {
```

The code already says that.

Better:

```groovy

    params.DEPLOY_ENV == 'production' &&
    params.DEPLOY_APPLICATION &&
    !params.RUN_EXTENDED_TESTS
```

# 126. Failure Scenario: Missing Configuration

Suppose your configuration stage forgets:

```groovy
env.APP_URL
```

for production.

Later:

```groovy
echo "Deploying to ${env.APP_URL}"
```

may produce an invalid or missing target.

A strong Pipeline should verify critical configuration before using it.

---

# 127. Validate Derived Configuration

After mapping:

```groovy
if (params.DEPLOY_ENV == 'production') {
    env.APP_URL = 'https://example.com'
}
```

you can verify:

```groovy
if (!env.APP_URL?.trim()) {
    error('APP_URL was not configured.')
}
```

Now:

```text
Configuration selection
        ↓
Configuration verification
        ↓
Execution
```

This prevents silent propagation of missing values.

---

# 128. Failure Scenario: Typo in Environment Variable

Suppose you define:

```groovy
env.APP_URL
```

but later use:

```groovy
env.APPLICATION_URL
```

They are different names.

The Pipeline will not magically know they mean the same thing.

Use consistent naming.

When debugging, ask:

```text
Was variable defined?

Is spelling identical?

Is scope correct?

Was it assigned before use?

Is value empty?
```

---

# 129. Failure Scenario: Scope

Suppose:

```groovy
stage('Configure') {
    environment {
        SPECIAL_VALUE = 'hello'
    }

    steps {
        echo "${env.SPECIAL_VALUE}"
    }
}
```

Then another stage expects:

```groovy
echo "${env.SPECIAL_VALUE}"
```

The stage-scoped environment variable was not intended to be globally available.

This is a scope problem.

Always ask:

```text
Where was this value defined?

Where should it be available?
```

---

# 130. Failure Scenario: Secret Printed

Suppose a future Pipeline uses credentials and someone adds:

```groovy
sh 'printenv'
```

for troubleshooting.

Now sensitive environment variables may be involved.

Even where Jenkins masking helps reduce accidental exposure, do not rely on masking as permission to print secrets. Jenkins explicitly warns that masking cannot prevent a malicious Pipeline from capturing credentials. ([Jenkins][2])

Troubleshooting must remain security-aware.

---

# 131. Failure Scenario: Unsafe Parameter Interpolation

Suppose:

```groovy
sh "deploy --version ${params.APP_VERSION}"
```

A user-controlled value has been interpolated into a command.

Jenkins warns about command injection through Groovy interpolation of user-controlled parameters. ([Jenkins][2])

Better design:

1. validate the value;
2. constrain its format;
3. expose it as an environment value;
4. use a fixed shell script with proper shell quoting.

For example:

```groovy
sh '''
    ./scripts/build.sh "$APP_VERSION"
'''
```

after strict version validation.

---

# 132. Troubleshooting Method

When configuration behaves incorrectly, trace:

```text
What value was expected?
        ↓
Where should it come from?
        ↓
Was parameter supplied?
        ↓
Did validation pass?
        ↓
Was configuration mapped?
        ↓
Was variable in correct scope?
        ↓
Did shell/process receive it?
        ↓
Did application interpret it correctly?
```

Do not immediately edit random Jenkins settings.
