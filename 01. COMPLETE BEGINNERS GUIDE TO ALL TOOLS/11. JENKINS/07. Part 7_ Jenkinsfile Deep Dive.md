# 1. The Mental Model for a Practical Jenkinsfile

A useful Jenkinsfile can be thought of as several layers:

```text
pipeline
│
├── agent
│
├── environment
│
├── options
│
├── parameters
│
├── triggers
│
├── tools
│
├── stages
│   │
│   ├── stage
│   │   ├── agent
│   │   ├── environment
│   │   ├── options
│   │   ├── when
│   │   ├── input
│   │   └── steps
│   │
│   ├── stage
│   └── stage
│
```

Not every Jenkinsfile needs every section.

That is important.

Do not think:

> A professional Jenkinsfile must contain every possible directive.

Instead:

```text

        ↓

        ↓
Add only what is needed
```

A simple project might need:

```text

```

A larger project might need:

```text
agent
environment
options
parameters
tools
stages

input
parallel
post
```

Your goal is not to make the Jenkinsfile complicated.

Your goal is to make the automation **clear, safe, predictable, and maintainable**.

# 2. A More Realistic Jenkinsfile

Before studying each section separately, look at this example:

```groovy
pipeline {
    agent any

    options {
        timestamps()
        disableConcurrentBuilds()
        timeout(time: 30, unit: 'MINUTES')
    }

    parameters {
        choice(
            name: 'DEPLOY_ENV',
            choices: ['development', 'staging', 'production'],
            description: 'Environment targeted by this build'
        )

        booleanParam(
            name: 'RUN_EXTENDED_TESTS',
            defaultValue: false,
            description: 'Run the extended test suite'
        )
    }

    environment {
        APP_NAME = 'veriqta-calculator'
    }

    stages {
        stage('Build') {
            steps {
                echo "Building ${env.APP_NAME}"
                sh 'python3 --version'
            }
        }

        stage('Test') {
            steps {
                sh '.venv/bin/python -m pytest -v'
            }
        }

        stage('Extended Tests') {
            when {
                expression {
                    return params.RUN_EXTENDED_TESTS
                }
            }

            steps {
                echo 'Running extended tests'
            }
        }

        stage('Deploy') {
            when {
                expression {
                    return params.DEPLOY_ENV == 'staging'
                }
            }

            input {
                message 'Deploy this build to staging?'
                ok 'Deploy'
            }

            steps {
                echo "Deploying to ${params.DEPLOY_ENV}"
            }
        }
    }

    post {
        success {
            echo 'Pipeline completed successfully.'
        }

        failure {
            echo 'Pipeline failed. Review the failed stage.'
        }

        cleanup {
            echo 'Running final cleanup.'
        }
    }
}
```

If that looks like a lot right now, that is fine.

By the end of this part, you should be able to read it section by section and understand why each part exists.

# 3. Declarative Pipeline Structure

A Declarative Pipeline begins with:

```groovy
pipeline {
}
```

Everything belonging to that Pipeline is placed inside this block.

At minimum, a useful Declarative Pipeline normally looks like:

```groovy
pipeline {
    agent any

    stages {
        stage('Build') {
            steps {
                echo 'Building'
            }
        }
    }
}
```

Think:

```text
pipeline
    ↓
Where does it execute?
    ↓
What stages exist?
    ↓
What work occurs inside each stage?
```

The official syntax requires a Declarative Pipeline to be enclosed in a `pipeline` block. ([Jenkins][1])

Here:


But:

Think:

while:

# 5. Agents

You already know:

```groovy
agent any
```

But now we need to understand agents more deeply.

An agent determines **where Pipeline work executes**.

Conceptually:

```text
Jenkins Pipeline
      ↓
Agent Selection
      ↓
Node
      ↓
Executor
      ↓
Workspace
      ↓
Commands
```

Jenkins supports top-level agents and stage-level agents. ([Jenkins][1])

---

# 6. Top-Level Agent

This:

```groovy
pipeline {
    agent any

    stages {
        ...
    }
}
```

means the Pipeline uses an allocated agent for its work.

The stages can use that execution context unless they define different behavior.

This is simple and appropriate for our current project.

---

# 7. `agent any`

```groovy
agent any
```

means:

> Execute on any suitable available Jenkins agent.

It does not mean:

```text
random computer on the network
```

It means an eligible node known to Jenkins.

---

# 8. Agent Labels

Suppose Jenkins has multiple agents:

```text
Jenkins
│
├── Agent 1
│   Label: linux
│
├── Agent 2
│   Label: windows
│
└── Agent 3
    Label: docker
```

You could specify:

```groovy
agent {
    label 'linux'
}
```

Now Jenkins needs an available agent matching:

```text
linux
```

This becomes useful when different workloads require different environments.

Jenkins currently supports label expressions as part of agent selection as well. ([Jenkins][1])

---

# 9. Why Labels Matter

Imagine:

```text
Build Linux Package
```

requires Linux.

But:

```text
Windows Compatibility Test
```

requires Windows.

A future Pipeline might use:

```groovy
pipeline {
    agent none

    stages {
        stage('Linux Test') {
            agent {
                label 'linux'
            }

            steps {
                sh './run-linux-tests.sh'
            }
        }

        stage('Windows Test') {
            agent {
                label 'windows'
            }

            steps {
                bat 'run-windows-tests.bat'
            }
        }
    }
}
```

Now different stages execute in appropriate environments.

---

# 10. `agent none`

You may also encounter:

```groovy
agent none
```

At the Pipeline level, this means:

```text
Do not allocate one global agent for the entire Pipeline.
```

Instead, individual stages can select their own agents.

Example:

```groovy
pipeline {
    agent none

    stages {
        stage('Build') {
            agent {
                label 'linux'
            }

            steps {
                echo 'Building on Linux'
            }
        }

        stage('Windows Test') {
            agent {
                label 'windows'
            }

            steps {
                bat 'echo Testing on Windows'
            }
        }
    }
}
```

This is especially useful for heterogeneous build environments.

Jenkins documents `agent none` as a way to avoid allocating a global executor and to require stages to provide their own execution context where needed. ([Jenkins][1])

---

# 11. Stage-Level Agents

An agent can be declared inside a stage:

```groovy
stage('Test') {
    agent {
        label 'test-agent'
    }

    steps {
        echo 'Running tests'
    }
}
```

Now only that stage requires:

```text
test-agent
```

This gives you fine-grained workload placement.

Imagine:

```text

```

If every stage waits for a different scarce agent, the Pipeline may spend time queued.

Agent design therefore affects:

```text

```

For now remember:

```text

```

# 13. Stages

A `stage` represents a meaningful phase.

Example:

```groovy
stages {
    stage('Build') {
        steps {
            echo 'Building'
        }
    }

    stage('Test') {
        steps {
            echo 'Testing'
        }
    }

    stage('Package') {
        steps {
            echo 'Packaging'
        }
    }
}
```

The Pipeline becomes:

```text
Build
  ↓
Test
  ↓
Package
```

A Declarative Pipeline requires at least one stage, and real Pipeline work is normally organized through these stage boundaries. ([Jenkins][1])

---

# 14. What Makes a Good Stage?

Good stages describe meaningful delivery phases:

```text
Checkout
Build
Unit Test
Integration Test
Security Scan
Package
Publish
Deploy
Verify
```

Poor stage design:

```text
Command 1
Command 2
Command 3
```

or:

```text
Stuff
More Stuff
Final Stuff
```

Stage names should help an engineer understand the workflow without opening every command.

# 15. Steps

Inside a stage:

```groovy
steps {
    echo 'Building application'
    sh 'python3 --version'
}
```

each operation is a Pipeline step.

Examples:

```groovy
echo 'Hello'
```

```groovy
sh 'pytest'
```

```groovy
archiveArtifacts artifacts: 'dist/*'
```

```groovy
error 'Validation failed'
```

Jenkins defines steps as the fundamental building blocks that tell Jenkins what to do. ([Jenkins][1])

# 16. Environment Variables

Real builds need configuration.

Suppose your application needs:

```text
Application name
Build mode
Target environment
API endpoint
Feature settings
```

Hardcoding every value repeatedly is poor practice.

Environment variables give processes named values.

For example:

```text
APP_NAME=veriqta-calculator
DEPLOY_ENV=staging
```

Inside a Unix shell:

```bash
echo "$APP_NAME"
```

could print:

```text
veriqta-calculator
```

---

# 17. Jenkins `environment` Directive

Declarative Pipeline supports:

```groovy
environment {
    APP_NAME = 'veriqta-calculator'
    BUILD_MODE = 'release'
}
```

Example:

```groovy
pipeline {
    agent any

    environment {
        APP_NAME = 'veriqta-calculator'
        BUILD_MODE = 'release'
    }

    stages {
        stage('Build') {
            steps {
                echo "Application: ${env.APP_NAME}"

                sh '''
                    echo "Build mode: $BUILD_MODE"
                '''
            }
        }
    }
}
```

Top-level environment variables apply across Pipeline steps, while stage-level environment variables can be scoped to a particular stage. ([Jenkins][1])

---

# 18. Pipeline-Level Environment Variables

This:

```groovy
pipeline {
    agent any

    environment {
        APP_NAME = 'veriqta-calculator'
    }

    stages {
        stage('Build') {
            steps {
                echo "Building ${env.APP_NAME}"
            }
        }

        stage('Test') {
            steps {
                echo "Testing ${env.APP_NAME}"
            }
        }
    }
}
```

makes:

```text
APP_NAME
```

available across those stages.

---

# 19. Stage-Level Environment Variables

You can narrow the scope:

```groovy
stage('Deploy') {
    environment {
        DEPLOY_ENV = 'staging'
    }

    steps {
        echo "Deploying to ${env.DEPLOY_ENV}"
    }
}
```

Now that variable belongs to the stage's execution scope rather than the whole Pipeline.

Think:

```text
Global configuration
        ↓
pipeline-level environment
```

versus:

```text
Stage-specific configuration
        ↓
stage-level environment
```

---

# 20. Do Not Put Secrets in Plain Environment Definitions

Do not write:

```groovy
environment {
    DATABASE_PASSWORD = 'MySecretPassword123'
}
```

inside a Git-controlled Jenkinsfile.

That stores the secret in source control.

Jenkins supports credentials integration with the `environment` directive, but credential management deserves its own treatment and will be covered comprehensively in Part 10. ([Jenkins][1])

For now:

```text
Non-sensitive configuration
→ normal environment variables
```

```text
Passwords/tokens/private keys
→ Jenkins Credentials
```

# 23. Inspect Environment Variables

On a Linux/Unix-like agent:

```groovy
stage('Inspect Environment') {
    steps {
        sh 'printenv'
    }
}
```

This prints environment variables visible to the shell.

Be careful.

In real environments, indiscriminately printing the environment can expose sensitive information.

Use it as a controlled learning/troubleshooting technique, not a default production logging practice.

# 24. `env` vs Shell Variables

This distinction is important.

Inside Pipeline/Groovy:

```groovy
echo "Build: ${env.BUILD_NUMBER}"
```

Inside a POSIX shell:

```groovy
sh '''
    echo "Build: $BUILD_NUMBER"
'''
```

Both may print the build number, but variable expansion occurs in different places.

Conceptually:

```text
${env.BUILD_NUMBER}
       ↓
Pipeline/Groovy context
```

versus:

```text
$BUILD_NUMBER
       ↓
Shell environment
```

Understanding that difference becomes extremely important when secrets and quoting are involved.

# 25. Options

The `options` directive changes Pipeline behavior.

Example:

```groovy
options {
    timestamps()
    disableConcurrentBuilds()
    timeout(time: 30, unit: 'MINUTES')
}
```

These do not perform application build work.

They control how Jenkins manages the Pipeline.

Jenkins currently supports Pipeline options such as timeouts, build retention, timestamps, concurrent-build control, retries, and others. Some options may come from plugins. ([Jenkins][1])

---

# 26. `timestamps()`

Example:

```groovy
options {
    timestamps()
}
```

This adds timestamps to Pipeline console output.

That can help answer:

```text
When did this operation start?

How long was Jenkins waiting?

When did the failure occur?
```

For troubleshooting production CI/CD systems, time information can be very useful.

---

# 27. `disableConcurrentBuilds()`

Imagine:

```text
Build #41
```

is deploying to staging.

Before it finishes:

```text
Build #42
```

starts deploying to the same staging environment.

Now both may modify the same target.

That can create race conditions.

You can use:

```groovy
options {
    disableConcurrentBuilds()
}
```

to prevent simultaneous executions of the same Pipeline.

Jenkins can queue the later run, and it also supports an `abortPrevious` form when that behavior is desired. ([Jenkins][1])

---

# 28. Build Retention

Jenkins builds consume storage through:

```text
Console logs
Artifacts
Metadata
Workspaces
Test reports
```

You may encounter:

```groovy
options {
    buildDiscarder(
        logRotator(numToKeepStr: '20')
    )
}
```

This tells Jenkins to retain a limited number of builds according to the configured policy.

Do not blindly retain every artifact forever.

But also do not delete important evidence without considering audit, troubleshooting, release, or compliance requirements.

---

# 29. Pipeline Timeout

A build should not necessarily run forever.

Imagine:

```text
Deployment command
      ↓
Network problem
      ↓
Command hangs
      ↓
Executor remains occupied
      ↓
Pipeline never finishes
```

Timeouts protect Jenkins from indefinitely stuck operations.

---

# 30. Global Timeout

Example:

```groovy
options {
    timeout(time: 30, unit: 'MINUTES')
}
```

This places a timeout around the Pipeline according to Jenkins' Declarative Pipeline semantics. ([Jenkins][1])

Example:

```groovy
pipeline {
    agent any

    options {
        timeout(time: 30, unit: 'MINUTES')
    }

    stages {
        stage('Build') {
            steps {
                echo 'Building'
            }
        }
    }
}
```

If execution exceeds the configured limit, Jenkins aborts it.

---

# 31. Stage-Level Timeout

You can protect only one stage:

```groovy
stage('Integration Test') {
    options {
        timeout(time: 10, unit: 'MINUTES')
    }

    steps {
        sh './run-integration-tests.sh'
    }
}
```

This is useful when:

```text
Pipeline may legitimately take 40 minutes
```

but:

```text
Integration tests should never exceed 10 minutes
```

---

# 32. Timeout and Agent Allocation

There is a subtle difference worth knowing.

For a top-level agent, Jenkins allocates the agent before the top-level timeout starts.

For a stage-level agent, stage options such as timeout are applied before allocating that stage's agent, so agent provisioning/queue time can count toward that stage timeout. ([Jenkins][1])

You do not need to memorize every nuance yet.

Remember:

```text
Where timeout is declared
can affect
what time is included.
```

# 33. Parameters

A parameter allows someone triggering the Pipeline to supply a value.

Instead of creating separate jobs:

```text
deploy-development

deploy-production
```

you might have:

```text
application-pipeline
        ↓
DEPLOY_ENV
        ↓
development / staging / production
```

Parameters make pipelines configurable.

# 34. Parameterized Pipeline

Example:

```groovy

    choice(
        name: 'DEPLOY_ENV',
        choices: ['development', 'staging', 'production'],

```

After Jenkins processes the parameter definition, the job can expose:

```text
Build with Parameters
```

instead of only:

```text

```

Declarative parameters are available through the `params` object and are also exported for build use. ([Jenkins][2])

# 37. Choice Parameters

# 38. Practical Lab 1: Parameterized Pipeline

Create:

```groovy
pipeline {
    agent any

    parameters {
        choice(
            name: 'DEPLOY_ENV',
            choices: ['development', 'staging', 'production'],
            description: 'Select the target environment'

            name: 'RUN_EXTENDED_TESTS',

            description: 'Run extended tests'

        stage('Configuration') {
            steps {
                echo "Environment: ${params.DEPLOY_ENV}"
                echo "Extended tests: ${params.RUN_EXTENDED_TESTS}"
            }
        }
    }
}
```

Commit and push.

Run the Pipeline.

After Jenkins recognizes the parameter configuration, you should be able to select:

```text
Build with Parameters
```

Choose different values and inspect the console output.

# 39. Parameter Safety

Parameters are user-controlled input.

Do not assume:

```text
parameter
=
safe value
```

For example, avoid blindly constructing shell commands from arbitrary strings.

Poor design:

```groovy
sh "deploy ${params.USER_COMMAND}"
```

especially if `USER_COMMAND` can contain arbitrary text.

Use controlled choices where practical, validate values, and never treat untrusted parameter input as inherently safe shell syntax.

# 41. Triggers

So far, you manually started Pipelines.

But CI/CD systems usually respond to events.

Examples:

```text
Developer pushes code
Scheduled time arrives
Repository changes
Another event occurs
```

The Declarative `triggers` directive can define certain automatic triggers in the Jenkinsfile. Jenkins supports triggers such as cron scheduling and SCM polling; webhook-driven integrations are also common but are often configured through SCM/plugin integration rather than simply a generic Declarative `triggers` entry. ([Jenkins][1])

---

# 42. Scheduled Trigger

Example:

```groovy
triggers {
    cron('H 2 * * *')
}
```

This represents a Jenkins cron schedule.

Jenkins cron syntax resembles traditional cron but includes Jenkins-specific features such as:

```text
H
```

which hashes scheduling to distribute load. ([Jenkins][1])

Do not automatically replace `H` with a fixed minute unless you genuinely require an exact minute.

---

# 43. Poll SCM

You may encounter:

```groovy
triggers {
    pollSCM('H/5 * * * *')
}
```

Conceptually:

```text
Jenkins
   ↓
Periodically checks SCM
   ↓
Did source change?
   ↓
YES → Build
```

This differs from a webhook:

```text
GitHub
   ↓
Event occurs
   ↓
Notifies Jenkins
   ↓
Build
```

Part 8 is dedicated to triggers and GitHub webhooks, so we will not over-expand that topic here.

# 44. Tools

Applications need build tools.

Examples:

```text
JDK
Maven
Gradle
```

Jenkins Declarative Pipeline supports a `tools` directive for configured tools.

Example:

```groovy
tools {
    jdk 'jdk-21'
}
```

or:

```groovy
tools {
    maven 'maven-3'
}
```

The important requirement is that the named tool must first exist in Jenkins tool configuration. Jenkins documents `jdk`, `maven`, and `gradle` as supported Declarative tool types, with names matching configured Jenkins tools. ([Jenkins][1])

---

# 45. Configure a Tool First

Conceptually:

```text
Manage Jenkins
    ↓
Tools
    ↓
Configure tool
    ↓
Give tool a Jenkins name
```

For example:

```text
Name: jdk-21
```

Then Jenkinsfile:

```groovy
tools {
    jdk 'jdk-21'
}
```

The string:

```text
jdk-21
```

must correspond to the Jenkins tool configuration.

Do not invent a name and assume Jenkins understands it.

---

# 46. Verify Tools

If you configure:

```groovy
tools {
    jdk 'jdk-21'
}
```

verify it:

```groovy
stage('Verify Tools') {
    steps {
        sh 'java -version'
    }
}
```

Again:

```text
configuration
≠
verification
```

Always confirm the actual runtime behavior.

# 47. `when`: Conditional Stage Execution

Not every stage should run every time.

For example:

```text
Build
```

should run.

```text
Test
```

should run.

But:

```text
Deploy Production
```

should probably not run during every development build.

The `when` directive lets Jenkins decide whether a stage should execute. ([Jenkins][1])

---

# 48. Simple `when` Expression

Example:

```groovy
stage('Deploy') {
    when {
        expression {
            return params.DEPLOY_ENV == 'staging'
        }
    }

    steps {
        echo 'Deploying to staging'
    }
}
```

Read it:

```text
Enter Deploy stage
      ↓
Evaluate condition
      ↓
Is DEPLOY_ENV staging?
      ↓
YES → execute
NO  → skip
```

---

# 49. Practical Lab 2: Conditional Deployment

Use:

```groovy
pipeline {
    agent any

    parameters {
        choice(
            name: 'DEPLOY_ENV',
            choices: ['development', 'staging'],
            description: 'Select deployment environment'
        )
    }

    stages {
        stage('Build') {
            steps {
                echo 'Building application'
            }
        }

        stage('Test') {
            steps {
                echo 'Testing application'
            }
        }

        stage('Deploy Staging') {
            when {
                expression {
                    return params.DEPLOY_ENV == 'staging'
                }
            }

            steps {
                echo 'Deploying to staging'
            }
        }
    }
}
```

Run once with:

```text
development
```

Expected:

```text
Build             SUCCESS
Test              SUCCESS
Deploy Staging    SKIPPED
```

Run again with:

```text
staging
```

Expected:

```text
Build             SUCCESS
Test              SUCCESS
Deploy Staging    SUCCESS
```

You have now created conditional Pipeline behavior.

# 54. Input Does Not Replace Authorization Design

# 55. Protect Human Input With Timeout

Imagine:

```text
Pipeline
   ↓
Waiting for approval
   ↓
Nobody responds
   ↓
Pipeline waits indefinitely
```

A better design can combine input with timeout.

For example:

```groovy
stage('Approval') {
    steps {
        timeout(time: 10, unit: 'MINUTES') {

        }
    }
}
```

Now approval cannot wait forever.

# 59. Retry

Some operations fail temporarily.

Examples:

```text
Transient network interruption
Temporary registry error
Remote service briefly unavailable
Cloud API transient failure
```

Immediately failing the entire Pipeline may sometimes be unnecessary.

Jenkins provides retry behavior.

---

# 60. Basic Retry

Example:

```groovy
retry(3) {
    sh './temporary-operation.sh'
}
```

Conceptually:

```text
Attempt operation
      ↓
Failure
      ↓
Try again
      ↓
Failure
      ↓
Try again
```

If the operation continues to fail after the allowed attempts, the failure propagates.

---

# 61. Retry Is Not a Way to Hide Broken Code

Do not do this:

```groovy
retry(20) {
    sh 'pytest'
}
```

because your application tests consistently fail.

Retry should normally address plausible transient failure.

Think:

```text
Network request failed once
→ retry may make sense
```

versus:

```text
Unit test says 2 + 2 = 5
→ retry does not fix the defect
```

Repeatedly executing deterministic failures wastes resources and hides the need for root-cause repair.

---

# 62. Stage-Level Retry

Declarative stage options also support retry behavior:

```groovy
stage('External Check') {
    options {
        retry(3)
    }

    steps {
        sh './check-external-service.sh'
    }
}
```

Jenkins documents `retry` as both a Pipeline option/stage option pattern and as a basic Pipeline step for retrying a block of work. ([Jenkins][1])

# 63. Practical Lab 4: Retry Failed Operations

Create a small script:

```text
scripts/transient-check.sh
```

For a deterministic learning demonstration, use:

```bash
#!/bin/sh

set -eu

STATE_FILE=".retry-state"

if [ ! -f "$STATE_FILE" ]; then
    echo "First attempt: simulated temporary failure"
    touch "$STATE_FILE"
    exit 1
fi

echo "Retry attempt: operation succeeded"
rm -f "$STATE_FILE"
```

Make it executable:

```bash
chmod +x scripts/transient-check.sh
```

Commit it.

Then:

```groovy
stage('Retry Demo') {
    steps {
        retry(3) {
            sh './scripts/transient-check.sh'
        }
    }
}
```

---

# 64. What Should Happen?

First attempt:

```text
.retry-state does not exist
       ↓
script creates it
       ↓
exit 1
       ↓
Jenkins sees failure
```

Retry:

```text
.retry-state exists
       ↓
script reports success
       ↓
removes state file
       ↓
exit 0
```

Expected Pipeline result:

```text
SUCCESS
```

even though the first attempt failed.

Now you have seen genuine retry behavior rather than merely reading about it.

---

# 65. Retry Requires Idempotency Awareness

This matters in real systems.

Imagine:

```text
Create customer invoice
```

succeeds remotely, but the network response is lost.

Jenkins thinks the operation failed.

Then retry creates another invoice.

Now you have duplicates.

Therefore:

```text
Retry
```

is safe only when you understand whether the operation can be repeated safely.

This introduces an important production concept:

```text
idempotency
```

An idempotent operation can be repeated without producing unintended additional effects.

Do not blindly retry deployment, database mutation, payment, or destructive operations.

# 66. `post`: Actions After Execution

You learned basic `post` handling in Part 6.

Now we will understand it more fully.

A Pipeline-level `post` block can perform actions depending on the final result.

Example:

```groovy
post {
    always {
        echo 'Pipeline finished'
    }

    success {
        echo 'Pipeline succeeded'
    }

    failure {
        echo 'Pipeline failed'
    }
}
```

Jenkins supports conditions including `always`, `changed`, `fixed`, `regression`, `aborted`, `failure`, `success`, `unstable`, `unsuccessful`, and `cleanup`. ([Jenkins][1])

---

# 67. Pipeline-Level vs Stage-Level `post`

Pipeline-level:

```groovy
pipeline {
    ...

    post {
        failure {
            echo 'Entire Pipeline failed'
        }
    }
}
```

Stage-level:

```groovy
stage('Test') {
    steps {
        sh 'pytest'
    }

    post {
        failure {
            echo 'Test stage failed'
        }
    }
}
```

Think:

```text
Pipeline post
=
react to overall Pipeline
```

```text
Stage post
=
react to specific stage
```

---

# 68. `always`

```groovy
post {
    always {
        echo 'This runs regardless of final result'
    }
}
```

Useful for work that should happen regardless of success or failure.

Examples may include:

```text
Publishing test reports
Collecting diagnostics
Certain cleanup tasks
```

---

# 69. `success`

```groovy
success {
    echo 'Build succeeded'
}
```

Only executes for success.

Possible future uses:

```text
Success notification
Artifact publication
Release workflow
```

depending on Pipeline design.

---

# 70. `failure`

```groovy
failure {
    echo 'Build failed'
}
```

Useful for:

```text

Diagnostics
Incident integration
```

---

# 71. `unstable`

A Jenkins build can be:

```text
UNSTABLE
```

rather than simply:

```text
SUCCESS
```

or:

```text
FAILURE
```

For example, certain test/reporting operations can mark a build unstable.

You can react with:

```groovy
unstable {
    echo 'Build is unstable'
}
```

Do not assume every non-success result is exactly the same.

---

# 72. `cleanup`

Current Declarative Pipeline supports:

```groovy
cleanup {
}
```

inside `post`.

It runs after the other post conditions have been evaluated, regardless of Pipeline/stage status. ([Jenkins][1])

Example:

```groovy
post {
    cleanup {
        echo 'Final cleanup'
    }
}
```

This gives you a clear place for final cleanup logic.

---

# 73. Workspace Cleanup

Our Python Pipeline creates:

```text
.venv/
build/
dist/
.retry-state
```

We may want to remove generated temporary state.

For a controlled example:

```groovy
post {
    cleanup {
        sh '''
            rm -rf .venv build
            rm -f .retry-state
        '''
    }
}
```

Notice that we did not delete:

```text
dist/
```

before considering whether we still need it.

Cleanup should be intentional.

---

# 74. Be Careful With `rm -rf`

This command is powerful:

```bash
rm -rf
```

Never build destructive paths carelessly.

Bad:

```bash
rm -rf "$SOME_VARIABLE"
```

without knowing whether the variable is empty or points somewhere unexpected.

Prefer narrowly scoped cleanup paths you understand.

In CI/CD:

```text
cleanup
```

should not become:

```text
hope this path is correct
```

# 87. Quoting: Why It Matters

Quoting is one of the most common sources of confusion in Jenkinsfiles.

You may have:

```groovy
echo "${env.BUILD_NUMBER}"
```

and:

```groovy
sh 'echo "$BUILD_NUMBER"'
```

and:

```groovy
sh '''
    echo "$BUILD_NUMBER"
'''
```

They look similar.

But they are not processed identically.

You need to know **who expands the variable**.

---

# 88. Groovy Double-Quoted Strings

Example:

```groovy
echo "Build ${env.BUILD_NUMBER}"
```

Groovy/Pipeline interpolation processes:

```text
${env.BUILD_NUMBER}
```

before the final value is passed to the `echo` step.

Conceptually:

```text
Groovy
   ↓
Resolve env.BUILD_NUMBER
   ↓
Construct final string
   ↓
echo
```

---

# 89. Groovy Single-Quoted Strings

Example:

```groovy
sh 'echo "$BUILD_NUMBER"'
```

Groovy does not interpolate `$BUILD_NUMBER` in the same way.

Instead, the string is passed to the shell.

Then the shell expands:

```text
$BUILD_NUMBER
```

The Jenkins basic-steps documentation explicitly illustrates this distinction with `withEnv`, noting that single quotes can allow the Bourne shell rather than Jenkins/Groovy to perform the expansion. ([Jenkins][3])

---

# 90. Why This Matters for Secrets

Suppose you eventually use a credential exposed as an environment variable.

You generally want to avoid unnecessarily interpolating secret values into Groovy strings.

The distinction between:

```groovy
sh "command $SECRET"
```

and:

```groovy
sh 'command "$SECRET"'
```

can matter for security and logging behavior.

We will treat credential handling properly in Part 10.

For now:

```text
Know who expands the variable.
```

---

# 91. Multiline Strings

For multiple shell commands:

```groovy
sh '''

    echo "Starting build"

    python3 --version

    python3 -m venv .venv
```

```text
        ↓
```


# 95. Multiline Command Failure

Consider:

```groovy
sh '''
    python3 --version
    command-that-does-not-exist
    echo "Finished"
'''
```

You should understand shell failure behavior rather than assuming every multiline script stops exactly where you expect.

For our learning scripts, we often use:

```bash
set -eu
```

to make failure handling more explicit.

---

# 96. What Does `set -e` Do?

In a POSIX-style shell script:

```bash
set -e
```

instructs the shell to exit for many unhandled command failures.

Example:

```bash
set -e

python3 --version
command-that-does-not-exist
echo "This should not normally continue"
```

But `set -e` has shell-language nuances, especially around conditional commands, pipelines, and other constructs.

Do not treat it as magical perfect error handling.

---

# 97. What Does `set -u` Do?

```bash
set -u
```

treats references to unset variables as errors in typical POSIX shell usage.

Example:

```bash
set -u

echo "$VARIABLE_THAT_DOES_NOT_EXIST"
```

This can expose configuration mistakes earlier.

Together:

```bash
set -eu
```

is useful for many simple CI shell blocks.

---

# 98. Bash vs `/bin/sh`

Another important production detail:

```groovy
sh '''
    ...
'''
```

should not make you assume every Bash-specific feature is safe.

If your script depends on Bash syntax, be explicit about the execution environment or use a checked-in script with an appropriate shebang and executable permissions.

For portable simple examples, keep shell syntax conservative.

# 99. Prefer Checked-In Scripts When Shell Logic Becomes Large

This is readable:

```groovy
sh '''
    python3 -m venv .venv
    .venv/bin/python -m pip install -r requirements-dev.txt
    .venv/bin/python -m pytest
'''
```

This is not a good long-term Jenkinsfile pattern:

```groovy
sh '''
    hundreds
    and
    hundreds
    of
    lines
    of
    shell
    logic
'''
```

If build logic becomes substantial, consider:

```text
scripts/
├── build.sh
├── test.sh
└── package.sh
```

Then Jenkinsfile:

```groovy
stage('Build') {
    steps {
        sh './scripts/build.sh'
    }
}
```

The Jenkinsfile should orchestrate.

It should not become an unreadable replacement for every build script.

```text
        ↓

        ↓
Checkout
```

# 101. Shell Exit Codes

Unix-like commands return exit statuses.

Conventionally:

```text
0
=
success
```

and:

```text
non-zero
=
some kind of failure
```

Example:

```bash
exit 0
```

signals success.

```bash
exit 1
```

signals failure.

A Jenkins `sh` step normally fails when the shell command returns non-zero unless you intentionally request different handling.

---

# 102. Capturing an Exit Status

Sometimes you intentionally need to inspect a command result.

Jenkins' `sh` step can support returning a status rather than immediately failing, depending on the step configuration.

Example pattern:

```groovy
script {
    def status = sh(
        script: 'test -f important-file.txt',
        returnStatus: true
    )

    echo "Exit status: ${status}"
}
```

Then:

```groovy
if (status != 0) {
    error 'Required file is missing'
}
```

This is useful when the Pipeline needs custom failure logic.

Do not use it simply to ignore failures.

---

# 103. `error`

You can deliberately fail the Pipeline with a meaningful message:

```groovy
error 'Required artifact was not generated'
```

Example:

```groovy
script {
    def status = sh(
        script: 'test -d dist',
        returnStatus: true
    )

    if (status != 0) {
        error 'Expected dist directory was not generated'
    }
}
```

This creates a more meaningful diagnostic than silently continuing.

---

# 104. Do Not Hide Failures

Dangerous:

```groovy
sh 'pytest || true'
```

If pytest fails:

```text
pytest returns failure
      ↓
|| true converts shell result
      ↓
Jenkins sees success
```

Now broken code may continue toward:

```text
Package
Publish
Deploy
```

That undermines CI.

Failures should be:

```text
handled intentionally
```

not:

```text
suppressed casually
```

---

# 105. Parallel Stages

Suppose you have:

```text
Unit Tests
Integration Tests
Linting
```

and they do not depend on each other.

Sequential execution:

```text
Unit Tests
    ↓
Integration Tests
    ↓
Lint
```

might take:

```text
5 + 8 + 3 = 16 minutes
```

If they can safely execute independently, parallel execution may reduce elapsed time.

Conceptually:

```text
              ┌→ Unit Tests
Build ────────┼→ Integration Tests
              └→ Lint
                     ↓
                  Package
```

Declarative Pipeline supports a `parallel` section containing nested stages. ([Jenkins][1])

---

# 106. Basic Declarative Parallel Structure

Example:

```groovy
stage('Tests') {
    parallel {
        stage('Unit Tests') {
            steps {
                echo 'Running unit tests'
            }
        }

        stage('Integration Tests') {
            steps {
                echo 'Running integration tests'
            }
        }
    }
}
```

Now:

```text
Unit Tests
```

and:

```text
Integration Tests
```

can execute concurrently, subject to available Jenkins execution resources.

---

# 107. Parallel Does Not Guarantee Unlimited Simultaneous Execution

If Jenkins lacks enough executors or agents, parallel branches may wait for resources.

So:

```text
parallel syntax
```

does not magically create infinite compute capacity.

Actual concurrency depends on:

```text
Agents
Executors
Resource availability
Stage requirements
```

This becomes important when scaling Jenkins.

---

# 108. Parallel Work Must Be Independent

Do not parallelize:

```text
Build application
```

and:

```text
Test application
```

if testing requires the completed build.

That dependency is:

```text
Build
  ↓
Test
```

not:

```text
Build ─┐
       ├ parallel
Test ──┘
```

Parallelism is appropriate when tasks can safely execute independently.

---

# 109. Workspace Conflicts

Parallel stages can also create conflicts if both modify the same files.

For example:

```text
Unit Test
   ↓
deletes dist/
```

while:

```text
Integration Test
   ↓
reads dist/
```

Running these concurrently can produce unpredictable behavior.

Before parallelizing, ask:

```text
Do these operations share mutable state?
```

# 112. `failFast`

Declarative parallel stages can be configured so that a failure in one branch causes the other parallel work to be aborted.

You may encounter:

```groovy
stage('Tests') {

    parallel {
        stage('Unit Tests') {
            steps {
```

```groovy

}
```

# 124. Parameters vs Environment Variables

These concepts are related but different.

| Concept                | Purpose                              |
| ---------------------- | ------------------------------------ |
| Parameter              | Input supplied to the Pipeline/build |
| Environment variable   | Value exposed to processes/runtime   |
| Jenkins build variable | Jenkins-provided build metadata      |
| Groovy variable        | Value used by Pipeline/Groovy logic  |

Example:

```groovy
parameters {
    choice(
        name: 'DEPLOY_ENV',
        choices: ['development', 'staging']
    )
}

environment {
    APP_NAME = 'veriqta-calculator'
}
```

Then:

```groovy
echo "${params.DEPLOY_ENV}"
echo "${env.APP_NAME}"
echo "${env.BUILD_NUMBER}"
```

---

# 125. Parameter Values as Environment Variables

Jenkins also makes parameter information available to the build environment, so shell commands can often access parameter names directly. ([Jenkins][1])

For example:

```groovy
parameters {
    string(
        name: 'RELEASE_VERSION',
        defaultValue: '1.0.0'
    )
}
```

Then on a POSIX shell:

```groovy
sh '''
    echo "Release version: $RELEASE_VERSION"
'''
```

But when writing Pipeline logic, using:

```groovy
params.RELEASE_VERSION
```

makes it clear that the value came from Pipeline parameters.

# 126. A Practical Jenkinsfile for This Part

Now combine the concepts.

For our learning application:

```groovy
pipeline {
    agent any

    options {
        timestamps()
        disableConcurrentBuilds()
        timeout(time: 30, unit: 'MINUTES')
    }

    parameters {
        choice(
            name: 'DEPLOY_ENV',
            choices: ['development', 'staging'],
            description: 'Select the deployment target'
        )

        booleanParam(
            name: 'RUN_EXTENDED_TESTS',
            defaultValue: false,
            description: 'Run the extended test suite'
        )
    }

    environment {
        APP_NAME = 'veriqta-calculator'
    }

    stages {
        stage('Build') {
            steps {
                echo "Building ${env.APP_NAME}"
                echo "Jenkins build: ${env.BUILD_NUMBER}"

                sh '''
                    set -eu

                    if [ ! -f pyproject.toml ]; then
                        echo "ERROR: pyproject.toml is missing."
                        exit 1
                    fi

                    if [ ! -f requirements-dev.txt ]; then
                        echo "ERROR: requirements-dev.txt is missing."
                        exit 1
                    fi

                    rm -rf .venv build dist

                    python3 --version
                    python3 -m venv .venv

                    .venv/bin/python -m pip install --upgrade pip
                    .venv/bin/python -m pip install -r requirements-dev.txt
                '''
            }
        }

        stage('Tests') {
            parallel {
                stage('Unit Tests') {
                    steps {
                        sh '''
                            set -eu
                            .venv/bin/python -m pytest -v
                        '''
                    }
                }

                stage('Environment Check') {
                    steps {
                        sh '''
                            set -eu

                            echo "Application: $APP_NAME"
                            echo "Build: $BUILD_NUMBER"
                            python3 --version
                        '''
                    }
                }
            }
        }

        stage('Extended Tests') {
            when {
                expression {
                    return params.RUN_EXTENDED_TESTS
                }
            }

            options {
                timeout(time: 5, unit: 'MINUTES')
            }

            steps {
                echo 'Running extended test suite'

                retry(2) {
                    sh '''
                        set -eu
                        .venv/bin/python -m pytest -v
                    '''
                }
            }
        }

        stage('Package') {
            steps {
                sh '''
                    set -eu

                    .venv/bin/python -m build

                    WHEEL_FILE="$(find dist -maxdepth 1 -type f -name '*.whl' -print -quit)"

                    if [ -z "$WHEEL_FILE" ]; then
                        echo "ERROR: Wheel artifact was not generated."
                        exit 1
                    fi

                    echo "Generated artifact:"
                    echo "$WHEEL_FILE"

                    ls -lh dist/
                '''

                archiveArtifacts artifacts: 'dist/*', fingerprint: true
            }
        }

        stage('Deploy Staging') {
            when {
                expression {
                    return params.DEPLOY_ENV == 'staging'
                }
            }

            input {
                message 'Deploy this build to staging?'
                ok 'Deploy'
            }

            steps {
                echo "Deployment approved for ${params.DEPLOY_ENV}"

                // Real deployment is intentionally deferred to later parts.
                echo 'Simulating staging deployment.'
            }
        }
    }

    post {
        success {
            echo "Build ${env.BUILD_NUMBER} completed successfully."
        }

        failure {
            echo "Build ${env.BUILD_NUMBER} failed. Review the failed stage and console output."
        }

        aborted {
            echo "Build ${env.BUILD_NUMBER} was aborted."
        }

        cleanup {
            sh '''
                rm -rf .venv build
                rm -f .retry-state
            '''

            echo 'Temporary build files cleaned.'
        }
    }
}
```

# 128. Important Retry Correction

Although the example above demonstrates syntax, think carefully before retrying:

```text
pytest
```

in a real Pipeline.

Deterministic unit tests should not normally need retries.

If a test only succeeds after repeated execution, you may have:

```text
Flaky test
Race condition
Timing dependency
External dependency problem
Poor test isolation
```

Do not normalize flaky tests by hiding them behind retries.

For real CI, retries are better reserved for operations known to have legitimate transient failure modes.
