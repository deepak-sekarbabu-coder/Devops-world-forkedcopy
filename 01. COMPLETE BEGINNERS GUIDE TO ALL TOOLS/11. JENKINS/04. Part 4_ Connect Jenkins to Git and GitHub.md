# Part 4: Connect Jenkins to Git and GitHub

## Learning Objective

In Part 3, you made Jenkins perform real automation.

You created a Freestyle job, executed shell commands, created files in the workspace, inspected environment variables, deliberately failed a build, read the console output, diagnosed the problem, and repaired it.

Your workflow looked like this:

```text
Jenkins
   ↓
Job
   ↓
Command
   ↓
Build
   ↓
Console Output
```

That was useful for learning Jenkins, but real software teams do not normally type their application source code directly into Jenkins.

Developers work with source control.

For this part, we are adding Git and GitHub to the system:

```text
Developer
    ↓
Git
    ↓
GitHub
    ↓
Jenkins
    ↓
Workspace
```

By the end of Part 4, you will be able to connect Jenkins to both public and private GitHub repositories, retrieve source code automatically, choose which branch Jenkins builds, inspect the exact commit being built, use HTTPS or SSH appropriately, configure credentials securely, and troubleshoot repository authentication and permission failures.

We will build this progressively:

```text
Developer
    ↓
Local Git Repository
    ↓
GitHub Repository
    ↓
Jenkins Git Plugin
    ↓
Git
    ↓
Checkout
    ↓
Jenkins Workspace
    ↓
Build Command
```

This is where Jenkins begins to look like a real Continuous Integration system.

---

# 1. Why CI Starts With Source Control

Imagine three developers working on an application.

```text
Developer A
Developer B
Developer C
```

If each developer simply keeps files on their laptop:

```text
Developer A
└── app.py

Developer B
└── app.py

Developer C
└── app.py
```

several questions immediately appear.

Which copy is current?

Who changed what?

What version should Jenkins build?

Which code was deployed?

How do we recover yesterday's version?

How do developers combine their work?

How does Jenkins know when code changes?

This is why modern software development depends heavily on version control.

Instead of Jenkins receiving random files from individual laptops, the workflow becomes:

```text
Developers
    ↓
Git
    ↓
Shared Repository
    ↓
Jenkins
```

The repository becomes the controlled source Jenkins retrieves.

---

# 2. Source Control and Continuous Integration

Remember what Continuous Integration means.

Developers integrate their changes frequently into a shared codebase, and automated systems validate those changes.

A simplified CI flow looks like this:

```text
Developer
    ↓
Change Code
    ↓
Git Commit
    ↓
Push
    ↓
Shared Repository
    ↓
Jenkins
    ↓
Checkout
    ↓
Build
    ↓
Test
    ↓
Result
```

Without source control, Jenkins has no reliable shared source from which to retrieve the application.

That is why source control usually sits near the beginning of CI.

---

# 3. What Is Git?

Git is a distributed version control system.

In plain English, Git helps track changes to files over time.

Suppose your project contains:

```text
sample-app/
├── README.md
├── app.sh
└── version.txt
```

You modify:

```text
app.sh
```

Git can record that change as a commit.

Later, another change can become another commit.

Conceptually:

```text
Commit A
   ↓
Commit B
   ↓
Commit C
   ↓
Commit D
```

Each commit represents a recorded state/change in the project's history.

Git allows you to answer questions such as:

* What changed?
* Who committed it?
* When was it committed?
* What commit came before it?
* Which branch contains it?
* Can we return to an earlier state?

Jenkins can use this history to determine exactly which version of source code it is building.

---

# 4. Git Is Not GitHub

This distinction matters.

Git is the version control system.

GitHub is a service that hosts Git repositories and provides collaboration features around them.

Think:

```text
Git
=
version control technology
```

while:

```text
GitHub
=
repository hosting and collaboration platform
```

You can use Git without GitHub.

Git repositories can be hosted by many systems, including GitHub, GitLab, Bitbucket, self-hosted Git servers, and other platforms.

For this series, we will use GitHub.

# 5. Local Repository vs Remote Repository

Suppose you create a Git repository on your computer.

That is a local repository.

```text
Your Computer
└── sample-app/
      └── .git/
```

You can then connect it to a remote repository hosted on GitHub:

```text
Local Git Repository
        ↓
      push
        ↓
GitHub Repository
```

Git commonly gives that remote the short name:

```text
origin
```

Therefore:

```text
origin
```

usually refers to the primary remote repository from which the local repository was cloned or to which it was configured to connect.

# 6. Git Refresher for Jenkins

You do not need to master all of Git before using Jenkins.

But you need to understand the commands behind what Jenkins is doing.

Important Git operations include:

```bash
git clone
```

Retrieve a repository into a new local directory.

```bash
git status
```

Show the current working-tree and staging state.

```bash
git add
```

Stage changes for a commit.

```bash
git commit
```

Record staged changes into Git history.

```bash
git push
```

Send local commits to a remote repository.

```bash
git fetch
```

Retrieve remote Git information and objects without necessarily changing the checked-out working files.

```bash
git checkout
```

Switch to or restore particular branches/files in traditional Git workflows. Jenkins' Git integration also performs checkout operations when preparing the workspace.

```bash
git log
```

Inspect commit history.

```bash
git branch
```

Inspect or manage branches.

These operations will become much more meaningful once Jenkins begins performing some of them automatically.

# 7. What Is a Commit?

A commit is a recorded change in Git history.

A commit has information such as:

* Commit identifier.
* Author.
* Date.
* Commit message.
* Parent commit.
* Recorded file changes.

A commit identifier is a hash.

You might see something resembling:

```text
3d8b7c7f...
```

A shortened version might appear as:

```text
3d8b7c7
```

Git uses these identifiers to distinguish commits.

Conceptually:

```text
main

A → B → C → D
            ↑
       exact commit
```

This becomes extremely useful in CI.

Instead of saying:

> Jenkins built the code sometime Tuesday.

we want to know:

> Jenkins built commit `C`.

That gives us traceability.

---

# 8. What Is a Branch?

A branch represents a line of development.

You might have:

```text
main
```

and:

```text
develop
```

and:

```text
feature/login
```

Conceptually:

```text
A ── B ── C ── D
         \
          E ── F
```

One branch may continue through `D`.

Another may contain `E` and `F`.

Jenkins needs to know which branch it should build.

That is why branch selection matters.

---

# 9. GitHub Repository URLs

Every GitHub repository can be addressed through repository URLs.

Two important forms for us are:

```text
HTTPS
```

and:

```text
SSH
```

An HTTPS GitHub repository URL typically looks like:

```text
https://github.com/OWNER/REPOSITORY.git
```

An SSH GitHub repository URL commonly looks like:

```text
git@github.com:OWNER/REPOSITORY.git
```

For example:

```text
https://github.com/veriqta/jenkins-sample-app.git
```

versus:

```text
git@github.com:veriqta/jenkins-sample-app.git
```

These can refer to the same repository.

The difference is how Git connects and authenticates.

---

# 10. HTTPS vs SSH

This is one of the first decisions you encounter when connecting Jenkins to GitHub.

## HTTPS

Example:

```text
https://github.com/OWNER/REPOSITORY.git
```

For a public repository, Jenkins can often retrieve the repository without authentication.

For a private GitHub repository, HTTPS authentication typically uses a GitHub personal access token rather than a GitHub account password.

## SSH

Example:

```text
git@github.com:OWNER/REPOSITORY.git
```

SSH uses public/private key authentication.

Conceptually:

```text
HTTPS
   ↓
Username + token-style credential
```

versus:

```text
SSH
   ↓
SSH private key
```

The Jenkins Git plugin supports username/password credentials for HTTP/HTTPS repository access and SSH private-key credentials for SSH repository access. ([Jenkins Plugins][1])

---

# 11. Which Should a Beginner Use?

We will learn both.

We will start with:

```text
Public repository
      +
HTTPS
      +
No credentials
```

because it lets you understand the checkout process without mixing authentication into the first lab.

Then we will progress to:

```text
Private repository
      +
HTTPS
      +
Jenkins credential
```

Finally, we will understand:

```text
SSH
      +
SSH key pair
      +
Host verification
```

This progression separates three different problems:

```text
Can Jenkins reach the repository?

Can Jenkins authenticate?

Is Jenkins authorized?
```

Those are not the same question.

# 17. Jenkins Git Plugin

Jenkins does not understand every source-control workflow through core functionality alone.

Plugins provide integrations.

The Jenkins Git plugin provides fundamental Git operations for Jenkins projects, including fetch, checkout, polling, branch handling, tagging, merging, and related repository operations. ([Jenkins Plugins][1])

Conceptually:

```text
Jenkins
   ↓
Git Plugin
   ↓
Git Client
   ↓
Git Repository
```

This plugin is commonly installed as part of the suggested Jenkins plugin set.

# 57. Authentication vs Authorization

Authentication asks:

```text
Who are you?
```

Authorization asks:

```text
What are you allowed to do?
```

Suppose Jenkins presents a valid identity.

Authentication succeeds.

But that identity does not have access to:

```text
private-repository-A
```

Authorization fails.

Therefore:

```text
Valid credential
```

does not automatically mean:

```text
Access to every repository
```

This distinction is extremely important when troubleshooting.

---

# 58. GitHub Password Authentication

Do not configure Jenkins with your normal GitHub account password for Git operations over HTTPS.

GitHub no longer accepts account passwords for Git authentication over HTTPS.

For HTTPS Git operations that require authentication, a personal access token can be used in place of a password.

We will use that model for the private repository lab.

---

# 59. Personal Access Tokens

A Personal Access Token, often shortened to:

```text
PAT
```

is a token that can authenticate certain operations with GitHub.

A token should be treated like a secret.

Do not:

```text
Commit it into Git.
```

Do not:

```text
Put it in README.md.
```

Do not:

```text
Echo it into Jenkins console output.
```

Do not:

```text
Post it in screenshots.
```

Do not:

```text
Hardcode it into shell commands.
```

Instead:

```text
GitHub Token
      ↓
Jenkins Credentials
      ↓
Credential ID
      ↓
Job uses credential
```

Jenkins provides a credentials system specifically so secrets do not need to be hardcoded into job definitions. ([Jenkins][3])

---

# 60. Fine-Grained vs Classic GitHub Tokens

GitHub provides more than one type of personal access token, including fine-grained personal access tokens and classic personal access tokens.

For new integrations, prefer the narrowest permissions that actually satisfy the requirement.

For Jenkins simply cloning a private repository, the credential should not receive broad administrative permissions it does not need.

Think:

```text
Jenkins needs:
read repository
```

Do not automatically grant:

```text
all repositories
+
organization administration
+
workflow administration
+
unrelated account permissions
```

Least privilege applies to tokens too.

GitHub organizations can also impose policies affecting token access, approval, or authorization, so the exact token configuration can depend on repository ownership and organization settings.

# 71. SSH Authentication

HTTPS with a token is not the only way Jenkins can access GitHub.

You can also use SSH.

The architecture becomes:

```text
Jenkins
   ↓
SSH Private Key
   ↓
SSH
   ↓
GitHub
   ↓
Repository
```

GitHub stores the corresponding public key or otherwise associates the public key with an authorized identity/repository access mechanism.

Jenkins stores the private key credential.

The Jenkins Git plugin requires an SSH private-key credential for SSH repository URLs. ([Jenkins Plugins][1])

---

# 72. Public Key vs Private Key

An SSH key pair contains:

```text
Private Key
Public Key
```

Conceptually:

```text
Private Key
   ↓
Keep secret
   ↓
Jenkins
```

while:

```text
Public Key
   ↓
Can be registered with GitHub
```

Never upload your private key to GitHub as the public key.

Never commit your private key to the repository.

Never print your private key into Jenkins logs.

# 73. Generate a Dedicated SSH Key

For example:


For example:

```text

```

This creates files conceptually like:

```text
jenkins_github_ed25519
jenkins_github_ed25519.pub
```

The first is private.

The `.pub` file is public.

To view the public key:



in public documentation or screenshots.

# 77. Credential Type Must Match Protocol

This is a common Jenkins Git mistake.

For HTTPS:

```text
https://...
```

the Git plugin expects:

```text
Username / password credential
```

where the password field can contain the GitHub token.

For SSH:

```text
git@github.com:...
```

the Git plugin expects:

```text
SSH private key credential
```

The Git plugin documentation explicitly distinguishes these credential types. ([Jenkins Plugins][1])

Do not configure:

```text
SSH URL
+
Secret text credential
```

and expect the Git plugin checkout to understand what you intended.

# 78. Host Key Verification

SSH introduces another security concept.

Suppose Jenkins connects to:

```text
github.com
```

How does it know it is actually talking to the intended SSH server?

SSH uses host keys to identify servers.

This helps defend against connecting blindly to an impersonating server.

Conceptually:

```text
Jenkins
   ↓
Connect to github.com
   ↓
Server presents host key
   ↓
Verify trusted identity
   ↓
Continue SSH authentication
```

This is separate from your Jenkins private key.

---

# 79. Two Different SSH Key Concepts

Beginners often confuse them.

## Client authentication key

This proves:

```text
Who is Jenkins?
```

It consists of the Jenkins-side private key and corresponding public key registered with GitHub.

## Server host key

This helps answer:

```text
Is this really the server Jenkins intended to contact?
```

These solve different security problems.

```text
Client Key
=
authenticate Jenkins to server
```

```text
Host Key
=
verify server identity
```

Do not confuse them.

---

# 80. Host Key Verification Strategy

The Jenkins Git client plugin provides SSH host key verification strategies.

Your available configuration depends on plugin versions and Jenkins configuration.

The secure principle is:

```text
Do not blindly trust an unexpected host identity.
```

If host verification fails, investigate the expected host key using trusted GitHub documentation or your organization's approved SSH configuration process.

Do not automatically disable host-key verification just to make the error disappear.

A security check that blocks a connection may be protecting you.

---

# 81. HTTPS vs SSH Summary

| Area                              | HTTPS                               | SSH                                          |
| --------------------------------- | ----------------------------------- | -------------------------------------------- |
| Example URL                       | `https://github.com/OWNER/REPO.git` | `git@github.com:OWNER/REPO.git`              |
| Public repo                       | Usually no credential needed        | SSH identity generally needed for SSH access |
| Private repo                      | Authentication required             | Authentication required                      |
| Jenkins credential for Git plugin | Username/password                   | SSH username/private key                     |
| GitHub secret                     | PAT can serve as HTTPS password     | Private SSH key stays with Jenkins           |
| Server verification               | TLS/HTTPS certificate chain         | SSH host-key verification                    |
| Beginner setup                    | Usually simpler                     | More SSH concepts                            |
| Automation suitability            | Excellent                           | Excellent                                    |

Neither protocol is automatically "the only correct one."

Use the method that matches your organization's security and operational model.

# 86. Authentication Failure vs Permission Failure

These can look similar.

## Authentication failure

Conceptually:

```text
GitHub does not accept the identity.
```

Possible causes:

* Invalid token.
* Revoked token.
* Expired token.
* Incorrect SSH key.
* Incorrect credential type.
* Wrong username/token combination.
* Credential missing.

Conceptually:

```text
Identity is known
but
identity cannot access this repository/action.
```

Possible causes:

* Token does not include the repository.
* Token lacks required permission.
* Organization policy blocks access.
* SSH key belongs to an identity without repository access.
* Repository access was removed.

The troubleshooting question is not simply:

> Are credentials configured?

It is:

```text
Are they valid?
```

and:

```text
Are they authorized for this resource?
```

# 95. Common Failure: Permission Changed


```text

```

# 96. Common Failure: SSH Host Key Verification

## Symptom

SSH repository checkout fails with host-key verification-related output.

## Investigation

Determine:

* Which host is Jenkins connecting to?
* Which host key does Jenkins expect?
* Has the host identity legitimately changed?
* Is the verification strategy configured correctly?

## Unsafe response

```text
Disable verification everywhere.
```

## Better response

Verify the expected host identity through an authoritative source and configure Jenkins appropriately.

Security errors should be understood, not simply suppressed.

# 97. Common Failure: Private Key Permission or Format Problem

An SSH key can fail for reasons such as:

* Wrong private key.
* Public key entered instead of private key.
* Unsupported or malformed key content.
* Incorrect passphrase.
* Public key not registered with the intended GitHub identity.
* Jenkins credential configured incorrectly.

Remember:

```text
GitHub gets public key
```

while:

```text
Jenkins protects private key
```

Do not reverse them.

---

# 98. Common Failure: Checkout Works but Build Fails

Suppose console output shows:

```text
Checking out Revision ...
```

successfully.

Then later:

```text
./app.sh: Permission denied
```

That is no longer a Git authentication problem.

The repository was retrieved successfully.

Your failure is later in the build.

Troubleshoot by layers:

```text
Repository connection   ✓
Authentication          ✓
Checkout                ✓
Workspace               ✓
Build command           ✗
```

This prevents you from wasting time regenerating tokens for a shell permission problem.

---

# 99. Common Failure: Repository Is Empty

Suppose Jenkins connects successfully but there is no useful branch or commit to check out.

An empty repository has no application commit for Jenkins to build.

Make sure the repository contains committed and pushed content.

Remember:

```text
File exists locally
```

is not enough.

It must be:

```text
tracked
   ↓
committed
   ↓
pushed
   ↓
available remotely
```

before Jenkins can retrieve it from GitHub.

# 100. Common Failure: Change Was Committed but Not Pushed

You make:

```text
version.txt = 1.0.5
```

then:

```bash
git add version.txt
git commit -m "Update version"
```

but forget:

```bash
git push
```

Jenkins continues building the previous remote commit.

Investigate:

```bash
git status
```

and:

```bash
git log --oneline --decorate -n 5
```

Then compare local and remote state.

The Jenkins checkout is only as current as the remote repository it can see.

# 101. Common Failure: Jenkins Uses a Different Commit Than Expected

Do not guess.

Inspect:

```text
GIT_COMMIT
```

and:

```bash
git rev-parse HEAD
```

Then compare that commit with GitHub.

Also verify:

```text
GIT_BRANCH
```

and:

```text
Branches to build
```

Possible causes include:

* Wrong branch.
* Change not pushed.
* Job configured for another repository.
* Build occurred before latest push.
* Branch selection pattern differs from expectation.

Commit hashes are evidence.

Use them.

# 102. Security: Give Jenkins Only the Repository Access It Needs

Suppose Jenkins only needs to clone:

```text
jenkins-private-app
```

It should not automatically receive administrative access to:

```text
Every repository
Every organization
Every workflow
Every deployment environment
```

Use:

```text
least privilege
```

The Jenkins security documentation recommends limiting credential access and defining credentials at the lowest practical scope. ([Jenkins][4])

Think:

```text
Required capability
      ↓
Minimum credential scope
      ↓
Specific Jenkins jobs
```

---

# 103. Security: Read-Only Is Often Enough for Checkout

Our current job needs to:

```text
read repository
```

It does not need to:

```text
delete repository
```

or:

```text
change organization settings
```

or necessarily:

```text
push commits
```

Therefore use read access where that satisfies the requirement.

Later workflows may genuinely need write operations, such as tagging or publishing changes.

Grant those permissions when required, not preemptively.

---

# 104. Security: Separate Credentials by Purpose

Avoid one giant credential such as:

```text
jenkins-super-admin-everything
```

used for:

```text
GitHub
AWS
Docker Registry
Production SSH
Artifact Repository
```

Instead, think:

```text
github-private-repo-read

docker-registry-push

production-deploy-ssh

artifact-repository-upload
```

This limits blast radius.

If one credential is compromised, the attacker should not automatically inherit every privilege Jenkins possesses.

---

# 105. Security: Job Configuration Can Be Powerful

Remember Part 3.

A user able to edit arbitrary shell commands can potentially execute code on the build node.

Now add repository credentials.

A poorly designed permissions model can allow users or repository-controlled build logic to misuse credentials.

Jenkins explicitly warns administrators to carefully scope SCM credentials, particularly in environments where users can influence repository content or job definitions. ([Jenkins][5])

For our beginner lab, the important lesson is:

```text
Source code
+
Jenkins job
+
Credentials
=
security boundary
```

Treat it seriously.

---

# 106. Workspace Security

After checkout, source code exists in the workspace.

That code should be treated as input to the build system.

A repository can contain:

```text
shell scripts
build scripts
Dockerfiles
configuration
dependency definitions
Jenkinsfiles
```

Later Jenkins may execute some of them.

Therefore:

```text
Repository write access
```

can become very powerful in a CI/CD environment.

This is one reason production CI systems require thoughtful access controls and isolated build agents.

# 110. Why Jenkins Checks Out a Specific Commit

Branches move.

Suppose:

```text

```

points to commit:

```text
A
```

at 10:00.

Then a developer pushes commit:

```text
B
```

and `main` moves:

```text
A → B
```

A build needs a specific source revision.

Therefore Jenkins ultimately builds a particular commit, not an abstract moving concept called "main."

Think:

```text
Branch
   ↓
resolves to revision
   ↓
specific commit
   ↓
checkout
   ↓
build
```

That exact commit gives us reproducibility and traceability.

# 112. Public Repository Troubleshooting Decision Tree

Use this mental model:

```text
Public repository checkout fails
          ↓
Is Git available?
      ┌───┴───┐
     NO      YES
      ↓        ↓
Install/    Is URL correct?
configure     │
Git        ┌──┴──┐
          NO    YES
           ↓      ↓
         Fix    Can node
         URL    reach GitHub?
                  │
              ┌───┴───┐
             NO       YES
              ↓         ↓
          Network/    Branch/
          DNS/TLS     repository
          issue       configuration
```

Do not immediately add credentials to a public repository just because checkout failed.

The cause may be unrelated to authentication.

# 113. Private Repository Troubleshooting Decision Tree

For private repositories:

```text
Private checkout fails
        ↓
Is URL correct?
        ↓
Is protocol correct?
        ↓
Is matching credential selected?
        ↓
Is credential valid?
        ↓

        ↓

        ↓
Does organization policy allow it?
        ↓
For SSH: does host verification succeed?
        ↓
Does branch/revision exist?
```

This gives you a systematic process instead of random trial and error.

# 114. Authentication Troubleshooting Table

| Symptom                         | Likely area                | Investigation                            |
| ------------------------------- | -------------------------- | ---------------------------------------- |
| Git executable not found        | Git installation           | `git --version`, `command -v git`        |
| Repository URL rejected         | Repository configuration   | Verify exact clone URL                   |
| Public repo inaccessible        | Network/DNS/TLS/URL        | Test reachability and `git ls-remote`    |
| Private repo inaccessible       | Authentication             | Check selected Jenkins credential        |
| Token stopped working           | Credential lifecycle       | Check expiry/revocation/access           |
| Valid token cannot read repo    | Authorization              | Check repository permissions             |
| SSH key rejected                | SSH authentication         | Check key pair and registered public key |
| Host key verification failed    | SSH server verification    | Verify expected host key                 |
| Branch not found                | Branch configuration       | Verify actual remote branch              |
| Checkout succeeds, script fails | Build step                 | Stop troubleshooting Git authentication  |
| Old code built                  | Remote/branch/commit state | Check push, branch and `GIT_COMMIT`      |

# 121. Knowledge Check Answers

### Answer 1

Source control provides a shared, versioned, traceable source from which Jenkins can retrieve code consistently.

### Answer 2

Git is a version control system. GitHub is a platform that hosts Git repositories and provides collaboration features.

### Answer 3

A Git repository contains version-controlled project content and Git history.

### Answer 4

A commit is a recorded point/change in Git history identified by a hash.

### Answer 5

A branch is a named line of development pointing through Git history.

### Answer 6

`git clone` creates a local copy of a remote repository.

### Answer 7

`git push` sends local commits to a configured remote repository.

### Answer 8

`origin` is the conventional short name Git commonly uses for the primary remote repository.

### Answer 9

HTTPS communicates with the repository over HTTPS and can use username/token authentication for private access. SSH uses SSH and public/private key authentication.

### Answer 10

Jenkins needs a Git implementation to retrieve and work with Git repositories.

### Answer 11

The Git plugin integrates Git operations such as fetch, checkout, branch selection, polling, and Git metadata with Jenkins jobs.

### Answer 12

It is the job configuration area that defines where Jenkins obtains source code.

### Answer 13

The repository's contents are publicly readable, so authentication may not be required for read access.

### Answer 14

GitHub needs to identify the requester and verify that it has permission to access the private repository.

### Answer 15

Authentication establishes identity. Authorization determines what that identity may access or do.

### Answer 16

A PAT is a secret token that can be used to authenticate permitted GitHub operations.

### Answer 17

In Jenkins Credentials, not directly in the job's shell commands or repository source.

### Answer 18

For the Jenkins Git plugin's HTTPS repository checkout:

```text
Username with password
```

with the GitHub token supplied as the password.

### Answer 19

```text
SSH Username with private key
```

### Answer 20

It helps Jenkins verify that the SSH server it reached is the server it intended to contact.

### Answer 21

Checkout prepares the selected repository revision as working files in the Jenkins workspace.

### Answer 22

Different branches can contain different source code.

### Answer 23

The commit hash Jenkins is using for the build.

### Answer 24

The local change may not have been committed and pushed to the remote repository Jenkins reads.

### Answer 25

Jenkins periodically checks the configured SCM for relevant changes.

### Answer 26

Polling asks the repository whether anything changed. A webhook allows the repository service to notify Jenkins when an event occurs.

### Answer 27

The identity may authenticate successfully but lack authorization for that repository.

### Answer 28

A compromised credential should expose only the minimum resources necessary.

### Answer 29

Because repository authentication and checkout already succeeded. The failure occurred later during command execution.

### Answer 30

Start with the Jenkins Console Output and determine which layer failed: Git executable, network, repository URL, authentication, authorization, branch selection, checkout, or the later build command.
