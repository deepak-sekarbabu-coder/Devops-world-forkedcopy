# Part 12: Jenkins Controller, Agents, Nodes, and Distributed Builds

## Learning Objective

Until now, your Jenkins environment has probably been simple:

```text
Developer
    ↓
GitHub
    ↓
Jenkins
    ↓
Build
    ↓
Test
    ↓
Artifact
```

And physically, it may have looked like this:

```text
One Linux Server
      ↓
Jenkins Controller
      ↓
Runs Jenkins
      ↓
Runs Pipeline
      ↓
Runs Git
      ↓
Runs Maven/Python/Node
      ↓
Creates Artifact
```

That is useful for learning.

It is not the architecture you should automatically carry into a serious Jenkins environment.

Jenkins is designed to support **distributed builds**. The controller coordinates work, while agents provide executors that perform that work. Jenkins also recommends setting controller executors to `0` so builds do not execute on the built-in node. ([Jenkins][1])

In this part, we move toward:

```text
                    Jenkins Controller
                           ↓
                       Build Queue
                           ↓
             Scheduling and Placement
                           ↓
          ┌────────────────┼────────────────┐
          ↓                ↓                ↓
       Agent 1          Agent 2          Agent 3
       Linux            Java             Docker
          ↓                ↓                ↓
      Executor         Executor         Executor
          ↓                ↓                ↓
      Workload         Workload         Workload
```

The learning objective is:

> Understand how Jenkins separates orchestration from execution and learn how controllers, nodes, agents, executors, labels, workspaces, queues, and agent connections work together.

By the end of Part 12, you should be able to:

* explain controller responsibilities;
* explain why production builds should normally not run on the controller;
* distinguish controllers, nodes, agents, and executors;
* create a second Jenkins node;
* configure a Linux agent;
* understand SSH and inbound agent connections;
* configure agent authentication;
* understand the remote root directory;
* understand agent workspaces;
* assign labels;
* use labels for workload placement;
* control where a Pipeline executes;
* understand executor capacity;
* observe the Jenkins build queue;
* deliberately take an agent offline;
* understand what happens to matching builds;
* diagnose agent connection failures;
* understand controller security;
* understand agent isolation;
* design a basic distributed Jenkins architecture.

Our target architecture is:

```text
Developer
    ↓
GitHub
    ↓
Jenkins Controller
    ↓
Build Queue
    ↓
Scheduler
    ↓
Label Matching
    ↓
Available Executor
    ↓
Linux Agent
    ↓
Workspace
    ↓
Git Checkout
    ↓
Build Tools
    ↓
Build
    ↓
Test
    ↓
Artifact
```

# 1. Start With the Problem

Imagine your Jenkins server performs everything.

```text
Jenkins Server
│
├── Jenkins web interface
├── Jenkins configuration
├── Jenkins credentials
├── Jenkins plugins
├── Build history
├── Pipeline scheduling
├── Git checkout
├── Maven builds
├── Python builds
├── Node.js builds
├── Docker builds
├── Integration tests
└── Deployment scripts
```

At first, this seems convenient.

There is only one machine.

But several problems appear as usage grows.

Suppose three teams use Jenkins.

```text
Team A
→ Java application
→ CPU-intensive Maven build

Team B
→ Node.js application
→ npm build

Team C
→ Docker application
→ container image build
```

All three workloads compete with the Jenkins controller.

Now imagine a test consumes all available memory.

```text
Application Test
      ↓
Consumes RAM
      ↓
Controller becomes slow
      ↓
Jenkins UI becomes slow
      ↓
Scheduling becomes slow
      ↓
Other builds suffer
```

Or a build accidentally executes:

```bash
rm -rf something-important
```

If the build runs directly on the controller, the consequences can be much more serious.

The problem is therefore not simply:

> Can Jenkins run builds locally?

It can.

The better question is:

> Should the machine responsible for controlling Jenkins also execute arbitrary application build workloads?

For serious Jenkins environments, usually not.

---

# 2. Why Separate Control From Execution?

A useful infrastructure principle is:

```text
Control
≠
Workload Execution
```

The Jenkins controller should focus on Jenkins orchestration.

Agents should execute application workloads.

Think:

```text
Controller
=
Coordinator
```

```text
Agent
=
Worker
```

Architecture:

```text
                  Jenkins Controller
                         │
                         │ assigns work
                         ↓
               ┌─────────┴─────────┐
               ↓                   ↓
          Linux Agent          Java Agent
               ↓                   ↓
             Build               Build
```

Jenkins documentation specifically recommends distributed builds as a way to protect controller stability from malicious or simply broken build scripts. ([Jenkins][2])

---

# 3. What Is the Jenkins Controller?

The **controller** is the central Jenkins process that manages the Jenkins environment.

Historically, older Jenkins documentation and interfaces used the term:

```text
master
```

Modern Jenkins terminology uses:

```text
controller
```

Similarly, older terminology often used:

```text
slave
```

Modern terminology uses:

```text
agent
```

You may still encounter old tutorials, configuration names, APIs, or legacy terminology.

For this series, we use:

```text
Controller
Agent
```

---

# 4. Controller Responsibilities

The controller is responsible for coordinating Jenkins.

Its responsibilities include areas such as:

```text
Web interface
Job configuration
Pipeline orchestration
Build scheduling
Build queue management
Agent management
Plugin management
Security configuration
Credential management
Build metadata
Pipeline state
Agent monitoring
```

A simplified architecture:

```text
                    Jenkins Controller
                           │
        ┌──────────────────┼──────────────────┐
        │                  │                  │
        ↓                  ↓                  ↓
    Job Config         Build Queue        Agents
        │                  │                  │
        └──────────────────┼──────────────────┘
                           ↓
                       Scheduling
```

The controller decides:

```text
What needs to run?
Where can it run?
When can it run?
Which executor is available?
```

---

# 5. What the Controller Should Not Become

Avoid treating the controller as:

```text
Jenkins
+
Compiler farm
+
Docker host
+
Test server
+
Deployment server
+
Database
+
Everything else
```

The controller is critical infrastructure.

Its stability matters.

If the controller is unavailable:

```text
Jenkins UI
Build scheduling
Pipeline coordination
Agent management
```

can all be affected.

Therefore controller resources should not casually compete with application workloads.

---

# 6. The Built-In Node

The machine running the Jenkins controller is represented inside Jenkins as the **built-in node**.

A beginner installation may allow builds to execute there.

Conceptually:

```text
Controller Machine
      ↓
Built-In Node
      ↓
Executor
      ↓
Build
```

This is convenient for Parts 1 through 11 because we were learning.

But Jenkins recommends setting the number of controller executors to `0`, leaving actual execution to agents. ([Jenkins][1])

Our architecture will therefore move toward:

```text
Controller
Executors = 0
      ↓
Does not run normal builds
      ↓
Agents perform builds
```

Do not change this yet if doing so would strand all your existing lab jobs. We will first establish a working agent.

---

# 7. What Is a Node?

A **node** is a Jenkins-configured machine or execution environment capable of participating in Jenkins build execution.

Examples might include:

```text
Linux VM
Windows Server
Physical machine
Cloud VM
Container
macOS machine
```

Inside Jenkins, you might have:

```text
Built-In Node
linux-agent-01
linux-agent-02
windows-agent-01
```

A node describes an execution resource Jenkins knows about.

---

# 8. What Is an Agent?

An **agent** is the process/environment connected to the controller that performs work for Jenkins.

Jenkins describes agents as providing executors that perform work requested by the controller. ([Jenkins][1])

Think:

```text
Node
=
configured execution machine/environment
```

and:

```text
Agent
=
Jenkins worker process operating there
```

In everyday Jenkins conversation, people sometimes use "node" and "agent" almost interchangeably.

But the distinction is useful:

```text
Node configuration
      ↓
Defines execution resource

Agent process
      ↓
Connects resource to controller
```

---

# 9. Controller vs Node vs Agent vs Executor

This is one of the most important distinctions in Part 12.

### Controller

Coordinates Jenkins.

### Node

Configured execution resource.

### Agent

Worker process connected to Jenkins for that resource.

### Executor

A slot that allows work to execute.

Mental model:

```text
Jenkins Controller
      ↓
Node
      ↓
Agent
      ↓
Executor
      ↓
Build
```

---

# 10. What Is an Executor?

An executor represents build execution capacity on a Jenkins node.

Suppose:

```text
Agent 1
Executors = 1
```

Then approximately:

```text
1 executor
=
1 executor slot for scheduled Jenkins work at a time
```

If two builds require that node:

```text
Build A
Build B
```

and only one executor exists:

```text
Executor
   ↓
Build A runs

Build B
   ↓
Waits
```

---

# 11. Multiple Executors

Suppose:

```text
Agent
Executors = 3
```

Then Jenkins can potentially execute several tasks concurrently on that node.

Conceptually:

```text
                 Agent
                   │
        ┌──────────┼──────────┐
        ↓          ↓          ↓
    Executor 1 Executor 2 Executor 3
        ↓          ↓          ↓
     Build A    Build B    Build C
```

But do not think:

```text
More executors
=
Always better
```

Each concurrent build consumes resources.

---

# 12. Executor Capacity

Imagine a machine has:

```text
4 CPU cores
8 GB RAM
```

and every build needs:

```text
3 GB RAM
```

Configuring:

```text
10 executors
```

would allow Jenkins to attempt too much concurrent work.

Potential result:

```text
10 builds
   ↓
Memory pressure
   ↓
Swapping
   ↓
Slow builds
   ↓
Out-of-memory failures
   ↓
Unstable agent
```

Executor count should reflect workload and machine capacity.

---

# 13. Capacity Is More Than CPU

Agent capacity depends on:

```text
CPU
Memory
Disk
Disk I/O
Network
Tool requirements
Container capacity
Licensing constraints
External dependencies
Workload characteristics
```

For example:

```text
Unit test
```

may be lightweight.

But:

```text
Large integration test suite
```

may consume substantial memory and CPU.

Do not choose executor counts only from CPU core count.

Measure actual workloads.

---

# 14. Build Queue

What happens when Jenkins has work but no suitable executor is available?

The work waits in the **build queue**.

Architecture:

```text
Pipeline requested
      ↓
Jenkins Controller
      ↓
Build Queue
      ↓
Suitable node?
      ↓
Suitable label?
      ↓
Online?
      ↓
Free executor?
      ↓
YES
      ↓
Run build
```

If not:

```text
Build Queue
      ↓
Wait
```

---

# 15. Why a Build Can Be Queued

A build may wait because:

```text
No agent is online
No matching label exists
Matching agent is offline
All matching executors are busy
Node usage restrictions prevent scheduling
Agent is disconnected
Agent is temporarily offline
Required environment is unavailable
```

Therefore:

```text
Queued
```

does not mean:

```text
Jenkins is broken
```

It means Jenkins has not yet found eligible execution capacity.

---

# 16. Scheduling

Jenkins scheduling is the process of deciding where queued work should execute.

Simplified:

```text
Build enters queue
       ↓
Determine requirements
       ↓
Find eligible nodes
       ↓
Check labels
       ↓
Check node restrictions
       ↓
Check online state
       ↓
Check executors
       ↓
Assign workload
```

This is where labels become extremely important.

---

# 17. What Is a Label?

A label is metadata assigned to Jenkins nodes to describe capabilities or characteristics.

Examples:

```text
linux
windows
docker
java
python
nodejs
high-memory
arm64
gpu
production-deploy
```

Jenkins documents labels as a way to group agents according to capabilities so jobs can restrict themselves to appropriate agents. ([Jenkins][1])

For example:

```text
Agent 1
Labels:
linux java
```

```text
Agent 2
Labels:
linux docker
```

```text
Agent 3
Labels:
windows
```

---

# 18. Why Labels Matter

Suppose your Pipeline needs Docker.

Without placement controls:

```text
Pipeline
   ↓
Any available agent
```

It might land on:

```text
Agent without Docker
```

and fail:

```text
docker: command not found
```

Instead:

```text
Pipeline
   ↓
Requires label "docker"
   ↓
Only docker-capable agents considered
```

Labels connect:

```text
Workload requirement
```

to:

```text
Agent capability
```

---

# 19. Labels Should Describe Real Capabilities

Do not add:

```text
docker
```

to an agent that does not actually provide the required Docker capability.

A label is a scheduling promise.

If you label a node:

```text
java21
```

the node should actually provide the expected Java environment.

Otherwise:

```text
Scheduler trusts label
      ↓
Pipeline scheduled
      ↓
Tool missing
      ↓
Build fails
```

Your infrastructure metadata must reflect reality.

---

# 20. Label Design

Good labels describe useful scheduling properties.

Examples:

```text
linux
windows
arm64
x86_64
java17
java21
docker
high-memory
gpu
```

Avoid unnecessarily creating a unique label for every single job.

You want reusable capability descriptions.

For example:

```text
linux && java21
```

conceptually means:

> Give this workload a node that satisfies both capabilities.

---

# 21. Pipeline Agent Selection

Until now, many of our Jenkinsfiles used:

```groovy
pipeline {
    agent any
}
```

That means Jenkins may use an appropriate available agent without a more specific label requirement.

Now we can write:

```groovy
pipeline {
    agent {
        label 'linux'
    }

    stages {
        stage('Build') {
            steps {
                sh '''
                    set -eu
                    echo "Running on Linux agent"
                    hostname
                '''
            }
        }
    }
}
```

This tells Jenkins:

```text
Pipeline
   ↓
Needs label "linux"
   ↓
Scheduler searches matching nodes
```

---

# 22. Multiple Capability Requirements

Suppose a build requires:

```text
Linux
+
Docker
```

A label expression can be used where appropriate:

```groovy
agent {
    label 'linux && docker'
}
```

Conceptually:

```text
Agent A
linux
→ not enough

Agent B
docker
→ not enough

Agent C
linux + docker
→ eligible
```

This becomes powerful as Jenkins grows.

---

# 23. Labels Are Not Security Boundaries

This is critical.

A label such as:

```text
production
```

does not itself create strong security isolation.

Labels are primarily scheduling mechanisms.

Do not think:

```text
label = security control
```

You still need appropriate:

```text
Permissions
Credentials
Network controls
Agent isolation
Authorization
Host security
```

---

# 24. Node Usage

Jenkins node configuration can control how the node is used.

Common conceptual choices include:

```text
Use this node as much as possible
```

or:

```text
Only build jobs with label expressions matching this node
```

Jenkins documents these usage modes for agents. ([Jenkins][1])

For specialized agents, restricting them to explicitly matching jobs can be useful.

Example:

```text
expensive-gpu-agent
```

should probably not be consumed by a basic:

```text
echo "Hello"
```

job.

# 25. Remote Root Directory

When configuring a permanent agent, Jenkins asks for a **remote root directory**.

Example:

```text
/home/jenkins/agent
```

This is the base directory Jenkins uses on that agent for its files and workspaces.

Conceptually:

```text
/home/jenkins/agent/
│
├── workspace/
├── remoting/
└── other Jenkins agent data
```

Exact contents can vary.

---

# 26. Why "Remote"?

"Remote" means remote from the controller's perspective.

It does not necessarily mean the machine is on the public internet.

It might be:

```text
Controller:
10.0.1.10

Agent:
10.0.1.20
```

Both could exist on the same private network.

The agent is still a remote execution resource from Jenkins controller's perspective.

---

# 27. Choosing a Remote Root Directory

A good agent root should:

```text
Belong to the agent service account
Have sufficient disk capacity
Be writable by that account
Not expose sensitive unrelated files
Use predictable permissions
Have enough space for workspaces
```

Example:

```text
/home/jenkins/agent
```

or another dedicated filesystem location.

Avoid casually using:

```text
/root
/
```

or unrelated application directories.

---

# 28. Agent Workspaces

Each build needs a working directory.

On an agent, Jenkins creates workspaces under the node's workspace area.

Conceptually:

```text
Agent Root
   ↓
workspace/
   ↓
project-name/
```

Example:

```text
/home/jenkins/agent/workspace/veriqta-calculator/
```

Inside the workspace you may find:

```text
Source code
Jenkins-created files
Build output
Temporary files
Dependencies
Artifacts before archiving
```

---

# 29. Controller Workspace vs Agent Workspace

Previously you may have seen:

```text
/var/lib/jenkins/workspace/project
```

when builds ran on the built-in node.

After moving the build to an agent, the workspace may instead exist under something like:

```text
/home/jenkins/agent/workspace/project
```

This is important.

Do not write Pipeline scripts that assume:

```text
/var/lib/jenkins/workspace/...
```

Use:

```text
$WORKSPACE
```

or Jenkins workspace mechanisms.

---

# 30. Never Hardcode Agent Workspace Paths

Bad:

```bash
cd /home/jenkins/agent/workspace/my-app
```

Better:

```bash
cd "$WORKSPACE"
```

Often you do not even need the `cd`, because Jenkins already executes build steps from the workspace.

Verify:

```bash
pwd
```

and:

```bash
printf '%s\n' "$WORKSPACE"
```

The paths should reflect the current build context.

---

# 31. Static Agents

A **static agent** is an execution machine that remains provisioned independently of individual builds.

Examples:

```text
Physical Linux server
Persistent VM
Windows build server
macOS build machine
```

Architecture:

```text
Agent Machine Exists
       ↓
Connected to Jenkins
       ↓
Waits for Work
       ↓
Build arrives
       ↓
Executes
       ↓
Waits again
```

Static agents are easy to understand and are ideal for this beginner lab.

---

# 32. Static vs Ephemeral Agents

Static:

```text
Provision once
     ↓
Reuse repeatedly
```

Ephemeral:

```text
Build requested
     ↓
Agent created
     ↓
Build executes
     ↓
Agent destroyed
```

Later, systems such as cloud VMs, containers, and Kubernetes can provide dynamic or ephemeral agents.

Part 12 focuses primarily on static agents so you understand the architecture before automation hides it.



Representative result:


# 36. Network Verification

From the controller, verify the agent is reachable.

For SSH:

```bash
ssh YOUR_AGENT_USER@AGENT_IP
```

Do not continue configuring Jenkins SSH launch if ordinary SSH connectivity does not work.

Troubleshoot the network layer first.

Architecture:

```text
Controller
    ↓
Network
    ↓
SSH Service
    ↓
Agent Host
```

Jenkins cannot fix broken underlying connectivity.

# 37. Create a Dedicated Agent User

On the agent machine:

```bash
sudo useradd --create-home --shell /bin/bash jenkins
```

Depending on your Linux distribution, another account-management command such as `adduser` may be available.

Verify:

```bash
id jenkins
```

and:

```bash
getent passwd jenkins
```

Expected conceptually:

```text
jenkins user exists
home directory exists
shell is configured
```

---

# 38. Why Use a Dedicated User?

Do not connect the Jenkins agent as:

```text
root
```

simply because it avoids permission problems.

A dedicated account helps implement:

```text
Least privilege
File ownership
Process separation
Auditability
Reduced accidental access
```

The build should receive only the privileges it actually requires.

---

# 39. Prepare the Remote Root Directory

For this lab, use:

```text
/home/jenkins/agent
```

Create it:

```bash
sudo mkdir -p /home/jenkins/agent
```

Set ownership:

```bash
sudo chown -R jenkins:jenkins /home/jenkins/agent
```

Inspect:

```bash
ls -ld /home/jenkins/agent
```

The Jenkins agent user should own the directory.

---

# 40. Verify Write Access

Test as the agent user:

```bash
sudo -u jenkins touch /home/jenkins/agent/write-test
```

Then:

```bash
ls -l /home/jenkins/agent/write-test
```

Remove it:

```bash
sudo -u jenkins rm /home/jenkins/agent/write-test
```

If this fails, fix permissions before involving Jenkins.

# 41. Java Requirement

Jenkins agents require Java appropriate for the Jenkins version in use. Jenkins' agent documentation identifies Java and controller connectivity as fundamental agent requirements. ([Jenkins][1])

Check:

```bash
java -version
```

If Java is missing, install a Java version supported by your Jenkins release.

For the current series, we previously used OpenJDK 21 with our Jenkins environment.

On a compatible Ubuntu/Debian lab:

```bash
sudo apt update
```

```bash
sudo apt install openjdk-21-jre
```

Then:

```bash
java -version
```

Always check the current Jenkins Java support policy before choosing versions for a real deployment.

# 42. Agent Authentication

The controller must know it is communicating with an authorized agent environment.

The exact authentication mechanism depends on how the agent connects.

For an SSH-launched agent:

```text
Controller
   ↓
SSH credentials
   ↓
Agent host
```

For an inbound agent:

```text
Agent
   ↓
Jenkins-provided agent identity/secret
   ↓
Controller
```

Authentication should not be confused with ordinary user login to the Jenkins UI.

---

# 43. SSH Agents

With an SSH-launched agent, the controller connects to the agent machine over SSH.

Architecture:

```text
Jenkins Controller
       ↓
SSH
       ↓
Linux Host
       ↓
Authenticate
       ↓
Start Jenkins agent process
       ↓
Agent connects/communicates
       ↓
Online
```

This is a common and understandable model for persistent Linux agents.

---

# 44. What the SSH Agent Needs

At a high level:

```text
Reachable SSH service
Valid SSH credentials
Java
Writable remote root
Compatible environment
Network connectivity
```

The controller also needs the appropriate Jenkins SSH agent-launch capability/plugin.

Your exact available launch methods depend on installed plugins.

---

# 45. Prepare SSH Authentication

A strong lab approach is a dedicated SSH key.

On an administrative system, generate a dedicated key pair:

```bash
ssh-keygen -t ed25519 -C "jenkins-agent-01"
```

When prompted for a file, use a clearly named dedicated key rather than overwriting your personal SSH key.

For example:

```text
jenkins-agent-01-ed25519
```

You now have:

```text
Private key
Public key
```

The private key must be protected.

---

# 46. Install the Public Key on the Agent

The public key needs to be authorized for the dedicated agent account.

Conceptually:

```text
Public Key
     ↓
Agent's jenkins account
     ↓
~/.ssh/authorized_keys
```

Make sure ownership and permissions are appropriate.

Typical SSH expectations include:

```text
~/.ssh
→ restricted permissions

authorized_keys
→ restricted permissions
```

Do not place the private key on the agent as part of this controller-to-agent SSH design.

---

# 47. Test SSH Before Jenkins

From the controller or equivalent network location:

```bash
ssh -i /path/to/private-key jenkins@AGENT_IP
```

Then:

```bash
whoami
```

Expected:

```text
jenkins
```

Check:

```bash
java -version
```

Check:

```bash
test -w /home/jenkins/agent && echo "Writable"
```

Only after ordinary SSH works should you configure Jenkins.

---

# 48. Store the SSH Key in Jenkins Credentials

Do not paste private keys directly into Pipeline code.

From Jenkins:

```text
Manage Jenkins
→ Credentials
```

Create an appropriate SSH private key credential.

Conceptually:

```text
Kind:
SSH Username with private key

Username:
jenkins

Private Key:
dedicated agent private key

ID:
linux-agent-01-ssh
```

Use a meaningful credential ID.

The credential should exist at an appropriate scope and be limited as much as practical. Jenkins recommends limiting credential access to reduce attack surface. ([Jenkins][3])

# 70. Inbound Agents

```text
    ↓
```

---

# 71. Why Use an Inbound Agent?

Inbound agents can be useful when:

```text

Windows environment
Network architecture requires agent-initiated connections
```

Historically you may encounter the term:

```text

```

in older Jenkins material.

Modern Jenkins generally calls these inbound agents.

---

# 72. Inbound Agent Networking

Traditional inbound agents can use a dedicated TCP agent listener.

Jenkins documentation notes that this port is disabled by default, and it can be configured as random or fixed when needed. Modern Jenkins can also use WebSocket transport for inbound agents, avoiding the need for an additional dedicated TCP agent port. ([Jenkins][4])

This means you should not blindly open:

```text
50000
```

because an old tutorial told you to.

First determine your actual connection method.

---

# 73. WebSocket Inbound Agents

Conceptually:

```text
Agent
   ↓
WebSocket
   ↓
Existing Jenkins HTTP/HTTPS path
   ↓
Controller
```

This can simplify firewall architecture because an additional inbound agent TCP listener may not be required. ([Jenkins][4])

Always prefer the architecture appropriate for your environment rather than copying old Jenkins networking instructions.

# 74. Inbound Agent Authentication

# 89. Executors Share the Machine

Two executors do not create two physical computers.

They share:

```text

RAM
Disk
Network
Kernel
Installed tools
Potentially caches
```

So:

```text

```

means four concurrent execution slots on the same underlying node.

It does not mean four isolated servers.

# 90. Build Isolation

This brings us to an important security issue.

Suppose:

```text

```

and:

```text

```

run on the same persistent agent.

Depending on configuration, they may potentially interact through:

```text

Temporary directories
System resources
Network
Shared tools
```

Jenkins warns that more complex environments need to consider isolation between builds, not only isolation from the controller. ([Jenkins][5])


No single mechanism solves every isolation problem.

```text
Local configuration
```

# 93. Agent Trust

Do not assume:

```text

=
fully trusted forever
```

Agents execute code.

If an agent is compromised, the attacker may gain access to data available to builds executed there.

Jenkins includes controller protections specifically because agents and build workloads should not automatically have unrestricted controller access. Modern Jenkins hardens agent-to-controller communication by default. ([Jenkins][6])

# 94. Controller Isolation

```text

Test code

```

If that code executes directly on the controller:

```text

      ↓
Critical Jenkins machine
```

The risk is greater.

# 141. Jenkinsfile

For the Python calculator project, use:

```groovy
pipeline {
    agent {
        label 'linux'
    }

    stages {
        stage('Agent Information') {
            steps {
                sh '''
                    set -eu

                    echo "=== Agent Information ==="
                    echo "Node: $NODE_NAME"
                    echo "Workspace: $WORKSPACE"
                    echo "Build: $BUILD_NUMBER"

                    echo "Hostname:"
                    hostname

                    echo "User:"
                    whoami

                    echo "Working directory:"
                    pwd
                '''
            }
        }

        stage('Verify Environment') {
            steps {
                sh '''
                    set -eu

                    echo "=== Python ==="
                    python3 --version

                    echo "=== Git ==="
                    git --version

                    echo "=== Disk ==="
                    df -h .
                '''
            }
        }

        stage('Prepare') {
            steps {
                sh '''
                    set -eu

                    rm -rf .venv build dist

                    python3 -m venv .venv

                    .venv/bin/python -m pip install --upgrade pip
                    .venv/bin/python -m pip install -r requirements-dev.txt
                '''
            }
        }

        stage('Test') {
            steps {
                sh '''
                    set -eu

                    .venv/bin/python -m pytest -v
                '''
            }
        }

        stage('Build') {
            steps {
                sh '''
                    set -eu

                    .venv/bin/python -m build

                    test -d dist
                    ls -lah dist
                '''
            }
        }

        stage('Verify Artifact') {
            steps {
                sh '''
                    set -eu

                    WHEEL="$(find dist -maxdepth 1 -type f -name '*.whl' -print -quit)"

                    if [ -z "$WHEEL" ]; then
                        echo "ERROR: No wheel artifact found."
                        exit 1
                    fi

                    echo "Artifact found:"
                    echo "$WHEEL"
                '''
            }
        }
    }

    post {
        success {
            archiveArtifacts(
                artifacts: 'dist/*',
                fingerprint: true
            )
        }

        always {
            echo "Pipeline completed on node: ${env.NODE_NAME}"
        }
    }
}
```

# 151. Common Beginner Mistakes

### Mistake 1: Calling every machine an agent without understanding nodes

Remember:

```text
Node
→ configured execution resource

Agent
→ Jenkins worker process
```

### Mistake 2: Thinking executor means server

An executor is a workload slot, not a separate machine.

### Mistake 3: Adding too many executors

Result:

```text
Resource exhaustion
```

### Mistake 4: Running everything on controller

Result:

```text
Controller stability/security risk
```

### Mistake 5: Assuming controller tools exist on agents

Result:

```text
command not found
```

### Mistake 6: Using inaccurate labels

Result:

```text
Wrong workload placement
```

### Mistake 7: Treating labels as security boundaries

They are primarily scheduling metadata.

### Mistake 8: Using root for agents

Violates least privilege.

### Mistake 9: Disabling SSH host verification to make errors disappear

Weakens security.

### Mistake 10: Hardcoding workspace paths

Breaks portability.

### Mistake 11: Assuming queued means Jenkins is broken

Investigate scheduling.

### Mistake 12: Restarting controller whenever agent is offline

Diagnose the connection layer first.

### Mistake 13: Putting every credential on every agent

Increases exposure.

### Mistake 14: Sharing privileged agents with untrusted builds

Creates unnecessary security risk.

### Mistake 15: Opening inbound agent ports because an old tutorial says so

Modern inbound agents can use WebSocket, and network configuration should match your actual architecture. ([Jenkins][4])

# 166. Part 12 Complete

At the beginning of Part 12, your Jenkins mental model may have been:

```text
Jenkins Server
      ↓
Pipeline
      ↓
Build
```

That is no longer sufficient.

Your model should now be:

```text
                         Jenkins Controller
                                ↓
                           Build Queue
                                ↓
                            Scheduler
                                ↓
                         Label Matching
                                ↓
           ┌────────────────────┼────────────────────┐
           ↓                    ↓                    ↓
      Linux Agent          Java Agent          Docker Agent
           ↓                    ↓                    ↓
       Executor             Executor             Executor
           ↓                    ↓                    ↓
       Workspace            Workspace            Workspace
           ↓                    ↓                    ↓
         Tools                Tools                Tools
           ↓                    ↓                    ↓
       Workload             Workload             Workload
```

The controller's primary job is not:

```text
compile everything
test everything
run every shell command
```

Its role is to coordinate Jenkins.

The agents provide execution capacity.

The queue holds work that cannot yet run.

The scheduler decides where work can run.

Labels express capabilities.

Executors represent concurrency.

Workspaces hold working files.

And the build tools must exist where the workload actually executes.

The key production transition is:

```text
BEFORE

Controller
   ↓
Build
```

to:

```text
AFTER

Controller
   ↓
Queue
   ↓
Scheduler
   ↓
Agent
   ↓
Executor
   ↓
Workspace
   ↓
Build
```

You also learned that distributed Jenkins is not merely a performance feature.

It contributes to:

```text
Controller stability
Workload placement
Capacity management
Platform specialization
Security separation
Failure isolation
Scaling
```

But distributed execution introduces new operational questions:

```text
Which agents are online?

Which labels do they have?

How many executors?

What tools are installed?

Who can connect agents?

What credentials can workloads access?

Are builds isolated?

What happens if an agent fails?

What happens when capacity is exhausted?
```

Those are real Jenkins engineering questions.

Your next architecture builds directly on this.

You now have:

```text
GitHub
   ↓
Jenkins Controller
   ↓
Build Queue
   ↓
Agent
   ↓
Workspace
   ↓
Build
   ↓
Test
   ↓
Artifact
```

In **Part 13: Jenkins With Docker**, we will extend it to:

```text
Developer
    ↓
GitHub
    ↓
Jenkins Controller
    ↓
Docker-Capable Agent
    ↓
Git Checkout
    ↓
Application Test
    ↓
Dockerfile
    ↓
Docker Build
    ↓
Docker Image
    ↓
Container
    ↓
Application Verification
```

That introduces an important new security question:

> How should Jenkins be allowed to build containers without carelessly giving build workloads dangerous control over the host?

That is where Jenkins, distributed agents, Docker, permissions, build isolation, image construction, and containerized CI begin to come together.
