# Part 3: Jenkins Dashboard, Administration, and Your First Job

## Learning Objective

In Part 1, you learned why Jenkins exists and how CI/CD automation works.

In Part 2, you built your first Jenkins server:

```text
Computer
   ↓
Java
   ↓
Jenkins
   ↓
Jenkins Service
   ↓
Port 8080
   ↓
Web Browser
   ↓
Jenkins Web UI
```

Now Jenkins is running, but it is not useful merely because the dashboard loads.

A Jenkins server becomes useful when you give it work to perform.

That is what we are going to do in Part 3.

Our build is:

```text
Jenkins
   ↓
Job
   ↓
Build Step
   ↓
Command
   ↓
Build
   ↓
Console Output
```

By the end of this part, you will be able to:

* Navigate the Jenkins dashboard.
* Understand the major areas under Manage Jenkins.
* Find system configuration.
* Find tool configuration.
* Understand nodes and executors.
* Inspect installed plugins.
* Find the Jenkins credentials area.
* Create a Freestyle project.
* Add shell or Windows batch commands.
* Save job configuration.
* Start a build manually.
* Understand build numbers.
* Read build status.
* Read console output.
* Find and inspect a workspace.
* Examine useful build metadata.
* Inspect environment variables.
* Create files during a build.
* Understand build history.
* Disable and re-enable jobs.
* Delete individual builds safely.
* Deliberately cause a build to fail.
* Diagnose that failure from Jenkins output.

Most importantly, you are going to stop treating Jenkins as a web page and start treating it as an automation system.

# 1. Start With the Mental Model

Before clicking anything, understand what we are about to build.

Suppose we create a Jenkins job called:

```text
veriqta-first-job
```

Inside the job, we tell Jenkins to execute:

```bash
echo "Hello from Jenkins"
```

When we select:

```text
Build Now
```

the flow is approximately:

```text
User
  ↓
Jenkins Dashboard
  ↓
Job
  ↓
Build Requested
  ↓
Jenkins Scheduler
  ↓
Available Executor
  ↓
Workspace
  ↓
Shell Command
  ↓
Console Output
  ↓
Build Result
```

If everything succeeds, Jenkins records something like:

```text
Build #1
Result: SUCCESS
```

If we run it again:

```text
Build #2
```

Then again:

```text
Build #3
```

The job remains the same.

Each execution receives its own build number and build record.

Remember what you learned in Part 1:

```text
Job
=
definition of work

Build
=
one execution of that work
```

This distinction becomes real in this part.

# 3. What Is the Jenkins Dashboard?

The dashboard is the main starting page of the Jenkins web interface.

Think of it as the front door to your Jenkins controller.

As you create jobs, the dashboard gives you a central place from which to:

* See jobs.
* Open jobs.
* Start builds.
* See recent build activity.
* Create new items.
* Access administrative settings.
* Inspect build executors.
* Navigate Jenkins.

Your dashboard will become more populated as we create projects.

A new Jenkins installation may look relatively empty.

That is normal.

Conceptually:

```text
Jenkins Dashboard
│
├── New Item
├── Build History
├── Manage Jenkins
├── Jobs / Projects
├── Views
└── Executor information
```

The exact appearance can differ depending on:

* Jenkins version.
* Installed plugins.
* Permissions.
* Theme.
* Screen size.
* Configuration.

Do not worry if your dashboard is not pixel-for-pixel identical to a screenshot from an older tutorial.

Learn the concepts and navigation rather than memorizing where every button sits.

# 4. The Dashboard Is Not the Jenkins Server

This distinction is important.

The dashboard is:

```text
Web interface
```

Jenkins itself is:

```text
Running automation server
```

You are interacting with Jenkins through HTTP:

```text
Browser
   ↓
HTTP
   ↓
Jenkins Controller
   ↓
Jenkins Configuration / Jobs / Builds
```

Closing your browser does not stop Jenkins.

The Jenkins service continues running.

You proved this in Part 2 when you managed Jenkins using `systemctl`.

# 7. What Is Build History?

Jenkins records executions of jobs.

Suppose you run:

```text
veriqta-first-job
```

five times.

You may eventually have:

```text
Build #1
Build #2
Build #3
Build #4
Build #5
```

Build History gives you access to these executions.

This matters because automation without history would make troubleshooting difficult.

Imagine someone says:

> The build worked yesterday but failed today.

You need evidence.

Jenkins can preserve records of executions so you can compare what happened.

# 9. Administrator vs Ordinary Jenkins User

Not every Jenkins user should necessarily have access to everything under:

```text
Manage Jenkins
```

A Jenkins administrator may be able to:

* Configure the controller.
* Install plugins.
* Configure tools.
* Manage credentials.
* Manage nodes.
* Change security settings.
* Inspect system information.

An ordinary developer might only need permission to:

* View certain jobs.
* Run builds.
* Configure certain projects.
* Read build output.

This is an important security principle:

```text
Having access to Jenkins
       ≠
Needing Jenkins administrator access
```

Your learning installation uses an administrator account because you need to explore everything.

Do not translate that into:

> Everyone in a company should be a Jenkins administrator.

They should not.

# 14. Be Careful With Global Configuration

You are now in a dangerous part of Jenkins.

Why?

Because:

```text
Job configuration
```

usually affects a particular job.

But:

```text
System configuration
```

can affect the controller or many jobs.

Before changing global settings, ask:

```text
What uses this setting?

What will change?

Could existing builds be affected?

Can I reverse the change?
```

For this part, inspect more than you modify.

These two areas are easy to confuse.

Think:

```text

│
├── System
│     ↓
│   Controller-wide Jenkins settings
│
└── Tools
      ↓

```

For example:

```text

```

belongs to system-level configuration.

# 18. Nodes

Return to:


```text

```

Remember:

```text

        ↓
      Nodes
        ↓
```

# 19. What Is the Built-In Node?

Your Jenkins controller itself has a built-in node.

Conceptually:

```text
Jenkins Controller
      │
      └── Built-In Node
              ↓
           Executor
              ↓
             Job
```

For a simple learning environment, this can allow you to run your first basic job without creating a separate agent.

This is useful for learning.

It is not the architecture we will recommend for serious production workloads.

Later, you will build:

```text
Controller
    ↓
Agent
    ↓
Build
```

instead.

---

# 20. Why Production Builds Should Move to Agents

Suppose a build runs:

```text
CPU-intensive compilation
```

or:

```text
Untrusted project scripts
```

or:

```text
Docker operations
```

directly on the controller.

Now your central Jenkins service is sharing its environment with potentially heavy or risky build workloads.

This creates concerns involving:

* Security.
* Performance.
* Stability.
* Scalability.
* Isolation.

The Jenkins documentation specifically discourages running tasks on the built-in node for these reasons. ([Jenkins][5])

We will build agents properly in Part 12.

For Part 3:

```text
Built-in node
```

is acceptable for our controlled beginner lab.

# 21. Executors

When viewing a node, you will encounter the idea of executors.

An executor represents capacity for running work.

Suppose a node has:

```text
2 executors
```

Conceptually:

```text
Node
│
├── Executor 1
│      ↓
│    Build A
│
└── Executor 2
       ↓
     Build B
```

If both are occupied:

```text
Build C
```

must wait unless another eligible executor is available.

That waiting work enters the queue.

You learned this in Part 1.

Now you can see the infrastructure that makes the concept real.

# 23. Inspect Installed Plugins

Open the installed plugins area.

Look at some of the names.

Depending on what was installed during Part 2, you may see plugins related to:

* Credentials.
* Git.
* Pipeline.
* SSH.
* Build utilities.
* User-interface functionality.

Do not install anything just because its name sounds useful.

A common Jenkins beginner mistake is:

```text
Interesting plugin
      ↓
Install
      ↓
Another interesting plugin
      ↓
Install
      ↓
Another plugin
      ↓
Install
```

Soon the controller contains dozens of unnecessary dependencies.

Production plugin management should be deliberate.

---

# 24. Why Plugins Need Care

A plugin is executable software running as part of your Jenkins environment.

Therefore plugins can introduce:

* Security vulnerabilities.
* Compatibility problems.
* Dependency chains.
* Upgrade considerations.
* Configuration complexity.

The correct mindset is:

```text
Need capability
      ↓
Evaluate plugin
      ↓
Understand dependencies
      ↓
Install intentionally
      ↓
Maintain it
```

not:

```text
Install everything
```

We will cover plugin management much more deeply in Part 11.

# 25. Credentials

Return to:

```text
Manage Jenkins
```

Locate:

```text
Credentials
```

Credentials allow Jenkins to authenticate to external systems.

Examples include:

```text
GitHub
Container registry
Linux server
Cloud platform
Database
Artifact repository
```

Jenkins supports credential types such as secret text, username/password, secret files, SSH private keys, and certificates, depending on available plugins. Jenkins stores configured credentials in encrypted form on the controller and workflows normally refer to them through credential identifiers rather than hardcoding secrets directly. ([Jenkins][7])

# 29. Environment Variables

You will see environment variables throughout Jenkins.

An environment variable is a named value available to a process.

Examples from an operating system might include:

```text
PATH
HOME
USER
```

Jenkins also exposes build-related environment variables.

A job may receive information such as:

```text
JOB_NAME
BUILD_NUMBER
BUILD_ID
BUILD_URL
WORKSPACE
NODE_NAME
```

The exact set can depend on Jenkins, job type, plugins, parameters, and build context.

Jenkins documentation notes that build scripts commonly receive information through environment variables and warns that variables such as `PATH` can change how commands behave. ([Jenkins][9])

We are going to print some of these ourselves.

# 39. Where Does the Command Run?

This question is extremely important.

The command does not run:

```text
inside your browser
```

The browser only sends your configuration to Jenkins.

The command executes on the node assigned to run the build.

For our simple lab:

```text
Browser
   ↓
Jenkins Controller
   ↓
Built-In Node
   ↓
Executor
   ↓
Shell
   ↓
echo
```

Later:

```text
Controller
   ↓
Agent
   ↓
Executor
   ↓
Shell
```

This distinction becomes critical when jobs require tools or files.

# 40. Which User Runs the Command?

Remember the Linux user from Part 2:

```text
jenkins
```

Our package-based Jenkins service runs under that account.

Therefore build commands executing in this environment normally operate with the permissions available to the Jenkins process and its build environment.

This is why a command may work when you run it manually as your own Linux user but fail inside Jenkins.

For example:

```text
Your user
   ↓
Can read /home/ann/private-file
```

does not mean:

```text
jenkins user
   ↓
Can read /home/ann/private-file
```

Permissions matter.

We will prove which user is running shortly.

# 44. Build Number

Look at the Build History area.

You should see something similar to:

```text

```

This means:

```text
Build Number 1
```

It is the first recorded execution of this job.

Run the job again later and you should get:

```text

```

Then:

```text
#3
```

The build number identifies an execution within that job.

So:

```text
veriqta-first-job #1
```

and:

```text

```

are different executions of the same job.

---

# 45. Build Numbers Are Not Job Versions

This is worth clarifying.

Suppose:

```text
Build #10
```

exists.

That does not necessarily mean:

```text
Application version 10
```

It means Jenkins has assigned build number 10 to that job execution.

Application versioning is a separate concern.

Later, you might intentionally use a build number when constructing an artifact version, but Jenkins does not automatically make them the same concept.

# 46. Build Status

Each build receives a result.

Common results you will encounter include concepts such as:

```text
SUCCESS

FAILURE

UNSTABLE

ABORTED
```

There can be other states depending on job type and plugins.

For our first build, you want:

```text
SUCCESS
```

A successful build means Jenkins completed the configured work according to the job's success criteria.

It does not mean:

```text
the software is definitely bug-free
```

Jenkins only knows what you instructed it to check.

# 49. Learn to Read Console Output

Do not look only at:

```text

```

Read from the top.

You can often learn:

```text
Who or what started the build?

Where did it run?

Which workspace was used?

What command executed?

What did the command print?

Did Jenkins report an error?
```

# 67. Linux Shell Commands vs Windows Batch Commands

# 68. Why Shell Choice Matters

Suppose you write:

```bash

```

for a Windows `cmd.exe` batch step.


Think:

```text
Linux / Unix-like shell
      ↓
$VARIABLE
```

versus:

```text
Windows cmd.exe
      ↓
%VARIABLE%
```

Jenkins does not make operating-system command languages identical.

It runs the appropriate command interpreter configured for the build environment.

# 74. What Makes a Shell Build Fail?

This is one of the most important concepts in this entire part.

Commands return:

```text
exit codes
```

By convention:

```text
0
```

normally means:

```text
success
```

A non-zero exit code normally indicates some kind of failure.

For example:

```bash
exit 0
```

means successful shell termination.

While:

```bash
exit 1
```

indicates failure.

Jenkins uses command results to determine whether build steps succeeded.

```text

```

Now:

```bash

```

Then:

```bash

```

You should normally see:

```text

```

`$?` contains the exit status of the previous shell command.

This is fundamental Unix/Linux behavior.

Jenkins builds on top of these operating-system conventions.

tells you about:

```text
one Jenkins job execution
```

You can have:

```text

Job build = failed
```

There is no contradiction.

The automation server can be working perfectly while the automation it executed fails.

This distinction is extremely important.

# 98. Jenkins Failure vs Build Failure

Consider:

```text
Jenkins
   ↓
Runs test command
   ↓
Tests detect bug
   ↓
Command exits non-zero
   ↓
Build = FAILURE
```

Did Jenkins fail?

No.

Jenkins may have worked exactly as designed.

It correctly ran the test and correctly reported that the test failed.

This is a successful automation system reporting an unsuccessful workload.

Think:

```text
Pipeline reports failure correctly
          ≠
Jenkins itself is broken
```

# 102. Security Warning About Diagnostic Jobs

Be careful.

Commands such as:

```bash
printenv
```

and system-information commands can expose useful operational details.

A diagnostic job that is appropriate on your private learning controller may reveal too much information on a shared or production controller.

Potentially sensitive information includes:

* Internal hostnames.
* Paths.
* Environment variables.
* Tool locations.
* Network information.
* Credentials accidentally injected into environments.
* Infrastructure details.

Do not publish Jenkins console logs blindly.

Logs can contain sensitive data.

---

# 103. Security Warning About Arbitrary Shell Access

A user who can configure a Jenkins job that executes arbitrary shell commands may have significant capabilities on the machine where that job runs.

Consider:

```text
Jenkins user can configure job
          ↓
Job can execute shell
          ↓
Shell runs on Jenkins node
          ↓
Commands have node-level effects
```

This is why Jenkins permissions matter.

Allowing someone to edit build steps is not merely allowing them to "edit a web page."

You may effectively be allowing them to execute code in the build environment.

Production Jenkins authorization must therefore be designed carefully.

---

# 104. Do Not Run Jenkins Jobs as Root Just to Avoid Permission Problems

Suppose your build receives:

```text
Permission denied
```

A dangerous response is:

> Let's run Jenkins as root.

That may eliminate the immediate permission problem while creating a much larger security problem.

Instead:

```text
Understand required access
      ↓
Grant only necessary permission
      ↓
Keep Jenkins least-privileged
```

This is the correct engineering mindset.

# 107. Common First-Job Failures

Here is a practical troubleshooting table.

| Symptom                        | Possible cause                | First investigation                      |
| ------------------------------ | ----------------------------- | ---------------------------------------- |
| Build does not start           | No executor available         | Check queue/nodes/executors              |
| `command not found`            | Tool missing or PATH wrong    | `command -v`, `which`, `echo "$PATH"`    |
| `Permission denied`            | Jenkins lacks permission      | `whoami`, `ls -l`, `ls -ld`              |
| File missing                   | Wrong path/workspace          | `pwd`, `ls -la`                          |
| Variable empty                 | Variable not defined          | `printenv`                               |
| Shell syntax error             | Incorrect shell syntax        | Read console output near failing command |
| Windows variable not expanding | Used Linux syntax             | Use `%VARIABLE%` in batch                |
| Linux variable not expanding   | Used Windows syntax           | Use `$VARIABLE`                          |
| Build returns FAILURE          | Command exited non-zero       | Read console output                      |
| Old command still runs         | Configuration not saved       | Reopen Configure and verify              |
| Job cannot run                 | Job disabled                  | Re-enable project                        |
| Job waits indefinitely         | Node/executor issue           | Inspect queue and node status            |
| Browser works but job fails    | Jenkins itself may be healthy | Diagnose the build, not the service      |

# 108. Troubleshooting Method

For every first-job problem, use the same discipline.

## 1. Identify the symptom

Example:

```text
Build #8 = FAILURE
```

## 2. Open Console Output

Find the actual error.

## 3. Identify the failing command

Example:

```text
+ npm
npm: command not found
```

## 4. Understand the environment

Ask:

```text
Which node?

Which user?

Which workspace?

Which PATH?

Which operating system?
```

## 5. Test the hypothesis

For example:

```bash
command -v npm
```

## 6. Fix the cause

Perhaps install/configure the tool on the correct node.

## 7. Run again

Create a new build.

## 8. Verify

Do not stop because the error disappeared.

Confirm:

```text
Finished: SUCCESS
```

and verify the intended work actually occurred.

# 114. Knowledge Check Answers

### Answer 1

The dashboard is the main web interface from which you navigate Jenkins jobs, build activity, and administrative areas.

### Answer 2

Manage Jenkins contains controller administration and configuration functions.

### Answer 3

System configuration controls Jenkins-wide settings, while Tools configuration manages certain development/build tools Jenkins jobs can use.

### Answer 4

A node is an execution environment associated with Jenkins where work can run.

### Answer 5

An executor represents capacity on a node to execute Jenkins work.

### Answer 6

Plugins extend Jenkins with additional capabilities and integrations.

### Answer 7

Plugins add executable software, dependencies, maintenance requirements, and potentially security or compatibility risks.

### Answer 8

It manages authentication material Jenkins may need to access external systems.

### Answer 9

A Freestyle project is a Jenkins project configured largely through the web UI using build steps and other job settings.

### Answer 10

A build step is an action Jenkins performs during a build.

### Answer 11

It requests a new execution of the job.

### Answer 12

It is the first numbered execution of that job.

### Answer 13

Console Output is the captured textual output describing what happened during the build.

### Answer 14

The workspace is the filesystem area where Jenkins performs work for a job on a node.

### Answer 15

Build metadata is information describing an execution, such as build number, result, time, duration, trigger, node, and related information.

### Answer 16

An environment variable is a named value available to a process and often used to pass configuration or contextual information.

### Answer 17

An exit code of:

```text
0
```

normally represents success.

### Answer 18

A non-zero exit code normally represents failure.

### Answer 19

Jenkins may run under a different user, environment, PATH, working directory, node, operating system, or permission set.

### Answer 20

Disabling preserves the job while preventing ordinary execution. Deleting removes the job or build object being deleted.
