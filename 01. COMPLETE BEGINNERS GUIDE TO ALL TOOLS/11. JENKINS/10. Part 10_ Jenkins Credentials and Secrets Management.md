# Part 10: Jenkins Credentials and Secrets Management

## Learning Objective

In Part 9, you learned how to make one Jenkins Pipeline behave differently using controlled configuration:

```text
Jenkins Pipeline
      ↓
Parameters
      ↓
Validation
      ↓
Environment Selection
      ↓
Configuration
      ↓
Build
      ↓
Tests
      ↓
Deployment Decision
```

You also learned an important distinction:

```text
Non-sensitive configuration
≠
Sensitive configuration
```

Values such as these are normally non-sensitive:

```text
APP_VERSION=2.4.1
DEPLOY_ENV=staging
LOG_LEVEL=INFO
```

But real CI/CD systems eventually need values such as:

```text
GitHub token
Registry password
SSH private key
Cloud credential
API token
Database password
Certificate
```

Those are **secrets**.

We cannot simply write them into a Jenkinsfile.

The Pipeline therefore needs a secure bridge:

```text
Jenkins Pipeline
       ↓
Credential ID
       ↓
Jenkins Credentials Store
       ↓
Temporary Credential Binding
       ↓
Build / Push / Deploy
       ↓
Credential Removed From Build Context
```

Jenkins provides a Credentials system specifically for this purpose. Credentials are stored encrypted on the Jenkins controller and Pipeline jobs normally refer to them through credential IDs instead of embedding the actual values in Pipeline source. ([Jenkins][1])

By the end of Part 10, you should understand how to:

* identify secrets;
* keep secrets out of Git and Jenkinsfiles;
* add credentials to Jenkins;
* understand credential types and scopes;
* use credential IDs;
* bind credentials with `credentials()`;
* bind credentials temporarily with `withCredentials`;
* work with username/password credentials;
* work with secret text;
* understand SSH private-key credentials;
* understand certificate credentials;
* use credentials for Git, registries, SSH, and cloud systems;
* understand Jenkins masking and its limitations;
* diagnose authentication failures;
* rotate credentials;
* apply least privilege;
* prevent common credential leaks.

Most importantly, you should understand:

> Jenkins credential handling reduces accidental exposure, but a Pipeline that is allowed to use a credential must itself be treated as trusted code.

Jenkins explicitly warns that masking does not stop a malicious Pipeline from deliberately capturing credentials. ([Jenkins][2])

---

# 1. Start With the Problem: Software Automation Needs Authentication

So far, our Pipeline has mainly performed operations such as:

```text
Checkout
Build
Test
Create Artifact
```

But real delivery systems interact with external systems.

For example:

```text
GitHub
Container Registry
Linux Server
AWS
Azure
Google Cloud
Artifact Repository
Database
API
Kubernetes Cluster
```

Many of those systems require authentication.

Consider:

```text
Jenkins
   ↓
Push Docker image
   ↓
Container Registry
```

The registry asks:

```text
Who are you?

Are you allowed to push?
```

Or:

```text
Jenkins
   ↓
SSH
   ↓
Production Server
```

The server needs to determine:

```text
Who is connecting?

Can this identity log in?

What is it allowed to do?
```

Automation therefore requires **machine authentication**.

---

# 2. Authentication vs Authorization

These terms are related but different.

## Authentication

Authentication asks:

> Who are you?

Examples:

```text
Username + password
API token
SSH private key
Certificate
Cloud identity
```

## Authorization

Authorization asks:

> What are you allowed to do?

For example:

```text
Identity:
jenkins-registry-user

Permissions:
Pull image
Push image

Not permitted:
Delete repository
Manage users
Change billing
```

This distinction becomes critical when we discuss least privilege.

Jenkins itself also separates authentication from authorization in its access-control model. ([Jenkins][3])

---

# 3. What Is a Secret?

A secret is information that provides access, proves identity, decrypts information, or authorizes an operation and therefore must not be publicly exposed.

Examples include:

```text
Passwords
API tokens
Personal access tokens
Private keys
Cloud access keys
Database passwords
Registry passwords
Signing keys
Certificate private material
Webhook secrets
```

A secret should be treated differently from ordinary configuration.

---

# 4. Configuration vs Secret

Compare:

```text
APP_VERSION=2.4.1
```

with:

```text
REGISTRY_PASSWORD=super-secret-password
```

The first can usually appear in:

```text
Console output
Jenkinsfile
Build metadata
Configuration
Documentation
```

The second generally should not.

A useful mental model is:

```text
Configuration
      ↓
Would disclosure create meaningful security risk?
      ↓
   ┌──┴──┐
   │     │
  NO    YES
   │     │
Normal  Secret
config
```

---

# 5. Why Secrets Must Never Live in Jenkinsfiles

Imagine this Jenkinsfile:

```groovy
pipeline {
    agent any

    environment {
        REGISTRY_USERNAME = 'jenkins-user'
        REGISTRY_PASSWORD = 'SuperSecretPassword123'
    }

    stages {
        stage('Login') {
            steps {
                echo 'Logging into registry'
            }
        }
    }
}
```

This is unsafe.

Why?

Because the password is now part of Pipeline source.

If the Jenkinsfile is stored in GitHub:

```text
Secret
  ↓
Jenkinsfile
  ↓
Git commit
  ↓
GitHub
  ↓
Repository history
```

Now the secret may exist in:

```text
Developer clones
Forks
Backups
CI caches
Git history
Code review systems
Local machines
Mirrors
```

Removing it from the latest version does not automatically remove it from historical commits.

---

# 6. The Jenkinsfile Is Code, Not a Secret Vault

Your Jenkinsfile should describe:

```text
what the Pipeline does
```

not contain:

```text
the passwords required to do it
```

Good:

```groovy
credentials('docker-registry-jenkins')
```

Bad:

```groovy
REGISTRY_PASSWORD = 'ActualPasswordHere'
```

The Jenkinsfile should reference a credential.

It should not contain the credential itself.

---

# 7. Another Bad Approach: Secrets in Parameters

Part 9 introduced parameters.

You might think:

```groovy
parameters {
    string(
        name: 'PASSWORD',
        defaultValue: '',
        description: 'Enter registry password'
    )
}
```

That is not a good replacement for credential management.

Ordinary parameters are configuration inputs.

They are not your primary secret-management boundary.

Use Jenkins Credentials or another appropriate secret-management system.

---

# 8. Another Bad Approach: Secrets in Shell Scripts

Suppose your repository contains:

```text
scripts/
└── deploy.sh
```

and inside:

```bash
#!/usr/bin/env bash

REGISTRY_PASSWORD="MySecretPassword"

docker login ...
```

You have simply moved the problem.

The secret is still in source control.

The rule is not:

> Don't put secrets specifically in Jenkinsfiles.

The broader rule is:

> Do not store plaintext secrets in source-controlled application or Pipeline code.

Jenkins recommends keeping secrets out of SCM. ([Jenkins][4])

---

# 9. What Is the Jenkins Credentials Store?

Jenkins provides a Credentials system for storing authentication material.

Conceptually:

```text
                    Jenkins
                       ↓
                Credentials Store
                       ↓
       ┌───────────────┼───────────────┐
       │               │               │
 GitHub Credential  Registry       SSH Credential
       │           Credential           │
       └───────────────┼───────────────┘
                       ↓
                    Pipelines
```

Instead of storing:

```text
actual-secret-value
```

inside the Jenkinsfile, the Jenkinsfile references something like:

```text
github-readonly
```

That is the **credential ID**.

Jenkins stores configured credentials encrypted on the controller and exposes them to Pipeline code through controlled credential mechanisms. ([Jenkins][1])

---

# 10. Credential Storage Does Not Make a Pipeline Automatically Safe

This is one of the most important lessons in this chapter.

Suppose Jenkins safely stores:

```text
production-database-password
```

but a Jenkinsfile allowed to use it contains malicious code that sends the value elsewhere.

The Credentials Store cannot magically prevent that Pipeline from abusing a credential it has been authorized to consume.

Therefore:

```text
Secure credential storage
+
Trusted Pipeline code
+
Restricted access
+
Least privilege
+
Safe agents
=
Much stronger credential security
```

Not:

```text
Credentials Store
=
Everything automatically safe
```

Jenkins specifically warns that anyone able to modify a Pipeline that can use a credential may effectively gain the ability to use that credential. ([Jenkins][5])

# 12. Credential Types

Jenkins supports several credential types, including:

```text
Secret text
Username and password
Secret file
SSH Username with private key
Certificate
Docker Host Certificate Authentication
```

Availability can also depend on installed plugins. ([Jenkins][1])

We will focus on the types most relevant to your DevOps journey.

---

# 13. Username and Password Credentials

This type stores two related values:

```text
Username
Password
```

Examples:

```text
Registry username + password
Git username + token
Artifact repository username + password
Legacy API username + password
```

Conceptually:

```text
Credential ID:
registry-push

        ↓

Username:
jenkins-publisher

Password:
********
```

---

# 14. Secret Text Credentials

Secret text stores one sensitive string.

Examples:

```text
API token
Personal access token
Webhook secret
Service token
Access token
```

Conceptually:

```text
Credential ID:
monitoring-api-token

        ↓

Secret:
********
```

Use this when the authentication material is a single secret value rather than a username/password pair.

---

# 15. SSH Username With Private Key

SSH commonly authenticates using a private key.

Jenkins can store:

```text
Username
Private key
Optional passphrase
```

For example:

```text
Credential ID:
staging-ssh-deployer

Username:
deploy

Private key:
********

Passphrase:
********
```

Jenkins documents this credential type for SSH-based connections. ([Jenkins][1])

---

# 16. Certificate Credentials

Some systems authenticate clients using certificates.

Jenkins supports certificate credentials based on PKCS#12 certificate material with an optional password. ([Jenkins][1])

Conceptually:

```text
Certificate file
      +
Certificate password
      ↓
Jenkins Credential
```

You may encounter certificate authentication with:

```text
Enterprise services
Private APIs
Mutual TLS
Signing systems
Legacy infrastructure
```

Do not worry about mastering PKI here.

The important beginner lesson is that credentials are not limited to passwords.

---

# 17. Secret Files

Some tools expect authentication information in a file.

Examples may include:

```text
Service-account files
Configuration credentials
License files
Signing material
```

Jenkins can store secret-file credentials and temporarily expose the file when required.

Again:

```text
Repository
```

should not contain the secret file merely because a tool expects file-based authentication.

---

# 18. Credential IDs

Every credential should have a useful identifier.

For example:

```text
github-readonly
registry-push
staging-ssh-deployer
monitoring-api-token
```

The Jenkinsfile references the ID.

For example:

```groovy
credentials('monitoring-api-token')
```

The Jenkinsfile does **not** need to know the actual token.

---

# 19. Why Credential IDs Matter

Suppose today:

```text
registry-push
      ↓
username: jenkins-user
password: old-secret
```

Later you rotate the underlying credential:

```text
registry-push
      ↓
username: jenkins-user
password: new-secret
```

The Pipeline can continue referencing:

```text
registry-push
```

This separates:

```text
Pipeline identity/reference
```

from:

```text
actual secret material
```

---

# 20. Choose Meaningful Credential IDs

Bad:

```text
secret1
password2
abc
credential
```

Better:

```text
github-ci-read
container-registry-push
staging-ssh-deploy
artifact-repository-publish
```

A credential ID should communicate purpose without revealing the secret itself.

Jenkins recommends using a meaningful, consistent ID convention; if no ID is supplied, Jenkins can generate one. ([Jenkins][1])

---

# 21. Do Not Put Secrets in Credential IDs

Do not create:

```text
credential ID:
admin-password-SuperSecret123
```

The ID itself is metadata.

Keep sensitive values out of names, descriptions, job names, parameter names, and similar metadata.

---

# 22. Credential Scope

A credential should not automatically be available everywhere merely because Jenkins can technically store it centrally.

Jenkins distinguishes credential scope and location.

At the standard system credential interface, Jenkins documents:

```text
Global
System
```

scopes. ([Jenkins][1])

---

# 23. Global Credential Scope

A Global credential can be used by applicable Pipeline projects/items within the object hierarchy where it is defined. ([Jenkins][1])

For a beginner single Jenkins controller, you will commonly encounter credentials under:

```text
System
   ↓
Global credentials
```

But do not interpret "Global" as:

> Everyone should receive every credential.

Access still needs to be designed carefully.

---

# 24. System Credential Scope

System-scoped credentials are intended for Jenkins itself to perform system-level functions, such as certain controller administration or agent-related interactions, rather than ordinary Pipeline use. ([Jenkins][1])

This distinction matters.

Do not select scopes randomly until something starts working.

---

# 25. Folder-Level Credentials

Larger Jenkins environments often organize jobs into folders.

For example:

```text
Jenkins
│
├── Team-A/
│   ├── application-one
│   └── application-two
│
└── Team-B/
    ├── service-one
    └── service-two
```

Credentials defined at a lower appropriate level can reduce exposure.

Jenkins recommends defining credentials at the lowest practical level and granting access only to projects and people that actually require them. ([Jenkins][4])

Conceptually:

```text
Team A Credential
      ↓
Team A jobs

NOT

every job on Jenkins
```

---

# 26. Credential Scope and Least Privilege Work Together

Ask two separate questions:

```text
Where is this credential available?
```

and:

```text
What can this credential do externally?
```

For example:

```text
Jenkins scope:
only deployment jobs

External permission:
push image to one registry repository
```

Both matter.

# 27. Lab Preparation: Use Fake Credentials

The first exercises intentionally demonstrate secret exposure.

Do **not** use:

```text
Real GitHub token
Real AWS key
Real production password
Real SSH key
Real registry password
```

Use an obviously fake secret such as:

```text
VERIQTA-LAB-SECRET-ONLY-8472
```

This value should grant access to nothing.

# 28. Failure Lab 1: Expose a Test Secret Incorrectly

Create a temporary training Pipeline:

```groovy
pipeline {
    agent any

    environment {
        TEST_SECRET = 'VERIQTA-LAB-SECRET-ONLY-8472'
    }

    stages {
        stage('Unsafe Example') {
            steps {
                echo "Secret value: ${env.TEST_SECRET}"
            }
        }
    }
}
```

Run it.

---

# 29. Expected Result

You will likely see the fake value in the console:

```text
Secret value: VERIQTA-LAB-SECRET-ONLY-8472
```

The exact surrounding Jenkins output varies.

The point is that we deliberately stored an ordinary string and printed it.

Jenkins had no reason to treat that ordinary value as a securely bound credential.

---

# 30. Identify Every Security Problem

There are multiple problems.

### Problem 1

The secret is inside Pipeline source.

### Problem 2

If committed, it enters Git history.

### Problem 3

It is printed to the console.

### Problem 4

Anyone who can read the relevant source or logs may obtain it.

### Problem 5

Changing the secret requires changing Pipeline source.

The architecture is wrong.

---

# 31. The Correct Architecture

We want:

```text
Jenkinsfile
    ↓
Credential ID
    ↓
Jenkins Credentials Store
    ↓
Temporary Binding
    ↓
Command requiring authentication
```

Not:

```text
Jenkinsfile
    ↓
Actual Secret
```

You now have:

```text
Jenkins Credentials Store

```

# 34. `credentials()`

Declarative Pipeline provides the `credentials()` helper inside the `environment` directive.

Example:

```groovy
pipeline {
    agent any

    environment {
        LAB_SECRET = credentials('veriqta-lab-secret')
    }

    stages {
        stage('Use Credential') {
            steps {
                sh '''
                    echo "Credential has been injected."
                    test -n "$LAB_SECRET"
                '''
            }
        }
    }
}
```

Jenkins documents this pattern for supported credential types. ([Jenkins][6])

---

# 35. What `credentials()` Is Doing

Conceptually:

```text
credentials('veriqta-lab-secret')
              ↓
Find credential by ID
              ↓
Bind credential
              ↓
LAB_SECRET
              ↓
Pipeline process environment
```

The Jenkinsfile stores the reference:

```text
veriqta-lab-secret
```

not the actual secret.

---

# 36. Do Not Print It Just Because Jenkins Masks It

You might try:

```groovy
sh '''
    echo "$LAB_SECRET"
'''
```

and see something masked.

Do not build a habit around intentionally printing secrets.

Jenkins masking exists to reduce **accidental** disclosure. Jenkins explicitly states that masking does not stop malicious Pipeline code from obtaining or disclosing a credential. ([Jenkins][2])

Correct verification is:

```bash
test -n "$LAB_SECRET"
```

This asks:

> Was a non-empty value provided?

without printing it.

---

# 37. Environment Injection

Credential binding commonly makes credential material available temporarily through environment variables or temporary files.

Conceptually:

```text
Credentials Store
       ↓
Credential Binding
       ↓
Environment Variable
       ↓
Process
       ↓
External Service
```

For example:

```text
API_TOKEN
```

exists while the relevant build code needs it.

This is called credential/environment injection.

---

# 38. Pipeline-Level Credential Binding

This:

```groovy
pipeline {
    agent any

    environment {
        LAB_SECRET = credentials('veriqta-lab-secret')
    }

    stages {
        ...
    }
}
```

makes the binding available broadly across the Pipeline.

That may be wider than necessary.

Ask:

> Does every stage need this secret?

Usually the answer is no.

---

# 39. Stage-Level Credential Binding

Suppose only the Publish stage needs a registry credential.

Better:

```groovy
stage('Publish') {
    environment {
        REGISTRY_AUTH = credentials('registry-push')
    }

    steps {
        echo 'Publishing artifact'
    }
}
```

Now the credential is scoped more narrowly.

Jenkins supports `environment` at Pipeline or stage level; stage-level bindings reduce the portion of the Pipeline where the credential is available. ([Jenkins][2])

---

# 40. Principle: Bind Secrets as Late as Practical

Prefer:

```text
Checkout
   ↓
Build
   ↓
Test
   ↓
Package
   ↓
Bind Registry Credential
   ↓
Push
```

rather than:

```text
Bind Every Credential
   ↓
Checkout
   ↓
Build
   ↓
Test
   ↓
Package
   ↓
Push
```

A credential should exist in the build environment only where needed.

---

# 41. `withCredentials`

Another important mechanism is:

```groovy
withCredentials(...) {

}
```

This comes from Jenkins credential binding functionality.

It binds credentials for the enclosed block. ([Jenkins][7])

Conceptually:

```text
Normal Pipeline
     ↓
withCredentials
     ↓
Credential available
     ↓
Authenticated operation
     ↓
Block ends
     ↓
Binding ends
```

---

# 42. Secret Text With `withCredentials`

Example:

```groovy
pipeline {
    agent any

    stages {
        stage('Authenticated Operation') {
            steps {
                withCredentials([
                    string(
                        credentialsId: 'veriqta-lab-secret',
                        variable: 'LAB_SECRET'
                    )
                ]) {
                    sh '''
                        set +x
                        test -n "$LAB_SECRET"
                        echo "Credential is available to this operation."
                    '''
                }
            }
        }
    }
}
```

The secret is bound to:

```text
LAB_SECRET
```

inside the credential block.

---

# 43. Why `withCredentials` Is Useful

It makes the secret requirement visually obvious:

```groovy
withCredentials(...) {
    // operation requiring credential
}
```

The Pipeline reader can see:

```text
Credential begins here
        ↓
Sensitive operation
        ↓
Credential block ends here
```

This is often preferable when only a small section requires authentication.

---

# 44. `credentials()` vs `withCredentials`

Both can be useful.

### `credentials()`

Convenient in Declarative `environment` blocks.

Example:

```groovy
environment {
    TOKEN = credentials('api-token')
}
```

### `withCredentials`

Useful when credential access should be tightly wrapped around a particular operation.

Example:

```groovy
withCredentials([...]) {
    sh '...'
}
```

Do not ask only:

> Which syntax is shorter?

Ask:

> What is the narrowest sensible place this credential should be available?

---

# 45. Username/Password Binding

Suppose Jenkins contains:

```text
ID:
registry-push

Username:
jenkins-publisher

Password:
********
```

A `withCredentials` binding can separate them:

```groovy
withCredentials([
    usernamePassword(
        credentialsId: 'registry-push',
        usernameVariable: 'REGISTRY_USER',
        passwordVariable: 'REGISTRY_PASS'
    )
]) {
    sh '''
        set +x
        test -n "$REGISTRY_USER"
        test -n "$REGISTRY_PASS"
        echo "Registry credential is available."
    '''
}
```

---

# 46. Username/Password With `credentials()`

Declarative `credentials()` has useful behavior for username/password credentials.

Suppose:

```groovy
environment {
    REGISTRY = credentials('registry-push')
}
```

Jenkins can create:

```text
REGISTRY
REGISTRY_USR
REGISTRY_PSW
```

where the main variable represents a combined username/password form and the `_USR` and `_PSW` variables expose the individual components. ([Jenkins][6])

For readability and narrow binding, you may still prefer explicit `withCredentials` bindings in many operational stages.

---

# 47. Never Echo the Password

Do not do:

```bash
echo "$REGISTRY_PASS"
```

Do not do:

```bash
printf '%s\n' "$REGISTRY_PASS"
```

Do not encode it and print the encoded form.

Do not deliberately transform it until masking stops recognizing it.

The objective is not to test Jenkins masking.

The objective is to avoid exposing secrets.

---

# 48. What Is Masking?

When credentials are properly bound, Jenkins attempts to mask credential values that appear in build logs.

Instead of:

```text
SuperSecretPassword
```

you may see:

```text
****
```

Jenkins describes this as reducing the risk of accidental credential disclosure. ([Jenkins][2])

The key phrase is:

```text
reducing the risk
```

not:

```text
guaranteeing secrecy
```

---

# 49. Masking Is Not Encryption of Console Output

Do not think:

```text
Anything I print is safe because Jenkins will hide it.
```

That is false.

A Pipeline with access to a credential can potentially:

```text
write it to a file
transform it
send it over a network
include it in an artifact
pass it to another process
expose it through debugging
```

Masking is a safety net for certain accidental log exposure.

It is not a sandbox around malicious Pipeline code. ([Jenkins][2])

---

# 50. Console Logs Are Security-Relevant

Console logs are operational evidence.

They often contain:

```text
Commands
Paths
Hostnames
Errors
URLs
Build metadata
Tool output
```

If careless, they can also contain:

```text
Passwords
Tokens
Private data
Authorization headers
Connection strings
Credential-bearing URLs
```

Therefore console logging must be designed intentionally.

---

# 51. Shell Tracing Can Expose Values

Shell debugging modes can print expanded commands.

For example:

```bash
set -x
```

causes shell commands to be traced.

That is useful for troubleshooting.

It is dangerous around secrets.

A safer credential block often starts with:

```bash
set +x
```

to disable shell command tracing while sensitive values are in use.

This does not replace correct credential handling, but it reduces unnecessary command echoing.

---

# 52. Groovy Interpolation Is Dangerous Around Secrets

Avoid:

```groovy
sh "some-command --token ${TOKEN}"
```

This causes Groovy to interpolate the value before handing the command to the shell.

Prefer a fixed single-quoted Groovy script and let the shell expand the environment variable:

```groovy
sh '''
    set +x
    some-command --token "$TOKEN"
'''
```

Jenkins documentation recommends avoiding Groovy interpolation for credentials and explains that shell expansion is safer for bound secret variables. ([Jenkins][2])

Even better, when the external tool supports a secure mechanism such as stdin, credential files, or native credential helpers, use that instead of placing secrets directly on a command line.

---

# 53. Why Command-Line Secrets Can Be Risky

Consider:

```bash
tool --password "$PASSWORD"
```

Even if the Jenkins console does not reveal it, command-line arguments may sometimes be visible to other processes or diagnostic tooling on the same machine.

Prefer application-specific secure mechanisms where available:

```text
stdin
temporary credential file
credential helper
native identity provider
short-lived token
```

Security depends on the external tool as well as Jenkins.

Delete this unsafe code:

```groovy

    TEST_SECRET = 'VERIQTA-LAB-SECRET-ONLY-8472'
}
```

Replace it with:

```groovy
pipeline {
    agent any

    stages {
        stage('Use Secret Safely') {
            steps {
                withCredentials([
                    string(
                        credentialsId: 'veriqta-lab-secret',
                        variable: 'TEST_SECRET'
                    )
                ]) {
                    sh '''
                        set +x

                        if [ -z "$TEST_SECRET" ]; then
                            echo "Credential was not injected."
                            exit 1
                        fi

                        echo "Credential was injected successfully."
                    '''
                }
            }
        }
    }
}
```

# 55. Expected Result

You should see:

```text
Credential was injected successfully.
```

You should **not** need to see:

```text
VERIQTA-LAB-SECRET-ONLY-8472
```

to prove that credential binding worked.

This is a crucial engineering habit:

```text
Verify behavior
≠
Print secret
```

# 56. Verification Without Disclosure

Useful checks include:

```bash
test -n "$TOKEN"
```

or:

```bash
if [ -z "$TOKEN" ]; then
    exit 1
fi
```

For real authentication, the strongest verification is often:

```text
Credential bound
      ↓
Authenticated request
      ↓
Expected service response
```

For example:

```text
Registry login succeeds
Repository checkout succeeds
SSH authentication succeeds
API returns authorized response
```

# 63. SSH Username/Private-Key Binding

Credential Binding supports SSH private-key bindings that can expose a temporary key-file path plus associated username/passphrase variables. ([Jenkins][7])

Conceptually:

```text
Jenkins SSH Credential
       ↓
Temporary key file
       ↓
SSH command
       ↓
Remote server
```

The important lesson is:

> Jenkins can temporarily materialize credential data required by a tool without storing the private key in your repository.

# 64. Example SSH Binding Structure

A Pipeline may use a binding shaped like:

```groovy
withCredentials([
    sshUserPrivateKey(
        credentialsId: 'staging-ssh-deployer',
        keyFileVariable: 'SSH_KEY',
        usernameVariable: 'SSH_USER'
    )
]) {
    sh '''
        set +x
        test -f "$SSH_KEY"
        test -n "$SSH_USER"
        echo "SSH credential is available."
    '''
}
```

This verifies the binding without printing the private key.

Actual SSH deployment comes later.

# 65. SSH Host Verification Still Matters

Possessing a private key proves something about the **client**.

You must also verify the **server**.

Otherwise:

```text
Jenkins
   ↓
SSH
   ↓
Who is actually at the other end?
```

This is why SSH host-key verification remains important.

Do not "solve" host verification failures by blindly disabling verification in production.

# 68. Principle: Sometimes the Safest Secret Is No Stored Secret

Credential management is not only:

Sometimes the better question is:

> Can I eliminate this long-lived password entirely?

# 71. Least Privilege

Least privilege means:

> Give an identity only the permissions necessary to perform its required task, and no more.

Bad:

```text
Jenkins Cloud Credential
Permissions:
Administrator
```

when Jenkins only needs:

```text
upload one artifact
```

Better:

```text
Jenkins Artifact Credential
Permissions:
publish to required repository
```

---

# 72. Least Privilege Applies at Several Layers

### Jenkins user permissions

Who can create or configure credentials?

### Jenkins credential availability

Which jobs/folders can use them?

### External account permissions

What can the credential do on GitHub, registry, server, or cloud?

### Credential lifetime

How long does it remain valid?

### Pipeline scope

Which stages receive it?

### Agent scope

Which machines/processes can potentially observe it?

Security is layered.

# 73. Why Agent Security Matters

Suppose a Pipeline receives:

```text
PRODUCTION_TOKEN
```

while running on an agent shared with untrusted workloads.

The secret now exists temporarily in that execution environment.

A compromised or malicious process with sufficient access on that machine may be able to inspect sensitive build information.

Therefore:

```text
Credential security
```

also depends on:

```text
Agent security
Build isolation
Operating-system permissions
Workload trust
```

Jenkins warns that users able to control agents or Pipeline definitions may gain access to build information, including credentials. ([Jenkins][8])

---

# 74. Credentials and Untrusted Pull Requests

Consider:

```text
External contributor
      ↓
Pull request
      ↓
Modifies Jenkinsfile
      ↓
Pipeline runs
      ↓
Production credential available
```

That can become extremely dangerous.

Do not automatically expose trusted production credentials to untrusted code.

Jenkins explicitly warns that trust in credentials extends to users who can modify the Jenkinsfile used by a credential-enabled Pipeline. ([Jenkins][5])

This becomes particularly important in multibranch and pull-request workflows.

# 75. Credential Rotation

Secrets should not necessarily remain unchanged forever.

Credential rotation means replacing an existing secret with a new one.

Example:

```text
Old token
   ↓
Generate new token
   ↓
Update Jenkins credential
   ↓
Verify Pipelines
   ↓
Revoke old token
```

Jenkins recommends changing underlying credentials periodically. ([Jenkins][4])

---

# 76. Why Credential IDs Help Rotation

Suppose your Pipeline contains:

```groovy
credentials('registry-push')
```

The underlying password changes.

If the same credential entry is updated, your Jenkinsfile can continue referencing:

```text
registry-push
```

This reduces coupling between:

```text
Pipeline code
```

and:

```text
secret value
```

---

# 77. Safe Rotation Workflow

A sensible generic workflow is:

```text
1. Identify credential consumers
        ↓
2. Create/issue replacement secret
        ↓
3. Update Jenkins credential
        ↓
4. Run controlled verification
        ↓
5. Confirm authentication succeeds
        ↓
6. Revoke old credential
        ↓
7. Monitor for failures
```

The exact order can differ depending on whether the external system permits overlapping credentials.

The goal is to avoid both:

```text
security exposure
```

and:

```text
unplanned outage
```

---

# 78. Rotation Must Include External Revocation

Changing the value stored in Jenkins does not necessarily revoke the old secret at the external provider.

Suppose:

```text
GitHub token A
```

is replaced in Jenkins by:

```text
GitHub token B
```

If token A still exists at the provider, it may still work.

Therefore rotation includes:

```text
Issue new
Update consumer
Verify
Revoke old
```

not merely:

```text
Edit Jenkins
```

The Pipeline should fail because Jenkins cannot resolve the requested credential.

# 83. Authentication Troubleshooting Model

When authentication fails:

```text
Authentication Failure
        ↓
Does credential ID exist?
        ↓
Is correct credential type used?
        ↓
Is credential visible to this job?
        ↓
Was binding successful?
        ↓
Is username/identity correct?
        ↓
Is secret still valid?
        ↓
Does external system recognize it?
        ↓
Does identity have required permission?
        ↓
Is network connection working?
```

Do not rotate credentials blindly before understanding the failure.

---

# 84. Credential Not Found vs Authentication Failed

These are different failure classes.

## Credential not found

Jenkins itself cannot obtain the credential.

Possible causes:

```text
Wrong credential ID
Wrong scope
Credential deleted
Credential unavailable to job
Wrong credential type
```

## Authentication failed

Jenkins obtained credential material and attempted authentication, but the external service rejected it.

Possible causes:

```text
Wrong password
Expired token
Revoked token
Wrong username
Invalid SSH key
Certificate expired
Account disabled
```

---

# 85. Authentication vs Authorization Failure

Another important distinction:

```text
401-style problem
```

often conceptually means:

```text
You are not successfully authenticated.
```

while:

```text
403-style problem
```

often conceptually means:

```text
Your identity is known, but you are not allowed to perform this operation.
```

Exact HTTP behavior depends on the service.

For non-HTTP systems, the same distinction still exists:

```text
Authentication:
Who are you?

Authorization:
Can you do this?
```

Now:

```text
   ↓

```

If that file remains after the stage, other steps may read it.

```text

   ↓

   ↓

```

# 122. Complete Training Jenkinsfile

```groovy
pipeline {
    agent any

    parameters {
        string(
            name: 'APP_VERSION',
            defaultValue: '1.0.0',
            description: 'Application version in major.minor.patch format'
        )
    }

    environment {
        APP_NAME = 'veriqta-api'
    }

    stages {
        stage('Validate') {
            steps {
                script {
                    if (!(params.APP_VERSION ==~ /^\d+\.\d+\.\d+$/)) {
                        error(
                            "Invalid APP_VERSION '${params.APP_VERSION}'. " +
                            "Expected major.minor.patch."
                        )
                    }
                }
            }
        }

        stage('Build') {
            steps {
                echo "Building ${env.APP_NAME} ${params.APP_VERSION}"

                sh '''
                    set -eu

                    mkdir -p dist

                    printf '%s\n' \
                        "Application: $APP_NAME" \
                        "Version: $APP_VERSION" \
                        "Build: $BUILD_NUMBER" \
                        > dist/build-info.txt
                '''
            }
        }

        stage('Test') {
            steps {
                sh '''
                    set -eu

                    test -f dist/build-info.txt
                    grep -q "$APP_NAME" dist/build-info.txt

                    echo "Tests passed."
                '''
            }
        }

        stage('Verify Secret Text Binding') {
            steps {
                withCredentials([
                    string(
                        credentialsId: 'veriqta-publish-token',
                        variable: 'PUBLISH_TOKEN'
                    )
                ]) {
                    sh '''
                        set +x
                        set -e

                        if [ -z "$PUBLISH_TOKEN" ]; then
                            echo "Publish credential was not injected."
                            exit 1
                        fi

                        echo "Publish credential is available."
                        echo "Simulating authenticated publish operation."
                    '''
                }
            }
        }

        stage('Verify Username Password Binding') {
            steps {
                withCredentials([
                    usernamePassword(
                        credentialsId: 'veriqta-registry-lab',
                        usernameVariable: 'REGISTRY_USER',
                        passwordVariable: 'REGISTRY_PASS'
                    )
                ]) {
                    sh '''
                        set +x
                        set -e

                        test -n "$REGISTRY_USER"
                        test -n "$REGISTRY_PASS"

                        echo "Registry credential is available."
                        echo "Simulating registry authentication."
                    '''
                }
            }
        }

        stage('Verify Artifact') {
            steps {
                sh '''
                    set -eu

                    echo "Artifact contents:"
                    cat dist/build-info.txt
                '''
            }
        }
    }

    post {
        always {
            echo 'Pipeline finished.'

            sh '''
                rm -f \
                    token.txt \
                    credentials.txt \
                    private-key.pem
            '''
        }

        success {
            echo 'Credential training pipeline succeeded.'
        }

        failure {
            echo 'Credential training pipeline failed. Review the failure without printing secrets.'
        }
    }
}
```

# 132. What You Should Never Commit

Do not commit files such as:

```text
.env
```

if they contain real secrets.

Also avoid committing:

```text
credentials.json
private-key.pem
id_rsa
production-password.txt
cloud-keys.txt
registry-password.txt
```

A filename alone does not make something secure.

---

# 133. `.gitignore` Is Helpful but Not a Secret Manager

You may add:

```text
.env
*.pem
credentials.json
```

to `.gitignore`.

That reduces accidental commits.

But `.gitignore` does not:

```text
encrypt files
remove previously committed secrets
rotate compromised credentials
protect files from local users
replace Jenkins Credentials
```

Treat it as one preventive control, not secret management.

# 134. What to Do if a Real Secret Is Committed

Do not merely delete the line and assume the problem is solved.

Treat the credential as potentially compromised.

General response:

```text
1. Revoke or rotate credential
2. Replace it with a new credential
3. Remove exposed material from active source
4. Assess repository/history exposure
5. Determine who or what could access it
6. Review logs and usage where available
7. Store replacement correctly
8. Verify affected systems
```

The first security action is often credential revocation/rotation, because history cleanup alone cannot prove nobody copied the old secret.

---

# 135. What to Do if a Secret Appears in Jenkins Console Output

Treat it seriously.

General process:

```text
Stop further exposure
      ↓
Determine which credential leaked
      ↓
Rotate/revoke it
      ↓
Correct Pipeline/tool logging
      ↓
Restrict access to affected logs
      ↓
Investigate exposure
      ↓
Verify replacement
```

Do not rely on deleting the build log as the only response.

Someone may already have copied the credential.

---

# 136. Secret Redaction Is Not Secret Prevention

There are two different security goals:

```text
Prevent secret from entering logs
```

and:

```text
Mask secret after it appears
```

The first is stronger.

Design Pipelines so sensitive values are never intentionally printed.

Use masking as defense in depth.

```text
Provider policy
```

# 138. Credential Revocation

Revocation means making a credential invalid before or regardless of its natural expiration.

Reasons include:

```text
Employee departure
Suspected compromise
Repository leak
Machine compromise
Permission redesign
Routine rotation
Lost private key
```

A mature credential strategy needs a revocation process.

# 141. Environment-Specific Credentials

You may eventually have:

```text

ssh-deploy-staging
ssh-deploy-production
```

This can prevent:

```text
development Pipeline
```

from automatically receiving:

```text

```

Environment separation reduces blast radius.

# 142. Do Not Dynamically Accept Arbitrary Credential IDs From Users

Be careful with designs such as:

```text
CREDENTIAL_ID = user-supplied-string
```

and then blindly binding whichever credential name the user enters.

That may undermine intentional credential separation.

Pipeline code should control which trusted credentials are available for which operations.

# 143. Secrets Should Not Control Pipeline Logic When Avoidable

Avoid designs where you inspect the secret itself:

```text
If password == X
then production
```

Credential material should authenticate.

Configuration and policy should determine Pipeline behavior.

Keep:

```text
Authentication
```

separate from:

```text
Business/deployment logic
```

# 145. Security Model

Secret text:


```groovy

environment {
```

```groovy
sh "command --token ${API_TOKEN}"
```

```bash
echo "$PASSWORD"
```

```bash
printenv
```

around sensitive environments unless there is a carefully controlled reason.
