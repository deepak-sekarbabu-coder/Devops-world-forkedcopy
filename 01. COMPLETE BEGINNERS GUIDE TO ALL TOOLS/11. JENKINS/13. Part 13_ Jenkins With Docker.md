# 1. Start With the Problem

Before Docker, a Jenkins agent might build an application directly on the host operating system.

For example:

```text
Jenkins Agent
│
├── Python
├── pip
├── Node.js
├── npm
├── Java
├── Maven
├── Gradle
├── system libraries
└── application dependencies
```

Pipeline:

```text
GitHub
   ↓
Jenkins
   ↓
Install dependencies on agent
   ↓
Build application
   ↓
Run tests
```

This works.

But imagine Jenkins supports ten applications.

Application A requires:

```text
Python 3.x
```

Application B requires:

```text
Java 21
```

Application C requires:

```text
Node.js
```

Application D requires:

```text
different system libraries
```

Soon the Jenkins agent becomes:

```text
Jenkins Agent
│
├── Java
├── Maven
├── Gradle
├── Python
├── pip
├── Node.js
├── npm
├── Go
├── Ruby
├── application libraries
├── test tools
├── compilers
└── many different versions
```

This creates several problems.

# 2. Build Environment Drift

Suppose your developer's computer has:

```text
Python version A
Library version B
Operating-system package C
```

but Jenkins has:

```text
Python version D
Library version E
Operating-system package F
```

The application may work locally but fail in CI.

You hear:

> "But it works on my machine."

The underlying issue may be environmental differences.

Docker helps package a more predictable application environment.

# 3. What Docker Adds

Instead of depending entirely on the Jenkins agent's application runtime environment:

```text
Jenkins Agent
   ↓
Host Python
   ↓

   ↓
Application
```

you can build:

```text
Jenkins Agent
   ↓
Docker
   ↓
Application Image
   ↓

```

The image describes the application environment.

That can include:

```text

Metadata
```

# 4. Why Jenkins and Docker Are Commonly Combined

Jenkins answers:

> When should automation execute, and what steps should happen?

Docker answers:

> In what container image/environment should an application or build workload run?

Together:

```text
Developer
   ↓
GitHub
   ↓
Jenkins
   ↓
Docker Build
   ↓
Versioned Image
   ↓
Container
   ↓
Test
```

Jenkins provides automation and orchestration.

Docker provides container building and runtime capabilities.

# 5. Jenkins Does Not Replace Docker

Jenkins does not itself create Linux containers.

Docker does.

Similarly:

```text
Jenkins
≠
Docker
```

Jenkins can execute:

```bash

docker run
docker inspect
docker logs
docker stop
docker rm
```

but those commands communicate with Docker.

# 8. What Is the Docker CLI?

When you type:

```bash
docker version
```

or:

```bash
docker build .
```

you are using the Docker command-line client.

The client accepts your command and communicates with a Docker daemon.

Conceptually:

```text
User / Jenkins
      ↓
Docker CLI
      ↓
Docker API
      ↓
Docker Daemon
```

---

# 9. What Is the Docker Daemon?

The Docker daemon is the background service responsible for Docker Engine operations such as:

```text
Building images
Creating containers
Starting containers
Stopping containers
Managing networks
Managing volumes
Managing image storage
```

On a typical Linux Docker Engine installation, the daemon process is:

```text
dockerd
```

The system service is commonly:

```text
docker.service
```

---

# 10. Docker Client vs Docker Daemon

This distinction matters.

Running:

```bash
docker --version
```

proves the CLI exists.

It does not necessarily prove the Docker daemon is reachable.

For example:

```bash
docker --version
```

might succeed while:

```bash
docker ps
```

fails.

Why?

Because:

```text
docker --version
```

can report client information locally.

But:

```text
docker ps
```

needs to communicate with a Docker daemon.

---

# 11. Verify Docker Properly

Use:

```bash
docker version
```

This attempts to show both client and server information.

Also use:

```bash
docker info
```

If the daemon is inaccessible, you may see an error similar to:

```text
Cannot connect to the Docker daemon
```

The exact wording can vary.

# 12. Where Should Docker Be Installed?

From Part 12, remember:

```text

```

Suppose your Pipeline uses:

```groovy

    label 'docker'
}
```

and Jenkins schedules it on:

```text

```

Then Docker capability must be available to that execution environment.

Installing Docker only on the Jenkins controller will not help a Pipeline running on a separate agent.

Architecture:

```text

      ↓

      ↓
Agent
Docker required here
      ↓
docker build
```

# 13. Do Not Turn the Controller Into the Docker Build Host

In Part 12, we separated build execution from the controller.

Do not immediately destroy that architecture by installing every build capability on the controller and running container builds there.

Prefer:

```text

Docker workloads
```

rather than:

```text

+

+
Application builds
+

Everything
```

for a production-oriented architecture.

# 19. Install Repository Prerequisites

Run:

```bash
sudo apt update
```

Then:

```bash
sudo apt install -y ca-certificates curl
```

Create the keyring directory:

```bash
sudo install -m 0755 -d /etc/apt/keyrings
```

---

# 20. Add Docker's Official Signing Key

Run:

```bash
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg \
  -o /etc/apt/keyrings/docker.asc
```

Then:

```bash
sudo chmod a+r /etc/apt/keyrings/docker.asc
```

What happened?

Docker's repository signing key was downloaded and stored in the system keyring directory so APT can verify packages from the repository.

---

# 21. Add Docker's APT Repository

Run:

```bash
sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
```

Then:

```bash
sudo apt update
```

Do not copy Ubuntu repository configuration onto Debian without modification. Docker provides separate Debian instructions.

# 26. The Permission Problem Jenkins Will Encounter

Your administrator account may successfully run:

```bash
sudo docker ps
```

But Jenkins builds normally do not interactively type:

```text
sudo password
```

Your Jenkins agent account might run:

```bash
docker ps
```

and receive:

```text
permission denied
```

or an error indicating it cannot connect to the Docker daemon socket.

This introduces an important question:

> How will the Jenkins agent receive permission to control Docker?

---

# 27. The Docker Socket

On a typical rootful Linux Docker installation, the local Docker daemon is commonly accessible through:

```text
/var/run/docker.sock
```

Inspect it:

```bash
ls -l /var/run/docker.sock
```

You may see something conceptually similar to:

```text
srw-rw---- root docker ... /var/run/docker.sock
```

Important:

```text
root
docker
```

typically represent ownership information.

Access to this socket is security-sensitive.

---

# 28. What Is a Unix Socket?

A Unix socket allows processes on the same system to communicate.

Conceptually:

```text
Docker CLI
    ↓
/var/run/docker.sock
    ↓
Docker Daemon
```

When Jenkins executes:

```bash
docker build .
```

the CLI communicates with the daemon through this interface unless another Docker host is configured.

---

# 29. Docker Socket Access Is Powerful

This is one of the most important security lessons in this entire part.

Do not think:

```text
Access to docker.sock
=
permission to build harmless containers
```

Docker daemon control is extremely powerful.

A user able to control a traditional rootful Docker daemon may be able to create containers with dangerous host access, including host filesystem mounts.

Therefore:

```text
Docker daemon access
```

should be treated as highly privileged access.

---

# 30. Why the Docker Group Is Security-Sensitive

Linux Docker installations commonly create a group named:

```text
docker
```

Giving a user membership in that group can allow that user to communicate with the rootful Docker daemon without `sudo`.

That is convenient.

It is also powerful.

Therefore:

```text
docker group
```

should not be treated as an ordinary harmless application group.

Only trusted accounts should receive Docker daemon access.

---

# 31. Lab Configuration: Give the Jenkins Agent Docker Access

For this controlled training environment, if you intentionally choose the standard rootful Docker model, add the dedicated Jenkins agent account to the Docker group:

```bash
sudo usermod -aG docker jenkins
```

Breakdown:

```text
usermod
→ modifies user account

-a
→ append

-G
→ supplementary groups

docker
→ target group

jenkins
→ user
```

The `-a` is important.

Do not casually remove a user's existing supplementary groups.

---

# 32. Group Changes Do Not Magically Affect Existing Processes

After changing group membership, an already-running Jenkins agent process may not inherit the new group membership.

That means:

```text
/etc/group changed
```

does not necessarily mean:

```text
existing agent process changed
```

You may need to restart/reconnect the agent process or session so it receives the new group membership.

---

# 33. Verify Group Membership

Run:

```bash
id jenkins
```

Look for:

```text
docker
```

among the groups.

You can also use:

```bash
getent group docker
```

Then test as the Jenkins account:

```bash
sudo -u jenkins docker version
```

Depending on how the process/session is launched, you may need to restart the Jenkins agent before the new group membership is reflected there.

# 34. Reconnect the Jenkins Agent


# 40. Dockerfile Fundamentals

Now Jenkins can access Docker.

Next, it needs instructions describing how to build the application image.

Those instructions normally live in:

```text
Dockerfile
```

A Dockerfile is a text file containing Docker build instructions.

Example:

```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .

RUN pip install --no-cache-dir -r requirements.txt

COPY . .

CMD ["python", "app.py"]
```

We will explain every instruction.

---

# 41. `FROM`

```dockerfile
FROM python:3.12-slim
```

`FROM` selects the base image.

Conceptually:

```text
Base Image
    ↓
Python runtime
    ↓
Your application layers
```

Instead of constructing an entire filesystem from nothing, your image starts from an existing base.

---

# 42. Avoid Floating Base Images for Reproducibility

You might see:

```dockerfile
FROM python:latest
```

This is convenient but less predictable.

`latest` can point to a different image in the future.

A better beginner approach is to choose an explicit runtime version, for example:

```dockerfile
FROM python:3.12-slim
```

For stronger production reproducibility, teams may pin even more precisely, including immutable image digests.

The principle is:

```text
Build today
≈
Build tomorrow
```

as much as reasonably possible.

---

# 43. `WORKDIR`

```dockerfile
WORKDIR /app
```

This establishes the working directory inside the image/container.

Later commands operate relative to:

```text
/app
```

when appropriate.

It is similar conceptually to:

```bash
cd /app
```

but it becomes part of the image configuration.

---

# 44. `COPY`

```dockerfile
COPY requirements.txt .
```

This copies:

```text
requirements.txt
```

from the Docker build context into the image's current working directory.

Later:

```dockerfile
COPY . .
```

copies files from the build context into the image.

This is where build context becomes critical.

---

# 45. `RUN`

```dockerfile
RUN pip install --no-cache-dir -r requirements.txt
```

`RUN` executes a command while building the image.

It creates image filesystem changes.

This happens during:

```bash
docker build
```

not every time the final application container starts.

---

# 46. `CMD`

```dockerfile
CMD ["python", "app.py"]
```

`CMD` provides the default command for containers created from the image.

Conceptually:

```text
docker run image
       ↓
Container starts
       ↓
python app.py
```

---

# 47. Dockerfile Build Time vs Container Runtime

This distinction is fundamental.

### Build time

Instructions such as:

```dockerfile
RUN ...
COPY ...
```

participate in constructing the image.

### Runtime

Instructions such as the final:

```dockerfile
CMD ...
```

help determine what executes when a container starts.

Do not confuse:

```text
building image
```

with:

```text
running container
```

---

# 48. Image vs Container

An **image** is a packaged, read-only template used to create containers.

A **container** is a running or stopped instance created from an image.

Mental model:

```text
Dockerfile
    ↓
docker build
    ↓
Image
    ↓
docker run
    ↓
Container
```

One image can create many containers.

# 49. Our Practical Application

We will build a tiny Python web application.

Project structure:

```text
veriqta-docker-app/
├── Jenkinsfile
├── Dockerfile
├── .dockerignore
├── app.py
├── requirements.txt
└── tests/
    └── test_app.py
```

---

# 50. `app.py`

Create:

```text
app.py
```

with:

```python
from flask import Flask, jsonify

app = Flask(__name__)


@app.get("/")
def home():
    return jsonify(
        application="veriqta-docker-app",
        status="running"
    )


@app.get("/health")
def health():
    return jsonify(status="healthy"), 200


if __name__ == "__main__":
    app.run(host="0.0.0.0", port=5000)
```

Important:

```python
host="0.0.0.0"
```

allows the application to listen on the container's network interfaces rather than only:

```text
127.0.0.1
```

inside the container.

---

# 51. `requirements.txt`

Create:

```text
requirements.txt
```

For a learning project, it may contain compatible versions of:

```text

pytest
```

For example, use versions you have tested for the repository rather than leaving production dependencies permanently unconstrained.

The important lesson is:

```text
Dependency versions
→ part of reproducibility
```

For a production application, dependency locking should be handled intentionally.

# 52. `tests/test_app.py`

Create:

```python
from app import app


def test_health_endpoint():
    client = app.test_client()

    response = client.get("/health")

    assert response.status_code == 200
    assert response.get_json()["status"] == "healthy"
```

This gives us an application test that can run inside the container image.

# 53. Dockerfile

Create:

```text
Dockerfile
```

with:

```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .

RUN pip install --no-cache-dir -r requirements.txt

COPY app.py .
COPY tests ./tests

CMD ["python", "app.py"]
```

The image now contains:

```text
Python
Flask
pytest
Application

```

For a more mature production design, build/test dependencies and runtime dependencies would often be separated so test tooling does not have to remain in the final runtime image.

We will introduce that idea later.

# 54. What Happens During the Build?

Docker processes the instructions roughly as:

```text
FROM python:3.12-slim
        ↓
Create base filesystem
        ↓
WORKDIR /app
        ↓
COPY requirements.txt
        ↓
RUN pip install
        ↓
COPY app.py
        ↓
COPY tests
        ↓
Set default CMD
        ↓
Final Image
```

Each build instruction contributes to the resulting image and build cache behavior.

# 55. Build Context

Consider:

```bash
docker build -t veriqta-docker-app:1.0 .
```

The final:

```text
.
```

is extremely important.

It represents the build context.

The context is the collection of files available to the Docker build.

---

# 56. Why Build Context Matters

Suppose your repository contains:

```text
project/
├── Dockerfile
├── app.py
├── requirements.txt
├── .git/
├── .venv/
├── secrets.txt
├── huge-backup.zip
└── test-output/
```

If your build context is:

```text
.
```

then unnecessary files may become part of the context unless excluded.

That can cause:

```text
Slower builds
Larger context transfers
Unnecessary cache invalidation
Potential exposure of sensitive files
```

---

# 57. `.dockerignore`

Create:

```text
.dockerignore
```

Example:

```text

.gitignore
.venv
__pycache__
*.pyc
.pytest_cache
build
dist
*.log
.env
.env.*
```

This tells Docker to exclude matching files from the build context.

---

# 58. `.dockerignore` Is Not `.gitignore`

They solve different problems.

```text
.gitignore
→ controls what Git normally tracks
```

```text
.dockerignore
```

# 85. Build Cache

Docker does not necessarily rebuild every layer from scratch.

It can reuse cached build results when the relevant inputs have not changed.

Suppose:

```dockerfile
COPY requirements.txt .

RUN pip install --no-cache-dir -r requirements.txt

COPY app.py .
```

If only:

```text
app.py
```

changes, Docker may be able to reuse the dependency-installation layer.

That can make builds significantly faster.

---

# 86. Dockerfile Order Affects Cache

Compare:

```dockerfile
COPY . .

RUN pip install --no-cache-dir -r requirements.txt
```

with:

```dockerfile
COPY requirements.txt .

RUN pip install --no-cache-dir -r requirements.txt

COPY app.py .
COPY tests ./tests
```

In the first version, changing almost any copied file can invalidate the earlier copy-dependent cache.

In the second, application changes may leave the dependency layer reusable if `requirements.txt` did not change.

Dockerfile structure affects CI performance.

---

# 87. Cache Is Not Correctness

Do not think:

```text
CACHED
=
Docker skipped something incorrectly
```

Build cache is designed to reuse valid previous build results.

But if your build depends on undeclared external state, cache behavior can expose poor build design.

A reproducible build should explicitly declare its important inputs.

---

# 88. Force a Clean Rebuild for Troubleshooting

When investigating cache-related behavior, you can use:

```bash

  -t veriqta-docker-app:test \
  .
```

Do not automatically use:

```text
--no-cache
```

for every CI build.

Doing so throws away useful build acceleration.

Use it deliberately.

# 101. Wait for Application Readiness

A container being:

```text
running
```

does not guarantee:

```text
application ready
```

The process may need time to start.

Do not rely only on:

```bash
sleep 30
```

A better CI pattern is bounded retry.

Example:

```bash
attempt=1

while [ "$attempt" -le 10 ]; do
    if curl --fail --silent \
        "http://127.0.0.1:$HOST_PORT/health"; then
        echo
        echo "Application is healthy."
        exit 0
    fi

    echo "Health check attempt $attempt failed."
    attempt=$((attempt + 1))
    sleep 2
done

echo "Application did not become healthy."
exit 1
```

---

# 102. Why Bounded Retry Is Better

Fixed sleep:

```text
sleep 30
```

always waits 30 seconds.

Even if application starts in one second.

It can also fail if the application needs 31 seconds.

Bounded health polling asks:

```text
Is the application ready now?
```

repeatedly until:

```text
success
```

or:

```text
timeout/failure
```

# 106. Cleanup With `post`

Declarative Pipeline gives us:

```groovy
post {
    always {
        ...
    }
}
```

This is useful because cleanup should happen whether the Pipeline:

```text
succeeds
fails
is otherwise completed
```

within the behavior supported by the Pipeline execution.

---

# 107. Safe Container Cleanup

Example:

```groovy
post {
    always {
        sh '''
            docker rm -f "veriqta-app-$BUILD_NUMBER" \
              >/dev/null 2>&1 || true
        '''
    }
}
```

Why:

```text
docker rm -f
```

stops/removes the named container if necessary.

Why:

```text
|| true
```

here?

Because cleanup should not fail merely because the container never existed.

This is one of the places where deliberately tolerating a cleanup command failure can be appropriate.

Do not apply:

```text
|| true
```

to your actual tests.

---

# 108. Bad Use of `|| true`

Bad:

```bash
pytest || true
```

This hides real test failures.

Bad:

```bash
docker build . || true
```

This can hide image-build failure.

Potentially appropriate cleanup:

```bash
docker rm -f "$CONTAINER_NAME" || true
```

because absence of the temporary container may be acceptable.

Context matters.

---

# 109. Image Cleanup Is Different

You may want to keep the image after CI because it is the output you plan to publish.

Do not automatically delete:

```text
$IMAGE_NAME:$BUILD_NUMBER
```

if Part 14 will push it to a registry.

For a disposable training environment, however, old images may consume significant disk space.

Inspect:

```bash
docker image ls
```

and:

```bash
docker system df
```

before deleting resources.

---

# 110. Do Not Blindly Run `docker system prune -a`

You will often see:

```bash
docker system prune -a
```

recommended online.

Do not blindly place this in Jenkins.

On a shared Docker host, it may remove resources used or cached by other workloads.

Cleanup should target resources owned by the build whenever possible.

Prefer:

```text

specific image tag
specific build-owned resources
```

over:

```text
delete everything unused
```

without understanding the host.

# 123. Workspace Behavior With Docker Pipeline


# 134. Final Jenkinsfile

```groovy
pipeline {
    agent {
        label 'linux && docker'
    }

    options {
        timestamps()
        disableConcurrentBuilds()
        timeout(time: 30, unit: 'MINUTES')
    }

    environment {
        IMAGE_NAME = 'veriqta-docker-app'
        CONTAINER_PREFIX = 'veriqta-app'
    }

    stages {
        stage('Environment Verification') {
            steps {
                sh '''
                    set -eu

                    echo "=== Jenkins Environment ==="
                    echo "Job: $JOB_NAME"
                    echo "Build: $BUILD_NUMBER"
                    echo "Node: $NODE_NAME"
                    echo "Workspace: $WORKSPACE"

                    echo
                    echo "=== Host ==="
                    hostname
                    whoami
                    id

                    echo
                    echo "=== Docker ==="
                    docker version
                '''
            }
        }

        stage('Source Verification') {
            steps {
                sh '''
                    set -eu

                    echo "=== Repository Files ==="
                    ls -la

                    test -f Dockerfile
                    test -f .dockerignore
                    test -f app.py
                    test -f requirements.txt
                    test -f tests/test_app.py

                    echo "Required project files are present."
                '''
            }
        }

        stage('Generate Image Metadata') {
            steps {
                script {
                    env.SHORT_SHA = sh(
                        script: 'git rev-parse --short=12 HEAD',
                        returnStdout: true
                    ).trim()

                    env.IMAGE_TAG = "${env.BUILD_NUMBER}-${env.SHORT_SHA}"
                    env.FULL_IMAGE = "${env.IMAGE_NAME}:${env.IMAGE_TAG}"
                    env.CONTAINER_NAME = "${env.CONTAINER_PREFIX}-${env.BUILD_NUMBER}"
                }

                echo "Image: ${env.FULL_IMAGE}"
                echo "Container: ${env.CONTAINER_NAME}"
            }
        }

        stage('Build Docker Image') {
            steps {
                sh '''
                    set -eu

                    echo "Building:"
                    echo "$FULL_IMAGE"

                    docker build \
                      -t "$FULL_IMAGE" \
                      .
                '''
            }
        }

        stage('Inspect Docker Image') {
            steps {
                sh '''
                    set -eu

                    echo "=== Image List ==="
                    docker image ls "$IMAGE_NAME"

                    echo
                    echo "=== Image ID ==="
                    docker image inspect \
                      --format '{{.Id}}' \
                      "$FULL_IMAGE"

                    echo
                    echo "=== Image History ==="
                    docker image history "$FULL_IMAGE"
                '''
            }
        }

        stage('Test Inside Container') {
            steps {
                sh '''
                    set -eu

                    docker run \
                      --rm \
                      "$FULL_IMAGE" \
                      pytest -v
                '''
            }
        }

        stage('Run Application Container') {
            steps {
                sh '''
                    set -eu

                    docker rm -f "$CONTAINER_NAME" \
                      >/dev/null 2>&1 || true

                    docker run \
                      --name "$CONTAINER_NAME" \
                      -d \
                      -p 5000 \
                      "$FULL_IMAGE"

                    echo "Started container:"
                    docker ps \
                      --filter "name=$CONTAINER_NAME"
                '''
            }
        }

        stage('Verify Application') {
            steps {
                sh '''
                    set -eu

                    HOST_PORT="$(
                      docker port "$CONTAINER_NAME" 5000/tcp \
                      | head -n 1 \
                      | awk -F: '{print $NF}'
                    )"

                    if [ -z "$HOST_PORT" ]; then
                        echo "ERROR: Could not determine published port."
                        docker logs "$CONTAINER_NAME" || true
                        exit 1
                    fi

                    echo "Application host port: $HOST_PORT"

                    attempt=1

                    while [ "$attempt" -le 15 ]; do
                        echo "Health check attempt: $attempt"

                        if curl \
                            --fail \
                            --silent \
                            --show-error \
                            "http://127.0.0.1:$HOST_PORT/health"; then

                            echo
                            echo "Application health check passed."
                            exit 0
                        fi

                        attempt=$((attempt + 1))
                        sleep 2
                    done

                    echo
                    echo "ERROR: Application did not become healthy."

                    echo
                    echo "=== Container State ==="
                    docker container inspect \
                      --format '{{.State.Status}}' \
                      "$CONTAINER_NAME" || true

                    echo
                    echo "=== Container Logs ==="
                    docker logs "$CONTAINER_NAME" || true

                    exit 1
                '''
            }
        }

        stage('Runtime Inspection') {
            steps {
                sh '''
                    set -eu

                    echo "=== Running Container ==="
                    docker ps \
                      --filter "name=$CONTAINER_NAME"

                    echo
                    echo "=== Container Image ==="
                    docker container inspect \
                      --format '{{.Config.Image}}' \
                      "$CONTAINER_NAME"

                    echo
                    echo "=== Container Status ==="
                    docker container inspect \
                      --format '{{.State.Status}}' \
                      "$CONTAINER_NAME"

                    echo
                    echo "=== Container Logs ==="
                    docker logs "$CONTAINER_NAME"
                '''
            }
        }
    }

    post {
        success {
            echo "Docker CI workflow completed successfully."
            echo "Validated image: ${env.FULL_IMAGE}"
        }

        failure {
            echo "Docker CI workflow failed."

            sh '''
                echo "=== Failure Diagnostics ==="

                if docker container inspect "$CONTAINER_NAME" \
                    >/dev/null 2>&1; then

                    echo
                    echo "Container state:"
                    docker container inspect \
                      --format '{{json .State}}' \
                      "$CONTAINER_NAME" || true

                    echo
                    echo "Container logs:"
                    docker logs "$CONTAINER_NAME" || true
                else
                    echo "Application container does not exist."
                fi
            '''
        }

        cleanup {
            sh '''
                echo "=== Container Cleanup ==="

                docker rm -f "$CONTAINER_NAME" \
                  >/dev/null 2>&1 || true

                echo "Temporary application container removed."
            '''
        }
    }
}
```

# 150. Security: Never Mount Sensitive Host Paths Casually

Docker can mount host directories into containers.

Example syntax:

```bash

```

Do not casually mount:

```text

 /etc
 /var/lib/jenkins
 Jenkins credentials
 SSH directories
 cloud credentials
```

into application build containers.

A container with write access to sensitive host paths may alter the host.

# 152. Security: Do Not Run Everything as Root Inside Containers

Our beginner image uses the base image defaults to keep the first project simple.

```dockerfile

```

The exact implementation depends on the base image and application.

The principle is:

```text

```

inside containers too.

# 187. Common Beginner Mistakes

## Mistake 1: Installing Docker on the wrong machine

Pipeline executes on agent, but Docker exists only on controller.

## Mistake 2: Assuming Docker CLI means daemon works

Always verify server connectivity.

## Mistake 3: Using `sudo docker` manually and assuming Jenkins can do the same

Jenkins needs a deliberate permission model.

## Mistake 4: Treating Docker group membership as harmless

It provides powerful daemon access in the traditional rootful model.

## Mistake 5: Running Docker workloads on the controller

This undermines controller isolation.

## Mistake 6: Using `latest` for everything

Traceability suffers.

## Mistake 7: Forgetting `.dockerignore`

Build context becomes unnecessarily large or sensitive.

## Mistake 8: Copying secrets into images

Images are distributable artifacts.

## Mistake 9: Assuming successful build means application works

Run and test the container.

## Mistake 10: Assuming running container means application is healthy

Perform application-level verification.

## Mistake 11: Forgetting cleanup

Agents accumulate stale containers.

## Mistake 12: Running global prune commands blindly

Shared resources/caches may be affected.

## Mistake 13: Hardcoding host port 5000 for concurrent CI builds

Port collisions can occur.

## Mistake 14: Giving untrusted PRs Docker daemon access

This can be a serious security risk.

## Mistake 15: Using `--privileged` to fix unexplained failures

Investigate the required permission instead.

## Mistake 16: Mounting `/var/run/docker.sock` without understanding it

It exposes powerful Docker daemon control.

## Mistake 17: Assuming images exist on every agent

Local images belong to the Docker daemon where they were built.

## Mistake 18: Ignoring disk usage

Docker CI can consume large amounts of storage.

## Mistake 19: Hiding test failures with `|| true`

Tests must be allowed to fail the Pipeline.

## Mistake 20: Deleting diagnostic evidence before reading logs

Capture evidence first, clean second.

```text
Validated Versioned Docker Image
```

But that image currently exists only on the Docker host where Jenkins built it.

That creates the next problem.

Suppose:

```text
Jenkins Agent 1
      ↓
Builds
veriqta-docker-app:81-a6d8f4c
```

and later:

```text
Deployment Server
```

needs that exact image.

The deployment server does not automatically have access to Agent 1's local Docker storage.

We need:

```text
Central Image Storage
```

That leads directly to Part 14.

Our architecture will become:

```text
Developer
   ↓
Git Push
   ↓
GitHub
   ↓
Jenkins
   ↓
Test
   ↓
Docker Build
   ↓
Versioned Image
   ↓
Container Registry
   ↓
Pull Exact Version
   ↓
Deployment
```

In **Part 14: Container Registries and Artifact Management**, we will learn how to turn a locally built Docker image into a securely stored, versioned, traceable, retrievable CI artifact.
