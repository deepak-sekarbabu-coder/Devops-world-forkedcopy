```text
↓

↓
```

By the end of Part 2, you should have:

# 1. What You Are Building

Our first lab is intentionally small.

We need only two logical systems:

```text
CONTROL NODE
     │
     │ SSH
     ↓
MANAGED NODE
```

The control node runs Ansible.

The managed node is the Linux system Ansible will manage.

For learning, those systems can exist in several ways.

# 6. macOS Considerations

macOS can also serve as an Ansible control node.

A typical development setup might include:

```text
macOS
↓
Python
↓
pipx / virtual environment / package manager
↓
Ansible
↓
Built-in SSH client
```

The exact Python and package-management setup can differ from Linux.

Do not assume commands for Ubuntu package management apply to macOS.

For example:

```bash
sudo apt install ...
```

is a Debian/Ubuntu command.

It is not a macOS command.

On macOS, Homebrew is commonly used for developer tooling, but Python-isolated installation methods such as `pipx` are also useful.

---

# 7. Windows Considerations

Native Windows is not the normal supported Ansible control-node environment.

That does NOT mean Windows users cannot learn Ansible.

A practical architecture is:

```text
Windows
↓
WSL
↓
Linux Distribution
↓
Ansible
```

WSL stands for:

```text
Windows Subsystem for Linux
```

It provides a Linux environment inside Windows.

For learning:

```text
Windows
↓
WSL Ubuntu
↓
Ansible
↓
SSH
↓
Linux Managed Node
```

works well.

Important production distinction:

WSL can be useful for learning and development, but do not automatically design a production Ansible control architecture around a developer's WSL installation.

Production automation deserves a controlled execution environment.

---

# 8. What Is WSL?

WSL allows Windows users to run a Linux environment without using a traditional full desktop virtual machine.

Conceptually:

```text
Windows
│
└── WSL
    │
    └── Ubuntu
        │
        ├── Bash
        ├── Python
        ├── SSH
        ├── Git
        └── Ansible
```

From Ansible's perspective, you are operating inside the Linux environment.

---

# 9. Do Not Mix Windows and WSL Paths Carelessly

Inside WSL, Linux paths look like:

```text
/home/anne/projects
```

Windows paths look like:

```text
C:\Users\Anne\Projects
```

WSL can expose Windows drives through locations such as:

```text
/mnt/c/
```

But for beginner Linux tooling, it is often simpler to keep the Ansible project inside the Linux filesystem:

```text
~/projects/ansible-lab
```

rather than mixing Windows and Linux filesystem semantics unnecessarily.

# 10. Python and Ansible

# 11. Check Python on the Control Node

Try:

```bash
python3 --version
```

Example output:

```text
Python 3.x.x
```

You can also find the executable:

```bash

```

Example:

```text

```

---

# 12. Why We Do Not Hardcode a Python Version Here

Ansible's supported Python versions change as Ansible releases change.

Therefore do not memorize:

```text
"Ansible always requires Python X.Y."
```

Instead learn the engineering habit:

```text
Choose Ansible version
↓
Check its support matrix
↓
Check control-node Python
↓
Check target-node Python
↓
Verify compatibility
```

That is safer than carrying an old version requirement into a new environment.

# 13. Python Package Installation Concepts

You will encounter several ways to install Python applications.

These include:

```text
Operating-system package manager

pip

pipx

Python virtual environment
```

They are related, but they are not identical.

---

# 14. What Is pip?

`pip` is Python's package installer.

Conceptually:

```text
Python
↓
pip
↓
Python Package
```

For example, Ansible documentation supports Python package installation workflows using `pip`.

However, installing Python applications directly into a system Python environment can create dependency conflicts or be blocked by modern distribution protections.

That is one reason isolated environments are valuable.

---

# 15. What Is a Python Virtual Environment?

A virtual environment creates an isolated Python environment for a project or purpose.

Instead of:

```text
System Python
├── Tool A dependencies
├── Tool B dependencies
└── Tool C dependencies
```

you can have:

```text
System Python
│
├── Environment A
│   └── Ansible dependencies
│
└── Environment B
    └── Other dependencies
```

This reduces dependency conflicts.

---

# 16. Create a Virtual Environment

On a Linux/macOS environment with suitable Python support:

```bash
python3 -m venv .venv
```

This creates:

```text
.venv/
```

Activate it:

```bash
source .venv/bin/activate
```

Your prompt may change.

You can verify:

```bash
which python
```

and:

```bash
python --version
```

Then install packages inside that environment.

For example:

```bash
python -m pip install --upgrade pip
```

---

# 17. Leaving the Virtual Environment

When finished:

```bash
deactivate
```

This returns your shell to the normal Python environment.

---

# 18. What Is pipx?

`pipx` is designed for installing Python command-line applications in isolated environments while exposing their commands conveniently.

Mental model:

```text
pip

"I need Python packages in this Python environment."
```

versus:

```text
pipx

"I need this Python CLI application installed in isolation."
```

For command-line applications such as Ansible, `pipx` can provide a clean installation model.

---

# 19. Why pipx Is Attractive for Ansible

Instead of placing Ansible and all of its Python dependencies into your system Python environment:

```text
System Python
↓
Ansible + dependencies
```

pipx can isolate the application:

```text
pipx
↓
Dedicated Environment
↓
Ansible
↓
Command exposed to your shell
```

This can reduce dependency conflicts.

# 21. Do Not Mix Installation Methods Randomly

A common beginner problem is:

```text
Install Ansible with apt
↓
Install another Ansible with pip
↓
Install another with pipx
↓
Shell executes unexpected one
```

Then:

```bash
ansible --version
```

does not show the version you expected.

Avoid this.

Choose an installation strategy deliberately.

---

# 22. `ansible-core` vs `ansible`

This distinction matters.

There are two names beginners commonly encounter:

```text
ansible-core
```

and:

```text
ansible
```

They are not simply two spellings for exactly the same package.

---

# 23. What Is `ansible-core`?

`ansible-core` provides the core Ansible language, runtime, command-line tools, and built-in functionality.

Think:

```text
ansible-core
│
├── Core CLI
├── Playbook engine
├── Core plugins
├── ansible.builtin
└── Core runtime
```

It is the smaller core package.

---

# 24. What Is the Community `ansible` Package?

The community `ansible` package includes:

```text
ansible-core
+
A curated set of community collections
```

Conceptually:

```text
ansible
│
├── ansible-core
│
└── Additional Collections
```

That means installing `ansible` generally gives you a broader collection of content than installing only `ansible-core`.

---

# 25. Why This Difference Matters

Imagine a tutorial uses:

```text
community.general.some_module
```

A learner with the full community `ansible` package may already have the relevant collection.

A learner with only:

```text
ansible-core
```

may need to install the collection separately.

Therefore:

```text
"My Ansible command exists"
```

does not necessarily mean:

```text
"I have every collection used by this project."
```

---

# 26. Which Should a Beginner Install?

For a broad learning environment, the community `ansible` package can be convenient because it includes `ansible-core` plus a set of collections.

For controlled production environments, teams often deliberately define:

```text
Ansible Core Version

Required Collections

Collection Versions

Python Dependencies
```

rather than relying on whatever happens to be installed globally.

For this first lab, either installation can teach the core concepts because:

```text
ansible.builtin.ping
```

belongs to `ansible-core`.

# 27. Installation Path A: pipx

First ensure `pipx` is installed using the appropriate method for your operating system.

Verify:

```bash

```

Then one possible installation is:

```bash

```

After installation, open a new shell if required and verify:


Read the message first.

# 28. Installation Path B: Python Virtual Environment

Create a project environment:

```bash
mkdir -p ~/projects/ansible-lab
cd ~/projects/ansible-lab
```

Create the environment:

```bash
python3 -m venv .venv
```

Activate it:

```bash
source .venv/bin/activate
```

```bash
python -m pip install --upgrade pip
```

```bash

```

Verify:

```bash

```

```bash

```

# 29. Installing Only `ansible-core`

If you deliberately want only the core package in an isolated Python environment:

```bash

```

Then verify:

```bash

```

Again, do not install both packages randomly simply because you see both names.

# 30. Installation Path C: Operating-System Package Manager

Ansible is also packaged by operating systems.

The exact command depends on your operating system and release.

For example, some Linux distributions provide packages named:

```text
ansible
```

and some may provide:

```text
ansible-core
```

The important production rule is:

> Use the installation instructions appropriate to your actual operating system and verify the resulting Ansible version.

Do not copy Ubuntu installation commands into Fedora.

Do not copy Fedora commands into macOS.

Do not assume package repositories all contain the same release.


# 59. SSH Keys

SSH public-key authentication uses a key pair:

```text
Private Key
+
Public Key
```

Conceptually:

```text
CONTROL NODE

Private Key
     │
     ↓
SSH Authentication
     │
     ↓
MANAGED NODE

Public Key authorized
```

The private key stays private.

Do not copy it onto random systems.

Do not commit it to Git.

---

# 60. Check Existing SSH Keys

Look inside:

```bash
ls -la ~/.ssh
```

You may already have keys.

Common filenames include:

```text
id_ed25519
id_ed25519.pub
```

but your environment may differ.

Do not overwrite an existing key blindly.

---

# 61. Create a Learning SSH Key

If you need a new key:

```bash
ssh-keygen -t ed25519
```

Follow the prompts.

For a dedicated lab, you can choose a descriptive filename.

For example:

```text
~/.ssh/ansible_lab
```

This can create:

```text
~/.ssh/ansible_lab
~/.ssh/ansible_lab.pub
```

The first is private.

The `.pub` file is public.

---

# 62. Private vs Public Key

Memorize this.

```text
ansible_lab
=
PRIVATE KEY
```

Protect it.

```text
ansible_lab.pub
=
PUBLIC KEY
```

This is the key that may be installed into the remote account's authorized keys.

Never post your private key in:

```text
GitHub

Slack

Email

Documentation

Screenshots

Tickets
```

---

# 63. Private-Key File Permissions

SSH is intentionally strict about private-key permissions.

On a Unix-like control node, a private key often needs restrictive permissions.

For example:

```bash
chmod 600 ~/.ssh/ansible_lab
```

This means conceptually:

```text
Owner → read/write
Others → no access
```

Depending on your setup, other restrictive modes may also be appropriate.

---

# 64. Why SSH Rejects Loose Permissions

Fix the permissions rather than disabling the protection.


```text

```

Use it when your environment requires explicit control.

# 77. Privilege Escalation

SSH access and administrator privileges are separate concepts.

You might connect as:

```text
deploy
```

but need elevated privileges to:

```text
Install packages

Modify /etc

Manage services

Create system users
```

On Linux, this often involves:

```text
sudo
```

Ansible calls its privilege-escalation system:

```text
become
```

---

# 78. SSH User vs Become User

Do not confuse:

```text
SSH user
```

with:

```text
Privilege-escalated user
```

Example:

```text
Ansible
↓
SSH as anne
↓
Managed Node
↓
sudo / become
↓
root privilege for required task
```

You do not necessarily need to SSH directly as root.

---

# 79. `sudo`

On many Linux systems:

```bash
sudo command
```

allows an authorized user to execute a command with elevated privileges.

Test on the managed node:

```bash
sudo -v
```

or a harmless command such as:

```bash
sudo whoami
```

Expected when properly authorized:

```text
root
```

Your system may ask for a password.

---

# 80. `become`

Ansible exposes privilege escalation through `become`.

From the CLI, you will later encounter:

```bash
-b
```

which means:

```text
--become
```

If a sudo password is required, you may encounter:

```bash
-K
```

which prompts for the become password.

Do not place privileged passwords directly into ordinary command history or plaintext files.

# 94. What `ansible.builtin.ping` Actually Does

This is important.

It is NOT the same as:

```bash
ping 192.0.2.50
```

The operating-system `ping` command normally tests ICMP network reachability.

Ansible's:

```text
ansible.builtin.ping
```

tests whether Ansible can successfully make the required connection and execute the module with usable Python support on a POSIX target.

On success it returns:

```text
pong
```

```text
lab01
```

```text
SUCCESS
```

```text

```

```text

```

No.


Did the test module execute successfully?

Yes.



# 137. Troubleshooting Table

| Symptom                      | Likely Area            | First Investigation                   |
| ---------------------------- | ---------------------- | ------------------------------------- |
| `ansible: command not found` | PATH/install           | `which ansible`                       |
| Wrong Ansible version        | Multiple installations | `which ansible`, `ansible --version`  |
| `python3: command not found` | Python                 | Check Python installation             |
| Inventory warning            | Inventory syntax/path  | `ansible-inventory --list`            |
| No hosts matched             | Host pattern/inventory | `--list-hosts`                        |
| Connection timeout           | Network/firewall       | Manual SSH/network path               |
| Connection refused           | SSH service/port       | Manual SSH                            |
| Permission denied publickey  | SSH auth               | User/key/authorized_keys              |
| Host key error               | SSH identity           | Verify target identity                |
| `UNREACHABLE`                | Connection stack       | Manual SSH                            |
| Python interpreter error     | Managed-node runtime   | Check remote Python                   |
| sudo failure                 | Privilege escalation   | Test `sudo` manually                  |
| Become password required     | sudo policy            | `-K` or secure credential strategy    |
| Module not found             | Package/collection     | `ansible-doc`, collection list        |
| Unexpected config            | Configuration source   | `ansible --version`, `ansible-config` |

# 162. Knowledge Check

## Question 1

What is the control node?

### Answer

The system on which Ansible is installed and from which Ansible automation is initiated.

---

## Question 2

Can macOS act as an Ansible control node?

### Answer

Yes, subject to the supported Ansible and Python requirements for the version being used.

---

## Question 3

Can native Windows normally act as the Ansible control node?

### Answer

Ansible does not natively run on Windows as a normal control node. Windows users can use environments such as WSL for learning and development.

---

## Question 4

What does WSL provide?

### Answer

A Linux environment running on Windows, allowing Linux tooling such as Python, SSH, Git, and Ansible to run there.

---

## Question 5

Why does Python matter on the control node?

### Answer

Ansible itself runs in a Python environment.

---

## Question 6

Why can Python matter on a Linux managed node?

### Answer

Many standard Ansible modules execute Python-based code on POSIX managed nodes.

---

## Question 7

Does Ansible normally need to be installed on the managed node?

### Answer

No.

---

## Question 8

What is `pip`?

### Answer

Python's package installer.

---

## Question 9

What is a Python virtual environment?

### Answer

An isolated Python environment that allows packages and dependencies to be installed without mixing them directly into another Python environment.

---

## Question 10

Why can `pipx` be useful?

### Answer

It installs Python command-line applications into isolated environments while exposing their CLI commands conveniently.

---

## Question 11

What is `ansible-core`?

### Answer

The core Ansible runtime, language, CLI tooling, built-in plugins, and built-in collection functionality.

---

## Question 12

What is the community `ansible` package?

### Answer

A broader package containing `ansible-core` together with a curated set of Ansible collections.

---

## Question 13

What does `ansible --version` tell you?

### Answer

It reports important runtime details including the Ansible core version, executable and module locations, configuration information, collection paths, and Python information.

---

## Question 14

What is `ansible-config` for?

### Answer

Inspecting and working with Ansible configuration.

---

## Question 15

What is `ansible-doc` for?

### Answer

Reading documentation for installed Ansible modules, plugins, and related content.

---

## Question 16

What is `ansible-galaxy` for?

### Answer

Working with reusable Ansible content such as collections and roles.

---

## Question 17

Why test SSH manually before Ansible?

### Answer

Because it isolates the connection layer. If SSH itself does not work, an Ansible connection that depends on SSH is unlikely to work.

---

## Question 18

What is the difference between an inventory alias and `ansible_host`?

### Answer

The alias is the name Ansible uses for the inventory host, while `ansible_host` can specify the actual network address used for the connection.

---

## Question 19

What does `ansible_user` specify?

### Answer

The remote account Ansible should use when connecting to that host.

---

## Question 20

What does `ansible_ssh_private_key_file` specify?

### Answer

The SSH private key Ansible should use for the relevant SSH connection.

---

## Question 21

What does `--list-hosts` do?

### Answer

It displays the hosts matched by a host pattern without executing a module against them.

---

## Question 22

Is `ansible.builtin.ping` an ICMP ping?

### Answer

No. It is an Ansible test module used to verify successful contact and usable module execution support, including Python for normal POSIX use.

---

## Question 23

What does `pong` mean?

### Answer

The Ansible ping module successfully executed and returned its expected result.

---

## Question 24

Why does `ansible.builtin.ping` normally report `changed: false`?

### Answer

Because the test does not need to alter the target's configuration.

---

## Question 25

What is `become`?

### Answer

Ansible's privilege-escalation mechanism.

---

## Question 26

Is the SSH user necessarily root?

### Answer

No. Ansible can connect using an ordinary account and elevate privileges for tasks that require them.

---

## Question 27

What does `-b` mean?

### Answer

Enable privilege escalation, or `--become`.

---

## Question 28

What does `-K` do?

### Answer

It prompts for the become password when one is required.

---

## Question 29

What should you investigate first when Ansible reports `UNREACHABLE`?

### Answer

The connection path: inventory, host/address, network, SSH, authentication, and related connection configuration.

---

## Question 30

Why should private SSH keys never be committed to Git?

### Answer

They are authentication secrets. Exposing them can allow unauthorized access to systems that trust the corresponding public key.
