# Part 8: Conditionals, Loops, Handlers, and Task Control

## Teach Ansible Logic Without Turning Playbooks Into Programming Chaos

In Part 7, you learned how Ansible receives and creates data:

```text
Inventory Data
+
Variables
+
Facts
+
Registered Results
↓
Playbook Logic
↓
Configuration
```

You learned how to answer questions such as:

```text
What environment is this?

What operating system is this?

What value belongs to this host?

What happened when the previous task ran?

What hosts belong to this group?
```

Now we need to use that information.

Consider these requirements:

```text
If the server is Debian-based
↓
Use the appropriate package workflow
```

```text
If monitoring is enabled
↓
Configure monitoring
```

```text
For every required package
↓
Ensure the package is installed
```

```text
If a configuration file changes
↓
Restart the service
```

```text
If deployment fails
↓
Run recovery tasks
```

```text
Only perform database migration once
↓
Do not run it independently on every application server
```

These are control-flow problems.

Ansible provides tools for them:

```text
when
loops
handlers
changed_when
failed_when
blocks
rescue
always
tags
delegation
run_once
serial
```

But there is an important engineering principle:

> A playbook should contain enough logic to express infrastructure behavior clearly, but not so much tangled logic that it becomes difficult to understand, test, and operate.

The goal of Part 8 is therefore not:

```text
Turn YAML into a programming language
```

The goal is:

```text
Data
↓
Simple Decision
↓
Predictable Task
↓
Observable Result
```

---

# 1. The Part 8 Mental Model

Your new model is:

```text
VARIABLES
+
FACTS
+
REGISTERED RESULTS
        │
        ↓
    CONDITIONS
        │
        ↓
   SHOULD TASK RUN?
     /         \
   YES          NO
    │            │
    ↓            ↓
 Execute       Skip
    │
    ↓
 Changed?
  /     \
YES      NO
 │        │
 ↓        ↓
Notify   Continue
Handler
 │
 ↓
Continue Play
 │
 ↓
Handler Executes
```

This is the foundation of dynamic Ansible automation.

---

# 2. Static Automation vs Conditional Automation

A static task says:

```text
Do this.
```

A conditional task says:

```text
Do this only when this condition is true.
```

A loop says:

```text
Do this for every item.
```

A handler says:

```text
Do this later, but only if a relevant task changed something.
```

A block says:

```text
Treat these related tasks as a logical unit.
```

A rescue section says:

```text
If a task in this block fails, perform recovery actions.
```

An always section says:

```text
Run these tasks regardless of whether the block succeeded or was rescued.
```

Together, these allow playbooks to respond intelligently to infrastructure state.

---

# 3. `when`

The primary Ansible conditional keyword is:

```yaml
when:
```

Example:

```yaml
- name: Display production message
  ansible.builtin.debug:
    msg: "This is a production server"
  when: app_environment == 'production'
```

Mental model:

```text
app_environment == production?
        │
    ┌───┴───┐
   YES      NO
    │        │
    ↓        ↓
 Execute    Skip
```

---

# 4. Important `when` Syntax Rule

Inside a normal templated value, you often write:

```yaml
msg: "{{ app_environment }}"
```

But a `when` expression is already interpreted as a conditional expression.

Write:

```yaml
when: app_environment == 'production'
```

not:

```yaml
when: "{{ app_environment == 'production' }}"
```

The same principle applies to expressions in:

```text
when

changed_when

failed_when
```

Do not unnecessarily wrap the entire expression in:

```text
{{ }}
```

# 5. First Conditional Lab

Create:

```text
playbooks/conditionals.yml
```

```yaml
---
- name: Learn Ansible conditions
  hosts: all
  gather_facts: false

  vars:
    app_environment: development

  tasks:
    - name: Display development message
      ansible.builtin.debug:
        msg: "Development configuration is active"
      when: app_environment == 'development'

    - name: Display production message
      ansible.builtin.debug:
        msg: "Production configuration is active"
      when: app_environment == 'production'
```

Run:

```bash
ansible-playbook \
  -i inventory/hosts.yml \
  playbooks/conditionals.yml
```

Expected conceptually:

```text
Development task
↓
OK

Production task
↓
SKIPPED
```

A skipped task is not necessarily a problem.

It can mean your conditional logic worked correctly.

# 6. Boolean Conditions

Suppose Part 7 defined:

```yaml
monitoring_enabled: true
```

You can use the Boolean directly:

```yaml
- name: Configure monitoring
  ansible.builtin.debug:
    msg: "Monitoring configuration would run here"
  when: monitoring_enabled
```

Meaning:

```text
monitoring_enabled == true?
↓
Run task
```

---

# 7. Testing for False

You can use:

```yaml
when: not monitoring_enabled
```

Example:

```yaml
- name: Report monitoring disabled
  ansible.builtin.debug:
    msg: "Monitoring is disabled"
  when: not monitoring_enabled
```

Mental model:

```text
monitoring_enabled
│
├── true
│   └── Configure monitoring
│
└── false
    └── Skip monitoring
```

---

# 8. Be Careful With Boolean Data Types

These are conceptually different:

```yaml
monitoring_enabled: true
```

and:

```yaml
monitoring_enabled: "true"
```

The first is a Boolean.

The second is a string.

Data types matter when writing conditions.

Do not fix conditional problems by randomly changing quotes.

Inspect the actual variable type and value.

---

# 9. Variable-Based Conditions

Variables can control execution.

Example:

```yaml
app_environment: production
```

Then:

```yaml
- name: Configure production settings
  ansible.builtin.debug:
    msg: "Applying production settings"
  when: app_environment == 'production'
```

Another example:

```yaml
worker_count: 8
```

```yaml
- name: Report high worker count
  ansible.builtin.debug:
    msg: "This server uses more than four workers"
  when: worker_count > 4
```

---

# 10. Comparison Operators

You will commonly encounter expressions such as:

```text
==
!=
>
<
>=
<=
```

Examples:

```yaml
when: app_environment == 'production'
```

```yaml
when: app_environment != 'development'
```

```yaml
when: worker_count >= 4
```

Keep conditions readable.

If the reader needs several minutes to understand one `when` expression, consider simplifying the design.

---

# 11. Fact-Based Conditions

Facts from Part 7 can drive decisions.

Example:

```yaml
- name: Report Debian-family host
  ansible.builtin.debug:
    msg: "This host belongs to the Debian OS family"
  when: ansible_facts['os_family'] == 'Debian'
```

Or:

```yaml
- name: Report Red Hat-family host
  ansible.builtin.debug:
    msg: "This host belongs to the Red Hat OS family"
  when: ansible_facts['os_family'] == 'RedHat'
```

---

# 12. Fact-Based Automation

Conceptually:

```text
Gather Facts
↓
Inspect OS Family
↓
Debian?
├── Yes → Debian-family behavior
└── No
     ↓
RedHat?
├── Yes → Red Hat-family behavior
└── No → Other behavior
```

This makes automation adaptable.

---

# 13. Do Not Guess Fact Values

Do not assume:

```text
Ubuntu
```

is the value of:

```text
ansible_facts['os_family']
```

Ubuntu systems commonly belong to the:

```text
Debian
```

OS family.

Inspect your actual facts:

```bash
ansible all \
  -i inventory/hosts.yml \
  -m ansible.builtin.setup \
  -a 'filter=ansible_os_family'
```

Then write the condition from observed data.

---

# 14. Distribution-Specific Conditions

Sometimes OS family is too broad.

You may need:

```yaml
when: ansible_facts['distribution'] == 'Ubuntu'
```

or another actual distribution value discovered from your hosts.

Choose the level appropriate to the task.

Use:

```text
OS family
```

when behavior applies broadly.

Use:

```text
Distribution
```

when behavior genuinely differs by distribution.

---

# 15. Registered-Result Conditions

Part 7 introduced:

```yaml
register:
```

Now registered results become inputs to decisions.

Example:

```yaml
- name: Check whether application directory exists
  ansible.builtin.stat:
    path: /opt/veriqta
  register: app_directory

- name: Report existing application directory
  ansible.builtin.debug:
    msg: "Application directory exists"
  when: app_directory.stat.exists
```

Mental model:

```text
Inspect System
↓
Register Result
↓
Evaluate Result
↓
Condition True?
↓
Execute Task
```

---

# 16. Conditions Based on Return Codes

Suppose:

```yaml
- name: Run application health command
  ansible.builtin.command:
    cmd: /opt/veriqta/bin/healthcheck
  register: health_result
  changed_when: false
  failed_when: false
```

A later task might inspect:

```yaml
- name: Report healthy application
  ansible.builtin.debug:
    msg: "Application health command succeeded"
  when: health_result.rc == 0
```

Another:

```yaml
- name: Report unhealthy application
  ansible.builtin.debug:
    msg: "Application health command did not succeed"
  when: health_result.rc != 0
```

Do not use this pattern blindly.

Understand the command's documented exit-code semantics.

---

# 17. Multiple Conditions

Sometimes several facts must all be true.

Example:

```text
Production
AND
Monitoring enabled
```

You can write:

```yaml
when:
  - app_environment == 'production'
  - monitoring_enabled
```

Multiple entries in a normal `when` list are effectively combined with:

```text
AND
```

Meaning:

```text
Condition 1
AND
Condition 2
↓
Both Must Be True
```

---

# 18. `and`

You can also explicitly use:

```text
and
```

Example:

```yaml
when: app_environment == 'production' and monitoring_enabled
```

This is useful for compact conditions.

But readability matters.

For several independent requirements, a list is often easier to read:

```yaml
when:
  - app_environment == 'production'
  - monitoring_enabled
  - worker_count >= 4
```

---

# 19. `or`

Use:

```text
or
```

when either condition is sufficient.

Example:

```yaml
when: app_environment == 'staging' or app_environment == 'production'
```

Meaning:

```text
Staging?
   OR
Production?
↓
Run
```

---

# 20. Membership Tests

When checking several acceptable values, this can be easier to read:

```yaml
when: app_environment in ['staging', 'production']
```

Instead of:

```yaml
when: app_environment == 'staging' or app_environment == 'production'
```

Choose the expression that communicates the requirement most clearly.

---

# 21. `not`

Use:

```text
not
```

to invert a Boolean condition.

Example:

```yaml
when: not maintenance_mode
```

Meaning:

```text
maintenance_mode is false
↓
Run
```

You may also encounter:

```yaml
when: app_environment != 'production'
```

Use whichever expresses the intent clearly.

---

# 22. Parentheses

Complex Boolean expressions can become ambiguous to human readers.

Instead of:

```yaml
when: production_mode and monitoring_enabled or emergency_mode
```

write something clearer, such as:

```yaml
when: (production_mode and monitoring_enabled) or emergency_mode
```

Better still, ask whether the logic should be simplified.

Infrastructure automation should be easy to review under pressure.

---

# 23. Defined Checks

Sometimes a variable is optional.

Use:

```yaml
when: support_contact is defined
```

Example:

```yaml
- name: Display support contact
  ansible.builtin.debug:
    msg: "{{ support_contact }}"
  when: support_contact is defined
```

This prevents attempting to use the variable when it does not exist.

---

# 24. Undefined Checks

You can test the opposite:

```yaml
when: support_contact is undefined
```

Example:

```yaml
- name: Warn when support contact is missing
  ansible.builtin.debug:
    msg: "No support contact is configured"
  when: support_contact is undefined
```

---

# 25. Defined Does Not Mean Valid

This:

```yaml
support_contact: ""
```

means the variable is defined.

But its value is an empty string.

Therefore:

```text
Defined
≠
Correct
≠
Non-empty
≠
Safe
```

Validation should match your actual requirement.

# 27. What Is a Loop?

Suppose you need these packages:

```text
git
curl
unzip
```

You could write:

```yaml
- name: Install git
  ansible.builtin.package:
    name: git
    state: present

- name: Install curl
  ansible.builtin.package:
    name: curl
    state: present

- name: Install unzip
  ansible.builtin.package:
    name: unzip
    state: present
```

That repeats the same logic.

A loop allows:

```text
One Task
↓
Many Data Items
```

---

# 28. `loop`

Example:

```yaml
- name: Install required packages
  ansible.builtin.package:
    name: "{{ item }}"
    state: present
  loop:
    - git
    - curl
    - unzip
```

Ansible conceptually performs:

```text
item = git
↓
Run task

item = curl
↓
Run task

item = unzip
↓
Run task
```

---

# 29. The Default Loop Variable: `item`

Inside a normal loop:

```text
item
```

represents the current loop element.

Example:

```yaml
- name: Display package
  ansible.builtin.debug:
    msg: "Current package is {{ item }}"
  loop:
    - git
    - curl
    - unzip
```

Expected conceptually:

```text
Current package is git
Current package is curl
Current package is unzip
```

---

# 30. Looping Over a Variable

Part 7 defined lists such as:

```yaml
required_packages:
  - git
  - curl
  - unzip
```

Use:

```yaml
- name: Install required packages
  ansible.builtin.package:
    name: "{{ item }}"
    state: present
  loop: "{{ required_packages }}"
```

Now:

```text
Configuration Data
↓
required_packages
↓
Loop
↓
package module
```

This separates data from automation logic.

---

# 31. Do Not Loop When the Module Accepts a List Efficiently

An important engineering nuance:

Some modules can accept an entire list directly.

For example, depending on the module and desired behavior:

```yaml
- name: Install required packages
  ansible.builtin.package:
    name: "{{ required_packages }}"
    state: present
```

may be preferable to calling the package module once per item.

Do not use loops simply because loops exist.

Ask:

> Does the module already accept the data structure I have?

---

# 32. Loop Variables

`item` works well for simple loops.

But this:

```yaml
msg: "{{ item }}"
```

becomes harder to understand in larger tasks.

You can define a more descriptive loop variable.

Example:

```yaml
- name: Display required packages
  ansible.builtin.debug:
    msg: "Package: {{ package_name }}"
  loop: "{{ required_packages }}"
  loop_control:
    loop_var: package_name
```

Now:

```text
package_name
```

clearly describes the current value.

---

# 33. Why Named Loop Variables Matter

Compare:

```yaml
path: "{{ item.path }}"
```

with:

```yaml
path: "{{ directory.path }}"
```

The second is easier to understand.

Good automation is written for humans first.

---

# 34. Looping Over Dictionaries in a List

Suppose:

```yaml
application_users:
  - name: deploy
    shell: /bin/bash
  - name: monitoring
    shell: /usr/sbin/nologin
```

Use:

```yaml
- name: Create application users
  ansible.builtin.user:
    name: "{{ item.name }}"
    shell: "{{ item.shell }}"
    state: present
  loop: "{{ application_users }}"
```

Each `item` is now a dictionary.

---

# 35. Structured Loop Mental Model

```text
application_users
│
├── Item 1
│   ├── name: deploy
│   └── shell: /bin/bash
│
└── Item 2
    ├── name: monitoring
    └── shell: /usr/sbin/nologin
```

During first iteration:

```text
item.name
↓
deploy
```

During second:

```text
item.name
↓
monitoring
```

---

# 36. Use a Named Variable for Structured Data

Better:

```yaml
- name: Create application users
  ansible.builtin.user:
    name: "{{ account.name }}"
    shell: "{{ account.shell }}"
    state: present
  loop: "{{ application_users }}"
  loop_control:
    loop_var: account
```

This reads naturally:

```text
For each account
↓
Create account.name
↓
Use account.shell
```

---

# 37. Dictionaries and Loops

Suppose your data is:

```yaml
service_ports:
  http: 80
  https: 443
  metrics: 9090
```

A dictionary is not naturally the same thing as a list of objects.

Ansible/Jinja provides ways to transform dictionary structures for iteration, such as `dict2items`.

Conceptually:

```text
Dictionary
↓
Convert to Items
↓
Loop
```

Example:

```yaml
- name: Display service ports
  ansible.builtin.debug:
    msg: "{{ item.key }} uses port {{ item.value }}"
  loop: "{{ service_ports | dict2items }}"
```

Expected:

```text
http uses port 80
https uses port 443
metrics uses port 9090
```

# 38. Conditional Loops

A condition can apply to each loop iteration.

Example:

```yaml
users:
  - name: deploy
    enabled: true
  - name: legacy
    enabled: false
  - name: monitoring
    enabled: true
```

Task:

```yaml
- name: Create enabled users
  ansible.builtin.user:
    name: "{{ account.name }}"
    state: present
  loop: "{{ users }}"
  loop_control:
    loop_var: account
  when: account.enabled
```

Mental model:

```text
deploy
↓
enabled?
↓
YES
↓
Create

legacy
↓
enabled?
↓
NO
↓
Skip
```

---

# 39. Conditions Are Evaluated Per Loop Item

This is important.

For:

```yaml
loop: "{{ users }}"
when: account.enabled
```

the condition is evaluated separately for each item.

Therefore one task may produce:

```text
changed
skipped
ok
changed
skipped
```

across different items.

---

# 40. Registered Loop Results

You can register the result of a loop.

Example:

```yaml
- name: Check application files
  ansible.builtin.stat:
    path: "{{ item }}"
  loop:
    - /etc/veriqta/app.conf
    - /opt/veriqta/app
    - /var/log/veriqta
  register: file_checks
```

Unlike a normal single-task result, a loop produces a collection of per-item results.

---

# 41. Inspect Registered Loop Results

Do not guess the structure.

Use:

```yaml
- name: Inspect loop results
  ansible.builtin.debug:
    var: file_checks
```

You will typically find a:

```text
results
```

collection containing information for each iteration.

Mental model:

```text
file_checks
└── results
    ├── result for item 1
    ├── result for item 2
    └── result for item 3
```

---

# 42. Loop Over Previous Loop Results

You can later process:

```yaml
file_checks.results
```

For example:

```yaml
- name: Display checked paths
  ansible.builtin.debug:
    msg: "Checked {{ item.item }}"
  loop: "{{ file_checks.results }}"
```

This looks strange at first:

```text
item.item
```

The outer `item` is the current result object.

The inner `.item` refers to the original loop input stored in that result.

Inspect the data before using it.

```text
playbooks/loops.yml
```

```yaml
---
- name: Learn loops

  gather_facts: false

    lab_directories:
```

```text
Loops

Idempotency
```

# 44. What Is a Handler?

A handler is a task designed to run when another task reports a change and notifies it.

Classic example:

```text
Configuration File Changes
↓
Restart Service
```

You do not want:

```text
Restart Service Every Playbook Run
```

You want:

```text
Restart Service Only When Required
```

That is what handlers solve.

---

# 45. First Handler

Example:

```yaml
tasks:
  - name: Deploy nginx configuration
    ansible.builtin.copy:
      src: nginx.conf
      dest: /etc/nginx/nginx.conf
      mode: "0644"
    notify: Restart nginx

handlers:
  - name: Restart nginx
    ansible.builtin.service:
      name: nginx
      state: restarted
```

Mental model:

```text
Copy Configuration
↓
Did Task Change?
├── NO → No Notification
└── YES
     ↓
Notify Restart nginx
     ↓
Continue Tasks
     ↓
Handler Runs
     ↓
nginx Restarts
```

---

# 46. `notify`

The keyword:

```yaml
notify:
```

tells Ansible which handler should be notified if the task reports:

```text
changed
```

Example:

```yaml
notify: Restart nginx
```

The name must correspond to the handler being notified.

---

# 47. A Handler Is Not Normally Executed Immediately

This is critical.

Imagine:

```text
Task 1
↓
Configuration Changed
↓
Handler Notified

Task 2
↓
Another configuration task

Task 3
↓
Verification preparation

End of task section
↓
Handler Runs
```

Handlers are normally deferred until the relevant handler execution point rather than running immediately after every notification.

This reduces unnecessary repeated restarts.

---

# 48. Why Deferred Execution Matters

Suppose five tasks update nginx configuration:

```text
Task A → changed → notify
Task B → changed → notify
Task C → ok
Task D → changed → notify
Task E → changed → notify
```

You do not want:

```text
Restart
Restart
Restart
Restart
```

You usually want:

```text
All Configuration Changes
↓
One Restart
```

Handlers provide this pattern.

---

# 49. Multiple Notifications of the Same Handler

If several tasks notify the same handler during the same handler cycle:

```text
Task A
↓
notify Restart nginx

Task B
↓
notify Restart nginx

Task C
↓
notify Restart nginx
```

the handler is normally executed once.

This is called deduplication.

---

# 50. Multiple Handlers From One Task

One changed task can notify multiple handlers.

Example:

```yaml
notify:
  - Restart application
  - Restart monitoring agent
```

Do not assume notification order controls execution order.

Handlers execute according to their handler-definition/insertion order, not simply the order in which they appear under `notify`.

---

# 51. Why Handlers Matter

Without handlers:

```yaml
- name: Deploy config
  ansible.builtin.copy:
    src: app.conf
    dest: /etc/veriqta/app.conf

- name: Restart application
  ansible.builtin.service:
    name: veriqta
    state: restarted
```

The restart task executes every time it is reached.

Even when the configuration did not change.

With a handler:

```text
Configuration Unchanged
↓
No Restart
```

```text
Configuration Changed
↓
Restart
```

This is much better operational behavior.

---

# 52. Service Restart Pattern

A common production pattern is:

```text
Template/Copy Configuration
↓
Changed?
↓
Notify Handler
↓
Finish Related Tasks
↓
Restart/Reload Service
```

For some services, a reload may be less disruptive than a restart.

Use the operation appropriate to the service and configuration change.

Do not automatically restart everything.

# 53. Handler Lab

Create:

```text
playbooks/handler-lab.yml
```

```yaml
---
- name: Learn handlers
  hosts: web
  become: true
  gather_facts: false

  tasks:
    - name: Deploy handler lab page
```

to:

---

# 54. Handlers Depend on `changed`

The key relationship is:

```text
Task Result
↓
changed = true?
↓
notify
↓
handler
```

Therefore incorrect changed reporting can cause incorrect handler behavior.

That leads directly to:

```text
changed_when
```

---

# 55. `changed_when`

Sometimes a module or command does not report change in the way your automation needs.

Ansible allows you to override the changed status using:

```yaml
changed_when:
```

Example:

```yaml
- name: Read application status
  ansible.builtin.command:
    cmd: /opt/veriqta/bin/status
  register: app_status
  changed_when: false
```

Why?

Because reading status does not modify the system.

---

# 56. Why `changed_when` Matters

Without correct changed reporting:

```text
Read-Only Command
↓
Reported Changed
↓
Misleading Play Recap
↓
Potential Handler Notification
```

Correct semantics should be:

```text
Read-Only Operation
↓
No State Change
↓
changed = false
```

Accurate change reporting improves:

```text
Idempotency visibility

Handler behavior

Auditing

CI/CD interpretation

Troubleshooting
```

---

# 57. Conditional `changed_when`

You can base change status on task results.

Example concept:

```yaml
- name: Run custom configuration tool
  ansible.builtin.command:
    cmd: /opt/veriqta/bin/configure
  register: configure_result
  changed_when: "'configuration updated' in configure_result.stdout"
```

Now:

```text
Output contains configuration updated?
├── YES → changed
└── NO → not changed
```

Only use output parsing when the tool's output contract is sufficiently reliable.

A purpose-built idempotent Ansible module is often preferable.

---

# 58. Multiple `changed_when` Conditions

A list of `changed_when` conditions is combined using implicit:

```text
AND
```

Example:

```yaml
changed_when:
  - configure_result.rc == 0
  - "'updated' in configure_result.stdout"
```

Both must be true.

If you require:

```text
Condition A OR Condition B
```

use an explicit expression with `or`.

---

# 59. `failed_when`

Just as you can define what counts as changed, you can define what counts as failure.

Example:

```yaml
- name: Run application validation
  ansible.builtin.command:
    cmd: /opt/veriqta/bin/validate
  register: validation_result
  changed_when: false
  failed_when: validation_result.rc != 0
```

This explicitly defines the failure condition.

---

# 60. Why `failed_when` Exists

Not every command uses:

```text
0 = success
everything else = failure
```

in a way that matches your automation requirements.

Some tools have meaningful non-zero exit codes.

Some commands may return zero but print evidence that should make your automation fail.

`failed_when` lets you express the real success contract.

---

# 61. Failure Based on Output

Example:

```yaml
- name: Validate application
  ansible.builtin.command:
    cmd: /opt/veriqta/bin/check
  register: validation_result
  changed_when: false
  failed_when: "'ERROR' in validation_result.stderr"
```

Now Ansible considers the task failed if the specified error text appears.

Do this only when you understand the command's documented behavior.

---

# 62. Multiple `failed_when` Conditions

This:

```yaml
failed_when:
  - validation_result.rc != 0
  - "'ERROR' in validation_result.stderr"
```

means:

```text
RC non-zero
AND
stderr contains ERROR
↓
Failure
```

It does **not** mean either condition independently causes failure.

---

# 63. `or` With `failed_when`

If either condition should cause failure:

```yaml
failed_when: validation_result.rc != 0 or 'ERROR' in validation_result.stderr
```

This distinction is important.

Do not accidentally weaken failure detection.

---

# 64. Never Hide Real Failures With `failed_when: false`

You may encounter:

```yaml
failed_when: false
```

This tells Ansible not to treat the task result as failed according to its normal result.

It can be useful when you deliberately want to inspect the result yourself.

But this pattern:

```yaml
failed_when: false
```

everywhere is dangerous.

You can convert genuine failures into apparently successful automation.

Use it only when subsequent logic intentionally evaluates the result.

---

# 65. `changed_when` and `failed_when` Mental Model

A task result contains two different questions:

```text
Did the task change the system?
```

and:

```text
Did the task succeed?
```

These are not the same.

A task can be:

```text
OK + Successful
```

```text
Changed + Successful
```

```text
Failed
```

Your conditions should represent reality.

---

# 66. What Is a Block?

A block groups related tasks.

Example:

```yaml
- name: Configure application
  block:
    - name: Create directory
      ansible.builtin.file:
        path: /opt/veriqta
        state: directory

    - name: Deploy configuration
      ansible.builtin.copy:
        src: app.conf
        dest: /opt/veriqta/app.conf
```

Think:

```text
BLOCK
│
├── Task
├── Task
└── Task
```

Blocks improve organization and allow shared directives and structured error handling.

---

# 67. Applying Conditions to Blocks

Suppose several tasks should run only in production.

Instead of repeating:

```yaml
when: app_environment == 'production'
```

on every task, you can apply it at block level.

Example:

```yaml
- name: Production configuration
  when: app_environment == 'production'
  block:
    - name: Configure production service
      ansible.builtin.debug:
        msg: "Configure service"

    - name: Configure production monitoring
      ansible.builtin.debug:
        msg: "Configure monitoring"
```

The directive is inherited by the tasks inside the block.

---

# 68. Block-Level Privilege Escalation

Similarly:

```yaml
- name: Privileged configuration
  become: true
  block:
    - name: Create system directory
      ansible.builtin.file:
        path: /opt/veriqta
        state: directory

    - name: Create configuration directory
      ansible.builtin.file:
        path: /etc/veriqta
        state: directory
```

This avoids unnecessary repetition.

---

# 69. Blocks Are Not Arbitrary Functions

Do not create enormous blocks containing unrelated work merely to make the YAML look organized.

Good:

```text
Application Deployment Block
```

Poor:

```text
Everything This Server Ever Needs Block
```

Blocks should express logical relationships.

---

# 70. Error Handling With Blocks

Blocks also support:

```text
block
rescue
always
```

Mental model:

```text
BLOCK
↓
Run Main Tasks
↓
Success?
├── YES
│    ↓
│  ALWAYS
│
└── NO
     ↓
   RESCUE
     ↓
   ALWAYS
```

This gives you controlled failure handling.

---

# 71. `rescue`

Example:

```yaml
- name: Deploy application safely
  block:
    - name: Deploy application
      ansible.builtin.command:
        cmd: /opt/veriqta/bin/deploy

  rescue:
    - name: Report deployment failure
      ansible.builtin.debug:
        msg: "Deployment failed. Recovery workflow started."
```

If a task in the block returns a failed state, Ansible can execute the rescue section.

---

# 72. `always`

Tasks under:

```yaml
always:
```

run after the block/rescue flow.

Example:

```yaml
- name: Deployment workflow
  block:
    - name: Deploy application
      ansible.builtin.command:
        cmd: /opt/veriqta/bin/deploy

  rescue:
    - name: Report failure
      ansible.builtin.debug:
        msg: "Deployment failed"

  always:
    - name: Record completion
      ansible.builtin.debug:
        msg: "Deployment attempt completed"
```

---

# 73. Real Error-Handling Pattern

Think:

```text
Enter Deployment
↓
Attempt Change
↓
Verify Change
↓
SUCCESS?
├── YES
│   ↓
│ Continue
│
└── NO
    ↓
  Rescue
    ↓
Collect Evidence
    ↓
Recover/Roll Back Where Safe
    ↓
Report Failure
```

Then:

```text
Always
↓
Cleanup Temporary State
```

This is more useful than blindly ignoring failures.

---

# 74. Important Block Limitation

Not every problem behaves like a rescuable task failure.

For example, invalid task definitions and unreachable hosts are not simply converted into normal `rescue` execution.

Therefore:

```text
block/rescue
≠
catch absolutely everything
```

Understand what kind of failure occurred.

---

# 75. `ignore_errors`

Ansible provides:

```yaml
ignore_errors: true
```

Example:

```yaml
- name: Run optional check
  ansible.builtin.command:
    cmd: /opt/veriqta/bin/optional-check
  ignore_errors: true
```

If the task returns a normal failed result, Ansible can continue instead of stopping further task execution for that host.

---

# 76. Why `ignore_errors` Is Dangerous

Consider:

```text
Deploy Application
↓
FAILED
↓
ignore_errors: true
↓
Continue
↓
Report Deployment Successful
```

That is not resilience.

That is hiding failure.

Careless `ignore_errors` can produce:

```text
Partial configuration

Broken deployments

Misleading CI results

Incorrect verification

Unnoticed security failures

Harder incidents
```

---

# 77. `ignore_errors` Does Not Ignore Everything

It does not mean:

```text
Ignore every possible problem.
```

For example, it does not magically solve:

```text
Undefined variables

Syntax errors

Connection/unreachable problems

Certain execution problems
```

Treat it as a narrow execution-control tool, not a universal error suppressor.

---

# 78. Better Than Blind Error Ignoring

Instead of:

```yaml
ignore_errors: true
```

ask:

```text
Why can this task fail?

Which failures are acceptable?

Which failures are dangerous?

Should I inspect rc?

Should I use failed_when?

Should I use block/rescue?

Should I verify the final state?
```

Make failure semantics explicit.

---

# 79. Error-Handling Lab

Create:

```text
playbooks/error-handling.yml
```

```yaml
---
- name: Learn structured error handling
  hosts: all
  gather_facts: false

  tasks:
    - name: Demonstrate block rescue and always
      block:
        - name: Run successful task
          ansible.builtin.command:
            cmd: /bin/true
          changed_when: false

        - name: Force controlled failure
          ansible.builtin.command:
            cmd: /bin/false
          changed_when: false

        - name: This task should not run
          ansible.builtin.debug:
            msg: "You should not see this from the main block"

      rescue:
        - name: Report rescued failure
          ansible.builtin.debug:
            msg: "The block failed and rescue is running"

      always:
        - name: Report finalization
          ansible.builtin.debug:
            msg: "The always section is running"
```

Run it.

Observe execution order.

# 80. What Are Tags?

Tags allow you to label tasks, blocks, roles, or plays for selective execution.

Suppose a playbook contains:

```text
Packages
Configuration
Application Deployment
Monitoring
Verification
```

Sometimes you want only:

```text
Verification
```

Tags can help.

---

# 81. First Tag

Example:

```yaml
- name: Verify web service
  ansible.builtin.uri:
    url: http://127.0.0.1/
    status_code: 200
  tags:
    - verify
```

Run:

```bash
ansible-playbook \
  -i inventory/hosts.yml \
  playbooks/site.yml \
  --tags verify
```

This selects tagged work according to Ansible's tag behavior.

---

# 82. Multiple Tags

Example:

```yaml
tags:
  - web
  - configuration
```

A task can belong to several logical categories.

Useful categories might include:

```text
packages

configuration

deploy

security

monitoring

verify
```

Keep tag naming predictable.

---

# 83. `--skip-tags`

You can exclude tagged tasks.

Example:

```bash
ansible-playbook \
  -i inventory/hosts.yml \
  playbooks/site.yml \
  --skip-tags monitoring
```

This can be useful when intentionally omitting a category of work.

But be careful with task dependencies.

---

# 84. Tags Can Break Workflow Assumptions

Suppose:

```text
Task A
↓
Creates configuration

Task B
↓
Uses configuration

Task C
↓
Verifies configuration
```

If tagging allows someone to run:

```text
Task C
```

without prerequisites, verification may fail or become meaningless.

Selective execution is powerful.

Design tasks so their assumptions are understood.

---

# 85. Useful Tag Inspection

Before selective execution, inspect available tags.

For example:

```bash
ansible-playbook \
  -i inventory/hosts.yml \
  playbooks/site.yml \
  --list-tags
```

You can also inspect tasks:

```bash
ansible-playbook \
  -i inventory/hosts.yml \
  playbooks/site.yml \
  --list-tasks
```

Use inspection before production execution.

---

# 86. Tags Are Not Environment Isolation

Do not use:

```text
--tags production
```

as your primary mechanism for deciding which hosts are production.

Inventory determines infrastructure targeting.

Tags select categories of automation.

Keep those concepts separate:

```text
Inventory
↓
WHERE
```

```text
Tags
↓
WHAT
```

---

# 87. Delegation Introduction

Normally:

```text
Play targets web01
↓
Task executes against web01
```

Sometimes the task logically belongs elsewhere.

Example:

```text
Deploy web01
↓
Remove web01 from load balancer
```

The load-balancer action may need to execute:

```text
on localhost
```

or:

```text
on a load-balancer management host
```

This is where delegation enters.

---

# 88. `delegate_to`

Example:

```yaml
- name: Perform controller-side deployment action
  ansible.builtin.command:
    cmd: /usr/local/bin/update-load-balancer "{{ inventory_hostname }}"
  delegate_to: localhost
```

Conceptually:

```text
Current Play Host
↓
web01

Task Context
↓
web01

Execution Location
↓
localhost
```

Delegation changes where the action runs.

---

# 89. Real Delegation Pattern

A rolling deployment may eventually resemble:

```text
web01
↓
Delegate to Load Balancer
↓
Remove web01
↓
Update web01
↓
Verify web01
↓
Delegate to Load Balancer
↓
Return web01
```

Then repeat for:

```text
web02
web03
...
```

You will build this properly in Part 16.

For now, understand the concept.

---

# 90. Delegation Is Not Automatically Serialized

This is an important production warning.

Suppose 20 web hosts all run a task:

```yaml
delegate_to: localhost
```

That does not automatically mean:

```text
one at a time
```

Multiple hosts can still cause delegated work to execute concurrently.

This matters when multiple tasks modify the same shared resource.

Concurrency must be designed deliberately.

---

# 91. What Is `run_once`?

Normally:

```text
10 Hosts
↓
Task Executes 10 Times
```

Sometimes you need:

```text
10 Hosts
↓
Task Executes Once
```

Use:

```yaml
run_once: true
```

Example:

```yaml
- name: Perform one-time database migration
  ansible.builtin.command:
    cmd: /opt/veriqta/bin/migrate
  run_once: true
```

---

# 92. `run_once` Mental Model

Without:

```text
web01 → migrate
web02 → migrate
web03 → migrate
```

With:

```text
One selected host
↓
migrate
```

This is useful for tasks that should not run independently on every host.

---

# 93. Do Not Assume `run_once` Means a Specific Host

`run_once: true` does not mean:

```text
Always run on web01.
```

It causes the task to execute for the first available host in the relevant batch.

If execution must happen on a specific machine, combine the design with appropriate delegation or explicit targeting.

---

# 94. `run_once` and Registered Results

A `run_once` task can produce results that Ansible applies to hosts in the active batch.

This can surprise beginners.

Do not treat:

```text
run_once
```

as merely:

```text
skip all other hosts
```

It has execution-context implications.

---

# 95. `run_once` and `serial`

This is a particularly important nuance.

Suppose:

```yaml
serial: 2
```

and there are six hosts.

Ansible processes:

```text
Batch 1
2 hosts

Batch 2
2 hosts

Batch 3
2 hosts
```

A task using:

```yaml
run_once: true
```

can run once **per serial batch**, not necessarily once for the entire play.

Remember this before using `run_once` for something such as a database migration.

---

# 96. What Is Serial Execution?

By default, Ansible can operate against multiple hosts in parallel according to its strategy and fork configuration.

For deployments, you may not want to update every server simultaneously.

Example:

```yaml
- name: Rolling web deployment
  hosts: web
  serial: 2
```

Meaning:

```text
Web Servers
↓
Process 2
↓
Complete Play for Batch
↓
Next 2
↓
Complete Play
↓
Continue
```

---

# 97. Why `serial` Matters

Imagine:

```text
10 production web servers
```

Updating all 10 simultaneously could remove all serving capacity.

Instead:

```text
Batch 1
web01
web02
↓
Update
↓
Verify

Batch 2
web03
web04
↓
Update
↓
Verify
```

This is the beginning of rolling deployment design.

---

# 98. `serial` Is Not a Complete Deployment Strategy

Simply adding:

```yaml
serial: 1
```

does not automatically create a safe production rollout.

You still need to consider:

```text
Load balancer membership

Health checks

Capacity

Session behavior

Database compatibility

Application startup time

Failure thresholds

Rollback

Monitoring

Traffic recovery
```

`serial` controls batch size.

It does not solve every deployment problem.

---

# 99. Combining Delegation and Serial Execution

A future production pattern may be:

```yaml
- name: Rolling deployment
  hosts: web
  serial: 1

  tasks:
    - name: Remove host from load balancer
      ansible.builtin.command:
        cmd: "/usr/local/bin/remove-host {{ inventory_hostname }}"
      delegate_to: localhost

    - name: Deploy application
      ansible.builtin.debug:
        msg: "Deployment would happen here"

    - name: Verify application
      ansible.builtin.debug:
        msg: "Verification would happen here"

    - name: Return host to load balancer
      ansible.builtin.command:
        cmd: "/usr/local/bin/add-host {{ inventory_hostname }}"
      delegate_to: localhost
```

Do not copy this into production as-is.

It is an architecture example.

Real load-balancer operations should use appropriate supported APIs/modules and proper verification.

---

# 100. Combining Conditions and Loops

Now we can combine concepts.

Data:

```yaml
application_users:
  - name: deploy
    enabled: true
    shell: /bin/bash

  - name: oldservice
    enabled: false
    shell: /usr/sbin/nologin

  - name: monitoring
    enabled: true
    shell: /usr/sbin/nologin
```

Task:

```yaml
- name: Create enabled application accounts
  ansible.builtin.user:
    name: "{{ account.name }}"
    shell: "{{ account.shell }}"
    state: present
  loop: "{{ application_users }}"
  loop_control:
    loop_var: account
  when: account.enabled
```

Now you have:

```text
Structured Data
↓
Loop
↓
Condition
↓
Task
```

---

# 101. Combining Conditions and Registered Results

Example:

```yaml
- name: Check application directory
  ansible.builtin.stat:
    path: /opt/veriqta
  register: app_dir

- name: Report application installation
  ansible.builtin.debug:
    msg: "Application directory exists"
  when: app_dir.stat.exists

- name: Report application missing
  ansible.builtin.debug:
    msg: "Application directory does not exist"
  when: not app_dir.stat.exists
```

Now runtime evidence controls later execution.

---

# 102. Combining Conditions and Handlers

Example:

```yaml
- name: Deploy production configuration
  ansible.builtin.template:
    src: app.conf.j2
    dest: /etc/veriqta/app.conf
    mode: "0644"
  when: app_environment == 'production'
  notify: Restart application
```

Flow:

```text
Production?
↓
YES
↓
Template Runs
↓
Changed?
↓
YES
↓
Notify
↓
Restart Later
```

---

# 103. Combining Loops and Handlers

A looped task can notify a handler.

Example:

```yaml
- name: Deploy configuration fragments
  ansible.builtin.copy:
    src: "{{ config_file }}"
    dest: "/etc/veriqta/{{ config_file }}"
  loop:
    - app.conf
    - logging.conf
    - monitoring.conf
  loop_control:
    loop_var: config_file
  notify: Restart application
```

If the looped task reports change because one or more iterations changed, the handler can be notified.

The service still does not need to restart once per changed file.

---

# 104. Handler Timing and Failures

Consider:

```text
Configuration Changed
↓
Handler Notified
↓
Later Task Fails
```

By default, a notified handler may not run on a host where a later task failure prevents normal completion for that host.

That can create a difficult state:

```text
New Configuration Written
+
Old Service Process Still Running
```

Ansible provides mechanisms such as forced handlers for cases where this behavior must be changed.

But forcing handlers also has operational consequences.

Understand the failure path rather than enabling it blindly.

---

# 105. Flushing Handlers

Sometimes a handler must run before the normal handler execution point.

Ansible provides:

```yaml
- name: Flush handlers
  ansible.builtin.meta: flush_handlers
```

Conceptually:

```text
Change Configuration
↓
Notify Handler
↓
Flush Handlers
↓
Handler Executes Now
↓
Continue
```

Use this only when later tasks genuinely require the handler's effect.

---

# 106. Example Flush Pattern

```yaml
- name: Deploy service configuration
  ansible.builtin.template:
    src: app.conf.j2
    dest: /etc/veriqta/app.conf
  notify: Restart application

- name: Apply notified handlers now
  ansible.builtin.meta: flush_handlers

- name: Verify restarted application
  ansible.builtin.uri:
    url: http://127.0.0.1:8080/health
    status_code: 200
```

This can make sense when verification must happen after the new configuration has been activated.

---

# 107. The Danger of Excessive Logic

It is possible to write a playbook containing:

```text
Conditions inside loops

Loops over deeply nested dictionaries

Registered results

Nested blocks

Rescue blocks

Delegation

run_once

Many tags

Complex Boolean expressions
```

all inside one file.

Technically valid does not mean maintainable.

---

# 108. Keep Playbook Logic Understandable

Prefer:

```text
Simple Data
↓
Simple Condition
↓
Clear Task
```

over:

```text
Five Nested Structures
↓
Complex Filter Chain
↓
Six Boolean Conditions
↓
Dynamic Task Behavior
↓
Nobody Understands It During Incident
```

Automation is operational documentation.

Humans must be able to understand it.

---

# 109. When Logic Becomes Too Complex

Ask whether complexity should move into:

```text
Better variable design

Separate task files

Roles

Templates

Purpose-built modules

Different plays

Clearer inventory grouping

Application code
```

Ansible should orchestrate infrastructure clearly.

It should not become an accidental general-purpose application written in YAML.

---

# 110. Common Conditional Mistakes

Avoid:

```text
Using {{ }} around the entire when expression

Comparing Boolean values as strings

Guessing fact values

Using undefined variables without checking

Writing huge Boolean expressions

Using facts before gathering them

Assuming skipped means failed

Ignoring data types
```

---

# 111. Common Loop Mistakes

Avoid:

```text
Looping when module accepts a list directly

Using item everywhere in complex loops

Not inspecting registered loop results

Assuming every iteration changed

Creating deeply nested loops unnecessarily

Mixing unrelated operations into one loop

Using a loop to hide duplicated but semantically different tasks
```

---

# 112. Common Handler Mistakes

Avoid:

```text
Restarting services unconditionally

Notifying a handler from a task that falsely reports changed

Assuming handlers run immediately

Assuming handler notification order equals execution order

Creating many duplicate restart handlers

Using restart where reload is sufficient

Forgetting failure behavior before handler execution
```

---

# 113. Common Error-Handling Mistakes

Avoid:

```text
ignore_errors: true everywhere

failed_when: false everywhere

Calling failure handling a rollback when it is not

Suppressing errors without verification

Continuing after security-critical failures

Treating unreachable hosts as ordinary task failures

Assuming rescue catches every possible error
```

---

# 114. Common `run_once` Mistakes

Avoid assuming:

```text
run_once
=
exactly once forever
```

or:

```text
run_once
=
always web01
```

or:

```text
run_once + serial
=
once for entire play
```

Understand batches and execution context.

---

# 115. Common Delegation Mistakes

Avoid:

```text
Assuming delegated tasks are automatically serialized

Assuming variables always refer to the original host

Writing concurrently to one delegated file from many hosts

Delegating actions that cannot be delegated

Using localhost without understanding what credentials/tools it needs
```

# 126. Verification Block

```yaml

          register: web_health
          changed_when: false

        - name: Display successful HTTP status
          ansible.builtin.debug:

        - name: Report failed web verification
          ansible.builtin.debug:
            msg: "Web verification failed on {{ inventory_hostname }}"

        - name: Stop play for failed verification
          ansible.builtin.fail:
            msg: "Web server verification failed on {{ inventory_hostname }}"

      always:
        - name: Report verification completion
          ansible.builtin.debug:
            msg: "Verification attempt completed for {{ inventory_hostname }}"

      tags:
        - verify
```

# 140. `failed_when` Lab

Use a harmless command whose return code you understand.

Example:

```yaml
- name: Check whether nginx process is visible
  ansible.builtin.command:
    cmd: pgrep nginx
  register: nginx_process
  changed_when: false
  failed_when: nginx_process.rc not in [0, 1]
```

Here you deliberately define:

```text
0
↓
Process found

1
↓
Process not found

Other
↓
Unexpected command problem
```

Whether this is the right health check for a real production service is a separate question.

The lab teaches exit-code interpretation.

# 149. Handlers and Idempotency

Handlers work best when upstream tasks accurately understand state.

Ideal:

```text
Desired Configuration Already Present
↓
Task = OK
↓
No Notification
↓
No Restart
```

Change required:

```text
Desired Configuration Different
↓
Task = CHANGED
↓
Notify
↓
Restart Once
```

This is a major reason to prefer idempotent modules over arbitrary shell commands.

```yaml

    cmd: /opt/veriqta/configure
```

You must understand:

```text

Can an idempotent module replace it?

Can changed_when accurately describe the behavior?
```

Do not attach handlers blindly to arbitrary commands.

```text
Should this run?
↓
when
```

```text
For which items?
↓
loop
```

```text
Did anything actually change?
↓
changed_when
```

```text
Did the operation actually succeed?
↓
failed_when
```

```text
Did a change require a follow-up action?
↓
notify
↓
handler
```

```text
What happens when something fails?
↓
block
↓
rescue
↓
always
```

```text
Which category of automation should run?
↓
tags
```

```text
Where should this task execute?
↓

```

```text
↓
```
