# Part 6: Ansible Playbooks and Task Execution

## Move From Individual Commands to Repeatable Automation

In Part 5, you learned how to make Ansible perform individual operations.

You ran commands such as:

```bash
ansible web -i inventory/hosts.yml -m ansible.builtin.ping
```

and:

```bash
ansible web \
  -i inventory/hosts.yml \
  -b \
  -m ansible.builtin.package \
  -a 'name=nginx state=present'
```

You also learned the basic execution model:

```text
Engineer
↓
Ansible CLI
↓
Inventory
↓
Host Pattern
↓
Module
↓
Module Arguments
↓
Managed Host
↓
Result
```

That works well for:

* Quick investigations
* Connectivity tests
* Troubleshooting
* One-time operations
* Learning modules

But imagine configuring a web server properly.

You need to:

```text
Install Web Server
↓
Create Configuration
↓
Start Service
↓
Enable Service
↓
Deploy Web Page
↓
Verify HTTP Response
```

You could execute six separate ad hoc commands.

But tomorrow, another engineer needs to repeat the process.

Next week, you need to configure ten more servers.

Next month, the configuration changes.

Now questions appear:

```text
Which commands should run?

In what order?

Which hosts should receive them?

Which commands need root privileges?

What happens if one fails?

How do we review the automation?

How do we store it in Git?

How do we run exactly the same process again?
```

This is where playbooks become essential.

A playbook turns individual Ansible operations into structured, repeatable automation.

The Part 6 mental model is:

```text
Ad Hoc Commands
↓
Individual Operations
↓
Tasks
↓
Plays
↓
Playbook
↓
Repeatable Automation
```

By the end of this part, you will build your first real web-server playbook and understand exactly how Ansible executes it.

---

# 1. What Is an Ansible Playbook?

An Ansible playbook is a YAML file containing one or more plays that describe automation Ansible should execute.

A playbook can describe:

```text
Which hosts to target

Which operations to perform

What order to perform them

Whether privilege escalation is required

What desired state should exist

How configuration should be verified
```

For example:

```yaml
---
- name: Configure web servers
  hosts: web
  become: true

  tasks:
    - name: Install nginx
      ansible.builtin.package:
        name: nginx
        state: present

    - name: Start nginx
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true
```

This is no longer a collection of shell commands you need to remember.

It is automation stored as code.

---

# 2. Why Playbooks Matter

Suppose you manually configure a server.

You might write down:

```text
SSH to server

Install nginx

Create directory

Copy configuration

Start nginx

Enable nginx

Deploy website

Test website
```

But documentation alone does not perform those operations.

A playbook can encode them.

Instead of:

```text
Human reads instructions
↓
Human executes every step
↓
Human may make mistakes
```

you move toward:

```text
Engineer writes desired automation
↓
Git stores it
↓
Ansible reads it
↓
Ansible executes tasks
↓
Infrastructure reaches desired state
↓
Results are verified
```

---

# 3. Playbooks Are Automation as Code

A playbook is text.

That means it can be:

```text
Stored in Git

Reviewed in pull requests

Compared between versions

Tested

Linted

Executed by CI/CD

Reused

Audited

Rolled back to an earlier version

Shared with other engineers
```

This is one of the reasons playbooks fit naturally into DevOps workflows.

# 4. Ad Hoc Command vs Playbook

An ad hoc command:

```bash
ansible web \
  -i inventory/hosts.yml \
  -b \
  -m ansible.builtin.package \
  -a 'name=nginx state=present'
```

Equivalent playbook task:

```yaml
- name: Install nginx
  ansible.builtin.package:
    name: nginx
    state: present
```

The module did not disappear.

The module moved into structured YAML.

This is the connection between Part 5 and Part 6.

# 5. The Core Playbook Hierarchy

The most important structural model is:

```text
PLAYBOOK
│
├── PLAY
│   │
│   ├── Hosts
│   ├── Play Settings
│   │
│   └── Tasks
│       │
│       ├── Task
│       │   └── Module
│       │       └── Arguments
│       │
│       ├── Task
│       │   └── Module
│       │       └── Arguments
│       │
│       └── Task
│           └── Module
│               └── Arguments
│
└── PLAY
    │
    ├── Hosts
    └── Tasks
```

Remember:

```text
Playbook
↓
contains plays

Play
↓
targets hosts and contains tasks

Task
↓
calls a module

Module
↓
performs an operation

Arguments
↓
tell the module what state or action you want
```

---

# 6. What Is a Play?

A play connects:

```text
A group of hosts
```

with:

```text
A set of tasks
```

Think:

```text
PLAY
=
WHO
+
WHAT
```

For example:

```yaml
- name: Configure web servers
  hosts: web

  tasks:
    - name: Install nginx
      ansible.builtin.package:
        name: nginx
        state: present
```

The play answers:

```text
WHO?
↓
web
```

and:

```text
WHAT?
↓
Install nginx
```

---

# 7. What Is a Task?

A task is an individual unit of work inside a play.

Example:

```yaml
- name: Install nginx
  ansible.builtin.package:
    name: nginx
    state: present
```

Break it down:

```text
Task
│
├── name
│   └── Install nginx
│
└── module
    └── ansible.builtin.package
        │
        ├── name: nginx
        └── state: present
```

---

# 8. Tasks Usually Call Modules

From Part 5, you already know modules such as:

```text
ansible.builtin.package

ansible.builtin.file

ansible.builtin.copy

ansible.builtin.service

ansible.builtin.user

ansible.builtin.uri
```

Inside a playbook, you use the same modules.

Example:

```yaml
- name: Create application directory
  ansible.builtin.file:
    path: /opt/veriqta
    state: directory
    mode: "0755"
```

The playbook is not replacing modules.

It is organizing module execution.

---

# 9. Module Arguments in YAML

In an ad hoc command:

```bash
-a 'path=/opt/veriqta state=directory mode=0755'
```

In a playbook:

```yaml
ansible.builtin.file:
  path: /opt/veriqta
  state: directory
  mode: "0755"
```

This is easier to read and maintain.

Instead of compressing everything into one command line, YAML gives each argument structure.

---

# 10. Your First Tiny Playbook

Create:

```text
playbooks/
└── first-playbook.yml
```

Contents:

```yaml
---
- name: My first Ansible play
  hosts: web

  tasks:
    - name: Test Ansible connectivity
      ansible.builtin.ping:
```

This playbook has:

```text
1 play

1 host pattern

1 task

1 module
```

---

# 11. Understanding the YAML

```yaml
---
```

marks the beginning of a YAML document.

Then:

```yaml
- name: My first Ansible play
```

starts the first play.

The hyphen means this play is an item in the top-level YAML list.

Then:

```yaml
hosts: web
```

tells Ansible which inventory hosts the play targets.

Then:

```yaml
tasks:
```

introduces the ordered task list.

Then:

```yaml
- name: Test Ansible connectivity
```

starts a task.

Finally:

```yaml
ansible.builtin.ping:
```

calls the ping module.

---

# 12. Playbook Structure

A typical beginner playbook looks like:

```yaml
---
- name: Description of the play
  hosts: target_group
  become: true
  gather_facts: true

  tasks:
    - name: First task
      ansible.builtin.some_module:
        argument: value

    - name: Second task
      ansible.builtin.another_module:
        argument: value
```

Mental model:

```text
YAML Document
↓
Play
↓
Play Settings
↓
Tasks
↓
Task
↓
Module
↓
Arguments
```

# 13. The `name` Keyword

You will see `name` frequently.

For a play:

```yaml
- name: Configure production web servers
```

For a task:

```yaml
- name: Install nginx
```

These names appear in Ansible output.

Good names make automation understandable.

---

# 14. Bad Task Names

Avoid:

```yaml
- name: nginx
```

or:

```yaml
- name: package
```

or:

```yaml
- name: task 1
```

These tell the engineer very little.

---

# 15. Better Task Names

Prefer:

```yaml
- name: Install nginx web server
```

```yaml
- name: Create nginx document root
```

```yaml
- name: Deploy VERIQTA home page
```

```yaml
- name: Ensure nginx is started and enabled
```

The task name should tell you what the task intends to accomplish.

---

# 16. Task Names Become Operational Evidence

Imagine seeing:

```text
TASK [task 4]
```

fail in production.

Compare that with:

```text
TASK [Deploy nginx virtual host configuration]
```

The second immediately gives you context.

Good naming improves:

```text
Readability

Troubleshooting

Logs

Code reviews

Operational handoffs
```

# 17. The `hosts` Keyword

Every normal play needs to know which managed hosts it targets.

Example:

```yaml
hosts: web
```

This uses the inventory patterns you learned in Part 4.

It could target:

```yaml
hosts: web
```

or:

```yaml

```

or:

```yaml

```

or a more complex inventory pattern.

# 18. Inventory Still Controls Infrastructure

The playbook does not normally contain IP addresses for every server.

Instead:

```text
Playbook
↓
hosts: web
↓
Inventory
↓
web01
web02
web03
```

This separation is valuable.

The playbook describes automation.

The inventory describes infrastructure targets.

---

# 19. `become`

You learned privilege escalation in Part 5.

At the command line:

```bash
-b
```

Inside a play:

```yaml
become: true
```

Example:

```yaml
---
- name: Configure web servers
  hosts: web
  become: true

  tasks:
    - name: Install nginx
      ansible.builtin.package:
        name: nginx
        state: present
```

Tasks in the play inherit the play-level privilege escalation setting unless overridden.

---

# 20. Why Put `become` at Play Level?

Imagine six tasks all require root privileges.

You could write:

```yaml
- name: Install nginx
  become: true
```

then:

```yaml
- name: Create directory
  become: true
```

then:

```yaml
- name: Start nginx
  become: true
```

But if nearly every task requires elevation, play-level configuration can be clearer:

```yaml
- name: Configure web servers
  hosts: web
  become: true
```

Use privilege deliberately.

Do not elevate automation unnecessarily.

---

# 21. `gather_facts`

Ansible can gather information about managed hosts before normal tasks execute.

This behavior is controlled by:

```yaml
gather_facts: true
```

For many normal plays, fact gathering is enabled by default.

You can make your intention explicit:

```yaml
---
- name: Configure web servers
  hosts: web
  become: true
  gather_facts: true
```

---

# 22. What Are Facts?

Facts are discovered information about managed systems.

Examples can include information about:

```text
Operating system

Distribution

Architecture

Hostname

Network interfaces

Memory

Processors

Python environment
```

You will study facts properly in Part 7.

For now, understand:

```text
Play starts
↓
Gather facts
↓
Ansible learns about managed host
↓
Normal tasks begin
```

---

# 23. When Fact Gathering May Be Disabled

Some plays do not need system facts.

You may see:

```yaml
gather_facts: false
```

This can avoid unnecessary fact gathering.

Do not disable it automatically for performance.

Ask:

> Does this play depend on facts?

Later, when your tasks use operating-system information and other discovered data, this decision becomes important.

---

# 24. Task Ordering

Ansible playbooks are ordered.

Consider:

```yaml
tasks:
  - name: Create application directory
    ansible.builtin.file:
      path: /opt/veriqta
      state: directory

  - name: Copy application file
    ansible.builtin.copy:
      src: files/app.txt
      dest: /opt/veriqta/app.txt
```

The directory task appears first because the later task depends on the directory.

---

# 25. Order Matters

This sequence makes sense:

```text
Install nginx
↓
Create configuration
↓
Deploy content
↓
Start service
↓
Verify
```

This may not:

```text
Verify nginx
↓
Start nginx
↓
Install nginx
```

Ansible does not automatically rearrange your tasks into what it thinks is logical.

You design the sequence.

---

# 26. Default Task Execution Mental Model

Suppose inventory contains:

```text
web01
web02
web03
```

and the play contains:

```text
Task 1
Task 2
Task 3
```

Under Ansible's default linear strategy, think:

```text
Task 1
├── web01
├── web02
└── web03
↓
Task 2
├── web01
├── web02
└── web03
↓
Task 3
├── web01
├── web02
└── web03
```

Ansible normally processes a task across the active hosts in the play before moving to the next task.

Later you will learn strategies, `serial`, `throttle`, and advanced execution control.

# 30. First Playbook Run

Run:

```bash
ansible-playbook \
  -i inventory/hosts.yml \
  playbooks/first-playbook.yml
```

Conceptual output:

```text
PLAY [My first Ansible play]

TASK [Test Ansible connectivity]

PLAY RECAP
web01 : ok=2 changed=0 unreachable=0 failed=0 ...
```

Exact formatting and counters can differ by Ansible version, configuration, plugins, and the playbook itself.

Focus on what the output means.

---

# 31. Understanding `OK`

You may see:

```text
ok: [web01]
```

This means the task succeeded for that host without reporting a change.

Think:

```text
Task succeeded
+
No managed-state change
```

---

# 32. Understanding `CHANGED`

You may see:

```text
changed: [web01]
```

This means:

```text
Task succeeded
+
Module reports state changed
```

For example:

```text
nginx absent
↓
Install nginx
↓
changed
```

---

# 33. Understanding `FAILED`

You may see:

```text
fatal: [web01]: FAILED!
```

This indicates a task failed for that host.

Possible causes include:

```text
Bad module argument

Permission failure

Missing package

Invalid configuration

Command failure

Service failure

Missing file

Application error
```

Read the returned message.

Do not stop at the word `FAILED`.

---

# 34. Understanding `UNREACHABLE`

You may see:

```text
UNREACHABLE
```

This means Ansible could not successfully communicate with the host through the configured connection path.

Possible causes:

```text
Host offline

Wrong IP

DNS failure

SSH port blocked

Wrong SSH username

Wrong key

Authentication failure

Routing problem
```

This differs from a module failure.

---

# 35. Understanding `SKIPPED`

You may see:

```text
skipping: [web01]
```

A skipped task was intentionally not executed under the current conditions.

Later, common reasons will include:

```text
when conditions

tags

check-mode logic

platform-specific tasks
```

Skipped does not automatically mean failed.

---

# 36. Task Result Mental Model

```text
Host Selected
↓
Reachable?
├── No → UNREACHABLE
└── Yes
    ↓
    Should Task Run?
    ├── No → SKIPPED
    └── Yes
        ↓
        Did Task Succeed?
        ├── No → FAILED
        └── Yes
            ↓
            Did State Change?
            ├── Yes → CHANGED
            └── No → OK
```

---

# 37. The Play Recap

At the end of execution, Ansible provides a play recap.

Example:

```text
PLAY RECAP

web01 : ok=7 changed=3 unreachable=0 failed=0 skipped=0 rescued=0 ignored=0
web02 : ok=7 changed=2 unreachable=0 failed=0 skipped=0 rescued=0 ignored=0
```

This is one of the first places you should inspect after a playbook run.

---

# 38. Reading the Play Recap

Typical counters include:

```text
ok
↓
Successful task results
```

```text
changed
↓
Tasks reporting changes
```

```text
unreachable
↓
Connection failures
```

```text
failed
↓
Task failures
```

```text
skipped
↓
Skipped tasks
```

You may also see counters such as:

```text
rescued

ignored
```

which you will understand later when studying advanced failure handling.

---

# 39. Do Not Read Only the Recap

A recap such as:

```text
failed=1
```

tells you something failed.

It does not necessarily tell you why.

Troubleshooting should include:

```text
Find failed host
↓
Find failed task
↓
Read task result
↓
Read module message
↓
Inspect stdout/stderr if applicable
↓
Investigate managed system
↓
Fix root cause
```

# 44. First Real Playbook

Create:

```text
playbooks/web.yml
```

Use:

```yaml
---
- name: Configure web servers
  hosts: web
  become: true
  gather_facts: true

  tasks:
    - name: Install nginx web server
      ansible.builtin.package:
        name: nginx
        state: present

    - name: Create nginx document root
      ansible.builtin.file:
        path: /var/www/html
        state: directory
        mode: "0755"

    - name: Deploy VERIQTA home page
      ansible.builtin.copy:
        src: ../files/index.html
        dest: /var/www/html/index.html
        mode: "0644"

    - name: Ensure nginx is started and enabled
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true

    - name: Verify nginx HTTP response
      ansible.builtin.uri:
        url: http://127.0.0.1/
        status_code: 200
```

This is your first real configuration playbook.

# 45. Read the Playbook Before Running It

Never develop the habit:

```text
Copy YAML
↓
Immediately execute
```

Read it.

The play:

```yaml
- name: Configure web servers
```

documents its purpose.

Then:

```yaml
hosts: web
```

selects the web hosts.

Then:

```yaml
become: true
```

enables privilege escalation.

Then:

```yaml
gather_facts: true
```

enables fact gathering.

Then:

```yaml
tasks:
```

begins the ordered work.

# 51. Configuration vs Verification

Notice the playbook contains both:

```text
Configuration Tasks
```

and:

```text
Verification Task
```

Configuration:

```text

Create

Copy
```

```text

```

Good automation should not stop at:

You want evidence that the desired service actually works.

---

# 55. Syntax Correct Does Not Mean Operationally Correct

This can be perfectly valid YAML:

```yaml
- name: Install package
  ansible.builtin.package:
    name: definitely-not-a-real-package
    state: present
```

The syntax may be valid.

The package may still not exist.

Therefore:

```text
Syntax Valid
≠
Operationally Correct
```

```text
↓
Re-run
```

---

# 57. Check Mode

Run:

```bash
ansible-playbook \
  -i inventory/hosts.yml \
  playbooks/web.yml \
  --check
```

Check mode asks supporting modules to predict what they would change without intentionally applying those changes.

Think:

```text
Current State
↓
Desired State
↓
Prediction
↓
No Intended Mutation
```

---

# 58. Check Mode Is a Simulation

Do not call it a perfect dry run.

It is not.

Modules have different check-mode support.

A task may also depend on a previous task actually changing the system.

Example:

```text
Task 1
↓
Create directory

Task 2
↓
Use directory
```

During simulation, Task 1 may report what it would do without actually creating the directory.

Task 2 may then encounter a state that would have been different during a real execution.

This is one reason check mode cannot perfectly reproduce every real run.

---

# 59. Check Mode and Registered Results

Later you will learn registered variables.

For now, understand another limitation:

```text
Task A
↓
Would produce runtime data

Task B
↓
Depends on Task A's real runtime data
```

Simulation may not provide the same information as actual execution.

Treat check mode as evidence, not proof.

Example:


# 61. Check + Diff

```text

↓

```

# 62. Diff Security Warning

Be careful with diff output.

Configuration files can contain:

```text

Private configuration

Connection strings

Secrets

Internal infrastructure details
```

Displaying a diff in:

```text

CI logs

Shared build systems

Tickets

Chat
```

can expose sensitive data.

Do not enable `--diff` blindly around secret-bearing files.

# 65. Idempotency

Now playbooks make the importance of idempotency obvious.

Suppose the desired state is:

```text
nginx installed

document root exists

page deployed

nginx started

nginx enabled

HTTP responds
```

After the first successful run, that state should already exist.

Run the playbook again.

---

# 66. Re-running the Playbook

```bash
ansible-playbook \
  -i inventory/hosts.yml \
  playbooks/web.yml
```

On a well-designed state-aware playbook, you should expect fewer changes, often:

```text
changed=0
```

if nothing external has changed and all requested states remain satisfied.

---

# 67. Why Re-running Matters

A playbook should not normally mean:

> Perform these mutations every time.

It should often mean:

> Ensure these states are true.

First run:

```text
Wrong/Absent State
↓
Corrections
↓
Desired State
```

Second run:

```text
Desired State Already Exists
↓
No Unnecessary Changes
```

---

# 68. Idempotency Is Not Automatic

Do not assume:

```text
Written in Ansible
=
Idempotent
```

For example, careless use of:

```text
ansible.builtin.shell

ansible.builtin.command
```

can create repeated side effects.

A playbook can be valid Ansible and still be badly designed.

```text
↓

↓

↓

```

```text

```

Do not automatically accept repeated changes.

# 73. Playbook Readability Rules

As your playbooks grow:

```text
Use descriptive play names

Use descriptive task names

Use consistent indentation

Use FQCNs

Keep module arguments readable

Group related tasks logically

Avoid unexplained shell commands

Avoid clever YAML tricks

Make desired state obvious

Keep verification close to the behavior it verifies
```

Automation is read more often than it is written.

---

# 74. Do Not Optimize for Fewest Lines

Bad engineering goal:

> How can I make this playbook as short as possible?

Better goal:

> Can another engineer safely understand what this automation does?

Five clear lines are better than one clever line nobody wants to maintain.

# 80. Failure Behavior

Understanding failure is critical.

Suppose:

```text
web01
web02
web03
```

are targeted.

Task 2 fails on:

```text
web02
```

By default, Ansible normally stops running subsequent tasks on that failed host while continuing the play for other active hosts.

Conceptually:

```text
Task 1
web01 → OK
web02 → OK
web03 → OK

Task 2
web01 → OK
web02 → FAILED
web03 → OK

Task 3
web01 → runs
web02 → removed from normal execution
web03 → runs
```

This matters enormously in production.

---

# 81. Partial Success Is Possible

A playbook run can leave:

```text
web01
↓
successfully configured

web02
↓
failed halfway

web03
↓
successfully configured
```

Therefore:

```text
Playbook Finished
```

does not automatically mean:

```text
Every Host Reached Desired State
```

Always inspect the recap.

---

# 82. Failure Creates Operational Questions

When one host fails:

```text
What changed before failure?

Which tasks completed?

Which task failed?

Did other hosts continue?

Is the service partially deployed?

Can the playbook safely be rerun?

Does the failed host need manual repair?

Could partial state affect users?
```

This is why idempotency is so valuable.

A well-designed playbook is easier to rerun after fixing the underlying issue.

# 84. Rerunning After Failure

Suppose:

```text

Task 3 → failed
```

```text

↓
```


# 96. `--start-at-task`

Suppose your playbook contains:

```text
Install nginx

Create document root

Deploy home page

Start nginx

Verify HTTP
```

You want execution to begin at:

```text
Deploy VERIQTA home page
```

Use:

```bash
ansible-playbook \
  -i inventory/hosts.yml \
  playbooks/web.yml \
  --start-at-task="Deploy VERIQTA home page"
```

---

# 97. Why `--start-at-task` Exists

It can be useful when:

```text
Testing

Troubleshooting

Recovering from a failed run

Developing a long playbook
```

For example:

```text
Task 1 → OK
Task 2 → OK
Task 3 → FAILED
```

After fixing Task 3, you may sometimes choose to restart at that named task.

---

# 98. `--start-at-task` Is Not a General Dependency Solver

If you start halfway through:

```text
Task 1
↓
Create directory

Task 2
↓
Create configuration

Task 3
↓
Start application
```

and you begin directly at Task 3 on a fresh server, the required configuration may not exist.

Ansible does not infer:

> Task 3 depends on Task 1 and Task 2, so I should execute them.

You are responsible for understanding dependencies.

Also, `--start-at-task` has limitations with dynamically included tasks and roles, which becomes relevant later in the series.

# 102. Verification Tasks

A mature mental model separates:

```text

```

from:

```text
Verification
```


```text

↓

↓
Service Running?
↓

↓

↓
Correct Content?
↓

```

The further down this chain you verify, the stronger your evidence becomes.

```text

≠

```

This principle matters far beyond Ansible.

# 161. Knowledge Check

## Question 1

What is an Ansible playbook?

### Answer

A YAML file containing one or more plays that define repeatable automation against selected hosts.

---

## Question 2

What is a play?

### Answer

A structure that maps selected managed hosts to an ordered set of tasks and related execution settings.

---

## Question 3

What is a task?

### Answer

An individual unit of work in a play, normally calling an Ansible module with specific arguments.

---

## Question 4

What is the hierarchy?

### Answer

```text
Playbook
↓
Play
↓
Task
↓
Module
↓
Arguments
```

---

## Question 5

What does `hosts` do?

### Answer

It defines the inventory pattern targeted by a play.

---

## Question 6

What does `become: true` do?

### Answer

It enables privilege escalation for task execution according to the configured become mechanism.

---

## Question 7

What does `gather_facts` control?

### Answer

Whether Ansible automatically gathers system facts for the play.

---

## Question 8

In what order do tasks normally execute?

### Answer

From top to bottom within the play.

---

## Question 9

Under the default linear strategy, what generally happens across multiple hosts?

### Answer

Ansible runs the current task across the active hosts in the play before moving to the next task.

---

## Question 10

What command executes a playbook?

### Answer

```text
ansible-playbook
```

---

## Question 11

What does `--syntax-check` do?

### Answer

Checks playbook syntax without executing the playbook.

---

## Question 12

Does a successful syntax check prove the playbook will work?

### Answer

No. Runtime, dependency, connection, permission, package, service, and application failures can still occur.

---

## Question 13

What does `--check` do?

### Answer

Runs Ansible in check mode so supporting modules try to predict changes without intentionally applying them.

---

## Question 14

Is check mode a perfect dry run?

### Answer

No.

---

## Question 15

Why not?

### Answer

Module support varies, and later tasks may depend on real changes or runtime results that do not exist during simulation.

---

## Question 16

What does `--diff` do?

### Answer

For supporting modules, it displays before-and-after differences for changes such as file or template content.

---

## Question 17

Why can `--diff` be security-sensitive?

### Answer

The output may expose secrets or sensitive configuration.

---

## Question 18

What does `--limit` do?

### Answer

It further restricts the hosts eligible for execution.

---

## Question 19

What do tags do?

### Answer

They label plays or tasks so selected subsets can be run.

---

## Question 20

What does `--skip-tags` do?

### Answer

It excludes tasks and plays matching specified tags from the selected execution.

---

## Question 21

What does `--start-at-task` do?

### Answer

Starts execution at a task matching the specified task name, subject to Ansible's documented limitations.

---

## Question 22

Why can starting halfway through a playbook be dangerous?

### Answer

Earlier tasks may have established prerequisites required by later tasks.

---

## Question 23

What does `OK` mean?

### Answer

The task succeeded and did not report a managed-state change.

---

## Question 24

What does `CHANGED` mean?

### Answer

The task succeeded and reported that it changed managed state.

---

## Question 25

What does `FAILED` mean?

### Answer

The task operation failed for that host.

---

## Question 26

What does `UNREACHABLE` mean?

### Answer

Ansible could not successfully use the configured connection to the host.

---

## Question 27

What does `SKIPPED` mean?

### Answer

The task was intentionally not executed under the current execution conditions.

---

## Question 28

What is the Play Recap?

### Answer

The per-host summary at the end of a playbook run showing execution results such as successful, changed, unreachable, failed, and skipped counts.

---

## Question 29

What normally happens after a task fails on one host?

### Answer

By default, that host normally stops participating in later normal tasks in the play while other active hosts can continue.

---

## Question 30

Why is this important?

### Answer

A playbook can partially succeed across infrastructure, leaving some hosts configured and others incomplete.

---

## Question 31

What is idempotency?

### Answer

The property where repeatedly applying the same desired state does not keep making unnecessary changes after that state has been reached.

---

## Question 32

How can you perform a simple idempotency test?

### Answer

Run the playbook successfully, run it again without changing anything, and inspect whether tasks report unnecessary changes.

---

## Question 33

Does Ansible automatically make every playbook idempotent?

### Answer

No.

---

## Question 34

Why are task names important?

### Answer

They make automation readable and make execution output, troubleshooting, code review, and operational logs easier to understand.

---

## Question 35

Can a playbook contain multiple plays?

### Answer

Yes.

---

## Question 36

Why would you use multiple plays?

### Answer

To orchestrate different sets of tasks against different host groups or stages of a larger system.

---

## Question 37

Why include verification tasks?

### Answer

Because successful configuration tasks do not necessarily prove that the resulting application or service behaves correctly.

---

## Question 38

Does `state: started` prove a web application is healthy?

### Answer

No. The service process may be running while the application is still failing.

---

## Question 39

What should happen before a production playbook execution?

### Answer

At minimum, understand the code, validate syntax, confirm inventory and target scope, assess expected changes, understand privileges and failure impact, plan verification, and know how recovery will work.

---

## Question 40

What is the key difference between Part 5 and Part 6?

### Answer

Part 5 executed individual modules interactively. Part 6 organizes module operations into repeatable, ordered, version-controllable automation.
