# Part 1: Ansible Foundations and Configuration Management

## Build the Correct Mental Model Before Writing Automation

Before you write your first Ansible playbook, you need to understand the problem Ansible is solving.

If you skip this foundation, Ansible can easily look like this:

```text
Some YAML
↓
Some SSH
↓
Something happens on a server
```

That is not enough.

By the end of this part, you should understand this:

```text
Engineer
↓
Ansible Control Node
↓
Inventory
↓
Playbook
↓
Tasks
↓
Modules
↓
Connection Plugin
↓
Managed Nodes
↓
Desired Configuration
```

More importantly, you should be able to explain why every layer exists.

---

# 1. Start With the Problem, Not the Tool

Imagine that you are responsible for one Linux server.

You need to:

* create an administrator account
* install Nginx
* create an application directory
* copy configuration files
* configure permissions
* start Nginx
* enable Nginx at boot
* deploy an application
* verify that the service is running

With one server, you could log in manually.

```text
Engineer
↓
SSH
↓
Server
↓
Run Commands
```

Now imagine 5 servers.

Then 20.

Then 100.

Then 1,000.

The problem changes.

You are no longer asking:

> How do I configure a Linux server?

You are asking:

> How do I make hundreds of systems consistently reach and maintain the configuration I intend?

That is where configuration management becomes important.

---

# 2. Infrastructure Administration Before Automation

Before tools such as Ansible, administrators commonly managed machines manually.

Suppose you had three web servers:

```text
web01
web02
web03
```

An administrator might connect to the first server:

```bash
ssh admin@web01
```

Then manually run commands such as:

```bash
sudo apt update
sudo apt install nginx
sudo systemctl enable nginx
sudo systemctl start nginx
```

Then repeat the process:

```bash
ssh admin@web02
```

and again:

```bash
ssh admin@web03
```

This works.

The problem is not that manual administration is impossible.

The problem is what happens as infrastructure grows and changes.

---

# 3. The Manual Administration Problem

Imagine 100 servers need the same configuration change.

An engineer could theoretically connect to each server:

```text
Server 001
Server 002
Server 003
...
Server 100
```

and execute the same commands.

But several problems appear.

## Problem 1: Human error

On server 37, someone might type:

```text
version 1.4
```

instead of:

```text
version 1.5
```

## Problem 2: Forgotten steps

The engineer installs the package but forgets to restart the service on one machine.

## Problem 3: Different engineers

Engineer A follows one procedure.

Engineer B follows another.

## Problem 4: Poor reproducibility

Three months later, nobody remembers exactly how a server was configured.

## Problem 5: Slow changes

A five-minute change repeated across 100 machines becomes an operational burden.

## Problem 6: Difficult recovery

If a server is destroyed, rebuilding it manually requires remembering every previous configuration decision.

## Problem 7: Configuration drift

Machines that were originally identical gradually become different.

That last problem is especially important.

---

# 4. What Is Configuration Drift?

Configuration drift happens when systems that are supposed to have the same configuration gradually become different.

Imagine:

```text
DAY 1

web01 → Nginx 1.x → correct config
web02 → Nginx 1.x → correct config
web03 → Nginx 1.x → correct config
```

Six months later:

```text
web01 → configuration changed manually
web02 → package updated manually
web03 → firewall rule changed during incident
```

Now:

```text
web01 ≠ web02 ≠ web03
```

The servers have drifted.

---

# 5. Why Configuration Drift Happens

Drift can come from many places:

* manual changes
* emergency fixes
* package upgrades
* security patches
* troubleshooting
* different administrators
* undocumented commands
* configuration-file edits
* temporary changes that become permanent
* application deployments
* permission changes
* service changes
* infrastructure replacements

For example:

```text
Monday:
All web servers use worker_connections = 1024

Tuesday:
Engineer changes web02 to 4096 while troubleshooting.

Wednesday:
Incident ends.

Thursday:
Nobody remembers to restore web02.
```

Now:

```text
web01 = 1024
web02 = 4096
web03 = 1024
```

That is drift.

---

# 6. Why Drift Is Dangerous

Configuration drift creates systems that behave differently even though everyone assumes they are identical.

That can produce:

```text
Different performance

Different security posture

Different application behavior

Different failures

Different troubleshooting results
```

A production incident becomes harder because:

```text
"It works on web01"
```

does not guarantee:

```text
"It works on web02."
```

Automation attempts to reduce this uncertainty.

---

# 7. SSH-Based Administration

SSH solved an important problem.

Instead of physically accessing a Linux server, administrators could manage it remotely.

Architecture:

```text
Administrator
↓
SSH Client
↓
Network
↓
SSH Server
↓
Remote Linux Host
```

For example:

```bash
ssh anne@192.0.2.10
```

After authentication, you receive a remote shell.

You can then execute commands.

SSH is extremely important to understanding Ansible because SSH is commonly how Ansible connects to POSIX managed nodes.

But SSH by itself does not solve configuration management.

---

# 8. SSH Does Not Equal Automation

SSH gives you remote access.

It does not automatically give you:

```text
Desired-state management

Repeatability

Inventory management

Reusable automation

Conditional execution

Configuration templates

Structured results

Configuration enforcement
```

You could write:

```bash
ssh server1 "sudo apt install nginx"
ssh server2 "sudo apt install nginx"
ssh server3 "sudo apt install nginx"
```

That is automation of a sort.

But the system becomes difficult to maintain as complexity increases.

---

# 9. The Next Step: Shell Scripts

Administrators naturally began putting repeated commands into scripts.

Instead of typing:

```bash
sudo apt update
sudo apt install nginx
sudo systemctl enable nginx
sudo systemctl start nginx
```

every time, you might create:

```bash
#!/bin/bash

sudo apt update
sudo apt install -y nginx
sudo systemctl enable nginx
sudo systemctl start nginx
```

Now you have repeatability.

Run the script again when another server needs the same setup.

This is much better than remembering commands manually.

---

# 10. Shell Scripts Are Still Valuable

Ansible does not make shell scripting useless.

Shell scripts remain excellent for:

* small local automation
* command pipelines
* bootstrapping
* operating-system tasks
* build processes
* utilities
* glue logic
* situations where a shell is genuinely the correct interface

The lesson is not:

> Shell scripts are bad.

The lesson is:

> Shell scripts and configuration-management systems solve overlapping but different problems.

---

# 11. Where Shell Scripts Become Difficult

Imagine a script needs to ensure Nginx is installed.

A naive script might execute:

```bash
sudo apt install -y nginx
```

every time.

But a more mature script needs to ask:

```text
Is Nginx already installed?

Which operating system is this?

Which package manager exists?

Which version is installed?

Does configuration already exist?

Did configuration actually change?

Should the service restart?

Did the command fail?

How should the failure be reported?
```

You can write all of this logic yourself.

But your script begins becoming a configuration-management system.

This is one reason configuration-management tools exist.

---

# 12. What Is Configuration Management?

Configuration management is the disciplined process of defining, applying, maintaining, and verifying the configuration of systems.

Think:

```text
What should this server look like?
↓
Describe that configuration
↓
Apply it
↓
Verify it
↓
Keep systems consistent
```

Configuration may include:

```text
Packages

Users

Groups

Files

Directories

Permissions

Services

Application configuration

SSH settings

Scheduled jobs

Security settings

Runtime configuration
```

Instead of relying entirely on memory and manual procedures, configuration becomes automation.

---

# 13. Desired Configuration

Suppose your requirement is:

```text
Nginx must be installed.

Nginx must be running.

Nginx must start after reboot.
```

That describes a desired configuration.

The machine currently might look like:

```text
Nginx: absent
Service: nonexistent
```

You want:

```text
Nginx: installed
Service: running
Startup: enabled
```

The automation system helps move:

```text
CURRENT STATE
↓
DESIRED STATE
```

---

# 14. What Is Ansible?

Ansible is an automation tool used to manage remote systems and control their desired state.

You can use it for work such as:

* configuration management
* system administration
* application deployment
* orchestration
* provisioning tasks
* security configuration
* cloud automation
* network automation
* operational automation

Instead of manually configuring every machine, you describe automation in structured files and allow Ansible to execute that work against selected systems.

---

# 15. The Basic Ansible Idea

Suppose you have:

```text
web01
web02
web03
```

and all three need Nginx.

Instead of:

```text
Engineer
├── SSH → web01 → install nginx
├── SSH → web02 → install nginx
└── SSH → web03 → install nginx
```

you can move toward:

```text
Engineer
↓
Ansible
↓
Web Server Group
├── web01
├── web02
└── web03
↓
Ensure Nginx Is Installed
```

You define the operation once.

Ansible applies it to the selected machines.

---

# 16. Why Ansible Was Created

Infrastructure teams needed better ways to automate repeated operational work across many systems without maintaining large amounts of custom remote-management logic.

The problems include:

```text
Manual repetition

Configuration drift

Inconsistent servers

Slow deployments

Undocumented changes

Complex shell automation

Large server fleets

Repeated administrative tasks

Configuration enforcement

Coordinated multi-system operations
```

Ansible provides a structured automation model for these problems.

---

# 17. Problems Ansible Helps Solve

## Repeatability

You define an operation once and can execute it repeatedly.

```text
Playbook
↓
Run Today
↓
Run Tomorrow
↓
Run on Replacement Server
```

---

## Consistency

The same automation can be applied to many machines.

```text
Web Configuration
├── web01
├── web02
├── web03
└── web04
```

This reduces accidental differences.

---

## Configuration Enforcement

You can describe a required state such as:

```text
Package: installed

File: correct

Service: running

Service startup: enabled
```

Ansible can inspect the system and make changes where needed.

---

## Automation

Repeated operational work can become code instead of repeated human actions.

---

## Documentation Through Automation

A well-written playbook tells engineers something important about how systems are configured.

Instead of only having:

```text
"Ask Michael. He configured the server."
```

you can have:

```text
roles/
playbooks/
inventory/
templates/
```

under version control.

Automation is not a replacement for documentation, but it can become an important executable record of intended configuration.

# 18. Ansible and Server Provisioning

The word **provisioning** can mean different things depending on context.

Ansible can provision or configure many kinds of resources through modules and collections.

For example, automation may interact with cloud APIs.

But in many modern environments a useful separation is:

```text
Terraform
↓
Create Infrastructure

Ansible
↓
Configure Systems
```

Example:

```text
Terraform
↓
VPC
↓
Subnet
↓
Security Group
↓
EC2
↓
Ansible
↓
Packages
↓
Users
↓
Configuration
↓
Application
```

This is not an absolute law.

It is an architectural boundary you should understand and choose deliberately.

# 19. Application Deployment

Ansible can also participate in application deployment.

For example:

```text
Application Artifact
↓
Ansible
↓
Application Servers
↓
Copy / Download Artifact
↓
Configure Application
↓
Restart or Reload Service
↓
Verify
```

For multiple servers, deployment might become:

```text
Load Balancer
↓
Server A removed from traffic
↓
Deploy A
↓
Verify A
↓
Return A to traffic
↓
Server B removed
↓
Deploy B
↓
Verify B
↓
Return B
```

That introduces another important concept:

**orchestration**.

---

# 20. What Is Orchestration?

Automation often handles an individual operation.

Orchestration coordinates multiple operations, systems, or stages.

For example:

```text
Configure Database
↓
Configure Application Servers
↓
Configure Web Servers
↓
Restart Services
↓
Run Verification
```

Order matters.

Relationships matter.

Failure handling matters.

Ansible can coordinate such workflows.

---

# 21. Automation vs Orchestration

A useful beginner distinction is:

### Automation

```text
Perform this task automatically.
```

Example:

```text
Install Nginx.
```

### Orchestration

```text
Coordinate multiple automated actions in the required sequence.
```

Example:

```text
Drain Server
↓
Deploy Application
↓
Restart Service
↓
Run Health Check
↓
Return Server to Load Balancer
```

The concepts overlap, but the distinction is useful.

# 22. Infrastructure Operations

Ansible is not limited to initial server setup.

It can help automate ongoing operations such as:

```text
Package changes

Security hardening

Certificate deployment

Service management

Application deployment

Scheduled maintenance

Configuration verification

Incident remediation
```

That is why Ansible appears across DevOps, cloud, platform, SRE, security, and operations teams.

# 23. Desired State

Desired state is one of the most important ideas in configuration management.

Suppose:

```text
Current State:

nginx = not installed
```

Your automation says:

```text
Desired State:

nginx = installed
```

Ansible uses an appropriate module to move the machine toward that state.

Afterward:

```text
Current State
=
Desired State
```

Now imagine running the automation again.

Ideally:

```text
Current State
=
Desired State
```

so no unnecessary change occurs.

This leads to idempotency.

---

# 24. What Is Idempotency?

Idempotency means that repeatedly applying an operation should not continue changing a system once the intended state has already been reached.

Think:

```text
FIRST RUN

Current:
Nginx absent

Desired:
Nginx installed

Result:
CHANGE
```

Second run:

```text
SECOND RUN

Current:
Nginx installed

Desired:
Nginx installed

Result:
NO CHANGE REQUIRED
```

Third run:

```text
THIRD RUN

Current:
Nginx installed

Desired:
Nginx installed

Result:
NO CHANGE REQUIRED
```

This property is extremely valuable for configuration management.

---

# 25. Idempotency Is Not Magic

Do not make this beginner mistake:

> Everything written in Ansible is automatically idempotent.

That is false.

Many Ansible modules are designed to be idempotent.

But your automation can still behave non-idempotently.

For example, blindly executing arbitrary shell commands may make a change every time.

Conceptually:

```yaml
- name: Append text every run
  ansible.builtin.shell: echo "hello" >> /tmp/example.txt
```

Run it five times and you may get:

```text
hello
hello
hello
hello
hello
```

Ansible cannot magically turn arbitrary operations into desired-state operations.

Your choice of module and automation design matters.

---

# 26. Why Purpose-Built Modules Matter

Instead of thinking:

```text
Which Linux command can I execute?
```

start thinking:

```text
Which Ansible module represents the operation I want?
```

For example, instead of building shell logic around file creation, package installation, or service management, Ansible provides modules designed for those domains.

This gives Ansible more information about the intended operation.

---

# 27. Declarative Automation

Declarative thinking focuses on the state you want.

Conceptually:

```text
Package nginx
State: present
```

You are saying:

> Nginx should exist.

The module determines whether a change is required.

---

# 28. Imperative Operations

Imperative thinking focuses on the steps to execute.

For example:

```text
Run apt update
Run apt install
Run systemctl start
Run systemctl enable
```

That is closer to:

> Execute these instructions.

---

# 29. Ansible Uses Both Styles

Do not oversimplify Ansible as purely declarative.

Ansible playbooks contain ordered tasks.

That ordering is procedural.

At the same time, many modules let individual tasks express desired state.

Therefore a useful mental model is:

```text
PLAYBOOK
=
Ordered Workflow
+
Desired-State Operations
```

For example:

```text
Task 1 → package should exist
Task 2 → configuration file should exist
Task 3 → service should be enabled and running
```

The playbook provides sequence.

The modules often provide state-aware behavior.

---

# 30. Ansible Is Agentless

One of Ansible's major architectural characteristics is that it is generally agentless.

With agent-based configuration management, you might have:

```text
Central System
↓
Agent
↓
Server
```

Every managed server needs a dedicated management agent installed and operating.

Ansible generally does not require an Ansible daemon running permanently on each managed Linux host.

Instead:

```text
Control Node
↓
Connection
↓
Managed Node
```

Ansible connects when work needs to be performed.

---

# 31. What Agentless Does Not Mean

Agentless does not mean:

```text
The managed machine requires absolutely nothing.
```

The target still needs the requirements for the connection and the modules being used.

For typical POSIX management this commonly includes:

```text
Network connectivity

SSH

Authentication

Suitable Python support for Python-based modules
```

There are exceptions.

Some modules or connection types have different requirements.

Windows is also different and commonly uses PowerShell-based mechanisms and Windows-specific modules.

---

# 32. Push-Based Automation

Traditional Ansible operation is commonly described as push-based.

The control side initiates the operation:

```text
Control Node
↓
Connects to Targets
↓
Pushes / Executes Required Automation
↓
Returns Results
```

Compare conceptually with a pull model:

```text
Managed Node
↓
Periodically Contacts Management System
↓
Retrieves Configuration
↓
Applies Configuration
```

Ansible's normal CLI/playbook model is closer to the first architecture.

---

# 33. The Control Node

The **control node** is the system where Ansible is installed and from which you run Ansible commands.

Example:

```text
Your Linux Workstation
↓
Ansible Installed
↓
Control Node
```

Or:

```text
CI Runner
↓
Ansible Installed
↓
Control Node
```

The control node may contain:

```text
Ansible

Inventory

Playbooks

Roles

Collections

Configuration

Templates

Variables
```

---

# 34. Control Node Operating Systems

Ansible's control node is normally a Unix-like environment.

Examples include:

```text
Linux

macOS

BSD
```

Windows is not natively used as a normal Ansible control node.

A Windows user may use a Linux environment such as WSL for learning and development.

Production support considerations should always be checked against the Ansible version and environment you intend to use.

---

# 35. The Managed Node

A **managed node** is a system Ansible manages.

You may also hear:

```text
Managed host

Target

Remote host
```

Examples:

```text
Linux Server

Windows Server

Network Device

Cloud Resource
```

depending on the automation and collection being used.

Ansible itself normally does not need to be installed on a standard managed node.

---

# 36. Control Node vs Managed Node

Do not confuse them.

```text
CONTROL NODE

Runs Ansible
Stores automation content
Initiates automation
Connects to targets
```

versus:

```text
MANAGED NODE

Receives automation
Runs relevant module operations
Ends in desired configuration
```

Architecture:

```text
Control Node
├── web01
├── web02
├── app01
└── db01
```

---

# 37. Inventory

How does Ansible know that:

```text
web01
web02
app01
db01
```

exist?

Through inventory.

Inventory describes the managed nodes available to Ansible and can organize them logically.

Conceptually:

```text
Inventory
│
├── webservers
│   ├── web01
│   └── web02
│
├── appservers
│   └── app01
│
└── databases
    └── db01
```

Inventory answers an important question:

> Which systems should this automation target?

---

# 38. Why Groups Matter

Suppose you need Nginx only on web servers.

You should not need to manually list every web server in every task.

Instead:

```text
Group: webservers
↓
web01
web02
web03
```

Your play can target:

```text
webservers
```

The inventory separates:

```text
WHAT MACHINES EXIST?
```

from:

```text
WHAT AUTOMATION SHOULD RUN?
```

That separation becomes powerful at scale.

---

# 39. Static and Dynamic Inventory

A static inventory is explicitly maintained.

Conceptually:

```text
web01
web02
db01
```

But cloud infrastructure changes frequently.

Instances may appear and disappear.

A dynamic inventory source can discover infrastructure from an external system.

For example:

```text
AWS
↓
Inventory Plugin
↓
Discover EC2 Instances
↓
Build Inventory
↓
Ansible Targets Hosts
```

You will study this deeply later.

For now remember:

> Inventory tells Ansible what it can target and how those targets are organized.

# 40. Modules

A module is a unit of Ansible functionality that performs a specific operation.

Think:

```text
Need to manage package
↓
Package-related module

Need to manage file
↓
File-related module

Need to manage user
↓
User-related module

Need to manage service
↓
Service-related module
```

Modules are one of the most important Ansible concepts.

---

# 41. Example Module Mental Model

Suppose you want:

```text
Nginx installed
```

A package-management module can:

```text
Inspect package state
↓
Determine whether change is required
↓
Install if necessary
↓
Return result
```

Instead of you manually implementing:

```text
Check package
↓
Parse output
↓
Determine state
↓
Install
↓
Handle result
```

the module encapsulates much of that operational logic.

---

# 42. Module Results

Ansible modules return structured results.

During playbook execution you will frequently see concepts such as:

```text
ok

changed

failed

unreachable

skipped
```

Very roughly:

```text
ok
=
Task succeeded without requiring change

changed
=
Task succeeded and changed target

failed
=
Task execution failed

unreachable
=
Ansible could not successfully reach/use target connection

skipped
=
Task was intentionally not executed
```

These results become essential during troubleshooting.

---

# 43. Tasks

A **task** describes an action Ansible should perform.

Conceptually:

```text
Task
↓
Module
↓
Arguments
```

Example:

```yaml
- name: Ensure Nginx is installed
  ansible.builtin.package:
    name: nginx
    state: present
```

Break it down.

---

# 44. Task Name

```yaml
name: Ensure Nginx is installed
```

This tells humans what the task intends to do.

Good task names matter because Ansible output becomes operational evidence.

Compare:

```text
TASK [stuff]
```

with:

```text
TASK [Ensure Nginx is installed]
```

The second is much easier to troubleshoot.

---

# 45. Module Name

```yaml
ansible.builtin.package:
```

This selects the module.

The full name:

```text
ansible.builtin.package
```

is a Fully Qualified Collection Name, commonly shortened to **FQCN**.

Conceptually:

```text
ansible
↓
builtin
↓
package
```

Using FQCNs makes the source of a module explicit.

---

# 46. Module Arguments

```yaml
name: nginx
state: present
```

These are arguments passed to the module.

Conceptually:

```text
MODULE
package

ARGUMENTS
name = nginx
state = present
```

Meaning:

> Ensure that the package named nginx is present.

---

# 47. From Task to Result

The mental model is:

```text
Task
↓
Module
↓
Arguments
↓
Target
↓
Inspect State
↓
Change If Required
↓
Return Result
```

This is the core of Ansible.

---

# 48. Plays

A **play** maps a set of hosts to the tasks that should run against them.

Conceptually:

```text
PLAY

Target:
webservers

Tasks:
1. Install Nginx
2. Deploy configuration
3. Start Nginx
```

The important relationship is:

```text
HOSTS
+
TASKS
=
PLAY
```

---

# 49. Example Play

```yaml
- name: Configure web servers
  hosts: webservers

  tasks:
    - name: Ensure Nginx is installed
      ansible.builtin.package:
        name: nginx
        state: present
```

Read this in plain English:

> On the machines belonging to the webservers target, ensure that Nginx is installed.

That is much more useful than memorizing YAML indentation without understanding the intention.

---

# 50. Playbooks

A **playbook** is a YAML file containing one or more plays.

Conceptually:

```text
PLAYBOOK
│
├── Play 1
│   ├── Hosts
│   └── Tasks
│
└── Play 2
    ├── Hosts
    └── Tasks
```

For example:

```text
site.yml

Play 1:
Configure web servers

Play 2:
Configure application servers

Play 3:
Configure database servers
```

---

# 51. Task vs Play vs Playbook

Memorize the relationship, not just the words.

```text
TASK
=
One operation
```

```text
PLAY
=
Selected hosts
+
Tasks
```

```text
PLAYBOOK
=
One or more plays
```

Diagram:

```text
Playbook
│
├── Play
│   ├── Host Group
│   ├── Task
│   ├── Task
│   └── Task
│
└── Play
    ├── Host Group
    ├── Task
    └── Task
```

# 52. Variables

Hardcoding every value makes automation difficult to reuse.

Suppose you write:

```text
Application port = 8080
```

directly everywhere.

Development may need:

```text
8080
```

Production might use a different value.

Variables separate:

```text
Automation Logic
```

from:

```text
Configuration Data
```

---

# 53. Variable Mental Model

Instead of:

```text
Install package nginx
```

you might eventually have:

```text
web_package = nginx
```

and automation uses:

```text
Install {{ web_package }}
```

Now different systems or environments can supply appropriate values.

Variables can be defined in several places, including inventory, playbooks, variable files, roles, and command-line inputs.

Ansible has precedence rules to determine which value wins when multiple definitions exist.

You will learn those rules later.

# 54. Facts

# 56. Templates

Static files are not always enough.

Suppose every server needs an application configuration containing its own hostname.

A static file would require one file per machine.

Conceptually:

```text

+

+
Facts
↓
Rendered Configuration
↓
Managed Node
```

# 57. Template Example

Conceptual template:

```text
server_name = {{ inventory_hostname }}
application_port = {{ application_port }}
environment = {{ environment_name }}
```

For `web01`, Ansible might render:

```text
server_name = web01
application_port = 8080
environment = production
```

For `web02`:

```text
server_name = web02
application_port = 8080
environment = production
```

Same template.

Different data.

---

# 58. Where Template Rendering Happens

An important architectural detail:

```text
Template
↓
Rendered on Control Node
↓
Result Sent to Managed Node
```

The managed node does not need to perform the Jinja rendering itself.

This matters when understanding Ansible's architecture.

# 59. Handlers

Suppose Ansible changes:

```text
/etc/nginx/nginx.conf
```

Nginx may need to reload or restart.

But you do not necessarily want to restart Nginx every time the playbook runs.

You want:

```text
Configuration changed?
├── No  → Do not restart
└── Yes → Notify restart/reload handler
```

That is a major use case for handlers.

---

# 60. Handler Mental Model

```text
Task
↓
Configuration Changed?
        │
        ├── No → Continue
        │
        └── Yes
             ↓
          Notify
             ↓
          Handler
             ↓
       Restart / Reload
```

A handler is a special kind of task triggered by notification from a task that reports a change.

---

# 61. Why Handlers Matter

Without handlers, beginners often write:

```text
Copy configuration
↓
Restart service
```

every run.

Even when the configuration did not change.

Handlers allow a better pattern:

```text
Ensure configuration
↓
Change?
├── No → nothing
└── Yes → restart when appropriate
```

That reduces unnecessary disruption.

# 72. Ansible and SSH

For typical POSIX hosts:

```text

↓

↓
```

```text

Private key wrong

Host-key verification fails

Authentication fails
```

Understanding SSH will make you a much better Ansible troubleshooter.

```text

↓
```

# 74. Connection Plugins

SSH is common, but Ansible's architecture is not limited to SSH.

Connection behavior is extensible through connection plugins.

Depending on target and use case, different connection mechanisms can be used.

For example:

```text
POSIX Host
↓
SSH
```

Windows can use mechanisms such as:

```text
PowerShell Remoting / WinRM

or

supported SSH configurations
```

Other technologies can have different connection models.

Therefore the more accurate architecture is:

```text
Ansible
↓
Connection Plugin
↓
Managed Target
```

not:

```text
Ansible always equals SSH.
```

# 75. Ansible and Python

Python is also important to Ansible.

The Ansible control software runs using Python.

For many POSIX managed-node modules, Ansible transfers and executes Python-based module code on the managed node.

A simplified model:

```text

↓
Ansible
↓
SSH
↓
Managed Node
↓

↓
Python
↓
```

# 76. Does the Managed Node Need Ansible Installed?

Normally:

```text
NO
```

That is part of the agentless model.

A normal Linux managed node generally does not need:

```text
ansible
```

installed.

But many modules require suitable Python support on the target.

This distinction matters:

```text
Ansible installed on target?
No.

Python potentially required for modules?
Yes.
```

---

# 77. Python Exceptions

Do not memorize:

> Every Ansible operation always requires Python on every target.

That is too broad.

Different target types, modules, and connection mechanisms have different requirements.

For example:

* Windows uses Windows-specific modules, commonly implemented through PowerShell.
* Network devices can have different execution models.
* Some bootstrapping operations can work without the normal Python-module path.

The correct rule is:

> Check the requirements of the platform, connection plugin, collection, and module you are using.

# 97. When Ansible May Not Be the Best Tool

Ansible is not automatically the answer to every automation problem.

It may not be the best primary tool when the real requirement is:

### Provisioning a large cloud resource graph

A tool such as Terraform may provide a better infrastructure-lifecycle model.

### Building software

Use a build system.

### Container orchestration

Use an orchestration platform such as Kubernetes where appropriate.

### High-frequency application logic

Do not turn Ansible into your application runtime.

### Simple local command

A short shell command or script may be enough.

### Continuous application processing

Ansible is an automation system, not a general-purpose continuously running application platform.

### A task already solved by the platform

Do not add Ansible merely because you know Ansible.

| Create deploy user               | Task + user-management module |
| Install Nginx                    | Task + package module         |
| Create directory                 | Task + file module            |
| Generate config                  | Template                      |
| Restart after config change      | Handler                       |
| Different environment values     | Variables                     |
| Detect OS                        | Facts                         |
| Group reusable web configuration | Role                          |

You are beginning to think in Ansible architecture.

# 114. Step 3: Think About Idempotency

Ask:

> What should happen on the second run?

Expected:

```text
User already exists
→ no unnecessary change

Package already installed
→ no unnecessary change

Directory already correct
→ no unnecessary change

Configuration unchanged
→ no unnecessary change

Service already running
→ no unnecessary change
```

That is the behavior you should aim for.


Conceptually:

```text
↓

Ansible

↓
```

That is configuration management.

# 127. Knowledge Check

Answer these before continuing.

### Question 1

What problem does configuration management solve?

### Answer

It helps teams define, apply, maintain, and verify intended system configuration consistently and repeatedly across systems.

---

### Question 2

What is configuration drift?

### Answer

It is the divergence that occurs when systems that should have equivalent intended configuration become different over time.

---

### Question 3

Is SSH the same as configuration management?

### Answer

No. SSH provides remote connectivity and command execution. Configuration management adds structured automation for managing intended system configuration across systems.

---

### Question 4

What is a control node?

### Answer

The system on which Ansible runs and from which automation is initiated.

---

### Question 5

What is a managed node?

### Answer

A system or target that Ansible manages.

---

### Question 6

Does Ansible normally need to be installed on every Linux managed node?

### Answer

No. Ansible is generally agentless. Many standard POSIX modules do, however, require suitable Python support on the managed node.

---

### Question 7

What is inventory?

### Answer

Inventory describes and organizes the managed nodes that Ansible can target.

---

### Question 8

What is a module?

### Answer

A unit of Ansible functionality that performs a particular operation against a target or service.

---

### Question 9

What is a task?

### Answer

A definition of an individual action in Ansible, typically invoking a module with arguments.

---

### Question 10

What is a play?

### Answer

A mapping between selected hosts and the tasks or roles that should run against them.

---

### Question 11

What is a playbook?

### Answer

A YAML file containing one or more plays.

---

### Question 12

What is idempotency?

### Answer

The property where repeatedly applying an operation does not continue changing a system after the desired state has already been achieved.

---

### Question 13

Is every Ansible operation automatically idempotent?

### Answer

No. Module behavior and automation design determine whether repeated execution is safe and state-aware.

---

### Question 14

What are facts?

### Answer

Information Ansible discovers about managed systems, such as operating-system, networking, hardware, and filesystem information.

---

### Question 15

What are variables?

### Answer

Named values used to make automation configurable and reusable across systems and environments.

---

### Question 16

What is a template?

### Answer

A source used to generate configuration or text dynamically from variables, facts, and expressions.

---

### Question 17

What is a handler?

### Answer

A special task normally triggered by a notification from another task that reported a change.

---

### Question 18

What is a role?

### Answer

A structured reusable unit for organizing related Ansible tasks, handlers, variables, defaults, templates, files, and supporting content.

---

### Question 19

What is a collection?

### Answer

A distribution format that can package related Ansible content such as modules, plugins, roles, and playbooks.

---

### Question 20

What is a plugin?

### Answer

Code that extends Ansible's core behavior, such as connection, inventory, lookup, filter, callback, or strategy functionality.

---

### Question 21

What is Ansible Galaxy?

### Answer

An ecosystem and distribution service for reusable Ansible content such as collections and roles.

---

### Question 22

What is the difference between Ansible and Terraform?

### Answer

They overlap, but Terraform commonly focuses on provisioning and lifecycle management of infrastructure resources, while Ansible commonly excels at configuration management and operational automation. They are frequently used together with clear ownership boundaries.

---

### Question 23

Why are purpose-built modules often preferable to shell commands?

### Answer

They can understand the operation being requested, inspect relevant state, provide structured results, and often support idempotent desired-state behavior.

---

### Question 24

Why can automation be dangerous?

### Answer

Automation increases execution speed and scale. A mistake that would affect one manually managed machine can potentially affect an entire inventory.

---

### Question 25

What is the first question when Ansible fails?

### Answer

Determine which layer failed: inventory, connectivity, authentication, privilege escalation, variables, module execution, operating system, service, or application.
