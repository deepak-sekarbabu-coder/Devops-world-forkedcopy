# Part 13: Ansible Security, Secrets, and Vault

## Secure the Automation System Itself

Ansible can configure hundreds or thousands of systems.

That makes it powerful.

It also makes the Ansible environment itself a security-sensitive system.

If an attacker compromises:

```text
Your Ansible control node
```

they may gain a path toward:

```text
SSH identities

Cloud credentials

Vault secrets

API tokens

Inventory information

Configuration files

Privileged access

Production servers
```

So security cannot begin at the managed node.

It must begin much earlier.

---

# 1. The Security Path

This is the security path you should keep in your head throughout this chapter:

```text
Engineer
↓
Git Repository
↓
Ansible Control Node / CI
↓
Secrets
↓
SSH Identity
↓
Privilege Escalation
↓
Managed Node
↓
Configuration
```

Every arrow represents a trust boundary.

Every layer can introduce risk.

---

# 2. The Real Security Model

Do not think:

```text
Ansible
↓
Server
```

Think:

```text
Engineer Identity
↓
Source Repository
↓
Dependency Supply Chain
↓
Control Node / CI Runner
↓
Ansible Runtime
↓
Secrets
↓
Connection Identity
↓
Managed Host
↓
Privilege Escalation
↓
Configuration Change
↓
Application / Service
```

Security must protect the complete chain.

---

# 3. What Are We Protecting?

An Ansible environment may contain or access:

```text
SSH private keys

SSH passwords

Sudo passwords

Application passwords

Database passwords

API tokens

Cloud credentials

TLS private keys

Service-account credentials

Vault passwords

Inventory information

Infrastructure addresses

Configuration files

Deployment credentials

Secrets retrieved from external systems
```

You must protect both:

```text
Secrets
```

and:

```text
The systems capable of retrieving those secrets.
```

---

# 4. Security Has Multiple Goals

A secure automation system should protect:

## Confidentiality

Unauthorized users should not read sensitive information.

## Integrity

Unauthorized users should not modify automation, configuration, or dependencies.

## Availability

Automation should remain usable when needed.

## Authenticity

You should know which system and dependency you are communicating with.

## Authorization

Automation should only perform actions it is permitted to perform.

## Accountability

Important automation activity should be attributable and reviewable.

---

# 5. Automation Increases Blast Radius

Manual administration might compromise:

```text
One administrator
↓
One server
```

Centralized automation may provide access to:

```text
One automation identity
↓
Hundreds of servers
```

or:

```text
One CI runner
↓
Cloud credentials
↓
Entire environment
```

Automation reduces repetitive work.

But concentrated privilege increases the importance of security controls.

---

# 6. Security Principle: Least Privilege

The most important principle in this chapter is:

```text
Give an identity only the permissions it needs,
for only the systems it needs,
for only as long as it needs them.
```

Not:

```text
Everything is root because automation is easier that way.
```

---

# 7. Security Principle: Separation of Duties

Where appropriate, separate:

```text
Code Authoring

Code Review

Secret Administration

Production Approval

Production Execution
```

One person should not automatically need unrestricted control over every security layer.

---

# 8. Security Principle: Short-Lived Credentials

Where your platform supports them, prefer:

```text
Temporary credentials
```

over:

```text
Long-lived static credentials
```

Examples include:

```text
Temporary cloud credentials

Federated identities

OIDC-issued credentials

Short-lived tokens

Short-lived certificates
```

The exact mechanism depends on your environment.

---

# 9. Security Principle: Never Trust Storage Location Alone

Do not assume something is safe because it lives in:

```text
A private Git repository

A CI system

An environment variable

A hidden file

A developer laptop

A Docker container
```

Those are storage or execution locations.

They are not automatically security controls.

---

# 10. Control-Node Security

The Ansible control node is one of the most sensitive systems in your automation architecture.

Why?

Because it may contain:

```text
Ansible

Inventory

SSH configuration

SSH private keys

Vault passwords

Cloud credentials

Collection dependencies

Automation code

Temporary decrypted data
```

And it can often communicate with managed infrastructure.

---

# 11. Control Node Mental Model

```text
                 CONTROL NODE
                      │
      ┌───────────────┼───────────────┐
      ↓               ↓               ↓
  Repository      Credentials      Inventory
      │               │               │
      └───────────────┼───────────────┘
                      ↓
                    Ansible
                      ↓
                  Infrastructure
```

Compromise the control node and the attacker may inherit significant automation capability.

---

# 12. Control-Node Security Requirements

A production control node should generally have:

```text
Strong authentication

Limited user access

Secure operating-system configuration

Security updates

Minimal unnecessary software

Restricted network exposure

Controlled SSH keys

Controlled secrets

Auditable access

Controlled dependency installation

Protected logs

Backup/recovery strategy where required
```

The exact controls depend on organizational risk.

---

# 13. Do Not Use a Random Personal Machine as the Production Security Model

A laptop is perfectly reasonable for learning.

But production automation needs a deliberate execution environment.

Bad architecture:

```text
Personal Laptop
↓
Random Packages
↓
Long-Lived Production Keys
↓
Production
```

Better:

```text
Reviewed Repository
↓
Controlled CI / Automation Runtime
↓
Approved Dependencies
↓
Short-Lived or Controlled Credentials
↓
Production
```

---

# 14. Separate Development and Production Access

Your development environment should not automatically have unrestricted production credentials.

Think:

```text
Development Credentials
↓
Development Environment
```

```text
Staging Credentials
↓
Staging Environment
```

```text
Production Credentials
↓
Production Environment
```

This limits blast radius.

# 15. Secure the Ansible Configuration

Ansible configuration can change security-sensitive behavior.

Examples include:

```text
Host-key checking

Plugin paths

Vault password sources

Connection behavior

Privilege escalation

Logging

Inventory behavior
```

Therefore:

```text
ansible.cfg
```

is part of your security configuration.

Review it.

Do not blindly copy configuration files from the internet.

---

# 16. Inspect Effective Configuration

Use:

```bash
ansible-config dump
```

You can also inspect configuration sources with appropriate `ansible-config` commands.

The goal is to understand:

```text
What configuration is actually active?
```

not merely:

```text
What do I think my configuration says?
```

# 17. SSH Security

For ordinary POSIX managed hosts, SSH is a common Ansible connection mechanism.

Conceptually:

```text
Control Node
↓
SSH
↓
Remote User
↓
Managed Node
```

SSH security therefore becomes part of Ansible security.

---

# 18. SSH Authentication

Common SSH authentication approaches include:

```text
Public-key authentication

Password authentication

SSH agent-based identities

Certificates or enterprise identity mechanisms
```

depending on the environment.

For automation, SSH keys are commonly used.

---

# 19. SSH Key Pair Mental Model

A key pair contains:

```text
Private Key
+
Public Key
```

The public key can be placed on an authorized server.

The private key must remain protected.

Think:

```text
Control Node
│
└── Private Key
       │
       ↓
    proves identity
       │
       ↓
Managed Node
│
└── Authorized Public Key
```

---

# 20. The Private Key Is Sensitive

Do not:

```text
Commit it to Git

Paste it into playbooks

Put it into README files

Share it in chat

Email it casually

Bake it into container images

Store it in public artifacts
```

A private SSH key is authentication material.

Treat it like a credential.

---

# 21. SSH Key Permissions

OpenSSH commonly expects private key files to have restrictive permissions.

For a user-owned private key, a typical secure mode is:

```bash
chmod 600 ~/.ssh/id_ed25519
```

This means:

```text
Owner = read + write

Group = none

Others = none
```

Depending on your workflow, even more restrictive modes may be appropriate.

---

# 22. Inspect Key Permissions

Run:

```bash
ls -l ~/.ssh/
```

Example shape:

```text
-rw------- user user ... id_ed25519
-rw-r--r-- user user ... id_ed25519.pub
```

Your exact filenames may differ.

Do not assume every private key is named:

```text
id_ed25519
```

---

# 23. Dangerous Permission Example

Do not solve SSH errors with:

```bash
chmod 777 private-key.pem
```

That makes the key accessible far too broadly.

A permissions error is telling you to protect the key.

Do not "fix" the warning by destroying the protection.

---

# 24. SSH Agent Concept

An SSH agent can hold authentication identities for a session.

Conceptually:

```text
Private Key
↓
SSH Agent
↓
SSH Client
↓
Managed Host
```

This can reduce repeated passphrase entry.

But access to the agent itself is security-sensitive.

---

# 25. SSH Key Passphrases

A private key can be protected with a passphrase.

This adds protection if the key file is stolen.

But automation needs a secure mechanism for unlocking or accessing credentials.

Do not remove passphrases simply because secure automation requires design work.

---

# 26. Separate SSH Identities

Consider whether different environments should use different identities.

For example:

```text
Development Key
↓
Development Servers
```

```text
Production Automation Identity
↓
Production Servers
```

This limits the consequences of credential compromise.

---

# 27. Remote Users

Ansible connects as a remote user.

This may be specified through:

```text
Inventory

Play configuration

CLI options

Connection configuration
```

You previously used concepts such as:

```text
ansible_user
```

The remote user is the initial identity Ansible uses on the managed node.

---

# 28. Do Not Default to Root SSH

A convenient but risky design is:

```text
SSH directly as root
↓
Do everything
```

A better model is often:

```text
SSH as controlled automation user
↓
Privilege escalation only where required
```

This creates a clearer privilege boundary.

---

# 29. Host-Key Checking

SSH does more than authenticate the client.

The client also needs confidence that it is communicating with the intended server.

SSH host keys provide server identity verification.

Conceptually:

```text
Client
↓
Connects to server
↓
Server presents host key
↓
Client verifies expected identity
↓
Connection continues
```

---

# 30. Why Host-Key Checking Matters

Without server identity verification, you increase the risk of communicating with an unintended or malicious endpoint.

Potential problem:

```text
Control Node
↓
Attacker / Wrong Host
↓
Automation Connection
```

You do not want your automation blindly trusting whatever answers on port 22.

---

# 31. Ansible Host-Key Checking

Host-key checking is enabled by default for the built-in SSH connection behavior.

It can be configured through Ansible configuration, environment variables, and connection settings.

Do not disable it globally simply because your first SSH connection produced a host-key error.

---

# 32. Dangerous Shortcut

You may see tutorials suggesting:

```ini
[defaults]
host_key_checking = False
```

as a universal fix.

Do not adopt that blindly.

It removes an important server identity check.

---

# 33. Better Question

When host-key verification fails, ask:

```text
Is this a new host?

Was the server rebuilt?

Did the IP move?

Did the host key legitimately change?

Is DNS correct?

Am I reaching the correct environment?

Could this be an interception attempt?

Is known_hosts stale?
```

Investigate before overriding.

---

# 34. `known_hosts`

SSH commonly records trusted host keys in:

```text
~/.ssh/known_hosts
```

or other configured known-hosts locations.

This creates remembered host identity.

---

# 35. Host-Key Failure Workflow

```text
HOST KEY ERROR
↓
STOP
↓
Identify Target
↓
Verify DNS/IP
↓
Verify Expected Host Key
↓
Determine Why It Changed
↓
Update Trust Record If Legitimate
↓
Retry
```

Not:

```text
HOST KEY ERROR
↓
Disable Security
```

---

# 36. Automating Known Host Trust

Ansible includes tools for managing known-host entries.

For example, the relevant built-in module is:

```text
ansible.builtin.known_hosts
```

Use documented, verified host-key material.

Do not automatically trust arbitrary keys returned by an untrusted network path.

---

# 37. Privilege Escalation

Sometimes the remote SSH user cannot perform a required operation.

For example:

```text
Install system package

Modify /etc configuration

Create system user

Restart system service
```

These operations may require elevated privileges.

Ansible calls privilege escalation:

```text
become
```

---

# 38. `become`

Example:

```yaml
---
- name: Configure Linux servers
  hosts: web
  become: true

  tasks:
    - name: Ensure Nginx is installed
      ansible.builtin.package:
        name: nginx
        state: present
```

Conceptually:

```text
SSH User
↓
Privilege Escalation
↓
Elevated Identity
↓
Task
```

---

# 39. `become` Does Not Mean "Always Root"

Privilege escalation means becoming another user through an appropriate become mechanism.

The common Linux case is:

```text
sudo
↓
root
```

but Ansible supports multiple become mechanisms.

Do not reduce the concept to:

```text
become = root
```

---

# 40. `become_user`

You can specify the target identity.

Example:

```yaml
become: true
become_user: application
```

This means:

```text
Use privilege escalation
↓
Become application
```

rather than necessarily becoming root.

---

# 41. Important `become_user` Concept

Setting:

```yaml
become_user: application
```

does not by itself enable privilege escalation.

You still need:

```yaml
become: true
```

where escalation is required.

Think:

```text
become
=
Should escalation happen?
```

```text
become_user
=
Which identity should we become?
```

---

# 42. Become Methods

Ansible supports become plugins for systems such as:

```text
sudo

su

doas
```

and others.

Inspect available plugins:

```bash
ansible-doc -t become -l
```

Then inspect one:

```bash
ansible-doc -t become ansible.builtin.sudo
```

Use the mechanism appropriate to the target platform.

---

# 43. Least Privilege With `become`

Bad model:

```text
Automation User
↓
NOPASSWD: ALL
↓
root
↓
Anything
```

This may be easy.

It may also grant far more privilege than the automation actually requires.

A better security review asks:

```text
Which commands/actions are required?

Which systems require them?

Which automation identity needs them?

Can the scope be reduced?

Can privilege be separated by role?
```

---

# 44. Sudo Configuration

Linux sudo policy is commonly managed through:

```text
/etc/sudoers
```

and:

```text
/etc/sudoers.d/
```

Do not edit sudo policy carelessly.

A malformed sudo configuration can break administrative access.

---

# 45. Validate Sudo Configuration

When creating sudo configuration, use appropriate validation.

For example, `visudo` provides syntax validation capabilities.

Ansible file/template deployment can also use validation mechanisms where supported.

The principle is:

```text
Generate
↓
Validate
↓
Install
```

not:

```text
Overwrite sudo policy
↓
Hope
```

---

# 46. Example Sudo Template Deployment

Conceptually:

```yaml
- name: Deploy automation sudo policy
  ansible.builtin.template:
    src: automation-sudoers.j2
    dest: /etc/sudoers.d/automation
    owner: root
    group: root
    mode: "0440"
    validate: "/usr/sbin/visudo -cf %s"
  become: true
```

Always test the actual policy in a disposable environment first.

---

# 47. Why `0440`?

A sudo policy file does not need to be writable by ordinary users.

Example:

```text
Owner: root

Group: root

Mode: 0440
```

The exact security policy must match your environment.

---

# 48. Become Passwords

Some sudo configurations require a password.

Ansible can prompt for privilege-escalation credentials.

For example:

```bash
ansible-playbook site.yml --ask-become-pass
```

Do not hardcode the become password into:

```text
site.yml

inventory.ini

README.md
```

---

# 49. Secrets

A secret is information that must not be disclosed to unauthorized users.

Examples:

```text
Passwords

API tokens

Private keys

Cloud access credentials

Database credentials

OAuth client secrets

TLS private keys

Service-account credentials

Vault passwords
```

---

# 50. Configuration Is Not Automatically a Secret

Examples:

```text
HTTP port = 8080

Application environment = production

Package version = 1.4.2
```

may be configuration but not necessarily secrets.

Separate:

```text
Configuration Data
```

from:

```text
Secret Data
```

This improves security design.

---

# 51. Secret Lifecycle

Think beyond storage.

```text
Secret Created
↓
Stored
↓
Distributed
↓
Retrieved
↓
Used
↓
Logged?
↓
Rotated
↓
Revoked
↓
Destroyed
```

A secret-management strategy must consider the entire lifecycle.

---

# 52. Hardcoded Secrets Are Dangerous

Bad:

```yaml
db_password: SuperSecretPassword123
```

If committed, it can spread into:

```text
Git history

Developer clones

CI logs

Backups

Forks

Caches

Code review systems
```

Removing the current line later does not necessarily remove the historical exposure.

---

# 53. Inventory Secrets

Do not place plaintext secrets casually into:

```text
inventory.ini

hosts.yml

group_vars

host_vars
```

if those files are stored insecurely.

Variables are data containers.

They are not encryption.

---

# 54. Environment Variables

Secrets are sometimes passed through environment variables.

Example concept:

```bash
export APPLICATION_TOKEN="..."
```

This can be preferable to committing the secret to Git.

But environment variables are not magically secure.

They may leak through:

```text
Debug output

Process environments

CI configuration

Crash reports

Child processes

Shell history if assigned carelessly

Misconfigured logs
```

Use them according to your platform's threat model.

---

# 55. Avoid Secrets in Command-Line Arguments

Be cautious with:

```bash
some-command --password SECRET
```

Command-line arguments can sometimes be exposed through:

```text
Process listings

Shell history

CI logs

Audit systems
```

Prefer secure credential mechanisms supported by the tool.

---

# 56. Ansible Vault

Ansible Vault encrypts Ansible variables and files.

It allows sensitive data to be stored in encrypted form rather than plaintext.

Think:

```text
Plaintext Secret
↓
Ansible Vault Encryption
↓
Encrypted Data
↓
Git Repository
```

Then during execution:

```text
Encrypted Data
+
Vault Password
↓
Decryption
↓
Ansible Runtime
↓
Secret Used
```

---

# 57. Critical Vault Limitation

Ansible Vault protects:

```text
DATA AT REST
```

It does not automatically protect:

```text
DATA IN USE
```

Once decrypted, a secret may still leak through:

```text
Task output

Debug statements

Templates

Logs

Callbacks

Error messages

External commands

Application logs
```

This distinction is fundamental.

---

# 58. `ansible-vault`

Inspect the command:

```bash
ansible-vault --help
```

Core actions include:

```text
create

encrypt

encrypt_string

edit

view

rekey

decrypt
```

---

# 59. Create an Encrypted File

Run:

```bash
ansible-vault create group_vars/production/vault.yml
```

You will be prompted for a vault password unless another password source is configured.

Your editor opens.

Add sensitive variables.

Example:

```yaml
---
vault_database_password: "training-secret"
vault_application_token: "training-token"
```

When you close the editor, the file is stored encrypted.

Use fake secrets in training.

---

# 60. Inspect the Encrypted File

Run:

```bash
cat group_vars/production/vault.yml
```

You should not see the plaintext variables.

Instead you will see an Ansible Vault payload beginning with a header similar to:

```text
$ANSIBLE_VAULT;...
```

Do not manually edit the encrypted payload.

---

# 61. Encrypt an Existing File

Suppose you already have:

```text
secrets.yml
```

Encrypt it:

```bash
ansible-vault encrypt secrets.yml
```

Verify:

```bash
cat secrets.yml
```

The plaintext should no longer be directly visible.

---

# 62. Important Before Encrypting

Encryption does not erase previous copies.

If plaintext already existed in:

```text
Git history

Backups

CI artifacts

Chat messages

Email

Shared drives
```

encrypting the current file does not undo the previous exposure.

You may need rotation and incident response.

---

# 63. View an Encrypted File

Use:

```bash
ansible-vault view secrets.yml
```

Provide the correct vault password.

This decrypts the content for viewing without permanently replacing the encrypted file with plaintext.

---

# 64. Edit an Encrypted File

Use:

```bash
ansible-vault edit secrets.yml
```

Conceptually:

```text
Encrypted File
↓
Temporary Decryption for Editing
↓
Editor
↓
Save
↓
Encrypted Again
```

Your editor environment therefore becomes part of the security boundary.

---

# 65. Editor Security

When editing secrets, consider whether your editor creates:

```text
Swap files

Backup files

Recovery files

Temporary files

Cloud synchronization copies

Plugin telemetry
```

Vault encryption does not protect plaintext copies created independently by an editor.

---

# 66. Rekey an Encrypted File

If you need to change the vault secret:

```bash
ansible-vault rekey secrets.yml
```

Conceptually:

```text
Old Vault Password
↓
Decrypt
↓
New Vault Password
↓
Re-encrypt
```

---

# 67. When Should You Rekey?

Examples:

```text
Team member loses access

Vault password may be exposed

Credential-management policy changes

Environment separation changes

Periodic rotation policy requires it
```

Rekeying changes the Vault encryption password.

It does not automatically rotate the application secrets stored inside.

---

# 68. Vault Password vs Stored Secret

Do not confuse:

```text
Vault Password
```

with:

```text
Database Password Stored Inside Vault
```

Changing one does not automatically change the other.

Example:

```text
Vault Password Rotated
↓
File Encryption Changed
```

but:

```text
Database Password
↓
Still Same
```

unless you rotate it separately.

---

# 69. Decrypt a File

You can permanently decrypt a vaulted file:

```bash
ansible-vault decrypt secrets.yml
```

Afterward the file is plaintext.

That is materially different from:

```bash
ansible-vault view secrets.yml
```

Use `decrypt` deliberately.

---

# 70. Why Permanent Decryption Is Risky

After:

```bash
ansible-vault decrypt secrets.yml
```

the file may become:

```text
Readable by tools

Visible to editors

Accidentally committed

Copied into backups

Indexed

Uploaded
```

Re-encrypt promptly if plaintext storage was not intentional.

---

# 71. Encrypt Individual Variables

You do not always need to encrypt an entire file.

Ansible Vault can encrypt individual strings.

Use:

```bash
ansible-vault encrypt_string
```

A safer interactive pattern is:

```bash
ansible-vault encrypt_string --ask-vault-pass --stdin-name 'vault_database_password'
```

Then enter the secret through standard input when prompted.

---

# 72. Why Avoid Putting the Secret Directly in the Command?

You may encounter examples such as:

```bash
ansible-vault encrypt_string 'my-secret' --name 'password'
```

This may expose sensitive data through:

```text
Shell history

Process inspection

Terminal recording

CI logs
```

Prefer interactive or controlled input mechanisms for real secrets.

---

# 73. Encrypted Variable Shape

An encrypted variable may look conceptually like:

```yaml
vault_database_password: !vault |
  $ANSIBLE_VAULT;...
  ENCRYPTED_DATA
```

The exact encrypted payload will differ.

Do not copy someone else's encrypted example and expect your vault password to decrypt it.

---

# 74. Whole-File Encryption vs Variable Encryption

Whole-file encryption:

```text
Everything Hidden
```

Advantages:

```text
Variable names hidden

Simple mental model
```

Disadvantages:

```text
Harder code review

Harder diffs
```

Variable-level encryption:

```text
Structure Visible
+
Secret Value Encrypted
```

Advantages:

```text
Better context

Potentially easier review
```

Disadvantages:

```text
Variable names and surrounding structure remain visible
```

Choose intentionally.

---

# 75. Public Variable + Vault Variable Pattern

A useful pattern is:

```yaml
database_host: db01.internal
database_port: 5432
database_user: application
database_password: "{{ vault_database_password }}"
```

Then store:

```yaml
vault_database_password: ...
```

in encrypted content.

This separates:

```text
Normal Configuration
```

from:

```text
Secret Material
```

---

# 76. Naming Secret Variables

A common convention is:

```text
vault_database_password

vault_api_token

vault_service_key
```

Then normal variables reference them.

Example:

```yaml
application_token: "{{ vault_application_token }}"
```

The prefix itself does not provide security.

It provides clarity.

---

# 77. Vault Passwords

Encrypted content requires the correct vault password or password source.

The vault password is itself:

```text
A Secret
```

Do not solve secret storage by:

```text
Encrypting secrets
↓
Committing the decryption password beside them
```

That defeats the architecture.

---

# 78. Prompt for Vault Password

Run:

```bash
ansible-playbook site.yml --ask-vault-pass
```

Ansible prompts interactively.

This is useful for:

```text
Learning

Manual execution

Some controlled administrative workflows
```

It is usually inconvenient for unattended CI.

---

# 79. Vault Password Files

You can supply a password file:

```bash
ansible-playbook site.yml \
  --vault-password-file /secure/path/vault.pass
```

The file contains the vault password.

Protect it.

---

# 80. Secure Vault Password File

Example:

```bash
chmod 600 /secure/path/vault.pass
```

Then verify:

```bash
ls -l /secure/path/vault.pass
```

And:

```text
DO NOT COMMIT IT TO GIT.
```

# 88. Critical Vault ID Nuance

A Vault ID label is not automatically a cryptographic identity boundary.

```text

=
Absolute enforced isolation
```

Ansible has configuration related to matching vault IDs when stricter behavior is desired.

Understand your configuration.

# 100. AWS Secrets Manager With Ansible

The `amazon.aws` collection provides a Secrets Manager lookup plugin.


# 101. AWS Secret Lookup Concept

```yaml
       'amazon.aws.secretsmanager_secret',
```

# 102. Where Does the AWS Lookup Execute?

Therefore:

```text

↓

↓
```

This can be an important security advantage.

# 110. `no_log`

Ansible tasks may display sensitive values.

You can suppress task result logging with:

```yaml
no_log: true
```

Example:

```yaml
- name: Configure application credential
  ansible.builtin.template:
    src: app-secrets.j2
    dest: /etc/myapp/secrets.conf
    owner: root
    group: root
    mode: "0600"
  no_log: true
```

Use `no_log` when task output could expose sensitive data.

---

# 111. Why `no_log` Matters

Without appropriate protection, output could expose:

```text
Passwords

Tokens

API responses

Secret variables

Module arguments

Error messages containing credentials
```

Logs are often retained much longer than terminal sessions.

---

# 112. `no_log` Is Not Encryption

`no_log: true` does not encrypt:

```text
The source variable

The destination file

The network connection

The secret manager

The application

The managed host
```

It primarily controls Ansible's task output/logging behavior.

---

# 113. `no_log` Has Limits

Do not think:

```text
no_log: true
=
Secret cannot leak
```

A secret may still be exposed through:

```text
Application logs

External commands

Files

Templates

Shell tracing

Other tasks

Callback/plugin behavior

Debug statements elsewhere

Remote process behavior

Misconfigured CI
```

Treat it as one control.

---

# 114. Do Not Debug Secrets

Bad:

```yaml
- name: Show password
  ansible.builtin.debug:
    var: database_password
```

Even if you intend to delete the line later, it may enter:

```text
CI logs

Terminal logs

Screenshots

Chat transcripts

Support tickets
```

Debug metadata.

Not secrets.

---

# 115. Safe Debugging Pattern

Instead of:

```text
Print secret value
```

verify:

```text
Is variable defined?

Is expected structure present?

Did secret lookup succeed?

Did dependent service authenticate?
```

without revealing the secret.

---

# 116. Secret Verification

Do not verify a password by printing it.

Verify the outcome.

Example:

```text
Retrieve Database Credential
↓
Configure Application
↓
Start Application
↓
Application Connects Successfully
```

Success is the verification.

The secret value does not need to be displayed.

# 117. Secure Templates

Templates can contain secrets.

Example:

```jinja2

DATABASE_PASSWORD={{ database_password }}
```

The rendered destination becomes sensitive.

---

# 118. Secure Template Destination

Example:

```yaml
- name: Deploy application environment file
  ansible.builtin.template:
    src: app.env.j2
    dest: /etc/myapp/app.env
    owner: root
    group: myapp
    mode: "0640"
  no_log: true
  notify: Restart application
```

Permissions must match the application's actual runtime needs.

Do not automatically use `0644` for secret-bearing configuration.

```text
+

↓

↓

↓
```

# 130. Incident Response Mental Model

```text
Secret Exposure Discovered
↓
Assume Compromise According to Risk
↓
Revoke / Rotate Secret
↓
Investigate Exposure
↓
Remove Secret From Current Code
↓
Address Repository History If Required
↓
Check Logs / Artifacts / Forks / Caches
↓
Update Secure Storage
↓
Verify New Credential
↓
Document Incident
```

Rotation comes first because history rewriting cannot make an exposed credential trustworthy again.

---

# 131. Rotation

Rotation means replacing a credential with a new credential and invalidating the old one.

Examples:

```text
API Token A
↓
API Token B
↓
Revoke A
```

or:

```text
Database Password Old
↓
Database Password New
↓
Update Consumers
↓
Disable Old
```

---

# 132. Rotation Requires Coordination

Changing a secret too early can cause an outage.

Think:

```text
Create New Credential
↓
Store Securely
↓
Update Consumers
↓
Verify New Credential
↓
Revoke Old Credential
```

Exact order depends on whether the underlying system supports overlapping credentials.

---

# 133. Rotation and Ansible Vault

If an application password changes:

```text
Application Credential
↓
Rotate
↓
Update Vaulted Value
↓
Deploy
↓
Verify
```

If the Vault encryption password changes:

```text
ansible-vault rekey
```

These are separate operations.

# 136. Secure Role Design

A reusable role should not contain environment secrets.

Bad role:

```text
roles/database/defaults/main.yml
↓
production_database_password: REAL_PASSWORD
```

A role should define an interface.

The caller supplies sensitive data securely.

---

# 137. Role Security Boundary

Think:

```text
ROLE
↓
Defines Required Input
```

not:

```text
ROLE
↓
Owns Every Production Secret
```

Example:

```yaml
database_password: "{{ vault_database_password }}"
```

The role consumes the value.

Secret management occurs outside the reusable implementation.

---

# 138. Defaults Must Not Contain Real Secrets

Role defaults are designed to provide default values.

They are generally inappropriate for production secrets.

Bad:

```yaml
database_password: "ProdPassword123"
```

Better:

```yaml
database_password: ""
```

or require the caller to supply the value and validate that requirement.

---

# 139. Validate Required Sensitive Inputs

A role can verify that required data exists without printing it.

Example:

```yaml
- name: Validate required database secret
  ansible.builtin.assert:
    that:
      - database_password is defined
      - database_password | length > 0
    fail_msg: "database_password must be provided securely."
  no_log: true
```

This verifies presence without intentionally displaying the value.

---

# 140. Do Not Hide Everything With `no_log`

Overusing:

```yaml
no_log: true
```

can make troubleshooting difficult.



# 190. Production Secret Standard

A mature production policy should establish rules such as:

```text
No plaintext production secrets in Git.

No production private keys in Git.

No Vault password stored beside encrypted content.

No secret output in CI logs.

No unrestricted production credential where narrower access is possible.

No unreviewed secret-manager access.

No dependency gets production credentials without review.

Secrets must have owners.

Secrets must have rotation procedures.

Exposed secrets must be revoked or rotated.

Environment boundaries must be preserved.

Production access must be auditable.
```

# 204. Secure Tasks

```yaml
---
- name: Validate required secrets
  ansible.builtin.assert:
    that:
      - application_database_password is defined
      - application_database_password | length > 0
      - application_api_token is defined
      - application_api_token | length > 0
    fail_msg: "Required application secrets were not provided."
  no_log: true

- name: Ensure application group exists
  ansible.builtin.group:
    name: "{{ application_group }}"
    state: present
  become: true

- name: Ensure application user exists
  ansible.builtin.user:
    name: "{{ application_user }}"
    group: "{{ application_group }}"
    create_home: false
    system: true
    state: present
  become: true

- name: Ensure application configuration directory exists
  ansible.builtin.file:
    path: "{{ application_config_directory }}"
    state: directory
    owner: root
    group: "{{ application_group }}"
    mode: "0750"
  become: true

- name: Deploy protected application configuration
  ansible.builtin.template:
    src: application.env.j2
    dest: "{{ application_config_directory }}/application.env"
    owner: root
    group: "{{ application_group }}"
    mode: "0640"
  become: true
  no_log: true
  notify: Restart application
```

Granting only the permissions necessary for a required operation.

To prevent unauthorized users from reading or using the private key.

It makes the file broadly accessible and destroys the intended protection.

The initial account Ansible uses when connecting to a managed host.

Ansible's privilege-escalation mechanism.

The identity Ansible should become during privilege escalation.

No. `become` must also be enabled where escalation is required.

Because direct unrestricted root access increases blast radius and removes useful privilege boundaries.

Allowing only the privileged operations actually required.

Sensitive information that unauthorized users should not obtain.

Variables organize data but do not encrypt it.

Sensitive Ansible variables and files at rest.

It does not automatically protect decrypted secrets while they are in use.
