# 2. What Is a Server Baseline?

A server baseline is the minimum configuration that a server should have before workloads are placed on it.

For example:

```text
Correct administrative users

Approved SSH keys

Required operating-system packages

Correct timezone

Correct hostname

Required directories

Correct permissions

Required services enabled

Required kernel settings

Scheduled maintenance tasks

Standard environment configuration
```

Different organizations will have different baselines.

A web server baseline may differ from a database server baseline.

But many systems share a common foundation.

# 6. Generic `package` Module

The generic module is:

```text
ansible.builtin.package
```

Example:

```yaml
- name: Ensure curl is installed
  ansible.builtin.package:
    name: curl
    state: present
```

The purpose is simple:

```text
Tell Ansible what package state you want
↓
Let Ansible use the appropriate underlying package manager
```

---

# 7. Package State

A common desired state is:

```yaml
state: present
```

Meaning:

```text
The package must be installed.
```

Example:

```yaml
- name: Install Git
  ansible.builtin.package:
    name: git
    state: present
```

If Git is missing:

```text
CHANGED
```

If the required package is already installed:

```text
OK
```

That is declarative configuration management.

---

# 8. Removing Packages

Use:

```yaml
state: absent
```

Example:

```yaml
- name: Remove obsolete package
  ansible.builtin.package:
    name: some-obsolete-package
    state: absent
```

Mental model:

```text
Desired State
↓
Package Absent

Installed?
├── YES → Remove → CHANGED
└── NO  → Nothing Required → OK
```

Do not experiment with removal on systems you care about.

Packages can have dependencies and operational consequences.

---

# 9. Installing Multiple Packages

You can provide a list.

```yaml
- name: Install baseline packages
  ansible.builtin.package:
    name:
      - curl
      - git
      - vim
      - unzip
      - rsync
    state: present
```

This is usually clearer than writing five nearly identical tasks.

---

# 10. Why Use the Generic Package Module?

The generic module is useful when:

```text
The operation is simple

Package names are consistent

You do not require package-manager-specific functionality
```

Example:

```yaml
ansible.builtin.package:
  name: curl
  state: present
```

may work across several supported distributions.

---

# 11. Generic Does Not Mean Universal

This is important.

Suppose Ubuntu calls a package:

```text
example-dev
```

while another distribution calls it:

```text
example-devel
```

The generic package module does not magically make package names identical.

You may need distribution-specific variables.

Example:

```yaml
baseline_packages:
  Debian:
    - curl
    - git
    - example-dev

  RedHat:
    - curl
    - git
    - example-devel
```

The abstraction is useful, but operating-system differences still exist.

# 13. APT

APT is commonly used by Debian-family systems, including Ubuntu.

Ansible provides:

```text
ansible.builtin.apt
```

Basic example:

```yaml
- name: Install nginx on Debian-family systems
  ansible.builtin.apt:
    name: nginx
    state: present
```

---

# 14. Updating the APT Cache

Package metadata can become stale.

Ansible can update the APT cache:

```yaml
- name: Update APT cache
  ansible.builtin.apt:
    update_cache: true
```

You can also combine cache update and installation:

```yaml
- name: Install nginx with refreshed package metadata
  ansible.builtin.apt:
    name: nginx
    state: present
    update_cache: true
```

---

# 15. Cache Validity

Constantly refreshing package metadata can waste time.

APT automation can use cache-age controls where appropriate.

Conceptually:

```text
Is cache sufficiently recent?
├── YES → Reuse
└── NO  → Refresh
```

The exact policy should match your environment.

# 17. APT Package Versions

Sometimes you need a specific version.

APT package syntax commonly follows a form such as:

```text
package=version
```

Example structure:

```yaml
- name: Install an explicitly selected package version
  ansible.builtin.apt:
    name: "example-package={{ required_package_version }}"
    state: present
```

Do not copy an invented version number from a tutorial.

First inspect versions available from the repositories configured on your actual system.

---

# 18. Why Version Pinning Exists

Imagine production has been tested with:

```text
Application Dependency
↓
Version X
```

Automatically moving to:

```text
Version Y
```

could introduce:

```text
Behavior changes

Configuration changes

Dependency changes

Compatibility problems

Security fixes

Breaking changes
```

Package-version strategy is an engineering decision.

---

# 19. `present` vs `latest`

Compare:

```yaml
state: present
```

with:

```yaml
state: latest
```

Conceptually:

```text
present
↓
Ensure some acceptable installed version exists
```

```text
latest
↓
Move toward the latest version available from configured repositories
```

Do not blindly use:

```yaml
state: latest
```

everywhere in production.

# 24. Distribution Detection

Facts can help choose operating-system-specific tasks.

Example:

```yaml
- name: Install Debian packages
  ansible.builtin.apt:
    name: "{{ baseline_packages }}"
    state: present
    update_cache: true
  when: ansible_facts['os_family'] == 'Debian'
```

And:

```yaml
- name: Install Red Hat family packages
  ansible.builtin.dnf:
    name: "{{ baseline_packages }}"
    state: present
  when: ansible_facts['os_family'] == 'RedHat'
```

You learned the pieces already:

```text
Facts
+
Conditionals
+
Package Modules
```

Now we are combining them.

# 33. Generic `service` Module

Example:

```yaml
- name: Ensure nginx is running
  ansible.builtin.service:
    name: nginx
    state: started
```

This describes desired runtime state.

---

# 34. Starting a Service

```yaml
- name: Start nginx
  ansible.builtin.service:
    name: nginx
    state: started
```

Mental model:

```text
Nginx Running?
├── YES → OK
└── NO  → Start → CHANGED
```

---

# 35. Stopping a Service

```yaml
- name: Stop nginx
  ansible.builtin.service:
    name: nginx
    state: stopped
```

This ensures the service is not running.

Stopping services can create outages.

Target carefully.

---

# 36. Restarting a Service

```yaml
- name: Restart nginx
  ansible.builtin.service:
    name: nginx
    state: restarted
```

Restart means:

```text
Stop
+
Start
```

Operationally, that can cause interruption.

Do not restart a service after every playbook run unless that is genuinely required.

---

# 37. Reloading a Service

Some services can reload configuration without a complete process restart.

Example:

```yaml
- name: Reload nginx
  ansible.builtin.service:
    name: nginx
    state: reloaded
```

Whether reload is supported and what it means depends on the service.

Always check the service documentation.

---

# 38. Restart vs Reload

Think:

```text
Configuration Changed
↓
Can Service Safely Reload?
├── YES → Reload
└── NO  → Restart If Required
```

Reload may reduce disruption.

But never assume every service supports it.

---

# 39. Enabling a Service

A running service and a boot-enabled service are different concepts.

```text
Running
↓
What is happening now?
```

```text
Enabled
↓
Should it start automatically during boot?
```

Example:

```yaml
- name: Enable nginx at boot
  ansible.builtin.service:
    name: nginx
    enabled: true
```

---

# 40. Start and Enable Together

Common pattern:

```yaml
- name: Ensure nginx is enabled and running
  ansible.builtin.service:
    name: nginx
    state: started
    enabled: true
```

This manages:

```text
Current State
+
Boot State
```

---

# 41. Disabling a Service

```yaml
- name: Disable unnecessary service
  ansible.builtin.service:
    name: example-service
    enabled: false
```

This controls boot behavior.

If you also want it stopped:

```yaml
- name: Stop and disable unnecessary service
  ansible.builtin.service:
    name: example-service
    state: stopped
    enabled: false
```

You may encounter older examples using:

```text

```

```text
ansible.builtin.systemd_service
```

For new material, prefer the clearer FQCN:

```text
ansible.builtin.systemd_service
```

---

# 45. systemd Daemon Reload

Suppose you deploy:

```text
/etc/systemd/system/veriqta.service
```

systemd may need to reread unit definitions.

Ansible can request:

```yaml
- name: Reload systemd manager configuration
  ansible.builtin.systemd_service:
    daemon_reload: true
```

This is different from:

```text
Reloading an application service.
```

Do not confuse them.

---

# 46. Two Different Reloads

```text
daemon_reload
↓
Tell systemd to reread unit definitions
```

versus:

```text
state: reloaded
↓
Ask a service/unit to reload its own configuration
```

These solve different problems.

---

# 47. Service Handler Pattern

From Part 8 and Part 9:

```yaml
- name: Deploy application configuration
  ansible.builtin.template:
    src: app.conf.j2
    dest: /etc/veriqta/app.conf
    owner: root
    group: root
    mode: "0644"
  notify: Restart application
```

Handler:

```yaml
handlers:
  - name: Restart application
    ansible.builtin.systemd_service:
      name: veriqta
      state: restarted
```

Now restart happens because configuration changed.

---

# 48. Better Service Automation

Avoid:

```text
Install Package
↓
Restart Service

Every Run
```

Prefer:

```text
Install Package
↓
Deploy Configuration
↓
Configuration Changed?
├── NO → Continue
└── YES → Notify Handler
             ↓
          Restart/Reload
```

This reduces unnecessary disruption.

# 54. Home Directories

A normal interactive user often needs a home directory.

Example:

```text
/home/appadmin
```

Use:

```yaml
create_home: true
```

where appropriate.

Service accounts may have different requirements.

Do not assume every account needs an interactive home.

---

# 55. User Shells

A login shell might be:

```text
/bin/bash
```

But service accounts may intentionally use a non-login shell.

The correct shell depends on the account's purpose.

Ask:

```text
Does this human need interactive login?

Is this a service identity?

Should this account be prevented from interactive shell access?
```

Account configuration is a security decision.

# 57. Groups

---

# 58. Create Groups Before Depending on Them

A clean sequence is:

```text
Create Group
↓
Create User
↓
Assign User to Group
↓
Configure Permissions
```

Example:

```yaml
- name: Create application administrators group
  ansible.builtin.group:
    name: appadmins
    state: present

- name: Create application administrator
  ansible.builtin.user:
    name: appadmin
    groups:
      - appadmins
    append: true
    create_home: true
    shell: /bin/bash
    state: present
```

---

# 59. Supplementary Groups

A user can belong to multiple groups.

Example:

```yaml
groups:
  - appadmins
  - monitoring
```

Be careful with group-management semantics.

Removing or replacing supplementary memberships can unexpectedly remove access.

Understand the `append` behavior before changing existing accounts.

# 61. Password Concepts

Linux accounts may authenticate through several mechanisms.

Examples include:

```text
Password

SSH public key

Central identity provider

Directory service

Other PAM-backed mechanisms
```

Ansible's user module can manage password-related account data, but this requires care.

---

# 62. Never Put Plaintext Passwords in Playbooks

Do not write:

```yaml
password: MySecretPassword123
```

into a repository.

Linux user password fields generally expect an appropriate password hash rather than a plaintext password.

Even password hashes are sensitive authentication material.

Protect them.

---

# 63. Password Authentication vs SSH Keys

For administrative SSH access, organizations commonly use public-key authentication.

Conceptually:

```text
Administrator
│
├── Private Key
│   └── Remains Protected by Administrator
│
└── Public Key
    ↓
Managed Server
    ↓
authorized_keys
```

Never deploy someone's private SSH key to a server as though it were an authorized key.

# 66. Install an SSH Public Key

Suppose the control node has:

```text
~/.ssh/id_ed25519.pub
```

A task could use:

```yaml
- name: Install administrator SSH public key
  ansible.posix.authorized_key:
    user: appadmin
    state: present
    key: "{{ lookup('file', lookup('env', 'HOME') + '/.ssh/id_ed25519.pub') }}"
```

The lookup reads the public key from the control side.

---

# 67. Understand the SSH Key Flow

```text
Control Node
│
│ Public Key
│ ~/.ssh/id_ed25519.pub
│
↓
Ansible
↓
Managed Node
│
└── /home/appadmin/.ssh/authorized_keys
```

The private key stays protected.

---

# 68. Verify SSH Access Safely

Before disabling any existing access path, open a second terminal and verify the new account.

For example:

```bash
ssh appadmin@SERVER
```

Do not close your working administrative session until the replacement access path is proven.

This matters especially when changing remote authentication.

---

# 69. Avoid Locking Yourself Out

Dangerous sequence:

```text
Create New Account Incorrectly
↓
Disable Existing Administrator
↓
Discover New SSH Key Does Not Work
↓
Locked Out
```

Safer:

```text
Create New Account
↓
Install Key
↓
Verify Login
↓
Verify Privilege Escalation
↓
Only Then Retire Old Access
```

Access changes require staged verification.

---

# 70. `exclusive` SSH Key Management

The authorized-key module can manage keys exclusively.

Conceptually:

```text
exclusive: true
↓
Only specified authorized keys should remain
```

This is powerful.

It can also remove valid keys unexpectedly.

Do not use exclusive key management casually.

Also understand how exclusivity interacts with multiple keys and loops before using it.

---

# 71. Sudo

`sudo` allows authorized users to execute commands with another user's privileges, commonly root.

Example:

```bash
sudo systemctl restart nginx
```

But:

```text
SSH Access
```

and:

```text
Sudo Access
```

are separate privileges.

A user may be able to log in without being able to administer the server.

---

# 72. Sudo Configuration

Sudo configuration commonly exists in:

```text
/etc/sudoers
```

and:

```text
/etc/sudoers.d/
```

Never treat sudo configuration as an ordinary text file without validation.

A syntax mistake can break administrative access.

---

# 73. Dedicated Sudoers Files

A common pattern is:

```text
/etc/sudoers.d/appadmins
```

rather than stuffing every rule into the main file.

This improves separation and ownership.

---

# 74. Validate Sudo Configuration

When deploying sudoers configuration as a file or template, validate it.

Example pattern:

```yaml
- name: Deploy administrator sudo configuration
  ansible.builtin.copy:
    content: |
      %appadmins ALL=(ALL) ALL
    dest: /etc/sudoers.d/appadmins
    owner: root
    group: root
    mode: "0440"
    validate: "/usr/sbin/visudo -cf %s"
```

This is much safer than blindly writing the file.

---

# 75. Passwordless Sudo

You may encounter:

```text
NOPASSWD
```

Example concept:

```text
%group ALL=(ALL) NOPASSWD: ALL
```

Do not automatically give every administrator unrestricted passwordless sudo.

Evaluate:

```text
Automation requirements

Interactive-user requirements

Threat model

Audit requirements

Command scope

Privilege boundaries
```

---

# 76. More Restrictive Sudo

Where practical, a sudo rule can permit specific commands instead of:

```text
ALL
```

Mental model:

```text
User Needs to Restart One Service
```

does not automatically mean:

```text
User Needs Unrestricted Root Access
```

Least privilege applies to sudo too.

---

# 77. `community.general.sudoers`

There is also a dedicated module:

```text
community.general.sudoers
```

in the `community.general` collection.

It can manage sudoers rules without manually building every file.

Because it is not part of `ansible-core`, dependency management matters.

For now, understand both approaches:

```text
Validated sudoers file
```

and:

```text
Dedicated sudoers module
```

```text
Application software
```

```text
/etc/veriqta
↓
Configuration
```

```text

↓

```

```text

```

Actual application conventions may differ.

# 81. Create Application Directories

Example:

```yaml
- name: Create application directories
  ansible.builtin.file:
    path: "{{ item.path }}"
    state: directory
    owner: "{{ item.owner }}"
    group: "{{ item.group }}"
    mode: "{{ item.mode }}"
  loop:
    - path: /etc/veriqta
      owner: root
      group: appgroup
      mode: "0750"

    - path: /var/lib/veriqta
      owner: appuser
      group: appgroup
      mode: "0750"

    - path: /var/log/veriqta
      owner: appuser
      group: appgroup
      mode: "0750"
```

Now the loop is operating over structured data.

# 82. Permission Design

```text

```

as a universal fix.

```text
Who must write?

```

# 83. Cron

Cron is a traditional Unix/Linux scheduling system.

It runs commands according to schedules.

Examples:

```text
Nightly cleanup

Periodic backups

Log processing

Health scripts

Maintenance jobs
```

Ansible provides:

```text
ansible.builtin.cron
```

---

# 84. First Cron Job

Example:

```yaml
- name: Run cleanup every day
  ansible.builtin.cron:
    name: "veriqta cleanup"
    minute: "30"
    hour: "2"
    job: "/usr/local/bin/veriqta-cleanup"
```

This represents:

```text
02:30
↓
Every Day
↓
Run Cleanup Command
```

---

# 85. Cron Fields

Traditional cron uses:

```text
Minute
Hour
Day of Month
Month
Day of Week
```

Conceptually:

```text
* * * * *
│ │ │ │ │
│ │ │ │ └── Day of week
│ │ │ └──── Month
│ │ └────── Day of month
│ └──────── Hour
└────────── Minute
```

Be careful with schedules.

A scheduling mistake can run a job far more frequently than intended.

---

# 86. Cron User

Cron jobs run under an identity.

That matters because the identity controls:

```text
Filesystem access

Environment

Permissions

Available credentials

Home directory

PATH
```

Do not schedule everything as root.

Use the least privileged appropriate account.

---

# 87. Cron Environment Is Different

A command that works interactively may fail from cron because cron may have a different:

```text
PATH

HOME

Shell

Environment variables

Working directory
```

Prefer:

```text
Absolute command paths

Explicit environment

Explicit file paths
```

for important scheduled jobs.

---

# 88. Cron Environment Variables

The Ansible cron module can also manage cron environment entries.

For example, you may need an explicit:

```text
PATH
```

for a controlled job environment.

But do not put secrets casually into cron environment entries.

They may be visible in configuration.

---

# 89. Cron Idempotency

Ansible tracks managed cron jobs by name.

Therefore:

```yaml
name: "veriqta cleanup"
```

is operationally important.

Changing the name may cause Ansible to treat it as a different cron entry.

Use stable, descriptive names.

---

# 90. Removing a Cron Job

Example:

```yaml
- name: Remove obsolete cleanup job
  ansible.builtin.cron:
    name: "old cleanup job"
    state: absent
```

Again, identify the correct job precisely.

---

# 91. Cron vs systemd Timers

```text

```

Cron is still common and important to understand.

Systemd timers can offer stronger integration with:

```text

```

Do not assume cron is the only scheduling mechanism.

# 96. Kernel Configuration

The Linux kernel exposes runtime parameters through:

```text
sysctl
```

Examples can influence:

```text
Networking

Memory behavior

Kernel behavior

Security-related controls
```

These settings can have system-wide consequences.

---

# 97. sysctl Mental Model

Conceptually:

```text
Desired Kernel Parameter
↓
Persistent Configuration
↓
Kernel Runtime Value
```

You need to distinguish:

```text
Persisted value
```

from:

```text
Currently active value
```

depending on how you configure it.

---

# 98. `ansible.posix.sysctl`

Ansible provides:

```text
ansible.posix.sysctl
```

through the `ansible.posix` collection.

Example:

```yaml
- name: Enable IPv4 forwarding
  ansible.posix.sysctl:
    name: net.ipv4.ip_forward
    value: "1"
    state: present
    sysctl_set: true
    reload: true
```

Do not enable IP forwarding merely because this example exists.

Use kernel settings only when the system architecture requires them.

---

# 99. Why sysctl Requires Care

A kernel parameter can affect:

```text
Network routing

Memory pressure

TCP behavior

Security boundaries

Application performance

Host stability
```

Do not copy "Linux tuning" lists from random blogs into production.

Every setting needs a reason.

---

# 100. Verify sysctl

For a parameter such as:

```text
net.ipv4.ip_forward
```

you can inspect it on Linux with:

```bash
sysctl net.ipv4.ip_forward
```

You should verify both:

```text
Desired Persistent Configuration
```

and:

```text
Effective Runtime Value
```

where relevant.

---

# 101. Dangerous Performance Tuning

Avoid:

```text
Someone says this sysctl makes Linux faster
↓
Copy 30 values
↓
Deploy Everywhere
```

Prefer:

```text
Observed Requirement
↓
Understand Parameter
↓
Test
↓
Measure
↓
Review Risk
↓
Deploy
↓
Verify
```

Performance tuning without measurement is guesswork.

```yaml
    - name: Configure system hostname
```

# 152. Idempotency

A server baseline should be safe to run repeatedly.

First run:

```text
Create Group       CHANGED
Create User        CHANGED
Install Key        CHANGED
Install Packages   CHANGED
Create Directory   CHANGED
Deploy Config      CHANGED
Set Timezone       Maybe CHANGED
Set Hostname       Maybe CHANGED
Create Cron        CHANGED
Start Service      CHANGED
```

Second run:

```text
Group Correct       OK
User Correct        OK
Key Correct         OK
Packages Correct    OK
Directory Correct   OK
Config Correct      OK
Timezone Correct    OK
Hostname Correct    OK
Cron Correct        OK
Service Running     OK
```

That is the desired pattern.

# 153. Not Every Operation Is Naturally Idempotent

Compare:

```yaml
ansible.builtin.package:
  name: nginx
  state: present
```

with:

```yaml
ansible.builtin.command:
  cmd: useradd appadmin
```

The package module understands package state.

The raw command merely executes.

This is why purpose-built modules are usually preferable.

---

# 154. Bad User Automation

Avoid:

```yaml
- name: Create user
  ansible.builtin.shell: useradd appadmin
```

Why?

Second run may fail because the user already exists.

Use:

```yaml
ansible.builtin.user:
  name: appadmin
  state: present
```

The module understands desired state.

---

# 155. Bad Package Automation

Avoid:

```yaml
- name: Install nginx
  ansible.builtin.shell: apt-get install -y nginx
```

when:

```text
ansible.builtin.apt
```

already models the operation.

Purpose-built modules give Ansible more state awareness.

# 156. Bad Service Automation

Avoid:

```yaml

    cmd: systemctl start nginx
```

when:

```text

```

can express:


as desired state.

# 197. Production Decision Model

Before automating any Linux setting, ask:

```text
What state do I want?
↓
Which resource owns that state?
↓
Does an Ansible module model it?
↓
Is the module built-in or collection-based?
↓
What privileges are required?
↓
What could this change break?
↓
Is it idempotent?
↓
How will I verify it?
↓
How will I recover?
```

That is much stronger than:

```text
What shell command can make this happen?
```
