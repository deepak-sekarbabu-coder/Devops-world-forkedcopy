# 3. The Infrastructure Boundary

One of the most important lessons in the project is deciding what Ansible does **not** own.

Terraform already owns:

```text
VPC

Subnets

Routes

Security Groups

Load Balancer

EC2 Instances

IAM Infrastructure
```

Ansible owns:

```text
Operating-System Configuration

Users

Groups

Packages

Application Directories

Application Deployment

Configuration Files

Service Configuration

Security Baseline

Monitoring Configuration
```

The boundary is:

```text
Terraform
↓
Infrastructure Provisioning

Ansible
↓
Configuration Management
```

---

# 4. Why the Boundary Matters

Imagine Terraform creates:

```text
aws_instance.web_a
```

Then Ansible discovers that instance and configures Linux.

Do not have Terraform and Ansible independently fight over the same configuration.

For example:

```text
Terraform
↓
Creates EC2
```

and:

```text
Ansible
↓
Configures Nginx inside EC2
```

is a clear ownership model.

But:

```text
Terraform modifies /etc/nginx/nginx.conf

AND

Ansible modifies /etc/nginx/nginx.conf
```

creates conflicting ownership.

Production automation should answer:

```text
Who owns this state?
```

for every important resource.

# 74. Validate Before Installing Configuration

A stronger production design uses the module's validation capability when practical.

For example:

```yaml
- name: Deploy validated VERIQTA Nginx site configuration
  ansible.builtin.template:
    src: veriqta.conf.j2
    dest: /etc/nginx/sites-available/veriqta.conf
    owner: root
    group: root
    mode: "0644"
    validate: "/usr/sbin/nginx -t -c %s"
  notify: Reload Nginx
  become: true
```

However, native validators may require the candidate file to make sense as a complete configuration.

A site fragment cannot always be validated as though it were a complete main configuration.

Therefore test your validation strategy against the exact service layout rather than copying a command blindly.

# 103. Blocks, Rescue, and Always

Create a controlled deployment section:

```yaml
tasks:
  - name: Deploy and verify application
    block:
      - name: Apply application role
        ansible.builtin.include_role:
          name: application

      - name: Verify application endpoint
        ansible.builtin.uri:
          url: "http://127.0.0.1:80/health"
          status_code: 200

    rescue:
      - name: Report deployment failure
        ansible.builtin.debug:
          msg: "Application deployment or verification failed on {{ inventory_hostname }}"

    always:
      - name: Record deployment attempt
        ansible.builtin.debug:
          msg: "Deployment attempt completed on {{ inventory_hostname }}"
```

This demonstrates structured failure handling.

It does **not** automatically make rollback safe.

# 104. Build Rollback as an Explicit Operation

Create:

```text

```

For our static application, rollback means deploying a previously approved application version.

Do not invent an automatic magical rollback.

Require:

```text

```

Example precondition:

```yaml
---
- name: Roll back application
  hosts: role_web
  serial: 1
  become: true

  pre_tasks:

      ansible.builtin.assert:
        that:
          - rollback_application_version is defined
          - rollback_application_version | length > 0

  tasks:
    - name: Display rollback target
      ansible.builtin.debug:
        msg: "Rolling {{ inventory_hostname }} back to {{ rollback_application_version }}"
```

A real artifact-based application would retrieve that approved previous artifact.
