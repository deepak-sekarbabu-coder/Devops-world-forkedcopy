# Part 17: Ansible with AWS and Dynamic Inventory

## Move Ansible From Fixed Lab Machines Into Cloud Environments

Until now, most of our Ansible examples have assumed that we already know our servers.

We might have written an inventory like this:

```yaml
all:
  children:
    web:
      hosts:
        web01:
          ansible_host: 10.10.20.11
        web02:
          ansible_host: 10.10.20.12
        web03:
          ansible_host: 10.10.20.13
```

That works well in a lab.

It can also work in small environments where servers rarely change.

Cloud environments are different.

Imagine an AWS environment where:

```text
EC2 instances are created
↓
Instances are terminated
↓
Auto Scaling creates replacements
↓
IP addresses change
↓
Development environments appear
↓
Temporary environments disappear
↓
Applications scale
↓
New regions are introduced
```

A manually maintained inventory quickly becomes unreliable.

You do not want an engineer constantly editing:

```text
inventory.ini
```

every time AWS changes.

Instead, Ansible can ask AWS:

```text
Which EC2 instances currently exist?

Which ones are running?

Which ones belong to production?

Which ones are web servers?

Which ones are application servers?

Which ones are in this region?

What private IP addresses do they currently have?

What tags describe them?
```

AWS answers those questions through its APIs.

Ansible converts the returned infrastructure metadata into inventory.

This is **dynamic inventory**.

The architecture for this part is:

```text
Terraform
↓
AWS Infrastructure
↓
EC2 Tags
↓
Ansible Dynamic Inventory
↓
Discovered Hosts
↓
Roles
↓
Server Configuration
↓
Application
```

This is a major step forward.

We are moving from:

```text
Ansible knows three fixed lab servers.
```

to:

```text
Ansible discovers the current infrastructure automatically.
```

---

# 1. What Changes in the Cloud?

In a traditional environment, you might think of a server as:

```text
web01 = 10.10.20.11
```

and expect that relationship to remain stable.

In AWS, an EC2 instance has much more metadata:

```text
Instance ID
AMI
Instance type
Region
Availability Zone
VPC
Subnet
Private IP
Public IP
Security groups
IAM role
State
Tags
Launch time
```

The IP address is only one attribute.

The more important question becomes:

```text
What does this instance represent?
```

That is where tags become extremely useful.

# 4. Ansible and Cloud Infrastructure

Ansible can interact with AWS in two broad ways.

## Cloud control

Ansible can call AWS APIs to work with cloud resources.

Examples include:

```text
EC2 instances
Security groups
AMIs
Load balancers
S3
IAM-related resources
VPC-related resources
```

## Server configuration

Ansible can connect to operating systems and configure them.

Examples:

```text
Users

Packages

Services

Configuration files

Applications

Monitoring agents

Security settings
```

These are related but different responsibilities.

---

# 5. Infrastructure Provisioning vs Configuration Management

A useful production distinction is:

```text
Infrastructure Provisioning
```

versus:

```text
Operating-System and Application Configuration
```

Infrastructure provisioning answers:

```text
Should an EC2 instance exist?

Which subnet should it use?

Which security group?

Which IAM role?

Which load balancer?

Which VPC?

Which route table?
```

Configuration management answers:

```text
Which Linux users should exist?

Which packages should be installed?

Which service should run?

Which application version?

Which configuration file?

Which monitoring agent?

Which permissions?
```

# 10. Why Not Put Everything in Terraform?

Terraform does support provisioners.

However, HashiCorp recommends exhausting alternatives before using provisioners because Terraform cannot model provisioner behavior as predictably as normal infrastructure resources.

For operating-system configuration, a dedicated configuration-management system such as Ansible usually provides a cleaner architecture.

Use the right ownership tool for the right layer.

---

# 11. Why Not Let Both Tools Own the Same Thing?

Suppose Terraform manages:

```text
/etc/nginx/nginx.conf
```

and Ansible also manages:

```text
/etc/nginx/nginx.conf
```

Now two systems believe they own the same configuration.

That creates:

```text
Conflicting desired state

Unexpected changes

Difficult troubleshooting

Unclear ownership
```

Production rule:

```text
One resource or configuration concern should have a clearly defined owner.
```

# 21. AWS Authentication

Before Ansible can ask AWS:

```text
Which EC2 instances exist?
```

AWS must know:

```text
Who is making this request?
```

That is authentication.

Then AWS asks:

```text
What is this identity allowed to do?
```

That is authorization.

Keep those concepts separate.

---

# 22. Authentication vs Authorization

Authentication:

```text
Who are you?
```

Authorization:

```text
What may you do?
```

Example:

```text
Credentials valid
↓
Authentication succeeds
```

but:

```text
ec2:DescribeInstances not permitted
↓
Authorization fails
```

---

# 23. IAM

AWS Identity and Access Management is central to Ansible's AWS access.

IAM controls identities and permissions.

Conceptually:

```text
Principal
↓
IAM Policies
↓
Allowed AWS Actions
↓
AWS Resources
```

---

# 24. IAM Principal

An AWS API request operates as a principal.

Depending on the environment, that identity might come from:

```text
IAM role

Federated identity

AWS IAM Identity Center session

Assumed role

EC2 instance role

CI identity

Temporary STS credentials
```

Avoid building modern automation around unnecessary permanent credentials.

---

# 25. Least Privilege

Least privilege means:

```text
Grant only the permissions required for the automation's responsibility.
```

Suppose dynamic inventory only needs to discover EC2 metadata.

It should not automatically receive permission to:

```text
Terminate instances

Delete VPCs

Change IAM policies

Delete databases
```

because discovery does not require those actions.

---

# 26. Separate Discovery and Mutation Permissions

A strong design may distinguish:

```text
Inventory Discovery Identity
```

from:

```text
Infrastructure Mutation Identity
```

and:

```text
Configuration Deployment Identity
```

Not every automation stage needs the same permissions.

---

# 27. AWS Credential Sources

AWS tooling can obtain credentials through supported credential-provider mechanisms.

Depending on your environment, these may include:

```text
Environment variables

Shared AWS credential/config files

IAM Identity Center sessions

Assumed IAM roles

EC2 instance roles

Container/task roles

CI workload identity mechanisms
```

The exact credential chain is handled by the AWS SDK/tooling environment.

---

# 28. Do Not Put AWS Credentials in Playbooks

Bad:

```yaml
aws_access_key: AKIA...
aws_secret_key: very-secret-value
```

Worse:

```text
Commit that file to Git.
```

Credentials should come from secure credential mechanisms.

---

# 29. Environment Variables

AWS tooling commonly recognizes variables such as:

```text
AWS_ACCESS_KEY_ID
AWS_SECRET_ACCESS_KEY
AWS_SESSION_TOKEN
AWS_REGION
```

For temporary credentials, the session token matters.

But environment variables are still secrets.

Do not:

```text
Print them

Commit them

Paste them into logs

Include them in screenshots

Store them in shell history carelessly
```

---

# 30. Verify AWS Identity

Before blaming Ansible, verify the AWS identity being used.

With AWS CLI installed and authenticated:

```bash
aws sts get-caller-identity
```

Typical output contains:

```json
{
  "UserId": "...",
  "Account": "...",
  "Arn": "..."
}
```

This answers:

```text
Which AWS identity am I currently using?
```

That is one of the first AWS troubleshooting commands you should learn.

---

# 31. Short-Lived Credentials

Prefer temporary credentials where practical.

Temporary credentials:

```text
Expire automatically

Include an access key

Include a secret key

Include a session token
```

They reduce the lifetime of exposed credentials compared with long-lived static access keys.

They do not remove the need for:

```text
Least privilege

Secret handling

Audit logging

Secure CI design
```

---

```text
Engineer / CI Identity
↓
Authenticate
↓
Assume Deployment Role
↓
Temporary Credentials
↓

```

This becomes particularly useful across:

```text

```

---

# 33. Multi-Account Concept

Instead of one permanent credential with access everywhere:

```text
Central Identity
       |
       +---- Assume Dev Role
       |
       +---- Assume Staging Role
       |
       +---- Assume Production Role
```

Each role can have different permissions.

Production can have stricter controls.

---

# 34. EC2 Instance Roles

If Ansible or supporting automation runs on EC2, an IAM role can be associated with the instance.

AWS makes temporary credentials available through the instance metadata mechanism.

AWS SDKs can obtain those temporary credentials automatically.

That avoids storing long-lived AWS access keys on the EC2 machine.

# 35. CI Authentication

Conceptually:

```text

↓
Workload Identity
↓
AWS Role
↓
Temporary Credentials
↓
AWS API
```

rather than:

```text

↓

↓
```

# 36. AWS Regions

AWS resources exist within geographic regions.

Examples include region identifiers such as:

```text
us-east-1
us-west-2
eu-west-1
```

Do not assume your target resources exist in the region your tooling is currently querying.

---

# 37. Region Mistakes

Imagine your EC2 servers exist in:

```text
us-east-1
```

but your dynamic inventory queries:

```text
us-west-2
```

Result:

```text
No expected hosts discovered
```

You may incorrectly conclude:

```text
Inventory plugin is broken.
```

The actual problem is:

```text
Wrong region.
```

---

# 38. Region Should Be Explicit

For production inventory, prefer deliberate region configuration.

Example:

```yaml
regions:
  - us-east-1
```

Or multiple approved regions:

```yaml
regions:
  - us-east-1
  - us-west-2
```

Do not accidentally discover an entire global estate if the playbook should manage only one region.

# 43. Bad Tagging Strategy

Instance 1:

```text

```


# 44. Static Inventory Limitations

Suppose your inventory contains:

```ini
[web]
10.20.1.10
10.20.1.11
10.20.1.12
```

Then AWS replaces one instance.

Now the real environment is:

```text
10.20.1.10
10.20.1.11
10.20.1.27
```

but Ansible still thinks:

```text
10.20.1.12
```

exists.

This is inventory drift.

---

# 45. Inventory Drift

```text
AWS Changes
↓
Static Inventory Does Not Change
↓
Inventory Becomes Stale
↓
Automation Targets Wrong/Missing Hosts
```

This is why dynamic infrastructure benefits from dynamic discovery.

# 55. Filtering Running Instances

You normally do not want terminated or irrelevant instances.

Example concept:

```yaml
filters:
  instance-state-name: running
```

This tells discovery to focus on running instances.

---

# 56. Filter by Tag

Example:

```yaml
filters:
  instance-state-name: running
  tag:AnsibleManaged: "true"
```

Conceptually:

```text
All EC2 Instances
↓
Running Only
↓
AnsibleManaged=true
↓
Inventory
```

---

# 57. Environment Filtering

For a production-only inventory:

```yaml
filters:
  instance-state-name: running
  tag:Environment: production
  tag:AnsibleManaged: "true"
```

Now staging servers should not enter this inventory merely because they exist in the same account.

---

# 58. Why Filtering Is a Security Control

Inventory filtering is not only organizational convenience.

Suppose your playbook contains:

```text
Restart application
```

and your inventory accidentally includes:

```text
Production
Staging
Development
```

Your blast radius is much larger than intended.

Good discovery boundaries are part of safe automation.

# 60. Dynamic Grouping

Discovery answers:

```text
Which hosts exist?
```

Grouping answers:

```text
What do these hosts represent?
```

You might want groups such as:

```text
production

staging

web

api

worker
```

AWS tags provide the metadata needed to construct them.

---

# 61. `keyed_groups`

The AWS EC2 inventory plugin can construct groups from host metadata.

Conceptually:

```yaml
keyed_groups:
  - prefix: tag
    key: tags
```

This can create groups derived from tags.

Exact generated names depend on the plugin configuration and sanitization rules.

Always inspect:

```bash
ansible-inventory --graph
```

instead of guessing the final group name.

---

# 62. More Controlled Grouping

You can build groups from particular tag values.

For example, conceptually:

```yaml
keyed_groups:
  - prefix: environment
    key: tags.Environment

  - prefix: role
    key: tags.Role
```

If AWS contains:

```text
Environment = production
Role = web
```

you may obtain groups resembling:

```text
environment_production

role_web
```

Verify actual names from your environment.

---

# 63. Why Prefixes Matter

Without clear prefixes, a group called:

```text
production
```

does not tell you:

```text
Production what?
```

A group such as:

```text
environment_production
```

communicates intent.

Likewise:

```text
role_web
```

is clearer than:

```text
web
```

when generated automatically.

---

# 64. Environment Grouping

Suppose you have:

```text
Environment=development
Environment=staging
Environment=production
```

Dynamic groups can produce:

```text
environment_development
environment_staging
environment_production
```

Then a play can target:

```yaml
hosts: environment_production
```

But targeting only environment may still be too broad.

---

# 65. Combining Groups With Host Patterns

Suppose you have:

```text
environment_production
```

and:

```text
role_web
```

You want:

```text
Production web servers only.
```

Use an intersection pattern:

```text
environment_production:&role_web
```

Example:

```yaml
- name: Configure production web servers
  hosts: "environment_production:&role_web"
```

This builds on the inventory-pattern skills from Part 4.

---

# 66. Do Not Encode Everything Into One Group

Avoid creating endless groups like:

```text
production_web_east_team_a_customer_facing_blue
```

when separate dimensions can express:

```text
Environment
Role
Region
Team
Application
```

Then compose the target through inventory patterns.

# 68. Stable Inventory Identity

An EC2 instance ID is stable for the life of that instance.

An IP address may change.

This makes instance IDs useful inventory identities in many designs.

Then `ansible_host` can point to the actual network address.

# 84. Discovery vs Connection

This distinction is fundamental.

Because:

```text

```

while:

```text

```

Those are two different systems.

55. AWS discovery works, but the managed-node connection/execution path has a problem.

56. Wrong identity, account, region, permissions, filters, tags, state, or plugin configuration.

57. Invalid credentials are an authentication problem; AccessDenied is generally an authorization problem after an identity is recognized.

58. It destroys least privilege and hides the real permission requirement.

59. Missing tags, incorrect expressions, unexpected metadata, or group-name sanitization.

60. Private VPC addresses are not normally directly routable from the public Internet.

61. Wrong user, key, authorized-key configuration, or SSH policy.

62. Temporary credentials expire.

63. Valid automation could modify the wrong environment.

64. Tags can control which systems automation discovers and targets.

65. Temporarily storing discovered inventory data to reduce repeated source queries.

66. Fewer API calls versus potentially stale discovery.

67. Additional inventory information obtained from Systems Manager inventory when configured and authorized.

68. To make automation reproducible and prevent untested dependency changes.

69. Ansible may execute from a different Python environment than the shell/global Python installation.

70. Terraform creates AWS infrastructure and metadata; AWS exposes current EC2 state; Ansible dynamic inventory discovers that state; Ansible groups the hosts; roles configure the servers; application deployment and verification follow.

```text
Verify the AWS account.

Verify the AWS region.

Use least privilege.

Control tag mutation.

Filter inventory deliberately.

Inspect dynamic inventory before mutation.

Choose connection addresses deliberately.

Pin collections.
```
