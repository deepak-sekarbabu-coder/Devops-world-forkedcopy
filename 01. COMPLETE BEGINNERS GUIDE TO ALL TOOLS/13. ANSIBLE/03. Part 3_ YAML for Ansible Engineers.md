# Part 3: YAML for Ansible Engineers

## Learn to Read the Language Before Building Complex Automation

Ansible automation is written primarily using YAML.

Before you start building serious playbooks, roles, variables, inventories, handlers, and templates, you need to be comfortable reading structured YAML.

A beginner who skips YAML often reaches a frustrating stage where an Ansible error appears to be an Ansible problem when the actual problem is simply:

* incorrect indentation
* a list where a dictionary was expected
* a dictionary where a scalar was expected
* incorrect quoting
* malformed nesting
* an unexpected data type

Part 3 fixes that problem before it starts.

By the end of this part, you should be able to move naturally through:

```text
Scalar
↓
List
↓
Dictionary
↓
Nested Data
↓
Task
↓
Play
↓
Playbook
```

The goal is not:

> "I can copy YAML."

The goal is:

> "I can look at YAML and understand the data structure it represents."

---

# 1. What Is YAML?

YAML is a human-readable data-serialization language.

That sounds complicated.

It simply means YAML provides a structured way to represent data.

For example, imagine you want to describe a server.

You could write:

```text
Server name is web01.
Server port is 80.
Server is enabled.
```

YAML can represent the same information structurally:

```yaml
server_name: web01
port: 80
enabled: true
```

Now both humans and software can interpret the structure.

---

# 2. YAML Is Data, Not Just Formatting

This distinction is critical.

Consider:

```yaml
port: 80
```

This is not merely attractive formatting.

It represents a relationship:

```text
KEY
port

VALUE
80
```

Conceptually:

```text
port
↓
80
```

The YAML parser turns the text into structured data.

Ansible then works with that data.

---

# 3. Why Ansible Uses YAML

Ansible automation needs to describe things such as:

```text
Hosts

Variables

Tasks

Module arguments

Configuration

Lists of packages

Lists of users

Service settings

Handlers

Roles
```

YAML is useful because complex structures can remain relatively readable.

For example:

```yaml
packages:
  - nginx
  - git
  - curl
```

A human can quickly understand:

```text
packages
↓
three items
↓
nginx
git
curl
```

This readability is one reason YAML fits configuration-management workflows well.

---

# 4. YAML Does Not Execute the Server Configuration

This is an important mental model.

YAML itself does not:

```text
Install Nginx

Create users

Restart services

Connect to servers
```

YAML represents structured information.

Ansible interprets the structures according to Ansible's own rules.

Think:

```text
YAML
↓
Structured Data
↓
Ansible Interprets Structure
↓
Ansible Performs Automation
```

Do not confuse the serialization language with the automation engine.

---

# 5. YAML Files

YAML files commonly use:

```text
.yml
```

or:

```text
.yaml
```

For example:

```text
site.yml
```

or:

```text
site.yaml
```

Both extensions are widely encountered.

A repository might contain:

```text
ansible-project/
├── inventory.ini
├── ansible.cfg
├── site.yml
├── variables.yml
└── tasks.yml
```

The filename does not determine the data structure inside the file.

You must read the content.

---

# 6. YAML Documents

A YAML file can contain a YAML document.

A document may optionally begin with:

```yaml
---
```

This is called a document-start marker.

For example:

```yaml
---
server_name: web01
port: 80
```

The marker tells a YAML parser:

```text
A YAML document begins here.
```

You will frequently see it in Ansible examples.

---

# 7. Is `---` Always Required?

No.

Many YAML files parse correctly without it.

For example:

```yaml
server_name: web01
port: 80
```

can still be valid YAML.

Do not think:

```text
No ---
=
Invalid YAML
```

That is incorrect.

The document marker is useful and common, but its absence does not automatically make a YAML file invalid.

---

# 8. Document End Marker

YAML also defines:

```yaml
...
```

as a document-end marker.

For example:

```yaml
---
server_name: web01
port: 80
...
```

You will see `---` much more often than `...` in ordinary Ansible projects.

You do not need to add `...` to every file.

---

# 9. First YAML Building Block: Scalars

A scalar is a single value.

Examples:

```yaml
name: web01
```

```yaml
port: 443
```

```yaml
enabled: true
```

The values:

```text
web01

443

true
```

are scalar values.

Think:

```text
SCALAR
=
one value
```

---

# 10. Common Scalar Types

You will frequently work with:

```text
Strings

Numbers

Booleans

Null values
```

Later these values will appear inside larger structures.

---

# 11. Key-Value Pairs

One of the most important YAML patterns is:

```yaml
key: value
```

Example:

```yaml
hostname: web01
```

Here:

```text
hostname
=
key
```

and:

```text
web01
=
value
```

---

# 12. The Space After the Colon Matters

Write:

```yaml
hostname: web01
```

not:

```yaml
hostname:web01
```

In the first example, YAML clearly represents a mapping entry.

Get into the habit of writing:

```text
key:
SPACE
value
```

---

# 13. Strings

Strings represent text.

Example:

```yaml
hostname: web01
```

The value:

```text
web01
```

is interpreted as text.

Another example:

```yaml
environment: production
```

Another:

```yaml
application: payments-api
```

---

# 14. Strings Do Not Always Need Quotes

This is valid:

```yaml
name: nginx
```

So is:

```yaml
name: "nginx"
```

And:

```yaml
name: 'nginx'
```

For simple text values, quotes are often unnecessary.

But quoting becomes important when values contain special characters, ambiguous values, or syntax that could be interpreted differently.

---

# 15. Numbers

YAML can represent numeric values.

```yaml
port: 8080
```

Conceptually:

```text
port
↓
integer
↓
8080
```

Another:

```yaml
replicas: 3
```

These are different from:

```yaml
port: "8080"
```

because quoted `8080` is text.

---

# 16. Data Type Matters

Compare:

```yaml
port: 8080
```

with:

```yaml
port: "8080"
```

They look similar to a human.

But structurally:

```text
8080
=
number
```

while:

```text
"8080"
=
string
```

Software consuming the value may care about that distinction.

This is one source of subtle automation bugs.

---

# 17. Booleans

A Boolean represents two logical states.

For modern YAML written for Ansible, prefer explicit:

```yaml
enabled: true
```

or:

```yaml
enabled: false
```

Conceptually:

```text
true
=
yes, logically enabled
```

```text
false
=
no, logically disabled
```

---

# 18. Do Not Confuse Boolean and String

These are different:

```yaml
enabled: true
```

and:

```yaml
enabled: "true"
```

The first is intended as a Boolean.

The second is a string containing the characters:

```text
t r u e
```

This distinction matters when Ansible or a module expects a particular data type.

---

# 19. YAML Truth Values and Historical Confusion

YAML has had different schema behavior across versions and parsers.

Historically, values such as:

```text
yes
no
on
off
```

have caused confusion because some YAML parsing behavior interpreted them as Boolean-like values.

For Ansible automation, prefer clear Boolean values:

```yaml
enabled: true
```

```yaml
enabled: false
```

rather than relying on ambiguous-looking values.

The engineering rule is:

> Make the intended data type obvious.

---

# 20. Null Values

Null represents the absence of a meaningful value.

For example:

```yaml
middle_name: null
```

Conceptually:

```text
middle_name
↓
no value
```

Null is not the same as:

```yaml
middle_name: "null"
```

The quoted version is a string.

---

# 21. Empty and Null Are Not Always the Same Concept

Consider:

```yaml
description: ""
```

This represents an empty string.

Compare:

```yaml
description: null
```

This represents a null value.

Conceptually:

```text
""
=
a string containing zero characters
```

while:

```text
null
=
no value
```

Software may treat them differently.

---

# 22. First Data-Type Table

| YAML              | Intended Concept |
| ----------------- | ---------------- |
| `name: nginx`     | String           |
| `name: "nginx"`   | String           |
| `port: 80`        | Number           |
| `port: "80"`      | String           |
| `enabled: true`   | Boolean          |
| `enabled: "true"` | String           |
| `value: null`     | Null             |
| `value: "null"`   | String           |
| `value: ""`       | Empty string     |

Do not judge a value only by how it looks.

Ask:

> What data type will the parser create?

# 24. Lists

A list contains multiple ordered items.

Example:

```yaml
packages:
  - nginx
  - git
  - curl
```

Conceptually:

```text
packages
↓
LIST
├── nginx
├── git
└── curl
```

The hyphen identifies a list item.

---

# 25. Read a List Out Loud

When you see:

```yaml
packages:
  - nginx
  - git
  - curl
```

read it as:

> `packages` is a list containing `nginx`, `git`, and `curl`.

That simple habit makes unfamiliar YAML easier to understand.

---

# 26. List Indentation

Notice:

```yaml
packages:
  - nginx
  - git
  - curl
```

The list belongs to:

```text
packages
```

because it is nested underneath it.

Whitespace represents structure.

That is one of the most important YAML concepts.

---

# 27. Lists Can Contain Numbers

```yaml
ports:
  - 80
  - 443
  - 8080
```

Conceptually:

```text
ports
↓
LIST
├── 80
├── 443
└── 8080
```

---

# 28. Lists Can Contain Booleans

Technically:

```yaml
flags:
  - true
  - false
  - true
```

The list structure does not require every example to contain strings.

---

# 29. Inline Lists

YAML can also express a list using flow syntax:

```yaml
packages: [nginx, git, curl]
```

This represents the same basic data structure as:

```yaml
packages:
  - nginx
  - git
  - curl
```

For larger configuration structures, the block form is often easier to read.

Throughout this course, readability takes priority over making YAML artificially compact.

---

# 30. Dictionaries

A dictionary, also called a mapping, associates keys with values.

Example:

```yaml
server:
  hostname: web01
  port: 80
  enabled: true
```

Conceptually:

```text
server
↓
DICTIONARY
├── hostname → web01
├── port → 80
└── enabled → true
```

---

# 31. Dictionary vs List

Compare:

```yaml
packages:
  - nginx
  - git
```

This is:

```text
LIST
```

Compare:

```yaml
server:
  hostname: web01
  port: 80
```

This is:

```text
DICTIONARY
```

The difference is fundamental.

---

# 32. Mental Shortcut

When you see:

```yaml
- something
```

think:

```text
LIST ITEM
```

When you see:

```yaml
something: value
```

think:

```text
KEY → VALUE
```

When you see:

```yaml
something:
  another_key: value
```

think:

```text
NESTED DICTIONARY
```

---

# 33. Nested Data

YAML becomes powerful when structures are nested.

Example:

```yaml
server:
  hostname: web01
  network:
    ip_address: 192.0.2.10
    port: 443
```

Conceptually:

```text
server
↓
dictionary
├── hostname → web01
└── network
    ↓
    dictionary
    ├── ip_address → 192.0.2.10
    └── port → 443
```

---

# 34. Read Nested YAML From the Outside In

Do not start by staring at the deepest line.

Start here:

```yaml
server:
```

Ask:

> What is `server`?

Its indented children tell you.

Then:

```yaml
network:
```

Ask:

> What is `network`?

Again, inspect its children.

Read structure from the outside inward.

---

# 35. Lists of Dictionaries

This is one of the most important structures for Ansible engineers.

Example:

```yaml
users:
  - name: alice
    role: developer
  - name: bob
    role: administrator
```

What is `users`?

A list.

What does each list item contain?

A dictionary.

Conceptually:

```text
users
↓
LIST
├── DICTIONARY
│   ├── name → alice
│   └── role → developer
│
└── DICTIONARY
    ├── name → bob
    └── role → administrator
```

---

# 36. Recognizing a List of Dictionaries

Look at:

```yaml
- name: alice
  role: developer
```

The:

```text
-
```

starts a list item.

Inside that item:

```text
name
role
```

are dictionary keys.

Therefore:

```text
list item
↓
dictionary
```

---

# 37. Why Lists of Dictionaries Matter in Ansible

You will repeatedly encounter structures resembling:

```yaml
users:
  - name: alice
    groups:
      - developers
      - docker
  - name: bob
    groups:
      - administrators
```

Or:

```yaml
applications:
  - name: api
    port: 8080
  - name: frontend
    port: 3000
```

Understanding this structure now makes loops and variables much easier later.

---

# 38. Dictionaries Containing Lists

A dictionary value can itself be a list.

Example:

```yaml
server:
  hostname: web01
  packages:
    - nginx
    - curl
    - git
```

Conceptually:

```text
server
↓
DICTIONARY
├── hostname → web01
└── packages
    ↓
    LIST
    ├── nginx
    ├── curl
    └── git
```

# 39. More Complex Nested Data

Consider:

```yaml
server:
  hostname: web01
  network:
    ports:
      - 80
      - 443
  packages:
    - nginx
    - curl
```

Read it carefully.

```text
server
↓
dictionary
├── hostname → scalar
├── network → dictionary
│   └── ports → list
│       ├── 80
│       └── 443
└── packages → list
    ├── nginx
    └── curl
```

This is how you should mentally parse YAML.

# 41. Indentation Is Structure

In many programming languages, indentation is mostly presentation.

In YAML, indentation represents hierarchy.

Consider:

```yaml
server:
  hostname: web01
  port: 80
```

`hostname` and `port` belong underneath:

```text
server
```

because they are indented to the same level beneath it.

---

# 42. Think in Levels

Example:

```yaml
infrastructure:
  web:
    hostname: web01
    ports:
      - 80
      - 443
```

Think:

```text
LEVEL 0
infrastructure

LEVEL 1
web

LEVEL 2
hostname
ports

LEVEL 3
list items
```

Visualizing levels helps diagnose malformed YAML.

---

# 43. Spaces, Not Tabs

Use spaces for YAML indentation.

Do not use tab characters for indentation.

A file may visually appear aligned while containing a mixture of:

```text
spaces
+
tabs
```

and produce confusing parsing problems.

Configure your editor to insert spaces when working with YAML.

---

# 44. How Many Spaces?

A common convention in Ansible YAML is two spaces per indentation level.

For example:

```yaml
server:
  network:
    ports:
      - 80
      - 443
```

Notice the progression.

The most important rule is consistency and correct structural nesting.

Do not randomly alternate indentation widths.

---

# 45. Bad Indentation Example

This is structurally wrong for the intended relationship:

```yaml
server:
  hostname: web01
    port: 80
```

`port` has been pushed into an invalid or unintended indentation level.

A parser may reject the file.

---

# 46. Another Indentation Problem

Suppose you intended:

```yaml
server:
  hostname: web01
  port: 80
```

but wrote:

```yaml
server:
  hostname: web01
port: 80
```

This may still be valid YAML.

But it means something different.

The first structure is:

```text
server
├── hostname
└── port
```

The second is:

```text
server
└── hostname

port
```

The parser may accept it.

Your intended structure is still wrong.

This is an important lesson:

> Valid YAML does not necessarily mean correct configuration.

---

# 47. Syntax Errors vs Semantic Errors

There are at least two broad categories of mistakes.

## Syntax or parsing failure

The YAML parser cannot understand the document.

## Structurally valid but wrong data

The YAML parses successfully, but it does not represent what you intended.

The second category can be more dangerous.

---

# 48. Quoting

YAML supports unquoted, single-quoted, and double-quoted strings.

Examples:

```yaml
name: nginx
```

```yaml
name: 'nginx'
```

```yaml
name: "nginx"
```

All can represent strings.

But the quote styles behave differently.

---

# 49. Single Quotes

Example:

```yaml
message: 'Hello world'
```

Single quotes are useful when you want text to remain relatively literal.

Example:

```yaml
path: 'C:\temp\example'
```

Backslashes inside single-quoted YAML strings are not treated as double-quoted escape sequences.

---

# 50. Single Quote Inside a Single-Quoted String

To represent a literal single quote inside a single-quoted YAML string, double it.

Example:

```yaml
message: 'It''s running'
```

The resulting text conceptually represents:

```text
It's running
```

This syntax can look strange at first.

---

# 51. Double Quotes

Example:

```yaml
message: "Hello world"
```

Double-quoted YAML strings support escape sequences.

For example:

```yaml
message: "line one\nline two"
```

Here:

```text
\n
```

can represent a newline escape.

This differs from single-quoted strings.

---

# 52. When Quoting Helps

Quoting can help when a value:

* contains special characters
* could be interpreted as another data type
* contains leading or trailing spaces that matter
* begins with characters meaningful to YAML
* needs escape processing
* should clearly remain a string

Example:

```yaml
version: "1.0"
```

may communicate more clearly that the value should be treated as text.

---

# 53. Do Not Quote Everything Blindly

This:

```yaml
enabled: "true"
```

is not equivalent to deliberately supplying a Boolean:

```yaml
enabled: true
```

Likewise:

```yaml
port: "443"
```

is not the same data type as:

```yaml
port: 443
```

Quoting changes semantics.

Use it deliberately.

---

# 54. Special Characters

YAML gives structural meaning to several characters in particular contexts.

Examples include:

```text
:
-
#
[
]
{
}
&
*
!
|
>
%
@
`
```

You do not need to memorize the complete YAML grammar today.

You need to understand the engineering rule:

> If a string could be mistaken for YAML syntax, quote it appropriately.

---

# 55. The Colon

A colon followed by structural whitespace commonly separates a key from a value.

Example:

```yaml
protocol: https
```

If your string contains colon-space content, quoting may be needed.

Example:

```yaml
message: "Status: healthy"
```

This makes the intended scalar obvious.

---

# 56. The Hash Character

`#` begins a YAML comment when used in the appropriate context.

Example:

```yaml
port: 443  # HTTPS port
```

Everything after the comment marker is not part of the value.

But compare:

```yaml
password_example: "abc#123"
```

Inside the quoted string, the hash is part of the text.

---

# 57. Comments

Comments help explain configuration.

Example:

```yaml
# Public HTTPS port
port: 443
```

Inline comment:

```yaml
enabled: true  # Enable the service
```

Use comments to explain:

```text
Why

Constraints

Non-obvious decisions

Operational context
```

Do not use comments merely to translate obvious YAML into English.

Bad:

```yaml
port: 443  # This is the port
```

Better:

```yaml
port: 443  # Public HTTPS listener
```

---

# 58. Multiline Strings

Sometimes a value needs multiple lines.

For example:

```text
Welcome to the server.
This system is monitored.
Unauthorized access is prohibited.
```

YAML provides block scalar styles for this.

The two most important are:

```text
|
```

and:

```text
>
```

---

# 59. Literal Block `|`

Example:

```yaml
message: |
  Welcome to the server.
  This system is monitored.
  Unauthorized access is prohibited.
```

The literal block style preserves line breaks.

Conceptually the value remains:

```text
Welcome to the server.
This system is monitored.
Unauthorized access is prohibited.
```

with line boundaries preserved.

---

# 60. When Literal Blocks Are Useful

Literal blocks are useful for content where line structure matters.

Examples can include:

```text
Configuration snippets

Shell scripts

Messages

Certificates or structured text where appropriate

File content
```

In Ansible, you will eventually see multiline content in module arguments and templates.

---

# 61. Folded Block `>`

Example:

```yaml
description: >
  This application runs on the internal network
  and serves requests from the application
  load balancer.
```

The folded style generally turns ordinary line breaks into spaces.

Conceptually:

```text
This application runs on the internal network and serves requests from the application load balancer.
```

---

# 62. Literal vs Folded

Think:

```text
|
↓
preserve line structure
```

```text
>
↓
fold ordinary lines into a paragraph
```

That is enough for the beginner mental model.

YAML has additional block-scalar details involving trailing newlines and chomping indicators, but we do not need to overload Part 3 with every YAML grammar feature.

# 64. Inline Dictionaries

YAML also supports flow-style dictionaries.

Example:

```yaml
server: {hostname: web01, port: 80}
```

This represents approximately the same data structure as:

```yaml
server:
  hostname: web01
  port: 80
```

For substantial Ansible configuration, block-style YAML is usually easier to review.

Prefer readability.

---

# 65. YAML vs JSON

JSON and YAML can represent similar structured data.

JSON example:

```json
{
  "server": {
    "hostname": "web01",
    "port": 443,
    "enabled": true
  }
}
```

Equivalent conceptual YAML:

```yaml
server:
  hostname: web01
  port: 443
  enabled: true
```

Both describe:

```text
server
↓
dictionary
├── hostname → string
├── port → number
└── enabled → Boolean
```

---

# 66. JSON Is More Punctuation Heavy

JSON uses characters such as:

```text
{
}

[
]

,

"
```

extensively.

YAML block style relies more heavily on:

```text
indentation

colon

hyphen
```

That often makes configuration easier for humans to scan.

But YAML's whitespace sensitivity creates its own class of mistakes.

---

# 67. YAML Is Not Simply "JSON Without Braces"

That shortcut is too shallow.

YAML includes features such as:

```text
Block scalars

Comments

Document markers

Multiple scalar styles

Anchors and aliases

Tags

Additional syntax
```

You do not need all of those features for ordinary Ansible engineering.

The important point is that YAML is its own language.

# 69. YAML Parsing

Before Ansible can use YAML, the text must be parsed.

Conceptually:

```text
YAML Text
↓
YAML Parser
↓
Structured Data
↓
Ansible
```

If the YAML parser cannot understand the structure:

```text
Ansible cannot meaningfully use the intended data.
```

This is why some Ansible failures happen before any SSH connection occurs.

---

# 70. Parse Failure vs Remote Failure

Suppose your playbook has malformed YAML.

The failure path may be:

```text
Control Node
↓
Read YAML
↓
Parse
X
```

Ansible never reaches:

```text
SSH
↓
Managed Node
```

This is different from:

```text
YAML parsed
↓
Inventory loaded
↓
SSH attempted
↓
Authentication failed
```

Learn to identify the failure layer.

# 72. Ansible Syntax Checking

Once we start writing playbooks, Ansible itself provides syntax-checking capabilities.

For example, later you will use patterns such as:

```bash
ansible-playbook playbook.yml --syntax-check
```

But understand what this means.

Ansible syntax checking is not merely a generic YAML parser.

It also understands expected Ansible structures.

# 73. Three Validation Questions

Whenever reading automation YAML, ask:

```text
1. Is this valid YAML?

2. Does it produce the intended data structure?

3. Is that structure valid for Ansible in this location?
```

Those are three different questions.

---

# 74. Common YAML Mistake: Tabs

Bad:

```text
server:
<TAB>hostname: web01
```

Use spaces.

Your editor should be configured to make tabs visible or convert them to spaces.

---

# 75. Common YAML Mistake: Wrong Indentation

Intended:

```yaml
server:
  hostname: web01
  port: 80
```

Broken:

```yaml
server:
  hostname: web01
    port: 80
```

The parser cannot interpret the intended hierarchy correctly.

---

# 76. Common YAML Mistake: Wrong Nesting

Intended:

```yaml
server:
  network:
    port: 443
```

Accidentally:

```yaml
server:
  network:
  port: 443
```

The second structure does not say:

```text
network contains port
```

Instead `network` has no nested `port` underneath it, and `port` is at the same level as `network`.

This may parse.

It is still logically wrong.

---

# 77. Common YAML Mistake: Missing Space

Avoid:

```yaml
hostname:web01
```

Use:

```yaml
hostname: web01
```

Spacing around structural syntax matters.

---

# 78. Common YAML Mistake: List Structure

Correct:

```yaml
packages:
  - nginx
  - git
  - curl
```

Broken or unintended:

```yaml
packages:
  nginx
  git
  curl
```

Those lines do not create the intended YAML list.

List items need list syntax.

---

# 79. Common YAML Mistake: Misaligned List Items

Correct:

```yaml
packages:
  - nginx
  - git
  - curl
```

Wrong:

```yaml
packages:
  - nginx
    - git
  - curl
```

The indentation incorrectly changes the hierarchy.

---

# 80. Common YAML Mistake: Data Type

Suppose an application expects a numeric port.

You write:

```yaml
port: "8080"
```

The YAML may be perfectly valid.

But you supplied a string.

This is not a parsing failure.

It is a data-type problem.

---

# 81. Common YAML Mistake: Boolean as String

Compare:

```yaml
enabled: false
```

with:

```yaml
enabled: "false"
```

The second is text.

Depending on how a consumer evaluates values, supplying the wrong type can produce surprising behavior.

Do not rely on software to correct your data model.

---

# 82. Common YAML Mistake: Accidental Comment

Suppose you intend the literal value:

```text
abc # production
```

but write:

```yaml
value: abc # production
```

The parser treats:

```text
# production
```

as a comment.

The value is effectively:

```text
abc
```

If the hash belongs to the string, quote it:

```yaml
value: "abc # production"
```

---

# 83. Common YAML Mistake: Unquoted Special Content

A value containing syntax-significant characters can become ambiguous.

Instead of relying on parser interpretation, make your intent explicit.

For example:

```yaml
message: "Status: healthy"
```

Readable automation is better than clever YAML.

---

# 84. Duplicate Keys

Consider:

```yaml
server:
  port: 80
  port: 443
```

What is the intended value of `port`?

That configuration is ambiguous from a human review perspective.

Different tooling may reject duplicate keys, warn about them, or effectively allow a later value to overwrite an earlier one.

Do not depend on duplicate-key behavior.

Treat duplicate mapping keys as an error in automation code.

Correct it:

```yaml
server:
  http_port: 80
  https_port: 443
```

or model the data appropriately.

---

# 85. Why Duplicate Keys Are Dangerous

Imagine:

```yaml
firewall:
  enabled: true
  ...
  enabled: false
```

in a long file.

A reviewer may read the first value and miss the second.

Automation should be designed for unambiguous review.

Production rule:

> One mapping key should represent one clear value within that mapping.

---

# 86. Common YAML Mistake: Copy-Paste Indentation

Copying YAML from:

```text
Web pages

PDF files

Chat messages

Documentation

Tickets
```

can introduce:

```text
tabs

nonstandard spaces

incorrect indentation

smart quotes

missing characters
```

Never assume copied YAML is valid.

Inspect it in a proper editor.

---

# 87. Common YAML Mistake: Smart Quotes

These:

```text
“production”
```

are not the same characters as:

```text
"production"
```

Word processors and rich-text applications can replace ordinary quotes with typographic quotes.

Configuration files should be edited as plain text.

---

# 88. Common YAML Mistake: Invisible Characters

Sometimes a file looks correct but contains:

```text
tabs

carriage returns

nonbreaking spaces

unexpected Unicode characters
```

A code editor that can reveal whitespace and file encoding can help.

When debugging strange parsing behavior, do not assume every invisible character is harmless.

# 97. Ansible Task Shape

A simple Ansible task can look like:


# 98. What Is the Top-Level Structure?

The line begins:

```yaml

```

```text

```

That list item contains a dictionary.

Conceptually:

```text
LIST ITEM
↓
DICTIONARY
├── name
└── ansible.builtin.package
```

The module key itself contains another dictionary:

```text
ansible.builtin.package
↓
DICTIONARY
├── name → nginx
└── state → present
```

```yaml

    name: nginx
```

```text

Key:
ansible.builtin.package

Value:
dictionary
↓
name → nginx
state → present
```

That is YAML literacy.

# 100. Task Meaning

Now add the Ansible interpretation.

```text

↓
Ensure Nginx is installed

↓
ansible.builtin.package

Module arguments
↓

state = present
```


Both matter.

# 101. Multiple Tasks

Consider:

```yaml

  ansible.builtin.package:
    name: nginx

  ansible.builtin.service:
    name: nginx
```

Structurally:

```text

├── TASK DICTIONARY

│   └── package module

    ├── name

```

Tasks are naturally represented as a list.

# 102. Why Task Order Is Easy to Read

A list is ordered.

Therefore:

```yaml

- task B
- task C
```

communicates an ordered sequence.

That fits the idea of tasks within an Ansible play.

We will study task execution deeply later.

For now, understand the data structure.

# 103. From Task to Play

A play groups automation against hosts.

A simplified shape:

```yaml

  hosts: web

  tasks:

      ansible.builtin.package:
        name: nginx
        state: present
```

Again, do not memorize Ansible yet.

Parse the YAML.

---

# 104. Structural Breakdown of the Play

At the top:

```text

```

means:

```text

```

That list item is a dictionary containing:

```text

hosts

become

tasks
```

Now inspect:

```text

```

Its value is:

```text

```

The list contains:

```text

```

```text

↓

↓

↓

├── name → string
├── hosts → string
├── become → Boolean
└── tasks
    ↓

    └── TASK
        ↓
        DICTIONARY
        ├── name
        └── module
            ↓
            DICTIONARY
            ├── name
            └── state
```

This is the progression we wanted.

# 138. YAML Does Not Know What `hosts` Means

This is a subtle but powerful distinction.

Given:

```yaml
hosts: web
```

YAML sees:

```text
key = hosts
value = web
```

YAML itself does not know:

```text
web is an Ansible inventory host pattern.
```

Ansible provides that meaning.

Likewise:

```yaml
become: true
```

YAML understands:

```text
key + Boolean
```

Ansible understands:

```text
enable privilege escalation
```

Separate syntax from semantics.

# 151. Security Consideration: YAML Can Contain Secrets

YAML is merely a data format.

Nothing about:

```text
.yml
```

makes a file secure.

This is dangerous:

```yaml

```

if committed to Git.

Likewise:

```yaml
aws_secret_access_key: ...
```

is not protected simply because it lives inside an Ansible variable file.

Later we will use secure secret-management mechanisms.

For now:

> Never assume configuration data is safe merely because it is YAML.

# 161. Knowledge Check

## Question 1

What is YAML?

### Answer

A human-readable data-serialization language used to represent structured data.

---

## Question 2

Does YAML itself install software?

### Answer

No. YAML represents data. Ansible interprets Ansible-specific YAML structures and performs automation.

---

## Question 3

What is a scalar?

### Answer

A single value such as a string, number, Boolean, or null value.

---

## Question 4

What is a key-value pair?

### Answer

A mapping between a named key and its associated value.

Example:

```yaml
port: 443
```

---

## Question 5

What indicates a block-style list item?

### Answer

A hyphen at the appropriate indentation level.

---

## Question 6

What is a dictionary?

### Answer

A mapping containing keys associated with values.

---

## Question 7

Can a dictionary contain a list?

### Answer

Yes.

---

## Question 8

Can a list contain dictionaries?

### Answer

Yes.

---

## Question 9

Why is indentation important?

### Answer

Because indentation expresses hierarchy and nesting in block-style YAML.

---

## Question 10

Should tabs be used for YAML indentation?

### Answer

No. Use spaces.

---

## Question 11

Must every YAML file begin with `---`?

### Answer

No. It is a document-start marker and is common, but its absence does not automatically make a YAML document invalid.

---

## Question 12

What is the difference between:

```yaml
port: 443
```

and:

```yaml
port: "443"
```

### Answer

The first is intended as a number; the second is a string.

---

## Question 13

What is the difference between:

```yaml
enabled: false
```

and:

```yaml
enabled: "false"
```

### Answer

The first is a Boolean; the second is a string.

---

## Question 14

What does `null` represent?

### Answer

The absence of a meaningful value.

---

## Question 15

Is null the same as an empty string?

### Answer

No.

---

## Question 16

What does `|` do for a block scalar?

### Answer

It represents literal-style multiline text and preserves line structure.

---

## Question 17

What does `>` do?

### Answer

It represents folded multiline text, generally folding ordinary line breaks into spaces.

---

## Question 18

What does `#` commonly indicate?

### Answer

A comment when used in comment context.

---

## Question 19

Why might a string containing `#` need quotes?

### Answer

To make clear that the hash and following text belong to the string rather than beginning a comment.

---

## Question 20

What is dangerous about duplicate keys?

### Answer

They create ambiguous configuration and may be rejected, warned about, or handled in ways that hide one value behind another depending on tooling.

---

## Question 21

Can valid YAML still be wrong?

### Answer

Yes. It can parse successfully while representing the wrong hierarchy, value, or data type.

---

## Question 22

What are the three questions to ask about Ansible YAML?

### Answer

1. Is it valid YAML?
2. Does it represent the intended data structure?
3. Is that structure valid and correct for Ansible?

---

## Question 23

What is the top-level structure of a normal Ansible playbook?

### Answer

A list of plays.

---

## Question 24

What is a play structurally?

### Answer

A dictionary inside the playbook's list.

---

## Question 25

What is `tasks` commonly?

### Answer

A list of task dictionaries.

---

## Question 26

What is a module's argument block structurally?

### Answer

Typically a dictionary mapping argument names to values.

---

## Question 27

Does YAML understand that `hosts` refers to Ansible inventory?

### Answer

No. YAML only parses the key and value. Ansible gives `hosts` its Ansible-specific meaning.

---

## Question 28

What should you do before randomly changing indentation after a parsing error?

### Answer

Determine the intended hierarchy, inspect the surrounding structure, and then correct the indentation to represent that hierarchy.

---

## Question 29

Why can a quoted Boolean be dangerous?

### Answer

Because `"false"` is a string rather than the Boolean `false`, which may not match what the consuming system expects.

---

## Question 30

Why is YAML knowledge important for Ansible troubleshooting?

### Answer

Because many apparent Ansible problems are actually YAML parsing, nesting, or data-type problems that occur before or independently of remote automation.

```text
    ├── Scalar
```

Once you can see that structure without effort, Ansible YAML stops looking like mysterious configuration syntax.
