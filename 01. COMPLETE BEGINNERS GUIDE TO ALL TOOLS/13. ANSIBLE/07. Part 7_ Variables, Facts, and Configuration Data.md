# Part 7: Variables, Facts, and Configuration Data

## Make Playbooks Reusable Instead of Hardcoded

In Part 6, you built a real Ansible playbook.

You moved from individual ad hoc commands to repeatable automation:

```text
Web Servers
↓
Install Web Server
↓
Create Configuration
↓
Start Service
↓
Enable Service
↓
Deploy Web Page
↓
Verify HTTP Response
```

But the playbook still contained hardcoded information.

For example:

```yaml
- name: Install nginx
  ansible.builtin.package:
    name: nginx
    state: present
```

and:

```yaml
- name: Create document root
  ansible.builtin.file:
    path: /var/www/html
    state: directory
```

and:

```yaml
- name: Verify HTTP
  ansible.builtin.uri:
    url: http://127.0.0.1/
    status_code: 200
```

This works.

But imagine that you now have:

```text
Development
Staging
Production
```

and each environment is different.

Development might use:

```text
application_port = 8080
```

Staging:

```text
application_port = 8081
```

Production:

```text
application_port = 80
```

Or perhaps:

```text
Development
↓
2 application workers

Production
↓
8 application workers
```

You do not want three almost-identical playbooks.

You want:

```text
ONE PLAYBOOK
+
DIFFERENT DATA
=
DIFFERENT CONFIGURATION
```

This is where variables become essential.

Then Ansible goes further.

Some information does not need to be manually defined at all.

Ansible can discover:

```text
Operating system

Distribution

Hostname

IP addresses

Memory

CPU information

Network interfaces
```

These discovered values are called **facts**.

Tasks can also produce information while a playbook is running.

For example:

```text
Run HTTP Request
↓
Receive Status Code
↓
Store Result
↓
Use Result Later
```

This is done with **registered variables**.

Ansible also provides special information about its own execution and inventory through **magic variables**.

By the end of Part 7, your mental model should become:

```text
Inventory Data
+
Variables
+
Facts
+
Registered Results
↓
Playbook Logic
↓
Configuration
```

This is the point where playbooks stop being collections of hardcoded values and start becoming reusable automation systems.

---

# 1. Why Variables Exist

Consider this playbook:

```yaml
---
- name: Configure web server
  hosts: web
  become: true

  tasks:
    - name: Install nginx
      ansible.builtin.package:
        name: nginx
        state: present

    - name: Create application directory
      ansible.builtin.file:
        path: /opt/veriqta
        state: directory
        mode: "0755"
```

Several values are embedded directly into the tasks:

```text
nginx

/opt/veriqta

0755
```

These are hardcoded values.

Hardcoding is not always wrong.

A value that genuinely should never vary may be perfectly reasonable to write directly.

The problem begins when the same automation must work with different values.

For example:

```text
Development
application_directory = /opt/veriqta-dev

Staging
application_directory = /opt/veriqta-staging

Production
application_directory = /opt/veriqta
```

Copying the entire playbook three times would create unnecessary duplication.

Instead, create a variable:

```yaml
app_directory: /opt/veriqta
```

Then reference it:

```yaml
path: "{{ app_directory }}"
```

Now the automation and the data are separated.

# 2. The Variable Mental Model

Think:

```text
Hardcoded Playbook

Install nginx
Create /opt/veriqta
Listen on 8080
Deploy version 1.0
```

becomes:

```text
PLAYBOOK
+
VARIABLE DATA
```

For example:

```text
Playbook
│
├── package_name
├── app_directory
├── app_port
└── app_version
```

Then:

```text
Development Values
↓
Same Playbook
↓
Development Configuration
```

or:

```text
Production Values
↓
Same Playbook
↓
Production Configuration
```

# 3. Variables Separate Logic From Data

Think of your automation as two broad categories.

## Logic

```text
Install package

Create directory

Deploy file

Start service

Verify endpoint
```

## Data

```text
Package name

Directory path

Port

Username

Environment

Application version
```

Variables help separate them.

```text
AUTOMATION LOGIC
+
CONFIGURATION DATA
↓
RESULTING CONFIGURATION
```

This becomes increasingly important as infrastructure grows.

# 4. Your First Variable

Example:

```yaml
vars:
  web_package: nginx
```

Then:

```yaml
- name: Install web server
  ansible.builtin.package:
    name: "{{ web_package }}"
    state: present
```

Ansible evaluates:

```text
{{ web_package }}
↓
nginx
```

The module effectively receives:

```yaml
name: nginx
```

---

# 5. Jinja Expressions

You will commonly reference variables using:

```text
{{ variable_name }}
```

For example:

```yaml
dest: "{{ app_directory }}"
```

or:

```yaml
msg: "Application port is {{ app_port }}"
```

The double curly braces indicate a Jinja expression.

Jinja is the templating system Ansible uses for expressions and templating.

You will study Jinja2 much more deeply in Part 9.

For now, learn to recognize:

```text
{{ ... }}
```

as:

> Evaluate this expression and use its resulting value here.

---

# 6. Variable Naming Rules

Ansible variable names should contain:

```text
Letters

Numbers

Underscores
```

A variable cannot begin with a number.

Good examples:

```yaml
app_port: 8080
web_package: nginx
deployment_environment: production
app_version_2: "2.0"
```

Invalid examples include:

```text
app-port

app port

5app
```

Avoid Python keywords and Ansible/playbook keywords as variable names.

---

# 7. Good Variable Naming

A variable name should explain what the value represents.

Poor:

```yaml
p: 8080
```

Better:

```yaml
port: 8080
```

Better in a larger project:

```yaml
app_port: 8080
```

Similarly:

```yaml
d: /opt/veriqta
```

is poor.

Prefer:

```yaml
app_directory: /opt/veriqta
```

---

# 8. Namespace Variables Where Useful

As projects grow, generic variable names become dangerous.

Imagine:

```yaml
port: 8080
```

Which port?

```text
Application?

nginx?

Database?

Metrics?

SSH?
```

Prefer descriptive names:

```yaml
veriqta_app_port: 8080
veriqta_metrics_port: 9090
database_port: 5432
```

Clear naming reduces collisions and confusion.

---

# 9. Do Not Use Variable Names as Security

A variable beginning with an underscore is not automatically private.

For example:

```yaml
_database_password: secret
```

does not make the value secure.

Naming conventions are not security controls.

Secrets require proper secret-management techniques, which you will study in Part 13.

---

# 10. Scalar Variables

A scalar is a single value.

Examples:

```yaml
app_name: veriqta
app_port: 8080
worker_count: 4
debug_enabled: false
environment: production
```

These values have different data types.

---

# 11. String Variables

Example:

```yaml
app_name: veriqta
```

or:

```yaml
app_name: "veriqta"
```

Use:

```yaml
- name: Display application name
  ansible.builtin.debug:
    msg: "Application: {{ app_name }}"
```

Expected output conceptually:

```text
Application: veriqta
```

---

# 12. Numeric Variables

Example:

```yaml
app_port: 8080
worker_count: 4
```

These are numeric values.

Do not automatically quote every value.

This:

```yaml
worker_count: 4
```

is an integer.

This:

```yaml
worker_count: "4"
```

is normally a string.

Data types matter.

---

# 13. Boolean Variables

Example:

```yaml
debug_enabled: false
```

or:

```yaml
monitoring_enabled: true
```

These can later drive conditions.

Conceptually:

```text
monitoring_enabled
↓
true
↓
Run monitoring configuration
```

You will use this extensively in Part 8.

---

# 14. Null Values

A variable can intentionally have no value.

For example:

```yaml
optional_value: null
```

Null is different from:

```yaml
optional_value: ""
```

The second is an empty string.

Understanding the distinction becomes important when modules, APIs, templates, and conditions expect specific data types.

---

# 15. Lists

Suppose your application needs several packages.

Instead of:

```yaml
package_one: git
package_two: curl
package_three: unzip
```

use a list:

```yaml
required_packages:
  - git
  - curl
  - unzip
```

Mental model:

```text
required_packages
│
├── git
├── curl
└── unzip
```

---

# 16. Accessing List Items

List positions begin at zero.

Given:

```yaml
required_packages:
  - git
  - curl
  - unzip
```

then:

```text
required_packages[0]
↓
git
```

```text
required_packages[1]
↓
curl
```

```text
required_packages[2]
↓
unzip
```

Example:

```yaml
- name: Display first required package
  ansible.builtin.debug:
    msg: "{{ required_packages[0] }}"
```

---

# 17. Dictionaries

A dictionary stores related key-value pairs.

Example:

```yaml
application:
  name: veriqta
  port: 8080
  environment: production
```

Mental model:

```text
application
│
├── name
│   └── veriqta
├── port
│   └── 8080
└── environment
    └── production
```

---

# 18. Accessing Dictionary Values

You can commonly access dictionary values with dot notation:

```text
application.name
```

or bracket notation:

```text
application['name']
```

Example:

```yaml
- name: Display application port
  ansible.builtin.debug:
    msg: "Port: {{ application.port }}"
```

Bracket notation:

```yaml
- name: Display application port
  ansible.builtin.debug:
    msg: "Port: {{ application['port'] }}"
```

---

# 19. Dot Notation vs Bracket Notation

Both are commonly encountered.

Dot notation:

```text
application.port
```

is concise.

Bracket notation:

```text
application['port']
```

can be safer when keys conflict with dictionary attributes or contain characters unsuitable for dot notation.

As a beginner, learn to read both.

---

# 20. Nested Variables

Real configuration data often contains nested structures.

Example:

```yaml
application:
  name: veriqta
  runtime:
    port: 8080
    workers: 4
  logging:
    level: info
    directory: /var/log/veriqta
```

Mental model:

```text
application
│
├── name
│
├── runtime
│   ├── port
│   └── workers
│
└── logging
    ├── level
    └── directory
```

---

# 21. Accessing Nested Data

For:

```yaml
application:
  runtime:
    port: 8080
```

you can use:

```text
application.runtime.port
```

Example:

```yaml
- name: Display application port
  ansible.builtin.debug:
    msg: "{{ application.runtime.port }}"
```

Or:

```yaml
msg: "{{ application['runtime']['port'] }}"
```

---

# 22. Lists Inside Dictionaries

Example:

```yaml
application:
  name: veriqta
  packages:
    - git
    - curl
    - unzip
```

Structure:

```text
application
│
├── name
│   └── veriqta
│
└── packages
    ├── git
    ├── curl
    └── unzip
```

Access:

```text
application.packages[0]
```

returns:

```text
git
```

# 23. Dictionaries Inside Lists

Example:

```yaml
application_users:
```

Structure:

```text
application_users
│
```

# 25. Where Variables Can Come From

This is where Ansible becomes more complex.

Variables can come from many locations.

Examples include:

```text
Play variables

Task variables

Inventory variables

Host variables

Group variables

host_vars files

group_vars files

Variable files

Role defaults

Role variables

Registered variables

Facts

Extra variables
```

This flexibility is powerful.

It can also become confusing.

The goal is not to put variables everywhere.

The goal is to understand the available scopes and then design a predictable variable strategy.

---

# 26. Play Variables

Variables can be defined directly inside a play.

Example:

```yaml
---
- name: Configure application
  hosts: web

  vars:
    app_name: veriqta
    app_port: 8080

  tasks:
    - name: Display application configuration
      ansible.builtin.debug:
        msg: "{{ app_name }} listens on {{ app_port }}"
```

These variables are available to tasks in that play.

---

# 27. When Play Variables Are Useful

Play variables can be appropriate when values belong specifically to that play.

For example:

```yaml
vars:
  maintenance_message: "Scheduled maintenance"
```

But if values describe infrastructure or environments, inventory-based variables may be a better design.

Ask:

> What does this value belong to?

Not merely:

> Where can Ansible technically accept it?

---

# 28. Task Variables

A variable can be scoped to a specific task.

Example:

```yaml
- name: Display task-specific message
  ansible.builtin.debug:
    msg: "{{ task_message }}"
  vars:
    task_message: "This value belongs to this task"
```

The variable is associated with that task.

This can be useful for highly local values.

---

# 29. Avoid Unnecessary Task Variables

Do not hide important infrastructure configuration inside random tasks.

Poor design:

```text
Task 1
↓
production_port defined here

Task 17
↓
another production value

Task 29
↓
database hostname
```

Important configuration should be organized predictably.

---

# 30. Inventory Variables

You learned inventory in Part 4.

Inventory can also contain variables.

Example INI concept:

```ini
[web]
web01 ansible_host=192.0.2.10 app_port=8080
web02 ansible_host=192.0.2.11 app_port=8081
```

Here each host has a different application port.

---

# 31. Host Variables

Host variables belong to one host.

Example:

```text
web01
↓
app_port = 8080

web02
↓
app_port = 8081
```

Use host-specific variables when the value genuinely differs for that host.

Do not create host-level differences unnecessarily.

Too many unique host values make infrastructure harder to reason about.

---

# 32. Group Variables

Group variables apply to inventory groups.

Suppose:

```text
web01
web02
web03
```

all belong to:

```text
web
```

and all should use:

```text
nginx
```

Instead of defining:

```text
web01 → nginx
web02 → nginx
web03 → nginx
```

define it once for the group.

Conceptually:

```text
web
│
├── web_package: nginx
│
├── web_service: nginx
│
└── web_port: 80
```

All hosts in the group can receive those values.

---

# 33. Why Group Variables Scale Better

Think:

```text
100 Web Servers
```

You could define:

```text
100 identical host variables
```

or:

```text
1 group variable
```

Group variables reduce duplication.

---

# 34. `group_vars`

A common project structure is:

```text
ansible-project/
├── ansible.cfg
├── inventory/
│   └── hosts.yml
├── group_vars/
│   ├── all.yml
│   └── web.yml
└── playbooks/
    └── site.yml
```

Example:

```text
group_vars/web.yml
```

```yaml
---
web_package: nginx
web_service: nginx
web_document_root: /var/www/html
```

Now hosts in the appropriate `web` group can use those variables.

---

# 35. `group_vars/all.yml`

Values that genuinely apply broadly can be stored in:

```text
group_vars/all.yml
```

For example:

```yaml
---
organization_name: VERIQTA
default_timezone: UTC
```

Do not turn `all.yml` into a dumping ground.

Ask whether the value really applies to every host.

---

# 36. `host_vars`

Host-specific variable files can be organized using:

```text
host_vars/
```

Example:

```text
host_vars/
├── web01.yml
└── web02.yml
```

`host_vars/web01.yml`:

```yaml
---
app_port: 8080
```

`host_vars/web02.yml`:

```yaml
---
app_port: 8081
```

---

# 37. Host vs Group Variable Design

Prefer:

```text
Shared value
↓
Group variable
```

Use:

```text
Unique host value
↓
Host variable
```

Example:

```text
All production web servers use port 443
↓
group_vars
```

but:

```text
web03 has a unique management address
↓
host_vars
```

This keeps exceptions visible.

---

# 38. Environment-Specific Values

Suppose you have:

```text
development

staging

production
```

Each environment may differ.

For example:

```text
Development
workers = 2
logging = debug

Staging
workers = 4
logging = info

Production
workers = 8
logging = warning
```

You should not duplicate the entire automation.

Separate:

```text
Automation Logic
```

from:

```text
Environment Data
```

# 39. Environment Variable Architecture

Conceptually:

```text

├── development data

```

Then:

```text

+

↓
```

# 42. Variable Files

Example:



# 43. `vars_files`

A play can load an external variable file.

Example:

```yaml
---
- name: Configure application
  hosts: web

  vars_files:
    - ../vars/application.yml

  tasks:
    - name: Display application port
      ansible.builtin.debug:
        msg: "{{ app_port }}"
```

Mental model:

```text
application.yml
↓
vars_files
↓
Play
↓
Tasks
```

---

# 44. Why Variable Files Help

Without external files:

```text
Playbook
│
├── automation
├── application settings
├── environment settings
└── other data
```

With variable files:

```text
Playbook
↓
Automation Logic

Variable Files
↓
Configuration Data
```

This can improve readability and reuse.

---

# 45. Do Not Confuse Separation With Secret Management

Moving:

```yaml
database_password: supersecret
```

from:

```text
playbook.yml
```

to:

```text
vars.yml
```

does not automatically secure it.

If both files are committed to Git in plaintext, the secret remains exposed.

Variable organization and secret protection are different problems.

Part 13 will handle secrets properly.

# 46. Role Variables Introduction

Later, you will build roles.

Roles can define variables in locations such as:

```text
roles/webserver/defaults/main.yml
```

and:

```text
roles/webserver/vars/main.yml
```

These have different precedence behavior.

For now, remember:

```text
Role Defaults
↓
Designed to be easy to override
```

while:

```text
Role Vars
↓
Higher precedence and harder to override
```

You will study this properly in Part 11.

# 47. Defaults

Defaults are values used when no more specific value has been provided.

Conceptually:

```text
Default web port
↓
80
```

but production could override it:

```text
Production web port
↓
443
```

A good reusable automation component often provides sensible defaults while allowing callers or environments to override them deliberately.

---

# 48. Why Defaults Matter

Imagine a reusable web-server role.

It could define:

```yaml
web_port: 80
```

as a default.

Most environments use it unchanged.

Production may provide:

```yaml
web_port: 443
```

The reusable logic does not need modification.

---

# 49. Variable Precedence

Now we reach one of the most important and commonly misunderstood Ansible topics.

Suppose the same variable appears in several places:

```text
Role Default
↓
web_port = 80

Inventory
↓
web_port = 8080

Play
↓
web_port = 8081

Task
↓
web_port = 8082

Extra Variable
↓
web_port = 9000
```

Which value wins?

Ansible uses variable precedence rules.

---

# 50. Why Precedence Exists

Ansible needs deterministic behavior when multiple definitions of the same variable are available.

Conceptually:

```text
Multiple Candidate Values
↓
Precedence Rules
↓
Effective Value
```

Without precedence rules, the result would be ambiguous.

---

# 51. Beginner Precedence Mental Model

Do not attempt to memorize the complete precedence table immediately.

Start with this simplified mental model:

```text
Easy-to-override defaults
↓
Inventory/group/host data
↓
Play-related values
↓
Task/runtime values
↓
Explicit extra variables
```

This is intentionally simplified.

Ansible's complete precedence system contains more levels.

---

# 52. Important Precedence Warning

Do not build your project around memorizing dozens of override levels.

Better design:

```text
Variable
↓
One obvious source
```

Poor design:

```text
app_port
↓
Defined in 7 locations
↓
Engineer guesses which wins
```

The official Ansible guidance encourages teams to define variables predictably instead of relying unnecessarily on precedence battles.

---

# 53. Extra Variables

You can provide variables at runtime using:

```text
--extra-vars
```

or:

```text
-e
```

Example:

```bash
ansible-playbook \
  -i inventory/hosts.yml \
  playbooks/deploy.yml \
  -e "app_version=2.5.0"
```

Now:

```text
app_version
↓
2.5.0
```

for that execution.

---

# 54. Extra Variables Have Very High Precedence

Extra variables are especially powerful because they override other variable sources under Ansible's variable precedence rules.

That makes them useful.

It also makes careless use dangerous.

Example:

```bash
-e "environment=production"
```

may override what the project normally derives from inventory or other variable sources.

Know what you are overriding.

---

# 55. Extra Variable Data Types

This matters.

Using:

```bash
-e "workers=4"
```

with key-value syntax treats the supplied value as a string.

If you need structured types such as:

```text
Boolean

Integer

List

Dictionary
```

JSON syntax can preserve those types.

Example:

```bash
ansible-playbook \
  playbooks/site.yml \
  -e '{"workers":4,"monitoring_enabled":true}'
```

Do not ignore data types.

---

# 56. Extra Variables From a File

You can also load runtime extra variables from a YAML or JSON file.

Example:

```bash
ansible-playbook \
  playbooks/site.yml \
  --extra-vars "@release.yml"
```

This can be useful for structured runtime configuration.

But again:

```text
Variable File
≠
Secret Store
```

---

# 57. Safe Precedence Design

A good beginner strategy is:

```text
Role Defaults
↓
Reusable component defaults

Group Variables
↓
Shared environment/service values

Host Variables
↓
Real host-specific exceptions

Play Variables
↓
Values genuinely specific to the play

Extra Variables
↓
Deliberate runtime overrides
```

The exact architecture will vary by project.

The important principle is:

> Make it obvious where a value is supposed to come from.

---

# 58. Avoid Variable Shadowing

Variable shadowing occurs when the same name is defined in multiple places and one value replaces another.

Example:

```text
group_vars/production.yml
app_port = 443
```

then:

```text
playbook
app_port = 8080
```

then:

```text
CLI
-e app_port=9000
```

Now troubleshooting becomes:

> Why is the application listening on 9000?

The answer may require tracing variable precedence.

Avoid unnecessary duplication.

---

# 59. Variables Are Data, Facts Are Discovered Data

This distinction is essential.

A variable might be something you define:

```yaml
app_port: 8080
```

A fact might be something Ansible discovers:

```text
Operating system

Hostname

Memory

CPU

Network information
```

Mental model:

```text
Variables
↓
Information we provide
```

```text
Facts
↓
Information Ansible discovers
```

Facts are still variables from the perspective of playbook expressions, but their source is discovery from managed systems.

---

# 60. What Are Ansible Facts?

Facts are information gathered about managed systems.

Examples can include:

```text
Hostname

Operating system family

Distribution

Distribution version

Architecture

Processor information

Memory

Network interfaces

IP addresses

Filesystem information

Python information
```

Exact available facts depend on the managed platform, installed utilities, Ansible version, fact-gathering subsets, and environment.

Do not assume every host exposes identical facts.

---

# 61. Fact Gathering

By default, Ansible normally gathers facts at the beginning of a play.

Example:

```yaml
---
- name: Inspect servers
  hosts: all
  gather_facts: true
```

You may see:

```text
TASK [Gathering Facts]
```

before your normal tasks.

---

# 62. Fact Gathering Mental Model

```text
Play Starts
↓
Connect to Managed Host
↓
Gather Facts
↓
Build ansible_facts Data
↓
Run Tasks
```

The playbook can then use discovered information.

---

# 63. Disabling Fact Gathering

If facts are unnecessary:

```yaml
gather_facts: false
```

Example:

```yaml
---
- name: Simple connectivity workflow
  hosts: all
  gather_facts: false
```

This can reduce unnecessary work.

But do not disable fact gathering if later tasks depend on facts.

# 64. `ansible_facts`


Example:

```yaml
- name: Display all gathered facts

    var: ansible_facts
```

Be prepared for a large amount of output.

# 65. Inspect Facts Before Guessing Their Structure

One of the worst beginner habits is guessing fact names.

Instead:

```text

↓

↓
Understand Structure
↓

```

```text

```

# 74. The `setup` Module

The module responsible for gathering many standard host facts is:

```text
ansible.builtin.setup
```

You can call it directly.

Example:

```bash
ansible web \
  -i inventory/hosts.yml \
  -m ansible.builtin.setup
```

This can produce a large fact structure.

---

# 75. Why `setup` Is Useful

Use it when you need to answer questions such as:

```text
What facts exist?

What does this operating system report?

What is the exact key?

What value does Ansible see?

Why is my condition not behaving as expected?
```

It is both a discovery and troubleshooting tool.

---

# 76. Filtering Facts

Instead of printing everything, filter the output.

Example:

```bash
ansible web \
  -i inventory/hosts.yml \
  -m ansible.builtin.setup \
  -a 'filter=ansible_distribution*'
```

This can reduce output to distribution-related facts matching the filter.

Another useful example:

```bash
ansible web \
  -i inventory/hosts.yml \
  -m ansible.builtin.setup \
  -a 'filter=ansible_memory_mb'
```

The exact fact set can vary by environment.

Use filtering to inspect the facts actually available on your hosts.

# 77. Fact Names in `setup` Output vs `ansible_facts`

A detail that confuses beginners:

The `setup` module output may display fact keys using the familiar:

```text
ansible_
```

prefix.

But when accessing values inside:

```text
ansible_facts
```

the prefix is generally omitted.

For example, setup output may conceptually show:

```text
ansible_distribution
```

while the dictionary access is:

```text
ansible_facts['distribution']
```

Learn the structure rather than blindly copying names.

# 80. Fact Caching

By default, facts are normally held in memory for the current Ansible execution.

Ansible can also use fact-cache plugins to retain facts beyond the immediate gathering operation.

Conceptually:

```text
Managed Hosts
↓
Gather Facts
↓
Fact Cache
↓
Later Automation
```

Fact caching becomes useful at larger scale or when information from hosts needs to remain available without gathering it repeatedly.

Do not enable caching blindly.

Cached information can become stale.

# 81. Facts Can Become Stale

Facts describe a host at the time they were gathered.

Imagine:

```text
09:00
↓
Gather memory/network facts

11:00
↓
Infrastructure changes
```

Previously gathered information may no longer describe current reality.

Treat facts as discovered data with a collection time, not eternal truth.


# 86. Registered Variables

Now we move from:

```text
Data defined before execution
```

and:

```text
Data discovered from host
```

to:

```text
Data produced during execution
```

A task returns information.

You can capture that result using:

```text
register
```

---

# 87. First Registered Variable

Example:

```yaml
- name: Check application uptime
  ansible.builtin.command:
    cmd: uptime
  register: uptime_result
```

Now:

```text
uptime_result
```

contains the task result.

You can inspect it:

```yaml
- name: Display uptime result
  ansible.builtin.debug:
    var: uptime_result
```

---

# 88. Registered Result Mental Model

```text
Task Executes
↓
Module Returns Result
↓
register
↓
Variable
↓
Later Tasks Can Read It
```

Example:

```text
command: uptime
↓
Return Data
↓
uptime_result
↓
stdout
rc
changed
failed
...
```

The exact return fields depend on the module.

---

# 89. Registered Variables Are Usually Dictionaries

Suppose:

```yaml
- name: Run uptime
  ansible.builtin.command:
    cmd: uptime
  register: uptime_result
```

The result may contain fields such as:

```text
changed

stdout

stderr

rc

start

end
```

depending on the module.

Never assume every module returns the same structure.

Read the module's documentation.

---

# 90. Inspect Before Referencing

Bad approach:

```text
I think the field is output.text.value
```

Better:

```yaml
- name: Inspect complete result
  ansible.builtin.debug:
    var: uptime_result
```

Then inspect the actual structure.

Only then write:

```yaml
msg: "{{ uptime_result.stdout }}"
```

---

# 91. `stdout`

For command-like modules, standard output may be available through:

```text
stdout
```

Example:

```yaml
- name: Display command output
  ansible.builtin.debug:
    msg: "{{ uptime_result.stdout }}"
```

---

# 92. `stderr`

If a command writes to standard error, the result may expose:

```text
stderr
```

Example:

```yaml
- name: Display standard error
  ansible.builtin.debug:
    msg: "{{ command_result.stderr }}"
```

Do not assume stderr automatically means the task failed.

Programs can write warnings to stderr and still exit successfully.

Inspect the return code and module result.

---

# 93. Return Codes

Command-like tasks commonly expose:

```text
rc
```

where:

```text
0
```

usually indicates command success under normal Unix conventions.

But always understand the command you are executing.

Different programs can define special exit-code semantics.

---

# 94. Registered Results and Module Documentation

Every module can return its own fields.

Therefore:

```text
Task
↓
Module
↓
Module RETURN Documentation
↓
Expected Result Structure
```

This is why learning:

```bash
ansible-doc
```

in Part 2 was important.

Example:

```bash
ansible-doc ansible.builtin.command
```

Inspect the return-value documentation.

---

# 95. Registered Variables Are Runtime Data

A normal registered variable is stored for the current playbook run.

It is not automatically persisted as long-term configuration.

Think:

```text
Current Execution
↓
Task Runs
↓
register
↓
Result Available Later During Run
```

After the run ends, do not assume that registered result exists during tomorrow's run.

# 96. Register Lab

Create:

```text
playbooks/register-lab.yml
```

```yaml
---
- name: Learn registered variables
  hosts: web
  gather_facts: false

  tasks:
    - name: Read system uptime
      ansible.builtin.command:
        cmd: uptime
      register: uptime_result
      changed_when: false

      ansible.builtin.debug:
```

```yaml

```

here?

Because reading uptime does not change system state.

# 100. Accessing Nested Registered Data

Imagine a result:

```yaml

  status: healthy

    code: 200
    server: nginx
```

Then:

```text

```

would conceptually access:

```text
200
```

or:

```text
service_result['response']['code']
```

Nested data is extremely common in Ansible.

Learn to inspect structure before writing expressions.

# 101. Reading Nested Data Step by Step

Given:

```text
application
└── database
    └── connection
        └── port
```

do not stare at:

```text
application.database.connection.port
```

as one giant expression.

Read it:

```text

↓

↓
connection
↓

```

This makes complex Ansible data much easier to understand.

# 102. Undefined Variables

What happens if you write:

```yaml
msg: "{{ application_port }}"
```

but:

```text
application_port
```

was never defined?

Ansible normally reports an undefined-variable error rather than silently inventing a value.

This is useful.

It prevents many hidden configuration mistakes.

---

# 103. Example Undefined Variable Failure

Playbook:

```yaml
---
- name: Undefined variable lab
  hosts: web
  gather_facts: false

  tasks:
    - name: Display missing variable
      ansible.builtin.debug:
        msg: "{{ nonexistent_variable }}"
```

Run it.

Observe the failure.

Read the error carefully.

Then ask:

```text
Was the variable misspelled?

Was the expected variable file loaded?

Is the host in the correct group?

Was fact gathering disabled?

Is the variable defined under another scope?

Did precedence produce something unexpected?
```

---

# 104. The `default` Filter

Sometimes an undefined variable should intentionally fall back to a default.

Example:

```yaml
msg: "{{ app_port | default(8080) }}"
```

Meaning:

```text
Is app_port defined?
├── Yes → use app_port
└── No → use 8080
```

This can make optional configuration safer and more reusable.

---

# 105. Defaults Can Also Hide Mistakes

Suppose production requires:

```text
database_hostname
```

but you write:

```yaml
database_hostname | default('localhost')
```

A missing production configuration could silently fall back to:

```text
localhost
```

and cause serious problems.

Therefore:

```text
Default
≠
Always Safer
```

Use defaults when a fallback is genuinely valid.

Fail when missing configuration should be considered an error.

---

# 106. Safe Default Design

Good candidate:

```yaml
log_level: "{{ configured_log_level | default('info') }}"
```

if `info` is genuinely safe.

Potentially dangerous:

```yaml
production_database: "{{ database_host | default('localhost') }}"
```

if production must always provide a real database endpoint.

Ask:

> Is the fallback actually correct, or am I hiding missing configuration?


# 117. `hostvars` and Facts

```text

↓
```


# 118. Important `hostvars` Limitation

This expression:


If those facts have not been gathered or cached, the information may not be available.

This is a common beginner mistake.

# 122. Refactored Playbook

Create:

```text

```

```yaml
---
- name: Configure reusable web servers
  hosts: web
  become: true
  gather_facts: true

  tasks:
    - name: Install web server package
      ansible.builtin.package:
        name: "{{ web_package }}"
        state: present

    - name: Create web document root
      ansible.builtin.file:
        path: "{{ web_document_root }}"
        state: directory
        mode: "0755"

    - name: Deploy web page
      ansible.builtin.copy:
        content: |
          <!doctype html>
          <html lang="en">
          <head>
            <meta charset="utf-8">
            <title>{{ web_page_title }}</title>
          </head>
          <body>
            <h1>{{ web_page_title }}</h1>
            <p>Host: {{ inventory_hostname }}</p>
            <p>Distribution: {{ ansible_facts['distribution'] }}</p>
          </body>
          </html>
        dest: "{{ web_document_root }}/index.html"
        mode: "0644"

    - name: Ensure web service is started and enabled
      ansible.builtin.service:
        name: "{{ web_service }}"
        state: started
        enabled: true

    - name: Verify web service HTTP response
      ansible.builtin.uri:
```
