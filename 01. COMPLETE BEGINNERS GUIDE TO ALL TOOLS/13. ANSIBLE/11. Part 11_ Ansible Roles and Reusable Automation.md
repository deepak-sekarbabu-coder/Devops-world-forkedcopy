# Part 11: Ansible Roles and Reusable Automation

## Move From Large Playbooks to Maintainable Automation

By Part 10, you can automate a real Linux server.

You can:

```text
Create users
Create groups
Install packages
Deploy files
Render templates
Manage permissions
Configure services
Install SSH keys
Configure sudo
Schedule jobs
Configure system settings
Verify the result
```

That is a major step.

But it creates a new problem.

Your playbook can become enormous.

Imagine this:

```text
site.yml

Task 1
Task 2
Task 3
...
Task 48
...
Task 97
...
Task 163
...
Task 241
```

It may work.

But working automation is not automatically maintainable automation.

As your infrastructure grows, you need a better structure.

That structure is built around:

```text
ROLES
```

Roles let you move from:

```text
One Giant Playbook
```

to:

```text
Small, Purposeful, Reusable Automation Components
```

---

# 1. Part 11 Mental Model

We are moving from this:

```text
site.yml
│
├── Install packages
├── Create users
├── Configure SSH
├── Configure sudo
├── Configure firewall
├── Install Nginx
├── Configure Nginx
├── Deploy application
├── Configure monitoring
├── Start services
├── Verify services
└── 200 more lines
```

to:

```text
site.yml
│
├── common
├── security_baseline
├── nginx
├── application
└── monitoring
```

Each role owns one meaningful responsibility.

---

# 2. What Is an Ansible Role?

An Ansible role is a structured collection of related automation content.

A role can contain:

```text
Tasks

Handlers

Templates

Files

Default variables

Role variables

Metadata

Dependencies

Documentation
```

Instead of placing everything directly inside a playbook, you organize related automation into a predictable directory structure.

---

# 3. Simple Role Mental Model

Think of a role as:

```text
ROLE
│
├── Inputs
│
├── Logic
│
├── Files
│
├── Templates
│
├── Handlers
│
├── Metadata
│
└── Resulting State
```

For example:

```text
nginx role
│
├── Input
│   ├── nginx_port
│   ├── nginx_worker_connections
│   └── nginx_server_name
│
├── Tasks
│   ├── Install Nginx
│   ├── Deploy configuration
│   └── Ensure service running
│
├── Template
│   └── nginx.conf.j2
│
├── Handler
│   └── Reload Nginx
│
└── Result
    └── Configured Nginx server
```

---

# 4. Why Roles Exist

Roles solve several problems.

Without roles:

```text
Large Playbooks
↓
Repeated Tasks
↓
Repeated Templates
↓
Repeated Variables
↓
Difficult Maintenance
↓
Configuration Divergence
```

With roles:

```text
Reusable Responsibility
↓
Defined Inputs
↓
Organized Implementation
↓
Consistent Result
```

---

# 5. What Roles Give You

Roles provide:

```text
Organization

Reuse

Consistency

Separation of responsibilities

Predictable file locations

Cleaner playbooks

Easier testing

Easier documentation

Easier review

Easier team ownership

Better version control
```

But roles do not automatically make bad automation good.

A badly designed role is still bad automation.

---

# 6. When Should Something Become a Role?

A useful question is:

```text
Does this represent a meaningful infrastructure responsibility?
```

Examples:

```text
common

security_baseline

nginx

application

monitoring

postgresql

docker

node_exporter
```

These are understandable responsibilities.

---

# 7. What Should Not Automatically Become a Role?

Do not create a role merely because you have a task.

Bad decomposition:

```text
roles/
├── install_curl/
├── create_directory/
├── copy_file/
├── start_nginx/
└── create_user/
```

You have not created architecture.

You have created fragmentation.

---

# 8. The Opposite Problem: Giant Roles

This is also poor design:

```text
roles/
└── everything/
    ├── users
    ├── ssh
    ├── sudo
    ├── firewall
    ├── nginx
    ├── application
    ├── database
    ├── monitoring
    ├── backups
    └── logging
```

That role has too many responsibilities.

---

# 9. Good Role Boundary

A useful role should usually represent:

```text
One Meaningful Responsibility
```

Not necessarily:

```text
One Task
```

and not:

```text
The Entire Infrastructure
```

For example:

```text
nginx
```

can reasonably own:

```text
Nginx package

Nginx directories

Nginx configuration

Nginx service

Nginx validation

Nginx handlers
```

Those pieces belong together.

---

# 10. Role Design Question

Before creating a role, ask:

```text
What responsibility does this role own?
```

You should be able to answer in one sentence.

Example:

```text
The nginx role installs, configures, enables,
and verifies the Nginx service.
```

Good.

Compare:

```text
The common role does some common stuff.
```

Too vague.

Define its boundary.

Inspect:

```bash
find roles/nginx -maxdepth 2 -type f
```

# 17. `tasks/`

The most important role directory is commonly:

```text
tasks/
```

Its default entry point is:

```text
tasks/main.yml
```

Example:

```yaml
---
- name: Install Nginx
  ansible.builtin.package:
    name: "{{ nginx_package_name }}"
    state: present

- name: Deploy Nginx configuration
  ansible.builtin.template:
    src: nginx.conf.j2
    dest: "{{ nginx_config_path }}"
    owner: root
    group: root
    mode: "0644"
  notify: Reload Nginx

- name: Ensure Nginx is enabled and running
  ansible.builtin.service:
    name: "{{ nginx_service_name }}"
    state: started
    enabled: true
```

This is the role's execution logic.

---

# 18. `handlers/`

Handlers belong under:

```text
handlers/
```

Default:

```text
handlers/main.yml
```

Example:

```yaml
---
- name: Reload Nginx
  ansible.builtin.service:
    name: "{{ nginx_service_name }}"
    state: reloaded
```

Now tasks inside the role can notify:

```yaml
notify: Reload Nginx
```

---

# 19. Why Handlers Belong With the Role

The Nginx role owns:

```text
Nginx Configuration
```

It should generally also own:

```text
What must happen when that configuration changes
```

Therefore:

```text
nginx/
├── tasks/
├── templates/
└── handlers/
```

forms a cohesive component.

---

# 20. `templates/`

Role templates belong under:

```text
templates/
```

Example:

```text
roles/nginx/templates/nginx.conf.j2
```

Task:

```yaml
- name: Deploy Nginx configuration
  ansible.builtin.template:
    src: nginx.conf.j2
    dest: "{{ nginx_config_path }}"
    owner: root
    group: root
    mode: "0644"
```

Inside a role, you normally do not need to write:

```text
roles/nginx/templates/nginx.conf.j2
```

as `src`.

The role provides search-path context.

---

# 21. Role Template Example

Create:

```text
roles/nginx/templates/nginx.conf.j2
```

Example training template:

```jinja2
# Managed by Ansible

user {{ nginx_user }};
worker_processes {{ nginx_worker_processes }};

events {
    worker_connections {{ nginx_worker_connections }};
}

http {
    server {
        listen {{ nginx_listen_port }};
        server_name {{ nginx_server_name }};

        root {{ nginx_document_root }};

        location / {
            try_files $uri $uri/ =404;
        }
    }
}
```

Do not assume this is a universal production Nginx configuration.

It is a training example.

Production configuration depends on your operating system, Nginx packaging, application architecture, TLS design, logging, proxying, security requirements, and performance requirements.

---

# 22. `files/`

Static files belong under:

```text
files/
```

Example:

```text
roles/application/files/healthcheck.sh
```

Task:

```yaml
- name: Install application health-check script
  ansible.builtin.copy:
    src: healthcheck.sh
    dest: /usr/local/bin/veriqta-healthcheck
    owner: root
    group: root
    mode: "0755"
```

Again:

```text
src: healthcheck.sh
```

is normally enough from inside the role.

---

# 23. `files/` vs `templates/`

Use:

```text
files/
```

when the source should be transferred without Jinja rendering.

Use:

```text
templates/
```

when the source contains dynamic values.

Mental model:

```text
Static Content
↓
files/
```

```text
Dynamic Jinja2 Content
↓
templates/
```

---

# 24. Example

Static script:

```bash
#!/usr/bin/env bash
uptime
```

Could live in:

```text
files/
```

Dynamic application configuration:

```jinja2
listen_port={{ application_port }}
environment={{ application_environment }}
```

belongs in:

```text
templates/
```

---

# 25. `defaults/`

Role defaults live under:

```text
defaults/main.yml
```

Example:

```yaml
---
nginx_package_name: nginx
nginx_service_name: nginx
nginx_listen_port: 80
nginx_server_name: _
nginx_document_root: /var/www/html
nginx_worker_processes: auto
nginx_worker_connections: 1024
```

These are intended to be easy for callers to override.

---

# 26. Why Defaults Matter

Without defaults, the role might require every caller to specify:

```text
Package name
Service name
Port
Document root
Worker count
Server name
```

even when sensible defaults exist.

Instead:

```text
Role Default
↓
Works for Normal Case
```

while:

```text
Inventory / Role Parameter / Other Appropriate Override
↓
Customizes Environment
```

---

# 27. Default Variables Are an Interface

Think of:

```text
defaults/main.yml
```

as part of the role's public interface.

If a user is expected to customize:

```text
nginx_listen_port
```

then defining:

```yaml
nginx_listen_port: 80
```

in defaults communicates:

```text
This is configurable.
```

---

# 28. Namespace Role Variables

Avoid generic role variables such as:

```yaml
port: 80
user: nginx
path: /var/www/html
```

These names are too broad.

Prefer:

```yaml
nginx_listen_port: 80
nginx_user: nginx
nginx_document_root: /var/www/html
```

Why?

Because multiple roles share the same variable namespace during execution.

Clear prefixes reduce collisions and ambiguity.

---

# 29. `vars/`

Role variables can live in:

```text
vars/main.yml
```

Example:

```yaml
---
nginx_config_directory: /etc/nginx
```

But you must understand an important difference.

Role vars have much higher precedence than role defaults.

They are harder for ordinary inventory configuration to override.

---

# 30. Defaults vs Vars

Mental model:

```text
defaults/
↓
Public, easily overridable defaults
```

```text
vars/
↓
Role-owned values that are deliberately harder to override
```

This difference matters.

---

# 31. Beginner Rule for Defaults vs Vars

Ask:

```text
Should the person using this role reasonably change this?
```

If:

```text
YES
```

consider:

```text
defaults/main.yml
```

If:

```text
NO, this is an implementation detail or tightly controlled role value
```

you may consider:

```text
vars/main.yml
```

But do not overuse role vars.

---

# 32. Why Overusing `vars/` Is a Problem

Suppose you put:

```yaml
nginx_listen_port: 80
```

in:

```text
vars/main.yml
```

A team tries to set:

```yaml
nginx_listen_port: 8080
```

in ordinary inventory.

They may discover their inventory value does not win because of Ansible variable precedence.

Now your role is unnecessarily difficult to customize.

---

# 33. Good Role Interface Design

A reusable role should make clear:

```text
What can callers configure?

What must callers configure?

What values have defaults?

What values are internal?

What state will the role create?
```

This is role interface design.

---

# 34. Inputs

An input is configuration supplied to or consumed by a role.

Example:

```yaml
nginx_listen_port: 8080
nginx_server_name: app.example.test
nginx_document_root: /srv/application
```

Conceptually:

```text
Caller
↓
Role Inputs
↓
Role Logic
↓
Managed State
```

---

# 35. Required Inputs

Not every input should have a fake default.

Imagine an application role needs:

```text
application_release_version
```

Do not invent:

```yaml
application_release_version: latest
```

merely to prevent an undefined-variable error if "latest" would be unsafe.

Some values should be required.

---

# 36. Validate Required Inputs

A simple approach:

```yaml
- name: Validate required application inputs
  ansible.builtin.assert:
    that:
      - application_release_version is defined
      - application_release_version | length > 0
    fail_msg: "application_release_version must be provided."
```

Fail early.

Fail clearly.

---

# 37. Role Argument Validation Concept

Modern Ansible roles can also define role argument specifications.

This provides a formal way to describe and validate expected role arguments.

A role can use:

```text
meta/argument_specs.yml
```

to describe inputs.

This is especially valuable for reusable roles.

---

# 38. Example Argument Specification

Conceptually:

```yaml
---
argument_specs:
  main:
    short_description: Configure the VERIQTA Nginx service
    options:
      nginx_listen_port:
        type: int
        required: false
        default: 80

      nginx_server_name:
        type: str
        required: true
```

The exact interface should reflect the real role.

Do not add argument validation merely for decoration.

Use it to make incorrect role usage fail clearly.

---

# 39. Why Role Input Validation Matters

Without validation:

```text
Wrong Input
↓
Role Executes 12 Tasks
↓
Template Fails
↓
Confusing Error
```

With validation:

```text
Wrong Input
↓
Validation
↓
Immediate Clear Failure
```

That improves maintainability.

---

# 40. Outputs Concept

Roles do not behave exactly like traditional programming functions with formal return objects.

But a role can still produce things that later automation uses.

Examples:

```text
Managed infrastructure state

Registered data

Facts

Files

Service state

Host-level variables created deliberately
```

Treat "outputs" as a design concept rather than pretending every role has a formal return value.

---

# 41. Example Role Output Concept

Suppose an application role discovers:

```text
application_deployed_version
```

A later verification step may use that information.

But be careful about hidden coupling.

A role should not secretly create dozens of variables that unrelated roles must know about.

---

# 42. Prefer Explicit Interfaces

Bad architecture:

```text
Role A
↓
Secretly Sets 17 Variables
↓
Role B Somehow Depends on Them
```

Better:

```text
Inventory / Playbook
↓
Explicit Configuration
├── Role A
└── Role B
```

or a clearly documented dependency where one truly exists.

---

# 43. `meta/`

Role metadata lives under:

```text
meta/
```

Common file:

```text
meta/main.yml
```

Metadata can describe role information and dependencies.

For distributed roles, metadata can also support ecosystem information used by Ansible tooling and Galaxy workflows.

---

# 44. Role Dependencies

Suppose an application genuinely requires another role to run first.

Conceptually:

```text
application
↓
depends on
↓
runtime
```

A role dependency can express that relationship.

---

# 45. Dependency Example

Conceptual `meta/main.yml`:

```yaml
---
dependencies:
  - role: common
```

When appropriate, dependencies can also receive parameters.

But use dependencies carefully.

---

# 46. Do Not Hide Your Entire Architecture in Dependencies

This is technically tempting:

```text
application
↓
depends on nginx
↓
depends on security
↓
depends on common
↓
depends on monitoring
```

Now running:

```text
application
```

silently triggers half the infrastructure.

That may surprise operators.

---

# 47. Explicit Composition vs Hidden Dependencies

For infrastructure orchestration, this is often easier to understand:

```yaml
roles:
  - common
  - security_baseline
  - nginx
  - application
  - monitoring
```

The architecture is visible.

Use role dependencies when the dependency is truly intrinsic to the role.

---

# 48. Dependency Question

Ask:

```text
Can this role meaningfully function without that other role?
```

If no:

```text
Possible true dependency
```

If yes, but your site merely happens to use both:

```text
Compose them explicitly in the playbook
```

Example:

```text
roles/nginx/README.md
```

Documentation is part of the role.

# 50. What a Role README Should Explain

At minimum:

```text
Role purpose

Supported systems

Prerequisites

Required values

Example usage
```

# 51. Example README Structure

````markdown
# nginx

## Purpose

Installs and configures Nginx for VERIQTA-managed web servers.

## Supported Platforms

- Ubuntu
- Debian

## Requirements

- Privilege escalation
- Python available on managed nodes

## Role Variables

### nginx_listen_port

Default: `80`

TCP port used by the training web server configuration.

### nginx_server_name

Required for environments using explicit virtual-host names.

## Example

```yaml
roles:
  - role: nginx
    vars:
      nginx_listen_port: 8080
````

## Verification

The role verifies that the Nginx service is running.

## Security Notes

Production deployments should define TLS, exposure, firewall,
logging, and reverse-proxy policy separately.

````

Documentation should help someone use the role without reading every implementation file.

# 52. Calling a Role With `roles`

The simplest role usage is:

```yaml
---
- name: Configure web servers
  hosts: web
  become: true

  roles:
    - nginx
````

Ansible loads the role as part of the play.

---

# 53. Multiple Roles

Example:

```yaml
---
- name: Configure web servers
  hosts: web
  become: true

  roles:
    - common
    - security_baseline
    - nginx
    - application
    - monitoring
```

This is much easier to read than hundreds of inline tasks.

---

# 54. Pass Variables to a Role

Example:

```yaml
roles:
  - role: nginx
    vars:
      nginx_listen_port: 8080
      nginx_server_name: app.example.test
```

Now the role remains reusable.

# 55. Role Invocation Mental Model

```text
Play
↓
Role Invocation
↓
Inputs
↓
Role Tasks
↓
Templates / Files
↓
Handlers
↓
Desired State
```

---

# 56. Role Defaults and Caller Overrides

Role:

```yaml
# roles/nginx/defaults/main.yml

nginx_listen_port: 80
```

Caller:

```yaml
roles:
  - role: nginx
    vars:
      nginx_listen_port: 8080
```

Result:

```text
Role Default
80
↓
Caller Supplies
8080
↓
Role Uses
8080
```

This is one reason role defaults are useful.

---

# 57. Inventory Overrides

You can also keep environment-specific configuration in inventory.

Example:

```text
group_vars/production.yml
```

```yaml
nginx_listen_port: 443
```

while:

```text
group_vars/development.yml
```

might contain:

```yaml
nginx_listen_port: 8080
```

The same role can serve multiple environments.

---

# 58. Roles Should Not Know Your Entire Environment

Bad role design:

```yaml
when: inventory_hostname == 'prod-web-03'
```

scattered throughout the role.

Now the reusable Nginx role knows about one specific server.

Prefer environment data outside the role.

---

# 59. Better Design

Inventory:

```yaml
nginx_listen_port: 8080
```

Role:

```yaml
- name: Deploy Nginx configuration
  ansible.builtin.template:
    src: nginx.conf.j2
    dest: "{{ nginx_config_path }}"
```

The role knows:

```text
How to configure Nginx
```

Inventory knows:

```text
How this environment differs
```

---

# 60. Role Reuse

Suppose you have:

```text
Development
Staging
Production
```

Do not copy:

```text
roles/nginx_dev
roles/nginx_staging
roles/nginx_prod
```

just because values differ.

Prefer:

```text
roles/nginx
```

plus environment-specific variables.

---

# 61. Reuse Architecture

```text
                  nginx role
                     │
          ┌──────────┼──────────┐
          ↓          ↓          ↓
     Development   Staging   Production
          │          │          │
        Vars       Vars        Vars
```

One implementation.

Different configuration.

---

# 62. `include_role`

A role can also be dynamically included as a task.

Example:

```yaml
- name: Load Nginx role
  ansible.builtin.include_role:
    name: nginx
```

This appears inside a task context.

---

# 63. Conditional Role Inclusion

Example:

```yaml
- name: Configure Nginx when requested
  ansible.builtin.include_role:
    name: nginx
  when: web_server_enabled | bool
```

This is dynamic role reuse.

---

# 64. Looping Over `include_role`

Because dynamic includes operate at runtime, they can be useful with loops.

Conceptual example:

```yaml
- name: Configure selected components
  ansible.builtin.include_role:
    name: "{{ component_role }}"
  loop:
    - nginx
    - monitoring
  loop_control:
    loop_var: component_role
```

Do not build clever dynamic-role loops simply because they are possible.

Explicit architecture is often easier to understand.

# 65. `import_role`

Static role reuse uses:

```text
ansible.builtin.import_role
```

Example:

```yaml
- name: Import Nginx role
  ansible.builtin.import_role:
    name: nginx
```

This is also placed in a task context.

# 66. Static vs Dynamic Role Reuse

High-level mental model:

```text
import_role
↓
Static
↓
Role content processed as part of playbook parsing
```

```text
include_role
↓
Dynamic
↓
Role loaded during task execution
```

This distinction affects behavior.

---

# 67. Do Not Reduce the Difference to One Sentence

Static vs dynamic reuse affects areas such as:

```text
When content is processed

Conditionals

Loops

Tags

Variable exposure

Error timing

Task visibility
```

You do not need to memorize every edge case today.

You do need the correct mental model.

---

# 68. Basic Selection Rule

When you simply want a known role as part of a play:

```text
roles:
```

is often the clearest.

When you need task-time dynamic behavior:

```text
include_role
```

may be appropriate.

When you intentionally need static task-style role reuse:

```text
import_role
```

may be appropriate.

Do not choose based on whichever syntax you remember first.

---

# 69. Static Reuse

Think:

```text
Ansible Reads Playbook
↓
Imported Content Becomes Known
↓
Execution Later Follows That Structure
```

---

# 70. Dynamic Reuse

Think:

```text
Ansible Executes Tasks
↓
Reaches Include
↓
Evaluates Runtime Context
↓
Loads Included Content
↓
Executes It
```

# 71. Important `include_role` Tag Behavior

Do not assume a tag placed on a dynamic role include automatically behaves exactly like a tag applied to every task inside that role.

Dynamic inclusion has specific tag semantics.

If you need task keywords such as tags applied to included role tasks, `include_role` supports an `apply` mechanism.

Example concept:

```yaml
- name: Include Nginx role
  ansible.builtin.include_role:
    name: nginx
    apply:
      tags:
        - web
  tags:
    - always
```

Test your tag behavior.

Do not assume.

---

# 72. `include_role` and Task Keywords

A useful mental distinction:

```text
Keyword on include_role
↓
May apply to the include operation
```

versus:

```text
apply:
↓
Can apply supported task keywords to tasks inside the included role
```

This is one reason static and dynamic reuse are not interchangeable in every situation.

```text

↓

```


A dynamic include can select the appropriate file.

# 80. Safer OS Mapping

```yaml
- name: Load Debian-family tasks
  ansible.builtin.include_tasks: debian.yml

- name: Load Red Hat-family tasks
  ansible.builtin.include_tasks: redhat.yml
  when: ansible_facts['os_family'] == 'RedHat'
```

# 112. Role Ordering

Order can matter.

```text

↓

↓

↓
```

```text

```

---

# 113. Role Ownership Rule

A role should generally create the resources it needs when those resources belong to its responsibility.

Bad:

```text
common role
↓
Creates /opt/myapp

application role
↓
Assumes it exists
```

Better:

```text
application role
↓
Creates /opt/myapp
↓
Deploys application there
```

Now the application role is more self-contained.

---

# 114. Self-Contained Does Not Mean Duplicated

A role should own its resources.

But do not make every role independently install:

```text
curl
git
python
```

without thought.

If multiple roles require shared platform prerequisites, define clear ownership.

---

# 115. Role Boundaries Are Architecture

Role design asks:

```text
Who owns this resource?
```

Examples:

```text
/etc/nginx/nginx.conf
↓
nginx
```

```text
/opt/veriqta
↓
application
```

```text
monitoring-agent.service
↓
monitoring
```

```text
admin SSH access
↓
security_baseline
```

Clear ownership reduces conflicts.

---

# 116. Two Roles Should Not Fight Over the Same File

Danger:

```text
Role A
↓
Manages /etc/example.conf
```

```text
Role B
↓
Also manages /etc/example.conf
```

Now execution order determines the final state.

That is configuration conflict.

---

# 117. Single Ownership Principle

Prefer:

```text
One Managed Resource
↓
One Clear Automation Owner
```

Other roles may consume information about it.

They should not casually overwrite it.

---

# 118. Role Naming

Use names that communicate responsibility.

Good:

```text

security_baseline

nginx

application

monitoring
```

Poor:

```text

setup

stuff

misc

server

```

A name should tell the reader what the role owns.

For local roles, choose a consistent naming convention.

For future collection compatibility, underscore-based names are a safe convention:


rather than building naming habits around hyphens.

# 126. Role Versioning Concept

Reusable automation changes over time.

You may have:

```text
v1.0.0

v1.1.0

v2.0.0
```

Versioning helps consumers understand which role revision they are using.

---

# 127. Why Version Roles?

Imagine ten projects consume the same role.

Then you change:

```text
Default port

Package source

Configuration format

Variable name

Service behavior
```

If everyone automatically consumes the newest revision, one change can affect many environments.

Versioning creates control.

---

# 128. Versioning Mental Model

```text
Reusable Role
↓
Version
↓
Tested Consumer
↓
Controlled Upgrade
```

not:

```text
Reusable Role
↓
Whatever Changed Today
↓
Production
```

# 129. Semantic Versioning Concept

Many projects use a pattern such as:

```text
MAJOR.MINOR.PATCH
```

Conceptually:

```text
PATCH
↓
Backward-compatible fixes
```

```text
MINOR
↓
Backward-compatible functionality
```

```text
MAJOR
↓
Breaking interface changes
```

Your project should define and document its versioning policy.

# 132. Role Idempotency

A role should normally converge repeatedly.

Example:

```text
First Run
↓
Install Nginx
Deploy Config
Start Service
CHANGED
```

Second run:

```text
Package Correct
Config Correct
Service Running
OK
```

That is desirable.

---

# 133. Test Role Idempotency

Run:

```bash
ansible-playbook -i inventory/hosts.yml site.yml
```

Then run it again:

```bash
ansible-playbook -i inventory/hosts.yml site.yml
```

Investigate unexpected:

```text
changed
```

results.

Do not blindly declare that every changed result is a bug.

Some operations are intentionally non-idempotent.

But understand every recurring change.

---

# 134. Common Role Idempotency Problems

Examples:

```text
shell commands that run every time

command tasks without state guards

templates containing changing timestamps

random values generated each run

service restarts called directly every run

downloads without stable conditions

scripts that always modify files

tasks with incorrect changed_when
```

---

# 135. Timestamp Trap

Bad template:

```jinja2
# Generated at {{ ansible_date_time.iso8601 }}
```

Every run produces different content.

Then:

```text
Template Changed
↓
Handler Notified
↓
Service Restarted
```

every run.

Do not place changing data in managed configuration unless you actually need it.

---

# 136. Idempotent Handler Design

Prefer:

```text
Template
↓
Changed?
├── NO → No Handler
└── YES → Notify Handler
```

instead of:

```text
Template
↓
Restart Service Regardless
```

Example:

```text

↓

```

```text
RedHat
↓
DNF
```

But you do not want one unreadable `main.yml`.


```yaml
  ansible.builtin.dnf:
```

The implementation adapts.

# 141. Avoid Platform Logic Everywhere

Bad:

```text
Task 1 when Debian
Task 2 when RedHat
Task 3 when Debian
Task 4 when RedHat
Task 5 when Debian
Task 6 when RedHat
...
```

Better:

```text
Detect Supported Family
↓
Load Appropriate Implementation
```

when the implementations meaningfully diverge.

# 142. Fail on Unsupported Platforms

Do not silently skip everything.

Example:

```yaml
- name: Verify supported operating-system family
  ansible.builtin.assert:
    that:
      - ansible_facts['os_family'] in ['Debian', 'RedHat']
    fail_msg: >-
      The common role does not currently support
      {{ ansible_facts['os_family'] }}.
```

Explicit failure is often safer than partial configuration.

# 143. Role Testing Concepts

A role should not be considered reusable merely because it worked once on your laptop.

Testing should ask:

```text
Does it parse?

Do inputs validate?

Does it work on supported platforms?

Is it idempotent?

Does it produce expected files?

Are permissions correct?

Does the service start?

Does verification pass?

Does failure occur clearly on unsupported input?
```

```text

≠
```

# 151. Verification Inside vs Outside the Role

There are two useful layers.

Role-level verification:

```text
Does this component work?
```

System-level verification:

```text
Does the assembled system work?
```

Both matter.

Nginx role:

```text

```

```text
Can the application be reached through the complete production path?
```

# 153. Role Documentation

Documentation should answer:

```text
Why does this role exist?

What does it manage?

What does it not manage?

Which platforms are supported?

What inputs exist?

Which are required?

What are the defaults?

What dependencies exist?

Which collections are required?

What handlers exist?

How do I verify it?

```

---

# 154. Documentation Is Not Optional for Reuse

If the only way to use a role is:

```text
Read 700 lines of YAML
```

the role interface is poorly documented.

Reusable automation needs human-readable contracts.

---

# 155. Avoid Hidden Assumptions

Bad role:

```text
Assumes user deploy exists

Assumes /opt/app exists

Assumes nginx already installed

Assumes port 8080 is free

Assumes Ubuntu

Assumes systemd

Assumes internet access
```

without documenting any of it.

A reusable role should either:

```text
Manage the requirement
```

or:

```text
Declare the requirement
```

---

# 156. Avoid Hidden Side Effects

A role called:

```text
nginx
```

should not unexpectedly:

```text
Create application users

Modify database configuration

Install Docker

Change hostname

Disable firewall

Create cloud resources
```

Role names should align with role behavior.

---

# 157. Avoid Giant Roles

Warning signs:

```text
One role has 70 unrelated variables

One role configures five unrelated services

One role owns files across unrelated applications

One role contains hundreds of unrelated tasks

Every server receives the same giant role
```

Ask whether responsibilities need separation.

---

# 158. Avoid Tiny Meaningless Roles

Warning signs:

```text
install_curl role

create_tmp_directory role

restart_service role

copy_one_file role
```

Reuse does not require turning every operation into an abstraction.

---

# 159. Goldilocks Role Principle

Aim for:

```text
Not Too Large
+
Not Meaninglessly Small
=
Cohesive Responsibility
```

There is no universal task-count threshold.

Use responsibility and ownership as your guide.

---

# 160. Avoid Role Chains That Nobody Understands

Bad:

```text
site.yml
↓
role_a
↓
dependency role_b
↓
include role_c
↓
import role_d
↓
include tasks from role_e
```

Possible?

Maybe.

Maintainable?

Probably not.

Favor architecture people can trace.

---

# 161. Avoid Clever Automation

Infrastructure automation should usually optimize for:

```text
Predictability

Readability

Reviewability

Recoverability
```

not cleverness.

If a junior engineer cannot determine why a role ran, your architecture may be too opaque.

---

# 162. Role Failure Boundaries

Suppose:

```text
common succeeds
security_baseline succeeds
nginx fails
application not yet run
monitoring not yet run
```

You need to understand the resulting partial state.

Roles organize code.

They do not provide transactional rollback automatically.

---

# 163. Roles Are Not Transactions

Do not assume:

```text
Role Fails
↓
Everything Role Changed Automatically Rolls Back
```

That is not the normal Ansible model.

Design recovery deliberately.

---

# 164. Recovery Thinking

For important roles, ask:

```text
What can fail halfway?

What state remains?

Can I safely rerun?

Will the role converge?

Do I need backup before replacing configuration?

Can I restore the previous version?

Will a handler run?

How do I verify recovery?
```

---

# 165. Security Role Design

Security-sensitive roles deserve extra care.

Examples:

```text
SSH

sudo

Firewall

Authentication

Certificates

Secrets
```

A mistake can remove access or create exposure.

Use:

```text
Validation

Staged changes

Backups where appropriate

Explicit verification

Recovery access

Small rollout batches
```

---

# 166. Do Not Put Secrets in Role Defaults

Bad:

```yaml
database_password: SuperSecret123
```

in:

```text
defaults/main.yml
```

Role repositories are commonly version-controlled and shared.

Defaults are not secret storage.

---

# 167. Do Not Put Secrets in Role Vars Either

Moving a plaintext secret from:

```text
defaults/
```

to:

```text
vars/
```

does not make it secure.

Variable precedence and secret protection are separate problems.

Part 13 will cover Vault and secret handling.

---

# 168. Files Can Be Sensitive Too

Check:

```text
files/

templates/

README examples

test fixtures

defaults/

vars/
```

for:

```text
Private keys

Tokens

Passwords

Certificates with private material

Internal credentials

Sensitive endpoints
```

before committing a role.

---

# 169. Role Reuse Across Teams

A shared role should minimize assumptions about:

```text
Hostnames

Inventory group names

Specific server addresses

Personal usernames

Environment names

Company-specific paths
```

unless those are intentionally part of its contract.

# 170. Local Role vs Shared Role

A local project role may reasonably be tightly coupled to one infrastructure.

A reusable organizational or public role requires a stronger interface.

Think:

```text
Local Role
↓
Reuse inside one repository
```

versus:

```text
Shared Role
↓
Reuse across repositories or teams
```

The second needs stronger:

```text
Documentation

Input validation

Compatibility policy

Testing

Versioning
```

# 171. Standalone Roles and Collections

A standalone project can contain:

```text
roles/
```

directly.

Roles can also be distributed inside Ansible collections.

Conceptually:

```text
Collection
│
├── Roles
├── Modules
├── Plugins
├── Playbooks
└── Other Ansible Content
```

Part 12 will cover this properly.

# 172. Collection Role Naming

When roles are distributed inside collections, naming rules matter.

Use clean role names such as:

```text
security_baseline
```

instead of relying on names that may not be valid in collection role structures.

This is another reason consistent underscore naming is useful.

---

# 173. Fully Qualified Collection Roles

A role distributed in a collection can be referenced by an FQCN conceptually like:

```text
namespace.collection.role_name
```

Example shape:

```text
company.platform.nginx
```

Do not invent a namespace for a real dependency.

Use the actual collection documentation.

# 174. Role Search Paths

Ansible must be able to find standalone roles.

Typical project structure:

```text
project/
├── site.yml
└── roles/
    └── nginx/
```

works naturally for common project layouts.

Role paths can also be configured.

If Ansible says it cannot find a role, investigate the search path rather than copying the role randomly into directories.

```text

```

```text
Managed-node destination
```

# 178. Troubleshooting Undefined Role Variable

Error:

```text
nginx_listen_port is undefined
```

Investigate:

```text
Should it have a default?

Is it required?

Was it documented?

Was it supplied in inventory?

Was it supplied as a role parameter?

Is the variable name misspelled?

Is the expected group applied to this host?
```

Do not solve every undefined variable by adding random defaults.

---

# 179. Troubleshooting Wrong Variable Value

Think:

```text
Unexpected Value
↓
Role Default?
↓
Inventory?
↓
Play Variable?
↓
Role Var?
↓
Role Parameter?
↓
Extra Variable?
↓
Other Higher-Precedence Source?
```

Variable precedence still matters inside roles.

---

# 180. Troubleshooting Handler Did Not Run

Check:

```text
Was handler notified?

Did notifying task actually report changed?

Does notify name match handler/listen target?

Was the relevant role/task executed?

Was execution stopped by an earlier failure?

Was the handler intentionally flushed earlier/later?
```

Do not force a task to report changed just to make a handler execute unless that accurately represents reality.

---

# 181. Troubleshooting Wrong OS Tasks

Check:

```text
Were facts gathered?

What is ansible_facts['os_family']?

Does the role support that value?

Was the correct include selected?

Does the package name differ?

Does the service name differ?

Does the configuration path differ?
```

Never guess the OS fact value.

Inspect it.

# 182. Troubleshooting Dynamic Includes

```text
File existence

Variable scope
```

Dynamic reuse means runtime context matters.

# 183. Troubleshooting Static Imports


or:

# 220. Practical Assessment

Without copying the completed example, build:

```text
site.yml
│
├── common
├── security_baseline
├── nginx
├── application
└── monitoring
```

Requirements:

```text
1. Every role has a documented responsibility.

2. Public variables use role-specific prefixes.

3. Configurable values use defaults appropriately.

4. Required inputs are validated.

5. No plaintext secrets exist in roles.

6. Static assets use files/.

7. Dynamic configuration uses templates/.

8. Service reactions use handlers.

9. Nginx tasks are separated into meaningful task files.

10. OS-specific logic is isolated cleanly.

11. Unsupported operating systems fail clearly where appropriate.

12. site.yml shows architecture rather than implementation detail.

13. At least one role is invoked with custom parameters.

14. At least one training example demonstrates include_role.

15. At least one training example demonstrates import_role.

16. At least one role demonstrates include_tasks or import_tasks appropriately.

17. Important component outcomes are verified.

18. First execution succeeds.

19. Second execution demonstrates appropriate idempotency.

20. Every role has a useful README.
```

Then explain why each role boundary exists.

If you cannot explain the boundary, reconsider the design.

# 223. The Most Important Role Design Rule

Do not ask:

```text
How many tasks should a role contain?
```

Ask:

```text
What responsibility does this role own?
```

Then ask:

```text
Are all these tasks necessary to fulfill that responsibility?
```

and:

```text
Does anything here belong to another responsibility?
```

That is how you find useful role boundaries.
