# Part 15: Ansible Troubleshooting and Failure Investigation

## Build the Troubleshooting Skills Required in Real Environments

Ansible automation is valuable because it allows you to make predictable changes across many systems.

But real infrastructure is not predictable all the time.

Networks fail.

DNS records become stale.

SSH keys expire or are replaced.

Users lose permissions.

Repositories disappear.

Packages change.

Variables are overridden.

Templates contain mistakes.

Services refuse to start.

Python exists on one server and not another.

One server succeeds while another fails halfway through the same deployment.

A production Ansible engineer therefore needs two different skills:

```text
BUILDING AUTOMATION
+
INVESTIGATING AUTOMATION
```

Writing a playbook is only part of the job.

You must also be able to answer:

```text
What failed?

Where did it fail?

Why did it fail?

What changed before it failed?

Which hosts are affected?

Is it an Ansible problem or a remote-system problem?

Can I safely run the automation again?

How do I prove the system is healthy afterward?
```

That is what this part teaches.

---

# 1. What Troubleshooting Actually Means

Troubleshooting is not:

```text
See error
↓
Search error online
↓
Copy random fix
↓
Run again
```

Professional troubleshooting is:

```text
Observe
↓
Classify
↓
Isolate
↓
Collect Evidence
↓
Form Hypothesis
↓
Test Hypothesis
↓
Find Root Cause
↓
Apply Controlled Fix
↓
Run Again
↓
Verify
```

The difference is important.

Random fixes can make an error disappear while leaving the actual problem unresolved.

# 3. Why Troubleshooting by Layers Works

Imagine this command fails:

```bash
ansible-playbook -i inventory/production.yml site.yml
```

Many engineers immediately open:

```text
site.yml
```

and start changing tasks.

But the playbook may be perfectly correct.

The actual failure could be:

```text
Wrong inventory
Wrong hostname
Broken DNS
Firewall
Port 22 blocked
Wrong SSH key
Wrong remote user
Sudo denied
Python missing
Collection missing
Undefined variable
Invalid template
Broken package repository
Service configuration error
Application failure
```

The visible Ansible error is often only the point where another problem became visible.

# 5. First Rule: Read Before Changing

When something fails, do not immediately rerun it.

Read the output.

Capture:

```text
Play name
Task name
Host
Status
Error message
Return code
stdout
stderr
Timestamp
PLAY RECAP
```

Then ask:

```text
What is the first layer I can prove is broken?
```

---

# 6. Reading Ansible Output

You will repeatedly encounter these states:

```text
ok
changed
failed
unreachable
skipped
```

Understanding them is foundational.

---

# 7. `ok`

Example:

```text
ok: [web01]
```

Usually this means:

```text
Task completed successfully
+
No change was required
```

For example:

```yaml
- name: Ensure Nginx is installed
  ansible.builtin.package:
    name: nginx
    state: present
```

If Nginx is already installed, you may receive:

```text
ok: [web01]
```

Ansible inspected the current state and found that it already matched the requested state.

---

# 8. `ok` Does Not Mean Everything Is Healthy

Suppose:

```text
TASK [Ensure configuration directory exists]
ok: [web01]
```

That proves only that this task did not need to change the directory.

It does not prove:

```text
Nginx is healthy
Application is healthy
Database works
Port 443 works
Users can reach the service
```

Task status must always be interpreted in context.

---

# 9. `changed`

Example:

```text
changed: [web01]
```

This normally means Ansible believes the task changed managed state.

Examples:

```text
Package installed
File created
Template updated
User created
Permissions changed
Service started
```

---

# 10. Expected `changed`

On a fresh server:

```text
Install Nginx
↓
changed
```

is expected.

---

# 11. Suspicious `changed`

Suppose you run the same stable playbook repeatedly:

```text
Run 1 → changed
Run 2 → changed
Run 3 → changed
Run 4 → changed
```

That deserves investigation.

A properly designed state-management task should often become:

```text
Run 1 → changed
Run 2 → ok
Run 3 → ok
```

when nothing else has changed.

Repeated changes can reveal an idempotency problem.

---

# 12. `failed`

Example:

```text
fatal: [web01]: FAILED!
```

This generally means Ansible got far enough to execute the task but the task returned a failure.

Examples:

```text
Package does not exist
Command returned failure
Template could not render
Configuration validation failed
File operation failed
Service refused to start
```

---

# 13. `unreachable`

Example:

```text
fatal: [web01]: UNREACHABLE!
```

This usually means Ansible could not successfully establish or use the required connection to the managed host.

Think first about:

```text
Inventory
DNS
Routing
Firewall
Port
SSH
Authentication
Host keys
Remote user
Bastion configuration
```

Do not begin by debugging the Nginx task.

The Nginx task may never have executed.

---

# 14. FAILED vs UNREACHABLE

This distinction should become automatic.

```text
UNREACHABLE
↓
Can Ansible reach and connect to the machine?
```

```text
FAILED
↓
Ansible got farther. Why did the operation fail?
```

That one distinction can save enormous troubleshooting time.

---

# 15. `skipped`

Example:

```text
skipping: [web01]
```

A task may be skipped because of:

```text
when condition
Tag selection
Operating-system condition
Loop condition
Variable-driven logic
Check-mode behavior
```

Skipped is not necessarily an error.

---

# 16. Unexpected Skips

Suppose:

```yaml
- name: Install package on Debian systems
  ansible.builtin.apt:
    name: nginx
    state: present
  when: ansible_facts['os_family'] == 'Debian'
```

The task unexpectedly says:

```text
skipping: [web01]
```

Do not rewrite the condition immediately.

Inspect the actual fact:

```yaml
- name: Inspect OS family
  ansible.builtin.debug:
    var: ansible_facts['os_family']
```

Troubleshooting means inspecting reality rather than assuming it.

---

# 17. PLAY RECAP

At the end of a playbook, you might see:

```text
PLAY RECAP

web01 : ok=18 changed=3 unreachable=0 failed=0 skipped=2
web02 : ok=10 changed=1 unreachable=1 failed=0 skipped=1
web03 : ok=12 changed=2 unreachable=0 failed=1 skipped=0
```

This is one of your most useful summaries.

---

# 18. Reading PLAY RECAP

From that example:

```text
web01
```

completed without a reported failed or unreachable task.

```text
web02
```

became unreachable.

```text
web03
```

experienced a task failure.

That means you already have two different investigations:

```text
web02 → connection investigation

web03 → task/system investigation
```

---

# 19. Partial Success

Suppose you manage:

```text
web01
web02
web03
web04
web05
```

and:

```text
web01 → success
web02 → success
web03 → failed
web04 → success
web05 → success
```

Your environment may now contain different states.

This is called a partial failure situation.

Production troubleshooting must account for this.

---

# 20. Ansible Is Not Automatically Transactional

Suppose:

```text
Task 1 → success
Task 2 → success
Task 3 → changed
Task 4 → changed
Task 5 → FAILED
```

Ansible does not automatically undo Tasks 1 through 4.

That means:

```text
FAILED
```

does not mean:

```text
Nothing changed.
```

This is one of the most important production lessons in this entire series.

---

# 21. Verbosity

Ansible allows you to increase diagnostic output using repeated:

```text
-v
```

Common troubleshooting levels:

```text
-v
-vv
-vvv
-vvvv
```

Do not automatically jump to maximum output.

Increase detail as necessary.

---

# 22. `-v`

Example:

```bash
ansible-playbook \
  -i inventory/production.yml \
  site.yml \
  -v
```

Use when normal output does not provide enough information.

Think:

```text
Normal output
↓
Need a little more detail
↓
-v
```

---

# 23. `-vv`

Example:

```bash
ansible-playbook \
  -i inventory/production.yml \
  site.yml \
  -vv
```

Provides additional execution detail.

Useful when:

```text
-v was insufficient
```

but you do not yet need deep connection debugging.

---

# 24. `-vvv`

Example:

```bash
ansible-playbook \
  -i inventory/production.yml \
  site.yml \
  -vvv
```

This is a useful general troubleshooting level.

It can expose significantly more information about execution and connections.

---

# 25. `-vvvv`

Example:

```bash
ansible \
  -i inventory/production.yml \
  web01 \
  -m ansible.builtin.ping \
  -vvvv
```

This is particularly useful when investigating connection behavior such as SSH.

---

# 26. More Verbosity Is Not Always Better

Very verbose output can:

```text
Create thousands of lines
Hide the useful error
Expose infrastructure details
Expose command arguments
Produce huge CI logs
Complicate incident investigation
```

Use verbosity deliberately.

---

# 27. Security and Verbose Logs

Treat verbose output as potentially sensitive.

It may expose:

```text
Hostnames
IP addresses
Usernames
Paths
Commands
Infrastructure topology
Module arguments
Operational details
```

Do not blindly paste production debug output into:

```text
GitHub issues
Public forums
Chat rooms
Tickets visible outside your organization
```

Review it first.

---

# 28. Start With Inventory

Before debugging SSH, confirm that Ansible is targeting the host you think it is targeting.

Use:

```bash
ansible-inventory \
  -i inventory/production.yml \
  --graph
```

This shows inventory relationships.

---

# 29. Inspect the Complete Inventory

Use:

```bash
ansible-inventory \
  -i inventory/production.yml \
  --list
```

This helps you inspect how Ansible parsed the inventory.

---

# 30. Inspect One Host

Use:

```bash
ansible-inventory \
  -i inventory/production.yml \
  --host web01
```

Ask:

```text
What does Ansible believe about web01?
```

Look for things such as:

```text
ansible_host
ansible_user
ansible_port
ansible_python_interpreter
group-derived variables
host variables
```

---

# 31. Inventory Alias Problems

Example:

```yaml
all:
  children:
    web:
      hosts:
        web01:
          ansible_host: 10.10.20.15
```

Here:

```text
web01
```

is the inventory hostname.

But Ansible connects to:

```text
10.10.20.15
```

Do not confuse:

```text
inventory_hostname
```

with:

```text
ansible_host
```

---

# 32. Wrong Inventory

A technically perfect playbook can still cause an incident if you run:

```bash
ansible-playbook \
  -i inventory/production.yml \
  maintenance.yml
```

when you intended:

```text
staging
```

Troubleshooting includes verifying operational context.

---

# 33. Host-Pattern Problems

Suppose:

```bash
ansible webservers \
  -i inventory/production.yml \
  -m ansible.builtin.ping
```

returns a warning that no hosts matched.

Possible causes:

```text
Group does not exist
Group name misspelled
Inventory did not load
Wrong inventory supplied
Dynamic inventory returned no matching hosts
Pattern syntax incorrect
```

---

# 34. Verify Host Patterns Before Changes

Use:

```bash
ansible \
  -i inventory/production.yml \
  web \
  --list-hosts
```

For a playbook:

```bash
ansible-playbook \
  -i inventory/production.yml \
  site.yml \
  --list-hosts
```

This performs no configuration change.

It answers:

```text
Which hosts are selected?
```

---

# 35. Complex Patterns

Example:

```bash
ansible \
  -i inventory/production.yml \
  'web:&production' \
  --list-hosts
```

Quote complex patterns so the shell does not interpret special characters unexpectedly.

---

# 36. DNS Failures

Common symptoms include messages similar to:

```text
Could not resolve hostname

Name or service not known

Temporary failure in name resolution
```

At this point, your troubleshooting layer is:

```text
Hostname
↓
DNS Resolution
```

You have not yet proven an SSH authentication problem.

---

# 37. Test DNS From the Control Node

On Linux systems you might use:

```bash
getent hosts web01.example.com
```

Where available:

```bash
dig web01.example.com
```

or:

```bash
nslookup web01.example.com
```

Expected result:

```text
Hostname resolves to an address.
```

The exact command depends on your control-node operating system.

---

# 38. DNS Investigation Questions

Ask:

```text
Is hostname correct?

Does the DNS record exist?

Is the control node using the expected DNS resolver?

Is VPN required?

Is this private DNS?

Is split-horizon DNS involved?

Did the server address recently change?

Is ansible_host correct?
```

---

# 39. Do Not Hide DNS Problems With Permanent Hardcoding

Changing:

```text
web01.example.com
```

to a random IP might make today's command work.

But you may hide:

```text
Broken DNS
Incorrect service discovery
Failover problems
Dynamic infrastructure behavior
```

Fix the correct layer.

---

# 40. Network Failures

If DNS works, continue downward.

Possible network problems include:

```text
Missing route
Firewall
Cloud security group
Network ACL
VPN disconnected
Private subnet
Bastion required
Host firewall
Wrong IP
Host offline
```

---

# 41. ICMP Ping Does Not Prove SSH Works

This may succeed:

```bash
ping web01.example.com
```

while SSH fails.

Or ICMP may be blocked while SSH works perfectly.

They are different protocols.

Test the protocol you actually need.

---

# 42. Port 22

SSH commonly listens on TCP port:

```text
22
```

But do not assume every environment uses port 22.

Inventory may contain:

```yaml
ansible_port: 2222
```

Always test the actual configured endpoint.

---

# 43. Testing the SSH Port

Where Netcat is installed:

```bash
nc -vz web01.example.com 22
```

Possible success resembles:

```text
Connection ... succeeded
```

The exact output varies by implementation.

---

# 44. Connection Timeout

A timeout can suggest:

```text
Routing failure
Firewall drop
Security-group rule
VPN problem
Host unavailable
Wrong address
```

It does not automatically mean:

```text
Wrong SSH key
```

---

# 45. Connection Refused

A refusal often means:

```text
Destination was reachable
+
Nothing accepted the connection on that port
```

Possible reasons:

```text
sshd stopped
Wrong port
Service not listening
Firewall actively rejecting
```

This is different evidence from a timeout.

---

# 46. Manual SSH Testing

Before blaming Ansible, reproduce the connection outside Ansible.

Example:

```bash
ssh \
  -i ~/.ssh/ansible_ed25519 \
  ansible@10.10.20.15
```

For a custom port:

```bash
ssh \
  -p 2222 \
  -i ~/.ssh/ansible_ed25519 \
  ansible@10.10.20.15
```

Use the same:

```text
Host
Port
User
Key
Jump host
```

that Ansible should use.

---

# 47. SSH Debugging

OpenSSH supports verbose diagnostics.

Use:

```bash
ssh -vvv \
  -i ~/.ssh/ansible_ed25519 \
  ansible@10.10.20.15
```

Look for:

```text
Which hostname was used?

Which port?

Which keys were attempted?

Was the key accepted?

Which authentication methods were offered?

Where did negotiation stop?
```

---

# 48. SSH-Key Failures

A common symptom is:

```text
Permission denied (publickey)
```

Possible causes:

```text
Wrong private key
Wrong remote user
Public key missing remotely
Wrong authorized_keys file
Key revoked
Local permissions unsafe
Remote SSH permissions wrong
SSH agent offered unexpected identity
Server policy rejects key
```

---

# 49. Local Private-Key Permissions

Inspect:

```bash
ls -l ~/.ssh/ansible_ed25519
```

A commonly appropriate restrictive permission is:

```bash
chmod 600 ~/.ssh/ansible_ed25519
```

Never troubleshoot private keys using:

```bash
chmod 777 ~/.ssh/ansible_ed25519
```

That weakens security and SSH may reject unsafe permissions.

---

# 50. Remote SSH Files

For the remote user, inspect:

```text
~/.ssh/
~/.ssh/authorized_keys
```

Check:

```text
Correct ownership
Correct key
Appropriate permissions
Correct user
```

Do not overwrite production `authorized_keys` simply because authentication failed.

Inspect first.

---

# 51. Wrong Remote User

Inventory might say:

```yaml
ansible_user: deploy
```

But perhaps the correct account is:

```text
ansible
```

The same SSH key may work for one account and fail for another.

Test:

```bash
ssh deploy@server
```

and verify the intended user.

---

# 52. User Failure Investigation

Ask:

```text
Does user exist?

Is account locked?

Does user have a valid shell?

Does sshd permit the user?

Is the correct public key installed?

Is the home directory correct?

Are .ssh permissions correct?
```

---

# 53. Cloud Default Users

Do not assume every Linux image uses:

```text
ubuntu
```

or:

```text
ec2-user
```

The default account depends on:

```text
Cloud provider
Image
Distribution
Image publisher
Organization customization
```

Verify the image documentation.

---

# 54. Host-Key Verification

SSH host keys answer:

```text
Am I connecting to the server I think I am connecting to?
```

A warning such as:

```text
REMOTE HOST IDENTIFICATION HAS CHANGED
```

must be investigated.

---

# 55. Legitimate Reasons a Host Key May Change

Examples:

```text
Server rebuilt
VM replaced
IP reused
Host keys intentionally rotated
Image recreated
```

But an unexpected change can also mean you are connecting to the wrong system.

---

# 56. Why Blindly Disabling Host-Key Checking Is Dangerous

Host-key verification protects server identity.

Blindly disabling it can make it easier to connect to:

```text
Wrong machine
Impersonated machine
Unexpected endpoint
```

Do not convert a security warning into a silent connection.

---

# 57. Safe Host-Key Investigation

Verify:

```text
Was the host rebuilt?

Was key rotation planned?

Was the IP reassigned?

Is DNS correct?

Can the new fingerprint be verified through a trusted source?
```

Only then update your trusted host-key data.

---

# 58. Manual SSH Works but Ansible Fails

This is excellent diagnostic information.

You have probably eliminated several possibilities.

Now investigate:

```text
ansible_host
ansible_user
ansible_port
ansible_ssh_private_key_file
ansible.cfg
SSH common arguments
ProxyCommand / jump host
Connection plugin
Python
become
```

---

# 59. Find the Active Ansible Configuration

Run:

```bash
ansible --version
```

This provides useful information including the active configuration-file location.

Also inspect configuration with:

```bash
ansible-config dump
```

Do not assume Ansible is using the `ansible.cfg` you are looking at.

---

# 60. Privilege Escalation

Successful SSH only proves:

```text
Ansible can connect as remote user.
```

It does not prove:

```text
Remote user can become root.
```

Flow:

```text
SSH as deploy
↓
become
↓
sudo
↓
root operation
```

---

# 61. `become`

Example:

```yaml
- name: Install Nginx
  ansible.builtin.package:
    name: nginx
    state: present
  become: true
```

If the task fails, determine whether:

```text
Package installation failed
```

or:

```text
Privilege escalation failed
```

Those are different investigations.

---

# 62. Common Sudo Failures

You might see messages involving:

```text
sudo password required

user is not allowed to run sudo

permission denied

incorrect password
```

This tells you the connection succeeded farther than a pure SSH failure.

---

# 63. Inspect Sudo Rights

After logging into the disposable/test server:

```bash
sudo -l
```

This can help show the commands the account is permitted to run.

Where appropriate:

```bash
sudo -n true
```

can test whether non-interactive passwordless sudo succeeds.

---

# 64. Become Password

If your environment legitimately uses a sudo password:

```bash
ansible-playbook \
  -i inventory/lab.yml \
  site.yml \
  --ask-become-pass
```

Short option:

```bash
-K
```

This concerns privilege escalation.

It is different from the SSH connection password.

---

# 65. `become_user`

Example:

```yaml
become: true
become_user: appuser
```

Do not assume every `become` operation means:

```text
root
```

Troubleshoot both:

```text
Remote connection user
```

and:

```text
Privilege-escalation target user
```

---

# 66. Do Not "Fix" Sudo by Giving Unlimited Root

A poor troubleshooting response is:

```text
Give automation account unrestricted passwordless root forever.
```

Ask instead:

```text
Which operation needs privilege?

Why?

Which user should perform it?

Can privilege be scoped?

Is this expected by the security design?
```

Troubleshooting should not weaken your security architecture.

---

# 67. Python Failures

Many Ansible modules executed on POSIX managed hosts require a suitable Python interpreter.

Therefore:

```text
SSH works
```

does not guarantee:

```text
Ansible modules work.
```

---

# 68. Interpreter Discovery

Ansible normally attempts to discover a suitable Python interpreter when required.

Possible interpreter paths include paths such as:

```text
/usr/bin/python3
```

but you must not assume a universal path.

---

# 69. Check Python Manually

Connect to the managed host:

```bash
command -v python3
```

Then:

```bash
python3 --version
```

If inventory explicitly specifies:

```yaml
ansible_python_interpreter: /usr/bin/python3
```

verify that exact interpreter exists.

---

# 70. Wrong Explicit Interpreter

Suppose inventory contains:

```yaml
ansible_python_interpreter: /usr/local/bin/python3
```

but:

```bash
command -v python3
```

returns:

```text
/usr/bin/python3
```

Your explicit override may be the problem.

---

# 71. When Explicit Interpreter Selection Helps

It can be useful when:

```text
Multiple Python versions exist
Discovery chooses an unsuitable interpreter
A deterministic interpreter is required
A specialized environment is required
```

But hardcoding a nonexistent or stale path creates failures.

---

# 72. Minimal Hosts

Some minimal Linux images may not initially provide the Python environment expected by ordinary Ansible modules.

In those environments, Python may need to be bootstrapped before normal module execution.

The important lesson is:

```text
SSH connectivity
≠
Python module readiness
```

---

# 73. Missing Modules

You may encounter messages indicating Ansible cannot resolve a module/action.

Investigate:

```text
Spelling
FQCN
Installed collection
Collection path
Ansible version
Collection version
Execution environment
```

---

# 74. Check Module Documentation

Use:

```bash
ansible-doc ansible.builtin.package
```

For another collection:

```bash
ansible-doc namespace.collection.module_name
```

If Ansible cannot find it, investigate dependency installation.

---

# 75. Collections

List installed collections:

```bash
ansible-galaxy collection list
```

Compare this environment against your project's:

```text
requirements.yml
```

---

# 76. Collection Failures

Typical causes include:

```text
Collection missing
Wrong collection version
FQCN wrong
Collection incompatible
Collection installed in another environment
Collection unavailable inside CI execution environment
```

---

# 77. Dependency Failures

A common production problem looks like:

```text
Works on engineer laptop
Fails in CI
```

Why?

Because:

```text
Laptop dependency set
≠
CI dependency set
```

Compare:

```text
Python version
ansible-core version
Ansible package version
Collections
Roles
Configuration
Environment variables
Execution environment
```

---

# 78. Reproducible Dependency Installation

If your repository uses:

```text
requirements.yml
```

install from that controlled definition:

```bash
ansible-galaxy collection install \
  -r requirements.yml
```

Do not randomly install unrelated latest versions during an incident unless that is the intentional fix.

---

# 79. YAML Errors

Common YAML mistakes include:

```text
Incorrect indentation
Tabs
Missing colon
Broken quotes
Malformed list
Malformed mapping
```

Example:

```yaml
- name Install Nginx
```

is missing the colon after:

```text
name
```

# 100. Loop Example

Data:

```yaml
users:
  - name: alice
    shell: /bin/bash
  - name: bob
    shell: /bin/zsh
```

Task:

```yaml
- name: Create users
  ansible.builtin.user:
    name: "{{ item.username }}"
    shell: "{{ item.shell }}"
```

```yaml
- name: Create users

    name: "{{ item.name }}"
```


# 126. Retry Does Not Mean "Run Again and Hope"

# 127. Why Idempotency Makes Recovery Safer

Ideal state:

```text
Tasks 1-11 already correct
↓
Root cause of task 12 fixed
↓
Playbook rerun
↓
Tasks 1-11 → ok
↓
Task 12 → succeeds
↓
Remaining tasks execute
```

That is one of the greatest operational benefits of idempotent automation.

---

# 128. Non-Idempotent Retry Danger

Consider:

```yaml
- name: Create customer
  ansible.builtin.command:
    cmd: /opt/application/create-customer
```

If the command creates a new customer every time:

```text
First execution → customer created
Later task fails
Rerun → duplicate customer
```

A rerun is not automatically safe.

---

# 129. Retry Strategies

Choose based on failure type.

```text
Transient failure
→ retries/until/delay

One-host failure
→ --limit

Known failed task
→ possibly --start-at-task

Subset of functionality
→ tags, if dependencies are understood

Safe idempotent playbook
→ full rerun may be safest
```

# 130. `--limit`

Suppose only:

```text
web03
```

failed.

You can restrict execution:

```bash
ansible-playbook \
  -i inventory/production.yml \
  site.yml \
  --limit web03
```

---

# 131. Verify `--limit`

Before mutation:

```bash
ansible-playbook \
  -i inventory/production.yml \
  site.yml \
  --limit web03 \
  --list-hosts
```

Expected:

```text
Only intended recovery hosts are listed.
```

---

# 132. Multiple Hosts

Example:

```bash
ansible-playbook \
  -i inventory/production.yml \
  site.yml \
  --limit 'web03:web07'
```

Always verify the pattern before executing production changes.

---

# 133. `--start-at-task`

Suppose a named task failed:

```text
Install application package
```

You can run:

```bash
ansible-playbook \
  -i inventory/production.yml \
  site.yml \
  --start-at-task="Install application package"
```

This begins execution at the matching task.

---

# 134. `--start-at-task` Is Not State Reconstruction

Suppose earlier tasks:

```text
Created user
Created directory
Installed repository
Created secret
```

If those prerequisites are missing or incorrect, starting later may fail.

`--start-at-task` means:

```text
Start execution here.
```

It does not mean:

```text
Guarantee all previous prerequisites are correct.
```

---

# 135. Dynamic Inclusion Limitation

Tasks inside dynamically included content using constructs such as:

```text
include_tasks
include_role
```

cannot generally be jumped into directly using `--start-at-task`.

This connects directly to the static versus dynamic reuse concepts from Part 11.

---

# 136. Tags

Suppose:

```yaml
- name: Deploy configuration
  ansible.builtin.template:
    src: application.conf.j2
    dest: /etc/application/application.conf
  tags:
    - configuration
```

You can run:

```bash
ansible-playbook \
  -i inventory/production.yml \
  site.yml \
  --tags configuration
```

---

# 137. Tag Recovery Risk

Imagine:

```text
Install package
↓
Create directory
↓
Deploy configuration
```

If you execute only:

```text
configuration
```

but package/directory prerequisites do not exist, the task may fail.

Tags select execution.

They do not automatically resolve dependencies.

---

# 138. Skip Tags

Example:

```bash
ansible-playbook \
  -i inventory/production.yml \
  site.yml \
  --skip-tags expensive_test
```

Do not skip a failing validation merely to obtain:

```text
failed=0
```

A green recap is not the goal.

Correct production state is the goal.

# 139. Retry With `until`

Some failures are legitimately transient.

Example:

```yaml
- name: Wait for application health
  ansible.builtin.uri:
    url: http://127.0.0.1:8080/health
    status_code: 200
  register: application_health
  until: application_health.status == 200
  retries: 10
  delay: 3
```

This makes sense if the application requires time to start.

---

# 140. When Retry Makes Sense

Examples:

```text
Service startup delay
Eventually consistent API
Temporary endpoint availability
Port waiting
Transient external dependency
```

---

# 141. When Retry Does Not Make Sense

Do not retry:

```text
Invalid password
Wrong package name
Malformed YAML
Invalid configuration
Undefined variable
Wrong SSH key
```

100 retries do not repair a deterministic configuration error.

# 142. Safe Recovery

A production recovery should answer:

```text
What failed?

What already changed?

Which hosts changed?

What is the root cause?

Is rerun idempotent?

Are there external side effects?

Are handlers pending?

Should recovery target one host?

Should we rerun everything?

How will success be verified?
```

Example:


It also does not make every class of error disappear.

Do not use it simply because you want the playbook to appear successful.

# 152. Root-Cause Analysis

This is not a root cause:

```text
Ansible failed.
```

Neither is:

```text
Nginx broke.
```

A useful root cause is specific.

Example:

```text
The Nginx role rendered an invalid listen directive because the production web_port variable contained a string that included the protocol prefix.
```

Now you know:

```text
What failed
Why
Where
What needs correction
```

---

# 153. Symptom vs Root Cause

Symptom:

```text
Nginx will not start.
```

Root cause:

```text
The generated Nginx configuration contains an invalid directive.
```

Deeper root cause:

```text
The role accepted an unvalidated input value and CI had no configuration-validation test.
```

---

# 154. Trigger vs Root Cause

Trigger:

```text
Deployment ran at 10:00.
```

Root cause:

```text
Production variable generated invalid configuration.
```

The deployment exposed the defect.

Do not automatically confuse:

```text
last event
```

with:

```text
root cause
```

---

# 155. Root Cause vs Contributing Factors

Example:

```text
Root Cause:
Incorrect production repository URL.
```

Contributing factors:

```text
No pre-deployment repository validation
No staging parity
Poor error reporting
No automated integration test
```

Both matter.

But they are not the same thing.

---

# 156. The Five Whys

Example:

```text
Why did deployment fail?
Nginx would not restart.

Why?
Configuration was invalid.

Why?
upstream_port was empty.

Why?
Production inventory did not define it.

Why?
Role interface documentation did not mark it as required and no assertion checked it.
```

Now you have an actionable engineering problem.

---

# 157. Corrective Action

Example:

```text
Define upstream_port correctly.
```

That repairs the immediate issue.

---

# 158. Preventive Action

Example:

```text
Add role argument validation/assertion.

Validate generated Nginx configuration.

Test production inventory in CI.

Document required role inputs.
```

This reduces recurrence.

Strong troubleshooting improves the automation system.

| ---------------------------- | ------------------- | ----------------------------------- |

| UNREACHABLE                  | Network/SSH         | DNS, port, SSH, `-vvvv`             |

| Sudo denied                  | Privilege           | become settings, `sudo -l`          |

| Template fails               | Jinja/data          | Inputs/template                     |

| Service fails                | Remote service      | status/logs/config validator        |

# 213. Common Beginner Mistakes

Avoid:

```text
Rerunning before reading the error

Changing multiple things simultaneously

Treating FAILED and UNREACHABLE as identical

Editing YAML when DNS is broken

Changing SSH keys when package repository is broken

Disabling host-key verification blindly

Using chmod 777

Giving unrestricted sudo

Installing random latest collections

Ignoring skipped tasks

Using ignore_errors to hide failures

Using failed_when: false to hide real errors

Using defaults to hide required missing variables

Deleting package locks blindly

Disabling SELinux/AppArmor blindly

Restarting services repeatedly without reading logs

Assuming Ansible rolled back previous changes

Assuming failed=0 means application healthy

Ignoring partial fleet state

Skipping post-recovery verification
```

---

# 214. Production Troubleshooting Principles

Use these rules:

```text
Observe before changing.

Preserve evidence.

Classify the failure layer.

Verify assumptions.

Use read-only inspection first.

Make one controlled change at a time.

Do not weaken security to make errors disappear.

Understand partial state.

Prefer idempotent recovery.

Reduce blast radius where appropriate.

Read the remote system's own logs.

Verify the application, not just Ansible.

Document the root cause.

Improve automation after the incident.
```

# 221. Final Mental Model

Never reduce Ansible troubleshooting to:

```text
FAILED
↓
Google error
↓
Try random command
```

Use:

```text
Symptom
↓
Inventory
↓
Target Pattern
↓
Network
↓
SSH
↓
Authentication
↓
Privilege Escalation
↓
Python
↓
Variables
↓
Task
↓
Module
↓
Remote System
↓
Service / Application
↓
Logs
↓
Root Cause
↓
Fix
↓
Run Again
↓
Verify
```

A beginner sees:

```text
fatal: [web03]: FAILED!
```

and thinks:

```text
Ansible is broken.
```

A capable engineer asks:

```text
Which layer failed?
```

A production engineer asks:

```text
Which layer failed?

What evidence proves it?

What changed before the failure?

Which hosts are affected?

What state are they in now?

What is the smallest safe fix?

Can the automation be rerun safely?

How will I prove recovery?

How do we prevent this from happening again?
```

That is the level of troubleshooting you are building toward.
