# Part 9: Files, Templates, and Jinja2

## Learn How Ansible Generates and Manages Real Configuration Files

In Part 8, you learned how Ansible makes decisions:

```text
Variables
+
Facts
+
Registered Results
↓
Conditions
↓
Loops
↓
Tasks
↓
Handlers
```

Now we are going to use those capabilities to solve one of the most important problems in infrastructure automation:

```text
How do we reliably create and manage configuration files?
```

Almost every production system depends on files.

Examples include:

```text
/etc/nginx/nginx.conf

/etc/ssh/sshd_config

/etc/systemd/system/myapp.service

/etc/prometheus/prometheus.yml

/etc/docker/daemon.json

/etc/myapp/application.conf

/opt/myapp/config.yml

/var/www/html/index.html
```

A DevOps engineer constantly deals with:

```text
Directories

Configuration files

Permissions

Ownership

Templates

Service configuration

Environment-specific settings

Secrets

Certificates

Application files

Symbolic links
```

Manually editing these files does not scale.

We want:

```text
Desired Configuration
↓
Defined in Git
↓
Rendered by Ansible
↓
Validated
↓
Deployed
↓
Service Reloaded/Restarted If Required
↓
Verified
```

That is the purpose of Part 9.

# 2. What Is File Management?

File management means ensuring filesystem objects have the desired state.

That can include:

```text
File exists

Directory exists

File contains correct content

Correct owner

Correct group

Correct permissions

Symbolic link points to correct target

Obsolete file is absent

Configuration is rendered correctly

Configuration is valid

Service uses the new configuration
```

Ansible provides several modules for different file-management jobs.

The most important in this chapter are:

```text
ansible.builtin.copy

ansible.builtin.file

ansible.builtin.lineinfile

ansible.builtin.blockinfile

ansible.builtin.template
```

Do not treat them as interchangeable.

Each solves a different problem.

---

# 3. File Management Decision Model

A useful first mental model is:

```text
What am I trying to manage?
│
├── Entire static file
│   └── copy
│
├── File/directory/link properties
│   └── file
│
├── One specific line
│   └── lineinfile
│
├── One managed block inside existing file
│   └── blockinfile
│
└── Entire dynamic file
    └── template
```

This distinction prevents many bad Ansible designs.

---

# 4. `copy`

The `copy` module transfers file content to managed nodes.

Typical use cases:

```text
Static configuration files

Scripts

Certificates where appropriate

HTML files

Application files

Small static assets

Files whose contents do not need Jinja2 rendering
```

Basic example:

```yaml
- name: Copy application configuration
  ansible.builtin.copy:
    src: files/app.conf
    dest: /etc/veriqta/app.conf
```

Mental model:

```text
Control Node
│
│ files/app.conf
│
↓
Ansible
↓
Managed Node
│
└── /etc/veriqta/app.conf
```

---

# 5. Source and Destination

The two fundamental parameters are:

```text
src
dest
```

Example:

```yaml
ansible.builtin.copy:
  src: files/banner.txt
  dest: /etc/veriqta/banner.txt
```

Here:

```text
src
↓
Source file
```

and:

```text
dest
↓
Destination on managed node
```

# 7. First Static File

Create:

```text
files/banner.txt
```

Contents:

```text
Managed by Ansible.
Manual changes may be overwritten.
```

Playbook task:

```yaml
- name: Deploy managed banner
  ansible.builtin.copy:
    src: files/banner.txt
    dest: /etc/veriqta/banner.txt
    owner: root
    group: root
    mode: "0644"
```

```bash
cat /etc/veriqta/banner.txt
```

```bash
ls -l /etc/veriqta/banner.txt
```

```text

Owner

Group

```

```text

```

# 9. Inline Content With `copy`

`copy` can also create a file directly from inline content.

Example:

```yaml
- name: Create health file
  ansible.builtin.copy:
    content: |
      healthy
    dest: /var/www/html/health.txt
    owner: root
    group: root
    mode: "0644"
```

This is useful for small files.

---

# 10. When Inline Content Becomes a Bad Idea

This is reasonable:

```yaml
content: |
  healthy
```

This becomes difficult:

```yaml
content: |
  hundreds
  of
  configuration
  lines
  embedded
  inside
  the
  playbook
```

Large dynamic configurations usually belong in:

```text
templates/
```

Large static files usually belong in:

```text
files/
```

Keep playbooks readable.

---

# 11. `copy` Is Idempotent

Suppose the destination already contains exactly the required content.

Ansible can determine that no update is required.

Conceptually:

```text
Desired File
↓
Compare With Existing State
↓
Same?
├── YES → OK
└── NO  → CHANGED
```

This is important for handlers.

# 12. File Ownership

Linux files have ownership information.

Typically:

```text
User Owner

Group Owner
```

Example:

```text
root:root
```

or:

```text
veriqta:veriqta
```

Ansible can enforce these properties.

Example:

```yaml
owner: veriqta
group: veriqta
```

---

# 13. Why Ownership Matters

Incorrect ownership can cause:

```text
Application cannot read configuration

Application cannot write data

Unauthorized user can modify configuration

Deployment fails

Service fails to start

Security exposure
```

Ownership is part of configuration management.

# 18. File Permissions

Linux permissions answer questions such as:

```text
Can the owner read this?

Can the owner write this?

Can the owner execute this?

Can members of the group read this?

Can other users read this?
```

The three fundamental permissions are:

```text
r = read

w = write

x = execute
```

---

# 19. Permission Classes

Permissions apply to:

```text
u = user/owner

g = group

o = others
```

You may also encounter:

```text
a = all
```

---

# 20. Numeric Permission Values

Numeric permissions use:

```text
read    = 4
write   = 2
execute = 1
```

Combine them:

```text
7 = read + write + execute

6 = read + write

5 = read + execute

4 = read
```

---

# 21. Understanding `0755`

```text
0755
```

means:

```text
Owner
7
rwx

Group
5
r-x

Others
5
r-x
```

Common for directories and executable files when appropriate.

---

# 22. Understanding `0644`

```text
0644
```

means:

```text
Owner
6
rw-

Group
4
r--

Others
4
r--
```

Common for non-sensitive configuration or content files when world-readable access is acceptable.

---

# 23. Understanding `0600`

```text
0600
```

means:

```text
Owner
6
rw-

Group
0
---

Others
0
---
```

This is often appropriate for sensitive files that only the owner should access.

---

# 24. Quote Numeric Modes

Prefer:

```yaml
mode: "0644"
```

instead of relying on YAML numeric interpretation.

Similarly:

```yaml
mode: "0755"
```

and:

```yaml
mode: "0600"
```

Treat filesystem modes deliberately.

---

# 25. Why Quoting Modes Matters

Permission modes represent filesystem permission notation.

They should not accidentally become ordinary decimal integers during YAML parsing or data manipulation.

A strong convention is:

```text
Always quote numeric permission modes.
```

Example:

```yaml
mode: "0640"
```

---

# 26. Symbolic Modes

Ansible also supports symbolic permission notation.

Example:

```yaml
mode: "u=rw,g=r,o="
```

Meaning:

```text
Owner
↓
read + write

Group
↓
read

Others
↓
no permissions
```

Another example:

```yaml
mode: "u+rwx,g+rx,o+rx"
```

---

# 27. Numeric vs Symbolic Modes

Numeric:

```yaml
mode: "0644"
```

is compact and common.

Symbolic:

```yaml
mode: "u=rw,g=r,o=r"
```

can be easier to understand when teaching or expressing a specific permission relationship.

Choose deliberately.

---

# 28. Never Guess Permissions

Do not automatically assign:

```text
0777
```

because a permission problem exists.

That often means:

```text
Everyone can read

Everyone can write

Everyone can execute
```

depending on the object and system context.

Solve the ownership or access requirement properly.

---

# 29. Permissions Are Security Controls

A configuration file may contain:

```text
Database credentials

API tokens

Private keys

Service credentials

Connection strings

Internal endpoints
```

Using:

```yaml
mode: "0644"
```

for every configuration file is not safe.

Determine who actually needs access.

---

# 30. Managing Existing File Properties

The `file` module can manage properties of an existing file.

Example:

```yaml
- name: Secure application configuration
  ansible.builtin.file:
    path: /etc/veriqta/app.conf
    owner: root
    group: veriqta
    mode: "0640"
```

This manages metadata without necessarily replacing the file contents.

---

# 31. `state: touch`

You may encounter:

```yaml
state: touch
```

which can ensure a file exists and update its timestamps according to module behavior.

Do not use `touch` merely because you want:

```text
an empty file that remains unchanged
```

without understanding timestamp implications.

Choose state according to the desired filesystem behavior.

---

# 32. Symbolic Links

A symbolic link points to another filesystem path.

Conceptually:

```text
/etc/veriqta/current.conf
↓
/opt/veriqta/releases/v2/app.conf
```

Create one:

```yaml
- name: Create current configuration link
  ansible.builtin.file:
    src: /opt/veriqta/releases/v2/app.conf
    dest: /etc/veriqta/current.conf
    state: link
```

---

# 33. Link Mental Model

```text
Destination Link
/etc/veriqta/current.conf
        │
        ↓
Target
/opt/veriqta/releases/v2/app.conf
```

Here:

```text
src
```

is the target the link should point to.

```text
dest
```

is the symbolic-link path being managed.

---

# 34. Why Links Are Useful

Symbolic links are common for:

```text
Release switching

Current-version pointers

Shared configuration

Enabled/available configuration patterns

Application deployments
```

But links add another layer of indirection.

Always verify both:

```text
Link exists

Target exists
```

---

# 35. Verify Symbolic Links

Use:

```bash
ls -l /etc/veriqta/current.conf
```

and:

```bash
readlink /etc/veriqta/current.conf
```

If appropriate:

```bash
readlink -f /etc/veriqta/current.conf
```

Understand the difference between the link path and its target.

---

# 36. File Removal

To remove a file:

```yaml
- name: Remove obsolete configuration
  ansible.builtin.file:
    path: /etc/veriqta/old.conf
    state: absent
```

Mental model:

```text
Desired State
↓
Absent

File Exists?
├── YES → Remove → CHANGED
└── NO  → Already Desired → OK
```

---

# 37. Directory Removal Is Powerful

This:

```yaml
- name: Remove obsolete directory
  ansible.builtin.file:
    path: /opt/veriqta/old-release
    state: absent
```

can remove a directory and its contents.

Treat destructive states carefully.

Before production deletion verify:

```text
Exact path

Environment

Target hosts

Data retention requirements

Backup requirements

Rollback requirements
```

---

# 38. Destructive Automation Rule

Before using:

```yaml
state: absent
```

ask:

```text
What exactly will disappear?

Can the operation be reversed?

Is data inside the path valuable?

Could a variable resolve to the wrong path?

Is this the correct environment?

Do I have a verified backup?
```

Deletion deserves stronger review than creation.

---

# 39. What Is `lineinfile`?

`ansible.builtin.lineinfile` manages a particular line inside a text file.

It is useful when:

```text
You need one line

You need to replace one line

You need to ensure one setting exists

You do not own the entire file
```

Example:

```yaml
- name: Configure application environment
  ansible.builtin.lineinfile:
    path: /etc/veriqta/app.conf
    regexp: '^ENVIRONMENT='
    line: 'ENVIRONMENT=production'
```

---

# 40. `lineinfile` Mental Model

```text
Existing File
↓
Search for Matching Line
↓
Found?
├── YES → Ensure Correct Value
└── NO  → Insert Desired Line
```

The exact behavior depends on the parameters you configure.

---

# 41. Appropriate `lineinfile` Use Case

Suppose a vendor owns a large configuration file.

You only need:

```text
ENABLE_METRICS=true
```

Replacing the entire file may be inappropriate.

A targeted line can make sense.

Example:

```yaml
- name: Enable application metrics
  ansible.builtin.lineinfile:
    path: /etc/vendor/app.conf
    regexp: '^ENABLE_METRICS='
    line: 'ENABLE_METRICS=true'
```

---

# 42. Removing a Line

Example:

```yaml
- name: Remove deprecated option
  ansible.builtin.lineinfile:
    path: /etc/veriqta/app.conf
    regexp: '^LEGACY_MODE='
    state: absent
```

This ensures matching content is absent according to the module's behavior.

---

# 43. Why Regular Expressions Matter

A task such as:

```yaml
regexp: '^PORT='
```

means:

```text
Find a line beginning with PORT=
```

Then:

```yaml
line: 'PORT=8080'
```

defines the desired line.

Regular expressions are powerful.

They are also easy to misuse.

Test them carefully.

---

# 44. Fragile Regular Expression Example

Suppose a file contains:

```text
APP_PORT=8080
ADMIN_PORT=9090
PORT=80
```

A poorly designed expression such as:

```text
PORT
```

may match more than you intended.

A stronger expression might be:

```text
^PORT=
```

depending on the actual file format.

Never use regex patterns without understanding what they match.

---

# 45. What Is `blockinfile`?

`ansible.builtin.blockinfile` manages a block of text inside another file.

Example:

```yaml
- name: Add managed application block
  ansible.builtin.blockinfile:
    path: /etc/veriqta/app.conf
    block: |
      METRICS_ENABLED=true
      METRICS_PORT=9090
```

Ansible surrounds the managed block with marker lines by default.

---

# 46. Block Mental Model

```text
Existing File
│
├── Existing unmanaged content
│
├── BEGIN ANSIBLE MANAGED BLOCK
│   ├── Managed line
│   └── Managed line
│
├── END ANSIBLE MANAGED BLOCK
│
└── Existing unmanaged content
```

This allows Ansible to identify its managed section later.

---

# 47. Appropriate `blockinfile` Use Cases

Useful when:

```text
Ansible owns one section of a larger file

A configuration accepts a multi-line block

You must preserve surrounding content

Replacing the entire file is inappropriate
```

Examples might include:

```text
A managed hosts-file section

A specific service configuration block

A controlled multi-line application section
```

Use it only when the target file format makes this safe.

---

# 48. Custom Block Markers

You can define clearer markers.

Example:

```yaml
- name: Manage VERIQTA configuration block
  ansible.builtin.blockinfile:
    path: /etc/veriqta/app.conf
    marker: "# {mark} VERIQTA MANAGED BLOCK"
    block: |
      METRICS_ENABLED=true
      METRICS_PORT=9090
```

This helps humans understand ownership.

---

# 49. Why Line-by-Line Editing Can Become Fragile

Imagine managing a configuration file using:

```text
25 lineinfile tasks

8 blockinfile tasks

Several regular expressions

Conditional insertions

Environment-specific replacements
```

Now ask:

```text
What should the complete final file look like?
```

That answer may be difficult.

The configuration has become the accumulated result of many mutations.

---

# 50. Mutation vs Desired Document

Line editing follows:

```text
Existing File
+
Mutation 1
+
Mutation 2
+
Mutation 3
↓
Final File
```

Templating follows:

```text
Desired Configuration Model
+
Variables
↓
Complete Desired File
```

When you own the entire configuration file, the second model is often easier to reason about.

---

# 51. Why Excessive `lineinfile` Becomes Fragile

Problems can include:

```text
Vendor file format changes

Regex no longer matches

Duplicate settings

Unexpected comments

Different initial file versions

Incorrect insertion positions

Conflicting tasks

Ordering problems

Hard-to-understand final state
```

The issue is not that `lineinfile` is bad.

The issue is using it for problems better solved by full-file management.

---

# 52. File-Management Decision Rule

Ask:

```text
Do I own the entire file?
```

If yes:

```text
Static?
↓
copy

Dynamic?
↓
template
```

If no:

```text
One controlled line?
↓
lineinfile

One controlled block?
↓
blockinfile
```

This is not an absolute law, but it is a strong design starting point.

---

# 53. What Is a Template?

A template is a source file containing:

```text
Static text
+
Dynamic expressions
+
Optional logic
```

Ansible processes the template and produces the final file.

Example source:

```text
templates/app.conf.j2
```

```jinja2
environment={{ app_environment }}
port={{ app_port }}
workers={{ worker_count }}
```

Variables:

```yaml
app_environment: production
app_port: 8080
worker_count: 4
```

Rendered result:

```text
environment=production
port=8080
workers=4
```

---

# 54. Template Architecture

```text
Template
+
Variables
+
Facts
        │
        ↓
Jinja2 Rendering
        │
        ↓
Complete Text File
        │
        ↓
Managed Node
```

Ansible performs Jinja2 templating on the control node.

The managed host receives the rendered result.

---

# 55. What Is Jinja2?

Jinja2 is a templating language.

It allows you to combine:

```text
Text

Variables

Expressions

Conditionals

Loops

Filters

Comments
```

to generate output.

Ansible integrates Jinja2 into its templating system.

---

# 56. `.j2`

A common convention is to give Jinja2 template files the extension:

```text
.j2
```

Examples:

```text
nginx.conf.j2

app.conf.j2

prometheus.yml.j2

index.html.j2

systemd.service.j2
```

The `.j2` extension is a convention that tells humans:

```text
This file is a template.
```

The deployed destination normally does not keep `.j2`.

Example:

```text
templates/app.conf.j2
↓
/etc/veriqta/app.conf
```

---

Create:

```text
templates/app.conf.j2
```

Contents:

```jinja2
# Managed by Ansible

port={{ app_port }}
workers={{ worker_count }}
```

Define variables:

```yaml
app_environment: development

```

Task:

```yaml
- name: Deploy application configuration

    src: templates/app.conf.j2
    dest: /etc/veriqta/app.conf
    owner: root
    group: root
    mode: "0644"
```

Mental model:

```text
app.conf.j2
+
Variables
↓
Jinja2
↓
Rendered app.conf
↓
/etc/veriqta/app.conf
```

---

# 59. Verify Rendered Output

Run:

```bash
cat /etc/veriqta/app.conf
```

Expected conceptually:

```text
# Managed by Ansible

environment=development

workers=2
```

Do not verify the template source only.

Verify the rendered destination.

---

# 60. Variables in Templates

Basic syntax:

```jinja2
{{ variable_name }}
```

Example:

```jinja2
server_name={{ server_name }}
```

If:

```yaml
server_name: web01.example.com
```

the rendered output becomes:

```text
server_name=web01.example.com
```

---

# 61. Facts in Templates

Facts can also be referenced.

Example:

```jinja2
hostname={{ ansible_facts['hostname'] }}
```

Another example:

```jinja2
os_family={{ ansible_facts['os_family'] }}
```

This lets one template adapt to each managed host.

---

# 62. Host-Specific Rendering

Suppose inventory contains:

```text
web01
web02
web03
```

The same template can render differently for every host because each host has different:

```text
Facts

Host variables

Group variables

Inventory data
```

Conceptually:

```text
One Template
       │
       ├── web01 data → web01 configuration
       ├── web02 data → web02 configuration
       └── web03 data → web03 configuration
```

That is a major reason templating is powerful.

---

# 63. Jinja2 Expressions

Inside:

```text
{{ }}
```

you can use expressions.

Example:

```jinja2
worker_limit={{ worker_count * 2 }}
```

If:

```yaml
worker_count: 4
```

the result becomes:

```text
worker_limit=8
```

Keep expressions understandable.

Complex business logic usually does not belong inside configuration templates.

---

# 64. String Expressions

Example:

```jinja2
service_url=http://{{ app_host }}:{{ app_port }}
```

Variables:

```yaml
app_host: app.internal
app_port: 8080
```

Result:

```text
service_url=http://app.internal:8080
```

---

# 65. Nested Variables

Suppose:

```yaml
application:
  port: 8080
  workers: 4
```

Template:

```jinja2
port={{ application.port }}
workers={{ application.workers }}
```

You can also use bracket notation where appropriate.

For example:

```jinja2
port={{ application['port'] }}
```

---

# 66. Prefer Clear Data Structures

Instead of:

```yaml
app_prod_primary_backend_port: 8080
```

you may prefer:

```yaml
application:
  environment: production
  backend:
    host: app01.internal
    port: 8080
```

Then:

```jinja2
environment={{ application.environment }}
backend={{ application.backend.host }}:{{ application.backend.port }}
```

Structured variables can make templates easier to understand.

Do not over-nest data unnecessarily.

---

# 67. Jinja2 Conditionals

Templates can contain conditional logic.

Syntax:

```jinja2
{% if condition %}
content
{% endif %}
```

Example:

```jinja2
{% if monitoring_enabled %}
metrics_enabled=true
metrics_port=9090
{% endif %}
```

If:

```yaml
monitoring_enabled: true
```

the lines are rendered.

If false, they are omitted.

---

# 68. `if` / `else`

Example:

```jinja2
{% if app_environment == 'production' %}
log_level=warning
{% else %}
log_level=debug
{% endif %}
```

This allows environment-specific rendering.

---

# 69. `elif`

Example:

```jinja2
{% if app_environment == 'production' %}
log_level=warning
{% elif app_environment == 'staging' %}
log_level=info
{% else %}
log_level=debug
{% endif %}
```

Conceptually:

```text
Production?
├── YES → warning
└── NO
     ↓
Staging?
├── YES → info
└── NO  → debug
```

---

# 70. Do Not Build Huge Decision Trees in Templates

This is possible:

```text
if
  if
    if
      loop
        if
          filter
```

But that does not make it good engineering.

Templates should primarily describe:

```text
What should this configuration file look like?
```

If the template becomes difficult to understand, reconsider the variable structure or automation design.

---

# 71. Jinja2 Loops

Suppose:

```yaml
backend_servers:
  - app01.internal
  - app02.internal
  - app03.internal
```

Template:

```jinja2
{% for server in backend_servers %}
server={{ server }}
{% endfor %}
```

Rendered output:

```text
server=app01.internal
server=app02.internal
server=app03.internal
```

---

# 72. Loop Mental Model

```text
backend_servers
│
├── app01.internal
├── app02.internal
└── app03.internal
        │
        ↓
Jinja2 Loop
        │
        ↓
One Configuration Entry Per Server
```

---

# 73. Looping Over Structured Data

Variables:

```yaml
backend_servers:
  - name: app01
    address: 10.0.2.11
    port: 8080

  - name: app02
    address: 10.0.2.12
    port: 8080
```

Template:

```jinja2
{% for backend in backend_servers %}
server {{ backend.name }} {{ backend.address }}:{{ backend.port }}
{% endfor %}
```

Rendered:

```text
server app01 10.0.2.11:8080
server app02 10.0.2.12:8080
```

---

# 74. Ansible Loop vs Jinja2 Loop

Do not confuse these.

Ansible task loop:

```yaml
loop: "{{ backend_servers }}"
```

means:

```text
Execute task repeatedly.
```

Jinja2 loop:

```jinja2
{% for backend in backend_servers %}
...
{% endfor %}
```

means:

```text
Render text repeatedly inside one template.
```

Different jobs.

---

# 75. Choosing Between Them

Suppose you need:

```text
Three directories
```

Use an Ansible task loop.

Suppose you need:

```text
Three backend entries inside one nginx configuration
```

Use a Jinja2 loop.

Mental model:

```text
Repeat Infrastructure Operation
↓
Ansible loop
```

```text
Repeat Rendered Text
↓
Jinja2 loop
```

# 76. Jinja2 Filters

Filters transform values.

Syntax:

```jinja2
{{ value | filter }}
```

Example:

```jinja2
{{ app_name | upper }}
```

If:

```yaml
app_name: veriqta
```

the output becomes conceptually:

```text
VERIQTA
```

---

# 77. Filter Pipeline

Think:

```text
Original Value
↓
Filter
↓
Transformed Value
```

Example:

```jinja2
{{ app_name | lower }}
```

Filters are data transformations.

---

# 78. Common Filter Concepts

You may encounter filters for:

```text
Default values

String transformation

List processing

Dictionary transformation

JSON formatting

YAML formatting

Joining values

Selecting values

Mapping attributes
```

Do not try to memorize every filter.

Learn how to find and understand the one you need.

---

# 79. `default`

A very useful filter is:

```text
default
```

Example:

```jinja2
log_level={{ log_level | default('info') }}
```

If:

```text
log_level
```

is undefined, the rendered value becomes:

```text
info
```

---

# 80. Do Not Use Defaults to Hide Required Configuration

This can be dangerous:

```jinja2
database_password={{ database_password | default('password') }}
```

If the variable is required, silently substituting a weak fallback is bad engineering.

Ask:

```text
Is this value genuinely optional?
```

If no:

```text
Fail visibly when it is missing.
```

---

# 81. Joining Lists

Suppose:

```yaml
allowed_methods:
  - GET
  - POST
  - PUT
```

Template:

```jinja2
allowed_methods={{ allowed_methods | join(',') }}
```

Result:

```text
allowed_methods=GET,POST,PUT
```

---

# 82. Formatting Data

Ansible provides filters that can serialize structured data.

For example, you may encounter:

```text
to_json

to_yaml

to_nice_json

to_nice_yaml
```

Use serialization filters when the destination format genuinely requires them.

Do not manually build complex JSON when a safe serialization mechanism is available.

# 83. Jinja2 Comments

Template comments use:

```jinja2
{# This is a Jinja2 comment #}
```

These comments are processed by the template engine and normally do not appear in the rendered output.

Compare:

```jinja2
{# Internal template comment #}
# Rendered configuration comment
```

The second line is ordinary text and can appear in the final configuration.

---

# 84. Comments Can Contain Sensitive Information

Do not put secrets in comments.

Bad:

```text
# Temporary password is ...
```

Whether the comment exists in:

```text
Template source

Rendered configuration

Git history

Logs
```

it can still leak sensitive information.

Comments are not secret storage.

---

# 85. Template Source vs Destination

Example:

```yaml
ansible.builtin.template:
  src: templates/nginx.conf.j2
  dest: /etc/nginx/nginx.conf
```

Mental model:

```text
Control Node
templates/nginx.conf.j2
        │
        ↓
     Render
        │
        ↓
Managed Node
/etc/nginx/nginx.conf
```

Do not confuse the source template with the rendered destination.

---

# 86. Template Ownership

Example:

```yaml
owner: root
group: root
```

The rendered file should have ownership appropriate to the consuming service.

Do not automatically use:

```text
root:root
```

for every file.

Determine the actual service requirement.

# 87. Template Permissions

Example:

```yaml
mode: "0644"
```

For sensitive configuration:

```yaml
mode: "0600"
```

or perhaps:

```yaml
mode: "0640"
```

with a controlled service group.

Permission design depends on:

```text
Who creates the file?

Who reads the file?

Who modifies the file?

Does the service run as root?

Does a service group need access?

Does the file contain secrets?
```

---

# 88. Directory Permissions Matter Too

A file may be:

```text
0600
```

but its parent directory may expose unexpected information.

Or the service may not be able to traverse the directory.

Security requires understanding:

```text
File permissions
+
Directory permissions
+
Ownership
+
Service identity
```

not just one `mode`.

# 89. Backups

Several file-manipulation modules can create backup copies when configured to do so.

For example:

```yaml
- name: Deploy application configuration
  ansible.builtin.template:
    src: templates/app.conf.j2
    dest: /etc/veriqta/app.conf
    owner: root
    group: root
    mode: "0640"
    backup: true
```

This can preserve a previous destination version before replacement.

---

# 90. Why Backups Help

A backup may help when:

```text
New configuration is incorrect

Manual comparison is required

Incident investigation needs the old file

Emergency recovery is necessary
```

But:

```text
backup: true
```

is not a complete backup strategy.

---

# 91. Backup Security

If the original file contains secrets, its backup probably does too.

Therefore:

```text
Sensitive Current File
↓
Sensitive Backup
```

Do not create unlimited sensitive backup files without considering:

```text
Permissions

Retention

Disk usage

Secret rotation

Cleanup

Compliance requirements
```

# 92. Configuration Validation

One of the strongest production patterns is:

```text
Render
↓
Validate
↓
Install
```

instead of:

```text
Render
↓
Install
↓
Hope
```

Some Ansible file-management modules support a:

```text
validate
```

parameter.

---

# 93. Why Validation Matters

Imagine generating:

```text
/etc/nginx/nginx.conf
```

with a syntax error.

Without validation:

```text
Bad Configuration
↓
Installed
↓
Service Restart
↓
Service Fails
↓
Outage
```

Better:

```text
Bad Configuration
↓
Validation Fails
↓
Final File Not Replaced
↓
Task Fails
↓
Service Keeps Existing Configuration
```

where the service's validation tool supports that workflow.

---

# 94. `validate`

Conceptually:

```yaml
validate: "validation-command %s"
```

Ansible uses a temporary candidate file and substitutes its path for:

```text
%s
```

The validator checks that candidate before it becomes the final destination.

---

# 95. Example Nginx Validation Pattern

A pattern may look like:

```yaml
- name: Deploy nginx configuration
  ansible.builtin.template:
    src: templates/nginx.conf.j2
    dest: /etc/nginx/nginx.conf
    owner: root
    group: root
    mode: "0644"
    validate: "/usr/sbin/nginx -t -c %s"
  notify: Reload nginx
```

Important:

The exact validation command must match the software you are configuring and how its configuration is structured.

Test the validator in your environment.

---

# 96. Validation Command Security

The validation command is not passed through a normal shell for arbitrary shell expansion.

Do not expect constructs such as:

```text
pipes

shell redirection

wildcards

shell variable expansion
```

to behave as though you had written a shell script.

For complex validation, use a dedicated validation mechanism or script designed for the job.

---

# 97. Validation Is Not Service Verification

These are different:

```text
Configuration Validation
```

asks:

```text
Is this candidate configuration syntactically or structurally acceptable?
```

Service verification asks:

```text
Did the service actually start and behave correctly?
```

You often need both.

---

# 98. Strong Deployment Pattern

```text
Render
↓
Validate Candidate
↓
Deploy
↓
Changed?
↓
Notify Handler
↓
Reload/Restart
↓
Verify Service State
↓
Verify Application Behavior
```

This is much stronger than:

```text
Copy file
↓
Restart
↓
Done
```

---

# 99. Template-Triggered Handlers

Example:

```yaml
- name: Deploy application configuration
  ansible.builtin.template:
    src: templates/app.conf.j2
    dest: /etc/veriqta/app.conf
    owner: root
    group: root
    mode: "0640"
  notify: Restart application
```

Handler:

```yaml
handlers:
  - name: Restart application
    ansible.builtin.service:
      name: veriqta
      state: restarted
```

---

# 100. Template Handler Flow

```text
Template Source
+
Variables
↓
Render
↓
Compare With Destination
↓
Different?
├── NO
│   ↓
│ OK
│
└── YES
    ↓
CHANGED
    ↓
Notify Handler
    ↓
Continue Tasks
    ↓
Handler Executes
    ↓
Service Restarted
```

This is one of the most important Ansible patterns.

---

# 101. Reload vs Restart

A configuration change does not always require a full restart.

Some services support:

```text
Reload
```

which can apply configuration with less disruption.

Others require:

```text
Restart
```

Use the service's documented behavior.

Do not assume:

```text
configuration changed
=
restart everything
```

# 102. Configuration Deployment Should Be Atomic Where Possible

Ansible's file-management modules generally aim to avoid exposing partially written destination files and use safe file operations where supported.

This matters because you do not want a service reading:

```text
Half of a configuration file
```

while deployment is still writing it.

Avoid unsafe write behavior unless the environment genuinely requires it and you understand the race-condition and corruption risks.

# 148. Build the Playbook

Create:

```text
playbooks/files-and-templates.yml
```

```yaml
---
- name: Manage web files and templates
  hosts: web
  become: true
  gather_facts: true

  tasks:
    - name: Install web server
      ansible.builtin.package:
        name: "{{ web_package }}"
        state: present

    - name: Create web document root
      ansible.builtin.file:
        path: "{{ web_root }}"
        state: directory
        owner: root
        group: root
        mode: "0755"

    - name: Deploy generated web page
      ansible.builtin.template:
        src: templates/index.html.j2
        dest: "{{ web_root }}/index.html"
        owner: root
        group: root
        mode: "0644"
      notify: Restart web service

    - name: Ensure web service is enabled and running
      ansible.builtin.service:
        name: "{{ web_service }}"
        state: started
        enabled: true

    - name: Apply pending handlers before verification
      ansible.builtin.meta: flush_handlers

    - name: Verify web page
      ansible.builtin.uri:
        url: http://127.0.0.1/
        status_code: 200
        return_content: true
      register: web_response
      changed_when: false

    - name: Verify rendered title appears
      ansible.builtin.assert:
        that:
          - site.title in web_response.content
        fail_msg: "Rendered site title was not found in the HTTP response"
        success_msg: "Rendered web page verified successfully"

  handlers:
    - name: Restart web service
      ansible.builtin.service:
        name: "{{ web_service }}"
        state: restarted
```

```text

↓
RENDER
↓
VALIDATE
↓
DEPLOY
↓
ACTIVATE
↓
VERIFY
```

And for sensitive configuration:

```text
PROTECT SOURCE
↓
RENDER SECURELY
↓
RESTRICT DESTINATION
↓
CONTROL OUTPUT
↓
CONTROL BACKUPS
↓
VERIFY WITHOUT LEAKING SECRETS
```

That is the foundation of production configuration management with Ansible.
