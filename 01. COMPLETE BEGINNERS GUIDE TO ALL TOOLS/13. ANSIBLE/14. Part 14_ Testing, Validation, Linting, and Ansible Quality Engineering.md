# Part 14: Testing, Validation, Linting, and Ansible Quality Engineering

## Learn How to Prove Automation Works Before Production

Writing an Ansible playbook is not the same as proving that it works.

A playbook can:

* contain valid YAML
* pass syntax checking
* pass linting
* look correct in check mode

and still fail when it reaches a real server.

Even worse, it can execute successfully and still configure the wrong thing.

That is why production Ansible needs a testing strategy.

The goal of this chapter is to move from:

```text
I wrote the automation.
```

to:

```text
I have evidence that the automation is structurally valid,
targets the intended systems,
applies correctly,
is repeatable,
and produces the required operational result.
```

---

# 1. The Validation Pipeline

This is the mental model for Part 14:

```text
YAML
↓
Syntax Check
↓
Lint
↓
Inventory Validation
↓
Check Mode
↓
Test Environment
↓
Apply
↓
Second Apply
↓
Idempotency Check
↓
Functional Verification
```

In a stronger production workflow:

```text
Developer Change
↓
Local Validation
↓
Static Analysis
↓
Security Checks
↓
CI Pipeline
↓
Disposable Test Environment
↓
Real Apply
↓
Idempotency Test
↓
Functional Tests
↓
Review / Approval
↓
Production Deployment
↓
Production Verification
```

No single stage proves everything.

Each stage answers a different question.

---

# 2. The Core Quality Questions

Before production, you want evidence for at least these questions:

```text
Is the YAML valid?

Can Ansible parse the playbook?

Can Ansible load the required roles and collections?

Is the inventory valid?

Are the expected hosts selected?

Does linting identify bad practices?

Are obvious security problems present?

Does check mode predict unexpected changes?

Can the automation actually run?

Does it succeed in a controlled environment?

Can it run twice without unnecessary changes?

Did it create the expected configuration?

Is the service actually running?

Is the port actually reachable?

Does the application actually respond?

Are files protected correctly?

Does failure stop the pipeline?
```

Testing Ansible is therefore much more than:

```bash
ansible-playbook site.yml --syntax-check
```

# 5. Testing Vocabulary

Before continuing, understand these terms.

## Validation

Checking whether something satisfies expected structural or behavioral requirements.

## Linting

Static examination of source files for patterns, errors, conventions, and quality problems.

## Static Analysis

Examining code or configuration without necessarily executing the complete workload.

## Functional Testing

Checking whether the resulting system actually performs the required function.

## Idempotency Testing

Checking whether repeated execution produces unnecessary changes.

## Integration Testing

Testing how multiple components work together.

## Smoke Testing

A small set of important checks used to determine whether a system is basically operational.

## Regression Testing

Testing whether previously working behavior remains correct after a change.

## Quality Gate

A required validation step that must succeed before the workflow continues.

# 6. Start With the Cheapest Tests

A useful engineering principle is:

```text
Fast + Cheap Checks First
↓
Slower Tests Later
↓
Expensive / Production-Like Tests Last
```

For example:

```text
YAML Validation
↓
Syntax
↓
Lint
↓
Inventory
↓
Security Scanning
↓
Test Environment
↓
Functional Testing
```

Do not provision an entire test environment just to discover:

```text
mapping values are not allowed here
```

because your YAML indentation was wrong.

# 7. YAML Validation

Ansible playbooks, inventories, variable files, role files, and many configuration files use YAML.

Before Ansible semantics matter, the YAML itself must be structurally valid.

Example:

```yaml
---
- name: Configure web servers
  hosts: web

  tasks:
    - name: Install Nginx
      ansible.builtin.package:
        name: nginx
        state: present
```

This has valid YAML structure.

---

# 8. YAML Errors

Example:

```yaml
---
- name: Configure web servers
  hosts: web

  tasks:
    - name: Install Nginx
      ansible.builtin.package:
      name: nginx
        state: present
```

The hierarchy is wrong.

Depending on the exact mistake, you may get:

```text
YAML parser error
```

or YAML that parses but means something different from what you intended.

Remember Part 3:

```text
Valid YAML
≠
Correct Data Structure
≠
Correct Ansible Automation
```

---

# 9. The Three YAML Questions

Always ask:

```text
1. Is this valid YAML?

2. Does it create the data structure I intended?

3. Does that structure make sense to Ansible?
```

These are different questions.


# 12. Ansible Syntax Checking

Ansible provides syntax checking through:

```bash
ansible-playbook playbook.yml --syntax-check
```

This asks Ansible to load and parse the playbook without executing it.

---

# 13. Example

Run:

```bash
ansible-playbook playbooks/site.yml --syntax-check
```

Expected successful output is typically brief and identifies the playbook.

Exact output can vary by Ansible version and configuration.

---

# 14. What Syntax Checking Can Catch

Syntax checking can identify problems such as:

```text
Malformed playbook structure

Invalid task structure

Certain module/action errors

Some malformed parameters

Missing required imports/includes during loading

Other parse/load failures
```

The exact detection depends on the content being loaded.

---

# 15. What Syntax Checking Cannot Prove

Passing:

```bash
ansible-playbook site.yml --syntax-check
```

does NOT prove:

```text
SSH works

sudo works

Package exists

Repository works

Template produces valid application config

Service starts

Port opens

Application responds

Credential is valid

Cloud API accepts request

Playbook is idempotent

Correct hosts were selected

Business behavior is correct
```

It proves a much narrower thing.

---

# 16. Syntax Check Mental Model

```text
Playbook
↓
Load YAML
↓
Load Ansible Structure
↓
Resolve Required Automation Content
↓
Parse
↓
PASS / FAIL
```

No production change should occur from syntax checking.

---

# 17. Syntax Check Should Be Early

Run syntax checking:

```text
During development

Before committing

During pull requests

Inside CI
```

It is fast enough that there is little reason to wait until deployment.

---

# 18. Syntax Check All Entry-Point Playbooks

If your repository contains:

```text
playbooks/
├── site.yml
├── baseline.yml
├── deploy.yml
├── verify.yml
└── rollback.yml
```

do not assume checking only:

```text
site.yml
```

validates every independent entry point.

Validate the playbooks your operational workflows actually execute.

Therefore inventory testing is part of quality engineering.

```text

```

# 29. Connectivity Validation

Inventory structure can be correct while hosts remain unreachable.

A controlled connectivity test may use:

```bash
ansible web \
  -i inventory/lab/hosts.yml \
  -m ansible.builtin.ping
```

Remember:

```text
ansible.builtin.ping
≠
ICMP ping
```

It validates that Ansible can successfully execute the module path required for the target.

# 30. Check Mode

Run:

```bash
ansible-playbook \
  -i inventory/lab/hosts.yml \
  playbooks/site.yml \
  --check
```

Short form:

```bash
ansible-playbook site.yml -C
```

Check mode asks modules that support it to predict what would change without actually making those changes.

---

# 31. Check Mode Mental Model

Normal:

```text
Inspect Current State
↓
Calculate Required Change
↓
Apply Change
↓
Report Result
```

Check mode:

```text
Inspect Current State
↓
Calculate Predicted Change
↓
Do Not Apply
↓
Report Prediction
```

---

# 32. Check Mode Is a Simulation

This distinction is critical.

```text
CHECK MODE
=
Prediction
```

not:

```text
CHECK MODE
=
Successful Real Deployment
```

---

# 33. Example

Suppose:

```yaml
- name: Ensure Nginx is installed
  ansible.builtin.package:
    name: nginx
    state: present
```

In check mode, a module supporting check mode may determine:

```text
Nginx missing
↓
Would install
↓
changed
```

but the package is not actually installed.

---

# 34. Why This Matters

A later task might require Nginx to exist.

Example:

```yaml
- name: Ensure Nginx is started
  ansible.builtin.service:
    name: nginx
    state: started
```

During a simulated run, the state required by later tasks may never actually be created.

This can make check-mode behavior different from real execution.

---

# 35. Check-Mode Support Is Module-Specific

Not every module behaves identically in check mode.

Some provide:

```text
Full prediction
```

Some provide:

```text
Partial prediction
```

Some provide:

```text
No check-mode support
```

Always inspect module documentation.

---

# 36. Example: `command`

Arbitrary commands are difficult for Ansible to predict.

Example:

```yaml
- name: Run database migration
  ansible.builtin.command:
    cmd: /opt/app/migrate
```

How could Ansible know what that arbitrary executable will change without running it?

It usually cannot.

That is why command-style automation needs careful testing.

---

# 37. `creates` and `removes`

For some command tasks, you can provide state clues.

Example:

```yaml
- name: Initialize application
  ansible.builtin.command:
    cmd: /opt/app/initialize
    creates: /var/lib/myapp/initialized
```

Now Ansible has a file-state signal it can inspect.

This also improves idempotency design.

---

# 38. Check-Mode Magic Variable

Ansible exposes:

```text
ansible_check_mode
```

You can condition behavior based on whether the playbook is executing in check mode.

Example:

```yaml
when: not ansible_check_mode
```

Use this deliberately.

Do not litter every playbook with check-mode exceptions just to make a green simulation.

---

# 39. Forcing Check Mode for a Task

A task can specify:

```yaml
check_mode: true
```

This forces that task to behave in check mode even during a normal run.

This can be useful for prediction/testing patterns.

---

# 40. Forcing Normal Execution During `--check`

A task can specify:

```yaml
check_mode: false
```

This means the task can execute normally even when the overall playbook was launched with:

```text
--check
```

This is powerful and potentially dangerous.

---

# 41. Important Safety Warning

Do not assume:

```bash
ansible-playbook site.yml --check
```

means:

```text
Absolutely nothing can possibly change.
```

A task explicitly configured with:

```yaml
check_mode: false
```

may still execute normally.

Review your automation.

---

# 42. Check Mode and Registered Results

Check mode can become complicated when later tasks depend on results from earlier tasks that were skipped or only simulated.

Example:

```text
Task A
↓
Register result
↓
Task B condition depends on result
```

If Task A cannot meaningfully execute in check mode, Task B may not behave like the real deployment.

---

# 43. Check Mode and External Systems

Be especially cautious with:

```text
APIs

Cloud resources

Databases

Shell scripts

Custom modules

External commands

Third-party collections
```

Do not assume simulation support.

Inspect documentation and test behavior.

---

# 44. Check Mode Is Still Valuable

Despite its limitations, check mode is excellent for:

```text
Previewing many state changes

Detecting unexpected drift

Reviewing configuration changes

Testing state-aware modules

Pre-deployment inspection
```

Use it as one layer.

Not the only layer.

---

# 45. Diff Mode

Run:

```bash
ansible-playbook site.yml --diff
```

Diff mode asks modules that support it to show before-and-after differences.

It is especially useful for file and template changes.

---

# 46. Check + Diff

A useful development combination is:

```bash
ansible-playbook \
  -i inventory/lab/hosts.yml \
  playbooks/site.yml \
  --check \
  --diff
```

Mental model:

```text
What Would Change?
+
Show Me How It Would Change
```

---

# 47. Limit the Blast Radius

When inspecting changes, use a controlled target:

```bash
ansible-playbook \
  -i inventory/staging/hosts.yml \
  playbooks/site.yml \
  --check \
  --diff \
  --limit web01
```

This is safer and easier to review than flooding the terminal with hundreds of host diffs.

---

# 48. Diff Output Example

Suppose a template changes:

```text
worker_processes 2;
```

to:

```text
worker_processes 4;
```

Diff mode may show a before/after difference.

Exact output depends on the module and Ansible version.

---

# 49. Diff Mode Has Security Risk

A configuration file may contain:

```text
Passwords

Tokens

Private URLs

API credentials

Database strings

Certificates

Sensitive application configuration
```

Diff mode can expose changed content.

---

# 50. Disable Diff for Sensitive Tasks

Example:

```yaml
- name: Deploy sensitive application configuration
  ansible.builtin.template:
    src: secrets.conf.j2
    dest: /etc/myapp/secrets.conf
    owner: root
    group: root
    mode: "0600"
  diff: false
  no_log: true
```

Remember Part 13:

```text
Useful Validation
```

must not become:

```text
Secret Leakage
```

---

# 51. Check Mode vs Diff Mode

```text
CHECK MODE
↓
Should a change happen?
```

```text
DIFF MODE
↓
What content differs?
```

They solve related but different problems.

---

# 52. Idempotency Testing

Ansible automation should generally converge systems toward desired state.

A powerful test is:

```text
First Apply
↓
Second Apply
```

The second run should normally report:

```text
No unnecessary changes
```

---

# 53. Idempotency Test Workflow

```text
Fresh Test Host
↓
Apply Playbook
↓
Record Result
↓
Apply Same Playbook Again
↓
Inspect changed Count
```

Expected:

```text
First Run
changed > 0
```

possibly.

Then:

```text
Second Run
changed = 0
```

for stable desired-state tasks.

---

# 54. Example First Run

You may see:

```text
PLAY RECAP
web01 : ok=12 changed=7 unreachable=0 failed=0
```

That may be completely normal.

The server required configuration.

---

# 55. Example Second Run

Run the same playbook again.

A desirable result might be:

```text
PLAY RECAP
web01 : ok=12 changed=0 unreachable=0 failed=0
```

Now you have evidence that the playbook converged.

---

# 56. Changed Count Is Evidence, Not Absolute Proof

Do not blindly enforce:

```text
changed=0
```

for every conceivable playbook.

Some tasks intentionally change each run.

Examples might include:

```text
Rotating ephemeral data

Triggering deliberate operational actions

Generating new artifacts by design
```

The engineering question is:

```text
Was the reported change expected?
```

---

# 57. False Change

Example:

```yaml
- name: Restart Nginx
  ansible.builtin.command:
    cmd: systemctl restart nginx
```

Every run executes the command.

That is not desired-state design.

Better:

```text
Configuration changes
↓
Notify Handler
↓
Restart only when required
```

This is one reason handlers matter.

---

# 58. Idempotency Reveals Design Quality

Repeated unnecessary changes can reveal:

```text
Poor module choice

Unconditional shell commands

Unstable templates

Generated timestamps

Random values

Bad changed_when logic

Incorrect file ownership

Repeated service restarts
```

An idempotency failure is often a design smell.

---

# 59. Unstable Template Example

Bad template:

```jinja2
# Generated at {{ ansible_date_time.iso8601 }}
server_name {{ server_name }};
```

Every run may produce different content.

That causes:

```text
Template Changed
↓
Handler Triggered
↓
Service Restarted
```

even when the functional configuration is unchanged.

Do not embed volatile values unless they are genuinely required.

---

# 60. `changed_when` Can Hide Problems

You learned:

```yaml
changed_when: false
```

in Part 8.

Do not use it merely to make an idempotency test pass.

Bad philosophy:

```text
Task always changes
↓
Force changed=false
↓
Green test
```

You have hidden the signal.

You have not fixed the behavior.

---

# 61. Testing Desired State vs Functional State

Suppose Ansible reports:

```text
nginx
state: started
```

That does not automatically prove:

```text
Website works correctly
```

You need both:

```text
Configuration State Verification
+
Functional Verification
```

---

# 62. Example

Ansible may successfully:

```text
Install Nginx
↓
Start Nginx
```

but users receive:

```text
HTTP 500
```

because the application behind Nginx is broken.

Automation success is not application success.

# 65. Installation

Install `ansible-lint` according to its current official installation documentation and your project's Python/dependency strategy.

For isolated development environments, a virtual environment is commonly appropriate.

```bash

```

Activate on Linux/macOS:


Then install your pinned development dependencies according to your project policy.

Do not let every engineer install arbitrary versions and assume they will receive identical results.

---

# 70. Syntax Checking Inside `ansible-lint`

Current `ansible-lint` also performs Ansible syntax checking as a prerequisite for lint processing.

This is important because a file Ansible cannot load cannot meaningfully undergo many later Ansible-specific lint checks.

Still, keeping explicit syntax-check commands in CI can make pipeline intent and failure stages clearer.

---

# 71. Lint Profiles

Modern `ansible-lint` supports profiles that group rules into progressive quality levels.

Do not blindly choose the strictest profile on day one for a large legacy repository.

Instead:

```text
Understand Current Quality
↓
Choose Standard
↓
Fix Violations
↓
Enforce Standard in CI
```

---

# 72. Lint Configuration

A repository may contain lint configuration.

Conceptually:

```text
Repository
├── Ansible content
├── Dependency definitions
└── Lint policy
```

This helps every engineer and CI runner use consistent expectations.

---

# 73. Avoid Blind Rule Skipping

Bad response:

```text
Lint failed.
↓
Disable rule.
```

Better:

```text
Lint failed.
↓
Understand rule.
↓
Determine whether finding is valid.
↓
Fix code if appropriate.
↓
Document narrowly justified exception if necessary.
```

---

# 74. Quality Exceptions Need Ownership

Sometimes an exception is legitimate.

For example:

```text
Legacy integration

Third-party limitation

Intentional operational command

Test fixture
```

But exceptions should be:

```text
Narrow

Documented

Reviewed

Temporary where possible
```

not:

```text
Disable everything that turns red.
```


Static analysis is:

```text
Fast
+
Repeatable
+

```

---

# 76. Static Analysis Limitation

Static analysis cannot prove:


# 80. Secret Scanning Has False Positives

```text

Examples

```


---

# 81. Secret Scanning Has False Negatives

A scanner may miss:

```text
Custom credential formats

Obfuscated secrets

Unusual tokens

Secrets that do not match known patterns
```

---

# 101. `ansible.builtin.assert`

Ansible includes:

```text
ansible.builtin.assert
```

for checking conditions.

Example:

```yaml
- name: Verify required variables
  ansible.builtin.assert:
    that:
      - application_port is defined
      - application_port | int > 0
      - application_port | int < 65536
```

If an assertion fails, the task fails.

---

# 102. Why Assertions Matter

Without assertions:

```text
Bad Input
↓
Automation Continues
↓
Failure Happens Later
```

With assertions:

```text
Bad Input
↓
Fail Early
↓
Clear Explanation
```

---

# 103. Custom Assertion Messages

Example:

```yaml
- name: Validate application port
  ansible.builtin.assert:
    that:
      - application_port | int >= 1024
      - application_port | int <= 65535
    fail_msg: "application_port must be between 1024 and 65535."
    success_msg: "Application port is valid."
```

Clear failures improve troubleshooting.

---

# 104. Assertions Are Not Only for Variables

You can assert facts and registered results.

Example:

```yaml
- name: Verify supported operating system
  ansible.builtin.assert:
    that:
      - ansible_facts['os_family'] in ['Debian', 'RedHat']
    fail_msg: "This role does not support this operating-system family."
```

This makes role boundaries explicit.

---

# 105. Verification Tasks

A deployment should answer:

```text
Did Ansible finish?
```

and:

```text
Does the system now satisfy the required state?
```

These are different.

---

# 106. File Verification

Use:

```text
ansible.builtin.stat
```

Example:

```yaml
- name: Inspect application configuration
  ansible.builtin.stat:
    path: /etc/myapp/app.conf
  register: app_config
```

Then:

```yaml
- name: Verify application configuration exists
  ansible.builtin.assert:
    that:
      - app_config.stat.exists
      - app_config.stat.isreg
```

---

# 107. Permission Verification

Extend the assertion:

```yaml
- name: Verify application configuration permissions
  ansible.builtin.assert:
    that:
      - app_config.stat.exists
      - app_config.stat.pw_name == 'root'
      - app_config.stat.gr_name == 'myapp'
      - app_config.stat.mode == '0640'
```

This proves more than:

```text
File exists.
```

---

# 108. Why Permission Verification Matters

A configuration file can be functionally correct but insecure.

Example:

```text
Correct database password
+
mode 0777
```

The application may work.

The security state is wrong.

Quality includes security properties.

# 112. Port Verification

```text

```

```text

```



# 114. HTTP Verification

Use:

```text
ansible.builtin.uri
```

for HTTP/HTTPS interactions.

Example:

```yaml
- name: Verify application health endpoint
  ansible.builtin.uri:
    url: http://127.0.0.1/health
    method: GET
    status_code: 200
  register: health_response
```

Now you are testing application behavior at the HTTP layer.

---

# 115. Assert HTTP Result

You can explicitly verify:

```yaml
- name: Verify health response
  ansible.builtin.assert:
    that:
      - health_response.status == 200
```

Depending on the module invocation, a non-accepted status may already fail the task.

Explicit assertions can still document important expectations.

---

# 116. Verify Response Content

Suppose your endpoint returns:

```text
healthy
```

You may verify the content when appropriate.

Example concept:

```yaml
- name: Verify application health response
  ansible.builtin.uri:
    url: http://127.0.0.1/health
    return_content: true
    status_code: 200
  register: health_response

- name: Assert application reports healthy
  ansible.builtin.assert:
    that:
      - "'healthy' in health_response.content"
```

Use the actual contract of your application.

---

# 117. Do Not Leak Secrets During HTTP Verification

Do not dump:

```text
Authorization headers

Tokens

Session cookies

Sensitive response bodies
```

into CI logs.

Use:

```yaml
no_log: true
```

where sensitive request or result data could be exposed.

---

# 118. External vs Local Verification

Checking:

```text
http://127.0.0.1
```

from the managed host proves local availability.

It does not prove:

```text
Users can reach application through load balancer.
```

You may need external verification.

# 134. False Confidence

This is one of the most important concepts in Part 14.

Automation testing can create false confidence.

Example:

```text
Syntax check passed.
```

Engineer concludes:

```text
Production ready.
```

Wrong.

---

# 135. False Confidence Example: Check Mode

```text
--check passed
```

does not mean:

```text
Real execution will pass.
```

Some tasks may have been skipped or simulated imperfectly.

---

# 136. False Confidence Example: Container

```text
Role passed in container.
```

does not necessarily mean:

```text
Role works after VM reboot.
```

The container may not reproduce the boot environment.

---

# 137. False Confidence Example: Service

```text
systemd says active
```

does not necessarily mean:

```text
Application serves valid requests.
```

---

# 138. False Confidence Example: HTTP 200

Even:

```text
HTTP 200
```

may not prove:

```text
Checkout workflow works.
```

A homepage can work while the database path is broken.

Tests must match the actual risk.

---

# 139. False Confidence Example: Idempotency

```text
changed=0
```

does not prove:

```text
System is correctly configured.
```

A playbook that does nothing can be perfectly "idempotent."

You still need functional verification.

# 171. Test Isolation

One test should not unpredictably depend on another test's leftovers.

Bad:

```text
Test A creates user
↓
Test B accidentally depends on user
```

Better:

```text
Known Starting State
↓
Test
↓
Cleanup
```

or create disposable environments.

---

# 172. Repeatability

A good automated test should produce the same result when:

```text
Same code
+
Same inputs
+
Same controlled environment
```

are used.

Flaky tests destroy trust.

---

# 173. Flaky Tests

A flaky test sometimes passes and sometimes fails without meaningful code changes.

Causes may include:

```text
Race conditions

Timing assumptions

External service instability

DNS delays

Uncontrolled dependency versions

Shared environments

State left by previous tests
```

Do not normalize flaky infrastructure tests.

Investigate them.

---

# 174. Waiting Correctly

Do not blindly use:

```yaml
- ansible.builtin.pause:
    seconds: 60
```

when you actually need:

```text
Wait until service port becomes available.
```

Use condition-based waiting where possible.

Example:

```yaml
- name: Wait for application port
  ansible.builtin.wait_for:
    host: 127.0.0.1
    port: 8080
    timeout: 60
```

This can be faster and more deterministic.

---

# 175. Timeout Design

Every wait should eventually fail.

Bad:

```text
Wait forever.
```

Better:

```text
Wait for condition
↓
Timeout
↓
Fail clearly
```

This keeps CI from hanging indefinitely.

# 189. Verification Playbook

`playbooks/verify.yml`

```yaml
---
- name: Verify web server
  hosts: web
  gather_facts: false

  tasks:
    - name: Inspect deployed web page
      ansible.builtin.stat:
        path: /var/www/html/index.html
      register: web_page

    - name: Verify web page metadata
      ansible.builtin.assert:
        that:
          - web_page.stat.exists
          - web_page.stat.isreg
          - web_page.stat.mode == '0644'

    - name: Wait for HTTP port
      ansible.builtin.wait_for:
        host: 127.0.0.1
        port: 80
        state: started
        timeout: 30

    - name: Request local web page
      ansible.builtin.uri:
        url: http://127.0.0.1/
        method: GET
        return_content: true
        status_code: 200
      register: nginx_response

    - name: Verify expected page content
      ansible.builtin.assert:
        that:
          - "'Ansible Quality Lab' in nginx_response.content"
```

# 218. Final Mental Model

Do not ask:

```text
Does my playbook run?
```

Ask:

```text
Can the YAML be parsed?

Can Ansible load it?

Does it meet our quality rules?

Does inventory resolve correctly?

Are the intended hosts selected?

Are secrets protected?

What does check mode predict?

What does diff reveal?

Can the automation apply to a clean test system?

Does it converge?

Does the second run remain stable?

Does the resulting system satisfy expected state?

Does the service actually work?

Do security properties remain correct?

Does failure stop promotion?

Can we verify production after deployment?
```

That is the difference between:

```text
Ansible scripting
```

and:

```text
Ansible Quality Engineering
```
