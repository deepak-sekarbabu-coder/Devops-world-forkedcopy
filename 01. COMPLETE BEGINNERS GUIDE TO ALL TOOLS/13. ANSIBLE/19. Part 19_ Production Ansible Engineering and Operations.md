# Part 19: Production Ansible Engineering and Operations

## Bridge the Gap Between Ansible Tutorials and Real Configuration-Management Engineering

You already know how to write Ansible.

That is not the same as knowing how to operate Ansible in production.

A tutorial often ends here:

```text
Write Playbook
↓
Run Playbook
↓
PLAY RECAP
↓
Success
```

Production engineering begins where that tutorial ends.

In production, we must answer:

```text
Who owns this automation?

Where does the code live?

Who can change it?

Who reviews it?

Which version of Ansible runs it?

Which collections are installed?

Which environments can it reach?

Which credentials can it use?

How many servers can it change at once?

What happens when server 17 of 100 fails?

How do we recover?

How do we know the service actually works?

What happens when someone manually changes a server?

How do we upgrade Ansible safely?

How do we handle deprecated modules?

Where are deployment records stored?

How do auditors know what happened?

Who gets called when automation breaks production?
```

These are production Ansible questions.

This chapter moves us from:

```text
Ansible User
```

to:

```text
Ansible Production Engineer
```

---

# 1. The Production Ansible Mental Model

Production Ansible is not:

```text

```

Production Ansible is a complete operating system for configuration change:

```text
Standards
↓
Git
↓
Review
↓
Testing
↓
Security
↓
Approval
↓
Controlled Execution
↓
Verification
↓
Monitoring
↓
Drift Detection
↓
Recovery
↓
Maintenance
↓
Audit Evidence
```

The requested production flow is:

```text
Change Request
↓
Ansible Code
↓
Pull Request
↓
Syntax / Lint
↓
Security
↓
Test
↓
Review
↓
Approval
↓
Controlled Execution
↓
Managed Nodes
↓
Verification
↓
Monitoring
↓

```

But production operation is actually cyclical:

```text

↓

↓
Verify
↓
Operate
↓

↓

↓
Create New Change
↓

```

Configuration management never really ends.

---

# 2. Production Automation Standards

A production Ansible repository should have documented standards.

Without standards, ten engineers may produce ten completely different automation styles.

You eventually get:

```text
Role A uses FQCNs.

Role B does not.

Role C stores passwords in vars.

Role D retrieves secrets externally.

Role E uses shell everywhere.

Role F uses modules.

Role G restarts services after every task.

Role H never restarts them.

Role I targets all hosts.

Role J has no verification.
```

Technically, all of these may contain valid YAML.

Operationally, the repository becomes difficult to trust.

# 7. Inventory Standards

Inventory deserves production engineering discipline.

Inventory determines:

```text
WHAT EXISTS
```

and:

```text
WHAT ANSIBLE CAN TARGET
```

A bad task targeting the correct host is dangerous.

A correct task targeting the wrong hosts can be equally dangerous.

---

# 8. Inventory Should Represent Operational Reality

Useful dimensions might include:

```text
Environment

Application

Service

Role

Region

Availability zone

Criticality

Lifecycle

Operating system

Ownership
```

Example conceptual groups:

```text
environment_production

role_web

role_application

region_us_east_1

criticality_tier_1
```

This enables deliberate intersections.

Example:

```text
environment_production:&role_web
```

---

# 9. Avoid Ambiguous Inventory Groups

A group called:

```text
servers
```

tells us almost nothing.

Likewise:

```text
prod
```

may be too broad for many operations.

Prefer groups that express meaningful operational classification.

---

# 10. Inventory Must Not Become a Secret Store

Avoid:

```yaml
db_password: SuperSecretPassword
```

inside ordinary inventory.

Inventory should contain configuration and targeting information.

Secrets should use approved secret-management mechanisms.

---

# 11. Dynamic Inventory in Production

For dynamic cloud infrastructure:

```text
Cloud API
↓
Metadata / Tags
↓
Inventory Plugin
↓
Dynamic Groups
↓
Target Pattern
```

This avoids manually maintaining host lists that quickly become stale.

But dynamic inventory introduces a new requirement:

```text
Metadata becomes operationally important.
```

If tags determine targeting, incorrect tags can become deployment errors.

---

# 12. Inventory Metadata Is Part of Your Control Plane

Suppose Ansible discovers production through:

```text
Environment=production
Role=web
AnsibleManaged=true
```

Changing those tags can alter which servers Ansible sees.

Therefore:

```text
Who can modify infrastructure metadata?
```

becomes a security and operations question.

---

# 13. Inventory Validation

Before mutation:

```bash
ansible-inventory \
  -i inventories/production/aws_ec2.yml \
  --graph
```

Then inspect the intended pattern:

```bash
ansible \
  "environment_production:&role_web" \
  -i inventories/production/aws_ec2.yml \
  --list-hosts
```

The target set should never be a surprise.

---

# 14. Playbook Standards

Playbooks should primarily describe orchestration.

Avoid giant files containing every implementation detail.

Prefer:

```yaml
---
- name: Apply Linux baseline
  hosts: managed_linux
  become: true

  roles:
    - common
    - users
    - security_baseline
    - monitoring
```

rather than thousands of unrelated tasks in one playbook.

---

# 15. Playbook Names Should Explain Intent

Weak:

```yaml
- hosts: web
```

Better:

```yaml
- name: Deploy production web application
  hosts: "environment_production:&role_web"
```

A reader should understand the operation before reading every task.

---

# 16. Tasks Need Meaningful Names

Weak:

```yaml
- name: Copy file
```

Better:

```yaml
- name: Deploy Nginx virtual-host configuration
```

Weak:

```yaml
- name: Run command
```

Better:

```yaml
- name: Validate application database connectivity
```

Task names become:

```text
Documentation
+
Runtime output
+
Troubleshooting clues
+
Audit context
```

---

# 17. Role Standards

Roles should represent coherent responsibilities.

Good:

```text
common

users

security_baseline

nginx

application

monitoring
```

Weak:

```text
everything

server

misc

stuff
```

A role should have an understandable contract.

# 18. Role Contract

A role should make clear:

```text
What it manages

What variables it accepts

What defaults exist

What dependencies exist

Which platforms are supported

Which services it changes

Which handlers it may notify

What privileges it requires

How it is tested
```

# 19. Role Boundaries

Do not make:

```text
nginx
```

secretly responsible for:



# 20. Naming Conventions

Choose predictable names.

Examples:

```yaml
application_name:
application_version:
application_port:
deployment_environment:
monitoring_enabled:
```

Avoid meaningless names:

```yaml
x:
tmp2:
thing:
flag1:
```

---

# 21. Boolean Naming

Prefer variables whose meaning is obvious:

```yaml
monitoring_enabled: true
```

instead of:

```yaml
monitoring: 1
```

Similarly:

```yaml
automatic_restart_enabled: false
```

is easier to understand.

---

# 22. Naming Consistency

Do not alternate randomly between:

```text
prod

production

prd

live
```

unless those genuinely mean different things.

Pick a vocabulary.

Use it consistently.

---

# 23. FQCN Standards

Production content should generally prefer Fully Qualified Collection Names.

Example:

```yaml
ansible.builtin.package:
```

instead of:

```yaml
package:
```

Example:

```yaml
ansible.builtin.template:
```

Example:

```yaml
amazon.aws.aws_ec2:
```

FQCNs make module origin explicit.

---

# 24. Why FQCN Matters

Collections can contain plugins with similar short names.

FQCN answers:

```text
Which collection provides this plugin?
```

That improves:

```text
Readability

Searchability

Troubleshooting

Migration

Dependency awareness
```

---

# 25. YAML Style

Production YAML should be boring.

That is good.

Prefer:

```yaml
---
application_name: payments
application_port: 8080
monitoring_enabled: true
```

Use consistent indentation.

Avoid tabs.

Use explicit booleans:

```yaml
true
false
```

Use quoting deliberately where type interpretation matters.

---

# 26. Avoid Clever YAML

Production code should optimize for:

```text
Clarity
```

not:

```text
Look how clever this expression is.
```

If an expression requires five minutes to understand, consider simplifying it.

---

# 27. Dependency Management

Your repository may depend on:

```text
Python

ansible-core

Collections

External roles

Python libraries

System packages

Cloud SDKs
```

Dependencies must be explicit.

---

# 28. Ansible Version Management

Do not use:

```text
Whatever Ansible happens to be installed.
```

Define and test a supported version or version range.

For example, your project documentation may state:

```text
Supported automation runtime:
ansible-core version tested by this repository
```

Then CI should use that runtime.

---

# 29. Why Ansible Version Drift Is Dangerous

Different versions can change:

```text
Module behavior

Warnings

Deprecations

Python requirements

Plugin behavior

Collection compatibility

Parsing behavior
```

A laptop and CI runner should not unknowingly run unrelated versions.

---

# 30. Check the Runtime

Use:

```bash
ansible --version
```

Record it in CI logs.

This helps answer:

```text
Which automation engine executed this deployment?
```

---

# 31. Collection Versioning

Collections evolve independently.

Examples:

```text
amazon.aws

ansible.posix

community.general
```

A newer collection can contain:

```text
New functionality

Bug fixes

Behavior changes

Deprecations

Removed features
```

Do not treat collection upgrades as invisible.

---

# 32. Collection Requirements

Example:

```yaml
---
collections:
  - name: amazon.aws
    version: "APPROVED_VERSION"

  - name: ansible.posix
    version: "APPROVED_VERSION"

  - name: community.general
    version: "APPROVED_VERSION"
```

Install:

```bash
ansible-galaxy collection install \
  -r collections/requirements.yml
```

Use actual versions your organization has tested.

---

# 33. Role Versioning

External roles also require version governance.

Do not write:

```text
Install whatever newest role exists today.
```

Production automation should know which role revision was tested.

Depending on source, this may involve:

```text
Release version

Git tag

Git commit

Approved artifact
```

---

# 34. Dependency Reproducibility

The goal is:

```text
Same Repository Revision
+
Same Automation Runtime
+
Same Dependencies
=
Predictable Execution Environment
```

Perfect determinism is difficult.

But uncontrolled dependency drift makes production much worse.

# 36. Development

Development optimizes for:


# 37. Staging

Staging should provide meaningful production confidence.

It should resemble production in important dimensions such as:

```text

Configuration structure

```

while remaining safely isolated.

# 38. Production

Production optimizes for:

```text
Availability

Security

Predictability

Auditability

Controlled change

Recovery
```

Convenience is not the primary objective.

---

# 39. Account Isolation

In AWS, stronger environments may use separate accounts:

```text
Development AWS Account

Staging AWS Account

Production AWS Account
```

Then production access requires a distinct production role.

This reduces accidental cross-environment access.

---

# 40. Inventory Isolation

Avoid one huge inventory where:

```text
development

staging

production
```

can be confused easily.

Prefer explicit boundaries.

Example:

```text
inventories/
├── development/
├── staging/
└── production/
```

or separate cloud inventory definitions.

---

# 41. Credential Isolation

Development credentials should not automatically work in production.

Prefer:

```text
Development Identity
↓
Development Only
```

```text
Production Identity
↓
Production Only
```

This turns many accidental production actions into authorization failures instead of outages.

---

# 42. Control-Node Security

The Ansible control node is powerful.

It may possess:

```text
SSH access

Vault access

Cloud credentials

Inventory access

Privileged automation code

Production network access
```

Compromising it may compromise many managed nodes.

---

# 43. Harden the Control Node

Production controls may include:

```text
Restricted administrator access

Strong authentication

Patch management

Disk encryption

Endpoint protection

Audit logging

Minimal installed software

Protected SSH material

Restricted outbound/inbound network access

Secret-management integration
```

The exact controls depend on your environment.

---

# 44. Engineers' Laptops vs Production Execution

Avoid depending indefinitely on:

```text
One engineer's laptop
```

as your production control plane.

Laptops contain:

```text
Different software versions

Personal SSH configuration

Local credentials

Uncommitted files

Unknown dependencies

Different network state
```

Use controlled execution infrastructure.

---

# 45. Execution Environment Concept

An execution environment packages the automation runtime and its dependencies into a controlled execution image/environment.

Conceptually:

```text
Execution Environment
├── ansible-core
├── Collections
├── Python
├── Python Dependencies
└── System Dependencies
```

Then:

```text
Pipeline / Automation Platform
↓
Known Execution Environment
↓
Ansible
```

---

# 46. Why Execution Environments Matter

Without one:

```text
Laptop A
Ansible version X
Collection version Y
Python version Z
```

```text
Runner B
Ansible version Q
Collection version R
Python version S
```

With controlled execution environments:

```text
Approved Runtime
↓
Repeatable Automation Environment
```

This reduces environmental drift.

---

# 47. Execution Environments Do Not Solve Everything

They do not automatically solve:

```text
Bad playbooks

Wrong inventory

Overprivileged credentials

Application bugs

Network failures

Bad approvals

Incorrect variables
```

They solve runtime consistency, not every production problem.

---

# 48. SSH Architecture

For normal POSIX managed hosts:

```text
Ansible Control Environment
↓
SSH
↓
Managed Node
```

Production design must answer:

```text
Which source can SSH?

Which destination?

Which port?

Which user?

Which authentication method?

Which host-key policy?

Which privilege escalation?
```

---

# 49. Private Networks

Production hosts often should not expose SSH directly to the public internet.

Architecture:

```text
CI / Control Environment
↓
Private Connectivity
↓
Private EC2
```

Possible connectivity mechanisms include organization-specific combinations of:

```text
VPN

Private runner

Bastion

Private network peering

Managed remote-access services
```

---

# 50. Bastion Concept

A bastion can provide a controlled path:

```text
Ansible
↓
Bastion
↓
Private Server
```

instead of:

```text
Internet
↓
Every Production Server
```

The bastion itself becomes a critical security boundary.

---

# 51. Bastion Security

Protect:

```text
Who can reach it

Who can authenticate

What destinations it can reach

What is logged

How credentials are handled

How it is patched

How access is revoked
```

Do not turn a bastion into:

```text
The server everybody shares a password for.
```

---

# 52. Privilege Escalation

A connection user does not necessarily need permanent root login.

Conceptually:

```text
SSH
↓
Restricted Automation User
↓
become
↓
Approved Privileged Operation
```

This creates separation between:

```text
Connection
```

and:

```text
Privilege.
```

---

# 53. Least Privilege

Ask:

```text
What does this automation actually need?
```

Not:

```text
What permission makes every error disappear?
```

Avoid solving authorization failures by immediately granting:

```text
ALL permissions everywhere.
```

---

# 54. Least Privilege Applies Everywhere

Apply it to:

```text
Control-node users

CI runners

SSH accounts

sudo

AWS IAM

Vault

Secret managers

Git repositories

Artifact stores

Production approvals
```

Least privilege is architectural.

---

# 55. Secrets Management

Production Ansible commonly needs secrets.

Examples:

```text
Database credentials

API tokens

TLS private keys

Service credentials

Vault passwords

Cloud secrets
```

These must not become ordinary plaintext variables.

---

# 56. Ansible Vault

Ansible Vault protects sensitive Ansible data at rest.

Example:

```bash
ansible-vault encrypt group_vars/production/vault.yml
```

The encrypted file can be stored in Git if your organization's security model permits it.

But:

```text
Encrypted file
+
Vault password
```

must not be stored together insecurely.

---

# 57. Vault Is Not Runtime Isolation

After decryption:

```text
Secret
↓
Exists in memory/runtime
↓
May be passed to module/application
```

Therefore Vault does not eliminate runtime secret-handling requirements.

---

# 58. External Secret Systems

Organizations may use systems such as:

```text
Cloud secret managers

Enterprise vault systems

Credential brokers

Certificate authorities
```

Conceptually:

```text
Ansible
↓
Authenticated Identity
↓
Secret System
↓
Required Secret
↓
Task
```

This can avoid storing some secrets inside the Ansible repository entirely.

---

# 59. Prefer Secret Retrieval at the Necessary Boundary

Instead of:

```text
Secret copied everywhere
```

prefer:

```text
Authorized workload
↓
Retrieve required secret
↓
Use it for required purpose
```

Minimize:

```text
Copies

Lifetime

Scope

Exposure
```

---

# 60. Secret Logging

Be careful with:

```yaml
ansible.builtin.debug:
```

registered variables,

```text
-vvv
```

diff output,

callback plugins,

CI logs,

and failure messages.

Secrets can escape encryption through logging.

# 64. Check Mode Before Change

Where useful:

```bash
ansible-playbook \
  -i inventories/production/aws_ec2.yml \
  playbooks/site.yml \
  --check
```

This can help predict supported changes.

But remember:

```text
Check Mode
≠
Guaranteed Deployment Result
```

---

# 65. Diff Review

For supporting modules:

```bash
ansible-playbook \
  -i inventories/production/aws_ec2.yml \
  playbooks/site.yml \
  --check \
  --diff
```

This may reveal configuration changes before deployment.

But never assume diff output is safe for secret-bearing content.

---

# 66. Review the Change Set

Before production:

```text
Expected:
web01 changed
web02 changed
web03 changed
```

Unexpected:

```text
database01 changed
bastion01 changed
monitoring01 changed
```

Stop.

Investigate.

Unexpected scope is itself a production warning.

---

# 67. Blast Radius

Blast radius means:

```text
How much of the system can this change affect if it goes wrong?
```

Examples:

```text
One file

One host

One availability zone

One service

All web servers

Entire production estate
```

Good production engineering tries to reduce unnecessary blast radius.

---

# 68. Blast-Radius Reduction

Techniques include:

```text
Specific host patterns

--limit

serial

Environment isolation

Account isolation

Small pull requests

Canary hosts

Maintenance windows

Rolling deployment

Separate failure domains
```

---

# 69. Rolling Changes

Instead of:

```text
100 servers
↓
Change all 100 simultaneously
```

use:

```text
Batch 1
↓
Verify
↓
Batch 2
↓
Verify
↓
Batch 3
```

when the service architecture supports it.

---

# 70. Serial Deployment

Example:

```yaml
---
- name: Update production application
  hosts: "environment_production:&role_application"
  serial: 2

  roles:
    - application
```

Only a batch is processed at a time.

---

# 71. Serial Is Not Automatically Zero Downtime

If you have:

```text
2 servers
```

and:

```yaml
serial: 2
```

both may be changed in the same batch.

If both become unavailable:

```text
Outage.
```

Batch size must reflect capacity and architecture.

---

# 72. Failure Domains

A failure domain is a boundary within which failures may be correlated.

Examples:

```text
Host

Rack

Availability zone

Region

Cluster

Database shard
```

Do not design rolling deployment without understanding failure domains.

---

# 73. Availability-Zone Awareness

Imagine:

```text
AZ-A
web01
web02

AZ-B
web03
web04
```

A poor batch could update:

```text
web01 + web02
```

together.

If AZ-B is already degraded, risk increases.

Production rollout design should understand topology.

---

# 74. Canary Deployment Concept

Start with a small representative subset.

```text
Canary Host
↓
Deploy
↓
Verify
↓
Observe
↓
Continue
```

If canary fails:

```text
STOP
```

before affecting the whole fleet.

---

# 75. Maintenance Windows

Some changes should only happen during:

```text
Approved time periods
```

because they may involve:

```text
Restart

Capacity reduction

Database maintenance

Kernel changes

Network interruption
```

The window should be part of the operational plan.

---

# 76. Maintenance Window Is Not a Safety Mechanism by Itself

Running a dangerous change at 2 a.m. does not make it safe.

You still need:

```text
Testing

Review

Recovery

Monitoring

Staff availability
```

---

# 77. Idempotency

Production configuration management depends heavily on safe convergence.

Desired:

```text
Current State
↓
Ansible
↓
Desired State
```

Second run:

```text
Desired State
↓
Ansible
↓
No Unnecessary Change
```

---

# 78. Why Idempotency Matters Operationally

Suppose host 27 fails halfway through a deployment.

After correcting the cause, you want:

```text
Rerun
```

to be safe.

Idempotent automation allows already-correct hosts to remain correct while incomplete hosts converge.

---

# 79. Non-Idempotent Automation Makes Recovery Hard

Imagine:

```yaml
ansible.builtin.shell: echo "entry" >> /etc/example.conf
```

Every rerun adds another line.

Then recovery becomes:

```text
Failure
↓
Rerun
↓
More Damage
```

That is poor production automation.

---

# 80. Configuration Drift

Configuration drift occurs when actual system state diverges from intended state.

Example:

```text
Git says:
worker_processes auto;

Server says:
worker_processes 1;
```

The managed node has drifted.

---

# 81. Causes of Drift

Common causes:

```text
Manual SSH changes

Emergency fixes

Unmanaged scripts

Package updates

Application installers

Cloud-init

Other automation tools

Configuration management bugs

Security tools

Vendor agents
```

---

# 82. Drift Is Not Always Malicious

Sometimes an engineer manually changes a server because:

```text
Production is down.
```

The manual change may be necessary.

The problem begins when:

```text
Emergency change
```

never returns to:

```text
Managed configuration.
```

---

# 83. Drift Detection

Possible approaches include:

```text
Scheduled check-mode runs

Configuration monitoring

File-integrity monitoring

Compliance scanning

Periodic Ansible reconciliation

External observability
```

The correct approach depends on system criticality.

---

# 84. Drift Remediation

When drift is found:

```text
Detect
↓
Understand
↓
Determine Authoritative State
↓
Update Code If Necessary
↓
Review
↓
Apply
↓
Verify
```

Do not automatically overwrite every difference without understanding why it exists.

---

# 85. Desired State Must Be Authoritative

Suppose emergency response discovers that:

```text
Git configuration is wrong.
```

An engineer manually fixes production.

The answer is not:

```text
Run old Ansible again and break it.
```

Instead:

```text
Emergency Fix
↓
Validate
↓
Update Ansible Source
↓
Review
↓
Reconcile Fleet
```

---

# 86. Emergency Manual Changes

Sometimes production incidents require:

```text

```

This should be controlled.

```text

Why

When

Hosts

Follow-up required
```

---

# 87. Reconciliation

After emergency action:

```text

↓

↓
Update Automation
↓
Test
↓
Review
↓
Deploy
↓
```

A snowflake server is a server whose state depends on undocumented manual history.

Example:

```text

because

```

Ansible exists partly to prevent this.

```text
↓

↓
```


# 93. Service Restart Design

Restarting services is not a trivial detail.

Ask:

```text
Does this change require restart?

Can service reload instead?

Will restart interrupt traffic?

How long does restart take?

Can multiple servers restart together?

What if restart fails?
```

---

# 94. Reload vs Restart

Some services support:

```text
Reload
```

which may apply configuration with less disruption.

Others require:

```text
Restart
```

Never assume reload semantics without checking the actual service.

---

# 95. Handler Design

Handlers should represent actions triggered by meaningful changes.

Example:

```yaml
- name: Deploy Nginx configuration
  ansible.builtin.template:
    src: nginx.conf.j2
    dest: /etc/nginx/nginx.conf
    owner: root
    group: root
    mode: "0644"
  notify: Reload Nginx
```

Handler:

```yaml
- name: Reload Nginx
  ansible.builtin.service:
    name: nginx
    state: reloaded
```

---

# 96. Do Not Notify Restart for Unrelated Changes

Changing:

```text
Static HTML
```

usually should not automatically restart Nginx.

Handlers should correspond to actual operational requirements.

---

# 97. Validate Before Restart

For critical configuration:

```text
Render
↓
Validate
↓
Install
↓
Notify
↓
Reload / Restart
↓
Verify
```

Do not replace a working configuration with invalid syntax and discover the problem only after the service dies.

```text
↓

↓

↓

↓

↓

↓

↓
```

# 100. Minimal-Downtime Changes

```text
↓
```

```text
↓

↓

↓

↓

↓

↓
```

# 102. Load-Balancer Drain

Removing a server from new traffic does not always mean:

```text

```

Existing connections may still exist.

A proper drain strategy may need:

```text

Wait for active requests

Confirm connection state

Perform change
```

Exact behavior depends on the load balancer and application.

# 124. Partial Failure

Imagine:

```text
web01 changed successfully
web02 changed successfully
web03 failed
web04 untouched
web05 untouched
```

You now have a mixed fleet.

That is a real production state.

---

# 125. Questions After Partial Failure

Ask:

```text
Are web01 and web02 healthy?

Is web03 serving traffic?

Was web03 drained?

Did handlers run?

Are untouched nodes healthy?

Are versions compatible?

Can the playbook safely rerun?

Should we continue?

Should we recover changed hosts?
```

Do not make a decision based only on:

```text
PLAY RECAP failed=1
```

---

# 126. Safe Partial-Failure Recovery

Possible pattern:

```text
Stop
↓
Verify Healthy Nodes
↓
Investigate Failed Host
↓
Fix Root Cause
↓
Test Failed Host
↓
Rerun Limited Scope
↓
Verify
↓
Resume Remaining Batches
```

Part 15 commands such as:

```text
--limit
```

may help narrow recovery scope.

---

# 127. Example Limited Recovery

```bash
ansible-playbook \
  -i inventories/production/aws_ec2.yml \
  playbooks/deploy.yml \
  --limit web03
```

Only do this when:

```text
The playbook supports safe targeted execution.
```

---

# 128. `--start-at-task`

This can be useful during carefully understood recovery:

```bash
ansible-playbook \
  playbooks/deploy.yml \
  --start-at-task "Deploy application artifact"
```

But it bypasses earlier tasks.

Those earlier tasks may establish required state.

Use it only when you understand the dependency chain.

---

# 129. Tags During Recovery

Example:

```bash
ansible-playbook \
  playbooks/site.yml \
  --tags application
```

Again:

```text
Convenient
≠
Automatically Safe
```

Tagged tasks must be designed to function independently if operators will use them that way.

```text

Deploy Previous Application Version
```

Which one is correct depends on the failure.

# 131. Fix Forward

Sometimes the safest recovery is:

```text

↓

```

rather than reversing everything.

Example:

```text

↓

↓

↓
```

# 132. Rollback

Rollback may work when state is genuinely reversible.

Example:

```text

↓

```

But database/schema/data changes may make this impossible.

Never promise rollback without testing it.

```text

↓

↓

↓

↓
```

This depends on architecture.

```text
12,000 lines
```

```text
Poor ownership

Difficult testing

Huge blast radius

Difficult reuse

Difficult review
```

Shell remains appropriate for cases where shell behavior is actually required.


# 172. Production Anti-Pattern: `no_log` Everywhere

`no_log: true` can protect sensitive output.

But applying it indiscriminately destroys useful diagnostics.

Use it where secrets require it.

Do not use it to hide poor automation.

# 176. Production Anti-Pattern: Secrets in Inventory

# 177. Production Anti-Pattern: Restart Everything


# 218. From Tutorial Ansible to Production Ansible

At the beginning of this series, the model was:

```text
Engineer
↓
Ansible
↓
Server
```

It is now:

```text
Organization
↓
Standards
↓
Git
↓
Code
↓
Testing
↓
Security
↓
Review
↓
Approval
↓
Controlled Runtime
↓
Identity
↓
Inventory
↓
Ansible
↓
Managed Infrastructure
↓
Verification
↓
Monitoring
↓
Operations
↓
Feedback
```

That is production configuration management.

The goal is no longer:

```text
Can Ansible make the change?
```

The production question is:

```text
Can we make the correct change,
to the correct systems,
using the correct identity,
with the correct dependencies,
at the correct time,
at a controlled blast radius,
prove that it worked,
recover if it did not,
understand exactly what happened,
and maintain the system safely afterward?
```

If the answer is yes, you are moving beyond Ansible tutorials.

You are doing **Production Ansible Engineering and Operations**.
