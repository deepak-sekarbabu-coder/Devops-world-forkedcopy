# Part 5: Ad Hoc Commands and Ansible Modules

## Learn Ansible Interactively Before Building Large Playbooks

In Part 4, you learned how Ansible identifies infrastructure through inventory.

You now understand:

```text
Control Node
↓
Inventory
↓
Host Pattern
↓
Managed Hosts
```

But knowing which servers exist is only half of the story.

Now Ansible needs to do something to those servers.

You might want to:

```text
Test connectivity

Check uptime

Inspect disk space

Create a directory

Copy a file

Install a package

Create a user

Start a service

Download a file

Call an HTTP endpoint
```

You could immediately begin writing playbooks.

But that would hide an important part of how Ansible works.

Before building larger automation, you should learn how to interact with Ansible directly.

That is the purpose of:

# Ad Hoc Commands

The Part 5 learning path is:

```text
Inventory
↓
Select Hosts
↓
Choose Module
↓
Provide Module Arguments
↓
Execute
↓
Read Result
↓
Determine Changed / Unchanged / Failed / Unreachable
↓
Verify
```

And our practical progression will be:

```text

↓
Inspect Uptime
↓
Create Directory
↓
Copy File
↓
Install Package
↓
Start Service
↓
Verify Service
```

By the end of this part, an Ansible command should no longer look like mysterious CLI syntax.

When you see:

```bash
ansible web -i inventory/hosts.yml -m ansible.builtin.ping
```

you should mentally break it into:

```text
ansible
↓
Run an ad hoc Ansible operation

web
↓
Target the web inventory group

-i inventory/hosts.yml
↓
Use this inventory

-m ansible.builtin.ping
↓
Execute the ping module
```

That mental model is the foundation for understanding playbook tasks later.

---

# 1. What Is an Ad Hoc Command?

An ad hoc command is a direct Ansible command used to perform an operation without first creating a playbook.

For example:

```bash
ansible web -i inventory/hosts.yml -m ansible.builtin.ping
```

This tells Ansible:

```text
Use inventory/hosts.yml
↓
Find hosts matching web
↓
Connect to those hosts
↓
Execute ansible.builtin.ping
↓
Return results
```

You did not create a YAML playbook.

You asked Ansible to perform the operation directly from the command line.

---

# 2. Why Ad Hoc Commands Exist

Sometimes you need a quick operation.

For example:

```text
Are these servers reachable?

How long have they been running?

Does this file exist?

What kernel are they running?

Is this service running?

Can Ansible authenticate to this host?

What user is Ansible operating as?
```

Creating an entire playbook for a quick investigation may be unnecessary.

An ad hoc command lets you interact with the infrastructure immediately.

---

# 3. When Ad Hoc Commands Are Useful

Ad hoc commands are particularly useful for:

```text
Connectivity testing

Investigation

Troubleshooting

One-time administrative operations

Small controlled changes

Inventory verification

Module experimentation

Learning module behavior

Emergency inspection
```

They are excellent for learning because they expose the basic Ansible execution model.

---

# 4. When Ad Hoc Commands Are Not Enough

Imagine your deployment requires:

```text
Create user
↓
Create directories
↓
Install packages
↓
Copy configuration
↓
Start application
↓
Configure service
↓
Verify endpoint
```

You could execute six or more ad hoc commands manually.

But now you have problems:

```text
Where is the automation documented?

Can another engineer reproduce it?

What order should commands run?

Which variables were used?

What happens if step 4 fails?

Can Git review the automation?

Can CI/CD execute it consistently?
```

That is where playbooks become much better.

Think:

```text
Ad Hoc Commands
↓
Interactive / Immediate Operations
```

and:

```text
Playbooks
↓
Repeatable / Version-Controlled Automation
```

Ad hoc commands teach you the building blocks that playbooks will organize.

# 8. Basic Ad Hoc Command Structure

The general mental model is:

```text
ansible
<host-pattern>
-i <inventory>
-m <module>
-a '<module-arguments>'
<additional-options>
```

For example:

```bash
ansible web \
  -i inventory/hosts.yml \
  -m ansible.builtin.command \
  -a 'uptime'
```

Read it as:

```text
ansible
↓
Use the ad hoc CLI

web
↓
Target hosts matching web

-i inventory/hosts.yml
↓
Use this inventory

-m ansible.builtin.command
↓
Use command module

-a 'uptime'
↓
Pass uptime as module arguments
```

# 9. The Host Pattern

Immediately after:

```text
ansible
```

you normally provide a host pattern.

Example:

```bash
ansible web ...
```

Here:

```text
web
```

is the pattern.

From Part 4, you already know patterns can represent:

```text
One host

A group

Several groups

An intersection

An exclusion

All hosts
```

---

# 10. Target One Host

Example:

```bash
ansible web01 -i inventory/hosts.yml -m ansible.builtin.ping
```

Target:

```text
web01
```

Before running:

```bash
ansible web01 -i inventory/hosts.yml --list-hosts
```

Verify the host is what you expect.

---

# 11. Target a Group

Example:

```bash
ansible web -i inventory/hosts.yml -m ansible.builtin.ping
```

Target:

```text
web
```

Every inventory host matching the `web` pattern can be selected.

---

# 12. Target All Hosts

```bash
ansible all -i inventory/hosts.yml -m ansible.builtin.ping
```

This may target every host in the inventory.

Be careful.

The fact that a command is short does not mean its blast radius is small.

Before a production operation:

```bash
ansible all -i inventory/hosts.yml --list-hosts
```

Ask:

> Do I actually intend to operate on every host?

---

# 13. Complex Patterns Still Work

For example:

```bash
ansible 'web:&production' \
  -i inventory/hosts.yml \
  -m ansible.builtin.ping
```

Conceptually:

```text
web
AND
production
```

Or:

```bash
ansible 'web:!production' \
  -i inventory/hosts.yml \
  -m ansible.builtin.ping
```

Conceptually:

```text
web
MINUS
production
```

Always quote complex patterns so your shell does not interpret special characters unexpectedly.

---

# 14. Inventory Selection

The option:

```text
-i
```

means inventory.

Example:

```bash
-i inventory/hosts.yml
```

So:

```bash
ansible web -i inventory/hosts.yml -m ansible.builtin.ping
```

means:

```text
Find web
↓
inside inventory/hosts.yml
↓
then execute ping
```

---

# 15. Module Selection

The option:

```text
-m
```

selects the module.

Example:

```bash
-m ansible.builtin.ping
```

Therefore:

```bash
ansible web \
  -i inventory/hosts.yml \
  -m ansible.builtin.ping
```

uses:

```text
ansible.builtin.ping
```

against the selected hosts.

---

# 16. Module Arguments

The option:

```text
-a
```

passes arguments to the selected module.

Example:

```bash
ansible web \
  -i inventory/hosts.yml \
  -m ansible.builtin.command \
  -a 'uptime'
```

Here:

```text
uptime
```

is passed to:

```text
ansible.builtin.command
```

# 17. First Command Anatomy

Study this carefully:

```bash
ansible web \
  -i inventory/hosts.yml \
  -m ansible.builtin.command \
  -a 'uptime'
```

Breakdown:

| Part                      | Meaning              |
| ------------------------- | -------------------- |
| `ansible`                 | Ad hoc Ansible CLI   |
| `web`                     | Host pattern         |
| `-i`                      | Inventory option     |
| `inventory/hosts.yml`     | Inventory source     |
| `-m`                      | Module selection     |
| `ansible.builtin.command` | Module               |
| `-a`                      | Module arguments     |
| `'uptime'`                | Command module input |

Do not memorize the whole line as one sentence.

Understand its pieces.

Examples include modules for:

```text

Files

Directories

Packages

Services

Users

Groups

Downloads

HTTP requests
```

Think:

```text
Ansible
↓
Select Module
↓
Module Knows How to Perform a Particular Operation

```

When you ask Ansible to:


# 21. Fully Qualified Collection Names

You will frequently see module names written like:

```text
ansible.builtin.copy
```

This is a:

# Fully Qualified Collection Name

or:

```text
FQCN
```

Its structure is:

```text
namespace.collection.module
```

For example:

```text
ansible.builtin.command
```

means:

```text
ansible
↓
namespace

builtin
↓
collection

command
↓
module
```

```text
ansible.builtin
```

```text
ansible.builtin.user

ansible.builtin.group

ansible.builtin.get_url

ansible.builtin.debug
```

# 23. Short Names vs FQCNs

You may see:

```bash
-m ping
```

instead of:

```bash
-m ansible.builtin.ping
```

For built-in modules, short names commonly work.

However, throughout this series we will usually prefer:

```text
ansible.builtin.ping
```

because the FQCN makes module ownership explicit and helps avoid ambiguity when different collections contain similarly named plugins or modules.

# 24. Why Collections Matter

Ansible's ecosystem contains collections.

A collection can contain:

```text

Roles

Plugins

Playbooks
```

Therefore, not every module belongs to:

```text

```

Later you may encounter modules such as those belonging to cloud, networking, Kubernetes, database, or vendor collections.

The FQCN tells you where functionality comes from.

# 30. Lab 1: Ping Hosts

First verify the target:

```bash
ansible web \
  -i inventory/hosts.yml \
  --list-hosts
```

Then:

```bash
ansible web \
  -i inventory/hosts.yml \
```

```text
web01 | SUCCESS => {

    "ping": "pong"

```

---

# 31. `ansible.builtin.ping` Is Not ICMP Ping

This distinction is essential.

Linux:

```bash
ping 192.0.2.10
```

normally tests network reachability using ICMP.

Ansible:

```bash
ansible web01 \
  -i inventory/hosts.yml \
  -m ansible.builtin.ping
```

does something different.

Conceptually:

```text
Ansible
↓
Connect to managed host
↓
Verify usable remote Python
↓
Execute test module
↓
Return pong
```

It is an Ansible connectivity/module execution test.

---

# 32. What a Successful Ansible Ping Tells You

A successful result gives confidence that important parts of the Ansible path are working:

```text
Inventory targeting

Connection

Authentication

Usable Python for the module

Basic module execution

Result return path
```

It does not prove every future operation will work.

For example, it does not prove:

```text
sudo works

package repositories work

service exists

application is healthy

firewall rules are correct
```

---

# 33. Understanding `SUCCESS`

You may see:

```text
SUCCESS
```

This means the module operation completed successfully for that host.

But success does not necessarily mean infrastructure changed.

Look at:

```text
"changed": false
```

or:

```text
"changed": true
```

---

# 34. `changed`

Ansible modules commonly report whether an operation changed managed state.

Example:

```text
"changed": false
```

means the operation reports no managed-state change.

Example:

```text
"changed": true
```

means the operation reports that it changed something.

This distinction becomes central to Ansible.

---

# 35. Changed Does Not Mean Success vs Failure

These are different questions:

```text
Did operation succeed?
```

and:

```text
Did operation change state?
```

You can have:

```text
SUCCESS
changed=false
```

or:

```text
SUCCESS
changed=true
```

Both can be successful.

---

# 36. Idempotency

Now we introduce one of the most important Ansible concepts:

# Idempotency

An operation is idempotent when repeatedly applying the same desired state does not keep making unnecessary changes once that state is already satisfied.

Example desired state:

```text
Directory /opt/veriqta exists
```

First run:

```text
Directory absent
↓
Ansible creates it
↓
changed=true
```

Second run:

```text
Directory already exists correctly
↓
No change required
↓
changed=false
```

That is the behavior we want from state-aware automation.

---

# 37. Idempotent Module Mental Model

```text
Desired State
↓
Inspect Current State
↓
Already Correct?
├── Yes → No Change
└── No → Make Required Change
↓
Return Result
```

This is very different from blindly executing commands.

# 40. Why Can `command` Report Changed?

Ansible cannot generally infer the semantic effect of an arbitrary command.

For example:

```text
uptime
```

is read-only.

But:

```text
useradd bob
```

changes state.

The command module cannot universally understand the intent of every executable.

Therefore, arbitrary command execution does not provide the same state-awareness as purpose-built modules.

This is one reason you should prefer specific modules when they exist.

---

# 41. Command Return Values

Command-like modules may return useful fields such as:

```text
rc

stdout

stderr

stdout_lines

stderr_lines

cmd

start

end

delta
```

Understanding these makes troubleshooting much easier.

---

# 42. `rc`

`rc` means:

```text
return code
```

or process exit status.

For conventional Unix commands:

```text
0
```

usually indicates success.

A nonzero value generally indicates another outcome or error, although individual programs define their own exit-code semantics.

Never assume every nonzero value has the same meaning.

Read the command's documentation.

---

# 43. `stdout`

`stdout` means:

```text
standard output
```

This is where a program normally writes its normal output.

Example:

```bash
uptime
```

may write uptime information to stdout.

Ansible can return that information in:

```text
stdout
```

---

# 44. `stderr`

`stderr` means:

```text
standard error
```

Programs commonly use it for error or diagnostic output.

Example:

```bash
cat /file/that/does/not/exist
```

may write an error message to stderr.

Ansible can expose it as:

```text
stderr
```

---

# 45. Why `stdout` and `stderr` Matter

When a command fails, do not read only:

```text
FAILED
```

Inspect:

```text
rc

stdout

stderr
```

These often tell you why.

Troubleshooting flow:

```text
FAILED
↓
Read message
↓
Read rc
↓
Read stderr
↓
Read stdout
↓
Identify failing program
↓

```

# 46. Failure Lab: Nonexistent Command

On a disposable lab host:

```bash

  -i inventory/hosts.yml \
```

---

# 47. `command` Does Not Use a Shell

This is critical.

`ansible.builtin.command` does not process the command through a remote shell.

Therefore shell features such as:

```text
|

>

<

*

;

&
```

do not behave as shell syntax.

For example:

```bash
ansible web \
  -i inventory/hosts.yml \
  -m ansible.builtin.command \
  -a 'cat /etc/passwd | grep root'
```

does not mean:

```text
run cat
↓
pipe output
↓
grep root
```

in the way a shell would interpret it.

---

# 48. Why `command` Avoids a Shell

Skipping the shell makes execution more predictable and reduces risks associated with shell parsing.

When shell features are unnecessary, prefer:

```text
ansible.builtin.command
```

over:

```text
ansible.builtin.shell
```

---

# 49. `shell` Module

The module:

```text
ansible.builtin.shell
```

runs commands through a shell on the managed node.

Example:

```bash
ansible web \
  -i inventory/hosts.yml \
  -m ansible.builtin.shell \
  -a 'printf "%s\n" "hello" | grep hello'
```

Now the pipe is interpreted by the shell.

---

# 50. Command vs Shell

The fundamental distinction is:

```text
command
↓
Execute program directly
↓
No shell processing
```

versus:

```text
shell
↓
Execute through shell
↓
Shell syntax available
```

---

# 51. When to Use `command`

Use `command` when you simply need to execute a program.

Examples:

```bash
uptime
```

```bash
whoami
```

```bash
uname -r
```

```bash
hostname
```

No shell features are required.

---

# 52. When `shell` May Be Required

Shell functionality may be needed for operations involving:

```text
Pipes

Redirection

Shell operators

Shell-specific expressions

Certain shell expansions
```

Example:

```bash
cat /var/log/example.log | grep ERROR
```

But do not use `shell` merely because you are familiar with Bash.

---

# 53. Shell Security Risk

Imagine a variable enters:

```text
shell command
```

without safe handling.

Shell metacharacters can change what is executed.

Therefore:

```text
User-controlled input
+
shell parsing
=
potential command injection risk
```

Rule:

> Use `command` unless you actually require shell behavior, and treat variable input to shell operations as security-sensitive.

---

# 54. Better Than Command When a Module Exists

Suppose you want to create:

```text
/opt/veriqta
```

You could run:

```bash
mkdir -p /opt/veriqta
```

using `command`.

But Ansible has:

```text
ansible.builtin.file
```

which understands file-system state.

Prefer the purpose-built module.

---

# 55. Idempotent Module vs Raw Command

Compare:

```bash
mkdir /opt/veriqta
```

with:

```text
file:
  path=/opt/veriqta
  state=directory
```

The first means:

```text
Execute mkdir
```

The second means:

```text
Ensure this path is a directory
```

That difference is central to configuration management.

---

# 56. Imperative Thinking

```text
Run:
mkdir /opt/veriqta
```

means:

> Perform this operation.

---

# 57. Desired-State Thinking

```text
path=/opt/veriqta
state=directory
```

means:

> Make sure this state is true.

That is closer to how Ansible should normally be used.

---

```text
ansible.builtin.file
```

Creating:

```text
/opt/veriqta
```

The option:

```text

```

means:

```text

```

It tells Ansible to use privilege escalation according to the configured become method and settings.

# 61. Privilege Escalation

Your SSH user may be:

```text
ansible
```

but the operation may need:

```text
root
```

Conceptually:

```text
SSH as ansible
↓
Privilege escalation
↓
Perform privileged operation
```

Ansible calls this:

```text
become
```

---

# 62. `--become`

Long form:

```bash
--become
```

Short form:

```bash
-b
```

Example:

```bash
ansible web \
  -i inventory/hosts.yml \
  --become \
  -m ansible.builtin.file \
  -a 'path=/opt/veriqta state=directory'
```

---

# 63. Become Password

Some environments require a password for privilege escalation.

The CLI can prompt for it using:

```text
--ask-become-pass
```

short form:

```text
-K
```

Example:

```bash
ansible web \
  -i inventory/hosts.yml \
  -b \
  -K \
  -m ansible.builtin.package \
  -a 'name=nginx state=present'
```

Do not put sudo passwords directly into shell history.

# 64. Verify Directory Creation

After creating the directory:


# 103. Parallelism

Ansible can operate on multiple hosts in parallel.

The CLI option:

```text
-f
```

or:

```text
--forks
```

controls the number of parallel worker processes Ansible uses for the operation.

Example:

```bash
ansible web \
  -i inventory/hosts.yml \
  -f 10 \
  -m ansible.builtin.ping
```

Conceptually:

```text
Selected Hosts
↓
Parallel Workers
↓
Operations executed across hosts
```

---

# 104. Why Parallelism Matters

Imagine:

```text
1 host
```

versus:

```text
500 hosts
```

Sequential execution could be unnecessarily slow.

Parallelism improves throughput.

But more concurrency is not always better.

---

# 105. Parallelism and Production Risk

Increasing concurrency can increase pressure on:

```text
SSH infrastructure

Bastion hosts

Package repositories

APIs

Databases

Load balancers

Shared storage

Applications
```

For example:

```text
Restart service on 100 web servers simultaneously
```

could cause an outage.

The command may be technically valid.

The operational strategy may be terrible.

Parallelism is therefore both:

```text
Performance concern
+
Reliability concern
```

# 108. Check Mode Concept

Ansible provides:

```text
--check
```

often called:

```text
check mode
```

The idea is:

```text
What would Ansible change?
```

without intentionally applying supported changes.

Example:

```bash
ansible web \
  -i inventory/hosts.yml \
  -b \
  --check \
  -m ansible.builtin.file \
  -a 'path=/opt/check-mode-demo state=directory'
```

---

# 109. Check Mode Is Not Magic

Not every module supports check mode equally.

Some support it fully.

Some partially.

Some cannot meaningfully predict an arbitrary operation.

For example, arbitrary command execution is fundamentally difficult to simulate.

Therefore:

> Check mode is useful evidence, not a guarantee of future behavior.

Always inspect the module's documentation for check-mode support.

```text

```

can provide limited state-awareness.



# 112. Modules First, Commands Second

Use this decision process:

```text

↓

├── Yes → Prefer module
```

```text

```

means the module reports that managed state changed.

Example:

```text

```

means it reports no state change.

# 116. `failed`

A failed operation indicates that the task/module operation did not complete successfully according to Ansible's result evaluation.

You may see output such as:

```text

```

Read the accompanying result.

Look for:

```text
msg

rc

stderr

exception information where present
```

---

# 117. `unreachable`

`UNREACHABLE` is especially important.

It means Ansible could not successfully reach/use the host through the configured connection path.

Possible causes:

```text
Wrong ansible_host

DNS failure

Network route failure

Firewall

SSH port closed

Wrong SSH user

Wrong SSH key

Authentication failure

Host offline
```

This is different from a module reaching the host and then failing.

---

# 118. Failed vs Unreachable

Think:

```text
UNREACHABLE
↓
Could not establish/use required connection path
```

versus:

```text
FAILED
↓
Reached execution stage but requested operation failed
```

This distinction speeds up troubleshooting.

---

# 119. `skipped`

A result may be:

```text
SKIPPED
```

when Ansible intentionally does not execute an operation under the current conditions.

You will see this more often when learning:

```text
Conditions

Check mode

Playbooks

Tags

Platform-specific tasks
```

A skipped task is not automatically an error.

---

# 120. Result-State Mental Model

```text
Host Selected
↓
Can Ansible Reach It?
├── No → UNREACHABLE
└── Yes
    ↓
    Should Operation Run?
    ├── No → SKIPPED
    └── Yes
        ↓
        Did Operation Succeed?
        ├── No → FAILED
        └── Yes
            ↓
            Did State Change?
            ├── Yes → changed=true
            └── No → changed=false
```

This mental model will become extremely useful when reading playbook output.

# 121. Exit Codes

At the operating-system level, programs return exit codes.

Conventionally:

```text
0
↓
success
```

while nonzero values usually indicate another condition or failure.

For example:

```bash
ansible web \
  -i inventory/hosts.yml \
  -m ansible.builtin.command \
  -a 'true'
```

should execute a command that returns success.

Whereas:

```bash
ansible web \
  -i inventory/hosts.yml \
  -m ansible.builtin.command \
  -a 'false'
```

returns a nonzero command status and Ansible will normally treat the operation as failed.

---

# 122. Module Result vs Ansible CLI Exit Status

Do not confuse:

```text
Remote command rc
```

with:

```text
ansible CLI process exit status
```

The remote program may return an `rc` as part of its module result.

Separately, the local `ansible` CLI itself exits with a status that can be used by:

```text
Shell scripts

CI/CD pipelines

Automation wrappers
```

Later, when automating Ansible itself, both layers matter.

# 131. Common Mistake: Wrong Pattern

You run:

```bash
ansible webs ...
```

but the group is:

```text
web
```

Do not change the pattern to:

```text
all
```

just to make something happen.

Verify:

```bash
ansible web -i inventory/hosts.yml --list-hosts
```

---

# 132. Common Mistake: Forgetting `-b`

You attempt:

```text
Install package
```

as an unprivileged user.

The module fails due to permissions.

Do not assume package management is broken.

Ask:

```text
Does this operation require privilege escalation?
```

Then use appropriate become configuration.

---

# 133. Common Mistake: Using `-b` Everywhere

The opposite is also bad.

Do not elevate every operation automatically.

Principle:

```text
Least privilege
```

Use elevated privileges only where required.

Read-only operations such as:

```text
uptime
```

normally do not need root.

---

# 134. Common Mistake: Confusing Local and Remote Paths

With:

```text
copy
```

you need to understand where:

```text
src
```

and:

```text
dest
```

exist.

Conceptually:

```text
src
↓
control side
```

```text
dest
↓
managed node
```

Confusing those locations is a common beginner error.

---

# 135. Common Mistake: Using Shell Pipes With `command`

This will not behave like a shell pipeline:

```bash
-m ansible.builtin.command \
-a 'ps aux | grep nginx'
```

because `command` does not invoke a shell.

If shell parsing is genuinely required:

```bash
-m ansible.builtin.shell \
-a 'ps aux | grep nginx'
```

But first ask whether a more structured module or command can solve the problem safely.

---

# 136. Common Mistake: Assuming `changed=true` Means Something Is Wrong

For a mutating first run:

```text
changed=true
```

may be exactly correct.

Example:

```text
Directory absent
↓
Directory created
↓
changed=true
```

The important question is:

> Was the change expected?

---

# 137. Common Mistake: Ignoring Repeated Changes

Suppose the same state-aware operation reports:

```text
changed=true
```

every single run.

Investigate.

Possible explanations include:

```text
Task genuinely changes every time

Wrong module choice

Incorrect desired state

External process reverting configuration

Module behavior

Non-idempotent argument combination
```

Repeated unexpected changes are an operational signal.

---

# 138. Common Mistake: Treating Check Mode as Proof

A clean check-mode run does not guarantee the real execution will succeed.

Real execution may still encounter:

```text
Package repository failure

Disk full

Permission issue

Service startup failure

Network outage

API failure

Dependency problem
```

Check mode is valuable, but it is not a substitute for verification.

---

# 139. Common Mistake: Ignoring Module Documentation

Bad workflow:

```text
Search random example
↓
Copy command
↓
Run in production
```

Better:

```text
Identify module
↓
ansible-doc
↓
Official documentation
↓

↓

↓
```

# 140. Common Mistake: Using Raw Commands for Package Installation

Poor:

```bash
ansible web \
  -b \
  -m ansible.builtin.shell \
  -a 'apt-get install -y nginx'
```

Better on an appropriate Debian-family system:

```bash
ansible web \
  -b \
  -m ansible.builtin.apt \
  -a 'name=nginx state=present'
```

The second expresses desired package state.

# 141. Common Mistake: Restarting Services Without Need

This:

```text
restart service
```

can interrupt traffic.

Do not restart a service merely because you changed something somewhere.

Later, Ansible handlers will teach you how to trigger service actions only when relevant configuration changes.

For now, understand that:

```text
restart
```

has operational consequences.

# 184. Knowledge Check

## Question 1

What is an ad hoc Ansible command?

### Answer

A direct command-line Ansible operation executed against selected hosts without first creating a playbook.

---

## Question 2

Which CLI command is commonly used for ad hoc operations?

### Answer

```text
ansible
```

---

## Question 3

What comes after `ansible` in the basic ad hoc command structure?

### Answer

A host pattern.

---

## Question 4

What does `-i` specify?

### Answer

The inventory source.

---

## Question 5

What does `-m` specify?

### Answer

The Ansible module.

---

## Question 6

What does `-a` provide?

### Answer

Arguments for the selected module.

---

## Question 7

What is an Ansible module?

### Answer

A unit of functionality Ansible uses to perform a particular type of operation against a target or within the automation workflow.

---

## Question 8

What is an FQCN?

### Answer

A Fully Qualified Collection Name identifying a plugin or module by namespace, collection, and name.

Example:

```text
ansible.builtin.copy
```

---

## Question 9

Why use FQCNs?

### Answer

They make module ownership explicit, improve documentation linking, and reduce ambiguity with similarly named content from other collections.

## Question 10

What does `ansible.builtin.ping` test?

### Answer

Basic Ansible connectivity and the ability to execute the ping module using usable Python on the managed node. It is not ICMP ping.

---

## Question 11

What is idempotency?

### Answer

The property where repeatedly applying the same desired state does not continue making unnecessary changes after the desired state has been reached.

---

## Question 12

What does `changed=true` mean?

### Answer

The module reports that it changed managed state.

---

## Question 13

Does `changed=false` mean failure?

### Answer

No. It often means the desired state was already satisfied.

---

## Question 14

What is the difference between `command` and `shell`?

### Answer

`command` executes a program without remote shell processing, while `shell` executes the command string through a shell and therefore supports shell syntax such as pipes and redirection.

---

## Question 15

Which should generally be preferred when shell features are unnecessary?

### Answer

`ansible.builtin.command`.

---

## Question 16

Why?

### Answer

It avoids unnecessary shell parsing and is generally more predictable and safer.

---

## Question 17

Should `command` be preferred over a purpose-built state-aware module?

### Answer

Usually no. If a suitable module models the resource or desired state, use that module.

What does `-b` mean?

### Answer

Prompt for the privilege-escalation password when required.

What does `-e` provide?

### Answer

Extra variables.

## Question 32

Why should secrets not normally be supplied directly through `-e` on a shell command line?

### Answer

They may become visible through shell history, process inspection, logs, or CI output.

---

## Question 33

What does `-f` control?

### Answer

The number of forks, or parallel worker processes used for execution.

---

## Question 34

Why can excessive parallelism be dangerous?

### Answer

It can overload shared infrastructure or cause too many disruptive changes simultaneously.

---

## Question 35

What does `--check` do?

### Answer

Requests check mode, allowing supporting modules to predict changes without intentionally applying them.

---

## Question 36

Does every module fully support check mode?

### Answer

No.

---

## Question 37

Does check mode guarantee that the real run will succeed?

### Answer

No.

---

## Question 38

What is `stdout`?

### Answer

Standard output produced by a program.

---

## Question 39

What is `stderr`?

### Answer

Standard error or diagnostic output produced by a program.

---

## Question 40

What is `rc`?

### Answer

The return code of the executed command where applicable.

---

## Question 41

What does `UNREACHABLE` generally indicate?

### Answer

Ansible could not successfully establish or use the configured connection to the host.

---

## Question 42

What does `FAILED` generally indicate?

### Answer

The requested operation reached an execution stage but failed according to Ansible's result evaluation.

---

## Question 43

Why are `UNREACHABLE` and `FAILED` important to distinguish?

### Answer

They point to different troubleshooting layers: connection problems versus operation/module problems.

---

## Question 44

What does `SKIPPED` mean?

### Answer

Ansible intentionally did not execute the operation under the current conditions.

---

## Question 45

How should you verify a service?

### Answer

At multiple relevant layers: package/state, process/service state, network availability where applicable, and ultimately the application's meaningful health or endpoint behavior.

# 190. The Most Important Part 5 Rule

Do not ask:

> What shell command can I make Ansible run?

Ask:

> Is there an Ansible module that already understands the resource I want to manage?

That question leads to better automation.

Instead of:

```text
shell → mkdir
```

think:

```text
file → state=directory
```

Instead of:

```text
shell → apt install
```

think:

```text
apt/package → state=present
```

Instead of:

```text
shell → useradd
```

think:

```text
user → state=present
```

Instead of:

```text
shell → systemctl start
```

think:

```text
service/systemd_service → state=started
```

That is the beginning of real configuration management.
