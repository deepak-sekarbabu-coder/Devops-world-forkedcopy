# Part 18: Ansible in CI/CD: Automated Configuration Delivery

## Move Ansible From an Engineer's Terminal Into a Controlled Pipeline

Up to this point, you have learned how to:

* write Ansible playbooks
* build inventories
* use variables and facts
* create roles
* manage dependencies
* protect secrets
* test automation
* troubleshoot failures
* control rolling execution
* discover AWS infrastructure dynamically

You can now run something like:

```bash
ansible-playbook \
  -i inventory/production.aws_ec2.yml \
  playbooks/site.yml
```

from an engineer's terminal.

Technically, that works.

Operationally, it creates an important question:

```text
Who is allowed to run it?

From which computer?

Using which Ansible version?

Using which collection versions?

Against which inventory?

Using which credentials?

Was the code reviewed?

Did the tests pass?

Was production approval granted?

Which Git commit was deployed?

Who deployed it?

When was it deployed?

What happened?

Was the deployment verified?
```

If the answer is:

```text
We trust the engineer to remember everything.
```

you do not yet have a strong production delivery system.

Part 18 changes that.

We move from:

```text
Engineer
↓
Terminal
↓
ansible-playbook
↓
Production
```

to:

```text
Git Push
↓
CI
↓
YAML Validation
↓
Ansible Syntax Check
↓
ansible-lint
↓
Security / Secret Scan
↓
Role Tests
↓
Check / Test Environment
↓
Review
↓
Approval
↓
Ansible Playbook
↓
Managed Infrastructure
↓
Verification
```

This is **Automated Configuration Delivery**.

---

# 1. What CI/CD Means for Ansible

CI/CD is commonly associated with application code.

For example:

```text
Developer
↓
Git
↓
Build
↓
Test
↓
Package
↓
Deploy
```

But Ansible automation is also code.

A playbook can:

```text
Create users

Change sudo policy

Install packages

Replace configuration files

Restart services

Change application versions

Modify security settings

Deploy credentials

Configure hundreds of servers
```

A mistake in application code may break an application.

A mistake in infrastructure automation may break:

```text
Every application server simultaneously.
```

That makes automated validation especially important.




# 23. Separate Validation and Deployment Runners

A strong design may separate:

```text
Untrusted Validation
```

from:

```text
Trusted Deployment
```

For example:

```text

↓

↓
Lint / Syntax / Tests
```

then after merge and approval:

```text

↓
Trusted Private Runner
↓

```

This limits where production credentials are available.

---

# 24. Never Give Pull Requests Production Credentials Automatically

This is especially important when repositories accept changes from:

```text

External contributors

Large engineering teams
```

Unreviewed code should not automatically gain access to:

```text

Production Vault passwords

```

Validation and privileged deployment should be separate trust stages.

# 28. Why Version Pinning Matters

Imagine Monday:

```text
ansible-core version A
```

Friday:

```text
ansible-core version B
```

Your pipeline silently installs the newest version each run.

A change in behavior may make:

```text
Same Git commit
```

produce:

```text
Different automation behavior.
```

That weakens reproducibility.

# 41. Empty Inventory Is Not Success

Suppose a production deployment targets:

```text
environment_production:&role_web
```

but discovers zero hosts.

The playbook may have nothing to do.

That does not necessarily mean:

```text

```

The pipeline should know whether zero targets are expected.

For production, often they are not.

# 42. Preflight Assertions

You can create explicit guardrails.

For example:

```yaml
- name: Require production target group
  hosts: localhost
  gather_facts: false

  tasks:
    - name: Verify production web hosts were discovered
      ansible.builtin.assert:
        that:
          - groups['environment_production'] is defined
          - groups['role_web'] is defined
        fail_msg: Expected production inventory groups were not discovered.
```

More sophisticated checks may validate actual target counts or metadata.


# 62. Check Mode in CI

Run:

```bash
ansible-playbook \
  -i inventory/test/hosts.yml \
  playbooks/site.yml \
  --check
```

Check mode asks supporting modules to predict what they would change without applying those changes.

---

# 63. Check Mode Is a Simulation

Do not interpret:

```text
Check mode passed
```

as:

```text
Deployment will definitely succeed.
```

Some modules:

```text
Fully support check mode
```

others:

```text
Partially support it
```

and some:

```text
Cannot predict useful behavior.
```

Tasks depending on earlier runtime changes may also behave differently.

---

# 64. Example Check-Mode Limitation

Imagine:

```text
Task 1
Create directory

Task 2
Write file into directory
```

During a normal run:

```text
Directory created
↓
File written
```

In check mode, Task 1 may predict creation without actually creating it.

Task 2 may then behave differently because the directory does not physically exist.

That is why check mode is useful evidence, not proof.

---

# 65. Diff Mode

You may combine:

```bash
ansible-playbook \
  -i inventory/test/hosts.yml \
  playbooks/site.yml \
  --check \
  --diff
```

This can show proposed changes for modules supporting diff mode.

Very useful for:

```text
Templates

Configuration files
```

---

# 66. Diff Output Can Leak Secrets

Imagine a template contains:

```text
DATABASE_PASSWORD
API_TOKEN
PRIVATE_KEY
```

`--diff` could expose sensitive before/after content.

For secret-bearing tasks, consider:

```yaml
diff: false
```

and appropriate:

```yaml
no_log: true
```

where necessary.

CI logs are not a safe secret store.

---

# 67. Idempotency Testing

A core configuration-management test is:

```text
Apply
↓
Apply Again
```

The second run should normally produce:

```text
changed=0
```

for stable state.

---

# 68. Why Second Apply Matters

First run:

```text
changed=17
```

may be completely correct.

The server needed configuration.

Second run:

```text
changed=0
```

demonstrates that the playbook recognizes the desired state.

If second run repeatedly reports:

```text
changed=8
```

investigate.

# 69. Common Idempotency Failures

Examples:

```text
shell command always runs

timestamp inserted into template

command rewrites file every run

service restarted unconditionally

random value generated every run

download performed without state check
```

Idempotency testing catches automation that looks successful but creates unnecessary change.

# 90. OIDC Concept

OpenID Connect allows a CI platform to present an identity token to a cloud provider.

Conceptually:

```text
CI Job
↓
OIDC Token
↓
AWS IAM Trust Policy
↓
Assume Role
↓
Temporary AWS Credentials
↓
Deployment
↓
Credentials Expire
```

No permanent AWS access key needs to be stored in the repository's CI secret store for that workflow.

---

# 91. OIDC Does Not Mean "No Authentication"

OIDC replaces one authentication pattern with another.

AWS must still determine:

```text
Which CI identities do I trust?

Which repository?

Which branch?

Which environment?

Which role?

Which permissions?
```

The trust relationship must be restrictive.

---

# 92. OIDC Trust Boundary

Bad concept:

```text
Any workflow
from any repository
↓
Production AWS Role
```

Better:

```text
Approved Repository
+
Approved Branch / Environment
+
Expected OIDC Claims
↓
Production Deployment Role
```

Cloud IAM policy still determines what that role can do.

---

# 93. GitHub Actions OIDC Permissions

A GitHub Actions workflow that needs an OIDC token uses:

```yaml
permissions:
  id-token: write
  contents: read
```

`id-token: write` allows the job to request an OIDC token.

It does not by itself grant permission to modify AWS.

AWS still decides whether the token may assume the requested role.

---

# 94. AWS OIDC Flow

```text
↓

↓

↓
AWS STS
↓

↓
Assume IAM Role
↓
Temporary AWS Credentials
↓

```

```bash

ansible --version

echo "Checking inventory..."
ansible-inventory \
  -i inventory/development.aws_ec2.yml \
```

---

# 108. Why `set -euo pipefail`?

For Bash scripts:

```text
-e
```

helps stop after command failures.

```text
-u
```

helps detect unset variables.

```text
-o pipefail
```

helps pipelines fail when an earlier piped command fails.

This reduces silent shell-script failures.

It does not replace explicit error handling for complex deployment logic.

# 109. Deployment Script

`scripts/deploy.sh`:

```bash
#!/usr/bin/env bash
set -euo pipefail

ENVIRONMENT="${1:?environment required}"

case "$ENVIRONMENT" in
  development|staging|production)
    ;;
  *)
    echo "Unsupported environment: $ENVIRONMENT" >&2
    exit 1
    ;;
esac

INVENTORY="inventory/${ENVIRONMENT}.aws_ec2.yml"

echo "Validating target inventory..."

ansible-inventory \
  -i "$INVENTORY" \
  --graph

echo "Running preflight..."

ansible-playbook \
  -i "$INVENTORY" \
  playbooks/preflight.yml

echo "Deploying..."

ansible-playbook \
  -i "$INVENTORY" \
  playbooks/site.yml

echo "Verifying..."

ansible-playbook \
  -i "$INVENTORY" \
  playbooks/verify.yml
```

This script still relies on external controls for:

```text
Authentication

Approval

Secret management

Environment protection
```

Do not bury those controls inside a shell script.

# 132. GitHub Actions vs Jenkins

| ----------------- | --------------------------- | -------------------------- |

The engineering principles do not.

# 154. Retry vs Recovery

```text

↓

```

```text

↓
```

# 155. Rollback Concepts

Rollback sounds simple:

```text
Deploy old version.
```

Infrastructure configuration makes it more complicated.

Some changes are easily reversible:

```text
Application artifact version
```

Some are not:

```text
Database migration

Deleted data

Package upgrade with incompatible state

Security key rotation

OS upgrade
```

Therefore:

```text
Rollback
```

must be designed, not assumed.

---

# 156. Git Revert Is Not Infrastructure Rollback

Suppose:

```text
Commit A
```

changes a service configuration.

You deploy it.

Then:

```bash
git revert
```

creates a commit restoring old code.

That does not automatically restore:

```text
Every external side effect
```

caused by the original deployment.

Git state and infrastructure state are related but not identical.

# 157. Recovery-First Thinking

Before production deployment ask:

```text
What could fail?

Can we safely rerun?

Can we restore the previous application version?

Can we restore the previous configuration?

Are backups available?

Will handlers behave safely?

Will the database remain compatible?

Can unhealthy nodes remain drained?
```

That is production engineering.


```text

↓

↓

```

Do not invent rollback behavior for an application that does not support it.

# 180. Production Preflight

```yaml

          - tags.Role == 'web'
```

# 182. Verification Playbook

```yaml
---
- name: Verify deployed application
  hosts: "environment_production:&role_web"
  gather_facts: false

  tasks:
    - name: Wait for application port
      ansible.builtin.wait_for:
        host: 127.0.0.1
        port: "{{ application_port }}"
        timeout: 60

    - name: Check health endpoint
      ansible.builtin.uri:
        url: "http://127.0.0.1:{{ application_port }}/health"
        status_code: 200
      register: health

    - name: Confirm health
      ansible.builtin.assert:
        that:
          - health.status == 200
```

```text
Failure
```

```text
Fake success.
```

Do not write wrapper scripts that accidentally swallow failures.
