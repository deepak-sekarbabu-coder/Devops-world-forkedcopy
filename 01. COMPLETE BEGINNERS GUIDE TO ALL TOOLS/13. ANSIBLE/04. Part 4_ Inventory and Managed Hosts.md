# Part 4: Inventory and Managed Hosts

## Learn How Ansible Knows What Infrastructure It Controls

In Part 2, you installed Ansible and connected to a managed node.

In Part 3, you learned to read YAML as structured data.

Now we answer one of the most important questions in Ansible:

> How does Ansible know which servers exist, how to reach them, and which servers belong together?

The answer is:

# Inventory

Ansible inventory describes the managed infrastructure Ansible can target.

A useful first mental model is:

```text
Engineer
↓
Ansible
↓
Inventory
↓
Which hosts exist?
↓
How do I connect to them?
↓
Which groups do they belong to?
↓
Which variables apply to them?
↓
Target Selected Hosts
↓
Run Automation
```

Without a useful inventory, Ansible may be installed perfectly and your playbook may be valid, but Ansible still needs to know which infrastructure you intend to manage.

---

# 1. What Is Ansible Inventory?

An inventory is Ansible's representation of managed hosts and groups of managed hosts.

For example, imagine that your infrastructure contains:

```text
web01
web02
app01
db01
```

Ansible needs a structured way to know these systems exist.

An inventory can describe them.

For example:

```ini
[web]
web01
web02

[application]
app01

[database]
db01
```

You have now created three groups:

```text
web

application

database
```

and assigned hosts to them.

---

# 2. Inventory Is More Than a Server List

A beginner may think:

```text
Inventory
=
list of IP addresses
```

That is incomplete.

Inventory can describe:

```text
Hosts

Groups

Group relationships

Connection addresses

SSH users

SSH ports

Python interpreters

Environment membership

Host-specific variables

Group-specific variables

Connection configuration
```

Inventory therefore helps answer:

```text
WHAT HOST?
↓
web01

WHERE?
↓
192.0.2.10

HOW DO I CONNECT?
↓
SSH

WHICH USER?
↓
ansible

WHICH PORT?
↓
22

WHICH ENVIRONMENT?
↓
production

WHICH ROLE?
↓
web
```

---

# 3. Inventory Does Not Create Infrastructure

This distinction matters.

Suppose inventory contains:

```yaml
web:
  hosts:
    web01:
      ansible_host: 192.0.2.10
```

This does not create a server at:

```text
192.0.2.10
```

It describes a host that Ansible can attempt to manage.

Think:

```text
Terraform
↓
May create infrastructure
```

while:

```text
Ansible Inventory
↓
Describes managed targets to Ansible
```

Ansible can certainly participate in provisioning workflows, but merely adding something to inventory does not create it.

---

# 4. Inventory and the Control Node

Recall the architecture:

```text
Engineer
↓
Ansible Control Node
↓
Inventory
↓
Managed Nodes
```

Inventory lives on the control side of the automation relationship.

Ansible reads inventory before deciding which managed nodes should receive an operation.

---

# 5. Inventory Architecture

Our Part 4 architecture is:

```text
Inventory
│
├── development
│
├── staging
└── production
    │
    ├── web
    ├── application
    └── database
```

But this diagram introduces two different ways of classifying servers.

One dimension is:

```text
ENVIRONMENT
↓
development
staging
production
```

Another is:

```text
FUNCTION
↓
web
application
database
```

A host can belong to more than one group.

For example:

```text
prod-web-01
```

might belong to:

```text
production
+
web
```

This becomes extremely useful.

---

# 6. Why Inventory Groups Matter

Suppose you have:

```text
100 servers
```

You do not want to manually type every hostname whenever you deploy something.

Instead:

```text
web
↓
all web servers
```

or:

```text
production
↓
all production servers
```

or through patterns:

```text
web:&production
```

which conceptually means:

```text
hosts in web
AND
hosts in production
```

This is one of the reasons inventory becomes powerful.

---

# 7. Static Inventory

A static inventory is manually defined and maintained.

For example:

```ini
[web]
web01
web02

[database]
db01
```

The infrastructure list does not automatically discover itself.

Someone or some process updates the inventory when hosts change.

Static inventory is excellent for learning because you can see exactly what Ansible is reading.

---

# 8. Static Inventory vs Dynamic Inventory

Static inventory:

```text
Engineer maintains host definitions
↓
Inventory file
↓
Ansible
```

Dynamic inventory:

```text
External infrastructure source
↓
Inventory plugin
↓
Discover infrastructure
↓
Ansible
```

Dynamic sources can become useful when infrastructure changes frequently.

Examples might include infrastructure information obtained from:

```text
Cloud providers

CMDB systems

External inventory systems
```

We will not build dynamic inventory yet.

First master static inventory.

# 13. Read the Inventory

The inventory says:

```text
web
├── web01
└── web02

application
└── app01

database
└── db01
```

This tells Ansible about logical inventory names.

It does not yet necessarily tell Ansible how DNS or networking resolves those names.

---

# 14. Hosts

A host is an individual inventory target.

Examples:

```text
web01

web02

app01

db01
```

Each inventory hostname should uniquely identify that host inside Ansible's inventory model.

---

# 15. Inventory Hostname vs Real Network Address

This distinction is extremely important.

Suppose:

```text
web01
```

is your friendly inventory name.

The actual server address might be:

```text
192.0.2.10
```

You can represent that relationship:

```ini
[web]
web01 ansible_host=192.0.2.10
```

Now:

```text
web01
↓
Inventory identity
```

while:

```text
192.0.2.10
↓
Connection destination
```

---

# 16. `ansible_host`

`ansible_host` tells Ansible the host name or address to use when connecting when it differs from the inventory name.

Example:

```ini
[web]
web01 ansible_host=192.0.2.10
```

Conceptually:

```text
Ansible target
↓
web01

Connection address
↓
192.0.2.10
```

This gives you stable, meaningful inventory names without forcing those names to be directly resolvable by DNS.

---

# 17. Host Aliases

Consider:

```ini
[web]
prod-web-01 ansible_host=192.0.2.10
```

Here:

```text
prod-web-01
```

acts as the inventory hostname.

The connection destination is:

```text
192.0.2.10
```

You can therefore run:

```bash
ansible prod-web-01 -i inventory/inventory.ini -m ansible.builtin.ping
```

Ansible resolves the inventory entry and attempts the connection using its associated connection information.

---

# 18. Why Use Friendly Inventory Names?

Compare:

```text
10.10.30.17
```

with:

```text
prod-payments-web-01
```

The second name communicates more context.

Useful naming can help identify:

```text
Environment

Application

Function

Instance number
```

For example:

```text
dev-web-01

stg-web-01

prod-web-01

prod-web-02

prod-app-01

prod-db-01
```

Good names improve readability and troubleshooting.

---

# 19. IP Addresses as Inventory Hosts

You can use an IP address directly:

```ini
[web]
192.0.2.10
192.0.2.11
```

Then the inventory hostname itself is the address.

This can be fine for small labs.

But larger environments often benefit from meaningful aliases.

---

# 20. DNS Names

You can also use resolvable DNS names:

```ini
[web]
web01.example.internal
web02.example.internal
```

If your control node can resolve those names and reach them, Ansible can use them as connection targets.

---

# 21. Three Common Host Models

## Direct IP

```ini
[web]
192.0.2.10
```

## DNS name

```ini
[web]
web01.example.internal
```

## Inventory alias plus address

```ini
[web]
web01 ansible_host=192.0.2.10
```

The third pattern is useful when you want the Ansible identity to remain meaningful even if the underlying connection address changes.

---

# 22. `ansible_user`

Ansible also needs to know which remote user should be used for the connection.

Example:

```ini
[web]
web01 ansible_host=192.0.2.10 ansible_user=ansible
```

Conceptually:

```text
Inventory Host
↓
web01

Network Destination
↓
192.0.2.10

Remote Login User
↓
ansible
```

---

# 23. `ansible_port`

SSH normally uses port:

```text
22
```

But a host might expose SSH on another port.

Example:

```ini
[web]
web01 ansible_host=192.0.2.10 ansible_user=ansible ansible_port=2222
```

Connection model:

```text
web01
↓
192.0.2.10
↓
TCP 2222
↓
SSH
↓
ansible user
```

Do not change SSH ports merely because an example uses a custom port.

Your inventory must describe your actual environment.

---

# 24. SSH Private Key Configuration

A host may require a particular private key.

A connection variable commonly used for this purpose is:

```text
ansible_ssh_private_key_file
```

For example:

```ini
[web]
web01 ansible_host=192.0.2.10 ansible_user=ansible ansible_ssh_private_key_file=~/.ssh/ansible_lab
```

The private key stays on the control node.

Never copy private SSH keys onto managed servers merely to make Ansible work.

---

# 25. SSH Key Permissions

On Linux and macOS, SSH commonly expects private keys to have restrictive permissions.

For example:

```bash
chmod 600 ~/.ssh/ansible_lab
```

Then inspect:

```bash
ls -l ~/.ssh/ansible_lab
```

Never make a private key world-readable just to solve a permissions error.

Bad troubleshooting:

```bash
chmod 777 ~/.ssh/ansible_lab
```

That weakens security instead of fixing the underlying problem correctly.

---

# 26. Python Interpreter Configuration

Many Ansible modules require Python on a managed Linux node.

Ansible normally performs interpreter discovery, but there are situations where you may need to specify the interpreter explicitly.

For example:

```ini
web01 ansible_host=192.0.2.10 ansible_python_interpreter=/usr/bin/python3
```

This tells Ansible which Python interpreter should be used for that host.

Do not hardcode this unnecessarily across every host.

Use it when your environment requires explicit interpreter selection.

---

# 27. Connection Variables Together

A lab host could look like:

```ini
[web]
web01 ansible_host=192.0.2.10 ansible_user=ansible ansible_port=22 ansible_ssh_private_key_file=~/.ssh/ansible_lab ansible_python_interpreter=/usr/bin/python3
```

This works conceptually, but it is becoming difficult to read.

That introduces an important inventory design principle:

> Do not duplicate shared configuration on every host when it logically belongs to a group.

---

# 28. Group Variables in INI Inventory

Suppose every host in the `web` group uses:

```text
ansible_user = ansible
```

Instead of:

```ini
[web]
web01 ansible_host=192.0.2.10 ansible_user=ansible
web02 ansible_host=192.0.2.11 ansible_user=ansible
```

you can express shared group configuration:

```ini
[web]
web01 ansible_host=192.0.2.10
web02 ansible_host=192.0.2.11

[web:vars]
ansible_user=ansible
```

Now both hosts inherit the group variable.

---

# 29. Host Variables vs Group Variables

Think:

```text
GROUP VARIABLE
↓
shared by hosts in group
```

while:

```text
HOST VARIABLE
↓
specific to one host
```

For example:

```ini
[web]
web01 ansible_host=192.0.2.10
web02 ansible_host=192.0.2.11 ansible_port=2222

[web:vars]
ansible_user=ansible
```

Here:

```text
ansible_user
↓
shared
```

while:

```text
web02 ansible_port
↓
host-specific
```

---

# 30. Do Not Turn Inventory Into a Giant Configuration File

Inventory can contain variables.

That does not mean every application variable should be shoved into the main inventory file.

As projects grow, separate:

```text
Inventory structure
↓
hosts/groups

Variables
↓
group_vars/
host_vars/
```

This usually creates cleaner projects.


```yaml

```

```text

↓
```

```text
├── web
│   ↓
│   hosts
│   ├── web01
│   └── web02
│
```

# 34. INI vs YAML Inventory

INI:

```ini
[web]
web01 ansible_host=192.0.2.10
web02 ansible_host=192.0.2.11
```

YAML:

```yaml
---
all:
  children:
    web:
      hosts:
        web01:
          ansible_host: 192.0.2.10
        web02:
          ansible_host: 192.0.2.11
```

Both can represent the same conceptual inventory.

---

# 35. Which Inventory Format Should You Use?

For a small inventory, INI can be very easy to read.

For larger hierarchical inventory, YAML can make complex relationships clearer.

YAML also provides clearer data typing.

For this series, you should understand both.

In larger examples, we will often favor YAML because Part 3 has already taught you how to reason about its structure.

---

# 36. Important INI Variable Typing Difference

Do not assume INI inventory variable values behave exactly like YAML values in every location.

INI inventory has context-specific parsing behavior.

That can produce confusing type differences.

For example, inline host variables and variables in an INI `:vars` section are not necessarily interpreted identically.

This is another reason YAML inventory can be easier when explicit data typing matters.

Engineering rule:

> Never guess the resulting variable type. Inspect what Ansible actually loaded.

Later we will use:

```bash
ansible-inventory
```

for exactly that reason.

# 40. Multiple Classification Dimensions

Suppose:

```text

```

belongs to:

```text

+
production
+
linux
+
aws
```

This is not duplication of the host.

It is multiple group membership.

That allows you to reason about infrastructure from different perspectives.

---

# 41. Grouping by What, Where, and When

A useful production inventory model considers several dimensions.

## What?

```text
web
database
application
monitoring
```

## Where?

```text
us_east
eu_west
datacenter_a
```

## When?

```text
development
staging
production
```

This is much more scalable than creating arbitrary groups without a clear model.

---

# 42. Child Groups

A group can contain other groups.

For example:

```text
production
↓
web
application
database
```

But be careful.

If the same functional group contains hosts from multiple environments, simply making `web` a child of `production` would incorrectly make every web host production.

Your hierarchy must represent reality.

---

# 43. Environment-Specific Child Groups

A safer model might be:

```text
production
├── production_web
├── production_application
└── production_database
```

Then:

```text
web
```

can also aggregate:

```text
development_web
staging_web
production_web
```

This gives you two classification dimensions without incorrectly mixing environments.

---

# 44. Production Inventory Architecture

A stronger architecture is:

```text
all
│
├── development
│   ├── development_web
│   ├── development_application
│   └── development_database
│
├── staging
│   ├── staging_web
│   ├── staging_application
│   └── staging_database
│
└── production
    ├── production_web
    ├── production_application
    └── production_database
```

Then functional parent groups can aggregate corresponding environment-specific groups:

```text
web
├── development_web
├── staging_web
└── production_web
```

and similarly for:

```text
application

database
```

---

# 45. Why This Architecture Is Useful

You can now answer different questions.

Target:

```text
production
```

to select production infrastructure.

Target:

```text
web
```

to select web infrastructure across environments.

Target an intersection:

```text
web:&production
```

to select only web hosts that are also in production.

This is much more expressive.

---

# 46. Parent Groups

A parent group contains child groups.

Conceptually:

```text
production
↓
PARENT

production_web
production_application
production_database
↓
CHILDREN
```

Hosts belonging to child groups are also members of the parent group through that hierarchy.

---

# 47. Child Groups in INI

INI uses the `:children` modifier.

Example:

```ini
[production_web]
prod-web-01
prod-web-02

[production_application]
prod-app-01

[production_database]
prod-db-01

[production:children]
production_web
production_application
production_database
```

Now `production` is a parent group.

---

# 48. Child Groups in YAML

Equivalent conceptual structure:

```yaml
---
all:
  children:
    production:
      children:
        production_web:
          hosts:
            prod-web-01:
            prod-web-02:

        production_application:
          hosts:
            prod-app-01:

        production_database:
          hosts:
            prod-db-01:
```

YAML makes the hierarchy visually obvious.

# 49. Group Hierarchy

Think:

```text
all
↓
production
↓
production_web
↓
prod-web-01
```

This introduces variable precedence.

We will study variable precedence deeply later.

For now, understand that group hierarchy affects which variables may apply to a host.

# 59. Group-Level Connection Variables

Suppose every Linux server uses:

```text
ansible
```

as its automation user.

Instead of repeating:

```yaml
ansible_user: ansible
```

on every host, create a shared group.

Example:

```yaml
all:
  children:
    linux:
      vars:
        ansible_user: ansible
      hosts:
        web01:
          ansible_host: 192.0.2.10
        app01:
          ansible_host: 192.0.2.20
```

Now both hosts receive the shared variable through group membership.

---

# 60. Why Group Variables Reduce Duplication

Bad pattern:

```text
100 hosts
×
same ansible_user
×
same interpreter
×
same common settings
```

Better:

```text
Group
↓
Shared variables
↓
Hosts inherit appropriate values
```

This makes configuration easier to review and change.

---

# 61. But Do Not Overgeneralize

Suppose most Linux servers use:

```text
ansible_user: ansible
```

but one legacy server requires:

```text
ansible_user: automation
```

Do not force the shared value onto the exception.

The host can have host-specific configuration.

Inventory should describe reality, not pretend every server is identical.

---

But do not place something in `all` merely because it is convenient.

Only put values there when they genuinely apply across the inventory.

`host_vars` and `group_vars` discovery depends on where Ansible is looking for inventory/playbook-relative variable files.

# 68. Inventory Precedence Introduction

A host may receive variables from multiple places.

For example:

```text
all
↓
production
↓
production_web
↓
prod-web-01
```

Suppose all four levels define:

```text
application_port
```

Which value wins?

That is a variable precedence question.

Ansible has defined precedence behavior.

We will study the complete precedence model later.

For now, remember:

> The same variable can be defined at multiple levels, so you must know where a final value came from.

---

# 69. Simple Precedence Mental Model

For inventory-related reasoning, you will often encounter a progression conceptually like:

```text
Broad group value
↓
More specific group value
↓
Host-specific value
```

But the complete Ansible precedence system includes many additional sources.

Do not turn this simplified mental model into a universal rule for every Ansible variable source.

Later we will study:

```text
configuration

command-line options

inventory

play variables

task variables

extra variables

and other sources
```

properly.

---

# 70. Why Precedence Matters

Suppose:

```text
group_vars/all.yml
```

contains:

```yaml
application_port: 8080
```

while:

```text
host_vars/prod-web-01.yml
```

contains:

```yaml
application_port: 9090
```

You need to know which value Ansible sees for that host.

Do not guess.

Inspect the host.

# 85. Host Patterns

Ansible uses patterns to determine which inventory hosts should be targeted.

For example:

```bash
ansible web -i inventory/lab.yml --list-hosts
```

Pattern:

```text
web
```

means:

```text
hosts belonging to web
```

---

# 86. Pattern: `all`

```bash
ansible all -i inventory/lab.yml --list-hosts
```

Targets all inventory hosts.

Be careful with this in production.

`all` can represent a very large blast radius.

---

# 87. Pattern: One Host

```bash
ansible web01 -i inventory/lab.yml --list-hosts
```

Targets the inventory host:

```text
web01
```

Remember that patterns use inventory identities.

If:

```text
web01
↓
ansible_host=192.0.2.10
```

then your inventory identity remains `web01`.

---

# 88. Pattern: Multiple Groups

Suppose you want hosts in either:

```text
web
```

or:

```text
application
```

A pattern can combine groups.

For example:

```text
web:application
```

Before executing anything, verify:

```bash
ansible 'web:application' -i inventory/lab.yml --list-hosts
```

Quoting patterns is a good shell habit, particularly as patterns become more complex.

---

# 89. Pattern Union

Conceptually:

```text
web:application
```

means:

```text
web
OR
application
```

The resulting target set includes hosts from either group.

---

# 90. Pattern Intersection

Suppose a host belongs to:

```text
web
```

and:

```text
production
```

You can select the intersection:

```text
web:&production
```

Conceptually:

```text
web
AND
production
```

Use:

```bash
ansible 'web:&production' -i inventory/production.yml --list-hosts
```

---

# 91. Pattern Exclusion

Suppose you want:

```text
web
```

but not:

```text
staging
```

Pattern:

```text
web:!staging
```

Conceptually:

```text
web
MINUS
staging
```

Verify:

```bash
ansible 'web:!staging' -i inventory/hosts.yml --list-hosts
```

---

# 92. Combined Pattern

A more complex example:

```text
web:application:&production:!maintenance
```

Conceptually:

```text
(web OR application)
AND production
EXCLUDING maintenance
```

Complex patterns are powerful.

They are also easy to misunderstand.

Always inspect the resulting host list before making a production change.

---

# 93. Pattern Safety Rule

Before:

```text
restart

upgrade

remove

delete

reconfigure

deploy
```

run:

```bash
ansible '<pattern>' -i <inventory> --list-hosts
```

and inspect the result.

Production automation begins with knowing your blast radius.

---

# 94. Limiting Hosts

Ansible commands and playbook runs can be further restricted with:

```text
--limit
```

or:

```text
-l
```

Suppose a playbook targets:

```yaml
hosts: production
```

but during investigation you only want:

```text
prod-web-01
```

You could use:

```bash
ansible-playbook -i inventory/production.yml site.yml --limit prod-web-01
```

This narrows the selected hosts for that run.

---

# 95. `--limit` Does Not Rewrite the Playbook

Suppose the playbook says:

```yaml
hosts: production
```

and you run:

```bash
ansible-playbook -i inventory/production.yml site.yml --limit production_web
```

Think:

```text
Playbook target
↓
production

LIMIT
↓
production_web

Actual eligible target set
↓
intersection
```

`--limit` narrows the run.

It does not permanently change the playbook.

# 99. Overlapping Groups

Overlapping groups are not inherently a problem.

A server can legitimately belong to:

```text

web

linux

aws

us_east
```

because each group describes a different characteristic.

The problem occurs when overlapping groups define conflicting variables and nobody understands which value applies.

# 100. Good Overlap vs Bad Overlap

```text

group_b
group_c
group_new
misc
special
servers2
```

with no documented purpose.

Production inventory needs meaningful taxonomy.

# 116. Production Inventory Safety

Production inventory should make it difficult to misunderstand:

```text
Which environment am I targeting?

Which hosts are selected?

Which account or network is this?

Which credentials are used?

Which groups overlap?

Which variables apply?
```

Names such as:

```text
prod-web-01
```

can help humans.

But naming is only one layer of protection.

---

# 117. Separate Production Access

A mature environment may separate production through:

```text
Different credentials

Different SSH keys or certificates

Different bastion paths

Different cloud accounts

Different CI/CD environments

Different approval controls

Different inventory sources

Different automation permissions
```

Do not rely solely on a group named:

```text
production
```

as your safety mechanism.

---

# 118. Inventory Security

Inventory can contain sensitive operational information.

Potential examples:

```text
Internal hostnames

Private addresses

SSH usernames

Network topology

Environment names

Connection paths
```

Treat inventory as infrastructure information.

Do not assume it is harmless because it contains no password.

---

# 119. Never Store Private SSH Key Material in Inventory

Do not do this:

```yaml
private_key: |
  -----BEGIN ...
```

Inventory may reference the location of an appropriate key:

```yaml
ansible_ssh_private_key_file: ~/.ssh/ansible_lab
```

but the secret key material itself should not be committed to ordinary inventory.

---

# 120. Never Put Plaintext Passwords Into Git Inventory

Bad:

```yaml
ansible_password: SuperSecretPassword123
```

especially when committed to a normal Git repository.

Later you will learn appropriate secret-management mechanisms such as Ansible Vault and external secret-management approaches.

For now:

```text
Inventory
≠
secret vault
```

---

# 121. Host Variables Can Also Be Sensitive

Moving a secret from:

```text
inventory.yml
```

to:

```text
host_vars/web01.yml
```

does not make it secure.

It is merely in another file.

Security depends on how the secret is protected, not on the directory name.

```bash
ansible all -i inventory/hosts.yml --list-hosts
```

## List group


```bash
ansible 'web:&production' -i inventory/hosts.yml --list-hosts
```

## Exclusion

```bash
ansible 'web:!production' -i inventory/hosts.yml --list-hosts
```

## Connectivity test

```bash
ansible web -i inventory/hosts.yml -m ansible.builtin.ping
```

```bash
ansible web01 -i inventory/hosts.yml -m ansible.builtin.ping -vvvv
```

# 192. Knowledge Check

## Question 1

What is inventory?

### Answer

Ansible's representation of managed hosts, groups, relationships, connection information, and associated inventory variables.

---

## Question 2

Does adding a host to inventory create that server?

### Answer

No. Inventory describes a target; it does not automatically create the infrastructure.

---

## Question 3

What are two common static inventory formats?

### Answer

INI and YAML.

---

## Question 4

What is a host?

### Answer

An individual inventory target known to Ansible.

---

## Question 5

What is a group?

### Answer

A logical collection of inventory hosts or child groups.

---

## Question 6

Can one host belong to several groups?

### Answer

Yes.

---

## Question 7

Why would a production web server belong to both `production` and `web`?

### Answer

The groups describe different dimensions: environment and function.

---

## Question 8

What is a child group?

### Answer

A group included beneath another group.

---

## Question 9

What is a parent group?

### Answer

A group containing child groups.

---

## Question 10

What is `all`?

### Answer

The implicit group representing all hosts in the inventory.

---

## Question 11

What does `ansible_host` represent?

### Answer

The hostname or address Ansible should connect to when it differs from the inventory hostname.

---

## Question 12

What is the difference between `web01` and `ansible_host: 192.0.2.10`?

### Answer

`web01` is the inventory identity. `192.0.2.10` is the connection destination.

---

## Question 13

What does `ansible_user` configure?

### Answer

The remote user used for the connection.

---

## Question 14

What does `ansible_port` configure?

### Answer

The connection port, such as a nondefault SSH port.

---

## Question 15

What does `ansible_ssh_private_key_file` identify?

### Answer

The private SSH key file Ansible should use for the connection.

---

## Question 16

Should private SSH key contents be committed inside inventory?

### Answer

No.

---

## Question 17

What does `ansible_python_interpreter` control?

### Answer

Which Python interpreter Ansible should use on the managed node where applicable.

---

## Question 18

Should it always be hardcoded?

### Answer

No. Ansible can perform interpreter discovery, and explicit configuration should be used when required by the environment.

---

## Question 19

What is `group_vars`?

### Answer

A conventional mechanism for loading variables associated with inventory groups.

---

## Question 20

What is `host_vars`?

### Answer

A conventional mechanism for loading variables associated with individual inventory hosts.

---

## Question 21

Why use group variables?

### Answer

To avoid duplicating values that logically apply to multiple hosts.

---

## Question 22

What is variable precedence?

### Answer

The rules Ansible uses to determine the effective value when the same variable is defined by multiple applicable sources.

---

## Question 23

Do you need to memorize the entire precedence model in Part 4?

### Answer

No. You need to understand that precedence exists and learn to inspect effective host variables rather than guessing.

---

## Question 24

What does `ansible-inventory --graph` do?

### Answer

It displays the inventory group and host hierarchy.

---

## Question 25

What does `ansible-inventory --list` do?

### Answer

It displays Ansible's processed inventory information.

---

## Question 26

What does `ansible-inventory --host web01` do?

### Answer

It displays inventory information and resolved inventory variables for the specified host.

---

## Question 27

What does `--list-hosts` help verify?

### Answer

Which hosts a target pattern matches before executing remote work.

---

## Question 28

What does:

```text
web:application
```

mean conceptually?

### Answer

Hosts in `web` OR `application`.

---

## Question 29

What does:

```text
web:&production
```

mean?

### Answer

Hosts belonging to both `web` and `production`.

---

## Question 30

What does:

```text
web:!production
```

mean?

### Answer

Hosts in `web` excluding hosts in `production`.

---

## Question 31

What does `--limit` do?

### Answer

It further restricts the hosts eligible for a particular command or playbook run.

---

## Question 32

If inventory parsing succeeds, does that prove SSH connectivity?

### Answer

No.

---

## Question 33

If SSH works, does that prove Python is correctly available for all Ansible modules?

### Answer

No.

---

## Question 34

What should you investigate if a pattern matches no hosts?

### Answer

The inventory source, inventory hostname/alias, group names, pattern syntax, and parsed inventory.

---

## Question 35

Why are overlapping groups useful?

### Answer

They allow the same host to be classified across multiple dimensions such as environment, function, location, or platform.

---

## Question 36

When do overlapping groups become confusing?

### Answer

When group purpose is unclear or groups provide conflicting variables without a understood precedence/design model.

---

## Question 37

Why should static inventory be maintained?

### Answer

Because real infrastructure can change while a static inventory remains unchanged, producing stale or missing host definitions.

---

## Question 38

Why can dynamic inventory become useful in cloud environments?

### Answer

Because hosts may be created, replaced, or removed frequently, making manual static inventory maintenance brittle.

---

## Question 39

Is inventory a secret-management system?

### Answer

No.

---

## Question 40

What should you do before running a potentially destructive command against a complex pattern?

### Answer

Inspect the inventory and use `--list-hosts` to verify the exact target set.

# 197. Part 4 Production Rule

Before Ansible changes anything, you should be able to answer:

```text
WHAT INVENTORY?
↓
Which source am I using?

WHAT HOSTS?
↓
Which systems exist in it?

WHAT GROUPS?
↓
How are they classified?

WHAT PATTERN?
↓
Which systems am I selecting?

WHAT ADDRESS?
↓
Where will Ansible connect?

WHAT USER?
↓
Who will Ansible connect as?

WHAT CREDENTIAL?
↓
How will authentication happen?

WHAT VARIABLES?
↓
Which values apply?

WHAT ENVIRONMENT?
↓
Development, staging, or production?

WHAT BLAST RADIUS?
↓
Exactly how many hosts will receive this operation?
```

Only then should the conversation move to:

```text
What task should Ansible execute?
```

```text

Target Pattern Failure
```

The goal is:

That is the inventory foundation required before serious Ansible automation begins.
