# Part 16: Advanced Playbook Engineering and Execution Control

## Move From Simple Automation to Controlled Multi-Server Operations

Up to this point, you have learned how to tell Ansible what state you want.

You can:

* install packages
* manage services
* create users
* deploy files
* render templates
* use variables
* build roles
* manage dependencies
* protect secrets
* test automation
* troubleshoot failures

But production automation introduces another problem:

**How should changes move through a fleet of servers?**

Imagine that you manage 100 application servers.

A playbook that works perfectly on one server can still cause a major outage if it restarts all 100 servers at the same time.

The question is no longer only:

```text
What configuration should this server have?
```

The question becomes:

```text
Which servers should change?

How many should change at once?

In what order?

What happens if one fails?

When should the deployment stop?

Which tasks should happen only once?

Which tasks should run somewhere else?

How do we remove a server from traffic?

How do we wait for existing users to leave?

How do we deploy the change?

How do we restart safely?

How do we verify health?

When is the server allowed back into traffic?

How do we continue to the next server?
```

That is execution control.

This part moves Ansible from:

```text
Configuration Automation
```

toward:

```text
Controlled Production Orchestration
```

---

# 1. The Core Mental Model

A simple playbook often looks like this:

```text
Hosts
↓
Tasks
↓
Configuration
```

Production execution is closer to:

```text
Fleet
↓
Execution Strategy
↓
Concurrency Limit
↓
Batch Selection
↓
Preconditions
↓
Traffic Control
↓
Configuration Change
↓
Controlled Restart
↓
Readiness Wait
↓
Health Verification
↓
Traffic Restoration
↓
Next Batch
↓
Final Verification
```

You are now controlling not only **what** Ansible does but also:

```text
WHEN

WHERE

HOW MANY AT ONCE

IN WHAT ORDER

UNDER WHAT CONDITIONS

WHAT HAPPENS AFTER FAILURE
```

---

# 2. Why Execution Control Matters

Suppose you have:

```text
web01
web02
web03
web04
web05
```

A basic play might target:

```yaml
- name: Update web servers
  hosts: web
```

Without additional controls, multiple hosts may execute tasks concurrently.

That can be perfectly appropriate for:

```text
Installing monitoring agents

Creating users

Deploying harmless files

Collecting information
```

But it can be dangerous for:

```text
Application restarts

Database changes

Load-balancer changes

Cluster maintenance

Rolling upgrades

Stateful systems

Infrastructure maintenance
```

The same automation can be safe or unsafe depending on execution strategy.

---

# 3. Configuration vs Orchestration

Configuration asks:

```text
What should one machine look like?
```

Orchestration asks:

```text
How should multiple machines coordinate while reaching that state?
```

For example:

```text
Configuration:

Install application version 4.2
```

Orchestration:

```text
Remove Server A from traffic
↓
Wait for connections to drain
↓
Install version 4.2
↓
Restart application
↓
Wait for application
↓
Verify health
↓
Return Server A to traffic
↓
Repeat for Server B
```

Part 16 is primarily about the second problem.

---

# 4. Execution Strategies

Ansible uses strategy plugins to decide how tasks progress across hosts.

Two important concepts are:

```text
linear

free
```

Do not confuse strategies with:

```text
serial
forks
throttle
run_once
```

Those affect execution too, but they solve different problems.

---

# 5. Linear Strategy

The standard execution model is:

```yaml
strategy: linear
```

Conceptually:

```text
TASK 1
web01
web02
web03
↓
wait for applicable hosts in the current batch

TASK 2
web01
web02
web03
↓
wait

TASK 3
web01
web02
web03
```

Hosts move through tasks approximately in lockstep within the current batch.

---

# 6. Linear Mental Model

Suppose:

```text
web01 takes 2 seconds
web02 takes 8 seconds
web03 takes 4 seconds
```

for Task 1.

Conceptually:

```text
TASK 1

web01 ── done
web02 ──────── done
web03 ──── done

                 ↓

TASK 2 begins for the batch
```

The faster host does not simply race through every remaining task while slower hosts are still completing earlier tasks.

That is the core idea behind linear execution.

---

# 7. Why Linear Is Useful

Linear execution makes workflows easier to reason about when tasks have sequential relationships.

Examples:

```text
Install package
↓
Deploy configuration
↓
Restart service
↓
Verify service
```

It is particularly useful when:

```text
Execution ordering matters

Hosts should broadly remain aligned

Rolling batches are being used

Failures need predictable boundaries
```

---

# 8. Explicit Linear Example

```yaml
---
- name: Configure web servers
  hosts: web
  strategy: linear

  tasks:
    - name: Install application
      ansible.builtin.package:
        name: example-app
        state: present
      become: true

    - name: Start application
      ansible.builtin.service:
        name: example-app
        state: started
      become: true
```

Because linear is normally the default strategy, explicitly specifying it is often unnecessary.

However, seeing it explicitly helps you understand the execution model.

---

# 9. Free Strategy

The free strategy changes the model.

Example:

```yaml
strategy: free
```

Conceptually:

```text
web01:
Task 1 → Task 2 → Task 3 → Task 4

web02:
Task 1 ─────────→ Task 2 → Task 3 → Task 4

web03:
Task 1 → Task 2 ─────────→ Task 3 → Task 4
```

Each host can progress through the play as quickly as it can.

---

# 10. Linear vs Free

## Linear

```text
Host A ─ Task1 ─ wait ─ Task2 ─ wait ─ Task3
Host B ─ Task1 ──────── Task2 ──────── Task3
Host C ─ Task1 ─── wait Task2 ─── wait Task3
```

## Free

```text
Host A ─ Task1 ─ Task2 ─ Task3 ─ DONE
Host B ───── Task1 ───── Task2 ─ Task3
Host C ─ Task1 ───── Task2 ───── Task3
```

---

# 11. When Free Can Be Useful

The free strategy can be useful when:

```text
Hosts are independent

Some hosts are much slower than others

There is no fleet-wide lockstep requirement

You want hosts to progress independently
```

Examples might include certain:

```text
Independent maintenance jobs

Large heterogeneous fleets

Non-coordinated configuration operations
```

---

# 12. When Free Requires Extra Care

Free execution can make coordinated operations harder to reason about.

Be cautious when:

```text
Hosts depend on each other

Tasks coordinate shared infrastructure

Load-balancer state matters

One host must wait for another

Database migrations interact with application deployment

Strict rolling order matters
```

Do not select a faster strategy simply because it sounds more efficient.

Execution semantics matter more than raw speed.

---

# 13. Forks

Ansible uses worker processes to execute work across hosts.

The number of workers is controlled by:

```text
forks
```

A typical default is:

```text
5
```

Conceptually:

```text
100 hosts
+
forks = 5
↓
At most roughly five host operations can be actively worked on concurrently for the applicable task,
subject to other execution controls.
```

---

# 14. Configuring Forks

In `ansible.cfg`:

```ini
[defaults]
forks = 20
```

Or:

```bash
ansible-playbook \
  -i inventory/production.yml \
  site.yml \
  --forks 20
```

Short form:

```bash
ansible-playbook -f 20 site.yml
```

---

# 15. More Forks Does Not Automatically Mean Better

Increasing forks can increase:

```text
Control-node CPU usage

Memory usage

Network connections

SSH sessions

API calls

Package repository traffic

Load on managed infrastructure
```

You might overwhelm:

```text
Control node

Bastion host

Repository server

API

Database

Load balancer

Network
```

Concurrency is a capacity decision.

---

# 16. Parallelism

Parallelism means multiple operations can happen concurrently.

Do not think only:

```text
More parallel = faster = better
```

Think:

```text
Concurrency
↓
Capacity
↓
Blast Radius
↓
Failure Impact
```

A deployment that finishes in two minutes but takes down every server is not better than one that takes ten minutes safely.

---

# 17. Forks vs Serial

These are different.

`forks` controls worker capacity.

`serial` controls deployment batch size.

Example:

```text
forks = 20
serial = 2
```

The play processes only two hosts in the current batch even though Ansible has capacity for more workers.

---

# 18. `serial`

`serial` is one of the most important production execution controls.

Example:

```yaml
---
- name: Rolling application deployment
  hosts: web
  serial: 1
```

This means:

```text
Process one host through the play
↓
Then move to another host
```

---

# 19. Serial 1

Suppose:

```text
web01
web02
web03
```

With:

```yaml
serial: 1
```

Conceptually:

```text
web01
Task 1
Task 2
Task 3
Verify
↓
web02
Task 1
Task 2
Task 3
Verify
↓
web03
Task 1
Task 2
Task 3
Verify
```

This is useful for conservative rolling changes.

---

# 20. Serial 2

```yaml
serial: 2
```

For:

```text
web01
web02
web03
web04
web05
```

the batches conceptually become:

```text
Batch 1
web01
web02

Batch 2
web03
web04

Batch 3
web05
```

---

# 21. Percentage-Based Serial

You can also use percentages.

Example:

```yaml
serial: "20%"
```

For 100 servers:

```text
Approximately 20 servers per batch
```

The actual batching follows Ansible's serial calculation rules.

---

# 22. Progressive Batch Sizes

Ansible can use a list:

```yaml
serial:
  - 1
  - 5
  - 10
```

Conceptually:

```text
First batch
1 host

Second batch
5 hosts

Remaining batches
10 hosts each
```

This is useful for progressive rollout strategies.

---

# 23. Canary-Like Progression

You might use:

```yaml
serial:
  - 1
  - 5
  - "20%"
```

Conceptually:

```text
Small initial exposure
↓
Larger second batch
↓
Broader rollout
```

This does not by itself create a complete canary deployment system.

You still need:

```text
Verification
Metrics
Failure thresholds
Rollback/recovery
Traffic management
```

---

# 24. Rolling Changes

A rolling change means:

```text
Do not update the entire fleet simultaneously.
```

Instead:

```text
Select Batch
↓
Update
↓
Verify
↓
Continue
```

The goal is to maintain enough healthy capacity while deployment continues.

---

# 25. Batch Deployment

A batch is the current group of hosts being processed.

With:

```yaml
serial: 3
```

a 12-host fleet becomes conceptually:

```text
Batch 1 → 3 hosts
Batch 2 → 3 hosts
Batch 3 → 3 hosts
Batch 4 → 3 hosts
```

Failures can then be evaluated within those batches.

---

# 26. Why Batch Size Matters

Suppose your application needs at least:

```text
8 healthy servers
```

and has:

```text
10 total servers
```

Taking five servers offline simultaneously would violate that capacity requirement.

A safer batch might be:

```text
1
```

or:

```text
2
```

depending on traffic and redundancy.

Batch size is an application-availability decision, not merely an Ansible preference.

---

# 27. `throttle`

`throttle` limits concurrency for a particular:

```text
Task
Block
Play
```

Example:

```yaml
- name: Restart application
  ansible.builtin.service:
    name: example-app
    state: restarted
  become: true
  throttle: 1
```

Even if more hosts could otherwise execute concurrently, this task is restricted.

---

# 28. Why Throttle Exists

Imagine:

```text
serial: 10
forks: 20
```

but a database-related operation should run on only:

```text
2 hosts at a time
```

You can apply:

```yaml
throttle: 2
```

to that operation.

---

# 29. Throttle Cannot Create More Concurrency

Suppose:

```text
forks = 5
serial = 3
throttle = 20
```

You do not get 20 concurrent executions.

The tighter limits still apply.

Think:

```text
forks
serial
throttle
↓
Most restrictive applicable concurrency boundary wins
```

---

# 30. `serial` vs `throttle`

Use `serial` when you want:

```text
The whole play to progress through host batches.
```

Use `throttle` when you want:

```text
A specific task or block to have a smaller concurrency limit.
```

Example:

```yaml
- name: Deploy application
  hosts: web
  serial: 5

  tasks:
    - name: Deploy files
      ansible.builtin.copy:
        src: application/
        dest: /opt/application/
      become: true

    - name: Restart application carefully
      ansible.builtin.service:
        name: application
        state: restarted
      become: true
      throttle: 1
```

---

# 31. `run_once`

Some operations should happen once rather than on every host.

Example:

```yaml
- name: Run database migration
  ansible.builtin.command:
    cmd: /opt/application/migrate-database
  run_once: true
```

But there is an extremely important detail.

---

# 32. `run_once` and Batches

If you combine:

```yaml
serial: 2
```

with:

```yaml
run_once: true
```

the `run_once` task can execute once **for each serial batch**.

This surprises many engineers.

---

# 33. Example

Fleet:

```text
web01
web02
web03
web04
```

Configuration:

```yaml
serial: 2
```

Task:

```yaml
- name: Run migration
  ansible.builtin.command:
    cmd: /opt/application/migrate
  run_once: true
```

Conceptually:

```text
Batch 1
web01 + web02
↓
migration once

Batch 2
web03 + web04
↓
migration once again
```

That may be disastrous if the migration must occur exactly once.

---

# 34. Exactly-Once Thinking

If an operation truly must execute once across the entire play, do not assume `run_once` plus `serial` provides that guarantee.

A common explicit approach is to select a known host conditionally:

```yaml
when: inventory_hostname == ansible_play_hosts_all[0]
```

But even then, ask whether a distributed deployment tool should own an operation requiring strong exactly-once semantics.

For critical database migrations, consider:

```text
Dedicated migration stage
CI/CD orchestration
Database migration tooling
Application-level locking
Advisory locks
Explicit deployment workflow
```

Ansible's `run_once` is an execution directive, not a distributed transaction guarantee.

---

# 35. `run_once` Results

Another important detail:

The result and facts from a `run_once` task are normally applied to hosts in the current batch.

Do not assume the registered result behaves exactly like an ordinary per-host task.

Test the data structure you intend to use.

---

# 36. Delegation

Normally:

```yaml
hosts: web
```

means tasks execute against:

```text
web hosts
```

But sometimes a task related to `web01` must actually execute somewhere else.

That is delegation.

---

# 37. `delegate_to`

Example:

```yaml
- name: Remove server from load balancer
  ansible.builtin.command:
    cmd: "/usr/local/bin/lb-remove {{ inventory_hostname }}"
  delegate_to: loadbalancer01
```

The play may target:

```text
web01
```

while this task executes on:

```text
loadbalancer01
```

---

# 38. Delegation Mental Model

```text
Current Play Host
web01
↓
Task says delegate_to
↓
loadbalancer01
↓
Task executes there
```

This is useful for:

```text
Load-balancer control

DNS operations

API calls

Management servers

Monitoring systems

Deployment controllers

Database administration hosts
```

---

# 39. Load-Balancer Example

Conceptually:

```yaml
- name: Remove current web server from traffic
  ansible.builtin.command:
    cmd: "/usr/local/bin/remove-node {{ inventory_hostname }}"
  delegate_to: lb01
```

Then:

```yaml
- name: Update application
  ansible.builtin.package:
    name: example-app
    state: latest
  become: true
```

Then:

```yaml
- name: Return current web server to traffic
  ansible.builtin.command:
    cmd: "/usr/local/bin/add-node {{ inventory_hostname }}"
  delegate_to: lb01
```

The commands here are placeholders for your actual load-balancer integration.

Production systems should prefer supported APIs/modules where available instead of invented shell wrappers.

---

# 40. Delegation Does Not Automatically Serialize

This is extremely important.

Suppose five web hosts all execute:

```yaml
delegate_to: lb01
```

Ansible may still have multiple workers operating against `lb01`.

Delegation means:

```text
Execute somewhere else
```

not:

```text
Execute one at a time
```

If the delegated resource cannot safely handle concurrent operations, add appropriate execution control.

---

# 41. Delegation and Throttle

Example:

```yaml
- name: Update shared load-balancer configuration
  ansible.builtin.command:
    cmd: "/usr/local/bin/update-lb {{ inventory_hostname }}"
  delegate_to: lb01
  throttle: 1
```

Now the delegated operation is serialized.

---

# 42. Delegation and Variables

Delegation changes connection context.

Be careful with variables related to:

```text
Connection
Interpreter
Shell
Become
Host
```

The delegated host's context can affect them.

`inventory_hostname` continues to identify the original play host, which is often exactly what you need when telling a load balancer which backend is being updated.

---

# 43. Local Actions

Sometimes the task should run on the Ansible control node.

You can use:

```yaml
delegate_to: localhost
```

Example:

```yaml
- name: Call deployment API from control node
  ansible.builtin.uri:
    url: "https://deployment-api.example.com/maintenance"
    method: POST
  delegate_to: localhost
```

---

# 44. `local_action`

Ansible also supports shorthand local actions.

Conceptually:

```yaml
- name: Run something locally
  local_action:
    module: ansible.builtin.command
    cmd: /usr/local/bin/example
```

For readability in modern playbooks, explicit:

```yaml
delegate_to: localhost
```

is often easier to understand.

---

# 45. Control-Node Tasks

Examples of operations that may logically happen from the control node include:

```text
Calling an external API

Updating a deployment system

Interacting with a cloud API

Updating monitoring

Creating deployment records

Checking an external endpoint
```

But remember:

```text
localhost
```

means the machine executing Ansible.

In CI, that may be:

```text
CI runner
Execution environment
Container
Automation controller
```

not your laptop.

---

# 46. Local Python Environment

Control-node execution depends on the Python environment available to the Ansible process.

Do not assume:

```text
/usr/bin/python
```

and:

```text
Ansible's current Python
```

are always identical.

This matters especially in:

```text
Virtual environments
CI containers
Execution environments
```

---

# 47. Blocks

Blocks let you group tasks.

Example:

```yaml
- name: Application deployment
  block:
    - name: Deploy application
      ansible.builtin.copy:
        src: application/
        dest: /opt/application/

    - name: Restart application
      ansible.builtin.service:
        name: application
        state: restarted
```

Block-level directives can reduce repetition.

---

# 48. Block-Level Privilege

Instead of:

```yaml
task 1:
  become: true

task 2:
  become: true

task 3:
  become: true
```

you can use:

```yaml
- name: Privileged application changes
  become: true
  block:
    - name: Create directory
      ansible.builtin.file:
        path: /opt/application
        state: directory

    - name: Deploy configuration
      ansible.builtin.template:
        src: application.conf.j2
        dest: /etc/application.conf
```

---

# 49. Rescue

A block can define:

```text
rescue
```

tasks that execute after a task failure within the block.

Example:

```yaml
- name: Deploy application safely
  block:
    - name: Deploy application
      ansible.builtin.command:
        cmd: /opt/deploy/new-version

    - name: Verify application
      ansible.builtin.uri:
        url: http://127.0.0.1:8080/health
        status_code: 200

  rescue:
    - name: Record deployment failure
      ansible.builtin.debug:
        msg: "Deployment failed on {{ inventory_hostname }}"
```

---

# 50. Rescue Is Not Automatic Rollback

This is important.

`rescue` means:

```text
Run these tasks after an applicable failure.
```

It does not mean:

```text
Undo everything automatically.
```

If you want rollback, you must explicitly design rollback behavior.

---

# 51. Explicit Rollback Example

Conceptually:

```yaml
- name: Deploy application with recovery
  block:
    - name: Activate new release
      ansible.builtin.command:
        cmd: /opt/application/bin/activate-new-release

    - name: Verify new release
      ansible.builtin.uri:
        url: http://127.0.0.1:8080/health
        status_code: 200

  rescue:
    - name: Restore previous release
      ansible.builtin.command:
        cmd: /opt/application/bin/restore-previous-release
```

Whether this is truly safe depends entirely on the application's release design.

---

# 52. Always

`always` tasks execute regardless of whether the main block succeeds or enters rescue.

Example:

```yaml
- name: Deployment operation
  block:
    - name: Deploy
      ansible.builtin.command:
        cmd: /opt/application/deploy

  rescue:
    - name: Report failure
      ansible.builtin.debug:
        msg: Deployment failed

  always:
    - name: Record deployment completion
      ansible.builtin.debug:
        msg: Deployment attempt finished
```

---

# 53. Where `always` Is Useful

Examples:

```text
Cleanup

Temporary-file removal

Maintenance-state cleanup

Audit logging

Restoring temporary controls

Final diagnostics
```

But do not assume every cleanup operation is safe after every failure.

---

# 54. Important Block Limitation

`rescue` responds to task failures in the block.

It is not a universal handler for every possible failure class.

Problems such as:

```text
Invalid task definitions

Certain syntax problems

Unreachable hosts
```

do not behave like ordinary failed tasks inside the block.

Design accordingly.

---

# 55. Host Failures

By default, a task failure usually stops later task execution for that host while other hosts may continue.

This can produce:

```text
web01 → successful
web02 → failed
web03 → successful
web04 → successful
```

Production execution must decide when this behavior is acceptable.

---

# 56. Failure Thresholds

During rolling deployments you may want:

```text
A small number of failures → continue

Too many failures → stop deployment
```

Ansible provides:

```text
max_fail_percentage
```

---

# 57. `max_fail_percentage`

Example:

```yaml
---
- name: Rolling deployment
  hosts: web
  serial: 10
  max_fail_percentage: 20
```

This places a failure threshold on the current batch.

---

# 58. Important Percentage Rule

The threshold must be **exceeded** to abort.

For example, if:

```text
serial = 10
max_fail_percentage = 20
```

then exactly 2 failed hosts is:

```text
20%
```

which does not exceed the threshold.

The next failure would push the batch beyond 20%.

This distinction matters when designing exact failure tolerances.

---

# 59. Exact Failure-Count Thinking

Suppose:

```text
Batch size = 4
```

and you want execution to stop when:

```text
2 hosts fail
```

Using:

```yaml
max_fail_percentage: 50
```

would not stop exactly at two because the percentage must be exceeded.

A value such as:

```yaml
max_fail_percentage: 49
```

causes two failures out of four to exceed the threshold.

Always calculate your intended behavior.

---

# 60. `max_fail_percentage` and Serial

With `serial`, the threshold applies to the current batch.

This is important because:

```text
Fleet = 100
Batch = 5
```

means failure control operates around the current five-host rollout group rather than simply treating the entire 100-host fleet as one undifferentiated execution set.

---

# 61. `any_errors_fatal`

Sometimes:

```text
One critical failure
```

should stop the entire operation.

Use:

```yaml
any_errors_fatal: true
```

Example:

```yaml
---
- name: Critical coordinated maintenance
  hosts: web
  any_errors_fatal: true
```

---

# 62. What `any_errors_fatal` Means

Conceptually:

```text
Critical task fails
↓
Complete handling of that fatal task for current batch
↓
Stop play execution across hosts
```

Use it where proceeding after a failure would be unsafe.

---

# 63. Good Use Case

Suppose all load balancers must enter maintenance before application servers can be stopped.

Workflow:

```text
Disable LB A
Disable LB B
↓
Only if both succeed
↓
Stop application fleet
```

If disabling one load balancer fails, continuing might create unsafe traffic behavior.

That is a reasonable place to consider fatal execution semantics.

---

# 64. `any_errors_fatal` Is Not a Default Recommendation

Do not place:

```yaml
any_errors_fatal: true
```

everywhere.

Sometimes one broken server should not prevent maintenance on 500 independent servers.

The right behavior depends on system architecture.

---

# 65. Task Retries

Some operations fail temporarily.

Examples:

```text
Service still starting

API temporarily unavailable

DNS record propagating

Cloud resource becoming ready

Application warming up
```

For transient conditions, Ansible supports retry loops.

---

# 66. `until`

Example:

```yaml
- name: Wait for application health
  ansible.builtin.uri:
    url: http://127.0.0.1:8080/health
    status_code: 200
  register: application_health
  until: application_health.status == 200
  retries: 10
  delay: 5
```

Mental model:

```text
Attempt
↓
Check condition
↓
Condition false
↓
Wait
↓
Retry
↓
Condition true
↓
Continue
```

---

# 67. `retries`

`retries` controls how many retry attempts Ansible permits for the `until` loop.

Example:

```yaml
retries: 10
```

Do not think of retries as:

```text
Try forever.
```

A deployment should eventually declare failure.

---

# 68. `delay`

Example:

```yaml
delay: 5
```

means Ansible waits between retry attempts.

Without sensible delay, you may hammer:

```text
Application

API

Database

External service
```

with repeated requests.

---

# 69. Good Retry Design

A retry should answer:

```text
What transient condition are we waiting for?

How long should it reasonably take?

How often should we check?

What happens if it never becomes ready?
```

---

# 70. Bad Retry Design

This is poor reasoning:

```text
Task fails
↓
Set retries to 100
```

If the real problem is:

```text
Wrong password

Invalid configuration

Wrong package

Missing permission
```

time will not repair it.

---

# 71. Waiting vs Retrying

Use retries when:

```text
You need to repeat an operation until its result meets a condition.
```

Use waiting when:

```text
You need to wait for a known state such as a port becoming available.
```

The concepts overlap, but the appropriate module can make intent clearer.

---

# 72. `wait_for`

`ansible.builtin.wait_for` can wait for conditions including:

```text
Port open

Port closed

Connections drained

File present

File absent

Text appearing in a file/socket

Time period
```

---

# 73. Wait for Port

Example:

```yaml
- name: Wait for application port
  ansible.builtin.wait_for:
    host: 127.0.0.1
    port: 8080
    state: started
    timeout: 60
```

This means:

```text
Wait up to 60 seconds for TCP port 8080 to accept a connection.
```

---

# 74. Port Open Is Not Application Healthy

This is critical.

```text
Port 8080 open
```

proves:

```text
Something is listening.
```

It does not prove:

```text
Application can serve requests correctly.

Database works.

Dependencies work.

Correct version is running.
```

Therefore:

```text
wait_for
↓
uri
↓
assert
```

is often stronger than `wait_for` alone.

---

# 75. Wait for Port to Stop

Example:

```yaml
- name: Wait for old service port to close
  ansible.builtin.wait_for:
    port: 8080
    state: stopped
    timeout: 30
```

Useful during controlled shutdown operations.

---

# 76. Wait for Connections to Drain

`wait_for` also supports:

```yaml
state: drained
```

for TCP connection draining.

Conceptually:

```text
Remove backend from load balancer
↓
Stop accepting new traffic
↓
Existing connections remain
↓
Wait for connections to drain
↓
Perform maintenance
```

This is a powerful building block for rolling maintenance.

---

# 77. Drain Example

On a server listening on port 8080:

```yaml
- name: Wait for active connections to drain
  ansible.builtin.wait_for:
    host: 0.0.0.0
    port: 8080
    state: drained
    timeout: 120
```

Whether this accurately models your application's traffic behavior depends on:

```text
Protocol

Connection reuse

Keep-alive behavior

Load balancer

Long-lived connections

WebSockets

Excluded monitoring connections
```

Do not blindly assume TCP drain equals business-level drain.

---

# 78. Waiting From the Control Node

Sometimes you need to test connectivity from outside the server.

Example:

```yaml
- name: Wait until application port is externally reachable
  ansible.builtin.wait_for:
    host: "{{ ansible_host }}"
    port: 8080
    timeout: 60
  delegate_to: localhost
```

This tests from the control-node network perspective.

---

# 79. Internal vs External Verification

These answer different questions.

```text
127.0.0.1:8080 from application server
```

asks:

```text
Is the application listening locally?
```

External test asks:

```text
Can another system reach it?
```

Load-balancer health asks:

```text
Does the production traffic path consider it healthy?
```

Strong deployments may need multiple levels.

---

# 80. Assertions

`ansible.builtin.assert` lets you turn assumptions into explicit requirements.

Example:

```yaml
- name: Validate deployment inputs
  ansible.builtin.assert:
    that:
      - application_version is defined
      - application_version | length > 0
      - deployment_environment in ['staging', 'production']
    fail_msg: Deployment inputs are invalid.
```

---

# 81. Preconditions

A precondition answers:

```text
What must already be true before this change is allowed?
```

Examples:

```text
Correct environment

Correct application version

Enough healthy servers

Maintenance flag enabled

Required variable defined

Required directory exists

Dependency reachable
```

---

# 82. Preconditions Prevent Unsafe Starts

Instead of:

```text
Start deployment
↓
Discover halfway through that a required variable is missing
```

prefer:

```text
Validate requirements
↓
Fail early
↓
Make no deployment changes
```

---

# 83. Example Precondition

```yaml
- name: Verify minimum fleet size
  ansible.builtin.assert:
    that:
      - groups['web'] | length >= 2
    fail_msg: Rolling deployment requires at least two web servers.
```

This is only an example.

Actual availability requirements should come from your application's architecture.

---

# 84. Post-Deployment Verification

After deployment, verify the desired outcome.

Example:

```yaml
- name: Verify HTTP health
  ansible.builtin.uri:
    url: http://127.0.0.1:8080/health
    status_code: 200
    return_content: true
  register: health
```

Then:

```yaml
- name: Validate application response
  ansible.builtin.assert:
    that:
      - health.status == 200
      - "'healthy' in health.content"
```

---

# 85. Verification Layers

A strong deployment may verify:

```text
Process
↓
Port
↓
Local Health Endpoint
↓
External Endpoint
↓
Load Balancer
↓
Monitoring
```

Not every application requires every layer, but understand the distinction.

---

# 86. Async Tasks

By default, tasks are generally synchronous.

Conceptually:

```text
Start Task
↓
Wait
↓
Task Finishes
↓
Next Task
```

Long-running operations may need asynchronous execution.

---

# 87. `async`

Example:

```yaml
- name: Run long maintenance operation
  ansible.builtin.command:
    cmd: /opt/application/bin/maintenance
  async: 1800
  poll: 30
```

This gives the task an asynchronous execution window.

---

# 88. Async With Polling

With:

```yaml
async: 1800
poll: 30
```

conceptually:

```text
Start operation
↓
Allow up to 1800 seconds
↓
Poll every 30 seconds
↓
Wait until completion/failure/timeout
↓
Continue
```

The play still waits for the result before proceeding.

The advantage is that the long-running operation is managed through Ansible's asynchronous mechanism rather than relying on one ordinary synchronous operation for its entire duration.

---

# 89. Fire-and-Forget

Example:

```yaml
async: 1800
poll: 0
```

means:

```text
Start operation
↓
Do not wait for completion
↓
Continue immediately
```

This requires much more care.

---

# 90. Why `poll: 0` Is Dangerous

Suppose:

```text
Task 1 starts package update asynchronously
Task 2 immediately starts another package operation
```

You may create:

```text
Package-manager lock conflict
```

Fire-and-forget changes execution dependencies.

Do not use it just to make playbooks appear faster.

---

# 91. Tracking Async Jobs

A fire-and-forget task can be registered:

```yaml
- name: Start long-running operation
  ansible.builtin.command:
    cmd: /opt/application/bin/long-job
  async: 1800
  poll: 0
  register: long_job
```

The result contains an asynchronous job identifier.

---

# 92. `async_status`

You can later check the job:

```yaml
- name: Wait for long-running operation
  ansible.builtin.async_status:
    jid: "{{ long_job.ansible_job_id }}"
  register: long_job_result
  until: long_job_result is finished
  retries: 60
  delay: 10
```

This creates an explicit synchronization point.

---

# 93. Async Time Budget

Suppose:

```yaml
async: 600
```

but your polling logic may wait:

```text
20 minutes
```

The async job itself may already have exceeded its permitted runtime.

Your:

```text
async
retries
delay
```

settings should make sense together.

---

# 94. Async and Check Mode

Do not assume asynchronous tasks behave normally under check mode.

Current Ansible async execution has limitations with check mode.

Design and test those tasks explicitly.

---

# 95. Long-Running Operations

Possible examples:

```text
Large backup

Database maintenance

Image creation

Package upgrade

Large data migration

Slow external API operation

Long compilation/build
```

Before using async, ask:

```text
Can operation safely run in background?

Does another task depend on completion?

Can operation be retried?

Is it idempotent?

How is success verified?

What happens if control node disappears?
```

---

# 96. Timeouts

Timeouts prevent operations from waiting indefinitely.

Conceptually:

```text
Wait for expected condition
↓
Condition never happens
↓
Eventually fail
```

Without timeouts, a deployment can hang far longer than intended.

---

# 97. Task Timeout

Ansible task execution supports timeout controls in applicable contexts.

Example concept:

```yaml
- name: Run bounded operation
  ansible.builtin.command:
    cmd: /opt/application/bin/check
  timeout: 60
```

This is different from:

```text
async timeout

wait_for timeout

connection timeout

HTTP timeout
```

Always identify which timeout you are configuring.

---

# 98. Timeout Taxonomy

Think:

```text
Connection Timeout
→ How long to establish/use connection?

Task Timeout
→ How long may task action execute?

Async Limit
→ How long may async job run?

wait_for Timeout
→ How long may desired state take?

HTTP/API Timeout
→ How long may request take?
```

Do not treat all timeout settings as interchangeable.

---

# 99. Tags

Tags allow selective execution.

Example:

```yaml
- name: Deploy configuration
  ansible.builtin.template:
    src: application.conf.j2
    dest: /etc/application/application.conf
  tags:
    - configuration
```

Run:

```bash
ansible-playbook site.yml --tags configuration
```

---

# 100. Tags in Advanced Workflows

Useful categories might include:

```text
precheck

deploy

configuration

restart

verify

cleanup
```

But tags must not become an excuse to create unsafe partial workflows.

---

# 101. Dependency Problem With Tags

Suppose:

```text
deploy
↓
restart
↓
verify
```

If you run only:

```bash
--tags verify
```

that may be fine.

If you run only:

```bash
--tags restart
```

you may restart a service without deploying the intended configuration.

Understand dependencies between tagged tasks.

---

# 102. List Tags

Before selective execution:

```bash
ansible-playbook site.yml --list-tags
```

Also inspect:

```bash
ansible-playbook site.yml --list-tasks
```

and:

```bash
ansible-playbook site.yml --list-hosts
```

Selective execution deserves extra verification.

# 103. Dynamic Includes

`ansible.builtin.include_tasks` dynamically includes task files during execution.

Example:

```yaml
- name: Include operating-system tasks
  ansible.builtin.include_tasks:
    file: "{{ ansible_facts['os_family'] | lower }}.yml"
```

The selected file can depend on runtime data.

---

# 104. Dynamic Inclusion Mental Model

```text
Play starts
↓
Facts/variables become available
↓
Runtime decision
↓
Select task file
↓
Load tasks
↓
Execute
```

This provides flexibility.

---

# 105. Looping Dynamic Includes

Example:

```yaml
- name: Configure application components
  ansible.builtin.include_tasks:
    file: configure-component.yml
  loop:
    - api
    - worker

    loop_var: component
```

Dynamic includes work well when inclusion itself needs:

```text

Variable-driven filenames
```

# 106. Static Imports

`ansible.builtin.import_tasks` statically imports tasks.

Example:

```yaml
- name: Import validation tasks
  ansible.builtin.import_tasks:
    file: validate.yml
```

Think:

```text
Build play structure
↓
Imported tasks become part of it
↓
Execute
```

---

# 107. Static vs Dynamic

Simplified mental model:

```text
import_tasks
→ static reuse
```

```text
include_tasks
→ dynamic runtime reuse
```

This distinction affects:

```text
Conditionals

Loops

Tags

Task visibility

--start-at-task behavior

Execution reasoning
```

---

# 108. Condition on Import

Example:

```yaml
- name: Import production validation
  ansible.builtin.import_tasks: production-validation.yml
  when: deployment_environment == 'production'
```

The condition is effectively applied to imported tasks.

---

# 109. Condition on Include

Example:

```yaml
- name: Load production tasks
  ansible.builtin.include_tasks: production.yml
  when: deployment_environment == 'production'
```

Here the inclusion decision happens dynamically.

# 110. Why This Matters for Troubleshooting

From Part 15:

```text
--start-at-task
```

cannot generally jump directly into tasks hidden inside dynamic includes.

Static imports are more visible to Ansible's initial task structure.

Execution architecture affects troubleshooting architecture.

# 111. Multi-Play Workflows

A playbook can contain multiple plays.

This is extremely useful for orchestration.

Example:

```text
Play 1
Validate deployment

Play 2
Prepare load balancer

Play 3
Deploy application servers

Play 4
Verify service

Play 5
Finalize deployment
```

Different plays can target different host groups.

---

# 112. Example Multi-Play Architecture

```yaml
---
- name: Validate control systems
  hosts: localhost
  connection: local
  gather_facts: false
  tasks:
    - name: Validate deployment version
      ansible.builtin.assert:
        that:
          - application_version is defined

- name: Update web fleet
  hosts: web
  serial: 1
  tasks:
    - name: Deploy application
      ansible.builtin.debug:
        msg: "Deploy {{ application_version }}"

- name: Verify load balancers
  hosts: load_balancers
  tasks:
    - name: Verify load-balancer service
      ansible.builtin.service:
        name: example-lb
        state: started
```

---

# 113. Multi-Play Workflows vs Giant Plays

Do not force unrelated infrastructure into one enormous play.

Use separate plays when:

```text
Different host groups are involved

Different privilege models exist

Different execution strategies are required

Different failure semantics are required

Workflow stages are logically distinct
```

# 117. Load-Balancer Drain Concepts

Suppose users are reaching:

```text
Load Balancer
     |
     +---- web01
     +---- web02
     +---- web03
```

You want to update `web01`.

Do not simply:

```text

```

Instead:

```text

↓
Drain existing connections
↓
Update web01
↓
Verify web01
↓
Return web01
```

```text
↓

↓

↓

↓

↓

↓

↓

↓

↓

↓

↓
```

# 119. Zero Downtime vs Minimal Downtime

Be careful with the phrase:

```text
zero downtime
```

Ansible alone cannot guarantee zero downtime.

True zero-downtime behavior depends on:

```text
Application architecture

Load balancer

Health checks

Session handling

Database compatibility

Schema migration strategy

Capacity

Connection draining

Startup time

Shutdown behavior

Deployment artifact

Rollback design
```

A more responsible goal is often:

```text
Zero or minimal user-visible interruption
```

with architecture designed to support it.

---

# 120. Capacity Requirement

Suppose:

```text
3 application servers
```

and normal traffic requires all three at full load.

Taking one server out of rotation may overload the remaining two.

A rolling playbook cannot solve insufficient capacity.

Before rolling maintenance:

```text
Verify remaining fleet can serve traffic.
```

# 121. Safe Restart Pattern

Weak:

```yaml
- name: Restart application
  ansible.builtin.service:
    name: application
    state: restarted
```

Stronger architecture:

```text
Remove From Traffic
↓
Drain
↓
Validate Configuration
↓
Restart
↓
Wait for Port
↓
Health Check
↓
Return to Traffic
```

---

# 122. Reload vs Restart

Where the application supports safe reload:

```text
Reload
```

may cause less disruption than:

```text
Restart
```

But do not assume reload is universally supported or equivalent.

Use the service/application's documented behavior.

# 123. Handlers and Safe Restarts

Configuration changes often notify a handler:

```yaml
handlers:
  - name: Restart application
    ansible.builtin.service:
      name: application
      state: restarted
```

But in advanced rolling deployments, restart timing may need tighter orchestration.

You may need:

```text
Configuration deployment
↓
Validation
↓
Explicit handler flush
↓
Wait
↓
Health verification
```

---

# 124. `meta: flush_handlers`

Example:

```yaml
- name: Deploy application configuration
  ansible.builtin.template:
    src: application.conf.j2
    dest: /etc/application/application.conf
  notify: Restart application

- name: Run notified handlers now
  ansible.builtin.meta: flush_handlers

- name: Wait for application
  ansible.builtin.wait_for:
    port: 8080
    timeout: 60
```

Without flushing, the restart might occur later than the verification task expects.

---

# 125. Handler Timing Matters

Bad logic:

```text
Deploy config
↓
Notify restart
↓
Immediately verify new configuration is live
↓
Handler has not run yet
```

Correct reasoning:

```text
Deploy config
↓
Validate
↓
Restart/reload at intentional point
↓
Wait
↓
Verify
```

# 139. Add Load-Balancer Control

Conceptually:

```yaml
pre_tasks:
  - name: Remove current server from load balancer
    ansible.builtin.command:
      cmd: "/usr/local/bin/remove-backend {{ inventory_hostname }}"
    delegate_to: lb01

  - name: Wait for existing application connections to drain
    ansible.builtin.wait_for:
      host: 0.0.0.0
      port: "{{ application_port }}"
      state: drained
      timeout: 120
```

Then after deployment:

```yaml
post_tasks:
  - name: Return current server to load balancer
    ansible.builtin.command:
      cmd: "/usr/local/bin/add-backend {{ inventory_hostname }}"
    delegate_to: lb01
```

Again, those load-balancer commands are architectural placeholders.

---

# 140. Safer Block Structure

A stronger pattern is:

```yaml
- name: Rolling maintenance for current server
  block:
    - name: Remove server from load balancer
      ansible.builtin.command:
        cmd: "/usr/local/bin/remove-backend {{ inventory_hostname }}"
      delegate_to: lb01

    - name: Wait for connections to drain
      ansible.builtin.wait_for:
        host: 0.0.0.0
        port: "{{ application_port }}"
        state: drained
        timeout: 120

    - name: Deploy application
      ansible.builtin.include_role:
        name: application

    - name: Return server to load balancer
      ansible.builtin.command:
        cmd: "/usr/local/bin/add-backend {{ inventory_hostname }}"
      delegate_to: lb01

  rescue:
    - name: Report failed deployment
      ansible.builtin.debug:
        msg: "Deployment failed on {{ inventory_hostname }}"

  always:
    - name: Record deployment attempt
      ansible.builtin.debug:
        msg: "Deployment attempt completed for {{ inventory_hostname }}"
```

But there is a critical production question here.

---

# 141. Do Not Automatically Return a Failed Server to Traffic

A dangerous rescue design would be:

```text
Deployment fails
↓
Always add server back to load balancer
```

If the server is unhealthy, you have just restored broken capacity to production traffic.

Instead:

```text
Deployment fails
↓
Attempt safe rollback if designed
↓
Verify rollback
↓
Only return server if healthy
```

Traffic restoration should be conditional on verified health.

```text
Remove Server
↓

↓

↓
Verification
   |
   +---- PASS ----> Return to Traffic
   |

                        |
                        v
                    Verify Again
                        |
              +---------+---------+
              |                   |
            PASS                 FAIL
              |                   |
              v                   v
       Return to Traffic     Keep Out of Traffic
                             Stop / Escalate
```

This is production thinking.

# 145. Final Fleet Verification

Per-host success is not enough.

After all batches complete, perform fleet-level checks.

Examples:

```text
Load balancer reports expected healthy backends

External application endpoint responds

Correct application version is serving

Monitoring is healthy

Error rate has not spiked
```

Ansible can perform some of these checks directly; others may belong to your observability/deployment platform.

# 146. Separate Local and External Health

Per-host:

```yaml
- name: Verify local health
  ansible.builtin.uri:
    url: "http://127.0.0.1:{{ application_port }}/health"
    status_code: 200
```

External:

```yaml
- name: Verify production endpoint
  ansible.builtin.uri:
    url: https://app.example.com/health
    status_code: 200
  delegate_to: localhost
  run_once: true
```

Remember the `run_once` and serial interaction discussed earlier.

For true one-time final verification, placing this check in a separate final play is often clearer.

# 147. Better Multi-Play Design

# 148. Example Final Verification Play

```yaml
- name: Verify production service after deployment
  hosts: localhost
  connection: local
  gather_facts: false

  tasks:
    - name: Check public health endpoint
      ansible.builtin.uri:
        url: https://app.example.com/health
        status_code: 200
      register: public_health
      retries: 5
      delay: 5
      until: public_health.status == 200

    - name: Assert production endpoint is healthy
      ansible.builtin.assert:
        that:
          - public_health.status == 200
```

This naturally executes once because the play itself targets localhost.

```text
Long-lived connections

Monitoring traffic

Application connection leak

Wrong port
```

# 152. Failure Scenario 3: Restart Completes but Health Fails

Possible causes:

```text
Application process running but dependency unavailable

Wrong configuration

Database unavailable

Wrong version

Health endpoint failing

Port listening before application ready
```


# 153. Failure Scenario 4: Delegated LB Task Fails

Now ask:

```text
Is LB reachable?

Does delegated host have required credentials?

Did API reject request?

Is backend name correct?

Was task executed concurrently?

Should deployment continue?
```

# 154. Failure Scenario 5: Async Job Never Completes

Investigate:

```text
Did job start?

Was async window long enough?

Does job ID exist?

Did remote process fail?

Was host rebooted?

Was async status data cleaned?

Is polling logic correct?
```

# 155. Failure Scenario 6: Too Many Hosts Fail

With a failure threshold:

```text
Batch begins
↓
Failures exceed threshold
↓
Abort remaining rollout
```

This prevents one bad release from automatically spreading through the entire fleet.

# 156. Failure Scenario 7: `run_once` Migration Runs Multiple Times

Cause:

```text
serial batches
+
run_once
```

Lesson:

```text
run_once
```

means once per current batch in this context.

Do not use it casually for destructive global operations.

---

# 157. Failure Scenario 8: Free Strategy Breaks Coordination

Host A may reach:

```text
Return to traffic
```

while Host B is still several tasks behind.

If the workflow assumes lockstep behavior, the strategy choice is wrong.

Use execution semantics that match system requirements.

---

# 158. Failure Scenario 9: Throttle Does Nothing Extra

Suppose:

```text
forks = 2
throttle = 10
```

You expected ten concurrent operations.

But only two workers are available.

`throttle` restricts concurrency.

It does not create workers.

# 159. Failure Scenario 10: Always Block Restores Traffic Too Early

Bad:

```text
always:
  add backend
```

The host failed deployment but was automatically restored.

Correct lesson:

```text
Cleanup
```

and:

```text
Traffic restoration
```

are not necessarily the same operation.

Health must control re-entry.

# 161. Common Mistake: Confusing Forks With Batch Size

Wrong:


Correct:

```text
forks = worker capacity
```

# 162. Common Mistake: Using Serial Without Capacity Planning

```yaml
serial: 5
```

is not automatically safe.

If removing five servers leaves insufficient capacity, the deployment is unsafe.

---

# 163. Common Mistake: Assuming `run_once` Means Globally Once

With serial batches, that assumption can be false.

Understand execution scope.

---

# 164. Common Mistake: Delegating Without Thinking About Concurrency

Five source hosts can generate concurrent work on one delegated host.

Protect shared resources.

---

# 165. Common Mistake: Using `free` Everywhere

Faster host progression is not always desirable.

Coordination matters.

---

# 166. Common Mistake: Using Rescue as Magic Rollback

`rescue` executes tasks.

It does not reverse state automatically.

---

# 167. Common Mistake: Putting Dangerous Recovery in Always

`always` means:

```text
Run regardless of block outcome.
```

That makes it a dangerous place for unconditional:

```text
Return to traffic
Delete evidence
Mark deployment successful
```

---

# 168. Common Mistake: Waiting Only for Port

```text
Port open
```

does not prove:

```text
Healthy application.
```

Add functional verification.

---

# 169. Common Mistake: Infinite Retry Thinking

Every wait/retry needs a failure boundary.

Eventually:

```text
Not ready
```

must become:

```text
Deployment failed
```

so humans or higher-level automation can respond.

---

# 170. Common Mistake: Async Everything

Async introduces:

```text
Concurrency

State tracking

Synchronization

Cleanup

Failure handling
```

Use it only when the operation benefits from it.

---

# 171. Common Mistake: Blindly Increasing Forks

Higher concurrency can overwhelm dependencies.

Measure before increasing.

---

# 172. Common Mistake: Restarting Entire Fleet

A task like:

```yaml
hosts: web
tasks:
  - service:
      name: application
      state: restarted
```

may cause simultaneous disruption.

Ask:

```text
Should this be rolling?
```

---

# 173. Common Mistake: No Prechecks

Do not discover basic requirements after half the fleet has changed.

Validate first.

---

# 174. Common Mistake: No Postchecks

A green play recap proves only what Ansible reported about task execution.

Verify the service.

---

# 175. Common Mistake: Mixing Global and Per-Host Operations

Example:

```text
Database migration
```

may be global.

```text
Application restart
```

may be per-host.

Design them separately.

# 176. Advanced Production Rules

Use these rules:

```text
Control concurrency intentionally.

Know the current batch.

Reduce blast radius.

Verify before disruption.

Remove from traffic before disruptive maintenance.

Drain where appropriate.

Prefer validated configuration.

Restart only when required.

Wait for readiness.

Verify actual health.

Return only healthy nodes to traffic.

Stop bad rollouts early.

Do not confuse run_once with global exactly-once execution.

Protect delegated shared resources.

Bound retries.

Bound waiting.

Treat async as concurrency, not magic speed.

Design explicit recovery.

Perform final fleet verification.
```
