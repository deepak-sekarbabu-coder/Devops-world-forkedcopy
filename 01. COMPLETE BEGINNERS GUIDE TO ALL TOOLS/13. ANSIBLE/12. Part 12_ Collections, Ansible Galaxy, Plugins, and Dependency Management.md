
# 3. What Is an Ansible Collection?

An Ansible collection is a distribution format for related Ansible content.

A collection can package content such as:

```text
Modules

Plugins

Roles

Playbooks

Documentation

Supporting code
```

A collection therefore gives publishers a structured way to distribute automation capabilities.

# 5. Why Collections Exist

Historically, Ansible content could become tightly associated with the main Ansible codebase or be distributed in less standardized ways.

Collections provide a cleaner distribution model.

They allow:

```text
Different publishers
↓
to maintain
↓
Different automation content
↓
with
↓
Independent release cycles
```

This matters because:

```text
AWS changes

Cisco products change

VMware changes

Cloud APIs change

Kubernetes changes

Community tooling changes
```

Those integrations do not all need to follow exactly the same release lifecycle as `ansible-core`.

# 7. What Is a Namespace?

Every collection belongs to a namespace.

A collection name follows:

```text

```

Examples of the shape:

```text

```

The first part is:

```text
namespace
```

The second part is:

```text
collection name
```

# 9. Collection Naming

Collection identity is:


# 11. What Is an FQCN?

FQCN means:

```text
Fully Qualified Collection Name
```

For modules and many plugin references, it identifies the content together with the collection that provides it.

Example:

```text
ansible.builtin.copy
```

Break it apart:

```text
ansible
↓
namespace

builtin
↓
collection

copy
↓
module
```

So:

```text
ansible.builtin.copy
```

means:

```text
copy module
from
ansible.builtin collection
```

---

```text
namespace.collection.content
```

For example:

```text
ansible.builtin.file
```

```text

```

```text
ansible.builtin.service
```

```text
ansible.builtin.template
```

```text

```

You have already been using this model throughout the course.

# 13. Short Name vs FQCN

You may encounter:

```yaml
- name: Copy file
  copy:
    src: app.conf
    dest: /etc/app.conf
```

and:

```yaml
- name: Copy file
  ansible.builtin.copy:
    src: app.conf
    dest: /etc/app.conf
```

The second form makes the content provider explicit.

# 30. Installing a Collection

General syntax:

```bash
ansible-galaxy collection install namespace.collection
```

Example:

```bash
ansible-galaxy collection install community.general
```

This asks `ansible-galaxy` to install that collection using configured content sources.

# 31. Install a Specific Collection Version

You can specify a version.

Example pattern:

```bash
ansible-galaxy collection install namespace.collection:1.2.3
```

The actual version must exist.

Do not copy a tutorial's version number without checking.

# 32. Why Specific Versions Matter

```text

```

If your project never declared its tested dependency version, the two environments may behave differently.

That damages reproducibility.

# 40. `requirements.yml`

Ansible can install multiple dependencies from a requirements file.

Common name:

```text
requirements.yml
```

This allows your repository to declare external dependencies.

---

# 41. Collection Requirements Example

Create:

```text
collections/requirements.yml
```

Example structure:

```yaml
---
collections:
  - name: community.general
    version: "VERSION_YOU_HAVE_TESTED"
```

Replace the placeholder with a real tested version.

Do not publish fictional dependency versions.

---

# 42. Multiple Collections

Conceptually:

```yaml
---
collections:
  - name: namespace_a.collection_a
    version: "TESTED_VERSION"

  - name: namespace_b.collection_b
    version: "TESTED_VERSION"
```

Now your dependency set is visible.

---

# 43. Install From Requirements

```bash
ansible-galaxy collection install -r collections/requirements.yml
```

# 49. Pinning Versions

Version pinning means deliberately controlling which dependency version your automation uses.

Example concept:

```yaml

  - name: namespace.collection
    version: "1.4.2"
```

This provides stronger reproducibility than simply asking for whatever version happens to be newest at installation time.

# 59. Verify Installed Collections

Ansible provides collection verification capabilities.

General command:

```bash
ansible-galaxy collection verify namespace.collection
```

This can compare installed collection content against the corresponding distribution content when the required source information is available.

---

# 60. Verify a Specific Version

Pattern:

```bash
ansible-galaxy collection verify namespace.collection:VERSION
```

Specifying the expected version helps avoid accidentally comparing against an unintended release.

---

# 61. Verification With Requirements

Collections declared in a requirements file can also participate in verification workflows.

Example:

```bash
ansible-galaxy collection verify -r collections/requirements.yml
```

Important:

Dependencies pulled indirectly by those entries may need separate consideration and verification.

Do not assume one command proves the security of your entire dependency graph.

---

# 62. Signed Collection Verification

Some distribution servers can provide collection signatures.

Where supported, Ansible can use signature verification mechanisms during collection workflows.

This strengthens authenticity checking.

But:

```text
Signature Verification
≠
Code Security Review
```

A correctly signed collection can still contain a bug or unsafe behavior.

Examples include:

```text

```

There are additional plugin categories as well.

This chapter focuses on the ones most important to your current learning path.

```text

↓

```


Ansible's architecture includes modules and many categories of plugins that interact with execution in different ways.

# 172. Production Dependency Standard

A serious production project should define standards such as:

```text
All external dependencies must be declared.

All production dependencies must have an approved source.

Versions must be controlled.

Dependencies must be reviewed before adoption.

Compatibility must be documented.

Dependencies must be tested in clean environments.

Upgrades must go through code review.

Security-impacting updates must be prioritized appropriately.

Unused dependencies must be removed.

Custom dependencies must have owners.

Production should not depend on undocumented workstation state.
```

---

# 173. Production Dependency Rule 1

## Declare Everything

Do not rely on:

```text
"Oh, that collection is already installed on the runner."
```

Your repository should make its dependency requirements discoverable and reproducible.

---

# 174. Production Dependency Rule 2

## Pin What You Test

If CI validates:

```text
Collection 4.2.1
```

but production silently installs:

```text
Whatever is newest
```

your testing contract is weak.

Production should run the dependency set you intentionally validated.
