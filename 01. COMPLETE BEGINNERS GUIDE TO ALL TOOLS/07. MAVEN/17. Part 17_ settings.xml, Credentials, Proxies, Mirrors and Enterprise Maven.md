# Part 17: settings.xml, Credentials, Proxies, Mirrors and Enterprise Maven

Up to this point, most of our Maven configuration has lived inside `pom.xml`.

The POM tells Maven about the project:

* What the project is called
* Which dependencies it needs
* Which plugins it uses
* How it should compile
* How it should test
* How it should package
* Which modules belong to the build

But some Maven configuration should not belong to the project.

Consider these questions:

* Where should your repository username be stored?
* Where should a CI/CD pipeline get repository credentials?
* What if your company does not allow Maven to connect directly to Maven Central?
* What if all dependency downloads must pass through JFrog Artifactory or Sonatype Nexus Repository?
* What if your company requires an HTTP proxy?
* What if your laptop and a CI server need different credentials?
* How does Maven know which credentials belong to which repository?
* What does a `401 Unauthorized` error actually mean?
* Why might Maven report an SSL certificate error even when the dependency exists?

These problems take us outside `pom.xml` and into Maven's external configuration system.

The most important file is:

```text
settings.xml
```

The central mental model for this part is:

```text
Project configuration
        |
        v
     pom.xml


User / machine / environment configuration
        |
        v
   settings.xml
```

In a simple public project, Maven might communicate directly with Maven Central:

```text
Developer
    |
    v
  Maven
    |
    v
Maven Central
```

In an enterprise environment, the architecture often looks more like this:

```text
Developer
    |
    v
  Maven
    |
    v
settings.xml
    |
    v
Enterprise Repository Manager
    |
    +----> Internal Artifacts
    |
    +----> Cached External Artifacts
    |
    v
Maven Central
```

By the end of this part, you should understand not only how to create `settings.xml`, but why organizations use it and how it becomes part of a secure Maven build environment.

---

# 17.1 Start With the Most Important Distinction

Maven configuration comes from several places.

Two of the most important are:

```text
pom.xml
settings.xml
```

They do not serve the same purpose.

A beginner may look at both files and think:

> They are both XML files that configure Maven, so why do I need two?

Because they answer different questions.

The POM answers:

```text
How should this project be built?
```

The settings file answers questions closer to:

```text
How should Maven operate for this user or environment?
```

For example, suppose VERIQTA has this project:

```text
veriqta-platform/
├── pom.xml
└── src/
```

Its POM might declare:

```xml
<groupId>com.veriqta</groupId>
<artifactId>veriqta-platform</artifactId>
<version>1.0.0</version>
```

It might also declare dependencies and plugins.

Those things describe the project.

Now suppose Ann needs authentication to an internal repository.

Her username should not normally be committed into the project's POM.

Instead:

```text
Project
   |
   +-- pom.xml
   |      |
   |      +-- project identity
   |      +-- dependencies
   |      +-- plugins
   |      +-- build configuration
   |
   +-- Maven user environment
          |
          +-- ~/.m2/settings.xml
                 |
                 +-- credentials
                 +-- mirrors
                 +-- proxies
                 +-- user profiles
```

This separation becomes extremely important in real organizations.

---

# 17.2 `pom.xml` Versus `settings.xml`

A useful comparison is:

| `pom.xml`                      | `settings.xml`                              |
| ------------------------------ | ------------------------------------------- |
| Describes a Maven project      | Configures Maven's environment              |
| Usually committed to Git       | Usually not committed with the project      |
| Shared by the development team | May differ between users and environments   |
| Declares dependencies          | Can provide repository credentials          |
| Declares plugins               | Can configure plugin groups                 |
| Defines build behavior         | Can configure mirrors                       |
| Defines project profiles       | Can define environment-specific profiles    |
| Defines project coordinates    | Can configure proxies                       |
| Can reference repositories     | Can provide authentication for repositories |

Think of it this way:

```text
pom.xml
"What does this project require?"

settings.xml
"How does this Maven installation reach and authenticate to the systems it needs?"
```

That distinction will help you understand almost everything else in this part.

---

# 17.3 What Is `settings.xml`?

`settings.xml` is an XML configuration file used to customize Maven behavior outside an individual project POM.

A basic file looks like this:

```xml
<?xml version="1.0" encoding="UTF-8"?>

<settings xmlns="http://maven.apache.org/SETTINGS/1.0.0"
          xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
          xsi:schemaLocation="
              http://maven.apache.org/SETTINGS/1.0.0
              https://maven.apache.org/xsd/settings-1.0.0.xsd">

</settings>
```

The root element is:

```xml
<settings>
```

Inside it, Maven can configure areas such as:

```text
localRepository
interactiveMode
offline
pluginGroups
servers
mirrors
proxies
profiles
activeProfiles
```

You do not need all of them in every file.

A minimal `settings.xml` can contain only the configuration you actually need.

---

# 17.4 User Settings

The most common settings file is the user's Maven settings file.

On macOS and Linux, its usual location is:

```text
~/.m2/settings.xml
```

The `~` means:

```text
the current user's home directory
```

For example, on macOS it may correspond to something similar to:

```text
/Users/ann/.m2/settings.xml
```

On Linux:

```text
/home/ann/.m2/settings.xml
```

On Windows, Maven uses the user's home directory, commonly resulting in a path similar to:

```text
C:\Users\Ann\.m2\settings.xml
```

The important concept is not memorizing every operating-system path.

Remember:

```text
User home
   |
   v
 .m2
   |
   +-- repository/
   |
   +-- settings.xml
```

The `.m2` directory is Maven's user-level working area.

---

# 17.5 Does `settings.xml` Always Exist?

No.

A fresh Maven installation may work perfectly without a user-created:

```text
~/.m2/settings.xml
```

For a simple public project, Maven can use defaults.

For example:

```bash
mvn compile
```

may download dependencies without you ever creating `settings.xml`.

You normally create or customize the file when you need something such as:

```text
private repository authentication
repository mirrors
corporate proxies
custom local repository location
settings profiles
enterprise repository routing
```

This is important because beginners sometimes search for `settings.xml`, cannot find it, and assume Maven is installed incorrectly.

It may simply not exist yet.

---

# 17.6 Inspect the `.m2` Directory

On macOS or Linux:

```bash
ls -la ~/.m2
```

You may see:

```text
repository
settings.xml
```

or perhaps only:

```text
repository
```

The command:

```bash
ls -la ~/.m2
```

means:

* `ls` lists directory contents.
* `-l` requests detailed listing information.
* `-a` includes hidden entries.
* `~/.m2` specifies Maven's user-level directory.

If `.m2` does not exist yet, Maven may create it after Maven begins resolving artifacts.

You can create the directory yourself when necessary:

```bash
mkdir -p ~/.m2
```

Then create:

```text
~/.m2/settings.xml
```

Do not delete your existing `.m2` directory simply to create a settings file. It may already contain your local Maven repository.

---

# 17.7 Global Settings

Maven can also have global settings.

Conceptually:

```text
Maven installation
        |
        v
      conf
        |
        v
  settings.xml
```

This settings file applies at the Maven installation level.

The exact installation directory depends on how Maven was installed.

For a Maven binary distribution, you may have something conceptually like:

```text
apache-maven-3.x.x/
├── bin/
├── boot/
├── conf/
│   └── settings.xml
└── lib/
```

The global settings file is therefore associated with the Maven installation.

The user settings file belongs to the individual user.

Think:

```text
Global settings
      +
User settings
      |
      v
Effective Maven settings
```

User-level settings can customize or override relevant global configuration.

---

# 17.8 User Settings Versus Global Settings

Suppose an organization installs Maven with company-wide configuration.

Global configuration might establish organizational defaults.

Then individual developers may have their own:

```text
~/.m2/settings.xml
```

for user-specific configuration.

Conceptually:

```text
Global Maven configuration
          |
          v
   global settings.xml
          |
          +
          |
User Maven configuration
          |
          v
 ~/.m2/settings.xml
          |
          v
Effective settings
```

Avoid casually modifying global Maven configuration on a workstation unless you understand why it is required.

User-level settings are usually easier to manage because they do not modify the Maven installation itself.

---

# 17.9 Inspecting Effective Settings

Remember from Part 4:

```bash
mvn help:effective-settings
```

This becomes especially useful now.

Run:

```bash
mvn help:effective-settings
```

Maven calculates the effective settings after considering applicable settings sources.

This can help answer:

* Which mirror is configured?
* Which profiles are active?
* Is a proxy configured?
* Which local repository is Maven using?
* Did Maven read the settings file I expected?

When debugging Maven environment problems, this command should become familiar.

Be careful when sharing settings output publicly. Configuration output may reveal internal repository names, hosts, usernames, or other environment details.

# 17.10 Local Repository Configuration

By default, Maven's local artifact repository normally lives under:

```text
~/.m2/repository
```

You learned about this in Part 7.

The flow was:

```text
pom.xml
   |
   v
Maven
   |
   +-- check local repository
   |
   +-- if missing, contact remote repository
   |
   v
download
   |
   v
cache locally
```

`settings.xml` can change the local repository location.

For example:

```xml
<settings>
    <localRepository>/path/to/custom/maven-repository</localRepository>
</settings>
```

Now Maven can use:

```text
/path/to/custom/maven-repository
```

instead of the default location.

---

# 17.11 Should You Change the Local Repository?

Usually, beginners do not need to.

The default:

```text
~/.m2/repository
```

works well for most local development.

A custom location may be useful in specialized environments such as:

* Managed build systems
* Containerized CI runners
* Dedicated build storage
* Controlled enterprise workstations
* Special caching arrangements

Do not confuse:

```text
local repository
```

with:

```text
remote repository
```

The local repository exists on your machine or build environment.

A remote repository exists somewhere Maven reaches over a network.

```text
Developer Machine

~/.m2/repository
      |
      | local cache
      |
      v
    Maven
      |
      | network
      v
Remote Repository
```

---

# 17.12 What Is a Maven Server?

Inside `settings.xml`, Maven has a section called:

```xml
<servers>
```

A `<server>` entry provides authentication or related connection information for a repository or other server Maven needs to access.

Example:

```xml
<settings>

    <servers>

        <server>
            <id>veriqta-releases</id>
            <username>example-user</username>
            <password>example-password</password>
        </server>

    </servers>

</settings>
```

Do not copy real passwords into examples or repositories.

The important structure is:

```text
servers
   |
   +-- server
          |
          +-- id
          +-- username
          +-- password
```

The most important field for understanding how this works is:

```xml
<id>
```

---

# 17.13 Server IDs

Maven needs a way to connect credentials in `settings.xml` with a repository referenced elsewhere.

It uses IDs.

Suppose a POM contains:

```xml
<distributionManagement>
    <repository>
        <id>veriqta-releases</id>
        <url>https://repo.example.com/releases</url>
    </repository>
</distributionManagement>
```

The settings file contains:

```xml
<server>
    <id>veriqta-releases</id>
    <username>example-user</username>
    <password>example-password</password>
</server>
```

The matching value is:

```text
veriqta-releases
```

Maven conceptually performs:

```text
Repository
ID = veriqta-releases
        |
        v
settings.xml
        |
        v
Find server
ID = veriqta-releases
        |
        v
Use its credentials
```

This is why server IDs matter.

The ID is not merely a decorative name.

It connects configuration pieces.

---

# 17.14 Why Credentials Should Not Normally Be in `pom.xml`

Imagine putting this into a project committed to Git:

```xml
<username>ann</username>
<password>MyRealPassword</password>
```

Then:

```text
Credential
    |
    v
pom.xml
    |
    v
git add
    |
    v
git commit
    |
    v
Git repository
    |
    +--> teammates
    +--> CI systems
    +--> backups
    +--> forks
    +--> mirrors
```

Even if you remove the password in a later commit, it may remain in Git history.

The better separation is:

```text
pom.xml
   |
   +-- repository ID
   +-- project configuration

settings.xml / CI secret system
   |
   +-- credentials
```

This is one of the reasons Maven separates project configuration from environment configuration.

# 17.15 Private Artifact Repositories

Not every dependency belongs in Maven Central.

An organization may create internal Java libraries such as:

```text
com.veriqta:logging-library:2.0.0
com.veriqta:security-core:1.4.1
com.veriqta:platform-client:3.2.0
```

These artifacts may be proprietary.

The organization does not want them published publicly.

Instead, it hosts them in a private artifact repository.

The architecture becomes:

```text
VERIQTA Application
        |
        v
      Maven
        |
        v
Private Artifact Repository
        |
        +-- logging-library
        +-- security-core
        +-- platform-client
```

Developers and CI systems authenticate to that repository.

---

# 17.16 What Is a Repository Manager?

A repository manager is a service used to store, organize, proxy, cache, and control access to software artifacts.

For Maven environments, repository managers often handle artifacts such as:

```text
JAR
POM
WAR
metadata
checksums
source artifacts
Javadoc artifacts
```

Instead of every developer contacting every external repository independently:

```text
Developer A ---> Maven Central
Developer B ---> Maven Central
Developer C ---> Maven Central
CI Runner 1 ---> Maven Central
CI Runner 2 ---> Maven Central
```

the organization can use:

```text
Developer A ----\
Developer B -----\
Developer C ------> Enterprise Repository Manager ---> Maven Central
CI Runner 1 -----/
CI Runner 2 ----/
```

This creates a central control point.

---

# 17.17 Why Enterprises Use Repository Managers

Repository managers can provide several benefits.

They can:

* Store private company artifacts
* Proxy Maven Central
* Cache downloaded artifacts
* Reduce repeated external downloads
* Control which repositories developers use
* Apply access controls
* Support internal release processes
* Improve build resilience
* Provide auditing
* Centralize artifact management

Imagine 500 CI builds all requiring:

```text
org.junit.jupiter:junit-jupiter
```

Without a repository manager, many builds may repeatedly depend on an external service.

With proxy caching:

```text
First request
Developer
   |
   v
Repository Manager
   |
   v
Maven Central
   |
   v
Download artifact
   |
   v
Cache artifact


Later request
Developer
   |
   v
Repository Manager
   |
   v
Cached artifact
```

The external artifact does not necessarily need to be downloaded from Central every time.

# 17.18 Nexus Repository Concepts

Sonatype Nexus Repository is one repository-management platform commonly used with Maven.

At a conceptual level, a Nexus deployment may contain repositories serving different purposes.

For example:

```text
Nexus Repository
      |
      +-- hosted repository
      |
      +-- proxy repository
      |
      +-- group repository
```

A hosted repository stores artifacts managed by the organization.

For example:

```text
company-releases
company-snapshots
```

A proxy repository acts as an intermediary for an external repository such as Maven Central.

A group repository can provide a single endpoint representing multiple repositories.

Conceptually:

```text
Maven
  |
  v
Nexus Group
  |
  +-- Company Releases
  |
  +-- Company Snapshots
  |
  +-- Maven Central Proxy
```

From Maven's perspective, this can greatly simplify repository access.

---

# 17.19 JFrog Artifactory Concepts

JFrog Artifactory is another widely used artifact repository manager.

The terminology differs somewhat, but the core ideas are similar.

Conceptually, Artifactory may expose:

```text
local repositories
remote repositories
virtual repositories
```

A local repository stores artifacts directly managed by the organization.

A remote repository proxies another repository.

A virtual repository can provide one logical endpoint across multiple underlying repositories.

Conceptually:

```text
Maven
  |
  v
Artifactory Virtual Repository
  |
  +-- Internal Releases
  |
  +-- Internal Snapshots
  |
  +-- Maven Central Remote
```

The beginner-level concept to remember is:

```text
Nexus and Artifactory can sit between Maven and artifact sources.
```

They can store internal artifacts and proxy external artifacts.

# 17.20 Internal Maven Repositories

Suppose VERIQTA creates:

```text
veriqta-security-library
```

The library is packaged as:

```text
veriqta-security-library-1.0.0.jar
```

Its coordinates are:

```text
groupId:
com.veriqta

artifactId:
veriqta-security-library

version:
1.0.0
```

The artifact may be deployed to an internal repository.

Another project declares:

```xml
<dependency>
    <groupId>com.veriqta</groupId>
    <artifactId>veriqta-security-library</artifactId>
    <version>1.0.0</version>
</dependency>
```

Maven then resolves it through the configured repository infrastructure.

The application does not need someone to manually copy the JAR into the project.

That is the same dependency-management principle you learned earlier, now applied inside an organization.

# 17.21 Maven Central Proxying

In an enterprise environment, Maven may not be allowed to communicate directly with Maven Central.

Instead:

```text
Maven
  |
  X
Direct Maven Central access blocked
```

The approved architecture might be:

```text
Maven
  |
  v
Corporate Repository Manager
  |
  v
Maven Central
```

The repository manager becomes a proxy.

When Maven requests an artifact:

```text
org.example:library:1.0.0
```

the flow may be:

```text
1. Maven requests artifact

2. Repository manager checks cache

3. If cached:
      return artifact

4. If not cached:
      request artifact upstream

5. Validate/store artifact

6. Return artifact to Maven
```

This is one reason Maven mirrors are important.

---

# 17.22 What Is a Maven Mirror?

A Maven mirror tells Maven to use one repository endpoint in place of another repository or set of repositories.

Mirrors are configured inside:

```xml
<mirrors>
```

Example:

```xml
<settings>

    <mirrors>

        <mirror>
            <id>company-mirror</id>
            <name>Company Maven Mirror</name>
            <url>https://repo.example.com/maven</url>
            <mirrorOf>central</mirrorOf>
        </mirror>

    </mirrors>

</settings>
```

This tells Maven, conceptually:

```text
When you would use Central,
use company-mirror instead.
```

So:

```text
Before

Maven
  |
  v
Maven Central


After

Maven
  |
  v
Company Mirror
  |
  v
Maven Central
```

---

# 17.23 Understanding `<mirrorOf>`

The important mirror field is:

```xml
<mirrorOf>
```

For example:

```xml
<mirrorOf>central</mirrorOf>
```

means the mirror applies to the repository with the ID:

```text
central
```

A common enterprise configuration may use:

```xml
<mirrorOf>*</mirrorOf>
```

The `*` means the mirror is intended to cover all repository IDs according to Maven's mirror matching rules.

Conceptually:

```text
Repository A --\
Repository B ----> Enterprise Mirror
Repository C --/
```

This can force repository access through an approved repository manager.

However, mirror patterns can become more sophisticated.

Do not blindly copy a complex `mirrorOf` expression from the internet.

A badly configured mirror can prevent Maven from reaching repositories it genuinely needs.

---

# 17.24 Mirror Versus Repository

These concepts are easy to confuse.

A repository says:

```text
This is a place where Maven artifacts may exist.
```

A mirror says:

```text
When Maven tries to use certain repositories, use this endpoint instead.
```

For example:

```text
POM says:
Use repository X

settings.xml says:
Mirror X through repository Y
```

Then Maven may effectively use Y.

The mirror is a routing decision.

---

# 17.25 Why Organizations Use Mirrors

Mirrors can help organizations:

* Centralize external artifact access
* Route Maven Central through Nexus or Artifactory
* Cache artifacts
* Apply repository policy
* Reduce direct internet access
* Improve auditability
* Restrict unapproved repositories
* Provide a consistent repository endpoint

Without a mirror:

```text
Developer
   |
   +-- Central
   +-- Repository A
   +-- Repository B
   +-- Repository C
```

With enterprise routing:

```text
Developer
   |
   v
Repository Manager
   |
   +-- Central
   +-- Approved Repository A
   +-- Approved Repository B
```

This is much easier for an organization to control.

# 17.26 Mirrors and Credentials

Suppose your mirror is:

```xml
<mirror>
    <id>company-mirror</id>
    <url>https://repo.example.com/maven</url>
    <mirrorOf>*</mirrorOf>
</mirror>
```

and the repository requires authentication.

Your server configuration may use the same ID:

```xml
<server>
    <id>company-mirror</id>
    <username>example-user</username>
    <password>example-password</password>
</server>
```

The relationship is:

```text
Mirror
ID = company-mirror
        |
        v
Server credentials
ID = company-mirror
```

The IDs allow Maven to associate credentials with the server it contacts.

This is a common source of authentication problems.

If the IDs do not match correctly, Maven may reach the repository but fail to authenticate.

---

# 17.27 What Is a Proxy?

A repository mirror and a network proxy are not the same thing.

A repository mirror handles artifact repository routing.

A network proxy controls network traffic.

A company may require outbound web traffic to pass through a proxy.

Instead of:

```text
Maven
  |
  v
Internet
```

the architecture becomes:

```text
Maven
  |
  v
Corporate Proxy
  |
  v
Internet
```

Maven can configure this in:

```xml
<proxies>
```

---

# 17.28 Basic Proxy Configuration

Example:

```xml
<settings>

    <proxies>

        <proxy>
            <id>corporate-proxy</id>
            <active>true</active>
            <protocol>http</protocol>
            <host>proxy.example.com</host>
            <port>8080</port>
        </proxy>

    </proxies>

</settings>
```

Let's break this down.

```xml
<id>corporate-proxy</id>
```

provides a name for the proxy configuration.

```xml
<active>true</active>
```

enables it.

```xml
<protocol>http</protocol>
```

defines the proxy protocol.

```xml
<host>proxy.example.com</host>
```

defines the proxy server.

```xml
<port>8080</port>
```

defines the network port.

The flow becomes:

```text
Maven
  |
  v
proxy.example.com:8080
  |
  v
External Repository
```

---

# 17.29 Authenticated Proxies

Some corporate proxies require authentication.

Conceptually, Maven can configure:

```xml
<proxy>
    <id>corporate-proxy</id>
    <active>true</active>
    <protocol>http</protocol>
    <host>proxy.example.com</host>
    <port>8080</port>
    <username>example-user</username>
    <password>example-password</password>
</proxy>
```

Again, never use real credentials in documentation, screenshots, public repositories, or examples.

If your organization manages the proxy, follow its approved credential mechanism rather than inventing your own configuration.

---

# 17.30 Non-Proxy Hosts

Sometimes traffic to internal systems should not pass through the corporate proxy.

For example:

```text
repo.internal.example.com
```

may be reachable directly inside the company network.

Maven proxy configuration can define non-proxy hosts.

Conceptually:

```xml
<nonProxyHosts>localhost|*.example.internal</nonProxyHosts>
```

This means certain hosts can bypass the configured proxy.

The architecture becomes:

```text
                  +--> Internal Repository
                  |
Maven ------------+
                  |
                  +--> Corporate Proxy --> Internet
```

Incorrect proxy exclusion configuration can cause confusing connectivity failures.

---

# 17.31 Proxy Troubleshooting

Suppose Maven reports:

```text
Connection timed out
```

or:

```text
Connection refused
```

Do not immediately assume Maven Central is unavailable.

Ask:

1. Does this network require a proxy?
2. Is Maven configured to use it?
3. Is the proxy hostname correct?
4. Is the port correct?
5. Does the proxy require authentication?
6. Should the repository bypass the proxy?
7. Can another network tool reach the repository?
8. Does Maven work from a different network?

A useful reasoning model is:

```text
Maven
  |
  v
Network configuration
  |
  +-- DNS
  +-- Proxy
  +-- Firewall
  +-- TLS
  +-- Repository
```

A dependency resolution error is not always a dependency problem.

It may be a network-path problem.

# 17.32 Profiles in `settings.xml`

You learned Maven profiles in Part 16.

Profiles can also exist inside:

```text
settings.xml
```

Example:

```xml
<settings>

    <profiles>

        <profile>
            <id>enterprise</id>

            <properties>
                <company.environment>true</company.environment>
            </properties>
        </profile>

    </profiles>

</settings>
```

This is different from putting the profile in `pom.xml`.

The settings profile belongs to the Maven environment rather than the project source.

---

# 17.33 Active Profiles

A settings file can explicitly activate profiles:

```xml
<activeProfiles>
    <activeProfile>enterprise</activeProfile>
</activeProfiles>
```

A larger example:

```xml
<settings>

    <profiles>

        <profile>
            <id>enterprise</id>

            <properties>
                <company.environment>true</company.environment>
            </properties>
        </profile>

    </profiles>

    <activeProfiles>
        <activeProfile>enterprise</activeProfile>
    </activeProfiles>

</settings>
```

Now the profile can become active automatically for Maven using those settings.

Verify active profiles with:

```bash
mvn help:active-profiles
```

This is especially useful when:

```text
Build works on Developer A's laptop
Build fails on Developer B's laptop
```

One possibility is that their settings profiles differ.

---

# 17.34 Project Profiles Versus Settings Profiles

Use the distinction:

```text
POM profile
   |
   v
Project-related build variation


Settings profile
   |
   v
User/environment Maven configuration
```

Do not move ordinary project build logic into a developer's private `settings.xml`.

Otherwise:

```text
Developer A
has hidden configuration

Developer B
does not

CI
does not

Result:
different builds
```

Project behavior that everyone needs should normally remain visible in the project.

# 17.35 Plugin Groups

Maven plugins have coordinates.

A plugin may conceptually be identified by:

```text
groupId
artifactId
```

Maven supports plugin groups in `settings.xml`.

Example:

```xml
<pluginGroups>
    <pluginGroup>com.example.maven.plugins</pluginGroup>
</pluginGroups>
```

This can allow Maven to consider additional plugin groups when resolving shortened plugin prefixes.

This feature is less central to everyday beginner Maven use than repositories, mirrors, servers, and proxies, but you should recognize:

```xml
<pluginGroups>
```

when you encounter enterprise Maven settings.

# 17.36 Authentication to Private Repositories

Suppose Maven needs:

```text
com.veriqta:internal-platform-library:2.0.0
```

The artifact exists only in the enterprise repository.

The flow might be:

```text
pom.xml
   |
   v
Dependency coordinates
   |
   v
Maven
   |
   v
settings.xml
   |
   +-- repository routing
   +-- credentials
   |

Enterprise Repository
   |

Artifact
```

```text
Repository

200 response / artifact download
```

```text
401
```

# 17.37 Understanding `401 Unauthorized`

A `401` generally indicates an authentication problem.

The server is effectively saying:

```text
I cannot accept this request as authenticated.
```

Common causes include:

* Missing credentials
* Wrong username
* Wrong password or token
* Expired token
* Incorrect server ID
* Maven not reading the expected settings file
* Authentication mechanism changed
* CI secret unavailable

Suppose Maven reports an error similar to:

```text
status: 401 Unauthorized
```

Do not delete `.m2/repository` as your first response.

That does not fix invalid credentials.

Instead investigate authentication.

---

# 17.38 Troubleshooting a 401 Error

Use this reasoning process.

### Problem

Maven cannot download from the private repository.

### What you see

Something similar to:

```text
401 Unauthorized
```

### Possible cause

Maven reached the repository, but authentication failed.

### Investigate

Check:

```bash
mvn help:effective-settings
```

Confirm the expected server configuration exists.

Then compare IDs.

For example:

```text
Repository ID:
veriqta-private

Server ID:
veriqta-private
```

If instead:

```text
Repository ID:
veriqta-private

Server ID:
veriqta-repository
```

Maven may not associate the credentials as expected.

Also verify:

* Username or token is valid
* Credential has not expired
* CI secret is actually available
* Correct settings file is being used

### Fix

Correct the credential source or ID mapping.

### Verify

Run the Maven operation again.

For example:

```bash
mvn clean verify
```

or the appropriate dependency or deployment command.

---

# 17.39 Understanding `403 Forbidden`

A `403` usually means the server understood the request but refuses the requested operation.

Conceptually:

```text
401
"Who are you? Authentication failed or is required."

403
"I know enough about this request, but access is not allowed."
```

The exact behavior depends on the repository system and authentication setup, but this distinction is useful.

Possible `403` causes include:

* User lacks repository permission
* User can download but cannot deploy
* User can access releases but not snapshots
* Repository policy blocks the operation
* Token lacks required scope
* Artifact path is restricted

---

# 17.40 A Realistic 403 Scenario

Suppose a developer can run:

```bash
mvn dependency:resolve
```

successfully.

But:

```bash
mvn deploy
```

fails with:

```text
403 Forbidden
```

This tells us something important.

Authentication may be working.

The account may have:

```text
read permission
```

but not:

```text
deploy/write permission
```

The troubleshooting model is:

```text
Download succeeds
      |
      v
Authentication probably works
      |
      v
Deploy fails with 403
      |
      v
Investigate authorization
```

Do not immediately change the password.

Check repository permissions.

# 17.41 Authentication Versus Authorization

These two words are related but different.

Authentication asks:

```text
Who are you?
```

Authorization asks:

```text
What are you allowed to do?
```

Example:

```text
Username + token
       |
       v
Authentication
       |
       v
Identity established
       |
       v
Authorization check
       |
       +-- download allowed?
       +-- upload allowed?
       +-- delete allowed?
       +-- release allowed?
```

This distinction matters well beyond Maven.

You will encounter it in:

* Cloud platforms
* Kubernetes
* CI/CD systems
* Git hosting
* APIs
* Databases
* Linux
* Artifact repositories

# 17.42 Credential Security

A settings file may contain credentials, so it must be treated as sensitive.

Do not:

* Commit personal `settings.xml` containing secrets to Git
* Paste repository passwords into public issues
* Put credentials in screenshots
* Send credentials in chat channels
* Hardcode production passwords into POMs
* Print credentials in CI logs

On a Unix-like system, inspect file permissions:

```bash
ls -l ~/.m2/settings.xml
```

If the file contains sensitive information, restrict access appropriately according to your operating system and organizational policy.

For example, on a personal Unix-like workstation:

```bash
chmod 600 ~/.m2/settings.xml
```

means:

```text
Owner:
read + write

Group:
no permissions

Others:
no permissions
```

Verify:

```bash
ls -l ~/.m2/settings.xml
```

You may see something similar to:

```text
-rw------- ... settings.xml
```

This protects the file from other ordinary local users, but it does not encrypt the credentials inside it.

File permissions and credential encryption solve different problems.

---

# 17.43 Plaintext Password Problem

A simple Maven server configuration may contain:

```xml
<server>
    <id>private-repository</id>
    <username>example-user</username>
    <password>example-password</password>
</server>
```

The problem is obvious.

Anyone who can read the file can read the password.

Maven provides a password encryption mechanism intended to avoid storing certain server and proxy passwords as immediately readable plaintext.

However, beginners need to understand the security boundary correctly.

Maven password encryption is not a complete enterprise secrets-management platform.

It should not be treated as equivalent to:

* Vault
* Cloud secret managers
* CI secret stores
* Hardware-backed credential systems

It is a Maven credential-protection mechanism.

---

# 17.44 Maven Password Encryption Concept

At a high level, Maven's password encryption workflow involves:

```text
Master password
      |
      v
Maven security configuration
      |
      v
Encrypt server password
      |
      v
Encrypted-looking value
      |
      v
settings.xml
```

The purpose is to avoid leaving the repository password as obvious plaintext in `settings.xml`.

Conceptually:

```text
Before

<password>MyRealPassword</password>


After

<password>{encrypted-value}</password>
```

Maven can use its security configuration to recover the credential when needed.

The exact commands and supported behavior can vary with Maven generation and tooling, so always use the documentation appropriate to the Maven version deployed by your organization.

The important beginner concept is:

```text
Do not assume that putting a password in settings.xml automatically makes it secure.
```

# 17.45 CI/CD Credentials

CI/CD changes the situation.

A CI runner should not depend on Ann's personal:

```text
~/.m2/settings.xml
```

The build environment needs its own credential strategy.

Conceptually:

```text
CI Pipeline
    |
    v
Secret Store
    |
    v
Repository Credentials
    |
    v
Maven Configuration
    |
    v
Private Repository
```

A pipeline platform may securely store:

```text
MAVEN_REPOSITORY_USERNAME
MAVEN_REPOSITORY_TOKEN
```

and expose them only to authorized jobs.

The exact mechanism depends on the CI platform.

The important principle is:

```text
Credentials should enter the build securely at execution time.

They should not live permanently in the project's source code.
```

# 17.46 Environment Variables

Environment variables are one mechanism used to supply values to build environments.

Suppose the environment provides:

```text
MAVEN_REPO_USER
MAVEN_REPO_PASSWORD
```

Maven expressions can access environment variables through the `env` namespace in supported configuration contexts:

```text
${env.MAVEN_REPO_USER}
```

and:

```text
${env.MAVEN_REPO_PASSWORD}
```

Conceptually:

```text
CI Secret Store
      |
      v
Environment Variable
      |
      v
Maven configuration
      |
      v
Repository authentication
```

But environment variables are not automatically perfectly secure.

Secrets can still leak through:

* Debug output
* Shell tracing
* Process configuration
* Misconfigured CI logs
* Generated files
* Child processes

Treat them as sensitive.

---

# 17.47 Never Echo Secrets for Debugging

Suppose a pipeline cannot authenticate.

Do not debug by doing:

```bash
echo "$MAVEN_REPO_PASSWORD"
```

That may expose the password in logs.

Instead, test non-sensitive properties of the environment.

For example, your CI system may provide secure ways to confirm that a secret exists without displaying its value.

The troubleshooting question should be:

```text
Was the credential supplied?
```

not:

```text
What is the credential? Print it for me.
```

This is an important DevOps security habit.

# 17.48 Repository Deployment Credentials

Remember the lifecycle phase:

```text
deploy
```

When Maven deploys an artifact:

```bash
mvn deploy
```

the flow may be:

```text
Source
   |
   v

   v
Test
   |
   v
Package
   |
   v
Verify
   |
   v
Install locally
   |
```

```text
release artifacts
```

from:

```text
snapshot artifacts
```

For example:


may go to a release repository.

While:

```text
1.1.0-SNAPSHOT
```

may go to a snapshot repository.

Conceptually:

```text
Maven Build
    |
    +-- 1.0.0
    |      |
    |      v
    |   Releases
    |
    +-- 1.1.0-SNAPSHOT
           |

        Snapshots
```

# 17.50 SSL and TLS Repository Connections

Most modern repository connections use HTTPS.

For example:

```text
https://repo.example.com
```

HTTPS uses TLS to protect network communication.

Very roughly:

```text
Maven
  |
  v
TLS connection
  |
  v
Repository Server
```

TLS helps Maven:

* Encrypt traffic
* Verify the server's identity through certificates
* Protect credentials and artifacts while travelling over the network

When certificate validation fails, Maven may refuse the connection.

That is usually a security feature, not Maven being unnecessarily difficult.

---

# 17.51 Common Certificate Errors

You may encounter messages involving terms such as:

```text
PKIX path building failed
certificate
SSLHandshakeException
unable to find valid certification path
```

These often indicate a trust problem.

Conceptually:

```text
Maven / Java
      |
      v
Repository presents certificate
      |
      v
Java validates trust chain
      |
      +-- trusted -> continue
      |
      +-- not trusted -> connection fails
```

This often appears in corporate environments using:

* Internal certificate authorities
* TLS inspection
* Internal repository certificates
* Custom trust chains

---

# 17.52 Do Not "Fix" TLS by Disabling Security

A dangerous beginner response is:

```text
Certificate validation failed.

Therefore, disable certificate checking.
```

Do not make that your default solution.

The real question is:

```text
Why does Java not trust this certificate chain?
```

Possible causes include:

* Required corporate CA certificate is missing
* Repository certificate is expired
* Certificate hostname does not match
* Server is misconfigured
* TLS-inspection proxy presents a corporate certificate
* Wrong Java trust store is being used

The safe troubleshooting process is:

```text
Observe certificate error
        |
        v
Identify repository host
        |
        v
Inspect certificate chain
        |
        v
Determine expected CA
        |
        v
Correct trust configuration
        |
        v
Retry
```

Do not blindly bypass TLS verification in production environments.

---

# 17.53 Java Matters for Maven TLS

Remember:

```text
Maven requires Java.
```

Maven network operations run in the Java environment Maven is using.

That means certificate trust problems may depend on:

```text
JAVA_HOME
Java installation
Java trust store
JDK version
```

This is another reason:

```bash
mvn -version
```

is useful.

It tells you which Java runtime Maven is actually using.

Suppose:

```text
java -version
```

appears correct, but Maven still has a certificate problem.

Check:

```bash
mvn -version
```

You may discover Maven is using a different Java installation.

# 17.54 Troubleshooting SSL Repository Errors

### Problem

Maven cannot connect to an HTTPS artifact repository.

### What the beginner sees

Something involving:

```text
PKIX
SSLHandshakeException
certificate path
```

### Possible cause

The Java runtime Maven uses does not trust the repository's certificate chain.

### Investigate

First:

```bash
mvn -version
```

Identify:

```text
Java version
Java home
```

Then confirm the repository URL.

Determine whether:

* The certificate is valid
* The hostname matches
* A corporate proxy is intercepting TLS
* An internal CA is involved
* Your organization provides a required CA certificate

### Fix

Use the organization's approved trust configuration.

Do not download random certificates from unknown sources.

Do not disable TLS verification as a shortcut.

### Verification

Retry the Maven operation and confirm that the TLS handshake succeeds.

# 17.55 Troubleshooting Repository Resolution Systematically

Suppose Maven says:

```text
Could not transfer artifact
```

That message alone does not tell you the root cause.

The failure could occur at several layers.

Use this model:

```text
Maven command
     |
     v
Dependency coordinates
     |
     v
Repository selection
     |
     v
Mirror selection
     |
     v
Proxy/network
     |
     v
DNS
     |
     v
TLS
     |
     v
Authentication
     |
     v
Authorization
     |
     v
Artifact lookup
```

Different failures indicate different layers.

For example:

```text
Unknown host
→ DNS/network

Connection timed out
→ network/proxy/firewall

PKIX path building failed
→ TLS/certificate trust

401
→ authentication

403
→ authorization/policy

404
→ artifact/path may not exist

Could not find artifact
→ coordinates/repository/version problem
```

This is a much better troubleshooting model than repeatedly deleting `.m2`.

---

# 17.56 Why Deleting `.m2` Is Not a Universal Fix

Beginners sometimes learn:

```bash
rm -rf ~/.m2/repository
```

as a supposed Maven troubleshooting command.

This deletes the local Maven repository.

It can cause Maven to redownload a large amount of data.

It does not solve:

* Wrong credentials
* 403 permissions
* Proxy problems
* DNS failures
* Incorrect repository URLs
* TLS trust errors
* Wrong artifact coordinates
* Broken settings IDs

Deleting the entire repository should not be your first troubleshooting step.

If one cached artifact is genuinely corrupted, investigate and remove only the affected artifact directory when appropriate.

For example:

```text
~/.m2/repository/com/example/library/1.0.0/
```

is far more targeted than deleting everything.

Always understand what you are deleting before using `rm -rf`.

# 17.57 Debugging Maven Repository Problems

Maven provides additional logging with:

```bash
mvn -X <phase-or-goal>
```

For example:

```bash
mvn -X dependency:resolve
```

`-X` enables Maven debug output.

This can reveal detailed information about:

* Repository selection
* Mirrors
* Artifact resolution
* Plugins
* Settings
* Transport behavior

However, debug logs can be large and may reveal sensitive infrastructure information.

Do not post complete enterprise Maven debug logs publicly without reviewing them.

Another useful option is:

```bash
mvn -e <phase-or-goal>
```

which displays more exception information.

For example:

```bash
mvn -e package
```

Use detailed output to gather evidence, not simply to generate more text.

# 17.63 Developer Credentials Versus CI Credentials

A developer and CI pipeline should not necessarily share one credential.

A better model is:

```text
Developer
   |
   v
Developer identity
   |
   v
Repository permissions


CI Build
   |
   v
Machine/service identity
   |
   v
Repository permissions
```

This improves:

* Auditing
* Credential rotation
* Least privilege
* Incident response
* Access revocation

If a developer leaves an organization, their account can be revoked without breaking CI.

If CI credentials are compromised, they can be rotated independently.

# 17.68 Add a Mirror Conceptually

Do not point your working Maven environment at a fake repository and expect builds to succeed.

For learning purposes, understand the structure:

```xml

        <id>enterprise-repository</id>
        <name>Enterprise Maven Repository</name>
```

```text
Maven repository request
       |
       v
mirrorOf matching
       |
       v
enterprise-repository
       |
       v
https://repo.example.com/maven
```

Because our URL is only an example, do not use it for a real build.

# 17.70 Troubleshooting Lab

Imagine Maven reports:

```text
401 Unauthorized
```

Work through the problem without guessing.

### Observe

```text
401
```

### Interpret

The request reached an HTTP server.

Authentication is likely involved.

### Check

1. Which repository did Maven contact?
2. Which mirror was selected?
3. What is its ID?
4. Is there a matching `<server>`?
5. Are credentials actually available?
6. Has the token expired?
7. Is Maven reading the correct settings file?

Useful commands:

```bash
mvn help:effective-settings
```

and when appropriate:

```bash
mvn -X dependency:resolve
```

### Fix

Correct the actual authentication problem.

### Verify

Retry the operation.

Do not:

```text
randomly delete dependencies
change Java versions
disable SSL
add random repositories
```

unless evidence points to those areas.

# 17.72 Security Checklist for Maven Repository Access

Before considering an enterprise Maven configuration ready, verify:

* No repository passwords are committed to Git.
* No API tokens are hardcoded in `pom.xml`.
* CI credentials come from an approved secret store.
* Server IDs match repository or mirror IDs correctly.
* HTTPS is used for sensitive repository traffic.
* Certificate validation is not casually disabled.
* Developers have only the repository permissions they need.
* CI service accounts use least privilege.
* Release deployment credentials are restricted.
* Credentials can be rotated.
* Debug logs are reviewed before being shared.
* Internal repository URLs and usernames are treated appropriately.
* Random external repositories are not added without review.

# 17.73 What Maven Is Doing in an Enterprise Build

When you eventually run:

```bash
mvn clean verify
```

there may be much more happening than the terminal output initially suggests.

Conceptually:

```text
1. Start Maven

2. Find Maven configuration

3. Read global settings

4. Read user settings

5. Read project POM

6. Determine active profiles

7. Determine repository mirrors

8. Determine proxy configuration

9. Determine repository authentication

10. Build effective project model

11. Resolve plugins

12. Resolve dependencies

13. Check local repository

14. Contact enterprise repository when necessary

15. Repository manager checks cache/internal storage

16. Repository manager may contact Maven Central

17. Artifacts return to Maven

18. Maven caches artifacts locally

19. Maven executes lifecycle phases

20. Plugins compile, test and package the application
```

This is why a Maven error that appears during:

```text

```

may have nothing to do with your Java source code.

# 17.77 Knowledge Check Answers

### Answer 1

Because the POM is normally committed and shared. Hardcoded credentials could enter Git history and become exposed to developers, CI systems, forks, backups, or other systems.

### Answer 2

Usually:

```text
~/.m2/settings.xml
```

### Answer 3

Global settings belong to the Maven installation. User settings belong to an individual user's Maven environment and can customize relevant global configuration.

### Answer 4

It identifies a server configuration and allows Maven to associate credentials with the repository or server endpoint that uses the corresponding ID.

### Answer 5

Because Maven uses the ID relationship to locate the appropriate authentication configuration.

### Answer 6

A mirror redirects Maven artifact repository access. A proxy routes network traffic.

### Answer 7

To centralize artifact access, cache external artifacts, host private artifacts, enforce repository policies, control access, and reduce direct external repository dependency.

### Answer 8

Authentication determines identity. Authorization determines what that identity is permitted to do.

### Answer 9

Usually an authentication problem, such as missing, invalid, expired, or incorrectly associated credentials.

### Answer 10

Usually the request is understood but the operation is not permitted, often because of repository authorization or policy.

### Answer 11

Because certificate validation protects the integrity and identity of the HTTPS connection. The correct response is to investigate and fix the trust chain or certificate configuration.

### Answer 12

It shows Maven's effective settings and helps investigate configuration involving profiles, mirrors, proxies, servers, and the local repository.

### Answer 13

It tells Maven to use the specified user settings file for that invocation rather than relying only on the normal user settings location.

### Answer 14

Dedicated CI credentials support least privilege, independent rotation, auditing, revocation, and separation between human and machine identities.

### Answer 15

Because a `401` is normally related to authentication. Deleting cached dependencies does not repair incorrect credentials or server-ID configuration.

# 17.78 What You Should Now Understand

You should now understand that Maven configuration extends beyond the project itself.

The key separation is:

```text

→ project configuration

settings.xml
→ Maven user/environment configuration
```

You should understand:

```text
~/.m2/settings.xml
```

as Maven's usual user settings location and recognize that Maven can also have global settings associated with the Maven installation.

You should understand the purpose of:

```text
<servers>
<mirrors>
<proxies>
<profiles>
<activeProfiles>
<pluginGroups>
<localRepository>
```

You should understand how repository IDs connect configuration:

```text
Repository / Mirror ID
        |
        v
Server ID
        |
        v
Credentials
```

You should understand the role of enterprise repository managers such as Nexus Repository and JFrog Artifactory:

```text

    |
    v

    |
    v
Enterprise Repository Manager
    |
    +-- Internal artifacts
    +-- Release artifacts
```

That troubleshooting mindset becomes increasingly important as Maven moves from a developer's laptop into CI/CD and enterprise software delivery.
