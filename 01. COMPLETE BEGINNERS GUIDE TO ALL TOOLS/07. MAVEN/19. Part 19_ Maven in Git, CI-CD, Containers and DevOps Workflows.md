# Part 19: Maven in Git, CI/CD, Containers and DevOps Workflows

In the previous parts, you learned Maven as a build and project-management system.

You learned how Maven can:

* Compile Java source code
* Run automated tests
* Resolve dependencies
* Package applications
* Create JAR and WAR artifacts
* Install artifacts into the local Maven repository
* Publish artifacts to remote repositories
* Manage plugins and build configuration

# 19.1 Maven in a Real Development Workflow

Consider a Java application:

```text
veriqta-platform
```

A developer changes:

```text
src/main/java/com/veriqta/App.java
```

The developer might first run:

```bash
mvn test
```

or:

```bash
mvn verify
```

locally.

If the build succeeds, the developer commits the changes:

```bash
git add .
git commit -m "Add application health check"
```

The commit is pushed:

```bash
git push
```

A CI system detects the change.

The CI system checks out the repository and runs the project's automated build.

For example:

```bash
./mvnw verify
```

If verification succeeds, later pipeline steps might:

1. Publish a Maven artifact.
2. Build a Docker image.
3. Push the image to a container registry.
4. Promote an approved artifact or image.
5. Trigger or support deployment to an environment.

The important principle is:

```text
Developer machine
     |
     v
Source control
     |
     v
Automated build environment
     |
     v
Tested artifact
```

The developer's laptop should not be the only place where the project can successfully build.

---

# 19.2 Why CI Builds Matter

Suppose a developer says:

```text
"It works on my machine."
```

That does not prove the project can be built reliably elsewhere.

Their laptop may contain:

* Locally installed dependencies
* Uncommitted configuration
* A different JDK
* A different Maven version
* Environment variables nobody documented
* Files that are not in Git
* Credentials stored locally
* Old generated classes
* Cached dependencies
* Manually installed internal artifacts

A CI build asks a more useful question:

```text
Can this source revision be built in a controlled environment?
```

The desired model is:

```text
Git Commit
    |
    v
Known Build Environment
    |
    v
Known Build Process
    |
    v
Known Result
```

This is a foundation of repeatable software delivery.

---

# 19.3 Maven and Git Solve Different Problems

Beginners sometimes mix Maven and Git because both appear in the same workflow.

They have different responsibilities.

Git primarily manages source history.

Maven primarily manages the Java project build.

Think:

```text
Git
→ Which source version are we working with?

Maven
→ How do we turn that source into a tested artifact?
```

A simplified workflow is:

```text
Source Files
    |
    v
Git
    |
    v
Commit
    |
    v
CI
    |
    v
Maven
    |
    v
Build Artifact
```

Git does not replace Maven.

Maven does not replace Git.

---

# 19.4 What Belongs in Git?

A Maven project's Git repository normally contains the files required to understand, build, test, and maintain the project.

A project might look like:

```text
veriqta-platform/
├── .gitignore
├── .mvn/
├── mvnw
├── mvnw.cmd
├── pom.xml
├── README.md
├── Dockerfile
└── src/
    ├── main/
    │   ├── java/
    │   └── resources/
    └── test/
        ├── java/
        └── resources/
```

Depending on the project, Git may contain:

* Java source files
* Test source files
* `pom.xml`
* Maven Wrapper files
* Non-secret application configuration
* Dockerfile
* CI pipeline definitions
* Documentation
* Scripts required for the build
* Static resources
* Infrastructure configuration where appropriate

The repository should contain enough project information for an authorized developer or CI system to reproduce the intended build without relying on mysterious files from one developer's laptop.

---

# 19.5 What Should Not Normally Be Committed?

Several categories of files generally should not enter source control.

Examples include:

* Maven `target/` output
* IDE-specific temporary files
* Operating-system temporary files
* Local logs
* Local caches
* Passwords
* API keys
* Repository credentials
* Private keys
* Production secrets
* Personal environment configuration
* Generated artifacts that the build can reproduce

For Maven, one of the most important examples is:

```text
target/
```

---

# 19.6 Why `target/` Should Normally Be Ignored

When Maven compiles and packages a project, it creates:

```text
target/
```

This may contain:

```text
target/
├── classes/
├── test-classes/
├── surefire-reports/
├── generated-sources/
└── veriqta-platform-1.0.0.jar
```

These are build outputs.

They are derived from things such as:

```text
Source code
+
POM
+
Resources
+
Dependencies
+
Build configuration
```

If Maven can recreate them, committing them usually creates unnecessary problems.

For example:

```text
Developer A
→ builds target/

Developer B
→ builds different target/

Git
→ sees generated changes
```

That creates noise and can introduce stale output into the repository.

The preferred mental model is:

```text
Git
→ source and build instructions

Maven
→ generated build output

Artifact repository
→ published build artifacts
```

Do not use Git as a substitute for an artifact repository.

---

# 19.7 Understanding `.gitignore`

Git uses:

```text
.gitignore
```

to define untracked files and directories that should normally be ignored.

A simple Maven-oriented `.gitignore` could begin with:

```gitignore
target/

*.log

.DS_Store

.idea/

*.iml
```

The exact entries should match the project and development environment.

The most important Maven entry here is:

```gitignore
target/
```

This tells Git not to start tracking generated files under `target/`.

---

# 19.8 `.gitignore` Does Not Remove Already Tracked Files

This is a common beginner mistake.

Suppose you accidentally committed:

```text
target/
```

Then you add:

```gitignore
target/
```

You may expect Git to immediately stop tracking the existing files.

But `.gitignore` primarily affects untracked files.

If the files are already tracked, you need to remove them from Git's index without necessarily deleting your local build directory.

For example:

```bash
git rm -r --cached target/
```

Then commit the change:

```bash
git add .gitignore
git commit -m "Stop tracking Maven build output"
```

Before running `git rm`, understand what is being removed.

The:

```text
--cached
```

option tells Git to remove the path from the index rather than deleting the working-tree files in the normal way.

Verify afterward:

```bash
git status
```

Always inspect what Git plans to commit.

---

# 19.9 Never Use `.gitignore` as Your Only Secrets Protection

Suppose you create:

```text
credentials.txt
```

containing a real password.

You accidentally commit it.

Later you add:

```gitignore
credentials.txt
```

That does not erase the secret from Git history.

Once a real secret has been committed, treat it as potentially exposed.

The appropriate response can include:

* Revoke or rotate the credential.
* Remove it from current source.
* Assess whether repository history needs remediation.
* Investigate where the credential was exposed.
* Replace the workflow with proper secret management.

Do not assume:

```text
Added to .gitignore
=
secret is safe again
```

It does not.

---

# 19.10 A Maven Project Before Git

Suppose we have:

```text
veriqta-ci-app/
├── pom.xml
└── src/
    ├── main/java/com/veriqta/App.java
    └── test/java/com/veriqta/AppTest.java
```

Build it:

```bash
mvn clean verify
```

Now:

```text
target/
```

appears.

If we initialize Git:

```bash
git init
```

and inspect:

```bash
git status
```

Git may see `target/` as untracked content.

Create:

```text
.gitignore
```

and add:

```gitignore
target/
```

Run:

```bash
git status
```

again.

The generated Maven directory should no longer be offered as normal untracked content.

This demonstrates the separation between:

```text
source
```

and:

```text
build output
```

# 19.11 The Maven Wrapper

So far, we have commonly run:

```bash
mvn verify
```

This assumes the machine already has an appropriate Maven installation available through its `PATH`.

Teams can reduce this dependency by using the Maven Wrapper.

You may see:

```text
mvnw
mvnw.cmd
.mvn/
```

The wrapper allows developers and automation to invoke a project-associated Maven setup rather than requiring everyone to manually install and select Maven in exactly the same way.

On macOS and Linux, you commonly run:

```bash
./mvnw verify
```

On Windows:

```text
mvnw.cmd verify
```

---

# 19.12 What Is `mvnw`?

`mvnw` is the Unix-like launcher script used by the Maven Wrapper.

Instead of:

```bash
mvn test
```

you can run:

```bash
./mvnw test
```

Instead of:

```bash
mvn clean package
```

you can run:

```bash
./mvnw clean package
```

The build goals and phases are still Maven goals and phases.

The wrapper changes how the appropriate Maven runtime is obtained and invoked.

---

# 19.13 What Is `.mvn`?

A Maven Wrapper-enabled project commonly contains Maven-related project configuration under:

```text
.mvn/
```

Wrapper configuration is associated with this project-level Maven setup.

The important beginner mental model is:

```text
Project
   |
   +-- pom.xml
   |
   +-- mvnw
   |
   +-- mvnw.cmd
   |
   +-- .mvn/
```

Together, these make the build environment more self-describing.

---

# 19.14 Why Teams Use Maven Wrapper

Without a wrapper:

```text
Developer A
→ Maven version A

Developer B
→ Maven version B

CI server
→ Maven version C
```

This may not always break the build, but uncontrolled build-tool differences introduce another variable.

With the wrapper, teams can standardize Maven invocation more closely:

```text
Git Repository
      |
      v
Wrapper Configuration
      |
      +--> Developer A
      |
      +--> Developer B
      |
      +--> CI
```

Each environment can run:

```bash
./mvnw verify
```

This is particularly useful in CI.

---

# 19.15 Maven Wrapper Does Not Control Everything

A wrapper helps standardize Maven.

It does not automatically standardize:

* JDK version
* Operating system
* CPU architecture
* Environment variables
* External services
* Network behavior
* Repository contents
* Credentials
* Container runtime
* System packages

For example:

```text
Same Maven Wrapper
+
Java 17 on machine A
+
Java 21 on machine B
```

can still produce different behavior if the project is sensitive to the Java environment.

Therefore reproducibility requires looking at the complete build environment.

---

# 19.16 Reproducible Build Environments

A reproducible build aims to reduce uncontrolled differences between builds.

At a practical beginner level, think about controlling:

```text
Source revision
Maven version
JDK version
Dependencies
Plugin versions
Build configuration
Environment
Artifact inputs
```

A build pipeline should make these as explicit as practical.

For example:

```text
Git Commit
   |
   v
JDK 21
   |
   v
Maven Wrapper
   |
   v
Pinned Plugin Versions
   |
   v
Declared Dependencies
   |
   v
mvn verify
```

This is more predictable than:

```text
"Use whatever Java and Maven happen to be installed."
```

---

# 19.17 Reproducibility Versus Caching

Caching can make builds faster.

But caching should not become a hidden dependency.

For example, imagine a build succeeds only because a developer has:

```text
~/.m2/repository/com/company/old-library/1.0.0/
```

from an earlier manual installation.

A clean CI environment may fail.

That failure can reveal that the build was never truly self-contained.

A healthy question is:

```text
Could this project build from its declared source and authorized repositories in a clean environment?
```

# 19.18 Maven Enters CI/CD

CI means Continuous Integration.

At a practical level, CI automatically validates source changes.

A basic Java CI flow might be:

```text
Developer Push
     |
     v
Git Repository
     |
     v
CI Trigger
     |
     v
Checkout Source
     |
     v
Set Up JDK
     |
     v
Run Maven
     |
     v
Compile
     |
     v
Test
     |
     v
Verify
```

If something fails, the pipeline fails.

This gives the team automated feedback before unverified code moves further through delivery.

---

# 19.19 CI Versus CD

The abbreviation `CD` can refer to:

* Continuous Delivery
* Continuous Deployment

They are related but not identical.

A simplified model is:

```text
Continuous Integration
→ automatically build and test changes

Continuous Delivery
→ keep software in a deployable state and automate delivery steps, often with controlled promotion

Continuous Deployment
→ automatically deploy qualifying changes through to production according to the organization's process
```

Maven commonly plays a strong role in the build and verification portions.

It does not by itself define the organization's entire delivery strategy.

# 19.20 CI Pipeline Stages

A Maven-oriented pipeline might contain conceptual stages such as:

```text
Checkout
   |
   v
Build
   |
   v
Test
   |
   v
Verify
   |
   v
Publish Artifact
   |
   v
Build Container Image
   |
   v
Security Checks
   |
   v
Publish Image
   |
   v
Promote
   |
   v
Deploy
```

Different CI systems represent stages and jobs differently.

Do not focus first on syntax.

Understand the workflow.

---

# 19.21 Maven Phases and Pipeline Stages Are Not the Same Thing

This distinction matters.

Maven has lifecycle phases such as:

```text
compile
test
package
verify
install
deploy
```

A CI platform has jobs or stages such as:

```text
build
test
publish
containerize
deploy
```

They may be mapped together, but they are not the same system.

For example:

```text
CI Stage: Build
    |
    v
./mvnw package
```

or:

```text
CI Stage: Verify
    |
    v
./mvnw verify
```

The CI system orchestrates jobs.

Maven performs the Maven build inside those jobs.

---

# 19.22 Be Careful Not to Repeat Maven Work Unnecessarily

Consider:

```text
Stage 1:
mvn compile

Stage 2:
mvn test

Stage 3:
mvn package

Stage 4:
mvn verify
```

Remember Maven lifecycle behavior.

Running:

```bash
mvn verify
```

already executes earlier phases in the lifecycle.

If every CI stage starts a fresh Maven invocation, earlier work may be repeated.

This is not automatically wrong. Separate jobs can provide useful isolation, parallelism, reporting, or policy boundaries.

But the pipeline designer should understand the cost.

Do not split Maven commands into many stages merely because the Maven lifecycle has many phases.

---

# 19.23 A Simple CI Strategy

For a small project, one CI job might run:

```bash
./mvnw --batch-mode clean verify
```

The:

```text
--batch-mode
```

option, also written:

```text
-B
```

tells Maven to use non-interactive batch behavior suitable for automated environments.

A shorter form is:

```bash
./mvnw -B clean verify
```

This can:

* Clean previous build output
* Compile
* Run tests
* Package
* Execute verification-related work

Then later jobs can handle publishing and deployment only when policy allows them.

# 19.24 Maven in Jenkins

Jenkins is an automation server frequently used for CI/CD workflows.

A simplified Jenkins flow is:

```text
Git Repository
     |
     v
Jenkins Job
     |
     v
Checkout
     |
     v
Set Up Environment
     |
     v
./mvnw verify
     |
     v
Archive / Publish
```

Jenkins pipelines are often defined in a:

```text
Jenkinsfile
```

stored with the source code.

---

# 19.25 A Beginner Jenkins Pipeline

A simplified declarative example is:

```groovy
pipeline {
    agent any

    stages {
        stage('Checkout') {
            steps {
                checkout scm
            }
        }

        stage('Verify') {
            steps {
                sh './mvnw -B clean verify'
            }
        }
    }
}
```

Do not copy this blindly into every environment.

Jenkins agent configuration, JDK availability, operating system, credentials, Maven Wrapper permissions, and organizational Jenkins policies all matter.

The important flow is:

```text
Jenkins
   |
   v
Checkout repository
   |
   v
Execute Maven Wrapper
   |
   v
Receive exit status
   |
   v
Pass or fail pipeline
```

---

# 19.26 Maven Exit Status and CI

When Maven succeeds, the command exits successfully.

When the Maven build fails, it returns a non-zero exit status.

CI systems use command exit status to determine whether a step or job succeeded.

Conceptually:

```text
./mvnw verify
      |
      +--> success
      |      |
      |      v
      |   Continue
      |
      +--> failure
             |
             v
          Stop / mark failed
```

This is why you do not need a human to read:

```text
BUILD FAILURE
```

before the pipeline knows something failed.

# 19.27 Maven in GitHub Actions

GitHub Actions can run workflows based on events in a GitHub repository.

A Java workflow commonly needs to:

1. Check out the repository.
2. Configure a JDK.
3. Run Maven.
4. Optionally cache dependencies.
5. Store or publish artifacts.
6. Perform later delivery steps when appropriate.

A workflow file lives under:

```text
.github/workflows/
```

For example:

```text
.github/
└── workflows/
    └── maven.yml
```

---

# 19.28 A Simple GitHub Actions Maven Workflow

A beginner example could look like:

```yaml
name: Maven CI

on:
  push:
  pull_request:

jobs:
  verify:
    runs-on: ubuntu-latest

    steps:
      - name: Check out repository
        uses: actions/checkout@v4

      - name: Set up Java
        uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
          cache: maven

      - name: Verify project
        run: ./mvnw -B clean verify
```

Understand the flow before the YAML.

```text
push / pull request
      |
      v
GitHub Actions
      |
      v
Runner
      |
      v
Checkout
      |
      v
Java
      |
      v
Maven Wrapper
      |
      v
Verify
```

---

# 19.29 Understanding the GitHub Actions Example

This:

```yaml
on:
  push:
  pull_request:
```

defines events that can trigger the workflow.

This:

```yaml
runs-on: ubuntu-latest
```

selects the runner environment requested by the workflow.

This:

```yaml
uses: actions/checkout@v4
```

checks out repository content onto the runner.

Without source code, Maven has nothing to build.

This:

```yaml
uses: actions/setup-java@v4
```

configures Java.

This:

```yaml
java-version: '21'
```

requests Java 21.

This:

```yaml
cache: maven
```

enables Maven dependency caching support provided by the setup action.

Finally:

```yaml
run: ./mvnw -B clean verify
```

executes the Maven build.

The syntax differs.


# 19.32 Dependency Caching in CI

Maven may download many dependencies into:

```text
~/.m2/repository
```

If every pipeline begins with an empty local repository, the same dependencies may need to be downloaded repeatedly.

Caching can improve build speed.

Conceptually:

```text
Pipeline Run 1
     |
     v
Download dependencies
     |
     v
Cache reusable Maven data

Pipeline Run 2
     |
     v
Restore cache
     |
     v
Reuse eligible dependencies
```

This reduces unnecessary network downloads.

---

# 19.33 A Cache Is Not an Artifact Repository

Do not confuse these.

A CI cache exists mainly to accelerate future jobs or runs.

An artifact repository exists to store and distribute versioned software artifacts.

Think:

```text
CI Cache
→ performance

Artifact Repository
→ authoritative artifact distribution
```

For example:

```text
Maven dependencies cached by CI
```

are not a replacement for:

```text
Nexus / Artifactory / another Maven repository
```

---

# 19.34 Cache Keys and Invalidation

A cache should not be treated as permanently valid.

When dependency declarations change, the pipeline may need a different or refreshed cache.

For Maven, dependency inputs include:

```text
pom.xml
```

and potentially POM files across modules.

A conceptual cache strategy might be:

```text
POM state changes
      |
      v
Cache key changes
      |
      v
Dependencies restored or downloaded appropriately
```

The exact implementation depends on the CI platform.

---

# 19.35 Caching Can Hide Problems

Imagine the CI cache contains an internal artifact that is no longer available from the configured repository.

The build succeeds while the cache exists.

A clean runner later fails.

This reveals a problem:

```text
Build depends on cached state
instead of declared, retrievable dependencies.
```

Occasionally testing from a clean dependency state can reveal these hidden assumptions.

Caching should improve performance, not become undocumented infrastructure.

---

# 19.36 Build Artifacts Between Pipeline Stages

Suppose one CI job creates:

```text
target/veriqta-app-1.0.0.jar
```

A later job needs that exact JAR to build a Docker image.

You have several design options depending on the pipeline.

One is to pass the build output as a CI artifact between jobs.

Conceptually:

```text
Maven Build Job
      |
      v
veriqta-app-1.0.0.jar
      |
      v
CI Artifact Storage
      |
      v
Docker Build Job
```

The Docker job should not necessarily rebuild the application from source if the goal is to containerize the exact artifact that already passed verification.

---

# 19.37 Why Passing the Same Artifact Matters

Consider this poor workflow:

```text
Build Job
→ Maven builds JAR A
→ tests JAR A's source/build state

Docker Job
→ independently rebuilds
→ produces JAR B
→ puts JAR B in image
```

Even if the source appears identical, you have introduced another build.

A stronger artifact-oriented model is:

```text
Build once
     |
     v
Test / Verify
     |
     v
Artifact A
     |
     +--> Publish
     |
     +--> Containerize
     |
     +--> Promote
```

This supports the principle:

```text
Build once
Promote the same artifact
```

where the delivery architecture allows it.

---

# 19.38 CI Artifacts Versus Maven Repository Artifacts

A CI platform may let you upload:

```text
veriqta-app-1.0.0.jar
```

as a pipeline artifact.

A Maven repository can also store:

```text
com.veriqta:veriqta-app:1.0.0
```

They serve overlapping but different purposes.

CI artifacts are often useful for:

* Passing files between jobs
* Retaining logs or reports
* Temporary build outputs
* Pipeline debugging

Maven repositories are designed around:

* Maven coordinates
* Dependency resolution
* Versioned artifact distribution
* Shared consumption

A mature pipeline may use both.

---

# 19.39 Compile Stage

At the Maven level:

```bash
./mvnw compile
```

turns Java source into compiled classes.

Conceptually:

```text
src/main/java
      |
      v
Maven Compiler Plugin
      |
      v
javac
      |
      v
target/classes
```

In CI, compile failure should stop the build.

Examples include:

```text
cannot find symbol
package does not exist
unsupported release
syntax errors
```

Do not continue to packaging when the application cannot compile.

---

# 19.40 Test Stage

Maven can run unit tests with:

```bash
./mvnw test
```

The simplified flow is:

```text
Main source
   |
   v
Compile

Test source
   |
   v
Test compile
   |
   v
Surefire
   |
   v
Tests
   |
   +--> pass
   |
   +--> fail
```

A failed required test should normally fail the pipeline.

CI makes this valuable because the same test policy can run automatically for every qualifying change.

---

# 19.41 Package Stage

For a JAR project:

```bash
./mvnw package
```

eventually creates something like:

```text
target/veriqta-app-1.0.0.jar
```

The pipeline now has a build artifact.

But remember:

```text
package
```

does not mean:

```text
published to artifact repository
```

and it does not mean:

```text
deployed to production
```

It means the project reached Maven's packaging phase.

---

# 19.42 Verify Stage

For many CI builds, this is a useful command:

```bash
./mvnw verify
```

because it executes the lifecycle through verification.

Depending on project configuration, this may include:

* Compilation
* Unit testing
* Packaging
* Integration-test-related work
* Additional verification plugins

The exact behavior depends on the POM and plugins.

Do not assume every project performs the same checks merely because both run:

```bash
mvn verify
```

Inspect the project's build configuration.

---

# 19.43 Artifact Publishing Stage

Once an artifact has passed the required checks, a pipeline may publish it.

For Maven artifacts:

```bash
./mvnw deploy
```

can publish to the remote Maven repository configured for the project.

But publication should usually be controlled.

You may not want every pull request to publish a production release.

A policy might resemble:

```text
Pull Request
    |
    v
Compile + Test + Verify
    |
    X
No release publication


Approved Main Branch Build
    |
    v
Compile + Test + Verify
    |
    v
Publish qualifying artifact
```

The exact rules depend on the organization.

---

# 19.44 Do Not Give Every Pipeline the Same Credentials

A pull-request validation job may only need:

```text
read source
read dependencies
run tests
```

A release job may need:

```text
publish artifact
```

A deployment job may need:

```text
deploy to environment
```

These should not automatically share one highly privileged credential.

Use least privilege:

```text
Job
  |
  v
Required Action
  |
  v
Minimum Required Permission
```

---

# 19.45 Maven and Docker

Maven creates Java artifacts.

Docker packages applications and their runtime requirements into container images.

A common workflow is:

```text
Java Source
    |
    v
Maven
    |
    v
JAR
    |
    v
Docker Build
    |
    v
Container Image
```

For example:

```text
src/
 |
 v
mvn package
 |
 v
target/veriqta-app.jar
 |
 v
docker build
 |
 v
veriqta-app image
```

Maven and Docker are solving different problems.

---

# 19.46 Building a JAR Before Containerization

Suppose:

```bash
./mvnw clean verify
```

produces:

```text
target/veriqta-app-1.0.0.jar
```

A Dockerfile can copy that artifact:

```dockerfile
FROM eclipse-temurin:21-jre

WORKDIR /app

COPY target/veriqta-app-1.0.0.jar app.jar

ENTRYPOINT ["java", "-jar", "app.jar"]
```

Understand every line.

```dockerfile
FROM eclipse-temurin:21-jre
```

selects the base runtime image.

```dockerfile
WORKDIR /app
```

sets `/app` as the working directory inside the image.

```dockerfile
COPY target/veriqta-app-1.0.0.jar app.jar
```

copies the already-built JAR into the image.

```dockerfile
ENTRYPOINT ["java", "-jar", "app.jar"]
```

defines the process that starts when the container runs.

---

# 19.47 The External Maven Build Pattern

With the previous Dockerfile:

```text
CI Runner
    |
    v
./mvnw verify
    |
    v
target/app.jar
    |
    v
docker build
    |
    v
Container Image
```

Maven runs outside Docker.

Docker receives the finished JAR.

Advantages can include:

* Clear separation between Java build and image build
* Easy reuse of the verified JAR
* Straightforward artifact publication
* Easier access to Maven test reports before containerization

But the CI runner must provide the required Java and Maven environment.

---

# 19.48 Building With Maven Inside Docker

Another approach is to run Maven inside the Docker build.

Conceptually:

```text
Source
   |
   v
docker build
   |
   v
Maven build stage
   |
   v
JAR
   |
   v
Runtime stage
   |
   v
Final image
```

This is commonly implemented with a multi-stage Dockerfile.

---

# 19.49 What Is a Multi-Stage Docker Build?

A multi-stage Dockerfile contains multiple:

```dockerfile
FROM
```

instructions.

One stage can contain Maven and a JDK.

Another can contain only the Java runtime needed to run the application.

Conceptually:

```text
BUILD STAGE

Source
  |
  v
Maven + JDK
  |
  v
JAR
  |
  |
  +--------------------+
                       |
                       v
                RUNTIME STAGE

                 Java Runtime
                       |
                       v
                     JAR
                       |
                       v
                 Final Image
```

The final image does not need to include the entire Maven build environment.

---

# 19.50 Beginner Multi-Stage Maven Dockerfile

A simplified example:

```dockerfile
FROM maven:3-eclipse-temurin-21 AS build

WORKDIR /workspace

COPY pom.xml .
COPY src ./src

RUN mvn -B clean package

FROM eclipse-temurin:21-jre

WORKDIR /app

COPY --from=build /workspace/target/veriqta-app-1.0.0.jar app.jar

ENTRYPOINT ["java", "-jar", "app.jar"]
```

This Dockerfile has two stages:

```text
Stage 1
→ build

Stage 2
→ runtime
```

---

# 19.51 Understanding the Build Stage

This line:

```dockerfile
FROM maven:3-eclipse-temurin-21 AS build
```

creates a stage named:

```text
build
```

The stage contains a Maven and Java environment provided by the selected image.

Then:

```dockerfile
WORKDIR /workspace
```

sets the build working directory.

This:

```dockerfile
COPY pom.xml .
```

copies the POM.

This:

```dockerfile
COPY src ./src
```

copies source code.

Then:

```dockerfile
RUN mvn -B clean package
```

runs Maven during image construction.

The resulting JAR is created under the build stage's:

```text
/workspace/target/
```

---

# 19.52 Understanding the Runtime Stage

The second:

```dockerfile
FROM eclipse-temurin:21-jre
```

starts a new stage.

This stage does not inherit all files from the build stage.

Then:

```dockerfile
COPY --from=build /workspace/target/veriqta-app-1.0.0.jar app.jar
```

copies only the desired JAR from the build stage.

The result is conceptually:

```text
Build image contents
Maven
JDK
Source
Build cache
JAR
      |
      | Copy JAR only
      v
Runtime image
JRE
JAR
```

This helps keep build tooling out of the runtime image.

---

# 19.53 Why Not Put Maven in the Final Runtime Image?

The application usually needs Java to run.

It generally does not need Maven to run.

Keeping unnecessary build tooling in the runtime image can:

* Increase image size
* Increase unnecessary software in the runtime environment
* Increase maintenance burden
* Potentially increase attack surface

Think:

```text
Build environment
→ tools required to create software

Runtime environment
→ components required to run software
```

Do not automatically make them identical.

---

# 19.54 Maven Inside Versus Outside Containers

There is no single universal answer.

## Maven outside Docker

```text
CI
 |
 v
Maven
 |
 v
JAR
 |
 v
Docker
```

Benefits can include:

* Clear artifact separation
* Easy Maven test-report collection
* Easy publishing of the JAR independently
* Container build can consume an already verified artifact

## Maven inside Docker

```text
CI
 |
 v
Docker Build
 |
 v
Maven Build Stage
 |
 v
JAR
 |
 v
Runtime Stage
```

Benefits can include:

* Build tool environment described by container image
* Less dependence on host Maven installation
* Consistent containerized build stage

The engineering decision depends on:

* CI architecture
* Caching strategy
* Artifact policy
* Security requirements
* Build speed
* Reproducibility requirements
* Whether the JAR is independently published
* How promotion works

Understand the tradeoff rather than memorizing one pattern.

---

# 19.55 Do Not Accidentally Run Tests Twice Without a Reason

Suppose CI runs:

```bash
./mvnw clean verify
```

Then the Dockerfile runs:

```dockerfile
RUN mvn clean package
```

The project is being built again, and unit tests may run again.

That may be intentional.

But it may also be wasted work.

Ask:

```text
Which build produces the artifact we deploy?

Which build was tested?

Are we rebuilding after verification?

Are both builds using identical inputs?
```

The answers matter more than whether the Dockerfile looks sophisticated.

---

# 19.56 Docker Build Context and Maven Output

Suppose your Dockerfile uses:

```dockerfile
COPY target/veriqta-app.jar app.jar
```

but you run:

```bash
docker build .
```

before Maven has created the JAR.

Docker may fail because the source file does not exist in the build context.

The correct sequence for that design is:

```bash
./mvnw clean package
docker build .
```

Verify first:

```bash
ls -la target
```

Do not troubleshoot Docker networking when the actual problem is simply:

```text
JAR does not exist.
```

---

# 19.57 `.dockerignore`

Docker can use:

```text
.dockerignore
```

to exclude unnecessary content from the Docker build context.

This is different from:

```text
.gitignore
```

A file ignored by Git is not automatically ignored by Docker.

If using a multi-stage build that needs source code, your `.dockerignore` should not exclude files required for the build.

If using an external Maven build and Docker only needs the final JAR, you may be able to use a much smaller build context.

Always design the ignore file around the Dockerfile's actual needs.

---

# 19.58 Maven Artifact Repositories in CI

An enterprise Maven build may need:

```text
CI Runner
    |
    v
Maven
    |
    v
Enterprise Repository Manager
    |
    +--> Internal Libraries
    |
    +--> Approved External Dependencies
    |
    +--> Maven Central Proxy
```

Instead of every build communicating directly with many public repositories, an organization may route dependency access through an internal repository manager.

Benefits can include:

* Centralized access
* Caching
* Internal artifact hosting
* Repository policy
* Auditability
* Dependency availability control

---

# 19.59 Artifact Publishing From CI

Suppose the application version is:

```text
2.3.0
```

A release pipeline may run:

```bash
./mvnw -B deploy
```

Maven reads:

```text
pom.xml
```

and:

```text
settings.xml
```

or the CI-provided equivalent configuration.

The flow becomes:

```text
CI
 |
 v
Maven
 |
 v
Verify Build
 |
 v
Package
 |
 v
Artifact
 |
 v
Authenticate
 |
 v
Remote Maven Repository
```

The credentials should come from the CI platform's secret-management mechanism or another approved secret source.

They should not be hardcoded into the repository.

---

# 19.60 Credentials in Pipelines

A pipeline may need credentials for:

* Private Maven repositories
* Artifact publishing
* Container registries
* Deployment platforms
* Cloud services

Do not write:

```xml
<username>admin</username>
<password>real-production-password</password>
```

into a committed POM.

Likewise, do not put real passwords directly into:

```text
Jenkinsfile
GitHub Actions YAML
.gitlab-ci.yml
Dockerfile
shell scripts committed to Git
```

Instead, secrets should be supplied securely at runtime using the organization's approved secret mechanism.

---

# 19.61 Secrets and Environment Variables

CI systems can expose secret values to jobs without committing them to Git.

For example, Maven settings might reference:

```xml
<username>${env.MAVEN_REPO_USER}</username>
<password>${env.MAVEN_REPO_PASSWORD}</password>
```

Then the CI environment supplies those variables securely.

Conceptually:

```text
Secret Store
    |
    v
Authorized CI Job
    |
    v
Environment / temporary credential injection
    |
    v
Maven
    |
    v
Repository Authentication
```

Environment variables are a transport mechanism, not automatically a complete secrets-management solution.

You must still consider:

* Who can read them
* Whether commands print them
* Whether child processes inherit them
* Whether logs expose them
* How long they exist
* Whether they are rotated
* Whether the CI job actually needs them

---

# 19.62 Never Echo Secrets

This is dangerous:

```bash
echo "$MAVEN_REPO_PASSWORD"
```

Even if the CI platform masks known secrets, do not deliberately print sensitive values.

Also be careful with:

```bash
set -x
```

in shell scripts.

Shell tracing can print commands after expansion and may expose sensitive information depending on how commands are written.

The principle is:

```text
Secret required
    |
    v
Provide only to required process
    |
    v
Never deliberately print it
```

---

# 19.63 Pull Requests and Untrusted Code

This is a critical CI security concept.

Imagine an external contributor opens a pull request and modifies:

```text
Jenkinsfile
```

or:

```text
.github/workflows/build.yml
```

to run something malicious.

If that workflow automatically receives powerful production credentials, the contributor may be able to attempt credential theft or unauthorized actions.

Therefore:

```text
Untrusted code
+
high-privilege secrets
=
dangerous combination
```

CI systems should carefully control which events and branches can access sensitive credentials.

Do not give pull-request validation jobs production deployment secrets unless the security model explicitly requires and safely supports it.

# 19.64 Build Logs Are Operational Evidence

When Maven runs in CI, its console output becomes part of the build record.

Useful information can include:

```text
Maven version
Java version
Modules built
Plugins executed
Tests run
Warnings
Dependency failures
Compilation failures
Artifact names
BUILD SUCCESS
BUILD FAILURE
```

Build logs help answer:

```text
What failed?
Where did it fail?
Which module failed?
Did tests run?
Was packaging reached?
Was publishing attempted?
```

DevOps engineers should learn to read build logs systematically.

---

# 19.65 Reading a Maven CI Failure

Suppose the final output says:

```text
BUILD FAILURE
```

Do not stop there.

Scroll upward and locate the first useful failure.

For example:

```text
[ERROR] COMPILATION ERROR
```

means the failure layer is compilation.

If you see:

```text
Tests run: 12, Failures: 1
```

the failure layer is testing.

If you see:

```text
401 Unauthorized
```

during deployment, investigate repository authentication.

The reasoning process is:

```text
Final Failure
     |
     v
Find first meaningful error
     |
     v
Identify build stage
     |
     v
Form hypothesis
     |
     v
Gather evidence
     |
     v
Fix cause
     |
     v
Re-run
```

---

# 19.66 Example: Compilation Failure in CI

CI runs:

```bash
./mvnw verify
```

and reports:

```text
cannot find symbol
```

Possible causes include:

* Typo in a class or method name
* Missing import
* Missing dependency
* Dependency scope problem
* Generated source missing
* Wrong Java source level
* Code not committed to Git

That last one is important.

The developer's laptop may contain:

```text
Helper.java
```

but if it was never committed, CI does not have it.

Check:

```bash
git status
```

locally.

CI can expose source-control mistakes that local builds hide.

---

# 19.67 Example: Works Locally, Fails in CI

Suppose local:

```bash
mvn verify
```

passes.

CI fails:

```text
Could not find artifact
com.veriqta:internal-library:1.0.0
```

Possible explanation:

The developer previously ran:

```bash
mvn install
```

for that internal library.

So their local:

```text
~/.m2/repository
```

contains the artifact.

CI does not.

The proper fix is not:

```text
copy the developer's .m2 directory into CI
```

Instead, ask:

```text
Should this internal artifact be published to the authorized shared repository?
```

This is exactly why remote artifact repositories exist.

---

# 19.68 Example: Wrong Java Version

Local environment:

```text
Java 21
```

CI environment:

```text
Java 17
```

The build may fail with Java-version-related errors.

Check locally:

```bash
java -version
javac -version
./mvnw -version
```

Check the CI configuration.

Remember that:

```bash
./mvnw -version
```

shows which Java runtime Maven is actually using.

Do not assume the shell's apparent Java configuration and Maven's actual Java environment are always what you expect.

---

# 19.69 Dependency Scanning Concepts

Maven applications can depend on many third-party libraries.

For example:

```text
Application
   |
   +--> Framework A
   |
   +--> Library B
   |       |
   |       +--> Library C
   |
   +--> Library D
```

A vulnerability in a transitive dependency can affect the application even if the developer never explicitly added that library.

Dependency scanning attempts to identify known security problems associated with components in the dependency graph.

Conceptually:

```text
pom.xml
   |
   v
Dependency Graph
   |
   v
Scanner
   |
   v
Known Vulnerability Data
   |
   v
Findings
```

---

# 19.70 Dependency Scanning Is Not the Same as Testing

Unit tests ask questions such as:

```text
Does this code behave as expected?
```

Dependency scanning asks questions such as:

```text
Do known dependency versions have reported security vulnerabilities or policy concerns?
```

They complement each other.

A passing test suite does not prove dependencies are vulnerability-free.

A clean vulnerability scan does not prove the application works correctly.

---

# 19.71 Maven Dependency Visibility

Useful Maven commands include:

```bash
./mvnw dependency:tree
```

This shows the dependency hierarchy.

For example:

```text
com.veriqta:app:jar:1.0.0
+- org.example:library-a:jar:2.0.0
|  \- org.example:library-b:jar:4.1.0
```

This helps answer:

```text
Why is library-b in my application?
```

It may be transitive.

In dependency investigations, always understand:

```text
direct dependency
```

versus:

```text
transitive dependency
```

---

# 19.72 Software Supply-Chain Awareness

Your application is not made only from code your team wrote.

It may include:

```text
Your source
+
Maven plugins
+
Direct dependencies
+
Transitive dependencies
+
JDK
+
Base container image
+
Build actions/plugins
+
CI tooling
```

The software supply chain includes the systems and components involved in producing and delivering software.

A simplified chain is:

```text
Source
  |
  v
Dependencies
  |
  v
Build Tools
  |
  v
CI
  |
  v
Artifact
  |
  v
Container Image
  |
  v
Registry
  |
  v
Deployment
```

A compromise or mistake at one stage can affect downstream software.

---

# 19.73 Pin and Control Build Inputs

Consider a build that depends on:

```text
Unknown Maven version
Latest available JDK
Uncontrolled plugin versions
Random external repositories
Mutable container tags
Unreviewed CI actions
```

The build has many moving pieces.

A stronger approach controls important inputs where practical:

```text
Known source revision
Known JDK
Known Maven Wrapper
Explicit Maven plugin versions
Declared dependency versions
Approved repositories
Reviewed CI configuration
Controlled base images
```

This supports reliability and security.

---

# 19.74 Maven Plugin Supply-Chain Awareness

Dependencies are not the only software Maven downloads.

Maven plugins execute code as part of the build.

For example:

```text
Compiler Plugin
Surefire Plugin
Failsafe Plugin
Resources Plugin
JAR Plugin
Deploy Plugin
```

Therefore plugin governance matters too.

A malicious or compromised build plugin can be especially serious because it executes during the build.

This is one reason you learned earlier to control plugin versions and avoid adding arbitrary repositories.

---

# 19.75 Repository Trust

Do not solve dependency errors by adding random repositories until the build succeeds.

For example, blindly adding:

```xml
<repository>
    ...
</repository>
```

from an unknown website can expand your software supply-chain risk.

Ask:

```text
Who operates this repository?

Why is it required?

Is the artifact available from an approved repository?

Is this repository trusted by the organization?

Can the enterprise repository manager proxy it safely?
```

Availability is not the only concern.

Trust matters.

---

# 19.76 CI Configuration Is Production-Relevant Code

Files such as:

```text
Jenkinsfile
.github/workflows/*.yml
.gitlab-ci.yml
Dockerfile
pom.xml
```

can directly influence what software is built and delivered.

They should receive appropriate review.

A change from:

```bash
./mvnw verify
```

to:

```bash
./mvnw package -DskipTests
```

can materially change validation.

A changed Dockerfile can alter runtime contents.

A changed repository URL can alter dependency sources.

Treat build configuration as engineering code, not disposable administrative text.

# 19.77 Maven With Docker and Artifact Repositories

Now combine Maven publishing with Docker.

One possible workflow is:

```text
Git
 |
 v

 |
 v
Maven Verify
 |
 v
JAR
 |
 +--------------------+
 |                    |
 v                    v
Maven Repository   Docker Build
                        |
                        v
                   Docker Image
```

The JAR may be stored in an artifact repository while the Docker image is stored in a container registry.

These are different artifact systems.

---

# 19.78 Artifact Repository Versus Container Registry

A Maven artifact repository may store:

```text
veriqta-app-1.0.0.jar
veriqta-library-2.1.0.jar
POMs
Maven metadata
```

A container registry stores container images.

For example:

```text
veriqta-app:1.0.0
```

Conceptually:

```text
Maven Repository
→ Maven artifacts

Container Registry
→ container images
```

An enterprise product may support multiple repository formats, but the artifact types and workflows remain conceptually different.

---

# 19.79 Building the Docker Image

Suppose Maven produced:

```text
veriqta-app-1.0.0.jar
```

The next step might be:

```bash
docker build -t veriqta-app:1.0.0 .
```

Break it down:

```text
docker
→ Docker CLI

build
→ build an image

-t
→ assign a tag/name

veriqta-app:1.0.0
→ image name and tag

.
→ use the current directory as build context
```

Afterward:

```bash
docker image ls
```

can help verify the image exists locally.

---

# 19.80 Test the Container Before Publishing

Do not assume:

```text
Maven build succeeded
```

means:

```text
container starts correctly
```

The Docker image introduces additional concerns.

Run it:

```bash
docker run --rm veriqta-app:1.0.0
```

For a web application, port publishing may be required, for example:

```bash
docker run --rm -p 8080:8080 veriqta-app:1.0.0
```

The exact port depends on the application.

Then verify application behavior.

The flow becomes:

```text
Maven Tests
    |
    v
JAR
    |
    v
Docker Build
    |
    v
Container Test
    |
    v
Registry
```

---

# 19.81 Container Registry Publishing

After validation, a CI pipeline may publish the image to an approved container registry.

Conceptually:

```text
Docker Image
     |
     v
Authenticate
     |
     v
Container Registry
     |
     v
Versioned Image
```

The pipeline needs appropriate registry credentials or identity.

Again:

```text
credentials
```

must not be hardcoded into source control.

---

# 19.82 Do Not Use `latest` as Your Only Production Identity

Suppose every build publishes:

```text
veriqta-app:latest
```

Then someone asks:

```text
Which exact application build is production running?
```

`latest` alone may not answer that reliably.

A stronger tagging strategy can include immutable or traceable identifiers, such as:

```text
veriqta-app:1.4.2
```

and, depending on organizational policy, an identifier connected to:

```text
Git commit
CI build
release version
```

The key principle is traceability.

---

# 19.83 Connect Maven Version to Container Version

Suppose the Maven project is:

```text
com.veriqta:veriqta-app:2.3.0
```

The resulting JAR is:

```text
veriqta-app-2.3.0.jar
```

The container image could also be tagged:

```text
veriqta-app:2.3.0
```

Now the relationship is clearer:

```text
Git Release
    |
    v
Maven 2.3.0
    |
    v
JAR 2.3.0
    |
    v
Container Image 2.3.0
```

The exact naming policy can differ, but traceability between stages is valuable.

---

# 19.84 Production Promotion

A mature delivery workflow should distinguish:

```text
building software
```

from:

```text
promoting software
```

Imagine Maven creates:

```text
veriqta-app-2.3.0.jar
```

and Docker creates an image identified by an immutable digest.

The preferred idea is often:

```text
Build
   |
   v
Artifact
   |
   v
Test
   |
   v
Promote same artifact
   |
   +--> Development
   |
   +--> Staging
   |
   +--> Production
```

rather than:

```text
Build separately for development

Build again for staging

Build again for production
```

Rebuilding can introduce differences.

---

# 19.85 Build Once, Promote Many

This principle means:

```text
Create artifact once
      |
      v
Verify it
      |
      v
Promote the same artifact through environments
```

For example:

```text
Git Commit abc123
      |
      v
Maven Build
      |
      v
veriqta-app-2.3.0.jar
      |
      v
Docker Image
      |
      v
Immutable Image Digest
      |
      +--> Test
      |
      +--> Staging
      |
      +--> Production
```

The environment configuration can differ where appropriate.

The application binary should not silently become a different build at each stage.

---

# 19.86 Promotion Is Not the Same as Rebuilding

Suppose staging successfully tests:

```text
Image A
```

Then the production pipeline rebuilds the source and produces:

```text
Image B
```

Production is not necessarily receiving the exact image that staging tested.

A promotion model instead says:

```text
Staging tested Image A
        |
        v
Approve
        |
        v
Production receives Image A
```

This improves confidence about what was actually validated.

# 19.87 Maven Profiles and Production Promotion

You learned Maven profiles in Part 16.

Be careful with environment-specific builds.

If you build:

```text
development JAR
staging JAR
production JAR
```

from the same source using substantially different Maven profiles, you may undermine build-once promotion.

Prefer runtime configuration for values that genuinely vary by environment when the application architecture supports it.

For example:

```text
Same application artifact
        |
        +--> development configuration
        |
        +--> staging configuration
        |
        +--> production configuration
```

Do not embed production secrets into the Maven artifact.

CI reports:

```text

Docker:
COPY failed
```

Do not troubleshoot Java compilation.

Maven already succeeded.

```text

Is Docker using the correct build context?

Does .dockerignore exclude it?

Does the Dockerfile use the correct path?
```

```bash

```

Then compare the actual file with:

```dockerfile
COPY target/... .
```

This is evidence-based troubleshooting.

# 19.91 Scenario: Maven Cannot Download Dependencies in CI

Local build works.

CI reports dependency-resolution failure.

Investigate:

1. Does CI have network access to the repository?
2. Is `settings.xml` available where expected?
3. Is the mirror configured correctly?
4. Does the repository require authentication?
5. Are credentials available to this job?
6. Is the dependency only present in the developer's `.m2`?
7. Are coordinates correct?
8. Is the repository accessible through a corporate proxy?
9. Is TLS trust configured correctly?

The problem is not automatically Maven itself.

Maven may simply be reporting a repository or environment problem.

# 19.92 Scenario: Tests Pass Locally but Fail in CI

Possible causes include:

* Different JDK
* Time-zone assumptions
* Locale differences
* Missing environment variables
* Files not committed
* Case-sensitive filesystem differences
* Test ordering assumptions
* External service dependencies
* Port conflicts
* Timing-sensitive tests
* Different database or service configuration

Do not immediately disable the test.

Ask:

```text
What environmental assumption did the test make?
```

CI failures can expose hidden coupling.

# 19.93 Scenario: Pipeline Suddenly Downloads Hundreds of Dependencies

Possible causes include:

* Empty Maven cache
* Cache miss
* New runner
* Changed cache key
* Dependency version changes
* Plugin changes
* Local repository cleared

This may be normal.

The important question is whether dependencies come from expected, trusted repositories.

Do not judge build health only by download volume.



This is a good example of why file metadata can matter in CI.

# 19.95 Scenario: Wrapper Cannot Download Maven

* Proxy configuration
* Firewall restrictions
* DNS problems
* TLS trust
* Repository allowlists
* No outbound internet access

The solution may involve an approved internal distribution source or enterprise network configuration.

# 19.96 Scenario: Artifact Publishing Fails but Container Build Should Not Use an Unknown Artifact

```text
→ scheduled next
```

# 19.119 Common Beginner DevOps Mistakes With Maven

Avoid these patterns:

1. Committing `target/` to Git.
2. Committing repository passwords.
3. Building only on one developer's laptop.
4. Depending on locally installed `.m2` artifacts.
5. Using different undocumented Java versions.
6. Ignoring Maven Wrapper files.
7. Rebuilding separately for every environment without understanding why.
8. Running Maven tests repeatedly in several jobs without understanding lifecycle behavior.
9. Adding random Maven repositories to fix dependency failures.
10. Giving pull-request jobs production credentials.
11. Printing secrets into logs.
12. Treating CI cache as an artifact repository.
13. Using `latest` as the only production image identity.
14. Ignoring transitive dependencies.
15. Failing to control plugin versions.
16. Deploying an artifact different from the one that passed validation.
17. Troubleshooting `BUILD FAILURE` without finding the first meaningful error.
18. Disabling TLS validation to make repository access work.
19. Skipping tests to force successful pipelines.
20. Confusing Maven `deploy` with application deployment.
