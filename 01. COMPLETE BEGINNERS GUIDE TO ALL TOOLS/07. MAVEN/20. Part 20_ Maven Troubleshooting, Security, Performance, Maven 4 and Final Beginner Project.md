You have reached the final part of the beginner Maven series.

By this point, Maven should no longer look like a mysterious command that somehow turns Java code into a JAR.

You have learned the major pieces:

```text

Maven Project
    |
    v
pom.xml
    |
    +--> Dependencies
    |
    +--> Plugins
    |
    +--> Repositories
    |

Maven Lifecycle
    |
    +--> Compile
    +--> Test
    +--> Package
    +--> Verify

```

You also connected Maven to:

```text
Git
CI/CD
Artifact repositories
Docker
Container registries
Deployment workflows
```

The final skill is not learning another Maven command.

It is learning how to reason about Maven when things go wrong, how to keep builds secure and maintainable, and how to assemble everything you have learned into one complete project.

```text
Where did it fail?

How do I verify the actual fix?
```

That is much more useful than memorizing error messages.

# 20.1 The Maven Troubleshooting Mental Model

When Maven fails, beginners often focus immediately on:

```text
BUILD FAILURE
```

But `BUILD FAILURE` is normally the final result, not the useful diagnosis.

Imagine a doctor saying:

```text
"The patient is sick."
```

That tells you the outcome.

It does not tell you the cause.

Maven works similarly.

A failure can originate from many layers:

```text
Maven Command
    |
    v
Project Discovery
    |
    v
POM Parsing
    |
    v
Parent Resolution
    |
    v
Dependency Resolution
    |
    v
Plugin Resolution
    |
    v
Lifecycle Execution
    |
    +--> Resources
    +--> Compilation
    +--> Tests
    +--> Packaging
    +--> Verification
    |
    v
Artifact Installation / Deployment
```

Your first task is to identify the layer.

---

# 20.2 A Repeatable Troubleshooting Process

Use this process whenever a Maven build fails:

```text
Observe
   |
   v
Locate the first meaningful error
   |
   v
Identify the Maven stage
   |
   v
Classify the problem
   |
   v
Gather evidence
   |
   v
Form a hypothesis
   |
   v
Test the hypothesis
   |
   v
Apply the smallest correct fix
   |
   v
Run again
   |
   v
Verify
```

Do not begin by:

* Deleting random directories
* Changing dependency versions randomly
* Adding random repositories
* Disabling SSL verification
* Skipping tests
* Running commands copied from forums without understanding them
* Deleting your entire `.m2` repository for every problem

Troubleshooting should reduce uncertainty.

Random changes increase uncertainty.

# 20.3 Reading Maven Error Output

Run:

```bash
mvn verify
```

A failed build might end with:

```text
[INFO] ------------------------------------------------------------------------
[INFO] BUILD FAILURE
[INFO] ------------------------------------------------------------------------
```

Above that, Maven may display:

```text
[ERROR] Failed to execute goal ...
```

And above that may be the actual useful information.

For example:

```text
[ERROR] cannot find symbol
[ERROR] symbol:   class UserService
[ERROR] location: class com.veriqta.App
```

The useful clue is not:

```text
BUILD FAILURE
```

It is:

```text
cannot find symbol
```

That points toward compilation.

Read errors from the failure upward until you find the first meaningful cause.

---

# 20.4 Identify the Failing Maven Component

Maven errors often mention the plugin and goal that failed.

For example:

```text
Failed to execute goal
org.apache.maven.plugins:maven-compiler-plugin:...:compile
```

Break that down:

```text
org.apache.maven.plugins
→ plugin group

maven-compiler-plugin
→ plugin

compile
→ goal
```

This tells you Maven was performing compilation-related work.

If instead you see:

```text
maven-surefire-plugin
```

look toward unit tests.

If you see:

```text
maven-deploy-plugin
```

look toward artifact publication.

The failing plugin provides context.

---

# 20.5 Maven's `-e` Option

When the normal error output is insufficient, use:

```bash
mvn -e verify
```

`-e` means Maven should show error stack traces.

You can also write:

```bash
mvn --errors verify
```

A stack trace provides more detail about how an exception occurred.

Use `-e` when:

* The standard error hides useful exception details.
* A plugin throws an exception.
* You need more context around an internal Maven or plugin failure.

Do not assume that more output automatically means better understanding.

Start with normal output.

Escalate when necessary.

---

# 20.6 Maven's `-X` Option

For deeper debugging:

```bash
mvn -X verify
```

or:

```bash
mvn --debug verify
```

This enables Maven debug output.

It can show much more information about:

* Maven configuration
* Plugin execution
* Dependency resolution
* Repository access
* Class realms
* Lifecycle execution
* Properties
* Selected plugin parameters

The output can be very large.

Use it deliberately.

A useful progression is:

```text
Normal build
    |
    v
Read error
    |
    v
Need more detail?
    |
    v
-e
    |
    v
Still insufficient?
    |
    v
-X
```

Do not make `-X` your first response to every problem.

---

# 20.7 Security Warning About Debug Logs

Debug output may expose information about the environment.

Before sharing Maven debug logs publicly, inspect them.

They may reveal:

* Internal repository URLs
* File paths
* Usernames
* Environment information
* Project names
* Internal artifact coordinates
* Configuration details

Do not post raw enterprise build logs publicly without reviewing them.

Troubleshooting information can itself contain sensitive operational information.

# 20.8 Dependency Resolution Failures

A common Maven error looks conceptually like:

```text
Could not resolve dependencies for project ...
```

Maven is telling you:

```text
"I need an artifact, but I cannot obtain a usable copy."
```

Possible causes include:

* Incorrect coordinates
* Nonexistent version
* Repository unavailable
* Authentication failure
* Proxy failure
* Network failure
* Artifact not published
* Repository configuration error
* Cached failed resolution
* TLS or certificate problems
* Parent or BOM resolution problems

Start by identifying the exact artifact:

```text
groupId
artifactId
version
packaging
```

For example:

```text
com.veriqta:shared-utils:jar:1.2.0
```

Then ask:

```text
Does this artifact actually exist?

Which repository should contain it?

Can this machine reach that repository?

Does Maven have permission to retrieve it?
```

---

# 20.9 Dependency Resolution Troubleshooting

Suppose Maven reports that it cannot resolve:

```text
com.veriqta:shared-utils:1.2.0
```

Inspect the dependency declaration:

```xml
<dependency>
    <groupId>com.veriqta</groupId>
    <artifactId>shared-utils</artifactId>
    <version>1.2.0</version>
</dependency>
```

Check:

1. Is `groupId` correct?
2. Is `artifactId` correct?
3. Does version `1.2.0` exist?
4. Is the repository configured?
5. Is authentication required?
6. Can Maven reach the repository?
7. Is a mirror redirecting the request elsewhere?
8. Is the artifact only installed on another developer's machine?

Use:

```bash
mvn dependency:tree
```

when dependency relationships matter.

Use:

```bash
mvn help:effective-settings
```

when repository settings may be involved.

---

# 20.10 Plugin Resolution Failures

Dependencies are not the only artifacts Maven downloads.

Maven also resolves plugins.

A plugin resolution failure might report:

```text
Plugin ... could not be resolved
```

Possible causes include:

* Incorrect plugin coordinates
* Incorrect plugin version
* Plugin repository unavailable
* Maven Central or mirror unavailable
* Proxy problem
* Authentication issue
* Corrupted local plugin artifact
* Unsupported plugin/Maven combination

Remember:

```text
Application dependency
→ used by application/build classpath

Maven plugin
→ performs build work
```

Treat plugin resolution as its own failure category.

---

# 20.11 Compilation Failures

A compilation failure occurs when Java source cannot be successfully compiled.

Common messages include:

```text
cannot find symbol
```

```text
package ... does not exist
```

```text
incompatible types
```

```text
release version ... not supported
```

Possible causes include:

* Invalid Java syntax
* Missing import
* Missing dependency
* Wrong dependency scope
* Wrong package name
* Wrong source directory
* JDK mismatch
* Compiler configuration mismatch
* Generated source missing
* Source file not committed to Git

When compilation fails, inspect the compiler error before modifying Maven configuration.

Not every Maven compilation failure is a Maven problem.

Maven may simply be reporting a Java problem.

---

# 20.12 Java Compatibility Problems

Suppose the POM contains:

```xml
<properties>
    <maven.compiler.release>21</maven.compiler.release>
</properties>
```

but Maven runs using an older JDK.

Compilation may fail.

Check:

```bash
java -version
```

```bash
javac -version
```

and:

```bash
mvn -version
```

The most important output is the Java version Maven is actually using.

You may have several JDKs installed.

Your terminal's assumptions may not match Maven's actual runtime.

Investigate:

```text
JDK installed
     |
     v
JAVA_HOME
     |
     v
PATH
     |
     v
Maven runtime
     |
     v
Compiler configuration
```

# 20.13 Test Failures

A test failure is different from a compilation failure.

For example:

```text
Tests run: 8, Failures: 1, Errors: 0, Skipped: 0
```

This means Maven successfully reached the testing stage, but at least one test did not produce the expected result.

Inspect:

```text
target/surefire-reports/
```

for unit-test reports.

For integration tests configured through Failsafe, inspect the corresponding Failsafe reports.

Ask:

```text
Which test failed?

What assertion failed?

What value was expected?

What value was actually produced?

Does the failure reproduce locally?

Does the test depend on environment-specific state?
```

Do not immediately add a skip flag.

---

# 20.14 Test Failure Versus Test Error

These concepts are useful to distinguish.

A failure often means an assertion was not satisfied.

For example:

```text
Expected: 5
Actual: 4
```

An error often means the test could not complete normally.

For example:

```text
NullPointerException
```

or:

```text
Connection refused
```

Both can fail the Maven build, but they suggest different investigations.

# 20.15 Repository Failures

Maven repositories can fail for reasons unrelated to project source code.

Possible problems include:

* Repository unavailable
* DNS failure
* Network timeout
* Incorrect URL
* Proxy problem
* TLS problem
* Authentication problem
* Authorization problem
* Repository manager outage
* Artifact removed
* Mirror misconfiguration

Separate:

```text
Can Maven locate the repository?
```

from:

```text
Can Maven authenticate?
```

from:

```text
Does Maven have permission?
```

from:

```text
Does the requested artifact exist?
```

These are different questions.

---

# 20.16 Authentication Failures

A repository may respond with:

```text
401 Unauthorized
```

This usually points toward authentication.

Check:

* Username
* Password or token
* Credential expiry
* Server ID
* `settings.xml`
* CI secret availability
* Repository endpoint

Remember that Maven associates credentials with server IDs.

If the POM uses:

```xml
<repository>
    <id>veriqta-releases</id>
    ...
</repository>
```

the corresponding credentials must use the expected ID.

A mismatch can cause authentication to fail even when the username and password themselves are valid.

---

# 20.17 Authorization Failures

A:

```text
403 Forbidden
```

often means the server understood the request but does not allow the requested action.

Possible causes include:

* Account lacks deployment permission
* Trying to publish to a protected repository
* Attempting to overwrite an immutable release
* Wrong repository destination
* Repository policy restriction

Think:

```text
401
→ Who are you?

403
→ You are known, but are you allowed to do this?
```

This is a useful mental model, although exact server behavior can vary.

---

# 20.18 Corrupted `.m2` Artifacts

The local Maven repository usually lives under:

```text
~/.m2/repository
```

Occasionally a cached artifact can become incomplete or corrupted.

Symptoms can include:

* Invalid JAR errors
* Unexpected archive errors
* Failed downloads
* Cached resolution problems
* Checksums not matching
* A build failing locally while other machines succeed

Do not immediately delete:

```text
~/.m2/repository
```

entirely.

That may remove gigabytes of valid cached artifacts and force Maven to download everything again.

Prefer targeted troubleshooting.

If the problem is:

```text
org.example:example-library:2.0.0
```

locate only that artifact's local directory.

The coordinate mapping is approximately:

```text
org.example
→ org/example

example-library
→ example-library

2.0.0
→ 2.0.0
```

giving:

```text
~/.m2/repository/org/example/example-library/2.0.0/
```

After confirming that this artifact is the problem, remove only the affected cached version and allow Maven to retrieve it again from a trusted repository.

---

# 20.19 Why Deleting All of `.m2` Is Usually a Poor First Step

Deleting the entire repository can appear to fix some problems because it forces a clean download.

But it also destroys evidence.

Suppose the real problem was:

```text
wrong mirror configuration
```

or:

```text
invalid credentials
```

Deleting `.m2` does not fix either.

Now Maven simply has to redownload far more artifacts through the same broken configuration.

Troubleshoot the actual layer.

---

# 20.20 Force Maven to Check for Updates

Maven supports:

```bash
mvn -U verify
```

`-U` requests updated checks for relevant releases and snapshots according to Maven's behavior and repository metadata.

It can be useful when Maven has cached stale resolution state or when a new snapshot should be checked.

Do not use `-U` as a magical universal repair command.

Understand why you need an update.

# 20.21 Network Failures

Dependency and plugin resolution depend on network connectivity unless all required artifacts are already locally available.

Possible symptoms include:

```text
Connection timed out
```

```text
Connection refused
```

```text
Unknown host
```

```text
Name or service not known
```

Possible causes:

* No network connectivity
* DNS failure
* Firewall restriction
* Repository outage
* Proxy required
* Incorrect repository hostname
* VPN requirement
* Corporate network restrictions

Ask:

```text
Can the machine resolve the hostname?

Can it reach the repository?

Is a proxy required?

Does another network behave differently?

Is Maven configured differently from other tools?
```

Do not immediately change the POM.

---

# 20.22 Proxy Problems

Enterprise networks may require Maven traffic to pass through a proxy.

Proxy configuration can live in:

```text
~/.m2/settings.xml
```

A conceptual configuration is:

```xml
<settings>
    <proxies>
        <proxy>
            <id>corporate-proxy</id>
            <active>true</active>
            <protocol>http</protocol>
            <host>proxy.example.com</host>
            <port>8080</port>
        </proxy>
    </proxies>
</settings>
```

Do not copy placeholder values.

Use the actual configuration approved by your environment.

Proxy failures may appear as dependency failures even though the dependency coordinates are correct.

Always consider infrastructure between Maven and the repository.

---

# 20.23 SSL and Certificate Problems

A repository accessed over HTTPS depends on TLS certificate validation.

You may encounter errors mentioning:

```text
PKIX path building failed
```

or certificate trust.

Possible causes include:

* Untrusted internal certificate authority
* Expired certificate
* Incorrect certificate chain
* TLS interception by corporate infrastructure
* Wrong Java truststore
* Repository certificate misconfiguration

Do not solve this by blindly disabling certificate validation.

That weakens the security protecting artifact downloads.

The correct fix is usually to establish the appropriate trust configuration or correct the repository's certificate setup.

---

# 20.24 Why SSL Errors Matter for Maven Security

Maven downloads executable build components and application dependencies.

If secure transport is weakened, an attacker may have more opportunity to interfere with what the build receives.

The path is important:

```text
Maven
   |
   v
HTTPS
   |
   v
Repository
   |
   v
Dependency / Plugin
   |
   v
Build
```

Do not treat TLS as an annoying obstacle.

It protects part of your software supply chain.

# 20.25 Parent POM Resolution Errors

A child POM may declare:

```xml
<parent>
    <groupId>com.veriqta</groupId>
    <artifactId>veriqta-parent</artifactId>
    <version>1.0.0</version>
</parent>
```

Maven must resolve that parent.

Possible sources include:

* Reactor
* Relative path
* Local repository
* Remote repository

Failures may occur because:

* Parent version is wrong
* Parent was never installed or deployed
* `relativePath` points somewhere incorrect
* Repository configuration is missing
* Parent coordinates are wrong

The error may look like:

```text
Non-resolvable parent POM
```

Do not troubleshoot child dependencies before resolving the parent problem.

Maven may not yet have a complete project model.

---

# 20.26 Investigating `relativePath`

A parent declaration can contain:

```xml
<relativePath>../pom.xml</relativePath>
```

This tells Maven where it may locate a parent POM relative to the child.

In a multi-module project:

```text
veriqta-platform/
├── pom.xml
├── common-library/
│   └── pom.xml
└── application/
    └── pom.xml
```

a child may use the parent at:

```text
../pom.xml
```

If directories are moved but the relative path is not updated, parent resolution can fail.

Check the filesystem before blaming remote repositories.

---

# 20.27 Missing Versions

Maven may report that a dependency or plugin version is missing.

A dependency can sometimes omit its version when the version is supplied by:

```text
dependencyManagement
```

or an imported BOM.

For example:

```xml
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.example</groupId>
            <artifactId>example-library</artifactId>
            <version>3.2.0</version>
        </dependency>
    </dependencies>
</dependencyManagement>
```

Then a child can declare:

```xml
<dependency>
    <groupId>org.example</groupId>
    <artifactId>example-library</artifactId>
</dependency>
```

But if dependency management does not provide a version, Maven needs one.

Investigate:

```text
Where should this version come from?

Parent?

Current POM?

BOM?

dependencyManagement?

Was a parent changed?
```

---

# 20.28 Dependency Convergence Problems

Large projects can pull different versions of the same library.

For example:

```text
Application
├── Library A
│   └── Common Library 1.0
└── Library B
    └── Common Library 2.0
```

Maven performs dependency mediation, but the selected version may not always produce the behavior you intended.

Use:

```bash
mvn dependency:tree
```

Inspect:

* Which version was selected
* Which versions were omitted
* Which path introduced each dependency

In larger projects, teams may enforce dependency convergence rules through appropriate build tooling.

The important beginner concept is:

```text
Successful dependency resolution
```

does not automatically mean:

```text
Dependency graph is architecturally healthy.
```

---

# 20.29 Do Not Fix Version Conflicts Randomly

A common beginner reaction is:

```text
"Version 2.0 caused an error, so I'll try 2.1, 2.2, 3.0..."
```

Instead:

1. Inspect the dependency tree.
2. Identify which component introduces each version.
3. Read compatibility information.
4. Determine which version the application actually requires.
5. Manage the version intentionally.
6. Run tests.
7. Verify runtime behavior.

Dependency management should be evidence-based.

---

# 20.30 Plugin Compatibility Problems

Maven plugins interact with:

* Maven itself
* Java
* Project packaging
* Other plugins
* Build lifecycle
* Plugin-specific APIs

An old plugin may behave poorly with a newer JDK or Maven release.

A new plugin may require a newer Maven version.

When plugin failures appear after an upgrade, check:

```text
Maven version
Java version
Plugin version
Plugin documentation
Plugin compatibility requirements
```

Do not assume:

```text
Newest plugin
=
compatible with every old build
```

or:

```text
Old plugin
=
safe forever
```

Build tooling evolves.

# 20.31 Multi-Module Reactor Failures

Consider:

```text
veriqta-platform
├── common-library
├── application-core
├── application-service
└── application-web
```

Maven's reactor determines an appropriate build order.

A failure might look like:

```text
common-library        SUCCESS
application-core      SUCCESS
application-service   FAILURE
application-web       SKIPPED
```

This tells you something important.

`application-web` may not itself be broken.

It may have been skipped because an upstream required module failed.

Focus first on:

```text
application-service
```

not the skipped downstream module.

---

# 20.32 Reading the Reactor Summary

At the end of a multi-module build, Maven can display a reactor summary.

For example:

```text
Reactor Summary:

veriqta-platform ................. SUCCESS
common-library ................... SUCCESS
application-core ................. SUCCESS
application-service .............. FAILURE
application-web .................. SKIPPED
```

Read this before investigating every module.

It tells you where the build stopped.

The useful question is:

```text
What is the first module that actually failed?
```

---

# 20.33 Resuming a Reactor Build

For appropriate Maven builds, Maven can support resuming from a module after a failure.

You may encounter:

```bash
mvn -rf :application-service
```

where:

```text
-rf
```

means resume from.

Before using it, understand what was already built and whether the current build state makes resuming appropriate.

For a clean final verification, you may still want:

```bash
mvn clean verify
```

from the root.

A resumed build can save troubleshooting time.

A full clean build provides stronger final confirmation.

# 20.34 Effective POM Investigation

What you write in:

```text
pom.xml
```

is not always the entire configuration Maven uses.

Configuration may also come from:

* Super POM
* Parent POM
* Imported BOMs
* Plugin management
* Profiles
* Default lifecycle bindings

Use:

```bash
mvn help:effective-pom
```

This shows the effective project model Maven sees after inheritance and other model-building behavior.

This is extremely useful when asking:

```text
Where did this plugin come from?

Which dependency version is actually managed?

Which repository is configured?

Which property value is active?

Which plugin version is being used?
```

---

# 20.35 Saving the Effective POM

The effective POM can be large.

You can redirect output:

```bash
mvn help:effective-pom > effective-pom.xml
```

Then inspect:

```text
effective-pom.xml
```

Remember that this file is generated troubleshooting output.

Do not automatically commit it to Git.

Use it to understand Maven's final configuration.

---

# 20.36 Effective Settings Investigation

Project configuration is not the only Maven configuration.

User or global settings can change:

* Mirrors
* Servers
* Proxies
* Profiles
* Plugin groups
* Local repository behavior

Use:

```bash
mvn help:effective-settings
```

This helps investigate the settings Maven actually sees.

This is particularly valuable when:

```text
Build works on Developer A's machine
but fails on Developer B's machine.
```

Their POM may be identical.

Their effective settings may not be.

---

# 20.37 Be Careful When Sharing Effective Settings

Settings can contain or reveal sensitive configuration.

Review generated output before:

* Uploading it
* Posting it publicly
* Sending it to an external support forum
* Adding it to an issue

Treat configuration inspection output as potentially sensitive.

# 20.38 Maven Performance Begins With Measurement

A slow build does not automatically mean:

```text
Maven is slow.
```

The time may be spent in:

* Dependency downloads
* Compilation
* Unit tests
* Integration tests
* Code generation
* Static analysis
* Packaging
* Network operations
* Docker builds
* Large multi-module reactors

First determine where time is spent.

Do not optimize blindly.

The performance troubleshooting process is:

```text
Measure
   |
   v
Locate expensive work
   |
   v
Understand why it occurs
   |
   v
Change one thing
   |
   v
Measure again
```

# 20.39 Dependency Caching

Maven caches downloaded artifacts in:

```text
~/.m2/repository
```

This means subsequent builds often do not need to download every dependency again.

First build:

```text
Remote Repository
      |
      v
Download
      |
      v
Local .m2
      |
      v
Build
```

Later build:

```text
Local .m2
      |
      v
Build
```

This can significantly reduce repeated network work.

---

# 20.40 CI Caching

Ephemeral CI runners may begin with little or no Maven cache.

Without caching:

```text
Pipeline 1
→ download dependencies

Pipeline 2
→ download dependencies again

Pipeline 3
→ download dependencies again
```

With appropriate CI caching:

```text
Pipeline
   |
   v
Restore Maven cache
   |
   v
Download missing artifacts
   |
   v
Build
   |
   v
Save updated cache
```

Caching can improve performance.

But remember:

```text
cache
≠
artifact repository
```

A cache is an acceleration mechanism.

It should not become the only place where required internal dependencies exist.

---

# 20.41 Offline Builds

Maven supports offline mode:

```bash
mvn -o verify
```

or:

```bash
mvn --offline verify
```

This tells Maven not to access remote repositories.

It can work only when everything required by the build is already locally available.

If a required dependency or plugin is missing from `.m2`, the offline build fails.

Offline mode can be useful for:

* Testing whether a build depends on new network retrieval
* Working without network access
* Certain controlled build environments
* Diagnosing repository behavior

It is not a substitute for correct repository management.

---

# 20.42 Build Reproducibility

A reproducible build aims to make the build result predictable from controlled inputs.

Important inputs can include:

```text
Source revision
JDK
Maven version
POM
Parent POM
Dependencies
Plugin versions
Build configuration
Environment
Repository contents
```

Problems arise when builds depend on hidden state:

```text
Developer's local .m2
Undocumented environment variable
Random plugin version
Mutable dependency
Different JDK
Uncommitted file
Machine-specific path
```

The fewer hidden inputs, the easier a build is to reproduce.

---

# 20.43 Reproducible Does Not Simply Mean "It Builds Twice"

Suppose you run:

```bash
mvn package
```

twice and both commands succeed.

That does not automatically prove strong reproducibility.

Ask:

```text
Would it build on another machine?

Would CI build it?

Are dependency and plugin versions controlled?

Is the JDK controlled?

Does the build depend on timestamps or machine state?

Can the produced artifact be traced to its inputs?
```

Reproducibility is broader than repeated success on one laptop.

---

# 20.44 Avoiding Unnecessary Work

Maven's lifecycle already has ordering.

If you run:

```bash
mvn compile
mvn test
mvn package
mvn verify
```

as separate commands, Maven repeats earlier lifecycle work across those invocations.

For example:

```text
mvn package
```

already runs earlier required phases in the default lifecycle.

In CI, do not automatically create:

```text
Job 1: mvn compile
Job 2: mvn test
Job 3: mvn package
Job 4: mvn verify
```

without understanding the repeated work and job isolation.

Sometimes separate jobs are justified.

But the reason should be architectural, not misunderstanding of Maven phases.

---

# 20.45 Parallel-Build Concepts

Maven can support parallel reactor builds.

You may encounter:

```bash
mvn -T 1C verify
```

The `-T` option controls thread usage for parallel builds.

`1C` conceptually means approximately one thread per available CPU core.

Parallel execution can improve some large multi-module builds.

But parallelism is not automatically safe for every project.

Problems can arise when:

* Plugins are not thread-safe
* Modules share mutable external resources
* Tests assume exclusive access
* Build scripts write to shared paths
* External systems become bottlenecks

Do not enable parallel builds merely because more threads sound faster.

Test and measure.

# 20.46 Large Multi-Module Builds

A large reactor might contain:

```text
platform-parent
├── shared-model
├── shared-utils
├── authentication
├── billing
├── notifications
├── application-core
├── application-api
├── application-web
└── integration-tests
```

Building everything after every small change may become expensive.

Useful Maven concepts include:

```text
-pl
-am
-amd
-rf
```

You learned these in the multi-module section.

They can help perform targeted development builds.

For example:

```bash
mvn -pl application-web -am test
```

means conceptually:

```text
Build application-web
+
also build modules it requires
```

Use targeted builds during development where appropriate.

Before release, perform the complete required verification.

# 20.47 Performance Versus Correctness

Never sacrifice build correctness merely to make a dashboard show a faster number.

Bad optimization:

```text
Tests are slow
→ disable tests
```

Better investigation:

```text
Tests are slow
→ identify slow tests
→ understand external dependencies
→ improve test design
→ parallelize safely where appropriate
→ cache appropriate inputs
→ separate test categories appropriately
```

The goal is:

```text
fast enough
+
reliable
+
repeatable
```

not merely:

```text
fast
```

# 20.48 Maven Security Starts With Trust

Maven downloads code.

That simple fact has major security implications.

It may download:

* Dependencies
* Transitive dependencies
* Plugins
* Parent POMs
* BOMs
* Metadata

The build path is:

```text
Repository
    |
    v
Maven
    |
    v
Dependency / Plugin
    |
    v
Build
    |
    v
Application Artifact
```

Therefore repository trust matters.

# 20.49 Trusted Repositories

Do not add arbitrary repositories because Maven cannot find an artifact.

Before adding one, ask:

```text
Who operates it?

Why do we need it?

Is it approved?

Is the connection secure?

Could the artifact come from an existing trusted repository?

Can our enterprise repository manager proxy it?

What happens if this repository is compromised?
```

Every additional repository can expand the trust boundary of the build.

# 20.50 Dependency Risk

A Maven dependency becomes part of your application's software supply chain.

Risks can include:

* Known vulnerabilities
* Malicious releases
* Abandoned components
* Unexpected transitive dependencies
* Incompatible updates
* Licensing concerns
* Compromised publishing accounts

This does not mean:

```text
Never use dependencies.
```

Modern applications rely heavily on libraries.

It means:

```text
Know what you depend on.
Control versions.
Use trusted sources.
Monitor important dependencies.
Update deliberately.
```

---

# 20.51 Plugin Risk

Plugins deserve particular attention because they execute during the build.

Conceptually:

```text
Dependency
→ application/library code

Plugin
→ code that performs build operations
```

A malicious plugin could potentially interact with:

* Source files
* Build files
* Environment variables
* Network resources
* Generated artifacts
* Credentials available to the build process

Use trusted plugins and repositories.

Control plugin versions.

Do not paste unknown plugin configuration into a production build simply because a tutorial says it fixes something.

# 20.52 Repository Poisoning Concepts

Repository poisoning broadly refers to situations where a build obtains an unintended or malicious artifact because repository resolution, naming, trust, or publication controls were weak.

A simplified risk model is:

```text
Project requests artifact
       |
       v
Repository resolution
       |
       v
Unexpected malicious artifact
       |
       v
Build consumes it
```

Defenses can include:

* Trusted repositories
* Internal repository managers
* Controlled namespaces
* Explicit versions
* Repository policy
* Dependency monitoring
* Integrity verification
* Strong publishing controls

The beginner lesson is:

```text
Artifact resolution is part of security.
```

---

# 20.53 Checksums

Repositories can provide checksums for artifacts.

A checksum is a value calculated from file contents.

Conceptually:

```text
Artifact
   |
   v
Hash Function
   |
   v
Checksum
```

If file contents change:

```text
Different contents
→ different expected checksum
```

Checksums help detect accidental corruption and can participate in integrity verification.

But a checksum alone does not automatically prove that an artifact is trustworthy.

If an attacker controls both an artifact and its published checksum, both could potentially be replaced.

Integrity and trust are related but distinct concepts.

# 20.54 Secrets Do Not Belong in `pom.xml`

Never commit real credentials such as:

```xml
<username>admin</username>
<password>SuperSecret123</password>
```

to a project POM.

The POM normally belongs in Git.

Therefore secrets placed there may become:

* Visible to repository users
* Preserved in Git history
* Copied into forks
* Exposed in logs
* Scanned by external systems

Use approved secure mechanisms instead.

# 20.55 Maven Credentials and `settings.xml`

Repository credentials are commonly associated with Maven server configuration in:

```text
~/.m2/settings.xml
```

For example:

```xml
<servers>
    <server>
        <id>veriqta-releases</id>
        <username>${env.MAVEN_REPO_USER}</username>
        <password>${env.MAVEN_REPO_PASSWORD}</password>
    </server>
</servers>
```

The project POM can refer to the repository by ID without containing the actual secret.

In CI, the values can be supplied through the platform's approved secret mechanism.

Do not commit a real credential-bearing personal `settings.xml` to Git.

---

# 20.56 Least-Privilege Repository Credentials

Suppose one CI job only downloads dependencies.

It does not need deployment permission.

Another release job publishes artifacts.

It may need write permission.

Use separate privileges where appropriate:

```text
Build Job
→ read

Release Job
→ controlled write

Production Deployment Job
→ only deployment permissions actually required
```

Do not give every job one administrator credential.

Least privilege means:

```text
Give the process only the permissions required to perform its job.
```

---

# 20.57 Protecting CI/CD Credentials

CI credentials should be protected from:

* Untrusted pull requests
* Accidental logging
* Overly broad job access
* Long-lived unnecessary exposure
* Developers who do not need them
* Compromised build dependencies
* Malicious scripts

A useful model is:

```text
Secret Store
    |
    v
Authorized Job Only
    |
    v
Minimum Required Scope
    |
    v
Temporary Use
```

Where supported, short-lived identities can reduce risk compared with permanent static credentials.

# 20.60 Maven Wrapper as a Maintenance Tool

You already learned Maven Wrapper:

```text

```

Its importance grows as a project ages.

Without a wrapper:

```text

→ Maven version A

→ Maven version B

→ Maven version C
```

With a wrapper, the project can more explicitly control the Maven version used to invoke its build.

This helps when:

* Rebuilding older projects

The wrapper does not replace Maven knowledge.

It makes Maven version selection more manageable.

# 20.61 Maven 3 and Maven 4 Awareness

A beginner learning Maven today should understand that many existing projects were created and maintained using Maven 3, while Maven 4 represents the next major generation of Maven behavior and build tooling.

Do not think:

```text
Maven 4
=
completely different tool
```

The core Maven concepts remain recognizable:

* POM
* Coordinates
* Dependencies
* Plugins
* Repositories
* Lifecycle
* Goals
* Phases
* Modules
* Parent POMs

But major-version changes can affect build authors.

That is why migration should be deliberate.

# 20.62 Why Major Maven Versions Matter

A major Maven version can introduce:

* Behavior changes
* Model changes
* Validation changes
* New capabilities
* Removed or changed legacy behavior
* Plugin compatibility considerations
* Build authoring improvements
* New migration requirements

An old build may rely on behavior that newer Maven versions handle differently.

Therefore:

```text
"It builds with Maven 3"
```

does not automatically guarantee:

```text
"It will build unchanged with every Maven 4 release."
```

Test the actual project.

# 20.63 Maven 4 Concepts Beginners Should Recognize

You do not need to become a Maven 4 migration specialist at beginner level.

But you should recognize several modern Maven directions and concepts.

These include:

* Stronger and clearer project model behavior
* Improvements to Maven's build model and project structure
* Better handling of large reactor builds
* Changes intended to make builds more predictable
* Newer build-authoring capabilities
* Compatibility and migration considerations for existing Maven 3 projects
* Continued importance of Maven Wrapper for controlling build-tool versions

Maven 4 also introduces concepts and syntax that may not be appropriate to copy into a project that must remain compatible with older Maven versions.

This is why version awareness matters.

# 20.64 Maven 4 and Build Authors

A build author is someone responsible for Maven build configuration.

That includes engineers who maintain:

```text

parent POMs

multi-module structures
repository configuration
```

For build authors, a major Maven upgrade means checking more than:

# 20.66 Establish the Maven 3 Baseline First

Before migration, record:

```bash

```

Then:

```bash

```

You want a known-good baseline.

```text
already present
```

or:


Always establish the baseline first.

# 20.78 Project Stage 7: Create the Application POM

```text
veriqta-app/pom.xml
```

```xml
<?xml version="1.0" encoding="UTF-8"?>

<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
                             https://maven.apache.org/xsd/maven-4.0.0.xsd">
```
