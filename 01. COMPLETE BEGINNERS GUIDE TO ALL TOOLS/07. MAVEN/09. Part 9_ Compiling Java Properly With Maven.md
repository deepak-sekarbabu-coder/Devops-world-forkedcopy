# Part 9: Compiling Java Properly With Maven

## Introduction

In the earlier parts, you learned that Maven does not replace Java.

You also learned that when you run:

```bash
mvn compile
```

Maven moves through the default build lifecycle until it reaches the `compile` phase.

The actual Java compilation work is handled through the Maven Compiler Plugin.

Now we will go much deeper.

We are going to understand what compilation actually means, where Maven finds source code, where compiled files go, how dependencies become part of compilation, how Java versions affect the build, and how to troubleshoot compilation failures.

By the end of this part, you should be able to look at this:

```text
Java Source Files
        |
        v
Maven
        |
        v
Compiler Plugin
        |
        +---- Java release configuration
        |
        +---- Compilation classpath
        |
        +---- Source directories
        |
        v
Java Compiler
        |
        v
.class Files
        |
        v
target/classes
```

and understand every major step.

Our practical goal is to expand `veriqta-maven-app` from a single Java file into a small multi-class application and compile it properly with Maven.

# 1. What Does "Compile" Mean?

Java source code is written in files ending in:

```text
.java
```

For example:

```text
App.java
```

Inside the file, you might write:

```java
package com.veriqta.app;

public class App {

    public static void main(String[] args) {
        System.out.println("VERIQTA Maven application");
    }
}
```

This is Java source code.

A Java Virtual Machine does not normally execute this source file as the final application representation used in a traditional compiled Java build.

The source is compiled into Java bytecode.

The result is typically a file ending in:

```text
.class
```

For example:

```text
App.java
```

becomes:

```text
App.class
```

The basic process is:

```text
Java Source Code
App.java
    |
    v
Java Compiler
    |
    v
Java Bytecode
App.class
    |
    v
JVM
    |
    v
Running Application
```

Compilation is the transformation from Java source code into JVM bytecode.

---

# 2. Source Code Versus Compiled Code

Consider:

```java
public class App {
    public static void main(String[] args) {
        System.out.println("Hello");
    }
}
```

Humans can read this source code.

After compilation, Java creates bytecode in a `.class` file.

The `.class` file is not normal human-readable Java source.

It contains instructions designed for execution by the Java Virtual Machine.

So:

```text
.java
→ source code

.class
→ compiled Java bytecode
```

This distinction is fundamental.

---

# 3. Why Does Java Compile to Bytecode?

Many native languages compile directly toward machine instructions for a particular environment.

Java uses a JVM-oriented model.

A simplified flow is:

```text
Java Source
    |
    v
Java Compiler
    |
    v
Bytecode
    |
    v
JVM
    |
    v
Operating System / Hardware
```

Different platforms can provide compatible JVM implementations.

This helps make compiled Java applications portable across environments, subject to Java version, platform dependencies, native libraries, and other compatibility requirements.

The name essentially means:


Check the compiler installed on your machine:


# 5. Why Maven Does Not Replace `javac`

Maven is not itself the Java programming language compiler.

Instead, Maven gives you a structured build system around compilation.

Without Maven, you might manually do something such as:

```bash
javac App.java
```

With Maven:

```bash
mvn compile
```

Maven coordinates the build and invokes the compiler functionality through the Maven Compiler Plugin.

Conceptually:

```text
mvn compile
     |
     v
Maven lifecycle
     |
     v
compile phase
     |
     v
Maven Compiler Plugin
     |
     v
Java compiler
     |
     v
.class files
```

# 6. Why Not Just Use `javac` Directly?

For one Java file:

```bash
javac App.java
```

is manageable.

Imagine a project containing:

```text

```

Now add:

* Hundreds of Java files
* External dependencies
* Generated source
* Tests
* Multiple modules

* CI/CD
* Packaging
* Repeatable builds

Manual compilation becomes much harder.

Maven gives the project a repeatable build structure.

Instead of manually constructing a long compiler command, the developer can run:


From the Maven project root:




# 8. The Maven Compiler Plugin

The Maven Compiler Plugin integrates Java compilation into Maven's build lifecycle.

You encountered it in Part 8.

Its important goals include:

```text
compiler:compile
```

and:

```text
compiler:testCompile
```

They serve different source sets.

```text
compiler:compile
→ compile main application source

compiler:testCompile
→ compile test source
```

For this part, we are mainly concerned with:

```text
compiler:compile
```

---

# 9. Lifecycle Compilation Versus Direct Goal Execution

You can run:

```bash
mvn compile
```

or directly invoke:

```bash
mvn compiler:compile
```

These are not conceptually identical.

`mvn compile` means:

```text
Execute the default lifecycle through the compile phase.
```

`mvn compiler:compile` means:

```text
Directly invoke the Compiler Plugin's compile goal.
```

For normal builds, lifecycle-oriented commands such as:

```bash
mvn compile
```

are generally the natural way to work.



Inside:


Maven expects main Java source under:

```text
src/main/java
```

# 15. What Is the `target` Directory?

`target` is Maven's normal build output directory.

It contains generated build results.

Depending on the build, it may contain:

```text
target/
├── classes/
├── test-classes/
├── generated-sources/
├── generated-test-sources/
├── surefire-reports/
└── application.jar
```

Not every project produces every directory.

The important idea is:

```text
src/
→ source material

target/
→ generated build output
```

---

# 16. Do Not Put Source Code in `target`

Do not manually create important application source files under:

```text
target/
```

because Maven can delete the directory during:

```bash
mvn clean
```

For example:

```text
target/MyImportantCode.java
```

is a bad place for source code you want to preserve.

Generated build output should be treated as reproducible.

Your real source belongs under:

```text
src/
```

# 21. Understanding `User.java`

The first line:

```java
package com.veriqta.app.model;
```

places the class in:

```text
com.veriqta.app.model
```

Then:

```java
public class User
```

declares the `User` class.

This field:

```java
private final String name;
```

stores a user's name.

The constructor:

```java
public User(String name) {
    this.name = name;
}
```

allows us to create a user.

For example:

```java
User user = new User("Ann");
```

The method:

```java
public String getName() {
    return name;
```

# 22. Create `GreetingService.java`

Create:

```text

```

Add:

```java
package com.veriqta.app.service;

import com.veriqta.app.model.User;

    public String createGreeting(User user) {

    }

```

Notice:

```java

```

This creates a relationship:

```text
GreetingService
      |
      v
User
```

# 23. Update `App.java`

Create or update:

```text
src/main/java/com/veriqta/app/App.java
```

with:

```java
package com.veriqta.app;

import com.veriqta.app.model.User;
import com.veriqta.app.service.GreetingService;

public class App {

    public static void main(String[] args) {

        User user = new User("Engineer");

        GreetingService greetingService = new GreetingService();

        String message = greetingService.createGreeting(user);

        System.out.println(message);
    }
}
```

Now the application contains several cooperating classes.

# 27. What Is the Java Language Level?

Java evolves over time.

Different Java releases introduce:

* New syntax
* New language features
* New standard library APIs
* Runtime changes
* Compiler changes

A project therefore needs to define which Java release it targets.

For example, a project may target:

```text
Java 17
```

while another targets:

```text
Java 21
```

This affects what language features and APIs the project can safely use.

---

# 28. Installed JDK Versus Project Java Level

These are related but different.

Suppose your computer has:

```text
JDK 21
```

That tells you which JDK is available.

Your project might intentionally target:

```text
Java 17
```

So:

```text
Installed JDK
→ compiler/runtime available on the machine

Project release target
→ Java release compatibility the project requests
```

Do not assume they must always have the same number.

---

# 29. `maven.compiler.release`

A common Maven configuration is:

```xml
<properties>
    <maven.compiler.release>17</maven.compiler.release>
</properties>
```

This tells the Maven Compiler Plugin to compile against the specified Java release model, assuming the JDK/compiler in use supports that release setting.

For Java 21:

```xml
<properties>
    <maven.compiler.release>21</maven.compiler.release>
</properties>
```

Use the release required by your actual project.

---

# 30. Why `release` Matters

Suppose:

```text
Developer workstation
→ JDK 21

Production environment
→ Java 17
```

If the developer accidentally uses Java features or APIs unavailable in Java 17, the application may not be compatible with the production runtime.

A release target helps enforce the intended compatibility during compilation.

The goal is:

```text
Build environment
      |
      v
Compile intentionally
      |
      v
Artifact compatible with expected Java release
```

---

# 31. Source and Target Concepts

Older or existing Maven configurations may use:

```xml
<properties>
    <maven.compiler.source>17</maven.compiler.source>
    <maven.compiler.target>17</maven.compiler.target>
</properties>
```

You need to understand these concepts even if you use `release`.

Conceptually:

```text
source
→ which Java source language level is accepted

target
→ which JVM class-file target is generated
```

---

# 32. `source` Concept

The source level controls which Java language syntax the compiler accepts.

Conceptually:

```text
source = 17
```

means:

```text
Compile source according to the configured Java 17 language level.
```

If your source uses syntax introduced after that level, compilation can fail.

---

# 33. `target` Concept

The target level relates to the generated class-file version.

Conceptually:

```text
target = 17
```

means the compiler should produce class files for the corresponding target JVM level.

But source and target alone do not fully protect you from accidentally compiling against newer standard library APIs available in the JDK doing the compilation.

That is an important reason `release` exists.

---

# 34. Why `release` Is Often Preferable

The `--release` compiler mechanism provides a more complete compatibility model than simply combining `source` and `target` when supported.

Conceptually:

```text
source
→ language rules

target
→ class-file target

release
→ supported language, class-file target, and documented Java SE API view for that release
```

For modern builds, `maven.compiler.release` is often the clearer choice.

---

# 35. Do Not Configure Conflicting Java Levels

Avoid casually creating configurations such as:

```xml
<maven.compiler.release>17</maven.compiler.release>
<maven.compiler.source>21</maven.compiler.source>
<maven.compiler.target>21</maven.compiler.target>
```

This communicates contradictory intentions.

Choose a coherent Java compatibility policy.

For our beginner project, we can use:

```xml
<properties>
    <maven.compiler.release>17</maven.compiler.release>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
</properties>
```

if Java 17 is the intended project release.

# 40. What Is a Compilation Classpath?

Now we reach an important concept.

Suppose your code imports an external library:

```java
import org.apache.commons.lang3.StringUtils;
```

The Java compiler needs to know where the class:

```text
org.apache.commons.lang3.StringUtils
```

comes from.

It cannot compile references to classes it cannot find.

The set of classes and libraries available to the compiler forms the compilation classpath.

---

# 41. Simple Classpath Mental Model

Think of the classpath as:

```text
Places the compiler is allowed to look for classes it needs.
```

Suppose:

```text
App.java
    |
    +---- needs User.class
    |
    +---- needs ExternalLibrary.class
```

The compiler must be able to resolve those types.

Maven helps construct the appropriate classpath from the project and its dependencies.

---

# 42. Dependencies During Compilation

Suppose your POM contains a dependency:

```xml
<dependency>
    <groupId>org.apache.commons</groupId>
    <artifactId>commons-lang3</artifactId>
    <version>...</version>
</dependency>
```

Your source can then use a class provided by that library, assuming the dependency's scope makes it available during compilation.

Conceptually:

```text
pom.xml
   |
   v
Dependency declaration
   |
   v
Maven resolves dependency
   |
   v
Local repository
   |
   v
Dependency JAR
   |
   v
Compilation classpath
   |
   v
Java compiler can resolve imported classes
```

---

# 43. Compile Scope and Compilation

Recall dependency scopes from Part 6.

A normal `compile` dependency is available during main source compilation.

Conceptually:

```text
compile dependency
       |
       v
Compilation classpath
       |
       v
src/main/java can reference its classes
```

But not every dependency scope behaves the same way.

For example, a dependency that exists only for testing should not be assumed to be available to main application compilation.

---

# 44. Why Scope Mistakes Cause Compilation Errors

Imagine main code contains:

```java
import com.example.SomeLibrary;
```

but the corresponding dependency is declared with a scope that does not place it on the main compilation classpath.

The compiler may report that the package or symbol cannot be found.

The dependency exists in the POM, but it is not available where you expected it.

This is why:

```text
"Dependency exists"
```

does not automatically mean:

```text
"Dependency is on every classpath."
```

# 47. What Is a Symbol?

Compiler errors often mention:

```text
symbol
```

A symbol can refer to a program element the compiler is trying to identify, such as:

* Class
* Method
* Variable
* Field
* Interface

For example:

```java
User user = new User("Engineer");
```

The compiler needs to resolve:

```text
User
```

as a valid type.

If it cannot, you may see:

```text
cannot find symbol
```

---

# 48. Understanding `cannot find symbol`

Suppose you write:

```java
Usr user = new Usr("Engineer");
```

instead of:

```java
User user = new User("Engineer");
```

The compiler may not know what:

```text
Usr
```

means.

A simplified error might indicate:

```text
cannot find symbol
symbol: class Usr
```

This means the compiler tried to resolve the name but could not find a matching definition in the relevant context/classpath.

---

# 49. Common Causes of Missing Symbols

When you see:

```text
cannot find symbol
```

investigate:

1. Typo in the class name
2. Typo in the method name
3. Missing import
4. Wrong package
5. Missing dependency
6. Incorrect dependency scope
7. Source file not where expected
8. Generated source missing
9. Class renamed but references not updated
10. Wrong source set

Do not automatically add a new dependency.

First determine what symbol is actually missing.

---

# 50. Troubleshooting Missing Symbols

Use this reasoning:

```text
Cannot find symbol
       |
       v
What symbol?
       |
       v
Class, method, variable, field?
```

# 69. How to Investigate a Missing External Class

If an external class is missing:

# 70. Dependency Resolution Failure Versus Compilation Failure

These are different.

## Dependency resolution failure

Maven cannot obtain the required artifact.

Example concept:

```text

```

The compiler may never get a valid classpath.

## Compilation failure

Dependencies may resolve successfully, but Java source is invalid or references unavailable symbols.

Example:


Distinguishing these saves time.

# 71. What Is Source Encoding?

Source files contain characters.

Computers need an encoding to interpret those characters correctly.

A common encoding is:

```text
UTF-8
```

Your POM may contain:

```xml
<project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
```

This makes the intended source encoding explicit for Maven plugins that honor that project property.

---

# 72. Why Encoding Matters

Suppose your Java source contains:

```java
System.out.println("México");
```

or names and text containing accented or non-ASCII characters.

If the source file is stored using one encoding but interpreted using another, the compiler or application may encounter incorrect characters or errors.

Encoding consistency matters across:

```text
Developer editor
Source control
Maven build
CI runner
Packaging
Runtime
```

---

# 73. Encoding Problems

Possible symptoms include:

* Unmappable character errors
* Malformed input
* Strange replacement characters
* Different behavior locally and in CI
* Corrupted text

Investigate:

```text
What encoding is the file actually using?

What encoding does the build expect?

What encoding does the editor use?

What does CI use?
```

A clear project standard such as UTF-8 avoids many problems.

# 74. Compilation Warnings

* Unchecked operations
* Unsafe generic usage
* Other compiler concerns

# 76. Deprecated API Warnings

If compilation warns about deprecated code:

1. Identify the API.
2. Understand why it is deprecated.
3. Find the supported alternative.
4. Determine whether migration is appropriate.

Do not blindly suppress the warning.

# 94. Compile-Time Versus Runtime Errors

A compile-time error prevents successful compilation.

Example:


A runtime error occurs after code has compiled and the application is executing.

For example, an application may compile successfully but later fail because:

* A file is missing
* A server is unreachable
* A database connection fails
* A runtime dependency is absent
* Invalid runtime input occurs

Do not treat every Java failure as a Maven compilation problem.

```text
    +---- Plugin configuration
    |

    |
    v
compile phase
    |
    v

    |
    +---- Source files
    |
    +---- Compilation classpath
    |
    +---- Java release level
    |
    +---- Compiler configuration
    |
    +---- Generated source where applicable
    |
    v
Java Compilation
    |
    +---- Syntax checking
    |
    +---- Type checking
    |
    +---- Symbol resolution
    |
```
