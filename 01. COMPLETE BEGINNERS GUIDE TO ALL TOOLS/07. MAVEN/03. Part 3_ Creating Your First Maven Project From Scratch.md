# 1. What Is a Maven Project?

A Maven project is a software project that Maven can understand and manage according to Maven's project model.

At minimum, you will normally encounter a project configuration file named:

```text
pom.xml
```

along with source code arranged according to Maven conventions.

A simple Maven project may look like:

```text
my-application/
├── pom.xml
└── src/
    └── main/
        └── java/
```

A more complete structure may contain:

```text
my-application/
├── pom.xml
├── src/
│   ├── main/
│   │   ├── java/
│   │   └── resources/
│   └── test/
│       ├── java/
│       └── resources/
└── target/
```

The important relationship is:

```text
Maven Project
     |
     +---- pom.xml
     |
     +---- Application Source
     |
     +---- Resources
     |
     +---- Tests
     |
     +---- Build Output
```

Maven understands these pieces because they follow conventions.

---

# 2. A Directory Containing Java Is Not Automatically a Maven Project

Suppose you have:

```text
java-project/
└── Hello.java
```

That is a Java project directory in a general sense.

But it does not yet follow the normal Maven project model.

In Part 1, you could compile it manually:

```bash
javac Hello.java
```

Maven projects introduce structure and project metadata.

For example:

```text
maven-project/
├── pom.xml
└── src/
    └── main/
        └── java/
            └── Hello.java
```

Now Maven has:

```text
Project description
+
Standard source location
```

This allows Maven to know much more about how the project should be handled.

---

# 3. What Does Maven Need to Know About a Project?

Eventually Maven may need to know:

* What the project is called
* Which version it has
* Where its source code lives
* Where its tests live
* Which dependencies it needs
* Which Java version it should compile for
* Which plugins should participate in the build
* What kind of artifact should be produced

Instead of making every project invent its own build structure, Maven provides conventions.

The project's POM provides project-specific information.

The standard directory layout provides predictable locations for project files.

Together:

```text
pom.xml
+
Standard Directory Layout
        |
        v
Maven Understands Project
```

# 6. Understanding Maven's Standard Directory Layout

Maven expects certain files in standard locations.

A typical structure is:

```text
project-root/
├── pom.xml
└── src/
    ├── main/
    │   ├── java/
    │   └── resources/
    └── test/
        ├── java/
        └── resources/
```

When the project is built, Maven normally creates:

```text
target/
```

So the structure becomes:

```text
project-root/
├── pom.xml
├── src/
└── target/
```

Each location has a purpose.

---

# 7. Why Does Maven Expect a Standard Structure?

Remember the principle from Part 1:

```text
Convention over configuration
```

Maven prefers predictable defaults.

Instead of telling Maven:

```text
My Java source code is in:
application-code/java/files/

My test code is in:
testing/java-tests/

My resources are in:
configuration/resources/

Put compiled files in:
output/classes/
```

Maven provides standard locations.

For example:

```text
Application Java:
src/main/java

Application resources:
src/main/resources

Test Java:
src/test/java

Test resources:
src/test/resources

Generated build output:
target
```

If you follow these conventions, Maven already knows where to look.

---

# 8. Convention Reduces Configuration

Without conventions, every project might require extensive build configuration.

Project A:

```text
code/
tests/
output/
```

Project B:

```text
java-source/
unit-tests/
build-files/
```

Project C:

```text
application/
qa/
compiled/
```

A new engineer would first need to discover how every project is organized.

With Maven conventions:

```text
Project A
src/main/java
src/test/java
target

Project B
src/main/java
src/test/java
target

Project C
src/main/java
src/test/java
target
```

This makes Maven projects easier to recognize.

---

# 9. Why This Matters in DevOps

Imagine a CI pipeline receives 50 Maven repositories.

If they follow Maven conventions, the pipeline does not need completely different assumptions for every application.

A typical repository can be recognized as:

```text
Repository
   |
   +---- pom.xml
   |
   +---- src/
   |
   +---- target/ after build
```

A DevOps engineer examining an unfamiliar Java repository can immediately begin asking:

```text
Where is pom.xml?
What dependencies are declared?
What Maven phase is CI running?
What artifact appears under target?
```

Conventions improve predictability.

# 13. What Is `src`?

`src` is short for:

```text
source
```

The `src` directory contains files that belong to the project's source tree.

At the first level, Maven separates:

```text
main
```

from:

```text
test
```

So:

```text
src/
├── main/
└── test/
```

This separation is important.

---

# 14. What Is `src/main`?

`src/main` contains the application's main source material.

Conceptually:

```text
src/main/
├── java/
└── resources/
```

Think:

```text
main
=
Files that belong to the actual application
```

This is different from files used only for tests.

---

# 15. What Is `src/main/java`?

This is the conventional location for the application's Java source code.

```text
src/main/java/
```

For example:

```text
src/main/java/com/veriqta/app/Application.java
```

Maven understands that Java source files under this location are application source code.

Later, during compilation, Maven compiles this source.

Conceptually:

```text
src/main/java
      |
      v
Maven Compile
      |
      v
target/classes
```

---

# 16. What Is `src/main/resources`?

Not every application file is Java source code.

Applications can contain resources such as:

```text
.properties files
XML
JSON
YAML
Templates
Static configuration
Other application resources
```

Maven conventionally stores main application resources under:

```text
src/main/resources/
```

For example:

```text
src/main/resources/
└── application.properties
```

During the build, Maven can copy resources into the application's build output.

We will study resource processing in much greater depth later.

For now:

```text
src/main/java
→ Java application source

src/main/resources
→ Non-Java application resources
```

---

# 17. What Is `src/test`?

Tests are separated from application source.

Maven conventionally uses:

```text
src/test/
```

with:

```text
src/test/java/
src/test/resources/
```

This distinction allows Maven to treat test code differently from production application code.

---

# 18. What Is `src/test/java`?

Test Java source files belong under:

```text
src/test/java/
```

For example:

```text
src/test/java/com/veriqta/app/ApplicationTest.java
```

The main application might contain:

```text
src/main/java/com/veriqta/app/Application.java
```

while its test may appear under:

```text
src/test/java/com/veriqta/app/ApplicationTest.java
```

Conceptually:

```text
Application Source
src/main/java

Test Source
src/test/java
```

Later Maven can compile and run tests separately from main source.

---

# 19. What Is `src/test/resources`?

Tests sometimes require their own files.

Examples:

```text
Test configuration
Sample JSON
Fixture files
Test data
Mock resources
```

These can be placed under:

```text
src/test/resources/
```

These resources are intended for the test environment rather than normal application resources.

---

# 20. Main Versus Test Structure

The structure is deliberately symmetrical:

```text
src/
├── main/
│   ├── java/
│   └── resources/
└── test/
    ├── java/
    └── resources/
```

Think:

```text
main
→ actual application

test
→ code and resources used to test application
```

---

# 21. What Is `target`?

`target` is Maven's standard build-output directory.

This is where Maven places generated build files.

You do not normally write your application source code there.

Maven generates its contents.

After compilation, you may see:

```text
target/
└── classes/
```

Later builds may generate additional directories and files.

For example:

```text
target/
├── classes/
├── test-classes/
├── surefire-reports/
└── application.jar
```

The exact contents depend on what phases and plugins have run.

---

# 22. Source Versus Build Output

This distinction is fundamental.

```text
src/
→ You maintain this

target/
→ Maven generates this
```

Think of the flow:

```text
src/
 |
 v
Maven
 |
 v
target/
```

If `target` is deleted, your source code should still exist.

Maven should be able to recreate generated build output from the project source and configuration.

This is one reason generated `target` directories are normally not committed to Git.

# 23. What Are Java Packages?

Before creating our source file, we need to understand Java packages.

A Java package groups related classes into a namespace.

For example:

```java
package com.veriqta.app;
```

This says that the class belongs to:

```text
com.veriqta.app
```

Packages help:

* Organize classes
* Avoid naming conflicts
* Create logical namespaces
* Structure larger applications

---

# 24. Package Name and Directory Structure

A Java package such as:

```text
com.veriqta.app
```

normally maps to directories:

```text
com/
└── veriqta/
    └── app/
```

Therefore:

```java
package com.veriqta.app;
```

belongs conceptually under:

```text
src/main/java/com/veriqta/app/
```

A class named:

```text
Application
```

becomes:

```text
src/main/java/com/veriqta/app/Application.java
```

The mapping is:

```text
Package:
com.veriqta.app

        ↓

Directories:
com/veriqta/app

        ↓

Source:
src/main/java/com/veriqta/app/Application.java
```

---

# 25. Why Not Put `Application.java` Directly Under `src/main/java`?

Technically, Java can have classes in the unnamed package, but real projects normally use named packages.

Instead of:

```text
src/main/java/Application.java
```

we will use:

```text
src/main/java/com/veriqta/app/Application.java
```

This teaches the structure you will encounter in real Java projects.

# 48. What Maven Does When You Run `mvn compile`

At a high level, Maven:

1. Starts.
2. Locates the project's POM.
3. Reads the project model.
4. Determines the build lifecycle work required through `compile`.
5. Resolves required build plugins and related artifacts.
6. Processes resources as required by earlier lifecycle phases.
7. Finds Java source under the conventional source location.
8. Invokes compilation through Maven's compiler tooling.
9. Places generated class files in the build output directory.
10. Reports whether the build succeeded or failed.

Conceptually:

```text

     |
     v
Read pom.xml
     |
     v
Build Project Model
     |
     v
Resolve Required Build Components
     |
     v
Process Resources
     |
     v
Compile Java
     |
     v
target/classes
```

# 106. Knowledge Check Answers

## 1. What makes a project a Maven project?

It follows Maven's project model, normally includes a `pom.xml`, and typically uses Maven's standard project layout.

## 2. What is the project root?

The top-level directory of the project.

For this project:

```text
veriqta-maven-app/
```

## 3. Where is `pom.xml`?

At the project root in the standard project structure.

## 4. What does POM mean?

Project Object Model.

## 5. What belongs in `src/main/java`?

The application's main Java source code.

## 6. What belongs in `src/main/resources`?

Non-Java resources used by the main application.

## 7. What belongs in `src/test/java`?

Java test source code.

## 8. What belongs in `src/test/resources`?

Resources used by tests.

## 9. What is `target`?

Maven's standard generated build-output directory.

## 10. Should application source be written in `target`?

No.

Application source belongs under `src`.

## 11. Why standard directories?

They let Maven understand common project locations without requiring configuration for every directory.

## 12. What directory represents `com.veriqta.app`?

```text
com/veriqta/app
```

## 13. Where does our `Application.java` belong?

```text
src/main/java/com/veriqta/app/Application.java
```

## 14. What does `mvn compile` do?

It runs the Maven build through the compile phase, which includes processing required earlier lifecycle work and compiling the main application source.

## 15. Why does Maven download files?

Build tasks are performed using plugins and related artifacts that may need to be obtained from repositories.

## 16. Where are downloaded Maven artifacts normally cached?

```text
~/.m2/repository
```

## 17. Where are compiled main classes placed?

Normally:

```text
target/classes
```

## 18. `.java` versus `.class`?

`.java` contains source code.

`.class` contains compiled Java bytecode.

## 19. Why use `com.veriqta.app.Application`?

Because that is the fully qualified name of the packaged Java class.

## 20. What does `-cp target/classes` do?

It tells Java to include `target/classes` as a location where classes can be found.

## 21. Does `mvn compile` create the final JAR?

Not necessarily.

Compilation and packaging are separate build stages.

## 22. What does `mvn clean` do?

It removes generated build output from the Maven clean lifecycle, normally including the `target` directory in a standard project.

## 23. Why can Maven recreate `target`?

Because `target` contains generated build output produced from project source and configuration.

## 24. Why normally exclude `target` from Git?

Because it contains generated files that Maven can recreate.

## 25. Maven cannot find the POM?

Check your current working directory and verify that `pom.xml` exists there.

## 26. Java syntax error?

Read the compiler error, identify the source file and line, correct the Java source, and rebuild.

## 27. Plugin download failure?

Possible causes include network, repository, proxy, certificate, offline-mode, or Maven configuration problems.

## 28. Environment versus build problem?

An environment problem can prevent Maven from starting correctly.

A project build problem occurs after Maven starts but cannot successfully process the project.

## 29. Why create the project manually?

It exposes the Maven directory structure and project model instead of hiding them behind a generator.

## 30. What is our current build flow?

```text
Developer
    |
    v
Application.java
    |
    v
src/main/java/com/veriqta/app/
    |
    v
pom.xml + Maven conventions
    |
    v
mvn compile
    |
    v
Maven lifecycle
    |
    v
Compiler tooling
    |
    v
Java compiler
    |
    v
target/classes/com/veriqta/app/Application.class
```
