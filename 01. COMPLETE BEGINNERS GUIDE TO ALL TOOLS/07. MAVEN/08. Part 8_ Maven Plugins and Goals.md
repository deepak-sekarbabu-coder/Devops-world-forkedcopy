# Part 8: Maven Plugins and Goals

## Introduction

In Part 5, you learned that Maven has build lifecycles and phases.

You can run:

```bash
mvn compile
```

or:

```bash
mvn test
```

or:

```bash
mvn package
```

In Part 7, you learned how Maven retrieves artifacts from repositories.

Now we need to answer one of the most important Maven questions:

What actually performs the work?

When you run:

```bash
mvn compile
```

Maven does not contain one giant built-in function called "compile everything."

When you run:

```bash
mvn test
```

Maven itself is not the component that directly executes every test.

When you run:

```bash
mvn package
```

Maven does not personally create every JAR or WAR.

Instead, Maven coordinates the build and uses plugins to perform much of the actual work.

The beginner mental model is:

```text
Developer
    |
    v
Maven Command
    |
    v
Lifecycle Phase
    |
    v
Plugin Goal
    |
    v
Actual Build Work
```

For example:

```text
mvn compile
    |
    v
compile phase
    |
    v
Compiler Plugin
    |
    v
compiler:compile goal
    |
    v
Java source is compiled
```

This part will make that relationship clear.

By the end, you should understand:

* What a Maven plugin is
* Why Maven uses plugins
* What plugin goals are
* What plugin prefixes are
* How plugins have Maven coordinates
* What build plugins are
* What reporting plugins are
* What default lifecycle bindings are
* How plugin executions work
* How plugins are configured in `pom.xml`
* How goals are bound to lifecycle phases
* How to execute a plugin goal directly
* How common Maven plugins fit into the build
* Why plugin versions matter
* How to investigate plugin problems
* How to see which plugin actually performs a build task

The goal is that when Maven prints something such as:

```text
maven-compiler-plugin:compile
```

you understand exactly why it appeared.

---

# 1. What Is a Maven Plugin?

A Maven plugin is a collection of one or more goals that perform specific tasks during a Maven build or provide Maven-related utilities.

Examples of tasks include:

* Compiling Java source
* Copying resources
* Running unit tests
* Running integration tests
* Creating JAR files
* Creating WAR files
* Cleaning build output
* Installing artifacts locally
* Deploying artifacts remotely
* Analyzing dependencies
* Displaying Maven configuration
* Running Java programs

Think of Maven as the coordinator and plugins as specialized workers.

```text
                    Maven
                      |
        +-------------+-------------+
        |             |             |
        v             v             v
    Compiler       Surefire       JAR
     Plugin         Plugin        Plugin
        |             |             |
        v             v             v
     Compile         Test         Package
```

Maven understands the build model and lifecycle.

Plugins perform specific pieces of work.

---

# 2. Why Does Maven Use Plugins?

Imagine Maven directly implemented every possible build task.

It would need built-in logic for:

```text
Java compilation
Kotlin compilation
Testing
Packaging
Code generation
Static analysis
Documentation
Container-related tasks
Application execution
Deployment
Database tasks
Framework-specific tasks
```

The tool would become enormous and difficult to extend.

Instead, Maven uses a plugin architecture.

Conceptually:

```text
Maven Core
    |
    +---- Build model
    +---- POM processing
    +---- Lifecycle coordination
    +---- Dependency resolution
    +---- Plugin execution framework
              |
              v
           Plugins
```

Plugins provide specialized behavior.

---

# 3. Maven Core Versus Plugins

A useful distinction is:

```text
Maven Core
→ understands the project model
→ reads POMs
→ builds the effective model
→ coordinates lifecycles
→ resolves dependencies and plugins
→ determines what should execute

Plugins
→ perform specific build tasks
```

For example:

```text
Maven determines:
"We are executing the compile phase."

Compiler Plugin performs:
"Compile these Java source files."
```

This separation is fundamental to Maven.

---

# 4. A Plugin Can Contain Multiple Goals

A plugin is not necessarily one task.

A plugin can expose multiple goals.

Think:

```text
Plugin
   |
   +---- Goal A
   +---- Goal B
   +---- Goal C
```

Each goal represents a specific unit of work.

For example, the Maven Compiler Plugin has goals associated with compiling main source code and test source code.

Conceptually:

```text
Compiler Plugin
      |
      +---- compile
      |
      +---- testCompile
```

The plugin is the collection.

The goal is the particular task.

---

# 5. What Is a Plugin Goal?

A goal is a specific task provided by a Maven plugin.

Examples:

```text
compiler:compile
dependency:tree
dependency:list
help:effective-pom
help:effective-settings
```

The general form is:

```text
plugin-prefix:goal
```

For example:

```text
compiler:compile
```

means:

```text
compiler
→ plugin prefix

compile
→ goal
```

---

# 6. Goal Versus Phase

This distinction is critical.

A phase is a stage in a Maven lifecycle.

A goal is a task performed by a plugin.

For example:

```text
compile
```

can refer to a lifecycle phase when used as:

```bash
mvn compile
```

But:

```text
compiler:compile
```

is a plugin goal.

Used as:

```bash
mvn compiler:compile
```

it directly invokes that goal.

So:

```text
mvn compile
```

and:

```text
mvn compiler:compile
```

are related, but they do not mean exactly the same thing.

---

# 7. Beginner Mental Model: Phase Versus Goal

Think:

```text
PHASE
"What stage of the build are we reaching?"

GOAL
"What specific task should a plugin perform?"
```

Example:

```text
compile phase
     |
     v
compiler:compile goal
```

Another example:

```text
test phase
     |
     v
surefire:test goal
```

Another:

```text
package phase
     |
     v
jar:jar goal
```

for a typical JAR project.

Put all four concepts together:

```text
Lifecycle
    |
    v

    v
```

For example:


# 9. What Is a Plugin Prefix?

Typing the full Maven coordinates of a plugin every time would be inconvenient.

Maven supports plugin prefixes.

For example:

```bash
mvn dependency:tree
```

Here:

```text
dependency
```

is the plugin prefix.

The goal is:

```text
tree
```

Together:

```text
dependency:tree
```

means:

```text
Run the tree goal of the Maven Dependency Plugin.
```

# 11. Plugins Have Maven Coordinates

Plugins are artifacts too.

That means they can be identified using Maven coordinates.

A plugin has concepts such as:

```text
groupId
artifactId
version
```

For example, a Maven plugin may use coordinates conceptually like:

```text
org.apache.maven.plugins
:
maven-compiler-plugin
:
<version>
```

This should look familiar.

It uses the same coordinate model you learned for dependencies.

---

# 12. Plugin Coordinates Versus Dependency Coordinates

Both dependencies and plugins are Maven artifacts.

They can both have:

```text
groupId
artifactId
version
```

But their roles differ.

```text
Dependency
→ normally provides code/resources to your project

Plugin
→ performs work during the Maven build
```

For example:

```text
JUnit
→ project/test dependency

Maven Surefire Plugin
→ executes unit tests during the Maven build
```

Do not confuse the test framework with the plugin that runs tests.

---

# 13. Plugins Also Come From Repositories

In Part 7, you learned:

```text
Maven
→ Local Repository
→ Remote Repository
```

That applies to plugins too.

When Maven needs a plugin:

```text
Maven
   |
   v
Plugin Needed
   |
   v
Local Repository
   |
   +---- Found → Use
   |
   +---- Missing
            |
            v
      Remote Repository
            |
            v
         Download
            |
            v
        Cache Locally
            |
            v
          Execute
```

This is one reason the first Maven build can download many files even if your project has very few dependencies.

---

# 14. Plugin Dependencies

Plugins can also have their own dependencies.

So a build may resolve:

```text
Your project dependencies
+
Transitive project dependencies
+
Maven plugins
+
Plugin dependencies
```

This is important for both troubleshooting and software supply-chain security.

A plugin is executable build logic.

You should care where it comes from.

# 15. What Is a Build Plugin?

A build plugin participates in building the project.

Examples include plugins that:

* Compile source
* Copy resources
* Run tests
* Package applications
* Install artifacts
* Deploy artifacts

Build plugins are commonly configured inside:

```xml
<build>
    <plugins>
        ...
    </plugins>
</build>
```

---

# 16. Basic Build Plugin Structure

A plugin declaration can look like:

```xml
<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-compiler-plugin</artifactId>
            <version>PLUGIN_VERSION</version>
        </plugin>
    </plugins>
</build>
```

Do not literally use:

```text
PLUGIN_VERSION
```

in a real build.

It represents the specific plugin version your project chooses.

---

# 17. Understanding `<build>`

The:

```xml
<build>
```

section contains configuration related to how Maven builds the project.

Conceptually:

```text
pom.xml
|
+---- project identity
|
+---- dependencies
|
+---- properties
|
+---- build
       |
       +---- plugins
       +---- other build configuration
```

The build section does not mean:

```text
Start the build here.
```

It describes build-related configuration.

# 18. Understanding `<plugins>`

Inside:

```xml
<build>
```

the:

```xml
<plugins>
```

element contains build plugin declarations.

Example:

```xml
<build>
    <plugins>

        <plugin>
            ...
        </plugin>

        <plugin>
            ...
        </plugin>

    </plugins>

```

Think:

```text

   |

   |

   +---- Surefire Plugin
   +---- JAR Plugin
```

# 19. Understanding `<plugin>`

Each:

```xml
<plugin>
```

element describes one plugin.

For example:

```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-compiler-plugin</artifactId>
    <version>PLUGIN_VERSION</version>
</plugin>
```

This tells Maven which plugin artifact the project is referring to.

For plugins in Maven's standard plugin group:

```text

```

you may see examples where `groupId` is omitted.

For learning, however, it is useful to understand the complete identity:

```text
groupId
artifactId
version
```

because it reinforces that plugins are Maven artifacts.

# 21. What Is a Reporting Plugin?

Maven also supports reporting-oriented plugins.

Reporting plugins are associated with generating project reports, commonly as part of Maven's site/reporting mechanisms.

Examples of reports might involve:

* Project information
* Test reports
* Dependency information
* Code-quality information

Historically, reporting plugins are commonly configured under:

```xml
<reporting>
```

rather than:

```xml
<build>
```

depending on how the plugin and report are being used.

# 22. Build Plugin Versus Reporting Plugin

Beginner mental model:

```text
Build Plugin
→ participates in build work

Reporting Plugin
→ produces reports/project reporting output
```

The same underlying plugin ecosystem may sometimes support different modes of use, so always consult the plugin's actual documentation when configuring a real project.

For now, the key distinction is purpose.

# 23. What Are Default Lifecycle Bindings?

Here is where Maven becomes much clearer.

You already know Maven has phases such as:

```text
compile
test
package
install
deploy
```

But a phase is only a point in a lifecycle.

Actual work occurs because plugin goals are bound to phases.

A binding means:

```text
When Maven reaches this phase,
execute this plugin goal.
```

---

# 24. Lifecycle Binding Mental Model

Consider:

```text
compile phase
     |
     v
compiler:compile
```

The plugin goal is bound to the lifecycle phase.

Therefore:

```bash
mvn compile
```

causes Maven to move through the lifecycle until `compile`.

When it reaches phases that have goals bound to them, those goals execute.

---

# 25. Why Packaging Type Matters

Default lifecycle bindings can depend on the project's packaging type.

Recall:

```xml
<packaging>jar</packaging>
```

or:

```xml
<packaging>war</packaging>
```

A JAR project and a WAR project do not necessarily package themselves using the same plugin goal.

Conceptually:

```text
packaging = jar
     |
     v
package phase
     |
     v
JAR Plugin
     |
     v
jar:jar
```

Whereas:

```text
packaging = war
     |
     v
package phase
     |
     v
WAR Plugin
     |
     v
war:war
```

The lifecycle phase is still `package`.

The packaging-specific work differs.

# 27. `mvn package` Is Really a Chain of Work

Suppose you run:

```bash
mvn package
```

Maven does not simply jump to:

```text
Create JAR.
```

It progresses through earlier phases.

For a typical JAR project, the conceptual flow is:

```text
validate
   |
   v
...
   |
   v
process-resources
   |
   v
resources:resources
   |
   v
compile
   |
   v
compiler:compile
   |
   v
process-test-resources
   |
   v
resources:testResources
   |
   v
test-compile
   |
   v
compiler:testCompile
   |
   v
test
   |
   v
surefire:test
   |
   v
package
   |
   v
jar:jar
```

This is why `mvn package` can compile and test before creating the package.

---

# 28. Phase Names Do Not Perform Work by Themselves

This is subtle but important.

Think of a lifecycle phase as a labeled stage.

The actual task is performed by a goal bound to that stage.

So:

```text
Phase
→ position in lifecycle

Goal
→ executable task
```

That is why understanding plugins is necessary to understand Maven.

---

# 29. What Is Plugin Execution?

A plugin execution describes how and when a plugin goal should execute as part of the build.

It can specify:

* An execution ID
* A lifecycle phase
* One or more goals
* Configuration

The structure commonly looks like:

```xml
<plugin>
    ...
    <executions>
        <execution>
            <id>some-id</id>
            <phase>some-phase</phase>
            <goals>
                <goal>some-goal</goal>
            </goals>
        </execution>
    </executions>
</plugin>
```

---

# 30. Understanding `<executions>`

A plugin may need to run one or more times in specific ways.

The:

```xml
<executions>
```

container holds those execution definitions.

Think:

```text
Plugin
   |
   +---- Execution 1
   |
   +---- Execution 2
```

Each execution can have its own:

* ID
* Phase
* Goals
* Configuration

---

# 31. Understanding `<execution>`

An:

```xml
<execution>
```

describes one execution arrangement for the plugin.

Example:

```xml
<execution>
    <id>run-custom-task</id>
    <phase>verify</phase>
    <goals>
        <goal>some-goal</goal>
    </goals>
</execution>
```

This conceptually means:

```text
When build reaches verify
        |
        v
Run this configured plugin goal
```

assuming the plugin and goal support that use.

---

# 32. What Is the Execution ID?

Example:

```xml
<id>run-custom-task</id>
```

The ID gives the execution a name.

It helps:

* Identify the execution
* Distinguish multiple executions
* Understand effective POM output
* Work with inherited/plugin configuration

Use meaningful IDs.

For example:

```text
generate-client-code
```

is more understandable than:

```text
execution1
```

---

# 33. Understanding `<goals>`

The:

```xml
<goals>
```

element contains one or more:

```xml
<goal>
```

entries.

Example:

```xml
<goals>
    <goal>compile</goal>
</goals>
```

The goal belongs to the plugin surrounding the execution.

So if this is inside the Compiler Plugin:

```xml
<plugin>
    <artifactId>maven-compiler-plugin</artifactId>

    <executions>
        <execution>
            <goals>
                <goal>compile</goal>
            </goals>
        </execution>
    </executions>
</plugin>
```

the goal is the Compiler Plugin's:

```text
compile
```

goal.

---

# 34. Binding a Goal to a Phase

A simplified structure is:

```xml
<plugin>
    <groupId>example.group</groupId>
    <artifactId>example-plugin</artifactId>
    <version>PLUGIN_VERSION</version>

    <executions>
        <execution>
            <id>example-execution</id>
            <phase>verify</phase>

            <goals>
                <goal>example-goal</goal>
            </goals>
        </execution>
    </executions>
</plugin>
```

Conceptually:

```text
verify phase
     |
     v
example-plugin
     |
     v
example-goal
```

You have explicitly connected a plugin goal to a lifecycle phase.

---

# 35. Default Binding Versus Explicit Binding

There are two concepts to distinguish.

## Default lifecycle binding

Maven's lifecycle/packaging model already associates a goal with a phase.

Example conceptually:

```text
jar packaging
+
compile phase
→ compiler:compile
```

You did not need to write the binding yourself.

## Explicit binding

You configure a plugin execution yourself:

```xml
<phase>verify</phase>
```

and specify a goal.

Think:

```text
Default binding
→ Maven already knows it

Explicit binding
→ your POM tells Maven to add/configure it
```

---

# 36. What Is `<configuration>`?

Plugins often accept configuration parameters.

These are commonly placed inside:

```xml
<configuration>
```

Example conceptually:

```xml
<plugin>
    ...
    <configuration>
        <someOption>someValue</someOption>
    </configuration>
</plugin>
```

This tells the plugin how you want it to perform its task.

---

# 37. Plugin Configuration Is Plugin-Specific

There is no universal list of configuration options that works for every Maven plugin.

For example:

```text
Compiler Plugin
→ compiler-related options

Surefire Plugin
→ unit-test execution options

JAR Plugin
→ JAR packaging options

Exec Plugin
→ application/process execution options
```

Therefore you should never invent configuration keys because they sound reasonable.

Use the plugin's documented parameters.

---

# 38. Plugin-Level Configuration

Configuration can be placed directly inside a plugin declaration.

Example:

```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-compiler-plugin</artifactId>
    <version>PLUGIN_VERSION</version>

    <configuration>
        ...
    </configuration>
</plugin>
```

This configuration generally applies to the relevant plugin use according to Maven's configuration rules.

---

# 39. Execution-Level Configuration

Configuration can also appear inside a particular execution.

Conceptually:

```xml
<executions>
    <execution>
        <id>special-execution</id>

        <goals>
            <goal>some-goal</goal>
        </goals>

        <configuration>
            ...
        </configuration>
    </execution>
</executions>
```

This allows configuration to be associated with that specific execution.

This becomes useful when the same plugin has multiple executions requiring different behavior.

---

# 40. Running a Goal Directly

You do not always need to run a lifecycle phase.

A plugin goal can often be invoked directly.

General syntax:

```bash
mvn plugin-prefix:goal
```

Examples:

```bash
mvn compiler:compile
```

```bash
mvn dependency:tree
```

```bash
mvn help:effective-pom
```

This is direct goal execution.

---

# 41. Direct Goal Execution Versus Lifecycle Execution

Compare:

```bash
mvn compile
```

with:

```bash
mvn compiler:compile
```

First:

```text
mvn compile
→ execute lifecycle through compile
→ execute relevant bindings along the way
```

Second:

```text
mvn compiler:compile
→ directly invoke Compiler Plugin's compile goal
```

They may both result in Java compilation, but the execution model differs.

---

# 42. Why This Difference Matters

Suppose earlier lifecycle phases contain important work.

Running:

```bash
mvn compile
```

moves through the lifecycle to `compile`.

Running a single goal directly does not mean:

```text
Run the complete lifecycle until the equivalent phase.
```

It means:

```text
Invoke this goal.
```

That difference becomes important in more complex builds.

---

# 43. Running Multiple Things

Maven CLI can receive multiple tasks.

For example:

```bash
mvn clean package
```

Here:

```text
clean
→ phase in the clean lifecycle

package
→ phase in the default lifecycle
```

Maven executes them in the order requested.

You may also encounter combinations involving direct goals and phases.

Always read the command left to right and identify:

```text
Is this a lifecycle phase?

Or a plugin goal?
```

Run:

```bash
mvn package
```

You may see output resembling:

```text
--- maven-resources-plugin:...:resources (...) @ project ---
```

then:

```text

```

then:

```text

```

then:

```text

```

# 45. How to Read a Plugin Execution Line

Suppose Maven prints something conceptually like:

```text

```

Break it down:

```text

→ plugin artifact

3.x.x
→ plugin version

→ goal
```

If Maven also shows an execution identifier, that helps identify which configured/default execution is running.

Reading these lines is essential for troubleshooting.

# 49. Compiler Configuration

Modern Maven projects commonly define the Java release level using properties or plugin configuration.

For example:

```xml
<properties>
    <maven.compiler.release>17</maven.compiler.release>
</properties>
```

Conceptually this tells Maven's compiler configuration:

```text
Compile this project for Java 17 semantics/API level.
```

The exact appropriate Java release depends on the project.

Do not blindly set a Java version simply because another project uses it.

---

# 50. Common Compiler Plugin Problems

You may encounter errors involving:

* Unsupported release versions
* Missing JDK compiler
* Incorrect Java version
* Source syntax incompatible with configured release
* Missing dependencies
* Compilation errors
* Incorrect source directories

For example:

```text
release version 21 not supported
```

may indicate that Maven is running with a JDK that cannot compile for the requested release.

The problem may not be Maven itself.

Check:

```bash
java -version
```

```bash
javac -version
```

```bash
mvn -version
```

Remember that `mvn -version` shows which Java runtime Maven is actually using.

When you run:

```bash
mvn clean
```

the clean lifecycle normally invokes Clean Plugin functionality.

Conceptually:

```text
mvn clean
    |
    v
clean lifecycle
    |
    v
Clean Plugin
    |
    v
```

# 61. Maven Failsafe Plugin

The Maven Failsafe Plugin is designed for integration-test execution patterns.

# 62. Why Surefire and Failsafe Are Separate

Unit tests and integration tests often have different operational needs.

Unit tests may:

* Run quickly
* Test isolated units
* Avoid external infrastructure

Integration tests may:

* Start services
* Contact databases
* Use containers
* Exercise multiple components
* Require setup and cleanup

Maven's lifecycle provides phases specifically around integration testing:

```text
pre-integration-test
integration-test
post-integration-test
verify
```

Failsafe is designed to work with this style of lifecycle.

---

# 63. Why `verify` Matters With Failsafe

A common Failsafe pattern separates:

```text

```

from:

```text
Evaluate their final result
```

Conceptually:

```text

        |
        v
Prepare environment
        |
        v
integration-test
        |
        v
Run integration tests
        |
        v
post-integration-test
        |
        v
Clean up environment
        |
        v
verify
        |
        v
Check test results
```

This allows cleanup-related lifecycle work to happen before the build is finally failed for integration-test failures.

# 85. Default Bindings Can Make Plugins Seem Invisible

# 86. Why Configure a Plugin Explicitly?

If Maven already has default bindings, why declare the plugin?

Possible reasons include:

* Control plugin version
* Change plugin configuration
* Add executions
* Bind additional goals
* Override inherited/default behavior
* Make build behavior explicit

For production projects, controlling important plugin versions improves reproducibility.

# 87. Why Plugin Versions Matter

Suppose your POM declares:

* Parent POM

* Other inherited configuration

# 92. `<pluginManagement>` Does Not Automatically Mean "Run This Plugin"

Suppose a parent defines:

```xml

            ...
        </plugin>
```

That generally provides managed plugin information.

It does not, by itself, mean every child project executes that plugin as a new build plugin.

A child can reference the plugin under:

```xml

```

and inherit the managed configuration/version.

This distinction becomes very important later in multi-module Maven.

# 132. Common Beginner Mistakes

## Mistake 1

Thinking:

```text
mvn compile
```

and:

```text
mvn compiler:compile
```

are exactly identical.

They are not.

One invokes a lifecycle phase.

The other directly invokes a plugin goal.

---

## Mistake 2

Thinking phases themselves contain all build logic.

Actual build tasks are largely performed by plugin goals.

---

## Mistake 3

Thinking plugins are the same as dependencies.

They are both artifacts, but they serve different roles.

---

## Mistake 4

Thinking Surefire is JUnit.

It is not.

---

## Mistake 5

Thinking `mvn deploy` deploys the application to production.

In Maven's lifecycle, deploy normally concerns publishing artifacts to a remote repository.

---

## Mistake 6

Adding random plugins from old tutorials.

Every plugin added to a build should have a clear purpose and trusted source.

---

## Mistake 7

Leaving important plugin versions uncontrolled without understanding where their versions come from.

Inspect the effective build configuration.

---

## Mistake 8

Seeing:

```text
BUILD FAILURE
```

without reading which plugin and goal failed.

The plugin often tells you which part of the build needs investigation.

# 137. Knowledge Check Answers

## 1. What is a Maven plugin?

A Maven plugin is a collection of goals that performs specific build, reporting, or Maven-related tasks.

## 2. Why use plugins?

They allow Maven to coordinate specialized and extensible build functionality without implementing every possible task directly in Maven Core.

## 3. What is a goal?

A specific executable task provided by a plugin.

## 4. Multiple goals?

Yes.

A plugin can expose many goals.

## 5. Plugin prefix?

A shortened command-line identifier used to invoke a plugin's goals.

## 6. Prefix in `dependency:tree`?

```text
dependency
```

## 7. Goal?

```text
tree
```

## 8. Phase versus goal?

A phase is a stage in a lifecycle. A goal is a concrete task performed by a plugin.

## 9. `mvn compile` versus `mvn compiler:compile`?

`mvn compile` executes the lifecycle through the `compile` phase.

`mvn compiler:compile` directly invokes the Compiler Plugin's `compile` goal.

## 10. Plugin coordinates?

Yes.

Plugins are Maven artifacts.

## 11. Main coordinate elements?

```text
groupId
artifactId
version
```

## 12. Plugin versus dependency?

They are both artifacts, but they serve different purposes. Dependencies normally contribute code/resources to the project. Plugins perform build-related work.

## 13. Plugin dependencies?

Yes.

## 14. Where are plugins obtained?

From Maven repositories, using local and remote resolution mechanisms.

## 15. Build plugin?

A plugin that participates in building the project.

## 16. Reporting plugin?

A plugin used to produce project reporting information, commonly through Maven reporting/site mechanisms.

## 17. `<build>`?

It contains project build-related configuration.

## 18. `<plugins>`?

It contains build plugin declarations.

## 19. `<plugin>`?

It describes a particular plugin and its version, configuration, executions, and related information.

## 20. Default lifecycle binding?

A predefined association between lifecycle phases and plugin goals for a packaging type.

## 21. Why does packaging matter?

Different artifact types require different build tasks, especially during packaging.

## 22. Java compilation?

Maven Compiler Plugin.

## 23. Resources?

Maven Resources Plugin.

## 24. Unit tests?

Maven Surefire Plugin.

## 25. Integration tests?

Maven Failsafe Plugin is commonly used.

## 26. JAR packaging?

Maven JAR Plugin.

## 27. WAR packaging?

Maven WAR Plugin.

## 28. Local installation?

Maven Install Plugin.

## 29. Remote artifact publication?

Maven Deploy Plugin.

## 30. Dependency Plugin?

It provides goals for inspecting and working with project dependencies.

## 31. Exec Plugin?

It can execute programs or Java classes through Maven.

## 32. Help Plugin?

It helps inspect Maven configuration, effective models, plugins, goals, and related information.

## 33. `<executions>`?

A container for one or more configured plugin executions.

## 34. `<execution>`?

A definition describing a particular way a plugin goal or goals should participate in the build.

## 35. Execution ID?

A name identifying a particular plugin execution.

## 36. `<goals>`?

It lists plugin goals associated with the execution.

## 37. `<configuration>`?

It provides parameters controlling plugin behavior.

## 38. Execution-specific configuration?

Yes.

## 39. Bind goal to phase?

Configure the goal so Maven executes it when the lifecycle reaches that phase.

## 40. Can a `generate-sources` goal run during `mvn compile`?

Yes, if it is correctly bound.

## 41. Why?

Because `generate-sources` occurs before `compile`, and invoking `compile` executes earlier phases in that lifecycle.

## 42. Why can undeclared plugins run?

Default lifecycle bindings, parent configuration, profiles, or inherited Maven configuration can cause plugin goals to participate.

## 43. Effective POM?

It helps show the final project model Maven actually uses after inheritance and defaults are considered.

## 44. `help:describe`?

It describes Maven plugins, goals, and optionally detailed parameters.

## 45. Why control versions?

To improve build consistency, predictability, and reproducibility.

## 46. Maven version versus plugin version?

They are separate.

Maven itself and each plugin have independent versions.

## 47. `<pluginManagement>`?

It centrally manages plugin versions and configuration for reuse, especially across parent and multi-module builds.

## 48. Does plugin management automatically execute every managed plugin?

No.

Managing a plugin is not the same as declaring it as an active build plugin.

## 49. Why supply-chain concern?

Plugins execute code on developer machines and CI systems, which may have access to source code and sensitive build credentials.

## 50. First troubleshooting step?

Identify the plugin, goal, execution, and actual error associated with the failure.
