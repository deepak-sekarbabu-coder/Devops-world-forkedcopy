# Part 6: Maven Dependencies From Absolute Beginner Level

## Introduction

One of Maven's most important jobs is dependency management.

So far, your Maven project has used only Java functionality already available from the JDK.

That means your application could compile without downloading an external application library.

Real Java applications are different.

They often need third-party code for tasks such as:

* JSON processing
* Logging
* HTTP communication
* Testing
* Database access
* Security
* Web applications
* Dependency injection
* Configuration
* Messaging
* Serialization

Instead of writing all of that functionality yourself, your application can use libraries and frameworks created by other developers.

Those external components become dependencies.

This part builds the full beginner mental model:

```text
Application
    |
    +---- Dependency A
    |
    +---- Dependency B
    |
    +---- Dependency C
```

Then Maven expands that model further:

```text
pom.xml
   |
   v
Declared dependencies
   |
   v
Maven
   |
   v
Repositories
   |
   v
Download artifacts
   |
   v
Resolve transitive dependencies
   |
   v
Build classpath
   |
   v
Compile / Test / Run
```

By the end of this part, you should understand not only how to add a dependency, but how Maven finds it, resolves it, chooses versions, handles dependency scopes, deals with transitive dependencies, and reports dependency failures.

---

# 1. What Is a Software Dependency?

A software dependency is another piece of software that your application needs in order to build, test, or run.

Suppose you are writing a Java application that needs to convert Java objects into JSON.

You could write all JSON parsing and serialization logic yourself.

Or you could use an existing JSON library.

If your application requires that library, then the library is a dependency.

Conceptually:

```text
Your Application
      |
      v
JSON Library
```

Your application depends on that library for some functionality.

That is why it is called a dependency.

---

# 2. Why Applications Need Dependencies

Modern applications are built from many reusable components.

It would be inefficient for every team to recreate:

* Logging systems
* HTTP clients
* JSON parsers
* Database drivers
* Testing frameworks
* Encryption libraries
* Web servers
* Dependency injection frameworks

Instead:

```text
Application
    |
    +---- Reuse trusted library
    |
    +---- Reuse framework
    |
    +---- Reuse database driver
```

This saves development time and avoids repeatedly solving the same technical problem.

---

# 3. Dependencies Are Not Automatically Bad

Beginners sometimes hear about dependency risk and conclude:

```text
Dependencies are bad.
```

That is too simplistic.

Dependencies are fundamental to modern software development.

The real engineering questions are:

```text
Do we need this dependency?

Is it maintained?

Is the version appropriate?

Is it secure?

Is it trustworthy?

Is it compatible?

Do we understand what it brings transitively?
```

Good dependency management is about controlled reuse.

---

# 4. What Is a Library?

A library is reusable code that your application calls.

For example, imagine your application needs JSON functionality.

A JSON library might provide classes and methods that you use directly.

Conceptually:

```text
Application Code
      |
      v
Calls Library API
      |
      v
Library performs task
```

Your application remains in control of the program flow.

A library gives you functionality.

---

# 5. Library Example

Suppose a JSON library offers a class conceptually like:

```java
ObjectMapper mapper = new ObjectMapper();
```

Your code decides when to create and use it.

The relationship is:

```text
Your Code
   |
   v
Library
```

This is a common dependency pattern.

---

# 6. What Is a Framework?

A framework is broader than a simple utility library.

Frameworks often provide:

* Application structure
* Lifecycle
* Configuration conventions
* Dependency injection
* Web handling
* Component management
* Runtime behavior

A useful beginner distinction is:

```text
Library:
Your code calls the library.

Framework:
The framework often calls your code.
```

This is sometimes described as inversion of control.

---

# 7. Library Versus Framework

A simple mental model:

```text
LIBRARY

Your Application
      |
      v
Library Functionality


FRAMEWORK

Framework Runtime
      |
      v
Your Application Components
```

The distinction is not always perfectly sharp, but it is useful.

Maven can manage both libraries and frameworks as dependencies.

---

# 8. What Is a JAR?

Many Java dependencies are distributed as JAR files.

JAR means:

```text
Java Archive
```

A JAR can contain:

* Compiled `.class` files
* Resources
* Metadata
* Manifest information

Conceptually:

```text
library-source
   |
   v
compile
   |
   v
classes
   |
   v
package
   |
   v
library.jar
```

Your project can then use that JAR.

---

# 9. How Developers Managed Dependencies Manually

Before dependency-management tools became common, a developer might:

1. Visit a library website.
2. Download a JAR.
3. Create a `lib` directory.
4. Copy the JAR into the project.
5. Add it to the compiler classpath.
6. Add it to the runtime classpath.
7. Repeat this for every library.

The project might become:

```text
my-app/
├── src/
├── lib/
│   ├── json-library.jar
│   ├── logging-library.jar
│   ├── database-driver.jar
│   └── testing-library.jar
└── ...
```

This works for small cases, but becomes difficult quickly.

---

# 10. Why Copying JAR Files Manually Is Problematic

There are several problems.

## Problem 1: Version Confusion

Suppose you have:

```text
json-library.jar
```

Which version is it?

Maybe:

```text
2.10
```

Maybe:

```text
2.15
```

Maybe someone replaced the file without renaming it.

Without clear metadata, reproducibility suffers.

---

# 11. Problem 2: Everyone Must Get the Same Files

Developer A may have:

```text
library 1.2
```

Developer B may have:

```text
library 1.3
```

CI may have:

```text
library 1.1
```

Now:

```text
Developer A
→ BUILD SUCCESS

Developer B
→ BUILD FAILURE

CI
→ Different behavior
```

The dependency set is not defined consistently.

---

# 12. Problem 3: Transitive Dependencies

Suppose your application directly uses:

```text
Library A
```

but Library A itself needs:

```text
Library B
Library C
```

Now you also need B and C.

Then B may require D.

Conceptually:

```text
Application
   |
   v
Library A
   |
   +---- Library B
   |        |
   |        +---- Library D
   |
   +---- Library C
```

Manual dependency management becomes a graph problem.

---

# 13. Problem 4: Updating Becomes Difficult

Suppose a security advisory requires upgrading a library.

You need to answer:

```text
Where is this JAR copied?

Which projects use it?

Which version does each project have?

What other libraries does the new version require?
```

Without structured dependency metadata, upgrades become risky.

---

# 14. Problem 5: Classpath Management

Java needs dependencies on the classpath.

With many JAR files, commands become complicated.

Conceptually:

```bash
javac -cp "lib/a.jar:lib/b.jar:lib/c.jar:..." ...
```

Then runtime requires a compatible classpath too.

Maven automates much of this.

---

# 15. Maven's Dependency Model

Instead of copying JARs into your project manually, you declare what the project needs in:

```text
pom.xml
```

Maven then:

```text
Read dependency declaration
        |
        v
Determine artifact coordinates
        |
        v
Check local repository
        |
        v
Check remote repository if needed
        |
        v
Download artifact
        |
        v
Resolve transitive dependencies
        |
        v
Build classpath
```

This is dependency management.

---

# 16. Maven Dependency Declaration

Dependencies are declared inside:

```xml
<dependencies>
```

Each dependency is represented by:

```xml
<dependency>
```

Example:

```xml
<dependencies>

    <dependency>
        <groupId>com.fasterxml.jackson.core</groupId>
        <artifactId>jackson-databind</artifactId>
        <version>2.17.2</version>
    </dependency>

</dependencies>
```

This tells Maven that the project depends on a particular artifact.

---

# 17. Dependency Coordinates

Recall Maven coordinates from Part 4.

A dependency is identified using coordinates.

The core values are:

```text
groupId
artifactId
version
```

or:

```text
GAV
```

Example:

```text
com.fasterxml.jackson.core
:
jackson-databind
:
2.17.2
```

This identifies a specific Maven artifact version.

---

# 18. `groupId` in a Dependency

Example:

```xml
<groupId>com.fasterxml.jackson.core</groupId>
```

The `groupId` identifies the dependency's group or namespace.

This is not your project's `groupId`.

Inside a dependency declaration, it belongs to the dependency.

Compare:

```xml
<groupId>com.veriqta</groupId>
```

at project level

with:

```xml
<dependency>
    <groupId>com.fasterxml.jackson.core</groupId>
</dependency>
```

The first identifies your project group.

The second identifies an external dependency group.

---

# 19. `artifactId` in a Dependency

Example:

```xml
<artifactId>jackson-databind</artifactId>
```

This identifies the specific artifact within the dependency group.

Together:

```text
com.fasterxml.jackson.core
+
jackson-databind
```

identify the library family artifact.

The version completes the identity.

---

# 20. `version` in a Dependency

Example:

```xml
<version>2.17.2</version>
```

This tells Maven which version is requested.

Without controlled dependency versions, builds can become unpredictable.

For this beginner project, declare versions explicitly.

Later you will learn how parent POMs and dependency management can centralize them.

---

# 21. Add a Real Dependency to `veriqta-maven-app`

We will add Jackson Databind so the application can convert a Java object into JSON.

Inside `pom.xml`, add:

```xml
<dependencies>

    <dependency>
        <groupId>com.fasterxml.jackson.core</groupId>
        <artifactId>jackson-databind</artifactId>
        <version>2.17.2</version>
    </dependency>

</dependencies>
```

Place this inside the root:

```xml
<project>
```

element.

A simplified POM becomes:

```xml
<project ...>

    <modelVersion>4.0.0</modelVersion>

    <groupId>com.veriqta</groupId>
    <artifactId>veriqta-maven-app</artifactId>
    <version>1.0.0-SNAPSHOT</version>

    <properties>
        <maven.compiler.release>17</maven.compiler.release>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>

    <dependencies>

        <dependency>
            <groupId>com.fasterxml.jackson.core</groupId>
            <artifactId>jackson-databind</artifactId>
            <version>2.17.2</version>
        </dependency>

    </dependencies>

</project>
```

---

# 22. Update the Application to Use the Dependency

Change your application to something like:

```java
package com.veriqta.app;

import com.fasterxml.jackson.core.JsonProcessingException;
import com.fasterxml.jackson.databind.ObjectMapper;

import java.util.LinkedHashMap;
import java.util.Map;

public class Application {

    public static void main(String[] args) throws JsonProcessingException {

        Map<String, Object> application = new LinkedHashMap<>();
        application.put("name", "VERIQTA Maven App");
        application.put("environment", "learning");
        application.put("buildTool", "Maven");

        ObjectMapper objectMapper = new ObjectMapper();

        String json = objectMapper.writeValueAsString(application);

        System.out.println(json);
    }
}
```

Now your Java source imports classes that do not come from the JDK.

They come from Jackson.

---

# 23. What the `import` Statements Mean

These lines:

```java
import com.fasterxml.jackson.core.JsonProcessingException;
import com.fasterxml.jackson.databind.ObjectMapper;
```

tell Java which classes your source intends to use.

Without the dependency available on the compile classpath, compilation would fail.

Conceptually:

```text
Application.java
     |
     +---- needs ObjectMapper
     |
     v
Jackson dependency
```

This is where Maven dependency resolution becomes useful.

---

# 24. Run `mvn compile`

Run:

```bash
mvn clean compile
```

During this build, Maven may download new artifacts.

You may see repository download messages.

This is expected.

Maven is resolving the dependency graph.

---

# 25. What Maven Does With the Dependency

At a high level:

```text
pom.xml
   |
   v
Dependency declaration
   |
   v
Maven
   |
   v
Check ~/.m2/repository
   |
   +---- Found?
   |       |
   |       v
   |      Use it
   |
   +---- Missing?
           |
           v
      Remote repository
           |
           v
        Download
           |
           v
      Cache locally
           |
           v
      Add to classpath
           |
           v
        Compile
```

This entire process happens without you manually copying JAR files into the project.

---

# 26. How Maven Locates a Dependency

Maven uses dependency coordinates.

For:

```xml
<groupId>com.fasterxml.jackson.core</groupId>
<artifactId>jackson-databind</artifactId>
<version>2.17.2</version>
```

Maven knows the identity:

```text
com.fasterxml.jackson.core:jackson-databind:2.17.2
```

It then searches configured repositories.

The process normally begins with the local repository.

---

# 27. Local Repository First

By default, Maven uses:

```text
~/.m2/repository
```

Suppose the dependency already exists there.

Maven can reuse it.

Conceptually:

```text
Need artifact
    |
    v
Local repository
    |
    +---- exists
             |
             v
            use
```

This avoids unnecessary network downloads.

---

# 28. Remote Repository If Needed

If the artifact is not locally available, Maven can contact a configured remote repository.

For many public dependencies, Maven Central is commonly involved.

Conceptually:

```text
Need artifact
    |
    v
Local repository
    |
    X
Not found
    |
    v
Remote repository
    |
    v
Download
    |
    v
Local repository
    |
    v
Build
```

This is why the first build may take longer than later builds.

---

# 29. Repository Path From Coordinates

Coordinates also map into the local repository structure.

For:

```text
groupId:
com.fasterxml.jackson.core

artifactId:
jackson-databind

version:
2.17.2
```

the path conceptually becomes:

```text
~/.m2/repository/
└── com/
    └── fasterxml/
        └── jackson/
            └── core/
                └── jackson-databind/
                    └── 2.17.2/
```

Inside that directory you may find files including:

```text
jackson-databind-2.17.2.jar
jackson-databind-2.17.2.pom
```

plus repository metadata/checksum-related files.

---

# 30. Inspect the Downloaded Dependency

After a successful build:

```bash
ls ~/.m2/repository/com/fasterxml/jackson/core/jackson-databind/2.17.2/
```

You should see the dependency artifacts.

This proves Maven did not hide the dependency somewhere mysterious.

It resolved and stored it in the local artifact repository.

---

# 31. What Happens After `mvn compile`

After dependency resolution, Maven constructs the compilation classpath.

Conceptually:

```text
JDK classes
     +
Project dependencies
     +
Project source
     |
     v
Java compilation
```

Your source can now compile because:

```text
ObjectMapper
```

is available from the resolved Jackson JAR.

The result is still:

```text
target/classes/com/veriqta/app/Application.class
```

But the class now references external library classes.

---

# 32. Compilation Does Not Copy Every Dependency Into `target/classes`

A common beginner assumption is:

```text
Maven downloads the JAR and copies it into target/classes.
```

That is not how normal dependency resolution works.

`target/classes` contains your compiled classes and processed resources.

Dependency JARs normally remain in the local Maven repository and are placed on the relevant build classpath.

Conceptually:

```text
target/classes
→ your project classes/resources

~/.m2/repository
→ dependency artifacts
```

---

# 33. Running the Application Now Needs Dependencies Too

Earlier, you ran:

```bash
java -cp target/classes com.veriqta.app.Application
```

That worked because your application used only JDK classes.

Now the application depends on Jackson.

If you run only:

```bash
java -cp target/classes com.veriqta.app.Application
```

Java may fail because the Jackson classes are not on the runtime classpath.

You need both:

```text
Your classes
+
Dependency classes
```

This demonstrates an important principle:

```text
Compile dependency
≠ dependency automatically embedded in your output
```

Packaging dependencies into executable artifacts is a separate topic.

---

# 34. Dependency Classpath Mental Model

During compilation:

```text
src/main/java
     |
     +---- Jackson JAR
     |
     v
Compiler
```

During runtime:

```text
target/classes
     |
     +---- Jackson JAR
     |
     v
JVM
```

The dependency must be available in both contexts when required.

Maven can manage the build classpaths automatically.

---

# 35. Direct Dependencies

A direct dependency is one that your project explicitly declares.

For example:

```xml
<dependency>
    <groupId>com.fasterxml.jackson.core</groupId>
    <artifactId>jackson-databind</artifactId>
    <version>2.17.2</version>
</dependency>
```

This is a direct dependency because your POM explicitly contains it.

Think:

```text
Your Project
    |
    v
jackson-databind
```

---

# 36. Transitive Dependencies

A transitive dependency is a dependency required by one of your dependencies.

Suppose:

```text
Your Project
    |
    v
Dependency A
    |
    +---- Dependency B
    |
    +---- Dependency C
```

You declared A.

You did not explicitly declare B or C.

Maven can still resolve them because A declares them in its own POM.

B and C are transitive dependencies of your project.

---

# 37. Jackson Example

When you declare:

```text
jackson-databind
```

it depends on other Jackson components.

Conceptually:

```text
veriqta-maven-app
        |
        v
jackson-databind
        |
        +---- jackson-annotations
        |
        +---- jackson-core
```

You declared only:

```text
jackson-databind
```

but Maven may resolve the other artifacts transitively.

This is one of Maven's major benefits.

---

# 38. Why Transitive Dependencies Matter

Without transitive resolution, you would need to understand and manually declare every library required by every library.

Imagine:

```text
Application
   |
   +---- Library A
   |       |
   |       +---- B
   |       |    |
   |       |    +---- D
   |       |
   |       +---- C
   |
   +---- Library E
           |
           +---- F
```

The dependency graph can grow quickly.

Maven builds and resolves this graph for you.

---

# 39. Dependency Tree

Maven can show you the dependency graph.

Run:

```bash
mvn dependency:tree
```

This is extremely useful.

It tells you which dependencies are:

* Direct
* Transitive
* Nested
* Potentially omitted because of conflicts

---

# 40. Understanding `mvn dependency:tree`

The command:

```bash
mvn dependency:tree
```

uses the Maven Dependency Plugin.

Break it down:

```text
dependency
→ plugin prefix

tree
→ goal
```

This is direct plugin-goal syntax.

It does not mean:

```text
Run lifecycle through a phase called dependency.
```

There is no such default lifecycle phase here.

---

# 41. Example Dependency Tree

You may see output conceptually like:

```text
com.veriqta:veriqta-maven-app:jar:1.0.0-SNAPSHOT
\- com.fasterxml.jackson.core:jackson-databind:jar:2.17.2:compile
   +- com.fasterxml.jackson.core:jackson-annotations:jar:2.17.2:compile
   \- com.fasterxml.jackson.core:jackson-core:jar:2.17.2:compile
```

Read this as:

```text
Your project
   |
   v
jackson-databind
   |
   +---- jackson-annotations
   |
   +---- jackson-core
```

# 42. Read the Coordinate Format in the Tree

You may see entries like:

```text
groupId:artifactId:type:version:scope
```

For example:

```text

```

Break it down:


Dependency-tree output exposes a lot of useful information.

```bash
mvn dependency:list
```

# 45. What Is Dependency Scope?

Not every dependency is needed at every stage.

For example:

```text
A testing library
```

should generally not become a normal production runtime dependency.

A database driver may be needed at runtime.

An API supplied by an application server may be needed during compilation but provided by the runtime environment.

Maven scopes express where dependencies are intended to participate.

---

# 46. Maven Dependency Scopes

Important scopes include:

```text
compile
provided
runtime
test
system
import
```

Each scope affects:

* Which classpaths include the dependency
* Whether it is transitive
* Whether it participates in packaging/runtime expectations

These distinctions are essential.

---

# 47. `compile` Scope

`compile` is the default dependency scope.

If you omit:

```xml
<scope>
```

Maven normally treats the dependency as `compile`.

Example:

```xml
<dependency>
    <groupId>com.fasterxml.jackson.core</groupId>
    <artifactId>jackson-databind</artifactId>
    <version>2.17.2</version>
</dependency>
```

is effectively:

```xml
<dependency>
    <groupId>com.fasterxml.jackson.core</groupId>
    <artifactId>jackson-databind</artifactId>
    <version>2.17.2</version>
    <scope>compile</scope>
</dependency>
```

---

# 48. When `compile` Scope Is Appropriate

Use compile scope when the dependency is required by main application code and expected as part of the application's normal dependency model.

Examples might include:

* JSON libraries
* Utility libraries
* Core framework components
* API client libraries

Conceptually:

```text
Compile
→ needed

Test
→ needed

Runtime
→ needed
```

Compile scope is broadly available.

---

# 49. `provided` Scope

A `provided` dependency is needed to compile and test your project, but the runtime environment is expected to supply it.

Example:

```xml
<scope>provided</scope>
```

Conceptually:

```text
Compile
→ yes

Test
→ generally yes

Runtime packaging expectation
→ external environment provides it
```

A classic example is a servlet API when deploying to a compatible servlet container.

The application compiles against the API.

The container provides the implementation at runtime.

---

# 50. Why `provided` Exists

Imagine:

```text
Application
   |
   v
Servlet API
```

During development, the compiler needs those classes.

But when deployed to an application server:

```text
Application Server
    |
    +---- already provides Servlet API
```

Bundling another copy can be unnecessary or problematic.

So:

```text
provided
```

communicates:

```text
I need this to build, but the target environment provides it.
```

---

# 51. `runtime` Scope

A runtime dependency is not required for compiling the main application source, but is needed when the application runs.

Example:

```xml
<scope>runtime</scope>
```

A common conceptual example is a database driver when application code interacts through standard interfaces and the concrete driver is needed only at runtime.

Think:

```text
Compile
→ not necessarily needed

Runtime
→ needed
```

---

# 52. Runtime Example

Imagine application source depends on an interface:

```text
JDBC API
```

but the actual database connection requires a concrete PostgreSQL driver at runtime.

Conceptually:

```text
Compile:
Java interfaces available

Runtime:
PostgreSQL driver required
```

That driver may use `runtime` scope depending on the project design.

---

# 53. `test` Scope

A test-scoped dependency is needed only for test compilation and execution.

Example:

```xml
<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>5.10.3</version>
    <scope>test</scope>
</dependency>
```

Conceptually:

```text
Main compile
→ not needed

Main runtime
→ not needed

Test compile
→ needed

Test execution
→ needed
```

This is exactly what you want for a testing framework.

---

# 54. Why Test Dependencies Should Be Scoped

Suppose you use JUnit only to test your application.

Production does not need JUnit to run.

Without proper scope, you may unnecessarily expose testing dependencies to the main dependency graph.

Using:

```xml
<scope>test</scope>
```

communicates intent clearly.

---

# 55. `system` Scope

`system` scope points Maven to a dependency available through a local filesystem path rather than normal repository resolution.

Example conceptually:

```xml
<scope>system</scope>
<systemPath>/some/local/path/library.jar</systemPath>
```

This is generally discouraged for normal dependency management.

Why?

Because it breaks portability.

---

# 56. Why `system` Scope Is Problematic

Suppose your POM points to:

```text
/Users/ann/libs/company-library.jar
```

Your machine works.

CI runs on Linux:

```text
/home/runner/...
```

The file does not exist.

Build fails.

You have recreated the manual-JAR problem Maven was supposed to solve.

For normal reusable builds, repository-managed dependencies are preferable.

---

# 57. When `system` Might Appear

You may encounter it in:

* Legacy projects
* Vendor-specific local JAR situations
* Unusual closed-source dependencies
* Old enterprise builds

You should recognize it, but do not choose it casually.

A better long-term solution is often to place the artifact in an appropriate Maven repository.

---

# 58. `import` Scope

`import` is special.

It is not used like normal runtime or compile dependencies.

It is primarily used with:

```text
type = pom
```

inside:

```xml
<dependencyManagement>
```

to import dependency version management from a BOM.

BOM means:

```text
Bill of Materials
```

This will make much more sense in Part 14 when you learn dependency management.

For now:

```text
import

```

not:

```text

```

# 63. What Is an Optional Dependency?

A dependency can be marked:

```xml
<optional>true</optional>
```

Example:

```xml
<dependency>
    <groupId>com.example</groupId>
    <artifactId>feature-library</artifactId>
    <version>1.0.0</version>
    <optional>true</optional>
</dependency>
```

Optional means:

```text
This project uses the dependency, but consumers of this project should not automatically inherit it transitively.
```

This primarily affects downstream projects.

---

# 64. Optional Dependency Mental Model

Suppose:

```text
Project A
   |
   +---- Dependency X (optional)
```

Project B depends on A:

```text
Project B
   |
   v
Project A
```

Without optional behavior, X might normally appear transitively.

With:

```text
optional = true
```

Maven does not automatically propagate X to B as a normal transitive dependency.

Conceptually:

```text
B
|
v
A
|
X

X stops here unless B declares it itself.
```

---

# 65. Why Optional Dependencies Exist

A library may support an optional integration.

For example:

```text
Library A
   |
   +---- Core functionality
   |
   +---- Optional Metrics Library
```

Not every consumer needs metrics support.

Making that dependency optional prevents every consumer from automatically inheriting it.

This keeps dependency graphs more intentional.

---

# 66. Optional Does Not Mean Maven Ignores It in the Current Project

Important:

```text
optional
```

does not mean:

```text
Do not use this dependency in this project.
```

The declaring project still uses the dependency according to its scope.

Optional mainly controls transitive propagation to consumers.

---

# 67. What Is an Exclusion?

Sometimes a direct dependency brings a transitive dependency you do not want.

You can exclude it.

Example:

```xml
<dependency>
    <groupId>com.example</groupId>
    <artifactId>library-a</artifactId>
    <version>1.0.0</version>

    <exclusions>
        <exclusion>
            <groupId>com.example</groupId>
            <artifactId>library-b</artifactId>
        </exclusion>
    </exclusions>

</dependency>
```

This says:

```text
Use Library A,
but do not bring Library B through this dependency path.
```

---

# 68. Why Exclusions Exist

Imagine:

```text
Application
    |
    v
Library A
    |
    v
Logging Library X
```

But your organization requires:

```text
Logging Library Y
```

You may need to exclude X from A's transitive dependency graph and explicitly declare the desired solution.

Do this only when you understand the consequence.

---

# 69. Exclusion Mental Model

Before:

```text
Application
   |
   v
A
   |
   v
B
```

After exclusion:

```text
Application
   |
   v
A

B removed from this path
```

If another dependency path still introduces B, it may still remain in the final graph.

An exclusion applies to the specified dependency path.

---

# 70. Why Blind Exclusions Are Dangerous

A beginner may see an unwanted dependency and remove it without asking why the parent library needs it.

Then runtime may fail.

Use this reasoning:

```text
Why is dependency here?
      |
      v
Which parent introduces it?
      |
      v
Is it actually unused?
      |
      v
Is there a safer replacement?
      |
      v
Can parent library function without it?
      |
      v
Exclude only with evidence
```

# 71. Version Conflicts

Now consider a more difficult dependency graph.

Suppose:

```text
Your Project
   |
   +---- Library A
   |       |
   |       +---- Common Library 1.0
   |
   +---- Library B
           |
           +---- Common Library 2.0
```

Your application cannot normally use two incompatible versions of the same artifact coordinate in the same effective dependency classpath in the ordinary way.

Maven must choose.

This is dependency mediation.

---

# 72. Dependency Mediation

Dependency mediation is Maven's process for choosing which dependency version wins when different paths request different versions of the same artifact.

A core Maven rule is often described as:

```text
nearest definition
```

or nearest dependency path.

The dependency version closest to your project in the dependency tree normally wins.

---

# 73. Nearest-Definition Behavior

Consider:

```text
Application
   |
   +---- A
   |      |
   |      +---- X 1.0
   |
   +---- B
          |
          +---- C
                 |
                 +---- X 2.0
```

Path to X 1.0:

```text
Application → A → X
```

Path to X 2.0:

```text
Application → B → C → X
```

X 1.0 is nearer.

Maven will generally select:

```text
X 1.0
```

for the resolved dependency graph.

---

# 74. Same Depth Conflicts

Suppose:

```text
Application
   |
   +---- A → X 1.0
   |
   +---- B → X 2.0
```

Both X versions occur at the same depth.

Maven's dependency mediation then uses declaration order in the relevant dependency graph context, with the first encountered declaration generally winning.

This is one reason dependency order can occasionally matter in conflict resolution.

The safest approach is often not to rely on accidental ordering.

Explicitly manage important versions.

---

# 75. Direct Dependency Usually Wins Over Deeper Transitive Version

Suppose:

```text
Application
   |
   +---- X 2.0
   |
   +---- A
          |
          +---- X 1.0
```

You directly declared X 2.0.

That direct dependency is nearer than the transitive X 1.0.

So Maven generally resolves:

```text
X 2.0
```

This is a common way teams intentionally override transitive versions.

Later, dependency management provides a cleaner centralized method.

---

# 76. Inspect Version Mediation With `dependency:tree`

Run:

```bash
mvn dependency:tree
```

When conflicts exist, Maven can display clues such as versions being omitted for conflict.

You may see conceptual output like:

```text
+- library-a:1.0
|  \- common-lib:1.0
\- library-b:2.0
   \- common-lib:2.0 (omitted for conflict with 1.0)
```

The exact wording can vary.

This tells you Maven found multiple candidate versions and selected one.

---

# 77. Dependency Conflict Does Not Automatically Mean Build Failure

Maven may successfully mediate a version.

But the selected version may still be incompatible at runtime.

For example:

```text
Library B
expects method introduced in X 2.0

Maven selects X 1.0

Build succeeds

Runtime:
NoSuchMethodError
```

This is a classic dependency compatibility problem.

Dependency resolution success does not guarantee semantic compatibility.

---

# 78. Runtime Errors From Dependency Conflicts

You may encounter errors such as:

```text
NoSuchMethodError
ClassNotFoundException
NoClassDefFoundError
```

These can be caused by dependency/classpath issues.

Not every occurrence is Maven's fault, but dependency graphs are an important place to investigate.

Start with:

```bash
mvn dependency:tree
```

Ask:

```text
Which versions are present?

Which version won?

Who introduced it?

Was another version omitted?
```

# 79. Missing Dependencies

A missing dependency occurs when code needs a library that is not available through the project's effective dependency classpath.

Example:

```java
import com.example.Widget;
```

but no dependency provides:

```text
com.example.Widget
```

Compilation may report errors such as:

```text
package com.example does not exist
```

or:

```text
cannot find symbol
```

---

# 80. Missing Dependency Troubleshooting

Use this sequence:

```text
Compiler cannot find class
        |
        v
Which package/class?
        |
        v
Which artifact should provide it?
        |
        v
Is dependency declared?
        |
        v
Correct scope?
        |
        v
Dependency resolved?
        |
        v
Check dependency tree
        |
        v
Fix declaration/version/scope
```

Do not automatically add random JARs until the compiler stops complaining.

Understand which artifact owns the missing class.

# 81. Unresolved Artifact

An unresolved artifact is different.

Your POM may correctly declare:

```text
groupId
artifactId
version
```

but Maven cannot obtain the artifact.

The error may mention something like:

```text
Could not find artifact ...
```

or:

```text
Could not resolve dependencies
```

This is not a Java syntax error.

It is dependency resolution failure.

---

# 82. Common Causes of Unresolved Artifacts

Possible causes include:

* Incorrect `groupId`
* Incorrect `artifactId`
* Incorrect version
* Artifact does not exist
* Repository not configured
* Repository unavailable
* Network failure
* Proxy issue
* Authentication failure
* TLS/certificate issue
* Maven running offline
* Corrupted local metadata/cache
* Private artifact unavailable to the current environment

---

# 83. Example: Wrong Version

Suppose you declare:

```xml
<version>999.999.999</version>
```

for a library version that does not exist.

Maven may attempt to locate:

```text
group:artifact:999.999.999
```

and fail.

The Java code may be perfectly valid.

The POM XML may be perfectly valid.

The failure is:

```text
Artifact resolution
```

This distinction matters.

---

# 84. Example: Wrong Artifact ID

Suppose the real artifact is:

```text
jackson-databind
```

but you write:

```text
jackson-databindd
```

Maven treats that as a different coordinate.

It will try to resolve exactly what you asked for.

Dependency systems are precise.

A typo creates a new nonexistent identity.

---

# 85. Example: Artifact Exists Only in a Private Repository

Suppose:

```text
com.company:internal-library:4.2.0
```

exists only in the company's artifact repository.

Your developer machine has the correct `settings.xml`.

CI does not.

Result:

```text
Developer laptop
→ dependency resolves

CI
→ Could not find artifact
```

The POM may be correct.

The environment differs.

This is why Part 2 and Part 4 matter.

# 88. `401 Unauthorized`

If Maven receives:

```text

```

from a repository, authentication is likely required or credentials are invalid.

Investigate:

* Server ID
* `settings.xml`
* Credential source
* Repository URL
* CI secret configuration

# 89. `403 Forbidden`

A:

```text

```

generally means the server understood the request but refused it.

Possible causes:

* User lacks permission
* Repository policy blocks access
* Artifact path not allowed
* Deployment permission missing

Again, this is not a Java compilation problem.

# 90. `Unknown host`

This points toward DNS or network name resolution.

Ask:

```text
Can the machine resolve the repository hostname?

Does the CI runner have outbound network access?

Is a proxy required?
```

Do not edit Java source.

# 91. Timeout

A connection timeout can indicate:

* Network connectivity problem
* Firewall
* Proxy
* Repository outage
* Slow/unreachable service

Dependency resolution is partly a network operation.

Build failures can therefore originate outside the project itself.

# 92. Local Cache Problems

Occasionally a dependency artifact or metadata in:

```text
~/.m2/repository
```

may be incomplete or corrupted.

But do not respond by deleting the entire local repository every time.

First identify the specific artifact.

For example, if the problem concerns:

```text
com/example/library/1.0.0
```

investigate that artifact path.

Targeted cleanup is safer and faster than wiping everything.

---

# 93. Maven May Cache Failed Resolution Information

Maven can record metadata indicating that a resolution attempt failed and should not immediately be retried until an update interval passes.

This is one reason a corrected repository situation may still appear stale for a while.

You may encounter:

```bash
mvn -U ...
```

which requests dependency/plugin update checks.

Use it when you understand why a fresh remote check is needed.

Do not use `-U` blindly for unrelated compilation errors.

---

# 94. Dependency Scope Can Cause "Missing" Classes

Suppose a library is declared:

```xml
<scope>test</scope>
```

but your main application source imports it.

Then main compilation may fail.

Why?

Because test-scope dependencies are not intended for the main compile classpath.

The artifact may exist locally.

The coordinate may be correct.

The problem is the scope.

---

# 95. Scope Troubleshooting Model

If a class is missing:

```text
Dependency declared?
     |
     v
Dependency resolved?
     |
     v
Correct scope for this build stage?
     |
     v
Correct classpath?
```

Scope errors can look like missing dependency errors.

# 96. Transitive Dependency Security

Transitive dependencies matter for security because you may inherit software you never explicitly declared.

Suppose your POM has:

```text
10 direct dependencies
```

but the resolved tree contains:

```text
80 total artifacts
```

Your actual dependency surface is much larger than the visible POM.

This is why:

```bash
mvn dependency:tree
```

matters for security and supply-chain review.

---

# 97. Dependency Tree as a Supply-Chain Tool

The tree helps answer:

```text
What software does this build actually bring in?

Which dependency introduced this library?

Why is this vulnerable component present?

Can we upgrade or exclude it?
```

Dependency management is therefore both a build concern and a security concern.

---

# 98. Do Not Add Random Repositories to Fix Missing Dependencies

A dangerous beginner habit is:

```text
Artifact not found
→ search web
→ add random repository URL
```

This can expose the build to untrusted artifact sources.

A better process:

```text
Verify coordinate
→ Verify expected repository
→ Check official project source
→ Check organization policy
→ Configure only trusted repository
```

Repositories are part of the software supply chain.

---

# 99. Do Not Use Dynamic or Uncontrolled Versions Casually

Stable builds should make dependency versions intentional.

Avoid dependency versioning practices that make the build unpredictably resolve different artifacts over time.

A reproducible build should be able to answer:

```text
Which exact dependency version did we use?
```

Explicit, controlled version management supports that goal.

# 121. Troubleshooting Scenario: Dependency Appears Unexpectedly

## Symptom

You did not declare a library, but it appears in the build.

## Investigate

Run:

```bash
mvn dependency:tree
```

Trace upward from the unexpected library.

You should find the direct dependency that introduced it.

## Possible Actions

* Keep it if required
* Upgrade the parent dependency
* Exclude it if safe
* Replace the parent dependency
* Manage its version

Do not delete files from `.m2` and assume the graph changed.

The POM model controls the graph.

# 122. Troubleshooting Scenario: Test Library Visible in Production Code

## Symptom

Production source depends on a library declared with:

```xml
<scope>test</scope>
```

Main compilation fails.

## Cause

Test-scope dependency is not intended for the main compile classpath.

## Fix

Ask:

```text
Should production code really depend on this library?
```

If yes, use an appropriate production dependency and scope.

If no, move that code into tests.

Do not change the scope simply to silence the compiler without checking design intent.

---

# 123. Troubleshooting Scenario: Provided Dependency Missing at Runtime

## Symptom

Application compiles but fails at runtime because a class is missing.

Dependency uses:

```xml
<scope>provided</scope>
```

## Cause

Maven assumed the runtime environment would provide the dependency.

The environment did not.

## Investigate

Ask:

```text
What runtime was expected?

Does it actually provide this API/library?

Is the scope correct for our deployment model?
```

This is an architecture issue, not simply a Maven syntax issue.

---

# 124. Troubleshooting Scenario: System Dependency Breaks CI

## Symptom

Local build works.

CI fails because a local JAR path does not exist.

## Cause

`system` scope ties the build to a machine-specific path.

## Fix

Prefer publishing the artifact into a trusted Maven repository and declaring normal coordinates.

This restores build portability.

# 128. Avoid Dependency Hoarding

Do not add a library merely to use one trivial method if the functionality is simple enough to implement safely with the JDK.

Every dependency introduces:

* Maintenance responsibility
* Version-management work
* Supply-chain exposure
* Compatibility risk
* Transitive dependencies
* Potential vulnerability surface

This does not mean avoid libraries.

It means use them intentionally.

---

# 129. Keep Direct Dependencies Explicit

If your production source directly imports classes from a transitive dependency, consider declaring that artifact directly instead of relying accidentally on another library to bring it in.

Why?

Because:

```text
Your source directly depends on it.
```

The POM should clearly express important direct architectural dependencies.

If the upstream dependency stops bringing it transitively, your build should not unexpectedly break.

---

# 130. Example of Accidental Transitive Dependence

Suppose:

```text
Application
→ Library A
→ Library B
```

Your code starts importing classes from B directly.

But B is not declared in your POM.

Now your application implicitly relies on A continuing to depend on B.

If A later removes B:

```text
Application compile
→ failure
```

Better:

```text
Application
→ A
→ B directly
```

if application code truly depends on B.

# 131. Dependency Versioning and Production Reproducibility

A build should be able to answer:

```text
Exactly which versions were resolved?
```

This matters when:

* Reproducing a production incident
* Rolling back
* Investigating vulnerabilities
* Auditing software supply chain
* Comparing local and CI builds

The dependency tree is part of the build evidence.

# 132. CI Dependency Caching

In CI/CD systems, Maven dependencies may be cached to improve build speed.

Conceptually:

```text
First CI build
   |
   v
Download dependencies
   |
   v
Cache Maven repository data

Later build
   |
   v
Reuse cache
```

Caching improves performance.

But cache strategy must not create stale or unsafe dependency behavior.

CI should still respect the project's declared versions and Maven resolution rules.

---

# 133. Maven Does Not Mean "Always Download Latest"

For a fixed dependency:

```xml
<version>2.17.2</version>
```

Maven is resolving that requested version.

It is not supposed to silently replace it with:

```text
2.18.0
```

simply because a newer version exists.

This is important for build stability.

Upgrades should be intentional.

---

# 134. Snapshot Dependency Awareness

Dependencies themselves can use SNAPSHOT versions.

Example:

```xml
<version>2.0.0-SNAPSHOT</version>
```

That means the dependency is a changing development version.

Using snapshots can be appropriate in development environments, but they reduce immutability.

Production releases generally benefit from fixed artifact versions.

# 141. Knowledge Check Answers

## 1. What is a software dependency?

Another software component that the project needs to build, test, or run.

## 2. Why use dependencies?

To reuse existing functionality instead of rebuilding everything from scratch.

## 3. What is a library?

Reusable code that your application calls.

## 4. What is a framework?

A broader application structure/runtime that often manages or calls application components.

## 5. What is a JAR?

A Java Archive containing compiled classes, resources, and metadata.

## 6. Why not copy JARs manually?

It creates version confusion, classpath problems, weak reproducibility, and difficult transitive dependency management.

## 7. Where are dependencies declared?

Inside:

```xml
<dependencies>
```

in `pom.xml`.

## 8. Core dependency coordinates?

```text
groupId
artifactId
version
```

## 9. `groupId`?

The broader dependency namespace/group.

## 10. `artifactId`?

The specific artifact within that group.

## 11. `version`?

The requested artifact version.

## 12. What does Maven check first?

The local Maven repository.

## 13. Default local repository?

```text
~/.m2/repository
```

## 14. Why download dependency POMs?

Because Maven needs metadata, including transitive dependency information.

## 15. Direct dependency?

A dependency explicitly declared by your project.

## 16. Transitive dependency?

A dependency introduced through another dependency.

## 17. `dependency:tree`?

It shows the hierarchical dependency graph and transitive relationships.

## 18. `dependency:list`?

It lists the resolved dependency artifacts.

## 19. Dependency scope?

A rule describing where a dependency participates in build and runtime classpaths.

## 20. Default scope?

```text
compile
```

## 21. Compile scope?

For normal application dependencies needed for main compilation and runtime.

## 22. Provided scope?

Needed to compile/test, but expected to be supplied by the runtime environment.

## 23. Runtime scope?

Needed at runtime but not required for normal main-source compilation.

## 24. Test scope?

Used only for test compilation and execution.

## 25. Why avoid system scope?

It depends on machine-specific filesystem paths and harms portability.

## 26. Import scope?

Used with POM-type dependencies in dependency management to import BOM-managed versions.

## 27. Optional dependency?

It is used by the declaring project but does not automatically propagate transitively to consumers.

## 28. Can the current project use it?

Yes.

## 29. Exclusion?

It removes a specified transitive dependency from a particular dependency path.

## 30. Why dangerous?

The parent dependency may genuinely need the excluded component.

## 31. Version conflict?

Different dependency paths request different versions of the same artifact.

## 32. Dependency mediation?

Maven's process for choosing which version is used.

## 33. Nearest definition?

The dependency version closest to the root project generally wins.

## 34. Direct 2.0 versus transitive 1.0?

The directly declared 2.0 is normally nearer and wins.

## 35. Can runtime still fail?

Yes. The selected version may not satisfy every dependency's binary/API expectations.

## 36. `Could not find artifact`?

Maven could not resolve the requested artifact coordinate from available repositories.

## 37. Missing declaration versus unresolved artifact?

Missing declaration means the project did not include the required dependency.

Unresolved artifact means it was declared but Maven could not obtain it.

## 38. 401?

Missing or invalid authentication credentials.

## 39. 403?

The request was understood but access is forbidden, often because of permissions or repository policy.

## 40. Why inspect the tree for `NoSuchMethodError`?

Because conflicting dependency versions can cause runtime binary incompatibility.

## 41. Why test scope?

Testing libraries should not normally become production dependencies.

## 42. Why provided runtime problems?

Because Maven assumes the runtime environment supplies that dependency.

If it does not, required classes may be missing.

## 43. Why more resolved dependencies than POM blocks?

Because direct dependencies bring transitive dependencies.

## 44. Why supply-chain concern?

Every transitive artifact expands the software components the build trusts and ships or relies on.

## 45. Why controlled versions?

They support reproducibility, auditing, compatibility, security review, and predictable builds.
