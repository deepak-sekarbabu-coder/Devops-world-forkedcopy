# 1. Start With the Most Important Idea

A common beginner assumption is:

```text
mvn compile
```

means:

```text
Run the Maven compile command.
```

That description is understandable, but technically incomplete.

`compile` is not simply an independent command.

It is a phase in Maven's default build lifecycle.

Similarly:

```bash
mvn test
```

asks Maven to execute the default lifecycle through the `test` phase.

And:

```bash
mvn package
```

asks Maven to execute the default lifecycle through the `package` phase.

This distinction explains much of Maven's behavior.

---

# 2. The Beginner Maven Build Mental Model

Think of a Maven build as a sequence of checkpoints.

For example:

```text
Start
 |
 v
validate
 |
 v
compile
 |
 v
test
 |
 v
package
 |
 v
verify
 |
 v
install
 |
 v
deploy
```

If you ask Maven to reach:

```text
compile
```

Maven processes the lifecycle up to that point.

If you ask Maven to reach:

```text
test
```

Maven processes everything required through `test`.

If you ask Maven to reach:

```text
package
```

Maven processes everything required through `package`.

This is why Maven commands often perform more work than the phase name alone appears to suggest.

# 3. What Happens When `mvn` Runs?

Suppose you are inside:

```text
veriqta-maven-app/
```

and run:

```bash
mvn package
```

At a high level, several things happen.

```text
Terminal
   |
   v
mvn command
   |
   v
Maven starts
   |
   v
Maven determines its environment
   |
   v
Maven locates the project
   |
   v
Maven reads pom.xml
   |
   v
Maven builds the effective project model
   |
   v
Maven interprets the requested phase/goal
   |
   v

   |
   v
Maven resolves required plugins/dependencies
   |
   v

   |
   v
Maven reports success or failure
```

There are many implementation details beneath this, but this is the correct beginner mental model.

# 4. Maven Starts With the CLI

CLI means:

```text
Command-Line Interface
```

When you type:

```bash
mvn package
```

you are using Maven's command-line interface.

The executable is:

```text
mvn
```

The argument:

```text
package
```

tells Maven what you want executed.

Maven CLI commands can contain:

* Lifecycle phases
* Plugin goals
* Options
* Properties
* Profiles
* Multiple execution targets

You will gradually learn each form.

---

# 5. Basic Maven CLI Syntax

One of the simplest forms is:

```bash
mvn <phase>
```

Examples:

```bash
mvn validate
```

```bash
mvn compile
```

```bash
mvn test
```

```bash
mvn package
```

```bash
mvn verify
```

```bash
mvn install
```

Another important form is:

```bash
mvn <plugin-prefix>:<goal>
```

Example:

```bash
mvn help:effective-pom
```

Here:

```text
help
```

identifies the Maven Help Plugin through its prefix.

And:

```text
effective-pom
```

is a goal provided by that plugin.

These two command styles represent different concepts.

---

# 6. Phase Syntax

The general pattern is:

```bash
mvn <phase>
```

For example:

```bash
mvn compile
```

means:

```text
Execute Maven's default lifecycle through the compile phase.
```

Similarly:

```bash
mvn package
```

means:

```text
Execute Maven's default lifecycle through the package phase.
```

The word:

```text
through
```

is important.

Maven does not normally jump directly to `package` while ignoring everything before it.

---

# 7. Plugin Goal Syntax

The common shorthand syntax is:

```bash
mvn <plugin-prefix>:<goal>
```

Example:

```bash
mvn help:effective-pom
```

Break it down:

```text
mvn
|
+-- help
|    |
|    +-- plugin prefix
|
+-- effective-pom
     |
     +-- goal
```

Conceptually:

```text
Maven
→ Help Plugin
→ effective-pom goal
```

You already used this in Part 4.

---

# 8. What Is a Maven Plugin?

Maven itself coordinates the build.

Much of the actual work is performed by plugins.

Examples of build work include:

* Compiling Java
* Running tests
* Creating JAR files
* Copying resources
* Installing artifacts
* Deploying artifacts
* Cleaning generated files

Think:

```text
Maven
   |
   v
Coordinates build
   |
   v
Plugins
   |
   v
Perform specific work
```

A plugin can provide one or more goals.

---

# 9. What Is a Goal?

A goal is a specific unit of work provided by a Maven plugin.

Examples include conceptual tasks such as:

```text
Compile Java source
Run tests
Create a JAR
Delete build output
Install an artifact
```

A plugin can contain multiple goals.

Think:

```text
Plugin
 |
 +-- Goal A
 +-- Goal B
 +-- Goal C
```

For example, a compiler-related plugin can provide compilation goals.

A clean-related plugin provides cleaning functionality.

A JAR-related plugin provides JAR-building functionality.

---

# 10. Phase Versus Goal

This distinction is essential.

A phase is:

```text
A stage in a Maven lifecycle.
```

A goal is:

```text
A specific task performed by a plugin.
```

Think:

```text
PHASE
=
Where are we in the build process?

GOAL
=
What actual task should a plugin perform?
```

Example:

```text
compile phase
        |
        v
Compiler plugin goal
        |
        v
Java source is compiled
```

The phase provides the position in the build.

The plugin goal performs the work.

---

# 11. A Real-World Analogy

Imagine building a house.

The project has stages:

```text
Foundation
→ Framing
→ Electrical
→ Plumbing
→ Inspection
→ Completion
```

Those are similar to phases.

Within a stage, workers perform specific tasks.

For example:

```text
Electrical stage
    |
    +-- Install wiring
    +-- Install outlets
    +-- Install panel
```

Those individual tasks are closer to goals.

Maven works similarly:

```text
Build Lifecycle
    |
    +-- Phase
          |
          +-- Plugin Goal
          +-- Plugin Goal
```

A phase organizes work.

Goals perform work.

---

# 12. A Phase Does Not Perform Work by Itself

This is an important technical point.

A lifecycle phase is essentially a named stage.

Actual work occurs when plugin goals are bound to phases.

Think:

```text
Phase
 |
 v
Bound plugin goal
 |
 v
Actual work
```

For example:

```text
compile phase
 |
 v
compiler plugin compile goal
 |
 v
.class files
```

Without goals bound to phases, a phase itself is just a point in the lifecycle.

---

# 13. What Does "Bound to a Phase" Mean?

You will frequently hear:

```text
This goal is bound to the compile phase.
```

That means Maven associates the plugin goal with that lifecycle stage.

When execution reaches the phase, Maven runs the bound goal.

Conceptually:

```text
compile
   |
   +-- compiler:compile
```

Another phase may have:

```text
test
   |
   +-- surefire:test
```

And:

```text
package
   |
   +-- jar:jar
```

The exact bindings depend partly on the project's packaging and configuration.

---

# 14. What Is a Lifecycle?

A lifecycle is an ordered sequence of phases representing a broader build process.

Think:

```text
Lifecycle
 |
 +-- Phase 1
 |
 +-- Phase 2
 |
 +-- Phase 3
 |
 +-- Phase 4
```

The phases have a defined order.

Maven uses this order to determine what should happen before reaching the phase you requested.

---

# 15. Maven Has Three Built-In Lifecycles

Maven defines three built-in build lifecycles:

```text
clean
default
site
```

They serve different purposes.

```text
clean
→ remove output from previous builds

default
→ build, test, package, verify, install, deploy the project

site
→ generate project documentation/site information
```

Do not confuse lifecycle names with individual phases inside those lifecycles.

---

# 16. The Clean Lifecycle

The clean lifecycle exists to clean output created by previous builds.

Its phases are:

```text
pre-clean
clean
post-clean
```

The most commonly used phase is:

```text
clean
```

You normally run:

```bash
mvn clean
```

---

# 17. What Does `mvn clean` Do?

In a standard Maven project, the clean process normally removes the build directory:

```text
target/
```

Suppose your project contains:

```text
veriqta-maven-app/
├── pom.xml
├── src/
└── target/
    ├── classes/
    ├── test-classes/
    └── veriqta-maven-app-1.0.0.jar
```

Run:

```bash
mvn clean
```

The generated build output under `target` is removed.

Your source remains:

```text
veriqta-maven-app/
├── pom.xml
└── src/
```

Maven is removing generated build output, not deleting your source code.

---

# 18. Why Clean Builds Matter

Suppose an old `.class` file remains in `target`.

You change or remove the corresponding source.

If stale build output remains, troubleshooting can become confusing.

A clean build starts by removing previous generated output.

This is why you often see:

```bash
mvn clean package
```

or:

```bash
mvn clean verify
```

in local development and CI/CD systems.

---

# 19. Clean Lifecycle Mental Model

```text
Old Build Output
       |
       v
    pre-clean
       |
       v
      clean
       |
       v
   post-clean
       |
       v
Clean Build Workspace
```

Most beginners interact directly with:

```bash
mvn clean
```

rather than the pre-clean and post-clean phases.

---

# 20. The Default Lifecycle

The default lifecycle is the main software build lifecycle.

This is where phases such as these live:

```text
validate
compile
test
package
verify
install
deploy
```

But those are only the major phases beginners usually encounter.

The complete lifecycle contains additional phases.

Understanding their order helps you understand how Maven builds software.

---

# 21. Default Lifecycle Phases

The default lifecycle includes the following phases, in order:

```text
validate
initialize
generate-sources
process-sources
generate-resources
process-resources
compile
process-classes
generate-test-sources
process-test-sources
generate-test-resources
process-test-resources
test-compile
process-test-classes
test
prepare-package
package
pre-integration-test
integration-test
post-integration-test
verify
install
deploy
```

There are additional less commonly discussed phases associated with packaging and integration-test preparation in Maven's lifecycle model, but the sequence above contains the core phases you need to understand for this beginner curriculum and the phases you will most often reason about.

We will now walk through them in order.

---

# 22. `validate`

The first phase we will focus on is:

```text
validate
```

Run:

```bash
mvn validate
```

Its purpose is to begin lifecycle processing and confirm that the project model is available and suitable for continuing the build.

At this stage, Maven is not yet compiling your application.

Think:

```text
Project
   |
   v
Can Maven understand the project sufficiently to begin?
```

---

# 23. What `validate` Does Not Mean

Do not interpret:

```bash
mvn validate
```

as:

```text
Maven proves every line of Java is correct.
```

It does not.

It also does not mean:

```text
All tests passed.
```

or:

```text
The application works.
```

Those happen later.

`validate` is an early lifecycle phase.

---

# 24. `initialize`

Next comes:

```text
initialize
```

This phase allows initialization work to occur before source generation and compilation.

A plugin may bind work here that prepares state needed by later build stages.

Examples could include:

* Initializing build properties
* Preparing build metadata
* Establishing values used later

For many simple beginner projects, you may not visibly notice anything happening during this phase.

That is normal.

A phase can exist even when your particular project has no meaningful plugin work bound to it.

---

# 25. Empty Phases Are Important to Understand

A beginner may think:

```text
If Maven prints nothing for a phase, the phase does not exist.
```

That is incorrect.

The lifecycle defines the phases.

Your project determines what goals are bound to them.

So:

```text
Lifecycle phase exists
        |
        v
Are any goals bound?
        |
    +---+---+
    |       |
   Yes      No
    |       |
    v       v
Work runs  Little/no visible work
```

---

# 26. `generate-sources`

Next:

```text
generate-sources
```

This phase exists for generating source code that should later be compiled.

Some projects generate Java code from:

* Schemas
* API definitions
* Protocol definitions
* Code-generation tools
* Other structured inputs

Conceptually:

```text
Definition/Input
       |
       v
generate-sources
       |
       v
Generated Java Source
       |
       v
compile
```

Your beginner project may not generate any source.

That is fine.

---

# 27. Why Generated Source Exists

Not all source code must be manually written by developers.

Imagine an API description is used to generate Java client classes.

Instead of maintaining those generated classes manually:

```text
API definition
     |
     v
Code generator
     |
     v
Java classes
```

Maven gives this process a logical place:

```text
generate-sources
```

The generated code can then participate in compilation.

---

# 28. `process-sources`

After source generation comes:

```text
process-sources
```

This phase allows source-related processing before compilation.

The exact behavior depends on plugins bound by the project.

Again, a simple project may have no visible task here.

The important beginner idea is the ordering:

```text
generate-sources
       |
       v
process-sources
       |
       v
generate-resources
       |
       v
process-resources
       |
       v
compile
```

---

# 29. `generate-resources`

Next:

```text
generate-resources
```

This phase allows resources to be generated for inclusion in the application.

Resources are non-Java files used by the application.

Examples:

```text
.properties files
XML configuration
JSON files
templates
static files
other application resources
```

Generated resources are resources created during the build rather than manually stored as final source files.

---

# 30. `process-resources`

Next:

```text
process-resources
```

This is important in normal Maven projects.

Resources from the conventional location:

```text
src/main/resources
```

are typically processed and copied toward the main build output.

Suppose:

```text
src/main/resources/application.properties
```

exists.

During resource processing, it may end up under:

```text
target/classes/application.properties
```

Conceptually:

```text
src/main/resources
        |
        v
process-resources
        |
        v
target/classes
```

---

# 31. Why Resources Go Into `target/classes`

Java runtime classpaths often include:

```text
target/classes
```

Maven therefore places compiled classes and processed application resources together in the main output area.

You might end up with:

```text
target/classes/
├── com/
│   └── veriqta/
│       └── App.class
└── application.properties
```

This lets the application access both compiled code and runtime resources from the classpath.

---

# 32. `compile`

Now we reach:

```text
compile
```

Run:

```bash
mvn compile
```

This asks Maven to execute the default lifecycle through the `compile` phase.

For a standard Java JAR project, Java source under:

```text
src/main/java
```

is compiled.

Conceptually:

```text
src/main/java
       |
       v
Java compiler
       |
       v
.class files
       |
       v
target/classes
```

---

# 33. What Actually Performs Compilation?

The phase itself does not contain a Java compiler.

For a standard Java build, Maven's lifecycle mapping associates an appropriate compiler plugin goal with the compile phase.

Conceptually:

```text
compile phase
      |
      v
compiler plugin
      |
      v
compile goal
      |
      v
javac/compiler operation
      |
      v
.class files
```

This is the relationship between:

```text
Lifecycle
Phase
Plugin
Goal
```

---

# 34. What Happens With `mvn compile`?

Run:

```bash
mvn compile
```

Maven does not start conceptually at the compile phase and ignore everything before it.

It executes the lifecycle through `compile`.

Simplified:

```text
validate
   |
   v
initialize
   |
   v
generate-sources
   |
   v
process-sources
   |
   v
generate-resources
   |
   v
process-resources
   |
   v
compile
```

Any bound goals encountered along that route execute.

---

# 35. `process-classes`

After compilation comes:

```text
process-classes
```

This phase allows post-processing of compiled class files.

For example, specialized tooling might:

* Transform bytecode
* Enhance classes
* Instrument classes
* Perform other class-level processing

A basic Maven project may not use this phase visibly.

But it exists as a lifecycle extension point.

---

# 36. Why `process-classes` Comes After `compile`

Because the classes need to exist before they can be processed.

The order reflects dependency between operations:

```text
Java Source
    |
    v
compile
    |
    v
.class files
    |
    v
process-classes
```

Maven's lifecycle gives plugins predictable stages for these tasks.

---

# 37. `generate-test-sources`

Now Maven begins preparing test source.

```text
generate-test-sources
```

is similar to `generate-sources`, but for test code.

Conceptually:

```text
Test definitions/input
        |
        v
generate-test-sources
        |
        v
Generated test source
```

Your simple project may not use generated test code.

---

# 38. `process-test-sources`

Next:

```text
process-test-sources
```

This allows test source to be processed before test compilation.

Again, a standard small project may have no visible action here.

---

# 39. `generate-test-resources`

This phase allows test resources to be generated.

These are resources intended for testing rather than production runtime.

Think:

```text
Production resources
→ src/main/resources

Test resources
→ src/test/resources
```

Generated test resources belong to the test side of the build.

---

# 40. `process-test-resources`

This phase processes test resources.

For a conventional Maven project:

```text
src/test/resources
```

can be processed and copied to:

```text
target/test-classes
```

Conceptually:

```text
src/test/resources
        |
        v
process-test-resources
        |
        v
target/test-classes
```

---

# 41. `test-compile`

Next comes:

```text
test-compile
```

This phase compiles test source code.

Source:

```text
src/test/java
```

Output:

```text
target/test-classes
```

Conceptually:

```text
src/test/java
      |
      v
test-compile
      |
      v
target/test-classes
```

---

# 42. Main Compilation Versus Test Compilation

Do not confuse:

```text
compile
```

with:

```text
test-compile
```

`compile` handles main application source:

```text
src/main/java
→ target/classes
```

`test-compile` handles test source:

```text
src/test/java
→ target/test-classes
```

Diagram:

```text
MAIN CODE

src/main/java
      |
      v
   compile
      |
      v
target/classes


TEST CODE

src/test/java
      |
      v
 test-compile
      |
      v
target/test-classes
```

---

# 43. `process-test-classes`

After test compilation:

```text
process-test-classes
```

allows additional processing of compiled test classes.

Like `process-classes`, this may not perform visible work in a basic project.

It exists so plugins have a defined lifecycle stage for test-class post-processing.

---

# 44. `test`

Now Maven reaches:

```text
test
```

Run:

```bash
mvn test
```

This asks Maven to execute the default lifecycle through the `test` phase.

Tests appropriate to this phase are run.

In a normal Java project, unit tests are commonly executed here through Maven's test tooling.

---

# 45. What Happens Before `test`?

Maven must first prepare everything needed for testing.

Simplified:

```text
validate
   |
   v
initialize
   |
   v
generate/process main sources/resources
   |
   v
compile
   |
   v
generate/process test sources/resources
   |
   v
test-compile
   |
   v
test
```

This explains why:

```bash
mvn test
```

can compile your main application and test code before executing tests.

---

# 46. Why Maven Cannot Test Before Compiling

Imagine a test class contains Java source:

```text
CalculatorTest.java
```

The JVM cannot directly execute ordinary `.java` source as a Maven unit-test class in this build flow.

The test source must first be compiled.

Likewise, the application classes being tested generally need to exist.

Therefore:

```text
Main source
   |
   v
compile
   |
   v
Main classes

Test source
   |
   v
test-compile
   |
   v
Test classes
   |
   v
test
```

The lifecycle order encodes this dependency.

---

# 47. `prepare-package`

After testing comes:

```text
prepare-package
```

This phase exists for work required before packaging.

A project might need to:

* Transform content
* Prepare generated files
* Assemble intermediate structures
* Perform packaging preparation

A simple JAR project may have little visible activity here.

---

# 48. `package`

Next:

```text
package
```

Run:

```bash
mvn package
```

This executes the default lifecycle through the package phase.

For a JAR project, Maven normally creates a JAR artifact.

For example:

```text
target/veriqta-maven-app-1.0.0-SNAPSHOT.jar
```

---

# 49. `mvn package` Does More Than Create a JAR

This is one of the most important beginner lessons.

You might think:

```bash
mvn package
```

means:

```text
Create JAR.
```

More accurately:

```text
Execute the default lifecycle through package.
```

That includes earlier stages.

Simplified:

```text
validate
   |
   v
compile
   |
   v
test-compile
   |
   v
test
   |
   v
package
```

Therefore, if tests fail, packaging normally does not complete successfully.

---

# 50. Why Packaging Happens After Testing

Maven's default lifecycle encourages a sensible build sequence:

```text
Can project begin?
      |
      v
Compile application
      |
      v
Compile tests
      |
      v
Run tests
      |
   Pass?
   /   \
 No     Yes
 |       |
 v       v
FAIL   Package
```

This helps prevent an ordinary successful package build from silently ignoring failing unit tests.

---

# 51. Packaging Depends on Project Type

Remember from Part 4:

```xml
<packaging>jar</packaging>
```

For JAR packaging:

```text
package
→ normally produce JAR
```

For WAR packaging:

```text
package
→ normally produce WAR
```

For POM packaging:

```text
package
→ behaves differently because the project model itself is central
```

Lifecycle phase names remain consistent, but the goals bound to them can depend on packaging.

---

# 52. Lifecycle Mapping

This leads to an important concept:

```text
Lifecycle mapping
```

Maven knows that for a particular packaging type, certain plugin goals should normally be bound to certain phases.

Simplified JAR example:

```text
process-resources
      |
      v
resources plugin goal

compile
      |
      v
compiler plugin goal

test
      |
      v
test plugin goal

package
      |
      v
jar plugin goal

install
      |
      v
install plugin goal

deploy
      |
      v
deploy plugin goal
```

This is why Maven can perform a useful standard Java build without requiring you to manually bind every basic goal.

---

# 53. `pre-integration-test`

After package comes:

```text
pre-integration-test
```

This phase exists to prepare an environment needed for integration testing.

Examples could include:

* Starting supporting services
* Preparing test infrastructure
* Starting an application
* Creating temporary environments
* Preparing test data

Conceptually:

```text
Packaged Application
       |
       v
pre-integration-test
       |
       v
Integration-test environment ready
```

---

# 54. What Is an Integration Test?

A unit test usually tests a relatively small piece of code in isolation.

An integration test checks interaction between components or systems.

For example:

```text
Application
    |
    +---- Database
    |
    +---- HTTP service
    |
    +---- Message broker
```

An integration test might verify that these pieces work together correctly.

That often requires more setup than a unit test.

This is why Maven provides lifecycle stages specifically around integration testing.

---

# 55. `integration-test`

Next comes:

```text
integration-test
```

This phase is intended for running integration tests against an appropriately prepared environment.

Conceptually:

```text
Application package
       |
       v
Prepared environment
       |
       v
integration-test
       |
       v
Integration results
```

Important beginner note:

Simply naming a test "integration test" does not automatically configure Maven correctly.

Plugins still need appropriate configuration and lifecycle bindings.

The lifecycle provides the stage.

Plugins provide the actual test execution.

---

# 56. `post-integration-test`

After integration testing comes:

```text
post-integration-test
```

This phase exists for cleanup after integration tests.

For example:

```text
pre-integration-test
→ start test environment

integration-test
→ run integration tests

post-integration-test
→ stop test environment
```

This order is important.

You do not want temporary services or test infrastructure left running unnecessarily after a build.

---

# 57. Why `post-integration-test` Matters

Imagine a build starts a temporary application server.

If the build never stops it:

* Ports may remain occupied
* Processes may continue running
* CI agents may become polluted
* Later builds may fail
* Resources may be wasted

The lifecycle provides a cleanup stage:

```text
Setup
→ Test
→ Cleanup
```

This is a general engineering pattern, not just a Maven concept.

---

# 58. `verify`

Next:

```text
verify
```

Run:

```bash
mvn verify
```

This executes the default lifecycle through the `verify` phase.

The purpose of `verify` is to allow checks that confirm the package meets required quality or validity criteria.

Depending on project configuration, verification might include checks such as:

* Integration test result verification
* Quality rules
* Packaging checks
* Additional validation plugins
* Policy checks

The exact checks depend on the project.

---

# 59. `package` Versus `verify`

A useful beginner distinction:

```text
package
→ create the package

verify
→ continue beyond packaging and run configured verification steps
```

Conceptually:

```text
Source
  |
  v
Compile
  |
  v
Test
  |
  v
Package
  |
  v
Artifact
  |
  v
Verify
  |
  v
Artifact/build accepted by configured checks
```

---

# 60. Why CI Often Uses `verify`

For a CI pipeline, simply producing a JAR may not be enough.

You may want to know:

```text
Did unit tests pass?

Did integration tests pass?

Did required quality checks pass?

Is the package acceptable?
```

A command such as:

```bash
mvn verify
```

is therefore often a more meaningful CI build target than only:

```bash
mvn package
```

The exact best command still depends on the project and pipeline design.


```bash
mvn install
```

After building and verifying the project, Maven installs the project's artifact into the local Maven repository.

The default local repository is commonly:

```text
~/.m2/repository
```

# 62. What Does Install Mean?

Do not confuse:

```bash
mvn install
```

with:

```text
Install Maven on my computer.
```

It does not install Maven itself.

It means:

```text
Install this project's built artifact into the local Maven repository.
```

```text
deploy
```

# 66. `install` Versus `deploy`

This distinction is critical.

```text

```

```text
                  Maven Build
                      |
             +--------+--------+
```

# 67. Why Remote Deployment Matters

In a team, other developers and CI systems cannot normally access your laptop's:

```text
~/.m2/repository
```

A shared remote artifact repository allows authorized systems to retrieve published artifacts.

Conceptually:

```text
CI Build
   |
   v
Maven deploy
   |
   v
Remote Artifact Repository
   |
   +---- Team A
   +---- Team B
   +---- CI pipeline
   +---- Deployment tooling
```

Remote repository configuration and repository managers will be covered in greater depth later.

---

# 68. Security Warning About `mvn deploy`

Do not casually run:

```bash
mvn deploy
```

against an organization's real repository.

Deployment can publish artifacts to shared infrastructure.

Before deploying, understand:

* Which repository is configured
* Whether it accepts snapshots or releases
* Which credentials Maven uses
* Whether you are authorized to publish
* Which version you are publishing
* Whether the artifact has passed required checks

In a learning project without configured remote deployment, `mvn deploy` may fail.

That is not necessarily a Maven installation problem.

It may simply mean no valid deployment repository is configured.

# 69. Why Later Phases Execute Earlier Phases

This is the core lifecycle rule.

Suppose the order is:

```text
A
→ B
→ C
→ D
→ E
```

If you request:

```text
D
```

Maven executes:

```text
A
→ B
→ C
→ D
```

It does not jump directly to D.

The same idea applies to the Maven default lifecycle.

---

# 70. `mvn compile`

Run:

```bash
mvn compile
```

Simplified execution:

```text
validate
→ initialize
→ generate-sources
→ process-sources
→ generate-resources
→ process-resources
→ compile
```

You asked Maven to reach `compile`.

Everything before `compile` in that lifecycle is traversed.

---

# 71. `mvn test`

Run:

```bash
mvn test
```

Maven continues farther:

```text
validate
→ ...
→ compile
→ ...
→ test-compile
→ process-test-classes
→ test
```

Therefore:

```bash
mvn test
```

does not mean:

```text
Run tests without preparing the project.
```

It means:

```text
Execute the default lifecycle through test.
```

---

# 72. `mvn package`

Run:

```bash
mvn package
```

Maven continues farther:

```text
validate
→ ...
→ compile
→ ...
→ test
→ prepare-package
→ package
```

For a JAR project, this normally results in a JAR.

---

# 73. `mvn verify`

Run:

```bash
mvn verify
```

Maven continues through:

```text
package
→ pre-integration-test
→ integration-test
→ post-integration-test
→ verify
```

along with all earlier phases.

This makes `verify` useful when your project has checks configured after packaging.

---

# 74. `mvn install`

Run:

```bash
mvn install
```

Maven executes everything through:

```text
install
```

Simplified:

```text
validate
→ compile
→ test
→ package
→ integration testing stages
→ verify
→ install
```

The artifact is then installed into the local repository.

---

# 75. `mvn deploy`

Run:

```bash
mvn deploy
```

Maven executes the default lifecycle through its final phase:

```text
validate
→ compile
→ test
→ package
→ verify
→ install
→ deploy
```

This is why `deploy` is not simply:

```text
Upload a random JAR.
```

It belongs at the end of a structured build lifecycle.

# 83. Why `mvn clean package` Is Common

# 84. `mvn clean` Versus `mvn clean package`

# 85. Multiple Phases and Goals in One Maven Invocation

Maven allows multiple execution targets.

For example:

```bash
mvn clean package
```

You can also encounter commands combining lifecycle phases and explicit plugin goals.

Conceptually:

```bash
mvn <target1> <target2> <target3>
```

Maven processes the requested items in command-line order.

This gives Maven CLI considerable flexibility.

---

# 86. Be Careful With Repeated Lifecycle Execution

Consider:

```bash
mvn compile package
```

A beginner may think:

```text
compile once
then package
```

But `package` itself requires lifecycle execution through `package`.

Because Maven processes requested lifecycle targets, specifying overlapping phases can cause earlier lifecycle work to be traversed again.

In normal usage, you usually do not need:

```bash
mvn compile package
```

If your real goal is packaging, use:

```bash
mvn package
```

because `package` already includes the earlier phases.

---

# 87. Another Redundant Example

You generally do not need:

```bash
mvn test package
```

when you simply want a normal package build.

Why?

Because:

```bash
mvn package
```

already executes through:

```text
test
```

before reaching:

```text
package
```

Prefer expressing the final lifecycle state you actually need.

---

# 88. Practical Rule

Instead of:

```bash
mvn validate compile test package
```

normally use:

```bash
mvn package
```

because the lifecycle already provides the ordering.

Similarly, instead of:

```bash
mvn compile test package verify
```

normally use:

```bash
mvn verify
```

The lifecycle is Maven's orchestration mechanism.

Use it.

---

# 89. Phase Versus Direct Goal Execution

Suppose you run:

```bash
mvn package
```

You are invoking a lifecycle phase.

Maven executes all appropriate earlier lifecycle phases.

But suppose you directly invoke a plugin goal:

```bash
mvn help:effective-pom
```

You are asking for that specific plugin goal.

You are not asking Maven to execute the default lifecycle through `package`, `test`, or `compile`.

This difference is crucial.

---

# 90. Direct Goal Execution Does Not Mean Full Lifecycle Execution

A plugin goal can be executed directly:

```bash
mvn plugin-prefix:goal
```

This does not automatically mean:

```text
validate
→ compile
→ test
→ package
```

unless the goal itself or surrounding configuration causes other work.

The command means:

```text
Execute this plugin goal.
```

This is why you must understand whether you are invoking:

```text
A lifecycle phase
```

or:

```text
A plugin goal
```

---

# 91. How to Recognize the Difference

These are phases:

```bash
mvn compile
mvn test
mvn package
mvn verify
mvn install
```

These use plugin-goal syntax:

```bash
mvn help:effective-pom
mvn help:effective-settings
mvn help:evaluate
```

A simple visual clue is:

```text
:
```

in the plugin-goal syntax.

But do not rely only on punctuation.

Understand the underlying concept.

# 94. `[INFO] Scanning for projects`

```text

```

it is locating and processing Maven project information.

Later, with multi-module builds, "scanning for projects" becomes even more meaningful because Maven may discover a reactor of multiple Maven modules.

# 95. Project Coordinates in Output

You may see something resembling:

```text

```

```text
groupId

```

become visible.

# 96. Reading Plugin Execution Lines

You may see lines conceptually resembling:

```text

```

Break it down:

```text

→ plugin prefix/name context

→ plugin version Maven is using

compile
→ plugin goal

→ project/module being processed
```

This is valuable troubleshooting information.

It tells you what actual plugin goal is running.

# 97. Phase Names May Not Be the Most Visible Part of Output

You asked Maven for:

```bash
mvn package
```

but the output may prominently show plugin goals such as:

```text

```

Because:

```text

```

This is another reason the phase-versus-goal distinction matters.

# 98. `[INFO]`

Maven commonly prefixes informational messages with:

```text
[INFO]
```

These are normal status messages.

Examples:

```text
[INFO] Scanning for projects...
[INFO] Building ...
[INFO] BUILD SUCCESS
```

Do not treat every line as an error simply because the output is long.

---

# 99. `[WARNING]`

You may encounter:

```text
[WARNING]
```

A warning means Maven or a plugin has identified something worth your attention, but the build may still continue.

Examples might involve:

* Deprecated configuration
* Missing recommended metadata
* Plugin warnings
* Duplicate declarations
* Potential build problems

Do not ignore warnings automatically.

A successful build can still contain warnings that should be investigated.

---

# 100. `[ERROR]`

Errors are commonly marked:

```text
[ERROR]
```

An error usually means some required build step failed.

Possible causes include:

* Compilation error
* Test failure
* Dependency resolution failure
* Plugin execution failure
* Invalid POM
* Repository access failure
* Authentication failure

The correct response is not:

```text
Run random Maven commands until it works.
```

Read the first meaningful failure and determine which build stage failed.

---

# 101. `BUILD SUCCESS`

A successful build normally ends with:

```text
BUILD SUCCESS
```

This means Maven successfully completed the execution you requested.

But always ask:

```text
What exactly did I request?
```

For example:

```bash
mvn validate
```

followed by:

```text
BUILD SUCCESS
```

does not mean:

```text
The application compiled and all tests passed.
```

It means Maven successfully completed through the `validate` phase.

---

# 102. Success Is Relative to the Requested Target

Compare:

```bash
mvn validate
```

with:

```bash
mvn verify
```

Both can end with:

```text
BUILD SUCCESS
```

But they prove different things.

`mvn validate`:

```text
Early lifecycle execution completed successfully.
```

`mvn verify`:

```text
The build completed through the verify phase, including all configured work bound to phases before it.
```

Always interpret success in context.

---

# 103. `BUILD FAILURE`

When Maven cannot complete the requested execution, you may see:

```text
BUILD FAILURE
```

Do not focus only on those two words.

`BUILD FAILURE` tells you the outcome.

The useful information is usually earlier.

Search upward for:

```text
[ERROR]
```

and identify:

```text
Which phase or goal was running?

What error occurred?

Which file?

Which line?

Which dependency?

Which test?

Which repository?

Which plugin?
```

# 143. Troubleshooting Scenario: `mvn compile` Fails

## Problem

You run:

```bash
mvn compile
```

and receive:

```text
BUILD FAILURE
```

## Possible Causes

* Java syntax error
* Wrong Java release
* Missing dependency required for compilation
* Compiler plugin configuration
* Generated source failure
* Invalid source path/configuration

## Investigate

Read the compiler error.

Check:

```bash
mvn -version
```

Inspect:

```xml
<maven.compiler.release>...</maven.compiler.release>
```

Check the exact Java source file and line.

## Fix

Correct the actual cause.

## Verify

```bash
mvn clean compile
```

---

# 144. Troubleshooting Scenario: `mvn test` Fails

## Problem

Compilation succeeds, but:

```bash
mvn test
```

fails.

## Possible Causes

* Test assertion failure
* Test compilation error
* Missing test dependency
* Test setup failure
* Incorrect test configuration
* Application bug exposed by the test

## Investigate

Read:

* Test name
* Failure message
* Stack trace
* Test reports

Test reports are commonly written under:

```text
target/
```

in plugin-specific report directories.

## Fix

Correct the test or application behavior based on evidence.

## Verify

```bash
mvn test
```

---

# 145. Troubleshooting Scenario: `mvn package` Fails

## Problem

Compilation and tests may succeed, but packaging fails.

## Possible Causes

* Packaging plugin configuration
* Invalid archive configuration
* Missing required files
* File permission issue
* Packaging-specific plugin failure

## Investigate

Identify which plugin goal failed.

If the output indicates the JAR plugin, investigate packaging rather than Java compilation.

## Verify

```bash
mvn clean package
```

---

# 146. Troubleshooting Scenario: `mvn install` Fails

## Problem

The package is created but local installation fails.

## Possible Causes

* Local repository permissions
* Disk problems
* Filesystem issues
* Corrupted metadata
* Install plugin failure

## Investigate

Check Maven's reported local repository.

You can inspect settings with:

```bash
mvn help:effective-settings
```

Check filesystem permissions and available disk space when relevant.

## Verify

```bash
mvn install
```

---

# 147. Troubleshooting Scenario: `mvn deploy` Fails

## Problem

Everything builds locally, but remote publication fails.

## Possible Causes

* Repository not configured
* Wrong repository URL
* Missing credentials
* Invalid credentials
* Insufficient permissions
* Network failure
* DNS failure
* Proxy configuration
* Snapshot sent to release-only repository
* Release rejected by repository policy

## Investigate

Ask:

```text
Did verify succeed?

Did install succeed?

Which repository is Maven targeting?

Are credentials configured safely?

Can the CI environment reach the repository?

Is this a snapshot or release?
```

## Security

Do not print passwords or tokens while troubleshooting.

## Verification

After correcting the actual repository problem, rerun the appropriate deployment process.

# 158. Maven's Design Philosophy

Maven is not asking every project to invent its own build sequence.

Instead, it provides a standardized model:

```text
There is a lifecycle.

The lifecycle has phases.

Plugins provide goals.

Goals are bound to phases.

Packaging influences default bindings.

The POM can customize configuration.

Maven executes the requested lifecycle path.
```

This standardization is one reason engineers can enter an unfamiliar Maven project and often begin with familiar commands such as:

```bash
mvn test
```

or:

```bash
mvn verify
```

# 164. Security and the Maven Lifecycle

Build stages can execute plugins and code-related tooling.

Therefore:

* Review POM changes
* Pin important plugin versions where appropriate
* Protect repository credentials
* Use trusted artifact repositories
* Avoid arbitrary third-party build plugins
* Treat CI build permissions carefully
* Do not expose deployment credentials to untrusted pull requests
* Do not blindly execute unknown Maven projects with powerful credentials

A build system is part of the software supply chain.

```bash
mvn package
```

on an untrusted repository is not conceptually equivalent to merely reading source code.

Build tooling may execute configured plugin behavior.

For unknown projects:

```text
Inspect source
→ Inspect POM
→ Understand build plugins
→ Use an isolated environment where appropriate
→ Avoid exposing sensitive credentials
→ Then build
```

This is a useful production-security habit.

# 172. Knowledge Check Answers

## 1. What is Maven's CLI?

The command-line interface used to interact with Maven, normally through the `mvn` executable.

## 2. What does `mvn compile` request?

It asks Maven to execute the default lifecycle through the `compile` phase.

## 3. What is a lifecycle?

An ordered sequence of build phases representing a broader build process.

## 4. What is a phase?

A named stage within a Maven lifecycle.

## 5. What is a plugin?

A Maven component that provides functionality for performing build tasks.

## 6. What is a goal?

A specific unit of work provided by a Maven plugin.

## 7. Phase versus goal?

A phase represents where Maven is in the lifecycle.

A goal represents actual plugin work.

## 8. What does binding mean?

It means a plugin goal is associated with a lifecycle phase so Maven executes that goal when it reaches the phase.

## 9. Three lifecycles?

```text
clean
default
site
```

## 10. Which contains `clean`?

The clean lifecycle.

## 11. Which contains `compile`?

The default lifecycle.

## 12. Which contains `site`?

The site lifecycle.

## 13. Does package execute compile first?

Yes, as part of executing the default lifecycle through `package`.

## 14. Why?

Because `compile` appears earlier than `package` in the ordered default lifecycle.

## 15. Does test compile main source first?

Yes. The lifecycle reaches main compilation before test execution.

## 16. Why `generate-sources`?

To provide a standard lifecycle stage where build tooling can generate source code before compilation.

## 17. What happens during process-resources?

Main application resources are typically processed and copied toward the main output directory.

## 18. Main compiled classes?

Normally:

```text
target/classes
```

## 19. Test compiled classes?

Normally:

```text
target/test-classes
```

## 20. Compile versus test-compile?

```text
compile
→ main application source

test-compile
→ test source
```

## 21. What happens during test?

Configured tests appropriate to that lifecycle stage, commonly unit tests, are executed.

## 22. Why prepare-package?

It provides a stage for work required immediately before packaging.

## 23. Package for JAR?

Maven normally creates a JAR artifact.

## 24. Why integration-test surrounding phases?

They provide standard stages for setup, integration-test execution, and cleanup.

## 25. Verify?

It provides a stage for configured checks that verify the built package and build results.

## 26. What does install install?

The current project's Maven artifact and related project metadata.

## 27. Where?

Normally in the local Maven repository:

```text
~/.m2/repository
```

## 28. What does deploy deploy?

The Maven artifact to a configured remote artifact repository.

## 29. Same as Kubernetes deployment?

No.

Maven artifact deployment and runtime application deployment are different processes.

## 30. Why does install run earlier phases?

Because Maven executes the default lifecycle in order through the requested phase.

## 31. Is clean automatic with package?

No.

## 32. `mvn clean package`?

Execute the clean lifecycle through clean, then the default lifecycle through package.

## 33. Why is `compile package` unnecessary?

Because requesting `package` already causes Maven to traverse the earlier compile phase.

## 34. `help:effective-pom`?

It directly invokes the `effective-pom` goal of Maven's Help Plugin.

## 35. Does it package the application?

No, not merely because that goal was requested.

## 36. BUILD SUCCESS?

Maven successfully completed the execution you requested.

## 37. Does validate success prove tests passed?

No. Test execution occurs later.

## 38. BUILD FAILURE?

Maven could not successfully complete the requested execution.

## 39. Where is the root cause?

Usually in the error messages appearing before the final `BUILD FAILURE` line.

## 40. Compilation works, tests fail?

Investigate the test stage, test reports, test configuration, and application behavior exposed by the failing tests.

## 41. Verify succeeds, deploy fails?

Focus first on the deployment stage, such as repository configuration, credentials, permissions, or networking.

## 42. Why not blindly skip tests?

Because skipping a failed test hides the signal without fixing the underlying problem.

## 43. Why treat unknown Maven builds carefully?

Because Maven plugins and build configuration can execute code and interact with the filesystem, network, repositories, and credentials.

## 44. Why useful in CI/CD?

Standard lifecycle phases provide predictable build stages that automation systems can invoke consistently.

## 45. Simplified flow?

```text
Source
→ validate
→ compile
→ test
→ package
→ verify
→ install
→ deploy
```

# 173. Final Mental Model

The most important lesson from this part is not a list of Maven commands.

It is the relationship between four concepts:

```text
Lifecycle
    |
    v
Phase
    |
    v
Bound Plugin Goal
    |
    v
Actual Build Work
```

When you type:

```bash
mvn package
```

think:

```text
I am asking Maven to execute the default lifecycle through the package phase.
```

Maven then follows the lifecycle:

```text
Earlier phases
     |
     v
compile
     |
     v
test
     |
     v
package
```

At those phases, plugin goals perform the actual work.

When you type:

```bash
mvn help:effective-pom
```

think differently:

```text
I am directly requesting a particular plugin goal.
```

And remember that Maven has three built-in lifecycles:

```text
clean
→ remove previous build output

default
→ build and distribute the artifact

site
→ generate and deploy project site information
```

For everyday development, the major default lifecycle path to keep in your head is:

```text
                  Java Source
                      |
                      v
                   validate
                      |
                      v
                   compile
                      |
                      v
                     test
                      |
                      v
                   package
                      |
                      v
                    verify
                      |
                      v
                   install
                      |
                      v
                    deploy
                      |
            +---------+---------+
            |                   |
            v                   v
     Local Repository    Remote Repository
```

And for a clean build:

```text
Old target/
    |
    v
mvn clean package
    |
    v
Clean lifecycle
    |
    v
Old build output removed
    |
    v
Default lifecycle
    |
    v
validate
    |
    v
compile
    |
    v
test
    |
    v
package
    |
    v
Fresh artifact
```

When a build fails, use the same model in reverse:

```text
BUILD FAILURE
      |
      v
Where did lifecycle execution stop?
      |
      v
Which plugin goal failed?
      |
      v
What evidence did it report?
      |
      v
What category of problem is this?
      |
      v
Fix the root cause
      |
      v
Run the appropriate lifecycle target again
      |
      v
Verify
```

Once this model is clear, Maven stops being a collection of commands to memorize.

It becomes an ordered build system that you can inspect, reason about, automate, and troubleshoot.
