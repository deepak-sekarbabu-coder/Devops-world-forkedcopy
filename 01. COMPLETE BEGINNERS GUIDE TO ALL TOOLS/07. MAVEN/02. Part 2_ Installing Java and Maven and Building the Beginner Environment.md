# Part 2: Installing Java and Maven and Building the Beginner Environment

## Introduction

In Part 1, you learned why Maven exists.

You learned the basic relationship:

```text
Developer
→ Java source code
→ Maven
→ Compile
→ Test
→ Package
→ Application artifact
```

Before Maven can build a Java project, however, the computer needs the correct environment.

That environment includes several pieces:

```text
Operating System
      |
      v
JDK
      |
      +---- java
      |
      +---- javac
      |
      v
JAVA_HOME
      |
      v
PATH
      |
      v
Maven
      |
      v
mvn
```

A surprising number of Maven problems are actually environment problems.

For example:

```text
mvn: command not found
```

may mean Maven is installed but PATH is incorrect.

An error involving `JAVA_HOME` may mean Maven exists but cannot locate the intended Java installation.

A build that works in an IDE but fails in the terminal may mean the IDE and terminal are using different JDKs or different Maven installations.

A project that works on one developer's machine but fails on another may involve different Java versions.

This part therefore focuses on building a clean Maven workstation from the ground up.

# 1. What Does Maven Require?

Maven is primarily associated with Java projects, and Maven itself runs on Java.

That means Maven needs access to an appropriate Java installation.

At a beginner level, think of the relationship like this:

```text
Computer
   |
   v
JDK
   |
   v
Java Runtime
   |
   v
Maven
   |
   v
Java Project Build
```

Maven does not replace Java.

Maven uses Java.

When Maven needs to compile Java source code, it participates in a process that depends on Java development tooling.

This is why setting up Java correctly comes before setting up Maven.

---

# 2. The Three Pieces Beginners Often Confuse

You will frequently encounter these terms:

```text
JVM
JRE
JDK
```

They are related, but they are not identical.

A useful conceptual model is:

```text
JDK
 |
 +---- Development tools
 |       |
 |       +---- javac
 |       +---- other tools
 |
 +---- Java runtime capabilities
         |
         v
        JVM
```

Let's understand each one.

---

# 3. What Is the JVM?

JVM means:

```text
Java Virtual Machine
```

The JVM executes Java bytecode.

Recall Part 1:

```text
Hello.java
    |
    v
javac
    |
    v
Hello.class
    |
    v
JVM
    |
    v
Running Program
```

The `.class` file contains Java bytecode.

The JVM provides the environment that executes that bytecode.

This is a major part of Java's portability model.

Instead of compiling the same Java source directly into separate native executables for every operating system in the traditional model, Java source is typically compiled into bytecode.

A suitable JVM for the operating system then executes that bytecode.

Conceptually:

```text
Java Source
    |
    v
Bytecode
    |
    +-------------------+
    |         |         |
    v         v         v
macOS JVM  Linux JVM  Windows JVM
```

The JVM implementation itself is platform-specific.

The bytecode model helps Java applications remain portable across systems with compatible Java runtimes.

---

# 4. What Is the JRE?

JRE means:

```text
Java Runtime Environment
```

Historically, the JRE referred to the runtime environment needed to run Java applications.

For beginner understanding:

```text
JRE
→ Run Java applications
```

The JRE concept is different from the full development environment.

If you only wanted to execute an already compiled Java application, runtime components could be sufficient.

But a developer needs more.

A developer needs tools such as the Java compiler.

That brings us to the JDK.

---

# 5. What Is the JDK?

JDK means:

```text
Java Development Kit
```

The JDK provides the tools required to develop Java applications.

Important commands include:

```text
java
javac
```

The distinction is:

```text
java
→ launches Java applications

javac
→ compiles Java source code
```

A developer working with Maven should normally have a JDK available.

Think:

```text
JDK
 |
 +---- java
 |
 +---- javac
 |
 +---- development tools
 |
 +---- runtime capabilities
```

---

# 6. JDK Versus JRE

A simple comparison is:

| Component   | Main Purpose                        |          Can Run Java? |               Development Tools? |
| ----------- | ----------------------------------- | ---------------------: | -------------------------------: |
| JVM         | Executes Java bytecode              | Yes, as runtime engine |                               No |
| JRE concept | Provides Java runtime environment   |                    Yes | Not the full development toolset |
| JDK         | Develops and runs Java applications |                    Yes |                              Yes |

For Maven development, remember:

```text
Use a JDK.
```

Why?

Because Maven projects frequently need to compile Java source code.

Compilation requires development tooling.

---

# 7. Why Maven Needs Java

Maven itself is a Java-based application.

When you execute:

```bash
mvn
```

the Maven launcher eventually starts Maven using Java.

Conceptually:

```text
Terminal
   |
   v
mvn
   |
   v
Maven Launcher
   |
   v
Java
   |
   v
Maven Runtime
```

Maven then performs build work.

For a Java project:

```text
Maven
 |
 +---- Read pom.xml
 |
 +---- Resolve dependencies
 |
 +---- Execute plugins
 |
 +---- Compile Java
 |
 +---- Run tests
 |
 +---- Package application
```

This means Maven needs to know which Java installation it should use.

That is where your Java environment becomes important.

# 8. Understanding Java Versions

Java has different versions.

You may encounter versions such as:

```text
Java 8
Java 11
Java 17
Java 21
Java 25
```

Projects do not necessarily use the same Java version.

A company may maintain one application that requires Java 17 and another that requires Java 21.

This creates an important distinction:

```text
Java installed on your computer
```

is not automatically the same as:

```text
Java version required by the project
```

---

# 9. Why Java Versions Matter

Suppose your project requires Java 21.

Your machine uses Java 17.

The project may use language features or APIs that Java 17 does not support.

The build can fail.

The reverse can also cause compatibility problems depending on how the project is configured.

Therefore, when joining a Java project, one of your first questions should be:

```text
Which Java version does this project require?
```

Do not automatically install the newest Java version and assume every project will work with it.

The project's requirements should guide the version choice.

---

# 10. LTS Java Versions

You may encounter the term:

```text
LTS
```

LTS means:

```text
Long-Term Support
```

Certain Java releases receive longer support lifecycles from relevant vendors.

Organizations often standardize on particular LTS releases.

But do not assume:

```text
latest = required
```

or:

```text
LTS = automatically compatible with every project
```

Always check the project requirements.

# 11. Checking Whether Java Is Already Installed

Before installing anything, inspect your current system.

This is an important engineering habit:

```text
Inspect first
→ Change second
```

Do not install another JDK before discovering what is already installed.

Open your terminal.

Run:

```bash
java -version
```

---

# 12. Understanding `java -version`

The command:

```bash
java -version
```

asks the Java launcher to report its version information.

Break it down:

```text
java
```

is the Java application launcher.

```text
-version
```

asks it to display version information and exit.

The output varies by Java distribution and version.

You may see something similar to:

```text
openjdk version "21.0.x" ...
OpenJDK Runtime Environment ...
OpenJDK 64-Bit Server VM ...
```

Do not worry if your exact wording differs.

Important information includes:

* Java version
* Java distribution
* Runtime information
* JVM information
* Architecture information in some distributions

The most immediate question is:

```text
Does Java exist, and which Java am I using?
```

---

# 13. Checking the Java Compiler

Now run:

```bash
javac -version
```

This checks the Java compiler.

Example:

```text
javac 21.0.x
```

Again, your version may differ.

The important thing is that `javac` is available.

---

# 14. Why Check Both `java` and `javac`?

Because they answer different questions.

```bash
java -version
```

asks:

```text
Can I launch Java, and which runtime is being selected?
```

```bash
javac -version
```

asks:

```text
Can I compile Java, and which compiler is being selected?
```

For a Maven development environment, you generally want both.

Check:

```bash
java -version
javac -version
```

If both commands work and show compatible versions, that is a good sign.

---

# 15. What If `java` Works but `javac` Does Not?

Suppose:

```bash
java -version
```

works.

But:

```bash
javac -version
```

returns something like:

```text
command not found
```

This tells you something important.

You have access to a Java runtime command, but the Java compiler is not currently accessible through your shell.

Possible reasons include:

* You do not have a full JDK installed
* A JDK exists but PATH does not include its `bin` directory
* Multiple Java installations exist
* Your shell is selecting a different Java installation than expected

Do not immediately conclude:

```text
Java is completely broken.
```

Gather more evidence.

---

# 16. Environment Variables

Before configuring Java correctly, you need to understand environment variables.

An environment variable is a named value available to processes running in an environment.

Examples include:

```text
PATH
HOME
JAVA_HOME
```

Think of them as named pieces of configuration.

For example:

```text
JAVA_HOME=/some/path/to/jdk
```

This associates the name:

```text
JAVA_HOME
```

with a filesystem path.

Programs and scripts can inspect that variable.

---

# 17. Why Environment Variables Exist

Applications often need configuration that differs between machines.

Hardcoding every machine-specific value inside applications would be inconvenient.

Environment variables provide one way of exposing configuration to processes.

For example:

```text
JAVA_HOME
→ Where the selected JDK lives

PATH
→ Which directories the shell searches for commands
```

These two variables are particularly important for our Maven setup.

---

# 18. What Is `JAVA_HOME`?

`JAVA_HOME` is an environment variable commonly used to identify the root directory of a Java installation, normally a JDK for development environments.

Conceptually:

```text
JAVA_HOME
    |
    v
/path/to/jdk
```

Inside that JDK are directories such as:

```text
bin
lib
conf
```

The `bin` directory contains executable tools.

For example:

```text
$JAVA_HOME/bin/java
$JAVA_HOME/bin/javac
```

The exact JDK layout can vary by platform and distribution, but this mental model is useful.

---

# 19. `JAVA_HOME` Is Not the `java` Executable

A common beginner mistake is setting:

```text
JAVA_HOME=/path/to/java
```

where `/path/to/java` points directly to the executable.

That is normally incorrect.

`JAVA_HOME` should point to the Java installation root.

Conceptually:

Incorrect:

```text
JAVA_HOME=/some/jdk/bin/java
```

Correct concept:

```text
JAVA_HOME=/some/jdk
```

Then:

```text
$JAVA_HOME/bin/java
```

points to the executable.

---

# 20. Checking `JAVA_HOME`

On macOS or Linux, run:

```bash
echo $JAVA_HOME
```

If configured, you should see a directory.

For example:

```text
/path/to/jdk
```

If nothing appears, `JAVA_HOME` may not be set in that shell session.

That does not automatically mean Java is unavailable.

This is an important distinction.

You can have:

```bash
java -version
```

working while:

```bash
echo $JAVA_HOME
```

is empty.

Why?

Because PATH may already allow the shell to find `java`.

`JAVA_HOME` and PATH solve related but different problems.

---

# 21. What Is PATH?

PATH is an environment variable containing a list of directories that the shell searches when you type a command.

Suppose you type:

```bash
java
```

You did not type the complete filesystem path to Java.

The shell needs to find the executable.

It searches directories listed in PATH.

Conceptually:

```text
You type:
java

        |
        v

Shell reads PATH

        |
        v

Search directory 1
Search directory 2
Search directory 3
...

        |
        v

Find java executable

        |
        v

Execute it
```

---

# 22. Inspecting PATH

On macOS or Linux:

```bash
echo $PATH
```

You may see something resembling:

```text
/usr/local/bin:/usr/bin:/bin:/some/other/path
```

Directories are separated by colons on Unix-like systems.

The shell searches them in order.

That order matters.

---

# 23. Why PATH Order Matters

Imagine PATH contains:

```text
/old-java/bin
/new-java/bin
/usr/bin
```

Both Java directories contain a `java` command.

When you type:

```bash
java -version
```

the shell generally uses the first matching executable it finds.

That means:

```text
PATH order
→ determines which java may run
```

This becomes important when multiple Java versions are installed.

The same issue can happen with Maven.

---

# 24. `JAVA_HOME` Versus PATH

These concepts are frequently confused.

`JAVA_HOME` says:

```text
This is the Java installation I want tools to consider.
```

PATH says:

```text
These are the directories where my shell should search for executable commands.
```

A common Unix-like configuration concept is:

```bash
export JAVA_HOME="/path/to/jdk"
export PATH="$JAVA_HOME/bin:$PATH"
```

The first line defines `JAVA_HOME`.

The second places the JDK's `bin` directory near the beginning of PATH.

Now commands such as:

```bash
java
javac
```

can be found there.

---

# 25. Understanding `export`

On common Unix shells, you may see:

```bash
export JAVA_HOME="/path/to/jdk"
```

`export` makes the variable available to child processes launched from the shell.

This matters because Maven runs as a process started from your shell.

A shell variable that is not exported may not be inherited by child processes.

For beginner setup, environment configuration commonly uses:

```bash
export VARIABLE=value
```

---

# 26. Temporary Versus Persistent Environment Variables

If you type:

```bash
export JAVA_HOME="/path/to/jdk"
```

directly in a terminal, it affects the current shell environment.

Close the terminal and open another one, and the setting may disappear.

To make configuration persistent, it is normally placed in a shell startup file.

The exact file depends on the shell.

Examples include:

```text
~/.zshrc
~/.bashrc
~/.bash_profile
```

Do not blindly edit all of them.

First determine which shell you are using.

---

# 27. Checking Your Shell

On macOS or Linux, you can inspect:

```bash
echo $SHELL
```

You may see:

```text
/bin/zsh
```

or:

```text
/bin/bash
```

If you use Zsh, configuration commonly goes into:

```text
~/.zshrc
```

If you use Bash, the appropriate startup file can depend on the operating system and whether the shell is interactive or a login shell.

The important lesson is:

```text
Know your shell before changing shell configuration.
```

# 28. Installing a JDK

There are several ways to install a JDK.

You can generally use:

1. A JDK distribution installer
2. A package manager
3. A manually managed JDK distribution
4. A Java version manager in more advanced environments

For a beginner, the most important requirement is not the installation method.

It is knowing:

* Which JDK you installed
* Which version it is
* Where it lives
* Which `java` your shell selects
* Which `javac` your shell selects
* What `JAVA_HOME` points to

After installation, always verify.

# 29. Choosing a JDK Distribution

Java development can involve different JDK distributions.

You may encounter names such as:

```text
OpenJDK
Eclipse Temurin
Amazon Corretto
Oracle JDK
Microsoft Build of OpenJDK
```

A JDK distribution packages an implementation of the Java platform for developers.

Different organizations may standardize on different distributions.

For a real project, check:

* Organization standards
* Supported Java version
* Operating system
* Architecture
* Licensing requirements
* Production compatibility requirements

For learning Maven, a suitable modern JDK is enough, but in professional environments you should follow the project's requirements.

# 30. CPU Architecture Matters Too

Modern systems may use different processor architectures.

Common examples include:

```text
x86_64
amd64
arm64
aarch64
```

For example, newer Apple Silicon Macs use ARM-based processors.

You should install software appropriate for your operating system and processor architecture.

On macOS or Linux, you can inspect architecture with:

```bash
uname -m
```

Possible output:

```text
arm64
```

or:

```text
x86_64
```

# 31. macOS JDK Setup

There are multiple valid ways to install Java on macOS.

A common approach is to use a package manager.

Another is to install a JDK distribution directly.

The exact command depends on the distribution and package manager you choose.

After installation, the important verification steps remain the same:

```bash
java -version
javac -version
```

Then inspect the selected Java installation.

macOS provides a useful utility:

```bash
/usr/libexec/java_home
```

This can report an appropriate Java home.

Run:

```bash
/usr/libexec/java_home
```

You may receive a path to a JDK.

You can then configure:

```bash
export JAVA_HOME=$(/usr/libexec/java_home)
```

For a particular installed Java version, macOS also supports version-selection options through this utility.

The exact version should match the project you intend to build.

---

# 32. Persisting `JAVA_HOME` on macOS With Zsh

If your shell is Zsh, open:

```text
~/.zshrc
```

Add an appropriate configuration such as:

```bash
export JAVA_HOME=$(/usr/libexec/java_home)
export PATH="$JAVA_HOME/bin:$PATH"
```

Save the file.

Reload it:

```bash
source ~/.zshrc
```

Then verify:

```bash
echo $JAVA_HOME
```

and:

```bash
java -version
```

and:

```bash
javac -version
```

Do not copy a version-specific configuration unless you actually have that version installed.

# 33. Finding the Selected Java Executable on macOS or Linux

Use:

```bash
which java
```

This shows the command PATH resolves.

You can also run:

```bash
which javac
```

For more shell-aware command resolution information, many shells support:

```bash
type -a java
```

This can be particularly useful if multiple Java commands are available.

For example:

```text
java is /path/one/java
java is /path/two/java
```

Now you know multiple candidates exist.

# 34. Linux JDK Setup

On Linux, JDK installation often uses the distribution's package manager.

Examples of package-manager families include:

```text
APT
DNF
YUM
```

The exact package name depends on:

* Linux distribution
* Repository
* Required Java version

For example, on a Debian or Ubuntu-based environment, you would typically:

2. Install the appropriate OpenJDK development package.
3. Verify `java`.
4. Verify `javac`.

Check the project's required version first.

# 35. Example Linux Verification

After installation:

```bash
java -version
```

Then:

```bash
javac -version
```

Find the selected executable:

```bash
which java
```

Inspect:

```bash
which javac
```

You may also need to resolve symbolic links to determine the actual installation location.

For example:

```bash
readlink -f "$(which java)"
```

A result may lead to something conceptually similar to:

```text
/usr/lib/jvm/<jdk>/bin/java
```

The JDK root would then be conceptually:

```text
/usr/lib/jvm/<jdk>
```

not:

```text
/usr/lib/jvm/<jdk>/bin/java
```

# 36. Multiple Java Versions on Linux

Linux machines may contain several JDKs.

For example:

```text
Java 17
Java 21
Java 25
```

Some Linux distributions provide an alternatives mechanism for selecting commands.

You may encounter commands such as:

```bash
update-alternatives --config java
```

and possibly:

```bash
update-alternatives --config javac
```

depending on the distribution and permissions.

Be careful.

You want `java`, `javac`, and `JAVA_HOME` to describe a coherent environment.

A problematic environment could look like:

```text
java
→ Java 21

javac
→ Java 17

JAVA_HOME
→ Java 11
```

That is exactly the kind of inconsistency you should detect.

# 37. Windows Java Concepts

Windows uses the same fundamental Java concepts:

```text
JDK
JAVA_HOME
PATH
java
javac
```

But environment-variable syntax differs.

A JDK may be installed under a location similar to:

```text
C:\Program Files\Java\...
```

or another vendor-specific directory.

`JAVA_HOME` should point to the JDK root.

Conceptually:

```text
JAVA_HOME
=
C:\path\to\jdk
```

PATH should include the JDK's:

```text
%JAVA_HOME%\bin
```

Windows uses:

```text
%JAVA_HOME%
```

in many command contexts where Unix-like shells would use:

```text
$JAVA_HOME
```

# 39. PowerShell Environment Variable Syntax

The core concepts are identical even though the shell syntax differs.

# 41. Installing Apache Maven

Maven can be installed in more than one way.

Common approaches include:

1. Downloading an official Maven binary distribution
2. Installing Maven using an operating-system package manager

Both approaches can work.

They differ mainly in who manages the Maven files and updates.

---

# 42. What Is a Maven Binary Distribution?

Maven is distributed as prebuilt binary archives.

Depending on platform and release, you may encounter archive formats such as:

```text
.tar.gz
.zip
```

A binary distribution contains Maven ready to run.

You do not need to compile Maven from source just to use it.

Conceptually:

```text
Maven Binary Archive
        |
        v
Extract
        |
        v
Maven Installation Directory
        |
        +---- bin
        +---- conf
        +---- lib
        +---- other Maven files
```

---

# 43. Binary Distribution Versus Source Distribution

You may encounter:

```text
Binary distribution
```

and:

```text
Source distribution
```

They are different.

A binary distribution is intended for running Maven.

A source distribution contains Maven's source code.

As a Maven user, you normally want the binary distribution.

You are trying to use Maven, not build Maven itself.

---

# 44. Maven Installation Directory

When a Maven binary archive is extracted, it creates a Maven directory.

Conceptually:

```text
apache-maven-x.y.z/
├── bin/
├── boot/
├── conf/
├── lib/
└── ...
```

The exact contents can vary by Maven version.

The most important beginner directories are:

```text
bin
conf
lib
```

---

# 45. Maven `bin` Directory

The `bin` directory contains Maven launch scripts.

Conceptually:

```text
MAVEN_HOME/bin
```

On Unix-like systems, the `mvn` launcher is available there.

If that directory is available through PATH, you can type:

```bash
mvn
```

instead of the complete path.

---

# 46. Maven `conf` Directory

The Maven installation contains global configuration.

An important file is commonly:

```text
conf/settings.xml
```

This is Maven's global settings location for that installation.

Later we will distinguish this from your personal Maven settings.

---

# 47. Maven `lib` Directory

The `lib` directory contains libraries Maven itself needs.

As a beginner, you normally should not manually modify Maven's internal library files.

Your application dependencies do not belong here.

That is an important distinction.

Do not think:

```text
My Java application needs Jackson.
I should copy Jackson into Maven's lib directory.
```

No.

Project dependencies are managed through the Maven project and repositories.

---

# 48. What Is Maven Home?

You may encounter terms or variables such as:

```text
Maven home
MAVEN_HOME
M2_HOME
```

Historically, environment variables such as `M2_HOME` have appeared in Maven setups.

For modern beginner understanding, Maven home refers conceptually to the Maven installation directory.

For example:

```text
/path/to/apache-maven-x.y.z
```

Inside it:

```text
bin/
conf/
lib/
```

Do not confuse Maven's installation directory with:

```text
~/.m2
```

They are completely different things.

# 49. Maven Installation Directory Versus `.m2`

This distinction is extremely important.

## Maven Installation

Contains Maven itself.

Conceptually:

```text
/path/to/apache-maven/
├── bin
├── conf
└── lib
```

## `.m2`

Lives in the user's home directory by default.

Conceptually:

```text
~/.m2/
```

It contains user-specific Maven data.

These are not the same location.

---

# 50. What Is the `.m2` Directory?

By default, Maven uses a directory named:

```text
.m2
```

inside the user's home directory.

On macOS or Linux:

```text
~/.m2
```

On Windows, conceptually:

```text
%USERPROFILE%\.m2
```

This directory commonly contains:

```text
repository/
settings.xml
```

although `settings.xml` may not exist until you create or configure it.

---

# 51. What Is `.m2/repository`?

This is Maven's default local artifact repository.

As Maven downloads dependencies and plugins, artifacts are cached locally.

Conceptually:

```text
Remote Repository
       |
       v
     Maven
       |
       v
~/.m2/repository
       |
       v
Project Build
```

Suppose a project needs a library.

Maven may:

1. Check the local repository.
2. If the artifact is available and acceptable, use it.
3. If not, contact an appropriate remote repository.
4. Download the artifact.
5. Store it locally.
6. Use it during the build.

You will study repository behavior in depth in Part 7.

For now:

```text
~/.m2/repository
=
Maven's default local artifact cache/repository
```

---

# 52. What Is `~/.m2/settings.xml`?

This is the user's Maven settings file.

It can contain user-specific Maven configuration.

Examples include:

* Mirrors
* Proxies
* Repository server definitions
* Credentials references/configuration
* Profiles
* Local repository configuration

This becomes especially important in enterprise environments.

For example:

```text
Developer
   |
   v
~/.m2/settings.xml
   |
   v
Company Artifact Repository
```

Do not place random configuration in this file without understanding what it does.

We will study `settings.xml` properly later.

# 60. Understanding `mvn -version`

A typical result may contain information resembling:

```text
Apache Maven 3.x.x
Maven home: /path/to/maven
Java version: 21.x.x, vendor: ...
Java home: /path/to/jdk
Default locale: ...
Platform encoding: ...
OS name: "...", version: "...", arch: "...", family: "..."
```

Exact wording and values vary.

Let's understand what each category means.

---

# 61. `Apache Maven ...`

Example:

```text
Apache Maven 3.x.x
```

This tells you the Maven version being executed.

This matters because projects, plugins, wrappers, and organizations may require particular Maven versions.

If you expected one Maven version but see another, you may have multiple Maven installations.

---

# 62. `Maven home`

Example:

```text
Maven home: /path/to/maven
```

This tells you where the running Maven installation lives.

This is extremely useful when troubleshooting multiple installations.

Suppose you thought Maven was installed in:

```text
/opt/apache-maven
```

but `mvn -version` reports another directory.

Your shell is not running the Maven installation you thought it was.

---

# 63. `Java version`

Example:

```text
Java version: 21.x.x
```

This tells you which Java version Maven is actually running with.

Do not assume Maven uses the Java version you intended.

Check this line.

If your project requires Java 21 but Maven reports Java 17, you have found an important environment mismatch.

---

# 64. `vendor`

The Java information may include a vendor.

Examples can include various JDK providers.

This tells you which JDK distribution Maven is using.

In some enterprise environments, this matters because the organization standardizes on a particular JDK distribution.

---

# 65. `Java home`

Example:

```text
Java home: /path/to/jdk
```

This shows the Java installation Maven is actually using.

Compare this with:

```bash
echo $JAVA_HOME
```

If they differ unexpectedly, investigate.

Your environment may contain multiple Java installations or launcher behavior you did not anticipate.

---

# 66. Locale

You may see information such as:

```text
Default locale
```

Locale influences language and regional behavior for certain operations.

For most beginner Maven builds, you will not modify this.

But it can matter in some builds involving:

* Locale-sensitive tests
* Generated content
* Date formatting
* Text processing

---

# 67. Platform Encoding

You may see:

```text
Platform encoding
```

Character encoding determines how text characters are represented.

Examples include:

```text
UTF-8
```

Encoding mismatches can create build problems involving:

* Source files
* Resource files
* Generated output
* Tests
* Non-ASCII characters

Modern projects often explicitly standardize encoding to avoid machine-specific behavior.

You will later see Maven properties related to encoding.

# 68. Operating System Information

This helps identify the platform Maven is running on.

Architecture may show values representing:


depending on the system and Java environment.

This can matter when builds involve platform-specific components.

# 72. Maven Configuration Locations

Maven configuration exists at different levels.

Two important levels are:

```text
Global Maven configuration

```

There is also project configuration through:

```text

```

These solve different problems.

# 73. Global Maven Configuration

The Maven installation has a configuration directory.

Conceptually:

```text
MAVEN_HOME/conf/
```

An important file is:

```text
settings.xml
```

Conceptually:

```text
MAVEN_HOME/conf/settings.xml
```

This is global to that Maven installation.

It can affect users running that installation.

On shared or centrally managed systems, global configuration may be controlled by administrators.

---

# 74. User Maven Configuration

The user-level Maven settings file is normally:

```text
~/.m2/settings.xml
```

on Unix-like systems.

On Windows, conceptually:

```text
%USERPROFILE%\.m2\settings.xml
```

This belongs to the individual user's Maven environment.

It can contain settings such as:

* Repository mirrors
* Proxy configuration
* Server configuration
* Profiles

---

# 75. Project Configuration

A Maven project's primary project configuration is:

```text
pom.xml
```

This belongs with the project.

Conceptually:

```text
project/
├── pom.xml
└── src/
```

This is different from:

```text
~/.m2/settings.xml
```

A useful distinction is:

```text
pom.xml
→ describes the project

settings.xml
→ describes Maven's environment or user-specific behavior
```

# 76. User Configuration Versus Global Configuration

Think of Maven configuration layers like this:

```text
Maven Installation
      |
      v
Global settings
      |
      v
User settings
      |
      v
Project POM
      |
      v
Build
```

The exact rules for how individual settings combine can be more detailed, but this gives you the beginner mental model.

# 77. Why User Configuration Is Often Better Than Editing Global Maven Files

Suppose you need configuration specific to your account.

Examples:

* Your proxy
* Your repository credentials
* Your local environment

Editing the global Maven installation may be inappropriate because:

* Other users may use it
* Package-manager updates may replace files
* The configuration may not move with your user environment
* Administrative permissions may be required

User-specific Maven configuration belongs naturally in the user configuration layer.

However, organizations may deliberately manage global settings.

Follow the environment's standards.

# 78. Security Warning About `settings.xml`

Maven settings can involve repository credentials.

Do not casually:

* Commit personal `settings.xml` to Git
* Publish credentials
* Paste passwords into public repositories
* Put production secrets in tutorials
* Hardcode credentials into `pom.xml`

A common dangerous mistake would be:

```text
Git Repository
   |
   v
settings.xml containing real credentials
   |
   v
Public Git Hosting
```

Treat credentials as secrets.

We will cover Maven credential management later.

# 84. Common Error: `mvn: command not found`

You type:

```bash
mvn -version
```

and receive:

```text
mvn: command not found
```

Do not immediately assume Maven is not installed.

Possible causes:

1. Maven is not installed.
2. Maven is installed but not in PATH.
3. PATH changes have not been loaded.
4. You installed Maven in another environment.
5. You opened a shell that does not load the configuration file you edited.
6. The installation is incomplete.

---

# 85. Troubleshooting `mvn: command not found`

Start with:

```bash
which mvn
```

If nothing is returned, the shell cannot currently resolve Maven through PATH.

If you manually installed Maven, inspect its directory.

Suppose Maven exists at:

```text
/opt/apache-maven-x.y.z
```

Check:

```text
/opt/apache-maven-x.y.z/bin
```

Does it contain the Maven launcher?

If yes, inspect:

```bash
echo $PATH
```

Is that `bin` directory included?

If not, PATH is likely the issue.

# 86. Correcting a Maven PATH Problem

Conceptually:

```bash
export PATH="$MAVEN_HOME/bin:$PATH"
```

Then verify:

```bash
which mvn
```

and:


Place the correct configuration in the appropriate shell startup file.

On Unix-like systems.



If these fail, your `JAVA_HOME` may be incorrect.


The problem is Java selection.

# 125. Security and Production Awareness

Even though this is only environment setup, good security habits start now.

## Do Not Run Random Installation Scripts

Understand what you are downloading and from where.

Prefer trusted software sources.

## Do Not Use `sudo` as a Universal Fix

If a command fails because of permissions, understand why.

Running every Maven command with elevated privileges can create ownership problems in:

```text
~/.m2
```

and other project directories.

## Do Not Store Secrets in Shell Configuration Without Understanding the Risk

Files such as:

```text
~/.zshrc
~/.bashrc
~/.m2/settings.xml
```

can contain sensitive information if used carelessly.

Protect credentials appropriately.

## Do Not Commit Personal Maven Settings

A personal settings file may contain information that should not enter source control.

## Do Not Delete `.m2` Every Time a Build Fails

The local repository can sometimes contain a problematic cached artifact, but deleting everything should not be your first troubleshooting action.

Find the actual cause.

# 129. Knowledge Check Answers

## 1. Why does Maven need Java?

Maven itself runs using Java and commonly builds Java projects that require Java development tools.

## 2. What does JDK mean?

Java Development Kit.

## 3. JDK versus JRE concept?

The JRE concept focuses on running Java applications.

The JDK provides the development tools required to build Java applications, including the compiler.

## 4. What does `java -version` tell you?

It reports information about the Java runtime selected when the `java` command is executed.

## 5. What does `javac -version` tell you?

It reports the version of the Java compiler selected by the shell.

## 6. Why check both?

Because successfully running Java does not automatically prove that a suitable Java compiler is available.

## 7. What is an environment variable?

A named value that can provide configuration information to processes.

## 8. What does `JAVA_HOME` represent?

The root location of the intended Java installation, normally a JDK for development.

## 9. Should it point directly to `java`?

No.

It should normally point to the JDK root, not directly to `bin/java`.

## 10. What is PATH?

PATH is a list of directories the shell searches for executable commands.

## 11. Why does PATH order matter?

If several directories contain commands with the same name, the earlier matching directory can determine which command runs.

## 12. What does `which java` show?

It shows which Java executable is selected through command resolution on common Unix-like systems.

## 13. Why install multiple JDKs?

Different projects may require different Java versions.

## 14. Why can multiple JDKs cause problems?

Because `JAVA_HOME`, `java`, `javac`, Maven, the IDE, and CI can accidentally select different JDKs.

## 15. What is a Maven binary distribution?

A prebuilt Maven package intended for running Maven.

## 16. What is Maven home?

The directory containing a Maven installation.

## 17. What is `.m2`?

The default user-specific Maven directory.

## 18. What is `.m2/repository`?

Maven's default local repository where downloaded and locally installed artifacts are stored.

## 19. What is `~/.m2/settings.xml`?

The user's Maven settings file.

## 20. Global versus user settings?

Global settings belong to the Maven installation.

User settings belong to an individual user's Maven environment.

## 21. What does `mvn -version` tell you?

It reports Maven's version and environment information, including Maven home and the Java runtime Maven is using.

## 22. Why check Maven's Java?

Because the Java used by Maven may not be the version you expected.

## 23. Why can IDE and terminal builds differ?

They may use different Maven installations, JDKs, settings, or environment variables.

## 24. Why can local and CI builds differ?

The machines may have different Java versions, Maven versions, configuration, caches, credentials, and environment variables.

## 25. What should you check for `mvn: command not found`?

Check whether Maven exists and whether its executable directory is available through PATH.

## 26. What should you check for incorrect `JAVA_HOME`?

Inspect the variable, verify the directory exists, verify `bin/java` and `bin/javac`, and compare the selected Java with Maven's Java.

## 27. How can multiple Maven installations affect builds?

Different terminals, IDEs, or PATH configurations may execute different Maven versions.

## 28. Why not immediately delete `.m2`?

Because many build failures have nothing to do with the local repository, and deleting it can hide the actual problem while forcing unnecessary downloads.

## 29. Why is `mvn -version` useful after installation?

It is a quick diagnostic snapshot showing which Maven and Java environment is actually active.
