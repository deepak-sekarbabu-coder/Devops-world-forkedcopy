# Part 16: Maven Profiles, Environments and Build Customization

Modern applications rarely operate under one fixed set of conditions.

A developer may build an application on a laptop. A CI pipeline may build the same application for automated testing. Another pipeline may prepare an artifact for staging. Production may require stricter validation or different packaging behavior.

The dangerous solution is to create completely different builds for every environment.

Maven provides profiles so engineers can introduce controlled variations while keeping one primary build model.

This part explains how Maven profiles work, how Maven activates them, where profiles should live, what should vary between environments, and where profiles become dangerous.

By the end, we will build:

```text
Base application
        |
        +-- development configuration
        |
        +-- test configuration
        |
        +-- production-oriented build configuration
```

The important principle throughout this part is:

```text
Profiles should customize a build.

Profiles should not create several unrelated builds hidden inside one POM.
```

---

# 16.1 The Problem Profiles Solve

Suppose VERIQTA has a Java application called:

```text
veriqta-platform
```

Developers need convenient local settings.

The test environment needs predictable test configuration.

Production builds need stricter checks.

A naive approach might create:

```text
pom-development.xml
pom-test.xml
pom-staging.xml
pom-production.xml
```

Then engineers run:

```bash
mvn -f pom-development.xml package
```

or:

```bash
mvn -f pom-production.xml package
```

This quickly becomes difficult to maintain.

A dependency version may be updated in one POM but forgotten in another.

A plugin may behave differently.

One environment may accidentally compile different source code.

Eventually:

```text
development build
        !=
test build
        !=
production build
```

That destroys one of the most valuable properties of a build system:

```text
reproducibility
```

Maven profiles provide a controlled alternative.

---

# 16.2 What Is a Maven Profile?

A Maven profile is a named collection of configuration that can modify parts of Maven's effective build model when the profile is active.

A profile can provide or modify things such as:

```text
properties
dependencies
repositories
plugin repositories
build configuration
plugins
reporting configuration
modules
```

A simple conceptual model is:

```text
Base POM
   |
   +-- profile: development
   |
   +-- profile: test
   |
   +-- profile: production
```

The base POM contains configuration that should apply everywhere.

Profiles contain only configuration that genuinely needs to differ.

For example:

```xml
<profiles>

    <profile>
        <id>development</id>

        <properties>
            <build.environment>development</build.environment>
        </properties>
    </profile>

</profiles>
```

The profile does nothing unless Maven activates it.

---

# 16.3 The `<profiles>` Element

Profiles defined in a project's POM are placed inside:

```xml
<profiles>
```

Each individual profile uses:

```xml
<profile>
```

Example:

```xml
<project>

    ...

    <profiles>

        <profile>
            <id>development</id>

            <properties>
                <build.environment>development</build.environment>
            </properties>
        </profile>

        <profile>
            <id>test</id>

            <properties>
                <build.environment>test</build.environment>
            </properties>
        </profile>

        <profile>
            <id>production</id>

            <properties>
                <build.environment>production</build.environment>
            </properties>
        </profile>

    </profiles>

</project>
```

The structure is:

```text
<profiles>
    |
    +-- <profile>
    |       |
    |       +-- <id>
    |
    +-- <profile>
    |       |
    |       +-- <id>
    |
    +-- <profile>
            |
            +-- <id>
```

---

# 16.4 Profile IDs

Every profile should have an ID.

Example:

```xml
<profile>
    <id>development</id>
</profile>
```

The ID identifies the profile when activating it from the command line.

For example:

```bash
mvn package -Pdevelopment
```

Here:

```text
-P
```

means:

```text
activate the specified Maven profile
```

and:

```text
development
```

is the profile ID.

Use clear profile names.

Good examples:

```text
development
integration-tests
release
production
java-21
native-build
```

Poor examples:

```text
profile1
special
new
temp
stuff
```

A profile name should explain why the build variation exists.

---

# 16.5 Activating Profiles with `-P`

The most explicit way to activate a Maven profile is:

```bash
mvn package -Pdevelopment
```

The general form is:

```bash
mvn <goal-or-phase> -P<profile-id>
```

For example:

```bash
mvn test -Ptest
```

or:

```bash
mvn verify -Pproduction
```

You may also activate multiple profiles.

For example:

```bash
mvn verify -Pproduction,integration-tests
```

Conceptually:

```text
Base POM
   +
production profile
   +
integration-tests profile
   =
effective build configuration
```

Explicit activation is often easier to understand in CI/CD because the pipeline clearly states which profile it requested.

---

# 16.6 Checking Active Profiles

When builds become complicated, engineers need to know which profiles Maven actually activated.

Use:

```bash
mvn help:active-profiles
```

Maven displays profiles that are currently active.

For example:

```text
The following profiles are active:

 - development
```

You can combine the command with explicit activation:

```bash
mvn help:active-profiles -Pproduction
```

This is particularly useful when investigating unexpected behavior.

If a build behaves differently on two machines, check:

```bash
mvn help:active-profiles
```

before assuming the source code is responsible.

---

# 16.7 Understanding Profile Activation

Profiles do not always need to be activated manually.

Maven supports several activation mechanisms.

Important ones include:

```text
explicit activation
default activation
property activation
JDK activation
OS activation
file activation
settings-based activation
```

The activation mechanism matters because it determines when Maven changes the build model.

---

# 16.8 Default Profile Activation

A profile can be active by default.

Example:

```xml
<profile>
    <id>development</id>

    <activation>
        <activeByDefault>true</activeByDefault>
    </activation>

    <properties>
        <build.environment>development</build.environment>
    </properties>
</profile>
```

Now running:

```bash
mvn package
```

can use the development profile without:

```bash
-Pdevelopment
```

This can be convenient for local development.

But default profiles require care.

An engineer may incorrectly assume:

```text
mvn package
```

always means the same thing.

In reality, automatic profile activation can change the effective build.

A useful rule is:

```text
Prefer obvious build behavior over clever automatic behavior.
```

---

# 16.9 Property-Based Activation

A profile can activate when a property exists or matches a particular value.

Example:

```xml
<profile>
    <id>production</id>

    <activation>
        <property>
            <name>environment</name>
            <value>production</value>
        </property>
    </activation>

    <properties>
        <build.environment>production</build.environment>
    </properties>
</profile>
```

Then run:

```bash
mvn package -Denvironment=production
```

Maven sees:

```text
environment=production
```

and activates the profile.

The flow becomes:

```text
-Denvironment=production
        |
        v
property activation
        |
        v
production profile
        |
        v
production-oriented Maven configuration
```

This is useful when a build system already communicates configuration through Maven properties.

---

# 16.10 `-D` Versus `-P`

Beginners often confuse:

```text
-P
```

and:

```text
-D
```

They serve different purposes.

`-P` explicitly activates profiles.

Example:

```bash
mvn package -Pproduction
```

`-D` defines a user property.

Example:

```bash
mvn package -Denvironment=production
```

A profile may then use that property as an activation condition.

So:

```text
-Pproduction
```

means:

```text
activate the profile named production
```

while:

```text
-Denvironment=production
```

means:

```text
define a Maven user property named environment
```

That property may influence plugins, expressions, or profile activation depending on the POM.

---

# 16.11 JDK-Based Activation

Profiles can activate according to the JDK running Maven.

Example:

```xml
<profile>
    <id>java-21</id>

    <activation>
        <jdk>21</jdk>
    </activation>

    <properties>
        <maven.compiler.release>21</maven.compiler.release>
    </properties>
</profile>
```

This may be useful during controlled Java migrations.

For example:

```text
Developer machine
JDK 21
   |
   v
java-21 profile activates
```

However, automatically changing important build behavior according to the local JDK can reduce reproducibility.

If the project requires Java 21, it is often better to enforce that requirement rather than quietly changing the build depending on whatever Java version happens to run Maven.

For example, teams may use Maven Enforcer rules to fail when the wrong JDK is used.

That is often safer than:

```text
wrong JDK
→ different profile
→ different build
```

---

# 16.12 OS-Based Activation

Maven can activate profiles according to operating-system characteristics.

Example:

```xml
<activation>
    <os>
        <family>unix</family>
    </os>
</activation>
```

Other OS criteria can include characteristics such as:

```text
name
family
architecture
version
```

An example profile:

```xml
<profile>
    <id>unix-build</id>

    <activation>
        <os>
            <family>unix</family>
        </os>
    </activation>
</profile>
```

This can help when a genuinely platform-specific tool must run.

But use OS-specific profiles carefully.

A build that silently behaves differently on:

```text
macOS
Linux
Windows
```

may become difficult to reproduce.

For DevOps teams, this becomes especially important because developers may use macOS while CI runners use Linux.

For example:

```text
Developer
macOS
   |
   v
Build succeeds

CI Runner
Linux
   |
   v
Different profile activates
   |
   v
Build fails
```

The root cause may be the profile rather than the application.

---

# 16.13 File-Based Activation

Maven can activate profiles based on whether a file exists or is missing.

Example:

```xml
<activation>
    <file>
        <exists>local-development.properties</exists>
    </file>
</activation>
```

Conceptually:

```text
local-development.properties exists
             |
             v
development profile activates
```

Maven also supports activation based on a missing file.

For example:

```xml
<activation>
    <file>
        <missing>some-file.txt</missing>
    </file>
</activation>
```

This can be useful for specialized local workflows.

However, it can also produce hidden environmental dependencies.

If one developer has:

```text
local-development.properties
```

and another does not, the same Maven command may produce different behavior.

Therefore, file activation should be deliberate and documented.

---

# 16.14 POM Profiles

Profiles can be defined directly in:

```text
pom.xml
```

These are commonly called POM profiles.

Example:

```xml
<profiles>

    <profile>
        <id>development</id>

        <properties>
            <build.environment>development</build.environment>
        </properties>
    </profile>

</profiles>
```

POM profiles travel with the project.

That makes them visible to:

```text
developers
CI systems
build agents
code reviewers
future maintainers
```

This is a major advantage.

If build behavior belongs to the project itself, defining it in the POM often makes the behavior easier to discover and review.

---

# 16.15 Settings Profiles

Profiles can also exist in Maven's:

```text
settings.xml
```

A user's Maven settings commonly live at:

```text
~/.m2/settings.xml
```

A settings profile might look like:

```xml
<settings>

    <profiles>

        <profile>
            <id>company-repository</id>

            <properties>
                <repository.environment>internal</repository.environment>
            </properties>
        </profile>

    </profiles>

</settings>
```

Settings profiles are useful for configuration tied to a developer, machine, organization, or Maven installation rather than project source.

This distinction matters.

Think:

```text
pom.xml
    |
    +-- project build behavior

settings.xml
    |
    +-- user or environment-specific Maven configuration
```

Repository credentials, for example, should not be committed into a POM.

---

# 16.16 Activating Profiles from `settings.xml`

`settings.xml` can define active profiles.

Example:

```xml
<settings>

    <activeProfiles>
        <activeProfile>company-repository</activeProfile>
    </activeProfiles>

</settings>
```

Now Maven can automatically activate:

```text
company-repository
```

for that Maven environment.

This can be useful in enterprise environments.

But it creates an important troubleshooting question:

```text
Is the build behavior coming from the repository,
or from this machine's Maven settings?
```

Again:

```bash
mvn help:active-profiles
```

helps answer that question.

---

# 16.17 Properties Inside Profiles

Profiles commonly define properties.

Example:

```xml
<profile>
    <id>development</id>

    <properties>
        <build.environment>development</build.environment>
        <debug.enabled>true</debug.enabled>
    </properties>
</profile>
```

Another profile can provide different values:

```xml
<profile>
    <id>production</id>

    <properties>
        <build.environment>production</build.environment>
        <debug.enabled>false</debug.enabled>
    </properties>
</profile>
```

Elsewhere in the POM, those properties can be referenced using:

```text
${property.name}
```

For example:

```xml
${build.environment}
```

This creates a controlled substitution mechanism.

---

# 16.18 Build-Time Configuration Versus Runtime Configuration

This distinction is essential.

A Maven profile affects the build.

But many application environment differences belong at runtime.

Consider:

```text
database host
database password
API endpoint
log level
feature flag
service URL
cloud credentials
```

These values often should not require rebuilding the application.

A stronger architecture is:

```text
Source Code
    |
    v
Maven Build
    |
    v
Application Artifact
    |
    +--------------------+
    |                    |
    v                    v
Staging              Production
runtime config       runtime config
```

The artifact remains substantially the same.

The environment supplies runtime configuration.

This supports:

```text
build once
promote the same artifact
```

which is usually preferable to:

```text
build staging artifact
build another production artifact
hope they are equivalent
```

---

# 16.19 Development Configuration

Let's create the first profile for our example application.

```xml
<profile>
    <id>development</id>

    <properties>
        <build.environment>development</build.environment>
        <tests.skip>false</tests.skip>
        <build.debug>true</build.debug>
    </properties>
</profile>
```

Activate it:

```bash
mvn clean package -Pdevelopment
```

This tells Maven:

```text
clean previous build output
activate development
execute package lifecycle
```

Development-oriented configuration may prioritize:

```text
fast feedback
debug information
developer convenience
local integration
```

But it should not completely redefine how the application works.

---

# 16.20 Test Configuration

Now create a test-oriented profile.

```xml
<profile>
    <id>test</id>

    <properties>
        <build.environment>test</build.environment>
        <tests.skip>false</tests.skip>
        <integration.tests.enabled>true</integration.tests.enabled>
    </properties>
</profile>
```

Run:

```bash
mvn clean verify -Ptest
```

Notice that we use:

```text
verify
```

rather than simply:

```text
package
```

because integration-test workflows commonly extend into later lifecycle phases.

The conceptual pipeline becomes:

```text
compile
   |
   v
unit tests
   |
   v
package
   |
   v
integration testing
   |
   v
verify
```

---

# 16.21 Staging Configuration

Staging should resemble production as closely as practical.

A staging profile might contain build-related configuration such as:

```xml
<profile>
    <id>staging</id>

    <properties>
        <build.environment>staging</build.environment>
        <tests.skip>false</tests.skip>
        <strict.validation>true</strict.validation>
    </properties>
</profile>
```

Run:

```bash
mvn clean verify -Pstaging
```

But be careful.

You do not want:

```text
staging source code
```

and:

```text
production source code
```

to become separate implementations.

Staging should help validate what will eventually run in production.

---

# 16.22 Production-Oriented Build Configuration

Now create a production-oriented profile.

```xml
<profile>
    <id>production</id>

    <properties>
        <build.environment>production</build.environment>
        <tests.skip>false</tests.skip>
        <strict.validation>true</strict.validation>
        <build.debug>false</build.debug>
    </properties>
</profile>
```

Run:

```bash
mvn clean verify -Pproduction
```

The important phrase is:

```text
production-oriented build
```

not necessarily:

```text
production configuration
```

Maven can prepare and validate an artifact intended for production.

Actual production credentials and operational secrets should come from secure deployment/runtime systems.

---

# 16.23 What Should Vary Between Environments?

Profiles work best when the differences are genuinely build-related.

Reasonable differences might include:

```text
additional validation
integration-test execution
code-generation options
packaging behavior
debug metadata
special build plugins
release checks
environment-specific build metadata
```

For example:

```text
development
→ faster developer feedback

test
→ additional test execution

production
→ stricter validation
```

The underlying application should remain recognizable as the same application.

---

# 16.24 What Should Not Vary?

Be suspicious when profiles start changing:

```text
core business logic
fundamental source behavior
security rules
dependency versions without strong justification
large dependency sets
application architecture
database credentials
cloud credentials
API secrets
private keys
production passwords
```

For example, this design is dangerous:

```text
development profile
→ library version 1

test profile
→ library version 2

production profile
→ library version 3
```

Now you are not really testing the same application that you deploy.

Similarly:

```text
development
→ secure authentication disabled

production
→ completely different authentication system
```

creates a dangerous testing gap.

---

# 16.25 Why Secrets Should Never Live in Profiles

Never do this:

```xml
<profile>
    <id>production</id>

    <properties>
        <database.password>SuperSecretPassword123</database.password>
        <api.key>abc123secret</api.key>
    </properties>
</profile>
```

If the POM enters Git:

```text
secret
  |
  v
Git commit
  |
  v
repository history
  |
  +-- developer clones
  +-- CI logs
  +-- forks
  +-- backups
  +-- caches
```

Deleting the current line later does not reliably erase the secret from Git history or every system that copied it.

Secrets belong in dedicated secret-management mechanisms.

Examples include:

```text
CI/CD secret stores
cloud secret managers
Vault
Kubernetes Secrets combined with appropriate encryption and access controls
runtime environment injection
credential stores
```

Maven's:

```text
settings.xml
```

is also commonly used for Maven repository authentication, rather than putting repository credentials directly in `pom.xml`.

The core principle is:

```text
POM
→ describes the build

Secret system
→ provides credentials securely
```

---

# 16.26 Environment Variables and Maven

CI systems frequently expose configuration through environment variables.

Maven can reference environment variables using:

```text
${env.VARIABLE_NAME}
```

For example:

```xml
${env.BUILD_NUMBER}
```

But the ability to reference an environment variable does not automatically make every use safe.

Be particularly careful with secrets.

Passing secrets through Maven can expose them through:

```text
debug output
plugin configuration
generated files
process arguments
build logs
artifacts
```

Whenever possible, credentials should only be exposed to the process that genuinely requires them.

# 16.27 A Better Environment Strategy

A mature application often separates concerns like this:

```text
                    Source
                      |
                      v
                  Maven Build
                      |
                      v
                  Artifact
                      |
          +-----------+-----------+
          |           |           |
          v           v           v
         Dev        Staging     Production
          |           |           |
          v           v           v
      Runtime       Runtime     Runtime
      Config        Config      Config
```

The build artifact remains consistent.

Environment-specific operational configuration arrives later.

For example:

```text
DATABASE_URL
API_ENDPOINT
LOG_LEVEL
FEATURE_FLAGS
SERVICE_DISCOVERY
CREDENTIALS
```

may be supplied during deployment or runtime.

This dramatically improves confidence when promoting artifacts.

# 16.28 Build Once, Deploy Many

Consider two pipelines.

### Pipeline A

```text
Git commit
   |
   +-- build development artifact
   |
   +-- build staging artifact
   |
   +-- build production artifact
```

Three builds may produce three subtly different outputs.

Now consider:

### Pipeline B

```text
Git commit
   |
   v
Build
   |
   v
Test
   |
   v
Artifact
   |
   +-- deploy to test
   |
   +-- promote to staging
   |
   +-- promote to production
```

Pipeline B gives stronger artifact consistency.

You know that the artifact reaching production is the artifact that passed earlier validation.

This is why Maven profiles should not become a substitute for proper deployment configuration.

---

# 16.29 Profile Misuse

Profiles are powerful enough to create bad architectures.

One common misuse is excessive environment profiles:

```text
dev
dev2
qa
qa2
qa-special
staging
staging-new
production
production-old
production-hotfix
customer-a
customer-b
customer-c
```

Then the POM becomes hundreds or thousands of lines of conditional behavior.

Another misuse is hiding major dependency differences inside profiles.

For example:

```xml
<profile>
    <id>production</id>

    <dependencies>
        <!-- huge production-only dependency graph -->
    </dependencies>
</profile>
```

Now:

```text
mvn test
```

may not test the dependency graph that production uses.

That weakens confidence in the build.

---

# 16.30 The Profile Explosion Problem

Imagine a project supporting:

```text
4 environments
3 operating systems
3 Java versions
2 database types
```

If profiles represent every combination, engineers may effectively face:

```text
4 × 3 × 3 × 2 = 72
```

possible build combinations.

Testing every combination becomes difficult.

This is configuration explosion.

The solution is not simply more profiles.

Instead, separate concerns.

```text
Build concerns
→ Maven

Deployment concerns
→ deployment tooling

Secrets
→ secret management

Runtime configuration
→ application/environment configuration

Infrastructure differences
→ infrastructure tooling
```

---

# 16.31 Reproducibility Concerns

A reproducible build should produce equivalent results when given equivalent:

```text
source
dependencies
build configuration
toolchain
inputs
```

Profiles introduce another input:

```text
active profile
```

Automatic activation introduces even more hidden inputs:

```text
operating system
JDK
files
properties
settings.xml
```

Consider:

```bash
mvn clean package
```

Developer A gets one result.

Developer B gets another.

Why?

Possible explanation:

```text
Developer A
→ JDK 21
→ java-21 profile activated

Developer B
→ JDK 17
→ profile not activated
```

Or:

```text
Developer A
→ local file exists
→ local profile activated

CI
→ file missing
→ profile inactive
```

This is why implicit activation should be used carefully.

---

# 16.32 Debugging Profile Problems

Suppose the application builds locally but fails in CI.

Start by checking active profiles:

```bash
mvn help:active-profiles
```

Then inspect the effective POM:

```bash
mvn help:effective-pom
```

You can also compare:

```bash
mvn help:effective-pom -Pdevelopment
```

with:

```bash
mvn help:effective-pom -Pproduction
```

This helps reveal what Maven actually sees after:

```text
parent inheritance
profile activation
property resolution
plugin configuration
dependency management
```

A useful troubleshooting sequence is:

```text
Symptom
   |
   v
Check active profiles
   |
   v
Check effective POM
   |
   v
Check properties
   |
   v
Check settings.xml
   |
   v
Check JDK and OS
   |
   v
Check activation conditions
   |
   v
Compare CI and local environments
```

# 16.33 Building the VERIQTA Example

Project:

```text
veriqta-environment-demo/
├── pom.xml
└── src/
    └── main/
        └── java/
            └── com/
                └── veriqta/
                    └── App.java
```

Create the directories:

```bash
mkdir -p veriqta-environment-demo/src/main/java/com/veriqta
```

Move into the project:

```bash
cd veriqta-environment-demo
```

---

# 16.34 Create the Java Application

Create:

```text
src/main/java/com/veriqta/App.java
```

Add:

```java
package com.veriqta;

public class App {

    public static void main(String[] args) {
        System.out.println("VERIQTA application started.");
    }
}
```

Notice something important.

We are not creating:

```text
AppDevelopment.java
AppTest.java
AppProduction.java
```

We have one application.

Environment differences should remain controlled.

---

# 16.35 Create the Base POM

Create:

```text
pom.xml
```

with:

```xml
<?xml version="1.0" encoding="UTF-8"?>

<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="
             http://maven.apache.org/POM/4.0.0
             https://maven.apache.org/xsd/maven-4.0.0.xsd">

    <modelVersion>4.0.0</modelVersion>

    <groupId>com.veriqta</groupId>
    <artifactId>veriqta-environment-demo</artifactId>
    <version>1.0.0-SNAPSHOT</version>

    <properties>
        <maven.compiler.release>21</maven.compiler.release>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>

        <build.environment>base</build.environment>
        <tests.skip>false</tests.skip>

The base configuration defines safe defaults.

Profiles will override only selected properties.

                <build.debug>true</build.debug>

```

There is one small typo to catch deliberately before running it. This line:

```xml
<project.build.sourceEncoding>UTF-8</project.sourceEncoding>
```

must have matching opening and closing element names.

Correct it to:

```xml
<project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
```

This is a useful reminder that Maven POMs are XML, so malformed element names will stop Maven before profile logic even matters.

# 16.42 A CI/CD Example

Imagine a pipeline receives this commit:

```text
abc123
```

A weaker design might do:

```text
Commit abc123
   |
   +-- mvn package -Ptest
   |       |
   |       v
   |   artifact A
   |
   +-- mvn package -Pstaging
   |       |
   |       v
   |   artifact B
   |
   +-- mvn package -Pproduction
           |
           v
       artifact C
```

Production artifact C was not literally the artifact tested earlier.

A stronger model is:

```text
Commit abc123
      |
      v
mvn clean verify
      |
      v
Artifact A
      |
      v
Artifact Repository
      |
      +-- Test
      |
      +-- Staging
      |
      +-- Production
```

Environment configuration is supplied during deployment.

That gives engineers a much stronger statement:

```text
The exact artifact running in production is the artifact we tested.
```

# 16.43 Profiles in Multi-Module Projects

Profiles become even more important after the multi-module concepts from Part 15.

Suppose:

```text
veriqta-platform
├── common-library
├── application-core
├── application-service
└── application-web
```

The parent POM may define shared profiles.

For example:

```xml
<profiles>

    <profile>
        <id>production</id>

        <properties>
            <strict.validation>true</strict.validation>
        </properties>
    </profile>

</profiles>
```

Child projects can inherit appropriate profile configuration through the parent relationship.

This allows organizations to centralize legitimate build differences rather than copying profile definitions into every module.

But do not use this as an excuse to build a huge parent POM full of environment-specific conditions.

# 16.44 Profile Activation Troubleshooting Scenario

Suppose a developer reports:

```text
The production build works on my MacBook,
but it fails on the Linux CI runner.
```

Do not immediately change code.

First reproduce the build command:

```bash
mvn clean verify -Pproduction
```

Then inspect active profiles:

```bash
mvn help:active-profiles -Pproduction
```

Check Maven:

```bash
mvn -version
```

This reveals information including:

```text
Maven version
Java version
Java home
OS
architecture
```

Then inspect:

```bash
mvn help:effective-pom -Pproduction
```

Compare the environments.

Possible root cause:

```text
Symptom
Production build fails only in CI

State
Local = macOS + JDK 21
CI = Linux + JDK 17

Hypothesis
An automatically activated profile changes configuration

Diagnostic
mvn help:active-profiles

Finding
java-21 profile active locally
not active in CI

Fix
standardize the JDK and enforce the required toolchain

Verify
run the same build in both environments
```

That is production-oriented Maven troubleshooting.

# 16.45 Profile Design Rules

When creating a Maven profile, ask these questions.

1. Is this difference really a build concern?

2. Could runtime configuration solve the problem instead?

3. Will developers know when this profile is active?

4. Does the profile change dependencies?

5. Does it change what is tested?

6. Could it make local and CI builds different?

7. Does it contain credentials?

8. Can the resulting build still be reproduced?

9. Could the same artifact be promoted instead?

10. Is the profile solving a real problem or hiding configuration debt?

These questions prevent profiles from becoming configuration dumping grounds.

# 16.46 Recommended Responsibility Boundaries

A useful engineering model is:

| Concern                           | Better Location                        |
| --------------------------------- | -------------------------------------- |
| Java compiler configuration       | Maven                                  |
| Dependency versions               | Maven                                  |
| Build plugins                     | Maven                                  |
| Integration-test build behavior   | Maven                                  |
| Packaging                         | Maven                                  |
| Build validation                  | Maven                                  |
| Repository configuration          | Maven settings / repository management |
| Database password                 | Secret manager                         |
| API credentials                   | Secret manager                         |
| Kubernetes replica count          | Deployment configuration               |
| Production hostname               | Runtime/deployment configuration       |
| Cloud infrastructure              | Infrastructure as Code                 |
| Feature flags                     | Runtime feature-management system      |
| Application environment variables | Deployment/runtime configuration       |

The exact architecture varies, but the separation principle remains valuable.

# 16.47 Common Profile Mistakes

### Mistake 1: Putting secrets in the POM

Wrong:

```xml
<database.password>secret123</database.password>
```

Better:

```text
retrieve/inject secrets through an appropriate secret-management mechanism
```

### Mistake 2: Creating a profile for everything

Wrong:

```text
dev-local
dev-cloud
test-local
test-cloud
staging-blue
staging-green
prod-blue
prod-green
```

Profiles should not become an environment-management platform.

### Mistake 3: Different dependencies everywhere

If production uses dependencies that tests never see, your tests may provide false confidence.

### Mistake 4: Excessive automatic activation

A command like:

```bash
mvn package
```

should not produce mysterious results depending on hidden files and machine characteristics unless there is a strong reason.

### Mistake 5: Using profiles instead of deployment configuration

Changing:

```text
database URL
API endpoint
production credentials
Kubernetes namespace
```

does not necessarily require rebuilding the Java application.

# 16.48 Production Principle: Keep Builds Boring

Reliable build systems should be predictable.

An engineer should be able to understand:

```text
source
+
POM
+
declared inputs
=
artifact
```

without discovering dozens of hidden conditions.

Profiles are valuable when they make intentional differences explicit.

They become dangerous when they create:

```text
hidden builds
implicit environments
dependency drift
secret leakage
untested production behavior
machine-specific artifacts
```

A healthy Maven project usually has a relatively small number of clearly justified profiles.

# 16.51 What You Should Understand Now

You should now understand that a Maven profile is not simply an "environment file."

It is a mechanism for modifying Maven's effective build configuration under controlled conditions.

Profiles can be:

```text
defined in pom.xml
defined in settings.xml
activated explicitly with -P
activated by properties
activated by JDK
activated by OS
activated by files
activated by default
```

You should also understand the architectural warning:

```text
Just because Maven can vary something
does not mean Maven should vary it.
```

The strongest build systems minimize unnecessary differences.

A mature pipeline aims for:

```text
one source revision
        |
        v
one controlled build
        |
        v
one tested artifact
        |
        v
promote through environments
```

rather than:

```text
one source revision
        |
        +-- development build
        +-- test build
        +-- staging build
        +-- production build
             |
             v
       "hopefully identical"
```

Profiles are therefore best used for controlled build customization, not as a replacement for runtime configuration, deployment systems, or secret management.

With profiles understood, Maven is no longer just compiling Java and downloading dependencies. It is becoming a controlled part of a larger software delivery system.
