# Part 12: Resources, Properties, Configuration Files and Filtering

## Introduction

So far, our Maven project has mostly focused on Java source code.

But real applications contain much more than `.java` files.

A Java application might need:

```text
application.properties
application.yml
logging.xml
config.json
messages.properties
templates/
static/
certificates/
SQL files
text files
```

These files are not Java source code, but the application may still need them while it runs.

Maven calls many of these files resources.

In this part, we will extend:

```text
veriqta-maven-app
```

so the application contains real configuration files, processes them correctly, copies them into the build output, packages them into the JAR, and loads them from the Java classpath.

You will also learn Maven resource filtering.

Filtering allows Maven to take something like:

```properties
app.name=${project.name}
app.version=${project.version}
```

and produce:

```properties
app.name=VERIQTA Maven Application
app.version=1.0.0
```

during the build.

But filtering introduces an important boundary.

Maven can substitute configuration values.

Maven is not a secrets-management system.

By the end of this part, you should understand this flow:

```text
src/main/resources
        |
        v
Maven Resources Plugin
        |
        +---- copy
        |
        +---- optionally filter
        |
        v
target/classes
        |
        v
Package
        |
        v
JAR
        |
        v
Application loads resource from classpath
```

---

# 1. What Is a Maven Resource?

A resource is generally a non-Java file that belongs to the project and needs to participate in the build or become available to the application.

Examples include:

```text
.properties
.yml
.yaml
.json
.xml
.txt
.html
.css
.js
.sql
.csv
```

as well as images, templates, certificates, localization files, and other application assets.

For example:

```text
src/main/resources/application.properties
```

might contain:

```properties
app.name=VERIQTA Maven Application
app.environment=development
```

The Java compiler does not compile this file into bytecode.

Instead, Maven normally copies it into the application's output.

---

# 2. Java Source Versus Resources

Keep these two paths separate.

Java source:

```text
src/main/java
```

Resources:

```text
src/main/resources
```

Java source follows:

```text
.java
 |
 v
Java Compiler
 |
 v
.class
```

Resources normally follow:

```text
.properties / .yml / .json / .xml / etc.
 |
 v
Resource Processing
 |
 v
Copied Resource
```

Eventually they meet:

```text
target/classes/
```

For example:

```text
target/classes/
├── com/
│   └── veriqta/
│       └── app/
│           └── App.class
└── application.properties
```

Both can then be packaged into the JAR.

---

# 3. Why Applications Need Resources

Suppose this Java code contains everything directly:

```java
public class App {

    public static void main(String[] args) {
        String applicationName = "VERIQTA Maven Application";
        String environment = "development";
        int port = 8080;

        System.out.println(applicationName);
        System.out.println(environment);
        System.out.println(port);
    }
}
```

This works.

But configuration is now hardcoded into Java source.

Changing:

```text
8080
```

to:

```text
9090
```

requires changing source code and rebuilding.

A resource file can separate some configuration from program logic:

```properties
app.name=VERIQTA Maven Application
app.environment=development
app.port=8080
```

Now we have:

```text
Java code
→ application behavior

Configuration
→ values used by that behavior
```

That separation is useful, although where configuration should live depends on whether the value is intended to be fixed at build time or supplied at runtime.

We will make that distinction carefully later.

---

# 4. Maven's Standard Main Resource Directory

Maven's standard directory for main application resources is:

```text
src/main/resources
```

Our project can now look like:

```text
veriqta-maven-app/
├── pom.xml
├── src/
│   ├── main/
│   │   ├── java/
│   │   │   └── com/
│   │   │       └── veriqta/
│   │   │           └── app/
│   │   │               └── App.java
│   │   └── resources/
│   │       └── application.properties
│   └── test/
│       ├── java/
│       └── resources/
└── target/
```

This follows Maven's convention-over-configuration approach.

Maven already knows that:

```text
src/main/resources
```

is normally the main resource directory.

---

# 5. `src/main/resources`

Files under:

```text
src/main/resources
```

are normally application resources.

Examples:

```text
src/main/resources/
├── application.properties
├── config.yml
├── logging.xml
├── messages.properties
├── banner.txt
└── templates/
    └── welcome.html
```

During the build, Maven normally processes and copies these resources into:

```text
target/classes/
```

while preserving their relative structure.

---

# 6. Resource Copying

Suppose we have:

```text
src/main/resources/application.properties
```

Maven normally copies it to:

```text
target/classes/application.properties
```

Suppose we have:

```text
src/main/resources/config/database.properties
```

Maven normally copies it to:

```text
target/classes/config/database.properties
```

The relative path is preserved.

Mental model:

```text
src/main/resources
        |
        v
process-resources
        |
        v
target/classes
```

# 7. Why `target/classes` Contains More Than `.class` Files

The name:

```text
target/classes
```

can make beginners think:

> This directory contains only compiled Java classes.

It does not.

It is the main output directory used for application classes and processed resources.

You might see:

```text
target/classes/
├── com/
│   └── veriqta/
│       └── app/
│           ├── App.class
│           └── ConfigLoader.class
├── application.properties
├── config.yml
└── templates/
    └── welcome.html
```

Therefore:

```text
target/classes
=
compiled application classes
+
processed application resources
```

# 8. Which Lifecycle Phase Processes Resources?

Recall the default lifecycle.

A simplified section is:

```text
validate
    |
    v
generate-sources
    |
    v
process-sources
    |
    v
generate-resources
    |
    v
process-resources
    |
    v
compile
```

Main application resources are normally processed during:

```text
process-resources
```

This occurs before:

```text
compile
```

# 10. Resources Continue Into Later Phases

Because Maven executes earlier phases when a later phase is requested:

```bash

```

```text

        |
        v

        |
        v

        |
        v

        |
        v

        |
        v

        |

```

# 11. The Maven Resources Plugin

Maven uses plugins to perform build work.

Resource processing is primarily handled by:

```text
Maven Resources Plugin
```

Its artifact ID is:

```text
maven-resources-plugin
```

The plugin performs tasks including copying project resources into build output directories.

Conceptually:

```text
Maven lifecycle
      |
      v
process-resources
      |
      v
Maven Resources Plugin
      |
      v
resources:resources
      |
      v
target/classes
```

---

# 12. Plugin Goal for Main Resources

The relevant goal for main resources is:

```text
resources:resources
```

You can think of it as:

```text
plugin prefix : goal
```

Therefore:

```text
resources
:
resources
```

means:

```text
Maven Resources Plugin
→ process/copy main project resources
```

The lifecycle normally invokes this automatically.



# 16. Why Separate Main and Test Resources?

Suppose your test uses:

```text
src/test/resources/fake-payment-response.json
```

That file exists only to support testing.

You probably do not want it in the production JAR.

Keeping it under:

```text
src/test/resources
```

allows Maven to make it available to tests without treating it as a normal application resource.

This separation gives us:

```text
Production resources
→ src/main/resources

Test-only resources
→ src/test/resources
```

# 18. Properties Files

A Java properties file is a common key-value configuration format.

Example:

```properties
app.name=VERIQTA Maven Application
app.version=1.0.0
app.port=8080
app.environment=development
```

The basic mental model is:

```text
key=value
```

For example:

```text
app.port
```

is the key.

```text
8080
```

is the value.

---

# 19. Why Properties Files Are Common

Properties files are simple and well supported by Java.

They can be used for:

* Application settings
* Feature settings
* Build metadata
* Messages
* Framework configuration
* Logging configuration
* Environment-related defaults

However, not every value belongs inside a packaged properties file.

Secrets require special handling, which we will cover later.

# 20. YAML Files

YAML is another common configuration format.

Example:

```yaml
app:
  name: VERIQTA Maven Application
  environment: development
  server:
    port: 8080
```

YAML uses indentation to express structure.

The hierarchy above is:

```text
app
├── name
├── environment
└── server
    └── port
```

YAML is common in technologies such as:

* Spring-based applications
* Kubernetes
* CI/CD systems
* Infrastructure tooling
* Application configuration systems

Maven itself does not automatically understand the business meaning of every YAML file.

It can still copy that YAML file as a resource.

---

# 21. YAML Indentation Matters

This:

```yaml
app:
  server:
    port: 8080
```

is structurally different from incorrectly indented YAML.

Beginners should remember:

```text
YAML structure depends heavily on indentation.
```

Do not use tabs casually in YAML configuration.

The parser used by the application determines whether the YAML is valid.

Maven resource copying alone does not prove that the YAML content is semantically correct.

# 26. What Is the Java Classpath?

The classpath tells Java where it can find classes and resources required by an application.

In Part 11, you saw the classpath in relation to dependency classes.

The classpath also matters for resources.

Conceptually:

```text
Java Runtime
     |
     v
Classpath
     |
     +---- Application classes
     |
     +---- Dependency classes
     |
     +---- Application resources
```

When resources are copied into:

```text
target/classes
```

they can become classpath resources.

---

# 27. What Is a Classpath Resource?

A classpath resource is a non-class file available through locations on the application's classpath.

Suppose:

```text
src/main/resources/application.properties
```

becomes:

```text
target/classes/application.properties
```

When:

```text
target/classes
```

is on the classpath, the application can request:

```text
application.properties
```

as a classpath resource.

After packaging, the resource may also live inside the JAR.

---

# 28. Filesystem Path Versus Classpath Resource

This distinction is essential.

Filesystem path:

```text
/Users/ann/veriqta/config/application.properties
```

means:

> Find this file at this location on the operating system filesystem.

Classpath resource:

```text
application.properties
```

means:

> Search the application's classpath for a resource with this name.

These are different lookup models.

---

# 29. Why Hardcoded Filesystem Paths Are Problematic

Suppose Java contains:

```java
new FileInputStream("/Users/ann/veriqta/application.properties");
```

It may work on one MacBook.

But on a Linux server:

```text
/Users/ann/
```

may not exist.

Inside a container:

```text
/Users/ann/
```

probably does not exist either.

The application becomes tied to one filesystem layout.

Classpath resources can be useful when configuration or assets are intentionally packaged with the application.

---

# 30. Loading a Classpath Resource in Java

Java's class-loading APIs can retrieve classpath resources.

Example:

```java
package com.veriqta.app;

import java.io.IOException;
import java.io.InputStream;
import java.util.Properties;

public class App {

    public static void main(String[] args) throws IOException {

        Properties properties = new Properties();

        try (InputStream input =
                     App.class.getClassLoader()
                              .getResourceAsStream("application.properties")) {

            if (input == null) {
                throw new IllegalStateException(
                    "application.properties was not found on the classpath"
                );
            }

            properties.load(input);
        }

        System.out.println(properties.getProperty("app.name"));
        System.out.println(properties.getProperty("app.environment"));
    }
}
```

Do not worry about memorizing every Java API call.

Focus on the resource flow.

---

# 31. Understanding the Resource-Loading Code

This:

```java
App.class.getClassLoader()
```

obtains the class loader associated with the application class.

Then:

```java
.getResourceAsStream("application.properties")
```

asks for a classpath resource named:

```text
application.properties
```

If Maven copied:

```text
src/main/resources/application.properties
```

to:

```text
target/classes/application.properties
```

the resource can be found when the relevant classes directory is on the classpath.

---

# 32. Why Check for `null`?

This:

```java
getResourceAsStream(...)
```

can return:

```text
null
```

if the resource cannot be found.

Without checking, later code may fail in a less understandable way.

Therefore:

```java
if (input == null) {
    throw new IllegalStateException(
        "application.properties was not found on the classpath"
    );
}
```

gives a clearer error.

This is a good troubleshooting habit:

```text
Fail clearly
rather than
fail mysteriously later.
```

---

# 33. Resource Path Example

Suppose your resource is:

```text
src/main/resources/config/application.properties
```

After processing:

```text
target/classes/config/application.properties
```

The classpath resource name becomes:

```text
config/application.properties
```

Therefore:

```java
.getResourceAsStream("config/application.properties")
```

may be appropriate.

Not:

```text
src/main/resources/config/application.properties
```

because that is the source-tree path, not the packaged classpath resource path.

# 37. Resource Filtering

Copying is only one thing Maven can do with resources.

Maven can also perform resource filtering.

Filtering means Maven reads placeholders in resource files and replaces them with values during the build.

Suppose:

```properties
app.name=${project.name}
app.version=${project.version}
```

During filtering, Maven can turn this into:

```properties
app.name=VERIQTA Maven Application
app.version=1.0.0
```

This is build-time substitution.

---

# 38. Copying Versus Filtering

Without filtering:

```text
Source resource
app.version=${project.version}
        |
        v
Copy
        |
        v
Output resource
app.version=${project.version}
```

With filtering:

```text
Source resource
app.version=${project.version}
        |
        v
Maven resolves project.version
        |
        v
Output resource
app.version=1.0.0
```

That difference is critical.

---

# 39. Filtering Is Not Enabled for Everything Automatically

Do not assume every:

```text
${...}
```

inside every resource is automatically replaced.

Filtering must be configured appropriately for the resource set.

For example:

```xml
<build>
    <resources>
        <resource>
            <directory>src/main/resources</directory>
            <filtering>true</filtering>
        </resource>
    </resources>
</build>
```

This tells Maven to treat the main resource directory as filtered resources.

---

# 40. Understanding `<resources>`

This:

```xml
<resources>
```

defines the resource sets used by the build.

Inside it:

```xml
<resource>
```

describes one resource set.

Then:

```xml
<directory>src/main/resources</directory>
```

tells Maven where the resource files live.

Finally:

```xml
<filtering>true</filtering>
```

enables filtering for that resource set.


# 45. What `${...}` Means

In Maven contexts, expressions often use:

```text
${property.name}
```

For example:

```text
${project.version}
```

means:

> Resolve the value represented by `project.version`.

And:

```text
${app.environment}
```

means:

> Resolve the Maven property named `app.environment`.

The exact available expression sources depend on context and Maven configuration.

Do not assume every arbitrary name has a value.

---

# 46. Unresolved Properties

Suppose:

```properties
app.region=${app.region}
```

but Maven has no value for:

```text
app.region
```

The placeholder may remain unresolved or otherwise behave according to the plugin/configuration involved.

If you see:

```properties
app.region=${app.region}
```

inside:

```text
target/classes
```

ask:

```text
Was filtering enabled?

Does the property exist?

Did I spell the property correctly?

Am I inspecting the generated file or the source file?

Is this resource included in the filtered resource set?
```

# 47. Command-Line Properties

Maven properties can also be supplied from the command line using:

```text
-D
```

For example:

```bash
mvn package -Dapp.environment=staging
```

Here:

```text
-D
```

defines a Java system property for the Maven process, which Maven commonly exposes for property resolution.

The supplied value is:

```text
app.environment=staging
```

A filtered resource using:

```properties
app.environment=${app.environment}
```

can therefore receive:

```properties
app.environment=staging
```

depending on the project's filtering configuration and property precedence.

# 48. Build-Time Substitution

This process occurs while Maven builds the application.

Example:

```text
Source:
app.environment=${app.environment}

Build command:
mvn package -Dapp.environment=staging

Filtered artifact:
app.environment=staging
```

This is called build-time substitution.

The important word is:

```text
build-time
```

The value is inserted before the final artifact is produced.

---

# 49. Build-Time Configuration Versus Runtime Configuration

This distinction is extremely important for DevOps.

Build-time configuration:

```text
Source
    |
    v
Maven Build
    |
    +---- value inserted
    |
    v
Artifact
```

Runtime configuration:

```text
Artifact
    |
    v
Application starts
    |
    +---- environment provides value
    |
    v
Running application
```

These are not the same model.

---

# 50. Example of Build-Time Configuration

Suppose:

```properties
app.environment=${app.environment}
```

and:

```bash
mvn package -Dapp.environment=production
```

produces a JAR containing:

```properties
app.environment=production
```

The production value is now embedded inside the artifact.

If you want staging instead, you may be tempted to rebuild:

```bash
mvn package -Dapp.environment=staging
```

Now you have a different artifact.

This has consequences for build-once-and-promote workflows.

---

# 51. Why Environment-Specific Builds Can Be Problematic

Recall Part 11:

```text
Build once
→ test
→ publish
→ promote same artifact
```

Now imagine:

```text
mvn package -Dapp.environment=dev
→ dev.jar

mvn package -Dapp.environment=staging
→ staging.jar

mvn package -Dapp.environment=production
→ production.jar
```

You are no longer promoting the exact same artifact.

You are building three artifacts.

Each build can theoretically differ.

For deployment-specific configuration, runtime configuration is often a better design.

---

# 52. Runtime Configuration Mental Model

A stronger architecture for many environment-specific values is:

```text
Same application artifact
        |
        +----------------+
        |                |
        v                v
     Staging          Production
        |                |
        v                v
Runtime config A     Runtime config B
```

For example:

```text
Same JAR
+
APP_PORT=8080
```

in staging.

And:

```text
Same JAR
+
APP_PORT=80xx
```

in another environment, according to application needs.

The exact mechanism depends on the application framework and deployment platform.

---

# 53. When Build-Time Filtering Is Useful

Filtering is still useful.

Good candidates can include:

```text
Application build version
Artifact ID
Build metadata
Non-secret static labels
Generated informational files
Compile/build-specific constants
Documentation metadata
```

Example:

```properties
build.artifact=${project.artifactId}
build.version=${project.version}
```

These values naturally describe the build itself.

---

# 54. When to Be Careful With Filtering

Be cautious with values such as:

```text
Production database URL
Production API endpoint
Deployment environment
Region-specific runtime configuration
Credentials
Passwords
Tokens
Private keys
```

Some may belong in runtime configuration.

Secrets especially should not be embedded casually into the build artifact.

---

# 55. Environment-Specific Values

An application might need different values in different environments.

Example:

```text
Development
database.host=localhost

Testing
database.host=test-db.internal

Production
database.host=prod-db.internal
```

There are several ways software systems can handle environment differences.

Maven filtering is one possible build-time mechanism.

But it is not always the correct deployment architecture.

Ask first:

```text
Does this value describe the build?

Or does it describe the environment where the artifact runs?
```

That question helps determine whether Maven should own the value.

---

# 56. Build Properties Are Not Automatically Runtime Environment Variables

This can confuse beginners.

Suppose you run:

```bash
mvn package -Dapp.environment=staging
```

That does not mean the deployed Java process will automatically have an operating-system environment variable named:

```text
app.environment
```

Instead, Maven can use the property during its own build process.

If filtering inserts it into a file, the value becomes part of that generated resource.

Build properties and runtime environment variables are separate concepts.

---

# 57. Operating-System Environment Variables

An environment variable belongs to a process environment.

On macOS/Linux:

```bash
export APP_ENVIRONMENT=development
```

Then:

```bash
echo "$APP_ENVIRONMENT"
```

might display:

```text
development
```

A Java application can read environment variables at runtime using Java APIs or framework configuration.

That is different from Maven resource filtering.

---

# 58. Build-Time and Runtime Flow Comparison

Build-time:

```text
Maven property
      |
      v
Resource filtering
      |
      v
Value embedded in resource
      |
      v
JAR
```

Runtime:

```text
JAR
      |
      v
Application process
      |
      v
Read environment variable/config source
      |
      v
Use runtime value
```

A professional application may use both, but for different purposes.

---

# 59. Maven Filter Files

Maven can also use separate filter files containing property values.

Conceptually:

```text
filters/
└── development.properties
```

with:

```properties
app.environment=development
app.region=local
```

The POM can configure Maven to use a filter file while processing resources.

This separates some build-time values from the main resource template.

---

# 60. Example Filter File

Create:

```text
filters/development.properties
```

with:

```properties
app.environment=development
app.region=local
```

Resource:

```text
src/main/resources/application.properties
```

contains:

```properties
app.name=${project.name}
app.version=${project.version}
app.environment=${app.environment}
app.region=${app.region}
```

Conceptually:

```text
application.properties template
        +
development.properties
        +
Maven project properties
        |
        v
Resource filtering
        |
        v
Processed application.properties
```

---

# 61. Configuring a Filter File

A build configuration can include:

```xml
<build>

    <filters>
        <filter>filters/development.properties</filter>
    </filters>

    <resources>
        <resource>
            <directory>src/main/resources</directory>
            <filtering>true</filtering>
        </resource>
    </resources>

</build>
```

This tells Maven:

1. Use the configured filter file.
2. Process resources from `src/main/resources`.
3. Enable filtering.

---

# 62. What Happens During Filtering?

Suppose the template contains:

```properties
app.environment=${app.environment}
```

Filter file:

```properties
app.environment=development
```

Maven processes:

```text
Template
+
Property source
        |
        v
Resolve placeholder
        |
        v
Generated resource
```

Result:

```properties
app.environment=development
```

# 63. Multiple Property Sources

Maven properties can come from several places, including:

* Project model values
* `<properties>` in the POM
* Command-line user properties
* Filter files
* Maven settings and other Maven model/configuration sources in relevant contexts
* System/environment-related expressions where supported

This introduces an important concept:

```text
property precedence
```

If the same property is defined in multiple places, one value may override another according to Maven's property-resolution behavior and the plugin context.

Do not create unnecessarily complicated property hierarchies.

They become difficult to troubleshoot.

---

# 64. Keep Property Sources Understandable

A beginner project should avoid this:

```text
Property defined in:
POM
+
parent POM
+
profile
+
filter file
+
command line
+
CI variable
+
settings.xml
```

unless there is a genuine reason.

Otherwise, when you ask:

```text
Where did this value come from?
```

the answer becomes difficult.

Prefer a clear ownership model.

---

# 65. Encoding

Text files are stored using character encodings.

Common modern projects use:

```text
UTF-8
```

Encoding determines how characters are represented as bytes.

This matters for resources containing:

```text
Accented characters
Non-English text
Symbols
Localized messages
Configuration
Templates
```

If one tool writes a file using one encoding and another reads it using the wrong encoding, text can become corrupted.

---

# 66. Set Project Encoding

A Maven POM commonly declares:

```xml
<properties>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
</properties>
```

You may also encounter:

```xml
<project.reporting.outputEncoding>UTF-8</project.reporting.outputEncoding>
```

These properties help establish predictable encoding behavior for plugins that honor them.

---

# 67. Resource Encoding

The Maven Resources Plugin can use a configured encoding.

Conceptually:

```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-resources-plugin</artifactId>
    <version>CONTROLLED_VERSION</version>

    <configuration>
        <encoding>UTF-8</encoding>
    </configuration>
</plugin>
```

Use an explicitly selected compatible plugin version in a real project.

This helps avoid depending on platform-default encodings.

---

# 68. Why Platform Defaults Are Dangerous

Imagine:

```text
Developer laptop
→ default encoding A

CI runner
→ default encoding B

Production build machine
→ default encoding C
```

The same text resource may be interpreted differently.

Explicit configuration reduces ambiguity.

This connects resource handling with reproducible builds.

---

# 69. Example Encoding Problem

Suppose:

```properties
welcome.message=Bienvenido a VERIQTA
```

or a resource contains names and text using characters outside basic ASCII.

If the file is read using the wrong encoding, the output may contain corrupted characters.

Troubleshooting questions:

```text
What encoding was the source file saved with?

What encoding did Maven use?

What encoding does the application expect?

Did filtering rewrite the file?

Did CI use different defaults?
```

---

# 70. Filtering and Binary Files

Resource filtering is primarily intended for text-based resources.

Be careful with binary resources such as:

```text
.png
.jpg
.gif
.pdf
.zip
.jar
```

Trying to filter binary files can corrupt them because Maven may interpret bytes as text.

A safer structure often separates:

```text
Filtered text resources
```

from:

```text
Unfiltered binary resources
```

---

# 71. Separate Filtered and Unfiltered Resources

For example:

```text
src/main/resources/
├── config/
│   └── build-info.properties
├── static/
│   └── logo.png
└── documents/
    └── guide.pdf
```

You may configure filtering selectively rather than applying it indiscriminately to everything.

Conceptually:

```text
config/*.properties
→ filter

images/documents/binary files
→ copy unchanged
```

---

# 72. Includes

Maven resource configuration can select which files should be included.

Conceptually:

```xml
<resource>
    <directory>src/main/resources</directory>

    <includes>
        <include>**/*.properties</include>
    </includes>

    <filtering>true</filtering>
</resource>
```

This says:

```text
From src/main/resources
→ include matching .properties files
→ enable filtering
```

The `**` pattern commonly represents directories recursively in this kind of file matching.

---

# 73. Excludes

You can also exclude files.

Example concept:

```xml
<excludes>
    <exclude>**/*.secret</exclude>
</excludes>
```

However, do not use an exclusion as your primary secrets-management strategy.

A secret file should ideally never be committed into the source tree in the first place.

---

# 74. Escaping

Sometimes you want a placeholder-like expression to remain literal rather than being replaced.

For example, a configuration template may need the final output to contain:

```text
${RUNTIME_VALUE}
```

because another system will resolve it later.

But Maven filtering may interpret that expression as something it should process.

This is where escaping becomes relevant.

---

# 75. Why Escaping Exists

Suppose the source resource intentionally contains:

```text
${DATABASE_HOST}
```

and you want that exact text to survive Maven's build because another runtime tool will replace it later.

Without a clear escaping strategy, you may get:

```text
unexpected replacement
```

or:

```text
unresolved placeholder behavior
```

depending on configuration.

Maven Resources Plugin supports escape-related configuration so expressions intended for later processing can be protected.

The exact syntax should be deliberately configured rather than assumed.

---

# 76. Alternative Delimiters

Another way to reduce placeholder collisions is to use a deliberate filtering delimiter.

Instead of:

```text
${project.version}
```

for filtered resource values, some projects use a distinct form such as:

```text
@project.version@
```

when configured appropriately.

Then a resource might contain:

```properties
build.version=@project.version@
runtime.host=${DATABASE_HOST}
```

Conceptually:

```text
@...@
→ Maven build-time filtering

${...}
→ preserved for another configuration system
```

This can make ownership clearer.

The exact delimiter behavior must be configured in the Maven Resources Plugin.

---

# 77. Why Placeholder Collisions Matter

Modern applications may involve several systems that recognize similar syntax:

```text
Maven
Shell
CI/CD platform
Spring configuration
Docker/Compose
Kubernetes templates
Infrastructure tools
Application frameworks
```

If multiple systems see:

```text
${SOMETHING}
```

you need to know:

```text
Which system owns this placeholder?
```

Otherwise one layer may replace a value intended for another layer.

---

# 78. Think in Configuration Layers

A useful DevOps mental model is:

```text
Source configuration template
        |
        v
Build-time configuration
        |
        v
Artifact
        |
        v
Deployment-time configuration
        |
        v
Runtime configuration
        |
        v
Running application
```

Do not mix these layers without understanding who resolves each value.

# 79. Security: Configuration Is Not Automatically Secret

A file named:

```text
config.properties
```

is not secure simply because it is called configuration.

Suppose it contains:

```properties
database.username=admin
database.password=SuperSecretPassword
api.token=abc123
```

and lives under:

```text
src/main/resources
```

Then:

```text
Secret
 |
 v
Git
 |
 v
Maven
 |
 v
target/classes
 |
 v
JAR
 |
 v
Artifact repository
 |
 v
Deployment
```

The secret may now exist in many places.

---

# 80. Why Secrets Should Not Be Committed Into `pom.xml`

Never treat:

```xml
<properties>
    <database.password>real-production-password</database.password>
</properties>
```

as a safe secret-storage method.

If committed, the secret can exist in:

```text
Git history
Developer clones
Pull requests
Code reviews
CI checkouts
Backups
Mirrors
Logs
Caches
```

Deleting the current line later does not necessarily erase it from Git history or every copied location.

---

# 81. Why Maven Filtering Is Not Secrets Management

You might think:

> I will keep the password somewhere and let Maven inject it into `application.properties`.

Suppose:

```properties
database.password=${database.password}
```

becomes:

```properties
database.password=ActualProductionPassword
```

during filtering.

Now the secret may exist in:

```text
target/classes/application.properties
```

and then:

```text
application.jar
```

The secret has been embedded into the artifact.

Filtering moved the secret.

It did not securely manage it.

---

# 82. Secrets Embedded in JARs Can Be Read

Suppose a JAR contains:

```text
application.properties
```

You already learned:

```bash
jar tf application.jar
```

can list the archive.

And:

```bash
unzip -p application.jar application.properties
```

can display a packaged resource.

Therefore a secret inside the resource should not be treated as hidden merely because it is inside a JAR.

A JAR is an archive, not a secret vault.

---

# 83. Better Secret Handling

Production secrets should generally come from a dedicated secret-delivery mechanism appropriate to the environment.

Examples of categories include:

```text
Cloud secret-management service
Platform secret store
CI/CD secret store
Orchestrator secret mechanism
External secret-management system
Secure runtime environment injection
```

The application receives the value when needed rather than permanently embedding it into source or a generic build artifact.

---

# 84. Runtime Secret Flow

A safer conceptual model:

```text
Git
 |
 v
Application source
(no production secret)
 |
 v
Maven
 |
 v
Artifact
(no production secret)
 |
 v
Deployment
 |
 +-------------------+
 |                   |
 v                   v
Artifact        Secret system
 |                   |
 +---------+---------+
           |
           v
    Running process
```

The artifact and secret meet at runtime or controlled deployment time.

---

# 85. Environment Variables and Secrets

Environment variables are often used as one mechanism for delivering runtime configuration.

For example:

```text
DATABASE_PASSWORD
```

But environment variables are not magically secure either.

They can be exposed through:

* Process inspection in some environments
* Debug output
* Crash reports
* CI logs
* Misconfigured deployment manifests
* Shell history if handled badly
* Diagnostic tooling

The principle is not:

```text
Environment variable = always secure.
```

The principle is:

```text
Use an appropriate secrets-management mechanism and avoid embedding secrets into source/build artifacts.
```

---

# 86. Do Not Print Secrets

Avoid code such as:

```java
System.out.println(System.getenv("DATABASE_PASSWORD"));
```

and avoid build scripts that echo secrets.

A secret that is securely stored but then printed into CI logs is no longer being handled safely.

---

# 87. Do Not Pass Secrets Casually on the Maven Command Line

This may look convenient:

```bash
mvn package -Ddatabase.password=REAL_PASSWORD
```

but command-line secrets can be risky.

Depending on the operating system and environment, command arguments may be exposed through:

* Process listings
* Shell history
* CI logs
* Debug output
* Build records

And if filtering inserts the value into the artifact, you have an additional exposure.

Do not use Maven command-line filtering as your default production-secret strategy.

---

# 88. Configuration Ownership

Before adding a value, classify it.

Ask:

```text
Is this source configuration?

Is this build metadata?

Is this test data?

Is this environment configuration?

Is this a secret?

Is this runtime state?
```

Then place it appropriately.

Example:

```text
Application version
→ build metadata

Sample test JSON
→ src/test/resources

HTML template
→ src/main/resources

Production database password
→ secret-management system

Deployment-specific endpoint
→ often runtime/deployment configuration
```

---

# 89. Main Resources Versus External Configuration

Not all configuration has to be packaged inside:

```text
src/main/resources
```

An application can have:

```text
Packaged defaults
+
External runtime configuration
```

For example:

```text
JAR
├── default application settings
└── application code

Runtime environment
└── environment-specific overrides
```

The exact precedence depends on the framework/application.

This model allows one artifact to run in multiple environments.

---

# 90. Good Packaged Defaults

A packaged resource might contain safe defaults:

```properties
app.name=VERIQTA Maven Application
app.timeout.seconds=30
app.feature.logging=true
```

But deployment-specific or secret values can come from outside the artifact.

Conceptually:

```text
Packaged defaults
        |
        v
Application
        ^
        |
Runtime overrides
```

# 91. Test Resources and Secrets

Tests also require care.

Do not put real production credentials into:

```text
src/test/resources
```

just because the file is "only for tests."

Test resources can still be:

```text
Committed to Git
Downloaded by developers
Processed by CI
Stored in caches
Included in test artifacts
Printed in logs
```

Use fake or isolated test credentials where appropriate.

# 92. Example Safe Test Configuration

use a local disposable test setup:


```text
Testing should not require production secrets.
```

```text
        |
```

# 95. Troubleshooting: Resource in Wrong Directory

Wrong:

```text
src/resources/application.properties
```

Maven's standard main resource directory is:

```text
src/main/resources
```

Unless you deliberately configure a custom resource directory, Maven will not treat arbitrary paths as standard resources.

Fix:

```text
src/main/resources/application.properties
```

Then:

```bash
mvn clean package
```

# 102. Troubleshooting: Binary Resource Becomes Corrupted

Problem:

An image or binary file works before the Maven build but not afterward.

Ask:

```text
Was resource filtering enabled for the binary file?
```

If yes, filtering may have attempted text processing.

Separate binary resources from filtered text resources or configure non-filtered file extensions/resource sets appropriately.

Do not solve binary corruption by repeatedly copying random versions of the file.

Understand how Maven processed it.

# 107. Example Combined Build Section

Conceptually:

# 120. The DevOps Lesson

Compare:

```text
Build 1
app.environment=staging
        |
        v
artifact A
```

with:

```text
Build 2
app.environment=production
        |
        v
artifact B
```

These are not the same artifact bytes.

Therefore a strict build-once/promote model would prefer:

```text
One artifact
        |
        +----------------+
        |                |
        v                v
Staging runtime      Production runtime
config               config
```

rather than rebuilding application binaries merely to change environment configuration.
