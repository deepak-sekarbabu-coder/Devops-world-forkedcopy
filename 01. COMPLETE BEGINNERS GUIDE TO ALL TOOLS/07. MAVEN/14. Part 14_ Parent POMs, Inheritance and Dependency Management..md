# Part 14: Parent POMs, Inheritance and Dependency Management

## Introduction

So far, you have mostly worked with individual Maven projects.

A single application can have its own:

```text
pom.xml
```

That POM can define:

* Project coordinates
* Java version
* Dependencies
* Dependency versions
* Plugin versions
* Compiler configuration
* Testing configuration
* Build behavior
* Properties

For one project, this is manageable.

Now imagine an organization has:

```text
orders-service
payments-service
users-service
inventory-service
notification-service
reporting-service
```

Each application could have its own POM containing the same Java version, test versions, compiler configuration, plugin versions, encoding settings, and organizational defaults.

That creates repetition.

For example:

```text
orders-service/pom.xml
→ Java 21
→ JUnit version
→ Compiler Plugin version
→ Surefire Plugin version

payments-service/pom.xml
→ Java 21
→ JUnit version
→ Compiler Plugin version
→ Surefire Plugin version

users-service/pom.xml
→ Java 21
→ JUnit version
→ Compiler Plugin version
→ Surefire Plugin version
```

What happens when the organization needs to change one of those values?

Without centralized management, engineers may need to modify many POM files.

Even worse, projects can slowly become inconsistent:

```text
Service A → JUnit version A
Service B → JUnit version B
Service C → JUnit version C

Service A → Compiler Plugin version X
Service B → Compiler Plugin version Y
Service C → no explicit version
```

Maven provides several mechanisms for managing this problem:

```text
Parent POMs
Inheritance
dependencyManagement
pluginManagement
BOMs
Effective POMs
```

These concepts are essential when moving from:

```text
one small Maven project
```

toward:

```text
multiple projects
shared organizational standards
large application builds
enterprise Java environments
```

In this part, we will build:

```text
Parent POM
    |
    +---- shared Java version
    +---- shared properties
    +---- dependency versions
    +---- plugin versions
    +---- plugin configuration
    |
    v
Child Application
```

Before building it, we need to understand exactly what Maven is doing.

---

# 1. Why Repeated Maven Configuration Becomes Difficult

Start with three independent applications:

```text
veriqta-orders
veriqta-payments
veriqta-users
```

Each has:

```text
pom.xml
```

Suppose every POM contains:

```xml
<properties>
    <maven.compiler.release>21</maven.compiler.release>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
</properties>
```

Each also declares the same test dependency:

```xml
<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>...</version>
    <scope>test</scope>
</dependency>
```

And perhaps the same plugin configuration.

Conceptually:

```text
Project A
├── Java version
├── dependency versions
└── plugin configuration

Project B
├── Java version
├── dependency versions
└── plugin configuration

Project C
├── Java version
├── dependency versions
└── plugin configuration
```

This produces duplication.

Duplication is not merely inconvenient.

It creates configuration drift.

---

# 2. What Is Configuration Drift?

Configuration drift happens when projects that were supposed to follow the same standard gradually become different.

For example:

```text
Initial state

Orders   → Java 21
Payments → Java 21
Users    → Java 21
```

Later:

```text
Orders   → Java 21
Payments → Java 17
Users    → Java 21
```

Or:

```text
Orders   → Surefire Plugin version A
Payments → Surefire Plugin version B
Users    → Maven default/inherited version
```

Sometimes the differences are intentional.

Sometimes they happen because one project was updated and another was forgotten.

Centralized Maven configuration helps distinguish:

```text
intentional difference
```

from:

```text
accidental inconsistency
```

---

# 3. The Parent POM Concept

Maven allows one POM to act as the parent of another POM.

The parent can contain configuration shared by child projects.

Mental model:

```text
Parent POM
    |
    +---- common properties
    +---- common dependency management
    +---- common plugin configuration
    +---- common build configuration
    |
    +-------------------+
    |                   |
    v                   v
Child A              Child B
```

Instead of repeating the same configuration everywhere:

```text
Child A → duplicate settings
Child B → duplicate settings
Child C → duplicate settings
```

you can define common configuration in one parent:

```text
                 Parent
                    |
          +---------+---------+
          |         |         |
          v         v         v
       Child A   Child B   Child C
```

---

# 4. What Is a Parent POM?

A parent POM is a Maven POM referenced by another Maven project through the:

```xml
<parent>
```

element.

A child project can inherit selected Maven configuration from that parent.

For example, a child might begin:

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
                             https://maven.apache.org/xsd/maven-4.0.0.xsd">

    <modelVersion>4.0.0</modelVersion>

    <parent>
        <groupId>com.veriqta</groupId>
        <artifactId>veriqta-parent</artifactId>
        <version>1.0.0</version>
    </parent>

    <artifactId>veriqta-app</artifactId>

</project>
```

Notice something unusual.

The child does not explicitly declare:

```xml
<groupId>
```

or:

```xml
<version>
```

after the parent section.

Why?

Because those values can be inherited from the parent.

---

# 5. Understanding `<parent>`

Consider:

```xml
<parent>
    <groupId>com.veriqta</groupId>
    <artifactId>veriqta-parent</artifactId>
    <version>1.0.0</version>
</parent>
```

This identifies the parent POM.

Break it apart.

```xml
<groupId>com.veriqta</groupId>
```

identifies the parent's group.

```xml
<artifactId>veriqta-parent</artifactId>
```

identifies the parent artifact.

```xml
<version>1.0.0</version>
```

identifies the parent version.

Together:

```text
com.veriqta:veriqta-parent:1.0.0
```

These are the coordinates of the parent.

Do not confuse these coordinates with the child's final coordinates.

---

# 6. Parent Coordinates Versus Child Coordinates

Suppose:

```text
Parent:

com.veriqta:veriqta-parent:1.0.0
```

and the child contains:

```xml
<artifactId>veriqta-app</artifactId>
```

while inheriting `groupId` and `version`.

The child's coordinates become:

```text
com.veriqta:veriqta-app:1.0.0
```

Therefore:

```text
Parent coordinates
≠
Child coordinates
```

The child inherits some coordinate values but still has its own artifact identity.

---

# 7. What Is POM Inheritance?

Inheritance means configuration from one POM contributes to the effective configuration of a child POM.

Conceptually:

```text
Parent configuration
        |
        v
Child configuration
        |
        v
Combined Maven model
        |
        v
Effective configuration
```

The child POM does not need to physically contain every inherited value.

Maven combines the models.

---

# 8. A Programming Analogy, With a Warning

If you have encountered object-oriented programming, the word:

```text
inheritance
```

may sound familiar.

The analogy can help slightly:

```text
Parent
   |
   v
Child receives shared characteristics
```

But Maven POM inheritance has Maven-specific merging and inheritance rules.

Do not assume Java class inheritance rules apply to POMs.

Treat Maven inheritance as its own configuration model.

---

# 9. A Basic Parent POM

Create a parent:

```text
veriqta-parent/
└── pom.xml
```

A simple parent could look like:

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
                             https://maven.apache.org/xsd/maven-4.0.0.xsd">

    <modelVersion>4.0.0</modelVersion>

    <groupId>com.veriqta</groupId>
    <artifactId>veriqta-parent</artifactId>
    <version>1.0.0</version>

    <packaging>pom</packaging>

</project>
```

The important new line is:

```xml
<packaging>pom</packaging>
```

---

# 10. Why Parent POMs Commonly Use `pom` Packaging

You previously learned packaging types such as:

```text
jar
war
pom
```

A configuration-oriented parent project commonly uses:

```xml
<packaging>pom</packaging>
```

because its primary purpose is not to produce an application JAR.

It exists to describe and share Maven project configuration.

Mental model:

```text
Application project
→ packaging jar
→ produces application/library JAR

Web application
→ packaging war
→ produces WAR

Parent/configuration project
→ packaging pom
→ provides Maven model/configuration
```

---

# 11. What Can Children Inherit?

Children can inherit many useful parts of a parent POM.

Examples include:

* `groupId`
* `version`
* Properties
* Dependency declarations
* Dependency management
* Build configuration
* Plugin configuration
* Plugin management
* Reporting configuration
* Repository configuration
* Distribution management
* Other Maven model elements that Maven defines as inheritable

However, not every POM element is inherited in the same way.

Some elements identify the individual project and must remain specific to the child.

The safest mental model is not:

```text
Child receives a literal copy of the entire parent POM.
```

Instead:

```text
Maven combines parent and child models
according to Maven's inheritance and merging rules.
```

---

# 12. `groupId` Inheritance

Parent:

```xml
<groupId>com.veriqta</groupId>
```

Child:

```xml
<parent>
    <groupId>com.veriqta</groupId>
    <artifactId>veriqta-parent</artifactId>
    <version>1.0.0</version>
</parent>

<artifactId>veriqta-app</artifactId>
```

The child does not declare its own `groupId`.

It inherits:

```text
com.veriqta
```

Therefore:

```text
Child groupId
=
com.veriqta
```

---

# 13. `version` Inheritance

Parent:

```xml
<version>1.0.0</version>
```

Child:

```xml
<artifactId>veriqta-app</artifactId>
```

If the child does not declare its own project version, it can inherit:

```text
1.0.0
```

Therefore:

```text
com.veriqta:veriqta-app:1.0.0
```

---

# 14. Can a Child Override the Version?

Yes.

A child can have its own project version when appropriate.

For example:

```xml
<artifactId>veriqta-app</artifactId>
<version>2.0.0</version>
```

Now:

```text
Parent version
→ 1.0.0

Child project version
→ 2.0.0
```

The `<parent>` section still identifies:

```text
com.veriqta:veriqta-parent:1.0.0
```

while the child's own coordinates become:

```text
com.veriqta:veriqta-app:2.0.0
```

This distinction is important.

---

# 15. Properties Inheritance

Suppose the parent contains:

```xml
<properties>
    <maven.compiler.release>21</maven.compiler.release>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
</properties>
```

A child can inherit those properties.

Instead of repeating:

```xml
<maven.compiler.release>21</maven.compiler.release>
```

in every project, define it once.

Mental model:

```text
Parent

Java release = 21
Encoding = UTF-8

        |
        +-------------+
        |             |
        v             v
     Child A       Child B

Java 21          Java 21
UTF-8            UTF-8
```

---

# 16. Why Properties Are Useful in Parent POMs

Properties can centralize values used repeatedly.

For example:

```xml
<properties>
    <maven.compiler.release>21</maven.compiler.release>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>

    <junit.version>...</junit.version>
    <maven.compiler.plugin.version>...</maven.compiler.plugin.version>
    <maven.surefire.plugin.version>...</maven.surefire.plugin.version>
</properties>
```

Then elsewhere:

```xml
<version>${junit.version}</version>
```

or:

```xml
<version>${maven.compiler.plugin.version}</version>
```

This gives meaningful names to centrally managed values.

---

# 17. Can a Child Override an Inherited Property?

Yes.

Suppose the parent defines:

```xml
<properties>
    <maven.compiler.release>21</maven.compiler.release>
</properties>
```

A child could define:

```xml
<properties>
    <maven.compiler.release>17</maven.compiler.release>
</properties>
```

The child's value can override the inherited property for that child.

This can be useful.

It can also undermine standardization if done carelessly.

Before overriding a parent property, ask:

```text
Is this project genuinely different?

Or am I creating accidental configuration drift?
```

---

# 18. Dependency Inheritance

There are two concepts beginners must keep separate:

```text
dependency inheritance
```

and:

```text
dependency management
```

They are not the same.

Suppose the parent contains:

```xml
<dependencies>
    <dependency>
        <groupId>org.junit.jupiter</groupId>
        <artifactId>junit-jupiter</artifactId>
        <version>${junit.version}</version>
        <scope>test</scope>
    </dependency>
</dependencies>
```

A child can inherit that dependency.

That means the dependency becomes part of the child's dependency model even if the child does not declare it itself.

Conceptually:

```text
Parent <dependencies>
        |
        v
Child receives dependency
```

This is different from `dependencyManagement`.

---

# 19. Why Automatically Inheriting Dependencies Can Be Too Broad

Imagine a parent declares:

```text
Database driver
Web framework
JSON library
Testing library
Messaging library
```

under:

```xml
<dependencies>
```

Then children may inherit dependencies they do not actually use.

For example:

```text
Orders Service
→ needs database library

Notification Service
→ does not

Simple CLI Tool
→ does not
```

If all three inherit the dependency simply because they share a parent, the parent is forcing unnecessary dependencies into projects.

This is one reason:

```xml
<dependencyManagement>
```

is so important.

---

# 20. What Is Dependency Management?

Maven provides:

```xml
<dependencyManagement>
```

to centrally manage dependency information, especially versions, without automatically making every managed dependency an active dependency of every child.

This distinction is critical.

Think:

```text
<dependencies>
→ This project uses these dependencies.

<dependencyManagement>
→ If this project or a child uses these dependencies, use these managed details.
```

---

# 21. Dependency Declaration Versus Dependency Management

Consider:

```xml
<dependencies>
    <dependency>
        <groupId>org.junit.jupiter</groupId>
        <artifactId>junit-jupiter</artifactId>
        <version>...</version>
        <scope>test</scope>
    </dependency>
</dependencies>
```

This declares JUnit as a dependency.

Now compare:

```xml
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.junit.jupiter</groupId>
            <artifactId>junit-jupiter</artifactId>
            <version>...</version>
        </dependency>
    </dependencies>
</dependencyManagement>
```

This manages JUnit's version.

It does not, by itself, mean every child now uses JUnit.

---

# 22. The Most Important Dependency Management Mental Model

Remember:

```text
dependencyManagement
        |
        v
Defines rules/defaults for dependencies
        |
        v
Does NOT automatically mean
"put all of these libraries on every child's classpath"
```

The child still declares the dependency when it needs it:

```xml
<dependencies>
    <dependency>
        <groupId>org.junit.jupiter</groupId>
        <artifactId>junit-jupiter</artifactId>
        <scope>test</scope>
    </dependency>
</dependencies>
```

Notice:

```text
No version.
```

Why?

Because the parent manages it.

---

# 23. Parent Dependency Management Example

Parent:

```xml
<dependencyManagement>
    <dependencies>

        <dependency>
            <groupId>org.junit.jupiter</groupId>
            <artifactId>junit-jupiter</artifactId>
            <version>${junit.version}</version>
        </dependency>

    </dependencies>
</dependencyManagement>
```

Child:

```xml
<dependencies>

    <dependency>
        <groupId>org.junit.jupiter</groupId>
        <artifactId>junit-jupiter</artifactId>
        <scope>test</scope>
    </dependency>

</dependencies>
```

Resolution:

```text
Child says:
"I need JUnit."

Parent says:
"When JUnit is used, use the managed version."

Maven combines them.
```

---

# 24. Why Centralizing Versions Matters

Without dependency management:

```text
orders/pom.xml
→ JUnit version A

payments/pom.xml
→ JUnit version A

users/pom.xml
→ JUnit version A
```

To upgrade:

```text
Edit orders
Edit payments
Edit users
```

With parent dependency management:

```text
Parent
→ JUnit version A
```

Children:

```text
Orders   → declares JUnit
Payments → declares JUnit
Users    → declares JUnit
```

To change the managed version:

```text
Parent
→ JUnit version B
```

The children that consume that parent and do not override the version can now resolve the centrally managed version.

---

# 25. Why Children Should Often Omit Managed Versions

Suppose the parent manages:

```text
JUnit = version X
```

but a child declares:

```xml
<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>version-Y</version>
    <scope>test</scope>
</dependency>
```

The child has now explicitly selected its own version.

That may defeat the purpose of centralized management.

Usually, when the parent is intentionally controlling the version, the child uses:

```xml
<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <scope>test</scope>
</dependency>
```

The absence of a version is deliberate.

---

# 26. Dependency Management Does More Than Versions

Beginners often summarize `dependencyManagement` as:

```text
a place for versions
```

Version centralization is one of its most important uses, but Maven dependency management can provide additional managed dependency information, such as scope and exclusions in appropriate cases.

The core beginner rule remains:

```text
dependencyManagement
=
central dependency policy/defaults

dependencies
=
dependencies actually declared for use
```

# 29. Install the Parent POM Locally

If the child is going to resolve a parent that is not available from a remote repository and is not being resolved from a suitable local relative path, the parent must be available to Maven.

For a local learning environment, one useful approach is:

```bash
cd veriqta-parent
mvn install
```

Because the packaging is:

```xml
<packaging>pom</packaging>
```

Maven installs the parent POM artifact into your local repository.

Conceptually:

```text
veriqta-parent/pom.xml
        |
        v
mvn install
        |
        v
~/.m2/repository/com/veriqta/veriqta-parent/1.0.0/
        |
        v
Parent available for resolution
```

# 30. How Maven Finds a Parent

When a child declares:

```xml
<parent>
    <groupId>com.veriqta</groupId>
    <artifactId>veriqta-parent</artifactId>
    <version>1.0.0</version>
</parent>
```

Maven needs to resolve that parent POM.

For a typical child project, Maven can look for a parent POM through a relative filesystem path first, by default commonly:

```text
../pom.xml
```

unless `relativePath` changes or disables that behavior.

If an appropriate local parent is not resolved that way, Maven can resolve the parent through configured repositories, including the local Maven repository.

This is why project layout and parent installation matter.

---

# 31. Understanding `<relativePath>`

A child can explicitly specify:

```xml
<parent>
    <groupId>com.veriqta</groupId>
    <artifactId>veriqta-parent</artifactId>
    <version>1.0.0</version>
    <relativePath>../pom.xml</relativePath>
</parent>
```

This tells Maven where to look for the parent relative to the child POM.

For example:

```text
workspace/
├── pom.xml
└── child-app/
    └── pom.xml
```

From:

```text
child-app/pom.xml
```

the path:

```text
../pom.xml
```

points to:

```text
workspace/pom.xml
```

---

# 32. Parent Stored Elsewhere

Suppose:

```text
workspace/
├── parent/
│   └── pom.xml
└── child/
    └── pom.xml
```

Then the child could use an appropriate relative path such as:

```xml
<relativePath>../parent/pom.xml</relativePath>
```

However, organizations often publish reusable parent POMs to an artifact repository rather than relying on arbitrary filesystem relationships between unrelated repositories.

---

# 33. Empty `<relativePath/>`

You may encounter:

```xml
<relativePath/>
```

inside `<parent>`.

This tells Maven not to use the normal local relative-parent lookup and instead resolve the parent using repository resolution.

Conceptually:

```text
<relativePath/>
        |
        v
Do not use normal ../pom.xml parent lookup
        |
        v
Resolve parent through Maven repositories
```

This can be useful when the parent is an externally published or organizational parent rather than a POM sitting above the project on disk.

---

# 34. Common Parent Resolution Error

You may see an error similar in meaning to:

```text
Non-resolvable parent POM
```

Possible causes include:

* Wrong parent `groupId`
* Wrong parent `artifactId`
* Wrong parent `version`
* Incorrect `relativePath`
* Parent not installed locally
* Parent not published remotely
* Repository unavailable
* Authentication problem
* Network problem

Use a structured investigation.

---

# 35. Parent Resolution Troubleshooting

Check:

```text
1. Are parent coordinates correct?
2. Does relativePath point to the expected POM?
3. Does that POM have the expected coordinates?
4. If repository resolution is required, is the parent installed or published?
5. Can Maven reach the repository?
6. Is repository authentication working?
```

Do not randomly modify dependency versions.

A parent-resolution failure occurs before Maven can fully construct the project's model.

---

# 36. Parent Versus Aggregator

This distinction is essential.

A:

```text
parent
```

and an:

```text
aggregator
```

solve different problems.

A parent provides inheritance.

An aggregator collects modules so Maven can build them together.

These roles can exist in the same POM, but they are conceptually different.

---

# 37. Parent Mental Model

```text
Parent POM
    |
    | inheritance
    v
Child POM
```

Question answered:

```text
Where does this child receive shared configuration from?
```

---

# 38. Aggregator Mental Model

```text
Aggregator POM
    |
    +---- Module A
    +---- Module B
    +---- Module C
```

Question answered:

```text
Which projects should Maven build together?
```

Aggregation will become especially important when studying multi-module builds.

For now, remember:

```text
Parent
→ inheritance

Aggregator
→ reactor/build grouping
```

---

# 39. Can One POM Be Both?

Yes.

A POM can:

```text
act as parent
```

and:

```text
list modules as aggregator
```

at the same time.

That is common in multi-module projects.

But do not conclude:

```text
Every parent is automatically an aggregator.
```

or:

```text
Every aggregator must be the parent.
```

Those statements are false.

---

# 40. Parent Without Aggregation

Imagine an organization publishes:

```text
com.veriqta:veriqta-parent:1.0.0
```

Hundreds of independent repositories may use it.

The parent does not need:

```xml
<modules>
```

listing all of those projects.

It simply provides shared configuration.

Conceptually:

```text
Published Parent POM
        |
        +---- independent service A
        +---- independent service B
        +---- independent service C
```

The services may live in entirely different Git repositories.

---

# 41. Aggregator Without Parent Relationship

You can also have an aggregator that builds modules even if the aggregator is not necessarily the parent providing their inherited configuration.

Conceptually:

```text
Build Aggregator
├── Module A
└── Module B
```

while:

```text
Module A
→ inherits Organization Parent

Module B
→ inherits Organization Parent
```

The aggregation relationship and inheritance relationship are separate.

# 42. The Super POM

In Part 4, you learned that Maven has a built-in:

```text
Super POM
```

Every Maven project ultimately inherits defaults from Maven's Super POM.

Conceptually:

```text
Maven Super POM
        |
        v
Your Parent POM
        |
        v
Child POM
```

Even if you do not explicitly declare your own parent, Maven still has built-in model defaults.

---

# 43. Why the Super POM Matters Here

Suppose you inspect a tiny child POM:

```xml
<project>
    ...
    <artifactId>veriqta-app</artifactId>
</project>
```

Yet Maven knows more configuration than appears in that file.

Why?

Because the final Maven model can be influenced by:

```text
Super POM
+
Parent POM
+
Child POM
+
profiles and other applicable model inputs
```

This leads us back to the:

```text
Effective POM
```

---

# 44. What Is the Effective POM?

The effective POM is the effective Maven project model after Maven has combined relevant inherited and configured information.

A useful beginner mental model is:

```text
Super POM
     +
Parent POM
     +
Child POM
     +
Applicable configuration
     |
     v
Effective POM
```

It answers:

```text
What configuration does Maven effectively see for this project?
```

---

# 45. Inspecting the Effective POM

From the child project:

```bash
mvn help:effective-pom
```

This can produce a large amount of XML.

That is normal.

You are looking for evidence of:

* Inherited `groupId`
* Inherited version
* Inherited properties
* Dependency management
* Plugin management
* Plugin configuration
* Maven defaults

Do not assume the literal child `pom.xml` contains the entire build model.

---

# 46. Why `help:effective-pom` Is Valuable

Suppose the child does not contain:

```xml

```

but Maven compiles for Java 21.

Where did the setting come from?

Run:

```bash
mvn help:effective-pom
```

Then investigate.

It may have come from:

```text
parent property
plugin configuration
profile
other inherited configuration
```

The effective POM helps answer:

```text
Why is Maven behaving this way?
```

# 47. Effective POM Troubleshooting Pattern

When build behavior surprises you:

```text

        |
        v

        |
        v

        |
```

---

# 48. Dependency Management Across Several Children

Suppose the parent manages:

```text
JUnit
Jackson
SLF4J
```

Conceptually:

```text
Parent
│
├── JUnit = version X
├── Jackson = version Y
└── SLF4J = version Z
```

Child A declares:

```text
JUnit
Jackson
```

Child B declares:

```text
JUnit
SLF4J
```

Child C declares:

```text
Jackson
```

The result:

```text
Child A
→ JUnit X
→ Jackson Y

Child B
→ JUnit X
→ SLF4J Z

Child C
→ Jackson Y
```

The parent manages versions.

Each child chooses which dependencies it actually needs.

---

# 49. Why This Is Better Than Forcing Dependencies

If the parent placed everything under:

```xml
<dependencies>
```

all children might receive all dependencies.

Instead:

```xml
<dependencyManagement>
```

allows:

```text
Central version control
+
Child-specific dependency selection
```

This is one of Maven's most useful organizational patterns.

---

# 50. Dependency Version Override

Suppose the parent manages:

```text
Library A = 3.0
```

but one child explicitly declares:

```xml
<dependency>
    <groupId>example</groupId>
    <artifactId>library-a</artifactId>
    <version>2.5</version>
</dependency>
```

The explicit child dependency version can override the managed version for that declaration.

This may be necessary temporarily.

But it should be intentional.

Ask:

```text
Why is this child different?

Is the exception documented?

When will it return to the managed baseline?
```

---

# 51. Centralized Version Properties

A parent can use:

```xml
<properties>
    <junit.version>...</junit.version>
    <jackson.version>...</jackson.version>
</properties>
```

and then:

```xml
<dependencyManagement>
    <dependencies>

        <dependency>
            <groupId>org.junit.jupiter</groupId>
            <artifactId>junit-jupiter</artifactId>
            <version>${junit.version}</version>
        </dependency>

    </dependencies>
</dependencyManagement>
```

This gives the version a meaningful central name.

---

# 52. But Do Not Create Properties for Everything Blindly

You might be tempted to create:

```text
library1.version
library2.version
library3.version
library4.version
...
library100.version
```

That can become difficult to maintain.

Modern dependency ecosystems often provide another mechanism:

```text
BOM
```

which stands for:

```text
Bill of Materials
```

---

# 53. What Is a Maven BOM?

A BOM is a POM designed to provide a coordinated set of dependency versions.

Think:

```text
BOM
    |
    +---- Library A → compatible version
    +---- Library B → compatible version
    +---- Library C → compatible version
    +---- Library D → compatible version
```

Instead of manually choosing every related library version yourself, you can import a BOM that manages a tested or intended version set.

---

# 54. What Does BOM Mean?

BOM means:

```text
Bill of Materials
```

In Maven, a BOM is typically a POM whose dependency-management information can be imported into another project's dependency management.

It does not mean:

```text
download every library listed in the BOM.
```

It means:

```text
use this coordinated dependency-management information
when relevant dependencies are declared.
```

---

# 55. Why BOMs Exist

Suppose a framework consists of:

```text
framework-core
framework-web
framework-json
framework-security
framework-testing
```

These components may need compatible versions.

Without a BOM, you might manually configure:

```text
core     → 5.x
web      → 5.x
json     → 5.x
security → 5.x
testing  → 5.x
```

But compatibility may be more complicated than simply giving every artifact the same number.

The framework maintainers know which versions are designed to work together.

They can publish a BOM.

Then:

```text
Framework BOM
        |
        v
Coordinated dependency versions
```

---

# 56. BOM Mental Model

Without a BOM:

```text
Developer
├── choose A version
├── choose B version
├── choose C version
├── choose D version
└── hope combination is compatible
```

With a BOM:

```text
Maintainer-provided BOM
├── manages A version
├── manages B version
├── manages C version
└── manages D version

Developer
→ imports BOM
→ declares needed dependencies
```

---

# 57. Importing a BOM

A BOM is commonly imported inside:

```xml
<dependencyManagement>
```

The pattern is:

```xml
<dependencyManagement>
    <dependencies>

        <dependency>
            <groupId>example.group</groupId>
            <artifactId>example-bom</artifactId>
            <version>...</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>

    </dependencies>
</dependencyManagement>
```

Two lines are especially important:

```xml
<type>pom</type>
```

and:

```xml
<scope>import</scope>
```

---

# 58. Why `<type>pom</type>`?

The BOM is a POM artifact.

You are not importing a normal application JAR onto the classpath.

You are importing dependency-management information from a POM.

Therefore:

```xml
<type>pom</type>
```

tells Maven that the dependency is a POM artifact.

---

# 59. Why `<scope>import</scope>`?

The:

```xml
<scope>import</scope>
```

mechanism is used within dependency management to import the managed dependency information from another POM.

Mental model:

```text
External BOM
        |
        v
dependencyManagement
        |
        v
Current project's managed dependency set
```

This is different from ordinary runtime or compile dependency scopes.

---

# 60. Import Scope Is Special

You learned scopes such as:

```text
compile
provided
runtime
test
system
import
```

`import` is special.

It is used with a dependency of type `pom` inside:

```xml
<dependencyManagement>
```

for importing dependency-management information.

Do not use:

```xml
<scope>import</scope>
```

as if it were an ordinary application classpath scope.

---

# 61. BOM Does Not Automatically Add Dependencies

Suppose a BOM manages:

```text
Library A
Library B
Library C
```

You import it.

That does not automatically mean your application depends on all three.

The child still declares what it needs:

```xml
<dependencies>

    <dependency>
        <groupId>example</groupId>
        <artifactId>library-a</artifactId>
    </dependency>

</dependencies>
```

The BOM supplies the managed version.

Mental model:

```text
BOM
→ Which version should be used?

dependencies
→ Which library does this project actually use?
```

---

# 62. Parent Versus BOM

These concepts overlap in purpose but are not the same.

A parent POM can provide broad Maven configuration:

```text
properties
dependency management
plugin management
plugin configuration
build configuration
repositories
other inherited settings
```

A BOM is primarily used to provide dependency-management information.

Think:

```text
Parent POM
→ broad project/build inheritance

BOM
→ dependency version alignment
```

---

# 63. Why BOMs Are Useful Across Different Parents

A project can have only one direct Maven parent.

But it can import dependency-management BOMs.

This is a major reason BOMs are useful.

Imagine:

```text
Organization Parent
        |
        v
Child Application
```

The child also needs dependency versions from:

```text
Framework BOM
Cloud BOM
```

It does not need those BOMs to become its parent.

Instead:

```text
Organization Parent
        |
        v
Child
        |
        +---- imports Framework BOM
        +---- imports Cloud BOM
```

This allows dependency-management composition.

---

# 64. Why You Cannot Simply Have Several Parents

A Maven project has one direct `<parent>` declaration.

You cannot write:

```xml
<parent>
    Parent A
</parent>

<parent>
    Parent B
</parent>

<parent>
    Parent C
</parent>
```

to combine multiple unrelated parents.

This limitation is one reason reusable BOMs are valuable.

---

# 65. Parent Chain

Although a child has one direct parent, that parent can itself have a parent.

Conceptually:

```text
Super POM
    |
    v
Corporate Parent
    |
    v
Java Service Parent
    |
    v
Application
```

This forms an inheritance chain.

Configuration can flow through that chain according to Maven's inheritance rules.

---

# 66. Deep Parent Chains Can Become Difficult

Technically, inheritance chains can be useful.

But excessive layers can make builds difficult to understand.

Imagine:

```text
Child
→ Service Parent
→ Department Parent
→ Company Parent
→ External Parent
→ Super POM
```

An engineer asks:

```text
Why is this plugin configured this way?
```

Now they may need to inspect several layers.

Prefer inheritance structures that are deliberate and understandable.

# 68. Managing Dependency Versions Across Projects

Consider:

```text
Parent POM
    |
    +---- JUnit version
    +---- JSON library version
    +---- logging API version
    |
    +-------------------------+
    |            |            |
    v            v            v
Orders        Payments      Users
```

Now a version update can be coordinated through the parent.

This helps with:

* Consistency
* Security upgrades
* Dependency maintenance
* Compatibility management
* Reproducible builds
* Organizational standards

However, centralization does not remove the need for testing.

Changing a centrally managed version can affect many projects.

# 69. Centralized Changes Have a Larger Blast Radius

Suppose:

```text
Parent v1.0.0
→ Library A version 2
```

and many projects use it.

Then a new parent:

```text
Parent v1.1.0
→ Library A version 3
```

may affect every project that upgrades to the new parent.

Central management provides consistency.

It also increases the importance of:

```text
testing
versioning
release notes
change control
compatibility validation
```

---

# 70. Do Not Silently Change Published Parent Versions

Suppose many projects use:

```text
com.veriqta:veriqta-parent:1.0.0
```

A strong release practice is not to publish a completely different configuration under the same immutable release version.

Instead, publish a new version when the parent changes materially:

```text
1.0.0
1.1.0
2.0.0
```

Then consumers can upgrade deliberately.

This improves reproducibility.

---

# 71. Parent Version as Organizational Configuration Version

Think of a parent version as more than:

```text
some number Maven requires
```

It can represent a versioned build standard.

For example:

```text
veriqta-parent:1.0.0
→ Java baseline A
→ dependency policy A
→ plugin policy A

veriqta-parent:2.0.0
→ Java baseline B
→ dependency policy B
→ plugin policy B
```

Projects can then move between organizational build baselines deliberately.

# 72. Plugin Configuration Inheritance

Dependencies are only part of the problem.

Projects also repeatedly configure plugins.

For example:

```text
Compiler Plugin
Surefire Plugin
Failsafe Plugin
JAR Plugin
Resources Plugin
```

A parent POM can provide plugin configuration.

For example:

```xml
<build>
    <plugins>

        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-compiler-plugin</artifactId>
            <version>${maven.compiler.plugin.version}</version>

            <configuration>
                <release>${maven.compiler.release}</release>
            </configuration>
        </plugin>

    </plugins>
</build>
```

Children can inherit applicable build plugin configuration.

---

# 73. Why Plugin Inheritance Helps

Without shared plugin configuration:

```text
Project A
→ Compiler Plugin config

Project B
→ Compiler Plugin config

Project C
→ Compiler Plugin config
```

With a parent:

```text
Parent
→ Compiler Plugin configuration
        |
        +---- Child A
        +---- Child B
        +---- Child C
```

This can standardize:

```text
Java release
test execution
integration testing
packaging behavior
code-generation behavior
build checks
```

---

# 74. But Not Every Plugin Should Automatically Run Everywhere

Imagine a parent contains an active plugin for:

```text
WAR packaging task
```

but one child is:

```text
command-line JAR
```

Another is:

```text
library
```

Another is:

```text
web application
```

Automatically activating every plugin in every child can create unnecessary or incorrect behavior.

This leads to:

```xml
<pluginManagement>
```

---

# 75. What Is `<pluginManagement>`?

`pluginManagement` is similar in spirit to dependency management.

It allows a POM to define plugin versions and configuration centrally without necessarily making every managed plugin execute in every child merely because it appears in plugin management.

Mental model:

```text
<plugins>
→ Plugins active for this build according to lifecycle/bindings/configuration.

<pluginManagement>
→ Managed defaults for plugins when they are used.
```

This distinction is essential.

---

# 76. Plugin Management Example

Parent:

```xml
<build>
    <pluginManagement>
        <plugins>

            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-compiler-plugin</artifactId>
                <version>${maven.compiler.plugin.version}</version>

                <configuration>
                    <release>${maven.compiler.release}</release>
                </configuration>
            </plugin>

        </plugins>
    </pluginManagement>
</build>
```

A child can then declare:

```xml
<build>
    <plugins>

        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-compiler-plugin</artifactId>
        </plugin>

    </plugins>
</build>
```

The child can receive the managed plugin version and configuration.

---

# 77. Plugin Management Does Not Mean "Run Every Plugin"

Suppose the parent manages:

```text
Compiler Plugin
Failsafe Plugin
JAR Plugin
WAR Plugin
```

That does not mean every child should execute all four simply because they appear under:

```xml
<pluginManagement>
```

Instead:

```text
Parent
→ knows how plugin should be configured

Child
→ uses/activates plugin when appropriate
```

This helps centralize standards without forcing irrelevant plugin executions.

---

# 78. Important Lifecycle Binding Nuance

Some plugins already participate because Maven's lifecycle binds goals based on packaging.

For example, a JAR project has default lifecycle behavior for compilation, testing, and packaging.

`pluginManagement` can influence configuration/version selection when those plugins are part of the build model.

Therefore, do not oversimplify:

```text
Plugin only runs if I explicitly type it under child <plugins>.
```

Lifecycle bindings also matter.

The better mental model is:

```text
Lifecycle determines required build work
+
Plugin bindings determine goals
+
Plugin management can provide managed configuration
+
Explicit plugins can activate/configure additional behavior
```

---

# 79. Dependency Management Versus Plugin Management

These two concepts look similar.

## Dependency management

```xml
<dependencyManagement>
```

controls managed information for dependencies.

Dependencies are libraries/components the project uses.

## Plugin management

```xml
<pluginManagement>
```

controls managed information for build plugins.

Plugins perform build tasks.

Remember:

```text
Dependency
→ application/build classpath component

Plugin
→ performs Maven build work
```

Therefore:

```text
dependencyManagement
→ dependency policy

pluginManagement
→ plugin policy
```

---

# 80. Side-by-Side Mental Model

```text
DEPENDENCIES

Parent
└── dependencyManagement
        |
        v
Child declares dependency
        |
        v
Managed version/config applies
```

```text
PLUGINS

Parent
└── pluginManagement
        |
        v
Plugin participates/is declared as appropriate
        |
        v
Managed version/config applies
```

Both mechanisms centralize configuration while avoiding unnecessary activation.

# 81. Why Plugin Versions Should Be Managed

You learned earlier that plugin versions should be controlled.

In an organization with many Maven projects, repeating plugin versions everywhere creates the same drift problem as dependency versions.

For example:

```text

→ Compiler Plugin X

Service B
→ Compiler Plugin Y

Service C
→ unspecified/default behavior
```

A parent can centralize:

```text

```

This makes build behavior more predictable.

```text
3. Do groupId and artifactId match exactly?
4. Is the expected BOM actually imported?
5. Is the child declaring the same artifact?
6. Does effective-pom show the managed dependency?
```

Do not immediately add a random version to make the error disappear.

Find out why management did not apply.

---

# 98. Exact Coordinates Matter

Suppose the parent manages:

```text
org.example:library-a
```

but the child declares:

```text
org.example:library-b
```

Maven will not apply `library-a`'s managed version to `library-b`.

Dependency management is based on dependency identity.

Check:

```text
groupId
artifactId
type
classifier where relevant
```

when troubleshooting managed dependencies.

---

# 99. Common Mistake: Putting Management Outside the Correct Container

Wrong conceptual structure:

```xml
<dependencyManagement>
    <dependency>
        ...
    </dependency>
</dependencyManagement>
```

Correct structure:

```xml
<dependencyManagement>
    <dependencies>
        <dependency>
            ...
        </dependency>
    </dependencies>
</dependencyManagement>
```

Remember:

```text
dependencyManagement
    |
    v
dependencies
    |
    v
dependency
```

---

# 100. Common Mistake: Expecting Managed Dependencies to Appear Automatically

Parent:

```xml
<dependencyManagement>
    <dependencies>
        <dependency>
            ...
        </dependency>
    </dependencies>
</dependencyManagement>
```

Beginner expectation:

```text
Now every child has this library.
```

Incorrect.

Correct model:

```text
Now children have managed information available
if they declare/use that dependency.
```

---

# 101. Common Mistake: Duplicating Versions in Children

Parent:

```text
JUnit → managed version X
```

Child:

```xml
<dependency>
    ...
    <version>X</version>
</dependency>
```

This may still build, but it reduces the value of centralized management.

Worse:

```xml
<version>Y</version>
```

may create an intentional or accidental override.

When centralized management is the goal:

```text
Let the parent/BOM manage the version.
```

---

# 102. Common Mistake: Confusing Parent Dependency With Parent Dependency Management

Parent:

```xml
<dependencies>
```

means children can inherit actual dependency declarations.

Parent:

```xml
<dependencyManagement>
```

means children can inherit managed dependency information.

Remember:

```text
Parent dependencies
→ potentially inherited dependency use

Parent dependencyManagement
→ inherited dependency policy
```

This distinction prevents many confusing builds.

---

# 103. Common Mistake: Assuming Everything Is Inherited

Not every element behaves as a simple inherited value.

For example, a child must still have its own:

```text
artifactId
```

to identify itself.

Some project metadata and structural relationships are project-specific.

When uncertain:

```bash
mvn help:effective-pom
```

Inspect what Maven actually constructed.

---

# 104. Common Mistake: Wrong Parent Version

Child:

```xml
<parent>
    <groupId>com.veriqta</groupId>
    <artifactId>veriqta-parent</artifactId>
    <version>2.0.0</version>
</parent>
```

but only:

```text
1.0.0
```

exists.

Result:

```text
Parent resolution failure
```

Check the exact parent coordinates.

---

# 105. Common Mistake: `relativePath` Points to the Wrong POM

Imagine:

```text
workspace/
├── old-parent/
│   └── pom.xml
├── new-parent/
│   └── pom.xml
└── child/
    └── pom.xml
```

If the child's relative path points to the wrong file, Maven may report that the POM at that location has the wrong coordinates.

Troubleshoot:

```bash
cat ../expected-parent/pom.xml
```

Verify:

```text
groupId
artifactId
version
```

against the child's `<parent>` declaration.

---

# 106. Common Mistake: Editing the Parent but Building Against an Older Installed Version

Suppose the child resolves:

```text
veriqta-parent:1.0.0
```

from `.m2`.

You edit the parent source directory but do not reinstall it.

The child may continue using the previously installed POM.

If repository/local installation is how the parent is resolved, run:

```bash
cd veriqta-parent
mvn install
```

Then rebuild the child.

Better still, use clear versioning rather than repeatedly changing the meaning of a release version.

---

# 107. Common Mistake: Child Overrides Central Policy Accidentally

Parent:

```xml
<maven.compiler.release>21</maven.compiler.release>
```

Child:

```xml
<maven.compiler.release>17</maven.compiler.release>
```

The child may now behave differently.

That may be intended.

If not, it is configuration drift.

When troubleshooting, compare:

```text
parent
child
effective POM
```

---

# 108. Common Mistake: Confusing Parent With Aggregator

You run Maven from a parent POM expecting:

```text
all child projects to build
```

but the POM does not list modules.

Inheritance alone does not tell Maven:

```text
build these directories together.
```

That is aggregation.

Remember:

```text
Parent relationship
→ child points to parent

Aggregation relationship
→ aggregator lists modules
```

---

# 109. Common Mistake: Assuming `<pluginManagement>` Executes Everything

Parent:

```xml
<pluginManagement>
    <plugins>
        ...
    </plugins>
</pluginManagement>
```

Beginner expectation:

```text
Every managed plugin now automatically executes everywhere.
```

Incorrect.

Plugin management provides managed plugin configuration.

Actual execution depends on:

```text
lifecycle bindings
explicit plugin declarations
plugin executions
packaging
other build configuration
```

---

# 110. Common Mistake: Putting Plugins Under Dependency Management

Dependencies and plugins have different configuration sections.

Wrong mental model:

```text
Everything with groupId/artifactId/version
goes under dependencyManagement.
```

No.

Dependencies:

```xml
<dependencyManagement>
```

Plugins:

```xml
<build>
    <pluginManagement>
```

They serve different systems.

---

# 111. Common Mistake: Treating a BOM as a Normal Dependency

Wrong conceptual use:

```xml
<dependencies>
    <dependency>
        <groupId>...</groupId>
        <artifactId>...-bom</artifactId>
    </dependency>
</dependencies>
```

when the intention is to import dependency-management information.

The common BOM import pattern belongs under:

```xml
<dependencyManagement>
```

with:

```xml
<type>pom</type>
<scope>import</scope>
```

---

# 112. Common Mistake: Expecting BOM Import to Add Libraries

You import:

```text
Framework BOM
```

and then write no framework dependencies.

You expect the framework libraries to appear on the classpath.

They generally will not simply because the BOM was imported.

The BOM manages versions.

Your project still declares the libraries it uses.

---

# 113. Common Mistake: Overriding a BOM Without Understanding Why

Suppose a BOM manages:

```text
Library A → version X
Library B → version Y
```

You manually force:

```text
Library B → version Z
```

Perhaps Z is incompatible with A.

The BOM existed partly to coordinate compatible versions.

Overrides may be necessary, but they should be deliberate and tested.

---

# 114. Common Mistake: Importing Too Many BOMs

A project can import multiple BOMs, but this can create competing management rules.

For example:

```text
BOM A
→ manages library-x version 3

BOM B
→ manages library-x version 4
```

Now management precedence matters.

This can become difficult to reason about.

Do not import BOMs casually.

Know:

```text
why each BOM exists
what it manages
where overlap exists
which management should win
```

---

# 115. Dependency Management Precedence

Maven dependency version selection can involve several mechanisms:

```text
direct dependency versions
current POM dependency management
imported BOM management
parent dependency management
transitive dependency mediation
```

For a beginner, the important lesson is:

```text
A dependency version can come from somewhere other than
the visible <dependency> declaration.
```

When confused, use:

```bash
mvn dependency:tree
```

and:

```bash
mvn help:effective-pom
```

to investigate.

---

# 116. `dependency:tree` and Effective POM Solve Different Questions

Use:

```bash
mvn help:effective-pom
```

to understand:

```text
What Maven configuration/model is effective?
```

Use:

```bash
mvn dependency:tree
```

to understand:

```text
What dependencies were resolved and how are they related?
```

Together:

```text
Effective POM
→ configuration explanation

Dependency tree
→ dependency resolution explanation
```

---

# 117. BOM Inspection

If you import a BOM and want to understand what it manages, inspect:

* The BOM documentation
* Its POM
* Your project's effective POM
* Dependency tree after declaring relevant dependencies

Do not treat a BOM as a mysterious version switch.

Know what dependency family it is managing.

---

# 118. Parent POM as Build Policy

A parent POM can represent organizational build policy.

For example:

```text
VERIQTA Parent
│
├── Java release
├── encoding
├── dependency version policy
├── plugin version policy
├── test defaults
├── compiler defaults
└── build conventions
```

Then applications inherit the baseline.

This helps answer:

```text
How should VERIQTA Java projects build by default?
```

---

# 119. But a Parent POM Should Not Become a Dumping Ground

A bad parent POM can contain:

```text
dozens of irrelevant dependencies
hundreds of properties
plugins every project does not need
application-specific configuration
environment-specific values
credentials
unexplained profiles
old compatibility hacks
```

Eventually nobody knows why anything is there.

A parent should centralize genuinely shared build policy.

It should not become:

```text
every Maven configuration anyone has ever needed.
```

---

# 120. What Belongs in a Parent?

Good candidates include:

* Organization-wide Java release
* Encoding
* Common dependency versions
* Approved BOM imports
* Common plugin versions
* Common compiler configuration
* Common test-plugin configuration
* Common build-quality rules
* Reproducibility-related settings

Use judgment.

---

# 121. What May Not Belong in a Universal Parent?

Be cautious with:

* Application-specific dependencies
* One-service-only plugins
* Production credentials
* Database passwords
* Cloud secrets
* Machine-specific paths
* Environment-specific endpoints
* Configuration only one project needs
* Unrelated framework assumptions

Shared parents should remain broadly appropriate for their intended children.

---

# 122. Security and Parent POMs

Parent POMs can affect many projects.

Therefore a malicious or compromised parent can have a broad impact.

A parent may influence:

```text
plugins
repositories
dependencies
build behavior
distribution settings
```

Treat organizational parent POMs as supply-chain-sensitive artifacts.

Control:

* Who can publish them
* Where they are published
* How versions are changed
* Which repositories are trusted
* How updates are reviewed

---

# 123. Why Build Plugins Deserve Special Security Attention

Remember:

```text
Dependencies
→ code your application may compile/run with

Plugins
→ code Maven executes during the build
```

A build plugin can perform actions on the build machine.

Therefore centralized plugin management should not mean:

```text
trust every plugin automatically.
```

Organizations should deliberately control plugin sources and versions.

# 125. Parent Resolution in CI

A common mistake is:

```text
Build works on developer laptop.
Build fails in CI.
```

Why?

The developer may have:

```text
veriqta-parent
```

installed in:

```text
~/.m2
```

from an earlier local:

```bash
mvn install
```

CI starts with a clean environment.

The parent is not there.

Therefore, reusable organizational parents should generally be published to a repository that CI can access, or built as part of the same reactor when the project structure is designed that way.

Do not rely on invisible developer-machine state.

# 126. Local Repository Can Hide Missing Build Requirements

Suppose your laptop has:

```text
~/.m2/repository/com/veriqta/veriqta-parent/1.0.0
```

Your build succeeds.

Another engineer clones only the child project.

Their build fails.

This reveals:

```text
Your project depended on local state that was not reproducibly available.
```

A good build should make required artifact sources and project relationships explicit.

```xml
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0

                <groupId>org.junit.jupiter</groupId>
                <artifactId>junit-jupiter</artifactId>
                <version>${junit.version}</version>
            </dependency>

        </dependencies>
    </dependencyManagement>

    <build>
        <pluginManagement>
            <plugins>

                <plugin>
                    <groupId>org.apache.maven.plugins</groupId>
                    <artifactId>maven-compiler-plugin</artifactId>
                    <version>${maven.compiler.plugin.version}</version>

</project>
```

```text
        |
        +---- application-specific dependencies
        |
        +---- application-specific plugins
        |
        +---- application-specific source

        |
        v
Maven Lifecycle
        |
        v

```

A parent POM is not simply a way to make child POM files shorter.

Its deeper purpose is to establish controlled inheritance and reusable build policy.

`dependencyManagement` is not simply a list of dependencies. It defines how dependencies should be managed when projects use them.

A BOM is not a bundle of JARs. It is a way to import coordinated dependency-management information.

`pluginManagement` is not simply a list of plugins that Maven must execute. It provides controlled plugin versions and configuration for plugins participating in builds.

And the effective POM is where these layers finally come together.

Once you understand these distinctions, large Maven builds stop looking like unrelated XML files. You can trace where configuration originates, why a dependency has a particular version, why a plugin behaves a certain way, and how an organization can manage many Java builds without copying the same configuration into every repository.
