# Part 7: Maven Repositories and the .m2 Local Repository

## Introduction

In Part 6, you learned how to declare dependencies in `pom.xml`.

For example:

```xml
<dependency>
    <groupId>com.fasterxml.jackson.core</groupId>
    <artifactId>jackson-databind</artifactId>
    <version>2.17.2</version>
</dependency>
```

But this creates an important question:

Where does Maven actually get `jackson-databind` from?

The dependency is not stored inside your `pom.xml`.

The POM only describes what the project needs.

Maven must locate the actual artifact somewhere.

That is the job of Maven repositories.

The beginner mental model is:

```text
pom.xml
   |
   v
Maven
   |
   v
Local Repository
~/.m2/repository
   |
   +---- Artifact found?
   |        |
   |        v
   |       Use it
   |
   +---- Artifact missing?
            |
            v
      Remote Repository
            |
            v
     Download Artifact
            |
            v
     Cache Locally
            |
            v
         Use in Build
```

By the end of this part, you should understand:

* What a Maven repository is
* What an artifact repository does
* Where Maven stores downloaded dependencies
* What `.m2` is
* What `.m2/repository` contains
* How Maven coordinates map to directories
* What Maven Central is
* How Maven chooses where to search
* What JAR, POM, metadata, and checksum files are
* How releases and snapshots behave differently
* How additional repositories are configured
* What plugin repositories are
* Why random repositories are dangerous
* How Maven behaves offline
* How `mvn -o` works
* How `mvn -U` works
* How to troubleshoot corrupted local artifacts safely

The goal is to make Maven dependency downloads understandable rather than something that appears magically in the terminal.

---

# 1. What Is a Repository?

The word repository simply means a place where something is stored and organized.

You have already encountered repositories in other contexts.

For example, Git uses repositories to store project history and source code.

Maven also uses repositories, but Maven repositories serve a different purpose.

A Maven repository stores build artifacts and their associated metadata.

Examples include:

```text
JAR files
POM files
Plugin artifacts
Metadata
Checksums
Other packaged artifacts
```

A useful distinction is:

```text
Git Repository
→ primarily stores source code and version history

Maven Repository
→ stores versioned build artifacts and metadata
```

They solve different problems.

---

# 2. What Is an Artifact Repository?

An artifact repository is a system or storage location designed to organize and distribute software artifacts.

Recall from previous parts that an artifact is a packaged output or software component identified by Maven coordinates.

For example:

```text
com.fasterxml.jackson.core
:
jackson-databind
:
2.17.2
```

represents a specific version of a specific artifact.

An artifact repository provides somewhere Maven can retrieve that software.

Conceptually:

```text
Developer
    |
    v
Maven
    |
    v
Artifact Repository
    |
    +---- Library A
    +---- Library B
    +---- Plugin C
    +---- Internal Application D
```

---

# 3. What Can Maven Repositories Store?

A Maven repository can contain much more than third-party libraries.

Depending on the environment, it may contain:

* Open-source libraries
* Maven plugins
* Company libraries
* Shared internal modules
* Parent POMs
* BOMs
* Application artifacts
* Release artifacts
* Snapshot artifacts
* Metadata associated with those artifacts

For example, a company might build:

```text
com.company:payment-client:4.2.0
```

and publish it to an internal repository.

Another project can then declare:

```xml
<dependency>
    <groupId>com.company</groupId>
    <artifactId>payment-client</artifactId>
    <version>4.2.0</version>
</dependency>
```

Maven can retrieve it just like any other repository-managed dependency, assuming the repository is correctly configured and accessible.

---

# 4. Why Artifact Repositories Exist

Imagine a team without an artifact repository.

Developer A builds:

```text
payment-library.jar
```

and emails it to Developer B.

Developer B saves it somewhere.

Developer C gets another copy.

CI needs another copy.

Production packaging needs another copy.

Soon the team has:

```text
payment-library.jar
payment-library-new.jar
payment-library-final.jar
payment-library-fixed.jar
payment-library-final-fixed.jar
```

Nobody can confidently answer:

```text
Which version is this?

Who built it?

Which build should CI use?

Is this the same artifact everyone else has?

Has this file been modified?
```

Artifact repositories solve this by organizing software through stable coordinates and versions.

Instead of:

```text
Send me the JAR.
```

a project can say:

```text
I need:

com.company:payment-library:4.2.0
```

That is far more reproducible.

---

# 5. Maven Has Local and Remote Repositories

For a beginner, divide Maven repositories into two major categories:

```text
Maven Repositories
      |
      +---- Local Repository
      |
      +---- Remote Repositories
```

The local repository exists on the machine running Maven.

Remote repositories exist elsewhere and are normally reached over a network.

---

# 6. What Is the Maven Local Repository?

The Maven local repository is Maven's local storage area for artifacts on your computer.

By default, it is normally located at:

```text
~/.m2/repository
```

The `~` means:

```text
your user's home directory
```

On macOS or Linux, this may resolve conceptually to something like:

```text
/Users/username/.m2/repository
```

or:

```text
/home/username/.m2/repository
```

On Windows, the equivalent normally lives under the current user's home directory.

The important concept is not the exact username.

It is:

```text
User Home
   |
   v
.m2
   |
   v
repository
```

---

# 7. What Is `.m2`?

`.m2` is Maven's user-level directory.

On Unix-like systems, the leading dot means the directory is normally hidden from standard directory listings.

Its common location is:

```text
~/.m2
```

It can contain things such as:

```text
.m2/
├── repository/
└── settings.xml
```

Not every machine will necessarily have every file.

The two concepts are different:

```text
~/.m2/repository
→ local artifact repository

~/.m2/settings.xml
→ user-level Maven settings
```

Do not confuse them.

---

# 8. `.m2` Versus `.m2/repository`

Beginners often use these terms as though they mean exactly the same thing.

They do not.

`.m2` is the broader Maven user directory.

Inside it, `repository` is the local artifact repository.

Think:

```text
.m2
|
+---- repository
|
+---- settings.xml
```

Therefore:

```text
.m2
≠ only dependencies
```

and:

```text
.m2/repository
= Maven's default local artifact repository
```

---

# 9. Inspect `.m2` on macOS or Linux

Run:

```bash
ls -la ~/.m2
```

Break the command down:

```text
ls
→ list directory contents

-l
→ long listing format

-a
→ include hidden files/directories

~/.m2
→ Maven user directory
```

You may see:

```text
repository
settings.xml
```

or perhaps only:

```text
repository
```

depending on your configuration.

---

# 10. Inspect the Local Repository

Run:

```bash
ls ~/.m2/repository
```

You may see directories such as:

```text
com
org
io
net
```

These are not random directories.

They are part of Maven's coordinate-based storage structure.

---

# 11. Why Maven Needs a Local Repository

Suppose every time you ran:

```bash
mvn compile
```

Maven downloaded every dependency again.

A project with hundreds of dependencies would repeatedly:

* Consume bandwidth
* Wait on remote servers
* Depend heavily on network availability
* Slow down every build

Instead Maven can:

```text
Download once
     |
     v
Store locally
     |
     v
Reuse later
```

The local repository acts as a cache and as Maven's local artifact store.

---

# 12. The Local Repository Is More Than a Download Folder

It is tempting to think:

```text
.m2/repository
= downloads folder
```

That is incomplete.

The local repository can contain:

* Artifacts downloaded from remote repositories
* POM metadata
* Plugin artifacts
* Metadata about repositories
* Snapshot metadata
* Checksum-related information
* Artifacts installed locally with `mvn install`

Recall from Part 5:

```bash
mvn install
```

places the project's built artifact into the local Maven repository.

So the local repository contains both:

```text
Downloaded artifacts
+
Locally installed artifacts
```

---

# 13. What Is a Remote Repository?

A remote repository is an artifact repository Maven accesses over a network.

Conceptually:

```text
Your Computer
     |
     v
Maven
     |
     v
Internet / Company Network
     |
     v
Remote Artifact Repository
```

Remote repositories can be:

* Public
* Private
* Company-controlled
* Vendor-controlled
* Repository-manager proxies

---

# 14. What Is Maven Central?

Maven Central is the primary public repository used by the Maven ecosystem for a very large number of publicly published Java and JVM artifacts.

It contains artifacts from many open-source projects.

Examples include libraries from ecosystems such as:

* Jackson
* JUnit
* Apache Commons
* Logging libraries
* Testing libraries
* Framework components

When a beginner declares a common public dependency, Maven can often resolve it from Central without requiring the project to explicitly add a repository block.

---

# 15. Maven Central Is Not Maven Itself

Do not confuse:

```text
Apache Maven
```

with:

```text
Maven Central
```

Apache Maven is the build and project-management tool.

Maven Central is a public artifact repository.

Think:

```text
Maven
→ tool that needs artifacts

Maven Central
→ one major place Maven can retrieve public artifacts from
```

---

# 16. Maven Central Does Not Contain Everything

Not every artifact in the world exists in Central.

An organization may have private artifacts such as:

```text
com.veriqta.internal:deployment-library:1.0.0
```

that should not be public.

Those might exist in a private repository.

Some vendors may also distribute artifacts through repositories they control.

Therefore:

```text
Remote Repository
```

does not always mean:

```text
Maven Central
```

Central is one important remote repository.

---

# 17. Basic Dependency Resolution Flow

Suppose your POM contains:

```xml
<dependency>
    <groupId>com.fasterxml.jackson.core</groupId>
    <artifactId>jackson-databind</artifactId>
    <version>2.17.2</version>
</dependency>
```

Maven needs the corresponding artifact.

The simplified process is:

```text
pom.xml
   |
   v
Maven reads coordinates
   |
   v
Check local repository
   |
   +---- Found and usable
   |        |
   |        v
   |       Use it
   |
   +---- Not available
            |
            v
      Check configured
      remote repositories
            |
            v
       Locate artifact
            |
            v
         Download
            |
            v
      Store in local
         repository
            |
            v
       Use in build
```

---

# 18. Maven's Lookup Sequence

At beginner level, think about dependency resolution in this order:

```text
1. Project requests artifact

2. Maven identifies coordinates

3. Maven checks local repository

4. If remote resolution is required,
   Maven evaluates configured remote repositories

5. Maven retrieves artifact and metadata

6. Maven stores the retrieved files locally

7. Maven uses the artifact for the build
```

Real Maven resolution contains additional rules involving:

* Mirrors
* Repository policies
* Snapshot/update policies
* Plugin repositories
* Settings
* Metadata
* Authentication

We will introduce those without making the basic model unnecessarily complicated.

---

# 19. Coordinates Determine Repository Location

Maven does not simply throw every JAR into one huge folder.

It organizes artifacts according to Maven coordinates.

Recall:

```text
groupId
artifactId
version
```

For example:

```text
com.fasterxml.jackson.core
jackson-databind
2.17.2
```

These coordinates map into a directory structure.

---

# 20. Mapping `groupId` to Directories

The group ID:

```text
com.fasterxml.jackson.core
```

becomes directory segments:

```text
com/
fasterxml/
jackson/
core/
```

In other words:

```text
.
→ /
```

within the repository path.

Then Maven adds:

```text
artifactId
version
```

So:

```text
com.fasterxml.jackson.core
:
jackson-databind
:
2.17.2
```

maps conceptually to:

```text
com/
└── fasterxml/
    └── jackson/
        └── core/
            └── jackson-databind/
                └── 2.17.2/
```

---

# 21. Complete Local Repository Path

Inside the default local repository:

```text
~/.m2/repository/
└── com/
    └── fasterxml/
        └── jackson/
            └── core/
                └── jackson-databind/
                    └── 2.17.2/
```

This structure comes directly from the coordinates.

That means you can often predict where an artifact will be stored.

If you completed Part 6, try:

```bash
ls ~/.m2/repository/com/fasterxml/jackson/core/jackson-databind/
```

You may see one or more version directories.

For example:

```text
2.17.2
```

Then:

```bash
ls -la ~/.m2/repository/com/fasterxml/jackson/core/jackson-databind/2.17.2/
```

You should see several files associated with that artifact version.

# 23. What Files Are Stored There?

A repository directory may contain files such as:

```text
jackson-databind-2.17.2.jar
jackson-databind-2.17.2.pom
_remote.repositories
```

and potentially checksum or metadata-related files depending on how the artifact was retrieved and Maven's repository implementation.

Each file serves a purpose.

---

# 24. What Is the JAR File?

Example:

```text
jackson-databind-2.17.2.jar
```

This is the actual Java archive containing compiled classes and resources for the library.

Conceptually:

```text
Dependency Source
     |
     v
Compiled
     |
     v
Packaged
     |
     v
JAR Artifact
```

Your project uses classes from this artifact.

---

# 25. What Is the POM File in the Repository?

Example:

```text
jackson-databind-2.17.2.pom
```

This is metadata describing the artifact as a Maven project.

It can contain information Maven needs to understand things such as:

* Artifact identity
* Parent relationships
* Dependencies
* Dependency management
* Project metadata

This is important for transitive dependency resolution.

---

# 26. Why Maven Needs the Dependency's POM

Suppose your project declares:

```text
Library A
```

Library A depends on:

```text
Library B
Library C
```

How does Maven know?

It can read Library A's POM metadata.

Conceptually:

```text
Your pom.xml
    |
    v
Library A coordinates
    |
    v
Repository
    |
    +---- Library A JAR
    |
    +---- Library A POM
              |
              v
        Dependencies B and C
```

Maven then resolves B and C as necessary.

That is part of transitive dependency resolution.

---

# 27. What Are Metadata Files?

Repositories also use metadata files.

You may encounter files such as:

```text
maven-metadata.xml
```

Metadata can help Maven understand repository-level or version-level information.

This becomes especially important for:

* Snapshot artifacts
* Available versions
* Plugin resolution
* Update information

Do not assume every artifact directory contains exactly the same metadata files.

Their presence depends on the repository situation and how the artifact was obtained.

---

# 28. What Is `maven-metadata.xml`?

A simplified conceptual metadata file might describe:

```text
Artifact
→ available versions
→ latest/release information
→ snapshot information
→ update timestamps
```

For snapshots, metadata is particularly important because:

```text
1.0.0-SNAPSHOT
```

can represent changing builds over time.

Maven needs information that helps it locate the current snapshot artifact.

---

# 29. What Are Checksums?

A checksum is a calculated value derived from file contents.

It helps verify file integrity.

Conceptually:

```text
Artifact File
     |
     v
Checksum Algorithm
     |
     v
Checksum Value
```

If the downloaded file changes, its checksum normally changes too.

Repositories may publish checksum information alongside artifacts.

---

# 30. Why Checksums Matter

Imagine Maven expects an artifact with a known checksum.

The downloaded bytes should correspond to that expected content.

Checksums can help detect:

* Corrupted downloads
* Incomplete transfers
* Unexpected file changes

Checksums are useful for integrity verification.

They are not, by themselves, a complete software supply-chain security solution.

A checksum can tell you whether bytes match an expected checksum.

It does not automatically tell you whether the software itself is trustworthy or free from vulnerabilities.

---

# 31. Cached Artifacts

Once Maven downloads an artifact, it stores it in the local repository.

The next build may reuse it.

For example:

```text
FIRST BUILD

pom.xml
   |
   v
Local repository
   |
   X
Not found
   |
   v
Remote repository
   |
   v
Download
   |
   v
Cache locally


SECOND BUILD

pom.xml
   |
   v
Local repository
   |
   v
Found
   |
   v
Use cached artifact
```

This is why later builds are often faster.

---

# 32. The Local Repository Is Shared Across Maven Projects

Suppose you have:

```text
Project A
Project B
Project C
```

and all three need:

```text
jackson-databind:2.17.2
```

Maven does not normally download three separate copies into each project's source directory.

Instead:

```text
Project A ----\
Project B -----+----> ~/.m2/repository
Project C ----/
```

The same local repository can serve all three projects for that user.

---

# 33. Dependencies Are Not Normally Stored in the Project

Your Maven project might look like:

```text
veriqta-maven-app/
├── pom.xml
├── src/
└── target/
```

You do not normally need:

```text
veriqta-maven-app/lib/
```

full of manually downloaded dependencies.

The dependency definitions live in:

```text
pom.xml
```

and the artifacts are normally resolved through Maven repositories.

This helps keep the project cleaner and reproducible.

---

# 34. What Happens When an Artifact Is Missing Locally?

Suppose Maven needs:

```text
org.apache.commons:commons-lang3:3.16.0
```

but this directory does not yet contain the artifact:

```text
~/.m2/repository/org/apache/commons/commons-lang3/3.16.0/
```

Maven can attempt remote resolution.

Conceptually:

```text
Need commons-lang3:3.16.0
          |
          v
Check local repository
          |
          X
       Missing
          |
          v
Check configured remote repository
          |
          v
Found remotely
          |
          v
Download JAR/POM/metadata as needed
          |
          v
Store locally
          |
          v
Use in build
```

---

# 35. What If the Artifact Is Missing Remotely Too?

Suppose you declare:

```xml
<dependency>
    <groupId>com.example</groupId>
    <artifactId>does-not-exist</artifactId>
    <version>999.0.0</version>
</dependency>
```

Maven checks the appropriate repositories.

If the artifact cannot be found, Maven cannot build the dependency graph successfully.

You may see an error containing:

```text
Could not find artifact
```

or:

```text
Could not resolve dependencies
```

This is a repository-resolution problem.

---

# 36. Missing Artifact Reasoning

Do not immediately conclude:

```text
Maven is broken.
```

Ask:

```text
Are the coordinates correct?
        |
        v
Does this version exist?
        |
        v
Should it exist in Central?
        |
        v
Does it require another repository?
        |
        v
Is that repository configured?
        |
        v
Can this machine reach it?
        |
        v
Does it require authentication?
```

This reasoning prevents random configuration changes.

---

# 37. Release Artifacts

A release version represents a fixed published version.

Examples:

```text
1.0.0
2.5.1
3.16.0
```

Conceptually:

```text
Release 1.0.0
→ published artifact
→ intended to remain unchanged
```

If your POM says:

```xml
<version>1.0.0</version>
```

you expect that coordinate to identify a stable artifact.

---

# 38. Release Resolution

Suppose Maven resolves:

```text
com.example:library:1.0.0
```

and downloads it locally.

Later builds can reuse:

```text
~/.m2/repository/com/example/library/1.0.0/
```

A release coordinate is intended to be immutable.

Publishing different bytes repeatedly under the same release version is bad repository practice because it destroys reproducibility.

Think:

```text
1.0.0
→ one stable published release
```

---

# 39. Why Immutable Releases Matter

Imagine Monday:

```text
library:1.0.0
→ File A
```

and Friday:

```text
library:1.0.0
→ File B
```

without changing the version.

Now:

```text
Developer A
→ cached File A

Developer B
→ downloads File B

Both POMs say:
1.0.0
```

The same coordinates produce different software.

That is bad for:

* Reproducibility
* Incident investigation
* Auditing
* Rollbacks
* Security analysis

Release versions should therefore represent fixed artifacts.

---

# 40. What Is a SNAPSHOT?

A snapshot is a development version that may change.

Example:

```text
1.0.0-SNAPSHOT
```

The word:

```text
SNAPSHOT
```

communicates:

```text
This is not necessarily a final immutable release.
```

It represents ongoing development toward a future release.

---

# 41. Release Versus Snapshot

A simple mental model:

```text
RELEASE

1.0.0
→ fixed published version


SNAPSHOT

1.1.0-SNAPSHOT
→ development version
→ may be updated
```

This difference changes repository behavior.

---

# 42. Why Snapshot Resolution Is Different

Suppose your POM requests:

```text
com.veriqta:shared-library:1.0.0-SNAPSHOT
```

Maven cannot always assume the locally cached copy is permanently current.

The remote repository may contain a newer snapshot build.

Therefore snapshot resolution involves update policies and metadata.

Conceptually:

```text
Need 1.0.0-SNAPSHOT
       |
       v
Check local state
       |
       v
Should Maven check remote?
       |
       v
Consult repository policy/metadata
       |
       v
Possibly download newer snapshot
```

---

# 43. Timestamped Snapshots

Remote Maven repositories commonly store snapshot builds using timestamped artifact names.

You might request:

```text
1.0.0-SNAPSHOT
```

while repository metadata maps it to a concrete snapshot build conceptually like:

```text
1.0.0-20260907.021500-4
```

The exact timestamp and build number vary.

The important mental model is:

```text
Logical Version
1.0.0-SNAPSHOT

        |
        v

Specific Snapshot Build
1.0.0-<timestamp>-<build-number>
```

Metadata helps Maven determine which snapshot artifact corresponds to the requested snapshot.

---

# 44. Why Snapshots Can Change

Suppose a team publishes:

```text
1.0.0-SNAPSHOT
```

at 9 AM.

Then they make changes and publish another snapshot at 3 PM.

The logical dependency version may still be:

```text
1.0.0-SNAPSHOT
```

but the underlying artifact can be newer.

This is useful during active development.

It is less predictable than fixed release versions.

---

# 45. Why Production Should Treat Snapshots Carefully

Imagine a production build depends on:

```text
payment-library:2.0.0-SNAPSHOT
```

Build A may resolve one snapshot.

Build B may later resolve another.

Both POMs still appear to request:

```text
2.0.0-SNAPSHOT
```

This weakens reproducibility.

For production releases, fixed release versions are generally preferable.

---

# 46. What Is Repository Configuration?

Maven needs to know which remote repositories are available.

Repository configuration can come from several places, including:

* Maven defaults
* Project POMs
* Parent POMs
* `settings.xml`
* Mirrors
* Profiles

For beginners, remember:

```text
Repository behavior
≠ controlled only by pom.xml
```

Your effective Maven environment matters too.

---

# 47. Central Does Not Normally Need to Be Added Manually

For normal Maven projects using public artifacts available in Central, you generally do not need to add a repository declaration for Central manually.

Maven's default model already provides access to Central unless the environment changes that behavior through settings, mirrors, or other configuration.

Therefore avoid adding configuration simply because you saw it in a random tutorial.

Use the minimum repository configuration actually required.

---

# 48. Adding an Additional Repository

A project can declare another repository using:

```xml
<repositories>
    <repository>
        <id>example-repository</id>
        <url>https://repository.example.com/maven2</url>
    </repository>
</repositories>
```

This tells Maven about another location for dependency resolution.

Important:

Do not copy this example URL into a real project.

It is only demonstrating structure.

---

# 49. Understanding the Repository Declaration

Consider:

```xml
<repository>
    <id>company-releases</id>
    <url>https://repo.company.example/releases</url>
</repository>
```

`id`:

```text
company-releases
```

is an identifier for the repository configuration.

`url`:

```text
https://repo.company.example/releases
```

is the repository location.

Repository IDs can also matter when connecting repository definitions to settings such as authentication.

---

# 50. When an Additional Repository Might Be Needed

Examples include:

* Private company artifacts
* Vendor artifacts not published to Central
* Internal development repositories
* Controlled organizational artifact infrastructure

Do not add an additional repository unless there is a real reason.

---

# 51. Public Repository Versus Private Repository

A public repository may allow anyone to retrieve public artifacts.

A private repository may require:

* Authentication
* Authorization
* VPN access
* Company network access
* Tokens
* Credentials
* Client certificates

Conceptually:

```text
Maven
   |
   v
Private Repository
   |
   +---- Authentication
   |
   +---- Authorization
   |
   v
Artifact
```

---

# 52. Do Not Hardcode Repository Passwords in `pom.xml`

Suppose a private repository requires credentials.

Do not treat this as permission to write:

```text
username
password
token
```

directly into a POM committed to Git.

Credentials should be managed securely through appropriate Maven settings, CI secret systems, environment-specific mechanisms, or organizational credential tooling.

A POM may be shared publicly or across many developers.

Secrets should not be embedded in source-controlled project files.

---

# 53. Repository Managers in Organizations

Companies often use repository-management products.

Instead of every developer contacting many public repositories directly, the architecture may look like:

```text
Developer / CI
      |
      v
Company Repository Manager
      |
      +---- Internal Artifacts
      |
      +---- Cached Public Artifacts
      |
      +---- Approved External Sources
```

This gives organizations more control over:

* Availability
* Access
* Caching
* Security
* Artifact retention
* Internal releases
* External dependency policy

---

# 54. What Is a Maven Mirror?

A Maven mirror allows Maven to use one repository endpoint in place of another repository or set of repositories according to configuration.

A company might configure:

```text
Maven
   |
   v
Company Mirror
   |
   v
Approved artifact sources
```

rather than allowing every build to contact Central directly.

Mirror configuration commonly lives in:

```text
settings.xml
```

This is why two developers with the same POM can sometimes have different repository behavior.

---

# 55. POM Versus `settings.xml` for Repository Behavior

Think:

```text
pom.xml
→ project build definition

settings.xml
→ environment/user Maven configuration
```

A POM might say what repositories a project needs.

`settings.xml` can affect things such as:

* Mirrors
* Authentication
* Proxies
* Profiles
* Local repository location

This distinction matters in enterprise environments.

---

# 56. Inspect Effective Settings

Run:

```bash
mvn help:effective-settings
```

Break it down:

```text
mvn
→ Maven CLI

help
→ Maven Help Plugin prefix

effective-settings
→ goal
```

This shows the effective settings Maven sees after considering the relevant configuration.

It can help answer:

```text
Is a mirror configured?

Which repository-related settings are active?

Is a proxy configured?

What environment-specific configuration is Maven using?
```

Be careful when sharing output from settings-related commands because environment configuration may contain sensitive information.

---

# 57. Plugin Repositories

Maven resolves not only project dependencies.

It also needs plugins.

Recall:

```bash
mvn dependency:tree
```

uses a Maven plugin.

And lifecycle operations such as compilation, testing, and packaging are performed through plugins.

Therefore Maven also needs a way to resolve plugin artifacts.

---

# 58. Dependency Repository Versus Plugin Repository

Maven distinguishes between repositories used for project dependencies and repositories used for build plugins.

Conceptually:

```text
Repositories
→ project dependencies

Plugin Repositories
→ Maven build plugins
```

Central commonly provides both many dependencies and many Maven plugins, but the configuration concepts are distinct.

---

# 59. Configuring a Plugin Repository

A project can contain:

```xml
<pluginRepositories>
    <pluginRepository>
        <id>example-plugin-repository</id>
        <url>https://plugins.example.com/maven2</url>
    </pluginRepository>
</pluginRepositories>
```

Again, the URL is only structural example data.

Do not add random plugin repositories to a real project.

---

# 60. Why Maven Separates Plugin Repositories

Plugins execute build logic.

Dependencies provide software used by your project.

These are different roles.

Think:

```text
Dependency
→ code your application uses

Plugin
→ code Maven executes to perform build work
```

Because plugins execute during builds, controlling their source is especially important.

---

# 61. Why Adding Random Repositories Is Dangerous

Suppose Maven reports:

```text
Could not find artifact
```

A beginner searches the internet.

A forum says:

```text
Add this repository.
```

The beginner copies an unknown URL into `pom.xml`.

The build works.

Problem solved?

Not necessarily.

You have just changed the software supply chain.

---

# 62. Repository Trust Is a Security Decision

When you add a repository, you are effectively saying:

```text
Maven may retrieve software from this location.
```

That software may participate in:

* Compilation
* Testing
* Packaging
* Runtime dependencies
* Build plugin execution

Therefore repository configuration is a trust decision.

---

# 63. Risks of Untrusted Repositories

Potential risks include:

* Malicious artifacts
* Compromised dependencies
* Unexpected versions
* Abandoned repository infrastructure
* Dependency substitution
* Malicious build plugins
* Unreliable availability
* Weak transport or repository controls

Do not solve resolution failures by expanding trust blindly.

---

# 64. Safe Repository Reasoning

Before adding a repository, ask:

```text
Why is this repository required?
        |
        v
Who operates it?
        |
        v
Is it the official source?
        |
        v
Does the project's official documentation require it?
        |
        v
Does my organization approve it?
        |
        v
Can the artifact be obtained from an existing trusted repository?
```

If you cannot answer those questions, do not casually add it.

---

# 65. What Is an Offline Maven Build?

Maven normally has the ability to contact remote repositories when required.

Offline mode tells Maven not to use the network for repository resolution.

Run:

```bash
mvn -o package
```

The option:

```text
-o
```

means:

```text
offline
```

You can also encounter the longer form:

```bash
mvn --offline package
```

---

# 66. What Happens With `mvn -o`?

Suppose you run:

```bash
mvn -o package
```

Maven must rely on what is already available locally.

Conceptually:

```text
pom.xml
   |
   v
Maven Offline
   |
   v
Local Repository
   |
   +---- Everything available?
   |          |
   |          v
   |        Build
   |
   +---- Required artifact missing?
              |
              v
            Fail
```

Maven cannot simply download a missing dependency while offline.

---

# 67. Offline Does Not Mean "No Dependencies"

Offline mode does not remove dependencies.

It means:

```text
Do not contact remote repositories.
```

Maven can still use dependencies already available locally.

This distinction is important.

---

# 68. Practical Offline Test

First ensure your project builds normally:

```bash
mvn clean package
```

Then run:

```bash
mvn -o clean package
```

If every required artifact and plugin is already available locally, the build may succeed.

This demonstrates the role of:

```text
~/.m2/repository
```

---

# 69. Why Offline Builds Can Fail Unexpectedly

You may think:

```text
I already downloaded my dependencies.
```

But Maven may also need:

* Build plugins
* Plugin dependencies
* Parent POMs
* BOMs
* Metadata
* Other artifacts not previously cached

If one required component is absent locally, offline resolution can fail.

So:

```text
Dependencies cached
```

does not necessarily mean:

```text
Everything required for an offline build is cached.
```

---

# 70. What Does `-U` Mean?

Maven supports:

```bash
mvn -U package
```

`-U` tells Maven to force checks for updated releases and snapshots on remote repositories according to Maven's update behavior.

It is commonly used when Maven's cached resolution state appears stale, especially around snapshots or previously unavailable artifacts.

A beginner mental model:

```text
Normal build
→ use normal repository update rules

-U
→ request stronger remote update checking
```

---

# 71. `-U` Is Not "Upgrade All My Dependency Versions"

This is extremely important.

Suppose your POM says:

```xml
<version>2.17.2</version>
```

Running:

```bash
mvn -U package
```

does not mean:

```text
Change 2.17.2 to the newest Jackson version.
```

Maven still follows your dependency coordinates.

`-U` concerns repository update checks.

It is not a dependency-version upgrade command.

---

# 72. When `mvn -U` Can Be Useful

Possible situations include:

* A newer snapshot has been published
* Maven previously cached a failed resolution attempt
* A remote artifact became available after an earlier failure
* Repository metadata needs to be refreshed

For example:

```bash
mvn -U clean package
```

may cause Maven to recheck remote state more aggressively than a normal build.

---

# 73. Do Not Use `-U` as a Universal Fix

If the error is:

```text
cannot find symbol
```

because you misspelled a Java class, `-U` does not fix the source code.

If your POM contains the wrong artifact ID, `-U` does not magically discover what you intended.

If authentication is invalid, `-U` does not grant permission.

Use it when the problem actually relates to repository update state.

---

# 74. Failed Resolution Can Be Cached

Suppose Maven tries to resolve:

```text
com.company:library:1.0.0
```

but the artifact is unavailable.

Maven may store information about the failed attempt locally and avoid repeatedly contacting the remote repository until the relevant update interval passes.

Later, the artifact is published.

A normal build may still report that resolution was previously attempted and will not be retried until the update interval expires.

This is one situation where:

```bash
mvn -U package
```

can be useful.

---

# 75. What Is a Corrupted Local Artifact?

A local artifact is corrupted when the locally stored file is incomplete, damaged, or otherwise unusable.

For example:

```text
~/.m2/repository/com/example/library/1.0.0/library-1.0.0.jar
```

may exist but not contain valid expected data.

Possible causes can include:

* Interrupted downloads
* Filesystem problems
* Manual file modification
* Tooling failures
* Bad cached state

This is less common than simple POM mistakes, so do not assume corruption first.

---

# 76. Symptoms of Local Repository Problems

Possible symptoms include:

* Archive-reading errors
* Checksum failures
* Artifact descriptor errors
* Builds behaving differently across machines
* Local build failure while clean CI succeeds
* A dependency file existing locally but being unusable

However, these symptoms can have other causes too.

Investigate before deleting anything.

---

# 77. The Dangerous Beginner Fix

A common internet suggestion is:

```bash
rm -rf ~/.m2/repository
```

This deletes the entire local Maven repository.

Do not make this your first troubleshooting step.

Why?

Because you may remove:

* Thousands of cached artifacts
* Locally installed artifacts
* Dependencies required for offline work
* Plugins
* Parent POMs
* Internal artifacts not easily re-obtained

Then Maven must rebuild the entire local cache.

---

# 78. Why Deleting All of `.m2` Is Even Worse

Never casually run:

```bash
rm -rf ~/.m2
```

This can remove more than the repository.

Remember:

```text
~/.m2/
├── repository/
└── settings.xml
```

If `settings.xml` contains important Maven configuration, deleting `.m2` may remove:

* Repository configuration
* Mirror configuration
* Proxy configuration
* Authentication configuration
* Profiles

Treat `.m2` as important environment configuration.

---

# 79. Safer Troubleshooting Principle

Use the smallest possible repair.

Suppose the problem concerns:

```text
com.example:library:1.0.0
```

Map it to:

```text
~/.m2/repository/com/example/library/1.0.0/
```

Investigate that directory specifically.

Do not immediately destroy unrelated artifacts.

The principle is:

```text
Identify
→ Inspect
→ Isolate
→ Repair smallest scope
→ Re-resolve
→ Verify
```

---

# 80. Safely Inspect an Artifact Directory

First:

```bash
ls -la ~/.m2/repository/com/example/library/1.0.0/
```

Do not delete anything yet.

Look for:

* Expected JAR
* Expected POM
* Metadata
* Last-updated markers
* Unexpected zero-byte or obviously incomplete files

Then compare the error Maven reports with what exists locally.

---

# 81. `.lastUpdated` Files

You may encounter files ending with:

```text
.lastUpdated
```

These can record information associated with unsuccessful or incomplete repository resolution attempts.

For example, Maven may have tried to retrieve an artifact and failed.

The presence of a directory therefore does not prove:

```text
The dependency downloaded successfully.
```

Always inspect the contents.

---

# 82. Directory Exists Does Not Mean Artifact Exists

Suppose this exists:

```text
~/.m2/repository/com/example/library/1.0.0/
```

but inside you find only metadata or `.lastUpdated` files.

The actual:

```text
library-1.0.0.jar
```

may still be missing.

Therefore:

```text
Directory exists
≠ artifact successfully resolved
```

---

# 83. Targeted Local Cleanup

If you have strong evidence that one cached artifact version is bad and it can safely be downloaded again, you can remove only that artifact version directory.

Conceptually:

```text
Bad:
Delete entire ~/.m2/repository

Better:
Remove only the confirmed bad artifact version
```

For example, after verifying the exact path:

```bash
rm -rf ~/.m2/repository/com/example/library/1.0.0
```

WARNING:

`rm -rf` permanently removes the specified directory tree.

Before running it:

1. Confirm the path carefully.
2. Confirm the artifact can be retrieved again.
3. Make sure you are not deleting a locally installed artifact that exists nowhere else.
4. Do not run it with an incomplete or incorrectly typed path.

Then rerun Maven so the artifact can be resolved again.

---

# 84. Safer Alternative Before Deleting

Before removing anything, try to determine whether:

```bash
mvn -U clean package
```

is enough.

If the problem is stale failed-resolution metadata rather than a corrupted binary, a forced update check may resolve it without manual deletion.

The troubleshooting sequence should be:

```text
Read error
   |
   v
Verify coordinates
   |
   v
Verify repository access
   |
   v
Inspect dependency tree/settings
   |
   v
Try appropriate update
   |
   v
Inspect exact local artifact
   |
   v
Targeted cleanup only if justified
```

## Beginner Mistake

## Better Investigation


Then:


Then:


Deleting the local cache cannot create an artifact that does not exist remotely.

## Problem

The dependency was unavailable yesterday.

Today it has been published, but Maven still reports the previous failed resolution.

## Investigation

Confirm the artifact now exists in the expected trusted repository.

Then try:

```bash
mvn -U clean package
```

## Why?

Maven may have cached information about the previous failed resolution.

`-U` requests updated repository checks.

# 87. Local Repository Troubleshooting Scenario 3

## Problem

The artifact exists locally, but Maven reports that the JAR is invalid or unreadable.

## Investigation

Locate the exact coordinate.

Example:

```text
groupId:
com.example

artifactId:
library

version:
1.0.0
```

Map it:

```text
~/.m2/repository/com/example/library/1.0.0/
```

Inspect the files.

If corruption is confirmed and the artifact is safely available remotely, remove only that version directory and rebuild.

# 88. Local Repository Troubleshooting Scenario 4

## Problem

Your build succeeds normally but fails with:

```bash
mvn -o package
```

## Likely Meaning

At least one required artifact is not available locally.

It might be:

* A dependency
* A plugin
* A plugin dependency
* A parent POM
* A BOM
* Other required metadata/artifact

## Fix

Run an online build in a trusted network environment so required artifacts can be resolved.

Then test offline again.

# 89. Local Repository Troubleshooting Scenario 5

## Problem

Your laptop builds successfully.

CI reports:

```text
Could not resolve dependencies
```

## Do Not Conclude

```text
The POM must be correct because my laptop works.
```

Your laptop may already have the artifact cached.

CI may have a clean repository.

Investigate:

```text
Is the dependency really available from a configured remote repository?

Did I only install it locally?

Does CI have the correct settings?

Does CI have repository credentials?

Is a mirror required?

Can CI reach the repository?
```

This is a common DevOps scenario.

# 90. Locally Installed Artifacts Can Hide Problems

Suppose you previously ran:

```bash
mvn install
```

on:

```text
shared-library
```

Now:

```text
~/.m2/repository/com/veriqta/shared-library/1.0.0/
```

exists locally.

Another project depends on:

```text
com.veriqta:shared-library:1.0.0
```

Your laptop succeeds.

But the artifact was never deployed to a remote repository.

CI starts with a clean environment.

Result:

```text
Developer laptop
→ BUILD SUCCESS

CI
→ Could not find artifact
```

This is why local success does not prove remote reproducibility.

---

# 91. `install` Versus `deploy`

Recall:

```bash
mvn install
```

places your artifact into the local repository.

Conceptually:

```text
Project
   |
   v
mvn install
   |
   v
~/.m2/repository
```

By contrast, Maven's `deploy` lifecycle phase is used to publish artifacts to a configured remote repository as part of a deployment workflow.

Conceptually:

```text
Project
   |
   v
mvn deploy
   |
   v
Remote Repository
```

These are different destinations.

---

# 92. Why `mvn install` Is Useful

Suppose you are developing:

```text
library-a
```

and:

```text
application-b
```

locally.

Application B depends on Library A.

You can build Library A:

```bash
mvn install
```

Then Maven places Library A into the local repository.

Application B can resolve it locally.

This is useful during local multi-project development.

---

# 93. Why `mvn install` Is Not Enough for a Team

Your local repository belongs to your environment.

If another developer or CI needs the artifact, your local `mvn install` does not place it on their machines.

For shared artifacts, teams normally need an accessible remote repository.

Think:

```text
install
→ my local Maven repository

deploy
→ shared configured remote repository
```

---

# 94. Repository Resolution in CI/CD

In CI, Maven may run on an ephemeral machine or container.

Conceptually:

```text
CI Job Starts
    |
    v
Fresh Environment
    |
    v
Maven Build
    |
    v
Dependencies Needed
    |
    v
Remote Repository
```

Downloading every dependency from scratch can take time.

CI systems therefore often cache Maven's local repository or selected portions of it.

---

# 95. Maven Cache in CI

Conceptually:

```text
CI Run 1
   |
   v
Download dependencies
   |
   v
Save dependency cache

CI Run 2
   |
   v
Restore cache
   |
   v
Reuse artifacts
```

This can significantly improve build speed.

But cache configuration should not replace proper dependency declaration and repository configuration.

---

# 96. Cache Is Not the Source of Truth

A CI cache should be treated as a performance mechanism.

It should not be the only place where a required company artifact exists.

Good architecture:

```text
Remote Repository
→ source for published artifact

CI Cache
→ temporary performance optimization
```

Bad architecture:

```text
Artifact exists only in one old CI cache
```

Published artifacts should live in an appropriate artifact repository.

# 120. Practice: Repository Failure Reasoning

Suppose Maven reports:

```text

8. Check network connectivity.

9. Inspect local resolution state.

10. Re-run only after identifying a likely cause.
```

This is engineering troubleshooting.

# 124. Production Repository Principles

For production-oriented builds:

* Use trusted repositories.
* Keep release artifacts immutable.
* Control credentials securely.
* Avoid random repository additions.
* Prefer reproducible versions.
* Understand mirrors.
* Audit dependency sources.
* Inspect transitive dependencies.
* Keep CI repository configuration controlled.
* Do not rely on one developer's `.m2`.
* Publish shared internal artifacts properly.
* Treat build plugins as executable supply-chain dependencies.

# 125. Common Beginner Questions

## "Does Maven download dependencies into my project?"

Normally, no.

It stores repository artifacts in the local Maven repository.

---

## "Where are my downloaded dependencies?"

Usually:

```text
~/.m2/repository
```

---

## "Does `mvn clean` delete them?"

No.

`mvn clean` normally removes project build output, not the Maven local repository.

---

## "Why does the first build take longer?"

Maven may need to download dependencies, plugins, POMs, and metadata.

---

## "Why is the second build faster?"

Many required artifacts are already cached locally.

---

## "Does `-U` upgrade my dependency versions?"

No.

It requests updated remote checks. Your declared dependency versions do not automatically become newer releases just because you use `-U`.

---

## "Can Maven work without internet?"

Yes, if all required artifacts are already available locally and you use offline mode where appropriate.

---

## "Does an artifact directory mean the JAR exists?"

No.

The directory may contain only failed-resolution markers or metadata.

---

## "Should I delete `.m2` when Maven breaks?"

No.

Investigate the specific failure first.

# 129. Knowledge Check Answers

## 1. What is a Maven repository?

A structured location used to store and retrieve Maven artifacts and associated metadata.

## 2. What is an artifact repository?

A repository designed to organize, store, version, and distribute software artifacts.

## 3. What can it contain?

JARs, POMs, plugins, metadata, checksums, snapshots, releases, parent POMs, BOMs, and other packaged artifacts.

## 4. Local versus remote?

A local repository exists on the machine running Maven. A remote repository is accessed over a network.

## 5. What is Maven Central?

A major public repository containing many Java and JVM ecosystem artifacts.

## 6. Is Central Maven itself?

No.

Apache Maven is the build tool. Maven Central is an artifact repository.

## 7. Does everything exist in Central?

No.

Private, internal, or vendor-specific artifacts may live elsewhere.

## 8. What is `.m2`?

Maven's user-level directory, commonly under the user's home directory.

## 9. What is `.m2/repository`?

Maven's default local artifact repository.

## 10. Are they identical?

No.

`repository` is normally one component inside `.m2`.

## 11. Why maintain a local repository?

To cache artifacts, reuse them across builds, support local installs, and reduce repeated network downloads.

## 12. Default path?

Typically:

```text
~/.m2/repository
```

## 13. One repository per project?

Normally no.

Multiple Maven projects for the same user share the local repository.

## 14. How does `groupId` map?

Dots become directory separators.

For example:

```text
org.example
```

becomes:

```text
org/example
```

## 15. Path for `org.example:demo:1.0.0`?

```text
~/.m2/repository/org/example/demo/1.0.0/
```

## 16. What does the JAR contain?

Compiled Java classes and associated resources for the artifact.

## 17. Why retrieve dependency POMs?

They contain Maven metadata needed to understand the artifact, including dependency relationships.

## 18. Repository metadata?

Information Maven uses to understand artifact versions, snapshots, updates, and repository state.

## 19. Why important for snapshots?

Because Maven may need metadata to determine which concrete timestamped build represents a logical SNAPSHOT version.

## 20. Checksum?

A value derived from file contents that can help verify integrity.

## 21. Does it prove security?

No.

Integrity verification alone does not prove software is trustworthy or vulnerability-free.

## 22. Artifact exists locally?

Maven can normally reuse it according to repository and update rules.

## 23. Missing locally?

Maven can attempt to resolve it from configured remote repositories.

## 24. Missing remotely?

Dependency resolution fails.

## 25. Release version?

A fixed published software version such as:

```text
1.0.0
```

## 26. Why immutable?

So the same coordinates continue to represent the same artifact, supporting reproducibility.

## 27. SNAPSHOT?

A development version that may be updated over time.

## 28. Why remote checks?

Because a newer build of the same logical SNAPSHOT version may exist remotely.

## 29. Timestamped snapshot?

A concrete published snapshot build identified using a timestamp and build number behind a logical `-SNAPSHOT` version.

## 30. Why less reproducible?

The underlying artifact associated with the same SNAPSHOT coordinate can change.

## 31. Repository configuration sources?

POMs, parent POMs, Maven defaults, settings, profiles, and mirrors can all influence repository behavior.

## 32. When add another repository?

When a required trusted artifact is legitimately hosted outside the repositories already available to Maven.

## 33. Why avoid random repositories?

They expand the build's trust boundary and can introduce malicious, compromised, or unreliable artifacts.

## 34. Plugin repository?

A repository Maven can use for resolving build plugins.

## 35. Why security-sensitive?

Plugins execute code during the build.

## 36. `mvn -o package`?

Runs Maven in offline mode while executing the requested build.

## 37. Can offline mode download?

No.

## 38. Why can offline fail?

A required dependency, plugin, parent POM, BOM, plugin dependency, or other artifact may not be cached locally.

## 39. `mvn -U package`?

Requests Maven to perform updated remote checks for relevant releases and snapshots while running the build.

## 40. Does it automatically upgrade dependency versions?

No.

It does not rewrite your declared dependency version to the newest release.

## 41. Why remember failed resolution?

Maven can cache failed repository-resolution information according to update policies to avoid repeatedly making unsuccessful requests.

## 42. Corrupted dependency?

A locally stored artifact that is incomplete, damaged, or otherwise unusable.

## 43. Why not delete all `.m2/repository` first?

It removes unrelated cached and locally installed artifacts and often fails to address the actual root cause.

## 44. Why is deleting `.m2` worse?

It may also remove important Maven settings and environment configuration.

## 45. `.lastUpdated` files?

They can indicate previous unsuccessful or incomplete repository resolution attempts.

## 46. Why can laptop succeed while CI fails?

The laptop may have cached or locally installed artifacts that CI does not have, or the environments may use different settings, credentials, mirrors, or network access.

## 47. What does `mvn install` do?

It installs the project's built artifact into the local Maven repository.

## 48. What does `mvn deploy` do?

It publishes the artifact to a configured remote repository as part of the deploy lifecycle.

## 49. Why can local installs hide problems?

A project may resolve an artifact locally even though that artifact was never published somewhere CI or other developers can access.

## 50. Why are repositories part of supply-chain security?

Because repositories are sources from which builds retrieve code and build components that can affect the final software.

# 130. Final Mental Model

Maven does not magically know where libraries are.

The project declares what it needs:

```text
pom.xml
```

Maven converts that declaration into coordinates:

```text
groupId
:
artifactId
:
version
```

Then resolution begins:

```text
                     pom.xml
                        |
                        v
                      Maven
                        |
                        v
                 Artifact Needed
                        |
                        v
               ~/.m2/repository
                        |
              +---------+---------+
              |                   |
            Found               Missing
              |                   |
              v                   v
             Use           Remote Repository
                                  |
                        +---------+---------+
                        |                   |
                      Found               Missing
                        |                   |
                        v                   v
                     Download             FAIL
                        |
                        v
                Verify / Cache
                        |
                        v
                ~/.m2/repository
                        |
                        v
                       Use
                        |
                        v
                      Build
```

For transitive dependencies:

```text
Your POM
   |
   v
Dependency A
   |
   v
Dependency A's POM
   |
   +---- Dependency B
   |
   +---- Dependency C
             |
             v
       More Resolution
```

For releases:

```text
1.0.0
→ fixed artifact
→ intended to remain immutable
```

For snapshots:

```text
1.1.0-SNAPSHOT
→ changing development version
→ metadata/update checks
→ potentially newer snapshot build
```

For offline mode:

```text
mvn -o package

Maven
  |
  v
Local Repository Only
```

For forced update checking:

```text
mvn -U package

Maven
  |
  v
Recheck relevant remote state
```

And when something breaks, do not start with:

```text
Delete .m2
```

Start with:

```text
Observe error
     |
     v
Identify artifact
     |
     v
Verify coordinates
     |
     v
Determine expected repository
     |
     v
Check local state
     |
     v
Check settings/mirrors
     |
     v
Check network/authentication
     |
     v
Check remote availability
     |
     v
Repair smallest affected area
     |
     v
Rebuild
     |
     v
Verify
```

Once you understand this flow, Maven downloads stop looking like mysterious terminal activity.

You can look at a coordinate such as:

```text
com.fasterxml.jackson.core:jackson-databind:2.17.2
```

and understand:

```text
What Maven is looking for
→ where it looks locally
→ how the coordinate becomes a directory
→ when Maven goes remote
→ what gets downloaded
→ why POM metadata matters
→ why the artifact is cached
→ how future builds reuse it
→ why CI may behave differently
→ how snapshots differ from releases
→ and how to troubleshoot resolution without blindly deleting your Maven environment
```

That repository mental model is fundamental for Maven, Java builds, CI/CD pipelines, artifact management, and production software supply chains.
