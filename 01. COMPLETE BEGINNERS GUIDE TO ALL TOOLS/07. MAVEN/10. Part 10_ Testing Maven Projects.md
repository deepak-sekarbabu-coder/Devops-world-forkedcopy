# Part 10: Testing Maven Projects

## Introduction

In Part 9, you learned how Maven compiles Java source code.

Our build flow has reached this point:

```text
Java Source
    |
    v
mvn compile
    |
    v
Maven Compiler Plugin
    |
    v
target/classes
```

But successful compilation answers only one question:

```text
Can this source code be compiled?
```

It does not answer:

```text
Does the application behave correctly?
```

A program can compile perfectly and still contain serious bugs.

For example:

```java
public int add(int first, int second) {
    return first - second;
}
```

This is valid Java.

It compiles.

But the behavior is wrong.

If the method is supposed to add two numbers:

```text
2 + 3
```

the expected result is:

```text
5
```

but this implementation returns:

```text
-1
```

Compilation cannot detect that business-logic mistake.

Testing helps us detect it.

In this part, we will expand `veriqta-maven-app` with automated tests and understand how Maven compiles, discovers, runs, reports, and reacts to tests.

Our new mental model will become:

```text
Application Source
        |
        v
Compile
        |
        v
Application Classes
        |
        v
Test Source
        |
        v
Test Compile
        |
        v
Test Classes
        |
        v
Surefire
        |
        v
Unit Tests
        |
   +----+----+
   |         |
   v         v
PASS       FAIL
   |         |
   v         v
Continue   Build Failure
```

Later, we will add integration testing:

```text
Package Application
        |
        v
Prepare Test Environment
        |
        v
Failsafe
        |
        v
Integration Tests
        |
        v
verify
        |
   +----+----+
   |         |
   v         v
PASS       FAIL
```

The goal is not simply to memorize:

```bash
mvn test
```

The goal is to understand testing as a normal part of a reliable Maven build.

---

# 1. Why Do Automated Tests Exist?

Imagine you create a method:

```java
public String createGreeting(String name) {
    return "Hello, " + name;
}
```

You manually run the application.

You enter:

```text
Ann
```

You see:

```text
Hello, Ann
```

Everything looks correct.

Later, another developer changes the method:

```java
public String createGreeting(String name) {
    return "Goodbye, " + name;
}
```

The application still compiles.

Maven may report:

```text
BUILD SUCCESS
```

during compilation.

But the expected behavior has changed incorrectly.

Without a test, someone has to notice this manually.

An automated test can express the expected behavior:

```text
Given:
name = Ann

When:
createGreeting() runs

Then:
result should be "Hello, Ann"
```

Every build can verify this automatically.

---

# 2. What Is an Automated Test?

An automated test is code that checks whether other code behaves as expected.

Instead of a developer repeatedly doing this:

```text
Run application
→ Enter input
→ Read output
→ Decide whether output is correct
```

a test can perform the check automatically:

```text
Prepare input
→ Execute code
→ Compare actual result with expected result
→ Pass or fail
```

For example:

```java
assertEquals("Hello, Ann", greeting);
```

Conceptually:

```text
Expected
"Hello, Ann"
      |
      v
Compare
      ^
      |
Actual
result from application
```

If they match:

```text
PASS
```

If they do not:

```text
FAIL
```

---

# 3. Why Tests Matter

Automated tests help engineers:

* Detect regressions
* Validate expected behavior
* Refactor code more safely
* Find problems before deployment
* Document expected behavior
* Check edge cases repeatedly
* Build confidence in changes
* Protect important application logic
* Automate quality checks in CI/CD

Tests do not prove that software has no bugs.

A test checks only the behavior it was designed to test.

If you never test an important scenario, that scenario may still be broken.

---

# 4. What Is a Regression?

A regression occurs when functionality that previously worked becomes broken after a change.

Example:

```text
Version 1

createGreeting("Ann")
→ "Hello, Ann"

Developer changes code

Version 2

createGreeting("Ann")
→ "Goodbye, Ann"
```

If the required behavior was still `"Hello, Ann"`, the change introduced a regression.

A test can detect it:

```text
Code change
    |
    v
mvn test
    |
    v
Expected: Hello, Ann
Actual:   Goodbye, Ann
    |
    v
TEST FAILURE
```

---

# 5. Testing Is Part of the Build

Beginners sometimes think:

```text
Write code
→ Build application
→ Maybe test later
```

A better model is:

```text
Write code
    |
    v
Compile
    |
    v
Compile tests
    |
    v
Run automated tests
    |
    v
Package
    |
    v
Verify
    |
    v
Release or deploy
```

Testing is part of determining whether a build is trustworthy enough to continue.

---

# 6. Compilation Success Does Not Mean Test Success

Suppose:

```java
public int multiply(int a, int b) {
    return a + b;
}
```

This code is syntactically valid.

Therefore:

```bash
mvn compile
```

may succeed.

But:

```text
multiply(3, 4)
```

should return:

```text
12
```

The implementation returns:

```text
7
```

A test can detect the logical error.

This gives us two different questions:

```text
Compilation:
Can the code be transformed into valid classes?

Testing:
Does the code behave as expected?
```

---

# 7. Unit Tests

A unit test checks a relatively small piece of application behavior in isolation.

The "unit" might be:

* A method
* A class
* A small component

For example:

```text
GreetingService
```

might have a method:

```java
createGreeting(User user)
```

A unit test could verify:

```text
Input:
User("Ann")

Expected:
"Welcome to VERIQTA Maven, Ann!"
```

The test focuses on that small behavior.

---

# 8. What Makes a Good Beginner Unit Test?

A simple unit test normally has three conceptual stages:

```text
Arrange
→ prepare what the test needs

Act
→ execute the behavior

Assert
→ verify the result
```

This is often called:

```text
AAA
```

meaning:

```text
Arrange
Act
Assert
```

---

# 9. Arrange, Act, Assert Example

Suppose we test `GreetingService`.

## Arrange

Create the objects:

```java
User user = new User("Ann");
GreetingService service = new GreetingService();
```

## Act

Run the method:

```java
String result = service.createGreeting(user);
```

## Assert

Check the result:

```java
assertEquals("Welcome to VERIQTA Maven, Ann!", result);
```

The mental model is:

```text
Arrange
Create test state
    |
    v
Act
Execute behavior
    |
    v
Assert
Compare expected and actual
```

---

# 10. Integration Tests

An integration test checks how multiple parts of a system work together.

For example:

```text
Application
    |
    v
Database
```

or:

```text
Application
    |
    v
HTTP API
```

or:

```text
Service A
    |
    v
Service B
```

A unit test may test one class.

An integration test may test the interaction among several real components.

---

# 11. Unit Test Versus Integration Test

A simplified comparison:

| Unit Test                      | Integration Test                      |
| ------------------------------ | ------------------------------------- |
| Tests small behavior           | Tests components working together     |
| Usually fast                   | Often slower                          |
| Usually isolated               | May require external resources        |
| Easier to run frequently       | May require setup and cleanup         |
| Often no real database/network | May use real database/network/service |
| Commonly handled by Surefire   | Commonly handled by Failsafe          |

This distinction matters because Maven normally handles these two categories differently.

---

# 12. Why Integration Tests Need Different Treatment

Imagine an integration test needs:

```text
Database
```

Before the test:

```text
Start database
```

Then:

```text
Run application
```

Then:

```text
Execute integration tests
```

Afterward:

```text
Stop database
```

A simplified lifecycle becomes:

```text
pre-integration-test
        |
        v
Prepare environment
        |
        v
integration-test
        |
        v
Run integration tests
        |
        v
post-integration-test
        |
        v
Clean environment
        |
        v
verify
        |
        v
Evaluate result
```

This is one reason Maven provides integration-test-related lifecycle phases instead of treating every test identically.

In Part 9, you learned:

```text
src/main/java
```

contains main application source.

Tests normally live under:


Our project can now look like:

```text
veriqta-maven-app/
```

---

# 14. Why Tests Have Their Own Source Directory

Tests are source code, but they are not application production source.

Separating them gives Maven a clear model:

```text
src/main/java
→ application source

src/test/java
→ test source
```

This allows Maven to build different classpaths and outputs for them.

---

# 15. Where Test Classes Go

Main source:

```text
src/main/java
```

is normally compiled to:

```text
target/classes
```

Test source:

```text
src/test/java
```

is normally compiled to:

```text
target/test-classes
```

So:

```text
src/main/java
      |
      v
target/classes

src/test/java
      |
      v
target/test-classes
```

---

# 16. Tests Can Use Application Classes

A test under:

```text
src/test/java
```

needs access to application code.

For example:

```java
GreetingService service = new GreetingService();
```

The test compilation classpath therefore normally includes the compiled application classes.

Conceptually:

```text
target/classes
Application classes
       |
       +------------------+
                          |
src/test/java             |
       |                  |
       v                  v
        Test compilation
              |
              v
      target/test-classes
```

---

# 17. What Is a Test Dependency?

Your application may not need JUnit when it runs in production.

But your tests need JUnit to define and execute test behavior.

This means JUnit is a test dependency.

Conceptually:

```text
Application
→ does not require JUnit to perform business logic

Tests
→ require JUnit
```

That is what Maven's `test` dependency scope is designed for.

---

# 18. JUnit

JUnit is a widely used testing framework for Java.

It provides tools for writing tests, including:

* Test annotations
* Assertions
* Test lifecycle features
* Parameterized testing
* Other testing capabilities

For this beginner part, we need only the fundamentals required to understand Maven testing.

---

# 19. Add JUnit to the Maven Project

A modern Maven project using JUnit 5 may use the JUnit Jupiter dependency.

The dependency concept looks like:

```xml
<dependencies>

    <dependency>
        <groupId>org.junit.jupiter</groupId>
        <artifactId>junit-jupiter</artifactId>
        <version>YOUR_SELECTED_JUNIT_VERSION</version>
        <scope>test</scope>
    </dependency>

</dependencies>
```

Use a current version deliberately selected for your project rather than copying an arbitrary version from an old tutorial.

The important beginner detail is:

```xml
<scope>test</scope>
```

---

# 20. Why JUnit Uses Test Scope

Test scope means the dependency is intended for test compilation and execution.

Conceptually:

```text
JUnit
   |
   +---- available to src/test/java
   |
   +---- available during tests
   |
   +---- not treated as a normal production application dependency
```

This prevents testing libraries from unnecessarily becoming ordinary runtime dependencies of the application.

---

# 21. First JUnit Test

Create:

```text
src/test/java/com/veriqta/app/service/GreetingServiceTest.java
```

Example:

```java
package com.veriqta.app.service;

import com.veriqta.app.model.User;
import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.assertEquals;

class GreetingServiceTest {

    @Test
    void shouldCreateGreetingForUser() {

        User user = new User("Ann");
        GreetingService service = new GreetingService();

        String result = service.createGreeting(user);

        assertEquals(
            "Welcome to VERIQTA Maven, Ann!",
            result
        );
    }
}
```

Now we will understand every important part.

---

# 22. The Test Package

The file begins with:

```java
package com.veriqta.app.service;
```

Our test is stored under:

```text
src/test/java/com/veriqta/app/service/
```

The package structure mirrors the application's package organization.

This makes related application and test code easy to locate.

---

# 23. Importing the Application Class

Our test uses:

```java
import com.veriqta.app.model.User;
```

Because the test is already in:

```text
com.veriqta.app.service
```

it can refer directly to `GreetingService`.

The test is ordinary Java source and follows Java's normal package and import rules.

---

# 24. Importing `@Test`

This line:

```java
import org.junit.jupiter.api.Test;
```

imports JUnit's `Test` annotation.

Then:

```java
@Test
```

marks a method as a test method.

For example:

```java
@Test
void shouldCreateGreetingForUser() {
}
```

Without the test framework recognizing the method as a test, it would simply be another Java method.

---

# 25. What Is an Annotation?

You encountered annotations briefly in Part 9.

An annotation provides metadata about Java program elements.

For example:

```java
@Test
```

communicates:

```text
This method represents a test.
```

JUnit understands that metadata and treats the method accordingly.

---

# 26. Test Method Names

Our method is:

```java
shouldCreateGreetingForUser()
```

The name describes expected behavior.

Compare:

```java
test1()
```

with:

```java
shouldCreateGreetingForUser()
```

The second is more useful when reading reports.

Good test names help explain:

```text
What behavior is being tested?
```

---

# 27. Assertions

An assertion checks an expectation.

We use:

```java
assertEquals(expected, actual);
```

For example:

```java
assertEquals(
    "Welcome to VERIQTA Maven, Ann!",
    result
);
```

JUnit compares:

```text
Expected
"Welcome to VERIQTA Maven, Ann!"

Actual
result
```

If they match:

```text
PASS
```

If they differ:

```text
FAIL
```

---

# 28. Expected Versus Actual

Beginners should pay attention to argument order.

The common form is:

```java
assertEquals(expected, actual);
```

For example:

```java
assertEquals(5, calculator.add(2, 3));
```

Here:

```text
Expected:
5

Actual:
calculator.add(2, 3)
```

This distinction becomes important when reading test failure messages.

---

# 29. Other Basic Assertions

JUnit provides many assertions.

Examples include:

```java
assertTrue(condition);
```

```java
assertFalse(condition);
```

```java
assertNull(value);
```

```java
assertNotNull(value);
```

```java
assertThrows(ExpectedException.class, () -> {
    // code expected to throw
});
```

Do not try to memorize every assertion.

Understand the principle:

```text
Test
→ execute behavior
→ assert expectation
```

# 30. Run Tests With Maven

From the project root:

```bash
mvn test
```

This tells Maven to execute the default lifecycle through the `test` phase.

Remember the rule from Part 5:

```text
Invoking a later phase also invokes the earlier phases required before it.
```

Therefore `mvn test` does more than launch JUnit immediately.

---

# 31. What Happens During `mvn test`?

A simplified lifecycle flow is:

```text
mvn test
    |
    v
validate
    |
    v
process resources
    |
    v
compile
    |
    v
process test resources
    |
    v
test-compile
    |
    v
test
```

The application must be compiled before its tests can be properly executed.

---

# 32. Main Compilation and Test Compilation

The flow becomes:

```text
src/main/java
      |
      v
compile
      |
      v
target/classes
      |
      +--------------------+
                           |
src/test/java              |
      |                    |
      v                    v
        test-compile
             |
             v
    target/test-classes
             |
             v
           test
```

---

# 33. Test Compilation Can Fail

Tests are Java code.

Therefore they must compile too.

Suppose you write:

```java
assertEquals(
    "Hello",
    unknownVariable
);
```

and `unknownVariable` does not exist.

The test cannot compile.

That is different from:

```text
The test compiled but its assertion failed.
```

You need to distinguish these situations.

---

# 34. Three Important Outcomes

During testing, you may encounter:

```text
1. Test compilation error
2. Test failure
3. Test error
```

They are not identical.

---

# 35. Test Compilation Error

Example:

```java
User user = new Usr("Ann");
```

`Usr` does not exist.

The compiler fails before the test can run.

Conceptually:

```text
Test source
    |
    v
test-compile
    |
    v
COMPILATION ERROR
    |
    v
Test never executes
```

---

# 36. Test Failure

Suppose:

```java
assertEquals("Hello, Ann", "Goodbye, Ann");
```

The test executes successfully as Java code, but the assertion is false.

Conceptually:

```text
Test starts
    |
    v
Code executes
    |
    v
Assertion evaluated
    |
    v
Expected != Actual
    |
    v
FAILURE
```

---

# 37. Test Error

Suppose the test unexpectedly throws an exception.

For example:

```java
String value = null;
value.length();
```

The test may end with an error rather than an assertion failure.

Conceptually:

```text
Test starts
    |
    v
Unexpected exception
    |
    v
ERROR
```

---

# 38. Maven Surefire Plugin

The Maven Surefire Plugin is commonly responsible for running unit tests during Maven's `test` phase.

Mental model:

```text
mvn test
    |
    v
test phase
    |
    v
Maven Surefire Plugin
    |
    v
Test framework
    |
    v
Unit tests
```

Maven coordinates the lifecycle.

Surefire performs the test-running work associated with the test phase.

JUnit provides the testing framework and APIs used by the tests.

---

# 39. Maven, Surefire and JUnit Are Different Things

This distinction is important.

```text
Maven
→ build system and lifecycle coordinator

Surefire
→ Maven plugin used to execute tests in the test phase

JUnit
→ Java testing framework used to write and execute test behavior
```

A beginner may incorrectly think:

```text
JUnit is Maven.
```

It is not.

They work together.

---

# 40. Configure Surefire

A project may explicitly configure Surefire under:

```xml
<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-surefire-plugin</artifactId>
            <version>YOUR_CONTROLLED_VERSION</version>
        </plugin>
    </plugins>
</build>
```

As with the Compiler Plugin, use an intentionally selected compatible version.

Controlling plugin versions improves build predictability.

---

# 41. Test Discovery

How does Surefire know which test classes to execute?

It uses test discovery rules.

By default, Surefire recognizes common test class naming patterns.

Typical examples include names such as:

```text
GreetingServiceTest.java
CalculatorTest.java
UserServiceTests.java
TestPaymentService.java
```

The exact supported default patterns depend on Surefire's documented configuration.

The key beginner lesson is:

```text
Test naming affects automatic discovery.
```

---

# 42. Why Naming Conventions Matter

Suppose your test is called:

```text
GreetingServiceTest.java
```

That clearly communicates:

```text
This class tests GreetingService.
```

It also follows a conventional pattern that test tooling can discover.

If you choose an unusual name such as:

```text
GreetingServiceChecks.java
```

you should not automatically assume the default test discovery rules will execute it.

---

# 43. Do Not Trust "BUILD SUCCESS" Without Knowing What Ran

Imagine:

```text
Test class exists
        |
        v
Name does not match discovery pattern
        |
        v
Surefire does not discover it
        |
        v
No failing assertion runs
        |
        v
BUILD SUCCESS
```

That success would not prove the undiscovered test passed.

The test was never executed.

Always understand what the build actually ran.

# 48. Add More Than One Unit Test

Expand `GreetingServiceTest`:

```java
package com.veriqta.app.service;

import com.veriqta.app.model.User;
import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.assertEquals;

class GreetingServiceTest {

    @Test
    void shouldCreateGreetingForAnn() {

        User user = new User("Ann");
        GreetingService service = new GreetingService();

        String result = service.createGreeting(user);

        assertEquals(
            "Welcome to VERIQTA Maven, Ann!",
            result
        );
    }

    @Test
    void shouldCreateGreetingForEngineer() {

        User user = new User("Engineer");
        GreetingService service = new GreetingService();

        String result = service.createGreeting(user);

        assertEquals(
            "Welcome to VERIQTA Maven, Engineer!",
            result
        );
    }
}
```

Now:

```bash
mvn test
```

should execute multiple test methods.

---

# 49. Test Independence

Tests should generally avoid depending unnecessarily on another test having run first.

Bad mental model:

```text
Test A
creates required state
    |
    v
Test B
depends on Test A
```

Better:

```text
Test A
creates its own required state

Test B
creates its own required state
```

This makes tests easier to run independently and reduces order-dependent failures.

---

# 50. Running a Single Test Class

Sometimes you do not want to run the entire test suite.

With Surefire, you can commonly select a test using:

```bash
mvn -Dtest=GreetingServiceTest test
```

Break it down:

```text
mvn
→ run Maven

-D
→ define a Maven user property

test=GreetingServiceTest
→ select the test class

test
→ execute lifecycle through the test phase
```

This is useful while developing or troubleshooting one test class.

---

# 51. Running a Single Test Method

Surefire can also support selecting a method within a test class.

A common form is:

```bash
mvn -Dtest=GreetingServiceTest#shouldCreateGreetingForAnn test
```

Conceptually:

```text
GreetingServiceTest
        |
        v
shouldCreateGreetingForAnn
```

This lets you focus on one specific failing behavior.

Shells can treat some characters specially, so quoting the property may be appropriate in some environments:

```bash
mvn "-Dtest=GreetingServiceTest#shouldCreateGreetingForAnn" test
```

---

# 52. Running Selected Tests

Surefire supports test selection patterns and multiple selections.

For example, depending on your shell and Surefire configuration, you may select specific test classes using the `test` property.

The important principle is:

```text
Full suite
→ mvn test

Focused troubleshooting
→ select relevant tests
```

Do not permanently configure CI to run only your favorite test while ignoring the rest of the required suite.

---

# 53. Why Focused Tests Are Useful

Imagine the project has:

```text
2,000 unit tests
```

One fails:

```text
GreetingServiceTest
```

During debugging, repeatedly running all 2,000 tests may be unnecessary.

You can focus:

```text
All tests
        |
        v
Identify failing class
        |
        v
Run failing class
        |
        v
Identify failing method
        |
        v
Run method
        |
        v
Fix
        |
        v
Run full suite again
```

The last step matters.

A local fix may affect other tests.

---

# 54. Intentionally Break a Unit Test

Our practical goal includes learning what Maven reports when a test fails.

Change:

```java
assertEquals(
    "Welcome to VERIQTA Maven, Ann!",
    result
);
```

temporarily to:

```java
assertEquals(
    "Wrong message",
    result
);
```

Then run:

```bash
mvn test
```

Do not immediately fix the test.

Read the failure.

---

# 55. What a Failed Assertion Tells You

A JUnit failure typically gives information that helps identify:

* Test class
* Test method
* Expected value
* Actual value
* Source location
* Stack trace

For example, conceptually:

```text
Expected:
Wrong message

Actual:
Welcome to VERIQTA Maven, Ann!
```

The exact formatting depends on versions.

Your job is to identify:

```text
What did the test expect?

What actually happened?
```

---

# 56. Test Failure Versus Maven Build Failure

A test failure can cause the Maven build to fail.

Flow:

```text
Java compiles
    |
    v
Tests compile
    |
    v
Tests execute
    |
    v
Assertion fails
    |
    v
Surefire reports failure
    |
    v
Maven build fails
```

So:

```text
BUILD FAILURE
```

does not always mean:

```text
Compilation failed.
```

You must identify the failing stage.

---

# 57. How to Recognize a Test Failure

Look for evidence such as:

```text
maven-surefire-plugin
```

and:

```text
Tests run
Failures
Errors
Skipped
```

Then inspect:

```text
target/surefire-reports
```

Do not begin changing compiler settings if the compiler already succeeded and the failure is coming from a test assertion.

---

# 58. Fix the Broken Test

Restore:

```java
assertEquals(
    "Welcome to VERIQTA Maven, Ann!",
    result
);
```

Then:

```bash
mvn test
```

Verify:

```text

```

and:

```text

```

You have now experienced the complete cycle:

```text

→ intentionally break expectation
→ Maven test failure
→ inspect evidence
→ fix
→ verify
```

---

# 59. Do Not Automatically "Fix" a Failing Test by Changing the Test

This is extremely important.

Suppose:

```text

5

Actual:
7
```

A beginner might change:

```java
assertEquals(5, result);
```

to:

```java
assertEquals(7, result);
```

just to make the build green.

That may hide a real application bug.

When a test fails, ask:

```text
Is the application wrong?

Or is the test expectation wrong?
```

Investigate before changing either.

# 61. Skipping Tests

Sometimes Maven users intentionally skip tests.

But there are two different ideas beginners often confuse:

```text
Do not execute tests
```

and:

```text
Do not even compile tests
```

These are not the same.

---

# 62. Skip Test Execution

A common Maven property is:

```bash
mvn package -DskipTests
```

This tells supported Maven testing plugins to skip executing tests while still allowing test compilation in the normal build flow.

Conceptually:

```text
Main compile
    |
    v
Test compile
    |
    v
Do not execute tests
    |
    v
Continue build
```

This means broken test source can still cause the build to fail during test compilation.

---

# 63. Skip Test Compilation and Execution

Maven also supports a property commonly used as:

```bash
mvn package -Dmaven.test.skip=true
```

This skips test compilation as well as test execution in plugins that honor the property.

Conceptually:

```text
Main compile
    |
    v
Skip test compilation
    |
    v
Skip test execution
    |
    v
Continue
```

This is a much stronger form of skipping.

---

# 64. `skipTests` Versus `maven.test.skip`

Remember:

```text
-DskipTests
→ normally compile tests but do not run them

-Dmaven.test.skip=true
→ skip compiling and running tests
```

This difference is important.

If test code itself does not compile:

```bash
mvn package -DskipTests
```

may still fail.

But skipping test compilation can bypass that test compilation stage.

---

# 65. Why Skipping Tests Can Be Dangerous

Suppose:

```text
Application code changed
        |
        v
A test would detect a regression
        |
        v
Tests skipped
        |
        v
Artifact created
```

The artifact existing does not mean it passed the project's normal quality checks.

Therefore skipping tests should be intentional and justified.

---

# 66. When Might Tests Be Skipped?

There can be legitimate situations, such as:

* Certain local development workflows
* Isolating a packaging problem
* Troubleshooting build stages
* Specialized pipeline stages where tests already ran elsewhere

But:

```text
Tests are inconvenient
```

is not a good default reason to disable them.

For normal CI builds, required tests should generally run.

---

# 67. Why `mvn package` Normally Runs Unit Tests

Remember the default lifecycle:

```text
validate
    |
    v
compile
    |
    v
test
    |
    v
package
```

Because `test` comes before `package`, running:

```bash
mvn package
```

normally reaches the test phase before packaging.

So the mental model is:

```text
mvn package
     |
     v
Compile application
     |
     v
Compile tests
     |
     v
Run unit tests
     |
     v
Package application
```

If tests fail, packaging normally does not continue successfully.

---

# 68. Why `mvn install` Also Runs Earlier Tests

Likewise:

```bash
mvn install
```

moves farther through the same lifecycle.

Simplified:

```text
compile
→ test
→ package
→ verify
→ install
```

Therefore unit tests normally execute before the artifact reaches the install phase.

---

# 69. Integration Tests With Maven

Unit tests are not enough for every problem.

Suppose your application contains a repository component:

```text
UserRepository
```

A unit test may test logic without a real database.

But you may also need to know:

```text
Can the application actually connect to the database?

Can it insert a user?

Can it retrieve that user?

Does the real database schema work with the application?
```

Those are integration concerns.

---

# 70. Example Integration Test Scenario

Imagine:

```text
Java Application
      |
      v
PostgreSQL
```

An integration test may:

1. Start or connect to a test database.
2. Configure the application.
3. Insert data.
4. Query data.
5. Verify the result.
6. Clean up test state.

This is more involved than:

```java
assertEquals(5, calculator.add(2, 3));
```

---

# 71. Integration-Test Lifecycle Phases

Maven's default lifecycle contains phases specifically useful around integration testing:

```text
pre-integration-test
integration-test
post-integration-test
verify
```

Conceptually:

```text
pre-integration-test
→ prepare environment

integration-test
→ execute integration tests

post-integration-test
→ clean up environment

verify
→ check integration-test results and overall verification
```

---

# 72. Why Not Stop at `integration-test`?

This is a subtle but important Maven concept.

With integration testing, setup and cleanup may be bound to lifecycle phases surrounding `integration-test`.

If you invoke only:

```bash
mvn integration-test
```

you stop at the `integration-test` phase.

That means later lifecycle work, including `post-integration-test` and `verify`, has not been reached.

For builds using Failsafe, final test-result checking is typically associated with `verify`.

Therefore the normal command for a complete integration-test flow is:

```bash
mvn verify
```

not merely:

```bash
mvn integration-test
```

---

# 73. The `verify` Mental Model

Think:

```text
mvn verify
    |
    v
Compile
    |
    v
Unit tests
    |
    v
Package
    |
    v
Prepare integration environment
    |
    v
Run integration tests
    |
    v
Clean integration environment
    |
    v
Verify integration-test results
    |
    v
BUILD SUCCESS or BUILD FAILURE
```

This is why `verify` is an important command in CI.

---

# 74. Maven Failsafe Plugin

The Maven Failsafe Plugin is designed for integration tests.

A common setup binds two goals:

```text
failsafe:integration-test
```

and:

```text
failsafe:verify
```

The mental model is:

```text
integration-test phase
        |
        v
Failsafe integration-test goal
        |
        v
Run integration tests

verify phase
        |
        v
Failsafe verify goal
        |
        v
Evaluate results
```

---

# 75. Why Is It Called Failsafe?

The plugin is designed so that an integration-test failure does not immediately prevent later cleanup lifecycle phases from running before the build result is checked at `verify`.

Imagine:

```text
Start test server
      |
      v
Run integration test
      |
      v
Test fails
```

If Maven stopped instantly at that point, cleanup might not happen.

Instead, the desired model is:

```text
Start environment
      |
      v
Run test
      |
      v
Test fails
      |
      v
Cleanup environment
      |
      v
Verify result
      |
      v
BUILD FAILURE
```

This is especially useful when integration tests manage external processes or environments.

---

# 76. Surefire Versus Failsafe

Keep this distinction clear:

| Surefire                             | Failsafe                                        |
| ------------------------------------ | ----------------------------------------------- |
| Primarily unit tests                 | Primarily integration tests                     |
| Associated with `test`               | Associated with `integration-test` and `verify` |
| Fast test suite use case             | Broader component interaction use case          |
| Reports in `target/surefire-reports` | Reports commonly in `target/failsafe-reports`   |

Both are Maven plugins.

Neither is JUnit itself.

JUnit tests can be executed through these Maven plugins when configured appropriately.

---

# 77. Integration Test Naming

Failsafe uses naming conventions for integration tests.

Common default naming patterns include names such as:

```text
UserRepositoryIT.java
ApplicationIT.java
ITDatabaseConnection.java
```

A widely used convention is:

```text
*IT.java
```

where:

```text
IT
→ Integration Test
```

For example:

```text
DatabaseConnectionIT.java
```

This makes it easy to distinguish:

```text
GreetingServiceTest
→ unit test

DatabaseConnectionIT
→ integration test
```

---

# 78. Why Naming Separates Unit and Integration Tests

Imagine:

```text
src/test/java/
├── GreetingServiceTest.java
├── UserServiceTest.java
└── DatabaseConnectionIT.java
```

You may want:

```text
mvn test
```

to run fast unit tests.

Then:

```text
mvn verify
```

to include the broader integration-test process.

Naming conventions help the relevant plugins discover the appropriate tests.

# 79. Basic Failsafe Configuration

A simplified plugin configuration can look like:


This connects Failsafe's integration-test and verification goals to the appropriate lifecycle phases through their normal bindings.

# 81. Test Resources

```text

```

For example:

```text

├── test-data.json

```

These resources belong to the test environment rather than the production application source.

---

# 82. Main Resources Versus Test Resources

Remember:

```text
src/main/resources
→ application resources

src/test/resources
→ test-only resources
```

During the build, Maven processes them separately.

A test database configuration, for example, should not automatically become the production database configuration.

---

# 83. Never Put Real Secrets in Test Files

A test resource might need:

```text
database username
API endpoint
test configuration
```

Do not commit real production secrets such as:

```text
Production database password
Cloud access key
Private API token
SSH private key
```

into:

```text
src/test/resources
```

Tests are code and configuration stored in source control.

Treat test configuration with the same security awareness as application configuration.

# 84. Test Data Should Be Safe

Integration tests may create or delete data.

Do not point destructive integration tests at production systems.

A dangerous situation is:

```text
Integration test
     |
     v
Production database
     |
     v
DELETE / INSERT / UPDATE
```

Use isolated test environments.

Prefer:

```text
Integration test
     |
     v
Dedicated test environment
```

# 88. "Works on My Machine" Test Problems

A test may pass locally but fail in CI.

Possible causes include:

* Different Java versions
* Different operating systems
* Case sensitivity
* Missing environment variables
* Different time zones
* Different locale
* Filesystem assumptions
* Hardcoded paths
* Missing services
* Port conflicts
* Network access
* Different dependency caches
* Test ordering assumptions
* Race conditions
* Insufficient permissions

Do not immediately assume CI is broken.

Investigate the environmental difference.

---

# 89. Hardcoded Path Problem

A bad test might depend on:

```text
/Users/ann/Desktop/test-data.txt
```

That path may exist on your MacBook.

It probably does not exist on a Linux CI runner.

The test then becomes environment-dependent.

Prefer project-relative resources or proper test-resource loading.

---

# 90. Hardcoded Port Problem

Suppose an integration test assumes:

```text
Port 8080 is always free.
```

On a CI runner, another process may already use it.

The test fails.

The lesson is:

```text
Integration tests interact with environments.

Environment assumptions must be controlled.
```

---

# 91. Time-Dependent Tests

Suppose a test expects:

```text
Current hour = 09
```

It may pass locally and fail later.

Time-dependent tests need deliberate handling.

Think about:

* Time zone
* Current date
* Clock dependency
* Daylight saving changes

Tests should avoid uncontrolled environmental assumptions.

---

# 92. Flaky Tests

A flaky test sometimes passes and sometimes fails without a meaningful application change.

Example:

```text
Run 1 → PASS
Run 2 → PASS
Run 3 → FAIL
Run 4 → PASS
```

Possible causes include:

* Timing assumptions
* Race conditions
* Shared mutable state
* Network instability
* External service instability
* Test ordering
* Port conflicts
* Resource exhaustion

Flaky tests are dangerous because teams may stop trusting test failures.

---

# 93. Do Not Solve Flaky Tests by Blindly Rerunning Them

A retry may temporarily turn:

```text
FAIL
```

into:

```text
PASS
```

but the instability remains.

Use:

```text
Observe
→ reproduce
→ gather evidence
→ identify nondeterministic dependency
→ fix root cause
→ verify repeatedly
```

Retries can sometimes be part of a deliberate strategy, but they should not hide broken tests.

# 107. Tests as Executable Documentation

# 108. Test the Behavior, Not Maven

A unit test should normally test application behavior.

For example:

Your test suite should focus on your application's required behavior.

# 109. Do Not Overuse Implementation-Specific Assertions

```text
GreetingService returns the correct greeting.
```

Focus tests on meaningful behavior where possible.
