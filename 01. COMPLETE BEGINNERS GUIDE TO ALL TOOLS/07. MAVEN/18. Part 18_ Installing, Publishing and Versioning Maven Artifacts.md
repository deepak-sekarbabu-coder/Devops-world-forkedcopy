# Part 18: Installing, Publishing and Versioning Maven Artifacts

In the previous parts, you learned how Maven turns source code into build artifacts such as JAR files.

You also learned that Maven can resolve dependencies from:

* The local Maven repository
* Maven Central
* Private repositories
* Enterprise repository managers such as Nexus Repository and JFrog Artifactory

Now we need to examine the opposite direction.

So far, we have mostly asked:

```text
How does Maven get artifacts?
```

Now we ask:

```text
How does Maven publish the artifacts we create?
```

Imagine VERIQTA has two Maven projects:

```text
veriqta-common-library

veriqta-application
```

The application needs classes from the library.

We could manually copy:

```text
veriqta-common-library-1.0.0.jar
```

into the application.

But that would take us back to the dependency-management problems Maven was created to solve.

Instead, we want this:

```text
Library Source
      |
      v
Maven
      |
      v
Compile
      |
      v
Test
      |
      v
Package
      |
      v
JAR
      |
      +----------------------+
      |                      |
      v                      v
mvn install              mvn deploy
      |                      |
      v                      v
Local .m2             Remote Repository
      |                      |
      v                      v
Local Projects        Developers / CI
```

This introduces three Maven operations that beginners must clearly distinguish:

```text
package
install
deploy
```

They are related, but they do different things.

By the end of this part, you should understand how an artifact moves from source code to a local Maven repository, then to a shared remote repository, and finally into another application as a normal Maven dependency.

# 18.1 Start With the Complete Artifact Journey

Consider this library:

```text
veriqta-logging-library
```

Its Maven coordinates are:

```text
groupId:
com.veriqta

artifactId:
veriqta-logging-library

version:
1.0.0

packaging:
jar
```

Together:

```text
com.veriqta:veriqta-logging-library:1.0.0
```

The source project might look like:

```text
veriqta-logging-library/
├── pom.xml
└── src/
    ├── main/
    │   └── java/
    │       └── com/
    │           └── veriqta/
    │               └── logging/
    │                   └── VeriqtaLogger.java
    └── test/
        └── java/
            └── com/
                └── veriqta/
                    └── logging/
                        └── VeriqtaLoggerTest.java
```

We want the artifact to travel through several stages:

```text
Source Code
    |
    v
Compile
    |
    v
Test
    |
    v
Package
    |
    v
veriqta-logging-library-1.0.0.jar
    |
    v
Install Locally
    |
    v
~/.m2/repository
    |
    v
Deploy Remotely
    |
    v
Enterprise Artifact Repository
    |
    v
Consuming Application
```

Each stage solves a different problem.

---

# 18.2 What Does `mvn package` Do?

Start with:

```bash
mvn package
```

The `package` phase creates the distributable artifact for the project after executing the earlier phases required by the lifecycle.

For a normal JAR project, the simplified flow is:

```text
validate
   |
   v
compile
   |
   v
test
   |
   v
package
```

Suppose the POM contains:

```xml
<groupId>com.veriqta</groupId>
<artifactId>veriqta-logging-library</artifactId>
<version>1.0.0</version>
<packaging>jar</packaging>
```

After:

```bash
mvn package
```

Maven may create:

```text
target/veriqta-logging-library-1.0.0.jar
```

The important point is:

```text
package
=
create the project artifact
```

It does not mean:

```text
make this artifact available to every other Maven project on my machine
```

And it does not mean:

```text
publish this artifact to the company's remote repository
```

Those are later stages.

---

# 18.3 `package` Versus `install` Versus `deploy`

This distinction is fundamental.

| Command       | Main Result                                                                                            | Typical Location                         |
| ------------- | ------------------------------------------------------------------------------------------------------ | ---------------------------------------- |
| `mvn package` | Creates the artifact                                                                                   | Project `target/`                        |
| `mvn install` | Creates and installs it locally                                                                        | `target/` and local Maven repository     |
| `mvn deploy`  | Creates, installs as required by lifecycle progression, then publishes to configured remote repository | Local build output and remote repository |

The mental model is:

```text
package
   |
   v
Create artifact
   |
   v
target/


install
   |
   v
Create artifact
   |
   v
Install into local Maven repository
   |
   v
~/.m2/repository


deploy
   |
   v
Create artifact
   |
   v
Run required lifecycle phases
   |
   v
Publish to remote repository
```

Or more simply:

```text
package
→ I built it.

install
→ My local Maven environment can consume it.

deploy
→ Other authorized environments can consume it from a remote repository.
```

---

# 18.4 Why `mvn install` Exists

Imagine you are developing two separate projects.

Project A:

```text
veriqta-logging-library
```

Project B:

```text
veriqta-application
```

Project B depends on Project A.

Its POM contains:

```xml
<dependency>
    <groupId>com.veriqta</groupId>
    <artifactId>veriqta-logging-library</artifactId>
    <version>1.0.0</version>
</dependency>
```

But the library has not been published to Maven Central or your company repository.

How can Maven resolve it?

One solution during local development is:

```bash
mvn install
```

inside the library project.

This installs the artifact into your local Maven repository.

Then another Maven project on the same machine can resolve it.

---

# 18.5 What Happens During `mvn install`?

Run:

```bash
mvn install
```

Because `install` occurs later in Maven's default lifecycle, Maven executes the preceding phases needed to reach it.

A simplified flow is:

```text
validate
   |
   v
compile
   |
   v
test
   |
   v
package
   |
   v
verify
   |
   v
install
```

So Maven does not merely copy a random JAR into `.m2`.

It first builds the project through the lifecycle.

If compilation fails:

```text
install never happens
```

If tests fail:

```text
install normally never happens
```

If verification fails:

```text
install never happens
```

Only after the build successfully reaches `install` does Maven install the project artifacts into the local repository.

---

# 18.6 What Gets Installed Into `.m2`?

The default local Maven repository is normally:

```text
~/.m2/repository
```

For:

```text
groupId:
com.veriqta

artifactId:
veriqta-logging-library

version:
1.0.0
```

the repository path follows the coordinates.

The group ID:

```text
com.veriqta
```

becomes:

```text
com/veriqta
```

Then Maven adds:

```text
artifactId/version
```

giving:

```text
~/.m2/repository/
└── com/
    └── veriqta/
        └── veriqta-logging-library/
            └── 1.0.0/
```

Inside, you may find files such as:

```text
veriqta-logging-library-1.0.0.jar
veriqta-logging-library-1.0.0.pom
```

There may also be repository metadata or tracking files depending on how the artifact was produced and resolved.

The important idea is:

```text
Coordinates
    |
    v
Repository Path
```

---

# 18.7 Why Maven Installs the POM Too

A beginner may ask:

> Why does Maven need the POM? Isn't the JAR the actual library?

The JAR contains the compiled application or library classes.

But Maven also needs project metadata.

Suppose your library itself depends on another library.

Its POM might contain:

```xml
<dependencies>
    <dependency>
        <groupId>org.example</groupId>
        <artifactId>example-library</artifactId>
        <version>2.0.0</version>
    </dependency>
</dependencies>
```

When another project consumes your library, Maven may need that dependency information.

Therefore:

```text
JAR
→ executable/compiled library content

POM
→ Maven project and dependency metadata
```

Both matter.

# 18.8 Inspect the Installed Artifact

After:

```bash
mvn install
```

inspect the local repository.

On macOS or Linux:

```bash
ls -la ~/.m2/repository/com/veriqta/veriqta-logging-library/1.0.0
```

You should find the installed artifact.

You can also inspect the project's original build output:

```bash
ls -la target
```

Now compare:

```text
Project:
target/veriqta-logging-library-1.0.0.jar

Local repository:
~/.m2/repository/com/veriqta/veriqta-logging-library/1.0.0/
```

This demonstrates the difference between packaging and installation.

# 18.9 Build a Small Internal Library

Let's make this concrete.

Create:

```text
veriqta-logging-library
```

Inside:

```text
veriqta-logging-library/
├── pom.xml
└── src/
    ├── main/java/com/veriqta/logging/
    └── test/java/com/veriqta/logging/
```

Create:

```text
src/main/java/com/veriqta/logging/VeriqtaLogger.java
```

with:

```java
package com.veriqta.logging;

public class VeriqtaLogger {

    public static void info(String message) {
        System.out.println("[VERIQTA INFO] " + message);
    }
}
```

This is intentionally simple.

Our objective is Maven artifact publishing, not building a sophisticated logging framework.

---

# 18.10 Create the Library POM

Create:

```xml
<?xml version="1.0" encoding="UTF-8"?>

<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="
             http://maven.apache.org/POM/4.0.0
             https://maven.apache.org/xsd/maven-4.0.0.xsd">

    <modelVersion>4.0.0</modelVersion>

    <groupId>com.veriqta</groupId>
    <artifactId>veriqta-logging-library</artifactId>
    <version>1.0.0</version>

    <properties>
        <maven.compiler.release>17</maven.compiler.release>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>

</project>
```

The important coordinates are:

```text
com.veriqta
:
veriqta-logging-library
:
1.0.0
```

These coordinates become the library's identity.

Run:


`package` runs the build to the packaging stage.

If successful, inspect:

```bash

```

You should find something similar to:

At this point:

```text
Library Source
     |
     v
Maven
     |
     v
Package
     |
     v
target/veriqta-logging-library-1.0.0.jar
```

But another independent project cannot necessarily resolve it through normal Maven dependency resolution yet.

# 18.13 Consume the Locally Installed Library

Create another project:

```text
veriqta-application
```

Its POM contains:

```xml
<dependency>
    <groupId>com.veriqta</groupId>
    <artifactId>veriqta-logging-library</artifactId>
    <version>1.0.0</version>
</dependency>
```

Notice that you do not write:

```text
/Users/ann/veriqta-logging-library/target/veriqta-logging-library-1.0.0.jar
```

You use Maven coordinates.

This is the correct mental model:

```text
Application
    |
    v
Dependency coordinates
    |
    v
Maven
    |
    v
Local repository
    |
    v
Library artifact
```

# 18.14 Use the Library

Inside the consuming application:

```java
package com.veriqta.app;

import com.veriqta.logging.VeriqtaLogger;

public class App {

    public static void main(String[] args) {
        VeriqtaLogger.info("Application started");
    }
}
```

Compile:

```bash
mvn compile
```

Maven resolves:

```text
com.veriqta:veriqta-logging-library:1.0.0
```

from your local repository.

This proves the artifact can be consumed without manually copying the JAR.

---

# 18.15 The Limitation of `mvn install`

Now imagine another developer clones:

```text
veriqta-application
```

They run:

```bash
mvn compile
```

Maven needs:

```text
com.veriqta:veriqta-logging-library:1.0.0
```

But that artifact exists only in:

```text
your ~/.m2/repository
```

Their machine has a different local repository.

So the build may fail.

This demonstrates an important rule:

```text
mvn install
is local to the Maven environment where it was run.
```

It does not publish the artifact for your team.

For shared consumption, you need a remote artifact repository.

---

# 18.16 What Is Remote Deployment?

Remote deployment means publishing a Maven artifact to a repository accessible to other authorized users or systems.

Examples include:

* An internal Nexus Repository
* JFrog Artifactory
* Another Maven-compatible repository
* A repository used by your organization's CI/CD system

The flow changes from:

```text
Developer
   |
   v
Local .m2
```

to:

```text
Developer / CI
      |
      v
Maven
      |
      v
Remote Artifact Repository
      |
      +--> Developer A
      +--> Developer B
      +--> CI
      +--> Other applications
```

The Maven phase used for publishing is:

```text
deploy
```

---

# 18.17 What Does `mvn deploy` Mean?

Run:

```bash
mvn deploy
```

Maven executes the lifecycle through the `deploy` phase.

Conceptually:

```text
validate
   |
   v
compile
   |
   v
test
   |
   v
package
   |
   v
verify
   |
   v
install
   |
   v
deploy
```

Therefore:

```text
deploy
```

is not simply an upload command.

It represents the final phase of Maven's default lifecycle.

By the time Maven reaches `deploy`, the project should already have passed the earlier lifecycle stages.

---

# 18.18 `deploy` Does Not Mean Deploying Your Application to Production

This is a critical terminology distinction.

In Maven:

```bash
mvn deploy
```

usually means:

```text
publish the built artifact to a remote Maven repository
```

It does not automatically mean:

```text
deploy my application to Kubernetes
```

or:

```text
deploy my application to AWS
```

or:

```text
start my application on a production server
```

These are different forms of deployment.

For example:

```text
Maven deploy
→ publish JAR to artifact repository

Application deployment
→ take an application artifact and run it in an environment
```

A CI/CD pipeline might contain both:

```text
Source
  |
  v
Maven Build
  |
  v
mvn deploy
  |
  v
Artifact Repository
  |
  v
Deployment Pipeline
  |
  v
Container / VM / Kubernetes
  |
  v
Application
```

Do not confuse the two meanings.

# 18.19 Distribution Management

How does Maven know where to publish an artifact?

One important POM section is:

```xml
<distributionManagement>
```

This describes where project artifacts should be distributed.

A simplified example is:

```xml
<distributionManagement>

    <repository>
        <id>veriqta-releases</id>
        <name>VERIQTA Release Repository</name>
        <url>https://repo.example.com/releases</url>
    </repository>

    <snapshotRepository>
        <id>veriqta-snapshots</id>
        <name>VERIQTA Snapshot Repository</name>
        <url>https://repo.example.com/snapshots</url>
    </snapshotRepository>

</distributionManagement>
```

Do not use the example URL literally.

The important structure is:

```text
distributionManagement
        |
        +-- repository
        |      |
        |      +-- releases
        |
        +-- snapshotRepository
               |
               +-- snapshots
```

---

# 18.20 Why Release and Snapshot Repositories Are Often Separate

Consider these versions:

```text
1.0.0
```

and:

```text
1.1.0-SNAPSHOT
```

They represent different ideas.

A release version normally represents a specific published release.

A snapshot represents ongoing development toward a future release.

An organization may therefore use:

```text
releases repository
```

for:

```text
1.0.0
1.1.0
2.0.0
```

and:

```text
snapshots repository
```

for:

```text
1.1.0-SNAPSHOT
2.0.0-SNAPSHOT
```

The architecture becomes:

```text
Maven Project
     |
     v
Read Version
     |
 +---+----------------+
 |                    |
 v                    v
1.0.0             1.1.0-SNAPSHOT
 |                    |
 v                    v
Release Repo       Snapshot Repo
```

---

# 18.21 Connecting `distributionManagement` to Credentials

The POM should not contain repository passwords.

Instead, it provides repository IDs:

```xml
<repository>
    <id>veriqta-releases</id>
    <url>https://repo.example.com/releases</url>
</repository>
```

Your Maven settings can contain:

```xml
<server>
    <id>veriqta-releases</id>
    <username>${env.MAVEN_REPO_USER}</username>
    <password>${env.MAVEN_REPO_PASSWORD}</password>
</server>
```

The matching ID is:

```text
veriqta-releases
```

Maven conceptually performs:

```text
distributionManagement
        |
        v
Repository ID
        |
        v
settings.xml
        |
        v
Matching server ID
        |
        v
Credentials
        |
        v
Remote repository
```

This continues the security model from Part 17.

---

# 18.22 Release Versions

A Maven release version does not contain the `-SNAPSHOT` suffix.

Examples:

```text
1.0.0
1.2.4
2.0.0
5.7.1
```

A release should represent a known, identifiable artifact.

For example:

```text
com.veriqta:logging-library:1.0.0
```

should identify a specific build of that library.

If an application successfully used that artifact yesterday, requesting:

```text
1.0.0
```

tomorrow should not unexpectedly give completely different code.

That leads us to artifact immutability.

---

# 18.23 Artifact Immutability

Immutability means something does not change after it has been created or published.

For Maven releases, the desired principle is:

```text
One coordinate
=
One immutable artifact
```

For example:

```text
com.veriqta:logging-library:1.0.0
```

should continue to mean the same artifact.

Do not publish:

```text
1.0.0
```

today, modify the source tomorrow, and silently overwrite:

```text
1.0.0
```

with a different JAR.

Instead publish a new version, such as:

```text
1.0.1
```

or another version appropriate to your versioning policy.

---

# 18.24 Why Overwriting Releases Is Dangerous

Imagine Application A builds Monday using:

```text
logging-library:1.0.0
```

Application B builds Wednesday using:

```text
logging-library:1.0.0
```

But someone overwrote the release on Tuesday.

Now:

```text
Application A
→ 1.0.0
→ Artifact X

Application B
→ 1.0.0
→ Artifact Y
```

The coordinates are identical, but the bytes differ.

This damages reproducibility.

You can no longer confidently say:

```text
Both applications used exactly the same dependency version.
```

That is why mature repository policies commonly prevent release artifacts from being overwritten or redeployed.

---

# 18.25 Why Immutability Matters to DevOps

Artifact immutability supports:

* Reproducible builds
* Traceability
* Rollbacks
* Auditing
* Incident investigation
* Supply-chain security
* Release confidence

Imagine a production incident.

The team asks:

```text
Which exact library did production use?
```

If:

```text
1.4.2
```

could have represented several different JARs over time, investigation becomes much harder.

A better system is:

```text
Version 1.4.2
       |
       v
One published artifact
       |
       v
Never silently replaced
```

---

# 18.26 What Is a SNAPSHOT Version?

A snapshot version represents a version that is still under development.

Example:

```text
1.1.0-SNAPSHOT
```

This means, conceptually:

```text
This is ongoing development toward 1.1.0.
```

The contents associated with a snapshot can change over time.

That is intentionally different from a release.

Think:

```text
1.0.0
→ fixed release

1.1.0-SNAPSHOT
→ changing development version
```

---

# 18.27 A Typical Development Version Flow

A team might begin development with:

```text
1.1.0-SNAPSHOT
```

During development:

```text
Commit A
   |
   v
1.1.0-SNAPSHOT

Commit B
   |
   v
1.1.0-SNAPSHOT

Commit C
   |
   v
1.1.0-SNAPSHOT
```

When the version is ready for release:

```text
1.1.0-SNAPSHOT
      |
      v
Testing / verification
      |
      v
1.1.0
```

Then the next development cycle might begin as:

```text
1.2.0-SNAPSHOT
```

The exact release workflow depends on the organization, but the snapshot versus release distinction remains important.

---

# 18.28 Timestamped Snapshots

A remote Maven repository does not necessarily store repeated snapshot deployments as one physical file simply called:

```text
library-1.1.0-SNAPSHOT.jar
```

Repository systems can represent deployed snapshots using timestamped versions.

Conceptually, Maven may request:

```text
1.1.0-SNAPSHOT
```

while the repository stores snapshot builds resembling:

```text
veriqta-logging-library-1.1.0-20260907.120001-1.jar

veriqta-logging-library-1.1.0-20260907.142530-2.jar
```

The exact timestamp and build-number values will differ.

The important concept is:

```text
Logical version:
1.1.0-SNAPSHOT

Remote snapshot builds:
timestamp + build number
```

This lets a repository distinguish multiple deployments of the same logical snapshot version.

---

# 18.29 Why Timestamped Snapshots Exist

Imagine three CI builds publish:

```text
1.1.0-SNAPSHOT
```

during one day.

Without distinguishing the builds, it would be difficult for repository metadata to track which snapshot is current.

Instead:

```text
1.1.0-SNAPSHOT
       |
       +-- timestamped build 1
       |
       +-- timestamped build 2
       |
       +-- timestamped build 3
```

Metadata can tell Maven which snapshot build should currently satisfy the logical snapshot dependency.

---

# 18.30 SNAPSHOT Dependencies Can Change

Suppose an application declares:

```xml
<dependency>
    <groupId>com.veriqta</groupId>
    <artifactId>veriqta-logging-library</artifactId>
    <version>1.1.0-SNAPSHOT</version>
</dependency>
```

Monday's build may resolve one snapshot.

A later build may resolve a newer snapshot.

Therefore:

```text
SNAPSHOT
```

does not provide the same immutability expectation as a release.

This is one reason production systems should use deliberate version and promotion policies rather than casually depending on moving snapshots.

---

# 18.31 Snapshot Update Behavior

Maven uses repository metadata and update policies when determining whether it should check for newer snapshots.

You learned the command:

```bash
mvn -U package
```

The:

```text
-U
```

option forces Maven to check for updated releases and snapshots according to Maven's resolution behavior.

This can be useful when you expect a newer snapshot but Maven appears to be using locally cached information.

However:

```bash
mvn -U
```

should not become a substitute for understanding your dependency and repository configuration.

---

# 18.32 Release Versus Snapshot

| Release                               | Snapshot                               |
| ------------------------------------- | -------------------------------------- |
| Example `1.0.0`                       | Example `1.1.0-SNAPSHOT`               |
| Represents a published release        | Represents ongoing development         |
| Should normally be immutable          | Can change over time                   |
| Suitable for stable consumption       | Useful during active development       |
| Normally stored in release repository | Normally stored in snapshot repository |
| Should not normally be overwritten    | New snapshot deployments are expected  |

The mental model is:

```text
SNAPSHOT
→ moving development target

RELEASE
→ fixed published artifact
```

---

# 18.33 Maven Version Conventions

Maven treats the string:

```text
-SNAPSHOT
```

specially.

For example:

```text
2.0.0-SNAPSHOT
```

has snapshot semantics.

A version without it, such as:

```text
2.0.0
```

is treated as a non-snapshot version.

Organizations may use many version formats.

Examples can include:

```text
1.0.0
1.0.1
2.0.0
3.4.7
```

Some organizations may also use qualifiers appropriate to their release processes.

Do not assume that Maven itself forces every project to use semantic versioning.

Semantic versioning is a versioning convention that projects may choose to follow.

---

# 18.34 Semantic Versioning Fundamentals

Semantic Versioning commonly uses:

```text
MAJOR.MINOR.PATCH
```

For example:

```text
2.4.1
```

means:

```text
2 = MAJOR
4 = MINOR
1 = PATCH
```

The conceptual rules are:

```text
MAJOR
→ incompatible API changes

MINOR
→ backward-compatible functionality

PATCH
→ backward-compatible fixes
```

For example:

```text
1.0.0
```

A compatible bug fix might become:

```text
1.0.1
```

A backward-compatible feature might become:

```text
1.1.0
```

A breaking API change might become:

```text
2.0.0
```

This is the basic semantic versioning mental model.

---

# 18.35 Maven Does Not Automatically Know Your API Compatibility

Suppose you change:

```java
public void log(String message)
```

to:

```java
public void log(String message, int level)
```

Maven does not automatically decide:

```text
This requires version 2.0.0.
```

Versioning policy is a project and organizational responsibility.

Maven uses the version you declare.

Therefore:

```text
Maven
→ understands coordinates and version strings

Team
→ decides what version the software should have
```

This distinction matters.

# 18.36 Versioning an Internal Library

Suppose VERIQTA starts with:

```text

```

A bug is fixed without breaking the API.

The team may publish:

```text
1.0.1
```

The application can then change:

```xml
<version>1.0.0</version>
```

to:

```xml
<version>1.0.1</version>
```

Now both artifacts can coexist:

```text

├── 1.0.0/

```

This is much safer than replacing `1.0.0`.

# 18.37 What Is Repository Metadata?

Repositories contain more than JAR files.

Maven also works with metadata.

Metadata can help describe information such as:

* Available versions
* Snapshot information
* Timestamped snapshot builds
* Plugin information where applicable
* Artifact resolution information

A repository directory may contain files such as:

```text
maven-metadata.xml
```

Conceptually:

```text
Repository
   |
   +-- artifact files
   |
   +-- POM files
   |
   +-- metadata
   |
   +-- checksums
```

Maven uses this information during artifact resolution and publishing.

# 18.38 Metadata and Snapshots

Snapshot metadata becomes particularly important.

Suppose Maven requests:

```text
1.1.0-SNAPSHOT
```

The repository may contain timestamped builds.

Maven needs information that connects the logical snapshot version to the available remote snapshot artifact.

Conceptually:

```text
1.1.0-SNAPSHOT
      |
      v
Repository metadata
      |
      v
Current timestamped snapshot
      |
      v
Actual artifact
```

This is one reason manually editing repository contents is a bad practice.

The repository manager should manage artifact files and their metadata consistently.

# 18.39 Repository Permissions

Publishing requires more privilege than downloading.

A developer may have:

```text
READ
```

permission but not:

```text
WRITE
```

permission.

A release pipeline may have:

```text
READ
+
DEPLOY
```

permission.

An administrator may have broader repository-management permissions.

Think in terms of least privilege:

```text
Consumer
→ read

Developer
→ read, perhaps snapshot publishing if required

CI release identity
→ read + controlled deployment

Repository administrator
→ administrative operations
```

Do not give every user administrative access simply because they use Maven.

---

# 18.40 Why Repository Permissions Matter

Imagine any developer can:

```text
overwrite releases
delete artifacts
publish arbitrary versions
change repository configuration
```

A simple mistake could affect many builds.

Artifact repositories are part of the software supply chain.

Permissions should reflect that importance.

The principle is:

```text
Identity
   |
   v
Only required permissions
   |
   v
Required repository operations
```

This is least privilege applied to Maven publishing.

# 18.42 Internal Library Publishing Workflow

```text

WAR files
POM artifacts
```

```text

```


# 18.44 Publishing Source Artifacts

A normal library artifact may contain compiled `.class` files.

```text
veriqta-logging-library-1.0.0-sources.jar
```

A source JAR contains source code associated with the artifact.

This can help:

* IDE navigation
* Debugging
* Understanding library behavior
* Developer experience

When your IDE lets you jump into dependency source code, a source artifact may be involved.

# 18.45 Source JAR Coordinates and Classifiers

Recall classifiers from Part 11.

The main artifact might be:

```text
veriqta-logging-library-1.0.0.jar
```

A source artifact might be:

```text
veriqta-logging-library-1.0.0-sources.jar
```

Here:

```text

```

acts as a classifier.

Conceptually:

```text

        |
        +-- main JAR
        |
        +-- sources JAR
        |

```

The classifier distinguishes additional artifacts associated with the same project version.

# 18.46 Creating a Sources JAR

The Maven Source Plugin can create source artifacts.

A project can configure an appropriate plugin execution to attach a sources JAR during the build.

A representative configuration is:

```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-source-plugin</artifactId>
    <version>PLUGIN_VERSION</version>

    <executions>
        <execution>
            <id>attach-sources</id>
            <goals>
                <goal>jar-no-fork</goal>
            </goals>
        </execution>
    </executions>
</plugin>
```

Use an appropriate current plugin version for the build rather than copying an arbitrary old version.

The important concept is:

```text
Source Plugin
     |
     v
Collect project source
     |
     v
Attach sources artifact
     |
     v
*-sources.jar
```

# 18.47 Publishing Javadocs

A library can also publish generated API documentation.

# 18.48 Why Sources and Javadocs Matter

They are not replacements for the main artifact.

The main JAR is what applications normally compile or run against.

Sources and Javadocs support developers.

Think:

```text
Main JAR
→ software classes

Sources JAR
→ source code

Javadoc JAR
→ generated API documentation
```

For an internal library used by many engineering teams, publishing these supporting artifacts can make the library easier to understand and troubleshoot.

# 18.49 Checksums and Artifact Integrity

Artifact repositories may also store or serve checksum information.

A checksum is a value calculated from file contents.

Conceptually:

```text
Artifact bytes
     |
     v
Hash function
     |
     v
Checksum
```

If the artifact changes:

```text
different bytes
     |
     v
different checksum
```

Checksums help detect accidental corruption and support artifact integrity checks.

They should not be confused with digital signatures. A checksum alone does not prove who published an artifact.

# 18.50 What Happens During Remote Publishing?

Suppose the project version is:

```text
1.0.0
```

and you run:

```bash
mvn deploy
```

A simplified process is:

```text
1. Maven reads pom.xml.

2. Maven executes lifecycle phases.

3. Source is compiled.

4. Tests run.

5. Artifact is packaged.

6. Verification occurs.

7. Artifact reaches install.

8. Maven reads distributionManagement.

9. Maven determines release or snapshot destination.

10. Maven obtains authentication configuration.

11. Maven connects to the remote repository.

12. Maven uploads the artifact.

13. Maven uploads associated POM information.

14. Attached artifacts may also be uploaded.

15. Repository metadata is updated as required.

16. Build reports success or failure.
```

This is much more than:

```text
copy JAR to server
```

# 18.55 Common Deployment Failure: 401 Unauthorized

Suppose:

```bash
mvn deploy
```

fails with:

```text
401 Unauthorized
```

This generally points toward authentication.

Possible causes:

* Missing credentials
* Wrong username
* Wrong token
* Expired credential
* Wrong server ID
* Maven reading the wrong settings file
* CI secret missing

Use:

```bash
mvn help:effective-settings
```

carefully to inspect effective configuration.

Do not expose secrets when sharing output.

Check:

```text
distributionManagement repository ID
            |
            v
settings.xml server ID
```

They need to correspond correctly.

---

# 18.56 Common Deployment Failure: 403 Forbidden

Suppose authentication succeeds, but:

```bash
mvn deploy
```

returns:

```text
403 Forbidden
```

Possible causes include:

* Account lacks deployment permission
* User can read but not write
* Snapshot account is trying to publish to releases
* Release policy prevents redeployment
* Repository path is restricted
* CI token lacks the required authorization

Ask:

```text
Can I download?
Can I upload?
Am I publishing to the correct repository?
Is this version allowed to be published?
```

Do not assume every HTTP error means "wrong password."

# 18.57 Common Deployment Failure: Release Already Exists

Suppose:

```text
1.0.0
```

was already published.

You modify the code and try:

```bash
mvn deploy
```

again.

A properly controlled release repository may reject the deployment.

That is often desirable.

The correct response may be:

```text
Do not overwrite 1.0.0.

Create the appropriate new version.
```

For example:

```text
1.0.1
```

This preserves artifact immutability.

# 18.58 Common Deployment Failure: Wrong Repository Type

Suppose the project version is:

```text
1.1.0-SNAPSHOT
```

but Maven is being directed to a repository that accepts only releases.

The repository may reject it.

Likewise:

```text
1.0.0
```

may not belong in a snapshots-only repository.

Check:

```text
Project version
       |
       v
Snapshot or release?
       |
       v
Correct repository destination?
```

This is why `distributionManagement` commonly distinguishes:

```xml
<repository>
```

and:

```xml
<snapshotRepository>
```

# 18.59 Common Deployment Failure: Connection Problems

Possible messages include:

```text

Connection refused
Unknown host
```

Investigate:

```text

network connectivity
proxy
firewall
repository hostname
repository port
VPN requirements
```

Do not start changing the POM's version simply because the network is unavailable.

Use the failure layer to guide troubleshooting.

# 18.60 Common Deployment Failure: TLS Problems

You may see:

```text

SSLHandshakeException
certificate validation errors
```

As covered in Part 17, investigate:

* Which JDK Maven is using
* Certificate chain
* Corporate CA requirements
* TLS inspection
* Repository certificate validity
* Java trust configuration

Check Maven's Java environment:

```bash
mvn -version
```

Do not disable certificate validation as a blind workaround.

# 18.61 Common Deployment Failure: Tests Fail

Suppose:

```bash
mvn deploy
```

starts correctly but tests fail.

Maven may never reach the `deploy` phase.

Remember:

```text

```

comes after earlier lifecycle phases.

So:

```text
test failure
     |
     v
build stops
     |
     v
deploy never reached
```

This is not a repository failure.

Read the build output carefully.

Find the first meaningful failure rather than focusing only on the final:

```text
BUILD FAILURE
```

# 18.62 Common Deployment Failure: Wrong Coordinates

Suppose the artifact publishes successfully, but another application cannot resolve it.

Producer:

```text
groupId:

artifactId:
veriqta-logging-library

version:
1.0.0
```

Consumer accidentally requests:

```text
groupId:
com.veriqta

artifactId:
veriqta-logger-library

version:
1.0.0
```

Those are different coordinates.

Maven does not infer what you meant.

Always compare:

```text

artifactId
version
packaging/classifier where relevant
```

exactly.

# 18.63 Common Deployment Failure: Wrong Version

The repository contains:

```text
1.0.0
```

but the application requests:

```text
1.0.1
```

Maven may report that it cannot find the artifact.

Do not immediately assume repository authentication is broken.

First ask:

```text

```

Artifact troubleshooting begins with identity.

# 18.64 Common Deployment Failure: Cached Resolution Information

Sometimes Maven previously attempted to resolve an artifact and cached information about the failed attempt.

If the artifact has since become available, you may need Maven to check again.

Depending on the situation:

```bash

```

can force update checks.

But again:

```text

```

does not fix:

* Incorrect coordinates
* Missing permissions
* Invalid credentials
* Wrong repository
* A release that was never published

Use it when update behavior is actually the issue.

# 18.71 Version Selection Is Part of API Responsibility

When you publish a library, other applications may depend on it.

Changing the library can therefore affect them.

Imagine:

```java

```

exists in:

```text
1.0.0
```

Several applications use it.

You remove it in a new build.

If you silently overwrite:

```text
1.0.0
```

those applications may suddenly fail even though their POM did not change.

Proper versioning communicates change.

This is why artifact versioning is not merely naming files.

It is part of dependency contracts.

```text
     |
     v

     |

     |
```

Maven's role is primarily around:


These responsibilities should not be mixed together mentally.

# 18.83 Step 7: Understand the Remote Configuration

A real project may contain:

```xml
<distributionManagement>

    <repository>
        <id>veriqta-releases</id>
        <url>https://your-approved-repository/releases</url>
    </repository>

    <snapshotRepository>
        <id>veriqta-snapshots</id>
        <url>https://your-approved-repository/snapshots</url>
    </snapshotRepository>

</distributionManagement>
```

And the Maven environment may supply matching credentials through `settings.xml`.

Do not invent a real repository URL or credentials for this exercise.

The important relationship is:

```text
POM
→ destination

settings.xml
→ credentials

Repository manager
→ storage and access control
```

# 18.90 Knowledge Check Answers

### Answer 1

`mvn package` creates the project's packaged artifact in the build output directory. `mvn install` also reaches the install phase and places the project artifact and relevant metadata into the local Maven repository.

### Answer 2

It publishes the project's artifacts to the configured remote artifact repository after the build reaches the `deploy` phase.

### Answer 3

Normally:

```text
~/.m2/repository
```

### Answer 4

Because Maven checks the local repository during dependency resolution and can find the installed artifact by its coordinates.

### Answer 5

Because their Maven environment has its own local repository. Your `.m2` repository is not automatically shared with them.

### Answer 6

It tells Maven where project artifacts should be distributed, including release and snapshot deployment destinations.

### Answer 7

A release repository stores published non-snapshot versions. A snapshot repository stores development snapshot versions that may change over time.

### Answer 8

It represents an in-development version associated with the future `1.2.0` release.

### Answer 9

Because several builds of the same logical snapshot version can be published. Timestamp and build information allows the repository to distinguish them.

### Answer 10

A published release coordinate should continue to identify the same artifact rather than silently changing later.

### Answer 11

Because overwriting releases damages reproducibility, traceability, rollback confidence, auditing, and dependency reliability.

### Answer 12

No. Maven supports version strings and gives `-SNAPSHOT` special meaning, but the project's versioning policy is determined by the project or organization.

### Answer 13

Conceptually:

```text
MAJOR
→ incompatible API change

MINOR
→ backward-compatible functionality

PATCH
→ backward-compatible fix
```

### Answer 14

An additional artifact containing the project's source code, commonly using the `sources` classifier.

### Answer 15

An artifact containing generated Javadoc documentation for the project's Java API.

### Answer 16

Because consumers may need Maven metadata such as transitive dependency information associated with the published project.

### Answer 17

Because earlier lifecycle phases such as compilation, testing, packaging, or verification can fail before Maven reaches deployment.

### Answer 18

A Git repository primarily stores source and its history. A Maven repository stores versioned build artifacts and Maven metadata.

### Answer 19

No. Maven's `deploy` phase normally means publishing artifacts to a remote Maven repository. Running the application in production is a separate deployment process.

### Answer 20

Because the publishing identity should have only the repository permissions required for its job, reducing the impact of credential misuse or compromise.
