# Part 4: Understanding pom.xml From the Ground Up

## Introduction

In Part 3, you created your first Maven project:

```text
veriqta-maven-app/
├── pom.xml
├── src/
│   ├── main/
│   │   ├── java/
│   │   └── resources/
│   └── test/
│       ├── java/
│       └── resources/
└── target/
```

You also ran:

```bash
mvn compile
```

Maven found your Java source, compiled it, and placed the generated `.class` file under:

```text
target/classes/
```

But one important file was only introduced briefly:

```text
pom.xml
```

That file is at the center of almost every Maven project.

A beginner can easily open a POM and see something like this:

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
                             https://maven.apache.org/xsd/maven-4.0.0.xsd">

    <modelVersion>4.0.0</modelVersion>

    <groupId>com.veriqta</groupId>
    <artifactId>veriqta-maven-app</artifactId>
    <version>1.0.0</version>

</project>
```

and think:

```text
What is all of this XML?

Why does Maven need it?

What is modelVersion?

Why are there several different versions?

What are groupId and artifactId?

Where do Maven's defaults come from?

Why can Maven build things I never configured?
```

This part removes that mystery.

We will not treat `pom.xml` as a file you copy from another project.

You will learn how to read it.

You will build it gradually.

You will deliberately break it.

You will ask Maven to show you the configuration it actually uses.

By the end, the POM should feel like a readable description of a Maven project rather than mysterious XML.

---

# 1. What Does POM Mean?

POM stands for:

```text
Project Object Model
```

The POM is Maven's model of a project.

The physical file containing that model is normally:

```text
pom.xml
```

Think of the relationship like this:

```text
pom.xml
   |
   v
Project Object Model
   |
   v
Maven understands the project
```

The POM can describe information such as:

* Project identity
* Project version
* Packaging type
* Dependencies
* Build plugins
* Properties
* Repositories
* Modules
* Profiles
* Build configuration
* Project metadata

Not every POM contains all of these.

A small project may have a very small POM.

A large enterprise project may have a much more complex one.

---

# 2. Why Does `pom.xml` Exist?

Imagine Maven receives this directory:

```text
veriqta-maven-app/
└── src/
```

Maven can use conventions to guess some things.

For example, Maven already knows the conventional location:

```text
src/main/java
```

But conventions cannot tell Maven everything.

Maven still needs project-specific information.

For example:

```text
What is this project called?

Who does it belong to?

What version is it?

What artifact should it produce?

Which dependencies does it require?

Which Java release should be targeted?

Which plugins should run?

Is this a JAR, WAR, or something else?
```

That information can be described through the POM.

Conceptually:

```text
Maven Defaults
      +
Project POM
      |
      v
Effective Project Configuration
      |
      v
Build
```

---

# 3. The POM Is More Than Build Instructions

It is tempting to think:

```text
pom.xml = build script
```

That description is incomplete.

The POM represents a project model.

It can describe:

```text
Identity
Dependencies
Build behavior
Packaging
Metadata
Modules
Properties
Repositories
Profiles
```

This is why Maven calls it the:

```text
Project Object Model
```

rather than simply:

```text
build.xml
```

Maven builds around a model of the project.

---

# 4. Where Does `pom.xml` Live?

For a normal single-module Maven project:

```text
veriqta-maven-app/
├── pom.xml
└── src/
```

`pom.xml` lives in the project root.

If your terminal is currently inside:

```text
~/projects/veriqta-maven-app
```

running:

```bash
ls
```

should show something similar to:

```text
pom.xml
src
target
```

When you run:

```bash
mvn compile
```

from this project directory, Maven reads the project's POM.

---

# 5. Why Is the POM an XML File?

The filename is:

```text
pom.xml
```

The extension:

```text
.xml
```

means the document uses XML.

XML stands for:

```text
Extensible Markup Language
```

You do not need to become an XML specialist to use Maven.

But you need enough XML knowledge to:

* Read a POM
* Edit a POM
* Understand nesting
* Recognize attributes
* Avoid malformed XML
* Understand namespaces at a basic level
* Interpret Maven errors

We will learn only the XML concepts needed for Maven.

---

# 6. XML Elements

Consider:

```xml
<artifactId>veriqta-maven-app</artifactId>
```

This contains an XML element named:

```text
artifactId
```

It has:

```text
Opening tag
Content
Closing tag
```

Visually:

```text
<artifactId>veriqta-maven-app</artifactId>
     |              |                |
     |              |                |
 opening          value            closing
   tag                              tag
```

The opening tag is:

```xml
<artifactId>
```

The content is:

```text
veriqta-maven-app
```

The closing tag is:

```xml
</artifactId>
```

Notice the slash:

```text
/
```

in the closing tag.

---

# 7. Opening and Closing Tags

Most POM elements use matching opening and closing tags.

Example:

```xml
<version>1.0.0</version>
```

Opening:

```xml
<version>
```

Closing:

```xml
</version>
```

The names must match.

This is invalid:

```xml
<version>1.0.0</artifactId>
```

because:

```text
version
```

was opened, but:

```text
artifactId
```

was closed.

XML requires proper structure.

---

# 8. XML Is Case-Sensitive

XML element names are case-sensitive.

These are different:

```xml
<groupId>
```

```xml
<groupid>
```

```xml
<GroupId>
```

Maven expects the element defined by its POM model.

For example:

```xml
<groupId>com.veriqta</groupId>
```

Do not randomly change capitalization.

---

# 9. XML Nesting

Elements can contain other elements.

Example:

```xml
<project>
    <groupId>com.veriqta</groupId>
    <artifactId>veriqta-maven-app</artifactId>
    <version>1.0.0</version>
</project>
```

Here:

```text
project
```

is the parent element.

Inside it are child elements:

```text
groupId
artifactId
version
```

Conceptually:

```text
project
├── groupId
├── artifactId
└── version
```

This is nesting.

---

# 10. Proper Nesting Matters

This is valid:

```xml
<project>
    <name>VERIQTA Maven App</name>
</project>
```

This kind of overlapping structure is invalid:

```xml
<project>
    <name>
</project>
    </name>
```

XML elements must close in the correct order.

Think of containers:

```text
Open project
    Open name
    Close name
Close project
```

Not:

```text
Open project
    Open name
Close project
Close name
```

---

# 11. XML Attributes

XML elements can also contain attributes.

Look at part of the POM root element:

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0">
```

Here:

```text
project
```

is the element.

```text
xmlns
```

is an attribute.

Its value is:

```text
http://maven.apache.org/POM/4.0.0
```

The general pattern is:

```xml
<element attribute="value">
```

An attribute provides additional information about an element.

---

# 12. Elements Versus Attributes

Compare:

```xml
<version>1.0.0</version>
```

Here, `version` is an element.

Compare:

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0">
```

Here:

```text
xmlns
```

is an attribute of `project`.

Do not treat these as interchangeable.

Maven's POM model defines where specific information belongs.

---

# 13. XML Declaration

A POM commonly begins with:

```xml
<?xml version="1.0" encoding="UTF-8"?>
```

This is an XML declaration.

It tells XML-processing software information about the document.

`version="1.0"` means:

```text
XML version 1.0
```

`encoding="UTF-8"` means the document uses UTF-8 character encoding.

For beginners, you normally keep this declaration as-is.

---

# 14. What Is Character Encoding?

Computers ultimately store text as numeric data.

An encoding defines how characters map to bytes.

UTF-8 is a widely used encoding capable of representing a very large range of characters.

Declaring:

```xml
encoding="UTF-8"
```

helps tools interpret the file consistently.

Later, we will also configure the Java project's source encoding.

Do not confuse:

```text
XML file encoding
```

with:

```text
Java source encoding configuration
```

They are related ideas but apply to different things.

---

# 15. The `<project>` Element

The central root element of a Maven POM is:

```xml
<project>
```

A real POM normally uses the Maven namespace declarations:

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
                             https://maven.apache.org/xsd/maven-4.0.0.xsd">
```

Everything describing the project is nested inside the `project` element.

At the bottom:

```xml
</project>
```

closes it.

Conceptually:

```text
project
|
+-- modelVersion
+-- groupId
+-- artifactId
+-- version
+-- packaging
+-- name
+-- description
+-- url
+-- properties
+-- dependencies
+-- build
+-- ...
```

Not every child is required.

---

# 16. What Is an XML Namespace?

The root element contains:

```xml
xmlns="http://maven.apache.org/POM/4.0.0"
```

`xmlns` means:

```text
XML namespace
```

Namespaces help identify which vocabulary the XML elements belong to.

This matters because many technologies use XML.

An element called:

```xml
<project>
```

could theoretically mean different things in different XML vocabularies.

The namespace helps identify this document's elements as belonging to the Maven POM model.

For a beginner, the important mental model is:

```text
XML namespace
→ identifies the XML vocabulary being used
```

You normally copy the standard Maven root declaration rather than inventing your own namespace.

---

# 17. What Is `xmlns:xsi`?

You will also see:

```xml
xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
```

This declares the namespace prefix:

```text
xsi
```

which is used by:

```xml
xsi:schemaLocation="..."
```

You do not need to memorize the URI.

You should recognize that these lines relate to XML namespace and schema information, not to your application's Maven coordinates.

---

# 18. What Is `xsi:schemaLocation`?

You may see:

```xml
xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
                    https://maven.apache.org/xsd/maven-4.0.0.xsd"
```

This associates a namespace with a schema location.

An XML schema can describe the structure expected for XML documents.

Editors and XML-aware tooling can use schema information for features such as:

* Validation
* Suggestions
* Completion
* Detecting invalid structures

For normal Maven work, you generally leave the standard declaration alone.

---

# 19. Your Minimal Learning POM

Start with:

```xml
<?xml version="1.0" encoding="UTF-8"?>

<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
                             https://maven.apache.org/xsd/maven-4.0.0.xsd">

    <modelVersion>4.0.0</modelVersion>

    <groupId>com.veriqta</groupId>
    <artifactId>veriqta-maven-app</artifactId>
    <version>1.0.0</version>

</project>
```

Before adding anything else, understand every project-specific line.

---

# 20. What Is `modelVersion`?

The POM contains:

```xml
<modelVersion>4.0.0</modelVersion>
```

This identifies the version of the POM model being used.

For the Maven POM model covered here:

```text
4.0.0
```

is the model version you will commonly see.

Do not confuse this with your application's version.

Compare:

```xml
<modelVersion>4.0.0</modelVersion>
```

and:

```xml
<version>1.0.0</version>
```

They refer to different things.

---

# 21. `modelVersion` Versus Project `version`

Think:

```text
modelVersion
→ version of Maven's POM model

version
→ version of your project/artifact
```

For example:

```xml
<modelVersion>4.0.0</modelVersion>

<version>1.0.0</version>
```

does not mean your application has two competing versions.

One describes the POM model.

One identifies your project version.

---

# 22. Project Identity

Maven commonly identifies an artifact using coordinates.

The three most important coordinate values are:

```text
groupId
artifactId
version
```

Often abbreviated:

```text
GAV
```

So:

```text
G = groupId
A = artifactId
V = version
```

Example:

```xml
<groupId>com.veriqta</groupId>
<artifactId>veriqta-maven-app</artifactId>
<version>1.0.0</version>
```

The GAV coordinates are:

```text
com.veriqta:veriqta-maven-app:1.0.0
```

---

# 23. What Is `groupId`?

Our POM contains:

```xml
<groupId>com.veriqta</groupId>
```

The `groupId` identifies the broader group, organization, project family, or namespace associated with the artifact.

Organizations commonly use reverse-domain-style naming.

Examples:

```text
com.veriqta
org.example
io.company
```

This helps reduce naming collisions.

---

# 24. Why Reverse-Domain Style Is Common

Suppose many organizations create an artifact called:

```text
logging
```

Using only:

```text
logging
```

would create ambiguity.

But:

```text
com.companya:logging
```

and:

```text
org.companyb:logging
```

are distinct coordinates.

A domain-based namespace helps organizations choose globally distinctive group identifiers.

The exact `groupId` is a project naming decision, but reverse-domain style is common.

---

# 25. What Is `artifactId`?

Our project uses:

```xml
<artifactId>veriqta-maven-app</artifactId>
```

The `artifactId` identifies this specific project or artifact within its group.

Think:

```text
groupId
→ broader namespace

artifactId
→ particular project
```

Example:

```text
com.veriqta
    |
    +-- veriqta-maven-app
    +-- platform-api
    +-- billing-service
    +-- monitoring-library
```

---

# 26. What Is `version`?

Our project currently uses:

```xml
<version>1.0.0</version>
```

The version distinguishes one release or development version of an artifact from another.

For example:

```text
com.veriqta:veriqta-maven-app:1.0.0
```

and:

```text
com.veriqta:veriqta-maven-app:2.0.0
```

refer to different versions.

---

# 27. What Are Project Coordinates?

Coordinates are Maven's way of identifying artifacts.

The core coordinates are:

```text
groupId
artifactId
version
```

or:

```text
GAV
```

Our project:

```text
Group:
com.veriqta

Artifact:
veriqta-maven-app

Version:
1.0.0
```

becomes:

```text
com.veriqta:veriqta-maven-app:1.0.0
```

---

# 28. Why Coordinates Matter

Imagine a Maven repository containing thousands of artifacts.

A name such as:

```text
utils
```

is not enough.

There may be hundreds of artifacts called something similar.

Coordinates provide structured identity.

Conceptually:

```text
Repository
   |
   +-- Group
          |
          +-- Artifact
                  |
                  +-- Version
```

For our example:

```text
com.veriqta
    |
    +-- veriqta-maven-app
            |
            +-- 1.0.0
```

---

# 29. How Coordinates Map Into a Maven Repository

Maven's local repository commonly organizes artifacts according to their coordinates.

Suppose the coordinates are:

```text
com.veriqta:veriqta-maven-app:1.0.0
```

The group:

```text
com.veriqta
```

maps conceptually to:

```text
com/veriqta
```

Then:

```text
artifactId:
veriqta-maven-app
```

Then:

```text
version:
1.0.0
```

So a repository path can resemble:

```text
com/
└── veriqta/
    └── veriqta-maven-app/
        └── 1.0.0/
```

Later, after installing an artifact locally, you may see files such as:

```text
veriqta-maven-app-1.0.0.jar
veriqta-maven-app-1.0.0.pom
```

Coordinates are therefore not abstract labels. They are central to how Maven identifies and resolves artifacts.

# 30. Naming Conventions

A useful beginner convention is:

### `groupId`

Use a stable namespace, commonly reverse-domain style:

```text
com.veriqta
```

### `artifactId`

Use a descriptive project name:

```text
veriqta-maven-app
```

Common artifact IDs might resemble:

```text
user-service

```

### `version`

Use a consistent versioning strategy:

```text

```

# 31. What Is `packaging`?

Add:

```xml
<packaging>jar</packaging>
```

Our POM now becomes:

```xml
<modelVersion>4.0.0</modelVersion>

<groupId>com.veriqta</groupId>
<artifactId>veriqta-maven-app</artifactId>
<version>1.0.0</version>
<packaging>jar</packaging>
```

`packaging` tells Maven the type of artifact or project packaging involved.

Common values include:

```text
jar
war
pom
```

---

# 32. JAR Packaging

For a normal Java application or library:

```xml
<packaging>jar</packaging>
```

is common.

JAR means:

```text
Java Archive
```

Later:

```bash
mvn package
```

can produce a file such as:

```text
target/veriqta-maven-app-1.0.0.jar
```

The artifact filename reflects:

```text
artifactId
+
version
+
packaging extension
```

Conceptually:

```text
veriqta-maven-app
+
1.0.0
+
.jar

=

veriqta-maven-app-1.0.0.jar
```

---

# 33. What If `packaging` Is Missing?

This introduces an important Maven concept:

```text
Defaults
```

If you omit the `packaging` element in a normal Maven project, Maven's model defaults packaging to:

```text
jar
```

Therefore these can result in the same effective packaging:

```xml
<packaging>jar</packaging>
```

and an otherwise suitable POM where `packaging` is omitted.

This is our first clear example of:

```text
What you wrote
```

versus:

```text
What Maven actually uses
```

That distinction leads to the Effective POM later in this part.

---

# 34. WAR Packaging

Another packaging type is:

```xml
<packaging>war</packaging>
```

WAR means:

```text
Web Application Archive
```

WAR packaging has traditionally been used for Java web applications intended for deployment to compatible servlet containers or application servers.

You do not need to build a WAR yet.

For now, recognize that packaging influences Maven's build behavior and expected artifact.

# 35. POM Packaging

You may also encounter:

```xml

```

This is commonly used for projects whose primary purpose is to provide a POM, such as:

* Parent projects
* Aggregator projects
* Multi-module build roots
* Shared project configuration

You will understand this much better when you reach multi-module Maven builds.

# 41. Understanding Release Versions

Our version is:

```xml
<version>1.0.0</version>
```

This is a fixed version identifier.

In normal Maven usage, a version without the special `SNAPSHOT` suffix is generally treated as a release-style version.

Examples:

```text
1.0.0
1.1.0
2.0.0
2026.09
```

Maven does not force you to use semantic versioning.

The important Maven distinction here is:

```text
Snapshot version
```

versus:

```text
Non-snapshot version
```

---

# 42. What Is a SNAPSHOT Version?

A Maven version ending in:

```text
-SNAPSHOT
```

represents a development version that may still change.

Example:

```xml
<version>1.1.0-SNAPSHOT</version>
```

Think:

```text
1.1.0-SNAPSHOT
→ development toward a future 1.1.0 release
```

The artifact is not being treated as a fixed final release.

---

# 43. Why SNAPSHOT Exists

Imagine a team is developing version:

```text
1.1.0
```

during Monday.

The artifact changes Tuesday.

It changes again Wednesday.

If every intermediate development build were treated as the immutable final:

```text
1.1.0
```

artifact, consumers could have trouble distinguishing a fixed release from changing development builds.

Instead:

```text
1.1.0-SNAPSHOT
```

communicates:

```text
This version is still under development and can be updated.
```

---

# 44. SNAPSHOT Mental Model

Think:

```text
1.0.0
→ fixed release-style version

1.1.0-SNAPSHOT
→ changing development version
```

Typical flow:

```text
Development
     |
     v
1.1.0-SNAPSHOT
     |
     v
Test
     |
     v
Release
     |
     v
1.1.0
```

After releasing `1.1.0`, development might move to:

```text
1.2.0-SNAPSHOT
```

---

# 45. SNAPSHOT Does Not Mean "Broken"

A common beginner misunderstanding is:

```text
SNAPSHOT = bad build
```

No.

`SNAPSHOT` indicates development mutability.

A snapshot build may:

* Compile successfully
* Pass every test
* Run correctly

It is simply identified as a development version that may change.

---

# 46. Why Release Versions Matter

A release version is expected to identify a stable, fixed artifact.

If production says:

```text
Deploy version 2.4.1
```

the expectation is that:

```text
2.4.1
```

identifies the same released artifact whenever it is retrieved from the relevant repository.

That predictability matters for:

* Deployment
* Rollback
* Auditing
* Reproducibility
* Incident response
* Dependency management

# 48. What Are Maven Properties?

Now we introduce:

```xml
<properties>
```

Properties allow values to be defined and referenced elsewhere.

Example:

```xml
<properties>
    <java.version>17</java.version>
</properties>
```

Now we have created a property named:

```text
java.version
```

with the value:

```text
17
```

Properties help centralize values and reduce repetition.

---

# 49. Property Structure

The general form is:

```xml
<properties>
    <property.name>value</property.name>
</properties>
```

Example:

```xml
<properties>
    <java.version>17</java.version>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
</properties>
```

Here we have two properties:

```text
java.version = 17
project.build.sourceEncoding = UTF-8
```

---

# 50. What Does `${...}` Mean?

Maven uses expressions such as:

```text
${java.version}
```

to reference property values.

If:

```xml
<java.version>17</java.version>
```

then:

```text
${java.version}
```

resolves to:

```text
17
```

Think:

```text
Property definition
      |
      v
java.version = 17
      |
      v
${java.version}
      |
      v
17
```

---

# 51. Why Properties Are Useful

Suppose the Java version appears in several configuration locations.

Without a reusable property:

```xml
<source>17</source>
<target>17</target>
```

If you later change versions, you must update multiple places.

With:

```xml
<properties>
    <java.version>17</java.version>
</properties>
```

other configuration can reference:

```text
${java.version}
```

This gives you one logical location for the value.

---

# 52. Maven Has More Than Custom Properties

Maven expressions can refer to different categories of values.

You may encounter:

* User-defined properties
* Project properties
* Settings-related values
* Environment-related values
* System properties

For this part, focus on:

```text

```

# 53. Project Properties

Maven exposes information from the current project model through expressions.

For example:

```text
${project.groupId}
${project.artifactId}
${project.version}
${project.name}
```

If our POM contains:

```xml
<groupId>com.veriqta</groupId>
<artifactId>veriqta-maven-app</artifactId>
<version>1.0.0</version>
```

then conceptually:

```text
${project.groupId}
→ com.veriqta

${project.artifactId}
→ veriqta-maven-app

${project.version}
→ 1.0.0
```

This allows project metadata to be referenced elsewhere in Maven configuration.

---

# 54. Why Project Properties Matter

Suppose configuration needs the project version.

Hardcoding:

```text
1.0.0
```

again creates duplication.

Referencing:

```text
${project.version}
```

means:

```text
Use the version belonging to this project.
```

This reduces the risk of duplicated values drifting apart.

# 55. Java Compiler Properties

In Part 3, we used:

```xml
<properties>
    <maven.compiler.release>17</maven.compiler.release>
</properties>
```

This property is recognized by Maven's compiler tooling.

It indicates the Java release targeted by compilation when supported by the compiler plugin and JDK being used.

Example:

```xml
<properties>
    <maven.compiler.release>17</maven.compiler.release>
</properties>
```

Think:

```text
Java source
     |
     v
Maven Compiler Plugin
     |
     v

```

---

# 56. Why `release` Is Important

Java compatibility involves more than simply accepting language syntax.

When supported, the Java compiler's `--release` mechanism helps compile against the documented API and language level of a particular Java release.

For a modern Maven project, using:

```xml
<maven.compiler.release>17</maven.compiler.release>
```

is often clearer than independently configuring old-style source and target levels.

You may still encounter older projects using:

```xml
<maven.compiler.source>...</maven.compiler.source>
<maven.compiler.target>...</maven.compiler.target>
```

You need to recognize both styles.

---

# 57. `source` and `target` Properties

Older or differently configured projects may contain:

```xml
<properties>
    <maven.compiler.source>17</maven.compiler.source>
    <maven.compiler.target>17</maven.compiler.target>
</properties>
```

At a beginner level:

```text
source
→ accepted Java source language level

target
→ generated class-file target level
```

But with a suitable modern JDK and compiler plugin, `release` is often preferable because it also constrains the Java API level.

Do not blindly mix:

```text
release
source
target
```

without understanding why.

For our learning project, we will use:

```xml
<maven.compiler.release>17</maven.compiler.release>
```

# 58. Your Installed JDK Still Matters

Suppose the POM says:

```xml
<maven.compiler.release>21</maven.compiler.release>
```

but Maven is running with a JDK that cannot compile for that release.

The POM cannot magically install or become a newer JDK.

Check the Java Maven actually uses:

```bash
mvn -version
```

Remember the relationship:

```text
POM compiler configuration
      +
JDK Maven is using
      |
      v
Compilation capability
```

This is why environment troubleshooting from Part 2 remains important.

# 64. What Does POM Validation Mean?

There are several layers of correctness to think about.

A POM may need to be:

```text
Well-formed XML
        |
        v
Valid enough for Maven's model
        |
        v
Semantically sensible for your build
```

These are not exactly the same thing.

---

# 65. Layer 1: Well-Formed XML

This:

```xml
<artifactId>veriqta-maven-app</artifactId>
```

is well formed.

This:

```xml
<artifactId>veriqta-maven-app
```

is not.

Maven cannot correctly parse malformed XML.

---

# 66. Layer 2: Maven Model Correctness

Even valid XML can be wrong for Maven.

For example:

```xml
<project>
    <banana>something</banana>
</project>
```

may be syntactically valid XML.

But:

```text
banana
```

is not a standard Maven project element in that location.

XML syntax being valid does not automatically make the POM a valid Maven project model.

---

# 67. Layer 3: Build Correctness

A POM can parse successfully but still configure a build that fails.

For example:

```xml
<maven.compiler.release>99</maven.compiler.release>
```

might be perfectly valid XML.

But your installed JDK cannot compile for an imaginary or unsupported release.

So remember:

```text
Valid XML
≠
Valid Maven configuration
≠
Successful build
```

---

# 68. Common XML Error: Missing Closing Tag

Broken:

```xml
<name>VERIQTA Maven Application
```

Maven may report a non-parseable POM.

Fix:

```xml
<name>VERIQTA Maven Application</name>
```

---

# 69. Common XML Error: Mismatched Tags

Broken:

```xml
<name>VERIQTA Maven Application</description>
```

Opened:

```text
name
```

Closed:

```text
description
```

Fix:

```xml
<name>VERIQTA Maven Application</name>
```

---

# 70. Common XML Error: Incorrect Nesting

Broken:

```xml
<properties>
</project>
</properties>
```

Correct nesting requires:

```xml
<project>
    <properties>
    </properties>
</project>
```

Think:

```text
Open project
    Open properties
    Close properties
Close project
```

---

# 71. Common POM Error: Wrong Element Name

Broken:

```xml
<artifactID>veriqta-maven-app</artifactID>
```

Maven expects:

```xml
<artifactId>veriqta-maven-app</artifactId>
```

XML is case-sensitive.

Do not guess element names.

---

# 72. Common POM Error: Confusing `modelVersion` and `version`

Incorrect reasoning:

```text
My application is version 2.0.0, so I should change modelVersion to 2.0.0.
```

No.

Keep the POM model declaration appropriate:

```xml
<modelVersion>4.0.0</modelVersion>
```

Change the project version:

```xml
<version>2.0.0</version>
```

Result:

```xml
<modelVersion>4.0.0</modelVersion>

<groupId>com.veriqta</groupId>
<artifactId>veriqta-maven-app</artifactId>
<version>2.0.0</version>
```

---

# 73. Common POM Error: Treating `name` as `artifactId`

This:

```xml
<name>VERIQTA Maven Application</name>
```

does not replace:

```xml
<artifactId>veriqta-maven-app</artifactId>
```

The project name is metadata.

The artifact ID participates in Maven coordinates.

---

# 74. Common POM Error: Incorrect Java Version

Suppose:

```xml
<maven.compiler.release>21</maven.compiler.release>
```

but:

```bash
mvn -version
```

shows Maven running under an older JDK that cannot target Java 21.

The build can fail.

Investigate:

```bash
java -version
javac -version
mvn -version
```

Do not inspect only the POM.

The runtime environment matters.

---

# 75. Common POM Error: Putting Elements in the Wrong Place

XML nesting has meaning.

For example, properties belong inside:

```xml
<properties>
```

which belongs inside:

```xml
<project>
```

Do not randomly move elements because the document remains visually readable.

Maven expects a specific model structure.

---

# 76. What Is the Effective POM?

Now we reach one of the most important concepts in this part.

The POM file you wrote is not necessarily the complete configuration Maven ultimately uses.

Your `pom.xml` might say:

```xml
<groupId>com.veriqta</groupId>
<artifactId>veriqta-maven-app</artifactId>
<version>1.0.0</version>
```

But Maven knows much more than those three lines.

For example, even if you omit:

```xml
<packaging>jar</packaging>
```

Maven can still treat the project as JAR packaging by default.

Where did that come from?

The effective model includes configuration assembled from multiple sources and defaults.

The resulting project configuration is commonly inspected as the:

```text
Effective POM
```

---

# 77. Written POM Versus Effective POM

Think:

```text
Your pom.xml
      |
      +
Parent POM information
      |
      +
Super POM
      |
      +
Maven model defaults
      |
      +
Profile/configuration effects where applicable
      |
      v
Effective POM
```

For a beginner, the key idea is:

```text
pom.xml
→ what you explicitly wrote

Effective POM
→ the fuller project model Maven resolves and uses
```

---

# 78. Why the Effective POM Matters

Suppose you open `pom.xml` and cannot find any configuration mentioning a particular default plugin or repository behavior.

Yet Maven still behaves as though some configuration exists.

Instead of assuming Maven is doing something magical, inspect:

```text
Effective POM
```

This is especially useful when troubleshooting:

* Inherited configuration
* Parent POMs
* Default plugin behavior
* Repository definitions
* Build directories
* Lifecycle-related configuration
* Properties
* Plugin management

# 83. What Is the Super POM?

Maven has a built-in top-level POM model known as the:

```text
Super POM
```

All Maven project POMs ultimately inherit defaults from Maven's Super POM unless overridden through the project hierarchy/configuration.

Think:

```text
Super POM
    |
    v
Project POM
    |
    v
Effective POM
```

Later, when you introduce parent POMs:

```text
Super POM
    |
    v
Parent POM
    |
    v
Child POM
    |
    v
Effective POM
```

---

# 84. Why Does the Super POM Exist?

Imagine every Maven project had to manually configure every basic default.

Every POM would contain large amounts of repeated configuration.

Maven instead supplies foundational defaults.

Your project can then define only what it needs to define or override.

This supports Maven's broader philosophy:

```text
Convention over configuration
```

---

# 85. What Kind of Defaults Come From Maven?

Maven's effective behavior can include defaults or inherited values for things such as:

* Repository configuration
* Build directory locations
* Output locations
* Source locations through conventions
* Plugin behavior associated with lifecycle packaging
* Reporting-related defaults

Not every default comes from exactly the same mechanism.

This distinction matters.

Some behavior comes from:

```text
Super POM inheritance
```

Some comes from:

```text
Maven's model defaults
```

Some comes from:

```text
Standard directory conventions
```

Some comes from:

```text
Lifecycle mappings for the packaging type
```

Some comes from:

```text
Plugin defaults
```

Do not label every invisible Maven behavior as "the Super POM."

---

# 86. A Better Mental Model for Maven Defaults

Use:

```text
Maven Behavior
     |
     +---- Project pom.xml
     |
     +---- Parent POMs
     |
     +---- Super POM
     |
     +---- Model defaults
     |
     +---- Standard conventions
     |
     +---- Lifecycle mappings
     |
     +---- Plugin defaults/configuration
```

This is more accurate than:

```text
Everything Maven does automatically comes from the Super POM.
```

---

# 87. Super POM Versus Parent POM

These terms are related but not identical.

The Super POM is built into Maven.

A parent POM can be explicitly declared by a project.

Later, you may see:

```xml
<parent>
    ...
</parent>
```

That tells the project to inherit from a particular parent POM.

Even without an explicit parent, the Maven model ultimately inherits foundational information from the Super POM.

Conceptually:

```text

→ universal Maven base

Parent POM
→ optional project or organization-specific parent

Project POM
→ this project's own configuration
```

Compilation reports that the configured release is not supported.

A POM should not become a dumping ground.

Build configuration is production engineering code.

---

# 125. Security: Never Hardcode Secrets in the POM

Do not write:

```xml
<password>my-real-password</password>
```

into a project POM and commit it to Git.

Do not place:

* Repository passwords
* Cloud keys
* Tokens
* Private API keys
* Database credentials
* Deployment secrets

directly into source-controlled Maven configuration.

Why?

Because Git history can preserve secrets even after a line is later deleted.

Build systems frequently interact with powerful infrastructure.

A compromised build credential can become a supply-chain risk.

# 126. POM and Supply-Chain Awareness

The POM can influence:

```text
Dependencies
Plugins
Repositories
Build execution
Artifact production
```

That means changes to `pom.xml` deserve code review.

A malicious or careless POM change could potentially:

* Introduce an unsafe dependency
* Change a plugin
* Change artifact sources
* Alter build behavior
* Change generated artifacts

For DevOps engineers:

```text
pom.xml
```

is not "just configuration."

It participates directly in the software supply chain.

# 144. Knowledge Check Answers

## 1. What does POM stand for?

Project Object Model.

## 2. Why does Maven need it?

Conventions provide defaults, but Maven still needs project-specific information such as identity, version, dependencies, plugins, properties, and packaging.

## 3. What is an XML element?

A structured piece of XML represented by tags, such as:

```xml
<version>1.0.0</version>
```

## 4. Opening versus closing tag?

Opening:

```xml
<version>
```

Closing:

```xml
</version>
```

The closing tag contains `/`.

## 5. Is XML case-sensitive?

Yes.

## 6. What is nesting?

Placing elements inside other elements according to the document hierarchy.

## 7. What is an attribute?

Additional information declared inside an element's opening tag.

## 8. What is a namespace?

It identifies the XML vocabulary to which elements belong.

## 9. Maven POM root element?

```xml
<project>
```

## 10. What is `modelVersion`?

It identifies the Maven POM model version.

## 11. Is it the application version?

No.

## 12. What is `groupId`?

The broader namespace or group associated with the artifact.

## 13. What is `artifactId`?

The identifier for the specific artifact/project within the group.

## 14. What is `version`?

The project's artifact version.

## 15. What is GAV?

```text
GroupId
ArtifactId
Version
```

## 16. Our coordinates?

Using version `1.0.0-SNAPSHOT`:

```text
com.veriqta:veriqta-maven-app:1.0.0-SNAPSHOT
```

## 17. Why coordinates?

They give artifacts structured identities Maven can use for dependency and repository operations.

## 18. What does packaging control?

The project's packaging type and associated build expectations.

## 19. Default packaging?

```text
jar
```

## 20. What is a JAR?

A Java Archive.

## 21. What is a SNAPSHOT?

A Maven version marked as an evolving development version, typically using the `-SNAPSHOT` suffix.

## 22. Is it broken?

No.

It means the development version may change.

## 23. Why fixed releases?

They support predictable deployment, rollback, traceability, and reproducibility.

## 24. What are properties?

Named values that can be referenced by Maven configuration.

## 25. `${java.version}`?

It refers to the value associated with a property named `java.version`.

## 26. `${project.version}`?

It references the current Maven project's resolved version.

## 27. `maven.compiler.release`?

It configures the Java release target used by Maven compiler tooling when supported.

## 28. Why can it still fail?

Because the JDK Maven is actually using must support the requested release.

## 29. Why UTF-8?

To make text encoding explicit and improve consistency between build environments.

## 30. What is the Effective POM?

The resolved project model Maven uses after combining the relevant project configuration, inheritance, defaults, and other applicable model information.

## 31. Why is it larger?

Because Maven supplies or inherits configuration you did not explicitly write.

## 32. What is the Super POM?

Maven's built-in base POM from which Maven project models inherit foundational configuration.

## 33. Does every default come from it?

No.

Some behavior comes from model defaults, conventions, lifecycle mappings, plugin defaults, and other mechanisms.

## 34. `mvn help:effective-pom`?

It displays the effective POM.

## 35. `mvn help:effective-settings`?

It displays Maven's effective settings.

## 36. POM versus settings?

```text
pom.xml
→ project configuration

settings.xml
→ Maven user/environment configuration
```

## 37. Why not hardcode credentials?

Because POM files are commonly stored in source control and can expose secrets, including through Git history.

## 38. `help:evaluate`?

It lets you evaluate Maven expressions and inspect resolved project values.

## 39. How do you investigate `target`?

Inspect:

```bash
mvn help:effective-pom
```

or evaluate:

```bash
mvn help:evaluate -Dexpression=project.build.directory -q -DforceStdout
```

## 40. Why should DevOps engineers understand POMs?

Because Maven configuration controls how source becomes build output and can affect dependencies, plugins, repositories, versions, CI behavior, artifact creation, security, and deployment.

# 145. Final Mental Model

Do not leave this part thinking:

```text
pom.xml
=
some XML Maven requires
```

Use this mental model:

```text
                    pom.xml
                       |
        +--------------+--------------+
        |              |              |
        v              v              v
     Identity       Metadata       Build Inputs
        |              |              |
        v              v              v
     groupId          name         properties
   artifactId     description      packaging
     version           url
        |
        v
      GAV
        |
        +-----------------------------+
                                      |
                                      v
                                  Maven Model
                                      |
                       +--------------+--------------+
                       |                             |
                       v                             v
                  Inheritance                    Defaults
                       |                             |
                       +--------------+--------------+
                                      |
                                      v
                                Effective POM
                                      |
                                      v
                                  Maven Build
                                      |
                    +-----------------+-----------------+
                    |                 |                 |
                    v                 v                 v
                 Compile            Test             Package
                                                          |
                                                          v
                                                       Artifact
```

And outside the project model:

```text
settings.xml
     |
     +---- repositories/mirrors
     +---- credentials
     +---- proxies
     +---- user/environment configuration
     |
     v
Maven execution environment
```

The most important change in your understanding is this:

```text
pom.xml
is what you write.

Effective POM
is closer to what Maven actually sees.
```

When Maven behavior seems mysterious, do not immediately guess.

Inspect it:

```bash
mvn help:effective-pom
```

Inspect the environment when relevant:

```bash
mvn help:effective-settings
```

Inspect specific values:

```bash
mvn help:evaluate -Dexpression=project.version -q -DforceStdout
```

Then reason from evidence.

At this point, `pom.xml` should no longer look like mysterious XML. You should be able to open a basic Maven POM and identify the project, understand its coordinates, recognize its packaging and properties, distinguish development snapshots from releases, and investigate the effective configuration Maven actually uses.
