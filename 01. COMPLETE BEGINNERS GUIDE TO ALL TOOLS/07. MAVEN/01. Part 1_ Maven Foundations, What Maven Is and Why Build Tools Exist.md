
# Part 1: Maven Foundations, What Maven Is and Why Build Tools Exist

## Introduction

Before learning Maven commands, configuration files, dependencies, plugins, repositories, or build lifecycles, you need to understand why Maven exists.

A beginner can easily make the mistake of seeing Maven as just another command-line tool.

It is much more useful to understand Maven as part of a larger software build process.

When a developer writes Java code, that code does not automatically become a finished application.

Several things usually need to happen.

The code may need to be:

* Compiled
* Tested
* Combined with external libraries
* Packaged
* Checked for errors
* Prepared for deployment
* Stored as a reusable artifact

When a project becomes large, doing all of these tasks manually becomes slow, repetitive, and error-prone.

Build tools exist to manage these tasks.

Apache Maven is one of the most widely used build and project management tools in the Java ecosystem.

In this first part, you will learn:

* What a software build is
* What happens between writing Java code and running an application
* Why Java code must usually be compiled
* What build tools are
* Why build tools became necessary
* How Java can be compiled manually
* Why manual compilation becomes difficult in real projects
* What Maven is
* What Maven does
* How Maven differs from Java, Git, Jenkins, IDEs, Gradle, and Ant
* Where Maven fits in software development
* Where Maven fits in DevOps
* The Maven terms you will encounter later
* Why Maven uses conventions
* The basic Maven architecture
* What Maven will eventually automate for you

The goal is simple.

By the end of this part, Maven should no longer look like a mysterious tool.

# 1. What Is a Software Build?

A software build is the process of turning source code into something that can be executed, tested, distributed, or deployed.

Developers normally write code in a human-readable programming language.

For example, a Java developer might write:

```java
public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello from VERIQTA");
    }
}
```

This is Java source code.

A computer does not normally execute this source file directly.

The source code must go through a process before it becomes something that the Java runtime can execute.

That process is part of the software build.

A simple Java build might look like this:

```text
Java source code
        |
        v
Compilation
        |
        v
Java bytecode
        |
        v
Testing
        |
        v
Packaging
        |
        v
Application artifact
```

In a small program, the build process may contain only one or two steps.

In a real application, the build can involve many tasks.

For example:

```text
Source Code
    |
    v
Resolve Dependencies
    |
    v
Compile
    |
    v
Run Unit Tests
    |
    v
Run Integration Tests
    |
    v
Copy Resources
    |
    v
Generate Files
    |
    v
Package Application
    |
    v
Create Artifact
    |
    v
Publish Artifact
```

A build therefore means much more than simply compiling code.

Compilation is one part of the build.

# 2. What Happens Between Writing Java Code and Running an Application?

Suppose a developer creates a Java application.

They write a file named:

```text
Hello.java
```

Inside it:

```java
public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello from VERIQTA");
    }
}
```

The developer has written source code.

The next question is:

How does this become a running application?

The basic process is:

```text
Developer writes Java code
        |
        v
Java source file
Hello.java
        |
        v
Java compiler
javac
        |
        v
Compiled bytecode
Hello.class
        |
        v
Java Virtual Machine
JVM
        |
        v
Running application
```

Each step has a different purpose.

## Step 1: Write the Source Code

The developer writes Java instructions in a `.java` file.

Example:

```text
Hello.java
```

This file is designed to be readable by humans.

---

## Step 2: Compile the Source Code

The Java compiler reads the `.java` file.

The compiler checks the program for problems such as:

* Syntax errors
* Missing symbols
* Invalid Java statements
* Type errors

If the source code is valid, the compiler converts it into Java bytecode.

For example:

```text
Hello.java
```

becomes:

```text
Hello.class
```

The `.class` file contains Java bytecode.

---

## Step 3: Run the Compiled Code

The Java Virtual Machine, commonly called the JVM, executes the bytecode.

The command may look like:

```bash
java Hello
```

The JVM loads the compiled class and runs the program.

The output might be:

```text
Hello from VERIQTA
```

This process already involves several components:

```text
Java source
→ Java compiler
→ Bytecode
→ JVM
→ Running program
```

A build tool such as Maven does not replace Java.

Instead, it organizes and automates many of the tasks surrounding this process.

# 3. Source Code Versus Compiled Code

Understanding the difference between source code and compiled code is fundamental.

## Source Code

Source code is the code written by the developer.

For Java, source files normally end with:

```text
.java
```

Example:

```text
Hello.java
```

Source code is intended to be understandable by humans.

Example:

```java
public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello");
    }
}
```

---

## Compiled Code

Compiled code is generated by a compiler.

In Java, compilation produces bytecode stored in `.class` files.

Example:

```text
Hello.class
```

Java bytecode is not intended to be written manually by developers.

The JVM understands how to execute it.

The relationship is:

```text
Hello.java
Source Code
    |
    v
javac
Compiler
    |
    v
Hello.class
Bytecode
```

# 4. What Is a Build Tool?

A build tool is software that automates tasks required to turn source code into a usable software artifact.

A build tool can perform tasks such as:

* Compile source code
* Download libraries
* Manage dependencies
* Run tests
* Copy resources
* Generate files
* Package applications
* Create JAR files
* Create WAR files
* Run plugins
* Publish artifacts
* Clean old build files

Instead of the developer manually performing every task, the build tool coordinates them.

A simplified example:

Without a build tool:

```text
Developer
→ Find libraries manually
→ Download JAR files manually
→ Configure classpaths
→ Compile every source file
→ Compile tests
→ Run tests
→ Copy resources
→ Package files
→ Create JAR
```

With a build tool:

```text
Developer
→ Run build command
→ Build tool performs the workflow
```

This is one of the main reasons Maven exists.

---

# 5. Why Do Build Tools Exist?

Build tools exist because software projects quickly become too complicated to build manually.

Imagine a project with:

* 300 Java classes
* 50 external libraries
* 200 unit tests
* Configuration files
* Images
* Database scripts
* Multiple modules
* Different environments
* Multiple developers

Building such a project manually would require developers to repeatedly perform many tasks.

They would need to remember:

* Which files to compile
* Which libraries are required
* Which versions to use
* Which directories contain the files
* Which tests to run
* Which files belong in the final package
* Which command-line options are required
* Which resources need copying
* Where the final application should be placed

A build tool allows these rules to be defined once and reused.

This gives developers a more consistent build process.

# 6. Problems Developers Faced Before Modern Build Tools

Before modern build automation became common, developers frequently relied on manual procedures, scripts, or custom build instructions.

This caused several problems.

## Problem 1: Builds Were Difficult to Reproduce

One developer might successfully build the application.

Another developer might fail.

Why?

Their machine might have:

* Different library versions
* Different directory structures
* Different environment variables
* Different Java versions
* Missing files

This leads to the familiar problem:

```text
It works on my machine.
```

Build tools help standardize the process.

---

## Problem 2: Dependencies Had to Be Managed Manually

Suppose an application requires an external Java library.

Without dependency management, a developer might:

1. Visit a website.
2. Find the library.
3. Download a JAR.
4. Store it somewhere.
5. Add it to the Java classpath.
6. Repeat this for every dependency.

Now imagine 30 dependencies.

It gets worse because those dependencies may depend on additional libraries.

For example:

```text
Application
   |
   v
Library A
   |
   +---- Library B
   |
   +---- Library C
```

The application may depend on Library A.

But Library A may require Libraries B and C.

These are called transitive dependencies.

Managing this manually becomes difficult very quickly.

---

## Problem 3: Developers Used Different Build Instructions

One developer might use:

```bash
javac
```

Another might use a shell script.

Another might build from an IDE.

Another might use a custom batch file.

The same project could therefore behave differently depending on who built it.

---

## Problem 4: Build Scripts Became Complex

Developers often created scripts for repetitive tasks.

For example:

```bash
compile.sh
```

That script might compile code.

Another script might run tests.

Another might package the application.

Eventually the project could have many scripts.

The build system itself becomes something that developers must maintain.

---

## Problem 5: Large Projects Have Build Order Requirements

Suppose a project contains:

```text
common-library
application-service
web-application
```

The application service depends on the common library.

The web application depends on the application service.

The build order must therefore be:

```text
common-library
      |
      v
application-service
      |
      v
web-application
```

Building them in the wrong order may fail.

Modern build systems help coordinate these relationships.

# 14. Introduce a Compilation Error

It is useful to see what happens when compilation fails.

Change:

```java
System.out.println("Hello from VERIQTA");
```

to something invalid, for example:

```java
System.out.println("Hello from VERIQTA")
```

Notice the missing semicolon.

Now run:

```bash
javac Hello.java
```

You should receive a compilation error.

It may look similar to:

```text
error: ';' expected
```

The compiler is telling you that the Java syntax is invalid.

Fix the line:

```java
System.out.println("Hello from VERIQTA");
```

Then compile again:

```bash
javac Hello.java
```

Run:

```bash
java Hello
```

This simple troubleshooting cycle is important:

```text
Write
→ Compile
→ Read Error
→ Fix
→ Compile Again
→ Run
```

Build tools do not eliminate compilation errors.

They organize how compilation and other build tasks happen.

# 18. What Is Apache Maven?

Apache Maven is a build automation and project management tool used primarily in the Java ecosystem.

A simple beginner definition is:

Maven helps define, organize, and automate how a software project is built.

Instead of manually remembering every command, dependency, directory, and build step, you describe the project to Maven.

Maven then performs the required tasks.

For example:

```text
Developer
    |
    v
Maven Project
    |
    v
Maven reads project configuration
    |
    v
Downloads dependencies
    |
    v
Compiles code
    |
    v
Runs tests
    |
    v
Packages application
```

Maven is not the Java compiler itself.

Maven can invoke the Java compiler as part of a build.

That distinction is important.

# 27. Maven Versus Gradle

Gradle is another build automation tool.

Both Maven and Gradle can:

* Compile applications
* Manage dependencies
* Run tests
* Package software
* Build multi-module projects

The main difference for a beginner is that they use different build models and configuration styles.

Maven commonly uses:

```text
pom.xml
```

Gradle commonly uses files such as:

```text
build.gradle
```

or:

```text
build.gradle.kts
```

Maven strongly emphasizes conventions and a defined project model.

Gradle is often more flexible and programmable.

At beginner level, you do not need to decide which tool is universally better.

Many organizations use Maven.

Many others use Gradle.

Learning Maven gives you a strong understanding of build automation concepts that also help when learning other build tools.

# 28. Maven Versus Ant

Apache Ant is an older Java build tool that is still found in some environments.

Ant generally requires developers to describe build tasks more explicitly.

A developer might create instructions for:

```text
Compile these files
Copy these resources
Create this directory
Package these files
```

Maven moved toward a more standardized model.

Instead of describing every low-level action, Maven uses conventions and lifecycle phases.

Conceptually:

Ant often asks:

```text
What exact tasks should I execute?
```

Maven often asks:

```text
What kind of project is this, and what lifecycle phase do you want to run?
```

This distinction helped Maven reduce the amount of custom build configuration needed for common Java projects.

# 45. Why Maven Uses Conventions

One of Maven's major ideas is convention over configuration.

This means Maven expects projects to follow certain standard patterns.

For example, Maven commonly expects Java source code in:

```text

```

Tests usually go in:

```text

```

Build output usually goes in:

```text
target
```

Because Maven already knows these conventions, you do not need to describe every directory manually.

---

# 46. Convention Over Configuration

Convention over configuration means:

Use sensible defaults unless you specifically need something different.

Imagine two approaches.

## Approach A: Configure Everything

A build system could require:

```text
My source folder is here.
My test folder is here.
My output folder is here.
My resources are here.
My package should go here.
```

Every project would require a lot of configuration.

---

## Approach B: Follow a Convention

Maven says:

```text
Put Java source here:
src/main/java

Put tests here:
src/test/java

Put resources here:
src/main/resources

Build output goes here:
target
```

If you follow these conventions, Maven already understands your project.

This makes Maven builds more predictable.

A developer joining a new Maven project can often recognize the structure immediately.

---

```text

```

Now the project structure is predictable.

This is especially useful in larger engineering organizations.

# 63. Troubleshooting the Practical Activity

## Problem: `javac: command not found`

### What You See

You run:

```bash
javac Hello.java
```

and the shell reports that `javac` cannot be found.

### Possible Cause

The JDK may not be installed.

Or the JDK may exist but its `bin` directory is not available through PATH.

### Investigation

Run:

```bash
java -version
```

Then:

```bash
javac -version
```

If `java` exists but `javac` does not, you may have only a runtime environment or an incomplete Java setup.

### Fix

Install a proper JDK and make sure its tools are available in PATH.

### Verification

Run:

```bash
javac -version
```

You should see the compiler version.

---

# 64. Problem: `Could not find or load main class Hello`

You run:

```bash
java Hello
```

but Java cannot find the class.

Possible causes include:

* You are in the wrong directory
* `Hello.class` does not exist
* Compilation failed
* The class name does not match
* Package structure is involved

Start with:

```bash
ls
```

Verify that you can see:

```text
Hello.class
```

Then verify that you are running:

```bash
java Hello
```

from the correct directory.

This introduces an important troubleshooting habit.

Do not immediately guess.

Inspect the actual state first.

---

# 70. Knowledge Check Answers

## 1. What is a software build?

A software build is the process of transforming source code and related project files into a usable, testable, packaged, or deployable software output.

## 2. What is the difference between a `.java` file and a `.class` file?

A `.java` file contains Java source code written by a developer.

A `.class` file contains compiled Java bytecode.

## 3. What command compiles Java source code?

```bash
javac
```

## 4. What does the JVM execute?

Java bytecode.

## 5. Why does manual Java compilation become difficult in large projects?

Because large projects contain many source files, dependencies, tests, resources, modules, and packaging requirements.

## 6. What is a build tool?

A build tool automates tasks involved in turning source code into usable software.

## 7. What problem does Maven solve?

Maven standardizes and automates project builds, dependency management, testing, packaging, and related project tasks.

## 8. Is Maven the Java compiler?

No.

Maven can invoke compilation as part of the build process.

## 9. Is Maven part of Git?

No.

Git handles version control.

Maven handles builds.

## 10. How can Jenkins and Maven work together?

Jenkins can run Maven commands as part of a CI/CD pipeline.

## 11. What is a Maven artifact?

A file produced or managed by Maven, such as a JAR.

## 12. What is a dependency?

An external library or component required by the project.

## 13. What is a repository?

A location where software artifacts are stored.

## 14. What is a Maven plugin?

A component that performs a particular Maven build task.

## 15. What is a build phase?

A stage in the Maven build lifecycle.

## 16. What is a lifecycle?

An ordered sequence of build phases.

## 17. What does POM mean?

Project Object Model.

## 18. What are Maven coordinates used for?

They uniquely identify Maven projects and artifacts.

## 19. What does convention over configuration mean?

Maven uses standard project structures and sensible defaults so developers do not need to configure every detail manually.

## 20. Where does Maven fit in DevOps?

Maven commonly sits in the build stage between source code and the deployable application artifact.
