# Part 11: Packaging Applications, JARs, WARs and Build Artifacts

## Introduction

In the previous parts, you learned how Maven:

* Reads a project from `pom.xml`
* Resolves dependencies
* Compiles Java source code
* Compiles test code
* Runs automated tests
* Stops the build when required tests fail

Our build has reached this point:

```text
Source Code
    |
    v
Compile
    |
    v
Compiled Classes
    |
    v
Test
    |
    v
?
```

The next question is:

What does Maven actually produce?

Most software is not delivered to users as a directory containing hundreds of `.java` source files.

Instead, the build produces something that can be stored, distributed, deployed, installed, published, or consumed by another project.

That output is commonly called a build artifact.

For a Java application, the artifact might be:

```text
veriqta-app-1.0.0.jar
```

For a traditional Java web application, it might be:

```text
veriqta-web-1.0.0.war
```

For a parent or dependency-management Maven project, the important artifact may primarily be its:

```text
pom.xml
```

In this part, we will follow the complete path:

```text
Java Source
    |
    v
Compile
    |
    v
.class Files
    |
    v
Test
    |
    v
Package
    |
    v
Build Artifact
    |
    v
veriqta-app-1.0.0.jar
```

By the end, you should understand not only how to run:

```bash
mvn package
```

but also what Maven packages, where the output goes, how the artifact is named, what is inside it, whether it can be executed, how dependencies affect execution, and how Maven can produce additional artifacts such as sources and Javadoc JARs.

---

# 1. What Is an Artifact?

In Maven, an artifact is a file produced or used as a unit in the build and identified through Maven coordinates.

Common Maven artifacts include:

```text
JAR
WAR
POM
Sources JAR
Javadoc JAR
```

For our project:

```text
veriqta-maven-app
```

Maven may eventually produce:

```text
veriqta-maven-app-1.0.0.jar
```

That JAR is a build artifact.

---

# 2. Why Do We Need Build Artifacts?

Imagine an application contains:

```text
src/main/java/
├── App.java
├── User.java
├── GreetingService.java
├── Server.java
└── ServerService.java
```

After compilation:

```text
target/classes/
├── App.class
├── User.class
├── GreetingService.class
├── Server.class
└── ServerService.class
```

You could theoretically distribute all those files individually.

That quickly becomes inconvenient.

Instead, they can be packaged:

```text
App.class
User.class
GreetingService.class
Server.class
ServerService.class
        |
        v
     Package
        |
        v
veriqta-maven-app-1.0.0.jar
```

One artifact is much easier to:

* Store
* Version
* Copy
* Upload
* Publish
* Download
* Deploy
* Reference from another project
* Promote through environments

---

# 3. Source Code Is Not the Same as a Build Artifact

Keep these concepts separate.

Source code:

```text
src/main/java/com/veriqta/app/App.java
```

Compiled bytecode:

```text
target/classes/com/veriqta/app/App.class
```

Packaged artifact:

```text
target/veriqta-maven-app-1.0.0.jar
```

The transformation is:

```text
.java
 |
 | Java source compilation
 v
.class
 |
 | Packaging
 v
.jar
```

Maven coordinates these steps.

---

# 4. What Does "Packaging" Mean?

Packaging means assembling the appropriate build outputs into the project's distributable artifact format.

For a standard JAR project:

```text
Compiled classes
+
Processed resources
+
Artifact metadata
        |
        v
      JAR
```

For a web application:

```text
Web application content
+
Compiled classes
+
Libraries
+
Web metadata/configuration
        |
        v
       WAR
```

Packaging is therefore not the same thing as compilation.

---

# 5. Compile Versus Package

Compare:

```bash
mvn compile
```

with:

```bash
mvn package
```

`mvn compile` reaches the `compile` phase.

A simplified flow:

```text
Source
    |
    v
Compile
    |
    v
target/classes
```

`mvn package` goes farther:

```text
Source
    |
    v
Compile
    |
    v
Test
    |
    v
Package
    |
    v
Artifact
```

Therefore:

```text
mvn compile
```

does not mean:

```text
Create my final JAR.
```

But:

```text
mvn package
```

normally reaches the phase responsible for creating the project's main packaged artifact.

---

# 6. Maven Packaging Types

Maven supports different packaging types.

Three important beginner packaging values are:

```text
jar
war
pom
```

They are declared in `pom.xml`:

```xml
<packaging>jar</packaging>
```

or:

```xml
<packaging>war</packaging>
```

or:

```xml
<packaging>pom</packaging>
```

The selected packaging helps Maven determine:

* What kind of project this is
* Which default lifecycle bindings apply
* What artifact should normally be produced

---

# 7. JAR Packaging

JAR means:

```text
Java Archive
```

A JAR is an archive format commonly used to package Java classes and resources.

Example:

```text
veriqta-app-1.0.0.jar
```

A JAR may contain:

```text
Compiled .class files
Resources
META-INF metadata
Manifest
```

Depending on how the project is packaged, it may or may not contain dependency classes.

---

# 8. When Is JAR Packaging Used?

JAR packaging is common for:

* Java libraries
* Command-line applications
* Backend applications
* Reusable components
* Framework-based services
* Maven plugins, with specialized packaging/configuration in some cases
* Java modules and utilities

A JAR can represent either:

```text
Reusable library
```

or:

```text
Runnable application
```

Those are not automatically the same thing.

---

# 9. WAR Packaging

WAR commonly means:

```text
Web Application Archive
```

WAR files are associated with Java web applications designed for deployment to a servlet container or compatible application server environment.

Example:

```text
veriqta-web-1.0.0.war
```

Traditional deployment might look like:

```text
Java Web Application
        |
        v
Maven
        |
        v
WAR
        |
        v
Servlet Container / Application Server
```

Examples of environments historically associated with WAR deployment include servlet containers such as Apache Tomcat and application servers supporting the relevant Java web specifications.

---

# 10. JAR Versus WAR

At a beginner level:

| JAR                                                    | WAR                                                                        |
| ------------------------------------------------------ | -------------------------------------------------------------------------- |
| Java Archive                                           | Web Application Archive                                                    |
| Common for libraries and applications                  | Common for Java web applications deployed to a compatible container/server |
| Usually uses `.jar`                                    | Uses `.war`                                                                |
| May be directly executable if configured appropriately | Traditionally deployed to a web container/application server               |
| Packaging value `jar`                                  | Packaging value `war`                                                      |

Modern Java application architectures often use executable JARs, particularly for self-contained services.

WAR packaging still exists and remains relevant where deployment architecture requires it.

---

# 11. POM Packaging

A Maven project can also use:

```xml
<packaging>pom</packaging>
```

This does not mean Maven creates an application called:

```text
something.pom
```

in the same sense as packaging compiled classes into a JAR.

POM packaging is commonly used for projects whose primary purpose is Maven project organization and metadata.

Examples include:

* Parent projects
* Multi-module aggregators
* Dependency-management projects
* Centralized build configuration

Mental model:

```text
jar
→ package Java classes/resources

war
→ package Java web application

pom
→ project/build/dependency organization
```

We will explore multi-module projects later.

---

# 12. Maven's Default Packaging

Suppose your POM contains:

```xml
<project>
    ...
    <groupId>com.veriqta</groupId>
    <artifactId>veriqta-maven-app</artifactId>
    <version>1.0.0</version>
</project>
```

and does not explicitly contain:

```xml
<packaging>...</packaging>
```

Maven's default packaging is:

```text
jar
```

Therefore these are effectively equivalent for this purpose:

```xml
<packaging>jar</packaging>
```

and omitting the packaging element entirely.

For beginners, explicitly declaring it while learning can make the project easier to understand:

```xml
<packaging>jar</packaging>
```

---

# 13. Packaging Affects Lifecycle Bindings

Remember from Part 8 that Maven plugins perform much of Maven's actual work.

Packaging influences which plugin goals Maven binds to lifecycle phases by default.

For a JAR project, Maven has default bindings that ultimately include JAR creation during the `package` phase.

Conceptually:

```text
packaging = jar
       |
       v
Maven selects relevant default lifecycle bindings
       |
       v
package phase
       |
       v
JAR Plugin
       |
       v
.jar artifact
```

For WAR packaging:

```text
packaging = war
       |
       v
package phase
       |
       v
WAR Plugin
       |
       v
.war artifact
```

This is another example of Maven's convention-over-configuration model.

# 14. Our Beginner Project Coordinates

Assume our POM contains:

```xml
<groupId>com.veriqta</groupId>
<artifactId>veriqta-maven-app</artifactId>
<version>1.0.0</version>
<packaging>jar</packaging>
```

The Maven coordinates are:

```text
Group ID:
com.veriqta

Artifact ID:
veriqta-maven-app

Version:
1.0.0

Packaging:
jar
```

These values help determine the identity and default filename of the generated artifact.

# 15. Default Artifact Naming

For a normal JAR project, Maven commonly creates a filename using:

```text
artifactId-version.extension
```

Therefore:

```text
artifactId:
veriqta-maven-app

version:
1.0.0

packaging:
jar
```

produces:

```text
veriqta-maven-app-1.0.0.jar
```

The pattern is:

```text
${artifactId}-${version}.${extension}
```

Conceptually:

```text
veriqta-maven-app
        +
1.0.0
        +
jar
        |
        v
veriqta-maven-app-1.0.0.jar
```

---

# 16. SNAPSHOT Artifact Naming

If your version is:

```xml
<version>1.0.0-SNAPSHOT</version>
```

the locally packaged artifact is typically:

```text
veriqta-maven-app-1.0.0-SNAPSHOT.jar
```

Remember:

```text
SNAPSHOT
```

generally communicates that this version is under active development and may be replaced by newer builds with the same logical snapshot version.

A release version such as:

```text
1.0.0
```

represents a fixed release identity.

# 17. The `target` Directory

Maven normally places generated build output under:

```text
target/
```

After:

```bash
mvn package
```

you may see:

```text
target/
├── classes/
├── generated-sources/
├── generated-test-sources/
├── maven-archiver/
├── maven-status/
├── surefire-reports/
├── test-classes/
└── veriqta-maven-app-1.0.0.jar
```

The exact contents depend on:

* Maven version
* Plugins
* Project configuration
* Tests
* Generated sources
* Packaging type

Do not assume every project has exactly the same `target` contents.

---

# 18. What Is Generated and What Is Source?

This distinction is important.

You create and maintain:

```text
pom.xml
src/
```

Maven creates:

```text
target/
```

Conceptually:

```text
Project input
├── pom.xml
└── src/

        |
        v

      Maven

        |
        v

Generated output
└── target/
```

This is why `target/` is normally excluded from Git repositories.

It can usually be recreated from the source project.

---

# 19. Why `target/` Should Usually Not Be Committed to Git

Suppose every developer commits:

```text
target/classes
target/test-classes
target/*.jar
target/surefire-reports
```

The repository becomes filled with generated output.

Instead:

```text
Git Repository
     |
     +-- Source code
     +-- Tests
     +-- pom.xml
     +-- Required project files

CI/CD
     |
     v
mvn package
     |
     v
target/
```

The build system should reproduce the build output.

A typical `.gitignore` entry is:

```gitignore
target/
```

# 20. Running `mvn package`

From the project root:

```bash
mvn package
```

Remember that `package` is a lifecycle phase.

It is not simply:

```text
Run JAR Plugin immediately.
```

Maven executes earlier phases first.

Simplified:

```text
validate
    |
    v
compile
    |
    v
test-compile
    |
    v
test
    |
    v
package
```

Therefore:

```bash
mvn package
```

normally compiles the application and runs unit tests before creating the package.

# 24. What Is Inside a JAR?

A JAR is an archive.

You should not treat it as a mysterious binary blob.

Suppose the project contains:

```text
src/main/java/com/veriqta/app/App.java

src/main/java/com/veriqta/app/model/User.java

src/main/java/com/veriqta/app/service/GreetingService.java
```

The JAR may contain:

```text
META-INF/
META-INF/MANIFEST.MF
com/
com/veriqta/
com/veriqta/app/
com/veriqta/app/App.class
com/veriqta/app/model/User.class
com/veriqta/app/service/GreetingService.class
```

Resources from:

```text
src/main/resources
```

can also appear in the artifact.

# 25. Inspect JAR Contents

The JDK provides the `jar` command.

To list a JAR's contents:

```bash
jar tf target/veriqta-maven-app-1.0.0.jar
```

Break down:

```text
jar
→ JDK archive tool

t
→ list the archive's table of contents

f
→ use the archive file supplied as an argument
```

Then:

```text
target/veriqta-maven-app-1.0.0.jar
```

is the JAR we want to inspect.

```text
               |
```

# 27. Why `.java` Files Are Usually Not in the Main JAR

Your main JAR normally contains compiled application classes, not the original Java source files.

The normal transformation is:

```text
App.java
    |
    v
Compiler
    |
    v
App.class
    |
    v
JAR
```

If source code needs to be distributed separately, Maven can create a sources JAR.

We will cover that later in this part.

Suppose:

```text
src/main/resources/application.properties
```

contains:

```properties
app.name=VERIQTA Maven App
```

During the build, resources are typically copied into:

```text
target/classes/application.properties
```

Then the JAR may contain:

```text
application.properties
```

So:

```text
src/main/resources
        |
        v
process-resources
        |
        v
target/classes
        |
        v
package
        |
        v
JAR
```

# 29. The `META-INF` Directory

JAR files commonly contain:

```text
META-INF/
```

This directory stores metadata associated with the archive.

One particularly important file is:

```text
META-INF/MANIFEST.MF
```

This is the JAR manifest.

---

# 30. What Is a Manifest?

A manifest is a metadata file stored inside a JAR.

Its path is:

```text
META-INF/MANIFEST.MF
```

It can contain information about the archive.

Depending on how the JAR is built, entries may describe things such as:

* Manifest version
* Main class
* Class path
* Implementation information
* Build-related metadata

Not every JAR contains every possible manifest entry.

---

# 31. Inspect the Manifest

One simple method is:

```bash
unzip -p target/veriqta-maven-app-1.0.0.jar META-INF/MANIFEST.MF
```

On systems where `unzip` is available.

Alternatively, create a temporary directory and use the JDK `jar` tool:

```bash
mkdir /tmp/veriqta-jar-inspect
cd /tmp/veriqta-jar-inspect
jar xf /full/path/to/veriqta-maven-app/target/veriqta-maven-app-1.0.0.jar META-INF/MANIFEST.MF
cat META-INF/MANIFEST.MF
```

Be careful when extracting archives into working directories because files may be created or overwritten.

Use a disposable inspection directory.

---

# 32. Executable Versus Non-Executable JARs

This is one of the most important concepts in this part.

A JAR existing does not automatically mean this will work:

```bash
java -jar target/veriqta-maven-app-1.0.0.jar
```

A normal library JAR and an executable application JAR are both JAR files, but their intended use differs.

---

# 33. Non-Executable JAR

A normal JAR might contain:

```text
App.class
User.class
GreetingService.class
```

but not tell the Java launcher which class should start the application.

Running:

```bash
java -jar application.jar
```

requires the archive to provide the appropriate executable metadata, normally including a main class.

Without it, Java may report an error similar to:

```text
no main manifest attribute
```

The exact message depends on the situation and Java version.

---

# 34. What Is a Main Class?

A Java application normally starts from a class containing:

```java
public static void main(String[] args)
```

Example:

```java
package com.veriqta.app;

public class App {

    public static void main(String[] args) {
        System.out.println("VERIQTA Maven application started.");
    }
}
```

This method is the application entry point.

Conceptually:

```text
java
 |
 v
Main Class
 |
 v
main()
 |
 v
Application starts
```

---

# 35. Why the JAR Needs to Know the Main Class

Suppose the JAR contains:

```text
App.class
AdminTool.class
MigrationTool.class
ReportTool.class
```

Several classes could theoretically contain:

```java
public static void main(String[] args)
```

If you execute:

```bash
java -jar application.jar
```

Java needs to know which class is the application's entry point.

That information can be declared in the manifest:

```text
Main-Class: com.veriqta.app.App
```

---

# 36. Configure a Main Class With Maven

For a basic JAR, the Maven JAR Plugin can be configured to add a main-class entry to the manifest.

Conceptually:

```xml
<build>
    <plugins>

        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-jar-plugin</artifactId>
            <version>YOUR_CONTROLLED_VERSION</version>

            <configuration>
                <archive>
                    <manifest>
                        <mainClass>com.veriqta.app.App</mainClass>
                    </manifest>
                </archive>
            </configuration>
        </plugin>

    </plugins>
</build>
```

Use a deliberately selected compatible plugin version in the real project.

The important section is:

```xml
<mainClass>com.veriqta.app.App</mainClass>
```

---

# 37. What Is the Fully Qualified Main Class Name?

This:

```text
com.veriqta.app.App
```

is the fully qualified class name.

It combines:

```text
Package:
com.veriqta.app

Class:
App
```

to produce:

```text
com.veriqta.app.App
```

Do not write:

```text
src/main/java/com/veriqta/app/App.java
```

as the Java main-class name.

That is a filesystem path.

The main class uses Java package notation.

---

# 38. Build the Executable JAR

After configuring the manifest:

```bash
mvn clean package
```

Then inspect:

```bash
unzip -p target/veriqta-maven-app-1.0.0.jar META-INF/MANIFEST.MF
```

You should expect a main-class entry corresponding to your configuration.

Then try:

```bash
java -jar target/veriqta-maven-app-1.0.0.jar
```

# 39. The Dependency Problem

This is where beginners often encounter confusion.

Suppose your application uses an external library.

Your POM contains:

```xml
<dependency>
    ...
</dependency>
```

Maven downloads that dependency.

Compilation succeeds.

Tests succeed.

Maven creates:

```text
veriqta-maven-app-1.0.0.jar
```

You then run:

```bash
java -jar target/veriqta-maven-app-1.0.0.jar
```

and the application fails because a dependency class cannot be found.

Why?

Because a standard project JAR does not automatically mean:

```text
My classes
+
Every dependency
```

---

# 40. Standard JAR and Dependencies

A normal application JAR may look like:

```text
veriqta-maven-app-1.0.0.jar
|
+-- App.class
+-- User.class
+-- GreetingService.class
+-- application.properties
+-- META-INF/
```

Meanwhile, dependencies may exist separately:

```text
~/.m2/repository/...
```

or elsewhere in the runtime environment.

Therefore:

```text
Compile-time dependency resolution
```

does not automatically mean:

```text
Dependency classes are physically copied inside my JAR.
```

---

# 41. Compile Classpath Versus Runtime Classpath

During compilation, Maven constructs a classpath containing the required dependencies.

Conceptually:

```text
Application source
       |
       +---- dependency A
       +---- dependency B
       |
       v
Compilation
```

But when you later execute the application, Java also needs the necessary runtime classes.

Conceptually:

```text
Application JAR
       |
       +---- runtime dependency A
       +---- runtime dependency B
       |
       v
Java Runtime
```

If a required runtime class is unavailable, execution fails.

---

# 42. Common Missing Dependency Error

You may encounter errors such as:

```text
NoClassDefFoundError
```

or:

```text
ClassNotFoundException
```

These can indicate that a required class was not available at runtime.

Do not immediately assume:

```text
Maven failed to download the dependency.
```

Ask:

```text
Did compilation work?

Is the dependency present in Maven's dependency tree?

Is it required at runtime?

Is it included in or available to the runtime classpath?

Did I build a thin JAR but try to use it as a self-contained executable?
```

---

# 43. Thin JAR Concept

A normal application JAR that does not bundle all of its external dependencies is sometimes described as a thin JAR.

Conceptually:

```text
Thin JAR
|
+-- Application classes
+-- Application resources
+-- Metadata

Dependencies
|
+-- Separate
```

Runtime:

```text
Thin JAR
    +
External dependencies
    |
    v
Application
```

---

# 44. Fat JAR

A fat JAR generally packages application classes together with required dependency classes into one larger archive.

Conceptually:

```text
Application classes
        +
Dependency A classes
        +
Dependency B classes
        +
Resources
        |
        v
     Fat JAR
```

Example:

```text
veriqta-app-all.jar
```

The exact filename depends on configuration.

---

# 45. Uber JAR

The term:

```text
uber JAR
```

is commonly used similarly to:

```text
fat JAR
```

Both generally refer to creating a JAR containing the application plus its dependencies.

Terminology can vary between tools and teams.

The important mental model is:

```text
Normal/thin JAR
→ dependencies may remain external

Fat/Uber JAR
→ dependencies are bundled into a larger distributable archive
```

---

# 46. Why Fat JARs Exist

Suppose deployment requires:

```text
Copy one file to server
→ run application
```

Managing:

```text
application.jar
dependency-a.jar
dependency-b.jar
dependency-c.jar
dependency-d.jar
...
```

can be inconvenient.

A self-contained archive can simplify distribution:

```text
veriqta-app.jar
        |
        v
java -jar veriqta-app.jar
```

provided the artifact has been built correctly for that execution model.

---

# 47. Fat JAR Trade-Offs

Fat JARs are convenient, but they are not simply "better JARs."

Consider:

* Larger artifact size
* Duplicate files from dependencies
* Manifest handling
* Signature files
* Resource conflicts
* Dependency metadata
* Licensing requirements
* Class/resource collision behavior

Building a reliable fat JAR therefore requires appropriate tooling rather than blindly copying JAR files together.

---

# 48. Maven Shade Plugin Concept

One common Maven tool for building an uber/fat JAR is the Maven Shade Plugin.

Conceptually:

```text
Application JAR
      +
Dependency JAR A
      +
Dependency JAR B
      |
      v
Maven Shade Plugin
      |
      v
Shaded/Uber JAR
```

The plugin can also handle transformations required when combining archive contents.

We do not need to master every Shade Plugin option here.

The important concept is:

```text
Standard Maven JAR packaging
≠
Automatically bundle every dependency
```

---

# 49. Executable Does Not Necessarily Mean Fat

Do not confuse:

```text
Executable JAR
```

with:

```text
Fat JAR
```

An executable JAR means Java knows how to launch the application, normally through executable manifest information or framework-specific packaging.

A fat JAR means dependency content is bundled.

Therefore you can have:

```text
Executable thin JAR
```

that still requires external dependencies.

Or:

```text
Executable fat JAR
```

that includes dependencies.

These are separate properties.

---

# 50. JAR Mental Model

Think in two questions.

Question 1:

```text
Can Java identify how to start this JAR?
```

This concerns executability and the main class.

Question 2:

```text
Are all required runtime classes available?
```

This concerns dependencies and runtime classpath.

A JAR can solve Question 1 while still failing Question 2.

---

# 51. Running a Non-Fat Application With a Classpath

Java can run applications with an explicit classpath.

Conceptually:

```bash
java -cp "application.jar:dependency-a.jar:dependency-b.jar" com.veriqta.app.App
```

On Windows, the classpath separator is normally:

```text
;
```

rather than the Unix/macOS:

```text
:
```

The exact runtime command depends on the application and dependency layout.

The lesson is:

```text
Java runtime must be able to find required classes.
```

---

# 52. Do Not Use `.m2` as a Deployment Strategy

A beginner may think:

```text
My dependency is in ~/.m2/repository, so production will find it.
```

Not automatically.

The Maven local repository exists primarily for Maven's artifact resolution and build workflow.

Your deployment strategy should deliberately provide runtime dependencies.

For example:

```text
Fat JAR
```

or:

```text
Application distribution containing dependency JARs
```

or:

```text
Framework-specific executable packaging
```

or:

```text
Application server/container-provided dependencies
```

depending on the application architecture.

A WAR can contain a structure conceptually similar to:

```text

│   ├── lib/
```

# 55. `WEB-INF/classes`


```text

```

Modern Java web frameworks and servlet specifications may reduce or remove the need for extensive XML deployment descriptors through annotations and programmatic configuration.

The important beginner concept is that WAR packaging has a web-application-specific structure.

# 59. Modern JAR Deployment Model

# 64. What Is a Classifier?

A classifier distinguishes additional artifacts built from the same project coordinates.

Suppose the main artifact is:

```text
veriqta-maven-app-1.0.0.jar
```

The project might also produce:

```text
veriqta-maven-app-1.0.0-sources.jar
```

and:

```text
veriqta-maven-app-1.0.0-javadoc.jar
```

Here:

```text
sources
```

and:

```text
javadoc
```

act as classifiers.

# 65. Classifier Filename Pattern

A classified artifact commonly follows:

```text
artifactId-version-classifier.extension
```

Example:

```text
veriqta-maven-app-1.0.0-sources.jar
```

Breakdown:

```text
artifactId
veriqta-maven-app

version
1.0.0

classifier
sources

extension

```

---

# 66. Why Classifiers Exist

Without classifiers, these would all try to have essentially the same identity:

```text

Sources JAR
Javadoc JAR
```

Classifiers let Maven distinguish variants related to the same project/version.

Conceptually:

```text
com.veriqta
|
+-- veriqta-maven-app
    |
    +-- 1.0.0
        |
        +-- main JAR
        +-- sources JAR
        +-- javadoc JAR
```

# 67. Sources JAR

Example:


Compare:

```text

→ .class files
```

# 68. Why Sources JARs Are Useful

When another developer uses a library in an IDE, the IDE can often attach source artifacts.

This allows the developer to:

* Read library source
* Navigate into implementation
* Understand APIs
* Debug more effectively

For published Java libraries, sources JARs are particularly useful.

```text
      |
```

When attached properly, the sources archive can travel with the project's other artifacts during later installation or deployment.

# 75. Checksums

A checksum is a value calculated from file contents.

Conceptually:

```text
Artifact bytes
     |
     v
Hash algorithm
     |
     v
Checksum
```

Example conceptual files associated with repository artifacts might include checksum metadata for an artifact.

The exact algorithms, files, and repository behavior depend on the repository and publishing process.

---

# 76. Why Checksums Are Useful

Suppose an artifact is downloaded.

You want to detect whether its bytes match the expected artifact.

Conceptually:

```text
Original artifact
      |
      v
Expected checksum

Downloaded artifact
      |
      v
Calculated checksum

Compare
   |
 +-+-+
 |   |
 v   v
Same Different
 |   |
 v   v
Match Investigate
```

Checksums help detect accidental corruption and content mismatches.

They are not, by themselves, a complete replacement for cryptographic signing, trusted provenance, access control, or other supply-chain security measures.

---

# 77. Generate a Local SHA-256 Checksum on macOS or Linux

After building:

```bash
mvn clean package
```

you can calculate SHA-256 locally.

On many Linux systems:

```bash
sha256sum target/veriqta-maven-app-1.0.0.jar
```

On macOS:

```bash
shasum -a 256 target/veriqta-maven-app-1.0.0.jar
```

This is not Maven packaging the checksum automatically.

You are calculating it separately to understand artifact identity and integrity.

---

# 78. Why a One-Byte Change Matters

Hash functions are designed so that changing file contents changes the resulting digest.

Conceptually:

```text
Artifact A
→ SHA-256
→ checksum A

Artifact B
one byte different
→ SHA-256
→ checksum B
```

The checksums should differ.

This is useful when comparing build outputs.

---

# 79. Checksums Do Not Tell You Whether Software Is Safe

Suppose malware has a SHA-256 checksum.

The checksum can confirm:

```text
This is the same malware file I hashed earlier.
```

It cannot tell you:

```text
This software is trustworthy.
```

Integrity and trust are different questions.

Remember:

```text
Checksum
→ content integrity/identity evidence

Signature/provenance/trust controls
→ stronger questions about origin and authorization
```

---

# 80. Reproducible Builds

A reproducible build aims for the same source and controlled build inputs to produce equivalent, ideally byte-for-byte identical, artifacts.

Conceptually:

```text
Same source
+
Same build configuration
+
Same controlled inputs
        |
        v
Build A
        |
        v
artifact.jar

Same source
+
Same build configuration
+
Same controlled inputs
        |
        v
Build B
        |
        v
artifact.jar
```

Ideally:

```text
SHA-256 A
=
SHA-256 B
```

---

# 81. Why Builds May Not Be Reproducible Automatically

Build artifacts can accidentally include variable information such as:

* File timestamps
* Archive entry ordering
* Build timestamps
* Environment-specific metadata
* Different plugin versions
* Different dependency versions
* Different JDK versions
* Generated content
* Operating-system-dependent output

Therefore:

```text
Same Git commit
```

does not automatically guarantee:

```text
Byte-for-byte identical artifact
```

unless the build is designed and controlled for reproducibility.

---

# 82. Why Reproducible Artifacts Matter

Reproducibility can help with:

* Supply-chain assurance
* Build verification
* Release confidence
* Investigating artifact differences
* Comparing CI outputs
* Determining whether unexpected build inputs changed

For DevOps engineers, this connects build engineering with software supply-chain security.

---

# 83. Build Environment Is Part of the Artifact Story

Suppose:

```text
Developer Laptop
Java 21
Maven X
Plugin A version X
```

and:

```text
CI Runner
Java 17
Different Maven
Plugin A version Y
```

Even with the same source code, output may differ or one build may fail.

A reliable build should control important inputs such as:

```text
JDK version
Maven version where required
Plugin versions
Dependency versions
Build configuration
Locale/time-related behavior where relevant
```

---

# 84. Pin Plugin Versions

Avoid relying unnecessarily on whatever plugin version happens to be resolved through changing defaults.

Prefer explicit control for important plugins:

```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-jar-plugin</artifactId>
    <version>CONTROLLED_VERSION</version>
</plugin>
```

This improves build predictability.

The same principle applies to dependencies.

---

# 85. Avoid Dynamic Dependency Versions for Reliable Releases

A build that says, conceptually:

```text
Give me whatever version happens to be newest
```

is harder to reproduce than:

```text
Use this specific tested version
```

A release build should have deliberate dependency resolution.

The artifact should be traceable back to known inputs.

---

# 86. Reproducible Archive Timestamps

Archive timestamps are a classic reproducibility problem.

Imagine:

```text
Build Monday
→ App.class timestamp Monday

Build Tuesday
→ App.class timestamp Tuesday
```

Even if the compiled class contents are equivalent, archive metadata may cause the final JAR bytes to differ.

Modern Maven tooling provides mechanisms that can help normalize archive timestamps when properly configured.

The exact configuration depends on Maven/plugin versions and project requirements.

The beginner lesson is:

```text
Reproducibility includes metadata, not just source code.
```

---

# 87. Artifact Versioning

Suppose you build:

```text
veriqta-maven-app-1.0.0.jar
```

Then make a breaking change.

Publishing another unrelated binary under exactly the same immutable release identity creates ambiguity.

A better release process gives meaningful versions:

```text
1.0.0
1.0.1
1.1.0
2.0.0
```

The exact versioning policy depends on the project.

The important Maven principle is:

```text
Artifact identity includes version.
```

---

# 88. Never Manually Rename Artifacts Without Understanding the Consequences

Suppose Maven produces:

```text
veriqta-maven-app-1.0.0.jar
```

You manually rename it:

```text
production-final-new.jar
```

The file can still be a valid JAR.

But you have disconnected the filename from Maven's normal coordinate-based naming model.

In automated environments, prefer controlled build configuration and artifact metadata rather than arbitrary manual renaming.

---

# 89. Customizing the Final Artifact Name

Maven can configure the build's final name:

```xml
<build>
    <finalName>veriqta-app</finalName>
</build>
```

Then the output may become:

```text
target/veriqta-app.jar
```

instead of:

```text
target/veriqta-maven-app-1.0.0.jar
```

This can be useful in some deployment workflows.

However, understand the trade-off.

The filename no longer visibly carries the project version.

---

# 90. Versioned Versus Stable Deployment Filenames

Versioned artifact:

```text
veriqta-app-1.4.2.jar
```

Advantages include easier human identification and coexistence of versions.

Stable deployment filename:

```text
veriqta-app.jar
```

can simplify some scripts.

A deployment system may instead maintain:

```text
Artifact metadata:
version = 1.4.2
```

while using a standardized runtime filename.

There is no universal rule that every deployment must use one naming style.

What matters is traceability.

---

# 91. Artifact Traceability

For a production artifact, engineers should ideally be able to answer:

```text
Which application is this?

Which version is this?

Which source revision produced it?

Which build produced it?

Which dependencies were used?

Which tests ran?

Did they pass?

Where was the artifact published?

Which environment received it?
```

This becomes increasingly important in CI/CD and production systems.

---

# 92. Build Once, Promote the Same Artifact

A strong deployment principle is:

```text
Build once
→ test artifact
→ publish artifact
→ promote same artifact
```

rather than:

```text
Build for development
→ rebuild for testing
→ rebuild for staging
→ rebuild again for production
```

Why?

Every rebuild can theoretically introduce different inputs or output.

A stronger model is:

```text
Git Commit
    |
    v
CI Build
    |
    v
Artifact A
    |
    v
Tests
    |
    v
Artifact Repository
    |
    +--------+
    |        |
    v        v
Staging  Production
```

The same tested artifact moves forward.

---

# 93. Do Not Modify an Artifact After It Has Been Verified

Suppose:

```text
Artifact A
→ tests pass
```

Then someone unpacks it, modifies a configuration file inside it, and repackages it.

You now have:

```text
Artifact B
```

Artifact B is not byte-for-byte the artifact that passed those tests.

Prefer externalized environment configuration when appropriate rather than manually editing released binaries.

# 94. Maven Package Versus Install

Remember:

```bash
mvn package
```

creates the packaged artifact in:

```text
target/
```

But:

```bash
mvn install
```

continues farther through the lifecycle.

Conceptually:

```text
package
    |
    v
Create artifact
    |
    v
verify
    |
    v
install
    |
    v
Place artifact into local Maven repository
```

So:

```text

≠

```

---

# 95. Maven Package Versus Deploy

Likewise:

```bash
mvn deploy
```

goes farther.

Conceptually:

```text
Source
    |
    v
Compile
    |
    v
Test
    |
    v
Package
    |
    v
Verify
    |
    v
Install
    |
    v
Deploy
```

At the Maven lifecycle level, `deploy` is about publishing artifacts to a configured remote repository.

It does not automatically mean:

```text
Deploy my application to Kubernetes.
```

This distinction is critical for DevOps beginners.

# 96. Two Meanings of "Deploy"

In Maven:

```text

```

generally means publishing the project artifact to a remote Maven repository.

In DevOps conversations:


```text

```

Do not confuse them.

# 98. Why Not Store Every Release JAR in Git?

Git is primarily designed for source/version-control workflows.

* Repository policies

