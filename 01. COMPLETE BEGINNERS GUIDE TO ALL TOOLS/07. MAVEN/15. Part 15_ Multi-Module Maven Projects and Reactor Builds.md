# Part 15: Multi-Module Maven Projects and Reactor Builds

## Introduction

Until now, most of the Maven projects you have built have been relatively simple:

```text
veriqta-app
├── pom.xml
└── src
    ├── main
    └── test
```

That model is useful for learning Maven, but real applications can become much larger.

Imagine a platform containing:

* Shared utility code
* Domain or business logic
* Application services
* Web/API code
* Tests
* Configuration
* Multiple deployable components

Putting everything into one source tree can eventually become difficult to understand and maintain.

One solution is to divide the project into Maven modules.

Instead of:

```text
One Maven Project
        |
        v
Everything
```

you can build:

```text
veriqta-platform
│
├── common-library
├── application-core
├── application-service
└── application-web
```

Each module is its own Maven project with its own:

```text
pom.xml
```

but the modules can participate in one larger Maven build.

The complete architecture for this part will be:

```text
veriqta-platform
│
├── pom.xml
│
├── common-library
│   ├── pom.xml
│   └── src
│
├── application-core
│   ├── pom.xml
│   └── src
│
├── application-service
│   ├── pom.xml
│   └── src
│
└── application-web
    ├── pom.xml
    └── src
```

The dependency flow will be:

```text
common-library
      |
      v
application-core
      |
      v
application-service
      |
      v
application-web
```

And Maven will build the entire system using one command:

```bash
mvn clean verify
```

The key concept that makes this possible is the:

```text
Maven Reactor
```

By the end of this part, you should understand how Maven discovers modules, determines their build order, resolves dependencies between modules, performs partial builds, resumes failed builds, and coordinates an entire multi-module application.

---

# 1. What Is a Maven Module?

A Maven module is a Maven project that participates as part of a larger multi-module build.

A module normally has its own:

```text
pom.xml
```

and may also have its own:

```text
src/main/java
src/main/resources
src/test/java
src/test/resources
```

For example:

```text
common-library/
├── pom.xml
└── src/
    ├── main/
    │   └── java/
    └── test/
        └── java/
```

This means:

```text
common-library
```

is itself a Maven project.

It has its own:

* Coordinates
* Dependencies
* Packaging
* Source code
* Tests
* Build configuration
* Generated artifact

But it can also belong to a larger project.

---

# 2. Project Versus Module

A module is still a Maven project.

The word:

```text
module
```

describes its relationship to a larger build.

For example:

```text
application-core
```

can be:

```text
A Maven project
```

and simultaneously:

```text
A module of veriqta-platform
```

Think:

```text
Maven Project
     |
     +---- can exist independently
     |
     +---- can participate as a module
          in a multi-module build
```

---

# 3. What Is a Multi-Module Maven Project?

A multi-module Maven project contains multiple Maven projects that Maven can build together.

Example:

```text
veriqta-platform
│
├── pom.xml
│
├── common-library
│   └── pom.xml
│
├── application-core
│   └── pom.xml
│
├── application-service
│   └── pom.xml
│
└── application-web
    └── pom.xml
```

The root POM identifies the modules.

Conceptually:

```text
Root Maven Project
        |
        +---- Module A
        +---- Module B
        +---- Module C
        +---- Module D
```

Maven can then construct one coordinated build.

---

# 4. Why Applications Are Split Into Modules

Suppose everything is placed into one project:

```text
veriqta-platform
└── src/main/java
    ├── utilities
    ├── domain
    ├── services
    ├── web
    ├── database
    ├── integrations
    └── security
```

This may work.

A project does not need multiple modules simply because it has many packages.

But as the system grows, separate modules can provide useful boundaries.

For example:

```text
common-library
→ shared reusable code

application-core
→ domain and core application logic

application-service
→ application/service orchestration

application-web
→ HTTP/API boundary
```

The project structure now communicates architecture.

---

# 5. Modules Create Build Boundaries

Java packages create code organization.

Maven modules create stronger build-level boundaries.

For example:

```text
application-web
```

can depend on:

```text
application-service
```

while:

```text
application-core
```

does not need to depend on:

```text
application-web
```

This can help maintain architectural direction.

Instead of:

```text
Everything can easily reference everything
```

you can design:

```text
Web
 |
 v
Service
 |
 v
Core
 |
 v
Common
```

The dependencies themselves help describe the architecture.

---

# 6. Reasons to Use Modules

Modules can help with:

* Separation of concerns
* Reusable libraries
* Dependency boundaries
* Independent testing
* Clearer architecture
* Different packaging requirements
* Build organization
* Team ownership
* Reducing unnecessary dependencies
* Controlling which layers can reference other layers
* Separating deployable and non-deployable components

However, modules are not automatically better.

Too many modules can make a project unnecessarily complicated.

---

# 7. Do Not Create a Module for Every Package

A common beginner mistake is:

```text
users
→ module

orders
→ module

strings
→ module

exceptions
→ module

constants
→ module

helpers
→ module
```

This can create excessive build complexity.

Ask:

```text
Does this component need a meaningful build boundary?
```

A module should usually have a clear architectural reason to exist.

# 9. The Root Project

At the top:

```text
veriqta-platform/
└── pom.xml
```

This POM will perform two roles in our lab:

```text
Parent
+
Aggregator
```

These roles are related, but they are not the same.

You learned this distinction in Part 14.

Now we will use both roles together.

---

# 10. Parent Project

A parent project provides inherited Maven configuration.

For example:

```text
veriqta-platform
        |
        +---- Java version
        +---- encoding
        +---- dependency management
        +---- plugin management
        |
        v
Child modules
```

A module can declare:

```xml
<parent>
    <groupId>com.veriqta</groupId>
    <artifactId>veriqta-platform</artifactId>
    <version>1.0.0-SNAPSHOT</version>
</parent>
```

That creates an inheritance relationship.

---

# 11. Aggregator Project

An aggregator identifies projects that should participate in a reactor build.

It uses:

```xml
<modules>
```

For example:

```xml
<modules>
    <module>common-library</module>
    <module>application-core</module>
    <module>application-service</module>
    <module>application-web</module>
</modules>
```

This tells Maven:

```text
These projects belong to this aggregated build.
```

---

# 12. Parent Versus Aggregator Again

Remember:

```text
Parent
→ inheritance
```

while:

```text
Aggregator
→ build grouping
```

The parent answers:

```text
Where does this project inherit Maven configuration from?
```

The aggregator answers:

```text
Which Maven projects should participate in this reactor build?
```

These are different questions.

---

# 13. One POM Can Be Both

Our root:

```text
veriqta-platform/pom.xml
```

will act as both.

Conceptually:

```text
                   veriqta-platform
                          |
             +------------+------------+
             |                         |
             v                         v
          Parent                   Aggregator
             |                         |
             v                         v
    shared configuration       module discovery
             |                         |
             +------------+------------+
                          |
                          v
                       Modules
```

This is common in multi-module projects.

# 14. Packaging Type `pom`

The root project will use:

```xml
<packaging>pom</packaging>
```

Why?

Because the root is primarily coordinating Maven projects and configuration.

It is not itself the application JAR.

For example:

```text
veriqta-platform
→ pom packaging

common-library
→ jar packaging

application-core
→ jar packaging

application-service
→ jar packaging

application-web
→ jar packaging
```

The root coordinates.

The modules produce application artifacts.

# 16. The `<modules>` Element

Add:

```xml
<modules>
    <module>common-library</module>
    <module>application-core</module>
    <module>application-service</module>
    <module>application-web</module>
</modules>
```

Each `<module>` identifies the path to another Maven project relative to the aggregator POM.

Conceptually:

```text
veriqta-platform/pom.xml
        |
        +---- common-library/pom.xml
        +---- application-core/pom.xml
        +---- application-service/pom.xml
        +---- application-web/pom.xml
```

---

# 17. `<module>` Contains a Path

This is important.

When you write:

```xml
<module>common-library</module>
```

you are identifying the module directory relative to the aggregator.

Maven expects to find a Maven project there.

Usually:

```text
common-library/
└── pom.xml
```

The value is not simply an artifact ID lookup.

It represents a module path.

```text
directory:
```

# 20. Modules Can Inherit the Root Parent

The `common-library` POM can begin:

```xml
<parent>
    <groupId>com.veriqta</groupId>
    <artifactId>veriqta-platform</artifactId>
    <version>1.0.0-SNAPSHOT</version>
</parent>

<artifactId>common-library</artifactId>
```

Likewise:

```text
application-core
application-service
application-web
```

can use the same parent.

This gives:

```text
                   veriqta-platform
                          |
              parent inheritance
                          |
        +-----------------+-----------------+
        |                 |                 |
        v                 v                 v
     common            core             service
                                            |
                                            v
                                           web
```

But remember that inheritance and dependency relationships are separate.

---

# 21. Parent Relationship Is Not a Java Dependency

This is critical.

If:

```text
application-core
```

uses:

```xml
<parent>
    ...
    <artifactId>veriqta-platform</artifactId>
</parent>
```

that does not mean Java code in `application-core` can use classes from some other module.

Parent relationships provide Maven configuration.

Java/module dependencies are declared under:

```xml
<dependencies>
```

Do not confuse:

```text
Maven inheritance
```

with:

```text
Java artifact dependency
```

---

# 22. Three Relationships You Must Keep Separate

In a multi-module project, there may be three different relationships.

### Relationship 1: Inheritance

```text
Root Parent
    |
    v
Child Module
```

Configured using:

```xml
<parent>
```

### Relationship 2: Aggregation

```text
Aggregator
    |
    +---- Module A
    +---- Module B
```

Configured using:

```xml
<modules>
```

### Relationship 3: Dependency

```text
Module B
    |
    v
Module A
```

Configured using:

```xml
<dependencies>
```

These relationships are not interchangeable.

# 24. What Is Aggregation?

Aggregation is Maven's mechanism for collecting multiple projects into one build.

The aggregator says:

```text
Build these projects together.
```

Using:

```xml
<modules>
```

For example:

```xml
<modules>
    <module>common-library</module>
    <module>application-core</module>
</modules>
```

Maven loads those projects into a build session.

That build session is handled by the:

```text
Maven Reactor
```

---

# 25. What Is the Maven Reactor?

The Maven Reactor is Maven's mechanism for collecting, ordering, and building multiple projects in one build session.

Think:

```text
Aggregator POM
       |
       v
Discover modules
       |
       v
Read module POMs
       |
       v
Understand relationships
       |
       v
Calculate build order
       |
       v
Build projects
```

That coordinated mechanism is the reactor.

---

# 26. Why the Reactor Exists

Imagine manually building:

```text
common-library
application-core
application-service
application-web
```

You might have to run:

```text
cd common-library
mvn install

cd ../application-core
mvn install

cd ../application-service
mvn install

cd ../application-web
mvn package
```

This is cumbersome.

It also requires you to know the correct order.

The reactor can coordinate this.

From the root:

```bash
mvn clean verify
```

Maven determines the reactor projects and builds them in an appropriate order.

```text
Root POM
   |
   v
<modules>
   |
   v
Maven Reactor
   |
   +---- read project models
   +---- identify dependencies
   +---- determine order
   +---- execute lifecycle
   |
   v
Complete multi-module build
```

# 28. Reactor Build Order

Suppose:

```text
application-core
depends on
common-library
```

and:

```text
application-service
depends on
application-core
```

and:

```text
application-web
depends on
application-service
```

Then the natural build order is:

```text
1. common-library
2. application-core
3. application-service
4. application-web
```

because downstream modules need upstream artifacts.

---

# 29. Build Order Is Not Just the `<modules>` Order

Beginners often assume Maven simply builds modules exactly in the order written:

```xml
<modules>
    ...
</modules>
```

That is not the correct mental model.

The reactor sorts projects according to relevant project relationships.

Dependencies are especially important.

For example, even if modules were listed poorly, Maven can recognize:

```text
application-web
depends on application-service
```

and must ensure the dependency project is built first when both are part of the reactor.

Think:

```text
Module declaration
→ tells Maven what participates

Reactor sorting
→ determines appropriate build order
```

---

# 30. Reactor Sorting Relationships

Maven's reactor ordering can be influenced by project relationships such as:

* Project dependencies
* Plugin relationships
* Plugin dependencies
* Build extensions
* Module declaration order where no stronger ordering relationship exists

For beginners, the most important rule is:

```text
If Module B depends on Module A,
Module A must be available before B can be built.
```

---

# 31. Inter-Module Dependencies

Suppose:

```text
application-core
```

needs Java classes from:

```text
common-library
```

Then `application-core/pom.xml` declares:

```xml
<dependencies>

    <dependency>
        <groupId>com.veriqta</groupId>
        <artifactId>common-library</artifactId>
        <version>${project.version}</version>
    </dependency>

</dependencies>
```

Now there is an artifact dependency:

```text
application-core
        |
        v
common-library
```

---

# 32. Dependency Direction

When we draw:

```text
common-library
      |
      v
application-core
```

we may be describing architectural flow from lower layer to higher layer.

But Maven dependency statements are clearer when phrased explicitly:

```text
application-core
depends on
common-library
```

For troubleshooting, think from consumer to provider:

```text
Consumer
    |
    | depends on
    v
Provider
```

So:

```text
application-web
        |
        v
application-service
        |
        v
application-core
        |
        v
common-library
```

means each upper module consumes the module below it.

---

# 33. Why Inter-Module Dependencies Matter to the Reactor

Maven reads:

```xml
<dependency>
    <groupId>com.veriqta</groupId>
    <artifactId>common-library</artifactId>
    <version>1.0.0-SNAPSHOT</version>
</dependency>
```

It also sees that:

```text
common-library
```

is part of the current reactor.

Therefore Maven can connect:

```text
Dependency coordinates
```

to:

```text
Reactor project coordinates
```

and order the build accordingly.

---

# 34. Reactor Dependency Resolution

This is one of the most useful features of a multi-module build.

Suppose:

```text
application-core
```

needs:

```text
common-library
```

and both are being built in the same reactor.

Maven can use the reactor project as part of the current build.

You do not necessarily need to perform:

```bash
cd common-library
mvn install
```

before building from the root.

Instead:

```bash
mvn clean verify
```

can build both in the correct reactor order.

---

# 35. Reactor Versus Local Repository

Remember the local repository:

```text
~/.m2/repository
```

In independent builds, Maven often resolves internal artifacts from:

```text
local repository
or
remote repository
```

But in a reactor build, Maven knows about participating projects.

Conceptually:

```text
application-core needs common-library
                |
                v
Is matching project in reactor?
                |
               yes
                |
                v
Use reactor project during coordinated build
```

This is why multi-module builds can work before internal artifacts have been separately installed into `.m2`.

---

# 36. Matching Coordinates Matter

Suppose `common-library` has:

```text
com.veriqta:common-library:1.0.0-SNAPSHOT
```

but `application-core` requests:

```text
com.veriqta:common-library:2.0.0
```

These are not the same coordinates.

The fact that a directory named:

```text
common-library
```

exists does not make Maven ignore coordinates.

Inter-module dependencies still follow Maven artifact identity rules.

---

# 37. Managing Internal Module Versions

Because all modules in our lab use:

```text
1.0.0-SNAPSHOT
```

we could define internal dependencies using:

```xml
<version>${project.version}</version>
```

For example:

```xml
<dependency>
    <groupId>com.veriqta</groupId>
    <artifactId>common-library</artifactId>
    <version>${project.version}</version>
</dependency>
```

This can reduce repeated literal versions in a project where modules intentionally share a release version.

---

# 38. Be Careful With Version Expressions

Do not blindly use:

```xml
${project.version}
```

for every dependency in every Maven architecture.

It makes sense when the dependency is intentionally aligned with the consuming project's version.

In our single-version multi-module lab:

```text
Parent = 1.0.0-SNAPSHOT
Modules = 1.0.0-SNAPSHOT
```

it is appropriate.

In systems where modules have independent versions, dependency versions need different management.

# 48. Transitive Dependencies Between Modules

Because:

```text
application-service
depends on application-core
```

and:

```text
application-core
depends on common-library
```

`common-library` may be available transitively to `application-service`, depending on scope and other dependency rules.

But do not use transitivity as an excuse for poor dependency declarations.

If a module directly uses classes from another module, it is usually clearer to declare that dependency directly.

This makes the module's real requirements explicit.

---

# 49. Direct Dependency Principle

Suppose `application-service` directly imports:

```java
import com.veriqta.common.PlatformInfo;
```

even though it already receives `common-library` transitively through `application-core`.

A stronger design is usually:

```xml
<dependency>
    <groupId>com.veriqta</groupId>
    <artifactId>common-library</artifactId>
    <version>${project.version}</version>
</dependency>
```

because the service now directly uses that module's API.

Mental rule:

```text
If your code directly uses it,
declare it directly.
```

Do not make a module accidentally depend on another module's transitive dependency graph.

# 62. Build Failure Propagation

Suppose:

```text
application-core
```

```text

```

```text
common-library
→ SUCCESS

application-core
→ FAILURE

application-service
→ SKIPPED

application-web
→ SKIPPED
```

# 71. Building One Module

Sometimes you do not want the entire project.

Suppose you only changed:

```text

```

```text

```

`-pl` means:

```text

```

It selects specific reactor projects.

Example:

```bash
mvn -pl application-service test
```

This asks Maven to select that project for the requested build.

---

# 72. Understanding `-pl`

Think:

```text
Full Reactor
├── common-library
├── application-core
├── application-service
└── application-web
```

Command:

```bash
mvn -pl application-service test
```

Selection:

```text
application-service
```

The other projects are not automatically selected merely because they exist.

This leads to an important question:

```text
What if application-service needs application-core?
```

That is where:

```text
-am
```

becomes useful.

---

# 73. `-am`: Also Make Required Projects

`-am` means:

```text
--also-make
```

It tells Maven to also build reactor projects required by the selected project.

Suppose:

```text
application-service
        |
        v
application-core
        |
        v
common-library
```

Run:

```bash
mvn -pl application-service -am test
```

Maven selects:

```text
common-library
application-core
application-service
```

because those upstream projects are required.

---

# 74. `-pl` Plus `-am` Mental Model

```text
Selected:
application-service

Required by it:
application-core
common-library
```

Therefore:

```text
mvn -pl application-service -am test
```

means:

```text
Build application-service
plus the reactor projects it requires.
```

This is extremely useful during development.

---

# 75. Building `application-web` With Required Dependencies

Run:

```bash
mvn -pl application-web -am verify
```

Given our dependency chain:

```text
application-web
        |
        v
application-service
        |
        v
application-core
        |
        v
common-library
```

Maven should include the required upstream projects.

Conceptually:

```text
common-library
→ application-core
→ application-service
→ application-web
```

This effectively builds the application path without requiring unrelated modules if the project later becomes larger.

---

# 76. Why `-am` Matters

Suppose you start with a clean local repository and run:

```bash
mvn -pl application-web package
```

If required internal artifacts are not available and their projects were not selected into the build, dependency resolution may fail.

Using:

```bash
mvn -pl application-web -am package
```

tells Maven:

```text
Also build the reactor projects this selected project needs.
```

This makes the command much more reliable for source builds.

---

# 77. `-amd`: Also Make Dependents

Maven also provides:

```text
-amd
```

meaning:

```text
--also-make-dependents
```

This goes in the opposite direction.

Suppose you select:

```text
application-core
```

Which modules depend on it?

Directly:

```text
application-service
```

and downstream:

```text
application-web
```

So:

```bash
mvn -pl application-core -amd test
```

can select the project and reactor projects that depend on it.

---

# 78. `-am` Versus `-amd`

This distinction is essential.

### `-am`

```text
Selected project
        |
        v
What does it need?
```

Build required upstream projects.

### `-amd`

```text
Selected project
        |
        v
What depends on it?
```

Build downstream dependents.

Remember:

```text
-am
→ dependencies required by selected project

-amd
→ dependents that require selected project
```

Success.

```text

        |

        |
```

# 94. What Is a Reactor Failure?

A reactor failure occurs when one of the projects in the coordinated build cannot complete the requested lifecycle.

Example:

```text
common-library ........ SUCCESS
application-core ...... SUCCESS
application-service ... FAILURE
application-web ....... SKIPPED
```

The important question is:

```text
Why did application-service fail?
```

Not:

```text
Why was application-web skipped?
```

The skip is often a consequence.

---

Maven output can be long.

A useful troubleshooting pattern:

```text

      |
      v

      |
      v
Identify first failed module
      |
      v
Scroll to that module's failure
      |
      v
Find first meaningful compiler/test/plugin error
      |
      v
Fix cause
```

Do not focus only on the final stack trace.

# 98. Resuming Builds

Large reactor builds can take time.

Imagine:

```text
Module 1 → SUCCESS
Module 2 → SUCCESS
Module 3 → SUCCESS
Module 4 → FAILURE
Module 5 → SKIPPED
Module 6 → SKIPPED
```

After fixing Module 4, you may not always want to restart every completed module.

Maven supports:

```text
-rf
```

meaning:

```text
--resume-from
```

# 99. `--resume-from`

Suppose the failure occurred in:

```text
application-service
```

You can use:

```bash
mvn verify -rf :application-service
```

This tells Maven to resume from the selected project in the reactor sequence.

Depending on the build situation and whether earlier required artifacts are available, resuming can avoid rebuilding already completed projects.

# 100. Resume Mental Model

Original:

```text
common-library ........ SUCCESS
application-core ...... SUCCESS
application-service ... FAILURE
application-web ....... SKIPPED
```

Fix the service.

Resume:

```bash
mvn verify -rf :application-service
```

Conceptually:

```text
application-service
        |
        v
application-web
```

rather than automatically repeating every earlier successful project.

---

# 101. Important Resume Limitation

Resuming is not magic.

Suppose you originally ran:

```bash
mvn clean verify
```

Earlier modules were built in the reactor but not installed into `.m2`.

Then you begin a new Maven invocation with:

```bash
mvn verify -rf :application-service
```

The resumed build may still need upstream artifacts to be resolvable.

If they are not available from a repository, the resumed build can fail.

This is an important distinction between:

```text
reactor state from the previous process
```

and:

```text
artifacts available to a new Maven process
```

---

# 102. Why Resume Sometimes Surprises Beginners

They think:

```text
Maven built common-library five minutes ago,
so it must still know it.
```

But a new Maven command starts a new Maven process/build session.

If the required artifact is not:

```text
in the current reactor selection
```

or:

```text
available in a repository
```

Maven may not be able to resolve it.

This is why:

```text
verify
```

and:

```text
install
```

have different implications for later independent builds.

---

# 103. Safer Resume Thinking

Before resuming, ask:

```text
What does the failed module require?

Are those required artifacts:
1. selected into this resumed reactor?
2. installed locally?
3. available remotely?
```

If uncertain, a full:

```bash
mvn clean verify
```

is slower but simpler.

Correctness matters more than saving a few seconds.

---

# 104. `--resume-from` Versus `-pl`

These are different tools.

### `-pl`

Selects projects.

```bash
mvn -pl application-service test
```

### `-rf`

Resumes the reactor from a particular project.

```bash
mvn verify -rf :application-service
```

Think:

```text
-pl
→ What projects should be selected?

-rf
→ Where should reactor execution resume?
```

---

# 105. `-am` and `-rf` Solve Different Problems

`-am` answers:

```text
What upstream projects are required by my selection?
```

`-rf` answers:

```text
Where should this reactor build continue from?
```

Do not treat them as synonyms.

You now have several useful commands.

### Full build

```bash
mvn clean verify
```

### Build selected module

```bash
mvn -pl application-service test
```

### Build selected module plus required upstream projects

```bash
mvn -pl application-service -am verify
```

### Build selected module plus downstream dependents



Each command answers a different build question.

# 107. What Is a Circular Dependency?

A circular dependency occurs when modules depend on each other in a cycle.

Example:

```text
Module A
   |
   v
Module B
   |
   v
Module A
```

Or:

```text
A
|
v
B
|
v
C
|
v
A
```

This creates a dependency cycle.

---

# 108. Why Circular Dependencies Are a Problem

Suppose:

```text
A depends on B
```

Maven needs B before building A.

But:

```text
B depends on A
```

Maven needs A before building B.

Question:

```text
Which should Maven build first?
```

Neither can satisfy the dependency ordering.

Conceptually:

```text
Build A first?
→ needs B

Build B first?
→ needs A
```

The graph has no valid topological build order.

---

# 109. Circular Dependency Example

Suppose:

```text
application-core
depends on
application-service
```

while:

```text
application-service
depends on
application-core
```

Now:

```text
Core
 ↕
Service
```

This usually indicates an architectural problem.

Maven cannot simply guess which direction was intended.

---

# 110. Fixing Circular Dependencies

Do not try to fix a circular dependency by manipulating module order.

If:

```text
A depends on B
and
B depends on A
```

changing:

```xml
<modules>
```

order does not remove the cycle.

The dependency architecture needs to change.

---

# 111. Extracting Shared Abstractions

Suppose:

```text
Module A
```

needs an interface from B, while B needs another type from A.

One possible redesign:

```text
          shared-api
          /        \
         v          v
     Module A    Module B
```

Move the genuinely shared abstraction into a lower-level module.

Now:

```text
A → shared-api
B → shared-api
```

instead of:

```text
A ↔ B
```

This is often a cleaner dependency graph.

---

# 112. Circular Dependencies Are Architectural Signals

A Maven cycle is not merely:

```text
an annoying build error
```

It can indicate:

* Poor separation of concerns
* Layers that know too much about each other
* Shared contracts in the wrong module
* Bidirectional architecture
* Incorrect module boundaries

Treat the cycle as information about the system design.

---

# 113. Sensible Module Boundaries

Good module boundaries usually reflect meaningful responsibilities.

Our example:

```text
common-library
→ broadly reusable low-level code

application-core
→ domain/core application logic

application-service
→ orchestration/use-case layer

application-web
→ application entry/API boundary
```

This gives a clear dependency direction.

---

# 114. Dependency Direction Should Be Understandable

A healthy architecture might look like:

```text
Web
 |
 v
Service
 |
 v
Core
 |
 v
Common
```

A confusing architecture might look like:

```text
Web ─────→ Common
 ↑          |
 |          v
Service ← Core
 |          ↑
 +----------+
```

Not every complex graph is wrong.

But if engineers cannot explain why dependencies point in certain directions, the module design deserves review.

---

# 115. Modules Should Not Be Created Only for Folder Organization

If the only goal is:

```text
I want different folders
```

Java packages may be sufficient.

Maven modules add:

* Separate POMs
* Separate artifacts
* Dependency relationships
* Reactor complexity
* Potential versioning considerations
* Build selection behavior

Use that complexity when it buys something valuable.

---

# 116. Questions for Creating a Module

Before creating a new module, ask:

1. Does this code have a distinct responsibility?

2. Should other parts of the system depend on it independently?

3. Does it need its own artifact?

4. Does it have different dependencies?

5. Does it have different build requirements?

6. Is it reusable?

7. Does separating it enforce a useful architecture boundary?

8. Will the boundary remain understandable?

9. Does it need independent testing?

10. Is the extra Maven complexity justified?

---

# 117. Too Few Modules

Putting everything into one giant module can produce:

```text
One huge classpath
One huge test boundary
Weak architectural separation
Unclear ownership
Unnecessary dependencies everywhere
```

For example, web framework dependencies might become visible to code that should only contain core domain logic.

Modules can prevent this.

---

# 118. Too Many Modules

The opposite extreme can produce:

```text
dozens of tiny POMs
complex dependency graphs
slow cognitive navigation
difficult partial builds
version-management overhead
constant cross-module changes
```

The goal is not:

```text
maximum number of modules
```

The goal is:

```text
useful architectural boundaries
```

# 120. A More Complex Graph

Possible order:

Some projects may not have a dependency relationship between them.

Their relative order may then be determined by other reactor sorting rules.

# 122. Build Order Is Not Architecture Layer Number

Do not think Maven understands:

```text
Layer 1
Layer 2
Layer 3
```

Maven understands project relationships encoded in POMs.

If your intended architecture is:

```text
Web → Service → Core
```

but the POM says:

```text
Core → Web
```

Maven follows the declared dependency graph.

Your architecture must be encoded correctly.

# 124. What `clean` Does Across the Reactor

When:

```bash

```

is executed against the reactor, Maven runs the requested lifecycle work for the selected projects.

For each module, generated build output such as:

```text

```

is cleaned.

Then the default lifecycle proceeds through:

```text
validate

test

```

as appropriate.

Each module receives its own:


directory.

# 128. Dependency Tree From the Reactor

Running:

Each Maven project has its own dependency graph.

# 129. Module-Specific Dependencies

Suppose only:

```text
application-web
```

needs a web framework.

Declare it in:

```text
application-web/pom.xml
```

Do not automatically place it in the root:

```xml
<dependencies>
```

because then children may inherit an actual dependency they do not need.

If you want to centrally control its version, the root can use:

```xml
<dependencyManagement>
```

while only `application-web` declares the dependency.

This connects Part 14 directly to multi-module architecture.

---

# 130. Parent Dependency Management in a Multi-Module Build

Root:

```xml
<dependencyManagement>
    <dependencies>

        <dependency>
            <groupId>example</groupId>
            <artifactId>web-library</artifactId>
            <version>${web.library.version}</version>
        </dependency>

    </dependencies>
</dependencyManagement>
```

Then only:

```text
application-web
```

declares:

```xml
<dependency>
    <groupId>example</groupId>
    <artifactId>web-library</artifactId>
</dependency>
```

Now:

```text
Root
→ manages version

Web
→ chooses dependency
```

This is cleaner.

---

# 131. Plugin Management Across Modules

The root can also define:

```xml
<pluginManagement>
```

for:

* Compiler Plugin
* Surefire Plugin
* Failsafe Plugin
* JAR Plugin
* Other shared plugins

This helps keep module build behavior consistent.

For example:

```text
Root Parent
    |
    +---- Java release
    +---- Compiler Plugin version
    +---- Surefire Plugin version
    |
    +---- common-library
    +---- application-core
    +---- application-service
    +---- application-web
```

# 132. Module-Specific Plugins

Suppose only:

```text
application-web
```

needs a particular packaging plugin.

Do not activate it for every module.

The root can manage its version:

```text
pluginManagement
```

while:

```text
application-web
```

activates it under:

```xml
<build>
    <plugins>
```

Again:

```text
shared policy
```

belongs in the parent.

```text
module-specific behavior
```

belongs in the module.

# 133. Multi-Module Project Versus Microservices

Do not confuse:

```text
Maven module
```

with:

```text
microservice
```

A Maven module is a build/project boundary.

A microservice is an independently deployable service architecture concept.

A single microservice may contain several Maven modules.

For example:

```text
orders-service
├── orders-domain
├── orders-application
├── orders-infrastructure
└── orders-web
```

All four may ultimately contribute to one deployable service.

---

# 134. One Module Can Also Produce a Deployable Component

Alternatively:

```text
application-web
```

could eventually become the deployable application artifact.

Then:

```text
common-library
application-core
application-service
```

are supporting library modules.

Conceptually:

```text
common-library.jar
       |
       v
application-core.jar
       |
       v
application-service.jar
       |
       v
application-web.jar
       |
       v
Deployable application
```

The exact packaging architecture depends on the application.

---

# 135. Multi-Module Does Not Mean Multiple Deployments

This distinction is important.

You can have:

```text
10 Maven modules
```

and:

```text
1 deployable application
```

or:

```text
10 Maven modules
```

and:

```text
several deployable applications
```

Maven module architecture and deployment architecture are related but not identical.

---

# 136. Multi-Module Does Not Automatically Mean Monorepo

A Maven multi-module build commonly exists in one source repository because the aggregator needs access to the module projects.

But the general concepts of:

```text
parent POMs
published artifacts
dependency management
```

can also be used across independent repositories.

Do not confuse:

```text
multi-module reactor
```

with:

```text
all Maven projects in the organization
```

A reactor is the set of projects participating in a particular Maven build session.

---

# 137. What Is the Reactor Exactly?

The reactor is not a permanent repository structure.

It is the set of Maven projects participating in the current multi-project build and the mechanism Maven uses to coordinate them.

For example:

```bash
mvn verify
```

may produce one reactor selection.

Then:

```bash
mvn -pl application-service -am verify
```

produces a smaller selected build.

The source repository did not change.

The selected reactor projects did.

---

# 138. Reactor Is Build-Session Specific

Think:

```text
Repository
→ contains all projects

Maven command
→ selects projects

Reactor
→ coordinates selected multi-project build
```

This helps explain partial builds.

Command:

```bash
mvn clean verify
```

Selection:

```text
veriqta-platform

application-web
```

# 140. Partial Reactor

Command:


Selection conceptually:

```text
veriqta-platform where required for project model/build context

application-service
```

The exact displayed reactor set depends on project selection and Maven behavior, but the important concept is that the requested service and required upstream reactor projects are selected.

# 141. Downstream Reactor Selection

Command:

```bash
mvn -pl application-core -amd verify
```

Selection conceptually includes:

```text

application-web
```

because they are affected by the selected module's downstream dependency relationships.

# 142. `-am` and `-amd` Together

Maven allows project selection options to be combined for particular workflows.

Conceptually, if you select a middle module and ask for both required projects and dependents, you are asking Maven to consider both directions around that selected project.

However, do not create complicated command combinations merely because they are possible.

Choose the simplest command that expresses your build goal.

---

# 143. Build Command Decision Model

Ask:

```text
Do I need everything?
```

Yes:

```bash
mvn clean verify
```

Need one project only:

```bash
mvn -pl module test
```

Need one project plus what it requires:

```bash
mvn -pl module -am verify
```

Changed a shared module and need affected consumers:

```bash
mvn -pl module -amd verify
```

Need to continue after a failure:

```bash
mvn verify -rf :module
```

---

# 144. Build Order Troubleshooting

If Maven builds modules in an unexpected order, investigate:

1. What projects are in `<modules>`?

2. What are their coordinates?

3. Which module depends on which artifact?

4. Are internal dependency versions correct?

5. Are plugin relationships influencing order?

6. Are build extensions involved?

7. Are unrelated projects simply being ordered by module declaration?

Do not try to force order by randomly rearranging `<modules>` until the build works.

The dependency graph should be correct first.

---

# 145. Wrong Dependency Direction

Suppose you intended:

```text
Web
→ Service
→ Core
```

but accidentally put:

```xml
<dependency>
    <groupId>com.veriqta</groupId>
    <artifactId>application-web</artifactId>
</dependency>
```

inside `application-core`.

Now:

```text
Core
→ Web
```

The POM no longer represents your intended architecture.

This can eventually create:

```text
Core ↔ Web
```

cycles.

Dependency direction deserves architectural review.

---

# 146. Acyclic Dependency Graph

A good multi-module dependency graph should generally be:

```text
acyclic
```

meaning there is no path that eventually returns to the starting module.

Good:

```text
A → B → C → D
```

Bad:

```text
A → B → C → A
```

The first can be ordered.

The second contains a cycle.

---

# 147. Topological Ordering Mental Model

You do not need graph-theory expertise to use Maven, but one concept helps.

If dependencies form an acyclic graph, Maven can arrange projects so dependencies appear before consumers.

Example:

```text
D
↑
C
↑
B
↑
A
```

If:

```text
A depends on B
B depends on C
C depends on D
```

build:

```text
D
C
B
A
```

This is essentially the kind of ordering problem the reactor must solve.

---

# 148. Circular Dependency Troubleshooting

If Maven reports a cycle:

```text
A → B → C → A
```

investigate each dependency declaration.

Ask:

```text
Why does A need B?
Why does B need C?
Why does C need A?
```

Then determine:

* Is one dependency unnecessary?
* Is a shared interface in the wrong module?
* Should a common abstraction be extracted?
* Are the module boundaries wrong?
* Should two modules actually be one?

Do not hide the problem.

Fix the architecture.

---

# 149. When Two Modules Should Possibly Be One

Suppose:

```text
Module A
```

and:

```text
Module B
```

always:

* Change together
* Depend heavily on each other
* Cannot be understood independently
* Have no meaningful build boundary
* Constantly create dependency problems

Ask whether separating them provides any real value.

Sometimes the correct solution is not another abstraction.

It may be:

```text
merge the modules
```

Good architecture is not measured by module count.

---

# 150. When a Shared Module Makes Sense

A shared module can make sense when:

```text
Several modules need a stable reusable abstraction
```

For example:

```text
common-library
```

may provide:

* Shared domain primitives
* Stable utility functions
* Common interfaces
* Shared error types

But avoid turning it into:

```text
everything that did not fit anywhere else
```

---

# 151. The "Common" Module Trap

A module named:

```text
common
```

can become dangerous if every team dumps unrelated code into it.

Eventually:

```text
common
├── logging
├── database
├── web
├── security
├── billing
├── email
├── cloud
├── random helpers
└── legacy utilities
```

Now almost every module depends on it.

The result is strong coupling.

Our `common-library` is intentionally small for the learning exercise.

In production, shared modules should have clear ownership and purpose.

# 152. Dependency Scope Still Matters

Inter-module dependencies are ordinary Maven dependencies.

Therefore scopes still apply.

For example:

```xml
<dependency>
    <groupId>com.veriqta</groupId>
    <artifactId>test-support</artifactId>
    <version>${project.version}</version>
    <scope>test</scope>
</dependency>
```

This dependency participates only according to Maven's test-scope rules.

Multi-module architecture does not replace dependency-scope behavior.

---

# 153. Optional Dependencies Still Matter

If one module declares another as:

```xml
<optional>true</optional>
```

Maven's optional dependency semantics still apply.

Again:

```text
Reactor
```

coordinates projects.

It does not replace:

```text
normal Maven dependency semantics.
```

---

# 154. Exclusions Still Matter

Transitive inter-module dependencies can still interact with:

```xml
<exclusions>
```

For example:

```text
application-web
→ application-service
→ third-party library
```

If an exclusion is needed, Maven's ordinary dependency-resolution rules apply.

Always distinguish:

```text
project build ordering
```

from:

```text
dependency graph/classpath resolution
```

They are related, but not identical.

---

# 155. Parent Inheritance Still Matters

Every module can inherit:

```text
Java release
encoding
dependency management
plugin management
build configuration
```

from the root parent.

So the full model is now:

```text
                    Root POM
                    /      \
                   /        \
             Parent          Aggregator
               |                |
               v                v
        Shared config       Reactor modules
               \                /
                \              /
                 v            v
                  Module POMs
                      |
                      v
              Inter-module dependencies
                      |
                      v
                 Reactor ordering
                      |
                      v
                     Build
```

# 156. Root POM Responsibilities

A sensible root parent/aggregator may contain:

```text
Project coordinates
pom packaging
shared properties
dependency management
plugin management
modules
shared build policy
```

It should not automatically contain:

```text
every application dependency
every module-specific plugin
every environment-specific setting
```

Keep responsibilities clear.

# 157. Child Module Responsibilities

A module should define what is specific to itself:

```text
artifactId
module-specific dependencies
module-specific plugins
module-specific resources
module-specific source
module-specific tests
```

The root provides the shared baseline.

The child provides its actual function.

# 164. But Do Not Assume Reactor Build Equals Deployment

The reactor answers:

```text
How should Maven build these projects together?
```

Deployment answers:

```text
Which artifacts are deployed?
Where?
How?
In what environment?
```

For example:

```text
common-library.jar
```

may never be deployed independently.

It may only be a dependency of:

```text
application-web
```

Maven build architecture and deployment architecture must be considered separately.

---

# 165. Parallel Reactor Builds

Maven can support parallel project builds using thread-related command options.

For example, you may encounter:

```bash
mvn -T 1C clean verify
```

where thread configuration can allow reactor work to execute concurrently when possible.

However, parallel builds introduce additional concerns:

* Thread-safe plugins
* Shared resources
* Tests that interfere with each other
* Race conditions
* Log readability
* Build reproducibility

Do not use parallelism simply because it sounds faster.

First make the normal reactor build correct.

---

# 166. Build Correctness Before Build Speed

The correct order of priorities is:

```text
Correct build
      |
      v
Reproducible build
      |
      v
Understandable build
      |
      v
Then improve performance
```

Do not make the build graph harder to understand merely to save a small amount of local build time.

---

# 167. Common Mistake: Every Module Declares Different Java Versions

Root:

```text
Java 21
```

but:

```text
common-library → Java 17
core → Java 21
service → Java 22
web → Java 21
```

Sometimes mixed targets are intentional.

Often they are accidental.

Use parent inheritance to establish a baseline unless there is a real reason to differ.

---

# 168. Common Mistake: Repeating Plugin Versions Everywhere

Bad:

```text
common-library/pom.xml
→ Compiler Plugin version X

core/pom.xml
→ Compiler Plugin version X

service/pom.xml
→ Compiler Plugin version X

web/pom.xml
→ Compiler Plugin version X
```

Better:

```text
Root Parent
→ manage shared plugin version
```

Then modules inherit or activate it as appropriate.

This is exactly why Part 14 came before Part 15.

---

# 169. Common Mistake: Declaring All Dependencies in Root `<dependencies>`

If root contains:

```xml
<dependencies>
```

children may inherit actual dependencies.

This can give:

```text
common-library
```

web dependencies it does not need.

Instead:

```text
Root dependencyManagement
→ manages versions

Individual module dependencies
→ declare actual needs
```

This creates cleaner module classpaths.

---

# 170. Common Mistake: Assuming Aggregation Creates Dependencies

Root:

```xml
<modules>
    <module>common-library</module>
    <module>application-core</module>
</modules>
```

does not mean:

```text
application-core can automatically import classes from common-library.
```

Aggregation only groups projects into the build.

You still need:

```xml
<dependency>
```

in `application-core`.

---

# 171. Common Mistake: Assuming Parent Inheritance Creates Dependencies Between Siblings

Both:

```text
common-library
```

and:

```text
application-core
```

inherit:

```text
veriqta-platform
```

That does not make them dependencies of each other.

Sibling relationship:

```text
             parent
            /      \
           v        v
       common      core
```

does not mean:

```text
core → common
```

You must declare that dependency explicitly.

---

# 172. Common Mistake: Building a Consumer Without Required Projects

Command:

```bash
mvn -pl application-web package
```

but internal dependencies are not installed.

Build fails.

Fix:

```bash
mvn -pl application-web -am package
```

Now Maven also selects required reactor projects.

---

# 173. Common Mistake: Using `-am` When You Mean `-amd`

You changed:

```text
common-library
```

and want to test everything that depends on it.

You run:

```bash
mvn -pl common-library -am test
```

But `common-library` may have no upstream internal dependencies.

You actually wanted:

```bash
mvn -pl common-library -amd test
```

because you care about downstream dependents.

Remember:

```text
-am
→ what selected project needs

-amd
→ what needs selected project
```

---

# 174. Common Mistake: Using `-amd` When You Need Dependencies

You want to build:

```text
application-web
```

and all modules it requires.

You run:

```bash
mvn -pl application-web -amd package
```

But web may have no downstream dependents.

You wanted:

```bash
mvn -pl application-web -am package
```

because you need upstream dependencies.

---

# 175. Common Mistake: Assuming Resume Recreates Previous Reactor State

Original build:

```bash
mvn clean verify
```

fails late.

You start a new command:

```bash
mvn verify -rf :application-web
```

and assume every earlier artifact remains available simply because it succeeded in the previous reactor.

Not necessarily.

If upstream artifacts were not installed and are not part of the resumed selection, Maven may not resolve them.

Understand repository state before relying on resume.

---

# 176. Common Mistake: Solving Cycles by Reordering `<modules>`

Cycle:

```text
A → B
B → A
```

Beginner fix:

```text
Put A first.
```

Still impossible.

Then:

```text
Put B first.
```

Still impossible.

Correct fix:

```text
remove architectural cycle.
```

# 177. Common Mistake: Creating Modules With No Clear Boundary

If every change requires editing:

```text
module-a
module-b
module-c
module-d
```

and the modules cannot function or be understood separately, ask whether the boundaries are useful.

Maven should support the architecture.

The architecture should not exist merely to impress Maven.

---

# 178. Common Mistake: Shared Module Becomes a Dumping Ground

Avoid:

```text
common-library
→ everything reusable
→ everything inconvenient
→ everything nobody owns
```

Instead define its purpose.

For our lab:

```text
common-library
→ small stable shared functionality
```

In a real system, you may choose more precise module names.

---

# 179. Common Mistake: Directly Using Undeclared Transitive Modules

Suppose:

```text
service
→ core
→ common
```

Then service directly imports classes from common but does not declare common.

The code may compile while transitivity remains available.

But the module has a hidden direct requirement.

Better:

```text
service
→ core
service
→ common
```

if it genuinely uses both APIs.

Make dependencies explicit.

---

# 180. Common Mistake: Same Artifact ID Across Modules

Avoid:

```text
module-a
→ artifactId app

module-b
→ artifactId app
```

under the same group and version when they represent different artifacts.

Clear coordinates make reactor output, dependency trees, repositories, and troubleshooting easier.

---

# 181. Common Mistake: Parent Version Mismatch

Root:

```text
veriqta-platform:1.0.0-SNAPSHOT
```

Child:

```xml
<parent>
    ...
    <version>1.0.1-SNAPSHOT</version>
</parent>
```

Now Maven may fail parent resolution.

All parent references must identify the intended parent artifact.

---

# 182. Common Mistake: Internal Dependency Version Mismatch

`common-library`:

```text
1.0.0-SNAPSHOT
```

but core requests:

```text
2.0.0-SNAPSHOT
```

The reactor project does not satisfy the requested coordinates.

Always check:

```text
groupId
artifactId
version
```

when an internal dependency mysteriously fails to resolve.

```text
→ application team
```

This is another reason full reactor verification is valuable.

# 215. Reactor and CI Change Detection

* Releases
* Parent inheritance
* Reactor coordination


* Release coordination
* Compatibility management
* Version upgrades

# 221. Nested Aggregators

Large projects can contain nested module structures.

For example:

```text
veriqta-platform
├── libraries
│   ├── pom.xml
│   ├── common-library
│   └── security-library
│
└── applications
    ├── pom.xml
    ├── application-service
    └── application-web
```

The root may aggregate:

```text
libraries
applications
```

and those aggregators may aggregate their own modules.

This can organize very large projects.

---

# 222. Do Not Add Nested Aggregators Without Need

Nested structures can help large systems.

They can also make navigation harder.

For our architecture:

```text
four modules
```

a flat structure is easier:

```text
veriqta-platform
├── common-library
├── application-core
├── application-service
└── application-web
```

Use hierarchy when scale justifies it.

# 223. Module Path Versus Java Package

Do not confuse:

```text
application-core/
```

with:

```java
package com.veriqta.core;
```

One is:

```text
Maven module filesystem structure
```

The other is:

```text
Java package namespace
```

They often align conceptually but serve different purposes.

---

# 224. Module Artifact Versus Java Package

Likewise:

```text
artifactId = application-core
```

does not mean every Java package must begin:

```text
application.core
```

Artifact coordinates and Java package names are separate namespaces.

Use consistent conventions, but understand the distinction.

# 225. Reactor Debugging Checklist

When a multi-module build fails, check:

1. Did Maven discover the expected modules?

2. Is `<modules>` correct?

3. Are module paths correct?

4. Are module POMs valid?

5. Are parent coordinates correct?

6. Are module coordinates unique?

7. Are internal dependency coordinates correct?

8. Are versions aligned as intended?

9. What is the reactor build order?

10. Which module failed first?

11. Were later modules skipped?

12. Is there a dependency cycle?

13. Are you using `-pl`?

14. Should you also use `-am`?

15. Did you accidentally use `-amd`?

16. Are required artifacts only present in an old `.m2` state?

17. Does `dependency:tree` show the expected graph?

18. Does `help:effective-pom` show the expected inherited configuration?

# 233. Production Build Principle

A multi-module build should be reproducible from a clean environment.

Conceptually:

```text
Fresh CI worker
      |
      v
Checkout repository
      |
      v
Provide required JDK/Maven/settings
      |
      v
mvn clean verify
      |
      v
Successful reactor build
```

It should not depend on:

```text
Some developer installed an internal snapshot last Tuesday.
```

Avoid build assumptions such as:

```text
~/.m2 already contains internal artifact X
```

unless your CI caching strategy deliberately and safely manages that state.

A clean build is a valuable test of project reproducibility.

# 236. Security in Multi-Module Builds

A root parent can affect all modules through:

* Plugins
* Plugin management
* Dependencies
* Dependency management
* Repositories
* Build extensions
* Properties

Therefore root POM changes deserve careful review.

A malicious build plugin introduced at the root can have a much larger blast radius than a module-local change.

---

# 237. Dependency Security Across Modules

Suppose root dependency management upgrades a library due to a vulnerability.

Modules that use the managed dependency can inherit the corrected version.

This is a major advantage of centralized dependency management.

But you still need to verify:

```text
Which modules actually use the dependency?
Did any module override the version?
Did transitive resolution produce the expected result?
```

Use:

```bash
mvn dependency:tree
```

where necessary.

---

# 238. Module Boundaries and Least Dependency

A useful principle is:

```text
Each module should depend only on what it needs.
```

For example:

```text
common-library
```

should not need:

```text
web framework
database driver
HTTP server
```

if it only provides simple shared functionality.

Smaller dependency surfaces can improve:

* Understandability
* Security
* Build isolation
* Testability
* Upgrade control

---

# 239. Dependency Direction as Architecture Enforcement

Suppose your design says:

```text
Core must not know about Web.
```

Then:

```text
application-core/pom.xml
```

should not contain:

```text
application-web
```

as a dependency.

Maven module dependencies can help encode architectural intent.

If someone attempts to import a web class into core without the dependency, compilation fails.

That failure can be useful.

It protects the boundary.

# 259. Final Mental Model

At the beginning of your Maven learning path, the build looked like:

```text
Java Source
    |
    v
Maven
    |
    v
Compile
    |
    v
Test
    |
    v
Package
    |
    v
JAR
```

After learning parent POMs, the model became:

```text
Parent POM
    |
    v
Shared Configuration
    |
    v
Child Project
    |
    v
Maven Build
```

Now the model expands again:

```text
                         veriqta-platform
                                |
                   +------------+------------+
                   |                         |
                   v                         v
                Parent                   Aggregator
                   |                         |
                   v                         v
          Shared Configuration           Modules
                                             |
                                             v
                                       Maven Reactor
                                             |
                           +-----------------+-----------------+
                           |                 |                 |
                           v                 v                 v
                    common-library   application-core   application-service
                           |                 |                 |
                           +--------->-------+--------->-------+
                                                             |
                                                             v
                                                      application-web
```

From the dependency perspective:

```text
application-web
        |
        | depends on
        v
application-service
        |
        | depends on
        v
application-core
        |
        | depends on
        v
common-library
```

From the reactor build perspective:

```text
common-library
        |
        v
application-core
        |
        v
application-service
        |
        v
application-web
```

From the command line:

```text
mvn clean verify
        |
        v
Complete build
```

For a targeted build:

```text
mvn -pl application-web -am verify
        |
        v
application-web
+
everything it requires
```

For downstream impact:

```text
mvn -pl common-library -amd verify
        |
        v
common-library
+
projects that depend on it
```

And after a failure:

```text
mvn verify -rf :application-service
        |
        v
resume from application-service
```

The most important lesson is that a Maven multi-module project is not simply several directories with several POM files.

It is a project graph.

The root aggregator identifies the projects participating in the build.

The parent relationship provides shared configuration.

Dependency declarations describe which artifacts modules require.

The reactor reads those relationships, constructs the multi-project build, determines an appropriate order, and executes Maven lifecycles across the selected projects.

A well-designed multi-module project therefore gives you more than one convenient command.

It gives you an explicit architecture:

```text
Source boundaries
+
Artifact boundaries
+
Dependency boundaries
+
Shared build policy
+
Coordinated testing
+
Reactor build order
```

For the VERIQTA platform built in this part, the final model is:

```text
veriqta-platform
        |
        +---- Parent POM
        |
        +---- Aggregator
        |
        +---- common-library
        |          |
        |          v
        +---- application-core
        |          |
        |          v
        +---- application-service
        |          |
        |          v
        +---- application-web
        |
        v
Maven Reactor
        |
        v
mvn clean verify
        |
        v
Complete verified multi-module build
```

At this point, you are no longer using Maven only to compile a Java program.

You are using Maven to describe and coordinate the structure of an application made from multiple connected artifacts.
