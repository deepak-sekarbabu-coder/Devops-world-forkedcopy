# Project 5: Log Analyzer

Logs are one of the first places engineers go when something breaks.

A service may report:

```text
FAILED
```

A website may return:

```text
500 Internal Server Error
```

An SSH login may fail repeatedly.

A database connection may time out.

A reverse proxy may suddenly receive traffic from one IP address thousands of times.

The operating system may not tell you the full story.

The application may not tell you the full story either.

The evidence is often in the logs.

In this project, we will build:

```text
log-analyzer.sh
```

The script will analyze Linux or application log files and produce a useful summary.

A completed report might look like:

```text
==========================================================================
                          LOG ANALYSIS REPORT
==========================================================================
File:                /var/log/nginx/access.log
Timestamp:           2026-09-11 12:41:10
Lines Analyzed:      48291

----------------------------- SEVERITY -----------------------------------

Errors:              153
Warnings:            48

Most Common Error:
database connection timeout

--------------------------- HTTP TRAFFIC ---------------------------------

HTTP 2xx:            42118
HTTP 3xx:            1847
HTTP 4xx:            4289
HTTP 5xx:            37

HTTP 500 Responses:  37

--------------------------- SOURCE IPS -----------------------------------

Top Source IP:
10.0.1.18

Requests From IP:
1842

---------------------------- SECURITY ------------------------------------

Failed Login Attempts:
23

--------------------------------------------------------------------------
Analysis Status:     ATTENTION REQUIRED
==========================================================================
```

This script will not assume every log has exactly the same format.

Instead, we will build a practical analyzer that works particularly well with:

* Linux authentication logs
* Syslog-style logs
* Application logs
* Nginx access logs
* Apache access logs
* Nginx error logs
* General text logs containing severity keywords

The project will teach you how engineers turn raw text into operational information.

# 1. Project Scenario

Imagine an application team reports:

```text
Users are getting errors from the website.
```

You check Nginx:

```bash
systemctl is-active nginx
```

It returns:

```text
active
```

That tells you Nginx is running.

It does not tell you whether the application is healthy.

You open the access log:

```bash
sudo tail -n 50 /var/log/nginx/access.log
```

You notice several:

```text
500
```

responses.

Then you inspect the application log:

```bash
grep -i "error" /var/log/veriqta-app/application.log
```

You find:

```text
ERROR database connection timeout
ERROR database connection timeout
ERROR database connection timeout
```

Now the incident looks different.

The problem is not that Nginx stopped.

The reverse proxy is running, but requests are failing because the application cannot reach its database.

This is why log analysis matters.

# 5. Important Limitation

Logs are not universally structured.

For example, an Nginx access log and a Java application log may look completely different.

This means a script cannot safely assume:

```text
Field 1 is always IP
Field 9 is always HTTP status
```

for every log file in existence.

Our script will use:

* General pattern matching for severity
* Common access-log assumptions for HTTP analysis
* Common SSH failure patterns for authentication analysis

Later, we will make the script capable of selecting analysis modes.

# 12. Match Whole Severity Words

A naive search for:

```bash
grep -i "error"
```

could match text like:

```text
error_count=0
```

or some unrelated string.

For common text logs, a better pattern is:

```bash
grep -Eiw "ERROR" samples/application.log
```

Options:

```text
-E   extended regular expressions
-i   case insensitive
-w   whole word
```

For this project, we will keep the severity matching understandable rather than trying to build a universal parser.

# 14. Pipelines

A pipeline passes the output of one command into another.

Example:

```bash
grep -i "error" samples/application.log |
sort |
uniq -c
```

This means:

```text
grep
  |
  v
sort
  |
  v
uniq -c
```

The commands cooperate to transform raw log data.

---

# 15. Why `sort` Comes Before `uniq`

Try:

```bash
printf '%s\n' error timeout error timeout error |
uniq -c
```

You may get separate counts because identical lines are not adjacent.

`uniq` only groups neighboring duplicate lines.

So use:

```bash
printf '%s\n' error timeout error timeout error |
sort |
uniq -c
```

Now duplicates are adjacent.

# 16. Find Most Common Errors

Our application log contains timestamps.

If we simply do:

```bash
grep "ERROR" samples/application.log |
sort |
uniq -c
```

the timestamps make each line unique.

We need to remove the variable prefix.

Given:

```text
2026-09-11 12:03:07 ERROR database connection timeout
```

we want:

```text
database connection timeout
```

Use `awk`:

```bash
awk '/ERROR/ {
    $1=""
    $2=""
    $3=""
    sub(/^ +/, "")
    print
}' samples/application.log
```

Output:

```text
database connection timeout
database connection timeout
database connection timeout
failed to publish message to queue
database connection timeout
```

Now:

```bash
awk '/ERROR/ {
    $1=""
    $2=""
    $3=""
    sub(/^ +/, "")
    print
}' samples/application.log |
sort |
uniq -c |
sort -nr
```

Output:

```text
4 database connection timeout
1 failed to publish message to queue
```

---

# 17. Why `sort -nr`

`sort` options:

```text
-n  numeric
-r  reverse
```

So:

```bash
sort -nr
```

places the largest count first.

# 24. Important Parsing Warning

Do not assume `$9` is always the HTTP status in every access log.

Nginx log formats are configurable.

For example, an administrator can define:

```nginx

```

and change the field order.

Your parser must match the actual log format.

For this project, we assume common Nginx or Apache access-log formatting.

```bash
awk '

    status=$9

    if (status >= 200 && status < 300)
        success++
    else if (status >= 300 && status < 400)
        redirect++
    else if (status >= 400 && status < 500)
        client_error++
    else if (status >= 500 && status < 600)
        server_error++

    print "3xx:", redirect+0
    print "4xx:", client_error+0
    print "5xx:", server_error+0
```

# 29. Validate the Input File

Our script will be used like:

```bash
./log-analyzer.sh /var/log/nginx/access.log
```

First check whether an argument exists.

```bash
if [[ $# -lt 1 ]]; then
    printf 'ERROR: Log file required.\n' >&2
    exit 3
fi
```

Then:

```bash
LOG_FILE="$1"
```

Check existence:

```bash
if [[ ! -f "$LOG_FILE" ]]; then
    printf 'ERROR: File does not exist: %s\n' "$LOG_FILE" >&2
    exit 3
fi
```

Check readability:

```bash
if [[ ! -r "$LOG_FILE" ]]; then
    printf 'ERROR: File is not readable: %s\n' "$LOG_FILE" >&2
    exit 3
fi
```

# 31. Log Type Detection

We could require:

```bash
./log-analyzer.sh --type nginx file
```

but we can also attempt basic automatic detection.

For example:

```bash
detect_log_type() {

    if grep -qm1 -E '"(GET|POST|PUT|DELETE|PATCH|HEAD|OPTIONS) .*HTTP/[0-9.]+"' "$LOG_FILE"; then
        LOG_TYPE="http"

    elif grep -qm1 -E 'sshd|Failed password|Accepted publickey' "$LOG_FILE"; then
        LOG_TYPE="auth"

    else
        LOG_TYPE="generic"
    fi
}
```

This is heuristic.

It can be wrong.

That is why production-grade tooling should allow an explicit override.

# 35. Generic Severity Analysis

Create:

```bash
analyze_generic() {

    ERROR_COUNT=$(
        grep -Eic '(^|[^[:alnum:]_])ERROR([^[:alnum:]_]|$)' \
            "$LOG_FILE" || true
    )

    WARNING_COUNT=$(
        grep -Eic '(^|[^[:alnum:]_])WARN(ING)?([^[:alnum:]_]|$)' \
            "$LOG_FILE" || true
    )
}
```

Why:

```bash
|| true
```

Because `grep` returns:

```text
0 if matches found
1 if no matches found
2 if an error occurred
```

With strict Bash behavior, no match can otherwise interfere with script execution.

---

# 36. A Note About `grep -c`

When `grep -c` finds zero matches, it prints:

```text
0
```

but may still return exit code:

```text
1
```

That is not necessarily an operational error.

It means:

```text
No matching lines.
```

Understanding command return codes matters when building reliable Bash programs.

# 37. Find the Most Common Generic Error

This is difficult to solve universally because application log formats differ.

For our sample format:

```text
DATE TIME ERROR message
```

we can remove the first three fields.

Create:

```bash
get_top_error() {

    local result

    result=$(
        awk '
            toupper($3) == "ERROR" {
                $1=""
                $2=""
                $3=""

                sub(/^[[:space:]]+/, "")

                print
            }
        ' "$LOG_FILE" |
        sort |
        uniq -c |
        sort -nr |
        head -n 1
    )

    if [[ -n "$result" ]]; then
        TOP_ERROR_COUNT=$(awk '{print $1}' <<< "$result")

        TOP_ERROR_MESSAGE=$(
            sed -E 's/^[[:space:]]*[0-9]+[[:space:]]+//' <<< "$result"
        )
    else
        TOP_ERROR_COUNT=0
        TOP_ERROR_MESSAGE="None detected"
    fi
}
```

---

# 38. Why This Error Extraction Is Imperfect

Consider:

```text
2026-09-11T12:00:00Z ERROR database timeout
```

versus:

```text
ERROR 2026-09-11 database timeout
```

versus JSON:

```json
{"level":"error","message":"database timeout"}
```

One parser cannot correctly interpret all three formats without additional logic.

That is why mature log systems use structured logs.

---

# 39. Structured Logging

A JSON application log might look like:

```json
{
  "timestamp": "2026-09-11T12:03:07Z",
  "level": "ERROR",
  "service": "veriqta-api",
  "message": "database connection timeout"
}
```

Structured logs are easier for machines to parse reliably.

Tools commonly used include:

* Elasticsearch
* OpenSearch
* Loki
* Splunk
* Datadog
* CloudWatch Logs
* Graylog
* Vector
* Fluent Bit

Bash is useful for local analysis, but structured centralized logging scales much better.

# 44. Security Interpretation

Suppose one IP generates:

```text
250 failed SSH logins
```

That may indicate:

* Credential guessing
* Automated scanning
* Misconfigured automation
* A user using an outdated password
* Bot activity

Do not automatically conclude:

```text
The server is compromised.
```

Failed login attempts mean authentication failed.

You still need to investigate whether any successful login followed.

---

# 45. Search Successful SSH Logins

For OpenSSH logs, inspect:

```bash
grep -E 'Accepted password|Accepted publickey' /var/log/auth.log
```

You can compare source addresses.

For example:

```text
Failed password from 203.0.113.25
Accepted password from 203.0.113.25
```

is more concerning than repeated failures with no successful authentication.

# 46. Regular Expressions

A regular expression describes a pattern.

Examples:

```text
ERROR
```

matches literal ERROR.

```text
ERROR|WARNING
```

matches either.

```text
5[0-9][0-9]
```

matches:

```text
500
501
502
...
599
```

This is useful for HTTP server errors.

---

# 47. Regex for IPv4 Addresses

A simple loose pattern is:

```text
([0-9]{1,3}\.){3}[0-9]{1,3}
```

This will match values that look like IPv4 addresses.

But it does not ensure every octet is <= 255.

For logs we usually prefer extracting known fields rather than building extremely complicated IP regexes.

# 52. Complete Working Script

Replace `log-analyzer.sh` with:

```bash
#!/usr/bin/env bash

set -u
set -o pipefail

# ------------------------------------------------------------------
# Log Analyzer
# ------------------------------------------------------------------
#
# Usage:
#   ./log-analyzer.sh [options] LOG_FILE
#
# Exit codes:
#   0 = OK
#   1 = ATTENTION
#   2 = CRITICAL
#   3 = Script/input error
#
# ------------------------------------------------------------------

LOG_TYPE="auto"
TOP_COUNT=5
OUTPUT_FILE=""

LOG_FILE=""
TIMESTAMP=""
TOTAL_LINES=0

ERROR_COUNT=0
WARNING_COUNT=0

TOP_ERROR_COUNT=0
TOP_ERROR_MESSAGE="None detected"

HTTP_2XX=0
HTTP_3XX=0
HTTP_4XX=0
HTTP_5XX=0
HTTP_500=0

TOP_IP="None"
TOP_IP_COUNT=0

FAILED_LOGINS=0
TOP_FAILED_IP="None"
TOP_FAILED_IP_COUNT=0

OVERALL_STATUS="OK"

ERROR_WARNING=1
ERROR_CRITICAL=100

HTTP_5XX_WARNING=1
HTTP_5XX_CRITICAL=50

FAILED_LOGIN_WARNING=10
FAILED_LOGIN_CRITICAL=100


show_help() {

    cat <<EOF
Usage:
  $0 [options] LOG_FILE

Options:
  --type TYPE     Log type: auto, generic, http, auth
  --top N         Number of ranked results to display
  --output FILE   Write report to a file
  --help          Display this help

Examples:
  $0 application.log

  $0 --type http /var/log/nginx/access.log

  $0 --type auth /var/log/auth.log

  $0 --top 10 /var/log/nginx/access.log

  $0 --output report.txt application.log
EOF
}


is_integer() {
    [[ "$1" =~ ^[0-9]+$ ]]
}


parse_arguments() {

    while [[ $# -gt 0 ]]; do

        case "$1" in

            --type)

                if [[ $# -lt 2 ]]; then
                    printf 'ERROR: --type requires a value.\n' >&2
                    exit 3
                fi

                LOG_TYPE="$2"

                case "$LOG_TYPE" in
                    auto|generic|http|auth)
                        ;;
                    *)
                        printf 'ERROR: Unsupported log type: %s\n' \
                            "$LOG_TYPE" >&2
                        exit 3
                        ;;
                esac

                shift 2
                ;;

            --top)

                if [[ $# -lt 2 ]]; then
                    printf 'ERROR: --top requires a value.\n' >&2
                    exit 3
                fi

                if ! is_integer "$2" ||
                   (( $2 < 1 || $2 > 50 )); then

                    printf 'ERROR: --top must be between 1 and 50.\n' >&2
                    exit 3
                fi

                TOP_COUNT="$2"
                shift 2
                ;;

            --output)

                if [[ $# -lt 2 ]]; then
                    printf 'ERROR: --output requires a filename.\n' >&2
                    exit 3
                fi

                OUTPUT_FILE="$2"
                shift 2
                ;;

            --help|-h)

                show_help
                exit 0
                ;;

            --*)

                printf 'ERROR: Unknown option: %s\n' "$1" >&2
                exit 3
                ;;

            *)

                if [[ -n "$LOG_FILE" ]]; then
                    printf 'ERROR: Only one log file may be analyzed at a time.\n' >&2
                    exit 3
                fi

                LOG_FILE="$1"
                shift
                ;;
        esac

    done
}


validate_input() {

    if [[ -z "$LOG_FILE" ]]; then

        printf 'ERROR: A log file is required.\n\n' >&2
        show_help
        exit 3
    fi

    if [[ ! -f "$LOG_FILE" ]]; then

        printf 'ERROR: File does not exist: %s\n' \
            "$LOG_FILE" >&2

        exit 3
    fi

    if [[ ! -r "$LOG_FILE" ]]; then

        printf 'ERROR: File is not readable: %s\n' \
            "$LOG_FILE" >&2

        exit 3
    fi
}


check_dependencies() {

    local commands=(
        awk
        grep
        sed
        sort
        uniq
        head
        wc
        date
    )

    local cmd
    local missing=0

    for cmd in "${commands[@]}"; do

        if ! command -v "$cmd" >/dev/null 2>&1; then

            printf 'ERROR: Required command not found: %s\n' \
                "$cmd" >&2

            missing=1
        fi

    done

    if (( missing != 0 )); then
        exit 3
    fi
}


detect_log_type() {

    if [[ "$LOG_TYPE" != "auto" ]]; then
        return
    fi

    if grep -qm1 -E \
        '"(GET|POST|PUT|DELETE|PATCH|HEAD|OPTIONS) .*HTTP/[0-9.]+"' \
        "$LOG_FILE"; then

        LOG_TYPE="http"

    elif grep -qm1 -E \
        'sshd|Failed password|Accepted publickey|authentication failure' \
        "$LOG_FILE"; then

        LOG_TYPE="auth"

    else

        LOG_TYPE="generic"

    fi
}


analyze_generic() {

    ERROR_COUNT=$(
        grep -Eic \
            '(^|[^[:alnum:]_])ERROR([^[:alnum:]_]|$)' \
            "$LOG_FILE" || true
    )

    WARNING_COUNT=$(
        grep -Eic \
            '(^|[^[:alnum:]_])WARN(ING)?([^[:alnum:]_]|$)' \
            "$LOG_FILE" || true
    )
}


get_top_error() {

    local result

    result=$(
        awk '
            toupper($3) == "ERROR" {

                $1=""
                $2=""
                $3=""

                sub(/^[[:space:]]+/, "")

                print
            }
        ' "$LOG_FILE" |
        sort |
        uniq -c |
        sort -nr |
        head -n 1
    )

    if [[ -n "$result" ]]; then

        TOP_ERROR_COUNT=$(
            awk '{print $1}' <<< "$result"
        )

        TOP_ERROR_MESSAGE=$(
            sed -E \
                's/^[[:space:]]*[0-9]+[[:space:]]+//' \
                <<< "$result"
        )

    else

        TOP_ERROR_COUNT=0
        TOP_ERROR_MESSAGE="None detected"

    fi
}


analyze_http() {

    HTTP_2XX=$(
        awk '
            $9 ~ /^2[0-9][0-9]$/ {
                count++
            }

            END {
                print count+0
            }
        ' "$LOG_FILE"
    )

    HTTP_3XX=$(
        awk '
            $9 ~ /^3[0-9][0-9]$/ {
                count++
            }

            END {
                print count+0
            }
        ' "$LOG_FILE"
    )

    HTTP_4XX=$(
        awk '
            $9 ~ /^4[0-9][0-9]$/ {
                count++
            }

            END {
                print count+0
            }
        ' "$LOG_FILE"
    )

    HTTP_5XX=$(
        awk '
            $9 ~ /^5[0-9][0-9]$/ {
                count++
            }

            END {
                print count+0
            }
        ' "$LOG_FILE"
    )

    HTTP_500=$(
        awk '
            $9 == 500 {
                count++
            }

            END {
                print count+0
            }
        ' "$LOG_FILE"
    )
}


get_top_ip() {

    local result

    result=$(
        awk '{print $1}' "$LOG_FILE" |
        sort |
        uniq -c |
        sort -nr |
        head -n 1
    )

    if [[ -n "$result" ]]; then

        TOP_IP_COUNT=$(
            awk '{print $1}' <<< "$result"
        )

        TOP_IP=$(
            awk '{print $2}' <<< "$result"
        )

    else

        TOP_IP_COUNT=0
        TOP_IP="None"

    fi
}


analyze_auth() {

    FAILED_LOGINS=$(
        grep -Ec \
            'Failed password|authentication failure|Invalid user' \
            "$LOG_FILE" || true
    )
}


get_top_failed_login_ip() {

    local result

    result=$(
        awk '
            /Failed password/ {

                for (i=1; i<=NF; i++) {

                    if ($i == "from") {
                        print $(i+1)
                    }
                }
            }
        ' "$LOG_FILE" |
        sort |
        uniq -c |
        sort -nr |
        head -n 1
    )

    if [[ -n "$result" ]]; then

        TOP_FAILED_IP_COUNT=$(
            awk '{print $1}' <<< "$result"
        )

        TOP_FAILED_IP=$(
            awk '{print $2}' <<< "$result"
        )

    else

        TOP_FAILED_IP_COUNT=0
        TOP_FAILED_IP="None"

    fi
}


get_metric_status() {

    local value="$1"
    local warning="$2"
    local critical="$3"

    if (( value >= critical )); then

        printf 'CRITICAL'

    elif (( value >= warning )); then

        printf 'ATTENTION'

    else

        printf 'OK'

    fi
}


update_overall_status() {

    local status="$1"

    if [[ "$status" == "CRITICAL" ]]; then

        OVERALL_STATUS="CRITICAL"

    elif [[ "$status" == "ATTENTION" &&
            "$OVERALL_STATUS" == "OK" ]]; then

        OVERALL_STATUS="ATTENTION"

    fi
}


evaluate_status() {

    local status

    status=$(
        get_metric_status \
            "$ERROR_COUNT" \
            "$ERROR_WARNING" \
            "$ERROR_CRITICAL"
    )

    update_overall_status "$status"

    if [[ "$LOG_TYPE" == "http" ]]; then

        status=$(
            get_metric_status \
                "$HTTP_5XX" \
                "$HTTP_5XX_WARNING" \
                "$HTTP_5XX_CRITICAL"
        )

        update_overall_status "$status"
    fi

    if [[ "$LOG_TYPE" == "auth" ]]; then

        status=$(
            get_metric_status \
                "$FAILED_LOGINS" \
                "$FAILED_LOGIN_WARNING" \
                "$FAILED_LOGIN_CRITICAL"
        )

        update_overall_status "$status"
    fi
}


print_header() {

    printf '%s\n' \
        "=========================================================================="

    printf '%s\n' \
        "                          LOG ANALYSIS REPORT"

    printf '%s\n' \
        "=========================================================================="

    printf '%-22s %s\n' \
        "File:" "$LOG_FILE"

    printf '%-22s %s\n' \
        "Detected Type:" "$LOG_TYPE"

    printf '%-22s %s\n' \
        "Timestamp:" "$TIMESTAMP"

    printf '%-22s %s\n' \
        "Lines Analyzed:" "$TOTAL_LINES"
}


print_generic_report() {

    printf '\n%s\n' \
        "----------------------------- SEVERITY -----------------------------------"

    printf '%-22s %s\n' \
        "Errors:" "$ERROR_COUNT"

    printf '%-22s %s\n' \
        "Warnings:" "$WARNING_COUNT"

    printf '\n%-22s %s\n' \
        "Top Error Count:" "$TOP_ERROR_COUNT"

    printf '%-22s %s\n' \
        "Most Common Error:" "$TOP_ERROR_MESSAGE"
}


print_http_report() {

    printf '\n%s\n' \
        "--------------------------- HTTP TRAFFIC ---------------------------------"

    printf '%-22s %s\n' "HTTP 2xx:" "$HTTP_2XX"
    printf '%-22s %s\n' "HTTP 3xx:" "$HTTP_3XX"
    printf '%-22s %s\n' "HTTP 4xx:" "$HTTP_4XX"
    printf '%-22s %s\n' "HTTP 5xx:" "$HTTP_5XX"

    printf '\n%-22s %s\n' \
        "HTTP 500 Responses:" "$HTTP_500"

    printf '\n%s\n' \
        "--------------------------- SOURCE IPS -----------------------------------"

    printf '%-22s %s\n' \
        "Top Source IP:" "$TOP_IP"

    printf '%-22s %s\n' \
        "Requests From IP:" "$TOP_IP_COUNT"

    printf '\nTop %s Source IPs:\n' "$TOP_COUNT"

    awk '{print $1}' "$LOG_FILE" |
        sort |
        uniq -c |
        sort -nr |
        head -n "$TOP_COUNT"
}


print_auth_report() {

    printf '\n%s\n' \
        "---------------------------- SECURITY ------------------------------------"

    printf '%-22s %s\n' \
        "Failed Login Attempts:" "$FAILED_LOGINS"

    printf '%-22s %s\n' \
        "Top Failed Source IP:" "$TOP_FAILED_IP"

    printf '%-22s %s\n' \
        "Attempts From IP:" "$TOP_FAILED_IP_COUNT"
}


print_footer() {

    printf '\n%s\n' \
        "--------------------------------------------------------------------------"

    printf '%-22s %s\n' \
        "Analysis Status:" "$OVERALL_STATUS"

    printf '%s\n' \
        "=========================================================================="
}


generate_report() {

    {
        print_header

        print_generic_report

        case "$LOG_TYPE" in

            http)
                print_http_report
                ;;

            auth)
                print_auth_report
                ;;

            generic)
                ;;

        esac

        print_footer

    } | if [[ -n "$OUTPUT_FILE" ]]; then

            tee "$OUTPUT_FILE"

        else

            cat

        fi
}


return_status() {

    case "$OVERALL_STATUS" in

        OK)
            return 0
            ;;

        ATTENTION)
            return 1
            ;;

        CRITICAL)
            return 2
            ;;

        *)
            return 3
            ;;
    esac
}


main() {

    parse_arguments "$@"

    validate_input

    check_dependencies

    TIMESTAMP=$(date '+%Y-%m-%d %H:%M:%S')

    TOTAL_LINES=$(wc -l < "$LOG_FILE")

    detect_log_type

    analyze_generic

    get_top_error

    case "$LOG_TYPE" in

        http)

            analyze_http
            get_top_ip
            ;;

        auth)

            analyze_auth
            get_top_failed_login_ip
            ;;

        generic)
            ;;

    esac

    evaluate_status

    generate_report

    return_status
}


main "$@"
exit $?
```

# 67. Troubleshooting: HTTP Counts Are Wrong

Suppose:

```text
HTTP 5xx: 0
```

but you can clearly see 500 responses.

Check:

```bash
head /var/log/nginx/access.log
```

Then:

```bash
awk '{print $9}' /var/log/nginx/access.log |
head
```

If `$9` is not the status code, your Nginx log format differs from the format expected by the script.

You need to inspect:

```text
/etc/nginx/nginx.conf
```

and files under:

```text
/etc/nginx/conf.d/
/etc/nginx/sites-enabled/
```

for:

```nginx
log_format
```

Do not change the production logging configuration merely to satisfy the script.

Change the parser to match reality.

# 68. Troubleshooting: Errors Are Not Detected

Suppose your application logs use:

```text
level=ERR
```

instead of:

```text
ERROR
```

Our default search will miss them.

Inspect:

```bash
head -n 50 application.log
```

Then adjust the pattern.

Example:

```bash
grep -Ei 'ERROR|ERR|FATAL' application.log
```

This is why log-analysis scripts must understand the application's logging format.

# 69. Troubleshooting: Binary File Message

Sometimes `grep` may report:

```text
Binary file matches
```

The file may contain non-text bytes.

You can force text processing with:

```bash
grep -a
```

But first verify why the file is being treated as binary.

Do not blindly parse arbitrary files as logs.

# 70. Troubleshooting: Huge Log File

Suppose the log is:

```text
80 GB
```

Running several full-file passes can be expensive.

Our current script runs multiple commands over the file.

For small and medium logs, that is fine.

For very large files, optimize.

Options include:

* Analyze only recent lines
* Analyze a time window
* Use one-pass `awk`
* Use rotated files
* Use centralized log platforms
* Stream data incrementally

# 72. Do Not Copy Sensitive Logs Carelessly

Logs may contain:

* Usernames
* IP addresses
* Session identifiers
* URLs
* Query parameters
* Tokens
* Email addresses
* Internal hostnames
* Stack traces
* Database information
* Personal data

* Public GitHub repositories
* Public chat channels
* Unapproved external tools

without reviewing and sanitizing them.

# 73. Log Injection and Untrusted Content

Remember that log content may come from users.

For example, an HTTP user-agent field may contain arbitrary text.

Never blindly execute log content.

This would be dangerous:

```bash
eval "$LOG_LINE"
```

Never do that.

Logs are data.

Treat them as untrusted input.

# 74. Most Frequent IP Does Not Automatically Mean Attack

Suppose:

```text
10.0.1.18 = 50,000 requests
```

That could be:

* A load balancer
* Reverse proxy
* Monitoring service
* NAT gateway
* Legitimate high-volume client
* Security scanner
* Attacker

You need context.

In proxied environments, the direct source IP may not even be the original client IP.

---

# 75. Reverse Proxy IPs

If traffic reaches Nginx through:

```text
Client
   |
   v
Load Balancer
   |
   v
Nginx
```

the source IP logged by Nginx may be the load balancer.

Applications often use headers such as:

```text
X-Forwarded-For
```

But these headers must be handled carefully because clients may forge them unless trusted proxy configuration is correct.

---

# 76. HTTP 4xx vs HTTP 5xx

These categories mean different things.

## 4xx

Generally represents a client-side request problem.

Examples:

```text
400 Bad Request
401 Unauthorized
403 Forbidden
404 Not Found
429 Too Many Requests
```

## 5xx

Generally represents server-side failures.

Examples:

```text
500 Internal Server Error
502 Bad Gateway
503 Service Unavailable
504 Gateway Timeout
```

During an incident, a sudden increase in 5xx responses is often important.

---

# 77. Understand Common 5xx Errors

## 500

Application or server processing error.

## 502

A proxy could not get a valid response from an upstream service.

For Nginx this often means:

```text
Nginx
   |
   X
   |
Application
```

## 503

Service unavailable.

Possible causes:

* Application overloaded
* Maintenance
* No healthy backends
* Dependency unavailable

## 504

Gateway timeout.

Often means an upstream service took too long to respond.

These codes give direction, not final root cause.

# 97. Production Upgrade: Rate Calculations

Instead of only:

```text

```

```text

```

```text
5xx rate = 0.074%
```

---

# 98. Calculate HTTP 5xx Rate

For example:

```bash
TOTAL_REQUESTS=$(wc -l < access.log)

HTTP_5XX=$(awk '$9 ~ /^5/ {count++} END {print count+0}' access.log)

RATE=$(
    awk \
        -v errors="$HTTP_5XX" \
        -v total="$TOTAL_REQUESTS" \
        'BEGIN {
            if (total > 0)
                printf "%.2f", errors/total*100
            else
                print "0.00"
        }'
)
```

Output:

```text
5xx Rate: 0.07%
```

# 99. Why Rates Matter

```text

```

Server B has more raw errors but a dramatically lower failure rate.

Operational analysis requires context.
