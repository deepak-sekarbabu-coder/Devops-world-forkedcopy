# Project 10: Website Health Checker

A website can fail in several different ways.

It may:

* Stop responding completely
* Resolve to the wrong IP
* Reject the TCP connection
* Take too long to respond
* Return a redirect
* Return `403 Forbidden`
* Return `404 Not Found`
* Return `500 Internal Server Error`
* Return `502 Bad Gateway`
* Return `503 Service Unavailable`
* Return HTTP `200` while the application itself is broken

In this project, we will build:

```text
website-health-checker.sh
```

The script will use:

```bash
curl
```

to monitor website availability.

A successful check might produce:

```text
==========================================================================
                       WEBSITE HEALTH REPORT
==========================================================================

URL:                  https://example.com
HTTP Status:          200
Response Time:        0.24s
Redirects:            0
Final URL:            https://example.com/
Connection:           SUCCESS
Status:               HEALTHY

==========================================================================
```

A failed site might produce:

```text
==========================================================================
                       WEBSITE HEALTH REPORT
==========================================================================

URL:                  https://example.com
HTTP Status:          503
Response Time:        1.82s
Redirects:            0
Connection:           SUCCESS
Status:               CRITICAL

Reason:
Service Unavailable

==========================================================================
```

Or:

```text
URL:                  https://example.com
HTTP Status:          N/A
Response Time:        5.00s
Connection:           FAILED
Status:               CRITICAL

Reason:
Connection timed out
```

The main engineering lesson is:

```text
Website availability is not one check.

It is a chain of DNS, network, TLS, HTTP, and application behavior.
```

# 1. Project Scenario

Imagine the VERIQTA application is available at:

```text
https://veriqta.example
```

A user reports:

```text
The website is down.
```

That statement is not enough to diagnose the problem.

You need to determine:

```text
Does DNS resolve?

Can TCP connect?

Did TLS succeed?

Did the server return HTTP?

Which status code?

Was there a redirect?

How long did it take?

Did we reach the expected application?
```

You could manually run:

```bash
curl -I https://veriqta.example
```

Then:

```bash
curl -w '%{http_code}\n' https://veriqta.example
```

Then:

```bash
curl -w '%{time_total}\n' https://veriqta.example
```

Then inspect redirects.

Instead, we will automate the whole first-level investigation.

# 4. HTTP Basics

When a client requests:

```text
https://example.com
```

the request may conceptually flow through:

```text
Client
  |
  v
DNS
  |
  v
Network
  |
  v
TCP Connection
  |
  v
TLS
  |
  v
HTTP Server
  |
  v
Application
```

A failure at any layer can make the website appear unavailable.

---

# 5. What `curl` Does

`curl` is a command-line tool for transferring data using protocols such as HTTP and HTTPS.

Try:

```bash
curl https://example.com
```

This prints the response body.

For monitoring, we usually do not need to print the full HTML.

Instead, we need metadata.

---

# 6. Check HTTP Headers

Run:

```bash
curl -I https://example.com
```

You may see:

```text
HTTP/2 200
content-type: text/html
content-length: 1256
```

`-I` requests headers.

However, not every application handles HEAD requests exactly like GET requests.

For realistic health checks, we will use normal requests while discarding the body.

---

# 7. Discard Response Body

Use:

```bash
curl \
    -s \
    -o /dev/null \
    https://example.com
```

Here:

```text
-s
Silent mode

-o /dev/null
Discard response body
```

This lets us collect metadata without dumping HTML into the terminal.

---

# 8. Capture HTTP Status

Use:

```bash
curl \
    -s \
    -o /dev/null \
    -w '%{http_code}\n' \
    https://example.com
```

Example:

```text
200
```

The:

```text
-w
```

option means:

```text
write-out
```

It lets `curl` print connection and request information after completing the transfer.

---

# 9. Capture Response Time

Run:

```bash
curl \
    -s \
    -o /dev/null \
    -w '%{time_total}\n' \
    https://example.com
```

Example:

```text
0.241832
```

This means roughly:

```text
0.24 seconds
```

---

# 10. Capture Status and Time Together

Use:

```bash
curl \
    -s \
    -o /dev/null \
    -w '%{http_code} %{time_total}\n' \
    https://example.com
```

Example:

```text
200 0.241832
```

Now we have two useful metrics.

# 11. Useful `curl` Timing Metrics

`curl` can expose several timings.

For example:

```text
time_namelookup
time_connect
time_appconnect
time_starttransfer
time_total
```

These correspond approximately to:

```text
DNS resolution
TCP connection
TLS handshake
time until first response byte
total request time
```

That becomes extremely useful during troubleshooting.

# 12. Detailed Timing Command

Run:

```bash
curl \
    -s \
    -o /dev/null \
    -w 'DNS: %{time_namelookup}\nConnect: %{time_connect}\nTLS: %{time_appconnect}\nTTFB: %{time_starttransfer}\nTotal: %{time_total}\n' \
    https://example.com
```

Example:

```text
DNS: 0.011
Connect: 0.031
TLS: 0.084
TTFB: 0.180
Total: 0.241
```

---

# 13. Why Timing Breakdown Matters

Suppose total response time is:

```text
5.8 seconds
```

That alone does not tell you why.

Scenario A:

```text
DNS:      5.2s
Connect:  5.3s
TTFB:     5.5s
Total:    5.8s
```

The delay begins around DNS.

Scenario B:

```text
DNS:      0.01s
Connect:  0.03s
TLS:      0.08s
TTFB:     5.7s
Total:    5.8s
```

Now the server or upstream application appears slow.

That distinction is operationally useful.

# 24. Redirects Are Not Automatically Failures

A redirect can be expected.

Examples:

```text

example.com -> www.example.com
/login -> identity provider
```

So:

```text
301
302
```

should not automatically mean:

```text
website down
```

Context matters.

Question 1:


# 26. Important HTTP Codes

We will specifically detect:

```text
200
301
302
403
404
500
502
503
```

But we should understand the broader status classes.

---

# 27. HTTP 2xx

Generally:

```text
successful response
```

Examples:

```text
200 OK
201 Created
204 No Content
```

For a normal website health check, `200` is often expected.

---

# 28. HTTP 3xx

Redirects.

Examples:

```text
301 Moved Permanently
302 Found
307 Temporary Redirect
308 Permanent Redirect
```

These are not necessarily errors.

---

# 29. HTTP 403

```text
403 Forbidden
```

The server understood the request but refuses access.

Possible reasons:

* Authentication/authorization
* WAF
* IP restrictions
* CDN policy
* Access-control configuration

The server itself may be perfectly healthy.

---

# 30. HTTP 404

```text
404 Not Found
```

The server responded, but the requested resource is unavailable.

For:

```text
/
```

this may indicate a deployment or routing problem.

For a deliberately nonexistent path, it may be expected.

---

# 31. HTTP 500

```text
500 Internal Server Error
```

Usually means the application or server encountered an unexpected error.

Check application logs.

---

# 32. HTTP 502

```text
502 Bad Gateway
```

Often seen when a proxy cannot get a valid response from its upstream.

Architecture:

```text
Client
  |
  v
Nginx / Load Balancer
  |
  X
  |
Application
```

Possible causes include:

* Application process down
* Wrong upstream port
* Connection refused
* Protocol mismatch
* Upstream crash

---

# 33. HTTP 503

```text
503 Service Unavailable
```

Possible causes:

* Application overloaded
* Maintenance
* Dependency unavailable
* No healthy backends
* Service deliberately unavailable

---

# 34. HTTP 504

Although not specifically required, you should know:

```text
504 Gateway Timeout
```

A gateway or proxy waited too long for an upstream service.

This is very common in production troubleshooting.

---

# 35. `curl` Exit Codes Matter

HTTP status and `curl` execution status are different.

A server can return:

```text
HTTP 500
```

while `curl` itself successfully performed the request.

That means:

```text
curl communication succeeded
application returned server error
```

Conversely:

```text
HTTP code 000
```

often appears when no HTTP response was received.

---

# 36. Test `curl` Exit Code

Run:

```bash
curl \
    -s \
    -o /dev/null \
    https://example.com
```

Then immediately:

```bash
echo $?
```

`0` normally means the transfer succeeded at the `curl` level.

# 37. Common `curl` Failure Codes

Some useful ones include:

```text
5   proxy resolution failure
6   host resolution failure
7   connection failure
28  timeout
35  TLS/SSL connection error
60  certificate verification failure
```

Do not assume these are the only possible codes.

We will classify the most useful ones.

---

# 38. DNS Failure

Try an intentionally invalid lab hostname:

```bash
curl \
    --connect-timeout 3 \
    https://veriqta-host-that-does-not-exist.invalid
```

You may receive:

```text
Could not resolve host
```

The exit code is commonly:

```text
6
```

This is different from HTTP `404`.

There was no HTTP exchange.

---

# 39. Connection Failure

A resolved host may reject the connection.

For example:

```text
Connection refused
```

Common `curl` code:

```text
7
```

Possible causes:

* Service not listening
* Wrong port
* Firewall behavior
* Application down

---

# 40. Timeout

Use:

```text
curl exit code 28
```

to identify timeout conditions.

This may happen during:

* Connection
* TLS
* Response wait
* Data transfer

Timing details help narrow it down.

---

# 41. TLS Failure

HTTPS adds another failure layer.

Possible problems:

* Expired certificate
* Hostname mismatch
* Untrusted CA
* TLS protocol incompatibility
* Broken certificate chain

Never solve production certificate failures by permanently adding:

```bash
-k
```

or:

```bash
--insecure
```

to monitoring.

That disables certificate verification.

---

# 42. Why `--insecure` Is Dangerous

A health check that ignores TLS verification may report:

```text
HEALTHY
```

even though users receive certificate errors.

Certificate validation is part of HTTPS health.

Keep verification enabled.

# 48. Health Policy

We need clear rules.

For this lab:

```text
200-299     HEALTHY

301/302
without following redirects
             REDIRECT

400-499     WARNING

500-599     CRITICAL

Connection failure
             CRITICAL

DNS failure CRITICAL

Timeout     CRITICAL

TLS failure CRITICAL
```

If redirects are followed and the final endpoint returns 200:

```text
HEALTHY
```

but we still report the redirect count.

---

# 49. Response-Time Thresholds

Example defaults:

```text
Warning:   >= 1.0 seconds
Critical:  >= 3.0 seconds
```

These are lab thresholds.

Do not treat them as universal production standards.

A checkout request and a static image may have completely different latency expectations.

---

# 50. Compare Decimal Numbers

Bash arithmetic does not natively handle decimal floating-point values well.

Use `awk`.

Example:

```bash
awk -v value="$RESPONSE_TIME" \
    'BEGIN { exit !(value >= 3.0) }'
```

If the comparison is true:

```text
exit 0
```

This lets Bash use it in:

```bash
if
```

# 51. Complete Working Script

Use:

```bash
#!/usr/bin/env bash

set -u
set -o pipefail

umask 077

# ------------------------------------------------------------------
# Website Health Checker
# ------------------------------------------------------------------
#
# Exit codes:
#   0 = HEALTHY
#   1 = WARNING
#   2 = CRITICAL
#   3 = Input/configuration error
#
# ------------------------------------------------------------------

URL=""

CONNECT_TIMEOUT=5
MAX_TIME=10

WARNING_TIME="1.0"
CRITICAL_TIME="3.0"

FOLLOW_REDIRECTS=true

HTTP_CODE="000"
RESPONSE_TIME="0"
REDIRECT_COUNT="0"
FINAL_URL=""

CURL_STATUS=0
CURL_ERROR=""

DNS_TIME="0"
CONNECT_TIME="0"
TLS_TIME="0"
TTFB_TIME="0"

HEALTH_STATUS="UNKNOWN"
HEALTH_REASON=""

ERROR_FILE=""

SCRIPT_DIR=$(
    cd -- "$(dirname -- "${BASH_SOURCE[0]}")" &&
    pwd
)

readonly SCRIPT_DIR

LOG_DIR="$SCRIPT_DIR/logs"
LOG_FILE="$LOG_DIR/website-health.log"


show_help() {

    cat <<EOF
Usage:
  $0 [options] URL

Options:
  --connect-timeout N   Connection timeout in seconds
                        Default: 5

  --max-time N          Maximum total request time
                        Default: 10

  --warning-time N      Warning response-time threshold
                        Default: 1.0

  --critical-time N     Critical response-time threshold
                        Default: 3.0

  --no-follow           Do not follow HTTP redirects

  --help                Display this help

Examples:
  $0 https://example.com

  $0 \
    --connect-timeout 3 \
    --max-time 8 \
    https://example.com

  $0 \
    --warning-time 0.5 \
    --critical-time 2.0 \
    https://example.com

  $0 \
    --no-follow \
    http://example.com
EOF
}


is_integer() {
    [[ "$1" =~ ^[0-9]+$ ]]
}


is_number() {
    [[ "$1" =~ ^[0-9]+([.][0-9]+)?$ ]]
}


cleanup() {

    if [[ -n "${ERROR_FILE:-}" &&
          -f "$ERROR_FILE" ]]; then

        rm -f -- "$ERROR_FILE"
    fi
}


trap cleanup EXIT


parse_arguments() {

    while [[ $# -gt 0 ]]; do

        case "$1" in

            --connect-timeout)

                [[ $# -ge 2 ]] || {
                    printf 'ERROR: --connect-timeout requires a value.\n' >&2
                    exit 3
                }

                if ! is_integer "$2" || (( $2 < 1 )); then

                    printf 'ERROR: Invalid connection timeout.\n' >&2
                    exit 3
                fi

                CONNECT_TIMEOUT="$2"
                shift 2
                ;;

            --max-time)

                [[ $# -ge 2 ]] || {
                    printf 'ERROR: --max-time requires a value.\n' >&2
                    exit 3
                }

                if ! is_integer "$2" || (( $2 < 1 )); then

                    printf 'ERROR: Invalid maximum request time.\n' >&2
                    exit 3
                fi

                MAX_TIME="$2"
                shift 2
                ;;

            --warning-time)

                [[ $# -ge 2 ]] || {
                    printf 'ERROR: --warning-time requires a value.\n' >&2
                    exit 3
                }

                if ! is_number "$2"; then

                    printf 'ERROR: Invalid warning threshold.\n' >&2
                    exit 3
                fi

                WARNING_TIME="$2"
                shift 2
                ;;

            --critical-time)

                [[ $# -ge 2 ]] || {
                    printf 'ERROR: --critical-time requires a value.\n' >&2
                    exit 3
                }

                if ! is_number "$2"; then

                    printf 'ERROR: Invalid critical threshold.\n' >&2
                    exit 3
                fi

                CRITICAL_TIME="$2"
                shift 2
                ;;

            --no-follow)

                FOLLOW_REDIRECTS=false
                shift
                ;;

            --help|-h)

                show_help
                exit 0
                ;;

            --*)

                printf 'ERROR: Unknown option: %s\n' "$1" >&2
                exit 3
                ;;

            *)

                if [[ -n "$URL" ]]; then

                    printf 'ERROR: Only one URL may be supplied.\n' >&2
                    exit 3
                fi

                URL="$1"
                shift
                ;;
        esac

    done
}


check_dependencies() {

    local commands=(
        curl
        awk
        date
        mkdir
        mktemp
        rm
    )

    local cmd

    for cmd in "${commands[@]}"; do

        if ! command -v "$cmd" >/dev/null 2>&1; then

            printf 'ERROR: Required command missing: %s\n' \
                "$cmd" >&2

            exit 3
        fi

    done
}


validate_inputs() {

    if [[ -z "$URL" ]]; then

        printf 'ERROR: URL is required.\n\n' >&2
        show_help
        exit 3
    fi

    if [[ ! "$URL" =~ ^https?:// ]]; then

        printf 'ERROR: URL must begin with http:// or https://\n' >&2
        exit 3
    fi

    if awk \
        -v warning="$WARNING_TIME" \
        -v critical="$CRITICAL_TIME" \
        'BEGIN { exit !(warning >= critical) }'; then

        printf 'ERROR: Warning threshold must be lower than critical threshold.\n' \
            >&2

        exit 3
    fi
}


log_message() {

    local level="$1"
    local message="$2"

    mkdir -p "$LOG_DIR"

    printf '[%s] [%s] %s\n' \
        "$(date '+%Y-%m-%d %H:%M:%S')" \
        "$level" \
        "$message" \
        >> "$LOG_FILE"
}


perform_request() {

    local -a curl_options
    local result

    ERROR_FILE=$(mktemp)

    curl_options=(
        -sS
        -o /dev/null
        --connect-timeout "$CONNECT_TIMEOUT"
        --max-time "$MAX_TIME"
    )

    if [[ "$FOLLOW_REDIRECTS" == true ]]; then
        curl_options+=(-L)
    fi

    result=$(
        curl \
            "${curl_options[@]}" \
            -w '%{http_code}|%{time_total}|%{num_redirects}|%{url_effective}|%{time_namelookup}|%{time_connect}|%{time_appconnect}|%{time_starttransfer}' \
            "$URL" \
            2>"$ERROR_FILE"
    )

    CURL_STATUS=$?

    CURL_ERROR=$(
        cat "$ERROR_FILE"
    )

    IFS='|' read -r \
        HTTP_CODE \
        RESPONSE_TIME \
        REDIRECT_COUNT \
        FINAL_URL \
        DNS_TIME \
        CONNECT_TIME \
        TLS_TIME \
        TTFB_TIME \
        <<< "$result"

    HTTP_CODE="${HTTP_CODE:-000}"
    RESPONSE_TIME="${RESPONSE_TIME:-0}"
    REDIRECT_COUNT="${REDIRECT_COUNT:-0}"
    FINAL_URL="${FINAL_URL:-$URL}"
    DNS_TIME="${DNS_TIME:-0}"
    CONNECT_TIME="${CONNECT_TIME:-0}"
    TLS_TIME="${TLS_TIME:-0}"
    TTFB_TIME="${TTFB_TIME:-0}"
}


classify_curl_failure() {

    case "$CURL_STATUS" in

        5|6)

            HEALTH_STATUS="CRITICAL"
            HEALTH_REASON="DNS resolution failed"
            ;;

        7)

            HEALTH_STATUS="CRITICAL"
            HEALTH_REASON="Connection failed"
            ;;

        28)

            HEALTH_STATUS="CRITICAL"
            HEALTH_REASON="Request timed out"
            ;;

        35)

            HEALTH_STATUS="CRITICAL"
            HEALTH_REASON="TLS/SSL connection failed"
            ;;

        60)

            HEALTH_STATUS="CRITICAL"
            HEALTH_REASON="TLS certificate verification failed"
            ;;

        *)

            HEALTH_STATUS="CRITICAL"

            if [[ -n "$CURL_ERROR" ]]; then
                HEALTH_REASON="$CURL_ERROR"
            else
                HEALTH_REASON="curl failed with exit code $CURL_STATUS"
            fi
            ;;
    esac
}


classify_http_status() {

    if (( CURL_STATUS != 0 )); then
        classify_curl_failure
        return
    fi

    if [[ ! "$HTTP_CODE" =~ ^[0-9]{3}$ ]]; then

        HEALTH_STATUS="CRITICAL"
        HEALTH_REASON="No valid HTTP status received"
        return
    fi

    case "$HTTP_CODE" in

        2??)

            HEALTH_STATUS="HEALTHY"
            HEALTH_REASON="Successful HTTP response"
            ;;

        301|302|307|308)

            if [[ "$FOLLOW_REDIRECTS" == true ]]; then

                HEALTH_STATUS="WARNING"
                HEALTH_REASON="Final response is still a redirect"

            else

                HEALTH_STATUS="WARNING"
                HEALTH_REASON="HTTP redirect detected"
            fi
            ;;

        403)

            HEALTH_STATUS="WARNING"
            HEALTH_REASON="HTTP 403 Forbidden"
            ;;

        404)

            HEALTH_STATUS="WARNING"
            HEALTH_REASON="HTTP 404 Not Found"
            ;;

        4??)

            HEALTH_STATUS="WARNING"
            HEALTH_REASON="HTTP client error"
            ;;

        500)

            HEALTH_STATUS="CRITICAL"
            HEALTH_REASON="HTTP 500 Internal Server Error"
            ;;

        502)

            HEALTH_STATUS="CRITICAL"
            HEALTH_REASON="HTTP 502 Bad Gateway"
            ;;

        503)

            HEALTH_STATUS="CRITICAL"
            HEALTH_REASON="HTTP 503 Service Unavailable"
            ;;

        5??)

            HEALTH_STATUS="CRITICAL"
            HEALTH_REASON="HTTP server error"
            ;;

        *)

            HEALTH_STATUS="WARNING"
            HEALTH_REASON="Unexpected HTTP status"
            ;;
    esac
}


response_time_at_least() {

    local threshold="$1"

    awk \
        -v value="$RESPONSE_TIME" \
        -v threshold="$threshold" \
        'BEGIN {
            exit !(value >= threshold)
        }'
}


evaluate_response_time() {

    if [[ "$HEALTH_STATUS" == "CRITICAL" ]]; then
        return
    fi

    if response_time_at_least "$CRITICAL_TIME"; then

        HEALTH_STATUS="CRITICAL"
        HEALTH_REASON="Response time exceeded critical threshold"
        return
    fi

    if response_time_at_least "$WARNING_TIME"; then

        HEALTH_STATUS="WARNING"

        if [[ "$HEALTH_REASON" == "Successful HTTP response" ]]; then
            HEALTH_REASON="Response time exceeded warning threshold"
        else
            HEALTH_REASON="$HEALTH_REASON; response is slow"
        fi
    fi
}


print_report() {

    printf '%s\n' \
        "=========================================================================="

    printf '%s\n' \
        "                       WEBSITE HEALTH REPORT"

    printf '%s\n' \
        "=========================================================================="

    printf '\n%-22s %s\n' \
        "URL:" "$URL"

    printf '%-22s %s\n' \
        "HTTP Status:" "$HTTP_CODE"

    printf '%-22s %ss\n' \
        "Response Time:" "$RESPONSE_TIME"

    printf '%-22s %s\n' \
        "Redirects:" "$REDIRECT_COUNT"

    printf '%-22s %s\n' \
        "Final URL:" "$FINAL_URL"

    if (( CURL_STATUS == 0 )); then

        printf '%-22s %s\n' \
            "Connection:" "SUCCESS"

    else

        printf '%-22s %s\n' \
            "Connection:" "FAILED"
    fi

    printf '\n%s\n' \
        "---------------------------- TIMINGS -------------------------------------"

    printf '%-22s %ss\n' \
        "DNS:" "$DNS_TIME"

    printf '%-22s %ss\n' \
        "Connect:" "$CONNECT_TIME"

    printf '%-22s %ss\n' \
        "TLS:" "$TLS_TIME"

    printf '%-22s %ss\n' \
        "Time To First Byte:" "$TTFB_TIME"

    printf '%-22s %ss\n' \
        "Total:" "$RESPONSE_TIME"

    printf '\n%s\n' \
        "--------------------------------------------------------------------------"

    printf '%-22s %s\n' \
        "Status:" "$HEALTH_STATUS"

    printf '\nReason:\n%s\n' \
        "$HEALTH_REASON"

    printf '%s\n' \
        "=========================================================================="
}


write_log() {

    log_message \
        "INFO" \
        "url=$URL http=$HTTP_CODE curl_exit=$CURL_STATUS response_time=$RESPONSE_TIME redirects=$REDIRECT_COUNT health=$HEALTH_STATUS"
}


return_status() {

    case "$HEALTH_STATUS" in

        HEALTHY)
            return 0
            ;;

        WARNING)
            return 1
            ;;

        CRITICAL)
            return 2
            ;;

        *)
            return 3
            ;;
    esac
}


main() {

    parse_arguments "$@"

    check_dependencies

    validate_inputs

    perform_request

    classify_http_status

    evaluate_response_time

    print_report

    write_log

    return_status
}


main "$@"
exit $?
```

```text
TTFB:    6.50s
Total:   6.55s
```

the delay occurs after the connection is established.

Possible causes:

* Application processing
* Database
* Upstream API
* Queue
* Server overload

# 125. Production Upgrade: Resolve a Specific Backend

`curl` can test a hostname against a specific IP while preserving the hostname for HTTP/TLS.

Example concept:

```bash
curl \
    --resolve example.com:443:192.0.2.10 \
    https://example.com
```

This is useful for debugging:

```text
DNS
load balancer
specific backend/path
```

Use only against systems you are authorized to test.

# 126. Why `--resolve` Is Powerful

Suppose DNS points:

```text
example.com -> load balancer
```

but you want to test a new endpoint before changing DNS.

`--resolve` lets you connect to a chosen IP while still requesting:

```text
example.com
```

This preserves:

* Host header
* TLS server name

making it useful for controlled troubleshooting.

# 129. Security: Server-Side Request Risks

If this script becomes a web service where arbitrary users can submit URLs, that changes the security model dramatically.

An attacker could attempt to make it request:

```text
localhost
internal services
cloud metadata endpoints
```

This is an SSRF risk.

Our script assumes the operator controls the URLs.

Do not expose unrestricted URL checking to untrusted users.
