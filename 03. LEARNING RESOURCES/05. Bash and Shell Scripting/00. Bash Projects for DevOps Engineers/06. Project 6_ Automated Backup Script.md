# Project 6: Automated Backup Script

A backup is only useful if it is:

* Created successfully
* Stored somewhere safe
* Verifiable
* Restorable
* Retained long enough to matter

A script that runs:

```bash
tar -czf backup.tar.gz /etc /home
```

and exits without checking anything is not a reliable backup system.

In this project, we will build:

```text
automated-backup.sh
```

The script will back up:

```text
/etc
/home
application configuration
```

It will create timestamped archives such as:

```text
backup-2026-09-11-0200.tar.gz
```

Then we will improve it with:

* Retention
* Backup verification
* Logs
* Failure detection
* Checksums
* Optional remote copy
* Restore validation

A successful run might look like:

```text
==========================================================================
                         BACKUP REPORT
==========================================================================
Timestamp:          2026-09-11 02:00:14
Hostname:           backup-server-01
Backup Directory:   /opt/backups

Sources:
  /etc
  /home
  /opt/veriqta/config

Archive:
  backup-2026-09-11-0200.tar.gz

Archive Size:       1.8G
SHA256:             6fa34c...

Archive Check:      PASSED
Checksum Check:     PASSED
Remote Copy:        DISABLED

Retention:          7 days
Old Backups Removed: 2

Overall Status:     SUCCESS
==========================================================================
```

The most important lesson in this project is:

```text
Creating an archive is not the same as proving you have a usable backup.
```

# 1. Project Scenario

Imagine you support a Linux application server.

The server contains:

```text
/etc
```

for operating-system and service configuration.

It also contains:

```text
/home
```

for user-owned files.

Your application keeps configuration under:

```text
/opt/veriqta/config
```

A deployment goes wrong.

A configuration file is overwritten.

Someone asks:

```text
Can we restore yesterday's configuration?
```

If your answer is:

```text

```

that is not good enough.

You need to know:

* Did the archive get created?
* Did `tar` finish successfully?
* Is the archive readable?
* Did the expected files make it inside?
* Has the file changed since creation?
* Are old backups being retained correctly?
* Is there another copy if the server itself is lost?

That is what we will build.

# 4. Why We Use `tar`

`tar` combines many files and directories into one archive.

For example:

```bash
tar -cf backup.tar /etc /home
```

Here:

```text
-c   create archive
-f   specify archive filename
```

Compression can be added with:

```bash
tar -czf backup.tar.gz /etc /home
```

Here:

```text
-z   gzip compression
```

So:

```text
-czf
```

means:

```text
create
gzip compress
write to specified file
```

---

# 5. `tar` and `gzip` Are Different Things

These concepts are often mixed together.

`tar` creates an archive.

`gzip` compresses data.

Conceptually:

```text
/etc
/home
/config
   |
   v
 tar archive
   |
   v
backup.tar
   |
   v
gzip compression
   |
   v
backup.tar.gz
```

`tar -z` lets us perform both operations through one command.

# 14. Why Quoting Paths Matters

Always prefer:

```bash
"$BACKUP_DIR/$BACKUP_NAME"
```

over:

```bash
$BACKUP_DIR/$BACKUP_NAME
```

because paths can contain whitespace or shell-sensitive characters.

Quoting variables is one of the most important shell scripting habits.

---

# 15. Use an Array for Backup Sources

Instead of repeating paths throughout the script:

```bash
SOURCES=(
    "lab/etc"
    "lab/home"
    "lab/application-config"
)
```

Then pass:

```bash
"${SOURCES[@]}"
```

to `tar`.

Example:

```bash
tar -czf "$BACKUP_FILE" "${SOURCES[@]}"
```

This is easier to maintain.

---

# 16. Validate Every Source

A backup script should not silently ignore an expected path.

Create:

```bash
validate_sources() {

    local source

    for source in "${SOURCES[@]}"; do

        if [[ ! -e "$source" ]]; then

            printf 'ERROR: Backup source does not exist: %s\n' \
                "$source" >&2

            exit 3
        fi
    done
}
```

Now a missing source causes a clear failure.

# 18. Validate the Destination

```bash
prepare_backup_directory() {
```

# 20. Create the Backup Function

Use:

```bash
create_backup() {

    printf 'Creating backup...\n'

    if tar -czf "$BACKUP_FILE" "${SOURCES[@]}"; then

        printf 'Backup archive created successfully.\n'

    else

        printf 'ERROR: tar failed while creating backup.\n' >&2

        rm -f "$BACKUP_FILE"

        exit 2
    fi
}
```

Notice:

```bash
if tar ...; then
```

We inspect `tar`'s return code.

That is much safer than running `tar` and assuming success.

# 21. Why We Remove Failed Partial Archives

Imagine `tar` creates:

```text
backup-2026-09-11-0200.tar.gz
```

but fails halfway through.

If that incomplete file remains, someone may later assume it is a valid backup.

So on creation failure:

```bash
rm -f "$BACKUP_FILE"
```

removes the incomplete artifact.

This is one of the few places where deletion is appropriate because the script itself just created the failed file.

# 22. Verify the Archive Structure

Use:

```bash
tar -tzf "$BACKUP_FILE" >/dev/null
```

If the archive is corrupted or unreadable, this should fail.

Create:

```bash
verify_archive() {

    if tar -tzf "$BACKUP_FILE" >/dev/null 2>&1; then

        ARCHIVE_STATUS="PASSED"

    else

        ARCHIVE_STATUS="FAILED"

        printf 'ERROR: Backup archive verification failed.\n' >&2

        exit 2
    fi
}
```

---

# 23. Verification Is Not the Same as Restore Testing

This:

```bash
tar -tzf backup.tar.gz
```

proves the archive can be read.

It does not prove:

* Every required file is present
* Permissions are correct
* The application can start from restored configuration
* Databases are consistent
* A full disaster recovery works

This distinction matters.

---

# 24. Verify Required Files

Suppose the application requires:

```text
lab/application-config/app.env
```

Check:

```bash
tar -tzf "$BACKUP_FILE" |
grep -Fx 'lab/application-config/app.env'
```

You can build a required-file list:

```bash
REQUIRED_BACKUP_ITEMS=(
    "lab/etc/server.conf"
    "lab/application-config/app.env"
)
```

Then validate each one.

---

# 25. Create a Required-File Verification Function

Use:

```bash
verify_required_items() {

    local item

    for item in "${REQUIRED_BACKUP_ITEMS[@]}"; do

        if ! tar -tzf "$BACKUP_FILE" |
             grep -Fxq "$item"; then

            printf 'ERROR: Required item missing from archive: %s\n' \
                "$item" >&2

            exit 2
        fi
    done
}
```

Now the script validates content, not only archive readability.

# 26. Create a SHA-256 Checksum

Run:

```bash
sha256sum backups/test-backup.tar.gz
```

Example:

```text
6fa34c22...  backups/test-backup.tar.gz
```

A checksum provides a fingerprint of the archive.

If even one bit changes, the checksum should change.

---

# 27. Save the Checksum

Run:

```bash
sha256sum "$BACKUP_FILE" > "${BACKUP_FILE}.sha256"
```

Now you have:

```text
backup-2026-09-11-0200.tar.gz
backup-2026-09-11-0200.tar.gz.sha256
```

---

# 28. Verify the Checksum

Run:

```bash
sha256sum -c "${BACKUP_FILE}.sha256"
```

Expected:

```text
backup-2026-09-11-0200.tar.gz: OK
```

Create:

```bash
verify_checksum() {

    if sha256sum -c "${BACKUP_FILE}.sha256" >/dev/null 2>&1; then

        CHECKSUM_STATUS="PASSED"

    else

        CHECKSUM_STATUS="FAILED"

        printf 'ERROR: Checksum validation failed.\n' >&2

        exit 2
    fi
}
```

---

# 29. Why Checksums Matter

A backup may become corrupted due to:

* Storage failure
* Transfer corruption
* File truncation
* Bit errors
* Human mistakes

Checksum verification helps detect unexpected changes.

It does not provide encryption.

It also does not by itself prove the data is logically useful.

# 33. Backup Retention

Suppose you keep backups forever.

Eventually the backup disk fills.

We need retention.

For example:

```text
Keep backups for 7 days.
```

The script can remove older archives.

But retention is destructive behavior, so it must be tightly scoped.

---

# 34. Safe Retention Rule

We only want to delete files matching:

```text
backup-*.tar.gz
backup-*.tar.gz.sha256
```

inside:

```text
BACKUP_DIR
```

We do not want:

```bash
rm -rf "$BACKUP_DIR"/*
```

That is too broad.

---

# 35. Inspect Before Deleting

Test:

```bash
find backups \
    -type f \
    -name 'backup-*.tar.gz' \
    -mtime +7 \
    -print
```

This only prints matches.

Do this before adding deletion.

---

# 36. Add Safe Retention Deletion

Once confirmed:

```bash
find "$BACKUP_DIR" \
    -type f \
    -name 'backup-*.tar.gz' \
    -mtime "+$RETENTION_DAYS" \
    -delete
```

And checksums:

```bash
find "$BACKUP_DIR" \
    -type f \
    -name 'backup-*.tar.gz.sha256' \
    -mtime "+$RETENTION_DAYS" \
    -delete
```

---

# 37. Count Removed Backups

We want the report to say:

```text
Old Backups Removed: 2
```

Safer approach:

```bash
mapfile -t OLD_BACKUPS < <(
    find "$BACKUP_DIR" \
        -type f \
        -name 'backup-*.tar.gz' \
        -mtime "+$RETENTION_DAYS"
)
```

Then:

```bash
REMOVED_BACKUPS=${#OLD_BACKUPS[@]}
```

After validating paths, delete each one deliberately.

---

# 38. Safer Retention Function

Use:

```bash
apply_retention() {

    local old_backup
    local checksum_file

    REMOVED_BACKUPS=0

    mapfile -t old_backups < <(
        find "$BACKUP_DIR" \
            -maxdepth 1 \
            -type f \
            -name 'backup-*.tar.gz' \
            -mtime "+$RETENTION_DAYS"
    )

    for old_backup in "${old_backups[@]}"; do

        checksum_file="${old_backup}.sha256"

        printf 'Removing expired backup: %s\n' \
            "$old_backup"

        rm -- "$old_backup"

        if [[ -f "$checksum_file" ]]; then
            rm -- "$checksum_file"
        fi

        ((REMOVED_BACKUPS+=1))
    done
}
```

Using:

```text
-maxdepth 1
```

limits the search to the backup directory itself.

That reduces accidental scope.

# 40. Remote Backups

A local backup stored on the same server has an obvious weakness.

If the server is destroyed, the backup may disappear with it.

For stronger protection:

```text
Application Server
       |
       v
Local Backup
       |
       v
Remote Storage
```

Possible destinations include:

* Another Linux server
* Object storage
* Backup appliance
* Cloud storage
* Dedicated backup platform

---

# 41. Remote Copy With `scp`

A simple approach:

```bash
scp "$BACKUP_FILE" \
    backup-host:/srv/backups/
```

But production usage requires:

* SSH key management
* Host-key verification
* Network access
* Permissions
* Storage capacity
* Transfer failure handling

# 42. Prefer `rsync` for Many File Transfers

For backups, you may also use:

```bash
rsync -av \
    "$BACKUP_FILE" \
    backup-host:/srv/backups/
```

`rsync` can provide better transfer behavior than simple `scp` in some workflows.

Our script will make remote transfer optional.

# 48. Exclusions

You may not want to back up:

* Cache directories
* Temporary files
* Build artifacts
* Runtime sockets
* Huge files that are recreated automatically

With `tar`:

```bash
tar \
    --exclude='*.tmp' \
    --exclude='cache/' \
    -czf backup.tar.gz \
    source/
```

Be careful.

A bad exclusion can remove something important from the backup.

---

# 49. Absolute Paths and Tar Warnings

If you run:

```bash
tar -czf backup.tar.gz /etc
```

GNU tar may report something like:

```text
Removing leading '/' from member names
```

That is normal.

The archive stores:

```text
etc/...
```

rather than dangerous absolute extraction paths.

This is generally safer for restoration.

# 50. Complete Working Script

Now build the full version.

```bash
#!/usr/bin/env bash

set -u
set -o pipefail

# ------------------------------------------------------------------
# Automated Backup Script
# ------------------------------------------------------------------
#
# Exit codes:
#   0 = SUCCESS
#   1 = SUCCESS with non-critical warning
#   2 = Backup or verification failure
#   3 = Configuration/input error
#
# ------------------------------------------------------------------

BACKUP_DIR="./backups"
LOG_DIR="./logs"

RETENTION_DAYS=7

REMOTE_DESTINATION=""

TIMESTAMP=""
HOSTNAME_VALUE=""

BACKUP_NAME=""
BACKUP_FILE=""
CHECKSUM_FILE=""

ARCHIVE_STATUS="NOT RUN"
CHECKSUM_STATUS="NOT RUN"
REMOTE_STATUS="DISABLED"
OVERALL_STATUS="SUCCESS"

REMOVED_BACKUPS=0

# Lab sources.
# Replace these only after validating the script.
SOURCES=(
    "lab/etc"
    "lab/home"
    "lab/application-config"
)

REQUIRED_BACKUP_ITEMS=(
    "lab/etc/server.conf"
    "lab/application-config/app.env"
)

SCRIPT_DIR=$(
    cd -- "$(dirname -- "${BASH_SOURCE[0]}")" &&
    pwd
)

readonly SCRIPT_DIR

BACKUP_DIR="$SCRIPT_DIR/backups"
LOG_DIR="$SCRIPT_DIR/logs"
LOG_FILE="$LOG_DIR/backup.log"


show_help() {

    cat <<EOF
Usage:
  $0 [options]

Options:
  --backup-dir PATH     Backup destination directory
  --retention DAYS      Number of days to retain backups
  --remote DESTINATION  Optional remote destination
  --help                Display this help

Examples:
  $0

  $0 --retention 14

  $0 --backup-dir /opt/backups

  $0 --remote \
     veriqta-backup@backup-host:/srv/backups/
EOF
}


is_integer() {
    [[ "$1" =~ ^[0-9]+$ ]]
}


parse_arguments() {

    while [[ $# -gt 0 ]]; do

        case "$1" in

            --backup-dir)

                if [[ $# -lt 2 ]]; then
                    printf 'ERROR: --backup-dir requires a path.\n' >&2
                    exit 3
                fi

                BACKUP_DIR="$2"
                shift 2
                ;;

            --retention)

                if [[ $# -lt 2 ]]; then
                    printf 'ERROR: --retention requires a value.\n' >&2
                    exit 3
                fi

                if ! is_integer "$2" || (( $2 < 1 )); then

                    printf 'ERROR: Retention must be a positive integer.\n' \
                        >&2

                    exit 3
                fi

                RETENTION_DAYS="$2"
                shift 2
                ;;

            --remote)

                if [[ $# -lt 2 ]]; then
                    printf 'ERROR: --remote requires a destination.\n' >&2
                    exit 3
                fi

                REMOTE_DESTINATION="$2"
                shift 2
                ;;

            --help|-h)

                show_help
                exit 0
                ;;

            *)

                printf 'ERROR: Unknown option: %s\n' "$1" >&2
                show_help
                exit 3
                ;;
        esac
    done
}


check_dependencies() {

    local commands=(
        tar
        gzip
        date
        mkdir
        sha256sum
        find
        hostname
        du
        df
        grep
        rm
    )

    local cmd
    local missing=0

    for cmd in "${commands[@]}"; do

        if ! command -v "$cmd" >/dev/null 2>&1; then

            printf 'ERROR: Required command missing: %s\n' \
                "$cmd" >&2

            missing=1
        fi

    done

    if [[ -n "$REMOTE_DESTINATION" ]]; then

        if ! command -v scp >/dev/null 2>&1; then

            printf 'ERROR: scp is required for remote backup.\n' >&2
            missing=1
        fi
    fi

    if (( missing != 0 )); then
        exit 3
    fi
}


log_message() {

    local level="$1"
    local message="$2"

    mkdir -p "$LOG_DIR"

    printf '[%s] [%s] %s\n' \
        "$(date '+%Y-%m-%d %H:%M:%S')" \
        "$level" \
        "$message" \
        >> "$LOG_FILE"
}


validate_sources() {

    local source

    for source in "${SOURCES[@]}"; do

        if [[ ! -e "$source" ]]; then

            log_message \
                "ERROR" \
                "Backup source missing: $source"

            printf 'ERROR: Backup source does not exist: %s\n' \
                "$source" >&2

            exit 3
        fi

        if [[ ! -r "$source" ]]; then

            log_message \
                "ERROR" \
                "Backup source unreadable: $source"

            printf 'ERROR: Backup source is not readable: %s\n' \
                "$source" >&2

            exit 3
        fi
    done
}


prepare_backup_directory() {

    if ! mkdir -p "$BACKUP_DIR"; then

        printf 'ERROR: Unable to create backup directory: %s\n' \
            "$BACKUP_DIR" >&2

        exit 3
    fi

    if [[ ! -w "$BACKUP_DIR" ]]; then

        printf 'ERROR: Backup directory is not writable: %s\n' \
            "$BACKUP_DIR" >&2

        exit 3
    fi
}


initialize_backup() {

    TIMESTAMP=$(date '+%Y-%m-%d-%H%M')
    HOSTNAME_VALUE=$(hostname)

    BACKUP_NAME="backup-${TIMESTAMP}.tar.gz"
    BACKUP_FILE="$BACKUP_DIR/$BACKUP_NAME"

    CHECKSUM_FILE="${BACKUP_FILE}.sha256"
}


report_destination_space() {

    local available_kb

    available_kb=$(
        df -Pk "$BACKUP_DIR" |
        awk 'NR==2 {print $4}'
    )

    log_message \
        "INFO" \
        "Available destination space: ${available_kb} KB"
}


create_backup() {

    log_message \
        "INFO" \
        "Starting backup: $BACKUP_NAME"

    printf 'Creating backup archive...\n'

    if tar -czf "$BACKUP_FILE" "${SOURCES[@]}"; then

        log_message \
            "INFO" \
            "Backup archive created: $BACKUP_FILE"

    else

        log_message \
            "ERROR" \
            "tar failed while creating backup"

        rm -f -- "$BACKUP_FILE"

        printf 'ERROR: Backup creation failed.\n' >&2

        exit 2
    fi
}


verify_archive() {

    printf 'Verifying archive structure...\n'

    if tar -tzf "$BACKUP_FILE" >/dev/null 2>&1; then

        ARCHIVE_STATUS="PASSED"

        log_message \
            "INFO" \
            "Archive verification passed"

    else

        ARCHIVE_STATUS="FAILED"

        log_message \
            "ERROR" \
            "Archive verification failed"

        printf 'ERROR: Archive verification failed.\n' >&2

        exit 2
    fi
}


verify_required_items() {

    local item

    for item in "${REQUIRED_BACKUP_ITEMS[@]}"; do

        if ! tar -tzf "$BACKUP_FILE" |
             grep -Fxq "$item"; then

            log_message \
                "ERROR" \
                "Required archive item missing: $item"

            printf 'ERROR: Required item missing from backup: %s\n' \
                "$item" >&2

            exit 2
        fi
    done

    log_message \
        "INFO" \
        "Required backup items verified"
}


create_checksum() {

    printf 'Creating SHA-256 checksum...\n'

    if sha256sum "$BACKUP_FILE" > "$CHECKSUM_FILE"; then

        log_message \
            "INFO" \
            "Checksum created"

    else

        log_message \
            "ERROR" \
            "Checksum creation failed"

        printf 'ERROR: Unable to create checksum.\n' >&2

        exit 2
    fi
}


verify_checksum() {

    printf 'Verifying checksum...\n'

    if sha256sum -c "$CHECKSUM_FILE" >/dev/null 2>&1; then

        CHECKSUM_STATUS="PASSED"

        log_message \
            "INFO" \
            "Checksum verification passed"

    else

        CHECKSUM_STATUS="FAILED"

        log_message \
            "ERROR" \
            "Checksum verification failed"

        printf 'ERROR: Checksum verification failed.\n' >&2

        exit 2
    fi
}


apply_retention() {

    local old_backup
    local checksum_file
    local -a old_backups=()

    mapfile -t old_backups < <(
        find "$BACKUP_DIR" \
            -maxdepth 1 \
            -type f \
            -name 'backup-*.tar.gz' \
            -mtime "+$RETENTION_DAYS"
    )

    for old_backup in "${old_backups[@]}"; do

        checksum_file="${old_backup}.sha256"

        printf 'Removing expired backup: %s\n' \
            "$old_backup"

        if rm -- "$old_backup"; then

            ((REMOVED_BACKUPS+=1))

            log_message \
                "INFO" \
                "Removed expired backup: $old_backup"

        else

            log_message \
                "WARNING" \
                "Unable to remove expired backup: $old_backup"

            OVERALL_STATUS="WARNING"
        fi

        if [[ -f "$checksum_file" ]]; then

            rm -- "$checksum_file" ||
                log_message \
                    "WARNING" \
                    "Unable to remove checksum: $checksum_file"
        fi
    done
}


copy_remote() {

    if [[ -z "$REMOTE_DESTINATION" ]]; then

        REMOTE_STATUS="DISABLED"
        return
    fi

    printf 'Copying backup to remote destination...\n'

    if scp \
        "$BACKUP_FILE" \
        "$CHECKSUM_FILE" \
        "$REMOTE_DESTINATION"; then

        REMOTE_STATUS="PASSED"

        log_message \
            "INFO" \
            "Remote backup copy completed"

    else

        REMOTE_STATUS="FAILED"
        OVERALL_STATUS="WARNING"

        log_message \
            "WARNING" \
            "Remote backup copy failed"

        printf 'WARNING: Local backup succeeded, but remote copy failed.\n' \
            >&2
    fi
}


get_backup_size() {

    BACKUP_SIZE=$(
        du -h "$BACKUP_FILE" |
        awk '{print $1}'
    )
}


print_report() {

    printf '\n%s\n' \
        "=========================================================================="

    printf '%s\n' \
        "                         BACKUP REPORT"

    printf '%s\n' \
        "=========================================================================="

    printf '%-22s %s\n' \
        "Timestamp:" "$TIMESTAMP"

    printf '%-22s %s\n' \
        "Hostname:" "$HOSTNAME_VALUE"

    printf '%-22s %s\n' \
        "Backup Directory:" "$BACKUP_DIR"

    printf '\nSources:\n'

    local source

    for source in "${SOURCES[@]}"; do
        printf '  %s\n' "$source"
    done

    printf '\n%-22s %s\n' \
        "Archive:" "$BACKUP_NAME"

    printf '%-22s %s\n' \
        "Archive Size:" "$BACKUP_SIZE"

    printf '%-22s %s\n' \
        "Archive Check:" "$ARCHIVE_STATUS"

    printf '%-22s %s\n' \
        "Checksum Check:" "$CHECKSUM_STATUS"

    printf '%-22s %s\n' \
        "Remote Copy:" "$REMOTE_STATUS"

    printf '%-22s %s days\n' \
        "Retention:" "$RETENTION_DAYS"

    printf '%-22s %s\n' \
        "Old Backups Removed:" "$REMOVED_BACKUPS"

    printf '\n%s\n' \
        "--------------------------------------------------------------------------"

    printf '%-22s %s\n' \
        "Overall Status:" "$OVERALL_STATUS"

    printf '%s\n' \
        "=========================================================================="
}


return_status() {

    case "$OVERALL_STATUS" in

        SUCCESS)
            return 0
            ;;

        WARNING)
            return 1
            ;;

        *)
            return 2
            ;;
    esac
}


main() {

    parse_arguments "$@"

    check_dependencies

    prepare_backup_directory

    validate_sources

    initialize_backup

    report_destination_space

    create_backup

    verify_archive

    verify_required_items

    create_checksum

    verify_checksum

    apply_retention

    copy_remote

    get_backup_size

    print_report

    log_message \
        "INFO" \
        "Backup completed with status: $OVERALL_STATUS"

    return_status
}


main "$@"
exit $?
```

# 67. Permissions and `/etc`

Some files under `/etc` may be readable only by root.

* Dedicated privileged service account
* Controlled `sudo`
* Backup agent

Do not solve permission problems by making sensitive files world-readable.

# 68. Backing Up `/home`

```text
SSH keys
credentials
personal files

application data
```

# 69. Backup Permissions

Inspect:

```bash
ls -l backups/
```

You may want restrictive permissions:

```bash
chmod 700 backups
```

And:

```bash
chmod 600 backups/*.tar.gz
chmod 600 backups/*.sha256
```

A stronger approach is to set:

```bash
umask 077
```

near the beginning of the script.

Then newly created backup files default to private permissions.

---

# 70. Add `umask`

Near the top:

```bash
umask 077
```

This is useful because backups may contain:

* Password hashes
* SSH configuration
* API configuration
* TLS configuration
* Application secrets
* User data

---

# 71. Backup Encryption

Compression is not encryption.

This:

```text
.tar.gz
```

does not mean the backup is protected from someone who obtains the file.

For sensitive backups, consider encryption using approved organizational tooling.

Possible approaches include:

* Encrypted storage volume
* Object-storage server-side encryption
* Backup product encryption
* GPG
* KMS-backed encryption

Key management is just as important as encryption itself.

---

# 72. Do Not Store the Encryption Key Beside the Backup

A pattern like:

```text
backup.tar.gz.gpg
backup-decryption-key.txt
```

in the same directory defeats much of the protection.

Separate key management from backup storage.

---

# 73. Local Backups Are Not Enough

Consider:

```text
Server
 |
 +-- Application
 |
 +-- /opt/backups
```

If the entire server is destroyed, both disappear.

A stronger architecture is:

```text
Application Server
       |
       +-- Local Backup
       |
       +-- Remote Backup
                |
                v
         Separate Failure Domain
```

---

# 74. The 3-2-1 Principle

A commonly used backup strategy is conceptually:

```text
3 copies of data
2 different storage types
1 copy off-site/off-system
```

The exact implementation depends on the organization, but the underlying idea is avoiding a single failure domain.

# 78. Failure Detection

The script should consider several failure points:

```text
Source missing
Destination unavailable
Permission denied
Disk full
tar failure
Archive corruption
Checksum failure

Remote copy failure
```

These failures are not equally severe.

# 79. Local Failure vs Remote Failure

Suppose:

```text
Local backup: SUCCESS
Remote copy:  FAILED
```

The backup still exists locally.

Our script classifies this as:

```text
WARNING
```

rather than total backup failure.

Your organization's policy may consider off-site failure critical.

Design severity according to recovery requirements.

# 80. Backup Exit Codes

Our script uses:

```text
0 = SUCCESS
1 = Backup created but a non-critical step failed
2 = Backup or verification failed
3 = Configuration or input error
```

This makes automation possible.

A scheduler can detect a failed run without parsing human-readable text.

# 82. Cron and Privileges

If backing up protected system paths, a user crontab may not have sufficient privileges.

You may instead use:

* Root crontab
* System cron
* systemd timer
* Dedicated backup account

Whatever you choose, apply least privilege.

# 83. Systemd Timers

For production Linux environments, a `systemd` timer can be a cleaner scheduling option than cron.

# 84. Backing Up Databases Is Different

Do not assume:

```bash
tar -czf database-backup.tar.gz /var/lib/mysql
```

is always a safe live database backup.

Databases may require:

* Logical dump
* Native backup tooling
* Snapshot coordination
* Filesystem freeze
* Transaction consistency
* Replication-aware backup

Examples include:

```text
mysqldump
pg_dump
database-native snapshots
```

A filesystem copy of a live database can be inconsistent.

---

# 85. Application Consistency

Even ordinary application data can change while `tar` is reading it.

Suppose:

```text
File A backed up at 02:00:01
File B modified at 02:00:03
File C backed up at 02:00:05
```

The archive may represent different moments in time.

For configuration files this may be acceptable.

For transactional systems it may not be.

---

# 86. Backup Logs Should Tell You What Failed

Bad log:

```text
Backup failed.
```

Better:

```text
[ERROR] tar failed while reading /home/veriqta/projects
```

Better logs reduce incident investigation time.

# 87. Detect Empty Backups

A backup file can exist but be unexpectedly tiny.

Check:

```bash
du -h "$BACKUP_FILE"
```

A production version could compare archive size with historical backups.

Example:

```text
Yesterday: 18 GB
Today:    12 MB
```

That should trigger investigation.

---

# 88. Production Upgrade: Minimum Backup Size

Example:

```bash
MIN_BACKUP_BYTES=104857600
```

That is 100 MiB.

Check:

```bash
stat -c '%s' "$BACKUP_FILE"
```

Then warn if below an expected minimum.

Do not choose arbitrary size thresholds without understanding the workload.

---

# 89. Production Upgrade: Backup Size Anomaly

A stronger approach is comparing against historical values.

For example:

```text
Average previous size: 20 GB
Current size:          2 GB
Change:               -90%
```

That may indicate:

* Missing mount
* Missing source
* Permission problem
* Exclusion mistake
* Application data moved

---

# 90. Missing Mount Problem

Suppose:

```text
/data
```

normally contains 500 GB.

But the disk fails to mount.

The directory still exists as an empty local directory.

A naive backup may happily archive the empty directory and report success.

This is dangerous.

For critical mounted paths, verify:

```bash
findmnt /data
```

before backup.

---

# 91. Production Upgrade: Expected Mount Validation

Example:

```bash
EXPECTED_MOUNTS=(
    "/home"
    "/data"
)
```

Then:

```bash
findmnt -rn /data
```

A missing required mount should stop the backup.

This prevents silently backing up the wrong filesystem.

---

# 92. Retention Is Not the Same as Recovery Policy

Keeping:

```text
7 days
```

may be appropriate for one workload and completely inadequate for another.

Real retention policies might include:

```text
7 daily
4 weekly
12 monthly
7 yearly
```

depending on business requirements.

Our simple day-based retention is only the beginning.

---

# 93. Never Let Retention Delete the New Backup

The naming pattern and path restrictions matter.

Retention should target:

```text
expired known backup files
```

not arbitrary files in the directory.

That is why we restrict:

```text
-maxdepth 1
-name 'backup-*.tar.gz'
```

---

# 94. Production Upgrade: Dry Run

Before retention deletes anything, support:

```bash
./automated-backup.sh --dry-run
```

Then show:

```text
Would delete:
backup-2026-08-31-0200.tar.gz
backup-2026-09-01-0200.tar.gz
```

without removing anything.

Dry-run behavior is valuable around destructive automation.

---

# 95. Production Upgrade: Locking

What if the previous backup is still running when the next one starts?

You could end up with overlapping jobs.

Use a lock.

For example, with `flock`:

```bash
flock
```

Conceptually:

```text
Backup starts
   |
   v
Acquire lock
   |
   +-- success -> continue
   |
   `-- already locked -> exit
```

---

# 96. Why Overlapping Backups Are Dangerous

Two simultaneous backups can:

* Consume excessive disk I/O
* Consume CPU
* Fill the destination
* Conflict with retention
* Produce confusing logs
* Transfer the wrong artifacts

Production backup jobs should usually prevent overlap.

# 97. Production Upgrade: Temporary Filename

A safer pattern is:

```text
backup-2026-09-11-0200.tar.gz.part
```

while the archive is being created.

Only after successful verification rename it to:

```text
backup-2026-09-11-0200.tar.gz
```

Then incomplete files are obvious.

# 98. Atomic Publication Pattern

Conceptually:

```text
Create:

Verify:
backup.tar.gz.part

Checksum:
backup.tar.gz.part

Success:
rename -> backup.tar.gz
```

This reduces the chance another system consumes a half-created backup.

# 105. Troubleshooting: `Permission denied`

If `tar` reports:

```text
Permission denied
```

identify the path.

Do not immediately run:

```bash
chmod -R 777
```

That is not an acceptable fix.

Investigate:

```bash
ls -ld PATH
```

and:

```bash
namei -l PATH
```

Then decide whether the backup account needs authorized access.

---

# 106. Troubleshooting: `No space left on device`

Check:

```bash
df -h "$BACKUP_DIR"
```

Then:

```bash
df -i "$BACKUP_DIR"
```

You may be out of:

* Capacity
* Inodes

Also inspect old backups:

```bash
du -sh "$BACKUP_DIR"
```

and:

```bash
du -h "$BACKUP_DIR"/* |
sort -hr |
head
```

# 107. Troubleshooting: Backup Is Much Smaller Than Expected

```text
Are sources mounted?

```


Check `tar` output and logs.

# 108. Troubleshooting: `tar: file changed as we read it`

You may see:

```text
file changed as we read it
```

This means a source file changed while `tar` was reading it.

For frequently changing data, consider:

* Application-aware backups
* Snapshots
* Brief application quiescing
* Database-native backup tools
* Exclusions for transient files

Do not suppress the warning without understanding it.

# 109. Troubleshooting: Checksum Fails

If:

```bash
sha256sum -c backup.sha256
```

fails, do not use the backup as if nothing happened.

Investigate:

* Did the archive change?
* Was transfer incomplete?
* Was the file truncated?
* Was the checksum generated against another file?
* Is storage corrupt?

Checksum failure means integrity can no longer be assumed.


# 115. Recovery Point Objective

Backup frequency is tied to how much data loss is acceptable.

If you back up every 24 hours, you could potentially lose almost 24 hours of changes.

That concept is often described as Recovery Point Objective, or RPO.

Our Bash script does not choose the business RPO.

It implements the schedule you give it.

---

# 116. Recovery Time Objective

You should also consider how long restoration can take.

A 10 TB backup might be perfectly valid but take too long to restore for the business requirement.

This is related to Recovery Time Objective, or RTO.

Backup design is not only about creating files.

It is about recovery.
