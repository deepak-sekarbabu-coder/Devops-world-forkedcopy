# Project 9: SSH Automation Script

SSH is one of the most important tools in Linux administration.

A DevOps engineer may need to:

* Check uptime across several servers
* Verify disk usage
* Check whether a service is running
* Collect system information
* Inspect memory
* Run a read-only diagnostic command
* Confirm whether a host is reachable

Doing this manually against one server is easy:

```bash
ssh veriqta@web01 "uptime"
```

Doing it across:

```text
web01
web02
web03
api01
api02
db01
db02
worker01
worker02
```

becomes repetitive.

In this project, we will build:

```text
ssh-automation.sh
```

The script will:

* Read servers from an inventory file
* Connect using SSH
* Use SSH keys
* Run remote commands
* Detect unreachable systems
* Detect authentication failures
* Detect remote command failures
* Apply connection timeouts
* Produce a clean report
* Return meaningful exit codes

Example output:

```text
==========================================================================
                         SSH AUTOMATION REPORT
==========================================================================

HOST                 CONNECTION       COMMAND
--------------------------------------------------------------------------

web01                REACHABLE        PASSED
web02                REACHABLE        PASSED
db01                 UNREACHABLE      NOT RUN
api01                REACHABLE        FAILED

--------------------------------------------------------------------------
Reachable:            3
Unreachable:          1
Command Failures:     1

Overall Status:       WARNING
==========================================================================
```

The production upgrade will allow us to run a health check across multiple Linux servers.

The most important rule in this project is:

```text
SSH automation must not trade security for convenience.
```

We will not solve connection problems by blindly disabling host-key verification.

# 1. Project Scenario

Imagine you support several Linux servers:

```text
web01
web02
db01
```

An incident starts.

The monitoring system says:

```text
One or more servers may be unhealthy.
```

You need a quick first-level check.

Manually:

```bash
ssh veriqta@web01 "uptime"
```

Then:

```bash
ssh veriqta@web02 "uptime"
```

Then:

```bash

```

Maybe:

```text

```

That wastes time.

Instead, we want:

```bash

    --inventory inventory.txt \
    --user veriqta \
    --command uptime
```

and receive:

```text
web01   reachable
web02   reachable
db01    unreachable
```

This is the beginning of multi-server automation.

# 5. Important SSH Concepts

SSH stands for:

```text
Secure Shell
```

It allows encrypted remote administration.

Basic syntax:

```bash
ssh user@server
```

Example:

```bash
ssh veriqta@web01
```

Remote command:

```bash
ssh veriqta@web01 "uptime"
```

SSH connects, executes the command, prints the result, and exits.

# 6. Remote Execution

Try:

```bash
ssh veriqta@web01 "hostname"
```

Possible output:

```text
web01
```

Try:

```bash
ssh veriqta@web01 "uptime"
```

Example:

```text
02:31:40 up 42 days, 3:22, 1 user, load average: 0.10, 0.07, 0.05
```

Try:

```bash

```

```text
The command executes on the remote server, not your local machine.
```

# 7. SSH Keys

Password-based SSH automation is usually a poor design.

Imagine this loop:

```bash
for host in web01 web02 db01; do
    ssh veriqta@"$host" uptime
done
```

If every connection asks:

```text
Password:
```

the script is not really automated.

SSH keys solve this.

---

# 8. Public and Private Keys

An SSH key pair contains:

```text
Private Key
Public Key
```

The private key remains with the client.

The public key is placed on the server.

Conceptually:

```text
Engineer Machine

Private Key
    |
    |
    +----------------------+
                           |
                           v

                      Remote Server
                      Public Key
```

Never copy the private key onto every server.

On your administration machine:

```bash
ssh-keygen -t ed25519
```

```text

```

Use the appropriate location.

For example:

```text
~/.ssh/id_ed25519
```

Use a passphrase where your environment requires it.

```text
~/.ssh/id_ed25519
```

and:

```text

```

The first is:

```text

```

The second is:

```text
PUBLIC
```

# 11. Private Key Permissions

Check:

```bash

```

A common secure mode is:

```text
600
```

Set:


```bash

```

# 13. SSH Permissions

Typical settings:

```bash
chmod 700 ~/.ssh
```

and:

```bash
chmod 600 ~/.ssh/authorized_keys
```

Ownership must match the account.

For example:

```bash
chown -R veriqta:veriqta /home/veriqta/.ssh
```

Use the actual primary group on the remote system.

# 23. Problem: SSH Can Hang

If:

```text
db01
```

is unreachable, SSH may wait.

Automation should have a timeout.

Use:

```bash
ssh \
    -o ConnectTimeout=5 \
    veriqta@db01 \
    "uptime"
```

This gives the connection attempt a defined limit.

---

# 24. Batch Mode

Use:

```bash
-o BatchMode=yes
```

This prevents SSH from interactively prompting for credentials.

Example:

```bash
ssh \
    -o BatchMode=yes \
    -o ConnectTimeout=5 \
    veriqta@web01 \
    "uptime"
```

For automation, this is very useful.

If authentication is unavailable, the command fails instead of waiting for input.

---

# 25. Host-Key Verification

The first time you connect to a server manually, SSH may ask:

```text
The authenticity of host 'web01' can't be established.
Are you sure you want to continue connecting?
```

This is a security feature.

The server's host key helps verify that you are connecting to the expected machine.

---

# 26. Do Not Blindly Disable Host-Key Checking

You may see examples such as:

```bash
ssh \
    -o StrictHostKeyChecking=no \
    ...
```

Do not make this your default production solution.

This can weaken protection against connecting to an unexpected or impersonated server.

For controlled automation, manage host keys properly.

# 28. Populate Host Keys Carefully

For a trusted environment, you may obtain host keys through:

* Configuration management
* Infrastructure provisioning
* Trusted server inventory
* Organizational SSH certificate systems
* Verified `ssh-keyscan` workflow

`ssh-keyscan` retrieves keys, but retrieval alone does not prove they belong to the intended system.

Verification still matters.

# 29. Connection Testing

We want:

```text
web01   reachable
web02   reachable
db01    unreachable
```

A simple test is:

```bash
if ssh \
    -o BatchMode=yes \
    -o ConnectTimeout=5 \
    veriqta@"$host" \
    "true"; then

    echo "$host reachable"

else

    echo "$host unreachable"

fi
```

The remote:

```bash
true
```

does nothing except return:

```text
0
```

---

# 30. Why `true` Is Useful

`true` is a command whose purpose is to succeed.

Run:

```bash
true
```

Then:

```bash
echo $?
```

Expected:

```text
0
```

So:

```bash
ssh host true
```

is a lightweight way to test successful remote command execution.

---

# 31. Reachability Is More Than Ping

Do not equate:

```text
ping works
```

with:

```text
SSH works
```

A server may:

* Block ICMP
* Allow SSH
* Respond to ping but have port 22 blocked
* Have SSH service down
* Reject your authentication

Our script tests actual SSH access.

That is more relevant.

---

# 32. SSH Exit Codes

SSH returns non-zero when:

* Connection fails
* Authentication fails
* Host verification fails
* Remote command fails

This creates an important challenge.

Suppose:

```bash
ssh veriqta@web01 "false"
```

The SSH connection succeeds, but the remote command returns:

```text
1
```

SSH passes that failure back.

So:

```text
non-zero
```

does not always mean:

```text
server unreachable
```

We need better classification.

---

# 33. Test a Remote Command Failure

Run:

```bash
ssh veriqta@web01 "false"
```

Then:

```bash
echo $?
```

Likely:

```text
1
```

The server was reachable.

The command failed.

This distinction matters.

---

# 34. Separate Connection Test From Command Execution

A clean design is:

```text
Phase 1:
Can I connect?

Phase 2:
If yes, run command.
```

That lets us distinguish:

```text
CONNECTION FAILURE
```

from:

```text
REMOTE COMMAND FAILURE
```

# 35. Connection Function

Create:

```bash
check_connection() {

    local host="$1"

    ssh \
        -o BatchMode=yes \
        -o ConnectTimeout="$CONNECT_TIMEOUT" \
        "$SSH_USER@$host" \
        "true" \
        >/dev/null 2>&1
}
```

Return:

```text
0
```

means the SSH test succeeded.

# 37. Capture Remote Output

Example:

```bash
output=$(
    ssh veriqta@web01 "uptime" 2>&1
)
```

Then:

```bash
status=$?
```

Do not overwrite `$?` before saving it.

---

# 38. Exit Status Must Be Captured Immediately

Wrong:

```bash
output=$(ssh ...)
echo "Finished"
status=$?
```

Now `$?` belongs to:

```text
echo
```

not SSH.

Correct:

```bash
output=$(ssh ... 2>&1)
status=$?
```

Immediately.

If supplied:

```bash

    echo "Identity file not found"

```

```bash

```

---

# 43. Never Log Private Key Contents

A safe log can say:

```text
identity_file=/home/veriqta/.ssh/id_ed25519
```

if needed.

It should never contain:

```text
-----BEGIN OPENSSH PRIVATE KEY-----
```

If private key contents appear in your logs, treat that as a credential exposure incident.

# 44. Prefer SSH Config

Instead of putting every option in the script, SSH supports:

```text
~/.ssh/config
```

Example:

```text

    HostName 10.0.1.10
    User veriqta
    IdentityFile ~/.ssh/id_ed25519
```

Then:

```bash
ssh web01
```

works without repeating everything.

This becomes useful as environments grow.

# 47. Blast Radius

This command:

```bash

```

on one server is dangerous.

Running it automatically across:

```text

```

is dramatically worse.

* Validation
* Dry run
* Explicit confirmation
* Read-only defaults
* Small batches

become.

# 50. Complete Working Script

Use:

```bash
#!/usr/bin/env bash

set -u
set -o pipefail

umask 077

# ------------------------------------------------------------------
# SSH Automation Script
# ------------------------------------------------------------------
#
# Exit codes:
#   0 = All hosts reachable and all commands successful
#   1 = One or more hosts/commands failed
#   2 = Major execution failure
#   3 = Input/configuration error
#
# ------------------------------------------------------------------

INVENTORY_FILE=""
SSH_USER=""
REMOTE_COMMAND="uptime"

IDENTITY_FILE=""
CONNECT_TIMEOUT=5

DRY_RUN=false

TOTAL_HOSTS=0
REACHABLE_HOSTS=0
UNREACHABLE_HOSTS=0
COMMAND_FAILURES=0

OVERALL_STATUS="SUCCESS"

SCRIPT_DIR=$(
    cd -- "$(dirname -- "${BASH_SOURCE[0]}")" &&
    pwd
)

readonly SCRIPT_DIR

LOG_DIR="$SCRIPT_DIR/logs"
LOG_FILE="$LOG_DIR/ssh-automation.log"

OUTPUT_DIR="$SCRIPT_DIR/output"


show_help() {

    cat <<EOF
Usage:
  $0 [options]

Required:
  --inventory FILE    Inventory containing remote hosts
  --user USER         Remote SSH username

Optional:
  --command CMD       Remote command
                      Default: uptime

  --identity FILE     SSH private key file

  --timeout N         SSH connection timeout in seconds
                      Default: 5

  --output-dir DIR    Directory for per-host command output

  --dry-run           Display intended actions only

  --help              Display this help

Examples:
  $0 \
    --inventory inventory.txt \
    --user veriqta

  $0 \
    --inventory inventory.txt \
    --user veriqta \
    --command "df -h /"

  $0 \
    --inventory inventory.txt \
    --user veriqta \
    --identity ~/.ssh/id_ed25519 \
    --command "uptime"

  $0 \
    --inventory inventory.txt \
    --user veriqta \
    --dry-run
EOF
}


is_integer() {
    [[ "$1" =~ ^[0-9]+$ ]]
}


parse_arguments() {

    while [[ $# -gt 0 ]]; do

        case "$1" in

            --inventory)

                [[ $# -ge 2 ]] || {
                    printf 'ERROR: --inventory requires a file.\n' >&2
                    exit 3
                }

                INVENTORY_FILE="$2"
                shift 2
                ;;

            --user)

                [[ $# -ge 2 ]] || {
                    printf 'ERROR: --user requires a value.\n' >&2
                    exit 3
                }

                SSH_USER="$2"
                shift 2
                ;;

            --command)

                [[ $# -ge 2 ]] || {
                    printf 'ERROR: --command requires a value.\n' >&2
                    exit 3
                }

                REMOTE_COMMAND="$2"
                shift 2
                ;;

            --identity)

                [[ $# -ge 2 ]] || {
                    printf 'ERROR: --identity requires a file.\n' >&2
                    exit 3
                }

                IDENTITY_FILE="$2"
                shift 2
                ;;

            --timeout)

                [[ $# -ge 2 ]] || {
                    printf 'ERROR: --timeout requires a value.\n' >&2
                    exit 3
                }

                if ! is_integer "$2" ||
                   (( $2 < 1 || $2 > 120 )); then

                    printf 'ERROR: --timeout must be between 1 and 120 seconds.\n' \
                        >&2

                    exit 3
                fi

                CONNECT_TIMEOUT="$2"
                shift 2
                ;;

            --output-dir)

                [[ $# -ge 2 ]] || {
                    printf 'ERROR: --output-dir requires a path.\n' >&2
                    exit 3
                }

                OUTPUT_DIR="$2"
                shift 2
                ;;

            --dry-run)

                DRY_RUN=true
                shift
                ;;

            --help|-h)

                show_help
                exit 0
                ;;

            *)

                printf 'ERROR: Unknown option: %s\n' "$1" >&2
                show_help
                exit 3
                ;;
        esac

    done
}


check_dependencies() {

    local commands=(
        ssh
        date
        mkdir
    )

    local cmd

    for cmd in "${commands[@]}"; do

        if ! command -v "$cmd" >/dev/null 2>&1; then

            printf 'ERROR: Required command missing: %s\n' \
                "$cmd" >&2

            exit 3
        fi

    done
}


validate_inputs() {

    if [[ -z "$INVENTORY_FILE" ]]; then

        printf 'ERROR: --inventory is required.\n' >&2
        exit 3
    fi

    if [[ ! -f "$INVENTORY_FILE" ]]; then

        printf 'ERROR: Inventory file not found: %s\n' \
            "$INVENTORY_FILE" >&2

        exit 3
    fi

    if [[ ! -r "$INVENTORY_FILE" ]]; then

        printf 'ERROR: Inventory file is not readable: %s\n' \
            "$INVENTORY_FILE" >&2

        exit 3
    fi

    if [[ -z "$SSH_USER" ]]; then

        printf 'ERROR: --user is required.\n' >&2
        exit 3
    fi

    if [[ ! "$SSH_USER" =~ ^[a-z_][a-z0-9_-]*$ ]]; then

        printf 'ERROR: Invalid SSH username: %s\n' \
            "$SSH_USER" >&2

        exit 3
    fi

    if [[ -n "$IDENTITY_FILE" ]]; then

        if [[ ! -f "$IDENTITY_FILE" ]]; then

            printf 'ERROR: Identity file not found: %s\n' \
                "$IDENTITY_FILE" >&2

            exit 3
        fi

        if [[ ! -r "$IDENTITY_FILE" ]]; then

            printf 'ERROR: Identity file is not readable: %s\n' \
                "$IDENTITY_FILE" >&2

            exit 3
        fi
    fi

    mkdir -p "$LOG_DIR"
    mkdir -p "$OUTPUT_DIR"
}


log_message() {

    local level="$1"
    local message="$2"

    printf '[%s] [%s] %s\n' \
        "$(date '+%Y-%m-%d %H:%M:%S')" \
        "$level" \
        "$message" \
        >> "$LOG_FILE"
}


build_ssh_options() {

    SSH_OPTIONS=(
        -o BatchMode=yes
        -o ConnectTimeout="$CONNECT_TIMEOUT"
    )

    if [[ -n "$IDENTITY_FILE" ]]; then

        SSH_OPTIONS+=(
            -i "$IDENTITY_FILE"
        )
    fi
}


check_connection() {

    local host="$1"

    ssh \
        "${SSH_OPTIONS[@]}" \
        "$SSH_USER@$host" \
        "true" \
        >/dev/null 2>&1
}


run_remote_command() {

    local host="$1"
    local output_file="$2"

    ssh \
        "${SSH_OPTIONS[@]}" \
        "$SSH_USER@$host" \
        "$REMOTE_COMMAND" \
        > "$output_file" \
        2>&1
}


process_host() {

    local host="$1"
    local output_file
    local command_status

    ((TOTAL_HOSTS+=1))

    output_file="$OUTPUT_DIR/${host}.txt"

    if [[ "$DRY_RUN" == true ]]; then

        printf '%-20s %-15s %s\n' \
            "$host" \
            "DRY RUN" \
            "$REMOTE_COMMAND"

        return
    fi

    if ! check_connection "$host"; then

        ((UNREACHABLE_HOSTS+=1))

        OVERALL_STATUS="WARNING"

        printf '%-20s %-15s %-15s\n' \
            "$host" \
            "UNREACHABLE" \
            "NOT RUN"

        log_message \
            "ERROR" \
            "host=$host connection=UNREACHABLE"

        return
    fi

    ((REACHABLE_HOSTS+=1))

    run_remote_command \
        "$host" \
        "$output_file"

    command_status=$?

    if (( command_status == 0 )); then

        printf '%-20s %-15s %-15s\n' \
            "$host" \
            "REACHABLE" \
            "PASSED"

        log_message \
            "INFO" \
            "host=$host connection=REACHABLE command=PASSED"

    else

        ((COMMAND_FAILURES+=1))

        OVERALL_STATUS="WARNING"

        printf '%-20s %-15s %-15s\n' \
            "$host" \
            "REACHABLE" \
            "FAILED"

        log_message \
            "ERROR" \
            "host=$host connection=REACHABLE command=FAILED exit_code=$command_status"

    fi
}


process_inventory() {

    local host

    while IFS= read -r host || [[ -n "$host" ]]; do

        host="${host#"${host%%[![:space:]]*}"}"
        host="${host%"${host##*[![:space:]]}"}"

        [[ -z "$host" ]] && continue

        [[ "$host" =~ ^# ]] && continue

        process_host "$host"

    done < "$INVENTORY_FILE"
}


print_header() {

    printf '%s\n' \
        "=========================================================================="

    printf '%s\n' \
        "                         SSH AUTOMATION REPORT"

    printf '%s\n' \
        "=========================================================================="

    printf '\n%-20s %-15s %-15s\n' \
        "HOST" \
        "CONNECTION" \
        "COMMAND"

    printf '%s\n' \
        "--------------------------------------------------------------------------"
}


print_summary() {

    printf '\n%s\n' \
        "--------------------------------------------------------------------------"

    printf '%-24s %s\n' \
        "Total Hosts:" "$TOTAL_HOSTS"

    printf '%-24s %s\n' \
        "Reachable:" "$REACHABLE_HOSTS"

    printf '%-24s %s\n' \
        "Unreachable:" "$UNREACHABLE_HOSTS"

    printf '%-24s %s\n' \
        "Command Failures:" "$COMMAND_FAILURES"

    printf '\n%-24s %s\n' \
        "Overall Status:" "$OVERALL_STATUS"

    printf '%s\n' \
        "=========================================================================="
}


return_status() {

    if [[ "$DRY_RUN" == true ]]; then
        return 0
    fi

    if (( UNREACHABLE_HOSTS > 0 ||
          COMMAND_FAILURES > 0 )); then

        return 1
    fi

    return 0
}


main() {

    parse_arguments "$@"

    check_dependencies

    validate_inputs

    build_ssh_options

    print_header

    process_inventory

    print_summary

    log_message \
        "INFO" \
        "run_complete total=$TOTAL_HOSTS reachable=$REACHABLE_HOSTS unreachable=$UNREACHABLE_HOSTS command_failures=$COMMAND_FAILURES"

    return_status
}


main "$@"
exit $?
```


This improves accountability.

# 123. Security: Forced Commands

For specialized automation, an SSH public key can be restricted to a specific command through `authorized_keys`.

This can dramatically reduce what a key can do.

That is useful for narrowly scoped automation.

---

# 124. Security: SSH Certificates

Large organizations may use SSH certificates instead of distributing static public keys to every server.

This improves:

* Expiration
* Central trust
* Access lifecycle
* Key management

Our lab uses ordinary SSH keys because the underlying mechanics are easier to learn first.

# 125. Security: Never Commit Private Keys


```text
.gitignore is not a security control.
```
