# Project 9: Build a Unified AWS DevOps Audit Tool

## Capstone Project

Project 9 combines everything students built throughout the AWS Python automation series into one production-minded command-line application.

Until now, the projects have been separate:

```text
EC2 Inventory

S3 Governance

IAM Security Audit

Tagging Automation

EBS Cleanup Analysis

Security Group Audit

RDS Operational Audit

CloudWatch Monitoring Automation
```

That was intentional.

Students first needed to understand each operational domain independently.

Now the architecture changes.

Instead of maintaining eight unrelated scripts:

```text
ec2_inventory.py
s3_inventory.py
iam_audit.py
tag_audit.py
ebs_cleanup.py
security_group_audit.py
rds_audit.py
cloudwatch_monitoring.py
```

students will build:

```text
aws_audit.py
```

as the single command-line entry point.

But they will **not** copy thousands of lines of code into one enormous Python file.

Instead:

```text
CLI
 ↓
Modules
 ↓
Shared Utilities
 ↓
AWS APIs
```

The result becomes a reusable AWS DevOps auditing framework.

# 6. Why Modules Matter

Do not build:

```text
aws_audit.py
20,000 lines
```

That creates:

```text
Difficult testing
Difficult troubleshooting
Merge conflicts
Tight coupling
Repeated code
Unsafe changes
Poor readability
```

Instead:

```text
aws_audit.py
```

should primarily coordinate modules.

For example:

```python
from modules.ec2_inventory import run_ec2_audit
from modules.s3_inventory import run_s3_audit
from modules.iam_audit import run_iam_audit
```

Then:

```python
if command == "ec2":
    return run_ec2_audit(context)
```

The entry point decides **what to run**.

The module decides **how that audit works**.

# 8. Module Contract

Every audit module should expose a predictable interface.

For example:

```python
def run(context):
    ...
```

and return something resembling:

```python
{
    "module": "ec2",
    "status": "SUCCESS",
    "inventory": [],
    "findings": [],
    "errors": [],
    "summary": {}
}
```

The CLI should not need to understand every internal EC2 operation.

It only needs the standardized result.

---

# 10. Do Not Confuse Module Status With Compliance

Example:

```text
Module execution:
SUCCESS

Findings:
27 HIGH
```

This means:

```text
The audit worked successfully
and discovered problems.
```

It does **not** mean:

```text
Infrastructure passed.
```

Likewise:

```text
Module:
FAILED

Findings:
0
```

does not mean:

```text
No security problems.
```

It means the assessment failed.

---

# 11. Three Different Status Dimensions

Maintain separately:

```text
Execution Status

Assessment Status

Compliance Status
```

Example:

```text
Execution:
SUCCESS

Assessment:
COMPLETE

Compliance:
FAIL
```

Another:

```text
Execution:
SUCCESS

Assessment:
PARTIAL

Compliance:
UNKNOWN
```

because some resources returned AccessDenied.

This distinction prevents dangerous reporting.

# 15. argparse

Start with:

```python
import argparse
```

Create:

```python
def build_parser():
    parser = argparse.ArgumentParser(
        description=(
            "VERIQTA Unified AWS "
            "DevOps Audit Tool"
        )
    )

    parser.add_argument(
        "--profile",
        help="AWS CLI profile"
    )

    parser.add_argument(
        "--regions",
        nargs="+",
        help="Regions to scan"
    )

    parser.add_argument(
        "--config",
        default="config/settings.yaml"
    )

    parser.add_argument(
        "--output-dir",
        default="reports"
    )

    parser.add_argument(
        "--log-level",
        default="INFO",
        choices=[
            "DEBUG",
            "INFO",
            "WARNING",
            "ERROR"
        ]
    )

    parser.add_argument(
        "--dry-run",
        action="store_true"
    )

    subparsers = (
        parser.add_subparsers(
            dest="command",
            required=True
        )
    )

    return parser
```

# 26. Account Guardrails

Production automation should support:

```yaml
aws:
  allowed_accounts:
    - "123456789012"
    - "210987654321"
```

```python

    allowed_accounts
    and account_id
    not in allowed_accounts

        account_id

```

This prevents accidental execution against an unintended account.

# 33. Why Retries Matter

AWS APIs can temporarily fail because of:

```text
Throttling

Transient network errors

Service-side conditions

Rate limits
```

A production audit should not immediately collapse because one request was temporarily throttled.

But:

```text
AccessDenied
```

is not something to endlessly retry.

---

# 34. Retryable Versus Non-Retryable

Conceptually:

```text
Throttling
→ retry

temporary service failure
→ retry

connection problem
→ potentially retry

AccessDenied
→ do not blindly retry

ValidationError
→ fix request

InvalidParameter
→ fix code/configuration
```

Retries must be deliberate.

# 40. Pagination

Every module must ask:

```text
Can this AWS API paginate?
```

Do not assume one response contains everything.

Create:

```text
utils/pagination.py
```

Example:

```python
def paginate_items(
    client,
    operation_name,
    result_key,
    **kwargs
):
    paginator = (
        client.get_paginator(
            operation_name
        )
    )

    items = []

    for page in paginator.paginate(
        **kwargs
    ):
        items.extend(
            page.get(
                result_key,
                []
            )
        )

    return items
```

# 79. CSV Exporter

```python
import csv


def export_csv(
    rows,
    path,
    fieldnames=None
):
    if not rows:
        return

    path = Path(path)

    path.parent.mkdir(
        parents=True,
        exist_ok=True
    )

    if fieldnames is None:
        fieldnames = list(
            rows[0].keys()
        )

    with path.open(
        "w",
        newline="",
        encoding="utf-8"
    ) as file:
        writer = csv.DictWriter(
            file,
            fieldnames=fieldnames
        )

        writer.writeheader()
        writer.writerows(rows)
```

Nested structures should be normalized before CSV export.

def assume_role(

# 298. Final Production Mindset

A junior engineer may ask:

```text
Can Python delete this?
```

A production engineer asks:

```text
Should this be deleted?

What evidence proves that?

Who owns it?

What depends on it?

What policy authorizes this?

What happens if we are wrong?

Can we recover?

How many resources could be affected?

Has anything changed since approval?

How will we verify success?

How will another engineer understand
what happened tomorrow?
```

That difference is the real purpose of Project 9.
