# Project 4: AWS Resource Tagging Automation

## Scenario

The organization has a growing AWS environment.

Teams are creating:

* EC2 instances
* EBS volumes
* RDS databases
* load balancers
* Lambda functions
* S3 buckets
* VPC resources
* other AWS infrastructure

The resources work technically, but there is an operational problem.

Many resources do not have consistent tags.

An engineer opens the AWS console and finds resources such as:

```text
i-0abc123...
vol-0def456...
database-prod-02
my-random-bucket
```

But important questions cannot be answered easily:

```text
Who owns this?

Which application uses it?

Is it production or development?

Which team pays for it?

Was it created manually or through Terraform?

Can it be safely modified?

Can it be safely deleted?
```

Finance also has a problem.

The monthly AWS bill contains resources that cannot easily be assigned to:

* applications
* departments
* projects
* environments
* teams
* cost centers

Operations has another problem.

During an incident, engineers discover an EC2 instance but cannot immediately determine who owns it.

Security finds an exposed resource but does not know which team should receive the finding.

The organization decides to introduce a tagging standard.

Required example tags:

```text
Environment
Owner
Application
CostCenter
ManagedBy
```

The DevOps team now needs automation that can:

```text
Discover resources
        ↓
Retrieve tags
        ↓
Normalize tags
        ↓
Evaluate tagging policy
        ↓
Detect missing tags
        ↓
Detect invalid values
        ↓
Generate recommendations
        ↓
Produce audit reports
```

But the team wants something more advanced.

After reviewing findings, approved resources should optionally be remediated.

Therefore the project introduces two operating modes:

```bash
python tag_audit.py --mode audit
```

and:

```bash
python tag_audit.py --mode remediate
```

The difference is critical.

```text
AUDIT
    ↓
Read only
    ↓
Discover problems
    ↓
Recommend changes
```

versus:

```text
REMEDIATE
    ↓
Discover
    ↓
Validate
    ↓
Check authorization
    ↓
Check exclusions
    ↓
Check allowlist
    ↓
Preview changes
    ↓
Confirm
    ↓
Apply approved changes
    ↓
Read resource again
    ↓
Verify
    ↓
Record before/after evidence
```

This is the first project in the series where students deliberately cross an important boundary:

```text
READ
  ↓
DECIDE
  ↓
WRITE
```

That means safety controls become much more important.

# Part 1: Why AWS Tags Matter

An AWS tag is a key-value pair associated with a resource.

Example:

```text
Key:
Environment

Value:
production
```

Another:

```text
Key:
Owner

Value:
platform-team
```

Together:

```text
Environment = production
Owner = platform-team
Application = payments-api
CostCenter = CC-1042
ManagedBy = terraform
```

Tags add operational context to infrastructure.

Without tags:

```text
EC2 Instance
i-0123456789abcdef0
```

With tags:

```text
EC2 Instance
i-0123456789abcdef0

Environment = production
Owner = platform-team
Application = payments-api
CostCenter = CC-1042
ManagedBy = terraform
```

The infrastructure has not changed technically.

But operationally, it has become much easier to understand.

# Part 9: Infrastructure as Code Changes the Remediation Decision

Suppose Terraform defines:

```hcl
tags = {
  Environment = "production"
  Owner       = "platform-team"
}
```

But an external script adds:

```text
Application = payments-api
```

The resource now has a tag that Terraform configuration may not know about.

Depending on how the resource and provider configuration are managed, future Terraform operations could produce unexpected drift or changes.

Therefore:

```text
Can the AWS API modify this?
```

and:

```text
Should this automation modify this?
```

are completely different questions.

Production automation must understand this distinction.

# Part 20: Implement Pagination

Never assume one response contains every resource.

Create:

```python
def discover_resources(
    client
):
    paginator = (
        client.get_paginator(
            "get_resources"
        )
    )

    resources = []

    for page in paginator.paginate():
        resources.extend(
            page.get(
                "ResourceTagMappingList",
                []
            )
        )

    return resources
```

This gives us a regional collection of resource-tag mappings returned by the API.

# Part 22: Parse the Resource ARN

An ARN may look like:

```text
arn:aws:ec2:us-east-1:123456789012:instance/i-0123456789abcdef0
```

Useful components include:

```text
Partition
Service
Region
Account
Resource
```

Create:

```python
def parse_arn(arn):
    parts = arn.split(
        ":",
        5
    )

    if len(parts) != 6:
        return {
            "arn": arn,
            "service": None,
            "region": None,
            "account_id": None,
            "resource": None
        }

    return {
        "arn": arn,
        "partition": parts[1],
        "service": parts[2],
        "region": parts[3],
        "account_id": parts[4],
        "resource": parts[5]
    }
```

For production-grade ARN handling, remember that resource components vary by service.

# Part 23: Normalize Tag Structures

AWS commonly represents tags as:

```python
[
    {
        "Key": "Environment",
        "Value": "production"
    },
    {
        "Key": "Owner",
        "Value": "platform-team"
    }
]
```

This is awkward for repeated lookups.

Convert it to:

```python
{
    "Environment": "production",
    "Owner": "platform-team"
}
```

Create:

```python
def normalize_tags(tags):
    normalized = {}

    for tag in tags or []:
        key = tag.get("Key")
        value = tag.get("Value")

        if key is None:
            continue

        normalized[key] = (
            value
            if value is not None
            else ""
        )

    return normalized
```

Now:

```python
environment = tags.get(
    "Environment"
)
```

becomes simple.

# Part 27: Missing Key vs Empty Value

These are different:

```text
Owner
does not exist
```

versus:

```text
Owner = ""
```

Both may violate policy.

But reporting should distinguish them.

Create:

```python
def find_empty_tags(
    tags,
    required_tags
):
    empty = []

    for key in required_tags:
        if (
            key in tags
            and not str(
                tags[key]
            ).strip()
        ):
            empty.append(key)

    return empty
```

# Part 32: Build a Validation Function

Create:

```python
def validate_tags(
    tags,
    policy
):
    required = policy.get(
        "required_tags",
        []
    )

    allowed_values = policy.get(
        "allowed_values",
        {}
    )

    patterns = policy.get(
        "patterns",
        {}
    )

    missing = find_missing_tags(
        tags,
        required
    )

    empty = find_empty_tags(
        tags,
        required
    )

    invalid = []

    for key, allowed in (
        allowed_values.items()
    ):
        if key not in tags:
            continue

        value = tags[key]

        if value not in allowed:
            invalid.append(
                {
                    "key": key,
                    "value": value,
                    "reason": (
                        "VALUE_NOT_ALLOWED"
                    )
                }
            )

    for key, pattern in (
        patterns.items()
    ):
        if key not in tags:
            continue

        value = tags[key]

        if not validate_pattern(
            value,
            pattern
        ):
            invalid.append(
                {
                    "key": key,
                    "value": value,
                    "reason": (
                        "PATTERN_MISMATCH"
                    )
                }
            )

    return {
        "missing": missing,
        "empty": empty,
        "invalid": invalid
    }
```

# Part 39: Build Recommendations

```python
def build_recommendations(
    resource_arn,
    validation,
    approved_defaults
):
    approved = (
        approved_defaults.get(
            resource_arn,
            {}
        )
    )

    recommendations = {}

    for key in validation[
        "missing"
    ]:
        if key in approved:
            recommendations[key] = {
                "action": "ADD",
                "value": approved[key],
                "approved": True
            }
        else:
            recommendations[key] = {
                "action": "REVIEW",
                "value": None,
                "approved": False
            }

    return recommendations
```

# Part 46: Build Safe Change Planning

```python
def build_change_plan(
    existing_tags,
    recommended_tags,
    allow_overwrite=False
):
    additions = {}
    conflicts = {}
    unchanged = {}

    for key, new_value in (
        recommended_tags.items()
    ):
        if key not in existing_tags:
            additions[key] = (
                new_value
            )
            continue

        old_value = (
            existing_tags[key]
        )

        if old_value == new_value:
            unchanged[key] = (
                old_value
            )
            continue

        if allow_overwrite:
            conflicts[key] = {
                "old_value": old_value,
                "new_value": new_value,
                "overwrite_allowed": True
            }
        else:
            conflicts[key] = {
                "old_value": old_value,
                "new_value": new_value,
                "overwrite_allowed": False
            }

    return {
        "additions": additions,
        "conflicts": conflicts,
        "unchanged": unchanged
    }
```

# Part 54: Create a Remediation Function

```python
def apply_tags(
    client,
    resource_arn,
    tags,
    dry_run=True
):
    if not tags:
        return {
            "status": "SKIPPED",
            "reason": "NO_CHANGES"
        }

    if dry_run:
        return {
            "status": "DRY_RUN",
            "resource_arn": (
                resource_arn
            ),
            "tags": tags
        }

    response = client.tag_resources(
        ResourceARNList=[
            resource_arn
        ],
        Tags=tags
    )

    failures = response.get(
        "FailedResourcesMap",
        {}
    )

    if resource_arn in failures:
        return {
            "status": "FAILED",
            "details": failures[
                resource_arn
            ]
        }

    return {
        "status": "SUCCESS",
        "resource_arn": (
            resource_arn
        ),
        "tags": tags
    }
```

# Part 56: Verification

Retrieve the resource tags again.

Then verify:

```python
def verify_changes(
    current_tags,
    expected_tags
):
    failures = {}

    for key, expected in (
        expected_tags.items()
    ):
        actual = current_tags.get(
            key
        )

        if actual != expected:
            failures[key] = {
                "expected": expected,
                "actual": actual
            }

    return {
        "verified": (
            len(failures) == 0
        ),
        "failures": failures
    }
```

# Part 192: Final Verification Checklist

Project 4 is complete when students can verify:

## Tagging Strategy

* Required tags are documented.
* Tag purposes are documented.
* Allowed values are defined.
* Value patterns are defined.
* Policy is stored separately from code.
* Policy version is recorded.

## Discovery

* AWS regions are discovered.
* Resources are collected across regions.
* Pagination is implemented.
* ARN metadata is extracted.
* Unsupported resources are recognized.
* Regional failures do not hide successful regions.

## Inspection

* Existing tags are retrieved.
* Raw tags are preserved.
* Tags are normalized.
* AWS-reserved tags are handled safely.
* Completely untagged resources are identified.
* Partially tagged resources are identified.

## Validation

* Missing tags are detected.
* Empty values are detected.
* Invalid values are detected.
* Environment values are validated.
* Cost-center patterns are validated.
* Tag key case problems can be detected.
* Invalid values are not automatically "corrected" without authority.

## Recommendations

* Missing tags generate recommendations.
* Approved values are distinguished from unknown values.
* The script never invents ownership.
* The script never invents cost centers.
* Existing conflicts generate REVIEW findings.
* IaC-managed resources can receive source-of-truth recommendations.

## Audit Mode

* `--mode audit` performs no writes.
* Findings are generated.
* Compliance status is generated.
* Recommendations are generated.
* Reports are exported.

## Remediation Mode

* `--mode remediate` exists.
* Dry run exists.
* Dry run executes no AWS writes.
* Allowlists are enforced.
* Exclusions are enforced.
* Exclusions override allowlists.
* Protected environments receive stronger controls.
* Approved values are required.
* Existing tags are not overwritten by default.
* Confirmation is required for interactive real changes.
* Non-interactive execution requires explicit authorization.

## State Safety

* Current state is recorded.
* Proposed state is recorded.
* Resource state is re-read before changes.
* Stale plans are rejected.
* Existing values are protected.
* Idempotent changes are implemented.

## Change Execution

* Approved missing tags can be added.
* Per-resource failures are inspected.
* Partial failures are handled.
* AccessDenied is handled separately.
* Unsupported resources are handled separately.
* Retryable and non-retryable failures can be distinguished.

## Verification

* Resources are read after modification.
* Expected values are compared with actual values.
* Failed verification is not reported as success.
* Before-and-after evidence is generated.

## Reporting

* CSV inventory is produced.
* CSV findings are produced.
* CSV change history is produced.
* JSON report is produced.
* Run ID is recorded.
* UTC timestamp is recorded.
* Policy version is recorded.
* Compliance and remediation statuses remain separate.

## Security

* No credentials are hardcoded.
* Audit and remediation permissions can be separated.
* Least privilege is used.
* Reports are protected.
* Sensitive metadata is not carelessly logged.
* AWS-reserved tags are not rewritten.
* Production remediation is controlled.
* No destructive resource operations exist.

```text
   ↓

```

Once automation gains permission to modify AWS resources, the engineering standard must become much higher.

The safe model is:

```text
DISCOVER
   ↓
READ
   ↓
NORMALIZE
   ↓
VALIDATE
   ↓
RECOMMEND
   ↓
CHECK SOURCE OF TRUTH
   ↓
CHECK EXCLUSIONS
   ↓
CHECK ALLOWLIST
   ↓
DRY RUN
   ↓
APPROVE
   ↓
RE-READ CURRENT STATE
   ↓
CHANGE
   ↓
READ AGAIN
   ↓
VERIFY
   ↓
REPORT
```

The central production lesson is:

```text
Just because automation CAN change something
does not mean automation SHOULD change it.
```

And an equally important lesson is:

```text
A successful API call
does not prove
a correct operational decision.
```

The best automation is not the automation that makes the most changes.

It is the automation that knows:

```text
what to change,
what not to change,
when it lacks enough information,
when a human decision is required,
where the source of truth lives,
and how to prove that an approved change
produced the intended result.
```

That mindset prepares you perfectly for Project 5, **Unattached EBS Volume Detection**, where the stakes increase again because the automation will begin identifying infrastructure that may eventually become a candidate for destructive cleanup.
