# Project 3: IAM Security Auditing Automation

## Scenario

The security team has a recurring problem.

Every quarter, somebody has to manually inspect AWS IAM and answer questions such as:

* How many IAM users exist?
* Which users have console access?
* Which users have access keys?
* Which access keys are old?
* Which credentials appear unused?
* Which users do not have MFA?
* Which users belong to which groups?
* Which policies are attached directly to users?
* Which users have inline policies?
* Which roles exist?
* Which principals can assume those roles?
* Are any policies potentially too broad?
* Are wildcard permissions being used?
* Which findings require immediate investigation?
* Which findings simply require review?

For a small AWS account, engineers might inspect these things manually.

For an organization with many users, roles, groups, policies, service accounts, CI/CD identities, and automation workloads, manual inspection becomes inconsistent and difficult to repeat.

Security asks the DevOps team to build a repeatable IAM auditing system.

The goal is not:

```text
Find suspicious IAM configuration
        ↓
Delete it
```

The goal is:

```text
Discover
    ↓
Collect Evidence
    ↓
Analyze
    ↓
Classify
    ↓
Report
    ↓
Investigate
    ↓
Approve
    ↓
Remediate
    ↓
Verify
```

This project introduces one of the most important principles in infrastructure automation:

```text
Detection ≠ Remediation
```

If an access key is 180 days old, that does not automatically mean:

```text
Delete the key.
```

It means:

```text
Investigate the key.
```

The key may belong to:

* a production deployment system
* an old employee
* a CI/CD process
* a migration job
* a forgotten application
* a third-party integration
* an emergency account
* a legacy workload

Deleting credentials without understanding their dependencies can create a production outage.

# Part 1: Understand IAM Auditing from a DevOps Perspective

IAM controls who and what can perform actions inside AWS.

Conceptually:

```text
Principal
   |
   v
Authentication
   |
   v
Authorization
   |
   v
AWS Resource
```

Principals can include:

```text
Human
Workload
AWS Service
Federated Identity
IAM Role Session
IAM User
```

IAM auditing therefore asks:

```text
WHO
can do
WHAT
to WHICH RESOURCE
under WHICH CONDITIONS?
```

But DevOps engineers should ask another question:

```text
Is this identity still operationally necessary?
```

That matters because IAM is connected directly to production systems.

# Part 2: IAM Users, Groups, Roles, and Policies

Students must understand the basic model before automating it.

## IAM User

Represents an IAM identity with long-lived identity configuration.

Example:

```text
veriqta-legacy-deployer
```

A user may have:

* console credentials
* access keys
* group memberships
* attached managed policies
* inline policies
* MFA devices

## IAM Group

A collection of IAM users.

Example:

```text
DevOpsEngineers
```

A policy attached to the group can grant permissions to group members.

## IAM Role

A role is designed to be assumed.

Examples:

```text
EC2ApplicationRole
GitHubDeploymentRole
EKSAdminRole
ReadOnlyAuditRole
```

Roles are central to modern AWS workload authentication.

## IAM Policy

A policy contains authorization rules.

Simplified:

```json
{
  "Effect": "Allow",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::example/*"
}
```

# Part 3: Authentication and Authorization Are Different

Authentication asks:

```text
Who are you?
```

Authorization asks:

```text
What are you allowed to do?
```

An identity can authenticate successfully while having extremely limited permissions.

Another identity may authenticate successfully and have administrator-level permissions.

IAM auditing focuses heavily on authorization, credential hygiene, and identity lifecycle.

# Part 9: Understand Pagination

IAM APIs frequently paginate results.

Never assume:

```python
response = iam.list_users()
users = response["Users"]
```

contains every user.

Use Boto3 paginators.

Create:

```python
def paginate(
    client,
    operation_name,
    result_key,
    **kwargs
):
    paginator = client.get_paginator(
        operation_name
    )

    results = []

    for page in paginator.paginate(
        **kwargs
    ):
        results.extend(
            page.get(
                result_key,
                []
            )
        )

    return results
```

Now:

```python
users = paginate(
    iam,
    "list_users",
    "Users"
)
```

def calculate_age_days(
    create_date,
    now=None
):
    if not create_date:

    if now is None:

# Part 21: Detect Inactive Keys

Access keys have states such as:

```text
Active
Inactive
```

An inactive key is not necessarily dangerous.

It may be part of an intentional key-rotation process.

But an inactive key that remains indefinitely may indicate incomplete cleanup.

Classification example:

```text
Inactive access key
→ REVIEW
```

Do not automatically delete it.

# Part 22: Detect Old Active Keys

Define:

```python
ACCESS_KEY_REVIEW_DAYS = 90
ACCESS_KEY_HIGH_DAYS = 180
```

Then:

```python
def classify_key_age(
    age_days,
    status
):
    if age_days is None:
        return {
            "status": "REVIEW",
            "severity": "LOW"
        }

    if status == "Inactive":
        return {
            "status": "REVIEW",
            "severity": "LOW"
        }

    if age_days >= (
        ACCESS_KEY_HIGH_DAYS
    ):
        return {
            "status": "FAIL",
            "severity": "HIGH"
        }

    if age_days >= (
        ACCESS_KEY_REVIEW_DAYS
    ):
        return {
            "status": "REVIEW",
            "severity": "MEDIUM"
        }

    return {
        "status": "PASS",
        "severity": "INFO"
    }
```

Again, these thresholds represent our lab policy.

# Part 29: Wait for the Credential Report

Create:

```python
import time


def wait_for_credential_report(
    iam,
    attempts=10,
    delay_seconds=2
):
    for attempt in range(
        1,
        attempts + 1
    ):
        response = (
            iam.generate_credential_report()
        )

        state = response.get(
            "State"
        )

        if state == "COMPLETE":
            return True

        time.sleep(
            delay_seconds
        )

    return False
```

Production automation should avoid infinite waiting.

Use bounded retries.

# Part 34: Parse Boolean Values

Create:

```python
def parse_bool(
    value
):
    if value is None:
        return None

    normalized = (
        value.strip().lower()
    )

    if normalized == "true":
        return True

    if normalized == "false":
        return False

    return None
```

Never use:

```python
bool("false")
```

because:

```python
bool("false")
```

evaluates to:

```text
True
```

Any non-empty Python string is truthy.

This is a classic automation bug.

# Part 38: Identify Users Without MFA

A simplistic script might say:

```text
Every IAM user without MFA
→ HIGH
```

That can create noisy findings.

A better rule:

```text
IAM user
    +
Console password enabled
    +
MFA inactive
        ↓
Finding
```

Example:

```python
def evaluate_mfa(
    credential_row
):
    password_enabled = (
        has_console_password(
            credential_row
        )
    )

    mfa_active = has_mfa(
        credential_row
    )

    if (
        password_enabled is True
        and mfa_active is False
    ):
        return {
            "status": "FAIL",
            "severity": "HIGH",
            "message": (
                "Console-capable IAM "
                "user does not have "
                "MFA active."
            )
        }

    if (
        password_enabled is True
        and mfa_active is True
    ):
        return {
            "status": "PASS",
            "severity": "INFO",
            "message": (
                "MFA is active."
            )
        }

    return {
        "status": "PASS",
        "severity": "INFO",
        "message": (
            "No console password "
            "detected."
        )
    }
```

---

# Part 39: MFA Has More Context Than One Boolean

Do not teach students that:

```text
mfa_active = false
```

always means:

```text
Identity has no strong authentication.
```

Modern organizations may use federation and centralized identity systems instead of IAM users for human access.

The report should clearly identify what it is evaluating:

```text
IAM-user MFA configuration
```

not make unsupported claims about the organization's entire authentication architecture.

# Part 42: Build an Unused Credential Rule

For example:

```python
UNUSED_CREDENTIAL_DAYS = 90
```

Then:

```python
def evaluate_key_usage(
    last_used_date,
    key_status,
    now=None
):
    if key_status != "Active":
        return {
            "status": "REVIEW",
            "severity": "LOW",
            "message": (
                "Access key is inactive."
            )
        }

    if last_used_date is None:
        return {
            "status": "REVIEW",
            "severity": "MEDIUM",
            "message": (
                "No last-used timestamp "
                "was available."
            )
        }

    unused_days = days_since(
        last_used_date,
        now=now
    )

    if unused_days >= (
        UNUSED_CREDENTIAL_DAYS
    ):
        return {
            "status": "REVIEW",
            "severity": "MEDIUM",
            "message": (

```

Most importantly, students learn the production rule:

```text
DETECTION ≠ REMEDIATION
```

A security finding tells us:

```text
Something requires attention.
```

It does not automatically tell us:

```text
Destroy the resource.
```

The mature workflow is:

```text
Detect
   ↓
Collect Evidence
   ↓
Classify
   ↓
Report
   ↓
Identify Owner
   ↓
Investigate Dependencies
   ↓
Decide
   ↓
Approve
   ↓
Remediate
   ↓
Verify
```

That final distinction is what separates a useful security script from dangerous automation.

A script can identify a 300-day-old access key in seconds.

A production engineer asks the harder questions:

```text
Who owns it?

What uses it?

Why does it still exist?

What happens if we disable it?

Can we replace it with temporary credentials?

How do we test the replacement?

What is our rollback plan?

Who approves the change?

How do we verify the remediation?
```

That is the mindset students should carry into every remaining AWS automation project.
