# Project 5: Unattached EBS Volume Detection and Safe Cleanup Automation

## Scenario

The organization has been running workloads in AWS for several years.

EC2 instances are regularly:

* created
* replaced
* rebuilt
* scaled
* terminated
* migrated

But engineers discover a growing cost problem.

Some EBS volumes remain after the EC2 instances that used them are terminated.

For example:

```text
EC2 Instance
i-0123456789abcdef0
        |
        v
EBS Volume
vol-0123456789abcdef0
```

The EC2 instance is terminated.

But:

```text
EBS Volume
vol-0123456789abcdef0
```

remains.

The volume may no longer be attached to anything.

AWS continues storing the data.

The organization continues paying for the storage.

One abandoned volume may not matter much.

But imagine:

```text
Development accounts
Testing accounts
Production accounts
Sandbox accounts
Multiple AWS regions
Hundreds of engineers
Years of infrastructure changes
```

Now the environment may contain:

```text
10 GiB
100 GiB
500 GiB
2 TiB
```

unattached volumes scattered across multiple regions.

The DevOps team needs automation that can answer:

```text
Which EBS volumes are unattached?

How old are they?

How large are they?

What type are they?

Who owns them?

Which application created them?

Which environment do they belong to?

How long have they been unattached?

Should they be investigated?

Should they be excluded?

Should they be snapshotted?

Could they eventually be deleted?

How much storage is potentially being wasted?
```

Students will build an EBS cost-waste detector.

But the project must never assume:

```text
Unattached = Safe to delete
```

That assumption is dangerous.

An unattached EBS volume might contain:

* production data
* a database filesystem
* logs
* forensic evidence
* backups
* application data
* migration data
* manually preserved data
* disaster-recovery data
* data waiting to be attached to a replacement instance

Therefore the project follows:

```text
DETECT
   ↓
INVESTIGATE
   ↓
SNAPSHOT
   ↓
APPROVE
   ↓
DELETE
   ↓
VERIFY
```

Never:

```text
DETECT
   ↓
DELETE
```

The central lesson is:


It cannot automatically understand every business reason why the resource exists.

For example:



# 3. Understand EC2 and EBS

Amazon Elastic Block Store provides block storage commonly used by EC2 instances.

Conceptually:

```text
EC2
 |
 +---- Root EBS Volume
 |
 +---- Data EBS Volume
 |
 +---- Additional EBS Volume
```

An EC2 instance may have one or several EBS volumes.

Example:

```text
EC2 Instance
i-veriqta-example
      |
      +---- /dev/xvda
      |       |
      |       v
      |    Root Volume
      |
      +---- /dev/xvdf
              |
              v
           Data Volume
```

Volumes have independent identities.

Example:

```text
vol-0123456789abcdef0
```

---

# 4. EBS Volumes Have Their Own Lifecycle

An important beginner lesson:

```text
EC2 lifecycle
```

and:

```text
EBS lifecycle
```

are related but not identical.

An instance may disappear while a volume remains.

Whether a volume is automatically deleted can depend on the block-device configuration and how the resource was provisioned.

This is why orphaned storage can accumulate.

---

# 5. Root Volumes and `DeleteOnTermination`

An EC2 block-device mapping can contain:

```text
DeleteOnTermination
```

Conceptually:

```text
DeleteOnTermination = true
```

means the associated EBS volume is configured to be deleted when that instance is terminated.

Whereas:

```text
DeleteOnTermination = false
```

can allow the volume to remain.

Students should understand this because some unattached volumes exist intentionally due to lifecycle configuration.

# 9. Separate Detection From Cleanup

Our CLI should eventually support:

```bash
python scripts/ebs_cleanup.py --mode audit
```

and:

```bash
python scripts/ebs_cleanup.py --mode snapshot
```

and:

```bash
python scripts/ebs_cleanup.py --mode delete
```

These modes should have different capabilities.

## Audit

Read only.

## Snapshot

May create snapshots for explicitly approved candidates.

## Delete

May delete only explicitly approved volumes that pass every safety gate.

This separation dramatically reduces accidental destructive execution.

Audit mode should use read-only permissions wherever practical.



```text

```

The exact production policy should be restricted according to account, resource, tagging controls, role design, and organizational requirements.

# 12. Separate IAM Roles

A stronger production design:

```text
EBS Audit Role
     |
     +---- Describe only


EBS Snapshot Role
     |
     +---- Describe
     +---- Create approved snapshots


EBS Cleanup Role
     |
     +---- Describe
     +---- Restricted DeleteVolume
```

Do not give the ordinary inventory script deletion privileges simply because deletion might eventually be needed.

---

# 13. Why This Matters

If the audit process is compromised:

```text
Read-only role
```

limits the attacker's ability to destroy volumes.

The destructive role should have a much smaller operational window and stricter authorization.

# 20. Detect Unattached Volumes

A simple first check:

```python
def is_unattached(volume):
    return (
        volume.get("State")
        == "available"
        and len(
            volume.get(
                "Attachments",
                []
```

# 26. Calculate Volume Age

```python
from datetime import datetime, timezone


def calculate_age_days(
    create_time,
    now=None
):
    if create_time is None:
        return None

    if now is None:
        now = datetime.now(
            timezone.utc
        )

    if (
        create_time.tzinfo
        is None
    ):
        create_time = (
            create_time.replace(
                tzinfo=timezone.utc
            )
        )

    delta = now - create_time

    return delta.days
```

# 38. Implement Exclusion Detection

```python
def has_exclusion_tag(
    tags,
    exclusion_rules
):
    for key, allowed_values in (
        exclusion_rules.items()
    ):
        actual = tags.get(key)

        if (
            actual is not None
            and actual
            in allowed_values
        ):
            return True, key

    return False, None
```

# 41. Candidate Evaluation

Conceptually:

```python
def classify_volume(
    record,
    policy
):
    if record["state"] != "available":
        return "ATTACHED"

    excluded, _ = has_exclusion_tag(
        record["tags"],
        policy.get(
            "exclusion_tags",
            {}
        )
    )

    if excluded:
        return "EXCLUDED"

    if (
        record.get("environment")
        in policy.get(
            "protected_environments",
            []
        )
    ):
        return "PROTECTED"

    age = record.get(
        "volume_age_days"
    )

    minimum = policy.get(
        "minimum_age_days",
        30
    )

    if age is None:
        return "INVESTIGATE"

    if age < minimum:
        return "UNATTACHED_NEW"

    return "CLEANUP_CANDIDATE"
```

For production use, replace creation-age-only logic with better historical evidence where possible.

# 46. Collect One Region

```python
from botocore.exceptions import (
    BotoCoreError,
    ClientError
)


def collect_region_volumes(
    session,
    region,
    logger
):
    ec2 = session.client(
        "ec2",
        region_name=region
    )

    records = []

    try:
        volumes = list_volumes(
            ec2
        )

        for volume in volumes:
            records.append(
                normalize_volume(
                    volume,
                    region
                )
            )

    except ClientError as error:
        logger.error(
            "EBS scan failed "
            "region=%s error=%s",
            region,
            error
        )

        raise

    except BotoCoreError as error:
        logger.error(
            "AWS SDK failure "
            "region=%s error=%s",
            region,
            error
        )

        raise

    return records
```

# 76. Build a Safety Gate

```python
def deletion_safety_check(
    volume,
    snapshot,
    approved,
    excluded,
    dry_run
):
    reasons = []

    if not approved:
        reasons.append(
            "NOT_APPROVED"
        )

    if excluded:
        reasons.append(
            "EXCLUDED"
        )

    if volume.get("State") != (
        "available"
    ):
        reasons.append(
            "VOLUME_NOT_AVAILABLE"
        )

    if volume.get(
        "Attachments",
        []
    ):
        reasons.append(
            "VOLUME_HAS_ATTACHMENTS"
        )

    if not snapshot_is_complete(
        snapshot
    ):
        reasons.append(
            "SNAPSHOT_NOT_COMPLETE"
        )

    return {
        "safe_to_proceed": (
            len(reasons) == 0
        ),
        "reasons": reasons,
        "dry_run": dry_run
    }
```

This is only one layer. Production authorization must exist outside this function too.

# 130. Production Guardrail

```python
def check_blast_radius(
    approved_volumes,
    max_count,
    max_gib
):
    count = len(
        approved_volumes
    )

    total_gib = sum(
        item["size_gib"]
        for item
        in approved_volumes
    )

    return {
        "count": count,
        "total_gib": total_gib,
        "count_allowed": (
            count <= max_count
        ),
        "capacity_allowed": (
            total_gib <= max_gib
        )
    }
```

# 198. Project 5 Complete

Students began with a simple cost question:

```text
Are we paying for EBS volumes
```

They discovered that the technical detection is relatively easy:

```text
DescribeVolumes
      ↓
State = available
      ↓
Attachments = []
```

The difficult engineering question is:

```text
What are we allowed to do about it?
```

That requires:

```text
Ownership

Historical context

Tagging

Age thresholds

Cost awareness

Exclusions

Infrastructure-as-code awareness

Kubernetes awareness

Backup requirements

Security holds

Approval

Snapshots

Verification

IAM separation

Dry runs

Blast-radius controls

Audit evidence
```

The most important lesson from Project 5 is:

```text
UNATTACHED
≠
UNUSED

UNUSED
≠
UNIMPORTANT

OLD
≠
ABANDONED

CANDIDATE
≠
APPROVED

SNAPSHOT REQUESTED
≠
SNAPSHOT COMPLETE

DELETE REQUESTED
≠
DELETE VERIFIED
```

The production workflow remains:

```text
DETECT
   ↓
INVESTIGATE
   ↓
SNAPSHOT
   ↓
VERIFY SNAPSHOT
   ↓
APPROVE
   ↓
REVALIDATE
   ↓
DELETE
   ↓
VERIFY DELETION
   ↓
REPORT
```

Never:

```text
if volume["State"] == "available":
    delete(volume)
```

The goal of good infrastructure automation is not to make destructive actions faster.

The goal is to make **correct, controlled, recoverable, observable, and auditable decisions**.

A junior engineer may look at an unattached 500 GiB EBS volume and think:

```text
Waste.
Delete it.
```

A production-minded engineer asks:

```text
Why is it unattached?

How long has it actually been unattached?

Who owns it?

What application used it?

Is it referenced by Terraform?

Is Kubernetes expecting it?

Is there a preservation tag?

Is there a security or legal hold?

Is this the correct AWS account?

Is this production?

Has somebody approved cleanup?

Do we have a verified recovery snapshot?

Has the resource changed since approval?

What is our blast radius?

Can we prove exactly what happened afterward?
```

That difference in thinking is the real purpose of Project 5.

The student is no longer simply learning:

```text
Python + Boto3
```

They are learning:

```text
Python
   +
AWS APIs
   +
Infrastructure State
   +
FinOps
   +
Safety Engineering
   +
Change Control
   +
Recovery
   +
Verification
   +
Production Judgment
```

And that prepares them for **Project 6: Security Group Auditing**, where the challenge changes from identifying potential cost waste to identifying potentially dangerous network exposure without breaking legitimate production access.
