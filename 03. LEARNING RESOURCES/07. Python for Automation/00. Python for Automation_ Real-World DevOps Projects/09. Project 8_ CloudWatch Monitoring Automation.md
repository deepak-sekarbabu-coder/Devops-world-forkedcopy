# Project 8: CloudWatch Monitoring Automation

## Scenario

The infrastructure team has a growing AWS environment.

Every week, engineers deploy:

* EC2 instances
* RDS databases
* application servers
* production workloads
* staging environments
* temporary environments
* new database instances

The infrastructure itself is being automated, but monitoring is still being configured manually.

An engineer creates an EC2 instance.

Someone must remember to create:

```text
CPU alarm
Status-check alarm
```

A database is deployed.

Someone must remember to create:

```text
CPU alarm
Connection alarm
Storage alarm
Memory alarm
```

Sometimes they remember.

Sometimes they forget.

Sometimes one engineer uses:

```text
CPU > 70%
```

while another uses:

```text
CPU > 90%
```

Some alarms evaluate for:

```text
5 minutes
```

while others evaluate for:

```text
30 minutes
```

Some notify the correct SNS topic.

Others point to an old topic.

Some production resources have excellent monitoring.

Others have none.

The problem is no longer:

```text
Can engineers create CloudWatch alarms?
```

The problem is:

```text
Can the organization guarantee
consistent monitoring coverage?
```

Students will solve this by building a CloudWatch monitoring automation system.

The automation will:

```text
Discover Resources
        ↓
Classify Environment
        ↓
Determine Monitoring Policy
        ↓
Discover Existing Alarms
        ↓
Compare Expected vs Actual
        ↓
Create Missing Alarms
        ↓
Update Incorrect Alarms
        ↓
Skip Ineligible Resources
        ↓
Identify Obsolete Alarms
        ↓
Verify Configuration
        ↓
Generate Monitoring Coverage Report
```

This project introduces an important DevOps principle:

```text
Infrastructure automation
without monitoring automation
is incomplete automation.
```

Without automation, monitoring often becomes:

```text
Deploy Resource
      ↓
Remember Monitoring
      ↓
Maybe Create Alarm
      ↓

      ↓
```

The desired model is:

```text
Deploy Resource
      ↓
Resource Discovered
      ↓
Monitoring Policy Applied
      ↓

      ↓
Existing Alarms Compared
      ↓
Missing Alarms Created
      ↓
Incorrect Alarms Updated
      ↓
Configuration Verified
      ↓
Coverage Report Generated
```

Monitoring becomes part of infrastructure operations rather than an optional task.

# 7. Metrics

A metric is a time-ordered set of data points representing some measurement.

Examples:

```text
EC2 CPU utilization

RDS CPU utilization

Database connections

Free storage space

Instance status-check failures
```

Think:

```text
Resource
   ↓
Measurement
   ↓
Metric
   ↓
Datapoints Over Time
```

---

# 8. Metric Example

An EC2 instance might produce:

```text
12:00 CPUUtilization = 32%

12:05 CPUUtilization = 47%

12:10 CPUUtilization = 86%

12:15 CPUUtilization = 92%

12:20 CPUUtilization = 94%
```

CloudWatch stores this time-series data.

An alarm evaluates that data according to rules.

---

# 9. Metrics Are Not Alarms

This distinction is essential.

```text
Metric
=
measurement
```

Example:

```text
CPUUtilization = 92%
```

An alarm is:

```text
Rule applied to metric data.
```

Example:

```text
If CPUUtilization > 85%
for 3 evaluation periods,
enter ALARM state.
```

# 12. Paginate Metric Discovery

```python
def list_metrics(
    cloudwatch_client,
    namespace=None
):
    paginator = (
        cloudwatch_client
        .get_paginator(
            "list_metrics"
        )
    )

    kwargs = {}

    if namespace:
        kwargs["Namespace"] = namespace

    metrics = []

    for page in paginator.paginate(
        **kwargs
    ):
        metrics.extend(
            page.get(
                "Metrics",
                []
            )
        )

    return metrics
```

Example:


This tells CloudWatch:


# 19. Retrieve EC2 CPU Data

Example:

```python
from datetime import (
    datetime,
    timedelta,
    timezone
)


def get_ec2_cpu_statistics(
    cloudwatch_client,
    instance_id
):
    end_time = datetime.now(
        timezone.utc
    )

    start_time = (
        end_time
        - timedelta(
            hours=1
        )
    )

    response = (
        cloudwatch_client
        .get_metric_statistics(
            Namespace="AWS/EC2",
            MetricName="CPUUtilization",
            Dimensions=[
                {
                    "Name":
                        "InstanceId",
                    "Value":
                        instance_id
                }
            ],
            StartTime=start_time,
            EndTime=end_time,
            Period=300,
            Statistics=[
                "Average"
            ]
        )
    )

    return response.get(
        "Datapoints",
        []
    )
```

# 36. Thresholds

A threshold defines the boundary an alarm evaluates.

Example:

```text
CPU > 85%
```

Threshold:

```text
85
```

Comparison:

```text
GreaterThanThreshold
```

---

# 37. Comparison Operators

Examples conceptually include:

```text
GreaterThanThreshold

GreaterThanOrEqualToThreshold

LessThanThreshold

LessThanOrEqualToThreshold
```

The correct operator depends on the metric.

Example:

```text
CPU:
GreaterThanThreshold
```

Example:

```text
FreeStorageSpace:
LessThanThreshold
```

---

# 38. Thresholds Must Match Metric Direction

For CPU:

```text
High value
=
potential problem
```

For free storage:

```text
Low value
=
potential problem
```

Therefore:

```text
CPU > threshold
```

versus:

```text
FreeStorage < threshold
```

Do not blindly reuse comparison operators.

---

# 39. Evaluation Periods

Suppose:

```text
Period:
5 minutes

EvaluationPeriods:
3
```

The alarm evaluates multiple periods rather than reacting to one isolated data point.

This can reduce noise.

---

# 40. Datapoints to Alarm

A mature configuration may use:

```text
EvaluationPeriods:
5

DatapointsToAlarm:
3
```

Conceptually:

```text
3 breaching datapoints
within 5 evaluated periods
```

may trigger the alarm.

This can be useful when workloads fluctuate.

---

# 41. Alarm Sensitivity

Too sensitive:

```text
CPU > 70%
for one minute
```

might generate noisy alerts.

Too insensitive:

```text
CPU > 99%
for one hour
```

might react too late.

Monitoring design balances:

```text
Detection speed
        ↕
Alert noise
```

# 42. Missing Data

CloudWatch alarms need defined behavior when expected datapoints are missing.

Possible strategies conceptually include treating missing data as:

```text
missing

notBreaching

breaching

ignore
```

This is a critical operational decision.

---

# 43. Why Missing Data Matters

Suppose a metric disappears because:

```text
Resource stopped

Resource deleted

Agent failed

Metric stopped publishing

Service behavior changed
```

Should the alarm:

```text
Alarm?

Remain unchanged?

Treat absence as healthy?

Move to insufficient data?
```

There is no universal answer.

It depends on the metric.

---

# 44. Missing Data Is Not Automatically Healthy

A dangerous configuration is:

```text
No data
→ everything is fine
```

For some availability signals, missing telemetry itself may be meaningful.

For other metrics, absence can be expected.

Configure intentionally.

# 52. Sanitize Alarm Names

Resource identifiers or application names may contain characters unsuitable for your naming standard.

Create a helper:

```python
import re


def sanitize_name(value):
    value = value.lower()

    value = re.sub(
        r"[^a-z0-9-_]+",
        "-",
        value
    )

    return value.strip("-")
```

Apply your organization's naming constraints consistently.

# 55. Idempotency

Running:

```bash
python scripts/cloudwatch_monitoring.py
```

ten times should not create ten copies of the same logical alarm.

The desired result is:


```python
def ec2_monitoring_eligible(
    instance
):
    state = instance.get(
        "state"
    )

    tags = instance.get(
        "tags",
        {}
    )

    if state != "running":

            False,
            "NOT_RUNNING"

        tags.get(

    return (
        True,
        "ELIGIBLE"
    )
```

# 132. Verify Alarm

```python
def get_alarm(
    cloudwatch,
    alarm_name
):
    response = (
        cloudwatch.describe_alarms(
            AlarmNames=[
                alarm_name
            ],
            AlarmTypes=[
                "MetricAlarm"
            ]
        )
    )

    alarms = response.get(
        "MetricAlarms",
        []
    )

    if not alarms:
        return None

    return alarms[0]
```

Then compare against expected configuration.
