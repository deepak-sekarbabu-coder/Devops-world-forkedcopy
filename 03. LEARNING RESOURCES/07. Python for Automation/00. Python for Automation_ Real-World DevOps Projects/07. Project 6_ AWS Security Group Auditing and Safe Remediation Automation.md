# Project 6: AWS Security Group Auditing and Safe Remediation Automation

## Scenario

The organization has been running workloads in AWS for several years.

During that time:

* engineers created EC2 instances
* applications were migrated
* environments were rebuilt
* load balancers were introduced
* databases were moved
* Kubernetes clusters were deployed
* temporary troubleshooting rules were added
* vendors required temporary access
* development environments became permanent
* old applications were retired
* IP addresses changed
* security groups were copied
* infrastructure ownership changed

Security-group rules accumulated.

Some rules were intentionally created.

Some were temporary.

Some are no longer understood.

Some expose services far more broadly than necessary.

Examples include:

```text
SSH
TCP/22
Source: 0.0.0.0/0
```

```text
RDP
TCP/3389
Source: 0.0.0.0/0
```

```text
All Traffic
All Ports
Source: 0.0.0.0/0
```

and IPv6 equivalents:

```text
::/0
```

The security team asks:

> Which security groups expose sensitive services, which resources use those groups, which findings actually represent risk, and what should we change without breaking production?

Manually opening every security group in the AWS console is not scalable.

Students will build an automated security-group auditing system.

The system will:

```text
Discover Security Groups
        ↓
Parse Rules
        ↓
Understand Sources/Destinations
        ↓
Detect Exposure
        ↓
Identify Resources
        ↓
Apply Security Policy
        ↓
Reduce False Positives
        ↓
Assign Severity
        ↓
Generate Findings
        ↓
Recommend Remediation
        ↓
Dry Run
        ↓
Require Approval
        ↓
Revalidate
        ↓
Controlled Remediation
        ↓
Verify
        ↓
Report
```

The project must never assume:

```text
Public rule = automatically delete
```

because a public rule might be intentional.

For example:

```text
ALB
TCP/443
0.0.0.0/0
```

may be exactly what an internet-facing web application requires.

But:

```text
EC2
TCP/22
0.0.0.0/0
```

usually deserves much stronger scrutiny.

The central engineering lesson is:

```text
Exposure detection
≠
Risk understanding
≠
Remediation authorization
```

# 2. Security Groups in Plain English

A security group is a stateful virtual firewall associated with supported AWS resources.

At a simplified level:

```text
Internet
   |
   |
Security Group
   |
   v
EC2 Instance
```

The security group controls permitted network traffic.

There are two major directions:

```text
Inbound
```

and:

```text
Outbound
```

Inbound rules determine traffic allowed toward the associated resource.

Outbound rules determine traffic the resource is allowed to send.

---

# 3. Security Groups Are Stateful

This is fundamental.

Suppose an inbound rule allows:

```text
Client
   |
   | TCP/443
   v
EC2
```

Return traffic for that allowed connection is automatically permitted by the stateful behavior of security groups.

You do not normally create a corresponding inbound/outbound pair simply for return traffic.

Students must understand this before trying to audit network controls.

---

# 4. Security Groups Are Allow-Based

Security groups define permitted traffic.

They are not ordered firewall rule lists where one rule explicitly denies another.

Conceptually:

```text
ALLOW TCP/443 from 0.0.0.0/0
```

means HTTPS traffic matching that rule is permitted.

You should not design the auditor as if it is searching for:

```text
ALLOW
DENY
ALLOW
DENY
```

rules in priority order.

That is not the security-group model.

---

# 5. Security Groups Operate in a VPC Context

A security group belongs to a VPC.

Useful fields include:

```text
GroupId
GroupName
Description
VpcId
IpPermissions
IpPermissionsEgress
Tags
```

Example:

```text
Group ID:
sg-0123456789abcdef0

Name:
veriqta-web-sg

VPC:
vpc-0123456789abcdef0
```

The VPC context matters when understanding references and resource associations.

# 6. Inbound Rules

Example:

```text
Type:
HTTPS

Protocol:
TCP

Port:
443

Source:
0.0.0.0/0
```

This means IPv4 clients from anywhere can potentially reach TCP/443, assuming the resource is otherwise network reachable.

Notice the wording:

```text
potentially reach
```

A security-group rule alone does not prove end-to-end internet reachability.

Other factors matter.

---

# 7. Security Group Exposure Is Not the Entire Network Path

Suppose:

```text
Security Group:
TCP/22 from 0.0.0.0/0
```

But the EC2 instance:

```text
has no public IP
```

and sits in:

```text
a private subnet
```

The rule is still overly broad and worth reviewing.

But it does not necessarily prove that the instance is currently reachable directly from the public internet.

Therefore mature reporting distinguishes:

```text
Security-group exposure
```

from:

```text
Confirmed end-to-end internet reachability
```

Project 6 primarily audits security-group configuration.

---

# 8. Outbound Rules

Example:

```text
Protocol:
All

Destination:
0.0.0.0/0
```

This is common in default or permissive security-group configurations.

Whether it is acceptable depends on:

* workload requirements
* environment
* organizational policy
* data sensitivity
* egress architecture
* network inspection controls
* proxy/firewall architecture

Do not automatically classify every broad outbound rule as a critical vulnerability.

# 11. Design Two Modes

Like Projects 4 and 5, separate observation from modification.

```bash
python scripts/security_group_audit.py \
  --mode audit
```

and:

```bash
python scripts/security_group_audit.py \
  --mode remediate
```

Audit mode:

```text
READ ONLY
```

Remediation mode:

```text
CONTROLLED CHANGE
```

The auditor should be useful even if remediation permissions are never granted.

---

# 12. IAM Design

The audit role should use read-only permissions required for the resources being inspected.

For the core security-group audit, students need permission to inspect things such as:

```text
EC2 security groups
network interfaces
EC2 instances
VPC information
```

A remediation role requires additional permission to revoke or modify explicitly approved security-group rules.

Production principle:

```text
Audit permissions
≠
Remediation permissions
```

Do not give `RevokeSecurityGroupIngress` to a read-only reporting process just because a future workflow might use it.

---

# 13. Separate Security Roles

A stronger architecture:

```text
Security Audit Role
        |
        +---- Describe only


Security Remediation Role
        |
        +---- Describe
        +---- Restricted rule modification
```

The remediation role should be invoked only during an approved change.

# 20. Normalize Rules

Instead of making every detector understand raw AWS dictionaries, convert permissions into predictable records.

Example:

```python
{
    "direction": "inbound",
    "protocol": "tcp",
    "from_port": 22,
    "to_port": 22,
    "source_type": "ipv4",
    "source": "0.0.0.0/0"
}
```

This dramatically simplifies later policy evaluation.

```text

```

This is extremely common in tiered architectures.

Example:

```text

   |
```


# 27. Parse an Entire Security Group

```python
def normalize_security_group(
    security_group,
    region
):
    inbound = []
    outbound = []

    for permission in (
        security_group.get(
            "IpPermissions",
            []
        )
    ):
        inbound.extend(
            parse_permission(
                permission,
                "inbound"
            )
        )

    for permission in (
        security_group.get(
            "IpPermissionsEgress",
            []
        )
    ):
        outbound.extend(
            parse_permission(
                permission,
                "outbound"
            )
        )

    tags = normalize_tags(
        security_group.get(
            "Tags",
            []
        )
    )

    return {
        "region": region,
        "group_id":
            security_group.get(
                "GroupId"
            ),
        "group_name":
            security_group.get(
                "GroupName"
            ),
        "description":
            security_group.get(
                "Description"
            ),
        "vpc_id":
            security_group.get(
                "VpcId"
            ),
        "tags": tags,
        "inbound_rules": inbound,
        "outbound_rules": outbound
    }
```

Now detection logic works against a stable internal model.

# 28. Understand IPv4 CIDRs

A CIDR such as:

```text
10.0.0.0/8
```

represents a network range.

A very important CIDR is:

```text
0.0.0.0/0
```

This represents all IPv4 addresses.

For inbound rules it means:

```text
Any IPv4 source
```

subject to the other rule conditions.

---

# 29. Understand IPv6 CIDRs

IPv6 has the equivalent:

```text
::/0
```

This represents all IPv6 addresses.

A security scanner that checks only:

```text
0.0.0.0/0
```

is incomplete.

Always evaluate both:

```text
IPv4
0.0.0.0/0

IPv6
::/0
```

# 30. Public CIDR Detection

```python
def is_world_cidr(
    source

    return source in {
        "0.0.0.0/0",
```

Consider:

```text

0.0.0.0/0
```

That may be intentional.


# 32. Detect SSH

SSH normally uses:

```text
TCP/22
```

Do not check only:

```python
from_port == 22
```

```text
20-30
```

# 33. Port Range Helper

```python
def port_in_range(
    target_port,
    from_port,
    to_port
):
    if (
        from_port is None
        or to_port is None
    ):
        return False

    return (
        from_port
        <= target_port
        <= to_port
    )
```

Now:

```text
22-22
```

matches.

So does:

```text
20-30
```

---

# 34. Detect Public SSH

```python
def is_public_ssh(
    rule
):
    return (
        rule["direction"]
        == "inbound"
        and rule["protocol"]
        in {"tcp", "6"}
        and is_world_cidr(
            rule["source"]
        )
        and port_in_range(
            22,
            rule["from_port"],
            rule["to_port"]
        )
    )
```

# 42. Calculate Port Range Size

```python
def port_range_size(
    from_port,
    to_port
):
    if (
        from_port is None
        or to_port is None
    ):
        return None

    return (
        to_port
        - from_port
        + 1
    )
```

Examples:

```text
22-22
1 port

8000-8010
11 ports

1-65535
65,535 ports
```

---

# 43. Detect Broad Public Port Ranges

Example:

```python
def is_broad_public_range(
    rule,
    threshold=100
):
    if not is_world_cidr(
        rule["source"]
    ):
        return False

    size = port_range_size(
        rule["from_port"],
        rule["to_port"]
    )

    if size is None:
        return False

    return size >= threshold
```

The threshold should be policy-driven.

# 48. ICMP

ICMP rules use different semantics from normal TCP/UDP port ranges.

```python
def list_network_interfaces(
    ec2_client

        ec2_client.get_paginator(
            "describe_network_interfaces"
```

# 56. Usage Mapping Function

```python
def build_sg_usage_map(
    interfaces
):
    usage = {}

    for interface in interfaces:
        attachment = (
            interface.get(
                "Attachment",
                {}
            )
        )

        for group in interface.get(
            "Groups",
            []
        ):
            group_id = group.get(
                "GroupId"
            )

            if not group_id:
                continue

            usage.setdefault(
                group_id,
                []
            )

            usage[group_id].append(
                {
                    "eni_id":
                        interface.get(
                            "NetworkInterfaceId"
                        ),
                    "interface_type":
                        interface.get(
                            "InterfaceType"
                        ),
                    "description":
                        interface.get(
                            "Description"
                        ),
                    "private_ip":
                        interface.get(
                            "PrivateIpAddress"
                        ),
                    "instance_id":
                        attachment.get(
                            "InstanceId"
                        ),
                    "status":
                        interface.get(
                            "Status"
                        )
                }
            )

    return usage
```

# 65. Example CIDR Helper

```python
import ipaddress


def cidr_contains(
    parent,
    child
):
    try:
        parent_network = (
            ipaddress.ip_network(
                parent,
                strict=False
            )
        )

        child_network = (
            ipaddress.ip_network(
                child,
                strict=False
            )
        )

        return (
            child_network.subnet_of(
                parent_network
            )
        )

    except ValueError:
        return False
```

# 97. Rule Revocation

For an explicitly approved IPv4 ingress rule, the remediation process may eventually call the appropriate EC2 security-group ingress revocation API.

The dangerous function should be isolated.

Conceptually:

```python
def revoke_ipv4_ingress(
    ec2_client,
    group_id,
    protocol,
    from_port,
    to_port,
    cidr
):
    return (
        ec2_client
        .revoke_security_group_ingress(
            GroupId=group_id,
            IpPermissions=[
                {
                    "IpProtocol":
                        protocol,
                    "FromPort":
                        from_port,
                    "ToPort":
                        to_port,
                    "IpRanges": [
                        {
                            "CidrIp":
                                cidr
                        }
                    ]
                }
            ]
        )
    )
```

Only an approved remediation workflow should call this function.
