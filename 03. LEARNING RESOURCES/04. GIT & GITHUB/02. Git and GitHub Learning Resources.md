## What It Is

Git and GitHub are related technologies, but they are not the same thing.

**Git** is a distributed version control system used to track changes to files over time. It allows engineers to create commits, work with branches, compare changes, merge development histories, restore previous versions, and collaborate without overwriting one another's work.

**GitHub** is a cloud-based development and collaboration platform built around Git repositories. It provides repository hosting and additional capabilities such as:

- Pull requests
- Code reviews
- Issues
- Discussions
- GitHub Actions
- Releases
- Packages
- Projects
- Security scanning
- Repository permissions
- Branch protection
- Rulesets
- Webhooks
- APIs

In DevOps, Git repositories frequently become the source of truth for application code, infrastructure definitions, deployment configuration, automation, documentation, and operational changes.

---

## What It Does

Git records and manages changes to files.

Git allows engineers to:

- Initialize repositories
- Clone repositories
- Track files
- Stage changes
- Create commits
- Create branches
- Switch between branches
- Merge branches
- Rebase commits
- Compare changes
- Restore previous versions
- Tag releases
- Work with remote repositories
- Resolve merge conflicts
- Inspect repository history

GitHub extends Git with remote collaboration and software delivery capabilities.

GitHub allows teams to:

- Host Git repositories
- Collaborate through pull requests
- Review changes
- Protect important branches
- Manage repository access
- Track issues
- Manage projects
- Publish releases
- Store packages
- Run CI/CD workflows

- Integrate engineering tools
- Maintain technical documentation

## Why Engineers Use It

Git is fundamental to modern DevOps workflows because infrastructure and application changes should be versioned, reviewable, reproducible, and auditable.

DevOps engineers commonly store the following in Git:

- Application source code
- Terraform configurations

- Ansible playbooks
- Kubernetes manifests

- Docker Compose files
- CI/CD pipelines
- GitHub Actions workflows
- Jenkinsfiles
- Argo CD configuration
- Shell scripts
- Python automation
- YAML configuration
- Documentation
- Runbooks
- Policy definitions

GitHub provides the collaboration and automation layer around these repositories.

Together, Git and GitHub allow engineering teams to move infrastructure and software changes through controlled workflows rather than making undocumented changes directly in production.

## Production Notes

Git should be treated as infrastructure for engineering change management, not simply as a place to save files.

In mature DevOps environments, Git often becomes a source of truth for:

* Application code
* Infrastructure
* Kubernetes configuration
* CI/CD pipelines
* Deployment configuration
* Security policies
* Automation
* Documentation

Production changes should normally move through controlled workflows.

For example:

```text
Change
  |
Branch
  |
Commit
  |
Push
  |
Pull Request
  |
Automated Checks
  |
Review
  |
Approval
  |
Merge
  |
Deployment
  |
Verification
```

Engineers should understand Git history well enough to investigate:

* Who changed something?
* What changed?
* When did it change?
* Why was it changed?
* Which commit introduced the problem?
* Which release contains the change?
* Can the change be safely reverted?

Commands such as:

```bash
git log
git show
git diff
git blame
git bisect
git reflog
```

can become important troubleshooting tools.

Git should also be connected to production observability.

When a deployment causes an incident, engineers should be able to correlate the affected deployment with the corresponding:

* Commit
* Pull request
* Pipeline
* Artifact
* Release
* Infrastructure change

## Security Notes

Git repositories can contain some of an organization's most sensitive engineering information.

Important security practices include:

* Never commit passwords
* Never commit API keys
* Never commit cloud credentials
* Never commit private SSH keys
* Never commit database passwords
* Never commit production secrets
* Never place secrets in Terraform files
* Never place secrets directly in Kubernetes manifests
* Use `.gitignore` appropriately
* Protect important branches
* Require pull-request reviews where appropriate
* Use least-privilege repository permissions
* Protect CI/CD credentials
* Protect GitHub Actions secrets
* Review third-party GitHub Actions before using them
* Pin third-party Actions appropriately
* Restrict self-hosted runner access
* Use short-lived credentials where possible
* Use OpenID Connect where appropriate
* Enable dependency scanning
* Enable secret scanning where available
* Enable code scanning where appropriate
* Review repository access regularly
* Protect release workflows
* Audit sensitive repository changes

Removing a secret from the latest version of a file does not necessarily remove it from Git history.

If a credential is committed accidentally:

1. Treat the credential as compromised.
2. Revoke or rotate it immediately.
3. Investigate its use.
4. Remove the sensitive data from repository history when required.
5. Review how the secret entered the repository.
6. Add controls to prevent recurrence.
